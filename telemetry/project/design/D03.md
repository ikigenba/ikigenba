# Decision 3 — The loopback ingest endpoint

## Decision.

`internal/ingest` implements the receiving half of the protocol's ingest API
(research §1.4) and nothing else.

```go
// Mount registers the loopback-only ingest route on the chassis router.
// Exclusion from request recording is NOT done here: it is the composition
// root's Spec.TelemetryExclude entry (D1).
func Mount(rt *appkit.Router, store *db.Store, clock telemetry.Clock)

type Request struct {
    Records []record.Record `json:"records"`
    Dropped int64           `json:"dropped,omitempty"`
}

type Response struct {
    Stored   int `json:"stored"`
    Rejected int `json:"rejected"`
}
```

**Route:** `POST /ingest`, registered through `Router.HandleLoopback`, which
wraps appkit's `LoopbackOnly` guard — any request carrying `X-Forwarded-Proto`
(nginx stamps it on everything it proxies) gets a bare 404 without the handler
running. telemetry writes no guard of its own. D6 additionally gives the nginx
fragment no location that could reach `/ingest`, so the path is unreachable from
outside by two independent mechanisms.

**Never self-recorded.** The path `/ingest` is listed in the composition root's
`Spec.TelemetryExclude` (D1), which the chassis passes to
`server.Options.RecordExclude`, so posting a batch produces no `request` record
about the post itself. The exclusion is an **exact-path list on the Spec, not a
wrapper on this route**: the chassis's recorder sits in the middleware chain
above the mux and cannot see per-route registration (research §2.4). This
package therefore does nothing about recording at all — it registers a plain
loopback route — and telemetry's tests assert the observable outcome: after a
real loopback POST, the store holds exactly the posted records and nothing whose
`op` names the ingest path. The coupling is one line in two files, so the route
path and the excluded path are pinned together by R-VOXX-062N.

**Validation is two-tiered, and the tiers differ on purpose:**

- **Envelope-level → reject the whole request.** A body that is not JSON, is not
  an object, has no `records` key, or whose `records` is not an array is a
  **`400 Bad Request`**, and **nothing is stored** — including any `dropped`
  count in the same body. A malformed envelope means the sender is broken or
  something other than a reporter is talking to the port; storing half of it
  would corrupt the record of what happened. The body cap is 8 MiB (well above
  the protocol's ≤256-record batch of ≤8 KiB-params records); over-cap is
  `413 Request Entity Too Large`, nothing stored.
- **Record-level → reject the record, keep the batch.** Each element is
  `Validate`d independently. Valid records are stored; invalid ones are counted,
  logged individually at warn with the failing field and the offending record's
  `id` (never its contents), and reported back. The response is **`202
  Accepted`** with `{"stored":N,"rejected":M}` even when `M > 0` — and even when
  `N == 0`.

The asymmetry is the point: a reporter batches up to 256 unrelated records from
unrelated chains, so one bad record must not destroy 255 good ones. But a
reporter cannot fix what it never learns about, so rejection is **loud** — a
per-record warn log plus a non-zero `rejected` in the response body. "Loud" is
never "fatal to the caller": the response is still 202 because the protocol's
best-effort promise means the caller must never treat telemetry as a failure
source (product: "A reporting service is never harmed by telemetry").

**The `dropped` count** is persisted via `Store.NoteDropped` when positive,
attributed to the batch's records' `service` (all records in a batch come from
one reporter; the empty string when the batch carried no records to attribute
from). A negative or absent count is a no-op. `DroppedTotal` is surfaced in the
`health` details so an investigator can see the store is incomplete without
issuing a query.

**Method and content:** anything other than `POST /ingest` on that path is a 405
from the chassis mux. A missing or wrong `Content-Type` is tolerated — the body
is what matters and a fire-and-forget reporter must not be tripped by a header.

**Storage is synchronous** within the request: the handler writes the batch and
only then answers 202. The reporter is already asynchronous (ring buffer,
background flush), so a second queue inside telemetry would add a window where
telemetry has acknowledged records it can still lose, breaking the "what is
accepted is durable" promise for no gain.

## Rejected.

- **All-or-nothing batch validation** (reject the entire batch on one bad
  record). Loses up to 255 unrelated, well-formed records — from other chains and
  other services — because of one bug in one instrumentation site. The forensic
  cost is exactly backwards.
- **Silent per-record dropping** (store what parses, say nothing). The reporter
  would never learn its instrumentation is broken, and the store would be quietly
  incomplete — the failure mode the whole "loss is visible" promise exists to
  prevent.
- **Answering 400 when records were rejected.** The reporter clears its dropped
  counter only on a 2xx (research §2.4), so a 400 for a batch we *did* partly
  store would make the reporter re-report a drop count it already delivered,
  double-counting the loss. 202 + a `rejected` count carries the same
  information with none of that. The converse also falls out: 400 is exactly
  right for a refused envelope, because there the counter *should* stay
  uncleared and be re-reported on the reporter's next successful batch.
- **A telemetry-side write queue with a 202 before the write.** Acknowledging
  before durability contradicts the durability promise, to save latency on a
  loopback SQLite insert that the reporter is not waiting on anyway.
- **Re-validating protocol thresholds** (param sizes, digest formats) at ingest.
  The reporter owns them (research §1.3); a second enforcement point converts a
  reporter bug into deleted evidence.
- **A bespoke loopback check** (inspecting `RemoteAddr`, or rejecting on
  identity headers). appkit's `LoopbackOnly` is the suite's single answer to "did
  this cross nginx?" and keying on anything else re-introduces the conflation
  `project/design/D20.md` at the repo root explicitly removed.
- **Requiring authentication on `/ingest`.** On-box processes are inside the
  trust boundary; a shared secret between the chassis and telemetry would be one
  more secret on the box guarding a port nothing outside can reach.

## Verification.

- R-VIUF-3BD6 — A real loopback `POST /ingest` (over an actual TCP listener,
  through the chassis router) carrying a batch of well-formed records returns
  **202** with `{"stored":<n>,"rejected":0}`, and every posted record is
  afterwards readable from real SQLite with its `id`, `op`, `service`,
  `correlation_id`, and verbatim `params` bytes intact.
- R-VK2B-H33V — A batch containing both well-formed and malformed records
  returns **202** with `stored` equal to the well-formed count and `rejected`
  equal to the malformed count, and the store afterwards contains exactly the
  well-formed records and none of the malformed ones. (Malformed cases exercised:
  a record with an unknown `kind`, one with a non-`lifecycle` kind and an empty
  `correlation_id`, one with an unparseable `time`, and one whose `params` is a
  JSON array rather than an object.)
- R-VLA7-UUUK — A malformed **envelope** stores nothing and answers **400**: a
  body that is not JSON, a JSON array at top level, and an object whose
  `records` is a string each return 400 with an empty store — and a 400 body
  that also carried `dropped: 5` leaves `DroppedTotal` at 0 (the whole request
  is refused, not partially applied).
- R-VMI4-8ML9 — The ingest route is loopback-only: an otherwise valid request
  carrying `X-Forwarded-Proto: https` receives a bare **404** and stores
  nothing, while the byte-identical request without that header returns 202 and
  stores its records. (Real listener; proves the guard is on the route, not a
  property of the test client.)
- R-VNQ0-MEBY — Posting `dropped: 7` alongside records persists the count
  attributed to the batch's service, `DroppedTotal` reports 7, and a second
  batch with `dropped: 3` brings it to 10 (counts accumulate, they do not
  overwrite); a batch with `dropped: 0` or no `dropped` key adds nothing.
- R-VOXX-062N — The ingest path is never self-recorded: the Spec's
  `TelemetryExclude` contains exactly the path this package registers (asserted
  against the route pattern, not a duplicated literal), and after three real
  loopback `POST /ingest` calls totalling *n* records the store holds exactly
  *n* records and **no** record whose `service` is `telemetry` with an `op`
  containing `/ingest`. (Dropping the exclusion entry, or changing the route
  path without the entry, produces a `request` record per POST and fails this.)
- R-VQ5T-DXTC — A request body larger than the 8 MiB cap answers **413** and
  stores nothing, and the handler does not buffer the whole oversized body
  before deciding — a body streamed past the cap is cut off at the limit.
