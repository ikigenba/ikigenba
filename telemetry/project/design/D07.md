# Decision 7 — Test strategy and the end-to-end layer

## Decision.

The test plan is part of the architecture: seams exist so behavior can be
exercised, and the substrate for each claim is chosen so a wrong implementation
actually fails.

**The substrate rules, stated once:**

- **Storage claims run against real SQLite.** Every store test opens a real
  temp-file database with the same driver and options `serve` uses, and applies
  the real migration set through the appkit runner. There is no in-memory fake
  store and no interface a test can substitute for the database — a mock would
  accept any schema, any index set, and any comparison semantics, so it could
  not falsify a missing index, a wrong `INSERT OR IGNORE`, or a lexicographic
  timestamp bug. `EXPLAIN QUERY PLAN` is used where the claim is "this is
  index-backed", because that is the only assertion a fake cannot pass.
- **Transport claims run over a real loopback listener.** Where the property
  under test *is* the transport — the loopback guard, the HTTP status codes, the
  JSON-RPC envelope — the test binds a real `127.0.0.1` listener on an ephemeral
  port and speaks to it with a real `http.Client`. Calling a handler's
  `ServeHTTP` directly would pass while the route was never registered.
- **Time is injected everywhere else.** A `Clock` seam supplies `received_at`
  and the retention cutoff; the pruner's ticker is a channel a test drives. No
  test sleeps, and no test depends on wall-clock ordering.

**`internal/e2e` is the layer that proves the pieces compose.** Everything else
tests one package; this layer stands up the **real service** — the actual
`appkit.Spec` from the composition root, on a real ephemeral loopback port, over
a real temp-file database with the real migrations — and drives it only through
its two public doors: HTTP `POST /ingest` and HTTP `POST /mcp`. It reaches
inside nothing. Its job is the one claim no unit test can make: *a record a
service reports is, afterwards, findable by an investigator through the MCP
surface.* That claim spans the ingest codec, the store, the schema, the query
builder, the cursor, and the tool layer, and every one of those seams is a place
where two correct-looking halves can disagree.

The e2e fixture posts a **multi-service, multi-hop chain**: a `root` record, an
`edge`, several `request` records from different services, an `outbound`, a
`publish`/`consume` pair, and a `lifecycle` start — the shape a real incident
has — plus records from an unrelated chain that must not leak into the answers.

**What the suite deliberately does not attempt.** The chassis's own
instrumentation (that appkit records MCP dispatch, mints correlation ids, and
emits lifecycle records) is `appkit`'s to prove and is out of this module's
scope boundary. telemetry tests only the observable consequence it owns: that
the ingest route produces no self-record (D3). Likewise the nginx fragment is
verified by parsing the committed file (D6), not by standing up nginx — that is
the repo-root front-door's job, and a fragment test that needed `:8080` would be
skipped far more often than run, which the plan's honesty rule forbids counting
as a pass.

## Rejected.

- **A store interface with a memory implementation for the tool tests.** It
  would make `internal/mcp` tests fast and prove nothing: the filter
  composition, the cursor, and the ordering are all SQL, so a memory
  implementation would be a second, differently-buggy query engine that the
  tests then validated instead of the real one.
- **`httptest.NewServer` for the loopback-guard test.** It is a real listener, so
  it is fine for most transport tests — but the guard's claim is about what the
  chassis router does with `X-Forwarded-Proto`, so the test must go through the
  registered route rather than a hand-wrapped handler.
- **Golden-file assertions over whole tool responses.** They break on every
  additive field and pass on semantic regressions; the ids pin named properties
  instead.
- **Standing up nginx in the module's suite** to prove the fragment. Cross-module
  (the front door is the repo root's), slow, and skip-prone.
- **Property-based/fuzz testing the record codec.** The record shape is a fixed,
  small, externally-owned contract; enumerated cases state the contract more
  legibly than a generator would.

## Verification.

- R-WC40-9T5U — End-to-end round trip against the real composed service: with
  the actual `appkit.Spec` served on a real ephemeral loopback port over a real
  temp-file database, a multi-service chain posted to `POST /ingest` is
  afterwards retrievable through `POST /mcp` — `chain` returns every record of
  that chain from every service, in time order, and none from the unrelated
  chain seeded alongside it; `search` narrowed by service and time range returns
  the expected subset; and `get` on an id taken from those results returns the
  same record with its `params` bytes unchanged from what was posted. (No
  package internals are touched: the test speaks only HTTP.)
- R-WDBW-NKWJ — Accepted records survive a restart: after the e2e ingest, the
  served instance is stopped and a **new** instance is started over the **same**
  database file, and `chain`/`get` through the new instance return the same
  records — proving durability came from the database and not from process
  memory.
