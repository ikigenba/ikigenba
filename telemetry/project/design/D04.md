# Decision 4 — Retention: the configured window and the pruner

## Decision.

`internal/retention` owns the only code path that removes records.

```go
// DefaultDays is the product's contractual default retention window.
const DefaultDays = 90

// Interval is how often the pruner runs while the process lives.
const Interval = 1 * time.Hour

// Days resolves the configured window from the environment. An absent, empty,
// unparseable, or non-positive value yields DefaultDays, and the fallback is
// logged at warn naming the offending value.
func Days(getenv func(string) string, log *slog.Logger) int

type Pruner struct { /* store, clock, days, interval, logger */ }

func New(store *db.Store, clock telemetry.Clock, days int, log *slog.Logger) *Pruner

// PruneOnce computes cutoff = clock.Now().Add(-days*24h) and prunes below it,
// returning the number of records removed.
func (p *Pruner) PruneOnce(ctx context.Context) (removed int, err error)

// Run prunes once immediately, then on every tick of ticks, until ctx is done.
// The ticker is a parameter so tests drive it deterministically.
func (p *Pruner) Run(ctx context.Context, ticks <-chan time.Time)

// Start wires a Pruner from the router's config and launches Run on a real
// hourly ticker for the process's lifetime.
func Start(rt *appkit.Router, store *db.Store, clock telemetry.Clock)
```

**Configuration** is the manifest key `TELEMETRY_RETENTION_DAYS` (D1's
`ManifestExtras`), read from the environment at startup — the suite's ordinary
config path, sourced from `etc/current/manifest.env` by the launcher. It is read
once at startup, not per tick: changing retention is a config change plus a
restart, which is the suite's normal deploy shape.

**A bad value is never obeyed and never fatal.** `TELEMETRY_RETENTION_DAYS=0`,
`-5`, `forever`, or an empty string all resolve to 90 with a warn log. The two
failure modes this excludes are the dangerous ones: `0` must not mean "prune
everything" (a typo would destroy the store on the next tick), and an
unparseable value must not mean "never prune" (the store grows without bound on
a single box until the disk fills).

**Cadence.** The pruner runs once at startup and then hourly. Hourly rather than
daily because a service that is restarted often would, on a daily timer, rarely
reach its first tick; running at startup plus hourly makes the pruner's
liveness independent of uptime. A prune is a single indexed `DELETE` over a
bounded tail, so the cost of running it 24× more often than strictly needed is
nil.

**Failures are logged and retried on the next tick**, never fatal: a prune error
must not take down the store that holds the evidence.

**Scope of deletion** is exactly `Store.PruneBefore` (D2): records and
`ingest_drops` rows strictly older than the cutoff. Nothing else in the database
is touched — the migration-tracking table in particular is untouched, which
matters because it is in the same file.

**Interaction with the chain promise.** Pruning is what makes a chain
potentially incomplete, so D5's `chain` result carries the store's oldest
retained timestamp; product's "complete or honestly bounded" promise is
satisfied by that pairing, not by pruning behavior alone.

## Rejected.

- **Treating `TELEMETRY_RETENTION_DAYS=0` as "keep nothing" or "keep forever".**
  Either reading makes a plausible typo catastrophic in one direction or the
  other. Falling back to the documented default is the only choice where the
  worst case is "retention is 90 days and a warn line says why".
- **Re-reading the env on every tick.** Config on this box arrives through the
  manifest and a restart; a live-reload path would be a second configuration
  mechanism serving no operator workflow.
- **A daily timer.** Ties the pruner's liveness to uptime: a service restarted
  every few hours during a deploy window might never prune.
- **Deleting in bounded chunks with a sleep between them.** Anti-load machinery
  for a problem this box does not have; a single-writer SQLite deleting a day's
  tail is milliseconds.
- **`VACUUM` after pruning.** Rewrites the whole database file and holds an
  exclusive lock, to return disk that the next 90 days of records will
  immediately reuse.
- **Making pruning a chassis concern.** Retention windows are per-service policy;
  no other service wants telemetry's.
- **A `prune` verb on the binary.** The chassis verb set is fixed
  (`serve`/`version`/`manifest`/`migrate`/`schema`); adding one would put
  telemetry outside the uniform tooling for a job the process already does.

## Verification.

- R-VRDP-RPK1 — With `TELEMETRY_RETENTION_DAYS` unset, `Days` resolves to
  **90**, and a `PruneOnce` against real SQLite with a deterministic clock keeps
  a record aged 89 days while removing one aged 91 days. (Pins the value, not
  merely "some positive window": a default of 30 or 365 fails.)
- R-VSLM-5HAQ — Every invalid value resolves to 90 rather than to 0 or to
  "disabled": `""`, `"0"`, `"-5"`, `"forever"`, and `"90.5"` each yield 90 from
  `Days`, and a `PruneOnce` configured from `"0"` leaves a record aged 1 day in
  place (a 0-day window would delete it) while still removing one aged 91 days
  (a disabled pruner would keep it).
- R-VTTI-J91F — `Run` prunes without a restart: started against a store holding
  a record that is inside the window, then with the injected clock advanced past
  the window and a tick delivered on the ticker channel, the record is gone —
  and the initial pre-tick prune already ran (a record already outside the
  window at start is removed before any tick is delivered).
- R-VV1E-X0S4 — A prune removes only aged-out record data: after a prune that
  deletes records and `ingest_drops` rows, the `schema_migrations` table's rows
  are unchanged and a subsequent migration run finds the schema already at its
  current version, so the database is still usable. A `PruneBefore` error is
  logged and does not stop `Run` — a following tick still prunes successfully.
