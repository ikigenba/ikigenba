# Decision 5 — The forensic MCP surface: `search`, `chain`, `get`, `guide`

## Decision.

`internal/mcp` declares exactly **four** domain tools over `appkit/mcp`; the
chassis supplies `health` and `reflection`. There is no fifth tool, and in
particular nothing that writes. The surface follows
`docs/mcp-discovery-convention.md` (tiers) and `docs/structured-mcp-design.md`
(structured results).

```go
func NewHandler(store *db.Store, clock telemetry.Clock, rt *appkit.Router) (http.Handler, error)
func Tools(store *db.Store, clock telemetry.Clock) []appkitmcp.Tool
```

### Tier 0 — `instructions`

Orientation plus routing vocabulary plus one pointer to the guide, in two
sentences. It names the domain in the words an investigator actually types —
audit trail, forensics, "what happened", who did what when, traces, correlation
id, chain, request history — because these are the routing hooks that let an
agent pick telemetry without an external skill:

> Forensic record store for this box: the audit trail of who did what, when, and
> in what order across every service — MCP calls, HTTP requests, outbound calls,
> event publishes and consumes, and service starts and stops. Use `search` to
> find records (by time, service, kind, actor, operation, outcome, or content
> digest), `chain` to follow one correlation id through every service it
> touched, and `get` to read one record in full; call `guide` for the record
> model and worked examples.

### Tier 1 — the tools

**`search`** — bounded, filtered, cursored. Input:

| arg | shape |
|---|---|
| `since`, `until` | RFC3339 timestamps; open-ended when omitted |
| `service`, `kind` | exact match; `kind` constrained to the closed vocabulary |
| `owner_email`, `client_id` | exact match on the actor |
| `op_contains` | case-insensitive substring of `op` |
| `status`, `error` | exact match on the outcome class |
| `sha256` | exact match on the body digest — "where else did these bytes appear" |
| `limit` | 1–500, default 50 |
| `cursor` | opaque continuation from a previous page |

All supplied filters compose with **AND**. Output:
`{records: [...], next_cursor: "", retention_horizon: ""}` — `next_cursor` empty
when the page is the last one, `retention_horizon` the oldest record time the
store still holds. An out-of-range `limit`, an unknown `kind`, an unparseable
timestamp, or a corrupt cursor is a `validation` error naming the offending
argument (not a silent clamp — an agent that asked for 5000 must learn the
ceiling rather than believe it got 5000).

**`chain`** — one argument, `correlation_id`. Returns the complete chain,
ascending in time, across every service:
`{records: [...], count: N, retention_horizon: "", possibly_truncated: bool}`.
`possibly_truncated` is true when the chain's earliest record is at or before
the retention horizon — the honest form of product's "complete or honestly
bounded" promise. An unknown correlation id returns an **empty result, not an
error**: "this chain has no records" is an answer, and forcing an agent to
branch on an error code to learn it is hostile.

**`get`** — one argument, `id`. Returns the whole record, `params` and `detail`
included verbatim. An unknown id is a `not_found` error.

**`guide`** — flat, read-only, no arguments, plain text, no output schema
(prose-tool exception). Its document is `//go:embed`ed so it always matches the
running binary. It carries what tiers 0 and 1 deliberately do not: the record
field catalog, the seven `kind` values and what each one means, the `op` shape
per kind, what `params`/`outcome`/`detail` hold, the elision representation
(`{"$elided": {...}}`) an investigator will encounter in `params`, the explicit
statement that bodies and conversations are never stored, and worked examples —
basic (find a failing MCP call in the last hour) and advanced (take that
record's `correlation_id`, follow the chain, and find the same digest elsewhere
with a `sha256` search). The guide is referenced in exactly two places: the
`instructions` above and `guide`'s own description.

### Structured results

`search`, `chain`, and `get` each declare an `outputSchema` and return
`StructuredResult(v)` — `structuredContent` plus the mirrored text block. Errors
use the closed vocabulary: `validation` for bad arguments, `not_found` for an
unknown record id, `internal` for a store failure. `guide` returns
`TextResult` and declares no output schema.

### What the surface deliberately lacks

No `delete`, no `redact`, no `annotate`, no `tag`, no `purge`, no `count`, no
`stats`, no `aggregate`, no `timeline`, no `export`. The store is append-only
from the MCP surface and analytics-free (product Scope). The absence is a
checkable property of the declared tool-name set, not a matter of restraint.

### Records of the surface itself

telemetry's own tool calls are recorded by the chassis's MCP dispatch
instrumentation, exactly like any other service's (research §1.6, §2.4). Nothing
here suppresses that: a `search` shows up in the store as a `request` record
with `op` = `mcp:search`, which is what makes "who went looking" answerable.
`params` for these calls are the search arguments themselves — a correlation id
or an email is metadata, not content, so no argument is declared sensitive.

## Rejected.

- **A `count` or `stats` tool.** It is the thin end of analytics, which product
  excludes outright; `search` with a small limit answers "did this happen" and
  the honest answer to "how often" is a separate product.
- **Any mutation tool** (delete a record, redact a field, annotate a chain). A
  forensic store an agent can edit is not evidence, and a redaction tool implies
  the store contains something worth redacting — which the record model already
  prevents by construction.
- **Merging `chain` into `search` as a `correlation_id` filter.** It reads
  identical but promises differently: `search` is bounded and newest-first,
  `chain` is unbounded and oldest-first and is the *whole* chain. Collapsing
  them would make the product's completeness promise depend on an agent
  remembering to page.
- **Erroring on an unknown correlation id.** "No records" is a legitimate,
  informative answer; an error makes the common case of "the id was from
  yesterday and aged out" look like a malfunction.
- **Silently clamping an over-range `limit`.** The agent then believes it saw
  everything up to 5000 when it saw 500 — the exact way a forensic tool lies.
- **`OFFSET`-style `page` arguments.** Wrong under continuous insert (D2).
- **Putting the record-field catalog in tool descriptions.** Tier 1 is loaded on
  every connection; the catalog is what tier 2 exists for.
- **Exposing the guide only as an MCP resource.** Most clients never surface
  resources into the agent's context, so an agent told to read the guide could
  not (`docs/mcp-discovery-convention.md`).
- **Declaring the search arguments sensitive** so they are elided from
  telemetry's own records. It would make the "who went looking, for what"
  records useless, and the arguments are metadata by construction.

## Verification.

- R-VW9B-ASIT — `tools/list` over the real MCP handler returns exactly the tool
  names `{search, chain, get, guide, health, reflection}` — set equality, so an
  extra tool fails — and no declared tool's name or description contains
  `delete`, `redact`, `annotate`, `purge`, `stats`, `aggregate`, or `export`.
- R-VXH7-OK9I — `search` filters compose with AND over real SQLite: against a
  seeded corpus, a query giving `service`, `kind`, `owner_email`, `op_contains`,
  `status`, and a time range returns only records matching **all** of them, and a
  record differing in exactly one of those fields (each of the six exercised in
  turn) is excluded. A `sha256` query returns records from **two different
  services** that share one digest and no record with a different digest.
- R-VYP4-2C07 — `search` is bounded and cursored on the wire: omitting `limit`
  returns at most 50 records; `limit: 500` is accepted; `limit: 0` and
  `limit: 501` each return a `validation` error naming `limit` and **no**
  records (not a clamped page); calling `search` again with the returned
  `next_cursor` yields the following page with no record repeated from the
  first, and the last page returns an empty `next_cursor`.
- R-VZX0-G3QW — `chain` returns the complete ordered chain and reports its
  boundedness: for a correlation id with records from three services it returns
  all of them ascending by time with `count` matching, `retention_horizon` equal
  to the store's oldest record time, and `possibly_truncated: false`; when the
  chain's earliest record is at or before that horizon it returns
  `possibly_truncated: true`. An unknown correlation id returns an empty
  `records` list with `count: 0` and **no** error (`isError` absent).
- R-W2CT-7N8A — `get` returns one record in full — including `params` and
  `detail` as objects byte-identical to what was ingested — and an unrecognized
  id returns a tool error carrying the code `not_found` (not `internal`, not an
  empty success).
- R-W3KP-LEYZ — `search`, `chain`, and `get` each declare an `outputSchema` in
  `tools/list` and each success result carries `structuredContent` conforming to
  it plus a text block whose JSON parses to the same value; `guide` declares
  **no** `outputSchema` and returns a text-only result.
- R-W4SL-Z6PO — `guide` returns a non-empty plain-text document that names all
  seven `kind` values, describes `params`, `outcome`, and `detail`, shows the
  `{"$elided": ...}` representation, states that bodies and conversations are
  never stored, and contains at least one worked example whose tool name and
  argument names all exist in the declared tool set (so a documented example
  cannot drift from the surface).
