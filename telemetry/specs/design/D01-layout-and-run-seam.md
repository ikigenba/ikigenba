# D01-layout-and-run-seam

telemetry is the suite's trail of events: one Go binary that takes the events every service on the host posts to its socket at `/ingest`, keeps them in its own SQLite database for a retention window, offers four read-only MCP tools over them at `/mcp`, and serves a landing page at `/` that says what it is. This design is the structural ground the other designs stand on: where the code lives, which package exports which name, how the version, the manifest, the nginx fragment and the usage text are declared, the seam through which the process is run so that the command, the server, the pages, the store and the tools can be tested without a real process, the seam through which the handler is built, the store that is both the trail and the sink telemetry's own events go to, and the domain terms every later design uses.

The module is `github.com/ikigenba/ikigenba/telemetry`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/telemetry` because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`, like every other binary in the repository. `cmd/telemetry` is wiring only.

## The two dependencies

telemetry depends on two modules besides the standard library. The first is `github.com/ikigenba/ikigenba/appkit`, the platform's shared library, required by its released version like any published module, with no `replace` directive; until that release's tag is pushed the module cache is seeded from the local repository as `AGENTS.md` records. The second is `modernc.org/sqlite`, the pure-Go SQLite driver auth already uses, which keeps the release build cgo-free. Which release of either is data: `AGENTS.md` and `go.mod` name it, and no requirement names a version.

appkit is a sibling sub-project, reached only through its published packages and their documented contracts, and telemetry uses four of them. `page` gives the banner, the launcher and the footer, and serves the shared stylesheet, fonts, licences and launcher script under `page.StaticPrefix`. `identity` gives `identity.Require`, which wraps every route but `/ingest`, so a request reaches the pages, the shared files and `/mcp` only with an `X-User-Id`. `mcp` gives the server mounted at `/mcp`, on which the four tools are registered with `mcp.AddTool`, and the client the tests drive it with. `telemetry` gives the whole of the trail's machinery: `telemetry.Event` and its `MarshalJSON`, the one shape every record has; `telemetry.IngestHandler`, which telemetry mounts at `telemetry.IngestPath` to take siblings' events; `telemetry.Middleware`, which records every request but an ingest; and `telemetry.Writer`, through which telemetry's own `service.started`, `service.stopping`, `request.started`, `request.finished` and `tool.called` are recorded. appkit owns the banner's markup, the stylesheet, fonts, licences and launcher script, the MCP transport and protocol, schema derivation, argument decoding and its error text, the reading of the services file, the shape of an event, the framework events, the ingest handler's refusals and how a writer queues, retries and writes out an event; telemetry authors none of them and restates none of their contracts. telemetry records no event of its own beyond appkit's framework events: everything it does is a request or a tool call, and the trail is of what the suite did, not of telemetry's bookkeeping.

Because the module's root package and appkit's `telemetry` package share a name, a file that imports both aliases one of them; only `internal/web` and tests import the root package.

## Where the environment is read

Two appkit constructors read `IKIGENBA_SERVICES` (`services.Variable`) from the real process environment, once, during the call, and keep the path: `page.New`, whose kit's `Banner` method reads the file afresh for the launcher, and `mcp.NewServer`, which reads it afresh for the instructions it gives a client when its `Instructions` is nil. Neither offers a form that takes the path from a caller. Reading the real environment is what the run seam keeps out of everything below `main`, so `main` calls `page.New` once at start and puts in `Process.MCP` a function that calls `mcp.NewServer`, which `Run` calls once when it starts to serve, with the writer it has built. A test that calls `mcp.NewServer` first sets the variable with `testing.T.Setenv`, to the empty string or to a file of its own, as `AGENTS.md` asks.

The handler reads the services file a third time, for the banner's auth links: the profile link and the sign-out form address the `url` of the file's `auth` entry when there is one, and the space the request's `Host` names otherwise (`D04-pages`). `cli.Run` looks `IKIGENBA_SERVICES` up through the seam's `LookupEnv`, once, when it starts to serve, and hands the value to the handler as `Config.ServicesPath`; the handler reads the file afresh for every page. None of these reads can fail a start: an unset or empty variable, or a file that is missing, unreadable or malformed, lists no services, gives no instructions, and sends the auth links to the request's own space. Unlike every other app, telemetry does not read the services file to find the telemetry service: it is the telemetry service, and its own events go straight into its store, so appkit's socket sink is never built and nothing of telemetry's reads the environment on a delivery.

`main` builds the banner source as the `Banner` method of `page.New(web.ServiceName, cli.Version)`, and the server maker as a function that returns `mcp.NewServer(mcp.ServerConfig{Name: web.ServiceName, Version: cli.Version, Telemetry: w})` for the writer `w` it is given, with `Instructions` nil so that the instructions a client is given are telemetry's description read afresh from the services file by appkit's default, and passes them to `cli.Run` in `Process` with `DBSource` set to `state/telemetry.db`, `Now`, `Sleep`, `Rand`, `Inherit` and `Unsetenv` left nil so that `Run` uses the real clock, a real pause, `crypto/rand`, the real descriptor 3 and the real environment. It cancels `Run`'s context on `SIGTERM` or `SIGINT` with a cause whose text is the signal's name, `SIGTERM` or `SIGINT`, which `Run` records as the reason of `service.stopping`. `web.ServiceName` is the one declaration of the name, `web.Description` the one declaration of the description outside the manifest, and `cli.Version` the one declaration of the version, so the footer, the about screen, the MCP `serverInfo`, the service named in every event and the version `service.started` carries all name the same release.

That `main` hands them on correctly is wiring, proved only by the one exec'ing test that `AGENTS.md` admits: it builds the binary, runs `--version`, `manifest` and `bogus`, and a bare start with no socket, and then serves on a socket it passes as descriptor 3, from a working directory it owns, with an environment it composes, and makes these requests over that socket with the identity headers set: a `GET /` with `IKIGENBA_SERVICES` unset, whose footer names the name and the version; a `GET /` with a services file that lists a service with an icon, which carries the launcher; an appkit `mcp.Client` call of `catalog`, whose `serverInfo` names telemetry; a `server/discover` sent as raw HTTP, which carries telemetry's description from the services file, or no instructions when the variable is unset; a `POST /ingest` of one event, which a `trace` through the client then answers; and a `search` for telemetry's own `service.started`. It then stops the child with `SIGTERM`, and in a second run over the same database with `SIGINT`, and in that second run searches for the first run's `service.stopping`. The child's database is the `state/telemetry.db` it creates under the test's working directory, which is how the test proves that `main` passed that path.

## Packages

The module's root package, `telemetry`, holds the embedded templates. telemetry's markup is the two human-authored `html/template` files in `assets/`, `landing.html` (the template `landing`) and `about.html` (the template `about`), which the build run reads and never writes. Go's `embed` reaches only files at or below the embedding package's directory, so the root package, the directory holding `go.mod`, is the one that can embed them. It exports one name, `Assets`, a file system holding exactly those two files, and `internal/web` parses them from it into the set `page.Templates()` returns. Nothing else lives at the root.

Five internal packages hold the concerns, each one concern and each small enough for a reader to hold whole.

- `internal/cli` owns the program as a command: the version, the manifest text, the nginx fragment, the usage text, the exit codes, the run seam, the argument handling `D02-cli` specifies, and the serve path `D03-serve` specifies — reading the drain deadline, the retention window and the services path, taking the socket the host passes in, opening the store, building the writer and the handler, sweeping, telling systemd it is ready, and recording the start and the stop in the trail.
- `internal/server` owns the listener's life and nothing else, exactly as in the platform's reference app: handed a context, a listener, a handler, a drain deadline and a function to call when the drain is over, it serves and drains; it knows nothing of routes, identity, HTML, MCP, the store, telemetry's writer, sockets passed in or systemd.
- `internal/web` owns telemetry's whole HTTP surface: the one handler, which mounts the ingest handler at `/ingest` outside everything and wraps everything else in `identity.Require` and that in `telemetry.Middleware`; the routing, the landing page and the about screen (`D04-pages`), the failure shapes, the mounting of appkit's shared files under `/_appkit/`, and the mounting of the MCP server at `/mcp` with the four tools registered on it (`D03-serve`).
- `internal/store` owns the trail: the SQLite database, its schema, the insertion of a record (which is what makes `*store.Store` a `telemetry.Sink`), the sweep that removes records older than a moment, and the reads the four tools are built on (`D05-store`).
- `internal/tools` owns the four MCP tools, `catalog`, `search`, `count` and `trace`: their names, descriptions, schemas and annotations, what each answers and refuses, and the text of each refusal (`D06-mcp`, `D07-search`, `D08-count`).

Dependencies point one way. `cmd/telemetry` imports `internal/cli`, `internal/web` (for `ServiceName`) and appkit's `page`, `mcp` and `telemetry`. `internal/cli` imports `internal/server`, `internal/web`, `internal/store` and appkit's `page`, `mcp` and `telemetry` (whose types `Process` names). `internal/web` imports the root package, `internal/store`, `internal/tools` and appkit's `page`, `identity`, `mcp`, `services` and `telemetry`. `internal/tools` imports `internal/store` and appkit's `mcp` and `identity`. `internal/store` imports appkit's `telemetry` and the SQLite driver, and `internal/server` and the root package import nothing of telemetry's or appkit's. Nothing imports `internal/cli` but `cmd/telemetry`. Which package imports which is not observable, so this paragraph is guidance, not a requirement.

The tools live in a package of their own, as dummy's do, because their schemas, descriptions and refusal texts are a contract with models, proved through `mcp.Client`, not by reading HTML; the handler registers them on the server it is given, so one server backs one handler. The store is the sink rather than a type beside it because there is exactly one thing a delivered event can become, a record, and a second name for that would be a name with no second member; the ingest handler and telemetry's own writer are handed the same `*store.Store`, so a sibling's event and one of telemetry's own enter the trail by the one path and keep one arrival order.

## The run seam

The run seam is `cli.Run`. It takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package or from the environment-reading constructors: the arguments without the program name, an environment lookup, a way to remove a variable from the environment, the process's own id, the two output streams, a way to turn an inherited descriptor into a listener, the clock, the pause, the random source, the database source, the banner source and a function that makes the MCP server from the telemetry writer. Its return value is the exit code. `main` fills `Process` from the real process and cancels the context on a signal; a test fills it with buffers, a map, a pid of its choosing, a listener it bound itself, a clock and a pause it controls, a reader of known bytes, a database path in a temporary directory of its own or an in-memory SQLite source, a banner closure and a function that calls `mcp.NewServer` with the writer it is given, and cancels the context itself, with `context.WithCancelCause` when it checks the reason. `Run`'s behaviour when it serves with a nil `Banner` or a nil `MCP` is not contract, so a test that serves supplies both. Nothing below `main` reads `os.Args`, the real environment, the real pid, the real clock or the real streams, changes the real environment, calls `page.New`, or installs a signal handler; `mcp.NewServer` is called only through `Process.MCP`.

Socket activation hands the process a listening socket as file descriptor 3, and the one thing below the seam that touches a real descriptor is turning that number into a `net.Listener`. `Process.Inherit` is that step: `main` leaves it nil, and `Run` then makes the listener from the real descriptor; a test supplies a function that returns a listener it bound itself. The environment half of the protocol — `LISTEN_PID`, `LISTEN_FDS`, `NOTIFY_SOCKET`, `DRAIN_SECONDS`, `RETENTION_DAYS` and `IKIGENBA_SERVICES` — arrives through `LookupEnv`, and removing the `LISTEN_*` variables goes through `Process.Unsetenv`. Readiness is the `READY=1` datagram a test receives on a socket it named in `NOTIFY_SOCKET`, the same signal systemd waits for. There is no listen factory and no readiness callback: telemetry binds nothing, so there is no bind to fake, and the datagram is the readiness signal. What `Run` does once it has the socket — the environment's checks and their order, opening the store, the sweep at start, readiness, serving, the hourly sweep, the drain and how it ends — is `D03-serve`, stated as what a client, the store and the streams see.

Time is injected because telemetry measures and decides by it. `Process.Now` is the clock the writer stamps telemetry's own events with and the moment each sweep subtracts the retention window from; `Process.Sleep` is the pause the writer waits between delivery attempts with and the wait `Run` makes between one hourly sweep and the next, so a test's `Sleep` that returns at once, or when the test says so, triggers the next sweep without a timer, and a test's `Now` that it advances by hand ages a record without sleeping. `Process.Rand` is the source the request middleware mints request ids from. Each is nil in `main` and means the real one: `time.Now`, a real pause that ends when its context does, `crypto/rand.Reader`.

`Process.DBSource` is the database source `Run` opens with `store.Open`: on a host `main` sets `state/telemetry.db`, relative to the working directory, and a test sets a path inside a temporary directory it owns or an in-memory source. A start refused as a usage error has touched nothing, not even the database, because `Run` checks the environment and takes the socket before it opens the store (`D03-serve`); the diagnostic for a store that cannot be opened names `DBSource` as given.

The seam carries no sink. telemetry's own events go to its store, and `Run` builds the writer over the store it opened, so a test of `Run` reads telemetry's own trail back the way an agent does, through the tools over the socket, or by opening the same database with `store.Open` once `Run` has returned. A test that wants to see what the writer records without a database builds the handler itself (below) over a writer of its own with a `*telemetry.Capture` as its sink. A test that wants the store to fail makes its own database fail after the handler has it: it closes the store it handed the handler, or removes the write permission of the directory holding its database file (`D05-store` says why the directory and not the file).

## The handler's seam

`web.Handler` takes a `web.Config`: the banner source, the server `Process.MCP` made, the path of the services file, the store and the writer. The handler has no stream of its own: everything it has to say is an event, and an event that cannot be stored is written out by the writer. The design states what a handler does only for a `Config` whose `Banner`, `Store` and `Telemetry` are not nil and whose `MCP` came from `mcp.NewServer` with that same writer, on which no tool has been registered and which has not yet served, since the handler registers the four tools on it with `tools.Register`. A test builds the writer with appkit's `telemetry.New`, naming `web.ServiceName`, over a `*telemetry.Capture` or over the store it built, calls `Flush` before it reads `Capture.Events`, and shuts the writer down before it ends; it drives `/mcp` with appkit's `mcp.Client` and asserts on the `Result` and the `ToolInfo` the client returns.

## The store, the sink and the trail

`store.Open` opens or creates the database at a source and returns the one `*store.Store` the process serves over; `Close` releases it. A `*store.Store` is a `telemetry.Sink`: its `Deliver` inserts the event it is handed as one record, which is what the ingest handler calls for a sibling's event and what telemetry's own writer calls for its own, so the two reach the trail by one path. `Sweep` removes every record whose time is before a moment; `Run` calls it at start, with the moment `RETENTION_DAYS` days before `Now`, and again after every hour. The reads behind the tools — the catalog, a filtered page, a count, a trace — are `D05-store`'s to declare, and `D06-mcp`, `D07-search` and `D08-count` use them.

Every later design speaks of the same few things, defined once here. A **record** is a `telemetry.Event` the store has taken and not yet swept; the **trail** of a store is its records. The **arrival order** of the trail is the order the store took the records in: a record stored before another was handed in comes first, whatever the two records' times, so a sibling whose clock runs behind still has its events read in the order it posted them, and two records with the same time are told apart by it. `search` reads the trail backwards in arrival order within equal times, and `trace` forwards.

## Declarations and the checkout

The version is a `var` in `internal/cli`; its value is data, and a requirement fixes only its name, that it is a `var`, and its shape, `v` then a semantic version. The manifest is a constant in the same package holding exactly the text the bootstrap story shows, with a trailing newline: telemetry's name; its description, the one line the host publishes in its services file, the about screen shows and the MCP endpoint gives its clients as instructions; that it is not the host's default app; that it is one of the suite's MCP services; no secrets; its one setting, `RETENTION_DAYS`, with its default; and its database. It declares no port, because telemetry serves on the socket the host passes it. The usage text is a constant there too, whose value `D02-cli` fixes.

The nginx fragment is a constant there as well, `NginxConf`, holding exactly the one directive the public ingest path needs. The host's nginx proxies everything on telemetry's public name to the same socket siblings post to, and opsctl and the sandbox include the app's `etc/nginx.conf*` inside its server block before every location they declare; an exact-match location (`location = /ingest`, nginx's `ngx_http_core_module` documentation of the `location` directive: an exact match ends the search) answering `return 404` (the `return` directive of `ngx_http_rewrite_module`, allowed in a `location` context) therefore answers the public `/ingest` 404 before any other location, the authenticating gate included, while the same path on the socket still takes every sibling's events. The fragment redeclares none of the host's own locations. Nothing prints it: the bootstrap story fixes the usage text and its one command, `manifest`, and a command the usage text does not list would be a story change; the constant's value is contract, proved by use as the manifest's is, and the file beside it is kept in step by the build run.

The package story lists exactly four members in the release file — `bin/telemetry`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`. `share/icon.svg` is telemetry's icon, an SVG image a human draws, and its presence in the package is what lists telemetry in the platform's launcher on a space; it is a human-authored input like `assets/`, never written by the build run. The two files under `etc/` are not: the build run writes `etc/manifest.toml` holding exactly the text of the `Manifest` constant and `etc/nginx.conf` holding exactly the text of the `NginxConf` constant, and `devctl build` refuses an app whose `manifest` disagrees with the committed `etc/manifest.toml`. No test reads the checkout, so those copies, like the icon and the release tarball, are outside what a requirement can state. Everything telemetry serves is inside the binary — its templates, embedded by the root package, and appkit's embedded files alike — and nothing on disk but its database.

## Consumer tasks

The binary's start, in outline: `main` hands `cli.Run` a `Process` whose `Banner` is the kit's `Banner` method, whose `MCP` returns `mcp.NewServer` over the writer it is given, whose `DBSource` is `state/telemetry.db`, and whose `Now`, `Sleep`, `Rand`, `Inherit` and `Unsetenv` are nil, under a context it cancels with the signal's name as the cause. `Run` checks `DRAIN_SECONDS` and `RETENTION_DAYS`, takes the socket, opens the store with `store.Open(p.DBSource)`, sweeps, and tells systemd it is ready; then builds the writer with `telemetry.New` from a `telemetry.Config` naming `web.ServiceName`, `Version`, the store as `Sink`, a guarded `p.Stderr`, `p.Now`, `p.Sleep` and `p.Rand`; calls `p.MCP` with it; builds the handler with `web.Handler` from a `web.Config` carrying the banner source, that server, the services path, the store and the writer; calls `Writer.Ready`; serves until the context ends, sweeping after every hour; and then, inside the drain window, calls `Writer.Shutdown` with the context's cause as the reason.

The handler, in outline: a request whose path is exactly `/ingest` goes to `telemetry.IngestHandler(cfg.Store)` and nowhere else; every other request goes to `telemetry.Middleware(cfg.Telemetry, identity.Require(mux))`, the mux holding the landing page, the about screen, `page.Static` at `page.StaticPrefix` and `cfg.MCP` at `/mcp`, with `tools.Register(cfg.MCP, cfg.Store)` called once when the handler is built.

A test of the run seam serves with a temporary database, cancels with `context.WithCancelCause`, and reads telemetry's own trail back through the tools over the listener it made, or with `store.Open` on the same source once `Run` has returned. A test of the handler builds its own writer over a `*telemetry.Capture`, the server with `mcp.NewServer` over that writer, a store over an in-memory source, and the handler with `web.Handler`, drives it, calls `Writer.Flush`, and asserts on the events by name, attributes, request id and user; it closes the store to see the undelivered lines, and posts to `/ingest` as a sibling would to fill the trail. A test of a tool builds a store, fills it through `Deliver`, registers the tools on a server over a capturing writer with `tools.Register`, and calls them through `mcp.Client`.

## The documents

`D02-cli` is the command: `--version`, `manifest`, `--help`, the usage error, and the rule that a command touches no environment. `D03-serve` is the serve path and the handler's skeleton: the environment's checks, the socket, the store's opening and its diagnostic, the sweeps and when they run, readiness, the route split and the ingest mount, identity, the answers for a path that does not exist and a method a route does not take, the shared files, telemetry's own events and what reaches stderr, the drain and the stop. `D04-pages` is the landing page and the about screen with their banner. `D05-store` is the database: its schema, `Open`, `Deliver`, `Sweep` and the reads the tools are built on. `D06-mcp` is the MCP endpoint's contract with a client, `tools.Register`, the four tools' list entries, `catalog` and `trace`. `D07-search` is `search`, and `D08-count` is `count`.
