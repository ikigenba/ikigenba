# D06-mcp

telemetry's MCP endpoint is the trail offered to models: four read-only tools, `catalog`, `search`, `count` and `trace`, registered on the one `mcp.Server` the handler mounts at `/mcp`. This document is the whole of `internal/tools` but for two tools' calls: it declares `Register`, which puts the four tools on a server in that order; fixes what a client sees of each in `tools/list`, its name, the description written for a model, its input and output schemas and its annotations; fixes the shapes every tool's answer and refusal share and the record object every record is answered as; and states what `catalog` and `trace` answer. `search` is `D07-search` and `count` is `D08-count`; both use the shapes fixed here.

Everything around the tools is appkit's or another document's, and this one restates none of it. appkit's `mcp` server is the transport and the protocol: the methods `/mcp` answers on both protocol families and their envelopes, `resultType`, `_meta`'s `serverInfo`, `ttlMs` and `cacheScope`, the 405 for a method other than POST, the `Origin`, `Content-Type` and size checks, the 500 for a request that reached the server without a caller, the unknown-tool protocol error with its `Unknown tool: <name>` message, the instructions read afresh from the services file for `server/discover` and `initialize`, the schema derivation from Go types, the strict argument decoding and its `invalid arguments:` text, the success result built from a handler's output, and the `tool.called` event recorded for every call that reaches a tool, with its `kind`, `outcome` and `duration_us`. The server itself is built by `main` with `web.ServiceName`, `cli.Version` and telemetry's writer, and `Instructions` nil (`D01-layout-and-run-seam`); mounting it at `/mcp`, inside `identity.Require` and the telemetry middleware, and calling `Register` on it with the handler's store are `D03-serve`'s. The tools read the store `Register` was given and nothing else; the store's reads are `D05-store`'s.

## What a client is told

Each tool is registered with `mcp.AddTool`, so its schemas are derived from Go types `internal/tools` keeps unexported; those types are not contract, the schemas they produce are, and they are stated here whole, property descriptions included, since a model reads them. The descriptions are the ones the stories fix, word for word: a one-line summary a catalogue can show on its own, then a paragraph on how to call the tool. All four read the trail and change nothing, so all four carry the annotations appkit gives a tool whose `Effect` is `mcp.Read`, which is what makes the gateway run them with `call` and never with `mutate`.

Only `trace` marks an argument required, so a `trace` without `request_id` is refused by appkit's decoder with `request_id: missing required field` and the handler never runs. `trace`'s `request_id` is a plain string field, not a pointer, so `"request_id":null` is refused the same way, with `request_id: expected string, got null`, rather than read as an id; every other argument is optional, and a member outside a tool's schema is appkit's `unknown field`. The search filters `since`, `until`, `user`, `request_id`, `limit` and `cursor` are pointer fields of the input type, so an argument that is present with an empty or zero value is told from one left out: `"user":""` asks for the records that have no user, `"limit":0` is refused as out of range rather than taken as the default, and `"since":""` is refused as a time the tool cannot read. `catalog`'s `service` and `event` are plain strings, because no service and no event has an empty name, so an empty value narrows to nothing a non-empty one could not and is treated as left out. `attrs` is a `json.RawMessage`, the one field appkit derives an open object schema for, and the tool reads its members itself (`D07-search`).

Every output schema marks each member that is always present required, since appkit always writes a non-pointer field and a client may rely on it; `search`'s `cursor` and `count`'s `groups` are the two members that are present only sometimes, and are not marked. The **record schema** is one object schema the two tools that answer records share.

## What a call answers

A tool that can do what it was asked answers a success result: `structuredContent`, a JSON object, and one text block holding that object encoded compactly. A tool that cannot, a time it cannot read, a limit out of range, a cursor no search issued, a `by` it does not know, returns an error from its handler, which appkit turns into an `isError` result with no `structuredContent` and one text block saying why in the words the stories fix; the trail records the call with the outcome `error`. A tool that cannot read the trail — the store's read returns an error that is not its verdict on a cursor or a `by` — refuses the same way with `cannot read the trail`, whichever tool it is, and never answers as if the trail were empty or quotes the store's error; a test makes the read fail by closing the store after `Register` has it, or by dropping the `records` table of a file-backed store through a connection of its own. That refusal comes before any success answer, an empty one included, so a tool never reports an empty trail it did not read. A malformed cursor or an unknown `by` is refused in its own words even then, since the store reports those before it reads anything (`D05-store`). A filter that matches nothing is not a failure but an empty answer. A record in any answer is the **record object** of the store's `Record`: the event as it was ingested, members in the order `time`, `service`, `event`, `request_id`, `user`, `attrs`, the time to the microsecond in UTC, `attrs` exactly as stored, so it is equal as a JSON value to the event the sibling posted.

`catalog` answers what the trail holds by name, from `Store.Catalog` with the two names it was given, each empty when left out: one entry per service in name order, each event in name order with its count, its newest time and its attribute keys, and an empty list when nothing qualifies. `trace` answers one request's records from `Store.Trace`, oldest first, in the order the services lived it, every record and no page, and an empty list for an id no record carries, the same answer for an id the sweep has removed as for one that never was. Both read the trail as it is when the call runs, so a record delivered before the call is in the answer and the call's own `tool.called`, recorded after it answers, never is.

The tools record nothing of their own: every call's `tool.called` is appkit's, and `Register` takes no writer because the tools have no event to emit. They change nothing: the trail after any call is the trail before it.

## Consumer tasks

The handler registers the tools once when it is built, `tools.Register(cfg.MCP, cfg.Store)`, on the server `mcp.NewServer` returned for the handler's writer, and mounts that server at `/mcp`.

A model, through the gateway's `call` or a client at `/mcp`, lists the tools and reads the whole catalog with `catalog` and `{}`; narrows it with `{"service":"dummy"}` or `{"event":"service.started"}`; traces one request with `trace` and `{"request_id":"3f9c2a7be1d04c6a8b5e0f1d2c3b4a59"}`, getting `{"records":[...]}` oldest first, or `{"records":[]}` for an id the trail does not hold.

A test builds a store with `store.Open`, fills it through `Deliver`, builds a writer over a `*telemetry.Capture`, a server with `mcp.NewServer` over that writer, calls `tools.Register(srv, s)`, serves the server on loopback behind `identity.Require`, and drives it with appkit's `mcp.Client`: `ListTools` for the four `ToolInfo`, whose `Name`, `Description`, `InputSchema`, `OutputSchema` and `Effect()` it asserts, and `CallTool(ctx, caller, "catalog", args)`, `args` being the bytes `{"service":"dummy"}`, for a `Result` whose `MarshalJSON` it asserts on.
