# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail telemetry records of itself from its start to its stop, and the rules its handler keeps on every route — the identity gate, the request's id, the request's two events, the exact mounts of `/ingest` and `/mcp`, the shared files, and the answer for a path that does not exist. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, the display string `main` reads, `cli.Run`, the exit codes, `server.Serve`, `server.DrainError`, `web.Config`, `web.Handler`, `web.ServiceName`, `telemetry.Migrations`, `store.New`, `(*store.Store).Deliver`, `(*store.Store).Sweep`, and `tools.Register`; appkit's `db` package (its D15 and D16) owns the database handle and the migrations; appkit's `telemetry` package (its designs D11 to D14) owns the events, the writer, the ingest handler and the middleware this design wires, its `identity` package the gate, its `page` package the shared files, and its `mcp` package the endpoint. `D02-cli` decides that an empty `Args` means serve and that nothing else touches the environment. This design says how `Run` reads the drain deadline, the retention window and the services path, takes the socket the host passes in, opens the database and builds the store over it, sweeps at start and every hour, tells systemd it is ready, serves and stops, and how `Serve` treats the listener it is handed, in these shapes: a clean start over an existing database, a first start that creates the database, a stop that drains, a stop whose drain runs out, the five ways a start is refused before the database, the start refused because the database cannot be opened, and the start over a database a newer telemetry upgraded, which warns, sweeps and serves. What the handler answers at `/`, `/about` and `/tools` is `D04-pages`; what it answers at `/mcp` is `D06-mcp`, `D07-search` and `D08-count`; what a record is and how the store keeps it is `D05-store`.

## The terms every app serves on

telemetry serves on the platform's common terms, the same as every app. It serves only on a listening socket it inherits and never opens one of its own. On a host, opsctl publishes `ikigenba-telemetry.socket`, holding the Unix stream socket `/run/ikigenba/telemetry.sock`, beside `ikigenba-telemetry.service`, a `Type=notify` service that runs the binary with no arguments as the `ikigenba` user; nginx proxies telemetry's public name to that socket, and every other service on the host posts its events to the same socket at `/ingest`, never through nginx. A deploy restarts the service alone, so the socket, and the connections queued on it — siblings' events among them — outlive every restart.

telemetry takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment once it has taken the socket. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket named by `NOTIFY_SOCKET`, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace. On `SIGTERM` or `SIGINT` it stops accepting, lets the requests it already accepted finish for at most `DRAIN_SECONDS`, then cuts off whatever is left, says how many it cut off, and exits 1. It closes its own copy of the socket and never removes the socket's path. `DRAIN_SECONDS` is a positive whole number of seconds, 5 when unset or empty, with no upper limit of telemetry's own; opsctl owns its value and the unit's stop timeout.

Two things set telemetry apart from its siblings. It has a database: `RETENTION_DAYS`, a positive whole number of days, 15 when unset or empty, is how long a record stays in its trail, and `state/telemetry.db`, resolved against `Process.Dir` and so relative to the working directory in the binary, is the SQLite database `Run` opens or creates through appkit's `db.Open`, telemetry being its only writer. And it is the telemetry service: its own events go straight into that store, which is the sink of the writer `Run` builds, so no services file is needed to find the way and nothing of telemetry's reads the environment on a delivery. The environment also carries `IKIGENBA_SERVICES`, the path of the host's services file. `Run` looks it up through `LookupEnv` when it starts to serve and hands the value to the handler as `Config.ServicesPath`; the handler reads the file afresh for every page, for the banner's auth links (`D04-pages`). Nothing about the variable or the file can stop a start: unset, empty, or naming a file that is missing, unreadable or malformed, telemetry starts, serves and says nothing about it, and its pages send the auth links to the request's own space. The same environment may carry `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE`, the code the host is running; telemetry reads them once, at start, through appkit's `version.Read` in `main` (`D01-layout-and-run-seam`); its pages' footer and about screen show the release and commit of the identity it returns, and its `service.started` and its MCP `serverInfo` carry that identity's display string as its version. Neither is ever a reason not to start: with neither set the release, the commit and the string are empty and telemetry serves all the same.

The suite is a closed system: telemetry trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts a sibling — the MCP gateway calling it at its socket — to have forwarded them. Every request but an ingest has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it as it arrives, 32 lowercase hexadecimal digits from the random source `Process.Rand` supplies, and that id is the one every event about the request carries. telemetry calls no sibling.

telemetry's standard error holds only trouble: a condition it cannot continue from — a start it refuses, a database it cannot open, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off — and an event of its own trail that it could not store. One warning joins them: appkit's line over a database a newer telemetry upgraded, written once, before `READY=1`. A request it answers with a 5xx, the missing-identity 500 included, is a handled failure, recorded by that request's `request.finished` with its status and earning no line; a sibling's event the store will not take is answered 500 and is the sibling's trouble to report; a sweep writes nothing. So the handler has no stream at all, and `Run` writes only its start-up refusals, its store diagnostic, the warning `db.Open` writes through it, its accept failure, its drain cut-off, and the lines its writer writes for undelivered events. Under systemd a healthy telemetry writes nothing to the journal.

## Checking the environment

With `Args` empty, `Run` reads `DRAIN_SECONDS` first, then `RETENTION_DAYS`, then looks for its socket, and only then opens the store, so a start refused for any of the first three has touched nothing, not even the database. Each of the two values is spelled the way opsctl writes an integer: one or more ASCII digits, no sign, no leading zero, no unit, no whitespace. There is no upper limit, so a value too large for a `time.Duration` is the longest drain, or the longest window, a `time.Duration` holds rather than an error or a wrap to a negative duration. A value that is not acceptable is a usage error, quoted back verbatim, and the order fixes which is reported when more than one thing is wrong: a bad `DRAIN_SECONDS` over a bad `RETENTION_DAYS`, and either over a missing socket. The **retention window** is the duration a record is kept: fifteen days, each of twenty-four hours, when `RETENTION_DAYS` is unset or empty, and that many days otherwise.

A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one. Anything else — `LISTEN_FDS` unset, empty, `0` or not a number, `LISTEN_PID` unset or naming another process — is no socket passed in, and a count above one is a unit telemetry will not guess about. Both are usage errors with the detail line saying how to run telemetry correctly. None of the refused starts takes the descriptor, unsets a variable, opens the database, serves anything or tells systemd anything; a test sees that as `Inherit` never called, no `Unsetenv` call, no datagram, no `Accept` on any listener, and an empty `Dir` still empty.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv` and takes descriptor 3 as its listener: through `Process.Inherit` when a test supplies one, otherwise with `net.FileListener` over the real descriptor. The Go `net` documentation of `UnixListener.SetUnlinkOnClose` states that a listener made by `FileListener` does not remove the socket file when it is closed, and `FileListener` documents that closing the listener does not affect the file it was made from; closing is all telemetry ever does to the socket, so the path systemd created stays, and systemd's own copy keeps queueing connections for the next telemetry. If the descriptor cannot be made into a listener, that is trouble on the host rather than a caller's typo: `telemetry: ` and the error, exit 1, and the database is still untouched.

## The store and the sweeps

With the listener in hand, `Run` opens its database with appkit's `db.Open` (its D15 and D16): the path is the **database path**, `state/telemetry.db` resolved against `Process.Dir`, which `Run` passes as `filepath.Join(Dir, "state", "telemetry.db")`, so with an empty `Dir` it is the relative path appkit resolves against the process's working directory; the migrations are `telemetry.Migrations()`; the clock is `Process.Now`; the service is `web.ServiceName`; and the writer for appkit's warning is `Process.Stderr`. appkit creates the missing directories and the file, applies the migrations the database has not had and stamps them with that clock, and refuses a database it cannot open; how it does each is appkit's contract, and telemetry's tests do not re-prove it. They prove the wiring instead: after a start in an empty `Dir` with a fixed clock, appkit's `db.Status` reports `Dir`'s `state/telemetry.db` exactly as it reports a database the test made itself with `db.Open`, `telemetry.Migrations()` and that clock. A database an older telemetry created before it carried migrations is brought up to date the same way, keeping every record it holds, because `0001` is the schema it already has (`D05-store`).

When `db.Open` fails, the start is refused as trouble on the host: one line, `telemetry: cannot open database state/telemetry.db: ` and the error's text, exit 1, before anything is served, before systemd is told anything, and before any event is recorded. The path in the line is the relative one the manifest declares, whatever `Dir` is, so an operator reads the same line on every host; the error's text names the absolute path where appkit's does. A newline in that text is replaced by a space, so the line is one line whatever appkit's error holds. Under systemd the start fails and the socket keeps queueing for a telemetry that can serve. Two such refusals are a regular file named `state` where the directory belongs and a `state/telemetry.db` telemetry cannot open. A missing database is not this error; it is the first start.

A database a newer telemetry has upgraded, as after a deploy rolled back, records a migration this telemetry does not carry. It is not refused: data never rolls back, so older code runs on newer data. appkit's `db.Open` applies nothing to it and writes one warning line, beginning with the service name it was given and naming the lowest version this telemetry does not carry, to the writer it was given, which is `Process.Stderr`; under systemd that line reaches the journal. It is written before `READY=1`, it is the whole warning, and the trail records nothing about it. Then the start goes on exactly as over any database: `Run` sweeps, reports ready, records `service.started` and serves the trail the database holds. telemetry states nothing about the line's wording: a test compares what `Run` wrote with what its own `db.Open` call, given the same service name and a buffer, writes over the same database, and that the line begins `telemetry: ` is what shows `Run` handed appkit telemetry's name.

With the database open, `Run` builds the store over the handle with `store.New` and keeps the handle open through the drain, so a request still being handled when the stop comes can still deliver and read, and the writer's last deliveries, `service.stopping` among them, can still be stored; it closes the handle once `Serve` has returned. The store does not own the handle; `Run` does.

Then the first sweep. Before telemetry reports ready it removes every record whose time is before the moment of the sweep less the retention window, so a telemetry that was stopped for a while never serves a stale trail; the moment is read from `Process.Now`, the sweep is `Sweep` on the store it opened, and a test with a fixed clock and a database it filled beforehand sees exactly the records older than the window gone once `READY=1` arrives, and the rest kept. Then once every hour for as long as it runs: `Run` pauses for one hour through `Process.Sleep` — the same pause the writer waits between delivery attempts with, so a test tells the two apart by the duration, an hour against the writer's fifty and one hundred milliseconds — and when the pause returns while the context is not done, sweeps again at the clock's new moment, then pauses again. A test's `Sleep` that blocks an hour-long pause until the test releases it, after advancing the clock, triggers the next sweep without a timer; the sweep is complete before the next hour-long pause begins, so a `Sleep` that signals the test when it is called again is the moment the test reads the trail. A sweep that fails writes nothing and changes nothing telemetry says; the next sweep, an hour later, tries again, so the removals are promised only while the database can be written, and a record past the window is never promised gone from a database that cannot be. The sweep is routine, not trouble, and nothing a sibling posts is refused for its age.

## Readiness and the trail of a run

The socket has been listening since systemd made it, so from that moment every connection is queued and will be answered: ready is true before the first `Accept`, and sending it first means a failure to send is reported without anything having been served. That failure is trouble — under `Type=notify` systemd would otherwise wait out its start timeout — so it is `telemetry: ` and the error, exit 1, and no connection is ever accepted and no event recorded.

When it serves, `Run` builds one telemetry writer with appkit's `telemetry.New`, naming the service `web.ServiceName` and the version `Process.Version`, the display string `main` read, delivering to the store it opened — a `*store.Store` is a `telemetry.Sink` — stamping with `Process.Now`, pausing with `Process.Sleep`, drawing request ids from `Process.Rand`, and writing the lines for undelivered events to `Process.Stderr` through the same guard as its own lines. It makes the MCP server by calling `Process.MCP` with that writer, once, and hands the same writer to the handler as `Config.Telemetry`, so every event of the process goes through one queue into one store. The **run's writer** is that writer, and the store it delivers to is where every record of telemetry's own lands, in arrival order beside the siblings' (`D01-layout-and-run-seam`).

Once it has sent `READY=1`, and before it accepts any connection, `Run` calls `Writer.Ready`, so `service.started`, carrying `Process.Version`, is the first record telemetry makes at each start, before any request's. When `ctx` is done it drains the server first, so every request that finishes records its `request.finished`, and then, through `Serve`'s `stop`, inside the same drain window — a context whose deadline is the drain deadline — calls `Writer.Shutdown` with the reason, which records `service.stopping` as the last event and delivers what is queued. The reason is the text of `context.Cause(ctx)`, which in the binary is the signal's name, `SIGTERM` or `SIGINT`. When the requests use the whole window, nothing is left for storing: every event still queued, `service.stopping` included, is written to `Stderr` as an `undelivered event` line before the stop line, which is always `Run`'s last, and `Serve` cuts the remaining requests off only after `stop` has returned, so a cut-off request's late `request.finished` is recorded after `Shutdown` began and is written out, never stored. Past the deadline, appkit's writer gives every delivery it begins a context that is already done (its D12), and the store refuses such a delivery without touching the trail (`D05-store`), so the trail holds no `service.stopping` from a run whose drain ran out, and no `request.finished` for a request it cut off.

Storing the trail never holds up readiness or a request: appkit's writer queues and returns, so a store that fails changes neither when `READY=1` is sent nor any answer; the events go to `Stderr` instead, one `telemetry: undelivered event: ` line each, in the order they were recorded, and telemetry keeps serving. A test proves the trail at this seam by reading it back the way an agent does — through the tools over the listener it made, or through a store over a handle `db.Open` returns for the database path once `Run` has returned — and the undelivered lines through the events the writer cannot deliver at a stop: the `service.stopping` of a drain that ran out, and the `request.finished` of a request it cut off. A test of `Run` has no hand on the handle `Run` opened, so it makes that store refuse writes from outside: once `READY=1` has arrived it opens its own handle on the database path with `telemetry.Migrations()` and, through `DB.Write`, creates a trigger that aborts every insert into `records`, the table the schema declares (`D05-store`); every delivery then fails, and the run's events go to `Stderr` while the answers are unchanged. At the handler the same outcome is proved over a store whose handle the test made fail with `SetFailing(true)`.

This design assumes a clock — `Process.Now` for `Run`, the `Now` of the writer's configuration for the handler — that reads times in the UTC years 0 through 9999, the years an RFC 3339 time can spell, and each requirement whose outcome depends on an event of telemetry's being recorded says so in its own text. Go's `time.Time.MarshalJSON` documents that a time it cannot represent as RFC 3339, a year out of range say, is reported as an error, and appkit's `Event.MarshalJSON` rejects a malformed event, so an event stamped outside those years cannot be encoded: it becomes neither a record nor an `undelivered event` line, and what telemetry records or writes under such a clock is not contract.

## Serving and stopping

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next telemetry — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then closes their connections without the rest of their responses and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. The count is of calls to `h.ServeHTTP` that had begun and not returned; a connection still sending its request headers is not a request yet, and is closed at once like an idle one. `stop` is called once, when the drain is over — as soon as every request has finished, or at the deadline before anything is cut off — with a context that ends at the deadline; that is the one moment that is after every finished request and before any cut-off request can finish, which is what `Run` needs to close its trail. `internal/server` knows nothing of telemetry: `stop` is just a function. `Run` reports a cut-off as `telemetry: stopped with <n> requests unfinished` (`1 request` when `<n>` is 1) and exits 1. `Serve`'s behaviour for a drain that is not positive is not contract.

An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `telemetry: ` and the error, exit 1. The drain is stated at two seams. At `Serve` a test hands in the duration. At `Run` it exists only as `DRAIN_SECONDS`, so the requirement is what a client sees: a request still being handled when `ctx` is done is given the drain deadline and cut off less than a second after it. A test holds a request open — a `POST /mcp` whose declared `Content-Length` exceeds the bytes it sends — with `DRAIN_SECONDS=1`, unset and empty.

`Serve` is silent in its own right: Go's `net/http` documents at `Server.ErrorLog` that, when that field is nil, server errors go through the `log` package's standard logger to the real standard error, so `Serve` gives the server an `ErrorLog` that goes nowhere. A healthy run whose trail is stored is silent from start to finish; nothing reaches `Stdout` while serving. Once `Run` has returned it writes nothing more: an undelivered-event line for an event recorded after the drain deadline, a cut-off request's `request.finished` say, appears before the stop line or not at all. `Run` makes sure no two writes to `Stderr` are ever in progress at once, its own lines and the writer's alike, because requests are concurrent and a test's `Stderr` is a `bytes.Buffer` the race detector watches. No read, write or idle timeouts are contract; the build sets `ReadHeaderTimeout` because the lint gate's gosec `G112` demands it, and must not set a write timeout that could cut a response short inside the drain.

## The handler's rules on every route

`web.Handler` splits its surface in two at the door. A request whose path is exactly `/ingest` goes to appkit's `telemetry.IngestHandler` over `Config.Store` and nowhere else: no identity is looked for — a sibling's writer, not a caller, posts there — and no event of telemetry's own is recorded for it, since one request per sibling event would double the trail. What that handler answers — 405 with `Allow: POST` for a method other than `POST`, 415 for a body not declared `application/json`, 413 past `telemetry.MaxEventBytes`, 400 for a body that is not exactly an event, 204 once the store has taken the event, 500 when it will not — is appkit's contract (its D13), stated here only as the handler's answer being that handler's, which a test proves by comparing against one it builds with `telemetry.IngestHandler` itself over a store of its own, and by posting an event and finding it, byte for byte, as a record.

Every other request goes to appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping appkit's `identity.Require`, wrapping the mux: `/`, `/about` and `/tools` (`D04-pages`), `page.Static()` at `page.StaticPrefix`, and `Config.MCP` at exactly `/mcp`, with the four tools registered on that server by `tools.Register` once, when the handler is built. So a request without `X-User-Id` is answered by appkit's identity middleware before the path or the method is looked at — a lost caller without identity gets the 500, not the 404 — and every such request still records its two events. Routing is on the request's `URL.Path` as `net/http` decodes it, exactly, and never redirects: `/mcp/`, `/ingest/`, and any path beneath either, `/assets/...`, `/_appkit` without its slash, a trailing-slash variant and a path holding `.` or `..` segments are all **telemetry's 404**, one line of plain text, the copy constant `web.NotFound`, with no banner and no footer, whatever the method; which is why the handler cannot lean on `http.ServeMux`'s pattern matching as it stands, since that would answer some of them with a redirect.

The shared files are routes like any other, served by the handler, which passes every request whose path begins with `/_appkit/` to the handler `page.Static()` returns, unchanged: that handler compares the request's whole `URL.Path` against `/_appkit/<name>` itself, so no prefix is stripped. Delegation is one requirement; the requirements after it state what telemetry fixes about the answer, as its own observable behaviour, so that telemetry's tests fail if a different appkit release stopped giving it. They agree with appkit's published contract for `page.Static` (its D04), which fixes the same files, types, validators and refusals. Five paths name a file by a fixed name: `/_appkit/` followed by `theme.css`, `feedback.js`, `favicon.svg`, `OFL.txt` or `TABLER-LICENSE.txt`, compared byte for byte; any other name under `/_appkit/`, the `launcher.js` an earlier appkit served included, answers 404. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit are not served, and a font path with its hash taken out answers 404. telemetry never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads (`D04-pages`), and the paths the served stylesheet names, each a `url("…")` of a name ending in `.woff2` beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet telemetry serves. Every 200 and 304 for a served name carries one strong `ETag`; a font path's carries one `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again, and every other served name's one `Cache-Control: no-cache`, so a browser keeps its copy but asks each time; the tag's value is opaque here, and that different content yields a different tag is appkit's property, since telemetry embeds nothing of its own under `/_appkit/`. Revalidation is fixed only for a plain request, one carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`; several `If-None-Match` lines, a malformed list, `Last-Modified`, and `If-Modified-Since` without `If-None-Match` are not fixed here.

Every request the handler answers other than an ingest, whatever its path and whether or not it carries an identity, records `request.started` as it arrives and `request.finished` once its answer is complete, with every other event of the request — a tool call's `tool.called` — between them, all under the request's id and its `X-User-Id`. The handler records no event of its own beyond these: what each records, and when, is appkit's contract, and the requirements below state what a test of telemetry observes of it. The handler never waits on the store to answer: a page does not need the store, and a store that will not take telemetry's own events costs the trail those events, written out by the writer, and the request nothing.

## REQUIREMENTS

- R-OZKD-A5FT: `Serve` MUST accept connections on `ln` and answer every request received on them over HTTP/1.1 with the response `h` produces for that request, and MUST NOT return while `ctx` is not done and serving has not failed.
- R-P0S9-NX6I: When `ctx` is done, `Serve` MUST stop accepting connections and close `ln`, and MUST close every connection that carries no request.
- R-P206-1OX7: When `ctx` is done, `Serve` MUST let every call to `h.ServeHTTP` already in progress continue and MUST deliver the complete response of every such call that returns within `drain` after `ctx` was done; when every such call has returned and its response has been delivered before `drain` has elapsed, `Serve` MUST then call `stop`, when it is not nil, and MUST return nil once that call has returned, without waiting for `drain` to elapse.
- R-P382-FGNW: When `n` calls to `h.ServeHTTP`, `n` at least 1, are still in progress once `drain` has elapsed after `ctx` was done, `Serve` MUST call `stop`, when it is not nil, and only after that call has returned close the connections those requests arrived on without writing the rest of their responses, and MUST then return a `*DrainError` whose `Unfinished` is `n`, without waiting for those calls to `h.ServeHTTP` to return.
- R-P4FY-T8EL: `Serve` MUST call `stop` at most once, MUST NOT call it while `ctx` is not done or when it returns because serving failed while `ctx` was not done, and MUST pass it a context that is done once `drain` has elapsed after `ctx` was done, and not before.
- R-P5NV-705A: `(*DrainError).Error` MUST return exactly `"stopped with 1 request unfinished"` when `e.Unfinished` is 1, and exactly `"stopped with " + strconv.Itoa(e.Unfinished) + " requests unfinished"` for every other value of `e.Unfinished`.
- R-P6VR-KRVZ: When serving fails while `ctx` is not done, `Serve` MUST return a non-nil error, and `Serve` MUST NOT return nil for any reason other than `ctx` being done.
- R-P83N-YJMO: `Serve` MUST write nothing to the `log` package's default logger and nothing to any process stream, whatever `ln` and `h` do: the diagnostics `net/http`'s server writes through its `ErrorLog`, such as an `Accept` error it retries or a handler that panics, MUST be discarded, so that a test which points the `log` package's output at a buffer and drives `Serve` with a listener whose `Accept` returns a temporary error and a handler that panics finds the buffer empty when `Serve` returns.
- R-PAJG-Q342: `Run` MUST accept a non-empty `DRAIN_SECONDS` value if and only if it consists of one or more ASCII decimal digits, the first of which is not `0`, and no other characters, whatever the magnitude of the integer those digits denote, so that `0`, `-1`, `2.5`, `5s`, `05`, ` 5`, and `abc` are refused and no value is refused for being large.
