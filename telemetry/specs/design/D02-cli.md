# D02-cli

telemetry as a command: what `cli.Run` does with the arguments that `D01-layout-and-run-seam` hands it through `Process`. This design covers the four commands (`--version`, `manifest`, `--help`, `db status`), the usage error, and the rule that a command never looks at the environment or the socket, and that only `db status` looks at the database. When `Args` is empty, telemetry serves, and everything from there — the drain deadline, the retention window, the socket the host passes in, the store, the sweeps, readiness, the drain on a signal, and the failures of each — is `D03-serve`; what the handler then answers is `D04-pages` and the designs it leads to.

`Run` takes at most two arguments and the arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching the environment: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity, `manifest` writes `Manifest` exactly as `D01-layout-and-run-seam` declares it, and `--help` writes `Usage`, the constant `D01-layout-and-run-seam` declares and whose value this design fixes byte for byte, so the help text is contract. The one two-word command is `db status`. Any other `Args` is a usage error. The argument telemetry complains about is the first one it does not take: the first element when that is not a recognised word; `db` itself when it stands alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`, which takes nothing; and otherwise the second element, which is surplus after `--version`, `manifest` or `--help` whatever it says. An argument that starts with `-` is an unknown option; any other is an unknown command. Both diagnostics follow the repository's command-line conventions: the first line begins `telemetry: `, and after exactly one empty line comes the hint to run `telemetry --help`, unprefixed because telemetry is speaking for itself. The usage text is never written to `Stderr`.

`db status` is an operator's look at the database: which of the migrations the binary carries the database `state/telemetry.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status` (its D16), which telemetry calls with the path `state/telemetry.db` resolved against `Process.Dir` (the process's working directory when `Dir` is empty, as `main` leaves it) and the migrations `telemetry.Migrations()` returns, writing straight to `Stdout`. telemetry adds nothing to the lines and states nothing about their format; its requirements say only that the bytes on `Stdout` are the ones `db.Status` writes for that path and those migrations, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database, never with a format it spells out. `db.Status` only looks: it applies nothing, sweeps nothing, changes nothing and creates nothing, so before telemetry's first start `db status` reports every migration pending and leaves the directory as it was. When it returns an error, telemetry says so on one line, `telemetry: ` and the error's text, and exits 1; a newline in that text is replaced by a space, so the diagnostic is one line whatever appkit's error holds. Whatever `db.Status` had already written to `Stdout` stays there: the findings are product, and the repository's command-line conventions send a report to stdout whole, bad news included. That is the one case in which a failure may leave anything on `Stdout`. A database that records a migration this telemetry does not carry, one a newer telemetry upgraded, is not a failure: older code runs on newer data (`D03-serve`), appkit's `db.Status` lists every line, the unknown version among them, and returns nil, so `db status` writes nothing to `Stderr` and exits 0. A database that cannot be read yields no lines at all and exits 1. `db status` reads no environment, takes no socket and reads no clock.

The help text says what telemetry serves — ingest at `/ingest`, the MCP tools at `/mcp`, and a landing page at `/` — and where — on the socket systemd passes in — and names the exit codes, which is where the contract the rest of the design realises is declared: 0 for success, 1 for a failure, 2 for a usage error. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a drain deadline or a retention window that is not a number) exits 2, while trouble on the host once telemetry is past its checks — a socket that cannot be taken, a database it cannot open, a drain that runs out — exits 1, and so does a `db status` whose database cannot be read. The constant for 1 is `ExitServerFailed`, the help text's `failure`.

Arguments are checked before anything else. A command never needs a socket, and only `db status` reads a database, so `telemetry --version` succeeds with nothing passed in and `telemetry bogus` fails as an unknown command whatever the environment holds; `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the banner source, the server maker or the clock unless `Args` is empty. A command records no event: the trail is what telemetry records while it serves, and a command never builds the writer. Only `db status` reads anything under `Dir`, and it creates nothing there; every other command, and every usage error, leaves `Dir` as it found it, so `telemetry db bogus` reads no database and creates nothing.

Every failure but that one `db status` case leaves `Stdout` empty, so a caller that reads the streams separately sees a product or a complaint, never a mixture. Every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole even when another writer such as journald interleaves with the same stream.

## The two files under etc/

The manifest and the nginx fragment are facts about the binary, so the binary carries them as the constants `Manifest` and `NginxConf`. The committed `etc/manifest.toml` holds exactly the text of `Manifest`, so the checkout can be read without a build, and `devctl build` refuses an app where the two differ; `etc/nginx.conf` holds exactly the text of `NginxConf`, and the host's nginx includes it in telemetry's server block so that the public `/ingest` answers 404. The build run writes both files from the constants and keeps them in step, as `D01-layout-and-run-seam` records. Neither file is a requirement: `AGENTS.md` forbids every test to read the checkout, `etc/` included, and a requirement no admitted test can decide is not a requirement. The constants' values are contract, proved by use — `manifest` prints `Manifest`, and `NginxConf` is a declared constant a test compiles against — and the files are their copies. Nothing prints the fragment: the bootstrap story fixes the usage text and its commands, `manifest` and `db status`, and a command that printed the fragment would be a story change.

## REQUIREMENTS

- R-QXCY-WVJI: `Usage` MUST be exactly `"Usage: telemetry [command]\n\nServe the suite's trail of events: ingest at /ingest, MCP tools at /mcp, and\na landing page at /, on the socket systemd passes in. With no command, serve.\n\nCommands:\n  manifest    print the app manifest\n  db status   print applied and pending migrations\n\nOptions:\n  --help      print this help\n  --version   print the version\n\nExit codes:\n  0  success\n  1  failure\n  2  usage error\n"`.
- R-THDE-02PA: When `Args` is exactly `["--version"]`, `Run` MUST write `p.Version` followed by a single `"\n"` to `Stdout` and nothing else, write nothing to `Stderr`, and return `ExitSuccess`, so that an empty `p.Version` writes exactly `"\n"`.
- R-OPT6-7ZI9: When `Args` is exactly `["manifest"]`, `Run` MUST write exactly `Manifest` to `Stdout` and nothing else, write nothing to `Stderr`, and return `ExitSuccess`.
- R-OR12-LR8Y: When `Args` is exactly `["--help"]`, `Run` MUST write exactly `Usage` to `Stdout` and nothing else, write nothing to `Stderr`, and return `ExitSuccess`.
- R-QYKV-ANA7: When `Args` is exactly `["db", "status"]`, `Run` MUST write to `Stdout` exactly the bytes, and nothing else, that appkit's `db.Status` (package `github.com/ikigenba/ikigenba/appkit/db`) writes to its writer when called with a context that is not done and a `db.Config` whose `Path` is `filepath.Join(p.Dir, "state", "telemetry.db")` and whose `Migrations` is the root package's `telemetry.Migrations()`, over the database as it is when `Run` is called; so that `Run` reports the migrations of `state/telemetry.db` under `p.Dir`, or under the process working directory when `p.Dir` is empty.
- R-QZSR-OF0W: When `Args` is exactly `["db", "status"]` and the `db.Status` call R-QYKV-ANA7 describes returns nil, `Run` MUST write nothing to `Stderr` and return `ExitSuccess`.
- R-TILA-DUFZ: When `Args` is exactly `["db", "status"]` and the `db.Status` call R-QYKV-ANA7 describes returns a non-nil error `err`, `Run` MUST write exactly `"telemetry: " + r + "\n"` to `Stderr`, where `r` is `err.Error()` with every newline character replaced by one space, and return `ExitServerFailed`, having written to `Stdout` what R-QYKV-ANA7 states; so that a `p.Dir` whose `state/telemetry.db` is a regular file that is not a SQLite database gets nothing on `Stdout` and that one line on `Stderr`.
- R-TJT6-RM6O: When `Args` is exactly `["db", "status"]` and `p.Dir`'s `state/telemetry.db` is a SQLite database the process can read whose `schema_migrations` holds, besides the version of every migration `telemetry.Migrations()` holds, a version that `telemetry.Migrations()` does not hold, `Run` MUST write to `Stdout` what R-QYKV-ANA7 states, write nothing to `Stderr`, and return `ExitSuccess`, so that a database a newer telemetry upgraded is reported line by line, its unknown version among the lines, and is not a failure.
- R-R28K-FYIA: When `Args` is exactly `["db", "status"]` and `p.Dir` names an empty directory, that directory MUST still be empty when `Run` returns.
- R-R4OD-7HZO: When `Args` is not empty and is not exactly `["db", "status"]`, `Run` MUST create, remove or change nothing under `p.Dir`, so that when `p.Dir` names an empty directory it is still empty when `Run` returns.
- R-R5W9-L9QD: `Run` MUST treat `Args` as a usage error unless `Args` is empty or is exactly one of `["--version"]`, `["manifest"]`, `["--help"]`, or `["db", "status"]`.
- R-R745-Z1H2: On a usage error from `Args`, the offending argument MUST be `Args[0]` when `Args[0]` is none of `--version`, `manifest`, `--help`, or `db`, or when `Args` is exactly `["db"]`; `Args[2]` when `Args[0]` is `db` and `Args[1]` is `status`; and `Args[1]` otherwise.
- R-OUOR-R2H1: On a usage error from `Args`, `Run` MUST write exactly `"telemetry: unknown option '" + arg + "'\n\nsee 'telemetry --help' for usage\n"` to `Stderr` when the offending argument `arg` begins with `-`, and exactly `"telemetry: unknown command '" + arg + "'\n\nsee 'telemetry --help' for usage\n"` otherwise, MUST write nothing to `Stdout`, and MUST return `ExitUsage`.
- R-R8C2-CT7R: When `Args` is not empty, `Run` MUST return without calling `LookupEnv`, `Unsetenv`, `Inherit`, `Banner`, `MCP`, `Now`, `Sleep` or `Rand`'s `Read`, without taking file descriptor 3, and without sending anything to a notification socket, so that the outcome of a command or a usage error is the same whatever the environment holds, and so that a `Process` whose `Banner`, `MCP`, `Inherit`, `Now`, `Sleep` and `Rand` are nil is enough for every command.
- R-R9JY-QKYG: Whenever `Run` returns a value other than `ExitSuccess` it MUST have written nothing to `Stdout` other than, when `Args` is exactly `["db", "status"]`, the bytes R-QYKV-ANA7 states, and every diagnostic `Run` writes MUST be delivered as a single call to `Stderr.Write` whose first line begins `telemetry: `.
