# D05-store

The store is the trail. `internal/store` owns telemetry's one SQLite database: the schema it creates, the insertion of a record, which is what makes `*store.Store` a `telemetry.Sink` and lets the ingest handler and telemetry's own writer share one path into the trail, the sweep that removes records older than a moment, and the five reads the four MCP tools are built on. `D01-layout-and-run-seam` declares `Store`, `Open`, `Close`, `Deliver` and `Sweep` and defines a record, the trail and the arrival order; this document states what they do and declares the reads, the filter they share, the page a search answers with, its cursor, the catalog's entries and the groups a count is split into. `D06-mcp`, `D07-search` and `D08-count` use these names and declare none of their own against the database.

## One database, one writer

The database is the one the manifest declares, `state/telemetry.db` on a host, and telemetry is its only writer. `Open` takes the source `cli.Run` is given: an ordinary filesystem path, for which it creates the missing parent directories and the database with its schema on a first start and opens the existing database afterwards, or one of SQLite's special sources, the empty string, `:memory:` and a `file:` URI, which keep the meaning the driver gives them (SQLite's documentation of in-memory and temporary databases and of URI filenames) and for which nothing is created on the filesystem. A test hands `Open` a path inside a temporary directory or an in-memory source; whichever it hands, the store it gets back is one database for as long as it is open, so a record one call stores is read by every later call, which a pool of in-memory connections would not give. `Open` never settles for a database it cannot write: a database the process can only read would fail the first delivery, so it is refused at the start, where the diagnostic is `D03-serve`'s to write. A failure after the start, the directory holding the database made unwritable while telemetry runs or a filesystem that has filled, is a delivery that fails and a sweep that fails, each reported to its caller and nothing more; the store recovers on its own once the database can be written again, with no reopening. The stories' operator makes such a database's directory unwritable; the mechanism a test uses for it is below.

The driver is `modernc.org/sqlite`, registered with `database/sql` under the name `sqlite`; which release is data (`AGENTS.md`, `go.mod`). The schema is contract because an operator and the host's replication see it: a table `records` holding the envelope, one row per record, and a table `attrs` holding one row per attribute of each record, so an attribute of any service is found by one index without a schema per service. A record's row carries an integer `id` that grows with the arrival order, so that two records with the same time are told apart by the order telemetry took them in; its time as a count of microseconds since the Unix epoch, which is what the filters compare and the buckets truncate; the four strings of the envelope; and the attributes as the JSON text they have in the record's JSON, so the record is answered exactly as it was ingested without being rebuilt. Each attribute's row carries the value as its JSON text too, which is what keeps a number apart from a string when a filter asks for one. A test proves the schema the way an operator would read it: it opens the same source with the driver and queries `sqlite_master` and the `table_info` and `index_info` pragmas (SQLite's documentation of the schema table and of `PRAGMA table_info` and `PRAGMA index_info`).

A store that cannot be read — closed, or its `records` table gone — answers every read with an error that is neither `ErrCursor` nor `ErrGroupBy`, which is what lets the tools tell a trail they cannot read from a question they cannot answer; a malformed cursor and an unknown grouping are still reported as such, since telling them needs no database. The cannot-store cases are made testable by an outcome the store guarantees rather than by a setting: a database whose directory cannot be written is a database that cannot be written (R-3IWT-P0S2). The journal mode is the store's own choice and not contract, since a fresh connection reports only a mode the database file persists; SQLite's default, the rollback journal (SQLite's documentation of `PRAGMA journal_mode`), gives that outcome, because in it every write transaction creates a journal file in the database's directory, so a database whose directory cannot be written is a database that cannot be written, at once and on the connection the store already holds, and once the directory can be written again the store writes again with nothing reopened. A test therefore removes the write permission of the directory holding the database file and restores it, which is a fixture inside its own temporary tree, and it needs no hand on the `*Store` to do so, which is what a test of `cli.Run` lacks (`S12`) and a test of the handler has only through `Close` (`S06`). Removing the file's own write permission is not such a mechanism: the connection the store already holds was opened before the change and keeps writing, which a probe of the driver confirms, and the write-ahead-log mode would defeat the directory mechanism too, since its journal persists and needs no new file once created. The stories' precondition is accordingly the directory holding the database made unwritable, which is the same thing to an operator and immediate for a test. A permission binds only an ordinary user: the gates run as one (`AGENTS.md`), and a root user, whom it does not bind, would see such a delivery succeed.

## Deliver and the record

`Deliver` is what both the ingest handler and telemetry's writer call, so it never writes to any stream and never refuses an event for its age or its service. A valid event becomes exactly one record; the record's JSON is the bytes `Event.MarshalJSON` returned for the event, and the `Record` the reads return is that JSON taken apart: the time at the microsecond, the four strings, and the `attrs` member as it is. An event the store cannot take because the database cannot be written is an error that does not wrap `telemetry.ErrRejected`, so the writer retries it and then writes its `undelivered event` line (`S12`), and the ingest handler answers 500 so the sender retries (`S06`). An event whose `MarshalJSON` fails can never become a record, and that error does wrap `ErrRejected`; neither caller hands the store such an event, since the ingest handler admits only valid bodies and the writer writes a malformed event out itself. `Deliver` honours its context before it touches the database: a `ctx` that is already done is an error that wraps `ctx.Err()`, does not wrap `ErrRejected`, and stores nothing. appkit's writer leans on exactly this at a stop. Its D12, in its requirement on the context of a `Deliver` call, states that the context the writer passes to each `Deliver` call is done once the context given to a `Shutdown` in progress is done, and in its requirement on `Shutdown` that once `Shutdown`'s context is done it writes out every event still queued, the one whose delivery is in progress included, without waiting for that delivery to return; the ids are appkit's and are not repeated here, since every id-shaped string under `specs/design` enters telemetry's gap. So once the drain deadline has passed, a delivery that begins stores nothing, and a stopping run's `service.stopping` goes to standard error and never lands in the trail, which is what `D03-serve` promises for a drain that ran out (`S02`).

## Sweep

`Sweep` removes every record whose time is before the moment it is given, and the attributes of each, and leaves every record at or after that moment as it was. It works in bounded batches so a long-stopped telemetry whose database holds weeks of records does not hold one write transaction open across the whole backlog; the batch size is not observable and is not contract. When it runs is `D03-serve`'s: once at start and after every hour, with the moment `RETENTION_DAYS` days before the clock.

## The reads

Every read answers from the trail as it is when the read runs and changes nothing. A **filter** is the one `search` and `count` share: a time range, `Since` inclusive and `Until` exclusive, compared as instants; any-of lists of services and events; an exact user and an exact request id, each a pointer so that the empty string, which many records carry, can be asked for; and attributes, every pair of which a record must carry with exactly that value, a number matching a number and a string a string, which is decided by comparing the JSON text of the two. A value in the filter's attributes that is not a valid attribute value, such as the `null` or the nested object a client might send, matches no record, since no record carries one. `Search` reads the matching records newest first, and among records with one time in the reverse of the arrival order, so a search reads the trail backwards exactly; it answers one page of at most `limit` records and a cursor when more match. The cursor is opaque to the client and holds no server state: it encodes the position of the last record answered, its time and its id, and a checksum, so that a cursor no search issued, a made-up string or one damaged in transit, is told from a real one and refused, and so that a cursor still works after a restart and after a sweep has removed the record it points at. It encodes the position only; the filters are the caller's to send again, and a cursor sent with other filters continues from the same position under those filters. `Trace` reads one request's records oldest first, in arrival order among equal times, so the sequence reads as the services lived it. `Catalog` reads what the trail holds by name: the services, each service's events, and for each event how many records, the newest time and the attribute keys. `Count` counts the matching records, and `CountBy` splits that count by a field of the envelope, by a time bucket, or by an attribute; the groups of a field or an attribute are ordered by count descending then key ascending, the buckets oldest first. An attribute group is keyed by the value's text, a string as itself and a number or boolean as its JSON text, because the group's key is answered as a JSON string (`D08-count`); an attribute whose values differ only in type, the number 200 and the string `200`, therefore falls in one group, while the filter keeps them apart. `GroupBy` is the spelling the tool receives, and a spelling that is none of the eight forms is `ErrGroupBy`, which the tool turns into its own refusal.

## Consumer tasks

The ingest handler and the writer share the store: `cli.Run` opens it with `store.Open(p.DBSource)`, hands it to `telemetry.New` as the `Sink` and to `web.Handler` as `Config.Store`, and `web.Handler` mounts `telemetry.IngestHandler(cfg.Store)` at `/ingest` and registers the tools with `tools.Register(cfg.MCP, cfg.Store)`. The sweep at start is `s.Sweep(ctx, now.Add(-retention))`.

A test fills a store through `Deliver` with events whose times, services, users, request ids and attributes it chooses, then reads them back: `s.Search(ctx, store.Filter{Services: []string{"dummy"}}, 50, "")` for the newest page and `s.Search(ctx, f, 50, page.Next)` for the one after it; `s.Trace(ctx, id)` for one request; `s.Catalog(ctx, "", "")` for the whole catalog; `s.Count(ctx, f)` and `s.CountBy(ctx, f, store.ByHour)` or `store.GroupBy(store.AttrPrefix + "status")` for the counts. It ages records by calling `s.Sweep` with a later moment, never by waiting. It makes a delivery fail by closing the store, or by removing the write permission of the directory holding the database file, and sees `Deliver` return an error that does not wrap `telemetry.ErrRejected`; it restores the permission and sees the next `Deliver` on the same store succeed. It hands `Deliver` a context it has already cancelled and sees an error that wraps `context.Canceled` and a trail unchanged. It proves the schema by opening the same source with `sql.Open("sqlite", source)` and reading `sqlite_master`, and the cannot-store outcome by removing and restoring the write permission of the directory holding the database file.
