# D05-store

The store is the trail. `internal/store` owns telemetry's schema and everything telemetry does with its SQLite database through appkit's `db` handle: the insertion of a record, which is what makes `*store.Store` a `telemetry.Sink` and lets the ingest handler and telemetry's own writer share one path into the trail, the sweep that removes records older than a moment, and the five reads the four MCP tools are built on. `D01-layout-and-run-seam` declares `Store`, `New`, `Deliver`, `Sweep` and `Migrations` and defines a record, the trail and the arrival order; this document states what they do and declares the schema, the reads, the filter they share, the page a search answers with, the position a page continues from, the catalog's entries and the groups a count is split into. `D06-mcp`, `D07-search` and `D08-count` use these names and declare none of their own against the database.

## One database, one writer

The database is the one the manifest declares, `state/telemetry.db` on a host, and telemetry is its only writer. Opening it is appkit's: `db.Open` (appkit's D15 and D16) creates the missing directories and the file, sets the journal mode and the rest of the connection's settings, refuses a database it cannot write, applies the migrations the database has not had, and opens one that records a migration it was not given, one a newer telemetry upgraded, applying nothing to it and writing one warning line to the `Stderr` it is given; `DB.Read` and `DB.Write` run the transactions, `Write` on the one writer. That contract is appkit's, and telemetry's design restates none of it and its tests re-prove none of it. `cli.Run` opens the handle (`D03-serve`) and builds the store over it with `store.New`; the store neither opens nor closes a handle, so whoever opened it closes it, and a test builds a store the same way over a handle on a file in its own temporary directory. Every write the store makes, a delivery and a sweep, is a `Write`, and every read a `Read`. A failure after the start, storage that has begun refusing writes while telemetry runs, is a delivery that fails and a sweep that fails, each reported to its caller and nothing more; the store recovers on its own once the database can be written again, with no new handle.

The schema is contract because an operator and the host's replication see it. It is two migrations, which the root package carries as `migrations/0001_trail.sql` and `migrations/0002_attrs_record.sql` (`D01-layout-and-run-seam`). `0001` creates a table `records` holding the envelope, one row per record, and a table `attrs` holding one row per attribute of each record, so an attribute of any service is found by one index without a schema per service. A record's row carries an integer `id` that grows with the arrival order, so that two records with the same time are told apart by the order telemetry took them in; its time as a count of microseconds since the Unix epoch, which is what the filters compare and the buckets truncate; the four strings of the envelope; and the attributes as the JSON text they have in the record's JSON, so the record is answered exactly as it was ingested without being rebuilt. Each attribute's row carries the value as its JSON text too, which is what keeps a number apart from a string when a filter asks for one. `0002` adds one index, `attrs_record_key` on `attrs(record_id, key)`, and changes nothing else (see "Served by the database" below). Each migration creates every table and index only if it does not exist and seeds nothing, so a database an older telemetry created before it carried migrations, which already holds `0001`'s schema and its records, is adopted as it is: `db.Open` applies `0001` to it, which changes nothing, then `0002`, which adds the index, and records both as applied. A test proves the schema the way an operator would read it: it opens a fresh database in its own temporary directory with `telemetry.Migrations()` and, inside a `DB.Read`, queries `sqlite_master` and the `table_info` and `index_info` pragmas (SQLite's documentation of the schema table and of `PRAGMA table_info` and `PRAGMA index_info`). It proves the adoption by storing records through a store, dropping `schema_migrations` through a `DB.Write`, and opening the file again with telemetry's migrations.

A store whose handle has been made to fail answers every call with an error, and every read's error is not `ErrGroupBy`, which is what lets the tools tell a trail they cannot read from a question they cannot answer; an unknown grouping is still reported as such, since telling it needs no database. A malformed page token never reaches the store: `D07-search` refuses it before the store is read. The cannot-store and cannot-read cases are made testable by appkit's failure seam, not by a fixture on the filesystem: a test calls `SetFailing(true)` on the handle its store was built over, sees every `Deliver` fail with an error that does not wrap `telemetry.ErrRejected` and every read fail, then calls `SetFailing(false)` and sees the same store deliver and read again with nothing reopened. The journal mode is appkit's (WAL, which the host's replication also needs), and no requirement of telemetry's depends on it.

## Deliver and the record

`Deliver` is what both the ingest handler and telemetry's writer call, so it never writes to any stream and never refuses an event for its age or its service. A valid event becomes exactly one record; the record's JSON is the bytes `Event.MarshalJSON` returned for the event, and the `Record` the reads return is that JSON taken apart: the time at the microsecond, the four strings, and the `attrs` member as it is. An event the store cannot take because the database cannot be written is an error that does not wrap `telemetry.ErrRejected`, so the writer retries it and then writes its `undelivered event` line, and the ingest handler answers 500 so the sender retries. An event whose `MarshalJSON` fails can never become a record, and that error does wrap `ErrRejected`; neither caller hands the store such an event, since the ingest handler admits only valid bodies and the writer writes a malformed event out itself. `Deliver` honours its context before it touches the database: a `ctx` that is already done is an error that wraps `ctx.Err()`, does not wrap `ErrRejected`, and stores nothing. appkit's writer leans on exactly this at a stop. Its D12, in its requirement on the context of a `Deliver` call, states that the context the writer passes to each `Deliver` call is done once the context given to a `Shutdown` in progress is done, and in its requirement on `Shutdown` that once `Shutdown`'s context is done it writes out every event still queued, the one whose delivery is in progress included, without waiting for that delivery to return; the ids are appkit's and are not repeated here, since every id-shaped string under `specs/design` enters telemetry's gap. So once the drain deadline has passed, a delivery that begins stores nothing, and a stopping run's `service.stopping` goes to standard error and never lands in the trail, which is what `D03-serve` promises for a drain that ran out.

## Sweep

`Sweep` removes every record whose time is before the moment it is given, and the attributes of each, and leaves every record at or after that moment as it was. It works in bounded batches so a long-stopped telemetry whose database holds weeks of records does not hold one write transaction open across the whole backlog; the batch size is not observable and is not contract. When it runs is `D03-serve`'s: once at start and after every hour, with the moment `RETENTION_DAYS` days before the clock.

## The reads

Every read answers from the trail as it is when the read runs and changes nothing. A **filter** is the one `search` and `count` share: a time range, `Since` inclusive and `Until` exclusive, compared as instants; any-of lists of services and events; an exact user and an exact request id, each a pointer so that the empty string, which many records carry, can be asked for; and attributes, every pair of which a record must carry with exactly that value, a number matching a number and a string a string, which is decided by comparing the JSON text of the two. A value in the filter's attributes that is not a valid attribute value, such as the `null` or the nested object a client might send, matches no record, since no record carries one. `Search` reads the matching records newest first, and among records with one time in the reverse of the arrival order, so a search reads the trail backwards exactly; it answers one page of at most `limit` records after a given position, or the first ones when no position is given, and, when more match, the position of the last record it answered, which a caller hands back to get the page after. A **position** is a record's sort key, its row's `ts` and `id`, as a `Position`; the store knows nothing of tokens, of the page size a tool allows, or of filters a position was read under, so a position works after a restart, after a sweep has removed the record it names and under other filters, where it continues from the same place. `D07-search` turns it into appkit's opaque page token. `Trace` reads one request's records oldest first, in arrival order among equal times, so the sequence reads as the services lived it. `Catalog` reads what the trail holds by name: the services, each service's events, and for each event how many records, the newest time and the attribute keys. `Count` counts the matching records, and `CountBy` splits that count by a field of the envelope, by a time bucket, or by an attribute; the groups of a field or an attribute are ordered by count descending then key ascending, the buckets oldest first. An attribute group is keyed by the value's text, a string as itself and a number or boolean as its JSON text, because the group's key is answered as a JSON string (`D08-count`); an attribute whose values differ only in type, the number 200 and the string `200`, therefore falls in one group, while the filter keeps them apart. `GroupBy` is the spelling the tool receives, and a spelling that is none of the eight forms is `ErrGroupBy`, which the tool turns into its own refusal.

## Served by the database

Every read is answered by SQL, following the suite's storage rule (`shape/`, Storage; appkit's D25): the filter is the query's `WHERE`, the order its `ORDER BY`, a search's window its `LIMIT`, an index backs the order, and the store holds no more than one page plus one row of a search, and of the other reads only their answer. The load-everything path the reads once shared is gone. A filter's time range compares `ts`, a bound finer than a microsecond rounding up, which is what keeps `Since` inclusive and `Until` exclusive on the instant; `Services` and `Events` are each a set membership; `User` and `RequestID` an equality, byte for byte; and each pair of `Attrs` a lookup in `attrs`, among the record's rows, of the row for that key whose `value` is byte for byte the text the matching rule names (R-JV3T-CFV2), the bytes `json.Marshal` gives for the basic form of the filter's value. The store computes that text once per pair, as it did before, and the database compares it with `value`, which holds the member's text exactly as the record's JSON carries it (R-SDSN-D0FD), so the normalisation is `encoding/json`'s on both sides: a string quoted and escaped as `encoding/json` escapes a string, `true` and `false` as themselves, an integer in decimal without exponent or fraction, so that the integer `500` and the float `500.0` both read `500`, and a float as `encoding/json` writes a `float64`; the string `"500"` reads `"500"`, quotes included, and never equals the number. A value that is not a valid attribute value has no such text and matches nothing, so the search answers no record without asking the database to compare one. Matching therefore answers exactly what it answered when it was decided outside the database.

A search's window is the matching rows after the position, ordered by `ts` descending then `id` descending, with one more row than the page so the store knows whether more follow; the first page has no position clause. `Count` is a count over the same filter, `CountBy` the same count grouped, ordered as R-K7AT-65A0, R-K8IP-JX0P and R-K9QL-XORE state; `Trace` reads one request id's rows ordered by `ts` then `id`; `Catalog` reads the distinct services, events and attribute keys with their counts and newest times.

The indexes are contract, since an operator and the host's replication see them, and `0001`'s already back every order a common search asks for. `id` is the table's `INTEGER PRIMARY KEY`, so it is the row's rowid, and SQLite ends every entry of an index on a rowid table with the rowid (SQLite's documentation of rowid tables and of `PRAGMA index_xinfo`, which lists it as the index's last column): `records_ts` is keyed `(ts, id)` and `records_svc_ts`, `records_ev_ts`, `records_req_ts` and `records_user_ts` are keyed `(svc, ts, id)` and so on. So a search with no filter, a time range, one service, one event, one user or one request id, with or without the position, walks one of those indexes backwards and stops after one page plus one row, with no sort; `EXPLAIN QUERY PLAN` shows that index and no temporary B-tree for the order, which a probe on this schema confirmed for each of those cases under the SQLite that `modernc.org/sqlite` carries. Two cases sort: a `services` or `events` filter naming several names searches the index once per name and sorts what matched, keeping only one page plus one row as it goes; and `CountBy`'s groups and `Catalog`'s entries, which are answers, not lists. `0002` adds `attrs_record_key` on `attrs(record_id, key)` because each pair of an attribute filter asks of one record's row whether it carries one key with one value, which `attrs_key_value` on `(key, value)` cannot answer without visiting every row that carries the pair; with it, the lookup is one index probe per record the order visits, and the sweep's removal of a batch's attributes, which selects them by `record_id`, stops reading the whole table. `(record_id, key)` rather than `(record_id)` alone, because a record carries one row per key, so the pair finds the one row to compare.

`0002` only adds; it drops nothing. `attrs_key_value` and the five `records` indexes stay, the previous release runs on the new schema unchanged, since the schema it reads and writes is `0001`'s and an index changes no answer, and a release that rolls back opens a database that records `0002`, a migration it does not carry, as appkit's `db.Open` allows. No index the suite ships twice: an explicit `(ts, id)` beside `records_ts` would be the same index written twice.

## Consumer tasks

The ingest handler and the writer share the store: `cli.Run` opens the handle with `db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "telemetry.db"), Migrations: telemetry.Migrations(), Now: p.Now, Service: web.ServiceName, Stderr: p.Stderr})`, builds the store with `store.New(d)`, hands it to `telemetry.New` as the `Sink` and to `web.Handler` as `Config.Store`, and `web.Handler` mounts `telemetry.IngestHandler(cfg.Store)` at `/ingest` and registers the tools with `tools.Register(cfg.MCP, cfg.Store)`. The sweep at start is `s.Sweep(ctx, now.Add(-retention))`.

A test opens a handle with `db.Open` on a file in its own temporary directory with `telemetry.Migrations()` and a clock it controls, builds a store with `store.New(d)`, fills it through `Deliver` with events whose times, services, users, request ids and attributes it chooses, then reads them back: `s.Search(ctx, store.Filter{Services: []string{"dummy"}}, 25, nil)` for the newest page and `s.Search(ctx, f, 25, page.Next)` for the one after it, while `page.Next` is not nil; `s.Trace(ctx, id)` for one request; `s.Catalog(ctx, "", "")` for the whole catalog; `s.Count(ctx, f)` and `s.CountBy(ctx, f, store.ByHour)` or `store.GroupBy(store.AttrPrefix + "status")` for the counts. It ages records by calling `s.Sweep` with a later moment, never by waiting. It makes a delivery fail with `d.SetFailing(true)` and sees `Deliver` return an error that does not wrap `telemetry.ErrRejected` and every read return an error; it calls `d.SetFailing(false)` and sees the next `Deliver` on the same store succeed. It hands `Deliver` a context it has already cancelled and sees an error that wraps `context.Canceled` and a trail unchanged. It proves the schema by reading `sqlite_master` and the pragmas inside `d.Read`, and a page's `Next` by reading the `ts` and `id` of the last record's row there, and closes the handle when it ends.

- R-I5QJ-QE1E: `Search(ctx, f, limit, after)` with `limit` at least 1 and a non-nil `after`, whatever `f` and `*after` hold, a position that is no retained record's included, MUST return a nil error and a `Page` whose `Records` are the first `limit` records matching `f`, in the search order, among the records after `*after`, all of them when fewer are, in that order, a zero-length slice when none is, and whose `Next` is nil when no record that matches `f` and is after `*after` follows the last of them in the search order, and otherwise a pointer to the position of the last of them; so that successive `Search` calls with one `f` and one `limit`, the first given a nil `after` and each later one the previous `Next`, until a nil `Next`, together return every record matching `f` exactly once, in the search order, when the trail does not change between them.
- R-I6YG-45S3: `Search(ctx, f, limit, after)` MUST return the zero `Page` and a non-nil error when `limit` is less than 1, whatever `f` and `after` are.
- R-K4V0-ELSM: `Catalog(ctx, service, event)` MUST return a nil error and one `CatalogEntry` per distinct `Service` among the records `r` for which `service` is empty or equals `r.Service` and `event` is empty or equals `r.Event`, ordered by `Service` ascending in byte order, each holding one `EventEntry` per distinct `Event` among those records of that service, ordered by `Event` ascending in byte order, whose `Count` is the number of those records of that service and event, whose `LastSeen` is the latest `Time` among them, and whose `Attrs` holds each distinct member name of their `Attrs` objects once, ascending in byte order, a zero-length slice when they carry none; and a zero-length slice of entries when no record qualifies.
- R-K62W-SDJB: `Count(ctx, f)` MUST return a nil error and the number of records matching `f`.
- R-K7AT-65A0: `CountBy(ctx, f, by)` with `by` equal to `ByService`, `ByEvent`, `ByUser` or `ByRequestID` MUST return a nil error, the number of records matching `f`, and one `Group` per distinct value of the record field the constant names (`Service`, `Event`, `User` or `RequestID`, the empty string a value like any other) among those records, whose `Key` is that value and whose `Count` is the number of those records carrying it, ordered by `Count` descending and then by `Key` ascending in byte order; a zero-length slice when no record matches.
- R-K8IP-JX0P: `CountBy(ctx, f, by)` with `by` equal to `ByMinute`, `ByHour` or `ByDay` MUST return a nil error, the number of records matching `f`, and one `Group` per distinct **bucket** among those records, where a record's bucket is the latest instant at or before its `Time` that in UTC has, for `ByMinute`, zero seconds and a zero fraction, for `ByHour`, zero minutes, seconds and fraction, and for `ByDay`, the time 00:00:00 and a zero fraction; the `Key` of a group MUST be its bucket formatted with the layout `2006-01-02T15:04:05Z` in UTC and its `Count` the number of those records in the bucket, and the groups MUST be ordered by bucket ascending, a bucket with no record left out, and a zero-length slice when no record matches.
