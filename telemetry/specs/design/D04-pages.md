# D04-pages

What telemetry's handler answers at its two pages: the landing page at `/`, which tells a person what telemetry is and names the four tools an agent reaches it with, and the about screen at `/about`, which shows its name, its version and its description; the refusal of any other method at either; and the frame both are drawn in — the platform's banner and footer, the launcher when the host lists services with icons, and the auth links the banner carries. `D01-layout-and-run-seam` declares the names this design behaves through — `web.Handler`, `web.Config` with its banner source and services path, `web.ServiceName`, `web.Description`, and the root package's `Assets` — and `D03-serve` owns the rules the handler keeps on every route, these two included: the identity gate, so a request without `X-User-Id` never reaches anything this design states; the trail, under which every request this design answers records its `request.started` and `request.finished` and nothing else, and writes nothing to any stream; telemetry's 404 for every path that is not a route; and the rule that no response sets a cookie. Tests of this design carry `D03-serve`'s ids where they exercise those rules.

## The two pages

Both pages are the human-authored templates in `assets/`, `landing.html` (the template `landing`) and `about.html` (the template `about`), embedded by the root package. The handler builds **telemetry's template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; each template draws `banner` first in its body and `footer` last, both from the page's banner data, and invokes `{{template "preload"}}` in its head. The code adds no template function and writes no markup of its own: the body of a `GET /` is exactly the output of `landing` for the request's **landing data**, and the body of a `GET /about` exactly the output of `about` for its **about data**, which a test can render itself and compare byte for byte. Each takes `GET` and `HEAD` — a `HEAD` is answered with the status and headers of the `GET` and no body — and refuses every other method with a 405 naming `GET, HEAD` and an empty body.

The landing data has one member, `Banner`, named by the template's top comment: the `page.Banner` the handler's banner source returns, called while the request is answered with the **banner user** — the caller's `X-User-Email` exactly as it arrived, auth's profile URL and auth's logout URL. The about data has two: the same `Banner`, whose `Service` and `Version` the screen shows as the name and the version, and `Description`, the service's one-line description, which is `web.Description`, the manifest's description, so the screen says the same with or without a services file. In the binary the banner source is the `Banner` method of appkit's kit, made with `page.New(ServiceName, v)`, `v` being the display string `main` reads (`D01-layout-and-run-seam`), which adds the service's name, that display string and the launcher's services, read afresh from the host's services file; what the banner and the launcher draw from it is appkit's contract (its D02 and D03), and whether the binary carries the launcher and names that display string in its footer is `D01-layout-and-run-seam`'s exec test. Over a services file that lists telemetry with an icon, that kit marks telemetry's entry current and so shows telemetry's icon in the mark; over one that lists no service with an icon, the mark shows the name `telemetry` alone and the banner holds no launcher button. A handler test uses a closure of its own, and the banner source is called exactly once per page, so every page is drawn from banner data fetched for that page.

Auth's two URLs come from the services file's entry named `auth` when it has one with a URL: that URL followed by `/` for the profile, and by `/logout` for sign-out. The file is the one at `Config.ServicesPath`, read afresh for every page through appkit's `services.Read`, and the **listed entries** are what it holds as the request is answered — nothing at all when it cannot be read, since a broken services file never breaks a page. Otherwise telemetry reads the space from the request's `Host`: a trailing `:` and port digits are dropped, then a single leading `telemetry.` label; auth is `auth.` and that space, under the request's scheme. The **scheme** is `X-Forwarded-Proto` when that header is exactly `http` or exactly `https`, and `https` for anything else, an absent or empty header included. There is no fixed fallback address. An entry named `auth` whose URL is empty is not usable, so it falls back the same way. Serving a page reads the trail for nothing and contacts no sibling: the only file it reads is the services file.

## Copy

The words, markup and hooks of both pages are copy: they live in `landing.html` and `about.html` and nowhere else, each template's top comment naming the data it receives and the hooks it carries for the stylesheet. This design names each template and the data it receives and nothing of what it draws; a test proves a page by executing the named template with that data and comparing byte for byte, so `html/template`'s contextual autoescaping is what keeps a caller's or the services file's bytes from becoming markup. A template that cannot show a state this design names is an issue for a human, never a change to the asset.
