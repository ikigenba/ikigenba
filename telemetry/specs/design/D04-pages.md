# D04-pages

What telemetry's handler answers at its two pages: the landing page at `/`, which tells a person what telemetry is and names the four tools an agent reaches it with, and the about screen at `/about`, which shows its name, its version and its description; the refusal of any other method at either; and the frame both are drawn in — the platform's banner and footer, the launcher when the host lists services with icons, and the auth links the banner carries. `D01-layout-and-run-seam` declares the names this design behaves through — `web.Handler`, `web.Config` with its banner source and services path, `web.ServiceName`, `web.Description`, and the root package's `Assets` — and `D03-serve` owns the rules the handler keeps on every route, these two included: the identity gate, so a request without `X-User-Id` never reaches anything this design states; the trail, under which every request this design answers records its `request.started` and `request.finished` and nothing else, and writes nothing to any stream; telemetry's 404 for every path that is not a route; and the rule that no response sets a cookie. Tests of this design carry `D03-serve`'s ids where they exercise those rules.

## The two pages

Both pages are the human-authored templates in `assets/`, `landing.html` (the template `landing`) and `about.html` (the template `about`), embedded by the root package. The handler builds **telemetry's template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher` and `footer`; each template draws `banner` first in its body and `footer` last, both from the page's banner data. The code adds no template function and writes no markup of its own: the body of a `GET /` is exactly the output of `landing` for the request's **landing data**, and the body of a `GET /about` exactly the output of `about` for its **about data**, which a test can render itself and compare byte for byte. Each takes `GET` and `HEAD` — a `HEAD` is answered with the status and headers of the `GET` and no body — and refuses every other method with a 405 naming `GET, HEAD` and an empty body.

The landing data has one member, `Banner`, named by the template's top comment: the `page.Banner` the handler's banner source returns, called while the request is answered with the **banner user** — the caller's `X-User-Email` exactly as it arrived, auth's profile URL and auth's logout URL. The about data has two: the same `Banner`, whose `Service` and `Version` the screen shows as the name and the version, and `Description`, the service's one-line description, which is `web.Description`, the manifest's description, so the screen says the same with or without a services file. In the binary the banner source is the `Banner` method of appkit's kit, which adds the service's name, telemetry's version and the launcher's services, read afresh from the host's services file; what the banner and the launcher draw from it is appkit's contract (its D02 and D03), and whether the binary carries the launcher and names the version in its footer is `D01-layout-and-run-seam`'s exec test. A handler test uses a closure of its own, and the banner source is called exactly once per page, so every page is drawn from banner data fetched for that page.

Auth's two URLs come from the services file's entry named `auth` when it has one with a URL: that URL followed by `/` for the profile, and by `/logout` for sign-out. The file is the one at `Config.ServicesPath`, read afresh for every page through appkit's `services.Read`, and the **listed entries** are what it holds as the request is answered — nothing at all when it cannot be read, since a broken services file never breaks a page. Otherwise telemetry reads the space from the request's `Host`: a trailing `:` and port digits are dropped, then a single leading `telemetry.` label; auth is `auth.` and that space, under the request's scheme. The **scheme** is `X-Forwarded-Proto` when that header is exactly `http` or exactly `https`, and `https` for anything else, an absent or empty header included. There is no fixed fallback address. An entry named `auth` whose URL is empty is not usable, so it falls back the same way. Serving a page reads the trail for nothing and contacts no sibling: the only file it reads is the services file.

## Reading the page

The tests have no HTML parser — appkit and the SQLite driver are telemetry's module dependencies and neither carries one — so this design fixes the hooks the templates' top comments name and the visible text the stories quote, and defines how each is read with the standard library: start and end tags, attributes read left to right as a browser reads them, with a value or bare, an element's content, and normalisation (tags removed, character references unescaped, whitespace collapsed). Rules about the page's own markup are read over its **written markup**, the body with appkit's banner and footer taken out, because those are appkit's output. The hook requirements are stated for a **plain page request**, whose host, service names and auth URL carry nothing that escaping would change and whose banner's name and version carry no whitespace that collapsing would change; the byte-for-byte requirement covers every other request, so `html/template`'s contextual autoescaping is what keeps a caller's or the services file's bytes from becoming markup. A hook the template lacks is an issue for a human, never a change to the asset.

The landing page's hooks, from `landing.html`'s comment: an `h1` reading `telemetry`; the summary paragraph `p#summary` with the class `lede`; the list `dl#tools` with the class `kv`, holding one `dt[data-tool=<name>]` per tool in the order `catalog`, `search`, `count`, `trace`, each holding the tool's name in a `code` element and followed by a `dd` describing it in the one-line summary that is also the first line of the tool's MCP description (`D06-mcp`); and `a#about-link` leading to `/about`. The about screen's, from `about.html`'s: an `h1` reading `About telemetry`; the list `dl#about` with the class `kv`, holding `dt` `Name` then `dd#about-name`, `dt` `Version` then `dd#about-version`, and `dt` `Description` then `dd#about-description`; and `a#home-link` leading to `/`. Each page is titled — `telemetry` and `About telemetry` — links `/_appkit/theme.css` as its stylesheet, links `/_appkit/feedback.js`, appkit's button-feedback script, as one deferred script in its head, declares the phone-width viewport, carries no other script of its own and names no resource on another host; the service's name is lowercase `telemetry` everywhere, and `Telemetry` appears nowhere in the page's own markup. The head is the template's, not appkit's: a page opts in to the feedback script by linking it, as it links the stylesheet, and the appkit banner does not load it. What the script does in a browser — press feedback on buttons — is appkit's and needs a JavaScript engine the gates do not have, so what is fixed is the hook a standard-library test can see: the `script` start tag in the head, its `src` and its `defer`.
