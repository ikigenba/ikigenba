# D04-pages

What telemetry's handler answers at its three pages: the landing page at `/`, which tells a person what telemetry is; the tools page at `/tools`, which lists the MCP tools an agent reaches it with, each by its name and description; and the about screen at `/about`, which shows its name, its version and its description; the refusal of any other method at each; and the frame all three are drawn in — the platform's banner, with its trail and page menu, and footer, the launcher when the host lists services with icons, and the auth links the banner carries. `D01-layout-and-run-seam` declares the names this design behaves through — `web.Handler`, `web.Config` with its banner source, its MCP server and services path, `web.ServiceName`, `web.Description`, and the root package's `Assets` — and `D03-serve` owns the rules the handler keeps on every route, these three included: the identity gate, so a request without `X-User-Id` never reaches anything this design states; the trail of events, under which every request this design answers records its `request.started` and `request.finished` and nothing else, and writes nothing to any stream; telemetry's 404 for every path that is not a route; and the rule that no response sets a cookie. Tests of this design carry `D03-serve`'s ids where they exercise those rules. This design declares the two names the tools page is drawn from, `web.ToolsData` and `web.Tool`.

## The three pages

All three pages are the human-authored templates in `assets/`, `landing.html` (the template `landing`), `about.html` (the template `about`) and `tools.html` (the template `tools`), embedded by the root package. The handler builds **telemetry's template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; each template draws `banner` first in its body and `footer` last, both from the page's banner data, and invokes `{{template "preload"}}` in its head. The code adds no template function and writes no markup of its own: the body of a `GET /` is exactly the output of `landing` for the request's **landing data**, the body of a `GET /about` exactly the output of `about` for its **about data**, and the body of a `GET /tools` exactly the output of `tools` for a `web.ToolsData`, each of which a test can render itself and compare byte for byte. Each takes `GET` and `HEAD` — a `HEAD` is answered with the status and headers of the `GET` and no body — and refuses every other method with a 405 naming `GET, HEAD` and an empty body.

Every page is drawn from its **page banner**: the `page.Banner` the handler's banner source returns, called once while the request is answered with the **banner user** — the caller's `X-User-Email` exactly as it arrived, auth's profile URL and auth's logout URL — with its `Trail` then set by the handler to the page's place under the service: no level on the landing page, one level named `about` at `/about` on the about screen, and one named `tools` at `/tools` on the tools page. appkit's banner draws the trail after the service's own crumb and marks the current row of its page menu from it — the landing row when the trail is empty, the Tools or the About row when it is exactly that one level (appkit's D02 and D03) — so the trail is what tells the menu where the reader is. A banner source that returns a `Trail` of its own has it replaced, never extended. The landing data has one member, `Banner`, named by the template's top comment: the page banner. The about data has two: the same `Banner`, whose `Service` and `Version` the screen shows as the name and the version, and `Description`, the service's one-line description, which is `web.Description`, the manifest's description, so the screen says the same with or without a services file. The tools page's data is a `web.ToolsData`: its `Banner`, the page banner, and its `Tools`, one `web.Tool` per tool registered on `Config.MCP`, the very server the handler mounts at `/mcp`, holding the tool's name and description as that server's `Tools` method (appkit's D08) reports them, in registration order; so the page lists exactly the four tools `tools/list` gives an agent, in the same order and with the same descriptions, and cannot drift from them. The tool descriptions are copy a model reads, owned by `internal/tools` (`D06-mcp`); the page shows them and says nothing of their words.

In the binary the banner source is the `Banner` method of appkit's kit, made with `page.New(ServiceName, v)`, `v` being the display string `main` reads (`D01-layout-and-run-seam`), which adds the service's name, that display string, the launcher's services, the home link and whether the service has tools, read afresh from the host's services file; what the banner, its trail, its page menu and the launcher draw from it is appkit's contract (its D02 and D03), and whether the binary carries the launcher and names that display string in its footer is `D01-layout-and-run-seam`'s exec test. Over a services file that lists telemetry with an icon, that kit marks telemetry's entry current and so shows telemetry's icon in the trail's root; over one that lists no service with an icon, the banner holds no launcher button. A handler test uses a closure of its own, and the banner source is called exactly once per page, so every page is drawn from banner data fetched for that page.

Auth's two URLs come from the services file's entry named `auth` when it has one with a URL: that URL followed by `/` for the profile, and by `/logout` for sign-out. The file is the one at `Config.ServicesPath`, read afresh for every page through appkit's `services.Read`, and the **listed entries** are what it holds as the request is answered — nothing at all when it cannot be read, since a broken services file never breaks a page. Otherwise telemetry reads the space from the request's `Host`: a trailing `:` and port digits are dropped, then a single leading `telemetry.` label; auth is `auth.` and that space, under the request's scheme. The **scheme** is `X-Forwarded-Proto` when that header is exactly `http` or exactly `https`, and `https` for anything else, an absent or empty header included. There is no fixed fallback address. An entry named `auth` whose URL is empty is not usable, so it falls back the same way. Serving a page reads the trail of events for nothing and contacts no sibling: the only file it reads is the services file.

## No notice page

telemetry draws no notice page. Its 404 is `D03-serve`'s, one line of plain text with no banner, and its 405 has an empty body, so no answer but the three pages carries a banner or executes a template, and `assets/` holds no not-found template.

## Copy

The words, markup and hooks of the three pages are copy: they live in `landing.html`, `about.html` and `tools.html` and nowhere else, each template's top comment naming the data it receives and the hooks it carries for the stylesheet. This design names each template and the data it receives and nothing of what it draws; a test proves a page by executing the named template with that data and comparing byte for byte, so `html/template`'s contextual autoescaping is what keeps a caller's or the services file's bytes from becoming markup. A trail is proved the same way: the test supplies the banner, sets the trail this design names on its own copy, executes the template and compares. A template that cannot show a state this design names is an issue for a human, never a change to the asset.

- R-RRK4-NC8R: telemetry's design defines the **scheme** of a request as the value `r.Header.Get("X-Forwarded-Proto")` returns for it when that value is exactly `http` or exactly `https`, and as `https` for every other value, the empty string included; and every requirement of telemetry's design that names a request's scheme MUST denote that value.

- R-RTZX-EVQ5: telemetry's design defines the **listed entries** of a handler `web.Handler(cfg)` returned, for a request, as the `services.List` that appkit's `services.Read(cfg.ServicesPath)` returns at the time that request is answered when the error it returns is nil, and as an empty list when that error is not nil, `cfg.ServicesPath` being empty or naming a file that does not exist, cannot be read or is not a services file included; every requirement of telemetry's design that names the listed entries MUST denote that list, so that a services file rewritten between two requests is seen by the second as rewritten.
