# Decision 3 — The local dev stack: `bin/start` / `bin/stop`, and how a service joins it

**Decision.** `bin/start` is the local-dev mirror of the box's systemd story: it
builds every Go service, stages the prod-shaped runtime manifest root, launches
each service on its loopback port, and brings up the dev front door on `:8080`
so the full path-routed auth chain is reachable end to end. `bin/stop` is its
exact inverse. Both are **app-agnostic** — parameterized by the service name and
nothing else.

**The service list and its resolution rules.** `bin/start` carries one list of
the suite's deployable services and, for each:

- resolves the **port from the registry** — `registry.MustPort("<svc>")` in Go,
  or derived from the service's `etc/manifest.env` in shell. **No port literal
  appears anywhere in this tooling**; the registry exists so a port is written
  in exactly one place, and the launcher resolves rather than restates.
- resolves the **version** from `<svc>/VERSION`, falling back to `dev` when the
  file is absent.
- exports **`<SVC>_WWW_PATH="$repo/<svc>/share/www"`** in the launch function of
  **every service whose tree carries a `share/www`** (equivalently: whose
  chassis Spec declares `WWW`). The chassis fails loudly at boot when the tree
  is missing, so a WWW service launched without this export dies immediately —
  which is how the gap surfaces, and why the export is part of joining the
  stack, not an optional nicety. Dev points straight at the **source tree's**
  assets (no `share/current` staging): edits are live on refresh, and there is
  no copy to drift. The membership rule is mechanical — a service directory
  containing `share/www` must have a matching `<SVC>_WWW_PATH` export in
  `bin/start`, no exceptions and no extras.
- reads the service's own **`etc/env.list`** (`root project/design/D12.md`) in a
  **scoped subshell**, so its customer data and dev config reach that process's
  environment and nothing else. Each `config NAME value` line is exported
  verbatim; each `secret NAME` line is resolved from the operator's login
  keyring — `secret-tool lookup name <NAME>`, the same keyring
  `bin/push-secrets` reads, reachable inside the netns dev instance. No `.envrc`
  and no `~/.secrets` file is read. A `secret NAME` that does not resolve — no
  keyring entry, or an entry whose value is empty — **aborts that service's
  launch loudly**: the launcher writes a diagnostic naming the service and the
  unresolved secret to that service's log, then exits non-zero, so the
  `✗ <svc> exited — see tmp/<svc>.log` pointer the start-up wait already prints
  leads straight to the cause instead of an empty log. This mirrors
  `bin/push-secrets`' resolve-or-abort rule (D2): an undeclarable secret is a
  setup error surfaced at once, never a value silently defaulted to empty. The
  failure is scoped to the one service and the rest of the stack still comes up,
  because each launcher runs in its own scoped subshell.
- writes the built binary, the pidfile, the log (`tmp/<svc>.log`), and the
  SQLite state under the run dir, all gitignored.

`bin/stop` signals each tracked pid in **reverse start order** (front door
first, then services), `TERM` then `KILL` for stragglers, removing each pidfile;
`bin/stop --clean` additionally wipes the run dir's dev state.

**Staging the runtime manifest root.** Before launching anything, `bin/start`
builds, under the run dir, the **same layout the box uses** — the versioned
`etc/<version>/manifest.env` behind an `etc/current` symlink defined by the
install-tree and env contracts (`project/design/D01.md` and
`project/design/D11.md` at the repo root, not restated here) — so a service
started locally reads its environment through exactly the path it will read on
the box. This staging half is a **layout reader**, and is proven under the gate
rather than trusted (D5).

**How a new service joins.** Adding a deployable service to the local stack is
adding its name to `bin/start`'s (and `bin/stop`'s) list. Two sibling seams
change with it and are **outside this workspace's scope** — the repo-root
`go.work` `use` entry, and the front door's fragment list (`nginx/`) — each
owned where it lives. The order is fixed: the wiring lands **after** the
service's module exists, because a `go.work` entry naming a nonexistent module
breaks every workspace build.

**Rejected.**
- *Hardcoding a service's loopback port in `bin/start`.* The registry is the
  single place a port is written; a literal here is a second one, guaranteed to
  drift. Rejected.
- *Launching services directly without staging the manifest root.* The dev stack
  would then read its environment through a shape the box does not have, and any
  drift between the two would surface only in production — which is exactly the
  failure this staging (and D5's proof of it) exists to prevent. Rejected.
- *Wiring a service into the stack before its module exists.* Breaks the
  workspace build for every module until the service's own loop runs; the
  reverse order costs nothing. Rejected.
- *A single shared env sourced once for the whole stack.* Every service would
  see every other's customer data, and local would stop resembling the box's
  per-app secret delivery. Rejected for the per-service `etc/env.list` read in a
  scoped subshell.
- *Staging `share/` under the run dir the way `etc/` is staged.* The manifest
  root is staged because the box-shaped **read path** is the thing under proof;
  assets have no versioned read path worth mirroring in dev, and a copy would
  make every template edit require a restack. The direct source-tree path is
  the point. Rejected.
- *Letting `set -euo pipefail` kill the launcher on a failed `secret-tool
  lookup`.* A bare `value="$(secret-tool lookup name "$name")"` assignment dies
  under `errexit` before the binary is exec'd and before anything is written, so
  the service surfaces only a generic "exited" against an empty log — a missing
  keyring entry is then indistinguishable from a real crash and the operator has
  nothing to act on. Rejected for the explicit resolve-or-abort diagnostic in the
  Decision above.

**Verification.**

This Decision mints **no requirement ids** for its orchestrating half: building
fifteen binaries, launching processes, and standing up nginx is the
deliberately-untested tier per Conventions — not hermetic, not runnable under
the gate (it needs ports, secrets, and a full build), and a mock-backed stand-in
could not falsify any of it. That half is verified by the operator running the
stack: fifteen services answering behind the dev front door, which is product's
success criterion. The per-service secret resolution and its resolve-or-abort
diagnostic belong to this same untested tier: the only substrate that could
falsify them is a real login keyring, which the hermetic gate deliberately
carries none of (Conventions). They are verified out of gate — standing the
stack up with a service whose `secret` line has no keyring entry must abort that
one service with a diagnostic naming the service and the unresolved secret, the
rest of the stack still coming up.

Its **staging half is the exception** and is proven in-gate: `bin/start
--stage-only` under a temp run dir is exercised by `bin/bintest`, whose ids
belong to **D5** (which owns the seams that make it testable). This Decision
carries no ids of its own so that one behavior has one id in one place.
