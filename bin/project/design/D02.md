# Decision 2 — `bin/push-secrets`: seeding a service's deployed secrets from its `etc/env.list`

**Decision.** `bin/push-secrets` is the **only** procedure by which a service's
deployed secrets are seeded. It is the workstation-side half of the suite's
per-app secrets contract; the parameter's path, its value shape, and the
box-side launcher that consumes it are the umbrella's
(`root project/design/D12.md`) and are **not restated here**. This
Decision owns only the tool: where it reads its input, how it resolves values,
and what it prints.

**The `env.list` parse rule (strict, no exceptions).** An app's committed
`<app>/etc/env.list` (`root project/design/D12.md`) is the single source of
truth for the customer data it needs. A line matching exactly

    secret NAME

marks a pushed key. Two other line forms are recognized and **never pushed**:
`config NAME value` lines are dev-only configuration (channel 4,
`root project/design/D21.md`) that never rides to the box, and `rotating NAME`
lines are per-environment rotating credentials (channel 5,
`root project/design/D32.md`) whose value lives in the service's `state/` and is
seeded by `opsctl`, never through this parameter. `push-secrets` derives the
pushed key set from `secret` lines alone, so a `rotating` key can never reach the
shared parameter. Because `env.list` names only what an app pushes, there is **no
opt-out annotation** and no workstation-only escape hatch to track: a value that
must stay local is simply not a `secret` line (workstation-only secrets such as
`IKIGENBA_TOKEN` appear in no app's `env.list` and live only in the operator's
keyring).

**The tool.** One bash script at repo root beside its `bin/` siblings, same
style:

- **`bin/push-secrets <app>`** — parse `<app>/etc/env.list` by the strict rule
  above; resolve each `secret NAME` value (a same-named environment variable
  overrides, else the operator's login keyring via
  `secret-tool lookup name <NAME>`, else abort); assemble the flat JSON object
  with `jq`; write it through a `chmod 600` temp file (trap-cleaned) so the
  value never appears on a command line. No `env.list`, or no `secret` lines,
  pushes the empty object — "no secrets" is a deliberately seeded state, never
  an absence.
- **`bin/push-secrets --all`** — sweep every deployable app (the top-level
  directories carrying a `VERSION`), report per app, and exit non-zero if any
  app failed.
- **`bin/push-secrets --dry-run [<app>|--all]`** — print each app's target
  parameter name and the **key names** it would push, calling no cloud API.

**Value fidelity (the load-bearing property).** A resolved value is preserved
**byte-for-byte except that trailing newlines are trimmed**. Interior
whitespace — notably the embedded newlines of a multi-line PEM private key —
must survive resolution and JSON assembly unchanged, on **both** resolution
paths (environment override and the keyring value). A value that is empty
after trimming aborts.

**Configuration.** The account comes from `<app>/etc/deploy.env`, present in
every deployable app; the AWS profile defaults to that account name and the
region to the suite's default, both overridable by environment. A live SSO
session is required, and a failed cloud call aborts loudly rather than
continuing the sweep silently.

**Output discipline.** Output shows key **names** and **masked** values only
(first four and last four characters). A full secret value never appears in
output, on a command line, or in a log.

**No read-modify-write.** Because the parameter is per app, the write path is a
plain overwrite of that app's own parameter: there is **no fetch, no merge, and
no sibling preservation**. The clobber risk that the shared-blob era's seven
per-service `bin/secrets` scripts existed to manage is deleted along with them,
and `sops/seed-secrets.md` documents `bin/push-secrets` as the only procedure.

**Rejected.**
- *Parsing the old `.envrc` line form + `~/.secrets/<NAME>` files.* Coupled the
  pushed key set to a personal shell-config file and scattered plaintext secret
  values across the filesystem. Rejected — `etc/env.list` is the committed,
  single declaration of the key set and the keyring holds the dev values
  encrypted at rest (`root project/design/D12.md`).
- *A second manifest listing keys separately from the dev config.* One more
  file per app to keep in sync; `etc/env.list` already carries both, and the
  tool reads only its `secret` lines. Rejected.
- *Keeping the seven per-service `bin/secrets` scripts.* Seven
  re-implementations of one read-modify-write, each able to clobber the others'
  keys. Rejected — one tool, per app, overwrite-only.
- *Implementing the tool in Go with unit tests.* Operator decision: it is bash
  like its `bin/` siblings, in the deliberately-untested tier, verified once
  outside the build loop. Rejected for this iteration.
- *Printing values unmasked in `--dry-run` so the operator can eyeball them.*
  Puts secrets in scrollback and in any captured terminal log for a check that
  key names already satisfy. Rejected.

**Verification.**

This Decision mints **no requirement ids** of its own. `push-secrets` is bash
orchestration around a live cloud API, the deliberately-untested tier per
Conventions: the only substrate that could falsify its live-push claims is a real
parameter store, which the hermetic gate cannot provide, and a mock-backed
assertion would confirm a string was assembled, never that a secret arrived.

The **one exception is the channel-5 exclusion**, which is pure parse logic and
so hermetically testable without any cloud, via `--dry-run` (key names only):

- R-EJ1W-1G19 (owned by `root project/design/D32.md`, `[proof: bin]`) —
  `push-secrets`, given an `etc/env.list` carrying a `rotating NAME` line,
  produces a key set that **omits** NAME while a `secret` key in the same file is
  still present. Substrate: a `bin/bintest` test execing the real `push-secrets
  --dry-run` against a temp-dir app fixture (its own `etc/env.list` +
  `etc/deploy.env`), asserting the printed key set includes the `secret` key and
  excludes the `rotating` and `config` keys — no keyring, no network.

It is verified **once, manually, outside the build loop**: `--dry-run` output
compared against every app's `etc/env.list` `secret` lines, then one live push
compared — **by key names only** — against the seeded parameters. That push must
include an app carrying a **multi-line secret** (a PEM private key), and the
check reads back that parameter's key *shape* only — per-key value length and
line count, never a value — confirming the multi-line key survives with its
interior newlines intact. The box-side half is an already-live external contract
(`root project/design/D12.md`), verified by the services starting healthy on their
per-app parameters. Phases realizing this Decision therefore carry structural
deterministic checks, not id-tagged tests.
