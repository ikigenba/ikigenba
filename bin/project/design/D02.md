# Decision 2 — `bin/push-secrets`: seeding a service's deployed secrets from its `.envrc`

**Decision.** `bin/push-secrets` is the **only** procedure by which a service's
deployed secrets are seeded. It is the workstation-side half of the suite's
per-app secrets contract; the parameter's path, its value shape, and the
box-side launcher that consumes it are the umbrella's
(`project/design/D12.md` at the repo root) and are **not restated here**. This
Decision owns only the tool: where it reads its input, how it resolves values,
and what it prints.

**The `.envrc` parse rule (strict, no exceptions).** An app's `.envrc` is the
single source of truth for the secrets it needs. A line matching exactly

    export NAME="$(cat ~/.secrets/NAME)"

— the **same** `NAME` on both sides — marks a pushed secret. Nothing else is
pushed: plain exports are local-only by construction, and the **repo-root
`.envrc` is never parsed** (it is not an app), so workstation-only secrets are
exported there and inherited locally via `source_up` without ever riding to the
box. There is **no opt-out annotation**: a secret that must stay local belongs
in the root `.envrc`, not the app's. An app's `.envrc` therefore conforms to the
plain-line form; loop or generated constructions do not parse.

**The tool.** One bash script at repo root beside its `bin/` siblings, same
style:

- **`bin/push-secrets <app>`** — parse `<app>/.envrc` by the strict rule above;
  resolve each name (a same-named environment variable overrides, else the
  contents of `~/.secrets/<NAME>`, else abort); assemble the flat JSON object
  with `jq`; write it through a `chmod 600` temp file (trap-cleaned) so the
  value never appears on a command line. No `.envrc`, or no matching lines,
  pushes the empty object — "no secrets" is a deliberately seeded state, never
  an absence.
- **`bin/push-secrets --all`** — sweep every deployable app (the top-level
  directories carrying a `VERSION`), report per app, and exit non-zero if any
  app failed.
- **`bin/push-secrets --dry-run [<app>|--all]`** — print each app's target
  parameter name and the **key names** it would push, calling no cloud API.

**Value fidelity (the load-bearing property).** A resolved value is preserved
**byte-for-byte except that trailing newlines are trimmed**. Interior
whitespace — notably the embedded newlines of a multi-line PEM private key —
must survive resolution and JSON assembly unchanged, on **both** resolution
paths (environment override and `~/.secrets/<NAME>` file). A value that is empty
after trimming aborts.

**Configuration.** The account comes from `<app>/etc/deploy.env`, present in
every deployable app; the AWS profile defaults to that account name and the
region to the suite's default, both overridable by environment. A live SSO
session is required, and a failed cloud call aborts loudly rather than
continuing the sweep silently.

**Output discipline.** Output shows key **names** and **masked** values only
(first four and last four characters). A full secret value never appears in
output, on a command line, or in a log.

**No read-modify-write.** Because the parameter is per app, the write path is a
plain overwrite of that app's own parameter: there is **no fetch, no merge, and
no sibling preservation**. The clobber risk that the shared-blob era's seven
per-service `bin/secrets` scripts existed to manage is deleted along with them,
and `sops/seed-secrets.md` documents `bin/push-secrets` as the only procedure.

**Rejected.**
- *A per-service secrets manifest file, or opt-out annotations in `.envrc`.* A
  second list to keep in sync with the first; the `.envrc` **is** the list, and
  giving workstation-only secrets a home in the root `.envrc` keeps the rule
  exception-free. Rejected.
- *Keeping the seven per-service `bin/secrets` scripts.* Seven
  re-implementations of one read-modify-write, each able to clobber the others'
  keys. Rejected — one tool, per app, overwrite-only.
- *Implementing the tool in Go with unit tests.* Operator decision: it is bash
  like its `bin/` siblings, in the deliberately-untested tier, verified once
  outside the build loop. Rejected for this iteration.
- *Printing values unmasked in `--dry-run` so the operator can eyeball them.*
  Puts secrets in scrollback and in any captured terminal log for a check that
  key names already satisfy. Rejected.

**Verification.**

This Decision mints **no requirement ids** — deliberately. `push-secrets` is
bash orchestration around a live cloud API, the deliberately-untested tier per
Conventions: the only substrate that could falsify its claims is a real
parameter store, which the hermetic gate cannot provide, and a mock-backed
assertion would confirm a string was assembled, never that a secret arrived.

It is verified **once, manually, outside the build loop**: `--dry-run` output
compared against every app's `.envrc`, then one live push compared — **by key
names only** — against the seeded parameters. That push must include an app
carrying a **multi-line secret** (a PEM private key), and the check reads back
that parameter's key *shape* only — per-key value length and line count, never a
value — confirming the multi-line key survives with its interior newlines
intact. The box-side half is an already-live external contract
(`project/design/D12.md`), verified by the services starting healthy on their
per-app parameters. Phases realizing this Decision therefore carry structural
deterministic checks, not id-tagged tests.
