# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail repos records of itself from its start to its stop, the bus events it holds, delivers or drops, and the rules its handler keeps on every route — the identity gate, the request's id, the request's event cause, the request's two events, the route table that sends each path to the pages, the shared files, `/mcp`, the git routes or the event bus's two paths, and the answer for a path that does not exist. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run`, the exit codes, `settings.Read` and `settings.Error`, `server.Serve`, `server.DrainError`, `web.Config`, `web.Handler`, `web.ServiceName`, `git.Find`, `store.Open` with `store.ErrRoot`, `(*store.Store).Verify`, the root package's `repos.Migrations`, `limits.New` and `(*limits.Limits).Drain`, `maintenance.Start` and `(*maintenance.Scheduler).Stop`, `smarthttp.Handler` with `smarthttp.Emits`, `tools.Register` and `clone.Base` with `clone.NewContext`. appkit's `db` package (its D15 and D16) owns opening the catalog and bringing it up to date, its `telemetry` package (its designs D11 to D14) the events, the writer and the request middleware this design wires, its `identity` package the gate, its `page` package the shared files, its `mcp` package the endpoint, and its `events` package the emitter, the cause middleware and the two handlers the events app reaches repos at. `D02-cli` decides that an empty `Args` means serve, that a usage error exits 2 and trouble on the host exits 1, and that nothing else touches the environment. This design says in what order `Run` checks its start, which refusal touches what, how it takes the socket, opens and verifies the store, builds the writer, the emitter, the limits, the maintenance schedule and the handler, tells systemd it is ready, serves and stops, and how `Serve` treats the listener it is handed, in these shapes: a clean start, a first start, a start with no services file or no telemetry, a stop that drains, a stop whose drain runs out, a restart, the ways a start is refused, and the start over a catalog a newer repos upgraded, which warns and serves. What the handler answers at `/`, at `/about` and under `/_appkit/` is `D04-pages`; at `/mcp`, `D06-mcp`, `D07-tools` and `D09-limits`; on a git path, `D08-git` under `D09-limits`; what the store creates, opens, verifies and rebuilds is `D05-store`; what the maintenance schedule does is `D10-maintenance`.

## The terms repos serves on

repos serves on the platform's common terms, the same as every app. It serves only on a listening socket it inherits and never opens one of its own; on a host that is `/run/ikigenba/repos.sock`, held by `ikigenba-repos.socket` beside the `Type=notify` `ikigenba-repos.service`, and nginx proxies repos' public name, git's requests included, to it. A deploy restarts the service alone, so the socket and the connections queued on it outlive every restart; that a restart refuses no request is the socket's doing, and repos' part is to finish what it accepted and leave the socket where systemd put it.

repos takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment once it has taken the socket, so no git it starts inherits a claim meant for it. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket `NOTIFY_SOCKET` names, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace. On `SIGTERM` or `SIGINT` it stops accepting, refuses at once every git operation still waiting for a slot or a lock, lets the requests it accepted finish for at most the drain deadline, then cuts off whatever is left, says how many it cut off, and exits 1. It closes its own copy of the socket and never removes the socket's path.

The suite is a closed system: repos trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway calling it at its socket to have forwarded them. Every request has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it, 32 lowercase hexadecimal digits from the random source `Process.Rand` supplies. `Process.Rand` is also where the store draws repository ids and the emitter bus event ids, so `Run` hands the writer, the store and the emitter one reader that never lets two reads of `Process.Rand` overlap.

The events app reaches repos at its socket too, on two paths of its own: `/events`, where it would deliver events repos accepts, and `/declarations`, where it reads what repos emits and accepts. repos accepts no event, so it mounts appkit's `events.DeliveryHandler` with no handlers, which answers every valid delivery 404, and `events.DeclarationsHandler` over its emitter, which answers `GET` with the declaration `smarthttp.Emits` gives and an empty list of accepted events. The events app calls without a user, so these two paths sit outside the identity gate, inside the request middleware like every path; nginx never passes them on, since repos' fragment answers both 404 at its public name (`D02-cli`). A push made in reaction to an event names it with `X-Event-Cause` and `X-Event-Depth`; appkit's `events.Middleware` puts the pair on the request's context when both are well formed and ignores them as a whole otherwise, and the bus events the push emits carry it (`D08-git`). The headers change nothing else: the trail's events have fixed attributes that hold neither.

repos' standard error holds only trouble: a start it refuses, appkit's one warning line over a catalog a newer repos upgraded, a socket it cannot take, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off, the lines appkit's writer writes for an event it could not deliver, and the lines appkit's emitter writes, `repos: lost event: ` and the event's JSON, for a bus event it dropped. A request answered with any status, the missing-identity 500 included, a git operation refused for a limit or killed for its deadline, and a repository found broken at start are handled failures, recorded in the trail and earning no line. So the handler has no stream at all, and while telemetry and the event bus take every event, the clock reads a year 0 through 9999 (see The trail of a run), no request's `X-Event-Depth` names a depth above 1000000, and no push overflows the emitter's queue, a running repos writes nothing to either stream; the queue holds `events.DefaultQueueCapacity`, 1024 bus events, so a push moving more refs than that can drop the excess, each with its line. A bus event the events app takes late earns no line. What git writes to its own standard error is `D08-git`'s and never reaches repos' standard error.

## Checking the start

With `Args` empty, `Run` checks, in this order: its nine settings, through `settings.Read` over `LookupEnv` (`D01-layout-and-run-seam` fixes the spelling, the defaults, the order of the nine and the text of the refusal); then whether a socket was passed in; then whether git is on the `PATH`; and only then opens the catalog and the store. Each refusal is the first one that applies, so a bad setting is reported whether or not a socket was passed in or git is installed, and a missing socket whether or not git is installed.

A bad setting is the caller's mistake: `repos: `, the `Error` text of the `*settings.Error`, a newline, exit 2. A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one; anything else is no socket passed in, and a count above one is a unit repos will not guess about. Both are usage errors, exit 2, with the detail line saying how to run repos. None of these three refusals takes the descriptor, unsets a variable, looks for git, creates or opens anything under `Process.Dir`, serves, tells systemd anything, or records an event.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv` and takes descriptor 3 as its listener: through `Process.Inherit` when a test supplies one, otherwise with `net.FileListener` over the real descriptor, which, as Go's `net` documentation of `FileListener` and `UnixListener.SetUnlinkOnClose` states, leaves the socket's path in place when the listener is closed. A descriptor that cannot be made into a listener is trouble on the host: `repos: ` and the error, exit 1.

Then git. `Run` hands `git.Find` the value `LookupEnv` gives for `PATH` (empty when unset) and `Process.Environ`; when it finds none (`D01-layout-and-run-seam` states how it looks), that is a host missing a dependency opsctl provisions: `repos: git not found on PATH`, exit 1, before the catalog is opened, so a host without git keeps its state exactly as it was — an absent `state/` is still absent.

## The store, verification and readiness

With git found, `Run` opens the catalog with appkit's `db.Open` over that path, the root package's `repos.Migrations()`, `Process.Now`, the service `web.ServiceName`, and a writer for appkit's warning that reaches `Process.Stderr` in one write, and the store with `store.Open` over the handle it got, the directory `state/repos` under `Process.Dir`, the git it found, `Process.Now`, and the guarded `Process.Rand`; a catalog `db.Open` has just created, from an absent or empty file, is one the store rebuilds from the directories (`D05-store`). `db.Open` creates `state/` and the database on a first start, applies every migration the database has not had, and refuses a path it cannot use and a database it cannot write (appkit's D15 and D16); on its way it may create and remove a probe file of its own in `state/`, which is appkit's and never outlives the call. `D05-store` states what `store.Open` creates — the empty `state/repos/` — and when it fails with `store.ErrRoot`. `Run` writes every `db.Open` failure, and every `store.Open` failure but `store.ErrRoot`, as `repos: cannot open database state/repos.db: ` and the error's text; `store.ErrRoot` is `repos: cannot create directory state/repos: ` and the error's text; either text has its newlines made spaces, so the diagnostic is one line. The paths are always these relative spellings, whatever `Dir` holds. Either is exit 1, before anything is served, before systemd is told anything and before any event is recorded. A missing database is not this error: it is a first start, or a rebuild (`D05-store`). An open that fails while the context is done — the signal came during start-up — is not trouble either: like a signal during verification, it is a clean stop, exit 0, with no line. `Run` removes nothing: a start that fails or stops, or a process killed, before the store's rebuild has committed leaves the catalog unsettled, and the next start rebuilds it (`D05-store`).

With the store open, `Run` builds the run's writer with appkit's `telemetry.New` over `Process.Sink`, as `D01-layout-and-run-seam` declares, and verifies every repository with `Store.Verify` over that writer, so each `repo.unavailable` `D05-store` records comes before `service.started`. `D05-store` lets `Verify` fail for a context that is done or a store that is failing (R-YVUR-MTG8). `Run` never closes its handle before it stops and never makes it fail, and a catalog that `db.Open` just opened can fail before `Verify` only by a race with something outside repos, so through `Run` the one testable failure is the signal coming during start-up. For the race, `Run`'s answer is the database diagnostic, `repos: cannot open database state/repos.db: ` and the error's text, exit 1, with no `READY=1`; no test can produce it through `Run`, so it is stated here and not as a requirement. A signal that arrives before `Run` has begun to report ready — during verification, or before `Run` was even called — is a stop, not a failure, so it is exit 0 (`D02-cli` keeps 1 for a server that failed, and a repos that finished everything stops with 0): `Run` sends no `READY=1`, accepts nothing, records neither `service.started` nor `service.stopping`, lets every event already recorded (verification's `repo.unavailable` among them) be delivered or written out, and returns. The refusals before the store still come first, whatever the context holds.

Then `Run` builds the run's emitter, appkit's `events.New` with `Service` `web.ServiceName`, `Emits` `smarthttp.Emits()`, `Sink` `Process.EventSink` (appkit's `events.NewSocketSink` when it is nil), `Telemetry` the run's writer, `Process.Now`, `Process.Sleep`, the guarded `Process.Rand`, `Process.Stderr` through the same guard as the writer's, and the default queue capacity and retry window; builds the limits, `limits.New` over the settings it read and the clock `limits.Clock{Now: Process.Now, After: Process.After}`; starts the maintenance schedule with `maintenance.Start` over the same store, git and limits, the run's writer, and no `Hold`; calls `Process.MCP` once with the run's writer, once it has passed verification and is about to report ready; and builds the handler with `web.Handler` over `Process.Banner`, that server, the value `LookupEnv` gave for `IKIGENBA_SERVICES` (read once, here), the store, the git, the limits, the run's writer and the run's emitter. Nothing about `IKIGENBA_SERVICES` or the file it names can stop a start: unset, empty, or naming a file that is missing, unreadable or malformed, repos starts, serves and says nothing about it; its pages lose the launcher, its endpoint the instructions, its clone addresses the `repos` entry, its events, with no `telemetry` entry to find, go to standard error, and its bus events, with no `events` entry to find, are held and then dropped, all as the owning designs state.

The socket has been listening since systemd made it, so ready is true before the first `Accept`, and sending it first means a failure to send is reported before anything was served: `repos: ` and the error, exit 1. Once `READY=1` is sent, and before any connection is accepted, `Run` calls `Writer.Ready`, so `service.started`, carrying `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), is the first event of a run after verification's. With neither `IKIGENBA_COMMIT` nor `IKIGENBA_RELEASE` set that string is empty, and repos starts and serves all the same: an identity is never a reason not to start.

## A catalog a newer repos upgraded

A deploy rolled back to an older binary leaves it over a catalog that records a migration this repos does not carry. It is not refused: data never rolls back, so older code runs on newer data. appkit's `db.Open` applies nothing to it, not even a migration repos carries that the catalog lacks, and writes one warning line, beginning with the service name it was given and naming the lowest version this repos does not carry, zero-padded to four digits, to the writer it was given; `Run` passes that line to `Process.Stderr` in one write, and under systemd it reaches the journal. It is written before `READY=1`, it is the whole warning, and the trail records nothing about it. Then the start goes on exactly as over any catalog: the store opens over the handle, verification runs, `Run` reports ready, records `service.started` and serves every repository the catalog names. repos states nothing about the line's wording: a test compares what `Run` wrote with what its own `db.Open` call, given the same service name and a buffer, writes over the same database, and that the line begins `repos: ` is what shows `Run` handed appkit repos' name. `db status` over such a catalog lists the unknown version and exits 0 (`D02-cli`).

## The trail of a run

Every event of the process goes through the run's writer: the handler's, the tools', the git routes', the limits', maintenance's and verification's. appkit's writer queues and returns, so neither readiness nor any answer waits on telemetry; an event it cannot deliver goes to standard error as `repos: undelivered event: ` and the event's JSON (appkit's D12), in the order recorded, and repos keeps serving. A test sees this at `Run` with a `Sink` whose `Deliver` fails, and in the binary by leaving `IKIGENBA_SERVICES` unset, which leaves the socket sink nowhere to deliver. That a telemetry installed or restarted after repos started is found without a restart, and that an event already written out is not sent again, is appkit's socket sink, which reads the services file afresh on every delivery (its D13), and the binary gets it because `main` leaves `Process.Sink` nil (R-KF5M-9FL1); the same holds for the event bus's socket sink and `Process.EventSink`; `Run` adds nothing to it. Bus events go through the run's emitter, which also queues and returns, so no answer waits on the event bus either. While the events app cannot take one — not installed, stopped, unreachable — the emitter keeps it and retries, pausing with `Process.Sleep` between attempts, for appkit's retry window, `events.DefaultRetryWindow`, measured by `Process.Now` from the start of its first delivery attempt (not from the event's time, so an event queued behind another gets its full window) to the end of each failed attempt, so time an attempt itself takes counts; once a failed attempt ends with the window used up, to the instant, there is no further attempt; an event the events app takes within it, and before the drain deadline once repos is stopping, is delivered once and leaves no trace, and one it has not taken by then is **dropped**: appkit's emitter writes `repos: lost event: ` and the event's JSON to standard error and records `event.lost` through the run's writer, with `event`, the dropped event's id, and `cause`, its cause, under the dropped event's request id and user, so the trail says what was lost after the `repo.pushed` it shadowed. A delivery the events app refuses for good — appkit's sink then returns an error matching `events.ErrRejected` — is not retried: that one attempt drops the event at once, with its line and its `event.lost`, before or after the stop. A test drives the window with a `Sleep` that advances its own `Now`, and an `EventSink` that fails with an error other than `events.ErrRejected`, never with real waiting. That `Run` writes nothing after it returns is proved the only way a negative can be: the test keeps reading its `Stderr` buffer for a bounded moment after `Run` returns and finds it unchanged.

This design assumes a clock that reads times in the UTC years 0 through 9999, the years an RFC 3339 time can spell; appkit's writer cannot encode an event stamped outside them, and what repos records under such a clock is not contract.

## Stopping

When `ctx` is done — in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the context's cause — `Run` at once calls `Limits.Drain`, so every git operation still waiting for its slot or lock is answered with the draining refusal `D09-limits` states (`503`, `Retry-After` of `QUEUE_SECONDS`, the body `smarthttp.Stopping`, and `operation.rejected` with `limit` `draining`) while the requests in progress carry on; and it stops the maintenance schedule with `Scheduler.Stop` over a context that ends at the drain deadline, so no maintenance begins after the signal and one already running goes on until it ends or the deadline kills it (`D10-maintenance`). That `Stop`'s context ends at the drain deadline, and what a running maintenance does at it, is proved at `D10-maintenance`'s `Scheduler` seam with its `Hold` hook, since through `Run`, with no `Hold` and a real `git gc`, a maintenance cannot be held in flight; at `Run` the requirement is only that `Stop` has been called by the time `Run` returns, which a test sees by firing the interval channel afterwards and finding no new cycle. Draining the limits alone would not show it, since `D10-maintenance`'s draining rules stop per-repository work, not the schedule. It drains the server through `Serve`. Once every request has finished, and the schedule has stopped, `Run` calls the emitter's `Shutdown` inside the same drain window, which goes on delivering the bus events it holds and drops, each with its line and its `event.lost`, any the events app has not taken when the window ends, even one whose attempt still under way then succeeds; then `Writer.Shutdown` with the reason, the text of `context.Cause(ctx)`, which records `service.stopping` as the last event, after every such `event.lost`, and delivers what is queued. Last, it closes the catalog's handle.

The **drain deadline** is `DRAIN_SECONDS`, as `settings.Read` returns it, in seconds, the longest `time.Duration` when that many seconds is longer, and it runs on real time: `Process.After` is never used for it (`D01-layout-and-run-seam`), so a drain test runs with `DRAIN_SECONDS=1` and waits about a second. When the requests use the whole window, every event still queued, `service.stopping` included, is written to standard error before the stop line, which is always `Run`'s last; `Serve` cuts the remaining requests off only after its `stop` has returned, and ends their contexts, so `D08-git` ends each one's git and every process that git started and the client's connection closes without the rest of its answer. What a push cut off this way leaves is `D08-git`'s and `D09-limits`' to state: its refs are guaranteed unchanged only when the whole pack had not reached git, and once its git has ended, however it ended, a `repo.pushed` is recorded for every ref that changed; recorded after the deadline, such an event is written out or not at all, like the request's `request.finished`, and its bus event, emitted after the emitter has shut down, is dropped with its line written out or not at all. `Run` returns less than a second after the deadline, with every git it started gone, and says `repos: stopped with <n> requests unfinished` (`1 request` for one), exit 1. A maintenance run killed at the deadline is not a request and is not counted. A cut-off request's `request.finished`, recorded after the deadline, is written out or not at all, never delivered; so telemetry's trail shows the cut-off request by its `request.started` alone. A test sees "every git it started gone" without relying on where git runs: it puts a variable with a value unique to the test in `Process.Environ`, which every git `Run` starts receives (R-9Y6A-DUU3) and passes to the processes it starts, holds a push open with an `io.Pipe` body so that the drain deadline cuts it off, and, once `Run` has returned, scans `/proc/*/environ` on Linux, without starting a process, finding no process whose environment holds that variable.

## Serving and stopping the listener

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next repos — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then ends those requests' contexts, closes their connections without the rest of their responses, and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. The count is of calls to `h.ServeHTTP` that had begun and not returned. `stop` is called once, when the drain is over, with a context that ends at the deadline. An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `repos: ` and the error as `Run`'s last line, exit 1. A run that ends this way makes no promise about the requests it had in progress or about `service.stopping`; there is no signal to name as its reason. `Serve` gives its server an `ErrorLog` that goes nowhere, since Go's `net/http` documents that a nil one writes to the real standard error. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` because gosec `G112` demands it, and must not set a write timeout, which would cut a long clone short.

## The handler's routes

`web.Handler` is appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping, for the event bus's two paths, appkit's `events.DeliveryHandler(nil)` at exactly `/events` and `events.DeclarationsHandler(Config.Events, nil)` at exactly `/declarations`, and for every other path appkit's `events.Middleware`, wrapping `identity.Require`, wrapping the route table; so every request records its two events, the two bus paths answer the events app whether or not a user is named, and any other request without `X-User-Id` is answered 500 with `identity.MissingBody` whatever its path or method — never 404 or 405, and no page, no tool and no git runs for it. Routing is on the request's `URL.Path` as `net/http` decodes it, compared exactly, and never redirects. Every path falls to exactly one route:

- exactly `/events` and exactly `/declarations`: appkit's two bus handlers, every method, with or without identity (above).
- `/`, `/about` and `/tools`: the landing page, the about screen and the tools page, every method (`D04-pages`, which owns their 405 too).
- an **appkit path**, beginning `/_appkit/` (`D04-pages` defines it): appkit's `page.Static()`, unchanged (`D04-pages`).
- exactly `/mcp`: `Config.MCP`, with the six tools registered on it by `tools.Register` once, when the handler is built (`D06-mcp`).
- a **git path**: one whose first segment — the characters after the leading `/` up to the next `/` or the end — ends in `.git`, such as `/notes.git`, `/notes.git/info/refs`, `/.git/x` and `/mcp.git`: the handler `smarthttp.Handler` returns over the same store, git, limits, writer and emitter, every method, whatever follows the first segment (`D08-git`, which answers an unknown name with its own 404, and a dumb-protocol or other path under a repository, or a route asked with the wrong method, with repos' 404).
- everything else — `/nope`, `/assets/theme.css`, `/mcp/` and anything beneath it, `/about/`, `/tools/`, `/notes`, `/notes/info/refs`, `//`, `/_appkit` without its slash — is **repos' 404**: one line of plain text, `smarthttp.NotFound`, whatever the method.

repos calls no sibling while serving a request: D04-pages states it for the pages and the shared files (R-T4IT-TXRJ), and this design for `/mcp`, the git paths and repos' 404, with the same observable — a services file whose entries name sockets the test listens on, none of which has a connection pending once the answer has arrived, the deliveries to the telemetry and events entries excepted.

Before handing a request to `/mcp`, the handler puts the request's clone address in its context with `clone.NewContext` and `clone.Base` over `Config.ServicesPath`, so the tools build their URLs from it (`D07-tools`). A request to a page, a shared file, a bus path or a path that does not exist records nothing but its two request events.

The middleware records `request_bytes` as the bytes of the request body the handler read and `response_bytes` as the bytes of body it wrote (appkit's D14), both after any chunked coding is removed and with no header counted. So a page `GET` counts 0 and the page's length; repos' 404 counts its one line, and `D08-git`'s 404 for an unknown repository its own; and a git `POST` git completes counts the whole body as the client sent it, since `D08-git` streams all of it to git, and every byte of the answer git wrote.

## REQUIREMENTS

- R-P98K-SZ69: `server.Serve` MUST accept connections on `ln` and answer every request received on them over HTTP/1.1 with the response `h` produces for that request, and MUST NOT return while `ctx` is not done and serving has not failed.
- R-PAGH-6QWY: When `ctx` is done, `server.Serve` MUST stop accepting connections and close `ln`, and MUST close every connection that carries no request.
- R-PBOD-KINN: When `ctx` is done, `server.Serve` MUST let every call to `h.ServeHTTP` already in progress continue and MUST deliver the complete response of every such call that returns within `drain` after `ctx` was done; when every such call has returned and its response has been delivered before `drain` has elapsed, `Serve` MUST then call `stop`, when it is not nil, and MUST return nil once that call has returned, without waiting for `drain` to elapse.
- R-PCW9-YAEC: When `n` calls to `h.ServeHTTP`, `n` at least 1, are still in progress once `drain` has elapsed after `ctx` was done, `server.Serve` MUST call `stop`, when it is not nil, and only after that call has returned make the context of each of those requests done and close the connections those requests arrived on without writing the rest of their responses, and MUST then return a `*DrainError` whose `Unfinished` is `n`, without waiting for those calls to `h.ServeHTTP` to return.
- R-PE46-C251: `server.Serve` MUST call `stop` at most once, MUST NOT call it while `ctx` is not done or when it returns because serving failed while `ctx` was not done, and MUST pass it a context that is done once `drain` has elapsed after `ctx` was done, and not before.
- R-PFC2-PTVQ: `(*server.DrainError).Error` MUST return exactly `"stopped with 1 request unfinished"` when `e.Unfinished` is 1, and exactly `"stopped with " + strconv.Itoa(e.Unfinished) + " requests unfinished"` for every other value of `e.Unfinished`.
- R-PGJZ-3LMF: When serving fails while `ctx` is not done, `server.Serve` MUST return a non-nil error, and `Serve` MUST NOT return nil for any reason other than `ctx` being done; an `Accept` error whose `Temporary` method returns true MUST be retried, and an `Accept` error that is not a `net.Error` MUST end serving.
