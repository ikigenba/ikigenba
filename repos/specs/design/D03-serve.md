# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail repos records of itself from its start to its stop, and the rules its handler keeps on every route — the identity gate, the request's id, the request's two events, the route table that sends each path to the pages, the shared files, `/mcp` or the git routes, and the answer for a path that does not exist. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run`, the exit codes, `settings.Read` and `settings.Error`, `server.Serve`, `server.DrainError`, `web.Config`, `web.Handler`, `web.ServiceName`, `git.Find`, `store.Open` with `store.ErrDatabase` and `store.ErrRoot`, `(*store.Store).Verify`, `limits.New` and `(*limits.Limits).Drain`, `maintenance.Start` and `(*maintenance.Scheduler).Stop`, `smarthttp.Handler`, `tools.Register` and `clone.Base` with `clone.NewContext`. appkit's `telemetry` package (its designs D11 to D14) owns the events, the writer and the request middleware this design wires, its `identity` package the gate, its `page` package the shared files, and its `mcp` package the endpoint. `D02-cli` decides that an empty `Args` means serve, that a usage error exits 2 and trouble on the host exits 1, and that nothing else touches the environment. This design says in what order `Run` checks its start, which refusal touches what, how it takes the socket, opens and verifies the store, builds the writer, the limits, the maintenance schedule and the handler, tells systemd it is ready, serves and stops, and how `Serve` treats the listener it is handed, in the shapes the serve story (`S02`) shows: a clean start, a first start, a start with no services file or no telemetry, a stop that drains, a stop whose drain runs out, a restart, and the seven ways a start is refused. What the handler answers at `/`, at `/about` and under `/_appkit/` is `D04-pages`; at `/mcp`, `D06-mcp`, `D07-tools` and `D09-limits`; on a git path, `D08-git` under `D09-limits`; what the store creates, opens, verifies and rebuilds is `D05-store`; what the maintenance schedule does is `D10-maintenance`.

## The terms repos serves on

repos serves on the platform's common terms, the same as every app. It serves only on a listening socket it inherits and never opens one of its own; on a host that is `/run/ikigenba/repos.sock`, held by `ikigenba-repos.socket` beside the `Type=notify` `ikigenba-repos.service`, and nginx proxies repos' public name, git's requests included, to it. A deploy restarts the service alone, so the socket and the connections queued on it outlive every restart; that a restart refuses no request is the socket's doing, and repos' part is to finish what it accepted and leave the socket where systemd put it.

repos takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment once it has taken the socket, so no git it starts inherits a claim meant for it. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket `NOTIFY_SOCKET` names, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace. On `SIGTERM` or `SIGINT` it stops accepting, refuses at once every git operation still waiting for a slot or a lock, lets the requests it accepted finish for at most the drain deadline, then cuts off whatever is left, says how many it cut off, and exits 1. It closes its own copy of the socket and never removes the socket's path.

The suite is a closed system: repos trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway calling it at its socket to have forwarded them. Every request has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it, 32 lowercase hexadecimal digits from the random source `Process.Rand` supplies. `Process.Rand` is also where the store draws repository ids, so `Run` hands both the writer and the store one reader that never lets two reads of `Process.Rand` overlap.

repos' standard error holds only trouble: a start it refuses, a socket it cannot take, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off, and the lines appkit's writer writes for an event it could not deliver. A request answered with any status, the missing-identity 500 included, a git operation refused for a limit or killed for its deadline, and a repository found broken at start are handled failures, recorded in the trail and earning no line. So the handler has no stream at all, and while telemetry takes every event a running repos writes nothing to either stream. What git writes to its own standard error is `D08-git`'s and never reaches repos' standard error.

## Checking the start

With `Args` empty, `Run` checks, in this order: its nine settings, through `settings.Read` over `LookupEnv` (`D01-layout-and-run-seam` fixes the spelling, the defaults, the order of the nine and the text of the refusal); then whether a socket was passed in; then whether git is on the `PATH`; and only then opens the store. Each refusal is the first one that applies, so a bad setting is reported whether or not a socket was passed in or git is installed, and a missing socket whether or not git is installed.

A bad setting is the caller's mistake: `repos: `, the `Error` text of the `*settings.Error`, a newline, exit 2. A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one; anything else is no socket passed in, and a count above one is a unit repos will not guess about. Both are usage errors, exit 2, with the detail line saying how to run repos. None of these three refusals takes the descriptor, unsets a variable, looks for git, creates or opens anything under `Process.Dir`, serves, tells systemd anything, or records an event.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv` and takes descriptor 3 as its listener: through `Process.Inherit` when a test supplies one, otherwise with `net.FileListener` over the real descriptor, which, as Go's `net` documentation of `FileListener` and `UnixListener.SetUnlinkOnClose` states, leaves the socket's path in place when the listener is closed. A descriptor that cannot be made into a listener is trouble on the host: `repos: ` and the error, exit 1.

Then git. `Run` hands `git.Find` the value `LookupEnv` gives for `PATH` (empty when unset) and `Process.Environ`; when it finds none (`D01-layout-and-run-seam` states how it looks), that is a host missing a dependency opsctl provisions: `repos: git not found on PATH`, exit 1, before the store is opened, so a host without git keeps its state exactly as it was — an absent `state/` is still absent.

## The store, verification and readiness

With git found, `Run` opens the store with `store.Open` over the two paths of `D01-layout-and-run-seam` under `Process.Dir`, the git it found, `Process.Now` and the guarded `Process.Rand`. `D05-store` states what `Open` creates on a first start — `state/`, the database with its schema, the empty `state/repos/` — and when it fails with `store.ErrDatabase` or `store.ErrRoot`. `Run` maps the two with `errors.Is`: `store.ErrRoot` is `repos: cannot create directory state/repos: ` and the error's text; every other failure, `store.ErrDatabase` among them, is `repos: cannot open database state/repos.db: ` and the error's text. The paths are always these relative spellings, whatever `Dir` holds. Either is exit 1, before anything is served, before systemd is told anything and before any event is recorded. A missing database is not this error: it is a first start, or a rebuild (`D05-store`). An `Open` that fails while the context is done — the signal came during start-up — is not trouble either: like a signal during verification, it is a clean stop, exit 0, with no line.

With the store open, `Run` builds the run's writer with appkit's `telemetry.New` over `Process.Sink`, as `D01-layout-and-run-seam` declares, and verifies every repository with `Store.Verify` over that writer, so each `repo.unavailable` `D05-store` records comes before `service.started`. `D05-store` lets `Verify` fail for a context that is done, a store that was closed, or a catalog that became unwritable after `Open` succeeded (R-QBMJ-0G2N). `Run` never closes its store before it stops, and a catalog that `Open` just opened can turn unwritable before `Verify` only by a race with something outside repos, so through `Run` the one testable failure is the signal coming during start-up. For the race, `Run`'s answer is the database diagnostic, `repos: cannot open database state/repos.db: ` and the error's text, exit 1, with no `READY=1`; no test can produce it through `Run`, so it is stated here and not as a requirement. A signal that arrives before `Run` has begun to report ready — during verification, or before `Run` was even called — is a stop, not a failure, so it is exit 0 (`D02-cli` keeps 1 for a server that failed, and `S02` stops a repos that finished everything with 0): `Run` sends no `READY=1`, accepts nothing, records neither `service.started` nor `service.stopping`, lets every event already recorded (verification's `repo.unavailable` among them) be delivered or written out, and returns. The refusals before the store still come first, whatever the context holds.

Then `Run` builds the limits, `limits.New` over the settings it read and the clock `limits.Clock{Now: Process.Now, After: Process.After}`; starts the maintenance schedule with `maintenance.Start` over the same store, git and limits, the run's writer, and no `Hold`; calls `Process.MCP` once with the run's writer, once it has passed verification and is about to report ready; and builds the handler with `web.Handler` over `Process.Banner`, that server, the value `LookupEnv` gave for `IKIGENBA_SERVICES` (read once, here), the store, the git, the limits and the run's writer. Nothing about `IKIGENBA_SERVICES` or the file it names can stop a start: unset, empty, or naming a file that is missing, unreadable or malformed, repos starts, serves and says nothing about it; its pages lose the launcher, its endpoint the instructions, its clone addresses the `repos` entry, and its events, with no `telemetry` entry to find, go to standard error, all as the owning designs state.

The socket has been listening since systemd made it, so ready is true before the first `Accept`, and sending it first means a failure to send is reported before anything was served: `repos: ` and the error, exit 1. Once `READY=1` is sent, and before any connection is accepted, `Run` calls `Writer.Ready`, so `service.started`, carrying `Version`, is the first event of a run after verification's.

## The trail of a run

Every event of the process goes through the run's writer: the handler's, the tools', the git routes', the limits', maintenance's and verification's. appkit's writer queues and returns, so neither readiness nor any answer waits on telemetry; an event it cannot deliver goes to standard error as `repos: undelivered event: ` and the event's JSON (appkit's D12), in the order recorded, and repos keeps serving. A test sees this at `Run` with a `Sink` whose `Deliver` fails, and in the binary by leaving `IKIGENBA_SERVICES` unset, which leaves the socket sink nowhere to deliver. That a telemetry installed or restarted after repos started is found without a restart, and that an event already written out is not sent again, is appkit's socket sink, which reads the services file afresh on every delivery (its D13, R-WS9F-QZ7O), and the binary gets it because `main` leaves `Process.Sink` nil (R-RUI5-75QD); `Run` adds nothing to it. That `Run` writes nothing after it returns is proved the only way a negative can be: the test keeps reading its `Stderr` buffer for a bounded moment after `Run` returns and finds it unchanged.

This design assumes a clock that reads times in the UTC years 0 through 9999, the years an RFC 3339 time can spell; appkit's writer cannot encode an event stamped outside them, and what repos records under such a clock is not contract.

## Stopping

When `ctx` is done — in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the context's cause — `Run` at once calls `Limits.Drain`, so every git operation still waiting for its slot or lock is answered with the draining refusal `D09-limits` states (`503`, `Retry-After` of `QUEUE_SECONDS`, `repos is stopping; try again later`, and `operation.rejected` with `limit` `draining`) while the requests in progress carry on; and it stops the maintenance schedule with `Scheduler.Stop` over a context that ends at the drain deadline, so no maintenance begins after the signal and one already running goes on until it ends or the deadline kills it (`D10-maintenance`). That `Stop`'s context ends at the drain deadline, and what a running maintenance does at it, is proved at `D10-maintenance`'s `Scheduler` seam with its `Hold` hook, since through `Run`, with no `Hold` and a real `git gc`, a maintenance cannot be held in flight; at `Run` the requirement is only that `Stop` has been called by the time `Run` returns, which a test sees by firing the interval channel afterwards and finding no new cycle. Draining the limits alone would not show it, since `D10-maintenance`'s draining rules stop per-repository work, not the schedule. It drains the server through `Serve`. Once every request has finished, and the schedule has stopped, `Run` calls `Writer.Shutdown` with the reason, the text of `context.Cause(ctx)`, inside the same drain window, which records `service.stopping` as the last event and delivers what is queued.

The **drain deadline** is `DRAIN_SECONDS`, as `settings.Read` returns it, in seconds, the longest `time.Duration` when that many seconds is longer, and it runs on real time: `Process.After` is never used for it (`D01-layout-and-run-seam`), so a drain test runs with `DRAIN_SECONDS=1` and waits about a second. When the requests use the whole window, every event still queued, `service.stopping` included, is written to standard error before the stop line, which is always `Run`'s last; `Serve` cuts the remaining requests off only after its `stop` has returned, and ends their contexts, so `D08-git` ends each one's git and every process that git started and the client's connection closes without the rest of its answer. What a push cut off this way leaves is `D08-git`'s and `D09-limits`' to state: its refs are guaranteed unchanged only when the whole pack had not reached git, and once its git has ended, however it ended, a `repo.pushed` is recorded for every ref that changed; recorded after the deadline, such an event is written out or not at all, like the request's `request.finished`. `Run` returns less than a second after the deadline, with every git it started gone, and says `repos: stopped with <n> requests unfinished` (`1 request` for one), exit 1. A maintenance run killed at the deadline is not a request and is not counted. A cut-off request's `request.finished`, recorded after the deadline, is written out or not at all, never delivered; so telemetry's trail shows the cut-off request by its `request.started` alone. A test sees "every git it started gone" without relying on where git runs: it puts a variable with a value unique to the test in `Process.Environ`, which every git `Run` starts receives (R-KWF9-LYN5) and passes to the processes it starts, holds a push open with an `io.Pipe` body so that the drain deadline cuts it off, and, once `Run` has returned, scans `/proc/*/environ` on Linux, without starting a process, finding no process whose environment holds that variable.

## Serving and stopping the listener

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next repos — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then ends those requests' contexts, closes their connections without the rest of their responses, and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. The count is of calls to `h.ServeHTTP` that had begun and not returned. `stop` is called once, when the drain is over, with a context that ends at the deadline. An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `repos: ` and the error as `Run`'s last line, exit 1. A run that ends this way makes no promise about the requests it had in progress or about `service.stopping`; there is no signal to name as its reason. `Serve` gives its server an `ErrorLog` that goes nowhere, since Go's `net/http` documents that a nil one writes to the real standard error. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` because gosec `G112` demands it, and must not set a write timeout, which would cut a long clone short.

## The handler's routes

`web.Handler` is appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping appkit's `identity.Require`, wrapping the route table, so every request records its two events and a request without `X-User-Id` is answered 500 with `identity.MissingBody` before its path or method is looked at — no page, no tool and no git runs for it. Routing is on the request's `URL.Path` as `net/http` decodes it, compared exactly, and never redirects. Every path falls to exactly one route:

- `/` and `/about`: the landing page and the about screen, every method (`D04-pages`, which owns their 405 too).
- an **appkit path**, beginning `/_appkit/` (`D04-pages` defines it): appkit's `page.Static()`, unchanged (`D04-pages`).
- exactly `/mcp`: `Config.MCP`, with the six tools registered on it by `tools.Register` once, when the handler is built (`D06-mcp`).
- a **git path**: one whose first segment — the characters after the leading `/` up to the next `/` or the end — ends in `.git`, such as `/notes.git`, `/notes.git/info/refs`, `/.git/x` and `/mcp.git`: the handler `smarthttp.Handler` returns over the same store, git, limits and writer, every method, whatever follows the first segment (`D08-git`, which answers an unknown name `repository not found`, a dumb-protocol or other path under a repository `not found`, and a route asked with the wrong method `not found`).
- everything else — `/nope`, `/assets/theme.css`, `/mcp/` and anything beneath it, `/about/`, `/notes`, `/notes/info/refs`, `//`, `/_appkit` without its slash — is **repos' 404**: one line of plain text, `not found`, whatever the method.

repos calls no sibling while serving a request: D04-pages states it for the pages and the shared files (R-6508-RWPF), and this design for `/mcp`, the git paths and repos' 404, with the same observable — a services file whose entries name sockets the test listens on, none of which has a connection pending once the answer has arrived, the telemetry entry's deliveries excepted.

Before handing a request to `/mcp`, the handler puts the request's clone address in its context with `clone.NewContext` and `clone.Base` over `Config.ServicesPath`, so the tools build their URLs from it (`D07-tools`). A request to a page, a shared file or a path that does not exist records nothing but its two request events.

The middleware records `request_bytes` as the bytes of the request body the handler read and `response_bytes` as the bytes of body it wrote (appkit's D14), both after any chunked coding is removed and with no header counted. So a page `GET` counts 0 and the page's length; repos' 404 counts 10, and `D08-git`'s `repository not found` 21; and a git `POST` git completes counts the whole body as the client sent it, since `D08-git` streams all of it to git, and every byte of the answer git wrote.

- R-PAGH-6QWY: When `ctx` is done, `server.Serve` MUST stop accepting connections and close `ln`, and MUST close every connection that carries no request.

- R-PCW9-YAEC: When `n` calls to `h.ServeHTTP`, `n` at least 1, are still in progress once `drain` has elapsed after `ctx` was done, `server.Serve` MUST call `stop`, when it is not nil, and only after that call has returned make the context of each of those requests done and close the connections those requests arrived on without writing the rest of their responses, and MUST then return a `*DrainError` whose `Unfinished` is `n`, without waiting for those calls to `h.ServeHTTP` to return.
