# D08-git

repos serves each repository over git's smart HTTP protocol at `/<name>.git/`, and only that protocol, by running the host's own `git http-backend` against the repository's directory. This document is the git routes, `internal/smarthttp`, and what `internal/git` adds for them: how a git path is split into a name and the rest, how the name is resolved among the caller's repositories, which requests are git's four smart routes and what every other request under a repository is answered, how `git http-backend` is started (its arguments, the configuration it is handed and every variable of its environment), how request and response bodies stream through repos, what happens when the client goes away, and the two domain events of a git request, `repo.fetched` and `repo.pushed`. `D01-layout-and-run-seam` declares `git.Git`, `git.Find`, `Output`, the two buffer constants, `smarthttp.Config`, `smarthttp.Handler` and the attributes of both events; `D03-serve` decides which paths reach `smarthttp.Handler` (every git path, every method) and records each request's `request.started` and `request.finished`; `D05-store` states `Find`, `Dir` and availability; `D09-limits` owns everything a limit decides on these routes — the size check of the push routes, the slots, queues and lock taken with `Limits.Acquire`, the operation deadline, the refusals they answer and the `operation.*` events, and the `push_max_bytes` outcome whose configuration this document hands git.

## Names, routes and refusals

A git path's first segment ends in `.git`; what precedes `.git` is the **name**, and everything after the first segment is the **rest** (empty for `/notes.git`). The name is resolved among the caller's repositories only, the caller being the `identity.Caller` appkit's gate put in the request's context. A name that `store.ValidName` refuses never reaches the store: an id in the path, `/rep_3f9a0c1d2e4b5a69.git/...`, holds `_` and is a name that matches nothing, though `Store.Find` would read it as an id. An unknown name, another user's repository and an id-shaped name are all answered `404` with `repository not found`, whatever the rest, the method, the query or the body, so another user's repository is indistinguishable from one that does not exist. A repository that verification found unavailable still resolves, and every request under its name is answered `503` with `repository unavailable` and no `Retry-After`, because there is nothing to retry soon. A store that cannot be read is answered `500` with `cannot reach the repositories; try again later`, the words the tools use for the same trouble; the stories do not reach this case, and it is decided here so that a request never runs git against a repository it could not resolve.

Under an available repository exactly four requests are git's: `GET` of the rest `/info/refs` whose query names `service` once, as `git-upload-pack` or `git-receive-pack`, and `POST` of the rest `/git-upload-pack` or `/git-receive-pack`. The two upload-pack routes are the operation fetch, the two receive-pack routes the operation push. Every other request — `info/refs` without a `service`, which is how git's dumb protocol begins, a file of the repository by path (`HEAD`, `objects/info/packs`, a loose object), a git route asked with the other method, the bare `/notes.git` — is answered `404` with `not found`, before git runs, so no file of a repository's directory is ever served as a file. `git http-backend` would serve the dumb protocol itself (`http.getanyfile` defaults to true, git-http-backend(1)); repos also hands it `http.getanyfile=false`, but the refusal is repos' own.

For a smart route the order is: resolve the name; on the push routes, `D09-limits`' size check; `Limits.Acquire`, which may wait; then resolve the repository again, by its id this time, with `Store.Find(ctx, caller, id)`. A request that waited while its repository was deleted finds it gone and is answered `repository not found` with no git run; one that waited while its repository was renamed runs against that same repository, so a push that began under the old URL runs to its end (`S08`). A store that fails then is answered `500` as before. Only then does git start, under the grant, with the deadline `D09-limits` arms.

## Running git http-backend

Go's `net/http/cgi` refuses a request body without a `Content-Length`, and git sends every push larger than its `http.postBuffer` chunked, so repos does not use it. `internal/git` gains `Command`, which builds an unstarted `exec.Cmd` for the git `Find` found, with the environment `Find`'s `environ` returns followed by the variables the caller adds (a name in both takes the added value, as `os/exec` keeps the last), and which, when its context ends, kills git and every process git started, so that `receive-pack`, which `http-backend` starts with the request body as its input, dies with it and no orphan keeps the body or the answer open. `smarthttp` starts `git http-backend` with it, writes the request body to its standard input and reads its standard output.

The arguments are `-c http.getanyfile=false -c http.uploadpack=true -c http.receivepack=true -c receive.maxInputSize=<PUSH_MAX_BYTES> -c receive.autogc=false -c gc.auto=0 http-backend`; the last two keep a push from starting `git gc` on its own (git-config(1), `receive.autogc`, `gc.auto`), since collection is maintenance's, under its own slot and lock. A configuration given with `git -c` before the subcommand reaches every git that `http-backend` starts: git(1) documents that `-c` passes the configuration to the command, and a real run proved it for the children — `receive.maxInputSize` given so refused an over-size push in `receive-pack` (`fatal: pack exceeds maximum allowed size`), `uploadpack.allowFilter` given so changed `upload-pack`'s advertisement, `http.getanyfile=false` turned the dumb protocol's `HEAD` into `403`, `http.uploadpack=false` and `http.receivepack=false` refused their services, and git's own trace2 (`trace2.eventTarget`, `trace2.configParams`, `trace2.envVars` in the global config file the test composes) reports the `-c` values and the environment of `http-backend` and its children, which is how a test reads them without a hook or a shell. A `-c` setting outranks every configuration file, so the limit is the setting repos was started with for every repository, whatever its own `config` holds or when it was created.

The environment is `Process.Environ`'s, as `git.Find` was given it, plus exactly ten variables. Seven are the CGI variables git-http-backend(1) reads: `GIT_PROJECT_ROOT`, the directory that holds the repository's directory, and `PATH_INFO`, `/<id>.git` and the rest, so git finds the repository by id and never by name; `REQUEST_METHOD`; `QUERY_STRING`, `service=<service>` for `GET info/refs` and empty for a `POST`; `CONTENT_TYPE`, the request's `Content-Type`; `REMOTE_USER`, the caller's user id, without which `http-backend` refuses `receive-pack`; and `GIT_HTTP_EXPORT_ALL`, without which it refuses a repository that has no `git-daemon-export-ok`. Two carry request headers git reads under their CGI names: `HTTP_GIT_PROTOCOL`, the `Git-Protocol` header, which `http-backend` copies to `GIT_PROTOCOL` so protocol v2 works, and `HTTP_CONTENT_ENCODING`, the `Content-Encoding` header, without which `http-backend` reads a gzip-compressed `upload-pack` request (git sends one when its negotiation is long) as garbage — a real run answered `fatal: protocol error: bad line length character` without it and served the pack with it. Each is empty when the header is absent, which git treats as absent. The tenth is `LC_ALL=C`, so git's messages are untranslated: a real run under `LANGUAGE=de` sent the push refusal in German, and `D09-limits` recognises `pack exceeds maximum allowed size` in git's answer. `CONTENT_LENGTH` is never set by repos, so git reads its input to its end whether or not the request had a length, and `REMOTE_ADDR` is not set because git uses it only for a reflog identity a bare repository does not keep. None of the ten carries the `Authorization` header and repos adds no `HTTP_AUTHORIZATION`, which `D11-on-a-space` relies on.

## Streaming

repos never holds a whole body. The request body is copied to git's input as it arrives, through a buffer of `git.CopyBufferSize` bytes, and git's output is copied to the client as git writes it, through another, flushed after each write. A real run proved that `http-backend` writes its header block for `receive-pack` before reading any of the push, and that `receive-pack` updates its refs, writes its whole answer and exits once the pack it was sent is complete, without waiting for its input to end. So a test that pushes with an `io.Pipe` body it has not closed sees the ref move and receives the whole answer before it closes the pipe — proof that the body reached git before the body ended — and one that has sent only part of the pack receives the status and headers while git is still reading — proof that the status and headers are sent before git finishes. That the answer's body is relayed as git writes it shows in a fetch whose answer is larger than every buffer between git and a client that stops reading: the client holds the first bytes of the pack while git, blocked on its full pipe, has not ended, which git's trace2 event file shows by the absence of `http-backend`'s `exit` event; a test shrinks the socket buffers on both sides and fetches a pack of several MiB, so that no internal buffer larger than the fixed ones could hold the answer and pass. The handler reads the request body while the answer is being written, which `net/http` permits for HTTP/1.1 only after `http.ResponseController`'s `EnableFullDuplex` (appkit's middleware unwraps to the real writer); a probe confirmed that the whole answer reaches a client whose request body is still open.

git's answer begins with a CGI header block: `Name: value` lines and an empty line, a `Status:` line giving a status other than 200. `git.ReadHeader` parses it, reading no more than `git.MaxHeaderBytes` of block and failing with `git.ErrHeader` when the block is longer, malformed, or cut short; the status, every header and every byte after the block are relayed unchanged, so what passes on these routes is git's protocol exactly as git writes it. A real `git http-backend` never writes such a block, so what the handler answers when `ReadHeader` fails is not contract and no requirement states it; the bound is proved at `ReadHeader` itself.

That repos' memory does not grow with a pack is the reason for the fixed buffers, but it is not provable by a test `AGENTS.md` permits: resident memory is not a deterministic observable of a unit test and the story's 50 MiB push is far beyond what the tests may push. What is proved is the streaming that makes it true: the request body reaches git before it ends, the answer and its first body bytes reach the client before git ends, a chunked body is read like any other, and the header block is bounded. Resident memory itself is the untestable residue.

## When the client goes away

A client that goes away while git runs — its connection closed, which repos learns from the request's context, from a failed read of the body or from a failed write of the answer — has its git killed at once, through `Command`'s context; `ServeHTTP` then returns without waiting for the operation deadline, the grant is released (`D09-limits`), and git, which changes a ref only once a whole push has arrived, has changed nothing when the pack was not complete. The same holds when the request's context is ended by the stop, at the drain deadline (`D03-serve`): git is killed, its processes have ended before `ServeHTTP` returns, and a real run that killed `http-backend`'s whole process group mid-pack left the refs as they were and `git fsck` clean (it leaves receive-pack's quarantine directory under `objects/`, which `fsck` ignores). A fetch whose git repos ended records no `repo.fetched`, since it did not complete; a push records `repo.pushed` for whatever its refs show once git has ended, however git ended, which is nothing unless the whole pack had arrived. A push can be killed after git has moved its refs: `receive-pack` updates every ref before it writes its report, so a push of thousands of refs to a client that stops reading leaves git blocked on its report with the refs already moved — a real run of 20000 refs left all 20000 moved while `receive-pack` was still running — and killing it then leaves them moved, which is why the comparison is made however git ended. A client sees the report's first bytes only after the refs have moved, which is how a test reaches that moment without waiting. The test sets `receive.keepAlive=0` in its `GIT_CONFIG_GLOBAL` file, so `receive-pack` sends no keepalive before the refs move and the first body bytes the client reads are the report's.

## Events

A `POST git-upload-pack` that completes — its git exited with status 0 by itself and its whole answer relayed — records one `repo.fetched` after git has ended. Its `bytes` are the pack it served: git sends the pack on side-band channel 1 in both protocol versions, so `bytes` is the sum of the payloads of the answer's channel-1 packets, which is exactly the file a client's `GIT_TRACE_PACKFILE` (git(1)) writes; a real run measured both at 2000998 bytes for a v0 and a v2 clone, and 0 for the v2 `ls-refs` request of an empty repository's clone, which carries no pack. The advertisement routes record no domain event.

A `POST git-receive-pack` whose git ran records, once git has ended however it ended, one `repo.pushed` for each ref whose value differs between just before git started and just after it ended, with `old` and `new` the values then, forty zeros for a ref absent on one side. Comparing the refs is exact because the push holds its repository's write lock (`D09-limits`): nothing else changes a ref meanwhile, and a push git refused, whether for a non-fast-forward or for its size, changed none. The order of several is not fixed. A push keeps its grant, and so its lock, until its `repo.pushed` events are emitted, so two pushes to one repository record their events in the order they ran; a test sees it through the `Limits`' own clock, kept separate from the writer's and the middleware's: once `Pressure` shows the second push queued and the test has closed the first push's body, the next call of that clock's `Now` is the one that makes the second push's grant, inside the first push's `Release` (no other caller reads that clock meanwhile: the handler reads it neither itself nor through the grant once granted, the second push's `Acquire` read it when it began to wait, and the first push's deadline uses only `After`); the test holds that call, flushes the writer (appkit's `Writer.Flush` returns once every event queued before it is delivered), and finds the first push's `repo.pushed` events, which a handler that released before emitting could not yet have emitted. Both events carry the request's id and caller in their envelope and the repository's id, never its name.

## Consumer tasks

A handler test serves `smarthttp.Handler` inside appkit's `identity.Require` and `telemetry.Middleware` (or `web.Handler`) over a `*telemetry.Capture`, on loopback; creates `notes` with `s.Create`; clones, fetches and pushes through it with the test's own `git`, whose config sets the identity headers as `http.extraHeader` and, to force a chunked push with a small pack, a small `http.postBuffer`; and compares the events with refs it reads back with `git --git-dir=<Store.Dir(id)> for-each-ref` and with the file `GIT_TRACE_PACKFILE` wrote. It sends raw requests for the refusals. It holds a push body open with `io.Pipe`, writing a push request it captured from its own git, to watch the ref move before it closes the pipe, or closes the connection mid-pack to watch `ServeHTTP` return. It observes git's environment and configuration through trace2: its `GIT_CONFIG_GLOBAL` file sets `trace2.eventTarget` to a file in its temporary tree, `trace2.envVars` to the variables it checks and `trace2.configParams` to the keys it checks, and it reads the `def_param` events; it replaces `os.Stdout` and `os.Stderr` with pipes around a request whose git writes to its standard error; and it learns that no git ran by an `environ` passed to `git.Find` that counts its calls. A test of `internal/git` calls `ReadHeader` on byte readers, and runs `Command` for `http-backend` with a held input to see the whole process tree die with the context.

The handler's own flow: `caller, _ := identity.FromContext(ctx)`; `r, err := s.Find(ctx, caller.UserID, name)` after `store.ValidName(name)`; `D09-limits`' size check and `g, err := l.Acquire(ctx, r.ID, op, lock)`; `defer g.Release()`; `s.Find(ctx, caller.UserID, r.ID)` again; `cmd := cfg.Git.Command(gitCtx, "", env, "-c", ..., "http-backend")` with `StdinPipe` and `StdoutPipe` and its standard error discarded; `status, h, body, err := git.ReadHeader(stdout)`; relay through `make([]byte, git.CopyBufferSize)`, selecting on `g.Deadline()`; then `cfg.Telemetry.Emit(ctx, "repo.pushed", ...)` or `"repo.fetched"`.
