# D02-cli

repos as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, and the three constants whose text is fixed here — the usage text, the manifest and the nginx fragment — with the two files under `etc/` that copy the last two. When `Args` is empty repos serves, and everything from there is `D03-serve`.

The arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Version` and a newline, `manifest` writes `Manifest`, and `--help` writes `Usage`. The one two-word command, `db status`, prints the catalog's migrations (below). Any other `Args` is a usage error. The argument repos complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone, which is not a command by itself; the third when the first two are `db status`; otherwise the second, which is surplus or, after `db`, not a database command. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `repos: `, and after exactly one empty line comes the hint to run `repos --help`, unprefixed because repos is speaking for itself. The usage text is never written to `Stderr`.

The help text says what repos serves and where, and names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. `D03-serve` leans on that split: a start the caller got wrong — no socket, several sockets, a setting that is not a positive whole number — exits 2, while trouble on the host once repos is past its checks — no git on the `PATH`, a database it cannot open, a drain that runs out — exits 1.

Arguments are checked before anything else. A command needs no socket and no git, so `repos --version` succeeds with nothing passed in and `repos bogus` fails whatever the environment holds; `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, the timer, the random source, the sink, the banner source or the server maker unless `Args` is empty, and no command but `db status` reads the state directory. A command runs no git and records no event: the trail is what repos records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns, `db status` included. Every failure leaves `Stdout` empty, `db status`'s lines excepted, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## db status

`repos db status` shows an operator the schema the binary expects beside what the catalog holds. Its whole body is appkit's `db.Status` (its D16), called with the `Config` `Run` gives `db.Open` when it serves — the path `state/repos.db` under `Dir` and the root package's `repos.Migrations()` — and `Stdout`; it reads no clock, so the `Config` carries no `Now`. appkit owns the lines, what it reads and that it changes nothing: one line per version, `applied` with its time, `pending`, or `unknown` with its time; every version pending and nothing created when there is no database. repos owns the grammar and the exits: what `db.Status` writes goes to `Stdout` whatever it returns; nil is exit 0 with `Stderr` empty; an error is one line on `Stderr`, `repos: ` and the error's text on one line, and exit 1, so a catalog a newer repos upgraded prints its lines, the unknown one among them, then fails, and one that cannot be read prints nothing and fails. It neither reads nor rebuilds the repositories: it starts no git and looks at nothing under `state/repos/`.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text is exactly the bootstrap story's: repos' name; its description, which is `web.Description`; that it is not the host's default app; that it is one of the suite's MCP services; no secrets; the eight settings of `[env]` with the defaults `settings.Defaults` holds, in the order `settings.Read` checks them; the `[database]` table that tells opsctl to keep and replicate `state/repos.db`; and the `[resources]` table opsctl writes into the service unit — `cpu_weight` 50 and `io_weight` 50, half the share of a service that declares none, and `memory_max` `1G` — which bounds repos and every git it runs together (opsctl's `S7-apps.md`: three optional keys, `cpu_weight` and `io_weight` whole numbers from 1 to 10000, `memory_max` a whole number of bytes with an optional `K`, `M` or `G`). It declares no port and no `DRAIN_SECONDS`, which are opsctl's to refuse and to own.

## The nginx fragment

The host's nginx includes an app's `etc/nginx.conf*` at the level of the app's server block (opsctl's `S5-nginx.md`, `include /opt/<app>/etc/nginx.conf*;`), before every location the host declares, and nginx inherits a directive set at server level into every location that does not set it; opsctl's generated locations set none of the body-size, timeout and buffering directives, precisely so an app that takes large, slow uploads can widen them for its own block. repos' fragment, the constant `NginxConf`, does exactly what the package story asks and nothing else, one directive per line, each allowed in the `server` context by nginx's documentation:

- `client_max_body_size 0;` — no limit on a request body (ngx_http_core_module: "Setting size to 0 disables checking of client request body size"), so a push is refused only by repos' own `PUSH_MAX_BYTES`.
- `proxy_request_buffering off;` — the body is sent to repos "immediately as it is received" (ngx_http_proxy_module).
- `proxy_http_version 1.1;` — the same documentation: "When HTTP/1.1 chunked transfer encoding is used to send the original request body, the request body will be buffered regardless of the directive value unless HTTP/1.1 or HTTP/2 is enabled for proxying", and nginx before 1.29.7 proxies with HTTP/1.0 by default; git sends every push over 1 MiB chunked, so without this line the large push the stories stream would be spooled.
- `proxy_buffering on;` — nginx reads repos' answer "as soon as possible" into its buffers (ngx_http_proxy_module), so a slow client does not hold a git process open; it is nginx's default, stated so that no wider setting can turn it off for repos.
- `proxy_read_timeout 3600s;` and `proxy_send_timeout 3600s;` — each is the idle time allowed "between two successive read [write] operations" with the upstream, not a limit on the whole response, 60 seconds by default; nginx keeps the connection to repos open while repos works and gives up only after an hour in which nothing has passed. A push's git writes nothing back until its whole pack has arrived, and an operation may first wait `QUEUE_SECONDS` for its slot, so the longest silence at the defaults is `QUEUE_SECONDS` plus `OPERATION_SECONDS`, 630 seconds; 3600 seconds covers it with room, and is the value opsctl's own probe of a 300 MB push through the git location used. An operator who raises the two settings past an hour together widens nginx's silence beyond what this fixed fragment allows.

The fragment carries no location and no credential directive: the git challenge is the host's (opsctl's `S5-nginx.md`), and nothing here touches what nginx logs.

## The two files under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ; `etc/nginx.conf` holds exactly the text of `NginxConf`. The build run writes both from the constants and keeps them in step. The constants' values are proved by use — `manifest` prints `Manifest`, and `NginxConf` is a declared constant a test compiles against and compares. The files are proved by use too: the root package embeds `etc/` as it embeds `assets/`, and exports it as `Etc`, so a test compares the embedded `manifest.toml` and `nginx.conf` with the two constants without ever opening the checkout, and a build whose `etc/` lacks either file, or holds a stale copy, fails to compile or fails that test. `devctl build` checks the manifest once more on its own. That test lives in the external test package `repos_test` beside the root package, since it imports both the root package and `internal/cli`, and `internal/cli` reaches the root package through `internal/web`, so a test inside package `repos` would form an import cycle. Nothing prints the fragment: the bootstrap story fixes the usage text and its one command.
