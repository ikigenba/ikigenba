# D09-limits

repos runs git for anyone who asks, so it bounds how much git it runs: how many operations at once, how long one may wait and run, and how large a push or a repository may grow. This document is `internal/limits` — the slots, the queues, the per-repository write lock, the queue wait and the operation deadline, the stop's refusal of waiters, what makes a repository busy, and the pressure snapshot — together with what a git request observes of those limits at `smarthttp.Handler` (the refusals, their words and their events), and the `status` tool, which shows the pressure to a model. `D01-layout-and-run-seam` declares `limits.Clock`, `Op`, `Limits`, `New`, `Settings`, `Clock`, `Drain`, `Busy` and `TryHold`; this document declares the acquire API and the pressure snapshot, and states what every one of them does. The settings, their defaults and their parsing are `D01`'s; the git routes, name resolution, the exec of `git http-backend`, the configuration it hands git and the events `repo.pushed` and `repo.fetched` are `D08-git`'s; maintenance's use of the same API is `D10-maintenance`'s; the `status` tool's list entry (description, schemas, kind) and the refusal for an unreachable store are `D06-mcp`'s.

## Slots, queues and the lock

Every operation is of one of two kinds. A fetch is a read; a push and a maintenance run are writes. Each kind has its own slots, `READ_SLOTS` and `WRITE_SLOTS`, and its own queue of at most `QUEUE_LENGTH` waiters, and the two never share, so a flood of clones never holds up a push. An operation asks with `Limits.Acquire`, naming the repository by id, its `Op`, and whether it needs the repository's write lock: a `POST git-receive-pack` and a maintenance run do, everything else does not. Reads take no lock, so a clone goes on while its repository is pushed to or maintained.

`Acquire` either grants at once, refuses at once, or waits. It grants at once when its kind has a free slot, the lock (if it asked for it) is free, the repository is not held by `TryHold`, and no waiter of its kind could take that slot first. It refuses at once with `ErrQueueFull` when it cannot be granted and its kind's queue already holds `QUEUE_LENGTH` waiters. Otherwise it joins its kind's queue — a push waiting only for the lock counts among the writes waiting, as the story says — and waits for both together, holding nothing while it waits, for at most `QUEUE_SECONDS` measured on `Clock.After`; when that channel delivers first it refuses with `ErrQueueTimeout`. A slot that comes free goes to the waiter of its kind that has waited longest among those that can take it, and it is handed over inside the `Release` (or hold release) that freed it, as many times over and for both kinds as free slots and eligible waiters allow: by the time `Release` returns, the waiter's grant is made and counted active, and no newcomer can take the slot ahead of a waiter. A push stuck on one repository's lock never holds up a push to another. `Drain`, called at a stop, turns every waiter away with `ErrDraining` and refuses every later call the same way; grants already made run on. `Draining` reports whether `Drain` has been called, so maintenance can tell a repository it reaches after the stop (and records nothing for) from one that was waiting when the stop came (and records `draining` for). A waiter whose context ends leaves the queue with an error wrapping the context's cause. Whatever the error, nothing is held.

A granted operation is in flight until its `Grant` is released: it counts as active, and its repository is busy. `Grant.Waited` is how long it waited, zero when it did not; `Grant.Deadline` arms the operation's `OPERATION_SECONDS` on `Clock.After` the first time it is called, which the git routes do when git starts; `Grant.Release` frees the slot and the lock, and is safe to call twice; a push releases its grant only once its `repo.pushed` events are recorded (`D08-git`), so two pushes to one repository record theirs in the order they ran, and every grant is released before `ServeHTTP` returns. `TryHold` is how `delete` makes sure nothing runs on a repository while it is removed: it succeeds only on a repository that is not busy, makes it busy, and while held no `Acquire` on that repository is granted, of any kind; its waiters wait as for a slot and, once it is released, find the repository gone (`D08-git` re-resolves the repository by its id after `Acquire`). `Pressure` is a snapshot of each kind's slots, active and queued counts, taken without waiting for anything.

Every setting can be as large as an `int64` holds. Slots and queue lengths are counts, never allocations, and a number of seconds turned into a `time.Duration` saturates at the longest duration.

## Sync points

Tests drive limits without sleeping, through the clock they hand `limits.New`, so two moments are contract. A waiting `Acquire` is counted `queued` before it calls `After` for its queue wait, and calls it exactly once; an `Acquire` granted or refused at once calls `After` not at all. A grant is counted `active`, and its repository busy, before `Acquire` returns it — so also before `Deadline` calls `After` for the operation's deadline. A test therefore learns that a request is waiting when its fake `After` is asked for `QUEUE_SECONDS`, and that it holds its grant when asked for `OPERATION_SECONDS`, and fires either when it chooses. A deadline that fires at any time after that `After` call and before git has ended counts, git started or not, so the firing never races git's start; this matches maintenance (`D10-maintenance`), where a deadline already fired when git starts is a timeout. `wait_us` is measured on the injected `Now`, and `operation.waited` is recorded only when the wait measured more than zero, so a test that wants to see it advances `Now` while the request waits. Every git request has released its grant by the time `smarthttp.Handler`'s `ServeHTTP` returns, which a test that wraps the handler observes.

## What a git request sees

For each git request, `D08-git` resolves the name, and then, on the two push routes only, repos measures the repository with `Store.Size` before seeking any slot (a repository deleted meanwhile is answered `404` `repository not found`, and a store that cannot be reached `500` `cannot reach the repositories; try again later`, as `D08-git` answers them): a repository at or over `REPO_MAX_BYTES` is answered `507` with `repository is at its size limit of <REPO_MAX_BYTES> bytes` and no `Retry-After`, since waiting will not help, while fetches go on as before. The ceiling is checked as each request begins, so a push that starts under it is taken whole even when it carries the repository over. Then the request acquires: a fetch route `Acquire(ctx, id, Fetch, false)`, `GET info/refs?service=git-receive-pack` `Acquire(ctx, id, Push, false)`, `POST git-receive-pack` `Acquire(ctx, id, Push, true)`. A full queue and a wait too long are both answered `503` with `Retry-After` set to `QUEUE_SECONDS` and the one line `too many git operations; try again later`; a waiter turned away by a stop is answered the same way with `repos is stopping; try again later`. None of these runs git. A request that waited and then runs git records `operation.waited` once its grant and the re-resolution of its repository by id have succeeded, before git starts; one whose repository was deleted while it waited is answered `404` and records none, and one renamed while it waited runs against the same repository. A request refused with `507` or `503` records exactly one operation event, its `operation.rejected`, and never `operation.waited`. With one clock behind both the limits and the writer, `wait_us` never exceeds the request's `duration_us`. A git still running when its deadline delivers is killed and its connection closed without the rest of the answer; the request records `operation.timed_out`. A push killed before its whole pack reached git has moved no ref; one whose pack was complete may have, and records `repo.pushed` for what moved (`D08-git`). A client that goes away while waiting leaves the queue; one that goes away while git runs has its git killed (`D08-git`); neither records a limit event.

`PUSH_MAX_BYTES` is git's own limit: `D08-git` hands git `receive.maxInputSize` from the setting the `Limits` holds, for every repository whatever its age, and git refuses an over-size pack as it arrives, in its own words, `pack exceeds maximum allowed size`, which reach the client in the answer git writes and repos relays. git reports that refusal only in its answer (receive-pack answers `200` and exits as for any refused push, so neither status nor exit tells it apart), so that answer is how repos knows: a `POST git-receive-pack` whose answer carries those words records `operation.rejected` with `limit` `push_max_bytes`, and no other request does. The text was observed with a real git (a push of a 5 MiB pack to a repository with `receive.maxInputSize` 1048576 answered `fatal: pack exceeds maximum allowed size` on side-band channel 2, then `unpack unpack-objects abnormal exit`).

`Store.Size` does not fail for a catalogued repository (`D05-store`); it fails with `store.ErrNotFound` for one deleted after the name was resolved, answered `404` `repository not found`, and otherwise only when the store cannot be reached, answered `500` with `D08-git`'s text (R-3M3I-62O4), both before any slot is sought.

## The status tool

`status` takes no arguments and answers `{"read":{...},"write":{...},"repos":[...]}`: the two kinds' `slots`, `active` and `queued` from one `Pressure` snapshot, for every user's operations alike, and then the caller's own repositories from `Store.List`, by name ascending, each with `id`, `name`, `size_bytes` (`Store.Size`, as `list` gives it), `limit_bytes` (`REPO_MAX_BYTES`), `available` and `busy` (`Limits.Busy`). It takes no slot and waits for nothing, so it answers at once under any load. A catalog or disk it cannot read is the unreachable-store refusal of `D06-mcp`.

## Consumer tasks

The git routes: after resolving `notes` to `id`, a `POST git-receive-pack` calls `Store.Size(ctx, id)` and answers `507` when it is at least `l.Settings().RepoMaxBytes`; otherwise `g, err := l.Acquire(r.Context(), id, limits.Push, true)`, answering `503` for `errors.Is(err, limits.ErrQueueFull)`, `ErrQueueTimeout` or `ErrDraining` and nothing for a cancelled request; on a grant it `defer g.Release()`, records `operation.waited` when `g.Waited() > 0`, starts git, and selects on `g.Deadline()` beside git's end.

`delete`: `release, ok := l.TryHold(id)`; when `!ok` it refuses as busy, else it removes the repository and calls `release()`. `status`: `p := l.Pressure()`, `s.List(ctx, caller)`, then `s.Size` and `l.Busy` for each.

A test of the limits builds `limits.New(s, limits.Clock{Now: clock, After: after})` whose `after` records each requested duration and returns a channel the test fires; it fills the read slots with `Acquire(ctx, "a", limits.Fetch, false)`, starts one more `Acquire` in a goroutine, waits until `after` is asked for 30 seconds, reads `Pressure().Read.Queued == 1`, advances `clock`, releases a grant and asserts the waiter's `Waited()`. A test of the handler serves `smarthttp.Handler` inside appkit's `identity.Require` and `telemetry.Middleware` over a `*telemetry.Capture`, holds slots by calling `Acquire` and `TryHold` on the `*limits.Limits` it built, or with a push whose body is an `io.Pipe` it keeps open, and pushes with real git from its own environment.

- R-XDNC-RTG4: The limit git enforces on the pack of a `POST git-receive-pack` that `smarthttp.Handler` runs MUST be `l.Settings().PushMaxBytes` of its `Config`'s `Limits`, whatever that value was when the repository was created, so that a push whose pack is over 4 times one `Limits`' `PushMaxBytes` is refused with git's `pack exceeds maximum allowed size` reaching the client, no ref moved, and no object the push sent readable in the repository, and the same push to the same repository through a handler whose `Limits` has a `PushMaxBytes` over 4 times that pack's size is accepted.
