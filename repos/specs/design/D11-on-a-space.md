# D11-on-a-space

What repos itself contributes when it runs on a space and in a sandbox, and what it does not. The package story (`S16-package.md`), the space stories (`S17-on-a-space.md`) and the sandbox stories (`S18-in-a-sandbox.md`) prove the whole path from a checkout to a browser, git and an agent, and almost every step on that path belongs to someone else: devctl builds and ships the file, opsctl installs it, writes the environment, publishes the socket, bounds the unit and generates nginx, auth decides every credential, the host's nginx challenges git, the mcp gateway relays tool calls, the events app takes, stores and serves the bus events repos emits, and the sandbox stands the same arrangement up on a developer's machine. repos' own share is what the earlier designs already state — the manifest and the nginx fragment (`D02-cli`), the serve path (`D03-serve`), the pages (`D04-pages`), the tools and the clone address (`D07-tools`), the git routes and the bus events of a push (`D08-git`), the emitter, its retries and losses and the event bus's two paths (`D03-serve`), the limits (`D09-limits`) — plus one guarantee those stories lean on that no single earlier document owns: the token a caller presents never leaves repos in anything repos writes. This design states that guarantee, and the one thing the sandbox story says repos must not do with its environment; for every other outcome of the three stories it names the owner, and it says plainly what can be checked only on a running space.

This design declares no name. Everything it states is behaviour of names `D01-layout-and-run-seam` and `D02-cli` declare: `cli.Run` and `cli.Process`, `web.Handler`, and the tools `D07-tools` registers.

## What ships

The package story lists four members of the release file: `bin/repos`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`. Two of those are repos' contract and are already designed: the manifest's and the fragment's exact texts are the constants `cli.Manifest` and `cli.NginxConf`, and the root package's `Etc` proves that `etc/` holds exactly those two files with exactly those bytes (`D02-cli`), which is also how "nothing under `etc/` but the manifest and the fragment" is proved. That the binary in the file, asked `--version` with neither `IKIGENBA_COMMIT` nor `IKIGENBA_RELEASE` set, prints one empty line — it carries no identity of its own, and the commit in the file's name is nowhere inside it — is `D02-cli`'s `--version` over the display string `D01-layout-and-run-seam` defines, and that `repos manifest` prints the manifest byte for byte is `D02-cli`'s. That the binary is static `linux/amd64` and cgo-free is the release build gate of `AGENTS.md`, not a requirement. That no `assets/` directory or font ships beside the binary follows from the pages and appkit's shared files being embedded (`D01-layout-and-run-seam`, `D04-pages`). That neither the database nor any repository is in the file, and that repos creates `state/repos.db` and `state/repos/` on its first start, is `D01-layout-and-run-seam`'s and `D03-serve`'s.

The rest of the file is not repos' to state. The tarball, its member list, its name `repos-<sha>.tar.xz` carrying the full sha of the clean commit it was built from, with no tag read, and no member's path carrying it, are `devctl build`'s; `share/icon.svg` is human-authored (`AGENTS.md`), and that its presence lists repos in the launcher is opsctl's services file (opsctl's `S9-services.md`: an entry's `icon` is the file's bytes). No test reads the checkout, so the tarball and the icon, like telemetry's and mcp's, are outside what a requirement can state; a developer checks them with the package story's own `tar` commands.

## The credential

On a space every request repos receives has already been admitted by auth, and nginx passes the client's `Authorization` header on to repos untouched: git's `Basic` credential on a git route, an agent's `Bearer` token on whatever the gateway or a client sends. repos never needs the header — the caller is `X-User-Id` — and the stories promise that the token's secret is in no record any of them leaves: not in the trail, not in a clone's `.git/config`, not in the developer's global git config. repos can keep its part of that promise, and prove it, at its own seams.

A request carries a **credential header** when its `Authorization` header is `Basic ` and the standard base64 of `<u>:<p>`, or `Bearer <p>`, the test choosing `<u>` and `<p>` long, with an uppercase letter in every 8-character stretch of each and of their base64 value so that no hex id, sha or number can match them, and occurring nowhere else in what it sends or pushes. Its **secret strings** are every run of 8 or more consecutive characters of `<p>`, of `<u>`, and of the base64 value, so a truncated or partial leak counts as a leak. Four guarantees follow. First, nothing repos records — no event's name, envelope or attribute — holds a secret string, whatever the request was: a page, a tool call, a fetch, a push. `D01-layout-and-run-seam` already fixes each domain event's exact keys and forbids a credential among them, and appkit's middleware records only the method and the path, so this is the end-to-end statement of what those already imply, proved through `Run` with a capturing sink. Second, nothing repos writes to standard error holds one either, including the lines appkit's writer writes for events it could not deliver. Third, no response repos writes holds one, and the clone address and the credential guidance do not depend on the header at all: `clone.Base` gives the same address with or without it (`D07-tools`, R-94UA-J9EC), and the landing page's clone line and helper command, and a `show` result, are the same with or without it. Fourth, nothing repos leaves on disk holds one: after a run that served such requests, no file under its working directory — the catalog, each repository's config, refs, reflogs and hooks' leftovers alike — contains a secret string, which also catches a credential that reached a git process through its environment (as `REMOTE_USER`, say) and was written down. With `D07-tools`' exact clone URLs — the services file's `url`, which opsctl writes as `https://<name>.<host>`, and the repository's name — that is what makes "the clone URL holds no credential" true, so the origin git records in `.git/config` holds none; the guidance's helper reads `$IKIGENBA_TOKEN` when git asks, so the global git config holds the helper and nothing of the token.

Which variables a git process repos starts is given is `D08-git`'s, which names the CGI variables it sets; the fourth guarantee is what this design proves of them, and `D08-git` is expected to name none that carries the `Authorization` value.

## In a sandbox

In a sandbox repos is the same binary in the same arrangement: the sandbox builds it from the worktree, runs it under its own units with a working directory of its own (`<sandbox data>/apps/repos`), gives it the environment of a host — `DRAIN_SECONDS`, `IKIGENBA_SERVICES` and the manifest's eight settings — with `IKIGENBA_COMMIT` set to the worktree's full sha, `-dirty` appended when the tree has changes, and no `IKIGENBA_RELEASE`, plus variables a host never sets, puts its own nginx in front with repos' `etc/nginx.conf` from the checkout included in repos' server, and challenges git and routes through auth's `/check` as a host does (sandbox's `S3-apps.md` and `S4-routing.md`). All of that is the sandbox's. repos' contributions are the ones it makes on a space:

- It serves under the sandbox like any app, at `http://repos.<name>.localhost:<port>`, which the sandbox prints; its catalog and repositories are under its working directory (`D01-layout-and-run-seam`, R-SE0J-BHLH), so they survive `down` and `up` because the sandbox keeps that directory until `wipe`.
- Its clone URL is built from the sandbox's services file, whose `url` for repos is `http://repos.wip.localhost:7400`, so it is `http://repos.wip.localhost:7400/<name>.git` and the guidance names `credential.http://*.wip.localhost:7400.helper` (`D07-tools`, `D04-pages`).
- It runs the first `git` on the `PATH` it is given (`D01-layout-and-run-seam`); that the sandbox's `PATH` holds the developer's own `git` is the sandbox's arrangement, which its stories do not promise, so it is a sandbox-level check.
- It reads nothing from its environment beyond what a host gives it, so the variables only the sandbox sets change nothing it does. That is stated below (R-GUUE-SI18) as the set of names `Run` looks up; `AGENTS.md`'s run-seam rule is what keeps repos' own code from reading the environment any other way. Readers sit outside `LookupEnv` by appkit's published design: `page.New` and `mcp.NewServer`, which `main` calls, and appkit's two socket sinks, telemetry's and the event bus's, read `IKIGENBA_SERVICES` from the real environment (`D01-layout-and-run-seam`). The whole environment still reaches the git repos runs through `Environ`, as on a host.
- Its footer, its about screen, its MCP `serverInfo` and its `service.started` carry the display string `main` reads from `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` (`D01-layout-and-run-seam`, R-KDXP-VNUC), which under the sandbox is the worktree's short commit, with `-dirty` after it when the tree had changes; the shortening is appkit's `version.Display`, and the value it shortens is the sandbox's. Those two variables are a host's identity for the code it runs, read in `main` and never through `LookupEnv`.
- The same credential guarantees hold; `sandbox logs repos` showing no line is `D03-serve`'s quiet standard error.

The landing page, the agent's create and push, and the large push in the sandbox stories are the space stories' outcomes again, with the sandbox in place of opsctl and the host's nginx, and the same owners. So are the sandbox's event stories: the catalog and the search through the gateway, a push with `X-Event-Cause` and `X-Event-Depth`, which the sandbox's nginx passes through because it sets neither (`D03-serve`, R-E7QV-CU4V, R-E5B2-LANH), a push while the sandbox's events units (`S18`'s `sandbox-wip-events.socket` and `.service`, its sandbox being `wip`) are stopped and started again within a few minutes or left stopped too long, and the two bus paths answered 404 by the sandbox's nginx with repos' fragment included; stopping and starting the events app's units is the sandbox's and systemd's.

## What only a space can show

These outcomes are space-level checks: no test of repos can make them, and they are verified by running the stories on a space or in a sandbox.

- An unauthenticated git request is challenged, a refused or malformed credential is answered `403`, and in each case nothing reaches repos' socket and repos records no event — nginx's and auth's doing.
- The host's nginx access log holds no token: its format is opsctl's (`S5-nginx.md`), and repos neither writes it nor affects it. That format logs `$remote_user`, which nginx fills with a Basic credential's username (`token` with the guidance's helper), so the log holds the username though not the password.
- The `PATH` the sandbox gives repos holds the developer's own `git`.
- repos' own resident memory, not counting the git it runs, stays far below the pack's size during a large push or fetch (`S11-git.md`). No test measures memory; what a test proves is that repos never holds the body or the answer whole: a push reaches git before its body ends (`D08-git`, R-D750-DRE3), a fetch's answer reaches the client before git ends (R-L3QO-KSYG), the answer a `POST` holds back while its body arrives is bounded and released once git has written `git.CopyBufferSize` bytes after its header block (R-2BTM-M9KJ, R-2FHB-RKSM), the CGI header block is bounded by `git.MaxHeaderBytes` (R-CRAB-EQR2, R-CSI7-SIHR), and the copies run through buffers of `git.CopyBufferSize` (D01's R-T7A4-HZE5). The memory itself is observed on a space or in a sandbox during the 50 MiB push.
- A 50 MiB chunked push passes the host's or the sandbox's nginx without `413` and without spooling — the fragment's directives are `D02-cli`'s constant, but that nginx honours them as included is checked only through nginx. nginx stops passing a request body upstream once the upstream's response header has arrived, so the push gets through only because repos sends nothing of a `POST`'s answer until the body has ended (`D08-git`, R-2BTM-M9KJ); that requirement is proved without nginx, and the push through nginx is checked on a space or in a sandbox.
- The release file holds exactly the four members, the icon is an SVG, and the launcher a browser opens lists repos marked as the current page.
- auth's records of each request (`check.allowed`, `check.refused`) and the gateway's relay of `create`.
- The events app's `catalog` and `search` answers, relayed by the gateway, that events delivers a held bus event once it is enabled or started again within the retry window, and that the host's or the sandbox's nginx answers `/events` and `/declarations` 404 with the fragment included and passes `X-Event-Cause` and `X-Event-Depth` through. repos' side is proved at its own seams: the declaration it serves, the bus events it hands its sink, the retry window measured by an injected clock, and the fragment's text; a real nginx with the fragment included in a server holding a prefix location `/` and a regex location answered `GET`, `POST` and `PUT` of both paths 404 and passed `/events/`, `/eventsx` and other paths on.

## REQUIREMENTS

- R-Y0WW-GAO7: repos' design defines a request as carrying a **credential header** when it has exactly one `Authorization` header whose value is either `Basic ` followed by the standard base64 encoding (RFC 4648, with padding) of `<u>:<p>`, or `Bearer <p>`, where `<u>` and `<p>` are each at least 16 ASCII letters and digits, and every run of 8 consecutive characters of `<u>`, of `<p>`, and of the base64 value (the `Basic` form) holds at least one uppercase ASCII letter; defines that request's **secret strings** as every substring of 8 or more characters of `<p>`, of `<u>`, and of the base64 value; and requires that no secret string occur anywhere else in what the test sends to repos or has repos store — no other header, path, query or request body of any request in the same test, no tool argument, and no content, path, ref name, commit message or author of anything it pushes or places in a fixture; every requirement of repos' design that names a credential header or its secret strings MUST denote that.
- R-GTMI-EQAJ: When `Run` serves with a non-nil `Sink` requests carrying credential headers — each of `GET /`, `GET /about`, an MCP request to `/mcp` calling each of the tools `list`, `show`, `status`, `create`, `rename` and `delete`, and a clone, a fetch and a push by a real `git` through the git routes, sent once with a `Basic` credential header and once with a `Bearer` one — no event handed to that `Sink`'s `Deliver` MUST contain any secret string of any of those requests in its event name, its envelope request id or user, or the value of any of its attributes, a string attribute's text and the decimal form of a numeric attribute alike.
- R-S64N-K6TA: When `Run` serves requests that carry credential headers, as R-GTMI-EQAJ describes, and then stops, nothing `Run` writes to `Stderr` from its call to its return MUST contain any secret string of any of those requests, whatever the `Sink`'s `Deliver` returns, so that a `Sink` whose `Deliver` always returns an error leaves no secret string on `Stderr` either.
- R-EGA6-18BQ: When `Run` serves with a non-nil `EventSink` the requests R-GTMI-EQAJ describes, no bus event handed to that `EventSink`'s `Deliver` MUST contain any secret string of any of those requests in its event name, its `ID`, its envelope request id or user, its `Cause`, or the value of any of its attributes.
