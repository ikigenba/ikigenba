# D06-mcp

repos' MCP endpoint is its repositories offered to models: six tools, `list`, `show`, `status`, `create`, `rename` and `delete`, registered on the one `mcp.Server` the handler mounts at `/mcp`. This document is the endpoint part of `internal/tools`: it states what `Register` puts on a server, in that order; fixes what a client sees of each tool in `tools/list`, its name, the description written for a model, its input and output schemas and its annotations; fixes the two shapes every tool's answer takes, the success result and the refusal; and states, once for all six tools, how a call is answered when repos cannot reach its catalog or its repositories on disk. What each tool does when it can do its work is another document's: `list`, `show`, `create`, `rename` and `delete` are `D07-tools`, and `status` is `D09-limits`. Both use the shapes and the unreachable-store rule fixed here and restate neither.

## What is someone else's

Everything around the tools is appkit's or another document's, and this one restates none of it.

- appkit's `mcp` server (appkit `D07-mcp-server`) is the transport and the protocol: `/mcp` takes only POST, one JSON-RPC message per POST, one `application/json` body per answer, no session and no stream, whatever the request's `Accept` says (R-IHVY-KSVV, R-IKBR-CCD9, R-J3U5-GO8D); the 2026-07-28 envelope (`resultType`, `_meta`'s `serverInfo`, `ttlMs`, `cacheScope`; R-8J6S-YHCY, R-JDLC-IU5X, R-4AEH-0NQX); the earlier revisions `2025-11-25` and `2025-06-18`, `initialize` echoing or defaulting the revision, `notifications/initialized` answered 202, the same results without the 2026 members, and protocol errors answered 200 (R-INZG-HNLC, R-4CU9-S78B, R-J8PQ-ZR75, R-496K-MW08, R-IFG5-T9EH, R-8KEP-C93N, R-J1EC-P4QZ, R-8LML-Q0UC); the 405 with `Allow: POST` and an empty body for GET, DELETE and every other method (R-I395-ZJZJ); the `Origin`, `Content-Type`, size and header-mismatch checks (R-I4H2-DBQ8, R-I5OY-R3GX, R-I6WV-4V7M, R-IU2Y-EIAT); the unknown-tool protocol error, code `-32602` and message `Unknown tool: <name>`, 400 on the 2026 path and 200 on the earlier ones, with no tool run and no `tool.called` (R-JIGY-1X4P, R-J06G-BD0A, R-2WYQ-47FY); and `server/discover`'s and `initialize`'s `instructions`, read afresh from the services file for every request that asks, absent when the file is unset, unreadable or has no `repos` entry (R-JG15-ADNB, R-4AEH-0NQX, R-496K-MW08).
- appkit's `AddTool` and its schema rule (appkit `D08-mcp-tools`, `D09-mcp-schema`) are the Tool object's members and their order (R-BTJA-WZ53), the annotations each `Effect` gives (R-BZMS-TTUK), the derivation of the schemas from Go types (R-6MRV-S1RK, R-TZ75-CGOD, R-6RNH-B4QC), the strict reading of `arguments` against the input schema with its `invalid arguments:` text and the order of its lines (R-L31W-WW5H, R-BG4E-PHZG, R-BIK7-H1GU, R-MQSZ-NNHI), the success result built from a handler's output (R-LHOP-I51T), the `isError` result built from a handler's error (R-LIWL-VWSI), and the `tool.called` event recorded for every call that reaches a tool, with its `tool`, `kind`, `outcome` and `duration_us`, under the caller's request id and user, after whatever the handler recorded (R-2WYQ-47FY, R-2Y6M-HZ6N, R-2ZEI-VQXC, R-30MF-9IO1, R-31UB-NAEQ, R-JPSY-MGRS).
- The server is built by `main` with `web.ServiceName`, `cli.Version` and the writer `Run` builds, and `Instructions` nil, so a client's instructions are repos' description as the services file gives it (`D01-layout-and-run-seam`, which also proves the `serverInfo` and the instructions at the binary). The path `/mcp` exactly, the `not found` answer for a path beneath it, every method on `/mcp` reaching the server, `identity.Require` around it with its 500 `identity header missing` for a request without `X-User-Id` (appkit R-KHHE-4A9R, R-KBDW-7FKA), the request middleware and its `request.started` and `request.finished`, the clone address in each request's context, calling `Register` once with the handler's store, limits and writer, and what reaches stderr are `D03-serve`'s.
- The store, and what each of its methods returns after `Close`, is `D05-store`'s; the slots, queues and busy test are `D09-limits`'.

## What a client is told

Each tool is registered with `mcp.AddTool`, so its schemas are derived from Go types `internal/tools` keeps unexported; those types are not contract, the schemas they produce are, and they are stated here whole, property descriptions included, since a model reads them. The descriptions are the stories' word for word: a one-line summary a catalogue can show on its own, the line the landing page shows beside the tool's name, then a paragraph on how to call the tool. `list`, `show` and `status` change nothing and carry the annotations appkit gives `mcp.Read`; `create` adds a repository and changes or removes none, `mcp.Additive`; `rename` breaks every existing clone's remote URL and `delete` removes a repository for good, `mcp.Destructive`. That is what makes the gateway run the first three with `call` and the last three with `mutate`, and what `tool.called`'s `kind` says.

The arguments are plain strings marked required: `repo` for `show`, `rename` and `delete`, `name` for `create` and `rename`, with `repo` before `name`. So a missing one is appkit's `missing required field`, a `null` one is `expected string, got null` rather than read as absent, a member outside the schema is `unknown field`, and the lines come in schema order then sending order. Since appkit never calls a handler whose arguments it refused, no rule of repos is held to arguments that did not read cleanly. `list` and `status` take no arguments and their schema is the closed empty object.

Every output schema marks required each member that is always present, since appkit always writes a non-pointer field. No output property carries a description: the tool's description says what each member means, and the stories leave it open.

**`head` is absent, not `null`.** A repository with no commit on `main`, and an unavailable one, has no sha to give. A `null` would need the type `["string", "null"]`, and appkit's schema rule cannot express that: a pointer field's schema is its element's schema, a nil pointer is left out of the output, a required pointer in an output panics, and appkit writes no `null` (appkit R-TZ75-CGOD, R-6RNH-B4QC, R-6QFK-XCZN); a `RawTool` could write one but carries no `outputSchema`, which the stories require. So `head` is an optional string, `{"type":"string"}` and not required, and a result with no sha to give leaves it out. The descriptions of `list` and `show` say so, and the stories and `D07-tools`' results follow; a `null` would take an appkit release whose schema rule has a nullable form.

## What a call answers

A tool that can do what it was asked answers a **success result**: `structuredContent`, a JSON object, and one text block holding that object encoded compactly. A tool that cannot answers a **refusal**: `isError` true, no `structuredContent`, and one text block saying why. Both are defined below for every document that states a tool's answer.

Every tool answers from the catalog, and most from the disk, so a tool that cannot read or write them has nothing true to say. It never answers as if the caller had no repositories; whichever of the six tools was called, it refuses with exactly `cannot reach the repositories; try again later`, quoting nothing of the underlying error, and `tool.called` records the outcome `error`. That is the case whenever a store method the answer is made from returns an error that is neither of the store's verdicts, `store.ErrNotFound` (an unknown repository) and `store.ErrNameTaken`. A test produces it by closing the store after `Register` has it, after which every method fails so (R-NKSJ-VT7L), or, for a write that follows a read that succeeded, by removing the write permission of the directory holding the database, after which the store reads but cannot write (`D05-store`); the second is what catches a tool that ignores a failed write. The refusal takes precedence over every answer that would need the failed result, a success result and the `repo: no repository '<repo>'` and `name: '<name>' is already one of your repositories` offences included, so a tool never reports an answer it did not read. A call refused whatever the catalog holds is refused as its own document says even then: arguments refused as appkit reads them, and a `name` that breaks the naming rule. A refused `create`, `rename` or `delete` has changed nothing on disk or in the catalog, and records no `repo.*` event. The server keeps serving: `tools/list` reads nothing of the store and answers the same six tools after the store has closed.

Decisions recorded: `head` is absent rather than `null` (above). `rename` with a `name` that breaks the naming rule and a store that cannot be reached is refused with `invalid arguments:` and the naming line, not with the unreachable text; whether the refusal also carries a `repo` line is `D07-tools`'. No output property carries a description. Integers in the output (`size_bytes`, `limit_bytes`, `slots`, `active`, `queued`) are signed, `{"type":"integer"}`, with no `minimum`.

## Consumer tasks

The handler registers the tools once when it is built, `tools.Register(cfg.MCP, tools.Config{Store: cfg.Store, Limits: cfg.Limits, Telemetry: cfg.Telemetry})`, on the server `mcp.NewServer` returned for that writer, and mounts that server at `/mcp` (`D03-serve`).

A model, through the gateway's `call` or a client at `/mcp`, lists the six tools; reads its repositories with `list` and `{}`, gets a clone URL with `show` and `{"repo":"notes"}`, checks pressure with `status` and `{}`; through `mutate`, makes one with `create` and `{"name":"notes"}`, renames it with `rename` and `{"repo":"notes","name":"journal"}`, and removes it with `delete` and `{"repo":"journal"}`. A refusal's text tells it what to fix (`invalid arguments:` and one line per offence) or to try again later.

A test builds a store with `store.Open` over a temporary directory and a git from `git.Find`, limits with `limits.New(settings.Defaults(), limits.Clock{...})`, a writer with `telemetry.New` over a `*telemetry.Capture`, a server with `mcp.NewServer(mcp.ServerConfig{Name: web.ServiceName, Version: cli.Version, Telemetry: w})`, calls `tools.Register(srv, tools.Config{Store: s, Limits: l, Telemetry: w})`, and serves the server on loopback behind `identity.Require`, inside a handler that sets `clone.NewContext` for each request. It drives it with appkit's `mcp.Client`: `ListTools(ctx, caller)` for the six `mcp.ToolInfo`, whose `Name`, `Description`, `InputSchema`, `OutputSchema` and `Effect()` it asserts; `CallTool(ctx, caller, "rename", args)`, `args` being the bytes `{"name":5,"bogus":true}`, for a refusal it asserts through `Result.MarshalJSON`; and, after `s.Close()`, `CallTool(ctx, caller, "list", nil)` for the unreachable refusal and the `tool.called` with outcome `error` in the capture, then a second `store.Open` over the same paths to see that nothing changed. The earlier revisions and `server/discover`, which the client does not send, are appkit's to prove and `D01-layout-and-run-seam`'s at the binary.
