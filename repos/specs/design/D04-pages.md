# D04-pages

What repos' handler answers at its two pages and at the platform's shared files: the landing page at `/`, which tells a person what repos is, names the six tools an agent reaches it with and says how to clone with git without writing the token to disk; the about screen at `/about`, which shows its name, its version and its description; the refusal of any other method at either; the frame both are drawn in — the platform's banner and footer, the launcher when the host lists services with icons, and the auth links the banner carries; and the eight shared files under `/_appkit/` the pages load. `D01-layout-and-run-seam` declares the names this design behaves through — `web.Handler`, `web.Config` with its banner source and services path, `web.ServiceName`, `web.Description`, the root package's `Assets`, and `internal/clone`'s `Base`, `URL`, `Credentials` and `Guidance` — and `D03-serve` owns the rules the handler keeps on every route, these included: the route table, the identity gate, so a request without `X-User-Id` never reaches anything this design states; the trail, under which every request this design answers records its `request.started` and `request.finished` and nothing else; repos' 404 for every path that is not a route, `/assets/...` among them; that nothing reaches standard error while telemetry takes every event; and the rule that no response sets a cookie. Tests of this design carry `D03-serve`'s ids where they exercise those rules.

## The two pages

Both pages are the human-authored templates in `assets/`, `landing.html` (the template `landing`) and `about.html` (the template `about`), embedded by the root package. The handler builds **repos' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher` and `footer`; each template draws `banner` first in its body and `footer` last, both from the page's banner data. The code adds no template function and writes no markup of its own: the body of a `GET /` is exactly the output of `landing` for the request's **landing data**, and the body of a `GET /about` exactly the output of `about` for its **about data**, which a test can render itself and compare byte for byte. Each takes `GET` and `HEAD` — a `HEAD` is answered with the status and headers of the `GET` and no body — and refuses every other method with a 405 naming `GET, HEAD` and an empty body.

The landing data has the three members `landing.html`'s top comment names. `Banner` is the `page.Banner` the handler's banner source returns, called while the request is answered with the **banner user** — the caller's `X-User-Email` exactly as it arrived, auth's profile URL and auth's logout URL. `ReposURL` is `<repos-url>`, the address git reaches repos at, exactly what `clone.Base` returns for the request and `Config.ServicesPath`. `Credentials` is the credentials text split into its three non-empty lines, exactly what `clone.Guidance` returns for that address. Which address `Base` returns — the services file's `repos` entry less one trailing `/`, else the request's scheme and its `Host` whole — and what the five lines of the credentials text say are `D07-tools`' (the same text is the `credentials` member of what `show` and `create` return), and `clone.URL`, which joins the address and a name, is `D01-layout-and-run-seam`'s; this design states only which hooks carry those values. The page lists no repositories, whatever the caller holds, so serving it reads no catalog and no repository directory: the store may be failing and its directory gone and the page is the same.

The about data has two members: the same `Banner`, whose `Service` and `Version` the screen shows as the name and the version, and `Description`, the service's one-line description, which is `web.Description`, the manifest's description, so the screen says the same with or without a services file. In the binary the banner source is the `Banner` method of appkit's kit, which adds the service's name, repos' version and the launcher's services, read afresh from the host's services file; what the banner and the launcher draw from it — the mark, the profile link titled with the email, the sign-out form, the launcher's entries in the file's order, a switched-off service titled `<name> is unavailable`, repos' own entry marked current, the search field and the hidden no-match line — is appkit's contract (its D02 and D03), whether the binary names the version in its footer is `D01-layout-and-run-seam`'s exec test, and that the binary's banner source really is that kit — the launcher drawn from the services file, repos' own entry marked current — is proved by the same exec test against one requirement here, since `Process.Banner` is set by `main` and a nil one is not contract. A handler test uses a closure of its own, and the banner source is called exactly once per page, so every page is drawn from banner data fetched for that page.

Auth's two URLs come from the services file's entry named `auth` when it has one with a URL: that URL followed by `/` for the profile, and by `/logout` for sign-out. The file is the one at `Config.ServicesPath`, read afresh for every page through appkit's `services.Read`, and the **listed entries** are what it holds as the request is answered — nothing at all when it cannot be read, since a broken services file never breaks a page. Otherwise repos reads the space from the request's `Host`: a trailing `:` and port digits are dropped, then a single leading `repos.` label; auth is `auth.` and that space, under the request's scheme. The **scheme** is `X-Forwarded-Proto` when that header is exactly `http` or exactly `https`, and `https` for anything else, an absent or empty header included. There is no fixed fallback address. An entry named `auth` whose URL is empty is not usable, so it falls back the same way. Serving a page contacts no sibling: the only file it reads is the services file.

## Reading the page

The tests have no HTML parser — appkit and the SQLite driver are repos' module dependencies and neither carries one — so this design fixes the hooks the templates' top comments name and the visible text the stories quote, and defines how each is read with the standard library: start and end tags, attributes read left to right as a browser reads them, with a value or bare, an element's content, and normalisation (tags removed, character references unescaped, whitespace collapsed). Rules about the page's own markup are read over its **written markup**, the body with appkit's banner and footer taken out, because those are appkit's output. The hook requirements are stated for a **plain page request**, whose host, service names and auth and repos URLs carry nothing that escaping would change and whose banner's name and version carry no whitespace that collapsing would change; the byte-for-byte requirement covers every other request, so `html/template`'s contextual autoescaping is what keeps a caller's or the services file's bytes from becoming markup. A hook the template lacks is an issue for a human, never a change to the asset.

The landing page's hooks, from `landing.html`'s comment: an `h1` reading `repos`; the summary paragraph `p#summary` with the class `lede`; a section headed `MCP tools` holding the list `dl#tools` with the class `kv`, one `dt[data-tool=<name>]` per tool in the order `list`, `show`, `status`, `create`, `rename`, `delete`, each holding the tool's name in a `code` element and followed by a `dd` holding the first line of the tool's MCP description, which `D06-mcp` fixes for all six; `section#clone` headed `Clone with git`, holding `p#clone-url`, whose `code` element holds the clone address of a repository named `<name>`, `p#credentials-intro`, `code#git-helper` inside a `pre`, and `p#credentials-warning`, carrying the credentials text's first, third and fifth lines; and `a#about-link` leading to `/about`. The about screen's, from `about.html`'s: an `h1` reading `About repos`; the list `dl#about` with the class `kv`, holding `dt` `Name` then `dd#about-name`, `dt` `Version` then `dd#about-version`, and `dt` `Description` then `dd#about-description`; and `a#home-link` leading to `/`. Each page is titled — `repos` and `About repos` — links `/_appkit/theme.css` as its stylesheet, loads `/_appkit/feedback.js` with one deferred script in its head, declares the phone-width viewport, carries no script of its own and names no resource on another host; the service's name is lowercase `repos` everywhere, `Repos` appears nowhere in the page's own markup, and no page holds `IKIGENBA_TOKEN=` or any token: the byte-for-byte requirements leave a page no input but the request's `Host`, `X-Forwarded-Proto` and `X-User-Email`, the services file and the banner, and that no response, a page included, carries a credential the request held is `D11-on-a-space`'s (R-C1Z1-1DA5, R-Y24S-U2EW).

The feedback script is appkit's button-feedback script, served through repos like the stylesheet. The head is the template's, not appkit's: a page opts in to the feedback script by linking it, as it links the stylesheet, and the appkit banner does not load it. What the script does in a browser — an enabled button, the banner's `Sign out` among them, visibly reacting as the user presses it — is appkit's and needs a JavaScript engine the gates do not have, so what is fixed is the hook a standard-library test can see: the `script` start tag in the head, its `src` and its `defer`, which the template writes bare. That tag is the only `script` start tag the page's own markup carries, and its `src` names a path on repos' own host; the launcher's script, which also carries a `src`, sits in the appkit banner. A page carries no script of its own.

## The shared files

The stylesheet, its three fonts, the launcher's script, the button-feedback script and the two licences are the platform's shared files: appkit's `page` package embeds them and its `page.Static()` handler serves them under `page.StaticPrefix`, `/_appkit/`. repos holds no copy of any of them, reads nothing from disk to answer for them, and authors none; it passes every request whose path begins with `/_appkit/` (and that has an identity, `D03-serve`'s gate) to that handler unchanged, which compares the whole `URL.Path` against `/_appkit/<name>` itself, so no prefix is stripped. repos serves no favicon and nothing under `/assets/`; a path there is `D03-serve`'s 404. Delegation is one requirement; the requirements after it state what `S04` fixes about the answer, as repos' own observable behaviour, so that repos' tests fail if a different appkit release stopped giving it. They agree with appkit's published contract for `page.Static` (its D04), which fixes the same eight names, types, validators and refusals. Exactly eight paths name a file: `/_appkit/` followed by `theme.css`, `launcher.js`, `feedback.js`, `InterVariable.woff2`, `InterVariable-Italic.woff2`, `JetBrainsMono.woff2`, `OFL.txt` or `TABLER-LICENSE.txt`, compared byte for byte. Every 200 and 304 for one carries one strong `ETag` and one `Cache-Control: no-cache`; the tag's value is opaque here, and that different content yields a different tag is appkit's property, since repos embeds nothing of its own under `/_appkit/`. Revalidation is fixed only for a plain request, one carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`; several `If-None-Match` lines, a malformed list, `Last-Modified`, and `If-Modified-Since` without `If-None-Match` are not fixed by the stories and not fixed here.
