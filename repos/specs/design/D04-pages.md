# D04-pages

What repos' handler answers at its two pages and at the platform's shared files: the landing page at `/`, drawn from the address git reaches repos at and the credential guidance; the about screen at `/about`, which shows its name, its version and its description; the refusal of any other method at either; the frame both are drawn in — the platform's banner and footer, the launcher when the host lists services with icons, and the auth links the banner carries; and the shared files under `/_appkit/` the pages load. `D01-layout-and-run-seam` declares the names this design behaves through — `web.Handler`, `web.Config` with its banner source and services path, `web.ServiceName`, `web.Description`, the root package's `Assets`, and `internal/clone`'s `Base`, `URL`, `Credentials` and `Guidance` — and `D03-serve` owns the rules the handler keeps on every route, these included: the route table, the identity gate, so a request without `X-User-Id` never reaches anything this design states; the trail, under which every request this design answers records its `request.started` and `request.finished` and nothing else; repos' 404 for every path that is not a route, `/assets/...` among them; that nothing reaches standard error while telemetry takes every event; and the rule that no response sets a cookie. Tests of this design carry `D03-serve`'s ids where they exercise those rules.

## The two pages

Both pages are the human-authored templates in `assets/`, `landing.html` (the template `landing`) and `about.html` (the template `about`), embedded by the root package. The handler builds **repos' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; each template draws appkit's frame from the page's banner data. The code adds no template function and writes no markup of its own: the body of a `GET /` is exactly the output of `landing` for the request's **landing data**, and the body of a `GET /about` exactly the output of `about` for its **about data**, which a test can render itself and compare byte for byte. Each takes `GET` and `HEAD` — a `HEAD` is answered with the status and headers of the `GET` and no body — and refuses every other method with a 405 naming `GET, HEAD` and an empty body.

The landing data has the three members `landing.html`'s top comment names. `Banner` is the `page.Banner` the handler's banner source returns, called while the request is answered with the **banner user** — the caller's `X-User-Email` exactly as it arrived, auth's profile URL and auth's logout URL. `ReposURL` is `<repos-url>`, the address git reaches repos at, exactly what `clone.Base` returns for the request and `Config.ServicesPath`. `Credentials` is the credentials text split into its three non-empty lines, exactly what `clone.Guidance` returns for that address. Which address `Base` returns — the services file's `repos` entry less one trailing `/`, else the request's scheme and its `Host` whole — and what the credentials text holds are `D07-tools`' (the same text is the `credentials` member of what `show` and `create` return), and `clone.URL`, which joins the address and a name, is `D01-layout-and-run-seam`'s; this design states only that the page is drawn from those values. The page lists no repositories, whatever the caller holds, so serving it reads no catalog and no repository directory: the store may be failing and its directory gone and the page is the same.

The about data has two members: the same `Banner`, whose `Service` and `Version` the screen shows as the name and the version, and `Description`, the service's one-line description, which is `web.Description`, the manifest's description, so the screen says the same with or without a services file. In the binary the banner source is the `Banner` method of the kit `main` made with `page.New(ServiceName, v)`, `v` being the display string `main` reads (`D01-layout-and-run-seam`), which adds the service's name, that display string, empty when the host set no identity, and the launcher's services, read afresh from the host's services file. What the banner and the launcher draw from that value, and how, is appkit's contract (its D02 and D03); that the binary's footer carries the display string is `D01-layout-and-run-seam`'s exec test, and that the binary's banner source really is that kit, reading the file `IKIGENBA_SERVICES` names, is proved by the same exec test against one requirement here (R-UEA4-U7Z1), since `Process.Banner` is set by `main` and a nil one is not contract. A handler test uses a closure of its own, and the banner source is called exactly once per page, so every page is drawn from banner data fetched for that page.

Auth's two URLs come from the services file's entry named `auth` when it has one with a URL: that URL followed by `/` for the profile, and by `/logout` for sign-out. The file is the one at `Config.ServicesPath`, read afresh for every page through appkit's `services.Read`, and the **listed entries** are what it holds as the request is answered — nothing at all when it cannot be read, since a broken services file never breaks a page. Otherwise repos reads the space from the request's `Host`: a trailing `:` and port digits are dropped, then a single leading `repos.` label; auth is `auth.` and that space, under the request's scheme. The **scheme** is `X-Forwarded-Proto` when that header is exactly `http` or exactly `https`, and `https` for anything else, an absent or empty header included. There is no fixed fallback address. An entry named `auth` whose URL is empty is not usable, so it falls back the same way. Serving a page contacts no sibling: the only file it reads is the services file.

## How a page is proved

A page's words, markup and hooks are its template's alone: the templates live in `assets/`, and each one's opening comment names the data it receives and the hooks it draws for people and the stylesheet. This design names each template and the data it receives, and nothing of what it draws. A test proves a page by executing the named template of repos' template set with the data a requirement states and comparing byte for byte, or by checking that a value the test supplied appears in the body; `html/template`'s contextual autoescaping is what keeps a caller's or the services file's bytes from becoming markup. What a page loads from `/_appkit/` — the stylesheet, the font appkit's `preload` template preloads, the feedback script and the favicon — is its template's choice among appkit's files; what repos serves there is below. That no response, a page included, carries a credential the request held is `D11-on-a-space`'s (R-C1Z1-1DA5, R-VCFB-JSQH). A template that cannot show a state this design names is an issue for a human, never a change to the asset.

## The shared files

The stylesheet, its three fonts, the launcher's script, the button-feedback script, the favicon and the two licences are the platform's shared files: appkit's `page` package embeds them and its `page.Static()` handler serves them under `page.StaticPrefix`, `/_appkit/`. repos holds no copy of any of them, reads nothing from disk to answer for them, and authors none; it passes every request whose path begins with `/_appkit/` (and that has an identity, `D03-serve`'s gate) to that handler unchanged, which compares the whole `URL.Path` against `/_appkit/<name>` itself, so no prefix is stripped. repos serves no favicon of its own, nothing at `/favicon.ico` and nothing under `/assets/`; each is `D03-serve`'s 404, since a browser takes the page's icon from its head's link. Delegation is one requirement; the requirements after it state what repos guarantees about the answer, as its own observable behaviour, so that repos' tests fail if a different appkit release stopped giving it. They agree with appkit's published contract for `page.Static` (its D04), which fixes the same files, types, validators and refusals. Six paths name a file by a fixed name: `/_appkit/` followed by `theme.css`, `launcher.js`, `feedback.js`, `favicon.svg`, `OFL.txt` or `TABLER-LICENSE.txt`, compared byte for byte. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit are not served, and a font path with its hash taken out is a 404. repos never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads, and the paths the served stylesheet names, each a `url("…")` of a name ending in `.woff2` beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet repos serves. Every 200 and 304 for a served name carries one strong `ETag`. A font path's answer carries one `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again; every other served name's carries one `Cache-Control: no-cache`, so a browser keeps its copy but asks each time. The tag's value is opaque here, and that different content yields a different tag is appkit's property, since repos embeds nothing of its own under `/_appkit/`. Revalidation is fixed only for a plain request, one carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`; several `If-None-Match` lines, a malformed list, `Last-Modified`, and `If-Modified-Since` without `If-None-Match` are not fixed here.
