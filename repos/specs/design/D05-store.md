# D05-store

The store is the repositories. `internal/store` owns the rows of repos' one SQLite database, the catalog, and the directories under the repositories' root: it reaches the catalog through the handle appkit's `db` package opened, creates the root at start, rebuilds a missing catalog from the directories, verifies every catalogued repository before repos is ready, makes, renames and removes a repository in the catalog and on disk together, and answers the reads the tools, the git routes and maintenance are built on. `D01-layout-and-run-seam` declares `Config`, `Store`, `Open`, `Repo`, `ErrNotFound`, `ErrRoot`, `Verify`, `Find`, `List`, `All`, `Dir`, `Size`, `IDPrefix`, `ValidID` and `ValidName`, and fixes `Dir`, `ValidID` and `ValidName`, and declares the root package's `Migrations`; this document states what the rest do, fixes the schema those migrations make, and declares `ErrNameTaken`, `Create`, `Rename`, `Delete`, `Head` and `DefaultBranch`. `D07-tools`, `D08-git`, `D09-limits` and `D10-maintenance` use these names and declare none of their own against the catalog or the directories.

## One catalog, one writer, and the directories

The catalog is `state/repos.db` on a host and repos is its only writer. It is opened through appkit's `db` package: `cli.Run` calls `db.Open` with the path, the root package's `repos.Migrations()`, its clock, repos' service name and a writer for appkit's warning, and opens the store over the handle it gets back (`D03-serve`). What `db.Open` does — creating the missing parent directories, refusing a path or a database it cannot use, setting the journal mode, applying the migrations, and, over a database that records a version this binary does not carry, applying nothing, writing one warning line and opening it all the same — and what the handle's `Read`, `Write`, `Close` and `SetFailing` do is appkit's contract (its D15 and D16). This design restates none of it, and no test of repos proves it again or proves SQLite's own guarantees. The store reaches the catalog only through that handle.

The schema is one migration, `0001_catalog.sql`, which the root package embeds from `migrations/`: the table `repos`, one row per repository, holding its id (the primary key), its name, its owner, its created time as text in the layout `2006-01-02T15:04:05Z`, and its availability as the integer 1 or 0, with no two rows of one owner sharing a name — the table every earlier repos made. It is written `CREATE TABLE IF NOT EXISTS`, so on a catalog an earlier repos kept, which records no migration, it changes nothing and is recorded as applied, and every repository that catalog named is served as it was (R-UU8W-FALR); on a new file it makes the table. It seeds no row. The schema is contract as far as the schema test (R-Z99N-UALV, R-ZAHK-82CK) and the adoption of an earlier catalog need it; no sibling reads the database, and the host's replication copies it whole. A later change to it is a new migration file, never an edit of this one.

What an operator and a restart see is contract too: a repository a store holds when its handle is closed is the repository a store over the next handle holds, with the same id, name, owner, created time and availability; and a catalog lost entirely is rebuilt from the directories to the same ids, names, owners and created times. A test proves the catalog that way, by closing the handle and opening another, and by opening a store over a new catalog, never by reading rows; the schema test and the adoption test are the two that touch tables.

`Open` takes the handle, the root, the git, the clock and the random source. It creates the root when absent and refuses one it cannot use with `ErrRoot`, keeping the underlying error's text as its own, which `D03-serve` writes after the diagnostic's prefix. It rebuilds the catalog from the directories when the catalog is **unsettled**: it names no repository and no `Open` over it has yet succeeded (R-UJ9S-ZCXI). A catalog `db.Open` has just made, because `state/repos.db` was absent or of no bytes, is unsettled, so a lost catalog is rebuilt (`S14`); a catalog any `Open` has succeeded over stays settled, even once every repository in it is deleted, so a database that is present is the catalog, and a directory it does not name is left alone. The rebuild is one `Write`, and the store records in that same transaction that the catalog is settled; an `Open` of an unmarked catalog that needs no rebuild records the mark in one `Write` as its last step. Where it keeps the mark is its own, never a table, since the schema is the migrations'. So a start that fails or stops before it commits, or a process killed at any point before it, leaves the catalog unsettled, and the next start rebuilds it, as `S14` says of an interrupted first start. An earlier repos' catalog naming at least one repository is settled by its first successful `Open`; one naming none is, like a new one, rebuilt from the directories, which differ from it only by an entry an earlier rebuild left uncatalogued.

A catalog that cannot be reached mid-operation is made, in a test, with the handle's `SetFailing(true)`: from then until `SetFailing(false)`, and from the handle's `Close`, the store is **failing**, and every method answers with an error that is neither of the store's verdicts and changes nothing (R-Z6TV-2R4H). It is the one way the store's, the tools' and the git routes' tests make the catalog unreachable; under WAL a directory's permissions no longer are. A permission removed from the root or a repository's directory still fails git's own writes, which is how a failed directory step is produced. A permission binds only an ordinary user, and the gates run as one (`AGENTS.md`).

Every directory is the bare repository `Dir(id)`, `state/repos/<id>.git`. Siblings read it with their own git (`S15`): its `HEAD` names `refs/heads/main`, its `config` file holds the four `ikigenba.*` values, and its name never changes, because a rename writes only `ikigenba.name`. That a reader running while a push lands sees the repository before or after it is git's guarantee for any bare repository, not repos'. Nothing but repos writes under the root; the store never changes a directory the catalog does not name.

## Creating, renaming and deleting

`Create` mints the id from `Config.Rand`, eight bytes at a time, written as 16 lowercase hexadecimal digits after `IDPrefix`, so a test that hands in known bytes knows the id in advance; an id already catalogued, or whose directory path already holds an entry, is drawn again. The created time is `Config.Now` in UTC, truncated to the second, the precision the tools answer it in. git makes the directory as an empty bare repository whose `HEAD` names `refs/heads/main`, with sha-1 objects so every sha is the 40 hexadecimal digits the stories show, and with nothing from git's template directory, so a host's templates never put a hook into a repository repos serves (git-init(1), "TEMPLATE DIRECTORY": `--template` takes precedence over `GIT_TEMPLATE_DIR` and `init.templateDir`; a probe confirmed an empty `--template=` copies nothing even with `GIT_TEMPLATE_DIR` naming a directory holding `hooks/post-receive`). Its `config` then gains `pack.windowMemory` `64m`, `pack.threads` `1` and `core.bigFileThreshold` `16m`, which bound the memory of packing (git-config(1)), and the four identity values in the order `id`, `name`, `owner`, `created`, which is the order `git config --get-regexp '^ikigenba\.'` prints them in (`S15`; a probe confirmed `git config --file` appends a new key to its section and `--get-regexp` lists in file order). A create that fails at any step leaves neither a row nor a directory.

Each mutation keeps its row and its directory together on the handle's one writer: its directory step runs inside the `Write` that changes its row, and the transaction commits only once that step has succeeded. A step that fails ends the function with an error, so nothing of the row is kept; a commit that fails after the step has the step undone before the call returns. `Write` queues every mutation behind the one before it, so two creates of one name end with one repository, and `Verify` records availability through `Write` too. Reads go through `Read`. The store keeps no lock of its own beside the handle. How a step is undone is the store's own; what the requirements fix is the outcome, both or neither.

`Rename` changes the row's name and the directory's `ikigenba.name` together, or neither: a probe confirmed `git config --file <config> ikigenba.name <new>` rewrites that one line and leaves every other byte of the file as it was. An unavailable repository's directory is not written. `Delete` removes the directory, or whatever entry is at its path, and the row together; a delete that fails leaves both as they were.

A name is unique per owner. `ErrNameTaken` is a create or rename onto a name the owner already uses; two creates of one name racing each other end with one repository. `ValidName` and `ValidID` are `D01-layout-and-run-seam`'s; the store refuses a name `ValidName` refuses, though `D07-tools` refuses it first.

## Reads

`Find` resolves a caller's `ref` among that owner's repositories only, as an id when it begins `rep_` and as a name otherwise; another owner's repository, and a ref that could name nothing, are `ErrNotFound`. `List` is one owner's repositories by name, `All` every repository by id. `Head` is the sha the ref named exactly `refs/heads/main` points at, as `git rev-parse --verify -q refs/heads/main` reads it (git-rev-parse(1), `--verify`, `-q`; a probe confirmed exit 1 and no output for an empty repository and for one holding only `refs/heads/main/x`, which `for-each-ref refs/heads/main` would wrongly match, and the sha for a loose or packed `main`), empty for a repository with no commit on `main`; for an unavailable repository it is empty without the directory being read, since verification found it unreadable, and for an available repository whose directory is no longer sound it is empty too, the soundness check deciding and not git's exit status, since `rev-parse --verify` still prints the sha from a directory without `config` or with an unlistable `objects/` or `refs/`: a probe showed `git rev-parse` exits 128 with `fatal: not a git repository` both for a missing directory and for one whose `HEAD` is gone, and a `Head` that failed there would turn one damaged repository into a failed listing. `Size` is the sum of the lengths of the regular files in the directory, the measure every size in repos uses (`size_bytes`, `REPO_MAX_BYTES` in `D09-limits`, `size_before` and `size_after` in `D10-maintenance`). Apparent lengths, not allocated blocks, keep it the same on every filesystem, so a test computes the expected value by walking the directory itself. A file `Size` cannot read counts nothing rather than failing, so one broken repository never fails a whole listing; `Size` is 0 when nothing is at the path.

The tools, the git routes and maintenance tell an unreachable store from everything else by the error alone: `ErrNotFound` and `ErrNameTaken` are answers about the repositories, and any other error from a method means the catalog or the disk could not be reached (`D06-mcp`). A failing store answers every method with such an error.

## Verification and rebuild

`Verify` runs once per start, after `Open` and before repos is ready (`D03-serve`). It asks git whether each catalogued repository's directory opens as a bare repository, which is what git checks before it runs any command in one, and records the answer as the repository's availability. A probe of `git --git-dir=<dir> rev-parse --is-bare-repository` showed it prints `true` for a sound bare repository, prints `false` when `config` is gone, and fails with `not a git repository` when the directory is missing, empty, or lacks `HEAD`, `objects/` or `refs/`, or when any of these has its permissions removed; a regular file at the path fails too. That probe also showed `--is-bare-repository` still prints `true` when `objects/` or `refs/` keeps its execute permission but loses its read permission (mode `0300`), so soundness also asks that both directories can be listed. Damage deep in the object store is not this check's to find. Each repository found unsound gets one `repo.unavailable`, with no request id and no user. Verification only reads, so the directory a repairer finds is exactly what was there, and a repository repaired while repos was stopped is available again on the next start.

A catalog is rebuilt when `Open` finds it unsettled: new, because the start found no file at `state/repos.db` or a file of no bytes, or left so by a start that never finished. An entry of the root becomes a row when it is **identified**: its name is a valid id followed by `.git`, it is a directory and not a symbolic link (a link is left alone, uncatalogued and unreported, since a directory elsewhere is not one repos keeps), and its `config` gives, as `git config --file <dir>/config --get` reads each key (the last value when a key repeats, git-config(1), `--get`), an `ikigenba.id` equal to that id, a valid `ikigenba.name`, a non-empty `ikigenba.owner`, and an `ikigenba.created` in exactly the form `Create` writes. A directory whose `HEAD` or `objects/` is gone but whose config still names its owner is identified: guessing is what the rule forbids, and its config is no guess, so it is catalogued and then found unavailable by verification, where its owner can see it and delete it. Anything else is left alone, uncatalogued and unreported, since it names no repository. Two identified directories claiming one owner and name cannot both be catalogued: the one created earliest is, the smaller id breaking a tie, and each other is left on disk untouched, uncatalogued, and reported with `repo.unavailable` by the first `Verify` of that `*Store`, so the operator learns of it before `service.started`. A rebuild records no `repo.created`. Once a catalog exists, a directory it does not name is left alone, neither served nor removed.

## Decisions

- Rebuild duplicates: earliest `ikigenba.created`, then smaller id, is catalogued; the rest are reported once with `repo.unavailable` on the start that rebuilt, and never again, since later starts find a catalog.
- Rebuild catalogues any identified directory, broken or not, and lets verification decide availability; an `ikigenba.created` not in the form `Create` writes, or an invalid name, makes a directory unidentified.
- A zero-length database file counts as absent, so it is rebuilt; a start that never finished its rebuild leaves the catalog unsettled, and the next one rebuilds.
- The baseline migration is the earlier repos' table, `CREATE TABLE IF NOT EXISTS`, so an earlier catalog is adopted with nothing changed.
- `Size` is apparent bytes of regular files. A rename changes `size_bytes` by the difference in the names' lengths, since `ikigenba.name` lives in the directory.
- `Head` of an unavailable repository is empty and reads nothing, and of an available one whose directory is no longer sound is empty with no error; `Size` of one is what its directory holds.
- A symbolic link named `<id>.git` in the root is never identified on a rebuild: left alone, uncatalogued, unreported.

## Consumer tasks

`cli.Run` opens the catalog with `d, err := db.Open(ctx, db.Config{Path: filepath.Join(dir, "state", "repos.db"), Migrations: repos.Migrations(), Now: p.Now})`, then the store with `s, err := store.Open(ctx, d, store.Config{Root: filepath.Join(dir, "state", "repos"), Git: g, Now: p.Now, Rand: p.Rand})`, tells `errors.Is(err, store.ErrRoot)` from every other failure and writes `D03-serve`'s diagnostic with `err.Error()` as the reason, builds the writer, calls `s.Verify(ctx, w)` before `Writer.Ready`, hands `s` to `web.Config.Store`, and calls `d.Close()` after the drain.

The tools (`D07-tools`): `list` is `s.List(ctx, caller)` and, per repository, `s.Size(ctx, r.ID)` and `s.Head(ctx, r.ID)`; `show` is `s.Find(ctx, caller, ref)` then the same two, with `store.DefaultBranch` as `default_branch`; `create` is `s.Create(ctx, caller, name)`, `ErrNameTaken` becoming the name's reason line; `rename` is `s.Find` then `s.Rename(ctx, r.ID, name)`; `delete` is `s.Find`, `Limits.TryHold(r.ID)`, then `s.Delete(ctx, r.ID)`. `ErrNotFound` from `Find` is the `repo:` reason line; any error that is neither sentinel is `D06-mcp`'s unreachable-store refusal.

The git routes (`D08-git`): `s.Find(ctx, caller, name)` resolves `/<name>.git/`, `r.Available` false answers `503`, and `s.Dir(r.ID)` is the project path `git http-backend` is given; `D09-limits` compares `s.Size(ctx, r.ID)` with `REPO_MAX_BYTES`. Maintenance (`D10-maintenance`): `s.All(ctx)`, skipping a repository whose `Available` is false, with `s.Size` before and after `git gc` in `s.Dir(r.ID)`.

A test opens a catalog with `db.Open` at a path in a temporary directory, with `repos.Migrations()` and a clock it fixes, and a store over it with a root beside it, a git found by `git.Find` over its own git environment, a `Now` it sets and a `Rand` of known bytes; it creates with `s.Create(ctx, "u_1", "notes")`, reads the directory back with its own `git config --file`, `git symbolic-ref` and `git for-each-ref`, pushes a commit with fixed dates through its own git and reads `s.Head`, and compares `s.Size` with its own walk of the directory. It removes a directory's `HEAD`, closes the handle, opens another handle and a store over it, and calls `s.Verify(ctx, w)` over a writer on a `*telemetry.Capture`; it opens a store over a new catalog to see a rebuild, and over one whose every repository was deleted to see none; it makes the catalog fail with `SetFailing(true)` on the handle, and a directory step fail by removing a write permission from the root or a repository's directory; and it breaks the root by putting a regular file where it goes. For the schema it opens a new catalog and reads `sqlite_master` and the two pragmas. For the adoption it makes an earlier repos' catalog in its stored form: a `db.Open` with an empty set of migrations, then, through `Write`, the table by R-UU8W-FALR's statement, its rows, and `DROP TABLE schema_migrations`; it closes that handle and opens the file with `repos.Migrations()`.
