# D10-maintenance

Every push leaves loose objects and small packs behind, and a forced push or a deleted branch leaves commits nothing reaches, so repos collects each repository with git's own garbage collection on a schedule. This document is `internal/maintenance`: when a cycle runs, what one cycle does to each repository, how a repository's maintenance competes with pushes for the same write slots and lock, what it records, and how it ends at a stop. Its exported surface, `maintenance.Config`, `Scheduler`, `Start`, `(*Scheduler).Stop` and `Cycle`, is declared in `D01-layout-and-run-seam` (R-F0W3-YBFK); this document only states what they do. The slots, queues, lock and deadlines themselves are `D09-limits`' (`Limits.Acquire` and its `Grant`); maintenance is one more caller of them, with the operation `maintenance` and the repository's lock.

## The schedule

`maintenance.Start` starts a schedule and returns at once. The interval is `MAINTENANCE_HOURS` hours, read from the `Settings` of the `Limits` in the config, turned into a duration that saturates rather than wraps. The schedule's every wait is a channel from the `Limits`' `Clock.After`, so a test that hands repos its own `After` sees the interval asked for and fires it when it chooses; nothing waits real time. The first cycle is due one interval after `Start`, not at it, so a restart never sets off a burst of work. As each cycle begins the schedule asks for the next interval, so the next cycle is due one interval after this one began; if this cycle runs longer, the next begins as soon as it ends. One schedule never runs two cycles at once.

`maintenance.Cycle` runs one cycle at once and returns when it is done. It is how a test runs a cycle without the schedule, and every cycle the schedule runs behaves the same way.

## One cycle

A cycle lists the repositories (`Store.All`) as it begins and takes the available ones one at a time, in no fixed order; it begins waiting for the next only once the one before has ended. An unavailable repository (`Repo.Available` false, `D05-store`) has no directory git can open, so the cycle passes it by: no wait, no git, no event.

Maintaining a repository is a write like a push. It asks `cfg.Limits` for a write slot and the repository's write lock together, through `Acquire` with `limits.Maintenance` and the lock, so it waits for them exactly as a push to that repository would, is counted among the writes waiting, never runs beside a push to the same repository, and makes a push that comes after it wait. Reads take no lock, so a clone of the repository goes on while it is maintained. The sync points tests rely on follow from `D09-limits`' `Acquire`: the maintenance is counted in `Pressure().Write.Queued` before `After` is called for its queue wait, and in `Pressure().Write.Active`, its repository busy, before `Hold` is called.

When `Acquire` refuses, the repository is skipped this cycle and tried again next cycle, and the cycle goes on: a full writes' queue records `operation.rejected` with `limit` `queue_length`, a wait past `QUEUE_SECONDS` records it with `queue_seconds`. A stop is different: a maintenance waiting when the stop comes is given up with `limit` `draining`, and the cycle ends there, recording nothing for the repositories it had not reached; they are maintained in the next start's first cycle. Before each repository the cycle asks `Limits.Draining` (`D09-limits`), so a repository reached after `Drain` is passed by in silence. Should `Drain` land between that check and the `Acquire` call, the `ErrDraining` that comes back at once may be recorded as `draining` or passed over; no requirement decides that instant.

A repository deleted while its maintenance waited is gone by the time the grant comes: delete refuses a busy repository, waiting is not busy, and a maintenance waiting behind a delete's `TryHold` hold is granted only once that hold ends, after the directory is gone. Its maintenance then releases the grant, runs no git, calls no `Hold`, and records nothing; there is nothing to skip next cycle. Once the lookup finds the repository, a maintenance that waited (its grant's `Waited` above zero) records `operation.waited` with `wait_us` its wait in whole microseconds; one whose lookup fails records none. A store that fails mid-cycle (`Store.Size`, or the `Store.Find` by owner and id that follows the grant, failing other than with not-found) costs that repository its run: no `maintenance.finished`, the grant released, the cycle on to the next. Then `Hold`, the test hook, is called with the repository's id, while the slot and the lock are held and before git starts; maintenance starts no git until `Hold` returns. `Run` leaves `Hold` nil. A test that sets it holds a maintenance in flight for as long as it likes: that is how `status` showing a repository busy under maintenance, `delete` refused under maintenance, a clone or a push meeting a maintenance, and a stop during maintenance are driven.

## The git it runs

Maintenance runs `git gc` in the repository's directory as the command `git.Git`'s `Command` builds (`D08-git`), whose context ends the git and every process it started when the maintenance ends, and with its output discarded, with git's own defaults and nothing more: no `--aggressive`, no `--prune` of its own. git-gc(1) documents what that does: it packs the repository's reachable objects, packs its refs, and prunes unreachable loose objects older than its default expiry ("`--prune=<date>`: Prune loose objects older than date (default is 2 weeks ago, overridable by the config variable gc.pruneExpire)"); since `gc.cruftPacks` defaults to true, unreachable objects too recent to prune go into a cruft pack rather than staying loose. It changes no ref, and a bare repository keeps no reflog by default (git-config(1), `core.logAllRefUpdates`), so a commit a forced push left behind is unreachable and, once old enough, goes. A probe with the host's git confirmed the outcomes the requirements below state: a bare repository holding only loose objects from pushes, all reachable, reads `count: 0` and `packs: 1` in `git count-objects -v` after `git gc` (an empty repository reads `packs: 0`, so the requirement asks for at least one ref); a loose unreachable object whose modification time is long past is gone; one written just now stays readable (in a second, cruft, pack, so that repository then reads `packs: 2`).

The run is bounded like any other git operation: the grant's operation deadline (`OPERATION_SECONDS`, `D09-limits`) is asked for when git starts, and when it delivers before git has ended — been waited for — git is killed and waited for and only then judged, by the one rule `D09-limits` defines for every git repos runs: a run whose git ended by itself, exiting with status 0, finished, and records `maintenance.finished` as though the deadline had not fired; anything else is recorded as `operation.timed_out`. A `git gc` that exited with status 0 just before its deadline delivered is therefore not a timeout, though no client would ever have seen the difference; the trail would. One that failed by itself, with another status, in the instant before it was waited for while its deadline delivered is recorded as timed out, the cost `D09-limits` accepts. git's collection replaces packs only once their successors are complete and never touches a ref, so a run killed at any moment leaves the repository whole.

## What it records

Maintenance is not a request and has no caller: every event it records carries an empty request id and an empty user. A repository whose git ran to a successful end records `maintenance.finished` with its id, `duration_us`, the whole microseconds git ran by the `Limits`' clock, and `size_before` and `size_after`, the repository's size (`Store.Size`) measured just before git started and just after it ended. A run that was killed, or whose git failed, records no `maintenance.finished`, and the cycle goes on. The closed list of events in `D01-layout-and-run-seam` has no event for a git that failed, so such a run is silent; the next cycle tries again. Maintenance has no output stream: `maintenance.Config` carries none, and git's own output is discarded. The only lines a maintenance can cause on stderr are the writer's `undelivered event` lines for its events (`D03-serve`). How `Run` wires the schedule (the `Limits` built over `Process.Now` and `Process.After`, `Start` before the first connection, `Stop` at the signal) is `D03-serve`'s.

## Stopping

`Scheduler.Stop` is the stop. At the signal `D03-serve` has `Run` call `Limits.Drain` at once, so waiting git requests are refused without delay (R-QB1G-NV5S), and stop the schedule alongside it, with the drain deadline as `Stop`'s context (R-A0M3-5EBH). This document's requirements hold whichever of `Drain` and `Stop` comes first. From the stop on, no cycle begins and no repository's maintenance begins waiting. A maintenance waiting for its slot or lock when the stop comes — `Limits.Drain` refusing its `Acquire`, or `Stop` called while it waits — is given up with `operation.rejected` `draining`. A maintenance in flight runs to its end, `maintenance.finished` and all, if it ends before the deadline; `Stop` returns once it has. At the deadline, `Hold`'s context is cancelled, and the maintenance in flight ends recording nothing at all (no `maintenance.finished`, no `operation.timed_out`): its git, if started, is killed with every process it started, and if not, never starts. It is not a request, so it is not among the requests `D03-serve` counts as unfinished. `Cycle`'s context plays both parts at once for a cycle run without a schedule: when it ends, nothing more begins, a waiting maintenance is given up with `draining`, and the one in flight ends as at a deadline.

Drain during maintenance is proved at this seam, not through `cli.Run`: a test starts a schedule with a `Hold` that blocks, fires the interval, waits for `Hold` to be called, calls `Limits.Drain` (after which `Draining` is true, so no race decides what happens next), calls `Stop` in a goroutine with a context of its own, and either lets `Hold` return (the maintenance finishes; no other repository is touched) or cancels the context (`Hold`'s context is done; no `maintenance.finished`).

## Consumer tasks

`Run` builds `limits.New(s, limits.Clock{Now: p.Now, After: p.After})`, then `sched := maintenance.Start(maintenance.Config{Store: st, Git: g, Limits: lim, Telemetry: w})`; on the signal it calls `lim.Drain()` at once and `sched.Stop(drainCtx)` alongside it (`Stop` waits for a maintenance in flight), as `D03-serve` fixes.

A test of the schedule builds a store over a temporary directory with two repositories pushed to by real git, a `*telemetry.Capture`-backed writer, and `limits.New` with a `Clock` whose `Now` reads a time the test sets and whose `After` records each duration it is asked for and hands back a channel the test fires. After `maintenance.Start(cfg)` returns, the test finds one recorded duration of one hour (`MAINTENANCE_HOURS=1`) and no event; it fires that channel, sees a second one-hour request (the next cycle is due an hour after this one began), follows the cycle through a `Hold` that reports each id it is called with, and finally finds one `maintenance.finished` per repository and `git count-objects -v` reading `count: 0` and `packs: 1` in each directory. A test of the late deadline lets a cycle's `git gc` end by itself and only then fires its deadline: it asks for nothing new, since the deadline is the channel its own `After` returned for `OPERATION_SECONDS` once `Hold` returned (R-GZR4-5WN3), and it learns that `git gc` has exited with status 0 and been waited for from its `trace2.eventTarget` file and `kill(pid, 0)`, as `D09-limits` describes; it finds `maintenance.finished` and no `operation.timed_out`, on every run of `go test -count=100 -cpu=1`. A test of contention holds a repository's lock with `lim.Acquire(ctx, id, limits.Push, true)`, calls `maintenance.Cycle(ctx, cfg)` in a goroutine, sees the maintenance's queue-wait `After` request, advances `Now`, and either releases the grant (`operation.waited`, since `Now` moved while it waited, then `maintenance.finished`) or fires the queue-wait channel (`operation.rejected` `queue_seconds`, and the other repository still maintained).
