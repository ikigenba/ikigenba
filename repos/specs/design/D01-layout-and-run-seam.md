# D01-layout-and-run-seam

repos is the suite's home for git repositories: one Go binary that serves each of a user's repositories over git's smart HTTP at `/<name>.git/` by running the host's own `git http-backend`, offers six MCP tools at `/mcp` (`list`, `show`, `status`, `create`, `rename`, `delete`), keeps every repository as a bare git repository on disk under `state/repos/`, catalogued in its own SQLite database, `state/repos.db`, tidies each one on a schedule with git's own collection, tells the suite's event bus of every ref a push moves, and serves a landing page at `/` and an about screen at `/about`. This design is the structural ground the other designs stand on: where the code lives, which package exports which name, the seam through which the process is run so that the command, the server, the pages, the store, the git routes, the limits, the maintenance schedule and the tools can be tested without a real process, the seams through which the handler and its parts are built, the settings and how they are read, the paths, where the version it shows comes from, the vocabulary every later design uses, and the events repos records and emits.

The module is `github.com/ikigenba/ikigenba/repos`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/repos`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/repos` is wiring only.

## The dependencies

repos depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required at a published release through the ordinary module proxy and checksum database, like any other module, with no `replace` directive pointing into the repository, whose `db` package brings `modernc.org/sqlite`, the pure-Go SQLite driver, which keeps the release build cgo-free; repos imports no driver of its own. Which release of appkit is data that `AGENTS.md` and `go.mod` hold; no requirement names one. It also runs one program, the host's `git`, which `AGENTS.md` declares in the toolchain and opsctl provisions on a host; repos links no git library.

appkit is a sibling reached only through its published packages. repos uses eight of them. `db` opens the catalog, brings it up to date with repos' migrations, runs every read and write of it, and prints `db status` (its D15 and D16). `services` reads the services file (for the `repos` entry every clone address is built from). `page` gives the banner, the launcher, the footer and the font preload, the template set the two pages are parsed into, and the shared static files under `page.StaticPrefix`. `identity` gives `identity.Require`, which wraps every route but the event bus's two, so nothing — the pages, `/mcp`, the git routes — is reached without an `X-User-Id`. `mcp` gives the server mounted at `/mcp` and the client the tests drive it with. `telemetry` gives the event, the request middleware (whose `request.finished` carries the request's and the response's body byte counts), the writer, the socket sink that finds the telemetry service through the services file, and the capturing sink the tests use. `events` gives the emitter that sends a bus event to the event bus, the `events` app, holding it and retrying while the bus is away and dropping it with an `event.lost` in the trail and a line on standard error when it stays away too long; the middleware that reads an event's cause from `X-Event-Cause` and `X-Event-Depth`; the two handlers the events app reaches every service at, `/events` and `/declarations`; the socket sink that finds the events app through the services file; and the capturing sink the tests use. `version` gives the code identity the host hands every app: `version.Display()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment at the time of the call and returns the **display string** built from them, `r142 (c604e32)`, the short commit alone, the label alone, or the empty string when neither is set. repos carries no version of its own: nothing in its source or its build names one. appkit owns all of their contracts; repos restates none.

## Where the environment is read

`version.Display` reads `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` from the real process environment, and `main` calls it exactly once, first, and holds the result `v`: that value is the version repos shows everywhere it shows one, and the one it hands `page.New`, the server maker and `Run`. So one start reads the two variables once, and `--version`, which is a run of its own, reads them once too. Nothing below `main` calls `version.Display`; `Run` receives the string as `Process.Version`, writes it for `--version` (`D02-cli`) and gives it to the writer it builds as the writer's `Version`, so `service.started` carries it (`D03-serve`); an in-process test hands it any string it likes, the empty string included, and sets no variable. This is the one shape every app copies: one call in `main`, its result passed down. That `main` hands appkit and `Run` that string is wiring, proved by the one exec'ing test of `AGENTS.md`: it composes non-empty `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` into the child's environment and computes the string it expects by calling `version.Display` itself after setting the same two values with `testing.T.Setenv`, so the expectation rests on appkit's promise and no test spells a version; it also runs `--version` with neither variable in the child's environment and expects one empty line.

As in telemetry, `page.New` and `mcp.NewServer` read `IKIGENBA_SERVICES` from the real environment when they are called, so `main` calls `page.New` once, with `v`, and puts in `Process.MCP` a function that calls `mcp.NewServer` over the writer `Run` builds, with `v` as its `Version`, with `Instructions` nil so that a client's instructions are repos' description read afresh from the services file. `Run` looks `IKIGENBA_SERVICES` up through `LookupEnv`, once, when it starts to serve, and hands the value on as the services path the handler reads afresh for the banner's auth links and for the `repos` entry every clone URL is built from. The third and fourth readers are appkit's two socket sinks, telemetry's and the event bus's, which read the variable from the real environment on every delivery; they are what a nil `Process.Sink` and a nil `Process.EventSink` mean, so they are used only by the binary, and a test of `Run` names its own sinks. None of these reads can fail a start.

The git repos runs takes its environment from the seam too. `Process.Environ` is the whole environment every git process is started with, and `PATH` from `LookupEnv` is where the executable named `git` is looked for, in the order of its entries as a shell looks, except that an empty or relative entry is skipped, so repos never runs a `git` it finds through its working directory. A test therefore composes the git environment `AGENTS.md` asks for (its own `HOME`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL`, `GIT_TERMINAL_PROMPT=0`, a `PATH` holding git's directory) and hands it to `Run` without touching the real environment. git documents that it honours these variables (git(1), "ENVIRONMENT": `GIT_CONFIG_GLOBAL` replaces `$HOME/.gitconfig` and `$XDG_CONFIG_HOME/git/config`, `GIT_CONFIG_NOSYSTEM` skips the system file), which is what makes a test's git independent of the developer's.

## Packages

The module's root package, `repos`, holds what the module embeds: it exports `Assets`, a function returning a file system holding exactly `landing.html` and `about.html` from `assets/`, which `internal/web` parses into the set `page.Templates()` returns; `Etc`, a function returning a file system holding exactly `manifest.toml` and `nginx.conf` from `etc/`, through which a test proves that the two files the build writes are the constants' copies (`D02-cli`); and `Migrations`, a function returning a file system holding exactly the catalog's one migration, `0001_catalog.sql`, from `migrations/`, at its root as appkit's `db.Config.Migrations` wants it (`D05-store`). Nothing else lives at the root. Because the root package's name is `repos`, a file that imports it beside nothing else of that name needs no alias.

Eleven internal packages hold the concerns, each one concern.

- `internal/cli` owns the program as a command: the manifest and nginx fragment constants and the usage text (`D02-cli`), the exit codes, the run seam, `db status` (`D02-cli`), and the serve path (`D03-serve`): reading the settings, taking the socket, finding git, opening the catalog and the store, verifying, building the writer, the emitter, the limits, the maintenance schedule and the handler, readiness, and the stop.
- `internal/server` owns the listener's life and nothing else, exactly as telemetry's: it serves a handler on a listener and drains for a deadline (`D03-serve`).
- `internal/settings` owns the nine numbers repos reads from its environment, their defaults, how each is spelled, and the refusal of one that is not acceptable (this document).
- `internal/web` owns the HTTP surface: the one handler, the route table, identity, the request middleware and the event bus's cause middleware, the landing page and the about screen (`D04-pages`), the shared static files, the mounting of the MCP server at `/mcp`, of the git routes and of the event bus's two paths (`D03-serve`).
- `internal/store` owns the repositories: the catalog's rows, reached through the handle appkit's `db` gives it, each repository's directory and the `ikigenba.*` configuration it carries, startup verification, the rebuild of a missing catalog from disk, and the layout siblings read (`D05-store`).
- `internal/git` owns running the host's git: finding the executable, the environment every git runs with, running a git command, and the bridge to `git http-backend` with its fixed buffers (`D08-git`).
- `internal/smarthttp` owns the git routes, `/<name>.git/...`: resolving the name, refusing what is not git's smart protocol, streaming each request through `git http-backend`, and the one event repos emits to the bus, whose declaration it exports (`D08-git`), under the limits (`D09-limits`).
- `internal/limits` owns slots, queues, the per-repository write lock, the queue and operation deadlines, the size checks, draining at a stop, and the pressure the `status` tool reports (`D09-limits`).
- `internal/maintenance` owns the scheduled collection of every repository (`D10-maintenance`).
- `internal/tools` owns the six MCP tools: their names, descriptions, schemas, effects, results and refusals (`D06-mcp`, `D07-tools`; `status` is `D09-limits`').
- `internal/clone` owns the clone address and the credential guidance text, which the landing page and the tools `create` and `show` share (`D07-tools`).

Dependencies point one way: `cmd/repos` imports `internal/cli`, `internal/web` and appkit; `internal/cli` imports everything below it; `internal/web` imports the root package, `store`, `git`, `limits`, `smarthttp`, `tools` and `clone`; `smarthttp` and `maintenance` import `store`, `git` and `limits`; `tools` imports `store`, `limits` and `clone`; `store` imports `git`; `limits` imports `settings`; `git`, `settings` and `clone` import nothing of repos'. Which package imports which is not observable, so this paragraph is guidance; a stub of the declared surface compiles in this arrangement.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package or the environment-reading constructors, and returns the exit code. It extends telemetry's seam in five ways. `Environ` is the environment every git process starts with. `After` is the timer seam for exactly three waits — an operation's wait for a slot and its lock against `QUEUE_SECONDS`, a running git operation's `OPERATION_SECONDS`, and the interval between maintenance cycles — each of which ends when a channel `After` returned delivers; the drain deadline (`DRAIN_SECONDS`) and the writer's delivery attempts run on real time, as in telemetry, because the drain is the one wait the tests of `AGENTS.md` keep to a few real seconds, so a test that hands in an `After` of its own fires a deadline or a cycle when it chooses, and never sleeps; `Now` is the clock those waits are measured and stamped by (`operation.waited`'s `wait_us`, a repository's `created`, every event's time). `Dir` is the working directory the two state paths resolve against, so a test gives repos a temporary directory of its own instead of changing the process's. `Sink` is where the writer `Run` builds delivers, a `*telemetry.Capture` in a test and appkit's socket sink in the binary; `EventSink` is where the emitter `Run` builds delivers bus events, an `*events.Capture` in a test, or one whose `Deliver` fails or blocks, and appkit's event-bus socket sink in the binary. The emitter measures how long it has retried an event by `Now` and pauses between attempts with `Sleep`, so a test whose `Sleep` advances its own `Now` drives an event past the retry window with no real waiting.

`Process.Inherit`, `Unsetenv`, `Pid`, `Stdout`, `Stderr`, `Sleep`, `Rand`, `Banner` and `MCP` are telemetry's. `Version` is the display string `main` read, which `Run` prints for `--version` and records in `service.started`. `Rand` is the source request ids, repository ids and bus event ids are drawn from. A held slot or lock needs no hook of its own: a test of `Run` holds one with a git request whose body it keeps open, and a test of the handler, which builds the `*limits.Limits` it hands in, holds a slot or a repository's lock directly through that value's methods (`D09-limits`), or makes a repository busy with `TryHold`. Maintenance, which no request drives, has one hook, `maintenance.Config.Hold`: a test that sets it holds a repository's maintenance in flight, slot and lock taken and git not yet started, until it lets `Hold` return, which is how a stop during maintenance, `status` showing a repository busy under maintenance, and `delete` refused under maintenance are driven. `Run` leaves it nil.

## Settings

repos reads nine numbers at start: `DRAIN_SECONDS`, the space's, and the eight the manifest's `[env]` declares (`D02-cli`), in this order: `READ_SLOTS`, `WRITE_SLOTS`, `QUEUE_LENGTH`, `QUEUE_SECONDS`, `OPERATION_SECONDS`, `PUSH_MAX_BYTES`, `REPO_MAX_BYTES`, `MAINTENANCE_HOURS`. Each is spelled as opsctl writes an integer — one or more ASCII digits, no sign, no leading zero, no unit, no white space — and an unset or empty one is its default: 5, 8, 2, 16, 30, 600, 104857600 (100 MiB), 1073741824 (1 GiB) and 24. repos sets no upper limit: digits beyond what an `int64` holds read as the largest `int64`, and a consumer turning a count of seconds or hours into a `time.Duration` saturates at the longest duration rather than wrapping. `settings.Read` returns them as a `settings.Settings`, or the first one that is not acceptable as a `*settings.Error` whose text is the diagnostic `D03-serve` writes after `repos: `.

The settings mean this: `READ_SLOTS` and `WRITE_SLOTS` are how many fetches and how many writes (pushes and maintenance runs) run at once; `QUEUE_LENGTH` how many of each kind may wait; `QUEUE_SECONDS` the longest an operation waits for its slot and its lock together, and the `Retry-After` of a refusal; `OPERATION_SECONDS` the longest a git operation runs; `PUSH_MAX_BYTES` the largest pack one push may send, which git enforces as the pack arrives (`receive.maxInputSize`, git-config(1): "If the size of the incoming pack stream is larger than this limit, then git-receive-pack will error out, instead of accepting the pack file"); `REPO_MAX_BYTES` the size on disk at which a repository takes no push; `MAINTENANCE_HOURS` the interval between maintenance cycles. Their behaviour is `D09-limits`' and `D10-maintenance`'s.

## Paths

Relative to `Process.Dir` (the process's own working directory when empty, which is how `main` leaves it, and `/var/opt/ikigenba/repos` on a host): the catalog is the SQLite database `state/repos.db`, and the repositories live in `state/repos/`, one bare git repository per repository at `state/repos/<id>.git`, named by the repository's id and never by its name. The diagnostics of `D03-serve` name the two paths in this relative form whatever `Dir` holds. A catalog that cannot be created, opened or brought up to date is a failure of appkit's `db.Open`, and `store.Open` reports a failure to create or open the repositories' directory with `store.ErrRoot`, so `Run` can write the matching diagnostic of `D03-serve` (`cannot open database state/repos.db: <reason>` or `cannot create directory state/repos: <reason>`). `db status` reads the same `state/repos.db` under `Dir` (`D02-cli`).

## git's published interface

Everything repos does to a repository it does by running `git`. The facts the later documents rely on are git's documented ones. `git http-backend` is a CGI program (git-http-backend(1)): it finds the repository by concatenating `GIT_PROJECT_ROOT` and `PATH_INFO`, relies on `REQUEST_METHOD`, `QUERY_STRING`, `CONTENT_TYPE`, `REMOTE_USER` and `REMOTE_ADDR`, refuses to export a repository without `git-daemon-export-ok` unless `GIT_HTTP_EXPORT_ALL` is set, enables `receive-pack` only for a request with `REMOTE_USER` set (or `http.receivepack` true), serves the dumb protocol too unless `http.getanyfile` is false, and copies `HTTP_GIT_PROTOCOL` to `GIT_PROTOCOL` for protocol v2. `receive.maxInputSize` caps a push's pack stream (git-config(1)). `pack.windowMemory`, `pack.threads` and `core.bigFileThreshold` bound the memory of packing (git-config(1)), which is why `create` writes them into each repository (`D05-store`). `git gc` collects a repository and prunes only unreachable loose objects older than its default expiry (git-gc(1), `--prune`). How repos composes these is `D08-git`'s and `D10-maintenance`'s; that it never uses Go's `net/http/cgi`, which refuses a chunked request body, but runs `git http-backend` itself, streaming the request body to its standard input and its standard output to the client through fixed buffers of `git.CopyBufferSize` bytes, with the CGI header block bounded by `git.MaxHeaderBytes`, is fixed here so the memory a transfer takes does not grow with the pack.

## Vocabulary

A **repository** (in events and tools, a **repo**) is one row of the catalog and one directory: its **id**, `rep_` and 16 lowercase hexadecimal digits, minted when it is created from `Rand` and never changed, under appkit's registered entity prefix `rep_` for the entity type `repo`; its **name**, 1 to 64 characters, each a lowercase ASCII letter, a digit or `-`, the first a letter or a digit, unique among its owner's repositories and changeable; its **owner**, the `X-User-Id` of the caller who created it; its **created** time; and whether it is **available**. The **caller** is the `identity.Caller` of the request. A repository is visible to its owner alone: for every other caller it does not exist. A value `ref` names a repository of a caller as its id when it begins `rep_` and as its name otherwise; a name never holds `_`, so the two never meet.

A repository's **directory** is `state/repos/<id>.git`. A repository is **unavailable** when the last startup verification found its directory missing or not openable by git as a bare repository, and **available** otherwise. Its **size** is the bytes its directory holds on disk, as `D05-store` measures it.

An **operation** is one git process repos runs on a repository: a **fetch** (both routes of `git-upload-pack`, a clone or a fetch), a **push** (both routes of `git-receive-pack`), or a **maintenance** run. A fetch is a **read**; a push and a maintenance run are **writes**. An operation is **waiting** from the moment it asks for its slot (and, for a `POST git-receive-pack` and a maintenance run, its repository's lock) until it has them or is refused, and **in flight** from then until its git has ended. A repository is **busy** while an operation on it is in flight or it is held by `TryHold`; a waiting operation does not make it busy. These two definitions, and that of available, are vocabulary, not requirements: `D09-limits` states busy through `Limits.Busy` and `TryHold`, and `D05-store` states available through `Repo.Available` after `Store.Verify`.

## Events

repos records appkit's framework events — `service.started` and `service.stopping` (`D03-serve`), `request.started` and `request.finished` (`D03-serve`, through appkit's middleware), `tool.called` (`D06-mcp`, through appkit's MCP server), `event.lost` (`D03-serve`, through appkit's emitter, with `event`, the dropped bus event's id, and `cause`, its cause) — and these domain events, and no others. Each names a repository by its id under the key `repo`; none carries a repository's name, a commit message, a path within a repository, an author, a credential, a query or a tool's arguments. The table below is the whole list; the requirement for each fixes its attributes, and the owning document states when it is recorded.

| Event | Attributes | Owner |
|---|---|---|
| `repo.created` | `repo`, `owner` | `D07-tools` |
| `repo.renamed` | `repo`, `owner` | `D07-tools` |
| `repo.deleted` | `repo`, `owner` | `D07-tools` |
| `repo.pushed` | `repo`, `ref`, `old`, `new` | `D08-git` |
| `repo.fetched` | `repo`, `bytes` | `D08-git` |
| `operation.waited` | `repo`, `operation`, `wait_us` | `D09-limits` (git), `D10-maintenance` (maintenance) |
| `operation.rejected` | `repo`, `operation`, `limit` | `D09-limits` (git, draining), `D10-maintenance` (maintenance) |
| `operation.timed_out` | `repo`, `operation`, `limit` | `D09-limits` (git), `D10-maintenance` (maintenance) |
| `maintenance.finished` | `repo`, `duration_us`, `size_before`, `size_after` | `D10-maintenance` |
| `repo.unavailable` | `repo` | `D05-store` |

repos also **emits** to the event bus, the `events` app, exactly one event, `repo.pushed`, with the same four attributes: for each `repo.pushed` the git routes record, they emit one **bus event** beside it, with the same request id and user, and with the cause and depth the push's `X-Event-Cause` and `X-Event-Depth` set (`D08-git`, `D03-serve`). The bus event is in addition to the trail's record, never in place of it; nothing else repos does — a command, a tool, maintenance, verification — emits one. `smarthttp.Emits` is the declaration, which the emitter `Run` builds is made with and the events app reads at `/declarations`.

## Consumer tasks

The binary's start: `main` calls `v := version.Display()` and hands `cli.Run` a `Process` whose `Args`, `LookupEnv`, `Environ`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Version` is `v`, whose `Banner` is the `Banner` method of `page.New(web.ServiceName, v)`, whose `MCP` returns `mcp.NewServer(mcp.ServerConfig{Name: web.ServiceName, Version: v, Telemetry: w})`, and whose `Inherit`, `Now`, `Sleep`, `After`, `Rand`, `Dir`, `Sink` and `EventSink` are left zero; it cancels the context on `SIGTERM` or `SIGINT` with the signal's name as the cause. `Run` reads `settings.Read(p.LookupEnv)`, takes the socket, finds git with `git.Find` over `PATH` and `p.Environ`, opens the catalog with `db.Open` from a `db.Config` naming `state/repos.db` under `p.Dir`, `repos.Migrations()`, `p.Now`, the `Service` `web.ServiceName` and a `Stderr` that reaches `p.Stderr`, opens the store with `store.Open` over that handle from a `store.Config` naming `state/repos` under `p.Dir`, the git, `p.Now` and `p.Rand`, builds the writer with `telemetry.New` over `p.Sink` with `p.Version` as its `Version`, verifies with `Store.Verify`, builds the emitter with `events.New` over `p.EventSink`, `smarthttp.Emits()` and the writer, builds `limits.New(s, limits.Clock{Now: p.Now, After: p.After})`, starts `maintenance.Start`, builds the handler with `web.Handler` from a `web.Config`, tells systemd it is ready, calls `Writer.Ready`, and serves; on the signal it calls `Limits.Drain`, stops the scheduler, drains, shuts the emitter down and then the writer, and closes the handle (`D03-serve`).

The handler: `web.Handler` mounts the pages, `page.Static`, `cfg.MCP` at `/mcp` with `tools.Register(cfg.MCP, tools.Config{...})` called once, and `smarthttp.Handler(smarthttp.Config{...})` for the git routes, all inside `identity.Require` inside `events.Middleware` inside `telemetry.Middleware`, and beside them, inside `telemetry.Middleware` but outside `identity.Require`, `events.DeliveryHandler(nil)` at `/events` and `events.DeclarationsHandler(cfg.Events, nil)` at `/declarations`; it records each request's clone address with `clone.NewContext(ctx, clone.Base(r, cfg.ServicesPath))` so the tools build their URLs from it.

A test of the run seam serves on a listener it bound, with a `Version` of its own, a temporary `Dir`, a `*telemetry.Capture` as `Sink`, an `*events.Capture` (or a sink that fails or blocks) as `EventSink`, an `Environ` and `LookupEnv` over one map holding its git environment, a `Now` and `After` it controls, and cancels with `context.WithCancelCause`. A test of the handler opens a catalog with `db.Open` at a path in a temporary directory, with `repos.Migrations()` and a clock it controls, builds a store with `store.Open` over that handle and a root beside it, a git with `git.Find`, `limits.New` with its own clock, a writer over a `*telemetry.Capture`, an emitter with `events.New` over an `*events.Capture` and `smarthttp.Emits()`, the server with `mcp.NewServer` over that writer with a version string of its own, and the handler with `web.Handler`; it drives `/mcp` with `mcp.Client`, git routes with real `git` through a loopback forwarder or raw HTTP, holds slots through the `*limits.Limits` it built, and calls `maintenance.Cycle` to run a maintenance cycle at once.
