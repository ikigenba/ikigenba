# Decision 18 — The loopback filesystem + commit API

**Decision.** Owning services read and write their artifacts' content through a
loopback HTTP API modeled on dropbox's filesystem API, with two differences that
follow from being a version plane: every read is addressable **at a ref**, and
every write **is a commit**. repos is an ordinary content-plane holder under
`root project/design/D19.md` — that contract's holder rules (streaming, the
loopback-private handler guard, `rev` pinning with 409/404, addressing by the
holder's own key) are cited, not restated.

**These routes carry bytes, never verbs.** Creating, renaming, archiving, and
merging a repository are domain verbs and live only on `POST /mcp` (D22), which
an owning service reaches over loopback by asserting its own identity headers —
there is no REST twin of a domain verb here, because MCP is the suite's single
verb surface. What this Decision owns is the byte and commit traffic the content
plane exists for.

All routes are mounted at the composition root through the shared chassis
`rt.HandleLoopback` guard (keyed on the "did this cross nginx?" marker), so a
request that arrived through nginx gets **404** from every one of them. Bodies
between services are explicitly fine under the content-plane contract; the
reference rule governs the agent-facing surface, which is D22's.

Every route takes `kind` and `name` as query parameters and resolves them
through `Custody.Path` (D17), so an invalid or escaping key is a **400** before
anything touches disk. `ref` defaults to `main`.

| method + path | behavior |
|---|---|
| `GET /content?kind=&name=&path=&ref=&rev=` | stream one file's bytes |
| `GET /list?kind=&name=&ref=&path=` | recursive listing of the tree |
| `GET /stat?kind=&name=&path=&ref=` | one entry's metadata + `content_url` |
| `GET /archive?kind=&name=&ref=` | the whole tree as a tar |
| `PUT /content?kind=&name=&path=&message=&actor=&rev=` | one file → one commit on `main` |
| `DELETE /content?kind=&name=&path=&message=&actor=` | remove a path → one commit on `main` |
| `POST /commit` | many changes → **one** commit on `main` |

## Reads

- **`GET /content`** resolves `ref` to a commit sha and streams the blob at
  `path` with `Content-Length`, a `Content-Type` from the file extension
  (`application/octet-stream` when unknown), and two response headers:
  `X-Repos-Rev` (the resolved commit sha) and `X-Repos-Blob` (the blob sha).
  - `rev=<sha>` is the **pin**: when the resolved commit sha differs, the
    response is **409** with no body bytes streamed.
  - An unknown `ref`, or a `path` absent from that tree, is **404**. The two are
    distinguishable by the body's plain-text detail line, never by the status.
  - Range and conditional requests are permitted, never required; the contract
    is the exact bytes.
- **`GET /list`** returns JSON
  `{"kind","name","ref","rev","entries":[{"path","type","size","blob_sha"}]}`,
  recursive from `path` (default the root), `type` ∈ `file`|`dir`, driven by
  `git ls-tree -r -l -t`. An empty repository (no commits) lists zero entries
  with an empty `rev` rather than erroring — a freshly created repository is a
  normal state, not a missing one.
- **`GET /stat`** returns one entry's metadata plus a `content_url` assembled as
  `registry.BaseURL("repos") + "/content?" + url.Values{…}.Encode()`, so a
  consumer never constructs the URL and never sees a literal address. Absent
  path → **404**.
- **`GET /archive`** streams `git archive --format=tar <ref>` with
  `Content-Type: application/x-tar` and `X-Repos-Rev`. This is the owning
  service's materialization route: the tar contains the tree's files and **no
  VCS metadata** — no `.git` directory, no refs, no objects. An empty repository
  is **404** (there is no tree to export), which is the signal a caller needs to
  distinguish "nothing committed yet" from "an empty tree".

## Writes — mutate-as-commit

All three write routes commit to `main` and nowhere else. They are performed
with git **plumbing against the bare repository**, with no worktree and no
checkout, through a temporary `GIT_INDEX_FILE` under `os.MkdirTemp`:

```
git hash-object -w --stdin              < body            → blob sha (per put)
git read-tree <head>                                       (skipped when the repo is empty)
git update-index --add --cacheinfo 100644,<blob>,<path>    (per put)
git update-index --force-remove <path>                     (per delete)
git write-tree                                             → tree sha
git commit-tree <tree> [-p <head>] -m <message>            → commit sha
```

then `Service.ApplyRefUpdate` (D17) moves `refs/heads/main` with the
compare-and-swap old value and appends the `push` event (D23).

- **The commit is atomic by construction**: one `write-tree`/`commit-tree` pair
  covers every change in the call, so `POST /commit` with N puts and M deletes
  advances history by **exactly one** commit.
- **File mode** is `100644` for every written file; an existing path's mode is
  preserved when it is `100755`. repos stores no other mode — no symlinks, no
  submodules, no gitlinks.
- **Attribution.** The `actor` parameter (the caller's `X-Client-Id`) becomes
  the commit **author**: `<actor> <actor@ikigenba.local>`. The **committer** is
  always `ikigenba <repos@ikigenba.local>`. Author and committer dates come from
  the injected `Clock`, so a test's commit shas are deterministic.
- **`message`** is required and non-empty (**400** otherwise); the plane's whole
  value is a legible history.
- **`rev` / `parent_rev` is the optimistic-concurrency pin**: when supplied and
  different from the current `main` head, the response is **409** and **no
  commit is created**. Omitting it means last-write-wins, which is what an
  owning service's own synchronous edit path wants.
- **The empty-repository case**: with no `main` yet, the commit is created with
  no parent and `ApplyRefUpdate` creates the ref.
- **Deletes are idempotent**: `DELETE /content` for a path that is not in the
  tree, and a `POST /commit` whose changes leave the tree byte-identical, return
  **200** with the **current** head sha and create **no commit**. An empty
  commit is history noise, and an owning service replaying a sync must not
  produce one.
- **Size cap**: a request body larger than `REPOS_MAX_COMMIT_BYTES` is **413**
  with the `too_large` detail, enforced with `http.MaxBytesReader` before any
  blob is written.

`POST /commit`'s body:

```json
{"kind":"sites","name":"acme","message":"sync","actor":"sites:acme",
 "parent_rev":"<sha, optional>",
 "changes":[{"op":"put","path":"index.html","content_b64":"…"},
            {"op":"delete","path":"old.css"}]}
```

Batch content is base64 in JSON rather than multipart: the callers are sites'
sync, prompts'/scripts' import, and seeding — all machine callers on loopback
whose payloads are already in memory — and one JSON shape keeps the route's
parsing, its size cap, and its error contract single.

**Error contract.** Every 4xx body is a single plain-text line carrying the
domain error text (`repos: not found: no entry at "index.html" in main`), never
a fixed placeholder: these responses are what an owning service surfaces to a
user. `ErrValidation` → 400, `ErrNotFound` → 404, `ErrConflict`/`ErrForcePush` →
409, over the cap → 413, anything else → 500.

**Rejected.**
- **A worktree per write.** Checking out, editing, and committing would need a
  lock per repository, disk proportional to the artifact, and a cleanup path for
  every crash. Plumbing against the bare repository with a temporary index is
  the operation git itself provides for exactly this.
- **Exposing a branch parameter on the write routes.** Writes through this API
  are the owning services' vibe edits, which the plane contract defines as going
  straight to `main`. Anything wanting a branch has a real git door (D19); a
  second, weaker branch-writing surface would be a way to bypass the door's
  hooks.
- **Returning the file bytes from a write.** The caller supplied them; the
  useful result is the new `rev`, which is what pins the next read.
- **Making `rev` mandatory on writes.** The owning service's own edit path is
  already serialized by that service's domain lock, and demanding a read before
  every write would double the round trips for the common case. It is available
  for the callers that need it and free for the ones that do not.
- **Allowing empty commits when a delete or a sync is a no-op.** History would
  accumulate entries that changed nothing, and every consumer of `push` would
  wake up for them.
- **Multipart for the batch route.** Two body parsers, two size-cap
  implementations, and two error shapes for one operation, in exchange for
  avoiding a 4/3 expansion on payloads that are already resident in the caller's
  memory on the same box.
- **Serving these routes publicly through nginx with an identity gate.** The
  content plane's holder contract requires loopback-private by handler guard;
  the agent-facing surface is MCP (D22), which is where an external caller
  belongs.

**Verification.** (Real `git` binary throughout; bare repositories under
`t.TempDir()`; routes driven through `net/http/httptest` against the shipped
handler wiring; the shas asserted against real `git rev-parse`/`ls-tree`
output.)

- R-JJL2-2I2O — `GET /content` returns the **exact bytes** of a committed file
  with `X-Repos-Rev` equal to real git's `rev-parse main`; an unknown `path`
  returns **404** and an unknown `ref` returns **404**, each with a plain-text
  body naming what was missing (the two bodies differ).
- R-JKSY-G9TD — after a second commit changes the file, `GET /content` with
  `rev=<the first commit sha>` returns **409** and streams **no** file bytes,
  while the same request with `rev=<the current head>` returns 200 and the
  current bytes — a handler that ignores `rev` fails both halves.
- R-JM0U-U1K2 — `GET /list` over a repository whose tree is
  `a.txt`, `sub/b.txt`, `sub/c/d.txt` returns every file path with its `size`
  and `blob_sha` plus the `dir` entries, recursively; `path=sub` returns only
  the entries under `sub`; and a repository with **no commits** returns 200 with
  zero entries and an empty `rev` rather than an error.
- R-JN8R-7TAR — `GET /stat` returns a file's size and blob sha, and its
  `content_url` is byte-equal to
  `registry.BaseURL("repos")+"/content?"+<encoded kind,name,path,rev>`; fetching
  that exact URL returns the same bytes; `stat` of an absent path returns
  **404**.
- R-JOGN-LL1G — `GET /archive` streams a tar whose member set is **exactly** the
  tree's files at the requested ref (no `.git` member, no ref or object files),
  each member's bytes byte-identical to the committed content; requesting an
  earlier `ref` yields that older tree; an empty repository returns **404**.
- R-JPOJ-ZCS5 — every route in this Decision returns **404** when the request
  carries the nginx-crossed marker (`X-Forwarded-Proto`), and the same requests
  without it succeed — proven for a read route, a write route, and `POST
  /commit`.
- R-JQWG-D4IU — `PUT /content` creates **exactly one** commit on `main`
  (`git rev-list --count main` increases by 1) whose parent is the previous
  head, whose author name is the supplied `actor`, whose committer is
  `ikigenba`, and whose message is the supplied `message`; the returned `rev`
  equals real git's new `rev-parse main`, and `GET /content` afterward returns
  the written bytes.
- R-JS4C-QW9J — `PUT /content` with a stale `rev` returns **409**, and afterward
  `git rev-parse main` is **unchanged** and the commit count has not moved — the
  pin prevents the write rather than reporting after it.
- R-JTC9-4O08 — `DELETE /content` of an existing path creates one commit whose
  tree no longer contains the path; `DELETE /content` of an **absent** path
  returns **200** with the current head and creates **no** commit (`rev-list
  --count` unchanged) and publishes **no** event.
- R-JUK5-IFQX — `POST /commit` carrying three puts and one delete advances
  `main` by **exactly one** commit whose tree contains all three new files and
  not the deleted one; a batch whose changes leave the tree identical returns
  the current head and creates no commit.
- R-JVS1-W7HM — a `PUT /content` (and a `POST /commit`) against a repository
  with **no commits** creates the initial commit with **no parent**
  (`git rev-list --count main` == 1, `git rev-parse main^` fails) and creates
  `refs/heads/main`.
- R-JY7U-NQZ0 — a request body exceeding `REPOS_MAX_COMMIT_BYTES` returns
  **413** with the `too_large` detail and creates no blob and no commit; a body
  one byte under the cap succeeds.
