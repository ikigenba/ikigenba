# Decision 19 — The git smart-HTTP door

**Decision.** repos serves the **real git smart-HTTP protocol** for every live
repository, so an ordinary `git` client — the owner's laptop, an on-box run —
clones, fetches, and pushes with no special tooling. There is one door and two
authenticated paths into it, exactly as `root project/design/D24.md` states.

## Route and mechanism

The handler is mounted at the prefix `/git/` at the composition root (nginx's
trailing-slash `proxy_pass` strips `/srv/repos/`, so a laptop's
`https://<account>.ikigenba.com/srv/repos/git/code/demo.git/info/refs` arrives
as `/git/code/demo.git/info/refs`). The handler:

1. Parses `/git/<kind>/<name>.git/<rest>`, validates `<kind>`/`<name>` through
   `Custody.Path` (D17) — an invalid key, an unknown repository, or an
   **archived** repository is **404**, indistinguishable from each other.
2. Authenticates (below) and derives the **push scope**.
3. Execs `git http-backend` as a CGI program through the `Git` seam's `RunIn`,
   streaming the request body to its stdin and parsing its CGI response
   (headers, blank line, body) onto the `http.ResponseWriter`.

```
GIT_PROJECT_ROOT   = <state>/git
GIT_HTTP_EXPORT_ALL= 1
PATH_INFO          = /<kind>/<name>.git/<rest>
REQUEST_METHOD, QUERY_STRING, CONTENT_TYPE, CONTENT_LENGTH, HTTP_CONTENT_ENCODING
REMOTE_USER        = <the authenticated actor>
REPOS_PUSH_SCOPE   = owner | run          ← read by the pre-receive hook (D17)
GIT_COMMITTER_NAME/EMAIL, GIT_AUTHOR_NAME/EMAIL = the actor
```

`http-backend` is git's own CGI implementation of the protocol; repos
implements no pkt-line framing, no capability negotiation, and no pack
handling of its own.

## The two authenticated paths

Authentication is decided by **which side of nginx the request arrived from**,
using the same "did this cross nginx?" marker the loopback guard uses:

- **Crossed nginx → the owner path.** nginx has already run `auth_request`
  against the dashboard's introspection hook, which accepts a dashboard-minted
  personal access token supplied as the HTTP **Basic password** (the username is
  ignored) and injects the owner headers (D10). repos **trusts them blindly**,
  as it does on every other surface. A crossed request with an empty
  `X-Owner-Id` is **401** — repos never serves a request nginx let through
  unidentified. The actor is the owner email; the push scope is **`owner`**,
  which the hook reads as "`main` may advance by fast-forward". PAT minting,
  storage, and acceptance are the **dashboard's**, and are not this tree's.
- **Loopback → the run path.** The request carries a repository-scoped **run
  token** (D20) as the Basic password or a Bearer token. It is validated against
  the `run_tokens` table; a missing or unparseable credential is **401** with
  `WWW-Authenticate: Basic realm="repos"` (which is what makes an ordinary `git`
  client supply one on the retry). The actor is `run:<kind>/<name>`; the push
  scope is **`run`**, which the hook reads as "`main` may not be touched at
  all".

There is no third path: a loopback request with no token and a crossed request
with no owner id are both refused, so the door is never anonymous.

## Ref updates and events

`receive-pack` moves refs itself, under the `pre-receive` hook — that is the
only correct place for the force-push decision, and D17 owns the hook. The
handler therefore does not call `ApplyRefUpdate`; instead, for a
`git-receive-pack` request it snapshots `Custody.Refs()` **before** and
**after** the CGI invocation and publishes one `push` event (D23) per
`refs/heads/*` that was created or moved, carrying the old and new shas and the
authenticated actor. Refs the hook refused never appear in the after-snapshot,
so a rejected force-push publishes nothing. Deletions publish nothing (D23).

This emission is proven **live through the composition root** — a real `git`
push against the assembled `cmd/repos` service, observed as an envelope on the
real `/feed` — not merely at the outbox table. The door and the event producer
are wired to the same service at the composition root (the git-door handler and
`SetProducer` share it), so an assembly that mounted the door on a
producer-less service would emit nothing on this path; the live proof below is
what catches that class of wiring regression, which a table-level assertion
cannot.

## What the door is not

The door serves **live** repositories only. Archived repositories are 404 — a
recovery is an operator act on disk, not a clone. And the door is the only
surface in repos that writes refs from outside; there is no "push via MCP" verb
and no branch parameter on the loopback write API (D18).

**Rejected.**
- **Implementing the smart-HTTP protocol in Go.** Pkt-line framing, capability
  negotiation, shallow/partial-clone handling, and pack negotiation are a large,
  evolving surface that git already implements correctly and that every future
  git client expects to match. `http-backend` is the supported way to serve it,
  and the whole tree already depends on the real `git` binary.
- **`git daemon` / the git:// protocol.** Unauthenticated by design, a second
  port to expose, and unreachable from a laptop through the apex TLS front door.
- **Serving the door only over loopback and telling humans to use the MCP
  surface.** The product promise is `git clone` from a laptop; a bespoke
  download verb is not that.
- **repos validating personal access tokens itself.** Token minting and
  introspection are the dashboard's single job for every surface in the suite;
  a second validator in repos would be a second place to revoke. repos trusts
  the injected headers exactly like every other service.
- **Deciding force-push protection in the handler by inspecting the pack.**
  The handler cannot see the ref updates until `receive-pack` has parsed them,
  and by then they are being written. The hook is the only pre-write hook point.
- **Letting a run token push to `main` when the update is a fast-forward.**
  The plane's posture is asymmetric on purpose: automation proposes on a branch
  and reaches `main` through an authored merge (D21). A fast-forward exception
  would make every run's last commit an implicit merge.
- **Publishing events from a `post-receive` hook.** Rejected in D17 for the same
  reason: a shell script that must reach the service is a dependency and a
  silent failure mode; the before/after diff needs neither.

**Verification.** (Every id below drives the **real `git` binary** against the
shipped handler mounted on an `httptest` server — the substrate that can
actually falsify a protocol claim. Client working copies and bare repositories
under `t.TempDir()`; the run-token path uses a token minted through D20.)

- R-JZFR-1IPP — `git clone http://<httptest>/git/code/demo.git` into a temp
  directory **succeeds** against a repository holding three commits, and the
  clone's `git rev-list --count HEAD` is 3 with a tip sha equal to the origin's
  `main` — a real end-to-end clone, not an assertion about a handler's headers.
- R-K0NN-FAGE — from that clone, committing and `git push origin
  HEAD:refs/heads/ikigenba/work` **succeeds**; the bare repository afterward
  reports the new ref at the pushed sha, and a **second** fresh `git clone`
  followed by `git fetch origin ikigenba/work` retrieves that commit.
- R-K1VJ-T273 — a `git push --force origin <divergent>:refs/heads/main` over
  the **owner** path **fails** (non-zero exit, stderr carrying the hook's
  rejection text) and afterward the bare repository's `main` points at
  **exactly** the sha it pointed at before the attempt.
- R-K33G-6TXS — a fast-forward `git push origin HEAD:main` over the **owner**
  path **succeeds** and moves `main` to the pushed sha.
- R-K4BC-KLOH — a push that updates two branches in one invocation publishes
  **exactly two** `push` events, one per branch, each carrying the short branch
  name, the new sha, the previous sha (empty for a newly created branch), and
  the authenticated actor; a push whose only ref update the hook **refused**
  publishes **zero** events.
- R-K5J8-YDF6 — a `git push --force` that rewrites `refs/heads/ikigenba/work`
  onto a divergent commit **succeeds** and the ref moves — every ref but `main`
  is unrestricted, so an implementation that set `receive.denyNonFastForwards`
  fails here.
- R-K6R5-C55V — `GET /git/code/demo.git/info/refs?service=git-upload-pack`
  returns 200 with `Content-Type: application/x-git-upload-pack-advertisement`
  and a body whose first pkt-line is `# service=git-upload-pack`; the same
  request for an unknown name, an invalid name (`../escape`), and an
  **archived** repository each return **404** with identical bodies.
- R-K7Z1-PWWK — a request carrying the nginx-crossed marker but **no**
  `X-Owner-Id` is **401**; a loopback request with **no** credential is **401**
  carrying `WWW-Authenticate: Basic realm="repos"`; and a real `git clone` with
  no credentials against the loopback door fails rather than succeeding
  anonymously.
- R-27UP-QL4F — with the **assembled `cmd/repos` service** stood up through the
  real composition root (`spec.Handlers` mounted and the eventplane producer
  injected via `spec.Producer`) on a real `httptest.NewServer` socket, and a
  subscriber connected to that same assembly's `/feed`, a real `git` client that
  clones the door and pushes a new branch causes the subscriber to receive the
  `push` envelope for that branch: `source` `repos`, event/routing key
  `repos:push/sites/<name>`, `subject` `/sites/<name>`, a **non-empty**
  `correlation_id`, and a payload whose `sha` equals the pushed head and whose
  `actor` is the authenticated owner. This drives the git door through the real
  assembly onto the real wire — an implementation that mounted the door on a
  producer-less service, or that wrote the outbox row without it reaching
  `/feed`, fails here even though the table-level R-K4BC-KLOH still passes.
