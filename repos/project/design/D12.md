# Decision 12 — A session carries its correlation id in its row, so the chain survives the runner's detached contexts and a restart

**Decision.** A repos session is **asynchronous by construction**: the request or
consumed event that dispatches it returns long before the work finishes, and the
runner deliberately completes sessions on `context.Background()` so a cancelled
caller cannot kill a running agent (`internal/runner/runner.go`). Correlation
therefore cannot ride the context end to end the way it does for a synchronous
request — the context that knows the id is gone by the time the outcome is
written. The id is carried in the **session row** instead.

**The column.** `sessions` gains `correlation_id TEXT NOT NULL DEFAULT ''`,
added by a **new, additive** migration (`ALTER TABLE sessions ADD COLUMN`)
created with `bin/create-migration repos <name>` — never by editing a committed
migration, and never by rebuilding the table (existing rows keep their data and
get the empty default). `repos.Session` gains the matching field:

```go
type Session struct {
	ID            string
	RepoName      string
	// …
	CorrelationID string   // the chain this session belongs to; "" when unknown
	LogPath       string
}
```

`Store.InsertSession` persists it and `scanSession` reads it back; every other
store method is unchanged.

**Where the value comes from.** Every session is built in one place —
`Runner.Enqueue(ctx, SessionRequest)`, the single seam both entry paths go
through — so that is the single capture point: it reads the ambient correlation
id off its `ctx` with the accessor appkit's correlation package exposes (appkit's
design owns its name) and sets `CorrelationID` on the `Session` it inserts. No
field is added to `SessionRequest`; the id travels on the context, which is what
the context is for.

The two paths that reach `Enqueue` must therefore hand it a **live** context:

- **the webhooks consume hop** (`internal/repos/intake.go`) — the event-plane
  consumer's handler context carries the id the producing chain had, or the root
  the chassis minted for an event that arrived without one;
- **the MCP `start` tool** (`internal/tools`) — the handler context carries the
  id nginx and the chassis put there.

R-BWXC-UZOY drives both, because a path that quietly substitutes its own
context would leave the field empty with no other symptom. When no id is on the
context the field is stored empty; nothing is invented at this layer.

**Where the value is used.** Three places, all on paths where the causal context
is already gone. The runner derives the context it runs a session under from the
dispatcher's background context, so **everything a running session does is
off-chain unless the stored id is put back**:

- **The session's own execution context.** When the dispatcher admits a queued
  session, the context it runs under carries that session's stored
  `CorrelationID`. This is what makes D11 pay off in production: the GitHub peer
  calls a run makes — the queued comment, the label transitions, the token
  fetch, `pr_create` — are issued on that context, so the instrumented client
  finds an id to propagate and github's `request` records join the same chain.
  Without this the peers would be instrumented but chain-less for every
  dispatched run, which is most of repos' outbound traffic.

- **The outcome event.** `AppendOutcome`'s closure currently discards its
  context (`func(_ context.Context, tx *sql.Tx, session Session) error`). It
  stops discarding it and hands it to the outbox `Append`, whose new signature
  carries `correlation_id` from context onto the outbox row and the wire
  envelope. That signature change is **compile-caught** — the build fails until
  this call site is updated, which is exactly the intended forcing function.
- **The runner's detached completions.** Everywhere the runner finishes work on
  a fresh background context — the cancel path, the completion path, the reaper
  success call, and `Recover`'s post-restart sweep — it derives that context
  **carrying the session's stored `CorrelationID`** rather than a bare
  `context.Background()`. The outcome event, and any outbound call made on that
  path, therefore land on the original chain.

This is what makes a repos session reconstructible: the MCP call or webhook
event that started it, the session's own boundary, and the outcome event
published minutes later all share one id — including across a process restart,
where `Recover` writes the outcome from a boot context that knows nothing.

**Scope.** What happens *inside* the dispatched agent session (its git
subprocesses, its tool calls, its provider traffic) is out of recording scope per
D11; this Decision records the session's **boundary** only.

**repos mints no chain root.** appkit offers `rec.StartRoot(ctx, "<op>", nil)`
for self-started background work with no inbound request behind it — one call
per cycle. repos has exactly one such cycle, the reaper's periodic worktree
sweep, and it deliberately does not use it: the sweep's entire body is git
subprocess work (out of scope per D11), it publishes no event and makes no
outbound HTTP call, so a root record would open a chain with no hops in it. The
other two candidates are not roots at all — a dispatched run continues the chain
its stored id names, and `Recover`'s outcome events carry each session's stored
id. If the sweep ever grows a recordable hop, `StartRoot` is the seam to add,
and adding it is a new Decision, not an implementation detail.

**Rejected.**
- **Holding the correlation id in memory on the running session instead of in
  the row.** Cheaper, and it works for a normal completion — but the entire
  reason repos needs this at all is that a session outlives its caller, and the
  worst case is the process dying mid-session. `Recover` runs after a restart
  with no memory of anything; an in-memory id would be exactly `""` in the one
  case where a forensic reader most needs the link. R-BZD5-MJ6C is the id that
  discriminates the two designs.
- **Threading the caller's context into the runner instead of detaching.** It
  would put the id everywhere for free, and it would also let a cancelled MCP
  call or a closed SSE connection abort a running agent session mid-push. The
  detachment is a deliberate property of the session engine (D5); this Decision
  works with it rather than trading it away for telemetry.
- **Reconstructing the chain by joining on session id instead.** A forensic
  reader would have to know that repos sessions are special and join records by
  a payload field. The whole point of one correlation id per causal chain is that
  `chain` answers this uniformly for every service.
- **Putting the id in the event payload.** The suite has moved the correlation
  id to a first-class envelope/outbox field; a payload convention is exactly what
  that supersedes.

**Verification.**
- R-BVPG-H7Y9 — against a **real temp-file SQLite** with the full embedded
  migration set applied, a session inserted with a correlation id reads back
  through `GetSession`/`ListSessions` with that exact id, and a session inserted
  with none reads back as the empty string (not a NULL scan error) — proving the
  column exists with its non-null empty default on a database the runner
  actually migrated.
- R-BWXC-UZOY — dispatching a session **through each of its two real entry
  points** — the webhooks consumer handler and the MCP `start` tool — with a
  correlation id on the inbound context stores exactly that id on the new
  session row; the same dispatch with no id on the context stores the empty
  string. An entry point that leaves the field empty while an id is present
  fails.
- R-LM2I-ORUI — a session dispatched by the runner makes its **GitHub peer calls
  on a context carrying the session's stored correlation id**: driving a run
  whose row holds a known id, with the peer's injected client recording each
  request, every request the run causes carries that id on its `Context()`. A
  runner that runs the session on a bare dispatcher/background context fails —
  and fails while R-BT9N-POGV still passes, since that id proves only that a
  supplied context survives the peer, not that the runner supplies a live one.
- R-BY59-8RFN — driving a session to a terminal status through the runner's
  **real completion path** (real SQLite, real outbox, the runner's own detached
  background context) writes an outbox row whose correlation id equals the
  session row's stored id. A runner that finishes on a bare
  `context.Background()`, or an `AppendOutcome` that still discards its context,
  yields an empty correlation id on the row and fails.
- R-BZD5-MJ6C — `Runner.Recover`, invoked on a **boot context carrying no
  correlation id** over a database holding a `running` session whose row has a
  stored id, writes that session's outcome event with that stored id — not
  empty, and not a newly minted one. An implementation that carries the id only
  in memory fails this while still passing R-BY59-8RFN.
