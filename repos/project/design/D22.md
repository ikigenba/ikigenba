# Decision 22 — The MCP tool surface

**Decision.** repos' agent- and owner-facing surface is MCP, conforming to
`root project/design/D20.md` — structured results with declared output schemas,
the closed error vocabulary, and the three discovery tiers — cited and not
restated. `POST /mcp` is identity-gated by the chassis (D1); every verb is
owner-scoped on `X-Owner-Id` and attributes its writes to `X-Client-Id`.

## The caller model: MCP is the only verb surface, for agents and services alike

**MCP is the suite's single verb surface** (`root project/design/D20.md`), and
that rule is what decides how an *owning service* — sites, prompts, scripts —
creates, renames, or archives the repository behind one of its artifacts. It
does not get a private REST twin. It **speaks MCP to repos' loopback
`POST /mcp`**, asserting the identity headers itself:

| header | what the calling service sends |
|---|---|
| `X-Owner-Id` | the owner the artifact belongs to — the same id that service stores on its own row |
| `X-Owner-Email` | that owner's display snapshot |
| `X-Client-Id` | the calling service's actor string (`sites:<slug>`, `prompts:<prompt_id>`) |

This is the contract's own rule read straight: *the request carries identity;
the handler never cares which door it came through.* nginx injects the headers
for a request from outside; an on-box caller asserts them itself, being inside
the trust boundary already. repos' identity gate refuses on an absent or empty
`X-Owner-Id` and is otherwise indifferent to the caller's nature — a browser's
agent and a sibling service reach the same tool table, and the `X-Client-Id` is
what tells the resulting commit and event apart.

The loopback **plumbing** routes (D18's content/list/stat/archive/commit, D20's
`/run-token`) are not an exception to this: they carry **bytes and non-verb
concerns**, which is exactly what the content plane is for. No domain verb of
repos exists anywhere but here.

**Two idempotency facts owning services depend on**, stated so a seeding or
reconciliation pass can be written against them:

- **`create` of an existing key returns the `conflict` code**, never a silent
  success. A caller adopting a repository left by a partial earlier run
  branches on that code — the closed vocabulary exists so a machine caller can.
  The verb stays honest about what it did rather than collapsing two outcomes
  into one result.
- **`delete` of an already-archived repository succeeds**, returning the
  existing archived record unchanged and publishing no second event. Archiving
  is idempotent because the state it moves toward is terminal; a retry after a
  crashed delete must not be an error.

**Eight domain tools plus `guide`**, and nothing else:

| tool | arguments | returns |
|---|---|---|
| `create` | `kind?` (default `code`), `name` | the new repository |
| `list` | `kind?` | live repositories, this owner's |
| `get` | `kind?`, `name` | one repository: head sha, branches, `clone_url` |
| `rename` | `kind?`, `name`, `to` | the repository at its new key |
| `delete` | `kind?`, `name` | the archived repository |
| `merge` | `kind?`, `name`, `branch` | `{merged, rev, strategy}` (D21) |
| `status_set` | `kind?`, `name`, `sha`, `check`, `state`, `detail?` | the stored status (D21) |
| `status_list` | `kind?`, `name`, `sha` | the statuses for that commit (D21) |
| `guide` | — | the usage document, plain text (Tier 2) |

- **`kind` defaults to `code`** everywhere, because an owner working through MCP
  is almost always working on a plain repository. All four kinds are accepted on
  every verb: an owning service pre-creating or renaming its own artifact's
  repository uses the same surface, and repos arbitrates no names between
  services — uniqueness within a kind is the owning service's job, and repos
  simply reports `conflict` when a key is taken.
- **`create`** initializes a real bare repository (D17) and inserts the
  `repositories` row in one operation; the repository starts with **no commits**
  and is immediately clonable and pushable through the door.
- **`get`** answers from git, not from the DB: the head sha and branch list come
  from `Custody.Refs`, and `clone_url` is the public door address for the mount
  (`/srv/repos/git/<kind>/<name>.git`), which is what a human pastes into
  `git clone`.
- **`delete` is archive** (D17): the repository leaves every listing, the door
  404s it, its bare repository moves under `state/archive/`, and an `archived`
  event is published (D23). It is recoverable, its history is intact, and the
  key becomes available again. **There is deliberately no disk-purge verb** —
  reclaiming disk is an operator act outside this service, and the absence of
  the verb is the enforcement.
- **`merge`, `status_set`, `status_list`** are thin adapters over D21's service
  methods; the behavior is D21's and is not restated here.
- **No push, no branch-write, no content verb.** Bytes travel over the loopback
  content surface (D18) and refs move through the git door (D19); an agent that
  wants file content calls the owning service, which is where the artifact's
  domain lives. Putting a content read on repos' MCP surface would make the
  version plane a second file API.

**Discovery.** Tier 0 (`initialize` instructions) is two or three sentences
naming the service in the vocabulary a user types — *git, repository, version
history, branch, commit, clone, merge* — the create→work→merge flow in one
clause, and one pointer to `guide`. Tier 1 tool descriptions are lean and
keyword-forward, and carry the two cross-cutting rules a caller cannot call
correctly without: `delete` archives rather than destroys, and `merge` refuses
on a red or pending status. Tier 2 (`guide`) carries the kind catalog, the key
shape, the branch conventions, the status vocabulary, and worked examples.

**Canonical-subset input schemas.** Every declared `inputSchema` stays within
agentkit's canonical tool-schema subset. The consumer is the **prompts**
service: it attaches repos as an MCP peer through agentkit, whose send gate
validates each discovered tool's `inputSchema` against that subset and fails
the whole run on any construct outside it — the fix belongs at the server, not
the client. Concretely, the schema helper in `internal/mcp/tools.go` never
emits `additionalProperties` at any depth; the construct is outside the subset
even as `false`. Unknown argument keys are simply ignored by handlers. Output
schemas are not gated and keep the shape the result contract requires.

**Errors** map to the contract's closed set: `ErrValidation` → `validation`,
`ErrNotFound` → `not_found`, `ErrConflict` and `ErrForcePush` → `conflict`,
over-cap bodies → `too_large`. `source_unavailable` is unused — repos has no
upstream to be unavailable.

**Rejected.**
- **A `purge`/`destroy` verb behind a confirmation flag.** Product and the plane
  contract both forbid destroying history from the surface; a flag is a
  confirmation dialog, not a boundary. Not having the code path is the boundary.
- **Separate `archive` and `delete` verbs.** Two names for one operation invites
  a caller to look for the "real" delete. `delete` archives, and its description
  and result say so.
- **A `push` or `commit` MCP verb.** It would be a third way to move a ref, with
  none of the door's hooks, and it would put file bytes in an agent's context —
  which the content-plane contract exists to prevent.
- **Per-kind tool sets** (`site_create`, `script_create`, …). The plane's whole
  claim is that the kinds share one custody model; four parallel surfaces would
  triple the tool count and the guide.
- **Loopback REST twins of the domain verbs** (`POST /repos`, `POST /rename`,
  `DELETE /repos`) so owning services need not speak MCP. That is a second verb
  surface, which the MCP contract forbids outright: two implementations of
  `create` to keep in step, two error mappings, two places a rule like
  archive-not-delete could drift. A service asserting its own identity headers
  on `POST /mcp` is the contract's stated on-box path and needs no new route.
- **A service-only identity mode** (a shared secret or a `X-Service-Name`
  header granting a caller owner-less access to the verbs). It would invent a
  second principal on a single-owner box and put an authorization decision
  inside repos, which is exactly what "nginx is the sole trust boundary" and the
  owner-id contract remove. The calling service knows the owner; it says so.
- **Making `create` idempotent (success on an existing key).** A caller that
  wanted to know whether it created the repository or found one could no longer
  tell, and a genuine name collision between two artifacts would go silent. The
  `conflict` code is machine-branchable precisely so an adopting caller can
  treat it as "already there" while a colliding caller can treat it as an error.
- **Emitting `additionalProperties: false` as reject-unknown-keys
  documentation.** The construct is outside agentkit's canonical subset
  entirely, so its presence fails every prompts run that attaches repos, and it
  documented a rejection no handler ever enforced.
- **Making `kind` required.** The owner's common case is `code`, and a required
  discriminator on every call is friction for the caller the surface exists for.
- **Returning branch listings from `list`.** `list` is a roster and must stay
  cheap; enumerating refs for every repository turns it into N git invocations.
  `get` is where refs are read.

**Verification.** (Tools driven through the assembled MCP handler over
`httptest` with asserted identity headers; real `git` and real migrated temp
SQLite underneath.)

- R-KSPC-80ID — `tools/list` advertises **exactly** `create`, `list`, `get`,
  `rename`, `delete`, `merge`, `status_set`, `status_list`, and `guide`, plus
  the chassis `health` and `reflection`, and nothing else; every tool except
  `guide` declares a non-empty `outputSchema`, and `guide` declares none (the
  contract's prose exception). The `initialize` instructions name the service's
  routing vocabulary and point at `guide`.
- R-KTX8-LS92 — `create` with `{"name":"demo"}` creates the repository under
  kind `code` and a real `git clone` of it through the door succeeds; a second
  `create` for the same key returns the `conflict` code and creates nothing; an
  unknown kind returns `validation`; and `create` under kind `sites` works
  identically (all four kinds accepted).
- R-KV54-ZJZR — `list` returns only the calling owner's **live** repositories:
  a repository created by a different `owner_id` is absent, an archived one is
  absent, and `kind` filters the result. A second owner presenting the same
  `owner_email` sees none of the first owner's rows.
- R-KWD1-DBQG — `get` returns the repository's head sha equal to real git's
  `rev-parse main`, a branch list equal to the repository's real
  `refs/heads/*`, and a `clone_url` ending `/srv/repos/git/<kind>/<name>.git`;
  `get` of an unknown name returns `not_found`, and `get` of an **empty**
  repository returns success with an empty head sha and an empty branch list.
- R-KXKX-R3H5 — `rename` makes the repository reachable under the new key with
  the **same** head sha and commit count (verified by cloning it) and
  unreachable under the old key (`get` → `not_found`); renaming onto an existing
  key returns `conflict` and moves nothing.
- R-KYSU-4V7U — `delete` removes the repository from `list` and makes the door
  404 it, while the archived bare repository still yields **every** commit to a
  real `git clone`; `create` of the same key afterward succeeds; a **second**
  `delete` of the already-archived repository succeeds, returns the same
  archived record, and publishes **no** second `archived` event; and a source
  scan over repos' non-test `.go` files finds **no** `os.Remove`/`os.RemoveAll`
  call targeting the git or archive roots — the absence of a destroy path is
  itself asserted.
- R-JFAI-W00R — the **loopback service-caller path**: a `POST /mcp` request
  arriving **without** the nginx-crossed marker but carrying asserted
  `X-Owner-Id`, `X-Owner-Email`, and `X-Client-Id` reaches the tool table, and a
  `create` through it stores a row whose `owner_id` is the asserted id and whose
  `owner_email` is the asserted email — **even when the tool arguments carry a
  different or bogus owner value**, which is ignored because owner is not an
  accepted argument. The same request with an empty `X-Owner-Id` is refused, and
  a later caller presenting a **different** `owner_id` gets `not_found` for that
  repository. (Substrate: the assembled `appkit/mcp` handler over real SQLite
  with identity injected as an on-box caller sets it; the stored row read back
  from the DB.)
- R-JGIF-9RRG — no tool's declared `inputSchema` contains the key
  `additionalProperties` **at any depth**: a test walks every registered tool's
  emitted `inputSchema` recursively (maps and arrays) and finds zero
  occurrences, so agentkit's canonical-subset gate accepts the whole surface
  when prompts attaches repos as an MCP peer.
- R-L00Q-IMYJ — every domain tool's success result carries `structuredContent`
  that validates against the `outputSchema` that same tool advertised in
  `tools/list`, **plus** a text block whose JSON is byte-equal to the structured
  content (checked for all eight, driven from the advertised schema rather than
  from re-typed literals, so adding a tool without a schema fails).
- R-L2GJ-A6FX — error results carry `isError` and a structured `code` from the
  closed set: an unknown kind → `validation`, an unknown repository →
  `not_found`, a duplicate `create` → `conflict`, a merge blocked by a failing
  status → `conflict`; no error result carries a code outside
  `{validation, not_found, conflict, too_large, source_unavailable}`.
