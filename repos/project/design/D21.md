# Decision 21 — Statuses and the `merge` verb

**Decision.** repos executes nothing, so the only thing it can know about the
quality of a commit is what someone told it. **Statuses** are that record, and
**`merge`** is the one place they are enforced. Both realize
`root project/design/D24.md`'s merge posture: humans and workflows call the same
verb, there is no ambient end-of-run merge, and CI is other services' business.

## Statuses

A status is a verdict about one commit, from one named check:

```go
type Status struct {
    Kind, Name string
    SHA        string // 40-hex, must resolve in the repository
    Check      string // the check's name, chosen by the reporter
    State      string // pending | success | failure
    Detail     string // optional human text or URL
    Actor      string // X-Client-Id of the reporter
    UpdatedAt  time.Time
}

func (s *Service) SetStatus(ctx context.Context, st Status) (Status, error)
func (s *Service) ListStatuses(ctx context.Context, kind, name, sha string) ([]Status, error)
```

- The key is `(kind, name, sha, check)` — a check reporting again about the same
  commit **replaces** its previous verdict rather than appending, so the current
  verdict is a lookup and never a fold over history. The natural flow is
  `pending` at start and `success`/`failure` at the end, from the same check
  name.
- `State` is a closed set of exactly those three values; anything else is
  `ErrValidation`.
- `SHA` must **resolve to a commit in that repository** (`git cat-file -e
  <sha>^{commit}`), else `ErrNotFound`. A verdict about a commit that does not
  exist here is a bug in the reporter, and accepting it would let a gate be
  satisfied by a typo.
- Statuses are **never garbage-collected** by repos and never expire: they are a
  small, append-shaped record of what was checked.

## The gate

A commit's gate is computed **only** from the statuses recorded for that exact
sha:

```go
// Gate returns nil when the sha may be merged, or an error naming the checks
// that block it.
func gate(statuses []Status) error
```

- **Zero statuses → no gate.** A repository nobody wired a check to merges
  freely. This is the contract's explicit rule, and it is what keeps checks
  opt-in.
- Any status in state `failure` or `pending` blocks. The refusal names the
  blocking check names and their states, so the caller knows what to fix or wait
  for.
- Only statuses for the **branch head sha** count. A branch's earlier commits
  are not consulted: the head is what is being merged.

## `merge`

```go
func (s *Service) Merge(ctx context.Context, kind, name, branch, actor string) (MergeResult, error)
// MergeResult{Merged bool, Rev string, Strategy "fast-forward"|"merge-commit"|"up-to-date"}
```

Order of operations, each step refusing before the next:

1. Resolve the repository (`ErrNotFound`), the branch head, and `main`
   (`ErrNotFound` for an unknown branch). `branch` == `main` is
   `ErrValidation`.
2. **Already merged**: when the branch head is already an ancestor of `main`
   (`git merge-base --is-ancestor`), return `{Merged:false,
   Strategy:"up-to-date", Rev:<main>}` — success, **no commit, no event**.
3. **Gate**: `gate(ListStatuses(kind, name, branchHead))`; a block is
   `ErrConflict` carrying the check names.
4. **Conflict check**: `git merge-tree --write-tree main branch`. A non-zero
   exit, or reported conflicts, is `ErrConflict` — and **nothing has been
   written**, because `merge-tree` computes the merged tree in the object
   database without touching a ref or needing a worktree.
5. **Apply**: when `main` is an ancestor of the branch head, fast-forward
   (`Strategy:"fast-forward"`, the branch head becomes `main`). Otherwise create
   a merge commit over the tree `merge-tree` produced:
   `git commit-tree <tree> -p <main> -p <branchHead> -m "merge <branch> into main"`
   (`Strategy:"merge-commit"`), authored by `actor`, committed by `ikigenba`.
6. Move `refs/heads/main` through `ApplyRefUpdate` (D17), which appends the
   `push` event (D23) in the same transaction. Both strategies are
   fast-forwards of `main` by construction, so the choke point's `main` rule is
   satisfied rather than bypassed.

The branch is **not** deleted on merge: whether a branch outlives its merge is
its author's business, and deleting it would publish nothing (D23) while
removing the only handle for inspecting what was merged.

**Rejected.**
- **Executing checks inside repos.** That is arbitrary code execution in the
  custodian — exactly what the plane contract rejects. A check is an ordinary
  scripts/prompts workflow triggered on `repos:push/…` that clones the pushed
  sha and posts a status back.
- **Required-check configuration per repository** (a list of check names that
  must be present before a merge is allowed). It would make merging impossible
  until an unrelated service happened to register, and it puts CI topology in
  the custodian's schema. "Whatever was reported must be green" is enough policy
  and needs no configuration.
- **Statuses keyed by branch instead of sha.** A branch moves; a verdict is
  about the code that was tested. Keying on the branch would let a green run
  vouch for a commit pushed after it.
- **Treating `pending` as passing.** A check that announced it is running and
  has not finished is precisely the case a gate exists for; letting it through
  makes the whole mechanism advisory.
- **Merging with a worktree checkout and `git merge`.** It needs a working
  directory, a lock, and a cleanup path for a conflicted state left on disk.
  `merge-tree --write-tree` answers "does this conflict, and what is the merged
  tree" with no ref and no worktree, so a refusal costs nothing and leaves
  nothing.
- **Auto-merging on a green status arriving.** Ambient merge behavior is
  rejected by the plane contract: intent lives in the caller, not the platform.
- **Squash or rebase strategies.** They rewrite the branch's commits, which
  breaks the sha every recorded status refers to and every event already
  published. Fast-forward or merge commit, nothing else.

**Verification.** (Real `git` binary; real migrated temp SQLite; commits and
branches constructed with real git, and every claim about `main` read back with
`git rev-parse`.)

- R-KFAG-0JCQ — `SetStatus` for a sha that resolves in the repository stores the
  verdict and returns it; calling it again for the same
  `(kind, name, sha, check)` with a different state leaves **exactly one** row
  carrying the new state; a `state` outside `{pending, success, failure}`
  returns `ErrValidation`; and a `sha` that does not resolve as a commit in that
  repository returns `ErrNotFound` and stores nothing.
- R-KHQ8-S2U4 — `ListStatuses` returns every check recorded for a sha and an
  empty result for a sha with none; a status recorded under the **same sha** in
  a **different repository** is not returned (the listing is scoped by
  `(kind, name)`, not by sha alone).
- R-KIY5-5UKT — merging a branch that is strictly ahead of `main` fast-forwards:
  `main` afterward equals the branch head, `MergeResult.Strategy` is
  `fast-forward`, **no new commit object is created**
  (`git rev-list --count main` equals the branch's count), and exactly one
  `push` event for `main` is published carrying the old and new shas.
- R-KK61-JMBI — merging a branch that has **diverged** from `main` without
  conflicting creates a **merge commit**: `main`'s new tip has exactly two
  parents (the previous `main` and the branch head, in that order),
  `Strategy` is `merge-commit`, the merged tree contains both sides' changes,
  and one `push` event is published.
- R-KLDX-XE27 — merging a branch whose change conflicts with `main` (both sides
  edited the same line of the same file) returns `ErrConflict`, leaves `main` at
  **exactly** its previous sha, creates no commit, and publishes **no** event.
- R-KMLU-B5SW — with a `failure` status recorded for the branch head, merge
  returns `ErrConflict` whose message **names that check**, and `main` is
  unchanged; recording `success` for the same check and merging again succeeds
  and moves `main`.
- R-KNTQ-OXJL — with a `pending` status recorded for the branch head (and no
  failure), merge returns `ErrConflict` naming the pending check and `main` is
  unchanged — a gate that treats `pending` as passing fails here.
- R-KP1N-2PAA — a branch head with **zero** status rows merges successfully
  (the no-gate rule), and a branch head whose every status is `success` also
  merges; a status recorded against a **different** sha of the same branch does
  not block the head.
- R-KQ9J-GH0Z — merging a branch whose head is already an ancestor of `main`
  returns success with `Strategy: "up-to-date"` and `Merged: false`, creates no
  commit (`rev-list --count main` unchanged), and publishes no event.
- R-KRHF-U8RO — merging an unknown branch returns `ErrNotFound`, merging in an
  unknown repository returns `ErrNotFound`, and `branch == "main"` returns
  `ErrValidation`; in all three cases `main` is unchanged and nothing is
  published.
