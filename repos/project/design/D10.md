# Decision 10 — nginx fragment & the canonical landing page

**Decision.** repos ships a location fragment at `etc/nginx.conf` (a fragment,
no `server{}`/cert/listen; `MOUNT` `/srv/repos/` and `PORT` `3007` literal in
the file, dev port-rewritten by `nginx/run`), in the suite's standard tiers plus
**one repos-only tier: the git door**.

1. `location = /srv/repos/.well-known/oauth-protected-resource` — open (PRM
   bootstrap, no `auth_request`).
2. `location = /srv/repos/feed { return 404; }` — the event plane is
   loopback-only and never reachable through nginx.
3. Session-gated human tier: `location = /srv/repos/` and
   `location /srv/repos/static/` — `auth_request /_session-authn`,
   `error_page 401 = @login_bounce`. The exact landing location forwards the
   owner identity from the session subrequest; the static-assets location
   forwards no identity.
4. **The git door** — `location /srv/repos/git/`, below.
5. Bearer tier: `location /srv/repos/` (prefix) — `auth_request /_authn`,
   identity headers **replaced** from subrequest vars, proxy to
   `http://127.0.0.1:3007/`, with the standard 429-recovery block.

repos' **loopback surfaces** (D18's content/list/stat/archive/commit routes and
D20's `/run-token`) get no location of their own: they are loopback-private by
handler guard, which is the content plane's stated mechanism
(`root project/design/D19.md`), and the bearer prefix would otherwise proxy them
— so the handler guard, not the fragment, is what makes them unreachable from
outside. The fragment's `= /srv/repos/feed` 404 remains as defence in depth for
the one route the event-plane contract requires it for.

## The git door location

```nginx
location /srv/repos/git/ {
    auth_request /_authn;                       # accepts a PAT as the Basic password
    auth_request_set $repos_git_owner    $upstream_http_x_owner_email;
    auth_request_set $repos_git_owner_id $upstream_http_x_owner_id;
    auth_request_set $repos_git_client   $upstream_http_x_client_id;
    auth_request_set $repos_git_correlation $upstream_http_x_correlation_id;
    proxy_set_header X-Owner-Email    $repos_git_owner;
    proxy_set_header X-Owner-Id       $repos_git_owner_id;
    proxy_set_header X-Client-Id      $repos_git_client;
    proxy_set_header X-Correlation-Id $repos_git_correlation;

    client_max_body_size 0;            # a push is as large as the pack
    proxy_request_buffering off;       # stream the pack; never spool it to disk
    proxy_buffering off;               # stream the response back as git produces it
    proxy_read_timeout 3600s;          # a large clone or push is not idle

    proxy_pass http://127.0.0.1:3007/git/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;
}
```

- The prefix is **longer** than the bearer `/srv/repos/` prefix, so nginx
  selects it regardless of order in the file.
- The dashboard's `/_authn` hook is what makes a **personal access token
  supplied as the Basic password** work: it is the dashboard's introspection
  that accepts the PAT and emits the owner headers. repos trusts what arrives
  (D19); PAT minting and acceptance are the dashboard's tree, not this one.
- The four buffering/size/timeout directives are not decoration: with default
  settings, nginx spools an entire push to disk and truncates it at
  `client_max_body_size`, and a large clone stalls behind `proxy_read_timeout`.
  A git door that has not disabled them is a door that fails on real
  repositories, which is why they are pinned by an id.

**Owner-identity header contract.** The dashboard introspection hooks
(`/_authn`, `/_session-authn`) emit four owner headers on every allow,
fail-closed: `X-Owner-Id` (durable key, never empty), `X-Owner-Email` (display
and audit, never empty), `X-Owner-Name` and `X-Owner-Picture` (percent-encoded,
may be empty). Every location that forwards identity captures them with
`auth_request_set` and replaces them on the upstream request with one
`proxy_set_header` each (identity hygiene: one set per name overrides any
client-smuggled inbound header). The bearer tier additionally forwards
`X-Client-Id` from `$repos_client`. Variables are service-prefixed so the
fragment stays unique inside the shared apex server block.

**Landing page:** `Spec.WWW: true`; `share/www/landing.html` is the canonical
Carbon layout (eyebrow, display service name, one-line lead, the
Service/Version/API panel) rendered by `rt.WWW()` at `GET /{$}` with
`{{.Service}}`/`{{.Version}}`; `share/www/static/` carries `tokens.css` and the
vendored fonts. Only this service's three text fields differ from the canonical
template.

**Rejected.**
- **Skipping the landing page** — every suite app serves the uniform page; its
  absence reads as a broken deploy.
- **Routing the git door through the ordinary bearer prefix.** It would inherit
  request buffering, the default body cap, and the short read timeout, all of
  which break real clones and pushes; and it would proxy to `/` rather than
  `/git/`, hiding the door's own path parsing behind a rewrite.
- **A `location = /srv/repos/content { return 404; }` block for the loopback
  routes.** The handler guard is the mechanism the content-plane contract names;
  an nginx block is optional defence in depth that would have to be kept in sync
  with every route added to D18.
- **Exposing MCP-read surfaces over bespoke public HTTP routes** — all
  owner-facing reads go through the bearer-gated `/mcp`.

**Verification.**
- R-G1OF-AAC8 — a content-assertion `nginx_test.go` over the shipped
  `etc/nginx.conf` proves: the PRM exact location with no `auth_request`;
  `= /srv/repos/feed` returning 404; both session-gated locations with
  `error_page 401 = @login_bounce`; the bearer prefix tier replacing the
  identity headers; and the `127.0.0.1:3007` upstream.
- R-J3QD-3HFN — `nginx_test.go` proves the git-door location exists as the
  prefix `/srv/repos/git/`, is gated by `auth_request /_authn`, forwards
  `X-Owner-Id`, `X-Owner-Email`, `X-Client-Id`, and `X-Correlation-Id` each from
  its own `auth_request_set` variable, proxies to `http://127.0.0.1:3007/git/`
  (not to `/`), and carries **all four** of `client_max_body_size 0`,
  `proxy_request_buffering off`, `proxy_buffering off`, and a
  `proxy_read_timeout` of at least 600s. A fragment missing any one of the four
  fails.
- R-UZVS-S08C — `nginx_test.go` proves the session landing block
  (`location = /srv/repos/`) captures all four owner headers from the
  `/_session-authn` subrequest and forwards them, each via its own
  service-prefixed variable: `$repos_session_owner` → `X-Owner-Email`,
  `$repos_session_owner_id` → `X-Owner-Id`, `$repos_session_owner_name` →
  `X-Owner-Name`, `$repos_session_owner_picture` → `X-Owner-Picture`. A block
  forwarding only `X-Owner-Email` fails.
- R-V13P-5RZ1 — `nginx_test.go` proves the bearer prefix block
  (`location /srv/repos/`) captures all four owner headers from the `/_authn`
  subrequest and forwards them, each via its own service-prefixed variable,
  while `X-Client-Id` from `$repos_client` stays forwarded unchanged.
- R-G2WB-O22X — `GET /{$}` through the assembled handler renders the landing
  with service name `repos` and the running version, byte-parity with the
  canonical layout apart from the three service-specific text fields.
- R-G448-1TTM — `GET /static/tokens.css` (and one vendored font) serve with
  correct content types from `share/www/static/` through the chassis.
