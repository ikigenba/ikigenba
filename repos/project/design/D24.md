# Decision 24 — The landing page lists the live repositories (server render + layout)

**Decision.** repos' landing page grows from the canonical static version card
into the service's owner-facing index: it lists every **live** repository the
service holds, alongside the service name and running version. The route stays
`GET /{$}` at the bare mount root, session-gated at nginx (D10), rendered
in-process from the store and from git (always accurate, no generated file on
disk). This supersedes the canonical-conformance landing D10 formerly pinned
(the canonical byte-parity behavior left the design, and its minted id and
tagged test are deleted with it); D10 keeps the nginx fragment and the
static-asset serving, and this Decision owns the page.

The layout, interaction pattern, and styling deliberately mirror the suite's
proven listing-landing shape (the one sites established): filter bar above the
table, pager below it, sortable header via `aria-sort` + CSS, hidden-until-JS
controls, Carbon component styling from the existing tokens, a top-left Home
link, and a per-row copy button replicating the suite copy-button pattern
(ground truth in `project/research/research.md`). repos owns its own bytes;
nothing is linked from or pinned to another service's tree.

## The data

A new store query feeds the page:

```go
// ListAllRepositories returns every live repository regardless of owner,
// ordered by kind then name. Archived rows are excluded.
func (s *Store) ListAllRepositories(ctx context.Context) ([]Repository, error)
```

The landing page is the box's index of what exists — all owners' live
repositories — matching the MCP `list`'s "live only" posture but not its
per-owner scoping: the page sits behind the session gate, and the box is a
single-owner deployment; the owner sees everything the custodian holds.

The `GET /{$}` handler (constructed at the composition root with the Store,
the Custody, and the version) queries `ListAllRepositories`, resolves each
repository's head via `Custody.Refs` (D17), and passes a view model to
`share/www/landing.html` through `rt.WWW().Render`:

```go
type landingView struct {
    Service string
    Version string
    Repos   []repoRow
}

type repoRow struct {
    Kind      string // island data
    Name      string // island data
    Key       string // "<kind>/<name>" — the visible row identity and the sort key
    Sha       string // first 7 hex of the main tip; "" when the repository has no commits
    ClonePath string // "/srv/repos/git/<kind>/<name>.git" — the mount-anchored door path
}
```

- **`Key`** is the one visible identity: names are unique only within a kind,
  so the row shows `code/demo`, never a bare `demo`. It is plain text — a
  repository has no browsable page to link to, so there is no anchor.
- **`Sha`** is the tip of the repository's `default_branch` (`main`) read from
  `Custody.Refs`, abbreviated to its first 7 characters, rendered in a mono
  cell. A repository with no commits yet (a normal state, D17) has no sha; the
  template renders an em-dash (`—`) and the island carries `""`.
- **`ClonePath`** is byte-identical to the MCP `get` verb's `clone_url` (D22):
  `/srv/repos/git/<kind>/<name>.git`. There is **one** notion of a
  repository's clone address; the page carries the same mount-anchored path
  and the client controller (D25) prefixes the page origin to produce the
  absolute URL the copy button puts on the clipboard. The server does not
  render an absolute URL — repos has no public-base-URL knob (D15) and needs
  none; the origin the viewer is already on is the origin `git clone` needs.

## The layout

The centered `main` is a single top-to-bottom stack:

1. **Home link** — `.home`, absolute top-left, `<a class="home" href="/">Home</a>`,
   linking to the apex root (the dashboard, the suite `DEFAULT` app), styled
   with the existing mono-label tokens (muted, brightening on hover/focus).
   The label is `Home`, not `Dashboard`.
2. **Eyebrow** — `.eyebrow`, text exactly `Git custodian`.
3. **Name + version, one heading line** — `{{.Service}}` with `{{.Version}}`
   inline inside the same `<h1>` (display font at the 28px scale, the version
   keeping the mono/uppercase/muted `.version` treatment with left spacing).
4. **Lead paragraph** — exactly `Holds one git repository per versioned
   artifact and answers ordinary git clients through the suite gateway.`
5. **The filter bar — above the table.** A search input (`#repo-search`,
   fuzzy filter on the `kind/name` key, D25) and a **Clear** button, rendered
   hidden-until-JS.
6. **The repository table** — one row per live repository. Two data-bearing
   headers: **Name** (sortable — carries `data-sort-key="key"`) and **Sha**
   (not sortable, no `data-sort-key`). A final action column at the far right:
   its header unlabelled (an `sr-only` "Copy" for assistive tech), each row's
   cell holding a **copy button** (copy icon + `Copy` label) carrying that
   row's `ClonePath` as a data attribute, hidden-until-JS, styled by the
   replicated suite copy-button pattern. Adjacent to the table sits a hidden
   no-match message (`<p class="no-match" hidden>No repositories match.</p>`).
7. **The pager — below the table.** A Prev / Next pager with a `Page X of Y`
   readout, hidden-until-JS, revealed only past one page (D25).

**Removed wholesale** from the canonical markup: the big display `<h1>` scale
(the heading drops to 28px and carries name and version together), the bordered
three-cell Service / Version / API `<dl>` including the `POST /mcp` value, and
the stale v1 text fields (`Repository session runner`, the lead beginning
`Repos clones repositories`).

**The JSON data island (the client's data source, D25).** Alongside the visible
table, `landing.html` emits the rows once more as a JSON array in an inline
`<script type="application/json" id="repos-data">`. Each element is
`{kind, name, key, sha, clonePath}` — the visible table and the island render
from the one `Repos` slice, so they never disagree. An empty slice renders an
empty island (`[]`). The island is what D25's controller parses; the server
does no filtering, sorting, or pagination (beyond the store's kind-then-name
ordering, which is also the client's default sort ascending).

**Sort affordances (CSS over the semantic attribute).** The active sort state
is the `aria-sort` attribute (`ascending`/`descending`) D25's controller
stamps on the Name `<th>`; the visual is pure CSS over it
(`th[aria-sort="ascending"]::after { content: " ▲" }`, `descending` → `" ▼"`),
plus `cursor: pointer` and a hover affordance on `th[data-sort-key]`. The
server render carries **no** `aria-sort`.

**Hidden-until-JS — and hidden must actually hide.** The interactive controls
(search input, Clear, the pager region, the no-match message, the per-row copy
buttons) carry the `hidden` attribute (plus the `js-only` class and a root
`no-js`→`js` class the controller flips) in the server render, and the
stylesheet forces the attribute to win over any authored `display` on a class:

```css
[hidden] { display: none !important; }
```

With JS off the page is the plain full table; with JS on the controller
reveals the controls.

**Styling.** The interactive controls adopt the shared Carbon `.input` / `.btn`
component styles and the copy control the replicated `.copy-btn` /
`.copy-label` / `.is-copied` rules, all composed from the token custom
properties already in `share/www/static/tokens.css` — no new token values. The
copy label reserves the width of `Copied` up front (a `min-width`, text
right-aligned, the action cell right-aligning the button) so the
`Copy`→`Copied` swap never changes the button, cell, or table width; the
real-browser proof of that is D26's.

**Rejected.**
- **Keeping the canonical Service / Version / API card beside the table.** It
  duplicates the name and surfaces a `POST /mcp` value with no on-page use;
  the suite's listing-landing shape drops it.
- **A separate Kind column.** Settled with the operator: the row identity is
  the combined `kind/name` key — one column, one sort key, and the string the
  clone path is built from.
- **Rendering the name as a link.** A repository has no browsable page; a
  dead anchor is worse than plain text. The actionable affordance is the copy
  button.
- **Showing the full 40-hex sha.** Table noise; anyone needing the full sha
  clones or calls `get`. Seven characters is git's own abbreviation floor and
  reads as git.
- **A sortable Sha column.** Ordering by sha means nothing; Name is the only
  sort key.
- **Server-computed absolute clone URLs.** Needs a public-base-URL knob repos
  does not have (D15) for a value the browser already knows; the client
  prefixes `location.origin` (D25) and the copied string is proven end-to-end
  in D26.
- **Filtering the listing to the session owner's repositories.** The MCP
  `list` scopes per owner because identity arrives per call; the landing is
  the box's index behind the session gate on a single-owner box. Settled with
  the operator: all live repositories.
- **Reading shas from a DB mirror instead of git.** D2's rule: the DB never
  answers a question git owns; a push moves refs behind the DB's back by
  construction.
- **A generated index file on disk; serving the index publicly.** The index is
  the live-rendered, session-gated landing page.

**Verification.** (Template ids render the repo-real `share/www` tree via
`appkit/web` with fixed inputs; handler ids drive the `GET /{$}` handler
against a real migrated store and real bare repositories under `t.TempDir()`
with commits made through the real `git` binary — the substrates that can
falsify the claims.)

- R-RP30-4NV1 — over a real migrated SQLite seeded with live rows under **two
  distinct `owner_id`s** plus one archived row, `ListAllRepositories` returns
  every live row regardless of owner, ordered by kind then name, and never the
  archived row. An implementation that scopes to one owner, includes archived
  rows, or returns unordered fails.
- R-RQAW-IFLQ — rendering `landing.html` places the service name and version on
  a **single heading line** (the version string inside the same `<h1>` as the
  name), and the page contains **no** Service / Version / API card: the
  substring `POST /mcp` is absent and no `<dl>` field labels from the old card
  remain.
- R-RRIS-W7CF — the eyebrow text is exactly `Git custodian` and the lead
  paragraph is exactly `Holds one git repository per versioned artifact and
  answers ordinary git clients through the suite gateway.`; the stale v1 texts
  (`Repository session runner`, a lead beginning `Repos clones repositories`)
  are absent.
- R-RSQP-9Z34 — rendering with a non-empty `Repos` slice: the search input and
  Clear control appear **between the lead paragraph and the table**, and the
  pager region (with its page-readout element) appears **after the table**
  (asserted by document order: lead < controls < table < pager); a hidden
  no-match element is present adjacent to the table; the **Name** header
  carries `data-sort-key="key"`, the **Sha** header carries **no**
  `data-sort-key`, and the far-right action header contains `sr-only`
  assistive text rather than a visible label.
- R-RTYL-NQTT — hidden actually hides: the search input, Clear, pager,
  no-match message, and each row's copy button carry the `hidden` attribute in
  the server render, **and** the page's stylesheet contains a `[hidden]` rule
  forcing `display: none` with `!important`. Controls that render visibly
  without JS fail.
- R-RV6I-1IKI — the sort-affordance CSS is present: caret rules keyed on
  `th[aria-sort="ascending"]` / `th[aria-sort="descending"]` (an appended
  `▲` / `▼`) and a `cursor: pointer` rule targeting `th[data-sort-key]`; the
  server markup itself carries **no** `aria-sort` attribute.
- R-RWEE-FAB7 — the interactive controls are styled, not native chrome: the
  search input, Clear, Prev, and Next each carry a non-empty `class`, and
  every class named resolves to a rule present in the page's styles. A
  class-less native control, or a class with no backing rule, fails.
- R-RXMA-T21W — driving the `GET /{$}` handler against a store and custody
  seeded with a `code` repository and a `sites` repository: each rendered row's
  far-right cell holds a copy button that (a) carries the `hidden` attribute in
  the server render, (b) exposes that row's `ClonePath` — exactly
  `/srv/repos/git/code/<name>.git` and `/srv/repos/git/sites/<name>.git` — as
  its data attribute, byte-identical to the same row's island `clonePath`, and
  (c) carries a styling-hook class that resolves to a rule.
- R-RYU7-6TSL — driving the `GET /{$}` handler against seeded repositories
  whose `main` tips are real commits (made through the real `git` binary):
  each row's Name cell text is the `kind/name` key and its Sha cell is
  **exactly the first 7 characters** of that repository's real `main` sha. A
  handler that renders the bare name, a wrong or full-length sha, or reads the
  sha from anywhere but git fails.
- R-S023-KLJA — a seeded repository with **no commits** renders its row with an
  em-dash (`—`) in the Sha cell, and its island element carries `sha: ""`. A
  handler that errors on the no-commit state, or omits the row, fails.
- R-S19Z-YD9Z — rendering with a non-empty slice emits a
  `<script type="application/json" id="repos-data">` whose parsed JSON is an
  array with one element per row, each carrying `kind`, `name`, `key`, `sha`,
  and `clonePath`, with `key` equal to `<kind>/<name>`; rendering with an
  empty slice emits an island parsing to `[]`. Malformed JSON or a missing
  field fails.
- R-S2HW-C50O — driving the `GET /{$}` handler against a store holding one
  live and one **archived** repository: the archived repository's key appears
  **nowhere** in the page — not in the table, not in the island.
- R-S4XP-3OI2 — the rendered landing body contains the home link: an anchor
  whose `href` is exactly `/`, distinct from the page's `static/` asset
  references.
- R-S65L-HG8R — rendering with an empty `Repos` slice returns without error
  and still contains the service name and version (the page degrades to the
  heading with no rows).
