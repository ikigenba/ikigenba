# Decision 23 — Events: the `push` and `archived` families

**Decision.** repos is an event-plane **producer only** (D1 declares no
consumers). It conforms to `root project/design/D18.md` — envelope, routing key,
matcher, and the SSE wire are that contract's and are not restated here — and
declares exactly **two** kinds:

| kind | subject | payload |
|---|---|---|
| `push` | `/<kind>/<name>` | `{"kind","name","branch","sha","old_sha","actor"}` |
| `archived` | `/<kind>/<name>` | `{"kind","name","archived_path"}` |

```go
// internal/repos/events.go
var Events = eventplane.Registry{
    {Kind: "push",     Subject: "/<kind>/<name>", Doc: "a branch of a repository moved"},
    {Kind: "archived", Subject: "/<kind>/<name>", Doc: "a repository was archived"},
}
```

- **`push` fires on every ref update, from every door**, and is the only signal
  the rest of the suite needs: an edit committed through the loopback API (D18),
  a push through the git door (D19), and a merge (D21) all produce the same
  event with the same shape. A consumer cannot tell — and must not need to tell
  — which door a change came through.
- `branch` is the **short** branch name (`main`, `ikigenba/fix-nav`), not the
  full ref. Only `refs/heads/*` updates publish; tag and note updates do not.
- `old_sha` is the empty string when the branch is being created, and the new
  sha is never empty (a branch **deletion** publishes no event: nothing to
  fetch, nothing to refresh — and `main` can never be deleted at all).
- `actor` is the `X-Client-Id` of the loopback caller, or the owner email on the
  door's owner path, or the run token's repository-scoped identity on the door's
  run path. It is provenance, never authorization.
- **The subject is the repository key, so ordinary glob matching does the
  routing** a consumer needs: `repos:push/sites/**` for every site,
  `repos:push/code/myapp` for one repository. Nothing parses the key apart.

**Publication is transactional at the seam that changed the state**: the outbox
row is appended on the same `*sql.Tx` as the DB write it accompanies (D2,
R-J1AK-BXY9), and the ordering with respect to the non-transactional git ref
update is stated in D17.

The events are published through the appkit/eventplane producer injected at the
composition root (`Spec.Producer`), served on the loopback-only `/feed` that the
nginx fragment 404s publicly (D10).

**Rejected.**
- **Separate kinds per door** (`commit`, `door_push`, `merged`). Consumers care
  that a branch moved and what it now points at; three kinds would make every
  consumer subscribe to three patterns to learn one fact, and would leak repos'
  internal topology into everyone else's subscription list.
- **A `commit` kind carrying the changed file paths.** The payload would grow
  without bound on a large commit and would duplicate what a consumer can read
  from D18's list/archive routes at the announced sha. The event stays a small
  fact; bytes move on the content plane.
- **Publishing branch deletions.** No consumer has an action for one: an owning
  service materializes `main`, and an automated actor deleting its own branch is
  housekeeping. Adding the event would mean every consumer handling an
  empty-sha special case forever.
- **A `created` kind for repository creation.** Creation is immediately followed
  by the first commit in every real flow, and a repository with no commits has
  nothing for a consumer to do. The first `push` is the useful signal.
- **Naming the kinds `repo.pushed` / `repo.archived`.** The contract's rule is
  that `source` already says what the service deals in, so the kind carries no
  redundant noun prefix.

**Verification.**
- R-JDHK-5ND7 — the `Events` registry declares exactly the two kinds `push` and
  `archived` and no others, each with the subject shape above; the chassis
  `reflection` tool advertises both, and advertises **no** subscriptions (repos
  consumes nothing).
- R-JFXC-X6UL — a commit made through the D18 loopback API against a real
  migrated SQLite publishes exactly one event with kind `push`, subject
  `/code/demo`, and a payload whose `branch` is `main`, whose `sha` equals the
  new head reported by real `git rev-parse`, whose `old_sha` equals the previous
  head (and is empty for the repository's first commit), and whose `actor` is
  the request's `X-Client-Id`.
- R-JH59-AYLA — archiving a repository publishes exactly one event with kind
  `archived`, subject `/<kind>/<name>`, and an `archived_path` equal to the
  stored `repositories.archived_path`; no `push` event accompanies it.
- R-JID5-OQBZ — with the real eventplane producer over a real migrated temp
  SQLite and the real `/feed` SSE handler on an `httptest` server, a subscriber
  connected to the feed receives the `push` event produced by a real commit,
  with `source` `repos`, the routing key `repos:push/code/demo`, and a non-empty
  `correlation_id` — proving the declared registry actually rides the wire
  rather than only existing in a table.
