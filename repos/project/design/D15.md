# Decision 15 — Env-channel conformance: the session-engine knobs surface in the manifest; the org is customer data

**Problem.** repos' operator-facing knobs sit outside every configuration
channel (root `project/design/D21.md`): `REPOS_PROVIDER`, `REPOS_MODEL`,
`REPOS_SESSION_TTL`, and `REPOS_MAX_SESSIONS` are env reads whose defaults only
the code states — the compiled `Spec` declares no `ManifestExtras`, so there is
no supported production channel to see or set them ("someone remembers to
export them" is not a channel). And `REPOS_GITHUB_ORG` defaults to the literal
`"ikigenba"` in `cmd/repos/spec.go` — an account fact compiled into the binary,
while the github service already receives its org (`IKIGENBA_GITHUB_ORG`)
through the app-config parameter.

**Decision.** Route every repos value per the root routing contract.

1. **The session-engine knobs are channel-1 manifest knobs.** The `Spec` gains
   its first extras, and the committed `repos/etc/manifest.env` gains the same
   lines after `CONSUMES=webhooks`:

   ```go
   ManifestExtras: []appkit.ManifestKV{
       {Key: "REPOS_PROVIDER", Value: "anthropic"},
       {Key: "REPOS_MODEL", Value: "claude-opus-4-8"},
       {Key: "REPOS_SESSION_TTL", Value: "30m"},
       {Key: "REPOS_MAX_SESSIONS", Value: "2"},
   },
   ```

   The reads in `reposSpec()`'s `Handlers` are unchanged (`config.EnvOr` /
   `EnvOrDuration` / `EnvOrInt`); in production the launcher exports every
   manifest key, so the manifest line is what the process receives, and the
   code defaults become dev fallback that must agree with the manifest's stated
   values. The existing drift proof (R-8IAN-FB87, adopted in D14, already
   derived from `reposSpec()`) pins the byte agreement automatically.

2. **`REPOS_GITHUB_ORG` is customer data** (channel 2; parameter shape at root
   `project/design/D12.md`): `repos/.envrc` gains the strict line form
   `export REPOS_GITHUB_ORG="$(cat ~/.secrets/REPOS_GITHUB_ORG)"`, so
   `bin/push-secrets` ships it in the app-config parameter alongside
   `ANTHROPIC_API_KEY` — the same routing the github service and the
   dashboard's GitHub trio already use. The operator step (per
   `sops/seed-secrets.md`): seed `~/.secrets/REPOS_GITHUB_ORG` — normally a
   symlink to `IKIGENBA_GITHUB_ORG` — before the next push. The code keeps its
   `EnvOr(..., "ikigenba")` read: the default remains the dev fallback for this
   account, but the *channel* is the parameter, and the manifest never carries
   it (per-customer values cannot live in a committed file).

3. **Channel-4 classifications recorded**, so no value is channel-less:
   `REPOS_GITHUB_HOOK` (event-subscription override; default
   `Subscriptions`'s built-in hook name) and `REPOS_BOT_LOGIN` (optional
   self-comment filter; empty disables) are dev-only overrides with working
   code defaults; `REPOS_STATE_DIR` is the state-root override analogous to
   `<APP>_DB_PATH`. None enters the manifest.

4. **Adoption of the box-path-literal guard.** This Decision adopts the root
   env contract's `[proof: per-service]` id **R-VKB6-SHHV** (root
   `project/design/D11.md`): a source-scan test in `cmd/repos/main_test.go`
   walks repos' non-test `.go` files and fails on any `"/opt` string literal —
   repos is clean today, and the guard keeps it that way.

**Rejected.**
- *Put `REPOS_GITHUB_ORG` in `manifest.env`.* The manifest is committed and
  identical on every box; the org is an account fact. Rejected — channel 2.
- *Promote `REPOS_GITHUB_HOOK` / `REPOS_BOT_LOGIN` too.* Neither is an
  operator-facing tuning knob — one names an event subscription whose default
  is the product itself, the other is an optional dev filter; surfacing them
  would grow the manifest without an operator who needs them. Rejected —
  channel 4, revisit if an operator need appears.
- *Read the org from the github service at runtime instead of env.* Adds a
  cross-service call for a launch-time constant and couples repos' boot to
  github's availability; the parameter channel already solves distribution.
  Rejected.

**Verification.**
- R-L9EG-DDWC — with no environment set, the resolved values of
  `REPOS_PROVIDER`, `REPOS_MODEL`, `REPOS_SESSION_TTL`, and
  `REPOS_MAX_SESSIONS` equal the values stated in the committed
  `repos/etc/manifest.env` (parse the committed file, compare against the
  code's resolved defaults) — an edit to either side alone fails. Substrate:
  unit test in `cmd/repos/main_test.go` reading the committed manifest.
- Adopts **R-VKB6-SHHV** (root `project/design/D11.md`, `[proof: per-service]`)
  — no `"/opt` string literal in repos' non-test Go source. Substrate: the
  source-scan test in `cmd/repos/main_test.go`.
- The `.envrc` routing line is config, not testable behavior; its check lives
  in the phase's done bar (an exact-line grep), not as an id.
