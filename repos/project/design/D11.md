# Decision 11 — repos' two direct HTTP peers take the Router-provided instrumented outbound HTTP client

**Decision.** repos makes direct outbound HTTP calls from exactly two places,
both aimed at the **github service on loopback**:

- `internal/repos/git.go` — `HTTPTokenSource`, which fetches an installation
  token with `GET <github>/token`.
- `internal/repos/ghpeer.go` — `GitHubPeer`, which drives every GitHub verb with
  `POST <github>/mcp`.

Both are constructed at the composition root (`cmd/repos/spec.go`) with
`http.DefaultClient`. Both take the **instrumented outbound HTTP client the
chassis Router provides** instead — `rt.HTTPClient(…)`, which hands back a client
already wired to the recorder, so repos never touches the recorder itself. The
Router is in scope exactly where these are built, inside the `Spec.Handlers`
closure:

```go
// cmd/repos/spec.go — the injection points stay; only the client changes.
tokens   := repos.NewHTTPTokenSource(rt.HTTPClient(…), clock.Now)
protocol := repos.NewProtocol(repos.NewGitHubPeer(rt.HTTPClient(…)))

// internal/repos/git.go, internal/repos/ghpeer.go — signatures unchanged.
func NewHTTPTokenSource(client *http.Client, now func() time.Time) *HTTPTokenSource
func NewGitHubPeerAt(baseURL string, client *http.Client) *GitHubPeer
```

Resolve the exact `rt.HTTPClient` argument list from appkit's design when this
builds — appkit owns that signature and it is still settling. Nothing below
depends on the call's shape.

The injected-`*http.Client` seam is deliberately kept: it is what lets tests
point either peer at an `httptest` server, and it is where the instrumented
client is supplied in production. Both peers' **nil-client fallbacks to
`http.DefaultClient` are deleted** rather than repointed: a silent fallback is
how an uninstrumented client survives a refactor unnoticed, and with the
composition root always supplying one, a nil client is a programming error, not a
mode.

**What the chassis client is (consumed as an external fact).** appkit's design
owns this client. repos consumes only its contract: it is an `*http.Client`; each
call through it is recorded as a telemetry record of kind `outbound` (operation,
elapsed, status class, response size + SHA-256 digest — never the response
bytes); and it propagates the ambient `X-Correlation-Id` **only** to loopback
suite peers, reading the id off the outgoing request's context. repos asserts
none of the recording, and none of the header logic — that is appkit's behavior
with appkit's ids, and re-proving it here would duplicate chassis coverage.

What repos must prove is the half that depends on repos: that its own call paths
thread a **live context** down to the wire, so there is an id there for that
transport to find. That is observable from `internal/repos` with an injected
`*http.Client` whose `Transport` is a recording `RoundTripper` — the recorder
sees each request and its `Context()` — so no `*appkit.Router` is needed in a
test.

Because github is a loopback peer, every one of these calls carries the id, and
the resulting pair of records — repos' `outbound` and github's `request` — share
one correlation id, which is what makes a repos-initiated GitHub action
reconstructible across the two services.

**Scope: what repos does NOT instrument.** repos' most conspicuous outward
activity does not travel through an `*http.Client` at all:

- **git subprocesses** (`internal/repos/git.go` shelling out to the real `git`
  binary — clone, fetch, worktree, push over HTTPS to github.com).
- **dispatched agent sessions** (`internal/runner` running an agentkit
  conversation in a worktree, and everything the agent's own tools do inside it).

Neither is recorded, by design and per the suite brief: work happening inside a
spawned subprocess or a sandbox is out of recording scope. The **boundary** is
recorded — the MCP call or consumed event that dispatched the session, and the
session's outcome (D12) — and the session's own transcript is already archived
under `state/` (D9). Nothing in this Decision or in D12 attempts to reach inside
a subprocess, and no phase should try: an agent's in-session tool calls belong to
the transcript, not the telemetry record. The `git push` credential path in
particular stays exactly as it is (a one-invocation `http.extraHeader`), and no
correlation id is ever sent to github.com — a third party.

**Rejected.**
- **Instrumenting the `git` subprocess by injecting `http.extraHeader:
  X-Correlation-Id`.** github.com is a third party; the propagation rule
  forbids it, and it would leak the suite's internal chain ids to an external
  service. It also would not produce a record, since no Go client is involved.
- **Wrapping `exec.Command` for git so subprocess calls become `outbound`
  records.** A git invocation is not an HTTP call; forcing it into the
  `outbound` shape would put a fabricated method/host/path in the record and
  break the meaning of the kind. If git-level visibility is ever wanted it is a
  new kind, decided suite-wide, not smuggled in here.
- **Dropping the `*http.Client` parameters and constructing the instrumented
  client inside each peer.** It would remove the seam tests use to point a peer
  at an `httptest` server, and the composition root is where dependencies are
  supposed to be chosen (Conventions).

**Verification.**
- R-BT9N-POGV — a `GitHubPeer` verb call (e.g. `IssueGet`) driven against an
  `httptest` server with an injected client whose `Transport` records each
  request: the request reaches the wire through **that** client, and its
  `Context()` carries the exact correlation id placed on the call's context — so
  the chassis transport has an id to propagate. A peer that substitutes its own
  context, or that falls back to a package-default client, fails.
- R-BUHK-3G7K — an `HTTPTokenSource` token fetch (`GET /token`) likewise goes
  through the injected recording client carrying the call's context id —
  **including the refetch after the injected clock passes the cached token's
  expiry**, so a token refresh is proven to stay on the chain rather than going
  out bare. A refresh path that reaches for a different client or context fails
  while the first fetch still passes.
