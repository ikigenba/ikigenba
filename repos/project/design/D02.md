# Decision 2 — Data model & migrations

**Decision.** SQLite, owned by this service alone, created by embedded
migrations (`internal/db/migrations/`, `//go:embed`, applied by the appkit
runner). **The database holds metadata only; git holds the content.** No blob,
tree, commit, or ref lives in SQLite — the bare repositories under `state/git/`
(D17) are the store of record for everything git owns, and the DB carries only
what git cannot answer: the repository roster, recorded check verdicts, and
live run tokens.

Three domain tables plus the eventplane outbox:

```sql
CREATE TABLE repositories (
    kind           TEXT NOT NULL,      -- sites | scripts | prompts | code
    name           TEXT NOT NULL,      -- the owning service's own key
    owner_id       TEXT NOT NULL,      -- stable scoping key (root project/design/D17.md)
    owner_email    TEXT NOT NULL,      -- write-once display snapshot; never read for logic
    default_branch TEXT NOT NULL,      -- always 'main' today; a column, not a literal, so the live line is named once
    archived_at    TEXT,               -- NULL = live; set = archived (D17)
    archived_path  TEXT,               -- relative path under state/archive/ once archived
    created_at     TEXT NOT NULL,      -- RFC3339Nano UTC
    PRIMARY KEY (kind, name)
);
CREATE INDEX idx_repositories_owner ON repositories(owner_id);

CREATE TABLE statuses (
    kind       TEXT NOT NULL,
    name       TEXT NOT NULL,
    sha        TEXT NOT NULL,          -- the 40-hex commit the verdict is about
    check_name TEXT NOT NULL,          -- the check's name, chosen by whoever ran it
    state      TEXT NOT NULL,          -- pending | success | failure
    detail     TEXT,                   -- optional human detail / URL
    actor      TEXT NOT NULL,          -- X-Client-Id of the reporter
    updated_at TEXT NOT NULL,
    PRIMARY KEY (kind, name, sha, check_name)
);
CREATE INDEX idx_statuses_sha ON statuses(kind, name, sha);

CREATE TABLE run_tokens (
    token_sha256 TEXT PRIMARY KEY,     -- lowercase hex sha256 of the token; the token itself is NEVER stored
    kind         TEXT NOT NULL,
    name         TEXT NOT NULL,        -- the single repository this token may touch
    expires_at   TEXT NOT NULL,        -- RFC3339Nano UTC
    created_at   TEXT NOT NULL
);
CREATE INDEX idx_run_tokens_expiry ON run_tokens(expires_at);
```

plus the outbox table created from the current eventplane `outbox.SchemaSQL`
(kind/subject envelope, with the correlation-id column) in its own migration,
pinned by a DDL drift guard the same way the sibling services pin theirs.

**Owner keying** follows `root project/design/D17.md` by citation: `owner_id`
is the sole scoping and provenance key, and `owner_email` is captured once at
row creation and never updated or read for logic. `list` filters on `owner_id`
and only on `owner_id`.

**The rebuild migration.** The frozen v1 migrations
(`20260715173914_create_repos.sql`, `20260715173925_create_sessions.sql`,
`20260716013729_consumer_feed_offset.sql`, `20260720015420_owner_id_keying.sql`,
`20260804212311_add_sessions_correlation_id.sql`) stay committed and are never
edited or deleted — the runner keys on the version and an edited body silently
skips. The v2 shape ships as **one new timestamped migration** (via
`bin/create-migration repos <name>`) that **drops `repos`, `sessions`, and
`feed_offset`** and creates the three tables above. Dropping is correct here and
only here: repos' v1 on-box state is a roster of GitHub clones and finished
agent transcripts, explicitly disposable by operator direction, and it holds no
customer content — the customer content of the version plane does not exist yet.
The outbox migration is untouched. From this migration forward the ordinary
suite rule applies with full force: repos' `state/` is primary customer data
under `root project/design/D05.md`, and no later schema change may drop a row.

`internal/repos/store.go` — `type Store struct{ db *sql.DB }` over the shared
single-writer handle, value-object rows (`repos.Repository`, `repos.Status`,
`repos.RunToken`), with the queries the domain needs: `InsertRepository`,
`GetRepository`, `ListRepositories(ownerID, kind?)` (live rows only),
`RenameRepository`, `ArchiveRepository`, `SetStatus` (upsert on the composite
PK), `ListStatuses(kind, name, sha)`, `InsertRunToken`, `LookupRunToken(hash)`,
`SweepExpiredTokens(now)`. Every method that changes state and publishes takes a
`*sql.Tx` so the outbox append rides the same transaction (D23).

**Rejected.**
- **Mirroring refs, commits, or trees into SQLite.** A second copy of what git
  already knows is a cache with no invalidation story: a push through the door
  (D19) moves refs behind the DB's back by construction. git is queried
  directly; the DB never answers a question git owns.
- **A `sha`-keyed commits table to hang statuses off.** The sha is a foreign key
  into git, not into SQLite. A commit row would have to be created before a
  status could be recorded, adding a write path whose only purpose is
  referential decoration.
- **Storing the run token in plaintext.** A DB read (backup, drill, casual
  inspection) would then be a credential leak. Only the sha256 is stored;
  lookup hashes the presented token.
- **Keeping the `feed_offset` table "just in case".** repos is a producer only;
  an offset row for a subscription that does not exist is state with no
  consumer, and its DDL drift guard would pin a library constant this tree no
  longer uses.
- **Preserving the v1 `repos`/`sessions` rows through the rebuild.** Nothing in
  them maps onto a v2 concept: a row named a GitHub clone URL and a finished
  agent transcript, neither of which the version plane has. Carrying them
  forward would mean shipping columns no code reads.
- **A single `repos` table keyed by a synthetic id.** `(kind, name)` *is* the
  identity in the plane's contract (`root project/design/D24.md`); a surrogate
  key would add a lookup between every caller's key and the row.

**Verification.**
- R-IWEY-SUZH — applying the full embedded migration set through the appkit
  runner to a fresh real SQLite database yields exactly the `repositories`,
  `statuses`, `run_tokens`, and `outbox` tables with the columns above
  (`repositories` with the composite `(kind, name)` primary key, `owner_id` and
  `owner_email` NOT NULL and an `owner_id` index; `statuses` with the
  four-column primary key; `run_tokens` keyed on `token_sha256`), **and no
  `repos`, `sessions`, or `feed_offset` table**; the DDL drift guard asserts
  the newest outbox migration contains the current eventplane
  `outbox.SchemaSQL` verbatim.
- R-IYUR-KEGV — applying the full embedded migration set to a database that
  already holds the v1 shape (`repos`, `sessions`, and `feed_offset` created and
  each seeded with a row) leaves those three tables **absent** and the three v2
  tables present with **zero rows**, and the run exits without error. (Real
  temp-file SQLite: build the v1 shape, seed, run the appkit runner over the
  full migration dir, inspect `sqlite_master` and every row count.)
- R-J02N-Y67K — over a real migrated temp SQLite: a `Repository`, a `Status`,
  and a `RunToken` round-trip through the Store with every field intact;
  `SetStatus` called twice for the same `(kind, name, sha, check_name)` leaves
  **exactly one** row carrying the second call's `state` and `detail` (upsert,
  not append); `ListStatuses` for an unseen sha returns an empty slice, not an
  error; `SweepExpiredTokens` deletes a token whose `expires_at` is before the
  injected now and leaves an unexpired one.
- R-J1AK-BXY9 — a state change plus its outbox append are one transaction:
  archiving a repository inside a transaction that the test then forces to roll
  back leaves the `repositories` row **unarchived** and **no** `outbox` row
  behind (atomicity of the D23 pairing, proven at the store seam against real
  SQLite).
- R-J2IG-PPOY — with two owners presenting an **identical `owner_email`** but
  **distinct `owner_id`** seeded in real SQLite, `ListRepositories(idA, nil)`
  returns exactly idA's repositories and never idB's — an implementation
  filtering on `owner_email` fails — and each returned row carries its own
  stored `owner_email` snapshot verbatim; archived rows appear in neither
  listing.
