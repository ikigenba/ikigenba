# Decision 13 — The nginx fragment captures the minted correlation id on gated locations and strips it on the ungated one

**Decision.** `repos/etc/nginx.conf` gains one capture-and-forward pair per
**gated** location and one strip line on its single ungated proxying location, so
the `X-Correlation-Id` reaching the repos process is always trustworthy.

- **Gated locations** — the bearer-gated catch-all `location /srv/repos/` (via
  `/_authn`), the git door `location /srv/repos/git/` (via `/_authn`, D10), and
  the two session-gated locations `= /srv/repos/` and `/srv/repos/static/` (via
  `/_session-authn`) — capture the id the dashboard's introspection endpoint
  minted and returned on the auth subrequest, then forward it, **overwriting**
  anything the client sent:

  ```
  # bearer-gated catch-all
  auth_request_set $repos_correlation $upstream_http_x_correlation_id;
  proxy_set_header X-Correlation-Id $repos_correlation;

  # the git door
  auth_request_set $repos_git_correlation $upstream_http_x_correlation_id;
  proxy_set_header X-Correlation-Id $repos_git_correlation;

  # each session-gated location
  auth_request_set $repos_session_correlation $upstream_http_x_correlation_id;
  proxy_set_header X-Correlation-Id $repos_session_correlation;
  ```

  The door's own git subprocesses are out of recording scope (the spine's
  Conventions), so the id the door captures is what ties the *request* — the
  clone or the push and its outcome — to the chain, not git's internal chatter.

- **The ungated PRM bootstrap**
  `= /srv/repos/.well-known/oauth-protected-resource` has no auth subrequest and
  therefore no minted id, so it **erases** the header and lets the service mint:

  ```
  proxy_set_header X-Correlation-Id "";
  ```

  An empty `proxy_set_header` value means nginx does not pass that field upstream
  at all (see `project/research/research.md`), so the chassis takes its mint
  branch. This is what makes an id un-injectable: an unauthenticated caller
  fetching the PRM doc cannot join or poison somebody else's chain.

- `= /srv/repos/feed { return 404; }` proxies nothing and is untouched; so is the
  named `@repos_authn_500` re-emit location. repos' loopback-only routes (D18,
  D20) have no nginx location at all, so nothing there to capture.

The `$repos_correlation` / `$repos_session_correlation` split follows the
fragment's existing naming (`$repos_owner` on the bearer location,
`$repos_session_owner` on the session-gated ones). Reusing one variable name
across several locations is safe because `auth_request_set` binds per location.
The single `proxy_set_header X-Correlation-Id` per location is the same
per-header identity hygiene the owner headers already rely on: one set for a name
replaces any client-supplied value for that name on the upstream request.

Nothing else in the fragment moves: the location set, each location's auth
posture, the `@login_bounce` bounce on the session gates, the owner-header
forwarding, the `@repos_authn_500` rate-limit re-emit, and the literal loopback
port `3007` all stay as they are. D10's existing fragment ids keep asserting that
shape and stay true.

**What the fragment can and cannot prove.** The end-to-end promise — that a real
id, minted by real introspection, arrives at the repos process and cannot be
supplied by an anonymous caller — is falsifiable only against a live nginx plus
the dashboard's introspection endpoint, which is a suite-root concern outside
`repos/`. What repos *can* prove is that the shipped fragment says the right
thing, and it already proves exactly that for its routing and identity shape:
`cmd/repos/nginx_test.go` reads `repos/etc/nginx.conf` from disk and asserts its
content under D10's ids. The correlation lines extend those same assertions and
are pinned the same way, so the ids below are scoped to what a content read
genuinely shows — the directives are present, on the right locations, in the
right form — and claim nothing about a live chain.

**Rejected.**
- **Trusting an inbound `X-Correlation-Id` on the PRM bootstrap** (no strip
  line). It is the one location on the mount reachable with no token at all;
  without the strip, anyone could pin a request onto an arbitrary chain and the
  forensic record would be caller-controlled.
- **Letting the repos process decide whether to trust the header.** That puts
  trust logic in the service and breaks "nginx is the sole trust boundary" — the
  process cannot tell which location matched; only nginx knows.
- **Skipping `/srv/repos/static/` because it only serves assets.** A landing-page
  asset fetch is part of the same human session as the landing page; dropping the
  id there would fragment one browsing chain into several for no gain, since the
  gate and the capture cost one line each.
- **One shared `$repos_correlation` variable for every location.** It works
  (bindings are per-location) but hides that the bearer, door, and session gates
  are different subrequests; the existing owner-header naming already draws that
  line.
- **Skipping the git door because git subprocesses are not recorded.** The
  *request* is recorded — a clone or a push arriving, and whether it was
  refused — and that record is worth nothing off the chain that dispatched it.

**Verification.** (Proven by `cmd/repos/nginx_test.go`, which already reads
`repos/etc/nginx.conf` from disk, extended.)
- R-9DUI-TUQJ — **every gated location captures and forwards the minted id.** All
  four — the bearer-gated `location /srv/repos/`, the git door
  `location /srv/repos/git/`, `= /srv/repos/`, and `/srv/repos/static/` —
  contain both halves: an `auth_request_set` binding a `$repos_correlation` /
  `$repos_git_correlation` / `$repos_session_correlation` variable to
  `$upstream_http_x_correlation_id`, **and** a `proxy_set_header X-Correlation-Id`
  whose value is that same variable. A fragment where any one of the four omits
  either half, or forwards the client-supplied `$http_x_correlation_id` instead
  of the captured variable, fails — asserting only that the string
  `X-Correlation-Id` appears somewhere would not.
- R-9F2F-7MH8 — **the ungated PRM bootstrap strips the header.**
  `= /srv/repos/.well-known/oauth-protected-resource` contains
  `proxy_set_header X-Correlation-Id "";` and no `auth_request`, and no gated
  location carries the empty-value form. A fragment that leaves the one
  token-free location without the strip — the case where an anonymous caller
  could inject a chain id — fails.
