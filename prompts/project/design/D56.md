# Decision 56 — The run token and the authenticated git door

> **External ordering.** See the banner in D51. The git smart-HTTP door, the
> run-token endpoint, its scoping (one repository, fetch plus push to non-`main`
> refs), and the force-push refusal are the plane's, specified in `root
> project/design/D24.md` and realized by repos.

## Decision

A run clones and pushes over the plane's **loopback git door**, authenticated
with a **short-lived run token** minted per run. prompts holds no long-lived
git credential and mints nothing itself.

**Minting.** At spawn, before the clone, prompts calls
`version.RunToken(nameKey, runID, ttl)` (D52) and receives a `Credential`
carrying the clone URL, a username, a password, and an expiry. The **requested
TTL is the configured run TTL plus the fixed 10-minute margin** of the
run-lifetime contract (`root project/design/D26.md`) — with `PROMPTS_RUN_TTL`
at its default 30m, 40m — because a token that expires mid-run turns the
agent's final push into an authentication failure it cannot fix; the margin
also covers the clone that precedes the run's own clock. The plane honors the
request verbatim (no ceiling, no default); the bound on the lifetime is the
contract's 6h cap on `PROMPTS_RUN_TTL` itself, enforced at startup (D49).

**Installation.** The credential goes into the clone's **local** git config as
a Basic authorization header, never into the remote URL:

```
git -C <sandbox> config http.<cloneURL>.extraHeader "Authorization: Basic <base64(user:token)>"
```

`extraHeader` keyed to the clone URL, rather than `https://user:token@host/…`,
keeps the token out of `git remote -v`, out of every error message git prints,
and out of the `output.jsonl` transcript when the agent runs a git command that
fails. It stays in one file, `.git/config`, which the run fs surface does not
expose (D55).

**The token is deliberately reachable by the run**, since the run is the thing
that pushes. That is safe because of what the plane scopes it to: one
repository, fetch plus push to non-`main` refs, minutes of life. The blast
radius of a run that leaks its own token is a branch on its own repository,
which the run could push anyway.

**What the run can and cannot do**, all enforced by the plane and merely relied
on here: it fetches and pushes `ikigenba/*` and any other non-`main` ref; a
push to `main` is refused; a force-push to `main` is refused. Merging is not a
git operation from the run — it is the plane's `merge` verb, which the in-run
agent reaches as an ordinary suite MCP peer (D19), and **only** when the
prompt's own instructions tell it to. There is no ambient end-of-run merge, in
prompts or anywhere else.

## Rejected

**A long-lived per-service git credential.** It would make every run able to
push every prompt's repository for the life of the box, and it would live in
the service's environment where nothing expires it.

**Embedding the token in the remote URL.** One `git remote -v`, one failed
fetch's error output, and the token is in the run transcript and in the model's
context. `extraHeader` is the same wire result with none of that.

**A credential helper script in the sandbox.** An executable prompts writes
into a directory the agent can edit, run as part of every git invocation. A
config value is inert.

**Passing `-c http.extraHeader=…` per git command instead of writing config.**
It works for prompts' own clone and fails for every command the *agent* runs,
which is the whole reason the credential is there.

**Requesting a token TTL equal to the run TTL exactly.** The last push happens
at the end of a run, which is precisely when a same-length token has expired.
The margin is the cheap fix.

**Having prompts perform an end-of-run merge, or push `main` on the run's
behalf.** `root project/design/D24.md` places merge intent in the workflow
author's text, not in the platform. A prompt that should merge says so and
calls the verb.

## Verification

(Real substrate: a **real bare repository** served over loopback by the **real
`git http-backend`** through `net/http/cgi`, with a wrapper that records the
`Authorization` header, rejects requests without it, and refuses updates to
`refs/heads/main`. The real `git` client performs every clone and push.)

- R-S49H-XMZB — after spawn, `.git/config` in the run workspace contains an
  `http.<cloneURL>.extraHeader` entry carrying the minted credential as
  `Authorization: Basic …`, and the configured `remote.origin.url` contains
  **neither** the username nor the token. A build embedding credentials in the
  remote URL passes a connectivity check and fails this.
- R-S5HE-BEQ0 — the clone against the door succeeds with the credential
  installed and the server records the `Authorization` header on the fetch;
  with the credential omitted, the same clone fails and no workspace is left
  behind at the run's sandbox path. The negative half is discriminating: a
  build that never sends the header would pass an unauthenticated server.
- Adopts **R-35MV-X124** (`root project/design/D26.md`,
  `[proof: per-service]`) — the recorded `RunToken` request asks for a TTL of
  **exactly** the configured run TTL plus 10 minutes (with
  `PROMPTS_RUN_TTL=30m`, `40m`); a bare run TTL or any other margin fails.
  Substrate: the recorded-plumbing fake plane.
- R-3AIH-G40W — one token is minted per run — a second run mints a second
  token rather than reusing the first.
- R-RZDW-EK0J — from the run workspace the real `git` client pushes
  `ikigenba/run-<run_id>` to the door and the branch appears in the bare
  repository's refs; a push of the same commit to `main` is **refused** and
  `main` in the bare repository still points at its previous sha. Both halves
  run against the same server, so a build that simply cannot push fails the
  first.
