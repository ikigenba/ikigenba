# Decision 47 — Rebuild to adopt: event-plane chain continuation, the `root` record at spawn, and the recorded boundary of a run

> **External ordering (operator-sequenced, not built by any prompts phase).**
> This Decision consumes **both** chassis revisions and cannot build before
> they land: appkit's correlation middleware and `StartChain` (its D20),
> telemetry recorder, MCP-dispatch
> and plain-HTTP request instrumentation, and lifecycle records; and
> eventplane's `correlation_id` outbox column + wire envelope field, its
> ctx-populated `Append`, and the correlation id it surfaces into consumer
> handler contexts.

## Decision

Most of prompts' telemetry arrives **free, by rebuilding against the new
chassis**: inbound MCP tool calls (`request`, `mcp:<tool>`), the loopback
plumbing endpoints `/complete` and `/embed` and the human UI routes
(`request`), the `start`/`stop` `lifecycle` pair, and `outbound` records for
peer MCP calls (D45). Three things do **not** arrive free and are this
Decision's subject.

### 1. The event-plane chain crosses in and out

**In (consumer).** The chassis hands the consumer handler a context carrying
the delivered event's `correlation_id`. `consume.Handler` fans out on detached
goroutines (`context.Background()`, so a fired run outlives the engine's
request context) — which would drop the value. The detached context is
therefore re-seeded from the handler's:

```go
// internal/consume/consume.go — inside the fan-out loop.
corr := correlation.FromContext(ctx)      // the delivered event's chain, "" when absent
go func(promptID string) {
    fireCtx := correlation.WithContext(context.Background(), corr)
    if err := fire(fireCtx, promptID, source, ev.Kind, ev.Subject, ev.ID, ev.Payload); err != nil { … }
}(promptID)
```

`FireFunc`'s signature is unchanged — the chain rides the context that path
already carries, so D15's `Consumers` wiring and D24's fan-out contract are
untouched. `startRun` then applies D44's one rule: an envelope that carried a
chain **continues** it; an envelope that carried none makes the run its own
root.

**Out (producer).** eventplane's `Append` becomes ctx-populated and the outbox
grows a `correlation_id` column, so prompts' single emission path is
compile-caught: `FinishRun` → `outcomeEvent` → `outbox.Append(ctx, tx,
Event{Kind, Subject, Payload})`, still on the **same transaction** as the run's
terminal-state write (at-most-once, cancelled-emits-nothing — D25, unchanged).
`FinishRun` already reads the run row to build the outcome payload; it wraps
its own context with that row's `correlation_id` before appending, so the
emitted event carries the **run's** chain no matter which context the terminal
write arrived on (the runner's terminal write deliberately uses a fresh
background context). A self-chained downstream prompt, or notify, therefore
continues the chain that started the upstream run rather than beginning a new
one.

**Schema.** eventplane's revised `outbox.SchemaSQL` is re-applied by each
producer through its own runner: prompts appends **one new timestamped
migration** minted with `bin/create-migration prompts outbox_correlation` that
drops and recreates the outbox table per the revised constant verbatim (a
`DROP TABLE`/`DROP INDEX` preamble + the constant's DDL) — outbox rows are
disposable retention data. Frozen migrations (`005_outbox.sql` and the D25
outbox-routing migration) are **not** touched; the DDL drift guard
(`internal/db/migrations_outbox_test.go`) re-points at the **newest** outbox
migration. This mirrors exactly the handling D25 already established.

### 2. Rooting a chain at spawn — seed the context, then `StartChain`

When a run roots its own chain (D44: no inbound chain id), the origin is
established through appkit's correlation API (its D20), consumed as an external
fact. prompts mints no chain id, builds no record, and never talks to the
recorder. When the run inherits a chain, none of this happens: the chain
already has an origin, and a second root would falsify which one started it.

**Durable-root reuse comes out of composition, not a parameter.**
`StartChain` adopts the context's id with `correlation.Ensure` semantics and
mints **only when absent**, so seeding the context first is exactly what makes
the run its own root:

```go
ctx = correlation.WithContext(ctx, runID) // a run id is a valid suite ULID
ctx = correlation.StartChain(ctx, op)     // adopts runID, records the `root`
```

No caller-supplied-id parameter is needed and no two-ULID origin can arise: the
id `StartChain` records is the one already on the context. prompts supplies the
**op** — `run:<run-id>`, the settled origin form for a run spawn — and the
seeded id, which is the run's own, per the durable-root-reuse rule
(`docs/correlation-ids.md` names a run explicitly as an entity whose own ULID
*is* the chain id).

The domain reaches that two-line composition through one narrow injected
function, so `internal/prompt` imports no chassis telemetry type and tests
observe the decision directly:

```go
// internal/prompt — injected by the composition root, which binds it to the
// seed-then-StartChain composition above. nil returns ctx unchanged, so
// telemetry-disabled builds and every existing test are unaffected.
type RootStarter func(ctx context.Context, rootID, op string) context.Context
```

What is proven here is prompts' half — *whether and with what* the seam is
called — never `StartChain`'s own adopt-or-mint behavior, which is appkit's
coverage. Rooting is best-effort by the chassis contract: a failed or disabled
recorder never fails a spawn.

### 3. The recorded boundary of a run — what is deliberately NOT recorded

A run's **boundary** is recorded: the spawn (`root` or the inbound `request`
that caused it), every suite peer MCP call the in-run agent makes (`outbound`,
D45), the outcome event (`publish`), and the terminal `calls` row's spend.
The run's **inside** is not: the agent's provider traffic, its reasoning, its
builtin sandbox tool use (Bash/Read/Write/Edit/Glob/Grep, Fetch, the File*
share tools) produce **no** telemetry records. That is not an omission — it is
the design: prompts already archives the full conversation in the run's
`output.jsonl`, and the correlation id resolves a chain to the run
(D44's `run_list` filter), so telemetry never duplicates LLM conversation
content and never grows a second, lossy copy of it.

## Rejected

**Extending `FireFunc` with a correlation-id parameter** — every consumer
signature in D15's `Consumers` table and D24's fan-out would move to carry a
value the context already carries end to end; the detached-goroutine re-seed is
three lines at the one place the context is deliberately broken.

**Letting the fired run mint a fresh chain and ignoring the event's id** — that
severs the trail at exactly the interesting hop (the thing that caused the run
is one feed away) and defeats the whole capability for triggered work.

**Emitting a `root` record for every run, inherited or not** — two origins on
one chain; a forensic reader could not tell which one actually started it.

**Building the `root` record in prompts instead of going through the chassis
API** — the record model, the recorder's best-effort semantics, and the context
plumbing are all chassis-owned; a service-local copy is a second implementation
to drift. prompts contributes only the two facts it alone knows: that this
spawn roots a chain, and that its durable root is the run.

**Calling `StartChain` on an unseeded context and letting it mint** — it would
mint a fresh ULID for an origin that already owns one, putting two ids on one
run and contradicting the durable-root-reuse rule. Seeding first costs one line
and makes the rule structural.

**Recording the in-sandbox agent's tool use and provider round-trips** — it
would duplicate `output.jsonl` in a lossier form, put unbounded LLM content
through a store designed for skeletons, and make telemetry's storage grow with
model verbosity. The archive is the content store; telemetry points at it.

**Threading the chain id into `Append` explicitly as an argument** — the
eventplane contract populates it from context; passing it twice invites the two
to disagree.

## Verification

(Real substrates: the consume claims run the real `consume.Handler` over the
real `prompt.Service` + `Store` + temp SQLite substrate D15's smoke test
already uses; the outbox claim reads a real SQLite outbox row back by SQL after
a real `FinishRun`; the rooting claims observe the injected `RootStarter`.)

- R-HZD1-FEUB — an event delivered on a handler context carrying correlation id
  `X` fires a run whose stored `correlation_id` is exactly `X` (read back by
  SQL) — proving the id survives the detached fan-out goroutine; a build that
  fires on a bare `context.Background()` stores the run id instead and fails.
- R-I0KX-T6L0 — an event delivered on a context carrying **no** correlation id
  fires a run whose stored `correlation_id` equals that run's own id (not
  empty), and the same event delivered twice produces two runs on two distinct
  chains.
- R-I1SU-6YBP — after `FinishRun` lands a succeeded run whose row carries
  correlation id `X`, the real SQLite outbox holds exactly one row for that run
  whose `correlation_id` column is exactly `X`, written on the same transaction
  as the terminal-state write; a cancelled run still emits no row.
- R-I30Q-KQ2E — the injected `RootStarter` is called **exactly once** for a run
  that roots its own chain, with `rootID` equal to the run id and `op` exactly
  `run:<run-id>`; for a run started on a context already carrying chain `X` it
  is called **zero** times.
- R-I48M-YHT3 — the boundary holds: for a run whose fake provider drives the
  agent through at least one **builtin sandbox** tool use, the injected
  `RootStarter` is still called exactly once (the spawn) and nothing in the run
  path emits anything naming that tool, while the run's `output.jsonl` **does**
  contain the `tool_use` record for it — the archive holds the inside,
  telemetry holds only the boundary.
