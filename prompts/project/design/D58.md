# Decision 58 — `repos` joins the trigger sources: prompts as the version plane's workflow runner

## Decision

The version plane publishes a `push` family on every ref update (`root
project/design/D24.md`). prompts is the suite's trigger surface, so adding that
producer to its consumed sources is what makes a prompt a CI check, a
merge-on-green workflow, or a "regenerate the site when the blog branch lands"
job — without any new mechanism, because D24's canonical-filter triggers
already express it:

```
repos:push/sites/blog
repos:push/prompts/daily-digest
repos:push/**
```

Four coordinated edits, all of them the existing shapes:

1. **`knownFamilies` gains `repos`** (`internal/prompt/trigger.go`):
   `"repos": {"push"}`. Subjects stay open, so
   `repos:push/<kind>/<name>` validates without prompts knowing any repository
   name. As with every other entry, this static table tracks the producer's own
   spec and carries the same known, accepted drift cost D24 already recorded.
2. **`sources` gains `repos`** (`cmd/prompts/main.go`), yielding one more
   `Spec.Consumers` entry, one more feed loop, one more cursor — the plain
   per-upstream shape D15 established. `consume.Subscriptions` therefore yields
   a `repos` subscription with `Filter` `**` like every other in-edge; no
   consume-side code changes.
3. **`etc/manifest.env` `CONSUMES` gains `repos`**, keeping the manifest's
   declared in-edges equal to the code's (the D49 drift oracle compares them,
   so a build that edits one and not the other fails there).
4. **The feed URL** resolves as every other upstream's does: the env override
   `PROMPTS_REPOS_FEED_URL` when set, defaulting through
   `registry.BaseURL("repos")` (D14). No literal.

**Self-chaining still works and now closes a loop worth naming**: a prompt
triggered on `repos:push/prompts/<some-prompt>` reacts to a change in another
prompt's own definition — the plane's histories are ordinary subjects,
including prompts' own.

**The known-source error message changes**, since the set it names is now
seven. That behavior is D24's and keeps its id there (`R-6KLN-PNOI`, whose line
D24 states in terms of the known set rather than a count); this Decision mints
no id for it, and the phase that builds the new source re-realizes D24's id
alongside its own.

## Rejected

**Filtering the `repos` in-edge to `push` at the subscription level.** Every
other in-edge is `**` and lets the per-prompt trigger do the filtering; a
special case here would diverge for no benefit and would silently drop a family
repos adds later.

**Teaching prompts repos' full family vocabulary now.** `push` is the family
`root project/design/D24.md` guarantees ("at minimum"); the rest are repos'
spec's to declare, and a table entry for a family nobody publishes is a trigger
that validates and never fires.

**A dedicated "CI" concept in prompts — required statuses, check registration,
a pipeline surface.** The plane's gate is statuses posted by ordinary
workflows, and a workflow is a prompt with a trigger. Adding a CI object here
would build a second, worse version of what the trigger already is.

## Verification

- R-SBKW-89FH — `repos:push/prompts/daily-digest` and `repos:push/**` are
  accepted by `validateTrigger` and store derived `source = "repos"`;
  `repos:nosuchkind/**` is rejected with `ErrValidation`; and an unknown source
  (`github:push/**`) is rejected with an error naming the known set **including
  `repos`**. The real `eventplane/routing` matcher and real SQLite are the
  substrate.
- R-SCSS-M166 — `consume.Subscriptions(sources)` yields a subscription whose
  `Source` is `repos` and whose `Filter` is exactly `**`; the committed
  `etc/manifest.env` `CONSUMES` list contains `repos`; and the resolved
  `repos` feed URL equals `PROMPTS_REPOS_FEED_URL` when set and the
  registry-derived address for service name `repos` when unset — with no port
  literal in the source. A build adding the source but not the manifest entry
  fails the manifest half (and D49's oracle).
