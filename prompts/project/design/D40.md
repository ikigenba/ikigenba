# Decision 40 — Two loaders: the live prompt and the run's frozen copy

## Decision

"The prompt" means two different things depending on the question, and each gets its own named loader returning the same shape. Choosing the function is choosing the meaning.

```go
// Executed is the prompt a run runs: everything pinned at spawn.
type Executed struct {
    Name         string
    UserPrompt   string
    SystemPrompt string
    Config       Config
}

// LoadFromPrompt reads the live definition from the prompts table, owner-scoped.
// Spawn is its only caller.
func (s *Service) LoadFromPrompt(ctx context.Context, ownerID, promptID string) (Executed, error)

// LoadFromRun reads the frozen snapshot from <runsDir>/<run_id>/input/.
// Package-level and unauthorized: callers past the owner check use it directly.
func LoadFromRun(runsDir, runID string) (Executed, error)

// RunExecuted resolves runID to its owner-scoped run row, then LoadFromRun.
// Every run-side read path uses this.
func (s *Service) RunExecuted(ctx context.Context, ownerID, runID string) (Executed, error)
```

**The rule this encodes: the run path never reads the `prompts` table.**

- **Spawn** — `LoadFromPrompt`, write the result into `<runsDir>/<run_id>/input/`, insert the `runs` row. The single crossing point between the two worlds.
- **`runner.execute`** — `LoadFromRun`. It already reads the pinned files deliberately rather than the live prompt; this replaces its hand-rolled reads with the shared loader. It calls the package-level form because the runner is downstream of authorization and because the dependency direction forbids the other: `Service` holds the `Runner`, and `internal/runner` imports package `prompt`, so a `Service` method is not reachable from there.
- **Every read of a past run** — `RunExecuted`. The MCP surface and the browse UI (D35) get the prompt text and config a run actually executed.

The two loaders legitimately disagree, and that is the point: edit a prompt after a run and `LoadFromPrompt` reports the new text while `LoadFromRun` reports what ran. Delete the prompt and `LoadFromPrompt` fails while `LoadFromRun` still answers.

**`event.json` stays out of `Executed`.** The runner also reads the triggering event from `input/`, but an event is not the prompt. It keeps its own read so `Executed` means one thing.

**`RunList` drops its prompt lookup.** `Service.RunList` currently calls `GetPrompt(ctx, ownerID, promptID)` before querying, purely as an ownership check. That is the wrong source for it: once the prompt is deleted the check cannot pass, so a deleted prompt's runs become unlistable even though the rows are intact and the caller owns them. `runs` rows carry both `prompt_id` and `owner_id`, so the query answers ownership itself — which is already how `RunGet` and every other run-side method scope, via `runForOwner`. The precondition is removed and the query is owner-scoped directly:

```go
func (s *Service) RunList(ctx context.Context, ownerID, promptID string) ([]Run, error) {
    return s.store.ListRunsByPromptForOwner(ctx, ownerID, promptID)
}
```

An unknown or unowned `prompt_id` returns an empty list rather than an error — the caller owns no runs under it, which is the truthful answer and is indistinguishable from a prompt that never had runs.

## Rejected

**Soft-delete prompts (a `deleted_at` column, filtered everywhere)** — the obvious fix for "a run's prompt is gone", and rejected. It keeps deleted rows alive in every prompt query, adds a filter each of those queries must remember, and — the real objection — re-couples a run to a mutable prompt row. The snapshot is already the more correct source: a prompt edited after a run would misreport what that run executed even with the row still present. Soft-delete solves the deletion case and leaves the editing case broken.

**One loader with a flag (`Load(ctx, id, fromRun bool)`)** — rejected: the flag hides the choice that matters, and the two forms differ in authorization, dependency direction, and failure mode. Two names make the meaning legible at every call site.

**Make `LoadFromRun` a `Service` method for symmetry** — rejected: `internal/runner` cannot reach it. Symmetry at the cost of the runner re-implementing the read is a poor trade; `RunExecuted` restores the symmetric, authorized form for callers that need it.

**Have `RunList` return an error for an unknown `prompt_id`** — rejected: distinguishing "no such prompt" from "no runs" requires the prompts-table read this Decision exists to remove, and the distinction buys the caller nothing.

## Verification

- R-ZOYX-Y9WA — after a run completes against a prompt, updating that prompt's `user_prompt` and config leaves `RunExecuted` for that run returning the original text and config, while `LoadFromPrompt` for the same prompt returns the updated ones. Both are asserted in the same test: a build reading the live row from the run path returns the updated text from both and fails.
- R-ZREQ-PTDO — after a run completes and its prompt is deleted, `RunList` for that `prompt_id` and owner still returns that run, and `RunExecuted` still returns the prompt text and config it executed. A build retaining the `GetPrompt` precondition returns an error and fails the first clause.
- R-ZSMN-3L4D — `RunExecuted` called with an owner id that does not match the run's `owner_id` returns the not-found error and no `Executed` content, for a run that exists and whose files are present on disk; the run's true owner receives the content. This pins that moving the read to disk did not drop the owner scope.
