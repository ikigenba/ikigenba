# Decision 40 — Two loaders: the live definition and the run's pinned commit

## Decision

"The prompt" means two different things depending on the question, and each gets
its own named loader returning the same shape. Choosing the function is choosing
the meaning — and since D51 the two now read from two different places, which
makes the choice load-bearing rather than merely tidy.

```go
// Executed is the prompt a run runs: everything pinned at spawn.
type Executed struct {
    Name         string
    UserPrompt   string
    SystemPrompt string
    Config       Config
}

// LoadFromPrompt reads the LIVE definition: the prompt's row for its metadata
// plus the version plane's main tip for prompt.md / system.md / config.json
// (D52, D53). Spawn and Get are its callers.
func (s *Service) LoadFromPrompt(ctx context.Context, ownerID, promptID string) (Executed, error)

// LoadFromRun reads the run's PINNED definition out of the run's own clone at
// the commit recorded on the run row: `git -C <runsDir>/<runID>/sandbox show
// <sha>:<path>`. Package-level and unauthorized: callers past the owner check
// use it directly. It touches neither the prompts table nor the version plane.
func LoadFromRun(runsDir, runID, sha string) (Executed, error)

// RunExecuted resolves runID to its owner-scoped run row (which carries the
// sha), then LoadFromRun. Every run-side read path uses this.
func (s *Service) RunExecuted(ctx context.Context, ownerID, runID string) (Executed, error)
```

**The rule this encodes: the run path reads neither the `prompts` table nor the
version plane.** Everything a past run needs is inside the run's own directory.

- **Spawn** — `LoadFromPrompt` for the metadata and the resolved head sha,
  recorded on the row; the definition itself arrives with the clone (D55). The
  single crossing point between the two worlds.
- **`runner.execute`** — `LoadFromRun` at the run's sha. It calls the
  package-level form because the runner is downstream of authorization and
  because the dependency direction forbids the other: `Service` holds the
  `Runner`, and `internal/runner` imports package `prompt`, so a `Service`
  method is not reachable from there.
- **Every read of a past run** — `RunExecuted`. The MCP surface and the browse
  UI (D35) get the definition a run actually executed.

The two loaders legitimately disagree, and that is the point: commit to a
prompt's `main` after a run and `LoadFromPrompt` reports the new text while
`LoadFromRun` reports the commit that ran. Delete the prompt — archiving its
repository (D53) — and `LoadFromPrompt` fails while `LoadFromRun` still answers,
because the clone is local and the commit is immutable.

**`event.json` stays out of `Executed`.** The runner also reads the triggering
event from `input/`, but an event is not the prompt. It keeps its own read so
`Executed` means one thing.

**`RunList` has no prompt lookup.** Ownership is answered by the `runs` rows
themselves, which carry both `prompt_id` and `owner_id` — the same way `RunGet`
and every other run-side method scope, via `runForOwner`:

```go
func (s *Service) RunList(ctx context.Context, ownerID, promptID string) ([]Run, error) {
    return s.store.ListRunsByPromptForOwner(ctx, ownerID, promptID)
}
```

An unknown or unowned `prompt_id` returns an empty list rather than an error —
the caller owns no runs under it, which is the truthful answer and is
indistinguishable from a prompt that never had runs.

## Rejected

**Soft-delete prompts (a `deleted_at` column, filtered everywhere)** — the
obvious fix for "a run's prompt is gone", and rejected. It keeps deleted rows
alive in every prompt query, adds a filter each of those queries must remember,
and — the real objection — re-couples a run to a mutable prompt row. The pinned
commit is already the more correct source: a prompt edited after a run would
misreport what that run executed even with the row still present.

**One loader with a flag (`Load(ctx, id, fromRun bool)`)** — rejected: the flag
hides the choice that matters, and the two forms differ in authorization,
dependency direction, storage, and failure mode. Two names make the meaning
legible at every call site.

**Make `LoadFromRun` a `Service` method for symmetry** — rejected:
`internal/runner` cannot reach it. `RunExecuted` restores the symmetric,
authorized form for callers that need it.

**Have `LoadFromRun` ask the version plane for the sha's blobs** — rejected in
D55: it makes a past run's own history unreadable exactly when the repository is
archived or the plane is down.

**Have `RunList` return an error for an unknown `prompt_id`** — rejected:
distinguishing "no such prompt" from "no runs" requires a prompts-table read
this Decision exists to remove, and the distinction buys the caller nothing.

## Verification

- R-ZOYX-Y9WA — after a run completes against a prompt, updating that prompt
  (a new commit on its `main`) leaves `RunExecuted` for that run returning the
  original text and config, while `LoadFromPrompt` for the same prompt returns
  the updated ones. Both are asserted in the same test: a build reading the live
  definition from the run path returns the updated text from both and fails.
- R-ZREQ-PTDO — after a run completes and its prompt is deleted (its repository
  archived), `RunList` for that `prompt_id` and owner still returns that run,
  and `RunExecuted` still returns the text and config it executed **with the
  version-plane client failing every call** — proving the run-side read touches
  neither the prompts table nor the plane.
- R-ZSMN-3L4D — `RunExecuted` called with an owner id that does not match the
  run's `owner_id` returns the not-found error and no `Executed` content, for a
  run that exists and whose clone is present on disk; the run's true owner
  receives the content. This pins that moving the read off the database did not
  drop the owner scope.
