# Decision 6 — Suite discovery: the inventory peer set and the live catalog

## Decision

`prompts/internal/suite` owns *which peers a run may reach* and *what the
catalog says about them*. It no longer produces `agentkit.MCPServer`
attachments — the gateway (D19) surfaces peers to the model, and this package
feeds it.

**The peer set** is a pure inventory-to-peer mapping, no network I/O:

```go
// Peer is one reachable suite service, addressed and identified for the run.
type Peer struct {
    Name    string            // the bare service name, e.g. "crm"
    BaseURL string            // http://127.0.0.1:<port>/mcp (registry-resolved, D14)
    Headers map[string]string // the run's identity + chain id, injected on every request
}

func Discover(ctx context.Context, manifestRoot, ownerID, ownerEmail, promptID, correlationID string) []Peer
```

It reads the box inventory under `manifestRoot` (`appkit/inventory`: services
whose manifest sets `MCP=true`, already sorted by name), excludes `prompts`
itself (a run must not spawn a run), resolves each port by service name through
the shared `registry` (D14), and returns one `Peer` per remaining service. It
cannot fail and returns a non-nil (possibly empty) slice. Headers are the
identity trio — `X-Owner-Id: ownerID`, `X-Owner-Email: ownerEmail`,
`X-Client-Id: "prompts:" + promptID` — plus `X-Correlation-Id: correlationID`
when non-empty (absent when empty; D45 owns the chain-propagation claim).
`Name` is the **bare** service name: the `ikigenba_` prefix died with the
attachment path — the model addresses services by catalog name through
`suite_call`, and peers see only HTTP headers.

**The live catalog** backs the `suite_services` gateway tool:

```go
// CatalogEntry is one catalog row. Summary is the first sentence of the
// peer's MCP server instructions; empty when the peer did not answer.
type CatalogEntry struct {
    Name    string
    Summary string
}

func Catalog(ctx context.Context, peers []Peer, clients func(Peer) InstructionLister) []CatalogEntry
```

`Catalog` fans out concurrently to every peer's `initialize` (via the D60
client's `Instructions`), takes the **first sentence** of each server's
instructions as its summary, and returns one entry per peer **in the peers'
order** (inventory order — sorted by name, deterministic). A peer that fails
to answer still gets its row, with an empty summary: the catalog never omits a
live-inventory service and never fails as a whole. Summaries are fetched live
precisely so the catalog can never drift from what the services say about
themselves — the anti-drift rule that forbids hard-coded per-service prose
(D19) applies to catalog summaries too.

`InstructionLister` is the one-method seam (`Instructions(ctx) (string,
error)`) satisfied by `*mcpclient.Client`; tests satisfy it with fakes and
drive the real client against `httptest` peers where the wire matters.

## Rejected

- **`agentkit.MCPServer` attachments (the previous shape of this Decision)** —
  eager attachment serializes every peer tool schema into every round-trip
  (~90% of a run's starting context, measured cross-provider, research §1) and
  fails the whole run when any single peer is down at spawn. Both costs were
  accepted only because agentkit had closed the deferral route; the gateway
  reopens progressive discovery without agentkit's help, so the price no
  longer buys anything.
- **A static name→summary map in prompts** — hard-coded per-service prose is
  exactly the drift D19's framing rule forbids: a renamed or newly deployed
  service silently gets stale or missing text. The services' own instructions
  are the single source; fetching them live is ~13 parallel loopback calls
  measured in milliseconds.
- **Names-only catalog (no summaries)** — cheaper, but the cross-model
  experiment (research §7) steered every model through name+summary rows, and
  summaries are what disambiguate `repos` from `github` without burning an
  exploratory `suite_tools` call.
- **Tool counts in the catalog** — would require a `tools/list` fan-out per
  catalog call and carried no observed weight in the experiment.
- **Failing the catalog when a peer is down** — reintroduces spawn-time
  fragility the gateway exists to remove; a name-only row degrades gracefully
  and `suite_tools`/`suite_call` against that peer report the real error.

## Verification

- R-ORZ1-QIWX — `Discover` called with an inventory holding two non-`prompts`
  services and a `prompts` self entry returns exactly two `Peer` values, each
  `Name` the bare service name, each `BaseURL` that service's registry
  loopback `/mcp` address, and no entry for `prompts`; every `Headers` map
  carries `X-Owner-Id`, `X-Owner-Email`, and `X-Client-Id` equal to
  `"prompts:" + promptID`. A build forwarding only `X-Owner-Email` fails this
  (id-gated peers would 401).
- R-OT6Y-4ANM — `Catalog` over two peers whose instructions begin with known
  multi-sentence texts returns rows in peer order whose `Summary` is exactly
  each text's first sentence — not the whole instructions block (the
  discriminating property against dumping full instructions into the
  catalog).
- R-OUEU-I2EB — `Catalog` over two peers where one refuses connections
  returns **both** rows — the dead peer's with `Name` intact and `Summary`
  empty — and returns no error. A build that dropped the row or failed the
  catalog fails this.
