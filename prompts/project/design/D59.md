# Decision 59 — Retiring the content columns

## Decision

Once the seeding pass (D54) has moved every prompt's definition into the
version plane and the read and write paths go through it (D53, D55), the
`prompts` table's three content columns are dead weight that can only disagree
with the truth. This Decision removes them — **last in the sequence, and
additively**.

One new timestamped migration, minted with `bin/create-migration prompts
<name>`:

```sql
ALTER TABLE prompts DROP COLUMN user_prompt;
ALTER TABLE prompts DROP COLUMN system_prompt;
ALTER TABLE prompts DROP COLUMN config_json;
```

`ALTER TABLE … DROP COLUMN` (SQLite 3.35+) **preserves every row**. The table is
not rebuilt and no data is copied: prompts holds production data, so a
drop-and-recreate is not available here the way it was during the migration
window D36 worked in. Nothing else in the schema changes; `name`, `name_key`,
`source_path`, the owner columns, and the timestamps stay.

**Ordering is the safety argument, and it is a plan constraint, not a comment.**
The seeding phase must be built, run, and green before this migration is
written; the content exists in both places for that interval, and the columns
are dropped only once the plane demonstrably holds them. A build loop that ran
this phase first would destroy the only copy.

**The domain follows.** `Prompt` drops `UserPrompt`, `SystemPrompt`, and
`Config`, keeping only metadata; the definition travels as `Executed` (D40),
returned by `Get`/`LoadFromPrompt` from the plane and by `RunExecuted` from the
run's clone. `Store` methods stop reading or writing the three columns, and
`InsertPrompt`/`UpdatePrompt` become metadata writes.

## Rejected

**Dropping the columns in the same migration that adds `name_key`.** It puts
the destructive step before the pass that copies the data. Two migrations, in
plan order, with a proven seeding in between.

**Rebuilding the table (`CREATE new; INSERT SELECT; DROP; RENAME`).** The
conventional pre-3.35 pattern, and here it is a full copy of production rows
for a change `DROP COLUMN` does in place. Every row copied is a row that can be
lost.

**Leaving the columns in place, unused.** They would be read by the next person
who greps for `user_prompt`, and they would drift from the repository the first
time anyone pushes from a laptop. A superseded column that still holds
plausible-looking data is a trap.

**Keeping `config_json` as a denormalized copy so validation can run without a
plane read.** Validation runs on the config the *caller* supplied, at
create/update time, before the commit — it never needs the stored copy.

## Verification

(Real substrate: a temp-file SQLite database seeded with prompt rows through
the real `Store`, then advanced by the appkit migration runner over the full
embedded migration set.)

- R-SE0O-ZSWV — after the full migration set is applied to a database holding
  three prompt rows, `PRAGMA table_info(prompts)` reports **no**
  `user_prompt`, `system_prompt`, or `config_json` column, and **all three rows
  are still present** with their ids, names, name keys, source paths, and
  timestamps unchanged. The row-preservation half is the discriminating
  property: a drop-and-recreate migration satisfies the column assertions and
  fails this.
- R-SF8L-DKNK — with the columns gone, `Get` on a prompt returns its user
  prompt, system prompt, and config read from the version plane (observed
  through a recording fake client issuing exactly one `Read(nameKey, "main")`),
  and a source scan finds the identifiers `user_prompt`, `system_prompt`, and
  `config_json` in **no** non-test Go source (excluding `project/` and the
  frozen migration files, whose committed bodies are immutable). A build that
  drops the columns but leaves the store reading them fails to compile or fails
  the scan.
