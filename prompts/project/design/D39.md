# Decision 39 — The run directory is durable state, and holds the whole run

## Decision

A run's on-disk artifacts live under the service's **durable state tree** in one directory per run, and that directory holds everything the run produced:

```
<stateDir>/runs/<run_id>/
    input/            # config.json, user_prompt.txt, system_prompt.txt, event.json
    output.jsonl      # the agentkit LogRecord log
    sandbox/          # the run's working directory
```

`<stateDir>` is `filepath.Dir(PROMPTS_DB_PATH)` — the same tree that already holds `prompts.db` and `auth.json`, chowned to the service and never touched by deploy. On the box that is `/opt/prompts/state/runs/<run_id>/`.

**Two defects are corrected by this.**

*The run directory was scratch.* `cmd/prompts/main.go` derived `runsDir` from the **generation cache** (`filepath.Join(filepath.Dir(generationPath), "runs")`) and called `recreateRunsDir`, which does `os.RemoveAll` on it at **every service start**. Both the pinned inputs and `output.jsonl` were therefore destroyed on every restart, deploy, and reboot, while the `runs` rows that point at them survived in the database. The observable result was a run row whose output and executed prompt had silently vanished — the record pointing at nothing. `runner.go`'s description of `input/` as "the immutable record of exactly what this run executes" was true only within one process lifetime. `recreateRunsDir` is deleted outright; nothing prunes run directories.

*A run was split across two trees.* Sandboxes already lived in durable state at `<stateDir>/sandboxes/<run_id>/` while inputs and output lived in cache, so one run was two half-records with two lifetimes, keyed by the same id. The sandbox moves under the run directory so a run is one directory. `sandbox.New` is rooted at `<stateDir>/runs` and resolves a run's root as `<run_id>/sandbox`; nothing else about sandbox confinement changes.

**Nothing is reclaimed automatically.** Run directories accumulate until explicitly deleted (D41). No retention window, no pruning pass, no size cap. This is deliberate for now: the alternative is a policy with a default that silently destroys production records, and the box has no evidence yet about what growth actually looks like.

**No migration path.** Existing run directories are not moved and existing `runs` rows are not rewritten, because there are none: the box's prompts, runs, calls, and sandboxes were deleted before this Decision was sealed. A run row predating this change would point at a cache path that no longer exists, which is indistinguishable from the pre-existing defect and needs no special handling.

## Rejected

**Leave `runs/` in cache and accept the loss** — rejected: it makes every run row a dangling pointer after the next restart, and the product now promises that a run's record survives indefinitely. A record that outlives what it describes is worse than no record.

**Keep `runs/` in cache but stop deleting it on boot** — rejected: the generation cache is by definition reclaimable, and a future cache-clearing step (a deploy, an operator, a disk-pressure hook) would take the run history with it. Durability belongs in the tree whose contract is durability.

**Move inputs and output to durable state but leave `sandboxes/` where it is** — rejected: it keeps a run split across two sibling trees with the same key, so deletion (D41) has to remember both, and any future per-run operation has to as well. One run, one directory.

**Add a retention window now (age out run directories after N days)** — rejected as scope: it is a product promise about destroying customer data, it needs a default nobody has evidence for, and the `calls` table already carries its own separately-specified retention for bodies. Deletion is explicit until there is a reason for it not to be.

**Store `output.jsonl` in the database instead** — rejected: it is an append-only log of unbounded size written during the run; SQLite is the wrong shape and the streaming write is the point.

## Verification

- R-ZMJ5-6QEW — after a run completes, `<stateDir>/runs/<run_id>/` exists and contains `input/config.json`, `input/user_prompt.txt`, `input/system_prompt.txt`, `output.jsonl`, and `sandbox/`; the path is under the directory holding the database file, and no run artifact exists under the generation-cache directory. A build that still derived the runs directory from the cache path fails the last clause.
- R-ZNR1-KI5L — a run's directory and every file in it survive a service restart: with a completed run on disk, running the composition root's startup a second time against the same state directory leaves `input/`, `output.jsonl`, and `sandbox/` byte-identical, and `run_output` returns the same content afterwards. A build retaining `recreateRunsDir` deletes the tree and fails this — the discriminating property, since a test that only checked the path would pass on a boot-scratch implementation.
