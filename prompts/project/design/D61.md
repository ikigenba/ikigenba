# Decision 61 — Patch-semantics `update`: omitted means unchanged, and no empty prompt is ever stored

## Decision

`update` adopts the suite's edit-tool merge contract
(`root project/design/D27.md`): **an omitted field is unchanged; a sent field is
intentional.** This replaces the shipped full-replacement shape, under which an
update sending only a config blanked `user_prompt` to `""` (surfacing two calls
later as an agentkit failure at run start) and an omitted `name` derived a bogus
uppercase name key that routed through the plane's `Rename` and failed with a
repos validation error. Both defects fall out of one representational fix:
distinguishing *omitted* from *present* end to end.

**The input carries presence.** `prompt.UpdateInput` moves to pointer fields —
`nil` is omitted, non-nil is sent:

```go
type UpdateInput struct {
    Name         *string // nil: keep; "": clear to unnamed (ULID-derived key)
    UserPrompt   *string // nil: keep; ""/whitespace-only: validation error
    SystemPrompt *string // nil: keep; "": clear (plane Delete of system.md)
    Config       *Config // nil: keep; non-nil: whole-value replace, validated
}
```

The MCP tool handler parses its arguments into the same pointer shape, so
JSON-absent and JSON-empty stay distinct from the wire to the store. The
`update` input schema is unchanged (`prompt_id` required, everything else
optional — D9's config schema included); what changes is what optional *means*,
and the tool description now says it (below).

**Merge, then validate, then write.** `Service.Update` reads the current
definition (the plane's `Read(nameKey, "main")` plus the row's name — the same
read D53 already makes), overlays the sent fields per the rules above, and
validates the **result**: the effective config through `ValidateConfig` (D3,
unchanged — a nil `Config` still validates the *current* stored config, so a
config that has become invalid against a changed environment still surfaces),
and the effective user prompt through the non-empty rule below. Only then does
it commit changed files and write the row (D53's mechanics, unchanged). An
omitted name derives no key and triggers no rename; a sent name that derives a
new key is a rename (D53); a sent empty name clears to the unnamed state —
`NameKey("", id)`'s ULID-derived key — via the same rename path, because
unnamed is a state `create` can express and `update` must be able to reach.

**No empty prompt, at any door.** A prompt whose effective `user_prompt` is
empty or whitespace-only can never run, so no writer may store one — fail
loudly, fail early, at the edge:

- `create` rejects an empty/whitespace `user_prompt` with a `ValidationError`
  before inserting anything.
- `update` rejects a sent empty/whitespace `user_prompt` the same way, before
  any plane call or row write.
- `import` rejects a fetched mirror file that is empty or whitespace-only,
  alongside its existing UTF-8 and 1 MiB guards, before any plane call or
  adoption upsert — a prior imported definition stays intact.

The run path stays trusting (validate at boundaries): with all three writers
guarded, no stored prompt can be empty, and no belt-and-suspenders check is
added at run start.

**The description states the merge rule** (the D27 description discipline, in
D20's Tier 1). The `update` tool's description carries, verbatim in spirit:
*"Any field omitted is left unchanged — send only what you want to change.
`config` is replaced whole when sent (keys omitted from a sent config reset to
defaults). An empty `system_prompt` or `name` clears it; `user_prompt` cannot
be emptied."* The `create` description is untouched except that `user_prompt`
must be non-empty.

## Rejected

**Keep replace semantics and mark every field required.** Honest, but it makes
a config bump resend the whole prompt body, punishes the suite's normal caller
(an agent editing one field), and diverges from the merge contract every other
edit-shaped tool in the suite already follows (crm `save`, scripts `update`).

**Reject an explicit empty `name` instead of clearing.** It would make the
unnamed state reachable only at create — a state you can enter but never
return to. The rename machinery the clear needs already exists (D53); the
asymmetry would need a footnote forever.

**A sentinel value (e.g. `"-"`) to mean clear.** Magic strings in a typed
surface; pointers already carry presence, and JSON already distinguishes
absent from empty.

**Guarding the run path too.** With every writer validating, a stored empty
prompt is unreachable; a run-time re-check would be the defensive re-validation
of internal state the suite's principles reject.

## Verification

(Substrate: the real `prompt.Service` and `Store` over a temp-file SQLite
database through the real migration runner, with a recording fake
`version.Client` — as D53. The description behavior is asserted on the real
`toolDescriptors()` table, as D9.)

- R-A8EU-5VUL — `update` sending **only** a config leaves the stored row's
  name and name key unchanged, issues **zero** `Rename` calls, and issues
  exactly one `Commit` whose batch is exactly `["config.json"]` (no
  `prompt.md`, no `system.md`); conversely `update` sending only a
  `user_prompt` issues one `Commit` whose batch is exactly `["prompt.md"]`,
  leaving the stored config readable and equal to its prior value. A build
  that blanks omitted fields, or derives a name key from an omitted name,
  fails one half or the other.
- R-A9MQ-JNLA — `update` sending `user_prompt` as `""` (and separately as
  whitespace-only) returns a `ValidationError`, issues zero `Commit` and zero
  `Rename` calls, and leaves the definition readable and unchanged.
- R-AAUM-XFBZ — `update` sending `name: ""` on a named prompt issues exactly
  one `Rename(oldKey, <ULID-derived key>)` and afterwards the row's name is
  empty and its name key is the ULID-derived key; the definition files are
  uncommitted (name-only update commits nothing).
- R-AC2J-B72O — `create` with an empty (and separately whitespace-only)
  `user_prompt` returns a `ValidationError`, no prompt row exists afterwards,
  and the fake plane records zero `Create` and zero `Commit` calls.
- R-ADAF-OYTD — `import` of a mirror file whose fetched bytes are empty (and
  separately whitespace-only) returns an error, issues zero plane calls, and a
  previously imported definition for another path remains readable and
  unchanged.
- R-AEIC-2QK2 — the `update` tool descriptor returned by `toolDescriptors()`
  has a description containing both `omitted` and `unchanged` (the stated
  merge rule), and the `create` tool descriptor's schema still lists
  `user_prompt` and `config` as required. A build that fixes semantics but
  ships the old description fails.
