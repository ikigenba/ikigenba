# Decision 29 — The completion queue: durable handoff for sibling-service inference

## Decision

prompts' second workload class — stateless, tool-less completions for sibling daemons — is a **durable work queue**, not a synchronous call. A consumer *submits* a fully-described unit of inference work and is answered immediately; prompts owns the item durably until the consumer collects the result and acknowledges it. **No verb on this surface ever waits on inference.** The prior synchronous `POST /complete` request/response is expunged: holding an HTTP connection open across a model call raced the chassis's 15 s write deadline and silently severed responses the handler believed it had sent — the synchronous concept was wrong, not merely mis-tuned.

Like its predecessor, the surface is loopback-only plumbing in the `/feed`/`/run-content` tier — mounted via `rt.HandleLoopback`, no identity headers, never routed by nginx. It is deliberately not MCP: `/mcp` is the product surface for agents; this is infrastructure for daemons.

### The item

A queue item belongs to a **consumer** — the collecting service, `^service:[a-z0-9._-]+$`, e.g. `service:wiki` — and is identified within that consumer by a consumer-constructed, opaque **idempotency key**. The item separately carries an **origin** with unchanged D28 attribution semantics (*who caused* the work — `user:<email>`, `trigger:<source>`, or `service:<name>`), stamped on every `calls` row the item produces; partitioning is the consumer's, attribution is the origin's, and the two are deliberately distinct fields. It carries an opaque **context** envelope the consumer will need to apply the result — **on the wire, `context` is an arbitrary JSON value** (an object, array, string, number — whatever shape the consumer's envelope takes), decoded as raw JSON, never as a Go string. prompts validates only that it is well-formed JSON when present, stores its serialized bytes, and echoes exactly those bytes back at every read, never interpreting them; an omitted `context` is stored empty and reads back as `null`. (The type is contractual: the first integration failed precisely because prompts declared `context` a JSON *string* while its consumer sent the envelope *object* both specs described.) The inference payload is the existing completion vocabulary unchanged (D28 name grammar, D2/D3 config keys, `system`, role/text `messages` with a final `user` turn).

The `completions` table carries the columns below. The **ownership columns** (`owner`, `lease_expires_at`, `reclaims`) arrive in a second timestamped migration (`bin/create-migration prompts add-completion-lease`); committed migrations are immutable, so the original `create-completions` migration is never edited.

```sql
CREATE TABLE completions (
  id           TEXT PRIMARY KEY,            -- ULID (internal/ids)
  consumer     TEXT NOT NULL,               -- collecting service (^service:… ), the partition key
  origin       TEXT NOT NULL,               -- D28 origin grammar (attribution: who caused the work)
  key          TEXT NOT NULL,               -- consumer-constructed idempotency key, opaque
  context      TEXT NOT NULL DEFAULT '',    -- serialized JSON value (consumer envelope), echoed byte-verbatim; '' = absent
  name         TEXT NOT NULL,               -- D28 name grammar
  group_id     TEXT NOT NULL DEFAULT '',
  correlation_id TEXT NOT NULL DEFAULT '',  -- D44 chain id captured at submission
  attempt      INTEGER NOT NULL DEFAULT 1,  -- the CONSUMER's attempt number, echoed to calls rows
  request      TEXT NOT NULL,               -- marshaled inference payload; written once, never updated
  status       TEXT NOT NULL CHECK (status IN ('queued','running','done','failed')),
  owner        TEXT NOT NULL DEFAULT '',    -- executing process epoch (ULID); '' when unclaimed
  lease_expires_at TEXT NOT NULL DEFAULT '',-- RFC3339 UTC; the claim is void past this instant
  reclaims     INTEGER NOT NULL DEFAULT 0,  -- times a lease expired without renewal or release
  result       TEXT NOT NULL DEFAULT '',    -- the unwrapped envelope `result` JSON value (done only)
  error        TEXT NOT NULL DEFAULT '',    -- failure reason (failed only)
  error_code   TEXT NOT NULL DEFAULT '',    -- the machine-readable code beside `error`
  usage_json   TEXT NOT NULL DEFAULT '',    -- aggregate agentkit Usage across executed round trips
  cost_usd     REAL NOT NULL DEFAULT 0,
  created_at   TEXT NOT NULL,               -- RFC3339 UTC
  started_at   TEXT NOT NULL DEFAULT '',
  finished_at  TEXT NOT NULL DEFAULT ''
);
CREATE UNIQUE INDEX completions_consumer_key ON completions (consumer, key);
CREATE INDEX completions_status_created ON completions (status, created_at);
CREATE INDEX completions_consumer_status ON completions (consumer, status, created_at);
CREATE INDEX completions_lease ON completions (status, lease_expires_at);
```

### Lifecycle

`queued → running → done | failed`. Contractual constants:

- **Runtime bound: 4 hours.** The one inference timeout. The executor runs each item under a 4 h context deadline spanning every internal round trip; exceeding it fails the item with a reason naming the bound.
- **Retention: until acknowledged**, plus a **7-day safety TTL** after reaching a terminal state, for consumers that died forever. An hourly sweep deletes only terminal items older than the TTL; `queued`/`running` items are never swept. A terminal result is deleted at the TTL whether or not it was ever collected: a consumer absent longer than a week loses results, which is a stated limit of ack-based retention, not an accident.
- **Ownership is a lease, not a boot sweep.** Liveness is a property of the row, so a restart is not a special case.

#### The lease

`Claim` takes the oldest eligible item that is `queued`, **or** `running` with an expired lease, stamping it with the executor's `owner` and a fresh `lease_expires_at`. The executor **renews** the lease while it holds the item. Reclaiming an expired lease increments `reclaims`; at `reclaims >= 2` the item is **failed** instead of re-queued, with an error naming abandonment, so a poison item that kills its process cannot be re-executed at full model cost forever.

The **owner token is a fresh ULID minted per process start** — never a PID, hostname, or second-granularity timestamp. Two processes colliding on one token would silently degrade every ownership guard below into no guard at all.

**What the lease does and does not bound.** It bounds concurrent *writers*. It does **not** bound concurrent *executions*: a lease can expire while its executor sits inside an outbound provider call, which is a resource SQLite cannot fence, and no renewal-to-TTL ratio closes that window — an executor learns it lost the lease only when a renewal *returns*, and a renewal blocked behind the single shared database connection has not failed, it simply has not returned. **A reclaim may therefore duplicate provider spend, and that is accepted**: the alternative it replaces is an item stranded forever, unreachable by any consumer. The exposure is minimized rather than denied:

- Renewal is **owner-guarded**. Zero rows affected means the lease was **lost**, not that the write should be retried.
- Losing the lease **cancels the execution context**, aborting the in-flight provider stream, rather than merely suppressing the terminal write.
- The executor **re-checks ownership before each corrective round trip**, so an executor that has already lost its item cannot spend three more times.
- Renewal runs under its own short context. An executor that cannot reach the connection abandons *before* expiry and takes the graceful, non-counting path: connection starvation must degrade into a free requeue, never into a failed item. This matters because starvation is systemic rather than random — it recurs, and it correlates with exactly the fan-out load that produces it, so counting it would fail items for being busy.
- The lease TTL is at least **5×** the renewal interval, giving four missed renewals of headroom.

**Graceful shutdown releases every held lease and does not count a reclaim.** Release is guarded on **owner and `status='running'`** and runs on a context that outlives cancellation:

- unguarded by owner, a shutdown release arriving after another worker reclaimed would flip that worker's actively-executing item back to `queued`, admit a third execution, and destroy the reclaimer's paid result;
- unguarded by status, a worker that has just written `done` would flip a terminal row back to `queued` and re-execute completed work;
- on a cancelled context the update fails instantly and the item sits `running` for the whole TTL — the very restart cost the clause exists to prevent.

Shutdown waits for releases to complete before the database handle closes, within a bounded wait. Because release is free, an ordinary deploy costs nothing against the reclaim bound: after any number of clean restarts an item's `reclaims` is still 0.

**There is no boot fast-path** that treats a foreign `owner` as dead on sight. One-box-one-process is a convention nothing enforces — deploy overlap, a second clone or worktree running a stack, a rollback started while the current binary drains, a hand-started debug binary — and such a rule would directly contradict graceful release, which guarantees the outgoing process needs *time* to exit. Items from an unclean exit are waited out like any other expired lease, which costs one TTL of recovery latency after an unclean exit only.

#### Terminal writes

Terminal writes are **asymmetrically** guarded, not symmetrically owner-guarded:

> **`Complete` lands from any owner unless the row is already `done`** — success is last-writer-wins.
> **`Fail` lands only from the current owner**, and never overwrites a `done` — failure is first-writer-wins.

Symmetric guarding would lose paid work: a reclaimer whose provider call fails fast would write `failed` over an item whose original executor is alive and about to succeed, the consumer would see a failure, and the same work would be submitted and paid for again. The asymmetry is sound because `request` is written once at `Ensure` and never updated, so **every execution of a row answers the identical question and any success is a valid answer**. It converts every duplicate-execution ordering from "lose the success you paid for" into "deliver the success you paid for".

A write that loses — a stale owner, or a row that vanished because the consumer acked it mid-execution — is a **logged no-op**, never an error and never an overwrite. The executor never discards a terminal write's error: a store failure is retried a bounded number of times and then logged at error level naming the item, because the money is already spent and the result is the only thing left to save.

**Every terminal path writes `finished_at`**, including the reclaim-bound failure. The sweep requires a non-empty `finished_at`, so a terminal row without one is both unackable and unsweepable and would leak forever in a partition nobody drains.

**Spend accounting under duplication.** `calls` is the authoritative spend surface: every executed round trip inserts its own row, so a duplicated execution is fully recorded there. The item's own `usage_json`/`cost_usd` reflect its **winning execution only**, and the divergence between the two is exactly the duplicated spend. D63 exposes reclaim counts so that divergence is attributable rather than invisible.

### The verbs

1. **Ensure** — `POST /completions`. Validates (below), then inserts the item `queued` and returns `202 {"id","status"}` immediately. When `(consumer, key)` already exists — whatever its state — returns `200` with the existing item's full read shape (result included when terminal) and **executes nothing**: resubmission is always safe and never duplicates spend.
2. **Get** — `GET /completions/{id}?consumer=<consumer>`. One item's read shape: `{"id","consumer","origin","key","context","status","result"?,"error"?,"code"?,"usage"?,"cost_usd"?}` — `context` is the stored JSON value emitted byte-verbatim (`null` when absent). `result` only when `done`; `error`/`code` only when `failed`. An unknown id, **or an id belonging to another consumer**, → `404` — after an ack or the TTL, gone is gone, and a consumer treats it as terminal.
3. **Inbox** — `GET /completions?consumer=<consumer>`. The **terminal, unacknowledged** items for that consumer, oldest-first, each in the full read shape, capped at 100 per response. The response body is a **bare JSON array**, never an object wrapping an `items` field. There is no cursor: a consumer drains by acking and re-reading. A partition nobody drains therefore returns the same oldest 100 until the TTL reaps them, which is accepted.
4. **Ack** — `DELETE /completions/{id}?consumer=<consumer>`. The consumer has durably applied the result; prompts deletes the row. `204` on delete, `404` when already gone **or owned by another consumer** (idempotent from the consumer's view). A later Ensure with the same key is new work.

**`consumer` is a real partition, enforced on every verb.** Get and Ack match on `(id, consumer)`, not on id alone. These are loopback routes shared by every service on the box, so an id-only match would let any service read another service's completion results or ack items out of another service's inbox; a partition enforced on one verb of four is not a partition.

**Ack is otherwise unguarded, and that is stated rather than left implicit.** It deletes an item in any state, so acking a non-terminal item destroys work in flight and orphans a live executor. **Not acking a non-terminal item is the consumer's obligation.** prompts does not refuse the request, because a refusal has no safe landing: a consumer that classifies the refusal as a permanent failure will respond by acking, and an item that can be neither completed nor removed is a worse outcome than the mistake it guards. The terminal-write path therefore tolerates a vanished row as a logged no-op, on the same footing as a stale-owner write.

Delivery is **at-least-once**: an item stays in the inbox until acked, so a consumer that crashes between apply and ack sees it again; applying idempotently is the consumer's stated obligation. Items are independent; no cross-item ordering is guaranteed.

**Validation at Ensure** reuses the existing gate: `prompt.ValidateConfig` over the assembled `{provider, model, config}`, plus envelope checks — consumer grammar (`^service:[a-z0-9._-]+$`), origin and name grammar (D28), non-empty `key` (**≤ 1024 bytes**), `context` — when present — well-formed JSON of any value shape, ≤ 64 KiB serialized, messages non-empty with a final `user` turn, body ≤ 10 MiB. Any failure → `400` with `{"error":"…","code":"…"}` naming the problem: no row, no `calls` row, nothing executed.

The key cap is **1024 bytes, and that is a mitigation rather than a fix**: a rejected Ensure loses whatever work the consumer was submitting, and the cap is the only reason a long key is rejected at all. Raising it makes the wall harder to hit; it does not remove it. **Key length remains the consumer's obligation** — a consumer that constructs keys from unbounded text must bound or digest them itself.

### The failure envelope

Every error response carries a stable, machine-readable `code` **beside** the human-readable `error`, never replacing it or restructuring it. The code vocabulary is a product contractual constant, used here by value and re-declared nowhere.

The rule: **a 4xx is permanent** — no retry can clear it, because the submission itself is what is wrong. **A 5xx is transient** — a retry can clear it, because the condition belongs to the environment.

**Transient means prompts labels the failure; prompts does not retry internally.** An internal retry would interact with both the reclaim bound and the runtime bound while buying nothing a consumer's own collection loop does not already provide. Without the code a consumer's only substrate is flattened status text, which makes a transient store error indistinguishable from a malformed request — and a consumer that guesses "permanent" destroys work that a retry would have saved.

### Execution and the JSON contract

A pool of executor goroutines (pool size = the D31 call cap) claims items and runs them through the same provider path as before (catalog resolve, injected provider factory, D31 `AcquireCall` around every provider round trip, D38 `auth` handling).

**The pool never silently drains.** A worker that meets an error logs it and continues after a backoff; only context cancellation ends a worker, and `Run` returns non-nil only on a context error. A worker that returned permanently on a transient database error would shrink the pool one error at a time until the queue wedged while the process still reported healthy — indistinguishable, from a consumer's side, from a slow model. Errors from the initial reclaim pass at startup stay fatal; only the steady-state loop is resilient.

**A panic fails its own item, not the process.** Each item executes under a recover boundary: without one, a single malformed provider response takes down every item in flight alongside it, and each of those unrelated items comes back with a reclaim charged against it.

**Claim prefers a consumer with no items running**, falling back to global oldest-first FIFO. Under pure FIFO an interactive item submitted behind an N-unit fan-out waits for all N — the delay is a function of queue position, not of pool size, so the concurrency cap does not bound it. The preference is one predicate rather than a scheduling policy: it must exclude consumers with no queued rows, or a consumer with nothing to do would win the preference and block the queue.

**The queue is JSON-in, JSON-out, always.** Every `done` item's `result` is a syntactically valid JSON value. The mechanism: the executor appends a fixed envelope instruction to the request's `system` directing the model to reply with **only**

```json
{"status": "ok" | "error", "result": <any JSON value>, "message": "<why, when error>"}
```

then validates the reply parses as exactly that envelope (one JSON object; `status` ∈ {ok, error}; `result` present when ok; `message` non-empty when error — decoration is tolerated by carving the outermost JSON object before validating). A reply that fails envelope validation triggers an **internal corrective round trip** (the conversation replayed with the bad reply as an assistant turn plus a fixed corrective user turn), up to **3** corrective round trips per item; exhaustion fails the item with a reason naming the envelope. The envelope is internal between prompts and the model — prompts **unwraps** it: `status:"ok"` → item `done` with `result` = the envelope's `result` value; `status:"error"` → item `failed` with `error` = the envelope's `message` (the model's honest "I can't produce what you asked" channel). A provider/stream error (after agentkit's own retry policy) fails the item with the provider error.

**Accounting is unchanged in grain (D28):** every executed provider round trip — the first and each internal corrective — writes one `calls` row, class `completion`, carrying the item's origin/name/group_id/attempt and correlation id, exactly as each call completes. A `calls` insert failure fails the item (D28's fail-loud rule). The item's `usage_json`/`cost_usd` aggregate across the executed round trips of its winning execution.

**Telemetry:** the two read verbs — the inbox `GET /completions` and the poll `GET /completions/{id}` — are listed in the chassis `RecordExclude`, so a consumer's poll loop does not flood the forensic record; Ensure and Ack are recorded normally. The submission's D44/D45 correlation id is captured on the row and stamped on every `calls` row the item produces, so the chain survives the asynchronous gap.

**`POST /complete` is removed** — handler, route, and tests. `POST /embed` (D30) is untouched: an embedding is a sub-second call with no unbounded inference to decouple from, so queue semantics would be machinery without a customer.

**Test seam.** The executor takes the injectable provider-factory (`func(prompt.Config, func(string) string) (agentkit.Provider, error)`); handler- and executor-level tests drive the real HTTP surface and a real (temp) DB with a fake provider scripting envelope-compliant, envelope-violating, erroring, and slow replies. Every timing and identity constant is a **constructor parameter**, so no test waits on wall time and none needs a mock store:

- `NewStore` takes its clock (already) **and the owner token** — an owner derived inside the store cannot be tested.
- `NewExecutor` takes the runtime bound (already), **the lease duration, the renewal interval, an injected clock/ticker seam, and a `*slog.Logger`**. Heartbeat behavior is unprovable without the clock seam except by sleeping, and unprovable without the logger except by inspecting nothing.

Store-level failures are staged against **real** substrate by closing the `*sql.DB` — a genuine SQLite error, not a fake — and log assertions run against a `slog` handler over a buffer.

## Rejected

**The synchronous request/response endpoint (the prior form of this decision)** — a response held open across a model call races the chassis's 15 s `WriteTimeout`; the handler completes and records 200 while the client reads EOF. Observed in production: every consumer `/complete` over ~15 s died this way while every faster call succeeded. Raising the timeout only moves the wall; the handoff removes it.

**"Restart requeues, never fails" — the prior lifecycle rule.** It flipped every `running` row back to `queued` at boot with no bound, so an item that killed its process was re-executed at full model cost on every boot, forever. It also made liveness a property of *boot*: an item stranded by a failed terminal write in a process that keeps running was never recovered at all, because nothing but a restart could move it.

**A per-item execution counter incremented at claim (the first replacement considered).** It counts *claims*, not *abandonments*, so it charges the bound to ordinary restarts and to the items that merely happened to be in flight when some other item panicked. Two deploys inside one runtime bound would permanently fail healthy work. The lease distinguishes an orphan from a live long execution without a wall-clock guess, which is the property the counter cannot supply.

**Failing every `running` item at boot** — the run sweep's rule, one line and no migration. Its cost is that an ordinary deploy fails in-flight four-hour completions. That trade is what earns the lease.

**A wall-clock reaper that fails any `running` row older than the runtime bound plus a grace period.** It cannot distinguish an orphan from a live execution, so it fires against work in progress and overwrites a paid success with a failure — manufacturing the double-spend the lease exists to prevent.

**A heartbeat-free lease set longer than the runtime bound.** It makes recovery from an unclean exit slower than the 4 h bound, which is longer than any plausible consumer deadline: the consumer gives up first, and prompts bills for work already abandoned. The renewal cost it avoids is a handful of small updates per minute.

**A queue-age ceiling that fails items left `queued` too long.** It and a consumer's own job deadline are two uncoordinated timeout ladders where both orderings lose: set short, it fails good never-executed work whenever prompts is merely busy, converting back-pressure into data loss; set long, prompts bills for work the consumer has already given up on. The harm it targeted — items queued forever — is produced by worker death, which the resilient pool fixes at the source.

**Refusing an Ack of a non-terminal item (`409`).** The guard is correct in isolation and wrong in composition: a refusal has no safe landing, because a consumer that reads it as permanent responds by acking, and an item that can be neither completed nor removed re-heads an oldest-first inbox forever. The obligation is stated on the consumer instead.

**Symmetric owner-guarding of terminal writes.** It discards a paid success whenever a reclaimer's own attempt fails first. The asymmetric rule delivers the success instead, and is safe because `request` is immutable.

**A boot fast-path treating a foreign owner as dead.** "One box, one process" is a convention nothing enforces, and the rule contradicts graceful release, which guarantees an outgoing process takes time to exit. Keeping it would require an OS-level advisory lock to *prove* exclusivity; waiting the lease out costs one TTL after an unclean exit only.

**An ack tombstone — retaining an acked key so a later Ensure dedupes against it.** Consumers depend on ack-deletes-the-key: an ack means the work is durably applied, and a re-Ensure of the same key afterwards is deliberately new work. A tombstone would silently turn a legitimate resubmission into a no-op.

**A fair-share or QoS scheduling layer over the queue** — priorities, budgets, per-consumer quotas. D31 rejected this class for the same reason it is rejected here: no evidence demands it on a one-owner box, and `calls` makes any backlog visible. The claim preference above is deliberately the cheapest discriminating form — one predicate over the existing FIFO — and not the beginning of a scheduler. Revisit only against a measured starvation.

**Internal retry of transient failures.** It interacts with both the reclaim bound and the runtime bound, and duplicates a loop the consumer already runs. Labelling is the whole obligation.

**A forced structured-output tool (`tool_choice`-forced result tool, or provider-native JSON schema)** — the preferred enforcement mechanism, blocked on capability: agentkit's `GenSettings` exposes no tool choice, and its OpenAI-compat layer hardwires `tool_choice:"auto"`. Revisit when agentkit grows forced tool choice; the contract to consumers would not change.

**Consumer-supplied JSON Schemas per item** — consumers must semantically validate `result` anyway, so per-item schema plumbing buys little and complicates the surface.

**Results over the event plane** — the outbox retains by time horizon and row backstop, not by consumption: a consumer down past the horizon loses results forever while its jobs wait on them. Ack-based retention is the point.

**`context` as a JSON string** — typing the field `string` forces every consumer to marshal, string-encode, and double-decode an envelope prompts never inspects; it is exactly the reading that broke the first integration.

**Lease/claim semantics on the inbox** — the *read* side needs no lease: one consumer per partition, single-flight inbox loops. Plain list + per-item ack. (The execution-side lease above is a different mechanism on a different verb.)

**A cursor on the inbox.** The cap is a page, not a backlog limit, and a consumer that acks what it reads always advances. A cursor would add a paging protocol to serve only the case of a partition nobody drains, which the TTL already ends.

**Long-polling or SSE on the read verbs** — a held response walks back into the write-deadline race in miniature; interval polling against `RecordExclude`-ed loopback GETs costs microseconds.

**Streaming responses / an MCP surface / a stored template entity** — rejected before for reasons the queue does not disturb.

- R-JA69-7AVC — Ensure with an out-of-catalog model, a malformed consumer/origin/name, an empty `key`, an empty `messages`, or a final non-`user` turn returns `400` naming the problem, and neither `completions` nor `calls` gains a row.

- R-JF1U-QDU4 — A reply envelope with `status:"error"` fails the item with `error` equal to the envelope's `message`, and no `result` is stored.
- R-JG9R-45KT — A provider/stream failure fails the item with the provider error in `error`; the `calls` row records the same error with class/origin/name intact.
- R-JHHN-HXBI — An item still executing when the configured runtime bound elapses (tiny bound + slow fake provider) fails with `error` naming the bound; the executor never leaves it `running` past the bound.
- R-JJXG-9GSW — Get returns the item's current shape at every stage — `queued`/`running` with no result, `done` with `result`/`usage`/`cost_usd` and the verbatim `context`, `failed` with `error` — and `404` for an unknown id.
- R-JL5C-N8JL — Inbox returns exactly the requesting consumer's **terminal** items, oldest-first, each carrying `key`, verbatim `context`, and `result`/`error`; another consumer's items and `queued`/`running` items never appear.

- R-JOT1-SJRO — The retention sweep deletes a terminal item whose `finished_at` is older than the 7-day TTL, and retains both a younger terminal item and any `queued` item regardless of age (injected clock); an item reaped to a terminal state by the reclaim bound carries a non-empty `finished_at` and is therefore deleted by the same rule once it ages past the TTL.
- R-JQ0Y-6BID — Every queue verb is mounted through the chassis loopback guard: a loopback request carrying no `X-Owner-Email` header succeeds on all four verbs.
- R-JR8U-K392 — The server's `RecordExclude` contains exactly the two read paths (`/completions` GETs); the composition wiring passes them so inbox and item polls produce no telemetry request records while Ensure and Ack do.
- R-JSGQ-XUZR — `POST /complete` no longer exists: the route returns `404` and no handler for it remains in the binary (the synchronous endpoint is expunged).
- R-U7PZ-0AIV — `context` is a JSON value end to end: an Ensure whose `context` is a JSON **object** (and one whose is an array) is accepted with `202`, and every read of the item — Get at a non-terminal stage, Get when terminal, and the inbox row — emits the stored `context` **byte-identical** to the submitted serialization; an Ensure that omits `context` reads back `"context": null` (never `""` and never a JSON-encoded string wrapping the value).
- R-U8XV-E29K — An Ensure whose `context` field is not well-formed JSON fails the body decode with `400` naming the problem, and neither `completions` nor `calls` gains a row.
- R-ZJKL-8UQY — Claiming an item whose lease has expired returns it to execution under the new owner and increments `reclaims` by exactly 1 (injected clock, two distinct owner tokens, real temp SQLite).
