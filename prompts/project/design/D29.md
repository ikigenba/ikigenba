# Decision 29 — The completion queue: durable handoff for sibling-service inference

## Decision

prompts' second workload class — stateless, tool-less completions for sibling daemons — is a **durable work queue**, not a synchronous call. A consumer *submits* a fully-described unit of inference work and is answered immediately; prompts owns the item durably until the consumer collects the result and acknowledges it. **No verb on this surface ever waits on inference.** The prior synchronous `POST /complete` request/response is expunged: holding an HTTP connection open across a model call raced the chassis's 15 s write deadline and silently severed responses the handler believed it had sent — the synchronous concept was wrong, not merely mis-tuned.

Like its predecessor, the surface is loopback-only plumbing in the `/feed`/`/run-content` tier — mounted via `rt.HandleLoopback`, no identity headers, never routed by nginx. It is deliberately not MCP: `/mcp` is the product surface for agents; this is infrastructure for daemons.

### The item

A queue item belongs to a **consumer** — the collecting service, `^service:[a-z0-9._-]+$`, e.g. `service:wiki` — and is identified within that consumer by a consumer-constructed, opaque **idempotency key**. The item separately carries an **origin** with unchanged D28 attribution semantics (*who caused* the work — `user:<email>`, `trigger:<source>`, or `service:<name>`), stamped on every `calls` row the item produces; partitioning is the consumer's, attribution is the origin's, and the two are deliberately distinct fields. It carries an opaque **context** envelope the consumer will need to apply the result — **on the wire, `context` is an arbitrary JSON value** (an object, array, string, number — whatever shape the consumer's envelope takes), decoded as raw JSON, never as a Go string. prompts validates only that it is well-formed JSON when present, stores its serialized bytes, and echoes exactly those bytes back at every read, never interpreting them; an omitted `context` is stored empty and reads back as `null`. (The type is contractual: the first integration failed precisely because prompts declared `context` a JSON *string* while its consumer sent the envelope *object* both specs described — the 2026-08-11 local verification, every wiki ingest 400-ing at handoff.) The inference payload is the existing completion vocabulary unchanged (D28 name grammar, D2/D3 config keys, `system`, role/text `messages` with a final `user` turn).

New table, one timestamped migration (`bin/create-migration prompts create-completions`), owned by a new **`internal/completion`** package:

```sql
CREATE TABLE completions (
  id           TEXT PRIMARY KEY,            -- ULID (internal/ids)
  consumer     TEXT NOT NULL,               -- collecting service (^service:… ), the partition key
  origin       TEXT NOT NULL,               -- D28 origin grammar (attribution: who caused the work)
  key          TEXT NOT NULL,               -- consumer-constructed idempotency key, opaque
  context      TEXT NOT NULL DEFAULT '',    -- serialized JSON value (consumer envelope), echoed byte-verbatim; '' = absent
  name         TEXT NOT NULL,               -- D28 name grammar
  group_id     TEXT NOT NULL DEFAULT '',
  correlation_id TEXT NOT NULL DEFAULT '',  -- D44 chain id captured at submission
  attempt      INTEGER NOT NULL DEFAULT 1,  -- the CONSUMER's attempt number, echoed to calls rows
  request      TEXT NOT NULL,               -- marshaled inference payload (model/provider/config/system/messages)
  status       TEXT NOT NULL CHECK (status IN ('queued','running','done','failed')),
  result       TEXT NOT NULL DEFAULT '',    -- the unwrapped envelope `result` JSON value (done only)
  error        TEXT NOT NULL DEFAULT '',    -- failure reason (failed only)
  usage_json   TEXT NOT NULL DEFAULT '',    -- aggregate agentkit Usage across executed round trips
  cost_usd     REAL NOT NULL DEFAULT 0,
  created_at   TEXT NOT NULL,               -- RFC3339 UTC
  started_at   TEXT NOT NULL DEFAULT '',
  finished_at  TEXT NOT NULL DEFAULT ''
);
CREATE UNIQUE INDEX completions_consumer_key ON completions (consumer, key);
CREATE INDEX completions_status_created ON completions (status, created_at);
CREATE INDEX completions_consumer_status ON completions (consumer, status, created_at);
```

### Lifecycle

`queued → running → done | failed`. Contractual constants:

- **Runtime bound: 4 hours.** The one timeout. The executor runs each item under a 4 h context deadline spanning every internal round trip; exceeding it fails the item with a reason naming the bound.
- **Retention: until acknowledged**, plus a **7-day safety TTL** after reaching a terminal state, for consumers that died forever. An hourly sweep deletes only terminal items older than the TTL; `queued`/`running` items are never swept.
- **Restart requeues, never fails.** On boot, `running` items return to `queued` and re-execute — completions are stateless, so re-execution is safe. (This is deliberately the opposite of the run sweep's mark-failed: a run's sandbox state is unrecoverable; a completion's input is fully in its row.)

### The verbs

1. **Ensure** — `POST /completions`. Validates (below), then inserts the item `queued` and returns `202 {"id","status"}` immediately. When `(consumer, key)` already exists — whatever its state — returns `200` with the existing item's full read shape (result included when terminal) and **executes nothing**: resubmission is always safe and never duplicates spend.
2. **Get** — `GET /completions/{id}`. One item's read shape: `{"id","consumer","origin","key","context","status","result"?,"error"?,"usage"?,"cost_usd"?}` — `context` is the stored JSON value emitted byte-verbatim (`null` when absent). `result` only when `done`; `error` only when `failed`. Unknown id → `404` — after an ack or the TTL, gone is gone, and a consumer treats it as terminal.
3. **Inbox** — `GET /completions?consumer=<consumer>`. The **terminal, unacknowledged** items for that consumer, oldest-first, each in the full read shape, capped at 100 per response (drain by repeating). `queued`/`running` items and other consumers' items never appear.
4. **Ack** — `DELETE /completions/{id}`. The consumer has durably applied the result; prompts deletes the row. `204` on delete, `404` when already gone (idempotent from the consumer's view). A later Ensure with the same key is new work.

Delivery is **at-least-once**: an item stays in the inbox until acked, so a consumer that crashes between apply and ack sees it again; applying idempotently is the consumer's stated obligation. Items are independent; no cross-item ordering is guaranteed.

**Validation at Ensure** reuses the existing gate: `prompt.ValidateConfig` over the assembled `{provider, model, config}`, plus envelope checks — consumer grammar (`^service:[a-z0-9._-]+$`), origin and name grammar (D28), non-empty `key` (≤ 256 bytes), `context` — when present — well-formed JSON of any value shape, ≤ 64 KiB serialized (malformed JSON there fails the whole body decode → `400`, exactly like any other malformed field), messages non-empty with a final `user` turn, body ≤ 10 MiB. Any failure → `400` with `{"error":"…"}` naming the problem: no row, no `calls` row, nothing executed.

### Execution and the JSON contract

A pool of executor goroutines (pool size = the D31 call cap) claims the oldest `queued` item (`UPDATE … SET status='running', started_at=… WHERE id = (oldest queued)` — single-writer SQLite makes the claim race-free), then runs it through the same provider path as before (catalog resolve, injected provider factory, D31 `AcquireCall` around every provider round trip, D38 `auth` handling).

**The queue is JSON-in, JSON-out, always.** Every `done` item's `result` is a syntactically valid JSON value. The mechanism: the executor appends a fixed envelope instruction to the request's `system` directing the model to reply with **only**

```json
{"status": "ok" | "error", "result": <any JSON value>, "message": "<why, when error>"}
```

then validates the reply parses as exactly that envelope (one JSON object; `status` ∈ {ok, error}; `result` present when ok; `message` non-empty when error — decoration is tolerated by carving the outermost JSON object before validating). A reply that fails envelope validation triggers an **internal corrective round trip** (the conversation replayed with the bad reply as an assistant turn plus a fixed corrective user turn), up to **3** corrective round trips per item; exhaustion fails the item with a reason naming the envelope. The envelope is internal between prompts and the model — prompts **unwraps** it: `status:"ok"` → item `done` with `result` = the envelope's `result` value; `status:"error"` → item `failed` with `error` = the envelope's `message` (the model's honest "I can't produce what you asked" channel). A provider/stream error (after agentkit's own retry policy) fails the item with the provider error.

**Accounting is unchanged in grain (D28):** every executed provider round trip — the first and each internal corrective — writes one `calls` row, class `completion`, carrying the item's origin/name/group_id/attempt and correlation id, exactly as each call completes. A `calls` insert failure fails the item (D28's fail-loud rule). The item's `usage_json`/`cost_usd` aggregate across its executed round trips.

**Telemetry:** the two read verbs — the inbox `GET /completions` and the poll `GET /completions/{id}` — are listed in the chassis `RecordExclude`, so a consumer's poll loop does not flood the forensic record; Ensure and Ack are recorded normally. The submission's D44/D45 correlation id is captured on the row and stamped on every `calls` row the item produces, so the chain survives the asynchronous gap.

**`POST /complete` is removed** — handler, route, and tests. `POST /embed` (D30) is untouched: an embedding is a sub-second call with no unbounded inference to decouple from, so queue semantics would be machinery without a customer.

**Test seam:** as before, the executor takes the injectable provider-factory (`func(prompt.Config, func(string) string) (agentkit.Provider, error)`); handler- and executor-level tests drive the real HTTP surface and a real (temp) DB with a fake provider scripting envelope-compliant, envelope-violating, erroring, and slow replies. The runtime bound is a constructor parameter (production value 4 h) so a test can prove it with a tiny bound.

## Rejected

**The synchronous request/response endpoint (the prior form of this decision)** — a response held open across a model call races the chassis's 15 s `WriteTimeout`; the handler completes and records 200 while the client reads EOF. Observed in production: every wiki `/complete` over ~15 s died this way while every faster call succeeded. Raising the timeout only moves the wall; the handoff removes it.

**A forced structured-output tool (`tool_choice`-forced result tool, or provider-native JSON schema)** — the preferred enforcement mechanism, blocked on capability: agentkit's `GenSettings` exposes no tool choice, and its OpenAI-compat layer hardwires `tool_choice:"auto"` (some routed providers cannot force at all — `WarnToolChoiceForced` exists precisely to report that degradation). Revisit when agentkit grows forced tool choice; the contract to consumers would not change.

**Consumer-supplied JSON Schemas per item** — consumers must semantically validate `result` anyway, so per-item schema plumbing buys little and complicates the surface; the fixed envelope keeps prompts' guarantee simple (valid JSON, honest error channel) and leaves shape judgment where the domain knowledge lives.

**Results over the event plane** — the outbox retains by time horizon and row backstop, not by consumption: a consumer down past the horizon loses results forever while its jobs wait on them, which is exactly the loss class this redesign closes. Ack-based retention is the point; broadcast facts the plane remains right for.

**`context` as a JSON string** — typing the field `string` forces every consumer to marshal its envelope, string-encode the marshaled bytes, and double-decode on the way back, purely to satisfy a type prompts never inspects; and it is exactly the reading that broke the first integration (consumer sent the envelope object, prompts' decoder rejected it as "cannot unmarshal object into … string"). Raw JSON costs prompts nothing — the column stays `TEXT`, the bytes are stored as-is — and keeps "opaque, echoed verbatim" literally true.

**Lease/claim semantics on the inbox** — guards contention that cannot occur: one consumer per origin, single-flight inbox loops. Plain list + per-item ack.

**Long-polling or SSE on the read verbs** — a held response walks back into the write-deadline race in miniature; interval polling against `RecordExclude`-ed loopback GETs costs microseconds. An SSE nudge stays a possible latency optimization, deliberately unspecced.

**Streaming responses / an MCP surface / a stored template entity** — rejected before for reasons the queue does not disturb (no streaming consumer; plumbing off the product surface; callers own their text).

## Verification

- R-J7QG-FRDY — Ensure with a valid request inserts one durable `queued` row and returns its id and status immediately, making **no** provider call on the request path (the injected provider factory is never invoked by the handler).
- R-J8YC-TJ4N — Ensure is idempotent on `(consumer, key)`: a second submission with the same key returns the existing item — including its `result` when already `done` — creates no second row, and triggers no second execution; the same key under a **different** consumer is a distinct item.
- R-JA69-7AVC — Ensure with an out-of-catalog model, a malformed consumer/origin/name, an empty `key`, an empty `messages`, or a final non-`user` turn returns `400` naming the problem, and neither `completions` nor `calls` gains a row.
- R-JBE5-L2M1 — The executor drives a `queued` item to `done` via the injected fake provider: the reply envelope's `result` value lands verbatim in the item's `result`, `usage`/`cost_usd` reflect the fake's reported usage at catalog rates, and exactly one `calls` row (class `completion`, the item's origin/name/group_id/attempt) is written.
- R-JCM1-YUCQ — A reply that is not the valid envelope triggers an internal corrective round trip: the fake provider sees a second request replaying the conversation with its bad reply as an assistant turn plus a corrective user turn; a valid envelope on the retry lands the item `done`, and **each** executed round trip wrote its own `calls` row.
- R-JDTY-CM3F — A provider that never produces a valid envelope fails the item after exactly 3 corrective round trips (4 provider calls total), with `error` naming the envelope contract.
- R-JF1U-QDU4 — A reply envelope with `status:"error"` fails the item with `error` equal to the envelope's `message`, and no `result` is stored.
- R-JG9R-45KT — A provider/stream failure fails the item with the provider error in `error`; the `calls` row records the same error with class/origin/name intact.
- R-JHHN-HXBI — An item still executing when the configured runtime bound elapses (tiny bound + slow fake provider) fails with `error` naming the bound; the executor never leaves it `running` past the bound.
- R-JIPJ-VP27 — On boot, items left `running` by a dead process return to `queued` and re-execute to a terminal state; none are marked failed by the sweep itself.
- R-JJXG-9GSW — Get returns the item's current shape at every stage — `queued`/`running` with no result, `done` with `result`/`usage`/`cost_usd` and the verbatim `context`, `failed` with `error` — and `404` for an unknown id.
- R-JL5C-N8JL — Inbox returns exactly the requesting consumer's **terminal** items, oldest-first, each carrying `key`, verbatim `context`, and `result`/`error`; another consumer's items and `queued`/`running` items never appear.
- R-JMD9-10AA — Ack deletes the item: a subsequent Get returns `404`, the inbox no longer lists it, a repeated Ack returns `404` without error, and a subsequent Ensure with the same key creates a **new** item that executes.
- R-JOT1-SJRO — The retention sweep deletes a terminal item older than the 7-day TTL and retains a younger terminal item and any `queued`/`running` item regardless of age (injected clock).
- R-JQ0Y-6BID — Every queue verb is mounted through the chassis loopback guard: a loopback request carrying no `X-Owner-Email` header succeeds on all four verbs.
- R-JR8U-K392 — The server's `RecordExclude` contains exactly the two read paths (`/completions` GETs); the composition wiring passes them so inbox and item polls produce no telemetry request records while Ensure and Ack do.
- R-JSGQ-XUZR — `POST /complete` no longer exists: the route returns `404` and no handler for it remains in the binary (the synchronous endpoint is expunged).
- R-U7PZ-0AIV — `context` is a JSON value end to end: an Ensure whose `context` is a JSON **object** (and one whose is an array) is accepted with `202`, and every read of the item — Get at a non-terminal stage, Get when terminal, and the inbox row — emits the stored `context` **byte-identical** to the submitted serialization; an Ensure that omits `context` reads back `"context": null` (never `""` and never a JSON-encoded string wrapping the value).
- R-U8XV-E29K — An Ensure whose `context` field is not well-formed JSON fails the body decode with `400` naming the problem, and neither `completions` nor `calls` gains a row.
