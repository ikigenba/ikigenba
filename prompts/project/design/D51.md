# Decision 51 — A prompt definition is a git tree: the fixed layout and the repo name key

> **External ordering (operator-sequenced, not built by any prompts phase).**
> This Decision and D52–D59 consume the **version plane** — `root
> project/design/D24.md` — realized by the **repos** service: the bare
> repository per artifact keyed `prompts/<name>`, the MCP domain verbs
> (create/rename/delete) on repos' loopback `/mcp` door, the byte plumbing
> routes (commit, list, archive), the run-token endpoint, and the git
> smart-HTTP door. The request shapes prompts emits against that surface are
> pinned in D52 as prompts' own emission contract; repos' spec owns the
> serving side. repos has shipped this surface.

## Decision

A prompt's **definition is a git tree**, held by the version plane as one bare
repository keyed `prompts/<name-key>`. The `prompts` row keeps the prompt's
**metadata** — id, owner, name, name key, source path, timestamps, triggers,
and (on runs) correlation and the pinned definition sha. It is no longer the
content's home: `user_prompt`, `system_prompt`, and `config_json` are
superseded columns, retired by D59 after the seeding pass of D54 has moved
their contents into the plane.

**The layout is fixed and small.** Every prompt repository has the same three
addressable files at its root, plus whatever else the prompt's author puts
there:

| path | meaning | required |
|---|---|---|
| `prompt.md` | the user prompt — the single turn the run sends | yes |
| `config.json` | the resolved `Config` (provider, model, the fifteen tuning keys) | yes |
| `system.md` | the optional system prompt, prepended by the framing prompt | only when non-empty |
| anything else | supporting files the definition carries (data, templates, scripts) | — |

Trees are the shape **from day one**: there is no single-file era to migrate
away from later, and a prompt that today is one paragraph can grow a directory
of fixtures without a schema change. The three names above are the only paths
prompts itself reads or writes; everything else in the tree is the author's and
travels to the run untouched.

**The name key.** The repository key is a slug of the prompt's name:

```go
// prompts/internal/prompt — NameKey slugs a prompt name into its repository key.
//
//	lowercase; every run of characters outside [a-z0-9] collapses to a single
//	"-"; leading and trailing "-" trimmed; truncated to 64 bytes (then
//	re-trimmed); an empty result falls back to the prompt's own ULID.
func NameKey(name string) string
```

Boring on purpose: it is a pure function of the name, it produces a key that is
legible in a clone URL and on a laptop's disk, and it never consults the
database. The repository is then `prompts/<NameKey(name)>` — the plane adds no
second namespace, exactly as `root project/design/D24.md` requires.

**Uniqueness is prompts' job, and prompts makes it global.** The plane's
namespace is flat within a kind, so two prompts whose names slug to the same
key would name one repository. prompts therefore stores the derived key in a
`name_key` column carrying a **unique index over the whole table**, not merely
per owner: a global constraint satisfies the owner-unique requirement and, on a
box where two users could each name a prompt "Daily digest", refuses the
collision instead of silently sharing a history. `create` and `update` reject a
name whose key is already held, with a `*ValidationError` naming the existing
prompt's name and its key. The one place a collision is resolved rather than
refused is the seeding backfill (D54), which cannot refuse rows that already
exist.

**Schema.** One new timestamped migration, minted with
`bin/create-migration prompts <name>`, **additive only** — every existing row
is preserved (prompts holds production data; nothing is rebuilt or dropped):

```sql
ALTER TABLE prompts ADD COLUMN name_key TEXT;
CREATE UNIQUE INDEX idx_prompts_name_key ON prompts(name_key) WHERE name_key IS NOT NULL;
ALTER TABLE runs ADD COLUMN definition_sha TEXT;
```

`name_key` is nullable at first so the migration can land before the backfill;
SQLite treats NULLs as distinct, so the unique index tolerates the interval.
D54's seeding pass fills every row; from then on every write path sets it.
`runs.definition_sha` is the commit a run executed (D55).

## Rejected

**A single-file definition now, trees later.** The migration cost is paid
twice: once to move content into the plane and again to reshape every read and
write around a directory. The tree is the end state, and starting there costs
one extra file in the initial commit.

**Keying the repository on the prompt's ULID (`prompts/01J…`).** Unique for
free and unreadable everywhere it matters — the clone URL, the laptop
directory, the `repos:push/prompts/<name>` trigger filter an author writes by
hand. A name key that follows the rename is worth the rename call.

**Owner-scoped uniqueness (`UNIQUE(owner_id, name_key)`).** It matches the
`prompts` table's other indexes but not the namespace it is defending: the
repository key carries no owner segment, so two owners' identical keys collide
in the plane while passing the constraint. Global uniqueness is the honest
shape.

**Suffixing on collision at create/update time (`daily-digest-2`).** A silent
rename of the thing the user just named, discovered later in a clone URL.
Refusing names the conflict while the user is still looking at it. Seeding is
the exception because there is no user present to re-name.

**Keeping `config_json` in the database and putting only the prose in git.**
The config is the half most worth versioning — a model change is exactly the
edit an owner wants to diff, revert, and merge — and splitting the definition
across two stores means a run pins one half and races the other.

## Verification

(Real substrates: the slug is a pure function proven directly; the schema
claims apply prompts' full embedded migration set through the appkit runner to
a real temp-file SQLite database seeded with pre-migration rows.)

- R-RDFP-IOO1 — `NameKey` maps `"Daily Digest"` → `"daily-digest"`,
  `"  bills/AWS — 2026!  "` → `"bills-aws-2026"` (runs of non-`[a-z0-9]`
  collapse to one `-`, ends trimmed), a 200-character name to a 64-byte key
  with no trailing `-`, and `"—— ——"` (nothing alphanumeric) to the supplied
  fallback id. The collapse-and-trim pair is the discriminating property: an
  implementation replacing each bad character one-for-one yields
  `bills-aws---2026-` and fails.
- R-RENL-WGEQ — creating a prompt named `"Daily Digest"` and then creating a
  second named `"daily digest!"` (a different name, the same key) returns a
  `*ValidationError` naming the existing prompt and the key `daily-digest`,
  and inserts no second row; renaming a third prompt onto that key through
  `update` is rejected the same way and leaves the third prompt's name
  unchanged. A build enforcing uniqueness only per owner accepts the pair
  under two owner ids and fails the cross-owner half.
- R-RFVI-A85F — applying the full embedded migration set to a real SQLite
  database **already holding** prompt and run rows leaves `prompts` with a
  `name_key` column and a unique index over it, `runs` with a
  `definition_sha` column, and **every pre-existing row still present with its
  id and content intact** (row counts and ids compared before and after). The
  preservation half is the discriminating property: a drop-and-recreate
  migration passes the column assertions and fails this.
