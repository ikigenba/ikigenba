# Decision 41 — `run_delete`: removing a run and everything it produced

## Decision

A new MCP tool, `run_delete`, removes one run completely:

```go
// RunDelete removes the run's database rows and its whole directory.
// Owner-scoped via the run's own owner_id. Idempotent.
func (s *Service) RunDelete(ctx context.Context, ownerID, runID string) error
```

MCP surface: `run_delete(run_id)` — one run per call, no bulk form.

**What it removes**, in this order:

1. the run's `calls` rows (the per-inference accounting records keyed by `run_id`, D28);
2. the `runs` row;
3. the run's directory, `<stateDir>/runs/<run_id>/`, which since D39 holds `input/`, `output.jsonl`, and `sandbox/` together — one `RemoveAll` of one path. Since D55 the sandbox is a git clone, so the run's local history goes with it; the prompt's repository in the version plane is untouched, and any branch the run pushed there survives, which is the point of pushing.

Rows go before files: a crash between the two leaves orphaned bytes on disk, which are invisible and reclaimable, whereas the reverse order leaves rows pointing at nothing, which is exactly the defect D39 exists to correct.

**Scoping and preconditions.** Ownership is resolved through `runForOwner` — the run's own `owner_id`, never the prompt's — so a run whose prompt has been deleted is still deletable by its owner. A run belonging to another owner is reported as not found, not as forbidden, consistent with every other run-side method. Deleting an absent run is not an error.

**An in-flight run is cancelled first.** If the run is still executing, `run_delete` signals cancellation (the `RunCancel` path) and refuses with a message saying the run is being cancelled and to retry. It does not wait, and it does not delete underneath a live writer: the runner holds an open `output.jsonl` handle and a sandbox the model is using, and removing them mid-write turns a clean cancellation into an arbitrary failure.

**This is the only way run history is removed.** Nothing ages out, nothing is pruned, and deleting a prompt still removes only the prompt.

**Deleting a prompt does not cascade.** That behavior is unchanged and is restated here because it is the reason this tool is needed: a prompt's `delete` removes the prompt row and its triggers and archives its repository (D53) only. Its runs survive with their rows, directories, and accounting intact, and remain listable (D40) and readable by `run_id`. The two deletions are independent; removing a prompt's runs means calling `run_delete` for each.

## Rejected

**Cascade run deletion from prompt `delete`** — rejected: it makes removing a prompt silently destroy an unbounded amount of production history, including the accounting rows that answer spend questions. The non-cascading behavior is deliberate and predates this Decision; adding a tool to remove runs explicitly is the correct way to make history removable without making it removable by accident.

**A bulk form (`run_delete(prompt_id)` deleting every run of a prompt)** — rejected for now: it is the shape most likely to be invoked with the wrong id, against records that cannot be recovered, and the loop over single deletes is available to any caller that means it. Worth revisiting with evidence that the loop is a real burden.

**Delete files before rows** — rejected: it produces the dangling-row state D39 was written to eliminate.

**Delete an in-flight run immediately, cancelling implicitly** — rejected: it removes files under an executing writer, so the run's own failure mode becomes whatever I/O error happens to surface first, and the cancellation path stops being the single way a run stops early.

**Keep the `calls` rows for accounting after the run is gone** — rejected: they would be attributed to a `run_id` that no longer resolves, so spend reports would carry rows nobody can explain. A deleted run's spend leaves the totals with it, and that is the trade the owner is making by deleting it.

**Soft-delete runs (mark, hide, reclaim later)** — rejected for the same reasons D40 rejects soft-deleting prompts, plus one more: the files are the bulk of a run, and a soft delete that leaves them on disk does not do the thing the owner asked for.

## Verification

- R-ZTUJ-HCV2 — after a completed run with at least one `calls` row is deleted, the run's row is absent, its `calls` rows are absent, and `<stateDir>/runs/<run_id>/` does not exist; a second run created alongside it retains its row, its `calls` rows, and its directory. The surviving-run half is the discriminating property: a build deleting by a too-broad predicate passes the first three assertions.
- R-ZV2F-V4LR — `run_delete` called with an owner id that does not match the run's `owner_id` returns the not-found error, and afterwards the run's row and its directory are both still present; the run's true owner then deletes it successfully. A build scoping through the prompt rather than the run fails this for a run whose prompt was deleted.
- R-ZWAC-8WCG — after deleting a prompt that has a completed run, that run's row, its `calls` rows, and its directory are all still present, and `run_delete` on it then succeeds. This pins non-cascade and the tool's independence from the prompt in one assertion.
