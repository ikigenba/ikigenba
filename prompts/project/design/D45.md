# Decision 45 — Chain propagation on suite peer calls: `X-Correlation-Id` in the `MCPServer` headers

> **External ordering.** Consumes appkit's correlation contract (the
> `X-Correlation-Id` header, `eventplane/correlation`'s accessors) and D44's
> stored run correlation id. The operator builds appkit and eventplane first;
> nothing here edits either.

## Decision

Every suite MCP call an in-run agent makes carries the run's chain id, so the
cross-service work a run causes is reconstructible as one chain. Since D6,
prompts owns no MCP client: peers are attached as `agentkit.MCPServer` entries
(`{Name, URL, Headers}`), and agentkit injects each entry's `Headers` map on
**every** request it makes to that server — `tools/list` and each `tools/call`
alike. Propagation is therefore one map entry, not a transport:

- `Discover` gains a trailing `correlationID string` parameter:

  ```go
  func Discover(ctx context.Context, manifestRoot, ownerID, ownerEmail, promptID, correlationID string) []agentkit.MCPServer
  ```

  When `correlationID` is non-empty, every returned entry's `Headers` map
  carries `X-Correlation-Id: correlationID` beside the identity trio
  (`X-Owner-Id`, `X-Owner-Email`, `X-Client-Id`); when it is empty (a caller
  with no chain — should not happen for a run, since D44 mints-or-inherits at
  spawn), the key is simply absent, and each receiving peer's chassis mints
  per its own read-or-mint rule rather than receiving an empty header.
- The **runner** threads the **run row's stored** `CorrelationID` (D44) into
  its `discover` seam and seeds the run's execution context with the same id
  via `eventplane/correlation`, so everything else the run's machinery does on
  that context (outbox appends, direct records) sits on the same chain.

**The recorded boundary, stated honestly.** agentkit's `MCPServer` exposes no
transport or `*http.Client` injection seam, so these peer calls do
**not** pass through the chassis's instrumented outbound client, and prompts
emits no `outbound` record for them. The hop is still fully reconstructible:
each receiving peer records the inbound call (kind `request`) with this chain
id and the `prompts:<id>` client id, so the forensic chain shows the call from
the receiving side. If a later agentkit release grows a client-injection seam,
adopting it (and gaining the outbound-side record) is a new Decision.

## Rejected

- **Migrating a prompts-owned MCP client onto the chassis's instrumented
  outbound client** (`rt.HTTPClient(...)`, via a narrow `Doer` seam). This was
  the shape sealed against the older prompts-owned client and died with
  `internal/mcpclient`: agentkit now owns the client end to end and offers no
  injection point. Re-growing a prompts-side MCP client purely to route peer
  calls through the chassis would resurrect the dispatch path D6 deliberately
  deleted, to buy an outbound record that the receiving peer's inbound record
  already substantially provides.
- **Stamping the header per-turn by mutating `Headers` between turns.** The
  run's chain id is fixed for the run's lifetime; a static map entry at
  attachment time is the whole mechanism, and per-turn mutation adds a moving
  part with nothing to move.
- **Passing the run id instead of the stored correlation id.** An
  event-triggered run continues the envelope's chain (D44); its run id and its
  chain id differ by design, and stamping the run id would sever exactly those
  chains.

## Verification

(Real substrate: agentkit's own MCP client driven through a `Conversation`
against a real in-process `httptest` peer that records the headers of every
inbound request — a stub of prompts' own code cannot show that agentkit
actually injects the map on the wire.)

- R-HPLU-D8WR — `Discover` called with correlation id `X` returns entries
  whose `Headers` all carry `X-Correlation-Id` exactly `X` beside the
  unchanged identity trio; called with an empty correlation id, no entry's
  `Headers` contains the key at all (absent, not empty-valued).
- R-HS1N-4SE5 — end-to-end through a `Conversation` with a recording
  `httptest` MCP peer attached via `Discover`'s output: the peer's inbound
  `tools/list` **and** a dispatched `tools/call` both arrive carrying
  `X-Correlation-Id` exactly `X` — a build whose header reaches discovery but
  not dispatch (or vice versa) fails this.
- R-HT9J-IK4U — the runner passes the **run row's** stored `CorrelationID`
  into its `discover` seam: for a run whose stored correlation id `X` differs
  from its run id, the injected `discover` observes `X` (not the run id, and
  not empty), and the run's context inside `execute` reports `X` through
  `correlation.FromContext`.
