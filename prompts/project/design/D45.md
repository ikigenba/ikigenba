# Decision 45 — Chain propagation on suite peer calls: `X-Correlation-Id` on every gateway hop

> **External ordering.** Consumes appkit's correlation contract (the
> `X-Correlation-Id` header, `eventplane/correlation`'s accessors) and D44's
> stored run correlation id. The operator builds appkit and eventplane first;
> nothing here edits either.

## Decision

Every suite MCP call an in-run agent makes carries the run's chain id, so the
cross-service work a run causes is reconstructible as one chain. Since the
gateway rewrite (D6/D19/D60), prompts owns the client again: peers are
`suite.Peer` values whose `Headers` map the D60 client injects on **every**
request it makes — `initialize`, `tools/list`, and each `tools/call` alike.
Propagation is one map entry:

- `Discover` keeps its trailing `correlationID string` parameter. When
  non-empty, every returned `Peer`'s `Headers` map carries
  `X-Correlation-Id: correlationID` beside the identity trio (`X-Owner-Id`,
  `X-Owner-Email`, `X-Client-Id`); when empty (a caller with no chain —
  should not happen for a run, since D44 mints-or-inherits at spawn), the key
  is simply absent, and each receiving peer's chassis mints per its own
  read-or-mint rule rather than receiving an empty header.
- The **runner** threads the **run row's stored** `CorrelationID` (D44) into
  its `discover` seam and seeds the run's execution context with the same id
  via `eventplane/correlation`, so everything else the run's machinery does on
  that context (outbox appends, direct records) sits on the same chain.

**The recorded boundary, improved.** The previous shape of this Decision
accepted a gap: agentkit's `MCPServer` path exposed no transport seam, so peer
hops emitted no `outbound` record and the chain showed each hop only from the
receiving side. The D60 client's `Doer` seam closes that gap — the composition
root passes the chassis's instrumented outbound client (`rt.HTTPClient(...)`),
so every peer hop is now recorded from **both** sides: prompts' `outbound`
record and the receiving peer's `request` record, on the same chain id. The
run's *inside* (provider traffic, sandbox tool use) remains unrecorded, as
D47 states.

## Rejected

- **Stamping the header per-call by mutating `Headers` between gateway
  calls** — the run's chain id is fixed for the run's lifetime; a static map
  entry at `Discover` time is the whole mechanism.
- **Passing the run id instead of the stored correlation id.** An
  event-triggered run continues the envelope's chain (D44); its run id and its
  chain id differ by design, and stamping the run id would sever exactly those
  chains.
- **Leaving the peer hops uninstrumented (a bare `http.Client`)** — the
  previous shape's accepted gap existed only because agentkit offered no
  seam; with a prompts-owned client the instrumented transport is one
  composition-root argument, and declining it would be re-accepting a fixed
  defect.

## Verification

- R-P5DX-Y02K — `Discover` called with correlation id `X` returns peers whose
  `Headers` all carry `X-Correlation-Id` exactly `X` beside the unchanged
  identity trio; called with an empty correlation id, no peer's `Headers`
  contains the key at all (absent, not empty-valued).
- R-P7TQ-PJJY — end-to-end through `Runner.execute` with a recording
  `httptest` peer: for a run whose stored correlation id `X` differs from its
  run id, the peer's inbound `tools/list` (driven by `suite_tools`) **and** a
  dispatched `tools/call` (driven by `suite_call`) both arrive carrying
  `X-Correlation-Id` exactly `X` — not the run id, and not absent — and the
  run's context inside `execute` reports `X` through `correlation.FromContext`.
  A build whose header reaches listing but not dispatch (or vice versa) fails
  this.
