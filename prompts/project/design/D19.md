# Decision 19 — Suite tools behind the three-tool gateway

## Decision

The in-run agent reaches suite services through **three always-on gateway
tools** — `suite_services`, `suite_tools`, `suite_call` — instead of carrying
every peer tool's definition on every round-trip. The run's toolset is the 13
sandbox built-ins (D5) plus these three; `Conversation.MCPServers` is **no
longer populated** and no `ikigenba_*` tool appears in the provider tools
array. This reverses the eager attachment this Decision previously carried:
the measured price of eagerness (~90% of a run's starting context, growing
linearly with the suite, research §1) bought nothing once cross-model
comprehension of the gateway pattern was verified by experiment (research §7).

**The three tools** live in `prompts/internal/gateway` and are built with
`agentkit.NewTool` over fixed Go structs — which is what clears the sealed
`Tool` obstacle that killed deferral: the *gateway's* schemas are compile-time
Go types even though the *peers'* schemas are runtime data that the gateway
relays as text.

```go
package gateway

// Tools returns the three gateway tools over the run's peer set.
// catalog is D6's Catalog closed over the peers; clients yields a D60
// client per peer (composition root closes it over the instrumented Doer).
func Tools(peers []suite.Peer, catalog CatalogFunc, clients ClientFunc) []agentkit.Tool

type suiteServicesInput struct{} // no arguments

type suiteToolsInput struct {
    Service string `json:"service" jsonschema:"description=A service name from suite_services"`
}

type suiteCallInput struct {
    Service string `json:"service" jsonschema:"description=A service name from suite_services"`
    Tool    string `json:"tool" jsonschema:"description=Bare tool name as listed by suite_tools, e.g. save"`
    Args    string `json:"args" jsonschema:"description=The tool's arguments as one JSON object literal, e.g. {\"id\":\"X\"}"`
}
```

- **`suite_services`** — no arguments; returns D6's catalog as JSON: one
  `{name, summary}` row per reachable service, in deterministic (inventory)
  order. Its description states that services must be discovered here and
  their tools loaded via `suite_tools` before calling.
- **`suite_tools(service)`** — returns the peer's server instructions plus its
  `tools/list` result — names, descriptions, and input schemas relayed
  byte-verbatim (D60) — as JSON text. No caching: each call is a live
  loopback list (research §8 makes it cheap; freshness is free). An unknown
  service returns an error result naming the valid service names, so recovery
  costs no extra round-trip.
- **`suite_call(service, tool, args)`** — parses `args` as one JSON object
  (`NewTool` cannot declare a free-form object parameter, research §2, so the
  object rides as a string); rejects non-JSON or non-object args with an
  error result naming the problem, **without dispatching**; otherwise
  dispatches the bare tool name with the parsed arguments to the peer via the
  D60 client and relays the result text. The gateway validates nothing about
  the arguments beyond JSON-object well-formedness — the peer's own
  validation is authoritative (D27 structured errors) — and every error result
  it frames (unknown service, unknown tool, peer `isError`, unreachable peer)
  names the failing service and tool and points at `suite_tools("<service>")`
  for the schema.

**Failure is per-call, never per-run.** A peer that is down costs exactly the
gateway calls addressed to it, each returning an error result the model can
react to; the run itself proceeds. This deliberately retires the spawn-time
all-or-nothing failure the previous shape accepted (a dead peer failed the
whole run) — there is no spawn-time peer contact at all.

**Runner wiring** (the D7 conversation assembly, restated here as the owning
decision):

```go
conv := &agentkit.Conversation{
    ...
    Tools: append(
        runtools.All(sandboxRoot, r.sourcePortAllowed, shareCfg), // 13 sandbox tools (D5/D21/D26)
        gateway.Tools(peers, catalog, clients)...,                // the 3 gateway tools
    ),
    // MCPServers is not set.
}
```

The injectable `discover` seam now returns `[]suite.Peer` (D6); the gateway
tool constructors are pure functions over that value, so the runner test seams
are unchanged in kind.

**Framing prompt**: `framing_prompt.go` replaces the "services are attached
and callable directly" sentence with one short paragraph stating the flow —
the account's services are reachable through `suite_services` (list them),
`suite_tools` (load one service's tool schemas), and `suite_call` (invoke one
tool with JSON arguments) — and that a service's tools must be inspected
before first use. It still names **no individual service** (the attached set
is per-box; hard-coded prose would drift) and composes unchanged with the
event preamble's "use the identifiers in `payload` with the suite tools" and
with D23/D57's claims.

## Rejected

- **Eager `MCPServers` attachment (the previous shape of this Decision)** —
  see D6's Rejected; the measured cost and the spawn-time fragility bought
  nothing once the gateway was validated.
- **Harness-side JSON Schema validation of `suite_call` args** — a full
  2020-12 validator dependency and a second validation pass that can drift
  from the peer's authoritative one, to pre-empt an error the peer already
  reports in structured form (D27). The gateway checks only what it owns:
  that `args` is one JSON object.
- **Dynamic injection of real tool entries after `suite_tools`** (typed
  per-tool schemas appearing in the provider tools array mid-run) — the
  fallback shape if argument fidelity through the string-carried `args` had
  proven poor. The experiment showed 4/5 models flawless and the one semantic
  miss (sign inversion) equally likely under typed attachment, since the
  convention lives in description text either way (research §7). Not carried
  as a mechanism; a future Decision if evidence changes.
- **Per-prompt config knob selecting eager vs gateway** — two presentation
  modes means two framing prompts, two test matrices, and drift between them,
  to hedge a question the experiment already answered. Rollback is the deploy
  layer's previous release.
- **Pre-warming the triggering service's tools on event runs** — a special
  case in run assembly to save one round-trip, resting on the guess that the
  event's source service is the one the prompt acts with. Deferred; a clean
  additive Decision if latency or token data ever argues for it.
- **A dedicated per-service meta-tool (`crm(tool, args)`, one per peer)** —
  multiplies gateway surface by the peer count and still needs the same
  string-carried args; the three-tool shape is the ecosystem-standard triple
  (research §7).

## Verification

- R-OVMQ-VU50 — a run's `Conversation` (observed via a recording fake
  provider's first `Request`) carries exactly the 13 sandbox tools plus
  `suite_services`, `suite_tools`, and `suite_call`; no tool name begins with
  `ikigenba_`, and no MCP server resolution occurs (a spawn with an
  unreachable peer in the peer set still reaches the provider). A build still
  populating `MCPServers` fails the last clause.
- R-OWUN-9LVP — `suite_tools` for a known service returns the stub peer's
  instructions and its tools with schemas byte-identical to what the peer
  published; for an unknown service it returns an error result whose text
  contains every valid service name and dispatches nothing.
- R-OY2J-NDME — `suite_call` with `args` that is not valid JSON, and
  separately `args` that is valid JSON but not an object (`"[1,2]"`), returns
  an error result naming the defect and `suite_tools`, and the recording peer
  observes **zero** `tools/call` requests.
- R-OZAG-15D3 — `suite_call` with a known service, bare tool name, and a
  valid JSON-object `args` dispatches exactly one `tools/call` to that peer
  carrying the tool name and the parsed arguments object, and returns the
  peer's result text as the tool result.
- R-P0IC-EX3S — a peer answering `isError: true` yields an error-framed tool
  result that names the service and tool and points at `suite_tools`, and the
  run completes normally (the error reaches the model, not the run status).
- R-P1Q8-SOUH — `suite_call` (and `suite_tools`) addressed to a peer that
  refuses connections returns an error result naming that service, and the
  run still completes `succeeded` — the discriminating property against the
  retired spawn-time all-or-nothing failure, which a build that contacts
  peers at spawn would reintroduce.
- R-P2Y5-6GL6 — the framing prompt sent as the conversation `System` names
  `suite_services`, `suite_tools`, and `suite_call` and the
  discover-inspect-invoke order, contains no occurrence of `load_tools`, no
  `ikigenba_`, and no individual service name (composes with R-6I5U-Y474 and
  D57's ids).
- R-P461-K8BV — end-to-end through `Runner.execute` with a scripted fake
  provider that calls `suite_services`, then `suite_tools` for a stub peer's
  service, then `suite_call` invoking one of its tools: the call dispatches to
  the stub peer and the run completes `succeeded`, with `tool_use` and
  `tool_result` `LogRecord` lines for all three gateway calls present in
  `output.jsonl`.
