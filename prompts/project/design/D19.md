# Decision 19 — Suite tools are eager, attached as MCP servers

## Decision

The in-run agent carries every attached suite tool's full definition on every round-trip. The suite's peers reach the run as **agentkit MCP server attachments** (D6): the runner assigns `Discover`'s output to `Conversation.MCPServers`, agentkit lists each peer's tools itself, and those tools join the eager tool set alongside the sandbox tools. There is no catalog, no `load_tools`, and no loading step — a suite tool is callable from the run's first round-trip.

This reverses the progressive-discovery design this Decision previously carried. That design consumed agentkit's `DeferredToolGroup`, whose `Tools` field requires `[]agentkit.Tool` values. `agentkit.Tool` is sealed and `RawTool` — the only constructor accepting a runtime-discovered schema — was removed in agentkit v0.12.0 (research §2). Peer schemas are learned over MCP at spawn and are not Go types, so no discovered tool can be placed in a group. MCP-sourced tools land in agentkit's eager base set by construction, with no path into `DeferredTools`.

**Runner wiring** (the D7 conversation assembly, restated here as the owning decision):

```go
// Runner.discover changes type:
discover func(ctx context.Context, owner, promptID string) []agentkit.MCPServer

// In execute:
conv := &agentkit.Conversation{
    ...
    Tools:      runtools.All(sandboxRoot, sourcePortAllowed), // sandbox tools (D5/D21)
    MCPServers: r.discover(ctx, run.OwnerID, run.PromptID),   // D6 attachments
    // DeferredTools is not set.
}
```

The injectable `discover` seam is unchanged in shape, only in element type. An empty discovery result (no peers, unreadable inventory) means `MCPServers` is empty and agentkit performs no MCP resolution — a run on a bare box behaves exactly as today.

**The cost, stated plainly.** Measured against a live local suite, 6 services is ~79 tools ≈ 8k tokens of serialized definitions resident per round-trip; a full box (~11 peers, ~120 tools) lands around 15–18k tokens, paid whether or not a single suite tool is called, plus tool-choice dilution across the full set (research §1). This is the price of the bump and is accepted. It is not mitigated here, and no exception list narrows it: partial eagerness would be policy to maintain with no mechanism to enforce it.

**Framing prompt**: `framing_prompt.go`'s `framingPrompt` drops the `load_tools` guidance paragraph entirely. What replaces it is one sentence stating that the account's services are available as tools and are callable directly — generic on purpose, naming **no individual service**, because the attached set is per-box and per-run and hard-coded prose would drift. The event preamble (`eventPreamble`) is unchanged; its "use the identifiers in `payload` with the suite tools" guidance composes with the sentence above and needs no edit, since it never named the loading mechanism.

## Rejected

**Keep deferral by pinning agentkit at v0.11.0** — rejected in D1: it preserves this Decision's prior shape at the cost of freezing prompts one release behind indefinitely, and forgoes the corrected per-offering catalog data validation now depends on.

**A prompts-side meta-dispatch surface (`suite_call(service, tool, arguments)`)** — the one shape that preserves progressive discovery under a sealed `Tool` interface, since the meta-tool's input is a Go struct. Rejected in D6 for the reason this Decision originally rejected it: real tools would be driven through a stringly wrapper with no provider-native schema on the actual call. The earlier rejection assumed agentkit would carry the mechanism instead; agentkit has since removed it. That makes the alternative no better than it was, only lonelier.

**Keep a hand-picked eager subset and defer the rest** — unreachable: there is no deferral mechanism left to put the rest into.

**Enumerate the attached services in the framing prompt** — the inventory is per-box and per-run; prose would drift from the live attachment set it duplicates.

## Verification

- R-ZIVG-1F6T — a run's `Conversation` is built with `MCPServers` equal to the entries the injected `discover` returned and `DeferredTools` empty; observed via a recording fake provider's first `Request`, that request's tool array contains the sandbox tools **and** each attached peer's tools, and contains no tool named `load_tools`. A build that still populated `DeferredTools` would surface `load_tools` and fail this.
- R-ZK3C-F6XI — the framing prompt sent as the conversation `System` contains no occurrence of `load_tools`, and contains no individual service name (no `ikigenba_` and no per-service enumeration).
- R-ZLB8-SYO7 — end-to-end through `Runner.execute` with a scripted fake provider that calls an attached suite tool **natively on its first round-trip**, with no prior `load_tools` call: the tool dispatches to the stub peer and the run completes `succeeded`, with the `tool_use`/`tool_result` `LogRecord` lines present in `output.jsonl`. A build requiring a load step first would never reach the tool and would fail this.
