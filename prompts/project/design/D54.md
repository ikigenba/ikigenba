# Decision 54 — Seeding: the one-time, idempotent definition backfill

> **External ordering.** See the banner in D51.

## Decision

Every prompt on the box today has its definition in three database columns and
no repository. Seeding moves them, once, without losing a byte — and it is a
**boot-time Go pass, not a SQL migration**, because a migration cannot make an
HTTP call and the destination is another service.

```go
// prompts/internal/prompt — SeedDefinitions is the one-time backfill. It is
// idempotent: a prompt whose repository already carries a commit is skipped,
// so the second and every later boot make zero commits.
func (s *Service) SeedDefinitions(ctx context.Context) (seeded int, err error)
```

**What it does, per prompt row, in id order:**

1. **Assign the name key** when `name_key` is NULL: `NameKey(p.Name)` (D51),
   falling back to the prompt's ULID when the name slugs to nothing. On
   collision with a key already taken, append `-2`, `-3`, … until free —
   seeding cannot refuse a row that already exists, so this is the one place a
   key is adjusted rather than rejected (D51). The chosen key is written to the
   row.
2. **`Create`** the repository (idempotent on the plane's side).
3. **`Head`** it. A repository that already has a commit is **skipped** — its
   definition is already the truth, and re-committing the columns would clobber
   a laptop push with stale bytes.
4. Otherwise **`Commit`** one batch: `prompt.md` from `user_prompt`,
   `config.json` from `config_json` verbatim, and `system.md` only when
   `system_prompt` is non-empty. Message `seed <name>`.

**Nothing is deleted and nothing is rewritten.** The columns keep their values
through this pass; D59 retires them in a later, separate phase, and only after
seeding has run. That ordering is the whole safety argument: the content exists
in two places for the interval, and the columns are dropped only once the plane
holds them.

**When it runs, and what happens when the plane is down.** The composition root
calls `SeedDefinitions` after migrations and **before** the server accepts
traffic. A `version.ErrUnavailable` is retried with bounded exponential backoff
for up to 30 seconds — enough to cover repos still starting under an
`opsctl`-ordered box restart — and, if it still fails, boot **exits non-zero**
with a message naming the version plane. Serving with unseeded prompts is the
worse outcome: every `get` and every run would fail one at a time with an
obscure error, and an owner would be told their prompt is empty.

**It is safe to run forever.** The pass stays in the boot path rather than
being a one-shot script an operator must remember: on a seeded box it is one
`Head` per prompt and no writes, and it is the mechanism that heals a prompt
whose repository was archived or lost.

## Rejected

**A SQL migration.** It cannot reach the plane. A migration that stamped a
"needs seeding" flag and deferred the work would just be this pass with an
extra column.

**A one-shot `opsctl` or `bin/` command the operator runs during deploy.** It
is a step that can be skipped, on a box where skipping it means every prompt
reads as empty. The idempotent boot pass costs one `Head` per prompt and cannot
be forgotten.

**Non-fatal seeding (log and serve anyway).** It converts one loud, actionable
boot failure into a scatter of confusing runtime failures, and it lets a
half-seeded box serve some prompts and not others.

**Lazy seeding on first access.** It spreads the plane dependency across every
read path, and the first access is often an event-triggered run at 3am with
nobody watching.

**Overwriting a repository that already has commits.** The whole point of the
plane is that the repository outranks the row. A re-seed after a laptop push
would silently revert the owner's work.

**Refusing on a key collision, as create does.** There is no user present to
re-name, and refusing means the box will not boot. Suffixing is the only
choice that preserves both rows.

## Verification

(Substrate: the real `Service` and `Store` over a temp-file SQLite database
through the real migration runner, seeded with pre-conversion rows, driving a
recording fake `version.Client`.)

- R-RTAE-HPB2 — with three prompts seeded in the database and a fake plane
  reporting no commits, the first `SeedDefinitions` returns `seeded == 3` and
  issues three `Commit` calls; a **second** call on the same state — the fake
  now reporting a head for each — returns `seeded == 0` and issues **zero**
  `Commit` calls while still leaving every row's `name_key` set. The
  zero-commit second pass is the discriminating property: a build that
  re-commits unconditionally passes the first assertion and clobbers on the
  second.
- R-RUIA-VH1R — a prompt row with a non-empty `system_prompt` seeds a batch of
  exactly `prompt.md`, `config.json`, `system.md` whose contents equal the
  row's three columns byte for byte (`config.json` verbatim, not re-marshalled
  into a different key order), a row with an empty `system_prompt` seeds a
  batch of exactly two paths, and two rows named `"Report"` and `"report!"`
  receive the distinct keys `report` and `report-2` — both persisted, neither
  row refused.
- R-RVQ7-98SG — with a fake plane returning `ErrUnavailable` for the first two
  attempts and succeeding on the third, boot completes and every prompt is
  seeded; with a fake failing for the whole retry window, the composition
  root's startup returns a non-nil error whose message names the version plane
  and **no HTTP listener is opened**. A build that logs and continues serves a
  request in the second case and fails it.
