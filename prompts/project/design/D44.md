# Decision 44 — The correlation id on the record: `runs.correlation_id`, `calls.correlation_id`, mint-or-inherit at spawn

> **External ordering (operator-sequenced, not built by any prompts phase).**
> This Decision consumes appkit's **correlation package** (its D20) — the
> read-or-mint middleware, its context accessors (`correlation.FromContext`,
> `correlation.WithContext`), and `correlation.StartChain` (adopts the
> context's id with `Ensure` semantics, minting only when absent, and records
> the `root`; reached through D47's seam) over the `X-Correlation-Id` header,
> whose ids are bare 26-char Crockford-base32 ULIDs — specified in appkit's
> own `project/` and realized by appkit's telemetry phases, **which must be
> BUILT before this Decision's phase runs**. prompts consumes those accessors
> as a fixed external contract and never re-implements them (`internal/ids`
> keeps minting run ids; it does not mint chain ids).

## Decision

A run is the suite's **durable root of an agent chain**: the forensic agent
resolves a chain's correlation id to a prompts run and reads that run's
archived conversation from prompts. That linkage only works if the id is
**stored, durably, on the run row** — so it becomes a first-class column, not a
derived or in-memory value.

**One rule at spawn, for every path.** `Service.startRun` (the shared start
path for the manual `run` MCP verb and the event-fired `RunByEvent`) reads the
chain id from its own context and falls back to the run's own id:

```go
// internal/prompt/service.go — inside startRun, after runID is minted.
corrID := correlation.FromContext(ctx)
if corrID == "" {
    // Durable-root reuse: the run IS the root (docs/correlation-ids.md). The
    // injected RootStarter seam (D47) seeds the ctx with the run id and calls
    // the chassis StartChain, which adopts the seeded id (minting only when
    // absent) and records the `root`. prompts never mints a chain id itself.
    corrID = runID
    ctx = s.startRoot(ctx, runID, "run:"+runID)
}
run.CorrelationID = corrID
```

- **Manual MCP run** — the chassis middleware has already put the inbound
  request's `X-Correlation-Id` (nginx-supplied at the edge, or a loopback
  peer's) on the request context, so the run **continues** the caller's chain.
  An external caller's chain therefore reaches the run without prompts doing
  anything special.
- **Event-fired run** — the consumer re-attaches the envelope's correlation id
  onto the detached fire context (D47); `startRun` reads it the same way.
- **No inbound chain** — the run's own ULID **is** the correlation id, per the
  durable-root-reuse rule in `docs/correlation-ids.md`. A run that roots a
  chain and the chain itself therefore share one identifier, so "resolve the
  chain id to the run" is a primary-key lookup, and no second ULID exists to
  keep in sync. Establishing that origin — adopting the id into the context and
  emitting the `root` record — goes through the chassis root-start helper, not
  through anything prompts mints or builds; the seam and its proof are D47's.

**Storage — one new timestamped migration** minted with
`bin/create-migration prompts correlation_id` (never a hand-picked number),
additive on both tables (no rebuild, no data loss, no frozen migration
touched):

```sql
ALTER TABLE runs  ADD COLUMN correlation_id TEXT NOT NULL DEFAULT '';
ALTER TABLE calls ADD COLUMN correlation_id TEXT NOT NULL DEFAULT '';
CREATE INDEX runs_correlation  ON runs  (correlation_id);
CREATE INDEX calls_correlation ON calls (correlation_id);
```

`''` on a pre-migration row means "recorded before the chain existed" and is
never confused with a real id (a chain id is always 26 characters).

**`calls.correlation_id`** (D28's table gains the column and `Filter` gains the
dimension): every inference unit records the chain that caused it — a session
row from the run's `correlation_id` (threaded through `FinishRunInput`
alongside the usage columns, D33), a `/complete` or `/embed` row from
`correlation.FromContext` on the inbound loopback request. This keeps the
existing `group_id` column doing its own job (below) and makes "what inference
did this chain cause, and what did it cost" one SQL predicate.

**`group_id` and `correlation_id` are kept, with distinct meanings.** They are
not aligned and not merged:

- `group_id` is the **inference grouping** key — the run id for a session row,
  the caller's own job id for a `/complete`/`/embed` row. It is chosen by the
  *caller* for reporting (`usage` grouped by job, `calls` filtered by job) and
  is free-form; nothing propagates it across a service boundary.
- `correlation_id` is the **causal chain** key — assigned by the suite's
  correlation contract, propagated verbatim on every hop, never re-minted
  mid-chain.

They coincide by accident today (wiki passes a job ULID as `group_id`) and will
diverge the moment one job issues calls on two chains or one chain spans two
jobs. Collapsing them would make a *reporting* label load-bearing for
*forensics* and would silently break whenever a caller reuses a group label.
D29/D30's request field keeps its name and semantics; its documentation stops
calling it a "correlation id" (rewritten in place there).

**Model + MCP surface.** `prompt.Run` gains
`CorrelationID string \`json:"correlation_id,omitempty"\``, so `run_get` and
`run_list` expose it; `run_list` accepts an optional `correlation_id` argument
filtering to exactly the runs on that chain. That argument is the forensic
pivot: telemetry answers "which chain", prompts answers "which run", and the
run's `output.jsonl` is the only copy of the conversation.

## Rejected

**Deriving the chain id from the run id alone (no column).** Works only for
runs that root their own chain; a run continuing an inbound chain would have no
place to record it, and the wiki→prompts and MCP-caller cases are exactly the
ones the capability exists for.

**Minting a fresh chain id for a root run instead of reusing the run id.** Two
ULIDs naming one origin, both needing to be stored and kept consistent, for no
gain — and it contradicts the durable-root-reuse rule the suite already
publishes.

**Merging `group_id` into `correlation_id`.** Different owners, different
lifetimes, different guarantees (see above). One is a caller's reporting label;
the other is a propagated protocol value.

**Storing the chain id only on `calls` (not on `runs`).** The forensic pivot is
chain → run → archived conversation; a run with no terminal `calls` row yet (or
a cancelled run that never wrote one) would be unreachable exactly when someone
is asking what a stuck run did.

**Putting the chain id in the pinned `input/` tree instead of a column.** The
pinned inputs are what the run *executes*; a chain id is not an execution
input, and a file is not queryable — `run_list` filtering needs an indexed
column.

## Verification

(Real substrates throughout: migration and storage claims apply prompts' full
embedded migration set through the appkit runner to a fresh real SQLite
database and read back by SQL; MCP claims drive the assembled `appkit/mcp`
handler.)

- R-HIAG-2MGL — applying prompts' full embedded migration set to a fresh real
  SQLite database yields a `runs` table **and** a `calls` table each carrying a
  `correlation_id` column, with indexes `runs_correlation` and
  `calls_correlation` present, while every frozen committed migration remains
  byte-identical to its committed body.
- R-HJIC-GE7A — a run started through `Service.Run` on a context carrying **no**
  correlation id persists `correlation_id` **exactly equal to the run's own
  id** (read back by SQL) — not empty, and not some other 26-char ULID (a build
  that mints a second id fails this).
- R-HKQ8-U5XZ — a run started on a context carrying correlation id `X`
  persists `correlation_id == X`, which is **not** the run id — the inbound
  chain is continued, never replaced.
- R-HLY5-7XOO — a `calls` Row inserted with a `correlation_id` reads back via
  `Get` with that exact value, and `List` filtered by that correlation id
  returns exactly the seeded rows carrying it (2 of 5 seeded rows), excluding
  rows on other chains and rows with an empty id.
- R-HN61-LPFD — after a run completes, its session `calls` row's
  `correlation_id` equals the **run row's** `correlation_id` (both for a run
  that rooted its chain and for a run that inherited id `X` — in the inherited
  case the value is `X`, not the run id).
- R-HODX-ZH62 — through the assembled MCP handler: `run_get` returns the run's
  `correlation_id`, and `run_list` given `correlation_id: X` returns exactly
  the runs stored with `X` (a run on a different chain is absent) — the schema
  advertises the `correlation_id` argument.
