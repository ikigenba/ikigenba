# Decision 53 — The write path: create, update, import, rename, and delete go through the version plane

> **External ordering.** See the banner in D51.

## Decision

Every mutation of a prompt's **definition** becomes a commit; every mutation of
its **metadata** stays a row write; a rename is both. `prompt.Service` gains one
field — `Version version.Client` (D52), field-injected at the composition root
like `Fetcher` — and the four write verbs thread it.

**`create`** — validate the config (D3, unchanged), derive and reserve the name
key (D51), insert the row, then, in one plane round trip pair: `Create` the
repository and `Commit` the initial layout as a **single batch**:

```
prompt.md    <- in.UserPrompt
config.json  <- the validated Config, JSON with a trailing newline
system.md    <- in.SystemPrompt, present in the batch ONLY when non-empty
```

The commit message is `create <name>`. Order matters: the row is inserted first
so the prompt id exists to attribute the commit (`X-Client-Id:
prompts:<prompt id>`), and a plane failure after the insert **rolls the row
back** — a prompt whose definition was never committed would be a row pointing
at nothing, the defect D39 exists to eliminate on the run side.

**`update`** — resolve the effective definition under patch semantics (D61: a
field the call omits keeps its current value; the plane's current definition is
the base), validate, then commit **only the files whose content changed**, in
one batch: `prompt.md` when the user prompt changed, `config.json` when the
config changed, `system.md` when the system prompt changed (a system prompt
cleared to explicit empty is a `File{Delete: true}`; an *omitted* system prompt
is untouched). An update touching only the name commits nothing. The commit
message is `update <name>`. When a config is sent it is whole-value: the
committed `config.json` is the whole resolved object (D2).

**A rename is a plane rename.** When `update` **sends** a name that derives a
new key (an omitted name is never a rename — D61), prompts derives the new key,
checks it is free (D51), calls `Rename(oldKey, newKey)`, and only
then writes the row's `name`/`name_key`. Rename first, row second: a failed
rename leaves both stores consistent, whereas a renamed row over an unrenamed
repository loses the prompt's history behind a key nobody looks up. A rename
and a content edit in the same `update` are one rename followed by one commit.

**`import`** — the Dropbox mirror adoption is kept exactly as it is (fetch,
UTF-8 and 1 MiB guards, `(owner_id, source_path)` upsert, direction strictly
Dropbox → prompts). What changes is where the body lands: the fetched bytes are
batch-committed as **`prompt.md`**, message `import <source path>`. A first
import also `Create`s the repository and commits the seeded default
`config.json` (`importDefaultModel`) in the same batch; a re-import commits
`prompt.md` alone, so a body refresh never rewrites a config the owner has
since tuned.

**`delete`** — removes the prompt row and its triggers (non-cascade, unchanged:
its runs survive, D40/D41) and calls `Archive(nameKey)`. Archive, never delete:
the history is hidden from listings and recoverable, and reclaiming its disk is
a deliberate operator act (`root project/design/D24.md`). A prompt's runs keep
working after the archive because a run reads its definition from its own clone
(D55), not from the plane.

**Reads split by cost.** `Get` reads the live definition from the plane
(`Read(nameKey, "main")`) and returns it with the row's metadata — this is
`LoadFromPrompt`'s new body (D40). **`List` returns metadata only** — name,
owner, name key, timestamps, running count, last run — and no definition
content, because a list of N prompts must not become N plane round trips. The
MCP `list` tool and the browse UI's prompts tab already show exactly these
fields; `get` is where a definition is read.

**Failure is loud and leaves nothing half-written.** A `version.ErrValidation`
or `ErrConflict` surfaces as the MCP `isError` content envelope (D17's
mapping); an `ErrUnavailable` fails the call naming the version plane. In no
case does a write verb report success having committed nothing.

## Rejected

**Commit first, insert the row second.** The commit needs the prompt id for
attribution, and a commit with no row behind it is an orphan repository nobody
can find. Insert-then-commit-then-rollback keeps the failure recoverable in the
store, which is the half prompts controls.

**Two-phase commit / a durable outbox for plane writes.** The failure window is
one loopback call on one box; the compensation is a row delete. An outbox would
add a table, a drain loop, and a partially-visible prompt state to remove a
race that a rollback already closes.

**Keeping the row's `user_prompt` in sync as a cache.** Two sources of truth,
one of them silently stale after a laptop push. The columns are retired (D59),
not shadowed.

**Renaming by create-new + archive-old.** It severs history at the rename — the
one moment a user most expects it to survive — and doubles the repository count
for a typo fix.

**Deleting the repository on `delete`.** Refused by the contract and by
judgment: the runs that executed against it are still readable, and a prompt
deleted by mistake is otherwise unrecoverable.

**Having `List` read every definition so the payload shape is unchanged.** It
turns a listing into N round trips and returns bodies no lister reads. The
narrowed payload is the honest surface.

## Verification

(Substrate: the real `prompt.Service` and `Store` over a temp-file SQLite
database through the real migration runner, with a **recording fake**
`version.Client` — the plane's own wire behavior is D52's to prove; what
falsifies these is which calls prompts makes, in what order, with what
contents.)

- R-RLZ0-72UW — `create` with a non-empty system prompt issues `Create` then
  exactly one `Commit` whose batch is exactly the three paths `prompt.md`,
  `config.json`, `system.md`, with `prompt.md` equal to the input user prompt
  and `config.json` parsing to the validated `Config`; the same create with an
  **empty** system prompt issues a batch of exactly two paths, with no
  `system.md` entry. The empty-system half is the discriminating property: a
  build always writing three files passes the first assertion and fails this.
- R-ROES-YMCA — `update` changing only the config issues exactly one `Commit`
  whose batch is exactly `["config.json"]`; an update clearing the system
  prompt issues a batch containing `system.md` with `Delete: true`; an update
  changing only the name issues **zero** `Commit` calls and exactly one
  `Rename(oldKey, newKey)` that precedes the row write (observed by the fake
  failing `Rename` and the row's name being unchanged afterwards).
- R-RPMP-CE2Z — a first `import` of a mirror path issues `Create` plus one
  `Commit` whose batch is `prompt.md` (the fetched bytes verbatim) and
  `config.json` (the seeded default model); a **re-import** of the same path
  issues one `Commit` whose batch is exactly `["prompt.md"]` and no `Create`,
  leaving a config the owner edited between the two imports uncommitted and
  intact.
- R-RQUL-Q5TO — `delete` of a prompt with a completed run issues exactly one
  `Archive(nameKey)` and **zero** delete-style calls, removes the prompt row
  and its triggers, and leaves the run's row and directory present and
  readable. A build calling a repository delete, or cascading to the runs,
  fails.
- R-RS2I-3XKD — when the fake `Commit` returns `ErrUnavailable`, `create`
  returns a non-nil error naming the version plane and **no prompt row
  exists** afterwards (the rollback); when it fails on `update`, the stored
  row's name and name key are unchanged and the call returns an error rather
  than reporting success.
- R-SGGH-RCE9 — `List` over three prompts issues **zero** `Read` calls to the
  plane and returns entries carrying name, name key, and timestamps but no
  definition content, while `Get` on one of them issues exactly one
  `Read(nameKey, "main")` and returns that definition's user prompt, system
  prompt, and config. The zero-reads half is the discriminating property: a
  build reading each definition to fill the list passes every content
  assertion and fails this.
