# D14-delivery

What prompts does when the events app delivers an event to it: `Deliver`, the one method of the run core (`internal/runs`) that the event bus calls. For every prompt holding a subscription whose pattern matches the delivered event's name it makes one run of that prompt, however many of its subscriptions match, as the prompt's owner and with the owner's email, with the event as its input, unless the prompt already has a run from that event; and it answers the events app whether the delivery is done, irrelevant, or to be delivered again, exactly as scripts answers it. This document declares `Deliver` and states what it does. `D04-store` declares the subscriptions, `Subscribers`, `Delivered`, the trigger word `event`, the run's `Event`, and the prompt's `OwnerEmail`; `D07-runs` declares the run core, the copy constants its refusals are worded with, `runs.Request` with its `Caller` and `Cause`, the run spec and environment, and everything a run does once `Run` makes it; `D10-trail` states the run's events as the trail shows them; `D03-serve` mounts `Deliver` behind appkit's `events.DeliveryHandler` and `events.DeclarationsHandler` at `events.EventsPath` and `events.DeclarationsPath`, inside `telemetry.Middleware` and outside `identity.Require`; `D11-tools` declares `subscribe` and `unsubscribe`, which make and remove the subscriptions.

Delivery is scripts' unchanged but for what a run is. A run is an agent session, not a Python script, so there is no ref and no git: nothing is resolved or unpacked between the delivery's checks and the run's process. The departures are these. The run carries the owner's email, which scripts never carried: the run spec holds the owner's user id and email (decision 11), and an event run has no caller of its own, so the email is the one the prompt kept from its creator (`OwnerEmail`). The run's record carries the prompt's model as the delivery read it. And because making a run no longer waits on git, the runs of one delivery need not be made side by side; the order in which one delivery makes its runs is not contract.

## What is someone else's

How a delivery reaches prompts is appkit's events contract, read from the published `appkit/events` package: `events.DeliveryHandler` refuses a request that is not a valid delivery (a method other than `POST`, a body that is not JSON, one delivered event and its attempt, or a body larger than `events.MaxDeliveryBytes`), picks the handler registered for the event's name, else the matching pattern with fewest stars, else the `*` handler, calls it with the request's context (to which it adds the event's cause with `events.NewContext`) and the `events.Delivery`, and writes the answer: `events.OK()` and `events.Skip()` as status 200, `events.Fail(msg)` as status 500 carrying `msg`, which the events app retries. `events.Outcome` is a comparable struct, so a test compares outcomes with `==`. prompts registers one `*` handler, `Deliver`, so it accepts every event name, and declares that it emits none: `events.DeclarationsHandler` with a nil emitter answers `{"emits":[],"accepts":["*"]}`. The delivery carries no identity: its request id is the one `telemetry.Middleware` read from `X-Request-Id` or minted, which it places in the request's context as an `identity.Caller` and which `Deliver` reads with `identity.FromContext`. `Event.MarshalJSON` of a delivered event (a positive `Seq` and a set `Received`) is the canonical text with the eleven members `id`, `time`, `service`, `event`, `request_id`, `user`, `attrs`, `cause`, `depth`, `seq` and `received`, and no `attempt`. What the events app retries, and when, is its own; prompts only makes redelivery safe.

## Matching and making

`Deliver` looks at the event's `event` (its name) and `id` only. Its **subscribers** are the prompts `Subscribers` names for the name, of every owner: each prompt holding at least one subscription whose pattern matches the name word for word under appkit's rule, a `*` standing for exactly one word, once however many of its patterns match; neither the event's `attrs`, nor its `service`, nor its `user` narrows them, so a prompt that cares which repository a push moved reads its input and decides. For each subscriber it makes a run as `Run` makes one, except that it is never refused for a full queue, with a context the delivery's end does not reach, and a request whose `Input` is the event's canonical JSON, whose `Caller` is the prompt's owner, the owner's email as the prompt keeps it, and the delivery's request id, and whose `Cause` is the event's id and depth. So the run is a run like any other — same folder, same child, same spec, same limits, same endings and pruning — with trigger `event`, its `Event` the event's id, its environment carrying `IKIGENBA_EVENT_ID` and `IKIGENBA_EVENT_DEPTH`, its spec carrying the owner, the email, the request id and the cause, its first user message the prompt's text followed by the event, and its events under the delivery's request id and the owner. The runs of a delivery share the core's `RUN_MAX_ACTIVE` slots and its one queue with the runs `run` makes: a delivery's run made while every slot is taken is queued, and its `run.started` comes when its process starts. A delivery is all or nothing for the runs it needs: before making any it counts the subscribers that have no run yet from the event, and refuses the delivery when there are more of them than the free slots and free queue places together; the runs it then makes are never refused for a full queue, so the queue may briefly hold more than `RUN_MAX_QUEUED`, as it may for `run`.

One prompt gets at most one run from one event. `Run` asks `Delivered` first, so a redelivered event makes nothing for a prompt that has its run, whether that run is running, ended or pruned; a delivery arriving while an earlier attempt of the same event is still making a prompt's run (the events app retries after its own attempt timeout) is refused for that prompt at once with `runs.ErrStarting`, and answered `events.Fail(runs.Starting)`, so the events app tries again and finds the run made; one core never starts two processes for one event and prompt. This rests on `D07-runs` refusing such a `Run` call with `runs.ErrStarting` at once, before it reads `Config.Now` or `Config.Rand`, as scripts' run core does; the tests that hold a making at a `Config.Rand` read depend on that order. The run and its delivered-event memory are written in one transaction (`D04-store`), so a run recorded is a delivery remembered, across a restart too. A prompt deleted while its run was being made has nothing to make.

## Answers

- `events.Fail(runs.Stopping)` once `Drain` has been called, before anything is read or made, and when a subscriber's run was refused by the drain or cut off at its deadline: a run started now would only be killed, and the events app delivers the event again to a prompts serving again.
- `events.Fail(store.Unreachable)` when the catalog cannot be read to find the subscribers, or when a subscriber gets no run for any other reason (a catalog that will not take the record, a folder that cannot be made): treating the event as one nobody is subscribed to would lose the run for good.
- `events.Fail` with `runs.NoRuns` filled with the reason `Config.Unavailable` holds, when some subscriber has no run yet from the event and prompts started without a control group to run prompts in: recording the run as one that could not start would spend the event.
- `events.Fail` with `runs.QueueFull` filled with `RUN_MAX_QUEUED`, when the subscribers that have no run yet from the event outnumber the free slots and queue places: starting some and not others, or dropping one, would lose a run.
- `events.Fail(runs.Starting)` when an earlier attempt of the same event is still making a subscriber's run.
- `events.Fail(runs.NoEventID)` for an event without an id, which appkit's handler never passes on; nothing is made.
- `events.Skip()` when no subscription matches the name: there is nothing to retry. A call during part of which the catalog fails may answer either this or `events.Fail(store.Unreachable)`, depending on whether its read of the subscribers met the failure; the requirements fix the answer only for a catalog failing throughout the call or not at all.
- `events.OK()` when every subscriber has its run from this event, made now or by an earlier delivery (a call that made every run itself answers so even if the catalog fails just after), a run that could not start and was recorded `failed` included: its failure is the run's, and delivering again would fail the same way.

A delivery that is refused keeps every run it did make; the redelivery makes the rest and nothing twice. `Deliver` returns only once every run it makes is recorded or abandoned, so an accepted delivery's runs are in the catalog, and in `runs` and `result`, by the time the events app has its answer.

## Decisions

- `Deliver` is a method of `*runs.Core`, not a package of its own: the core already holds the store, the drain and `Run`, and a method value is an `events.Handler`, so `D03-serve` registers `events.Handlers{"*": core.Deliver}` and needs no new configuration.
- The event run's email is the prompt's `OwnerEmail`, the creator's `X-User-Email` kept at `create`: the delivery carries no identity, and the run spec carries an email (decision 11), so the prompt keeps one for the runs no caller asks for. An empty `OwnerEmail` gives an empty email.
- Runs are recorded before the answer, as `run` records them before answering: the store records a run only once its process has started, it was queued, or it failed, so the process of each started run starts before the answer and the agent runs on after it. A run made after an `OK` could be lost by a stop in between, and one acknowledged but not yet recorded would be missing from `runs` when a caller looks for it.
- The delivery's own context does not cut a run off: the events app gives up on an attempt after its own attempt timeout, and a run cut off with it would be cut off again on every retry. The run goes on and is recorded, and the retry finds it.
- The drain refuses every delivery, a delivery no prompt is subscribed to included, so a stopping prompts answers the events app one way.
- The unavailable and queue-full refusals come only once the subscribers that need a run are known: an event nobody is subscribed to, or one every subscriber already has its run from, is answered as before, since retrying it would change nothing. The refusal's wire is the events app's; the texts are the same copy constants the tools answer with, so an operator reading the events app's failures reads what a model would.
- The capacity check is the delivery's, not each run's, because starting some subscribers' runs and not others would lose a run; a run `run` makes concurrently may still take a counted place, and the queue then briefly holds more than `RUN_MAX_QUEUED`.
- Matching ignores everything but the name, so the subscribers of one name are one read of the catalog; the store does the matching (`D04-store`), so the delivery sees each matching prompt once and never decides which subscription matched, which nothing records.
- Scripts made a delivery's runs side by side so that one script's git did not wait on another's. prompts has no git, so it states no such requirement.

## Consumer tasks

Serving (`D03-serve`), `core` being the run core: `h := events.Handlers{"*": core.Deliver}`; `events.DeliveryHandler(h)` at `events.EventsPath` and `events.DeclarationsHandler(nil, h)` at `events.DeclarationsPath`, both inside `telemetry.Middleware(w, ...)` and outside `identity.Require`, by exact path.

`Deliver` itself, `rid` the request id `identity.FromContext(ctx)` gives: after `Drain`, `events.Fail(runs.Stopping)`; with an empty `d.Event.ID`, `events.Fail(runs.NoEventID)`; `subs, err := st.Subscribers(ctx, d.Event.Name)`, an error being `events.Fail(store.Unreachable)` and none `events.Skip()`; then `st.Delivered` for each, and `events.OK()` when none needs a run; with `Config.Unavailable` set, `events.Fail(fmt.Sprintf(runs.NoRuns, reason))`; with more needing a run than free slots and queue places, the queue-full answer; `b, _ := d.Event.MarshalJSON()`; for each `p` of `subs`, `_, err :=` the making of the run `c.Run(context.WithoutCancel(ctx), p, runs.Request{Input: b, Caller: identity.Caller{UserID: p.Owner, Email: p.OwnerEmail, RequestID: rid}, Cause: events.Cause{ID: d.Event.ID, Depth: d.Event.Depth}})` would make, less its queue-full refusal, a nil error, `store.ErrDelivered` and `store.ErrNotFound` meaning the prompt has, or needs, no run, `runs.ErrDraining` and `runs.ErrCutOff` the stopping answer, `runs.ErrStarting` the starting answer, and anything else the unreachable one; then `events.OK()` when every one is settled.

A test builds a store over its own catalog, a writer over a `*telemetry.Capture` and a core whose `BaseURL` names an `httptest` provider and whose `Keys` hold a key for the host of a model it picked from `agentkit.Catalog()`, as `D07-runs`' tests do, the child being the test binary's own `agent` role; creates prompts of two owners with `st.Create`, one with an `OwnerEmail`; subscribes them with `st.Subscribe`; and calls `core.Deliver(identity.NewContext(ctx, identity.Caller{RequestID: rid}), events.Delivery{Event: ev, Attempt: 1})` with an `events.Event` it builds (a positive `Seq` and a set `Received`), comparing the outcome with `events.OK()`, `events.Skip()` or `events.Fail(...)` by `==`, then reads `st.Runs`, the run's folder and transcript, what the provider received, and the capture. A prompt with `tools` `["bash"]` whose provider answers first with a call of Bash printing the environment shows the environment in the transcript's tool result; one with `["suite"]` whose provider calls a gateway tool shows the identity and cause the gateway received, the gateway being an appkit `mcp.Server` the test serves on a Unix socket named in a services file. It drives the same through `httptest` and `telemetry.Middleware(w, events.DeliveryHandler(events.Handlers{"*": core.Deliver}))` with a body `json.Marshal` makes of the event and its attempt, to see the request id flow. It holds a run's making with a `Config.Rand` whose `Read` blocks until the test releases it, to race deliveries, to fail the catalog with `SetFailing(true)` mid-delivery, or to call `core.Drain` with a done context mid-delivery; it calls `core.Drain` first to see the stopping answer. It fills the slots and the queue with runs whose provider holds its answer until the test releases it, with `MaxActive` and `MaxQueued` small, to see the queue-full answer and a delivery's run queued, and builds a core with `Unavailable` set to see that refusal.
