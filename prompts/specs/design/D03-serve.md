# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail prompts records of itself from its start to its stop, and the rules its one handler keeps on every request — which route a path falls to, the identity gate around every route but the events app's two, the request's id and its two events, and how a listener is served and drained. It covers, with what stopping, pruning and the provider keys add to a start and a stop, and what event delivery adds to the routes: a clean start, a first start, a start with no services file or no telemetry, a start with none of the five provider keys, a start that prepares the control group it runs every prompt run in or, without one, serves with runs unavailable, a start that settles runs a dead prompts left `running` or `queued` and prunes what is past keeping, a start over a catalog a newer prompts upgraded, which warns and serves, a stop that drains requests and runs and abandons the queue, a stop whose drain runs out on a request or on a run, a restart, and every way a start is refused.

`D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, `BaseURL`, `ScriptAfter` and `Cgroup`, the display string `main` reads, `cli.Run`, the keys `Run` may look up, and where the catalog and the runs directory resolve under `Process.Dir`. `D02-cli` declares the exit codes `cli.ExitSuccess`, `cli.ExitServerFailed` and `cli.ExitUsage`, and decides that an empty `Args` means serve. `D12-limits` declares `settings.Read`, `settings.Settings` and `settings.Error`. `D01-layout-and-run-seam` also declares the root package's `Migrations`, and names appkit's `db` package, whose `db.Open` with its `db.Config` fields `Service` and `Stderr`, `db.Status`, `DB.Close` and `DB.SetFailing` this design uses as appkit states them; `D04-store` declares `store.New`, `store.Config`, `store.Unreachable`, `store.PastKeeping` and the statuses and reasons. `D05-agent` declares `agent.KeyVariable` and `agent.Offering`; `D07-runs` declares `runs.New`, `runs.Config` with its fields, `(*runs.Core).Recover`, `Prune` and `Drain`, `runs.ErrDraining`, `runs.ErrCutOff`, `runs.Stopping`, `runs.NoRuns` and `runs.QueueFull`; `D06-runner` declares what each run's own control group holds. `D08-pages` declares `pages.ServiceName`, `pages.Load`, `pages.Config` and `pages.Handler`; `D09-run-files` declares what a run file path is, `web.FilesConfig` and `web.Files`; `D11-tools` declares `tools.Config` and `tools.Register`, and the drain refusal; `D14-delivery` declares `(*runs.Core).Deliver` and what a delivery answers and makes; `D02-cli` declares the nginx fragment that closes `/events` and `/declarations` at the public name. appkit's `telemetry` package owns the events, the writer and the request middleware this design wires; its `identity` package the gate, `Require`; its `page` package the shared files under `/_appkit/`; its `mcp` package the endpoint; its `events` package `EventsPath`, `DeclarationsPath`, `Handlers`, `DeliveryHandler` and `DeclarationsHandler`. agentkit names the five hosts, `agentkit.HostAnthropic`, `HostOpenAI`, `HostGemini`, `HostXAI` and `HostOpenRouter`. This document declares `server.Serve`, `server.DrainError`, `web.Config` and `web.Handler`, and says in what order `Run` checks its start and which refusal touches what, how it takes the socket, reads the provider keys, opens the catalog and the runs directory, settles and prunes the runs, builds the writer, the run core and the handler, tells systemd it is ready, serves and stops.

`internal/server` is a copy of scripts' package of the same name, which scripts copied from sites; with prompts it exists in a fourth app, which makes it a candidate for appkit. Promoting it is a separate change, and until it lands the copy is a debt this design records rather than designs away. Its requirements below are scripts', restated for prompts' module path.

Departures from scripts: prompts runs no git and no Python, so the start has no git or interpreter check and no `REPOS_DIR`, and nothing in it is a `source` or a `limits`; `cli.Process` has no `Environ` or `After`. The drain therefore has no `Halt`: no `run` call waits on a git run, so the run core's `Drain`, whose context ends at the drain deadline, is the whole of the stop's work on the runs. The five provider keys are read once at start and handed to the run core; none being set is never a refusal. `web.Config` loses `Source` and `Limits` and carries the two keep settings the pages quote, `KeepDays` and `KeepCount`.

## The terms prompts serves on

prompts serves on the platform's common terms, the same as every app. It serves only on a listening socket it inherits and never opens one of its own; on a host that is `/run/ikigenba/prompts.sock`, held by `ikigenba-prompts.socket` beside the `Type=notify` `ikigenba-prompts.service`. A deploy restarts the service alone, so the socket and the connections queued on it outlive every restart; prompts' part is to finish what it accepted and leave the socket where systemd put it, so that a connection made while no prompts runs waits in the socket's queue and the next prompts answers it (R-HHBT-L6RK, R-91VP-25Q6).

prompts takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment as it takes the socket, before it starts any process. The same environment may carry `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE`, the code the host is running; prompts reads them once, at start, through appkit's `version.Display` in `main` (`D01-layout-and-run-seam`), and shows the display string it returns as its version in its `service.started`, its pages' footer and about screen, and its MCP `serverInfo`. Neither is ever a reason not to start. `Run` never looks either up. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket `NOTIFY_SOCKET` names, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace.

The suite is a closed system: prompts trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway calling it at its socket to have forwarded them. The manifest declares `guests = false` (`D02-cli`), so every route but two, `/_appkit/` and `/mcp` included, is behind appkit's `identity.Require`: a request with no `X-User-Id` is answered 500 with `identity.MissingBody` before its path's handler or its method is looked at. The two are the exact paths `/events` and `/declarations` (`events.EventsPath` and `events.DeclarationsPath`), on which the suite's events app delivers events and asks which prompts accepts: a delivery carries no user, so neither path is behind the gate. They are closed to browsers by nginx: prompts' nginx fragment answers both 404 at prompts' public name (`D02-cli`). Every request has an id: the one nginx set, or the one appkit's request middleware makes up for it from the writer's random source, which is `Process.Rand`. `Process.Rand` is also where the catalog draws prompt ids and the run core draws run ids, so `Run` hands the writer, the store and the run core one reader that never lets two reads of `Process.Rand` overlap.

prompts' standard error holds only trouble: a start it refuses, a start that cannot prepare its control group and so can run no prompt, a socket it cannot take, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off, the lines appkit's writer writes for an event it could not deliver, and appkit's one warning over a catalog a newer prompts upgraded. A request answered with any status, a tool refused, a run that failed to start, exited non-zero, timed out, was cancelled or was killed at the drain deadline are handled, recorded in the trail, a run or a tool's result, and earn no line. A missing provider key earns none either: it is the run's to discover, as its child's `stderr` (`D05-agent`). What a child writes to its own streams is `D07-runs`' and never reaches prompts' standard error.

## Checking the start

With `Args` empty, `Run` checks, in this order: its twelve settings, through `settings.Read` over `LookupEnv` (`D12-limits` fixes the spelling, the defaults, the order and the text of the refusal); then whether a socket was passed in; then it opens the catalog; then it makes the runs directory. Then it prepares its control group, which is never a refusal (below). There is no git or interpreter check: the child is prompts' own binary (`D06-runner`). Each refusal is the first one that applies.

A bad setting is the caller's mistake: `prompts: `, the `Error` text of the `*settings.Error`, a newline, exit 2. A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one; anything else is no socket passed in, and a count above one is a unit prompts will not guess about. Both are usage errors, exit 2, with the detail line saying how to run prompts. None of these refusals touches `Process.Cgroup`, takes the descriptor, unsets a variable, looks up `PATH`, `NOTIFY_SOCKET`, `IKIGENBA_SERVICES` or a provider key, creates or opens anything under `Process.Dir`, serves, tells systemd anything, or records an event.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv`, before anything else it does, and takes descriptor 3 as its listener: through `Process.Inherit` when a test supplies one, otherwise with `net.FileListener` over the real descriptor, which, as Go's `net` documentation of `FileListener` and `UnixListener.SetUnlinkOnClose` states, leaves the socket's path in place when the listener is closed. A descriptor that cannot be made into a listener is trouble on the host: `prompts: ` and the error, exit 1.

## The provider keys

Once it has taken its listener, `Run` looks up each of the five provider keys once, the variable `agent.KeyVariable` names for each of agentkit's five hosts (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `XAI_API_KEY`, `OPENROUTER_API_KEY`), and hands the run core a map from each host to the value it found, the empty string when the key is unset (`runs.Config.Keys`, `D07-runs`). The run core picks a run's key by the host of its model's offering and hands it to the child on standard input alone (`D05-agent`, `D07-runs`). An answer `LookupEnv` gives later changes nothing: the keys are read at start and hold for the whole `Run`, as the settings do.

A missing or empty key is never a reason not to start, and earns no line: the manifest names the five as secrets, so the host refuses a deploy without them, and a developer's run without one is served all the same. A run whose host's key is empty is started like any other and ends as its child decides, which against a real provider is a refused credential (`D05-agent`). `Run` writes no key anywhere: not to either stream, not to a file and not to an event (`D13-on-a-space` restates the guarantee).

The five keys are in the serve process's own environment, as the host's environment file sets them, and in its memory. A run's `bash` command runs as the same user, so it could read `/proc/<pid>/environ` or `/proc/<pid>/mem` of the serve process. So, once it has taken its listener and before it starts any process or accepts a connection, `Run` makes its own process non-dumpable with `prctl(PR_SET_DUMPABLE, 0)` (through `golang.org/x/sys/unix`, already a direct requirement of prompts' `go.mod`), as the child does for itself (`D05-agent`): a non-dumpable process's `/proc/<pid>/environ` and `mem` are refused to an ordinary user, and ptrace is refused too (proc(5), prctl(2)). A child it starts is dumpable again after `execve`, which is why the child sets the flag itself. A test of `Run` first sets its own process dumpable with `prctl(PR_SET_DUMPABLE, 1)`, since an earlier in-process test of the `agent` role may have left it non-dumpable, and reads the flag while it holds a `run` call before that run has a process, so only a `Run` that made itself non-dumpable before any process passes.

## The catalog, the runs directory and readiness

`Run` opens the catalog with appkit's `db.Open` at `state/prompts.db` under `Process.Dir`, with the migrations `prompts.Migrations()`, the clock `Process.Now`, the service `pages.ServiceName` and, as the writer for appkit's warning, the guarded `Process.Stderr`, and builds the store over that handle with `store.New`, `Process.Now` and the guarded `Process.Rand`. On a first start `db.Open` creates `state/` and the database and applies every migration, so the catalog names no prompt and no run; on a later start it applies only the migrations the catalog has not had. Every failure of `db.Open` is `prompts: cannot open database state/prompts.db: ` and the error's text, each newline in it replaced by a space; the path is always this relative spelling, whatever `Process.Dir` is. A catalog a newer prompts has upgraded records a migration this prompts does not carry. It is not refused: appkit's `db.Open` applies nothing to it and writes one warning line, beginning with the service name it was given, to `Process.Stderr`, once, before `READY=1`, and the start goes on exactly as over any catalog. prompts states nothing about the line's wording: a test compares what `Run` wrote with what its own `db.Open` call, given the same service name and a buffer, writes over the same catalog.

Then `Run` makes the runs directory, `state/runs` under `Process.Dir`, with any missing parent, when it is absent; its failure is `prompts: cannot create directory state/runs: ` and the text of the error `os.MkdirAll` gives for that path. Either refusal is exit 1, before anything is served, before systemd is told anything and before any event is recorded.

Then `Run` builds the run's writer with appkit's `telemetry.New`, whose `Service` is `pages.ServiceName`, whose `Version` is `Process.Version`, and whose sink, standard error, clock, pause and random source are `Process.Sink` (or appkit's socket sink when it is nil), wrapped so that it is handed nothing once the drain deadline has passed, the guarded `Process.Stderr`, `Process.Now`, `Process.Sleep` and the guarded `Process.Rand`; and builds the run core, `runs.New` over the store, the writer, the runs directory, the `PATH` value it looked up, the `IKIGENBA_SERVICES` value (read once, here), the provider keys, `Process.BaseURL`, the nine run settings that are the core's, the control group and reason the cgroup step left (below), `Process.Now`, `Process.ScriptAfter` and the guarded `Process.Rand`. Building either touches nothing.

Then it settles what a previous process left: `Recover` marks every run still recorded `running` as `killed`, finishes every run still recorded `queued` as `failed` with reason `queue_abandoned`, and records each one's `run.finished`; `Prune` then removes every run past keeping, record and folder. Both run to completion once begun, whatever `ctx` does meanwhile. Beyond them the start looks at no run folder but those `Recover` measures and `Prune` removes, and starts no process.

When `Recover` or `Prune` returns an error, the catalog failed under them, and the start is refused: `prompts: ` and `store.Unreachable`, exit 1, before readiness and before `service.started`. A test makes `Recover` fail by making its own database fail once `Run` has opened it (Consumer tasks); a failure of `Prune` alone cannot be isolated that way, so the refusal for `Prune` is proved only as part of the same requirement.

A signal that arrives before `Run` has begun to report ready is a stop, not a failure: exit 0, with no `READY=1`, no connection accepted, and neither `service.started` nor `service.stopping`. Events already recorded by then — the `run.finished` of the runs `Recover` marked — are delivered or written out, within the drain deadline, before `Run` returns. The same holds for a start refused because `Recover` or `Prune` failed.

Then `Run` calls `Process.MCP` once with the writer and builds the handler with `web.Handler` over `Process.Banner`, that server, the `IKIGENBA_SERVICES` value, the store, the run core, the two keep settings and the writer. Nothing about `IKIGENBA_SERVICES` or the file it names can stop a start.

Sending `READY=1` comes first, so a failure to send is reported before anything was served: one line beginning `prompts: ` that names the notification socket's address, exit 1. Once `READY=1` is sent, and before any connection is accepted, `Run` calls `Writer.Ready`, so `service.started`, carrying `Process.Version`, is the first event of a run after the `run.finished` of every run `Recover` marked.

## The control group

On a host the service unit delegates its control group to prompts (the manifest's `delegate`, `D02-cli`), and `main` hands its directory to `Run` as `Process.Cgroup`. Once the runs directory is made, and before the runs are settled, `Run` takes the **cgroup step**, scripts' unchanged: it checks that the group is prompts' alone, its `cgroup.procs` naming `Process.Pid` and nothing else; moves its own process into a child group `main/`; enables the `cpu`, `memory` and `pids` controllers for the group's children; makes the child group `runs/`, writes `RUNS_MEMORY_MAX_BYTES` to its `memory.max` and `RUNS_CPU_PERCENT` percent of one CPU to its `cpu.max`; and enables `memory` and `pids` under `runs/`. Each run's own group is then made under `runs/` by the runner (`D06-runner`). The kernel's control group v2 documentation (`Documentation/admin-guide/cgroup-v2.rst`) proves the file semantics relied on: a process is moved by writing its pid to the target group's `cgroup.procs`; `cgroup.subtree_control` takes several space-separated `+controller` tokens in one write; `memory.max` takes a number of bytes; `cpu.max` takes `$MAX $PERIOD` in microseconds, `max` meaning no limit; and a group with controllers enabled for its children may hold no process of its own, which is why prompts moves itself into `main/` first.

When `Process.Cgroup` is empty, or the check or any creation or write fails, prompts does not refuse to start: it writes one line, `prompts: runs are unavailable: ` and the reason, to standard error before it reports ready, hands the run core an empty `Cgroup` and that reason as `Unavailable`, and serves as on any start, every `run` refused with `runs.NoRuns` filled with the same reason. The reason for an empty `Process.Cgroup` is exactly `no control group was found`. A step that failed part way is not undone. A start refused earlier touches no control group.

## The trail of a run

Every event of the process goes through the run's writer: the request middleware's, the tools', the run core's and the run's own. appkit's writer queues and returns, so neither readiness nor any answer nor any run waits on telemetry; an event it cannot deliver goes to standard error as `prompts: undelivered event: ` and the event's JSON, in the order recorded, and prompts keeps serving. Apart from `service.started`, `service.stopping` and the `run.*` events, every event is recorded while the handler answers a request and carries that request's id; a run's events carry the run's own user and request id (`D10-trail`).

This design assumes a clock that reads times in the UTC years 0 through 9999, the years an RFC 3339 time can spell; what prompts records under another clock is not contract.

## Stopping

When `ctx` is done — in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the context's cause — `Run` at once calls the run core's `Drain`, with a context that ends at the drain deadline. `Drain` at once finishes every queued run `failed` with reason `queue_abandoned`, starting none of them and recording each one's `run.finished`, so a `run` call whose run core call begins from then on is refused with `runs.ErrDraining`, which `D11-tools` answers with `runs.Stopping`, and a delivery whose `Deliver` begins from then on is answered `events.Fail(runs.Stopping)` with no run made (`D14-delivery`). Every other tool and page answers as ever. Requests in progress carry on, and so do the runs already running: prompts signals none of them before the deadline. It drains the server through `Serve`. Once every request has finished and `Drain` has returned, `Run` calls `Writer.Shutdown` with the reason, the text of `context.Cause(ctx)`, which records `service.stopping` as the last event and delivers what is queued, and returns 0 without waiting out the rest of the window.

The **drain deadline** is `DRAIN_SECONDS`, as `settings.Read` returns it, in seconds, the longest `time.Duration` when that many seconds is longer, and it runs on real time: `Process.ScriptAfter` is never used for it, so a drain test runs with `DRAIN_SECONDS=1` and waits about a second. At the deadline `Drain`'s context ends, and `Drain` kills every run still running, its session and control group whole, records each `killed` and records each `run.finished` (`D07-runs`). Only after `Drain` has returned does `Run` call `Shutdown`, so every killed run's `run.finished` precedes `service.stopping`; the window being spent, both go to standard error as `undelivered event` lines and never to the sink: from the drain deadline on, `Run` hands its sink nothing (R-8E23-8TO4). A run killed at the deadline is the stop working as designed: it never makes the stop exit non-zero.

A request still in progress at the deadline is cut off: `Serve` cuts the remaining requests off only after its `stop` has returned, ends their contexts and closes their connections without the rest of their answers, and `Run` says `prompts: stopped with <n> requests unfinished` (`1 request` for one), exit 1, as its last line, less than a second after the deadline. A cut-off request's `request.finished`, recorded after the deadline, is written out or not at all, never delivered. A `run` call whose run core call is still in progress at the deadline, held before it has recorded its run (in its read of `Process.Rand`, `D07-runs`), is made a cut-off call by `Drain`: it records no run, leaves no folder and starts nothing, and `Drain` waits for it to return; its tool answers nothing and records no `tool.called` (`D11-tools`), and its request counts among those cut off. A test holds a request open without sleeping by posting to `/mcp` with a body it never finishes. A test holds a run past the deadline by serving, as the run's provider, an `httptest` server that does not answer the child's request until the test releases it (a **held run**); it learns the child's pid from the `cgroup.procs` of the run's group in its stand-in tree (`runs/<run id>/`, `D06-runner`) while the run is held, and sees "every run gone" once `Run` has returned by finding that pid gone (R-XB1V-UIE6) and scanning `/proc/*/stat`, without starting a process, for any process not gone whose session field is that pid, the child being its session's leader (`D06-runner`). The child's `/proc/<pid>/environ` cannot serve, since the child is non-dumpable (`D05-agent`). A held run has no grandchild; that a `bash` command in a process group of its own is killed with its run's session is `D06-runner`'s, and that the kernel bounds a run's control group is proved on a space (`D13-on-a-space`). A test holds a `run` call before its record with a `p.Rand` that blocks the first read made after its prompts are created until the test releases it, sending `X-Request-Id` so that the middleware draws nothing from it.

## Serving and stopping the listener

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next prompts — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then ends those requests' contexts, closes their connections without the rest of their responses, and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. `stop` is called once, when the drain is over, with a context that ends at the deadline; `Run`'s `stop` waits for the run core's `Drain` and then shuts the writer down. An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `prompts: ` and the error as `Run`'s last line, exit 1. `Serve` gives its server an `ErrorLog` that goes nowhere, since Go's `net/http` documents that a nil one writes to the real standard error. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` because gosec `G112` demands it.

## The handler's routes

`web.Handler` is appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping a router that sorts every request by its path alone, whatever its host: the two **events paths**, exactly `/events` and exactly `/declarations`, go straight to appkit's events handlers, and every other path goes through `identity.Require` to the routes below. Routing is on the request's `URL.Path` as `net/http` decodes it, compared exactly, by hand — no `http.ServeMux`, which would clean `..` with a redirect — and the router itself never redirects:

- exactly `/events`: `events.DeliveryHandler(h)`, `h` being `events.Handlers{"*": Config.Runs.Deliver}`, built once, when the handler is built, so every delivery reaches `Deliver` (`D14-delivery`).
- exactly `/declarations`: `events.DeclarationsHandler(nil, h)`, over the same `h`: prompts emits nothing on the bus and accepts every name.
- exactly `/mcp`: `Config.MCP`, with the eleven tools registered on it by `tools.Register` once, when the handler is built.
- exactly `/`, `/about` and `/tools`: `pages.Handler` (`D08-pages`, which owns their pages and their 405).
- an **appkit path**, beginning `/_appkit/`: appkit's `page.Static()`, unchanged.
- every other path is a **prompt path**, whose first segment is a prompt's name: a **run file path**, as `D09-run-files` defines it, is answered by `web.Files`; every other prompt path — `/<name>/`, `/<name>`, `/<name>/runs/<run id>/`, `/nope`, `/about/`, `/tools/`, `/mcp/tools`, `/events/`, `/_appkit` — is answered by `pages.Handler`, which owns the prompt page, the run page, their redirects, the not-found page, and the catalog refusal on them (`D08-pages`).

`web.Handler` loads the template set once with `pages.Load` and hands it to the pages handler with `Config.Banner`, `Config.ServicesPath`, `Config.Store`, `Config.Runs`, `Config.MCP`, `Config.KeepDays` and `Config.KeepCount`, and to `web.Files` with `Config.Banner`, `Config.Store` and `Config.Runs`. It registers the tools with `Config.Store`, `Config.Runs` and `Config.Telemetry` on `Config.MCP`, the very server it hands the pages handler, so the tools page lists exactly what `tools/list` at `/mcp` advertises, in the same order, each by the first line of its description, and the two cannot drift; and it builds the two events handlers over `Config.Runs`. prompts calls no sibling while serving a request: no route connects to a socket the services file names, the telemetry entry's deliveries excepted. A run's child reaches the gateway on its own (`D05-agent`), and that is not a request prompts serves.

The middleware records `request_bytes` as the bytes of the request body the handler read and `response_bytes` as the bytes of body it wrote (appkit's HTTP middleware design).

## Decisions

- The settings refusal at `Run` (its line, its exit 2, touching nothing) is this design's alone, because it is the first step of the start's order; `D12-limits` keeps the `settings.Error` text. The rule that no socket, `PATH`, `NOTIFY_SOCKET`, `IKIGENBA_SERVICES` or provider-key lookup comes before the settings is also this design's; `D01-layout-and-run-seam` keeps the list of keys `Run` may look up.
- No git and no interpreter check: the child is prompts' own executable, which is there whenever prompts runs. The start order is scripts' with those two steps removed.
- The five provider keys are looked up once, after the listener is taken, so a start refused for its settings or its socket never reads a credential (one refused later, for the catalog or the runs directory, has read them and uses them for nothing); the run core gets them as a map keyed by agentkit's host, an unset key being the empty string. A missing key is not a refusal: the host enforces the five secrets at deploy, and refusing here would only take the pages and tools away from a developer missing one key. The run with no key goes ahead and its child reports the provider's refusal.
- `Run` makes `state/runs` itself, after the catalog and before `Recover`, so its refusal has its own line and comes before any run is marked.
- A failed `Recover` or `Prune` refuses the start with `prompts: ` and `store.Unreachable`, exit 1: starting over unsettled runs would leave records `running` that nothing ends. The line quotes no underlying error, as `D04-store` asks of every consumer of a catalog error.
- `Recover` and `Prune` run to completion once begun even when `ctx` ends during them, and a stop that arrives then is honoured right after, before readiness.
- The events recorded before readiness are flushed (delivered or written out, within the drain deadline) before a start that stops or is refused returns, with no `service.started` or `service.stopping`.
- The drain state is the run core's (`runs.ErrDraining`, `D07-runs`): a `create` or an `update` during the drain proceeds, and only `run` and a delivery are refused. With no git there is nothing for a `Halt` to end: `Drain`'s own context, ending at the deadline, is what kills the runs still running.
- From the drain deadline on, `Run` begins no `Deliver` on its sink: telemetry is to receive none of the events recorded once the window is spent, and `Run` keeps that promise by what it hands the writer as its sink.
- The serve process makes itself non-dumpable, as the child does, because it holds all five keys in its environment and memory and a run's `bash` command runs as the same user; without it, `/proc/<pid>/environ` of the serve process would hand a model every key (CHOICE).
- A `run` call held before its record at the deadline is cut off by the run core (`D07-runs`), which answers it with `runs.ErrCutOff`, and counted among the requests cut off. Its tool's handler then answers nothing and records nothing, as in scripts (`D11-tools`): no `tool.called` and no `run.*` event for it, from the deadline on.
- Killed runs never make the stop exit non-zero; only requests cut off do, through `*server.DrainError`; nor do queued runs abandoned at the signal.
- The cgroup step is never a refusal: without it prompts serves every page and every tool but `run`. Its first check, that `cgroup.procs` names prompts' process alone, keeps the exec'ing test from writing into the developer's real control group tree.
- The reason travels to the run core as `runs.Config.Unavailable`, so the refusal quotes exactly the reason the start printed.
- The stop line is always `Run`'s last write, which places it after every `undelivered event` line.
- There is no apex host and no guest: every request goes to the same routes whatever its `Host`, and every route but the two events paths is behind `identity.Require`, `/_appkit/` included.
- The events paths are outside `identity.Require` and inside `telemetry.Middleware`, matched exactly, as `/mcp` is, so a path beneath either is a prompt path, answered with the not-found page, and still behind the gate. Which methods and bodies they accept, and the status and body of each outcome, are appkit's events contract.
- `web.Config` carries `KeepDays` and `KeepCount` in place of scripts' `Limits`: they are the only settings the pages quote, and prompts has no `limits` package.
- `/tools` is one of prompts' own exact paths, like `/about`: the pages handler draws it from `Config.MCP`'s registered tools, so `tools` is a name no prompt may have (`D04-store`).
- The handler has no random source of its own: the request ids are the middleware's, drawn from the writer's.
- appkit's warning over a catalog ahead of the binary goes straight to `Process.Stderr` as `db.Open` writes it, so every requirement that bounds what a start writes to standard error once the catalog has opened admits that line.
- `internal/server` is copied from scripts unchanged in behaviour; the debt is recorded in prose.
