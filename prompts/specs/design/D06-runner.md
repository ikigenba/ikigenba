# D06-runner

How prompts starts a run's process and ends it. This document is `internal/runner`, the seam between the run core and the operating system: `Start` launches prompts' own binary as `prompts agent` (`D05-agent`, `D02-cli`) in a directory the caller names, with exactly the environment the caller gives and exactly the standard input the caller gives, in a session and process group of its own and, when the caller names one, in a control group of its own bounded by the memory and process limits the caller gives, and returns a `*Process` whose `Wait` answers how the child ended and whose `Kill` ends the child, and with it the whole session, and says whether it ended the child before the child ended on its own. It declares every exported name of `internal/runner` and states what each does. `D07-runs` composes the environment and the run spec it hands in as standard input, makes the run's folder, bounds the output through the writers it hands in, enforces `PROMPT_SECONDS`, decides what status an ending is recorded with, and maps a failed `Start` to `start_failed`. What the child does with its spec is `D05-agent`'s.

## The contract and the wrapper

The contract is the command, the working directory, the environment, the standard input, the two output streams, the session, and what an ending reads as. The command is fixed inside the runner (decision 1): the file `os.Executable()` names, with the one argument `agent`. That literal is the runner's own; `internal/runner` does not import `internal/agent`, and `D05-agent` declares `agent.Command` with the same value, which is the word `D02-cli` dispatches the role on. How the process is wrapped is the runner's own: the first implementation is a plain `exec` of the binary, and bubblewrap is the planned second, which binds the run folder at a fixed path and, unlike scripts' plan, keeps the network, since the model is on the other side of it (decision 10). Nothing above this package knows which is in use, so every requirement here is one both satisfy: the child finds its paths only through the variables it is given, signal deaths read as 128 plus the signal, and the session is killed whole. The run core never names the binary's path, never sets a process attribute, and never sends a signal itself.

## Starting

`Start` asks `os.Executable()` for the binary's path each time it is called, so it starts whatever file the running binary is at that moment, and runs it with the argument list that path followed by the one argument `agent`. It consults no `PATH`: the environment the caller gives is the child's and nothing else's. A file that cannot be executed is a `Start` that returns an error, which the run core records as `start_failed`. So is an `os.Executable()` that fails, which on Linux means `/proc/self/exe` cannot be read. That case is intended but not contract: no test the rules allow can make `os.Executable()` fail in the test binary, so no requirement states it. The process runs as prompts' own user and group. Its working directory is `Spec.Dir` as the process sees it (the bubblewrap runner may bind it elsewhere), its environment is exactly `Spec.Env`, nothing added, and it holds no open descriptor of the calling process but its three standard streams, whatever the calling process has open: prompts' own listening socket and database, and the run's control-group directory, are never a run's. It is the leader of a new session and of a new process group in it (`setsid(2)`), and everything it starts, whether it stays in the child's process group or moves to a process group of its own, as toolkit's `Bash` moves every command, stays in its session, where the runner finds it. `Start` returns as soon as the process is running; it never waits for it. A context ended before `Start` starts nothing; once `Start` has returned, the context is no longer consulted, because a run outlives the request that started it and is ended only by `Kill`.

## Standard input

Scripts gave its child an empty standard input. prompts hands the run spec, the API key for the model's host among it, on standard input and nowhere else (decision 11), so `Spec` gains `Stdin`: the child reads exactly those bytes on descriptor 0 and then end of file; a nil or empty `Stdin` is end of file at once. The bytes reach the child only there, through a pipe: never as an argument, never in its environment, never in a file the runner writes, since a key the runner wrote to a file, even one it opened as descriptor 0 and removed, would have touched disk. Descriptor 0 being a pipe is what a test can see. Delivering them never holds anything up: `Start` does not wait for the child to read them, and a child that exits, or closes its standard input, without reading them all still ends as it ended, the rest being dropped; `Wait` never waits for them to be read. The child closes its standard input once it has read the spec (`D05-agent`).

## The control group

When `Spec.Cgroup` names a directory, the run gets a control group of its own there, the run core naming it `<runs group>/<run id>` (`D07-runs`). `Start` makes the directory (never a missing parent; a directory already there is used as it is), writes the group's limits into it, `memory.max` `Spec.MemoryMax`, `memory.oom.group` `1`, `pids.max` `Spec.PidsMax` and `memory.swap.max` `0`, then opens the directory and asks `statfs(2)` what file system holds it. On a cgroup2 file system (`CGROUP2_SUPER_MAGIC`), the real tree, the process is created directly in the group: `syscall.ForkExec` with `SysProcAttr{Setsid: true, UseCgroupFD: true, CgroupFD: <the directory's descriptor>}`, which is `clone3(2)` with `CLONE_INTO_CGROUP`, and nothing is written to `cgroup.procs`. So on a real tree no memory and no process of a run is ever charged to prompts' own `main/` group: the child, and every process it starts, `bash` and what `bash` runs included, whatever process group or session it moves to, is born in the run's group under its limits. On any other file system, a stand-in only a test provides, and when `Cgroup` is empty, `Start` starts the process with `SysProcAttr{Setsid: true}` alone; on a stand-in it then writes its pid to `cgroup.procs`, and a write that fails kills it. A limit write that fails, a directory that cannot be made or opened, or a process that cannot be created in the group, starts nothing or kills what it started, and `Start` returns an error, which the run core records as `start_failed`; a directory `Start` made is removed again. When the child has ended, `Wait` writes `1` to `cgroup.kill`, which kills every process still in the group, the ones that left the session included, and removes the directory; a directory that cannot be removed does not change what `Wait` answers. An empty `Cgroup` gives the process no group of its own and makes `MemoryMax` and `PidsMax` meaningless; the run core never passes one when runs are available, but a test of the runner, or of the core, may.

Every operation on the group is a plain file operation under `Spec.Cgroup` — make a directory, write a file, remove the directory — but the placement, which on the real tree is the `clone3` above, so a test hands the runner a temporary directory standing in for the tree and reads back the files, the stand-in's `cgroup.procs` showing where the process was put; a real control group is never available to a gate, and the cgroup2 path is proved by the sandbox and space exercise (`D13-on-a-space`), not by a gate. The writes carry no newline. On a real cgroup file system the interface files already exist when the directory is made, a write to one is the kernel's to accept or refuse, and the directory is removed with `rmdir` once no process is left in it (`SIGKILL` being asynchronous, the runner waits for the group to empty, as it waits for the session); on a stand-in the files are made by the writes and removed with the directory. The file system type decides only the placement; every other step is the same on both.

## Output

What the processes of the child's session write to standard output and standard error, a `bash` in a process group of its own included, is copied to `Spec.Stdout` and `Spec.Stderr` as it arrives, in order, every byte written before the child exited delivered before `Wait` returns. A writer that fails does not stop the process or block it: the rest of that stream is read and dropped. Bounding what is kept is the writer's business (`D07-runs`). A nil writer discards its stream.

## Ending

A run is the child's: `Wait` returns when the child's own process has ended, whatever it started. The run's processes are the child's **session**: the child, every process in its process group, and every process that moved to a process group of its own without leaving the session. toolkit's `Bash` starts every command the model runs that way (`Setpgid`, verified in toolkit's `bash.go` at the pinned tag), so a `bash` command is out of reach of a signal to the child's process group but never out of its session, since `setpgid(2)` only moves a process between groups of one session. When the child ends, the runner kills whatever is left in its session before it collects the child's status, and `Wait` returns only once every process of the session is gone, collected or a zombie, since `SIGKILL` takes effect asynchronously, while the session's id is still the child's pid and cannot be reused by another run; so nothing a run starts and leaves in its session, a `bash` command still running included, outlives the run, writes to its output after it, or holds `Wait` open. Linux has no call that signals a session, so the runner kills one by its members: it reads `/proc`, takes every process whose session field in `/proc/<pid>/stat` is the child's pid, and for each opens a pidfd (`pidfd_open(2)`), reads that process's session again, and only when it is still the child's sends `SIGKILL` through the pidfd (`pidfd_send_signal(2)`), then reads `/proc` again, until no member is left that is not gone. A pidfd names one process for that process's whole life, so a member whose pid another process took between the read and the signal is never signalled: the session is re-read only after the pidfd names the process, and a signal through it reaches that process alone, alive or a zombie, never the pid's next holder. The session id itself cannot be reused while the child is unreaped, since it is the child's pid. A process that forks while the scan runs is caught by the next pass, as its child is born in the session. This holds with and without a control group, so in development and in tests, where `Cgroup` is empty or a stand-in, every `bash` command a run leaves is ended with the run.

A process that left the session with `setsid` is out of reach of the session kill. With a control group it is still in the run's group, and the `cgroup.kill` `Wait` writes once the child has ended reaches it: on a host, where every run has a control group (`D07-runs`), the end of a run, `Kill`'s included, since a killed child ends at once, ends every process the run started. Without one it survives the run; it cannot hold `Wait` open either, since the runner stops reading the streams once the session is gone, and what it writes afterwards is dropped. Bubblewrap's own process namespace closes that gap entirely.

`Wait` answers one number, the run's exit code under the status rule: the status the child exited with, 0 to 4 for the `agent` role (`D05-agent`), or 128 plus the signal's number when the child died of a signal, so 143 for a `SIGTERM` and 137 for a `SIGKILL`, the kernel's out-of-memory kill included: with `memory.oom.group` set, a group that needs more than `memory.max` is killed whole by `SIGKILL`, so the run reads `exited` 137, never `killed`. `Kill` answers from the runner's own record of the child's ending, not from the signal: a signal sent to the child after it has exited but before it is collected still succeeds, against the zombie, so its success says nothing. The runner's reaper records the child's ending under the same lock `Kill` takes. When `Kill` finds no ending recorded, it records that the run was killed, sends `SIGKILL` to the child through the child's own pidfd, and answers true without waiting; the killed child ends at once, and the end of the run then kills the rest of its session as above, before the child is collected; `Wait` then answers 137, whatever status the child's process itself ended with, since that `Kill` and the child's own exit may have crossed. When `Kill` finds the ending already recorded, or a `Kill` that answered true, it answers false, which is how the run core refuses a `cancel` that lost the race to the run's own exit (`D07-runs`). Which ending the run core records, `exited`, `killed` or `timed_out`, is decided by who called `Kill` and why, which the run core knows and the runner does not. `Kill` and `Wait` may be called from any goroutine, any number of times; `Kill` after `Wait` has returned does nothing and answers false.

## Departures from scripts

- The command is prompts' own binary as `prompts agent`, found with `os.Executable()`, in place of `python3.12 main.py` found on the environment's `PATH`. So `Find`, `ErrNotFound`, `PythonVersion` and `Interpreter` are gone, with `D03-serve`'s interpreter check; a child that cannot be found is a failed `Start`, never a start refusal.
- `Spec` gains `Stdin`; scripts' child had an empty standard input.
- There is no counterpart of scripts' "a tree with no `main.py` exits 2": the command names no file in `Spec.Dir`.
- `Spec.Dir` is the run folder, where scripts used the folder's `tree/` (`D07-runs`).
- The child leads a session of its own, not only a process group, and the end of a run, a `Kill`'s included, reaches its whole session. Scripts' reach was the process group; prompts' child starts every `bash` command in a process group of its own, which the group signal would miss.
- The descriptor rule is weaker than scripts' "exactly 0, 1 and 2": the child holds no descriptor of the calling process's beyond 0, 1 and 2. The child is a Go program, whose runtime opens descriptors of its own as it starts (observed), so "exactly" cannot hold; what the rule protects, prompts' socket, database and files never reaching a run, is kept whole.

## Proofs

Linux facts the requirements rest on, from the manual pages and, where marked, observed with a Go child started from Go: Go's `syscall` package on Linux (`exec_linux.go`) calls `setsid` before `setpgid` in the child, and `setpgid(2)` refuses a session leader with `EPERM`, so the child is started with `Setsid` alone, which already makes it a process group leader; pidfd_open(2), a pidfd refers to one process and stays referring to it after it exits, its pid never naming another process through it; pidfd_send_signal(2), a signal sent through a pidfd reaches only that process; it succeeds against a process that has exited and not yet been collected, a zombie, and fails with `ESRCH` only once the process has been collected (observed by the reviewer's probe), which is why `Kill` answers from the runner's record and not from the signal; setsid(2), a process that is not a process group leader, as a newly forked child is not, becomes the leader of a new session and of a new process group in it, both with its pid as their id; setpgid(2), a process may move only to a process group in its own session, so a process made with a process group id of 0 leads a new group whose id is its pid and stays in its session (observed: a Go child started with `Setsid` showed process group and session both its pid in `/proc/<pid>/stat`, and the `bash` it started with `Setpgid` showed its own process group and the child's session); proc(5), the fifth and sixth fields of `/proc/<pid>/stat` are the process group and the session; toolkit's `Bash` at the pinned tag starts each command with `SysProcAttr{Setpgid: true}` and, on its own timeout or cancellation, kills only that group; wait(2) and waitid(2), a child killed by a signal reports `WIFSIGNALED` and the signal, and `WNOWAIT` leaves the child waitable, so its pid, and with it the session id, is not reused until it is collected; execve(2), a descriptor without close-on-exec stays open across exec (observed: a file the parent opened with `syscall.Open` without `O_CLOEXEC` was open in a Go child started with `exec.Cmd`, so the runner must close it), and a Go child opens descriptors of its own as its runtime starts (observed: `anon_inode:[eventpoll]` and `anon_inode:[eventfd]` in its `/proc/self/fd`), which is why the descriptor requirement is stated as "none of the caller's", not as "exactly 0, 1 and 2"; that a child left holding the output pipe keeps a plain `exec.Cmd.Wait` from returning, which is why the session is killed before the status is collected and the streams are not waited on past it; and that `SIGKILL` is asynchronous, which is why `Wait` waits until every process of the session is gone rather than returning when the signal is sent. execve(2) and credentials(7): a process keeps its parent's user and group ids across fork and exec unless the file executed is set-user-ID or set-group-ID, which prompts' binary is not, so the plain runner sets no credential. pipe(7): a pipe holds 65536 bytes by default, a write with no reader left fails with `EPIPE`, and the `os/signal` documentation states that a Go program writing to a broken pipe on a descriptor other than 1 or 2 gets `EPIPE` rather than dying of `SIGPIPE`; so a 1 MiB `Stdin` exceeds what a pipe holds unread, and a child that exits unread makes the runner's write fail, which it drops. Go's `os.Executable` documentation: it returns the path of the executable that started the current process; on Linux it reads the link `/proc/self/exe` (and trims a trailing ` (deleted)`), failing when that cannot be read. Go's `os/signal` documentation: a `SIGTERM` the program does not handle makes it exit, and it exits by that signal (observed: a Go child that sent itself `SIGTERM` reported `WIFSIGNALED` with `SIGTERM`, exit code 143 under the status rule). Control groups, from the kernel's `Documentation/admin-guide/cgroup-v2.rst`: a group is a directory of the cgroup file system, made with `mkdir` and removed with `rmdir` once it has no live process and no child group; writing a pid to `cgroup.procs` migrates that process into the group, and a process's children are born in its group; `memory.max` is the hard memory limit, past which the group's processes are killed by the out-of-memory killer, and with `memory.oom.group` `1` the whole group is killed together; `memory.swap.max` `0` gives the group no swap; `pids.max` bounds the processes in the group, a `fork` or `clone` past it failing with `EAGAIN`; and writing `1` to `cgroup.kill` sends `SIGKILL` to every process in the group and its descendants. `clone3(2)`: with `CLONE_INTO_CGROUP` the child is created in the cgroup whose directory descriptor `cgroup` names; Go's `syscall.SysProcAttr` documents `UseCgroupFD` and `CgroupFD` as that flag and descriptor on Linux. `statfs(2)` reports `CGROUP2_SUPER_MAGIC` (`0x63677270`) as the type of a cgroup2 file system.

## Decisions

- The command is fixed in the runner, not passed in `Spec`: the contract is "this binary, `agent`", and a caller that cannot name another command cannot drift from it. The literal lives in the runner so the runner does not import the child's package.
- `Start` asks `os.Executable()` at each call rather than once at start, the way scripts looked the interpreter up at each call, so a binary that can no longer be found is a `start_failed` run rather than a failure nobody records.
- The test binary is the child under `go test`: no field names the executable's path, so a test cannot start anything but the test binary's own `agent` role, which is what the test rules allow.
- `Stdin` is a byte slice, not a reader: the spec is small and whole before the run starts, and a slice cannot block `Start` on a caller's reader.
- `Wait` returns one `int`; whether a signal was the runner's own is told by `Kill`'s answer, and a writer's failure is the writer's to remember.
- `Kill` answers a `bool` because only the runner can tell, without a race, whether the kill reached the child before it exited; the run core uses it to refuse a `cancel` of a run that had already ended.
- The session is killed before the child's status is collected, so the session id stays the child's pid, which no other process can take, while the scan runs. Members are signalled through pidfds after their session is re-read, so a member's pid reused by another process is never signalled.
- `Kill` and the end of a run reach the child's whole session rather than only its process group, because toolkit's `Bash` gives every command a process group of its own, and a `bash` command left running by a killed or finished run would otherwise outlive it wherever there is no control group: in development and in every test. The control group's `cgroup.kill` stays the reach for a process that left the session.
- On the real tree the process is created inside its group (`CLONE_INTO_CGROUP`) rather than moved there after it starts, because a process moved after it starts has already been charged to the group it started in and could fork there before the move (observed in scripts' sandbox). The stand-in path keeps the move, because a plain file write is what a test can prove; only tests take it.
- `Wait` writes `cgroup.kill` even when the session was already killed, because a process that left the session with `setsid` is out of the session kill's reach but not the control group's.

## Tests

Under `go test` the file `os.Executable()` names is the test binary, so the child a test starts through the runner is the test binary's own `agent` role. Every test package that starts runs (`runs`, `tools`, `web`, `cli`, the root package) has a `TestMain` that, when `os.Args[1:]` is exactly `["agent"]`, does `os.Exit(agent.Run(context.Background(), agent.Process{Stdin: os.Stdin, Stdout: os.Stdout, Stderr: os.Stderr, LookupEnv: os.LookupEnv}))`, and otherwise `os.Exit(m.Run())`; that is the real child, run against the test's `httptest` provider (`D05-agent`). The runner's own tests prove the runner, not the child: like scripts' runner tests, which wrote a `main.py` of their own for the real interpreter to run, the runner's test package's `TestMain` dispatches the same `["agent"]` argument list to a **probe** of the test's own, which reads what to do from its `Stdin` or from a variable in its `Env`, prints what it saw (its `os.Args`, its working directory's entries, `/proc/self/environ`, the link of each entry of `/proc/self/fd`, its process group and session, its user and group ids, what it read from standard input), writes pids to files, waits for a file the test creates, sends itself a signal, or exits with a status the test chose. A probe that needs a process of its own starts `bash` (`bash -c` with a command the test chose), found once by the test with `exec.LookPath` and handed to the probe by its absolute path, in the probe's process group, in a process group of its own (`Setpgid`, as toolkit's `Bash` does), or in a session of its own (`Setsid`); it never starts the test binary again. So no runner test starts anything but the test binary's own `agent` role through the runner and the `bash` that role starts, the two programs the test rules allow.

## Consumer tasks

Starting a run (`D07-runs`): `p, err := runner.Start(ctx, runner.Spec{Dir: <run folder>, Env: env, Stdin: spec, Stdout: out, Stderr: errw, Cgroup: filepath.Join(cfg.Cgroup, id), MemoryMax: cfg.RunMemoryMaxBytes, PidsMax: cfg.RunPidsMax})`, `env` being the thirteen variables `D07-runs` composes and `spec` the bytes of `json.Marshal` of the run's `agent.Spec`, for a run the `run` tool asked for and for one a delivered event started alike (`D14-delivery`), `out` and `errw` its bounded writers over the run's `stdout` and `stderr` files; a non-nil `err` is a failed run with `store.ReasonStartFailed`; otherwise the run is recorded `running` and a goroutine calls `code := p.Wait()` and records the ending. `cancel`, the drain deadline, a prompt's deletion and `PROMPT_SECONDS` call `p.Kill()` and record `killed` or `timed_out` when it returns true; a `cancel` whose `Kill` returns false is refused as a run that has already ended.

A runner test makes a temporary directory, calls `runner.Start` with that directory as `Dir`, an `Env` it composed (`HOME` in its temporary directory, `LANG=C.UTF-8`, the probe's instruction), a `Stdin` of its choosing and writers it reads; the probe tells the test what it saw; the test waits for `Wait` with a deadline that fails the test, and checks that a pid is gone through `/proc/<pid>/stat`. For the control group it names a `Cgroup` under its temporary directory, absent or made beforehand with whatever it wants there (a directory at `cgroup.procs`, a named pipe at `cgroup.kill`), reads the files `Start` wrote while the probe waits for a file the test creates, and sees the directory gone once `Wait` has returned.

## REQUIREMENTS

- R-X8M3-2YWS: The `internal/runner` package MUST export `type Spec struct { Dir string; Env []string; Stdin []byte; Stdout io.Writer; Stderr io.Writer; Cgroup string; MemoryMax int64; PidsMax int64 }`, where `io` is the standard library's `io`; `Dir` is the directory the process runs in, `Env` the whole environment it is given as `KEY=value` strings, `Stdin` the bytes it reads on its standard input before end of file, nil and empty alike meaning none, `Stdout` and `Stderr` where its standard output and standard error go, a nil writer meaning the stream is discarded, `Cgroup` the directory of the run's own control group, which `Start` makes and `Wait` removes, empty meaning the process is given no control group of its own, and `MemoryMax` and `PidsMax` the limits written to that group's `memory.max` and `pids.max`.
- R-X9TZ-GQNH: The `internal/runner` package MUST export `type Process` as a struct type with no exported fields, `func Start(ctx context.Context, s Spec) (*Process, error)`, and the methods `func (p *Process) Wait() int` and `func (p *Process) Kill() bool`.
- R-XB1V-UIE6: prompts' design defines a process as **gone** when no directory `/proc/<pid>` exists for its pid or the state field of `/proc/<pid>/stat` is `Z`; every requirement of prompts' design that names a gone process MUST denote this.
- R-5827-RHPW: When `ctx` is not done, `os.Executable()` returns a nil error in the calling process, and `Spec.Dir` is a directory, `Start(ctx, s)` MUST start the file that `os.Executable()` names, with an argument list of exactly that path followed by the one argument `agent`, with `Spec.Dir`, as the process sees it, as its working directory, whatever `Spec.Env` holds, an `Env` with no element beginning `PATH=` included, and return a non-nil `*Process` and a nil error; so that, under `go test`, a probe printing `os.Args` and the sorted names of the entries of its working directory prints the path the test's own `os.Executable()` returns followed by `agent`, and the names of the entries of `Spec.Dir` in sorted order.
- R-XEPK-ZTM9: The process `Start` starts MUST be started with exactly the elements of `Spec.Env` as its environment and no other variable, so that, for an `Env` with no two elements of the same key, a probe that writes the bytes of `/proc/self/environ` shows exactly the elements of `Env`, each followed by one NUL byte, and nothing else, whatever the calling process's own environment holds.
- R-12YA-5PC4: The process `Start` starts MUST be the leader of a new session and of a new process group in it, so that a probe that reads the process group and session fields of `/proc/self/stat` finds both equal to `os.Getpid()`, and the session field of `/proc/<ppid>/stat`, for its `os.Getppid()`, different from it.
- R-XH5D-RD3N: The process `Start` starts MUST read on its standard input exactly the bytes of `Spec.Stdin`, in order, and then end of file; so that a probe that reads its standard input to end of file and writes what it read to its standard output gives `Spec.Stdout` exactly the bytes of `Stdin`, for a `Stdin` of 1048576 arbitrary bytes, and nothing at all, without waiting, for a nil `Stdin` and for an empty one.
- R-5BPW-WSXZ: Delivering `Spec.Stdin` MUST NOT hold up `Start` or `Wait`: `Start` MUST return without waiting for any of `Stdin` to be read, and when the process exits, or closes its standard input, without reading all of `Stdin`, `Wait` MUST return as R-XS4H-7ARW, R-XTCD-L2IL and R-5AI0-J17A state, the unread bytes being dropped; so that, for a `Stdin` of 1048576 bytes, a probe that waits for a file the test creates after `Start` has returned and then exits 3 without reading its standard input has `Wait` return 3, and one that reads 10 bytes, closes descriptor 0 and exits 0 has `Wait` return 0.
- R-0ZAL-0E41: `Start` MUST give the process the bytes of `Spec.Stdin` only on its standard input, which MUST be a pipe: no argument and no environment variable of the process MUST hold them, and `Start` and `Wait` MUST create, change or remove no entry at or below `Spec.Dir`; so that, for a `Stdin` holding a marker of 32 random bytes in hexadecimal, a probe that reads the link `/proc/self/fd/0` before reading its standard input finds that it begins `pipe:`, for a nil, an empty and a 1048576-byte `Stdin` alike, a probe printing `os.Args` and `/proc/self/environ` and writing nothing to disk prints no marker, and the entries at or below `Spec.Dir`, with their bytes, are the same once `Wait` has returned as before `Start` was called.
