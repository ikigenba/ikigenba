# D05-agent

How one prompt run is run. This document is `internal/agent`, the binary's second role (decision 1): started by the app as `prompts agent`, the child reads a run spec on its standard input, builds an agentkit conversation for the spec's model with the tool groups the spec allows, sends the one user message, runs agentkit's tool loop to the end of that one turn, writes the model's final message (or, with a schema, the accepted object) to its standard output, keeps agentkit's log of the whole conversation as the run's `transcript.jsonl`, and exits with a code from 0 to 4 that is the run's outcome. It declares every exported name of `internal/agent` and states what each does. `D01-layout-and-run-seam` places the package; `D02-cli` dispatches the arguments `[agent.Command]` to `agent.Run` with an `agent.Process` built from `cli.Process`; `D06-runner` starts the binary with the one argument `agent` and the spec bytes on standard input; `D07-runs` composes those bytes with `json.Marshal` of an `agent.Spec`, composes the thirteen-variable environment, reads the exit code and sums usage from the transcript (decision 8); `D03-serve` reads the five provider keys through `agent.KeyVariable`; `D11-tools` checks a prompt's model with `agent.Offering` and its tools with `agent.ValidGroups`; `D12-limits` owns `RUN_MAX_TOOL_CALLS`, which reaches this document as `Spec.MaxToolCalls`; `D13-on-a-space` restates the credential guarantee end to end.

prompts has no scripts precedent for this package: scripts' child was `python3.12 main.py`, and its `D05-git-and-source` is gone with git. The shape follows scripts' D06 and D07: a package-level role function over an injected process seam, outcomes answered as exit codes, and requirements that state outcomes at the seams a test can reach.

## The run spec

The spec is one JSON object, the encoding `json.Marshal` gives of an `agent.Spec`, with exactly fourteen members: `model`, the model's name in agentkit's catalog; `key`, the API key for the host that serves that model by default; `system` and `prompt`, the prompt's system text and its text; `input`, the run's input object; `tools`, the tool groups; `schema`, the output schema; `max_tool_calls`, the run's tool-call bound; `user_id`, `email` and `request_id`, the identity the run acts as; `event_id` and `event_depth`, the cause of an event run; and `base_url`, the endpoint base URL, empty except under test. That is decision 11's list: the limits it names are only `max_tool_calls`, since `PROMPT_SECONDS` and the output bound are enforced by the app around the child, not by the child.

The child reads standard input to end of file and decodes it whole. A spec it cannot use is refused with exit 4 before anything else happens: bytes that are not exactly one JSON object, a member the spec does not name (so a stray `api_key` is caught rather than ignored), a member of the wrong type, an empty `model` or `prompt`, a `tools` list `ValidGroups` refuses, a negative `max_tool_calls` or `event_depth`, an `input` that is neither absent, `null` nor an object. Because `D07-runs` marshals a Go value, `input`, `schema` and `tools` arrive as `null` when the prompt has none: `null` or an absent member means `{}` for `input`, no schema for `schema`, and no groups for `tools`.

As soon as it has read the spec the child closes its standard input, before it sends anything to the provider or the gateway (decision 11, root ruling 3). From then on the key exists only in the memory of the authenticator agentkit builds from `agentkit.APIKeyRotator(spec.Key)`; it is never in the child's environment (the app does not put it there, `D07-runs`), never in a file the child writes and never on its standard error, whichever host serves the model and whether a round trip is answered or fails in transport: agentkit sends every key in a header, never in a URL, and replaces every credential secret of 16 bytes or more in the text of the errors it returns and the records it writes with `RedactionMark`; a key in a header is never quoted by a transport failure's text.

As the first thing it does, before it reads the spec, the child makes its own process non-dumpable with `prctl(PR_SET_DUMPABLE, 0)` (through `golang.org/x/sys/unix`, which prompts' `go.mod` already requires directly). A model's `bash` command runs as the same user as the child and is the child's own child, so on a host whose Yama `ptrace_scope` is 0 it could otherwise open `/proc/<child pid>/mem` and copy the key out of the child's memory; a non-dumpable process's `/proc/<pid>/mem` and `environ` are owned by root and refused to an ordinary user, and ptrace is refused too (proc(5), prctl(2)). The setting is the process's own and is not inherited across `execve`, so `bash` and what it starts stay ordinary. `prctl` with these arguments does not fail on Linux; should it, the child goes on, since no run is worse off than without it. The child writes no file of its own but `transcript.jsonl`: every other file a run leaves is one its tools wrote.

## The environment and the credential

The child reads four variables through `Process.LookupEnv`: `IKIGENBA_RUN_DIR`, where `transcript.jsonl` goes; `IKIGENBA_RUN_ID`, the transcript's id; `IKIGENBA_WORK_DIR`, the root of the file tools and Bash's starting directory; and `IKIGENBA_SERVICES`, read only when the spec offers `suite` (root ruling 4). The first three must be set and non-empty, or the run is exit 4.

The model is looked up with `agent.Offering`, which is exactly `agentkit.Lookup(model, "", "")`: the entry's default host and the best wire on it (decision 3). A model no longer in the catalog, the catalog having changed since the prompt was created, is exit 4. The offering's host names the key's variable through `agent.KeyVariable`, one of the five the manifest declares as secrets; agentkit exports no such map, so prompts owns it. The app, not the child, picks the key (`D03-serve`, `D07-runs`); the child takes `spec.Key` as given and never refuses an empty one: the provider's answer decides, an `auth` failure and exit 1 being the expected outcome.

The endpoint is `agentkit.NewEndpoint(auth)` with `auth` from `Offering.Authenticator(agentkit.APIKeyRotator(spec.Key))`, given `agentkit.WithBaseURL(spec.BaseURL)` only when `base_url` is not empty. With it empty every request goes to the offering's own API-key endpoint, agentkit's default, which only the sandbox check reaches (`D13-on-a-space` owns that check); with it set, to the test's `httptest` server, which is why the spec carries it ("prompts, precisely"). agentkit refuses a base URL that is not an absolute `http` or `https` URL with a host; the child answers that with exit 4. How the key is presented is agentkit's, per wire.

No generation settings are set (decision 3): the conversation's `Settings` is the zero value, so every run takes agentkit's defaults, and nothing is validated at `Send` that `create` could not have refused.

## Tool groups

A group not listed is not offered (decision 4), and the conversation's tools are always in one order, whatever order `tools` lists the groups in: `files` gives toolkit's `Read`, `Write`, `Edit`, `Glob` and `Grep`, each rooted at `IKIGENBA_WORK_DIR`, with no options; `bash` gives toolkit's `Bash` rooted there, which starts every command in that directory with the child process's own environment, the thirteen variables `D07-runs` composes and no key; `suite` gives the gateway's tools in the order the gateway lists them. A toolkit constructor that fails (the work directory missing, or no `bash` on the `PATH` for the `bash` group) is exit 4.

The suite bridge reaches the MCP gateway the way a script does. It reads the services file `IKIGENBA_SERVICES` names with appkit's `services.Read`, takes the entry `List.Find("mcp")` returns, and requires it to be enabled with a socket; an unset or empty variable, an unreadable file, or no usable entry is exit 4, the gateway being unreachable (decision 7). It then builds one appkit `mcp.Client` whose endpoint is the path `/mcp` over a connection to that Unix socket (appkit's `telemetry.SocketTransport`; `telemetry.SiblingClient` would panic without a writer, and the child has none), and lists the gateway's tools once with `ListTools`, before the conversation starts; a listing that fails is exit 4. Every request to the gateway, the listing and each call, carries the spec's user id, email and request id as `X-User-Id`, `X-User-Email` and `X-Request-Id` (`identity.Forward`, which omits an empty one), so the gateway records every `tool.called` under the owner and reaches every service as that user; for an event run it also carries `X-Event-Cause` and `X-Event-Depth` (the client's `HTTPClient` wraps `telemetry.SocketTransport` in a round tripper that calls `events.Forward` with each request's context, which holds `events.Cause{ID, Depth}`; appkit's `mcp.Client` forwards only the caller), as a script sends them on.

Each listed tool becomes one agentkit tool through `agentkit.NewToolFromSchema` with the gateway's name and description verbatim and a nil access function, which agentkit reads as `BlocksAll` (root ruling 1). Its schema is the listed input schema with the `additionalProperties` keyword removed from the root and from every subschema: appkit's generator emits `additionalProperties: false` on every struct object and agentkit's canonical subset refuses the keyword at any depth. Nothing else is rewritten; a schema the subset still refuses is exit 4, and an issue against the gateway, not something the child papers over (decision 4). When the model calls the tool, the bridge sends one `tools/call` with the model's arguments; the result the model reads is the gateway's MCP result object as JSON text, marked as a tool error when the result says `isError` or when the call itself failed (then the failure's text). A failed gateway call is the model's to handle; it never ends the run.

agentkit validates the whole tool set when the turn starts. Two tools sharing a name (a gateway listing a tool called `Read` beside the `files` group, say) is refused there with `agentkit.ErrInvalidConfig`, and the child reads that, too, as tools that could not be built: exit 4.

## One turn

A run is one turn (decision 5). The conversation is `agentkit.New(off.WireFormat, endpoint, off.WireModel, cfg)` with the tools above, the transcript's log, `Limits{MaxToolCalls: spec.MaxToolCalls}` (a zero field is no bound in agentkit, so a spec with `max_tool_calls` 0 runs unbounded; `D07-runs` never sends 0), and, when the spec has a schema, `&agentkit.OutputContract{Schema: spec.Schema}` with `MaxAttempts` zero, which is agentkit's `DefaultOutputAttempts`. A non-blank `system` is added with `AddSystem` as the one system message; a blank one is no system message, since agentkit refuses whitespace-only text and the store has no rule against it (CHOICE). Then one `Send` with one text block, `agent.UserMessage(spec.Prompt, input)`: the prompt text, and when the input, compacted, is not `{}`, an empty line and the compacted input. That is all the child says: no framing text is added by code; the system prompt is the author's and the tools describe themselves.

agentkit runs round trips until the model stops calling tools. Without a schema the run's answer is the text of the turn's last assistant message, its text blocks concatenated, written to standard output as it is, with no newline added. With a schema the answer is the object `agentkit.Output[json.RawMessage]` returns, the bytes agentkit accepted. Either is written only when the turn succeeded, so standard output is empty on every other exit.

Nothing is retried (decision 9): agentkit retries nothing on the turn path under an API key, and the child sends one turn, so a failed round trip ends the run.

## The transcript

Once the spec, the environment, the endpoint and the tools are in hand, the child creates `transcript.jsonl` in `IKIGENBA_RUN_DIR` (truncating any file there) and hands `agentkit.NewLog(file, now, runID)` to the conversation, `now` being `Process.Now` or `time.Now` when that is nil. A refusal before that point leaves no transcript, so the app sums zeros for it (decision 8). The file is written as the run goes, unbuffered: each record agentkit writes is one `Write` of one JSON line, so a run the app kills, cancels or times out keeps everything up to its last complete line. agentkit writes a round trip's `tool_use` records as the stream yields the assistant message that asks for the calls, before it dispatches any of them (agentkit's published design for the event log, and `conversation.go`), so a call's `tool_use` is on disk before its tool runs and a run cancelled during a long `bash` command still shows what it was running. On every return after the file was made the child closes the log, which writes the closing `summary` record, then closes the file.

The transcript holds agentkit's records and nothing else: one `conversation` record (the identity, which names the offering, the auth mode and the wire model and carries no key; the tools; the output contract; the limits), the system message if any, one `turn_start`, the user message, every assistant message, `tool_use` and `tool_result`, the tool-role `message` record agentkit writes after each round's tool results, one `usage` record per round trip carrying that round trip's `agentkit.Usage` and `agentkit.Cost`, an `output` record for an accepted object, a `limit` record for a limit, an `error` record for a provider or output failure, `turn_end`, and `summary`. That is the seam `D07-runs` reads: it decodes each line with `agentkit.LogRecord` and sums the `usage` records. Two facts it relies on, both agentkit's: a round trip that failed still writes its `usage` record (with whatever the provider reported, often zeros), so a provider failure counts one call; and a `tool_use` record is written for every call the model asked for, including the calls of a round that a limit refused, which never ran, while a `tool_result` record is written exactly once for each call that was dispatched (an unknown tool or bad arguments included, answered in-band) and never for a refused one (`conversation.go`, `event_sink.go`).

## Exit codes, standard output and standard error

The exit code is the outcome (decision 7). 0, `ExitAnswered`: the turn ended with a final message, and with a schema a valid object, written to standard output. 1, `ExitFailed`: the provider or model failed, an `*agentkit.Error` of any category other than an output or configuration failure, a 401, a 429, a 5xx, a dropped connection. 2, `ExitLimit`: a limit ended the turn (`agentkit.ErrLimitExceeded`); the only limit the child sets is `MaxToolCalls`. 3, `ExitNoOutput`: no valid output within the attempts (`agentkit.ErrInvalidOutput`, which agentkit carries in an `*agentkit.Error` of category `unknown`, so it is told apart before the category is). 4, `ExitUnusable`: the spec could not be read, or the environment, the model, the endpoint, the tools or the conversation could not be built, the gateway unreachable included. A death by signal reads 128 plus the signal through the runner, and `killed` and `timed_out` are the app's (`D06-runner`, `D07-runs`).

Standard error is empty on 0. On 1 to 4 it is exactly one line, written in one `Write`: `prompts: ` and then one of four copy constants, `Failed`, `LimitReached`, `NoOutput` and `Unusable`, each a format with one `%s`, filled with the failure's text with its newlines turned to spaces, then a newline. For 1 and 3 that text is the `*agentkit.Error`'s own `Error()`, which begins with agentkit's category name (`auth`, `invalid request`, `rate limit`, `overloaded`, `insufficient quota`, `timeout`, `transport`, `unknown`), so the category is on standard error as decision 9 says; agentkit exports no category-name function, and the child invents none. `D10-trail` keeps the category off the trail (root ruling 5). The app bounds and keeps standard error as the run's `stderr` (`D07-runs`).

## Departures and choices

- The child is prompts' own binary, not an interpreter (decision 1); it is tested as the test binary's own `agent` role through the runner (`D06-runner`), against an `httptest` provider found through `base_url`, and in-process by calling `agent.Run` with an in-memory `Process`.
- The child makes itself non-dumpable first thing, using `golang.org/x/sys/unix`, already a direct requirement of prompts' `go.mod` (decision 16) (CHOICE).
- Exit 4 covers every failure to build: spec, environment, model lookup, endpoint, toolkit, the gateway and its schemas, the transcript file, and a tool set agentkit refuses as configuration (CHOICE for the last).
- The transcript is created only once the tools are built, so a refused spec or an unreachable gateway leaves none (CHOICE).
- A blank `system` is no system message (CHOICE).
- The bridge's result text is the MCP result object as JSON, marked an error when `isError` is true or the call failed (CHOICE).
- `UserMessage`'s canonical JSON is `json.Compact`'s output, and "not `{}`" is judged after compacting (CHOICE, as the sheet).

## Tests

The real child is the test binary's own `agent` role started through the runner (`D06-runner`): a test of `runs`, `tools`, `web`, `cli` or the root package serves an `httptest` provider on loopback that answers in the wire of an offering it picked from `agentkit.Catalog()` (it spells no model name), sets `cli.Process.BaseURL` or `runs.Config.BaseURL` to its URL, and reads the run's files. For `suite` it serves an MCP server (appkit's `mcp.Server`, or a handler of its own answering JSON-RPC when it needs a tool appkit would not list) on a Unix socket in a short temporary directory, named as the `mcp` entry of a services file it wrote. A test of `internal/agent` calls `agent.Run` directly, with a `Stdin` over bytes it marshalled that records its `Close`, two recording writers, a `LookupEnv` over a map that records each key, a `Now` it controls, and a run folder of its own; it decodes `transcript.jsonl` line by line with `agentkit.LogRecord`. An in-process test never offers the `bash` group, because `Bash` runs its commands with the calling process's environment, which for an in-process test would be the test process's own; every requirement about `bash`, the environment it sees and the non-dumpable child is proved through the runner, where the child's environment is the one the test composed and `bash` is found once with `exec.LookPath`. An in-process `Run` also makes the test process non-dumpable, which changes nothing a test observes. The empty `base_url` path is `D13-on-a-space`'s sandbox check, never a gate.

## Consumer tasks

Composing and starting a run (`D07-runs`): `off, err := agent.Offering(p.Model)`; `key := cfg.Keys[off.Host]`; `b, _ := json.Marshal(agent.Spec{Model: p.Model, Key: key, System: p.System, Prompt: p.Prompt, Input: input, Tools: p.Tools, Schema: p.Schema, MaxToolCalls: max, UserID: caller.UserID, Email: email, RequestID: caller.RequestID, EventID: cause.ID, EventDepth: cause.Depth, BaseURL: cfg.BaseURL})`; `runner.Start(ctx, runner.Spec{…, Stdin: b, …})`; on `Wait`'s code `c`, `exited` with `c`; usage is the sum over the `usage` records of the run's `transcript.jsonl`.

Reading the keys at start (`D03-serve`): for each of the five hosts, `v, _ := p.LookupEnv(agent.KeyVariable(h))`.

Checking a prompt (`D11-tools`): `if _, err := agent.Offering(args.Model); err != nil` refuses with `UnknownModel`; `if !agent.ValidGroups(tools)` refuses with `InvalidTools`.

Dispatching the role (`D02-cli`): `if len(p.Args) == 1 && p.Args[0] == agent.Command { return agent.Run(ctx, agent.Process{Stdin: in, Stdout: p.Stdout, Stderr: p.Stderr, LookupEnv: p.LookupEnv, Now: p.Now}) }`.

A test of the child: `code := agent.Run(ctx, agent.Process{Stdin: recordingCloser(b), Stdout: &out, Stderr: &errw, LookupEnv: env.lookup, Now: clock.now})`; `code == agent.ExitAnswered`, `out.String() == t`; on a failure, `errw.String() == "prompts: " + fmt.Sprintf(agent.Failed, rec.Err.Error()) + "\n"` for the transcript's `error` record `rec`.
