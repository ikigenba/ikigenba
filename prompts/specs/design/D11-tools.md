# D11-tools

prompts' MCP endpoint is its catalog and its runs offered to models: eleven tools, `list`, `show`, `create`, `update`, `delete`, `subscribe`, `unsubscribe`, `run`, `runs`, `result` and `cancel`, registered on the one `mcp.Server` the handler mounts at `/mcp`. They are scripts' eleven, in scripts' order, with scripts' refusal order and scripts' copy where scripts has a refusal; the repository, the ref and the commit are gone, and a prompt's own fields, `model`, `prompt`, `system`, `tools` and `schema`, stand in their place. This document is `internal/tools`: what `Register` puts on a server, in that order; what a client sees of each tool in `tools/list` (its name, the description written for a model, its input schema, its output schema and its annotations); the argument and result types the package exports; which prompt a `name` argument and which run a `run` argument name; the rules each tool holds its arguments to, the order it checks them in and the copy constant each refusal is worded with; what a success answers and what it changes; the one answer every tool gives when the catalog cannot be reached; the drain refusal; and the `kind` and `outcome` of the `tool.called` each call records.

`D01-layout-and-run-seam` declares the run seam, `pages.ServiceName`, the display string `main` reads, the entity ids (`store.ValidPromptID`, `store.ValidRunID`), the root package's `prompts.Migrations()` and the wiring of the server `main` builds; `D04-store` declares the catalog (`store.Store` and its methods, `Find`, `List`, `Taken`, `Create`, `Update`, `FindRun`, `RunByID`, `Runs`, `Subscribe` and `Unsubscribe` among them, `store.Prompt`, `store.Subscription`, `store.Run` with its `Truncated` method, `store.Usage`, `store.Draft`, `store.Change`, `store.ValidName`, `store.ValidEvent`, the status, reason and trigger words, `store.Unreachable`, the sentinels `store.ErrNotFound`, `store.ErrNameTaken`, `store.ErrEnded` and `store.ErrNotSubscribed`, what a catalog error is and what leaving the catalog unchanged means); `D05-agent` declares `agent.Offering`, the model lookup every check of a model makes, and `agent.ValidGroups`, the rule a list of tool groups keeps; `D07-runs` declares `runs.Core` (`Run`, `Cancel`, `Delete`, `Drain`, `Folder`, `Gone`, `Sizes`), `runs.Request`, `runs.ErrDraining`, `runs.ErrCutOff`, `runs.ErrNoCgroup`, `runs.ErrQueueFull`, `runs.Config` (its `Runs`, `Unavailable`, `MaxActive` and `MaxQueued`), the run folder's entry names `runs.InputFile`, `runs.StdoutFile`, `runs.StderrFile`, `runs.TranscriptFile` and `runs.WorkDir`, the copy constants `runs.Stopping`, `runs.NoRuns` and `runs.QueueFull`, and states how a run is made, queued, started, ended, killed or taken from the queue with its prompt, how its usage is summed from its transcript, and how it is refused while draining, while runs are unavailable and while the queue is full; `D10-trail` declares every `prompt.*` and `run.*` event, their attributes, which outcome records each and in which order, and that `subscribe` and `unsubscribe` record none; `D03-serve` declares `web.Config` and `web.Handler`, which build the tools set, mount the server at `/mcp`, and cut off requests at the drain deadline. This document restates none of them.

## What is someone else's

- appkit's `mcp` server is the transport and the protocol: `/mcp` takes only POST, one JSON-RPC message per POST, one `application/json` answer, no session and no stream; `server/discover` and `initialize`; the 405 for every other method; the malformed-transport checks; and the protocol error for a tool prompts does not have.
- appkit's `AddTool` and schema rule are the Tool object's members and their order, the annotations each `Effect` gives, the derivation of every schema from the Go types declared below, the strict reading of `arguments` and its refusal, a `tools/call` with no `arguments` read as one with `{}` (restated below as prompts' own answer, so that prompts' tests fail should another appkit release stop giving it), the success result a typed handler's output becomes, the `isError` result a handler's error becomes, and the `tool.called` event for every call that reaches a tool, recorded after whatever the handler recorded. A pointer field is appkit's optional member: absent or JSON `null`, it reaches the handler as nil. A `json.RawMessage` field is appkit's one carrier of an arbitrary JSON object, schema `{"type":"object"}`, received as its bytes unaltered and refused, `null` included, when the value is not an object; written in a result, it is the stored bytes unaltered, and a nil one that is not required is left out. That is how `run`'s `input` reaches `input.json` byte for byte, and how a prompt's `schema` is kept and answered byte for byte.
- `main` builds the server with `pages.ServiceName`, the display string, the writer `Run` builds and `Instructions` nil (`D01-layout-and-run-seam`). Routing exactly `/mcp` to it, `identity.Require` around it, `telemetry.Middleware` with `request.started` and `request.finished`, calling `Register` once when the handler is built, and cutting a request off at the drain deadline are `D03-serve`'s.
- Which `prompt.*` and `run.*` events a call records, with which attributes, under which identity and in which order, is `D10-trail`'s: the tools emit `prompt.created`, `prompt.updated` (only when `store.Store.Update` reports a change) and `prompt.deleted` (only after `runs.Core.Delete` has returned) through the writer with the call's own context, and the run core emits every `run.*` event.
- What a run does once made, the child, its spec, its model call and its exit code, is `D05-agent`'s and `D07-runs`'s. A tool never starts a child itself and never reaches a provider.

## What a client is told

All eleven tools are registered with `mcp.AddTool`, in the order `list`, `show`, `create`, `update`, `delete`, `subscribe`, `unsubscribe`, `run`, `runs`, `result`, `cancel`, so every schema is derived from the argument and result types this package exports, and the schemas are stated here whole but for their descriptions. Each tool and each argument carries a description written for a model; the words are copy, held in the source, and a requirement says only that each is there. `list`, `show`, `runs` and `result` change nothing and are `mcp.Read`; `create`, `update`, `subscribe` and `run` add a prompt, a change of its fields, a subscription or a run, `mcp.Additive`; `delete` removes a prompt and every run for good, `unsubscribe` removes a subscription, and `cancel` kills a run, `mcp.Destructive`. That is what the gateway's `describe` reports as each tool's kind and what `tool.called`'s `kind` says.

Every output schema marks required each member that is always present, a non-pointer field tagged `mcp:"required"`; a member that is not always present is a pointer field, untagged, left out when nil, or, for a prompt's `schema`, a `json.RawMessage` left out when nil. No output property carries a description. Every argument carries a description, and a required one is tagged `mcp:"required"`.

`create`'s and `update`'s optional members, `system`, `tools` and, for `update`, `model` and `prompt`, are pointers, so a member sent as `null` counts as not sent. `schema` and `input` are objects: either is absent or an object, and `null` is refused as the arguments are read, before any rule of prompts'.

## Which prompt, which run

Every tool works for its caller alone, the `identity.Caller` appkit hands the handler. A `name` argument names the caller's prompt of that name, as `Store.Find` answers it for the caller's user id. Another user's prompt, a name no prompt has, a prompt's id, and a string `store.ValidName` refuses all name nothing, and are refused alike with the missing-prompt refusal, quoting the value as sent; a string `ValidName` refuses is refused without asking the catalog. A `run` argument names a run of one of the caller's prompts, as `Store.FindRun` answers it; another user's run, an id no run has (a pruned run's, a deleted prompt's), a prompt's id or name, and any string `store.ValidRunID` refuses name nothing, and are refused alike with the missing-run refusal, the last without asking the catalog. The caller so learns nothing of other users' prompts and runs, though their names stay taken for `create`.

## Rules, order and refusals

A handler is reached only with arguments appkit read cleanly. From there each tool checks its rules in a fixed order, and the first that fails is the whole answer, one line from a copy constant of `internal/tools` or `internal/runs`, the value quoted exactly as sent:

- `create`: the name rule (`tools.InvalidName`); the name not taken by any prompt of any owner (`tools.NameTaken`); the model known to `agent.Offering` (`tools.UnknownModel`); the `prompt` text not empty (`tools.EmptyPrompt`); `system` has no rule; the tool groups, when sent, kept by `agent.ValidGroups`, each one of `files`, `bash` and `suite` and none twice (`tools.InvalidTools`, quoting the list as `encoding/json` writes it); the schema, when sent, accepted by agentkit's `ValidateOutputSchema` (`tools.InvalidSchema`, with agentkit's reason).
- `show`, `delete` and `runs`: the prompt.
- `update`: the prompt; then, of the members sent, the model, the `prompt` text, the tool groups and the schema, each by `create`'s rule and in that order.
- `subscribe`: the prompt; then the event pattern, as `store.ValidEvent` reads it (`tools.InvalidEvent`). A pair already subscribed is not a refusal: it succeeds and changes nothing.
- `unsubscribe`: the prompt; then the event pattern; then the pair, the pattern compared exactly (`tools.NotSubscribed`).
- `run`: the prompt; then the drain (`runs.Stopping`); then runs being unavailable (`runs.NoRuns` with the reason prompts gave on stderr as it started); then the queue (`runs.QueueFull` with `RUN_MAX_QUEUED`).
- `result`: the run.
- `cancel`: the run; then that it is still queued or running (`tools.Ended`).

Values are compared exactly as sent, never trimmed or folded: a `prompt` of one space is not empty, and a model name differing from a catalog entry's only in case is unknown. A run that could not start is not a refusal but a run, answered `failed` with its reason as a success.

**The catalog.** Every tool answers from the catalog, so a tool that cannot read or write it has nothing true to say. It refuses with exactly `store.Unreachable`, quoting nothing of the underlying error, whenever a store method its answer is made from, directly or through the run core, fails with a catalog error (`D04-store`). A rule decidable without the catalog still answers first: the name rule and the run-id rule, as in scripts. The model, `prompt`, tools and schema rules need no catalog either, but they keep their place after the name check and the taken check, so with the catalog out of reach a `create` with a valid name gets the catalog line whatever its model; and the event rule likewise is checked only once the prompt has been found. A test produces a catalog error by turning on `SetFailing` for the store's handle before the call. prompts' tools run no git, so no declared hook sits between a call's reads and its writes, and no requirement states the answer to a catalog that fails partway through a call. `tools/list` reads nothing of the catalog. The same line answers a failure of `runs.Core.Run` that is not one of its sentinels, such as a run folder or `input.json` that cannot be made, since a tool has no other answer for it.

**A call cut off.** A `run` whose run core call is cut off (`D07-runs`) — its request's context ended, or the drain deadline passed, before its run was recorded — answers nothing and records nothing: the request is cut off (`D03-serve`), its caller gets no result, and the trail holds no `tool.called` for it. appkit's server records `tool.called` once a handler returns or panics and records none for a `tools/call` answered with no result, so such a handler never returns: it ends its goroutine without returning, as `runtime.Goexit` does. A test holds a `run` call before its record with a `runs.Config.Rand` that blocks until it lets it go.

**The drain.** Once the run core is draining (`D07-runs`), `run` refuses every call for a prompt of the caller's with `runs.Stopping`, after looking the prompt up, so the drain refusal never tells a caller that a prompt it does not own exists. Every other tool answers during the drain as it always does.

**Runs unavailable and the queue full.** Both come from `runs.Core.Run`, after the drain: `runs.ErrNoCgroup` when prompts started with no control group to run prompts in, and `runs.ErrQueueFull` when `RUN_MAX_QUEUED` runs are already queued, whoever's. The tools word neither from anything of their own: each refusal is the error's own text. Either is a refusal like the drain's: no run, no folder, no `run.*` event, `tool.called` with `outcome` `error`.

A refused call has changed nothing: no prompt made, changed or removed, no run and no run folder, no child started and no running child killed; and it records no `prompt.*` or `run.*` event.

## What a success answers and changes

`show`, `create`, `update`, `subscribe` and `unsubscribe` answer the **prompt object** (`tools.Prompt`): `id`, `name`, `model`, `prompt`, `system`, `tools`, `schema`, `created`, `subscriptions`, `last_run`; `system` always present, `""` when the prompt has none; `tools` always present, the groups in the order they were sent, `[]` when none; `schema` absent when the prompt has none and otherwise the schema exactly as it was sent; `subscriptions` as scripts' (`tools.Subscription`); `last_run` absent for a prompt never run and otherwise the newest run's `id`, `status`, `exit_code` (only when `exited`) and `started`, unchanged from scripts. `list` answers `{"prompts":[...]}` (`tools.PromptList`), one listing entry (`tools.ListedPrompt`) per prompt of the caller's, by name: the prompt object without `created`, `prompt`, `system` and `schema`, and with `subscriptions` the number of the prompt's subscriptions rather than the list. `delete` answers `{"deleted":true,"id":"<prompt id>"}` (`tools.Deleted`). `run` answers the **start answer** (`tools.Started`): `id`, `status` and `reason` (only when `failed`). `runs` answers `{"runs":[...]}` (`tools.RunList`), newest first, each a **run entry** (`tools.RunEntry`): `id`, `model`, `trigger`, `event` (only for a run an event started), `status`, `exit_code`, `started`, `finished` (absent while `queued` or `running`), `truncated`, `reason`, then the seven usage members `calls`, `tool_calls`, `input_tokens`, `cached_tokens`, `output_tokens`, `reasoning_tokens` and `cost_nanos`, present exactly when the run has ended; `cancel` answers the run entry of the run it ended. `result` answers the **run result** (`tools.RunResult`): the run object, `id`, `prompt` (the prompt's id), `model`, `user`, `request_id`, `trigger`, `event`, `status`, `exit_code`, `started`, `finished`, `stdout_bytes`, `stderr_bytes`, `truncated`, `reason` and the seven usage members, then `stdout`, `stderr`, `transcript_bytes` and `files`, or `files_gone` `true` when the run's folder is gone. `truncated` is everywhere `store.Run.Truncated`, either stream cut. Every time is RFC 3339 UTC to the second.

`create` adds one prompt, owned by the caller, with the caller's email kept as its owner's email for the runs events start; it makes no run folder and starts nothing. `update` sets each field whose member was sent, whole: a `system` of `""` clears the system prompt, a `tools` of `[]` clears the groups, and a `schema` replaces the schema whole; it never changes the name, a subscription or a run, and a run already made keeps the model it was made with. `subscribe` and `unsubscribe` add and remove one subscription and nothing else. `delete` hands the prompt to the run core, which kills its running runs, takes its queued runs from the queue, records their ends, removes its folders and its record, its subscriptions and its memory of delivered events going with the record, and returns; only then does the tool record `prompt.deleted`. `run` hands the prompt, the input's bytes and the caller to the run core, which answers at once without waiting for the model: `running` when a slot was free and the child started, `queued` when `RUN_MAX_ACTIVE` runs were running. A queued run is answered by `runs` and `result` as not yet finished, with no `finished`, no `exit_code` and no usage, and `result` answers its streams `""`, their sizes 0, its transcript 0 bytes and its files `[]`. `result` reads the run's folder: the kept stream files as they are at the call, the transcript's size, and every regular file under `work/`, at any depth, as its path there and its size, sorted by path, no symbolic link followed. `cancel` hands the run to the run core, which kills its child's session whole, or takes a queued run from the queue so it never starts, records it `killed` and its `run.finished`, and answers the ended record.

## Decisions

- Departures from scripts, all from the decisions document: the repository, `ref` and `sha` are gone from every argument and answer; `create` takes `model`, `prompt`, and optionally `system`, `tools` and `schema`; `update` takes any of the five in place of a required `ref`; the run entry and run result carry `model` and the seven usage members; the run result carries `transcript_bytes`, and its files are those under `work/`; and `truncated` is the OR of the two streams' cuts, which the store keeps apart (`D04-store`).
- **Clearing a schema is not designed.** The decisions document says `update`'s `schema` given as JSON `null` clears it. appkit's `mcp` cannot tell an absent object argument from `null`: a `json.RawMessage` field refuses `null` as the arguments are read, and a pointer to one is refused when the tool is registered. So `update`'s `schema`, when sent, replaces the schema whole, and nothing in this design clears it; what `update` answers to `"schema":null` is appkit's and no requirement states it. No string-encoded schema and no sentinel value stands in. This waits on an appkit release that can carry an optional object which may be `null`.
- `update` with no member but `name` succeeds and changes nothing, answering the prompt object as `show` would.
- `tools.EmptyPrompt` has no verb: there is nothing to quote. The other new constants, `tools.UnknownModel`, `tools.InvalidTools` and `tools.InvalidSchema`, have one `%s` each. `tools.InvalidTools` quotes the list as `encoding/json` writes the decoded strings, so `["web"]` is quoted `["web"]`, and `tools.InvalidSchema` quotes the text of agentkit's error.
- The model, `prompt`, tools and schema rules need no catalog but are not catalog-free rules: they keep their place after the catalog checks, so a failing catalog answers before them. Only scripts' two catalog-free rules, the name rule and the run-id rule, answer first.
- No requirement states a catalog failing partway through a call: scripts' mid-call hook was the git limits' clock, and prompts' tools run no git. scripts' cut-off `create` (one whose owner read the limits halted) has no counterpart, since `create` reads no repository; a cut-off `run` keeps scripts' treatment, the run core's `runs.ErrCutOff` standing where scripts' `limits.ErrHalted` stood (`D07-runs`).
- A cut-off call never returns, as in scripts; this depends on appkit's mcp server running a tool's handler on the goroutine of its `ServeHTTP` and recording `tool.called` after the handler returns and not from a deferred function, which appkit's design does not yet promise.
- The listing entry and the last-run object carry no cost and no usage: `list` and `last_run` are as scripts', and `runs` and `result` carry the usage.
- The seven usage members are absent while a run is `queued` or `running` and present once it has ended, zeros included, since a run's usage is summed when its child ends (`D07-runs`).
- `transcript_bytes` is present whenever the folder is, and 0 when the transcript is absent, as a stream that is absent reads `""`.
- The result types are exported so a test decodes `structuredContent` into them member for member; the argument types are exported so a test encodes arguments with them.
- A `run` whose prompt is deleted before its run is recorded is answered with the missing-prompt refusal, as in scripts: the run core reports the prompt gone (`D07-runs`), and a test holds the call open between its lookup and its record with a `runs.Config.Rand` that blocks, as scripts held it with a git hook.
- No package beyond `store`, `agent`, `runs` and appkit is needed: no tool answers a URL.

## Consumer tasks

The handler (`D03-serve`), when it is built, registers the tools once on the server `Process.MCP` made for the writer `w`: `tools.Register(srv, tools.Config{Store: st, Runs: core, Telemetry: w})`, where `core` is the `*runs.Core` built over the same `st` and `w`; and it mounts `srv` at exactly `/mcp` inside `identity.Require` inside `telemetry.Middleware` over `w`.

A model, through the gateway's `call`, lists the eleven tools, reads its prompts with `list` and `{}`, one with `show` and `{"name":"daily-digest"}`, the runs of one with `runs` and `{"name":"daily-digest"}`, and one run with `result` and `{"run":"prr_3f9a1c2e8b7d4a60"}`, calling `result` again while `status` is `queued` or `running`, and reading `stdout` as the answer and `cost_nanos` as what it cost once it has ended. Through `mutate` it makes a prompt with `create` and `{"name":"echo","model":<a catalog model>,"prompt":"Reply with exactly the word pong."}`, or with `"tools":["files","bash"]` and a `"schema":{...}` of its own; changes it with `update` and `{"name":"echo","system":"Be terse."}` or `{"name":"echo","tools":[]}`; starts a run with `run` and `{"name":"echo","input":{"since":"2026-10-04"}}`, getting `{"id":"prr_…","status":"running"}`, `{"id":"prr_…","status":"queued"}` when every slot is taken, or `{"id":"prr_…","status":"failed","reason":"start_failed"}`; ends one early with `cancel` and `{"run":"prr_…"}`; removes a prompt with `delete` and `{"name":"echo"}`; and makes a prompt run on every schedule cron fires with `subscribe` and `{"name":"echo","event":"cron.tick.fired"}`, stopping that with `unsubscribe` and the same arguments. A refusal's text, from a copy constant, tells it what to fix: that the model is unknown, the tools are invalid, the schema is refused and why, the prompt text is empty, the thing is not there, an event pattern is malformed, that it is too late, to try again later, or that no run can be made at all.

A tools test sets `IKIGENBA_SERVICES` with `t.Setenv` to the empty string; opens `db.Open(ctx, db.Config{Path: ..., Migrations: prompts.Migrations(), Now: ...})` over a temporary file and builds `store.New(d, store.Config{Now: ..., Rand: ...})` over it; builds a writer with `telemetry.New(telemetry.Config{Service: pages.ServiceName, Sink: capture, Now: ...})` over a `*telemetry.Capture`; serves an `httptest` server standing in for the provider and builds `runs.New(runs.Config{Store: st, Writer: w, Runs: ..., Keys: ..., BaseURL: <the test server's URL>, ...})`; builds `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: v, Telemetry: w})`; calls `tools.Register(srv, tools.Config{Store: st, Runs: core, Telemetry: w})`; and serves `srv` on loopback inside `identity.Require` inside `telemetry.Middleware` over `w`. Its package's `TestMain` runs the test binary's own `agent` role when asked, as `D06-runner` says. It picks every model from `agentkit.Catalog()`. It drives the server with `mcp.NewClient(mcp.ClientConfig{Endpoint: ...})`: `ListTools(ctx, caller)` for the eleven `mcp.ToolInfo`, whose `Name`, `Description`, `InputSchema`, `OutputSchema` and `Effect()` it asserts; `CallTool(ctx, caller, "create", args)` with `args` the `json.Marshal` of a `tools.CreateArgs`, or literal argument bytes for arguments the types cannot hold: a `create` or an `update` without `schema` and a `run` without `input`, since `encoding/json` encodes a nil `json.RawMessage` as `null` (`"schema":null` from a `tools.CreateArgs` or `tools.UpdateArgs` with a nil `Schema`, `"input":null` from a `tools.RunArgs` with a nil `Input`), which appkit refuses as the arguments are read, and an `omitempty` tag on those fields is no way out, since appkit refuses it when the tool is registered; it decodes `structuredContent` into `tools.Prompt`, `tools.PromptList`, `tools.Deleted`, `tools.Started`, `tools.RunList`, `tools.RunEntry` or `tools.RunResult`. It sends a `schema` or an `input` whose white space it chose by raw HTTP to `/mcp`. It holds a run running by having its provider server hold the child's request; makes the catalog unreachable with `SetFailing(true)` on the store's handle before the call; makes the run core fail otherwise by clearing every write permission bit of the runs directory before a prompt's first run; and drains with `core.Drain` in a goroutine of its own while a run is held. It reads the catalog back with `Store.Find`, `Store.Runs` and `Store.RunByID`, the run folders by walking `runs.Config.Runs`, and the trail with `Writer.Flush` and `Capture.Events`. No fixture, name, argument or expected text in such a test has the shape of a requirement id.
