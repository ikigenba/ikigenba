# D02-cli

prompts as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, what `db status` reports of the catalog, how the `agent` role is reached, and the three constants whose text is fixed here, the usage text, the manifest and the nginx fragment, with the two files under `etc/` that copy the manifest and the fragment. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version` and `Stdin`, `cli.Run` and the root package's `Etc` and `Migrations`; `D12-limits` declares `settings.Defaults` and the `Settings` it returns; `D08-pages` declares `pages.Description`; `D05-agent` declares `agent.Command`, `agent.Process`, `agent.Run` and `agent.KeyVariable`. When `Args` is empty prompts serves, and everything from there is `D03-serve`'s.

The arguments decide everything. An empty `Args` means serve. The three recognised single options and commands each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity, `manifest` writes `Manifest`, and `--help` writes `Usage`. The one two-word command, `db status`, reports the catalog's migrations (below), which in this prompts is `0001`, one line. The fourth single command, `agent`, is the child role: the app starts its own binary with that one argument for every run (`D06-runner`), and `Run` hands the process over to `agent.Run`, returning what it returns. Any other `Args` is a usage error. The argument prompts complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`; and otherwise the second, which is surplus whatever it says, so `agent x` complains of `x`. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `prompts: `, and after exactly one empty line comes the hint to run `prompts --help`, unprefixed because prompts is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. The constant for 1 keeps scripts' name, `ExitServerFailed`, though it also covers a `db status` that fails. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a setting that is not a positive whole number) exits 2, while trouble on the host once prompts is past its checks (a catalog it cannot open, a `state/runs` it cannot create, a drain that runs out) exits 1, and so does a `db status` whose catalog cannot be read. For every `Args` but `agent`, `Run` returns no other value.

`agent` is the one exception: its exit status is a run's outcome, which the app reads (`D05-agent`, `D07-runs`), and it ranges over 0 to 4. `Run` returns `agent.Run`'s value unchanged and adds nothing to it. The help text keeps the three-code block: `agent` is listed so an operator who sees it in a process list knows what it is, but it is the app's to start, and its codes are the app's to read, not a caller's.

## agent

`prompts agent` is the binary's second role (decision 1). `cli` owns only how it is reached: with `Args` exactly `[agent.Command]`, `Run` calls `agent.Run` with the context it was given and an `agent.Process` built from its own: `Stdout`, `Stderr`, `LookupEnv` and `Now` as they are, and `Stdin` as a reader of exactly `Process.Stdin`'s bytes whose `Close` closes `Process.Stdin` when that has a `Close` (a nil `Stdin` reads as empty). In the binary `main` passes the process's standard input, so the child's `Close` before its loop (decision 11) closes descriptor 0 itself. Everything the role does with those, the spec it reads, the transcript it writes, what it prints and what it returns, is `D05-agent`'s; this design states only that `Run` is that call and nothing more, so a test proves the dispatch by calling `agent.Run` itself with the same inputs and finding the same outcome.

The role is not the server. It takes no socket, opens no catalog, writes nothing under `Process.Dir` and nothing under `Process.Cgroup` (the runner already placed the child in its own control group), reads no random source, records no event, reads no setting (`D12-limits`; a refused `PROMPT_SECONDS` in its environment changes nothing), and builds no banner and no MCP server: those are the app's, and the child reaches the suite only through the gateway, when its spec offers `suite`. The paths it writes come from its environment (`IKIGENBA_RUN_DIR`, `IKIGENBA_WORK_DIR`), never from `Dir`. `Process.BaseURL` is the app's to put in each spec; the child reads its base URL from the spec, not from the seam.

## db status

`db status` is an operator's look at the catalog: which of the migrations the binary carries `state/prompts.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status` (its D16), which prompts calls with the path `state/prompts.db` resolved against `Process.Dir` (so relative to the working directory in the binary) and the migrations `prompts.Migrations()` returns, writing straight to `Stdout`; it reads no clock, so the `Config` carries no `Now`. prompts adds nothing to the lines and states nothing about their format; its requirements say only that the bytes on `Stdout` are the ones `db.Status` writes for that path and those migrations, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database, never with a format it spells out. `db.Status` only looks: it applies nothing and creates nothing, so before prompts' first start `db status` reports every migration pending and leaves the directory as it was. When it returns an error, prompts says so on one line, `prompts: ` and the error's text with each newline replaced by a space, and exits 1. Whatever `db.Status` had already written to `Stdout` stays there: findings are product, and the repository's command-line conventions send a report to stdout whole, bad news included. That is the one case among the commands in which a failure may leave anything on `Stdout`. A catalog that records a migration this prompts does not carry, one a newer prompts upgraded, is not a failure: older code runs on newer data (`D03-serve`), appkit's `db.Status` lists every line, the unknown version among them, and returns nil, so `db status` writes nothing to `Stderr` and exits 0. A catalog that cannot be read yields no lines at all and exits 1. `db status` reads no environment, takes no socket, starts no child and looks at nothing under `state/runs/`.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket and no provider key, and only `db status` reads the catalog, so `prompts --version` succeeds with nothing passed in and `prompts bogus` fails whatever the environment holds. Unless `Args` is empty or is `agent`, `Run` touches none of the environment, standard input, the control group under `Process.Cgroup`, the inherited descriptor, systemd's notification socket, the clock, the run timer, the random source, the sink, the banner source or the server maker, and only `db status` reads anything under the working directory, creating nothing there. A command starts no child and records no event: the trail is what prompts records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns, `db status` and `db bogus` included. Every failure but that one `db status` case leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`; its text is exactly the committed `etc/manifest.toml` the delivery seeded from decision 16. Its text: prompts' name; its description, which is `pages.Description`, the line the about screen shows, the host publishes in its services file, and the MCP endpoint gives its clients as instructions; that it is not the host's default app; that it is one of the suite's MCP services; `guests = false`, since every page and `/mcp` is for a signed-in user (decision 15); the five secrets, one per host agentkit knows an API-key endpoint for, each the variable `agent.KeyVariable` names for its host, in agentkit's host order (Anthropic, OpenAI, Gemini, xAI, OpenRouter), so the keys the host must hold are exactly the keys the run core can hand a child (decision 3); the eleven settings of `[env]` with the defaults `settings.Defaults` holds, `PROMPT_SECONDS`, `OUTPUT_MAX_BYTES`, `RUN_MAX_TOOL_CALLS`, `RUN_MEMORY_MAX_BYTES`, `RUNS_MEMORY_MAX_BYTES`, `RUNS_CPU_PERCENT`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE`, `RUN_MAX_QUEUED`, `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT`, in that order; the `[database]` table that tells the host to keep and replicate `state/prompts.db`; and the `[resources]` table opsctl writes into the service unit (opsctl's published interface): `slice` `apps`; `memory_max` `896M`, one ceiling over prompts and every child it runs together; `go_memory_limit` `128M`, the soft limit prompts' own Go runtime collects garbage against; and `delegate` `true`, so the host hands prompts' service its part of the control group tree, which `cli.Run` arranges and runs every child in (`D03-serve`). It declares no CPU or IO weight; no port, since prompts serves on the socket the host passes it; no `DRAIN_SECONDS`, which is opsctl's to set; and no `cache/`, since a run's folder is the product and lives under `state/runs/`.

## The nginx fragment

`/events` and `/declarations` are for prompts' siblings on its socket: the events app delivers events there and asks which prompts accepts (`D03-serve`, `D14-delivery`). The host's nginx proxies everything at prompts' public name to that same socket, so the fragment closes the two paths to the outside: the host and the sandbox include an app's `etc/nginx.conf` inside the server block of its public name, and the fragment's two exact-match locations, `location = /events` and `location = /declarations`, each answering `return 404`, therefore answer both paths 404 at the public name for every method, while the same paths on the socket stay open. nginx's documentation proves the two facts relied on: an exact-match `location` (`=`) is chosen, and ends the search for a location, when it matches, whatever order the server's locations are declared in (`ngx_http_core_module`, the `location` directive), and `return` is allowed in a `location` and ends processing with the code it names (`ngx_http_rewrite_module`). The fragment matches only those two exact paths, so `/events/` and `/declarations/<x>` reach prompts and are prompt paths, answered with the not-found page (`D03-serve`, `D08-pages`); and it redeclares none of the host's own locations.

The fragment is a fact about the binary like the manifest, so it is the constant `NginxConf`; nothing prints it. The `manifest` command prints `Manifest` alone, which is all `devctl build` compares. The constant's value is contract, proved by use as the manifest's is.

## The files under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ; the committed `etc/nginx.conf` holds exactly the text of `NginxConf`. The build run keeps both in step with the constants. The files are proved by use: the root package embeds the committed `etc/manifest.toml` and `etc/nginx.conf` and exports them as `Etc`, an `embed.FS` (`D01-layout-and-run-seam`), which only a `//go:embed` directive can fill (the `embed` package's documentation), so a test compares each embedded file with its constant without ever opening the checkout, and a build whose `etc/` lacks either file fails to compile while one holding a stale copy fails that test. That test lives in the external test package `prompts_test` beside the root package, since it imports both the root package and `internal/cli`, and `internal/cli` reaches the root package through `internal/pages`, so a test inside package `prompts` would form an import cycle.

What prompts' directory in the suite release holds beside `etc/` (`bin/prompts` and the human-drawn `share/icon.svg`) is `devctl build`'s output, which no test this design permits can see; it is `D13-on-a-space`'s to record, as is what nginx answers once a host or a sandbox includes `etc/nginx.conf`.

## Departures from scripts

The words differ where prompts differs: the program name, the help text's description, the description, eleven settings in `[env]`, a `guests = false` line and five secrets. The help text lists a third command, `agent`, and `Run` dispatches it to `agent.Run`, whose exit status (0 to 4) is the one return outside the three codes. The seam loses `Environ` and `After` (git's), so the list of things a command leaves untouched loses them, and gains `Stdin`, which no command but `agent` reads. A command starts no process at all; scripts named git and the interpreter.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, `Stdin` the process's standard input among them, and exits with what it returns. A developer types `prompts --version`, `prompts manifest` or `prompts --help` and reads stdout; an operator types `prompts db status` in `/var/opt/ikigenba/prompts` before or after a deploy and reads which migrations the catalog has had; `devctl build` runs `prompts manifest` and compares its output with the release's `etc/manifest.toml`, refusing the app when they differ; opsctl reads the manifest's `secrets`, `[env]`, `[database]` and `[resources]` from the release's `etc/manifest.toml`, and opsctl and the sandbox include the release's or checked-out `etc/nginx.conf` in prompts' server block. The runner starts `<exe> agent` with the spec on standard input (`D06-runner`), `main` hands that to `cli.Run`, and the run core reads the exit status `agent.Run` chose.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s) and `Dir` (an empty temporary directory) set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `p.Version + "\n"` (a `Version` it chose, and the empty string, which gives exactly `"\n"`), `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic, `["agent", "x"]` among the usage errors; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `ScriptAfter`, `Banner` and `MCP` to functions that record a call, `Stdin` and `Rand` to readers and `Sink` to a `*telemetry.Capture` that record any use, `Stderr` to a writer that counts its `Write` calls, and asserts none was used; it also sets `Cgroup` to a temporary directory holding only a `cgroup.procs` naming `Pid`, and finds it unchanged. A test of `db status` makes a catalog under its `Dir` with `db.Open` and `prompts.Migrations()` (or with an extra recorded version written through `DB.Write`, or a file that is not a database), closes it, runs `cli.Run` with `Args` `["db", "status"]`, and compares `Stdout` with what its own `db.Status` call wrote into a buffer for the same path and migrations before `Run` was called, and with what it writes after, and `Stderr` with `"prompts: "` and that call's error text when it returned one, or with nothing when it returned nil. A test of `agent` hands `cli.Run` `Args` `[]string{agent.Command}`, a `Stdin` holding spec bytes of its own (one `agent.Run` refuses, and one naming a model from `agentkit.Catalog()` against an `httptest` provider), a `LookupEnv` over a map naming a run directory outside `Dir` and holding a `PROMPT_SECONDS` that `settings.Read` refuses, a fixed `Now`, and recording `Unsetenv`, `Inherit`, `Sleep`, `ScriptAfter`, `Banner`, `MCP`, `Rand` and `Sink`; it calls `agent.Run` itself with the same bytes, a map naming a second run directory and the same `Now`, and compares the two returns, the two `Stdout`s, the two `Stderr`s and the two run directories, finds `Dir` and `Cgroup` as they were and nothing recorded, and finds its `Stdin`'s `Close` called exactly when its direct call closed the reader it was given. A test compares `cli.Manifest` with `pages.Description`, with the fields of `settings.Defaults()`, and with `agent.KeyVariable` of the five hosts. A test in package `prompts_test` reads `etc/manifest.toml` and `etc/nginx.conf` from `prompts.Etc()` with `fs.ReadFile` and compares them with `cli.Manifest` and `cli.NginxConf`.
