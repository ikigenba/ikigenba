# D01-layout-and-run-seam

prompts is the suite's prompt runner: one Go binary, behind the host's nginx at `prompts.<space>`, that keeps a catalog of each user's prompts, each naming a model in agentkit's catalog and the text the model is given, with an optional system prompt, the tool groups it allows (`files`, `bash`, `suite`) and an optional output schema, runs a prompt as one agent session over agentkit in a folder of the run's own, and keeps every run's input, output, transcript, files, usage and outcome. It offers eleven MCP tools at `/mcp` (`list`, `show`, `create`, `update`, `delete`, `subscribe`, `unsubscribe`, `run`, `runs`, `result`, `cancel`), runs a prompt each time the suite's events app delivers an event one of the prompt's subscriptions matches, keeps its catalog of prompts, their subscriptions and their runs in its own SQLite database, `state/prompts.db`, keeps each run's folder under `state/runs/`, and serves a catalog page at `/`, a page per prompt and per run, the run's files, and an about screen at `/about`, all to a signed-in user only, beside the two exact paths `/events` and `/declarations` on which the events app, a sibling on the socket, delivers events and learns which prompts accepts.

The binary has two roles. Serving, it is the app. As `prompts agent`, started by the app itself for each run, it is the child that runs that one run: it reads the run spec from its standard input, runs the agentkit tool loop in the run folder, writes the model's final message to its standard output and exits with a code that is the run's outcome (`D05-agent`). The app starts its own executable in that role the way scripts starts `python3.12 main.py`: a child in its own session and control group, with a composed environment, bounded output and a deadline (`D06-runner`, `D07-runs`). One binary keeps the release layout's rule of exactly one binary per app and gives the child the same build, version and module as the app.

This design is the structural ground the other designs stand on: where the code lives, which package owns which concern, the seam through which the process is run so that the command, the server, the pages, the store, the runs, the child and the tools can be tested without a real process, the entity ids, the fact that the child is the binary's own `agent` role, the paths, the migrations that give the catalog its schema, where the version it shows comes from, the files under `etc/`, and the one binary's wiring. Every other package's names are declared by the document that owns that package, listed below.

The module is `github.com/ikigenba/ikigenba/prompts`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/prompts`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/prompts` is wiring only.

## The dependencies

prompts depends on three modules besides the standard library, each a sibling library of this repository required at a published release through the ordinary module proxy and checksum database, with no `replace` directive: `github.com/ikigenba/ikigenba/appkit`, `github.com/ikigenba/ikigenba/agentkit` (the model catalog and `Lookup`, the API-key authenticator, the tool loop, tools built from a schema, the output contract, the limits, and the JSON Lines log a run's transcript is) and `github.com/ikigenba/ikigenba/toolkit` (the `Read`, `Write`, `Edit`, `Glob`, `Grep` and `Bash` tools rooted at a directory), plus `golang.org/x/sys`. The SQLite driver, the pure-Go one that keeps the release build cgo-free, arrives through appkit's `db` package; prompts never imports it. Which release of each is data that `AGENTS.md` and `go.mod` hold; no requirement names one. prompts runs no program of the host's for itself: it runs only its own executable, as the child. toolkit's `Bash` tool, which the `bash` group offers, runs `bash` from the `PATH` for each command the model gives it (`AGENTS.md` declares it in the toolchain); that is the child's, not the app's.

appkit is a sibling reached only through its published packages, and prompts uses eight of them: `db` and `version` (below), `services` (the services file), `page` (the banner, launcher, footer and font preload, the template set the six templates are parsed into, and the shared static files), `identity` (`Require` on every route but the events app's two, and the caller the child forwards to the gateway), `mcp` (the server mounted at `/mcp`, the client the tests drive it with, and the client the child reaches the gateway with), `telemetry` (the event, the request middleware, the writer, the socket sink and the capturing sink tests use), and `events` (the delivery and declarations handlers mounted at `events.EventsPath` and `events.DeclarationsPath`, the delivered event, its outcomes and its cause; `D03-serve`, `D14-delivery`). appkit's, agentkit's and toolkit's designs own their contracts; prompts restates none.

`github.com/ikigenba/ikigenba/appkit/db` is the suite's one way to keep a SQLite database. `db.Open` opens or creates the database at an ordinary file path, creating its missing directories, applies the migrations it is given that the database has not had, stamping each with the clock it is given, and refuses a database it cannot open; over a database that records a migration it was not given, it applies nothing, writes one warning line beginning with the `Config.Service` it is given, `prompts: `, to the `Config.Stderr` it is given, and opens it all the same; `DB.Read` runs a read-only transaction and `DB.Write` a transaction on the one writer; `DB.Close` closes the handle; `DB.SetFailing` makes a handle fail every transaction until it is turned off, which is how prompts' tests make the catalog fail; and `db.Status` writes, changing nothing, which migrations a database has had. All of that is appkit's contract: prompts restates none of it, and its tests re-prove none of it.

`github.com/ikigenba/ikigenba/appkit/version` is the code identity the host gives every app: `version.Display()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment at the time of the call and returns the **display string** built from them, the empty string when neither is set. prompts carries no version of its own: nothing in its source or its build names one.

The model providers are reached only by the child, through agentkit, at the endpoint of the model's offering in agentkit's catalog, or at the base URL the run spec carries when the app was given one (below). The app itself makes no request to a provider.

## Identity

Identity is established at nginx and arrives on every request in `X-User-Id`, `X-User-Email` and `X-Request-Id`, which appkit's `identity.Require` turns into an `identity.Caller` (`UserID`, `Email`, `RequestID`) on the request's context, and appkit's request middleware makes the request id of every event the request records. A prompt's owner is the `UserID` of the call that created it, and its creator's email is kept beside it (`D04-store`); a run's user and request id are the `UserID` and `RequestID` of the `run` call that caused it, recorded on the run (`D04-store`), handed to the child in the run spec and in `IKIGENBA_USER_ID` and `IKIGENBA_REQUEST_ID` (`D07-runs`), so that the child's calls to the gateway carry them on (`D05-agent`). A run the events app's delivery of an event makes acts instead as its prompt's owner and carries the request id of that delivery (`D14-delivery`). A test is a signed-in user by setting those headers, as `AGENTS.md` describes. Which routes exist and which of them require identity, every one but the events app's two, is `D03-serve`'s.

## Where the environment is read

`Run` reads every variable through `Process.LookupEnv`. Serving, it reads `DRAIN_SECONDS` and the eleven settings once at start, through `D12-limits`' settings reader; the five provider keys `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `XAI_API_KEY` and `OPENROUTER_API_KEY` once at start, held in memory and handed to each run's child only in its run spec on standard input, never in its environment (`D03-serve`, `D07-runs`); `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness (`D03-serve`); `PATH`, which every child is given verbatim (`D07-runs`); and `IKIGENBA_SERVICES`, once, when it starts to serve, whose value it hands on as the services path that the handler, the pages and the tools read afresh whenever they need the file, and which every child is given verbatim (`D07-runs`). In the `agent` role, `Run` hands its `LookupEnv` to the role, which reads only `IKIGENBA_RUN_DIR`, `IKIGENBA_RUN_ID`, `IKIGENBA_WORK_DIR` and `IKIGENBA_SERVICES` (`D05-agent`). A child's environment is exactly the thirteen variables `D07-runs` composes, its `PATH` taken from `LookupEnv`, so a test that chooses the `PATH` and the working directory chooses everything a child sees of the host. scripts' `Process.Environ`, the environment of every `git` it ran, has no counterpart: prompts runs no `git`.

`version.Display` reads `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` from the real process environment, and `main` calls it exactly once, first, and holds the result: that value is the version prompts shows everywhere it shows one, and the one it hands `page.New`, `mcp.NewServer` and `Run`, as `Process.Version`, which `Run` hands the writer it builds and writes for `--version`. Nothing below `main` calls `version.Display`, and `Run` never looks either variable up through `LookupEnv`, so an in-process test hands `Run` any string it likes as `Version`, the empty string included, and sets no variable.

Three readers of `IKIGENBA_SERVICES` sit outside the seam, all appkit's: `page.New` and `mcp.NewServer` read the real environment when they are called, and the socket sink reads it on every delivery. So `main` calls `page.New` once and puts in `Process.MCP` a function that calls `mcp.NewServer` with `Instructions` nil; and the socket sink is what a nil `Process.Sink` means, used only by the binary, while a test of `Run` names its own sink, a `*telemetry.Capture`.

## Packages

The module's root package, `prompts`, holds what the module embeds, because Go's `embed` reaches only files at or below the embedding package's directory. It exports `Assets`, a file system holding exactly the six templates from `assets/`, which `internal/pages` parses into the set `page.Templates()` returns (`D08-pages`); `Etc`, an `embed.FS` holding exactly `etc/manifest.toml` and `etc/nginx.conf`, through which a test proves that the committed files are the manifest and the nginx fragment `D02-cli` declares (the `embed` package documents that an `embed.FS` declared without a `//go:embed` directive is an empty file system, so the bytes a test reads from `Etc` are the committed files' as the build embedded them); and `Migrations`, a file system holding exactly the migrations from `migrations/`.

The catalog's schema is a sequence of migration files, each named with a four-digit version, that the binary carries and appkit's `db` applies in order. prompts is new, so it carries one, `0001_catalog.sql`, which makes every table `D04-store` declares; there is no earlier catalog to adopt. `Migrations()` is what `Run` hands `db.Open` and `db.Status`, and what a test hands `db.Open` to make a catalog of prompts' shape in its own temporary directory; it is the same on every call and depends on no file beside the binary. A later migration is a new file with the next version; none is ever edited once it has run on a production-grade space.

Eleven internal packages hold the concerns, one each. Ten follow scripts' names and roles; one, `agent`, is prompts' own and takes the place of scripts' `git`, `source` and `limits`, which prompts does not have.

- `internal/cli` owns the program as a command: the run seam (this document), the exit codes, the usage text, the manifest, the nginx fragment and the `agent` command (`D02-cli`), and the serve path (`D03-serve`).
- `internal/server` owns a listener's life: serving a handler and draining for a deadline (`D03-serve`).
- `internal/settings` owns the values prompts reads from its environment at start, their defaults, their spelling and the refusal of one that is not acceptable (`D12-limits`).
- `internal/store` owns the catalog: prompt, subscription and run records, usage, statuses, failure reasons, the name rule and the event-pattern rule (`D04-store`), and the entity ids (this document).
- `internal/agent` owns the child's role: the run spec, the model lookup and the host-to-key map, the tool groups and the suite bridge, the conversation and its one turn, the transcript, and the exit codes (`D05-agent`).
- `internal/runner` owns starting the binary's own `agent` role as one process in a session and process group of its own and in a control group of its own, handing it its spec on standard input, and ending it (`D06-runner`).
- `internal/runs` owns the run core: the run folder, composing the spec and the environment, starting, bounding, ending, recording, summing usage, recovering and pruning runs (`D07-runs`), the trail's run attributes (`D10-trail`), and the runs a delivered event makes (`D14-delivery`).
- `internal/urls` owns the addresses built from a request and the services file (`D08-pages`).
- `internal/pages` owns the template set, the six templates' data, the catalog, prompt, run and about pages, `ServiceName` and `Description` (`D08-pages`).
- `internal/tools` owns the eleven MCP tools (`D11-tools`).
- `internal/web` owns the one handler: the route table, the middlewares and the mounting, the events app's two paths included (`D03-serve`), and the run files beneath a run's page as `D09-run-files` places them.

The events prompts records are `D10-trail`'s; it names the package each is recorded from.

`internal/server` is a copy of sites' package of the same name, as scripts copied it; with prompts it exists in more than two apps, which makes it a candidate for appkit. Promoting it is a separate change, and until it lands the copy is a debt this design records rather than designs away.

Dependencies point one way: `cmd/prompts` imports `internal/cli`, `internal/pages` and appkit, its `version` package among them; `internal/cli` imports the root package, `server`, `settings`, `store`, `agent`, `runs`, `web` and `pages`; `web` imports `pages`, `tools`, `store`, `runs` and `urls`; `tools` imports `store`, `runs` and `agent`; `runs` imports `store`, `runner` and `agent`; `pages` imports the root package, `store`, `runs` and `urls`; `agent` imports at most `store`; the root package, `server`, `settings`, `store`, `runner` and `urls` import nothing of prompts'. `runner` in particular does not import `agent`: the one argument it starts the executable with is fixed inside it (`D06-runner`). Which package imports which is not observable, so this paragraph is guidance.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, and returns the exit code. It is scripts' seam with `Environ` and `After` removed and `Stdin` and `BaseURL` added. `Environ` was the environment of every `git` scripts ran and `After` the timer of one git operation; prompts runs no `git`, so both go. `Stdin` is what the `agent` role reads its run spec from, and closes once it has read it, before the loop starts (`D05-agent`); serving, `Run` never reads it. `BaseURL` is the endpoint base URL every run spec carries (`D05-agent`, `D07-runs`): empty, as `main` leaves it, each run's child reaches its model at the endpoint of the model's offering in agentkit's catalog; a test sets it to the URL of an `httptest` server it serves on loopback, which stands in for every provider, so no test reaches a real provider. There is no field naming another database, because appkit's `db` takes only an ordinary file path, so the catalog is always `state/prompts.db` under `Dir` and a test that needs its own catalog gives `Run` a temporary `Dir`.

`ScriptAfter` keeps scripts' name: it is the timer one run's `PROMPT_SECONDS` ends on, so a test fires a run's deadline without waiting; the drain deadline and the writer's delivery attempts run on real time, because the drain is the one wait `AGENTS.md` lets a test keep to a few real seconds. What the deadline does when it fires is `D12-limits`' and `D07-runs`'. `Now` is the clock every time prompts stamps is read from (a prompt's `created`, a run's `started` and `finished`, every event's time, the moment a prune measures age from, and the time each migration it applies is recorded at), and in the `agent` role the clock of the transcript's records. `Rand` is the source of every id prompts mints: request ids (through the writer), prompt ids and run ids; `Run` never reads it from two goroutines at once, so a test may hand in a `bytes.Reader`. `Dir` is the working directory the state paths resolve against. `Sink` is where the writer delivers: a `*telemetry.Capture` in a test, appkit's socket sink in the binary. `Cgroup` is the directory of the process's own control group, which a host delegates to prompts' service and which `Run` arranges (`D03-serve`): it moves its own process into a child group `main/`, makes a child group `runs/` that bounds every run together, and gives each run a group of its own beneath `runs/` (`D06-runner`, `D07-runs`). Every operation on it is a plain file operation, as the kernel's control group v2 documentation (`Documentation/admin-guide/cgroup-v2.rst`) describes its interface files, so a test hands `Run` a temporary directory standing in for the tree and reads what was written there. `Version` is the display string `main` read: `Run` writes it for `--version` (`D02-cli`) and gives it to the writer it builds, so `service.started` carries it (`D03-serve`). `Inherit`, `Unsetenv`, `Pid`, `Stdout`, `Stderr`, `Sleep`, `Banner` and `MCP` are as in scripts.

## Entity ids

A prompt's id is `prm_` and a run's id is `prr_`, each followed by 16 lowercase hexadecimal digits, the prefixes appkit's telemetry contract registers for the entity types `prompt` and `prompt_run`, both owned by `prompts`. A run of a prompt has its own prefix, not scripts' `run_`, because one prefix means one entity type suite-wide and a trace must tell a prompt's run from a script's by its id alone. Both are minted from 8 bytes of the random source, written in the order read. `internal/store` exports the prefixes, a validity check for each form, and the two functions that mint them: the store mints a prompt's id inside `Create` (`D04-store`), while the run core mints a run's id before anything of the run exists, because the run's folder is named by it before the run is recorded (`D07-runs`). Ids never change. A drawn prompt id that collides with one already catalogued is drawn again by the store, a bounded number of times (`D04-store`); a run id that collides with one already catalogued is refused by `AddRun` as a catalog error (`D04-store`), which with 64 random bits the run core does not plan for.

## The child is the binary's own `agent` role

scripts declared one Python version in its source and ran `python3.12 main.py` for every run. prompts has no interpreter to declare: every run's process is the file `os.Executable()` returns, started with exactly one argument, `agent`, so that `argv` is the executable and `agent` (`D06-runner`). The Go standard library documents that `os.Executable` returns the path name of the executable that started the current process, so the child is the app's own build, version and module, unless the file at that path is replaced while the app runs, as a release swap on a host may do; a run started across such a swap runs the new file's role. That argument is the `agent` command `D02-cli` declares, whose role `D05-agent` defines; an `os.Executable` that fails is a run that fails to start (`D06-runner`, `D07-runs`). Nothing on the host is looked for at start: there is no interpreter to find on `PATH` and no refusal for one missing.

Under `go test` the file `os.Executable()` returns is the test binary, so a test exercises the real child without building or exec'ing anything else. Every test package that starts runs (through `Run`, the run core, the tools, the handler or the runner) has a `TestMain` that, when the test binary's arguments after the program name are exactly `agent`, runs the `agent` role over the process's own standard input, standard output, standard error and environment and exits with its code, and otherwise runs the tests and exits with their result. That dispatch is test wiring, not contract, and it is what `AGENTS.md`'s "the test binary's own `agent` role through the runner" means. The provider is the test's `httptest` server, found through `Process.BaseURL`, which the run spec carries on to the child. So the requirement that replaces scripts' interpreter check is a run through `Run`: with `BaseURL` naming the test's server, a run's child reaches that server and its final message is the run's kept output.

## Paths

Relative to `Process.Dir` (the process's own working directory when empty, which is how `main` leaves it; `/var/opt/ikigenba/prompts` on a host, `<data>/apps/prompts/` in a sandbox): the catalog is the SQLite database `state/prompts.db`, opened with `db.Open`, `prompts.Migrations()` and `Process.Now`, `state/` created when absent; the runs live under `state/runs/`, one folder `state/runs/<prompt id>/<run id>/` per run, whose contents (`input.json`, `stdout`, `stderr`, `transcript.jsonl` and `work/`) are `D07-runs`'. The folders are the product, not a cache: they live under `state/`, never `cache/`, and nothing rebuilds them. prompts writes nothing outside `Dir` but under `Cgroup`; what a model's `bash` command writes elsewhere is the run's.

## The version

prompts declares no version. The one version string it shows is the display string `main` reads with `version.Display()`: `prompts --version` (`D02-cli`, through `Process.Version`), the footer of every page and the about screen's version (through `page.New(pages.ServiceName, v)`, `v` being that string), the MCP `serverInfo` (through `mcp.ServerConfig.Version`), and `service.started`'s `version` (through the writer's `telemetry.Config.Version`, which `Run` sets to `Process.Version`). Its value is data the host supplies at run time: with neither variable set it is empty, and prompts starts, serves and answers `--version` all the same. The child's environment holds neither variable, and the child shows no version.

## Decisions

- `Process` is scripts' seam less `Environ` and `After`, which existed only for `git`, plus `Stdin`, for the `agent` role, and `BaseURL`, for the provider under test. `ScriptAfter` keeps its name so the seam reads the same in both apps.
- `Stdin` is an `io.Reader`, as every other stream of the seam is; the `agent` role closes its standard input once it has read the spec, before the loop starts, so the provider key it carried can be read no more (`D05-agent`), and `cli` gives the role a reader whose close closes `Stdin` when `Stdin` is an `io.Closer`, a nil `Stdin` reading as empty (`D02-cli`). `main` hands it `os.Stdin`.
- `BaseURL` is a field of the seam and of the run spec, not an environment variable, so that the child's thirteen variables are the same under test as on a host, and nothing a model's `bash` command can read or set moves the endpoint. `main` leaves it empty, so the binary only ever reaches the providers' own endpoints.
- The child is the binary's own role, not a second binary under `libexec/`: `devctl build` builds one binary per app, and the role costs one subcommand. The runner fixes the executable and the argument inside itself, rather than taking a path, so nothing above the runner knows which process a run is and bubblewrap can later wrap the same exec line (`D06-runner`).
- `Cgroup` is a field, not something `Run` finds for itself, so that a test hands it a temporary directory and never touches the real control group tree. `main` resolves it from `/proc/self/cgroup`: the line that begins `0::` names the process's control group v2 path, which joined to `/sys/fs/cgroup` is the directory (`Documentation/admin-guide/cgroup-v2.rst`, and `cgroups(7)` for the file's format); with no such line, or no file, `Cgroup` is empty. That resolution is wiring, stated in prose and not as a requirement: the one exec'ing test cannot tell it from a `main` that leaves `Cgroup` empty, since a binary started under a test shares its control group with the test's own process, so either way its start meets a group it may not arrange and runs are unavailable (`D03-serve`). A space or a sandbox shows it (`D13-on-a-space`).
- The id functions live in `internal/store`, beside the records the ids name; the run core calls `store.NewRunID` with the seam's `Rand`.
- `main` calls `version.Display` once and hands the result to `page.New`, `mcp.NewServer` and `Run` as `Process.Version`, rather than letting `Run` look the two variables up through `LookupEnv`: appkit's `page` and `mcp` take the string, not a lookup, so one value read once is the only way every place prompts shows a version agrees.
- `Etc` returns an `embed.FS` rather than an `fs.FS` so that its type alone proves the bytes come from a `//go:embed` of the committed files; `Migrations` returns an `fs.FS` holding its files at its root, as `db.Config.Migrations` takes them.
- Paths, the services path, the version and the wiring of standard input are proved at `Run` and at the binary, since `main` is not usable: the binary requirements below are what the one exec'ing test of `cmd/prompts` proves. That test runs the binary as `prompts agent` once, with a spec on its standard input whose base URL names the test's server, because no other test can see that `main` hands the role the process's own standard input.

## Consumer tasks

The binary's start: `main` first calls `v := version.Display()`, then hands `cli.Run` a `cli.Process` whose `Args`, `LookupEnv`, `Unsetenv`, `Pid`, `Stdin`, `Stdout` and `Stderr` are the real process's, whose `Version` is `v`, whose `Banner` is the `Banner` method of `page.New(pages.ServiceName, v)`, whose `MCP` returns `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: v, Telemetry: w})`, whose `ScriptAfter` is `time.After`, whose `Cgroup` is the directory it resolves from `/proc/self/cgroup` (Decisions), and whose `Inherit`, `Now`, `Sleep`, `Rand`, `Dir`, `Sink` and `BaseURL` are left zero; it cancels the context on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name, and exits with what `Run` returns. Serving, `Run` reads the settings (`D12-limits`) and the five provider keys, and follows the serve path `D03-serve` states. Started as `prompts agent` by the runner, `Run` runs the role `D05-agent` defines over `Stdin`, `Stdout`, `Stderr`, `LookupEnv` and `Now`, and returns its code (`D02-cli`).

The run core mints a run: `id, err := store.NewRunID(rand)`, the folder `state/runs/<prompt.ID>/<id>/`, then the record (`D04-store`, `D07-runs`), then the child, the test binary under `go test`. A test of ids calls `store.NewPromptID(bytes.NewReader(known))` and `store.ValidRunID(s)`.

A test of the run seam builds a `cli.Process` with a `Version` of its choosing, a temporary `Dir`, a `Cgroup` elsewhere in its temporary tree whose `cgroup.procs` holds the decimal `Pid` it chose, a `LookupEnv` over one map holding a `PATH` it chose, its settings and five provider keys of its own, an `Inherit` returning a listener it bound, a `NOTIFY_SOCKET` it holds, a `Now`, a `ScriptAfter` and a `Rand` it controls, a `BaseURL` naming its `httptest` server, a `*telemetry.Capture` as `Sink`, a `Banner` from `page.New` and an `MCP` that calls `mcp.NewServer` (having set `IKIGENBA_SERVICES` with `t.Setenv`), calls `cli.Run` with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with `mcp.Client` (`create` with a model from `agentkit.Catalog()`, `run`, `result`) and raw HTTP, cancels, and inspects `Dir`, the capture, the streams and the requests its server received. A test of the root package calls `prompts.Assets()`, `prompts.Etc()` and `prompts.Migrations()` and lists and reads them with `fs.ReadDir` and `fs.ReadFile`. The one test that execs the binary builds `cmd/prompts` and runs it in a temporary working directory, and once as `prompts agent` with a spec on its standard input.

Compared with scripts: no `Environ` or `After` in the seam, no `REPOS_DIR`, no interpreter on `PATH`, one migration, and a child that is the binary itself.

## The documents
