# D04-store

The catalog: `internal/store`, which owns prompts' one SQLite database, `state/prompts.db`, and everything it records — every prompt's id, name, owner, owner's email, model, text, system prompt, tool groups, output schema and created time, every subscription of a prompt to an event pattern, every run's id, prompt, model, user, request id, trigger, event, status, exit code, times, output sizes, per-stream truncation, failure reason and usage, and the memory of which event each prompt has had a run from — together with the rules a prompt's name and an event pattern obey, the words a run's status, failure reason and trigger are spelled with, and the one line every consumer answers when the catalog cannot be reached. `D01-layout-and-run-seam` declares `cli.Process`, whose `Dir`, `Now` and `Rand` reach the catalog through `cli.Run`, resolves the path the catalog lives at, declares the root package's `Migrations`, and declares the entity ids this package exports (`PromptPrefix`, `RunPrefix`, `NewPromptID`, `NewRunID`, `ValidPromptID`, `ValidRunID`); `D03-serve` opens the catalog with appkit's `db.Open` at start, builds the store over that handle, writes the diagnostic for a catalog that will not open, and closes the handle after the drain. Opening, migrating, the journal mode, transactions and the failure seam are appkit's `db`, which this document restates none of. This document declares every other exported name of `internal/store`, the schema the root package's one migration creates, and states what each name does. What a tool checks before it calls the store and what it answers is `D11-tools`'; what the pages show of a record is `D08-pages`'; when a run is recorded, started, ended, recovered and pruned, how its usage is summed from its transcript, and its folder, are `D07-runs`'; which subscriptions a delivered event starts runs for is `D14-delivery`'s; what the trail carries of a record is `D10-trail`'s. The store holds no file but the database and starts no process.

## One catalog, one writer

prompts is the catalog's only writer, and no sibling reads it. Metadata is in the catalog and bytes are on disk: a run's input, output, transcript and work files are under its folder (`D07-runs`), and the catalog keeps only what lists and pages are drawn from, so a list or a page is one read of the catalog. A prompt's text, system prompt and schema are metadata in this sense (decision 2): they are the record, not a file. A run's record survives its folder going missing. What is contract is what a reader and a restart see: what a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds, field for field. A test proves the catalog's content that way, by closing the handle and opening another, never by reading rows.

The schema is contract too, because a migration, once it has run on a production-grade space, binds every later one. prompts is a new app, so there is no earlier catalog to adopt and no stored blob: the schema is one migration, `0001_catalog.sql`, which creates four real tables without `IF NOT EXISTS`, in the shape cron's catalog set. `prompts` holds one row per prompt: `id` (the primary key), `name` (unique), `owner_id`, `owner_email`, `model`, `prompt`, `system` (empty when the prompt has none), `tools` (a JSON array of the group words in the order given, `[]` when none), `schema` (the bytes as given, null when the prompt has none) and `created`. `subscriptions` holds one row per subscription: `prompt` and `event`, together the primary key, so a prompt never holds one pattern twice, and `created`. `runs` holds one row per run: `id` (the primary key), `prompt`, `model`, `user_id`, `request_id`, `trigger_kind` (named so because `TRIGGER` is an SQL keyword, as cron named its `when` column `schedule`), `event` (empty for a manual run), `status`, `exit_code`, `started`, `finished` (null while queued or running), `stdout_bytes`, `stderr_bytes`, `stdout_truncated`, `stderr_truncated` (each 0 or 1), `reason` (empty unless failed), and the seven usage columns `calls`, `tool_calls`, `input_tokens`, `cached_tokens`, `output_tokens`, `reasoning_tokens` and `cost_nanos`. `event_runs` holds one row per prompt and event id a run was made for: `prompt` and `event`, together the primary key. Every column is not null but `prompts.schema` and `runs.finished`. Times are text, RFC 3339 in UTC to the second; counts, sizes and flags are integers. A test proves the shape through `DB.Read` of `sqlite_master` and the `PRAGMA`s, and never reads rows beyond a fresh catalog's emptiness; beyond that shape, how the records are laid out is not contract. A later change to the schema is a new migration file under the expand-then-contract rule, never an edit of one that has run on a production-grade space.

The store does not open anything. `store.New` builds a store over a handle `db.Open` returned, with the clock and random source it stamps and draws from; every read is a `DB.Read` and every write a `DB.Write` on that handle, so the handle's one writer serializes the writes and the store keeps no lock of its own. A write that must check and change together — a create's name check and insert, an update's read and change, a run's prompt check and insert, an event run's insert with its delivered-event row, a subscription's check and insert or removal, an ending's check that the run is still queued or running, a prompt's removal with its runs, subscriptions and delivered-event rows — does both inside one `DB.Write`, which is what keeps the catalog's invariants under concurrent calls.

A catalog that fails is a **failing** store: from a `SetFailing(true)` on its handle until a `SetFailing(false)`, and once its handle is closed, every method answers a catalog error and changes nothing. That is the one failure seam: a test that needs a call's reads to succeed and its write to fail turns it on from an injected function the call calls between them — a test's `runs.Config.Now`, say — and never takes a permission away, which under WAL does not reliably fail a write.

## Prompts

A prompt's **id** is `prm_` and 16 lowercase hexadecimal digits (`D01-layout-and-run-seam`), drawn from the random source when the prompt is created and never changed. Its **name** is 1 to 64 bytes, each a lowercase ASCII letter, a digit or `-`, the first not `-`, and none of `about`, `mcp`, `events` and `declarations`, since those are prompts' own paths; it is taken as given, never trimmed or folded, and never changes, since there is no rename. Names are one namespace for the whole space, because the name is the URL segment: a name is **taken** when any prompt, of any owner, has it. Its **owner** is the user id of the caller that created it, and its **owner's email** the email that caller's request carried, kept so that a run a delivered event starts, which has no request of the owner's, still carries the owner's email to the child (root ruling 8, `D14-delivery`); the email may be empty, and the store never looks at it. Its **model** is a name in agentkit's catalog, which the tools check (`D11-tools`) and the store keeps verbatim without looking it up, so a prompt whose model later leaves the catalog is still read back. Its **prompt** is the text of the first user message, never empty. Its **system** prompt is optional, empty when there is none. Its **tools** are a list of group words, never nil, empty when there are none, kept in the order given; the store does not check the words, the tools do (`agent.ValidGroups`). Its **schema** is the output schema's bytes exactly as given, nil when there is none; the store does not check it, the tools do (`agentkit.ValidateOutputSchema`). **Created** is the time of the create in UTC to the second, the precision the tools answer it in.

A prompt changes through `Update`, which takes a `Change`: each member that is nil leaves its field alone, and each that is not replaces its field whole, so `update` (`D11-tools`) passes only the members its caller sent. A `System` pointing at the empty string clears the system prompt, and a `Tools` pointing at an empty or nil slice clears the groups. A `Model` or `Prompt` pointing at the empty string is refused, since neither may be empty. A `Schema` replaces the schema with the bytes it points at; one pointing at an empty value is refused, because clearing a schema is not designed in this release: decision 12 asks for `schema: null` to clear it, and appkit's `mcp` cannot tell that argument from an absent one (root ruling 7), so no consumer can ask for it and the store offers no way to do it. `Update` answers the prompt as it is after the call and whether any field's value is different from before, compared byte for byte, the tools element by element and in order; an update that changes nothing records no `prompt.updated` (`D10-trail`).

Every read that returns a prompt returns it with its **last run**: the newest of its runs, in the order `Runs` answers them, or none for a prompt that has never run. The landing page, `list`, `show`, `create` and `update` all show it, so it is part of the record a reader gets rather than a second query. Every read that returns a prompt returns it with its **subscriptions** too, so `show`, `create`, `update`, `subscribe` and `unsubscribe` answer them and `list` counts them without a second query.

## Subscriptions

A **subscription** is a pair, one prompt and one event pattern, kept as the exact string given, with **created**, the time of the `Subscribe` that made it, in UTC to the second. An **event pattern** is two or more words joined by single `.`s, each word either a lowercase letter followed by lowercase letters and digits, single `_` allowed between them, or exactly `*`. `ValidEvent` is the rule, exported because the tools check it after finding the prompt and before they call the store, and the store refuses a pattern it fails. It is the pattern rule of appkit's `events` package, which exports `Match` but no validator, so the store states it as a regular expression. A pattern **matches** an event name of as many words, word for word, each `*` standing for exactly one word, which is appkit's `events.Match`. `Subscribers` answers by matching; everything else compares patterns as strings: `Subscribe` is idempotent for the exact string and keeps the time the subscription was first made, another string is another subscription, and `Unsubscribe` removes only the subscription whose pattern is the string given, refusing a pair the store does not hold with `ErrNotSubscribed`. A prompt's subscriptions are listed in ascending byte order of the pattern. `Update` keeps them, and `Delete` removes them with the prompt. Subscriptions say nothing about runs: making one runs nothing, and removing one touches no run.

## Runs

A run's **id** is `prr_` and 16 lowercase hexadecimal digits, minted by the run core with `NewRunID` before the run is recorded, because its folder is named by it (`D07-runs`). Its **prompt** is its prompt's id, the one reference from a run to its prompt. Its **model** is the prompt's model when the run was asked for, kept on the run because an `update` may change the prompt's model later and the run page, `runs`, `result` and `run.started` show the model the run used. Its **user** and **request id** are those it acts as and was caused by. Its **trigger** is `manual` for a run the `run` tool asked for and `event` for one a delivered event started (`D14-delivery`), and its **event** is, for an event run, the id of the event it was made for, and empty otherwise. Its **started** and **finished** times are the run core's, kept in UTC to the second; started is the moment the run was asked for, whether its process started then or later, and finished is zero while the run is queued or running. **Stdout bytes** and **stderr bytes** are how many bytes of each stream the run kept, recorded when the run ends; while a run is queued or running the record holds zero and its files are the measure (`D07-runs`). **Stdout truncated** and **stderr truncated** say each stream was cut at `OUTPUT_MAX_BYTES`. Its **usage** is seven counts the run core sums from the run's transcript when the run ends (decision 8, `D07-runs`): `Calls`, the round trips; `ToolCalls`; `InputTokens`, `CachedTokens`, `OutputTokens` and `ReasoningTokens`; and `CostNanos`, agentkit's nano-USD integer, kept exactly as given, never converted or rounded. Its **status** is one of six words, and its **exit code** and **reason** apply only to one of them each:

- `queued` while the run waits for a slot, no process of it started (`D07-runs`);
- `running` while the process lives;
- `exited` when the child ended on its own, with its exit code, from 0 to 255: 0 to 4 are the child's outcomes (`D05-agent`) and 128 plus a signal's number a signal prompts did not send;
- `killed` when prompts killed it, or took it out of the queue before it started: on `cancel`, on its prompt's `delete`, at the drain deadline, or at the next start for a run still recorded `running`;
- `timed_out` when prompts killed it at `PROMPT_SECONDS`;
- `failed` when the child never started, with one of two reasons: `start_failed` (the process could not be launched) and `queue_abandoned` (the run was still waiting for a slot when prompts stopped, or when the next start found it recorded `queued`, or it was asked for after prompts began to stop while every slot was taken, and so was never queued at all).

Scripts' other five reasons were git's and its source's; prompts has neither, so a `failed` run here is only ever one that never started, and it has no output and no usage.

The status and reason words are exported constants of this package, beside the record whose field they fill, because the store refuses a record that does not use them and every consumer — the run core that writes them, the tools, pages and trail that show them — already imports the store; a reason's sentence on the run page is `D08-pages`'.

**Departures from scripts' run record.** Two, both decided elsewhere and recorded here. First, truncation is kept per stream: scripts keeps one `Truncated` flag saying either stream was cut, and prompts keeps `StdoutTruncated` and `StderrTruncated`, because the run page (`assets/run.html`) marks each stream it shows as cut on its own. The single flag scripts exposes is still what the trail's `run.finished` and the tools' run entry and result expose as `truncated`, and `Run.Truncated` is the one definition of it: the OR of the two. Second, a run keeps its usage (decision 8), seven integer columns on the run's row, zero until the run ends: set by `FinishRun` for a run that ends `exited`, `killed` or `timed_out`, whatever its child spent before it ended, and zero for a run that ends `failed` or a queued run that ends `killed`, neither of which ever ran. The store neither reads the transcript nor sums anything: the run core hands the counts in.

A run has three transitions in the catalog. `AddRun` records it once: `running`, after its process has started; `queued`, when every slot is taken and it must wait; or `failed`, when it could not start, or when it was asked for after the drain began while every slot was taken, which records it `failed` with `queue_abandoned` without ever queuing it; `D07-runs` decides which and when, and a run cut off before any is never recorded. `StartRun` moves a `queued` run to `running` once its process has started, keeping its `started`. `FinishRun` ends a run exactly once: a `running` run as `exited`, `killed` or `timed_out`, with its output sizes, truncation and usage, and a `queued` run as `killed` or `failed` with `start_failed` or `queue_abandoned`, with no output and no usage, since it never ran. Of two calls racing to end the same run, one succeeds and the other is told the run has already ended (`ErrEnded`), which is how `cancel` racing a run's own exit is refused; `StartRun` of a run no longer queued is told the same. Nothing moves a run back to `queued` or `running`, and nothing makes a running run `failed`.

## Reads

`Find` is a caller's own prompt by name, so another owner's prompt is indistinguishable from none; `List` is one owner's prompts, in ascending byte order of name; `Taken` is the space-wide name check. `FindRun` is a run of one of a caller's own prompts, so another owner's run is indistinguishable from none; `RunByID` is any run, for the run core. `Subscribers` is every prompt, of every owner, holding a subscription that matches one event name, each once, for the delivery (`D14-delivery`); `Delivered` says whether a prompt has had a run from one event id. `Runs` is one prompt's runs, newest first: in descending order of started, and among runs started in the same second in descending byte order of id. `Running` is every run still recorded `running`, of every owner, which a start marks `killed`, and `Queued` every run still recorded `queued`, which a start marks `failed` with `queue_abandoned` (`D07-runs`). `PastKeeping` is every run past keeping at a moment, over the whole catalog: a run that is neither `running` nor `queued`, that started more than `RUN_KEEP_DAYS` days of 24 hours before that moment, and that is not among its prompt's newest `RUN_KEEP_COUNT` runs in the order `Runs` answers them; every run counts toward that rank, a running or queued one included. The store reads neither setting; `D07-runs` hands in the values `D12-limits` read. All lists are never nil.

## Writes

`Create` mints a prompt's id and stamps its created time. `Update` changes the fields its `Change` names and says whether anything changed. `Delete` removes a prompt, its subscriptions, every run record of it whatever their status, and its delivered-event memory, in one step; the run core kills its running runs and removes its folders before that call (`D07-runs`). `Subscribe` and `Unsubscribe` add and remove a subscription and answer the prompt as it is after the call. `AddRun`, `StartRun` and `FinishRun` are the three transitions above; `AddRun` of an event run also records its prompt and event id in the same write, and refuses a second run of one prompt for one event id with `ErrDelivered`, which is the dedup on prompt id and event id decision 13 asks for: a redelivered event starts nothing, even after the first run is pruned. `DeleteRun` removes one run record, which is what pruning removes once the run core has removed the folder (`D07-runs`); it leaves the delivered-event memory, so `Delivered` still answers true for a pruned event run. At every moment every run the store holds names a prompt the store holds, so a run recorded while its prompt is being deleted is either refused or removed with it.

## Errors

`ErrNotFound`, `ErrNameTaken`, `ErrEnded`, `ErrNotSubscribed` and `ErrDelivered` are answers about the catalog's content. Every other error from a method is answered as the catalog being unreachable: every consumer answers it with `Unreachable`, or, for a page, with the unavailable page (`D08-pages`), never quoting the underlying error. A failing store, a random source that fails and a context already done all end there. So does a write given a value no consumer sends — a name `ValidName` refuses, an event pattern `ValidEvent` refuses, an empty owner, model or prompt text, a change that would empty the model, the text or the schema, a run that breaks the record's rules — which changes nothing. When one call meets several of these conditions, one fixed precedence decides its answer: a done context, then a failing store, then an invalid argument, then a missing record, then a taken name, an ended run, a missing subscription or an event already delivered.

## Decisions

- Ids are 8 bytes of `Rand`; a drawn prompt id already catalogued is drawn again, up to eight candidates in all, after which `Create` gives up with a catalog error, so a `Rand` that repeats itself cannot hold a call for ever. A run id already catalogued is a catalog error from `AddRun`; with 64 random bits the run core does not plan for it.
- Run times are given by the run core, not stamped by the store, because started is the moment of the `run` call and finished the moment the run core saw the end; the store keeps them to the second.
- The order of `Runs` breaks a tie of started by descending id, so the whole list is the exact reverse of ascending (started, id).
- Pruning is split: the store answers which runs are past keeping and deletes a record; the run core removes the folder first, so a failure between the two leaves a record whose files are gone, a state the pages and tools already show, never a folder no record names.
- A queued run is a record before its process exists, because `run` answers it at once and `runs` and `result` show it; `StartRun` is its own transition, so its `started` stays the moment it was asked for. The queue's order is the run core's, held in memory; the store keeps only the status, and `Queued` exists for the start that finishes what a dead prompts left waiting.
- `Delete` removes running runs' records too: the store does not wait for a process, and `D07-runs` ends every running run before calling it.
- The store has no `Open` and no `Close`: the handle is appkit's, opened and closed by `cli.Run`, and a store over it lives as long as it does.
- One migration with real tables, not scripts' baseline-plus-blob: scripts' `catalog` blob exists only to adopt catalogs earlier scripts releases wrote, and prompts has none. The tables follow cron: text times, a unique `name`, a primary key per natural pair.
- `Update(ctx, id, Change)` replaces scripts' `SetRef`: a prompt has five changeable fields where a script had one, and one write with pointer members keeps an `update` that names several fields atomic.
- The store keeps a prompt's model, groups and schema without checking them against agentkit: the tools check them before they call (`D11-tools`), and a record already stored must read back even when the catalog it was checked against has since moved.
- The owner's email is kept on the prompt, not looked up per run: a delivered event carries no request of the owner's, and decision 11 hands an event run's child the owner's email, so an event run takes the stored value (`D14-delivery`), while a manual run takes its caller's email from the request (`D07-runs`). The store keeps whatever `Create` was given, the empty string included, and `Update` never changes it.
- `Run.Model` is kept on the run, not read through its prompt, so a run shows the model it used after an `update` changed the prompt's.
- Usage is seven columns, not a JSON value, so a later page or tool could total them in SQL; `CacheWrite5mTokens` and `CacheWrite1hTokens`, which agentkit's usage also carries, are not kept, as decision 8 lists only seven.
- `Delivered` answers false, not `ErrNotFound`, for a prompt id the store does not hold: the run core asks it before anything else and a missing prompt is found by `AddRun`.
- Clearing a schema is out of this release (root ruling 7): a `Change` whose `Schema` points at an empty value is an invalid argument, not a clear, so no design reads an empty schema change two ways when appkit's `mcp` gains the absent-or-null distinction and a later design adds the clear.

## Consumer tasks

`cli.Run` opens the catalog with `d, err := db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "prompts.db"), Migrations: prompts.Migrations(), Now: p.Now})`; on any error while `ctx` is not done it writes `D03-serve`'s diagnostic; otherwise it builds `st := store.New(d, store.Config{Now: p.Now, Rand: rand})`, hands it to the run core and the handler, and calls `d.Close()` after the drain.

The tools (`D11-tools`), `u` being the `identity.Caller` of the call: `list` is `s.List(ctx, u.UserID)`, each `Prompt`'s `Last` giving `last_run` and `len(Subscriptions)` the count; `show` is `s.Find(ctx, u.UserID, name)`; `create` checks `store.ValidName(name)`, then `s.Taken(ctx, name)`, then the model, text, groups and schema, and calls `s.Create(ctx, store.Draft{Owner: u.UserID, OwnerEmail: u.Email, Name: name, Model: model, Prompt: text, System: system, Tools: groups, Schema: schema})`, `store.ErrNameTaken` still answering the taken refusal when a racing create won; `update` is `s.Find` then its checks then `s.Update(ctx, p.ID, store.Change{Model: &model, Tools: &groups})` with only the members sent, its `changed` deciding `prompt.updated`; `subscribe` is `s.Find`, then `store.ValidEvent(event)`, then `s.Subscribe(ctx, p.ID, event)`; `unsubscribe` is the same with `s.Unsubscribe`, `store.ErrNotSubscribed` answering `tools.NotSubscribed`; `delete` is `s.Find` then the run core's deletion, which ends with `s.Delete(ctx, p.ID)`; `runs` is `s.Find` then `s.Runs(ctx, p.ID)`; `result` and `cancel` are `s.FindRun(ctx, u.UserID, id)`, `cancel` then handing the run to the run core, whose `s.FinishRun` answering `store.ErrEnded` is the refusal `tools.Ended`. `store.ErrNotFound` is `tools.MissingPrompt` or `tools.MissingRun`; an error matching no sentinel is `store.Unreachable`. A `Run`'s `Status` compared with `store.StatusExited` decides whether `exit_code` is present, with `store.StatusFailed` whether `reason` is, with `store.StatusQueued` and `store.StatusRunning` whether the usage members are, its `Trigger` compared with `store.TriggerEvent` whether `event` is, and `r.Truncated()` is `truncated`.

The run core (`D07-runs`): `id, _ := store.NewRunID(rand)`; after the process has started, `s.AddRun(ctx, store.Run{ID: id, Prompt: p.ID, Model: p.Model, User: u.UserID, RequestID: u.RequestID, Trigger: store.TriggerManual, Status: store.StatusRunning, Started: started})`, or for an event run `Trigger: store.TriggerEvent, Event: req.Cause.ID` (`D14-delivery`), whose `store.ErrDelivered` means the prompt already has its run from that event, after a `s.Delivered(ctx, p.ID, req.Cause.ID)` asked first; or, when every slot is taken, the same with `Status: store.StatusQueued`, and once its process has started `s.StartRun(ctx, id)`; or for a run that could not start the same with `Status: store.StatusFailed`, `Reason: store.ReasonStartFailed` and `Finished` set; when the process ends, `s.FinishRun(ctx, id, store.Ending{Status: store.StatusExited, ExitCode: code, Finished: now, StdoutBytes: n, StderrBytes: m, StdoutTruncated: cutOut, StderrTruncated: cutErr, Usage: store.Usage{Calls: c, ToolCalls: t, InputTokens: in, CachedTokens: ca, OutputTokens: out, ReasoningTokens: re, CostNanos: cost}})`; for a queued run cancelled, `store.Ending{Status: store.StatusKilled, Finished: now}`, and abandoned, `store.Ending{Status: store.StatusFailed, Reason: store.ReasonQueueAbandoned, Finished: now}`; at start, `s.Running(ctx)` and a `FinishRun` with `store.StatusKilled` and the usage its transcript holds for each, and `s.Queued(ctx)` and a `FinishRun` with `store.StatusFailed` and `store.ReasonQueueAbandoned` for each; after every end, `s.PastKeeping(ctx, now, days, count)`, each run's folder removed, then `s.DeleteRun(ctx, r.ID)`; to delete a prompt, `s.Runs(ctx, p.ID)` to find what is running or queued, the kills and `FinishRun`s, then the folder `state/runs/<prompt id>/` removed, then `s.Delete(ctx, p.ID)`. The spec an event run's child reads takes `p.OwnerEmail` as its email (`D14-delivery`); a manual run's takes its caller's.

The trail (`D10-trail`) reads `r.Truncated()` and `r.Usage`'s `Calls`, `ToolCalls`, `InputTokens`, `OutputTokens` and `CostNanos` for `run.finished`. The pages (`D08-pages`, `D09-run-files`): the landing is `s.List(ctx, u.UserID)`; a prompt page is `s.Find` and `s.Runs`, `len` of which is the runs kept; a run page and its files are `s.Find` then `s.FindRun`, the run's `Prompt` compared with the prompt's `ID`, its `StdoutTruncated` and `StderrTruncated` marking each stream and `Truncated()` the card. For an error matching no sentinel, a page answers the unavailable page with status `503`, and a run's file answers `store.Unreachable` and a newline, as plain text with status `503`.

A test opens a handle with `d, err := db.Open(ctx, db.Config{Path: filepath.Join(t.TempDir(), "state", "prompts.db"), Migrations: prompts.Migrations(), Now: clock})` and builds a store with `store.New(d, store.Config{Now: clock, Rand: bytes.NewReader(known)})`; creates, finds, lists, updates and deletes prompts; adds, starts, finishes, lists and deletes runs, with usage and each stream's truncation; subscribes and unsubscribes prompts, patterns among them, and lists an event name's subscribers; adds event runs and asks `Delivered` before and after `DeleteRun` and `Delete`; asks which are past keeping at a moment it chooses; closes the handle and opens another on the same path to see the same records; and calls `d.SetFailing(true)` before a call to see a catalog error, and `d.SetFailing(false)` to see the same store answer again. A schema test opens a fresh catalog with `prompts.Migrations()` and, inside a `d.Read`, queries `sqlite_master`, `PRAGMA table_info`, `PRAGMA index_list` and `PRAGMA index_info`.

## REQUIREMENTS
