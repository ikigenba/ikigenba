# D13-on-a-space

What prompts itself contributes when it runs on a space and in a sandbox, and what it does not. The path from a checkout to a browser, curl and an agent crosses many hands, and almost every step on it belongs to someone else: devctl builds and ships the suite release and pushes the five provider keys to the space's parameter store, opsctl activates the release, writes the environment (the keys included), publishes the socket, bounds the unit, keeps and replicates the database and generates nginx, opsctl and the sandbox include prompts' nginx fragment in its server, the events app delivers the events other apps emit, auth decides every credential and whether a request reaches prompts at all, the host's nginx terminates TLS, sends a guest to sign in and challenges `/mcp`, the mcp gateway relays tool calls and answers a run's `suite` calls, the model providers answer a run's round trips, and the sandbox stands the same arrangement up on a developer's machine. prompts' own share is what the earlier designs already state — the layout, the run seam, the paths and the keys `Run` may look up (`D01-layout-and-run-seam`), the commands, the manifest and the fragment (`D02-cli`), the serve path, its start checks and the reading of the five keys at start (`D03-serve`), the catalog (`D04-store`), the child's role and its run spec (`D05-agent`), the process (`D06-runner`), the run core, the spec it composes and the child's thirteen variables (`D07-runs`), the pages (`D08-pages`), the run files (`D09-run-files`), the trail (`D10-trail`), the tools (`D11-tools`), the settings (`D12-limits`) and the delivery (`D14-delivery`) — plus one guarantee a space and a sandbox lean on that no single earlier document owns: neither the credential a caller presents nor any of the five provider keys lands in anything prompts records or keeps, in the environment of a run's child, or on standard error. For the keys it holds for every host, a run whose round trip fails in transport included, since agentkit sends every key in a header, never in a URL a transport failure's text could quote (`D05-agent`). This design states that guarantee, records where prompts departs from scripts' shape on a space, and says plainly what can be checked only on a running space or sandbox.

This design declares no name. Everything it states is behaviour of names other documents declare: `cli.Process` and `cli.Run`, and the `Sink`, `Stderr`, `Dir`, `Cgroup`, `LookupEnv` and `BaseURL` fields of `cli.Process` (`D01-layout-and-run-seam`); `agent.KeyVariable`, the child's role and its run spec (`D05-agent`); and the variable `IKIGENBA_WORK_DIR` and the run folder's files (`D07-runs`). It mentions them without restating them.

## What ships

The suite release holds four members of prompts' directory: `bin/prompts`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`. Two of those are prompts' contract and are already designed: the manifest's exact text — `guests = false`, `mcp = true`, the five secrets `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `XAI_API_KEY` and `OPENROUTER_API_KEY`, its `[env]` holding the eleven settings other than `DRAIN_SECONDS`, its `[database]` table naming `state/prompts.db`, its `[resources]` table (`slice` `apps`, `memory_max` `896M`, `go_memory_limit` `128M`, `delegate` true) and its `[home]` table (`group` `core`) — is `D02-cli`'s `cli.Manifest`; the fragment's exact text, the two exact-match locations answering `/events` and `/declarations` 404, is `D02-cli`'s `cli.NginxConf`; the root package's `Etc` holds exactly `manifest.toml` and `nginx.conf` with exactly those constants' bytes (`D01-layout-and-run-seam`, `D02-cli`), and since `Etc` is an `embed.FS` those bytes are the committed files'. A third file under `etc/` would give `Etc`'s `etc` directory a third entry, which is how "nothing under `etc/` but the manifest and the fragment" is proved. That `prompts --version` prints the display string of its environment, an empty line with no identity set, and `prompts manifest` prints the manifest byte for byte is `D02-cli`'s. That the binary is static `linux/amd64` and cgo-free is `AGENTS.md`'s release build gate, not a requirement. No `assets/` directory or font ships beside the binary: the templates are embedded in the root package (`D01-layout-and-run-seam`) and appkit's shared files are served from appkit's `page` package (`D08-pages`). Neither the database nor any run folder is in the release; prompts creates `state/prompts.db` and `state/runs/` on its first start (`D01-layout-and-run-seam`, `D03-serve`).

There is one binary and no second program. The child that runs a prompt is the same `bin/prompts` started as `prompts agent` (`D02-cli`, `D05-agent`, `D06-runner`), so it has the app's build, version and module, and the release layout's rule of one binary per app holds. Unlike scripts, prompts needs no interpreter and no `git` from the host. The one host program a run may start is `bash`, which toolkit's `Bash` tool runs for a prompt offering the `bash` group; every host and every developer's machine has it, and prompts makes no start check for it. toolkit's `Bash` refuses to be built when no `bash` is on the `PATH` (toolkit's published design for `Bash`), so on a host without it a run offering the `bash` group exits 4 with its tools unbuilt (`D05-agent`); it is not a start refusal.

The rest of the release is not prompts' to state. The tarball, its layout, the member list of prompts' directory, the release's name and top-level directory carrying the commit's full sha, and no member of prompts' directory or its path carrying it are `devctl build`'s; `share/icon.svg` is human-authored (`AGENTS.md`), and that its presence gives prompts' banner its icon is opsctl's services file. No test reads the checkout, so the tarball and the icon are outside what a requirement can state; a developer checks them with `tar`.

## The five keys on a host and on a developer's machine

prompts holds no key of its own. The manifest names five secrets, one per host agentkit knows an API-key endpoint for; on a space `devctl secrets push` takes each from the developer's environment or login keyring into the space's parameter store and opsctl writes them into `/etc/opt/ikigenba/prompts/env`, and in a sandbox `sandbox up` takes them from the shell that runs it. Every named secret must exist or opsctl and the sandbox refuse the app; that refusal is theirs, not prompts'. prompts reads the five once at start, through `LookupEnv`, keyed by host (`D03-serve`, `D07-runs`), and a missing or empty one is not a start refusal: a run whose model's host has no key is started with an empty one, and the provider's refusal decides its exit (`D05-agent`, `D07-runs`). That every space and sandbox has all five is the decisions document's guarantee, not something prompts checks.

The key a run needs goes to the child in one place only: the run spec prompts writes to the child's standard input (`D05-agent`, `D06-runner`, `D07-runs`). The child reads that spec whole, keeps the key in memory for the provider's authenticator, and closes its standard input before the model's first round trip (`D05-agent`). The child's environment is exactly the thirteen variables `D07-runs` composes, none of them a key, and that environment is what every `bash` command the model runs sees, because toolkit's `Bash` runs `bash -c` with the process's environment (toolkit's published design for `Bash`). The provider's endpoint receives the key, by design: that is the one place it is meant to go.

## On a space

prompts on a space is the same binary serving on the same terms as under a test: a socket passed as descriptor 3, `/var/opt/ikigenba/prompts` as its working directory, its settings and the five keys from `/etc/opt/ikigenba/prompts/env`, and `IKIGENBA_SERVICES` naming the host's services file `/run/ikigenba/services.json`. Who supplies each of those is opsctl's (the unit, the socket `/run/ikigenba/prompts.sock`, the environment file from the manifest's `[env]`, its secrets and the space's `DRAIN_SECONDS`, the apps' slice and the `[resources]` ceiling over the unit and so over every child it starts, the delegation of the unit's control group, the services file with its `url` `https://prompts.<space>` and `mcp` true, and the replication of the database `[database]` declares); what prompts does with them is the earlier designs'. With `/var/opt/ikigenba/prompts` as `Dir`, the catalog is `/var/opt/ikigenba/prompts/state/prompts.db` and the run folders are under `/var/opt/ikigenba/prompts/state/runs/`. Every child is handed that services file's path as `IKIGENBA_SERVICES` and the service's `PATH` verbatim (`D07-runs`), so a `suite` run reaches the gateway's socket as a script does. The run folders live under `state/` and stay on the host across releases; they are not replicated, and a catalog restored from the replica comes back with every run's files gone, which prompts shows as such (`D03-serve`, `D07-runs`).

The child reaches its model's provider over the network from the host: the endpoint is the offering's own, since `main` leaves `BaseURL` empty (`D01-layout-and-run-seam`), and only a test points it elsewhere. That the host can reach the providers is the space's; prompts adds no proxy and no retry (`D05-agent`).

Because the manifest says `guests = false`, the space's nginx puts every request for prompts to auth's `/check`. A request with no credential never reaches prompts: a page is redirected to sign in and `/mcp` is challenged with `401`, by nginx. A request whose credential auth refuses is answered by auth and never reaches prompts either. Every request nginx passes carries `X-User-Id` and `X-User-Email`, which appkit's `identity.Require` turns into the caller (`D03-serve`), `X-Forwarded-Proto: https`, which makes the addresses prompts builds `https` ones (`D08-pages`), and an `X-Request-Id`, which prompts records as each event's request id and hands to a run it starts (`D03-serve`, `D10-trail`, `D07-runs`). A deploy restarts prompts, which is a stop: a run still queued at the signal is finished `failed` with reason `queue_abandoned`, and a run still in flight at the drain deadline is killed, its session whole, and recorded `killed` (`D03-serve`, `D07-runs`).

The unit delegates its control group, so `main` finds prompts' own group and hands it to `Run` as `Cgroup` (`D01-layout-and-run-seam`), and the start arranges it: prompts in `main/`, every run together under `runs/`, bounded by `RUNS_MEMORY_MAX_BYTES` and `RUNS_CPU_PERCENT`, and each run in a group `runs/<run id>/` of its own, bounded by `RUN_MEMORY_MAX_BYTES` and `RUN_PIDS_MAX` and removed when the run ends (`D03-serve`, `D06-runner`). Every `bash` command a run's model starts is a descendant of the child and so stays in the run's group. Under a test those groups are plain files in a temporary directory; that the kernel enforces them is shown only on a space or in a sandbox.

The host's nginx includes `/opt/ikigenba/current/prompts/etc/nginx.conf` in prompts' server, so `/events` and `/declarations` at prompts' public name are answered 404 by nginx for every method and never reach the socket. On the socket the same two paths stay open to siblings: the events app delivers there every event an app emits, with no identity headers, and prompts answers as `D03-serve` routes it outside its identity gate, making the runs `D14-delivery` states, each as the prompt's owner with the owner's email.

## The credential and the keys

On a space every request prompts receives has been admitted by auth, and the client's `Authorization` header may reach prompts untouched: an agent's or curl's `Bearer` token, or git's `Basic` credential, which the host's nginx challenges for in every wired server block. prompts never needs the header — the caller is appkit identity's `identity.Caller`, from the identity headers nginx sets. prompts does need the five provider keys, and holds them in its own process for the life of `Run`, which it makes non-dumpable at start so that a run's `bash` command, running as the same user, cannot read them from its `/proc/<pid>/environ` or memory (`D03-serve`), as the child makes itself (`D05-agent`). Neither is to be in any record prompts leaves: not in the trail, not in prompts' standard error, not in any file under its working directory, and not in the environment of any child it starts, nor in what a child writes to its standard error. For a key, what a child writes to its standard error and the transcript it keeps hold none whether its round trips are answered or fail in transport (`D05-agent`). nginx's logs are opsctl's.

A request carries a **credential header** when its `Authorization` header is `Bearer <p>`, or `Basic ` and the standard base64 of `<u>:<p>`, the test choosing `<u>` and `<p>` long, with an uppercase letter in every 8-character stretch of each and of their base64 value, so that no id, request id or number prompts mints can match them, and occurring nowhere else in what it sends (R-1T6I-11M9). The test's **provider keys** are the five values its `LookupEnv` gives for the five variables `agent.KeyVariable` names, chosen the same way and occurring nowhere else in what the test hands prompts — in particular never in an answer of the provider fixture (R-1UEE-ETCY). Their **secret strings** and **key strings** are every run of 8 or more consecutive characters, so a truncated or partial leak counts as a leak. A secret written in another encoding — re-encoded in base64, URL-escaped, changed in case, split by other bytes — is outside what these tests can detect, as with scripts: the guarantees are about the credential's and the keys' own characters.

The guarantees are proved over one sequence of requests (R-YZAY-8W1G), made once with every request carrying a `Bearer` credential and once more, over prompts of other names, with every request carrying a `Basic` one, under one `Run` whose `LookupEnv` gives the five provider keys, whose `BaseURL` names a provider fixture the test serves, and whose services file holds no `mcp` entry. The sequence reaches every kind of route prompts serves behind the identity gate and every tool: `tools/list` and all eleven tools, a refused tool call, the catalog, about, tools and appkit paths, a prompt page and a run page with their slash-less forms, a prompt name and a run id that name nothing, each of a run's files, its `work/` folder and a directory under it as well as a file, a run that ends on its final message, a run the provider refuses, so that the child writes its one line naming the failure to standard error, a run of a prompt offering the `suite` group, which cannot build its tools because the services file names no gateway and so exits 4 with its own line on standard error before any round trip (`D05-agent`), a run cancelled while it waits on the provider, and a prompt deleted with a run in flight. Every run that reaches the provider is made, by the fixture, to call the `Bash` tool once to copy two things into its `work/` directory: the environment `bash` passes to the commands it runs, the bytes of `/proc/$$/environ`, which `bash` inherited from the child; and the child's own arguments, the bytes of `/proc/$PPID/cmdline`. The child's own `/proc/$PPID/environ` is not among them: the child is non-dumpable (`D05-agent`), so that file is refused to the run's `bash`, as it is meant to be, while its `cmdline` stays readable. That shows the child's environment and command line from inside a model's tool call, which is exactly where decision 11 keeps the key out of reach. The bash manual states that `$$` expands to the process id of the shell and `$PPID` to the process id of its parent, `proc_pid_environ(5)` states that `/proc/<pid>/environ` holds the environment the program running in that process was started with, `proc_pid_cmdline(5)` that `/proc/<pid>/cmdline` holds its arguments, and toolkit's `Bash` starts `bash -c` with the child's own environment (its published design), so the parent of that `bash` is the child. Observed while designing with bash 5.2.37: `env -i FOO=bar bash -c 'cat /proc/$$/environ'` printed `PWD=<the working directory>`, `FOO=bar`, `SHLVL=0` and `_=/usr/bin/cat`, because bash execs its last command in its own process and adds those variables to the environment it passes on; what is read is therefore the inherited environment plus bash's own few, which holds a leaked key whenever the child's environment does. A `bash -c 'cat /proc/$PPID/cmdline'` started from a known parent printed that parent's arguments. Because the run is a real child of the test binary (`AGENTS.md`), the key a run uses really crosses its standard input, and the provider fixture really receives it; that the right key reaches the provider is `D05-agent`'s and `D07-runs`' to state. A `suite` run's calls, when a gateway is there, carry the run's user, email and request id and never the key or the caller's header (`D05-agent`); the gateway's own records are the gateway's.

Seven guarantees follow. First, nothing prompts records — no event's name, envelope or attribute — holds a secret string or a key string (R-YZAY-8W1G); each event's exact keys are already fixed by the documents that own them (`D03-serve` for the request pair and the service events, `D10-trail` for every `prompt.*` and `run.*` event, appkit's MCP server for `tool.called`), and none of them reads the header or a key, so this is the end-to-end statement of what those already imply, proved through `Run` with a capturing sink. Second, nothing `Run` writes to `Stderr` holds one, including the journal's copy of an event telemetry could not take (R-Z0IU-MNS5). Third, neither the environment nor the arguments of any run's child hold one (R-Z1QR-0FIU): the environment is exactly the thirteen variables `D07-runs` composes, of the request only the caller's user id and the request id reach it, and the arguments are the fixed `agent` (`D06-runner`). Fourth, what a child writes to its standard error holds none, read as `result`'s `stderr` member and as the run's `stderr` file, the provider-refused run's and the unbuilt `suite` run's failure lines among them (R-Z2YN-E79J). Fifth, nothing prompts leaves on disk holds one, neither while a run is in flight nor after `Run` returns: no file under its working directory — the catalog and its SQLite sidecar files, and every run folder's `input.json`, `stdout`, `stderr`, `transcript.jsonl` and `work/` — contains a secret string or a key string, read once while the held runs wait on the provider, before they are cancelled or deleted, and once after `Run` returns (R-Z46J-RZ08). Sixth, no answer prompts gives in the sequence — no tool result and no body of a `GET` — holds one, so a key never reaches a caller (R-Z5EG-5QQX). Beside them, prompts sets no cookie, so no response to a page, run file or appkit path of the sequence carries `Set-Cookie` (R-Z6MC-JIHM); MCP answers are otherwise left to appkit's client. A run's `input.json` is the `input` argument byte for byte, which the test chose; the guarantee is that prompts adds nothing of the header or a key to it.

Two paths are not in the sequence. The catalog refusal, the unavailable page or answer a page or tool gives when the catalog cannot be read, would end the sequence, since the one way a test of `Run` has to make the catalog fail after `Run` opened it is dropping a table from a second handle (`D03-serve`). The two events paths are not in it either: nginx answers them 404 at the public name, so no credential-bearing request reaches them, and a delivery on the socket carries no `Authorization` header; a run a delivery makes is handed only the prompt's owner, the owner's email and the delivery's request id (`D14-delivery`), and its key reaches it the same way as a manual run's.

## In a sandbox

In a sandbox prompts is the same binary in the same arrangement. The sandbox takes as an app every immediate subdirectory of the checkout holding `etc/manifest.toml`, so prompts joins a sandbox with no change to sandbox: it builds `cmd/prompts` from the worktree, runs it under its own units with a working directory of its own (`<data>/apps/prompts`), gives it the environment of a host — `DRAIN_SECONDS`, `IKIGENBA_SERVICES`, the manifest's eleven settings and its five secrets from the shell that runs `sandbox up` — plus variables a host never sets, runs it in its apps' slice with its control group delegated, puts its own nginx in front, and routes every request through auth's `/check`. A shell without the five keys makes `sandbox up` refuse prompts' manifest; that refusal is the sandbox's. prompts' contributions are the ones it makes on a space:

- It serves at `http://prompts.wip.localhost:7400`. Its catalog and run folders are under its working directory (`D01-layout-and-run-seam`), so they survive `down` and `up` because the sandbox keeps that directory until `wipe`.
- Its runs reach the real providers with the developer's keys, since `BaseURL` is empty in the binary, and a `suite` run reaches the sandbox's gateway through the sandbox's services file (`D05-agent`, `D07-runs`).
- The sandbox's nginx includes prompts' `etc/nginx.conf` from the checkout in prompts' server, so `/events` and `/declarations` answer 404 at the public name while the events app delivers on the socket.
- An agent's `subscribe`, then an event of a matching name, runs the subscribed prompt with no further call, as its owner, with the event as its input (`D11-tools`, `D03-serve`, `D14-delivery`).
- Its addresses are built from the sandbox's services file, and the requests arrive with `X-Forwarded-Proto: http`, so its profile and sign-out addresses are `http://auth.wip.localhost:7400/` ones (`D08-pages`).
- It reads nothing from its environment beyond what a host gives it, so the variables only the sandbox sets change nothing it does: the keys `Run` looks up are the closed list `D01-layout-and-run-seam` states.
- Its control group is delegated as on a host, so it prepares it and runs each child in a group of its own beneath `runs/` exactly as on a space (`D03-serve`, `D06-runner`).
- The same credential and key guarantees hold; `sandbox logs prompts` showing no line is `D03-serve`'s quiet standard error.

## Departures from scripts

- The guarantee covers a second kind of secret. scripts keeps only the caller's credential out of its records; prompts also holds five provider keys of its own and keeps them out of the same records and out of every child's environment and standard error, handing the one a run needs only through the child's standard input.
- The child is prompts' own binary, so the host needs no `git` and no `python3.12`, no first-boot line names a program for prompts, and there is no start check for a program on the `PATH`.
- The child talks to the network: its provider is on the other side of it. scripts' runs need nothing outside the host but the suite's own sockets.
- The manifest declares `guests = false` and five secrets, where scripts' declares no `guests` and none; the effect on a guest is the same: nginx and auth turn every guest away before prompts.
- A run folder keeps `transcript.jsonl` and `work/` where scripts' kept `tree/` and `out/`, and the guarantee reaches both.

## What only a space can show

These outcomes are space-level checks: no test of prompts can make them, and they are verified on a space or in a sandbox. They are recorded here, not required.

- prompts' directory in the suite release holds exactly `bin/prompts`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, `bin/prompts` is a static `linux/amd64` executable, the icon is an SVG, the commit is in the release's name and top-level directory and nowhere in a member of prompts' directory or its path, and the binary, asked with no identity in its environment, prints an empty line for its version (devctl; `D02-cli`).
- The five keys reach `/etc/opt/ikigenba/prompts/env` from the space's parameter store, a space missing one refuses the app at activate, and a sandbox started from a shell without them refuses prompts' manifest (devctl, opsctl, the sandbox).
- A run reaches its model's real provider with the key for its host and comes back `exited` 0 with the model's answer as `stdout` and a non-zero cost (the provider, the host's network; prompts' part is the run, `D05-agent`, `D07-runs`).
- The sandbox shows prompts' own environment holding the five keys while no run folder, `stderr` file or event holds any of their characters (the sandbox, telemetry; prompts' part is this design's requirements).
- The unit runs as `ikigenba` in the apps' slice under `[resources]`, so `memory_max` bounds prompts and every child together, and its control group is delegated to prompts; the kernel holds each run to `RUN_MEMORY_MAX_BYTES`, with no swap, and `RUN_PIDS_MAX`, and every run together to `RUNS_MEMORY_MAX_BYTES` and `RUNS_CPU_PERCENT`, so a child or a `bash` command that takes too much memory is killed with its run's group while prompts and every other run go on; an operator reads those limits from `$cg/runs/` and `$cg/runs/<run id>/` while a run is going and finds the run's group gone once it ends (opsctl's unit and delegation, the kernel; prompts' part `D03-serve`, `D06-runner`, `D07-runs`); the database is kept and replicated across releases while the run folders are kept and not replicated (opsctl).
- A guest is redirected to sign in, a refused credential is answered `403`, and a `POST /mcp` with no credential is answered `401` with nginx's bearer challenge, in each case nothing reaching prompts' socket and prompts recording no event (nginx and auth; in a sandbox, the sandbox's nginx).
- auth's own records of each request and their sharing a request id with prompts' events (auth, nginx).
- The host's nginx log holds no token: its format is opsctl's, and prompts neither writes it nor affects it.
- The answers arrive over HTTP/2 and TLS on a space and over HTTP/1.1 in a sandbox (nginx).
- The host's nginx and the sandbox's include prompts' `etc/nginx.conf` in its server, so `/events` and `/declarations` answer 404 at the public name for every method, with or without a credential (opsctl, the sandbox, nginx; prompts' part is the fragment, `D02-cli`).
- The events app delivers to prompts' socket the events the space's or sandbox's apps emit, under a request id of its own and with no user (the events app; prompts' part is its answer and the runs it makes, `D03-serve`, `D14-delivery`).
- The gateway offers prompts' eleven tools, forwards the caller and the request id, and relays prompts' results; a `suite` run's calls appear in the trail as the gateway's `tool.called` under the prompt's owner with the run's request id (the mcp gateway, telemetry).
- The banner's mark and the sign-out button look as appkit's banner draws them, and the banner a browser opens shows prompts' icon (appkit's banner and scripts; no test runs them).

## REQUIREMENTS

- R-1T6I-11M9: prompts' design defines a request as carrying a **credential header** when it has exactly one `Authorization` header whose value is either `Bearer <p>`, or `Basic ` followed by the standard base64 encoding (RFC 4648, with padding) of `<u>:<p>`, where `<u>` and `<p>` are each at least 16 ASCII letters and digits, and every run of 8 consecutive characters of `<u>`, of `<p>`, and of that base64 value holds at least one uppercase ASCII letter; defines that request's **secret strings** as every substring of 8 or more characters of `<p>`, of `<u>`, and of the base64 value; and requires that no secret string occur anywhere else in what the test hands prompts — no other header, URL path, query or body of any request in the same test, no tool argument, a prompt's `prompt` and `system` and a run's `input` included, no value `LookupEnv` gives, no answer of a provider fixture, and no part of the services file; every requirement of prompts' design that names a credential header or its secret strings MUST denote that.
