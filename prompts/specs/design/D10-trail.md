# D10-trail

The trail: the contract of every `prompt.*` and `run.*` event prompts records — the closed set of event names, each domain event's attributes with their keys, types and values, which outcome records which event and in which request, the identity each event carries, and what no attribute ever carries — together with the three functions of `internal/runs` through which a run's events are formed. `D01-layout-and-run-seam` declares the names this design behaves through for a whole run (`cli.Process`, `cli.Run`, its `Sink`, `Now`, `Dir`, `LookupEnv`, `ScriptAfter` and `BaseURL`) and the entity ids (`store.ValidPromptID`, `store.ValidRunID`); `D04-store` declares the run record (`store.Run`, its `Usage` and its `Truncated` method) and the status, reason and trigger words; `D05-agent` declares the child role and its exit codes; `D03-serve` records the framework events (`service.started`, `service.stopping`, and the request pair through appkit's `telemetry.Middleware`) and wires identity; `D07-runs` decides when a run starts, ends, is cancelled, killed with its prompt, killed at the drain deadline or marked at the next start, and what its record then holds, its usage included; `D11-tools` declares the eleven tools, their results and refusals, and each tool's `tool.called`; `D14-delivery` decides which runs a delivered event makes and under whose identity. This document says, for those outcomes, which domain events they record with which values and under whose identity; it restates none of them.

## What is someone else's

The envelope of an event (`Time`, `Service`, `RequestID`, `User`), its JSON form, delivery, retries and the `undelivered event` line are appkit's telemetry contract and writer: its published writer hands the sink one event at a time in the order they were emitted, never holding up `Emit`; gives each event up to `telemetry.Attempts` attempts with pauses of `telemetry.RetryBackoff` and twice that between them; does not retry an event the sink rejects with an error wrapping `telemetry.ErrRejected`, which its socket sink returns for telemetry's `4xx`, that sink reading the services file afresh for every delivery; and writes an event it could not deliver as the `undelivered event` line. prompts states none of it again; it records every event through its one `*telemetry.Writer` with `Emit`, whose envelope request id and user are those of the `identity.Caller` on the context it is given. `telemetry.Attrs` is a `map[string]any` at the pinned appkit, and the writer carries `string`, `int64` and `bool` values as they are.

The registered entity prefixes `prm_` (entity type `prompt`) and `prr_` (entity type `prompt_run`), both owned by prompts, are rows of the registry in appkit's telemetry contract (`D11-telemetry-contract`, "Entity ids"). That registry is a design table with no code behind it, so the rows need no appkit release: the pinned appkit's telemetry package checks only that keys are snake_case, and `prompt` and `prompt_run` are. This design holds the requirements that prompts' values fit the rows, under the keys `prompt` and `prompt_run`.

## The events

prompts records exactly ten events: `service.started`, `service.stopping`, `request.started`, `request.finished`, `tool.called`, and the five domain events below. prompts calls no sibling itself, so it records no `sibling.called`. A run whose prompt offers the `suite` group reaches the gateway from the child, not from the app: the child is a separate process that holds no writer, and the gateway records each of its calls as `tool.called` under the run's user and request id. So a run's gateway calls are in the gateway's trail, never in prompts', and prompts' own `tool.called` is only ever for a call made to its own `/mcp`.

| Event | Attributes | Recorded when |
|---|---|---|
| `prompt.created` | `prompt` (`string`) | a `create` that succeeds |
| `prompt.updated` | `prompt` (`string`) | an `update` that succeeds and changes the stored value of at least one field; an `update` that changes nothing records none, and so do `subscribe` and `unsubscribe` |
| `prompt.deleted` | `prompt` (`string`) | a `delete` that succeeds, after the `run.finished` of every run of the prompt it killed |
| `run.started` | `prompt_run`, `prompt`, `model`, `trigger` (`string`, `manual` or `event`) | a run's process has started: at once, in its `run` call's request or its delivery's, before the call's `tool.called`; or later, for a run that was queued, when it leaves the queue, with no request around it |
| `run.finished` | `prompt_run`, `status` (`string`); `duration_us` (`int64`); `exit_code` (`int64`, only when `exited`); `reason` (`string`, only when `failed`); `truncated` (`bool`); `calls`, `tool_calls`, `input_tokens`, `output_tokens`, `cost_nanos` (`int64`, always) | a run reaches a final status, however it ends; a run that could not start, and a queued run that ended without starting (cancelled, deleted with its prompt, or `failed` with `queue_abandoned` at the stop or the next start), records only this |

Attributes name what happened, the ids of what it touched and, on `run.finished`, the counts it spent, never data: no prompt name, prompt text, system text, schema, tool group, run input, run output, transcript content, file name, email, provider key, query, argument, refusal text, error category, event name, event id or event attribute reaches a domain event. `run.finished` has no `prompt` and no `model`: the run's id leads to both through its `run.started` or `result`.

## Departures from scripts

prompts' trail is scripts' with these changes, all from the decisions document's trail decision (14):

- **Keys.** The entity keys are `prompt` (scripts' `script`) and `prompt_run` (scripts' `run`). A second run prefix is deliberate: a `run_` id means a scripts run suite-wide, and a trace tells the two apart from the id alone. The event names keep `run.started` and `run.finished`; only the attribute key and the id prefix change.
- **No `sha`.** prompts has no git, so `run.started` loses `sha`.
- **`model` on `run.started`.** It is the one name-like attribute, against scripts' rule that attributes carry only ids. It is the run's recorded `Model`, the prompt's model when the run was asked for, so a trace shows which model a run used without reading the catalog, even after an `update` has changed the prompt's model.
- **Usage on `run.finished`.** `calls`, `tool_calls`, `input_tokens`, `output_tokens` and `cost_nanos` are counts, not data, and are on every `run.finished`, `0` when the run spent nothing: a run that could not start, a queued run that never started, and a run whose transcript holds no usage. They are the record's `Usage` members as the run core summed them from the transcript (`D07-runs`); `cost_nanos` is agentkit's nano-USD integer, never converted. `cached_tokens` and `reasoning_tokens` are kept on the record and shown by the tools and pages but are not in the trail, since decision 14 lists exactly these five.
- **`truncated` is an OR.** The store records truncation per stream (`StdoutTruncated`, `StderrTruncated`); `truncated` is `store.Run.Truncated()`, true when either stream was cut, as scripts' single flag was.
- **No error category.** A provider failure ends the run `exited` with exit code 1 and the child's standard error naming agentkit's error category (`D05-agent`). Decision 9 says the category is "in `stderr` and the trail", but decision 14 lists `run.finished`'s attributes exactly and the category is not among them; decision 14's list wins, so the category is in `stderr` only and `run.finished` tells a provider failure only by `exit_code` 1.

## Identity

A request's `prompt.*` events carry its own request id and caller, as every handler's events do. A run's events are the exception: a run is caused by the `run` call that asked for it and keeps that call's user and request id, recorded on the run (`D04-store`), for as long as it lives. So both its `run.started` and its `run.finished` carry them, whenever its process starts, at once or later when it leaves the queue with no request around it, and whichever request or moment ends it: the child ending on its own, `PROMPT_SECONDS`, a `cancel` made under another request id, a `delete` of its prompt, the drain deadline, a stop that abandons it in the queue, or the next start finding it still recorded `running` or `queued`. The run core emits a run's events under a context carrying `runs.Caller` of its record, never the context of the request or moment that ends it, so a run's trail is whole under one request id, and the request that ended it is tied to it only by the run's id and by where the event falls in that request's window. `runs.Caller` carries no email: the envelope has no email, and the owner's email the child needs travels in the run spec (`D07-runs`), never in the trail.

A run a delivered event made (`D14-delivery`) was asked for by no `run` call: its record keeps the delivery's request id, the one `telemetry.Middleware` read or minted for the events app's request, not the event's own `request_id`, and its prompt's owner as its user, whoever caused the event; so its `run.started`, or its lone `run.finished` when it could not start, falls in the delivery's window when the delivery started it at once, and its `run.started` comes later, under the same two, when the delivery queued it, and its `run.finished` carries the same two whenever and however it ends, at the drain deadline included. A delivery records no `tool.called`, since no tool was called, and a delivery that makes no run records no `run.*` event. The event's id is the run's link back to it, in `result` and on the run's page, never in the trail.

## Where the events are formed

The run core, `internal/runs`, is the only place a run starts or ends, the place the event bus calls, and so the one emitter of `run.*` events: it exports `StartedAttrs`, `FinishedAttrs` and `Caller`, which form a run's attributes and its identity from its record, so the tools, pages and tests never form a run event themselves. The `prompt.*` events are emitted by the tools (`D11-tools`), the only callers that change the catalog's prompts, each with the call's own context and the one attribute `prompt`. No `trail` package exists: three pure functions over `store.Run` would be a concern without a caller of its own, and `runs` already imports the store and is the only caller.

## Decisions

- `duration_us` is passed to `FinishedAttrs` as a measured `time.Duration`, not derived from the record's `Started` and `Finished`, because the catalog keeps times to the second while the trail measures in microseconds; it runs from the reading of `Now` the `run` call (or the delivery) takes, a failed start's included, to the reading taken when the run core sees the end. A run killed at the drain deadline has its `run.finished` emitted before the writer's shutdown, but the drain has spent the deadline, and from the deadline on `Run` hands its sink nothing (`D03-serve`): that `run.finished` never reaches telemetry and is an `undelivered event` line before `service.stopping`'s. So the rules below that a run's `run.finished` precedes `service.stopping` in the trail are stated for a `Run` whose drain ended before its deadline; a trail cut at the deadline is `D03-serve`'s. A run the next start marks has no reading of its start but its record's, so its duration runs from its recorded `Started` to the moment it is marked.
- A `run` call does no slow work before it records its run: there is no git to resolve or unpack, only the catalog and the run folder. So scripts' rule for a call cut off by its client while its git was running has no counterpart here. A `run` call whose run was recorded, and so emitted `run.started`, can still get no answer, cut off at the drain deadline just after its recording or with its client gone; so the rule that every `run.started` names an answered call is stated only for a `Run` that cut off nothing and whose clients waited.
- A request that is not a tool call records its request pair and nothing else; `tool.called`'s attributes are appkit's, and the trail states them end to end only to prove prompts hands them to the sink unaltered.
- `truncated` and the five usage attributes are present on every `run.finished`, a failed start's included, holding the record's values.
- A queued run's `run.started` lies in no request's window: it is tied to its `run` call, or its delivery, by the request id it carries. Its `model` is the run's recorded model, the prompt's when the `run` call was made, even when an `update` changed the prompt's model while the run waited. A queued run abandoned at the stop is recorded at the signal, without waiting for any running run (`D07-runs`, `D03-serve`), so its `run.finished` precedes `service.stopping` and the `run.finished` of every run that ends within the drain.
- A refused tool call, a tool that only reads, `subscribe` and `unsubscribe`, a page, a run file and `/_appkit/` record no domain event; neither does pruning, nor the removal of an ended run with its prompt.
- A domain event is told to belong to a request by its request id for `prompt.*`, and by the request id of the `run` call or the delivery that made the run for `run.*`; position in another request's window is what ties a `cancel` or a `delete` to the `run.finished` it caused.
- Tests drive the child as `D05-agent` and `D07-runs` lay out: the runner starts the test binary's own `agent` role, which reaches a stand-in provider, an `httptest` server the test serves, at the base URL `Process.BaseURL` names. A run "that would not end of its own accord" is one whose stand-in provider withholds its answer until the test releases it or the run is killed; a run that "exits of its own accord with status `n`" is one whose child ends on its own, `0` when the stand-in answers with a final message and `1` when it answers with an error, say.

## Consumer tasks

The run core (`D07-runs`), once a run's process has started, at once or when it leaves the queue, its record `r` in hand: `w.Emit(identity.NewContext(ctx, runs.Caller(r)), "run.started", runs.StartedAttrs(r))`; when the run reaches a final status, its ended record `r` (usage summed, per-stream truncation recorded) and measured duration `d` in hand, however it ended: `w.Emit(identity.NewContext(base, runs.Caller(r)), "run.finished", runs.FinishedAttrs(r, d))`, `base` being any context, a cancel's request context or `context.Background()` alike.

The tools (`D11-tools`), `u` the call's caller: `create` on success calls `w.Emit(ctx, "prompt.created", telemetry.Attrs{"prompt": p.ID})`; `update` calls `w.Emit(ctx, "prompt.updated", telemetry.Attrs{"prompt": p.ID})` only when `store.Update` answered `changed`; `delete` hands the prompt to the run core's deletion, which kills its running runs and emits their `run.finished`, and once that returns calls `w.Emit(ctx, "prompt.deleted", telemetry.Attrs{"prompt": p.ID})`; `cancel` hands the run to the run core, which emits its `run.finished`; `run`, `subscribe` and `unsubscribe` emit nothing themselves.

A unit test calls `runs.FinishedAttrs(store.Run{ID: id, Status: store.StatusExited, ExitCode: 1, StderrTruncated: true, Usage: store.Usage{Calls: 2, ToolCalls: 1, InputTokens: 300, CachedTokens: 50, OutputTokens: 40, ReasoningTokens: 7, CostNanos: 9000}}, 1500*time.Microsecond)` and compares with the map holding `duration_us` 1500, `exit_code` 1, `prompt_run` the id, `status` `exited`, `truncated` true, `calls` 2, `tool_calls` 1, `input_tokens` 300, `output_tokens` 40 and `cost_nanos` 9000, each `int64`, and no `cached_tokens` or `reasoning_tokens`; and `runs.StartedAttrs` of a run with `Prompt`, `Model` and `Trigger` set with the four-key map. A trail test runs `cli.Run` with a `*telemetry.Capture` as `Sink`, a constant `Now`, a `BaseURL` naming its stand-in provider and a temporary `Dir` of its own, makes tool calls with `mcp.Client` over the inherited listener as callers with distinct request ids, posts deliveries to `/events` with an `X-Request-Id` of its own and no `X-User-Id`, stops the run, reads `Capture.Events()`, and opens the catalog under that `Dir` with `db.Open` and `prompts.Migrations()`, and a store over it, to compare each `run.finished` with `runs.FinishedAttrs` of the record.
