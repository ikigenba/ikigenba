# D12-limits

prompts starts its own binary's `agent` role for anyone who runs a prompt, and for every event a prompt is subscribed to, and each such child talks to a model provider and may call tools for as long as the model asks, so prompts bounds that work. It reads the numbers it bounds it with from its environment once, at start. This document is the package `internal/settings`: the twelve values prompts reads at start through `Process.LookupEnv`, `DRAIN_SECONDS`, the space's, and the eleven the manifest's `[env]` declares (`D02-cli`), `PROMPT_SECONDS`, `OUTPUT_MAX_BYTES`, `RUN_MAX_TOOL_CALLS`, `RUN_MEMORY_MAX_BYTES`, `RUNS_MEMORY_MAX_BYTES`, `RUNS_CPU_PERCENT`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE`, `RUN_MAX_QUEUED`, `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT`; their spelling, defaults, the order they are checked in and the refusal of one that is not acceptable. It also states how a serving `cli.Run` applies the settings it read: that they hold for the whole `Run`, that `PROMPT_SECONDS` is timed on `Process.ScriptAfter`, and that `RUN_MAX_TOOL_CALLS` reaches agentkit's tool-call limit. It declares every exported name of `internal/settings` and states what each does.

What the other documents own: `cli.Process`, `cli.Run`, `Process.ScriptAfter`, `Process.LookupEnv` and the keys `Run` may pass it are `D01-layout-and-run-seam`'s; the manifest's `[env]`, whose values are `settings.Defaults`' (in the order below, `DRAIN_SECONDS` left out), is `D02-cli`'s; the start order, the settings refusal's diagnostic and exit code, the cgroup step that writes `RUNS_MEMORY_MAX_BYTES` and `RUNS_CPU_PERCENT` into the group every run shares, the drain and its deadline of `DRAIN_SECONDS` real seconds, and handing the settings to the run core and the pages, are `D03-serve`'s; `runs.Config` and its fields `PromptSeconds`, `OutputMaxBytes`, `MaxToolCalls`, `KeepDays`, `KeepCount`, `RunMemoryMaxBytes`, `RunPidsMax`, `MaxActive`, `MaxQueued` and `ScriptAfter`, the composition of the run spec the child reads (whose `MaxToolCalls` carries the limit), timing a run on `ScriptAfter` and recording it `timed_out`, bounding each stream, the queue's bound and refusals, and pruning, are `D07-runs`'; the spec's fields and how the child builds its conversation with `agentkit.Limits` are `D05-agent`'s; writing `RUN_MEMORY_MAX_BYTES` and `RUN_PIDS_MAX` into each run's own control group is `D06-runner`'s; and the words a page shows for the runs a prompt keeps are `D08-pages`'.

## The settings

prompts reads twelve values at start, in this order, which is also the order they are refused in: `DRAIN_SECONDS`, `PROMPT_SECONDS`, `OUTPUT_MAX_BYTES`, `RUN_MAX_TOOL_CALLS`, `RUN_MEMORY_MAX_BYTES`, `RUNS_MEMORY_MAX_BYTES`, `RUNS_CPU_PERCENT`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE`, `RUN_MAX_QUEUED`, `RUN_KEEP_DAYS`, `RUN_KEEP_COUNT`. Each is spelled as opsctl writes an integer: one or more ASCII digits, no sign, no leading zero, no unit, no white space. An unset or empty one is its default: 5 seconds, 600 seconds, 1048576 bytes, 50 tool calls, 134217728 bytes, 536870912 bytes, 100 percent, 64 processes, 4 runs, 10 runs, 15 days and 10 runs. prompts sets no upper limit: digits beyond what an `int64` holds read as the largest `int64`; a `RUNS_CPU_PERCENT` over 100 lets the runs together use more than one CPU. `0` is refused for every one of them: for `RUN_MAX_TOOL_CALLS` because agentkit reads a zero `MaxToolCalls` as no bound at all, for `RUN_KEEP_COUNT` so that every prompt keeps at least its newest run whatever its age, for `RUN_KEEP_DAYS` so that a run is kept at least one day, which the catalog's `PastKeeping` (`D04-store`) relies on, for `RUN_MAX_ACTIVE` so that some run can always start, and for `RUN_MAX_QUEUED` so that there is always room for one run to wait.

`settings.Read` takes the lookup `Run` hands it (`Process.LookupEnv`) and returns a `settings.Settings`, or, for the first value in that order that is not acceptable, a `*settings.Error` naming it, quoting its value verbatim and giving its unit: `seconds`, `bytes`, `tool calls`, `percentage`, `processes`, `days` or `runs`. Its text is what `Run` writes after `prompts: ` (`D03-serve`): `<NAME> is '<value>', not a positive whole number of <unit>`, and, for the one setting that is a share rather than a count, `RUNS_CPU_PERCENT is '<value>', not a positive whole percentage`. That text is contract, not copy: a person reads it, but it is the conventions' diagnostic, carried from scripts, and a test compares it. `settings.Defaults` is the value `Read` returns when every variable is unset. Every field is a plain `int64`, the unit in the field's name.

## How a serving Run applies them

The values `Run` read at its start hold for the whole of that `Run`. Nothing in the catalog or under `state/runs/` remembers a setting, so a process never applies another process's value, and a value the environment holds later changes nothing until the next start. Every consumer reads its numbers from the plain values `Run` hands on from that one read (`D07-runs`' `Config`, `D03-serve`'s `web.Config`).

`PROMPT_SECONDS` is the wall-clock bound on one run, counted from the moment its process started, so a run that waited in the queue gets its full time once it leaves it. It is timed on `Process.ScriptAfter`, the seam's one timer, which keeps scripts' name: the run core asks it once per started process for `PROMPT_SECONDS` as a `time.Duration`, saturating at the longest duration, and a value on the channel while the run is running kills it `timed_out` (`D07-runs`). Nothing else in a serving `Run` calls `ScriptAfter`; the drain deadline is real time (`D03-serve`). agentkit has no wall clock of its own, so this is the only time bound a run has.

`RUN_MAX_TOOL_CALLS` is the most tool calls one run may dispatch, the files, bash and suite tools counted together. It travels `runs.Config.MaxToolCalls` (`D07-runs`), then the run spec's `MaxToolCalls`, which the child reads on its standard input (`D05-agent`), then `agentkit.Limits.MaxToolCalls`. agentkit's field is an `int`, so a value above `math.MaxInt` is carried as `math.MaxInt`; on the 64-bit hosts the suite runs on that is the largest `int64`, the most `Read` returns, so the cap only ever keeps the value from wrapping. A round trip that asks for more tool calls than are left dispatches none of them, writes a `limit` record to the run's `transcript.jsonl` naming the bound, and ends the turn, so the child exits 2 and the run is recorded `exited` with exit code 2 (`D05-agent`, `D07-runs`). No cost cap exists: agentkit has none, so tool calls and time are the caps, and the cost is visible on every run.

`OUTPUT_MAX_BYTES` bounds each of the child's two streams on its own, the answer on `stdout` and the diagnostic on `stderr` (`D07-runs`); `transcript.jsonl` and `work/` are not bounded by it, and pruning answers their growth. `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT` decide what every prune removes (`D07-runs`).

Six settings bound what runs take of the host, all carried from scripts unchanged except for two defaults. The kernel applies four through the control-group tree prompts arranges under `Process.Cgroup`, `main/` for the app and `runs/<run id>/` for each run: `RUNS_MEMORY_MAX_BYTES` and `RUNS_CPU_PERCENT` are written once, at start, into `runs/`, which every run shares (`D03-serve`), and `RUN_MEMORY_MAX_BYTES` and `RUN_PIDS_MAX` into each run's own group as it starts (`D06-runner`), through the run core's `Config` (`D07-runs`). A run the kernel kills for memory ends `exited` with exit code 137, as any death by a signal prompts did not send (`D06-runner`). The run core applies the other two: `RUN_MAX_ACTIVE` runs run at once and `RUN_MAX_QUEUED` more may wait, all or nothing, and the waiting runs are abandoned at stop (`D07-runs`). A run is mostly waiting on the network, so four may be active where scripts allows two, and the Go child with its shell commands fits in 128M where Python gets 256M. Above them all the manifest's `[resources]` `memory_max` bounds the service unit as a whole (`D02-cli`).

Every limit here bounds a run an event started exactly as it bounds one the `run` tool started: both are made by the same run core with the same `Config` (`D14-delivery`).

## Departures from scripts

- The `limits` package is dropped whole. scripts used it to time each git run on `Process.After` (`OPERATION_SECONDS`), to halt git at the drain deadline, and to carry `ErrTooLarge`, `ErrTimedOut` and `ErrHalted`; prompts runs no git, so `limits.Clock`, `limits.Limits`, `New`, `Settings`, `Operation`, `Halt` and the three sentinels go, with every requirement that stated them. `cli.Process` loses `After` and `Environ` (`D01-layout-and-run-seam`), and `ScriptAfter` is the seam's only timer.
- `TREE_MAX_BYTES`, `OPERATION_SECONDS` and `REPOS_DIR` are not settings: prompts unpacks no tree, runs no git and reads no repository. `SCRIPT_SECONDS` is renamed `PROMPT_SECONDS`. `Settings` loses `TreeMaxBytes`, `OperationSeconds` and `ReposDir`. A value the environment holds for any of the four old names is never read, so it is never refused.
- `RUN_MAX_TOOL_CALLS` is new, with the unit `tool calls`.
- `RUN_MEMORY_MAX_BYTES` defaults to 134217728 rather than 268435456, and `RUN_MAX_ACTIVE` to 4 rather than 2 (decision 10).

## Decisions

- `internal/settings` stays a package of its own so that `D03-serve` reads and refuses the settings before it builds anything, and so that `D02-cli`'s manifest is stated against `settings.Defaults`.
- `RUN_MAX_TOOL_CALLS`' unit word is `tool calls`, so its refusal reads as every other count's: `not a positive whole number of tool calls`.
- The cap at `math.MaxInt` is stated so that the conversion to agentkit's `int` never wraps to a negative bound, which agentkit refuses as an invalid configuration.
- `RUNS_CPU_PERCENT`'s unit is `percentage`, and `Error` words it `not a positive whole percentage`, because a share is not a count; every other unit reads `not a positive whole number of <unit>`.
- The resource settings are `Settings` fields like the rest, read and refused by `Read` in the order above, so a setting that cannot be read is refused before prompts touches any control group.

## Consumer tasks

The start (`D03-serve`): `s, err := settings.Read(p.LookupEnv)`; when `err != nil`, `Run` writes `"prompts: " + err.Error() + "\n"` to `Stderr` and refuses before it looks for its socket (the exit code is `D03-serve`'s). Otherwise `core := runs.New(runs.Config{…, PromptSeconds: s.PromptSeconds, OutputMaxBytes: s.OutputMaxBytes, MaxToolCalls: s.RunMaxToolCalls, KeepDays: s.RunKeepDays, KeepCount: s.RunKeepCount, RunMemoryMaxBytes: s.RunMemoryMaxBytes, RunPidsMax: s.RunPidsMax, MaxActive: s.RunMaxActive, MaxQueued: s.RunMaxQueued, ScriptAfter: p.ScriptAfter, …})` (`D07-runs`), its `Cgroup` the `runs/` group the start prepared with `s.RunsMemoryMaxBytes` and `s.RunsCPUPercent`; `web.Config`'s `KeepDays` and `KeepCount` are `s.RunKeepDays` and `s.RunKeepCount`; the drain deadline is `time.Duration(s.DrainSeconds) * time.Second` of real time, saturating.

The run core (`D07-runs`): composing a run's spec, its `MaxToolCalls` is `cfg.MaxToolCalls`, or `math.MaxInt` when that is larger; once the process starts, `cfg.ScriptAfter(<PromptSeconds as a saturating time.Duration>)`.

A test of the settings calls `settings.Read` with a lookup over a map and compares the result with `settings.Defaults()` or the expected `settings.Settings` with `==`, or uses `errors.As` to get the `*settings.Error` and compares its `Name`, `Value`, `Unit` and `Error()`. A test of a whole process hands `cli.Run` a `Process` whose `LookupEnv` answers `PROMPT_SECONDS` `30`, `OUTPUT_MAX_BYTES` `1024`, `RUN_MAX_TOOL_CALLS` `1` and `RUN_MAX_ACTIVE` `1`, the provider keys, and a `BaseURL` naming an `httptest` server standing in for the provider, and whose `ScriptAfter` records its durations and returns channels the test holds; it creates and runs prompts over appkit's `mcp.Client`, scripting the fake provider's answers and holding a request unanswered to keep a run running, reads the runs, their folders and the catalog, then starts a second `Run` over the same `Dir` with other values.
