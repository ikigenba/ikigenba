# D08-pages

What prompts draws as HTML and the addresses it draws with: the packages `internal/urls` and `internal/pages`; the seven human-authored templates `landing`, `prompt`, `run`, `about`, `tools`, `notfound` and `unavailable` and the three partials `run-status`, `run-duration` and `file-size` that `run.html` defines, the data each receives and how the code formats the values a template cannot (times, durations, sizes, counts and cost); the levels of the banner trail each page sets; the handler that answers `/`, `/about`, `/tools` and every prompt path that is not one of a run's files — the catalog, a prompt's page, a run's page, the about screen and the tools page, the redirects that add a missing trailing `/`, the not-found page, the unavailable page when the catalog cannot be read, and the refusal of any other method; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the names this design behaves through outside its two packages: the root package's `Assets`, and the run seam whose `Banner` the binary sets to the `Banner` method of `page.New(pages.ServiceName, id)`, `id` being the identity of the run `main` reads, a `version.Identity` whose `Release` and `Commit` are empty when the host sets neither. `D04-store` declares `store.Store`, its `List`, `Find`, `Runs` and `FindRun`, the records `store.Prompt`, `store.Subscription`, `store.Run` and `store.Usage`, the method `store.Run.Truncated`, the status, reason and trigger words, `store.ErrNotFound`, `store.Unreachable` and the failing store; `D07-runs` declares `runs.Core` and its `Folder`, `Gone` and `Sizes`, and the names of a run folder's entries, `runs.InputFile`, `runs.StdoutFile`, `runs.StderrFile`, `runs.TranscriptFile` and `runs.WorkDir`; `D09-run-files` declares the run file paths and the handler that answers them, which uses this design's set and its catalog refusal; `D03-serve` declares `web.Handler` and `web.Config`, defines a prompt path, and owns the route table, `identity.Require` around every route, the request's id and its two events, and that nothing reaches standard error while telemetry takes every event. The eleven tools' names and descriptions are `D11-tools`'; the tools page reads them from the server `D03-serve` mounts at `/mcp` through appkit's `mcp.Server.Tools`.

## Addresses

`internal/urls` builds the two addresses prompts writes into a page that are not its own: auth's profile page and auth's sign-out action, which the banner carries. Each reads the services file afresh through appkit's `services.Read` on every call, so a rewrite shows on the next page, and treats a file it cannot read — no path, no file, not a services file — as listing nothing, writing nothing about it. They are the `url` of the file's entry named `auth` followed by `/` and by `/logout`; with no such entry, or an empty `url`, the space is read from the request's `Host`, a trailing port dropped and then one leading `prompts.` label, and the scheme is the request's `X-Forwarded-Proto` when that is exactly `http` or exactly `https`, and `https` for anything else.

Every other address a page carries is a path of prompts' own, relative to the host the browser used: `/`, `/about`, `/tools`, `/<name>/`, `/<name>/runs/<run id>/` and the run's files beneath it. prompts never sends a visitor to sign in: nginx does that before a request reaches prompts (`guests = false`), and a request that arrives with no `X-User-Id` is appkit's `identity.Require` 500 on every route, so `urls` has no sign-in address.

## The template set and its data

The seven pages are the files of `assets/`, embedded by the root package and returned by `Assets()`; `run.html` also defines three partials, `run-status`, `run-duration` and `file-size`, which `landing`, `prompt` and `run` call. `pages.Load` builds **prompts' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `footer` and `preload`; the code adds no template function and writes no markup of its own. `Set.Write` is the one way any handler sends a page: it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set first, and sets nothing else. A `HEAD` gets the status and headers and no body.

Each template's data is a named struct whose fields are exactly what its opening comment names. The data carries values, never words: a run's status, exit code and failure reason as the store records them, a duration as whole minutes and seconds, a size as a scaled number and a unit, counts and a cost as the digits shown, and the truncation of each stream as a flag. Every word a page shows — the status word and its kind, the notice, a failure's title and sentence, the units, the nouns of the usage line — is chosen by the template from those values. The code formats what a template cannot without a function the set does not have:

- `LandingData`: the banner and one `PromptRow` per prompt of the caller's, by name; a row carries the prompt's name, its page's path, its model and its last run as a `RunRow`, nil when it never ran.
- `PromptData`: the banner, a `PromptCard` (id, name, model, its tool groups each as a `ToolGroup` with flags for the first and the last, the text, the system prompt, the output schema as stored, created, how many runs are kept and the retention rule), one `RunRow` per run, newest first (id, page path, the store's status and exit code, the model the run used, its cost, start and a `Duration`, nil when the run has none), and the event patterns the prompt is subscribed to, each exactly as subscribed, in the catalog's order, with no time, since the page shows none.
- `RunData`: the banner, a `PromptLink` (name and path), a `RunCard` (everything the run's summary shows: status and exit code, whether it has not ended yet, the model, its times, its `Duration`, the trigger and, for a run an event started, that event's id, the user and request ids, its `Usage` once it has ended, the sizes of its two streams and its transcript as `Size`s, whether output was cut overall and per stream, its `Failure` and whether its folder is gone), a `FileText` for each of `input.json`, `stdout` and `stderr` that exists, a `FileLink` for `transcript.jsonl` when it exists — the page links the transcript and never shows its contents — and one `FileRow` per regular file under `work/`, each with its `Size`.
- `AboutData`: the banner and `pages.Description`, the manifest's one-line description.
- `ToolsData`: the banner and one `Tool` per MCP tool, its name and the first line of its description, in the order the server holds them, read from the server's `Tools` as the page is drawn.
- `NoticeData`: only a banner, from which the not-found and unavailable pages draw appkit's footer with the banner's `Release` and `Commit`.

The three partials take a part of that data: `run-status` a `RunRow` or a `RunCard`, of which it reads the status and exit code, `run-duration` a `Duration` and `file-size` a `Size`. They are named so a test can execute one alone, and are proved by use: each page that calls one is compared whole.

No data type has a field for a prompt's owner, the owner's email, a provider key or anything of another user's, so no page can show them; a run's reason is carried only in its `Failure`. What the banner holds — the mark and its home link, the service's name and icon, the tools link, the profile link and the sign-out form — is appkit's output; this design states only which data a page is drawn with, and one binary-level requirement proves that the binary's banner source is appkit's kit reading the services file afresh.

The `unavailable` page is what a page path answers when the catalog cannot be read: status 503, drawn with the banner the banner source gives for the empty `page.User`, as the not-found page is, so it carries nothing of the error and is the same bytes for every caller. A run's files are not pages: `D09-run-files` answers them with the plain-text catalog refusal this design defines, and the tools answer with `store.Unreachable` (`D11-tools`).

## The banner trail

appkit's banner draws where a page sits in prompts as a trail of levels below the landing page, each a `page.Level`, a name and a URL. A page sets its levels on the banner's `Trail` after its banner source returns, replacing whatever the source returned; in the binary the source is appkit's kit, which also fills the banner's home link and whether the service has tools. The landing page has no level. The about screen has one, `about` at `/about`, and the tools page one, `tools` at `/tools`, each named by its path segment. A prompt's page has one, the prompt's name at `/<name>/`; a run's page two, the prompt's name at `/<name>/` and then the run id at `/<name>/runs/<run id>/`. The not-found and unavailable pages draw no banner, only its footer, so they keep the banner for the empty user with no level set; a run's files are bytes, not pages, and carry none (`D09-run-files`). No page draws levels of its own under `main`: the trail is the banner's. A test proves the levels by executing the page's template with the data this design states, the trail included, against a banner source that returns a fixed banner whose `Trail` is not empty, and comparing the bodies byte for byte, so the prompt's name and the run id it supplied appear in the body as the trail's levels.

## The pages handler

`pages.Handler` answers `/`, `/about`, `/tools`, and every **prompt path** — every path but `/`, `/about`, `/tools`, `/mcp`, `/events`, `/declarations` and those beginning `/_appkit/`, as `D03-serve` defines it — that is not a **run file path** (`D09-run-files`). `D03-serve` routes those paths to it inside `identity.Require`, so it never sees a request without a caller, and a test wraps it the same way; a request with no `X-User-Id` is appkit's 500 and draws nothing, which `D03-serve` states for every route (R-Y4TG-OMI3), this design restating none of it. It reads the path as **pieces**: the escaped path less its leading `/`, split at every `/`, each piece percent-decoded. A piece is compared byte for byte, never tidied: `.`, `..`, an empty piece and a piece that was percent-encoded are names like any other and match nothing that is not spelled so.

Each request is answered in this order. The method first: anything but `GET` and `HEAD` is refused 405 with `Allow: GET, HEAD` and an empty body, before the catalog is read, so the answer is the same for a prompt, another user's prompt and no prompt. Then:

- `/about` draws the about screen, reading no catalog, so it is served with the catalog unreachable. Its version is the banner's `Release` and `Commit`, whatever those hold, each empty included.
- `/tools` draws the tools page: the tools registered on `cfg.MCP`, read with its `Tools` as the page is drawn, each with its name and the first line of its description, in the order the server holds them. It reads no catalog, so it too is served with the catalog unreachable.
- `/` reads the caller's prompts with `store.List`, once, reads no run folder, and draws the catalog.
- A prompt path looks its first piece up among the caller's own prompts with `store.Find`. A name that is none of theirs — no prompt, another user's, a different letter case, `about`, `tools`, `mcp`, `events`, `declarations` — is the not-found page, whatever follows it, so `/events/` and `/declarations/cron.tick.fired` are answered with it and never reach the events app's handlers. Under one of theirs: the path that is the name alone is redirected 301 to `/<name>/`, the query kept; `/<name>/` draws the prompt page; `/<name>/runs/<run id>` and `/<name>/runs/<run id>/` look the run up with `store.FindRun`, and a run of this prompt is redirected or drawn the same way, while any other run id — no run, another prompt's, another user's, a malformed id, a `run_` id of scripts', a different letter case — is the not-found page; every other path under the prompt, `/<name>/runs/` included, is the not-found page.
- Any catalog read that answers neither a record nor `store.ErrNotFound` is answered with the unavailable page, status 503.

The contract states that answer for a failing store and for a request whose context is already done as it arrives: turning on `SetFailing` for the store's handle and cancelling a request's context are the ways the test rules allow to fail the catalog, and each fails the first read, `List` or `Find`. So no permitted test can fail `Runs` or `FindRun` alone, and a failure of either alone, answered the same way, is unstated as contract until the test rules decide whether a seam may fail one read. Likewise, that `/about`, `/tools` and a 405 read no catalog and that the catalog page reads it once and reads no run folder are contract only through their answers.

The not-found page is the `notfound` template with status 404, drawn with the banner the banner source gives for the empty `page.User`, so the answer to a path naming another user's prompt or run is byte for byte the answer to one naming nothing. A `HEAD` is answered with the status and headers its `GET` has and no body, redirects and refusals included. No answer sets a cookie. A page reads the catalog and, for the run page, the run's folder through `runs.Core`; it starts no process. Drawing a page writes nothing anywhere: nothing is created under the runs directory, not even a folder for a prompt that has never run.

## How the data is formatted

The data carries values and the templates choose the words. A run's `Status` and `ExitCode` are the record's, the exit code 0 unless the run exited (`D04-store`); `run-status` turns them into the status word and its kind. A time in a table is formatted with `pages.MinuteLayout`, the prompt's created time with `pages.CardLayout` and a run page's times with `pages.SecondLayout`, each in UTC and each carried as well in its RFC 3339 form; the layouts are copy constants of `pages`; how the source groups their declarations is its own business, so long as gate 5's lint passes, and no requirement. A duration is the record's finished less its started, in whole seconds, carried as whole minutes and the seconds left over, and is nil while the run is queued or running and when it failed to start. A size is the byte count scaled by the code: bytes under 1000, otherwise thousands or millions truncated to one decimal, carried as that number as a string and the unit `byte`, `kilobyte` or `megabyte`.

Usage is new beside scripts. The store keeps a run's usage as integers summed from its transcript, and its cost as `cost_nanos`, agentkit's nano-USD, never converted in a record (`D04-store`); the pages show dollars. A **cost text** is the nano-dollars rounded to the nearest micro-dollar, a half rounding up, written as whole dollars, `.` and six digits, so 23714000 nano-dollars read `0.023714`. A **count text** is the decimal digits of a count with a comma before each group of three counted from the right, so 18204 reads `18,204`. A run that has not ended has no usage: its `Usage` is nil and its row's `Cost` empty, since nothing is summed until the run ends. A run that ended carries its `Usage`, zeros included — a run that failed to start, or one with no transcript, shows zeros and a cost of `0.000000`.

The prompt card carries the prompt's fields as stored: the text, the system prompt (empty when none) and the output schema's bytes exactly as stored, not re-indented (empty when none). Its tool groups are carried in the order stored, each with `First` and `Last` set on the first and the last, so the template can join them without a function.

The run data carries what the run page needs for each state of a run. A run that has not ended, queued or running, has `Running` true, and the template words its notice from `Status`; it carries what its files hold so far and its stream sizes measured from them (`runs.Core.Sizes`); a queued run has no finish, no duration and no usage, and since its child has not started its folder holds no stream file and no transcript. A run abandoned in the queue (`store.ReasonQueueAbandoned`) or whose process could not be launched (`store.ReasonStartFailed`) carries a `Failure` holding the reason as recorded; the template chooses the failure's title and sentence from it. A run whose output was cut carries `StdoutTruncated` and `StderrTruncated` from the record, and `Truncated`, the record's `Truncated()`, true when either is; its stream sizes are the bytes kept. A run whose folder is gone (`runs.Core.Gone`) has `FilesGone` true, no file data, and stream and transcript sizes of zero, as the template's data says of a file that does not exist, though its record still holds the bytes its streams kept. Otherwise `Input`, `Stdout` and `Stderr` are present only for a file that exists, each with the file whole and its address (`D09-run-files`); `Transcript` is present only when `transcript.jsonl` exists, with its size and address, and `TranscriptSize` is that size or zero; and `Files` lists every regular file under `work/`, at any depth, hidden ones included and symbolic links left out, by path, each with its size and address. The card's `Trigger` and `Event` say who started the run: an event, by its id, or the `run` tool. Its `Model` is the run's, the prompt's model when the run was asked for, which may differ from the prompt's model now.

## How a page is proved

A test proves a page by executing the named template of its own copy of prompts' template set with the data this design states and comparing the body byte for byte, or by checking that a value it supplied appears in the body. No requirement names a heading, a label, a sentence, a class, an id or an attribute, and none defines how markup is read: the words and hooks are the templates', documented in each template's opening comment. `html/template`'s contextual autoescaping is what keeps a caller's, a prompt's or a run's bytes from becoming markup, and the byte-for-byte requirements cover every input. One requirement executes each template over every state this design names, so a template that cannot be executed for a named state fails a test; a template that cannot show a state this design names is an issue for a human, never a change to the asset.

## The head

Each template carries its own head, which loads appkit's stylesheet, favicon and button-feedback script from `/_appkit/` and invokes appkit's `preload` template for the font, whose URL carries a hash of its bytes that prompts never writes. What the head holds is the template's, so no requirement states it; the shared files it loads are served as the next section states.

## The shared files

The stylesheet, its three fonts, one of which every page preloads, the button-feedback script, the favicon and the two licences are the platform's shared files: appkit's `page` package embeds them and `page.Static()` serves them under `page.StaticPrefix`, `/_appkit/`. prompts holds no copy and reads nothing from disk for them; `D03-serve` hands every request whose path begins with `page.StaticPrefix` to that handler unchanged, inside `identity.Require` like every route. The requirements here state appkit's answer as prompts' own behaviour at `web.Handler`, so prompts' tests fail if a different appkit release stopped giving it. Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`.

Five shared files have fixed names: `theme.css`, `feedback.js`, `favicon.svg`, `OFL.txt` and `TABLER-LICENSE.txt`. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes; the plain names a font file carries in appkit are not served. prompts never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns and the paths the served stylesheet names, and a test learns them the same way. Every 200 and 304 for a shared file carries one strong `ETag`; a font path's carries `Cache-Control: public, max-age=31536000, immutable`, every other shared file's `Cache-Control: no-cache`.

## Decisions

- Scripts' pages, with `script` become `prompt` (decision 15), signed-in only. The catalog row and the prompt's run rows carry the model and the run's cost; the run card carries the model, the usage and cost, the transcript's size and a link to `transcript.jsonl`; the run's files are those under `work/`. A rendered transcript is deferred: the page links the file and never shows its contents.
- The run page carries truncation per stream, `StdoutTruncated` and `StderrTruncated`, beside `Truncated`, the OR of the two as `store.Run.Truncated` defines it. A departure from scripts, which had one flag, following the store's per-stream record (`D04-store`).
- Costs are shown in US dollars to six decimals, rounded to the nearest micro-dollar with a half rounding up; the record keeps nano-dollars. Counts are grouped by commas. Both are formatted by the code, as times are, since the set has no function to do it.
- A run that has not ended carries no usage and an empty cost; once ended, a run carries its usage whatever its status, zeros when nothing was spent or no transcript exists.
- The output schema is shown as the stored bytes, not re-indented.
- `ToolGroup` carries `First` and `Last` flags so the template joins the groups without a function.
- `FileLink` is a size and an address with no text: the transcript is linked, not shown.
- `Failure` carries only the reason: prompts has no repository, ref or git limit to name.
- `pages.Config` carries `KeepDays` and `KeepCount` in place of scripts' limits and source.
- The catalog unreachable on a page path is the `unavailable` page with status 503, drawn with the banner for the empty `page.User`, as the not-found page is. A run's files keep the plain-text catalog refusal, defined here for `D09-run-files`, and the tools keep their refusal.
- There is no guest branch and no `urls.SignIn`; a request without `X-User-Id` is appkit's 500 and draws no page.
- The scheme is exactly `http` or exactly `https`, case-sensitively; the auth space drops one leading `prompts.`.
- `PromptData.Subscriptions` is a slice of patterns, not of `store.Subscription`: the page shows no subscription's time.
- One `RunRow` type serves both a prompt's runs and the catalog's last run, whose template reads only its status, exit code, cost and start.
- Sizes are truncated, not rounded, to one decimal.
- A piece is percent-decoded before it is compared; nothing is tidied.
- The not-found page is drawn with the banner for the empty `page.User`, so it is the same bytes for every caller.
- The tools page lists the tools of the very `mcp.Server` `D03-serve` mounts at `/mcp`, read through appkit's `Tools`, rather than a list of its own, so the page and `tools/list` cannot drift; `pages.Config` carries that server as `MCP`. Each tool shows the first line of its description, as the template's data names; a description of one line shows whole.
- Each page replaces the banner's `Trail` whatever its source returned, the landing page with a trail of no level, so no page's levels rest on what the source leaves there.
- The not-found and unavailable pages keep the banner for the empty `page.User` with no level: their templates draw only its footer.
- The landing page carries no list of tools, the about screen no link home, and the prompt and run pages no breadcrumb of their own: the banner's home link, tools link and trail carry them. `RunData` keeps its `PromptLink`, which the run's summary still links.

## Consumer tasks

`web.Handler` calls `pages.Load()` once, when it is built, and builds `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, Runs: cfg.Runs, MCP: cfg.MCP, KeepDays: cfg.KeepDays, KeepCount: cfg.KeepCount})`, the two numbers being the settings `D12-limits` reads at start; it serves `/`, `/about`, `/tools` and every prompt path that is not a run file path with it, and every path beginning with `page.StaticPrefix` with `page.Static()`, each inside `identity.Require`. It builds `web.Files(web.FilesConfig{Banner: cfg.Banner, Pages: set, Store: cfg.Store, Runs: cfg.Runs})` with the same set and serves every run file path with it (`D09-run-files`). `cli.Manifest`'s description and the MCP server's name use `pages.Description` and `pages.ServiceName`.

A page request: `GET /summarize/runs/prr_d4a7e2c9f1b8630a/` reaches `pages.Handler` with the caller on its context; the method is `GET`; the pieces are `summarize`, `runs`, `prr_d4a7e2c9f1b8630a` and the empty string; `cfg.Store.Find(ctx, u.UserID, "summarize")` gives the prompt `x`, `cfg.Store.FindRun(ctx, u.UserID, "prr_d4a7e2c9f1b8630a")` the run `r`, whose `Prompt` is `x.ID`; the run is `exited` 0 with `StderrTruncated` set, so the card carries `Usage: &pages.Usage{Calls: "3", ToolCalls: "2", InputTokens: "18,204", ..., Cost: "0.023714"}`, `StderrTruncated: true` and `Truncated: true`; `cfg.Runs.Gone(r)` is false, so `cfg.Runs.Folder(r)` is read for `input.json`, `stdout`, `stderr`, `transcript.jsonl` (a `pages.FileLink`) and `work/`; `cfg.Runs.Sizes(r)` gives the stream sizes; `b := cfg.Banner(user)` is called with the banner user and `b.Trail` set to `[]page.Level{{Name: "summarize", URL: "/summarize/"}, {Name: "prr_d4a7e2c9f1b8630a", URL: "/summarize/runs/prr_d4a7e2c9f1b8630a/"}}`; and `cfg.Pages.Write(w, r, 200, "run", pages.RunData{Banner: b, ...})` sends the page. A tools request: `GET /tools` sets `b.Trail` to `[]page.Level{{Name: "tools", URL: "/tools"}}`, turns each `t` of `cfg.MCP.Tools()` into `pages.Tool{Name: t.Name, Description: d}`, `d` being `t.Description` up to its first line feed, and sends `cfg.Pages.Write(w, r, 200, "tools", pages.ToolsData{Banner: b, Tools: ts})`. The prompt page is drawn with `pages.PromptData{Banner: b, Prompt: pages.PromptCard{..., Tools: []pages.ToolGroup{{Name: "files", First: true}, {Name: "suite", Last: true}}, ...}, Runs: rows, Subscriptions: names}`.

A test of the handler builds a `store.Store` with `store.New` over a handle `db.Open` returned for a file in its temporary directory with `prompts.Migrations()`, creates prompts, subscribes them with `Subscribe`, and adds runs with `AddRun`, `StartRun` and `FinishRun`, event runs, truncated runs and runs with usage among them, makes run folders under a temporary `Runs` the `runs.Core` it builds names (or removes one), writes a services file in its temporary directory, builds `identity.Require(pages.Handler(pages.Config{...}))` with a `Banner` closure that counts its calls and returns a fixed `page.Banner` whose `Trail` is not empty and an `MCP` server from `mcp.NewServer` on which `tools.Register` put the eleven tools, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of prompts' template set from `page.Templates()` and `prompts.Assets()`, executes `landing`, `prompt`, `run`, `about` or `tools` with the data it expects, its banner the fixed one with `Trail` replaced by the page's trail, built from its own store calls, the rules above and `pages`' three layouts, and compares bodies byte for byte; it may execute a partial, `run-status` with a row it built, and find that text in a body. It calls `SetFailing(true)` on that handle, or serves a request whose context it cancelled first, to make the catalog unreachable, and compares the answer with `unavailable` executed with the `NoticeData` for the empty user's banner. A test of `urls` calls each function with a request and a services file of its own. A test of the shared files builds `web.Handler` as `D03-serve` states and requests `/_appkit/...` with `X-User-Id` set. The one exec test of the binary in `cmd/prompts` rewrites the services file between two `GET /` requests.

## REQUIREMENTS

- R-AU5G-JA8M: The package `internal/urls`, imported from the path `github.com/ikigenba/ikigenba/prompts/internal/urls` with the package name `urls`, MUST export `func Scheme(r *http.Request) string`, where `http` is the standard library's `net/http`.
- R-AVDC-X1ZB: The `internal/urls` package MUST export `func AuthProfile(r *http.Request, servicesPath string) string`.
- R-AWL9-ATQ0: The `internal/urls` package MUST export `func AuthLogout(r *http.Request, servicesPath string) string`.
- R-AXT5-OLGP: `urls.Scheme(r)` MUST return `http` when the value `r.Header.Get("X-Forwarded-Proto")` returns is exactly `http`, and `https` for every other value, so that `https`, `HTTPS`, `HTTP`, `Http`, `https, http`, `ftp`, the empty string and an absent header all give `https`.
