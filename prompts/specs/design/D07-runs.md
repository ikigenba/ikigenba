# D07-runs

The run core: `internal/runs`, the one place a run is made, started, bounded, ended, recorded, recovered and pruned, and the piece the event bus calls. A `*runs.Core` takes a prompt and a request, makes the run's folder, composes the run spec, starts the binary's own `agent` role through `internal/runner` in a control group of its own with the spec on its standard input, or queues the run when every slot is taken, and answers at once, without waiting for the child or a slot; from then on it enforces `PROMPT_SECONDS`, keeps the head of each output stream, records how the run ended with the usage its transcript reports, and prunes. It also ends runs on request (`cancel`), with their prompt (`delete`), at the drain deadline, and settles at start the runs a dead prompts left `running`. This document declares every exported name of `internal/runs` but the three `D10-trail` declares (`StartedAttrs`, `FinishedAttrs`, `Caller`) and `Deliver`, which `D14-delivery` declares, and states what each does.

`D01-layout-and-run-seam` declares `cli.Process`, whose `Now`, `ScriptAfter`, `Rand`, `Dir` and `BaseURL` reach the core through `cli.Run`, places the runs under `state/runs/`, and declares the run id (`store.NewRunID`); `D04-store` declares the prompt and run records, the `Usage` and `Ending` shapes, the status, reason and trigger words, and the transitions `AddRun`, `StartRun` and `FinishRun`; `D05-agent` declares the child: `agent.Spec`, the shape of the bytes this core writes to the child's standard input, `agent.Offering`, the exit codes 0 to 4 and what each means, and the transcript the child writes with agentkit's `NewLog`; `D06-runner` declares `runner.Start`, `Spec` (with its `Stdin`) and `Process` (`Wait`, `Kill`), and fixes the command, the binary's own file with the one argument `agent`; `D10-trail` declares the run's events and the three functions that form them; `D12-limits` reads and refuses the settings, so this document receives `PROMPT_SECONDS`, `OUTPUT_MAX_BYTES`, `RUN_MAX_TOOL_CALLS`, `RUN_KEEP_DAYS`, `RUN_KEEP_COUNT`, `RUN_MEMORY_MAX_BYTES`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE` and `RUN_MAX_QUEUED` as plain values. `D03-serve` builds the core, handing it the `runs/` control group its start prepared, or the reason it could not, and the five provider keys it read once at start, and calls `Recover`, `Prune` and `Drain`, and mounts `Deliver` as the event bus's handler; `D11-tools` calls `Run`, `Cancel` and `Delete`; `D14-delivery`'s `Deliver` makes, for each prompt a delivered event concerns, a run as `Run` makes one but never refused for a full queue (R-J1IB-PWWV); `D08-pages`, `D09-run-files` and `D11-tools` locate a run's files and learn that they are gone through `Folder`, `Gone` and `Sizes`.

## The run folder

Every run gets a folder of its own, `<Runs>/<prompt id>/<run id>/`, `Runs` being `state/runs` under the process's directory in a running prompts. The folder is the product, not a cache: nothing rebuilds it. A run that started holds five entries: `input.json`, the request's input byte for byte, the `input` argument or, for an event run, the event (`D14-delivery`), or `{}` without one; `work/`, empty at start, the `files` tools' root and the `bash` tool's directory; `stdout` and `stderr`, the head of each stream; and `transcript.jsonl`, agentkit's log of the run, which the child creates and writes as the run goes (`D05-agent`). The run's metadata is in the catalog; the folder holds no file of the core's own beyond `input.json`, `work/`, `stdout` and `stderr`, and the core never bounds or rewrites `transcript.jsonl`.

A run that could not start holds `input.json` and `work/` and no stream file, since it never opened a stream; a queued run holds the same until its process starts. Prompts has no git and no tree, so scripts' read-only `tree/`, its write-permission rules, and its failures of resolve and unpack (`repository_missing`, `commit_missing`, `too_large`, `git_failed`) are gone: a `failed` run is only ever `start_failed` or `queue_abandoned`.

`Folder`, `Gone` and `Sizes` are how the pages, the run files and the tools find a run's files without knowing the layout: `Folder` is the directory, the entry names are exported constants (`InputFile`, `StdoutFile`, `StderrFile`, `TranscriptFile`, `WorkDir`), `Gone` says the folder is no longer there (a fact about the run, shown as such, never an error), and `Sizes` is the bytes kept of each stream, the record's for an ended run and the files' for a running one, whose record holds zero until it ends.

## Starting a run

`Run` refuses at once, in this order: with `ErrDraining` once `Drain` has been called; with `ErrNoCgroup`, its text `runs.NoRuns` filled with the reason, while `Config.Unavailable` holds a reason; for a run an event asks for, as below; and with `ErrQueueFull` while `MaxQueued` runs are queued, a refusal the runs a delivery makes are spared, since the delivery counts its runs against the queue at once (`D14-delivery`, R-J1IB-PWWV). Otherwise it reads `Now` once, the run's `started` and the start of its duration, draws the run's id from `Rand`, makes the folder, writes `input.json` and makes `work/`. If fewer than `MaxActive` runs hold a slot and none is queued, it makes the two stream files, composes the run spec and starts the process; when the spec cannot be composed or the process cannot be launched, it removes the two stream files again. Only then does it record the run, `running`, emit `run.started`, and answer. Otherwise it records the run `queued`, emits nothing, and answers. A process that cannot be launched makes a run all the same: it is recorded `failed` with `start_failed`, its prune runs, its one `run.finished` is emitted, and `Run` answers it with a nil error. Two failures make no run at all: a folder, `input.json` or `work/` that cannot be made, and a catalog that will not take the record. Either way `Run` returns an error that matches none of the package sentinels, the process it may have started is killed and the folder removed, and the caller answers `store.Unreachable`.

A call is cut off, rather than failed, when its context ends or the drain deadline passes before it has recorded its run: it records nothing, removes the folder it had begun, starts nothing and emits nothing, and returns the context's cause, or an error matching `ErrCutOff` at the drain deadline, which no refusal matches. With no git, the only slow steps before the record are drawing the id from `Rand` and the catalog, and a test holds a call in progress with a `Rand` that blocks until it lets it go. Whenever `Run` returns an error, nothing of the call remains. Once the run is recorded, the caller's context no longer matters.

The process is the runner's fixed command, the binary's own `agent` role (`D06-runner`), with the run folder as its working directory (scripts used `tree/`), in a session and control group of its own, with exactly the thirteen variables decision 11 fixes, scripts' fourteen with `IKIGENBA_SHA` gone and the script's names replaced: `PATH`, prompts' own verbatim; `HOME` and `IKIGENBA_RUN_DIR`, the folder; `LANG`, `C.UTF-8`; `IKIGENBA_RUN_ID`; `IKIGENBA_PROMPT`, the prompt's id; `IKIGENBA_WORK_DIR` and `IKIGENBA_INPUT`, the paths of `work/` and `input.json`; `IKIGENBA_USER_ID` and `IKIGENBA_REQUEST_ID`, the run's user and request id; `IKIGENBA_EVENT_ID` and `IKIGENBA_EVENT_DEPTH`, the event's id and depth, empty and `0` for a run no event made; and `IKIGENBA_SERVICES`, prompts' services path verbatim, empty when prompts has none. That is what every `bash` command the model runs sees, and no provider key is among them.

The run spec is the rest of what the child needs, handed over on its standard input and nowhere else: exactly `json.Marshal` of an `agent.Spec` (`D05-agent` declares its shape and how the child reads it). The core fills it from the prompt as it was when `Run` was called, the request, and three values of its own: the key, `Config.Keys` at the host of the prompt model's offering (`agent.Offering`), empty when the model is no longer in agentkit's catalog or no key was read for that host, so that the child, not the core, answers it (exit 4 for an unknown model, agentkit's `auth` failure, exit 1, for an empty key); `MaxToolCalls`, `RUN_MAX_TOOL_CALLS` capped at `math.MaxInt`; and `BaseURL`, empty except under test, where it names the `httptest` server standing in for the provider. The key is therefore on no disk, in no environment, and in no event (decision 11): it lives in the pipe and in the child's memory. A queued run's spec is composed when its process starts, from the prompt and request the queue holds.

Runs are concurrent, across prompts and within one, up to `MaxActive` at once. A run **holds a slot** from the moment its process starts until its `run.finished` is emitted. A run beyond them waits in one queue, shared by every prompt and every user and by the runs events make, first in, first out. When a slot is released, after the ending's `run.finished`, the run queued longest starts: its stream files are made, its spec composed, its process started, its record moved to `running` with `Store.StartRun`, and its `run.started` emitted under its own caller. Its `started` stays the time it was asked for, so its duration counts the wait, while `PROMPT_SECONDS` counts from its process's start. A queued run whose process cannot be launched ends `failed` with `start_failed` and the next takes the slot. `Cancel` takes a queued run out of the queue and records it `killed`; `Delete` does so for its prompt's queued runs before it kills their running ones. The queue lives in the core's memory; the catalog keeps only each run's status.

Every process the core starts runs in a control group of its own, `<Config.Cgroup>/<run id>`, bounded by `RunMemoryMaxBytes` and `RunPidsMax` (`D06-runner`). An empty `Cgroup` with an empty `Unavailable` gives a run no control group, which only a test does.

A request with a `Cause` makes an **event run**: its trigger is `event` and its record keeps the event's id. One prompt gets at most one run from one event: `Run` asks `Store.Delivered` before it makes anything, and a call made while another call for the same prompt and event is still in progress is refused at once with `ErrStarting`, so one core never starts two processes for one event; `AddRun`'s `store.ErrDelivered` remains the guard for a race the core cannot see.

## Bounds, endings and usage

`PROMPT_SECONDS` is counted from the moment the process started, on the timer `ScriptAfter` returns, one per started process. `OUTPUT_MAX_BYTES` bounds each stream on its own: the first `OUTPUT_MAX_BYTES` bytes of a stream are kept in its file, the rest is read and dropped, the child is neither killed nor held up, and each stream's own truncation is recorded (`StdoutTruncated`, `StderrTruncated`), a departure from scripts' one flag that `D04-store` records; the trail's and the tools' `truncated` is `store.Run.Truncated()`, the two ORed. Nothing bounds `work/` or `transcript.jsonl`; pruning answers their growth.

A running run ends exactly once, and its status says who ended it: `exited`, with `runner.Process.Wait`'s code, when the child ended on its own, its code one of the five `D05-agent` gives meaning to (0 answered, 1 provider or model failed, 2 a limit ended the turn, 3 no valid output, 4 the spec or tools could not be built) or a signal's 128 plus its number; `timed_out` when the timer fired first; `killed` when `Cancel`, `Delete` or the drain deadline killed it first. `Kill` answering false means the child had already ended, so the ending is the run's own. The ending is recorded with `FinishRun` once no process of the child's session is left (`D06-runner`: the child is a session leader, and `Wait` and `Kill` take the whole session), `finished` and the end of the duration being one reading of `Now` taken then, with the usage the transcript reports; the prune every ending triggers runs next; and the run's `run.finished` is emitted last.

**Usage is read from the transcript** (decision 8). Once no process of the child's session is left, the core reads `transcript.jsonl` and sums it: `calls` is the number of `usage` records, one per round trip; `tool_calls` the number of `tool_result` records, the calls that were dispatched and returned (agentkit writes a `tool_use` for a call before its tool-call limit refuses it, so counting `tool_use` would report more than `RUN_MAX_TOOL_CALLS`); the four token counts the field-wise sums of the `usage` records' `Usage`; and `cost_nanos` the sum of their `Cost`, agentkit's nano-USD integer, never converted or rounded. Summing the records, not the closing `summary`, means a run killed or timed out mid-turn still reports what it spent; a line that does not decode (the partial last line of a killed child) is skipped, and so is a `usage` record with a missing or negative member; every sum stops at `math.MaxInt64`; a run with no transcript reports zeros. The file is read only when it is a regular file, opened without following a link and without blocking, so a FIFO or a link to `/dev/zero` the model left there reports zeros; lines of any length are read, and a line past 16 MiB is skipped without being held whole (CHOICE). The model's `bash` can write the transcript (it is in `HOME`), so the summing is total: whatever the file holds, the usage it gives is one the catalog accepts, and an ending is never refused for it. agentkit's cache-write token counts are not kept. A `failed` run never ran the child and keeps zeros (`D04-store`).

## Stopping, recovering and pruning

`Drain` is the stop: from its call `Run` refuses new runs, while the calls already accepted and the runs already running go on. At the call every queued run is finished `failed` with `queue_abandoned`, at once, its `run.finished` emitted, and no slot released from then on starts anything; a call in progress whose folder is made while every slot is taken is recorded `failed` with `queue_abandoned` the same way, and answered so. It returns as soon as no run is running and no `Run` call is in progress. When its context ends first, at the drain deadline, it kills every run still running and records each `killed`, emits each `run.finished`, and makes every `Run` call still in progress a cut-off call; it returns once those calls have returned and no process it started is alive. With no git there is no `limits.Halt` for `D03-serve` to call beside it. So every killed run's `run.finished` is emitted before the writer's shutdown, which `D03-serve` calls after `Drain` returns.

`Recover` runs at start, before readiness: every run still recorded `running` belonged to a prompts that died, so each is recorded `killed`, finished now, with the sizes its stream files hold and the usage its transcript holds, and its `run.finished` emitted; every run still recorded `queued` is recorded `failed` with `queue_abandoned` and never started. `Prune` follows it, and runs again after every ending: it removes every run `store.PastKeeping` names for `Now` and the two keeping settings, the folder first and then the record. It never touches a running or queued run and records no event. There is no timer.

## Decisions

- Settings arrive as plain `int64` values in `Config`; `D12-limits` parses, defaults and refuses them. `PromptSeconds` seconds past `math.MaxInt64` nanoseconds is `time.Duration(math.MaxInt64)`, as scripts caps `SCRIPT_SECONDS`. `MaxToolCalls` past `math.MaxInt` is `math.MaxInt` in the spec, whose field is an `int`.
- The provider key travels only in the spec on standard input (decision 11). The core holds the five keys in memory, picks one per run by the model's offering host, and writes it to the runner's `Stdin` and nowhere else; the environment it composes has no key, and no file it writes of its own and no event it emits holds one. Its copies of the child's two streams hold what the child wrote, so the guarantee for the whole folder is conditioned as `D05-agent`'s is: it holds while no response of the provider or of the gateway holds a substring of the key of eight or more bytes (R-MQKN-6C2I, as `D05-agent`'s R-MPCQ-SKBT), for every host and whether a round trip is answered or fails in transport. Protecting prompts' own process, which holds the five keys, from a run's processes reading its `/proc/<pid>/environ` or memory is `D03-serve`'s, which makes the serve process non-dumpable at start, as `D05-agent` makes the child; the core's guarantee keeps its condition that no process of the run read another's, which those two make hold for the serve process and the child, and which a test of the core alone, whose process is not made non-dumpable, cannot assume.
- A missing key, or a model that has left agentkit's catalog since the prompt was made, is not a refusal of the core's: the run is started with an empty key and the child's exit code says what happened (sheet CHOICE). The core never parses the child's standard error.
- The run folder is the child's working directory, so `HOME`, the working directory and `IKIGENBA_RUN_DIR` agree; `work/` is where the tools write. That departs from decision 1, which has the child run "the agentkit loop in the run folder": the core starts the child there, but the working directory is intended and not contract. No test can observe it: the child is non-dumpable (`D05-agent`), so no test the rules allow can read its `/proc/<pid>/cwd`, and toolkit's `Bash` sets each command's `cmd.Dir` to the tool root (its `bash.go` at the pinned tag), so a model's `pwd` shows `IKIGENBA_WORK_DIR`, never the child's own directory. Nothing the child or its tools do depends on it, since the transcript is written at `IKIGENBA_RUN_DIR` and every tool is rooted at `IKIGENBA_WORK_DIR` (CHOICE).
- The environment is proved through `bash`'s own `/proc/$$/environ`, which holds exactly what `bash` was started with, the child's environment, since toolkit's `Bash` runs `bash -c` with the child's environment. The command ends with `; :`, so `cat` is not the last command `bash` runs: `bash` must still be there to run `:`, so it cannot exec `cat` in its own process and must run it in a child, and `/proc/$$/environ` is read while `$$` is still the `bash` that was started. Whether `bash` forks before a last command whose output is redirected is not documented, so the check does not lean on it. Observed with bash 5.2.37: `env -i FOO=bar bash -c 'cat /proc/$$/environ > f; :'` leaves only `FOO=bar` in `f`, while a command `bash` execs in its own process, such as a bare `cp /proc/$$/environ f`, adds `PWD`, `SHLVL` and `_`. So the check is exact: any variable beyond the thirteen shows.
- A spec that `json.Marshal` cannot encode (an input that is not JSON, which neither `run` nor the delivery can send) is a run whose process cannot be launched: `failed` with `start_failed`.
- A queued run uses the prompt as it was when `run` was called; an `update` meanwhile changes later runs only (sheet CHOICE).
- Usage is summed from the transcript for every ending of a run whose process started, `Recover`'s included, and from nothing else: the core does not ask the child, and agentkit's `summary` record is not read. Cache-write token counts are not kept (sheet CHOICE).
- The drain refusal is the core's (`ErrDraining`), because the core is what the event bus calls and must refuse on its own. A call cut off at the drain deadline returns `ErrCutOff`, a sentinel of its own standing where scripts' `limits.ErrHalted` stood, and never one matching `ErrDraining`: the tools answer a refused call with the stopping refusal but a cut-off call with nothing at all (`D11-tools`), so the two must be told apart (CHOICE).
- A call whose context ends before it records its run is cut off: the caller gets no answer, so a record would be a run nobody asked to see.
- `start_failed` and `queue_abandoned` runs leave no stream files and zero usage, since they never opened a stream or ran the child.
- `Recover` records both truncation flags false: whether a dead prompts cut a stream is not known after the fact.
- A recorded `finished` is never before `started`: when `Now` has stepped back, `finished` is the run's `started`.
- `Cancel` of a run recorded `running` that has no process of this core records it `killed` all the same.
- The prune of an ending runs before that ending's `run.finished`, so the event marks a settled catalog.
- `Delete` removes folders before the records, as pruning does, and returns only after every killed run's `run.finished`, so `prompt.deleted`, which `D11-tools` emits after it returns, follows them.
- An event run is made as `Run` makes any run, with `Request.Cause`; the runs `Deliver` makes differ from a `Run` call's only in never being refused for a full queue (R-J1IB-PWWV). `Cause` is appkit's `events.Cause`, which the child is given both in its environment and in its spec, and forwards to the gateway.
- A queued run is recorded before it waits; the queue is the core's own; a queued run starts after the released slot's `run.finished`; the queue-full refusal counts once, at the call.
- `ErrNoCgroup` wraps the reason `Config.Unavailable` holds, so the tools answer its text as it is.
- The core reads `Config.Rand` from one goroutine at a time; sharing one `Rand` with the store and the writer is `cli.Run`'s to serialize (`D01-layout-and-run-seam`).
- toolkit's `Bash` starts each command in a process group of its own. `D06-runner` makes the child a session leader and kills and waits out its whole session, so a command the model left running ends with the run; this document's endings speak of the child's session.
- `tool_calls` counts `tool_result` records, the calls that ran and returned, not `tool_use` records, which agentkit also writes for a call its tool-call limit then refuses (CHOICE). A call killed before it returned is not counted.
- The usage summing is total: a `usage` record with a nil or negative member is skipped whole and every sum saturates at `math.MaxInt64`, so a transcript the model rewrote through `bash` cannot make an ending the catalog refuses (`D04-store`'s valid ending).

## Consumer tasks

At start (`D03-serve`): `core := runs.New(runs.Config{Store: st, Writer: w, Runs: filepath.Join(dir, "state", "runs"), Path: path, Services: servicesPath, Cgroup: runsGroup, Unavailable: reason, Keys: keys, BaseURL: p.BaseURL, PromptSeconds: s.PromptSeconds, OutputMaxBytes: s.OutputMaxBytes, MaxToolCalls: s.RunMaxToolCalls, KeepDays: s.RunKeepDays, KeepCount: s.RunKeepCount, RunMemoryMaxBytes: s.RunMemoryMaxBytes, RunPidsMax: s.RunPidsMax, MaxActive: s.RunMaxActive, MaxQueued: s.RunMaxQueued, Now: p.Now, ScriptAfter: p.ScriptAfter, Rand: rand})`, `keys` being `map[agentkit.Host]string` built from the five variables `agent.KeyVariable` names, looked up once through `p.LookupEnv`; then `core.Recover(bg)`, `core.Prune(bg)`, `bg` a context the stop signal does not end; then readiness. At the signal: `core.Drain(drainCtx)` beside the server's drain, and the writer's `Shutdown` after `Drain` returns.

The tools (`D11-tools`), `u` the call's caller: `run` is `s.Find` then `r, err := core.Run(ctx, pr, runs.Request{Input: raw, Caller: u})`: `errors.Is(err, runs.ErrDraining)` is the stopping refusal, `runs.ErrNoCgroup` the unavailable refusal, answered with `err.Error()`, `runs.ErrQueueFull` the queue-full refusal, answered with `err.Error()`, `store.ErrNotFound` the missing-prompt refusal, an error matching `runs.ErrCutOff` or the request context's cause a cut-off call, answered with nothing at all, and any other error `store.Unreachable`; otherwise `r.Status` is `running`, `queued` or `failed`, with `r.Reason`. `cancel` is `s.FindRun` then `core.Cancel(ctx, id)`, `store.ErrEnded` being the ended refusal. `delete` is `s.Find` then `core.Delete(ctx, pr.ID)`, then `prompt.deleted`. `result` is `s.FindRun`, then `core.Gone(r)` for `files_gone`, `core.Sizes(r)` for the byte counts, and the files under `core.Folder(r)`: `runs.StdoutFile`, `runs.StderrFile` (absent read as `""`), the size of `runs.TranscriptFile` (0 when absent) and the regular files under `runs.WorkDir`.

The delivery (`D14-delivery`), a method of the core: for each subscriber `pr`, a run made as `core.Run(context.WithoutCancel(ctx), pr, runs.Request{Input: b, Caller: identity.Caller{UserID: pr.Owner, Email: pr.OwnerEmail, RequestID: rid}, Cause: events.Cause{ID: d.Event.ID, Depth: d.Event.Depth}})`, `b` the event's canonical JSON, makes it but without the queue-full refusal, which the delivery has already counted for all its runs at once (`D14-delivery`), so a delivered run is never refused for a full queue; `errors.Is(err, store.ErrDelivered)` means the prompt already has its run.

The pages and run files (`D08-pages`, `D09-run-files`): `core.Folder(r)` joined with `runs.InputFile`, `runs.StdoutFile`, `runs.StderrFile`, `runs.TranscriptFile` or `runs.WorkDir`; `core.Gone(r)`; `core.Sizes(r)`.

A test builds a store, a writer over a `*telemetry.Capture`, and a core over a temporary `Runs`, with a `Now` it switches, a `ScriptAfter` whose channel it fires, a `PATH` it chose, `Keys` holding values of its own, and `BaseURL` naming an `httptest` server it serves as the provider; the package's `TestMain` runs the `agent` role when the binary is started with that one argument (`D06-runner`), so every run is the real child. A test **holds a run** by having its provider hold a response until the test releases it, which is how it fills a slot: with `MaxActive` 1 a run so held makes the next `Run` queue, deterministically. It holds a `Run` call in progress with a `Rand` that blocks until the test releases it; other calls then wait for that read only, since the core reads `Rand` from one goroutine at a time. It hands `Cgroup` a directory of its own and reads each run's control group files there, the child's pid among them. The child is non-dumpable (`D05-agent`), so its `/proc/<pid>/environ` and `cwd` are refused even to the test that started it, while its `/proc/<pid>/stat` and `cmdline` stay readable; the test sees the child's environment from inside a `bash` command of the run, which is dumpable and inherits it, by having its provider ask the `Bash` tool to copy `/proc/$$/environ`, and `$PPID`, the child's pid, into `work/`. It reads the folder, the transcript, the catalog and the capture.
