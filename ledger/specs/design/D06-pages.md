# D06-pages

What ledger draws as HTML: `internal/pages`, the four templates `landing`, `tools`, `about` and `notfound` of the root package's `Assets()` and the data each is executed with, `pages.Description`, the auth and sign-in addresses the pages build, and the page handler that answers `/`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it: the landing page, which says what the service is and relays the book as it stands, the tools page, the about screen and the not-found page (seam 4). The pages relay a few facts to show the service is up: they carry no form, no table of records, no per-record page and no paging, change no record and reach no sibling; the book is kept with the tools (`D07-tools`). A guest is sent to sign in, in campaigns' pattern. Decisions cited as seam N are the decisions document /home/mgreenly/projects/ikigenba-ledger.md.

`D01-layout-and-run-seam` declares `pages.ServiceName` and records that ledger has no `urls` package, so the two addresses the pages build live here; `D03-serve` routes every path that is not `/events`, `/declarations`, `/mcp` or under `/_appkit/` to this handler inside `identity.Optional`, defines a request's caller and a guest, and records why a guest is redirected here rather than refused by `identity.Require`; `D04-store` declares `store.Status`, the book and counts it answers, the store's today, and `store.Unreachable`; `D02-cli` bounds `pages.Description`'s bytes, since the manifest embeds it; `D07-tools` registers the tools the tools page lists, in its catalog order, and declares `tools.FirstLine`. appkit's `page`, `identity`, `mcp` and `services` packages own their contracts.

## The pages

The landing page, `/`, is the root of the banner's trail. It shows the book as one `store.Status` read answers it (`D04-store`): the currency, the lock date or that there is none, the fiscal year start, the count of open accounts, the count of transactions, reversals included, the date of the latest-dated transaction or that there is none, and the count of failing assertions, `check`'s set counted. Dates and codes are shown as stored and counts as plain integers, so the page formats nothing and needs no time layout. Every signed-in user sees the one book: it is the space's, not a user's.

The tools page lists every tool registered on the MCP server, in registration order, which is `D07-tools`' catalog order, each with the first line of its description as `tools.FirstLine` takes it; the about screen shows the service's name, the banner's `Release` and `Commit`, and `pages.Description`, the manifest's description. Each is one level below the root, `pages.ToolsLevel` and `pages.AboutLevel`. Every other path is the not-found page, 404, whatever the method; ledger has no per-record pages and no page values, so nothing else answers it. A query is ignored on every page.

The banner's user is the caller's email with auth's profile and sign-out addresses built on `pages.Auth`. The **auth address** is the `URL` of the services file's entry `auth`, every trailing `/` removed, or, with no such entry, built from the request's scheme and host with any port and a leading `ledger.` removed. The **sign-in address** is the auth address, then `/?return=`, then the request's own address query-escaped (`pages.SignIn`).

## Guests, methods and failures

The handler decides in this order. A guest is answered 302 to `pages.SignIn` with an empty body, whatever its path and method, before anything else is read. A signed-in request to a path that is not one of the three page paths is the not-found page, whatever its method. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD` and an empty body. None of these reads the store. Then, for `/` only, the store is read: a store that cannot be read is a **read refusal**, 503 in plain text with the line `store.Unreachable`, as campaigns answers. The tools page, the about screen and the not-found page read no store and are served the same while it fails. `HEAD` is answered as `GET` without a body. No answer sets a cookie.

## Recorded decisions

- **One data type per thing a template draws**, each field list exactly the template comment's, in its order (the root `AGENTS.md`'s Web assets rule; the field split into types is this design's own choice, as campaigns').
- **Counts are Go `int`**, as the template comments say and `store.Status` holds them (`D04-store`), so no conversion is needed.
- **Departure: `pages.Description` is declared with its value**, `Keep the business's books: accounts, transactions and statements.`, not as a copy constant without one as campaigns' `D07-pages` declares it. Reason: the brief and seam 1 fix the manifest's bytes, description included, and `D02-cli` gives the manifest verbatim and ties its description line to this constant; candidates declares its description with a value for the same reason. Its words still live in one place in the source.
- **Departure: no per-record pages and no paging on the landing page** (from campaigns' `D07-pages`, which pages its landing and has a page per campaign, and from `shape/README.md`'s Listing for pages). Reason: seam 4 asks for the basic footprint, a page of seven facts with no table of records, no per-record pages and no paging; the tools are the API and spa-ledger will be the browser front end. So there is no page value, no after- or before-token, no `last` and no 303, and a query is ignored rather than decoded.
- **No time layouts**: the landing shows dates as the store keeps them, `YYYY-MM-DD`, and the fiscal year start as `MM-DD`, as its template comment says; no page shows a stamp, so `pages.MinuteLayout` and `pages.SecondLayout` have no use here (a departure from campaigns' `D07-pages`).
- **The guest's redirect follows `D03-serve`'s recorded departure** (pages inside `identity.Optional` send a guest to sign in, with `guests = false` in the manifest so nginx gates too; candidates uses `identity.Require` instead). This document states only the redirect's answer.
- **A guest is sent to sign in before the method is looked at**, as campaigns' pages decided: every template comment says a guest is sent to sign in, and one rule for every path and method tells a guest nothing about which paths are pages.
- **The guest's 302 has an empty body**: it is not a page, so it draws no template, and net/http's redirect body would be markup the code writes.
- **`pages.Auth` and `pages.SignIn` are declared here**, their rules campaigns' `urls.Auth` and `urls.SignIn` with the host prefix `ledger.`: the pages are their only consumer, and `D01-layout-and-run-seam` records why ledger has no `urls` package. As campaigns decided, the sign-in address is built on the auth address, so the banner's profile and sign-out links and a guest's sign-in link name the same auth address in every case. No sibling-page builder is declared: no page links to artifacts.
- **The tools page reads the MCP server's registered tools**, `mcp.Server.Tools()`, at each request, as campaigns' does: `D03-serve` hands `pages.Config` the server on which `tools.Register` registers `D07-tools`' tools in catalog order, so the page and `tools/list` cannot disagree, and each row's description is `tools.FirstLine` of the registered description, the rule the catalog uses.
- **A database outage is a plain-text read refusal**: the landing template has no unavailable state, and `store.Unreachable` is the line ledger answers where the answer is not a page (`D04-store`). The guest's redirect, the 405, the not-found page and the tools and about pages are decided without the store, so they are the same during an outage.
- **`pages.Config` carries no clock and no artifacts client**: the store resolves today for the failing count (`D04-store` records that departure), and no page reaches artifacts.

## Consumer tasks

`web.Handler` (`D03-serve`) calls `set, err := pages.Load()` once and serves every page path with `identity.Optional(pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, MCP: cfg.MCP}))`, `tools.Register(cfg.MCP, ...)` having filled the server.

The landing reads `s, err := cfg.Store.Status(r.Context())`, answers the read refusal on an error, and executes `landing` through `set.Write(w, r, http.StatusOK, "landing", pages.LandingData{Banner: b, Currency: s.Book.Currency, LockDate: s.Book.LockDate, FiscalYearStart: s.Book.FiscalYearStart, OpenAccounts: s.OpenAccounts, Transactions: s.Transactions, LatestDate: s.LatestDate, FailingAssertions: s.FailingAssertions})`, `b` being `cfg.Banner(page.User{Email: …, ProfileURL: pages.Auth(r, cfg.ServicesPath) + "/", LogoutURL: pages.Auth(r, cfg.ServicesPath) + "/logout"})` with a nil `Trail`.

The tools page maps `cfg.MCP.Tools()` to `[]pages.ToolRow{{Name: t.Name, Description: tools.FirstLine(t.Description)}, …}` with `b.Trail` set to `[]page.Level{pages.ToolsLevel}`; the about screen executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}`, `b.Trail` set to `[]page.Level{pages.AboutLevel}`; the not-found page executes `notfound` with `pages.NotFoundData{Banner: b}`. A guest is answered by setting `Location` to `pages.SignIn(r, cfg.ServicesPath)` and writing the status 302 with no body.

A test opens a store over its own database with a clock it sets and a `Rand` it controls, sets the book, opens and closes accounts, posts and reverses transactions and asserts balances with the store's methods, writes a services file with a URL for `auth`, or none, and entries for `artifacts` and at least one other sibling, each naming a Unix socket on which a fake records each connection, builds its own set with `pages.Load()`, a writer `w := telemetry.New(telemetry.Config{Service: pages.ServiceName, Sink: &telemetry.Capture{}, Now: …, Rand: …})` it shuts down when it ends, a server `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Telemetry: w})` (which panics without a name or a writer, and reads `IKIGENBA_SERVICES`, so the test first sets that variable with `t.Setenv`) on which it registers tools (`tools.Register`, or tools of its own), serves `identity.Optional(pages.Handler(cfg))` with a fixed banner, sends raw requests with and without `X-User-Id`, and compares each body with what `set.Write` writes for the data the definitions below build; it compares the landing's data with `st.Status`, turns `SetFailing(true)` on for the read refusal, and inspects the fake's record of connections.
