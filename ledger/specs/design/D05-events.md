# D05-events

Decisions cited as seam N are /home/mgreenly/projects/ikigenba-ledger.md.

The bus: the one event ledger emits on the suite's event bus, `transaction.posted`, when a transaction is posted, a reversal included (seam 5), the record of a posted transaction in ledger's own trail, the declarations, and the two bus paths the events app reaches ledger on. This document declares the bus half of `internal/trail`: the event's name, the posting it carries, the two functions that make it and the declarations. `D08-trail` declares the rest of the package (the eleven trail-only names and their recording functions, `transaction.reversed` among them) and owns the closed set of telemetry event names, the trail's secrecy, and the `event.lost` a dropped bus event leaves in the trail. `D04-store` decides what a change is and reports whether one happened; `D07-tools` decides which tool calls change something, renders the amounts, and calls the functions declared here; `D03-serve` builds the run's writer and emitter, the latter with the declarations declared here, mounts `/events` and `/declarations`, puts a request's identity and event cause on its context, and owns the `lost event` line a dropped bus event leaves on stderr.

## The posted event

A posted transaction is told on the bus by `transaction.posted`, with six attribute keys, every key always present and every value a string:

- `transaction`: the transaction's `txn_` id.
- `date`: its date, `YYYY-MM-DD`.
- `flag`: its flag as posted, `pending` or `cleared`.
- `key`: the caller's idempotency key, empty when none (a reversal has none).
- `reverses`: the id of the transaction it reverses, empty when it is not a reversal.
- `postings`: every posting, in position order, each its account, its amount as the store renders it (`store.Amount.String()`, at the commodity's precision) and its commodity, written as one JSON array of objects in one string.

The name is literal; a subscriber (invoicing first) subscribes to it by its exact name, and a reversal rides the same event, told apart by `reverses`. The time of each is the bus event's own `Time`, so no attribute repeats it. Ids, a date, the flag, the key, account names, amounts and commodities only; never a payee, a narration, a tag, a link, metadata or an email (seam 5). The user is the envelope's `User`.

appkit's event attributes are flat: a value is a string, a number or a boolean, never a list. The postings are a list, so they ride as one string whose content is JSON; a subscriber decodes it. The encoding is fixed byte for byte, so the trail and the bus carry the same string and a subscriber's decoder never meets a surprise: an array, each element an object with the members `account`, `amount` and `commodity` in that order, no whitespace, each value encoded as Go's `encoding/json` encodes a string, and `[]` for no postings.

## Two ways at once, and once

A posted transaction goes two ways at once, as campaigns' events do: recorded in ledger's trail through the run's writer, and emitted on the bus through the run's emitter, under the same name, with the same attributes, the same request id and the same user. appkit's emitter records only `event.lost` in the trail, so the trail record is made by its own call of the writer's `Emit`.

A reversal is the exception. Seam 5 has every mutation record one event in the trail, and the reversal's is `transaction.reversed`, naming both ids (`D08-trail`); seam 5 also has reversals ride `transaction.posted` on the bus. So a reversal's `transaction.posted` goes on the bus only. Two functions keep the two paths apart: `trail.TransactionPosted` makes both halves, for `post`; `trail.ReversalPosted` takes no writer and makes the bus half only, for `reverse`, with `reverses` the original's id. The trail's record of a reversal is `D08-trail`'s `TransactionReversed`, which `D07-tools` calls beside it.

Each is told as the tool's caller: the request id and user are those of the `identity.Caller` on the context, and the bus event's cause is the event cause `events.Middleware` read from the call's headers, one level deeper, or none. Each call queues and returns: no answer waits for telemetry or the bus, and either half is made whatever becomes of the other. A bus event the emitter fails to deliver, refuses as malformed, or drops at a full queue or at the stop does not fail the call and does not undo the trail record or the posting; the emitter retries and drops as appkit's defaults say, and what a drop leaves is owned by `D08-trail` (the `event.lost` in the trail) and `D03-serve` (the line on stderr). The functions return nothing.

An event larger than the bus's limit (appkit's `events.MaxEventBytes`) would not be delivered; the number of postings one transaction may hold, which bounds it, is `D04-store`'s.

## The declarations

`trail.Emits()` is what the run's emitter is built with: the one name, literal, with its six keys in the order listed above, so appkit refuses a `transaction.posted` whose keys are not exactly these. The trail-only names of `D08-trail` are not declared: they never go on the bus.

ledger accepts no bus event (seam 5). The events app reaches it at its socket on `/events`, answered by appkit's `events.DeliveryHandler` with no handlers, and `/declarations`, answered by `events.DeclarationsHandler` over the run's emitter with no handlers, which answers the emission with `accepts` empty. The body is stated below because its content is this document's declarations; what the run's handler answers at `/events` is stated here too, since that ledger accepts nothing is this document's contract: it answers exactly as `events.DeliveryHandler(nil)` does. The route table, the routes' place outside the identity gate, and nginx's 404 for both paths at the public name are `D03-serve`'s and `D09-on-a-space`'s.

## Recorded decisions

- **`postings` is one JSON-encoded string.** Seam 5 puts each posting's account, amount and commodity in the payload; appkit's event attributes are flat basic values (appkit's `events` and `telemetry` both refuse any other kind), so a list cannot be an attribute. The alternatives were numbered keys (`posting_0_account` and so on), which appkit's exact-keys declaration cannot express for a varying count, and dropping the postings so a subscriber calls `transaction`, which the seam rules out. One string holding a JSON array is the smallest form that carries the seam's payload whole. Its bytes are fixed so the trail and the bus agree and a test can compare them.
- **Amounts in `postings` are rendered text**, as the store renders them at the commodity's precision beside the commodity, the same form every tool answers; never minor units, so a subscriber needs no precision table.
- **A reversal's `transaction.posted` is on the bus but not in the trail**, a departure from campaigns' "two ways at once", where every bus event is also a trail record. Seam 5 records exactly one trail event per mutation and names the reversal's `transaction.reversed`, and it puts reversals on the bus as `transaction.posted`; recording both in the trail would make a reversal two trail events. So `ReversalPosted` is a function of its own that takes no writer, and the trail's record of a reversal is `transaction.reversed` alone.
- `key` and `reverses` are always present, empty when none, as appkit's exact-keys rule requires.
- No time attribute: the bus event's envelope `Time` is the posting's time as told.
- The recording functions take plain strings and `trail.Posting` values, not store records (campaigns' decision), so the event's contract does not move when a store record gains a field, and the caller renders the amounts.
- **Told as the caller**, as campaigns' events: every posted event is made inside the tool call that posted, so the call's own identity and cause are the right ones.
- A failed or dropped bus event never fails a tool call nor undoes its posting: the posting is the record, the event a notice of it.
- ledger accepts no event and declares none to accept (seam 5); `/events` answers every delivery as appkit's handler with no handlers does.

## Consumer tasks

The tools (`D07-tools`) call `trail.TransactionPosted(ctx, cfg.Telemetry, cfg.Events, t.ID, t.Date, flag, t.Key, "", postings)` once `post` has posted a transaction, `postings` holding one `trail.Posting{Account, Amount, Commodity}` per posting in position order with `Amount` the posting's `store.Amount` rendered by its `String()`; and `trail.ReversalPosted(ctx, cfg.Events, r.ID, r.Date, flag, r.Key, original, postings)` (`r.Key` the reversal's key, empty since a reversal has none) once `reverse` has made a reversal, beside `D08-trail`'s `TransactionReversed`. A `post` answered from an existing key, a `reverse` answered with an existing reversal, a refused call and a read call make neither. `D03-serve` builds the emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`, mounts `events.DeliveryHandler(nil)` at exactly `/events` and `events.DeclarationsHandler(em, nil)` at exactly `/declarations`, both outside the identity gate, and puts `events.Middleware` on `/mcp` so a call's cause reaches the context. A test builds a writer with `telemetry.New` over a `*telemetry.Capture` and an emitter with `events.New` over an `*events.Capture` with `trail.Emits()` (and, for `ReversalPosted`, with that writer as the emitter's `Telemetry`), calls a function under `identity.NewContext` (and `events.NewContext` for a cause), flushes both, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`; it serves `events.DeclarationsHandler(em, nil)` with `httptest` to read the declarations.
