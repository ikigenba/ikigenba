# Decision 17 — Correlation adoption: the chain id crosses ledger's edge and reaches its outbox

> **⛔ EXTERNAL ORDERING — operator-sequenced, not built by any ledger phase.**
> This Decision consumes the shared leaf package `eventplane/correlation`, the
> revised `eventplane/outbox` (a `correlation_id` column and envelope field,
> and an `Append` populated from the caller's context), and the revised
> `appkit` chassis (correlation middleware, the telemetry recorder, MCP/HTTP
> request records, lifecycle records, the publish hop). Those surfaces are
> owned by the `appkit` and `eventplane` workspaces and are consumed here as
> fixed contracts — see `project/research/research.md` for the exact footprint.
> **appkit and eventplane must be BUILT before ledger's adoption phase runs**;
> until they land it cannot compile. ledger's nginx-fragment phase has no such
> dependency and can run at any time.

**Problem.** A forensic agent must be able to reconstruct any sequence of
events across the suite: who did what, when, in what order. That rests on one
id per causal chain, propagated verbatim on every hop. ledger sits on two of
those hops and gets neither for free:

1. **The edge.** nginx is ledger's sole trust boundary. The dashboard's
   introspection endpoints mint the chain id and return it on the auth
   subrequest, but a header that nginx does not explicitly capture and re-set
   simply never reaches the loopback service — so today every ledger request
   would arrive uncorrelated and the chassis would mint a fresh id per hop,
   producing exactly the severed trail the capability exists to prevent. Worse,
   the fragment's ungated locations would forward whatever `X-Correlation-Id`
   a public caller chose to send, letting an outsider inject themselves into
   someone else's chain.
2. **The producer seam.** Every committed ledger transaction appends a
   `transaction.recorded` event. The revised `Append` reads the correlation id
   off the context it is handed — but ledger's domain seam **drops the
   context**: `Service.Record(ctx, …)` has it, `Service.persist(tx, t)` does
   not, and `EventSink.AppendRecorded(tx, t)` does not either. A build that
   satisfies the compiler by handing `context.Background()` to `Append` appends
   a perfectly valid row with an **empty** `correlation_id`, and every chain
   that passes through ledger goes dark with nothing failing.

Everything else ledger needs arrives by recompiling against the chassis:
`request` records for the seven domain verbs and the standard tools,
`lifecycle` `start`/`stop`, the `publish` hop, and read-or-mint correlation
middleware on the loopback server. ledger writes no instrumentation code.

**Decision.**

### (a) The fragment carries the chain id across the trust boundary

`ledger/etc/nginx.conf` gains exactly two kinds of line, and removes none.

**Every gated location captures the introspection-minted id and forwards it,
overwriting anything the client sent.** The dashboard's `/_authn` (bearer) and
`/_session-authn` (cookie) hooks both return `X-Correlation-Id` on an allow, so
all three gated locations take the same treatment, with **service-prefixed**
variable names so they stay unique inside the one apex `server` block every
fragment is included into:

| location | gate | capture variable |
|---|---|---|
| `location /srv/ledger/` (prefix) | `/_authn` | `$ledger_correlation` |
| `location = /srv/ledger/` (landing) | `/_session-authn` | `$ledger_session_correlation` |
| `location /srv/ledger/static/` (assets) | `/_session-authn` | `$ledger_static_correlation` |

each as:

```
auth_request_set $ledger_correlation $upstream_http_x_correlation_id;
proxy_set_header X-Correlation-Id $ledger_correlation;
```

The identity-hygiene property that already protects `X-Owner-*` extends
unchanged to this header: nginx does not pass an inbound client header as a
proxy header unless explicitly set, and the last `proxy_set_header` for a name
wins — so a single set from the auth-subrequest variable **replaces** any
`X-Correlation-Id` a client tried to smuggle. The static tier is included even
though it forwards no owner identity, because an asset fetch is a real hop of
the page load's chain and correlating it costs one variable; the correlation id
is not identity and carries no authority.

**Every ungated public location strips the header:**

```
proxy_set_header X-Correlation-Id "";
```

on `location = /srv/ledger/.well-known/oauth-protected-resource`, the one
location under the mount that runs no `auth_request`. nginx omits a header set
to the empty string entirely, so the chassis sees no inbound id and mints one —
which is the correct outcome for a request with no authenticated cause. A
public caller can therefore never inject an id anywhere in ledger's fragment.

`location @ledger_authn_500` and the `error_page`/`@login_bounce` machinery
proxy nothing and are untouched.

### (b) The domain seam carries the context to `Append`

The context stops being dropped. Three signatures widen, all inside
`internal/ledger`:

```go
// service.go — the EventSink seam
type EventSink interface {
    AppendRecorded(ctx context.Context, tx *sql.Tx, t Transaction) error
    Ring()
}

// service.go
func (s *Service) persist(ctx context.Context, tx *sql.Tx, t Transaction) error

// events.go — the outbox adapter
func (o *outboxProducer) AppendRecorded(ctx context.Context, tx *sql.Tx, t Transaction) error
```

`persist` hands its `ctx` to `s.Outbox.AppendRecorded`, which hands it to the
revised `outbox.Append(ctx, tx, ev)` — which reads
`correlation.FromContext(ctx)` and stores the result on the row, minting
nothing. Both callers already hold a real request context:
`Record` (`transaction.go`) and `Reverse` (`reverse.go`) each receive `ctx` and
already use it for `BeginTx`, so each passes that same `ctx` to `persist`. The
chassis has already put the chain id on it. **No call site anywhere in ledger
constructs a context** — no `context.Background()`, no `context.TODO()`, on any
path that reaches `Append`. That is the whole of the change: no new package, no
new field, no id minting, no policy. ledger is a pure propagator.

`transactionRecordedEvent`, the payload shape, the `Ring()`-after-commit rule,
the one-event-per-committed-transaction rule (reversal mirrors included), and
the atomicity of the append with the journal write are **all unchanged**. The
correlation id rides the **envelope**, never the payload — ledger adds no
payload field for it, and the superseded payload-field convention in
`project/design/D14.md` at the repo root is not adopted.

### (c) The outbox schema movement

eventplane's `SchemaSQL` gains `correlation_id TEXT NOT NULL DEFAULT ''` as its
**last** column, and eventplane owns the upgrade text too —
`outbox.AddCorrelationIDSQL`, an `ALTER TABLE outbox ADD COLUMN`. eventplane
applies nothing itself; each service owns its migration runner.

Committed migrations are immutable and the runner silently skips an edited
body, so ledger appends **one new timestamped migration** minted with
`bin/create-migration ledger outbox_correlation` — never a hand-picked number —
whose body is `outbox.AddCorrelationIDSQL` verbatim. The frozen
`003_outbox.sql` and `20260712184833_outbox_routing.sql` are **not** touched.

Note what this is *not*: it is **not** the drop-and-recreate D15 used for the
kind/subject cutover. `ADD COLUMN` rewrites no rows, back-fills existing rows
with `''`, and leaves both the `seq` values and SQLite's `sqlite_sequence`
high-water mark untouched, so no consumer's cursor moves. Consequently the
existing DDL drift guard in `internal/db/migrations_outbox_test.go` stays
pointed at `20260712184833_outbox_routing.sql` — the newest migration that
carries a full `outbox.SchemaSQL` body — because the new migration carries an
`ALTER`, not the create text. Both spellings must nonetheless agree: a fresh
database built by `SchemaSQL` and an upgraded one built by the create-then-
`ALTER` sequence end up column-for-column identical, which is why the column is
declared last.

**ledger holds live customer data.** This migration touches the `outbox` table
only, adds one column, and drops nothing. No domain table, no journal row, and
no posting is in its path.

### (d) Deliberate non-changes

- **`etc/manifest.env` gains no key.** `TELEMETRY_INGEST_URL` and
  `TELEMETRY_ENABLED` are unprefixed, suite-wide, and default correctly
  (`research.md` §5). One suite-wide address does not get fifteen homes.
- **ledger writes no instrumentation.** No recorder call, no `root` record —
  ledger originates no work of its own; every ledger record has an inbound
  request or an event behind it, and the chassis emits all of them.
- **No outbound HTTP client migration.** ledger makes no outbound calls.
- **No MCP surface change.** No tool declares `SensitiveParams`: ledger's seven
  verbs take account paths, dates, memos, and integer cents — no credential,
  no token, no secret — and the per-value 1024-byte / per-record 8192-byte
  capture policy already bounds a large `record` call.

**Rejected.**
- **Capturing `X-Correlation-Id` only on the bearer prefix** — the landing page
  and its assets are real hops of a logged-in human's chain; leaving them
  uncorrelated makes a browser session unreconstructable for no saving.
- **Leaving the PRM location alone (no strip)** — it is the one unauthenticated
  path under the mount, so it is exactly where an outsider would inject an id
  to attach themselves to someone else's chain. Silence there is the whole
  point of the strip rule.
- **Forwarding the client's `X-Correlation-Id` when the auth subrequest did not
  return one** — resurrects the injection hole through the gated tier; the
  auth-subrequest variable is the only trusted source, and an empty one
  correctly makes the chassis mint.
- **Threading the correlation id as an explicit `string` argument through
  `persist`/`AppendRecorded` instead of the context** — makes ledger a
  participant in correlation policy, duplicates what the context already
  carries, and would need a second parameter every time the envelope grows.
  eventplane's promise is explicitly that a producer does nothing beyond
  passing along the context it already has.
- **Minting an id in the producer when the context carries none** — ledger is
  never the outermost cause of anything; a ledger write always has a caller.
  Minting here would fabricate a root and hide the real gap.
- **Adding `correlation_id` to the `transaction.recorded` payload** — the
  superseded convention. The envelope addresses; the payload stays the detail
  record, and duplicating the id invites the two to diverge.
- **Editing a committed outbox migration in place** — the runner keys on the
  version and skips an edited body, so the change would reach new databases and
  not ledger's live one. The exact failure mode the immutability rule exists
  to prevent.

**Verification.** The first two ids pin the **fragment**, following D4's
established practice in this workspace: a test reads `ledger/etc/nginx.conf`
from disk and asserts over its content, in the same `go test ./...` run (nginx
is not run by the suite).

- R-B98U-XGC9 — **every gated location captures and forwards the chain id.**
  All three gated locations in `ledger/etc/nginx.conf` carry both halves with
  service-prefixed variables: the bearer prefix `location /srv/ledger/` has
  `auth_request_set $ledger_correlation $upstream_http_x_correlation_id;` and
  `proxy_set_header X-Correlation-Id $ledger_correlation;`; the session
  exact-match `location = /srv/ledger/` has the same pair on
  `$ledger_session_correlation`; and `location /srv/ledger/static/` has it on
  `$ledger_static_correlation`. A fragment that captures without forwarding
  (or captures on only the bearer tier, leaving a logged-in human's page load
  and its assets uncorrelated) fails this. Its existing four `X-Owner-*`
  captures/forwards per identity-forwarding location, `X-Client-Id`, and the
  `@ledger_authn_500` re-emit all remain.
- R-BAGR-B82Y — **no location forwards a client-supplied id.** The ungated
  `location = /srv/ledger/.well-known/oauth-protected-resource` carries
  `proxy_set_header X-Correlation-Id "";` (nginx omits an empty-valued header,
  so the chassis mints for itself), **and** the whole file carries exactly
  **four** `proxy_set_header X-Correlation-Id` lines — the three
  auth-subrequest-sourced ones plus this strip. A fragment that adds a
  proxying location without a `X-Correlation-Id` set of its own, leaving the
  client's inbound value to reach the service, fails the count.

The three remaining ids are behaviors **ledger itself** proves, all against a **real** SQLite database
migrated through ledger's full embedded migration set (`db.FS` via the appkit
runner), with rows read back by SQL. They do not restate chassis coverage:
appkit proves read-or-mint middleware and eventplane proves the column, the
upgrade text, and the envelope; these prove that *ledger's own* migration set
and domain seam do not drop what those two hand it.

- R-Y3Z7-H9BG — ledger's migration set actually applies the upgrade: applying
  `db.FS` through the appkit runner to a fresh real SQLite database yields an
  `outbox` table carrying a `correlation_id` column that is `TEXT NOT NULL`
  with default `''` (`PRAGMA table_info`), and the resulting column list is
  **identical, in order,** to the one `outbox.SchemaSQL` alone produces on a
  separate fresh database — so an upgraded ledger and a new one are the same
  table. A build that adds the column to `SchemaSQL` but forgets ledger's own
  migration fails this, which is the failure that would break every ledger
  write on the live box.
- R-VOH6-HG8R — the chain id survives ledger's domain seam: a `Record` driven
  under a context carrying a known correlation id (placed with
  `correlation.WithContext`) appends an outbox row whose `correlation_id`, read back
  by SQL, is **exactly that id** — not empty, and not some other well-formed
  26-character id — and a `Reverse` driven under a second, different known id
  appends its mirror's row carrying **that** id, so both emit paths propagate
  rather than one. A build that hands `context.Background()` to `Append`, or
  that mints a fresh id in the producer, fails this.
- R-VPP2-V7ZG — correlation is never a precondition for bookkeeping: a
  `Record` driven under a context carrying **no** correlation id still commits
  — the transaction and its postings are present in the journal by SQL, the
  outbox row is appended with an **empty** `correlation_id`, and the call
  returns no error. A build that rejects, errors on, or synthesizes an id for
  an uncorrelated append fails this.
