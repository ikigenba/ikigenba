# D08-pages

What scrapes draws as HTML: `internal/pages`, the six templates `landing`, `run`, `row`, `tools`, `about` and `notfound` and the data each is executed with, and the handler that answers `/`, `/runs/<id>`, `/runs/<id>/rows/<source_id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it. It is gmail's pages with a run in place of a draft or transfer and a row page below it. Which requests reach the page handler is `D03-serve`'s, which keeps `/runs/<id>` for the run page and serves the sibling read path's run record at `/runs/<id>/record`; this document states what the page handler answers.

## The pages

The landing page (decision 10) shows each registered scraper, in name order, with its current run, the newest `done` (id linked, status, started, finished, rows, new, changed and gone), and its running run when one is (id linked); then the kept runs across scrapers, newest first in the store's run order (`D04-store`), each with its id linked, scraper, status, reason when failed, who started it, started, finished and rows. The landing page shows no row: no business name, address, phone or email reaches it. At most `pages.RunsShown` runs are listed, far more than retention keeps (`D06-runs`).

`/runs/<id>` is one run's record in full; when it failed, the reason's sentence, which the template chooses from `Reason`; when it is `done`, the first page of its rows in `source_id` order, each linked to its page, and the `next` the `rows` tool answers for that page, shown as a number for the reader to pass as `page` (decision log D6): no link, no query, no route. A run still `running` shows its record as it stands and no rows; the page does not stream. `/runs/<id>/rows/<source_id>` is one row: its envelope as a table and its raw record as formatted JSON. An unknown run id, a pruned one, a row the run does not hold and a run that is not `done` are answered alike, the not-found page with 404, byte for byte the not-found page of any other path.

The tools page lists the six tools in the catalog's order (`D10-tools`), each with its one-line description. The about screen shows the service's name, the banner's `Release` and `Commit` and `pages.Description`. Any other path is the not-found page, 404, whatever the method.

The landing page is the root of the banner's trail; a run page is one level below it, named by the run's id at `/runs/<id>`; a row page two, the run then the source id at `/runs/<id>/rows/<source_id>`; and the tools page and the about screen one, `pages.ToolsLevel` and `pages.AboutLevel`. The banner's user is the caller's email, with auth's profile and sign-out addresses built on `urls.Auth` (`D01-layout-and-run-seam`).

## Who started a run

A run started by a `scrape` call shows the caller's email; one started by a cron delivery shows `cron` and the trigger's slug (decision 4, the assets agent's call in the decisions log). The data carries both, `StartedBy` (the email, empty for a delivery) and `Trigger` (the slug, empty for a call), and the template chooses; the words are the template's.

## Pages show what is stored

Pages make no call to a source and change no record: a run's page shows the status the store holds. Runs belong to no one (decision 7), so every signed-in user sees the same pages.

## The data

Every value a template receives is a string, a slice, a pointer to a struct or an `int64` count. Times are the stored UTC times formatted twice, as the template comments name them: RFC 3339 to the second for a `time` element's `datetime`, and a `...Text` field in the page's layout, `pages.MinuteLayout` on the landing page and `pages.SecondLayout` on the run and row pages. A time not yet set gives both strings empty. The field names are the template comments'. On the row page a point's coordinates are text, a fact's value is its compact JSON text, the facts in ascending order of their keys, and the raw record is its JSON indented two spaces with its members in the order the source sent them.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so nginx sends a request with no credential to sign in before it reaches scrapes, and `D03-serve` mounts this handler inside `identity.Require`. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. The landing, run and row pages answer 503 with `store.Unreachable` as `D03-serve`'s read refusal when the store cannot be read; the about, tools and not-found pages are served without reading it.

## Recorded decisions

- Run pages at `/runs/<id>` and row pages at `/runs/<id>/rows/<source_id>` (decision 10). A path whose id fails `store.ValidRunID` is not looked up, and a row path's last segment is a source id once percent-decoded.
- `ServiceName`, `Description`, the two layouts and `RunsShown` are contract constants with values, as in gmail: `Description` is the manifest's text, which the host parses, and the `User-Agent` names it (`D05-scrapers`, decision log D2).
- One data type per thing a template draws, each field list the template comment's in its order: the landing's current run and running run are their own types because they carry fewer fields than a landing run row; the run page's row line carries only the five fields its table shows.
- Counts are `int64`, as the store holds them, and so is the run page's `Next`, as the `rows` tool's `next` is.
- The landing lists at most `RunsShown` (100) runs: decision 10 says runs newest first, and retention keeps `SCRAPE_KEEP_RUNS` done and as many failed runs per scraper, so with the default of 2 and one scraper at most five; the bound keeps the page and its query small if the setting is raised.
- The run page's rows are the `rows` tool's first page for the run with no name filter, computed by the same definition (`D10-tools`), so the `next` it shows is the tool's.
- Latitude and longitude are written with `strconv.FormatFloat(v, 'f', -1, 64)`, the shortest decimal that reads back as the stored value; FMCSA gives no point, so the row page shows none for it.
- An unknown, pruned or not-done run and a missing row are one not-found answer, byte for byte the not-found page of any other path; a database outage is a plain-text 503 with `store.Unreachable` and a newline, as in gmail.

## Consumer tasks

`web.Handler` (`D03-serve`) builds `s, err := pages.Load()` and mounts `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store, Scrapers: cfg.Scrapers})` inside `identity.Require` for the page paths. `D01-layout-and-run-seam`'s about requirement executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}`; `D02-cli` compares the manifest with `pages.Description`; `main` names the service `pages.ServiceName`. A test builds a store over its own database with a clock it sets, records runs of two scrapers with `AddRun`, fills some with rows of its own choosing, finishes some `done` and fails some with each reason, builds a registry of fake scrapers with `scrapers.New`, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a fixed banner, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template writes for a `LandingData`, a `RunData`, a `RowData`, a `ToolsData` built from `tools.Catalog()`, an `AboutData` or a `NotFoundData`; it asks a pruned run and a running run's row and gets the not-found page, and turns the store's failing switch on to see the 503.
