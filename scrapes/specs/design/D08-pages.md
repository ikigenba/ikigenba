# D08-pages

What scrapes draws as HTML: `internal/pages`, the six templates `landing`, `run`, `row`, `tools`, `about` and `notfound` and the data each is executed with, and the handler that answers `/`, `/runs/<id>`, `/runs/<id>/rows/<source_id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it. It is gmail's pages with a run in place of a draft or transfer and a row page below it. Which requests reach the page handler is `D03-serve`'s, which keeps `/runs/<id>` for the run page and serves the sibling read path's run record at `/runs/<id>/record`; this document states what the page handler answers.

## The pages

The landing page (decision 10) shows each registered scraper, in name order, with its current run, the newest `done` (id linked, status, started, finished, rows, new, changed and gone), and its running run when one is (id linked); then the kept runs across scrapers, newest first in the store's run order (`D04-store`), each with its id linked, scraper, status, reason when failed, who started it, started, finished and rows. The landing page shows no row: no business name, address, phone or email reaches it. The runs listed are one window of `paging.DefaultLimit`, the window the request's `page` query parameter names, and the value is one of four: empty or absent, the first window; the token the `runs` tool issues as `next`, the window after the run it names; a before-token, `paging.Token{Tool: "runs-before"}` over a run's started time and id, the `paging.DefaultLimit` runs that come before the one it names in the list's own order, newest first, that is the newer runs nearest it; and the literal `last`, the last `paging.DefaultLimit` runs, the oldest kept. Every window is drawn newest first. The window for the empty value or an after-token is exactly the runs a `runs` call (`D10-tools`) answers for the same `page` with no `scraper` and no `limit`, and its `Next` the very `next` that call answers, so a token on the page is one a model can hand to `runs` unchanged and a token `runs` gave is a page URL. `Page` is the value the request carried; `Prev` is the before-token over the window's first run on any window but the first; `Next` is the after-token over its last run when more follow, so it is always set on a before-window and never on the `last` window. The template draws First, Prev, Next and Last from them (`shape/`, Listing; `appkit/paging`, appkit's D25). The handler learns whether more follow as the tool does, by asking the store for one run more than the window in whichever direction it reads, so it never holds more than a window and one row: a backward read nearest first, reversed for display. A before-window or the `last` window that finds `paging.DefaultLimit` runs or fewer is the first window, and the page answers 303 to `/`, the one address the first window has. The scrapers list is bounded by the registry, so it is listed whole and does not page.

`/runs/<id>` is one run's record in full; when it failed, the reason's sentence, which the template chooses from `Reason`; when it is `done`, one window of `paging.DefaultLimit` of its rows in `source_id` order, each linked to its page, the window the request's `page` query parameter names, one of the same four: empty, the first window; the token the `rows` tool issues as `next`; a before-token, `paging.Token{Tool: "rows-before"}` over a source id, the `paging.DefaultLimit` rows whose source ids come before it in the list's ascending order, the nearest below it; and `last`, the rows with the greatest source ids. The window for the empty value or an after-token is exactly the rows a `rows` call (`D10-tools`) naming the run answers for the same `page` with no `name` and no `limit`, and its `Next` the very `next` that call answers. `Page`, `Prev` and `Next` mean what they mean on the landing page, and the template draws First, Prev, Next and Last from them (`shape/`, Listing; `appkit/paging`, appkit's D25); a before-window or the `last` window of `paging.DefaultLimit` rows or fewer answers 303 to the run's own path, `/runs/<id>`. A run still `running` shows its record as it stands and no rows; the page does not stream. A run that is not `done` shows no rows and no navigation whatever its `page`: the value is still decoded, and one that decodes, a before-token and `last` included, shows the page as it is without one, with `Page` the value carried, `Prev` and `Next` empty, and never redirects. The row page `/runs/<id>/rows/<source_id>` reads no query. `/runs/<id>/rows/<source_id>` is one row: its envelope as a table and its raw record as formatted JSON. An unknown run id, a pruned one, a row the run does not hold and a run that is not `done` are answered alike, the not-found page with 404, byte for byte the not-found page of any other path.

The tools page lists the six tools in the catalog's order (`D10-tools`), each with its one-line description. The about screen shows the service's name, the banner's `Release` and `Commit` and `pages.Description`. Any other path is the not-found page, 404, whatever the method.

The landing page is the root of the banner's trail; a run page is one level below it, named by the run's id at `/runs/<id>`; a row page two, the run then the source id at `/runs/<id>/rows/<source_id>`; and the tools page and the about screen one, `pages.ToolsLevel` and `pages.AboutLevel`. The banner's user is the caller's email, with auth's profile and sign-out addresses built on `urls.Auth` (`D01-layout-and-run-seam`).

## Who started a run

A run started by a `scrape` call shows the caller's email; one started by a cron delivery shows `cron` and the trigger's slug (decision 4, the assets agent's call in the decisions log). The data carries both, `StartedBy` (the email, empty for a delivery) and `Trigger` (the slug, empty for a call), and the template chooses; the words are the template's.

## Pages show what is stored

Pages make no call to a source and change no record: a run's page shows the status the store holds. Runs belong to no one (decision 7), so every signed-in user sees the same pages.

## The data

Every value a template receives is a string, a slice, a pointer to a struct or an `int64` count. Times are the stored UTC times formatted twice, as the template comments name them: RFC 3339 to the second for a `time` element's `datetime`, and a `...Text` field in the page's layout, `pages.MinuteLayout` on the landing page and `pages.SecondLayout` on the run and row pages. A time not yet set gives both strings empty. The field names are the template comments'. On the row page a point's coordinates are text, a fact's value is its compact JSON text, the facts in ascending order of their keys, and the raw record is its JSON indented two spaces with its members in the order the source sent them.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so nginx sends a request with no credential to sign in before it reaches scrapes, and `D03-serve` mounts this handler inside `identity.Require`. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. On `/` and a run path the `page` value is decided next: one the handler cannot decode is answered with the not-found page, never the first window, before the store is read, so the answer is the same while the store is unavailable; on a run path it is the same 404 whether or not a run has the id, so the order of the run lookup and the token is not observable. The landing, run and row pages answer 503 with `store.Unreachable` as `D03-serve`'s read refusal when the store cannot be read and the `page` value, where one is read, is decodable, never a page and never a redirect; the about, tools and not-found pages are served without reading it.

## Recorded decisions

- Run pages at `/runs/<id>` and row pages at `/runs/<id>/rows/<source_id>` (decision 10). A path whose id fails `store.ValidRunID` is not looked up, and a row path's last segment is a source id once percent-decoded.
- `ServiceName`, `Description` and the two layouts are contract constants with values, as in gmail: `Description` is the manifest's text, which the host parses, and the `User-Agent` names it (`D05-scrapers`, decision log D2).
- One data type per thing a template draws, each field list the template comment's in its order: the landing's current run and running run are their own types because they carry fewer fields than a landing run row; the run page's row line carries only the five fields its table shows.
- Counts are `int64`, as the store holds them. `Next`, on the landing and on the run page alike, is a string, the after-token over the window's last entry, the one its tool answers as `next` on an after-window, empty when none follows; `Prev` is a string, the before-token over the window's first entry, empty on the first window; `Page` is a string, the value the request carried, empty on the first window.
- The landing shows a window of runs, `paging.DefaultLimit` of them, rather than a bound of its own: decision 10 says runs newest first, and retention keeps `SCRAPE_KEEP_RUNS` done and as many failed runs per scraper, so with the default of 2 and three scrapers the page usually holds every run, but the suite's listing convention pages every list a person or an agent adds to.
- The run page's rows are the `rows` tool's window for the run and the same `page` with no name filter, computed by the same definition (`D10-tools`), so the `next` it shows is the tool's.
- The pages navigate (`design/`, the listing entry of 2026-10-13): each takes its tool's token as `?page=`, the first `page` in the query, and reads nothing else from it. Before, each showed its first window and named the tool and the token for the rest, with no way to page itself. A window of `paging.DefaultLimit` or fewer looks as it did, with an empty `Page` and `Next`.
- The pages go back as well as forward (`design/`, the listing entry of 2026-10-13, with Prev and Last; `shape/`, Listing). A before-token is issued under the tool's name with `-before` appended, so no tool accepts it and neither page mistakes it for the other's; `last` is the literal word, decodable on both pages. A backward window mirrors its list's order: the landing lists newest first, so the window before a run is the newer runs nearest it and `last` the oldest; the run page lists source ids ascending, so the window before a row is the lower source ids nearest it and `last` the greatest. Either is read nearest first with one entry more than the window and reversed for display, so it is drawn in the list's order like any window.
- A before-window or `last` window that finds `paging.DefaultLimit` entries or fewer before its position is the first window, and is answered 303 to the page's own path rather than drawn: the first window has one address, and the window drawn there is a full one, not the short head of the list a reversed read would leave. On a run that is not `done` no read happens that could underflow, so the page is drawn as for any decodable value.
- A before-token naming an entry no longer held, a pruned run or a row of a run that is gone, still names a position: the window is the one before where that entry sorted.
- A `page` the handler cannot decode is the not-found page, not the first window and not a 400: the URL names no window this service issued, as an unknown run id names no run. It is decided before the store is read, as the tools refuse a bad `page` before reading it, so a stale link answers the same while the database is down.
- On a run that is not `done`, a decodable `page` shows the page as without one and `Page` is the token carried, so `Page` always means the token the request carried; the template draws no navigation for a run that is not `done`. An undecodable one is the not-found page there too, so whether a token is accepted never depends on the run's status.
- Latitude and longitude are written with `strconv.FormatFloat(v, 'f', -1, 64)`, the shortest decimal that reads back as the stored value; FMCSA gives no point, so the row page shows none for it.
- An unknown, pruned or not-done run and a missing row are one not-found answer, byte for byte the not-found page of any other path; a database outage is a plain-text 503 with `store.Unreachable` and a newline, as in gmail.

## Consumer tasks

`web.Handler` (`D03-serve`) builds `s, err := pages.Load()` and mounts `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store, Scrapers: cfg.Scrapers})` inside `identity.Require` for the page paths. `D01-layout-and-run-seam`'s about requirement executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}`; `D02-cli` compares the manifest with `pages.Description`; `main` names the service `pages.ServiceName`. A test builds a store over its own database with a clock it sets, records runs of two scrapers with `AddRun`, fills some with rows of its own choosing, finishes some `done` and fails some with each reason, builds a registry of fake scrapers with `scrapers.New`, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a fixed banner, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template writes for a `LandingData`, its `Runs` and `Next` those a `runs` call with `{}` answers over the same store and, requested with `?page=` that call's `next`, those a `runs` call with `{"page": next}` answers and that token as `Page`, a `RunData`, its `Rows` the row lines of the `rows` a `rows` call with `{"run": id}` answers and its `Next` that answer's `next`, and likewise with `?page=` and `{"run": id, "page": next}`, a `RowData`, a `ToolsData` built from `tools.Catalog()`, an `AboutData` or a `NotFoundData`; it asks a pruned run and a running run's row and gets the not-found page, asks `/?page=bogus` and `/runs/<id>?page=bogus` and gets the not-found page with the store failing and not, and turns the store's failing switch on to see the 503. On each page it walks Next from the first window to the last and Prev back, collecting each window's ids, and checks that the backward walk yields the same windows in the opposite order and that the Prev from the second window answers 303 to the page's path; asks `?page=last` and compares its window with the last `paging.DefaultLimit` entries the Next walk reached; and builds a before-token with `paging.Token{Tool: "runs-before"}.Encode(started, id)` or `paging.Token{Tool: "rows-before"}.Encode(sourceID)` naming an entry no longer held.
