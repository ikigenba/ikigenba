# D04-store

The records: `internal/store`, which owns scrapes' tables in its SQLite database, `state/scrapes.db`: `runs`, one row per run a `scrape` call or a cron delivery started (decision 4), and `rows`, the rows of each run, addressed by the run and the record's `source_id` (decision 5), each until the prune removes its run, with `row_names` beside `rows`, each row's names for the `name` filter. It says what a run holds, the words its status and failure reason are spelled with, how a run is recorded, filled, finished and failed, how the comparison with the run before is counted, which reads the engine, the tools, the pages and the sibling read path have, how the prune decides what is past keeping, the errors every consumer tells apart, the one line every consumer answers when the database cannot be reached, and `db status`. Opening, migrating, transactions and the failure seam are appkit's `db`; `D01-layout-and-run-seam` resolves the path and declares the root package's `Migrations()`. It is gmail's store in shape, with a run in place of a transfer and its rows beside it.

## One database, one writer

scrapes is the only writer of its database, and the database is the only record of its runs and rows; nothing else is kept on disk (decision 1). `store.New` builds a store over a handle and opens or creates nothing. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds; a test proves the records that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`) answers every call with `ErrUnreachable` and changes nothing. `Config.Now` is the clock every stamp is read from, and `Config.Rand` the source run ids are drawn from; `Run` hands in `Process.Now` and `Process.Rand`, and the store has no default for either.

## Runs

A **run** is one walk of one scraper's source. Its **id** is `run_` and 16 lowercase hexadecimal digits, 8 bytes drawn from the random source when the run is recorded, drawn again when they are a run's id already. It keeps `scraper`, the registered name it walks; **started** and **finished**, each UTC to the second; the counts `rows`, `new`, `changed`, `unchanged` and `gone`, each 0 until the run is done; and its **starter**: for a `scrape` call, the caller's user id and email; for a cron delivery, the slug of the trigger whose fire was delivered (decision 4). It also keeps the request id it was started under, so the events of a run settled by the next start name the request that started it (`D07-events`), and, for a delivery, the bus event's id, the **delivery**, an internal column no tool, page or sibling answer carries: it is how a redelivered event is told from a new one (`D06-runs`).

Its **status** is one of three words: `running`, `done` and `failed`. A failed run has one of three **reasons**: `source`, `interrupted` and `store`; which failure is which is `D06-runs`'.

A run has four writes. `AddRun` records it `running`, stamping started and minting the id; it is refused `ErrBusy` while a run of the same scraper is `running`, so one run per scraper runs at a time and runs of different scrapers may overlap, and `ErrDelivered` when its delivery is one an existing run already carries, whatever that run's status. `PutRows` stores a batch of rows into a `running` run. `FinishRun` ends a `running` run `done` and writes its counts; `FailRun` ends a `running` run `failed` with a reason and removes its rows, in one write, so a run has rows only once it is done (decision 4). Of two calls racing on the same run one succeeds and the other is told it is no longer running (`ErrEnded`). Nothing moves a run back.

## Rows

A **row** is one record of one run, the envelope `D05-scrapers` declares (`source.Row`) with the raw record beside it. Within a run it is addressed by its `source_id`, unique within the run: a later `PutRows` of a row whose `source_id` the run already holds replaces that row, so a record a paging shift answers twice is kept once, as the later page spelled it (decision log D5). No row id is minted. The store writes the row's `run` and `scraper` from the run it is stored into, whatever the batch says, and keeps every other member as given, byte for byte for `facts` and `raw`.

Rows are read only from `done` runs: a `running` run's rows are a batch in progress and a `failed` run has none, so every row read of a run that is not `done` answers no row. `ListRowsAfter` is a done run's rows in ascending byte order of `source_id`, without `raw`, a window at a time: those whose `source_id` comes after a given one, or from the first when it is empty, at most a given number of them, and optionally only those one of whose `names` contains a given text, compared case-insensitively, `%`, `_` and `\` in that text meaning only themselves. It is how the `rows` tool and the run page read a page, as the suite's listing convention asks (`shape/`, Listing and Storage; appkit's D25, `appkit/paging`), so they hold no more than one page plus one row: a consumer asks for one more row than its page and learns from the extra one that more follow. Beside it sits the reversed window, `ListRowsBefore`, which the run page's backward step and its last window read (`D08-pages`): it mirrors the rows' own order, so it is at most a given number of the matched rows whose `source_id` comes before a given one in that order, nearest first, that is by `source_id` descending, every row from the end of the order when the given one is empty; the given `source_id` need not be any row's. The store knows nothing of tokens, page sizes or `next`; `GetRow` answers one row with `raw`; `EachRow` hands every row of a done run, with `raw`, in the same order, to a function, one at a time, for the sibling read path's stream.

## The comparison

When a run ends `done`, its counts are written against its **baseline**: the newest `done` run of the same scraper other than itself at that moment, newest meaning latest started and, among equal starts, greatest id (decision log D5). `rows` is the number of distinct rows the run holds. `new` counts its `source_id`s the baseline does not hold; `changed` those the baseline holds with another `digest`; `unchanged` those the baseline holds with the same `digest`; `gone` the baseline's `source_id`s the run does not hold. With no baseline, `new` is `rows` and the other three are 0.

## Reads and the prune

`GetRun` answers any run, whoever started it: runs belong to no one (decision 7). `ListRunsAfter` is the runs of one scraper, or of every scraper, in run order (newest first), a window at a time: those that come after a given position, a started time and an id, or from the first when the id is empty, and at most a given number of them. It is how the `runs` tool and the landing page read a page, as the suite's listing convention asks (`shape/`, Listing and Storage; appkit's D25, `appkit/paging`), so they hold no more than one page plus one row: a consumer asks for one more run than its page and learns from the extra one that more follow. The position's started time is a string, the run's `started` as the store keeps it, RFC 3339 in UTC to the second, so its byte order is time order; the store knows nothing of tokens, page sizes or `next`. Beside it sits the reversed window, `ListRunsBefore`, which the landing page's backward step and its last window read (`D08-pages`): it mirrors run order, so it is at most a given number of the runs that come before a given position in run order, that is newer than it, nearest first, that is oldest first, every run from the oldest when the position's id is empty; the position need not be any run's. `CurrentRun` is a scraper's newest `done` run, its **current** run; `RunningRun` its `running` run; `RunningRuns` every `running` run, which the start finishes `failed` with `interrupted`. `PruneRuns` removes, in one write, for each scraper, every `done` run beyond the newest keep count of its `done` runs and every `failed` run beyond the newest keep count of its `failed` runs, with their rows; a `running` run is neither counted nor removed (decision 11). A pruned run is gone from every read, its delivery with it. All lists are never nil.

## Errors

`ErrNotFound`, `ErrBusy`, `ErrDelivered` and `ErrEnded` are answers about the records. Every other error satisfies `errors.Is(err, ErrUnreachable)`; one the database refused because it was locked past appkit's busy timeout of five seconds (the driver's result code `SQLITE_BUSY`; `SQLITE_LOCKED` arises only from a lock within one connection, which the store never takes, so it is not designed), also satisfies `errors.Is(err, ErrLocked)`, so the engine (`D06-runs`) can tell a write worth trying again from one that is not without importing the driver. The store reads the code through the driver's exported `Code() int` on its error, by `errors.As` against an interface, so it imports no driver either, and every consumer answers it with `Unreachable` (a tool's `unavailable`, a page's unavailable answer, a delivery's `Fail`), never quoting the cause. A done context, a failing handle, a random source that fails and a write given a value no consumer sends all end there, the last changing nothing.

## `db status`

`scrapes db status` writes what appkit's `db.Status` writes for `state/scrapes.db` and the root package's `Migrations()`, and creates nothing.

## Recorded decisions

- The schema is four migrations. `0001_runs.sql`: `runs` (`id` primary key, `scraper`, `status`, `reason`, `started`, `finished`, `rows`, `new`, `changed`, `unchanged` and `gone` integers, `user_id`, `user_email`, `trigger`, `request_id`, `delivery`), with an index on `scraper` and `started`, and a unique index on `delivery` where it is not empty. `0002_rows.sql`: `rows` (`run`, `source_id`, `scraper`, `collected`, `digest`, `name`, `names` as a JSON array, `names_lower`, the lower-cased names joined, which the `name` filter read before `0004_row_names.sql` and no read uses since, `street`, `city`, `state`, `zip`, `county`, `lat`, `lon`, `people` as a JSON array, `facts` and `raw` as JSON text kept byte for byte), with a unique index on `run` and `source_id` and an index on `run` and `digest` (decision 11), the latter for the comparison. `0003_list_indexes.sql` adds the two indexes the runs window reads by, so both of its orders are index-backed; its whole text is `CREATE INDEX runs_scraper_started_id ON runs(scraper,started,id);` and `CREATE INDEX runs_started_id ON runs(started,id);`, one statement per line. It only adds indexes, so a release before it runs on the schema it leaves (the expand half of the root `AGENTS.md`'s rule); `runs_scraper_started` stays, and dropping it is a later release's contract step. `0004_row_names.sql` adds `row_names`, one row per name of each row, which the `name` filter reads; its whole text is `CREATE TABLE row_names ("run" TEXT NOT NULL, source_id TEXT NOT NULL, name TEXT NOT NULL, name_lower TEXT NOT NULL);`, `CREATE INDEX row_names_run_source ON row_names("run",source_id);` and `INSERT INTO row_names SELECT r."run",r.source_id,j.value,lower(j.value) FROM "rows" r,json_each(r.names) j;`, one statement per line, the last filling it from the rows already kept (observed with `sqlite3` and appkit's SQLite driver: a row whose `names` is `[]` gets no entry). It only adds, so a release before it runs on the schema it leaves; `names` and `names_lower` stay, and dropping `names_lower` is a later release's contract step. Times are RFC 3339 UTC to the second; an empty `finished` is one not yet set. No requirement states the schema, since a test proves the records through the store; the sandbox check, which sets a run to `running` by hand, writes these columns. `rows`, `new`, `trigger` and the other SQL keywords as column names are quoted in the migrations.
- The runs window is served by four statements, chosen by whether a scraper is given and whether a position is: `SELECT ... FROM runs WHERE scraper=? AND (started,id)<(?,?) ORDER BY started DESC,id DESC LIMIT ?`, the same without `scraper=? AND` for every scraper, and each without the row-value condition for the first window. One statement with `(?='' OR scraper=?)` would read the same rows, but SQLite plans a statement before its parameters are bound and cannot use `runs_scraper_started_id` for an equality behind an `OR`, nor a range behind `(?='' OR ...)`, so a deep page would scan from the newest run. No requirement states the statements; a test proves the windows through the store.
- The reversed runs window is four statements of the same shape: `SELECT ... FROM runs WHERE scraper=? AND (started,id)>(?,?) ORDER BY started,id LIMIT ?`, the same without `scraper=? AND`, and each without the row-value condition for the window from the oldest run, which `last` reads. Observed with `sqlite3` over the four migrations' schema and 2,000 runs of two scrapers, with and without `ANALYZE`: `EXPLAIN QUERY PLAN` gives `SEARCH runs USING INDEX runs_started_id ((started,id)>(?,?))`, `SEARCH runs USING INDEX runs_scraper_started_id (scraper=? AND (started,id)>(?,?))`, `SCAN runs USING INDEX runs_started_id` and `SEARCH runs USING INDEX runs_scraper_started_id (scraper=?)`, with no `USE TEMP B-TREE FOR ORDER BY`. The indexes `0003_list_indexes.sql` added serve both directions, so no migration is needed.
- The reversed rows window is two statements: `SELECT ... FROM "rows" r WHERE r."run"=? AND r.source_id<? ORDER BY r.source_id DESC LIMIT ?`, and the same without `AND r.source_id<?` for the window from the end, since `source_id<''` holds for no row; each with, when a `name` is given, the `EXISTS` of the forward window. Observed with `sqlite3` over 10,000 rows of one run: `SEARCH r USING INDEX sqlite_autoindex_rows_1 (run=? AND source_id<?)` and `(run=?)`, and for the filter `SEARCH n USING INDEX row_names_run_source (run=? AND source_id=?)`, with no temp B-tree. The unique `(run, source_id)` index serves both directions, so no migration is needed.
- The reversed windows keep the forward windows' parameters, a scraper for runs and a `name` for rows, though the pages pass neither: a store read is one shape in both directions, and the statements cost nothing more.
- The rows window is one statement, `SELECT ... FROM "rows" r WHERE r."run"=? AND r.source_id>? ORDER BY r.source_id LIMIT ?`, with, when a `name` is given, `AND EXISTS (SELECT 1 FROM row_names n WHERE n."run"=r."run" AND n.source_id=r.source_id AND instr(n.name_lower,?)>0)`. An empty `after` needs no statement of its own: every stored `source_id` is non-empty, so `source_id>''` holds for all of them. Observed with appkit's SQLite driver over 10,000 rows of one run, with and without the filter, at the first window and a deep one: `EXPLAIN QUERY PLAN` gives `SEARCH r USING INDEX sqlite_autoindex_rows_1 (run=? AND source_id>?)` and, for the filter, `SEARCH n EXISTS USING INDEX row_names_run_source (run=? AND source_id=?)`, with no `USE TEMP B-TREE FOR ORDER BY`; a page reads in about 0.15 ms unfiltered, 0.3 ms with a filter many rows match, and 17 ms with one that matches few or none, which walks the run's rows. `ListRowsAfter` no longer reads the whole run, as `EachRow` does.
- The `name` filter compares `name_lower`, written by `PutRows` as `strings.ToLower` of each name, with `strings.ToLower` of the given text, by `instr`, a plain substring test: `%`, `_` and `\` need no escaping and match only themselves. `LIKE` with an `ESCAPE` would do the same but refuses a pattern longer than 50,000 bytes (observed: `LIKE or GLOB pattern too complex`), which would turn a long `name` into `unavailable`. The lowering is Go's, not SQLite's `lower()`, which folds only ASCII letters, so the contract is stated per name as `strings.ToLower` compares (decision log D5).
- No index on `row_names("run",name_lower)`: a substring test cannot seek on it, and with it added and `ANALYZE` run the plans above were unchanged and the timings moved only within noise.
- `PutRows` deletes a row's `row_names` entries and inserts its current names in the same transaction as the row, so a replaced row is matched by the names it was last stored with; `FailRun` and `PruneRuns` delete a run's `row_names` with its rows. The backfill lowers with SQLite's `lower()`, so a name kept before `0004_row_names.sql` with a non-ASCII capital (`CAFÉ`) is matched only by its ASCII letters until its run is pruned, within `SCRAPE_KEEP_RUNS` new runs. A release before it, running beside this one during a rolling restart or after a rollback, ignores `row_names`: rows it stores get no entries, or keep stale ones when it replaces a row, and its prune leaves the entries of the runs it removes, which no read reaches since every read joins `rows`. Each heals as its run is pruned; a later migration may refill `row_names` from `names` if ever needed.
- The delivery is a column of `runs`, not a table of its own, and is forgotten with its run at the prune (decision log D5): the events app's retries end long before a run is pruned, and a delivery is the one place it is read.
- Busy and delivered are refused by `AddRun` itself, in its write, so two starts racing (a tool call and a delivery, or two attempts of one delivery) cannot both record a run.
- Rows are written per batch, one `PutRows` per page the scraper hands over, each in one transaction (decision log D5): nothing holds more than a page.
- The counts are computed by `FinishRun` in the same write that marks the run `done`, against the baseline as it is at that moment, so a run and its counts never disagree.
- `ListRowsAfter` answers no `raw`: the `rows` tool and the run page show the envelope only (decision 7), and a page of 25 raw records is 60 KB nobody reads.
- A run that is not `done` answers no rows rather than `ErrNotFound`, so the reads tell an unknown run (`ErrNotFound`) from a known one with nothing to show.
- `source_id` order is byte order: a source id is text, and FMCSA's numeric dot numbers sort as text there. A numeric order would bind the store to one source's ids.
- A write given a value no consumer sends answers an error matching `ErrUnreachable` and changes nothing, as in gmail; there is no `ErrInvalid`. The id redraw is bounded at 8 candidates, as in gmail.

## Consumer tasks

The engine (`D06-runs`), `c` the caller, records a tool start with `r, err := st.AddRun(ctx, store.Run{Scraper: "fmcsa", UserID: c.UserID, UserEmail: c.Email, RequestID: c.RequestID})`, `store.ErrBusy` answering `busy`; a delivery with `st.AddRun(ctx, store.Run{Scraper: name, Trigger: slug, UserID: c.UserID, RequestID: c.RequestID, Delivery: d.Event.ID})`, `store.ErrDelivered` and `store.ErrBusy` answering `Skip`. The work hands each page to `st.PutRows(ctx, r.ID, rows)` and ends with `st.FinishRun(ctx, r.ID)` or `st.FailRun(ctx, r.ID, store.ReasonSource)`. The start calls `st.RunningRuns(ctx)`; the sweep `st.PruneRuns(ctx, s.KeepRuns)`. The tools and pages call `st.ListRunsAfter(ctx, "", "", "", 26)` for a first page and `st.ListRunsAfter(ctx, "fmcsa", "2026-10-05T09:00:07Z", id, 26)` for the page after a run, `st.GetRun`, `st.CurrentRun(ctx, "fmcsa")`, `st.RunningRun`, `st.ListRowsAfter(ctx, id, "trucking", "", 26)` for a first page and `st.ListRowsAfter(ctx, id, "trucking", "1023916", 26)` for the page after a row; the pages call `st.ListRunsBefore(ctx, "", "2026-10-05T09:00:07Z", id, 26)` for the window before a run and `st.ListRunsBefore(ctx, "", "", "", 26)` for the last, `st.ListRowsBefore(ctx, id, "", "1023916", 26)` for the window before a row and `st.ListRowsBefore(ctx, id, "", "", 26)` for the last, each reversing what it answers; and `st.GetRow(ctx, id, "1023916")`; the sibling read path calls `st.EachRow(ctx, id, func(r source.Row) error { return enc.Encode(r) })`. `store.ErrNotFound` answers not found and `store.ErrUnreachable` `store.Unreachable`. A test opens its own database with `db.Open` and the root package's `Migrations()`, builds `store.New(d, store.Config{Now: clock, Rand: rnd})`, records runs of two scrapers, fills, finishes and fails them, flips `d.SetFailing(true)`, and reopens the path to prove what persists.
