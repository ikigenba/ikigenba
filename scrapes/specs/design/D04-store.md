# D04-store

The records: `internal/store`, which keeps scrapes' runs and their rows in two kinds of storage. The **catalog**, the SQLite database `state/scrapes.db`, holds `runs`, one row per run a `scrape` call or a cron delivery started (decision 4). A done run's rows are in the run's own **file**, a SQLite file in the **runs directory** named the run's id followed by `.db`, written once, in key order, when the run is loaded, and read for the run's life, addressed by the record's `source_id` (decision 5). It says what a run holds, the words its status and failure reason are spelled with, how a run is recorded, how its rows are collected and loaded into its file, how it is finished and failed, how the comparison with the run before is counted, which reads the engine, the tools, the pages and the sibling read path have, how the prune and the start's tidy remove files, the errors every consumer tells apart, the lines every consumer answers when the catalog cannot be reached or a done run's file is gone, and `db status`. Opening, migrating, transactions and the failure seam of the catalog are appkit's `db`, and so are the two opens a run file is built and read through, the bulk open and the immutable open (appkit's D26); `D01-layout-and-run-seam` resolves the paths and declares the root package's `Migrations()`; `D06-runs` drives each build and paces it. It is gmail's store in shape, with a run in place of a transfer and its rows in a file beside it.

## The catalog and the run files

scrapes is the only writer of its catalog and of its runs directory, `<Dir>/runs`, which sits beside `state/`, not under it, so the snapshot and the replica take the catalog alone (`D01-layout-and-run-seam`). The catalog is the only record of the runs; a run's file is the only record of its rows, and is regenerable from the source. `store.New` builds a store over a catalog handle and opens or creates nothing; `Config.Runs` names the runs directory, which `cli.Run` sets to `filepath.Join(Dir, "runs")`, and which the store creates only when a build first writes into it. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path, with the same runs directory, holds; a test proves the records that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`) answers every catalog call with `ErrUnreachable` and changes nothing. `Config.Now` is the clock every stamp is read from, and the clock each step of a build is timed by; `Config.Rand` the source run ids are drawn from; `Run` hands in `Process.Now` and `Process.Rand`, and the store has no default for either. `Config.ChunkBytes` and `Config.LoadRows` size a build's chunks and load transactions; `cli.Run` leaves both 0, which means `DefaultChunkBytes` (16 MiB) and `DefaultLoadRows` (5,000), and a test sets them small to see many steps.

## Runs

A **run** is one walk of one scraper's source. Its **id** is `run_` and 16 lowercase hexadecimal digits, 8 bytes drawn from the random source when the run is recorded, drawn again when they are a run's id already. It keeps `scraper`, the registered name it walks; **started** and **finished**, each UTC to the second; the counts `rows`, `new`, `changed`, `unchanged` and `gone`, each 0 until the run is done; and its **starter**: for a `scrape` call, the caller's user id and email; for a cron delivery, the slug of the trigger whose fire was delivered (decision 4). It also keeps the request id it was started under, so the events of a run settled by the next start name the request that started it (`D07-events`), and, for a delivery, the bus event's id, the **delivery**, an internal column no tool, page or sibling answer carries: it is how a redelivered event is told from a new one (`D06-runs`).

Its **status** is one of three words: `running`, `done` and `failed`. A failed run has one of three **reasons**: `source`, `interrupted` and `store`; which failure is which is `D06-runs`'.

A run has three catalog writes. `AddRun` records it `running`, stamping started and minting the id; it is refused `ErrBusy` while a run of the same scraper is `running`, so one run per scraper runs at a time and runs of different scrapers may overlap, and `ErrDelivered` when its delivery is one an existing run already carries, whatever that run's status. `FinishRun` ends a `running` run `done` with the counts its load answered, and is refused `ErrMissing` unless the run's file is in place, so a run is `done` only once its rows can be read. `FailRun` ends a `running` run `failed` with a reason and touches no file. Of two calls racing on the same run one succeeds and the other is told it is no longer running (`ErrEnded`). Nothing moves a run back.

## Building a run's file

A run's rows reach its file in two phases, each a sequence of **steps**, so that the engine can pace the disk (decisions document, decisions 3, 4 and 7). `Collect` of a `running` run answers a **collection**. In the **collect** phase the walk hands each page to `Add`, which encodes its rows into a buffer; each time the buffer holds `ChunkBytes` of encoded rows they are sorted and written as one **chunk**, a temporary file, and `Seal` writes what remains as the last. In the **load** phase `Load` merges the chunks, one row of each in memory, keeping for each `source_id` the row that arrived last, and inserts the rows in `source_id` order into a new file built through the bulk open, at most `LoadRows` rows per transaction; once the last is written the file is synced, renamed into place as the run's file and its directory synced. `Discard` deletes every file that collection made but a file its `Load` put in place, and touches nothing else, so a second collection of the same run, which the engine never opens, keeps its own files; the engine calls it whatever the build's outcome. `Load` writes no record: its counts reach the catalog only through `FinishRun`, and a `Load` of a run no longer `running` is refused as `FinishRun` would be.

Each chunk written and each load transaction is a step: once it is written the `Step` the engine handed in is told the bytes it wrote, a chunk's size or the file's growth, and how long the write took by `Config.Now`, and may pause before it returns (`D06-runs`); an error from it ends the call. The bytes of a load's steps sum to the size of the file it put in place.

Every file a build makes lies directly in the runs directory and is named the run's id followed by `.`, so a listing tells every run's files apart; nothing is at the run's file until `Load` succeeds, and after it nothing of the run but its file remains. A collection that failed answers every later call `ErrUnreachable`, and is discarded. `Add` refuses a row with an empty `source_id` and keeps nothing of that call; a call out of order (`Add` or `Seal` after `Seal`, `Load` before `Seal` or twice, anything after `Discard`) is refused and changes nothing.

## Rows

A **row** is one record of one run, the envelope `D05-scrapers` declares (`source.Row`) with the raw record beside it. Within a run it is addressed by its `source_id`, unique within the run: a row added again with a `source_id` the run already holds replaces the earlier, so a record a paging shift answers twice is kept once, as the later page spelled it (decision log D5). No row id is minted. The store writes the row's `run` and `scraper` from the run it is collected for, whatever the page says, and keeps every other member as given, byte for byte for `facts` and `raw`.

Rows are read only from `done` runs: a `running` run's rows are a build in progress and a `failed` run has none, so every row read of a run that is not `done` answers no row. Each read opens the run's file through the immutable open, one handle per call, and closes it when the call ends; a stream keeps its handle for its whole life, so a prune that deletes the file meanwhile does not cut it. A read of a `done` run whose file is gone answers `ErrMissing`, and one whose file is there but cannot be read `ErrUnreachable`. `ListRowsAfter` is a done run's rows in ascending byte order of `source_id`, without `raw`, a window at a time: those whose `source_id` comes after a given one, or from the first when it is empty, at most a given number of them, and optionally only those one of whose `names` contains a given text, compared case-insensitively, `%`, `_` and `\` in that text meaning only themselves. It is how the `rows` tool and the run page read a page, as the suite's listing convention asks (`shape/`, Listing and Storage; appkit's D25, `appkit/paging`), so they hold no more than one page plus one row: a consumer asks for one more row than its page and learns from the extra one that more follow. Beside it sits the reversed window, `ListRowsBefore`, which the run page's backward step and its last window read (`D08-pages`): it mirrors the rows' own order, so it is at most a given number of the matched rows whose `source_id` comes before a given one in that order, nearest first, that is by `source_id` descending, every row from the end of the order when the given one is empty; the given `source_id` need not be any row's. The store knows nothing of tokens, page sizes or `next`; `GetRow` answers one row with `raw`; `EachRow` hands every row of a done run, with `raw`, in the same order, to a function, one at a time, for the sibling read path's stream.

## The comparison

A run's counts are counted by its `Load` against its **compared run**: the newest `done` run of the same scraper whose file opens at that moment, opening meaning a regular file, not a symbolic link, that the store opens as a run file and whose rows it reads through to the end without error, newest meaning first in run order, latest started and, among equal starts, greatest id (decision log D5). The counting decides the compared run before it counts against it, so a file that fails partway through being read is passed over like any other that does not open, and never fails the load. A newer `done` run whose file is gone, or is there but cannot be opened or read through, whether empty, headerless, a header over garbage, another SQLite database or failing partway, is passed over, since its rows cannot be read; the load neither fails because of it nor deletes it, and with no older `done` run whose file opens every row is new and none gone. `rows` is the number of distinct rows the run holds. `new` counts its `source_id`s the compared run does not hold; `changed` those it holds with another `digest`; `unchanged` those it holds with the same `digest`; `gone` the compared run's `source_id`s the run does not hold. With no compared run, `new` is `rows` and the other three are 0. The engine hands the counts to `FinishRun`, which refuses counts that do not add up.

## Runs, the prune and the tidy

`GetRun` answers any run, whoever started it: runs belong to no one (decision 7). `ListRunsAfter` is the runs of one scraper, or of every scraper, in run order (newest first), a window at a time: those that come after a given position, a started time and an id, or from the first when the id is empty, and at most a given number of them. It is how the `runs` tool and the landing page read a page, as the suite's listing convention asks (`shape/`, Listing and Storage; appkit's D25, `appkit/paging`), so they hold no more than one page plus one row: a consumer asks for one more run than its page and learns from the extra one that more follow. The position's started time is a string, the run's `started` as the store keeps it, RFC 3339 in UTC to the second, so its byte order is time order; the store knows nothing of tokens, page sizes or `next`. Beside it sits the reversed window, `ListRunsBefore`, which the landing page's backward step and its last window read (`D08-pages`): it mirrors run order, so it is at most a given number of the runs that come before a given position in run order, that is newer than it, nearest first, that is oldest first, every run from the oldest when the position's id is empty; the position need not be any run's. `CurrentRun` is a scraper's newest `done` run, its **current** run, whether or not its file is in place; `RunningRun` its `running` run; `RunningRuns` every `running` run, which the start finishes `failed` with `interrupted`. These reads answer from the catalog alone and open no file.

`PruneRuns` removes, in one write, for each scraper, every `done` run beyond the newest keep count of its `done` runs and every `failed` run beyond the newest keep count of its `failed` runs; a `running` run is neither counted nor removed (decision 11). Once the records are gone it deletes the removed runs' files; when the write fails it deletes none. A pruned run is gone from every read, its delivery with it. `TidyFiles`, which the start calls before it serves (`D06-runs`), deletes everything in the runs directory but the files of `done` runs: a dead process's chunks and half-built files, the files of runs not `done`, files of runs the catalog no longer holds, and any name scrapes did not make. All lists are never nil.

## Errors

`ErrNotFound`, `ErrBusy`, `ErrDelivered`, `ErrEnded` and `ErrMissing` are answers about the records; `ErrMissing` is a done run whose file is not in place, which the pages, the tools and the sibling path answer apart from an outage, with `Missing` where the answer is a line. Every other error satisfies `errors.Is(err, ErrUnreachable)`; one the catalog refused because it was locked past appkit's busy timeout of five seconds (the driver's result code `SQLITE_BUSY`; `SQLITE_LOCKED` arises only from a lock within one connection, which the store never takes, so it is not designed), also satisfies `errors.Is(err, ErrLocked)`, so the engine (`D06-runs`) can tell a write worth trying again from one that is not without importing the driver. The store reads the code through the driver's exported `Code() int` on its error, by `errors.As` against an interface, so it imports no driver either, and every consumer answers it with `Unreachable` (a tool's `unavailable`, a page's unavailable answer, a delivery's `Fail`), never quoting the cause. A done context, a failing handle, a random source that fails, a run file that cannot be written or read, a step that refused, and a call given a value no consumer sends all end there, the last changing nothing.

## `db status`

`scrapes db status` writes what appkit's `db.Status` writes for `state/scrapes.db` and the root package's `Migrations()`, and creates nothing.

## Recorded decisions

- The catalog's schema is four migrations. `0001_runs.sql`: `runs` (`id` primary key, `scraper`, `status`, `reason`, `started`, `finished`, `rows`, `new`, `changed`, `unchanged` and `gone` integers, `user_id`, `user_email`, `trigger`, `request_id`, `delivery`), with an index on `scraper` and `started`, and a unique index on `delivery` where it is not empty. `0002_rows.sql`: `rows`, the rows of each run before run files. `0003_list_indexes.sql` adds the two indexes the runs window reads by, so both of its orders are index-backed; its whole text is `CREATE INDEX runs_scraper_started_id ON runs(scraper,started,id);` and `CREATE INDEX runs_started_id ON runs(started,id);`, one statement per line; `runs_scraper_started` stays, and dropping it is a later release's contract step. `0004_row_names.sql` adds `row_names`, each row's names for the old `name` filter. Times are RFC 3339 UTC to the second; an empty `finished` is one not yet set. No requirement states the schema, since a test proves the records through the store; the sandbox check, which sets a run to `running` by hand, writes these columns. `rows`, `new`, `trigger` and the other SQL keywords as column names are quoted in the migrations.
- The catalog's `rows` and `row_names` stay, neither written, read nor dropped, and this design adds no migration: the expand half of the root `AGENTS.md`'s rule. This release stops using them and the next drops them, so the release before this one, running beside it during a rolling restart or after a rollback, still runs on the schema this one leaves. Each sees the other's runs partly: the release before reads its rows from the catalog, so it sees this release's `done` runs with no rows; this release reads rows from run files, so it sees the release before's `done` runs as missing (`ErrMissing`), and passes them over as compared runs. That is accepted: on `us` the catalog is deleted before this release starts (decisions document, sequence step 3), and dev databases are reset. Rows the release before kept stay on disk until the next release drops the tables, since this one deletes no row.
- No row is ever deleted. Cleanup is a file delete: a failed build's files are discarded, a pruned run's file is deleted, and the start's tidy deletes the rest (decisions document, principle 4).
- The runs window is served by four statements, chosen by whether a scraper is given and whether a position is: `SELECT ... FROM runs WHERE scraper=? AND (started,id)<(?,?) ORDER BY started DESC,id DESC LIMIT ?`, the same without `scraper=? AND` for every scraper, and each without the row-value condition for the first window. One statement with `(?='' OR scraper=?)` would read the same rows, but SQLite plans a statement before its parameters are bound and cannot use `runs_scraper_started_id` for an equality behind an `OR`, nor a range behind `(?='' OR ...)`, so a deep page would scan from the newest run. No requirement states the statements; a test proves the windows through the store.
- The reversed runs window is four statements of the same shape: `SELECT ... FROM runs WHERE scraper=? AND (started,id)>(?,?) ORDER BY started,id LIMIT ?`, the same without `scraper=? AND`, and each without the row-value condition for the window from the oldest run, which `last` reads. Observed with `sqlite3` over the four migrations' schema and 2,000 runs of two scrapers, with and without `ANALYZE`: `EXPLAIN QUERY PLAN` gives `SEARCH runs USING INDEX runs_started_id ((started,id)>(?,?))`, `SEARCH runs USING INDEX runs_scraper_started_id (scraper=? AND (started,id)>(?,?))`, `SCAN runs USING INDEX runs_started_id` and `SEARCH runs USING INDEX runs_scraper_started_id (scraper=?)`, with no `USE TEMP B-TREE FOR ORDER BY`. The indexes `0003_list_indexes.sql` added serve both directions.
- A run file's schema is the loader's, created through the bulk open with no migrations: `rows`, `WITHOUT ROWID` with `source_id` its primary key, holding the envelope's members as the catalog's `rows` did (`scraper`, `run`, `collected`, `digest`, `name`, `names` and `people` as JSON arrays, `street`, `city`, `state`, `zip`, `county`, `lat`, `lon`, and `facts` and `raw` as text kept byte for byte); `rows_source_digest`, a covering index on `rows(source_id, digest)`, the narrow tree the comparison reads; and `names`, `WITHOUT ROWID` with the primary key `(source_id, seq)`, one row per name holding `name_lower`, for the `name` filter. No requirement states it: a test proves the rows through the store. A file is read only by the release that wrote it or a later one; a later release that changes the schema reads both or names the change.
- The run file's indexes are created before its inserts, a departure from the decisions document's "created after the load": the rows go in in `source_id` order, so every tree, the table, the covering index and `names`, only appends, and no index build sorts through temporary files afterwards. A consumer cannot see the difference.
- The rows windows on a run file are one statement each way: `SELECT ... FROM rows r WHERE r.source_id>? ORDER BY r.source_id LIMIT ?` and `SELECT ... FROM rows r WHERE r.source_id<? ORDER BY r.source_id DESC LIMIT ?`, the latter without its condition for the window from the end, since `source_id<''` holds for no row; each with, when a `name` is given, `AND EXISTS (SELECT 1 FROM names n WHERE n.source_id=r.source_id AND instr(n.name_lower,?)>0)`. An empty `after` needs no statement of its own: every stored `source_id` is non-empty. Observed with `sqlite3` over that schema and 10,000 rows: `SEARCH r USING PRIMARY KEY (source_id>?)` and `(source_id<?)`, the filter `SEARCH n USING PRIMARY KEY (source_id=?)`, and the comparison's ordered read `SCAN rows USING COVERING INDEX rows_source_digest`, with no temp B-tree.
- The `name` filter compares `name_lower`, written by the load as `strings.ToLower` of each name, with `strings.ToLower` of the given text, by `instr`, a plain substring test: `%`, `_` and `\` need no escaping and match only themselves. `LIKE` with an `ESCAPE` would do the same but refuses a pattern longer than 50,000 bytes (observed: `LIKE or GLOB pattern too complex`), which would turn a long `name` into `unavailable`. The lowering is Go's, not SQLite's `lower()`, which folds only ASCII letters, so the contract is stated per name as `strings.ToLower` compares (decision log D5). No index on `name_lower`: a substring test cannot seek on it.
- A chunk is the buffer's rows sorted by `source_id` and then by arrival, compressed, as the decisions document says; the codec is the store's own and keeps `facts` and `raw` byte for byte (as strings, since `encoding/json` compacts a `json.RawMessage` it writes), `collected` to the second, and each row's arrival sequence across `Add` calls, so the merge keeps the row that arrived last whichever chunk holds it. A collect step's bytes are the chunk's size on disk; a load step's are the file's growth, which sum to its size.
- `Load` builds the file under a temporary name, closes it, syncs it, renames it to the run's file and syncs the runs directory, so the file is whole on disk before the run can be recorded `done`, and a crash leaves at most a temporary for the tidy. The syncs are not observable in a test; that the file is in place when `Load` returns is.
- `FinishRun` takes the counts and refuses without the file: the counts are computed in the load, during the merge (decisions document, decision 5), and refusing makes "file in place, then `done`" the store's guarantee rather than the engine's habit. It checks the counts add up, so every `done` run keeps `rows` equal to `new` plus `changed` plus `unchanged`.
- The compared run passes over a newer `done` run whose file is gone (decisions document, decision 5), and one whose file is there but cannot be opened or read, alike: either way its rows cannot be read, so the next one back is the best comparison there is. A broken compared file does not fail the load: the run's own rows are sound, and failing it would fail every later run of the scraper until someone removed the file. The load leaves the broken file where it is; the reads answer it as unreachable and the prune retires it in time.
- The prune deletes the records first and the files after: a crash between leaves an orphan file the next start's tidy deletes, where the other order would leave a `done` run with no file, which reads as missing and is passed over as a compared run. A file it cannot delete is left for the tidy, silently, and when the write fails no file is touched (`D06-runs`' silent prune).
- The tidy deletes every entry in the runs directory but `done` runs' files, foreign names included: scrapes owns the directory, and anything else there is a leftover. It runs only at the start, before any build; called during a build it would delete that build's files.
- The runs directory is created at a build's first write, not at the start: the start gains no failure of its own, and a fresh `Dir` at ready still holds only `state` (`D01-layout-and-run-seam`). It and any directory above it the store creates are its owner's alone.
- A read opens the run's file through the immutable open, which takes no lock and creates nothing beside the file, one handle per call. `EachRow` keeps its handle until the stream ends, so a prune deleting the file meanwhile does not cut it: Linux keeps an open file's data until the last handle closes.
- `ErrMissing` does not match `ErrUnreachable`: a done run whose file is gone stays gone until a new run, while an outage passes, and the pages, the tools and the sibling path answer them apart (`D03-serve`, `D08-pages`, `D10-tools`). `Missing` is one line for the row page and the sibling path.
- `Config.ChunkBytes` and `Config.LoadRows` are test seams, as the scrapers' `BaseURL` is: `cli.Run` leaves them 0.
- `shape/`'s Storage entry is kept in substance and departed from in place: a run's rows are filtered, ordered and windowed by the database, with `WHERE`, `ORDER BY` and `LIMIT` on a primary key, holding no more than one page plus one row, but the database is the run's own write-once file, opened read-only per request, not the app's database. Why: writing each run's rows once, sequentially, into its own file keeps the replicated catalog small and makes cleanup a file delete (decisions document, principles 2, 4 and 5). The Listing entry is kept: tokens and windows are unchanged.
- The delivery is a column of `runs`, not a table of its own, and is forgotten with its run at the prune (decision log D5): the events app's retries end long before a run is pruned, and a delivery is the one place it is read.
- Busy and delivered are refused by `AddRun` itself, in its write, so two starts racing (a tool call and a delivery, or two attempts of one delivery) cannot both record a run.
- `ListRowsAfter` answers no `raw`: the `rows` tool and the run page show the envelope only (decision 7), and a page of 25 raw records is 60 KB nobody reads.
- A run that is not `done` answers no rows rather than `ErrNotFound`, so the reads tell an unknown run (`ErrNotFound`) from a known one with nothing to show.
- `source_id` order is byte order: a source id is text, and FMCSA's numeric dot numbers sort as text there. A numeric order would bind the store to one source's ids.
- A call given a value no consumer sends answers an error matching `ErrUnreachable` and changes nothing, as in gmail; there is no `ErrInvalid`. The id redraw is bounded at 8 candidates, as in gmail.

## Consumer tasks

The engine (`D06-runs`), `c` the caller, records a tool start with `r, err := st.AddRun(ctx, store.Run{Scraper: "fmcsa", UserID: c.UserID, UserEmail: c.Email, RequestID: c.RequestID})`, `store.ErrBusy` answering `busy`; a delivery with `st.AddRun(ctx, store.Run{Scraper: name, Trigger: slug, UserID: c.UserID, RequestID: c.RequestID, Delivery: d.Event.ID})`, `store.ErrDelivered` and `store.ErrBusy` answering `Skip`. The work opens the build with `col, err := st.Collect(ctx, r.ID, phase.Step)`, hands each page to `col.Add(ctx, rows)`, calls `col.Seal(ctx)`, then, holding the load lock, `counts, err := col.Load(ctx, phase2.Step)`, and ends with `st.FinishRun(ctx, r.ID, counts)` or `st.FailRun(ctx, r.ID, store.ReasonStore)`, calling `col.Discard()` whatever the outcome. The start calls `st.RunningRuns(ctx)` and `st.TidyFiles(ctx)`; the sweep `st.PruneRuns(ctx, s.KeepRuns)`. The tools and pages call `st.ListRunsAfter(ctx, "", "", "", 26)` for a first page and `st.ListRunsAfter(ctx, "fmcsa", "2026-10-05T09:00:07Z", id, 26)` for the page after a run, `st.GetRun`, `st.CurrentRun(ctx, "fmcsa")`, `st.RunningRun`, `st.ListRowsAfter(ctx, id, "trucking", "", 26)` for a first page and `st.ListRowsAfter(ctx, id, "trucking", "1023916", 26)` for the page after a row; the pages call `st.ListRunsBefore(ctx, "", "2026-10-05T09:00:07Z", id, 26)` for the window before a run and `st.ListRunsBefore(ctx, "", "", "", 26)` for the last, `st.ListRowsBefore(ctx, id, "", "1023916", 26)` for the window before a row and `st.ListRowsBefore(ctx, id, "", "", 26)` for the last, each reversing what it answers; and `st.GetRow(ctx, id, "1023916")`; the sibling read path calls `st.EachRow(ctx, id, func(r source.Row) error { return enc.Encode(r) })`. `store.ErrNotFound` answers not found, `store.ErrMissing` the missing answer each consumer's design names, and `store.ErrUnreachable` `store.Unreachable`. A test opens its own database with `db.Open` and the root package's `Migrations()`, builds `store.New(d, store.Config{Now: clock, Rand: rnd, Runs: filepath.Join(tmp, "runs"), ChunkBytes: 1, LoadRows: 2})`, records runs of two scrapers, collects, loads, finishes and fails them, deletes or overwrites a done run's file, puts a regular file where the runs directory belongs or a directory where a run's file belongs, flips `d.SetFailing(true)`, and reopens the path to prove what persists.
