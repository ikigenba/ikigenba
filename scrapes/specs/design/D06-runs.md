# D06-runs

The engine: `internal/runs`, the one place a run is started, worked, finished, settled at start and abandoned at the stop, and the place a cron fire delivered on the bus becomes a run. A `scrape` call (`D10-tools`) or a delivery hands the engine a scraper's name; the engine records the run `running` (`D04-store`), tells `scrape.started` (`D07-events`), answers at once, and builds the run in the background: it adds the rows the scraper hands over into the run's build, then loads them into the run's own file under `<Dir>/runs` (the store's run files, `D04-store`). When the build ends the run is finished `done` with the counts its load computed, its file in place, or `failed` with its reason and no file of it left, and `scrape.finished` is told. It is gmail's record-then-run shape without a queue: one run per scraper at a time, refused or skipped when one is running, runs of different scrapers walking side by side and loading one at a time. It also declares `internal/pace`, the write budget, latency backoff and pressure pause every phase of a build is paced with, the run record's JSON, which the tools and the sibling read path answer, and every refusal word the tools answer.

`D01-layout-and-run-seam` declares the run seam, the settings (the write budget and the pressure limit among them), the pressure file the binary passes and `cli.SweepInterval`; `D04-store` the records, their words, the run files, a build (`store.Build`) and what its walk and load write, the counts, the start-up tidy and the prune; `D05-scrapers` the registry, the `Scraper` interface and the FMCSA, PPP, MN parcels and Form 5500 scrapers; `D07-events` the events, the trail's phase events, what `/declarations` answers, and the identity and cause each event carries; `D09-trail` the closed set of event names; `D10-tools` the tools and the sentences a refusal word is shown with; `D03-serve` builds the engine, mounts the delivery and calls `Recover` and `Drain` in its start and stop.

## Starting a run

`Start` takes the caller and a scraper's name. A name the registry does not hold is refused `not_found`; once the drain has begun, `stopping`; a scraper with a run `running`, `busy` (the store refuses the record, so a tool call and a delivery racing for one scraper cannot both win); and the database failing is an error matching `store.ErrUnreachable`, which the tool answers `unavailable` (decision 7). Otherwise the run is recorded with the caller as its starter, `scrape.started` is told, the work begins in a goroutine, and `Start` answers the record, `running`, without waiting for the source: the MCP gateway gives a tool call fifty seconds and a full FMCSA walk takes minutes.

## The work

A run's work runs in a goroutine, as the starter: under `identity.NewContext(context.WithoutCancel(ctx), caller)`, `ctx` being the starting call's, so the work outlives the call but keeps its values, the event cause among them, and every `source.called` it records names the starter and the starting request (gmail's precedent). It is cancelled by the drain and by nothing else. A run's work is one build in two phases.

- **Walk.** The engine opens the run's build with the store's `Build` and asks the scraper to walk its source, under a context that carries the build's `Spool` (`source.WithSpool`, `D05-scrapers`), so a scraper that must hold a source's file whole, as the Form 5500 scraper holds each zip, holds it beside the run's temporaries, named as they are; each batch the scraper hands over is added to the build as it comes, so only one source page and the build's buffer are held at a time. The walk never writes into anything a reader sees: the build keeps its rows in temporaries named for the run beside the run files, and nothing sits at the run's `<id>.db` while it walks. When the walk returns nil the build is sealed, and the walk phase ends.
- **Load.** The sealed build is loaded: the store merges the temporaries, keeps the last row added per source id, writes the run's file in key order, counts the run against its compared run's file in the same pass, and puts the file in place at `<id>.db`. Only one run of the engine loads at a time, whatever its scraper; a run whose walk has returned waits, `running`, for the load before it to end.

Its end is one of four:

- the walk returns nil and the build is sealed and loaded: the run is finished `done` with the counts the load computed, its file already in place, and only then is `scrape.finished` told;
- the drain cancelled the work before the load returned, whether the walk was still running, the run was waiting for another's load, or its build was paused: `failed` with `interrupted`;
- the build failed, a batch it could not add, a seal or a load that failed, or the build it could not open: `failed` with `store`;
- any other failure of the walk, a source answer that could not be read or kept, or no answer after the retries: `failed` with `source`.

A run that fails leaves no file of it in the runs directory: its temporaries, and any file its load had made, are deleted. A scraper's current run stays its last `done` one. `scrape.finished` is told once the ending is recorded.

## Pacing a build

A build writes in steps: each chunk the walk writes, and each transaction the load commits. After each step the store reports the bytes it wrote and how long the write took (`store.Step`), and the engine paces the step through `internal/pace`, one `pace.Phase` per phase, started with `runs.Config`'s `Budget`, `PressureLimit`, `Pressure`, `Now` and `Sleep` (decisions document §7):

- **The write budget.** A phase has a rate, starting at the budget in bytes per second (the chunk's compressed bytes for the walk, the file's growth per transaction for the load). A step's expected time is its bytes at the current rate; when the write took less, the step pauses the difference, so a phase never writes faster than its rate. A budget below 1 means no budget pause and no backoff.
- **The latency backoff.** A step that took longer than its expected time halves the rate for the next step, never below `Budget / pace.FloorDivisor` (and never below 1 byte per second); each step on time adds `Budget / pace.RestoreDivisor` back (at least 1 byte per second), never above the budget. A slow disk slows the writer at once and the writer creeps back.
- **The pressure pause.** Between steps, after the budget pause, the phase reads the `full avg10` figure of the pressure file the run seam names (the kernel's I/O pressure, `/proc/pressure/io` on a host, documented in the kernel's PSI documentation) and, while it is above the limit, pauses `pace.PressurePoll` at a time and reads it again. A file that is not named, cannot be read or holds no such figure means no pressure pause, so nothing depends on the platform, and a test hands a file in its own directory.

Every pause goes through `Config.Sleep` with the work's context, so the drain ends a pause at once, and the phase totals its bytes, its elapsed time on `Config.Now` and the pauses it asked, which the trail's phase event carries.

## The trail of a build

Each phase that succeeds is recorded once in the trail (`D07-events`), through `trail.Phase`: `scrape.walked` once the walk returned and the build is sealed, and `scrape.loaded` once the load put the file in place, before the run is finished. Each carries the run's scraper and id, the phase's bytes, its duration and the time it paused, and belongs to the run's starter and request as `scrape.started` does. A phase that fails, or that the drain cancels, records nothing: an absent `scrape.loaded` says the load did not finish. Neither is emitted on the bus.

## Writes that meet a lock

The database can be locked past appkit's busy timeout by another writer, as litestream's checkpoint of a large WAL does on a host. The catalog is written by a run three times: `AddRun`, which `Start` and a delivery answer at once (a lock there answers `unavailable` or `Fail` as any other refusal does), and the ending, `FinishRun` or `FailRun`. An ending write the store answers `store.ErrLocked` is tried again after a pause through `Config.Sleep`, which `cli.Run` sets to `Process.Sleep`: `runs.WriteBackoff` doubling, 1, 2, 4, 8 and 16 seconds, for up to `runs.WriteRetries` retries. An ending still locked after them, or refused for any other reason, is given up: no event is told, the run leaves the engine's care and stays `running` until the next start's `Recover` settles it `interrupted` and its start-up tidy deletes whatever file it left. The build writes no catalog row, so no lock reaches it.

Each pause and each give-up writes one diagnostic line to `Config.Stderr`, which `cli.Run` sets to `Process.Stderr`: `scrapes: `, the run id, the call, a copy constant and the error, never a row's data. A build that fails writes one such line too, with `runs.GaveUp` and the call that failed (`Build`, `Add`, `Seal` or `Load`), so a run never fails `store` silently. A build failed because the drain cancelled the work writes nothing, since the run ends `interrupted` as it should.

The engine takes its store as `runs.Store`, the six methods it calls, which `*store.Store` implements, so that a test can hand it a wrapper of a real store that answers a lock on demand: a real lock costs appkit's five-second busy timeout per attempt.

## The delivery

scrapes keeps no schedule (decision 6). It accepts, for each scraper the registry holds, the exact event name `runs.FiredEvent` gives it, `cron.scrape_<scraper>.fired`, so today `cron.scrape_fmcsa.fired`, `cron.scrape_form5500.fired`, `cron.scrape_mn_parcels.fired` and `cron.scrape_ppp.fired`, and no pattern and not `*`: each fire of such a trigger is delivered to `POST /events` and handed to `Deliver` by appkit's delivery handler, which has already put the bus event's id and depth on the context as its cause. A delivery carries the bus event: its id, its name `cron.<slug>.fired`, its attributes `trigger` (the trigger's id), `when` (its schedule) and `scheduled` (the slot fired), the trigger's owner as its user and the fire's request id; and its attempt number. It carries no identity header of its own: the caller on its context is the one appkit's telemetry middleware built from the request, whose request id is the one the events app sent or one minted for it. The slug alone decides: a slug that is `scrape_` followed by a registered scraper's name starts a run of that scraper, whose starter is `cron` with that slug, and the answer `OK` comes at once, before the run ends. A slug naming no scraper, and a scraper already running, answer `Skip`: there is nothing to retry. The run record keeps the bus event's id as its delivery, so a retry of a delivery whose run was already started, whatever became of that run, is `Skip` too: redelivery is safe. A stopping engine answers `Fail` with `runs.Stopping` and a database that cannot be written `Fail` with `store.Unreachable`, so the events app delivers again to a scrapes serving again (decision log D5, as scripts answers). A fire of a trigger whose slug names no scraper is not delivered at all, since scrapes does not accept its name, and a delivery of such a name posted to the socket is answered 404 by appkit's delivery handler, since no handler takes it; `Deliver` handed one directly still answers `Skip`.

## Starting and stopping

`Recover` runs at start, before ready (`D03-serve`): every run still `running` was cut off by a dead process and is finished `failed` with `interrupted`, its `scrape.finished` told as its starter; then the store's `TidyFiles` leaves in the runs directory only the `<id>.db` of each `done` run, deleting temporaries, files of runs not `done` (an interrupted run's, a given-up ending's), files no run owns (a restored catalog has none of them) and foreign names. A catalog that cannot be read refuses the start. `Drain` is the stop: from its call `Start` refuses `stopping` and `Deliver` answers `Fail`; every running work is cancelled at once, whether it is walking, paused by its pacing or waiting for another run's load, its request in flight ended, its build's files deleted, and its run finished `failed` with `interrupted` (decision 11). `Drain` returns once every run the engine started has ended, or when its context ends, which `D03-serve` sets to the drain deadline, `DRAIN_SECONDS` after the signal.

## The sweep

Once before ready, after `Recover`, and then each time a wait of `cli.SweepInterval` on `Process.After` ends, the runs past keeping are pruned with `store.PruneRuns` and `SCRAPE_KEEP_RUNS`: for each scraper the newest `SCRAPE_KEEP_RUNS` `done` runs are kept and, separately, the newest `SCRAPE_KEEP_RUNS` `failed` runs, so a page still shows what went wrong; a `running` run is never pruned (decision 11). The current run is always among the kept. The prune removes the records first and then each removed run's file, so a crash between the two leaves an orphan the next start's tidy removes, never a `done` record without its file. A pruned run is gone from the tools, the pages and the sibling read path, and its file from the runs directory. A prune that fails is silent, keeps every record and every file, and is tried again at the next interval.

## The run record

The record the tools and the sibling read path answer is `runs.Record`, made from a stored run by `runs.RecordOf`: `id`, `scraper`, `status`, `reason` when failed, `started`, `finished` once ended, `rows`, `new`, `changed`, `unchanged` and `gone`, and the starter: `user` and `email` for a `scrape` call, `trigger` for a cron delivery (decision 4). The delivery and the request id are not part of it.

## Refusals

A refusal is a `*runs.Refusal`, a word. All of scrapes' refusal words are declared here, so the tools tell every refusal apart with one `errors.As` (`D10-tools`): `not_found`, `busy`, `no_run`, `stopping`, `unavailable` and `missing` (decision 7). The engine answers `not_found`, `busy` and `stopping`; `no_run`, a scraper with no current run, `unavailable`, the database failing, and `missing`, a `done` run whose file is gone, are the tools' (`D10-tools`). The sentences are `D10-tools`' copy constants, fixed text that names no value, as gmail's: no scraper, id or record content.

## Recorded decisions

- **The trigger slug is `scrape_<scraper>`, not `scrape-<scraper>`.** cron refuses a slug with a hyphen (observed: `create` of `scrape-fmcsa` answered `invalid slug 'scrape-fmcsa'`), since a slug is a word of the event name `cron.<slug>.fired` and an event-name word allows `_` but not `-`. `scrape_` keeps the decision's meaning with the one separator cron accepts. The about and landing templates' copy says `scrape-<scraper>` and is the assets' to change.
- **scrapes accepts exact names, not the decisions document's `cron.*.fired`.** The events app subscribes a service, and delivers an event to it, only when its declaration's `accepts` lists `*` or that event's exact name; a pattern among `accepts` is held and catalogued but subscribes nothing and accepts no name (events' design, `D04-store`: a service accepts a name its declaration lists, or `*`; a declaration whose `accepts` holds only patterns does not subscribe). Under `cron.*.fired` no fire reached scrapes (sandbox round 1). The decisions document holds events unchanged, so scrapes declares one exact name per registered scraper, `cron.scrape_<scraper>.fired`, derived from the registry each time it declares; the registry is fixed in code, so every name is known when scrapes declares, and a new scraper brings its name with its release. It does not declare `*`, which would have every event of the suite delivered to it only to be skipped. The rules of a delivery are unchanged: a registered scraper's slug starts a run and answers `OK` at once; busy, an unknown slug and a redelivery answer `Skip`; stopping and the database failing answer `Fail`.
- **Who a delivery's run is started as.** The delivery's context caller, as appkit's telemetry middleware builds it (its request id, and whatever user the request named), is the run's starter identity and the identity its events carry, with the delivered bus event as its cause (decision log D5); the run's starter shown is `cron` and the slug. The trigger owner the bus event names as its user is not taken as the starter: the decision names the starter `cron`, not a person.
- **Busy and unknown slugs skip; stopping and the database fail** (decision 6, decision log D5): a skipped fire is the same fire missed by a manual run, while a fire lost to a restart or a broken database would leave a month without a run.
- **Redelivery is told by the record**, not by memory: the delivery column survives a restart, and the store refuses a second run with the same delivery in the write that records it, so two attempts racing start one run.
- **The drain cancels at once** (decision 11: "a running scraper is cancelled"), rather than letting the work run to the deadline as gmail's transfers do: a walk takes minutes, a drain seconds, and the run cannot be resumed anyway. The cancel reaches a run paused by its pacing and a run waiting for the load, which end `interrupted` with their files deleted.
- **Walking is separate from storing** (decisions document principle 1, §3). The walk hands batches to a build that writes only its own temporaries; the run's file appears whole, by a rename, only once the load has written, counted and synced it. A reader never sees a half-built run, and a failed or interrupted run is cleaned up by deleting files, never rows. The `Scraper` interface is unchanged (principle 7): what a batch function's error now means is a build that could not take the batch.
- **The file is in place before the run is `done`, and `done` before `scrape.finished`** (§4). The store refuses `FinishRun` without the file (`D04-store`), so the order is the store's guarantee and not only the engine's habit: a sibling told `scrape.finished` always finds the rows.
- **One load at a time, across scrapers** (§4). The load is the heavy write; the engine holds a load lock rather than relying on the catalog's connection limit, which the load does not touch. Walks still run side by side, each pacing its own chunks; a run that finished walking waits `running` with its temporaries on disk, which `D11-on-a-space` counts in the disk peak.
- **The budget is per phase** (§7, settled). Each walk and each load paces itself at the budget; loads are serialised by the lock, so at most one load and the concurrent walks write at once. One shared, process-wide budget was rejected: it would make a run's pauses depend on what other scrapers do, which no test could pin down, and the heavy phase is already serialised.
- **The pace is measured per step from the write's own duration.** A step's pause is its expected time at the current rate less the time the write took, not less the time since the last step; otherwise the walk's time between chunks would read as a slow disk. Idle walk time therefore earns no budget credit, which keeps the pause simple and exact. The budget pause comes first, then the pressure loop; a phase's paused time is the sum of the pauses it asked, not wall time.
- **Backoff halves and restores by a tenth** (§7, settled): a step slower than its expected time halves the rate, floored at a sixteenth of the budget (256 KB/s at the default) so a slow patch never stalls a run; each step on time adds a tenth of the budget back, at least 1 byte per second, capped at the budget. The added minimum of 1 departs from the settled rule, which adds exactly a tenth: below a budget of 10 bytes per second a tenth rounds down to 0, and a rate once halved would never recover. At any real budget the two are the same. The constants are `pace`'s, not settings: the operator moves the budget and the limit, not the shape of the curve.
- **The pressure pause polls every 5 s** (settled): `full avg10` is a ten-second average, so a faster poll reads the same figure. Off when the file cannot be read, so a host without PSI, and every test, runs unpaused; the binary alone names `/proc/pressure/io` (`D01-layout-and-run-seam`).
- **`pace` is its own package** so the budget, backoff and pressure arithmetic is proved with exact byte counts and exact asked pauses, which an engine test cannot see per step. Every pause, budget and pressure alike, goes through the run seam's `Sleep`, so a test drives pacing with a fake `Now` and `Sleep` and a pressure file in its own directory.
- **A failed build writes one line** (settled): a run failed `store` writes one `runs.GaveUp` line naming the call that failed, keeping "nothing lost silently"; a phase that fails records no trail event.
- **A locked write is retried, and nothing is lost silently** (delivery of the scrapes run-engine repair). On the production host a write lock held more than five seconds (litestream checkpointing a large WAL) made a batch write answer busy, the walk fail, `FailRun` fail too, and the run stay `running` with no work behind it, refusing every start `busy` until a restart, with nothing on stderr or in the trail. The batches no longer touch the catalog, so the lock now meets only a run's ending. Decided: an ending write answered `store.ErrLocked` is retried through the run seam's `Sleep`, 1 s doubling, up to 5 retries; any other error, or the retries spent, gives the ending up, after which the run is removed from the engine's care and left for `Recover`; every retried or abandoned write writes one diagnostic line on stderr in the root conventions' `scrapes: ` form naming the run id, the call and the error. The store, not the engine, recognises a lock (`D04-store`), so `runs` never imports the driver; the engine takes its store as an interface so a test can inject a lock without waiting out the busy timeout. `Recover`'s and the drain deadline's own writes are unchanged. An ending's pauses end with the drain's deadline, which gives the ending up without a line; an ending being written once the load has returned when the drain begins is kept, not turned `interrupted`; and nothing is written to stderr once `Drain` has returned, since `Run` may have returned and its `Stderr` be gone. The run seam's tests of a real lock (the store's busy refusal in `D04-store`, and the engine's retry of a locked `FinishRun` here) wait out appkit's five-second busy timeout once each; `AGENTS.md`'s test discipline must admit them.
- **Precedence of endings**: a work the drain cancelled before its load returned is `interrupted` whatever its walk or build then returned; a build that failed is `store`; anything else the walk returns is `source`.
- **The prune lives in the store and runs from the serve path**, as gmail's; the engine owns `Recover` and `Drain`, which need its running works. The sweep's requirements are stated here, at the run seam. The prune deletes the record before the file, and the start-up tidy deletes whatever file a crash between the two leaves behind.
- **The tools' word for a gone file is `missing`** (settled): declared here with every refusal word, answered by `D10-tools`.
- **No queue and no limits setting**: one run per scraper is the whole concurrency rule (decision 4), and one load at a time the whole rule for the disk, so there is nothing to queue.
- **The walk's context carries the build's spool** (the Form 5500 pass's decision 4; settled by the orchestrator): a scraper knows neither the run's id nor the runs directory, and the `Scraper` interface stays as it is, so the engine, which holds both the build and the walk, puts `Build.Spool` on the context. A spool a scraper leaves is deleted by the build's `Seal` or `Discard` (`D04-store`), so the rule that a run leaves no file of it but its own holds for it as for the chunks. This spool is a source's file on its way to being read, not the spool of rows rejected below.
- **Rejected** (decisions document): a separate spool file the walk writes before the build; sorting a whole run in memory; looking up the previous run row by row to count it; building the file by `INSERT … SELECT … ORDER BY`; leaning on cgroup I/O limits instead of the engine's own budget; raising `memory_max` to hold more of a run (`D02-cli`, `D11-on-a-space`).
- **Deferred** (decisions document): a narrower run than the settings, cancelling a running run, deleting a run by hand; reloading a run's chunks after a death without a new walk (the tidy deletes them); cgroup I/O limits; copying a finished file to S3 (`D04-store`, `D11-on-a-space`).

## Consumer tasks

`D03-serve` builds the engine with `runs.New` and a `runs.Config` holding its store, registry, writer and emitter, `Process.Sleep`, `Process.Stderr` and `Process.Now`, the settings' write budget and pressure limit as `Budget` and `PressureLimit`, and `Process.Pressure` as `Pressure`; mounts the delivery and declarations handlers over `Handlers`; calls `Recover` and prunes once before ready, prunes again on each `After`, and calls `Drain` at the signal. The tools (`D10-tools`) call `Start` with the call's caller and answer `runs.RecordOf` of the run, telling a refusal by `errors.As` to a `*runs.Refusal` and its `Word`, and any other error `unavailable`. The sibling read path marshals `runs.RecordOf`. An engine test builds a store over its own database with `Runs` in its own directory (and `ChunkBytes` or `LoadRows` small where steps matter), a writer and an emitter over captures, a registry of fake scrapers that hand the batches the test chooses and block until released, a `Now` it holds still or advances, a `Sleep` that records each pause and returns, holds, or returns once its context is done, and a `Stderr` that records each `Write`; it starts runs, delivers fires, drains, and compares the store, the runs directory and the captured events. A test of a locked ending wraps its store in a `runs.Store` whose `FinishRun` or `FailRun` answers a lock the times it chooses. A test of a failed build puts a regular file where the runs directory belongs, or a directory where the run's file belongs. A pacing test drives `pace.Start` and `Step` directly with exact byte counts, a fake `Now` and `Sleep`, and a pressure file it rewrites from its `Sleep`.
