# D06-runs

The engine: `internal/runs`, the one place a run is started, worked, finished, settled at start and abandoned at the stop, and the place a cron fire delivered on the bus becomes a run. A `scrape` call (`D10-tools`) or a delivery hands the engine a scraper's name; the engine records the run `running` (`D04-store`), tells `scrape.started` (`D07-events`), answers at once, and walks the scraper's source in the background, storing each batch of rows the scraper hands over as it arrives (decision 4). When the walk ends the run is finished `done` with its counts, or `failed` with its reason and its rows removed, and `scrape.finished` is told. It is gmail's record-then-run shape without a queue: one run per scraper at a time, refused or skipped when one is running, runs of different scrapers side by side. It also declares the run record's JSON, which the tools and the sibling read path answer, and every refusal word the tools answer.

`D01-layout-and-run-seam` declares the run seam, the settings and `cli.SweepInterval`; `D04-store` the records, their words, the comparison and the prune; `D05-scrapers` the registry, the `Scraper` interface and the FMCSA, PPP and MN parcels scrapers; `D07-events` the events, what `/declarations` answers, and the identity and cause each event carries; `D10-tools` the tools and the sentences a refusal word is shown with; `D03-serve` builds the engine, mounts the delivery and calls `Recover` and `Drain` in its start and stop.

## Starting a run

`Start` takes the caller and a scraper's name. A name the registry does not hold is refused `not_found`; once the drain has begun, `stopping`; a scraper with a run `running`, `busy` (the store refuses the record, so a tool call and a delivery racing for one scraper cannot both win); and the database failing is an error matching `store.ErrUnreachable`, which the tool answers `unavailable` (decision 7). Otherwise the run is recorded with the caller as its starter, `scrape.started` is told, the work begins in a goroutine, and `Start` answers the record, `running`, without waiting for the source: the MCP gateway gives a tool call fifty seconds and a full FMCSA walk takes minutes.

## The work

A run's work runs in a goroutine, as the starter: under `identity.NewContext(context.WithoutCancel(ctx), caller)`, `ctx` being the starting call's, so the work outlives the call but keeps its values, the event cause among them, and every `source.called` it records names the starter and the starting request (gmail's precedent). It is cancelled by the drain and by nothing else. It asks the scraper to walk its source and stores each batch the scraper hands over with `store.PutRows` as it comes, so only one batch is held at a time (decision log D5). Its end is one of four:

- the walk returns nil: the run is finished `done` and its counts written against its baseline (`D04-store`);
- the drain cancelled the work before the walk returned: `failed` with `interrupted`;
- a batch could not be stored: `failed` with `store`;
- any other failure of the walk, a source answer that could not be read or kept, or no answer after the retries: `failed` with `source`.

A failed run keeps its record and loses its rows in the same write (decision 4), and a scraper's current run stays its last `done` one. `scrape.finished` is told once the ending is recorded.

## Writes that meet a lock

The database can be locked past appkit's busy timeout by another writer, as litestream's checkpoint of a large WAL does on a host. A batch write or an ending write the store answers `store.ErrLocked` is tried again after a pause through `Config.Sleep`, which `cli.Run` sets to `Process.Sleep`: `runs.WriteBackoff` doubling, 1, 2, 4, 8 and 16 seconds, for up to `runs.WriteRetries` retries. A batch still locked after them, or refused for any other reason, is refused and the run fails `store`, as before. An ending still locked after them, or refused for any other reason, is given up: no event is told, the run leaves the engine's care and stays `running` until the next start's `Recover` settles it `interrupted`. Each pause and each refusal or give-up writes one diagnostic line to `Config.Stderr`, which `cli.Run` sets to `Process.Stderr`: `scrapes: `, the run id, the store method, a copy constant and the error, never a row's data. A batch refused because the drain cancelled the work writes nothing, since the run ends `interrupted` as it should.

The engine takes its store as `runs.Store`, the five methods it calls, which `*store.Store` implements, so that a test can hand it a wrapper of a real store that answers a lock on demand: a real lock costs appkit's five-second busy timeout per attempt.

## The delivery

scrapes keeps no schedule (decision 6). It accepts, for each scraper the registry holds, the exact event name `runs.FiredEvent` gives it, `cron.scrape_<scraper>.fired`, so today `cron.scrape_fmcsa.fired`, `cron.scrape_mn_parcels.fired` and `cron.scrape_ppp.fired`, and no pattern and not `*`: each fire of such a trigger is delivered to `POST /events` and handed to `Deliver` by appkit's delivery handler, which has already put the bus event's id and depth on the context as its cause. A delivery carries the bus event: its id, its name `cron.<slug>.fired`, its attributes `trigger` (the trigger's id), `when` (its schedule) and `scheduled` (the slot fired), the trigger's owner as its user and the fire's request id; and its attempt number. It carries no identity header of its own: the caller on its context is the one appkit's telemetry middleware built from the request, whose request id is the one the events app sent or one minted for it. The slug alone decides: a slug that is `scrape_` followed by a registered scraper's name starts a run of that scraper, whose starter is `cron` with that slug, and the answer `OK` comes at once, before the run ends. A slug naming no scraper, and a scraper already running, answer `Skip`: there is nothing to retry. The run record keeps the bus event's id as its delivery, so a retry of a delivery whose run was already started, whatever became of that run, is `Skip` too: redelivery is safe. A stopping engine answers `Fail` with `runs.Stopping` and a database that cannot be written `Fail` with `store.Unreachable`, so the events app delivers again to a scrapes serving again (decision log D5, as scripts answers). A fire of a trigger whose slug names no scraper is not delivered at all, since scrapes does not accept its name, and a delivery of such a name posted to the socket is answered 404 by appkit's delivery handler, since no handler takes it; `Deliver` handed one directly still answers `Skip`.

## Starting and stopping

`Recover` runs at start, before ready (`D03-serve`): every run still `running` was cut off by a dead process and is finished `failed` with `interrupted`, its rows removed and its `scrape.finished` told as its starter. `Drain` is the stop: from its call `Start` refuses `stopping` and `Deliver` answers `Fail`; every running work is cancelled at once, its request in flight ended, and its run finished `failed` with `interrupted` (decision 11). `Drain` returns once every run the engine started has ended, or when its context ends, which `D03-serve` sets to the drain deadline, `DRAIN_SECONDS` after the signal.

## The sweep

Once before ready, after `Recover`, and then each time a wait of `cli.SweepInterval` on `Process.After` ends, the runs past keeping are pruned with `store.PruneRuns` and `SCRAPE_KEEP_RUNS`: for each scraper the newest `SCRAPE_KEEP_RUNS` `done` runs are kept and, separately, the newest `SCRAPE_KEEP_RUNS` `failed` runs, so a page still shows what went wrong; a `running` run is never pruned (decision 11). The current run is always among the kept. A pruned run is gone from the tools, the pages and the sibling read path. A prune that fails is silent and tried again at the next interval.

## The run record

The record the tools and the sibling read path answer is `runs.Record`, made from a stored run by `runs.RecordOf`: `id`, `scraper`, `status`, `reason` when failed, `started`, `finished` once ended, `rows`, `new`, `changed`, `unchanged` and `gone`, and the starter: `user` and `email` for a `scrape` call, `trigger` for a cron delivery (decision 4). The delivery and the request id are not part of it.

## Refusals

A refusal is a `*runs.Refusal`, a word. All of scrapes' refusal words are declared here, so the tools tell every refusal apart with one `errors.As` (`D10-tools`): `not_found`, `busy`, `no_run`, `stopping` and `unavailable` (decision 7). The engine answers `not_found`, `busy` and `stopping`; `no_run`, a scraper with no current run, and `unavailable`, the database failing, are the tools' (`D10-tools`). The sentences are `D10-tools`' copy constants, fixed text that names no value, as gmail's: no scraper, id or record content.

## Recorded decisions

- **The trigger slug is `scrape_<scraper>`, not `scrape-<scraper>`.** cron refuses a slug with a hyphen (observed: `create` of `scrape-fmcsa` answered `invalid slug 'scrape-fmcsa'`), since a slug is a word of the event name `cron.<slug>.fired` and an event-name word allows `_` but not `-`. `scrape_` keeps the decision's meaning with the one separator cron accepts. The about and landing templates' copy says `scrape-<scraper>` and is the assets' to change.
- **scrapes accepts exact names, not the decisions document's `cron.*.fired`.** The events app subscribes a service, and delivers an event to it, only when its declaration's `accepts` lists `*` or that event's exact name; a pattern among `accepts` is held and catalogued but subscribes nothing and accepts no name (events' design, `D04-store`: a service accepts a name its declaration lists, or `*`; a declaration whose `accepts` holds only patterns does not subscribe). Under `cron.*.fired` no fire reached scrapes (sandbox round 1). The decisions document holds events unchanged, so scrapes declares one exact name per registered scraper, `cron.scrape_<scraper>.fired`, derived from the registry each time it declares; the registry is fixed in code, so every name is known when scrapes declares, and a new scraper brings its name with its release. It does not declare `*`, which would have every event of the suite delivered to it only to be skipped. The rules of a delivery are unchanged: a registered scraper's slug starts a run and answers `OK` at once; busy, an unknown slug and a redelivery answer `Skip`; stopping and the database failing answer `Fail`.
- **Who a delivery's run is started as.** The delivery's context caller, as appkit's telemetry middleware builds it (its request id, and whatever user the request named), is the run's starter identity and the identity its events carry, with the delivered bus event as its cause (decision log D5); the run's starter shown is `cron` and the slug. The trigger owner the bus event names as its user is not taken as the starter: the decision names the starter `cron`, not a person.
- **Busy and unknown slugs skip; stopping and the database fail** (decision 6, decision log D5): a skipped fire is the same fire missed by a manual run, while a fire lost to a restart or a broken database would leave a month without a run.
- **Redelivery is told by the record**, not by memory: the delivery column survives a restart, and the store refuses a second run with the same delivery in the write that records it, so two attempts racing start one run.
- **The drain cancels at once** (decision 11: "a running scraper is cancelled"), rather than letting the work run to the deadline as gmail's transfers do: a walk takes minutes, a drain seconds, and the run cannot be resumed anyway.
- **A locked write is retried, and nothing is lost silently** (delivery of the scrapes run-engine repair). On the production host a write lock held more than five seconds (litestream checkpointing a large WAL) made `PutRows` answer busy, the walk fail, `FailRun` fail too, and the run stay `running` with no work behind it, refusing every start `busy` until a restart, with nothing on stderr or in the trail. Decided: a batch write or an ending write answered `store.ErrLocked` is retried through the run seam's `Sleep`, 1 s doubling, up to 5 retries; any other error, or the retries spent, refuses the batch (reason `store`, which already exists, so `candidates`, which reads `scrape.finished`'s `scraper`, `run` and `status` and not its reason, is unaffected) or gives up the ending, after which the run is removed from the engine's care and left for `Recover`; every retried or abandoned write writes one diagnostic line on stderr in the root conventions' `scrapes: ` form naming the run id, the store method and the error. The store, not the engine, recognises a lock (`D04-store`), so `runs` never imports the driver; the engine takes its store as an interface so a test can inject a lock without waiting out the busy timeout. `Recover`'s and the drain deadline's own writes are unchanged. An ending's pauses end with the drain's deadline, which gives the ending up without a line, as a batch refused by the drain writes none; an ending already being written when the drain begins is kept, not turned `interrupted`; and nothing is written to stderr once `Drain` has returned, since `Run` may have returned and its `Stderr` be gone. The run seam's tests of a real lock (R-LJIS-8NTQ, R-LEN6-PKUY) wait out appkit's five-second busy timeout once each; `AGENTS.md`'s test discipline must admit them.
- **Precedence of endings**: a work the drain cancelled is `interrupted` whatever its walk then returned; a walk ended by a refused batch is `store`; anything else the walk returns is `source`.
- **The prune lives in the store and runs from the serve path**, as gmail's; the engine owns `Recover` and `Drain`, which need its running works. The sweep's requirements are stated here, at the run seam.
- **No queue and no limits setting**: one run per scraper is the whole concurrency rule (decision 4), so there is nothing to queue.
- **Deferred** (decisions document): a narrower run than the settings, cancelling a running run, deleting a run by hand.

## Consumer tasks

`D03-serve` builds `eng := runs.New(runs.Config{Store: st, Scrapers: reg, Telemetry: w, Events: em, Sleep: p.Sleep, Stderr: p.Stderr})`, mounts `events.DeliveryHandler(eng.Handlers())` and `events.DeclarationsHandler(em, eng.Handlers())`, calls `eng.Recover(bg)` and `st.PruneRuns(bg, s.KeepRuns)` before ready, prunes again on each `After`, and calls `eng.Drain(drainCtx)` at the signal. The tools (`D10-tools`), `c` the call's caller: `r, err := eng.Start(ctx, c, "fmcsa")`, answering `runs.RecordOf(r)`; a refusal told with `var rf *runs.Refusal; errors.As(err, &rf)`, reading `rf.Word`, and any other error, which matches `store.ErrUnreachable`, answered `unavailable`. The sibling read path writes `json.Marshal(runs.RecordOf(r))`. A test builds a store over its own database, a writer and an emitter over captures, a registry `scrapers.New(fake)` whose fake scraper hands the batches the test chooses and blocks until released, and an engine; calls `Start` with an `identity.Caller`, calls `Deliver(events.NewContext(identity.NewContext(ctx, identity.Caller{RequestID: rid}), events.Cause{ID: id, Depth: 0}), events.Delivery{Event: ev, Attempt: 1})` with an `events.Event` named `cron.scrape_fmcsa.fired`, compares the outcome with `events.OK()`, `events.Skip()` or `events.Fail(...)` by `==`, polls `store.GetRun`, calls `Drain` with a context it cancels, and compares the store and the captured events. A test of a locked write wraps its store in a `runs.Store` whose `PutRows`, `FinishRun` or `FailRun` answers `errors.Join(store.ErrUnreachable, store.ErrLocked)` the number of times it chooses before delegating, hands a `Sleep` that records each duration and a `Stderr` that records each `Write`, and compares the pauses with `runs.WriteBackoff` doubled, and each line with `"scrapes: " + id + " PutRows: " + runs.Retrying + ": " + t + "\n"` built from the run's id and its own error. A run-seam test seeds a `Dir` with a run left `running` and with done and failed runs, drives `cli.Run` with an `HTTP` whose transport answers as a fake Socrata and holds an answer open when the test asks, an `After` whose channels it holds, and `DRAIN_SECONDS` 1, and reopens the database after `Run` returns.
