# D10-tools

The six MCP tools agents reach scrapes by through the MCP gateway: `internal/tools`. An agent learns what scrapers there are and which run of each is current with `scrapers`, starts a run now with `scrape`, reads the runs with `runs` and `run`, pages a run's rows with `rows` and reads one row with its raw record with `row` (decision 7). Every signed-in caller sees every run and row: runs belong to no one, so no answer depends on who asks, and the caller a tool is handed is used only to start a run as that caller (`D06-runs`). The run record is `D06-runs`' (`runs.Record`), the row's JSON is `D05-scrapers`' (`source.Row`), and the tools answer them as those documents encode them.

## The tools

- `scrapers` takes nothing and answers `scrapers`, one entry per registered scraper in name order, each its `name`, its `current` run (the newest `done`, absent when none) and its `running` run (absent when none), each a run record. Read-kind.
- `scrape` takes `scraper` and answers the run record it started, `running`; it does not wait for the source (`D06-runs`). Additive: it only adds a run.
- `runs` takes optional `scraper`, `page` and `limit` and answers `runs`, run records newest first (`D04-store`'s run order), of that scraper or of every scraper, `limit` at a time, with `next` when more remain (below). A name no run carries answers an empty list.
- `run` takes `run` and answers its record.
- `rows` takes optional `run`, `scraper`, `name`, `page` and `limit` and answers `rows`, the rows of one run in `source_id` order, `limit` at a time, with `next` when more remain (below), each the envelope without `raw`. The run is `run` when given; otherwise the current run of `scraper`; one of the two is required. `name` keeps only the rows one of whose `names` contains it, compared case-insensitively, `%` and `_` in it matching only themselves (`D04-store`). A run that is `running` or `failed` has no rows to show and answers an empty list (decision 4).
- `row` takes `run` and `source_id` and answers that row's envelope with `raw`.

## Paging

`runs` pages as the suite's listing convention asks (`shape/`, Listing and Storage), on the contract of appkit's `paging` package (`appkit/paging`, appkit's D25), which this document cites and never restates; dummy's `list_widgets` is the precedent. Its input declares `page`, an opaque string, and `limit`, an integer, as pointer fields carrying the shared descriptions `paging.PageDescription` and `paging.LimitDescription`, and its answer is `runs` then `next`, an opaque string present exactly when at least one run follows. An absent, null or empty `page` is the first page, and `next` is handed back as `page` unchanged; an absent or null `limit` is `paging.DefaultLimit`. The token is `paging.Token{Tool: "runs"}` over two strings, the key of the last run the page answered in run order: its started time as the store keeps it, RFC 3339 in UTC to the second, and its id. The tool asks the store's `ListRunsAfter` for one run more than the page and sets `next` only when the extra run came back, so a full last page carries no `next` and a run sharing its started time with the page's last is neither repeated nor skipped. The token does not bind `scraper`: keeping it the same is the caller's part, as D25 says. Before the store is read, a `limit` outside 1 to `paging.MaxLimit` is refused with the text of `paging.Window`'s error, and then a `page` the token does not decode with `paging.BadPage`; each refusal is that text alone, not one of the five words below, and is the same while the database is unreachable, since retrying cannot help. Paging records nothing: a `runs` call is appkit's `tool.called` like any other, which carries no arguments, so no token appears in any event or log line, and `D09-trail` is unchanged.

`rows` pages the same way. Its input declares `page` and `limit` as `runs`' does, with the same descriptions, and its answer is `rows` then `next`. Its key is the row's `source_id`, unique within a run, in ascending byte order: the token is `paging.Token{Tool: "rows"}` over one string, the `source_id` of the last row the page answered, and the tool asks the store's `ListRowsAfter` for one row more than the page. The token binds none of `run`, `scraper` and `name`: handed back with another run or another `name`, it resumes after that `source_id` in the new answer, as D25 says. The two paging refusals come first, before the run is resolved, so a bad `limit` or `page` is refused with its text even when neither `run` nor `scraper` is given, when the run is unknown, and while the database is unreachable. The run page shows a done run's rows a window of `paging.DefaultLimit` at a time, the window a `rows` token taken as its `?page=` names, and that window's `next` (`D08-pages`).

## Refusals

Apart from the two paging refusals `runs` and `rows` share above, a refusal is an MCP error result whose text is `<word>: <sentence>` (decision 7, as gmail's). The words are the five `D06-runs` declares: `not_found`, `busy`, `no_run`, `stopping` and `unavailable`. Each sentence is a copy constant, `tools.Refuse*`, one per word, so a refusal names no scraper, id, business name, address, phone or email the call or the store supplied (decision 13); the name or id the agent passed is already the agent's.

- `scrape`: what `Engine.Start` refuses, in its order (`D06-runs`): an unregistered name `not_found`, the drain `stopping`, a scraper already running `busy`; the database failing `unavailable`.
- `run` and `row`: an id that is not a run id, an unknown or pruned run, and for `row` a row the run does not hold or a run not `done`, are `not_found`.
- `rows`: `run` and `scraper` both absent, an id that is not a run id, an unknown or pruned run, an unregistered `scraper`, and a `scraper` given beside a `run` of another scraper are `not_found`; a registered `scraper` with no current run is `no_run`.
- `runs` and `rows`: a `limit` out of range is refused with `paging.Window`'s text, and then an undecodable `page` with `paging.BadPage`, before the store is read and, for `rows`, before any `not_found` or `no_run`.
- Every tool: the database failing is `unavailable`. Malformed arguments, a `page` that is not a string and a `limit` too large for a Go `int`, are appkit's schema refusal.

## Descriptions

Every tool's description is one line, a copy constant `tools.Describe<Tool>`, which the gateway's `describe` answers as the tool's first line (Verification). `tools.Catalog()` answers each tool's name with that line, in the order `scrapers`, `scrape`, `runs`, `run`, `rows`, `row`, for the tools page (`D08-pages`).

## Recorded decisions

- **Raw registration.** All six tools are registered with appkit's `mcp.AddRawTool` and answer what `encoding/json` writes, as gdrive registers its Drive tools: appkit's typed `mcp.AddTool` refuses a type with its own JSON encoding (`source.Row` has one) and a tag holding a comma, which `runs.Record`'s absent-when-empty members need. They therefore carry no output schema, and the answer's JSON is `D06-runs`' and `D05-scrapers`' contract, stated once there. The argument types are typed, so appkit derives the input schema and refuses malformed arguments before a handler runs; under its schema rules each field carries a `json:"<name>"` tag naming its property, with no `omitempty`, and each required property also `mcp:"required"`; `RunsArgs`' and `RowsArgs`' `Page` and `Limit` also carry a `description` tag repeating `paging.PageDescription` and `paging.LimitDescription` word for word, which appkit copies into the schema (observed with appkit's `mcp`). A structured answer is built as gdrive's are: the JSON as the one text block and as `structuredContent`, through `mcp.AddRawTool`.
- **`runs` follows D25 in place.** Its `page`, `limit` and `next` change shape in one release with no expand period: a tool's arguments and answer are not persisted, and every caller is a model reading the schema `tools/list` gives. The token's started time is the stored string rather than an `int64`, so every token the tool issues decodes to a position the store compares as it keeps it.
- **`RunList.Next`'s and `RowList.Next`'s tags repeat `paging.NextDescription`**, as D25 asks, though a raw tool has no output schema to show it (observed with appkit's `mcp`: `ToolInfo.OutputSchema` is empty for a tool registered with `mcp.AddRawTool`); no requirement states either tag, since no client can see it.
- **`rows` follows D25 in place**, as `runs` did, replacing decision log D6's page number: its `page`, `limit` and `next` change shape in one release with no expand period, since a tool's arguments and answer are not persisted and every caller is a model reading the schema `tools/list` gives. An integer `page` an agent remembers is refused by appkit's schema, and the agent starts again from the first page.
- **`rows`' paging refusals precede the run's.** Checking `limit` and `page` needs no store read, so they answer the same whatever `run` and `scraper` say and whether the database is reachable, as `runs`' do; a call both malformed in its paging and naming no run is told about its paging.
- **`rows` with both `run` and `scraper`**: `run` names the run and `scraper` must be its scraper, else `not_found`, since the pair then names no run; answering another scraper's rows would mislead. With neither, `not_found`: no run is named, and decision 7's five words hold no better one.
- **`runs` with an unregistered `scraper`** answers an empty list rather than a refusal: decision 7 gives `runs` no refusal for a name, and the list of a name no run carries is empty.
- **A running or failed run's `rows`** answers an empty list, not a refusal: the run exists, and it has no rows (decision 4); `row` of such a run is `not_found`, as `D04-store`'s `GetRow` answers.
- **Effects**: `scrapers`, `runs`, `run`, `rows` and `row` are `mcp.Read`; `scrape` is `mcp.Additive` (decision 7).
- **Descriptions are one line** with no shared guide line after it: the intent names none, and each first line must be one sentence of at most 120 characters ending with a full stop, which appkit's `mcp` requires.
- **Refusal sentences are constants**, so the secrecy of decision 13 holds by construction; a test compares the whole text.
- **Both page sizes are the caller's `limit`**, `paging.DefaultLimit` when absent; the run page uses `paging.DefaultLimit`, and this package declares no page size of its own.

## Consumer tasks

`D03-serve`'s handler calls `tools.Register(srv, tools.Config{Runs: eng, Scrapers: reg, Store: st})` once on the server `Process.MCP` made; the tools page reads `tools.Catalog()`. A model calls `scrapers` with `{}` and gets `{"scrapers":[{"name":"fmcsa"},{"name":"mn_parcels"},{"name":"ppp"}]}`; `runs` with `{"scraper":"fmcsa","limit":10}` and gets `{"runs":[…],"next":"<token>"}`, then the same with `"page":"<token>"` until an answer has no `next`, or `{"limit":0}` and is refused with `paging.Window`'s text, or a stale `page` and is refused with `paging.BadPage`; `scrape` with `{"scraper":"fmcsa"}` and gets `{"id":"run_…","scraper":"fmcsa","status":"running","started":"…","rows":0,…,"user":"…","email":"…"}`; `run` with `{"run":"run_…"}` until `done`; `rows` with `{"scraper":"fmcsa","name":"trucking"}` and gets `{"rows":[{"scraper":"fmcsa","run":"run_…","source_id":"1023916",…}],"next":"<token>"}`, then the same with `"page":"<token>"` until an answer has no `next`; `row` with `{"run":"run_…","source_id":"1023916"}` and gets the envelope with `raw`. Or it is refused `busy: <sentence>` and calls `run` on the running run `scrapers` names.
