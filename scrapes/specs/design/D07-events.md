# D07-events

The run events: `internal/trail`'s two bus events, `scrape.started` and `scrape.finished`, which scrapes emits on the suite's event bus and records in its own trail for every run (decision 9), and its two phase events, `scrape.collected` and `scrape.loaded`, which it records in its trail alone; their declarations; the identity and cause each carries; and what scrapes declares at `/declarations`, which emits the two bus events and accepts one exact `cron.scrape_<scraper>.fired` per registered scraper. `D06-runs` decides when each is told; `D03-serve` owns the route `/declarations` and builds the run's writer and emitter; `D09-trail` owns the trail as a whole, its closed set of names and its secrecy. `scrape.finished` with `status` `done` is the event the later `candidates` service will accept: it says a run's file of rows is in place and readable.

## The two bus events

A run's life is told by `scrape.started`, once the run is recorded `running`, and `scrape.finished`, once its ending is recorded, however it ended: `done`, or `failed` by the source, the store, the drain or the next start. `scrape.started` carries `scraper` and `run` (the run's id). `scrape.finished` carries `scraper`, `run`, `status`, `reason` (empty when `done`), and the counts `rows`, `new`, `changed`, `unchanged` and `gone`, integers, as the record holds them: the counts the load computed while it built the run's file, which the store writes into the record when it marks the run `done`. Ids, names, words and counts only: no record, business name, address, phone or email (decision 13).

Every bus event goes two ways at once under the same name, attributes, request id and user: recorded in the trail through the run's writer and emitted on the bus through the run's emitter, as gmail's transfer events do, because appkit's emitter records only `event.lost` in the trail. It is told after the write it reports is committed, never for a run that was not recorded and never for an ending the store could not record (`D06-runs`). For a `done` run that order runs further back: the run's file is in place under the runs directory before the store will mark the run `done` at all, the record is `done` before `scrape.finished` is told, so a consumer that hears `scrape.finished` with `status` `done` finds the rows already readable.

## The two phase events

A run's build has two phases, the collect (the walk's rows written to temporary chunks) and the load (the chunks merged into the run's file and put in place), and each that succeeds is told once in the trail: `scrape.collected` once the walk returned and the last chunk was written, and `scrape.loaded` once the run's file is in place, before the run is marked `done`. A phase that fails tells nothing; the absent event says which phase failed. So a `done` run's trail reads `scrape.started`, `scrape.collected`, `scrape.loaded`, `scrape.finished`; `D06-runs` decides when each is told.

Each phase event carries `scraper`, `run`, and three integers the engine's pacing measured over the phase: `bytes` (the bytes the phase wrote: the chunks' sizes for the collect, the file's size for the load), `duration_us` (the phase's elapsed time) and `paused_us` (the time the phase asked to sleep for the write budget and for I/O pressure), both in whole microseconds as `source.called`'s `duration_us` is. Like the bus events they are told as the run's starter. They are trail only: never emitted, not in `trail.Emits()`, so `/declarations` and what the bus carries are unchanged, and an operator reads a slow build from the trail without any consumer having to know these names.

## Under the request that started the run

Each event is told as the run's starter: its request id is the request id the run was recorded with and its user the run's user id, whatever context tells it, so a run's events name the request that started it even when the drain or the next start tells its end (decision 9). For a `scrape` call that is the tool call's request id and caller. For a delivery it is the delivery's request id, the one the events app sent or one minted for it, and whatever user the delivery's request named; and the delivered `cron.scrape_<scraper>.fired` bus event is the bus event's cause, one level deeper, because appkit's delivery handler puts it on the context the run is started under (`D06-runs`). A run's events made by the next start's settling carry no cause. The phase events are trail events, which carry no cause.

## The declarations

`trail.Emits()` declares the two bus names, literal, each with its attribute keys in order; the run's emitter is built with them, so appkit refuses a run event whose keys are not exactly these, or whose name is not one of these, and every key is always present. The engine's handlers are keyed by the names scrapes accepts, `runs.FiredEvent` of each scraper the registry holds: exact names, never a pattern or `*`, because the events app delivers only on `*` or an exact name (`D06-runs` records why). appkit's `events.DeclarationsHandler`, given the emitter and the engine's handlers, answers the emissions sorted by event name, each one's attributes in the order declared, and the accepted names sorted; so scrapes declares `scrape.finished` before `scrape.started` and accepts `cron.scrape_fmcsa.fired` alone. Each accepted event carries, as cron emits it, the attributes `trigger`, `when` and `scheduled`, the trigger's slug being the event name's middle word; scrapes reads only the name and the id (`D06-runs`).

## Recorded decisions

- Two fixed bus names and one function, `Record`, which knows which attributes each name carries and tells nothing for a name not its own, as gmail's `trail.Record`.
- Two fixed phase names and a second function, `Phase`, which takes no emitter: a phase event cannot reach the bus because nothing hands `Phase` a way there, and `Record` tells nothing for a phase name. A separate function rather than more names for `Record` because the phase's figures (bytes, elapsed, paused) are not the record's and the bus contract stays exactly two events.
- **Phase events in the trail only.** They exist so an operator can see how a build spent its time and how much of it the pacing paused; no service acts on them, and putting them on the bus would add declarations a consumer could come to rely on.
- **Phase figures as integers in microseconds**, as `source.called`'s `duration_us`, so the trail has one unit for time.
- **Events as the record's starter**, as gmail's transfer events are told as the record's caller: a run's end is told from the background or by the next start, where the starting request is gone, so the record keeps its request id and user (`D04-store`). The cause is the context's, which the work keeps from the starting call.
- The counts are integer attributes (an `int64` basic form), as gmail's `bytes`; `reason` is present and empty on a `done` run's `scrape.finished`, as appkit's exact-keys rule requires.
- The body `/declarations` answers is stated here because its content is this document's declarations; the route and its place outside the identity gate are `D03-serve`'s.

## Consumer tasks

The engine (`D06-runs`), once `store.AddRun` has returned a run `r`, calls `trail.Record(ctx, w, em, trail.Started, r)`; once a collect phase has succeeded, `trail.Phase(ctx, w, trail.Collected, r, bytes, elapsed, paused)` with the phase's totals from its pacing, and once the load has put the run's file in place, the same with `trail.Loaded`; and once `store.FinishRun` or `store.FailRun` has returned it ended, `trail.Record(ctx, w, em, trail.Finished, r)`. `cli.Run` builds its emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`; `D03-serve` answers `/declarations` with `events.DeclarationsHandler(em, eng.Handlers())`. A test builds a writer over a `*telemetry.Capture` and an emitter over an `*events.Capture` with `trail.Emits()`, calls `trail.Record` with a `store.Run` under a context carrying another caller and an `events.Cause`, flushes both, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`; it calls `trail.Phase` the same way with chosen bytes and durations and compares the one captured event; it serves `events.DeclarationsHandler(em, eng.Handlers())` with `httptest` to read the declarations; and it drives `cli.Run` with captures, makes a `scrape` call with the `mcp.Client` and posts a delivery of `cron.scrape_fmcsa.fired` to `/events` with an `X-Request-Id` of its own, and compares the run events of each.
