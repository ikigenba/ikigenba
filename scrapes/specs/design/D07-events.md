# D07-events

The run events: `internal/trail`'s two events, `scrape.started` and `scrape.finished`, which scrapes emits on the suite's event bus and records in its own trail for every run (decision 9); their declarations; the identity and cause each carries; and what scrapes declares at `/declarations`, which emits these two and accepts `cron.*.fired`. `D06-runs` decides when each is told; `D03-serve` owns the route `/declarations` and builds the run's writer and emitter; `D09-trail` owns the trail as a whole, its closed set of names and its secrecy. `scrape.finished` with `status` `done` is the event the later `candidates` service will accept: it says a new batch of rows has landed.

## The two events

A run's life is told by `scrape.started`, once the run is recorded `running`, and `scrape.finished`, once its ending is recorded, however it ended: `done`, or `failed` by the source, the store, the drain or the next start. `scrape.started` carries `scraper` and `run` (the run's id). `scrape.finished` carries `scraper`, `run`, `status`, `reason` (empty when `done`), and the counts `rows`, `new`, `changed`, `unchanged` and `gone`, integers, as the record holds them. Ids, names, words and counts only: no record, business name, address, phone or email (decision 13).

Every run event goes two ways at once under the same name, attributes, request id and user: recorded in the trail through the run's writer and emitted on the bus through the run's emitter, as gmail's transfer events do, because appkit's emitter records only `event.lost` in the trail. It is told after the write it reports is committed, never for a run that was not recorded and never for an ending the store could not record (`D06-runs`).

## Under the request that started the run

Each event is told as the run's starter: its request id is the request id the run was recorded with and its user the run's user id, whatever context tells it, so a run's two events name the request that started it even when the drain or the next start tells its end (decision 9). For a `scrape` call that is the tool call's request id and caller. For a delivery it is the delivery's request id, the one the events app sent or one minted for it, and whatever user the delivery's request named; and the delivered `cron.*.fired` bus event is the bus event's cause, one level deeper, because appkit's delivery handler puts it on the context the run is started under (`D06-runs`). A run's events made by the next start's settling carry no cause.

## The declarations

`trail.Emits()` declares the two names, literal, each with its attribute keys in order; the run's emitter is built with them, so appkit refuses a run event whose keys are not exactly these and every key is always present. `runs.Accepts`, `cron.*.fired`, is the one pattern scrapes accepts (`D06-runs`). appkit's `events.DeclarationsHandler`, given the emitter and the engine's handlers, answers the emissions sorted by event name, each one's attributes in the order declared, and the accepted patterns sorted; so scrapes declares `scrape.finished` before `scrape.started`. The accepted `cron.*.fired` carries, as cron emits it, the attributes `trigger`, `when` and `scheduled`, the trigger's slug being the event name's middle word; scrapes reads only the name and the id (`D06-runs`).

## Recorded decisions

- Two fixed names and one function, `Record`, which knows which attributes each name carries and tells nothing for a name not its own, as gmail's `trail.Record`.
- **Events as the record's starter**, as gmail's transfer events are told as the record's caller: a run's end is told from the background or by the next start, where the starting request is gone, so the record keeps its request id and user (`D04-store`). The cause is the context's, which the work keeps from the starting call.
- The counts are integer attributes (an `int64` basic form), as gmail's `bytes`; `reason` is present and empty on a `done` run's `scrape.finished`, as appkit's exact-keys rule requires.
- The body `/declarations` answers is stated here because its content is this document's declarations; the route and its place outside the identity gate are `D03-serve`'s.

## Consumer tasks

The engine (`D06-runs`), once `store.AddRun` has returned a run `r`, calls `trail.Record(ctx, w, em, trail.Started, r)`, and once `store.FinishRun` or `store.FailRun` has returned it ended, `trail.Record(ctx, w, em, trail.Finished, r)`. `cli.Run` builds its emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`; `D03-serve` answers `/declarations` with `events.DeclarationsHandler(em, eng.Handlers())`. A test builds a writer over a `*telemetry.Capture` and an emitter over an `*events.Capture` with `trail.Emits()`, calls `trail.Record` with a `store.Run` under a context carrying another caller and an `events.Cause`, flushes both, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`; it serves `events.DeclarationsHandler(em, eng.Handlers())` with `httptest` to read the declarations; and it drives `cli.Run` with captures, makes a `scrape` call with the `mcp.Client` and posts a delivery of `cron.scrape_fmcsa.fired` to `/events` with an `X-Request-Id` of its own, and compares the run events of each.
