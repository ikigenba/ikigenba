# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail home records of itself from its start to its stop, and the rules its handler keeps on every route — the identity gate, the request's id and the request's two events. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run` and the display string; `D02-cli` declares the exit codes and decides that an empty `Args` means serve. This document declares `internal/server`. `D04-pages` declares `pages.Handler` and `pages.Config` and states what is answered at `/`, at `/about`, under `/_appkit/` and at a path that is not a page. appkit's `telemetry` package owns the writer and the request middleware, and its `identity` package the gate; this document wires them and restates none of their contracts.

## The terms home serves on

home serves on the platform's common terms. It serves only on a listening socket it inherits and never opens one of its own; on a host that is `/run/ikigenba/home.sock`, held by `ikigenba-home.socket` beside the `Type=notify` `ikigenba-home.service`. A deploy restarts the service alone, so the socket and the connections queued on it outlive every restart; home's part is to finish what it accepted and leave the socket where systemd put it.

home takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment once it has taken the socket, as that manual page recommends. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket `NOTIFY_SOCKET` names, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace. Taking descriptor 3 in the binary is `net.FileListener`, which, as Go's `net` documentation of `FileListener` and `UnixListener.SetUnlinkOnClose` states, leaves the socket's path in place when the listener is closed.

The suite is a closed system: home trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them. Every request has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it, 32 lowercase hexadecimal digits.

home's standard error holds only trouble: a start it refuses, a socket it cannot take, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off, and the lines for an event it could not deliver. A request answered with any status, the missing-identity 500 included, is handled and recorded in the trail and earns no line. So the handler has no stream, and while telemetry takes every event a running home writes nothing to either stream.

## Checking the start

With `Args` empty, `Run` checks, in this order: `DRAIN_SECONDS`, then whether a socket was passed in. `DRAIN_SECONDS` is spelled as opsctl writes an integer — one or more ASCII digits, no sign, no leading zero, no unit, no white space — and is 5 when unset or empty; home sets no upper limit. A value that is not acceptable is a usage error, quoted back verbatim, and is reported whether or not a socket was passed in. A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one; anything else is no socket passed in, and a count above one is a unit home will not guess about. Both are usage errors, exit 2, with the detail line saying how to run home, and none of the refused starts takes the descriptor, unsets a variable, serves, tells systemd anything, or records an event.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv` and takes descriptor 3 as its listener, through `Process.Inherit`. A descriptor that cannot be made into a listener is trouble on the host: `home: ` and the error, exit 1.

## Readiness and the run's writer

`Run` builds the run's writer with appkit's `telemetry.New`, naming the service `pages.ServiceName` and the version `Process.Version`, delivering to `Process.Sink` (appkit's socket sink when it is nil) and writing the line for an undelivered event to `Process.Stderr` through the same guard as its own lines. It looks up `IKIGENBA_SERVICES` once and builds the handler with `pages.Handler` over `Process.Banner`, that value as the services path, and the writer. Nothing about `IKIGENBA_SERVICES` or the file it names can stop a start.

The socket has been listening since systemd made it, so ready is true before the first `Accept`, and sending it first means a failure to send is reported before anything was served: `home: ` and the error, exit 1. Once `READY=1` is sent, or there is no notification socket to send it to, and before any connection is accepted, `Run` calls `Writer.Ready`, so `service.started`, carrying `Process.Version`, is the first event of a run. A context that is done before `Run` has begun to report ready is a stop, not a failure: `Run` sends nothing, accepts nothing, records nothing and returns `ExitSuccess`.

appkit's writer queues and returns, so neither readiness nor any answer waits on telemetry; an event it cannot deliver goes to standard error as `home: undelivered event: ` and the event's JSON, in the order recorded, and home keeps serving. That a telemetry installed after home started is found without a restart is appkit's socket sink, which reads the services file afresh on every delivery.

## Stopping

When `ctx` is done — in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the context's cause — `Run` drains the server through `Serve`, and once every request has finished, or the drain deadline has come, it shuts the writer down with the reason, the text of `context.Cause(ctx)`, which records `service.stopping` and delivers what is queued, inside the same window. With nothing pending the stop is immediate: `service.stopping` is delivered and home exits 0 at once.

The **drain deadline** is `DRAIN_SECONDS` in seconds, the longest `time.Duration` when that many seconds is longer, measured in real time from the cancellation, so a drain test runs with `DRAIN_SECONDS=1` and waits about a second. When the requests use the whole window, every event still queued, `service.stopping` included, is written to standard error before the stop line, which is always `Run`'s last; `Serve` cuts the remaining requests off only after its `stop` has returned, and the client's connection closes without the rest of its answer. `Run` returns less than a second after the deadline and says `home: stopped with <n> requests unfinished` (`1 request` for one), exit 1. A cut-off request's `request.finished`, recorded after the deadline, is written out or not at all, never delivered.

## Serving and stopping the listener

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next home — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then ends those requests' contexts, closes their connections without the rest of their responses, and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. `stop` is called once, when the drain is over, with a context that ends at the deadline. An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `home: ` and the error as `Run`'s last line, exit 1. `Serve` gives its server an `ErrorLog` that goes nowhere, since Go's `net/http` documents that a nil one writes to the real standard error. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` because gosec `G112` demands it.

## The handler's rules on every route

The handler `pages.Handler` returns is appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping appkit's `identity.Require`, wrapping home's routes (`D04-pages`). So every request records its two events, and a request without `X-User-Id` is answered 500 with `identity.MissingBody` whatever its path or method — never 404 or 405, and no page and no shared file for it. home's manifest serves no guests, so nginx never lets such a request through; when one arrives the gate or the host is misconfigured. Routing is on the request's `URL.Path` as `net/http` decodes it, compared exactly, and never redirects.

home calls no sibling while serving a request: the events a request causes go to telemetry apart from it, and no answer waits for them. A request records nothing but its two request events, and the handler records no event of its own.

## Recorded decisions

- `Serve` takes a `stop` function, called once inside the drain window, so the writer's shutdown, and with it `service.stopping`, lands before any cut-off connection is closed.
- The writer is shut down after the requests drain, so `service.stopping` follows every finished request's `request.finished`.
- The drain deadline saturates at the longest `time.Duration`, since `DRAIN_SECONDS` has no upper limit.
- What becomes of the requests in progress at an accept failure, and whether `service.stopping` is recorded then, is left open, as in the precedent.

## Consumer tasks

`main` hands `cli.Run` the real process (`D01-layout-and-run-seam`). With `Args` empty, `Run` reads `DRAIN_SECONDS`, checks `LISTEN_PID` and `LISTEN_FDS`, calls `p.Unsetenv` for the three `LISTEN_*` names and `ln, err := p.Inherit(3)`, builds `w := telemetry.New(telemetry.Config{Service: pages.ServiceName, Version: p.Version, Sink: p.Sink, Stderr: stderr})` and `h := pages.Handler(pages.Config{Banner: p.Banner, ServicesPath: path, Telemetry: w})`; sends `READY=1`, calls `w.Ready()`, and runs `err = server.Serve(ctx, ln, h, drain, stop)` with `stop` calling `w.Shutdown(c, context.Cause(ctx).Error())`; it answers a `*server.DrainError` with `home: ` and its text, exit 1, and returns.

A test of `Run` builds a `cli.Process` with a `LookupEnv` over a map holding `LISTEN_PID` (the `Pid` it sets), `LISTEN_FDS` `1` and a `NOTIFY_SOCKET` it binds in a short temporary directory, an `Inherit` returning a Unix listener it bound, a `Version` of its own, a `*telemetry.Capture` (or a sink that fails or blocks) as `Sink`, and a `Banner` closure of its own. It runs `cli.Run` in a goroutine with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with raw HTTP (`GET /` with and without `X-User-Id`), cancels with `errors.New("SIGTERM")`, and inspects the exit code, the capture in order and the streams. A drain test sets `DRAIN_SECONDS` to `1`, holds a request open with a client that sends a request whose declared `Content-Length` exceeds the bytes it sends, and finds `home: stopped with 1 request unfinished` last on `Stderr` within about two seconds. A test of `server.Serve` serves a handler of its own on a Unix listener, cancels, and checks the drain, the `stop` call and the `*server.DrainError`. A test of the handler builds its own writer with `telemetry.New` over a `*telemetry.Capture`, builds `pages.Handler`, drives it with `httptest`, calls `Writer.Flush`, and asserts on the events by name, attributes, request id and user.
