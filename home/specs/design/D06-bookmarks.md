# D06-bookmarks

Each user's bookmarks themselves: what one is, whose it is, what makes one acceptable, where the set of them is kept and in what order. This is the whole of `internal/bookmarks`: the one table of home's SQLite database, `state/home.db`, the store over it, the limits a name and a URL obey, the five sentences a refused field is answered with and the one line answered when the database cannot be reached, the errors every consumer tells apart, the two directions a bookmark moves in, and the schema the migrations `0001_bookmarks.sql` and `0002_bookmark_order.sql` produce. No request, response, header, markup or event reaches this package. `D01-layout-and-run-seam` declares `cli.Process`, whose `Dir`, `Now` and `Rand` reach the store through `cli.Run`, resolves the path the database lives at, and declares and embeds the root package's `Migrations`; `D03-serve` opens the database with appkit's `db.Open` at start, builds the store over that handle and closes the handle at stop; `D04-pages` draws the landing page's bookmark tiles from the caller's `List`; `D07-bookmarks-page` owns the bookmarks page, the form, the icon, delete and move routes and the bookmark events; `D08-favicon` fetches the icon a `Draft` carries. Opening, migrating, transactions and the failure seam are appkit's `db`, which this document restates none of.

## One table, one writer

home is the database's only writer and the table is the only record of every user's bookmarks: a start that finds no database begins an empty one, and a database home has just created holds no bookmarks. The store does not open anything: `bookmarks.New` builds a store over a handle `db.Open` returned, with the clock it stamps created times from and the random source it draws ids from, and it neither owns nor closes the handle. What is contract is what a reader and a restart see: a store over a later handle on the same file holds what the earlier one held, for every user, field for field and in the same order, its icons included. A test proves that by closing and reopening, and proves the schema by reading the catalogue inside a `DB.Read`.

After both migrations the table `bookmarks` holds, in this order: `id`, the text primary key; `name`, text, not null; `url`, text, not null; `icon`, a blob, null when no icon was found; `icon_type`, text, the icon's media type, null with it; `created_by`, text, not null, the user id of the caller who added the bookmark and so its owner; `created_at`, text, not null, the created time as RFC 3339 in UTC to the second; and `position`, an integer, not declared not null, the bookmark's place in its owner's list. The pair of `created_by` and `name` is unique, the name compared under SQLite's `NOCASE` collation, a constraint the database itself enforces, so a user's duplicate is refused whatever code inserts it, which a test proves by running a raw `INSERT INTO bookmarks` inside a `DB.Write` with a name that differs from one the same user holds only in ASCII case and seeing the write fail and the table unchanged, and the same name for another user succeed. The database outlives a release, so the row's form is contract too: a later release reads what this one wrote, and a change to the table is a new migration under the expand-then-contract rule.

`0001_bookmarks.sql` is frozen and unchanged; it made `name` unique across the whole table. SQLite cannot drop a column-level `UNIQUE`, so `0002_bookmark_order.sql` rebuilds the table: it creates the new one with the seven columns as they were plus `position` last, and the per-user unique pair in place of the global one; copies every row, numbering each user's bookmarks from 1 in the order the space listed them until now, by name with ASCII letters folded to lower case and then by id; drops the old table and renames the new one; and adds an `AFTER INSERT` trigger that, when a new row's `position` is null, sets it to one more than the highest position its owner holds. The trigger is for the previous release's insert, which names seven columns; this release always sets `position` itself. A test proves the upgrade by use: it opens a database with an `fs.FS` holding only `0001_bookmarks.sql`, inserts rows for several users, closes it, reopens it with `home.Migrations()`, and reads each user's list.

## A bookmark

A bookmark is an id, a name, a URL, whose it is, whether it has an icon, and when it was added. Its **id** is `bmk_` and 16 lowercase hexadecimal digits, the 8 bytes one read of the store's random source gives, drawn again when they give the id of any bookmark the store holds, whoever owns it; an id is opaque, unique across the store and never changes. Its **owner** is its `CreatedBy`, the user id of the caller who added it, never an email; there is no other owner field. Its **name** is what a person sees on the tile: trimmed of surrounding white space, 1 to 40 characters counted in runes, and unique among its owner's bookmarks with ASCII letters compared case-insensitively, which is what `COLLATE NOCASE` decides, so one user cannot hold both `Docs` and `docs` while two users may each hold `Docs`, and `Émile` and `émile` can both be held. Its **URL** is an absolute `http` or `https` URL, trimmed, at most 2048 bytes, kept exactly as given; two bookmarks may share one. Its **icon** is the bytes and media type the favicon fetch found, or none; the `Bookmark` type carries only whether there is one, and `Icon` hands out the bytes, so a list never carries every icon. **Created** is the time of the create, in UTC to the second.

## Judging a submission

The form's two strings arrive raw, as a browser or `curl` sent them, and a refused form redraws them untouched, so `Submission` holds them raw and `Validate` judges them, trimming each itself. Each field gets at most one message, and the two are judged independently, so a submission wrong in both is told both at once. For the name: blank is `NameRequiredMessage`, then over `MaxNameRunes` runes is `NameTooLongMessage`. For the URL: over `MaxURLBytes` bytes is `URLTooLongMessage`, then anything that is not an absolute `http` or `https` URL with a host is `URLInvalidMessage`, a blank URL included. `Validate` reads no database, so it never reports a taken name: whether a name is held is decided by `Create`, in the same step as the insert, so two concurrent adds of one name for one user cannot both win. The sentences themselves are copy constants beside the rules that raise them, so the page cannot word them differently; `NameTakenMessage` is declared with them for the page to place after `ErrNameTaken`.

## Yours, in your order

Every read and write is the caller's: `List`, `Icon`, `Delete` and `Move` take the user id, and `Create` takes it as the draft's `CreatedBy`. Another user's bookmark id is treated exactly as an unknown one, so no answer tells a caller that someone else holds it. A user's **content** is what `List` returns for them, in order, and the store's other terms are defined over every user's content at once.

`List` is the user's bookmarks, by position and then by id, read and shown whole. `Create` validates the trimmed values again, answering `ErrInvalid` to anything `Validate` refuses, then decides the name among the owner's bookmarks and inserts as one step, answering `ErrNameTaken` to a name the owner holds; the new bookmark goes at the end of the owner's list; it reads the random source only for a bookmark it adds. `Icon` hands out a bookmark's stored bytes and media type, or `ErrNotFound` when the user holds no such bookmark or it has none. `Delete` removes a bookmark and says whether it removed one; an id the user does not hold is not an error, since removing is idempotent and the page answers both alike. A deleted bookmark's name is free at once, and the bookmarks after it keep their order: delete leaves a gap in the positions, which is harmless since only relative order is seen, and nothing renumbers.

`Move` swaps a bookmark with its neighbour in its owner's list, `Left` toward the start and `Right` toward the end, in one write, and reports the bookmark's index before and after as `Moved` with true. Moving the first bookmark left, the last right, an id the user does not hold, or in any direction other than the two changes nothing and is not an error: the zero `Moved`, false and nil. Concurrent moves are each one step, so the result is the moves applied one after another and no bookmark is lost or repeated. No other user's list changes.

## Errors

`ErrNotFound`, `ErrNameTaken` and `ErrInvalid` are answers about the bookmarks. Any other non-nil error a method returns means the database could not be reached, and every consumer answers it with `Unreachable`, never quoting the error. A test provokes it with the handle's `SetFailing(true)`, under which every method errors and changes nothing; once the switch is off the store answers as before. An invalid draft is refused `ErrInvalid` before the database is touched, whether or not it can be reached.

## Recorded decisions

- Departure: **the bookmarks are listed and read whole**, not paged or windowed (shape's Listing pages a list a person can add to, and its Storage windows a big list in the database): a user's bookmarks are a handful of links on their front door, configuration-sized, and the landing page and the bookmarks page show every one; `List` has no offset or limit (decisions document `ikigenba-bookmarks`, seam 1, which asks for this departure to be recorded; `ikigenba-bookmark-order` keeps them listed whole).
- Decision: **bookmarks belong to the user who added them**, their `created_by`; no column is added for the owner, and another user's id is treated as unknown everywhere (decisions document `ikigenba-bookmark-order`, seam 1, reversing the space-wide set of 2026-10-23).
- Decision: **a user's bookmarks are listed by `position`, then `id`**; `Create` appends, `Move` swaps neighbours, delete leaves a gap and nothing renumbers (decisions document, seam 1).
- Name uniqueness is per user and SQLite's `NOCASE`: ASCII letters fold, every other byte compares as it is (decisions document, seam 1). Folding other letters would need a collation SQLite does not ship. The upgrade numbers existing rows in the `NOCASE` order the space listed them in until now, so no one's bookmarks move when the release lands.
- Decision: **`0002_bookmark_order.sql` rebuilds the table**, because SQLite cannot drop the column-level `UNIQUE` on `name` (decisions document, seam 1).
- Decision (expand then contract): the previous release's `INSERT` names its seven columns and leaves `position` null; the trigger appends the row at the end of its owner's list (decisions document, seam 1).
- Decision (expand then contract): the previous release's `List` reads every row in name order, ignoring `position` and owner, so during a rollback every user sees every user's bookmarks, as they do today. Accepted: it is the current behaviour, and at writing only one user has bookmarks (decisions document, seam 1).
- Decision (expand then contract): the previous release's name check counts the name across all users, so during a rollback it refuses a name any user holds. Accepted for the same reason (decisions document, seam 1).
- Decision: **this release sets `position` itself and never relies on the trigger**; the trigger exists only so the previous release's insert lands in a sensible place (decisions document, seam 1).
- Decision: **`position` is appended last and nullable**, so the previous release's seven-column insert and its reads by column name keep working on the new table (a decision of this design, from the expand-then-contract rule).
- Decision: **`Create` keeps its signature**: `Draft.CreatedBy` already carries the owner, so the store scopes the name check and the append to it rather than taking a second user argument that could disagree with it (a decision of this design).
- Decision: **`Move` reports the indexes it moved between**, as `Moved`, and whether the order changed, so the handler records `bookmark.moved` with `from` and `to` without reading the list again, and records nothing for a move that changed nothing (a decision of this design; the event is `D07-bookmarks-page`'s).
- Decision: **a direction other than `Left` or `Right` is a move that changes nothing**, not an error, so the route can hand the form's value straight in and answer its one redirect (decisions document, seam 2: a missing or unrecognised `to` changes nothing).
- `Validate`'s precedence is the root's ruling (contract skeleton, section 5 item 9, adopted in section 7): a blank name before a long one, a long URL before an invalid one, a blank URL invalid; a taken name only from `Create`.
- `Create` refuses an invalid draft with `ErrInvalid` before it touches the database, so a failing store still answers `ErrInvalid` to one: the page validates first and never sends one, and the order makes the answer independent of the database (a decision of this design).
- There is no `ErrUnreachable` sentinel: every error other than the three is the unreachable answer (contract skeleton, section 2). A failing random source is one such error, as cron's store answers it, rather than dummy's fallback to `crypto/rand`; with the production source it does not happen.
- `Delete` answers a `bool`, not `ErrNotFound`: the page redirects alike for a known and an unknown id, and records `bookmark.deleted` only when one was removed (contract skeleton, section 2, which declares `Delete` as `(bool, error)`; events in `D07-bookmarks-page`).
- An `Icon` with empty `Data` is no icon, whatever its `Type`; a non-empty `Data` is stored with its `Type` exactly as given, so the store judges no media type (contract skeleton, section 2: `Icon` with empty `Data` is no icon, `HasIcon` is `len(d.Icon.Data) > 0`; the stored-as-given `Type` is a decision of this design; `D08-favicon` decides what is an icon).
- A nil `Now` or `Rand` in `Config` means `time.Now` or `crypto/rand.Reader`, which the binary wires through `cli.Run`; no requirement states it, since no permitted test reads the real clock or randomness (cron's store records the same).
- The row's on-disk form is stated, not only its round trip, because the database outlives a release and a later migration rewrites what this one wrote (a decision of this design; the column forms are decisions document seam 1 and contract skeleton, section 2).
- The field sentences arrive from Go as strings, as dummy's form passes them (orchestrator log D7).

## Consumer tasks

`cli.Run` (`D01-layout-and-run-seam`, `D03-serve`) opens the database with `d, err := db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "home.db"), Migrations: home.Migrations(), Now: now, Service: pages.ServiceName, Stderr: stderr})` and builds `st := bookmarks.New(d, bookmarks.Config{Now: now, Rand: rand})`, handing it to `pages.Config.Store`. Every route knows the caller's user id `userID`. The landing page (`D04-pages`) reads `k, err := st.List(ctx, userID)` and copies each `Bookmark`'s `ID`, `Name`, `URL` and `HasIcon` into a tile, in order. The bookmarks page (`D07-bookmarks-page`) reads the same list for its grid; for a `POST /bookmarks` it builds `sub := bookmarks.Submission{Name: name, URL: url}` from the form, redraws with `e := bookmarks.Validate(sub)` when `e.Any()`, otherwise fetches `data, typ := fetcher.Fetch(ctx, strings.TrimSpace(sub.URL))` (`D08-favicon`) and calls `b, err := st.Create(ctx, bookmarks.Draft{Name: sub.Name, URL: sub.URL, CreatedBy: userID, Icon: bookmarks.Icon{Type: typ, Data: data}})`, redrawing with `bookmarks.FieldErrors{Name: bookmarks.NameTakenMessage}` when `errors.Is(err, bookmarks.ErrNameTaken)`; the icon route answers `ic, err := st.Icon(ctx, userID, id)`, `bookmarks.ErrNotFound` being the not-found page; the delete route calls `removed, err := st.Delete(ctx, userID, id)`; the move route calls `m, moved, err := st.Move(ctx, userID, id, bookmarks.Direction(to))` and, when `moved`, records `bookmark.moved` with `m.From` and `m.To`. Every route answers any other non-nil error with `bookmarks.Unreachable`.

A test opens a handle with `db.Open(ctx, db.Config{Path: filepath.Join(t.TempDir(), "state", "home.db"), Migrations: home.Migrations(), Now: clock})`, builds `bookmarks.New(d, bookmarks.Config{Now: clock, Rand: bytes.NewReader(known)})`, creates with `Create` for two or more user ids, reads back with `List` and `Icon` for each, moves with `Move` using `bookmarks.Left` and `bookmarks.Right`, deletes with `Delete`, and closes the handle and opens another on the same path to see the same bookmarks in the same order. It reads `PRAGMA table_info(bookmarks)`, `sqlite_master` and a row of `bookmarks` inside `d.Read`. It inserts rows directly with an `INSERT INTO bookmarks` statement inside `d.Write`, bypassing the store: to see the database itself refuse a second row for one `created_by` whose name matches a held one with ASCII letters folded, such as `DOCS` after `Docs`, leaving the table as it was, and accept one that differs, such as `émile` after `Émile`, or one for another `created_by`; to set `position` and see `List` order by it; and naming only the seven older columns to see the row land last in its owner's list. It builds an `fstest.MapFS` holding the one file `0001_bookmarks.sql` read from `home.Migrations()`, opens a database with it, inserts rows for several users, closes it and reopens with `home.Migrations()` to see the upgrade's order. It calls `d.SetFailing(true)` before a call to see an unreachable store and `d.SetFailing(false)` to see it answer again, and hands in a `Rand` that fails. It calls `bookmarks.Validate` on the accepted and refused values the requirements list and compares fields with the message constants, never their words.
