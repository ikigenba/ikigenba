# D05-on-a-space

What home itself contributes when it runs on a space and in a sandbox, and what it does not. The path from a checkout to a browser on a space or in a sandbox is long, and almost every step on it belongs to someone else: devctl builds and ships the file, opsctl installs it, writes the environment, publishes the socket, bounds the unit and generates nginx, routing the space host itself to home because its manifest marks it the default app; auth decides every credential and whether a request reaches home at all; the host's nginx terminates TLS and sends a guest to sign in; every other app's banner links its product mark to home through appkit; and the sandbox stands the same arrangement up on a developer's machine. home's own share is what the earlier designs already state — the layout, the run seam, the display string and the binary's wiring (`D01-layout-and-run-seam`), the command, the manifest and the file under `etc/` (`D02-cli`), the serve path, the handler's rules and the quiet standard error (`D03-serve`), and the pages (`D04-pages`) — plus one guarantee a space and a sandbox lean on that no single earlier document owns: neither the credential a caller presents nor the caller's email lands in anything home records or writes. This design states that guarantee; for every other outcome on a space or in a sandbox it names the owner, and it says plainly what can be checked only on a running space.

This design declares no name. Everything it states is behaviour of names `D01-layout-and-run-seam` declares: `cli.Run` and `cli.Process`.

## What ships

The release file has three members: `bin/home`, `etc/manifest.toml` and `share/icon.svg`. The manifest is home's contract and is already designed: its exact text is the constant `cli.Manifest` (`D02-cli`, R-JTDB-TME1), the root package's `Etc` holds exactly `manifest.toml` (`D01-layout-and-run-seam`, R-4OZQ-UOEU, R-4RFJ-M7W8), and its contents are exactly that constant (`D02-cli`, R-4Q7N-8G5J); together those prove that nothing is under `etc/` but the manifest and that the committed manifest is byte for byte what `home manifest` prints, which is what `devctl build` checks. The manifest's own lines carry the rest of what a space asks of it: `default = true`, so the space host itself is routed to home; `guests = false`, so the host's nginx admits no visitor without a credential; `mcp = false`, so the services file does not mark home for the gateway; no `[env]`, since `DRAIN_SECONDS` is the space's; no `[database]`, since home keeps nothing; `[resources]` holding only `memory_max = "128M"`; and, last, `[home]` holding only `group = "core"`, with its description tied to the about screen's by R-5I9C-167I.

That the binary in the file, asked `--version` with neither `IKIGENBA_COMMIT` nor `IKIGENBA_RELEASE` set, prints one empty line is `D02-cli`'s `--version` (R-7DBT-2JZP) over the display string `D01-layout-and-run-seam` defines and the binary's wiring (R-4F8J-SIHA, R-DFYA-1J55); that it prints the manifest byte for byte is `D02-cli`'s R-5H1F-NEGT through the same wiring. That the binary is static `linux/amd64` and cgo-free is the release build gate of `AGENTS.md`, not a requirement. That no `assets/` directory or font ships beside the binary follows from the templates being embedded (R-3VQ5-O6M6, R-3WY2-1YCV) and appkit's shared files being served from inside it (`D04-pages`, R-5T8F-H3VR).

The rest of the file is not home's to state. The tarball, its member list and its name carrying the commit are `devctl build`'s; `share/icon.svg` is human-authored (`AGENTS.md`), never written by the build run and never opened by a test, and that its presence shows home's icon as the banner's trail root on home's pages is opsctl's services file read by appkit; home's landing page draws no tile for home.

## On a space

home on a space is the same binary serving on the same terms as under a test: a socket passed as descriptor 3 by the socket-activation protocol, `/opt/home` as its working directory, its environment from `/opt/home/etc/env`, `IKIGENBA_SERVICES` naming the host's services file. Who supplies each of those is opsctl's; what home does with them is the earlier designs'. The table maps each outcome on a space to its owner.

## The credential

On a space every request home receives has been admitted by auth, and the request that reaches home may still carry the client's `Authorization` header; whether and how the host's nginx passes it on is opsctl's, and home does not rely on either answer. home treats every credential form alike, and the guarantees are proved for a `Bearer` and, defensively, a `Basic` one. home never needs the header — the caller is appkit identity's, from the identity headers nginx sets — and a space and a sandbox rely on the credential's secret being in no record home leaves and on no event holding the caller's email. The trail is home's to keep clean, and so is everything home writes to standard error; nginx's logs are opsctl's. home writes no file, so there is nothing on disk to keep clean.

A request carries a **credential header** when its `Authorization` header is `Bearer <p>`, or `Basic ` and the standard base64 of `<u>:<p>`, the test choosing `<u>` and `<p>` long, with a letter other than `a` to `f` in every 8-character stretch so that no hexadecimal id can match them, and occurring nowhere else in what it sends. Its **secret strings** are every run of 8 or more consecutive characters of `<p>`, of `<u>` and of the base64 value, so a partial leak counts as a leak, and every comparison ignores ASCII case. The caller's email is marked the same way: an `X-User-Email` value of letters and digits around one `@`, whose every run of 8 or more characters is an **email string**. A chosen value could collide with what home writes whatever the credential, so a run counts only when its values are **admissible**: none of their strings is held by anything the test's reference run records or writes, the reference run being the same sequence made before it with no `Authorization` header at all and a marked email that shares no such string. A correct home writes nothing that depends on the credential or the email, so a test that checks admissibility, and picks other values when it fails, always finds a run the guarantees speak about, and a home that leaks still fails.

The guarantees are proved over one sequence of requests, the **credential sequence**, made once with every request carrying a `Bearer` credential and once with every request carrying a `Basic` one. It reaches every kind of route home serves — the landing page, the about screen, an appkit path, a path that is no page, a refused method, and requests with no `X-User-Id` that home refuses with appkit's 500. Two guarantees follow. First, no trail event — name, envelope or attribute — holds a secret string or an email string (R-4ACY-9FII); each event's exact keys are already fixed by `D03-serve`, so this is the end-to-end statement of what those already imply, proved through `Run` with a capturing sink. Second, nothing `Run` writes to `Stderr` holds one, including the lines it writes for an event it could not deliver (R-4951-VNRT).

## In a sandbox

In a sandbox home is the same binary in the same arrangement: the sandbox builds it from the worktree, runs it under its own units with a working directory of its own, gives it the environment of a host with `IKIGENBA_COMMIT` set to the worktree's commit, `-dirty` appended when the tree has changes, no `IKIGENBA_RELEASE`, and variables a host never sets, puts its own nginx in front, routes the space host to home as the default app, and routes every request through auth's `/check` because the manifest has `guests = false`. All of that is the sandbox's. home's contributions are the ones it makes on a space:

- It reads nothing from its environment beyond what a host gives it, so the variables only the sandbox sets change nothing it does: every key `Run` looks up is one of `D01-layout-and-run-seam`'s five (R-5ELM-VUZF). `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` are read by `main` for the identity and never through `LookupEnv` (R-DEQD-NREG, R-DFYA-1J55), and appkit's kit and socket sink read `IKIGENBA_SERVICES` from the real environment by appkit's published design.
- Its footer carries the release and commit, and its `--version` and `service.started` the display string, of the identity `main` reads from `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` (R-DEQD-NREG, R-4F8J-SIHA, R-DH66-FAVU, R-41TN-L1BN); the shortening is appkit's `version.Read`, and the value it shortens is the sandbox's.
- Its landing page shows the sandbox's services as the sandbox's services file lists them, read afresh for every page (R-JS5F-FUNC).
- The same credential and email guarantees hold; `sandbox logs home` showing no line is `D03-serve`'s quiet standard error (R-6GEI-QQYY).

## What only a space can show

These outcomes are space-level checks: no test of home can make them, and they are verified on a running space or sandbox. They are recorded here, not required.

- The release file holds exactly `bin/home`, `etc/manifest.toml` and `share/icon.svg`, the binary is a static `linux/amd64` executable, and the icon is an SVG (devctl; home's part is `Etc`, the constant and `--version`, above).
- The bare space host and `home.<space>` both reach home (opsctl's nginx and the sandbox's, from `default = true`).
- Every other app's banner mark links to home, and home's own pages show the mark, the trail root with home's icon, and the page menu with home and About (appkit's banner, from the services file's `home` entry).
- A guest is sent to sign in and a refused credential is answered `403`, in each case nothing reaching home's socket and home recording no event (nginx and auth).
- auth's own records of each request and their sharing a request id with home's events (auth, nginx).
- The host's nginx log holds no token: its format is opsctl's.
- The 128 MiB ceiling and the restart a deploy makes (opsctl, the kernel).
- The landing page's tiles look as the stylesheet draws them, and the page's style, script and favicon are fetched from home's own host (appkit's stylesheet and script; no test runs them).

## REQUIREMENTS

- R-449G-CKT1: home's design defines a request as carrying a **credential header** when it has exactly one `Authorization` header whose value is either `Bearer <p>`, or `Basic ` followed by the standard base64 encoding (RFC 4648, with padding) of `<u>:<p>`, where `<u>` and `<p>` are each at least 16 ASCII letters and digits, and defines that request's **secret strings** as every substring of 8 or more characters of `<p>`, of `<u>`, and of that base64 value; defines a request's **marked email** as its one `X-User-Email` value when that value is at least 16 ASCII letters and digits with exactly one `@` inserted, not first or last, and that request's **email strings** as every substring of 8 or more characters of its marked email; requires that every secret string and every email string hold at least one ASCII letter that is none of `a` to `f` and `A` to `F`; defines that a text **holds** a secret string or an email string when the string occurs in the text with ASCII letters compared case-insensitively; and requires that no secret string and no email string occur, compared that way, anywhere else in what the test hands home — no other header, URL path or query or request body of any request in the same test, and no fixture it places in its temporary directory; every requirement of home's design that names a credential header, a marked email, their secret strings or email strings, or a text holding one MUST denote that.
- R-47X5-HW14: home's design defines the **credential sequence** as the following requests made to the listener `Run` serves on, one after another, every request carrying a marked email and a credential header, of the `Bearer` form on every request of a first pass and of the `Basic` form on every request of a second pass made after the first in the same `Run`: with no `X-User-Id` header, `GET /`, `HEAD /` and `POST /about`; then, every request carrying the same non-empty `X-User-Id`, `GET /`, `HEAD /`, `GET /about`, `GET /_appkit/theme.css`, `GET` of a path that is no page, and `POST /`; defines the **reference run** of a run of the credential sequence as the run of `Run` the test makes before it that is the same in every respect — the services file `IKIGENBA_SERVICES` names, `X-User-Id`, the environment `p.LookupEnv` reports, the banner source and what the `Deliver` of `p.Sink` returns — except that none of its requests carries an `Authorization` header and its marked email holds none of the email strings of the run's; and defines a run of the credential sequence as **admissible** when none of its secret strings and email strings is held by the name, request id, user or the text or decimal form of any attribute value of any event handed to `p.Sink`'s `Deliver` in its reference run, or by what its reference run writes to `Stderr`; and every requirement of home's design that names the credential sequence, a reference run or an admissible run MUST denote that.
- R-4ACY-9FII: When `Run` serves an admissible run of the credential sequence with a non-nil `Sink`, no event handed to that `Sink`'s `Deliver` from the call of `Run` to its return MUST hold any secret string or any email string of any request of that sequence in its name, its request id, its user, or the value of any of its attributes, a string attribute's text and the decimal form of a numeric attribute alike.
- R-4951-VNRT: When `Run` serves an admissible run of the credential sequence with a `Sink` whose `Deliver` always returns an error that wraps `telemetry.ErrRejected`, and is then stopped by the cancellation of its context, nothing `Run` writes to `Stderr` from its call to its return MUST hold any secret string or any email string of any request of that sequence.
