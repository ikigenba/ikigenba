# D05-on-a-space

What home itself contributes when it runs on a space and in a sandbox, and what it does not. The path from a checkout to a browser on a space or in a sandbox is long, and almost every step on it belongs to someone else: devctl builds and ships the file, opsctl installs it, writes the environment, publishes the socket, bounds the unit, keeps and replicates the database and generates nginx, routing the space host itself to home because its manifest marks it the default app; auth decides every credential and whether a request reaches home at all; the host's nginx terminates TLS and sends a guest to sign in; every other app's banner links its product mark to home through appkit; the sites members bookmark answer home's favicon fetch or do not; and the sandbox stands the same arrangement up on a developer's machine. home's own share is what the earlier designs already state — the layout, the run seam, the database path, the display string and the binary's wiring (`D01-layout-and-run-seam`), the command, the manifest and the file under `etc/` (`D02-cli`), the serve path, the opening of the database, the handler's rules and the quiet standard error (`D03-serve`), the landing page and the about screen (`D04-pages`), the store (`D06-bookmarks`), the bookmarks page, its routes and its events (`D07-bookmarks-page`) and the favicon fetch (`D08-favicon`) — plus one guarantee a space and a sandbox lean on that no single earlier document owns: neither the credential a caller presents nor the caller's email lands in anything home records, keeps on disk or sends out. This design states that guarantee; for every other outcome on a space or in a sandbox it names the owner, and it says plainly what can be checked only on a running space.

This design declares no name. Everything it states is behaviour of names `D01-layout-and-run-seam` declares: `cli.Run` and `cli.Process`.

## What ships

The release file has three members: `bin/home`, `etc/manifest.toml` and `share/icon.svg`. The manifest is home's contract and is already designed: its exact text is the constant `cli.Manifest` (`D02-cli`), the root package's `Etc` holds exactly `manifest.toml` (`D01-layout-and-run-seam`, R-4OZQ-UOEU, R-4RFJ-M7W8), and its contents are exactly that constant (`D02-cli`, R-4Q7N-8G5J); together those prove that nothing is under `etc/` but the manifest and that the committed manifest is byte for byte what `home manifest` prints, which is what `devctl build` checks. The manifest's own lines carry the rest of what a space asks of it: `default = true`, so the space host itself is routed to home; `guests = false`, so the host's nginx admits no visitor without a credential; `mcp = false`, so the services file does not mark home for the gateway; no `[env]`, since `DRAIN_SECONDS` is the space's; `[database]` naming `state/home.db`, which the host keeps and replicates; `[resources]` holding only `memory_max = "128M"`; and, last, `[home]` holding only `group = "core"`, with its description tied to the about screen's by R-5I9C-167I.

That the binary in the file, asked `--version` with neither `IKIGENBA_COMMIT` nor `IKIGENBA_RELEASE` set, prints one empty line is `D02-cli`'s `--version` (R-7DBT-2JZP) over the display string `D01-layout-and-run-seam` defines and the binary's wiring (R-4F8J-SIHA, and `D01-layout-and-run-seam`'s statement of what `main` hands `Run`); that it prints the manifest byte for byte is `D02-cli`'s R-5H1F-NEGT through the same wiring. That the binary is static `linux/amd64` and cgo-free is the release build gate of `AGENTS.md`, not a requirement. That no `assets/` directory or font ships beside the binary follows from the templates being embedded (`D01-layout-and-run-seam`'s `Assets`) and appkit's shared files being served from inside it (`D04-pages`, R-5T8F-H3VR). That no migration ships beside it follows from the migrations being embedded too (`D01-layout-and-run-seam`'s `Migrations`). That the database is not in the file, and that home creates `state/home.db` under its working directory on its first start, is `D01-layout-and-run-seam`'s (the database path under `Dir`, and the binary keeping it under its working directory) and `D03-serve`'s (a fresh database at the first start).

The rest of the file is not home's to state. The tarball, its member list and its name carrying the commit are `devctl build`'s; `share/icon.svg` is human-authored (`AGENTS.md`), never written by the build run and never opened by a test, and that its presence shows home's icon as the banner's trail root on home's pages is opsctl's services file read by appkit; home's landing page draws no tile for home.

## The credential

On a space every request home receives has been admitted by auth, and the request that reaches home may still carry the client's `Authorization` header; whether and how the host's nginx passes it on is opsctl's, and home does not rely on either answer. home treats every credential form alike, and the guarantees are proved for a `Bearer` and, defensively, a `Basic` one. home never needs the header — the caller is appkit identity's, from the identity headers nginx sets — and a space and a sandbox rely on the credential's secret and the caller's email being in no record home leaves, in nothing home keeps on disk, and in no request home sends to the sites its members bookmark. The trail is home's to keep clean, and so is everything home writes to standard error, everything it keeps under its working directory, the database and its sidecar files included, and every request its favicon fetch sends; nginx's logs and the replicas of the database are opsctl's.

A request carries a **credential header** when its `Authorization` header is `Bearer <p>`, or `Basic ` and the standard base64 of `<u>:<p>`, the test choosing `<u>` and `<p>` long, with a letter other than `a` to `f` in every 8-character stretch so that no hexadecimal id can match them, and occurring nowhere else in what it sends. Its **secret strings** are every run of 8 or more consecutive characters of `<p>`, of `<u>` and of the base64 value, so a partial leak counts as a leak, and every comparison ignores ASCII case. The caller's email is marked the same way: an `X-User-Email` value of letters and digits around one `@`, whose every run of 8 or more characters is an **email string**. A chosen value could collide with what home writes whatever the credential, so a run counts only when its values are **admissible**: none of their strings is held by anything the test's reference run records, writes, leaves on disk or sends through its HTTP client, the reference run being the same sequence made before it, in a second directory holding the same starting contents and with the same clock, random source and HTTP answers, but with no `Authorization` header at all and a marked email that shares no such string. A correct home writes nothing that depends on the credential or the email, so a test that checks admissibility, and picks other values when it fails, always finds a run the guarantees speak about, and a home that leaks still fails.

The guarantees are proved over one sequence of requests, the **credential sequence** (R-34VS-2UR8), made once with every request carrying a `Bearer` credential and once with every request carrying a `Basic` one. It reaches every kind of route home serves — the landing page, the about screen, an appkit path, a path that is no page, a refused method, requests with no `X-User-Id` that home refuses with appkit's 500, and the bookmarks page, an add whose favicon fetch goes through the test's own HTTP client and finds an icon, that icon, a second add, that second bookmark's move one place left, the first bookmark's removal, and a last add that the sequence never removes, so a bookmark each pass made is still in the database when its files are checked. Four guarantees follow. First, no trail event — name, envelope or attribute — holds a secret string or an email string (R-MCK6-JYLH); each event's exact keys are already fixed by `D03-serve` and `D07-bookmarks-page`, so this is the end-to-end statement of what those already imply, proved through `Run` with a capturing sink. Second, nothing `Run` writes to `Stderr` holds one, including the lines it writes for an event it could not deliver (R-MDS2-XQC6). Third, nothing home leaves on disk holds one: after the sequence, no file under the test's temporary directory that holds `Dir` — the database and its SQLite sidecar files included, and anything beside `Dir` — holds a secret string or an email string unless it is byte for byte as it was before `Run` was called, and no entry the run made there holds one in its path (R-YSFR-NA2O). Fourth, no request home sends through `p.HTTP` holds one in its URL, its headers or its body (R-KT8X-S0TS), so the site a member bookmarks never learns who added it or what credential they presented.

## In a sandbox

In a sandbox home is the same binary in the same arrangement: the sandbox builds it from the worktree, runs it under its own units with a working directory of its own, gives it the environment of a host with `IKIGENBA_COMMIT` set to the worktree's commit, `-dirty` appended when the tree has changes, no `IKIGENBA_RELEASE`, and variables a host never sets, puts its own nginx in front, routes the space host to home as the default app, and routes every request through auth's `/check` because the manifest has `guests = false`. All of that is the sandbox's. home's contributions are the ones it makes on a space:

- It serves under the sandbox like any app; its database is `state/home.db` under its working directory (`D01-layout-and-run-seam`), so it is created on the first `up` (`D03-serve`'s fresh database) and survives `down` and `up` because the sandbox keeps that directory until `wipe`; the bookmarks each user added in a sandbox are still there after a redeploy.
- It reads nothing from its environment beyond what a host gives it, so the variables only the sandbox sets change nothing it does: every key `Run` looks up is one of `D01-layout-and-run-seam`'s five (R-5ELM-VUZF). `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` are read by `main` for the identity and never through `LookupEnv` (R-DEQD-NREG, and `D01-layout-and-run-seam`'s statement of what `main` hands `Run`), and appkit's kit and socket sink read `IKIGENBA_SERVICES` from the real environment by appkit's published design.
- Its footer carries the release and commit, and its `--version` and `service.started` the display string, of the identity `main` reads from `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` (R-DEQD-NREG, R-4F8J-SIHA, R-DH66-FAVU, R-41TN-L1BN); the shortening is appkit's `version.Read`, and the value it shortens is the sandbox's.
- Its landing page shows the sandbox's services as the sandbox's services file lists them, read afresh for every page (`D04-pages`, and the binary's landing page in `D01-layout-and-run-seam`), under the caller's own bookmarks.
- Its favicon fetch reaches what the sandbox's host can reach, a sibling's own URL in the sandbox included (`D08-favicon`); which sites answer is the sandbox's and theirs.
- The same credential and email guarantees hold; `sandbox logs home` showing no line is `D03-serve`'s quiet standard error.

## What only a space can show

These outcomes are space-level checks: no test of home can make them, and they are verified on a running space or sandbox. They are recorded here, not required.

- The release file holds exactly `bin/home`, `etc/manifest.toml` and `share/icon.svg`, the binary is a static `linux/amd64` executable, and the icon is an SVG (devctl; home's part is `Etc`, the constant and `--version`, above).
- The bare space host and `home.<space>` both reach home (opsctl's nginx and the sandbox's, from `default = true`).
- Every other app's banner mark links to home, and home's own pages show the mark, the trail root with home's icon, and the page menu with home and About and no row for the bookmarks page (appkit's banner, from the services file's `home` entry; `D07-bookmarks-page` records why).
- A guest is sent to sign in and a refused credential is answered `403`, in each case nothing reaching home's socket and home recording no event (nginx and auth).
- auth's own records of each request and their sharing a request id with home's events (auth, nginx).
- The host's nginx log holds no token: its format is opsctl's.
- The 128 MiB ceiling, the database's replication and the restart a deploy makes (opsctl, the kernel, litestream).
- A real site's favicon is found and drawn: what a site serves, and whether the host can reach it, is the site's and the network's; home's part is the fetch over the client it is handed (`D08-favicon`).
- The landing page's tiles look as the stylesheet draws them, a bookmark's icon is fetched by the browser from home's own host and from no site, and the page's style, script and favicon are fetched from home's own host (appkit's stylesheet and script; no test runs them).

## Recorded decisions

- The email guarantee extends to disk and to outbound fetches. cron's disk guarantee covers only the credential, because cron keeps the owner's email by design; home keeps none. A bookmark records who added it as the caller's `X-User-Id`, never the email (`D07-bookmarks-page`), as the decisions document asks, so no secret string and no email string may land in the database, its sidecars or anything else under the test's directory, and the favicon fetch carries neither to the bookmarked site.
- The disk and fetch guarantees are proved over the same credential sequence as the trail and standard-error ones, so one admissibility check covers all four; the reference run starts in a second directory holding the same contents and shares the clock, the random source and the HTTP answers, so the bookmarks it creates have the same ids, times and icons, and only the credential and the email differ. Each pass ends with a bookmark it never removes, so the disk check reads a live row the request with the marked email made, not only the free space a removed row leaves, whose contents are SQLite's and not home's to promise.
- The bookmark's name and URL are what a member typed and are kept and shown by design; the test chooses them, and the definition of a credential header already keeps every secret and email string out of them, so they cannot make a run fail.

## Consumer tasks

`main` hands `cli.Run` the real process with `Now`, `Rand` and `HTTP` nil and `Dir` empty (`D01-layout-and-run-seam`), so on a space and in a sandbox the database sits under the working directory opsctl or the sandbox gives the unit, and the favicon fetch goes out over the default client.

A test of the guarantees builds two temporary directories with the same contents, a services file of its own among them, so that every path it hands a run, `Dir` and the services file's included, differs from the other run's only in the directory it sits in, and runs `cli.Run` twice with a `cli.Process` set as `D03-serve`'s consumer tasks describe, adding `Dir` inside the run's own directory, a `Now` that returns one fixed time, a `Rand` that yields the same byte stream from its first read in both runs, a sink whose `Deliver` always returns the same value, and an `HTTP` whose transport is a function of its own that records each request and answers every one with the same small image. These are properties of what the test hands each run, never of what home happens to read or send, so a home that reads or sends more when a credential is present cannot disqualify its own reference run. The first run is the reference run: it makes the credential sequence with no `Authorization` header and a marked email of its own, reading the ids for the icon, move and delete paths from the `bookmark.created` events it captures, and ending each pass with an add under a fresh name that it leaves in place; the test collects every event, `Stderr`, every recorded request and every file and path under the reference directory, and checks that none holds a string of the values it picked for the second run, choosing others when one does. The second run makes the same sequence with a `Bearer` pass and then a `Basic` pass, and the test checks the captured events, `Stderr`, each recorded request's URL, headers and body, and, after `Run` returns, every file under its directory that changed and every path it made, `state/home.db` and its sidecars included, for any secret string or email string, ignoring ASCII case. A second pair of runs with a sink that rejects every event checks `Stderr` alone.
