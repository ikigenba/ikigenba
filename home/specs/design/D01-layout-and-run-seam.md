# D01-layout-and-run-seam

home is the suite's front door: one Go binary that serves, to a signed-in user, a landing page at `/` showing that user's own bookmarks, in the user's order, and then every other service on the space as tiles, backend services apart from core services, a bookmarks page at `/bookmarks` where each signed-in user adds, removes and reorders their own bookmarks, and an about screen at `/about`. Its manifest marks it the host's default app, so it answers at `home.<space>` and at the space host itself, and it is the home the banner's product mark links to on every app's pages. Its one piece of state is its users' bookmarks, each the own of the user who added it and kept in that user's order, which it keeps in a SQLite database of its own, with the icon of each, fetched from the bookmarked site once, when the bookmark is added. No user sees, opens, moves or removes another user's bookmark. It offers no MCP tools, neither emits nor accepts an event on the suite's event bus, and records in the trail, beyond appkit's request and service events, only its own `bookmark.created`, `bookmark.deleted` and `bookmark.moved`. This design is the structural ground the other designs stand on: where the code lives, which package owns which concern, the seam through which the process is run so that the command, the server, the store and the pages can be tested without a real process, where the database lives, where the version it shows comes from, and the one binary's wiring. `D02-cli` declares the exit codes, the usage text and the manifest and states what `Run` does with arguments, `db status` among them; `D03-serve` states the serve path `Run` follows with none, opening the database included, and the rules the handler keeps on every route; `D04-pages` declares the pages, their data and the handler, and states the landing page and the about screen; `D05-on-a-space` is what home contributes to a space and a sandbox; `D06-bookmarks` is the store; `D07-bookmarks-page` is the bookmarks page, its routes (adding, removing and moving a bookmark) and its events; `D08-favicon` is the fetch of a bookmark's icon.

The module is `github.com/ikigenba/ikigenba/home`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/home`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/home` is wiring only.

## The two dependencies

home depends on two modules besides the standard library. The first is `github.com/ikigenba/ikigenba/appkit`, required at a published release through the ordinary module proxy and checksum database, with no `replace` directive. Which release is data that `AGENTS.md` and `go.mod` hold; no requirement names one. appkit is a sibling reached only through its published packages, and home uses six of them: `page` (the banner and footer, the template set the four templates are parsed into, and the shared static files under `/_appkit/`), `services` (the services file, read afresh for auth's links and the landing page's tiles), `identity` (`Require` on every route), `telemetry` (the event contract, the request middleware, the writer every event goes through, the socket sink, the ingest handler and the capturing sink tests use), `db` (the database open path, its migrations and `db status`), and `version` (below). appkit owns all of their contracts; home restates none. In particular the banner's product mark, its trail root, its page menu and the footer are appkit's `Kit.Banner` and appkit's templates; home states only which banner each page is drawn with, which levels it sets, and which services the landing page draws as tiles. The banner's page menu has no row an app supplies, so the bookmarks page is reached from the landing page, not from the menu (`D07-bookmarks-page`).

The second is `golang.org/x/net/html`, the Go project's HTML tokenizer, through which `internal/favicon` finds a page's icon links (`D08-favicon`). The decisions document that delivered bookmarks accepted it as a dependency; which release is data, as for appkit.

`github.com/ikigenba/ikigenba/appkit/version` is the code identity the host gives every app: `version.Read()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment at the time of the call and returns a `version.Identity`, the release and the short commit, both empty when neither variable is set: the run's **identity**. Its `String` method gives the **display string**, which is what `version.Display()` returns for the same environment, the empty string when neither is set. How either is built is appkit's contract, and home's tests do not re-prove it. home carries no version of its own: nothing in its source or its build names one.

## Where the environment is read

`main` makes the one read of the environment that is not `Run`'s own: it calls `version.Read` exactly once, first, and holds the result, the identity, as the version home shows everywhere it shows one. It hands that identity to `page.New`, whose banners carry its release and commit to the footer, and its display string, from `String`, to `Run` as `Process.Version`, which `Run` writes for `--version` and gives the run's writer as its version. Nothing below `main` calls `version.Read` or `version.Display`, so a test of `Run` hands it any string as `Version`, the empty string included, and sets no variable.

`Run` reads every variable through `Process.LookupEnv`: `DRAIN_SECONDS` once at start, `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness (`D03-serve`), and `IKIGENBA_SERVICES` once, when it starts to serve, whose value it hands the handler as the services path that auth's links and the landing page's tiles are read from afresh for every page. A broken or absent services file never stops a start; it reads as a file that lists no services. home starts no process, so it has no environment to compose for one.

Two readers of `IKIGENBA_SERVICES` sit outside the seam, both appkit's: `page.New` reads the real environment when it is called and keeps the path, its kit's `Banner` reading the file afresh on every call; and appkit's socket sink reads the variable, and the file it names, on every delivery. So `main` calls `page.New` once and puts the kit's `Banner` method in `Process.Banner`; and the socket sink is what a nil `Process.Sink` means, used only by the binary, while a test of `Run` names its own sink.

## Packages

The module's root package, `home`, holds what the module embeds, because Go's `embed` reaches only files at or below the embedding package's directory. It exports `Assets`, a file system holding exactly the four templates from `assets/` — `landing.html`, `about.html`, `notfound.html` and `bookmarks.html` — which `internal/pages` parses into the set `page.Templates()` returns (`D04-pages`); `Etc`, a file system holding exactly `manifest.toml` from `etc/`, through which a test proves the committed manifest is the copy of `cli.Manifest` that `devctl build` requires (`D02-cli`); and `Migrations`, a file system holding exactly the migrations from `migrations/`. Nothing else lives at the root.

The database's schema is a sequence of migration files, each named with a four-digit version, that the binary carries and appkit's `db` applies in order. home carries two: `0001_bookmarks.sql`, which created the `bookmarks` table, and `0002_bookmark_order.sql`, which rebuilds it so each bookmark has an owner-scoped name and a position in its owner's order; `D06-bookmarks` describes the table they leave. `0001_bookmarks.sql` has run on a production-grade space and is frozen, so the reordering came as a second file rather than an edit to the first. `Migrations()` is what `Run` hands `db.Open` and `db.Status`, and what a test hands `db.Open` to make a database of home's shape in its own temporary directory; it is the same on every call and depends on no file beside the binary. A later migration is a new file with the next version; none is edited once it has run on a production-grade space.

Five internal packages hold the concerns, one each.

- `internal/cli` owns the program as a command: the run seam (this document), the exit codes, the usage text, the manifest and `db status` (`D02-cli`), and the serve path: reading the drain deadline and the services path, taking the socket, opening the database, building the run's writer, the store, the fetcher with its User-Agent, and the handler, readiness, and the stop (`D03-serve`).
- `internal/server` owns a listener's life: serving a handler and draining for a deadline (`D03-serve`).
- `internal/pages` owns the whole HTTP surface: `ServiceName` and `Description`, the template set, the four templates' data, and the one handler, which wraps every route in appkit's request middleware and identity gate, answers `/`, `/about`, the bookmarks routes and every path that is not a page, and hands `/_appkit/` to appkit's shared files (`D04-pages`, `D07-bookmarks-page`; the rules on every route are `D03-serve`'s).
- `internal/bookmarks` owns the users' bookmarks: the store over the database, every read and write scoped to one user, each user's order and the move that changes it, its types, validation, limits and errors, and the bookmark id (`D06-bookmarks`).
- `internal/favicon` owns the fetch of a bookmark's icon over the run seam's HTTP client, within one budget (`D08-favicon`).

There is no separate route package: home's route table is its pages, the bookmarks routes and one delegation, all of them the pages' concern, so it lives with the handler, as the gateway's does in the precedent for a pages-only app. Dependencies point one way: `cmd/home` imports `internal/cli`, `internal/pages` and appkit; `internal/cli` imports `server`, `pages`, `bookmarks`, `favicon` and the root package; `pages` imports the root package, `bookmarks` and `favicon`; the root package, `server`, `bookmarks` and `favicon` import nothing of home's. So `favicon` cannot read `pages.Description`, and `cli` builds the User-Agent it hands the fetcher. Which package imports which is not observable, so this paragraph is guidance.

## Why there are eight documents

home has a store and events of its own, so it carries the documents an app with those carries, and none of the documents an app with tools or a bus carries. `D01-layout-and-run-seam` lays out the module, the run seam, the paths and the binary's wiring; `D02-cli` holds the commands, the manifest with its `[database]` table, and `db status`; `D03-serve` holds the serve path, opening the database included, and the rules on every route; `D04-pages` holds the pages' data, the handler, the landing page and the about screen; `D05-on-a-space` holds what home contributes to a space and a sandbox, its database among them; `D06-bookmarks` holds the store and the schema of `0001_bookmarks.sql` and `0002_bookmark_order.sql`; `D07-bookmarks-page` holds the bookmarks page, the routes that add, remove and move bookmarks, and their events; and `D08-favicon` holds the fetch that finds each bookmark's icon. Its manifest says `mcp = false`, so there is no `/mcp`, no MCP server on the run seam and no `/tools` page. It neither emits nor accepts a bus event, so there is no emitter, no `/events` and no `/declarations`, and so no nginx fragment, which exists only to keep those two paths off the public name. The events it records are appkit's `request.started` and `request.finished`, from the request middleware, and `service.started` and `service.stopping`, from the run's writer, which `D03-serve` states, and its own `bookmark.created`, `bookmark.deleted` and `bookmark.moved`, which `D07-bookmarks-page` states.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, the clock, the random source, the network or the environment-reading constructor, and returns the exit code: the arguments without the program name, an environment lookup, a way to remove a variable from it, the process's own id, the two output streams, the display string, a way to turn an inherited descriptor into a listener, the clock, the random source, the directory the database lives under, the HTTP client the favicon fetch goes through, the banner source, and the sink the run's writer delivers to.

`Now` is the clock every time home stamps is read from: a bookmark's created time, the time each migration is recorded as applied at, and every event's time. `Rand` is the source of every value home mints: request ids, which the run's writer and appkit's middleware draw, and bookmark ids, `bmk_` and sixteen lowercase hex digits. `Run` reads `Rand` from one goroutine at a time, so a test may hand in a reader that is not safe for concurrent use. `Dir` is the directory the database path resolves against. `HTTP` is the client every request of a favicon fetch is sent through: a test hands one whose transport answers as a fake site does, so no test reaches the network. `Run` builds the fetcher with the User-Agent `pages.ServiceName + " (" + pages.Description + ")"`, scrapes' form. A nil `Now`, `Rand` or `HTTP` is `time.Now`, `crypto/rand.Reader` or `http.DefaultClient`, and an empty `Dir` the process's working directory; those defaults are what the binary uses, and a test never leaves them so, since they would reach the real clock, the real random source, the network or the developer's own directory.

There is no timer or pause on the seam: home waits for nothing but the drain, which runs on real time, and the fetch's budget, a context deadline `D08-favicon` states and a test proves through the deadline its transport sees, never by waiting. Nothing below `main` reads `os.Args`, the real environment, the real pid or the real streams, changes the real environment, calls `version.Read`, `version.Display` or `page.New`, or installs a signal handler.

## Paths

Relative to `Process.Dir` (the process's own working directory when empty, which is how `main` leaves it; `/opt/home` on a host, the app's directory in a sandbox): the database is the SQLite file `state/home.db`, opened with `db.Open`, `home.Migrations()` and `Process.Now`, `state/` created when absent. The diagnostics of `D02-cli` and `D03-serve` name the path in this relative form whatever `Dir` holds. home writes nothing outside `Dir`.

## The version

`internal/cli` declares no version. The one version home shows is the identity `main` reads from appkit's `version.Read`: its display string in `home --version` (`D02-cli`, through `Process.Version`) and in `service.started`'s `version` (through `Process.Version` and the run's writer), and its release and commit in the footer of every page (through `page.New(pages.ServiceName, id)`, `id` being that identity, and the banner's `Release` and `Commit`). Its value is data the host supplies at run time, never a requirement's: the binary's requirements compare with what `version.Read` and `version.Display` return under the same two values, so no test spells a version.

## Recorded decisions

- `internal/pages` owns the handler and its route table; no `internal/web` exists, since every route is a page, a bookmarks route or the one delegation to appkit's shared files.
- `DRAIN_SECONDS` is read and refused by `Run` itself, as in the precedent for a pages-only app; there is no settings package for one value.
- `Process` carries `Now`, `Rand` and `Dir` as cron declares them and `HTTP` as scrapes declares it, nil meaning `time.Now`, `crypto/rand.Reader` and `http.DefaultClient` (decisions log D3, D4). It carries no timer or pause, since home waits only on the drain and the fetch's budget, both real time that no test waits out.
- An empty `Dir` is the process's working directory, as cron treats it, and the binary leaves it empty; the decisions log's "required as cron requires it" is read as cron's actual rule (root ruling 8.7).
- The run's writer takes `Now` and `Rand`, as cron's does, so event times and request ids come from the seam like bookmark times and ids (root ruling 7.1).
- `Run`, not `internal/favicon`, builds the User-Agent, since `favicon` imports nothing of home's, as scrapes' `cli` builds its scrapers' (decisions log D3; the string is the decisions document's, seam 3).
- `golang.org/x/net/html` is home's one external dependency beyond appkit, accepted in the decisions document (seam 3).
- The root package exports `Etc` beside `Assets`, holding `manifest.toml`, so that the committed file is proved equal to `cli.Manifest` by use and the layout `AGENTS.md` describes holds.
- `main` reads the identity once, with `version.Read`, and takes the display string from its `String` rather than calling `version.Display` as well, so the footer and `--version` always come from one read.
- The wiring of `main` is proved at the binary by the one exec'ing test of `AGENTS.md`, since `main` is not usable from a test; the binary requirements below are what that test proves. The binary never adds a bookmark, so its nil `HTTP` never reaches the network.

## Consumer tasks

The binary's start: `main` first calls `id := version.Read()` and hands `cli.Run` a `cli.Process` whose `Args`, `LookupEnv`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Version` is `id.String()`, whose `Banner` is the `Banner` method of `page.New(pages.ServiceName, id)`, whose `Inherit`, `Now`, `Rand`, `HTTP` and `Sink` are left nil and whose `Dir` is left empty; it cancels the context on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name, and exits with what `Run` returns.

A test of the run seam builds a `cli.Process` with a `LookupEnv` over a map, an `Inherit` returning a listener it bound, a `NOTIFY_SOCKET` it holds, a `Version` string of its own, a `Now` returning a fixed time, a `Rand` of its own (a `*bytes.Reader` of `0x5a` bytes long enough for the run, say), a `Dir` inside a `t.TempDir()`, an `HTTP` whose `Transport` answers every request as a fake site does and records it, a `*telemetry.Capture` as `Sink` and a `Banner` from `page.New` (having set `IKIGENBA_SERVICES` with `t.Setenv`) or a closure of its own, calls `cli.Run` with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with raw HTTP, form-encoded `POST /bookmarks` included, cancels, and inspects the capture, the streams, the transport's requests and the temporary tree. To see what a run left in the database it runs `Run` again over the same `Dir`, or, once `Run` has returned, opens `state/home.db` under `Dir` with `db.Open` and `home.Migrations()`, or calls `db.Status` over it. A test of the root package calls `home.Assets()`, `home.Etc()` and `home.Migrations()` and lists and reads them with `fs.ReadDir` and `fs.ReadFile`. The one test that execs the binary builds `cmd/home` and runs it as several separate children, each serving child in a fresh empty temporary working directory of its own, composing each child's environment itself. Where it sets non-empty `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` in a child, it computes the display string it expects by calling `version.Display`, and the identity it expects by calling `version.Read`, after setting the same two values with `testing.T.Setenv`. It runs `--version` with neither variable in the child's environment and expects exactly one empty line, and runs `manifest`, `bogus` and a bare start with no socket. The serving runs each pass a listening socket as descriptor 3 and a `NOTIFY_SOCKET` the test holds: one with `IKIGENBA_SERVICES` unset, which requests `/about` (R-DH66-FAVU); one with a services file of `cron`, `home`, `auth`, `sites`, `scripts` and `events`, core and backend entries out of name order and one without an icon, that the test rewrites while the child serves, which requests `/` before and after the rewrite, computing each landing data it expects from `services.Read` of the file as it then stands and an empty bookmark list (R-LV0W-SA24), and after whose exit the working directory holds `state/home.db` (R-LW8T-61ST); and runs with a services file whose `telemetry` entry names a socket the test holds, serving `telemetry.IngestHandler` over a `*telemetry.Capture`, from which it reads the trail, one such run stopped by `SIGTERM` and another by `SIGINT` (R-41TN-L1BN, R-6ZWW-V2U2). After each serving child exits, it checks that the socket path still exists and still accepts a connection, since the binary leaves `Inherit` nil and is the one place that proves R-72CP-MMBG.
