# D01-layout-and-run-seam

home is the suite's front door: one Go binary that serves, to a signed-in user, a landing page at `/` showing every service on the space as tiles under the launcher's rules, and an about screen at `/about`. Its manifest marks it the host's default app, so it answers at `home.<space>` and at the space host itself, and it is the home the banner's product mark links to on every app's pages. It holds no state, keeps no database, offers no MCP tools, neither emits nor accepts an event on the suite's event bus, and records nothing in the trail beyond appkit's request and service events. This design is the structural ground the other designs stand on: where the code lives, which package owns which concern, the seam through which the process is run so that the command, the server and the pages can be tested without a real process, where the version it shows comes from, and the one binary's wiring. `D02-cli` declares the exit codes, the usage text and the manifest and states what `Run` does with arguments; `D03-serve` states the serve path `Run` follows with none and the rules the handler keeps on every route; `D04-pages` declares the pages, their data and the handler; `D05-on-a-space` is what home contributes to a space and a sandbox.

The module is `github.com/ikigenba/ikigenba/home`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/home`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/home` is wiring only.

## The one dependency

home depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required at a published release through the ordinary module proxy and checksum database, with no `replace` directive. Which release is data that `AGENTS.md` and `go.mod` hold; no requirement names one. appkit is a sibling reached only through its published packages, and home uses five of them: `page` (the banner, launcher and footer, the template set the three templates are parsed into, the services the banner carries, and the shared static files under `/_appkit/`), `services` (the services file, read afresh for auth's links), `identity` (`Require` on every route), `telemetry` (the event contract, the request middleware, the writer every event goes through, the socket sink, the ingest handler and the capturing sink tests use), and `version` (below). appkit owns all of their contracts; home restates none. In particular the banner's product mark, its trail root, its page menu and what the launcher selects from the services file are appkit's `Kit.Banner` and appkit's templates; home states only which banner each page is drawn with and which levels it sets.

`github.com/ikigenba/ikigenba/appkit/version` is the code identity the host gives every app: `version.Display()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment at the time of the call and returns the **display string** built from them, the empty string when neither is set. How it is built is appkit's contract, and home's tests do not re-prove it. home carries no version of its own: nothing in its source or its build names one.

## Where the environment is read

`main` makes the one read of the environment that is not `Run`'s own: it calls `version.Display` exactly once, first, and holds the result, the display string, as the version home shows everywhere it shows one. It hands that string to `page.New` and to `Run` as `Process.Version`, which `Run` writes for `--version` and gives the run's writer as its version. Nothing below `main` calls `version.Display`, so a test of `Run` hands it any string as `Version`, the empty string included, and sets no variable.

`Run` reads every variable through `Process.LookupEnv`: `DRAIN_SECONDS` once at start, `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness (`D03-serve`), and `IKIGENBA_SERVICES` once, when it starts to serve, whose value it hands the handler as the services path that auth's links are read from afresh for every page. A broken or absent services file never stops a start; it reads as a file that lists no services. home starts no process, so it has no environment to compose for one.

Two readers of `IKIGENBA_SERVICES` sit outside the seam, both appkit's: `page.New` reads the real environment when it is called and keeps the path, its kit's `Banner` reading the file afresh on every call; and appkit's socket sink reads the variable, and the file it names, on every delivery. So `main` calls `page.New` once and puts the kit's `Banner` method in `Process.Banner`; and the socket sink is what a nil `Process.Sink` means, used only by the binary, while a test of `Run` names its own sink.

## Packages

The module's root package, `home`, holds what the module embeds, because Go's `embed` reaches only files at or below the embedding package's directory. It exports `Assets`, a file system holding exactly the three templates from `assets/` — `landing.html`, `about.html` and `notfound.html` — which `internal/pages` parses into the set `page.Templates()` returns (`D04-pages`); and `Etc`, a file system holding exactly `manifest.toml` from `etc/`, through which a test proves the committed manifest is the copy of `cli.Manifest` that `devctl build` requires (`D02-cli`). Nothing else lives at the root.

Three internal packages hold the concerns, one each.

- `internal/cli` owns the program as a command: the run seam (this document), the exit codes, the usage text and the manifest (`D02-cli`), and the serve path: reading the drain deadline and the services path, taking the socket, building the run's writer and the handler, readiness, and the stop (`D03-serve`).
- `internal/server` owns a listener's life: serving a handler and draining for a deadline (`D03-serve`).
- `internal/pages` owns the whole HTTP surface: `ServiceName` and `Description`, the template set, the three templates' data, and the one handler, which wraps every route in appkit's request middleware and identity gate, answers `/`, `/about` and every path that is not a page, and hands `/_appkit/` to appkit's shared files (`D04-pages`; the rules on every route are `D03-serve`'s).

There is no separate route package: home's route table is three pages and one delegation, all of them the pages' concern, so it lives with the handler, as the gateway's does in the precedent for a pages-only app. Dependencies point one way: `cmd/home` imports `internal/cli`, `internal/pages` and appkit; `internal/cli` imports `server` and `pages`; `pages` imports the root package; the root package and `server` import nothing of home's. Which package imports which is not observable, so this paragraph is guidance.

## Why there are five documents

home has no store, no tools, no event bus and no trail of its own, so it has none of the documents an app with those carries. It keeps no database, so no `[database]` table, no migrations and no `Migrations`. Its manifest says `mcp = false`, so there is no `/mcp`, no MCP server on the run seam and no `/tools` page. It neither emits nor accepts an event, so there is no emitter, no `/events` and no `/declarations`, and so no nginx fragment, which exists only to keep those two paths off the public name. The events it records are appkit's `request.started` and `request.finished`, from the request middleware, and `service.started` and `service.stopping`, from the run's writer; `D03-serve` states them.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package or from the environment-reading constructor, and returns the exit code: the arguments without the program name, an environment lookup, a way to remove a variable from it, the process's own id, the two output streams, the display string, a way to turn an inherited descriptor into a listener, the banner source, and the sink the run's writer delivers to. It carries no clock, timer, random source or working directory: home stamps nothing of its own, waits for nothing but the drain, which runs on real time, mints no id but the request ids appkit's middleware makes up, and reads and writes no file. Nothing below `main` reads `os.Args`, the real environment, the real pid or the real streams, changes the real environment, calls `version.Display` or `page.New`, or installs a signal handler.

## The version

`internal/cli` declares no version. The one version string home shows is the display string `main` reads from appkit's `version.Display`: `home --version` (`D02-cli`, through `Process.Version`), the footer of every page and the about screen's version (through `page.New(pages.ServiceName, v)`, `v` being that string), and `service.started`'s `version` (through `Process.Version` and the run's writer). Its value is data the host supplies at run time, never a requirement's: the binary's requirements compare with what `version.Display` returns under the same two values, so no test spells a version.

## Recorded decisions

- `internal/pages` owns the handler and its route table; no `internal/web` exists, since every route is a page or the one delegation to appkit's shared files.
- `DRAIN_SECONDS` is read and refused by `Run` itself, as in the precedent for a pages-only app; there is no settings package for one value.
- `Process` carries no clock, timer, random source or directory, since home has no use for them that a test must control.
- The root package exports `Etc` beside `Assets`, holding `manifest.toml`, so that the committed file is proved equal to `cli.Manifest` by use and the layout `AGENTS.md` describes holds.
- The wiring of `main` is proved at the binary by the one exec'ing test of `AGENTS.md`, since `main` is not usable from a test; the binary requirements below are what that test proves.

## Consumer tasks

The binary's start: `main` calls `v := version.Display()` and hands `cli.Run` a `cli.Process` whose `Args`, `LookupEnv`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Version` is `v`, whose `Banner` is the `Banner` method of `page.New(pages.ServiceName, v)`, and whose `Inherit` and `Sink` are left nil; it cancels the context on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name, and exits with what `Run` returns.

A test of the run seam builds a `cli.Process` with a `LookupEnv` over a map, an `Inherit` returning a listener it bound, a `NOTIFY_SOCKET` it holds, a `Version` string of its own, a `*telemetry.Capture` as `Sink` and a `Banner` from `page.New` (having set `IKIGENBA_SERVICES` with `t.Setenv`) or a closure of its own, calls `cli.Run` with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with raw HTTP, cancels, and inspects the capture and the streams. A test of the root package calls `home.Assets()` and `home.Etc()` and lists and reads them with `fs.ReadDir` and `fs.ReadFile`. The one test that execs the binary builds `cmd/home` and runs it, in a temporary working directory, as several separate children, composing each child's environment itself. Where it sets non-empty `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` in a child, it computes the display string it expects by calling `version.Display` after setting the same two values with `testing.T.Setenv`. It runs `--version` with neither variable in the child's environment and expects exactly one empty line, and runs `manifest`, `bogus` and a bare start with no socket. The serving runs each pass a listening socket as descriptor 3 and a `NOTIFY_SOCKET` the test holds: one with `IKIGENBA_SERVICES` unset, which requests `/about` (R-3Y5Y-FQ3K); one with a services file of `auth`, `home` and `cron` that the test rewrites while the child serves, which requests `/` before and after the rewrite (R-40LR-79KY); and runs with a services file whose `telemetry` entry names a socket the test holds, serving `telemetry.IngestHandler` over a `*telemetry.Capture`, from which it reads the trail, one such run stopped by `SIGTERM` and another by `SIGINT` (R-41TN-L1BN, R-6ZWW-V2U2). After each serving child exits, it checks that the socket path still exists and still accepts a connection, since the binary leaves `Inherit` nil and is the one place that proves R-72CP-MMBG.
