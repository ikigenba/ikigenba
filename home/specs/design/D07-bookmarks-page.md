# D07-bookmarks-page

The bookmarks page and every route that adds, removes or serves a bookmark: the data the `bookmarks` template receives, `pages.BookmarkRow` and `pages.BookmarksData`; the bookmarks trail; `GET`/`HEAD`/`POST /bookmarks`, `GET`/`HEAD /bookmarks/<id>/icon` and `POST /bookmarks/<id>/delete`, with their redirects, refusals, redraws and the answer while the store cannot be reached; and the two events home records of its own, `bookmark.created` and `bookmark.deleted`. `D04-pages` owns `pages.Config`, `pages.Handler`, home's template set, the banner user, the root banner, the notice data, `/`, `/about` and the not-found page every other path gets; `D03-serve` owns the rules the handler keeps on every route, the identity gate, the request's two trail events and its request id among them; `D06-bookmarks` owns the store, `Validate`, `Submission`, `FieldErrors`, the copy constants and the errors; `D08-favicon` owns what `Fetcher.Fetch` sends and returns. Tests of this design carry those documents' ids where they exercise those rules.

## The page and its data

`bookmarks` (file `bookmarks.html`) receives `pages.BookmarksData`, the fields its opening comment names in its order: the banner, the bookmarks as `BookmarkRow`s (id, name, URL, whether it has an icon, and when it was added), the form's `Submission` to echo and its `FieldErrors` to place, and `NoIcon`, the flag for the warning an add whose fetch found no icon earns. A row is the store's `Bookmark` copied field for field, less `CreatedBy`, which the page never shows. The page sits one level below the landing page, so its banner carries the **bookmarks trail**, one level named `bookmarks`, the path segment, at `/bookmarks`, whatever trail the banner source returned, as the about screen carries the about trail (`D04-pages`). What the page says and how it draws a row, the form, the warning and the globe for a bookmark without an icon is the template's.

## The routes

`GET /bookmarks` draws the page with the bookmarks the store holds, an empty submission and no errors. Its query matters for one thing only: `NoIcon` is true exactly when the query's `icon` value is `none`. Nothing else in the data comes from the request's URL, and the trail's level points at `/bookmarks` bare, so the page's own links never carry the flag forward and the warning shows once. A `HEAD` gets the `GET`'s status and headers and no body. Any other method but `POST` is refused 405 with `Allow: GET, HEAD, POST` and an empty body, as home's other pages refuse.

`POST /bookmarks` takes a form-encoded body with the keys `name` and `url`. A body of any other media type is refused 415 with an empty body, unread, before anything else is looked at; home has no failure template, so the 415 is empty as its 405 is. A form-encoded submission is judged by `bookmarks.Validate` first: any field error is a 422 that redraws the page with the submission as sent and the errors beside their fields, and the store is unchanged and nothing is fetched. A valid submission has its site's icon fetched with `cfg.Favicon` from the trimmed URL, and is then created through `cfg.Store`; the store decides a taken name in the same step as the insert, so of two adds racing for one name exactly one wins and the other is a 422 carrying `bookmarks.NameTakenMessage` beside the name. A created bookmark is a 303 to `/bookmarks`, or, when the fetch found no icon, exactly to `/bookmarks?icon=none`, so the page that follows draws the warning. The bookmark records who added it by the caller's `X-User-Id`, never the email.

`GET /bookmarks/<id>/icon` serves a stored icon's bytes under the media type it was fetched with, cacheable privately for an hour. A stored icon may be SVG, which a browser opening the route directly would run as a document in home's origin, so the answer also forbids every source but inline style, sandboxes the document, and forbids sniffing. A bookmark that does not exist or has no icon is the not-found page. `POST /bookmarks/<id>/delete` removes the bookmark and answers 303 to `/bookmarks`; an id the store does not hold gets the same redirect, so a remove is idempotent. Neither reads a body. Each refuses any other method 405 with its `Allow`.

`<id>` is one non-empty path segment: a path with an empty segment there, or with more than one, is no bookmark route and is the not-found page `D04-pages` states. Routing is on `URL.Path` as `net/http` decodes it, as `D03-serve` states.

## When the store cannot be reached

While the database under the store fails, every route that reads or writes bookmarks has nothing true to say: drawing an empty table would tell the user the bookmarks were gone. So `GET`/`HEAD /bookmarks`, a form-encoded `POST /bookmarks` whatever its values (a rejection would redraw the table), the icon route and the delete route answer the **unreachable answer**, a plain-text 503 whose body is `bookmarks.Unreachable` and a newline, as dummy and cron answer. The 405s and the 415 need no bookmark and are answered as always. A test makes the store fail with appkit's `SetFailing(true)` on the database handle the store was built over, and can make it fail in the middle of an add from inside its fake transport, which sees the fetch before the store sees the insert.

## The events

A bookmark added is recorded as `bookmark.created`, between the request's `request.started` and `request.finished` and under its request id and user, in the shape of dummy's `widget.created`: `bookmark`, the new id; `name`, the stored name; `icon`, whether an icon was stored; `icon_bytes`, its size, 0 when none. The fetch's outcome rides on it and has no event of its own. A bookmark removed is recorded as `bookmark.deleted` with `bookmark` alone, and only when a bookmark was in fact removed. No other answer records either, and neither carries the URL or an email.

## Recorded decisions

- Departure: **no Bookmarks row in the page menu**, though the decisions document asks for one between home and About. The menu is appkit's `banner` template and `page.Banner` has no seam for an app-supplied row; adding one needs an appkit release, which this delivery's finish line forbids. The landing page's action and empty-state button reach `/bookmarks`, and the page's trail reaches home (orchestrator log D5).
- Addition beyond the decisions document: the icon answer carries `Content-Security-Policy` `pages.IconContentSecurityPolicy` and `X-Content-Type-Options` `pages.IconContentTypeOptions`, so a stored SVG opened at its route runs no script in home's origin (root ruling 7.2). `Cache-Control` is the document's, declared as `pages.IconCacheControl`.
- The store unreachable is a plain-text 503 with `bookmarks.Unreachable` on every bookmark route, following dummy and cron (root ruling 7.3).
- The 415 has an empty body and is answered without reading the body, as home's 405 is empty (root ruling 7.4).
- `CreatedBy` is the request's first `X-User-Id` value, never the email (root correction 8.2; decisions document seam 1).
- The 303 after an add carries `?icon=none` only when the fetch found no icon; `NoIcon` comes from the query alone, and the page's data carries nothing else of the request's URL (decisions document seam 2; orchestrator log D8).
- A removal of an unknown id is the same 303 and records nothing (decisions document seam 2).
- The submission is read from the body alone; a `name` or `url` in the query plays no part. Neither the icon route nor the delete route reads a body or looks at its media type. These are decisions of this design.
- The submission is stated for a body of at most 10 MiB, the cap `net/http`'s `ParseForm` keeps for a form body; what a longer body gets is not contract, so the handler may read the form with `ParseForm` and `PostForm`, which hold what `url.ParseQuery` returns even when the body cannot be parsed whole (a decision of this design).
- "Up" and "alone" hold over a request's whole span, and "up" also needs the store's `Rand` to read and the request's context to stay live, since `Create` fails on a failing `Rand` (`D06-bookmarks`); a store that changes state mid-request is stated only where a requirement names the change, as the failure during the fetch (a decision of this design).
- The event of a removal follows the bookmark, not the request: one `bookmark.deleted` per removal, so two removals racing for one bookmark record it once. No requirement states the race, since no seam holds a delete between its check and its removal for a test to provoke it (a decision of this design).
- A valid submission is always fetched, whether or not its name is taken, and the insert then decides a taken name: the decisions document orders validation, then the fetch, then the insert. Only a rejected submission fetches nothing.
- Event attribute keys follow dummy's `widget` and cron's `trigger`: the id is `bookmark` (skeleton "Events").

## Consumer tasks

For a signed-in `GET /bookmarks` the handler calls `b := cfg.Banner(u)` with the request's banner user `u` and `l, err := cfg.Store.List(ctx)`, a non-nil `err` giving the unreachable answer, and executes `bookmarks` with `pages.BookmarksData{Banner: bb, Bookmarks: rows, NoIcon: r.URL.Query().Get("icon") == "none"}`, `bb` being `b` with `Trail` set to `[]page.Level{{Name: "bookmarks", URL: "/bookmarks"}}` and `rows` holding `pages.BookmarkRow{ID: k.ID, Name: k.Name, URL: k.URL, HasIcon: k.HasIcon, Created: k.Created}` for each `k` of `l`. For a form-encoded `POST /bookmarks` it builds `s := bookmarks.Submission{Name: r.PostForm.Get("name"), URL: r.PostForm.Get("url")}`; when `bookmarks.Validate(s).Any()` it lists and redraws with `Submission: s` and those errors under 422; otherwise it calls `data, typ := cfg.Favicon.Fetch(ctx, strings.TrimSpace(s.URL))` and `k, err := cfg.Store.Create(ctx, bookmarks.Draft{Name: s.Name, URL: s.URL, CreatedBy: r.Header.Get("X-User-Id"), Icon: bookmarks.Icon{Type: typ, Data: data}})`, answering 422 with `bookmarks.FieldErrors{Name: bookmarks.NameTakenMessage}` on `bookmarks.ErrNameTaken`, the unreachable answer on any other error, and otherwise emitting `bookmark.created` through `cfg.Telemetry` and redirecting. The icon route answers from `cfg.Store.Icon(ctx, id)`, `bookmarks.ErrNotFound` giving the not-found page; the delete route calls `ok, err := cfg.Store.Delete(ctx, id)` and emits `bookmark.deleted` when `ok`.

A test of these routes opens a database with appkit's `db.Open` and `home.Migrations()` in its temporary directory, builds `bookmarks.New(d, bookmarks.Config{Now: fixed, Rand: fixed})` and `favicon.New(favicon.Config{HTTP: c})`, `c` an `*http.Client` whose transport the test owns and records, a writer with `telemetry.New` over a `*telemetry.Capture`, and `pages.Handler(pages.Config{...})` with a `Banner` closure returning a banner with a trail of its own. It sends requests with `httptest.NewRequest` carrying `X-User-Id` and `X-User-Email`; for each page it computes the `pages.BookmarksData` it expects from the banner its closure returned and the store's `List`, executes `bookmarks` of its own copy of home's template set and compares bodies byte for byte. It proves the icon stored by calling `Fetch` itself over the same transport; it proves the race by sending both adds at once over a transport that holds each fetch until both requests have reached it and fails the test after a timeout, so that a handler taking the adds one at a time fails rather than deadlocks, and checks the outcome whatever order the handler takes them in; it proves the unreachable answer with `d.SetFailing(true)`, before a request or from inside the transport; and it reads the events from the capture.
