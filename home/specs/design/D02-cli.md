# D02-cli

home as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, what `db status` reports of the database, and the two constants whose text is fixed here — the usage text and the manifest — with the file under `etc/` that copies the manifest. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, the display string `main` read, and its `Dir`, `Now`, `Rand` and `HTTP`, `cli.Run`, and the root package's `Etc` and `Migrations`; `D04-pages` declares `pages.Description`. When `Args` is empty home serves, and everything from there is `D03-serve`'s.

The arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity; `manifest` writes `Manifest`; and `--help` writes `Usage`. The one two-word command, `db status`, reports the database's migrations (below). Any other `Args` is a usage error. The argument home complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`; and otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `home: `, and after exactly one empty line comes the hint to run `home --help`, unprefixed because home is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. The constant for 1 is named `ExitServerFailed`, as in the other apps, though it also covers a `db status` that fails. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a `DRAIN_SECONDS` that is not a positive whole number) exits 2, while trouble on the host once home is past its checks (a socket it cannot take, a database it cannot open, a readiness it cannot report, a drain that runs out) exits 1, and so does a `db status` whose database cannot be read. `Run` returns no other value.

## db status

`db status` is an operator's look at the database: which of the migrations the binary carries `state/home.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status`, which home calls with the path `state/home.db` resolved against `Process.Dir` (so relative to the working directory in the binary) and the migrations `home.Migrations()` returns, writing straight to `Stdout`. home adds nothing to the lines and states nothing about their format; its requirements say only that the bytes on `Stdout` are the ones `db.Status` writes for that path and those migrations, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database, never with a format it spells out.

`db.Status` only looks: it applies nothing and creates nothing, so before home's first start `db status` reports every migration pending and leaves the directory as it was. When it returns an error, home says so on one line, `home: ` and the error's text with each newline replaced by a space, and exits 1. Whatever `db.Status` had already written to `Stdout` stays there: findings are product, and the repository's command-line conventions send a report to stdout whole, bad news included. That is the one case in which a failure may leave anything on `Stdout`. A database that records a migration this home does not carry, one a newer home upgraded, is not a failure: older code runs on newer data, appkit's `db.Status` lists every line, the unknown version among them, and returns nil, so `db status` writes nothing to `Stderr` and exits 0. `db status` reads no environment and takes no socket.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket, and only `db status` reads the database, so `home --version` succeeds with nothing passed in and `home bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, the random source, the HTTP client, the banner source or the sink, and only `db status` reads anything under the working directory, creating nothing there. A command fetches no icon and records no event: the trail is what home records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns, `db status` and `db bogus` included. Every failure but that one `db status` case leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text is fixed here: home's name; its description, which is `pages.Description`, the line the about screen shows and the host publishes in its services file; that it is the host's default app (`default = true`), so it answers at the space host itself as well as at `home.<space>`; that it is not one of the suite's MCP services; that it serves no guests (`guests = false`), so on a host with an authenticator nginx admits no visitor without a credential; no secrets; no `[env]` table, since home has no settings of its own and `DRAIN_SECONDS` is the space's; the `[database]` table, written as cron's is, that tells the host to keep and replicate `state/home.db`, where home keeps the users' bookmarks; the `[resources]` table opsctl writes into the service unit, whose only line is `memory_max = "128M"`; and, last, the `[home]` table, whose only line is `group = "core"`, marking home a core service. It declares no port, since home serves on the socket the host passes it, and no `cache/`, since home keeps nothing but its database. The description is copy: the manifest requirement fixes only that it is one line of characters a TOML basic string holds unescaped, and a second requirement ties it to `pages.Description`.

## The file under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ. The build run writes it from the constant and keeps them in step. The file is proved by use: the root package embeds `etc/` and exports it as `Etc` (`D01-layout-and-run-seam`), so a test compares the embedded `manifest.toml` with the constant without ever opening the checkout, and a build whose `etc/` lacks the file, or holds a stale copy, fails to compile or fails that test. That test lives in the external test package `home_test` beside the root package, since it imports both the root package and `internal/cli`, which imports the root package, so a test inside package `home` would form an import cycle.

## Recorded decisions

- The usage text's words are fixed here, as every app's are: `--help` output is a product a caller reads on stdout, and the precedent fixes it byte for byte.
- `[resources]` caps memory at 128M, as the precedent does; home's footprint is smaller, and lowering the cap is a later decision with nothing depending on it. The bookmarks leave it there, as the decisions document settles.
- The usage text gains only the `db status` line, as cron's has it; its first paragraph, a page of every service at /, stays true with bookmarks above the services (root ruling 7.7).
- `db status` is home's because home now keeps a database, and it is cron's command carried over unchanged but for the names: the same output, the same failure line, the same exit codes and the same rule that it creates nothing (the decisions document's seam 1, with cron as precedent for the manifest and migration layout).
- The rule that commands touch nothing takes the shape of cron's: `Args`, `Stdout`, `Stderr` and `Dir` set suffice for every command, and a command neither calls `Now`, reads `Rand`, nor sends through `HTTP`, all in one requirement rather than a second one for the new fields (root correction 8.1, after D4 gave the run seam `Now`, `Rand`, `Dir` and `HTTP`).

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `home --version`, `home manifest` or `home --help` and reads stdout; an operator types `home db status` in `/opt/home` before or after a deploy and reads which migrations the database has had; `devctl build` runs `home manifest` and compares its output with the release's `etc/manifest.toml`; opsctl and sandbox read the manifest's `[database]` table and keep `state/home.db` as they keep cron's; the help text tells a caller what `ExitSuccess`, `ExitServerFailed` and `ExitUsage` mean.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s), `Dir` (an empty temporary directory) and, for `--version`, `Version` set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `p.Version + "\n"` for a `Version` of its own choosing, the empty string included, `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Unsetenv`, `Inherit`, `Now` and `Banner` to functions that record a call, `Rand` to a reader that records a read, `HTTP` to a client whose transport records any request, and `Sink` to a sink that records any use, and asserts none was used. A test of `db status` makes a database under its `Dir` with `db.Open` and `home.Migrations()` (or with a fixed `Now`, or with a migrations file system holding home's migrations and one more, standing for a newer home, or puts a regular file that is not a database at `state/home.db`), closes it, runs `cli.Run` with `Args` `["db", "status"]`, and compares `Stdout` with what its own `db.Status` call wrote into a buffer for the same path and migrations before `Run` was called, and with what it writes after, and `Stderr` with `"home: "` and that call's error text. A test compares `cli.Manifest` with `pages.Description`. A test in package `home_test` reads `manifest.toml` from `home.Etc()` with `fs.ReadFile` and compares it with `cli.Manifest`.
