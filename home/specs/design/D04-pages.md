# D04-pages

What home draws as HTML and the one handler that serves it: the package `internal/pages`; the four templates `landing`, `about`, `notfound` and `bookmarks`, and the data of the first three; the handler that answers `/`, `/about` and every path that is neither a page nor a bookmarks route — the landing page and the about screen for the signed-in caller, the plain-text refusal of the landing page while the bookmarks cannot be read, the refusal of any other method on a page, and the not-found page; the banner's user and auth's two links; the landing page's bookmarks and tiles; the trail each page sets; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the root package's `Assets`, which holds exactly the four templates, and the run seam whose `Banner` the binary sets, and fixes the binary's landing page and about screen; `D03-serve` owns the rules the handler keeps on every route — the identity gate in front of every path, so a request without `X-User-Id` never reaches a page or a shared file, the request's two trail events, routing on `URL.Path`, and that nothing reaches standard error while telemetry takes every event; `D02-cli` publishes `pages.Description` in the manifest; `D06-bookmarks` declares the store the handler reads the bookmarks from and `bookmarks.Unreachable`; `D07-bookmarks-page` declares `pages.BookmarksData` and the answers on `/bookmarks` and the two routes under it, which the handler made here serves; `D08-favicon` declares the fetcher the handler's `Config` carries for that page. Tests of this design carry those documents' ids where they exercise those rules.

home has one asset concern beyond its templates, the shared files, and that is one delegation to appkit, so it is stated here with the pages rather than in a document of its own.

## The template set and its data

The four templates are the files of `assets/`, embedded by the root package and returned by `home.Assets()`. **home's template set** is made by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `footer` and `preload`; the code adds no template function and writes no markup of its own. Each template executes without error for any value of its data, so markup that cannot be executed is a test failure, not a broken page.

Each template's data is a named struct whose fields are exactly those its opening comment names. `LandingData` carries the banner, the space's bookmarks in `Bookmarks`, each a `BookmarkTile` holding a bookmark's id, name, URL and whether home holds an icon for it, and the tiles of the services, backend services in `Backend` and core services in `Core`, each a `Tile` holding a service's name, URL, icon and whether it is enabled. `AboutData` carries the banner and `pages.Description`, the manifest's one-line description, so the about screen says the same with or without a services file. `NoticeData` carries only a banner, for the not-found page's footer. `BookmarksData`, the bookmarks page's data, is `D07-bookmarks-page`'s.

## The templates

The four files of `assets/` are written by the user or the delivering agent, following the repository's `design/`; each defines one template of its own name and opens with a comment naming the data it receives. What a page says, its markup and its hooks live in its template and nowhere else: this design names each template and its data, never its words or its markup. `landing` (file `landing.html`) receives `pages.LandingData` and is the landing page at `GET /`; `about` (file `about.html`) receives `pages.AboutData` and is the about screen at `GET /about`; `notfound` (file `notfound.html`) receives `pages.NoticeData` and is the not-found page, answered with status 404; `bookmarks` (file `bookmarks.html`) receives `pages.BookmarksData` and is the bookmarks page, whose routes `D07-bookmarks-page` states. appkit's `banner`, `footer` and `preload` templates, which the set already defines, are the templates' to call with the data's `Banner`.

## The landing page's bookmarks

The landing page shows the space's bookmarks above the services: every bookmark the store holds, in the store's order (`D06-bookmarks` lists them by name), each as a bookmark tile carrying the bookmark's id, name, URL and whether an icon is held, unaltered. A tile with an icon draws it from `/bookmarks/<id>/icon`, which `D07-bookmarks-page` answers; one without draws the template's own glyph. The list is read afresh from the store for every landing page, so a bookmark added or removed on the bookmarks page shows on the next one. The bookmarks section is always drawn, with its empty state when there are none; both are the template's. The landing page draws no form: adding and removing happen on the bookmarks page.

When the store cannot be reached, the landing page is not drawn at all: drawing it without bookmarks would show the empty state and tell the user the space had none. `/` answers 503 in plain text instead, whose body is the line `bookmarks.Unreachable` and a newline, with no banner and no footer and nothing of the database's own error, and a `HEAD` gets the same with no body. That shape needs no template: it is a fixed line, as dummy and cron answer an unreachable store. The about screen, the not-found page, the refusals and the shared files need no bookmark, so they are answered as they are while the store can be reached. A test provokes the failure with appkit's `SetFailing(true)` on the database handle the store was made over.

## The landing page's tiles

The landing page shows every other service on the space as a tile. The handler reads the services file at `Config.ServicesPath` for the page, the read auth's links come from, and keeps the entries that carry an icon, in the file's order, skipping the one named `pages.ServiceName`: home draws no tile for itself, and nothing on the landing page is marked current. A tile is the entry's name, URL, icon and enabled flag unaltered, so a disabled service is a tile whose `Enabled` is false. The tiles of entries whose group is `core` go to `Core` and every other tile to `Backend`, each in file order; appkit's `services.Read` reads an entry with no group, or any group but `core`, as `application`, and those are the backend services. When the path is empty, or the file is missing, unreadable or not a services file, the file lists no services, as it does for auth's links, and both groups are empty. A group with no tiles is not drawn, and with neither the landing page draws its empty services state; both are the template's. The banner the page is drawn with plays no part in the tiles, and neither do the bookmarks.

## The trail

The landing page is home's root, so it adds no level. The about screen sits one level below it, so before drawing it the handler sets the banner's `Trail` to the **about trail**: one level, named `about`, the path segment, at `/about`; with it appkit's banner marks About as the current row of the page menu. The not-found page is a notice page and carries the root only. Each page sets its trail whatever trail the banner source returned: in the binary that is always empty, and a handler test's closure returns a trail of its own so that a handler which kept or extended it fails. The level's name is data the banner draws, the same on every app; the template turns it into words. The bookmarks page's trail is `D07-bookmarks-page`'s.

## The pages handler

`pages.Handler` answers every path, behind the rules `D03-serve` states. `/` and `/about` take `GET` and `HEAD`; any other method is refused 405 with `Allow: GET, HEAD` and an empty body. A path beginning `/_appkit/` is handed to appkit's `page.Static()` unchanged. `/bookmarks`, and a path `/bookmarks/<id>/icon` or `/bookmarks/<id>/delete` whose `<id>` is one non-empty path segment, are answered as `D07-bookmarks-page` states. Any other path is the not-found page, status 404, whatever the method, so a path that names nothing is never a 405: `/about/` and `/bookmarks/` are not redirected, `/bookmarks//icon` and `/bookmarks/a/b/icon` name no bookmark, and `/tools`, `/mcp`, `/events` and `/declarations`, which home does not serve, are not found. A `HEAD` gets the status and headers of the `GET` and no body. No answer sets a cookie.

Each page drawn is drawn with the banner the banner source returns for the **banner user** — the caller's `X-User-Email` exactly as it arrived and auth's two links; how often the source is called is not fixed, but each page is drawn from one call's result. auth's links come from the services file's entry named `auth`, read afresh for every request: its `url` followed by `/` and by `/logout`. With no such entry, an empty `url`, or no usable services file, the space is read from `Host`: a trailing `:` and port digits are dropped, then one leading `home.` label, and the links are `<scheme>://auth.<space>/` and `<scheme>://auth.<space>/logout`, the scheme being `X-Forwarded-Proto` when that is exactly `http` or exactly `https` and `https` otherwise. home answers at the space host itself as the default app, where `Host` carries no `home.` label and the space is the host as it stands.

## The shared files

The stylesheet, its fonts, the button feedback script, the favicon and the licences are appkit's: `page.Static()` serves them from files embedded in the binary, under the prefix `page.StaticPrefix`. home holds no copy of any of them and restates none of appkit's rules. Its one obligation is to hand every signed-in request under the prefix to appkit's handler unchanged — the whole `URL.Path`, prefix included — and to send back exactly what that handler answers. The requirement states that as an equality a test checks without knowing any of appkit's rules: it sends the same request to home's handler and to a handler `page.Static()` returned, and compares the status, every header field and the body. The careless mounts a test sends are the ones Go's `http.ServeMux` would supply: `/_appkit` without its slash, which is not under the prefix and so is the not-found page, and `/_appkit/../theme.css`, which is under the prefix and is answered as appkit answers it, never with a redirect.

## Proving a page

A page is proved by comparison, never by reading it: a test builds its own copy of home's template set, executes the named template with the data a requirement states, and compares the body byte for byte; no test looks for a word, a tag, a class or an id.

## Recorded decisions

- The landing page reads its own tiles from the services file rather than taking them from the banner, which carries no services; the read that gives auth's links gives the tiles too.
- home draws no tile for itself and marks none current: the banner's trail root and page menu already say where the user is.
- Tiles are split into two groups by the entry's `Group`: core, and every other as backend, each in file order. The group appkit reads as `application` is drawn as the backend services, the name the decisions document gives the group.
- The landing page's bookmarks are every bookmark the store holds, in the store's order, unaltered; the landing page draws no form, and the bookmarks page adds and removes them (the decisions document).
- `/` answers 503 in plain text with `bookmarks.Unreachable` when the store cannot be reached, rather than drawing the landing page with no bookmarks, which would show the empty bookmarks state and say the space had none. The decisions document is silent on an unreachable store; the delivery ruled that every route reading or writing bookmarks answers it so, following dummy's and cron's precedent (a decision of this design, settled for this delivery). The rest of the landing page is not drawn without them, though the services could be read: half a front door that hides the failure is worse than a plain refusal.
- The landing page and the not-found page are drawn with the banner's `Trail` set to nil, and the about screen with the about trail, whatever the banner source returned.
- The not-found page is drawn with a banner from the banner source for the request's banner user, so its footer carries the same release and commit as the other pages.
- The space for auth's links drops a trailing port, then a leading `home.` compared byte for byte and only when something follows it; the scheme is case-sensitive.
- The about trail's level is named `about`, the path segment, as every app names it; the name is data appkit's banner draws, not home's copy.

## Consumer tasks

`cli.Run` builds `pages.Handler(pages.Config{Banner: p.Banner, ServicesPath: path, Telemetry: w, Store: st, Favicon: f})`, `st` being the store over the database it opened and `f` the fetcher over `p.HTTP` (`D03-serve`), and serves it; `cli.Manifest` carries `pages.Description`; the binary's banner source is `page.New(pages.ServiceName, id).Banner`, `id` being the identity `main` read. For a signed-in `GET /` the handler calls `k, err := cfg.Store.List(ctx)` and, when `err` is not nil, answers 503 with `text/plain; charset=utf-8` and the body `bookmarks.Unreachable` followed by a newline; otherwise it calls `b := cfg.Banner(u)` with the request's banner user `u` and `l, err := services.Read(cfg.ServicesPath)`, an error giving an empty list, and executes `landing` with `pages.LandingData{Banner: root, Bookmarks: marks, Backend: backend, Core: core}`, `root` being `b` with `Trail` nil, `marks` the tiles `pages.BookmarkTile{ID: m.ID, Name: m.Name, URL: m.URL, HasIcon: m.HasIcon}` of each bookmark `m` of `k`, in order, and `core` and `backend` the tiles `pages.Tile{Name: e.Name, URL: e.URL, Icon: e.Icon, Enabled: e.Enabled}` of each entry `e` of `l` with `e.HasIcon` true and `e.Name` other than `pages.ServiceName`, in order, those with `e.Group == "core"` in `core` and the rest in `backend`; for `GET /about` it executes `about` with `pages.AboutData{Banner: ab, Description: pages.Description}`, `ab` being `b` with `Trail` set to `[]page.Level{{Name: "about", URL: "/about"}}`; for `/bookmarks` and the two routes under it it answers as `D07-bookmarks-page` states; for any other path it executes `notfound` with `pages.NoticeData{Banner: root}` under status 404.

A test of the handler writes a services file in its temporary directory, holding core and backend entries in a file order that is not the order of their names within either group, one named `home`, one without an icon and one disabled; opens a database in the same directory with appkit's `db.Open` and `home.Migrations()`, makes a store over it with `bookmarks.New` and adds bookmarks, one with an icon and one without, through `Create`; builds its own writer with `telemetry.New` over a `*telemetry.Capture` and a fetcher with `favicon.New`; builds `pages.Handler(pages.Config{...})` with that file as `ServicesPath`, that store and that fetcher, and a `Banner` closure that records its arguments and returns a fixed `page.Banner` with a non-empty `Trail` of its own, a `Service` other than `pages.ServiceName` and a `Home` other than the `url` of the file's `home` entry, so that a handler skipping by the banner rather than by name fails; and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It computes the `pages.LandingData` it expects from the banner its closure returned, from `services.Read` of the file it wrote and from the store's `List`, by the rule the landing data's definition states, builds its own copy of home's template set from `page.Templates()` and `home.Assets()`, executes `landing` with that data and compares bodies byte for byte, again after rewriting the file and after adding and deleting a bookmark, with an empty store, and with an empty `ServicesPath` and with one naming no file, expecting both groups empty; it does the same for `about` and `notfound`, and executes each of the four templates with the zero value of its data. It then calls `SetFailing(true)` on the database handle and expects `GET /` and `HEAD /` to answer 503 with `bookmarks.Unreachable` and a newline, and an empty body, while `/about` and a not-found path answer as before. It sends `/bookmarks/`, `/bookmarks//icon` and `/bookmarks/a/b/icon` and expects the not-found page. A test of the shared files requests `/_appkit/theme.css`, `/_appkit/nope.css`, `/_appkit/../theme.css` and `/_appkit` with a non-empty `X-User-Id` of the handler and of `page.Static()` and compares the answers.
