# D04-pages

What home draws as HTML and the one handler that serves it: the package `internal/pages`; the three templates `landing`, `about` and `notfound` and the data each receives; the handler that answers `/`, `/about` and every path that is not a page — the landing page and the about screen for the signed-in caller, the refusal of any other method on a page, and the not-found page; the banner's user and auth's two links; the trail each page sets; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the root package's `Assets`, which holds exactly the three templates, and the run seam whose `Banner` the binary sets, and fixes the binary's landing page and about screen; `D03-serve` owns the rules the handler keeps on every route — the identity gate in front of every path, so a request without `X-User-Id` never reaches a page or a shared file, the request's two trail events, routing on `URL.Path` without redirects, and that nothing reaches standard error while telemetry takes every event; `D02-cli` publishes `pages.Description` in the manifest. Tests of this design carry those documents' ids where they exercise those rules.

home has one asset concern beyond its templates, the shared files, and that is one delegation to appkit, so it is stated here with the pages rather than in a document of its own.

## The template set and its data

The three templates are the files of `assets/`, embedded by the root package and returned by `home.Assets()`. **home's template set** is made by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; the code adds no template function and writes no markup of its own. Each template executes without error for any value of its data, so markup that cannot be executed is a test failure, not a broken page.

Each template's data is a named struct whose fields are exactly those its opening comment names. `LandingData` carries the banner and the services the page shows as tiles. `AboutData` carries the banner and `pages.Description`, the manifest's one-line description, so the about screen says the same with or without a services file. `NoticeData` carries only a banner, for the not-found page's footer.

## The templates

The three files of `assets/` are written by the user or the delivering agent, following the repository's `design/`; each defines one template of its own name and opens with a comment naming the data it receives. What a page says, its markup and its hooks live in its template and nowhere else: this design names each template and its data, never its words or its markup. `landing` (file `landing.html`) receives `pages.LandingData` and is the landing page at `GET /`; `about` (file `about.html`) receives `pages.AboutData` and is the about screen at `GET /about`; `notfound` (file `notfound.html`) receives `pages.NoticeData` and is the not-found page, answered with status 404. appkit's `banner`, `launcher`, `footer` and `preload` templates, which the set already defines, are the templates' to call with the data's `Banner`.

## The landing page's services

The landing page shows the space's services under exactly the launcher's rules: entries with an icon only, in the services file's order, a disabled one faint and unlinked, home itself marked current. Those rules are already what appkit's `Kit.Banner` applies when it fills the banner's `Services` for the launcher, from the services file it reads afresh on every call. So the landing page's `Services` are the very `Services` of the banner the page is drawn with, taken from the same call of the banner source: one read of the services file per page, and the tiles and the launcher can never disagree. When the banner carries no services the landing page draws its empty state, which is the template's. home reads the services file itself only for auth's links (below).

## The trail

The landing page is home's root, so it adds no level. The about screen sits one level below it, so before drawing it the handler sets the banner's `Trail` to the **about trail**: one level, named `about`, the path segment, at `/about`; with it appkit's banner marks About as the current row of the page menu. The not-found page is a notice page and carries the root only. Each page sets its trail whatever trail the banner source returned: in the binary that is always empty, and a handler test's closure returns a trail of its own so that a handler which kept or extended it fails. The level's name is data the banner draws, the same on every app; the template turns it into words.

## The pages handler

`pages.Handler` answers every path, behind the rules `D03-serve` states. `/` and `/about` take `GET` and `HEAD`; any other method is refused 405 with `Allow: GET, HEAD` and an empty body. A path beginning `/_appkit/` is handed to appkit's `page.Static()` unchanged. Any other path is the not-found page, status 404, whatever the method, so a path that names nothing is never a 405: `/about/` is not redirected, and `/tools`, `/mcp`, `/events` and `/declarations`, which home does not serve, are not found. A `HEAD` gets the status and headers of the `GET` and no body. No answer sets a cookie.

Each page drawn is drawn with the banner the banner source returns for the **banner user** — the caller's `X-User-Email` exactly as it arrived and auth's two links; how often the source is called is not fixed, but each page is drawn from one call's result. auth's links come from the services file's entry named `auth`, read afresh for every request: its `url` followed by `/` and by `/logout`. With no such entry, an empty `url`, or no usable services file, the space is read from `Host`: a trailing `:` and port digits are dropped, then one leading `home.` label, and the links are `<scheme>://auth.<space>/` and `<scheme>://auth.<space>/logout`, the scheme being `X-Forwarded-Proto` when that is exactly `http` or exactly `https` and `https` otherwise. home answers at the space host itself as the default app, where `Host` carries no `home.` label and the space is the host as it stands.

## The shared files

The stylesheet, its fonts, the launcher's script, the button feedback script, the favicon and the licences are appkit's: `page.Static()` serves them from files embedded in the binary, under the prefix `page.StaticPrefix`. home holds no copy of any of them and restates none of appkit's rules. Its one obligation is to hand every signed-in request under the prefix to appkit's handler unchanged — the whole `URL.Path`, prefix included — and to send back exactly what that handler answers. The requirement states that as an equality a test checks without knowing any of appkit's rules: it sends the same request to home's handler and to a handler `page.Static()` returned, and compares the status, every header field and the body. The careless mounts a test sends are the ones Go's `http.ServeMux` would supply: `/_appkit` without its slash, which is not under the prefix and so is the not-found page, and `/_appkit/../theme.css`, which is under the prefix and is answered as appkit answers it, never with a redirect.

## Proving a page

A page is proved by comparison, never by reading it: a test builds its own copy of home's template set, executes the named template with the data a requirement states, and compares the body byte for byte; no test looks for a word, a tag, a class or an id.

## Recorded decisions

- The landing page's `Services` are the banner's own `Services` from the same call of the banner source, not a second read of the services file: appkit already applies the launcher's selection, order, `Enabled` and `Current`, and one read per page keeps the tiles and the launcher in step.
- The landing page and the not-found page are drawn with the banner's `Trail` set to nil, and the about screen with the about trail, whatever the banner source returned.
- The not-found page is drawn with a banner from the banner source for the request's banner user, so its footer carries the same display string as the other pages.
- The space for auth's links drops a trailing port, then a leading `home.` compared byte for byte and only when something follows it; the scheme is case-sensitive.
- The about trail's level is named `about`, the path segment, as every app names it; the name is data appkit's banner draws, not home's copy.

## Consumer tasks

`cli.Run` builds `pages.Handler(pages.Config{Banner: p.Banner, ServicesPath: path, Telemetry: w})` and serves it (`D03-serve`); `cli.Manifest` carries `pages.Description`; the binary's banner source is `page.New(pages.ServiceName, v).Banner`. For a signed-in `GET /` the handler calls `b := cfg.Banner(u)` with the request's banner user `u` and executes `landing` with `pages.LandingData{Banner: root, Services: b.Services}`, `root` being `b` with `Trail` nil; for `GET /about` it executes `about` with `pages.AboutData{Banner: ab, Description: pages.Description}`, `ab` being `b` with `Trail` set to `[]page.Level{{Name: "about", URL: "/about"}}`; for any other path it executes `notfound` with `pages.NoticeData{Banner: root}` under status 404.

A test of the handler writes a services file in its temporary directory, builds its own writer with `telemetry.New` over a `*telemetry.Capture`, builds `pages.Handler(pages.Config{...})` with a `Banner` closure that records its arguments and returns a fixed `page.Banner` with services and a non-empty `Trail` of its own, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of home's template set from `page.Templates()` and `home.Assets()`, executes `landing` with the `pages.LandingData` it expects and compares bodies byte for byte; it does the same for `about` and `notfound`, and executes each template with the zero value of its data. A test of the shared files requests `/_appkit/theme.css`, `/_appkit/nope.css`, `/_appkit/../theme.css` and `/_appkit` with a non-empty `X-User-Id` of the handler and of `page.Static()` and compares the answers.
