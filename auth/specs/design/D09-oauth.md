# D09-oauth

auth is the space's OAuth 2.1 authorization server for MCP clients. A client that knows only the gateway's address reads auth's metadata at `/.well-known/oauth-authorization-server` (RFC 8414), registers itself at `/register` (RFC 7591), sends the person's browser to `/authorize`, where the person approves or denies it on the approve page, and exchanges the code it is handed at `/token` for an MCP client token, which `/check` honors only on the space's MCP host (D06) and which the person sees and revokes from their profile (D07). This design owns those five routes; D03 routes requests to them and answers a failed store with its 500, D04 declares the store operations they call (`RegisterClient`, `LookupClient`, `CreateAuthCode`, `ConsumeAuthCode`, `CreateClientToken`) with the `Client`, `AuthCode` and `Token` types and the durations `AuthCodeTTL`, `UnusedClientTTL` and `ClientTokenTTL`, D01 declares `Assets()` and defines auth's template set, and D05 defines auth's own origin, the session cookie, the banner user, the recording of events and the vocabulary every auth page is read with.

## Where things are

Everything here hangs off auth's own origin (D05): `https://auth.<space>` on a host, and exactly `IKIGENBA_PUBLIC_URL` in a sandbox, where `server.Config.PublicURL` carries it. The metadata names the issuer and the three endpoints under it. The space's **MCP origin** is auth's own origin with its leading `auth.` label swapped for `mcp.` — `https://mcp.sbx.ikigenba.dev` on a host, `http://mcp.wip.localhost:7400` in the sandbox of S09 — and is the one resource server auth issues tokens for: a `resource` is acceptable only when its scheme and authority are the MCP origin's, and a request naming none means the **default resource**, the MCP origin followed by `/mcp`. A client token is bound to the **MCP host**, the MCP origin's host without its port, since `/check` compares it with the host nginx forwards (D06). The approve page names the gateway by the MCP origin without its scheme, port kept.

## Registration

Registration is open, takes no credential and checks no `Origin`. auth reads two members of the JSON object it is sent, `client_name` (optional, 1 to 200 characters, `MCP client` when absent) and `redirect_uris` (1 to 10 acceptable URIs), and ignores the rest. An acceptable redirect URI lands either on the person's own machine (`http://localhost` or `http://127.0.0.1`, any port and path) or on an `https` site, holds no fragment and no user part, and is at most 2048 bytes. A metadata fault is answered `invalid_client_metadata` before any redirect-URI fault is looked at, which is answered `invalid_redirect_uri` (RFC 7591 §3.2.2); success is `201` with the registration echoed in auth's own terms (RFC 7591 §3.2.1). A registration that never leads to a token is dropped after `UnusedClientTTL`; D04 does the dropping, and an unknown client is simply unknown here.

## Authorization

`GET /authorize` and the approve page's `POST /authorize` read the same parameters, the GET from its query and the POST from its form body, each by its first value, an empty value counting as absent. They are checked in one order. First the client and the redirect URI: an unknown client, or a redirect URI auth cannot resolve to one the client registered, is answered by auth itself with one line of plain text and no `Location`, because sending a browser to a URI auth cannot trust is the thing RFC 6749 §4.1.2.1 forbids. A requested URI matches a registered one byte for byte, or, both being loopback URIs on the same host, once their ports are dropped, so a client listening on whatever port is free still matches; the resolved URI is then the requested one. Once the redirect URI is known, every other fault goes back to the client as an **error redirect**: `302` to the resolved URI with `error=<code>` added to its query, and the request's `state`, escaped with `url.QueryEscape`, after it. The codes are RFC 6749 §4.1.2.1's `invalid_request`, `unsupported_response_type` and `access_denied`, and RFC 8707 §2's `invalid_target`. A request without PKCE S256 is `invalid_request`; OAuth 2.1 requires PKCE and auth supports only S256.

Only then is the session looked at. A person with no live session is sent to sign in with the authorization request as the return URL, which D05's sign-in page honors because auth's own host is under the space: for a GET the request's own query as it arrived, for a POST the posted parameters but `decision`, re-encoded by `url.Values.Encode`, which sorts them by name. A signed-in person gets the approve page on every GET, however often they have approved the client before. The POST additionally requires an `Origin` equal to auth's own origin before anything else, as the profile's POSTs do, and a `decision` of `approve` or `deny`: approving stores an auth code (D04) bound to the client, the person, the resolved redirect URI, the challenge and the resource (the default resource when the request named none) and sends it back as `code=<code>`; denying sends back `error=access_denied`.

## The approve page

The approve page is the human-authored template `approve` in `assets/approve.html`, which the build run never writes. The server writes no markup of its own for it: the body is exactly the output of `approve` of auth's template set (D01) for the request's **approve data**, which a test can render itself and compare byte for byte. The data's members are the `page.Banner` for the session's user, the client's registered name, the gateway name, the date the token would expire if approved now, the host the browser returns to, and the seven values the form carries back. Because the body is the template's output and the data members are plain strings, `html/template` writes the client's name, which anyone may register, as text and never as markup.

The hooks are read in D05's vocabulary — an auth page drawn with the banner, its written markup, a card titled, content, consists of, reads, carries, marks — so that every page-wide rule of D05 (title, stylesheet, favicon, feedback script, viewport, no inline style, no foreign URL) holds of the approve page too. The page is one card titled `Connect <name>`; three sentences say who wants what until when, warn the person, and name where they go next; one form posts the request back with `Approve` (the primary button) and `Deny` (a secondary one).

## Token

`/token` takes no credential and checks no `Origin`; every answer carries `Cache-Control: no-store` (RFC 6749 §5.1). A request whose `code` names a stored code uses the code up, whatever else it gets wrong, so a wrong verifier cannot be retried. Faults are RFC 6749 §5.2's `unsupported_grant_type`, `invalid_request` and `invalid_grant` and RFC 8707's `invalid_target`, as a JSON object `error` and `error_description`. The verifier is checked as RFC 7636 §4.6 says for S256: the base64url encoding, without padding, of the SHA-256 of the verifier's ASCII bytes must equal the stored challenge (RFC 7636 Appendix B: verifier `dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk` gives `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`, reproduced with Go's `crypto/sha256` and `base64.RawURLEncoding` while drafting). Success mints a client token (D04's `CreateClientToken`) owned by the approver, named after the client, bound to the MCP host, expiring `ClientTokenTTL` after the approval rather than after the exchange, and answers its secret once as a Bearer `access_token` with `expires_in` 90 days in seconds. There is no refresh token and no scope.

## The trail

Every request here records its request events (D03). Beyond them, a registration records `client.registered` under no user, an approval `client.approved` and a denial `client.denied` under the person, and a mint `token.minted` under the approver, each with one attribute naming the client or the token. A failure, a 500 included, records none of these, and no event carries a client's name, a redirect URI, a code, a challenge, a verifier, a `state`, a resource or a secret.

## Evidence

RFC 8414 §2 and §3 (metadata members, `/.well-known/oauth-authorization-server` for an issuer with no path, `200` with `application/json`); RFC 7591 §2 (`client_name`, `redirect_uris`, `grant_types`, `response_types`, `token_endpoint_auth_method` `none` for a public client), §3.2.1 (`201`, `client_id`, `client_id_issued_at`) and §3.2.2 (`400`, `invalid_redirect_uri`, `invalid_client_metadata`); RFC 6749 §4.1.2 (`code` and `state` in the redirect's query), §4.1.2.1 (no redirect to an invalid URI; `invalid_request`, `unsupported_response_type`, `access_denied`), §5.1 (`access_token`, `token_type`, `expires_in`, `Cache-Control: no-store`) and §5.2 (`400`, `invalid_request`, `invalid_grant`, `unsupported_grant_type`, `error_description`); RFC 8707 §2 (`resource` absolute with no fragment, `invalid_target`); RFC 7636 §4.6 and Appendix B (S256). Go's `net/url` documentation and a probe run while drafting: `url.Parse` lowercases the scheme, keeps the host's case, reports `User` for `https://u@ex.com/` and `Fragment` for `...#x`, rejects `http://localhost:abc/`, and accepts `not a url` as a relative reference (`IsAbs` false); `url.QueryEscape("a b&c=d/é")` is `a+b%26c%3Dd%2F%C3%A9`; `url.Values.Encode` sorts by key, so the values of `state=s&client_id=c&response_type=code` encode as `client_id=c&response_type=code&state=s`.
