# Decision 11 — Generation epochs: a restore mints a fresh epoch and stale cursors resync

**Decision.** The producer holds a live **generation** (epoch) token and stamps
every feed cursor with it, so a database restore or rollback cannot silently
corrupt a consumer's durable position. The token is a ULID minted by
`EnsureGeneration(path)` and exposed as `Outbox.Generation()`. Each cursor the
feed emits is `<generation>.<seq>` — the epoch is the left half of the opaque
cursor line D1 owns; the seq is the right half.

**The token lives outside the database file, and that is the point.** The
sidecar file `EnsureGeneration` reads and writes sits next to the database, not
inside it. A file-level restore of the `.db` alone therefore cannot roll the
token back in step with the data: the token stays, the mismatch is invisible,
which is exactly the case a bare-seq cursor could not survive. A **box-level**
restore or rollback (`opsctl restore` / `opsctl rollback`) removes the sidecar,
so the next boot finds it absent and mints a **new** epoch. An empty path yields
an ephemeral in-process token (tests only).

**A rewound seq space becomes a visible resync, never a silent skip.** A restore
or rollback rewinds the outbox's `AUTOINCREMENT` seq space: seqs that were
already delivered will be reissued to new events. A consumer resuming from a
bare pre-restore seq would silently skip or double-deliver across the seam. With
epoch-stamped cursors, the feed compares the cursor's generation half against
the live generation on connect; a mismatch is the `stale-epoch` resync reason.
The feed sends an `event: resync` frame and closes; the consumer treats a
received resync as authoritative, discards its persisted cursor, and
re-bootstraps from its configured start position (from-earliest for a
subscribe-from-earliest consumer) rather than trusting a seq the restored feed
will reuse. A silent data-integrity failure is turned into one visible,
logged reposition.

The resync reason set and the stale-epoch wire semantics are the suite wire
contract (`root project/design/D18.md`, on the SSE wire); this Decision records
eventplane's implementation of the epoch token and its restore behaviour, it
does not restate the wire.

**Rejected.**

- *A bare-seq cursor with no epoch.* After a restore the seq space rewinds, so a
  durable cursor of a plain seq silently skips or replays events across the
  seam. The epoch prefix is the only thing that makes the discontinuity
  detectable at connect.
- *Storing the epoch token inside the database file.* A file-level restore would
  roll the token back together with the data, so the consumer's stale cursor
  would still match the restored epoch and the skip would go undetected. The
  token must live outside the `.db` precisely so a restore invalidates it.
- *Minting the epoch once and reusing it forever.* That defeats the mechanism:
  the safety property is that removing the sidecar — what `opsctl restore` /
  `opsctl rollback` does — forces a fresh epoch on the next boot. A token that
  never changes cannot signal that a restore happened.
- *Having the consumer validate the epoch itself.* The consumer never parses the
  opaque cursor (D1); the feed owns the comparison and expresses the outcome as
  a resync reason, so the consumer's contract stays "a resync is authoritative,
  re-bootstrap" with no cursor introspection.

**Verification.**

- R-4BT8-D54J — `EnsureGeneration` mints a fresh epoch when the sidecar is
  absent after a restore: the first call against a temp path returns a non-empty
  generation and persists it; after the sidecar file is removed (simulating a
  restore), a second call returns a **different** non-empty generation and
  writes that re-minted value back to the sidecar path verbatim.
- R-4D14-QWV8 — a stale pre-restore cursor triggers a stale-epoch resync
  end-to-end (real `FeedHandler` + `httptest` + `consumer.Run` on real SQLite):
  a producer emits three events under one epoch and a consumer advances its
  durable cursor to `<oldgen>.3`; the sidecar is then removed and a second
  producer boots under a **new** epoch over the same database; on reconnect the
  feed detects the stale epoch, emits `resync`/`stale-epoch` (logged as data
  loss), and the consumer discards the stale cursor and replays events `1,2,3`
  from the start under the re-minted epoch.
