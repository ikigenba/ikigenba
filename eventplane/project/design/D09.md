# Decision 9 — `eventplane/observe`: an injectable hook on the publish and consume paths

**Decision.** A new stdlib-plus-`routing` leaf package `eventplane/observe`
defines a single callback type and the metadata it is handed; `outbox` and
`consumer` each accept one optional hook and call it after a hop completes. The
library learns nothing about who is listening — the appkit chassis wires its
telemetry recorder in at its composition root, which is the only arrangement the
dependency direction permits (appkit requires eventplane; the reverse is a
cycle — see research).

```go
package observe

// Hop names the event-plane hop being observed.
type Hop string

const (
    HopPublish Hop = "publish" // a producer appended an event
    HopConsume Hop = "consume" // a consumer's handler processed an event
)

// Event is the metadata of one completed hop. It is deliberately a SKELETON:
// addressing, identity, outcome and timing — never the payload. An observer
// that wants the body must get it from the domain, not from here.
type Event struct {
    Hop           Hop
    Source        string        // producing service (the consume side reports the upstream)
    Kind          string
    Subject       string
    EventID       string        // the envelope id; "" on a publish that failed before minting
    CorrelationID string        // the chain the hop belonged to; "" when uncorrelated
    Err           error         // nil on success; the failure otherwise
    Duration      time.Duration // time spent in the observed hop
}

// Key returns the canonical routing key of the observed event —
// routing.Key(Source, Kind, Subject).
func (e Event) Key() string

// Hook observes one completed hop. It is invoked synchronously, must not
// block, and must not assume it is called at most once per event (a
// re-delivered event is a second real consume hop). A nil Hook is never
// invoked. The library recovers from a panicking Hook: observation can never
// affect delivery.
type Hook func(ctx context.Context, ev Event)
```

*Wiring.* `outbox.Options` gains `Observe observe.Hook`; `consumer.Config`
gains `Observe observe.Hook`. Both default to nil (no observation), so no
existing caller changes.

*Producer side.* `Append` times itself and invokes the hook once on every call
that reached it — success **and** failure, including a rejected kind/subject
and a registry rejection, with `Err` set and `EventID` empty when the event
never got that far. The hop is observed at **append**, not at commit: the
library never sees the caller's `Commit` (the caller rings the doorbell
afterwards), and `Ring` carries no event identity. The consequence is explicit
and accepted — an appended event whose transaction is later rolled back still
produced a publish observation. `Append`'s own return value is unaffected by
the hook.

*Consumer side.* The engine times the handler invocation and invokes the hook
once per delivery, with the correlation id the handler's context carried (D8 —
so a minted root is reported, not the empty wire value) and `Err` set to the
handler's return, `ErrSkip` included. It is **not** invoked for the engine's
unparseable-envelope skip: no handler ran and there is no address to attribute
the hop to. Control frames (`resync`, `caught-up`, `status`, keepalives) are not
hops and are never observed. The hook's own outcome never influences the cursor:
the handler's return alone gates it, exactly as before.

*Isolation.* Every invocation on both sides is wrapped so a panic is recovered
and logged, and a returned value is impossible by construction (`Hook` returns
nothing). A hook that panics on every call therefore changes no delivery, no
ordering, and no cursor progress. Blocking is the one thing the library cannot
defend against — the contract says so, and the chassis' recorder is a buffered
non-blocking enqueue.

**Rejected.**

- *Importing appkit's recorder directly* — an import cycle (`appkit` requires
  `eventplane`), and it would bind the library to one chassis besides.
- *Publishing observations as events on the plane itself* — infinitely
  recursive (observing a publish publishes), and it would put observation
  inside the outbox transaction where a failure could roll back a domain write.
- *A `Hook` that returns an `error`* — invites a caller to believe the error
  matters, when the one non-negotiable property is that observation cannot
  affect delivery. Returning nothing makes that unmistakable.
- *An interface (`Observer` with a method) instead of a func type* — a func
  type composes trivially (a closure over the recorder), needs no adapter type
  in the chassis, and matches how `Handler` is already declared here.
- *Handing the hook the payload* — the observers this seam exists for record
  skeletons, not bodies; passing bulk domain content through a telemetry seam
  is the failure mode the suite's telemetry contract is built to avoid.
- *Invoking the hook asynchronously in a goroutine per hop* — an unbounded
  goroutine per event to defend against a blocking observer; the contract
  ("must not block") plus a buffering observer is the cheaper and more honest
  arrangement.
- *Observing the publish hop at `Ring()` instead of `Append`* — `Ring` is a
  bare doorbell carrying no event identity, and is not called at all on some
  paths; there is nothing there to observe.
- *Buffering publish observations on the `Outbox` and flushing them at `Ring`
  (to observe only committed events)* — the buffer would have to be keyed by
  transaction to be correct, since `Append` and `Ring` are separate calls with
  no handle between them; the library would be inventing transaction tracking
  it has deliberately never had, to fix an over-count on a path (rollback after
  a successful append) that is already rare and visible.

**Verification.**

- R-UXUQ-ZDNA — the publish hook fires exactly once per successful `Append`,
  with `Hop == HopPublish`, `Source`/`Kind`/`Subject` equal to what was
  appended, `Key()` equal to the canonical key (e.g.
  `dropbox:create/bills/a.pdf`), `EventID` equal to the id that lands in the
  outbox row (read back by SQL), `CorrelationID` equal to the appending
  context's id, and `Err == nil`.
- R-V0AJ-QX4O — failures are observed too: an `Append` rejected for an invalid
  kind, and one rejected by a non-empty registry, each fire the hook once with
  a **non-nil** `Err` and no row inserted — so an observer sees the attempt,
  not only the successes.
- R-V1IG-4OVD — the consume hook fires once per delivery over a real feed
  (real `FeedHandler` + `httptest` + `consumer.Run`) with `Hop == HopConsume`,
  the event's address and id, `Err == nil` for a handler returning nil, and
  `CorrelationID` equal to the id the handler's context carried — including
  the **minted root** case, where the wire value was `""` and the observation
  reports the non-empty minted id.
- R-V2QC-IGM2 — the consume hook reports the handler's failure and does not
  alter its effect: a handler returning a wrapped `ErrSkip` yields one
  observation whose `Err` satisfies `errors.Is(err, consumer.ErrSkip)` and the
  cursor still advances; a handler returning some other error yields an
  observation carrying that error and the engine still stalls, re-delivering
  the same event (which fires a second consume observation for the same event
  id).
- R-V3Y8-W8CR — `Duration` measures the real hop: a handler that sleeps 50ms
  yields a consume observation with `Duration >= 50ms`, while a handler
  returning immediately yields one under 50ms — the field tracks the work, not
  a constant.
- R-V565-A03G — observation cannot hurt delivery: with a hook that panics on
  every single call wired into **both** the producer and the consumer,
  `Append` still returns nil and the row is present, and a three-event feed is
  delivered in order to the handler with the cursor committed past all three
  (verified by reconnecting and receiving nothing) — byte-identical outcomes
  to the same scenario with a nil hook.
- R-V6E1-NRU5 — the hook is not invoked where there is no hop: with a hook
  recording every call, a frame whose envelope decodes with an empty `kind`
  produces **no** consume observation while the cursor still advances past it,
  and `caught-up`/`status`/keepalive frames produce none either — the
  observation count over such a stream is exactly the number of events whose
  handler ran.
