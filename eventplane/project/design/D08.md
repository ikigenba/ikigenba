# Decision 8 — Correlation on the consumer path: the chain enters the handler's context

**Decision.** The consumer engine restores the chain on the receiving side: the
envelope's `correlation_id` becomes both a visible field on the delivered event
and — the load-bearing half — the correlation id of the **context the handler
runs under**, so everything the handler causes belongs to the same chain
without the handler arranging anything.

*The event carries the wire fact.*

```go
type Event struct {
    ID            string          // envelope "id"
    Source        string          // envelope "source"
    Time          string          // envelope "time"
    Kind          string          // envelope "kind"
    Subject       string          // envelope "subject"
    CorrelationID string          // envelope "correlation_id" — "" when the event carried no chain
    Payload       json.RawMessage // opaque domain snapshot
}
```

`parseEvent` reads the new field alongside the others. `CorrelationID` reports
the **wire** fact and is never synthesized: an event published outside any chain
delivers `CorrelationID == ""`, even though its handler still runs correlated
(below). Keeping the two distinguishable is what lets a downstream observer say
"this chain started here" rather than inventing provenance.

That emptiness is **load-bearing, not incidental**. This field is the only place
the wire fact survives: once the engine has derived the handler's context, a
propagated id and a freshly minted root are indistinguishable from the context
alone, and the observation seam (D9) reports only the derived id. A downstream
observer that needs to know an event arrived uncorrelated — to record where a
chain began — has exactly one signal, `CorrelationID == ""`, and the chassis
relies on it. So the field must never be backfilled with the minted root as a
convenience: doing so would silently erase every chain origin in the suite while
every test that only checks "the handler is correlated" still passed.
R-UQJC-OR74 and R-UU71-U2F7 pin the guarantee in both directions.

*The handler runs inside the chain.* Where `handleFrame` today calls
`e.h(ctx, ev)`, it now calls the handler with a context derived as:

- the envelope's id when it is `correlation.Valid` — propagated **verbatim**;
- otherwise a **fresh root**, `correlation.New()`, attached for this event only.

The mint-on-absence case is the correlation standard's sanctioned one: no
durable root exists, and the alternative is downstream work with no chain at
all. It is per event, never per connection or per process — two uncorrelated
events must not appear to share a cause. A non-empty but malformed id is
treated exactly as absent: garbage is never propagated, and never allowed to
name a chain.

```go
// inside handleFrame, before invoking the handler
hctx := ctx
if id := ev.CorrelationID; correlation.Valid(id) {
    hctx = correlation.WithContext(ctx, id)
} else {
    hctx = correlation.WithContext(ctx, correlation.New())
}
```

Nothing else about delivery changes: the engine still invokes the handler for
every event, the handler's return still gates the cursor (nil / `ErrSkip` /
stall), and the engine's own unparseable-envelope skip still runs no handler and
still advances. On a stall-and-replay the event is re-delivered and its context
is re-derived — a propagated id is identical on every delivery; a minted root is
fresh per delivery, since each delivery is a distinct attempt at the work.

*Why this composes.* A handler that appends to its own outbox with the context
it was handed (D7's `Append(ctx, …)`) publishes an event carrying the original
chain id, with no correlation-specific code anywhere in the service. That is the
whole mechanism by which a chain survives an arbitrary number of hops.

**Rejected.**

- *Handing the id to the handler as a parameter or only as `ev.CorrelationID`* —
  every handler would then have to remember to re-attach it to every context it
  passes onward, which is precisely the propagation step that gets forgotten.
  The context already flows through every downstream call.
- *Minting once per connection or per consumer process* — cheaper, and wrong:
  unrelated events would report a shared cause, which is worse than no chain
  because it asserts a falsehood a forensic reader cannot detect.
- *Propagating a malformed id verbatim ("carry what you were given")* — the
  standard's verbatim rule presumes a well-formed id; carrying garbage spreads
  a value nothing can resolve and lets a bad producer name chains.
- *Synthesizing the minted root into `Event.CorrelationID`* — makes the
  delivered event misreport what was on the wire, erasing the distinction
  between a chain that arrived and one that started here.
- *Minting in the engine's unparseable-envelope path* — no handler runs, so
  there is nothing to correlate.

**Verification.**

- R-UQJC-OR74 — end-to-end over a real feed (real `FeedHandler` + `httptest` +
  `consumer.Run`, real SQLite): an event appended under correlation `X` is
  delivered with `ev.CorrelationID == X`, and an event appended under a bare
  context is delivered with `ev.CorrelationID == ""` (not a minted value).
- R-URR9-2IXT — the handler's **context** carries the propagated chain: for the
  event appended under `X`, `correlation.FromContext(hctx)` inside the handler
  equals exactly `X` (real feed round trip) — not a fresh id that merely
  happens to be valid.
- R-USZ5-GAOI — mint-on-absence, per event: two events appended under bare
  contexts are delivered to handlers whose contexts carry `Valid`, non-empty
  ids that are **different from each other** (ruling out both an empty context
  and a single per-connection or per-process root).
- R-UU71-U2F7 — a non-empty malformed id is treated as absent: an event whose
  envelope carries `correlation_id: "not-a-correlation-id"` (published by
  writing that value into a real outbox row) is delivered with the handler's
  context carrying a `Valid` id that is **not** that string, and
  `ev.CorrelationID` still reporting the wire value verbatim.
- R-UVEY-7U5W — the chain survives a hop, end to end on real substrates: two
  producers each with a real SQLite outbox and a real `FeedHandler`; producer A
  appends under correlation `X`; the consumer's handler appends to producer B's
  outbox using **the context it was handed**; a second consumer on B's feed
  receives an event whose `CorrelationID` is exactly `X`. No test-supplied
  plumbing carries `X` between the two — only the context.
- R-UWMU-LLWL — correlation changes no delivery behavior: over a real feed, an
  event whose envelope decodes with an empty `kind` is still engine-skipped
  (no handler, cursor advances, next event delivered), and a handler returning
  a non-skip error on a correlated event still stalls and re-delivers that same
  event before any later one.
