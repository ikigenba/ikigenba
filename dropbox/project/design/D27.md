# Decision 27 — nginx fragment: gated locations forward the edge-minted correlation id; ungated public locations clear it

**Problem.** The chassis trusts a well-formed inbound `X-Correlation-Id`
verbatim, because loopback callers are inside the trust boundary. That trust is
only sound if nothing *outside* the boundary can put a value in that header —
and today `dropbox/etc/nginx.conf` says nothing about the header at all. nginx
does not forward an inbound client header as a proxy header unless a
`proxy_set_header` names it, so the header is not currently *smuggled*; but it
is also not *supplied*, which means every gated request through the fragment
would arrive with no id and the chassis would mint a fresh one — discarding the
id the dashboard's introspection already minted for that chain and breaking the
`edge` record's link to everything downstream of it.

**Decision.** `dropbox/etc/nginx.conf` adopts the suite-wide fragment contract.
The change is purely additive; no existing location, variable, or
`proxy_pass` is rewritten.

### Gated locations capture and forward the minted id

The dashboard's introspection endpoints (`/_authn` and `/_session-authn`) mint
the correlation id for an allowed request and return it on the auth subrequest
response as `X-Correlation-Id`. Each of dropbox's three gated locations captures
it with `auth_request_set` and forwards it with `proxy_set_header`, using the
fragment's existing service-prefixed variable convention (every service fragment
is included into one apex `server` block, so names must be unique):

```
# location = /srv/dropbox/            (session tier — landing page)
auth_request_set $dropbox_session_correlation_id $upstream_http_x_correlation_id;
proxy_set_header X-Correlation-Id $dropbox_session_correlation_id;

# location /srv/dropbox/static/       (session tier — landing assets)
auth_request_set $dropbox_static_correlation_id $upstream_http_x_correlation_id;
proxy_set_header X-Correlation-Id $dropbox_static_correlation_id;

# location /srv/dropbox/              (bearer tier — MCP and everything else)
auth_request_set $dropbox_correlation_id $upstream_http_x_correlation_id;
proxy_set_header X-Correlation-Id $dropbox_correlation_id;
```

The **overwrite property** is the point, and it comes free from nginx's own
rules: a single `proxy_set_header X-Correlation-Id $var;` replaces any inbound
client value on the upstream request, exactly as the four `X-Owner-*` headers
and `X-Client-Id` are already replaced (D4). A client cannot smuggle a chain id
in through any gated location.

The static-asset tier is included even though it forwards no owner identity
today: it is session-gated, so the id is available, and an asset fetch that
belongs to a page view should sit on that page view's chain rather than opening
a fresh one.

### Ungated public locations clear the header

`= /srv/dropbox/.well-known/oauth-protected-resource` is the fragment's one
public, unauthenticated, *proxied* location — an MCP client with no token must
be able to fetch the RFC 9728 document. There is no auth subrequest, so there is
no minted id to capture; instead the location explicitly clears the header so
the chassis mints:

```
proxy_set_header X-Correlation-Id "";
```

### Locations that proxy nothing are untouched

`= /srv/dropbox/content { return 404; }` and `location @dropbox_authn_500`
(which only re-emits a `429` or `500`) never reach an upstream, so they have no
`proxy_set_header` to add and are left exactly as they are.

**Judgment call recorded.** The empty-value `proxy_set_header X-Correlation-Id
"";` is the form chosen over `proxy_set_header X-Correlation-Id $request_id;`
(nginx's own per-request id) or omitting the line entirely. Omitting it is
*currently* safe — nginx passes no unnamed inbound header through — but it makes
the safety an implicit consequence of nginx's default rather than a stated
property of the fragment, and it would silently become unsafe under a future
`proxy_pass_request_headers`-style change. `$request_id` would inject a
non-Crockford value the chassis would reject and replace anyway.

**Rejected.**
- **Relying on nginx's default not to forward inbound headers** — see the
  judgment call: correct today, but silent and fragile, and it leaves a reader
  of the fragment unable to see the guarantee.
- **Capturing the id only on the bearer tier** — a human's page view and its
  asset fetches would then start unrelated chains, and the dashboard `edge`
  record for the session gate would link to nothing.
- **Adding the header to `= /srv/dropbox/content` or `@dropbox_authn_500`** —
  neither proxies to an upstream; the directive would be dead config.
- **A shared `$correlation_id` variable name across service fragments** — every
  fragment is included into the same apex `server` block; the service prefix is
  what keeps the names from colliding.

**Verification.** The fragment is configuration, not Go, so — exactly as D4, D8,
D10 and D21 already do — it is pinned by a test that reads
`dropbox/etc/nginx.conf` from disk and asserts over its content. These ids
extend that existing fragment test in `cmd/dropbox`; they are a genuine
assertion over the shipped artifact, and they run in the same
`cd dropbox && go test ./...`. The *behavioral* consequences of the header —
that a trusted inbound id is honored and a malformed or absent one is minted —
are appkit's chassis claims and are not re-asserted here.

- R-VGTA-PXIA — each of the three **gated** locations carries both halves of the
  capture/forward pair with its own service-prefixed variable: `location =
  /srv/dropbox/` has `auth_request_set $dropbox_session_correlation_id
  $upstream_http_x_correlation_id;` and `proxy_set_header X-Correlation-Id
  $dropbox_session_correlation_id;`; `location /srv/dropbox/static/` the same
  with `$dropbox_static_correlation_id`; and the bearer-gated `location
  /srv/dropbox/` prefix the same with `$dropbox_correlation_id` — while its
  existing `X-Owner-*` and `X-Client-Id` forwards are retained unchanged. A
  fragment that captures without forwarding (or forwards a variable it never
  captured, which nginx renders as empty) fails.
- R-VI17-3P8Z — the ungated public
  `= /srv/dropbox/.well-known/oauth-protected-resource` location carries
  `proxy_set_header X-Correlation-Id "";` (the **empty** value, not a variable
  and not `$request_id`), and the file contains exactly **four**
  `proxy_set_header X-Correlation-Id` directives in total — one per proxying
  location — so neither the `= /srv/dropbox/content` 404 block nor the
  `@dropbox_authn_500` named location gained a dead directive and no gated
  location was missed or double-set.
