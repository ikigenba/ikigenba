# Decision 26 — The correlation chain through dropbox's Go surface: instrumented outbound clients, daemon root chains, context-threaded `Append`

> **External ordering (operator-sequenced, not built by any dropbox phase).**
> This Decision consumes three things dropbox does not own and does not design:
> the chassis's **instrumented outbound HTTP client**, obtained from the
> `Router` (`rt.HTTPClient(…)`) already wired to the recorder; the chassis's
> **root-start helper**, which mints a correlation id, returns a context
> carrying it, and emits the `root` record in one call; and eventplane's
> context-taking `Outbox.Append`. Their exact names and signatures belong to
> `appkit/project/design/` and `eventplane/project/design/`; the facts dropbox
> leans on are collected in `project/research/research.md`. Both must be **built
> before** this Decision's phase runs — the `Append` change is compile-caught,
> so dropbox does not build until it is threaded.
>
> dropbox mints **nothing itself**: it neither constructs a correlation id nor
> assembles a `root` record nor touches the recorder. It calls the chassis
> helper at the top of a cycle and passes the returned context down.

**Problem.** dropbox is the suite's noisiest outbound talker and its only
service whose most interesting work is caused by nobody: a longpoll wakes, a
page of deltas is applied, files are downloaded and events published, and an
upload queue drains — all with no inbound request anywhere in sight. Under the
new telemetry capability that produces two concrete defects.

1. **Every Dropbox API call is invisible.** `internal/dropbox/client.go`
   constructs its own `*http.Client`s (`rpc`, `longpoll`) and
   `internal/mcp/tools.go` constructs a third (`sourceClient`) for the
   `source_url` fetch. A privately-constructed client is not instrumented, so
   none of those calls produce an `outbound` record — a forensic agent asking
   "why did this file change" sees the local index write and nothing about the
   call that caused it.
2. **Daemon work has no chain.** The sync engine and the uploader run on the
   server lifecycle context, which carries no correlation id. Every record they
   produce would land with an empty `correlation_id`, so the whole
   longpoll → apply → publish story would be an unordered pile rather than a
   chain.

A third, smaller change rides along: `Outbox.Append` grows a `context.Context`
parameter, and dropbox's one append site currently has no context to give it.

**Decision.** dropbox stops constructing outbound HTTP clients and starts
opening root chains for its daemons, in four parts.

### 1. Every outbound client is injected, and built from the chassis

The three call sites each take their `*http.Client` as an **injected
dependency** built once at the composition root (`cmd/dropbox/main.go`) from the
chassis's instrumented outbound client. dropbox owns the *injection seam*;
appkit owns the *instrument*.

```go
// internal/dropbox — the existing optional-client parameter becomes required
// and gains its sibling. A nil client is a programming error, not a default.
func NewClient(cfg Config, rpc, longpoll *http.Client) *Client

// internal/mcp — the source_url fetcher is injected the same way.
func Tools(svc *dropbox.Service, sourcePortAllowed func(port int) bool,
	source *http.Client) []appkitmcp.Tool
```

**Timeouts stay dropbox's.** The three clients exist because they need
*different* deadlines, and instrumenting them must not flatten that: the rpc /
content client keeps its ~100s timeout, the longpoll client keeps its ≥600s
parked-read timeout (`longpollClientTimeout`), and the `source_url` fetcher
keeps its 5s dial / 5s response-header transport and its
`ErrUseLastResponse` redirect policy. The composition root obtains each client
from the Router's instrumented-client seam (`rt.HTTPClient(…)`), which returns a
client already wired to the chassis recorder. dropbox therefore asks that seam
for **three** clients, not one, and its requirement on the seam is that it admit
per-call-site policy: the rpc/content client's ~100s timeout, the longpoll
client's ≥600s timeout, and the `source_url` client's dial/response-header
transport plus its custom redirect policy. How that is expressed — options on
the call, a returned client the caller adjusts, or a transport it installs — is
appkit's shape to choose; dropbox's seam is the same either way. The
package-level constants
(`longpollClientTimeout`, the 5s dialer) stay where they are: they are dropbox's
policy, not the chassis's.

**No header goes to Dropbox.** Propagating `X-Correlation-Id` only to loopback
peers is the instrumented client's rule, not a dropbox conditional — dropbox
writes no host check. The observable consequence dropbox does assert is the one
that matters for a leak: calls to `api.dropboxapi.com` /
`content.dropboxapi.com` / `notify.dropboxapi.com` carry no correlation header
even when the ambient context has an id, while the loopback-confined
`source_url` fetch does.

### 2. The sync engine opens a root chain per cycle

`Engine.bootstrap` and each iteration of `Engine.steadyState`'s
longpoll → continue → apply loop is one causal unit, so each **starts a fresh
root chain**: at the top of the cycle the engine calls the chassis's
root-start helper with the origin name below, and the helper mints the id,
returns the cycle context carrying it, and emits the one `root` record —
best-effort, never blocking, exactly like every other record. The root is minted
**once per cycle**, never per detected change or per emitted event, so every
reaction to one cycle reconstructs as one chain. Every call made inside that
cycle — the Dropbox API calls, the mirror writes, the event appends — runs on
that context. Two consecutive cycles therefore carry two different ids, and one
cycle's downloads, index writes and published events all share one.

The root's origin name is **`dropbox:sync/<cycle>`**, where `<cycle>` is
`bootstrap` for the enumerate-or-resume pass and `longpoll` for a steady-state
pass. A parked longpoll that returns "no changes" still belongs to its cycle;
nothing special is done for it.

### 3. The uploader opens a root chain per drain pass that has work

`uploader.go` drains `upload_queue` asynchronously, deliberately decoupled from
the request that enqueued the row — the enqueuing request's chain ended when its
transaction committed. The drain pass is **work-gated**: it first reads the due
rows (a local SQLite query that produces no telemetry records), and when none
are due it returns having touched the recorder not at all — an idle pass emits
**zero** records. Only when at least one row is due does the pass open its
**own** root chain through the same chassis helper, origin
**`dropbox:upload/drain`**, and every Dropbox write call it makes runs on that
context. The gate matters because the uploader ticks every second: an
unconditional per-pass root is ~86,400 pure-noise records/day on an idle box,
which drowns the forensic timeline the capability exists to serve. The sync
engine's per-cycle root (§2) is deliberately **not** gated this way: a longpoll
cycle parks for minutes and makes a real API call whose `outbound` record the
root ties into its chain, so its idle cost is bounded and its root earns its
keep.

**The enqueuing request's id is deliberately not carried forward.** Carrying it
would mean a new `upload_queue` column, a migration, and a chain that stays open
across an arbitrary retry delay; the queue row already ties cause to effect by
path, and the forensic question ("what pushed this byte range up") is answered
by the drain chain plus the row.

### 4. `Append` is threaded with the causing context

`internal/dropbox/events.go`'s single `o.ob.Append(tx, e)` becomes
`o.ob.Append(ctx, tx, e)`, and the `EventSink` seam grows the context it needs
to do that:

```go
// internal/dropbox — the sink seam carries the chain the change happened on.
type EventSink interface {
	Emit(ctx context.Context, tx *sql.Tx, ev FileEvent) error
}
```

The context handed in is the one the change is **already** on — an MCP tool call
or a loopback route call is on that request's chain (put there by the chassis
middleware), a sync apply is on that cycle's root chain — so no call site
invents an id and none passes `context.Background()`. eventplane reads the id
from that context and stores it on the outbox row; dropbox's event **payload
gains no field** (the envelope carries the id, per the revision that supersedes
the old payload-field convention).

**What arrives free and is deliberately not designed here.** Inbound `request`
records for `POST /mcp` and the loopback routes, `lifecycle` start/stop records,
the `publish` hop at append, and the read-or-mint of an inbound header all come
from the rebuilt appkit/eventplane. dropbox neither wires nor re-proves them —
duplicating chassis coverage in a service suite is exactly the redundancy the
chassis exists to prevent.

**Rejected.**
- **A package-level instrumented client shared by all three call sites** —
  collapses three deliberately different timeouts into one, and the ≥600s parked
  read would either strangle rpc calls or leave the longpoll unreapable.
- **Keeping `NewClient(cfg, nil)` as "use the default"** — a nil client is now
  the one shape that silently disables instrumentation; making the parameter
  required turns a telemetry hole into a compile error.
- **Letting dropbox decide when to send `X-Correlation-Id`** (a host check in
  `client.go`) — the loopback-only rule would then be reimplemented, and drift,
  in every service that talks outward. It belongs in the one shared client.
- **One root chain for the whole daemon lifetime** — every sync cycle for weeks
  on one id: the chain stops being a chain and becomes a service-wide bucket.
- **No root at all (empty `correlation_id` for daemon work)** — the majority of
  dropbox's records would be unlinkable, which is the failure the capability
  exists to fix.
- **Carrying the enqueuing request's correlation id on the `upload_queue` row** —
  a migration and an indefinitely open chain to express a link the row already
  expresses; revisit only if a real forensic question needs it.
- **Recording dropbox's own `outbound`/`request` records in dropbox code, or
  hand-minting a root id and assembling its record** — that is the chassis's
  job, and the root-start helper exists precisely so every service's roots have
  one shape; a service that hand-rolls records diverges from all of them.
- **A root per detected change or per emitted event** — a cycle that applies a
  page of forty deltas would produce forty unrelated chains, which is the
  fragmentation the per-cycle root exists to prevent.
- **An unconditional root per uploader drain pass** (the original shape of §3) —
  at a one-second tick it is ~86,400 idle root records/day of pure noise; the
  root's purpose is to chain work, and a pass that finds no due rows does none.
- **Gating the sync cycle's root the same way** — the longpoll cycle makes a
  real API call before it can know whether changes exist; minting the root only
  on changes would orphan that call's `outbound` record from its chain, and at
  a 480s park the idle cost (~180 roots/day) is bounded anyway.

**Verification.** (Real substrates throughout: a `httptest` fake Dropbox for the
third-party side — the existing `client_test.go` pattern — a real loopback
`httptest` server for the `source_url` side, a recording `http.RoundTripper`
installed *by the composition root's own wiring path* so the assertion is about
what ships, and a real temp SQLite database migrated through the full embedded
set for the outbox claim.)

- R-TABR-0FWD — driving `NewClient`'s rpc and content calls against the
  `httptest` fake Dropbox, with a context carrying a valid correlation id,
  every request is observed at the injected instrumented seam (a build that
  constructs its own `http.Client` is never observed and fails), and **no**
  observed request to the fake Dropbox host carries an `X-Correlation-Id`
  header — neither the rpc/content calls nor the token-refresh exchange.
- R-TBJN-E7N2 — the composition root's wiring yields three distinct clients over
  the instrumented seam whose timeouts are preserved, not flattened: the
  longpoll client's `Timeout` is **≥ 600s**, the rpc/content client's is
  **> 0 and ≤ 120s**, and the two are not the same client value; the
  `source_url` client's redirect policy still returns `http.ErrUseLastResponse`.
- R-TCRJ-RZDR — an MCP `put` with a `source_url` pointing at a real loopback
  `httptest` server, invoked through the assembled MCP handler on a context
  carrying a known correlation id, reaches that server with an
  `X-Correlation-Id` request header equal to that id, and the fetch is observed
  at the injected instrumented seam — the bytes land in the mirror, proving the
  call completed rather than merely that a client was configured.
- R-TDZG-5R4G — a sync cycle and an uploader drain pass **that has due work**
  each run on a context whose correlation id is non-empty, 26 characters and
  Crockford-valid, is **different** for two consecutive cycles of the same
  daemon, and is **one and the same** id across every Dropbox API call and
  every event that a single cycle applying multiple changes makes — starting
  from an ambient context that carries **no** id. A build that inherits the
  lifecycle context fails (empty id); a build that opens a root per change
  rather than per cycle fails (two changes in one cycle carry two ids).
- R-NF5W-7DOI — the uploader's root is work-gated: a drain pass over an
  `upload_queue` with **no due rows** (empty, or rows whose retry gate is in
  the future) invokes the root-start seam **zero** times and emits no telemetry
  record of any kind, across multiple consecutive idle passes; a pass with at
  least one due row invokes it **exactly once**. A build that mints the root
  before checking the queue fails (idle passes observe a root); a build that
  mints per row fails (one pass draining two due rows observes two).
- R-TF7C-JIV5 — reading outbox rows back by SQL from the real migrated SQLite
  database: an event emitted by a service write performed on a context carrying
  a known correlation id stores **that exact id** in the row's
  `correlation_id` column, and an event emitted by a sync apply stores the
  **cycle's** root id (non-empty and Crockford-valid) — a build that appends
  with `context.Background()` leaves the column empty and fails both halves.
