# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail webhooks records of itself, and the route table its handler keeps. It is cron's serve path with three differences: a sweeper takes the scheduler's place (`D04-store` sweeps, this document says when), the identity gate is appkit's `identity.Optional` everywhere but `/mcp`, which keeps `identity.Require`, and the paths under `/in/` reach the ingress (`D05-ingress`). `internal/server` is cron's, unchanged.

## The terms webhooks serves on

webhooks serves only on a listening socket it inherits, taken as `sd_listen_fds(3)` documents, and reports readiness with `READY=1` to `NOTIFY_SOCKET` as `sd_notify(3)` documents. It trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them; nginx sets all three itself, so a sender outside the suite cannot forge them. Every request has an id: the one nginx set, or 32 lowercase hexadecimal digits appkit's request middleware draws from `Process.Rand`.

The events app reaches webhooks at its socket on `/events` and `/declarations`. webhooks accepts no event, so it mounts appkit's `events.DeliveryHandler` with no handlers, and `events.DeclarationsHandler` over its emitter, built with the four declarations of `trail.Emits()`. These two paths sit outside the identity gate; the fragment answers both 404 at the public name (`D02-cli`).

## The route table

Every request goes through appkit's `telemetry.Middleware`, which records `request.started` and `request.finished`. Then, by the URL path alone: `/events` and `/declarations` go to the event bus's two handlers; `/mcp` goes, through appkit's `events.Middleware` and `identity.Require`, to the MCP server, with webhooks' own address on the context for the tools (`D08-tools`); every other path goes through `identity.Optional`, then to the ingress when it begins `/in/`, to `page.Static()` when it begins `/_appkit/`, and otherwise to `pages.Handler` (`D06-pages`). A guest — a request with no `X-User-Id` — therefore reaches the ingress, the shared files and the pages, which send it to sign in; at `/mcp` it is answered appkit's 500 with `identity.MissingBody`, which on a host never happens because nginx demands a credential there first.

## Checking the start, the database, the sweep and readiness

With `Args` empty, `Run` checks the two settings, then whether exactly one socket was passed in, exactly as cron does, with the same diagnostics after `webhooks: `. It removes the three `LISTEN_*` variables, takes descriptor 3, and opens the database with `db.Open` at `state/webhooks.db`; a failure is `webhooks: cannot open database state/webhooks.db: ` and the reason, exit 1. It builds the store, the run's writer, the run's emitter (with `trail.Emits()`), and starts the sweeper (`internal/sweeper`), which sweeps once before `Run` goes on and then once each time a wait of `sweeper.Interval` on `Process.After` ends. Then it builds the handler, sends `READY=1`, and calls `Writer.Ready`, so `service.started` is the first event of a run.

## Stopping

When `ctx` is done `Run` stops the sweeper, drains the server for `DRAIN_SECONDS`, waits within the same window for the emitter to deliver what it holds, shuts the writer down with the cause's text as `service.stopping`'s reason, shuts the emitter down, and closes the database. A drain that runs out is `webhooks: stopped with <n> request(s) unfinished`, exit 1.

## Recorded decisions

- The sweep interval is one hour, events' interval; the first sweep runs before readiness, as events' and telemetry's do, so a start never serves deliveries already past the window.
- A sweep that fails, the database being unreachable, is silent and tried again at the next interval, as cron's failed fire is: it earns no line on standard error.
- `/_appkit/` is served to guests, as sites serves it, since the ingress's guests never ask for it and a guest's sign-in redirect never needs it either; nothing there is private.
