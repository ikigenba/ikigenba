# D08-tools

The six MCP tools agents reach webhooks by through the MCP gateway: `internal/tools`, and `internal/urls`, which builds the address each webhook is given. They follow cron's tools: every user lists, a page at a time, and shows every webhook, only the owner changes one, and another user's webhook is refused as one that does not exist.

## The tools

- `create` takes `slug` and an optional `scheme`, `bearer` (the default) or `github-hmac`, and answers the webhook with its `secret`, minted then and shown this once. It emits `webhook.<slug>.created`.
- `list` takes an optional `page` and `limit` and answers one page of the space's webhooks, by slug, without their created time, then `next` when more follow (below).
- `show` takes `slug` and answers one webhook.
- `rotate` takes `slug`, mints a new secret at once, so the old one stops working, and answers the webhook with the new `secret`; the URL is unchanged. Owner only. It emits `webhook.<slug>.rotated`.
- `delete` takes `slug`, deletes the webhook and its deliveries, and answers `{"deleted":true,"id":"whk_…"}`. Owner only. It emits `webhook.<slug>.deleted`.
- `delivery` takes `id` and answers one delivery to a webhook the caller owns: `id`, `hook` (the slug), `received`, `content_type`, `headers` (the kept headers present, each a `name` and a `value`), and the body as `body` when it is valid UTF-8 and as `body_base64` otherwise. A delivery to another user's webhook is refused as one that does not exist, since a body can hold private data; a script subscribed by another user sees the event's attributes but cannot fetch the body.

A webhook as `show` answers it has `id`, `slug`, `scheme`, `url`, `owner` (the owner's email), `created` and `last_received`, absent until the first delivery; `create` and `rotate` answer the same object plus `secret`. Times are RFC 3339 UTC to the second. No tool and no page shows a secret again.

`headers` is a list of name and value pairs, not an object keyed by header name, because appkit's MCP schema admits only property names of letters, digits and underscores.

## Paging

`list` pages, as the suite's listing rule asks (`shape/`, Listing), on the contract of appkit's `paging` package (appkit's D25), which this document cites and never restates; dummy's `list_widgets` is the precedent it copies. `ListArgs` declares two optional members, `Page *string` named `page` and `Limit *int` named `limit`, pointers because a pointer is how appkit makes a member optional, each with a `description` tag repeating `paging.PageDescription` or `paging.LimitDescription` word for word, since a struct tag is a literal; a test compares the description `ListTools` shows with the constant. `WebhookList` keeps `webhooks` and adds `next`, `Next *string` with a tag repeating `paging.NextDescription`, written exactly when at least one webhook follows the page and left out otherwise.

The key is the slug, space-wide as before: every user lists every webhook, in ascending byte order of slug. The token is `paging.Token{Tool: "list"}` over exactly one `string`, the slug of the last webhook the page answered, so the following page is the webhooks whose slug is greater in byte order. The tool reads one window from the store (`D04-store`): it asks `List` for one more webhook than the page size, answers the page, and sets `next` only when the extra webhook came back, so neither a `next` on a last page that happens to be full nor a webhook repeated or skipped at a page's edge is possible. An absent, null or empty `page` is the first page; a null `limit` is an absent one, `paging.DefaultLimit`. A token is a position, not a snapshot: a webhook created or deleted between two calls appears or not by where its slug falls.

A call is refused before the store is read in two cases. A `limit` outside 1 to `paging.MaxLimit` is refused with the text of the error `paging.Window` returns for it. A `page` that is not empty and that the token's `Decode` refuses — one another tool issued, a mistyped one, one made by hand — is refused with `paging.BadPage`. When both offend, the `limit` is the one reported. Because the store is not read, the answer is the same while the store is unreachable: the refusal, not `store.Unreachable`, which would tell a model to try again when its arguments can never succeed. A `limit` too large for a Go `int` never reaches the tool; appkit refuses it.

An agent pages through the space by calling `list` with `{}` or `{"limit":100}`, reading `webhooks`, and, while the answer carries `next`, calling again with `{"page":<next>}` and the same `limit`, until an answer comes back without `next`. The landing page takes the same token as its `page` query parameter and shows the same window a `list` call with that `page` and no `limit` answers, and navigates by that call's `next` (`D06-pages`).

A paged call is a tool call like any other: appkit's `tool.called` carries no arguments, so a page token appears in no event and no log line, and paging adds nothing to the trail (`D07-trail`).

## The address

The tools answer `url` from webhooks' own address, which the route table puts on the request's context (`D03-serve`): the `URL` of the services file's entry `webhooks`, or, with none, the forwarded scheme and the request's `Host`. Through the gateway the request's `Host` is the gateway's backend name, so on a host and in a sandbox the services file's entry decides.

## Refusals

A slug that breaks the rule is refused by `create` with `tools.InvalidSlug`, and by `show`, `rotate` and `delete` as a webhook that does not exist, `tools.NoWebhook`; a taken slug is `tools.SlugTaken`; an id that is not a delivery id, an unknown delivery and another user's delivery are `tools.NoDelivery`; and the database is `store.Unreachable`; `list`'s `limit` and `page` are refused with appkit's sentences, before the store is read (Paging, above). A refusal is an MCP error result whose text is the copy function's answer.
