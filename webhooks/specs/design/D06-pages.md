# D06-pages

What webhooks draws as HTML: `internal/pages`, the four templates `landing`, `tools`, `about` and `notfound` and the data each receives, and the handler that answers `/`, `/tools`, `/about` and every other path that reaches it. It follows cron's pages, with sites' guest rule: the handler runs under `identity.Optional` (`D03-serve`), so it sees guests, and a guest asking for a page is sent to sign in. There is no per-webhook or per-delivery page.

## The pages

The landing page shows one window of the space's webhooks, whoever owns them, sorted by slug, each with its id, slug, scheme, the address a sender posts to, its owner's email, whether the caller owns it, and its last received time in RFC 3339 and to the minute. The landing page lists data agents add, so it pages and navigates, as the suite's listing rule asks (`shape/`, Listing; appkit's D25). `GET /` takes one optional query parameter, `page`, the very token `list` issues as `next` (`paging.Token{Tool: "list"}` over a slug, `D08-tools`), and nothing else is read from the query. A request's **page value** is its first `page` value, empty when it carries none. An empty value asks for the first window, the first `paging.DefaultLimit` webhooks in ascending byte order of slug; a value the token decodes asks for the **window** after it, the next `paging.DefaultLimit` webhooks whose slug is greater than the one the token holds; either is exactly the `webhooks` a `list` call answers when passed that `page` and no `limit` (`D08-tools`). The template's `Page` is the page value, empty on the first window, so the template knows whether it draws the first window, and its `Next` is the **next token**, the very `next` that call answers, present exactly when more follow the window. The handler learns whether more follow the way the tool does, by asking the store's `List` for one webhook more than the window (`D04-store`). The window is always `paging.DefaultLimit` webhooks at most; `limit` is the tool's alone. What the template draws from `Page` and `Next` — the navigation, its links and when it appears — is the asset's. A page value the token cannot decode — one edited by hand, one another tool issued, a word such as `bogus` — names no window, so `GET /` answers it with the not-found page, status 404, never quietly with the first window; the tool's refusal, `paging.BadPage`, stays the agents' interface. The token is the last thing the handler weighs: a guest is sent to sign in and a method other than `GET` or `HEAD` is 405 whatever the query, and the token is decoded before the store is read, so the 404 is the same while the store is unreachable. The tools page shows the six tools in registration order (`D08-tools`), each with the first line of its description. The about screen shows the service's name, the banner's `Release` and `Commit` as its version, and `Description`. Every page's footer shows the banner's `Release` then its `Commit`, the identity `main` handed `page.New` (`D01-layout-and-run-seam`). The landing page sits at the root of the banner's trail; the tools page and the about screen are one level below it, named by their path segment, `pages.ToolsLevel` and `pages.AboutLevel`, which the handler sets as the banner's trail. Any other path is the not-found page, status 404, to a signed-in user and a guest alike, with the footer only.

The banner's user is the caller's email, with auth's profile and sign-out addresses: auth's entry in the services file when it has one, and otherwise `auth.` and the request's host with a leading `webhooks.` removed, under the forwarded scheme (`https` unless `X-Forwarded-Proto` says `http`). A webhook's address is webhooks' entry's URL in the services file followed by `/in/<slug>`, or, with no such entry, the forwarded scheme and the request's `Host` followed by `/in/<slug>`.

## Guests and methods

A request to `/`, `/tools` or `/about` whose method is not `GET` or `HEAD` is `405` with `Allow: GET, HEAD`. A guest's `GET` or `HEAD` of one of them is `302` to auth's sign-in, `<auth>/?return=` and the query-escaped address of the page asked for, which is where the host's nginx sends a guest of an app with `guests = false`. The landing page answers `503` with `store.Unreachable` as plain text when the store cannot be read, for a page value it can decode.

- R-P1AZ-FA0N: webhooks' design defines the **page value** of a request `r` as the value that `r.URL.Query().Get("page")` returns, the empty string when its URL carries no `page` key; defines a page value `p` to be **decodable** when `p` is empty or when `paging.Token{Tool: "list"}.Decode(p, &k)`, `k` being a `string`, returns a nil error, and **undecodable** otherwise, `paging` being appkit's package `github.com/ikigenba/ikigenba/appkit/paging` (appkit's D25); and every requirement in webhooks' design that names a request's page value, or a page value being decodable or undecodable, MUST denote these.
- R-P2IV-T1RC: webhooks' design defines, for a decodable page value `p` (R-P1AZ-FA0N) and a moment, the **webhooks after** `p` as the webhooks of every owner the store then holds, in ascending byte order of slug, when `p` is empty, and otherwise as those of them whose slug is greater in byte order than the `string` that `paging.Token{Tool: "list"}.Decode` stores for `p`; the **window** of the store for `p` at that moment as the first `paging.DefaultLimit` of the webhooks after `p`, or all of them when they number fewer; and the **next token** of the store for `p` at that moment as `paging.Token{Tool: "list"}.Encode(s)`, `s` being the slug of the last webhook of that window, when the webhooks after `p` number more than `paging.DefaultLimit`, and as the empty string otherwise; so that the window for `p` and the next token for `p` are the webhooks and the `next`, empty when absent, that a `list` call whose `page` is `p` and that carries no `limit` answers at that moment (`D08-tools` R-0J58-BJHF, R-0LL1-32YT); and every requirement in webhooks' design that names the webhooks after a page value, or the window or the next token of the store for a page value, MUST denote these.
