# Decision 18 — Correlation at the front door: strip-then-mint on the public ingress, capture-and-overwrite on every gated location

> **⛔ EXTERNAL ORDERING (operator-sequenced, not built by any webhooks
> phase).** The suite-wide telemetry capability introduces the correlation
> header `X-Correlation-Id` and the chassis read-or-mint middleware that
> honors it. The header name, the strip-then-mint rule for ungated public
> locations, and the ULID shape are **suite constants** owned by the root
> protocol doc (`project/design/D14.md` at the repo root), defined in the leaf package
> `eventplane/correlation` and applied by appkit's middleware; webhooks uses
> them by value and owns none of them. This Decision changes
> only the committed `webhooks/etc/nginx.conf` fragment, which is inert
> configuration — it needs no library to be correct — but its *effect* is only
> observable once appkit's middleware exists (D19).

**Problem.** webhooks is the one service in the suite whose front door is open
to the outside world. Its public ingress `POST /srv/webhooks/in/<name>` is
reached directly by third parties with **no** front-door auth chain (D4/D7
tier 6). Under the suite's correlation model the chassis **trusts** an inbound
`X-Correlation-Id`, because every other caller that reaches a service is a
loopback peer inside the trust boundary. That trust is exactly wrong for this
one location: an outside caller could otherwise stamp its own delivery with an
id of its choosing and have its traffic appear inside — or forge — another
tenant's chain. Meanwhile the *gated* locations have the opposite problem: the
dashboard's introspection endpoint mints the chain id for the request and
returns it on the auth subresponse, and unless the fragment captures and
forwards it, that id dies at nginx and the service mints an unrelated second
one, severing the chain at the edge.

**Decision.** The fragment splits its locations into exactly the two suite
cases, matching the tiering that already exists (D7):

**Ungated, publicly reachable locations STRIP.** Both locations that proxy
without an `auth_request` set the header to the empty string, so nginx forwards
a header nginx itself controls and no client value survives. An empty value is
"absent" to the read-or-mint middleware, so the service mints a fresh id per
delivery:

```nginx
# tier 1 — unauth PRM bootstrap
location = /srv/webhooks/.well-known/oauth-protected-resource {
    proxy_pass http://127.0.0.1:3006/.well-known/oauth-protected-resource;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Correlation-Id "";     # public: never trust a caller-supplied id
}

# tier 6 — PUBLIC inbound ingress
location /srv/webhooks/in/ {
    client_max_body_size 2m;
    proxy_pass http://127.0.0.1:3006/in/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Correlation-Id "";     # public: the delivery ALWAYS starts a fresh chain
    proxy_http_version 1.1;
}
```

**Gated locations CAPTURE and OVERWRITE.** Each of the three tiers that runs an
`auth_request` captures the id the dashboard minted, from the auth
subresponse, into a **service-prefixed, per-tier** variable, and forwards it
with a single `proxy_set_header` — which replaces any inbound value, the same
identity-hygiene property D7 established for the owner headers:

```nginx
location = /srv/webhooks/mcp {            # bearer tier
    auth_request_set $wh_corr $upstream_http_x_correlation_id;
    proxy_set_header X-Correlation-Id $wh_corr;
    …
}
location = /srv/webhooks/ {               # session tier (landing)
    auth_request_set $wh_session_corr $upstream_http_x_correlation_id;
    proxy_set_header X-Correlation-Id $wh_session_corr;
    …
}
location /srv/webhooks/static/ {          # session tier (landing assets)
    auth_request_set $wh_static_corr $upstream_http_x_correlation_id;
    proxy_set_header X-Correlation-Id $wh_static_corr;
    …
}
```

Three distinct variable names, one per location, in webhooks' own `$wh_*`
namespace: every service fragment is included into the single apex `server`
block, so a bare `$corr` would collide across services, and a name shared
across locations would blur which tier set it. If the dashboard's subresponse
carries no such header, the variable is empty and the middleware mints —
degrading to the strip case rather than to a stale id.

`= /srv/webhooks/feed` and the `/srv/webhooks/` catch-all `return 404` without
proxying, so there is nothing to set on either; the loopback `/feed` is
reached only by suite peers directly, where the header rides the peer's own
request.

**Nothing else in the fragment changes.** Every tier's precedence, gate,
upstream, owner-header plumbing, `client_max_body_size`, and the
`@webhooks_authn_500` re-emit are untouched.

**Rejected.**
- **Letting the ingress inherit a caller-supplied id (no strip line).** This is
  the whole exposure: `webhooks` is the suite's only public ingress, so it is
  the only place the "loopback callers are trusted" premise fails. A third
  party could stamp deliveries with a victim's chain id and pollute a forensic
  reconstruction, or replay one id across thousands of deliveries to make them
  indistinguishable.
- **Rejecting a delivery that arrives carrying `X-Correlation-Id`.** Tempting
  (it can only be an attempt to inject), but it would make webhooks 4xx on
  traffic from any well-meaning provider that happens to send a header of that
  name, and the failure would be invisible to the owner. Stripping is total,
  silent, and cannot regress.
- **Stripping in the Go handler instead of the fragment.** The handler could
  clear the header, but the chassis middleware runs *before* the handler, so
  the id would already be adopted. The suite's rule places the decision at the
  trust boundary, which is nginx, and keeping it there means the same rule
  reads identically in every service's fragment.
- **One shared `$wh_corr` for all three gated tiers.** `auth_request_set`
  variables are per-request and only the matched location sets them, so it
  would work — but D7 already pays the one-variable-per-tier cost for the owner
  headers precisely so a fragment never says which tier's value it is
  forwarding. Consistency beats three saved lines.
- **Also stripping on `= /srv/webhooks/feed` and the catch-all.** Both
  `return 404` without a `proxy_pass`; a `proxy_set_header` there is dead
  configuration that would suggest a proxied path exists.

**Verification.** The fragment is configuration, not Go, and nginx is not run by
the suite — so the substrate that can falsify a wrong location is the committed
fragment text itself. These ids extend the existing content-assertion tests over
the repo-real `webhooks/etc/nginx.conf` (`cmd/webhooks/nginx_test.go`, which
already pins tiers this way under R-TTUW-5O3V / R-XK5N-0I1E / R-XLDJ-E9S3), read
from disk and asserted **per location block**, not as a whole-file substring
search — a line in the wrong block must fail. The behavioral consequence, that a
delivery's chain id is minted by the service and rides the event it publishes, is
D19's and is exercised against the real ingress path and the real outbox.

- R-EL96-NKKT — in the committed fragment, **both** ungated proxying locations —
  `= /srv/webhooks/.well-known/oauth-protected-resource` and the public ingress
  prefix `/srv/webhooks/in/` — contain `proxy_set_header X-Correlation-Id "";`
  **within their own block**, and neither contains any `auth_request` or any
  `auth_request_set` of a correlation variable. (A fragment that omits the strip
  on either, or that forwards a captured variable there, fails: a public caller's
  id would reach the service.)
- R-EMH3-1CBI — in the committed fragment, each of the three gated locations —
  `= /srv/webhooks/mcp`, `= /srv/webhooks/`, and `/srv/webhooks/static/` —
  captures the id from the auth subresponse with its **own** service-prefixed
  variable (`auth_request_set $wh_corr`, `$wh_session_corr`, `$wh_static_corr`,
  each from `$upstream_http_x_correlation_id`) and forwards it with exactly one
  matching `proxy_set_header X-Correlation-Id $<that variable>;` in the same
  block; the three variable names are distinct, and no gated block carries the
  empty-string strip. (A fragment that drops the capture on any tier, reuses one
  variable across tiers, or crosses a variable between blocks fails.)
