# Decision 19 — One inbound delivery, one chain: the minted id rides the published event

> **⛔ EXTERNAL ORDERING (operator-sequenced, not built by any webhooks
> phase).** This Decision consumes two libraries revised elsewhere and must not
> be built before both land:
> - **eventplane** — the stdlib-only leaf package `eventplane/correlation`
>   (`Header`, `New`, `Valid`, `WithContext`, `FromContext`, `Ensure`), plus
>   `correlation_id` as a first-class outbox **column** and wire **envelope
>   field**, populated at `Append` from the caller's context.
> - **appkit** — the chassis read-or-mint request middleware over that package
>   (inbound `X-Correlation-Id` trusted when `correlation.Valid`, absent or
>   malformed → mint), the telemetry recorder, and plain-HTTP request recording
>   in the middleware chain.
>
> The `Append` call therefore takes a context —
> `Append(ctx context.Context, tx *sql.Tx, ev Event) error`, replacing today's
> `Append(tx, ev)`: a **compile-caught** signature change webhooks absorbs at
> its single emission site. eventplane owns those spellings; webhooks' claim is
> about the value that reaches the column, not the name of the function that
> puts it there.

**Problem.** An inbound delivery is the outermost cause of a causal chain that
can run arbitrarily deep into the suite: a provider POSTs `/in/deploy-hook`,
webhooks publishes `webhooks:received/deploy-hook`, and prompts, scripts,
notify and anything else subscribed react — each of those in turn publishing.
Today nothing ties those hops together. An investigator holding a single
delivery has no handle that reaches the work it caused, and an investigator
holding a downstream failure has no handle that reaches back to the delivery
that started it.

**What webhooks publishes today (ground truth, not vacuous).** One emission
path: the D4 ingress handler, on every accepted `POST /in/<name>`, calls
`Service.Record(ctx, wh, contentType, body, headers)`
(`internal/webhooks/events.go`), which appends
`outbox.Event{Kind: "received", Subject: "/" + wh.Name, Payload: raw}` on the
**same transaction** as the `last_triggered_at` touch, commits, then `Ring()`s
(D5/D15). `Record` already receives the request's `context.Context` and threads
it into `BeginTx`. That parameter is the seam this Decision needs — it is
already there.

**Decision.** The delivery's chain id is **minted by the chassis and carried by
the context**, and it reaches the event with no webhooks-owned plumbing beyond
passing the context one call deeper.

1. **The id is minted, never accepted, on the public ingress.** D18's fragment
   sets `X-Correlation-Id ""` on the ungated `/srv/webhooks/in/` location, so
   the chassis middleware always mints for a delivery that arrived through the
   front door. Every accepted delivery therefore starts a chain whose id no
   outside party chose or knows in advance. On any *other* path into the
   handler — a loopback suite peer, which is inside the trust boundary — an
   inbound id is honored verbatim, per the suite rule.

2. **The id flows by context, not by argument.** `Record` passes its existing
   `ctx` to the outbox append; eventplane reads the id from that context and
   writes it into the `correlation_id` column inside the **same transaction**
   that already carries the append and the touch. No field is added to
   `webhookReceivedPayload`, no parameter is added to `Record`, and the
   ingress handler is unchanged. The durable-before-ack property (D5) is
   untouched: the correlation id is committed with the row, so an id can never
   exist on an acknowledged delivery whose event is missing, or vice versa.

3. **The published envelope carries it.** eventplane's wire envelope gains
   `correlation_id`, so every consumer that reads webhooks' `/feed` receives
   the delivery's id and continues the chain into its own work. This is what
   makes the whole webhook→consumer→consumer's-consumer fan-out reconstructible
   from the one inbound delivery, and it **supersedes** the
   payload-field convention in `project/design/D14.md` at the repo root — webhooks adds no
   correlation field of its own to the payload. The routing key
   (`webhooks:received/<hook name>`, D15) and every payload field (D15/D5) are
   unchanged.

4. **The delivery itself is recorded by the chassis, not by webhooks.** The
   inbound `POST /in/<name>` is a plain-HTTP request in the middleware chain,
   so appkit records it as kind `request` with op `POST /in/<name>`,
   capture-under-threshold params, and an outcome carrying status, elapsed, and
   the response's size + SHA-256. The **raw request body is bulk and is never
   captured literally** — a webhook body is arbitrary third-party content, is
   capped at 1 MiB (D4), and routinely carries provider secrets; it is
   represented by size + SHA-256 only, which is also what makes "where else did
   these exact bytes appear" answerable across services. The query string **is**
   captured as params by the chassis, which is safe here by construction: a
   webhook's secret rides `Authorization: Bearer` (D4) or the
   `X-Hub-Signature-256` HMAC (D17), never the URL, and the only path segment is
   the hook name — which is routing, not a credential (D3: an unguessable name
   is defense in depth, never the boundary). webhooks declares no
   recorder calls of its own and adds no `root` record: the chassis-minted
   `request` record **is** the origin of the chain, and a second origin record
   would double-count it.

5. **The `published` hop is recorded by the shared plumbing.** eventplane
   exposes an injectable observation hook at append; appkit supplies it. This
   Decision names it only to say webhooks **does not** implement it — a service
   that hand-rolled a `publish` record would produce a duplicate.

Nothing else changes: the migration set that puts the `correlation_id` column
on every lineage — the `outbox_correlation` rebuild migration, the restored
frozen body, and the name-order drift-guard shape — is owned by **D21**, which
this Decision uses and does not restate; the MCP surface is untouched, and the
four owner tools gain no field.

**Rejected.**
- **Adding `correlation_id` to `webhookReceivedPayload`.** The
  older event-payload convention for the correlation id is exactly what
  `project/design/D14.md` at the repo root's envelope field supersedes; a
  payload copy would be a second source of truth
  that can disagree with the envelope, and every consumer would have to know
  webhooks' payload shape to find the id rather than reading one envelope
  field that is identical across all fifteen apps.
- **Passing the id to `Record` as an explicit string parameter.** It reads more
  explicitly, but it makes every producer in the suite responsible for
  remembering to thread it, and a forgotten call site fails silently (an empty
  column) rather than loudly. Context population is uniform and the ctx
  parameter already exists on this path.
- **Minting the id in the ingress handler instead of taking the chassis's.**
  Two minters means two chains for the one request: the chassis's `request`
  record would carry one id and the event another, and the delivery would no
  longer resolve to the work it caused.
- **Trusting an inbound `X-Correlation-Id` on the public ingress and recording
  it as "caller-asserted".** Even flagged, an attacker-chosen id lets a third
  party inject records into another chain, which is worse than useless in a
  forensic store. D18 strips it at nginx; this Decision assumes stripped.
- **Capturing the raw body into the record's params so a forensic agent can
  read the payload.** The brief's rule is explicit and this is the case it
  exists for: bodies are bulk, arbitrary, and secret-bearing. The event's
  payload already carries the body durably for consumers with a legitimate
  need; telemetry stores the skeleton.
- **Emitting a `root` record for the delivery.** `root` is for
  **self**-originated work with no inbound request to record (a cron tick, a
  spawn). An inbound delivery has a request record, which already names the op,
  the actor context, the timing, and the outcome.

**Verification.** Real substrates throughout, in the existing `internal/e2e`
layer (real temp-file SQLite built by webhooks' **full embedded migration
set**, the real domain service over the real `eventplane/outbox`, the real
ingress handler, and the real eventplane `FeedHandler` over `httptest`). A
mock outbox could not falsify any of these — it would accept whatever it was
handed; each claim is read back out of a real SQLite column or off a real SSE
frame.

- R-L1A1-XMRN — a real accepted `POST /in/<name>` delivery whose request
  carries **no** `X-Correlation-Id` results in exactly one outbox row whose
  `correlation_id`, read back by SQL, is a **26-character Crockford-base32**
  ULID (alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ` — not RFC 4648, so a
  base32 string containing `I`, `L`, `O` or `U` fails), is **non-empty**, and
  is **equal to the id the chassis put on the request context** (observed
  through the accessor inside the handler path); a second delivery to the same
  hook yields a **different** id, so a constant or a per-process id fails.
- R-L2HY-BEIC — a delivery arriving with an inbound `X-Correlation-Id` set to a
  known valid id (the trusted loopback-peer case) results in an outbox row
  whose `correlation_id` is **that exact id, verbatim** — proving the value is
  propagated, not re-minted at append. (A wrong implementation that always
  mints fails: the stored id differs from the supplied one.)
- R-L3PU-P691 — end-to-end over webhooks' own substrate: the event appended by
  a real accepted delivery and served by the real eventplane `FeedHandler` over
  an `httptest` SSE connection frames `event: webhooks:received/<hook name>`
  (the canonical key, unchanged) with a `data:` envelope whose
  `correlation_id` field equals the delivering request's id — so a consumer
  reading the feed can continue the chain — while the envelope still carries
  `kind` and `subject` and **no** `type` key.
