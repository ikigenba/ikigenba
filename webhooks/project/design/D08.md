# Decision 8 — Test strategy, harness & dev-onboarding

## Decision.

Testing is layered so each claim is exercised against a substrate that can
falsify it. The spine `README.md` Conventions pin the commands
(`go build ./...`, `go vet ./...`, `go test ./...`); the **layer vocabulary** is
the suite contract `root project/design/D23.md`, cited and not restated here, and
D20 records which layers this tree has (hermetic and composed, both in the
default gate; no live layer). This Decision owns what remains webhooks-specific:
the substrate rules below, and the dev-harness wiring the service needs to run at
all.

**What proves what:**

| claim | substrate | layer |
|---|---|---|
| secret gen/verify/`validateName` (D3), base64 round-trip (D5) | pure Go, no DB | hermetic |
| constraints, owner scoping, durable append, registry validation (D2, D3, D5) | **real temp-file SQLite** (`db.Open`) + injected deterministic `Clock` + real `eventplane/outbox` | hermetic |
| the ingress pipeline (D4) and the MCP tools (D6) | `httptest` over a real-SQLite `Service` | hermetic |
| landing renders name+version, 404 non-root, static served, canonical markup + FOUT (D9) | `httptest` over the `internal/web` handlers; embedded template/asset bytes | hermetic |
| every D7 tier — the ingress/MCP/PRM/feed locations as well as landing/static: match form, gate (or deliberate absence), captured and forwarded headers, upstream target, prior tiers intact | the committed `etc/nginx.conf` fragment **text** (`os.ReadFile` + string assertions, crm-`nginx_test.go`-style) | hermetic |
| the service behind those locations boots, migrates, and answers `/health` from its installed layout | the real `cmd/webhooks` binary, built and run on a free loopback port | composed |

**Substrate rules:**

- **Temp-file SQLite, never `:memory:`.** The outbox startup probe opens a second
  connection to assert `BEGIN IMMEDIATE` serialization, and D5's durable-before-ack
  test reopens the file; `:memory:` supports neither. Tests use
  `t.TempDir()` files, matching the crm convention.
- **Deterministic `Clock`** is injected wherever a timestamp is asserted, so
  `created_at` / `received_at` / `last_triggered_at` are stable.
- **No mocks where a real substrate exists.** A mocked store or outbox cannot
  falsify a UNIQUE/PK constraint, durability across reopen, owner scoping, or
  Append-time registry validation — it accepts whatever it is handed. Those
  claims run against the real DB and real outbox.
- **Every nginx tier is proven by content-assertion over the committed
  fragment.** No test here drives `:8080`. For the session-gated tiers the
  reason is intrinsic as well as contractual: the landing and `/static/`
  locations are gated by the dashboard **browser session** cookie
  (`/_session-authn`), which no in-tree harness mints — so a live request
  through `:8080` could only ever observe the `401` refusal, never the routed
  page. For every tier the falsifiable substrate for the *fragment's* match
  form, gate, captured variables, and upstream target is a string assertion over
  the committed `etc/nginx.conf`, exactly as crm's `nginx_test.go` does; the
  assembled front door is the suite's manual-layer check. The **page content**
  itself (name, version, markup) is
  proven directly by the hermetic landing tests against the in-process handler,
  which needs no gate. No landing behavior rests on a stub that accepts anything.

**The front door itself is a manual-layer check.** Whether a real nginx routes a
real request through to a real dashboard introspection cannot be settled inside
`webhooks/`, and the contract files the assembled-stack check as manual-layer
rather than as any tree's gate. So no test here drives `:8080`, and none may:
a gate that needs the suite up contends for shared host ports and cannot run in
a parallel worktree. What the gate owes the D7 tiers is that a **wrong committed
fragment fails** — a gated ingress, an ungated `/mcp`, a proxied feed, a missing
captured header — and that is a content assertion over the fragment text, the
substrate that can falsify exactly that. Each D7 id names the fragment property
it excludes, not merely that a fragment file exists. Nothing here is skipped:
skipping is banned outside live-tagged files, and this tree has none.

**Required dev-harness edits** (the only legitimate repo-root touches; needed to
run the service in the local suite):

- `go.work` — add `./webhooks` to the `use (…)` block.
- `bin/start` — add `webhooks` to the build list; add a `launch_webhooks`
  (exports `WEBHOOKS_DB_PATH`, runs on `:3006`); add to the PORTS map and the
  wait-for list.
- `bin/stop` — add `webhooks` to the shutdown list.
- `nginx/run` — add `webhooks` to the fragment copy loop.

**Chassis defaults.** Backup/restore use appkit's default SQLite snapshot verbs
(no `Spec.Backup`/`Spec.Restore` override). webhooks is **producer-only**: no
`Spec.Consumes`, no `Spec.Workers`.

## Rejected.

- **Mocked `Store`/outbox for integration.** Cannot falsify the load-bearing DB
  and outbox claims; a category error per the design-mode substrate rule.
- **`:memory:` SQLite.** Defeats the reopen-based durability test and the
  single-writer startup probe.
- **Proving D7 with `nginx -t` only.** Validates syntax, not which location
  matches or which gate it carries; the content assertions pin the properties a
  syntactically valid but wrong fragment would violate.
- **An automated `:8080` front-door layer in this tree's gate.** The contract's
  own rejected alternative: slow, flaky on shared host ports, unrunnable in
  parallel worktrees, and redundant with the fragment assertions plus the
  composed smokes. The assembled-stack check is manual-layer instead.
- **Skipping a layer when the suite is down.** Would let a broken fragment ship
  "green" — and skipping is banned outright outside live-tagged files. The fix
  is to have no gate item that needs the suite up.

## Verification.

This Decision is primarily the **strategy** that proves D1–D7; its own ids cover
only the two onboarding behaviors not owned by another Decision.

- R-UELV-YLA4 — webhooks is wired into the dev harness and is actually
  launchable: the committed `bin/start` carries a `launch_webhooks` entry and
  `bin/stop` carries `webhooks`, **and** the real `cmd/webhooks` binary, built
  and run with `serve` on a free loopback port, answers `/health` with `200`.
  (Substrate: composed — a committed-file assertion for the wiring, plus the
  tree's own real binary for the launchability. Bringing the suite up to observe
  this is the suite's manual-layer check, not this gate's: a missing build or
  launch entry fails the file assertion, and a binary that cannot boot fails the
  smoke.)
- R-UFTS-CD0T — The committed `etc/manifest.env` advertises the MCP resource
  (`MCP=true`, `MOUNT=/srv/webhooks/`), which is the source the dashboard's
  service inventory / authorization-server resource list reads at boot to derive
  the webhooks MCP resource (`…/srv/webhooks/mcp`). (Substrate: hermetic — a
  scan of the real committed manifest, the file the dashboard actually reads.
  An absent or malformed key fails it. That the running dashboard then lists the
  resource is observable only with the suite up, and is the suite's
  manual-layer check.)
