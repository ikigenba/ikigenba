# Decision 21 — Outbox schema convergence: the `outbox_correlation` rebuild migration, the restored frozen body, and the migration-immutability guard

**Problem.** D19 routes the chain id into the outbox's `correlation_id` column
and expected the column to arrive as a **new** migration applied through
webhooks' runner. What the tree carries instead is an in-place edit of the
already-committed `20260712201504_outbox_routing.sql` — the violation the
suite's migration rule (and this design's own Conventions) forbids. The appkit
runner keys on version and silently skips an edited body, so the lineages have
diverged: a fresh database (every test database) has the column, while a
database that applied the original body before the edit — the deployed one —
does not. On that lineage every `outbox.Append` fails with
`no such column: correlation_id`; because `Service.Record` appends the
`received` event and touches the hook in one durable-before-ack transaction
(D5), **every inbound `POST /in/<name>` delivery fails outright** until the
schema converges. This Decision converges the lineages and adopts the suite's
mechanical guard so the violation class cannot recur.

**Decision.**

1. **The frozen body is restored.** `20260712201504_outbox_routing.sql` is
   restored to its original committed body, byte-identical — sha256
   `571384126d4486bcaa1c123c863146ee548b6a4eb9a5ebee8627514b46847ac4`
   (recoverable as `git show 5e1bd355^:` that path). The restore changes
   nothing on any database (both lineages have that version recorded as
   applied); it makes the version→body mapping truthful again.

2. **One new rebuild migration converges both lineages.** A new timestamped
   migration, minted with `bin/create-migration webhooks outbox_correlation`,
   whose entire body is a drop-and-recreate to the library constant:

   ```sql
   DROP INDEX IF EXISTS idx_outbox_created_at;
   DROP TABLE IF EXISTS outbox;
   ```

   followed by `eventplane`'s `outbox.SchemaSQL` verbatim. Drop-and-recreate
   is correct because outbox rows are disposable retention data: the migration
   window is a deploy restart, retention would trim the rows anyway, and
   consumers survive an epoch change by design. The same body lands
   identically on the deployed lineage (drops the column-less table) and on a
   fresh lineage (drops the already-revised table).

3. **The DDL drift guard resolves its target by name order.** Per the suite
   contract (`root project/design/D25.md` §4), the guard in
   `internal/db/migrations_outbox_test.go` no longer names a migration file:
   it selects the **lexically-greatest** migration filename containing
   `outbox` and asserts that file contains `outbox.SchemaSQL` verbatim
   (R-A5V4-ANGY's existing assertion, re-pointed). Its frozen-legacy assertion
   on `003_outbox.sql` is unchanged.

4. **webhooks adopts the migration-immutability contract.** Per
   `root project/design/D25.md`, the tree commits
   `internal/db/migrations.sha256` — one `<sha256-hex>  <filename>` line per
   embedded migration, sorted by filename — and a guard test that recomputes
   and compares with total set equality. The manifest line for
   `20260712201504_outbox_routing.sql` carries the restored original's hash
   above, so the manifest also pins the restoration. Adoption id:
   R-NFQ1-NA7N (`root project/design/D25.md`, [proof: per-service]).

**Rejected.**

- **`ALTER TABLE outbox ADD COLUMN` (eventplane's `AddCorrelationIDSQL`).**
  Correct on the deployed lineage but fails where the edited migration already
  created the column — SQLite has no `ADD COLUMN IF NOT EXISTS`. The rebuild
  body is lineage-independent.
- **Leaving the edited `20260712201504` body in place.** Functionally inert
  once the rebuild migration exists, but the committed history would keep
  lying about what deployed databases ran, and the immutability manifest
  would enshrine the violation's bytes as frozen truth.
- **A one-off operator `ALTER` on the live box.** Fixes one database by hand
  and leaves the tree unable to reproduce it; schema state must be derivable
  from the migration set alone.

**Verification** (real substrates: both claims run the appkit migration runner
against real temp-file SQLite databases; the lineage claim constructs the
deployed history for real, not as a fixture description).

- R-NLTJ-K4X4 — lineage convergence: a real SQLite database prepared by
  applying the **original** `20260712201504_outbox_routing.sql` body (the
  restored bytes, i.e. an outbox with **no** `correlation_id` column) with
  that version recorded as applied, then migrated with webhooks' full current
  embedded set, ends with an `outbox` table whose columns match
  `outbox.SchemaSQL` (including `correlation_id`), and a subsequent
  `outbox.Append` on it succeeds. A migration set that only edits history
  (leaving the runner to skip the version) fails this — the deployed lineage
  stays broken.
- R-NN1F-XWNT — the restoration is byte-exact: the embedded
  `20260712201504_outbox_routing.sql` hashes to sha256
  `571384126d4486bcaa1c123c863146ee548b6a4eb9a5ebee8627514b46847ac4` — the
  original committed body — so the edited variant (or any future edit) fails
  by hash, independent of the manifest file's own correctness.
