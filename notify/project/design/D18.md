# Decision 18 — Telemetry adoption, Go side: the ntfy client on the chassis's instrumented outbound client, and a correlation id that survives the async seam

> **External ordering (operator-sequenced, not built by any notify phase).**
> This Decision consumes the chassis's **instrumented outbound HTTP client**,
> obtained from the `Router` (`rt.HTTPClient(…)`) already wired to the recorder,
> and the revised **eventplane consumer**, which surfaces the event's
> correlation id into the handler's context (minting a root when a delivered
> envelope carries none). Their exact names and signatures belong to
> `appkit/project/design/` and `eventplane/project/design/`; the facts notify
> leans on are collected in `project/research/research.md`. Both must be **built
> before** this Decision's phase runs. Unlike a producer service, notify has
> **no** compile-caught `Append` change — it produces nothing.

**Problem.** Under the suite telemetry capability notify has exactly two things
to get right, and it currently gets both wrong.

1. **The ntfy POST is invisible.** `push.NewClient` constructs its own
   `&http.Client{Timeout: pushTimeout}` in-package. A privately-constructed
   client is not instrumented, so notify's *only* outbound call — the one thing
   the service exists to do — produces no `outbound` record. A forensic agent
   asking "was the owner actually pushed for this run failure, and how long did
   it take" gets nothing.
2. **The correlation id dies at the async seam.** Both consumer handlers
   deliberately return before pushing, firing the POST on a goroutine started
   from `context.Background()`:

   ```go
   go func(displayName string) {
       ctx, cancel := context.WithTimeout(context.Background(), pushTimeout)
       defer cancel()
       c.Send(ctx, "New contact", displayName)
   }(p.DisplayName)
   ```

   `context.Background()` discards every value on the handler context — including
   the chain id the consumer just put there. The `consume` record would sit on
   the crm chain while the `outbound` record it caused sat on nothing, breaking
   the chain at exactly the hop that makes it interesting.

**Decision.** Two changes, one per defect.

### 1. The ntfy client's HTTP client is injected

`push.Client` stops constructing an `http.Client` and takes one:

```go
// internal/push — the HTTP client is a dependency, not a detail.
func NewClient(baseURL, topic, token string, hc *http.Client, logger *slog.Logger) *Client
```

The composition root (`cmd/notify/main.go`) obtains it once from the Router's
instrumented outbound client seam (`rt.HTTPClient(…)`) and hands the same client
to all three construction sites — the two `Spec.Consumers` handler factories and
the `Spec.Handlers` MCP `send` client. notify needs no custom redirect or cookie
policy, so it takes the seam's plain client shape.

**The timeout stays notify's.** `PushTimeout` (10s) is a notify policy — it is
the only thing that reaps a fire-and-forget goroutine against a black-holed
connection — and it must not be replaced by a chassis default. The constant
stays in `internal/push` and is exported so the composition root can set it on
the client the seam returns.

**Propagation policy is deliberately not notify's claim.** In production
`ntfy.sh` is a third party, so the instrumented client sends it no correlation
id; notify's test substrate is a mock ntfy on `127.0.0.1`, which the same rule
classifies as a loopback peer and *does* send the header to. Both behaviors are
appkit's rule, proven in appkit. notify asserts neither direction — asserting the
loopback behavior would pin the wrong thing, and asserting the third-party
behavior is impossible against the substrate notify tests on.

### 2. The async seam carries values without carrying cancellation

Both handlers' detached goroutines derive from the handler context instead of
discarding it:

```go
go func(title, body string) {
    // Keeps the handler ctx's VALUES (the correlation id) while being immune to
    // its cancellation; PushTimeout still guarantees termination.
    ctx, cancel := context.WithTimeout(context.WithoutCancel(hctx), PushTimeout)
    defer cancel()
    c.Send(ctx, title, body)
}(title, body)
```

Nothing else about the seam changes: the handler still returns immediately, the
engine still commits the cursor without waiting, a slow or dead ntfy still never
stalls the feed, and the goroutine is still bounded by `PushTimeout`. The only
difference is that the push now runs on the chain that caused it.

The MCP `send` path needs no change of its own — the tool handler is already
called with the request context the chassis middleware put the id on, and it
calls `Publish` synchronously with that context. It is covered by a Verification
id anyway, because "the id reaches the POST" is the property that matters and it
is cheap to falsify.

**What arrives free and is deliberately not designed here.** The `consume`
record and the handler-ctx id, the `request` record for `POST /mcp`, the
`lifecycle` start/stop records, inbound read-or-mint, and the loopback-only
propagation rule all come from the rebuilt appkit and eventplane. notify neither
wires nor re-proves them.

**Rejected.**
- **Keeping `context.Background()` and re-attaching the id by hand**
  (`correlation.With(context.Background(), correlation.From(hctx))`) — same
  effect for this one value, but it silently drops every *future* value the
  chassis puts on a handler context, and it makes `internal/push` import the
  correlation package to do what `context.WithoutCancel` does for free.
- **Passing the handler context straight through** — the engine cancels it when
  the handler returns, so the push would be aborted mid-flight. The whole point
  of the seam is that the push outlives the handler.
- **Making the push synchronous so the context is naturally in scope** — reverses
  the standing decision that a slow ntfy must never stall the feed cursor.
- **A package-level instrumented client in `internal/push`** — hides the
  dependency, and the three construction sites would silently diverge again.
- **Recording notify's own `outbound` record in `push.Publish`** — that is the
  chassis's job; a service that hand-rolls records diverges from every other
  service's shape.
- **Asserting that no correlation header reaches ntfy** — not falsifiable
  against notify's loopback mock, and it is appkit's claim regardless.

**Verification.** (Real substrates: the existing mock-ntfy `httptest` server,
driven through the **assembled** MCP handler and through the **real** handler
factories, with a recording `http.RoundTripper` installed via the same wiring
path the composition root uses — so what is asserted is what ships. Each claim
observes the context *at the moment the POST is made*, and every push assertion
requires the request to actually arrive at the mock, so a test cannot pass by
merely configuring a value.)

- R-TK2Y-2LTX — a `push.Client` built the way the composition root builds it
  makes its ntfy POST through the **injected** client: the request arrives at the
  mock ntfy server *and* is observed at the recording seam, and
  `internal/push` constructs no `http.Client` of its own (a build that keeps
  `&http.Client{Timeout: pushTimeout}` in `NewClient` is never observed at the
  seam and fails); the client notify hands over carries a `Timeout` of exactly
  `push.PushTimeout`.
- R-TLAU-GDKM — the crm `Handler`, invoked with a handler context carrying a
  known correlation id and a matching `contact.created` event, causes a POST that
  reaches the mock ntfy server on a context whose `correlation.From` equals that
  exact id — **and** the POST still completes when the handler context is
  cancelled immediately after the handler returns (proving the seam kept values
  without keeping cancellation). A build using `context.Background()` yields an
  empty id and fails; a build passing the raw context through is aborted by the
  cancellation and fails.
- R-TMIQ-U5BB — the prompts `PromptsHandler` behaves identically for both matched
  kinds (`run.succeeded` and `run.failed`): the resulting POST reaches the mock
  on a context whose correlation id equals the handler context's, and survives
  cancellation of the handler context.
- R-TNQN-7X20 — an MCP `send` driven through the assembled chassis handler with
  an inbound `X-Correlation-Id` reaches the mock ntfy server on a context whose
  `correlation.From` equals that inbound value, and the tool returns its success
  `structuredContent` — proving the call completed rather than that a value was
  configured.
