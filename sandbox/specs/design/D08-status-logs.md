# D08-status-logs

`status` and `logs` look inside this worktree's sandbox. Both are reports: their product goes to stdout, a failed unit included, and they return 0 when they could produce it. Both are worktree commands, so finding the sandbox, the checks made before anything else (no current directory, not in a checkout, a worktree holding a control character, unusable name, `HOME`, a state directory holding a control character, quote, backslash or a character systemd rejects, unknown sandbox, another worktree's sandbox) and their diagnostics are D03's; their help texts, option parsing and usage errors are D02's, including how `-n`, `--lines`, `-f`, `--follow` and the app operand are read. Neither takes a lock, needs the config root, or changes any file (D03). The apps they cover are the sandbox's recorded apps in the registry, which `down` keeps, so both work whether the sandbox is up or down.

`status` asks the systemd user manager for the `ActiveState` of the nginx unit and of each recorded app's service unit, one D03 unit state run per unit, and prints a two-column table: a `UNIT`/`STATE` header, a row for nginx, then one row per app in byte order of its name. The state is printed exactly as systemd gives it. The first column is padded to its widest entry plus two spaces. The table is written only once every run has answered; if any run fails there is no report, only the shared diagnostic, under the action `systemctl --user`, for the first failing run in row order.

`logs` runs one `journalctl --user` through the streaming runner and passes its standard output through to stdout untouched, as it arrives. Without an app it covers the nginx unit and every recorded app's socket and service; with an app, only that app's socket and service. An app the sandbox does not record is a precondition that was not met, reported before journalctl runs. The pager is always disabled, the output format is pinned to journalctl's short format, and the count and follow come from the command line as D02 reads them; the count goes to journalctl without leading zeros, and D02 has already refused one above 2147483647, more than journalctl accepts, so every count journalctl is given is one it takes. A journalctl failure is the shared external-failure diagnostic under the action `journalctl --user`, its standard error quoted. Following ends when the developer interrupts sandbox: the context is cancelled, the runner kills journalctl, and a followed `logs` that ends that way succeeds.
