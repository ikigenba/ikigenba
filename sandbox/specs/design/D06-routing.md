# D06-routing

Every request to a sandbox arrives at the sandbox's own nginx, which `up` configures and starts as a user unit (D04 writes both files and starts or reloads nginx; this document owns only what the two files say). nginx listens on `127.0.0.1:<port>` in plain HTTP and routes by host name, one name per app, to each app's Unix socket. When the checkout holds an app named `auth`, it is the authenticator, as on a host: every request for another app but an `OPTIONS` request, which nginx answers itself (below), is first put to auth's `/check` as an internal subrequest, and auth's answer decides it. A checkout without `auth` has no authenticator, as a host without one has none: every app's server is ungated, no request is put to a `/check`, and no browser is sent to sign in.

The configuration is one file that includes nothing from the system's nginx; the only files it includes are the apps' own fragments (below). Every runtime path nginx would otherwise take from its compiled-in defaults under `/var` is named under `<data>/nginx`, D03's nginx directory (R-F9C7-K7Y5), instead (pid file, the five temporary directories), with the error log on stderr and no access log, since nginx would otherwise open `/var/log/nginx/access.log` and fail as an ordinary user. The file sets neither `daemon` nor `user`; how nginx runs is the unit's business. Paths under `<data>` are written nginx-quoted, so a home directory holding spaces, `%` or `$` reads back unchanged; D03 keeps quotes and backslashes out of the state root, so none of them needs escaping (the fragment include, which names the worktree, is the exception, below). Every block holds exactly the directives this document lists and nothing more, because nginx inherits a directive written at `http` or `server` level into every location below it: the cross-origin `add_header` lines (below) are written at server level for exactly that reason, but a stray `auth_request` there would reach the named locations, and `proxy_intercept_errors` would turn an app's own 401 into a sign-in. An app's fragment, included at its server's level, is inherited the same way; what it does there is the app's choice, as on a host. Server names of up to 137 characters (a 63-character app in a 63-character sandbox under `.localhost`) need a larger server-name hash bucket than nginx's default.

Every server listens on `127.0.0.1:<port>` and nowhere else. One default server answers 404 to any host the file does not name: an unknown name under the sandbox, a foreign host, and the bare sandbox name when no app is the default. Bare `localhost` is the address Google returns the browser to; when the checkout holds `auth`, its server sends every path on to the same path and query at auth's origin. Without `auth` there is no sign-in to return to, so no server names bare `localhost` and the default server answers it 404 like any host the sandbox does not serve. Each app has one server named for it, and the default app's server also carries the bare sandbox name, so the default answers there exactly as at its own name. Each app's socket is an upstream named `app_<app>`.

Every location that passes a request to an app sets the same forwarding headers: `Host` as the client sent it, port included; the client's address in `X-Real-IP` and in `X-Forwarded-For`, which nginx replaces rather than appends to, because nginx is the first proxy and a client's own value is forged; `X-Forwarded-Proto: http`; and `X-Request-Id` from nginx's own `$request_id`, replacing a client's. The identity headers, `X-User-Id` and `X-User-Email`, are set in every such location, to the empty value (which nginx does not send) wherever auth has not just answered, so a client's own never passes, on any host.

With `auth` present, every app other than `auth` is gated; without it, none is. auth's own server is never gated, and answers `/check` and `/check/open` itself with 404, each an exact-match location (an `OPTIONS` request excepted, as on every path: below), so neither is ever asked of auth from outside (nginx's core module: an exact match ends the location search; the rewrite module's `return` stops processing). A gated server puts each request to an internal location at the reserved path `/_sandbox/auth`, which proxies to auth's `/check` with the request's headers (so its `Cookie` and `Authorization`), no body, the same forwarding headers and request id, no identity headers, and the request being decided named in three headers that replace any the client sent: `X-Original-Method` from `$request_method`, which in nginx's subrequest still gives the client's method although the subrequest itself is a `GET`, `X-Original-Host` from `$host`, the request's host name lowercased and without its port, and `X-Original-URI` from `$request_uri`, the path and query exactly as the client sent them, so auth can record which request it decided; the reserved path is the only one the gate takes from an app that does not welcome guests, and a client asking for it with any method but `OPTIONS` gets 404, since an `internal` location answers only nginx's own requests, `auth_request` subrequests among them, and 404 to any other (nginx's core module). A 2xx lets the request through with auth's `X-User-Id` and `X-User-Email`; a 403 is answered 403 everywhere except `/mcp` and below; a 401 is answered by a named location, 302 to sign in at auth's origin with the requested URL in `return` everywhere except `/mcp` and below, where it is nginx's own bearer challenge, `/api` and below, where it is nginx's own bearer challenge naming no metadata (below), and git's smart HTTP paths, where it is nginx's own Basic challenge. Both bearer challenges name the MCP gateway's protected-resource metadata, `<mcp origin>/.well-known/oauth-protected-resource`, where `<mcp origin>` is the origin the app `mcp` has in this sandbox whichever app was asked and whether or not the checkout holds `mcp`, as on a host. An MCP client starts signing in again only on a 401, so under `/mcp` a 403 is answered too, by `@sandbox_invalid_token`: `401`, a bearer challenge with `error="invalid_token"` and that metadata, and the same one line as the missing-credential challenge, so an expired or revoked token heals itself. auth_request copies a `WWW-Authenticate` only from a 401, so this named location answers directly, with no `satisfy any` step; a probe of nginx 1.26.3 with a stand-in authenticator whose 403 carried its own `WWW-Authenticate` confirmed the response carries the named location's header alone, and that a 403 outside `/mcp` still reaches the client as 403. On the server of an app that welcomes guests (D05), `location /` puts the request instead to a second internal location at the reserved path `/_sandbox/auth_open`, the open check location, which holds exactly what the auth check location holds except that it proxies to auth's `/check/open`; it is the second path the gate takes from such an app, and a client asking for it with any method but `OPTIONS` gets 404 too. `/check/open` answers as `/check` does except that where `/check` would answer 401 it answers 200 with no identity headers, so on that server's general paths a client without a credential reaches the app with no user: the two `auth_request_set` variables are then empty, and `proxy_set_header` does not send a header whose value is empty (nginx's proxy module). No 401 arises there, so that `location /` holds no `error_page`, and since its server level holds none either, it inherits none (an `error_page` is inherited only when the current level has none, nginx's core module); a 403 from `/check/open` is answered 403, as nginx's auth_request module documents for a 401 or 403 subrequest answer. `/mcp`, `/api`, every path under either and the git location keep `/_sandbox/auth`, auth's `/check` and their challenges on every gated server, and every gated server, welcoming guests or not, carries all nine named locations. Every gated server carries the `/mcp` locations whatever the app's manifest says about `mcp`, as a host's does, and `/mcp/` is a `^~` prefix location so a regular-expression location an app's fragment adds can never take a path under it from the gate. nginx's auth_request copies any `WWW-Authenticate` that auth's 401 carried onto the response, and `proxy_hide_header` does not stop it; passing the 401 through a named location with `satisfy any` and `allow all` drops it (nginx clears pending `WWW-Authenticate` headers whenever an access check succeeds under `satisfy any`), and `try_files` then hands the request to the location that answers. An app's own 401 is not nginx's and passes through untouched. git's smart HTTP protocol is reserved the same way: a git client sends no credential until challenged, acts only on `401` with `WWW-Authenticate: Basic`, and cannot follow a sign-in redirect, so every gated server also carries the regular-expression location `~ /(info/refs|git-upload-pack|git-receive-pack)$`, gated and relayed like `location /`, whose 401 passes through `@sandbox_git` to `@sandbox_git_reply`: `401`, a Basic challenge for the realm `ikigenba`, and one line saying to send the token as the password. git then asks its credential helper and retries with `Authorization: Basic`, which the subrequest carries to auth's `/check` like any header. nginx matches a location against the normalized path without its query, so `/notes.git/info/refs?service=git-upload-pack` is the git location's and `/notes.git/info/refsx` is not; `=` and `^~` matches are taken before regular expressions are tried, so `/mcp` and everything under `/mcp/` stay the MCP locations', and `/api` and everything under `/api/`, `/api/notes.git/info/refs` included, the API locations'; and regular expressions are tried in order of appearance, so one an app's fragment declares, being included first, is tried first. The configuration puts a space between the pattern's closing `$` and the `{` that opens the block, since R-SWXP-LN7R, like nginx, reads a `{` directly after `$` as part of the word.

The path `/api` and every path under `/api/` are reserved across the suite for programs that call an app, a page's script or an agent, which cannot follow a sign-in redirect. Every gated server, whatever the app's manifest holds and whether or not the app welcomes guests, carries `location = /api` and `location ^~ /api/` (the API locations), gated by `/_sandbox/auth` and relayed exactly as `location /` of an app that does not welcome guests, so a request auth admits, by cookie or by token, reaches the app with the identity auth gave, and auth's `/check` sees `X-Original-URI` naming the path, `/api/widgets` say. A 401 there passes through `@sandbox_api` to `@sandbox_api_reply`, by the same `satisfy any` step as the other challenges, so any `WWW-Authenticate` auth's 401 carried is dropped: `401`, `Content-Type: text/plain`, `WWW-Authenticate: Bearer realm="ikigenba"`, which names no metadata since a program has no sign-in flow to start here, the one line `authentication required: sign in or send Authorization: Bearer <token>`, and no `Location`. A 403 is not intercepted and reaches the client as 403, as everywhere outside `/mcp`. `/apix` is `location /`'s and is sent to sign in like any other path. The reserved path says nothing about what an app serves under it. An ungated server carries no API locations: without `auth`, `/api` reaches the app through `location /` like every other path.

Cross-origin access is decided at the gate, once, for every app: apps never set CORS headers, and no app ever receives an `OPTIONS` request. A page that `sites` publishes is served at the sites origin, `http://sites.<name>.localhost:<port>`, the origin D03 gives the app `sites`, and its script calls other apps from the browser with the suite's session cookie, so that one origin is allowed, and no other; it is allowed whether or not the checkout holds `sites`, and no setting changes it. The `http` block declares six `map` blocks: the first yields the request's `Origin` only when it matches a regular expression, anchored at both ends, that spells the sites origin with every `.` escaped, and the empty string for any other value or none; the rest derive from it and from the request method the value of each other header. Every app's server, gated or not and auth's included, so at every name an app answers at, the sandbox's bare name too when an app is the default, carries at its own level seven `add_header` lines, each with `always`, and, before its fragment's `include`, `if ($request_method = OPTIONS) { return 204; }`, so nginx answers every `OPTIONS` request 204 with an empty body before any location is chosen: no `/check` subrequest is made, nothing is proxied, and neither an exact location such as auth's `location = /check` nor an internal one is reached. With the sites origin a response carries `Access-Control-Allow-Origin` naming it, never `*`, and `Access-Control-Allow-Credentials: true`; the 204 adds `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` and `Access-Control-Max-Age: 600`, and every other response adds instead `Access-Control-Expose-Headers: Mcp-Session-Id, WWW-Authenticate`. Any other origin, or none, gets no `Access-Control-` header at all, because nginx sends no header whose `add_header` value is empty, and every response of such a server carries `Vary: Origin`. The headers ride every status the server gives: the app's own answer, the 302 to sign in, a 403 from auth passed through, the 404 of an internal location and of auth's `/check` locations, and every challenge. A location with no `add_header` of its own inherits the server's, so the locations that pass to an app, the `satisfy any` steps and `@sandbox_signin_reply` carry none; the four reply locations that add `WWW-Authenticate` inherit none of the server's, so each repeats the four lines a response other than the 204 carries. The default server and the bare-localhost server serve no app and carry none of this, so there an `OPTIONS` request is answered as any other request is. No `proxy_hide_header` is added for an app's own `Access-Control-` headers: an app that set one would send it beside the gate's.

nginx documents most of this. Its headers module (ngx_http_headers_module) says `add_header` adds its header only on 200, 201, 204, 206, 301, 302, 303, 304, 307 and 308 unless `always` is given, and that `add_header` directives are inherited from the previous level if and only if none is defined on the current level. Its map module (ngx_http_map_module) says source strings are matched ignoring case, that a source starting with `~` is a case-sensitive regular expression, and that a string without a mask is chosen before any regular expression, which is how `OPTIONS true` wins over `~ true$`. Its rewrite module (ngx_http_rewrite_module) allows `if` at server level and says the module's server-level directives run in order before a location is searched for, and that `return` stops processing. A probe of nginx 1.26.3 run as the developer, with stand-in auth and apps and this document's server-level lines, maps and locations, confirmed the rest: an `OPTIONS` request with the sites origin to `/mcp`, `/api/x` and `/_sandbox/auth` of a gated server, to `/check` and any other path of auth's server, to a guests app, to an ungated server and to the default app's bare name got 204 with an empty body and exactly the six headers S4 shows, and reached neither stand-in; another app's origin, `https://sites...`, `HTTP://SITES...`, `http://Sites...`, the sites origin with a trailing `/`, with a suffix or with a prefix, and no `Origin` at all got only `Vary: Origin`, so an empty `add_header` value sends no header; a map keyed on the sites origin as a plain string matched `HTTP://SITES...`, which is why the match is a regular expression; the four headers rode the app's 200 and 500, the 302 to sign in, auth's 403 passed through on a general path, under `/api` and under a guests app's `/api`, the 404 of `/_sandbox/auth` and of auth's `/check`, auth's own 401, and the 401 of each reply location, which carried its own `WWW-Authenticate` alone, the stand-in's dropped; `/api` and `/api/x` without a credential, on a guests app too, drew `@sandbox_api_reply`, an admitted token reached the app with auth's identity, `/apix` drew the 302 and `/api/notes.git/info/refs` the API challenge; an `OPTIONS` request to the default server and to the bare-localhost server got their 404 and 302 with none of the headers; and a location an app's fragment declared with an `add_header` of its own carried none of the gate's headers, though an `OPTIONS` request to it still got the 204.

Apps may bring nginx configuration of their own, as on a host, where production's nginx includes each app's `/opt/<app>/etc/nginx.conf*` in that app's server block. Here each app's server, gated or not and auth's included, holds one `include` of the app's fragment pattern (D05), ahead of its locations, so a fragment's directives apply to every request for the app's names, the bare sandbox name too when the app is the default. The default server and the bare-localhost server include nothing. The pattern names the checkout's files by absolute path, so nginx reads them as they are on disk, and the path is the same whether nginx tests the configuration where `up` stages it or loads it once it is moved into place (D04). nginx expands the pattern with glob(3) and accepts a pattern that matches nothing, so an app without fragments gets nothing extra; a fragment nginx cannot read or parse, or a match that is a directory, fails nginx's configuration test, which is how `up` learns of it (D04). The worktree's path may hold characters nginx's parser or glob would read specially (D03 refuses only control characters and invalid UTF-8 there), so the argument escapes glob's `*`, `?`, `[` and `\` in the path with a backslash and is quoted like any other argument, and nginx matches exactly the worktree's files. sandbox itself never reads a fragment, so the configuration it writes is the same whatever fragments exist or hold.

The nginx unit (D03's R-FKBB-05ME) is a user unit, described as `sandbox <name>: nginx`, so systemd's user manager runs nginx as the developer; it sets no user, group or privilege of its own, and it has no `[Install]` section because sandbox never enables a unit. Its command is the bare name `nginx`, which systemd resolves with its own compiled-in search path (the standard `bin` and `sbin` directories), not the developer's `PATH`, so sandbox looks nothing up. nginx is told its prefix (`<data>/nginx`) and its configuration file on the command line, and `-e stderr` replaces the error log nginx would otherwise open at start-up from its compiled-in path, so nothing is written under `/var/log`; the error log of the running nginx is stderr as the configuration says. nginx keeps the stderr the user manager gave it when it forks into the background, and its workers inherit it, so what the master and every worker log lands in the unit's journal for `logs`.

nginx stands in front of every app, so the unit runs in the sandbox's core slice (D03) with the core services, whatever the apps' manifests say. The unit is `Type=forking`, its pid file D03's nginx pid file, the path the configuration's `pid` names. nginx binds its listening socket before it forks into the background and exits non-zero when the bind fails, so `systemctl --user start` succeeds only once nginx is listening and fails when the port is already held. Reload runs two commands in order: nginx's configuration test, then nginx's own reload signal. A configuration that fails the test fails `systemctl --user reload` and leaves the running nginx serving the configuration it had; one that passes makes the running nginx load the newly written file. nginx applies a reload asynchronously: the command returns once the signal is sent, and the new configuration answers a moment later. Stopping the unit uses systemd's default, terminating every process of the unit, after which nginx has removed its pid file. Paths come from the developer's `HOME` or XDG variables and may hold spaces, `%` or `$`, so the unit writes each one in the form D03 gives its position, which systemd reads back unchanged: the two paths on the command lines unit-quoted as arguments, the pid file as a unit path value.

## REQUIREMENTS

In these requirements, the configuration is the nginx configuration file `up` writes (D03's R-FAK3-XZOU); `<data>`, `<name>` and `<port>` are the sandbox's data directory (D03's R-F38P-ND8O), name and port; the apps are the apps `up` discovered, the default app the one among them whose `default` is true. Directives and their arguments are read as R-SWXP-LN7R says; whitespace, comments, the quoting and escaping of an argument (except where R-XKZH-R9GD fixes it) and the order of directives within a block are not fixed, except that R-40PK-FUYY places each app's `include` before its server's locations and R-06OI-9QVD places the `OPTIONS` `if` block before that `include`, since nginx gives none of the other directives used here a meaning by order. The sites origin is the origin of the app `sites` (D03's R-0QNY-FX6R), whether or not the apps include `sites`. A `map` block's entries are read as directives: an entry's name is its source and its single argument its value.

### File and runtime paths

- R-SWXP-LN7R: Every directive, block and argument this document fixes MUST be found in the configuration as nginx's parser reads the file: outside quotes, a `#` that starts a word begins a comment running to the end of the line; a word not starting with a quote ends at a space, tab, carriage return, newline, `;` or `{`, except a `{` directly after `$`; a word starting with `"` or `'` ends at the next same quote, which is not part of it and must be followed by a space, tab, carriage return, newline, `;` or `{`, so `""` is an empty argument; a `\` keeps the character after it from ending a word or a quoted word; within any word, `\"`, `\'` and `\\` stand for their second character, `\t`, `\r` and `\n` for a tab, carriage return and newline, and a `\` before any other character stands for itself; `;` ends a directive, `{` after a directive's words opens its block, and a `}` that starts a word closes a block.

### Servers and upstreams

- R-4WSD-ERX6: For each app, the configuration's `http` block MUST hold one `upstream` block named `app_<app>` whose only directive is `server` with the single argument `unix:` followed by that app's socket path (D03's R-FLJ7-DXD3), and the configuration MUST hold no other `upstream` block.

- R-4Y09-SJNV: Every `server` block of the configuration MUST hold exactly one `listen` directive, whose first argument is `127.0.0.1:<port>`, and the configuration MUST hold no `listen` directive outside a `server` block, so nginx accepts connections on no other address.

- R-T0LE-QYFU: Exactly one `server` block of the configuration, the default server, MUST hold exactly two directives: `listen` with exactly the arguments `127.0.0.1:<port>` and `default_server`, and `return` with exactly the argument `404`.

- R-T1TB-4Q6J: Every `listen` directive of the configuration other than the default server's MUST have exactly one argument, `127.0.0.1:<port>`.

- R-RN6J-D5LA: When one of the apps is named `auth`, the configuration MUST hold one `server` block, the bare-localhost server (the server for D03's callback origin, R-0T3R-7GO5), whose directives are exactly its `listen`, `server_name localhost`, and `return` with exactly the arguments `302` and auth's origin (D03's R-0QNY-FX6R for the app `auth`) followed by `$request_uri`.

- R-ROEF-QXBZ: When none of the apps is named `auth`, the configuration MUST hold no bare-localhost server and no `server_name` directive naming `localhost`, so the default server answers a request for bare `localhost:<port>` with 404, verified at least by a checkout holding only `dummy`.

- R-52VV-BMMN: For each app, the configuration MUST hold exactly one `server` block, that app's server, whose `server_name` names `<app>.<name>.localhost`; its `server_name` MUST also name `<name>.localhost` when the app is the default app, and MUST name nothing else.

- R-T5H0-A1EM: When no app is the default app, the configuration MUST NOT hold a `server_name` directive naming `<name>.localhost`.

- R-RLYM-ZDUL: When one of the apps is named `auth` (the authenticator), auth's server MUST be ungated and every other app's server MUST be gated; when none is, every app's server MUST be ungated, verified at least by a checkout holding only `dummy` giving dummy's server the ungated app location and no auth check location.
