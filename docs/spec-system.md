# The spec system

A high-level overview of how spec-driven development works in this repository. For the authoritative details, see the `spec` skill (`.agents/skills/spec/`).

## The idea

Designs define **what** the software must do; code and tests satisfy them. Every requirement carries a permanent id, and a **mechanical gap** between "requirements that exist" and "requirements that have tests" drives an automated build loop until the gap is closed. Nothing tracks "done" by hand — it is always derived from what is on disk.

Three properties make this work:

- **Requirements are testable.** Each one is a single assertion with a finite, deterministic, efficient test. If you cannot test it, it is not a requirement.
- **Requirements have permanent ids.** Minted once with `idgen` (form `R-XXXX-XXXX`), never edited or reused. The id is the requirement's identity for life, even when its wording changes.
- **Tests are tagged with the id they cover.** So a plain `grep` can answer "which requirements have tests?" — and that is the whole progress-tracking mechanism.

## Layout

Everything lives under `specs/`, beside a project `AGENTS.md`:

```
specs/
  design/        design documents (D<int>-<slug>.md)
  build/         loop working state — gitignored, regenerated by $seal-spec
    PLAN.md      the current gap, ordered into phases
    brief.md     the current phase
  loops/         gather.md, build.md, verify.md (the loop prompts)
  issues/        open blockers, one markdown file each
AGENTS.md        the project's toolchain, test files, gates, and commit conventions
```

## Design documents

A design document defines a feature or subsystem. It defines the **public contract between modules** — the domain language, module boundaries, names, types, operation signatures, interfaces, contract constants, dependencies, observable behavior, and any state machine — and says **nothing about how a module is implemented internally**.

The litmus test: if something could change without any other module noticing, it is an implementation detail and does not belong in the design. If changing it would break or surprise a consumer, it is part of the contract and does.

Each document is prose followed by a `## REQUIREMENTS` list, one id-tagged bullet per requirement. **The requirements are the design**: the list is the document's entire normative content, and the prose is a friendly overview that binds nothing. Anything in scope — a name, a type's fields, a signature, a constant — is contract only if a requirement states it, because the freeze, the gap, and the loop see only requirements. Structural requirements declare the public names and shapes; behavioral requirements state observable behavior, referring to those names without re-declaring them:

```
- R-NEDL-QRWM: The `uploads` module MUST export `MaxUploadBytes = 10_485_760` and `Put(name string, r io.Reader) (URL, error)`.
- R-QRWM-NEDL: `Put` MUST reject uploads larger than `MaxUploadBytes` without persisting any bytes.
```

Designs are never sealed. They change at any time; a material change is made by deleting the old requirement and minting a new id for the replacement.

## The gap

The gap is a set difference on ids:

- an id in a design but not in any test → **add** it (implement it and write the tagged test),
- an id in a test but not in any design → **remove** it (delete that test and its dead code).

Presence alone defines the gap. Whether a test is *adequate* is judged separately (by verify, and by audit).

## The three operations

- **`$open-spec`** — author a design. It interrogates you (via `grill-me`) only when it needs information it cannot discover on its own, then writes the design document.
- **`$seal-spec`** — turn designs into build instructions. It checks the gates exist, materializes the loop prompts, computes the gap, and writes the ordered `PLAN.md`.
- **`$audit-spec`** — judge whether existing tests genuinely verify their requirements. Inadequate tests are un-tagged so the loop rebuilds them; requirements that turn out to be untestable or wrongly designed become issues.

## The build loop

`$seal-spec` produces a plan; `ralph` then runs three prompts in a cycle, each in a fresh context so all state lives on disk:

- **gather** — prepares one phase (one or more requirements) at a time. It writes `brief.md` with everything the builder needs (the relevant design prose, the phase's requirements, exact file paths, dependency signatures, and the project's gate commands from `AGENTS.md`) so the builder never has to explore.
- **build** — reads only the brief and implements the code and id-tagged tests for that phase and nothing more. It takes small steps but makes whatever large internal changes good architecture requires — refactoring freely below the contract, never reshaping the seams the design owns. build does not commit.
- **verify** — adversarially checks the work: it runs the project's gates from `AGENTS.md` and judges that each test genuinely asserts its requirement. It records gaps back into the brief for the next build turn, or marks the phase complete and commits it. Every commit is therefore a verified, green phase.

gather advances phase by phase until the plan is empty, then stops the run. Because "done" is derived from the committed tests, an interrupted run resumes simply by re-sealing.

## Gates

The concrete, project-specific details live in `AGENTS.md`, not in the spec system. It declares four things: the required **toolchain**, where the **test files** live, an ordered list of **gate** commands (tests, end-to-end tests, linting, and so on) that must all pass, and the **commit conventions** verify follows. verify reads it directly; gather copies what build needs into the brief. A missing tool becomes an issue.

## Issues

`specs/issues/` is the escalation channel for friction an agent **cannot** resolve in its role — a contradictory or unsatisfiable requirement, a wrong seam, a missing tool. Each is a markdown file that must carry proof. Any open issue halts the loop until a human resolves it (by deleting the file). This is distinct from the routine feedback verify leaves in the brief, which the builder closes on its own. To keep it from becoming a lazy exit, an issue the builder files is screened by verify before it can halt anything.
