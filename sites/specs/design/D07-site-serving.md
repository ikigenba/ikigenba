# D07-site-serving

What sites answers on a site path and at the apex host: the order a site path is answered in, from the refusal of a method to the file served from the site's tree; how the rest of the path is resolved in that tree, with its index files, its directory redirect, and the dotfiles, dot segments and symlinks it never serves; the site's own `404.html`; the content type, `ETag`, `304` and `Cache-Control` of what it serves; the sign-in redirect a private site gives a guest; the `503`s a site path meets when its tree cannot be had, and the request it leaves unanswered; and what an apex request is answered with. This document is `internal/serving`: it declares `serving.Config`, `serving.Sites` and `serving.Apex` and states what each handler answers. It behaves through names other documents declare: `D04-store` declares `store.Store`, `store.Site`, `store.Public`, `store.Private`, the catalog's `BySlug`, `Apex`, `Publish` and `Delete`, and what a catalog error is; `D05-git-and-cache` declares `cache.Cache` with its `Tree`, `Dir` and `RepoDir`, and says what a tree holds and how a missing one is rebuilt; `D10-limits` declares `limits.ErrDraining` and `limits.ErrHalted`; `D06-pages` declares `pages.Set` with its `Write`, `pages.Load`, `pages.NoticeData`, the `notfound` and `unavailable` templates and what they show, and `internal/urls`' `SignIn` and `ApexBase`. Neighbouring concerns are someone else's: `D03-serve` owns the route table, the host rule that tells an apex request from a gateway one (so `Host: backend`, the mcp gateway's, never reaches `serving.Apex`), the identity gates and `telemetry.Middleware` around both handlers, sites' catalog refusal, and the rule that nothing reaches standard error while serving; `D08-visitors-and-trail` owns what a view is, the visitor cookie a view carries, and every attribute of `site.viewed` and `site.unavailable`. Tests of this design carry those documents' ids where they exercise those rules.

## The order of a site path

`serving.Sites` answers every gateway path `D03-serve` routes to it. Its first segment is a slug; the rest of the path is resolved in that site's tree. sites answers in a fixed order, and the first rule that applies gives the answer: a method other than `GET` or `HEAD` is refused with `405` before anything is read; a catalog that cannot be read is answered with sites' catalog refusal, which `D03-serve` states (R-XQFX-1YI5); a slug that names no site gets the not-found page with `Cache-Control: no-cache`; a private site sends a guest to auth's sign-in; `/<slug>` without its slash is redirected to `/<slug>/`; a site with no published commit gets the not-found page; and only then is the tree asked for and the rest of the path resolved in it. A guest of a private site therefore learns nothing but that it asks for a sign-in, and no rule before the tree starts a rebuild.

## Resolving a path in a tree

The tree is the directory `cache.Tree` returns for the site's id, repository and published commit (`D05-git-and-cache`), and the path is resolved in it and nowhere else. The rest of the URL path is split at every `/`, never cleaned and never tidied: a segment that is empty before the last one, or that begins with `.` (which takes in `.`, `..` and every dotfile), makes the path name nothing, even where tidying would land on a real file. Each segment but the last must be a directory that is not a symlink; a last segment that is empty (the path ends in `/`) names that directory's `index.html`; a last segment that is a regular file is served; one that is a directory is redirected to add the `/`, its query kept; and anything else — absent, a symlink wherever it points, or any other kind of entry — is a missing file. The URL path is Go's decoded `URL.Path`, so `%2e%2e` is `..` and is refused like it. A missing file is answered `404` with the tree's own root `404.html` when that is a regular file, and with sites' not-found page otherwise.

## What a served file carries

A served file's body is the file's bytes as the tree holds them. Its `Content-Type` comes from sites' own extension table, below, never from the host's MIME files; its `Content-Length` is its size; its `ETag` is the published commit's sha in double quotes, the same for every file of the site, so a republish changes every tag at once; and it carries no `Last-Modified`. A request whose `If-None-Match` matches that tag is answered `304` instead. Only a served file and its `304` carry an `ETag`.

## Views, the cookie and the trail

Every answer about a known site from the redirect to `/<slug>/` on — a `200`, a `301`, a `304`, a `404` within the site or for an unpublished one, and every `503` but the catalog refusal — is a view (`D08-visitors-and-trail`), which sets the visitor cookie when the request carried no well-formed one and records `site.viewed`, and, for a failed rebuild, `site.unavailable` after it. What this design adds to every view is its `Cache-Control`: `public, no-cache` for a public site and `private, no-cache` for a private one, which only a user reaches. The `405`, the catalog `503`, the unknown slug's `404` with its bare `no-cache`, and the guest's sign-in `302` are not views.

## When the tree cannot be had

When `cache.Tree` fails, the request is served from nowhere else. While sites is draining (`D10-limits`), a rebuild that would start is refused with `limits.ErrDraining`, and the request is answered at once with the plain-text line `serving.Stopping` and `Retry-After: 30`. Any other failure — the repository gone, the commit gone, the tree too large, git too slow or failing (`D05-git-and-cache` sorts them into reasons) — is answered with the unavailable page and `Retry-After: 60`. Both carry the site's `Cache-Control` and no `ETag`, and the next request tries again. A request whose context ends while it waits on the rebuild (the visitor left, or `D03-serve` cut it off at the drain deadline), and one whose rebuild `Limits.Halt` ended, get no answer at all: nothing is written and nothing is recorded, so neither is a view.

## The apex

`D03-serve` hands every apex request to `serving.Apex`, whatever its method and path, `/`, `/about` and `/mcp` included. An apex answer reads the catalog's apex setting and the apex site's slug and nothing else — not the site's visibility, its commit, its tree, nor who asks — so it never refuses a method and is never a view. With an apex set it is a `302` to `urls.ApexBase` followed by `/<slug>/` and the request's path without its leading `/`, query kept; with none it is the not-found page with `Cache-Control: no-cache`; and when the catalog cannot be read, sites' catalog refusal, which `D03-serve` states for every apex request (R-XQFX-1YI5).

## Decisions

- The site record is read from the catalog afresh for every request, so a publish, an update or a delete takes effect on the next request.
- Redirect `Location`s are relative for the slug and directory redirects and absolute for the apex; the path part of the directory and apex redirects is Go's `URL.EscapedPath()`, so a path's percent-encoding survives the redirect.
- An empty segment before the last one (`/blog//x`) names nothing, as a dot segment does.
- The tree's `404.html` is used only when it is a regular file at the tree's root; a symlink or directory of that name gives sites' not-found page.
- The content-type extension is the last segment's suffix from its final `.`, compared in ASCII lower case; the table is fixed in sites, so a test's host decides nothing.
- `If-None-Match` is read from every field line the request carries; `*` matches as an element of the list as well as alone.
- The `304` carries neither `Content-Type` nor `Content-Length`.
- No requirement fixes a `Cache-Control` on the sign-in `302` or the apex `302`, so it is left unfixed.
- A request whose context ends while it waits on a rebuild, or whose rebuild was halted, gets no answer and records nothing. The unavailable page answers a rebuild that fails and the drain line only a rebuild refused while stopping; a request cut off at the drain deadline (whose context `D03-serve` ends) records no `site.*` event. A visitor who left and a request cut off cannot be told apart by the handler, and nobody is there to read an answer, so both are treated alike: no answer, no view, no event.

## Consumer tasks

`web.Handler` (`D03-serve`) builds one `serving.Config` from its own `web.Config` — `Banner`, `ServicesPath`, `Store`, `Cache`, `Telemetry` and `Rand` as given, and `Pages` the set `pages.Load()` returned — and calls `serving.Sites(c)` and `serving.Apex(c)` once each. For a request whose host is a gateway host and whose path no other route takes, it calls the `Sites` handler under `identity.Optional`; for an apex request it calls the `Apex` handler under `identity.Optional`; both sit under `telemetry.Middleware` over `cfg.Telemetry`, so a view's `site.viewed` lies between the request's `request.started` and `request.finished`.

A visitor's `GET /blog/style.css` reaches the `Sites` handler, which reads the caller from `identity.FromContext`, finds `blog` with `cfg.Store.BySlug(ctx, "blog")`, sees a public published site, asks `cfg.Cache.Tree(ctx, site.ID, site.Repo, site.Commit)` for its tree, resolves `style.css` in it, and answers `200` with `text/css; charset=utf-8`, the file's length, `ETag` of the commit and `Cache-Control: public, no-cache`; having found no `visitor.FromRequest(r)` id it mints one with `visitor.Mint(cfg.Rand)`, adds `Set-Cookie: visitor.Cookie(id, visitor.Secure(r))`, and records `site.viewed` through `cfg.Telemetry` as `D08-visitors-and-trail` states. A missing page writes the tree's `404.html`, or calls `cfg.Pages.Write(w, r, 404, "notfound", pages.NoticeData{Banner: cfg.Banner(page.User{})})`; a guest at a private site is sent to `urls.SignIn(r)`; and a failed `Tree` is written with `cfg.Pages.Write(w, r, 503, "unavailable", ...)` with `Retry-After: 60` and the site's `Cache-Control`. An apex `GET /hello?x=1` reaches the `Apex` handler, which calls `cfg.Store.Apex(ctx)` and answers `302` to `urls.ApexBase(r, cfg.ServicesPath) + "/blog/hello?x=1"`.

A test makes a temporary directory, finds the real git with `exec.LookPath` and calls `git.Find` with a `PATH` holding its directory and an `environ` returning the test's own git environment; builds `l := limits.New(settings.Defaults(), limits.Clock{After: after})` with an `after` whose channels it holds; opens the catalog with `db.Open(ctx, db.Config{Path: <temp>/sites.db, Migrations: sites.Migrations()})` and builds `store.New(d, store.Config{Now: now, Rand: rnd})` over it and creates and publishes sites in it with `Create` and `Publish`; and opens `cache.Open(cache.Config{Root: <temp>/cache/sites, Repos: <temp>/repos, Git: g, Limits: l})` over bare repository fixtures it made, shaped as repos lays one out, holding the files, directories, dotfiles and symlinks a test needs, unpacking each published commit with `Unpack`. It builds `serving.Config` with a `Banner` function of its own, the set `pages.Load()` returns, a `telemetry.Writer` from `telemetry.New` over a `telemetry.Capture`, and its own `Rand`; wraps `serving.Sites(cfg)` or `serving.Apex(cfg)` in `identity.Optional` (and `telemetry.Middleware` where it checks event order); sends requests to an `httptest.ResponseRecorder`, setting `X-User-Id`, `Host`, `X-Forwarded-Proto`, `Cookie`, `Referer` and `If-None-Match` as nginx and a browser would; compares page bodies with what `cfg.Pages.Write` writes for the same data; and reads events with `Flush` and `Capture.Events`. It drives the drain with `l.Drain()`, a catalog failure with `SetFailing(true)` on the store's handle, a failed rebuild by removing the tree and the repository directory, and a visitor who leaves as follows. Its `after` function, on the first call made after the test arms it (once every setup `Unpack` has returned), signals the test and then blocks until the test releases it, and on every call returns a channel the test holds and never fires; the cache is opened with a `cache.Config.Joined` hook that signals the test. The test starts the rebuild of a published site's missing tree with a direct `Tree` call on that cache, in a goroutine of its own, and waits for the `after` signal, so that rebuild is held before its first git starts and any later `Tree` call for that tree joins it (`D05-git-and-cache` R-CVGL-I2A4). It serves a `GET` of a file of that site, under a context it can cancel, in another goroutine of its own, so the test goroutine never blocks in the handler; waits for `Joined`; cancels that context; waits for the handler to return and checks, on a `http.ResponseWriter` of its own that records every call, that nothing was written; and only then releases `after` and waits for the direct `Tree` call to return. Every wait has a deadline that fails the test, and nothing sleeps. For the requirements that a request starts no git run, it checks that its `after` was not called while the request was answered, a call `D05-git-and-cache` (R-7PSE-YBDY) and `D10-limits` (R-ZWZU-8C1G) put before every git process the cache starts; `serving.Config` holds no `git.Git`, so the cache is the only git a handler reaches, and no test changes `PATH` for it. The host rule and the routing to both handlers are `D03-serve`'s tests.
