# D10-limits

sites runs the host's `git` for anyone who publishes or visits a site, so it bounds that work in two ways: how large a site's tree may be (`SITE_MAX_BYTES`) and how long one git run may take (`OPERATION_SECONDS`). This document is `internal/limits` — the `Limits` value that carries both settings for one run, the per-git-run deadline measured on an injected clock, the stop's two steps (draining, after which no new rebuild starts, and halting, which ends every git run still going), and the four sentinels the other packages report those limits with — together with how a serving `cli.Run` applies the settings it read. It declares every exported name of `internal/limits` and states what each does. The settings themselves, their names, defaults, parsing, refusal text and the order they are read in are `D01-layout-and-run-seam`'s (`settings.Settings`, `settings.Defaults`, `settings.Read`, `settings.Error`), as is the run seam (`cli.Process`, `cli.Run`); the manifest's `[env]` defaults are `D02-cli`'s; when `Run` calls `Drain` and `Halt` around its drain deadline is `D03-serve`'s; measuring a tree against `SITE_MAX_BYTES`, timing each git run with `Operation`, refusing a new rebuild while draining, and the `reason` values `too_large` and `timed_out` are `D05-git-and-cache`'s; the drain-time `503` is `D07-site-serving`'s; and the tool refusals that quote a limit, `site exceeds <n> bytes` and `git took longer than <n> seconds`, are `D09-tools`'s.

## The two limits

Both are positive whole numbers, read once when sites starts (`D01-layout-and-run-seam`), so an operator who changes one restarts sites for it to apply. `limits.New` takes the `settings.Settings` that `Run` read and a `Clock`, and the `Limits` it returns holds those settings unchanged for the life of the run: `Settings` answers them, and every consumer reads its numbers there. Nothing in the catalog or under `cache/` remembers a limit, so a run never applies another run's value.

`SITE_MAX_BYTES`, by default 268435456, is the most a site's tree may hold, and `Settings().SiteMaxBytes` is that number for the run; this document states only the value. What is measured (the sum of the sizes of the files of the commit as `git archive` emits them), that the limit is inclusive, that an unpack stops as soon as the sum passes it and leaves nothing of itself behind, that it is reported as `ErrTooLarge`, and that a tree already whole in the cache is not measured again are `D05-git-and-cache`'s requirements. sites sets no limit of its own on the number of files in a tree, the depth of its directories, or the length of its paths.

`OPERATION_SECONDS`, by default 600, is the longest one git run may take: resolving a ref, reading a repository's `ikigenba.owner`, checking a commit, or unpacking a tree, each timed on its own. A git run is one git process sites attempts to start: `D05-git-and-cache` calls `Operation` once for each, just before starting that git, runs it under the context `Operation` returns, and when that context ends because the deadline passed, kills git and reports the run as `ErrTimedOut`.

## Operations and the deadline

`Operation(ctx)` returns the context one git run runs under and the function that releases it. That context ends at the first of four things: `ctx` ends (a caller went away), the deadline passes (the channel `After` returned for `OPERATION_SECONDS` delivers), the run is halted, or the caller releases it. `context.Cause` of the ended context tells which: `ctx`'s own cause, `ErrTimedOut`, `ErrHalted`, or `context.Canceled`. Whichever comes first decides the cause, and nothing later changes it. Each git run of a rebuild shared by several requests runs under its own `Operation(context.Background())` (`D05-git-and-cache`), so only that run's deadline or a halt ends it, never one requester leaving.

## Draining and halting

A stop has two moments (`D03-serve`). At the signal `Run` calls `Drain`: from then on `Draining` answers true, and `D05-git-and-cache` starts no new rebuild, answering `ErrDraining` instead, which `D07-site-serving` turns into the drain-time `503`. Draining ends nothing and refuses no `Operation`: a publish running at the signal, and a rebuild already running, go on and finish within the drain if they can. When requests are still in progress at the drain deadline, `Run` calls `Halt` (`D03-serve`): every operation context still open ends at once with `ErrHalted`, so its git is killed, and every `Operation` after that returns a context already ended, so no git starts afterwards. No git sites started outlives the run.

## Sync points

Tests drive the deadline without sleeping, through the `Clock` they hand `limits.New` (and, for a whole run, through `cli.Process.After`), so one moment is contract. `Operation` calls `After` exactly once, with `OPERATION_SECONDS` as a `time.Duration`, before it returns, and so before the git it bounds can start; no other call of the package calls `After`. `Clock` carries `After` alone, since no limit is measured on a reading of the time. A nil `After` means `time.After`; that meaning is the declaration's gloss and is accepted as untestable, since proving it needs the real clock, so tests hand a non-nil `After`, and `cmd/sites` sets `Process.After` to `time.After` explicitly (`D01-layout-and-run-seam`). A test therefore learns that a git run is about to start when its fake `After` is asked for `OPERATION_SECONDS`, and fires the channel when it chooses; a channel on which a value is ready at any time after that call and before git has ended counts as the deadline passing, git started or not, so a test may return a channel with a value already ready and know the run fails as one that took too long. `Halt` ends every open operation context before it returns, so a test that calls it can then wait for git to be gone.

A number of seconds turned into a `time.Duration` saturates at the longest duration, so every setting `settings.Read` accepts is usable.

## Decisions

- `internal/limits` owns all four sentinels: `ErrTooLarge` and `ErrTimedOut` because they name these two limits, `ErrDraining` and `ErrHalted` because draining and halting live here; `D05-git-and-cache` returns them and `D09-tools` and `D07-site-serving` read them with `errors.Is`.
- The deadline is a context cause, not a timer the consumer selects on, so `D05-git-and-cache` bounds a git run by handing git the context and learns why it ended from `context.Cause`.
- `Drain` and `Halt` are separate: draining refuses only new rebuilds, so work accepted before the signal still finishes within the drain, and halting is the drain deadline's alone.
- sites sets no limit of its own on file count, depth or path length: the stories bound a tree by its bytes and its git runs by `OPERATION_SECONDS` only.
- The sentinels' `Error` texts are not contract; every text a user sees that quotes a limit is built by `D09-tools` from `Settings`.

## Consumer tasks

`Run` (`D03-serve`) calls `l := limits.New(s, limits.Clock{After: p.After})` with the settings `settings.Read` returned, and hands `l` to `cache.Config.Limits`, `web.Config.Limits` and on to `tools.Config.Limits`; where in the start this falls, before `cache.Open`, is `D03-serve`'s alone to state. On the signal it calls `l.Drain()`; when requests are still in progress at the drain deadline it calls `l.Halt()` (`D03-serve`).

The cache (`D05-git-and-cache`): for each git run, `op, cancel := l.Operation(ctx)`, `defer cancel()`, then runs git under `op`; once git has exited, whether it failed or not, it checks `context.Cause(op)` and, when `errors.Is(context.Cause(op), limits.ErrTimedOut)`, returns `limits.ErrTimedOut`. While unpacking it adds each file's size and, once the sum exceeds `l.Settings().SiteMaxBytes`, ends the unpack and returns `limits.ErrTooLarge`. `Tree`, about to start a rebuild, returns `limits.ErrDraining` when `l.Draining()`, and otherwise runs the shared rebuild with each of its git runs under its own `l.Operation(context.Background())`.

The tools (`D09-tools`): a `publish` whose `Unpack` returns an error matching `limits.ErrTooLarge` answers `site exceeds <n> bytes` with `n` = `l.Settings().SiteMaxBytes`, and one matching `limits.ErrTimedOut` answers `git took longer than <n> seconds` with `n` = `l.Settings().OperationSeconds`. Serving (`D07-site-serving`): a `Tree` error matching `limits.ErrDraining` is answered with the drain-time `503`.

A test of the limits builds `limits.New(settings.Defaults(), limits.Clock{After: after})` whose `after` records each requested duration and returns a channel the test holds; it calls `op, cancel := l.Operation(context.Background())`, reads that `after` was asked once for 600 seconds, fires the channel, waits on `op.Done()` with a deadline that fails the test, and asserts `errors.Is(context.Cause(op), limits.ErrTimedOut)`; it calls `l.Drain()` and reads `l.Draining()`; it opens a second operation, calls `l.Halt()`, and asserts the second is done with `ErrHalted` as soon as `Halt` returns. A test of a whole run hands `cli.Run` a `Process` whose `LookupEnv` answers `SITE_MAX_BYTES` `1048576` and `OPERATION_SECONDS` `60` and whose `After` records its durations and returns a channel with a value already ready, then publishes over appkit's `mcp.Client` and reads the refusals `D09-tools` states.

- R-NL8P-H9HD: The `internal/limits` package MUST export the method `func (l *Limits) Operation(ctx context.Context) (context.Context, context.CancelFunc)`.
- R-NMGL-V182: The `internal/limits` package MUST export the methods `func (l *Limits) Drain()`, `func (l *Limits) Draining() bool`, and `func (l *Limits) Halt()`.
- R-AQWB-LEGR: The `internal/limits` package MUST export variables `ErrTooLarge`, `ErrTimedOut`, `ErrDraining` and `ErrHalted`, each of type `error`, each non-nil and no one of them matched by `errors.Is` against another.
- R-X6MD-VC6F: For every `settings.Settings` whose `DrainSeconds`, `SiteMaxBytes` and `OperationSeconds` are each between 1 and `math.MaxInt64` inclusive, whatever its `ReposDir`, and for every `Clock`, `limits.New` MUST return a non-nil `*Limits` without panicking, and every call of that `Limits`' `Settings` MUST return a value equal to the `Settings` `New` was given, whatever other methods have been called on it.
- R-Y8J7-KPH5: When the `Clock` given to `limits.New` has a non-nil `After`, `l.Clock().After(d)` MUST call that `After` once with `d` and return the channel it returned; and whatever `Clock` `New` was given, the `After` field of the `Clock` that `l.Clock()` returns MUST NOT be nil.
- R-ZWZU-8C1G: When `Halt` has not been called on `l`, every `l.Operation(ctx)` call MUST, before it returns, call `l.Clock().After` exactly once, with `OperationSeconds` seconds as a `time.Duration`, or `time.Duration(math.MaxInt64)` when that number of nanoseconds exceeds `math.MaxInt64`, whatever the state of `ctx` and whether `Drain` has been called.

- R-TO8G-RL90: The context an `l.Operation(ctx)` call returns MUST NOT be done before the first of these: `ctx` is done, a value is ready to receive on the channel its `After` call returned (a value already ready when `Operation` returns counting from then), `l.Halt` is called (or had been called before), or the `context.CancelFunc` returned with it is called; once it is done, every later `context.Cause` of it MUST return the same error, whichever of the others happens afterwards.
