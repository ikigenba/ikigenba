# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail sites records of itself from its start to its stop, and the rules its one handler keeps on every request — which host a request is at, which route its path falls to, which identity gate wraps that route, the request's id and its two events, the answer when the catalog cannot be read, and how a listener is served and drained. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, the display string of the identity `main` read, `cli.Run`, `settings.Read`, `settings.Settings` and `settings.Error`, and it fixes where the catalog, the trees root and `REPOS_DIR` resolve under `Process.Dir`. `D02-cli` declares the exit codes `cli.ExitSuccess`, `cli.ExitServerFailed` and `cli.ExitUsage`. `D01-layout-and-run-seam` also declares the root package's `Migrations`, and names appkit's `db` package, whose `db.Open`, `DB.Close` and `DB.SetFailing` this design uses as appkit's D15 and D16 state them; `D04-store` declares `store.New`, `store.Config` and `store.Unreachable`; `D05-git-and-cache` declares `git.Find`, `cache.Open` and `cache.Config`; `D10-limits` declares `limits.New`, `limits.Clock`, `(*limits.Limits).Drain` and `(*limits.Limits).Halt`; `D06-pages` declares `pages.ServiceName`, `pages.Load`, `pages.Config`, `pages.Handler`, `urls.SitesURL`, `urls.NewContext` and `urls.FromContext`; `D07-site-serving` declares `serving.Config`, `serving.Sites` and `serving.Apex`; `D09-tools` declares `tools.Config` and `tools.Register`. appkit's `telemetry` package (its contract, writer, wire and HTTP middleware designs) owns the events, the writer and the request middleware this design wires; its `identity` package the two gates, `Require` and `Optional`; its `page` package the shared files under `/_appkit/`; its `mcp` package the endpoint. `D02-cli` decides that an empty `Args` means serve, and what a command does. This document declares `server.Serve`, `server.DrainError`, `web.Config` and `web.Handler`, and says in what order `Run` checks its start and which refusal touches what, how it takes the socket, opens the catalog and the trees root, builds the writer, the limits and the handler, tells systemd it is ready, serves and stops, in these shapes: a clean start, a first start, a start with no services file or no telemetry, a stop that drains, a stop whose drain runs out, a restart, the ways a start is refused, and a start over a catalog a newer sites has upgraded, which warns and serves. What a page answers is `D06-pages`; what a site path and the apex host answer, the drain refusal and the visitor cookie included, is `D07-site-serving` and `D08-visitors-and-trail`; what `/mcp`'s tools answer is `D09-tools`; what the catalog creates and holds is `D04-store`; how git runs and what the trees root holds is `D05-git-and-cache`; what the limits do is `D10-limits`.

## The terms sites serves on

sites serves on the platform's common terms, the same as every app. It serves only on a listening socket it inherits and never opens one of its own; on a host that is `/run/ikigenba/sites.sock`, held by `ikigenba-sites.socket` beside the `Type=notify` `ikigenba-sites.service` (`D11-on-a-space` records the host's part). A deploy restarts the service alone, so the socket and the connections queued on it outlive every restart; sites' part is to finish what it accepted and leave the socket where systemd put it.

sites takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment once it has taken the socket, so no git it starts inherits a claim meant for it. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket `NOTIFY_SOCKET` names, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace.

The suite is a closed system: sites trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway calling it at its socket to have forwarded them. Because the manifest declares `guests = true` (`D02-cli`), a request outside `/mcp` may arrive with no `X-User-Id` (nginx keeps `/api` and the paths under it behind the strict check too, so no such request reaches sites without one): that is a guest, whatever `X-User-Email` it carries. Every request has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it from the writer's random source, which is `Process.Rand`. `Process.Rand` is also where the catalog draws site ids and unlisted slugs and where the site routes draw visitor ids, so `Run` hands the writer, the store and the handler one reader that never lets two reads of `Process.Rand` overlap.

sites' standard error holds only trouble: a start it refuses, appkit's one warning over a catalog a newer sites upgraded, a socket it cannot take, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off, and the lines appkit's writer writes for an event it could not deliver. A request answered with any status — a 404, the missing-identity 500, a site's 503, the catalog's 503 — a tool refused and a git run that failed or ran too long are handled failures, recorded in the trail or a tool's result and earning no line. So the handler has no stream at all, and while telemetry takes every event a running sites writes nothing to either stream. What git writes to its own standard error is `D05-git-and-cache`'s and never reaches sites' standard error.

## Checking the start

With `Args` empty, `Run` checks, in this order: its four settings, through `settings.Read` over `LookupEnv` (`D01-layout-and-run-seam` fixes the spelling, the defaults, the order and the text of the refusal); then whether a socket was passed in; then whether git is on the `PATH`; then it opens the catalog; then it makes the trees root. Each refusal is the first one that applies, so a bad setting is reported whether or not a socket was passed in or git is installed, and a missing socket whether or not git is installed.

A bad setting is the caller's mistake: `sites: `, the `Error` text of the `*settings.Error`, a newline, exit 2. A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one; anything else is no socket passed in, and a count above one is a unit sites will not guess about. Both are usage errors, exit 2, with the detail line saying how to run sites. None of these refusals takes the descriptor, unsets a variable, looks for git, creates or opens anything under `Process.Dir`, serves, tells systemd anything, or records an event.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv` and takes descriptor 3 as its listener: through `Process.Inherit` when a test supplies one, otherwise with `net.FileListener` over the real descriptor, which, as Go's `net` documentation of `FileListener` and `UnixListener.SetUnlinkOnClose` states, leaves the socket's path in place when the listener is closed. A descriptor that cannot be made into a listener is trouble on the host: `sites: ` and the error, exit 1.

Then git. `Run` hands `git.Find` the value `LookupEnv` gives for `PATH` (empty when unset) and `Process.Environ`; when it finds none (`D05-git-and-cache` states how it looks), that is a host missing a dependency opsctl provisions: `sites: git not found on PATH`, exit 1, before the catalog is opened, so a host without git keeps its state exactly as it was — an absent `state/` is still absent. Finding git runs no git.

## The catalog, the trees root and readiness

With git found, `Run` opens the catalog with appkit's `db.Open` at `state/sites.db` under `Process.Dir`, with the migrations `sites.Migrations()`, the clock `Process.Now`, the service `pages.ServiceName` and `Process.Stderr` as the writer for appkit's warning, and builds the store over that handle with `store.New`, `Process.Now` and the guarded `Process.Rand`. On a first start `db.Open` creates `state/` and the database and applies every migration, so the catalog names no site and no apex; on a later start it applies only the migrations the catalog has not had, so a catalog an earlier sites kept is brought up to date and keeps every site and the apex (`D04-store`); sites never rebuilds a catalog from anywhere. Every failure of `db.Open` is `sites: cannot open database state/sites.db: ` and the error's text, each newline in it replaced by a space, whether the directory could not be made or the file is not a database it can open; the path is always this relative spelling, whatever `Process.Dir` is. Then `Run` builds the limits, `limits.New` over the settings it read and the clock `limits.Clock{After: Process.After}`, and opens the trees root with `cache.Open` over `cache/sites` under `Process.Dir`, the resolved `REPOS_DIR`, the git it found and those limits; `D05-git-and-cache` states that `Open` makes `cache/` and `cache/sites/` when absent, and its failure is `sites: cannot create directory cache/sites: ` and the error's text, whichever of `cache` and `cache/sites` is in the way. Either refusal is exit 1, before anything is served, before systemd is told anything and before any event is recorded; the catalog refusal leaves no `cache/` behind, and the trees-root refusal leaves the catalog `db.Open` created or brought up to date.

A catalog a newer sites has upgraded, as after a deploy rolled back, records a migration this sites does not carry. It is not refused: data never rolls back, so older code runs on newer data. appkit's `db.Open` applies nothing to it, not even a migration sites carries that it lacks, and writes one warning line, beginning with the service name it was given and naming the lowest version this sites does not carry, to the writer it was given, which is `Process.Stderr`; under systemd that line reaches the journal. It is written before `READY=1`, it is the whole warning, and the trail records nothing about it. Then the start goes on exactly as over any catalog: the trees root, the writer, `READY=1`, `service.started`, and every site and the apex the catalog holds served as ever. sites states nothing about the line's wording: a test compares what `Run` wrote with what its own `db.Open` call, given the same service name and a buffer, writes over the same database, and that the line begins `sites: ` is what shows `Run` handed appkit sites' name. `db status` over the same catalog lists every version and exits 0 (`D02-cli`).

That is the whole of the start's checking: `Run` does not look in `REPOS_DIR`, at any repository, at any published commit or at any tree under `cache/sites/`, runs no git, and unpacks, removes and rewrites no tree. A site whose tree is missing is rebuilt by the first request that needs it (`D05-git-and-cache`, `D07-site-serving`). A test sees "runs no git" without relying on where git lives: it puts `GIT_TRACE2_EVENT`, naming a file in its temporary directory, into `Process.Environ`, which every git `Run` starts receives; git writes its trace2 events there whenever it runs (git's `api-trace2` documentation), so the file is still absent once `READY=1` has arrived.

A signal that arrives before `Run` has begun to report ready — during the catalog's opening or before `Run` was even called — is a stop, not a failure: exit 0 (`D02-cli` keeps 1 for a server that failed), with no `READY=1`, no connection accepted, and neither `service.started` nor `service.stopping`. The refusals before the catalog still come first, whatever the context holds.

Then `Run` builds the run's writer with appkit's `telemetry.New`, whose `Service` is `pages.ServiceName`, whose `Version` is `Process.Version`, the display string of the identity `main` read (`D01-layout-and-run-seam`), and whose sink, standard error, clock, pause and random source are `Process.Sink`, `Process.Stderr`, `Process.Now`, `Process.Sleep` and the guarded `Process.Rand`; calls `Process.MCP` once with that writer; and builds the handler with `web.Handler` over `Process.Banner`, that server, the value `LookupEnv` gave for `IKIGENBA_SERVICES` (read once, here), the store, the trees root, the limits, the writer and the guarded `Process.Rand`. Nothing about `IKIGENBA_SERVICES` or the file it names can stop a start: unset, empty, or naming a file that is missing, unreadable or malformed, sites starts, serves and says nothing about it; its banner loses sites' icon, the link to home and the tools page's row in its menu, its endpoint the instructions, its site URLs the `sites` entry, and its events, with no `telemetry` entry to find, go to standard error, all as the owning designs state.

The socket has been listening since systemd made it, so ready is true before the first `Accept`, and sending it first means a failure to send is reported before anything was served: one line beginning `sites: ` that names the notification socket's address, exit 1. The rest of the line is the error Go's `net` package gives, which no test can fix, so only its start and the address are contract. Once `READY=1` is sent, and before any connection is accepted, `Run` calls `Writer.Ready`, so `service.started`, carrying `Process.Version` as its `version`, is the first event of a run; with neither `IKIGENBA_COMMIT` nor `IKIGENBA_RELEASE` set that string is empty, and sites starts and serves all the same.

## The trail of a run

Every event of the process goes through the run's writer: the request middleware's, the site routes', the tools' and the run's own. appkit's writer queues and returns, so neither readiness nor any answer waits on telemetry; an event it cannot deliver goes to standard error as `sites: undelivered event: ` and the event's JSON (appkit's writer design), in the order recorded, and sites keeps serving. Apart from `service.started` and `service.stopping`, every event a run records is recorded while the handler answers a request and carries that request's id: a start and a stop record nothing else, so a start over a catalog whose trees are missing or whose repositories are gone records no `site.unavailable` until a request asks for the site. A test sees this at `Run` with a `Sink` whose `Deliver` fails, and in the binary by leaving `IKIGENBA_SERVICES` unset, which leaves the socket sink nowhere to deliver. That a telemetry installed or restarted after sites started is found without a restart, and that an event already written out is not sent again, is appkit's socket sink, which reads the services file afresh on every delivery (its wire design), and the binary gets it because `main` leaves `Process.Sink` nil (`D01-layout-and-run-seam`); `Run` adds nothing to it.

This design assumes a clock that reads times in the UTC years 0 through 9999, the years an RFC 3339 time can spell; appkit's writer cannot encode an event stamped outside them, and what sites records under such a clock is not contract.

## Stopping

When `ctx` is done — in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the context's cause — `Run` at once calls `Limits.Drain`, before it stops accepting, so a site request handled from then on that would have to start a rebuild is answered with the drain refusal `D07-site-serving` states (`503`, `Retry-After: 30`, `serving.Stopping`) while the requests in progress, a publish unpacking or a rebuild others share among them, carry on. It drains the server through `Serve`. Once every request has finished, `Run` calls `Writer.Shutdown` with the reason, the text of `context.Cause(ctx)`, inside the same drain window, which records `service.stopping` as the last event and delivers what is queued.

The **drain deadline** is `DRAIN_SECONDS`, as `settings.Read` returns it, in seconds, the longest `time.Duration` when that many seconds is longer, and it runs on real time: `Process.After` is never used for it (`D01-layout-and-run-seam`), so a drain test runs with `DRAIN_SECONDS=1` and waits about a second. When the requests use the whole window, every event still queued, `service.stopping` included, is written to standard error before the stop line, which is always `Run`'s last; `Serve` cuts the remaining requests off only after its `stop` has returned, and ends their contexts, and `Run` calls `Limits.Halt`, so every git still running is killed (`D10-limits`, `D05-git-and-cache`) and the client's connection closes without the rest of its answer. A publish cut off this way leaves its site pointing where it did, and a rebuild cut off leaves its tree missing, as `D05-git-and-cache` and `D09-tools` state. `Run` returns less than a second after the deadline, with every git it started gone, and says `sites: stopped with <n> requests unfinished` (`1 request` for one), exit 1. A cut-off request's `request.finished`, recorded after the deadline, is written out or not at all, never delivered; so telemetry's trail shows the cut-off request by its `request.started` alone. A request cut off while it waits on a git run, or while it is still writing a view's answer, records nothing else from the deadline on: no `tool.called` and no `site.*` event, so a publish cut off records neither `site.published` nor `tool.called`, a view waiting on a rebuild or still writing its body when it is cut off records neither `site.viewed` nor `site.unavailable`, and no line of standard error carries one. The cut-off reaches a handler waiting on git as its git run's error: the request's context ends, or `Limits.Halt` ends the git, and `D09-tools` and `D07-site-serving` give that request no answer and record nothing for it. It reaches a view still writing as an ended context: `Serve` ends the request's context before it closes the connection, so the write that fails, or the last one that returns, finds the context done, and `D08-visitors-and-trail` records nothing for such a view. A test holds a request open without sleeping in one of two ways: it posts to `/mcp` with a body it never finishes, which keeps the handler reading; or, to hold a git run past the deadline, it puts `GIT_TRACE` naming a FIFO in its temporary directory into `Process.Environ` and never opens the FIFO for reading. git(1) documents that `GIT_TRACE` set to an absolute path makes git write its trace to that file. Opening a FIFO for writing blocks until a reader opens it (fifo(7)), so every git `Run` starts blocks at its first trace line until the drain deadline kills it. A test made the site before it adds `GIT_TRACE` to what `Process.Environ` returns, so `create`'s owner read is not held. A test sees "every git it started gone" by putting a variable with a value unique to the test in `Process.Environ`, which every git `Run` starts receives and passes to the processes it starts, and, once `Run` has returned, scanning `/proc/*/environ` on Linux, without starting a process, finding no process whose environment holds that variable.

## Serving and stopping the listener

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next sites — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then ends those requests' contexts, closes their connections without the rest of their responses, and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. The count is of calls to `h.ServeHTTP` that had begun and had neither returned nor ended their goroutine without returning; a `create` or `publish` whose client left while its git ran ends that way (`D09-tools`), so it never holds a later stop up. `stop` is called once, when the drain is over, with a context that ends at the deadline. An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `sites: ` and the error as `Run`'s last line, exit 1. `Serve` gives its server an `ErrorLog` that goes nowhere, since Go's `net/http` documents that a nil one writes to the real standard error. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` because gosec `G112` demands it.

## The handler's hosts and routes

`web.Handler` is appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping a router that sorts every request first by its host and then by its path, and wraps each route in one of appkit's two identity gates. Every request records its two events, whatever route answers it.

A request's **host** is its `Host` with the port dropped (`net.SplitHostPort`, when it parses). A host with no `.` in it, an empty one included, or one that begins with `sites.`, compared ASCII case-insensitively, is sites' own: nginx's `sites.<space>`, and the bare name a sibling sends over the socket, such as the MCP gateway's `Host: backend`. Every other host is the apex host, and every request at it, whatever its method and path — `/`, `/about`, `/tools` and `/mcp` included — goes to `serving.Apex` under `identity.Optional`.

At the gateway's host routing is on the request's `URL.Path` as `net/http` decodes it, compared exactly, by hand — no `http.ServeMux`, which would clean `..` with a redirect — and the router itself never redirects:

- exactly `/mcp`: `Config.MCP` under `identity.Require`, with the seven tools registered on it by `tools.Register` once, when the handler is built, and the request's sites address put in its context with `urls.NewContext` over `urls.SitesURL`, so the tools build each site's `url` from it (`D09-tools`). A request without `X-User-Id` is answered 500 with `identity.MissingBody` before its method is looked at.
- exactly `/`, `/about` and `/tools`: `pages.Handler` under `identity.Optional`, every method (`D06-pages`, which owns their pages, their 405 and the guest's sign-in redirect; the landing page's catalog refusal is this design's, below). The tools page lists what `Config.MCP.Tools()` returns once `tools.Register` has filled the server, each `mcp.RegisteredTool` mapped in order to a `pages.Tool` handed to the pages handler in `pages.Config.Tools`, so the page and `tools/list` cannot drift. `/tools` is not a site path, so it wins over a site whose slug is `tools` the way `/about` does; `D04-store` keeps the name from being taken.
- an **appkit path**, beginning `/_appkit/`: appkit's `page.Static()` under `identity.Optional`, unchanged (`D06-pages`).
- every other path — `/blog/`, `/nope`, `/about/`, `/tools/`, `/mcp/tools`, `/_appkit`, `//` — is a site path: `serving.Sites` under `identity.Optional` (`D07-site-serving`), which treats the first segment as a slug and answers an unknown one with the not-found page.

`web.Handler` loads the template set once with `pages.Load` and hands the same set to the pages and to both site handlers. It hands every route `Config.Banner`, `Config.ServicesPath`, `Config.Store`, and the site handlers `Config.Cache`, `Config.Telemetry` and `Config.Rand` as well.

When the catalog cannot be read — in a test, `Config.Store` closed — no answer that needs it is guessed: a signed-in `GET /`, every site path asked with `GET` or `HEAD` by anyone, and every apex request are answered 503 with the one line `store.Unreachable`, while `/about`, `/tools`, the shared files, a guest's sign-in redirect and every 405 are answered as ever. Such an answer is not a view, so it carries no visitor cookie and records no `site.*` event (`D08-visitors-and-trail`). This design alone states where sites' catalog refusal answers, at the one handler a request reaches; `D06-pages` and `D07-site-serving` cite it.

sites calls no sibling while serving a request: no route connects to a socket the services file names, the telemetry entry's deliveries excepted. Which answers carry the visitor cookie and which requests record a `site.*` event is `D08-visitors-and-trail`'s: a page, a shared file, the apex host and `/mcp` without identity carry no visitor cookie and record nothing but the two request events.

The middleware records `request_bytes` as the bytes of the request body the handler read and `response_bytes` as the bytes of body it wrote (appkit's HTTP middleware design), both after any chunked coding is removed and with no header counted. So a page `GET` counts 0 and the page's length, a `HEAD` 0 and 0, and the catalog's 503 counts 0 and 42.

## Decisions

- The settings refusal at `Run` (its line, its exit 2, touching nothing) is this design's alone, because it is the first step of the start's order; `D01-layout-and-run-seam` keeps only `settings.Error`'s text. The rule that no socket, `PATH`, `NOTIFY_SOCKET` or `IKIGENBA_SERVICES` lookup comes before the settings is also this design's alone; `D01-layout-and-run-seam` keeps the whitelist of keys `Run` may look up.
- The closed set of event names is `D08-visitors-and-trail`'s, and that every event the run's writer delivers reaches `Process.Sink` is `D01-layout-and-run-seam`'s; this design states the writer's random source, the service and clock of every event but the `site.*` events, whose envelope `D08-visitors-and-trail` states, and the order and envelope of `service.started` and `service.stopping`.
- The request id is appkit's middleware's to mint; this design states only the wiring: the handler sits under that middleware, and `Run`'s writer draws from `Process.Rand`.
- Three diagnostics are sites' own and follow the house form, each exit 1: a descriptor that cannot be made a listener and an accept failure are `sites: ` and the error's text, and a `READY=1` that cannot be sent is one line beginning `sites: ` and naming the notification socket's address.
- A signal during start-up is a clean stop, exit 0, as for repos; the refusals before the catalog are unaffected by it.
- `Run` builds the limits before it opens the trees root, because `cache.Config` carries them; building them touches nothing. The vocabulary's decision 7, as amended, records the same order.
- The stop line is always `Run`'s last write, which places it after every `undelivered event` line, `service.stopping`'s included.
- A request cut off while it waits on git records nothing from the drain deadline on. `Serve` ends the context of a cut-off request after `stop` has returned, and `Run` calls `Limits.Halt`, so such a handler meets a git error matching its ended context or `limits.ErrHalted`; either way it answers nothing and records nothing. appkit's mcp server records `tool.called` once a tool's handler returns or panics, and its tools design records none for a `tools/call` answered with no result, so a tool handler in that state never returns: it ends its goroutine once its context is done (as `runtime.Goexit` does), which a test observes deterministically (`D09-tools`); a site handler simply writes nothing and records nothing (`D07-site-serving`). A `request.finished` recorded for it after the deadline is still written out or dropped as above. A view still writing its body at the deadline is covered the same way: `Serve` ends the contexts of the cut-off requests before it closes their connections, so the view's last write returns with its context done and it records no `site.*` event (`D08-visitors-and-trail`). What remains a race is only a request whose last write returned just before the deadline and whose events are recorded just after it, or one cut off right after its catalog write; no test can fix which side of the deadline those fall on, so the requirement does not speak of them. A request that got no answer still has its `request.finished`, with whatever status appkit's middleware reports for it: a visitor who left while a rebuild ran, whose handler wrote nothing and returned, is reported 200, and a `create` or `publish` whose client left while its git ran, whose handler ended its goroutine without returning, is reported 500 by the middleware's deferred recording; neither status was sent to anyone. Neither status is contract: appkit's telemetry http design covers a handler that returns or panics, not one whose goroutine ends, so the 500 rests on appkit's current middleware, as `D09-tools` records for its mcp server, and no requirement states either status.
- The handler classifies the host before the path, so `/mcp` at the apex host is an apex request and never the MCP endpoint.

## Consumer tasks

`Run`, serving, calls `settings.Read(p.LookupEnv)`; looks up `LISTEN_PID` and `LISTEN_FDS`, unsets the three `LISTEN_*` variables and takes its listener from `p.Inherit(3)`; calls `git.Find` with the `PATH` it looked up and `p.Environ`; calls `db.Open` with a `db.Config{Path: filepath.Join(p.Dir, "state", "sites.db"), Migrations: sites.Migrations(), Now: p.Now, Service: pages.ServiceName, Stderr: p.Stderr}` and `store.New` over the handle with a `store.Config`; builds `limits.New(s, limits.Clock{After: p.After})`; calls `cache.Open` with a `cache.Config` over the trees root, the resolved `REPOS_DIR`, the `*git.Git` and the `*limits.Limits`; builds `telemetry.New(telemetry.Config{Service: pages.ServiceName, Version: p.Version, ...})`; calls `p.MCP(w)`; builds `web.Handler(web.Config{Banner: p.Banner, MCP: srv, ServicesPath: path, Store: st, Cache: c, Limits: l, Telemetry: w, Rand: rand})`; sends `READY=1`; calls `w.Ready()`; and calls `server.Serve(ctx, ln, h, drain, stop)`. When `ctx` is done it calls `l.Drain()` at once; `stop` calls `w.Shutdown(stopCtx, context.Cause(ctx).Error())`; and when the drain deadline elapses with requests still in progress it calls `l.Halt()`, so their git runs end. It closes the catalog's handle with `DB.Close` once `Serve` has returned. When `Serve` returns a `*server.DrainError` `e`, it writes `"sites: " + e.Error() + "\n"` and returns `cli.ExitServerFailed`; when it returns nil, `cli.ExitSuccess`.
