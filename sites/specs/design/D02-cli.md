# D02-cli

sites as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, what `db status` reports of the catalog, and the two constants whose text is fixed here, the usage text and the manifest, with the one file under `etc/` that copies the manifest. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, the display string `main` read, `cli.Run`, the root package's `Etc` and `Migrations`, and `settings.Defaults`; `D06-pages` declares `pages.Description`. When `Args` is empty sites serves, and everything from there is `D03-serve`'s.

The arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity, `manifest` writes `Manifest`, and `--help` writes `Usage`. The one two-word command, `db status`, reports the catalog's migrations (below). Any other `Args` is a usage error. The argument sites complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`; and otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `sites: `, and after exactly one empty line comes the hint to run `sites --help`, unprefixed because sites is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. The constant for 1 keeps its name, `ExitServerFailed`, though it now also covers a `db status` that fails. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a setting that is not a positive whole number) exits 2, while trouble on the host once sites is past its checks (no git on the `PATH`, a catalog it cannot open, a `cache/sites` it cannot create, a drain that runs out) exits 1, and so does a `db status` whose catalog cannot be read. `Run` returns no other value.

## db status

`db status` is an operator's look at the catalog: which of the migrations the binary carries `state/sites.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status` (its D16), which sites calls with the path `state/sites.db` resolved against `Process.Dir` (so relative to the working directory in the binary) and the migrations `sites.Migrations()` returns, writing straight to `Stdout`. sites adds nothing to the lines and states nothing about their format; its requirements say only that the bytes on `Stdout` are the ones `db.Status` writes for that path and those migrations, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database, never with a format it spells out. `db.Status` only looks: it applies nothing and creates nothing, so before sites' first start `db status` reports every migration pending and leaves the directory as it was, and a catalog an earlier sites kept, which records no migration, reads the same way. When it returns an error, sites says so on one line, `sites: ` and the error's text with each newline replaced by a space, and exits 1. Whatever `db.Status` had already written to `Stdout` stays there: findings are product, and the repository's command-line conventions send a report to stdout whole, bad news included. That is the one case in which a failure may leave anything on `Stdout`. A catalog that records a migration this sites does not carry, one a newer sites upgraded, is not a failure: older code runs on newer data (`D03-serve`), appkit's `db.Status` lists every line, the unknown version among them, and returns nil, so `db status` writes nothing to `Stderr` and exits 0. A catalog that cannot be read yields no lines at all and exits 1. `db status` reads no environment and takes no socket.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket, no git and no repository, and only `db status` reads the catalog, so `sites --version` succeeds with nothing passed in and `sites bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, the timer, the random source, the sink, the banner source or the server maker, and only `db status` reads anything under the working directory, creating nothing there. A command runs no git, so it reads no repository, and records no event: the trail is what sites records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns, `db status` and `db bogus` included. Every failure but that one `db status` case leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text is exactly the bootstrap story's: sites' name; its description, which is `pages.Description`, the line the about screen shows and the host publishes in its services file for the MCP gateway's instructions; that it is not the host's default app; that it is one of the suite's MCP services; that it serves guests (`guests = true`), so the host's nginx admits a visitor with no credential to every path but `/mcp`, `/api` and the paths under them, and sites decides for itself who must sign in (opsctl's `S5-nginx.md` and `S7-apps.md`); no secrets; the three settings of `[env]` with the defaults `settings.Defaults` holds, `REPOS_DIR`, `SITE_MAX_BYTES` and `OPERATION_SECONDS`, as the stories list them; the `[database]` table that tells the host to keep and replicate `state/sites.db`; and the `[resources]` table opsctl writes into the service unit, whose `memory_max` `128M` caps the memory of sites and every git it runs together. It declares no port, since sites serves on the socket the host passes it, no `DRAIN_SECONDS`, which is opsctl's to set, and no `cache/`, whose trees are disposable and rebuilt on demand.

## The file under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and the suite release ships what the binary emits as sites' `etc/manifest.toml`. The build run writes it from the constant and keeps the two in step. The file is proved by use: the root package embeds `etc/` and exports it as `Etc` (`D01-layout-and-run-seam`), so a test compares the embedded `manifest.toml` with `cli.Manifest` without ever opening the checkout, and a build whose `etc/` lacks the file, or holds a stale copy, fails to compile or fails that test. That test lives in the external test package `sites_test` beside the root package, since it imports both the root package and `internal/cli`, and `internal/cli` reaches the root package through `internal/pages`, so a test inside package `sites` would form an import cycle.

sites ships no nginx fragment: the host serves it with the configuration every app gets, opened to guests outside `/mcp`, `/api` and the paths under them by `guests = true` (`S20-package.md`), so this design declares no nginx constant and `Etc` holds the manifest alone. What sites' directory in the suite release holds beside `etc/` (`bin/sites`, and the human-drawn `share/icon.svg`), that nothing else is under `etc/` or `share/`, that no database or tree ships in it, and that the commit appears in the release's name and top-level directory and nowhere in the binary or a member of `sites/` are `devctl build`'s output, which no test this design permits can see; they are `D11-on-a-space`'s to record.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `sites --version`, `sites manifest` or `sites --help` and reads stdout; an operator types `sites db status` in `/var/opt/ikigenba/sites` before or after a deploy and reads which migrations the catalog has had; `devctl build` runs `sites manifest` and ships its output as the release's `sites/etc/manifest.toml`; the help text tells a caller what `ExitSuccess`, `ExitServerFailed` and `ExitUsage` mean.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s), `Dir` (an empty temporary directory) and, for `--version`, `Version` set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `p.Version + "\n"` for a `Version` of its own choosing, the empty string included, `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Environ`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `After`, `Banner` and `MCP` to functions that record a call, `Rand` to a reader and `Sink` to a `*telemetry.Capture` that record any use, and asserts none was used. A test of `db status` makes a catalog under its `Dir` with `db.Open` and `sites.Migrations()` (or with a fixed `Now` and an extra recorded version written through `DB.Write`, or a file that is not a database), closes it, runs `cli.Run` with `Args` `["db", "status"]`, and compares `Stdout` with what its own `db.Status` call wrote into a buffer for the same path and migrations before `Run` was called, and with what it writes after, and `Stderr` with `"sites: "` and that call's error text. A test compares `cli.Manifest` with `pages.Description` and `settings.Defaults()`. A test in package `sites_test` reads `manifest.toml` from `sites.Etc()` with `fs.ReadFile` and compares it with `cli.Manifest`.
