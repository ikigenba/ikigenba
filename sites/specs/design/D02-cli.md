# D02-cli

sites as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, and the two constants whose text is fixed here, the usage text and the manifest, with the one file under `etc/` that copies the manifest. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run`, `cli.Version`, the root package's `Etc`, and `settings.Defaults`; `D06-pages` declares `pages.Description`. When `Args` is empty sites serves, and everything from there is `D03-serve`'s.

`Run` takes at most one argument and the argument decides everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Version` and a newline, `manifest` writes `Manifest`, and `--help` writes `Usage`. Any other `Args` is a usage error. The argument sites complains about is the first one it does not take: the first element when that is not a recognised word, otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `sites: `, and after exactly one empty line comes the hint to run `sites --help`, unprefixed because sites is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a server that failed, 2 for a usage error. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a setting that is not a positive whole number) exits 2, while trouble on the host once sites is past its checks (no git on the `PATH`, a catalog it cannot open, a `cache/sites` it cannot create, a drain that runs out) exits 1. `Run` returns no other value.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket, no git, no catalog and no repository, so `sites --version` succeeds with nothing passed in and `sites bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, the timer, the random source, the sink, the banner source, the server maker, the database source or the working directory. A command runs no git, so it reads no repository, and records no event: the trail is what sites records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns. Every failure leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text is exactly the bootstrap story's: sites' name; its description, which is `pages.Description`, the line the about screen shows and the host publishes in its services file for the MCP gateway's instructions; that it is not the host's default app; that it is one of the suite's MCP services; that it serves guests (`guests = true`), so the host's nginx admits a visitor with no credential to every path but `/mcp` and sites decides for itself who must sign in (opsctl's `S5-nginx.md` and `S7-apps.md`); no secrets; the three settings of `[env]` with the defaults `settings.Defaults` holds, `REPOS_DIR`, `SITE_MAX_BYTES` and `OPERATION_SECONDS`, as the stories list them; the `[database]` table that tells the host to keep and replicate `state/sites.db`; and the `[resources]` table opsctl writes into the service unit, `cpu_weight` 50 and `io_weight` 50 and `memory_max` `1G`, which bounds sites and every git it runs together. It declares no port, since sites serves on the socket the host passes it, no `DRAIN_SECONDS`, which is opsctl's to set, and no `cache/`, whose trees are disposable and rebuilt on demand.

## The file under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ. The build run writes it from the constant and keeps the two in step. The file is proved by use: the root package embeds `etc/` and exports it as `Etc` (`D01-layout-and-run-seam`), so a test compares the embedded `manifest.toml` with `cli.Manifest` without ever opening the checkout, and a build whose `etc/` lacks the file, or holds a stale copy, fails to compile or fails that test. That test lives in the external test package `sites_test` beside the root package, since it imports both the root package and `internal/cli`, and `internal/cli` reaches the root package through `internal/pages`, so a test inside package `sites` would form an import cycle.

sites ships no nginx fragment: the host serves it with the configuration every app gets, opened to guests outside `/mcp` by `guests = true` (`S20-package.md`), so this design declares no nginx constant and `Etc` holds the manifest alone. What the release file holds beside `etc/` (`bin/sites`, and the human-drawn `share/icon.svg`), that nothing else is under `etc/` or `share/`, that no database or tree ships in it, and that the version appears only in the file's name and the binary are `devctl build`'s output, which no test this design permits can see; they are `D11-on-a-space`'s to record.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `sites --version`, `sites manifest` or `sites --help` and reads stdout; `devctl build` runs `sites manifest` and compares its output with the release's `etc/manifest.toml`; the help text tells a caller what `ExitSuccess`, `ExitServerFailed` and `ExitUsage` mean.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s) and `Dir` (an empty temporary directory) set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `cli.Version + "\n"`, `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Environ`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `After`, `Banner` and `MCP` to functions that record a call, `Rand` to a reader and `Sink` to a `*telemetry.Capture` that record any use, and `Database` to a path under `Dir`, and asserts none was used. A test compares `cli.Manifest` with `pages.Description` and `settings.Defaults()`. A test in package `sites_test` reads `manifest.toml` from `sites.Etc()` with `fs.ReadFile` and compares it with `cli.Manifest`.
