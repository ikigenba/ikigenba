# D04-store

The catalog: `internal/store`, which owns sites' one SQLite database, `state/sites.db`, and everything it records — every site's id, name, slug, owner, repository, ref, path, visibility, listing, published commit and path and times, and the one setting `apex` — together with the rules a site's name, slug and id obey and the one line every consumer answers when the catalog cannot be reached. `D01-layout-and-run-seam` declares `cli.Process`, whose `Dir`, `Now` and `Rand` reach the catalog through `cli.Run`, resolves the path the catalog lives at, and declares the root package's `Migrations`, the schema's migrations; `D03-serve` opens the catalog with appkit's `db.Open` at start, builds the store over that handle, writes the diagnostic for a catalog that will not open, and closes the handle after the drain. Opening, migrating, the journal mode, transactions and the failure seam are appkit's `db` (its D15 and D16), which this document restates none of. This document declares every exported name of `internal/store` and states what each does. What a tool checks before it calls the store, in which order, and what it answers is `D09-tools`'; what the landing page shows of a site is `D06-pages`'; how a site path or the apex host is answered from a record is `D07-site-serving`'s; the trees under `cache/sites/` and the repositories under `REPOS_DIR` are `D05-git-and-cache`'s. The store holds no file but the database and runs no git.

## One catalog, one writer

sites is the catalog's only writer, and the catalog is the only record of its sites: `cache/sites/` is disposable and rebuilt from a record, never the reverse. sites never rebuilds a catalog: a lost `state/sites.db` comes back only from the host's replica, so a start that finds no database begins an empty one and looks at nothing else on disk to fill it. What is contract is what a reader and a restart see: what a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds, field for field and with the same apex. A test proves the catalog's content that way, by closing and reopening, never by reading tables; the schema, the backfills and the `listed` column a write leaves (The schema, below) are the exception, read inside a `DB.Read` because `Visible` decides who sees a site from that column (R-CX0H-I4CR) and only the backfills and the writes keep it right.

## The schema

The schema is contract too, because a migration is applied to a catalog that already exists and the migrations must agree with what earlier releases left on disk, and with what the release before this one reads and writes while both run against it. There are three migrations. `0001_catalog.sql` is the schema sites has always created: a table `sites` with the columns `id`, the primary key, `name`, `slug`, `owner` and `payload`, the last holding the whole record as JSON, and a table `settings` of `key` and `value` holding the apex. Written with `CREATE TABLE IF NOT EXISTS` and seeding nothing, it creates both tables on a fresh catalog and changes nothing on a catalog an earlier sites kept, which `db.Open` then records as having had `0001`, so that catalog's sites and apex are served as they were.

`0002_listed.sql`, which the previous release brought, began moving the catalog's lists into SQL, the expand half; it adds and changes nothing a reader of `0001`'s shape depends on. It is exactly:

`ALTER TABLE sites ADD COLUMN listed INTEGER NOT NULL DEFAULT 0;` then `UPDATE sites SET listed = CASE WHEN json_extract(payload,'$.Listed') THEN 1 ELSE 0 END;` then `CREATE INDEX sites_owner_name ON sites(owner, name);`, `CREATE INDEX sites_slug ON sites(slug);` and `CREATE INDEX sites_listed_name ON sites(listed, name);`.

The column mirrors the record's `Listed`, 1 or 0, and the backfill fills it from each existing row's payload: JSON `true` gives 1, and `false` or a payload with no `Listed` member gives 0, since `json_extract` answers 1, 0 and null for them. `sites_owner_name` backs `List`'s window, `Find` and `Visible`'s window of the user's own unlisted sites, `sites_slug` backs `BySlug`, and `sites_listed_name` backs `Visible`'s window of listed sites. The payload keeps `Listed` too: the record's JSON stays the contract for every field a `Site` carries, `Listed` included (R-4FCV-HU6X), and for writing a row, since the previous release reads every row this release writes and decides its `Visible` from the payload (R-TWL1-XPY7); `listed` is a copy of one of its members that every write keeps equal to it (R-4NW6-68DS), and it alone decides who sees a site in `Visible` (R-CX0H-I4CR). Dropping `Listed` from the payload is a contract step for a release after the one that stops reading it.

`0003_backfill_listed.sql` is the second step, run before this release reads the column. It is exactly:

`UPDATE sites SET listed = CASE WHEN json_extract(payload,'$.Listed') THEN 1 ELSE 0 END;`

It runs `0002`'s backfill again, because rows written between the two can carry a `listed` that disagrees with their payload. While the previous release rolled out, the release before it still ran against the catalog `0002` had migrated: its insert names only the five columns of `0001`, so a row it created took the default 0, and its upsert sets only `payload`, so a row it created listed, or whose listing it changed, kept a stale `listed`. The previous release writes `listed` on every save (R-4NW6-68DS), as this one does, so once `0003` has run no write of either leaves a row stale, and the column can decide `Visible` (R-D0O6-NFKU). It adds no table, column or index, so the schema requirements stand as they were.

The previous release runs on this schema unchanged, as the root `AGENTS.md` asks of every release boundary, trivially, since `0003` holds no DDL: on its start over a catalog this release has migrated, appkit's `db.Open` finds a migration it does not carry, applies nothing and warns (`D03-serve`), and it then lists and serves as before. Its reads are this release's but for `Visible`, which it decides from the payload, and its writes keep `listed` equal to the payload's `Listed`, so a mix of the two releases, during a rolling restart or after a rollback, answers the same lists.

Each migration's test is one of the shape every service has: open a fresh catalog with `sites.Migrations()` and inspect `sqlite_master`, `PRAGMA table_info` and `PRAGMA index_list` with `PRAGMA index_info`; for the backfill, open a catalog with a file system holding only `0001_catalog.sql` taken from `sites.Migrations()`, write rows through `DB.Write` whose payloads say `Listed` true, false or nothing, close it, open it again with `sites.Migrations()` and read `listed` back; for the second backfill, open a catalog with a file system holding only `0001_catalog.sql` and `0002_listed.sql` taken from `sites.Migrations()`, write rows through `DB.Write` whose `listed` is 0 with a payload saying `Listed` true, 1 with one saying `Listed` false, and 1 with one saying nothing, close it, open it again with `sites.Migrations()` and read every column back; and, for adoption, build a catalog in the shape an earlier sites wrote, with no `schema_migrations`, and see a store over the opened handle answer its sites and apex.

## The handle

The store does not open anything. `store.New` builds a store over a handle `db.Open` returned, with the clock and random source it stamps and draws from; every read is a `DB.Read` and every write a `DB.Write` on that handle, so the handle's one writer serializes the writes and the store keeps no lock of its own. A write that must check and change together — a create's name check and insert, a publish's commit and time, an update's apex check, a delete of the apex — does both inside one `DB.Write`, which is what keeps the catalog's invariants under concurrent calls.

A catalog that fails is a **failing** store: from a `SetFailing(true)` on its handle until a `SetFailing(false)`, and once its handle is closed, every method answers a catalog error and changes nothing. That is the one failure seam: a test that needs a call's reads to succeed and its write to fail turns it on from a hook the call runs between them (the `limits.Clock.After` the cache calls before each git run, or `cache.Config.Joined`), and never takes a permission away, which under WAL does not reliably fail a write. A call that changes nothing (an `Update` that changes no field, a `SetApex` of the site already the apex, a `ClearApex` with none set) writes nothing that can fail on its own; its answer is decided by its reads.

## Sites

A site's **id** is `sit_` and 16 lowercase hexadecimal digits, under appkit's registered entity prefix for the entity type `site` (appkit's telemetry contract), drawn from the random source when the site is created and never changed. Its **name** is 1 to 64 bytes, each a lowercase ASCII letter, a digit or `-`, the first not `-`, and none of `about`, `mcp`, `api` or `tools`, since `/about`, `/tools` and `/mcp` are sites' own paths and `/api` is reserved across the suite on every app's host, sites' included (`tools` joined the list with the tools page; no site named `tools` is expected on any space, so the rule is stated and nothing migrates); it is taken as given, never trimmed or folded. Its **slug** is the first segment of its URL: its name when it is created listed, and its name, `-`, and 8 lowercase hexadecimal digits drawn from the random source when it is created unlisted; it is fixed at create and nothing changes it, `listed` included. Names are one namespace for the whole space, because the slug is the URL: a name is **taken** when any site, of any owner, has it as its name or as its slug, so an unlisted site takes two strings, and a drawn slug that is already taken is drawn again rather than refused. Its **owner** is the user id of the caller that created it, the `UserID` of the `identity.Caller` appkit's identity gives the request (`D03-serve`). Its **repository** is a repository id as repos names its directory, kept verbatim, so a site keeps working across a rename in repos; the store never looks at it. Its **ref** is the ref a publish without one resolves, and its **path** the directory of the repository a publish without one unpacks, empty when the site publishes from the root; the store keeps it exactly as given and gives no string any meaning, so what a path may be is `D09-tools`' check (with `cache.ValidPath`, `D05-git-and-cache`) before the store is called. Its **visibility** `public` or `private`, and **listed** whether the landing page shows it to others. **Created** is the time of the create and **published** the time of the last publish, both in UTC to the second, the precision the tools answer them in; **commit** is the sha that publish named and **published path** the path it unpacked, both empty and with a zero `Published` until the first publish; the published path sits beside the commit as the commit sits beside the ref, so a changed path, like a changed ref, changes nothing served until the next publish, and serving reads the published path, never the configured one. A site is **unpublished** while its commit is empty.

## Reads and writes

The reads are what the consumers are built from: `Find` is a caller's own site by name, so another owner's site is indistinguishable from none; `BySlug` is any owner's site by slug, for serving; `List` is one window of one owner's sites; `Visible` is one window of what the landing page lists to a user, the **visible set**, every site whose row is listed and that user's own unlisted ones, as the `listed` column says, and `VisibleBefore` one window of the same set read backwards; `Taken` is the space-wide name check. All lists are in ascending byte order of name and are never nil. `Find` and `BySlug` read the one row they answer, `WHERE owner=? AND name=?` and `WHERE slug=?`, and no longer load every row to pick one out; what they answer is unchanged.

## Listing

The store never hands out every site at once. `List` answers one window: at most `n` sites of one owner, in ascending byte order of name, those whose name is greater than `after`, or the first ones when `after` is empty, since every name is greater than the empty string. This is the suite's storage rule (`shape/`, Storage; appkit's D25): the query carries the owner and the position in its `WHERE`, the order in its `ORDER BY` and the window in its `LIMIT`, `WHERE owner=? AND name > ? ORDER BY name LIMIT ?`, and `sites_owner_name` backs it, so a page costs the same however deep it is and SQLite sorts nothing (`EXPLAIN QUERY PLAN` reports `SEARCH sites USING INDEX sites_owner_name (owner=? AND name>?)` and no temporary B-tree). The comparison and the order are byte order, SQLite's default `BINARY` collation, never one that folds case, so a position that is not a name, such as one an agent encoded by hand, still lands where byte order puts it. The store knows nothing of tokens, limits or pages: the `list` tool (`D09-tools`) turns the last name of a page into appkit's `paging` token, and asks for one more site than the page to learn whether more follow. A window of fewer than one site is empty, never "no limit", whatever SQLite makes of a negative `LIMIT`.

`Visible(ctx, user, after, n)` answers one window of the visible set: at most `n` sites, in ascending byte order of name, those whose name is greater than `after`, or the first ones when `after` is empty, exactly as `List` positions an owner's sites. The landing page pages with it (`D06-pages`), turning the last name it shows into a page token of its own, so the store knows nothing of tokens here either. It reads the `listed` column, never the payload, to decide who sees a site (R-CX0H-I4CR), in one query whose two halves are each index-backed and each carry the position: `SELECT name, payload FROM sites WHERE listed=1 AND name > ? UNION ALL SELECT name, payload FROM sites INDEXED BY sites_owner_name WHERE owner=? AND listed=0 AND name > ? ORDER BY name LIMIT ?`, the `ORDER BY` and `LIMIT` binding the compound, so `name` is in the result set for the `ORDER BY` to name, and `after` bound to both `name > ?`; the first window binds the empty string, which every name is greater than. `EXPLAIN QUERY PLAN` reports `MERGE (UNION ALL)`, its left side `SEARCH sites USING INDEX sites_listed_name (listed=? AND name>?)` and its right side `SEARCH sites USING INDEX sites_owner_name (owner=? AND name>?)`, and no temporary B-tree, for the first window and for every later one alike: SQLite merges the two index orders from the position on and its `LIMIT` stops the merge early, so a window costs the same however deep it is and `Visible` holds at most `n` sites, the landing page's one window plus one row, as `shape/` Storage asks. The `INDEXED BY` is needed: without `ANALYZE` statistics SQLite's planner picks `sites_listed_name (listed=? AND name>?)` for the owner side too, which walks every unlisted site of every owner past the position. The single query `WHERE (listed=1 OR owner=?) AND name > ? ORDER BY name LIMIT ?` is not used: it reads both indexes (`MULTI-INDEX OR`) and then sorts the whole remaining visible set in a temporary B-tree (`USE TEMP B-TREE FOR ORDER BY`) before its `LIMIT` cuts it. Both indexes already end in `name`, so the position is a range on each and no migration is needed. As with `List`, the comparison is byte order, an `after` that is no site's name lands where byte order puts it, and an `n` below 1 answers no site (R-YINC-0DTY) and is never bound straight into the `LIMIT`, since SQLite reads a negative `LIMIT` as no upper bound at all. A row whose `listed` disagrees with its payload, which only a hand-made row can now be, is seen by others exactly when its `listed` is 1 and still answers its payload's `Listed` (R-YJV8-E5KN).

`VisibleBefore(ctx, user, before, n)` is the same window read backwards, which the landing page's way back and its last window read (`D06-pages`): at most `n` sites of the visible set, in descending byte order of name, those whose name is less than `before`, or the last ones when `before` is empty, which here means no bound rather than a position. The position need not be a name any site holds: a `before` that is no site's name lands where byte order puts it. It is the forward window's query turned round, in two fixed statements whose values are bound as parameters: `SELECT name, payload FROM sites WHERE listed=1 AND name < ? UNION ALL SELECT name, payload FROM sites INDEXED BY sites_owner_name WHERE owner=? AND listed=0 AND name < ? ORDER BY name DESC LIMIT ?` for a `before` that is not empty, `before` bound to both `name < ?`, and the same without either `name < ?` for an empty one. `EXPLAIN QUERY PLAN` reports `MERGE (UNION ALL)`, its left side `SEARCH sites USING INDEX sites_listed_name (listed=? AND name<?)` and its right side `SEARCH sites USING INDEX sites_owner_name (owner=? AND name<?)`, or `(listed=?)` and `(owner=?)` for the unbounded statement, and no temporary B-tree (observed with `sqlite3` 3.46 over 10,000 rows): SQLite walks both indexes backwards from the position and its `LIMIT` stops the merge, so the last window costs what the first does and `VisibleBefore` too holds at most `n` sites. The `INDEXED BY` is there for the reason it is on `Visible`. It decides who sees a site from the `listed` column as `Visible` does, and an `n` below 1 answers no site and is never bound into the `LIMIT` (R-OPVQ-UEST). The store hands the sites back newest name first and knows nothing of pages; the landing page turns them into its order. Both indexes already end in `name`, so the reversed range needs no migration.

The earlier `List` and `Visible` read every site into one slice, and `Find` and `BySlug` did too to pick one out. The `list` tool and the landing page were their callers and now page, so the windows replace them and no whole-list method remains.

A sandbox check proves the shape at size: it loads 10,000 sites into a sandbox's catalog with `sqlite3`, times a `list` page and the landing page, watches the process's resident memory over 100 page reads for growth, and runs `EXPLAIN QUERY PLAN` on the `list` window, expecting `sites_owner_name` and no temporary B-tree, and on `Visible`'s query, with an empty position and with a later one, expecting `MERGE (UNION ALL)` with its listed side searching `sites_listed_name (listed=? AND name>?)`, its owner side `sites_owner_name (owner=? AND name>?)`, and no temporary B-tree, and on `VisibleBefore`'s two statements, expecting the same with `name<?` on each side, and with `listed=?` and `owner=?` alone for the unbounded one; it times the landing page's last window as well as its first. It also starts the previous release's binary against the catalog this release migrated and sees it start and list.

Every write names its site by id, which a consumer learned from a read. `Create` mints the id and the slug and stamps the created time; `Publish` sets the commit, the published path and the published time together, so a reader sees a site at its old commit and path or its new ones and never a mix, and leaves the configured path alone, since a one-off path is for that publish only; `Update` changes any of visibility, listing, ref and path, all or nothing, a path of the empty string clearing it to the root, and says which it changed; `Delete` removes a site and, when it was the apex, the apex with it. A field sent with the value it already has is not a change.

## The apex

The catalog holds one setting, `apex`: one site's id or nothing, nothing when a catalog begins. `Apex` reads it as the site it names, `SetApex` sets it to a public site, published or not, replacing whatever was there, and `ClearApex` unsets it. The apex site is always public: `SetApex` refuses a private site and `Update` refuses to make the apex site private, each with `ErrNotPublic` and changing nothing, and both decide against the same moment of the catalog, so no interleaving leaves a private apex. Deleting the apex site clears the setting in the same step, so the setting never names a site that is gone. Who may set or clear the apex is `D09-tools`'; the store takes any id.

## Errors

`ErrNotFound`, `ErrNameTaken` and `ErrNotPublic` are answers about the catalog's content. Every other error from a method is answered as the catalog being unreachable: every consumer answers it with `Unreachable`, the one line a tool refuses with, the landing page and every site path answer `503` with, and the apex host answers too, never quoting the underlying error. A failing store, a random source that fails and a context already done all end there. So does a write given a value no consumer sends — a name `ValidName` refuses, an empty owner or ref, a visibility other than `public` or `private`, a commit that is not a sha — which changes nothing: `D09-tools` refuses each of those first, with its own line. A path is never such a value, since the store gives a path no rule. When one call meets several of these conditions, one fixed precedence decides its answer: a done context, then a failing store, then an invalid argument, then a missing site, then a taken name or a private apex.

## Decisions

- Ids are 8 bytes of `Rand`, slug suffixes 4 bytes; a create reads id candidates first, then, for an unlisted site, slug candidates, so a test handing in known bytes knows both in advance.
- A drawn id already catalogued and a drawn slug already taken are drawn again, never refused.
- `Update` and `SetApex` check apex-must-be-public in the same step as the write.
- A deleted site's id is not remembered, so a later create may in principle draw it again; with 64 random bits the odds are negligible, and keeping tombstones was not worth it.
- The store has no `Open` and no `Close`: the handle is appkit's, opened and closed by `cli.Run`, and a store over it lives as long as it does. The mutex the store once held is gone, since `DB.Write` already runs one writer at a time.
- The schema is contract (R-9U9Q-8OGL, R-4AH9-YR85, R-Y074-44FP, R-4CX2-QAPJ, R-4E4Z-42G8, R-D0O6-NFKU), and so is the record's JSON in `payload`, as far as a catalog an earlier sites kept must be read (R-4FCV-HU6X).
- `0002` is expand only: one added column with a default, a backfill and three indexes, which the release before the previous one ignored. `0003` is expand only too, a backfill and no DDL, which the previous release runs on unchanged; it corrects the rows that release before it wrote during the previous release's rollout, so `Visible` can read `listed`. Contracting the payload's `Listed` is not part of either.
- `Visible` is one `UNION ALL` of two index-backed halves, each half on its own index, never the `OR` form, which sorts the whole visible set in a temporary B-tree; its owner half names `sites_owner_name` with `INDEXED BY`, so the plan does not hang on `ANALYZE`.
- `List` takes `after` and `n` and returns only the slice, after webhooks' and dummy's stores: the caller asks for one more than its page to learn whether more follow, so the store has no notion of a page. `Visible` takes `after` and `n` in the same style, `after` empty for the first window, since the landing page now pages (`D06-pages`); an earlier `Visible` took only `n`, while the landing page showed only its first page.
- Positioning `Visible` adds no migration: `sites_listed_name` is `(listed, name)` and `sites_owner_name` is `(owner, name)`, so each half's `name > ?` is a range on its own index, and the schema requirements stand as they were.
- `VisibleBefore` is a second method beside `Visible`, not a direction argument to it, so each statement stays fixed and each plan is checked on its own; an empty `before` is unbounded, which is how the landing page reads its last window, rather than a sentinel greater than every name, which a hand-made row could beat. It needs no migration: the reversed ranges run on the same two indexes.
- A window `n` below 1 is an empty answer, not a catalog error, so the precedence of R-U3WG-8CED gains no case.
- Only whole-second UTC times are accepted from an earlier catalog's `payload`, because every earlier sites wrote `Created` and `Published` as its clock's time in UTC truncated to the second, and so that every `Site` the store returns has the shape R-2K28-H01H states.
- The store validates nothing a tool has not already refused, beyond keeping its own invariants (name rule, owner, visibility, non-empty ref, commit shape).
- A path has no store invariant: `Create`, `Update` and `Publish` keep whatever string they are given, empty meaning the root. Its shape is `cache.ValidPath`'s and is refused by `D09-tools` before the catalog is touched, and whether it names a directory is known only at a publish, from git; the store importing the cache's rule would point a dependency the wrong way, and a second copy of the rule could drift from the first.
- The path adds two payload members, `Path` and `PublishedPath`, and no column: nothing selects or orders by a path, so no migration is needed and `Migrations` still holds the three files. Both members are written on every save, present when empty, as `Commit` is (R-TWL1-XPY7). A row without them, as every earlier sites wrote, reads as a site at the root (R-H4BE-JRMO), and a row with members this release does not know is read as if they were absent (R-H5JA-XJDD), so a later release can add members the same way.
- The previous release decodes the payload with the standard library's `encoding/json` into its own `Site`, which ignores members it does not know, so it reads a row this release wrote and serves the site from the root, as accepted for the one release the mix lasts. Its contract never promised that: its R-4FCV-HU6X reads rows whose members are exactly its eleven, and R-H5JA-XJDD makes the promise from this release on. Its writes rebuild the payload from what it decoded, so a `publish` or an `update` the previous release makes during the mix drops `Path` and `PublishedPath` from that row, so that site loses its configured path until its path is set again, and is served from the root until its next publish from a path.
- Setting a path to the value it already has is not a change, as for every other field; paths compare byte for byte.

## Consumer tasks

`cli.Run` opens the catalog with `d, err := db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "sites.db"), Migrations: sites.Migrations(), Now: p.Now})`; on any error while `ctx` is not done it writes `D03-serve`'s diagnostic `sites: cannot open database state/sites.db: ` with the error's text as the reason; an error from a `ctx` already done is a stop, not a failure, and `D03-serve` says what `Run` does then; otherwise it hands `store.New(d, store.Config{Now: p.Now, Rand: p.Rand})` to `web.Config.Store` and calls `d.Close()` after the drain.

The tools (`D09-tools`), `u` being the `identity.Caller` of the call: `list` is `s.List(ctx, u.UserID, after, n+1)`, `after` being the name its `page` decodes to or empty and `n` its page size, answering the first `n` and a `next` when the extra site came back; `show` is `s.Find(ctx, u.UserID, name)`; `create` checks `store.ValidName(name)`, then `s.Taken(ctx, name)`, then the repository and ref, then the visibility against `store.Public` and `store.Private`, and calls `s.Create(ctx, store.Draft{Owner: u.UserID, Name: name, Repo: repo, Ref: ref, Path: path, Visibility: visibility, Listed: listed})`, `path` empty when none was sent, `store.ErrNameTaken` still answering the taken rule's refusal when a racing create won; `publish` is `s.Find`, then the cache's resolve and unpack at the path it used, its one-off `path` or else `site.Path`, then `s.Publish(ctx, site.ID, sha, path)`; `update` is `s.Find` then `s.Update(ctx, site.ID, store.Change{Visibility: v, Listed: l, Ref: r, Path: p})`, the names it returns deciding the `site.*` events `D08-visitors-and-trail` states, and answering `apex site must be public` for `store.ErrNotPublic`; `delete` is `s.Find`, `s.Delete(ctx, site.ID)`, the cache's removal, and the apex event `D08-visitors-and-trail` states when `wasApex`; `apex` is `s.Apex(ctx)`, or `s.Find` then `s.SetApex(ctx, site.ID)`, or `s.ClearApex(ctx)`. `store.ErrNotFound` from `Find` is `no site named '<name>'`; an error matching none of the sentinels is the refusal `store.Unreachable`. A site object's `id` satisfies `store.ValidID`, which is also how every `site` event attribute is checked.

Pages and serving (`D06-pages`, `D07-site-serving`): the landing page is `s.Visible(ctx, u.UserID, after, paging.DefaultLimit+1)`, `u` being the `identity.Caller` of the request and `after` the name the request's `page` decodes to or empty, showing the first `paging.DefaultLimit` and setting `Next` to the page's own token over the last name shown when the extra site came back; for a before-token or `last` it is `s.VisibleBefore(ctx, u.UserID, before, paging.DefaultLimit+1)`, `before` being the name the token decodes to or, for `last`, empty, answering the redirect to `/` when fewer than `paging.DefaultLimit+1` sites came back and otherwise showing the first `paging.DefaultLimit` of them reversed; a row being the user's own when `Owner` equals that user id and published when `Commit` is not empty; a site path is `s.BySlug(ctx, slug)`, its `Visibility` compared with `store.Private` and its `Commit` and `PublishedPath` naming the tree; the apex host is `s.Apex(ctx)` and the site's `Slug`. Each answers `store.Unreachable` and a newline, as plain text with status `503`, for an error matching no sentinel.

A test opens a handle with `db.Open(ctx, db.Config{Path: filepath.Join(t.TempDir(), "state", "sites.db"), Migrations: sites.Migrations()})` and builds a store with `store.New(d, store.Config{Now: clock, Rand: bytes.NewReader(known)})`; creates with `s.Create`, reads back with `Find`, `BySlug`, `List`, `Visible` and `VisibleBefore` with positions and windows of its choosing, and `Taken`, reads a row's `listed` inside `d.Read` after a write, publishes, updates and deletes, sets and clears the apex, and closes the handle and opens another on the same path to see the same sites.
