# D01-layout-and-run-seam

sites is the suite's static site host: one Go binary that serves each site at `/<slug>/` on `sites.<space>` from a tree it unpacks with the host's own `git archive` out of one of repos' bare repositories, redirects the space's apex host to the apex site, offers seven MCP tools at `/mcp` (`list`, `show`, `create`, `publish`, `update`, `delete`, `apex`), keeps its catalog of sites and the apex setting in its own SQLite database, `state/sites.db`, keeps the unpacked trees under `cache/sites/`, and serves a landing page at `/`, an about screen at `/about` and a tools page at `/tools` to a signed-in user. This design is the structural ground the other designs stand on: where the code lives, which package owns which concern, the seam through which the process is run so that the command, the server, the pages, the store, the cache, the limits, the site paths and the tools can be tested without a real process, the settings and how they are read, the paths, the migrations that give the catalog its schema, where the version it shows comes from, and the one binary's wiring. `D02-cli` declares the exit codes, the usage text and the manifest and states what `Run` does with arguments; `D03-serve` states the serve path `Run` follows with none; every other package's names are declared by the document that owns that package, listed below.

The module is `github.com/ikigenba/ikigenba/sites`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/sites`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/sites` is wiring only.

## The dependencies

sites depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required by a released version with no `replace` directive. The SQLite driver, the pure-Go one that keeps the release build cgo-free, arrives through appkit's `db` package; sites never imports it. Which release is data that `AGENTS.md` and `go.mod` hold; no requirement names one. It runs one program, the host's `git`, which `AGENTS.md` declares in the toolchain and opsctl provisions on a host; sites links no git library.

appkit is a sibling reached only through its published packages, and sites uses seven of them: `db` (below), `version` (below), `services` (the services file, for the `sites` and `auth` entries the addresses are built from), `page` (the banner and footer, the font preload link and `page.PreloadURL()`, the template set the five templates are parsed into, and the shared static files), `identity` (`Require` on `/mcp`, `Optional` everywhere else, so a guest reaches a site with no identity headers), `mcp` (the server mounted at `/mcp` and the client the tests drive it with), and `telemetry` (the event, the request middleware, the writer, the socket sink and the capturing sink tests use). appkit's page, identity, MCP, services, telemetry, db and version designs own their contracts; sites restates none.

`github.com/ikigenba/ikigenba/appkit/db` is the suite's one way to keep a SQLite database. `db.Open` opens or creates the database at an ordinary file path, creating its missing directories, applies the migrations it is given that the database has not had, stamping each with the clock it is given, and refuses a database it cannot open; over a database that records a migration it was not given, one a newer binary upgraded, it applies nothing, writes one warning line beginning with the `Config.Service` it is given to the `Config.Stderr` it is given, and opens it all the same; `DB.Read` runs a read-only transaction and `DB.Write` a transaction on the one writer, so writes are serialized by the handle and sites keeps no lock of its own; `DB.Close` closes the handle; `DB.SetFailing` makes a handle fail every transaction until it is turned off, which is how sites' tests make the catalog fail; and `db.Status` writes, changing nothing, which migrations a database has had and which it has not, the ones it was not given among them, and returns nil over a database a newer binary upgraded. The journal mode, the busy timeout, the reader pool and the writability probe are appkit's too. All of that is appkit's contract (its D15 and D16): sites restates none of it, and its tests re-prove none of it.

`github.com/ikigenba/ikigenba/appkit/version` is the code identity the host gives every app: `version.Read()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment at the time of the call and returns the **identity**, a `version.Identity` holding a `Release` and a short `Commit`, each empty when its variable is unset; the identity's `String()` is the **display string** built from the two, the empty string when neither is set, and `version.Display()` returns that same string. How both are built is appkit's contract, and sites' tests do not re-prove it. sites carries no version of its own: nothing in its source or its build names one.

repos is reached only through the on-disk layout it publishes for siblings — one bare repository per repository at `<REPOS_DIR>/<rep id>.git`, whose `HEAD` names `refs/heads/main` and whose own config holds the `ikigenba.*` keys — read with the host's `git` as git's manual documents it. sites never names a path inside repos' tree, never calls repos over HTTP, and never writes under `REPOS_DIR` (`D05-git-and-cache`).

## Where the environment is read

`main` makes the one read of the environment that is not `Run`'s own: it calls `version.Read` exactly once, first, and holds the result, the identity. It hands the identity to `page.New`, whose banner carries its `Release` and `Commit` to the footer of every page and to the about screen, and the identity's display string, `id.String()`, to the `mcp.ServerConfig` its `Process.MCP` builds and to `Run` as `Process.Version`, which `Run` writes for `--version` and gives the run's writer as its `telemetry.Config.Version`. Nothing below `main` calls `version.Read` or `version.Display` or looks up `IKIGENBA_COMMIT` or `IKIGENBA_RELEASE`, so a test of `Run` hands it any string as `Version`, the empty string included, and sets no variable; one start of the binary reads the two variables once, and so does a `--version`, which is a run of its own. With neither set the identity is zero and the display string empty, and sites starts and serves all the same.

`Run` reads every variable through `Process.LookupEnv`: the three numbers and `REPOS_DIR` once at start, through `settings.Read`; `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness (`D03-serve`); `PATH`, where `git` is looked for (`D05-git-and-cache`); and `IKIGENBA_SERVICES`, once, when it starts to serve, whose value it hands on as the services path that the handler, the pages and the tools read afresh whenever they need the file. A broken or absent services file never stops a start; it reads as a file that lists no services. `Process.Environ` is the whole environment every `git` sites runs is started with, so a test composes the git environment `AGENTS.md` asks for (its own `HOME`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL`, `GIT_TERMINAL_PROMPT=0`, a `PATH` holding git's directory) and hands it to `Run` without touching the real environment; git honours those variables as git(1), "ENVIRONMENT", documents.

Three readers of `IKIGENBA_SERVICES` sit outside the seam, all appkit's: `page.New` and `mcp.NewServer` read the real environment when they are called, and the socket sink reads it on every delivery. So `main` calls `page.New` once and puts in `Process.MCP` a function that calls `mcp.NewServer` with `Instructions` nil, so a client's instructions are sites' description read afresh from the services file; and the socket sink is what a nil `Process.Sink` means, used only by the binary, while a test of `Run` names its own sink.

## Packages

The module's root package, `sites`, holds what the module embeds, because Go's `embed` reaches only files at or below the embedding package's directory. It exports `Assets`, a file system holding exactly the five templates from `assets/` — `landing.html`, `about.html`, `tools.html`, `notfound.html` and `unavailable.html` — which `internal/pages` parses into the set `page.Templates()` returns (`D06-pages`); `Etc`, a file system holding exactly `manifest.toml` from `etc/`, through which a test proves the file the build writes is `cli.Manifest`'s copy (`D02-cli`); and `Migrations`, a file system holding exactly the migrations from `migrations/`. sites ships no nginx fragment, so `Etc` holds nothing else. Nothing else lives at the root.

The catalog's schema is a sequence of migration files, each named with a four-digit version, that the binary carries and appkit's `db` applies in order. This sites carries one, `0001_catalog.sql`: the schema sites has always created, its `sites` and `settings` tables (`D04-store` declares them), written so that it creates each table only if it does not exist and seeds nothing, so a catalog an earlier sites kept before it recorded migrations is adopted as it is. `Migrations()` is what `Run` hands `db.Open` and `db.Status`, and what a test hands `db.Open` to make a catalog of sites' shape in its own temporary directory; it is the same on every call and depends on no file beside the binary. A later migration is a new file with the next version; none is ever edited once released.

Thirteen internal packages hold the concerns, one each.

- `internal/cli` owns the program as a command: the run seam (this document), the exit codes, the usage text and the manifest (`D02-cli`), and the serve path (`D03-serve`).
- `internal/server` owns a listener's life: serving a handler and draining for a deadline (`D03-serve`).
- `internal/settings` owns the four values sites reads from its environment at start, their defaults, how each is spelled, and the refusal of one that is not acceptable (this document).
- `internal/limits` owns `SITE_MAX_BYTES` and `OPERATION_SECONDS` as applied, the per-git-run deadline, draining and halting git (`D10-limits`).
- `internal/git` owns finding and running the host's `git` (`D05-git-and-cache`).
- `internal/store` owns the catalog: site records, the apex setting, ids, name and slug rules (`D04-store`).
- `internal/cache` owns repos' repositories as read through git and the trees under `cache/sites/` (`D05-git-and-cache`).
- `internal/urls` owns the addresses built from a request and the services file (`D06-pages`).
- `internal/pages` owns the template set, the five templates' data, `/`, `/about` and `/tools`, `ServiceName` and `Description` (`D06-pages`).
- `internal/visitor` owns the visitor cookie and the referrer host (`D08-visitors-and-trail`).
- `internal/serving` owns site paths and the apex host (`D07-site-serving`).
- `internal/tools` owns the seven MCP tools (`D09-tools`).
- `internal/web` owns the one handler: host classification, the route table, the middlewares and the mounting (`D03-serve`).

Dependencies point one way: `cmd/sites` imports `internal/cli`, `internal/pages` and appkit; `internal/cli` imports the root package, `server`, `settings`, `limits`, `git`, `store`, `cache`, `web` and `pages`; `web` imports `pages`, `serving`, `tools`, `store`, `cache`, `limits` and `urls`; `serving` imports `pages`, `store`, `cache`, `limits`, `urls` and `visitor`; `tools` imports `store`, `cache`, `limits` and `urls`; `pages` imports the root package, `store` and `urls`; `cache` imports `git` and `limits`; `limits` imports `settings`; the root package, `server`, `settings`, `git`, `store`, `visitor` and `urls` import nothing of sites'. Which package imports which is not observable, so this paragraph is guidance.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, and returns the exit code. It is repos' seam: there is no field naming another database, because appkit's `db` takes only an ordinary file path, so the catalog is always `state/sites.db` under `Dir` and a test that needs its own catalog gives `Run` a temporary `Dir`. `Environ` is the environment every git process starts with. `After` is the timer seam for exactly one wait, a git run's `OPERATION_SECONDS`, which ends when a channel `After` returned delivers, so a test fires that deadline when it chooses (`D10-limits`); the drain deadline and the writer's delivery attempts run on real time, because the drain is the one wait `AGENTS.md` lets a test keep to a few real seconds. `Now` is the clock every time sites stamps is read from (a site's `created` and `published`, every event's time, and the time each migration it applies is recorded at). `Rand` is the source of every id sites mints: request ids (through the writer), site ids, unlisted sites' slug suffixes and visitor ids. `Dir` is the working directory the state and cache paths and a relative `REPOS_DIR` resolve against. `Sink` is where the writer delivers: a `*telemetry.Capture` in a test, appkit's socket sink in the binary. `Version` is the display string of the identity `main` read, which `Run` prints for `--version` and records in `service.started`. `Inherit`, `Unsetenv`, `Pid`, `Stdout`, `Stderr`, `Sleep`, `Banner` and `MCP` are as in telemetry and repos.

## Settings

sites reads four values at start, in this order: `DRAIN_SECONDS`, the space's, and the three the manifest's `[env]` declares (`D02-cli`), `SITE_MAX_BYTES`, `OPERATION_SECONDS` and `REPOS_DIR`. The three numbers are spelled as opsctl writes an integer — one or more ASCII digits, no sign, no leading zero, no unit, no white space — and an unset or empty one is its default: 5, 268435456 and 600. sites sets no upper limit: digits beyond what an `int64` holds read as the largest `int64`. `REPOS_DIR` is any string; unset or empty it is `../repos/state/repos`, and it is never refused and never checked at start, since repos may be installed after sites. `settings.Read` returns them as a `settings.Settings`, or the first number that is not acceptable as a `*settings.Error` whose text is what `Run` writes after `sites: `. What the numbers do is `D03-serve`'s (the drain) and `D10-limits`' (the size and time limits).

## Paths

Relative to `Process.Dir` (the process's own working directory when empty, which is how `main` leaves it; `/var/opt/ikigenba/sites` on a host, `<data>/apps/sites/` in a sandbox): the catalog is the SQLite database `state/sites.db`, opened with `db.Open`, `sites.Migrations()` and `Process.Now`, `state/` created when absent; the trees live under `cache/sites/`, created with `cache/` at start and again whenever an unpack needs it, one directory `cache/sites/<site id>/<sha>/` per tree (`D05-git-and-cache`). The diagnostics of `D03-serve` name these paths in this relative form whatever `Dir` holds. `REPOS_DIR` is resolved once, at start: a relative value is joined to `Dir`, so the default is `/var/opt/ikigenba/sites/../repos/state/repos`, which is `/var/opt/ikigenba/repos/state/repos`, on a host, and `<data>/apps/sites/../repos/state/repos`, repos' own directory, in a sandbox; an absolute value is used as it is. A repository `<rep id>` is then the directory `<REPOS_DIR>/<rep id>.git`, looked for afresh whenever a tool or a site request needs it. sites writes nothing outside `Dir`.

## The version

`internal/cli` declares no version. What sites shows of the code running comes from the one identity `main` reads with appkit's `version.Read`. The footer of every page and the about screen's version carry its `Release` and then its `Commit`, through `page.New(pages.ServiceName, id)`, `id` being that identity, as appkit's `footer` and sites' `about` template draw them from the banner. Its display string, `id.String()`, is what `sites --version` prints (`D02-cli`, through `Process.Version`), the MCP `serverInfo`'s version (through `mcp.ServerConfig.Version`), and `service.started`'s `version` (through `Process.Version` and the run writer's `telemetry.Config.Version`). Their values are data the host supplies at run time, never a requirement's: the binary's requirements compare with what `version.Read` and `version.Display` return under the same two values (R-MCTV-AGJI, R-W4OI-ROHH), so no test spells a version.

## Decisions

- `Process` is repos' seam, with no database source of its own: the catalog's path is fixed under `Dir`, since appkit's `db` admits no in-memory database; `After` serves the one wait sites has on its clock, a git run's `OPERATION_SECONDS`.
- `settings.Settings` carries `ReposDir` unresolved, exactly as the environment gave it; `Run` resolves it against `Dir` once, at start, and never checks it there.
- The start order, the settings refusal's diagnostic, what exists when `READY=1` is sent, and that a broken services file never stops a start are `D03-serve`'s; this document adds only what they leave open: where the catalog, the trees and the repositories are, that a running sites writes nothing outside `Dir`, and that the services file and `REPOS_DIR` are read where `Run` was told at start.
- That a running sites writes nothing outside `Dir` is proved over the test's own temporary tree, the `TMPDIR` every git run is given included; a write to the process's own `os.TempDir()`, which comes from the real environment and not the seam, is outside what a test may observe, and is accepted as unprovable rather than designed around.
- Paths, the services path and the version are proved at `Run` and at the binary, since `main` is not usable: the binary requirements below are what the one exec'ing test of `cmd/sites` proves.

## Consumer tasks

The binary's start: `main` hands `cli.Run` a `cli.Process` whose `Args`, `LookupEnv`, `Environ`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Version` is `v`, the display string `id.String()` of the identity `id` it read first with `version.Read()`, whose `Banner` is the `Banner` method of `page.New(pages.ServiceName, id)`, whose `MCP` returns `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: v, Telemetry: w})`, whose `After` is `time.After`, set explicitly, and whose `Inherit`, `Now`, `Sleep`, `Rand`, `Dir` and `Sink` are left zero; it cancels the context on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name, and exits with what `Run` returns. `Run` reads `settings.Read(p.LookupEnv)`, writes `"sites: " + err.Error() + "\n"` and returns `cli.ExitUsage` when it refuses, and otherwise follows the serve path `D03-serve` states: the socket, `git.Find`, `db.Open` and `store.New`, `limits.New`, `cache.Open` with the trees directory under `p.Dir`, `REPOS_DIR` resolved against it and those limits, `telemetry.New`, `web.Handler`, readiness and the drain.

A test of the settings calls `settings.Read` with a lookup over a map and compares the result with `settings.Defaults()` or the expected `settings.Settings`, or uses `errors.As` to get the `*settings.Error` and compares its `Name`, `Value`, `Unit` and `Error()`. A test of the run seam builds a `cli.Process` with a temporary `Dir`, a `LookupEnv` and an `Environ` over one map holding its git environment and its settings, an `Inherit` returning a listener it bound, a `NOTIFY_SOCKET` it holds, a `Now`, an `After` and a `Rand` it controls, a `Version` string of its own, a `*telemetry.Capture` as `Sink`, a `Banner` from `page.New` and an `MCP` that calls `mcp.NewServer` (having set `IKIGENBA_SERVICES` with `t.Setenv`), calls `cli.Run` with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with `mcp.Client` and raw HTTP, cancels, and inspects `Dir`, the capture and the streams. A test of the root package calls `sites.Assets()`, `sites.Etc()` and `sites.Migrations()` and lists and reads them with `fs.ReadDir` and `fs.ReadFile`. The one test that execs the binary builds `cmd/sites` and runs it in a temporary working directory, composing non-empty `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` into the child's environment and computing the identity it expects by calling `version.Read`, and the display string by calling `version.Display`, after setting the same two values with `testing.T.Setenv`; it also runs `--version` with neither variable in the child's environment and expects exactly one empty line.
