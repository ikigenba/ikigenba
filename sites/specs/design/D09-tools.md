# D09-tools

sites' MCP endpoint is its catalog offered to models: seven tools, `list`, `show`, `create`, `publish`, `update`, `delete` and `apex`, registered on the one `mcp.Server` the handler mounts at `/mcp`. This document is `internal/tools`: what `Register` puts on a server, in that order; what a client sees of each tool in `tools/list` (its name, the description written for a model, its input schema, its output schema where it has one, and its annotations); the argument and result types the package exports; which site a `name` argument names; the rules each tool holds its arguments to, the order it checks them in and the exact words of every refusal; what a success answers and what it changes in the catalog and under `cache/`; the one answer every tool gives when the catalog cannot be reached; and the `kind` and `outcome` of the `tool.called` each call records. `D04-store` declares the names this design behaves through for the catalog (`store.Store` and its methods, `store.Site`, `store.ValidName`, `store.Unreachable`, `store.Public`, `store.Private` and the store's sentinels); `D05-git-and-cache` declares `cache.Cache`, `cache.ValidRepo`, `cache.ValidRef`, `cache.ErrRepositoryMissing`, `cache.ErrNoCommit`, `git.Error` and `git.ErrNotFound`, and states how a repository's owner is read, how a ref is resolved and how a tree is unpacked, pruned and removed; `D10-limits` declares `limits.Limits`, its settings and `limits.ErrTooLarge`, `limits.ErrTimedOut` and `limits.ErrHalted`, and states when a git run is ended; `D06-pages` declares `urls.SiteURL`, `urls.NewContext` and `urls.FromContext`; `D03-serve` declares `web.Config` and `web.Handler`, through which a test asks for a site's path while a publish runs. Every `site.*` event a tool records (its name, its attributes, which outcome records it and in which order) is `D08-visitors-and-trail`'s, and this document restates none of it.

## What is someone else's

Everything around the tools is appkit's or another document's.

- appkit's `mcp` server (appkit's MCP server design) is the transport and the protocol: `/mcp` takes only POST, one JSON-RPC message per POST, one `application/json` answer, no session and no stream; the 2026-07-28 envelope (`resultType`, `_meta`'s `serverInfo`, `ttlMs`, `cacheScope`); the earlier revisions `2025-11-25` and `2025-06-18`, `initialize` echoing or defaulting the revision, `notifications/initialized` answered 202, the same results without the 2026 members, and protocol errors answered 200 on them; the 405 with `Allow: POST` and an empty body for every other method; the malformed-transport checks; `server/discover`'s `supportedVersions` and `capabilities`; and the `instructions` of `server/discover` and `initialize`, read afresh from the services file's entry named after the server, absent when there is none.
- appkit's `AddTool`, `AddRawTool` and schema rule (appkit's MCP tools and MCP schema designs) are the Tool object's members and their order, the annotations each `Effect` gives, the derivation of schemas from Go types, the strict reading of `arguments` with its `invalid arguments:` text, the success result a typed handler's output becomes, the `isError` result a handler's error becomes, and the `tool.called` event for every call that reaches a tool, recorded after whatever the handler recorded, with `duration_us` measured on the writer's clock.
- The server is built by `main` with `pages.ServiceName`, the display string `main` reads (`D01-layout-and-run-seam`) and the writer `Run` builds, and `Instructions` nil, so its `serverInfo` is `{"name":"sites","version":<display>}` and its instructions are sites' description as the services file gives it; that wiring is `D01-layout-and-run-seam`'s and is proved at the binary. Routing exactly `/mcp` to the server (a path beneath it is a site path, `D07-site-serving`), `identity.Require` around it with its 500 for a request without `X-User-Id`, `telemetry.Middleware` with `request.started` and `request.finished`, putting the request's sites URL into its context with `urls.NewContext`, and calling `Register` once with the handler's store, cache, limits and writer are `D03-serve`'s.
- What each store method reads and writes, how ids, slugs and times are minted, and that a method fails while its store is failing, are `D04-store`'s. What the repository's owner, a resolved ref and an unpacked tree are, which git runs and with what environment, and what the cache methods answer, are `D05-git-and-cache`'s; the size limit and the per-run deadline are `D10-limits`'.

Story by story: what S05 tells of `initialize`, of `tools/list` on the earlier revisions and of a server with no services file (no `instructions` member, tools still offered) is appkit's MCP server design, given the server `main` builds with `Instructions` nil, which `D01-layout-and-run-seam` pins at the binary (no `instructions` member without a `sites` entry, R-R02K-R24N); the exact path `/mcp`, a path beneath it answered as a missing site, and the 405 for a browser's GET are `D03-serve`'s (with `D07-site-serving` for the site path); and the 2026-07-28 envelope's `serverInfo` and `server/discover`'s `instructions` for sites are `D01-layout-and-run-seam`'s wiring, proved at the binary, and `D03-serve`'s. This document states the tools those answers carry.

## What a client is told

`list`, `show`, `create`, `publish`, `update` and `delete` are registered with `mcp.AddTool`, so their schemas are derived from the argument and result types this package exports. The schemas are stated here whole, property descriptions included, since a model reads them. Each description is the stories' word for word: a one-line summary, the line the landing page shows beside the tool's name, then a paragraph on how to call the tool. `list` and `show` change nothing and are `mcp.Read`; `create`, `publish`, `update` and `apex` add a site, a publish or a setting that a later call can change back, `mcp.Additive`; `delete` removes a site for good and frees its name, `mcp.Destructive`. That is what the gateway's `describe` reports as each tool's kind and what `tool.called`'s `kind` says.

`visibility` is a plain string in every schema, not an enumeration, so `secret` or `Public` reaches the tool and is refused in sites' own words. Every output schema marks required each member that is always present, since appkit always writes a non-pointer field; `commit` and `published` are pointers, absent before a site's first publish. No output property carries a description.

**`apex` has no output schema.** Its result is `{"apex":<site object>}`, or `{"apex":null}` when no apex is set, as every story shows. appkit's schema rule has no nullable form: a nil pointer field is left out, not written `null`, so a typed `apex` could only answer `{}`. `apex` is therefore registered with `mcp.AddRawTool`, taking `ApexArgs` like any other tool, and its handler builds the wire `Result` by hand, with the same `content` and `structuredContent` a typed success carries. A raw tool carries no `outputSchema` in `tools/list` (appkit's MCP tools design). This is the one place sites departs from S05's listing, which shows `apex` with an output schema describing `apex` as either null or a site object; the departure is recorded here and in `D11-on-a-space`.

## Which site a name names

Every tool but `apex`'s read and clear works for its caller alone. The caller is the `identity.Caller` the handler receives. A `name` argument names the caller's site of that name, as `Store.Find` answers it for the caller's user id. Another user's site, a name no site has, a site's id or slug, and a string `store.ValidName` refuses all name nothing, and are refused alike with `no site named '<name>'`, quoting the value as sent. The caller therefore learns nothing about other users' sites, though their names stay taken for `create`. A string `store.ValidName` refuses is refused without asking the catalog, since no site can have it.

`apex` reads and clears the space's setting for any caller, and answers the apex site's object whoever owns it: this is the one place one user is shown another user's site. Setting the apex needs a site of the caller's own, named as above.

## Rules, order and refusals

A handler is reached only with arguments appkit read cleanly. From there each tool checks its rules in a fixed order, and the first that fails is the whole answer, one line in sites' own words:

- `create`: the name rule (`invalid name '<name>'`); the name not taken by any site, as name or as slug (`a site named '<name>' already exists`); the repository, `rep_` and 16 lowercase hexadecimal digits, whose directory exists and whose `ikigenba.owner` is the caller (`no repository '<repo>'`); the ref, when sent, a string git accepts as a ref name (`invalid ref '<ref>'`); the visibility, when sent, exactly `public` or `private` (`visibility must be public or private`).
- `show` and `delete`: the site.
- `publish`: the site; the repository, whose directory must exist (`repository '<repo>' is unavailable`); the ref, as sent or else the site's own, which must name a commit there (`no commit for '<ref>'`); the unpack, refused when the tree is too large (`site exceeds <SITE_MAX_BYTES> bytes`).
- `update`: the site; that at least one of `visibility`, `listed` and `ref` was sent (`update needs at least one of visibility, listed, ref`); the visibility; the ref; that the apex site stays public (`apex site must be public`).
- `apex`: not `name` and `clear` `true` together (`apex takes name or clear, not both`); the site; that it is public (`apex site must be public`).

A field counts as sent when its member is present and not `null`; appkit reads a `null` optional member as absent. Values are compared exactly as sent, never trimmed or folded.

Wherever git runs (reading the owner in `create`, resolving and unpacking in `publish`), two more refusals can answer: `git took longer than <OPERATION_SECONDS> seconds` when a git run is ended by its deadline, and git's own failure, `git failed`, then one empty line and each line git wrote to its stderr prefixed `> `, or `git failed` alone when git wrote nothing or could not be started. The numbers in the size and time refusals are the limits in force, `Limits.Settings()`' `SiteMaxBytes` and `OperationSeconds`.

**The catalog.** Every tool answers from the catalog, so a tool that cannot read or write it has nothing true to say. It refuses with exactly `cannot reach the catalog; try again later` (`store.Unreachable`), quoting nothing of the underlying error, whenever a store method its answer is made from fails with anything other than the store's verdicts `store.ErrNotFound`, `store.ErrNameTaken` and `store.ErrNotPublic`. A rule that can be decided without the catalog still answers first: the name rule, the ref rule, the visibility rule, update's empty change and apex's both. Such a failure is a **catalog error** (`D04-store`). A test produces it by turning on `SetFailing` on the store's handle after `Register` has the store: before the call, or, for a write that follows successful reads, from a hook the call runs between them, the `limits.Clock.After` the cache calls before each git run (`D04-store`, `D05-git-and-cache`). A call that would change nothing (an `update` sending only current values, an `apex` set to the site already the apex, a clear with none set) writes nothing that can fail on its own; its answer is decided by its reads. `tools/list` reads nothing of the catalog and is unaffected.

A refused `create`, `publish`, `update`, `delete` or `apex` has changed nothing in the catalog or under `cache/`. A publish that fails after its tree was unpacked leaves no part of that tree behind. No call writes to a repository. Each call that reaches a tool records one `tool.called` (a `create` or `publish` whose git run was halted or ended with its request's context excepted: it answers nothing and records nothing, `D03-serve`), `outcome` `ok` for a success and `error` for a refusal in sites' words. A refusal of the arguments as appkit reads them records `invalid_arguments` with `duration_us` 0. Which `site.*` events a call records is `D08-visitors-and-trail`'s.

## What a success answers and changes

`show`, `create`, `publish` and `update` answer the **site object** (`tools.Site`): `id`, `name`, `slug`, `url`, `repo`, `ref`, `visibility`, `listed`, `commit`, `created`, `published`, in that order, with `url` = `urls.SiteURL(base, slug)` for the sites URL the request's context carries, the times RFC 3339 UTC to the second, and `commit` and `published` absent while the site is unpublished. `list` answers `{"sites":[...]}` (`tools.SiteList`), one `tools.ListedSite` per site the caller owns, by name: `id`, `name`, `slug`, `url`, `visibility`, `listed`, `commit`. `delete` answers `{"deleted":true,"id":"<id>"}` (`tools.Deleted`). `apex` answers `{"apex":<site object>}` or `{"apex":null}`.

`create` adds one site, owned by the caller, `ref` `main`, `visibility` `public` and `listed` `true` unless sent, unpublished; it reads only the repository's owner and unpacks nothing. `publish` resolves the ref sent, or the site's own, unpacks that commit's tree, points the site at it with a new `published` time, keeps the stored ref, and leaves exactly that one tree under the site's directory, beside only the staging of unpacks of that site still running (`D05-git-and-cache`); publishing the commit the site already has succeeds again. The repository's owner is not checked again. `update` sets the fields sent and nothing else, never the name, the slug or the published commit, and runs no git. `delete` removes the record and the site's directory under `cache/sites/` (all but the staging of unpacks of that site still running, `D05-git-and-cache`), and clears the apex when the site was it. `apex` with `name` sets the apex, with `clear` `true` clears it, and with neither reads it; whichever it does, it leaves everything under the trees root as it was, the replaced apex site's directory included, and every site record is as `D04-store` keeps it.

**Which calls run git.** Only `create`'s owner read and `publish`'s resolve and unpack run git. `list`, `show`, `update`, `delete` and `apex` never do, whatever they answer, and neither does a `publish` refused at its site or its repository, before any ref is resolved. A test sees this at the seam the limits give: every git run calls the `After` of the cache's `limits.Clock` before it starts (`D10-limits`, `D05-git-and-cache`), so such a call makes no `After` call. **A publish is atomic.** The catalog keeps the site's old commit and `published` until the new tree is wholly unpacked, so until then every request for the site is answered from the old commit, with the old `ETag`; a test sees this by reading the catalog and asking for the site's path from inside the clock's `After`, which the publish calls before each of its git runs, and from inside the cache's `Unpacked` hook, which it calls once the new tree is whole and before it is installed (`D05-git-and-cache`). A publish that fails leaves the site's commit, its `published` and what its path answers as they were.

## Decisions

- Output schemas mark required every member that is always present (house style); the stories leave it open.
- A `name` that `store.ValidName` refuses is answered `no site named '<name>'` by `show`, `publish`, `update`, `delete` and `apex` without reading the catalog, so the answer holds when the catalog cannot be reached.
- With the catalog unreachable, a rule decidable without it answers before the catalog refusal, even when a catalog check comes earlier in the order (`update`'s site check before its visibility rule).
- Any failure of a git run other than its deadline and the size limit (a git that exits non-zero, a git that cannot be started, a failure writing the tree) is answered with git's failure text, which is `git failed` alone when there is no git stderr to quote. A `create` or `publish` whose git run was halted, or ended because its request's context ended (the client left, or `D03-serve` cut it off at the drain deadline), answers nothing and records nothing: appkit's server records `tool.called` once a handler returns or panics and records none for a `tools/call` answered with no result, so the handler never returns; it ends its goroutine without returning (as `runtime.Goexit` does), which a test sees deterministically by running `ServeHTTP` in a goroutine of its own and noting, in a deferred function, that the call never returned. This depends on appkit's mcp server as it now behaves, which its design does not promise: that a tool's handler runs on the goroutine of the server's `ServeHTTP`, and that `tool.called` is recorded after the handler returns and not from a deferred function, so a goroutine ended without returning records none. appkit's mcp design should come to state both; until it does, a change there can break this without breaking any appkit test.
- A publish whose catalog write fails after its tree was unpacked removes only what its own `Unpack` installed: the tree at `cfg.Cache.Dir(i, h)`, and only when nothing was at that path before the call, and the site directory when the call created it; so the catalog refusal leaves `cache/` as it was.
- A publish or delete whose catalog write succeeded answers success even when the `Prune` or `Remove` after it fails, since the catalog has already changed; the entries left behind go at the site's next `Prune` or `Remove`.
- A failed catalog write after successful reads in `update`, `delete` or `apex` answers `store.Unreachable` like any other catalog error, but none of them runs git, so no declared hook runs between their reads and their write and no test can reach that state; R-X9DB-P64F states the later-use case only for `create` and `publish`.
- `apex` is a raw tool with no output schema (above), and the apex result type is not exported: a test reads `apex`'s `structuredContent` with its own type around `*tools.Site`.

## Consumer tasks

The handler registers the tools once when it is built, `tools.Register(cfg.MCP, tools.Config{Store: cfg.Store, Cache: cfg.Cache, Limits: cfg.Limits, Telemetry: cfg.Telemetry})`, on the server `mcp.NewServer` returned for that writer, and mounts that server at `/mcp` inside a wrapper that sets `urls.NewContext(ctx, urls.SitesURL(r, servicesPath))` (`D03-serve`).

A model, through the gateway's `call`, lists the seven tools, reads its sites with `list` and `{}`, and one with `show` and `{"name":"blog"}`; through `mutate`, it makes one with `create` and `{"name":"docs","repo":"rep_8c21d4e0f7a3b915"}`, puts it on the web with `publish` and `{"name":"docs"}` (or `{"name":"docs","ref":"v1"}` for one publish from a tag), unlists it with `update` and `{"name":"docs","listed":false}`, makes it the apex with `apex` and `{"name":"docs"}`, and removes it with `delete` and `{"name":"docs"}`. A refusal's text tells it what to fix (`invalid name 'My Docs'`, `visibility must be public or private`), that the thing is not there (`no site named 'wiki'`, `no repository 'rep_0a0b0c0d0e0f1a2b'`, `no commit for 'nope'`), or to try again later (`cannot reach the catalog; try again later`).

A tools test sets `IKIGENBA_SERVICES` with `t.Setenv` to the empty string; finds git with `exec.LookPath` and builds `git.Find(path, environ)` with its isolated git environment; makes bare repository fixtures under a temporary repositories directory with `ikigenba.owner` set and commits with fixed dates; opens `db.Open(ctx, db.Config{Path: ..., Migrations: sites.Migrations()})` over a temporary file and builds `store.New(d, store.Config{Now: ..., Rand: ...})` over it with a fixed clock and a seeded random source; builds `limits.New(s, limits.Clock{After: ...})` from `settings.Defaults()` with a small `SiteMaxBytes` where it needs one; opens `cache.Open(cache.Config{Root: ..., Repos: ..., Git: g, Limits: l})`; builds a writer with `telemetry.New(telemetry.Config{Service: pages.ServiceName, Sink: capture, Now: ...})` over a `*telemetry.Capture`; builds `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: v, Telemetry: w})` for a version string `v` of its own; calls `tools.Register(srv, tools.Config{Store: st, Cache: c, Limits: l, Telemetry: w})`; and serves the server on loopback inside a wrapper that adds `urls.NewContext(ctx, "https://sites.sbx.ikigenba.dev")`, inside `identity.Require`, inside `telemetry.Middleware` over the same writer. It drives it with `mcp.NewClient(mcp.ClientConfig{Endpoint: ...})`: `ListTools(ctx, identity.Caller{UserID: "u_7f3a9c21"})` for the seven `mcp.ToolInfo`, whose `Name`, `Description`, `InputSchema`, `OutputSchema` and `Effect()` it asserts; `CallTool(ctx, caller, "create", args)` with `args` the `json.Marshal` of a `tools.CreateArgs`, or literal bytes such as `{"name":3,"clear":"yes","site":"blog"}` for `apex`; it reads each `mcp.Result` through `MarshalJSON`, decodes `structuredContent` into `tools.Site`, `tools.SiteList` or `tools.Deleted`, and compares the members, in order, and the one text block. It reads the catalog back with `Store.Find`, `Store.List` and `Store.Apex`, the trees by walking `cache.Config.Root`, and the repositories by walking their directories; it resolves the expected sha with its own `git rev-parse`. It makes a git run time out by handing `limits.Clock.After` a channel that has already delivered, makes git fail by damaging an object in a fixture, makes git unstartable by finding it through a symbolic link in its own directory and removing that link, makes the catalog unreachable with `SetFailing(true)` on the store's handle, before the call or from its `After` once the call's reads are done; and makes an unpack fail without git failing by publishing a commit whose tree `git mktree` made hostile, or by removing the write permission of `cache.Config.Root`, or of the site's directory under it, before the call. It calls `Writer.Flush` and reads the `Capture` for `tool.called`. No fixture, name, argument or expected text in such a test has the shape of a requirement id.
