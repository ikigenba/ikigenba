# D06-pages

What sites draws as HTML and the addresses it draws with: the packages `internal/urls` and `internal/pages`; the four human-authored templates `landing`, `about`, `notfound` and `unavailable`, the data each receives and the hooks each emits; the handler that answers `/` and `/about` — the landing page and the about screen for a signed-in user, the sign-in redirect for a guest, the refusal of any other method, while the plain-text answer when the landing page cannot read the catalog is `D03-serve`'s; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the names this design behaves through outside its two packages: the root package's `Assets`, and the run seam whose `Banner` the binary sets to the `Banner` method of `page.New(pages.ServiceName, v)`, `v` being the display string `main` reads (`D01-layout-and-run-seam`). `D04-store` declares `store.Store`, its `Visible` method, `store.Site` and `store.Unreachable`; `D03-serve` declares `web.Handler` and `web.Config` and owns the route table, the host classification (gateway host or apex host), the identity middlewares (`identity.Optional` around `pages.Handler` and the shared files), the trail every request records, and that nothing reaches standard error while telemetry takes every event. Which answers of a site path or of the apex host carry the not-found or unavailable page, with which status and headers, is `D07-site-serving`'s; the visitor cookie and every `site.*` event are `D08-visitors-and-trail`'s; the seven tools' names and descriptions, whose first lines the landing template carries, are `D09-tools`'. Tests of this design carry those documents' ids where they exercise those rules.

## Addresses

`internal/urls` builds every address sites writes into a page, a redirect or a tool's answer, from the request and the host's services file. Every function that takes a services path reads the file afresh through appkit's `services.Read` (appkit's services design) on every call, so a rewrite shows on the next request, and treats a file it cannot read — no path, no file, not a services file — as listing nothing, writing nothing about it. The **scheme** of a request is its first `X-Forwarded-Proto` value in lower case when that is `http` or `https` in any letter case, and `https` for anything else, an absent header included.

`SitesURL` is `<sites-url>`, the address every site answers under: the `url` of the services file's entry named `sites` with one trailing `/` dropped, and, with no such entry or an empty `url`, the scheme, `://` and the request's `Host` exactly as it arrived, port kept, since that is the address the browser just used. `SiteURL` joins it and a slug into `<sites-url>/<slug>/`, the URL the landing page links and `show` returns. `ApexBase` is the same entry's `url` less one trailing `/`, and otherwise the scheme, `://sites.` and the apex request's `Host`, port kept; `D07-site-serving` builds the apex redirect from it. `NewContext` and `FromContext` carry one request's `<sites-url>` in a context, so the tools `D09-tools` registers, which see no request, build the same URLs as the landing page.

auth's profile and sign-out links come from the services file's entry named `auth`: its `url` followed by `/` and by `/logout`. With no such entry or an empty `url`, the space is read from `Host`: a trailing `:` and port digits are dropped, then one leading `sites.` label, so `Host: sites.sbx.ikigenba.dev:443` gives `https://auth.sbx.ikigenba.dev/`. The sign-in redirect reads the space differently, as the stories fix it: only the leading `sites.` is dropped and the port is kept, and it never consults the services file. Its `Location` is `<scheme>://auth.<space>/?return=` followed by `<scheme>://<Host><request URI>` escaped with the standard library's `url.QueryEscape`, which is how the stories' examples encode the return URL. auth's sign-in address is fixed by sites' own stories (`S03`, `S12`), since no published auth design is available to cite.

## The template set and its data

The four templates are the files of `assets/`, embedded by the root package and returned by `Assets()`. `pages.Load` builds **sites' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; the code adds no template function and writes no markup of its own. `Set.Write` is the one way any handler sends a page: it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set first (a `Cache-Control`, a `Retry-After`, a visitor cookie) and sets nothing else, so a page answer carries no `ETag` unless its caller adds one. A `HEAD` gets the status and headers and no body. What `Write` does with a name the set does not define, or data of another type, is not contract.

Each template's data is a named struct whose fields are exactly those its opening comment names. `LandingData` carries the banner, `<sites-url>` and the rows; a `SiteRow` carries a site's slug, name, URL, visibility, whether it is listed, whether a commit is published, and whether the caller owns it — and nothing else, so no site's id, repository or commit can reach the page. `AboutData` carries the banner and `pages.Description`, the manifest's one-line description, so the about screen says the same with or without a services file. `NoticeData` carries only a banner, from which the not-found and unavailable pages draw appkit's footer, `sites <display>`, `<display>` being the banner's `Version`, which in the binary is the display string and may be empty; they draw no banner, because a guest may see them, and `D07-site-serving` builds that banner with an empty `page.User`. The banner and what it holds, in order — the mark showing the favicon, the product name `Ikigenba` and the service, sites' own icon before its name when the `page.Banner` carries one and its name alone otherwise; the launcher button after the mark; the profile link titled with the email; the sign-out form around an icon button with no text of its own, labelled and titled `Sign out` — the launcher's entries in the file's order, a switched-off service titled `<name> is unavailable`, sites' own entry marked current, and the icon in the mark, which the kit's `Banner` takes from the entry it marks current and leaves empty when it marks none, are appkit's output (its page banner and page templates designs); this design states which data a page is drawn with, and one binary-level requirement proves that the binary's banner source is appkit's kit reading the services file. Over a services file that lists sites with an icon, that kit marks sites' entry current and so shows sites' icon in the mark; the exec'ing test's services file gives every entry, `sites` included, an icon (R-66QV-EPPN), so its banner carries that icon in the mark as well as in the launcher, and the strings that requirement keeps out of every icon keep its counts true with the icon in both places.

## The pages handler

`pages.Handler` answers `/` and `/about`; `D03-serve` routes those two paths of the gateway host to it inside `identity.Optional`, and a test wraps it the same way. The method is looked at first: anything but `GET` and `HEAD` is refused 405 with `Allow: GET, HEAD` and an empty body, a guest's request included. A guest — a request whose `X-User-Id` is absent or empty, whatever `X-User-Email` it carries — is then sent to sign in with `302` and `Location: urls.SignIn(r)`; the body is not fixed. A signed-in user gets the page. The landing page reads the catalog through `store.Visible` for the caller's `UserID`, which returns every listed site and that user's own unlisted ones by name (`D04-store`); what `/` answers when that read fails, the 503 catalog refusal, and that the about screen is still served with the store closed, are `D03-serve`'s. The guest redirect and the 405 read no catalog, so they are the same with the store closed. No page reads a repository or runs git — `pages.Config` holds neither — and no answer sets a cookie (`D08-visitors-and-trail`, R-RDFN-99RW). The banner source is called once for each page drawn, with the **banner user**: the caller's `X-User-Email` as it arrived and auth's two links.

## Reading the page

The tests have no HTML parser, since none is an approved dependency, so this design fixes the hooks the templates' opening comments name and the visible text the stories quote, and defines how each is read with the standard library: start and end tags, attributes read left to right, with or without a value, an element's content, and normalisation (tags removed, character references unescaped, whitespace collapsed). Rules about a page's own markup are read over its **written markup**, the body with appkit's banner and footer taken out, since those are appkit's output. The hook requirements are stated for a **plain page request** and a **plain notice banner**, whose inputs carry nothing escaping would change; the byte-for-byte requirements cover every other input, so `html/template`'s contextual autoescaping is what keeps a caller's or the services file's bytes from becoming markup. A hook a template lacks is an issue for a human, never a change to the asset. The icon appkit's mark shows is the `page.Banner`'s `Icon`, the services file's SVG inserted verbatim as the launcher's icons are; a banner the kit returns carries as its `Icon` one of its `Services`' icons, or nothing when it lists none, so the conditions a requirement puts on the launcher's icons, or its banner's having no services, hold of the mark's icon too, and a test's banner source keeps to the same rule. The mark's favicon is an `img` inside the appkit banner, so it is not the page's icon link, which the written markup carries.

## The head every page carries

Every page sites draws — the landing page and the about screen, and the not-found and unavailable notice pages — carries the same six things before its body: a `title`, one stylesheet link to `/_appkit/theme.css`, one font preload link, which has the browser fetch upright Inter, the face nearly all the page's text is set in, before the stylesheet asks for it, one icon link to `/_appkit/favicon.svg` typed `image/svg+xml`, the suite's favicon, one deferred script loading `/_appkit/feedback.js`, appkit's button-feedback script, and the phone-width viewport, `width=device-width, initial-scale=1`. The head is the template's, not appkit's: a page opts in to the feedback script by linking it, as it links the stylesheet, and the appkit banner does not load it, so the notice pages, which draw no banner, link it all the same; the favicon is likewise the template's own link, never the banner's. The preload link is the one head element appkit draws: the font's URL carries a hash of its bytes that sites never writes, so each of the four templates — `landing.html`, `about.html`, `notfound.html` and `unavailable.html`, all parsed into appkit's set — invokes `{{template "preload"}}` in its head, beside its stylesheet link, and appkit's `preload` template renders the link, with `rel` `preload`, `as` `font`, `type` `font/woff2`, a bare `crossorigin`, and `page.PreloadURL()` as its `href`. sites draws no page from a template outside that set, so none uses appkit's `preloadURL` function instead. What the preload does in a browser is a browser's, so what is fixed is that link's attributes; it sits in the written markup, since only the banner and footer are taken out. Which icon a browser shows is the browser's, so what is fixed is the `link` start tag in the head, its `rel`, its `type` and its `href`. What the script does in a browser — press feedback on buttons — is appkit's and needs a JavaScript engine the gates do not have, so what is fixed is the hook a standard-library test can see: the `script` start tag in the head, its `src` and its `defer`, which a page writes bare. A page carries no script of its own: the only `script` start tags its own markup holds are the feedback script's, whose `src` names a path on sites' own host, and the launcher's script sits in the appkit banner. The files a site publishes are the site's own and are relayed as they are (`D07-site-serving`); none of this reaches them.

## The shared files

The stylesheet, its three fonts, the launcher's script, the button-feedback script, the favicon and the two licences are the platform's shared files: appkit's `page` package embeds them and `page.Static()` serves them under `page.StaticPrefix`, `/_appkit/`. sites holds no copy and reads nothing from disk for them, since `page.Static()` answers from files embedded in the binary whatever the working directory (appkit's page static design); `D03-serve` hands every gateway request whose path is an appkit path to that handler unchanged, under `identity.Optional`, so a guest gets exactly what a user gets, and states that delegation. The requirements here restate what `S04` fixes about the answer as sites' own behaviour, so sites' tests fail if a different appkit release stopped giving it. They agree with appkit's page static design.

Six shared files are named by a fixed name: `/_appkit/` followed by `theme.css`, `launcher.js`, `feedback.js`, `favicon.svg`, `OFL.txt` or `TABLER-LICENSE.txt`. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit, and a font path with its hash taken out, answer 404. sites never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads, and the names the served stylesheet gives in its `url("…")` values ending in `.woff2`, each beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet sites serves. A font path's 200 and 304 carry `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again; every other shared file's carry `Cache-Control: no-cache`, so a browser keeps its copy but asks each time.

Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`.

## Decisions

- The pages handler reads the caller from `identity.FromContext` as `identity.Optional` sets it, so its behaviour is stated for `identity.Optional(pages.Handler(cfg))`; the banner user's email is the request's first `X-User-Email`, which `Optional` carries unaltered for a signed-in user.
- The template data types are named structs (`LandingData`, `SiteRow`, `AboutData`, `NoticeData`), not maps, so `D07-site-serving` and tests construct the same values.
- `Set.Write` sets only `Content-Type`; every other header of a page answer is its caller's.
- The HTML reading vocabulary (tags, attributes, element content, normalisation, visible text) is defined here once and may be used by any sites document that reads a page.
- The space for auth's links drops a trailing port and the sign-in space keeps it, as `S03` and `S12` each fix; both strip a leading `sites.` compared ASCII case-insensitively and only when something follows it.

## Consumer tasks

`web.Handler` calls `pages.Load()` once, when it is built, and builds `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: path, Store: cfg.Store})` and serves `/` and `/about` with it inside `identity.Optional`, and every gateway-host path beginning with `page.StaticPrefix` with `page.Static()`. Serving a site path, `D07-site-serving` answers a missing page with `set.Write(w, r, http.StatusNotFound, "notfound", pages.NoticeData{Banner: cfg.Banner(page.User{})})` after setting its own `Cache-Control`, and a failed rebuild with `set.Write(w, r, http.StatusServiceUnavailable, "unavailable", pages.NoticeData{...})` after `Retry-After: 60`; it builds each site's URL with `urls.SiteURL(urls.SitesURL(r, path), slug)`, the private-site redirect with `urls.SignIn(r)`, and the apex redirect from `urls.ApexBase(r, path)`. Before calling the MCP server, `D03-serve` puts `urls.NewContext(r.Context(), urls.SitesURL(r, path))` on the request, and a tool takes the base back with `urls.FromContext(ctx)` and builds `urls.SiteURL(base, slug)`. `cli.Manifest`'s description and the MCP server's name use `pages.Description` and `pages.ServiceName`.

A test of the handler opens a `store.Store` over a temporary database, creates sites in it, writes a services file in its temporary directory, builds `identity.Optional(pages.Handler(pages.Config{...}))` with a `Banner` closure that counts its calls and returns a fixed `page.Banner`, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of sites' template set from `page.Templates()` and `sites.Assets()`, executes `landing` with the `pages.LandingData` it expects — rows from its own `store.Visible` call, URLs from `urls.SiteURL` — and compares bodies byte for byte; it reads hooks with the reading vocabulary below. It calls `SetFailing(true)` on the handle its store was built over to make the catalog unreachable. A test of `urls` calls each function with a request and a services file of its own. A test of the shared files builds `web.Handler` as `D03-serve` states and requests `/_appkit/...` with and without `X-User-Id`, taking the font paths from `page.PreloadURL()` and from the `url("…")` values of the `/_appkit/theme.css` it is served. The one exec test of the binary in `cmd/sites` rewrites the services file between two `GET /` requests.
