# D06-pages

What sites draws as HTML and the addresses it draws with: the packages `internal/urls` and `internal/pages`; the five human-authored templates `landing`, `about`, `tools`, `notfound` and `unavailable` and the data each receives, with the banner trail each page sets; the handler that answers `/`, `/about` and `/tools` — the landing page, the about screen and the tools page for a signed-in user, the sign-in redirect for a guest, the refusal of any other method, the not-found answer to a landing page token it cannot decode, the redirect to the first window when a step back reaches it, while the plain-text answer when the landing page cannot read the catalog is `D03-serve`'s; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the names this design behaves through outside its two packages: the root package's `Assets`, and the run seam whose `Banner` the binary sets to the `Banner` method of `page.New(pages.ServiceName, id)`, `id` being the identity `main` reads (`D01-layout-and-run-seam`). `D04-store` declares `store.Store`, its `Visible` and `VisibleBefore` methods, the visible set, `store.Site` and `store.Unreachable`; appkit's `paging` package (its D25) declares `paging.DefaultLimit` and `paging.Token`; `D03-serve` declares `web.Handler` and `web.Config` and owns the route table, the host classification (gateway host or apex host), the identity middlewares (`identity.Optional` around `pages.Handler` and the shared files), the trail every request records, and that nothing reaches standard error while telemetry takes every event. Which answers of a site path or of the apex host carry the not-found or unavailable page, with which status and headers, is `D07-site-serving`'s; the visitor cookie and every `site.*` event are `D08-visitors-and-trail`'s; the seven tools' names and descriptions are `D09-tools`', and which list `web.Handler` hands the tools page is `D03-serve`'s. Tests of this design carry those documents' ids where they exercise those rules.

## Addresses

`internal/urls` builds every address sites writes into a page, a redirect or a tool's answer, from the request and the host's services file. Every function that takes a services path reads the file afresh through appkit's `services.Read` (appkit's services design) on every call, so a rewrite shows on the next request, and treats a file it cannot read — no path, no file, not a services file — as listing nothing, writing nothing about it. The **scheme** of a request is its first `X-Forwarded-Proto` value in lower case when that is `http` or `https` in any letter case, and `https` for anything else, an absent header included.

`SitesURL` is `<sites-url>`, the address every site answers under: the `url` of the services file's entry named `sites` with one trailing `/` dropped, and, with no such entry or an empty `url`, the scheme, `://` and the request's `Host` exactly as it arrived, port kept, since that is the address the browser just used. `SiteURL` joins it and a slug into `<sites-url>/<slug>/`, the URL the landing page links and `show` returns. `ApexBase` is the same entry's `url` less one trailing `/`, and otherwise the scheme, `://sites.` and the apex request's `Host`, port kept; `D07-site-serving` builds the apex redirect from it. `NewContext` and `FromContext` carry one request's `<sites-url>` in a context, so the tools `D09-tools` registers, which see no request, build the same URLs as the landing page.

auth's profile and sign-out links come from the services file's entry named `auth`: its `url` followed by `/` and by `/logout`. With no such entry or an empty `url`, the space is read from `Host`: a trailing `:` and port digits are dropped, then one leading `sites.` label, so `Host: sites.sbx.ikigenba.dev:443` gives `https://auth.sbx.ikigenba.dev/`. The sign-in redirect reads the space differently: only the leading `sites.` is dropped and the port is kept, and it never consults the services file. Its `Location` is `<scheme>://auth.<space>/?return=` followed by `<scheme>://<Host><request URI>` escaped with the standard library's `url.QueryEscape`. auth's sign-in address is fixed by this design, since no published auth design is available to cite.

## The template set and its data

The five templates are the files of `assets/`, embedded by the root package and returned by `Assets()`. `pages.Load` builds **sites' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `footer` and `preload`; the code adds no template function and writes no markup of its own. `Set.Write` is the one way any handler sends a page: it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set first (a `Cache-Control`, a `Retry-After`, a visitor cookie) and sets nothing else, so a page answer carries no `ETag` unless its caller adds one. A `HEAD` gets the status and headers and no body. What `Write` does with a name the set does not define, or data of another type, is not contract.

Each template's data is a named struct. `LandingData` carries the banner, `<sites-url>`, the rows, the page value that chose them and the tokens for the windows before and after them; a `SiteRow` carries a site's slug, name, URL, visibility, whether it is listed, whether a commit is published, and whether the caller owns it — and nothing else, so no site's id, repository or commit can reach the page. `AboutData` carries the banner and `pages.Description`, the manifest's one-line description, so the about screen says the same with or without a services file; the about screen's version is the banner's `Release` and `Commit`. `ToolsData` carries the banner and the tools as `Tool` values, each a tool's name and description, in the order `pages.Config.Tools` holds them; the pages package reads no MCP server, so a test hands it any list it likes. `NoticeData` carries only a banner, from which the not-found and unavailable pages draw appkit's footer; `D07-site-serving` builds that banner with an empty `page.User`, since a guest may see them. What the banner and the footer hold is appkit's output (its page banner and page templates designs), the footer carrying the banner's `Release` and then its `Commit`, and what a page shows of its data is its template's; this design states which data a page is drawn with, and binary-level requirements prove that the binary's banner source is appkit's kit, made with the run's identity and reading the services file afresh.

## The banner's trail

appkit's banner draws a trail of levels below the app's root, which the app sets on the `page.Banner` the banner source returns, in its `Trail`, before drawing the page; the source itself, appkit's kit in the binary, returns none (appkit's page banner design). sites has two pages below its root, each one level named by its path segment: the about screen sets exactly `{Name: "about", URL: "/about"}` and the tools page exactly `{Name: "tools", URL: "/tools"}`. The landing page is the root and sets an empty trail, replacing whatever the source returned. The not-found and unavailable pages draw no banner, only its footer, since a guest may see them; they are drawn with the banner the source returns for an empty `page.User` (`D07-site-serving`), which carries no trail. The 405, the sign-in redirect and the catalog refusal draw no page at all. A site's own files at `/<slug>/...` are the site's bytes, served with no banner and so no trail. A test proves each level by executing the page's template with data whose banner carries the stated trail and comparing bodies, with a banner source that returns a non-empty trail of its own so that a page which leaves the source's trail in place fails, and by checking that the level's name and URL it expects appear in the body.

## The pages handler

`pages.Handler` answers `/`, `/about` and `/tools`; `D03-serve` routes those three paths of the gateway host to it inside `identity.Optional`, and a test wraps it the same way. The method is looked at first: anything but `GET` and `HEAD` is refused 405 with `Allow: GET, HEAD` and an empty body, a guest's request included. A guest — a request whose `X-User-Id` is absent or empty, whatever `X-User-Email` it carries — is then sent to sign in with `302` and `Location: urls.SignIn(r)`; the body is not fixed. A signed-in user gets the page. The tools page lists `Config.Tools` and reads nothing else, so it is served the same with the store closed. The landing page reads the catalog through `store.Visible` for the caller's `UserID`, which returns one window of the visible set, every listed site and that user's own unlisted ones, by name (`D04-store`). The landing page lists data agents add, so it pages, and navigates, as the suite's listing rule asks (`shape/`, Listing; appkit's D25). `GET /` takes one optional query parameter, `page`, and reads nothing else of the query: a request's **page value** is its first `page` value, empty when it carries none. An empty page value asks for the **first page**, the first `paging.DefaultLimit` sites of the visible set; an **after-token** asks for the **landing window** after the name it holds, the next `paging.DefaultLimit` sites of the visible set whose name is greater in byte order. The handler learns whether more follow the way a paged tool does, by asking `Visible` for one site more than the window, so it never holds more than a window and one row. When more follow, `Next` is the **next token**, the after-token over the name of the last site shown; `Page` is the page value itself, so the template knows whether it draws the first window. What the template draws from `Page`, `Prev` and `Next` — the navigation, its links and when it appears — is the asset's. A window is always `paging.DefaultLimit` sites at most; `limit` is not a page parameter.

The way back and the way to the end read the visible set backwards. A **before-token**, `paging.Token{Tool: "sites-before"}` over one `string`, carried in the same `page` parameter, asks for the window of the `paging.DefaultLimit` visible sites whose name precedes the one it holds, drawn in forward order, whether or not a site still has that name; the checksum appkit's token carries keeps it apart from an after-token, so one value never decodes as both. The **last value**, the literal `last`, asks for the last window: the last `paging.DefaultLimit` sites of the visible set, drawn forward. It is no token's spelling, since appkit's token always carries a four-byte checksum and so never decodes from four characters. The handler reads either from `VisibleBefore` (`D04-store`), asking for one site more than the window, the before-token's name or, for `last`, no bound, and drawing the first `paging.DefaultLimit` it gets back in reverse. When at most `paging.DefaultLimit` sites precede the position, or the visible set holds at most `paging.DefaultLimit` sites in all, the page value is said to **underflow**: the window it names is the first page, and the handler answers `303` with `Location: /`, so the first page keeps one address. The tokens follow from the window drawn. `Prev`, the **prev token**, is empty on the first page and on an empty window reached by an after-token, and otherwise the before-token of the window's first site, on an after-token's window, a before-token's and the last window alike; one more step back from a window that the first page overlaps lands on `/`. On a before-token's window `Next` is the after-token of its last site, the form of every other step forward, and on the last window it is empty, which is how the template knows to draw Last as the current item. `Page` stays the request's value throughout, `last` included, so the template draws First as a link on every window but the first. Stepping Next from the first page to the end and Prev back again visits the same windows in the opposite order; the last window ends with the final window of that walk and equals it when the visible set holds a multiple of `paging.DefaultLimit` sites, since it is always a full window.

The token is the page's own. `shape/`'s Listing entry has a page take the `page` token of the list tool over it, but no tool lists the visible set: `list` answers the caller's own sites (`D09-tools`), not other users' listed ones, so no tool's token names a position in it. The landing page therefore issues its own, `paging.Token{Tool: "sites"}` over exactly one `string`, the name of the last site a window showed, in the same form and refused the same way as a tool's (appkit's D25), and its before-token under that name with `-before` appended, as the entry has a page do with the tool's; that is the one departure from the entry, and the page otherwise follows it. A page value that is not empty, not `last` and decodes as neither token — one edited by hand, one `list` issued, a word such as `bogus` or `Last` — names no window, so `GET /` answers it with sites' not-found page and `Cache-Control: no-cache`, the answer a slug no site has gets (`D07-site-serving`), never quietly with the first window. It is decided after the method and the caller, so a guest is still sent to sign in and any other method still refused whatever the query, and before the catalog is read, so the 404 is the same while the catalog fails. Whether a before-token or `last` underflows is read from the catalog, so the redirect is given only while the catalog answers. What `/` answers when the read fails for a page value it can decode, the 503 catalog refusal, and that the about screen is still served with the store closed, are `D03-serve`'s. The guest redirect and the 405 read no catalog, so they are the same with the store closed, whatever the page value. The redirect to `/` draws no page and calls no banner source. No page reads a repository or runs git — `pages.Config` holds neither — and no answer sets a cookie (`D08-visitors-and-trail`, R-RDFN-99RW). The banner source is called once for each page drawn, with the **banner user**: the caller's `X-User-Email` as it arrived and auth's two links; the not-found page is drawn, as on a site path, with the banner it returns for an empty `page.User`.

## Copy

Every word, class, id and attribute a page carries is its template's, under `assets/`, and no requirement names one; the head every page carries (the stylesheet, the font preload, the favicon, the feedback script, the viewport) is the template's too. A test proves a page by executing the named template with the data this design states and comparing bodies byte for byte, or by checking that a value it supplied is or is not in the body; a **plain page request** keeps such a check's inputs free of anything `html/template`'s escaping would change. A template that cannot show a state this design names is an issue for a human, never a change to the asset.

## The shared files

The stylesheet, its three fonts, the button-feedback script, the favicon and the two licences are the platform's shared files: appkit's `page` package embeds them and `page.Static()` serves them under `page.StaticPrefix`, `/_appkit/`. sites holds no copy and reads nothing from disk for them, since `page.Static()` answers from files embedded in the binary whatever the working directory (appkit's page static design); `D03-serve` hands every gateway request whose path is an appkit path to that handler unchanged, under `identity.Optional`, so a guest gets exactly what a user gets, and states that delegation. The requirements here state the answer as sites' own behaviour, so sites' tests fail if a different appkit release stopped giving it. They agree with appkit's page static design.

Five shared files are named by a fixed name: `/_appkit/` followed by `theme.css`, `feedback.js`, `favicon.svg`, `OFL.txt` or `TABLER-LICENSE.txt`. `/_appkit/launcher.js`, which an earlier appkit served, is not one of them and answers 404 like any other unknown appkit path. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit, and a font path with its hash taken out, answer 404. sites never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads, and the names the served stylesheet gives in its `url("…")` values ending in `.woff2`, each beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet sites serves. A font path's 200 and 304 carry `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again; every other shared file's carry `Cache-Control: no-cache`, so a browser keeps its copy but asks each time.

Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`.

## Decisions

- The pages handler reads the caller from `identity.FromContext` as `identity.Optional` sets it, so its behaviour is stated for `identity.Optional(pages.Handler(cfg))`; the banner user's email is the request's first `X-User-Email`, which `Optional` carries unaltered for a signed-in user.
- The template data types are named structs (`LandingData`, `SiteRow`, `AboutData`, `ToolsData`, `Tool`, `NoticeData`), not maps, so `D07-site-serving` and tests construct the same values.
- The pages handler receives the tools page's list as data, `Config.Tools`, a `[]pages.Tool` that `web.Handler` fills once from the tools server's `Tools()` after `tools.Register` (`D03-serve`), rather than holding the `mcp.Server` itself, so `internal/pages` imports no MCP package and a test of it needs no server.
- `Set.Write` sets only `Content-Type`; every other header of a page answer is its caller's.
- The landing page's token is bound to `sites`, the service's name, since no tool issues it; a `list` token decodes under it only where the two names give it the same checksum (appkit's D25).
- The landing page's before-token is bound to `sites-before`, the page's own token name with `-before` appended, so the two directions share one parameter and neither decodes as the other.
- An underflowing before-token or `last` answers `303` to `/` rather than drawing a short or overlapping first window at a second address; the step back from the second window is such a redirect.
- `last` is a literal word, not a token, since the last window has no position to encode; it is checked before either token, so its meaning never hangs on decoding.
- The landing page's 404 for an undecodable page value is the answer an unknown slug gets, the not-found page with `Cache-Control: no-cache` and no `ETag`, so sites has one not-found answer on its host.
- The space for auth's links drops a trailing port and the sign-in space keeps it; both strip a leading `sites.` compared ASCII case-insensitively and only when something follows it.

## Consumer tasks

A person on the landing page follows its Next link to `/?page=<Next>` and sees the next window, its Prev link to `/?page=<Prev>` and sees the window before, and its Last link to `/?page=last` and sees the last window; First takes them back to `/`, and so does a Prev from the second window, by the redirect. The handler takes a page value of `last` as the last window; otherwise it decodes a non-empty one with `paging.Token{Tool: "sites"}.Decode(p, &after)` and, when that fails, with `paging.Token{Tool: "sites-before"}.Decode(p, &before)`, answering the not-found page when both fail. For an empty value or an after-token it calls `cfg.Store.Visible(ctx, u.UserID, after, paging.DefaultLimit+1)`, sets `Next` to `paging.Token{Tool: "sites"}.Encode(name)` over the last site it shows when the extra site came back, and, for an after-token, `Prev` to `paging.Token{Tool: "sites-before"}.Encode(name)` over the first. For a before-token or `last` it calls `cfg.Store.VisibleBefore(ctx, u.UserID, before, paging.DefaultLimit+1)`, `before` empty for `last`; fewer than `paging.DefaultLimit+1` sites back is the `303` to `/`, and otherwise it shows the first `paging.DefaultLimit` reversed, `Prev` the before-token over the first shown and `Next`, for a before-token only, the after-token over the last.

`web.Handler` calls `pages.Load()` once, when it is built, and registers the seven tools with `tools.Register(cfg.MCP, ...)`, maps `cfg.MCP.Tools()` in order to `[]pages.Tool{{Name: t.Name, Description: t.Description}, ...}`, builds `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: path, Store: cfg.Store, Tools: list})` and serves `/`, `/about` and `/tools` with it inside `identity.Optional`, and every gateway-host path beginning with `page.StaticPrefix` with `page.Static()`. Serving a site path, `D07-site-serving` answers a missing page with `set.Write(w, r, http.StatusNotFound, "notfound", pages.NoticeData{Banner: cfg.Banner(page.User{})})` after setting its own `Cache-Control`, and a failed rebuild with `set.Write(w, r, http.StatusServiceUnavailable, "unavailable", pages.NoticeData{...})` after `Retry-After: 60`; it builds each site's URL with `urls.SiteURL(urls.SitesURL(r, path), slug)`, the private-site redirect with `urls.SignIn(r)`, and the apex redirect from `urls.ApexBase(r, path)`. Before calling the MCP server, `D03-serve` puts `urls.NewContext(r.Context(), urls.SitesURL(r, path))` on the request, and a tool takes the base back with `urls.FromContext(ctx)` and builds `urls.SiteURL(base, slug)`. `cli.Manifest`'s description and the MCP server's name use `pages.Description` and `pages.ServiceName`.

A test of the handler opens a `store.Store` over a temporary database, creates sites in it, writes a services file in its temporary directory, builds `identity.Optional(pages.Handler(pages.Config{...}))` with a `Banner` closure that counts its calls and returns a fixed `page.Banner`, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of sites' template set from `page.Templates()` and `sites.Assets()`, executes `landing` with the `pages.LandingData` it expects — rows from its own `store.Visible` call for the same position, the name the request's `page` decodes to or empty, URLs from `urls.SiteURL`, `Page` the `page` it sent, and `Next` the token over the last row's name only when more than `paging.DefaultLimit` visible sites follow that position, among them a catalog of exactly `paging.DefaultLimit` visible sites and another user's unlisted site sorting after them, and a second window reached by sending the first window's `Next` back as `page` — and compares bodies byte for byte. Over a visible set of more than `paging.DefaultLimit` sites, among them another user's unlisted sites interleaved by name, it walks Next from `/` to the end, then Prev back, expecting each window's sites again in the opposite order and the `303` to `/` from the second window; it sends `page=last` and expects the last `paging.DefaultLimit` sites, ending with the final window of that walk, with an empty `Next`; over a visible set of at most `paging.DefaultLimit` sites it expects `page=last` to redirect; and it sends a before-token encoded over a name no site has, expecting the window of the sites whose names sort before it. It sends a guest's `GET /` with each kind of page value and expects the sign-in redirect. It sends `page=bogus`, `page=Last`, and a token `paging.Token{Tool: "list"}` encoded that both of the page's tokens refuse, with the catalog reachable and failing, and expects the not-found page with `Cache-Control: no-cache`. Its `Banner` closure returns a banner whose `Trail` is non-empty, and it expects `b.Trail = nil` on the landing page, `b.Trail = []page.Level{{Name: "about", URL: "/about"}}` in `pages.AboutData{Banner: b, Description: pages.Description}`, and `b.Trail = []page.Level{{Name: "tools", URL: "/tools"}}` in `pages.ToolsData{Banner: b, Tools: tools}`, `tools` being the `[]pages.Tool` it put in `pages.Config.Tools`, and checks that each tool's name and description it supplied appear in the `/tools` body. It calls `SetFailing(true)` on the handle its store was built over to make the catalog unreachable. A test of `urls` calls each function with a request and a services file of its own. A test of the shared files builds `web.Handler` as `D03-serve` states and requests `/_appkit/...` with and without `X-User-Id`, taking the font paths from `page.PreloadURL()` and from the `url("…")` values of the `/_appkit/theme.css` it is served. The one exec test of the binary in `cmd/sites` rewrites the services file between two `GET /` requests.
