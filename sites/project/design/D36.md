# Decision 36 — Site lifecycle against the version plane: create, delete, slug rotation

**Decision.** A site's life-cycle events are repository life-cycle events. Root
D24 makes it ambient — "creating a site implicitly creates its repository" — so
sites' three structural verbs each carry exactly one plane call, and the
display-name verb carries none. D20 owns what these tools accept and return and
is unchanged in shape; this Decision adds the plane call and fixes its ordering.

| verb | plane call | when |
|---|---|---|
| `create` | `version.Create(ctx, slug, owner)` | always, at every visibility |
| `delete` | `version.Delete(ctx, slug, owner)` (archive) | always |
| `set_visibility` | `version.Rename(ctx, old, new, owner)` | **only when the slug changes** |
| `rename` | none | never — see below |

All three are domain verbs, so they cross repos' MCP surface over loopback
(D32); the `owner` is the **site's** recorded owner, read off the row, not the
acting caller's. On `create` the two coincide because the row is born from the
acting `Identity` — which is why `create` inserts the row before it calls.

**`create`: local first, then the plane, and undo on failure.** The row and the
directory come first for two reasons: the row is what enforces slug uniqueness
(the PK, and the token-collision retry of D20 rides on it), so calling repos
before knowing the slug is actually free would mint repositories for slugs that
turn out to be taken; and the row is where the owner sites asserts comes from
(D32). So: `Store.Create` + `MkdirAll`, then `version.Create`. If the plane call
fails, sites **removes the row and the directory it just made** and returns the
error. A site whose repository does not exist must not exist, because every
subsequent write would fail and its content would live in no history; the failure
is clean and the caller simply retries.

**`delete`: the plane first, then local removal.** Both sides are idempotent, so
ordering is chosen for the failure case: with `version.Delete` first, an
unreachable repos means the site is untouched and the call is a plain retryable
error, rather than a site that has vanished locally while its repository is still
listed. Archiving is repos' business (history is preserved; root D24), and sites
neither knows nor cares that "delete" means "archive" — it makes the same call
either way.

**`set_visibility`: the slug is the repository key, so a re-slug is a rename.**
The plane key is `sites/<slug>` (D32), so every transition that changes the slug
must move the key or the repository would be stranded under a name nothing
addresses:

| transition | slug | plane |
|---|---|---|
| `public` ↔ `private`, slug kept | unchanged | **no call** |
| into `unlisted` (from anywhere, incl. `unlisted`→`unlisted` rotation) | regenerated token | `Rename(old, token)` |
| out of `unlisted` with `new_slug` | caller's slug | `Rename(token, new_slug)` |
| re-asserting the current visibility (idempotent no-op) | unchanged | **no call** |

The rename goes **first**, before `Store.SetVisibility` and `Layout.Move`, for the
same reason as `delete`: repos unreachable then means nothing moved anywhere and
the caller retries. The residual risk is real and worth naming — a rename that
succeeds remotely followed by a local failure leaves the repository under the new
key while the row still holds the old one, and the operator must reconcile it.
That window is one process-local failure wide, and the alternative ordering makes
the *common* failure (repos down) produce the same class of split instead of a
clean refusal.

**`rename` touches the plane not at all.** sites' `rename` changes the **display
name** — a database column, D15/D20 — and never the slug. The repository key is
the slug, so there is nothing to move. This is the one place where sites' verb
name and the plane's operation name collide, and they mean different things: a
site's label is not versioned content and has no repository representation.

**Visibility is not versioned either.** Moving a site between the public and
private trees moves a directory; the repository, its history, and its contents
are identical before and after. Nothing about a repository records which tier
serves it, and nothing should — that is sites' domain fact, held in the row.

**Rejected.**

- **Calling `version.Create` before inserting the row.** It would create
  repositories for slugs that are already taken and for tokens that lose the
  collision retry, and it would make a duplicate-slug `create` — an ordinary user
  error — leave litter in the custodian.
- **Letting `create` succeed when the plane call fails, and repairing later.**
  That is the silent-degradation shape D32 and D33 both reject: the site would
  serve content that no commit ever recorded until someone noticed.
- **Deleting the repository outright rather than calling repos and letting it
  archive.** Not sites' call to make. Root D24 puts the archive/reclaim policy in
  the custodian precisely so no owning service can destroy history by
  implementing delete a little too literally.
- **Keeping the old repository key and storing a mapping when a slug rotates.**
  A second namespace, which the plane's `<kind>/<name>` addressing exists to
  avoid, plus a table sites would have to keep true forever.
- **Creating a fresh repository on every unlisted rotation.** Rotation revokes a
  *URL*; it does not create a new site. A new repository would orphan the site's
  entire history on every revocation — the exact opposite of ambient versioning.
- **Making `rename` (display name) rename the repository.** The names coincide
  and the meanings do not.

**Verification.** (Substrate: hermetic. Driven through the assembled `appkit/mcp`
handler over a temp `SITES_ROOT`, a real migrated SQLite DB, and the
contract-conforming recording repos server of D32.)

- R-FARO-E6HT — **`create` creates the repository, and a plane failure creates
  nothing.** A successful `create(name, slug, "public")` produces exactly one
  recorded `Create` call for that slug; with the repos server made to fail
  `Create`, the same call returns an error envelope, `Store.Get(slug)` yields
  not-found, and `SiteDir(Public, slug)` **does not exist** — the row and
  directory made before the call were undone. An unlisted `create` likewise
  produces a `Create` call for the generated token.
- R-FBZK-RY8I — **`delete` archives before removing, and a plane failure removes
  nothing.** A successful `delete(slug)` produces exactly one recorded `Delete`
  call and leaves neither row nor directory; with the repos server made to fail
  `Delete`, the call returns an error envelope and **both** the row and
  `SiteDir(v, slug)` are still present with the directory's files
  byte-identical. A build that removes locally and then calls repos fails the
  second half.
- R-FD7H-5PZ7 — **a slug change renames the key.**
  `set_visibility(slug, "unlisted")` on a public site produces exactly one
  recorded `Rename` whose old key is the original slug and whose new key is the
  returned 30-char token; a second `set_visibility(token, "unlisted")`
  (rotation) produces a `Rename` from the first token to the second; and
  `set_visibility(token, "public", new_slug:"launch")` produces a `Rename` from
  the token to `launch`. A build that creates a new repository on rotation
  instead of renaming fails (a `Create` call appears where a `Rename` is
  required).
- R-FEFD-JHPW — **no slug change, no plane call.** `set_visibility` from private
  to public with the slug kept, re-asserting a site's current visibility, and
  `rename(slug, "New Label")` each produce **zero** recorded repos requests of
  any kind, while still performing their local effects (the directory moved to
  the other tier for the first, the name changed for the third). A build that
  renames the repository on a tier change, or on a display-name change, fails.
