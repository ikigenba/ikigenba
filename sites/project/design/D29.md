# Decision 29 — The nginx fragment captures the minted correlation id on gated locations and strips it on ungated ones

**Decision.** `sites/etc/nginx.conf` gains one capture-and-forward pair per
**gated** location and one strip line per **ungated** public location, so the
`X-Correlation-Id` reaching the sites process is always trustworthy.

The rule has exactly two halves:

- **Gated locations** (`= /srv/sites/mcp` via `/_authn`; `= /srv/sites/`,
  `/srv/sites/static/`, and `/srv/sites/private/` via `/_session-authn`) capture
  the id the dashboard's introspection endpoint minted and returned on the auth
  subrequest, then forward it — **overwriting** anything the client sent:

  ```
  # bearer-gated MCP endpoint
  auth_request_set $sites_correlation $upstream_http_x_correlation_id;
  proxy_set_header X-Correlation-Id  $sites_correlation;

  # each session-gated location
  auth_request_set $sites_session_correlation $upstream_http_x_correlation_id;
  proxy_set_header X-Correlation-Id  $sites_session_correlation;
  ```

- **Ungated public locations** (`= /srv/sites/.well-known/oauth-protected-resource`
  and the public site tier `/srv/sites/public/`) have no auth subrequest and
  therefore no minted id, so they **erase** the header and let the service mint:

  ```
  proxy_set_header X-Correlation-Id "";
  ```

  An empty `proxy_set_header` value means nginx does not pass that field to the
  upstream at all (see `project/research/research.md`), so the chassis sees no
  inbound id and mints one. This is what makes an id un-injectable from the
  public internet: an anonymous visitor to a public or unlisted site cannot join
  or poison somebody else's chain.

The `$sites_correlation` / `$sites_session_correlation` split follows the
fragment's existing naming (`$sites_owner` on the bearer location,
`$sites_session_owner` on the session-gated ones), and reusing one variable name
across several locations is safe because `auth_request_set` binds per location —
the same property D18 already relies on for the four owner headers. The single
`proxy_set_header X-Correlation-Id` per location is the same per-header identity
hygiene the owner headers use: one set for a name replaces any client-supplied
value for that name on the upstream request.

Nothing else in the fragment moves: the location set, the auth posture of each
location, the `@sites_authn_500` rate-limit re-emit, the `@login_bounce`
opt-ins (D24), the owner-header forwarding (D18/D26), and the literal loopback
port `3004` are all unchanged. The pre-existing fragment ids (D4, D18, D24, D26)
keep asserting that shape and stay true.

**What the fragment can and cannot prove.** The end-to-end promise — that a real
id, minted by real introspection, arrives at the sites process and cannot be
supplied by a public caller — is falsifiable only against a live nginx plus the
dashboard's introspection endpoint, which is a suite-root concern outside
`sites/`. What sites *can* prove is that the shipped fragment says the right
thing, and it already proves exactly that for its routing and identity shape:
`cmd/sites/main_test.go` reads `sites/etc/nginx.conf` from disk and asserts its
content under D4's, D18's, D24's, and D26's ids. The correlation lines extend
those same assertions and are pinned the same way, so the ids below are scoped to
what a content read genuinely shows — the directives are present, on the right
locations, in the right form — and claim nothing about a live chain.

**Rejected.**
- **Trusting the client's inbound `X-Correlation-Id` on the public tier** (no
  strip line). The brief's guarantee is that a public caller can never inject an
  id; without the strip, anyone on the internet could pin their requests onto an
  arbitrary chain, and the forensic record would be attacker-controlled. The
  ungated PRM bootstrap is the same exposure for the same reason.
- **Letting the sites process decide whether to trust the header.** That puts
  trust logic in the service and breaks "nginx is the sole trust boundary"
  (Conventions) — the service cannot tell a gated request from an ungated one;
  only nginx knows which location matched.
- **Passing the id through as a query parameter or a body field instead of a
  header.** It would have to survive `proxy_pass` path rewriting, would land in
  access logs, and would not reach the chassis's read-or-mint middleware, which
  reads a header.
- **One shared `$sites_correlation` variable for every location.** It works
  (bindings are per-location) but it hides that the bearer and session gates are
  different subrequests; the existing owner-header naming already draws that
  line and the fragment stays readable by following it.

**Verification.** (Proven by the existing test that reads `sites/etc/nginx.conf`
from disk, extended.)
- R-BN65-STRE — **every gated location captures and forwards the minted id.** All
  four — `= /srv/sites/mcp`, `= /srv/sites/`, `/srv/sites/static/`, and
  `/srv/sites/private/` — contain both halves: an `auth_request_set` binding a
  `$sites_correlation` / `$sites_session_correlation` variable to
  `$upstream_http_x_correlation_id`, **and** a `proxy_set_header X-Correlation-Id`
  whose value is that same variable. A fragment where any one of the four omits
  either half, or forwards the client-supplied `$http_x_correlation_id` instead
  of the captured variable, fails — asserting only that the string
  `X-Correlation-Id` appears somewhere would not.
- R-9CMM-G2ZU — **every ungated proxying location strips the header.** Both
  `= /srv/sites/.well-known/oauth-protected-resource` and `/srv/sites/public/`
  contain `proxy_set_header X-Correlation-Id "";`, and neither contains an
  `auth_request` or any correlation `auth_request_set`. Conversely no gated
  location carries the empty-value form. A fragment that leaves either public
  location without the strip line — the case where an internet caller could
  inject a chain id — fails.
