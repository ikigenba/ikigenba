# Decision 33 — The write path: commit through repos, then apply to the materialized copy

**Decision.** Every mutation an owner makes to a site's files becomes a **commit
on `main`** and is **applied to the served copy in the same tool call**, so the
edit is both historical and live-immediately. This is the sites-side half of the
"materialized copy" and "synchronous own-write apply" behaviors root D24 assigns
to this tree.

**The order is commit-then-apply, and the order is the design.** The repository
is canonical; the served tree under `SITES_ROOT` (D16) is derived. So:

1. Build the change set and call `version.Commit(ctx, slug, msg, changes)`.
2. On success, record the returned sha on the site row (`Store.SetRepoSha`, D15)
   and write the same bytes into `SiteDir(v, slug)`.
3. Return the tool's normal result.

If step 1 fails, **nothing local changes** and the tool returns an error: the
owner is told the edit did not happen, and it did not. If step 2 fails, the
repository is ahead of the copy — a state the system **heals by itself**, because
the commit produced a `repos:push` event whose sha differs from the recorded one,
and the consumer (D35) re-materializes. The reverse order has no such recovery:
applying first and failing to commit leaves a live site whose content exists in no
history, silently, forever. That asymmetry is the whole reason the order is fixed.

**Which tools take this path.** The mutating surface (D20), unchanged in shape:

| tool | change set | commit message |
|---|---|---|
| `file_write` | one `FileChange{Path, Data}` | `write <path>` |
| `file_edit` | one `FileChange{Path, Data}` carrying the **post-edit** bytes | `edit <path>` |
| `mkdir` | **none** — see below | — |
| `sync` | one batch of writes and deletes | D34 owns it |
| `create` / `delete` / `set_visibility` | repository lifecycle, not content | D36 owns them |

`file_read`, `file_glob`, `file_grep`, `file_list`, `list`, `rename`, and `guide`
read or touch no site bytes and make no repos call at all.

**`mkdir` commits nothing, deliberately.** Git tracks files, not directories;
there is no commit that represents an empty directory, and inventing a
`.gitkeep` would put a file in the owner's site that the owner never wrote and
would then serve it. So `mkdir` creates the directory in the materialized copy
only. The directory enters the repository the moment a file lands inside it —
`file_write` commits the full site-relative path, and git creates the intervening
tree entries. A re-materialization (D35) recreates every directory that holds a
file and does **not** recreate an empty one; an owner who made an empty directory
and never filled it will find it gone after an external push. That is a real,
accepted consequence of git's data model, not a defect to paper over.

**Path discipline.** A `FileChange.Path` is the site-relative, slash-separated
path the file tools already resolve and confine (`internal/files.ConfinePath`,
D10) — computed from the confined absolute path, never from raw tool input. A
path that escapes the site directory is already a `validation` error before any
repos call is made, so no traversal reaches the plane. On a site with a
non-empty publish root the committed path additionally carries the root prefix
(`<path>/<site-relative>`); that mapping and its proof are D38's — the
behaviors and ids in this Decision are stated for the default root, where the
mapping is the identity.

**Rapid successive writes.** Root D24 permits a producer to coalesce rapid writes
into one commit. sites does **not** coalesce: one mutating tool call is one
commit. Batching would mean holding an owner's bytes in memory across calls with
no bound on when they land in history, and the failure mode — a crash losing
committed-looking edits — is worse than a chatty history. The batch case that
genuinely exists is `sync`, and it is batched because it is *one* logical
operation (D34).

**Error mapping** (into D25's closed vocabulary): `ErrVersionUnavailable`
(refused connection, timeout, 5xx) → **`source_unavailable`**, the same code the
dropbox mirror's unavailability already uses — the caller's remedy is identical
(retry later). A repos-side rejection of a well-formed request → **`internal`**.
Confinement and validation failures never reach the plane and keep their existing
`validation` mapping.

**Rejected.**

- **Apply locally first, commit after (fire-and-forget history).** The tempting
  order — it makes the edit feel instant even when repos is down. It also makes
  "the site is serving content that exists in no history" an ordinary,
  unsignalled state. Versioning is ambient only if it is unconditional.
- **Applying locally and queueing the commit for retry.** A durable outbox for
  commits is a real design, and it is repos-plane machinery living in the wrong
  tree: it needs its own table, its own retention, its own ordering guarantees
  against the push consumer, and it reintroduces the divergence window it was
  meant to close. If commit-on-write proves too fragile in practice that is a new
  Decision, not a hedge built in now.
- **Degrading to local-only writes when repos is unreachable.** Same objection as
  D32's nil-client rejection, at runtime instead of construction: the owner would
  be told the edit succeeded, and its history would be gone.
- **Committing a `.gitkeep` for `mkdir`.** It puts a file the owner did not write
  into a directory the owner *will* serve — `/foo/.gitkeep` would be fetchable.
  Better to be honest that empty directories are not versioned.
- **Coalescing successive writes into one commit on a timer.** Covered above:
  unbounded window, worse failure mode, and it makes `file_write`'s return value
  a lie about what is in history.

**Verification.** (Substrate: hermetic. Driven through the assembled `appkit/mcp`
handler over a temp `SITES_ROOT`, a real migrated SQLite DB, and a
contract-conforming `httptest` repos server that records every call and can be
made to fail on demand — the same seam D20's ids already use.)

- R-ESH6-NMDE — `file_write` **commits and applies in one call**: writing
  `index.html` to a site yields (a) exactly one recorded `Commit` call carrying
  exactly one `FileChange` whose `Path` is `index.html` and whose `Data` is
  byte-identical to what was written, **and** (b) the file present at
  `SiteDir(v, slug)/index.html` with those same bytes, **and** (c) the returned
  sha recorded on the row (a subsequent `Get` reports it). A build that writes
  locally without committing fails (a); one that commits without writing fails
  (b) — and (b) is checked by reading the file, not by trusting the tool result.
- R-ETP3-1E43 — `file_edit` commits the **post-edit** bytes: after editing a
  file whose content was `alpha` into `beta`, the recorded commit's single
  change carries `beta` (not `alpha`, not a diff/patch body) and the file on
  disk reads `beta`. An implementation that commits the pre-edit content, or the
  replacement fragment rather than the whole resulting file, fails.
- R-EUWZ-F5US — `mkdir` makes **no repos call at all** (the recording server
  observes zero requests) and creates the directory in the served copy; a
  subsequent `file_write` into that directory commits a single change whose
  `Path` is the **full site-relative path including the directory segment**
  (`assets/app.css`, not `app.css`). A build that commits a placeholder file for
  `mkdir` fails the zero-request assertion.
- R-EW4V-SXLH — **a failed commit changes nothing locally.** With the repos
  server made to fail the commit, `file_write` of a new path returns an error
  envelope and that path **does not exist** under `SiteDir(v, slug)`; a
  `file_write` overwriting an existing file leaves the file's bytes
  byte-identical to before, and the row's recorded sha is unchanged. A build
  that writes first and commits second passes every other id here and fails this
  one — which is the point of the id.
- R-EXCS-6PC6 — **repos unavailable is `source_unavailable`, not `internal`.**
  With the repos server closed (connection refused) the `file_write` result is
  the `source_unavailable` error envelope of D25's vocabulary; with the server
  answering `400` to a well-formed commit the result is `internal`. A build that
  maps every repos failure to one code fails.
