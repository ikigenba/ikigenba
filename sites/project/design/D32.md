# Decision 32 — The version-plane client seam: `sites.VersionClient`

**Decision.** sites adopts the suite's version plane,
`root project/design/D24.md`. That contract owns what the plane *is* — repos as
the suite's git custodian, one bare repository per artifact keyed `<kind>/<name>`,
`main` as live, the materialized copy, the git door, archive-not-delete. This
Decision restates none of it. It owns exactly one thing: **the seam through which
sites talks to repos**, and the two properties of that seam sites can prove.

For sites the plane's key is **`sites/<slug>`** — the `kind` is `sites` and the
`name` is sites' own slug (D15), so the plane introduces no second namespace and
a slug rotation is a repo rename (D36), never a new repository.

**The seam is a Go interface in `internal/sites`, injected at the composition
root.** sites' domain packages never construct a client, never learn a URL, and
never import an HTTP transport:

```go
// internal/sites/version.go

// Commit identifies one commit on a repository's main branch.
type Commit struct {
    Sha string
}

// FileChange is one path-level change in a commit: Delete selects removal,
// otherwise Data is written at Path (creating or replacing).
type FileChange struct {
    Path   string // site-relative, slash-separated, never absolute, never "..", never a .git segment
    Data   []byte
    Delete bool
}

// TreeEntry is one plain file in an exported tree.
type TreeEntry struct {
    Path string
    Data []byte
}

// VersionClient is sites' whole view of repos. Every method addresses one site
// by its slug; the client is responsible for turning that into the plane's
// `sites/<slug>` key. Every method is called with the live request (or handler)
// context, which carries the correlation id and the acting client id.
type VersionClient interface {
    // Create makes the repository for a slug. Creating one that already exists
    // is a success — the client absorbs repos' conflict (the seeding path, D37,
    // depends on this idempotence).
    Create(ctx context.Context, slug string, owner Owner) error

    // Commit applies one or more changes to main as a SINGLE commit and returns
    // the resulting commit. A zero-change call is a no-op returning the current
    // tip. Message is the human-readable commit subject.
    Commit(ctx context.Context, slug, message string, changes []FileChange) (Commit, error)

    // Export returns the whole tree at main as plain files — no VCS metadata,
    // no directories (git has none), the bytes the served copy is made of.
    // A repository with no commits yet is NOT an error: it exports zero
    // entries and an empty Commit. (repos signals that case distinctly; the
    // implementation translates it, so no caller has to special-case it and a
    // freshly created repository can never stall the push consumer, D35.)
    Export(ctx context.Context, slug string) ([]TreeEntry, Commit, error)

    // Rename moves the repository key from oldSlug to newSlug.
    Rename(ctx context.Context, oldSlug, newSlug string, owner Owner) error

    // Delete archives the repository (history preserved; root D24). Deleting an
    // already-archived or absent repository is a success — the client absorbs
    // repos' not_found.
    Delete(ctx context.Context, slug string, owner Owner) error
}

// Owner is the identity a loopback caller asserts on repos' MCP surface. It is
// always the SITE's recorded owner (D15), never the acting caller's — repos'
// verbs are owner-scoped, and the seeding and consumer paths have no acting
// caller at all.
type Owner struct {
    ID    string // X-Owner-Id
    Email string // X-Owner-Email
}

// ErrVersionUnavailable is the sentinel every transport-level failure — refused
// connection, timeout, 5xx — is joined to, so the MCP layer maps it to
// source_unavailable (D25) rather than internal.
var ErrVersionUnavailable = errors.New("version plane unavailable")
```

**One implementation, two transports — because the suite has one verb surface.**
`NewVersionClient(base string, hc *http.Client) VersionClient` is the sole
production implementation, and behind that single interface the five methods
split by *what kind of thing they are*:

- **`Create`, `Rename`, `Delete` are domain verbs**, so they go over **MCP**:
  `tools/call` against repos' loopback `POST /mcp`, consuming
  `structuredContent` and branching on the closed error code.
  `root project/design/D20.md` is why — MCP is the suite's single verb surface
  and there is no second machine-facing API beside it, so a REST twin of a
  domain verb is not an option to weigh. This is an established pattern, not a
  new one: repos itself calls the github service exactly this way
  (`repos/internal/repos/ghpeer.go`).
- **`Commit` and `Export` are byte/plumbing operations**, so they go over repos'
  loopback content routes, where bytes belong (`root project/design/D19.md`'s
  content plane, and root D24's relation-to-the-content-plane paragraph).

Both transports' **exact paths, methods, tool names, and bodies are repos'
spec's to own** — this design cites the contracts and reads the shapes from
repos' own sealed design at build time. Restating them here would be drift by
construction the moment repos moves. What sites owns and pins is the interface
above and the properties below.

**Loopback callers assert identity; they do not carry a session.** sites reaches
repos' `/mcp` directly on loopback, never through nginx, so there are no
nginx-injected headers to forward. It **asserts** `X-Owner-Id`, `X-Owner-Email`,
and `X-Client-Id` on the request, the same shape `GitHubPeer` asserts today. The
owner it asserts is **the site's recorded owner** (`owner_id` / `owner_email` on
the row, D15) — not the acting caller's:

- repos' verbs are owner-scoped, so a repository created under one owner must be
  renamed and archived under that same owner or the later call cannot find it;
- the seeding pass (D37) and the push consumer (D35) have **no** acting caller
  at all, and the row's owner is the only truthful answer available.

At `create` time the two coincide by construction (the row is born from the
acting `Identity`). This is the first thing in sites that *reads* `owner_id` for
logic rather than display, and it is why capturing the stable id rather than
only the email was worth doing.

**`X-Client-Id` stays the attribution**, separately from the owner, and it is
the **acting** client id wherever one exists — the agent or client that made the
edit, threaded from the request `Identity`. Root D24 is explicit that a service's
own writes are attributed to the acting `X-Client-Id`, and that is the whole
value of the attribution: a history in which every commit reads `sites` records
that sites wrote it, which was never in doubt, and loses the only fact worth
keeping. On the **two callerless paths** — the seeding pass (D37) and the push
consumer (D35) — there is no acting client, so sites asserts its own service
identity in the form `sites:<slug>`, which is honest about what actually made
the call.

**Idempotence: repos is strict where it should be, and the client absorbs the
rest.** Two different situations, deliberately handled differently:

- **`create` on an existing key returns `conflict`, and that is correct** —
  collapsing "created" with "found" would make a genuine slug collision
  invisible to every caller. The closed error vocabulary exists so a machine
  caller can branch, so **sites branches**: `Create` maps `conflict` to success,
  which is how D37's seeding adopts a repository left by a partial earlier run
  without repos ever lying about what it did.
- **`delete` on an already-archived repository already succeeds** at repos —
  archiving is idempotent because its target state is terminal, so a retry after
  a crashed delete is not an error. The client's only translation is the
  narrower case of a repository that never existed at all (`not_found`), which
  D36's idempotent delete treats as done.

Both translations live here, at sites' seam, where the requirement comes from.
Pushing either into repos would weaken a verb for every other caller.

**Where it is built.** `cmd/sites/main.go`, inside the `Spec.Handlers` closure,
beside the existing mirror client:

```go
base := config.EnvOr(os.Getenv, "REPOS_BASE_URL", registry.BaseURL("repos"))
version := sites.NewVersionClient(base, rt.HTTPClient(30*time.Second))
```

The base resolves **by name through `registry`** (D9) with a `REPOS_BASE_URL`
override, exactly as the dropbox mirror base does — no port literal enters sites'
source. The HTTP client is the **Router-provided instrumented client**
(`rt.HTTPClient(…)`, D28): sites now makes two kinds of outbound call and both go
through the same instrumented seam, so every repos hop is an `outbound` telemetry
record and carries the ambient correlation id. As with dropbox, the registry
default is a loopback IP literal, which is what makes correlation propagate; a
`REPOS_BASE_URL` pointed at the *name* `localhost` would silently stop
propagating (D28's recorded hazard, unchanged and not re-patched here).

**Attribution rides the request.** Root D24 attributes a commit to the acting
`X-Client-Id`. sites does not invent an actor: the MCP handler reads the acting
identity off the request (`appkit.Identity`, already threaded for `owner_id` /
`owner_email`, D20) and the client puts the client id on every mutating call.
Calls with no acting client — the seeding pass (D37) and the push consumer's
re-materialization (D35, which mutates nothing remote) — carry sites' own service
identity instead of a forged one.

**Rejected.**

- **Restating repos' HTTP paths, tool names, and payloads in this design.**
  Citation is the mechanism (`$ikispec`). A local copy of another tree's wire
  contract is stale the first time repos edits an endpoint, and nothing would
  catch it — sites' tests would keep passing against sites' own fake.
- **Asking repos for loopback REST twins of `create`/`rename`/`delete`.** The
  shape sites originally wanted, and `root project/design/D20.md` forecloses it:
  MCP is the suite's single verb surface, and a second machine-facing API beside
  it is exactly what that contract exists to prevent. A REST twin would also
  need its own error vocabulary, its own schema, and its own tests, for verbs
  that already exist and already work.
- **Asserting the *acting caller's* owner instead of the site's.** It reads as
  the more natural choice and it breaks in two places: a repository created
  under one owner could not be renamed or archived by another, and the seeding
  and consumer paths have no acting caller to borrow an identity from. The row
  already records who owns the site; that is the answer.
- **Asking repos to make `create` and `delete` idempotent.** It would weaken two
  verbs for every other caller — an agent that typos an existing repository name
  should hear `conflict` — to spare sites' client two error-code checks.
- **Reaching for the client from inside `internal/mcp` or `internal/sites`.**
  Same reasoning as D28's rejection of a deeper mirror client: the base comes
  from config and config is chosen at the composition root. A package-level
  global is how an uninstrumented or misconfigured client survives a refactor.
- **A nil-client fallback that silently degrades to local-only writes.** This is
  the dangerous one. A build where a missing `VersionClient` means "just write
  the file and skip the commit" would lose history invisibly and pass every
  local test. There is exactly one production caller; a nil client is a
  programming error, not a mode. Absence of repos is a *runtime* failure with a
  visible error envelope (D33), never a silent downgrade.
- **A second, uninstrumented `http.Client` for repos** because the calls are
  "internal". They are the same kind of loopback hop as dropbox, and the whole
  point of D28's seam is that there is one answer.
- **Proving repos actually accepts what sites sends, from sites' suite.** That
  requires a real repos process, which lives outside this tree — building or
  running it here violates the scope boundary, and root D24 already assigns
  custody, the git door, and commit acceptance to **repos**' own ids. sites
  proves its half: that the calls are made, with the right content, through the
  right client, and that the local copy tracks them.

**Verification.** (Substrate: hermetic. The `VersionClient` under test is the
real implementation driven against an `httptest` server that conforms to repos'
contract — answering both its `/mcp` verb surface and its content routes — and
records what it received; a fake accepts whatever it is handed, so no id below
claims repos' acceptance — each pins something the recording server can falsify.
The one exception is R-ER9A-9UMP, whose layer is named on the id.)

- R-EOTH-IB5B — **every** repos call goes through the injected `*http.Client`
  and reaches the configured base, **across both transports**. Driven with a
  client whose `Transport` is a recording `RoundTripper`: a `Create`, a
  two-change `Commit`, an `Export`, a `Rename`, and a `Delete` yield **five**
  recorded requests — counts equal, none escaping to `http.DefaultClient` — and
  every recorded URL begins with the base the client was constructed with. The
  three verbs arrive as `tools/call` requests on repos' MCP endpoint and the two
  byte operations on the content routes; an implementation that sends a domain
  verb to a REST path, or a commit through `tools/call`, fails.
- R-NF7R-V95S — **the asserted identity is the site's owner, and attribution is
  the client id.** Every `Create`/`Rename`/`Delete` request carries
  `X-Owner-Id` and `X-Owner-Email` equal to the `owner` argument (verified with
  an owner whose id and email are unrelated values, so a build that derives one
  from the other fails) and an `X-Client-Id` distinct from both. A build that
  asserts the acting caller's owner, or that sends the email as the owner id,
  fails.
- R-NGFO-90WH — **the client absorbs exactly the two codes sites needs absorbed,
  and no others.** With the server answering `conflict` to `create`, `Create`
  returns **nil**; with it answering `not_found` to `delete`, `Delete` returns
  **nil**; with it answering `not_found` to `rename`, `Rename` returns a
  **non-nil** error (renaming a repository that is not there is a real failure
  sites must surface); and with it answering `validation` to `create`, `Create`
  returns a non-nil error. A client that swallows every error code passes the
  first two and fails the last two; one that swallows none fails the first two.
- R-EQ1D-W2W0 — the **live request context and the acting client id reach the
  wire**: driving a mutating MCP tool (D33) with an inbound request carrying
  `X-Client-Id: cli-alice` and a correlation id on its context, the recording
  transport observes that exact correlation id on the `Context()` of the
  outgoing repos request and `cli-alice` as the call's attribution — for **every**
  outgoing request, not merely the first. A handler path that detaches with
  `context.Background()`, or that attributes to the owner email or a hardcoded
  actor, fails.
- R-ER9A-9UMP — the **composition root actually wires the client**: the composed
  boot smoke (`cmd/sites/main_test.go`) starts sites' real binary with
  `REPOS_BASE_URL` pointed at a conforming stub server on loopback, performs one
  `file_write` through the running service's MCP endpoint, and the stub records
  the resulting commit call. A build whose `Spec.Handlers` constructs the tool
  table without a `VersionClient` — or with one built over
  `http.DefaultClient` — fails this even though every hermetic id above passes.
  **Substrate: composed** (sites' own built binary over loopback).
