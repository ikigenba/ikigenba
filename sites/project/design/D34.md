# Decision 34 — `sync` reconciles as **one** batch commit, then updates the copy

**Decision.** The `sync` verb (the Dropbox-mirror importer) keeps its MCP surface
exactly as D20 states it — same arguments, same result, same **never creates a
site** rule, same "leaves visibility and name unchanged" rule. What changes is
that its reconcile is no longer a bare filesystem operation: it becomes **one
commit** through the version plane, followed by the local update, in the same
call. The write-path order and its rationale are D33's and are not restated: the
commit is first, and a failed commit leaves the served copy untouched.

**One import is one commit.** `sync` is a single logical operation — "make this
site's files match that Dropbox subtree" — so it produces a single commit
carrying every write and every delete the reconcile implies, not one commit per
file. A hundred-file import that arrived as a hundred commits would make the
history unreadable for the one case where history is most useful (what did that
import actually change?), and would leave the repository in a hundred
intermediate states no user ever chose. This is the batch case D33 says exists. (On a site
with a non-empty publish root every write and delete in the batch carries the
root prefix — D38's mapping; this Decision's ids are stated for the default
root, where the mapping is the identity.)

**The shape of the pass**, with only the reconcile step changed:

1. Validate `source_path`, derive/validate the slug, `Store.Get` the site
   (`not_found` when it does not exist — unchanged, D20's R-56CN-HE21), stamp
   `source_path` on the row. No repos call yet.
2. Enumerate the mirror subtree and fetch each **file's** bytes — the
   **desired** set, keyed by path relative to `source_path`, including the
   `source_unavailable` mapping for mirror failures. **The enumeration keeps
   only file entries.** dropbox's loopback `/list` returns directory rows as
   well as file rows — and, because its prefix filter matches the queried path
   itself, the very row for `source_path` — each carrying a `kind`
   discriminator (`"file"` / `"dir"`) on the wire. The mirror entry type carries
   that `kind`, and the enumeration **skips every non-file entry**: a directory
   is never fetched. This is the fix for the failure where `sync` fetched a
   directory entry (the prefix row or a sub-directory) and `/content` answered
   `404` for it, surfacing spuriously as `source_unavailable`. Only real files
   enter the desired set; the reconcile below is unchanged by it.
3. Walk `SiteDir(v, slug)` for the **existing** relative file set. Unchanged.
4. **New:** build the change set — a `FileChange{Path, Data}` for every desired
   file, and a `FileChange{Path, Delete: true}` for every existing path not in
   the desired set — and issue **one** `version.Commit(ctx, slug, "sync
   <source_path>", changes)`. Record the returned sha on the row.
5. Apply the same change set locally through the type-safe in-place reconcile
   (`sites.Reconcile`, D42 — its file/directory type-change safety and
   delete-before-write ordering, unchanged here in shape or call site) and
   return `{slug, written, deleted}` — the same counts, now counting the same
   changes that went into the commit.

**An empty reconcile commits nothing.** When the desired set and the existing set
already agree, the change set is empty and `sync` makes **no** commit call: a
no-op import must not manufacture an empty commit on every poll. The tool still
returns `{written: 0, deleted: 0}` as it does today.

**Overwrite-all stays overwrite-all.** Today's reconcile writes every desired
file without comparing digests, and the change set is built the same way. That
means a re-sync of unchanged bytes produces a commit whose diff is empty rather
than no commit at all. Accepted: the alternative is a content comparison whose
only benefit is tidier history, and the existing behavior — the mirror is the
authority, write what it says — is the simpler contract. (The empty-change-set
case above is different: it is about *files present*, which the walk already
knows without hashing anything.)

**Rejected.**

- **One commit per file, reusing D33's single-file path.** Readability and
  atomicity both lose: an import would appear as an unbounded run of commits, and
  an interrupted import would leave the repository in a state that is neither the
  old tree nor the new one, with no single ref naming either.
- **Committing after the local reconcile** (so `written`/`deleted` are counted
  from what actually landed). It inverts D33's order for one tool, which is
  exactly how an inconsistency becomes permanent; and the counts are derivable
  from the change set before it is applied.
- **Hashing to skip unchanged files.** A real improvement to history hygiene and
  a real change to the importer's contract (it would stop being overwrite-all).
  Out of scope for adopting the plane; it is its own Decision if wanted.
- **Letting `sync` create the site (and its repository) when absent.** Rejected
  previously with the product promise and unchanged: `sync` reconciles content,
  it does not bring sites into being. The plane does not change that.

**Verification.** (Substrate: hermetic. Driven through the assembled `appkit/mcp`
`sync` handler over a temp `SITES_ROOT`, a real migrated SQLite DB, a fake
`sites.MirrorClient`, and the contract-conforming recording repos server of D32.)

- R-EYKO-KH2V — **one import is exactly one commit, carrying every change.**
  With the mirror offering three files and the site's directory already holding
  two files of which one is absent upstream, `sync` results in **exactly one**
  recorded `Commit` call whose change set contains three writes (paths and bytes
  matching the mirror) and **one** delete (the stale path), and **no** other
  repos call. A build issuing one commit per file fails the count; a build
  omitting the deletion fails the change set.
- R-EZSK-Y8TK — **the served copy matches the committed set.** After the same
  pass, `SiteDir(v, slug)` contains exactly the three mirrored files with the
  mirror's bytes and no longer contains the stale file, and the row carries the
  sha the commit returned. A no-op re-sync of an already-matching tree records
  **zero** `Commit` calls and returns `{written: 0, deleted: 0}` — an
  implementation that commits an empty change set on every poll fails.
- R-F28D-PSAY — **a failed batch commit leaves the copy untouched.** With the
  repos server made to fail the commit, `sync` returns an error envelope, the
  site directory's file set and every file's bytes are byte-identical to before
  the call, the stale file is **still present**, and the row's recorded sha is
  unchanged. A build that reconciles locally and then commits passes
  R-EYKO-KH2V and R-EZSK-Y8TK and fails this one.
- R-G118-GMFK — **`sync` imports only file entries; a directory entry is never
  fetched.** With the fake `MirrorClient` returning, for `source_path`, a
  directory entry (`kind: "dir"`, path equal to `source_path` — the prefix row
  dropbox emits) plus two file entries under it, `sync` produces a desired set
  of exactly the two files (their bytes fetched), makes **no** `Fetch` call for
  the directory entry, and returns without a `source_unavailable` error. A build
  that fetches every listed entry issues a `Fetch` for the directory path and
  fails — the exact `fetch "…": unexpected status 404` this fix removes.
