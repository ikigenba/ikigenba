# Decision 41 — Per-file and per-directory deletion: `file_delete` and `rmdir`

**Decision.** The file-tool surface gains two **mutating** tools so an owner can
remove content without deleting the whole site: `file_delete` (one file) and
`rmdir` (a directory and everything under it). Until now the only deletion was
whole-site `delete` (D20/D36), so a stray file or a directory that must become a
file (D33's refusal case) could not be removed at all. Both new tools are
version-planed exactly like every other content mutation: they take D33's
**commit-then-apply** order and its failure semantics, and on a site with a
non-empty publish root their committed paths carry the root prefix (D38).

Both address a site by its `slug` (the `site` argument, an unlisted site's token
included) and confine `path` under `SiteDir(site.Visibility, slug)` via
`internal/files.ConfinePath` (D10); a `..`-escaping or absolute path is a
`validation` error before any plane call, as for every file tool.

**`file_delete(site, path)`** — removes one regular file.

1. Resolve and confine `path`. Confinement failure → `validation`.
2. The confined path must name an **existing regular file**. A path that names a
   **directory** → `validation` (use `rmdir`); a path that does not exist →
   `not_found`. Both are decided locally, before any plane call.
3. Commit one `FileChange{Path: <root-prefixed site-relative>, Delete: true}`
   through `version.Commit(ctx, slug, "delete <path>", …)`. A failed commit
   changes nothing locally and returns an error (D33); repos unreachable →
   `source_unavailable`, a repos-side rejection of a well-formed request →
   `internal` (D33's mapping, unchanged).
4. On success record the returned sha (`Store.SetRepoSha`, D15) and remove the
   file from the served copy.

Result: `{deleted: <path>, site: <slug>}`.

**`rmdir(site, path)`** — removes a directory and every file beneath it.

1. Resolve and confine `path`. Confinement failure → `validation`.
2. The confined path must name an **existing directory**. A path that names a
   **regular file** → `validation` (use `file_delete`); a path that does not
   exist → `not_found`.
3. Enumerate the files under the directory in the served copy. Build **one**
   batch carrying a `FileChange{Path, Delete: true}` for **every** file beneath
   the prefix (git tracks files, not directories, so removing a directory *is*
   removing its files — the same reason `mkdir` commits nothing, D33), and issue
   **one** `version.Commit(ctx, slug, "rmdir <path>", …)`. A directory that
   holds no committed files (e.g. one just made by `mkdir`, never filled) yields
   an **empty batch and makes no commit** — it exists only in the served copy,
   so it is removed locally with no plane call, mirroring `mkdir`'s
   commits-nothing rule in reverse.
4. Commit-then-apply and failure semantics are D33's: a failed commit leaves the
   whole subtree in place; on success record the sha and remove the subtree from
   the served copy (`os.RemoveAll` of the confined directory).

Result: `{removed: <path>, site: <slug>, files: <count>}` where `files` is the
number of committed deletions (0 for a locally-only empty directory).

**Both are structured tools (D25).** `file_delete`'s `outputSchema` is
`{deleted: string, site: string}`; `rmdir`'s is `{removed: string, site: string,
files: integer}`. Their failures speak the closed vocabulary (D25): confinement
and wrong-type and missing-argument → `validation`, missing target →
`not_found`, repos unreachable → `source_unavailable`, a repos rejection or a
local filesystem failure → `internal`. Adding these two mutating tools takes the
domain surface from 15 to **17** tools and the full `tools/list` from 17 to
**19**; that count and the structured-tool tables are D13's, D20's, D21's, and
D25's and are updated there.

**Rejected.**

- **A single `delete(path)` that removes a file or a directory by inspecting the
  target's type.** One tool with two behaviors keyed on what happens to be on
  disk is exactly the ambiguity D33 refuses for `file_write`: an owner who means
  to delete a file but fat-fingers a directory path would wipe a subtree. Two
  named tools make the intent explicit and let each carry the right wrong-type
  refusal.
- **Recursive delete built from repeated single-file commits.** A directory
  removal is one logical operation; one commit per file would make an
  unreadable history and an interrupted removal would leave the repository in a
  state that is neither the old tree nor the new one — the same argument D34
  makes for `sync`. One `rmdir` is one commit.
- **`file_delete` tolerating a missing file as an idempotent success.** Whole-site
  `delete` is idempotent because "gone" is its whole point; a per-file delete of
  a path that is not there is far more likely a mistake (wrong slug, wrong path)
  worth surfacing as `not_found` than a no-op worth hiding.
- **A `.gitkeep`-style placeholder so an emptied directory survives in history.**
  Rejected for the same reason D33 rejects it for `mkdir`: it puts a file the
  owner never wrote into a directory the owner serves. An empty directory is not
  a versioned thing here; `rmdir` of a locally-only empty directory committing
  nothing is the honest consequence.
- **Applying the removal locally before the commit lands.** D33's order is the
  design: local-first would leave a site serving the absence of a file that
  still exists in history, or vice versa. Commit first.

**Verification.** (Substrate: hermetic. Driven through the assembled `appkit/mcp`
handler over a temp `SITES_ROOT`, a real migrated SQLite DB, and the
contract-conforming recording `httptest` repos server of D32 — the same seam
D33's ids use — that records every call and can be made to fail on demand.)

- R-FOU8-MX0M — **`file_delete` commits one deletion and removes the file, in one
  call.** Deleting `about.html` from a site that has it yields (a) exactly one
  recorded `Commit` carrying exactly one `FileChange` whose `Path` is
  `about.html` and whose `Delete` is set, (b) the file **absent** from
  `SiteDir(v, slug)` afterward (checked by reading the directory, not by
  trusting the result), and (c) the returned sha recorded on the row. A build
  that removes locally without committing fails (a); one that commits without
  removing fails (b).
- R-FQ25-0ORB — **`file_delete` on a directory path is `validation`, no plane
  call.** On a site whose copy holds `qr/index.html`, `file_delete("qr")`
  returns the `validation` envelope, the repos server records **zero** requests,
  and `qr/` and its file are byte-identical to before. A build that treats it as
  a recursive delete, or errors at the filesystem instead of validating up front,
  fails.
- R-FRA1-EGI0 — **`file_delete` on a missing file is `not_found`, no plane
  call.** `file_delete("nope.html")` on a site lacking it returns the
  `not_found` envelope and the repos server records **zero** requests. A build
  that returns an idempotent success, or maps it to `validation`/`internal`,
  fails.
- R-FSHX-S88P — **a failed `file_delete` commit changes nothing.** With the repos
  server made to fail the commit, `file_delete("about.html")` returns an error
  envelope, `about.html` is **still present** with byte-identical content under
  `SiteDir(v, slug)`, and the row's recorded sha is unchanged. A build that
  removes locally before (or regardless of) the commit fails.
- R-FTPU-5ZZE — **`file_delete` maps repos failures per D33.** With the repos
  server refusing connections the result is `source_unavailable`; with it
  answering `400` to a well-formed commit the result is `internal`. A build that
  collapses both to one code fails.
- R-FUXQ-JRQ3 — **`rmdir` removes a whole subtree in one commit.** On a site whose
  copy holds `qr/index.html`, `qr/app.css`, and `index.html`, `rmdir("qr")`
  yields **exactly one** recorded `Commit` whose change set is precisely the two
  deletions `qr/index.html` and `qr/app.css` (and **no** other repos call),
  leaves `SiteDir(v, slug)` holding exactly `index.html` with the `qr/`
  directory gone, records the sha, and returns `files == 2`. A build issuing one
  commit per file fails the count; one that deletes `index.html` too fails the
  change set.
- R-FW5M-XJGS — **`rmdir` on a regular-file path is `validation`, no plane
  call.** On a site whose copy holds a regular file `qr`, `rmdir("qr")` returns
  the `validation` envelope, the repos server records **zero** requests, and the
  file `qr` is byte-identical to before. A build that deletes the file anyway
  fails.
- R-FXDJ-BB7H — **a failed `rmdir` commit leaves the subtree in place.** With the
  repos server made to fail the commit, `rmdir("qr")` over a populated `qr/`
  returns an error envelope, every file under `qr/` is **still present** and
  byte-identical, and the row's recorded sha is unchanged. A build that removes
  the subtree before (or regardless of) the commit fails.
