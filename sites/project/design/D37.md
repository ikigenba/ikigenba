# Decision 37 — Seeding existing sites into the version plane

**Decision.** Every site that exists today predates the version plane: it has a
row and a served tree and no repository. Seeding is the one-time, **additive,
re-runnable** pass that gives each of them a repository whose initial commit is
the tree it is already serving. Root D24 names seeding as a sites-side behavior;
this Decision is its shape.

**The hard constraint first: nothing is destroyed, moved, or rewritten.** These
served trees are live customer data (the suite's production-data posture). The
pass reads the tree and writes to repos. It never deletes a file, never relocates
a directory, never rewrites a byte under `SITES_ROOT`, and never changes a row's
slug, name, visibility, owner, or timestamps. Its only local write is the
bookkeeping the next paragraph describes.

**Seeding is keyed on a row flag, not on asking repos.** D15 adds
`repo_seeded INTEGER NOT NULL DEFAULT 0` beside `repo_sha`; every pre-existing
row therefore arrives at `0` by the migration's default, which is exactly the set
that needs seeding.

```go
// internal/sites/seed.go

// Seed brings every unseeded site into the version plane. It processes rows
// with repo_seeded = 0, in slug order, and is safe to call repeatedly and
// concurrently with normal serving: a seeded row is never revisited.
// Returns the number of sites seeded by this call. On the first failure it
// stops and returns it, leaving already-seeded rows seeded.
func Seed(ctx context.Context, store *Store, layout Layout, vc VersionClient) (int, error)
```

Per unseeded site:

1. `vc.Create(ctx, slug, Owner{site.OwnerID, site.OwnerEmail})` — asserting the
   **row's** owner, which is the only identity this callerless pass has and the
   correct one for repos' owner-scoped verb (D32). Idempotent by D32's contract,
   so a repository left behind by a partial earlier run is adopted, not an error.
2. Walk `SiteDir(site.Visibility, slug)` for its regular files and build one
   change set of writes — the **whole current tree**, site-relative paths.
3. `vc.Commit(ctx, slug, "seed <slug>", changes)` — **one** commit, the tree as
   it stands. Record the returned sha in `repo_sha`.
4. Set `repo_seeded = 1`.

A site with **no files** commits nothing (an empty change set, per D33/D34) and
is still marked seeded with an empty `repo_sha`: it has a repository, it has
nothing to put in it, and the flag is what stops the pass from reconsidering it
every boot. The empty `repo_sha` is harmless — it can never equal a real sha, so
the echo gate (D35) simply lets the first real push through.

**Where it runs: a background pass at startup, not a boot gate.** The composition
root starts `Seed` in a goroutine once the server is listening, retrying with
backoff while it returns an error. It is deliberately **not** on the boot path:
services start in arbitrary order, and a sites process that refused to serve
until repos answered would take an unrelated service's slow start and turn it
into a site outage. Because the pass is keyed on the flag, every boot re-runs it
harmlessly and a run interrupted halfway simply resumes.

**A seeded site is a normal site from that moment on.** Nothing else in the
design has a "pre-plane" branch: the write path (D33), `sync` (D34), the push
consumer (D35), and the lifecycle verbs (D36) assume a repository exists. Between
boot and the pass completing, a write to a not-yet-seeded site calls repos with a
slug whose repository may not exist yet; repos answers with a failure, the tool
returns it, and the owner retries a moment later. That narrow window is accepted
rather than papered over with a create-on-demand branch in the write path, which
would be a second, rarely-exercised seeding implementation.

**Rejected.**

- **A dedicated one-shot verb the operator runs (`sites seed`).** It would be
  correct once and then be a step someone has to remember for every restored or
  rebuilt box. Startup + a flag makes the invariant "every row has a repository"
  self-restoring.
- **Blocking `serve` on seeding.** Turns repos' availability into sites'
  availability for a one-time migration.
- **Detecting "needs seeding" by asking repos whether the repository exists.**
  An N-call probe on every boot forever, to answer a question a boolean already
  answers, and it makes the pass's cost proportional to the number of sites for
  the entire life of the system rather than once.
- **Seeding lazily, on the first write to each site.** It puts a migration
  branch in the hot path and leaves untouched sites permanently unversioned —
  precisely the sites most likely to matter when someone finally wants history.
- **Committing the tree file-by-file** so the history "shows" the site being
  built. It fabricates a history that never happened; one honest initial commit
  says what is true.
- **Moving or rewriting the served tree as part of seeding** (for example
  exporting it back from repos to normalize it). The tree is live data and is
  already correct; reading it is the whole job.

**Verification.** (Substrate: hermetic. `Seed` is driven directly over a temp
`SITES_ROOT`, a real migrated SQLite DB holding pre-seeded rows, and the
contract-conforming recording repos server of D32.)

- R-FFN9-X9GL — **seeding creates a repository and one initial commit per
  unseeded site.** With two rows at `repo_seeded = 0` — one whose directory
  holds `index.html` and `css/app.css`, one whose directory is empty — `Seed`
  returns 2 and the repos server records: a `Create` for each slug; **exactly
  one** `Commit` for the first, whose change set is exactly the two files with
  their real bytes at the site-relative paths `index.html` and `css/app.css`
  (all writes, no deletes); and **no** `Commit` for the empty site. Afterwards
  both rows report `repo_seeded = 1`, and the first carries the sha the commit
  returned. An implementation that commits per file fails the count; one that
  manufactures an empty commit for the empty site fails the second half.
- R-FGV6-B17A — **re-running is a no-op.** Calling `Seed` a second time against
  the same database returns 0 and produces **zero** repos requests of any kind.
  A site created normally after seeding (already `repo_seeded = 1` via D36's
  `create`) is likewise never revisited. A build that keys on `repo_sha` being
  empty rather than on the flag fails, because the empty site's `repo_sha` stays
  empty forever.
- R-FI32-OSXZ — **seeding is non-destructive.** Capturing every file path and
  its bytes under `SITES_ROOT`, and every row's slug/name/visibility/owner
  fields/`created_at`, before and after a `Seed` — including a run where the
  repos server fails the second site's `Commit` — the two snapshots are
  **identical** in every respect except `repo_sha`/`repo_seeded`, and the failed
  site remains at `repo_seeded = 0` (so a later run picks it up) rather than
  being marked or skipped permanently.
