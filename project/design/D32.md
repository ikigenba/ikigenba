# Decision 32 — The rotating-credential channel: per-environment single-holder secrets in `state/`

**Decision.** This is a **suite contract**: the fifth configuration channel
(`project/design/D21.md`), owning the mechanics of a value class the per-app
parameter (`project/design/D12.md`) structurally cannot hold — a **single-holder
credential the service itself rotates at runtime**. An OAuth **refresh token** is
the motivating case: the provider may issue a new token and revoke the prior one,
so two deployments that share one token cannot coexist — whichever rotates first
revokes the other. Such a value is therefore **per-environment from the start**
(each deployment holds its own, independently consented) and **never traverses a
shared channel**. Where D12 owns channel 2's mechanics, this Decision owns
channel 5's.

**Home: a file under `state/`.** A rotating credential lives as a single file at
a path composed in-binary from `IKIGENBA_ROOT` (`project/design/D11.md`), under
the service's backed-up `state/` region (`project/design/D05.md`), exactly as the
SQLite DB path is composed — `${IKIGENBA_ROOT}/<svc>/state/<NAME>`, mode `0600`.
It is ordinary `state/`: backed up and restored with the rest, so a rotated value
survives both restart and restore. The value is **never** committed config
(channel 1/4), **never** in the per-app parameter (channel 2, D12), and **never**
in the operator keyring push path; the only thing any committed file carries is
the credential's *name and channel*, never its value.

**Declaration.** An app declares a rotating credential in its committed
`<app>/etc/env.list` with the line form

    rotating NAME

alongside the existing `secret NAME` (channel 2) and `config NAME value`
(channel 4) forms. A `rotating` line means: this key is a channel-5 credential —
**not** pushed to SSM, bootstrapped per environment, owned and rotated by the
service in `state/`. The push tooling (D12; `bin/project/design/D02.md`,
informational) derives its parameter key set from `secret` lines only and
**omits every `rotating` line**, so a rotating credential can never reach the
shared parameter.

**Bootstrap: a one-off `opsctl` seed, per environment.** Because the value is
per-environment and never shared, each deployment is seeded independently with
its own freshly-consented credential, once, after first deploy. A **generic
`opsctl` verb** writes a named rotating credential into a service's `state/` file
on the box: it composes the same `${IKIGENBA_ROOT}/<svc>/state/<NAME>` path,
writes the value `0600` from an out-of-band source (a temp file / stdin, never a
command line, matching `bin/push-secrets`' value discipline), and **refuses to
overwrite an existing file** — a credential the service may already have rotated
is never clobbered by a re-seed. A deliberate re-bootstrap is an explicit
`--force`, paired out-of-band with revoking the old grant. Local development
seeds the local checkout's `state/` by the same primitive (or the service's own
consent tool writing that path), so dev and prod each run their own value from
the start. The `opsctl` verb's own design (its name, flags, and error surface)
is `opsctl`'s, realizing this contract's ids `[proof: opsctl]`.

**Rotation: the service is the only steady-state writer.** At boot the service
reads the credential from its `state/` file and **fails loudly if it is absent**
— a never-seeded rotating credential must not start silently, mirroring D12's
launcher hard-fail on a missing parameter. When the provider issues a rotated
value the service writes it back to the same file atomically, so the next boot
reads the current token. `opsctl` writes the file exactly once at bootstrap; the
service owns every write thereafter.

**Rejected.**

- *Keeping rotating credentials in the per-app parameter (channel 2, D12).* The
  parameter is seeded once from a single dev value and is **read-only to the
  service** (the launcher exports it into `manifest.env`, SSM wins on collision),
  so (a) every environment would boot from the same token and the first to rotate
  would revoke the others', and (b) a rotation the service performs at runtime
  could never be written back and would be lost on the next restart. Rejected: a
  service-rotated single-holder value is channel 5, not channel 2.
- *A per-environment SSM parameter for the rotating value, seeded per box.*
  Reintroduces a shared-shaped channel that must be manually kept from
  cross-populating environments; the whole hazard is one value reaching two
  holders. A `state/`-only home makes "separate from the start, never shared"
  true by construction. Rejected.
- *Storing the credential in the service's SQLite DB rather than a plain file.*
  Forces the bootstrap tool to open and write another process's database (schema
  coupling, lock contention). A `state/` file keeps `opsctl` a filesystem tool
  and the seam trivial — the value is a file the service reads and rewrites.
  Rejected.
- *A single suite-wide consent producing one token for every environment.* Is
  exactly the shared-holder failure; a single-holder credential cannot be fanned
  out. Rejected — one consent per environment.

**Verification.** Channel 5's behaviors are proven where each lives; this
contract carries per-tree and per-service proof markers.

- R-EJ1W-1G19 `[proof: bin]` — `bin/push-secrets`, given an `etc/env.list`
  carrying a `rotating NAME` line, assembles a parameter whose key set **omits**
  NAME (a `rotating` key is never pushed), while a `secret` key in the same file
  is still pushed.
- R-EK9S-F7RY `[proof: opsctl]` — the `opsctl` seed verb writes a named rotating
  credential to `${IKIGENBA_ROOT}/<svc>/state/<NAME>` as a `0600` file whose
  bytes equal the supplied value.
- R-ELHO-SZIN `[proof: opsctl]` — the seed verb, run against an already-present
  credential file, **refuses and leaves the file unchanged** (non-zero exit);
  with `--force` it replaces the file.
- R-ENXH-KJ01 `[proof: per-service]` — an adopting service reads its rotating
  credential from the composed `state/` path at boot and **fails loudly when the
  file is absent**, rather than starting without it.
- R-EP5D-YAQQ `[proof: per-service]` — an adopting service, on a provider-issued
  rotation, writes the new value back to the same `state/` file, so a subsequent
  boot reads the rotated value (asserted by round-trip: rotate, restart, read).
