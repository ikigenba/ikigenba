# Decision 25 — The migration-immutability contract: frozen bodies, a hashed manifest, and the mechanical guard

**Problem.** Every schema-owning service applies its embedded migrations
forward-only through the appkit runner, which keys each migration on its
version string alone. The runner therefore **silently skips** an edited body:
a change smuggled into an already-committed migration file reaches every
*fresh* database (test databases, new installs) while every *existing*
database — including the live box — never sees it. The two lineages diverge
without a single failing test: the tree is green, and production is broken.
Until now the rule "never edit a committed migration" was prose in the suite
map and in service conventions — enforcement by willpower, and it has been
violated. This contract makes the rule mechanical.

**Decision.**

1. **A committed migration is immutable.** Once a migration file under a
   service's `internal/db/migrations/` has been committed, its bytes are
   frozen forever. Schema changes only ever *add* a new timestamped migration
   (minted with `bin/create-migration <service> <name>`); a committed file is
   never edited, renamed, or deleted. (This restates the suite map's standing
   rule normatively; this Decision is its single normative home.)

2. **The hashed manifest.** Each service that owns embedded migrations commits
   a manifest at `internal/db/migrations.sha256`, one line per migration file:

   ```
   <sha256-hex>  <filename>
   ```

   lines sorted by filename, hashing the file's exact bytes, `\n`-terminated.
   The manifest covers **every** file in the embedded migrations FS. Adding a
   migration adds exactly one line; nothing else about the manifest ever
   changes. When the guard test fails on a legitimately new migration, its
   failure message names the missing filename and the expected hash line, so
   keeping the manifest true is mechanical.

3. **The guard test.** The service carries a test that walks its embedded
   migrations FS, recomputes each file's sha256, and compares the resulting
   set against the committed manifest, failing on any difference — a changed
   hash (an edited body), a file absent from the manifest (an unmanifested
   addition), or a manifest line with no file (a deletion or rename). The
   comparison is total set equality, and every failure names the offending
   filename. The test reads only the embedded FS and the committed manifest —
   never git history, never the network.

4. **Schema-drift guards select the newest migration by name order, never by a
   hard-coded filename.** Several services assert that their newest
   outbox-shaped migration contains a library DDL constant verbatim (e.g.
   `eventplane`'s `outbox.SchemaSQL`). A guard of that shape that names a
   specific migration file *invites* the violation this contract forbids: when
   the constant is revised, the path of least resistance is to edit the named
   file in place. Such guards MUST resolve their target as the
   lexically-greatest matching migration filename (timestamps make name order
   application order), so a revised constant is satisfied only by adding a new
   migration.

**Rejected.**

- **Prose-only enforcement.** The rule already existed as prose in the suite
  map and in per-service conventions, and was violated by an unattended build
  loop on two services — reaching production undetected. Enforce with systems,
  not willpower.
- **Asserting frozen bodies inside each schema-drift test, per file.** Narrow
  frozen-body string assertions protect only the files someone thought to pin,
  grow without bound, and duplicate the bytes they protect. One manifest
  covers every file uniformly at one line each.
- **A git-history check (comparing worktree bytes against the earliest commit
  of each file).** Tests must not depend on the git repository being present
  or deep (shallow clones, exported trees); the committed manifest carries the
  same truth as reviewable data.
- **Owning the guard in `appkit` as a shared helper.** The check is ~20 lines
  of stdlib per service, and a shared helper would couple every service's test
  suite to an appkit test-support API for no real dedup. Nothing forbids a
  service using a helper later; the contract binds the *behavior*.
