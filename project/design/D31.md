# Decision 31 — The LLM-lint gate contract: a prompt-defined semantic lint pass on every tree's verify gate

**Decision.** This is a **suite contract**. Alongside the mechanical style gate
(D30), every spec-governed tree's verify gate additionally runs **llm-lint** —
a standalone linter whose rules are prompts and whose verdicts come from a cheap
model — over the tree's own files. The gate is **binary**: `llm-lint` exiting 0
passes; **any nonzero exit** (a finding, a missing credential, a model or config
error) is an open gap the tree's build loop must resolve, exactly like a failing
test or a D30 finding. The suite consumes only that pass/fail; it reads no
finding detail and pins nothing about the tool.

**Suite-wide and automatic.** There is no per-tree opt-in and no adoption tier.
Every tree is subject the moment its verify prompt runs the gate — the opposite
of D30's per-tree `.lint-tier` ratchet, and deliberately so: a golangci tier is
a per-tree judgment, but an LLM rule catalog starting from a single rule is not,
and only a suite-wide-automatic gate makes "every tree ready" reachable without
a separate adoption move per tree.

**All rules by default.** llm-lint selects its **entire builtin catalog** when
no `enable` list is configured. The baseline therefore names no rules, so a new
rule added to llm-lint upstream applies suite-wide automatically the next time
the gate runs, with no suite-side change.

**Per-tree control via `.llm-lint.json`.** A tree tunes its own rule set with a
committed **`<tree>/.llm-lint.json`** — llm-lint's native config, discovered by
nearest-ancestor walk-up from the tree root. This is the D30 `.lint-tier`
analogue: a purely tree-local write, made inside that tree's own spec move,
never a cross-tree edit. Because empty-`enable` still means *all rules*, muting
one rule is a one-liner (`{"disable":["<rule>"]}`) that needs no restatement of
the catalog.

**The suite baseline config.** One committed **repo-root `.llm-lint.json`** is
the visible suite-wide policy. It leaves `enable` absent (all rules on) and sets
**`exclude: ["project/**"]`** so no rule ever lints governed spec prose. Every
tree without its own config inherits this baseline by walk-up; a tree with its
own config **replaces** it (discovery is nearest-wins, with no merge), which is
why the baseline carries only rule policy — a value it set that a per-tree file
did not repeat would silently vanish for that tree.

**Direct invocation, no wrapper.** The verify gate runs the `llm-lint` binary
directly — `llm-lint .` from the tree root — with no `bin/`-hosted runner. The
suite pins **nothing** about the tool: not its version, not its model, not its
sampling. llm-lint owns its own configuration and defaults, and if a release
changes them the gate uses the new behavior. This is the deliberate inverse of
D30's tool-pinning stance, and it follows from the binary gate: since the suite
consumes only pass/fail, a wrapper's one surviving job — freezing verdicts so
they never drift — is a guarantee the suite has chosen not to want.

**Preconditions.** The gate needs the `llm-lint` binary on `PATH` and a provider
API key (`GOOGLE_API_KEY` for the default model) in the environment of whoever
runs verify. With either absent, `llm-lint` exits nonzero and the gate fails:
there is **no vacuous pass**, so a tree's verify can never be declared green
without the pass having actually run.

**Enforcement point.** Exactly one: **every spec-governed tree's verify gate**
includes the `llm-lint` step, folded into that tree's definition of "the suite
is green." As with D30, this lands in each tree's generated loop prompts as they
are next regenerated — no big-bang. Because most trees carry pre-existing
fixed-duration test sleeps the current catalog flags, a tree adopts the gate
through its **ordinary build loop**: a red gate is simply suite-not-green, an
open gap the loop closes like any other, using an inline `llm-lint:ignore` for a
sleep that is legitimately the behavior under test. Neither `bin/ship` nor dev
startup runs the gate.

**Rejected.**

- **A `bin/llm-lint` wrapper with version and model pinning (D30 parity).**
  D30's wrapper earns its keep by resolving per-tree tiers, owning the committed
  configs, and freezing the tool version so a verdict never drifts. Three of
  those jobs do not transfer: llm-lint has no tiers, needs no external config
  (enable-all is its default), and resolves per-tree config itself by walk-up
  discovery. Only version pinning would survive — and the binary gate makes even
  that unwanted, since the suite reads pass/fail rather than a stable verdict. A
  wrapper would add a `bin` build phase and proof ids to buy a guarantee
  explicitly declined here. If drift-proofing ever becomes worth its cost, it
  enters as its own Decision.
- **Suite-side model/temperature pinning.** Injecting `--model` or
  `temperature=0` into the gate command would have the suite second-guess the
  tool's own configuration. The tool owns those choices; the suite runs whatever
  it ships. Accepted cost, on the record: a future release can change a verdict,
  and a borderline file can occasionally flip between runs — the tool's call to
  make, consistent with "use the config."
- **Per-tree opt-in adoption (a marker each tree sets before the gate binds).**
  It would reintroduce D30's per-tree ratchet where no per-tree judgment exists,
  and by construction could not deliver "every tree ready" without a move per
  tree. Suite-wide-automatic binds every tree at once and lets each green up on
  its own loop.
- **A graduated or advisory rollout (findings reported but non-blocking).** An
  advisory gate holds by discipline — the very thing D30 and this contract exist
  to replace with a system. The gate is hard; a tree greens up through its build
  loop like any other red bar.

**Verification.** This is a **prose contract with no testable behavior of its
own**, so it carries **no ids**. Its single behavior — a tree's verify fails
when `llm-lint` exits nonzero over that tree — is realized in each spec-governed
tree's own verify loop and generated prompts, and proven there under that tree's
gate, never by the umbrella. The tool's own behavior (rule selection, config
discovery, suppression, exit codes) is proven in llm-lint's own repository, not
here.
