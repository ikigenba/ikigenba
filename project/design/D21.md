# Decision 21 — Configuration-channel routing: which value goes in which channel, and why

**Decision.** This is a **suite contract**: the routing rule that assigns every
configuration value a deployed service consumes to exactly one of four channels.
The channels' *mechanics* are owned elsewhere and cited, never restated here —
this Decision owns only the classification, so that no value ever needs a fifth,
ad-hoc path.

The four channels, and what each carries:

1. **Committed `manifest.env`** (`project/design/D11.md`) — **universal product
   configuration**: values identical on every customer box, shippable in the
   open. Identity/role keys (`APP`, `MOUNT`, `PORT`, `MCP`, `FEED`, `CONSUMES`)
   and every **operator-facing tuning knob** (retention windows, poll intervals,
   concurrency caps, session TTLs, model defaults). A knob is surfaced through
   the appkit `Spec`'s `ManifestExtras`, so the byte-equality drift test pins
   the committed file to the compiled default — the manifest is the complete,
   visible operator surface for universal knobs.
2. **The per-app app-config parameter** (`project/design/D12.md`) — **customer
   data**: every account-specific, uncommitted value, secret or not.
   Credentials and tokens, and equally non-secret account facts (a GitHub org,
   a workspace domain, an admin email list). Declared by the `secret NAME`
   lines of the app's `etc/env.list`, seeded to SSM, exported over
   `manifest.env` at launch (SSM wins on collision).
3. **The box-global environment file** (`/etc/ikigenba/env`;
   `project/design/D11.md`) — **box facts**: values that describe the box, not
   the app or the account's data — `IKIGENBA_DOMAIN`, `IKIGENBA_ROOT`.
   Terraform-provisioned; every unit inherits it; services *compose* from these
   and never restate them.
4. **In-code defaults** (`config.EnvOr` and kin) — **dev fallback only**: the
   value a knob resolves to in a checkout where none of the above is present.
   Every knob remains an env read, so an explicit export (a `config` line in the
   app's `etc/env.list`, a dev harness, or an opsctl verb run) always wins; but
   once a knob is classified into
   channel 1 its manifest line is what production receives, and the code
   default serves only development.

**The routing test**, applied per value: *would the value differ between two
customer boxes?* → channel 2. *Is it a fact about the box/host layout rather
than the app?* → channel 3. *Is it operator-relevant and the same for every
deployment?* → channel 1. *Is it only a development convenience?* → channel 4.
A value that production requires but no channel supplies is a defect: there is
no fifth channel, and "someone remembers to export it" is not a channel.

**Rejected.**

- *Per-customer values in the committed `manifest.env`.* The manifest ships in
  the release bundle, identical for every account — a per-customer value there
  is either wrong for every box but one, or leaks account facts into the repo.
  Rejected; that class is channel 2 by definition.
- *Routing by sensitivity ("secrets channel") instead of by variability.* The
  parameter's live contents already include non-secret account facts; a
  sensitivity rule strands those with no home. Variability between accounts is
  the property that actually decides where a value can live. Rejected (see
  `project/design/D12.md`'s Rejected list).
- *Folding this rule into D11/D12.* Each of those owns the mechanics of one
  channel; the routing rule spans all four, and stating it inside one channel's
  contract buries the classification where the other channels' adopters will
  not look. Rejected — one Decision owns the routing, the channels stay
  mechanical.

**Verification.** This is a prose contract with no testable behavior of its
own — it mints **no requirement ids**. Its enforcement is the channels' own
ids: the manifest drift/portability pair and the no-box-path-literal scan
(`project/design/D11.md`), and the per-service adoption Decisions that classify
each service's values against this rule.
