# Decision 17 — The owner-identity contract: `X-Owner-Id` is the scoping key

**Decision.** This is a **suite contract**: how every service names, stores, and
scopes on the person a request is made for. **`X-Owner-Id` is the stable key;
`X-Owner-Email` is display and audit only.**

Email is user-mutable — the dashboard offers alternate logins whose account
emails the user can edit — so email can never be a durable key. The dashboard
mints a stable opaque identifier per human (`identities.id`, keyed by the IdP
`(iss, sub)` pair) and forwards it on every authenticated request, on all three
auth surfaces, fail-closed.

**The header set.** nginx (via dashboard introspection) injects, and the chassis
reads:

| header | role |
|---|---|
| `X-Owner-Id` | the stable key — every scope, lookup, filter, uniqueness constraint, and authorization comparison uses this and only this |
| `X-Owner-Email` | display and audit only, never keyed on |
| `X-Owner-Name` | display only |
| `X-Owner-Picture` | display only |
| `X-Client-Id` | the acting client/actor |

The chassis identity value carries all five:

```go
type Identity struct {
    OwnerID      string // X-Owner-Id: the stable key
    OwnerEmail   string // X-Owner-Email: display/audit only
    OwnerName    string // X-Owner-Name: display only
    OwnerPicture string // X-Owner-Picture: display only
    ClientID     string // X-Client-Id
}
```

**The gate requires the id.** The chassis identity gate refuses the request (401,
with the ordinary challenge semantics) when `X-Owner-Id` is absent or empty. The
other owner headers are passed through as display data and are never gated on.
The MCP fallback header read follows the same rule, and the health envelope
reports `owner_id` alongside `owner_email` and `client_id`.

**Owner-scoped rows store both, and the email is a write-once snapshot.** Every
table that stores an owner stores two columns, named **`owner_id`** and
**`owner_email`** — those exact names, suite-wide, with no per-service variants:

- `owner_id TEXT NOT NULL` — the scoping and lookup key.
- `owner_email TEXT NOT NULL` — captured from the request headers at row
  creation, **never updated afterward**, never read for logic.

There is deliberately **no refresh mechanism**: no dashboard resolve endpoint, no
local identity cache, no identity events. If a person's email changes, rows
created before and after display different emails. Display may drift; keying
never does — and because both values sit on every row, any later grouping or
re-display fix already has the data it needs.

**Display surfaces carry both.** An MCP result, log field, or health envelope
that exposes an owner today keeps `owner_email` and adds `owner_id`.

**Event payloads follow the same rule.** The event envelope (D18) carries no
owner. A payload that names an owner carries the same **pair** — `owner_id` (the
for-whom key a consumer acts on) plus `owner_email` (the display snapshot) — never
a bare email.

**Rejected.**

- **Keying on email with a rename/merge fixup later.** A mutable key silently
  orphans data at the moment it changes, and the fixup needs a mapping only the
  dashboard has. The stable id already exists; using it costs nothing.
- **A per-service identity cache or a dashboard resolve endpoint.** Both add a
  live cross-service dependency and a staleness class, to fix *display* drift
  that the stored pair already makes fixable offline.
- **Dropping the email column entirely.** Audit and display need the value that
  was true at write time; recovering it later would require the very lookup this
  contract avoids.
- **A grace period where the chassis accepts `X-Owner-Email` as identity.** The
  id header is live on every surface, so a fallback would protect nothing while
  keeping a second identity path alive indefinitely.

**Verification.** This is a **prose contract with no testable behavior of its
own**, so it carries **no ids**. Its behaviors are proven where they are
implemented, informationally: the `Identity` value, the id-requiring gate, the MCP
fallback read, and the health envelope in **appkit**; the minting and forwarding
of `X-Owner-Id` in **dashboard**; and the `owner_id`/`owner_email` column pair,
its scoping use, and its display surfaces in each **service**'s own tree.
