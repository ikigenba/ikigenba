# Decision 14 — The telemetry and correlation contract

**Decision.** This is a **suite contract**: the forensic-telemetry record shape,
the correlation-id standard, and the ingest path every service records against.
It is stated **here, once, normatively** — this Decision *is* the contract, not a
pointer to one. Every implementing workspace (appkit, eventplane, the `telemetry`
service, dashboard, and each adopting service) cites this file and restates none
of it.

**The record allowlist.** A forensic record carries only explicitly chosen
fields — never a raw header dump, never a raw body, never response content:

| field | meaning |
|---|---|
| `id` | recorder-minted ULID |
| `time` | RFC3339Nano, UTC |
| `correlation_id` | the id of the causal chain (below) |
| `service` | emitting service name |
| `kind` | one of the seven kinds (below) |
| `actor` | `owner_email`, `client_id`; omitted when unknown |
| `op` | kind-specific operation string |
| `params` | structured request parameters, captured under the thresholds below |
| `outcome` | `status`, `error`, `duration_ms`, `bytes`, `sha256` |
| `detail` | kind-specific structured detail |

Response content is never stored — outcome, size, and digest only. Digests are
SHA-256, lowercase hex. The allowlist is the principle: a field is recorded
because it was chosen, never because it happened to be on the request.

**The seven kinds** and their `op` idioms:

- `edge` — `<METHOD> <original-uri>`, with `detail.decision` ∈
  `allow` | `deny` | `rate_limited`.
- `request` — `mcp:<tool>` or `<METHOD> <path>`.
- `outbound` — `<METHOD> <host><path>`.
- `publish` — the routing key `<source>:<kind><subject>` (D18).
- `consume` — the same routing key.
- `root` — the origin of a self-started chain, e.g. `cron:tick/<name>`,
  `run:<run-id>`.
- `lifecycle` — `start` | `stop`, with `detail.version`.

**Param capture under threshold.** Structured params are recorded per field. A
JSON-encoded value of **≤ 1024 bytes** is recorded literally. A value over that
cap — or one declared sensitive at tool registration — is replaced **in place**
by:

```json
{"$elided":{"bytes":N,"sha256":"<hex>"}}
```

The per-record `params` budget is **8192 bytes**; when a record exceeds it, the
largest values are elided first until the encoded params fit.

**The correlation standard.** One id per causal chain: a **bare 26-character
Crockford-base32 ULID** (48 bits of millisecond time + 80 bits of cryptographic
randomness), opaque, unique, time-sortable, with no prefix, separators, or
internal structure any consumer may parse. Crockford base32 is the sole allowed
alphabet.

- **Minted once, at the outermost cause** — the user's MCP call, web request, or
  a trigger firing on their behalf — never mid-chain. Everything the chain
  touches carries the same id, propagated **verbatim**; re-minting mid-chain
  severs the trail and is always wrong.
- **Transported over HTTP as `X-Correlation-Id`** (the product's contractual
  constant), the header value being exactly the bare ULID. The chassis
  reads-or-mints. Outbound propagation is **loopback peers only**, never to a
  third party.
- **The edge strips and mints.** A public caller can never supply the id: the
  introspection endpoint mints for gated routes and returns the id in its auth
  response, fragments overwrite anything client-supplied, and ungated public
  locations blank the header so the service mints.
- **Carried on events as an envelope field** (D18's `correlation_id`), not in a
  payload field. Self-originated work mints a `root` record.
- **Durable-root reuse.** When a chain is rooted at a durable entity that already
  has a suite ULID — an ingest job, a run — that entity's own id **is** the
  correlation id; mint fresh only when no durable root exists.
- **New adopters need no registration.** A service lacking a ULID minter copies
  the 26-character time-plus-random Crockford-base32 construction rather than
  inventing a variant.

**The ingest API.** `POST http://127.0.0.1:<telemetry-port>/ingest`,
loopback-only, where the port is `registry.MustPort("telemetry")`. Body:

```json
{"records":[...],"dropped":0}
```

`dropped` is optional; the endpoint answers `202`. Delivery is **best-effort**:
bounded buffering, batching, fire-and-forget. A down or slow sink drops records
and never blocks, errors, or crashes a sender.

**The recursion boundary.** The ingest path itself is never recorded; the
telemetry service's own MCP tools are recorded like any service's.

**Lifecycle.** Every service — telemetry included — emits a `lifecycle` record at
start (carrying its version) and at graceful stop.

**Scope exclusions.** Operator tooling, sandbox internals, and nginx-answered
requests that reach no service are outside the contract.

**Rejected.**

- **W3C Trace Context (`traceparent`) / OpenTelemetry.** A span model with parent
  ids, sampling flags, and a 16-byte hex trace id — none of which the forensic
  goal needs — whose id format conflicts with the suite's committed ULID
  standard. The suite wants chains, not spans, and one contract, not an SDK.
- **Leaving the contract implicit in the implementations.** Fifteen adopters
  reading each other's code is how the correlation standard ended up with one
  adopter and a wrong alphabet in the chassis. A stated contract is the fix, not
  more convention.
- **Two documents (a record protocol beside a correlation standard).** Two
  overlapping normative statements is worse than one; the record rules and the id
  rules are one contract with one home, this file.
- **An event-payload field for the correlation id.** Superseded by the envelope
  field: a payload convention is per-producer and invisible to the plane. The one
  historical adopter (wiki→prompts `group_id`) is re-homed by those services'
  own specs.

**Verification.** This is a **prose contract with no testable behavior of its
own**, so it carries **no ids**. Its behaviors are proven where they are
implemented, informationally: the read-or-mint middleware, the recorder, the
record kinds, and the instrumented outbound client in **appkit**; the outbox
`correlation_id` column, the envelope field, and the consumer-context id in
**eventplane**; the store and the forensic MCP surface in **telemetry**; the
strip-and-mint edge in **dashboard**; and adoption in each service. Suite-level
end-to-end outcomes are checked against the running stack by this workspace's
verification gate (product's success criteria).
