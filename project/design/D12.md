# Decision 12 — The per-app customer-data parameter contract

**Decision.** This is a **suite contract**: the external shape of a service's
deployed **customer data** — where it lives, what a value looks like, and what the
box does with it. *Customer data* is every account-specific, uncommitted value an
app needs: credentials and tokens, and equally the non-secret account facts that
merely must not be baked into a committed file — a GitHub org name, a workspace
domain, an admin email list. Secrets are one kind of customer data, not the
category. The tooling that *writes* a parameter is `bin/`'s
(`bin/project/design/D02.md`, informational); the tooling that *reads* one is the
platform launcher's, out-of-band. This Decision fixes only the point both sides
meet at.

**The parameter.** Every deployable service's customer data lives in **one SSM
parameter per app** — `/ikigenba/<ACCOUNT>/app-config/<app>` (SecureString,
Standard tier, region `us-east-2`) — whose value is a **flat JSON object**
`{ "KEY": "value", … }`. An app with no customer data holds an explicit `{}`:
"nothing customer-specific" is a deliberately seeded state, never an absence.
Parameter *existence* is script-managed (`put-parameter --overwrite` creates on
first push; see research); nothing per-app is Terraform-managed, so adding a
service to the suite requires no infrastructure change. `ACCOUNT` is the account
name each app carries in its `<svc>/etc/deploy.env`.

**The key set is the app's own development environment.** An app declares which
values are customer data in its committed **`<app>/etc/env.list`** manifest: each
`secret NAME` line marks one customer-data key, and the push tooling derives the
parameter's key set from exactly those lines. (`config NAME value` lines in the
same file are dev-only configuration — `project/design/D21.md`'s channel 4 — and
are never pushed.) The `env.list` keyword `secret` marks a value as customer data
bound for the parameter, **not** a claim that the value is sensitive: a non-secret
account fact such as an org name or a workspace domain is a `secret` line because
it is per-account data that must be pushed, exactly as `project/design/D21.md`
routes by variability, not sensitivity. The dev value of each `secret NAME` lives
in the operator's login keyring (libsecret; resolved by
`secret-tool lookup name <NAME>`), one keyed value per name, sensitive or not.
Local and deployed customer-data sets are equal by construction.

**One exclusion: a credential the service rotates.** A single-holder credential
the service itself rotates at runtime — an OAuth refresh token — is **not**
carried here, even though it is per-account. It is channel 5
(`project/design/D32.md`), declared `rotating NAME` (not `secret NAME`) and held
in the service's `state/`, never in this parameter. The push tooling derives the
key set from `secret` lines only and omits every `rotating` line, so such a
credential never reaches the shared parameter — where, seeded once from a single
value and exported read-only to the service, it would be shared across
environments and lost on the next restart.

Because the parameter is per-app, a write is a plain overwrite of the app's own
parameter: there is **no fetch, no merge, no sibling preservation**. Seeding one
service can never touch, corrupt, or drop another's values — the read-modify-write
clobber risk of the shared-blob era is gone by construction.

**The box-side consumer is an external contract**, already live (see research):
the platform launcher (`metaspot/templates/ikigenba-launch`, installed
out-of-band) fetches the app's own parameter, exports each key over `manifest.env`
(**SSM wins on collision**), and **hard-fails on any fetch error including
`ParameterNotFound`** — a never-seeded app must not start. The suite repo does not
own the launcher; this contract only fixes the parameter path, the value shape,
and that hard-fail rule.

**Value fidelity.** A pushed value is preserved **byte-for-byte except that
trailing newlines are trimmed** — interior whitespace, notably the newlines of a
multi-line PEM private key, must survive assembly and delivery unchanged, so a
service reads back exactly what its local environment declared.

**Rejected.**

- *Framing the parameter as a secrets channel.* Its live contents already
  included non-secret account facts (`GOOGLE_WORKSPACE_DOMAIN`, `GITHUB_ORG`);
  a secrets-only definition pushes every non-secret per-customer value toward
  the committed `manifest.env`, where it would wrongly become identical for
  every account. Rejected — the category is *uncommitted customer data*, and
  `project/design/D21.md` states the routing rule.
- *Advanced-tier (8 KB) shared blob.* Defers the same size wall for a monthly fee
  and keeps every write a clobber risk for all fifteen apps. Rejected.
- *Terraform-managed per-app parameters.* Makes every new service a
  `terraform apply`; today a new service touches no infrastructure. Rejected — the
  push tooling creates parameters, and Terraform's only involvement is the one-time
  IAM path grant (already applied).
- *Launcher tolerates `ParameterNotFound` for apps without customer data.*
  Softens the hard-fail contract: a typo'd path or a never-seeded
  credential-carrying app would silently start without its values — the exact
  failure mode the launcher exists to prevent. Rejected for the explicit `{}`
  seed.
- *Pushing an OAuth refresh token (a service-rotated credential) as a `secret`
  key.* The parameter is seeded once from one dev value and exported read-only to
  the service, so every environment would boot from the same token and the first
  rotation would revoke the rest, and a rotation the service performs could never
  be written back. Rejected — a rotating single-holder credential is channel 5
  (`project/design/D32.md`), not channel 2, declared `rotating NAME` and held in
  `state/`.
- *On-disk `~/.secrets/<NAME>` files as the dev value store.* Scatters plaintext
  secret material across the filesystem and couples every tool to a personal
  directory layout. Rejected — the dev value lives in the operator's login
  keyring, encrypted at rest, and the app's `etc/env.list` is the single
  committed declaration of which keys exist; there is no `.envrc` and no
  `~/.secrets` file duplicating that list.
- *Splitting the customer-data key set and the dev config into two files.* One
  more file per app to keep in sync; `etc/env.list` carries both kinds on
  distinct line forms (`secret NAME`, `config NAME value`), so the customer-data
  key set and the dev-only overrides are declared once, together, and the push
  tooling reads only the `secret` lines. Rejected.

**Verification.**

This contract mints **no requirement ids**. Both of its halves sit outside any
tree the green gate can assert against: the box-side consumer is an external,
already-live contract (see research: all deployed services healthy on per-app
parameters, `github_auth: ok` proving end-to-end flow), and the
repo-side writer is `bin/` shell tooling, verified once outside the build loop —
including one live push of an app carrying a **multi-line value** (a PEM private
key), read back by key *shape* only (per-key value length and line count, never a
value) to confirm interior newlines survive. Where that verification happens is
`bin/project/design/D02.md`'s (informational).
