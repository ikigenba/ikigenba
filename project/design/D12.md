# Decision 12 — The per-app secrets parameter contract

**Decision.** This is a **suite contract**: the external shape of a service's
deployed secrets — where they live, what a value looks like, and what the box does
with them. The tooling that *writes* a parameter is `bin/`'s
(`bin/project/design/D02.md`, informational); the tooling that *reads* one is the
platform launcher's, out-of-band. This Decision fixes only the point both sides
meet at.

**The parameter.** Every deployable service's deployed secrets live in **one SSM
parameter per app** — `/ikigenba/<ACCOUNT>/app-config/<app>` (SecureString,
Standard tier, region `us-east-2`) — whose value is a **flat JSON object**
`{ "KEY": "value", … }`. A secret-less app holds an explicit `{}`: "no secrets" is
a deliberately seeded state, never an absence. Parameter *existence* is
script-managed (`put-parameter --overwrite` creates on first push; see research);
nothing per-app is Terraform-managed, so adding a service to the suite requires no
infrastructure change. `ACCOUNT` is the account name each app carries in its
`<svc>/etc/deploy.env`.

Because the parameter is per-app, a write is a plain overwrite of the app's own
parameter: there is **no fetch, no merge, no sibling preservation**. Seeding one
service can never touch, corrupt, or drop another's secrets — the read-modify-write
clobber risk of the shared-blob era is gone by construction.

**The box-side consumer is an external contract**, already live (see research):
the platform launcher (`metaspot/templates/ikigenba-launch`, installed
out-of-band) fetches the app's own parameter, exports each key over `manifest.env`
(**SSM wins on collision**), and **hard-fails on any fetch error including
`ParameterNotFound`** — a never-seeded app must not start. The suite repo does not
own the launcher; this contract only fixes the parameter path, the value shape,
and that hard-fail rule.

**Value fidelity.** A pushed value is preserved **byte-for-byte except that
trailing newlines are trimmed** — interior whitespace, notably the newlines of a
multi-line PEM private key, must survive assembly and delivery unchanged, so a
service reads back exactly what its local environment declared.

**Rejected.**

- *Advanced-tier (8 KB) shared blob.* Defers the same size wall for a monthly fee
  and keeps every write a clobber risk for all fifteen apps. Rejected.
- *Terraform-managed per-app parameters.* Makes every new service a
  `terraform apply`; today a new service touches no infrastructure. Rejected — the
  push tooling creates parameters, and Terraform's only involvement is the one-time
  IAM path grant (already applied).
- *Launcher tolerates `ParameterNotFound` for secret-less apps.* Softens the
  hard-fail contract: a typo'd path or a never-seeded secret-carrying app would
  silently start without secrets — the exact failure mode the launcher exists to
  prevent. Rejected for the explicit `{}` seed.
- *A per-service secrets manifest file instead of deriving the key set from the
  app's own development environment.* A second list to keep in sync with the first;
  the development environment already **is** the list, which is what makes local
  and deployed secret sets equal by construction. Rejected.

**Verification.**

This contract mints **no requirement ids**. Both of its halves sit outside any
tree the green gate can assert against: the box-side consumer is an external,
already-live contract (see research: all deployed services healthy on per-app
parameters, `github_auth: ok` proving end-to-end secret flow), and the
repo-side writer is `bin/` shell tooling, verified once outside the build loop —
including one live push of an app carrying a **multi-line secret** (a PEM private
key), read back by key *shape* only (per-key value length and line count, never a
value) to confirm interior newlines survive. Where that verification happens is
`bin/project/design/D02.md`'s (informational).
