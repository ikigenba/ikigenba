# Decision 22 — Library dependency versioning: unversioned in-repo siblings, one suite-wide agentkit pin, a replace-free workspace

**Decision.** This is a **suite contract**: how every module in the mono-repo
consumes its library dependencies. It governs three channels, each with one
rule, and it names no version number anywhere — every check below is a check of
*form* or *agreement*, so the contract cannot go stale as pins advance.

**In-repo shared libraries (`appkit`, `eventplane`, `registry`) are consumed as
unversioned workspace siblings.** A consumer's committed `go.mod` states
`require <lib> v0.0.0` paired with `replace <lib> => ../<lib>` (the relative
path to the sibling tree). Never a tagged require: the libraries are
deliberately unversioned — there is one repo, one HEAD, and the production
build (`GOWORK=off`, inside a full worktree of HEAD) resolves the sibling by
the relative replace with no registry and no network. `v0.0.0` is the
placeholder Go requires syntactically; the replace always wins, so the number
is never resolved.

**Module paths in committed `go.mod` files are written as plain literals.** A
Go-quoted or escape-carrying module string (e.g. a `\x`-escaped path) is
byte-identical to the toolchain but invisible to textual verification — its
only effect is to defeat a reader or a check, so it is forbidden outright.
Mechanical checks parse the real module graph (`go mod edit -json`), which no
string escaping can evade.

**External first-party modules (`github.com/ikigenba/agentkit`) are consumed as
tagged modules with one suite-wide pin.** Every consumer's committed `go.mod`
states the **same** agentkit version; the contract is *agreement*, not a named
number — the pin advances by updating every consumer in one change. Divergent
pins are a defect: they mean two services ship against different library code
while claiming the same dependency.

**The committed workspace (`go.work`) wires modules and nothing else — it
carries no `replace` directive.** A workspace replace overrides every module's
committed pin silently, so dev compiles code prod never sees; the one such
directive this contract removed hid an eleven-minor-version divergence in a
consumer's pin. Working against a local checkout of an external module is done
with a *temporary, uncommitted* workspace edit, removed before commit.

Third-party dependency versions (the `golang.org/x/*` family and the rest) are
**deliberately not governed**: each module is its own Go module and minimal
version selection legitimately leaves different modules at different floors.
Raising a floor is routine maintenance, not contract conformance.

**Rejected.**
- *Tag and version the in-repo libraries.* Versioning theater inside one repo:
  every consumer ships from the same HEAD, so a tag adds release ceremony and a
  second source of truth with no independent consumer to serve. Rejected;
  the libraries stay unversioned (they carry no `VERSION` file either — that is
  the deployable-app mechanism, `root project/design/D03.md`).
- *Keep a committed `go.work` replace for local agentkit development.* This is
  the arrangement this contract explicitly removes: it pointed at an absolute
  path in one operator's home directory (tying the workspace to one machine)
  and masked consumers' committed pins in every dev build. Rejected; local
  library hacking uses a temporary uncommitted edit.
- *Vendor dependencies for the `GOWORK=off` build.* The relative replaces
  already make the production build hermetic for in-repo code, and agentkit is
  a verified, publicly fetchable tagged module; vendoring adds a large
  committed tree to solve a solved problem. Rejected.
- *Govern third-party version alignment.* Different modules at different
  minimal versions is how Go modules work; forcing repo-wide alignment is
  hand-maintained busywork with no defect it prevents. Rejected — only the
  first-party channels above are contractual.

**Verification.** Proven in the `bin` tree (`bin/bintest`), which owns
repo-root-scoped checks; each behavior reads **every committed `go.mod` in the
repo** via the parsed module graph (`go mod edit -json`), never a raw-text grep
an escape could evade.

- R-3R5W-79JK [proof: bin] — every committed `go.mod` that requires an in-repo
  library (`appkit`, `eventplane`, `registry`) requires it at exactly `v0.0.0`
  **and** carries a `replace` of that library to the relative sibling path
  (`../<lib>`); a tagged in-repo require, or a require with no matching
  relative replace, fails. Substrate: bintest unit over the parsed module
  graphs of all committed `go.mod` files.
- R-3SDS-L1A9 [proof: bin] — every module path written in a committed `go.mod`
  is a plain literal: the raw file bytes contain no quoted module path carrying
  an escape sequence (the parsed path and the written path are byte-identical).
  A `\x`-escaped module string — accepted by the toolchain, invisible to text
  search — fails. Substrate: bintest unit comparing `go mod edit -json` output
  against the raw file bytes.
- R-3TLO-YT0Y [proof: bin] — all committed `go.mod` files that require

  consumers pinning different versions fail. Substrate: bintest unit over the
