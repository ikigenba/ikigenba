# Decision 24 — The version plane: repos is the suite's git custodian

**Decision.** This is a **suite contract**: the fourth plane. The auth plane
decides who a request is from, the event plane (D18) moves small facts, the
content plane (D19) moves file bytes — and the **version plane** owns *history*.
Every piece of authored content in the suite — a hosted site, a script, a
prompt, and plain code repositories — is a git repository held by the **repos**
service, and everything else (serving, running, laptops, agents, workflows) is
a consumer of refs.

> **Versioning is ambient.** Creating a site, script, or prompt implicitly
> creates its repository; every mutation made through any service's MCP surface
> becomes a commit; nobody performs a git action to get history, and git is
> invisible until the day a user wants history, a laptop checkout, or an
> automated change — and then it is already true.

**Custody and addressing.** repos holds one **bare** git repository per
versioned artifact under its own `state/`, keyed `<kind>/<name>`. The kinds are
`sites`, `scripts`, `prompts` (each owned by the service of that name; the
`name` is that service's own key — a site slug, a script name — so the plane
adds no second namespace), and `code` (plain repositories owned by no other
service, created directly through repos). The owning service is responsible for
name uniqueness within its kind and calls repos' rename when its key changes.
No other service reads repos' disk; refs and bytes cross only repos' loopback
surfaces and the git door.

**`main` is live.** What is served or runnable is always the tip of `main`.
A service's own writes (vibe edits) commit **straight to `main`**, attributed
to the acting `X-Client-Id`; rapid successive writes may coalesce into one
commit. Force-pushes to `main` are rejected; every other ref is unrestricted.

**The materialized copy.** A service never serves or executes out of repos'
tree. Each owning service keeps its own **materialized copy** of `main` (a
plain exported tree, no VCS metadata) under its own `state/`, and each run
executes against a checkout **pinned to a commit sha** recorded on the run. On
the service's *own* write, the commit and the local copy update synchronously
in the same tool call, so edits stay live-immediately. *External* changes —
laptop pushes, merged branches — arrive as `repos:push` events, on which the
owning service refreshes its copy.

**One git door.** repos serves git **smart-HTTP** for every repository at its
mount (`/srv/repos/git/<kind>/<name>.git`). Two authenticated paths, one door:

- **Humans, through nginx**: a dashboard-minted personal access token supplied
  as the HTTP **Basic password** (username ignored), validated by the same
  dashboard introspection that gates every bearer surface. The owner may push
  directly to `main`.
- **On-box runs, over loopback**: a short-lived **run token** minted by repos
  and injected at run start; scoped to one repository, fetch plus push to
  non-`main` refs. Runs perform real `git clone`/`push` — no second
  materialization API exists for them.

**Merging.** Humans merge by default; automation merges only when authored.
repos exposes a single `merge` verb (branch into `main`) callable by the owner
and by workflows alike; a script or prompt merges only because its author wrote
the call into its body — there is no ambient end-of-run merge. The verb refuses
on conflict and, when the repository has **required statuses**, on any red or
pending status for the branch head. CI is not a mechanism of this plane: a
check is an ordinary scripts/prompts workflow triggered on `repos:push/…` that
clones the pushed sha, does its work, and posts a status back to repos. A
repository with no statuses has no gate.

**Events.** repos is an event producer: at minimum a `push` family (subject
`/<kind>/<name>`, payload carrying branch, sha, and actor) on every ref update,
so owning services refresh, CI triggers fire, and notify can announce proposed
branches. Exact families are repos' spec's to own.

**Archive, never casual deletion.** Deleting an artifact through its owning
service removes the service's row and materialized copy immediately, but repos
**archives** the bare repository (hidden from listings, recoverable) rather
than deleting history; reclaiming disk is a separate deliberate operator act.
repos' `state/` is primary customer data under the D05 backup boundary.

**Relation to the content plane (D19).** repos is an ordinary content-plane
holder: its loopback endpoints serve tree bytes addressed by its own key
(`kind/name`, path, ref), and a commit sha is a native `rev`. This plane is
**not** the "shared blob store" D19 rejects: it owns versioned artifact
*histories* whose namespace is the owning services' own keys, while each
service keeps its domain, its metadata, and its own serving copy. Point-to-point
byte transfer between services remains D19's business, unchanged.

**Rejected.**

- **Per-service git.** Each service embedding its own git custody would put the
  git binary, auth plumbing, commit discipline, and event publication in four
  trees instead of one, and lose the single choke point where attribution and
  history live.
- **A GitHub-backed store.** GitHub as the canonical store would force per-repo
  ceremony (repo creation, credentials, sync) onto artifacts whose users never
  asked for GitHub. Mirroring to GitHub is a future, per-repository, opt-in
  binding; in this contract's scope GitHub is untouched — nothing reads or
  writes it.
- **A platform-side merge posture for workflows.** An automatic end-of-run
  merge (or a mandatory proposal step) would relocate intent from the
  workflow's author to the platform. Merging is a verb in the workflow's own
  body; the author's text is the policy.
- **A second gate beside statuses.** Repos executing check scripts itself would
  reintroduce arbitrary code execution into the custodian; statuses posted by
  ordinary workflows keep repos execution-free.
- **Branch-then-merge ceremony for the owner.** Forcing the owner's laptop
  pushes through branches and reviews contradicts ambient versioning; trust is
  asymmetric by design — humans push `main`, automation earns `main` through
  authored merges and green statuses.

**Verification.** This is a **prose contract with no testable behavior of its
own**, so it carries **no ids**. Its behaviors are proven where they are
implemented: custody, the git door, tokens, merge, statuses, archive, and the
`push` events in **repos**; the materialized copy, synchronous own-write
apply, event-driven refresh, sha-pinned runs, and seeding in **sites**,
**scripts**, and **prompts**; Basic-password PAT validation on the git
location in **dashboard** — each in its own tree.
