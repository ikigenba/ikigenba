# Decision 28 — The changelog contract: per-app `CHANGELOG.md`, authored at bump time, enforced by bump

**Decision.** This is a **suite contract**: the per-release record every
deployable app keeps of what changed, and the release-time gate that keeps it
from going stale. It binds the fifteen VERSION-carrying apps (which carry the
file) and the off-box release tooling in `bin/` (which enforces it); the
tooling's own mechanics are specified in `bin/project/` (informational), which
adopts this contract.

**Which trees.** Every deployable app — exactly the trees with a committed
`<app>/VERSION` file — keeps a committed `<app>/CHANGELOG.md` beside it. The
unversioned trees (`appkit`, `eventplane`, `registry`, `opsctl`, `bin`,
`nginx`) carry none, by construction: the changelog anchors to `VERSION`, and
`bin/bump` operates only on VERSION-carrying apps.

**File shape.** A `# Changelog` title, then one section per release, newest
first. Each section is:

```
## vX.Y.Z — YYYY-MM-DD

- search matches phone numbers
- feed reconnects after nginx restart
```

The heading's version is the canonical `v`-prefixed SemVer form
(`root project/design/D03.md`) and equals the `<app>/VERSION` that release
committed. Bodies are plain `-` bullets only — no `Added`/`Changed`/`Fixed`
category subsections. Entries are **short, concise, and outcome-level**:
a few one-line bullets a box operator can read to learn what a release
changes, never commit narration or work-session detail. The audience is
**operator-first**, phrased so a customer could also read it; nothing on the
box serves or consumes the file.

**Authoring: at bump time, nothing staged.** There is no `Unreleased`
section and no per-merge discipline. The session performing a release
authors the new top section immediately before running `bin/bump`:
`git log` over `<app>/` since the app's previous VERSION commit is the
denominator of what the release contains, and `bin/bump <app> <part>
--dry-run` answers which version the heading must carry. Every release gets
a new section — a release with no operator-visible change satisfies the gate
with a single line (e.g. `- dependency rebuild`).

**Enforcement: bump is the gate.** `bin/bump` refuses to mint a version
unless the **first `## ` heading** of `<app>/CHANGELOG.md` carries exactly
the version it is about to write to `<app>/VERSION`; on refusal it exits
nonzero having written nothing and committed nothing. On success its
path-limited commit widens to exactly two paths — `<app>/VERSION` and
`<app>/CHANGELOG.md` — so main never holds a version whose changelog
disagrees. Bump validates the version token only; the date and the entry
text are the author's, unchecked.

**Seeding and ownership.** `CHANGELOG.md` is committed **operator data**,
exactly like `VERSION`: it is written by the release session and committed
by bump, never produced or edited by any build loop, and it is not governed
source in any subproject spec. Each existing app is seeded once, by the
operator, with a single baseline section for its current version whose one
bullet notes that earlier history lives only in git; no history is
reconstructed.

**Rejected.**

- *One suite-wide `CHANGELOG.md`.* The fifteen apps version and ship
  independently; a single log interleaves unrelated release streams and has
  no one version to anchor an entry to. Per-app files sit beside the
  per-app `VERSION` they describe.
- *An `Unreleased` staging section promoted by bump (or any continuous
  per-merge discipline).* This repo has no per-merge human moment — build
  loops commit autonomously — so the discipline has no enforcer, and
  accumulating entries as work lands encourages long, over-detailed logs.
  Authoring once at release time, from git history, keeps entries short and
  keeps bump's check trivial.
- *Keep-a-Changelog category subsections.* With entries deliberately few
  and one line each, categories are ceremony that invites padding.
- *Reconstructing history for the seed.* Expensive, of doubtful accuracy,
  and serving no decision anyone faces; git already holds the history.
- *Per-service proof ids.* Apps carry no changelog test: a missing or
  stale file is caught mechanically at the only moment it matters — bump
  time — so the behavior is proven once, in the tree that owns bump.

**Verification.** All enforcement lives in `bin/bump`; each id's tagged test
lives in `bin`'s declared proof tier.

- R-CKLX-X89X — with no `<app>/CHANGELOG.md` present, `bin/bump` exits
  nonzero, leaves `<app>/VERSION` unchanged, and creates no commit.
  [proof: bin]
- R-CLTU-B00M — when the first `## ` heading of `<app>/CHANGELOG.md`
  carries a version token other than the exact version bump is about to
  mint (e.g. the previous release's), `bin/bump` exits nonzero, leaves
  `<app>/VERSION` unchanged, and creates no commit. [proof: bin]
- R-CN1Q-ORRB — with a top heading matching the minted version, the single
  commit `bin/bump` creates contains exactly two paths: `<app>/VERSION` and
  `<app>/CHANGELOG.md`. [proof: bin]
- R-CO9N-2JI0 — `bin/bump <app> <part> --dry-run` prints the next version
  and writes no file, creates no commit, and pushes nothing, even when
  `<app>/CHANGELOG.md` is absent or its top heading mismatches — so the
  author can learn the version before writing the heading. [proof: bin]
