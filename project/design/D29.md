# Decision 29 — The brand icon contract: the shipped set, its static location, and the link markup

**Decision.**

Every service in the suite that serves HTML presents the **same browser-chrome
identity**: one icon set, one set of filenames, one markup shape. A user moving
between the dashboard at the apex and any `/srv/<svc>/` page sees one product,
not sixteen unrelated programs that happen to share a hostname.

**The shipped set is three files, and only these three:**

| file | what it is | why it ships |
|---|---|---|
| `favicon.ico` | multi-resolution ICO carrying 16×16, 32×32, 48×48 | answers the bare `/favicon.ico` request a browser makes with no markup at all, and covers legacy and bookmark surfaces |
| `favicon-32.png` | 32×32 PNG | what a modern browser prefers when both are offered |
| `apple-touch-icon.png` | 180×180 PNG | the iOS home-screen surface |

The canonical bytes live at **`design/brand/`** in the repo, alongside
`design/tokens.css` and `design/carbon.md`, and are copied into each tree by
hand exactly as `tokens.css` and the `.woff2` fonts already are. `design/` is
not spec-governed and owns no contract; it is the shared reference the trees
copy *from*. The masters that produced the set (`favicon-master.png`,
`banner.png`) live there too and ship nowhere.

**Nothing else ships.** A 16×16 PNG is redundant with the ICO's own 16×16
entry. The 192×192 and 512×512 PNGs exist to feed a **web app manifest**, and no
tree in this suite serves one; shipping them would put 245 KB per tree on disk
that nothing references. If the suite later adopts a manifest, that is its own
Decision and it brings those sizes back with it.

**The static location is the service's own static root**, the same directory
that already holds its `tokens.css` and its fonts. The suite has two shapes and
this contract binds both without preferring either:

    <svc>/share/www/static/          on-disk, installed as share/<v>/www/static
    <svc>/internal/web/static/       embedded into the binary with go:embed

**The markup is three `<link>` elements**, carried by **every HTML document the
service serves** — not only its landing page:

```html
<link rel="icon" href="static/favicon.ico" sizes="any">
<link rel="icon" type="image/png" href="static/favicon-32.png">
<link rel="apple-touch-icon" href="static/apple-touch-icon.png">
```

`sizes="any"` marks the ICO as the multi-resolution fallback so a browser that
understands both prefers the PNG rather than rasterizing the ICO.

**The `href` form is whatever the service already uses to reach its own static
mount** — this contract fixes the *target*, never the string. A service mounted
under `/srv/<svc>/` uses the relative `static/…` form its `tokens.css` link
already uses, so the page works identically behind the prefix-stripping front
door and on the bare loopback port. The apex dashboard uses the absolute
`/static/…` form its own stylesheet links use. A service that renders its
`<head>` through a shared layout with a mount variable keeps using that
variable. Any of these conforms; what does not conform is a URL that resolves
outside the service's own static mount.

**Content types are pinned by the service, never inherited from the box.**
`favicon.ico` is served as `image/x-icon` and both PNGs as `image/png`. Go
registers no MIME type for `.ico`, so an unpinned service falls through to
either the box's `/etc/mime.types` — which may not exist, and may disagree
between the dev machine and the live box — or to content sniffing. Both are
ambient state, and the suite already refused ambient state for fonts. A service
whose static path runs through `appkit/web` inherits the pinning from that
package's registration; a service serving its own static subtree pins `.ico`
itself, in its own code.

**Every service answers the bare `/favicon.ico` at its own root**, with an
explicit route. A `/static/` mount does not answer it: `/favicon.ico` and
`/static/favicon.ico` are different paths, and serving the second does not serve
the first. Each service therefore mounts `GET /favicon.ico` and **serves the
same bytes** its `static/favicon.ico` response carries, with the same pinned
`image/x-icon` type.

The route exists because the bare request is the one a client makes with no
markup at all: the speculative request a browser fires before it has parsed a
`<head>`, and the only request a client that never parses markup will ever make.
Two properties follow from who is asking. It is **ungated** — the same posture
`/static/` already has — because a client that cannot authenticate gets nothing
useful from a session redirect, which is the same failure as a `404` wearing a
different status code. And it **serves rather than redirects** to the static
path: a hop costs a round trip and fails outright for any client that does not
follow redirects, which is exactly the population this route exists to serve.

Where the request comes from differs by service, and both contexts are real. All
sixteen services share one origin in production, so a browser's unprompted
root-relative request lands on the apex and therefore on the dashboard. The
fifteen services under `/srv/<svc>/` see it in local development, where
`bin/start` runs each on its own loopback port and a browser pointed at that port
does issue it. They also see it in production, since nginx strips the
`/srv/<svc>/` prefix before forwarding, so `/srv/<svc>/favicon.ico` arrives at
the service as `/favicon.ico` and is answered by the same route.

**Only `favicon.ico` gets a root alias.** The root probes for
`/apple-touch-icon.png` and `/apple-touch-icon-precomposed.png` are iOS
Safari's fallback for a page that carries no `apple-touch-icon` markup, and
R-RYDN-YNR5 requires that markup on every document in every service, so the
fallback never fires here.

**This contract does not govern brand marks.** The `logo.png` served by the
dashboard header and the wiki brand link is a different asset with a different
job, and neither is touched here.

**Rejected.**

- **One copy of the bytes, served by `nginx` from a single suite-wide path.**
  It saves about 4.5 MB across the repo and costs every landing page a runtime
  dependency on a front door it does not own. Worse, the local-dev `:8080`
  front door and the live box would each need the route, and a service run
  straight on its loopback port would have no icons at all — so the same page
  would break differently in three environments. The suite already answered
  this question for `tokens.css` and the fonts by duplicating them per tree, for
  the same reason: a service's shipped bundle is complete on its own. Rejected.
- **One committed copy that each tree's build phase reads from `design/brand/`
  at build time.** This is a scope violation by construction: a `project/`
  governs only the tree it sits at the root of, so no service Decision may name
  a file in `design/`. The hand-copy is the same act, performed once by the
  build loop and then committed inside the tree, which keeps every Decision
  inside its own boundary. Rejected.
- **Ship the full eight-file set so nothing is missing later.** Each tree
  currently carries 112 KB of static payload; the full set adds 293 KB, nearly
  tripling it, and 212 KB of that is a single 512×512 PNG that no markup in the
  suite references. Unreferenced bytes in a shipped bundle read as cargo to the
  next reader and cost a real fraction of every release artifact. Rejected —
  the set grows when a manifest Decision needs it to.
- **Let content sniffing determine the `.ico` type.** It works: Go's sniff
  table maps the ICO magic bytes to `image/x-icon`, so every serving path in the
  suite happens to land correctly today. It is still correctness by accident,
  and it is silently defeated the moment a box grows an `/etc/mime.types` that
  disagrees, because `mime.TypeByExtension` is consulted first. The suite
  already registered `.woff2` explicitly rather than trust this. Rejected for
  the same reason.
- **Extend the contract to `nginx/parked/index.html`.** The parked page answers
  hosts that reached the box by mistake, and its own Decision
  (`nginx/project/design/D03.md`) keeps it bare on purpose. A branded tab icon
  there advertises the box's identity to precisely the traffic that should learn
  nothing from it, and it would give a static page its first installed-asset
  dependency. Rejected; the parked page stays out.
- **Leave the bare `/favicon.ico` unanswered and rely on the `<link>` markup.**
  Every modern browser reads the markup, so tabs, bookmarks, and the iOS home
  screen already show the mark without a root route. It fails the clients this
  set was assembled for: the file table above justifies shipping the ICO at all
  by the bare request, so an unanswered root path makes 15 KB per tree
  unreferenced by anything and reduces the ICO to the same cargo the 512×512 PNG
  was rejected for. Answering the request is cheaper than re-arguing the file.
  Rejected.
- **Redirect `/favicon.ico` to `/static/favicon.ico` instead of serving it.** It
  is a one-line mount and it reintroduces the failure at a different layer: the
  clients worth this route are the ones that do not parse markup, and the
  overlap with clients that do not follow redirects is not empty. It also costs
  a round trip on the request a browser fires before anything else. Serving the
  bytes directly is the same amount of code. Rejected.
- **Prove the root route once in `appkit` rather than per service.** The chassis
  mount would cover thirteen services. It would not cover `artifacts` and
  `github`, which register their own embedded static handlers, or `dashboard`,
  which registers its own table through the Apex bypass — three trees have
  already diverged from the chassis on exactly this route. A library-level proof
  also states the wrong claim: the behavior is that an assembled service answers
  a request, which is why R-RZLK-CFHU is per-service too. Rejected.
- **Mint one id per file per service.** Three files times sixteen services is
  forty-eight handles for two behaviors. The contract's behaviors are "the
  markup is present" and "the assets are served"; the file count is a detail
  inside each. Rejected.

**Verification.**

All three ids are `[proof: per-service]`: the behavior binds each adopting
service individually, so each proves it in its own tree, and a service adopts by
citing the id.

- R-RYDN-YNR5 — `[proof: per-service]` — every HTML document the service serves
  carries all three link elements, each resolving to the service's own static
  mount: `rel="icon"` with `sizes="any"` pointing at `favicon.ico`,
  `rel="icon"` with `type="image/png"` pointing at `favicon-32.png`, and
  `rel="apple-touch-icon"` pointing at `apple-touch-icon.png`. A service that
  serves more than one document proves it for **every** one of them, so a page
  added without the links fails rather than passing by omission; a document
  carrying two of the three fails.
- R-RZLK-CFHU — `[proof: per-service]` — a request for each of the three asset
  paths, issued **through the composition root** — the service's real assembled
  router or spec, reached at its mounted path, never a handler the test
  constructs — returns `200` with a non-empty body and the pinned content type:
  `image/x-icon` for `favicon.ico` and `image/png` for both PNGs. The type is
  asserted as an exact match, so a service that inherits `image/vnd.microsoft.icon`
  from a box MIME database fails rather than passing on a near-miss.
- R-8MFA-HUNC — `[proof: per-service]` — a `GET /favicon.ico` issued at the
  service's **root path**, **through the composition root** — the service's real
  assembled router or spec, never a handler the test constructs — returns `200`
  with `Content-Type` exactly `image/x-icon` and a body **byte-identical to the
  same router's `GET static/favicon.ico` response**. The byte comparison is the
  discriminating property: a route that serves some other file, an empty body,
  or a placeholder passes a status check and fails this one. A `3xx` fails the
  id outright — the route serves the bytes and does not redirect to the static
  path — and so does any response that depends on an authenticated session,
  since the test issues the request with no credentials of any kind.
