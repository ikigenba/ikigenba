# Decision 26 — The run-lifetime contract: a bounded run TTL and the derived run-token lifetime

**Problem.** A sandboxed run's git credential (the run token, root
`project/design/D24.md`) is deliberately reachable by the run itself, so its
lifetime is the temporal bound on a leak. That lifetime used to be governed
twice: each run-spawning service asked for its run TTL plus a margin, and repos
enforced a second, independently configured ceiling (`REPOS_RUN_TOKEN_TTL`).
The second path was configuration nothing used on a healthy box — the
requested value sat far under the ceiling — and it invited exactly the failure
it pretended to prevent: a run TTL raised past the ceiling would have produced
tokens silently shorter than their runs, surfacing as a baffling mid-run
authentication failure instead of a loud configuration error. One bound,
enforced at the source, replaces both.

**Decision.** This is a **suite contract** for every run-spawning service
(today prompts and scripts; any future service that mints run tokens adopts it
by citation).

1. **The run TTL is bounded at 6 hours.** A run-spawning service's run-TTL
   knob (`PROMPTS_RUN_TTL`, `SCRIPTS_RUN_TTL`, …) is operator-configurable
   with a hard suite-wide maximum of **6h**. The bound is a named constant in
   the adopting service, checked at the composition root: a configured run TTL
   over 6h (or zero/negative) refuses to boot — `serve` exits nonzero with an
   error naming the variable, its configured value, and the 6h maximum. Boot
   is the earliest point the defect is detectable; a clamped or ignored value
   would be a silent second policy.

2. **The run-token lifetime is derived, never configured.** The token a
   service mints for a run lives exactly the service's **configured run TTL
   plus a fixed ten-minute margin**. The margin absorbs what happens outside
   the run's own clock — the clone that precedes spawn and the final push at
   the run's deadline — so a token never expires before the run it serves.
   There is no per-service margin knob and no token-TTL knob anywhere: the
   only configuration is the run TTL itself, and the token's lifetime follows
   from it deterministically.

3. **The plane honors the request verbatim.** repos' mint endpoint takes the
   requested lifetime as a **required** argument and issues exactly what was
   asked; it applies no ceiling, no default, and no clamp of its own. The
   security property "no run credential outlives its bound" lives in this
   contract's 6h cap at the source, not in a second enforcement point.
   (Endpoint behavior — required field, rejection of absent or non-positive
   values — is repos' spec's to own and prove.)

**Rejected.**

- **A plane-side ceiling in repos (`REPOS_RUN_TOKEN_TTL`).** The prior shape.
  It could not be checked against the callers' run TTLs (repos cannot see
  their config), so an inconsistency surfaced as a silently capped token and a
  mid-run credential death rather than a startup error. It was also a second
  operator-facing knob whose only correct setting was "comfortably above every
  run TTL" — configuration with one right value is a constant, not a knob.
- **A configurable margin.** The margin covers clone time and the final push;
  it has one job and one sane value. A knob would be a second path to a token
  shorter than its run.
- **Capping in the plane *and* at the source.** Two enforcement points for one
  property drift independently; the failure mode of the pair (source raised,
  plane stale) is worse than either alone.
- **No bound at all.** A run TTL is the box's runaway backstop and the token
  lifetime rides on it; an unbounded knob makes a fat-fingered `720h` a
  month-long live credential factory.

**Verification.** Both ids are `[proof: per-service]`: every adopting service
carries its own tagged test.

- R-34EZ-J9BF — with the service's run-TTL variable configured **above 6h**,
  `serve` fails at startup: the process exits nonzero and its error output
  names the variable and the `6h` maximum, and no server starts; with the same
  variable at **exactly 6h** the service boots. A build that clamps, warns, or
  ignores the value fails the first half. Substrate: hermetic test driving the
  serve path with an injected environment.
- R-35MV-X124 — the run-token mint request the service issues at run spawn
  carries a `ttl` equal to the service's **configured run TTL plus exactly
  10m** (with a 30m run TTL, `40m`); a build that omits the field, uses the
  run TTL bare, or applies any other margin fails. Substrate: the service's
  existing recorded-plumbing seam (the fake plane records the request).
