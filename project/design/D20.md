# Decision 20 — The MCP surface contract: structured results, error vocabulary, and discovery

**Decision.** This is a **suite contract**: the shape of every service's MCP
surface — what a verb returns, how it fails, and how a connecting agent discovers
what the service can do. **MCP is the suite's single verb surface.** There is no
second, machine-facing API beside it.

> **Verbs and facts move over MCP; bytes move over the content plane (D19);
> nothing else exists.** A domain verb is registered **once** with the chassis
> and answers every caller — its result carries `structuredContent` for machines
> and mirrored text for agents, in one response.

Callers divide by kind, not by surface: **agents** (a remote client through
nginx, a sandboxed run over loopback) discover tools with `tools/list`, read
descriptions and guides, and consume the text rendering; **machines** (a scripts
run, any deterministic actor) call the same tools through one thin generic client
and consume `structuredContent`, never parsing prose.

## The result contract

Every chassis-served service conforms:

- **Protocol.** The chassis MCP layer speaks revision `2025-06-18`, which is what
  makes the single surface possible: a tool may declare an **`outputSchema`** and
  return **`structuredContent`** (a plain JSON object) alongside its text blocks
  in the same result.
- **Output schemas.** Each registered domain tool declares an `outputSchema`
  beside its `inputSchema`, surfaced by `tools/list`. The schema *is* the machine
  contract: versioned with the service, testable, and stable in the way
  agent-facing descriptions are deliberately not required to be.
- **Structured results.** A domain verb's success result carries
  `structuredContent` conforming to its declared schema, **plus** a text block
  mirroring the same JSON. The chassis provides one helper that emits both from a
  single typed value; hand-built content arrays are for the exceptions below.
- **Structured errors — a closed vocabulary.** A tool error keeps `isError` and a
  human message and **additionally** carries a code from the suite's shared,
  closed set as a structured field, so a machine caller branches on a code and
  never on message text:

  ```
  {"code": "<validation|not_found|conflict|too_large|source_unavailable>",
   "message": "<human-readable>"}
  ```

- **Prose exceptions.** Documentation tools (`guide`, `describe`) and raw-content
  reads stay plain text — they are for readers — and declare no output schema.
- **Chassis tools included.** The built-in `health` and `reflection` declare
  schemas and return structured results like any other verb.

## The identity contract on the surface

MCP verbs are owner-scoped, so a loopback caller must say who it acts for. **The
request carries identity (D17); the handler never cares which door it came
through.** nginx injects the owner headers for requests from outside; an on-box
caller asserts the same headers itself, being inside the trust boundary already.
`X-Client-Id` names the **actor** (`scripts:<script_id>`, `prompts:<prompt_id>`),
giving every write provenance. The loopback-private guard therefore keys on the
"did this cross nginx?" marker (`X-Forwarded-Proto`) alone and lives in the
chassis as one shared helper — keying it on an owner header would conflate "came
from outside" with "carries identity", which caller-asserted identity breaks.

## The discovery tiers

Each service is its own MCP server, and an agent must be able to find it and
drive it **from the connection alone**, with no separately installed skill. It
learns from three MCP-native channels, and content lives in the channel whose
delivery guarantee matches how badly the agent needs it — stronger guarantee,
tighter budget:

| tier | channel | guarantee | holds |
|---|---|---|---|
| **0** | `initialize` `instructions` | always loaded, once | orientation + routing vocabulary + one pointer to the guide |
| **1** | tool descriptions (`tools/list`) | always loaded, per tool | when to use each tool, its args, what it returns |
| **2** | a `guide` tool (`tools/call`) | loaded only when called | the full reference: field catalogs and worked examples |

The move that makes it work: **reference bulk does not live in Tier 0 or 1**,
where every connection pays for it. It lives in Tier 2, pulled on demand.

- **Tier 0** is two or three sentences: what the service is over, named in the
  vocabulary a user actually types — including everyday synonyms, which are the
  routing hooks that let an agent match the service without an external alias
  skill — the normal working flow across its verbs in one clause, and one pointer
  to the guide. Orientation, never a field catalog.
- **Tier 1** is lean and keyword-forward: when to use the tool, how to shape its
  arguments, what it returns, plus the cross-cutting semantics needed to call it
  correctly at all (a dedup rule, an append-only constraint, a
  declarative-set replacement rule). No per-entity catalogs. Findability
  vocabulary belongs here too, because tool search indexes tool descriptions.
- **Tier 2** is a single read-only tool, conventionally named **`guide`**,
  returning the service's usage document as text: the relocated catalogs plus
  basic and advanced worked examples. It is **a tool, not an MCP resource** —
  a tool is the channel with the hard delivery guarantee, since most clients do
  not surface resources into an agent's context. It is a **non-domain** tool, so
  adding domain entities still adds no tools. It starts **flat and input-free**
  (one call returns the whole document), gaining scoping only if one service's
  guide outgrows roughly a screen. The document is **embedded in the binary**, so
  the guide an agent reads always matches the running service.

**The guide is referenced in exactly two places** — the Tier 0 `instructions` and
the `guide` tool's own description — deliberately *not* in every tool
description, which would re-inflate Tier 1 for no gain.

**Discovery describes; it does not change behavior.** Adopting the tiers rewrites
how a surface is *described* and adds one read-only tool; the entity model, verb
semantics, validation, and event surface are untouched, and adoption must be
provably behavior-neutral for every existing call. Each service owns its own
strings: this contract fixes the shape and the tier boundaries, not the words.

**Rejected.**

- **A second, machine-facing surface** (a loopback domain/REST API mirroring each
  service's MCP verbs). It buys a machine caller one JSON-RPC envelope — ten
  lines of client code — in exchange for a permanent second surface on every
  service, a second set of routes to guard, and a mirroring discipline to police
  forever. Adding one later would mean this contract failed, not that it was
  incomplete.
- **Per-service client libraries.** A hand-written wrapper per service is a
  second, drift-prone description of an API that is already self-describing. One
  generic `call(service, tool, args) → structuredContent` client suffices; the
  tool schemas are the documentation.
- **Runtime schema enforcement in the transport.** The chassis surfaces
  `outputSchema` and helps produce conforming results; it does not validate every
  response against its schema at runtime. Conformance is the service's own test
  suite's job.
- **Bytes over MCP.** `structuredContent` carries facts and references, never
  file bodies; large or binary content stays on the content plane (D19).
- **Free-text error strings as the machine signal.** Parsing prose to branch is
  exactly the fragility that blocked deterministic callers in the first place.
- **MCP resources as the home for reference text.** Semantically tidier, but most
  clients never surface them, so an agent told to "read the guide" may have no
  way to. A service may expose the same bytes as a resource additionally; the
  tool is the guarantee.
- **A suite-level aggregating index.** Each service describes itself; nothing
  here routes or proxies across services.

**Verification.** This is a **prose contract with no testable behavior of its
own**, so it carries **no ids**. Its behaviors are proven where they are
implemented, informationally: the `2025-06-18` protocol, `Tool.OutputSchema`, the
structured-result helper, the shared error vocabulary, schemas for `health` and
`reflection`, and the shared loopback guard in **appkit**; the
`X-Forwarded-Proto` stamp on every proxied route in the **nginx** fragments; and
each service's own output schemas, error codes, `instructions`, tool
descriptions, and `guide` tool in that **service**'s tree.
