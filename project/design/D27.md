# Decision 27 — The edit-tool merge contract: patch semantics, whole-value fields, and the stated merge rule

**Decision.** This is a **suite contract**: the merge semantics of every MCP tool
that edits an existing entity's fields — a `save` with an id, an `update`, or any
partial-edit verb a service grows later. It exists because the suite's edit tools
are called by agents, and an agent's natural move is to send only the field it
wants to change. A surface where "omitted" can mean "blank it" turns that natural
move into silent data loss; the suite therefore fixes one rule, and requires each
tool to say it.

## The merge rule

- **Patch at the top level: an omitted field is unchanged.** An edit call names
  the entity and carries only the fields it intends to change. Every top-level
  field absent from the call keeps its stored value exactly — in every store the
  service writes (row, version plane, cache). An edit tool never derives a new
  value for a field the caller did not send; in particular, an omitted name is
  not a rename.
- **Declared whole-value fields replace as a unit.** A field whose value is a
  set or a structured object (a config object, a tag list, an email set) is
  edited by **whole-value replacement**: omit the field to keep it untouched;
  send it to replace the entire value, with keys or members not present in the
  sent value removed. There is no per-key merge inside a whole-value field —
  merge-within-merge would reintroduce the omitted-vs-cleared ambiguity one
  level down, behind a `null`-means-clear convention no two callers guess the
  same way. Which fields are whole-value is the service's own declaration, made
  in the tool description.
- **Explicit empty is intentional: clear where clearable, error where not.**
  Sending a field with an empty value (`""`, `[]`) is a deliberate act, never a
  no-op. For a field whose empty state the entity can legitimately hold
  (an optional label, a clearable tag set), explicit empty **clears** it. For a
  field the entity cannot function without, explicit empty is a **validation
  error** (the shared `validation` code, `root project/design/D20.md`), rejected
  at the edit call — never stored to fail later at use time. Each field's rule
  follows from the entity model: *an edit must be able to reach exactly the
  states create can express, and no others.*
- **Required fields stay required.** A tool may require fields on every call
  (a name that addresses the entity, an expression that is the entity's whole
  substance). A required field can never be omitted, so patch semantics hold
  vacuously; requiring everything is a conforming shape for a tool whose entity
  is one value.

## The description discipline

Every edit tool **states its merge rule in its Tier 1 description**
(`root project/design/D20.md` — a merge rule is exactly the "cross-cutting
semantics needed to call it correctly at all" that Tier 1 exists to carry), in
one or two clauses: that omitted fields are unchanged, which fields are
whole-value replacements, and what explicit empty does where the answer is not
obvious. The schema cannot carry this — JSON Schema "optional" is ambiguous
between "unchanged" and "defaults to zero" — so the description is the contract's
delivery channel. A caller must never need the guide, the source, or an
experiment to learn whether omitting a field destroys data.

## Rejected

- **Replace (PUT) semantics with all fields optional.** The shape prompts
  shipped: omitted fields silently blanked, an omitted name derived into an
  accidental rename. It survived until the first partial call from an agent,
  which is the suite's normal caller. Observed live: a config-only `update`
  blanked a prompt's `user_prompt` and the failure surfaced two calls later,
  at run start, as a provider error.
- **Replace semantics with all fields required.** Honest, and conforming for a
  one-value entity (the cron shape) — but as the general rule it makes every
  small edit resend every large field, and the moment one field is optional the
  trap reopens. Adopted only where the entity is small enough that "required
  everything" is the natural shape.
- **Per-key merge inside structured fields, `null` to clear a key.** Expressible
  in JSON, but it moves the omitted-vs-cleared ambiguity inside the object and
  keys interact (mutually exclusive settings, cross-field constraints) — a
  service would validate a merge result no caller ever saw. Whole-value
  replacement keeps validation over exactly what was sent.
- **Fixing the semantics but not the descriptions.** The rule is only as good as
  its delivery: an undocumented patch surface is safe but unguessable, and an
  agent that assumes wrong wastes a round trip or resends everything
  defensively. The stated rule is half the contract.

**Verification.** This is a **prose contract with no testable behavior of its
own**, so it carries **no ids**. Its behaviors are proven where they are
implemented, informationally: each service's own edit-tool semantics and
descriptions in that **service**'s tree (prompts' patch-semantics Decision and
its tagged tests; crm's documented field-merge and set-replacement rules;
scripts' omit-to-keep update; cron's all-required `update`).
