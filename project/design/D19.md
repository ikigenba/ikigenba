# Decision 19 — The content plane: bytes by reference

**Decision.** This is a **suite contract**: the third plane. The **auth plane**
decides who a request is from (nginx introspects, injects identity headers,
services trust them). The **event plane** (D18) moves small facts. The **content
plane** moves *file bytes* — the rule set for getting a file from the service
that holds it to the service that needs it. (The **version plane**, D24, owns
history; its custodian is an ordinary holder under this contract.)

> **Agents pass references; services move bytes.** A file crosses the suite as a
> reference. Only the two services at the ends of a transfer ever touch the
> bytes, and they exchange them over loopback HTTP — never through a model's
> context.

Two roles fall out, and an agent orchestrating a transfer holds neither: it
carries the reference from the holder's tool result to the acceptor's tool call.

**The reference.** The only file-shaped thing that may appear in an MCP result,
an event payload, or a prompt:

```json
{
  "content_url":  "http://127.0.0.1:3200/content?path=%2Fbills%2Faws%2F2026-06.pdf",
  "content_hash": "<64-hex content hash>",
  "size":         184230,
  "rev":          "015f3a…"
}
```

- `content_url` is a **loopback** URL, resolvable only on the box, appearing
  URL-encoded and complete. A consumer never constructs or rewrites it.
- `content_hash` and `size` let a consumer verify what it fetched and let an
  acceptor detect a torn or moved-on source.
- `rev` is present when the holder versions its content, supporting the pin
  contract below.

**The holder contract.** A service that owns bytes exposes a loopback `GET`
content endpoint that:

- **Streams the bytes** with a correct `Content-Type` and `Content-Length`; range
  and conditional requests are permitted, never required.
- Is **loopback-private by handler guard** — the handler answers 404 whenever it
  sees the marker of a request that crossed nginx, the same guard `/feed` uses.
  An nginx `location = … { return 404; }` fragment is optional defence in depth,
  never the mechanism. Content endpoints are **never** reachable from off the box.
- Is **pinnable** where the holder versions content: an optional `rev` (or
  equivalent) parameter demands "exactly the bytes this reference named" — a
  mismatch returns **409**, an absent object **404**. A consumer that fetched
  unpinned and finds `content_hash` differs knows a newer reference is in flight.
- Is **addressed by the holder's own key** — a mirror path, a
  `(message_id, part)` pair, a `(run_id, sandbox path)` pair. The plane imposes no
  shared namespace; the `content_url` encapsulates whatever the holder needs.

**The acceptor contract.** Every agent-facing verb that ingests a file takes a
**reference, not a body**:

- The tool signature is `…(dest…, source_url)`. The service fetches the stream
  itself and applies its own domain rules (size caps, path validation, its normal
  write path), so the tool call and its result stay small facts.
- **Fetch targets are confined**, absolutely: only `127.0.0.1`/`::1` on ports
  assigned in the shared service registry. Anything else is a validation error.
  No service fetches an arbitrary URL on an agent's say-so.
- Service-to-service HTTP *beneath* the plane (a loopback `PUT /content` whose
  body is the stream) is unaffected — bodies between services are fine. The
  reference rule governs the **agent-facing surface and the event plane**.
- A content-bearing convenience variant (small inline text an agent authored) may
  exist alongside under a tight size cap; the `source_url` form is the primary
  verb.

**The sanctioned crossing: a sandboxed run.** A prompts (or scripts) run is where
a reference legitimately becomes bytes an agent can operate on, and the crossing
lands **on disk, not in context**: a runner-executed — not model-executed —
`fetch(content_url, dest_path)` sandbox tool streams the URL under the same
loopback confinement into the run's sandbox and returns only
`{path, size, content_hash}`. The run then uses its ordinary file tools. **Run
files are content too**: a run's sandbox files are themselves addressable by
content URL, so a run's product travels onward by reference exactly as its input
arrived.

**Rejected.**

- **Inline bytes in tool results (`content_base64`).** An entire file decoded
  into an agent's context: token bloat, a hard size ceiling, and unreliable
  round-tripping of binary through a language model. Workable for a small text
  file, wrong as the general mechanism.
- **A shared blob store.** The plane is a convention over per-service endpoints;
  a storage service would add a component, a lifecycle, and a namespace to own,
  for transfers that are already point-to-point on one box. The version plane's
  custodian (D24) is not this: it owns versioned artifact *histories* whose
  namespace is the owning services' own keys, and every service keeps its
  domain, its metadata, and its own serving copy — unversioned point-to-point
  transfer stays per-service, exactly as rejected here.
- **A universal namespace or catalog.** Each holder keeps its own addressing; the
  plane standardizes the *shape* of a reference, not a global file tree.
- **Public or cross-box transfer.** Content endpoints never leave loopback; the
  plane assumes the single-box model throughout.
- **Generic internet fetching via `source_url`.** Confinement is absolute;
  bridging external content into the suite is a connector's domain job, never a
  generic fetch.

**Verification.** This is a **prose contract with no testable behavior of its
own**, so it carries **no ids**. Its behaviors are proven where they are
implemented, informationally: the shared loopback guard in **appkit**; the
loopback port table in **registry**; holder endpoints, `source_url` acceptor
verbs, the `rev`→409 pin, and the sandbox `fetch` tool in the services that
realize them — **dropbox**, **gmail**, **prompts**, **scripts**, and **repos**
(whose `rev` is a commit sha) — each in its own tree.
