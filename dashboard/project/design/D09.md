# Decision 9 — The shell footer: service name + running version on every shell page

**Decision.** Every page that wears the shared shell (D10) ends with a
**footer** in the wiki idiom: a hairline top border, mono uppercase muted text,
reading the service name and the running version —

```html
<footer>dashboard {{.Version}}</footer>
```

`{{.Version}}` is the **chassis-stamped runtime version** — the exact value the
appkit chassis reports for this binary, the same string surfaced by `/health`
and the `version` verb. The suite stamps it into the chassis at build time
(`-ldflags "-X appkit.version=…"`); an unstamped local build reports the chassis
default `dev`, so a `go build` footer reads `dashboard dev`. There is **no
dashboard-local version source and no dashboard-local fallback string**: the
dashboard sources the footer version exactly the way every other web-surface
service does (the wiki wires `rt.Version()` into its page handler at the
composition root, `wiki/cmd/wiki/main.go`), never from `debug.ReadBuildInfo`.

The value reaches the page through the **composition root**, not a page-local
lookup. `cmd/dashboard` passes the chassis runtime version (`appkit`'s
`Router.Version()`) into the server as a new field on the server-construction
seam —

```go
// server.Options (internal/server): the version the shell footer renders.
type Options struct {
	// Version is the build-stamped runtime version string the shell footer
	// renders verbatim, sourced from the chassis (appkit Router.Version()) at
	// the composition root. Required.
	Version string
	// … existing fields …
}
```

— the server stores it (`app.version`) and each shell page's template data
carries it. Every page renders `{{.Version}}` **verbatim** from that injected
value; no page computes its own version.

The footer is part of the shared shell markup (one definition, rendered on every
shell page), so it appears on the logged-in home, `/install`, `/metrics`,
`/profile`, and the other shell-wearing pages (D10). The **logged-out login
page is not a shell page and renders no footer** — it keeps its centered
sign-in wall unchanged (D7).

This replaces this Decision's previous rule ("no site footer anywhere"): the
old footer died because it was contentless chrome (`{{.Host}}` / a bare
wordmark); the shell footer earns its place by stating the one operational
fact a person at the page wants — what version is running — exactly as every
wiki page does.

**Rejected.**
- **No footer at all (the prior rule)** — the suite shell settled on a
  version-bearing footer (the wiki ships it); the dashboard conforming is the
  point of the shell adoption.
- **Restoring the old `{{.Host}}` footer** — the account host is already the
  address bar; the version is the fact the page can uniquely state.
- **A footer on the login page** — the sign-in wall is deliberately untouched
  by the shell adoption; adding chrome there is scope creep.
- **A page-local `debug.ReadBuildInfo().Main.Version` source** — this is the
  bug this Decision now forecloses. `Main.Version` is empty for a binary built
  as its own main module without `go install pkg@version`, which is exactly how
  the suite builds (`GOWORK=off -buildvcs=false`), so it always collapses to a
  hardcoded `v0.0.0+dev` and the footer never shows the real deployed version.
  It also invents a second version source alongside the chassis stamp every
  other service already uses. The footer reads the chassis runtime version
  instead.

**Verification.**
- R-VN4Y-ERZ1 — With the server constructed for a **known injected version**
  (`Options.Version`, e.g. `v9.9.9+seal`), the logged-in `GET /`, `GET /install`,
  `GET /metrics`, and `GET /profile` (live session) each render exactly one
  `<footer>` whose text is `dashboard <that exact injected version>` — the
  rendered version equals the injected value verbatim, so an implementation that
  ignores the injected version (a page-local source) fails — while the
  logged-out `GET /` renders **no** `<footer>`.
- R-EFJZ-FRQ1 — The retired `site-footer` is gone everywhere: the logged-in
  `GET /`, `GET /profile`, and a freshly-created PAT response carry the shell
  `<footer>dashboard ` and **no** `site-footer` markup, the logged-out `GET /`
  carries neither footer, and `GET /static/app.css` defines no `.site-footer`
  selector.
