# Decision 30 — The introspection endpoints are the suite's edge minter: a fresh correlation id per gated request

**Decision.** The dashboard is the only place a `/srv/<svc>/` request passes
through before it reaches a service, so it is where a request's **correlation
id** is born. All three loopback `auth_request` introspection endpoints —
`handleAuthn` (bearer), `handleAuthnPAT`, `handleSessionAuthn` (cookie) — mint a
**fresh correlation id on every decision** and, on an **allow**, return it as the
response header `X-Correlation-Id` alongside the identity headers D19 emits. The
service's nginx fragment captures that header with `auth_request_set` and
`proxy_set_header`s it upstream, so the whole chain the request causes — the
service's own record, its outbound loopback calls, the events it publishes and
whoever consumes them — carries one id back to this decision.

**The id.** A bare 26-character Crockford-base32 ULID, minted by the suite's
shared minter (`eventplane/correlation` — a leaf package appkit and eventplane
both depend on; its exact signature is that workspace's decision, and the
dashboard consumes it as an external fact: *give me one fresh id string*). The
dashboard mints nothing of its own here — a second implementation of the format
is exactly the drift the shared package exists to prevent. `internal/ids` is
**not** reused: its handles are deliberately timestamp-free (see research), and a
correlation id must be time-sortable.

```go
// The dashboard's consumption seam, satisfied at the composition root by the
// shared minter. One method, so a test can pin the emitted id exactly.
type correlationMinter interface {
	NewCorrelationID() string
}
```

**Minted per decision, not per allow.** A deny mints too. A probe that fails
authentication a hundred times produces a hundred distinct ids — one per
attempt — so each failed attempt is its own chain in the forensic record rather
than an unattributable heap. The minted id is what the edge record carries
(D31); on a deny it is *not* sent as a response header, because nginx never
forwards a denied request upstream and there is nothing downstream to correlate
with. Emitting it only on the allow branch also keeps the rule simple to state:
**if a request reaches a service, the id in its header is the id in the edge
record.**

**Inbound ids are never trusted at the edge.** The introspection request is a
subrequest of a *public* request, so any `X-Correlation-Id` on it originated
with the client. The endpoints ignore inbound values entirely — they do not read
the header, so there is no branch in which a client-supplied value can be echoed
or reused. Belt and braces, the dashboard's own fragment also blanks the header
on the way in (D33). This is the one asymmetry with appkit's read-or-mint
middleware, which *does* trust inbound ids: that middleware runs behind the trust
boundary where every caller is a loopback peer, and this endpoint runs at it.

**Session-authn is treated exactly like bearer-authn.** It gates the `sites`
PRIVATE tier: a real gated route serving real content to a real person, and a
page load that fans out into service work like any other. Treating it as a
lesser tier would leave a hole in the chain precisely where a human is browsing.
So it mints, returns, and records identically — the only differences are the
ones its coarse model already has (no client id, no chain id, no rate limit, so
no `rate_limited` decision can arise there).

**Rejected.**
- **Letting each service mint its own id and skipping the edge.** Then the auth
  decision and the work it authorized would carry different ids and could never
  be joined; the deny case would have no id at all, which is the case a forensic
  investigation most wants.
- **Trusting an inbound `X-Correlation-Id` on a gated public request.** It would
  let any caller choose its own chain id, poison an existing chain by replaying
  someone else's, or flood one id across unrelated work. The header is only
  trustworthy inside the loopback boundary.
- **One id per token/chain/session instead of per request.** A chain id already
  exists (`X-Chain-Id`) and answers "which grant"; the correlation id answers
  "which request", and collapsing the two would make every request from one agent
  indistinguishable in the record.
- **Reusing `internal/ids.New()`.** Opaque and collision-free, but carries no
  timestamp, so a chain could not be time-ordered without consulting every
  record's clock — and the suite contract fixes the format as a Crockford ULID.
- **Returning the id on deny responses too.** Harmless but meaningless (nginx
  discards the subrequest response on a non-2xx and forwards nothing), and it
  would blur the clean invariant that a returned id always equals a forwarded id.

**Verification.**
- R-X7FZ-83J9 — a `handleAuthn` **allow** response carries an `X-Correlation-Id`
  header that is exactly 26 characters and composed only of Crockford base32
  symbols (`0123456789ABCDEFGHJKMNPQRSTVWXYZ` — in particular containing no
  `I`, `L`, `O`, `U` and no lowercase), proving the Crockford format rather than
  merely a non-empty value.
- R-X8NV-LV9Y — two successive `handleAuthn` allows on the same token return
  **different** `X-Correlation-Id` values (a per-request mint, falsifying both a
  constant and a per-token/per-chain id).
- R-X9VR-ZN0N — a `handleAuthn` allow whose *request* carries an attacker-chosen
  `X-Correlation-Id` returns a value **different** from the supplied one, and the
  supplied value appears nowhere in the response headers.
- R-XB3O-DERC — a `handleSessionAuthn` **allow** response carries an
  `X-Correlation-Id` with the same format and per-request-freshness properties,
  and likewise never echoes a supplied inbound value.
- R-XCBK-R6I1 — a `handleAuthn` **deny** (401, invalid token) and a
  **rate-limited** (429) response each carry **no** `X-Correlation-Id` header at
  all, and so does a `handleSessionAuthn` 401.
