# Decision 1 — Page topology and the route map

**Decision.** The dashboard's human web surface is **five pages** served by four
routes. `GET /` stays a single handler that branches on the session — **login**
when logged out, **home** when logged in. Three session-gated routes sit beside
it: `GET /install`, `GET /metrics`, and `GET /profile`. No other human page
exists.

- **`GET /` (handler `handleIndex`)** keeps its `{{if .Owner}}` branch:
  - **logged out → the login page**: the sign-in wall (title, tagline, the two
    provider CTAs, and the diminished name-origin colophon). Its composition is
    **D7** and is unchanged by the shell adoption (D10) apart from the font
    tokens (D8).
  - **logged in → the home page**: the MCP service directory and nothing else.
    Its composition is **D5**; install instructions live on `/install` (D40),
    and token/grant administration on `/profile` (D3, D4).
- **`GET /install` (new handler `handleInstall`)** serves the install page
  (composition D40). It is gated exactly like the profile page: a
  missing/invalid session redirects `303 → /` (the D2 pattern); a valid session
  renders the page. Registered in `(*app).register` in `routes.go`; its
  template (`html/install.html`) joins the `template.ParseFS` set in
  `server.go` so a broken template fails startup, not a request.
- **`GET /profile` (handler `handleProfile`)** serves the profile page (D2
  gates it; D3/D4 fill it).
- **`GET /metrics` (handler `handleMetrics`)** serves the metrics page (D14).

This decision fixes the **topology and routing only**; page composition is
D5/D7/D40 and the metrics surface is D14; the shared shell is D10.

**Rejected.**
- **Keeping install instructions on the home page** — the home and the one-time
  connect task have different return cadences; the connect task reads better as
  its own page, reached from the shell navigation, and the home stays a clean
  directory.
- **A third route for the home** (e.g. `GET /home`) — the logged-in home is the
  *same URL* a returning owner already has bookmarked (`/`).
- **Serving install content only as the `curl` scripts** (`/install/claude`,
  `/install/codex`) with no human page — the human needs the copy-paste page;
  the script endpoints remain, unchanged, beneath the page route.

**Verification.**
- R-DB01-PG3A — `GET /` with no or an invalid session renders the **login** page
  (the sign-in controls are present) and contains none of the logged-in
  controls: no PAT-create form, no grants block, no profile link.
- R-DB03-PRF9 — `GET /profile` is a registered route distinct from `GET /` (it
  is reachable and does not fall through to the index handler).
- R-VH1G-HX9K — `GET /install` with a valid session returns `200` and renders
  the install page (the D40 composition), as a registered route distinct from
  the `/install/claude` and `/install/codex` script endpoints, which keep
  serving their scripts unchanged.
- R-VI9C-VP09 — `GET /install` with no or an invalid session redirects
  `303 → /` and reveals no install-page content.
