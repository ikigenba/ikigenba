# Decision 31 — Every gated auth decision emits an `edge` telemetry record

**Decision.** Each of the three introspection endpoints emits **exactly one**
telemetry record of kind `edge` per decision — allow, deny, or rate-limited —
through appkit's telemetry recorder. This is what makes the suite's forensic
record complete at its outermost hop: without it, a request that was *refused*
leaves no trace anywhere (the service never sees it), and an allowed request's
chain would begin one hop in, with no record of who was admitted, to what, or on
what credential.

**The seam: the chassis recorder, obtained from the Router.** The dashboard
**constructs no recorder of its own.** appkit's chassis owns the recorder's whole
lifecycle — env configuration, ring buffer, batching, flush cadence, and the
best-effort POST to the telemetry service — and exposes it as a **Router-level
accessor**, the sibling of `rt.HTTPClient(...)` for instrumented outbound calls.
The dashboard's composition root takes the recorder off the `*appkit.Router` it
already captures (the established `var rt *appkit.Router` idiom in
`cmd/dashboard/main.go` — the same capture the metrics collector uses for
`rt.Logger()`) and threads it into `server.Options`.

Most instrumentation in the suite arrives free through the chassis: MCP dispatch,
plain-HTTP request recording, and outbound calls made through
`rt.HTTPClient(...)` need no app code at all. Edge records are the
**direct-emitter** case — the chassis cannot know a gated request's decision, its
addressed service, or its original URI — so the dashboard emits them itself,
*through* the chassis's recorder rather than around it. One recorder per process
means one ring buffer, one batch stream, and one dropped-record count.

The dashboard depends on it through a one-method interface it owns, satisfied at
the composition root by the recorder the Router hands over (appkit owns the
accessor's exact name and the record type; this interface is a thin adapter so a
signature change lands in one line):

```go
// internal/server: the dashboard's consumption seam for the suite recorder.
// Record never blocks and never returns an error — recording is best-effort by
// contract, and an auth decision must not depend on it.
type telemetryRecorder interface {
	Record(ctx context.Context, rec telemetry.Record)
}
```

A nil recorder is a valid configuration (local dev, tests that do not care):
the endpoints call through a nil-safe helper, so "telemetry not wired" is
indistinguishable from "telemetry down" — both are silent no-ops.

**The record**, filled by construction from values the handler already holds —
never by dumping headers or bodies:

| field | value |
|---|---|
| `kind` | `edge` |
| `correlation_id` | the id minted for this decision (D30) — on an allow, the same id the response header returns and the request then carries |
| `service` | `dashboard` (the recording service) |
| `op` | `<METHOD> <original-uri>` — the *gated* request's method and URI, not the subrequest's |
| `actor` | `{owner_email, client_id}` as far as established at the point of decision; fields omitted when unknown |
| `outcome` | `{status, error}` — the status the endpoint returned and, on a deny, the same short reason class the audit row records (`invalid_token`, `resource_mismatch`, `workspace_mismatch`, `unknown_service`, …) |
| `detail` | `{decision: allow\|deny\|rate_limited, service: <addressed service>}` |

**Method and URI come from the fragment, not the subrequest.** nginx's
`auth_request` subrequest does not reliably carry the original method, and the
original URI is already passed explicitly as `X-Original-URI`. The dashboard's
own fragment therefore also forwards `X-Original-Method: $request_method` on both
internal locations (D33), and the handler composes `op` from those two headers.
When `X-Original-Method` is absent (an older fragment, a direct loopback caller),
`op` falls back to the subrequest's own method rather than fabricating one.

**Identity is recorded as far as it is established, never further.** A deny at
step (b)/(c)/(d) knows no owner, so `actor` is empty — an empty actor is the
honest record of an unauthenticated probe, and inventing one would be worse than
omitting it. A deny at (e)/(f) has a validated chain, so owner email and client
id are recorded. This is deliberately the same fill order the existing audit
events use.

**Never a raw dump.** The record is assembled field by field from named values.
The `Authorization` header, the `Cookie` header, the bearer token, and the PAT
never appear in any field — not in `op`, not in `outcome.error`, not in
`detail`. `X-Token-Id` (the server-side id, not the credential) is deliberately
*not* in the edge record either: the audit row already carries it durably, and
the forensic record has no need of a value one step from the secret.

**Recording never changes the decision.** The `Record` call sits after the
response status and headers are determined, is fire-and-forget, and cannot
return an error into the handler. A telemetry service that is down, slow, or
absent yields exactly the same status, headers, and body as one that is healthy.

**Rejected.**
- **Recording only allows.** Denials are the forensically interesting half: a
  credential-stuffing run against `/srv/ledger/` is invisible if only successes
  are recorded. The suite bought this capability precisely to see them.
- **One record per *request* instead of per decision.** There is exactly one
  decision per gated request, so these coincide — but stating it as
  per-decision makes the rate-limited case (which is neither an allow nor an
  authentication failure) obviously in scope rather than an afterthought.
- **Letting appkit's generic HTTP-request instrumentation cover it.** That
  records the *introspection subrequest* — `POST /internal/authn` on the
  dashboard, with the dashboard's own minted id — which describes the plumbing,
  not the gated request. It knows neither the decision, nor the addressed
  service, nor the original URI.
- **Recording the token id or a token prefix for correlation.** A prefix is a
  partial secret, and the id adds nothing the durable audit row lacks. The chain
  id in the audit row plus the correlation id in the record already join the two
  records.
- **A dashboard-constructed recorder (or its own ingest client).** It would give
  the process two ring buffers, two batch streams, and two dropped-record
  counters, and would duplicate the env configuration the chassis already reads —
  so a box could end up with telemetry half-enabled, and the dashboard's edge
  records could survive a chassis-level disable. The Router accessor is the one
  handle, exactly as `rt.HTTPClient(...)` is for outbound calls.
- **Blocking on the record, or dropping the allow when recording fails.** The
  contract is best-effort everywhere: telemetry being down must never take the
  box's authentication path with it.

**Verification.**

The claims below hinge on what is actually *sent* to the telemetry service, not
on a field being set on a struct. They are therefore driven against a **live
in-process HTTP sink** — an `httptest.Server` standing in for
`POST /ingest`, wired as the recorder's real ingest target and flushed before
assertion — and the assertions read the **decoded JSON the sink received**. A
stub recorder that accepts whatever it is handed would pass every one of these
without proving a record ever left the process, so it is not the substrate.
The endpoints themselves are driven as real HTTP through `(*app).routes()` with
`httptest`, so nothing about the handler is stubbed either.

- R-XDJH-4Y8Q — a `handleAuthn` **allow** results in exactly one record arriving
  at the live sink with `kind: "edge"`, `detail.decision: "allow"`, and a
  `correlation_id` **equal to the `X-Correlation-Id` header the same response
  returned** (the join between edge and chain; a different or empty id fails).
- R-XERD-IPZF — a `handleAuthn` **deny** (invalid token, 401) delivers an edge
  record with `detail.decision: "deny"` and an `outcome.status` of 401, and two
  successive denies deliver **two records with different `correlation_id`
  values** (per-attempt chaining, falsifying a shared or empty id).
- R-XFZ9-WHQ4 — a request refused by the rate limiter (429) delivers an edge
  record with `detail.decision: "rate_limited"` — distinct from `deny` — and
  `outcome.status` 429.
- R-XIF2-O17I — the delivered record's `op` equals `"<X-Original-Method> <X-Original-URI>"`
  for the gated request (e.g. `POST /srv/crm/mcp`, driven with those headers set
  to a method that differs from the subrequest's own, so a subrequest-method
  implementation fails), and `detail.service` is the addressed service name
  (`crm`).
- R-XJMZ-1SY7 — a `handleSessionAuthn` allow **and** a `handleSessionAuthn` 401
  each deliver their own edge record (`decision` `allow` / `deny`), so the
  private-static tier is not a hole in the record.
- R-XKUV-FKOW — with the ingest sink **unreachable** (closed listener) an allow
  still returns `200` with its full identity and correlation headers and a deny
  still returns `401`, and neither handler's latency depends on the sink: the
  auth decision is byte-identical to the healthy-sink run.
- R-XM2R-TCFL — across an allow and a deny, the **raw bytes** the sink received
  contain neither the bearer token/PAT string presented on the request nor the
  session cookie value nor the literal `Authorization` header value — proving
  allowlist-by-construction rather than a filtered dump.
