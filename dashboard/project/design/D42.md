# Decision 42 — Grok is a third install-script agent

**Decision.** The `/install/<agent>` script surface gains a third literal
`agent` value, `grokAgent`, registered at `GET /install/grok` on the existing
`handleInstall` seam. It is a peer of `claudeAgent` and `codexAgent`, not a new
handler family. The human page presents this route (D40); this Decision owns
the script the route serves.

- **`label`** is `Grok` — the word the script's closing restart line uses, and
  the same word D40 uses as the subsection `<h3>`.
- **`removeLine(name)`** emits
  `grok mcp remove --scope user <name> >/dev/null 2>&1 || true`.
- **`addLine(name, resource)`** emits
  `grok mcp add --scope user --transport http <name> <resource> --header 'Authorization: Bearer ${IKIGENBA_TOKEN}'`
  with the `${IKIGENBA_TOKEN}` reference single-quoted so the served bash does
  not expand it.

The body is the existing `installScript` skeleton: bash, `set -euo pipefail`,
the missing-token guard (`${IKIGENBA_TOKEN:-}` plus the three-step
mint / export / re-run instructions pointing at this request's scheme and
host), then for every `MCP=true` inventory service a remove-then-add pair
wrapped in the 🟢/🔴 `if`, and a final `${ok} of N successfully installed.`
plus `Restart Grok`. Names and URLs are `mcpLocalName` / `mcpResourceURL`
(D5's helpers) — `ikigenba_<svc>` against `<scheme>://<host><mount>mcp`.

This rests on the Grok MCP CLI facts in `project/research/research.md`: the
header is stored verbatim and expanded at load time; `grok mcp add` is an
upsert; there is no `--bearer-token-env-var`; user scope is the default and
is what a curl-piped script must pin. Remove-then-add stays, matching Claude
and Codex, even though Grok's add would succeed on a duplicate.

The route is public (no session) and `text/plain; charset=utf-8`, same as
`/install/claude` and `/install/codex`. A failed `inventory.Read` is
`handleInstall`'s existing contract: HTTP 500, no script body. No new named
error. The installer does not write `[compat.claude]`, does not start Grok
OAuth, and does not touch `~/.grok/mcp_credentials.json`.

**Rejected.**
- **Relying on Grok's Claude-compat MCP import instead of a native install** —
  a Grok-only customer has no `~/.claude.json` to inherit.
- **A headerless URL so Grok's MCP OAuth runs** — Claude and Codex authenticate
  with the PAT; Grok must too. A headerless add would write
  `~/.grok/mcp_credentials.json` instead of referencing `IKIGENBA_TOKEN`.
- **The Codex command shape** (`--url`, `--bearer-token-env-var`) — Grok does
  not accept those flags.
- **Writing `[compat.claude] mcps = false` from the installer** — that is the
  customer's Grok setting, not a registration step.
- **A customer path other than `GET /install/grok`** — local operator scripts
  are outside this tree.

**Verification.**
- R-Y6W7-R29G — `GET /install/grok` with no session cookie, driven through
  the registered route table (`New` / `httptest`), returns `200` with
  `Content-Type` `text/plain` and a body that starts with `#!/usr/bin/env bash`.
- R-Y844-4U05 — That body, against a fixture of dashboard (no `MCP`) plus
  crm and ledger (`MCP=true`) requested as `https://int.ikigenba.com`,
  contains `echo "Installing 2 MCP"`,
  `grok mcp remove --scope user ikigenba_crm >/dev/null 2>&1 || true`,
  `grok mcp add --scope user --transport http ikigenba_crm https://int.ikigenba.com/srv/crm/mcp --header 'Authorization: Bearer ${IKIGENBA_TOKEN}'`,
  the matching ledger remove and add,
  `if [ -z "${IKIGENBA_TOKEN:-}" ]; then`,
  `echo "${ok} of 2 successfully installed."`,
  and `Restart Grok`; it does not contain `claude mcp`, `codex mcp`, or
  `--bearer-token-env-var`.
