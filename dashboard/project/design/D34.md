# Decision 34 — Suite-contract conformance: the opsctl install layout and the authored env contract

**Decision.** The dashboard is a deployable app of the suite, so it **conforms by
default** to the suite-wide contracts the umbrella project owns. Two of those
contracts carry `[proof: per-service]` Verification ids, which means each adopting
app proves them **in its own tree**:

- **The `/opt/<svc>/` install layout** — `project/design/D08.md` at the repo root.
- **The portable authored `manifest.env` and the composed data paths** —
  `project/design/D11.md` at the repo root.

This Decision is the **citation**, and citation is adoption: the dashboard owns
none of those contracts' content, restates none of it, and takes each by value
from the umbrella Decision named above. What is local to the dashboard — and all
this Decision adds — is *where the proof lives* and *what substrate can falsify it
here*:

- The proofs live in **`cmd/dashboard/main_test.go`**, the composition root's test
  file, matching every other adopting app. No new package is introduced for them.
- The committed authored manifest is **`dashboard/etc/manifest.env`**; the
  compiled default it must byte-agree with is the one the dashboard's `Spec`
  declares. **The dashboard is the apex/`DEFAULT` app, and its manifest is the
  suite's shortest**: `APP=dashboard`, `MOUNT=/`, `DEFAULT=true`, `PORT=3000` —
  and nothing else. It declares **no `MCP=true`** (the dashboard exposes no MCP
  server; it is the identity plane the MCP apps are gated by), no `FEED`, no
  `CONSUMES`, and no outbox retention keys. `MOUNT=/` rather than `/srv/<svc>/`
  and `DEFAULT=true` rather than `false` are the apex's two shape differences from
  a path-routed service; neither is a deviation from either contract, both of
  which are written to cover the apex case.
- The boot proof runs the **built binary against a temporary root**, never the
  live box: a `t.TempDir()` tree with `state/`, `cache/`, `libexec/`, and
  `bin/run` symlinked to the binary, plus a manifest root the process reads its
  service inventory from. It is fully **offline** — the dashboard's IdP
  credentials are supplied as syntactically-valid throwaway values so
  configuration succeeds, and nothing contacts Google or GitHub. The proof is that
  the process booted from the layout, bound its port, served `/health` naming
  itself, created its DB under `state/`, and composed its generation sidecar under
  `cache/`. That the *credentials* actually authenticate is a different claim,
  owned by the sign-in Decisions against a live substrate; the boot smoke does not
  duplicate it and must not require network access.
- The dashboard's landing, login, profile, and metrics pages and their static
  assets are **embedded** (`ui/`, `template.ParseFS`), so it declares no `WWW` and
  the layout proof involves **no `share/` tier**.

Conformance is the default and this Decision records no deviation: the dashboard
departs from neither contract.

**Rejected.**
- **Restate the two contracts' requirements locally so the design reads
  self-contained.** A local restatement is drift by construction — it goes stale
  the moment the umbrella Decision is rewritten, and the suite's rule is cite,
  never restate. Rejected for citation by path.
- **Cite only the Decision paths and omit the ids.** Both contracts are marked
  `[proof: per-service]`: an app that adopts them must carry its own tagged tests.
  Citing the paths alone would leave the dashboard's proofs — which already exist
  in `cmd/dashboard/main_test.go` — attached to no Decision, invisible to the
  coverage check and deletable by anyone who could not tell what they were for.
  Rejected.
- **Claim an apex exemption from `[proof: per-service]` on the grounds that the
  dashboard is not a `/srv/` service.** The apex is installed by the same
  `opsctl` layout, ships the same authored manifest, and composes the same data
  paths; nothing about `MOUNT=/` or `DEFAULT=true` makes either contract
  inapplicable. An exemption would leave the one app that owns identity as the one
  app whose install layout nothing checks. Rejected.
- **Fold the citation into D1 (the page-topology Decision) or the design spine.**
  D1 owns the route map; the spine is cross-cutting facts only. A small, separate
  conformance Decision keeps the citation greppable and keeps both readable.
  Rejected.
- **Assert a live-Google/live-GitHub sign-in inside the boot smoke.** Not reachable
  in the offline unit suite; it would make the exit condition non-deterministic and
  duplicates claims that belong to the provider Decisions. Rejected.

**Verification.**

Each id below is **adopted**, not minted here: it belongs to the umbrella Decision
cited beside it, which states the behavior. These lines say only what substrate
proves it inside `dashboard/`.

- `R-4LKF-FB23` — adopted from `project/design/D08.md` at the repo root.
  Substrate: a Go test in `cmd/dashboard/main_test.go` that assembles a fresh
  `/opt/dashboard/`-shaped tree under `t.TempDir()` (`state/`, `cache/`,
  `libexec/`, `bin/run` → the built binary, an `etc/current/manifest.env` for the
  dashboard and for at least one path-routed service so the inventory is
  non-trivial), asserts `bin/run` resolves to the built binary, runs
  `bin/run serve` on a free loopback port, and asserts the served `/health` is
  `200` with `service: "dashboard"` and a `details` object, that the DB was
  created under `state/`, and that the generation sidecar path composes under
  `cache/`. Offline: no network, no real credentials.
- `R-8DF1-W89F` — adopted from `project/design/D11.md` at the repo root.
  Substrate: a Go test in `cmd/dashboard/main_test.go` scanning the committed
  `dashboard/etc/manifest.env` bytes and failing on an absolute `/opt/` path or a
  `DASHBOARD_DB_PATH=` / `DASHBOARD_GENERATION_PATH=` line.
- `R-8IAN-FB87` — adopted from `project/design/D11.md` at the repo root.
  Substrate: a Go test in `cmd/dashboard/main_test.go` comparing
