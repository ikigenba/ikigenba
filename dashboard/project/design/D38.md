# Decision 38 — The git door accepts a PAT as an HTTP Basic password

## Decision

Introspection (`handleAuthn`, `internal/server/authn.go`) gains **one** new
credential delivery form, on **one** resource: a request whose gated original
URI lies under the **git door** may present its personal access token as the
**HTTP Basic password** instead of a bearer. The suite's version plane (root
`project/design/D24.md`) puts repos' git smart-HTTP at
`/srv/repos/git/<kind>/<name>.git`, gated by the same `auth_request` that gates
every other surface, and git clients speak Basic — they do not send
`Authorization: Bearer` and do not understand a Bearer challenge. This decision
is the dashboard's whole slice of that plane: the *delivery form* changes, the
credential does not.

**The git-door test is a prefix on the forwarded original URI.** The handler
already receives the gated request's URI as `X-Original-URI` and strips the
query to resolve the bound resource (step (b)). The same query-stripped path
decides the git door:

```go
// gitDoorPrefix is repos' git smart-HTTP mount (root project/design/D24.md).
// The trailing slash is load-bearing: it is the whole boundary between the
// git door and every sibling path under /srv/repos/.
const gitDoorPrefix = "/srv/repos/git/"

// isGitDoorURI reports whether a forwarded X-Original-URI addresses the git
// door. The query string is stripped first, exactly as resourceForOriginalURI
// does.
func isGitDoorURI(originalURI string) bool
```

`/srv/repos/mcp`, `/srv/repos/`, and `/srv/repos/gitolite/x` are **not** the
git door. Bound-resource resolution (step (b)) is unchanged and still succeeds
for a git-door URI, because repos' configured resource
(`…/srv/repos/mcp`) is mounted under the same `/srv/repos/` prefix
`resourceForOriginalURI` keys on.

**The fallback sits exactly at step (c)'s failure branch.** Today a missing or
malformed `Authorization: Bearer` is an immediate 401. That branch becomes:
when — and only when — the request is on the git door, parse
`Authorization: Basic`, base64-decode the credentials, split at the first
colon, **discard the username entirely**, and treat the password as a candidate
PAT. Everything downstream is the existing path:

- The password must carry `pat.Prefix` (`ms_pat_`). If it does not, the request
  is denied; no store lookup happens.
- A prefixed password goes through **the same `handleAuthnPAT`** — the same
  `a.pats.ValidatePAT` (hash lookup, not-revoked, not-expired), the same
  skipped resource binding, the same workspace check, the same rate-limit key
  (`p.ID`), and the same allow branch emitting the four `X-Owner-*` identity
  headers plus `X-Client-Id: pat:<public_id>`, `X-Token-Id`, and
  `X-Correlation-Id`, with no `X-Chain-Id`. The identity contract of D19 and
  the edge-record contract of D31 are inherited whole, not restated.

A bearer presented on the git door keeps working exactly as it does today (both
the PAT and OAuth forks); Basic is consulted only after bearer extraction has
already failed.

**Basic is a git-door affordance, not a credential form of the platform.** On
every other gated surface — MCP bearers, `handleSessionAuthn` cookies — the
`Authorization` header is read exactly as today, so a Basic credential
presented to `/srv/crm/mcp` fails with today's `missing_bearer` 401 and today's
Bearer challenge even when its password is a live PAT. And **OAuth access
tokens are never accepted via Basic**: only the `ms_pat_` prefix opens the
fallback, so an `ms_oat_` password is refused on the git door as surely as a
random string. A PAT is the owner's own long-lived credential, minted and
revoked on the profile page (D3); an access token belongs to a delegated client
inside a chain, and handing one to a git remote would put a chain-bound
credential in a `.git/credentials` file.

**The challenge is Basic on the git door.** A 401 to a git client must be a
Basic challenge or the client will neither prompt for credentials nor retry.
So every 401 the introspection endpoint returns for a git-door request carries

```
WWW-Authenticate: Basic realm="ikigenba"
```

and **no** Bearer challenge and no `resource_metadata` — the RFC 9728 PRM URL
is meaningless to git. Non-git-door 401s are untouched: they keep the exact
Bearer challenge they emit today. The 403 loopback guard, the 429 rate-limit
response, and the 500 identity-lookup failure are unchanged on both paths.

**Audit and edge records are the existing ones with the Basic path named.** No
new record kind, no new emitter. `handleAuthnPAT`'s audit `Details` and the
edge record's reason carry the credential form so the two paths are separable
in the forensic record:

| condition (git door) | status | reason / detail |
|---|---|---|
| Basic + valid PAT | 200 | allow, audit `Details` gains `"cred": "basic"` |
| neither Bearer nor a parseable Basic header | 401 | `missing_credential` |
| Basic password without `ms_pat_` (including an `ms_oat_` token) | 401 | `basic_not_pat` |
| Basic password with `ms_pat_` failing `ValidatePAT` (unknown, revoked, expired) | 401 | `invalid_pat_basic` |

The bearer path's existing reasons (`missing_bearer`, `invalid_pat`,
`invalid_token`, …) keep their exact spellings, so no existing record changes.
D31's never-a-raw-dump rule governs here unchanged: the Basic credential — the
base64 blob and the decoded password alike — appears in no audit or edge field.

**No model change.** No new token type, no scopes, no columns, no migration,
and no change to minting or revocation. `internal/pat` is untouched. A PAT
revoked on the profile page stops working at the git door in the same request
that stops it working at an MCP endpoint, because it is the same lookup.

## Rejected

- **Accept Basic on every gated surface.** It would give every credential two
  delivery forms and double the auth surface for the benefit of one client
  family. Basic also carries the password on every request with no challenge
  semantics worth having outside git, and a broad acceptance would make a
  leaked PAT usable from any `curl -u` against any service — a real widening
  where the git door is a narrow, named need.
- **A separate git-token type.** A second credential model (mint, list,
  revoke, its own table, its own profile UI) buys isolation the PAT already
  has: a PAT is already the owner's own credential, already revocable in one
  click, already the thing the owner reaches for. The version plane's promise
  is that versioning is ambient — asking the owner to mint a *second* token
  before their first `git clone` contradicts it.
- **Accept OAuth access tokens (`ms_oat_`) via Basic too.** An access token is
  bound to one resource inside a chain and is short-lived; git stores whatever
  it is given in a credential helper and replays it indefinitely. Admitting one
  would either break on the resource binding the PAT path deliberately skips,
  or require relaxing that binding for git — a strictly worse trade than
  refusing the form.
- **Keep the Bearer challenge on git-door 401s.** git would not prompt, and the
  owner would see an opaque failure instead of a credential prompt. The
  `resource_metadata` URL an MCP client needs is noise to a git client.
- **Detect git by `User-Agent: git/…` or by the `service=git-upload-pack`
  query.** Both are client-controlled and would let any caller opt into the
  Basic fallback on any URI. The gate must be the resource, which nginx
  forwards and the client cannot forge past the front door.
- **A config knob for the git-door prefix.** The mount is fixed by the suite
  contract (root `project/design/D24.md`), so a knob would add an env var whose
  only correct value is the constant, plus a way to get it wrong.

## Verification

These are `server`-package HTTP tests driven through `(*app).routes()` with
`httptest` against a real migrated temp SQLite database — the same harness the
rest of the introspection tests use — so the PAT store, the identity lookup,
and the response headers are all real. The two record-delivery claims are
driven against the live in-process ingest sink D31 establishes, since a stub
recorder cannot falsify what left the process.

- R-39O6-OFFD — an introspection request with `X-Original-URI:
  /srv/repos/git/code/foo.git/info/refs?service=git-upload-pack`, no `Bearer`,
  and `Authorization: Basic <base64("anything:<valid ms_pat_ plaintext>")>`
  returns **200** carrying all four identity headers (`X-Owner-Id`,
  `X-Owner-Email`, `X-Owner-Name`, `X-Owner-Picture`) with the same values the
  identical PAT presented as a bearer produces, plus `X-Client-Id:
  pat:<public_id>` and `X-Token-Id`, and **no** `X-Chain-Id`.
- R-3AW3-2762 — the username is discarded: the same valid PAT password with the
  usernames `""`, `"x"`, and `"git"` yields three **200**s with byte-identical
  identity headers, so an implementation that matches, requires, or records the
  username fails.
- R-3C3Z-FYWR — the same Basic header carrying the same **valid** PAT, sent
  with `X-Original-URI: /srv/crm/mcp`, returns **401** with reason
  `missing_bearer` and a `WWW-Authenticate` value beginning `Bearer` that
  carries a `resource_metadata` parameter — today's behavior exactly, proving
  the fallback is not reachable off the git door.
- R-3DBV-TQNG — the prefix boundary holds: the same valid-PAT Basic header on
  `X-Original-URI: /srv/repos/mcp` and on `/srv/repos/gitolite/x` each returns
  **401**, while `/srv/repos/git/code/foo.git/info/refs` returns **200** — so a
  `strings.Contains("git")` or a `/srv/repos/` match fails.
- R-3EJS-7IE5 — a Basic password that is a **genuinely valid `ms_oat_` OAuth
  access token** (one that returns 200 when presented as a bearer on its own
  bound resource) is refused on the git door with **401** and reason
  `basic_not_pat`, and no `X-Owner-*` header is emitted.
- R-3FRO-LA4U — a **revoked** PAT and an **expired** PAT, each presented as the
  Basic password on the git door, each return **401** whose `WWW-Authenticate`
  is exactly `Basic realm="ikigenba"` — no `Bearer`, no `resource_metadata`
  substring — with reason `invalid_pat_basic`.
- R-3I7H-CTM8 — a git-door request with **no** `Authorization` header at all,
  and one with a malformed Basic header (non-base64 payload; and base64 with no
  colon), each return **401** with `WWW-Authenticate: Basic realm="ikigenba"`
  and reason `missing_credential`, and the handler does not panic.
- R-3JFD-QLCX — a **bearer** on the git door is unaffected: the same PAT sent as
  `Authorization: Bearer <plaintext>` with a git-door `X-Original-URI` returns
  **200** with the same identity headers, and an invalid bearer there returns
  **401** — proving Basic is consulted only after bearer extraction fails.
- R-3KNA-4D3M — the Basic-path allow delivers exactly one `edge` record to the
  live sink with `detail.decision: "allow"` and a `correlation_id` equal to the
  response's `X-Correlation-Id`, and its audit row's `Details` carries
  `"cred": "basic"`, while the equivalent bearer-PAT allow's audit row does
  **not** — the two paths are separable in the record.
- R-3LV6-I4UB — across a Basic allow and a Basic deny, the **raw bytes** the
  ingest sink received contain neither the base64 credential blob, nor the
  decoded PAT plaintext, nor the literal `Authorization` header value.
