# Decision 39 — The apex fragment sets the http-level `variables_hash_max_size` for the whole box

**Decision.** `dashboard/etc/nginx.conf` — the apex fragment `opsctl init-box`
installs as `/etc/nginx/conf.d/dashboard.conf` — begins, above its two `server`
blocks, with:

```nginx
variables_hash_max_size 2048;
```

`/etc/nginx/conf.d/*.conf` is included at `http` level by the box's stock
`nginx.conf`, so a top-of-file directive in this fragment configures the whole
front door. That placement is the point: the pressure comes from the *suite*,
not from any one file. Every service's `/srv/<svc>/` fragment declares its own
`auth_request_set` capture variables (owner, email, name, picture, client,
correlation, status, retry, session variants), and across the box's fifteen
fragments that is roughly 150 distinct nginx variables — more than nginx's
default variables hash (`variables_hash_max_size 1024`, bucket size 64) can
place. Until the table is enlarged, every `nginx -t` and every reload warns
`could not build optimal variables_hash`, and a warning printed on every reload
trains operators to ignore the channel a real problem would arrive on.

The dashboard carries the line because the dashboard owns nginx on the box: this
fragment already holds the box-wide, suite-serving pieces (the apex TLS server,
the `/_authn` and `/_session-authn` introspection locations every service
fragment calls, the `conf.d/locations/` include), and it redeploys with every
dashboard release, so the directive needs no opsctl change and no box re-init to
land or to change later. `2048` is the next power of two above the default and
is verified sufficient against the full current fragment set; if the suite ever
outgrows it, nginx warns again at `-t` time — loud and early — and the fix is a
one-line amendment here.

**Scope boundary.** The repo-root dev front door (`nginx/nginx.conf`) mirrors
this directive in its own `http` context so local `-t` runs are warning-free
too; that file lives outside this `project/` (the `nginx/` tree's
`project/design/D01.md` owns the mirror) and is not this Decision's to build or
test. The per-service fragments themselves need no change — a fragment is
included inside `server` context, where the directive cannot legally appear.

**Rejected.**

- **A separate opsctl-authored tuning file in `conf.d/`.** Keeps this fragment
  purely server blocks, but adds an opsctl template, an install step, and a
  third subproject's spec change to carry one line — and it lands only when a
  box is re-initialized, not on the next deploy.
- **Raising `variables_hash_bucket_size` instead.** nginx's warning offers
  either knob; a larger bucket makes every variables-hash lookup walk a longer
  chain on every request, while a larger table keeps lookups cheap for a few
  kilobytes of memory.
- **Leaving the default and tolerating the warning.** nginx falls back to a
  non-optimal hash and the config still works, but the cost is paid on every
  reload in operator attention, which is the scarcer resource.

**Proof.** Exactly as D20 and D33: nginx is never run by the suite's gate, so
the committed fragment is verified by a hermetic Go test that reads
`etc/nginx.conf` from disk and asserts its content and placement. The live
behavior — a warning-free `nginx -t` on the box — is a manual deploy-time
check.

**Verification.**

- R-6MX7-JDFX — `dashboard/etc/nginx.conf` contains the directive
  `variables_hash_max_size 2048;` **before the first `server {`** (file-content
  test reading the fragment from disk and comparing offsets; an implementation
  that omits the line, weakens the value below 2048, or places it inside a
  `server` block — where nginx would reject it at load time — fails).
