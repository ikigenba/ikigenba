# Decision 41 — Adopt the suite brand icon contract: the shipped icon set and its link markup

**Decision.** dashboard adopts the suite's **brand icon contract** —
`root project/design/D29.md` — which owns the shipped file set, the filenames,
the static location, the three `<link>` elements, and the pinned content types.
This Decision is the **citation, and citation is adoption**: dashboard owns none of
that contract's content and restates none of it normatively. What is local — and
all this Decision adds — is **where the files land in this tree, which documents
carry the markup, and where the proof lives**.

The contract carries three `[proof: per-service]` ids, which dashboard therefore proves
in its own tree:

- `R-RYDN-YNR5` — every HTML document the service serves carries all three link
  elements.
- `R-RZLK-CFHU` — each of the three asset paths answers `200` through the composition
  root with the pinned content type.
- `R-8MFA-HUNC` — the bare `GET /favicon.ico` answers `200` at the service's root
  path through the composition root, with the same bytes as the static path.

**Where the files land.** The three shipped files are committed into dashboard's own
static root, beside the `tokens.css` and `.woff2` fonts already there:

    dashboard/ui/static/favicon.ico
    dashboard/ui/static/favicon-32.png
    dashboard/ui/static/apple-touch-icon.png

They are copied from `design/brand/`, the suite's shared reference directory, by
the same hand-copy that already put `tokens.css` and the fonts in this tree.
Because they sit under an embedded static tree, they are compiled
into the binary by the package's existing `go:embed` directive and add roughly
47 KB to the shipped artifact.

**Which documents carry the markup.** dashboard serves five documents — `index.html`, `install.html`, `metrics.html`, `oauth_authorize.html`, `profile.html`, with **one** `<head>` in practice: all five render through the `shell_head` template in `ui/html/partials/shell.tmpl`, which already carries the `/static/tokens.css` and `/static/app.css` links.

**The `href` form** is the absolute `/static/…` form `shell_head`'s existing stylesheet links use — the dashboard answers on the apex, so its static mount *is* the origin root. The contract fixes the target — the service's own
static mount — and not the string, so this form conforms.

**The root-path route.** The dashboard is the one service that receives the bare
`/favicon.ico` request in production, since it owns the apex. The `/static/`
mount does not answer it — `internal/server/routes.go` mounts
`GET /static/` and `/favicon.ico` is a different path — so `register` gains an
explicit `mux.Handle("GET /favicon.ico", …)` beside it. The handler answers by
rewriting the request path to `/static/favicon.ico` on a shallow copy of the
request and delegating to `a.staticHandler()`, so the root path returns the same
bytes and the same content type as the static path by construction rather than
through a second read of the embedded tree.

The dashboard registers this itself rather than receiving it from the chassis:
it runs as the apex app through appkit's Apex bypass with its own complete route
table, so appkit's `Options.WWW` mount never applies to it.

The route is registered **outside every session gate**, exactly as
`GET /static/` already is — `register` gates per handler, not around the mux, so
a route added to the table is ungated unless its handler says otherwise. This is
load-bearing rather than incidental: the clients the root path exists for hold
no session, and a login redirect there fails them the same way a `404` does.

`internal/server/static.go` serves the embedded tree with `http.FileServerFS`
and does not route through `appkit/web`, so the dashboard pins `.ico` itself,
in that file's `init()`.

**Where the proof lives.** All three adopted ids are proven in **`internal/server/`**, the
package that assembles dashboard's real router and is therefore the only place a
request can reach the icon routes the way production does. The markup assertion
reads the committed documents through the same rendering path a user's request
takes; the asset assertion issues `GET` for each of the three paths against the
assembled router at its mounted prefix and checks status, non-empty body, and
exact content type. Neither test constructs a handler directly: a directly-driven
handler proves the bytes exist, never that the assembled service serves them.

**Rejected.**

- **Restate the file set and the markup locally so this design reads
  self-contained.** A local restatement is drift by construction: it goes stale
  the moment `root project/design/D29.md` changes, and the suite's rule is cite,
  never restate. Rejected.
- **Re-mint local ids for the two behaviors instead of citing `R-RYDN-YNR5` /
  `R-RZLK-CFHU`.** Both are `[proof: per-service]`: each is the suite's handle for one
  behavior, proven once per adopting tree. Parallel local ids would give one
  behavior two handles and break the id-to-behavior invariant. Rejected.
- **Assert the markup by string-matching the committed HTML file on disk instead
  of through the render path.** It is the cheaper test and it is a proxy: it
  proves a file contains a substring, not that the served response does. For a
  template-rendered head the two can differ. Rejected.
- **Prove the assets by calling the static handler directly.** Same proxy
  pattern: it cannot fail when the route is missing from the composition root,
  which is the failure actually worth catching. Rejected.
- **Treat the existing `GET /static/` mount as answering the bare
  `/favicon.ico`, so no root route is needed.** This is what this Decision said
  before, and it was simply false: `net/http`'s mux matches the two paths
  separately, so the root request `404`s while every `/static/` assertion passes.
  Nothing in the tree could catch it, because `R-RZLK-CFHU` only ever asks for
  the three `/static/…` paths. Rejected, and `R-8MFA-HUNC` exists to make the
  root path a covered behavior rather than an assumed one. Rejected.
- **Serve the root path from a second `http.FileServerFS` over the embedded
  tree.** It duplicates the `noDirFS` wrapper and gives the content type a
  second place to be decided, for a route whose entire contract is that it
  returns what the static path returns. Delegating to `a.staticHandler()` makes
  that identity structural. Rejected.

**Verification.**

All three ids below are **adopted**, not minted here: each belongs to
`root project/design/D29.md`, which states the behavior. These lines say only
what substrate proves it inside `dashboard/`.

- `R-RYDN-YNR5` — adopted from `root project/design/D29.md`. Substrate: hermetic — a Go
  test in `internal/server/` that renders every document dashboard serves through the real
  rendering path and asserts each response's `<head>` carries all three link
  elements: `rel="icon"` with `sizes="any"` at `favicon.ico`, `rel="icon"` with
  `type="image/png"` at `favicon-32.png`, and `rel="apple-touch-icon"` at
  `apple-touch-icon.png`. The document set is **enumerated from the committed
  tree**, not hard-coded, so a page added later without the links fails.
- `R-RZLK-CFHU` — adopted from `root project/design/D29.md`. Substrate: hermetic — a Go
  test in `internal/server/` that builds dashboard's real assembled router and issues `GET`
  for `favicon.ico`, `favicon-32.png`, and `apple-touch-icon.png` beneath the
  mounted static prefix, asserting `200`, a non-empty body, and `Content-Type`
  exactly `image/x-icon` for the ICO and exactly `image/png` for both PNGs.
- `R-8MFA-HUNC` — adopted from `root project/design/D29.md`. Substrate: hermetic — a Go
  test in `internal/server/` that builds dashboard's real assembled router and issues
  `GET /favicon.ico` at the **root path** with no session cookie and no bearer
  token, asserting `200` (not a `3xx`, so a redirect to `/static/favicon.ico`
  fails, and not a login redirect, so a gated route fails), `Content-Type`
  exactly `image/x-icon`, and a body byte-identical to the same router's
  `GET /static/favicon.ico` response.
