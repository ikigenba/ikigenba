# Decision 14 — HTTP surface: `/metrics` page, `/metrics/fragment`, the 60s poll

**Decision.** Two session-gated routes on the apex table, plus one `*app`
field and a poll block in `app.js`. The page and its refresh fragment reuse the
exact in-process session seams the profile/grants pages already use — no nginx
`auth_request`, no new gate.

The surface is named **metrics**, end to end: the routes, the handlers
(`internal/server/metrics.go`), the templates, the `*app` field, the `app.js`
block, and the page's own title and heading all read *Metrics*. The name
*telemetry* is retired from this surface entirely — it now names the suite's
forensic record service, and one word cannot mean both a box-health graph page
and a cross-service audit trail. **`/telemetry` and `/telemetry/fragment` are
not kept as aliases**: nothing outside the dashboard's own templates ever linked
to them (the page is reached only from the landing tile, D16), so a redirect
would be permanent debt bought for no caller.

```go
// server.Options gains:
Metrics *metrics.Store   // the shared store the collector writes (D13)

// *app gains the field; register() mounts:
mux.Handle("GET /metrics",          a.handleMetrics())
mux.Handle("GET /metrics/fragment", a.handleMetricsFragment())
```

- **`handleMetrics`** — full page. Resolves the session via `a.sessionOwner`; a
  **missing/invalid session redirects `303 → /`** (the profile-page pattern: the
  metrics page is a place you navigate to, so send a signed-out visitor to the
  login landing, not a bare 401). A valid session renders `ui/html/metrics.html`
  from the store's `Snapshot()` (charts built by D15), buffered-then-written so a
  template error is a clean 500.
- **`handleMetricsFragment`** — just the charts block (the `metrics_charts`
  partial) rendered from a fresh `Snapshot()`. It is the poll target, so a
  **missing session returns `401`** (the grants-fragment pattern: an XHR gets a
  status, not a redirect body).
- **The poll (`app.js`).** A block mirroring the live-grants client, but a plain
  `setInterval` rather than SSE (the data only moves on the 60s cadence, so a poll
  matches it and needs no long-lived connection): find `#metrics-block`, read its
  `data-fragment` URL, and every **60000 ms** `fetch` it (`credentials:
  "same-origin"`) and swap `innerHTML`; on a non-OK response leave the stale block.
- **Templates.** `ui/html/metrics.html` and `ui/html/partials/metrics_charts.tmpl`
  are in the `template.ParseFS(ui.Files, …)` list in `server.go`, so a broken
  metrics template fails startup, not a request.

**Rejected.**
- **Keeping the name "telemetry" for this page.** The suite gained a `telemetry`
  service whose whole job is the forensic record of every call in the suite; a
  box-health graph page sharing that name would make every future sentence
  ambiguous, in the code and in the owner's nav. The graph page is literally a
  metrics view, so it takes the accurate name and yields the other.
- **Redirecting `/telemetry` → `/metrics` for compatibility.** No external
  contract points at it: it is a human page reached from one in-app tile, never
  an API, never linked from another service. A permanent redirect would preserve
  the ambiguous word in the route table forever, which is the thing the rename is
  buying its way out of.
- **Renaming only the internal package, leaving the user-visible page
  "Telemetry".** Then the owner's nav and the code disagree, which is worse than
  either name alone; the rename is user-visible on purpose (D16 and the product).
- **SSE for the refresh.** The live-grants block uses SSE because grants change on
  arbitrary events; metrics change only every 60s, so a poll is the simpler,
  cadence-matched fit — no write-deadline clearing, keepalives, or subscription bus.
- **A JSON `/metrics/data` endpoint + client-side charting.** The chosen option
  keeps all chart geometry in Go (testable) and renders real SVG on first paint;
  a JSON+JS approach moves untested drawing into the browser and paints blank until
  JS runs.
- **Redirecting the fragment too.** A `303` in an XHR poll response is noise; the
  fragment returns a status the client can just ignore.
- **A shared page+fragment handler.** They differ in signed-out behavior (redirect
  vs 401) and in whether they emit the page chrome; two small handlers over one
  render helper is clearer than one branching on a query flag.

**Verification.**
- R-WWGV-S5V0 — `GET /metrics` with a valid session returns `200` and a body
  containing the metrics charts container, whose title/heading read "Metrics" and
  which contains no occurrence of the word "Telemetry" (http test with a minted
  session).
- R-WXOS-5XLP — `GET /metrics` with no/invalid session returns `303` with
  `Location: /` and no charts (http test).
- R-WYWO-JPCE — `GET /metrics/fragment` with a valid session returns `200` and
  the charts-block markup (http test).
- R-X1CH-B8TS — `GET /metrics/fragment` with no session returns `401` and does
  not render the charts (http test).
- R-X2KD-P0KH — the served `app.js` wires the metrics poll: it references
  `metrics-block`, fetches its fragment URL, uses a `60000` ms interval, and
  contains no `telemetry` identifier (served-asset text assertion).
- R-X3SA-2SB6 — the old routes are **gone, not aliased**: `GET /telemetry` and
  `GET /telemetry/fragment` driven with a **valid** session each return exactly
  `404` — not `200`, and not a `301`/`302`/`303` (http test; using a live session
  keeps a signed-out redirect from being mistaken for the old route surviving).
