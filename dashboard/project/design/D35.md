# Decision 35 — The authn rate limiter: per-token sliding window in `internal/ratelimit`

**Problem.** The `/internal/authn` introspection endpoints gate every `/srv/`
request on the box; a runaway or abusive bearer must not be able to hammer them
without bound. The limit has to be applied per credential without ever letting
credential material become a lookup key, and it must be trivially disabled for
tests and for an operator who opts out.

**Decision.** A dedicated package `dashboard/internal/ratelimit` owns the
limiter; the server consumes it as a required constructor option.

```go
// Limiter is a sliding-window rate limiter keyed by an opaque string.
type Limiter struct { /* limit, window, injected now, mutex, per-key hit ring */ }

func New(limit int, window time.Duration) *Limiter

// Decision reports one Decide outcome. WindowCount is the number of requests
// observed for the key within the current trailing window.
type Decision struct {
    Allowed     bool
    WindowCount int
    WindowStart time.Time
}

func (l *Limiter) Decide(key string) Decision
func (l *Limiter) Limit() int
func (l *Limiter) Window() time.Duration
```

- **The key is a server-side row id, never credential material.** The two
  decision sites (`internal/server/authn.go`) key on `oauth_tokens.id` for the
  OAuth path and the personal token's `id` for the PAT path. The plaintext and
  its hash never enter the limiter. The empty-key shortcut (allow without
  recording) is a defensive backstop, not the enforcement point — the contract
  lives at the call site.
- **Limiting runs only after auth fully passes**, so unauthenticated callers
  never consume a key's budget and cannot probe for a token's existence via
  rate-limit behavior.
- **Disabled is permissive by construction.** A nil `*Limiter`, a non-positive
  limit, or a non-positive window makes `Decide` return `Allowed: true`
  unconditionally — the opt-out for tests and operators.
- **In-memory, per-instance.** The ledger is a per-key timestamp slice guarded
  by a mutex; this box ships one dashboard instance, so a shared store is out of
  scope by the suite's one-box bet. The clock is an injected `now` seam for
  deterministic tests.
- **Config.** `cmd/dashboard/main.go` constructs the limiter from
  `DASHBOARD_AUTHN_RATE_LIMIT` (default 120) and
  `DASHBOARD_AUTHN_RATE_WINDOW` (default 10s); `server.Options.RateLimiter` is
  required (a nil option fails construction loudly).

The 429 response shape, its `Retry-After` header, the audit row, and the
`rate_limited` edge telemetry record are D31's; this Decision owns only the
windowing seam that produces the decision.

**Rejected.**
- **Keying by the token plaintext or its hash** — puts credential material in a
  long-lived in-memory map for zero benefit; the server-side row id is already
  unique per credential.
- **A persistent or shared-store limiter (SQLite/redis)** — a durable ledger
  for ephemeral window state, and multi-instance coordination this single-box
  deploy cannot need.
- **Limiting before authentication** — lets unauthenticated traffic exhaust a
  key's budget and turns the limiter into an existence oracle.
- **A fixed-window counter** — cheaper but bursts up to 2× the ceiling at
  window boundaries; the sliding window's trailing-interval count is the shape
  the ceiling promises.

**Verification.**
- R-I98E-62GS — with limit N over window W and an injected clock, N `Decide`
  calls for one key are allowed, the (N+1)th is **rejected** carrying
  `WindowCount == N`, and after the clock advances past W the same key is
  **allowed again** — a fixed-window or never-releasing counter fails the
  slide, and an implementation that ignores the ceiling fails the rejection.
