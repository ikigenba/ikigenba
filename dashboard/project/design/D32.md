# Decision 32 — The internal audit log stays; edge records are additive

**Decision.** `internal/audit` and its `audit_log` table are **kept unchanged**.
The `edge` telemetry records of D31 are added *alongside* the existing
`authn.allow` / `authn.deny` / `rate_limit.hit` audit rows, not in place of them.
An allow therefore writes two things: a durable audit row in the dashboard's own
SQLite (as today) and a best-effort edge record to the telemetry service (new).

The two records answer different questions and have different guarantees:

- **The audit log is the dashboard's security record, and it is durable.** Its
  write shares the request's transaction where the event is transactional, it
  lives in the dashboard's own database, it survives the telemetry service being
  down or absent, it is never sampled or dropped under load, and it is pruned
  only by an explicit admin command. Authorization decisions on the box's front
  door are exactly the kind of fact that must not be delivered best-effort.
- **The telemetry record is the suite's forensic trail, and it is best-effort.**
  Its value is *joinability* — one correlation id across every service — bought
  at the price of a ring buffer that drops oldest under pressure, a fire-and-
  forget POST, and a 90-day retention window. Excellent for reconstructing what
  happened; not a system of record.
- **Most audit events have no edge equivalent at all.** `federation.*`, `dcr.*`,
  `oauth.token.*`, `oauth.reuse.detected`, `oauth.chain.revoked`, `session.*`,
  `pat.*`, `admin.*` — the majority of the enumeration — are not gated-route
  decisions. Retiring the audit log to avoid duplicating three of its event types
  would delete the other twenty.

The overlap between them is three event types and is accepted as the price of
keeping a durable security log and a joinable forensic trail as separate
concerns. Nothing about the audit schema, event types, or write sites changes in
this work.

**Rejected.**
- **Retire the audit log and rely on telemetry.** It trades a durable,
  locally-owned, admin-pruned security record for a lossy one held by another
  service, and it would silently drop the twenty-odd audit event types that have
  no `edge` counterpart. A security log you can lose because a sibling service is
  down is not a security log.
- **Fold the audit write into the recorder (audit becomes a telemetry emitter).**
  Same loss of durability, plus it makes the dashboard's authentication path
  depend on another service's availability for a record it is obliged to keep —
  and would tempt a future change to block on delivery, which the best-effort
  contract forbids.
- **Fold telemetry into audit (emit edge records by tailing `audit_log`).**
  Preserves durability but loses the point: audit rows carry no correlation id
  and are dashboard-local, so nothing would join them to the service work the
  decision authorized, which is the entire capability being bought.
- **Write edge records only when telemetry is unconfigured, audit only when it
  is.** A conditional record is the worst of both — neither surface can be relied
  on, and every future reader has to know which mode the box was in.

**Verification.**
- R-XNAO-746A — a single `handleAuthn` allow produces **both**: an
  `authn.allow` row in the `audit_log` table of the real temp database (carrying
  its owner email, client id, and chain id as before) **and** an `edge` record
  delivered to the live ingest sink — and the audit row is written even when the
  sink is unreachable, proving the durable path does not depend on the
  best-effort one.
