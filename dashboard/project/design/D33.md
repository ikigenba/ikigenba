# Decision 33 — The apex nginx fragment blanks client-supplied correlation ids and forwards the original method

**Decision.** `dashboard/etc/nginx.conf` — the apex server block the dashboard
owns — gains two things:

1. **`X-Correlation-Id` is blanked on every location that proxies to the
   dashboard.** The apex `location /` and both internal introspection locations
   (`= /_authn`, `= /_session-authn`) each set `proxy_set_header
   X-Correlation-Id "";`. The apex is a **public, ungated** surface, so anything
   arriving in that header came from the client: blanking it means appkit's
   read-or-mint middleware behind it always mints, and no caller can inject
   itself into — or forge — a chain. This is the "ungated public locations strip
   the header" half of the suite rule; the dashboard has no gated locations of
   its own to carry the other half (it is the apex/`DEFAULT` app behind appkit's
   Apex bypass and runs no `auth_request` in front of its own routes), so
   `auth_request_set` capture appears in the *services'* fragments, not this one.

2. **`X-Original-Method` is forwarded on both internal locations.**
   `proxy_set_header X-Original-Method $request_method;` sits beside the existing
   `X-Original-URI $request_uri;`. The introspection endpoints need the *gated*
   request's method to compose an edge record's `op` (D31), and the
   `auth_request` subrequest does not carry it reliably. Both locations are
   dashboard-owned and shared by every service fragment on the box, so one line
   in each covers the whole suite — no per-service fragment change is needed for
   the method.

```nginx
location = /_authn {
    internal;
    proxy_pass              http://127.0.0.1:3000/internal/authn;
    proxy_pass_request_body off;
    proxy_set_header        Content-Length "";
    proxy_set_header        X-Original-URI    $request_uri;
    proxy_set_header        X-Original-Method $request_method;
    proxy_set_header        X-Correlation-Id  "";
}
```

**Proof.** nginx is never run by the suite's test harness, so — exactly as D20's
`@login_bounce` primitive is proven — this is verified by a Go test that **reads
`etc/nginx.conf` from disk** and asserts its content. The precedent is local and
id-tagged: `cmd/dashboard/main_test.go` already carries `R-XJBT-7YIF` and
`R-XKJP-LQ94`, which extract a named location block from the committed file and
assert *within that block*. These ids extend that pattern rather than settling
for a whole-file grep, so a directive added to the wrong location fails. The live
behavior (that nginx actually drops the header, and that `auth_request_set` in a
service fragment captures the minted id) remains a deploy-time smoke.

**Scope boundary.** Each service's own `<svc>/etc/nginx.conf` fragment must add
`auth_request_set $correlation_id $upstream_http_x_correlation_id;` +
`proxy_set_header X-Correlation-Id $correlation_id;` on its gated locations and
blank the header on its ungated public ones. Those files live in other trees and
are **out of scope** for this `project/` — this Decision covers only the
dashboard's own fragment.

**Rejected.**
- **Relying on the introspection handlers alone to ignore inbound ids.** They
  do (D30), and that is the load-bearing defense. But the apex `location /`
  serves the dashboard's *own* pages through appkit's read-or-mint middleware,
  which trusts inbound ids because it is designed for loopback peers — on the
  public apex that trust is misplaced, and only the fragment can correct it.
- **Blanking the header in application code instead of nginx.** The rule is a
  property of the trust boundary, and the boundary is nginx; putting it in Go
  would mean every future handler has to remember it, and would still leave the
  middleware trusting the value on some paths.
- **Passing the original method as part of `X-Original-URI`.** It would overload
  a header services already parse as a URI, breaking the existing
  resource-derivation logic for a value a second header carries cleanly.
- **Deriving the method from the subrequest instead.** nginx's `auth_request`
  subrequest is not a faithful copy of the client's request method, so an edge
  record's `op` would report a method the client never sent — a forensic record
  that quietly lies is worse than one that omits.

**Verification.**
- R-XOIK-KVWZ — the apex `location /` block in `dashboard/etc/nginx.conf`
  contains `proxy_set_header X-Correlation-Id "";` (file-content test reading the
  fragment from disk; an implementation that adds the line only to the internal
  locations fails).
- R-XPQG-YNNO — both the `= /_authn` and `= /_session-authn` location blocks
  contain `proxy_set_header X-Original-Method $request_method;` **and**
  `proxy_set_header X-Correlation-Id "";`, and both still contain the existing
  `X-Original-URI $request_uri` line (file-content test; asserting per-block, so
  adding the lines to only one location fails).
