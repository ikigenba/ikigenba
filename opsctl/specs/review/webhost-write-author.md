# Nginx write-only regeneration author review

## Complete restore consumer task

Current contract: `opsctl restore crm` cannot satisfy both regeneration and no
nginx reload through the D06 package surface. `nginx.Render` returns bytes but
does not publish them; `nginx.Apply` publishes, tests, and reloads. D14's old
prohibition on nginx regeneration must therefore be replaced by its owner.

Proposed operator tasks:

```sh
sudo opsctl restore crm
sudo opsctl restore dashboard
```

The database-bearing crm restore and the no-database dashboard restore each
regenerate the single owned nginx file from the manifests now on disk before
starting an app that was active on entry. Neither task tests or reloads nginx.
The restored routing will take effect when nginx is subsequently reloaded by
an operation that owns that action. D14 owns archive selection, restored-data
publication, callback timing, stopped-unit handling, progress and diagnostics.

The complete package consumer task, after CLI configuration loading has supplied
`hostName`, uses D14's injected callback:

```go
func restoreService(ctx context.Context, env host.Env, cloudEnv cloud.Env,
    store config.Store, service string, at *time.Time, hostName string,
) (backup.RestoreReport, error) {
    regenerateNginx := backup.NginxRegenerator(func(ctx context.Context) error {
        return nginx.Write(ctx, env, hostName)
    })
    return backup.Restore(ctx, env, cloudEnv, store, service, at, regenerateNginx)
}
```

This function is review-local consumer code, not a proposed export. `Write`
re-discovers the current manifests through `Render`; it does not accept stale
rendered bytes from before the restore. The callback propagates its error to
restore so D14 can prevent an app start. D14 R-1NHS-71WK supplies the injected callback
contract and R-1OPO-KTN9 calls it after successful restoration/regeneration
and before any unit starts; R-BE42-GCU4 owns CLI wiring, keeping `internal/backup` independent of `internal/nginx` and
`internal/cli`; nginx still depends internally only on host and apps. No new
public CLI subcommand is added.

## Failure consumers

- A restored malformed manifest, a discovery failure, or two routed defaults:
  calling `Write` returns the `Render` operational failure; the destination
  remains unchanged, and no candidate is written. Existing Render contract
  identifies malformed service/manifest failure or the conflicting services.
- Destination preparation or rename fails: `Write` returns an error, preserves
  previous bytes and mode or prior absence, and leaves no candidate temporary
  file behind. D14 consumes the error and owns the stopped-unit outcome.
- nginx or systemctl is absent, or the newly generated bytes would fail nginx
  validation: `Write` does not invoke either tool. Successful file publication
  is its success condition. This is exactly the restore seam; Apply retains
  its separate validation and reload behavior.
- Existing configuration bytes already match: `Write` still publishes using
  the specified atomic mode-0644 publication, returns nil, and executes no
  command.

The unresolved Apply failure-after-successful-test/reload issue remains in
[nginx-reload-failure.md](../issues/nginx-reload-failure.md). This extension
makes no decision about it. Existing external nginx configuration-acceptance
observations remain required before check-spec; this local filesystem API
adds no new external-tool assumption.
