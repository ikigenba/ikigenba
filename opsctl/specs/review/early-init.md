## Complete consumer tasks: current and proposed

### Initialize a configured host

Current D05 usage was `sudo opsctl init`: three PATH checks and DNS/host checks,
then exit 0 without configuring anything. Its help advertised an empty sequence.

Proposed usage, after installing the four prerequisites and supplying DNS and
backup credentials, sets all ten keys needed by the designed success case:

```sh
sudo opsctl config set host.name=ikigenba.dev
sudo opsctl config set aws.region=us-east-2
sudo opsctl config set acme.email=ops@ikigenba.dev
sudo opsctl config set dns.provider=route53
sudo opsctl config set dns.zones=ikigenba.dev:Z09565073GHK8BYWQ1A78
sudo opsctl config set backup.s3_uri=s3://example-bucket/ikigenba.dev/
sudo opsctl config set backup.host_files_seconds=86400
sudo opsctl config set backup.service_files_seconds=86400
sudo opsctl config set backup.service_db_seconds=86400
sudo opsctl config set backup.service_wal_seconds=300
sudo opsctl init
```

For the ready-host fixture in `init.md`, stdout is exactly:

```text
nginx: ok (/usr/sbin/nginx)
certbot: ok (/usr/bin/certbot)
systemctl: ok (/usr/bin/systemctl)
litestream: ok (/usr/bin/litestream)
dns.provider: ok (route53)
dns.zones: ok (ikigenba.dev)
host.name: ok (ikigenba.dev)
zone ikigenba.dev: ok (route53 Z09565073GHK8BYWQ1A78, 4 nameservers delegated)
host ikigenba.dev: ok (zone ikigenba.dev)
wildcard ikigenba.dev: ok (77.112.106.79)
```

Exit 0, empty stderr. The four domain setup actions have completed. Repeating
`sudo opsctl init` gives the same report and exit status for unchanged inputs;
current certificates and generated bytes remain unchanged. Changing, for example,
`backup.service_files_seconds` with `opsctl config set` then running `init`
regenerates the timer state from the store. A zero period leaves that backup timer
disabled/stopped while the renewal timer stays enabled/active (D12).

Unresolved beside this task: zero/unset database or WAL periods and missing
backup region/prefix are outside the completed replication success contract;
see ../issues/backup-replication-periods.md. In particular, the no-database,
all-zero setup case is not yet a verified success. The file-timer zero behavior
above does not resolve those replication inputs.

### Find and repair all prerequisites

Both designs accept `sudo opsctl init` and report missing certbot and host.name
on stdout with exit 2 and empty stderr, retaining eligible zone checks and
omitting host/wildcard checks. The proposed report additionally includes
`litestream: ok (/usr/bin/litestream)` in its fixed fourth position. After:

```sh
sudo dnf install -y certbot
sudo opsctl config set host.name=ikigenba.dev
sudo opsctl init
```

the proposed command completes all four setup actions; the old one only reran
checks. The package-manager line is the user's example of fixing the external
prerequisite, not an opsctl installation responsibility. If provider opening
fails while zones and host.name are valid, the proposed command still reports
host zone membership and wildcard resolution. Zone checks require a provider.

### Help, rejected arguments, corrupt store, and failed setup

In both designs `opsctl init --help` and `opsctl init -h` work for non-root users
without changing state; proposed help is the complete story text, now normative
inside R-LGEA-VQO1, and advertises four PATH checks and four setup steps.

`sudo opsctl init --force` or `sudo opsctl init ikigenba.dev` yields empty stdout,
exit 2, and stderr `opsctl: init takes no arguments\n\nsee 'opsctl init --help' for usage\n`.
No checks run. A corrupt store yields empty stdout, exit 1, and
`opsctl: /etc/ikigenba/config.json is corrupt\n` on stderr, preserving the file.

Newly possible setup failures leave the completed preflight report on stdout,
exit 1 and an operational diagnostic on stderr; external captured output is
quoted under D2. For example, a failing nginx application occurs after successful
certificate setup, preserves that certificate, follows D06's candidate-file
failure behavior, and invokes neither replication nor timers. Re-running after
repair is the complete recovery task; there is no rollback or alternate workflow.

### Internal composition surface

The consumer is `cli.Run(args, stdin, stdout, stderr, deps)` (D01); it owns a
`config.Store{Root: deps.Root}` (D03). Normalized dependencies construct
`host.Env{Root: deps.Root, Getenv: deps.Getenv, Execute: deps.Execute, Now: deps.Now}`.
The complete post-preflight task is the following sequence with an error return
terminating the sequence after each call:

```go
err := cert.Obtain(ctx, env, hostName, email)
// On error, report and stop. Otherwise:
err = nginx.Apply(ctx, env, hostName)
// On error, report and stop. Otherwise:
err = backup.SetupReplication(ctx, env, store)
// On error, report and stop. Otherwise:
err = backup.SetupTimers(ctx, env, store)
// On error, report and stop. Otherwise exit 0 with no additional output.
```

These declarations are owned by D07, D06, D11 and D12 respectively; D05 does not
add a new domain package or duplicate declarations. `cert.Obtain` accepts
`(context.Context, host.Env, string, string) error` and means obtain or renew if
due. The current API had no setup consumer. No standalone setup-step stdout is
relayed by the proposed init workflow.

For zone checks, an independently opened provider is handed to `dns.Open` by an
`Env.Open` callback that returns it without another opening action, preserving
`Deps.DNS.LookupNS`. This yields a correctly configured `Client.Check` resolver.
For host matching alone, `dns.Client{Zones: zones}.ZoneFor(hostName)` needs no
provider. Every mentioned field/method is declared in D01, D03 or D04; there is
no invented `ParseZones` export and no dereference of a client after Open fails.

## Decisions and evidence

No unresolved user-behavior question was identified in the D05 composition scope.
The corrupt-story introductory phrase “three PATH lookups” is stale editorial
text: its help, ready example and prerequisites explicitly require four including
litestream. D05 follows those concrete criteria. The formerly empty sequence and
provider-dependent host-membership check are superseded, not preserved for
compatibility.

Independent parsing follows D04's exact published grammar. Opening the provider
independently is necessary to expose two unrelated failures in one run. The
success client is obtained through dns.Open to preserve its private resolver
context; constructing a Check client manually would lose that dependency.

The original D05 recorded 2026-09-10 host PATH observations for nginx, certbot,
systemctl and a fixed-label resolver observation, but this author performed no
external probes and has no attached raw record establishing those observations.
The fourth executable and domain external-command assumptions require the root's
consolidated external-evidence review before check-spec. D05's report contract
can be tested with supplied dependencies; live availability is not claimed.

The story readiness fixture omits setup-key details such as ACME email in its
short preconditions. The complete task requires setup domain configuration too;
missing setup inputs produce the domain operational failure after the report,
not an invented extra preflight check. No new check beyond the exact help is
introduced. D07 owns obtaining a certificate while nginx is initially inactive;
D05 does not invent an nginx start operation.
