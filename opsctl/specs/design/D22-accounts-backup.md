# D22-accounts-backup

A host backup carries the host's people and businesses as well as its configuration, so a rebuilt host comes back whole (S08). This document is the part of package `internal/accounts` (D20) that serves it: the manifest that names every business group and user with their ids, the check a restore makes before it changes anything, and the three steps that put the shell group, each business group and each user back. D13 (package `internal/backup`) owns everything else: the objects, the archive and its members, extraction with numeric owners, modes and ACLs, the order of the steps, the result lines and the CLI. It builds on D20's and D21's vocabulary and restates none of it: `RefusedError` (R-00ZU-A64U), `ValidName` (R-04NJ-FHCX), how the account files are read (R-UNIU-EKTL, R-0BYX-Q3T3), what a taken name, a business group, a user and a group's members are (R-0D6U-3VJS, R-0EEQ-HNAH, R-0FMM-VF16, R-0GUJ-96RV), the `no group` refusal (R-UOQQ-SCKA), how commands run and fail (R-Y2P9-C9I9, R-XCVE-0N7E), a user's state (R-U6TD-F8WF), the installed timer (R-X1WA-KPJ5) and the timer step (R-X346-YH9U).

The manifest is what the files under `/etc` say and nothing more: each business group's slug, the gid of its group, the uid of its service account and its members; each user's name, uid, the gid of their private primary group, their state and their business groups. Two lists, sorted by name, each empty rather than absent when the host has none, so D13 writes `{"groups":[],"users":[]}` for a host with nobody. `ReadManifest` refuses to describe a host whose accounts a restore could not put back, a hand-made member of `shell` with a name `ValidName` rejects or two entries sharing an id, so a backup never holds a manifest its own restore would refuse; the backup then fails, as S08 wants when the accounts cannot be written.

A uid or gid is how every file in a home and a folder names its owner, so a restore never renumbers. `CheckManifest` reads the account files, runs nothing and changes nothing, and compares each entry with the host. An entry whose name the host lacks and whose ids no account or group holds will be made; an entry the host has with the same name, the same kind and the same ids is kept; anything else collides, and the first collision, groups before users and each in name order, is the refusal, in the words of S08. A manifest that is not well formed, a name `ValidName` rejects, two entries with one name or one id, a state other than the two, a user in a group the manifest does not name, is an error rather than a refusal: it says the object is broken, not that the host is in the way. `RestoreGroup` and `RestoreUser` make the same judgement for their own entry before they run anything, so neither renumbers when called without the check.

The shell group comes first, made the way hardening makes it (D19 R-QV5H-8JFL), since every user belongs to it and a restore runs before `init` on a rebuilt space.

A business group is made the way `opsctl group add` makes one over a folder already there: D13 unpacks `/srv/<slug>` first, and `RestoreGroup` then runs `groupadd` and `useradd` with the manifest's gid and uid given explicitly, never read from the folder, whose owners in the gates are the test's own since extraction there cannot chown, and then the rest of AddGroup's path. Every AddGroup side effect follows, the folder's owner, mode, setgid and default ACL, git left alone because the folder is already a repository, and the `safe.directory` entry that `/etc/gitconfig`, not part of the backup, needs on a new host. A group already there with the same ids is left exactly as it is. Members are not set here: users join their groups as they are made.

A user is made with `groupadd` for the private group with the manifest's gid and then one `useradd` with the manifest's uid, that group as primary, `shell` and the business groups as supplementary groups, the home field `/home/NAME`, and no home creation, since D13 has already unpacked the home and the key file with their owners: `--no-create-home` creates nothing and so copies no skeleton (useradd(8), `-M`). A user who was locked is created locked: `--expiredate 1970-01-02`, day 1 in useradd(8)'s documented `YYYY-MM-DD` form, sets the expiration field D21 reads as locked, so no failure later in the run can leave a locked user able to sign in with the key already in place. A user already there with the same ids is converged instead: `gpasswd` takes them out of each business group the manifest does not name and adds them to each it does, which leaves `shell`, `wheel` and every other group, and every other user, alone, so the re-run story's `dave` stays in `acme`. Then the user's state is made what the manifest says by running exactly what `opsctl user lock` or `opsctl user unlock` runs (R-X7ZS-HK8M, R-KV2L-Q7BD): a locked user loses lingering and any session, and an active user gets the timer step exactly when the timer is installed, which on a rebuilt space it is not until `init` (D21 `EnsureTimers`).

Undo follows D21's split by what a failure leaves. `RestoreGroup` is AddGroup's path, so it keeps AddGroup's undo (R-0T1J-2W6T): the account and group go, the folder stays, and a run again adopts it. `RestoreUser` does not take AddUser's undo. AddUser undoes because what it made, home included, is its own; here the home and key file are the backup's, unpacked before the call, and removing the account would gain nothing a re-run does not. Instead it follows `lock`, `unlock` and `delete`: a failed step stops the user there, and a run again converges, because every step after `useradd` succeeds again on a user who already has what it makes, and the check keeps a user with the manifest's name and ids. The one state a re-run could not get past is a private group made by `groupadd` whose `useradd` then failed: the name would be taken by a group that is not a user, and the check would refuse it. So that group alone is removed when `useradd` fails. This matches the sshd story, where the steps before the failure stay in place and a run once the cause is fixed finishes the job.

Tests use a temporary `Root` with fixture `/etc/passwd`, `/etc/group` and `/etc/shadow`, folders the test process creates under `<Root>/srv` with its own uid and gid, and recorded `Execute` whose fakes may rewrite the account files as the real tools would.
