# D14-service-restore

Restore combines independently timed service files and database history.
An app's socket and service are both stopped for the restore, socket first,
because an idle service behind a listening socket would otherwise be started
again by the next request mid-restore; an app counts as running when its
socket is. A disabled app (D10) stays disabled: its data is restored and
neither of its units is started. A restore puts data back under an app that
is already installed: `/opt/<service>/bin/<service>` is there and
`/opt/<service>/etc/manifest.toml` names the service. That installed manifest,
not anything the archive holds, says what the service declares, its secrets
and its database; application binaries, the manifest and unit installation
remain deployment responsibilities, and nothing under `/opt/<service>/` is
written. A failed restore retains the app activation intent for a retry on
the same running host.

The nginx configuration is regenerated after a restore through a callback the
CLI supplies, so the restored service's block appears without running init.
The CLI reads `host.apex` beside `host.name` for that callback (D06), so a
restored service that is the apex app answers at the parent domain again. As
install and uninstall do (D09, D10), the CLI checks a nonempty `host.apex`
against `host.name` before the workflow begins: a `host.apex` the host's name
cannot carry is refused with the shared D01 diagnostic before any object is
read, any unit stopped, or any file changed, so no step line is printed and
nothing is left stopped. The callback path remains the contract for a callback
failure of any other kind: it fails the restore at the nginx regeneration stage
with the completed steps and stopped units reported. The `host.name` the CLI
reads is passed through `host.NormalizeName` (D01) before the apex check and
the callback, so restore agrees with install and uninstall on the name.

The same callback rewrites the services file (D15) once `nginx.Write` has
succeeded, so a restored host's services file answers to what is now under `/opt`
without running init. The rewrite is silent, like the nginx regeneration it
follows; a restore that fails before the callback, or whose `nginx.Write`
fails, leaves the file as it was; and a failed rewrite fails the restore as a
failed nginx regeneration does. Restore's help text does not mention it. When
the restore needs the `ikigenba` account, it ensures it through D08's
`EnsureAccount`, the same contract install uses.

A restore writes `state/` to the service's data directory,
`/var/opt/ikigenba/<service>/state/` (D08), and the service's environment file
to `/etc/opt/ikigenba/<service>/env`, and rewrites no unit. An `etc/` that an
archive from before backups held `state/` only still carries is ignored. The
`source` step refuses, before it reads a backup or stops anything, three kinds
of service, in this order: one that is not installed, whether the host never
ran it or only its data is left after an uninstall; one whose `state/` is
still under `/opt/<service>/`; and one with no environment file under
`/etc/opt/ikigenba/<service>/`, the same check init makes (D05), whose unit
still names the old `/opt/<service>/etc/env`. Each names its fix: install the
app, which moves the state, writes the environment file and rewrites the unit
(D09), and the restore can then run. A manifest that is not TOML, or one
that names the service but has another fault, is an installed manifest with a
fault: it fails `source` with that fault in the words init and nginx use, not
as a service that is not installed; only a manifest that parses and names
another app or none means the service is not installed. A lone `/opt/<service>/cache/` or a
leftover `/opt/<service>/etc/env` is no reason to refuse and is left alone.

A backup holds no environment file, so every restore regenerates it as
install does: the `secrets` step reads this host's parameter for the service
and its timing settings before anything is stopped, and the `files` step
writes the file from them and the installed manifest. A missing secret fails
the restore at `secrets` with nothing stopped.

A restore `--from` a snapshot takes the state and the database from that one
object and reads neither the backups nor the replica, so the two halves are
one moment and a fresh space with no replica can be given data. The object is
fetched as named, wherever it lies; the host's role decides what it can read.
Otherwise it is the ordinary restore, step for step.
