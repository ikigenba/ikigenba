# D13-host-backup

The host keeps its configuration, its certificate and its accounts separately
from service data. The backup package owns archive and retirement operations;
the CLI renders their results.

A host backup samples one timestamp and writes two objects under `host/` with
it. The accounts archive, `<ts>.accounts.tar.zst`, comes first: the manifest
of business groups and users that `accounts.ReadManifest` gives (D22), each
user's key file and home, each group's folder, and the sshd host keys, every
member with its numeric owner, its mode and its POSIX ACLs. Then the
configuration archive, `<ts>.tar.zst`, which holds `/etc/ikigenba/` and
`/etc/letsencrypt/` and nothing more, as it always has, so an opsctl from
before accounts were kept restores the configuration of a newer backup and
passes over the accounts object beside it. A configuration object never exists
without its accounts object: when the accounts cannot be written, neither is
the configuration, and the run says both.

Owners and ACLs cross the D01 boundary as commands, so the gates prove them as
an ordinary user who cannot chown. The backup reads them from `getfacl` and,
for symbolic links, which getfacl skips, from `find`; the restore applies them
with `setfacl --restore`, which takes getfacl's own format, and, for links,
`chown --no-dereference`. A test supplies the output of the first two and
reads the arguments and standard input of the last two. Contents, entry types,
modes and link targets are read and written directly under `env.Root`, and a
test observes them with `Lstat`. ACLs travel in the tar as the PAX records
`SCHILY.acl.access` and `SCHILY.acl.default`, the keys star and GNU tar use.

The restore takes the newest configuration archive, as it always has, and the
accounts archive of the same timestamp text; a backup without one restores as
before and says the backup holds none. It reads both whole, validates them,
and checks every name and id the manifest holds against the host with
`accounts.CheckManifest` before it changes anything, so a collision leaves
even `/etc/ikigenba/` untouched. Then it puts back `/etc/ikigenba/` and
`/etc/letsencrypt/`; ensures the group `shell`; unpacks each folder and
recreates its group over it, in slug order; unpacks each home and key file and
recreates its user, in name order; and last puts back the sshd host keys,
checks sshd's configuration with `sshd -t` and reloads sshd, putting the
previous keys back when either fails, as hardening does for its drop-in (D19).
A host key the backup lacks is left in place. Each tree it restores is
replaced exactly, as `/etc/ikigenba/` is, so a second run makes the host what
the backup holds again.

Neither generated services file, `/run/ikigenba/services.json` nor a per-app
host's `/var/lib/ikigenba/services.json`, is archived or restored (D15,
R-9JTU-C7U1). Neither host backup nor host restore reads or touches anything
under `/opt/`, `/etc/opt/`, or `/var/opt/`; that is the service commands'
business. Nor does either read or write any account but a business group's or
a user's: not `ec2-user`, not the suite's `ikigenba`, no home but a user's.
Retirement synchronizes each database at its path in the service's data
directory, the same path `/etc/litestream.yml` names (D11).

Retirement takes the services discovery gives (D08): on a released host the
apps of the release `current` names, run by the units `activate` wrote, and
every data-only service, an app a later release dropped whose `state/` is
kept. A data-only service has no units to stop and no manifest, so it
declares no database to synchronize and only its files are taken, on the line
`opsctl backup` gives it. The host's two objects follow the services', the
accounts line before the host line. Retirement writes nothing under `/opt/ikigenba/`:
the links, the releases, and `/usr/local/bin/opsctl` stay as they were.

Retirement stops every app's socket before any app's service, so no request
and no app still running can start a service again, and leaves every unit
stopped and every enablement as it was: a disabled app is reported as
already inactive and disabled and stays disabled.

Retirement proves final database synchronization through Litestream's enabled
control socket before stopping `litestream.service`. The proof and its failure
policy are part of R-D6RM-9ONC; a service-stop result alone is never
synchronization proof.
