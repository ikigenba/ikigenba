# D05-init

`internal/cli` composes a complete, read-only preflight with the certificate,
nginx, slice, replication, timer and app setup domains. Independent findings are
reported together; dependent checks disappear only when their inputs are
unavailable. Setup is ordered, idempotent, and silent on success. Domain
designs own the generated files and unit behavior.

`init` runs on the three layouts D08's `ReadLayout` tells apart, and the
`apps` step is where they differ. On a *released host* its apps are the
release `current` names, and the step writes each one's whole environment
file and both units exactly as `activate` does (D17, D18), secrets included,
with the boot unit `ikigenba-services.service`, which it enables. Reading the
secrets needs `aws.region` and the cloud, so every app's secrets are read and
its file rendered before any file is written: a secret the parameter lacks
stops `init` in `install`'s words with no app changed, while what the earlier
steps did is kept. Then systemd is reloaded when a unit changed, and every
enabled app whose files changed is restarted, so a timing change is
`config set` followed by `init` here too. Nothing names `/opt/<name>/`, and no
`/opt/<name>/` is created or read. On a *per-app host*, one the first
`activate` has not yet cut over, `init` keeps that layout's behaviour: the
step writes the two timing values and the per-app services file's path into
every installed app (D09's `SetupTimeouts`), and an app whose data or
environment file has not moved stops `init` at `nginx.conf`, as below. On a
*fresh host*, which has no app yet, the step does nothing: `init` does the
host's own work, the certificate, slices, an nginx file with no app, an empty
`/run/ikigenba/services.json` and the `ikigenba` account it needs, Litestream
and the timers. `init` never moves `current` or `previous` and never touches a
release folder.

certbot's hooks name `opsctl` bare (D07), and certbot finds it on its PATH at
`/usr/local/bin/opsctl`, which on a fresh host does not exist until something
makes it. So once the preflight has passed, and before the `certificate` step,
`init` makes it a link when nothing is there: through `current` on a released
host, so it follows every later activate and rollback, and otherwise to the
opsctl that is running, which on a fresh host is the release's own, run by its
full path. Anything already there, file or link, is left alone; `activate`
replaces it (D18). No line reports the link.

The preflight also checks the two app timing keys, `apps.drain_seconds` and
`apps.stop_seconds` (D08), on its `timeouts` line. Rewriting a service unit
keeps the resource settings the app's manifest declares, or their defaults
(D08, D09, D17), so `init` never loosens or drops a limit. A manifest the
running opsctl refuses, such as one an older opsctl installed with
`io_weight`, stops `init` at `nginx.conf`, the first step that reads every
manifest, so nothing it or a later step generates is rewritten and no app
changes; nginx's refusal (D06) names the app and the manifest fault in
`install`'s words. On a per-app host, an installed app whose `state/` is still under `/opt/<name>/` stops `init` at the same step, before anything it or a later step generates is rewritten, with one `opsctl: <name>: /opt/<name>/state has not moved; install <name> first` line for the first such app in name order, checked before the manifests so that line wins; only `install` moves the data and rewrites the unit. An installed app with no environment file, `/etc/opt/ikigenba/<name>/env` (D08), is refused by the same check, with `opsctl: <name>: /opt/<name>/etc/env has not moved; install <name> first`: the per-app `apps` step rewrites units to name that file but reads no parameter, so it cannot write the secrets a missing file needs. Of the unmoved apps only the first in name order is reported, and one whose `state/` has not moved either is reported for its `state/`. `init` judges
a manifest's form only, never an app's `memory_max` against its slice. A
service that has only a data directory under `/var/opt/ikigenba/` (D08) is
not an app: the `apps` step writes nothing for it, leaves its data directory
alone, and creates no `/opt/<name>/` (D09). A refused `init` changes nothing
under `/var/opt/ikigenba/` either, as it changes no persistent host state
anywhere.

The `slices` step, right after `certificate`, is D09's
`SetupSlices`: it sizes the three slice units from the `MemTotal` of the
host's `/proc/meminfo` (read under the root like every host path, so a test
supplies a fake one) and writes them with nginx's drop-in. The ceilings are
fixed when the step runs; a resized host keeps the old ones until `init` runs
again, and `activate` and `install` read the units, never the host's memory. It reads no
manifest, so it runs before every step that does: a host whose installed
manifests this opsctl refuses still gets the slices that installing a fixed
release needs.

Every run also rewrites the services file (D15), `/run/ikigenba/services.json`
or a per-app host's `/var/lib/ikigenba/services.json`, right after `nginx.Apply`
succeeds, the same way `nginx apply` does. It is part of no named step and no
line reports it; the help text does not mention it. A failed rewrite stops the
sequence like any other setup failure, and a run that stops at or before nginx
leaves the file as it was.

The preflight finds `git` on PATH as it finds the other host programs. opsctl
itself never runs it; it is there for the apps, one of which serves git
repositories by running it, and every app may rely on finding it. The host's
first boot installs it; a host that lacks it is told so by the report, and the
fix is the package manager followed by `init` again.

For names, the preflight looks only at `host.name`, the space's own name. `host.apex`
(declared in D06) is handed through untouched: every run reads it from the
store beside `host.name` and passes it to `cert.Obtain` and `nginx.Apply`,
whose contracts derive the apex name and refuse a value the host name cannot
carry. The `certificate` step is the first to read it, so such a refusal
surfaces as an ordinary first-step failure after a complete preflight report,
never as a preflight finding.
