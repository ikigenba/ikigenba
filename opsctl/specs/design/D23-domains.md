# D23-domains

A custom domain is a DNS name outside the space's own names whose A record points at the host. It is a primary name, which nginx routes to the `sites` app, or a redirect name, which nginx answers with a 301 to the one primary name it belongs to. Package `internal/domain` owns the list of custom domains: its store key, the `Domain` type, the one name rule, and `List` and `Save`, which read and write the list. It imports `internal/config` and nothing of `internal/cli`, `internal/nginx`, `internal/cert` or `internal/accounts`, so nginx can read the list without a cycle. This document also declares the whole `opsctl domain` command, which `internal/cli` parses and composes from `cert` (D07), `domain`, `nginx` (D06) and `services` (D15).

The list lives in the configuration store (D03) under `host.domains`, shaped as `dns.zones` is (D04): one line of comma-separated entries, each `NAME` for a primary name or `NAME:PRIMARY` for a redirect name, with no spaces. opsctl writes it canonically, entries sorted by name, and writes an empty list by deleting the key rather than storing an empty value, so a host with no custom domains has no such key. Because the store is one file the host backup copies whole (D13), the list travels with the host backup with no change there; an older opsctl keeps the key untouched as D03 R-VHJD-YDWI requires. It is not an operator key: `domain add` and `domain remove` are its only writers, and no help text lists it. `List` validates as it reads, so a hand-edited value that names a redirect to an unlisted or redirect name, repeats a name, or holds a name outside the rule is reported rather than rendered. `List` validates the value's shape only: a hand-set entry naming the host's own name, a name under it, or the apex is not refused there or anywhere else, and only `add` keeps such names out; this is a known limitation. Likewise `config set host.apex` is not refused when the parent of `host.name` is already a listed custom domain, and the name is then both the apex and a custom domain; this is a known gap, left to the operator, who removes the domain first.

Two `domain` commands run at once may lose an update: each reads the list, and the later save wins. opsctl takes no lock for this; the commands are run by one operator at a time, and a lost entry shows in `domain list` and is added again; a removed name can also come back without its certificate, failing every nginx apply until `domain remove` is run for it again.

The name rule is a host name in lower-case ASCII: labels of letters, digits and hyphens, no label starting or ending with a hyphen, at most 253 bytes, no trailing dot, and a last label that is not all digits, so an IPv4 address is never a name. An internationalized name is given in its `xn--` form. The same rule bounds what reaches certbot's `--cert-name`, the lineage path `/etc/letsencrypt/live/<name>/` and nginx's `server_name`, and since it excludes `,` and `:` the stored value always splits back into the entries written.

A refusal, the host's state forbidding the request, reuses `*accounts.RefusedError` (D20): opsctl has one refusal type, D02 R-CS9P-PFDI maps it to exit 4 for the `group`, `user` and `domain` actions, and `cli` recognizes a refusal by that type alone. The `domain` action builds the refusal itself from the list and the host keys it read, so `internal/domain` stays free of `internal/accounts`.

`add` obtains the certificate first, through `cert.ObtainDomain` (D07), so a CA refusal changes nothing else. It then saves the list and applies nginx exactly as `opsctl nginx apply` does, `nginx.Apply` followed by `services.Write` (D06 R-EKTF-JNCW, D15). Apply is given nothing new: `nginx.Render` reads the list itself through `domain.List`, as it reads discovery and `apps.Disabled` (D06), so the store must hold the name before Apply runs, and every other writer of the nginx configuration (init, activate, rollback, enable, disable, restore) carries the custom domains without a change of its own. When Apply fails before or at `nginx -t`, D06 has put nginx's file back as it was unless that restore itself failed (D06 R-G0B8-HTXJ, R-5KKF-4QQ2), and after a failed reload the new file stays for the next apply to reconcile; either way `add` puts the list back as it was; the lineage is kept, and since certbot keeps a current lineage under `--keep-until-expiring` without asking the CA (certbot User Guide, "Renewing certificates", and its command-line reference for `--keep-until-expiring`), the same `add` run again reuses it. `remove` saves the list without the name, applies nginx the same way, and deletes the lineage last through `cert.DeleteDomain`, certbot's `delete --cert-name` (certbot User Guide, "Deleting certificates"). A failed Apply puts the list back and deletes nothing; a failed delete leaves the lineage behind with the name already out of the list and out of nginx, and a later `remove` of the now-unlisted name finds the lineage directory and runs the delete alone. The host's own names are refused whatever the list and `/etc/letsencrypt` hold, so the host's lineage is never reachable through `domain remove`. Nothing here departs from D06, D07 or D15: the composition is theirs, called as `nginx apply` calls it.

Memory is bounded by the host: the stored value is one line and the list a handful of entries, each held whole; certbot's, nginx's and systemctl's output is captured by `host.Env.Execute` as every other command's is.
