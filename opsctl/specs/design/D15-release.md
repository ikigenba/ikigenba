# D15-release

The release is opsctl's installation boundary. Hosts consume published assets;
they do not build opsctl. The installer is a separate shell entry point and
leaves platform configuration to the binary's configuration and init commands.
D02 owns the binary's version output. Open questions and external observations
are tracked outside this document in the release review and issue files.

## REQUIREMENTS

- R-IH58-0PHG: The opsctl release surface MUST consist of the tag `opsctl/<version>`, where `<version>` has the version-string shape declared in D02, and exactly three assets named `opsctl-<version>-linux-amd64`, `checksums.txt`, and `install.sh`, exposed at `https://github.com/ikigenba/ikigenba/releases/download/opsctl/<version>/<asset>`.
- R-UL9F-YPQI: Tagging an opsctl release MUST publish its release assets.
- R-PSAO-ADAF: The release's binary asset MUST be a statically linked Linux amd64 executable whose D02 version output equals the tag's `<version>`; that value is learned only by running the binary, never by reading source.
- R-IKSX-60PJ: The release's `checksums.txt` MUST contain exactly one entry for its binary asset, with that asset's SHA-256 digest represented as 64 hexadecimal digits followed by two spaces and the asset filename on one line, so the installer can select that binary unambiguously.
- R-UNP8-Q97W: The project MUST own the shell entry point `install.sh`, invoked as `bash <script-path> <version>` with exactly one version operand and diagnostic program name `opsctl-install`.
- R-UOX5-40YL: The release and installer surface MUST add no top-level opsctl command or option.
- R-UQ51-HSPA: The installer's persistent installation surface MUST be `/usr/local/bin/opsctl` for the binary and `/usr/local/share/ikigenba/opsctl-install.sh` for the saved installer.
- R-URCX-VKFZ: The installer MUST require no existing Ikigenba tool or Go compiler on a Linux amd64 host with Bash, `curl`, `install`, and `sha256sum`, effective uid 0, access to GitHub, and the requested release available.
- R-IOGM-BBXM: The version operand MUST select the release used for the binary and its checksum even when it differs from the release from which the executing installer was obtained; the installer MUST have no default version.
- R-IPOI-P3OB: A successful installation MUST place the requested binary at the binary installation path with mode `0755` and root ownership, using a rename that never exposes a partially written executable.
- R-IQWF-2VF0: Before renaming a downloaded binary into place, the installer MUST verify that its SHA-256 equals the selected release's checksum entry and that executing the candidate's `version` command succeeds with the version output declared by D02 for the requested operand.
- R-2B6J-MTG1: A successful installation MUST write exactly `install: ok (opsctl <version> -> /usr/local/bin/opsctl)` followed by LF to stdout, write nothing to stderr, and exit 0.
- R-USKU-9C6O: A successful first installation MUST leave a copy of the executing script at the saved installer path, including when the script was obtained from a different release than the operand, usable by a later `bash <saved-installer-path> <version>` invocation without first fetching a replacement installer.
- R-IUK4-86N3: A successful upgrade using the saved installer MUST replace the installed binary with the operand's release binary and leave that requested release's `install.sh` at the saved installer path.
- R-IVS0-LYDS: Every installation, upgrade, and repeated installation MUST leave the configuration store, nginx configuration, systemd units, and all contents under `/etc/ikigenba/`, `/etc/nginx/`, and `/opt/` unchanged, and MUST NOT run `config set` or `init`.
- R-0I5P-90PU: Installing the already-installed version MUST repeat the binary download and checksum verification, exit successfully with the normal success output, leave the installed binary byte-identical and the saved installer unchanged, and perform no host configuration action.
- R-UTSQ-N3XD: An installer invocation with no version operand MUST exit 2 without downloading or changing persistent host state, write nothing to stdout, and write exactly `opsctl-install: needs a version` followed by one newline to stderr.
- R-IZFP-R9LV: With a valid version operand and effective uid other than 0, the installer MUST write exactly `opsctl-install: must run as root` followed by one newline to stderr, write nothing to stdout, and exit 3 before downloading or changing host state.
- R-2CEG-0L6Q: When the requested release does not exist and fetching its checksum asset returns HTTP 404, the installer MUST exit 1, write exactly `install: failed: no release for <version>` followed by LF to stdout, and write exactly `opsctl-install: installation failed`, one empty line, and `<checksum-asset-url>: 404`, each terminated by LF, to stderr; the installed binary and saved installer MUST remain unchanged, including their absence on a fresh host.
- R-2DMC-ECXF: A downloaded binary whose checksum differs from the selected entry MUST cause exit 1, stdout containing exactly `install: failed: checksum mismatch for <binary-asset-name>` followed by LF, and stderr containing exactly `opsctl-install: installation failed`, one empty line, `expected <expected-digest>`, and `     got <actual-digest>`, each terminated by LF; the downloaded candidate MUST be removed and the previously installed binary and saved installer MUST remain unchanged.
- R-2EU8-S4O4: When the candidate binary reports a version different from the operand, the installer MUST exit 1, write exactly `install: failed: asked for <requested-version> but the binary reports <reported-version>` followed by LF to stdout, and write exactly `opsctl-install: installation failed` followed by LF to stderr; the candidate MUST never be renamed into place, and the previous binary and saved installer MUST remain unchanged.

- R-2G25-5WET: After operand and effective-user validation succeeds, the installer MUST report exactly one overall install outcome, using the specified success line on completion or `install: failed: <reason>` followed by LF on any installation failure, including download, checksum, candidate execution, or filesystem failures; reason MUST identify the failure with CR and LF replaced by literal `\r` and `\n` respectively. Failure MUST exit 1 and write `opsctl-install: installation failed` followed by LF to stderr without duplicating the failed outcome or its reason; separately specified diagnostic detail and quoted external-program output MUST follow the diagnostic convention after one blank line. Operand and root refusals MUST retain their diagnostic-only output and exit codes without an install outcome. A failure to write an outcome MUST exit 1, write the concise installation-failed diagnostic when possible, and never retry or emit a second outcome. No additional stage reports MUST be introduced.
