# D20-groups

A business group is one business on the host. Its SLUG names three things: a Linux group, a service account of the same name whose home is the folder, and the folder `/srv/<slug>` itself, a shared git repository the group's members write and no one else reads. Package `internal/accounts` owns groups and, in D21, users; this document declares the package, the account vocabulary both documents share, and the whole `opsctl group` command. `internal/cli` parses `group`, checks root and arguments, and calls the package; the package imports `internal/host` and `internal/hardening` (D19) for `hardening.ShellGroup`, and never imports `cli`.

The host's accounts are local files, so the package learns which accounts and groups exist from `/etc/passwd` and `/etc/group` under `host.Env.Root` alone rather than asking `getent` or `id`: a test writes the two files into its temporary root and the answer is exact and offline. What it reads besides, a folder under `/srv` and, in D21, `/etc/shadow` and key files, is read under the same root. Everything it changes, it changes through `host.Env.Execute` with the shadow-utils tools, `chown`, `chmod`, `setfacl` and `git`, so a test records each command, and ownership and modes a non-root test process cannot set are commands too. The one thing it writes itself is a new folder, which a test sees under its root.

The definitions are deliberately narrow. A name is taken when any account or any group has it. A business group is a group whose same-named account has the home `/srv/<name>`, so `shell`, `wheel`, `ikigenba` and `nginx` are never business groups, and naming one where a business group is wanted is the same refusal as naming nothing at all: `no group '<name>'`. A user is an account in the member list of the `shell` group, so `ec2-user` and service accounts never count as members.

A refusal is the host's state forbidding the request; it changes nothing and reaches the operator as exit 4 through `RefusedError`, which D02 maps. A tool failure is exit 1 with the tool's output quoted (D02). `group add` is the one operation that undoes: it removes the account and the group it made, and never the folder, so running `add` again adopts the folder. `group remove` has no undo; it removes the account first, because `groupdel` cannot remove an existing account's primary group, and then the group only if it is still there, since `userdel` itself removes a same-named group on a host whose `USERGROUPS_ENAB` is on. A removal that stopped between the two, `userdel` done and `groupdel` failed, leaves a leftover group: the group with no members listed, no account of its name, and its folder still at `/srv/<slug>`, owned by the group's GID as `add` set it. The shell group is never a leftover, so `remove` cannot delete the group D19 maintains, and neither is a group whose `/srv` directory belongs to some other gid. A leftover group is not a business group, so `list` and `members` never show it, but `remove` finishes the job by running `groupdel` alone; any other group that is not a business group, `wheel` or `shell`, is still `no group`.

Adopting a folder touches the folder alone: its owner, mode and default ACL are set, nothing inside it changes, and git is not initialised again when it is already a repository. When the folder's old uid and gid are free, the new account and group take them, so the files a returning business left behind are still theirs. A path at `/srv/<slug>` that is not a directory is refused, since `chown` would follow a symbolic link out of `/srv`.

The folder belongs to the service account, and git refuses a repository its user does not own unless the system configuration lists it as a `safe.directory` (git-config(1)), so `add` lists `/srv/<slug>` in `/etc/gitconfig` once; the entry stays with the folder, which `remove` keeps. Values recorded rather than opened, the account's home field and that `safe.directory` entry, are host paths whatever `Root` is; every path a command acts on is under `Root`.
