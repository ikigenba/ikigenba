# D21-users

A user is a person who signs in to the host over SSH. This document is the whole `opsctl user` command and the part of package `internal/accounts` (D20) that serves it. It builds on D20's shared vocabulary and restates none of it: the refusal type `RefusedError` (R-00ZU-A64U, R-027Q-NXVJ), the name rule `ValidName` (R-04NJ-FHCX), how the package reads `/etc/passwd` and `/etc/group` (R-UNIU-EKTL, R-0BYX-Q3T3), what a taken name is (R-0D6U-3VJS), what a business group is (R-0EEQ-HNAH), what a user is (R-0FMM-VF16), the `no group '<name>'` refusal (R-UOQQ-SCKA), and how commands run and fail (R-Y2P9-C9I9). The keys directory and the shell group are `hardening.KeysDir` and `hardening.ShellGroup` (D19).

A key is one ed25519 OpenSSH public key line, `ssh-ed25519 BODY [COMMENT]`, given as one argument. `ParseKey` accepts it only when BODY decodes to the wire form RFC 8709 section 4 defines for an ed25519 public key: the string `ssh-ed25519` followed by the 32-byte key, each as an RFC 4251 `string` (a four-byte big-endian length, then the bytes). Anything else, an RSA key, a private key, an options prefix such as `restrict`, or text that does not decode, is a usage error before anything happens. Two keys are the same key when type and BODY agree; the comment is the person's label, which sshd(8) ignores (AUTHORIZED_KEYS FILE FORMAT), so adding a key a user holds under another comment keeps the line they hold.

Each user's keys live in `/etc/ssh/authorized_keys/NAME`, one line per key, which the hardening drop-in names as the only `AuthorizedKeysFile` for members of `shell`. The file is replaced whole by renaming a temporary file over it, so sshd never reads half a file, and the new file belongs to the running process, root on a host, mode 0644, so the user cannot write it. Removing the last key leaves the file present and empty; deleting the user removes it.

`user add` runs `useradd` once with everything a user needs: `/bin/bash`, a private primary group (`--user-group`), the supplementary groups `shell` and GROUP, and a home `/home/NAME` that `useradd` creates (`--create-home`) with mode 0700 (`--key HOME_MODE=0700`, login.defs(5)). `useradd --create-home` copies a skeleton directory into the new home (useradd(8), `-k`); opsctl points `--skel` at an empty directory it makes for the call, so the home starts empty, as the story requires. A leftover `/home/NAME` does not make the name taken; only an account or group does (D20). `useradd --create-home` over an existing home warns that it already exists, copies nothing from the skeleton into it, changes neither its owner nor its contents, and still creates the account and exits 0 (useradd(8), `-m`: the home is created "if it does not exist"; shadow-utils 4.9 `useradd.c`, `create_home` and the "home directory %s already exists" warning), so `add` neither refuses it nor treats it specially. The home path is written into `/etc/passwd`, so it is the literal host path `/home/NAME`. When any step fails, `add` removes what that run made, judged by what the files show before and after, and nothing else. A home that was there before the run is not the run's to remove, and `userdel --remove` would remove it whenever its owner is the new uid (userdel(8), `-r`; shadow-utils 4.9 `userdel.c` checks only ownership), which a leftover home can be after a uid is reused; so the undo runs `userdel --remove` only when this run made the home, and plain `userdel` otherwise, leaving behind in that case any mail spool `useradd` made. shadow-utils' own `useradd` writes the account files only after the home is made (`useradd.c`, `create_home` before `close_files`), so the story's out-of-space failure (exit status 12, "can't create home directory") leaves no account; the undo still covers a failure after `useradd` succeeded.

A locked user's account has expired: `usermod --lock --expiredate 1` puts `!` before the password hash and sets the shadow account-expiration field to day 1 (usermod(8): to lock the account, not only the password, set EXPIRE_DATE to 1), and shadow(5) says an expired account may not log in. So `locked` is read from `/etc/shadow`: the expiration field holds a day on or before today. A fresh account's password already begins with `!` (shadow-utils `useradd` sets `!`), so the password field cannot tell a locked user from an active one. `loginctl terminate-user` kills every process of every session of the user (loginctl(1)), but fails when the user has no session ("is not logged in or lingering"), so lock asks `loginctl list-users` first. Lock always makes that check, even when the account is already locked, so a lock that failed between `usermod` and `loginctl` finishes when run again, while a locked user with no session sees nothing run that changes anything. Unlock reverses `usermod` with `--unlock --expiredate ""`; the empty date blanks the field (usermod(8)).

`delete` needs a locked user, so nothing of theirs runs. Every file anywhere under `/srv` the user owns goes to the service account of the top-level folder `/srv/<x>` it sits in, its group unchanged (`chown` with an owner alone keeps the group, chown(1)); a file in a top-level entry that is not a business group, or directly in `/srv`, goes to `root`, so no file is left owned by a uid a later account could be given. Then, after the key file, `userdel --remove` deletes the account, removes it from every group's member list, and removes its home (userdel(8)); it removes the private group too when `USERGROUPS_ENAB` is on (login.defs(5)), and opsctl removes that group itself when it is still there. The key file goes first, before `userdel`, so a `userdel` that removes the account but exits nonzero leaves no key file behind. Nothing is undone on failure: run again, `delete` completes, or answers `no user 'NAME'` once the account is gone.

`last_sign_in` comes from `lastlog -u NAME` (lastlog(8)), run with `LC_ALL=C` so its text is untranslated. shadow-utils' `lastlog` prints a header line and then one line ending either in `**Never logged in**` or in the time formatted by `strftime` as `%a %b %e %H:%M:%S %z %Y` (`lastlog.c`, `print_one`); the numeric offset makes the time exact, and opsctl reports it in UTC as RFC 3339.

Tests observe everything under a temporary `Root`: `/etc/passwd`, `/etc/group` and `/etc/shadow` written by the test, the key files, the `/srv` tree, and the commands `Execute` records, whose fakes may rewrite the account files as the real tool would.
