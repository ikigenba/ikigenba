# D21-users

A user is a person who signs in to the host over SSH. This document is the whole `opsctl user` command and the part of package `internal/accounts` (D20) that serves it. It builds on D20's shared vocabulary and restates none of it: the refusal type `RefusedError` (R-00ZU-A64U, R-027Q-NXVJ), the name rule `ValidName` (R-04NJ-FHCX), how the package reads `/etc/passwd` and `/etc/group` (R-UNIU-EKTL, R-0BYX-Q3T3), what a taken name is (R-0D6U-3VJS), what a business group is (R-0EEQ-HNAH), what a user is (R-0FMM-VF16), the `no group '<name>'` refusal (R-UOQQ-SCKA), and how commands run and fail (R-Y2P9-C9I9). The keys directory and the shell group are `hardening.KeysDir` and `hardening.ShellGroup` (D19).

A key is one ed25519 OpenSSH public key line, `ssh-ed25519 BODY [COMMENT]`, given as one argument. `ParseKey` accepts it only when BODY decodes to the wire form RFC 8709 section 4 defines for an ed25519 public key: the string `ssh-ed25519` followed by the 32-byte key, each as an RFC 4251 `string` (a four-byte big-endian length, then the bytes). Anything else, an RSA key, a private key, an options prefix such as `restrict`, or text that does not decode, is a usage error before anything happens. Two keys are the same key when type and BODY agree; the comment is the person's label, which sshd(8) ignores (AUTHORIZED_KEYS FILE FORMAT), so adding a key a user holds under another comment keeps the line they hold.

Each user's keys live in `/etc/ssh/authorized_keys/NAME`, one line per key, which the hardening drop-in names as the only `AuthorizedKeysFile` for members of `shell`. The file is replaced whole by renaming a temporary file over it, so sshd never reads half a file, and the new file belongs to the running process, root on a host, mode 0644, so the user cannot write it. Removing the last key leaves the file present and empty; deleting the user removes it.

`user add` runs `useradd` once with everything a user needs: `/bin/bash`, a private primary group (`--user-group`), the supplementary groups `shell` and GROUP, and a home `/home/NAME` that `useradd` creates (`--create-home`) with mode 0700 (`--key HOME_MODE=0700`, login.defs(5)). `useradd --create-home` copies a skeleton directory into the new home (useradd(8), `-k`); opsctl points `--skel` at an empty directory it makes for the call, so the home starts empty, and the only thing opsctl leaves in it is the link the timer's `enable` writes, as the story requires. A leftover `/home/NAME` does not make the name taken; only an account or group does (D20). `useradd --create-home` over an existing home warns that it already exists, copies nothing from the skeleton into it, changes neither its owner nor its contents, and still creates the account and exits 0 (useradd(8), `-m`: the home is created "if it does not exist"; shadow-utils 4.9 `useradd.c`, `create_home` and the "home directory %s already exists" warning), so `add` neither refuses it nor treats it specially. The home path is written into `/etc/passwd`, so it is the literal host path `/home/NAME`. When any step fails, `add` removes what that run made, judged by what the files show before and after, and nothing else. A home that was there before the run is not the run's to remove, and `userdel --remove` would remove it whenever its owner is the new uid (userdel(8), `-r`; shadow-utils 4.9 `userdel.c` checks only ownership), which a leftover home can be after a uid is reused; so the undo runs `userdel --remove` only when this run made the home, and plain `userdel` otherwise, leaving behind in that case any mail spool `useradd` made. shadow-utils' own `useradd` writes the account files only after the home is made (`useradd.c`, `create_home` before `close_files`), so the story's out-of-space failure (exit status 12, "can't create home directory") leaves no account; the undo still covers a failure after `useradd` succeeded.

When the host has the suite's user timer, the `/etc/systemd/user/turns.timer` that `init` and `activate` install, `add` gives the new user lingering and the timer, and `unlock` does the same. Lingering makes logind spawn a user manager for the user at boot and keep it after logouts (loginctl(1), `enable-linger`), so the timer runs without a sign-in. That manager is the system unit `user@UID.service`, keyed by the numeric uid (user@.service(5)), so opsctl reads the uid from `/etc/passwd`. logind starts the manager of a newly lingering user on its own, but asynchronously, which loginctl(1) does not say and opsctl does not rely on: it starts `user@UID.service` itself, and `systemctl start` waits until the unit's start-up has completed unless `--no-block` is given (systemctl(1), `--no-block`), so the manager is up before the next command. The timer is enabled in the user's own manager, not the system's. Plain `systemctl --user` talks to the manager of the calling user, root's here (systemctl(1), `--user`); `--machine=NAME@.host` connects to the named user's own bus on the local host (systemctl(1), `-M`: "--user --machine=lennart@.host"), a form systemd 248 added (NEWS, "CHANGES WITH 248": `sd_bus_open_user_machine()`, "exposed in the existing -M switch to systemctl") and so present in the systemd 252 this document reads elsewhere; so `enable --now` starts the timer there and creates the `[Install]` link for that user only (systemctl(1), `enable`), in their configuration directory `~/.config/systemd/user/` (systemd.unit(5), User Unit Search Path), written by their own manager and so owned by them. That link, `timers.target.wants/turns.timer` pointing at `/etc/systemd/user/turns.timer`, with the directories `.config/systemd/user/timers.target.wants/` that `enable` creates to hold it (systemd 252 `src/shared/install.c`, `create_symlink` calls `mkdir_parents_label`), is the only thing opsctl leaves in a home. Unlock runs the whole step on every user it is given, already active or not, so it restores whatever is missing and finishes a run that failed: each command succeeds again on a user who already has what it makes. The manuals do not say so; systemd 252's source does. logind's `SetUserLinger` (`src/login/logind-dbus.c`, `method_set_user_linger`) enables lingering by `touch` of `/var/lib/systemd/linger/NAME`, which succeeds on a file already there. A start job on an active unit finishes done: `unit_start` returns `-EALREADY` for an active unit (`src/core/unit.c`) and `job_run_and_invalidate` finishes a job with that answer as `JOB_DONE` (`src/core/job.c`), so `systemctl start` of a running `user@UID.service` and the start half of `enable --now` on an active timer succeed. `enable` of a unit whose link is already in place returns success without writing (`src/shared/install.c`, `create_symlink`: "already exists and points to the right place"). Were any of them to exit nonzero, it would only be a command failure, reported as such. Without the timer, on a host whose release predates turns, neither `add` nor `unlock` touches lingering or any manager.

`add` undoes lingering with the rest. When `enable-linger` succeeded in the run, the undo runs `loginctl disable-linger` and then stops `user@UID.service` before `userdel`, because userdel(8) will not remove an account that has running processes (CAVEATS; exit status 8) and logind keeps a manager around for `UserStopDelaySec`, 10 seconds by default, after nothing needs it (logind.conf(5)). `systemctl stop` waits for the stop to finish, since without `--no-block` systemctl waits for the requested operation (systemctl(1), `--no-block`: "Do not synchronously wait for the requested operation to finish"), so the manager is gone before `userdel` runs; the same holds for the stop in `delete`. Stopping a manager that is not running succeeds, which matters to an undo whose `user@UID.service` never came up and to a `delete` run again: in systemd 252 `unit_stop` returns `-EALREADY` for an inactive or failed unit (`src/core/unit.c`, lines 1986-1988), and `job_run_and_invalidate` finishes a stop job with that answer as `JOB_DONE` (`src/core/job.c`, lines 891-894 and 916-917). A timer link that `enable` wrote before the step failed goes with the home when the run made it; a home that was there before the run is kept, and such a link in it would stay. `unlock` undoes nothing: a timer step that fails leaves the user unlocked, and running `unlock` again finishes it.

`lock` and `delete` disable lingering, so a locked user's manager and timer no longer start at boot, and a deleted user leaves no lingering behind for a later account of the same name; userdel(8) says nothing of lingering. Both run `loginctl disable-linger` whether or not the timer is installed and whether or not the user lingers. loginctl(1) does not say what it does for a user who is not lingering; systemd 252's `method_set_user_linger` (`src/login/logind-dbus.c`) disables lingering by unlinking `/var/lib/systemd/linger/NAME` and ignores `ENOENT`, so it succeeds and changes nothing, which opsctl relies on, since otherwise every `lock` of such a user would fail. `lock` runs it on an already locked user too, so a lock that failed partway finishes when run again.

A locked user's account has expired. `usermod --expiredate 1 NAME` sets the shadow account-expiration field to day 1 (usermod(8), `-e`: an integer is a number of days after 1970-01-01), long past, and shadow(5) says a user whose account has expired is not allowed to log in, so sshd refuses every sign-in, a key included. The password field plays no part: an account `useradd` makes holds `!!` there, and shadow-utils will not unlock a password when that would leave the account passwordless, so lock and unlock change only the expiration field. So `locked` is read from `/etc/shadow`: the user's expiration field is nonempty. `loginctl terminate-user` kills every process of every session of the user (loginctl(1)), but fails when the user has no session ("is not logged in or lingering"), so lock asks `loginctl list-users` first. A user whose last session or manager is being torn down between the two commands can still make `terminate-user` fail; that is a command failure, and lock run again finishes. Lock always makes that check, even when the account is already locked, so a lock that failed between `usermod` and `loginctl` finishes when run again, while a locked user with no session sees nothing run but `loginctl disable-linger` and `loginctl list-users`. Unlock runs `usermod --expiredate "" NAME`; the empty date blanks the field and the account stays available with no date limit (usermod(8), `-e`).

`delete` needs a locked user, so no session of theirs runs; their manager may still, since `disable-linger` only queues the user for logind's garbage collection (systemd 252 `src/login/logind-dbus.c`, `method_set_user_linger` calls `user_add_to_gc_queue`), and a running manager would make `userdel` refuse the account (userdel(8), CAVEATS; exit status 8). Every file anywhere under `/srv` the user owns goes to the service account of the top-level folder `/srv/<x>` it sits in, its group unchanged (`chown` with an owner alone keeps the group, chown(1)); a file in a top-level entry that is not a business group, or directly in `/srv`, goes to `root`, so no file is left owned by a uid a later account could be given. Then it disables lingering and stops `user@UID.service`, the uid read from the user's `/etc/passwd` entry, and after the key file, `userdel --remove` deletes the account, removes it from every group's member list, and removes its home (userdel(8)); it removes the private group too when `USERGROUPS_ENAB` is on (login.defs(5)), and opsctl removes that group itself when it is still there. The key file goes first, before `userdel`, so a `userdel` that removes the account but exits nonzero leaves no key file behind. Nothing is undone on failure: run again, `delete` completes, or answers `no user 'NAME'` once the account is gone.

`last_sign_in` comes from the journal, because the login records a terminal session writes miss a sign-in that runs a command, git over ssh or scp. sshd logs `Accepted publickey for NAME from ...` for every sign-in it accepts, and on the host that message is in the journal under the unit `sshd.service`. opsctl asks `journalctl` for the newest such record with an anchored, case-sensitive PCRE2 pattern (journalctl(1), `-g`, `--case-sensitive`; pcre2pattern(3)) that ends in ` from `, so a name never matches a longer name that begins with it; the arguments go to `Execute` as an argv, so no shell quoting takes part, and every character of the name other than an ASCII letter, digit or `_` is escaped with a backslash, which is a no-op for a valid name's `-` and keeps a hand-made member of `shell` with an odd name from widening the match. The record's `__REALTIME_TIMESTAMP` is microseconds since the epoch as a decimal string (systemd.journal-fields(7); journalctl(1), `-o json`), reported in UTC as RFC 3339 to the second. journalctl(1) documents only that failure exits nonzero; systemd 252's `journalctl.c` answers a `--grep` that matched nothing with exit status 1, and with `--quiet` prints nothing, so that exit with empty output is the user who never signed in, and every other failure is a command failure.

Tests observe everything under a temporary `Root`: `/etc/passwd`, `/etc/group` and `/etc/shadow` written by the test, the key files, the `/srv` tree, and the commands `Execute` records, whose fakes may rewrite the account files as the real tool would.
