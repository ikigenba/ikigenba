# D09-install

Installation turns an S3 artifact and host-local configuration into a running app.
The CLI composes routing and replication between installation and app startup.
Every attempted artifact download reports its success or failure. Installation
and restart report service completion; status separately reports host facts.
App-owned persistent data survives installation. The installed trees belong to
root and the service account reaches them through its group, so the app can
run and read its configuration but cannot write `bin/`, `etc/`, or `share/` or
the files in them. What the app writes lives in its data directory (D08),
`/var/opt/ikigenba/<app>/`, which is its working directory and belongs to the
`ikigenba` account; the app creates `state/` and `cache/` there itself.

The `data` step, between `secrets` and `unpack`, makes that directory ready on
every install and brings across what an older install left under
`/opt/<app>/`. The data rules are stated once here and uninstall (D10) applies
them too: a `state/` or `cache/` only in the old place moves whole; a
`cache/` in both places is disposable, so the old one is dropped; a `state/`
in both places is two versions of the app's data, refused before anything
changes, for the operator to settle by hand. Only when something must move does
install stop the app, socket first and then service, each only if it was
running, so no request starts the old unit over half-moved data; the `unit`
step listens on the socket again and the `service` step starts the app.
`/opt/<app>/` itself is `root:root` with mode `0755`. Each entry moves by
rename; a host whose `/var` is a separate filesystem from `/opt` is not
supported by this one-time move: the rename fails, the `data` step says why,
and the entry stays whole where it was. A move that fails part way keeps
what moved and is finished by running the command again.
`init` refuses at its `nginx.conf` step while any installed app's `state/` is
still under `/opt/<app>/` (D05), since everything it generates names the data
directory. systemd.exec(5)
documents that a `WorkingDirectory=` without a `-` prefix must exist, so the
data directory is made before the unit naming it is written.

Every app runs as two units. `ikigenba-<app>.socket` holds the app's Unix
socket, `/run/ikigenba/<app>.sock`, owned by the `ikigenba` user and the
`nginx` group with mode `0660`, so nginx and the platform's own processes can
reach it and nothing else can; systemd creates `/run/ikigenba/` for it
(systemd.socket(5), `DirectoryMode=`). That owner, group, and mode are what
enforce the platform's single-unit trust model: nginx and the platform's own
processes, which all run as the one `ikigenba` user, are the only peers that
can connect, so an app may trust the identity headers it receives on its
socket. `ikigenba-<app>.service` is a `Type=notify` service handed that
socket, which it requires and follows. Both are enabled, so the app starts at
boot. An install over a running app whose data is in place restarts only the service: the socket
keeps listening, so requests wait on it and are answered by the new process.
An app disabled with `opsctl disable` (D10) stays disabled: its files and
units are replaced, but nothing is enabled or started. The drain deadline and
stop timeout come from the store (D08): `DRAIN_SECONDS` in `etc/env`,
`TimeoutStopSec=` in the service unit; `init`'s `apps` step writes changed
values into every installed app.

A manifest's `[resources]` (D08), defaults filled in, becomes lines of the
service unit: `Slice=`, `CPUWeight=`, `MemoryMax=` as a byte count,
`MemoryLow=32M` for a core app, `Environment=GOMEMLIMIT=` as a byte count,
and `Delegate=yes` and `OOMPolicy=continue` only when set; the socket unit
carries none and no unit carries `IOWeight=`. systemd.resource-control(5)
documents the resource settings and that they apply to the unit's whole
control group, systemd.service(5) documents `OOMPolicy=`, and systemd.kill(5)
documents `KillMode=control-group` as the default, so a `git` the app runs for
a client counts against the app's limits and stops with it. An app cannot
escape its ceiling by doing its work in children. A key the manifest drops
returns to its default at the next install. `init` rewrites a unit only with
the resources the installed manifest declares, so it keeps what install
wrote. Every app's `etc/env` also carries `IKIGENBA_SERVICES`, the path of the
services file (D15), whether or not the app ships an icon, and `init`'s `apps`
step adds it to an app installed before it existed.

The slices are `init`'s: `SetupSlices` writes `ikigenba.slice` (80% of the
host's `MemTotal`), `ikigenba-core.slice`, `ikigenba-apps.slice` (two thirds
of the first, with a `MemoryHigh` of fifteen sixteenths of its own), and
nginx's drop-in that puts nginx in the core slice, reloading systemd only when
a file's bytes changed and restarting nginx only when its drop-in did, since a
running service changes slice only when it starts. `install` reads the slice
units, not the host's memory, in its `file` step before anything is written: a
missing unit or a missing `MemoryMax` is the host's fault (exit 1, remedy
`opsctl init`), and a `memory_max` above the app's ceiling is the manifest's
(exit 2). A slice whose apps' `memory_max` values (with nginx's 128M for
`ikigenba.slice`) add up to more than twice its own `MemoryMax` is allowed,
and named at the end of the `unit` line. An installed copy of the incoming app
whose manifest this opsctl refuses does not block the install that replaces
it.

The `file` step parses the manifest with D08's `ParseManifest`, so every
manifest rule D08 states is an install refusal before anything is written: a
`port`, a `description` that is not one line of text, an `mcp = true` whose
`description` is empty, or a `description`, `mcp`, or `guests` of the wrong
type each fail the step as `<file>: etc/manifest.toml: <reason>` with exit 2.
`guests` itself appears on no install line; it reaches the host only through
the nginx configuration the `nginx` step regenerates (D06), so a reinstall
that changes only `guests` reports `services: ok (unchanged)` (D15).

A package that ships `share/icon.svg` puts its app in the service launcher.
The `file` step checks the icon with D08's `CheckIcon` before anything is
written; an icon entry that is not a regular file is judged not an SVG image
rather than refused as a link. After the `nginx` step the CLI rewrites the
services file and reports the change to the installed app's entry on a
`services` line (D15). Every installed app has an entry, icon or not, so a
first install reports `added`; the `ikigenba` account the unit stage needs is
D08's `EnsureAccount`, the same rule the services file uses.

Secret values come from the parameter `/<host.name>/<app>`, never from the
artifact. The nginx line names every name the app answers at: its own, the
host's when it is the default, and the root domain's apex when `host.apex`
names it. Install reads `host.apex` from the store before the workflow begins,
refuses there when the host name has no parent domain, and otherwise passes it
through to nginx; it never sets or changes it. The host name every install
surface uses (the secrets parameter, the nginx call, the report detail, and the
apex check) is `host.NormalizeName` of the stored `host.name` (D01).
