# D06-nginx

The nginx configuration is generated from the host name, the apex app, the
discovered services, and which of them systemd reports disabled. A read-only preview, a write-only regeneration, and an
apply operation share the same rendering contract. Restore uses regeneration
without testing or reloading nginx; its sequencing belongs to D14.

Two configuration keys drive the rendering. `host.name` is the space's own
name; every routed service answers at `<name>.<host.name>`, and the one whose
manifest sets `default` answers at `host.name` as well. `host.apex` names the
app that answers at the parent of `host.name`: the apex hostname is never
stored, it is derived by D01's `host.Apex`, which refuses a host name with no
parent. The apex choice is independent of the manifest default, so one app may
hold the space's name and another the apex, or one app both. When the named app
is not routed, the apex name sits on the 404 block beside the space's name and
wildcard, so it answers 404 under the host's certificate rather than falling
to the handshake-rejecting default block. A `host.apex` set on a host whose
name has no parent is refused by every operation that reads it, before
anything is rendered, written, or executed. The CLI hands the domain
operations the stored `host.name` as D01's `host.NormalizeName` spells it,
so the name in the configuration, the lineage path, and the refusal is the
same one every other command uses.

No app listens on a TCP port. Every routed app is proxied to its Unix socket,
`/run/ikigenba/<name>.sock`, held by its socket unit (D09); a service is
routed when its manifest names its app. A routed app whose socket unit
systemd reports disabled (D10's `Disabled`) keeps its block and every name it
answers at, but the block answers 503 and proxies nowhere, so a disabled app
reads as unavailable rather than missing. Rendering therefore asks systemd,
read-only, about each routed app; `show` still writes nothing. nginx gives
every request one id: `X-Request-Id` is set to `$request_id` on every proxied
request and on the authenticator subrequest, overwriting the client's, and
the same id ends each access-log line in the generated `ikigenba` format.

A routed service named `auth` is the platform's authenticator, recognized by
its routed manifest and not its name alone. Its presence rewrites every other
routed service's block into the wired shape: a request reaches the app only
after an internal subrequest to the authenticator's `/check` answers it a valid
session; the client can forge no identity, because the subrequest carries none
and the app receives only what the authenticator returned; the subrequest
tells the authenticator which request it is checking, carrying the client's
method, host, and request target as `X-Original-Method`, `X-Original-Host`,
and `X-Original-URI`, overwriting any the client sent; an absent session
becomes a redirect to the authenticator's sign-in host, while a refused one
passes through everywhere but under `/mcp`. The authenticator's own block stays unwired and answers its
public `/check` and `/check/open` with 404, whether or not any app serves
guests, so each is reachable only as a subrequest. With no routed `auth` on the host, every block is the plain proxy —
fail-open by honest absence, not a per-app choice. The authenticator is another
sub-project, reached only as an external tool through the published interface it
exposes; this design encodes only that observed grammar, never its internals.

The paths `/mcp` and `/mcp/...` are reserved across the suite for MCP, which
programs rather than browsers use to call an app's tools. Every wired block
carries, between `@auth_redirect` and `location /`, an exact `location = /mcp`
and a prefix `location ^~ /mcp/` that check and relay exactly as `location /`
does, differing only in what a 401 or 403 from the authenticator becomes: a
program cannot follow a sign-in redirect, so the named location
`@mcp_unauthorized` answers a 401 with `401`, `WWW-Authenticate: Bearer
realm="ikigenba", resource_metadata="<mcp origin>/.well-known/oauth-protected-resource"`
and one line of plain text saying to send a bearer token. An MCP client starts
signing in again only on a 401, so a refused token is answered by
`@mcp_invalid_token` with `401`, `WWW-Authenticate: Bearer
error="invalid_token", resource_metadata="<mcp origin>/.well-known/oauth-protected-resource"`
and the same line, and an expired or revoked token heals itself. The `<mcp
origin>` is always the MCP gateway's, `https://mcp.<host.name>`, whichever
app was asked and whether or not an `mcp` app is routed; the document it names
is the gateway's to serve. `/mcpx` is an ordinary path that redirects to sign
in. The locations are the
suite's, not an app's opt-in: every wired block carries them whatever its
manifest's `mcp` says, and plain, unwired, and disabled blocks carry none.
nginx documents each piece: ngx_http_auth_request_module says `auth_request`
denies with the subrequest's 401 or 403; ngx_http_core_module says
`error_page 401 = @name` (or `403`) hands the status to a named location that sets the final
status, `default_type` sets the `Content-Type` of a `return` body, and an `=`
or `^~` location wins over the `/` prefix for exactly the paths it names; and
ngx_http_headers_module says a header from `add_header` is added only to the
success and redirect codes nginx lists, hence `always`. ngx_http_auth_request_module's
own example passes `X-Original-URI $request_uri` on the subrequest; a probe of
nginx 1.26.3 confirmed that inside the subrequest `$request_method`, `$host`,
and `$request_uri` hold the client's request, not the subrequest's `GET
/check`, that a client-sent `X-Original-*` header is replaced, and that an
`=` location in an included app fragment answers without a subrequest. A probe of nginx with a stand-in
authenticator confirmed the whole exchange, including that `/mcpx` still
redirects and that nothing reaches the app on a 401 or 403. A later probe of
nginx 1.26.3 confirmed that under `/mcp` a 403 from the stand-in becomes
`@mcp_invalid_token`'s 401 carrying that one `WWW-Authenticate` header, a
`WWW-Authenticate` on the authenticator's 403 not being copied, while a 403
outside `/mcp` still reaches the client unchanged.

The paths `/api` and `/api/...` are reserved the same way, for the HTTP
interfaces apps offer to programs and to scripts on a page. Every wired block
carries, after the MCP locations, an exact `location = /api` and a prefix
`location ^~ /api/` that check against the strict `/_ikigenba/check` and relay
exactly as `location /` of the strict form does, in either form of the block,
so a request the authenticator admits, by session cookie or by token, reaches
the app with the identity it gave. Neither a program nor a page's script can
follow a sign-in redirect, so a 401 becomes the named location
`@api_unauthorized`: `401`, `WWW-Authenticate: Bearer realm="ikigenba"`, which
names no metadata since there is no sign-in flow for a program to start here,
and one line of plain text saying to sign in or send a bearer token. A 403 is
not intercepted and reaches the client unchanged, as everywhere outside
`/mcp`. `/apix` is an ordinary path, and `/api/notes.git/info/refs` is the API
location's, not the git location's, because a `^~` prefix match is taken
without consulting regular expressions. Like the MCP locations these are the
suite's, carried whatever the manifest says and absent from plain, unwired,
and disabled blocks. The reserved path says nothing about what an app serves
under it.

git's smart HTTP protocol is reserved the same way. A git client sends no
credential until it is challenged, and the only challenge it acts on is `401`
with `WWW-Authenticate: Basic`; it cannot follow a sign-in redirect. So every
wired block also carries, after the MCP locations, the regular-expression
location `~ /(info/refs|git-upload-pack|git-receive-pack)$`, matching the
three paths a clone, fetch, or push asks for (`.../info/refs?service=...`,
`.../git-upload-pack`, `.../git-receive-pack`), with the same subrequest and
identity relay as `location /`, except that a 401 becomes `@git_unauthorized`:
`401`, `WWW-Authenticate: Basic realm="ikigenba"`, and one line saying to send
the token as the password. git then asks its credential helper and retries
with `Authorization: Basic`, which the authenticator decides as it decides a
bearer token, and the app receives that header unchanged. Like the MCP
locations these are the suite's, carried whatever the manifest says and
absent from plain, unwired, and disabled blocks. ngx_http_core_module's
`location` documentation fixes the matching: a location is matched against
the normalized URI, which excludes the query string; exact `=` and `^~`
prefix matches are taken without consulting regular expressions, so `/mcp/`
and below stay the MCP locations' and `/api/` and below the API locations'; otherwise regular expressions are tried in
order of appearance and the first match wins over the `/` prefix, so a
regular-expression location an app's fragment declares, being included
earlier, is tried first. The `$` anchors the match at the end of the path, so
`/info/refsx` is an ordinary path. A probe of nginx 1.26.3 with a stand-in
authenticator and `git http-backend` behind the location confirmed that an
anonymous `git clone` is challenged and asks for credentials, that a clone
and a 300 MB push with the token as the Basic password succeed, that
`/info/refsx` and `/mcp/x/info/refs` are not the git location's, and that
auth's subrequest carries the query string in `X-Original-URI`.

An app that serves guests, visitors with no credential at all, says so with
`guests = true` in its manifest, read as D08's `Manifest.Guests`. On a host
with a routed `auth` its block is the wired block in its guests form, which
differs from the strict form in two places: a second internal location,
`/_ikigenba/check/open`, identical to `/_ikigenba/check` except that it asks
the authenticator's `/check/open`, follows it; and `location /` asks that
check instead, with no `error_page`. The authenticator's `/check/open` answers
as `/check` does, except that where `/check` would answer 401 it answers 200
with no identity, so a guest reaches the app with neither identity header, a
signed-in visitor with the identity relayed as before, and a 403 still reaches
the client unchanged. `/mcp`, `/mcp/...`, `/api`, `/api/...`, and the git location keep the strict
check and their challenges, and `@auth_redirect` stays though `location /` no
longer uses it. An apex name on the block is served the same way, being a name
on the same block. `guests` changes nothing else: with no authenticator the
app gets the plain block, a disabled app answers 503, and the authenticator's
own block is the same with or without such an app, its own `guests` ignored.
nginx documents each piece: ngx_http_auth_request_module says a 2xx answer
from the subrequest allows access and a 401 or 403 denies it with that code,
and that `auth_request_set` sets its variable from the subrequest's
`$upstream_http_*` once it completes; ngx_http_core_module says an `internal`
location answers an external request 404 and an exact `=` match ends location
search, so `/_ikigenba/check` and `/_ikigenba/check/open` are distinct and
neither is public, and `location = /check/open` on the authenticator's block
wins over its `location /`; and ngx_http_proxy_module says a header field
whose `proxy_set_header` value is an empty string is not passed to the proxied
server, so when the answer carries no identity the empty `$auth_user_id` and
`$auth_user_email` send no `X-User-Id` or `X-User-Email` upstream, and the
client's own, being redefined, never reach it.

Cross-origin access is decided at the gate, once, for every app: apps never
set CORS headers, and an app never sees a preflight. A page that `sites`
publishes is served at `https://sites.<host.name>` and its script calls other
apps from the browser with the suite's session cookie, so every block that
serves an app grants cross-origin access with credentials to that one origin,
the *allowed origin*, and to no other. It is derived from `host.name` alone,
whether or not a `sites` app is routed, and no configuration key changes it.
The file declares seven `map` blocks once, right after the log format, on every
host, a bare one included: the first yields the request's `Origin` only when
it matches the anchored, dot-escaped, case-sensitive regular expression for
the allowed origin, and the rest derive from it and from the request method
the value of each header. Every service block, plain, wired in either form,
the authenticator's, and disabled, at every name it answers at, carries seven
`add_header ... always` lines at the level of its server block and then `if
($request_method = OPTIONS) { return 204; }` before its include and its
locations, so every preflight is answered 204 by nginx with no subrequest and
nothing proxied. With the allowed origin, a response carries
`Access-Control-Allow-Origin` echoing it, never `*`, and
`Access-Control-Allow-Credentials: true`; the 204 adds the allowed methods,
request headers, and a ten-minute max age, and every other response instead
exposes `Mcp-Session-Id` and `WWW-Authenticate` to the script. Any other
origin, or none, gets no `Access-Control-` header at all, because a header
whose value is empty is not sent, and `Vary: Origin` is on every response so
no cache hands one origin's answer to another. The headers are on every
status a block gives, the app's own, the challenges, the 302 to sign in, a
403 from the authenticator, the authenticator's guarded 404, and a disabled
app's 503, so a page's script can read a refusal rather than see an opaque
network error. The four named challenge locations set their own
`WWW-Authenticate`, so they inherit none of the block's headers and repeat
the four a non-preflight response carries. The port-80 redirect, the
handshake-rejecting default, and the 404 block carry none of it.

nginx documents most of this. ngx_http_headers_module
(https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header) says
`add_header` adds a header only on the success and redirect codes it lists
unless `always` is given, and that `add_header` directives are inherited from
the previous level if and only if none is defined on the current level.
ngx_http_map_module (https://nginx.org/en/docs/http/ngx_http_map_module.html)
says a value starting with `~` is a case-sensitive regular expression and that
an exact string variant is chosen before any regular expression, which is how
`"OPTIONS true"` wins over `"~ true$"`. ngx_http_rewrite_module
(https://nginx.org/en/docs/http/ngx_http_rewrite_module.html) says its
directives at server level run before a location is searched for, and
`return` stops processing, so the preflight `if` answers before any location,
the app fragment's included. A probe of nginx 1.26.3 with a stand-in
authenticator and app confirmed what the documentation leaves unsaid: an
`add_header` whose value is empty sends no header; a preflight with the
allowed origin gets the 204 with exactly the six headers the stories show,
reaches neither the authenticator nor the app, and is logged with status 204;
the headers ride the app's 200, the 302, the 403, the guarded 404, the 503,
and each named location's 401; `https://elsewhere.example`, the allowed
origin with a suffix, over `http`, in upper case, with a trailing `/`, or
with any prefix gets only `Vary: Origin`; `/api` and `/api/x` without a
credential get `@api_unauthorized`'s 401 and body, a refused token 403, an
admitted one the app, and `/apix` the 302. The same probe showed a location an
app's fragment declares with an `add_header` of its own carrying none of the
block's headers, and an app's own `Access-Control-Allow-Origin` reaching the
client beside the block's; the gate owns these headers, and an app that sets
them breaks the grant for its own responses.

nginx passes a request's headers upstream, `Origin` among them, and an app
refuses a call whose `Origin` names a host other than its own: appkit's MCP
server answers it 403. So the gate also decides what `Origin` an app sees.
The seventh map yields the empty string when `$ikigenba_cors_origin` holds the
allowed origin and the request's `Origin` otherwise, and every location that
proxies in the plain block and in a wired block of either form, the app's
locations and the authenticator subrequest locations alike, sets `Origin`
from it: the allowed origin's `Origin` is left out, so the app takes a page's
call as it takes one from its own pages, while any other `Origin`, or none,
reaches the app as it came, so the app's own guard still refuses a foreign
one. The authenticator's own block passes every `Origin` on unchanged, because
the authenticator checks it to let any app on the space, `sites` included,
sign its user out. Every such location sets `proxy_set_header` already, so
it inherits none from its server block (ngx_http_proxy_module: the directives
are inherited from the previous level if and only if none is defined on the
current level), and each carries the line itself; a location an app's
fragment declares is the app's, as with the headers above. A probe of nginx
1.26.3 with a stand-in upstream confirmed it: the allowed origin reached the
upstream as no `Origin` header at all, and `https://elsewhere.example`, the
allowed origin over `http`, in upper case, with a trailing `/`, or with one
character changed reached it unchanged, as did no `Origin`, which stayed
absent; two `Origin` headers reach it joined into one value, which no app
takes for its own host.

An app's own `etc/nginx.conf*` is included at the level of its server block,
and nginx inherits a directive set there into every location of the block
that does not set it itself. The generated configuration therefore sets none
of the body-size, body-timeout, proxy-timeout, or buffering directives, so an
app that takes large, slow uploads (git pushes, say) widens nginx's 1 MiB body
limit, 60-second read timeout, and request buffering for its own block alone
with `client_max_body_size 0;`, `proxy_read_timeout 3600s;`, and
`proxy_request_buffering off;` in its fragment, and no key or manifest field
does it. The same probe confirmed it: with the fragment a 300 MB push streamed
through the git location; without it a 3 MB push was refused 413. The
authenticator subrequest never carries a body, so the fragment does not reach
`/check`.

Apply brings nginx to the generated configuration with
`systemctl reload-or-restart nginx`, which systemctl(1) documents as reloading a
unit that supports reload, and starting one that is not running. nginx's unit
declares `ExecReload`, so a running nginx is reloaded and keeps its connections,
while a host whose first boot enabled nginx without starting it comes up here
rather than failing init. `Update` is the conditional form `disable` and `enable` use: it publishes,
tests and reloads only when the rendered bytes differ from the file in place,
and reports whether it did, so an idempotent disable or enable reloads
nothing.

Every command that regenerates this configuration also rewrites the services
file (D15), and only once nginx's configuration has succeeded, so the two never
disagree about which apps are disabled. That is `internal/cli`'s composition,
not this package's: `Apply`, `Update`, and `Write` stay nginx-only. `nginx
apply` rewrites the file silently; a run that fails at nginx, `nginx -t`
included, leaves it as it was, and a failure of the rewrite itself fails the
command the way an nginx failure does, with nginx left applied.

Discovery is D08's: a service is any `/opt/<name>/` holding `etc/` or any
`/var/opt/ikigenba/<name>/` holding `state/`, but only
`/opt/<name>/etc/manifest.toml` routes it, so a service known only by its data
directory, such as the `state/` an uninstall leaves behind, gets no block and
is never the authenticator.

Application manifests belong to D08; the host
execution seam and the apex derivation belong to D01, and init sequencing
belongs to D05.
