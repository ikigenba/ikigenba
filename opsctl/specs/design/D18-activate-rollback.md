# D18-activate-rollback

`opsctl activate <sha> [label]` makes the release unpacked at
`/opt/ikigenba/releases/<sha>/` (D16) the one the host runs, and
`opsctl rollback` goes back to the one `previous` names. Both are commands
composed in `internal/cli` from operations other designs own: the release
layout (D16), the app model and discovery (D08), the release apps' files
(D17), nginx regeneration (D06), the services file (D15), Litestream
regeneration and snapshots (D11, D12), `Disabled` (D10), and, for rollback's
hand-off to previous's opsctl, D01's `Deps.Exec` seam. Neither declares an
exported Go name of its own; their contract is the command line, its output,
and what they leave on the host.

Only the opsctl a release carries knows how to put that release in place, so
`activate` refuses to be run by any other, and `rollback` is always run by the
opsctl inside `previous`: any other replaces itself with it by exec,
so its output reaches the caller as it is written and its exit code is the
caller's. Every activate checks before it changes anything outside the release
folder: the release tree, the host's layout, every manifest, every app's
secrets, and the slices' room. Then it writes, switches the links, reloads,
regenerates, and restarts every app one at a time, core apps first, each
`active` before the next is touched. The first failure stops the run and
nothing is undone; a run that fails leaves `previous` in place, so a rollback
or a second activate can still go either way. Only a run that succeeds removes
the releases neither link names.

What a host runs is judged once, at invocation: which apps it runs (D08's
`Discover`, so per-app installs on a per-app host and current's apps on a
released host), and which of them are disabled. A disabled app stays disabled:
its files are rewritten and nothing enables or starts it. An app the host runs
that the release lacks is stopped and disabled and its units and environment
directory removed; its data directory is kept, so it becomes a data-only
service.

The first activate on a per-app host is the cutover. Its data and environment
files are already where a release expects them, so nothing moves; every service
is snapshotted as `opsctl snapshot` does before anything goes, then each
`/opt/<app>/` that install made is removed with the per-app services file, and
the units step replaces or removes the per-app units. `/opt/` entries that are
not installed apps, such as an `/opt/aws/` a host image ships, are left alone.

The rolling restart restarts a running service and starts an inactive one,
never the socket, so requests wait on the socket and are answered by the new
process. Readiness is install's: the service is `Type=notify`, so systemd
finishes the start job only when the app reports ready (systemd.service(5)),
and the step then asks systemd for the service's state.
