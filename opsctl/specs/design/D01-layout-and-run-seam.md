# D01-layout-and-run-seam

The CLI composes small domain packages. Host execution, time, DNS, cloud
access, and the path of opsctl's own executable have injected boundaries so callers can exercise commands against a
temporary host tree without changing the machine running the tests. The
executable's path is how an opsctl finds the release it belongs to (D16): a
test hands it a path inside its temporary release folder.

The production cloud adapter is `internal/cloud/aws`. It uses the approved AWS
SDK v2 S3 and SSM modules behind the same injected boundary used by tests; no
gate contacts AWS. The bucket a host backs up to is named after the root
domain (`ikigenba.dev`), and a bucket name with dots in it cannot be addressed
as a hostname over TLS, so the adapter's S3 client always addresses the bucket
path-style, and it leaves the SDK's own endpoint configuration in force so a
gate test can point the client at a fake endpoint and watch the request shape.

`internal/host.Exec` captures a process's standard output whole by default, which suits the short outputs most commands read. A caller that pipes a large stream through a process, as the host backup does through `zstd`, names a writer in the command instead: Exec then hands each byte of standard output to that writer as the process produces it and keeps none of it, while standard error is still captured for the diagnostic. Exec returns only once the process has exited and its output has all been delivered, and a writer that refuses a write makes the run an error whatever the process's exit status, since output the caller did not receive cannot be a completed run.

The adapter's `PutObject` takes a body of any length, including one whose length nobody knows until it ends, and holds at most one part of it in memory. It reads the body in order: a body that ends within the first `PartSize` bytes (16 MiB) goes up as one conditional S3 `PutObject` of exactly those bytes; a longer one goes up as one S3 multipart upload of consecutive `PartSize` parts, the last the remainder, each part checksummed with CRC32 as the SDK's own upload manager does and the upload completed with every part's checksum and the same `If-None-Match: *` condition, so either way the object appears whole or not at all and never overwrites an existing one. The SDK wants each request's length and a body it can rewind, to retry the request and, over plain HTTP as in the gate tests, to checksum it; a stream has neither and a held part has both. The amount held is the reason for the part size: S3 requires every part but the last to be at least 5 MiB and allows at most 10,000 parts, so 16 MiB parts reach about 156 GiB while keeping the memory bound small; a body longer than that fails when S3 refuses the next part. Any failure before the upload completes, a body that ends in an error included, publishes nothing: the adapter stops sending parts, asks S3 to abort the upload so its parts are freed, and returns the failure that stopped it. The abort runs on a context the caller's cancellation does not reach, bounded by `AbortTimeout` so a stalled S3 cannot hold the failed run open, and its own failure is not reported in place of the cause; a host whose role may not abort uploads leaves incomplete parts behind, which S3 keeps until they are aborted or a lifecycle rule removes them, and the backup still fails for the reason it failed.

`internal/host` also holds the one derivation every apex-aware command shares:
`Apex` turns the host's own name into the parent domain it may answer at
(`ikigenba.dev` for `sbx.ikigenba.dev`) or refuses a name too short to have
one. It is a pure function of the host's name, which is a host fact. Beside
it sits `NormalizeName`, the one
spelling rule for a stored `host.name` (lowercase, one trailing dot dropped),
so every reader of the store hands the same bytes to `Apex`, to paths, and to
output.
