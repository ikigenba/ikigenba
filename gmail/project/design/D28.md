# Decision 28 — `GMAIL_REFRESH_TOKEN` adopts the rotating-credential channel (channel 5, `state/`)

**Problem.** `GMAIL_REFRESH_TOKEN` is classified as channel-2 customer data
(D24), seeded to the app-config parameter and exported read-only into the
service's environment at launch. But it is an OAuth **refresh token**: a
single-holder credential the provider may rotate and revoke, so two deployments
cannot hold the same one, and a value the service rotates cannot live in a
seed-once, read-only parameter. The suite contract for exactly this class is
`root project/design/D32.md` (channel 5): a per-environment credential the
service owns and rotates in its `state/`.

**Decision.** gmail adopts channel 5 for its refresh token; the two static OAuth
credentials are unchanged.

1. **Reclassification.** `gmail/etc/env.list` declares `rotating
   GMAIL_REFRESH_TOKEN` (no longer `secret`), so `bin/push-secrets` never pushes
   it to SSM (`root project/design/D32.md`; `bin/push-secrets` pushes `secret`
   lines only). `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET` stay channel 2
   (`secret` lines), identical across environments and read from the
   environment as today.

2. **The client reads the token from `state/`.** At the composition root
   (`cmd/gmail/main.go`) the refresh token is read from the file
   `${IKIGENBA_ROOT}/gmail/state/GMAIL_REFRESH_TOKEN`, composed from the
   box-global `IKIGENBA_ROOT` exactly as the SQLite path is
   (`root project/design/D05.md`, `root project/design/D11.md`), **not** from the
   environment. A missing file is a **loud boot failure** naming the credential,
   mirroring the launcher's hard-fail on a missing parameter — a never-seeded
   gmail must not start silently.

3. **Rotation persists back to `state/`.** The OAuth token source wraps the
   refresh so that when the provider returns a new refresh token it is written
   back to the same `state/` file atomically (temp file in the same dir, then
   rename, mode `0600`), so the next boot reads the rotated value. The service is
   the only steady-state writer of that file.

4. **`consent` seeds the local `state/` file.** `cmd/consent` writes the
   freshly-consented refresh token to the composed **local** `state/` path
   (`${IKIGENBA_ROOT}/gmail/state/GMAIL_REFRESH_TOKEN`, `0600`), **retiring the
   old `~/.secrets/GMAIL_REFRESH_TOKEN` writer** — the same place, and the same
   shape, the deployed service reads from, so dev matches prod. Each production
   box is seeded independently and once with its own consented token via
   `opsctl seed-state gmail GMAIL_REFRESH_TOKEN` (`root project/design/D32.md`,
   opsctl D19), so no two environments ever share a token.

The channel classifications this changes are corrected in place: D24 (§2), D25
(live credentials), D19 (live-check credentials), and CONVENTIONS all now state
that the refresh token is channel 5 held in `state/`, the client-id/secret pair
channel 2 from the environment.

**Rejected.**
- *Keeping `GMAIL_REFRESH_TOKEN` in channel 2 (the app-config parameter).* It
  would be seeded once from a single shared value and exported read-only, so
  every environment would boot from the same token — the first rotation revoking
  the others — and a rotation the service performs could never be written back
  (`root project/design/D32.md`). Rejected — channel 5.
- *Keeping `consent`'s `~/.secrets/GMAIL_REFRESH_TOKEN` writer.* `~/.secrets` is
  a retired dev mechanism nothing reads any longer, and it does not match how the
  token is delivered in prod (a `state/` file). Consent must write the same
  `state/` file the service reads, so dev and prod share one shape. Rejected.
- *Reading the refresh token from the environment and merely persisting rotations
  to `state/`.* Two sources of truth for one value; the first boot would take the
  env seed and a later boot the `state/` copy, diverging silently. Rejected —
  `state/` is the single source of truth after bootstrap.

**Verification.** The read-at-boot and persist-on-rotation behaviors are the
umbrella contract's per-service ids, adopted here (citation is adoption); the
consent writer is a gmail-local behavior with its own id.

- R-ENXH-KJ01 (owned by `root project/design/D32.md`, `[proof: per-service]`) —
  gmail reads its refresh token from `${IKIGENBA_ROOT}/gmail/state/GMAIL_REFRESH_TOKEN`
  at boot and **fails loudly, naming the credential, when the file is absent**,
  rather than starting without it. Substrate: hermetic test over a temp-dir
  `IKIGENBA_ROOT` (present file → resolved value; absent file → loud error).
- R-EP5D-YAQQ (owned by `root project/design/D32.md`, `[proof: per-service]`) —
  when the OAuth token source yields a rotated refresh token, gmail writes it
  back to the same `state/` file, so a re-read returns the rotated value.
  Substrate: hermetic test driving the token source with a fake that returns a
  new refresh token, asserting the file's new bytes (round-trip: seed, rotate,
  re-read).
- R-S3ZK-NBWM — `cmd/consent` writes the consented refresh token to the composed
  `${IKIGENBA_ROOT}/gmail/state/GMAIL_REFRESH_TOKEN` path as a `0600` file
  (**not** under `~/.secrets`). Substrate: hermetic test over a temp-dir
  `IKIGENBA_ROOT`, asserting the file location, mode, and bytes.
