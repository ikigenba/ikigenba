# Decision 23 — The poll cycle is a chain root: one correlation id per cycle, threaded into every append and every outbound call

**Problem.** gmail's poll daemon is **self-originated work**. Nothing calls it;
a ticker fires, the engine asks Google what changed, derives `mail.*` events,
and appends them to the outbox inside one transaction. There is no inbound
request whose correlation id it could inherit, so without a deliberate decision
every event gmail publishes carries an empty `correlation_id` and every Gmail
API call the cycle makes is uncorrelated. The chain would then begin at the
*reaction* — a consumer minting a root when it receives an uncorrelated event —
which loses the fact that one poll cycle caused all of them. The eventplane
library deliberately **never mints at `Append`**: an empty correlation id there
is a recorded gap, not a license to mint mid-chain.

**Decision.** A gmail poll cycle **opens a chain**. At the top of each cycle the
engine starts a root — mints one correlation id, installs it on the cycle's
context, and emits a `root` record — and threads that context through
everything the cycle does: the Gmail API calls and the event appends alike. One
cycle is one chain, so a forensic agent can ask "what did the 09:41 poll cause"
and get the Google calls, the events, and every consumer's reaction to them.

**One id per cycle, not per event.** All events derived from a single poll share
the chain; a cycle that derives nine events emits one root record and nine
`publish` hops on one id.

**The two cycle entry points.** `Engine.Poll(ctx)` is the steady-state cycle.
`Engine.bootstrap(ctx)` is the once-at-boot seed, which likewise makes outbound
Google calls with no caller to inherit from. Each starts its own root.

Consumed from appkit's design (see `project/research/research.md` — gmail
designs no minting of its own; the suite contract puts this idiom in one place
precisely so eight services do not hand-roll it):

```go
// appkit/telemetry — mint + install in ctx + emit the `root` record.
// Safe on a nil Recorder: still mints and installs, records nothing.
func StartRoot(ctx context.Context, rec *Recorder, op string) context.Context
```

The engine gains the recorder at the composition root, beside the other
runtime wiring, and starts the root at each cycle head:

```go
// cmd/gmail/main.go, in Handlers — the recorder joins the existing options.
engine = gm.NewEngine(gm.EngineOptions{
    DB: conn, Store: gm.NewStore(), Client: client,
    Logger: rt.Logger(), Interval: interval,
    Recorder: rt.Recorder(),      // nil when telemetry is disabled
})

// internal/gmail/sync.go
func (e *Engine) Poll(ctx context.Context) error {
    ctx = telemetry.StartRoot(ctx, e.rec, "poll:gmail")
    …                              // every Gmail call and the commit tx use this ctx
}
```

**The producer seam carries the context.** `EventSink` and its outbox
implementation take a leading `context.Context` so the cycle's id reaches
eventplane's revised `Append`, which is the only path that populates the
`correlation_id` column and wire field:

```go
type EventSink interface {
    // AppendMailEvent appends one mail event on the caller's tx, atomic with the
    // cursor advance. ctx carries the cycle's root correlation id.
    AppendMailEvent(ctx context.Context, tx *sql.Tx, ev MailEvent) error
    Ring()
}

func (o *outboxProducer) AppendMailEvent(ctx context.Context, tx *sql.Tx, ev MailEvent) error {
    e, err := buildPayload(ev)
    if err != nil {
        return err
    }
    return o.ob.Append(ctx, tx, e)   // eventplane's revised signature
}
```

`Engine.commit` already holds the cycle context and passes it to `BeginTx`; it
forwards the same context to each `AppendMailEvent`. The change is
**compile-caught** — the build cannot succeed while an old-signature call site
survives. `buildPayload`, the kinds and subjects (D18), and the post-commit
`Ring()` are untouched.

**The outbound calls inherit it for free.** Because the cycle's context is the
one already threaded into every `http.NewRequestWithContext` the client builds,
the instrumented transport (D21) reads the id off the request context and
records the Gmail calls on the same chain. Nothing extra is wired. The id is
still **not** sent to Google — the transport propagates the header only to
loopback IP literals.

**The outbox migration.** `correlation_id` becomes a first-class outbox column.
gmail appends **one new timestamped migration** (via `bin/create-migration`)
whose body is exactly eventplane's exported `outbox.AddCorrelationIDSQL`
(`ALTER TABLE outbox ADD COLUMN correlation_id TEXT NOT NULL DEFAULT '';`).
`ADD COLUMN` rewrites no rows and leaves `seq` and the `sqlite_sequence`
high-water mark untouched, so no consumer cursor moves. **Consequence for the
existing drift guard:** D18's `R-X9ED-THOL` asserted that the newest outbox
migration contains `outbox.SchemaSQL` verbatim. That identity no longer holds
once the newest migration is an `ALTER`, so D18's Verification for that id is
rewritten in place to assert the stronger, migration-count-independent property
— that the migrated table's column set matches the library schema's.

**Judgment calls recorded.** (a) The root starts at the **cycle** head rather
than per derived event, per the suite rule, so one cycle is one chain; a
per-event root would produce nine unrelated chains from one poll and destroy
the grouping the record exists to provide. (b) `bootstrap` gets its own root
rather than sharing the first `Poll`'s — it is a distinct unit of work that can
fail on its own, and conflating them would attribute the seed's Google calls to
a cycle that had not started. (c) The `op` string is `poll:gmail`, following the
brief's `<origin>:<name>` shape for root ops (`cron:tick/<name>`, `run:<run-id>`);
it is the string a forensic agent greps to find poll-originated chains, and the
convention is appkit's to standardize.

**Rejected.**
- **Minting nothing and letting consumers open the chain** — the settled suite
  rule now names background poll/watch/sync cycles as roots precisely because
  this loses the ability to tie several consumers' reactions back to the one
  cycle that caused them.
- **Letting eventplane mint when the append context carries no id** — the
  library cannot distinguish "this is a root" from "someone forgot to thread
  the context", so it would paper over the second case forever. eventplane
  records the gap instead; that is the correct division.
- **Storing a correlation id on `MailEvent` and passing it as a field** — the
  id is ambient cycle scope, and a payload field is exactly the convention
  `docs/correlation-ids.md` supersedes; `outbox.Event` deliberately has no such
  field.
- **Passing `context.Background()` at `outboxProducer`** — compiles, silently
  discards the chain, and is invisible in review.
- **Hand-rolling the mint (`correlation.New` + a hand-built `root` record) in
  gmail** — the brief puts the idiom in one appkit helper so the record's `op`,
  kind, and nil-recorder behavior are identical across the eight services that
  need it.
- **Recreating the outbox table to add `correlation_id` in column order** — an
  additive `ALTER` preserves `sqlite_sequence`; a recreate would restart rowids
  and strand every cursored consumer.

**Verification.** (In-process against a real SQLite database and a recording
fake `EventSink`, plus an injected stub `RoundTripper` — the same substrates
`sync_test.go` and `client_test.go` already use. The `root` **record's** shape
and the `publish` record's `correlation_id` are appkit's and eventplane's
promises, proven by their ids; what gmail must prove is that its cycle mints
once and threads the result everywhere.)
- R-PJWQ-547Q — during one `Engine.Poll` that derives **three** events, all
  three `AppendMailEvent` calls receive a context carrying the **same**
  correlation id, and that id satisfies `correlation.Valid` (26 characters,
  Crockford alphabet). A build that threads the bare worker context yields an
  empty id and fails; a build that starts a root per event yields three
  different ids and fails.
- R-PL4M-IVYF — two successive `Engine.Poll` cycles on the same engine yield
  **different** correlation ids on their appends — the discriminating property
  against a build that mints once per process (or once per engine) and reuses
  it for the life of the daemon.
- R-PMCI-WNP4 — the Gmail API requests issued during a cycle carry that same
  cycle id on their **request context**: a stub `RoundTripper` reading
  `correlation.FromContext(req.Context())` observes the id the cycle's appends
  used. A build that starts the root only around the commit, leaving the
  outbound calls uncorrelated, fails this.
