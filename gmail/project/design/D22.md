# Decision 22 — nginx fragment: forward the edge-minted `X-Correlation-Id` on gated locations, blank it on ungated ones

**Decision.** `gmail/etc/nginx.conf` gains one more forwarded header,
`X-Correlation-Id`, under the same identity-hygiene rule D4 established for the
four owner headers: on every **gated** location the value comes from the
dashboard's `auth_request` subrequest and **overwrites** anything the client
sent; on every **ungated public** location the header is explicitly set to the
empty string so the service mints its own.

The suite's correlation id is a bare 26-character Crockford base32 ULID carried
in `X-Correlation-Id` (see `project/research/research.md`). The dashboard's
introspection endpoints mint it per gated request and return it as a response
header on the auth subrequest; nginx is the only place that value can be
captured, so each service fragment must do so for itself. gmail is not the
minter and never validates the value — it forwards what the edge resolved.

## The gated locations

Each gated location captures the subrequest header into a **service-prefixed**
variable (the fragment's existing `$gmail_…` convention, so names stay unique
when every service fragment is included into the one apex `server` block) and
forwards it:

```
# Bearer-gated prefix — every path under the mount except the exact matches.
location /srv/gmail/ {
    auth_request /_authn;
    …                                                     # D4 owner headers, unchanged
    auth_request_set $gmail_correlation $upstream_http_x_correlation_id;
    proxy_set_header X-Correlation-Id $gmail_correlation;
    …
}

# Session-gated landing page (exact match) and its static asset tier.
location = /srv/gmail/ {
    auth_request /_session-authn;
    …                                                     # D4 owner headers, unchanged
    auth_request_set $gmail_session_correlation $upstream_http_x_correlation_id;
    proxy_set_header X-Correlation-Id $gmail_session_correlation;
    …
}

location /srv/gmail/static/ {
    auth_request /_session-authn;
    auth_request_set $gmail_session_correlation $upstream_http_x_correlation_id;
    proxy_set_header X-Correlation-Id $gmail_session_correlation;
    …
}
```

`$gmail_session_correlation` is declared by `auth_request_set` in both
session-gated locations. That is legal and unambiguous: exactly one location
handles a given request, so the variable is set at most once per request.

**Why this is safe against a smuggled id.** Identical to D4's owner-header
argument: nginx does not pass an inbound client header through as a proxy
header unless a `proxy_set_header` names it, and the last `proxy_set_header`
for a name wins. A single set from the subrequest variable therefore
**replaces** any client-supplied `X-Correlation-Id` on the upstream request. A
public caller cannot inject an id into the chain.

## The ungated public location

The PRM bootstrap is deliberately unauthenticated — there is no auth subrequest
and therefore no minted id to capture. It sets the header to the empty string
so nothing a client sent survives, and the gmail process mints its own id for
that request:

```
location = /srv/gmail/.well-known/oauth-protected-resource {
    proxy_pass http://127.0.0.1:3202/.well-known/oauth-protected-resource;
    proxy_set_header X-Correlation-Id "";
    …
}
```

**Locations that proxy nothing are untouched.** `location = /srv/gmail/feed`
and `location = /srv/gmail/attachment` are bare `return 404;` stubs and
`@gmail_authn_500` re-emits a status — none of them reaches an upstream, so
none of them carries a `proxy_set_header`. Direct loopback consumers of
`/feed` and `/attachment` reach the service without passing nginx at all and
supply their own correlation id on the wire.

**No Go change.** Reading the header (trust it when present, mint when absent)
is the appkit chassis's middleware, not gmail's code; this Decision covers the
shipped `etc/nginx.conf` artifact only.

**Rejected.**
- **Letting the client's `X-Correlation-Id` pass through on gated locations** —
  a public caller could then join or forge another actor's chain. The edge
  strips and the edge mints; that is the whole trust argument.
- **Omitting the header on ungated locations instead of setting it empty** —
  omitting is *not* stripping: nginx would forward nothing here either, but the
  explicit `""` states the intent in the artifact and survives a future edit
  that adds header pass-through. It also makes the rule greppable.
- **Capturing the id in the `= /srv/gmail/feed` and `= /srv/gmail/attachment`
  stubs** — they return 404 without proxying; there is no upstream request to
  set a header on.
- **One shared `include` for the correlation lines across all service
  fragments** — nginx `include` cannot parameterize the per-location variable
  name, and the fragment ships verbatim with no templating (D4). Explicit
  per-location directives are the only form that loads directly.
- **Minting the id in gmail's fragment (e.g. from `$request_id`)** — nginx's
  `$request_id` is a hex UUID, not the suite's Crockford ULID, and a
  per-service minter would break the one-id-per-causal-chain rule. The
  dashboard mints; services forward.

**Verification.** Proven the way every other line of this fragment already is:
by the content-assertion test that reads `gmail/etc/nginx.conf` from disk
(`cmd/gmail/nginx_test.go`) and asserts over the shipped artifact, running
under the normal `go test ./...`. nginx itself is not run by the suite. The
*recording* these headers feed is the chassis's promise, proven by appkit's
ids and not re-asserted here; what gmail owns is that the shipped config
forwards and strips the right values in the right places.
- R-1M1T-299W — the **bearer-gated prefix** `location /srv/gmail/` (the
  `auth_request /_authn` tier) carries both
  `auth_request_set $gmail_correlation $upstream_http_x_correlation_id;` and
  `proxy_set_header X-Correlation-Id $gmail_correlation;` — the capture alone,
  with no matching `proxy_set_header`, fails, since a captured variable that is
  never forwarded reaches the service as nothing.
- R-1N9P-G10L — **both** session-gated locations — the exact-match
  `location = /srv/gmail/` and `location /srv/gmail/static/` — carry
  `auth_request_set $gmail_session_correlation $upstream_http_x_correlation_id;`
  and `proxy_set_header X-Correlation-Id $gmail_session_correlation;`. Exactly
  two locations do so; a build that converts only the landing page and leaves
  the static tier unforwarded fails.
- R-1OHL-TSRA — the **ungated** PRM bootstrap
  (`location = /srv/gmail/.well-known/oauth-protected-resource`) carries
  `proxy_set_header X-Correlation-Id "";` — blanking, not forwarding — and the
  fragment contains **no** `auth_request_set` for a correlation variable inside
  it. Across the whole file exactly **four** `proxy_set_header X-Correlation-Id`
  directives appear (bearer, the two session tiers, and this empty one), so a
  stray fifth — notably one added to the `= /srv/gmail/feed` or
  `= /srv/gmail/attachment` 404 stubs, which proxy nothing — fails the check.
