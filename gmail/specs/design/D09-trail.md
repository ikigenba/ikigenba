# D09-trail

The trail: `internal/trail`, the five events gmail emits on the suite's event bus and records in its own trail, their declarations, the identity each carries; the closed set of event names gmail records; and decisions 16 and 8's secrecy, stated once for the whole app with decision 15 as root ruling A2 reads it. It is gdrive's trail with mail's references on the transfer events and a second family of events for drafts.

`gmail.called`, the record of every request to Gmail, is `D05-gmail`'s to emit: the Gmail client is the only thing that sees each request, its status and its timing. This document states only what the assembled run shows of it: one `gmail.called` per request Gmail is sent, with the attributes `endpoint`, `status` and `duration_us`, as the caller the request was made for. `sibling.called` is appkit's clients'; the request pair is appkit's `telemetry.Middleware`'s (`D03-serve` mounts it on every request); `tool.called` is appkit's MCP server's; `service.started` and `service.stopping` are `D03-serve`'s. When the engine tells each transfer event is `D06-transfers`'; when the drafts service tells each draft event is `D07-drafts`'.

## The transfer events

A transfer's life is told by `transfer.started`, when its work begins, and `transfer.finished`, when it ends however it ends, as in gdrive; a transfer that never ran has a `transfer.finished` and no `transfer.started`. Both carry, in this order, `transfer` (the id), `direction`, `message` (the Gmail message id: a pull's source, a push's draft message, the new one once a push is done), `attachment` (the part id, empty for a whole message and for a push), `draft` (the `drf_` id, empty for a pull) and `path`; `transfer.finished` adds `status`, `reason` (empty when `done`) and `bytes`, an integer. Each is told as the transfer's caller, the user id, email and request id the record keeps, whatever context tells it, so a transfer's trail is whole under the request id of the `pull` or `push` that recorded it, even when the queue, the drain or the next start tells it. The bus event carries the cause of the context it is told under.

## The draft events

`draft.created`, `draft.sent` and `draft.discarded` carry, in this order, `draft` (the `drf_` id), `message` (the draft's message id, the sent message's once sent), `thread`, and `attachments`, the count of the draft's attachments, an integer (root ruling A7). They are told as the caller on the context: the caller of the tool call that made the change. That is `compose` for `draft.created`, `send` or `discard` for an explicit send or discard, and for a draft a person sent or deleted in Gmail, whichever tool's reconciliation learned it (`draft`, `push`, `send` or `discard`, root ruling A5), as root ruling A7 settles.

## Both ways, after the write

Every event goes two ways at once under the same name, attributes, request id and user: recorded in the trail through the run's writer and emitted on the bus through the run's emitter (decision 13). It is told after the change it reports is committed and never for a change that did not happen: a refused call tells none, and a write the store refused tells none. The order of telling and committing is not observable at a sink, since both sinks are fed from queues; the contract therefore states it as what is observable: an event's attributes are the record's as the store then holds it, and no event names a change the store does not hold. A crash between the commit and the emit loses the event while the record stands, the window every sibling accepts.

## The declarations

`trail.Emits()` declares the five names, literal, each with its attribute keys in order. The run's emitter is built with them, and `/declarations` publishes them (`D03-serve`). The bus holds an emitted event to its declaration's keys exactly, so every key is always present, empty when it does not apply.

## Secrecy

Events and telemetry carry ids and counts only (decision 16). No address, subject, snippet, body text, attachment name, attachment byte, raw message or token reaches telemetry, the bus, standard output or standard error, on success or failure; gmail writes no log of its own, and a serving run writes standard error only as `D03-serve` says. Mail text reaches the caller's tool answers and the owner's own pages (root ruling A2), and nowhere else; a draft's body reaches only the `draft` tool's answer and `gmail.db`. A refusal's sentence names an id, never a subject, an address or a filename (decision 8). No tool answer and no page carries a token or an attachment's byte, raw or encoded. The token goes only to Gmail, never to artifacts or connections.

The rule is proved at the run seam, by use, as gdrive proves its own: fakes of connections, Gmail and artifacts serve a random token, random **markers** where mail text goes (subjects, address local parts, snippets, filenames, the connected account) and random **bodies** where long text or bytes go (message text, attachment data, artifact contents), the test's own `compose` and `search` arguments carry markers and bodies too, some answers are failures whose bodies echo everything, and every capture of the run, both sinks, both streams, every tool result and every page body, is searched. A body is searched by its 16-byte pieces, of its bytes and of both base64 encodings, so a leak of part of it, or of Gmail's encoded answer, or of a raw message that holds an attachment, is found.

## Recorded decisions

- Five fixed names and two functions: `Record` for a transfer, `RecordDraft` for a draft. Each knows which attributes its names carry and tells nothing for a name not its own.
- **Transfer events as the record's caller; draft events as the context's.** The transfer rule is gdrive's: its events are told from the background, where no request is around. A draft keeps no email or request id (`D04-store`), and every draft event is told inside the tool call that made the change, reconciliation included (root ruling A7), so the context's caller is the right one and the only one available.
- `attachment` and `draft` both present on every transfer event, one or both empty: decision 13's "`attachment` or `draft`" names which carries a value; the bus's exact-keys rule makes both keys present. This departs from gdrive's single `file`.
- `bytes` and `attachments` are integer attributes (an `int64` basic form), as gdrive's `bytes`.
- `gmail.called`'s attribute names are `endpoint`, `status` and `duration_us`, gdrive's `drive.called` shape and appkit's `sibling.called` timing name; the endpoint values are `D05-gmail`'s.
- A sink that refuses every event changes no tool answer and no record: the trail and the bus are told after the change, and their failure is theirs (appkit's `undelivered event` and `lost event` lines), never the call's. gdrive states no such rule; it is added here.
- `event.lost` is in the closed set, since the emitter is built with the writer (`D03-serve`).
- Secrecy is required of the whole run, because the leak it guards against is a wiring one only the assembled process shows. The page-level privacy of mail text between users is `D08-pages`'; the tool-level privacy is `D10-tools`'.
- A search `query` is treated as mail text: it may hold addresses, so it is a marker in the secrecy conditions and never reaches the trail.
- The connected account's address (connections' `account`) is an address under decision 16.

## Consumer tasks

The engine (`D06-transfers`), once the store holds a transfer `running`, calls `trail.Record(ctx, w, em, trail.TransferStarted, t)`, and once it holds its ending, `trail.Record(ctx, w, em, trail.TransferFinished, t)` with the transfer `store.FinishTransfer` returned. The drafts service (`D07-drafts`), once `store.AddDraft`, `store.MarkDraftSent` or `store.MarkDraftDiscarded` has returned a draft `d` with a nil error, calls `trail.RecordDraft(ctx, w, em, trail.DraftCreated, d)`, `trail.DraftSent` or `trail.DraftDiscarded`, `ctx` being the tool call's. `Run` builds its emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`. A test builds a writer over a `*telemetry.Capture` and an emitter over an `*events.Capture` with `trail.Emits()`, calls `trail.Record` with a `store.Transfer` under a context carrying another caller and a cause, calls `trail.RecordDraft` with a `store.Draft` under a context carrying a caller, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`. A test of secrecy drives `cli.Run` with the three fakes and the captures, makes every tool call and page request, lets the transfers end, cancels, and searches every capture.
