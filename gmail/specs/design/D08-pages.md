# D08-pages

What gmail draws as HTML: `internal/pages`, the six templates `landing`, `draft`, `transfer`, `tools`, `about` and `notfound` and the data each is executed with, and the handler that answers `/`, `/drafts/<id>`, `/transfers/<id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it. It is gdrive's pages with a second record beside the transfer: the landing page has two sections, and each kind of record has its own page under its own prefix.

## The pages

The landing page shows the first page of the caller's own drafts and then the first page of the caller's own transfers, each newest first in the order the store lists them (`D04-store`: drafts by descending created, transfers by descending started, ties by descending id). Both lists grow with use, so the page lists them as the suite's listing rule asks (`shape/`, Listing; appkit's D25, `paging`), as `dummy`'s panel does: each section holds at most `paging.DefaultLimit` rows, read as one store window, and when more remain the template receives the token the tool `drafts` or `transfers` (`D10-tools`) answers as `next` for the same first page, `DraftsNext` or `TransfersNext`, empty when none remain, so a person can hand it to an agent; there is no link and no navigation. What the template draws from it is the asset's. A draft row carries its id linking to its page, its status as stored, its subject, its `To` addresses, its attachment count, its Gmail link when the record has one, and when it was created and sent. A transfer row carries what gdrive's does with mail's references: id, direction, status, reason when failed, name linked to Gmail when done, the artifact's path linked to artifacts, bytes, started and finished. With no draft, or no transfer, the template shows that section's empty state. Another user's record is never shown.

`/drafts/<id>` is one draft's record in full except its body: Gmail's draft id while open, the message and thread ids, `To`, `Cc` and `Bcc`, the subject, the message it replies to, the Gmail link, created, modified and sent, and its attachments in the order attached, each with its path linked to the artifact, its name, content type and bytes. `/transfers/<id>` is one transfer's record in full, with the reason's sentence when failed, which the template chooses from `Reason`. Neither page streams: a record is shown as it stands when the page is loaded. An unknown id, a pruned one and another user's are answered alike, the not-found page with 404, byte for byte the not-found page of any other path, so a page never tells a caller that someone else's record exists.

The tools page lists the thirteen tools in the catalog's order (`D10-tools`), each with the first line of its description. The about screen shows the service's name, the banner's `Release` and `Commit` and `Description`. Any other path is the not-found page, 404, whatever the method.

The landing page is the root of the banner's trail; a draft page is one level below it, named by the draft's id at `/drafts/<id>`, a transfer page likewise at `/transfers/<id>`, and the tools page and the about screen are one level below it, `pages.ToolsLevel` and `pages.AboutLevel`. The banner's user is the caller's email, with auth's profile and sign-out addresses built on `urls.Auth` (`D01-layout-and-run-seam`).

## Pages show what is stored

Pages make no call to Gmail, artifacts or connections, and change no record (root rulings A5, A6). A draft's page and row show the status the store holds: a draft a person sent or deleted in Gmail stays `open` on the pages until a tool that reconciles touches it (`D07-drafts`). The same holds for a transfer still queued or running.

## Privacy

Mail text appears on the owner's own pages and nowhere else on a page (decision 15, root ruling A2): a draft's subject and recipients on the landing page and the draft page, a transfer's name, which is mail text for a pull (an attachment's filename or the message's subject, root ruling A1), on the landing page and the transfer page. The about, tools and not-found pages carry none. A draft's body is on no page: no page data type has a field that could carry it. No page carries a message's body, a snippet, a token or a byte of an attachment, since no page reads Gmail.

## The data

Every value a template receives is a string, a slice of strings, an `int` count or an `int64` byte count. Times are the stored UTC times formatted twice, as the template comments name them: RFC 3339 to the second for a `time` element's `datetime`, and a `...Text` field in the page's layout, `pages.MinuteLayout` on the landing page and `pages.SecondLayout` on the record pages. A time not yet set gives both strings empty. The field names are the template comments': the draft view's `GmailDraft` and `InReplyTo` are page data names for the record's `draft` and `reply_to` JSON members (root ruling A3), filled from the store's `GmailDraft` and `ReplyTo`.

A transfer's `ArtifactPage` is the artifact's page on artifacts, built with `urls.ArtifactPage` from the services file's `artifacts` entry and the artifact id the record holds, empty when it holds none (every push, and every pull not done). A draft attachment keeps no artifact id, so its `ArtifactPage` is derived from its path (root rulings A4 and A11): `urls.ArtifactFile` over the same base, the artifact's `/files/<path>` address, the same form as a transfer's `url`, and empty when the services file has no `artifacts` entry or its `URL` is empty. artifacts has no page addressed by path.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so nginx sends a request with no credential to sign in before it reaches gmail, and `D03-serve` mounts this handler inside `identity.Require`. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. The landing page and the record pages answer 503 with `store.Unreachable` as plain text when the store cannot be read; the about, tools and not-found pages are served without reading it.

## Recorded decisions

- **The landing page's tokens are the tools'**: `DraftsNext` is `paging.Token{Tool: "drafts"}` and `TransfersNext` `paging.Token{Tool: "transfers"}` over the key (`D04-store`) of the section's last row, the very `next` the tool answers with no arguments, so a person reads the rest of either list through an agent.
- Record pages at `/drafts/<id>` and `/transfers/<id>`, departing from gdrive's `/<id>`, because gmail has two kinds of record (orchestrator's settlement). A path whose id is not valid for its prefix (`store.ValidDraftID`, `store.ValidTransferID`) is not looked up; a draft id under `/transfers/` is the not-found page.
- `ServiceName`, `Description` and the two layouts are contract constants with values, as in gdrive: `Description` is the manifest's text, which the host parses (`D02-cli`), and the layouts are data formats the templates name.
- Draft row and draft view are two types, as the transfer's are, because their time layouts differ and the view carries more fields; each field list is the template comment's, in its order. `AttachmentCount` is an `int`, as the comment says.
- The landing draft row shows every recipient, as `landing.html` draws it: it carries `To`, `Cc` and `Bcc`, and the template joins them in that order; this is decision 15's "recipients".
- `AttachmentRow.ArtifactPage` is `urls.ArtifactFile(urls.Base(u), path)`, the orchestrator's ruling that it is derived from the path (root rulings A4 and A11). This departs from gdrive, whose artifact page is built from the artifact id, because a draft attachment holds no artifact id (`Head` answers none). With no `artifacts` entry or an empty `URL` it is empty and the template shows the path plain. The `draft.html` comment's wording, which builds the value from an id, is an asset nit the root reports.
- The banner's addresses are `urls.Auth` followed by `/` and by `/logout`, as `D01-layout-and-run-seam`'s about requirement shows.
- An unknown, pruned or another user's id is one not-found answer, byte for byte the not-found page of any other path.
- A database outage is a plain-text 503 with `store.Unreachable` and a newline, as in gdrive.

## Consumer tasks

`web.Handler` (`D03-serve`) builds `s, err := pages.Load()` and mounts `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store})` inside `identity.Require` for every path that is not `/mcp`, `/events`, `/declarations` or under `/_appkit/`. `D01-layout-and-run-seam`'s about requirement executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}`; `D02-cli` compares the manifest with `pages.Description`; `main` names the service `pages.ServiceName`. A test builds a store over its own database with a clock it sets, adds drafts and transfers for two users, attaches to some drafts, marks some sent and some discarded, finishes some transfers `done` with an artifact id and some `failed` with each reason, writes a services file naming an `artifacts` entry, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a fixed banner, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template writes for a `LandingData` of `DraftRow`s and `TransferRow`s with the two next tokens (more than `paging.DefaultLimit` records of one kind giving a non-empty one), a `DraftData`, a `TransferData`, a `ToolsData` built from `tools.Catalog()`, an `AboutData` or a `NotFoundData`; it asks the other user's ids and gets the not-found page, and turns the store's failing switch on to see the 503.
