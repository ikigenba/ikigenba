# D01-layout-and-run-seam

gmail is the suite's Gmail connector: one Go binary through which an agent reads a user's mail, moves attachments and whole messages into artifacts, and composes, fills and sends drafts on that user's behalf. Mail text (headers, snippets, body text) reaches the caller in tool answers; attachment bytes, raw messages and credentials never do, and move on the host as **transfers** (`D06-transfers`). An agent finds mail with `search`, `thread`, `show` and `labels`, asks for a transfer with `pull` (Gmail to artifact) or `push` (artifact onto a draft), and composes, sends and discards **drafts** with `compose`, `send` and `discard` (`D07-drafts`); thirteen MCP tools are offered at `/mcp` (`D10-tools`). Gmail is reached over its REST v1 API with an access token connections hands out (`D05-gmail`), artifacts over its socket. Transfers and drafts live in the app's own SQLite database, `state/gmail.db` (`D04-store`); each transfer that begins and ends and each draft created, sent or discarded is an event on the bus and in the trail, and every Gmail call is recorded as `gmail.called` (`D09-trail`). A landing page of the caller's drafts and transfers at `/`, a page per draft at `/drafts/<id>`, a page per transfer at `/transfers/<id>`, a tools page at `/tools`, an about screen at `/about` and the not-found page are served to a signed-in user (`D08-pages`).

This design is the structural ground the others stand on: where the code lives and what each package is for, the seam through which the process is run so that every part can be tested without a real process, the default client every Gmail call goes through, the paths, the migrations, the addresses every other document builds (`internal/urls`), where the identity and the display string come from, and the binary's wiring. The settings, the services file and the serve path are `D03-serve`'s; the command line is `D02-cli`'s. It follows gdrive's layout and run seam, the closest precedent, with mail's packages in place of Drive's.

The module is `github.com/ikigenba/ikigenba/gmail`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/gmail`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/gmail` is wiring only.

## The dependencies

gmail depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required at a published release with no `replace` directive. Its `db` package brings the pure-Go SQLite driver, which keeps the release build cgo-free. gmail uses appkit's `db`, `version`, `services`, `page`, `identity`, `mcp`, `telemetry`, `events`, `artifacts`, `connections` and `paging` (the listing token and window of appkit's D25), and restates none of their contracts. It speaks to Gmail with the standard library alone (decision 4): `net/http` for the calls, `mime/multipart`, `net/mail`, `net/textproto` and `encoding/base64` for the messages it builds; no Google library and no other module. Which release of appkit is data that `AGENTS.md` and `go.mod` hold.

## Where the environment is read

`main` makes the one read of the environment that is not `Run`'s own: it calls appkit's `version.Read` exactly once, first, and holds the result, the **identity**, whose `String()` is the **display string**. It hands the identity to `page.New`, whose banner carries its `Release` and `Commit` to every page's footer and to the about screen, and the display string to the `mcp.ServerConfig` its `Process.MCP` builds and to `Run` as `Process.Version`. Nothing below `main` calls `version.Read`. `Run` reads every variable through `Process.LookupEnv`: `DRAIN_SECONDS` and the seven settings of the manifest's `[env]` once at start, through `settings.Read` (`D03-serve`); `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness; and `IKIGENBA_SERVICES` once, when it starts to serve.

## Packages

The root package holds what the module embeds: `Assets` (the six templates `about.html`, `draft.html`, `landing.html`, `notfound.html`, `tools.html` and `transfer.html`), `Etc` (`manifest.toml` and `nginx.conf`) and `Migrations` (`0001_transfers.sql` and `0002_drafts.sql`, which create the two tables `D04-store` describes, and `0003_list_indexes.sql`, which adds the indexes its list windows read by). Its package name is `gmail`, the same as the Gmail client's; a file that needs both imports the root package under an alias of its own choosing.

The internal packages hold the concerns, one each, and each is declared in full by the document named:

- `internal/cli`: the run seam, the command, the serve path and the default Gmail client (this document, `D02-cli`, `D03-serve`).
- `internal/settings`: the eight settings (`D03-serve`).
- `internal/server`: a listener's life (`D03-serve`).
- `internal/web`: the route table, `web.Config` and `web.Handler` (`D03-serve`).
- `internal/store`: the transfer and draft records, their words, writes, reads and prunes (`D04-store`).
- `internal/gmail`: the Gmail REST v1 client, `gmail.Client` built by `gmail.NewClient(gmail.Config)`, the connector's own message, summary, attachment and label types, the message builder, and `gmail.called` (`D05-gmail`).
- `internal/transfers`: the engine, `transfers.Engine` built by `transfers.New(transfers.Config)`: validation and recording of `pull` and `push`, the caller's Google token, the queue, the background work as the caller, the start's settling (`Engine.Recover`) and the drain (`Engine.Drain`) (`D06-transfers`).
- `internal/drafts`: the drafts service, `drafts.Service` built by `drafts.New(drafts.Config)`: `compose`, `send`, `discard`, the reconciliation of a draft sent or deleted in Gmail, and the upload cap (`D07-drafts`).
- `internal/urls`: the addresses: the connect page, an artifact's page, an artifact's file address, auth's address, the Gmail web links and the record pages (this document).
- `internal/trail`: the transfer and draft events and the app's secrecy (`D09-trail`; `gmail.called` is `internal/gmail`'s).
- `internal/tools`: the thirteen tools (`D10-tools`).
- `internal/pages`: the templates' data and the page routes, `pages.ServiceName` and `pages.Description` (`D08-pages`).

Which imports which is guidance, not contract.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package and the network, and returns the exit code. It is gdrive's seam unchanged. `HTTP` is the client every call to Gmail goes through: a test hands one whose transport answers every request as a fake Gmail does, so no test reaches Google and no `Process` field names Gmail's address; `internal/gmail`'s own tests may instead point `gmail.Config.BaseURL` at a loopback fake (`D05-gmail`). `Now` is the clock every time gmail stamps or compares is read from: a transfer's started and finished, a draft's created, modified and sent, a pull's expiry check, the prunes' cut-off, every event's time. `After` is the sweeper's timer (`D03-serve`). `Rand` is the source of every value gmail mints: request ids, transfer ids, draft ids and bus event ids; whether the message builder draws its MIME boundaries from it is `D05-gmail`'s. `Inherit`, `Now` and `Rand` are the caller's to give whenever `Args` is empty: `Run` has no default for any of them, and the choice of the process's own descriptor 3, `time.Now` and `crypto/rand.Reader` is made once, at the process boundary, by `cmd/gmail`. The sibling sockets reach `Run` through the services file `IKIGENBA_SERVICES` names (`D03-serve`).

## The default Gmail client

A nil `HTTP` is the client `cli.DefaultHTTP` returns. It has no overall `Timeout`, because a push streams a draft of up to 35 MiB and a pull reads an answer of up to about 67 MiB, and the drain, not a clock on the whole exchange, ends a transfer cut short (`D03-serve`). Its transport bounds the parts of an exchange that should be quick: the dial (`cli.DialTimeout`, 10 seconds), the TLS handshake (`cli.TLSHandshakeTimeout`, 10 seconds) and the wait for response headers once the request, body included, has been written (`cli.ResponseHeaderTimeout`, 60 seconds, enough for Gmail to take a draft's whole upload).

## Paths

Relative to `Process.Dir` (the process's working directory when empty) the database is `state/gmail.db`, opened with `db.Open`, the root package's `Migrations()` and `Process.Now`; `state/` is created when absent. gmail writes nothing outside `Dir` and keeps no blob on disk: a pull holds one encoded copy in memory and a push streams (decision 12).

## The addresses

`internal/urls` holds every address gmail builds, declared here because the engine, the drafts service, the store, the pages and the tools all use them. The **connect page** is the `URL` of the services file's entry `connections`, every trailing `/` removed (`urls.Base`), followed by `/google/connect` (`urls.Connect`), and so relative when the file has no such entry. An artifact's **page** on artifacts is the `URL` of the entry `artifacts`, trailing `/` removed, then `/` and the artifact's id (`urls.ArtifactPage`), empty when either is empty: only a pull's `Put` answers an id. An artifact's **file address** is the same base then `/files/` and the artifact's path (`urls.ArtifactFile`), empty when either is empty: it is what a draft's attachment links to, since an attachment keeps a path and no id. The **auth address** is the `URL` of the entry `auth`, trailing `/` removed, or, with no such entry, built from the request's scheme and host with a leading `gmail.` removed (`urls.Auth`). The **Gmail links** are the settled forms: a message in Gmail's web interface is `https://mail.google.com/mail/u/0/#all/<message id>` (`urls.MessageLink`) and a draft is `https://mail.google.com/mail/u/0/#drafts/<message id>` (`urls.DraftLink`), each empty for an empty id. The **record pages** are `/drafts/<id>` (`urls.DraftPage`) and `/transfers/<id>` (`urls.TransferPage`), paths on gmail's own host.

## Recorded decisions

- The layout is gdrive's with `internal/gmail` in place of `internal/drive` and one package added, `internal/drafts`, which holds the composition rules, the reconciliation and the upload cap: those are neither the engine's (no transfer is involved in `compose`, `send` or `discard`) nor the client's (they are the connector's rules, not Gmail's). The MIME builder is `internal/gmail`'s, since building the message Gmail takes is part of speaking to Gmail.
- The root package and the client package are both named `gmail`, following each one's directory, as gdrive's root is named for its directory; a file importing both aliases the root. The alternative, a client package named for something other than its directory, was rejected as the stranger of the two.
- No `Process` field names Gmail's address, as gdrive's names none for Drive: a `Run`-level test reaches its fake Gmail through `HTTP`'s transport, and the base URL is a field of `gmail.Config` that `Run` leaves empty (`D05-gmail`).
- The default client's bounds are gdrive's; the response-header bound covers a draft upload's final answer, which Gmail gives once it has the whole message.
- `internal/urls` is declared here, not in the engine's document as gdrive declared it, because in gmail five documents build addresses and none of them is first. It gains the Gmail links, the record pages and `ArtifactFile`. Record pages at `/drafts/<id>` and `/transfers/<id>` depart from gdrive's `/<id>`, since gmail has two kinds of record (orchestrator's settlement).
- A draft attachment's link is derived from its path (root ruling A4). artifacts has a page only per id (`/<id>`) and a draft keeps no artifact id, since `Head` answers none; the one address on artifacts a path names is the artifact's `/files/<path>`, so `urls.ArtifactFile` is that derivation. This departs from the template comment of `draft.html`, which describes `.ArtifactPage` as built from an id; the page data is `D08-pages`'.
- The Gmail link forms are settled by the orchestrator, not proven here; `#all/` names a message in any label, and `#drafts/` takes the draft's message id, not Gmail's draft id.
- `Process.Inherit`, `Process.Now` and `Process.Rand` are required whenever `Args` is empty, as in gdrive; no requirement states the precondition, because no permitted test can observe a default.
- The dial bound is declared but no requirement proves it is applied, as in gdrive: a transport's dial function cannot be inspected offline.

## Consumer tasks

`main` calls `id := version.Read()` and `v := id.String()` and hands `cli.Run` a `cli.Process` whose `Args`, `LookupEnv`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Version` is `v`, whose `Banner` is `page.New(pages.ServiceName, id).Banner`, whose `Inherit` takes the process's own descriptor 3, whose `Now` is `time.Now`, whose `Rand` is `crypto/rand.Reader`, whose `After` is `time.After` and whose `MCP` returns `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: v, Telemetry: w})`, leaving the rest zero; it cancels the context on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name, and exits with what `Run` returns. `internal/cli` imports the root as, say, `app "github.com/ikigenba/ikigenba/gmail"` and the client as `gmail`, and opens `db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "gmail.db"), Migrations: app.Migrations(), ...})`. A test of the run seam writes a services file whose entries `artifacts` and `connections` name Unix sockets on which loopback fakes listen, builds a `cli.Process` with a temporary `Dir`, a `LookupEnv` over a map, an `Inherit` returning a listener it bound, a `Now`, an `After` and a `Rand` it controls, an `HTTP` whose transport answers as a fake Gmail, and capturing sinks; calls `cli.Run`, waits for `READY=1`, drives `/mcp` with `mcp.Client` and the pages with raw HTTP, cancels, and inspects `Dir`, the fakes' requests and the captures. The engine builds a pull's link with `urls.MessageLink(m)` and a push's with `urls.DraftLink(m)`; the store fills a draft's `Link` with the same two; the pages build `urls.ArtifactPage(urls.Base(u), t.ArtifactID)`, `urls.ArtifactFile(urls.Base(u), a.Path)`, `urls.DraftPage(d.ID)` and `urls.TransferPage(t.ID)`; the engine is built with `urls.Connect(urls.Base(connectionsURL))`.
