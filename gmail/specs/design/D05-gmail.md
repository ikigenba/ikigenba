# D05-gmail

The Gmail client: `internal/gmail`, the one place in gmail that speaks Gmail's REST v1 API and the one place that reads Gmail JSON (decision 4). It is written over the standard library alone and makes exactly the calls decision 4 names, all on `users/me`: `labels.list`, `messages.list`, `messages.get` (as `full`, `raw` and `minimal`), `messages.attachments.get`, `threads.get`, `drafts.create`, `drafts.get`, `drafts.update` by resumable upload, `drafts.send` and `drafts.delete`. Every answer is reduced at the edge to the connector's own types, a message summary, a full message with its attachment parts, a label, a page of summaries, a message's status, the statuses of a thread's messages, a draft and a body of decoded bytes, so the engine (`D06-transfers`), the drafts service (`D07-drafts`), the tools (`D10-tools`) and the pages never see a Gmail field name. It also holds the message builder, which turns a composition into the `message/rfc822` bytes `drafts.create` and `drafts.update` take, streaming each attachment's bytes through base64 as they are read, and the event `gmail.called` every request is recorded as.

## The client

A `Client` is built once per process from a `Config`: the `*http.Client` every request goes through (`cli.Process.HTTP`, whose default `D01-layout-and-run-seam` owns), the base URL, empty meaning Gmail's own `https://gmail.googleapis.com` (the discovery document's `rootUrl`), and the telemetry writer `gmail.called` is recorded through. The process leaves the base URL empty and its tests answer Gmail through `HTTP`'s transport; this package's own tests point the base URL at a loopback fake Gmail served with `httptest`. Both the API paths (`/gmail/v1/users/me/...`) and the upload path (`/upload/gmail/v1/users/me/...`) hang off the one base URL, as the discovery document places them.

A `Client` serves every user: the caller's access token, just obtained from `appkit/connections`' `Token`, is an argument of every call and travels as `Authorization: Bearer <token>`. Each call but `UpdateDraft` is one short exchange or a few, so a token taken just before it is good for all of it. The upload is the long exchange, and only its opening request carries the token: the session URI Gmail answers is the credential for the pieces, treated like the token and never shown in an error or an event.

## Reading mail

`Labels` answers the mailbox's labels in Gmail's order, each with its id, its name and whether it is Gmail's own (`type` `system`, observed for `INBOX`, `SENT`, `UNREAD`, the `CATEGORY_` labels and the rest). Decision 7 has the tools answer only `name` and `system` (`D10-tools`); the id stays inside the connector.

`Search`, `Thread` and `Show` each first ask `labels.list` once, because a summary names its labels by name and Gmail answers ids. `Search` passes the agent's query verbatim as `q` (decision 7: nothing escaped or built), narrows to one label when a label name is given (resolved to its id against that same answer, compared without regard to case, since Gmail's own `label:` search ignores case, and refused as not found when no label has that name), excludes spam and trash, and asks for 25 messages at a time (`PageSize`). Gmail answers ids only (observed: `messages` holds `id` and `threadId`, and is absent when nothing matches), so each listed message costs one `messages.get`. Decision 7 says that `get` is `format=metadata`; that format answers the top-level headers and no MIME parts at all (observed), so it cannot count attachments. The client asks for `format=full` instead and names with `fields` only the members a summary reads: the ids, labels, snippet, internal date, the headers and the `filename` of every part nine levels deep (`SummaryFields`), which leaves every body's data out of the answer (observed). Gmail answers all headers whatever `fields` says, so "naming only the headers the summary needs" is not achievable; the cost stays one `messages.get` per summary. A message deleted between the list and its `get` (answered 404) is left out of the page rather than failing it. The page token Gmail answers is passed out as `next` and back in as `page` untouched; a token Gmail refuses (observed: 400 `Invalid pageToken`) is `ErrBadPage`.

`Thread` asks `threads.get` with the same per-message `fields` and answers the thread's messages oldest first by internal date, 25 at a time. Gmail answers a thread whole, with no page token of its own, so the client pages it itself: `page` is the decimal offset of the first message, `next` the offset of the page after, both opaque to the agent; anything else handed back as `page` is `ErrBadPage`.

`Show` asks `messages.get` with `format=full` and no `fields`, so the whole part tree with every body Gmail inlines comes back, and answers the full message (decision 5): the summary's members, the `Message-ID` and `In-Reply-To` headers, the body text, whether it was cut, and the attachment parts. An attachment's id is the part's `partId` (`1`, `0.1.2`): Gmail's `attachmentId` changes on every read (observed: two reads of the same message a moment apart gave different `attachmentId`s for every part), so it is never answered. Every part with a non-empty `filename` is listed, an inline image with a filename included (decision 5 read literally, root ruling A17), in the tree's order. `Show` also carries the `Reply-To` and `References` headers for `D07-drafts`' reply defaults; the tools never answer them.

A summary's `date` is the message's `internalDate`, which Gmail documents as more reliable than the sender's `Date` header and which always parses; `from`, `to`, `cc` and `subject` are the header values as Gmail answers them, which arrive already decoded from RFC 2047 (observed: of a hundred messages, fourteen had non-ASCII sender or subject text and none carried an encoded word). Gmail's snippet is HTML-escaped (observed: `&#39;`, `&amp;`), so the client unescapes it. `link` is `urls.MessageLink` of the id (`D01-layout-and-run-seam`).

## The body

Decision 6's body is the first `text/plain` part in the tree's order, taken in a pre-order walk that counts the payload itself, among parts with no filename (an attached `.txt` is an attachment, not the body) whose body Gmail inlined as `data`. When there is none, it is the first such `text/html` part reduced to text by `ReduceHTML`; when there is neither, it is empty. Gmail answers a text part's data converted to UTF-8 whatever charset the part declares (observed: three `iso-8859-1` parts whose `data` was valid UTF-8 one byte longer than the part's `size` per non-ASCII character), so the client needs no charset table; any invalid UTF-8 left is replaced by U+FFFD, and CRLF line ends become LF. The text is cut at `BodyCap` (64 KiB) on a character boundary, with `truncated` true; the whole message stays available through `pull`.

`ReduceHTML` is exported so the reduction is proved directly. It drops comments and the contents of `script` and `style`, drops every tag, turns the start and end of each block element and each `br` into a line break, collapses runs of whitespace in text, unescapes entities, trims each line, keeps at most one empty line in a row, and trims the ends. It is lossy, as decision 6 says, and makes no attempt at tables or lists beyond line breaks. The standard library has no HTML parser; the reduction is a small scanner, which is why its rules are spelled out to the byte.

## The status of a message

`Stat` asks `messages.get` with `format=minimal` and answers the message's id, thread, internal date, `sizeEstimate`, and whether it carries the `SENT` label. It serves a whole-message `pull`, which checks `sizeEstimate` against `TRANSFER_MAX_BYTES` before recording (root ruling A9; observed: a message's `sizeEstimate` equalled the length of its decoded `raw` form). `ThreadStats` answers the same status, its size left 0, for every message of one thread, in Gmail's order, from one `threads.get` whose `fields` name only each message's ids, labels and internal date: the reconciliation of a draft Gmail no longer knows looks in the draft's thread for a message carrying `SENT` (root ruling A19); what the drafts service does with the answer is `D07-drafts`'.

## Bytes on the read side

Gmail answers no media stream (decision 12): `messages.attachments.get` answers `{"size", "data"}` and `messages.get` with `format=raw` answers the message with a `raw` member, each base64url text with padding inside JSON (observed). `Attachment` and `Raw` read the answer into one buffer and answer a `Content`: the decoded length and a reader that decodes from that buffer as it is read, so a pull holds one encoded copy, about four thirds of the bytes, and hands the reader straight to one artifacts `Put` (`D06-transfers`). How the client finds the `data` member inside its buffer without a second copy is its own; no test observes memory.

`Attachment` resolves the part id afresh: it asks `messages.get` with `format=full`, finds the part with that `partId` and a filename, refuses it as too large from the part's `size` before fetching, and fetches its current `attachmentId` with `messages.attachments.get`; a part whose body Gmail inlined as `data` with no `attachmentId` is answered from that data with no second request. Both `Attachment` and `Raw` take the transfer limit: a decoded length over it is `ErrTooLarge`, and an answer body longer than the encoded form of the limit plus 64 KiB of envelope is `ErrTooLarge` without being read further, so a lying `size` or `sizeEstimate` cannot make the client hold more than the limit allows.

## Building a message

A `Composition` is what `D07-drafts` keeps and `D06-transfers` rebuilds from: the sender (the connected account, `connections.Token.Account`), the recipients as parsed `mail.Address` values, the subject, the plain text, the reply headers, and the attachments, each a `Part` with its name, content type, length and an `Open` function that yields its bytes. `Build` makes an `Outgoing` from it without reading anything: its `Size` is the exact number of bytes the message will have, computed from the parts' lengths, so `D07-drafts` checks Gmail's 35 MiB cap (`UploadCap`, the discovery document's `maxSize` of 36,700,160 bytes for `drafts.create`, `drafts.update` and `drafts.send`) with `Build(c).Size()` before any byte moves, which is decision 7's "sizes times four thirds plus the headers and text" computed exactly, line breaks of the base64 included. The `Outgoing` is then read once, as an `io.Reader`: it opens each part only when the reading reaches it and encodes its bytes through base64 as they arrive, so only the headers and the text are held (decision 12).

The message is built with `net/mail`, `mime`, `mime/multipart` and `encoding/base64`. With no attachment it is a single `text/plain; charset=utf-8` part; with attachments it is `multipart/mixed` whose first part is the text and whose next parts are the attachments in order, each `Content-Disposition: attachment` with its filename and `Content-Transfer-Encoding: base64` in lines of 76. The text is base64 too, its lone LFs sent as CRLF and every other byte as given, so a lone CR round-trips: `mime/quotedprintable`'s text mode turns a lone CR into a line break, and the standard library offers no quoted-printable mode that keeps it while still breaking lines. Header values, an attachment's filename and content type included, have every CR and LF replaced by a space and are encoded as RFC 2047 words (or RFC 2231 parameters) when they need it, so no value can carry a line break into a header block. The values the composition supplies to the message's own header (each address's name and address, the subject and the reply headers) are cleaned by one rule: after that replacement, the spaces and tabs at the value's start and end are removed, so what `mail.ReadMessage` reads back, the subject after RFC 2047 decoding, equals the cleaned value whatever bytes the composition holds, and a value that cleans to nothing gives no header. There is no `Date` and no `Message-ID`: Gmail assigns them. The builder draws no randomness: its multipart boundary contains `=_`, a sequence that base64 output can never hold, so a fixed boundary is safe and a composition always builds to the same bytes, which tests compare directly. `Process.Rand` (`D01-layout-and-run-seam`) is therefore not needed here.

A part whose stream yields more or fewer bytes than its declared length breaks the message's declared size, so reading the `Outgoing` then fails with `ErrPartSize`; an `Open` or read failure is answered as it came, never as Gmail's failure, so the engine tells artifacts' failure (`artifacts`) from Gmail's (`provider`). The upload reads the `Outgoing` as it sends: it holds at most one piece of `PushChunk` bytes at a time, and the parts' streams are pulled only as each piece is filled.

## Drafts

`CreateDraft` sends the composed message in one JSON request, `{"message": {"raw": ..., "threadId": ...}}`, the thread given when the draft replies; a `compose` carries no attachment, so the whole message is small. `UpdateDraft` replaces a draft's message by resumable upload (decision 4): one `PUT` to the upload path with `uploadType=resumable`, the draft's id and thread as JSON metadata, the content type `message/rfc822` and the exact length; Gmail answers the session URI in `Location`; the message then goes in `PushChunk` pieces, each a `PUT` to that URI with its `Content-Range` and no `Authorization`, answered `308` with the range held until the last, whose answer is the draft. Gmail replaces the draft only when the last piece lands, which is what lets a failed push leave the draft as it was (decision 9). The answer's message id and thread are the draft's new ones, which `D06-transfers` stores (root rulings A6, A19). `GetDraft` is the reconciliation probe (`format=minimal`), answering the draft's current message id and thread; `SendDraft` sends a draft and answers the sent message's id and thread; `DeleteDraft` deletes it permanently.

## The trail

Every request the client sends is recorded as one `gmail.called` event through the writer, the shape of appkit's `sibling.called` and gdrive's `drive.called`: `endpoint`, the call's name from this design's table; `status`, the answer's status or 0 when none came; `duration_us`, the exchange up to the response headers on the writer's clock. Nothing else travels: no token, no id, no query, no label, no header and no byte of a body (decision 16). The event's request id and user are the caller's in the context. `D09-trail` owns the trail as a whole and its secrecy across the app; this document owns the client's emission, since only the client sees each request.

## Errors

Every failure is one of six kinds told apart with `errors.Is`. `ErrNotFound`: Gmail answered 404 or 400 to a read or delete whose path names a message, thread, attachment or draft id, or 404 to `drafts.send` or to opening a draft's upload (observed: a malformed message or thread id answers 400 `Invalid id value`, a stale attachment id 400 `Invalid attachment token`, a well-formed unknown message, thread or draft id 404), or a label name, a part id or an id given empty that names nothing; the tools refuse `not_found`, a transfer fails `not_found`, and the drafts service reconciles. `ErrUnauthorized`: Gmail answered 401 (observed for a bogus token, reason `authError`); consumers answer `reconnect`, since connections handed out a token Gmail refused (decision 14 and the brief's mapping; a departure from gdrive, whose client calls a 401 provider). `ErrTooLarge`: a message over `UploadCap`, a 413, or a pulled body over the limit. `ErrBadPage`: a page token Gmail or the client refuses. `ErrPartSize`: an attachment stream of the wrong length. `ErrProvider`: anything else Gmail did, 403 included, any other status, no answer, or an answer the client cannot read. When no answer came because the call's context was done, the error also matches the context's error, so the engine tells a drain from a Gmail failure.

No error text carries the token, the session URI, the query, a label name, any header or body of mail, or any byte of Gmail's answer body: Gmail's own error messages echo input (observed: `Invalid label: NOPE`), so the client never quotes them. An id may appear, as decision 8 allows a refusal's sentence to name one.

## Recorded decisions

- **Live read-only probes, 2026-10-12**, run before root ruling A15, which forbids any further probe of the real account without the root's word; with a token refreshed from the seeded grant (scopes `gmail.readonly`, `gmail.compose`, `drive`, `userinfo.email`, `openid`), not kept: `labels.list` answers `labels` of `{id, name, type}` with `type` `system` for Gmail's own; `messages.list` answers `messages` of `{id, threadId}`, `nextPageToken` and `resultSizeEstimate`, with `messages` absent when nothing matches, and accepts `includeSpamTrash=false`, `labelIds` and an empty `q`; a bogus `pageToken` and an unknown `labelIds` value answer 400; `messages.get` `format=metadata` answers the top-level headers named and no parts; `format=full` with a `fields` selection nine `parts` levels deep is accepted and answers only what it names, with no body data; `format=full` answers `partId` `""` for the payload and dotted ids below, `filename` on inline images, `body.attachmentId` and `body.size` on attachment parts and `body.data` on text parts; `attachmentId` changes between reads; `messages.attachments.get` answers `{size, data}` with `size` equal to the part's `body.size`; `format=raw` answers base64url with padding and `sizeEstimate` equal to the decoded length; `format=minimal` answers `id`, `threadId`, `labelIds`, `snippet`, `sizeEstimate`, `internalDate` (a decimal string of milliseconds) and `historyId`; `threads.get` with `fields` answers only `messages`, oldest first in the thread probed; snippets carry HTML entities; header values come decoded; text data comes as UTF-8; the error shapes listed under Errors.
- **The write side is proven from Google's published documentation** (root ruling A15; no draft was created, updated, sent or deleted while designing). Gmail's upload guide (developers.google.com/workspace/gmail/api/guides/uploads, read 2026-10-12) documents the resumable protocol under `/upload/gmail/v1/users/<userId>/...` with `uploadType=resumable`: the opening request with `Authorization`, `X-Upload-Content-Type`, `X-Upload-Content-Length` and metadata in a body whose `Content-Type` matches its format; the `200 OK` answer with the session URI in `Location`; the data sent by `PUT` to the session URI in chunks that are multiples of 256 KB but the last, each with `Content-Range: bytes <a>-<b>/<n>`; `308 Resume Incomplete` with `Range: bytes=0-<b>` between chunks; and `200 OK` when an existing resource is updated (`201 Created` for a new one; the client takes either). The guide's chunk examples carry no `Authorization`, which gdrive observed Drive accepts on the same Google protocol; the client sends none. The discovery document (fetched 2026-10-12) gives `drafts.update` as `PUT .../drafts/{id}` with a `Draft` body `{id, message}`, its media upload path, `accept` `message/*` and `maxSize` 36,700,160; `drafts.create`, `drafts.get` (`format` among `minimal`, `full`, `raw`, `metadata`), `drafts.send` (answers a `Message`) and `drafts.delete` (permanent). The host is the discovery document's `rootUrl`; the guide's examples use `www.googleapis.com`, which serves the same paths. `SendDraft` answers the sent message's id and thread from `drafts.send`'s answer, never the draft's message id: a later live probe (root ruling A19, recorded in `D07-drafts`) observed that a sent draft's message takes a new id, keeping the thread of the draft's last message, and that the draft's message id then answers 404.
- **`format=full` with `fields` for summaries**, a departure from decision 7's `format=metadata`, made for decision 5's `attachments` count and confirmed by root ruling A16: metadata answers no parts, so it cannot count attachments. Still one `messages.get` per summary. `SummaryFields` and `ThreadFields` name no `body` member at any level, so the summary path fetches no body data at all, inlined or not (observed: the answer carried none). Parts deeper than nine levels are not counted in a summary; `Show`, which asks for the whole tree, lists them all.
- **`ThreadStats` reads `threads.get` with `format=full` and `fields`** `messages(id,threadId,labelIds,internalDate)`, the form observed above to answer only what it names, rather than `format=minimal`, whose thread answer was never observed. It asks no `labels.list`: `SENT` is a system label whose id is its name (observed in `drafts.send`'s answer, root ruling A19), and `Stat.Sent` already reads the id.
- **Labels by name, case-insensitively**, and one `labels.list` per `Search`, `Thread` and `Show`, to map ids to names; an id the list does not hold is answered as itself.
- **A message gone between list and get is skipped**, so a page may hold fewer than 25 summaries while `next` is set.
- **`Thread`'s page token is the client's own**, a decimal offset, because `threads.get` has none; gdrive passes Drive's tokens only. An offset at or past the end answers an empty page.
- **`format=minimal` for `Stat` and `GetDraft`**, a departure from decision 4, which lists `metadata`, `full` and `raw` for `messages.get` and no format for `drafts.get`: the minimal form answers the ids, labels, `sizeEstimate` and `internalDate` that `Stat` and the reconciliation probe need and nothing of the mail, a smaller answer than `metadata`. The format is in the discovery document's enum for both calls and `messages.get` with it was observed before ruling A15.
- **400 on `drafts.send` and on opening an upload is `ErrProvider`**, not not-found: a draft a person edited in Gmail can be refused for its content (bad recipients), which says nothing about whether the draft exists; a 404 there is still `ErrNotFound`, and `D07-drafts` probes with `GetDraft` before it reconciles.
- **CR and LF are stripped from header values** by the builder, each replaced by a space, rather than refused: the composition reached the builder already validated by `D07-drafts`, and a stray line break in a reply header copied from the original must not fail a push.
- **The composition's header values are trimmed after the stripping**, the spaces and tabs at each end removed, because `net/mail`'s reader removes a value's leading spaces and tabs after unfolding (a build issue, resolved by this rule), so no encoding of `In-Reply-To` or `References` can carry them back; one rule for every such value, the subject and the addresses included, keeps the read-back equal to the cleaned value. A throwaway stdlib probe (Go 1.26) confirmed it: values with a leading CR, an interior LF and a trailing tab, an all-white-space value, and subjects needing RFC 2047 words read back through `mail.ReadMessage` and `mime.WordDecoder` equal to the cleaned form.
- **`date` is `internalDate`**, read in UTC.
- **The client's types carry no JSON contract.** `Label`, `Summary`, `Message`, `Attachment` and the rest are the connector's own types at the Gmail edge; the tools convert them into their own answer types, and `D10-tools` owns every answer's shape, `date`'s encoding included.
- **400 on a read or delete that names an id is not found; 400 on `drafts.send` and on opening an upload is `ErrProvider`.** Only status classifies an answer, as in gdrive, except that the client knows which request it sent: a 404 or 400 to `messages.get`, `messages.attachments.get`, `threads.get`, `drafts.get` or `drafts.delete` is `ErrNotFound`, a 404 to `drafts.send` or to opening an upload is `ErrNotFound`, and a 400 to either of those two is `ErrProvider` (see the decision on `drafts.send` above). 403 is `ErrProvider`: a missing Gmail scope is already `reconnect` at connections (decision 14), and Gmail's other 403s are rate limits.
- **401 is `ErrUnauthorized`**, which consumers answer `reconnect` (the brief's mapping), a departure from gdrive's `ErrProvider`.
- **The body skips parts with a filename** and needs no charset table (observed conversion to UTF-8); CRLF becomes LF so a plain body answers the text as written.
- **An attachment's content type is kept when it parses.** The part's `Content-Type` carries the media type and parameters `mime.ParseMediaType` reads from the stored content type, after CR and LF are replaced by spaces; a value that does not parse, or is empty, becomes `application/octet-stream`, so a malformed content type never reaches Gmail and never fails a push.
- **Fixed boundary, no randomness in the builder**; base64 text (root gate finding: quoted-printable text mode does not round-trip a lone CR; base64 does, with the stdlib alone, and the decoded text is what any mail client shows); base64 attachments in 76-character lines; no `Date` or `Message-ID` header.
- **`Size` is exact**, which subsumes decision 7's estimate of four thirds plus headers and text.
- **The read bound** is the encoded length of the limit, `4 × ⌈limit ÷ 3⌉`, plus 65,536 bytes of envelope (ids, labels, snippet), so a pull never holds much more than decision 12's four thirds.
- **`CreateDraft` uses the JSON `raw` form** rather than an upload: decision 4 names the resumable upload for `drafts.update` only, and a composed draft carries no attachment.
- **`gmail.called` is emitted by this package** through the writer in `Config`, as gdrive's client emits `drive.called`; `D09-trail` names it among the trail's events. Endpoint names are the API's method names, plus `upload.chunk` for each piece.
- **`PushChunk` lives here**, 8 MiB, a multiple of the 256 KiB Google's resumable protocol asks of every piece but the last.
- **No retry and no redirect policy of its own**: each request is sent once (decision 11: no retries), redirects left to `HTTP`.
- **Rejected** (decisions document): Google's Go client library; parsing MIME from raw text (only Gmail's `full` tree is read); Gmail's `attachmentId` as an id.

## Consumer tasks

`cli.Run` builds `gc := gmail.NewClient(gmail.Config{HTTP: hc, Telemetry: w})`. A read tool, holding the caller's access token `tok` obtained as `D10-tools` states, calls `gc.Labels(ctx, tok)`, `gc.Search(ctx, tok, gmail.Query{Text: q, Label: l, Page: p})`, `gc.Thread(ctx, tok, thread, p)` or `gc.Show(ctx, tok, id)`, and answers from the `[]gmail.Label`, the `gmail.Page`'s `Messages` and `Next`, or the `gmail.Message` in the shapes `D10-tools` declares. A pull's validation calls `gc.Show` and finds the `gmail.Attachment` whose `ID` is the part id, checking its `Bytes`, or `gc.Stat` and checks `SizeEstimate`; its background work calls `c, err := gc.Attachment(ctx, tok.AccessToken, m, part, limit)` or `gc.Raw(ctx, tok.AccessToken, m, limit)` and hands `c.Reader` to `artifacts.Client.Put`. `compose` calls `gc.Show` for a reply's headers, builds `o := gmail.Build(gmail.Composition{From: mail.Address{Address: tok.Account}, To: to, Subject: s, Text: body, InReplyTo: orig.MessageID, References: refs})` and calls `gc.CreateDraft(ctx, tok.AccessToken, orig.Thread, o)`, storing the `gmail.Draft`'s `ID`, `Message` and `Thread`. A push checks `gmail.Build(c).Size() <= gmail.UploadCap` with the new part's `Bytes` from `Head`, then builds the composition with each `gmail.Part{Name, ContentType, Bytes, Open: func() (io.ReadCloser, error) { _, r, err := ac.Get(ctx, path); return r, err }}` and calls `gc.UpdateDraft(ctx, tok.AccessToken, d.GmailDraft, d.Thread, gmail.Build(c))`, storing the answered `Message` and `Thread`. `send` calls `gc.SendDraft`, `discard` `gc.DeleteDraft`, and a reconciling tool `gc.GetDraft`, then on `ErrNotFound` `gc.ThreadStats(ctx, tok.AccessToken, d.Thread)` of the stored thread, as `D07-drafts` states. Each maps `errors.Is(err, gmail.ErrNotFound)`, `ErrUnauthorized`, `ErrTooLarge`, `ErrBadPage`, `ErrPartSize` and `ErrProvider` to its refusal word or failure reason. A test builds a `telemetry.Writer` over a capturing sink with a fixed clock, a fake Gmail on `httptest.Server` answering the JSON it chooses, and a `Client` with `BaseURL` set to it, and checks each request's method, path, query and headers, each reduction, each error kind and one `gmail.called` per request; a builder test calls `Build`, reads the `Outgoing` to the end, compares the count with `Size`, and parses the bytes with `net/mail` and `mime/multipart`.
