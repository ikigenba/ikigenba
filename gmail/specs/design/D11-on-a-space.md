# D11-on-a-space

What gmail contributes when it runs on a space and in a sandbox, which entries of the services file it uses, the trust it places in the identity it is sent (decision 21), and which of the contract's guarantees the delivery's sandbox check (decision 19) and the `us` smoke test (decision 20) stand on. It follows gdrive's on-a-space design. The guarantee such documents end with, that no secret reaches the trail, the bus, a page, a tool answer or standard error, is `D09-trail`'s here, as it is gdrive's trail document's there.

## What ships

The release holds four members of gmail's directory: `bin/gmail`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `brand-gmail`, human-authored. No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The manifest (`D02-cli`) carries what a space asks of it: `guests = false`, so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); `mcp = true`, so the gateway offers the thirteen tools; `secrets = []`, since the Google token comes from connections over its socket; `[env]` with the seven settings' defaults; `[database]` naming `state/gmail.db`; `[resources]` with `memory_max = "256M"` (decision 12); and `[home]` in the `core` group, so home lists gmail under Core Services. The fragment answers the bus's two paths 404 at the public name. `DRAIN_SECONDS` is the space's.

## On a space

gmail on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/gmail.sock`), `/var/opt/ikigenba/gmail` as its working directory, its settings from `/etc/opt/ikigenba/gmail/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses: `artifacts`, whose socket the artifacts client puts and gets over and whose `URL` the pages build artifact addresses from (`D08-pages`); `connections`, whose socket the connections client fetches the caller's Google token over and whose `URL` the connect page is built from (`D10-tools`); `telemetry` and `events`, appkit's sinks'; and `auth`, for the banner's addresses. A missing file or entry never refuses the start (`D03-serve`); a call that needs a missing client is refused (the word is `D10-tools`') and records nothing; with no `connections` entry no token can be had, so no request goes to Gmail either and no `sibling.called` or `gmail.called` is recorded for it.

## In a sandbox

The sandbox builds gmail from the worktree, gives it the seven settings from the manifest's `[env]`, puts every request through auth's `/check`, and includes `etc/nginx.conf` in gmail's server. Its state is `<data>/apps/gmail/state/`. An agent is curl on the developer's machine with the stored token, at `http://gmail.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools; the Google token comes from the sandbox's connections, whose grant the check seeds and removes.

## Trust

gmail believes the identity it is sent, as every sibling does (decision 21, as gdrive decision 17 states it): `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx or the gateway set them on a request to its socket. It checks them against nothing, asks auth nothing, and sends the same three on to connections when it fetches a token and to artifacts when it puts, heads or reads an artifact, through appkit's sibling clients, so connections hands out that user's token and artifacts records that user as owner and reads as that user. A transfer's work after its call has returned runs as the same caller, rebuilt from what the record keeps (`D06-transfers`). A process that can reach gmail's socket can therefore name any user, read that user's mail, move that user's attachments and send mail as that user; every service on the host is trusted, and the gateway and nginx are the only doors from outside.

## Recorded decisions

- The secrecy guarantee is `D09-trail`'s, as in gdrive.
- A missing `connections` entry refuses any tool that needs a token; a missing `artifacts` entry refuses `pull` and `push` before any transfer is recorded, gdrive's precedent (its orchestrator P3). This document states only what the run shows (a refusal, no request, no record, no `sibling.called` or `gmail.called`); the refusal's word, `unavailable` in gdrive, is `D10-tools`' to state. Whether a `pull` validates its message at Gmail before it finds artifacts missing is `D06-transfers`' choice; no requirement here constrains it. `D06-transfers` and `D10-tools` state the same at their own seams.
- `send` and `discard` are the first tools on the suite that act outward as the caller (real mail is sent); trust is unchanged by that, and the intent states it as gdrive's.
- The upload cap, the link forms and the scopes are not proved here; each is settled where `D05-gmail`, `D07-drafts` and `D01-layout-and-run-seam` record it.

## Consumer tasks

An operator installs the release; opsctl reads `etc/manifest.toml`, writes the seven settings and `DRAIN_SECONDS` into `/etc/opt/ikigenba/gmail/env`, drops `etc/nginx.conf` into gmail's server, adds gmail's entry to the services file and starts the unit. A test builds a `cli.Process` with a temporary `Dir`, a services file whose entries `artifacts` and `connections` name Unix sockets on which loopback fakes listen and record every request's headers, or one lacking either entry, an `HTTP` whose transport is a fake Gmail, capturing sinks, and its own `Now`, `After` and `Rand`; it calls `labels`, `compose`, `send`, `pull` and `push` through `mcp.Client` with identity headers of its choosing, waits for the transfers to end, cancels, and compares the headers the fakes recorded, the requests the transport was given and the stored records.
