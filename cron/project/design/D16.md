# Decision 16 — Correlation adoption and the tick root: every scheduled chain begins with a minted id and a `root` record

> **⛔ EXTERNAL ORDERING — operator-sequenced, not built by any cron phase.**
> This Decision consumes the shared leaf package `eventplane/correlation`, the
> revised `eventplane/outbox` (a `correlation_id` column and envelope field,
> `Append(ctx, tx, ev)`, `AddCorrelationIDSQL`), and the revised `appkit`
> chassis (correlation middleware, the `appkit/telemetry` recorder and its
> `Record`/`Kind`/`KindRoot` surface, request and lifecycle records, the
> publish hop). Those surfaces are owned by the `appkit` and `eventplane`
> workspaces and are consumed here as fixed contracts — see
> `project/research/research.md` for the exact footprint. **appkit and
> eventplane must be BUILT before cron's adoption phase runs**; until they land
> it cannot compile. cron's nginx-fragment phase has no such dependency and can
> run at any time.

**Problem.** A forensic agent must be able to reconstruct any sequence of
events in the suite. That rests on one id per causal chain, propagated verbatim
on every hop — and on every chain *having a beginning that can be found*. cron
is where the suite's scheduled work begins, and it fails both halves today.

1. **The edge.** nginx is cron's sole trust boundary. The dashboard's
   introspection endpoints mint the chain id and return it on the auth
   subrequest, but a header nginx does not explicitly capture and re-set never
   reaches the loopback service — so every crontab CRUD call would arrive
   uncorrelated and the chassis would mint a fresh id per hop. Worse, the
   fragment's ungated PRM location would forward whatever `X-Correlation-Id` a
   public caller chose to send.

2. **The tick has no root.** The tick worker is a `Spec.Workers` goroutine. No
   chassis middleware ever runs for it and no request context ever reaches it,
   so `correlation.FromContext` on its context returns `""` and
   `outbox.Append` — which never mints — would store `''`. Every scheduled
   chain in the suite would then be **rootless**: a consumer waking on a tick
   would find no id on the envelope, the chassis would mint one on the consumer
   side (appkit's consumer-arm root), and the trail would begin *at the
   consumer*, with nothing tying it back to which schedule fired, or when, or
   whether it fired at all. The one thing a forensic agent most wants to ask of
   scheduled work — "what did last night's `bill-sweep` set off?" — would have
   no answer. And a `context.Background()` at the `Append` call site compiles,
   appends a perfectly valid row, and produces exactly this outcome with
   nothing failing.

cron is the outermost cause of its own work: nothing upstream of a wall-clock
minute boundary exists to inherit an id from, and a crontab row is the
*schedule*, not the firing — reused every matching minute, so its identity
cannot distinguish Tuesday's tick from Wednesday's. The suite standard's
durable-root reuse rule therefore does not apply and its "mint fresh" case
does, which is exactly what `project/design/D14.md` at the repo root means by "a trigger
firing on the user's behalf" (`research.md` §2).

Everything else cron needs arrives by recompiling against the chassis:
`request` records for the seven crontab tools and the standard tools,
`lifecycle` `start`/`stop`, the `publish` hop at append, and read-or-mint
correlation middleware on the loopback server. cron writes no inbound
instrumentation.

**Decision.**

### (a) The fragment carries the chain id across the trust boundary

`cron/etc/nginx.conf` gains exactly two kinds of line, and removes none.

**Every gated location captures the introspection-minted id and forwards it,
overwriting anything the client sent.** The dashboard's `/_authn` (bearer) and
`/_session-authn` (cookie) hooks both return `X-Correlation-Id` on an allow, so
all three gated locations take the same treatment, with **service-prefixed**
variable names so they stay unique inside the one apex `server` block every
fragment is included into:

| location | gate | capture variable |
|---|---|---|
| `location /srv/cron/` (prefix) | `/_authn` | `$cron_correlation` |
| `location = /srv/cron/` (landing) | `/_session-authn` | `$cron_session_correlation` |
| `location /srv/cron/static/` (assets) | `/_session-authn` | `$cron_static_correlation` |

each as:

```
auth_request_set $cron_correlation $upstream_http_x_correlation_id;
proxy_set_header X-Correlation-Id $cron_correlation;
```

The identity-hygiene property that already protects `X-Owner-*` extends
unchanged to this header: nginx does not pass an inbound client header as a
proxy header unless explicitly set, and the last `proxy_set_header` for a name
wins — so a single set from the auth-subrequest variable **replaces** any
`X-Correlation-Id` a client tried to smuggle. The static tier is included even
though it forwards no owner identity, because an asset fetch is a real hop of
the page load's chain and correlating it costs one variable; the correlation id
is not identity and carries no authority.

**The one ungated proxying location strips the header:**

```
proxy_set_header X-Correlation-Id "";
```

on `location = /srv/cron/.well-known/oauth-protected-resource`. nginx omits a
header set to the empty string entirely, so the chassis sees no inbound id and
mints one — the correct outcome for a request with no authenticated cause. A
public caller can therefore never inject an id anywhere in cron's fragment.

`location = /srv/cron/feed` (`return 404;`) and `location @cron_authn_500`
proxy nothing and are untouched: the event plane stays unreachable through
nginx exactly as before.

### (b) The tick mints its root — in `fireOne`, once per firing

The mint goes at the **narrowest seam that corresponds one-to-one with an
emitted event**: `tick.Worker.fireOne`, which is the only place a tick event is
appended and is reached exactly once per `(schedule, slot)` that actually
fires. `Run` and `Fire` are both too wide — a scan may fire several independent
schedules in one minute, and those are separate chains that must not share an
id.

cron does **not** hand-roll mint + install + record. The chassis owns that
idiom (`Recorder.StartRoot`, which mints a fresh id ignoring any ambient one,
installs it on the returned context, and emits the `root` record — nil-safe on
a nil recorder, so correlation behavior is identical whether telemetry is on or
off):

```go
// internal/tick — fireOne, revised shape (illustrative)
func (w *Worker) fireOne(ctx context.Context, name string, slot, firedAt time.Time, slotStr string) error {
    ev, err := event.Build(name, slot, firedAt)
    if err != nil {
        return err
    }
    // cron is the outermost cause of this chain. StartRoot mints, installs the
    // id on ctx, and emits the root record. op is the canonical routing key of
    // the event about to be published.
    ctx, _ = w.rec.StartRoot(ctx, "cron:"+event.Kind+event.Subject(name), nil)

    tx, err := w.db.BeginTx(ctx, nil)
    // …unchanged: UPDATE crontab SET last_slot …; a 0-row result returns
    //   without appending…
    if err := w.ob.Append(ctx, tx, ev); err != nil {
        return err
    }
    return tx.Commit()
}
```

Three properties are load-bearing:

- **The root is started before `Append`,** so the minted id is on the context
  `outbox.Append` reads (`correlation.FromContext`) and lands on the outbox row
  and, from there, on the wire envelope every consumer sees. The consumer arm
  of appkit's root rule then never fires for a tick — the envelope is already
  correlated, so the chain continues rather than restarting.
- **`StartRoot`, not `StartChain`.** The chassis's choice rule is `StartRoot`
  when the work has no cause outside itself. A tick has none: nothing upstream
  of a minute boundary caused it. `StartChain` would adopt whatever id the
  worker's long-lived serve context happened to carry, fusing every tick for
  the process's lifetime into one chain.
- **One `StartRoot` per firing, not per scan.** appkit states the helper as one
  call per *cycle*; for cron the cycle is **one schedule's firing**, not the
  minute scan — which the chassis's own `op` example (`cron:tick/<name>`)
  already implies, since a per-scan call could not name a schedule. Two
  schedules matching the same minute are two independent chains and get two
  ids.

**Recorded trade-off.** `StartRoot` emits the root record when it is called,
before the transaction commits, so the rare defensive path where `fireOne`'s
guarded `UPDATE` affects 0 rows (another writer took the slot) leaves a root
record whose event was never published. This is accepted: cron is single-writer
through the chassis DB handle, and the ordinary repeat — a second `Fire` for a
slot already recorded — is caught by the in-scan `last_slot` guard *before*
`fireOne` is reached, so no root is emitted for it. A root with no accompanying
`publish` record is also legible on its own terms: it says a firing was
attempted and lost the slot race. Reordering the record after `Commit` would
mean re-implementing the chassis idiom inside cron, which is the drift the
helper exists to end.

Nothing else in the tick seam moves: the same per-schedule transaction Appends
the event and advances `last_slot` atomically, `Ring()` still fires once after
the scan, the payload shape `{name, scheduled_for, fired_at}` is unchanged, and
the id rides the **envelope**, never the payload — cron adds no payload field
for it, and the superseded payload-field convention in
`project/design/D14.md` at the repo root is not adopted.

### (c) The `op`, and how the recorder reaches the worker

**`op` is the canonical routing key of the event the tick publishes** —
`cron:tick/<name>` — so the root record and the `publish` record the chassis
emits for the same append name the same thing, and a forensic search by op
finds both ends of the seam. cron composes it from `event.Kind` and
`event.Subject(name)` rather than declaring a second format string, so the root
record and the emitted event cannot drift apart. The crontab `name` CHECK
(non-empty `[a-z0-9-]+`) makes the key well-formed by construction. `detail` is
nil: the firing's particulars live in the event payload and the `publish`
record, and a root record's job is to *exist and be findable*, not to duplicate
them. cron passes no actor — a tick has no owner and no client, and inventing
one would make the trail lie about who did something.

**The recorder reaches the worker the same way the store does.** `tick.Worker`
gains a `rec *telemetry.Recorder` field set by `tick.New`. cron's composition
root already captures `store` in `Spec.Handlers(rt)` and consumes it in
`Spec.Producer`; the recorder is captured the same way — `rt.Recorder()`, the
chassis accessor that returns the serve-wired recorder (nil when telemetry is
disabled) — and passed to `tick.New` alongside the outbox. Every `Recorder`
method is nil-safe, so `tick` carries no nil checks and no error handling, and
**telemetry being unreachable can never delay or fail a tick**.

cron does **not** construct a `telemetry.Recorder` of its own: a second
recorder would mean a second ring, a second flush loop, and a second reading of
the suite-wide config.

### (d) The outbox schema movement

eventplane's `SchemaSQL` gains `correlation_id TEXT NOT NULL DEFAULT ''` as its
**last** column, and eventplane owns the upgrade text too —
`outbox.AddCorrelationIDSQL`, an `ALTER TABLE outbox ADD COLUMN`. eventplane
applies nothing itself; each service owns its migration runner.

Committed migrations are immutable and the runner silently skips an edited
body, so cron appends **one new timestamped migration** minted with
`bin/create-migration cron outbox_correlation` — never a hand-picked number —
whose body is `outbox.AddCorrelationIDSQL` verbatim. The frozen
`003_outbox.sql` and the D14 `outbox_routing` migration are **not** touched.

This is **not** the drop-and-recreate D14 used for the kind/subject cutover:
`ADD COLUMN` rewrites no rows, back-fills existing rows with `''`, and leaves
both the `seq` values and SQLite's `sqlite_sequence` high-water mark untouched,
so no consumer's cursor moves and D14's `AUTOINCREMENT` guarantee is
undisturbed. Consequently the DDL drift guard in
`internal/db/migrations_outbox_test.go` stays pointed at the `outbox_routing`
migration — the newest one carrying a full `outbox.SchemaSQL` body — because
the new migration carries an `ALTER`, not the create text. Both spellings must
nonetheless agree: a fresh database built by `SchemaSQL` and an upgraded one
built by create-then-`ALTER` end up column-for-column identical, which is why
the column is declared last.

### (e) Deliberate non-changes

- **`etc/manifest.env` gains no key.** `TELEMETRY_INGEST_URL` and
  `TELEMETRY_ENABLED` are unprefixed, suite-wide, and default correctly
  (`research.md` §6). One suite-wide address does not get fifteen homes.
- **No outbound HTTP client migration.** cron makes no outbound calls.
- **No MCP surface change.** No crontab tool declares `SensitiveParams`:
  `create`/`update`/`delete`/`get`/`list` take a schedule name and a cron
  expression — no credential, no token, no secret.
- **No product change.** What a cron user gains — a scheduled chain that can be
  reconstructed end to end — is delivered by the *telemetry* service's MCP
  surface and is that product's promise to make. cron's contribution is
  mechanism, and a success criterion phrased over cron alone could not be
  confirmed against cron alone.
- **cron mints only at the tick.** Inbound MCP and web requests are the
  chassis's read-or-mint, untouched here.

**Rejected.**
- **Minting once per `Fire` (per tick scan)** — every schedule that matches the
  same minute would share one correlation id, fusing independent chains. A
  forensic agent asking what `bill-sweep` set off would get `nightly`'s work
  too, and the fusion would be invisible in the data.
- **Minting in `Run`** — worse still: one id for the whole process lifetime.
- **Minting in `Fire` per matching row, before `fireOne`** — mints for rows
  that then lose the `last_slot` race and never emit, leaving minted ids with
  no event. The seam has to be the one that also decides whether an event
  exists.
- **Hand-rolling mint + install + record after `Commit` instead of calling
  `StartRoot`** — this was the first shape considered, because it makes a
  phantom root impossible on the 0-row race. It loses: cron would re-implement
  the exact five-line idiom the chassis helper exists to stop nine services
  copying, and would drift from them on op format and on when the id is
  installed. The race is the defensive branch of a single-writer service, the
  ordinary repeat is already caught before `fireOne`, and a root with no
  publish is legible rather than false.
- **`StartChain` instead of `StartRoot`** — it adopts an ambient id when the
  context carries one. The tick worker's context is the long-lived serve
  context; if anything ever put an id on it, every tick for the process's
  lifetime would fuse into one chain. A tick has no cause outside itself, which
  is precisely the chassis's stated rule for `StartRoot`.
- **Reusing the crontab row's identity (or `<name>@<slot>`) as the correlation
  id** — the durable-root rule wants a durable entity that already carries a
  *suite ULID*; a schedule name is neither opaque nor unique per firing, and a
  composite key is not a ULID and would not pass `correlation.Valid`.
- **Letting appkit's consumer-arm root cover ticks** — it mints at the
  *consumer*, so the chain would begin one hop late and the tick itself would
  be outside it. The whole value of a cron root is that the trail starts at the
  firing.
- **Putting `correlation_id` in the tick payload** — the superseded
  convention. The envelope addresses; the payload stays the detail record, and
  duplicating the id invites the two to diverge.
- **cron constructing its own `telemetry.Recorder`** — a second ring, a second
  flush loop, and a second reading of the suite-wide config, all to avoid one
  accessor on the chassis runtime.
- **Filling the root record's `actor` with the schedule's creator** — cron does
  not store one, and inventing an actor for machine-originated work makes an
  audit trail lie about who did something.
- **Editing a committed outbox migration in place** — the runner keys on the
  version and skips an edited body, so the change would reach new databases and
  not existing ones.

**Verification.** The first two ids pin the **fragment**, following D4's
established practice in this workspace: a test reads `cron/etc/nginx.conf` from
disk and asserts over its content, in the same `go test ./...` run (nginx is not
run by the suite).

- R-BBON-OZTN — **every gated location captures and forwards the chain id.**
  All three gated locations in `cron/etc/nginx.conf` carry both halves with
  service-prefixed variables: the bearer prefix `location /srv/cron/` has
  `auth_request_set $cron_correlation $upstream_http_x_correlation_id;` and
  `proxy_set_header X-Correlation-Id $cron_correlation;`; the session
  exact-match `location = /srv/cron/` has the same pair on
  `$cron_session_correlation`; and `location /srv/cron/static/` has it on
  `$cron_static_correlation`. A fragment that captures without forwarding (or
  captures on only the bearer tier, leaving a logged-in human's page load and
  its assets uncorrelated) fails this. Its existing four `X-Owner-*`
  captures/forwards per identity-forwarding location, `X-Client-Id`, the
  `= /srv/cron/feed` 404, and the `@cron_authn_500` re-emit all remain.
- R-BE4G-GJB1 — **no location forwards a client-supplied id.** The ungated
  `location = /srv/cron/.well-known/oauth-protected-resource` carries
  `proxy_set_header X-Correlation-Id "";` (nginx omits an empty-valued header,
  so the chassis mints for itself), **and** the whole file carries exactly
  **four** `proxy_set_header X-Correlation-Id` lines — the three
  auth-subrequest-sourced ones plus this strip. A fragment that adds a
  proxying location without an `X-Correlation-Id` set of its own, leaving the
  client's inbound value to reach the service, fails the count.

The four remaining ids are the
behaviors **cron itself** proves. All run over **real substrates**: the tick
worker fires against a real SQLite database built by cron's full embedded
migration set through the appkit runner, and outbox rows are read back by SQL.
They do not restate chassis coverage — appkit proves read-or-mint middleware,
the recorder's ring/batching/ingest, and the `publish` hop; eventplane proves
the column, the upgrade text, and the envelope — these prove that *cron's own*
migration set applies the upgrade and that *cron's own* firing seam mints,
propagates, and roots correctly.

- R-2V3L-RE05 — cron's migration set actually applies the upgrade: applying
  `db.FS` through the appkit runner to a fresh real SQLite database yields an
  `outbox` table carrying a `correlation_id` column that is `TEXT`, `NOT NULL`,
  and defaults to `''` (`PRAGMA table_info`), and the resulting column list is
  **identical, in order,** to the one `outbox.SchemaSQL` alone produces on a
  separate fresh database. A build that adds the column to `SchemaSQL` but
  forgets cron's own migration fails this — the failure that would make every
  tick's `Append` error at runtime.
- R-2WBI-55QU — every published tick carries a freshly minted, well-formed root
  id: after `Fire` over two schedules (`nightly`, `bill-sweep`) whose exprs
  match the slot, the two outbox rows read back by SQL each carry a
  `correlation_id` that is **non-empty** and passes `correlation.Valid` (26
  characters, Crockford alphabet — an RFC 4648 id containing `I`/`L`/`O`/`U`,
  or any id of another length, fails). A build that leaves the tick context
  bare — so `Append` stores `''` — fails this.
- R-2XJE-IXHJ — a correlation id names one firing and no other: the two rows
  from the same `Fire` carry **different** `correlation_id` values (two
  schedules firing in one minute are two chains, not one), and a subsequent
  `Fire` for a later slot appends a row whose id differs from **both**. A build
  that mints once per scan, once per worker, or once per process passes
  R-2WBI-55QU and fails this.
- R-2YRA-WP88 — every firing has exactly one queryable root, and only a real
  firing does: driving `Fire` for schedule `bill-sweep` with the worker wired
  to an inspectable recorder yields **exactly one** record with `kind` `root`
  and `op` exactly `cron:tick/bill-sweep`, whose `correlation_id` **equals the
  `correlation_id` on that schedule's outbox row** read back by SQL — the tie
  that makes the chain queryable from its root. A second `Fire` for the **same**
  slot appends **zero** further outbox rows and emits **zero** further root
  records (the in-scan `last_slot` guard returns before `fireOne` is reached),
  so the at-most-once-per-`(schedule, slot)` guarantee covers roots as well as
  events. A build that starts the root in `Fire` — outside that guard — fails
  the second half.
