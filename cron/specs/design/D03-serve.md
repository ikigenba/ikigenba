# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail cron records of itself from its start to its stop, the bus events it holds, delivers or drops when it stops, and the rules its handler keeps on every route — the identity gate, the request's id, the request's event cause, the request's two events, and the route table that sends each path to the pages, the shared files, `/mcp` or the event bus's two paths. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run`, `settings.Read` with its refusal, which `Run` writes before anything here happens, the display string, and the database path `state/cron.db` under `Dir`; `D02-cli` declares the exit codes and decides that an empty `Args` means serve. This document declares `internal/server` and `internal/web`. `D04-store` declares the store `Run` builds over the database; `D05-scheduler` the scheduler `Run` starts before it is ready and stops at the signal; `D06-pages` what is answered at `/`, at `/about` and at a path that is not a page; `D07-trail` the declarations the emitter is built with and every trigger event; `D08-tools` the tools at `/mcp`. appkit's `db` package owns opening the database and bringing it up to date, its `telemetry` package the writer and the request middleware, its `identity` package the gate, its `page` package the shared files, its `mcp` package the endpoint, and its `events` package the emitter, the cause middleware and the two handlers the events app reaches cron at; this document wires them and restates none of their contracts.

## The terms cron serves on

cron serves on the platform's common terms. It serves only on a listening socket it inherits and never opens one of its own; on a host that is `/run/ikigenba/cron.sock`, held by `ikigenba-cron.socket` beside the `Type=notify` `ikigenba-cron.service`. A deploy restarts the service alone, so the socket and the connections queued on it outlive every restart; that a restart refuses no request is the socket's doing, and cron's part is to finish what it accepted and leave the socket where systemd put it.

cron takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment once it has taken the socket, as that manual page recommends. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket `NOTIFY_SOCKET` names, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace. Taking descriptor 3 in the binary is `net.FileListener`, which, as Go's `net` documentation of `FileListener` and `UnixListener.SetUnlinkOnClose` states, leaves the socket's path in place when the listener is closed.

The suite is a closed system: cron trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway calling it at its socket to have forwarded them. Every request has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it, 32 lowercase hexadecimal digits from `Process.Rand`. `Process.Rand` is also where the store draws trigger ids, the scheduler each fire's request id and the emitter bus event ids, so `Run` hands all four one reader that never lets two reads of `Process.Rand` overlap.

The events app reaches cron at its socket on two paths of its own: `/events`, where it would deliver events cron accepts, and `/declarations`, where it reads what cron emits and accepts. cron accepts no event, so it mounts appkit's `events.DeliveryHandler` with no handlers, and `events.DeclarationsHandler` over its emitter, built with the five declarations of `trail.Emits()`. appkit answers that declaration with the emissions sorted by name and each one's attributes in the order declared, so cron's `/declarations` body lists `created`, `deleted`, `fired`, `paused` and `resumed`, `fired` with `trigger`, `when`, `scheduled`; the serve story's quoted body, in declaration order with the fired attributes alphabetical, is not what appkit writes, and the body below is the contract. The events app calls without a user, so these two paths sit outside the identity gate, inside the request middleware like every path; nginx never passes them on, since cron's fragment answers both 404 at its public name (`D02-cli`). A tool call made in reaction to an event names it with `X-Event-Cause` and `X-Event-Depth`; appkit's `events.Middleware` puts the pair on the request's context when both are well formed and ignores them as a whole otherwise, and the bus event the call emits carries it.

cron's standard error holds only trouble: a start it refuses, appkit's one warning line over a database a newer cron upgraded, a socket it cannot take, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off, the lines appkit's writer writes for an event it could not deliver, and the lines appkit's emitter writes, `cron: lost event: ` and the event's JSON, for a bus event it dropped. A request answered with any status, the missing-identity 500 and the database's 503 included, and a fire that did not happen because the database could not be reached (`D05-scheduler`) are handled, recorded in the trail or answered to the caller, and earn no line. So the handler has no stream, and while telemetry and the event bus take every event and the clock reads a year 0 through 9999, a running cron writes nothing to either stream.

## Checking the start

With `Args` empty, `Run` checks, in this order: `DRAIN_SECONDS`, through `settings.Read` (`D01-layout-and-run-seam` states the refusal); then whether a socket was passed in; and only then opens the database. A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one; anything else is no socket passed in, and a count above one is a unit cron will not guess about. Both are usage errors, exit 2, with the detail line saying how to run cron, and neither takes the descriptor, unsets a variable, creates or opens anything under `Process.Dir`, serves, tells systemd anything, or records an event.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv` and takes descriptor 3 as its listener, through `Process.Inherit`. A descriptor that cannot be made into a listener is trouble on the host: `cron: ` and the error, exit 1.

## The database, the scheduler and readiness

`Run` opens the database with appkit's `db.Open` at `state/cron.db` under `Process.Dir`, with the root package's `cron.Migrations()`, `Process.Now`, the service `pages.ServiceName`, and a writer for appkit's warning that reaches `Process.Stderr` in one write. `db.Open` creates `state/` and the database on a first start and applies every migration the database has not had. Every `db.Open` failure is `cron: cannot open database state/cron.db: ` and the error's text with its newlines made spaces, exit 1, before anything is served, before systemd is told anything and before any event is recorded; the path is always this relative spelling, whatever `Dir` holds. A missing database is not this error: it is a first start. A regular file named `state` is one, and so is a file at `state/cron.db` that is not a database.

A database that records a migration this cron does not carry is not refused: data never rolls back, so older code runs on newer data. appkit's `db.Open` applies nothing to it and writes one warning line, beginning with the service name it was given and naming the lowest version this cron does not carry; `Run` passes that line to `Process.Stderr` in one write, before `READY=1`, and the trail records nothing about it. cron states nothing about the line's wording: a test compares what `Run` wrote with what its own `db.Open` call, given the same service name and a buffer, writes over the same database.

Then `Run` builds the store over the handle (`D04-store`), the run's writer with appkit's `telemetry.New` (service `pages.ServiceName`, `Process.Version`, `Process.Sink`, the guarded `Process.Stderr`, `Process.Now`, `Process.Sleep`, the guarded `Process.Rand`), and the run's emitter with appkit's `events.New` (service `pages.ServiceName`, `Process.EventSink`, the same guarded stream and random source, `Process.Now`, `Process.Sleep`, the run's writer as its `Telemetry`, `trail.Emits()` as its declarations, and the default queue capacity and retry window), and starts the scheduler with `scheduler.Start` over the store, the emitter, the writer, `Process.Now`, `Process.After` and the guarded random source. `Start` works out every active trigger's next slot from the moment cron starts and fires nothing (`D05-scheduler`), so the slots that passed while no cron ran are gone. `Run` calls `Process.MCP` once with the run's writer and builds the handler with `web.Handler` over `Process.Banner`, that server, the value `LookupEnv` gave for `IKIGENBA_SERVICES` (read once, here), the store, the scheduler, the writer and the emitter. Nothing about `IKIGENBA_SERVICES` or the file it names can stop a start.

A signal that arrives before `Run` has begun to report ready — during the open, or before `Run` was even called — is a stop, not a failure, so it is exit 0: `Run` sends no `READY=1`, accepts nothing, records neither `service.started` nor `service.stopping`, and returns. A `scheduler.Start` that fails with the context not done can only be a race with something outside cron over a database just opened; `Run` answers it with the database line, exit 1, and since no test can produce it through `Run`, it is stated here and not as a requirement.

The socket has been listening since systemd made it, so ready is true before the first `Accept`, and sending it first means a failure to send is reported before anything was served: `cron: ` and the error, exit 1. Once `READY=1` is sent, or there is no notification socket to send it to, and before any connection is accepted, `Run` calls `Writer.Ready`, so `service.started`, carrying `Process.Version`, is the first event of a run. With neither `IKIGENBA_COMMIT` nor `IKIGENBA_RELEASE` set the display string is empty, and cron starts and serves all the same.

## The trail of a run

Every event of the process goes through the run's writer: the handler's, the tools', the scheduler's and the emitter's `event.lost`. appkit's writer queues and returns, so neither readiness, nor any answer, nor any fire waits on telemetry; an event it cannot deliver goes to standard error as `cron: undelivered event: ` and the event's JSON, in the order recorded, and cron keeps serving. A test sees this at `Run` with a `Sink` whose `Deliver` fails, and in the binary by leaving `IKIGENBA_SERVICES` unset. That a telemetry installed after cron started is found without a restart is appkit's socket sink, which reads the services file afresh on every delivery; the same holds for the event bus's socket sink. Bus events go through the run's emitter, which also queues and returns; how it retries, and when it drops an event during the run, is `D07-trail`'s and appkit's. This design states what the emitter does at the stop, and the two lines and the one event a drop leaves: `cron: lost event: ` and the event's JSON on standard error, and `event.lost` in the trail, with `event`, the dropped event's id, and `cause`, its cause, under the dropped event's request id and user, as appkit's emitter records it.

This design assumes a clock that reads times in the UTC years 0 through 9999, the years an RFC 3339 time can spell; appkit's writer cannot encode an event stamped outside them, and what cron records under such a clock is not contract.

## Stopping

When `ctx` is done — in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the context's cause — `Run` at once stops the scheduler, so from the signal on no fire begins and no `last_fired` changes but by a fire already under way, which finishes (`D05-scheduler`): a slot that comes while cron drains is gone, and the next cron works out its triggers' next slots from its own start. It drains the server through `Serve`. Once every request has finished, it waits, within the same drain window, for the emitter to deliver the bus events it holds; then it shuts the writer down with the reason, the text of `context.Cause(ctx)`, which records `service.stopping` and delivers what is queued; then it shuts the emitter down, which drops any bus event still held, with its line and its `event.lost`. Last, it closes the database's handle.

That order is what the stopping stories show. With nothing pending the stop is immediate: `service.stopping` is delivered and cron exits 0 at once. A bus event the events app takes within the drain is delivered, and `service.stopping` follows it to telemetry as the last event. A bus event still not taken at the drain deadline leaves no time for anything: `service.stopping` is written to standard error as undelivered, then the drop's `cron: lost event: ` line, then its `event.lost` as undelivered, in that order, and cron exits 0, since a dropped bus event is not a request. So `service.stopping` is the last event telemetry receives, and the only events recorded after it are the `event.lost` of a bus event dropped when the drain ends and the `request.finished` of a request cut off at the deadline, both of which go to standard error or nowhere.

The **drain deadline** is `DRAIN_SECONDS`, as `settings.Read` returns it, in seconds, the longest `time.Duration` when that many seconds is longer, measured in real time from the cancellation: never through `Process.After` and never through `Process.Now` (`D01-layout-and-run-seam`), so a drain test runs with `DRAIN_SECONDS=1` and waits about a second. When the requests use the whole window, every event still queued, `service.stopping` included, is written to standard error before the stop line, which is always `Run`'s last; `Serve` cuts the remaining requests off only after its `stop` has returned, and ends their contexts, so the client's connection closes without the rest of its answer. `Run` returns less than a second after the deadline and says `cron: stopped with <n> requests unfinished` (`1 request` for one), exit 1. A cut-off request's `request.finished`, recorded after the deadline, is written out or not at all, never delivered, so telemetry's trail shows the cut-off request by its `request.started` alone.

## Serving and stopping the listener

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next cron — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then ends those requests' contexts, closes their connections without the rest of their responses, and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. `stop` is called once, when the drain is over, with a context that ends at the deadline. An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `cron: ` and the error as `Run`'s last line, exit 1. `Serve` gives its server an `ErrorLog` that goes nowhere, since Go's `net/http` documents that a nil one writes to the real standard error. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` because gosec `G112` demands it.

## The handler's routes

`web.Handler` is appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping, for the event bus's two paths, appkit's `events.DeliveryHandler(nil)` at exactly `/events` and `events.DeclarationsHandler(Config.Events, nil)` at exactly `/declarations`, and for every other path appkit's `events.Middleware`, wrapping `identity.Require`, wrapping the route table; so every request records its two events, the two bus paths answer the events app whether or not a user is named, and any other request without `X-User-Id` is answered 500 with `identity.MissingBody` whatever its path or method — never 404 or 405, never 503, and no page, no tool and no database read for it. Routing is on the request's `URL.Path` as `net/http` decodes it, compared exactly, and never redirects. Every path falls to exactly one route:

- exactly `/events` and exactly `/declarations`: appkit's two bus handlers, every method, with or without identity.
- an **appkit path**, beginning `/_appkit/`: appkit's `page.Static()`, unchanged; what it answers is `D06-pages`'.
- exactly `/mcp`: `Config.MCP`, with the seven tools registered on it by `tools.Register` once, when the handler is built (`D08-tools`), whatever the `Host` header says, so the gateway's `Host: backend` is answered as nginx's is.
- every other path, `/` and `/about` included: `pages.Handler` over the template set `pages.Load` returns, which answers the landing page, the about screen and, for every path that is not a page, the not-found page (`D06-pages`).

cron calls no sibling while serving a request: the events a request causes go to telemetry and the bus apart from it, and no answer waits for them. A request to a page, a shared file, a bus path or a path that does not exist records nothing but its two request events; a tool call records what `D08-tools` and `D07-trail` state between them.

## Recorded decisions

- The stop's order — scheduler first; requests; the emitter's delivery within the window; `service.stopping`; then the emitter's drops — is chosen to give the stopping stories' order of lines, which puts `service.stopping` before a dropped bus event's line and its `event.lost`. Observed with appkit's writer and emitter (probes): an emitter's `Flush` with a context that ends while its sink fails returns at that end without dropping anything; a writer's `Shutdown` with that ended context then writes `service.stopping` as undelivered; and the emitter's `Shutdown` with it writes the lost line and records `event.lost`, which the shut-down writer writes as undelivered.
- `/` , `/about` and every path that is no route of its own go to the one pages handler, which owns the landing page, the about screen, their methods and the not-found page (`D06-pages`), so the not-found page and the pages share one template set.
- The `/declarations` body differs from the serve story's quoted one in its order only; the story's body cannot be produced through appkit's handler, whose ordering is observed, not documented.
- The drain deadline saturates at the longest `time.Duration`, since `DRAIN_SECONDS` has no upper limit (`D01-layout-and-run-seam`).

## Consumer tasks

`main` hands `cli.Run` the real process (`D01-layout-and-run-seam`). With `Args` empty, `Run` reads `settings.Read(p.LookupEnv)`, checks `LISTEN_PID` and `LISTEN_FDS`, calls `p.Unsetenv` for the three `LISTEN_*` names and `ln, err := p.Inherit(3)`, opens `d, err := db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "cron.db"), Migrations: cron.Migrations(), Now: p.Now, Service: pages.ServiceName, Stderr: stderr})`, builds `st := store.New(d, store.Config{Now: p.Now, Rand: rand})`, `w := telemetry.New(telemetry.Config{Service: pages.ServiceName, Version: p.Version, Sink: p.Sink, Stderr: stderr, Now: p.Now, Sleep: p.Sleep, Rand: rand})`, `em := events.New(events.Config{Service: pages.ServiceName, Sink: p.EventSink, Stderr: stderr, Now: p.Now, Sleep: p.Sleep, Rand: rand, Telemetry: w, Emits: trail.Emits()})`, `sch, err := scheduler.Start(ctx, scheduler.Config{Store: st, Events: em, Telemetry: w, Now: p.Now, After: p.After, Rand: rand})`, and `h := web.Handler(web.Config{Banner: p.Banner, MCP: p.MCP(w), ServicesPath: services, Store: st, Scheduler: sch, Telemetry: w, Events: em})`; sends `READY=1`, calls `w.Ready()`, and runs `err = server.Serve(ctx, ln, h, drain, stop)` with `stop` flushing `em`, then `w.Shutdown(c, context.Cause(ctx).Error())`, then `em.Shutdown(c)`, having called `sch.Stop()` the moment `ctx` was done; it answers a `*server.DrainError` with `cron: ` and its text, exit 1, closes `d`, and returns.

A test of `Run` builds a `cli.Process` with a temporary `Dir`, a `LookupEnv` over a map holding `LISTEN_PID` (the `Pid` it sets), `LISTEN_FDS` `1` and a `NOTIFY_SOCKET` it binds in a short temporary directory, an `Inherit` returning a Unix listener it bound, a `Now`, an `After` and a `Rand` it controls, a `Version` of its own, a `*telemetry.Capture` (or a sink that fails) as `Sink`, an `*events.Capture` (or a sink that fails, blocks or recovers) as `EventSink`, a `Banner` from `page.New` and an `MCP` that calls `mcp.NewServer` (having set `IKIGENBA_SERVICES` with `t.Setenv`). It runs `cli.Run` in a goroutine with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with `mcp.Client` and raw HTTP (`GET /declarations` without identity, `GET /` without `X-User-Id`), moves its clock and delivers on its timer, cancels with `errors.New("SIGTERM")`, and inspects the exit code, `Dir`, the captures in order and the streams. A drain test sets `DRAIN_SECONDS` to `1`, holds a request open with a handler-side wait it controls (a landing page whose client stops reading, or an `io.Pipe` body), and finds `cron: stopped with 1 request unfinished` last on `Stderr` within about two seconds. A test of `server.Serve` serves a handler of its own on a Unix listener, cancels, and checks the drain, the `stop` call and the `*server.DrainError`. A test of `web.Handler` builds a `web.Config` over its own store, scheduler, writer and emitter and a server from `mcp.NewServer`, and drives the handler with `httptest` and `mcp.Client`.
