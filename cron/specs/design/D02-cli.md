# D02-cli

cron as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, what `db status` reports of the database, and the three constants whose text is fixed here — the usage text, the manifest and the nginx fragment — with the two files under `etc/` that copy the last two. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, the display string `main` read, `cli.Run`, and the root package's `Etc` and `Migrations`; `D06-pages` declares `pages.Description`. When `Args` is empty cron serves, and everything from there is `D03-serve`'s.

The arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity; `manifest` writes `Manifest`; and `--help` writes `Usage`. The one two-word command, `db status`, reports the database's migrations (below). Any other `Args` is a usage error. The argument cron complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`; and otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `cron: `, and after exactly one empty line comes the hint to run `cron --help`, unprefixed because cron is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. The constant for 1 is named `ExitServerFailed`, as in the other apps, though it also covers a `db status` that fails. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a `DRAIN_SECONDS` that is not a positive whole number) exits 2, while trouble on the host once cron is past its checks (a database it cannot open, a drain that runs out) exits 1, and so does a `db status` whose database cannot be read. `Run` returns no other value.

## db status

`db status` is an operator's look at the database: which of the migrations the binary carries `state/cron.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status`, which cron calls with the path `state/cron.db` resolved against `Process.Dir` (so relative to the working directory in the binary) and the migrations `cron.Migrations()` returns, writing straight to `Stdout`. cron adds nothing to the lines and states nothing about their format; its requirements say only that the bytes on `Stdout` are the ones `db.Status` writes for that path and those migrations, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database, never with a format it spells out. Observed with appkit's `db.Status`, that output is `0001 pending` and a newline for an absent database, which it leaves absent with no `state/` created, `0001 applied 2026-10-05T14:03:07.123456Z` and a newline for a database `db.Open` made with a clock reading that time, and nothing, with an error, for a file that is not a SQLite database or a directory at that path.

`db.Status` only looks: it applies nothing and creates nothing, so before cron's first start `db status` reports every migration pending and leaves the directory as it was. When it returns an error, cron says so on one line, `cron: ` and the error's text with each newline replaced by a space, and exits 1. Whatever `db.Status` had already written to `Stdout` stays there: findings are product, and the repository's command-line conventions send a report to stdout whole, bad news included. That is the one case in which a failure may leave anything on `Stdout`. A database that records a migration this cron does not carry, one a newer cron upgraded, is not a failure: older code runs on newer data (`D03-serve`), appkit's `db.Status` lists every line, the unknown version among them, and returns nil, so `db status` writes nothing to `Stderr` and exits 0. `db status` reads no environment and takes no socket.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket, and only `db status` reads the database, so `cron --version` succeeds with nothing passed in and `cron bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, the timer, the random source, the two sinks, the banner source or the server maker, and only `db status` reads anything under the working directory, creating nothing there. A command fires no trigger, emits nothing to the bus and records no event: the trail is what cron records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns, `db status` and `db bogus` included. Every failure but that one `db status` case leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text is fixed here: cron's name; its description, which is `pages.Description`, the line the about screen shows and the host publishes in its services file for the MCP gateway's instructions; that it is not the host's default app; that it is one of the suite's MCP services; that it serves no guests (`guests = false`), so on a host with an authenticator nginx admits no visitor without a credential; no secrets; no `[env]` table, since cron has no settings of its own and `DRAIN_SECONDS` is the space's, which a manifest never sets; the `[database]` table that tells the host to keep and replicate `state/cron.db`; the `[resources]` table opsctl writes into the service unit, whose only line is `memory_max = "128M"`; and, last, the `[home]` table, whose only line is `group = "core"`, naming the group home's landing page shows cron under, as opsctl's and sandbox's manifest rules define. It declares no port, since cron serves on the socket the host passes it, and no `cache/`, since cron keeps nothing but its database.

## The nginx fragment

cron's nginx fragment, the constant `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at cron's public name, so that the events app reaches them only on cron's socket (`D03-serve`); it holds nothing else. What it does on a space is `D09-on-a-space`'s to state.

## The files under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ; `etc/nginx.conf` holds exactly the text of `NginxConf`. The build run writes both from the constants and keeps them in step. The files are proved by use: the root package embeds `etc/` and exports it as `Etc` (`D01-layout-and-run-seam`), so a test compares the embedded `manifest.toml` and `nginx.conf` with the constants without ever opening the checkout, and a build whose `etc/` lacks a file, or holds a stale copy, fails to compile or fails that test. That test lives in the external test package `cron_test` beside the root package, since it imports both the root package and `internal/cli`, which imports the root package, so a test inside package `cron` would form an import cycle.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `cron --version`, `cron manifest` or `cron --help` and reads stdout; an operator types `cron db status` in `/opt/cron` before or after a deploy and reads which migrations the database has had; `devctl build` runs `cron manifest` and compares its output with the release's `etc/manifest.toml`; the help text tells a caller what `ExitSuccess`, `ExitServerFailed` and `ExitUsage` mean.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s), `Dir` (an empty temporary directory) and, for `--version`, `Version` set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `p.Version + "\n"` for a `Version` of its own choosing, the empty string included, `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `After`, `Banner` and `MCP` to functions that record a call, `Rand` to a reader and `Sink` and `EventSink` to sinks that record any use, and asserts none was used. A test of `db status` makes a database under its `Dir` with `db.Open` and `cron.Migrations()` (or with a fixed `Now` and an extra recorded version written through `DB.Write`, or a file that is not a database), closes it, runs `cli.Run` with `Args` `["db", "status"]`, and compares `Stdout` with what its own `db.Status` call wrote into a buffer for the same path and migrations before `Run` was called, and with what it writes after, and `Stderr` with `"cron: "` and that call's error text. A test compares `cli.Manifest` with `pages.Description`. A test in package `cron_test` reads `manifest.toml` and `nginx.conf` from `cron.Etc()` with `fs.ReadFile` and compares them with `cli.Manifest` and `cli.NginxConf`.
