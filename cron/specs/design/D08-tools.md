# D08-tools

cron's triggers offered to models: `internal/tools`, the seven MCP tools `list`, `show`, `create`, `update`, `pause`, `resume` and `delete`, registered on the one `mcp.Server` the handler mounts at `/mcp`. This document states what `Register` puts on a server, in that order; what a client is told of each tool in `tools/list` (its name, the description written for a model, its input and output schemas, and its annotations); the argument and result types the package exports; which trigger a `slug` names for each tool; the order each tool checks its arguments in and the exact words of every refusal; the one answer every tool gives when the database cannot be reached; what `list`, `show` and `create` answer and change; and the `kind` and `outcome` of the `tool.called` each call records. What `update`, `pause`, `resume` and `delete` answer and change when they succeed is the section "Changing a trigger".

## What is someone else's

- appkit's `mcp` server is the transport and the protocol: `/mcp` takes only POST, one JSON-RPC message per POST, one `application/json` answer, no session and no stream; the `2026-07-28` envelope (`resultType`, `_meta`, `ttlMs`, `cacheScope`) and the earlier revisions `2025-11-25` and `2025-06-18`, `initialize` echoing a requested earlier revision and answering `2025-11-25` otherwise, `202` with no body for `notifications/initialized`, no `Mcp-Session-Id`; the 405 with `Allow: POST` for every other method; the malformed-transport checks; the 400 status of a protocol error on `2026-07-28` and 200 on the earlier revisions; and the paging of `tools/list`. A client of an earlier revision is offered the same tools because the tools are registered once, for every revision; what a `tools/list` lists, whatever the revision, is this document's (R-KMYA-AGY3).
- appkit's `AddTool` and schema rule are the members of a Tool object and their order, the annotations each `Effect` gives, the derivation of every schema from the Go types declared below, the strict reading of `arguments` with its `invalid arguments:` text, the success result a handler's output becomes (the object as `structuredContent` and as one compact text block), the `isError` result a handler's error becomes (its `Error()` text as the one text block), and the `tool.called` event for every `tools/call` that reaches a tool, recorded through the server's writer after whatever the handler recorded, with `duration_us` 0 when the arguments were refused as they were read.
- `main` builds the server with `pages.ServiceName` as its name, the display string as its version, the run's writer as its `Telemetry` and `Instructions` nil, so `server/discover` and `initialize` answer cron's description from the services file, or no `instructions` at all (`D01-layout-and-run-seam`, R-8MMK-XMC2, R-8NUH-BE2R, R-8QAA-2XK5). Routing exactly `/mcp` to it whatever the `Host`, the gateway's `Host: backend` included, `identity.Require` around it with its 500 for a request without `X-User-Id`, `events.Middleware` reading a request's event cause, `telemetry.Middleware` with `request.started` and `request.finished`, calling `Register` once when the handler is built, and nothing on stderr for any answer are `D03-serve`'s (R-JYU5-3HMA, R-N5S6-SZ8G, R-JWEC-BY4W, R-JTYJ-KENI, R-KB14-X718).
- The store's rules (`store.ValidSlug`, `store.ValidWhen`, `store.Unreachable`, the sentinels, the order `List` answers in, what a failing store is) are `D04-store`'s. Who may change a trigger, when its next slot moves, and which lifecycle event a change records and emits are `D05-scheduler`'s; the name, attributes and bus form of those events are `D07-trail`'s. The tools change nothing themselves: every change goes through the scheduler, and every `next` they answer is the scheduler's `Next`.

## What a client is told

All seven tools are registered with `mcp.AddTool`, in S05's order, so every schema is derived from the argument and result types this package exports. Each description is S05's word for word: a one-line summary, the line the landing page shows beside the tool's name, then a paragraph on how to call the tool. `list` and `show` change nothing and are `mcp.Read`; `create`, `update` and `resume` add a trigger, change its schedule or set it firing again, which another call can change back, and are `mcp.Additive`; `pause` lets slots pass unfired and `delete` removes a trigger for good, so both are `mcp.Destructive`. That is what the gateway's `describe` reports as each tool's kind and what `tool.called`'s `kind` says.

appkit derives a schema's `required` list from the `mcp:"required"` struct tag and a property's `description` from the `description` tag. Every argument carries S05's description and is tagged required, as S05's input schemas show. The result types carry bare `json` tags only: S05 fixes neither which output members are required nor any output description, so the output schemas have no `required` list and no descriptions. A member S05 says is "not always present" is a pointer, left out when nil, never sent as `null`; appkit allows no tag option such as `omitempty`.

## Which trigger a slug names

Every signed-in caller sees every trigger: `list` lists them all and `show` shows any of them, whoever owns it. A `slug` names the trigger whose slug it is, byte for byte; a trigger's id is not its slug, and a string `store.ValidSlug` refuses names nothing, so `show` refuses it with `no trigger named '<slug>'` without reading the database. For `update`, `pause`, `resume` and `delete` a `slug` names only a trigger the caller owns: another user's trigger is, to them, a trigger that does not exist, refused with the same line, though `list` and `show` show it and `create` finds its slug taken.

## Refusals

A tool reached with arguments appkit could not read never runs: the call is refused with appkit's `invalid arguments:` text and records `tool.called` with `outcome` `invalid_arguments`. A handler reached with clean arguments checks its rules in a fixed order, and the first that fails is the whole answer, one line in cron's words, quoting the value exactly as sent: `invalid slug '<slug>'`, `a trigger named '<slug>' already exists`, `invalid when '<when>'` and `no trigger named '<slug>'`. Every tool answers `cannot reach the database; try again later` (`store.Unreachable`) when the database cannot be read or written, quoting nothing of the underlying error; only a rule decided without the database answers first: `create`'s slug rule, and the slug rule of the other tools, which names nothing. So with the database down a `create` whose `when` is not allowed, and an `update` of another user's trigger, both get the database line. A refused call creates, changes and removes nothing, records no `cron.*` event and emits nothing to the bus.

## list and show

`list` answers `{"triggers":[...]}`, one entry per trigger in the space, in the store's order, by slug; an entry is the trigger object without `created`; a space with no triggers gets `{"triggers":[]}`. `show` answers the trigger object: `id`, `slug`, `when` as it was sent, `owner` (the email the creating request carried), `status`, `created`, `last_fired` (the slot of its latest fire, absent until it has fired) and `next` (the scheduler's next slot, absent while paused or when the schedule names no slot to come). Both read only; neither records a `cron.*` event nor emits anything.

## create

`create` checks the slug rule, then whether any trigger, the caller's or another user's, has the slug, then the `when` rule, and hands the draft (slug, when, the caller's user id and email) to `Scheduler.Create`. Two creates of the same slug racing past that check are settled by the store, which keeps exactly one (`D04-store`, R-A95R-ALXE). The answer is the trigger object as it stands after the call: `active`, `created` the call's time, no `last_fired`, and `next` the first slot strictly after the call, absent for a schedule such as `0 0 30 2 *` that names no slot to come. `Scheduler.Create` records and emits `cron.<slug>.created` under the call's context, so the event carries the caller's user and request id, and, when the request named an event as its cause, that cause and the next depth.

## Changing a trigger

`update`, `pause`, `resume` and `delete` change one of the caller's own triggers, and only through the scheduler: `Scheduler.Update`, `Pause`, `Resume` and `Delete`, with the caller's user id as the owner, so the store, each trigger's next and the lifecycle events are what `D05-scheduler` states for those methods. Each finds the trigger first, so a slug that is not one of the caller's triggers is refused before anything else is looked at; only `update` has a second check, its `when`, under `create`'s rule, refused with `invalid when '<when>'` quoting it as sent.

`update` changes only the schedule. A `when` byte-identical to the trigger's is not a change: the call succeeds, the store and the trigger's next stay as they were. Any other allowed string is stored as sent, even one that names the same slots, and the next moves to the first slot of the new schedule after the call (after `last_fired` too), or there is none while the trigger is paused or when the schedule names no slot to come; the slot the old schedule called for is not fired. `update` records and emits no event of its own, whether it changed anything or not.

`pause` makes an active trigger paused, with no next; `resume` makes a paused trigger active, its next the first slot after the call (after `last_fired` too), so a slot that fell due while it was paused is never made up. Pausing a paused trigger or resuming an active one is not a change and not a refusal: the call answers the trigger as it is and, for `resume`, keeps the next it had, even a slot already due that the scheduler has not yet woken for. A pause or resume that changes the trigger records `cron.<slug>.paused` or `cron.<slug>.resumed` in the trail and emits it on the bus, through `trail.Lifecycle` (`D07-trail`), under the call's context; one that changes nothing records and emits nothing.

`delete` removes the trigger whatever its status, answers `{"deleted":true,"id":"<id>"}` with the id of the trigger it removed, and records and emits `cron.<slug>.deleted` with the schedule it had. The slug then names nothing, so every tool that takes it refuses it as it refuses any slug no trigger has, a second `delete` included, and any user may `create` it again. These four answer the trigger object `show` would answer once the call has returned, `delete` excepted.

## Recorded decisions

- The result types carry no `mcp:"required"` and no `description` tags (inventory flag A7: S05 leaves both open), so no output schema has a `required` list or a property description.
- A slug `store.ValidSlug` refuses is answered by `show`, `update`, `pause`, `resume` and `delete` with `no trigger named '<slug>'` without reading the database, so the answer holds while the database is down, as `create`'s `invalid slug` does; S05 counts a refusal decided "whatever the database holds" before the database line, and S07 says such a slug names nothing.
- A refusal is a handler error whose `Error()` is exactly the line: appkit turns it into the one text block of an `isError` result and records `outcome` `error`.
- A `create` whose `Scheduler.Create` returns an error satisfying `errors.Is(err, store.ErrSlugTaken)` is answered `a trigger named '<slug>' already exists`, but no requirement here states it: the tool looks the slug up before it creates, and no public seam of `D04-store` or `D05-scheduler` lets a test put a trigger with that slug into the store between the two calls deterministically, so concurrent creates would be a race no test can pin. That the store holds at most one trigger per slug under concurrent creates is `D04-store`'s (R-A95R-ALXE), and that `Scheduler.Create` passes its sentinel through is `D05-scheduler`'s (R-HCXV-N5IT).
- `Register` needs nothing of the database: `tools/list` answers the same while the store is failing.
- The argument types are exported so a test encodes arguments with them, and the result types so it decodes `structuredContent` into them member for member. `pause`, `resume` and `delete` each have an argument type of their own, though they take the same field, so each can change alone.
- `update` finds the trigger before it reads `when`, so a slug that is not the caller's trigger is `no trigger named` whatever `when` is (S08); a `when` byte-identical to the trigger's is a success that changes nothing and keeps the next, and the comparison is of the string, never of the slots (S08).
- `pause` of a paused trigger and `resume` of an active one are successes that change nothing, keep the next and emit nothing (S09). `resume` of an active trigger keeps a next that is already due but not yet fired, as the story says the call answers "the slot it was already due to fire".
- `delete` answers the id of the trigger it removed, as `Scheduler.Delete` returns it, whatever its status. A trigger created later with the same slug is a new trigger: its id is drawn as every create draws one (`D04-store`, R-V5SE-48L0, R-V70A-I0BP), drawn again only when it is the id of a trigger the store holds, and nothing either way is promised about whether it may equal the deleted trigger's id.

## Consumer tasks

The handler (`D03-serve`), when it is built, registers the tools once on the server `Process.MCP` made for the run's writer: `tools.Register(cfg.MCP, tools.Config{Store: cfg.Store, Scheduler: cfg.Scheduler})`, the scheduler being the one `scheduler.Start` returned over that store with the run's writer and emitter; and it mounts the server at exactly `/mcp` inside `identity.Require`, inside `events.Middleware`, inside `telemetry.Middleware` over the same writer.

A model, through the gateway's `call`, lists the seven tools, reads every trigger with `list` and `{}` (getting `{"triggers":[{"id":"crn_3f9a1c7e5b2d8046","slug":"hourly",...,"next":"2026-10-05T10:00:00Z"},...]}`, `{"triggers":[]}` in an empty space) and one with `show` and `{"slug":"nightly_backup"}`, another user's included; through `mutate` it makes one with `create` and `{"slug":"crm_sync","when":"*/15 * * * *"}`, getting `{"id":"crn_…","slug":"crm_sync","when":"*/15 * * * *","owner":"mg@example.com","status":"active","created":"2026-10-05T09:32:00Z","next":"2026-10-05T09:45:00Z"}`, and then subscribes a script to `cron.crm_sync.fired` in scripts. A refusal tells it what to fix (`invalid slug 'crm-sync'`, `invalid when '0 */15 * * * *'`, `invalid arguments:` LF `when: missing required field`), that the slug is taken (`a trigger named 'month_end' already exists`), that the trigger is not there or not its own (`no trigger named 'cleanup'`), or to try again later (`cannot reach the database; try again later`).
