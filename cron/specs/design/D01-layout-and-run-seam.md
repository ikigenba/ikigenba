# D01-layout-and-run-seam

cron is the suite's scheduler: one Go binary that keeps triggers, each a slug and a schedule, offers seven MCP tools at `/mcp` (`list`, `show`, `create`, `update`, `pause`, `resume`, `delete`), emits an event on the suite's event bus each time a trigger fires, keeps its triggers in its own SQLite database, `state/cron.db`, and serves a page of every trigger at `/` and an about screen at `/about` to a signed-in user. This design is the structural ground the other designs stand on: where the code lives, which package owns which concern, the seam through which the process is run so that the command, the server, the store, the scheduler, the pages and the tools can be tested without a real process, the one setting and how it is read, the paths, the migrations that give the database its schema, where the version it shows comes from, and the one binary's wiring. `D02-cli` declares the exit codes, the usage text, the manifest and the nginx fragment and states what `Run` does with arguments; `D03-serve` states the serve path `Run` follows with none; every other package's names are declared by the document that owns that package, listed below.

The module is `github.com/ikigenba/ikigenba/cron`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/cron`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/cron` is wiring only.

## The dependencies

cron depends on two modules besides the standard library. `github.com/ikigenba/ikigenba/appkit` is required at a published release through the ordinary module proxy and checksum database, with no `replace` directive; its `db` package brings the pure-Go SQLite driver, which keeps the release build cgo-free, and cron imports no driver of its own. `github.com/robfig/cron/v3` is used to parse schedules and to compute a parsed schedule's next time, and for nothing else: cron neither runs nor schedules anything through it, and keeps its own loop on its own injected clock and timer (`D05-scheduler`). Which release of either is data that `AGENTS.md` and `go.mod` hold; no requirement names one.

appkit is a sibling reached only through its published packages, and cron uses eight of them: `db` (the triggers' handle and its migrations, and `db status`), `version` (below), `services` (the services file, read afresh for the launcher, the auth links and the instructions), `page` (the banner, launcher and footer, the template set the three templates are parsed into, and the shared static files under `/_appkit/`), `identity` (`Require` on every route but the event bus's two, and the caller a fire runs as), `mcp` (the server mounted at `/mcp` and the client the tests drive it with), `telemetry` (the event contract, the request middleware, the writer every trail event goes through, the socket sink and the capturing sink tests use), and `events` (the emitter every bus event goes through, the cause middleware, the two handlers the events app reaches cron at, the socket sink and the capturing sink tests use). appkit owns all of their contracts; cron restates none.

`github.com/ikigenba/ikigenba/appkit/version` is the code identity the host gives every app: `version.Display()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment at the time of the call and returns the **display string** built from them, the empty string when neither is set. How it is built is appkit's contract, and cron's tests do not re-prove it. cron carries no version of its own: nothing in its source or its build names one.

## Where the environment is read

`main` makes the one read of the environment that is not `Run`'s own: it calls `version.Display` exactly once, first, and holds the result, the display string, as the version cron shows everywhere it shows one. It hands that string to `page.New`, to the `mcp.ServerConfig` its `Process.MCP` builds, and to `Run` as `Process.Version`, which `Run` writes for `--version` and gives the run's writer as its `telemetry.Config.Version`. Nothing below `main` calls `version.Display`, so a test of `Run` hands it any string as `Version`, the empty string included, and sets no variable; one start of the binary reads the two variables once, and so does a `--version`, which is a run of its own.

`Run` reads every variable through `Process.LookupEnv`: `DRAIN_SECONDS` once at start, through `settings.Read`; `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness (`D03-serve`); and `IKIGENBA_SERVICES`, once, when it starts to serve, whose value it hands on as the services path that the handler and the pages read afresh whenever they need the file. A broken or absent services file never stops a start; it reads as a file that lists no services. cron starts no process, so it has no environment to compose for one.

Three readers of `IKIGENBA_SERVICES` sit outside the seam, all appkit's: `page.New` and `mcp.NewServer` read the real environment when they are called, and the two socket sinks, telemetry's and the event bus's, read it on every delivery. So `main` calls `page.New` once and puts in `Process.MCP` a function that calls `mcp.NewServer` with `Instructions` nil, so a client's instructions are cron's description read afresh from the services file; and the socket sinks are what a nil `Process.Sink` and a nil `Process.EventSink` mean, used only by the binary, while a test of `Run` names its own sinks.

## Packages

The module's root package, `cron`, holds what the module embeds, because Go's `embed` reaches only files at or below the embedding package's directory. It exports `Assets`, a file system holding exactly the three templates from `assets/` — `landing.html`, `about.html` and `notfound.html` — which `internal/pages` parses into the set `page.Templates()` returns (`D06-pages`); `Etc`, a file system holding exactly `manifest.toml` and `nginx.conf` from `etc/`, through which a test proves the files the build writes are the copies of `cli.Manifest` and `cli.NginxConf` (`D02-cli`); and `Migrations`, a file system holding exactly the migrations from `migrations/`. Nothing else lives at the root. The root package's name is `cron`, which is also the package name of `github.com/robfig/cron/v3`; a file that imports both names one of them with an alias.

The database's schema is a sequence of migration files, each named with a four-digit version, that the binary carries and appkit's `db` applies in order. This cron carries one, `0001_triggers.sql`, which creates the `triggers` table `D04-store` describes. `Migrations()` is what `Run` hands `db.Open` and `db.Status`, and what a test hands `db.Open` to make a database of cron's shape in its own temporary directory; it is the same on every call and depends on no file beside the binary. A later migration is a new file with the next version; none is edited once it has run on a production-grade space.

Nine internal packages hold the concerns, one each.

- `internal/cli` owns the program as a command: the run seam (this document), the exit codes, the usage text, the manifest, the nginx fragment and `db status` (`D02-cli`), and the serve path (`D03-serve`).
- `internal/settings` owns the one value cron reads from its environment at start, `DRAIN_SECONDS`, its default, how it is spelled, and the refusal of one that is not acceptable (this document).
- `internal/server` owns a listener's life: serving a handler and draining for a deadline (`D03-serve`).
- `internal/store` owns the triggers' records: the `triggers` table reached through appkit's handle, the record's fields, the slug, schedule and id rules, and the errors every consumer tells apart (`D04-store`).
- `internal/trail` owns the five trigger events: their declaration to the event bus, and recording each in the trail and emitting it on the bus together (`D07-trail`).
- `internal/scheduler` owns time: each active trigger's next slot, the wait for it on the injected timer, firing, the changes a tool makes to a trigger, and stopping (`D05-scheduler`).
- `internal/pages` owns the template set, the three templates' data, `/` and `/about`, `ServiceName` and `Description` (`D06-pages`).
- `internal/tools` owns the seven MCP tools (`D08-tools`).
- `internal/web` owns the one handler: the route table, the middlewares and the mounting (`D03-serve`).

Dependencies point one way: `cmd/cron` imports `internal/cli`, `internal/pages` and appkit; `internal/cli` imports the root package, `settings`, `server`, `store`, `trail`, `scheduler`, `pages` and `web`; `web` imports `pages`, `tools`, `store` and `scheduler`; `pages` imports the root package, `store` and `scheduler`; `tools` imports `store` and `scheduler`; `scheduler` imports `store` and `trail`; `trail` imports `store`; the root package, `settings`, `server` and `store` import nothing of cron's. Which package imports which is not observable, so this paragraph is guidance.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, and returns the exit code. It carries no environment for a child, since cron starts no process. There is no field naming another database, because appkit's `db` takes only an ordinary file path, so the database is always `state/cron.db` under `Dir` and a test that needs its own gives `Run` a temporary `Dir`.

Two fields make the schedule testable without waiting. `Now` is the clock every time cron stamps, measures or compares is read from: a trigger's `created`, every event's time, every slot the scheduler compares with the present, and the time each migration it applies is recorded at. `After` is the timer seam: every wait of the scheduler for a trigger's next slot ends when a channel `After` returned delivers, so a test that hands in its own `After` learns each wait as it begins, moves its own `Now` to the slot, and delivers on the channel to make the slot come (`D05-scheduler`); nothing waits in real time for a slot. The drain deadline and the delivery attempts of the writer and the emitter run on real time and never on `After`, because the drain is the one wait `AGENTS.md` lets a test keep to a few real seconds; the writer and the emitter pause between attempts with `Sleep`, and measure an event's retry window by `Now`, so a test whose `Sleep` advances its own `Now` drives a bus event past its window with no real waiting.

`Rand` is the source of every id cron mints: request ids (through the writer's middleware), trigger ids, the request id of each fire, and bus event ids. `Dir` is the working directory the database resolves against. `Sink` is where the writer delivers, a `*telemetry.Capture` in a test and appkit's socket sink in the binary; `EventSink` is where the emitter delivers bus events, an `*events.Capture` in a test, or one whose `Deliver` fails or blocks, and appkit's event-bus socket sink in the binary. `Version` is the display string `main` read. `Inherit`, `Unsetenv`, `Pid`, `Stdout`, `Stderr`, `Banner` and `MCP` are as R-BYCF-VSOL states.

## Settings

cron has no settings of its own: its manifest has no `[env]` table (`D02-cli`). It reads one value at start, `DRAIN_SECONDS`, the space's, spelled as opsctl writes an integer — one or more ASCII digits, no sign, no leading zero, no unit, no white space — and 5 when unset or empty. cron sets no upper limit: digits beyond what an `int64` holds read as the largest `int64`. `settings.Read` returns it as a `settings.Settings`, or, when it is not acceptable, a `*settings.Error` whose text `Run` writes after `cron: `, as a usage error, before it looks for its socket; what the number does is `D03-serve`'s (the drain).

## Paths

Relative to `Process.Dir` (the process's own working directory when empty, which is how `main` leaves it; `/opt/cron` on a host, the app's directory in a sandbox): the database is the SQLite file `state/cron.db`, opened with `db.Open`, `cron.Migrations()` and `Process.Now`, `state/` created when absent. The diagnostics of `D03-serve` name the path in this relative form whatever `Dir` holds. cron writes nothing outside `Dir`.

## The version

`internal/cli` declares no version. The one version string cron shows is the display string `main` reads from appkit's `version.Display`: `cron --version` (`D02-cli`, through `Process.Version`), the footer of every page and the about screen's version (through `page.New(pages.ServiceName, v)`, `v` being that string), the MCP `serverInfo` (through `mcp.ServerConfig.Version`), and `service.started`'s `version` (through `Process.Version` and the run writer's `telemetry.Config.Version`). Its value is data the host supplies at run time, never a requirement's: the binary's requirements compare with what `version.Display` returns under the same two values, so no test spells a version.

## Recorded decisions

- appkit is required at `v0.17.0`, the release `AGENTS.md` names, which exports the `db`, `events` and `version` packages and whose `events` package admits the pattern declarations `cron.*.<kind>` the trail uses (`D07-trail`).
- `github.com/robfig/cron/v3` is required at `v3.0.1`, its newest release (`go list -m -versions` lists `v3.0.0-rc1 v3.0.0 v3.0.1`), and used for parsing only: its standard parser (`ParseStandard`, five fields plus descriptors) and the parsed schedule's `Next`. cron uses no `Cron` runner, no `Entry`, no job and no seconds field. Adding it is the external dependency `AGENTS.md` approves.
- `Process` carries no environment for a child, since cron starts no process; `After` serves every wait cron has on its clock, the scheduler's, and no other wait.
- The settings refusal is written by `Run` before it looks for its socket, which is how a bad `DRAIN_SECONDS` is reported whether or not a socket was passed in; the rest of the start order is `D03-serve`'s.
- That a running cron writes nothing outside `Dir` is proved over the test's own temporary tree; a write to the process's own `os.TempDir()` is outside what a test may observe, and is accepted as unprovable rather than designed around.
- The wiring of `main` is proved at the binary by the one exec'ing test of `AGENTS.md`, since `main` is not usable from a test; the binary requirements below are what that test proves.

## Consumer tasks

The binary's start: `main` calls `v := version.Display()` and hands `cli.Run` a `cli.Process` whose `Args`, `LookupEnv`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Version` is `v`, whose `Banner` is the `Banner` method of `page.New(pages.ServiceName, v)`, whose `MCP` returns `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: v, Telemetry: w})`, and whose `Inherit`, `Now`, `Sleep`, `After`, `Rand`, `Dir`, `Sink` and `EventSink` are left zero; it cancels the context on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name, and exits with what `Run` returns. `Run` reads `settings.Read(p.LookupEnv)`, writes `"cron: " + err.Error() + "\n"` and returns `cli.ExitUsage` when it refuses, and otherwise follows the serve path `D03-serve` states: the socket, `db.Open` and `store.New`, `telemetry.New`, `events.New` with `trail.Emits()`, `scheduler.Start`, `web.Handler`, readiness, and the stop.

A test of the settings calls `settings.Read` with a lookup over a map and compares the result with `settings.Defaults()` or the expected `settings.Settings`, or uses `errors.As` to get the `*settings.Error` and compares its `Name`, `Value`, `Unit` and `Error()`. A test of the run seam builds a `cli.Process` with a temporary `Dir`, a `LookupEnv` over a map, an `Inherit` returning a listener it bound, a `NOTIFY_SOCKET` it holds, a `Now`, an `After` and a `Rand` it controls, a `Version` string of its own, a `*telemetry.Capture` as `Sink` and an `*events.Capture` as `EventSink`, a `Banner` from `page.New` and an `MCP` that calls `mcp.NewServer` (having set `IKIGENBA_SERVICES` with `t.Setenv`), calls `cli.Run` with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with `mcp.Client` and raw HTTP, moves its clock and delivers on its timer, cancels, and inspects `Dir`, the captures and the streams. A test of the root package calls `cron.Assets()`, `cron.Etc()` and `cron.Migrations()` and lists and reads them with `fs.ReadDir` and `fs.ReadFile`. The one test that execs the binary builds `cmd/cron` and runs it in a temporary working directory, composing non-empty `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` into the child's environment and computing the display string it expects by calling `version.Display` after setting the same two values with `testing.T.Setenv`; it also runs `--version` with neither variable in the child's environment and expects exactly one empty line. Over the socket it sends `initialize` as raw HTTP, since `mcp.Client` cannot, and reads `tool.called` from the listener its services file names as `telemetry`.

## The documents

`D02-cli` is the command, the exit codes, the usage text, the manifest, the nginx fragment and the two files under `etc/`. `D03-serve` is the serve path, `internal/server` and `internal/web`. `D04-store` is `internal/store` and the `triggers` table. `D05-scheduler` is `internal/scheduler`: next slots, firing and stopping. `D06-pages` is `internal/pages` and the three templates. `D07-trail` is `internal/trail` and the events cron records and emits. `D08-tools` is `internal/tools`. `D09-on-a-space` is what cron contributes to a space and a sandbox.
