# D06-pages

What cron draws as HTML: the package `internal/pages`; the four templates `landing`, `about`, `tools` and `notfound` and the data each receives; the handler that answers `/`, `/about`, `/tools` and every path that is not a page — the landing page, the about screen and the tools page for the signed-in caller, the plain-text refusal when the landing page cannot read the database, the refusal of any other method on a page, and the not-found page; the banner's user, auth's two links and the banner's trail; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the root package's `Assets`, which holds exactly the four templates (R-Z8K0-RKG4), and the run seam whose `Banner` the binary sets, and fixes the binary's footer and about screen (`D01-layout-and-run-seam`); `D03-serve` declares `web.Handler` and `web.Config` and owns the route table (which paths reach `pages.Handler`, which reach appkit's `page.Static()`; R-ZAZT-J3XI, R-K19X-V13O), the one `mcp.Server` mounted at `/mcp` that it hands the pages handler, the identity gate in front of every page (`identity.Require`, so a request without `X-User-Id` never reaches this design's handler, R-JWEC-BY4W; the caller a page sees is the one R-JYU5-3HMA describes), the request's two trail events, and that nothing reaches standard error while telemetry takes every event; `D04-store` declares `store.Store`, its `List` and the order it gives (R-42KU-PL3N), `store.Trigger`, the failing store (R-PLFA-QUWV), what leaves the store unchanged (R-9WYR-GWIG) and `store.Unreachable` (R-4051-Y1M9); `D05-scheduler` declares `scheduler.Scheduler` and its `Next` (R-GS7L-51X0: none while paused; R-GOJV-ZQOX: a trigger's next), and computes no next for a schedule with no future slot (R-GNBZ-LYY8); `D08-tools` names the seven tools and registers them, in its order, on that server, and appkit's `Server.Tools` hands back what is registered; `D02-cli` publishes `pages.Description` in the manifest (R-8YTK-RBR0). Tests of this design carry those documents' ids where they exercise those rules.

## The template set and its data

The four templates are the files of `assets/`, embedded by the root package and returned by `cron.Assets()`. `pages.Load` builds **cron's template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `footer` and `preload`; the code adds no template function and writes no markup of its own. Each template executes without error for any value of its data, so markup that cannot be executed is a test failure, not a broken page. `Set.Write` is the one way the handler sends a page: with status 200 or 404 it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set and sets nothing else. A `HEAD` gets the status and headers and no body.

Each template's data is a named struct whose fields are exactly those its opening comment names. `LandingData` carries the banner and one `TriggerRow` per trigger, in the order `store.List` gives them, by slug. A `TriggerRow` carries what a row shows and nothing else — the id, the slug, the `when` as sent, the owner's email, the status, whether the caller owns the trigger, and the two times, each as a stamp (RFC 3339 in UTC to the second, `2026-10-05T09:00:00Z`) and as a minute text (UTC to the minute, `2026-10-05 09:00`) — so no trigger's `created` time and no user id can reach the page. `LastFired` and `LastFiredText` are empty while the trigger has never fired; `Next` and `NextText` are empty whenever `Scheduler.Next` answers no next: while the trigger is paused, and for a schedule with no future slot. `AboutData` carries the banner and `pages.Description`, the manifest's one-line description, so the about screen says the same with or without a services file and reads no trigger. `ToolsData` carries the banner and one `Tool` per tool registered on the server mounted at `/mcp`, in the order `Server.Tools` gives them, which is the order they were registered and the order `tools/list` names them: a `Tool` carries a tool's name and its whole description, the description written for a model. `NoticeData` carries only a banner, for the not-found page's footer.

## The templates

The four files of `assets/` are written by the user or the delivering agent, following the repository's `design/`; each defines one template of its own name and opens with a comment naming the data it receives. What a page says, its markup and its hooks live in its template and nowhere else: this design names each template and its data, never its words or its markup. `landing` (file `landing.html`) receives `pages.LandingData` and is the landing page at `GET /`; `about` (file `about.html`) receives `pages.AboutData` and is the about screen at `GET /about`; `tools` (file `tools.html`) receives `pages.ToolsData` and is the tools page at `GET /tools`; `notfound` (file `notfound.html`) receives `pages.NoticeData` and is the not-found page, answered with status 404. appkit's `banner`, `footer` and `preload` templates, which the set already defines, are the templates' to call, `banner` and `footer` with the data's `Banner`; the footer shows the banner's `Release` and then its `Commit`, the identity `main` handed `page.New`.

## The pages handler

`pages.Handler` answers every path `D03-serve` routes to it — `/`, `/about`, `/tools`, and every path that is not a page — behind `identity.Require`, so every request it sees names its caller, and a test wraps it the same way. `/`, `/about` and `/tools` take `GET` and `HEAD`; any other method is refused 405 with `Allow: GET, HEAD` and an empty body, before anything is read. Any other path is the not-found page, status 404, whatever the method, so a path that names nothing is never a 405: a trigger has no page, so `/hourly` is not found, and neither `/about/` nor `/tools/` is redirected. The landing page reads the triggers with one `store.List` call and asks the scheduler for each one's next; when that read fails it answers `503` with the plain text `store.Unreachable` (R-4051-Y1M9) and a newline, and no page, since saying the space has no triggers would be false. The tools page lists what one call of `Tools` on `Config.MCP` returns while the request is answered. The about screen, the tools page, the not-found page and the 405 read no trigger, so they are answered the same while the database is unreachable. No answer changes a trigger, fires anything or sets a cookie.

Each page drawn is drawn with the banner the banner source returns for the **banner user** — the caller's `X-User-Email` exactly as it arrived and auth's two links; how often the source is called is not fixed. auth's links come from the services file's entry named `auth`, read afresh for every request: its `url` followed by `/` and by `/logout`. With no such entry, an empty `url`, or no usable services file, the space is read from `Host`: a trailing `:` and port digits are dropped, then one leading `cron.` label, and the links are `<scheme>://auth.<space>/` and `<scheme>://auth.<space>/logout`, the scheme being `X-Forwarded-Proto` when that is exactly `http` or exactly `https` and `https` otherwise. What the banner draws from the banner user, the run's identity and the services file — cron's own icon (`Icon`) from the entry named `cron`, the suite's home (`Home`) from the `url` of the entry named `home` while it is enabled, whether the page menu offers the tools page (`Tools`) from the `mcp` of cron's own entry, the release and commit, the profile link and the sign-out form — is appkit's `page` package's output; this design states which data each page is drawn with, and two binary-level requirements prove that the binary's banner source is appkit's kit made for `pages.ServiceName` with the run's identity, called with the banner user of each request and reading the services file afresh for every page, and that a services file that does not exist breaks no page. There is no service launcher, and nothing replaces it.

The banner's trail is the page's place below cron's landing page; the landing page is its root and is never a level. `Kit.Banner` returns an empty `Trail` and fills `Home` and `Tools` from the services file, and the handler sets the trail on what the banner source returns before drawing the page, leaving every other field as the source gave it: the about screen carries exactly one level, named `about`, at `/about`; the tools page exactly one, named `tools`, at `/tools`; the landing page and the not-found page none. cron has no page below those two. That value is the **page banner** of the request, and every page is drawn with it.

## Proving a page

A page is proved by comparison, never by reading it: a test builds its own copy of cron's template set, executes the named template with the data a requirement states, and compares the body byte for byte, or finds in a body a value it supplied; no test looks for a word, a tag, a class or an id. The byte-for-byte requirements cover every input, so `html/template`'s contextual autoescaping keeps a caller's, a trigger's or the services file's bytes from becoming markup. One requirement is stated for a **plain page request**, whose inputs carry nothing escaping would change: no user id and no created time reaches the landing page (R-ET6G-NLRK).

## The shared files

The stylesheet, its three fonts, the button feedback script, the favicon and the two licences are appkit's: `page.Static()` serves them from files embedded in the binary, and `D03-serve` hands every signed-in request whose path begins `/_appkit/` to it unchanged. The requirements here state those answers as cron's own behaviour through `web.Handler`, so cron's tests fail if an appkit release stopped giving it; `/_appkit/launcher.js`, which an earlier release served, is now not found like any other path. The fonts are served only under **font paths**, names carrying a hash of each font's bytes: the path `page.PreloadURL()` returns and the names the served stylesheet gives in its `url("…")` values; cron never writes a font's name or hash, and a test learns them the same way. Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, which this design leaves open. A request for a shared file without `X-User-Id` is `D03-serve`'s 500.

## Recorded decisions

- The pages handler is stated for `identity.Require(pages.Handler(cfg))`, the wrapping `D03-serve` gives it; the caller's user id is the request's first `X-User-Id`, and the banner user's email its first `X-User-Email`, as it arrived.
- The not-found page is drawn with a banner from the banner source for the request's banner user, so its footer carries the same release and commit as the other pages.
- The pages handler gets the tools from the server itself: `Config.MCP` is the one `mcp.Server` `web.Handler` mounts at `/mcp` and registers the tools on, and the tools page calls its `Tools` for every request, so the page cannot disagree with `tools/list` and `internal/pages` needs no copy of the tool list made at build time.
- The handler replaces whatever `Trail` the banner source returns, so a test's banner source returns a trail of its own and finds it gone from the landing page and the not-found page, and replaced on the about screen and the tools page; the levels' names, `about` and `tools`, match the paths, as the banner's page menu does.
- The space for auth's links drops a trailing port, then a leading `cron.` compared byte for byte and only when something follows it; the scheme is case-sensitive (`HTTPS` gives `https`, and so does `Http`).
- Observed with appkit's published `page` package (probe, recorded with this design's evidence): its `banner`, `footer` and `preload` templates (and no `launcher`), and every answer of `page.Static()` the shared-file requirements state — types, strong `ETag`, `Cache-Control`, `304` on a matching `If-None-Match` (`*`, `W/`, lists with empty elements) whatever `If-Modified-Since` says, `200` on a mismatch, `405` with `Allow: GET, HEAD`, and `404` for every other `/_appkit/` path whatever the method, `/_appkit/launcher.js` included. Its published documentation states the same (`page.Static` serves `theme.css`, `feedback.js`, `favicon.svg`, the two licences and the fonts; `launcher.js` is 404).

## Consumer tasks

`web.Handler` calls `set, err := pages.Load()` once, when it is built, and routes every path that is not `/events`, `/declarations`, `/mcp` or under `/_appkit/` to `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, Scheduler: cfg.Scheduler, MCP: cfg.MCP})` inside `identity.Require`, `cfg.MCP` being the server it called `tools.Register` on. For `/about` the handler sets `b.Trail = []page.Level{{Name: "about", URL: "/about"}}` on the `b` the banner source returned, for `/tools` `b.Trail = []page.Level{{Name: "tools", URL: "/tools"}}`, and for every other page `b.Trail = nil`; for `/tools` it builds `pages.ToolsData{Banner: b, Tools: ts}`, `ts` holding `pages.Tool{Name: t.Name, Description: t.Description}` for each `t` in `cfg.MCP.Tools()`. `cli.Run` names the database's, writer's and emitter's service `pages.ServiceName`; `cli.Manifest` carries `pages.Description`; the binary's banner source is `page.New(pages.ServiceName, id).Banner`, `id` being the `version.Identity` `main` read for the run.

A test of the handler opens a `store.Store` over a temporary database, creates triggers through a scheduler it started with a clock it controls, writes a services file in its temporary directory, builds `identity.Require(pages.Handler(pages.Config{...}))` with a `Banner` closure that records its arguments and returns a fixed `page.Banner` carrying a `Trail` of its own, an `MCP` from `mcp.NewServer` (having set `IKIGENBA_SERVICES` with `t.Setenv`) on which it called `tools.Register`, or `AddTool` with tools of its own in an order that is not sorted, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of cron's template set from `page.Templates()` and `cron.Assets()`, executes `landing` with the `pages.LandingData` it expects, `about` with the `pages.AboutData` and `tools` with the `pages.ToolsData` it expects, each with the banner its closure returned and the trail it expects for the path, and compares bodies byte for byte. It calls `SetFailing(true)` on the handle its store was built over to make the database unreachable. A test of the shared files builds `web.Handler` as `D03-serve` states and requests `/_appkit/...` with a non-empty `X-User-Id`, taking the font paths from `page.PreloadURL()` and from the `url("…")` values of the stylesheet it is served. The one exec test of the binary in `cmd/cron` computes the expected banner by calling `page.New(pages.ServiceName, version.Read())` after setting `IKIGENBA_SERVICES`, `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` with `t.Setenv` to the values it gave the child, and rewrites the services file, disabling `home`, between two `GET /` requests.
