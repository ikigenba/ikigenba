# D06-pages

What cron draws as HTML: the package `internal/pages`; the three human-authored templates `landing`, `about` and `notfound`, the data each receives and the hooks each emits; the handler that answers `/`, `/about` and every path that is not a page — the landing page and the about screen for the signed-in caller, the plain-text refusal when the landing page cannot read the database, the refusal of any other method on a page, and the not-found page; the head every page carries; the banner's user and auth's two links; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the root package's `Assets`, which holds exactly the three templates (R-7N9H-U9TX), and the run seam whose `Banner` the binary sets, and fixes the binary's footer and about version (R-8K6S-62UO, R-8LEO-JULD); `D03-serve` declares `web.Handler` and `web.Config` and owns the route table (which paths reach `pages.Handler`, which reach appkit's `page.Static()`; R-K2HU-8SUD, R-K19X-V13O), the identity gate in front of every page (`identity.Require`, so a request without `X-User-Id` never reaches this design's handler, R-JWEC-BY4W; the caller a page sees is the one R-JYU5-3HMA describes), the request's two trail events, and that nothing reaches standard error while telemetry takes every event; `D04-store` declares `store.Store`, its `List` and the order it gives (R-ACTG-FX5H), `store.Trigger`, the failing store (R-PLFA-QUWV), what leaves the store unchanged (R-9WYR-GWIG) and `store.Unreachable` (R-CKAM-RO13); `D05-scheduler` declares `scheduler.Scheduler` and its `Next` (R-GS7L-51X0: none while paused; R-GOJV-ZQOX: a trigger's next), and computes no next for a schedule with no future slot (R-GNBZ-LYY8); `D08-tools` names the seven tools and their descriptions, whose first lines the landing template carries; `D02-cli` publishes `pages.Description` in the manifest (R-8YTK-RBR0). Tests of this design carry those documents' ids where they exercise those rules.

## The template set and its data

The three templates are the files of `assets/`, embedded by the root package and returned by `cron.Assets()`. `pages.Load` builds **cron's template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; the code adds no template function and writes no markup of its own. Each template executes without error for any value of its data, so markup that cannot be executed is a test failure, not a broken page. `Set.Write` is the one way the handler sends a page: with status 200 or 404 it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set and sets nothing else. A `HEAD` gets the status and headers and no body.

Each template's data is a named struct whose fields are exactly those its opening comment names. `LandingData` carries the banner and one `TriggerRow` per trigger, in the order `store.List` gives them, by slug. A `TriggerRow` carries what a row shows and nothing else — the id, the slug, the `when` as sent, the owner's email, the status, whether the caller owns the trigger, and the two times, each as a `datetime` value (RFC 3339 in UTC to the second, `2026-10-05T09:00:00Z`) and as its text (UTC to the minute, `2026-10-05 09:00`) — so no trigger's `created` time and no user id can reach the page. `LastFired` and `LastFiredText` are empty while the trigger has never fired; `Next` and `NextText` are empty whenever `Scheduler.Next` answers no next: while the trigger is paused, and for a schedule with no future slot. `AboutData` carries the banner and `pages.Description`, the manifest's one-line description, so the about screen says the same with or without a services file and reads no trigger. `NoticeData` carries only a banner, from which the not-found page draws appkit's footer, `cron <display>`; it draws no banner, as the story asks.

## The templates

The delivering agent writes `assets/landing.html`, `assets/about.html` and `assets/notfound.html` from this section; each file defines one template of its own name and opens with a comment naming the data it receives and the hooks it emits, as listed here. Every page's head holds, in any order, `<meta charset="utf-8">`, the viewport `meta` with `width=device-width, initial-scale=1`, the stylesheet link to `/_appkit/theme.css`, `{{template "preload"}}` (appkit's font preload link), the icon link to `/_appkit/favicon.svg` typed `image/svg+xml`, the deferred script `/_appkit/feedback.js`, and the `title`. The landing page and the about screen begin their body with `{{template "banner" .Banner}}` and end it with `{{template "footer" .Banner}}`; the not-found page ends its body with the footer and draws no banner. No page holds a `style` element, a `style` attribute or a script of its own.

`landing` (file `landing.html`, data `pages.LandingData`). ## The pages handler

`pages.Handler` answers every path `D03-serve` routes to it — `/`, `/about`, and every path that is not a page — behind `identity.Require`, so every request it sees names its caller, and a test wraps it the same way. `/` and `/about` take `GET` and `HEAD`; any other method is refused 405 with `Allow: GET, HEAD` and an empty body, before anything is read. Any other path is the not-found page, status 404, whatever the method, so a path that names nothing is never a 405: a trigger has no page, so `/hourly` is not found, and `/about/` is not redirected. The landing page reads the triggers with one `store.List` call and asks the scheduler for each one's next; when that read fails it answers `503` with the plain text `cannot reach the database; try again later` (`store.Unreachable`, R-CKAM-RO13) and a newline, no banner and no footer, since saying the space has no triggers would be false. The about screen, the not-found page and the 405 read no trigger, so they are answered the same while the database is unreachable. No answer changes a trigger, fires anything or sets a cookie.

Each page drawn is drawn with the banner the banner source returns for the **banner user** — the caller's `X-User-Email` exactly as it arrived and auth's two links; how often the source is called is not fixed. auth's links come from the services file's entry named `auth`, read afresh for every request: its `url` followed by `/` and by `/logout`. With no such entry, an empty `url`, or no usable services file, the space is read from `Host`: a trailing `:` and port digits are dropped, then one leading `cron.` label, and the links are `<scheme>://auth.<space>/` and `<scheme>://auth.<space>/logout`, the scheme being `X-Forwarded-Proto` when that is exactly `http` or exactly `https` and `https` otherwise. What the banner draws from the banner user and the services file — the mark, the profile link titled with the email, the sign-out form, the launcher with its entries in the file's order, a switched-off service titled `<name> is unavailable`, cron's own entry marked current — is appkit's `page` package's output; this design states which data each page is drawn with, and two binary-level requirements prove that the binary's banner source is appkit's kit made for `pages.ServiceName`, drawing the launcher's links in the file's order and reading the services file afresh for every page, and that a services file that does not exist gives no launcher.

## Reading the page

The tests have no HTML parser, since none is an approved dependency, so this design fixes the hooks the templates' opening comments name and the visible text the stories quote, and defines how each is read with the standard library: start and end tags, attributes, element content, normalisation and visible text. Rules about a page's own markup are read over its **written markup**, the body with appkit's banner and footer taken out. The hook requirements are stated for a **plain page request** and a **plain notice banner**, whose inputs carry nothing escaping would change; the byte-for-byte requirements cover every other input, so `html/template`'s contextual autoescaping keeps a caller's, a trigger's or the services file's bytes from becoming markup.

## The head every page carries

Every page carries a `title`, one stylesheet link to `/_appkit/theme.css`, one font preload link drawn by appkit's `preload` template, one icon link to `/_appkit/favicon.svg` typed `image/svg+xml`, one deferred script loading `/_appkit/feedback.js`, and the phone-width viewport. The head is the template's: the notice page, which draws no banner, links the feedback script all the same. The preload link is the one head element appkit draws, because the font's URL carries a hash cron never writes. What the scripts, the icon and the preload do in a browser is a browser's; what is fixed is the start tags a standard-library test can read.

## The shared files

The stylesheet, its three fonts, the launcher's script, the button feedback script, the favicon and the two licences are appkit's: `page.Static()` serves them from files embedded in the binary, and `D03-serve` hands every signed-in request whose path begins `/_appkit/` to it unchanged. The requirements here restate what `S04` fixes about those answers as cron's own behaviour through `web.Handler`, so cron's tests fail if an appkit release stopped giving it. The fonts are served only under **font paths**, names carrying a hash of each font's bytes: the path `page.PreloadURL()` returns and the names the served stylesheet gives in its `url("…")` values; cron never writes a font's name or hash, and a test learns them the same way. Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, which the stories leave open. A request for a shared file without `X-User-Id` is `D03-serve`'s 500.

## Recorded decisions

- The pages handler is stated for `identity.Require(pages.Handler(cfg))`, the wrapping `D03-serve` gives it; the caller's user id is the request's first `X-User-Id`, and the banner user's email its first `X-User-Email`, as it arrived.
- The not-found page is drawn with a banner from the banner source for the request's banner user, though it draws only the footer, so its footer carries the same display string as the other pages.
- The `yours` badge sits in `td.trigger-owner`, after the email, so the seven columns of the story stay seven.
- The empty state is `div#no-triggers.empty` holding an `h3` and a `p`, the design system's empty state.
- The space for auth's links drops a trailing port, then a leading `cron.` compared byte for byte and only when something follows it; the scheme is case-sensitive, as `S03` fixes (`HTTPS` gives `https`, and so does `Http`).
- Every page preloads upright Inter through appkit's `preload` template; no story asks for it and none forbids it, and it changes nothing a user reads.
- The HTML reading vocabulary is defined here once and may be used by any cron document that reads a page.
- Observed with appkit's published `page` package (probe, recorded with this design's evidence): its `banner`, `launcher`, `footer` and `preload` templates, the footer reading `{{.Service}} {{.Version}}`, and every `S04` answer of `page.Static()` — types, strong `ETag`, `Cache-Control`, `304` on a matching `If-None-Match` (`*`, `W/`, lists with empty elements) whatever `If-Modified-Since` says, `200` on a mismatch, `405` with `Allow: GET, HEAD`, and `404` for every other `/_appkit/` path whatever the method.

## Consumer tasks

`web.Handler` calls `set, err := pages.Load()` once, when it is built, and routes every path that is not `/events`, `/declarations`, `/mcp` or under `/_appkit/` to `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, Scheduler: cfg.Scheduler})` inside `identity.Require`. `cli.Run` names the database's, writer's and emitter's service `pages.ServiceName`; `cli.Manifest` carries `pages.Description`; the binary's banner source is `page.New(pages.ServiceName, v).Banner`.

A test of the handler opens a `store.Store` over a temporary database, creates triggers through a scheduler it started with a clock it controls, writes a services file in its temporary directory, builds `identity.Require(pages.Handler(pages.Config{...}))` with a `Banner` closure that records its arguments and returns a fixed `page.Banner`, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of cron's template set from `page.Templates()` and `cron.Assets()`, executes `landing` with the `pages.LandingData` it expects and compares bodies byte for byte, and reads hooks with the reading vocabulary. It calls `SetFailing(true)` on the handle its store was built over to make the database unreachable. A test of the shared files builds `web.Handler` as `D03-serve` states and requests `/_appkit/...` with a non-empty `X-User-Id`, taking the font paths from `page.PreloadURL()` and from the `url("…")` values of the stylesheet it is served. The one exec test of the binary in `cmd/cron` rewrites the services file between two `GET /` requests.
