# D07-trail

The trigger events: the five kinds of event cron emits on the suite's event bus about its triggers, their declaration to the events app, the record of each in cron's own trail, and how the run's emitter delivers them, holds them and drops them while cron serves. `D04-store` declares the `store.Trigger` an event is about; `D05-scheduler` decides when a change or a fire happens, as whom, and for which slot, and calls the two functions declared here; `D03-serve` builds the run's writer and the run's emitter, the latter with the declarations declared here, answers `/declarations` with them, puts a request's identity and event cause on its context, and owns everything about the stop, the `cron: lost event: ` line and the `event.lost` a dropped bus event leaves; `D08-tools` decides which tool calls change a trigger and records `tool.called`. This document declares `internal/trail`.

## The five trigger events

A trigger's life is told by five kinds of event: `created`, `paused`, `resumed` and `deleted`, the **lifecycle** kinds, each made by the one tool call that changes a trigger's existence or status, and `fired`, made by each fire. Each is named `cron.<slug>.<kind>`, the trigger's slug being the middle word, so the name alone says which trigger and what happened; a slug obeys the store's rule (`D04-store`), which makes every such name a valid event name. Each carries the trigger's id under `trigger`, so a trigger's whole story can be followed by its id after its slug has gone to another trigger, and its schedule under `when`, exactly as it was sent; a fire also carries `scheduled`, the slot it fired for, in RFC 3339 UTC to the second. The owner is named by the event's user, which is a user id; that no event carries an email or a credential is `D09-on-a-space`'s (R-Q84O-CC6Z, R-Q9CK-Q3XO).

Every trigger event goes two ways at once: it is recorded in cron's trail through the run's writer, and emitted on the bus through the run's emitter, under the same name, with the same attributes, the same request id and the same user. The bus event has three members the trail record lacks, its own id, its cause and its depth. appkit's emitter does not record what it emits in the trail: given a writer as its `Telemetry`, it records only `event.lost`, for a bus event it drops. So the trail record is made here, by its own call of the writer's `Emit`, and a trigger event is recorded once.

`trail.Lifecycle` and `trail.Fire` are the only way cron makes a trigger event, and each makes both halves in one call, under the context it is given. That context decides who the events are about: a lifecycle event carries the request id and user of the tool call that made it, and the event cause `events.Middleware` read from the call's headers (`D03-serve`), so the bus event of a change made in reaction to an event names that event as its cause, one level deeper; the trail record is the same either way. A fire runs under a context of its own, the trigger's owner with a request id made for that fire and no cause (`D05-scheduler`), so its bus event's cause is empty and its depth 0. Both calls queue and return: no answer and no fire waits for telemetry or the bus, and either half is made whatever becomes of the other.

`update`, a `pause` of a paused trigger, a `resume` of an active one, a refused call and a read make no trigger event (`D05-scheduler`, `D08-tools`); a page, a shared file, the start and the stop record only what `D03-serve` states.

## The declarations

`trail.Emits()` is what the run's emitter is built with (`D03-serve`): one pattern per kind, `cron.*.<kind>`, each with its attribute keys, the four lifecycle kinds with `trigger` and `when`, and `fired` with `trigger`, `when` and `scheduled`, in that order. A concrete name such as `cron.hourly.fired` is governed by its pattern, and appkit refuses an emitted event whose attribute keys are not exactly the declared ones. appkit answers `/declarations` with the emissions sorted by event name and each one's attributes in the order declared, so the body cron serves lists `created`, `deleted`, `fired`, `paused` and `resumed`, and `fired`'s attributes as `trigger`, `when`, `scheduled`. The body `D03-serve` states (R-JQAU-F3FF) is the contract. Event payloads are unaffected: an event's attributes are a JSON object, whose keys appear sorted.

## Delivery while cron serves

The run's emitter takes each bus event into its queue and returns at once. It delivers one event at a time, in the order emitted, to the events app through `Process.EventSink`. An event the bus does not take is tried again, with a pause between attempts through `Process.Sleep`, until five minutes have passed by `Process.Now` since its own first attempt, appkit's `events.DefaultRetryWindow`, which cron does not change; the events behind it wait, and once the head goes through the rest follow at once with no pause. An event the bus refuses for good, with appkit's `events.ErrRejected`, is not tried again. An event emitted while 1024 others wait, appkit's `events.DefaultQueueCapacity`, which cron does not change either, is not queued. Each of these is a drop (`D03-serve`): it leaves its `cron: lost event: ` line and its `event.lost`, and never reaches the bus. A fire whose bus event is dropped still happened: its `last_fired` was written before its events went out (`D05-scheduler`). At the stop the emitter goes on trying within the drain and drops what is left when the drain ends (`D03-serve`); an event emitted once its shutdown has begun is dropped at once.

Because the pause is `Process.Sleep` and the window is measured on `Process.Now`, a test drives an event past its window with a `Sleep` that advances its own clock, and waits no real time.

## Recorded decisions

- The trail record is made by `trail` itself through the writer, not left to the emitter, because appkit's emitter records only `event.lost` (observed: a delivered bus event over an emitter with a writer as its `Telemetry` records nothing in the trail).
- `fired` declares its attributes as `trigger`, `when`, `scheduled`, matching the lifecycle kinds' leading `trigger`, `when`; the order is visible only at `/declarations`.
- The emitter keeps appkit's default retry window and queue capacity: five minutes and 1024 events.
- `Lifecycle` with a kind that is not a lifecycle kind does nothing, so `Fired` cannot be emitted without its `scheduled`.

## Consumer tasks

The scheduler (`D05-scheduler`) calls `trail.Lifecycle(ctx, cfg.Telemetry, cfg.Events, trail.Created, t)` (or `Paused`, `Resumed`, `Deleted`) with the tool call's context once the store holds the change, and `trail.Fire(c, cfg.Telemetry, cfg.Events, t, s)` for a fire under the fire's own context once `last_fired` is written. `cli.Run` (`D03-serve`) builds the emitter with `Emits: trail.Emits()`; `D03-serve` and `D05-scheduler` name events with `trail.Name(slug, trail.Fired)` and the like. A test builds a writer with `telemetry.New` over a `*telemetry.Capture` and an emitter with `events.New` over an `*events.Capture` and `trail.Emits()`, calls `Lifecycle` or `Fire` under `identity.NewContext` (and `events.NewContext` for a cause), flushes both, and compares the captures; it serves `events.DeclarationsHandler(em, nil)` with `httptest` to read the declarations; and it drives `cli.Run` with an `EventSink` that fails, rejects or blocks and a `Sleep` that advances its clock to see a bus event retried, delivered or dropped.
