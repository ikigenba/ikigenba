# Decision 5 — Content-plane citizenship: holder endpoint + `import` acceptor

## Decision.

artifacts conforms to the content plane, `root project/design/D19.md`, in both
roles. Nothing here restates that contract; this Decision fixes artifacts'
concrete endpoints.

**Holder.** A loopback content endpoint, addressed by the service's own key
(the artifact id):

```
GET /content?id=<artifact-id>
```

- Streams the blob with correct `Content-Type` (as D4 derives it) and
  `Content-Length`.
- **Loopback-private by handler guard** — the shared chassis guard: `404`
  whenever the request carries the crossed-nginx marker, same as `/feed`.
  The nginx fragment additionally never proxies `/content` (D8's catch-all
  404s it) — defence in depth, not the mechanism.
- Unknown id → `404`. Visibility does **not** apply on the plane: both
  public and private artifacts are readable on loopback — one box, one
  owner; the public/private split governs the *human* surface (D4) only.
- No `rev` parameter: stored bytes are immutable (no overwrite, D2), so the
  reference's `content_hash` is the whole pin.

The **reference** artifacts emits (in `get`/`list` results, D6, and the
`created` event payload, D7):

```json
{
  "content_url":  "http://127.0.0.1:3009/content?id=<artifact-id>",
  "content_hash": "<64-hex sha256>",
  "size":         184230
}
```

composed from `registry.BaseURL("artifacts")`, never a hand-built literal.

**Acceptor.** `Service.Import(ctx, id Identity, sourceURL, filename,
visibility, description string) (Artifact, error)` — the engine behind the
MCP `import` tool (D6):

1. Validate `filename` (D2), `visibility`, and `sourceURL`: it must parse as
   an absolute `http` URL whose host is `127.0.0.1` or `::1` and whose port
   is one of the shared registry's assigned ports — anything else is a
   `validation` error before any network IO. Confinement is absolute
   (`root project/design/D19.md`).
2. `GET` the source URL; a non-200, connect failure, or read error → a
   `source_unavailable` error, nothing stored.
3. Stream the body through the same cap-hash-blob path as the upload ingress
   (D3 step 5): `MaxBytesReader` at the configured cap (over-cap → a
   `too_large` error, temp discarded), sha256 while streaming, temp+rename.
4. `CreateArtifact` in one transaction (the `created` event rides it, D7).
   Result: the stored artifact, exactly as if uploaded.

`filename` is caller-supplied (the agent carries it from the holder's
metadata alongside the reference) — artifacts never parses a filename out of
a foreign `content_url`.

## Rejected.

- **Deriving the filename from the source URL.** A holder's `content_url` is
  opaque by contract (a consumer never parses it); the caller names the file
  explicitly.
- **Applying visibility on the loopback holder endpoint.** The plane is
  inside the trust boundary; withholding private bytes from co-resident
  services would break "other services can read stored files" while
  protecting nothing (one box, one owner).
- **A `rev` pin.** Immutable bytes make `content_hash` a complete pin; a rev
  would be a second name for the same fact.
- **Hash verification of imported bytes against a caller-supplied expected
  hash.** The agent already carries `content_hash` in the reference, but
  enforcement belongs to consumers that *re-fetch*; the import result
  reports the stored hash, and the caller compares if it cares. Adding a
  parameter would grow the surface for a check one comparison away.

## Verification.

(Real HTTP between two in-process servers: an `httptest`/loopback stub
holder and the real artifacts service, real DB + blob dir.)

- R-441L-GJ14 — `GET /content?id=<stored id>` over loopback returns `200`,
  byte-identical content, correct `Content-Length`, for both a public and a
  **private** artifact; an unknown id returns `404`. Substrate: hermetic.
- R-46HE-82II — the same request carrying the crossed-nginx marker returns
  `404` (the shared guard), for a stored id. Substrate: hermetic.
- R-47PA-LU97 — the reference emitted for a stored artifact carries a
  `content_url` equal to `registry.BaseURL("artifacts") +
  "/content?id=" + id`, the stored 64-hex `content_hash`, and the stored
  `size` — and fetching that exact `content_url` yields bytes whose sha256
  equals the carried hash. Substrate: hermetic (real loopback fetch).
- R-48X6-ZLZW — `Import` from a loopback stub holder (serving a fixture on a
  registry-assigned port) stores an artifact whose bytes are byte-identical
  to the fixture, with the caller's filename/visibility, and returns it; the
  stored file then serves on its D4 URL. Substrate: hermetic (real
  loopback HTTP end to end).
- R-4A53-DDQL — `Import` refuses, with a validation error and **zero network
  IO** (a canary listener records no connection): a non-loopback host, a
  loopback URL on a port outside the registry table, an `https` scheme, and
  a relative URL. Table-driven. Substrate: hermetic.
- R-4BCZ-R5HA — `Import` from a stub returning 404 (and one dropping the
  connection mid-body) stores nothing and returns a `source_unavailable`
  error; a stub body exceeding the configured cap stores nothing and
  returns `too_large`. Substrate: hermetic.
