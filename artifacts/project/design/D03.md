# Decision 3 — Signed upload links: mint + the public upload ingress

## Decision.

The only external way in. Two halves: an owner-side **mint** (reached through
the MCP `upload` tool, D6) and a public, token-guarded **ingress** the minted
URL points at.

**Mint.** `Service.MintUpload(ctx, id Identity, filename, visibility,
description string) (Upload, error)`:

1. `ValidateFilename` (D2); `visibility` must be `public` or `private`;
   `description` optional. Any violation → a `validation` error (D6 maps it).
2. Opportunistic `PurgeExpiredUploads(now)` (D2).
3. Insert an `uploads` row: fresh `token` (D2 generator), `expires_at = now +
   24h` (the product's contractual lifetime, a constant `uploadTTL = 24 *
   time.Hour`).
4. Return the upload facts; D6 renders them, including the absolute
   front-door URL `https://<host>/srv/artifacts/u/<token>` and a ready-made
   `curl -T <file> <url>` command line for the agent to relay. The service
   composes the URL from the request's `Host`/`X-Forwarded-Proto` exactly as
   sites/webhooks compose theirs.

**The ingress.** nginx (D8) proxies `PUT /srv/artifacts/u/<token>` →
loopback `/u/<token>`, ungated. The handler is mounted **bare** — not wrapped
in `rt.RequireIdentity` — and self-guards. Pipeline, in strict order:

1. **Method gate.** Method != `PUT` → `405`. Name-agnostic.
2. **Defense-in-depth.** Any of `X-Owner-Id`, `X-Owner-Email`, `X-Client-Id`
   present → `404` (the request transited a gated front door, which must
   never reach `/u/`). `X-Forwarded-Proto` alone does **not** reject — the
   ingress tier legitimately sets it.
3. **Resolve token.** `strings.TrimPrefix(r.URL.Path, "/u/")`; empty → `404`.
4. **Authenticate the token.** `GetUpload(token)`; unknown token, expired
   (`expires_at` ≤ now), or already consumed → the **identical** `404` with
   the identical body. The token is the whole credential; every failure is
   indistinguishable.
5. **Stream under cap.** Wrap the body in `http.MaxBytesReader` at the
   configured `ARTIFACTS_MAX_UPLOAD_BYTES` (D1) and stream it through a
   sha256 hasher into `BlobStore.Create(artifactID)` (temp+rename, D2), never
   buffering the whole body in memory. Cap exceeded → `413`, temp discarded,
   nothing stored, the link **not** consumed. Any other read/write failure →
   `500`, temp discarded, link not consumed.
6. **Commit.** In one transaction: `CreateArtifact` (fresh id, the upload
   row's owner/filename/description/visibility, observed `size`, computed
   `content_hash`) + `ConsumeUpload(token, artifactID, now)`; the `created`
   event rides the same transaction once D7 wires the producer. If the
   consume reports it lost (a concurrent PUT won), roll back, remove the
   blob, → the uniform `404`. On success → `201` with JSON
   `{"id", "filename", "size", "content_hash", "url"}` where `url` is the
   file's download URL (D4 form, by visibility).

A failed attempt (405/404/413/500) leaves the link exactly as it was: usable
until TTL or a later success. Success kills it: step 4 refuses consumed
tokens, so the second PUT of the same link is `404`.

## Rejected.

- **POST multipart/form-data.** `curl -T` (PUT, raw body) is the simplest
  possible client instruction, has no boundary parsing, and streams
  naturally. A browser form is not a target — the agent-relayed `curl` is.
- **Distinct statuses for unknown vs expired vs consumed.** Enumeration
  resistance: one uniform `404` for every token failure, byte-identical, so
  an outsider cannot probe which tokens exist(ed) or their state.
- **Storing the pending upload's bytes before validating the token.**
  Authenticate first (step 4 precedes step 5); unauthenticated callers spend
  no server IO beyond the header read.
- **A signed-payload scheme (HMAC over the URL).** The token *is* the
  capability, stored server-side with single-use-and-TTL state; an HMAC
  scheme would still need that state to enforce single-use, adding key
  management for nothing.
- **Consume-on-first-attempt.** The operator's promise is "works until TTL
  or success"; burning the link on a failed attempt (a dropped connection, a
  413) would force a re-mint round-trip for every transient failure.

## Verification.

(All exercised via `httptest` driving the real handler over a `Service`
backed by real temp-file SQLite + a real temp-dir `BlobStore` + an injected
clock.)

- R-3MZ0-3QNE — `MintUpload` with a valid filename returns a token-bearing
  upload whose `expires_at` is exactly 24h after the injected now, and the
  rendered URL ends `/srv/artifacts/u/<token>`; a 129-byte filename and a
  visibility outside `public`/`private` each return a validation error and
  insert no row. Substrate: hermetic.
- R-3O6W-HIE3 — a `PUT /u/<token>` of N in-cap bytes against a fresh link
  returns `201` whose JSON names the new artifact id, `size` N, and the
  sha256 of exactly the sent bytes; the artifact row exists with the mint's
  filename/visibility/owner and the blob's bytes are byte-identical to what
  was sent. Substrate: hermetic (real DB, real blob dir).
- R-3PES-VA4S — after a successful upload, a second `PUT` of the same link
  returns `404` and creates nothing; an expired link (clock advanced past
  `expires_at`) returns `404`; an unknown token returns `404` — and all
  three responses are **byte-identical**. Substrate: hermetic.
- R-3QMP-91VH — a `PUT` of cap+1 bytes returns `413`, stores no artifact row
  and no readable blob, and the link then accepts a subsequent in-cap `PUT`
  (`201`) — the failed attempt did not consume it. A `PUT` of exactly the
  cap succeeds. The cap is read from `ARTIFACTS_MAX_UPLOAD_BYTES`, pinned by
  running the same pair at a small configured cap. Substrate: hermetic.
- R-3RUL-MTM6 — a non-`PUT` method to `/u/<token>` returns `405` whether or
  not the token exists. Substrate: hermetic.
- R-3T2I-0LCV — a `PUT /u/<valid token>` carrying `X-Owner-Id` (or
  `X-Owner-Email`, or `X-Client-Id`) is rejected `404` and consumes nothing;
  the same request carrying only `X-Forwarded-Proto` is accepted. Table
  driven over the three identity headers. Substrate: hermetic.
- R-3UAE-ED3K — two concurrent `PUT`s of the same link produce exactly one
  `201` and one `404`; exactly one artifact row and one blob exist
  afterwards. Substrate: hermetic (real DB serializing the consume).
- R-3VIA-S4U9 — `MintUpload` purges: with an expired unconsumed row present,
  a mint call removes it (and only it) while inserting the new row.
  Substrate: hermetic.
