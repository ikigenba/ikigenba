# D08-tools

The four MCP tools agents reach artifacts by through the MCP gateway: `internal/tools`. No tool accepts or returns an artifact's bytes; that is the point of the service. Every signed-in user lists and shows every artifact; only the owner deletes one, and anyone else is refused by name. The bytes are put and got at `/files/<path>` with curl (`D05-files`); `import` (`D09-import`) moves none either: it answers the plan an agent follows to put a file there itself.

## The tools

- `list` takes nothing and answers every artifact, sorted by path, each as the metadata object without `created`, under `artifacts`.
- `show` takes `path` and answers the artifact's metadata object (`files.Metadata`, `D05-files`), whoever owns it.
- `delete` takes `path`, deletes the artifact, owner only, and answers `{"deleted":true,"id":"art_…"}`. It records and emits `artifact.deleted` as the caller (`D07-trail`).
- `import` takes `path` and an optional `content_type` and `expires`, and answers the plan to put a file at that path: its `url`, `method`, `headers` and `instructions` (`D09-import`). It stores nothing and emits nothing.

The metadata object is `files.Describe` of the artifact and artifacts' own address, which the route table puts on the request's context (`D03-serve`): the services file's entry `artifacts`, or, with none, the forwarded scheme and the request's `Host`. Through the gateway the request's `Host` is the gateway's backend name, so on a host and in a sandbox the services file's entry decides the `url`.

## Descriptions

Every tool's description is its own first line, an empty line, and `tools.BytesGuide`, one constant line shared by all four. It names no host and no header: an agent learns those from `import`'s plan, and the address to fetch from the `url` that `show` and `list` answer. So the catalog takes no base, and every `ListTools` and the tools page give the same text whatever the services file says.

## Refusals

A path that breaks the rule (`store.ValidPath`) is refused with `tools.InvalidPath`; a valid path no artifact has with `tools.NoArtifact`; a `delete` by someone other than the owner with `tools.NotOwner`; and the database with `store.Unreachable`. `import`'s own refusals are `D09-import`'s. A refusal is an MCP error result whose text is the copy function's answer, which appkit makes of a handler's error (`ErrorResult(err.Error())`), so a refusal is an error whose `Error` is that answer.

## Recorded decisions

- An invalid path is its own refusal, not "no such artifact" as webhooks refuses an invalid slug: the files surface tells the two apart (400 and 404, decisions document 4), and the tools say the same thing.
- A non-owner's `delete` is refused as not the owner, not as an artifact that does not exist as webhooks does: every user can see every artifact, so hiding its existence would hide nothing (decisions document 8).
- `delete` is `mcp.Destructive`; `list`, `show` and `import` are `mcp.Read`. `import` reads the store to judge the path's owner and changes nothing, so it is a read tool, and the gateway lists it among the read tools.
- `Listed` is its own type, the metadata object less `created`, as webhooks' `ListedWebhook` is; `Metadata` is `files`', declared once (`D05-files`) and answered by `show` as it is.
- `Config` carries `Base` and `Now` for `import`: `Base` is `urls.Configured` of the services file, read once when `web.Handler` is built, the base the plan's `url` is built on, and the clock judges an expiry not later than now (`D09-import`). The other three tools use neither.
- Every tool's description ends with one constant line, `tools.BytesGuide` (decision D32: an agent that reaches artifacts only through the gateway cannot otherwise learn of `/files/<path>`). It names no host, superseding D34's host in the description: the host and the headers now reach an agent in `import`'s plan, where a test proves them (`D09-import`), so the catalog takes no base. Non-normative guidance for the copy `tools.BytesGuide` holds, which binds nothing and which the build may use: "No tool carries bytes: import answers the URL and the instructions to put a file, and show and list answer the url to fetch one."

## Consumer tasks

`D03-serve` registers the tools on the server it mounts at `/mcp` with `tools.Register(srv, tools.Config{Base: urls.Configured(path), Store: st, Telemetry: w, Events: em, Now: p.Now})`. The tools page reads `tools.Catalog()` and `tools.FirstLine` (`D06-pages`). A test builds a store over its own database, an `mcp.Server` with a capturing writer, an emitter over `events.Capture`, registers the tools, serves the server inside `identity.Require` behind a handler that puts a base on the context with `urls.NewContext`, and calls `mcp.Client.CallTool` with `tools.ListArgs{}`, `tools.PathArgs{Path: p}` and `tools.ImportArgs{Path: p}` encoded as JSON, decoding a success result's structured content into `tools.ArtifactList`, `files.Metadata`, `tools.Deleted` or `tools.Plan` and comparing a refusal's text with `tools.NoArtifact(p)`, `tools.InvalidPath(p)`, `tools.NotOwner(p)`, `tools.InvalidExpiry(e)`, `tools.PastExpiry(e)` or `store.Unreachable`.

- R-NGRH-4IUR: The `internal/tools` package MUST export the copy functions `func NoArtifact(path string) string`, `func InvalidPath(path string) string` and `func NotOwner(path string) string`, each answering a non-empty string that contains its argument.

- R-NKF6-9U2U: A `list` call MUST answer a success result whose structured content is an `ArtifactList` holding one `Listed` per artifact `store.List` returns, of every owner, in that order, each with the members of what `files.Describe` returns for that artifact and the base on the call's context (`urls.FromContext`) but `created`, and `artifacts` an empty array when there is none.

- R-NMUZ-1DK8: A `show` or `delete` call MUST be refused with `tools.InvalidPath(path)` when `store.ValidPath(path)` is false, and with `tools.NoArtifact(path)` when the path is valid and no artifact has it, changing nothing and emitting nothing.
