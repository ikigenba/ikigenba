# D09-import

How artifacts copies a file a sibling service holds without the caller touching a byte: `internal/fetch`, which decides whether a URL names a service on this space and fetches it over that service's socket with the caller's identity, and the `import` tool's behavior (`D08-tools` declares the tool, its arguments and its place in the catalog). The case is a scripts run that leaves a file under its `out/`: an agent calls `import` with the run file's URL and a path, and artifacts fetches the file from scripts as the agent, so scripts' own rules decide whether the agent may read it, streams the body into the store as a `PUT` would, and answers the metadata object.

## Which URLs

A URL is on the space when its origin — its scheme and its host, port included, as `net/url` parses them — equals the origin of the `url` of some entry in the services file, artifacts' own entry included. Entries are compared in the file's order and the first match is the target. Anything else is refused before any request is made: a URL that does not parse, one that is not absolute or carries user information, one whose origin no entry has, an entry with no socket, and any URL at all when there is no services file or it cannot be read. The services file is read afresh on each import. Import from public URLs is deferred; the services file is the whole allow list.

## The fetch

The fetch is one `GET` over the target entry's `Socket`, through appkit's `telemetry.SiblingClient` over `telemetry.SocketTransport`, the way the MCP gateway reaches a backend: the request is `http://<name>` followed by the URL's escaped path and query, `<name>` being the entry's name. appkit documents that the sibling client copies the caller on the request's context onto the call as `X-User-Id`, `X-User-Email` and `X-Request-Id` (`identity.Forward`) and records the call as `sibling.called` naming the target, the method and the path; so the sibling sees the agent, its own `identity.Require` admits it, its own rules decide, and the trail shows the hop under the call's request id. A redirect is not followed: any answer but 200 is refused, naming its status. The answer's `Content-Type` is stored verbatim, and absent it is `application/octet-stream`, as a `PUT`'s is; the body is stored as the sibling sent it, no content coding removed.

The whole fetch, from the request to the end of the body, is bounded by `IMPORT_SECONDS`: the bound is a wait on the channel `Process.ImportAfter` returns for the duration the `Settings.Import` method returns (`D01-layout-and-run-seam`), so a test ends it by delivering on that channel. A bound that ends before the body has ended refuses the import and leaves nothing behind.

## The import

`import` checks what it can without the sibling first, in this order: the path, the expiry's form, an expiry not later than now, the URL, and then the store, for an artifact at the path that another user owns. Only then does it ask the sibling. The body then streams into `store.Put` under `ARTIFACT_MAX_BYTES`, owned by the caller, with the expiry given or none, exactly as a `PUT` to `/files/<path>` would (`D04-store`): a new path creates an artifact and emits `artifact.created`, the owner's path is replaced in place under its id and emits `artifact.replaced`, and an absent `expires` clears any expiry. Every refusal leaves the store and the blob directory as they were and emits nothing; each is an MCP error result whose text is one of `tools`' copy functions.

## Recorded decisions

- Origin equality is the test of "a service on this space" (decisions D8): an entry is found by name only and carries an absolute origin, so equality is exact, and no appkit helper exists for it.
- The request goes to `http://<name>/…`, appkit's documented convention for a sibling call, not to the URL's own host; `SocketTransport` dials the socket whatever the host.
- Redirects are not followed: a sibling's 3xx is refused with its status, so what is stored is always the answer of the one URL the caller gave.
- The import's checks that need no sibling come first, so a refused import never makes the sibling serve a body it would throw away; the store checks the owner again when it records, so a path another user creates while the body streams is still refused.
- A body cut off by the sibling (`store.ErrBody`) has its own refusal, apart from a sibling that never answered and from the time bound: they mean different things to an agent deciding whether to retry.
- `ErrTimedOut` reaches the tool through the body's read error, which `store.Put` keeps in its chain (`D04-store`), so the tool tells the bound from a cut-off body without a clock of its own.

## Consumer tasks

`tools.Register` hands `cfg.Fetch` to `fetch.Get` for each `import`: `e, err := fetch.Target(cfg.Fetch.ServicesPath, url)` refuses `fetch.ErrNotOnSpace` early; `res, err := fetch.Get(ctx, cfg.Fetch, url)` answers a `*fetch.Response` or one of `fetch.ErrNotOnSpace`, `fetch.ErrNoAnswer`, `fetch.ErrTimedOut` or a `*fetch.StatusError`; then `st.Put(ctx, store.Draft{Path: p, ContentType: res.ContentType, Expires: exp, OwnerID: c.UserID, OwnerEmail: c.Email, Max: cfg.Max}, res.Body)` and `res.Body.Close()`. A test of `fetch` writes a services file naming a Unix socket in its own temporary directory on which it serves a stand-in sibling, builds a `fetch.Config` with a capturing writer and its own `After`, calls `fetch.Target` and `fetch.Get` under a context carrying a caller (`identity.NewContext`), and inspects what the stand-in received. A test of `import` does the same behind `tools.Register` and `mcp.Client`, then lists the blob directory and the store, and compares refusals with `tools.NotOnSpace(url)`, `tools.FetchFailed(status)`, `tools.FetchTimedOut(url)`, `tools.FetchUnanswered(url)`, `tools.FetchCutOff(url)`, `tools.TooLarge(limit)`, `tools.InvalidExpiry(expires)` and `tools.PastExpiry(expires)`.
