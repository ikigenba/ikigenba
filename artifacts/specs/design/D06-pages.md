# D06-pages

What artifacts draws as HTML: `internal/pages`, the five templates `landing`, `artifact`, `tools`, `about` and `notfound` and the data each receives, and the handler that answers `/`, `/<id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it. It follows webhooks' pages, with prompts' rule for an app whose manifest says `guests = false`, and adds one page webhooks has no counterpart for: an artifact's own page, the precedent for which is scripts' run page. The pages are read-only; nothing on them changes an artifact.

## The pages

The landing page shows one window of the artifacts in the space, whoever owns them, sorted by path, each with its id, path, bytes, content type, the owner's email, its modified time and its expiry, each time in RFC 3339 and to the minute, and the total bytes the space holds, the sum over every artifact, not only the rows shown; which window is the request's `page` query parameter's, stepped forward and back (below). An artifact's page, at `/<id>`, shows the whole metadata object (`D05-files`): its id, path, the absolute `/files/<path>` address its bytes are got at (`urls.File` of `urls.Base`), bytes, content type, SHA-256, the owner's email, and its created, modified and expiry times, each in RFC 3339 and to the second; the template draws the download link from the address. The tools page shows the four tools in registration order (`D08-tools`), each with the first line of its description. The about screen shows the service's name, the banner's `Release` and `Commit` as its version, and `Description`. Bytes are carried as the plain integer, never a humanised size.

The landing page sits at the root of the banner's trail, so its trail is empty. The tools page and the about screen are one level below it, `pages.ToolsLevel` and `pages.AboutLevel`. An artifact's page is one level below it too, named by the artifact's path and pointing at `/<id>`. Any other path is the not-found page, status 404, whatever the method, drawn with the footer only. An id that names no artifact, or a path segment that is not an id, is the not-found page too. The banner's user is the caller's email, with auth's profile and sign-out addresses: auth's entry in the services file when it has one, and otherwise `auth.` and the request's host with its port and a leading `artifacts.` removed, under the forwarded scheme.

Page bodies are never artifact bodies. A path under `/files/` never reaches this handler (`D03-serve` routes it to the files surface, `D05-files`), so no answer of this design is ever given for one.

## Windows, Page, Prev and Next

The landing page lists data agents add, so it pages, as the suite's listing rule asks (`shape/`, Listing; appkit's D25, cited and never restated), following `dummy`'s panel page, the precedent that rule names. `GET /` takes one optional query parameter, `page`, the very token the `list` tool issues as `next` (`paging.Token{Tool: "list"}` over an artifact's path, `D08-tools`), and nothing else is read from the query. A request's **page value** is its first `page` value, empty when it carries none. An empty page value asks for the first window: the first `paging.DefaultLimit` artifacts in ascending byte order of path, the same first page `list` answers with no arguments. A page value the token decodes asks for the window after it: the next `paging.DefaultLimit` artifacts whose path is greater than the one the token holds, whether or not an artifact still has that path, exactly the `artifacts` `list` answers when passed that `page` and no `limit`. `LandingData`'s `Page` is the page value, so the template knows whether it draws the first window, and its `Next` is the very `next` that call answers, empty when no artifact follows the window. The window is always `paging.DefaultLimit` artifacts at most; `limit` is the tool's alone. The handler reads such a window through the store's `List` (`D04-store`), asking for one artifact more than the window, so it never holds more than a window and one row.

The page also steps back. Its `Prev` is a **before-token**, `paging.Token{Tool: "list-before"}` over the path of the window's first artifact, a token only the page issues and `list` never accepts; it is empty on the first window and on an emptied later window. A page value that decodes as a before-token asks for the window before it: the last `paging.DefaultLimit` artifacts whose path is less than the one it holds, whether or not an artifact still has that path, drawn in ascending order; that window's `Next` is the `list` token of its last artifact and its `Prev` the before-token of its first. The page value `last`, the literal word, which decodes as neither token, asks for the last window: the last `paging.DefaultLimit` artifacts in path order, its `Prev` the before-token of its first artifact and its `Next` empty. Both are read through the store's `ListBefore`, the reversed window beside `List`, asking for one artifact more than the window and drawing the first `paging.DefaultLimit` it answers in reverse; when it answers no more than the window, the window wanted is the first window, so the page answers 303 to `/`, the first window's one address. A page value is **decodable** when it is empty, `last`, or decodes as either token. Stepping Next from the first window to the last and Prev back again visits the same windows in reverse and ends on `/`. What the template draws from `Page`, `Prev` and `Next`, the navigation, its links (First, Prev, Next and Last among them) and when they appear, is the asset's. `TotalBytes` is the store's `TotalBytes`, the bytes every artifact in the space holds, on every window, so it never shrinks to the window's sum.

A page value the token cannot decode, one edited by hand, one another tool issued, a word such as `bogus`, names no window, so `GET /` answers it with the not-found page an unknown path gets, never quietly with the first window; the tool's refusal sentence, `paging.BadPage`, stays the agents' interface. The handler decides in the order `dummy` does: identity (`identity.Require`), then the path, then the method, then the page value, and only then reads the store, so the 404 is the same while the store cannot be read, and a method other than `GET` or `HEAD` is the 405 whatever the query. Only a read of `/` reads the page value; every other page ignores its query.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so the host's nginx sends a request with no credential to sign in before it reaches artifacts, and `D03-serve` mounts this handler inside appkit's `identity.Require`, which answers a request without `X-User-Id` itself. So, as in prompts, there is no guest branch and no sign-in address: the page handler is `pages.Handler` wrapped in `identity.Require`, and a test wraps it the same way. A request to `/`, `/tools`, `/about` or `/<id>` whose method is not `GET` or `HEAD` is `405` with `Allow: GET, HEAD`, decided before the store is read and before the page value is read. The landing page, for a page value it can decode, and an artifact's page answer `503` with `store.Unreachable` as plain text when the store cannot be read, as webhooks' landing page does; artifacts has no `unavailable` template.

## Recorded decisions

- An artifact's page is new beside webhooks; its id is the address so a path, which may hold `/`, never has to be decoded from a page URL. Its trail level is the path, not the id (decisions D10).
- No guest branch and no `urls.SignIn`: prompts' `guests = false` precedent, where a request with no `X-User-Id` is `identity.Require`'s answer and draws nothing. The templates' remark that a guest is sent to sign in is nginx's doing.
- The `/<id>` segment is read from the request's escaped path, byte for byte, and must satisfy `store.ValidID`; a percent-encoded, upper-case or trailing-slash form is the not-found page, so there is one address per artifact.
- No `.Mine` on a row: per-user visibility was rejected, and nothing on the pages acts on ownership.
- The landing's times are to the minute (`2006-01-02 15:04`) as webhooks' are; the artifact page's to the second with the zone (`2006-01-02 15:04:05 UTC`), as its template comment says.
- The tools page reads `tools.Catalog()`, as webhooks' does, and shows only each description's first line.
- `Description` is a contract constant with its value stated, not a copy constant: decision 1 fixes it as the manifest's description, text the host parses (`D02-cli`), and the about page shows the same value.
- The about page carries a prose section explaining how the service works, beside the name, version and description list every other app's about page holds alone. It is a departure from every other app, accepted because the copy is useful to an agent reading the page (decisions D10); the design names only the template `about` and its data, `AboutData`, and states nothing of the section.
- The landing page navigates (`design/README.md`, the listing entry decided 2026-10-13): it takes `list`'s token as its own `page` query parameter and shows that window, replacing the first page alone with `Next` for an agent to continue through `list`; `dummy`'s panel page is the precedent. `TotalBytes` keeps meaning the bytes held in all artifacts, as the template says, read from the store in one query rather than summed over rows the page does not hold all of, the same on every window.
- Prev follows the listing entry of `design/README.md` as of commit `f3d0f51`: the before-token is a second `paging.Token` whose tool name, `list-before`, no tool takes, so `list` refuses it with `paging.BadPage` and the page alone pages backward; the before-window is read through `ListBefore` in one bounded query rather than by walking forward. A before-window preceded by at most a window, and `last` over at most a window, redirect to `/` rather than drawing the first window under a second address.
- Last is the literal page value `last`, not a token, so it is a stable, bookmarkable address; it needs no new template data, since the asset draws it from `Next`.
- An undecodable page value is the existing not-found page with its 404, as the listing rule asks, decided before the store is read; there is no page-specific refusal and no template for one.
- A database outage is plain-text 503 with `store.Unreachable` followed by a newline, as webhooks; the about, tools and not-found pages are served without reading the store.

## Consumer tasks

`web.Handler` (`D03-serve`), whose `web.Config` carries no template set, builds one with `s, err := pages.Load()` and mounts `identity.Require(pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store}))` for every path that is not `/files/`, `/mcp`, `/events`, `/declarations` or under `/_appkit/`. On `GET /` the handler reads `v := r.URL.Query().Get("page")`; when `v` is neither empty nor `last` it tries `paging.Token{Tool: "list"}.Decode(v, &key)` and then `paging.Token{Tool: "list-before"}.Decode(v, &key)`, and answers the not-found page when both fail, before the store is read. For an empty `v` or an after-token it calls `rows, err := cfg.Store.List(ctx, a, paging.DefaultLimit+1)`, `a` being nil for an empty `v` and `&key` otherwise, draws the first `paging.DefaultLimit` of `rows`, sets `Next` to `paging.Token{Tool: "list"}.Encode(last.Path)` when `rows` held one more, and, when `v` is not empty and it draws a row, sets `Prev` to `paging.Token{Tool: "list-before"}.Encode(first.Path)`. For a before-token or `last` it calls `rows, err := cfg.Store.ListBefore(ctx, b, paging.DefaultLimit+1)`, `b` being `&key` or nil for `last`; when `len(rows) <= paging.DefaultLimit` it answers 303 with `Location: /`; otherwise it draws `rows[:paging.DefaultLimit]` reversed, sets `Prev` to the before-token of the first row it draws and, for a before-token, `Next` to the `list` token of the last. Either way it calls `total, err := cfg.Store.TotalBytes(ctx)` and sets `Page` to `v`. The about requirement of `D01-layout-and-run-seam` executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}` where `b.Trail` is `[]page.Level{pages.AboutLevel}`; `D02-cli` builds the manifest with `pages.Description`; `main` names the service `pages.ServiceName`. A test builds a store over its own database, puts artifacts, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a `Banner` func returning a fixed banner, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template of its own set writes for a `LandingData` of `ArtifactRow`s, its `TotalBytes`, its `Page`, its `Prev` and its `Next`, an `ArtifactData` with an `ArtifactView`, a `ToolsData` of `ToolRow`s, an `AboutData` or a `NoticeData`; it puts exactly `paging.DefaultLimit` artifacts and then one more, with paths whose byte order differs from their case-folded order, to see `Next` empty and then set, the artifact past the page absent from the rows and its bytes in `TotalBytes`; it requests `/?page=` with that `Next` and compares the rows and `Next` with what a `list` call with that `page` and no `limit` answers; it requests `/?page=bogus`, and a token `paging.Token{Tool: "list_widgets"}` issued, with the store reachable and then failing, to see the not-found page both times; it walks Next from `/` to the end and Prev back, over a count that is not a multiple of the window, comparing each window's rows with the forward walk's in reverse and seeing the last Prev answered 303 to `/`; it requests Prev from the second window to see the 303, a before-token over a path no artifact has to see the window before where it would sort, and `/?page=last` to see the last window, equal to the final window of the walk over a multiple of the window; it turns on `SetFailing(true)` to see the 503.

- R-N886-G4NW: A request to `/`, `/tools`, `/about` or `/` followed by a string for which `store.ValidID` is true, whose method is neither `GET` nor `HEAD`, MUST be answered 405 with an `Allow` header of exactly `GET, HEAD` and an empty body, reading nothing from the store, so that the answer is the same whether or not an artifact has that id.
- R-Z9FD-8LXQ: When the store cannot be read, a `GET` or `HEAD` of `/` whose page value (R-YZO6-6G06) is decodable, and of `/` followed by a string for which `store.ValidID` is true, MUST be answered with a plain refusal (R-CHDX-Q2MD) with status 503 and line `store.Unreachable`, while `/tools`, `/about`, the not-found page of R-N4KH-ATFT and the 404 of R-Z5RO-3APN MUST be answered as when it can.
- R-NANZ-7O5A: A `HEAD` of a page MUST be answered with the status and headers the `GET` of the same page is answered with and no body; and no answer of the page handler MUST change any artifact or set a cookie.
