# D5-web-search-and-fetch

`WebSearch` and `WebFetch` are the web tools. `WebSearch` runs one query against the Brave Search API and answers the results as text; `WebFetch` fetches one public URL and answers its content as text, HTML turned into Markdown, paged with an offset. They mirror the Claude Code harness tools of the same names where a tool without a harness can: the schemas keep the harness's field names, and what the harness does with a model of its own (the `prompt` argument of its fetch, a small model summarizing the page) is absent, because toolkit has no model and the agent reads the page itself.

Neither tool touches the file system, so neither takes a root (D1). `WebSearch` takes the Brave subscription key instead, validated at construction as a root is: an empty or blank key is a constructor error the consumer sees at start, never the model per call. Both block nothing (agentkit D28), so agentkit may run several in one round.

## The client

Both tools take one option, `WithHTTPClient`, which returns an `HTTPClientOption` that is both a `WebSearchOption` and a `WebFetchOption`, the `SkipOption` pattern of D1. It replaces the tool's own client wholesale: every request the tool sends goes through the given client, which is how a consumer sets a proxy, a transport or tighter timeouts, and how the tests reach `httptest` servers on loopback. The Brave endpoint is a fixed `https` URL, unexported; a test reaches a stub for it by giving the tool a client whose transport answers that URL, so the request's path, query and headers are observed at the transport exactly as they would leave the process.

With no option, `WebSearch` uses a plain client with the standard library's defaults and a 30-second timeout, the same duration as `WebFetchTimeout` but unexported, and `WebFetch` builds a guarded one. The guard lives in the dialer: after a name is resolved, a connection to any address in the non-public ranges (loopback, private, shared address space, link-local, unique-local, unspecified, multicast, over IPv4 and IPv6) is refused before it is made, on every connection the client opens, redirect hops included. Checking at dial time, after resolution, is what stops a name that resolves to loopback and a public page that redirects inward. The shared address space (`100.64.0.0/10`) is refused beside the document's ranges because tailnets put their hosts there. Offline tests can reach only loopback with the default client, so the redirect-hop half of the guard is proven by the dial-time rule rather than by a test that redirects; that residual is accepted. This matters because the tool runs inside prompts on a host where services listen on loopback. The default fetch client also ignores the proxy environment, since a proxy is a connection the guard would have to vouch for. That is a property no offline test can tell apart (any proxy a test could start is on loopback, which the guard refuses either way), so it stays in this prose and in the code's documentation rather than in a requirement. A consumer who passes `WithHTTPClient` supplies its own guard or none; the option's documentation says so.

What the tool itself bounds holds whichever client is used: each fetch is limited to `WebFetchTimeout` from the start of the call as well as by the call's context, at most `WebFetchBodyBytes` of the body are read and a longer body is answered as if it ended there, with no mark, and at most ten redirects are followed (Go's default policy stops one short of that, refusing the tenth). The tool applies its redirect limit without touching the consumer's client. Both constants are exported so a consumer can see the limits; a release changes them.

## WebSearch

The input structs D2 to D4 show as code are not shown here: the design format keeps code out of prose, and the schema requirements below say the same thing normatively. The input has `query` (required), `allowed_domains` and `blocked_domains`, the harness tool's three fields, and nothing else: count, freshness, country and language are not the model's to set. Each call sends one GET to Brave's web search endpoint with the key in `X-Subscription-Token`, asking for twenty results with extra snippets, in the `us` market and English; the country and language are fixed by the tool until a consumer needs another market.

The domain lists filter the answer, not the request, so the request has one shape. A result's host matches a listed domain when it equals it or ends in `.` followed by it, ignoring case: `example.com` matches `example.com` and `www.example.com`, never `notexample.com`. An absent or empty `allowed_domains` allows every host; a host matching `blocked_domains` is dropped, even when it also matches `allowed_domains`. The first ten results kept, in Brave's order, are answered.

Each result is one block: a numbered title line, the URL, the description, each extra snippet, and the age labelled `Age:` when Brave gives one, so it is not read as another snippet. Blocks are separated by a blank line. Brave's text is passed through as Brave gives it, including the `<strong>` highlighting it puts in descriptions; only a line break inside a field becomes a space, so one field is always one line. When nothing is kept the answer is `No results.`, not an error.

Any status other than 200 is a `Call` error naming the status. Brave answers errors with a structured body (observed: a bad key is a 422 whose body has `type` `ErrorResponse` and an `error` object with `code` and `detail`), so the error carries that code and detail when the body has them and the body's first line otherwise. No status is given a meaning of its own: the code and detail already say what went wrong.

## WebFetch

The input is `url` (required) and `offset`, a character position in the content, as the harness tool's. Only `http` and `https` URLs with a host are fetched. Redirects are followed across hosts, and the answer reports where the chain ended; the harness hands a cross-host redirect back to the model instead, but a model with no harness is better served by arriving. A final status other than 2xx is an error naming the status, and its body is not answered.

What the model sees depends on the media type. HTML is converted to Markdown with `github.com/JohannesKaufmann/html-to-markdown/v2` (D1): headings, paragraphs, links with their targets made absolute against the final URL so the model can fetch them next, lists, tables, emphasis and code survive; scripts, styles, comments and markup do not. Other text, JSON, XML and JavaScript are answered as they are. Both are first decoded to UTF-8 in the WHATWG order `golang.org/x/net/html/charset` follows: a byte-order mark, then the `Content-Type` charset, then a `<meta>` declaration, then UTF-8 when the body is valid UTF-8, else Windows-1252. The last test looks at the whole body, not the library's first 1024 bytes, so a page with an ASCII head and UTF-8 further down is not misread, and an incomplete character at its end, as a cut at the body cap leaves, does not count against it. Anything else (PDF, images, archives, octet streams) is an error naming the media type: document extraction is the `ocr` sibling's (agentkit D0). A response whose `Content-Type` is absent or does not parse is typed by the standard library's content sniffing.

The answer is a header of three lines (the final URL, the final status, the media type), a blank line, then the content from `offset` on. `offset` counts characters of the content, never of the header, so the same page answers the same content at the same offset whatever its URL's length. The D1 cap applies to the whole answer, header included. A model that sees the truncation marker therefore saw the header plus 30,000 less the header's length characters of content, and calls again with `offset` advanced by that many. An `offset` at or past the end answers the header and one line saying there is no content at that offset and how many characters the content has. Each call fetches afresh; the tool keeps nothing.

## Live tests

A `*_live_test.go` file under the `live` build tag holds the two live tests `toolkit/AGENTS.md` provides for. `TestLiveWebSearch` reads `BRAVE_API_KEY`, fails when it is missing, searches a fixed well-known query and checks that Brave accepts the request and answers results; it prints neither the key nor the response. `TestLiveWebFetch` fetches `https://example.com/` with the default client and checks the header and that the content is Markdown with no markup left. The page carries no heading (observed 2026-10-19: one paragraph), so the test checks its paragraph rather than a heading.

- R-ALUQ-0YW8: Each `WebSearch` call MUST send exactly one HTTP request, a GET to `https://api.search.brave.com/res/v1/web/search` whose query parameters are exactly `q` equal to `query`, `count` equal to `20`, `extra_snippets` equal to `true`, `country` equal to `us`, and `search_lang` equal to `en`, carrying the header `X-Subscription-Token` equal to `key` and the header `Accept` equal to `application/json`.
- R-KDMF-VVQ6: From a 200 response, `WebSearch` MUST take the results from the JSON array `web.results` in order, MUST drop a result whose URL's host matches a `blocked_domains` entry, MUST drop a result whose host matches no `allowed_domains` entry when `allowed_domains` is non-empty, and MUST answer the first ten results kept, where a result's host is its URL's hostname without any port, a host matches an entry when, compared case-insensitively, it equals the entry or ends with `.` followed by the entry, and a result whose URL has no host matches no entry.
- R-KEUC-9NGV: `WebSearch` MUST answer the kept results as blocks separated by one empty line, with nothing before the first block or after the last, block i (counting from 1) being the lines `<i>. <title>`, then `<url>`, then `<description>` when non-empty, then each non-empty element of `extra_snippets` in order, then `Age: <age>` when `age` is present and non-empty, where each field is Brave's string unchanged except that every `\r\n`, `\r`, or `\n` in it is replaced by one space.
- R-APIF-6A4B: When no result is kept, including when the response has no `web.results`, `WebSearch` MUST return the text `No results.` and a nil error.
- R-AQQB-K1V0: When Brave answers a status other than 200, `WebSearch` MUST return an error whose text contains the status code and, when the body is a JSON object with `type` equal to `ErrorResponse` and an `error` object holding `code` and `detail`, both of those values, and otherwise the body's first line.
- R-ARY7-XTLP: When Brave answers 200 with a body that is not a JSON object, `WebSearch` MUST return a non-nil error.
