# Decision 2 — `run`: fragment regeneration and foreground launch

**Decision.**

`nginx/run` is a Bash script (`set -euo pipefail`) that does exactly two things
before handing the process to nginx: it **refreshes the per-service route
fragments** and it **creates the scratch directory nginx will not create for
itself**. It then `exec`s nginx in the foreground, so Ctrl-C stops the front door
and no daemon is left behind.

It resolves its own directory from `BASH_SOURCE` and the repo root as that
directory's parent, so it works from any working directory.

**Fragment regeneration is a verbatim copy, not a render.** For each service, the
script copies `<repo>/<svc>/etc/nginx.conf` — the fragment that service ships and
owns — to `nginx/locations/<svc>.conf`. Nothing is substituted: each fragment
already carries its loopback port as a literal, fixed by `registry/`, because the
same file is installed unchanged on the box by the service's own setup. The dev
front door is therefore the **dev mirror of that install step**, and a service's
route is defined in exactly one place — the service's tree — for both prod and
dev.

Two consequences of copying rather than generating:

- **Idempotent.** Generated fragments are overwritten on every run and are
  gitignored (`locations/*.conf`), with a `.gitkeep` holding the directory. A
  second run behaves like the first.
- **A missing fragment is skipped, not fatal.** The loop tests for the file and
  continues if it is absent, so a half-built checkout still starts a front door
  that routes whatever exists — and `include locations/*.conf` (D1) tolerates
  matching nothing.

**The service list is a literal list in the script**, currently the fifteen
path-routed services: `artifacts crm cron dropbox gmail github ledger notify
prompts repos scripts sites telemetry webhooks wiki`. The dashboard is
deliberately absent — it is not a `/srv/<svc>/` route but the `location /`
upstream (D1).
**Adding a service to the suite means adding its name here**, and that is the
whole wiring cost on this side; no port and no path is written, only the name.
This list must agree with the fragment list `bin/start` carries for its
port-offset mode; a service present in one and absent from the other means the
two dev front doors route different surfaces, which is exactly the drift that
left `/srv/repos/` unreachable on the default path.

**`mkdir -p tmp` is part of the script**, for the same reason it is part of
the config-test command in *Conventions*: `nginx.conf` puts all five scratch
paths under `tmp/`, and nginx creates the leaf directories but not their missing
parent. Without this line a fresh checkout fails at startup with a `mkdir()`
error, which is the failure this line exists to prevent — `logs/`, `tmp/`, and
`nginx.pid` are all gitignored, so a fresh checkout is exactly the case.

**Rejected.**

- *Symlinking each service's fragment instead of copying.* Cheaper to keep in
  step, but stops being the mirror of the install step (the box gets a copy), and
  a dangling link is a worse failure than a skipped file.
- *Deriving the service list from the filesystem (`*/etc/nginx.conf`).* Removes
  the one-line-per-service edit, but silently routes anything that happens to
  have that path, including a scratch or vendored tree, and makes the front door's
  surface unreadable from the script.
- *Reading ports from `registry/` and templating the fragments here.* Duplicates
  a rendering step the services already own, and creates a second place a route
  could be defined — the exact drift the copy avoids.
- *Backgrounding nginx and adding a `stop` script.* Adds pid-file lifecycle to a
  tool whose value is a live log in the terminal; `exec … -g 'daemon off;'` plus
  Ctrl-C needs none of it.
- *Failing when a service's fragment is missing.* Turns an incomplete checkout
  into an unusable front door, when a partial one is strictly more useful.

**Verification.**

This Decision mints **no requirement ids**: it is repo-root shell tooling of the
suite's deliberately untested tier, in a tree no module owns. There is no test
file here for an id tag to live in, and the script's real behavior — nginx coming
up with the right routes — is observed by running it.

Its proof is structural and manual, per *Conventions*:

- `bash -n run` exits 0.
- The script's `for svc in …` list names all fifteen services above —
  `grep -E 'for svc in' run` shows `artifacts` present at the head of the list
  and `repos` between `prompts` and `scripts`.
- After a run, `locations/` contains one `<svc>.conf` per name in the list
  whose service ships `etc/nginx.conf`, each **byte-identical** to that source
  (`diff` reports no difference) — a real check that falsifies a broken copy
  loop, unlike a grep of the script.
- Manually, once: with the suite up, each listed service answers through the
  front door's `/srv/<svc>/` path, and a second `run` in the same checkout starts
  cleanly.
