# Decision 5 — The `michaelgreenly.dev` vhost: the operator's site domain served from `sites`, with a same-origin tracking-beacon proxy to `webhooks`

**Decision.**

The operator's site domain, `michaelgreenly.dev` (product's contractual
constant), is answered by a **named** nginx server file that matches the domain
by `server_name` and proxies it to the `sites` service's public tier, serving
the public site whose slug is **`michaelgreenly-dev`** — and, on one reserved
path `/t`, proxies a same-origin tracking beacon to the `webhooks` ingress. This
tree owns one artifact:

    nginx/michaelgreenly.dev/nginx.conf   installed to /etc/nginx/conf.d/michaelgreenly.dev.conf

It is **committed source, not a template**: nothing in it is per-box
parameterized, so the committed bytes and the installed bytes are identical and
`diff` is the drift check. The one secret it needs (the webhook bearer, below)
lives in a **separate untracked include** placed on the box, never in these
committed bytes. Selection is by name, so it composes with D3 without touching
it: a `Host` of `michaelgreenly.dev` now matches this block and never falls
through to the parked `default_server`, while every other non-apex host still
lands on the parked page and the account's apex block is **not modified**.

**The server file** mirrors the apex/parked port shape so behavior is uniform.
The `:80` block keeps its own ACME location on the **shared** webroot
(`/var/lib/letsencrypt`) so webroot HTTP-01 renewal keeps working once this
named block outranks the parked default for this `Host`, then redirects
everything else to HTTPS. The `:443` block proxies the whole path space to the
sites public tier, **except** the reserved `/t` beacon path, which proxies to
the webhooks ingress:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name michaelgreenly.dev;

    location ^~ /.well-known/acme-challenge/ {
        root /var/lib/letsencrypt;
        default_type "text/plain";
    }

    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name michaelgreenly.dev;

    ssl_certificate     /etc/letsencrypt/live/michaelgreenly.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/michaelgreenly.dev/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;

    add_header Strict-Transport-Security "max-age=31536000" always;

    # Tracking beacon: same-origin POST forwarded to the webhooks ingress as an
    # authenticated inbound trigger. The Authorization bearer is set by the
    # untracked include, never committed here.
    location = /t {
        limit_except POST { deny all; }
        proxy_pass http://127.0.0.1:3006/in/mg-dev-track;
        include /etc/nginx/conf.d/michaelgreenly.dev.secret.conf;
        proxy_set_header X-Correlation-Id "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
    }

    location / {
        proxy_pass http://127.0.0.1:3004/public/michaelgreenly-dev/;
        proxy_set_header X-Correlation-Id "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
    }
}
```

Points of the shape that are decisions, not defaults:

- **The proxy target rewrites the domain root onto one site's public tree.**
  `location /` with a URI-carrying `proxy_pass` maps `/<path>` to
  `/public/michaelgreenly-dev/<path>` on the sites process — the same
  unauthenticated public tier the apex serves at
  `/srv/sites/public/michaelgreenly-dev/` — so the domain serves exactly one
  site, subpaths included, and site content is edited over the sites MCP
  surface with no change to this tree. The proxy headers mirror the sites
  public-tier fragment (empty `X-Correlation-Id`, forwarded `Host` and
  `X-Forwarded-Proto`). If the site is ever deleted or its slug changed, the
  domain serves the sites process's not-found answer — a content problem fixed
  in `sites`, not a config problem fixed here.
- **`/t` is a same-origin beacon sink that authenticates to the webhooks
  ingress.** A page on the site fires a fire-and-forget `POST /t` (its body the
  tracking token); because the page and `/t` share the `michaelgreenly.dev`
  origin, the browser sends it with no CORS preflight. nginx rewrites the exact
  `= /t` location onto the webhooks ingress path `/in/mg-dev-track` and adds the
  `Authorization: Bearer <secret>` that ingress requires (`webhooks` D4), so
  webhooks records the beacon as an authenticated `webhooks:received/mg-dev-track`
  fact. The exact-match `= /t` reserves exactly that one path; every other path
  still falls to `location /` and the site. `limit_except POST { deny all; }`
  means only a POST is ever proxied, so no stray GET carries the bearer
  upstream. The beacon is fire-and-forget: the page does not read the response,
  so the `202` (or any status) is never surfaced to the visitor.
- **The sites port `3004` and the webhooks port `3006` appear as literals.**
  This is the recorded exception in Conventions: each is that service's fixed
  row in `registry/`, pinned here the way the dashboard's apex block pins its
  own `3000`. A vhost cannot receive them through a service-shipped fragment,
  because the fragment maps `/srv/<svc>/` paths, not a domain root or a reserved
  beacon path.
- **The webhook bearer is injected from an untracked include, never committed.**
  The committed vhost carries only the `include
  /etc/nginx/conf.d/michaelgreenly.dev.secret.conf;` directive; the included
  file — placed on the box by the deploy runbook from `~/.secrets`, mode 600,
  never tracked — carries the single line `proxy_set_header Authorization "Bearer
  <secret>";`. So the secret lives in exactly one place on the box and never in
  this tree's bytes, in the served page, or in a QR target. `diff` against the
  committed source stays clean because the secret was never in it.
- **The domain gets its own certificate lineage, `michaelgreenly.dev`.** D3's
  own containment logic decides this: the shared `parked` lineage deliberately
  lets a lapsing member fail the whole renewal, an accepted blast radius when
  every member is a parking page — and an unacceptable one for a live site.
  Like the apex, a live domain rides its own lineage, so no parked-name lapse
  can strip its TLS and its own lapse strips no one else's. The domain is a
  member of the `parked` certificate today; that is harmless (the named block
  wins before certificates matter) but stale, so the **next** parked reissue
  drops it from the parked `-d` list, restoring D3's "the parked lineage names
  exactly the parked domains". Renewal rides the box's existing certbot timer;
  backup rides the existing certificate stream, which archives
  `/etc/letsencrypt` wholesale.
- **HSTS is set, unlike the parked block.** D3 withholds HSTS because an
  unrelated domain must not be pinned to HTTPS by a parking page. This domain
  is the opposite case: dedicated to the operator's own permanently-HTTPS
  site, so pinning is the point. One year, no `includeSubDomains` (no
  subdomains exist), no preload.
- **Bare domain only.** `www.michaelgreenly.dev` has no DNS record (product
  scope excludes it); this file deliberately does not name it, and adding it
  later is DNS plus a certificate change plus a `server_name` edit — a spec
  change here, DNS work elsewhere.

**Installation is an operator runbook step, not code in this tree** — exactly
D3's division. The certificate issuance, the placement of the untracked secret
include, the single `install` command, the validate-and-reload, and the
post-install verification checklist live in the repo-root `deploy.md`, which
this Decision cites and does not restate. Bootstrap order is
**cert-then-secret-then-config**: before this file exists,
`michaelgreenly.dev:80` lands on the parked `default_server`, whose `:80` block
already answers `/.well-known/acme-challenge/` from the shared webroot, so
issuing the new lineage succeeds first; the secret include must be in place
before the config is validated, because the `:443` block's `location = /t`
`include`s it and `nginx -t` reads it; the reverse order fails `nginx -t`,
because the `:443` block names a certificate path or an include path that is not
there yet.

**Rejected.**

- *Beaconing cross-origin straight from the page to the webhooks ingress.* The
  page would have to carry the bearer to authenticate (`webhooks` D4 mandates
  it), exposing the secret in view-source, the network tab, and the QR target;
  and adding an `Authorization` header makes the cross-origin POST a preflighted
  request. Proxying same-origin through `/t`, with nginx holding the secret,
  removes both problems. Rejected.
- *An open, secretless webhook for the beacon.* There is none: the webhooks
  ingress requires `Authorization: Bearer <secret>` on every trigger and returns
  a uniform 404 otherwise (`webhooks` D4). The bearer is not optional, so the
  same-origin secret-injecting proxy is the only secure way to fire it from a
  public page. Rejected.
- *Committing the bearer as a literal in this vhost* (or templating it in at
  install). It would put a live secret in the tree's committed bytes and break
  the `diff` drift check the moment it were redacted. The untracked include
  keeps the committed file secret-free and byte-stable. Rejected.
- *A general custom-domain feature (a domain field on a site, generated vhosts,
  per-domain issuance machinery in `opsctl`).* Real machinery for a portfolio
  of one. The one-off committed file costs a few blocks and forecloses nothing:
  a second custom domain, if it ever exists, is the moment to design the
  feature. Rejected.
- *Serving the site's files from disk in nginx (`root` on the sites state
  tree).* Bypasses the sites process, couples this tree to sites' on-disk
  layout, and reads state paths this tree has no business naming. The public
  tier is already an unauthenticated loopback proxy; use it. Rejected.
- *Routing via the apex (redirect or proxy to
  `int.ikigenba.com/srv/sites/public/…`).* A redirect leaks the suite path
  into the address bar and makes the domain a pointer, not a site; a
  self-proxy through the apex's `:443` re-enters TLS to reach a loopback
  service two hops away. Rejected.
- *Mirroring this vhost into the local dev front door (D1).* The dev front
  door is localhost-only with no TLS and no DNS for the domain, so a mirrored
  block would prove nothing the live check does not — the same reasoning that
  kept the parked block out of D1. Rejected.
- *Including `www`.* No DNS record exists, so a `server_name` for it is dead
  config and a certificate SAN for it would fail HTTP-01 outright. Rejected
  until DNS work (outside this tree) makes it real.
- *An unlisted site instead of a public slug.* The URL-is-credential model
  buys nothing behind a vhost that hides the path anyway, and a rotated token
  would break the committed config. Rejected; a stable public slug is the
  right coupling.

**Verification.**

This Decision mints **no requirement ids**, for D3's reason: its output is one
static committed file plus an untracked box-local secret include and an operator
runbook step; no code runs, no module owns this tree, and the suite's green gate
has nothing it could faithfully assert about it. The claims that matter — the
domain answering with the site over valid TLS from its own lineage while the
apex and the parked names are unaffected, and a same-origin `/t` beacon reaching
the webhooks ingress authenticated — hinge on a real certificate authority, real
DNS, a real nginx selecting by `server_name`, and the real webhooks ingress. They
are verified **once, manually, on the live box**, by the runbook's verification
checklist in the repo-root `deploy.md`, which must include:

- a cert-validating request to `https://michaelgreenly.dev/` returning `200`
  with the site's content (the same content the site serves at its
  `/srv/sites/public/michaelgreenly-dev/` address), the certificate presented
  being the `michaelgreenly.dev` lineage;
- a `POST` to `https://michaelgreenly.dev/t` (with a token body) returning the
  webhooks ingress `202`, and the `mg-dev-track` webhook's `last_triggered_at`
  advancing (or a `webhooks:received/mg-dev-track` fact appearing) — proving the
  same-origin secret-injecting proxy reaches the ingress authenticated; and a
  non-POST to `/t` refused by nginx without being proxied;
- a cert-validating request to at least one other parked name still returning
  the parked page — proving the named block stole only its own domain;
- a cert-validating request to the account apex still returning the dashboard,
  and one `/srv/<svc>/` path still routing — proving non-interference;
- `certbot certificates` showing exactly three lineages — the apex,
  `parked`, and `michaelgreenly.dev` — and, after the next parked reissue,
  the parked lineage no longer naming `michaelgreenly.dev`;
- a `diff` of the installed file against the committed source here, reporting
  no difference (the secret lives only in the separate untracked include, so it
  never appears in this diff).

A build phase realizing this Decision therefore carries deterministic
**structural** exit conditions (the exact committed file at its exact path,
containing both the site proxy and the `/t` beacon proxy), not id-tagged tests.
