# Decision 1 — The local dev front door: one unprivileged nginx on `:8080`

**Decision.**

`nginx/nginx.conf` is a **complete** nginx configuration — `main`, `events`, and
`http` contexts, not a fragment — that reproduces the production apex server
block minus TLS, so `localhost:8080/…` behaves like the account apex does on the
box. It is run unprivileged and in the foreground against this directory as
nginx's prefix, so `-p nginx` makes every relative path in it resolve inside the
tree.

The production apex block it mirrors is **owned elsewhere** (the dashboard ships
it as `dashboard/etc/nginx.conf`), as is the suite's gate-strip-inject contract
and the shape of each `/srv/<svc>/` fragment. This Decision owns only the dev
mirror: it cites those, copies none of them normatively, and adds no routing rule
of its own. If the mirror and the original disagree, the original is right and
this tree is the bug.

**Unprivileged by construction.** Three properties make it runnable by a
developer with no root and no system nginx involvement, and each is load-bearing
rather than incidental:

- **A high port.** `listen 8080` (and the IPv6 sibling) — the box's `:80` is
  taken by apache2 and binding `:80`/`:443` would need privilege anyway. `:8080`
  is the product's contractual constant.
- **Every writable path inside the prefix.** `pid nginx.pid` and the five scratch
  paths (`client_body_temp_path`, `proxy_temp_path`, `fastcgi_temp_path`,
  `uwsgi_temp_path`, `scgi_temp_path`) all resolve under `nginx/tmp/`. The system
  `/etc/nginx` is read only for `mime.types`, and nothing outside the tree is
  written.
- **Logs to the terminal.** `error_log /dev/stderr info` and `access_log
  /dev/stdout`, because the front door runs in the foreground and its whole value
  is watching the request chain happen. Nothing accumulates on disk to be cleaned
  up.

**The routing shape**, in the order the `server` block declares it:

- `location = /_authn` — `internal`, proxying to the dashboard's
  `/internal/authn`. Every `/srv/<svc>/` fragment issues its `auth_request`
  subrequest here. nginx forwards the client's `Authorization` header on its own;
  the config adds `X-Original-URI $request_uri` as the only resource hint, and
  drops the body (`proxy_pass_request_body off` plus an emptied
  `Content-Length`) so the subrequest stays a cheap loopback call. `internal;` is
  what keeps it unreachable from outside — it serves subrequests only.
- `location = /_session-authn` — the cookie-based sibling, proxying to the
  dashboard's `/internal/session-authn`, used by the `sites` PRIVATE tier. Same
  `internal` and same body-dropping shape; the browser's `Cookie` header is what
  carries identity.
- `location @login_bounce` — the login-bounce primitive a session-gated fragment
  opts into with `error_page 401 = @login_bounce;`. A logged-out **navigation**
  (or a client sending no `Sec-Fetch-Mode`) is redirected to `/login` carrying
  where it was headed; a scripted `cors` / `same-origin` / `no-cors` fetch keeps
  its clean `401` so the calling JavaScript can handle it. It must be declared
  **before** the fragment include, because the fragments reference it.
- `include locations/*.conf` — the per-service fragments (D2). A wildcard that
  matches nothing is not an error in nginx, so the front door starts fine with an
  empty `locations/`.
- `location /` — everything else proxies to the dashboard on `127.0.0.1:3000`
  over HTTP/1.1, with `X-Real-IP`, `X-Forwarded-For`, and `X-Forwarded-Proto
  $scheme`. `$scheme` is `http` locally, so the app sees plain HTTP and leaves
  cookies non-`Secure` and HSTS off — the same posture as plain-HTTP localhost.

**`Host` is forwarded as `$http_host`, not `$host`** — the raw header with its
port. The dashboard self-templates URLs (install scripts, MCP resource ids) from
it, so on the dev front door's non-default `:8080` the port must survive the hop.
In production, where `:443` is the default port, the two variables are identical,
so this is a difference the dev mirror needs and prod never notices.

**The dashboard's `127.0.0.1:3000` appears literally here** and is the one port
literal this tree contains: the front door's root proxy has to name a concrete
upstream, and nothing regenerates this file. Every *service* port arrives instead
inside the fragment that service ships (D2), so no `/srv/<svc>/` port is written
in this tree at all.

**Rejected.**

- *Using the system `/etc/nginx` and `sudo`.* Needs root, mutates a shared
  machine, and collides with whatever else runs there. The prefix-local form
  costs one flag.
- *A fragment plus the system's `nginx.conf` for the outer contexts.* Makes the
  dev front door depend on a file nobody in this repo controls, so the same tree
  behaves differently on two machines.
- *Reproducing TLS locally with a self-signed certificate.* Buys nothing the auth
  chain needs, and every client would then need the certificate trusted. TLS
  behavior is a live-box property, verified there.
- *Reusing the production apex block verbatim with variables for the port and
  TLS.* One file serving two very different jobs, each obscuring the other; the
  mirror is short enough to read whole, and drift is caught by using it.
- *Mirroring the parked `default_server` block here (D3).* The dev front door is
  localhost-only, on a high port, with no TLS and no parked DNS — a mirrored
  default host would prove nothing the live check does not.

**Verification.**

This Decision mints **no requirement ids**. Its entire output is one nginx
configuration file; no module owns this tree, nothing here runs under
`go test ./...`, and there is no seam a test could drive. An assertion that
grepped this config for its own directives would be a tautology, not a
falsifiable behavior.

Its proof is therefore of two kinds, both named in *Conventions*:

- **Structural, in-gate for any phase touching it:** `mkdir -p nginx/tmp &&
  nginx -p nginx -c nginx.conf -t` exits 0 — a real nginx parsing the real file,
  which does falsify a broken config.
- **Behavioral, once, against the running stack:** with `bin/start` up, the root
  address returns the dashboard; a `/srv/<svc>/` path with no credentials is
  refused *at the front door*; the same path with valid credentials reaches the
  service with its prefix stripped and its identity headers present. That claim
  hinges on a real nginx running a real `auth_request` against a real dashboard,
  and nothing reachable in-gate can falsify it.
