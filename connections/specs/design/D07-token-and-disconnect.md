# D07-token-and-disconnect

Using and ending a connection: the token route, `GET /token/<provider>`, through which a sibling on the host gets the caller's access token, and the broker's `Token` and `Disconnect`, the operations behind it and behind the landing page's Disconnect form (`D08-pages`) and the `disconnect` tool (`D10-tools`). The broker, its configuration and the provider names it knows are `D06-connect`'s.

## The token route

A connector on the host asks connections' socket for `/token/<provider>` with the identity headers of the user it acts for, the same headers it would send to any sibling, and gets JSON back for every outcome past identity. The route is never reachable from outside: the nginx fragment answers `/token/` 404 at the public name (`D02-cli`), and the socket believes the headers it is sent, as every sibling on the host is trusted (the decisions document's decision 17, `D03-serve`).

The answer is the caller's access token, its expiry, the connected account and the granted scopes. A token with at least two minutes left is answered from the store with no call to the provider; otherwise the broker refreshes it first and stores what the provider answered. A refresh the provider refuses, an HTTP 400 (`D05-providers`), means the grant is gone: the connection is marked broken, `connection.broken` is told as its owner, and the answer is 409 with the connect page the person must open (`D06-connect`'s `urls.Connect`), which every later call answers too, without asking the provider, until the person reconnects. A refresh that fails any other way, the provider unreachable or answering any other status, leaves the connection as it was and answers 502, so the next call tries again. A connection whose granted scopes lack one the provider requests is shown broken (`D10-tools`) but still answers its token: what it was granted still works.

Every refusal is a small JSON object whose `error` member is one of six fixed words, `broker.Refusal`, so a connector can switch on it: `unknown_provider` and `not_connected` (404), `reconnect` (409, with `url`), `provider` (502), `unavailable` (503, the database unreachable) and `method_not_allowed` (405, any method but `GET`).

## Disconnect

`Disconnect` revokes the grant at the provider with the refresh token and then deletes the connection whatever the provider answered, recording and emitting `connection.deleted`; a revoke the provider refused or that failed is recorded in the trail alone as `connection.revoke_failed` with the provider's status (`D09-trail`). A caller with no connection for the provider gets `store.ErrNotFound` and no provider is asked: the form answers it 302 to `/` (`D08-pages`), the tool refuses it.

## Recorded decisions

- The two-minute margin is `broker.RefreshMargin`; an access token whose expiry is at least that far after `Now`, truncated to the second, is answered from the store (brief, decision 6).
- A refresh answers 200 when it succeeds and the store takes the new token; when the store cannot be written after a successful refresh the route answers 503 and the provider's new token is lost. Google keeps the refresh token on refresh, so the next call refreshes again; a provider that rotates refresh tokens would lose the grant, which a second provider entry would have to reconsider.
- A refused refresh whose connection the store cannot then mark broken answers 503 `unavailable`, not 409, and tells no event: the connection was not changed. The next call refreshes, is refused again, and marks it.
- The token route answers JSON for every outcome past identity, the database outage included (`unavailable`, 503) and a method other than `GET` (`method_not_allowed`, 405, `Allow: GET`), rather than the pages' plain refusal: its caller is a program, and the route table hands it every method under `/token/` (`D03-serve`). `HEAD` is not taken: a token's only use is its body. The decisions document does not settle these.
- The provider word of the token route is everything after `/token/` in the escaped path; `/token/`, `/token/google/x` and `/token/goo%67le` name no provider and answer `unknown_provider`.
- Concurrent token requests that both find the access token near expiry both refresh; neither is guarded against the other, since Google answers each and keeps the refresh token.
- `Disconnect` revokes before it deletes and deletes whatever the revoke answered (brief, decision 7). When the store cannot delete after the revoke, the call answers `store.ErrUnreachable` and records and emits no `connection.deleted`, while a revoke that failed is still recorded as `connection.revoke_failed` (root decision); the connection is still stored with a revoked grant, so its next refresh is refused and marks it broken, and a later disconnect deletes it.
- The revoke is sent with the refresh token, never the access token: revoking a refresh token at Google revokes the grant (`D05-providers`).
- The JSON bodies end with one newline, as artifacts' JSON answers do.

## Consumer tasks

A connector on the host runs `GET /token/google` on `/run/ikigenba/connections.sock` with `X-User-Id`, `X-User-Email` and `X-Request-Id` as it received them, decodes a 200 into `broker.Token` and uses `AccessToken` until `Expires`, and on a 409 decodes `broker.Refusal` and hands `URL` to the person. The token route calls `tok, err := b.Token(r.Context(), name)` and answers `tok`, or `broker.Refusal{Error: broker.RefusalReconnect, URL: urls.Connect(urls.Configured(cfg.ServicesPath), name)}` for `broker.ErrReconnect`, and so on. The disconnect form and the `disconnect` tool call `c, err := b.Disconnect(ctx, name)` and tell `store.ErrNotFound` and `store.ErrUnreachable` apart with `errors.Is`. A test builds `web.Handler` over a store on its own database, `Clients` pointed at a fake provider that counts its requests and answers each token or revoke request as the test says, captures for the writer and the emitter, and a fixed `Now`; it seeds a connection with `store.Upsert`, sets its expiry with `store.SetAccess`, sends `GET /token/google` with the identity headers, and compares the body, the store, the fake's request count and the captured events.
