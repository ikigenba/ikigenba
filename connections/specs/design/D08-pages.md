# D08-pages

What connections draws as HTML: `internal/pages`, the five templates `landing`, `notice`, `tools`, `about` and `notfound` and the data each receives, and the handler that answers `/`, `/tools`, `/about`, `POST /<provider>/disconnect` and every other path the route table (`D03-serve`) hands it. It follows artifacts' pages, with auth's profile page as the precedent for a page that acts through POST forms. The connect and callback routes (`D06-connect`) are not this handler's; they draw the notice and not-found pages with this package's set and data types.

## The pages

The landing page shows the caller's own connections, one row per provider the broker knows, in the provider table's order (`D05-providers`): the provider's name and display name, the status `tools.StatusOf` gives (`D10-tools`), and, when the caller has a connection for it, the connected account, the granted scopes as stored, and the connection's created time in RFC 3339 and to the minute. Each row carries its control as a POST form the template draws from the row's name: Connect for a provider not connected, Reconnect and Disconnect otherwise. Connect and Reconnect post to `/<provider>/connect` (`D06-connect`); Disconnect posts to `/<provider>/disconnect`, answered here. Another user's connection is never shown. The tools page shows the three tools in registration order (`D10-tools`), each with the first line of its description. The about screen shows the service's name, the banner's `Release` and `Commit` as its version, and `Description`.

The notice page names why a connect did not complete: the provider's display name and one of seven failures, `pages.FailureMissing` through `pages.FailureAccount`, which the template turns into words. Which route answers it, with which failure and which status, is `D06-connect`'s; this file declares its data. Its data carries no code, token, verifier or state value, so the page cannot show one.

The landing page sits at the root of the banner's trail, so its trail is empty, and so does the notice page. The tools page and the about screen are one level below it, `pages.ToolsLevel` and `pages.AboutLevel`. Any other path is the not-found page, status 404, whatever the method, drawn with the footer only; so is `/<provider>/disconnect` for a provider the broker does not know. The banner's user is the caller's email, with auth's profile and sign-out addresses, as artifacts' are.

## Disconnecting from the page

`POST /<provider>/disconnect` disconnects the caller's connection for that provider through the broker (`D07-token-and-disconnect`), which revokes the grant at the provider, deletes the connection whatever the provider answers, records and emits `connection.deleted`, and records `connection.revoke_failed` when the revoke was not honoured (`D09-trail`). It must carry an `Origin` naming connections' own origin (`urls.SameOrigin`, `D06-connect`); one without it is refused 403 with `urls.CrossOrigin` and nothing happens, no revoke and no delete. Otherwise it answers 302 to `/`, so the browser lands on the list again. With no connection for that provider there is nothing to do: it answers the same 302 and changes nothing. Any other method on that path is 405 with `Allow: POST`.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so the host's nginx sends a request with no credential to sign in before it reaches connections, and `D03-serve` mounts this handler inside appkit's `identity.Require`. There is no guest branch and no sign-in address, as in artifacts. A request to `/`, `/tools` or `/about` whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. The landing page answers 503 with `store.Unreachable` as plain text when the store cannot be read, and so does the disconnect form.

## Recorded decisions

- `POST /<provider>/disconnect` answers 302 to `/` with or without a connection (brief, decision 1): a person who pressed Disconnect twice sees the list, not an error; the `disconnect` tool refuses the same case (`D10-tools`).
- A non-`POST` method on `/<provider>/disconnect` for a known provider is 405 with `Allow: POST`, as artifacts answers a page path's wrong method; the decisions document does not settle it, and a `GET` that disconnected would let a link do it.
- `POST /<provider>/disconnect` requires a same-origin `Origin`, as auth's `POST` forms do (auth's tokens design) and as the connect route's `POST` does (`D06-connect`): auth's session cookie is `SameSite=Lax` on the space's parent domain, so a page on a same-site sibling could otherwise submit the form for a signed-in person. An absent or different `Origin` is 403 with `urls.CrossOrigin` and does nothing. Root decision; the decisions document does not settle it. The check comes after the path names a known provider and the method is `POST`, and before the store is read.
- The notice page's data is `NoticeData` with the provider's display name and the failure; the not-found page has its own `NotFoundData`, where artifacts drew not-found with a `NoticeData` of the banner alone, because here `NoticeData` names the notice page.
- The failure values are contract constants with values stated, not copy: the template compares `.Failure` against them, so a renamed value would break the page without any copy changing.
- The status words and the broken rule are `tools`' (`D10-tools`); the landing page shows exactly the status `list` answers, so the two never disagree.
- The landing's time is to the minute (`2006-01-02 15:04`, UTC) beside RFC 3339 to the second, as the template comment says and artifacts' landing does.
- `Description` is a contract constant with its value stated, as artifacts': decision 1 fixes it as the manifest's description, which the host parses (`D02-cli`).
- The about page carries a prose section on how the service works, as artifacts' does; the design names only the template `about` and its data.
- A database outage is plain-text 503 with `store.Unreachable` followed by a newline, as artifacts; the about, tools and not-found pages are served without reading the store. The plain refusal is defined here because it is first needed here; if another file of this design defines it, that one stands and this definition goes.

## Consumer tasks

`web.Handler` (`D03-serve`) builds a set with `s, err := pages.Load()` and mounts `identity.Require(pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Providers: provs, Store: cfg.Store, Broker: b}))`, `provs` being each `cfg.Clients[i].Provider` in table order; it routes `POST /<provider>/disconnect` for a known provider to that handler inside `events.Middleware` (R-SJQW-F8QB), so the `connection.deleted` it emits carries the request's event cause, and mounts the handler without it for every path that is not `/<provider>/connect` or `/<provider>/callback` for a known provider, `/token/`, `/mcp`, `/events`, `/declarations` or under `/_appkit/`. The connect and callback routes (`D06-connect`) answer the notice page with `s.Write(w, r, status, "notice", pages.NoticeData{Banner: b, DisplayName: p.DisplayName, Failure: pages.FailureExpired})` and an unknown provider with `s.Write(w, r, http.StatusNotFound, "notfound", pages.NotFoundData{Banner: b})`. The about requirement of `D01-layout-and-run-seam` executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}` where `b.Trail` is `[]page.Level{pages.AboutLevel}`; `D02-cli` builds the manifest with `pages.Description`; `main` names the service `pages.ServiceName`. A test builds a store over its own database, upserts connections for two users, builds a broker whose providers point at a loopback fake provider, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a `Banner` func returning a fixed banner, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template of its own set writes for a `LandingData` of `ConnectionRow`s, a `ToolsData` of `ToolRow`s, an `AboutData` or a `NotFoundData`; it posts the disconnect form with and without a same-origin `Origin` and reads the store and the captured events after; it turns the store's failing switch on to see the 503.
