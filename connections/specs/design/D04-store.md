# D04-store

The grants and the flows in flight: `internal/store`, which owns connections' two tables in its SQLite database, `state/connections.db`: `connections`, one row per connection, and `pending`, one row per connect flow that has sent a browser to a provider and not yet come back. It says what a connection and a pending state hold, how a connection is created, replaced, refreshed, broken and deleted, how a pending state is stored and taken exactly once, the errors every consumer tells apart, and the one line every consumer answers when the database cannot be reached. Opening, migrating, transactions and the failure seam are appkit's `db`. It follows artifacts' store without the blob directory, and auth's login states for the pending table.

## One database, one writer

connections is the only writer of its database, and the database is the only record of its connections. `store.New` builds a store over a handle and opens or creates nothing. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds; a test proves the records that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`) answers every call with `ErrUnreachable` and changes nothing. `Config.Now` is the clock every stamp and every expiry comparison is read from, and `Config.Rand` the source connection ids are drawn from; `Run` hands in `Process.Now` and `Process.Rand` (`D01-layout-and-run-seam`).

## Connections

A **connection** is one user's grant at one provider: at most one per user id and provider name, private to that user. Its **id** is `con_` and 16 lowercase hexadecimal digits, 8 bytes drawn from the random source when the connection is first created, drawn again when they are a connection's id already. It keeps the user's id and the email the user's request carried, the provider's name, the connected account's email and subject as the provider named them, the refresh token, the current access token and when it expires, the scopes the provider granted in the order the provider table puts them (`D05-providers`), a **status**, `ok` or `broken`, and **created** and **modified**, every time UTC to the second.

`Upsert` is the callback's one write: it creates the user's connection for the provider, or replaces the grant in the one that exists under the same id and created time, and either way leaves it `ok`, so a reconnect heals a broken connection. `SetAccess` is a refresh's write: the new access token and its expiry, and the refresh token and the granted scopes only when the provider returned new ones. `MarkBroken` is a refused refresh's write. `Delete` removes the connection and answers it as it was, so the disconnect can emit its event with the account and the scopes. `Get` and `List` read only the caller's own; nothing in the store reads across users, which is how every page, tool and the token route show or use only the caller's connections.

## Pending states

A **pending state** is one connect flow in flight: the state value the browser carries to the provider and back, the PKCE verifier, the user's id and email, the provider's name and an expiry. The broker mints the state value and the verifier and sets the expiry (`D06-connect`); the store keeps them. `PutPending` stores one and, in the same write, removes every pending state whose expiry has come, and `PurgeExpiredPending`, which `Run` calls once at start, removes them too; there is no sweeper.

`TakePending` is the callback's one read, and it answers the four ways a state can be refused apart, so the callback names each failure: no such state for this provider (`ErrNotFound`), a state whose expiry has come (`ErrExpired`, and it is removed), a state another user began (`ErrForeign`, and it is left where it is, unused, since the user it belongs to may still come back with it), and otherwise the state itself, removed in the same write so that it is used exactly once, however many callbacks race for it. A state stored for one provider and presented at another's callback is no state for that provider: it is `ErrNotFound` and stays in place.

## Errors

`ErrNotFound`, `ErrExpired` and `ErrForeign` are answers about the call; every other error satisfies `errors.Is(err, ErrUnreachable)`, and every consumer answers it with `Unreachable`, never quoting the cause. A done context or a failing handle is answered first, before any of the others.

## Recorded decisions

- The schema is the one migration `0001_connections.sql`: `connections` (`id` primary key, `user_id`, `user_email`, `provider`, `account_email`, `account_subject`, `refresh_token`, `access_token`, `access_expires`, `scopes`, `status`, `created`, `modified`, with `user_id` and `provider` unique together) and `pending` (`state` primary key, `verifier`, `user_id`, `user_email`, `provider`, `expires`), with an index on `pending.expires`. `scopes` is the granted scopes joined with single spaces, which no scope holds (RFC 6749 §3.3). Times are RFC 3339 UTC to the second, which compare as text. As in artifacts, no requirement states the schema, since a test proves the records through the store; the sandbox check, which seeds a connection straight into `state/connections.db`, writes these columns.
- Refresh and access tokens are stored in plaintext, as webhooks keeps its secrets (the decisions document's decision 13): the database is replicated and backed up as every app's is, and nothing in the suite encrypts at rest.
- The connection's natural key is the user id and the provider name, and every operation but `Upsert` is addressed by it rather than by id: the broker, the pages and the tools all start from the caller and a provider word, and one connection per user per provider makes the pair unique.
- `TakePending` takes the provider and the caller's user id and decides the state's fate in one write, rather than a read the callback judges and a delete after it: the foreign and expired cases differ in whether the state survives, and single use under concurrent callbacks needs the check and the removal together. This departs from auth's `ConsumeLoginState`, which has no user to compare and no expiry of its own.
- A state presented at another provider's callback is answered `ErrNotFound` and left in place (the callback names it `unknown`, `D06-connect`); it is not consumed, since it was not this callback's to use.
- Expiry is "not later than now": a pending state whose expiry equals `Now()` to the second has expired, as an artifact's has in artifacts' store.
- `PutPending` removes expired states including, when the caller hands it one already expired, the one it stores; the broker never does.
- `Upsert` ignores the draft's `ID`, `Status`, `Created` and `Modified`: the store mints the id, sets `ok`, and stamps both times, so no caller can forge a connection's age or carry a broken status into a reconnect.
- `SetAccess` leaves the status as it is: the token route refreshes only an `ok` connection, and a refresh racing a refusal is not worth a guard.
- Ids are drawn from `Config.Rand` only when a connection is created, so a `Rand` that yields 8 bytes and then fails serves one create and any number of replaces, refreshes and pending states. No requirement guards the state value's uniqueness: it is 16 random bytes (`D06-connect`).
- The id redraw is bounded at 8 candidates (root decision): a collision of 8 random bytes is already improbable, so 8 in a row says the random source is broken, and the store answers `ErrUnreachable` and stores nothing rather than loop forever on a source that repeats.
- No `ErrInvalid`: every caller comes through `identity.Require` and a provider found in the table, so an empty user id or provider never reaches the store, and a guard nobody can reach is not a requirement.

## Consumer tasks

The connect route calls `st.PutPending(ctx, store.Pending{State: s, Verifier: v, UserID: c.UserID, UserEmail: c.Email, Provider: p.Name, Expires: now.Add(10 * time.Minute)})`. The callback calls `pd, err := st.TakePending(ctx, state, c.UserID, p.Name)` and names the failure by `errors.Is` with `store.ErrNotFound`, `store.ErrExpired` and `store.ErrForeign`; on success it exchanges with `pd.Verifier` and calls `con, created, err := st.Upsert(ctx, store.Connection{UserID: c.UserID, UserEmail: c.Email, Provider: p.Name, AccountEmail: g.Account.Email, AccountSubject: g.Account.Subject, RefreshToken: g.RefreshToken, AccessToken: g.AccessToken, AccessExpires: g.Expires, Scopes: g.Scopes})`. The token route calls `st.Get(ctx, c.UserID, p.Name)`, after a refresh `st.SetAccess(ctx, c.UserID, p.Name, store.Access{Token: g.AccessToken, Expires: g.Expires, Refresh: g.RefreshToken, Scopes: g.Scopes})`, and after a refusal `st.MarkBroken(ctx, c.UserID, p.Name)`, emitting with the connection it answers. The disconnect calls `st.Get`, revokes, then `st.Delete(ctx, c.UserID, p.Name)`. The landing page and the `list` tool call `st.List(ctx, c.UserID)` and compare `Status` with `store.StatusOK` and `store.StatusBroken`. `Run` calls `st.PurgeExpiredPending(ctx)` once before it serves. Every consumer answers `ErrUnreachable` with `store.Unreachable`. A test opens its own database with `db.Open` and `connections.Migrations()` in its own temporary directory, builds `store.New(d, store.Config{Now: clock, Rand: rnd})`, stores a foreign state with `PutPending` under another user id, flips `d.SetFailing(true)`, and reopens the path to prove what persists.
