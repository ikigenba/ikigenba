# D05-providers

The providers and the OAuth calls: `internal/providers`, which owns the provider table, the one place in connections that names a provider, and the four things connections asks of a provider, the authorization URL a browser is sent to, the exchange of a code for a grant, the refresh of an access token, and the revocation of a grant. Everything else in the app, the store, the routes, the tools, the pages and the events, is written over "a provider": it takes an entry of the table and a `Client` over it, and never compares a provider's name with a word of its own. Google is the only entry.

## An entry

An entry is a `Provider`: its **name**, the word in the routes and in the tools' `provider` argument (`google`); its **display name**, a copy value the pages and the `list` tool show, whose words the source holds; its authorization, token and revocation URLs; the fixed list of scopes it requests, in order; the name under which it grants a scope when that differs from the name it is requested by; the extra authorization parameters it needs; the names of its two manifest secrets, the client id and the client secret; and how the connected account is learned from the token response. `Table()` answers the entries `Run` serves when `Process.Providers` is nil (`D01-layout-and-run-seam`); a test hands `Run` its own table, an entry copied from `Table()` with its three URLs pointed at a loopback fake provider, so every call this design states is proven against the fake, auth's precedent with a table in place of discovery.

Google's entry requests `openid`, `email`, `https://www.googleapis.com/auth/drive`, `https://www.googleapis.com/auth/gmail.readonly` and `https://www.googleapis.com/auth/gmail.compose`, joined with single spaces, and adds `access_type=offline` and `prompt=consent` to the authorization URL so that Google always answers a refresh token. Google grants `email` under the name `https://www.googleapis.com/auth/userinfo.email`, and every other scope under the name it was requested by; `GrantedName` answers that name, so that a consumer can tell whether a connection's granted scopes hold every scope the entry requests (`D10-tools`' `StatusOf` does). The client id and secret are the ones auth reads, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, so production gets the web client and the sandbox the Desktop client with no change outside connections.

The **granted scopes** of a token response are its `scope` member split at spaces (RFC 6749 §3.3), put in the table's order: first the granted name of each scope the entry requests, in the entry's order, when the response names it, then any other scope the response names, in the order it names them. So Google's answer for the seeded grant, which named `userinfo.email`, `drive`, `gmail.compose`, `gmail.readonly` and `openid` in that order, is stored as `openid`, `userinfo.email`, `drive`, `gmail.readonly`, `gmail.compose`, the order every page and tool then shows.

## The calls

A `Client` is an entry with the client credentials the run read for it, the HTTP client every provider call is made through (`Process.HTTP`) and the clock expiries are computed from. `AuthorizeURL` builds the URL the connect route redirects to from a state value, a PKCE verifier and the callback's `redirect_uri`; it sends the S256 challenge of the verifier (RFC 7636 §4.2), never the verifier, and touches no network. The state value and the verifier are the broker's to draw (`D06-connect`).

`Exchange` posts the code, the verifier, the same `redirect_uri` and the client credentials to the token URL, as a form, and answers a `Grant`: the access token, the refresh token, the access token's expiry (now plus `expires_in` seconds), the granted scopes, and the account. `Refresh` posts the refresh token and the client credentials and answers the new access token and expiry, and the refresh token and the granted scopes only when the provider returned them, since a provider may keep the refresh token and may omit `scope` when it is unchanged (RFC 6749 §6, §5.1). `Revoke` posts the token to the revocation URL; revoking a refresh token at Google revokes the grant.

Every failure is one of three kinds, which every consumer tells apart with `errors.Is`. The provider **refused** (`ErrRefused`) when it answered with the status 400, the status RFC 6749 §5.2 gives `invalid_grant`: the code or the refresh token is no good, and asking again will not help; a refused refresh is what makes a connection `broken`. The call **failed** (`ErrFailed`) when no answer came (the provider unreachable, the context done), the answer had any other status that is not 2xx, `401` and every other 4xx and 5xx included, or a 2xx answer was not a usable token response; a failed refresh leaves the connection as it was. The **account** could not be learned (`ErrAccount`) when an exchange the provider granted carried no id token from which a non-empty `email` and `sub` could be read. `HTTPStatus` answers the status the provider answered, 0 when none came, which the disconnect records when a revocation fails (`D09-trail`).

Google's account is learned from the id token the token response carries: its payload, the second dot-separated part of the compact JWT decoded from unpadded base64url, is a JSON object whose `email` and `sub` are the account's email and subject. Its signature is not verified: the token came straight from the token endpoint, over TLS, in answer to the client's own authenticated request, which OpenID Connect Core 1.0 §3.1.3.7, item 6, allows in place of a signature check. An entry names its own way through `Account`, since another provider's id token may carry the account under other claims.

## Microsoft, not built

A Microsoft entry shows the table holds a second provider without a change outside it. Its authorization and token endpoints carry the directory's tenant id in their path, so the entry would need a third setting, the tenant, beside its two secrets, read by `Run` as it reads them; the entry's URLs would be built from it at start rather than written as constants. Its id token may carry the account under other claims than Google's, which its own `Account` would read. Some Graph scopes need an administrator's consent once per tenant before any user can grant them, which happens outside connections. Its revocation shape is not established and would be proven before the entry is built. None of this is built, and no requirement states it.

## Recorded decisions

- **Live probes of Google's refusals, 2026-10-11, bogus values only.** `POST https://oauth2.googleapis.com/revoke` with the form `token=bogus` answered `400`, `Content-Type: application/json; charset=utf-8`, body `{"error": "invalid_token"}`; with no `token` it answered `400` with `"error": "invalid_request"`. `POST https://oauth2.googleapis.com/token` with `grant_type=refresh_token`, `refresh_token=bogus`, `client_id=bogus`, `client_secret=bogus` answered `401` with `{"error": "invalid_client", "error_description": "The OAuth client was not found."}`; an `authorization_code` grant with a bogus code, verifier and client answered the same `401`; a `refresh_token` grant with no client credentials answered `400` with `"error": "invalid_request"` and `"Could not determine client ID from request."`. So Google reads the client credentials from the form body (it found and judged `client_id=bogus` there) and the revocation token from the form body, and every refusal observed is a 4xx with a JSON `error` member. Google's `invalid_grant` for a revoked or bogus refresh token with a real client was not probed, since that needs the real client secret; RFC 6749 §5.2 makes it a `400`. The design classifies by status alone, never by the `error` member: a refusal is a `400`, the status Google's revocation endpoint gave a bad token and the one RFC 6749 §5.2 gives `invalid_grant`.
- Google answers an invalid token at the revocation endpoint with `400`, where RFC 7009 §2.2 says `200`; connections treats any 2xx as revoked and anything else as a failed revocation it records, and deletes the connection either way, so the difference only decides whether a trail event is written.
- A refusal is a `400` only; `401` (`invalid_client`, as observed) and every other non-2xx status is a failure (root decision). A wrong or rotated client secret is the run's fault, not the grant's, and must not mark every user's connection `broken`: the token route answers 502 and the connection heals once the secret is right. The cost is that a provider refusing a dead grant with a status other than 400 would answer 502 on every use instead of asking for a reconnect; Google answers `invalid_grant` with 400 (RFC 6749 §5.2). Revoke is classified the same way, which changes only whether the disconnect's trail event carries a refusal or a failure.
- The successful exchange's shape was proven by the seeded grant's real token response (the members `access_token`, `expires_in` 3599, `id_token`, `refresh_token`, `scope`, `token_type` `Bearer`; the id token's payload carrying `email` and `sub` among others), obtained with the Desktop client and the five scopes. A real refresh response was not observed: the seeded refresh token must not be spent while designing. `Refresh` therefore reads only what RFC 6749 §5.1 and §6 define and treats `refresh_token` and `scope` as optional; the sandbox check, which refreshes against Google with the seeded grant, proves it.
- `token_type` is not checked, and `email_verified` and the id token's `iss`, `aud` and `exp` are not read: Google's internal client admits only the org's accounts (the decisions document's decision 14), the token came from the endpoint connections called, and the account is a label for the person, not an identity connections signs anyone in with. This departs from auth, which verifies the id token against Google's keys because it signs a user in by it.
- `expires_in` is required, though RFC 6749 §5.1 only recommends it: without it connections cannot tell when to refresh. It is bounded to one year, 31536000 seconds (root decision): an unbounded value such as `1e100` makes an expiry `time.Time` cannot hold, so any `expires_in` that is not an integer from 1 to 31536000 makes the response unusable, a failure like a missing `access_token`. The value is read exactly, whatever its notation: `3.6e3` is 3600, while `3600.0000000000001`, which a float64 would round to 3600, is not an integer and is refused; a string such as `"3600"` is not a number and is refused. An exchange without a `refresh_token` is a failure, since the grant would be useless the first time the access token expired; `prompt=consent` with `access_type=offline` makes Google always send one.
- An exchange whose `scope` is absent stores the granted names of the scopes the entry requests, as RFC 6749 §5.1 reads an absent `scope` (identical to the request); a refresh whose `scope` is absent keeps the stored scopes.
- The extra authorization parameters are a field of the entry rather than fixed in `AuthorizeURL`: `access_type` is Google's own parameter, and an entry for another provider would carry its own.
- The fixed authorization parameters are `response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge` and `code_challenge_method=S256`, as RFC 6749 §4.1.1 and RFC 7636 §4.3 name them; auth's design proved Google's authorization endpoint accepts them, and the seeded grant was minted with them and the two extras.
- `DisplayName` is the one copy value the provider table holds rather than an asset: the decisions document's decision 2 makes the display name part of an entry, and the landing and notice templates receive it as `.DisplayName` data, so it is data to every template that shows it. `R-9RK7-ZYCW` requires it non-empty and never states its words; changing them is an edit to the table alone.
- A provider's redirect is never followed (root decision): following a 307 or 308 would re-send the form, `client_secret` and the token included, to whatever URL the `Location` named. A 3xx is a failure carrying its status, like every other non-2xx answer but 400, whatever redirect policy the run's HTTP client has.
- A `scope` member that is present but empty, or holds only spaces, is read as absent: an exchange then stores the requested scopes' granted names, and a refresh keeps the stored ones, rather than storing an empty list that would show the connection `broken`.
- Each call sends one request and never retries: a code is single-use, and a refresh retried after a timeout could spend a rotated token twice. The response body is read whole without a cap: the provider is a trusted, fixed endpoint, and `memory_max` bounds the process.
- No error text carries a credential: the client secret, the code, the verifier and every token are sent only in a request body, never in a URL, so the transport's errors, which quote the URL, cannot hold one.
- The broker draws the verifier and the state value itself (`D06-connect`), and finds an entry among the run's clients by name, so providers exports no verifier minting and no table lookup; `Challenge` stays exported so a test can check the `code_challenge` a URL carries.

## Consumer tasks

`Run` takes `p.Providers`, or `providers.Table()` when it is nil, and for each entry `e` reads `e.ClientIDVar` and `e.ClientSecretVar` through `LookupEnv`, refusing to start when either is missing (`D01-layout-and-run-seam`), and builds `providers.Client{Provider: e, ID: id, Secret: secret, HTTP: hc, Now: now}` for `web.Config.Clients` (`D03-serve`). The broker's connect finds the client whose `Provider.Name` is the path's name among those clients, draws a verifier, stores the pending state, and redirects to `cl.AuthorizeURL(state, v, origin+"/"+e.Name+"/callback")`. The callback calls `g, err := cl.Exchange(ctx, code, pd.Verifier, redirectURI)` and answers `account` when `errors.Is(err, providers.ErrAccount)` and `exchange` for any other error, then upserts `g`. The token route calls `g, err := cl.Refresh(ctx, con.RefreshToken)`, marks the connection broken when `errors.Is(err, providers.ErrRefused)` and answers 502 otherwise. The disconnect calls `err := cl.Revoke(ctx, con.RefreshToken)` and, when it is not nil, records `providers.HTTPStatus(err)`. The tools and pages range over the table for `Name` and `DisplayName` and compare a connection's scopes with `e.GrantedName(s)` for each `s` in `e.Scopes`. A test starts an `httptest.Server` as the fake provider, copies `providers.Table()[0]` with `AuthorizeURL`, `TokenURL` and `RevokeURL` pointed at it, builds a `Client` with the server's client and a fixed `Now`, and checks each call's request form and its answer for 2xx, 4xx, 5xx, a closed server and malformed bodies, with `providers.Challenge` and RFC 7636's Appendix B vector.
