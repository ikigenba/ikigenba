# D09-trail

The trail as a whole: the closed set of event names campaigns records, the request pair the telemetry middleware records for every request, `sibling.called` for every request to candidates and to artifacts, the trail records of the four bus events, `campaign.visited` for every visit the guest route records, the clock and the random source every event is stamped and named from, and secrecy, stated once for the whole app. Decisions cited as doc N are /home/mgreenly/Documents/ikigenba-campaigns.md; those cited as log DN are /home/mgreenly/Documents/ikigenba-campaigns-decisions.md. Decisions cited as hand-picked outcome N are /home/mgreenly/Documents/ikigenba-campaigns-hand-picked.md; those cited as delivery log PN or delivery log S1-N are /home/mgreenly/Documents/ikigenba-campaigns-hand-picked-decisions.md.

Who records each name is another document's. The request pair is appkit's `telemetry.Middleware`'s, which `D03-serve` mounts on every request; `tool.called` is appkit's MCP server's; `service.started` and `service.stopping` are `D03-serve`'s, through the run's writer; `event.lost` is appkit's emitter's, since the emitter is built with the writer; `sibling.called` is appkit's `candidates` client's and appkit's `artifacts` client's, each of which records one for every request it sends. Three of the four bus names are recorded by package `tools`, through package `trail`'s `MemberAdded`, `MemberRejected` and `PieceDelivered`; the fourth, `campaign.member.opened`, is recorded by package `links`, through `trail.MemberOpened`, on a member's first visit and in the sweep `links` runs, an hour after the start and every hour after that (delivery log P8, delivery log S1-2). Each of the four functions records the trail half and emits the bus half at once; those functions, the name constants `trail.EventMemberAdded`, `trail.EventMemberRejected`, `trail.EventPieceDelivered` and `trail.EventMemberOpened`, `trail.Emits` and the events' attributes are `D05-events`'; which calls change something and so make one is `D08-tools`'; which visit opens a member and which members the sweep reports are `D06-links`' and `D04-store`'s; when the sweep runs is `D03-serve`'s. `campaign.visited` is recorded by package `links`, through `trail.Visited` under the name `trail.EventVisited`, both `D05-events`'; which requests are visits is `D06-links`'. This document states what the assembled run shows of them.

## The request pair

Every request, whatever its path and whether or not it carries an identity, is recorded by the telemetry middleware as one `request.started` (method, path) and one `request.finished` (status, duration, bytes), under its request id and its caller's user. The path is the request's URL path without its query. A visit to the guest route is a request like any other, so its `request.started` carries `/t/<token>`: the token reaches the trail there, and only there. A token is a tracking handle, not a credential: it opens nothing, answers nothing but a redirect to a destination the owner chose to make public, and holds nothing about the business it was sent to (doc 11, log D12), so the path is recorded whole, as appkit's middleware records every path, rather than masked by a middleware of campaigns' own. The visit's referrer, given in the `r` query parameter (log D10), never reaches the trail, since the query is not recorded. A delivery from the bus is a request too, `POST /events`, answered by appkit's delivery handler with no handlers, and records the request pair alone.

## The bus names in the trail

`campaign.member.added`, `campaign.member.rejected`, `campaign.piece.delivered` and `campaign.member.opened` go two ways at once, as cron's trigger events do: emitted on the bus through the run's emitter (`D05-events`) and recorded in the trail through the run's writer, under the same name, with the same attributes (`campaign`, `candidate`, `prospect_list`; `campaign`, `candidate`, `reason`; `campaign`, `candidate`, `piece`, `channel`, `how`; `campaign`, `candidate`, `at`; every value a string), the same request id and the same user. appkit's emitter records only `event.lost` in the trail, so the trail record is made by `trail` itself through the writer. Each of the first three is recorded under the tool call's context, so its request id and user are the call's, and before that call's `tool.called`; and it is recorded whatever becomes of its bus half, delivered, retried or dropped. What a drop leaves in the trail is this document's: appkit's emitter, built with the run's writer, records one `event.lost` for each bus event it drops, with `event`, the bus event's id, and `cause`, its cause, under the bus event's request id and user; the trail record of the change stays, so the trail shows both that the change happened and that the bus never heard of it. The line a drop writes to standard error is `D03-serve`'s. A call that changes nothing, a refused call and a read record none (log D22).

`campaign.member.opened` tells that a member's link was opened for the first time: `campaign`, the campaign's id, `candidate`, the member's candidate id, and `at`, the time of the member's earliest visit in RFC 3339, in UTC to the second. It is recorded once per member, whichever way it is found. On a visit, it is recorded under the visit request's id with no user, as `campaign.visited` is, after that request's `campaign.visited` and before its `request.finished`, so the trail reads the visit and the opening as one request. In the hourly sweep, which reports every member of a live campaign that has been visited and never reported, such as one the previous release saw visited, it is recorded with neither a request id nor a user, since no request asked for it; an empty request id is how the trail tells a backfilled opening from a live one (delivery log P8, hand-picked outcome 15). Like the other three, it is recorded in the trail whatever becomes of its bus half, and a drop leaves its `event.lost` beside it.

## campaign.visited

Each visit the guest route records (`D06-links`) is told by one `campaign.visited`, with `campaign`, the campaign's id, and `piece`, the piece's id, both strings, under the visit request's id and with no user, whatever identity headers the request carries (`D06-links`), so the visit event itself never names who opened the link; the request pair around it, recorded by appkit's `telemetry.Middleware`, records whatever user the request carries, so a signed-in owner's own visit shows that owner's user on its `request.started` and `request.finished` and none on its `campaign.visited`. It carries neither the token nor anything the visit's request shows: the visit's user agent, referrer and address are kept in the store, for `engagement` and the campaign page, and nowhere else (doc 13). A request that records no visit, an unknown token, a deleted campaign's token, a method other than `GET` and `HEAD`, a path under `/t/` that is not one token, records no `campaign.visited` and no `campaign.member.opened`. A member's first visit is told by both its `campaign.visited` and its `campaign.member.opened`; every later visit of that member, by any of its pieces, by its `campaign.visited` alone.

## sibling.called

One `sibling.called` per request to candidates: `target` `candidates`, the services file's entry name, `method` `POST`, `path` `/mcp`, the status answered and `duration_us`, as appkit's `candidates` client records it for every `ProspectList` and `Candidate` call (`add_prospect_list`, `add_member`, `add_members`, `merge_list`, and the campaign page's names). One per request to artifacts: `target` `artifacts`, with the method and path appkit's `artifacts` client sends for each of `Head` and `Show`, which `add_material` calls in that order, `Show` only once `Head` has passed (appkit/artifacts Head and Show (D22, v0.29.0; log D23)). Each carries the request id and user of the tool call or page request it was made for, since appkit's clients forward the caller on the context. campaigns calls no other sibling (doc 19, `D01-layout-and-run-seam`), so no `sibling.called` names a target but `candidates` and `artifacts`. What travels in a request body, a prospect list id or a candidate id, and what candidates answers, a business's name, address, phone, email and people, reach no event.

## The clock and the random source

Every event's time is read from `Process.Now`, and every request id the run mints and every bus event id are drawn from `Process.Rand` (`D01-layout-and-run-seam`). A test fills them with a fixed clock and a constant reader and finds the stamps and ids those give. Which ids, tokens and times the store mints from the same two is `D04-store`'s.

## Secrecy

No event, in the trail or on the bus, carries a business's name, other names, street, city, state, ZIP, county, phone, email or people, a visit's user agent, referrer or address, a token (but for the request pair's path), a campaign's name, description or destination, or a material's label. Events carry ids, channel and method words, tool names, counts and times, and the one sentence a person wrote that the bus carries by design, a rejection's `reason` (log D15). What candidates answers about a business reaches `merge_list`'s answer and the campaign page's names, which is what they are for; what a visit shows reaches `engagement`'s answer. Standard output and standard error carry none of it either. The rule is proved at the run seam, by use, as candidates proves its own: a fake candidates answers businesses whose every field holds a random **marker**, some of its answers are failures whose bodies echo every marker, the test's visits carry markers as user agent, referrer and address, its campaigns and materials are named with markers, and every capture of the run is searched for every marker and every token.

## Recorded decisions

- **A token is a tracking handle, not a credential** (doc 11, log D10, log D12; this design's choice of where it may appear): the request pair records `/t/<token>` as appkit's middleware records every path. Masking it would mean a middleware of campaigns' own beside appkit's, for a value that grants nothing; the trail is read only by the space's agents and owner, who can already read every token through `merge_list`. Every other event is required to hold no token, so the request pair is its only place.
- **The bus names are recorded through the writer by `trail`**, as cron records its own (cron's trail): appkit's emitter records no trail event for what it emits. The record is one event under the bus event's name, attributes, request id and user, not a second name, so the closed set grows by the four bus names only.
- **`campaign.visited` is a trail name, not a bus event** (log D15 names three bus events only; delivery log P7, hand-picked outcome 13 keep it so): a single visit changes no candidate's history, and nothing on the suite subscribes to it. It carries ids only, so that the trail can count visits per piece without holding what the store keeps about the visitor. What does change a candidate's history, that a member opened a link at all, is told once per member by the fourth bus event, `campaign.member.opened`.
- **`campaign.member.opened` carries no user** (delivery log P7, hand-picked outcome 13): it tells what a guest did, as `campaign.visited` does, so a signed-in owner's own first visit records the owner on the request pair only. Its pair with the bus event is proved in the assembled run, as the other three are, with the further conditions a visit's event and a sweep's event each meet.
- **The sweep's events carry no request id** (delivery log P8, delivery log S1-2, hand-picked outcome 15): the sweep, which since S1-2 runs each hour after the start rather than at it, answers no request, and minting an id for it would make a backfilled opening read as a request the trail never shows. Rejected for the backfill: a migration, which cannot reach the bus, and a command-line subcommand, which contradicts `D02-cli`'s rule that a command emits nothing.
- **This document declares no name.** The five constants, `trail.EventMemberAdded`, `trail.EventMemberRejected`, `trail.EventPieceDelivered`, `trail.EventMemberOpened` and `trail.EventVisited`, and the functions that record them are `D05-events`', so `trail` holds each name once; this document states what the assembled run shows of them, which a test of `trail` alone cannot: that the tools, the guest route and the sweep call them, under the request's context or none, and that nothing else reaches the trail.
- **Departure: a rejection's `why` is not a secrecy marker** (from candidates' trail, where every person-written text is a marker). It reaches the trail and the bus as `reason` (log D15): the owner writes it for candidates and agents to read. It is the one person-written text an event carries, so the secrecy conditions give no marker in it; a campaign's name and description, its destination and a material's label are carried by no event and are markers.
- **A material's path is not a marker**: appkit's `artifacts` client may send the path it checks in the request's path, which `sibling.called` records, and an artifact path names a file the space keeps, not a business.
- **Departure: secrecy under a failing database is not proved here** (from candidates' trail, which proves it at its handler). candidates proves it at its handler with `SetFailing(true)` on a handle it hands in; the run builds its store over its own handle, so the run seam cannot provoke it. A store failure's refusal and the guest route's answer to it are fixed copy and a redirect (`D08-tools`, `D06-links`) and hold no value the store or a sibling supplied, so it has nothing to leak.
- Markers are compared without regard to letter case and phone markers as digits, as candidates' are, and tokens without regard to case, since the guest route matches a token so (log D22).
