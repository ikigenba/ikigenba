The campaign events: the four kinds of event campaigns emits on the suite's event bus when a member is added, a member is rejected, a piece is delivered (doc 16, log D15), or a member first opens a link (hand-picked outcome 13), the record of each in campaigns' own trail, the trail-only record of a visit, their declarations, and the two bus paths the events app reaches campaigns on. This document declares `internal/trail`. `D04-store` decides what a change is and reports whether one happened; `D08-tools` decides which tool calls change something and calls the recording functions declared here; `D06-links` calls `Visited` for each visit and `MemberOpened` for a member's first visit, both on the live path and in the hourly sweep that catches up members whose first visit went untold; `D04-store` keeps the marker that makes the opened event once per member per campaign; `D03-serve` builds the run's writer and emitter, the latter with the declarations declared here, mounts `/events` and `/declarations`, puts a request's identity and event cause on its context, and owns the `lost event` line a dropped bus event leaves on stderr; `D09-trail` owns the closed set of telemetry event names, which includes the five names declared here, the trail's secrecy, and the `event.lost` a dropped bus event leaves in the trail (R-XYH1-M8MI).

## The four bus events

A member's and a piece's life in a campaign is told on the bus by four events, each with fixed attribute keys, every key always present and every value a string:

- `campaign.member.added`: `campaign` (the campaign's id), `candidate` (the candidate id as given, log D1), `prospect_list` (the `pl_` id of the prospect list the member came from, empty when added by id: `add_member`, `add_members`).
- `campaign.member.rejected`: `campaign`, `candidate`, `reason` (the owner's sentence saying why).
- `campaign.piece.delivered`: `campaign`, `candidate`, `piece` (the piece's id), `channel` (`mail` or `email`), `how` (`hand` in this version, doc 8; `system` once the system sends).
- `campaign.member.opened`: `campaign`, `candidate`, `at` (the member's earliest visit, RFC 3339 text in UTC to the second).

The names are literal, not patterns: the middle word is the thing the event is about, not a slug, so `candidates` subscribes to each by its exact name (log D15). The time of the first three is the bus event's own `Time`, so no attribute repeats it (log D3 named a time; the envelope carries it). The opened event carries `at` because the sweep may tell it long after the visit, so its envelope's `Time` is not the first visit's (hand-picked outcome 13). Ids, words and the owner's reason only; never a business name, address, phone, email, token or link.

## Two ways at once

Every bus event goes two ways at once, as cron's trigger events and candidates' pass events do: it is recorded in campaigns' trail through the run's writer, and emitted on the bus through the run's emitter, under the same name, with the same attributes, the same request id and the same user. appkit's emitter records only `event.lost` in the trail, so the trail record is made here by its own call of the writer's `Emit`, and each event is recorded once.

`trail.MemberAdded`, `trail.MemberRejected`, `trail.PieceDelivered` and `trail.MemberOpened` are the only way campaigns makes one of these events, and each makes both halves in one call under the context it is given. The first three are told as the tool's caller: the request id and user are those of the `identity.Caller` on the context, and the bus event's cause is the event cause `events.Middleware` read from the call's headers, one level deeper, or none. Each call queues and returns: no answer waits for telemetry or the bus, and either half is made whatever becomes of the other. A bus event the emitter fails to deliver, refuses as malformed, or drops at a full queue or at the stop does not fail the call and does not undo the trail record or the change; the emitter retries and drops as appkit's defaults say, and what a drop leaves is owned elsewhere: the `event.lost` it leaves in the trail is `D09-trail`'s (R-XYH1-M8MI), and the `lost event` line on stderr is `D03-serve`'s. The functions return nothing.

## The visit

`trail.Visited` records `campaign.visited` in the trail, with `campaign` and `piece` and nothing else, under the request's request id and with no user, so a signed-in owner's `campaign.visited` reads as any visitor's does (`D06-links`); the request pair `telemetry.Middleware` records for the same request still carries `X-User-Id`, and that pair is `D03-serve`'s and `D09-trail`'s; it takes no emitter and emits nothing on the bus. It records through a context of its own: appkit's `identity.NewContext(ctx, identity.Caller{RequestID: c.RequestID})`, `c` being the caller `identity.FromContext(ctx)` answers, so the writer's `Emit` finds the request id and an empty `UserID`. The visitor's user agent, referrer and address are kept in the store (`D04-store`, doc 13); keeping them out of telemetry is this design's own choice.

## The first open

`trail.MemberOpened` makes `campaign.member.opened`, both halves, for a member whose first visit `D04-store` has just marked, from the visit itself or from the hourly sweep. It is told as a visit is: under appkit's `identity.NewContext(ctx, identity.Caller{RequestID: c.RequestID})`, so both halves carry the request id of the context's caller and an empty user, a signed-in owner's open reading as any visitor's (delivery log P7). Its bus event's cause follows the same rule as the other three, one level below a well-formed cause on the context, or none; a visit and the sweep carry none. It takes the first visit's time as a `time.Time` and writes it as `at`, converted to UTC and cut to the second, so a sub-second or non-UTC time never reaches the bus. Like the others it queues and returns, and either half is made whatever becomes of the other.

## The declarations

`trail.Emits()` is what the run's emitter is built with: the four names, literal, each with its attribute keys in the order listed above, the opened event appended last, so appkit refuses a campaign event whose keys are not exactly these. `campaign.visited` is not declared: it never goes on the bus.

campaigns accepts no bus event. The events app reaches it at its socket on `/events`, where it would deliver accepted events, answered by appkit's `events.DeliveryHandler` with no handlers, and `/declarations`, answered by `events.DeclarationsHandler` over the run's emitter with no handlers. appkit answers the declarations with the emissions sorted by event name, each one's attributes in the order declared, and `accepts` empty; the opened event, declared last, therefore answers second, between added and rejected. The body is stated below because its content is this document's declarations; the routes, their place outside the identity gate, and nginx's 404 for both at the public name are `D03-serve`'s and `D10-on-a-space`'s. That campaigns accepts nothing is contract here: the run's handler answers at `/events` exactly as `events.DeliveryHandler(nil)` does, so a well-formed delivery of any event finds no handler and is answered 404 with an empty body.

## Recorded decisions

- The bus event names and keys are log D15's, finalized here, with the list's key named `prospect_list` by the funnel rename (decision 6): `prospect_list` on added, `reason` on rejected, `piece`, `channel` and `how` on delivered, each after `campaign` and `candidate`; every key always present, as appkit's exact-keys rule requires, so `prospect_list` is the empty string for a member added one at a time (log D15).
- **The event names stay; only the added event's list key moves**, in one release: candidates, the one subscriber, accepts both the new key and the previous release's (L `cohort`) this release, so a payload the previous release emitted, delivered or redelivered across the upgrade, and one this release emits, are both read. The previous release's key is not also sent: appkit's exact-keys rule would make it a second declared key, and the payload is the list's id in either case.
- No time attribute on added, rejected and delivered: log D3 listed a time in the payload, and the bus event's envelope `Time` is that time; repeating it would invite two clocks.
- `reason` carries the owner's rejection sentence as given (log D15). It is the owner's words about the campaign, not a business's contact data, which no event carries.
- The recording functions take plain strings, not store records, so the trail's contract does not move when a store record gains a field, and a caller names exactly what it tells.
- **Told as the caller**, unlike candidates' pass events, which are told as the pass's starter: the added, rejected and delivered events are made inside the tool call that made the change, so the call's own identity and cause are the right ones (as cron's lifecycle events); the opened event is made on a visit or by the hourly sweep, with no user, as the `campaign.member.opened` decisions below say.
- `campaign.visited` is trail-only, this design's own choice: a visit is the owner's engagement data, read through `engagement`; nothing on the suite subscribes to it, and the bus would carry a visitor-driven rate of events. It carries ids only; the visitor's user agent, referrer and address stay in the store.
- **`campaign.visited` names no user**, keeping the request id, to match `D06-links`, which ignores identity on `/t/`: a signed-in owner's `campaign.visited` is recorded as any visitor's is. This covers `campaign.visited` alone: the request pair still names the user, and it is `D03-serve`'s and `D09-trail`'s. Done with appkit's existing `identity.NewContext` and `identity.Caller`, no library change. A decision of this design, settled by the root for this delivery: the visitor is a guest, so the event names no user.
- A failed or dropped bus event never fails a tool call nor undoes its change, as cron's and candidates' events: the change is the record, the event a notice of it.
- The order of `Emits()` is the order the life is told (added, rejected, delivered), with opened appended last so the three earlier entries keep their places; it is visible only at `/declarations`, where appkit sorts by name anyway.
- **`campaign.member.opened`**, a fourth bus event, singular like the other three, with `campaign`, `candidate` and `at`, every key present and every value a string (hand-picked outcome 13, delivery log P7). Once per member per campaign, guarded by `D04-store`'s durable marker; later visits emit nothing, and `campaign.visited` stays trail-only and unchanged.
- **`at` is the first visit's time, RFC 3339 in UTC to the second**, because the sweep tells the event long after the visit and the envelope's `Time` is then the sweep's (hand-picked outcome 13, delivery log P7). The store's own time text is not reused: the attribute is a contract with candidates, which parses it as RFC 3339.
- **`campaign.member.opened` names no user**, keeping the request id, as `campaign.visited` does: the open is a guest's act, and a signed-in owner's open reads as any visitor's (delivery log P7).
- **Additive across the release boundary**: the previous release of candidates accepts only the events it names, so it ignores `campaign.member.opened`, and the previous release of campaigns never emits it (hand-picked outcome 13). Known limit: candidates' previous release does not accept `campaign.member.opened`, so one the live path sends while that release runs is not delivered to it and is not sent again once it upgrades, because the member's marker is already set; this is a case of `D04-store`'s limit that a bus event dropped after its marker is set is never re-sent, and the deploy-day window it leaves is the one "Accepted known limit: a live first visit in the deploy-day window is passed over" accepts.
- **The sweep waits an hour, and runs hourly after** (delivery log P8, delivery log S1-2). The events app moves a subscriber's cursor past the events it does not accept, and re-asks every service's declarations only on a timer of about a minute, so a sweep at campaigns' start on deploy day would be passed over for candidates whatever the restart order. So `cli.Run` (`D03-serve`) runs no sweep at start: it begins `links.StartSweep` (`D06-links`) each time `cli.Process.SweepAfter` (`D01-layout-and-run-seam`) delivers, first an hour after start and hourly after, so a restart within the hour postpones it; once caught up a sweep tells no one. This replaces delivery log P8's sweep at every start; the sweep itself is unchanged.
- **Accepted known limit: a live first visit in the deploy-day window is passed over** (delivery log S1-2). A first visit in the minute or so between campaigns' restart and the events app re-asking candidates' declarations is emitted and marked on the live path, so candidates passes over it and no sweep tells it again. It is a deploy-day window only; every first visit after it, and every untold one before the release, reaches candidates.

## Consumer tasks

The tools (`D08-tools`) call `trail.MemberAdded(ctx, cfg.Telemetry, cfg.Events, campaign, candidate, prospectList)` for each member `add_prospect_list`, `add_member` or `add_members` added (`prospectList` empty for `add_member` and `add_members`), `trail.MemberRejected(ctx, cfg.Telemetry, cfg.Events, campaign, candidate, why)` for a `reject` that rejected, and `trail.PieceDelivered(ctx, cfg.Telemetry, cfg.Events, campaign, candidate, piece, channel, how)` for each piece `deliver` or `deliver_channel` delivered, each with the tool call's context and only once the store has reported the change made; a call the store reports changed nothing (log D22, doc 23), a refused call and a read call none of them. The links handler (`D06-links`) calls `trail.Visited(r.Context(), cfg.Telemetry, v.Campaign, v.Piece)` once `Store.Visit` has recorded a visit, and never for an unknown token; then, when the visit answered `Opened`, `trail.MemberOpened(r.Context(), cfg.Telemetry, cfg.Events, v.Campaign, v.Candidate, v.First)`, and for a visit that did not, nothing on the bus. The sweep (`links.StartSweep`, `D06-links`), run on the schedule "The sweep waits an hour" records, calls `trail.MemberOpened` for each member `Store.MarkOpened` answers, with a context carrying no request id, so its events carry an empty request id and no cause. candidates, the one subscriber, accepts `campaign.member.opened` and records `at` as the member's first visit on that campaign; its previous release accepts only the events it names, so it ignores this one, which is safe across the release boundary: a mix of old and new during a rolling restart or after a rollback refuses nothing and breaks no delivery. `D03-serve` builds the emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`, mounts `events.DeliveryHandler(nil)` at exactly `/events` and `events.DeclarationsHandler(em, nil)` at exactly `/declarations`, both outside the identity gate, and puts `events.Middleware` on `/mcp` so a call's cause reaches the context. A test builds a writer with `telemetry.New` over a `*telemetry.Capture` and an emitter with `events.New` over an `*events.Capture` with `trail.Emits()`, calls a recording function under `identity.NewContext` (and `events.NewContext` for a cause), flushes both, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`; for `MemberOpened` it hands a time in a non-UTC zone with a fraction of a second and a context whose caller carries a user, and expects the UTC whole-second text and an empty user; it serves `events.DeclarationsHandler(em, nil)` with `httptest` to read the declarations.
