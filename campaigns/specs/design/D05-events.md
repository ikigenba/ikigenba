# D05-events

Decisions cited as doc N are /home/mgreenly/Documents/ikigenba-campaigns.md; those cited as log DN are /home/mgreenly/Documents/ikigenba-campaigns-decisions.md.

The campaign events: the three kinds of event campaigns emits on the suite's event bus when a member is added, a member is rejected, or a piece is delivered (doc 16, log D15), the record of each in campaigns' own trail, the trail-only record of a visit, their declarations, and the two bus paths the events app reaches campaigns on. This document declares `internal/trail`. `D04-store` decides what a change is and reports whether one happened; `D08-tools` decides which tool calls change something and calls the recording functions declared here; `D06-links` calls `Visited` for each visit; `D03-serve` builds the run's writer and emitter, the latter with the declarations declared here, mounts `/events` and `/declarations`, puts a request's identity and event cause on its context, and owns the `lost event` line a dropped bus event leaves on stderr; `D09-trail` owns the closed set of telemetry event names, which includes the four names declared here, the trail's secrecy, and the `event.lost` a dropped bus event leaves in the trail (R-XYH1-M8MI).

## The three bus events

A member's and a piece's life in a campaign is told on the bus by three events, each with fixed attribute keys, every key always present and every value a string:

- `campaign.member.added`: `campaign` (the campaign's id), `candidate` (the candidate id as given, log D1), `cohort` (the cohort's id the member came from, empty when added one at a time).
- `campaign.member.rejected`: `campaign`, `candidate`, `reason` (the owner's sentence saying why).
- `campaign.piece.delivered`: `campaign`, `candidate`, `piece` (the piece's id), `channel` (`mail` or `email`), `how` (`hand` in this version, doc 8; `system` once the system sends).

The names are literal, not patterns: the middle word is the thing the event is about, not a slug, so `candidates` subscribes to each by its exact name (log D15). The time of each is the bus event's own `Time`, so no attribute repeats it (log D3 named a time; the envelope carries it). Ids, words and the owner's reason only; never a business name, address, phone, email, token or link.

## Two ways at once

Every bus event goes two ways at once, as cron's trigger events and candidates' pass events do: it is recorded in campaigns' trail through the run's writer, and emitted on the bus through the run's emitter, under the same name, with the same attributes, the same request id and the same user. appkit's emitter records only `event.lost` in the trail, so the trail record is made here by its own call of the writer's `Emit`, and each event is recorded once.

`trail.MemberAdded`, `trail.MemberRejected` and `trail.PieceDelivered` are the only way campaigns makes one of these events, and each makes both halves in one call under the context it is given. Each is told as the tool's caller: the request id and user are those of the `identity.Caller` on the context, and the bus event's cause is the event cause `events.Middleware` read from the call's headers, one level deeper, or none. Each call queues and returns: no answer waits for telemetry or the bus, and either half is made whatever becomes of the other. A bus event the emitter fails to deliver, refuses as malformed, or drops at a full queue or at the stop does not fail the call and does not undo the trail record or the change; the emitter retries and drops as appkit's defaults say, and what a drop leaves is owned elsewhere: the `event.lost` it leaves in the trail is `D09-trail`'s (R-XYH1-M8MI), and the `lost event` line on stderr is `D03-serve`'s. The functions return nothing.

## The visit

`trail.Visited` records `campaign.visited` in the trail, with `campaign` and `piece` and nothing else, under the request's request id and with no user, so a signed-in owner's `campaign.visited` reads as any visitor's does (`D06-links`); the request pair `telemetry.Middleware` records for the same request still carries `X-User-Id`, and that pair is `D03-serve`'s and `D09-trail`'s; it takes no emitter and emits nothing on the bus. It records through a context of its own: appkit's `identity.NewContext(ctx, identity.Caller{RequestID: c.RequestID})`, `c` being the caller `identity.FromContext(ctx)` answers, so the writer's `Emit` finds the request id and an empty `UserID`. The visitor's user agent, referrer and address are kept in the store (`D04-store`, doc 13); keeping them out of telemetry is this design's own choice.

## The declarations

`trail.Emits()` is what the run's emitter is built with: the three names, literal, each with its attribute keys in the order listed above, so appkit refuses a campaign event whose keys are not exactly these. `campaign.visited` is not declared: it never goes on the bus.

campaigns accepts no bus event. The events app reaches it at its socket on `/events`, where it would deliver accepted events, answered by appkit's `events.DeliveryHandler` with no handlers, and `/declarations`, answered by `events.DeclarationsHandler` over the run's emitter with no handlers. appkit answers the declarations with the emissions sorted by event name, each one's attributes in the order declared, and `accepts` empty; the three names already sort in the declared order. The body is stated below because its content is this document's declarations; the routes, their place outside the identity gate, and nginx's 404 for both at the public name are `D03-serve`'s and `D10-on-a-space`'s. That campaigns accepts nothing is contract here: the run's handler answers at `/events` exactly as `events.DeliveryHandler(nil)` does, so a well-formed delivery of any event finds no handler and is answered 404 with an empty body.

## Recorded decisions

- The bus event names and keys are log D15's, finalized here: `cohort` on added, `reason` on rejected, `piece`, `channel` and `how` on delivered, each after `campaign` and `candidate`; every key always present, as appkit's exact-keys rule requires, so `cohort` is the empty string for a member added one at a time (log D15).
- No time attribute: log D3 listed a time in the payload, and the bus event's envelope `Time` is that time; repeating it would invite two clocks.
- `reason` carries the owner's rejection sentence as given (log D15). It is the owner's words about the campaign, not a business's contact data, which no event carries.
- The recording functions take plain strings, not store records, so the trail's contract does not move when a store record gains a field, and a caller names exactly what it tells.
- **Told as the caller**, unlike candidates' pass events, which are told as the pass's starter: every campaign event is made inside the tool call that made the change, so the call's own identity and cause are the right ones (as cron's lifecycle events).
- `campaign.visited` is trail-only, this design's own choice: a visit is the owner's engagement data, read through `engagement`; nothing on the suite subscribes to it, and the bus would carry a visitor-driven rate of events. It carries ids only; the visitor's user agent, referrer and address stay in the store.
- **`campaign.visited` names no user**, keeping the request id, to match `D06-links`, which ignores identity on `/t/`: a signed-in owner's `campaign.visited` is recorded as any visitor's is. This covers `campaign.visited` alone: the request pair still names the user, and it is `D03-serve`'s and `D09-trail`'s. Done with appkit's existing `identity.NewContext` and `identity.Caller`, no library change. A decision of this design, settled by the root for this delivery: the visitor is a guest, so the event names no user.
- A failed or dropped bus event never fails a tool call nor undoes its change, as cron's and candidates' events: the change is the record, the event a notice of it.
- The order of `Emits()` is the order the life is told (added, rejected, delivered); it is visible only at `/declarations`, where appkit sorts by name anyway.

## Consumer tasks

The tools (`D08-tools`) call `trail.MemberAdded(ctx, cfg.Telemetry, cfg.Events, campaign, candidate, cohort)` for each member `add_cohort` or `add_member` added (cohort empty for `add_member`), `trail.MemberRejected(ctx, cfg.Telemetry, cfg.Events, campaign, candidate, why)` for a `reject` that rejected, and `trail.PieceDelivered(ctx, cfg.Telemetry, cfg.Events, campaign, candidate, piece, channel, how)` for each piece `deliver` or `deliver_channel` delivered, each with the tool call's context and only once the store has reported the change made; a call the store reports changed nothing (log D22, doc 23), a refused call and a read call none of them. The links handler (`D06-links`) calls `trail.Visited(r.Context(), cfg.Telemetry, v.Campaign, v.Piece)` once `Store.Visit` has recorded a visit, and never for an unknown token. `D03-serve` builds the emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`, mounts `events.DeliveryHandler(nil)` at exactly `/events` and `events.DeclarationsHandler(em, nil)` at exactly `/declarations`, both outside the identity gate, and puts `events.Middleware` on `/mcp` so a call's cause reaches the context. A test builds a writer with `telemetry.New` over a `*telemetry.Capture` and an emitter with `events.New` over an `*events.Capture` with `trail.Emits()`, calls a recording function under `identity.NewContext` (and `events.NewContext` for a cause), flushes both, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`; it serves `events.DeclarationsHandler(em, nil)` with `httptest` to read the declarations.
