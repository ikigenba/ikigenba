# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the services file and the sibling clients built from it, the terms campaigns serves on, the listener's life, and the route table its one handler keeps with the identity each route takes. It is candidates' serve path less the engine, the prune sweep, the ZIP table, the facts fill, the repair and the website checker, with one piece of background work on an hourly timer, the **hourly sweep**, which sends the `campaign.member.opened` events the bus has not yet had (`D06-links`), first an hour after the start and hourly after, and with the identity gate as webhooks' (appkit's `identity.Optional` everywhere but `/mcp`, which keeps `identity.Require`) and a guest route, `/t/`, outside identity altogether (`D06-links`). This document declares `internal/server` and `internal/web`. Decisions cited as hand-picked outcome N are /home/mgreenly/Documents/ikigenba-campaigns-hand-picked.md; those cited as delivery log PN or delivery log S1-N are /home/mgreenly/Documents/ikigenba-campaigns-hand-picked-decisions.md.

`D01-layout-and-run-seam` declares the run seam (`cli.Process`, with its sweep timer `SweepAfter`, and `cli.Run`), the settings (`settings.Settings` and `Drain()`), the database path, the addresses (`urls.Auth`, `urls.SignIn`, `urls.Sibling`) and the hard rule; `D02-cli` the exit codes (`ExitSuccess`, `ExitUsage`, `ExitServerFailed`); `D04-store` the store (`store.New`, `store.Config`); `D05-events` the bus events, `trail.Emits()` and what `/events` and `/declarations` answer; `D06-links` the guest route (`links.Handler`, `links.Config`) and the sweep (`links.StartSweep`, `links.SweepBatchSize`) with its completion and failure lines; `D07-pages` the pages (`pages.Handler`, `pages.Config`), the sign-in redirect a guest gets and the tools page; `D08-tools` the tools (`tools.Register`, `tools.Config`) and their refusals; `D09-trail` the trail as a whole and its secrecy; `D10-on-a-space` the nginx fragment and the trust. appkit's `db`, `telemetry`, `events`, `identity`, `page`, `mcp`, `services`, `candidates` and `artifacts` packages own their contracts; this document wires them and restates none of them.

## The services file

`IKIGENBA_SERVICES` names the services file. campaigns uses five of its entries: `candidates`, whose socket the tools and the campaign page reach through appkit's `candidates` client (log D13, log D18); `artifacts`, whose socket `add_material` reaches through appkit's `artifacts` client, appkit/artifacts Head and Show (D22, v0.29.0; log D23); `auth`, read afresh per request by the pages through `urls.Auth` and `urls.SignIn` for the banner's links and a guest's sign-in address, as siblings read it; and `events` and `telemetry`, appkit's sinks', which read the file afresh on each delivery. The pages also read the entries `candidates` and `artifacts` afresh per request, through `urls.Sibling`, for the links to those services' pages (`D01-layout-and-run-seam`).

`Run` reads the file once, when it starts to serve, and builds the `candidates` client with `candidates.NewClient(candidates.ClientConfig{Service: e, Telemetry: w})` from the entry `candidates` it finds then, and the `artifacts` client with `artifacts.NewClient(artifacts.ClientConfig{Service: e, Telemetry: w})` from the entry `artifacts`, or none (a nil client) for an entry the file does not hold. Building either does no I/O and cannot fail, so an entry whose socket nothing serves on refuses nothing at the start; the first call that needs it finds out. With no client, or with one whose sibling does not answer, the tools that read the sibling are refused `unavailable` and the campaign page shows a member's name empty (`D07-pages`, `D08-tools`, log D19); everything else serves as with it. The absence of `candidates` or `artifacts` never stops campaigns serving (log D19). With `IKIGENBA_SERVICES` unset, naming no file, or naming one `services.Read` refuses, the start is not refused and campaigns serves as with a file holding no entry. A changed `candidates` or `artifacts` entry reaches the tools at the next start; a changed `auth` entry reaches the next page request.

Every request either client sends carries the caller of the tool call or page request it is sent for, forwarded by appkit's client from the context (log D18), so candidates and artifacts see the signed-in user, and each is recorded by the client as `sibling.called` (`D09-trail`).

## The terms campaigns serves on

campaigns serves only on a listening socket it inherits, taken as `sd_listen_fds(3)` documents, and reports readiness with `READY=1` to `NOTIFY_SOCKET` as `sd_notify(3)` documents. It trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway to have forwarded them (`D10-on-a-space`). Every request has an id: the one nginx or the caller set, or 32 lowercase hexadecimal digits appkit's telemetry middleware draws from `Process.Rand`.

The manifest declares `guests = true` (log D10), so nginx admits a request with no identity on every path but `/mcp` and `/api` and the paths under it (`D02-cli`, `D10-on-a-space`). A request with no `X-User-Id`, or an empty one, is a **guest**, whatever `X-User-Email` it carries.

The events app reaches campaigns at its socket on `/events` and `/declarations`. campaigns emits four bus events and accepts none (`D05-events`), so it mounts appkit's `events.DeliveryHandler` with no handlers and `events.DeclarationsHandler` over the run's emitter, built with `trail.Emits()`, with no handlers, as cron does. These two paths sit outside the identity gate; the fragment answers both 404 at the public name (`D10-on-a-space`).

## The route table

Every request goes through appkit's `telemetry.Middleware` over `Config.Telemetry`, which records the request pair (`D09-trail`) and puts the request's caller on its context. Then, by `URL.Path` alone, compared by hand, so nothing is cleaned and nothing redirected:

- exactly `/events` and exactly `/declarations`: the event bus's two handlers, every method, with or without identity.
- exactly `/mcp`: appkit's `events.Middleware`, then `identity.Require`, then the MCP server `Config.MCP`, on which the tools of `D08-tools` are registered with `tools.Register` once, when the handler is built. A guest is answered `identity.Require`'s 500 with `identity.MissingBody`, which on a host never happens because nginx demands a credential at `/mcp` first.
- a path beginning `/t/`: the links handler, `links.Handler` over `links.Config` with the store, the writer, the emitter and the default destination (`D06-links`), with no identity middleware: identity is ignored there.
- a path beginning `/_appkit/`: `identity.Optional`, then `page.Static()`; nothing there is private, and a guest's sign-in page may ask for it.
- every other path: `identity.Optional`, then the page handler, `pages.Handler` over `pages.Config` (`D07-pages`), which sends a guest a 302 to the sign-in address, as sites' pages do, and draws the page for a signed-in user. So `/`, `/about`, `/tools`, `/campaigns/<id>`, and `/nope`, `/t`, `/mcp/`, `/events/`, `/declarations/` and `/_appkit` all reach it.

This document states the routing only: which handler answers which path, under which identity. What a page, the guest route, a tool or a bus path answers is the owning document's. No answer on any route carries `Set-Cookie`.

The handler is built from a `web.Config` carrying what its routes need: the banner source, the MCP server, the services file's path, the store, the writer, the emitter, the two sibling clients (each nil when the services file named none at the start) and the settings, whose `DefaultDestination` the guest route sends an unknown token to and whose `LinkPrefix` the tools build links with (`D01-layout-and-run-seam`). `web.Handler` builds the links handler, the page handler and the tool registration from it; which fields each of `links.Config`, `pages.Config` and `tools.Config` takes is that document's.

## The start

With `Args` empty, `Run` checks the settings (`D01-layout-and-run-seam`), then whether exactly one socket was passed in, with the diagnostics below. It removes the three `LISTEN_*` variables, takes descriptor 3, and opens the database with `db.Open` at `state/campaigns.db` with `campaigns.Migrations()` and `Process.Now`; a failure is `campaigns: cannot open database state/campaigns.db: ` and the reason, exit 1. It builds the store with `store.New` and `store.Config` over `Process.Now` and `Process.Rand` (`D04-store`), the run's writer, the run's emitter with `trail.Emits()`, and the two sibling clients from the services file; records `service.started`, so that it is the first event of every run; builds the handler, calling `Process.MCP` once with the writer; sends `READY=1`; and serves. No sweep runs at the start (delivery log S1-2).

## The hourly sweep

While it serves, `Run` waits on a channel `Process.SweepAfter(time.Hour)` returned, `time.After` standing in when the field is nil (`D01-layout-and-run-seam`). Each time such a channel delivers while `ctx` is not done, `Run` runs one sweep, `links.StartSweep` over a `links.Config` with the store, the writer, the emitter and the default destination, writing to `Process.Stderr`, waits for the sweep's channel to close, and only then calls `SweepAfter(time.Hour)` again. So the sweeps follow the start by whole hours, never overlap, and a restart within the hour postpones the next one. `SweepAfter` is called for nothing else and with no other duration, never once `ctx` is done, and never by a command or a refused start.

The sweep is the one piece of background work campaigns does (`D06-links`): it walks the members a page of `links.SweepBatchSize` at a time, marks each member of a live campaign that has a visit and no marker, and sends one `campaign.member.opened` for each with its earliest visit's time, so a member visited before the event existed, or while the previous release ran after a rollback, gets its event once. A sweep that tells at least one member writes its completion line to `Stderr`; one that tells none writes nothing, so a service that is caught up leaves no line each hour; one the database fails under writes its failure line and ends, and the service goes on serving, the next hour's sweep finishing the work. It is idempotent through the marker it shares with the guest route: no member's event is sent by both a sweep and a visit. Nothing else is settled, swept or loaded, at the start or on a timer.

## Stopping

When `ctx` is done (in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the cause) `Run` drains the server for `DRAIN_SECONDS` (`settings.Settings.Drain()`), calls `SweepAfter` no more and waits on no channel it returned, waits for a sweep running when `ctx` became done, cut off by `ctx`, to close its channel, a sweep cut off writing no line and beginning no further page, waits within the same window for the emitter to deliver what it holds, shuts the writer down with the cause's text as `service.stopping`'s reason, shuts the emitter down, and closes the database. From the drain deadline on, `Run` hands neither sink anything: an event recorded after it reaches standard error as appkit's `undelivered event` and `lost event` lines. A drain that runs out on requests is `campaigns: stopped with <n> request(s) unfinished`, exit 1.

## Recorded decisions

- **`internal/server` is candidates' and webhooks', unchanged**: one function and one error type, declared here because `D01-layout-and-run-seam` assigns the listener's life to this document.
- **The identity gate is webhooks' shape** (log D10, log D22): `identity.Require` at `/mcp` alone, `identity.Optional` before the pages and the shared files, and nothing at `/t/`. Departure from candidates, whose every route but the bus's sits behind `identity.Require`: campaigns' manifest admits guests for the guest route, so a guest also reaches the pages, and the page handler, not nginx, sends it to sign in, as sites' pages do. The 302 is `D07-pages`'; this document only routes the guest there.
- **`/t/` takes no identity middleware.** Departure: webhooks' guest ingress, `/in/`, sits behind `identity.Optional`; campaigns' guest route sits behind none. `identity.Optional` would change nothing the links handler reads, since it ignores identity (`D06-links`); leaving it out keeps the guest route's answer independent of every identity header by construction. The request id still reaches the handler, on the caller appkit's telemetry middleware puts on the context, which `trail.Visited` reads (`D05-events`).
- **`/_appkit/` goes through `identity.Optional`**, as webhooks' and sites' do: the shared files are not private and a guest's page may load them. The brief names `page.Static()` there and nothing else; the wrapper changes no answer.
- **The sibling clients are built once, at the start**, from the entries the services file names then, as candidates builds its `scrapes` and `prompts` clients; the pages, which only build addresses, read the file afresh per request (`D01-layout-and-run-seam`).
- **`web.Config` carries the clients, not the services entries**, so the tools and the pages share one client per sibling, each built with the run's writer so its `sibling.called` events reach the trail.
- **`web.Config` carries the settings whole** rather than the two addresses: `web.Handler` passes `Settings.DefaultDestination` to `links.Config`'s `DefaultDestination` (`D06-links`), and the tools read `Settings.LinkPrefix` (`D08-tools`); `DrainSeconds` is carried and unused by the handler.
- **`web.Config` carries no clock and no random source**, as candidates' carries none: every time campaigns stamps (a campaign's created, a member's added and rejected, a piece's delivered and dropped, a material's added, a visit's at) is the store's `store.Config.Now` (`D04-store`, `D06-links`), and every id and token the store's `store.Config.Rand`; the writer and the emitter hold their own. A handler that needs one later adds it here with a new id.
- **`/events` is `D05-events`'** (R-3J3X-X9WS states it at `web.Handler`); this document states `/declarations` at the handler, since `D05-events` states only what `events.DeclarationsHandler` answers.
- **The start's answer to a failing database after `db.Open` is not required.** The start reads nothing from the store before ready, so there is no settling to fail; a store failure is provoked only on a handle a test hands in (candidates' AGENTS.md pattern), which `cli.Run` never takes. For the same reason a sweep's failure line under `Run` is described, not required: it is required of `links.StartSweep` over a store a test hands in (`D06-links`).
- **The opened events the bus missed are sent by an hourly sweep, not at the start** (hand-picked outcome 15, delivery log P8, delivery log S1-2): `campaign.member.opened` is new, so every member visited before it exists, and every member the previous release records a visit of after a rollback, would otherwise never get one. Delivery log P8 ran the sweep at every start; delivery log S1-2 moved it to a timer, because the events app moves a subscriber's cursor past the events it does not accept and re-asks each service's declarations only on a timer of about a minute, so a sweep at campaigns' start on deploy day would be passed over for candidates whatever the restart order (`D05-events` records the window and its known limit). So `Run` runs a sweep each time a channel `Process.SweepAfter(time.Hour)` returned delivers, the first an hour after the start, and calls `SweepAfter` again only once that sweep's channel has closed, so the store sees one walk at a time; the timer is the run seam's, so a test fires it and none waits an hour. Every sweep follows the migrations, which add the marker it reads, and `service.started`, and none holds back `READY=1`. A sweep that finds every visited member marked walks the members and sends nothing, and that hourly walk is the price of closing the rollback gap without the owner; it writes no line either, or an idle service would log one every hour. The marker is the store's, one write with the visit (`D04-store`), so a sweep and the guest route never send one member's event twice. `Run` waits for a running sweep's channel before it records `service.stopping` and flushes the emitter, so every opened event a sweep sent precedes `service.stopping` and is handed to the emitter before the stop's flush. Rejected: a migration, which cannot reach the bus; a CLI subcommand, which contradicts `D02-cli`'s rule that a command emits nothing and has no precedent in the suite; and a sweep at every start, for the passed-over window above (delivery log S1-2).
- **The timer's drive is required at `Run`, and so is that no sweep runs before it fires** (delivery log S1-2): a test that never fires the channel sees no sweep (R-QE9G-E0TY), one that fires it sees the sweep end before `SweepAfter` is called again (R-QD1K-0939), and the calls are bounded by occasion, duration and `ctx` (R-QFHC-RSKN, R-QGP9-5KBC). That a sweep begins after `service.started` follows from that event being the first of every run (R-QFOM-59QR). That `READY=1` is not held by a sweep needs no requirement of its own, since no sweep runs before the first delivery. That the stop waits for a running sweep's channel to close before it flushes the emitter and records `service.stopping` is described, not required, as the start's ordering is: no permitted test can tell it apart, since a sweep cut off while its page's flush is held has emitted its whole page and emits nothing more. What a test can see is required: such a sweep writes no line, begins no further page, and loses none of its opened events, each reaching the bus and recorded in the trail before `service.stopping` (R-ZKGA-8BYD).

## Consumer tasks

`Run`, serving, calls `s, err := settings.Read(p.LookupEnv)`, checks the socket, unsets the three `LISTEN_*` variables and takes `ln, _ := p.Inherit(3)`; opens `d, err := db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "campaigns.db"), Migrations: campaigns.Migrations(), Now: p.Now, Service: pages.ServiceName, Stderr: stderr})`; builds `st := store.New(d, store.Config{Now: p.Now, Rand: rnd})`, `w := telemetry.New(...)`, `em := events.New(events.Config{..., Telemetry: w, Emits: trail.Emits()})`; reads `list, err := services.Read(path)` and builds `cc := candidates.NewClient(candidates.ClientConfig{Service: e, Telemetry: w})` when `e, ok := list.Find("candidates")` finds an entry (nil otherwise) and `ac := artifacts.NewClient(artifacts.ClientConfig{Service: e, Telemetry: w})` likewise for `artifacts`; calls `w.Ready()`; builds `h := web.Handler(web.Config{Banner: p.Banner, MCP: p.MCP(w), ServicesPath: path, Store: st, Telemetry: w, Events: em, Candidates: cc, Artifacts: ac, Settings: s})`; sends `READY=1`; runs, beside `server.Serve`, a loop that takes `after := p.SweepAfter` (`time.After` when nil) and, until `ctx` is done, selects on `ctx.Done()` and `after(time.Hour)`, the latter running `<-links.StartSweep(ctx, links.Config{Store: st, Telemetry: w, Events: em, DefaultDestination: s.DefaultDestination}, p.Stderr)` before the next `after`; and calls `server.Serve(ctx, ln, h, s.Drain(), stop)`, `stop` waiting for that loop to end, then flushing `em`, then `w.Shutdown(c, context.Cause(ctx).Error())`, then `em.Shutdown(c)`; answers a `*server.DrainError` with `campaigns: ` and its text, `ExitServerFailed`; closes `d`.

`web.Handler(cfg)` calls `tools.Register(cfg.MCP, tools.Config{...})` once, builds `links.Handler(links.Config{Store: cfg.Store, Telemetry: cfg.Telemetry, Events: cfg.Events, DefaultDestination: cfg.Settings.DefaultDestination})` and `pages.Handler(pages.Config{...})` from `cfg` as `D07-pages` and `D08-tools` declare their configs, and returns `telemetry.Middleware(cfg.Telemetry, mux)`.

A test of the handler builds `web.Handler` over a store on its own database, a writer and an emitter over captures, a server from `mcp.NewServer`, `settings.Defaults()` (or settings of its own) and appkit clients built on fakes' sockets (or nil), serves it with `httptest`, and sends raw requests with the identity headers set or left out. A test of the start drives `cli.Run` with a listener, a `NOTIFY_SOCKET` it binds, a `Now`, a `Sleep` and a `Rand` it controls, a services file whose `candidates` and `artifacts` entries name fakes' sockets (or that leaves them out), and captures; waits for `READY=1`; drives `/mcp` with `mcp.Client`, the pages and `/t/<token>` with raw HTTP; rewrites the services file; cancels; and inspects the fakes' records, the captures, the streams and the exit code. A test of the hourly sweep first seeds `state/campaigns.db` under `Dir` through its own store, over a handle `db.Open` returned for that path with the root package's `Migrations()`: campaigns, members with a piece each, and visits through `Visit` at times its clock sets; then clears every member's marker through `DB.Write` with `UPDATE members SET opened_emitted = ''`, as the previous release would leave it, and closes the handle; drives `cli.Run` over that `Dir` with a `SweepAfter` that records each duration it is called with, signals the test at each call and returns a channel the test fires, and an `EventSink` that records each delivery, or holds one until the test releases it or its context is done; waits for `READY=1` and the first `SweepAfter` call; fires that call's channel; waits for the next call, by which the sweep has closed its channel, reading `Stderr` under a lock; fires again or cancels; and inspects what the `EventSink` was handed. No test sleeps or waits an hour.
