## The commands

The arguments decide everything. An empty `Args` means serve, and everything from there is `D03-serve`'s. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity; `manifest` writes `Manifest`; and `--help` writes `Usage`. The one two-word command, `db status`, reports the database's migrations (below). Any other `Args` is a usage error. The argument campaigns complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone; the word after `db` when that is not `status`; the word after `db status`; and otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `campaigns: `, and after exactly one empty line comes the hint to run `campaigns --help`. The usage text is never written to `Stderr`.

Arguments are checked before anything else. A command needs no socket and no setting, and only `db status` reads the database, so `campaigns --version` succeeds with nothing passed in and `campaigns bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, the pause, the sweep timer, the random source, the two sinks, the banner source or the server maker, and only `db status` reads anything under the working directory. A command other than `db status` creates, removes or changes nothing there; `db status` creates nothing in a directory that holds no database and leaves what `db.Status` reports unchanged, though appkit's read-only open of a database `db.Open` made in WAL mode may leave its `-shm` and `-wal` files beside it, so it is not held to leaving a database's directory byte for byte as it was, as cron's is not. A command records no visit, emits nothing to the bus, runs no sweep and records no event: the trail is what campaigns records while it serves, and the hourly sweep is `D03-serve`'s, begun only while serving, so a command never asks `SweepAfter` for a timer (delivery log S1-2). Every diagnostic is one write to `Stderr`.

## db status

`db status` is an operator's look at the database: which of the migrations the binary carries `state/campaigns.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints is appkit's `db.Status`, called with the path `state/campaigns.db` resolved against `Process.Dir` and the migrations `campaigns.Migrations()` returns, writing straight to `Stdout`; campaigns adds nothing to the lines and states nothing about their format. `db.Status` only looks: it applies nothing and creates nothing, so before campaigns' first start every migration is reported pending and the directory is left as it was. When it returns an error, campaigns says so on one line, `campaigns: ` and the error's text with each newline replaced by a space, and exits 1; whatever `db.Status` had already written to `Stdout` stays there, since findings are product.

## Exit codes

`ExitSuccess` (0), `ExitServerFailed` (1) and `ExitUsage` (2), as every app. A usage error, a setting refused (`D01-layout-and-run-seam`) or a socket missing or doubled (`D03-serve`) is 2; a database that will not open or a drain that ran out on requests (`D03-serve`), or a `db status` that fails, is 1. `Run` returns no other value.

## The usage text

`Usage` is what `--help` prints: the command's synopsis, what campaigns is, the commands and options above, and what each exit code means. No program parses it, so it is a copy constant: its words live in the source and no requirement or test spells them; a test compares `Stdout` with the constant itself.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox, devctl and home read it, so its text is contract and is stated byte for byte, all but the description's words, whose TOML value is `pages.Description`, and `etc/manifest.toml` holds the same bytes. It names the app `campaigns`; its description is `pages.Description`, the line the about screen shows and the host publishes in its services file for the MCP gateway's instructions, so its words are copy and live in that one constant; it is not the default app; it is an MCP service (`mcp = true`), so the gateway offers its tools; it serves guests (`guests = true`, log D10), so the host's nginx lets a request without a credential reach the guest route `/t/<token>` (`D06-links`) and the pages, which send a guest to sign in themselves (`D07-pages`), while `/mcp` still needs a credential; no secrets, since campaigns holds none and calls nothing outside the suite (doc 19, doc 20); an `[env]` table holding `CAMPAIGNS_DEFAULT_DESTINATION` and `CAMPAIGNS_LINK_PREFIX` with their defaults as strings, in the order `settings.Read` reads them, so the values the host writes into campaigns' environment are the ones campaigns applies when a setting is unset (log D11, log D22); the `[database]` table that has the host keep and replicate `state/campaigns.db`; a `[resources]` table whose only line is `memory_max = "128M"`; and, last, a `[home]` table whose only line is `group = "application"`. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app. The manifest declares no port, since campaigns serves on the socket the host passes it.

`etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ. It is proved by use: the root package embeds `etc/` as `Etc` (`D01-layout-and-run-seam`), so a test in the external test package `campaigns_test` compares the embedded `manifest.toml` with the constant.

## Recorded decisions

- **The manifest's description slot is stated by shape, not by its words, as cron's is.** candidates spells its description in `Manifest` because its `pages.Description` is declared with a value; campaigns' `pages.Description` is a copy constant of `D07-pages`, declared without one, so `Manifest` is stated byte for byte around a one-line TOML basic string, and a second requirement makes that line `pages.Description` exactly, its TOML value equal to the constant and holding a character other than a space. That is why `pages.Description` must be a constant on one line with no `"`, `\` or control character: written between the quotes unescaped, its TOML value is then itself. A copy change to the description then touches the constant and `etc/manifest.toml` and no requirement.
- **Departure: `Usage` is a copy constant.** candidates and cron spell their usage text in a requirement. The spec's rule on copy lists a command's stdout as contract because, and only where, a program parses it: `--version` is read by the host and `manifest` by devctl, opsctl, the sandbox and home, but no program parses `--help`; a person reads it, and a caller learns the commands and exit codes from this design, not by parsing help. So it is copy under the rule's own test, declared by name, and a test compares `Stdout` with the constant. The usage-error diagnostic stays spelled (R-98L9-T8UI) because it is not help: it is an error line a caller matches, which the same rule names as contract, its `campaigns: ` prefix, empty line and unprefixed hint are the repository's command-line conventions, and it is what a script sees on stderr when it calls the binary wrongly; candidates and cron spell it alike.
- The `[env]` values are compared with `settings.Defaults()` (`D01-layout-and-run-seam`), so a default cannot drift between the manifest and the code.
- `guests = true` is log D10's. `secrets = []` follows from doc 19 and doc 20: campaigns sends nothing and holds no credential. `memory_max = "128M"` is this design's decision: cron's figure, not candidates' 256M, since campaigns reads a window at a time, and its one background work, the hourly sweep `D03-serve` begins while serving (`D06-links`; delivery log P8, delivery log S1-2), reads `links.SweepBatchSize` members a page. `group = "application"` is this design's decision: campaigns is the funnel's, as candidates is, not the suite's.
- **`db status` is exempt from "creates nothing" only as cron's is:** a directory that holds no database stays empty, and what `db.Status` reports is the same after as before, because appkit's read-only open of a WAL database may leave `-shm` and `-wal` files (observed).
- **The exit codes are three declarations and one behaviour,** split as cron splits them, so a renamed or revalued constant re-mints one id.
- **`db status` is stated here, as cron's `D02` states it,** rather than in the store's document as candidates does: it is a command, its output is appkit's and its path and migrations are `D01-layout-and-run-seam`'s, so `D04-store` need say nothing of it.
- No release is named in the manifest or in any requirement.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `campaigns --version`, `campaigns manifest` or `campaigns --help` and reads stdout; an operator types `campaigns db status` in the working directory before or after a deploy; `devctl build` runs `campaigns manifest` and compares its output with the release's `etc/manifest.toml`; opsctl reads the manifest's `[env]` and writes the two defaults into campaigns' environment.

A test builds a `cli.Process` with only `Args`, `Stdout` and `Stderr` (two `bytes.Buffer`s), `Dir` (an empty temporary directory) and, for `--version`, `Version` set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `p.Version + "\n"`, `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `SweepAfter`, `Banner` and `MCP` to functions that record a call, `Rand` to a reader that records a read and `Sink` and `EventSink` to sinks that record any use, and asserts none was used. A test of `db status` makes a database under its `Dir` with `db.Open` and `campaigns.Migrations()` (or puts a file there that is not a database), closes it, runs `cli.Run` with `Args` `["db", "status"]`, and compares `Stdout` with what its own `db.Status` call writes for the same path and migrations before `Run` is called and with what it writes after, and `Stderr` with `"campaigns: "` and that call's error text. `D07-pages` declares `pages.Description` as `const Description string` whose value is one line holding a character other than a space and no `"`, `\` or control character, as R-V2DY-FCEO requires. A test checks the line of `cli.Manifest` that begins `description = ` against `pages.Description` and checks the constant's bytes, and the `[env]` lines against `settings.Defaults()`; a test in package `campaigns_test` reads `manifest.toml` from `campaigns.Etc()` with `fs.ReadFile` and compares it with `cli.Manifest`.
