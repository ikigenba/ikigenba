# D06-links

Decisions cited as doc N are /home/mgreenly/Documents/ikigenba-campaigns.md; those cited as log DN are /home/mgreenly/Documents/ikigenba-campaigns-decisions.md.

The guest route: `internal/links`, which answers every request whose path begins `/t/` on campaigns' own host. A visitor who opens a piece's link lands on the tracking page on michaelgreenly.dev, which forwards a campaign token to `/t/<token>` here, passing the page's own referrer as the query parameter `r` (log D10). This route records the visit against the token's piece and sends the visitor on to the campaign's destination; a request that names no piece is sent to the service's default destination and recorded nowhere (doc 12, log D11). This document owns the package whole: `links.Config`, `links.Handler`, which requests are visits, what a visit records, and the answer. The visit's write, its time and the token lookup are `D04-store`'s (`Store.Visit`); the `campaign.visited` trail event is `D05-events`' (`trail.Visited`); mounting the handler at `/t/`, the telemetry middleware around it and the setting the default destination comes from are `D03-serve`'s and `D01-layout-and-run-seam`'s; the closed set of telemetry names is `D09-trail`'s.

## Which requests are visits

A request is a **visit** when all of these hold: its method is `GET` or `HEAD`; its path, as `r.URL.Path` holds it after percent-decoding, is `/t/` followed by a **token-shaped** remainder, exactly 26 characters each of `a`–`z`, `A`–`Z` or `2`–`7`, and nothing else; and the store, asked with that remainder lowercased, answers a piece. So the path `/t/` alone, a remainder of 25 or 27 characters, one holding `0`, `1`, `8`, `9` or any punctuation, a trailing slash, a second segment, and a percent-encoded slash (which decodes to `/`) are all not visits, and neither is a path that does not begin `/t/`. The query string never affects whether a request is a visit. Tokens are minted lowercase (log D12), so lowercasing makes a token printed or typed in capitals still match (log D22); a remainder that is not token-shaped cannot be a token and is answered without asking the store.

A token the store knows is a visit whatever its piece's state, planned, delivered or dropped, and whether or not its member is rejected (doc 5, log D22): a link already in someone's hands keeps working. A token whose campaign is deleted is unknown (log D22), which the store decides by answering `ErrNotFound`.

## What a visit records

For each visit the handler calls `Store.Visit` with the lowercased token and:

- user agent: the request's first `User-Agent` value, empty when absent;
- referrer: the first value of the query parameter `r` when there is one and it is not empty, otherwise the request's first `Referer` value, empty when absent (log D10: the page passes `document.referrer`, since the forward from the page would otherwise leave the page itself as the referrer);
- address: the request's first `X-Real-IP` value, empty when absent, never the connection's remote address, which on a space is nginx's socket (log D10).

The store stamps the visit's time from its own `Now`, in UTC truncated to the second, and answers the campaign, the piece and the campaign's destination as it is now (`D04-store`). The handler then records `campaign.visited` through `trail.Visited` and answers. Nothing is deduplicated: every visit is a row, a scanner's pre-fetch and a person's open alike (doc 13), and a `HEAD` is a visit as a `GET` is.

The handler ignores identity. Whatever `X-User-Id`, `X-User-Email`, `Authorization` or `Cookie` a request carries, and whatever caller its context holds, it answers and records the same visit. It sets no cookie. It hands `trail.Visited` the request's own context; `trail.Visited` records the request id and no user (`D05-events`).

## The answer

Every request the handler answers gets **the visit answer** for some URL: status 302, a `Location` of that URL exactly as configured or stored, `Cache-Control: no-store`, `Content-Length: 0`, the `Date` `net/http` adds, no other header, and an empty body. A visit's URL is the campaign's destination as the store answered it; every other request's is `Config.DefaultDestination`. Those are the only two cases: an unknown token, a method other than `GET` or `HEAD`, a path that is not one token, and a store that cannot answer all get the default answer and record nothing, neither a visit nor a telemetry event. The answers to a known and an unknown token differ in `Location` alone (and `Date`), so the route reveals nothing about which tokens exist (doc 12).

## Recorded decisions

- A token is a tracking handle, not a credential (doc 11, log D10, log D12). It grants nothing but a visit row and a redirect to a destination that is public anyway, so it is not compared in constant time, may appear in the request pair's `path` (`D09-trail`) and in nginx's access log, and the route sits outside the identity gate (manifest `guests = true`, log D10). Anyone holding a link can add visits; that is what a link is (doc 13). A known token costs a write an unknown one does not, so latency could tell them apart to someone who already holds a token, who learns nothing new; 128 random bits (log D12) are not found by guessing.
- Unknown tokens, deleted campaigns' tokens, wrong methods, wrong shapes and store failures all answer the default destination, identically, and record nothing (log D11, log D22). A store failure is not a 503: the visitor holds a link from a letter and should land somewhere sensible (doc 12); the lost visit is the cost.
- The answer is a bare 302, not `http.Redirect`, which adds a `Content-Type` and an HTML body for `GET` and rewrites relative URLs; the `Location` is the destination byte for byte (log D10).
- `Cache-Control: no-store` so no browser or proxy replays the redirect without asking, which would lose visits and keep a destination after the owner changes it (doc 12, doc 13).
- Departure: `Content-Length: 0` is set by the handler, where the root's settled answer (a decision of this design) names only the headers `net/http` sets for an empty body. A raw HTTP/1.1 probe against `httptest.NewServer` showed `net/http` sends `Content-Length: 0` on an empty `GET` answer and no `Content-Length` on a `HEAD` answer; setting it makes the two the same bytes, so the method a request used cannot be read off the answer and every answer of the route is one shape (doc 12: a link that names nothing reveals nothing).
- The identical-bytes guarantee covers HTTP/1.1 requests with no body and no `Connection` header. The handler never reads a body; how `net/http` manages the connection for a client that asks for `Connection: close`, or for an unread body, is `net/http`'s and says nothing about tokens.
- `campaign.visited` records the request id and no user, whatever identity the request carries: a decision of this design, settled by the root for this delivery, since the visitor is a guest and the root's settled routes, a decision of this design that `D03-serve` routes by, ignore identity on `/t/`. doc 13 supports it: a visit keeps the piece, the time and what the request shows, not who is signed in. `trail.Visited` does this itself (`D05-events`), so the handler passes the request's context unchanged. Only links' own records are covered: the request pair `telemetry.Middleware` records still carries a signed-in visitor's `X-User-Id`.
- The `r` parameter wins over `Referer` only when non-empty, since the page sends `r` only when `document.referrer` is not empty (log D10); the value is kept as given, unvalidated, like the user agent (doc 13).
- `OPTIONS` never reaches the handler on a space: the host's nginx answers it 204 at the server block. The handler still answers it as any other method.
- `links.Config` is exactly the settled seam: `Store`, `Telemetry`, `DefaultDestination`. The visit's time is the store's `Now`, so the handler needs no clock; it needs no emitter, since a visit is not a bus event (log D15).

## Consumer tasks

`D03-serve` builds `links.Handler(links.Config{Store: st, Telemetry: w, DefaultDestination: <CAMPAIGNS_DEFAULT_DESTINATION as settings read it>})` and hands it every request whose `URL.Path` begins `/t/`, whatever its method, headers or form, with no identity middleware, inside appkit's `telemetry.Middleware` so the request pair and the request id are there; `/t` itself is the page handler's (`D03-serve`), so no request under `/t/` is redirected before this handler sees it. `D10-on-a-space` verifies on a space: a `curl -s -o /dev/null -D - -A <ua> 'https://campaigns.<space>/t/<token>?r=<ref>'` for a piece's token answers 302 to the campaign's destination with no `Set-Cookie`, and the `engagement` tool for that piece then shows one more visit with that user agent and referrer and the caller's address; the same token in capitals adds another; a 26-character token no piece has answers 302 to the default destination and `engagement` is unchanged; and the tracking page on michaelgreenly.dev forwards a campaign token here (log D10). The request pair around `/t/` (`request.started`, `request.finished`), and whether it carries a signed-in visitor's user, is `D03-serve`'s and `D09-trail`'s, not this handler's. A test of this package opens a store with appkit `db.Open` and `campaigns.Migrations()` in a temporary directory and `store.New` with a fixed `Now` and its own `Rand`, makes a campaign, members and pieces through the store, builds a writer with `telemetry.New` over a `*telemetry.Capture`, drives `links.Handler` with `httptest.NewRecorder` or, for wire bytes, `httptest.NewServer` and a client that does not follow redirects, reads visits back through the store, flushes the writer and compares the capture; it closes the database to make the store fail.

- R-28GD-3781: campaigns' design defines **the visit answer** for a URL `u` as the answer with status 302, exactly the headers `Location` with the value `u`, `Cache-Control` with the value `no-store`, `Content-Length` with the value `0`, and the `Date` header `net/http` adds, and an empty body; the handler `links.Handler(cfg)` returns MUST answer every request with the visit answer for some URL, whatever its method, path and headers; and when served with `httptest.NewServer`, any two of its answers for the same URL to HTTP/1.1 requests with no body and no `Connection` header MUST be the same bytes on the wire but for the `Date` header, a `GET` and a `HEAD` among them; so that a `HEAD` and a `POST` to an unknown token and a `GET` to a known one whose destination equals `cfg.DefaultDestination` differ only in `Date`.
- R-ZIJY-G9FA: When the handler receives a `GET` or `HEAD` whose `URL.Path` is `/t/` followed by a token of a piece whose campaign is not deleted, it MUST answer with the visit answer for that campaign's destination as the store holds it when the request is received; so that after the destination is changed from `https://a.example/` to `https://b.example/`, the next visit is sent to `https://b.example/`.
