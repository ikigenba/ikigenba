The guest route: `internal/links`, which answers every request whose path begins `/t/` on campaigns' own host. A visitor who opens a piece's link lands on the tracking page on michaelgreenly.dev, which forwards a campaign token to `/t/<token>` here, passing the page's own referrer as the query parameter `r` (log D10). This route records the visit against the token's piece, tells the bus the first time a member opens any of its links, and sends the visitor on to the campaign's destination; a request that names no piece is sent to the service's default destination and recorded nowhere (doc 12, log D11). The package also owns the sweep, which tells the bus of every member whose first open went untold (hand-picked outcome 15). This document owns the package whole: `links.Config`, `links.Handler`, `links.StartSweep`, `links.SweepBatchSize`, which requests are visits, what a visit records, when a first open is told, the sweep, and the answer. The visit's write, its time, the token lookup and the marker that makes a first open told once are `D04-store`'s (`Store.Visit`, `Store.MarkOpened`); the `campaign.visited` trail event and the `campaign.member.opened` event are `D05-events`' (`trail.Visited`, `trail.MemberOpened`); beginning a sweep each hour, through `D01-layout-and-run-seam`'s `Process.SweepAfter`, and waiting for it at the stop are `D03-serve`'s; mounting the handler at `/t/`, the telemetry middleware around it and the setting the default destination comes from are `D03-serve`'s and `D01-layout-and-run-seam`'s; the closed set of telemetry names is `D09-trail`'s.

## Which requests are visits

A request is a **visit** when all of these hold: its method is `GET` or `HEAD`; its path, as `r.URL.Path` holds it after percent-decoding, is `/t/` followed by a **token-shaped** remainder, exactly 26 characters each of `a`–`z`, `A`–`Z` or `2`–`7`, and nothing else; and the store, asked with that remainder lowercased, answers a piece. So the path `/t/` alone, a remainder of 25 or 27 characters, one holding `0`, `1`, `8`, `9` or any punctuation, a trailing slash, a second segment, and a percent-encoded slash (which decodes to `/`) are all not visits, and neither is a path that does not begin `/t/`. The query string never affects whether a request is a visit. Tokens are minted lowercase (log D12), so lowercasing makes a token printed or typed in capitals still match (log D22); a remainder that is not token-shaped cannot be a token and is answered without asking the store.

A token the store knows is a visit whatever its piece's state, planned, delivered or dropped, and whether or not its member is rejected (doc 5, log D22): a link already in someone's hands keeps working. A token whose campaign is deleted is unknown (log D22), which the store decides by answering `ErrNotFound`.

## What a visit records

For each visit the handler calls `Store.Visit` with the lowercased token and:

- user agent: the request's first `User-Agent` value, empty when absent;
- referrer: the first value of the query parameter `r` when there is one and it is not empty, otherwise the request's first `Referer` value, empty when absent (log D10: the page passes `document.referrer`, since the forward from the page would otherwise leave the page itself as the referrer);
- address: the request's first `X-Real-IP` value, empty when absent, never the connection's remote address, which on a space is nginx's socket (log D10).

The store stamps the visit's time from its own `Now`, in UTC truncated to the second, and answers the campaign, the piece and the campaign's destination as it is now (`D04-store`). The handler then records `campaign.visited` through `trail.Visited`, tells the member's first open when this visit is it (below), and answers. Nothing is deduplicated: every visit is a row, a scanner's pre-fetch and a person's open alike (doc 13), and a `HEAD` is a visit as a `GET` is.

The handler ignores identity. Whatever `X-User-Id`, `X-User-Email`, `Authorization` or `Cookie` a request carries, and whatever caller its context holds, it answers and records the same visit. It sets no cookie. It hands `trail.Visited` the request's own context; `trail.Visited` records the request id and no user (`D05-events`).

## The first open

A member is **opened** once any of its pieces has a visit, and the bus hears of it once per member per campaign, as `campaign.member.opened` (hand-picked outcome 13, delivery log P7). `Store.Visit` sets the member's marker in the same write as the visit and answers `Visited.Opened` true exactly when this call set it, with `Visited.First`, the member's earliest visit (`D04-store`). On `Opened` the handler calls `trail.MemberOpened` with the request's context after `trail.Visited`, so the trail tells the visit before the open; both halves carry the visit's request id and no user (`D05-events`). On a visit that did not set the marker, and on every request that is not a visit, the handler emits nothing on the bus. Because the marker is one write with the visit, of several visits racing on one member's links exactly one tells the open. The visitor's answer is the same either way, and nothing waits for telemetry or the bus.

A member is **untold** when it belongs to a live campaign, has at least one visit and its marker is empty: visits the previous release recorded, before the marker existed or after a rollback, leave members so. Only the sweep tells them.

## The sweep

`StartSweep` begins one sweep, which tells every untold member's first open (hand-picked outcome 15, delivery log P8). No sweep runs at the start: `D03-serve`'s `Run` begins one an hour after the start and another an hour after each one ends, timed by `D01-layout-and-run-seam`'s `Process.SweepAfter`, and waits for it before it stops (delivery log S1-2). It walks `Store.MarkOpened` from the zero `MemberKey`, `SweepBatchSize` members at a time in campaign-then-candidate order; each call marks and answers the page's untold members in one write, and the sweep calls `trail.MemberOpened` for each with `First` as `at`, under a context derived from the sweep's `ctx` that carries an empty `identity.Caller`, so its events carry an empty request id and user; whether it is cut off is still read from the sweep's own `ctx`. Before it asks for the next page it flushes `cfg.Telemetry` and `cfg.Events`, so a page's events are handed to their sinks before the next page is marked, and the queues of neither the writer nor the emitter, 1024 events each, ever overflow however many members the walk tells. It returns at once, works in the background, and closes the channel it returned once it has ended. When the walk reaches its end, a page shorter than `SweepBatchSize` answering the zero key, it writes its completion line to `stderr` if it told at least one member, and nothing if it told none; when the store fails under it, its failure line and the store's error, in the form campaigns' other store lines take, and stops, the next sweep finishing the work. A context that ends before the walk's last flush has returned cuts it off with no line, even after the walk reached its end. With no `stderr` it writes nothing. A sweep that finds no member untold walks every member, tells nothing and writes nothing, so once the suite is caught up the hourly sweep is silent. Members of a deleted campaign are never untold, so they are not swept (the guest route cannot reach their tokens either); rejected members are, since engagement counts them.

## The answer

Every request the handler answers gets **the visit answer** for some URL: status 302, a `Location` of that URL exactly as configured or stored, `Cache-Control: no-store`, `Content-Length: 0`, the `Date` `net/http` adds, no other header, and an empty body. A visit's URL is the campaign's destination as the store answered it; every other request's is `Config.DefaultDestination`. Those are the only two cases: an unknown token, a method other than `GET` or `HEAD`, a path that is not one token, and a store that cannot answer all get the default answer and record nothing, neither a visit nor a telemetry event. The answers to a known and an unknown token differ in `Location` alone (and `Date`), so the route reveals nothing about which tokens exist (doc 12).

## Recorded decisions

- A token is a tracking handle, not a credential (doc 11, log D10, log D12). It grants nothing but a visit row and a redirect to a destination that is public anyway, so it is not compared in constant time, may appear in the request pair's `path` (`D09-trail`) and in nginx's access log, and the route sits outside the identity gate (manifest `guests = true`, log D10). Anyone holding a link can add visits; that is what a link is (doc 13). A known token costs a write an unknown one does not, so latency could tell them apart to someone who already holds a token, who learns nothing new; 128 random bits (log D12) are not found by guessing.
- Unknown tokens, deleted campaigns' tokens, wrong methods, wrong shapes and store failures all answer the default destination, identically, and record nothing (log D11, log D22). A store failure is not a 503: the visitor holds a link from a letter and should land somewhere sensible (doc 12); the lost visit is the cost.
- The answer is a bare 302, not `http.Redirect`, which adds a `Content-Type` and an HTML body for `GET` and rewrites relative URLs; the `Location` is the destination byte for byte (log D10).
- `Cache-Control: no-store` so no browser or proxy replays the redirect without asking, which would lose visits and keep a destination after the owner changes it (doc 12, doc 13).
- Departure: `Content-Length: 0` is set by the handler, where the root's settled answer (a decision of this design) names only the headers `net/http` sets for an empty body. A raw HTTP/1.1 probe against `httptest.NewServer` showed `net/http` sends `Content-Length: 0` on an empty `GET` answer and no `Content-Length` on a `HEAD` answer; setting it makes the two the same bytes, so the method a request used cannot be read off the answer and every answer of the route is one shape (doc 12: a link that names nothing reveals nothing).
- The identical-bytes guarantee covers HTTP/1.1 requests with no body and no `Connection` header. The handler never reads a body; how `net/http` manages the connection for a client that asks for `Connection: close`, or for an unread body, is `net/http`'s and says nothing about tokens.
- `campaign.visited` records the request id and no user, whatever identity the request carries: a decision of this design, settled by the root for this delivery, since the visitor is a guest and the root's settled routes, a decision of this design that `D03-serve` routes by, ignore identity on `/t/`. doc 13 supports it: a visit keeps the piece, the time and what the request shows, not who is signed in. `trail.Visited` does this itself (`D05-events`), so the handler passes the request's context unchanged. Only links' own records are covered: the request pair `telemetry.Middleware` records still carries a signed-in visitor's `X-User-Id`.
- The `r` parameter wins over `Referer` only when non-empty, since the page sends `r` only when `document.referrer` is not empty (log D10); the value is kept as given, unvalidated, like the user agent (doc 13).
- `OPTIONS` never reaches the handler on a space: the host's nginx answers it 204 at the server block. The handler still answers it as any other method.
- `links.Config` is the settled seam plus the emitter: `Store`, `Telemetry`, `Events`, `DefaultDestination`. The visit's time is the store's `Now`, so the handler needs no clock. A visit itself is still not a bus event (log D15); the emitter is there for a member's first open, which is (hand-picked outcome 13, delivery log P7). The sweep takes the same `Config`, reading only its `Store`, `Telemetry` and `Events`.
- **The first open is told once per member per campaign, from a durable marker** (hand-picked outcome 13, delivery log P7): `campaign.visited` stays trail-only and unchanged, and later visits tell nothing. The marker is set in the visit's own write (`D04-store`), so the live path and the sweep share it and never tell one member twice; the cost is that an event the emitter drops after its marker is set is never sent again.
- **The open is told as the visit is: the request id and no user** (delivery log P7), for the reason `campaign.visited` names none. The sweep's events carry neither, since no request causes them.
- **The sweep runs in `internal/links`, each hour after the start and never at it** (hand-picked outcome 15, delivery log P8, delivery log S1-2): it is the same act as the live path, from the store's side, so it belongs with it. It waits an hour because events moves an ok subscriber's cursor past events it does not yet accept and re-asks every service's declarations only every 60 seconds, so a sweep at the start on deploy day would be passed over by candidates whatever the restart order; `D05-events` records the decision whole. It runs every hour rather than once, so visits the previous release records after a rollback are told within the hour. Rejected: a migration, which cannot reach the bus; and a CLI subcommand, which contradicts `D02-cli`'s rule that a command emits nothing and has no precedent in the suite.
- **The sweep flushes both the writer and the emitter between pages**, where the settled plan named only the emitter: each told member makes one trail event and one bus event, and appkit's writer, like the emitter, drops what arrives at a full queue of 1024, leaving an `undelivered event` line `D03-serve` forbids. Flushing both bounds each queue by one page.
- **The sweep's two lines are contract, not copy constants**, as campaigns' other stderr lines are: `D03-serve`'s sweep test waits for the completion line, so a program reads it.
- **A sweep that told no member writes nothing** (delivery log S1-2): it runs every hour, so a line for every caught-up sweep would fill the log forever; the completion line marks only a sweep that told someone.
- **A sweep that fails stops and keeps what it told**: the members of earlier pages are marked and their events queued; the failed page marked nothing, its call answering an error, and the next sweep begins the walk again from the zero key.

## Consumer tasks

Current usage: `D03-serve` builds `links.Handler(links.Config{Store: st, Telemetry: w, DefaultDestination: s.DefaultDestination})` and begins nothing at the start. Proposed usage: `web.Handler` builds `links.Handler(links.Config{Store: cfg.Store, Telemetry: cfg.Telemetry, Events: cfg.Events, DefaultDestination: cfg.Settings.DefaultDestination})`, and `Run`, while serving, calls `p.SweepAfter(time.Hour)` and, each time a channel it returned delivers while `ctx` is not done, calls `swept := links.StartSweep(ctx, links.Config{Store: st, Telemetry: w, Events: em, DefaultDestination: s.DefaultDestination}, p.Stderr)`, waits for `<-swept`, then calls `p.SweepAfter(time.Hour)` again; it begins no sweep at the start, and at the stop waits for a running sweep's `<-swept` before it flushes the emitter and records `service.stopping`. The handler, on a visit, calls `v, err := cfg.Store.Visit(ctx, tok, in)`, then `trail.Visited(r.Context(), cfg.Telemetry, v.Campaign, v.Piece)` and, when `v.Opened`, `trail.MemberOpened(r.Context(), cfg.Telemetry, cfg.Events, v.Campaign, v.Candidate, v.First)`. The sweep calls `next, opened, err := cfg.Store.MarkOpened(ctx, after, links.SweepBatchSize)` from `store.MemberKey{}`, `trail.MemberOpened(sctx, cfg.Telemetry, cfg.Events, o.Campaign, o.Candidate, o.First)` for each `store.Opened` `o`, `sctx` being `identity.NewContext(context.WithoutCancel(ctx), identity.Caller{})` (never `context.Background()`, which gosec's G118 refuses in a goroutine handed a `ctx`), so its events carry an empty `RequestID` and `User`; it reads `ctx`, not `sctx`, to know whether it is cut off; flushes `cfg.Telemetry` and `cfg.Events`, and goes on from `next` until it is the zero key.

`D03-serve` hands the handler every request whose `URL.Path` begins `/t/`, whatever its method, headers or form, with no identity middleware, inside appkit's `telemetry.Middleware` so the request pair and the request id are there; `/t` itself is the page handler's (`D03-serve`), so no request under `/t/` is redirected before this handler sees it. `D10-on-a-space` verifies on a space: a `curl -s -o /dev/null -D - -A <ua> 'https://campaigns.<space>/t/<token>?r=<ref>'` for a piece's token answers 302 to the campaign's destination with no `Set-Cookie`, and the `engagement` tool for that piece then shows one more visit with that user agent and referrer and the caller's address; the same token in capitals adds another; a 26-character token no piece has answers 302 to the default destination and `engagement` is unchanged; and the tracking page on michaelgreenly.dev forwards a campaign token here (log D10). The request pair around `/t/` (`request.started`, `request.finished`), and whether it carries a signed-in visitor's user, is `D03-serve`'s and `D09-trail`'s, not this handler's. A test of this package opens a store with appkit `db.Open` and `campaigns.Migrations()` in a temporary directory and `store.New` with a fixed `Now` and its own `Rand`, makes a campaign, members and pieces through the store, builds a writer with `telemetry.New` over a `*telemetry.Capture`, drives `links.Handler` with `httptest.NewRecorder` or, for wire bytes, `httptest.NewServer` and a client that does not follow redirects, reads visits back through the store, flushes the writer and compares the capture; it closes the database to make the store fail. A test of the first open builds the emitter with `events.New` over an `*events.Capture`, with `trail.Emits()` as its `Emits`, makes two `GET`s of one member's tokens, flushes the writer and the emitter, and compares both captures; for the race it makes several `GET`s at once. A test of the sweep makes members and visits through its own store, clears every member's marker through `DB.Write` as `D03-serve`'s test does, as the previous release leaves them, calls `done := links.StartSweep(ctx, cfg, &buf)`, receives from `done` with a deadline that fails the test, and compares `buf` and both captures; to hold the sweep at a page it builds the emitter or the writer over a sink whose `Deliver` blocks until the test releases it; to fail it, it calls `SetFailing(true)` on the handle; to cut it off, it cancels `ctx`.
