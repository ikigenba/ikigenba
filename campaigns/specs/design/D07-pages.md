# D07-pages

What campaigns draws as HTML: `internal/pages`, the five templates `landing`, `campaign`, `tools`, `about` and `notfound` of the root package's `Assets()` and the data each is executed with, `pages.Description`, and the page handler that answers `/`, `/campaigns/<id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it: the landing page of the campaigns, a page per campaign with its definition, material, members, pieces and engagement, the tools page, the about screen and the not-found page (doc 22). The pages are listings only: they carry no form, change no record, and campaigns are changed through the tools (doc 21, `D08-tools`). A guest is sent to sign in, as sites' pages send one (log D10). Decisions cited as doc N are /home/mgreenly/Documents/ikigenba-campaigns.md; those cited as log DN are /home/mgreenly/Documents/ikigenba-campaigns-decisions.md.

`D01-layout-and-run-seam` declares `pages.ServiceName` and the addresses this document builds with (`urls.Auth`, `urls.SignIn`, `urls.Sibling`, `urls.CandidatePage`, `urls.ProspectListPage`, `urls.ArtifactPage`); `D03-serve` routes every path that is not `/events`, `/declarations`, `/mcp`, under `/t/` or under `/_appkit/` to this handler inside `identity.Optional`, and defines a request's caller and a guest (R-PZTX-693Q); `D04-store` declares every read the pages make, the windows, the orders, the stamp and `store.Unreachable`; `D02-cli` bounds `pages.Description`'s bytes, since the manifest embeds it (R-V2DY-FCEO); `D08-tools` registers the tools the tools page lists and issues the `next` tokens the pages share. appkit's `page`, `paging`, `identity`, `mcp` and `candidates` packages own their contracts.

## The pages

The landing page, `/`, shows one window of the campaigns not deleted, `paging.DefaultLimit` of them, newest first in the store's campaign order (`D04-store`), each with its id, name, channels, when it was created, to the minute, and its counts: members, rejected ones included, pieces delivered, and members that opened anything (doc 14). It is the root of the banner's trail.

`/campaigns/<id>` is one campaign: its definition (name, description, channels, destination, who created it and when, to the second), its counts, its material whole in the order added (doc 9), and one window of its members, `paging.DefaultLimit` of them in the store's member order, added time then candidate id (log D19). Each member shows its candidate id linked to the candidate's page on candidates, the business's display name as candidates answers it when the page is read, the prospect list it came from linked to the prospect list's page, when it was added, whether any of its links was opened, its rejection, and one cell per channel the campaign uses: the piece's state, its delivery when delivered, and its opens with the first and last visit; a channel for which the member got no piece is an empty state, which the template words by channel (doc 6, log D16). A material reference shows its label and path, linked to the artifact's page on artifacts by the artifact id the reference holds (log D20). It is one level below the root, named by the campaign's id. The page never shows a business's address, phone or email, nor a piece's token or link: the merge list carries those (log D19).

The tools page lists every tool registered on the MCP server, in registration order, which is `D08-tools`' catalog order, each with the first line of its description; the about screen shows the service's name, the banner's `Release` and `Commit`, and `pages.Description`. Each is one level below the root, `pages.ToolsLevel` and `pages.AboutLevel`. Every other path is the not-found page, 404, whatever the method; so are a campaign path whose id names no campaign or a deleted one, an id that is not a well-formed campaign id, and a page value the page cannot decode. The not-found page is one answer, byte for byte the same for each of those.

The banner's user is the caller's email with auth's profile and sign-out addresses built on `urls.Auth` (`D01-layout-and-run-seam`). Times are shown as the templates' comments ask: a `time` element's `datetime` in RFC 3339 UTC to the second, and the text in `pages.MinuteLayout` on the landing and for a member's added, rejected, delivered, first and last times, and in `pages.SecondLayout` for a campaign's created time on its own page. Counts are plain integers.

## Paging

Each page that lists holds one list, so its page value is the query parameter `page` (`shape/`'s Listing, one-list form). The empty value asks for the first window. The token the list's tool issues as `next`, an **after-token**, asks for the window after the entry it names: the landing's are the `campaigns` tool's, `paging.Token{Tool: "campaigns"}` over a campaign's created text and id (`D04-store`, `D08-tools`); a campaign page's are the `campaign` tool's, `paging.Token{Tool: "campaign"}` over a member's added text and candidate id. A **before-token**, which only the page issues, is the same token under the tool's name with `-before` appended, `campaigns-before` or `campaign-before`, and asks for the `paging.DefaultLimit` entries preceding the one it names. The literal `last` asks for the last `paging.DefaultLimit` entries. Any other value is undecodable and is the not-found page, decided before the store is read.

The page reads a before-token's window and the last window through the store's reversed windows, `ListCampaignsReversed` and `ListMembersReversed`, asking for one entry more than it shows, so it learns whether the window **underflows**: when at most `paging.DefaultLimit` entries precede a before-token's position, or the list holds at most `paging.DefaultLimit` in all for `last`, the page answers a 303 to the list's first window, `/` or `/campaigns/<id>`, so each first window has one URL. Next is the after-token of the last entry shown, while more follow; Prev the before-token of the first entry shown, on any window but the first. The template data carries the page value the request carried (`Page`), `Prev` and `Next`, and the templates draw First, Prev, Next and Last from them.

## Names from candidates

The campaign page reads each shown member's business from candidates with appkit's `candidates` client, `Candidate(ctx, id)`, on the request's context, so the client forwards the signed-in user as the caller (log D18, `D03-serve`). The member's `Name` is the `Name` that call answers; when the run has no candidates client, or the call answers any error, not found, refused, unavailable or a transport failure alike, the name is empty and the template shows it as unknown (log D19). The page is drawn either way: a sibling that is down costs the names, never the page. The links to the candidate's and the prospect list's pages on candidates, and to the artifact's page on artifacts, are built on the services file's entries read for each request, and are empty when the file names no such sibling (`D01-layout-and-run-seam`, log D19). No other page reads candidates, and no page reads artifacts.

## Guests, methods and failures

The handler decides in this order. A guest, a request with no `X-User-Id` or an empty one (R-PZTX-693Q), is answered 302 to `urls.SignIn` with an empty body, whatever its path and method, before anything else is read. A signed-in request to a path that is not one of the four page paths is the not-found page, whatever its method. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD` and an empty body. An undecodable page value on `/` or a campaign page is the not-found page. None of these reads the store or calls candidates. Then the store is read: a campaign it does not hold live is the not-found page, an underflow is the 303, and a store that cannot be read is a **read refusal**, 503 in plain text with the line `store.Unreachable`, as candidates answers. The tools page, the about screen and the not-found page read no store and are served the same while it fails. `HEAD` is answered as `GET` without a body. No answer sets a cookie.

## Recorded decisions

- **One data type per thing a template draws**, each field list exactly the template comment's, in its order (the root `AGENTS.md`'s Web assets rule: design names each template and the data it receives; the field split into types is this design's own choice).
- **Departure: counts are Go `int`, not `int64` as candidates' pages declare them.** Reason: the template comments say `int`, and `store.Counts` and `store.PieceEngagement` hold `int` (`D04-store`, R-69F7-9UCS), so no conversion is needed; candidates uses `int64` because its store does.
- **`pages.Description` is declared here, without a value, as a copy constant** (the brief; D02's R-V2DY-FCEO bounds its bytes so the manifest can embed it): its words are copy, in one place.
- **Departure: the tools page reads the MCP server's registered tools**, `mcp.Server.Tools()`, at each request, rather than `tools.Catalog()` as candidates' does (this design's own choice, following sites' tools page). Reason: `D03-serve` hands `pages.Config` the server on which `tools.Register` registers `D08-tools`' tools in catalog order, as sites' tools page does, so the page and `tools/list` cannot disagree; `D08-tools` requires `Register` to register in catalog order (R-Q70F-FATK), so the page lists the catalog's order, and its first-line rule matches `tools.FirstLine` (R-SIVY-H8KM). Each row's description is the description's first line, the text before its first line feed, as the template comment asks.
- **Departure: a guest is sent to sign in before the method is looked at** (from sites' pages, which refuse a method with 405 first, and from candidates', which never see a guest). Every template comment, the not-found page's included, says a guest is sent to sign in; one rule for every path and method a guest sends here says so, and tells a guest nothing about which paths are pages (this design's own choice; log D10 admits guests, sites is the precedent for sending them to sign in).
- **The guest's 302 and the underflow's 303 have empty bodies** (this design's own choice): neither is a page, so neither draws a template, and net/http's redirect body would be markup the code writes.
- **One parameter, `page`** (`shape/`'s Listing): each page lists one list. The landing's after-tokens are the `campaigns` tool's (`D04-store`'s consumer tasks), and a campaign page's the `campaign` tool's, `paging.Token{Tool: "campaign"}` over a member's added text and candidate id, so a window on a page and the tool's answer for the same `page` are one window and a token on the page can be handed to an agent. Before-tokens use the tool's name with `-before` appended and `last` is the literal word, as `shape/`'s Listing and candidates' pages do; the tools refuse both, as any token they did not issue.
- **An underflow answers 303** to the list's first window, `/` or `/campaigns/<id>`, so every first window has one URL and an empty page value (`shape/README.md`, Listing, which prescribes the 303).
- **The last window is aligned to the end of the list**, the last `paging.DefaultLimit` entries, not the final window of the Next walk (`shape/README.md`, Listing: Last names the last 25 entries; candidates' pages read it the same way).
- **Unknown, malformed and deleted campaign ids, undecodable page values and paths that are not pages are one not-found answer**, byte for byte the same, as candidates' pages decided; a deleted campaign is held by the store but answered as one it does not hold (`D04-store`, log D22). A campaign deleted between the page's reads is not found too.
- **The material is shown whole**, as the store answers it and the `campaign` tool does (doc 9, doc 22; `D04-store` records this departure from `shape/README.md`'s Listing, and this page follows it): a campaign's material is a handful of templates.
- **Names are read live from candidates, and any failure leaves them empty** (log D16, log D19): campaigns keeps only the candidate id, so the name is candidates' as the page is read, and the page is drawn without it rather than refused. Only the members the window shows are read.
- **A database outage is a plain-text read refusal**: the templates have no unavailable state, and `store.Unreachable` is the line campaigns answers where the answer is not a page (`D04-store`). The guest's redirect, the 405, the not-found page and the tools and about pages are decided without the store, so they are the same during an outage.
- **The pages show no token, link, address, phone or email** (log D19): the data types carry none, and the merge list carries them for the agents.
- **`pages.Config` carries no clock** (this design's own choice, as candidates' pages): every time a page shows is a stamp the store wrote, so the page formats and never reads `Now`.
- The time layouts are contract constants with values, `pages.MinuteLayout` and `pages.SecondLayout` (this design's own choice, as candidates' pages; the template comments give the shown forms); which field takes which layout is the template comments'.

## Consumer tasks

`web.Handler` (`D03-serve`) calls `set, err := pages.Load()` once and serves every page path with `identity.Optional(pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, Candidates: cfg.Candidates, MCP: cfg.MCP}))`, `tools.Register(cfg.MCP, ...)` having filled the server.

The landing reads `p := r.URL.Query().Get("page")`, tries `paging.Token{Tool: "campaigns"}.Decode(p, &created, &id)`, then `paging.Token{Tool: "campaigns-before"}.Decode(p, &created, &id)`, then `p == "last"`, answering the not-found page when a non-empty `p` fits none; reads `rs, err := st.ListCampaigns(ctx, created, id, paging.DefaultLimit+1)` or `st.ListCampaignsReversed(ctx, created, id, paging.DefaultLimit+1)` (`"", ""` for `last`); answers 303 to `/` on an underflow; and executes `landing` with `pages.LandingData{Banner: b, Campaigns: []pages.CampaignRow{{ID: r.Campaign.ID, Name: r.Campaign.Name, Channels: r.Campaign.Channels, Created: …, CreatedText: …, Members: r.Counts.Members, Delivered: r.Counts.Delivered, Opened: r.Counts.Opened}, …}, Page: p, Prev: …, Next: …}` through `set.Write(w, r, http.StatusOK, "landing", data)`.

The campaign page, for `/campaigns/` followed by an `id` with `store.ValidCampaignID(id)`, decodes `page` with `campaign` and `campaign-before` into `&added, &cand`, reads `c, err := st.GetCampaign(ctx, id)`, `n, err := st.Counts(ctx, id)`, `ms, err := st.Materials(ctx, id)` and `rows, err := st.ListMembers(ctx, id, added, cand, paging.DefaultLimit+1)` or `st.ListMembersReversed`, then for each member shown `b, err := cfg.Candidates.Candidate(r.Context(), m.Member.Candidate)` when `cfg.Candidates` is not nil, and builds `pages.CampaignData` with `urls.CandidatePage(urls.Sibling(cfg.ServicesPath, "candidates"), …)`, `urls.ProspectListPage(…)` and `urls.ArtifactPage(urls.Sibling(cfg.ServicesPath, "artifacts"), x.Artifact)`, the banner's `Trail` the one level `page.Level{Name: id, URL: "/campaigns/" + id}`.

The tools page maps `cfg.MCP.Tools()` to `[]pages.ToolRow{{Name: t.Name, Description: first line of t.Description}, …}`; the about screen executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}`, `b.Trail` set to `[]page.Level{pages.AboutLevel}`.

A test opens a store over its own database with a clock it sets and a `Rand` it controls, makes campaigns, members, pieces, material and visits with the store's methods, deletes a campaign, writes a services file naming a fake candidates' Unix socket (or none) and URLs for `auth`, `candidates` and `artifacts`, builds its own set with `pages.Load()`, a server with `mcp.NewServer` on which it registers tools (`tools.Register`, or tools of its own), serves `identity.Optional(pages.Handler(cfg))` with a fixed banner, sends raw requests with and without `X-User-Id`, and compares each body with what `set.Write` writes for the data the definitions below build; it walks Next to the end and Prev back, asks `last` and the underflowing before-token for the 303, asks malformed, unknown and deleted ids and undecodable page values for the not-found page, turns `SetFailing(true)` on for the read refusal, and inspects the fake candidates' record of requests and their identity headers.
