# D07-events

The pass events: `internal/trail`'s two events, `pass.started` and `pass.finished`, which candidates emits on the suite's event bus and records in its own trail for every pass (decision 13); their declarations; the identity and cause each carries; the one event candidates accepts, `scrape.finished`; and what candidates declares at `/declarations`. `D06-passes` decides when each is told and what a delivery of `scrape.finished` does; `D03-serve` owns the route `/declarations` and builds the writer and emitter; `D09-trail` owns the trail as a whole, its closed set of names and its secrecy. It is scrapes' run events with a pass in place of a run.

## The two events

A pass's life is told by `pass.started`, once the pass is recorded `running`, and `pass.finished`, once its ending is recorded, however it ended: `done`, or `failed` by scrapes, the store, the drain or the next start. `pass.started` carries `pass` (the pass's id) and `trigger` (the run id a delivery named, or `rebuild`). `pass.finished` carries `pass`, `trigger`, `status`, `reason` (empty when `done`), and the nine counts `rows`, `new`, `changed`, `unchanged`, `gone`, `created`, `linked`, `rescored` and `unranged`, integers, as the record holds them. Ids, words and counts only: no business name, address, phone, email, person or ruling text (decision 18).

Every pass event goes two ways at once under the same name, attributes, request id and user: recorded in the trail through the writer and emitted on the bus through the emitter, as scrapes' run events do, because appkit's emitter records only `event.lost` in the trail. It is told after the write it reports is committed, never for a pass that was not recorded and never for an ending the store could not record (`D06-passes`).

## Under the pass's starter

Each event is told as the pass's starter: its request id is the request id the pass was recorded with and its user the pass's user id, whatever context tells it, so a pass's two events name the request that started it even when the drain or the next start tells its end. For a `rebuild` that is the tool call's request id and caller. For a delivery it is the delivery's request id, the one the events app sent or one minted for it, and whatever user the delivery's request named, which is none; the delivered `scrape.finished` is the bus event's cause, one level deeper, because appkit's delivery handler puts it on the context the pass is started under (`D06-passes`). A pass's events told by the next start's settling carry no cause. The service identity a delivery's pass reads scrapes as (`D06-passes`) is the reads' alone; the pass's own events keep its starter.

## The declarations

`trail.Emits()` declares the two names, literal, each with its attribute keys in order; the emitter is built with them, so appkit refuses a pass event whose keys are not exactly these and every key is always present. The engine's handlers are keyed by the one name candidates accepts, `trail.Accepted`, `scrape.finished`: an exact name, never a pattern or `*`, because the events app delivers only on `*` or an exact name. appkit's `events.DeclarationsHandler`, given the emitter and the engine's handlers, answers the emissions sorted by event name, each one's attributes in the order declared, and the accepted names sorted; so candidates declares `pass.finished` before `pass.started` and accepts `scrape.finished` alone. A `scrape.finished` carries, as scrapes emits it, `scraper`, `run`, `status`, `reason` and the run's five counts; candidates reads `scraper`, `run` and `status` and the event's id (`D06-passes`).

## Recorded decisions

- Two fixed names and one function, `Record`, which knows which attributes each name carries and tells nothing for a name not its own, as scrapes' `trail.Record`.
- **Events as the pass's starter**, as scrapes' run events: a pass's end is told from the background or by the next start, where the starting request is gone, so the record keeps its request id and user (`D04-store`). The cause is the context's, which the work keeps from the starting call.
- The counts are integer attributes (an `int64` basic form); `reason` is present and empty on a `done` pass's `pass.finished`, as appkit's exact-keys rule requires.
- The accepted name is declared as `trail.Accepted` beside the emitted ones, so the declarations and the handlers name it from one place.
- The body `/declarations` answers is stated here because its content is this document's declarations; the route and its place outside the identity gate are `D03-serve`'s.

## Consumer tasks

The engine (`D06-passes`), once `store.AddPass` has returned a pass `p`, calls `trail.Record(ctx, w, em, trail.Started, p)`, and once `store.FinishPass` or `store.FailPass` has returned it ended, `trail.Record(ctx, w, em, trail.Finished, p)`; its `Handlers()` answers `events.Handlers{trail.Accepted: e.Deliver}`. `cli.Run` builds its emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`; `D03-serve` answers `/declarations` with `events.DeclarationsHandler(em, eng.Handlers())`. A test builds a writer over a `*telemetry.Capture` and an emitter over an `*events.Capture` with `trail.Emits()`, calls `trail.Record` with a `store.Pass` under a context carrying another caller and an `events.Cause`, flushes both, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`; it serves `events.DeclarationsHandler(em, eng.Handlers())` with `httptest` to read the declarations; and it drives `cli.Run` with captures and a fake scrapes, makes a `rebuild` call with the `mcp.Client` and posts a delivery of `scrape.finished` to `/events` with an `X-Request-Id` of its own, and compares the pass events of each.
