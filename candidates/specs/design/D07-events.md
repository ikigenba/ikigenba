# D07-events

The pass events: `internal/trail`'s two events, `pass.started` and `pass.finished`, which candidates emits on the suite's event bus and records in its own trail for every pass (decision 13); their declarations; the identity and cause each carries; the two events candidates accepts, `scrape.finished` and `cron.judge_candidates.fired`; and what candidates declares at `/declarations`. `D06-passes` decides when each is told and what a delivery of either accepted event does; `D03-serve` owns the route `/declarations` and builds the writer and emitter; `D09-trail` owns the trail as a whole, its closed set of names and its secrecy. It is scrapes' run events with a pass in place of a run.

## The two events

A pass's life is told by `pass.started`, once the pass is recorded `running`, and `pass.finished`, once its ending is recorded, however it ended: `done`, or `failed` by scrapes, the store, the drain or the next start. `pass.started` carries `pass` (the pass's id), `kind` (`ingest`, `judge`, `rebuild` or `enrich`), `origin` (`run`, `cron`, `rebuild`, `enrich` or `pass`) and `trigger` (the run id a `scrape.finished` delivery named, the cron slug `judge_candidates`, `rebuild`, `enrich`, or for a pass another pass started the starting pass's id). `pass.finished` carries `pass`, `kind`, `origin`, `trigger`, `status`, `reason` (empty when `done`), and the counts `rows`, `new`, `changed`, `unchanged`, `gone`, `created`, `linked`, `judged`, `rescored`, `unranged`, `derived`, `due`, `fetched`, `https`, `http` and `none`, integers, as the record holds them. `derived` is the number of derived results the pass recorded, an enrich's or a rebuild's, and 0 for any other; what it counts is `D06-passes`'. The last five are the fetched website kind's, 0 for a pass that did not walk it; what each counts is `D15-website-check`'s. The enrich kind and origins, the five website keys and `derived` are additions only, so a subscriber written against an earlier release keeps reading every key it knew. Ids, words and counts only: no business name, address, phone, email, person or ruling text (decision 18).

`judged` is the number of candidates the pass judged, 0 for an ingest. Before the release that added `judged` the same count was called `rescored`; a script subscribed to `pass.finished` may read that key, and an event payload is persisted and may be delivered across a release boundary, so the rename goes by expand then contract: a release added `judged` and kept `rescored` beside it carrying the same value, to be dropped in a later release. The website check's release and the enrichers' release keep `rescored` still, since neither changes the events beyond adding counts; its removal remains owed. `kind` and `origin` are additions only. A consumer reads `judged`.

Every pass event goes two ways at once under the same name, attributes, request id and user: recorded in the trail through the writer and emitted on the bus through the emitter, as scrapes' run events do, because appkit's emitter records only `event.lost` in the trail. It is told after the write it reports is committed, never for a pass that was not recorded and never for an ending the store could not record (`D06-passes`).

## Under the pass's starter

Each event is told as the pass's starter: its request id is the request id the pass was recorded with and its user the pass's user id, whatever context tells it, so a pass's two events name the request that started it even when the drain or the next start tells its end. For a `rebuild` that is the tool call's request id and caller. For a delivery it is the delivery's request id, the one the events app sent or one minted for it, and whatever user the delivery's request named, which is none; the delivered `scrape.finished` or `cron.judge_candidates.fired` is the bus event's cause, one level deeper, because appkit's delivery handler puts it on the context the pass is started under (`D06-passes`). An `enrich` call's pass is told as that call, like a `rebuild`'s. A pass another pass started (origin `pass`, `D06-passes` decides when) has no user and is told under its starter's request id and its starter's event cause: a delivery's `scrape.finished` is the cause of the enrich its ingest starts, and a tool call's enrich hands on none to the judge it starts. A pass's events told by the next start's settling carry no cause, a follow-on's included: a pass with origin `pass` that `Recover` fails tells its end with no cause, like any recovered pass. The service identity a delivery's pass reads scrapes as (`D06-passes`) is the reads' alone; the pass's own events keep its starter. A judge pass reads nothing from scrapes.

## The declarations

`trail.Emits()` declares the two names, literal, each with its attribute keys in order; the emitter is built with them, so appkit refuses a pass event whose keys are not exactly these and every key is always present. The engine's handlers are keyed by the two names candidates accepts, `trail.Accepted`, `scrape.finished`, and `trail.AcceptedJudge`, `cron.judge_candidates.fired`: exact names, never a pattern or `*`, because the events app delivers only on `*` or an exact name, as scrapes accepts its triggers' `cron.scrape_<scraper>.fired`. cron emits `cron.<slug>.fired` for each fire of a trigger, and the owner creates the trigger `judge_candidates` with a daily schedule on each space. appkit's `events.DeclarationsHandler`, given the emitter and the engine's handlers, answers the emissions sorted by event name, each one's attributes in the order declared, and the accepted names sorted; so candidates declares `pass.finished` before `pass.started` and accepts `cron.judge_candidates.fired` and `scrape.finished`, in that order. A `scrape.finished` carries, as scrapes emits it, `scraper`, `run`, `status`, `reason` and the run's five counts; candidates reads `scraper`, `run` and `status` and the event's id (`D06-passes`). A `cron.judge_candidates.fired` carries, as cron emits it, `trigger`, `when` and `scheduled`; candidates reads only its name and id (`D06-passes`).

## Recorded decisions

- Two fixed names and one function, `Record`, which knows which attributes each name carries and tells nothing for a name not its own, as scrapes' `trail.Record`.
- **Events as the pass's starter**, as scrapes' run events: a pass's end is told from the background or by the next start, where the starting request is gone, so the record keeps its request id and user (`D04-store`). The cause is the context's, which the work keeps from the starting call.
- The counts are integer attributes (an `int64` basic form); `reason` is present and empty on a `done` pass's `pass.finished`, as appkit's exact-keys rule requires.
- **`rescored` kept beside `judged`**, both carrying the pass's judged count, so a subscriber written against an earlier release keeps reading a value while it moves; a later release removes `rescored` from `pass.finished` and its declaration. The website check's release and the enrichers' release do not, because neither's decisions change the events beyond adding counts.
- **The website check's counts follow `derived`**: the website check's release appended them after `unranged`, and the enrichers' release inserts `derived` before them; each always present, as appkit's exact-keys rule requires and as the record carries them; their meaning is `D15-website-check`'s, not restated here.
- **`derived` is inserted after `unranged`, not appended** (enrichers decision 12): the website check appended its counts, but `derived` takes the place the record and the pass page give it, first among the enrich counts, so the record, the declarations and the event list one order. It is an addition only: no key is renamed or removed, and a subscriber reads attributes by key, so a key's position changes nothing it reads. Every pass carries it, 0 for an ingest or a judge.
- **A pass another pass started is told under its starter's request id and event cause, with no user**: the follow-on is the starter's doing, so a subscriber can trace an enrich back to the scrape that set it going, and no person is named who did not ask for it.
- **The judge trigger is accepted by exact name**, `cron.judge_candidates.fired`, not `cron.*.fired`: a pattern among `accepts` subscribes nothing, as scrapes found. Its trigger is the fixed slug `store.TriggerJudge` (`D04-store`), so a judge pass's `trigger` is that slug.
- The accepted names are declared as `trail.Accepted` and `trail.AcceptedJudge` beside the emitted ones, so the declarations and the handlers name them from one place.
- The body `/declarations` answers is stated here because its content is this document's declarations; the route and its place outside the identity gate are `D03-serve`'s.

## Consumer tasks

The engine (`D06-passes`), once `store.AddPass` has returned a pass `p`, calls `trail.Record(ctx, w, em, trail.Started, p)`, and once `store.FinishPass` or `store.FailPass` has returned it ended, `trail.Record(ctx, w, em, trail.Finished, p)`; its `Handlers()` answers `events.Handlers{trail.Accepted: e.Deliver, trail.AcceptedJudge: e.Deliver}`. `cli.Run` builds its emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`; `D03-serve` answers `/declarations` with `events.DeclarationsHandler(em, eng.Handlers())`. A test builds a writer over a `*telemetry.Capture` and an emitter over an `*events.Capture` with `trail.Emits()`, calls `trail.Record` with a `store.Pass` under a context carrying another caller and an `events.Cause`, flushes both, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`; it serves `events.DeclarationsHandler(em, eng.Handlers())` with `httptest` to read the declarations; and it drives `cli.Run` with captures and a fake scrapes, makes a `rebuild` call with the `mcp.Client`, posts a delivery of `scrape.finished` and one of `cron.judge_candidates.fired` to `/events`, each with an `X-Request-Id` of its own, and compares the pass events of each. It makes an `enrich` call, with `HTTP` left nil (only the derived kinds walked) and with `HTTP` a client over an injected RoundTripper, and compares that pass's events, `derived` included, with the record a `pass` call answers; and it follows a delivered `scrape.finished` to the enrich its ingest starts, whatever `HTTP` is, and the judge that enrich starts once it has recorded a result, comparing each follow-on's events with its starter's.
