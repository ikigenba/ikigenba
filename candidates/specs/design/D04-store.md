# D04-store

The records: `internal/store`, which owns candidates' eight tables in its SQLite database, `state/candidates.db`, and every read and write of them (decision 16): `candidates`, one row per candidate business, never deleted (decision 4); `links`, one row per scrapes row attached to a candidate, addressed by its source key (decision 6); `estimates`, one per source per candidate; `assessments`, one per candidate (decision 8); `decisions`, the owner's rulings (decision 10); `passes`, one row per pass until the prune removes it (decision 11); `zip_drive`, the ZIP drive-time table, replaced whole at every start (decision 9); and `candidate_cargo`, one row per cargo tag of each candidate, kept beside the candidate's cargo so the shortlist's cargo filter is a lookup. This document declares the store's whole public surface: its records, the words they are spelled with, every method with its signature, the errors every consumer tells apart and the one line every consumer answers when the database cannot be reached. It states what the pass records, the ZIP table, the reads and their windows, the schema's eighth migration, the prune and `db status` do. What a row does to the candidates and links when it is attached, what a gone run does, and what each ruling does (`Attach`, `MarkGone`, `Decide`) are `D12-resolution`'s; what a re-score and a refresh write and which candidates the shortlist holds in which order (`Rescore`, `RescoreAll`, `RefreshShortlist`, the **shortlist**) are `D13-scoring`'s. Opening, migrating, transactions and the failure seam are appkit's `db`; `D01-layout-and-run-seam` resolves the path and declares the root package's `Migrations()`. It is scrapes' store in shape, with a pass in place of a run and the candidates, their evidence and the rulings beside it.

## One database, one writer

candidates is the only writer of its database, and the database is the only record of its candidates, links, estimates, assessments, rulings, passes and drive times; nothing else is kept on disk (decision 1). `store.New` builds a store over a handle and opens or creates nothing. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds; a test proves the records that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`) answers every call with `ErrUnreachable` and changes nothing. `Config.Now` is the clock every stamp is read from, and the moment a re-score or a refresh judges freshness at; `Config.Rand` is the source pass ids and candidate ids are drawn from. `Run` hands in `Process.Now` and `Process.Rand`, and the store has no default for either.

## By key

A pass costs in proportion to its rows, and the pages and the tools answer while it runs (orchestrator ruling, after a pass over the real FMCSA run of 16,706 rows never finished: every batch loaded, copied and compared the whole database under one lock). The store reaches every record the pass path needs by key through SQL, on decision 16's indexes: a link by its source key (the links' unique scraper and source id), the active candidates one of whose links holds a match key by the links' name key, state and ZIP, the oldest first, a candidate's links by the links' candidate, a candidate by its id, its estimates, assessment and rulings by its id, a ZIP's minutes by the ZIP. No write on the pass path reads a whole table, but for a rebuild's `RescoreAll`, which covers every active candidate by definition and so enumerates the active candidates once. An `Attach` touches its batch's rows and the candidates they attach to: an unchanged row costs the lookup of its link and the write of its run, last seen and gone; a candidate's display is re-derived from its own links once per batch for each candidate one of whose links the batch wrote, since a link's last seen and gone order the display (`D12-resolution`). `MarkGone` is one bounded statement per `MarkGone` call, over that call's scraper's links last seen in a run other than that call's run, after which it re-derives by key the display of each candidate whose link it marked, since gone orders the display, bounded by those candidates. `Rescore` reads and writes each candidate it is given by its id, reading the candidate's record, its own links and rulings, and the ZIP table's minutes for its display ZIP, and writing its estimates and assessment.

Every write is one write transaction of appkit's `db`, and the store holds no lock of its own across one: the only lock it keeps guards `Config.Rand`. A read goes through `db.Read`, which answers from what was last committed while a write transaction is open, since appkit's handle reads beside its one writer; so a page or a tool never waits for a batch, a re-score or a ruling. Calls racing still behave as one after another (R-GTSY-N29E, R-4YPM-MZ41), because every write goes through appkit's one writer. Which statements the store issues is not contract; that a read answers while a write is open is, and so is the time a pass over thousands of rows takes (`D06-passes`).

## The records

A **candidate** (`store.Candidate`) is one business: its id, `cand_` and 16 lowercase hexadecimal digits; its status, `active` or `merged`, with the id it was merged into; its display fields (name, every name, street, city, state, ZIP, county as `MN-115`, phone, email, people); its tags (class and cargo); and when it was created and last updated (decision 4). Which link the display fields come from and when they change is `D12-resolution`'s.

A **link** (`store.Link`) is one row's attachment to one candidate: the candidate, the source key (scraper and source id), the run the row was last seen in and its digest, the source's reading of the row as last seen (`sources.Reading`: the keys, the envelope's common fields, the tags, the filing date, the fleet test, the estimate and the exclusion signals), how it attached (`source_key`, `match_key` or `decision`) with its confidence, when it was first and last seen, and whether it is gone (decision 6). A source key is unique among links: a row attaches to one candidate at a time.

An **estimate** is one source's `sources.Estimate` for one candidate, at most one per source per candidate. An **assessment** (`store.Assessment`) is a candidate's one judgment against the fit test as the last re-score wrote it: the fleet test, the combined low, high and confidence, the newest filing date among its links not gone, the drive minutes from its display ZIP (nil when the table lacks it), its exclusions with their reasons and whether it is excluded, the score before freshness, the effective confidence, the score and its score key as the last re-score or refresh wrote them, the rules version and when it was scored (decisions 8 and 11). Freshness is judged at pass time: a re-score writes the effective confidence and the score at its own moment, and `RefreshShortlist`, which every pass ends with, whatever its ending, done, failed or interrupted, and the start runs before ready, rewrites them for every assessment at its moment (`D13-scoring`). A read shows what was last written and computes nothing, so a store read between two passes shows each assessment as of the last pass end, or as of its own re-score when one came later.

A **ruling** (`store.Ruling`) is one of the owner's decisions: its kind (`merge`, `split`, `not_same`, `exclude`, `include`), the candidate it names, the other candidate (the other side of a merge or a `not_same`, the new candidate of a split), the source keys a split moved, why, who (user id and email) and when (decision 10). Rulings are never changed or removed.

A **pass** (`store.Pass`) is one resolve and re-score. Its id is `pass_` and 16 lowercase hexadecimal digits. It keeps its **trigger**, the run id a delivery named or `rebuild`; its **status**, one of `running`, `done` and `failed`, and when failed one of three **reasons**, `scrapes`, `interrupted` and `store` (which failure is which is `D06-passes`'); **started** and **finished**, each UTC to the second; the nine counts, each 0 until the pass is done; its starter's user id and email; the request id it was started under; and, for a delivery, the bus event's id, the **delivery**, an internal column no tool or page shows: it is how a redelivered event is told from a new one (`D06-passes`).

Every id the store mints, a pass's or a candidate's, is its prefix and 8 bytes read from `Config.Rand`, written as 16 lowercase hexadecimal digits, drawn again when it is the id of a record of its kind the store holds.

## Passes

A pass has three writes. `AddPass` records it `running`, stamping started and minting the id. It is refused `ErrDelivered` when its delivery is one an existing pass carries, or when its trigger is a run id an existing pass names, whatever that pass's status; and otherwise `ErrBusy` while any pass is `running`, so one pass runs at a time (decision 11). `FinishPass` ends a `running` pass `done` with the nine counts its work gathered; `FailPass` ends a `running` pass `failed` with a reason and leaves everything the pass wrote in place, since every write is idempotent and the next pass or a rebuild repairs it (decision 11). Of two calls racing on the same pass one succeeds and the other is told it is no longer running (`ErrEnded`). Nothing moves a pass back.

The counts a pass finishes with are the sums of the `store.Counts` its writes answered: `Attach` answers `Rows`, `New`, `Changed`, `Unchanged`, `Created` and `Linked` for a batch; `MarkGone` answers `Gone`; `Rescore` and `RescoreAll` answer `Rescored` and `Unranged`. What each counts is the owning document's.

`GetPass` answers any pass, whoever started it. `ListPasses` is one window of the passes in pass order, newest first: those after a position, the started text and id of the last pass of the window before, at most `n`; `RunningPasses` every pass still `running`, which the start finishes `failed` with `interrupted` (`D06-passes`). `PrunePasses` removes, in one write, every `done` pass beyond the newest keep count of `done` passes and every `failed` pass beyond the newest keep count of `failed` passes; a `running` pass is neither counted nor removed (decision 16). A pruned pass is gone from every read, its delivery and trigger with it. Candidates, links, estimates, assessments and rulings are never pruned; the prune touches none of them. A re-score replaces a candidate's estimates and assessment (`D13-scoring`); a merge moves the merged candidate's links to the survivor, and the merged candidate otherwise keeps what it had at the merge: its display fields, tags, estimates and last assessment (`D12-resolution`).

## The ZIP table

`ReplaceZipDrive` replaces the whole table with the map it is given in one write; the start hands it the root package's `ZipDrive()`, so the table is always the release's (decision 9). `ZipMinutes` answers one ZIP's minutes. A re-score reads the table for each candidate's display ZIP (`D13-scoring`).

## Reads

`GetCandidate` answers any candidate, active or merged: a merged candidate's record carries its status and the id it was merged into. `Links`, `Estimates`, `GetAssessment` and `Rulings` answer what the store holds for one candidate; each tells an unknown candidate (`ErrNotFound`) from a known one with nothing to show, except `GetAssessment`, which answers `ErrNotFound` for a candidate not yet scored too. Links come not gone first, then newest filing first, so the freshest evidence leads; rulings newest first. `ListCandidates` is one window of the active candidates newest first, those after a position, the created text and id of the last candidate of the window before, at most `n`, optionally only those one of whose names contains a text, case-insensitively, those at a ZIP, or those one of whose links has a phone key (decision 14). `Shortlist` is one window of the shortlist under a filter, those after a position, the score key and candidate id of the last entry of the window before, at most `n`, each entry with its candidate and its assessment as stored; which candidates, in which order, with which numbers, is `D13-scoring`'s. Each window is filtered, ordered and cut by the database on an index (appkit's D25, the suite's Storage convention): a read holds at most the window it was asked for, and the tools and pages ask for one more than they show to learn whether more follow. The store knows nothing of tokens; the tools and pages encode and decode them with `appkit/paging` from the position fields an entry carries (`D10-tools`, `D08-pages`). All lists are never nil.

## Errors

`ErrNotFound`, `ErrBusy`, `ErrDelivered`, `ErrEnded` and `ErrInvalid` are answers about the records; `ErrInvalid` is `Decide`'s alone, a ruling that is malformed or one the records forbid (`D12-resolution`). Every other error satisfies `errors.Is(err, ErrUnreachable)`, and every consumer answers it with `Unreachable` (a tool's `unavailable`, a page's unavailable answer, a delivery's `Fail`, a pass failed `store`), never quoting the cause. A done context, a failing handle, a random source that fails and a write given a value no consumer sends all end there, the last changing nothing.

## `db status`

`candidates db status` writes what appkit's `db.Status` writes for `state/candidates.db` and the root package's `Migrations()`, and creates nothing.

## Recorded decisions

- **A store fails only through its handle's `SetFailing`**, the one way candidates' test discipline provokes a database failure (candidates/AGENTS.md); what a store answers once its handle is closed is not contract, since no test may close the store to make it fail.

- The schema is eight migrations: seven, one per table in decision 16's order, named as the scaffold's `AGENTS.md` names them, and an eighth that only expands them. `0001_candidates.sql`: `candidates` (`id` primary key, `status`, `merged_into`, `name`, `names` as a JSON array, `names_lower`, `street`, `city`, `state`, `zip`, `county`, `phone`, `email`, `people` as a JSON array, `class`, `cargo` as a JSON array, `created`, `updated`), indexed on `status` and `created`. `0002_links.sql`: `links` (`scraper`, `source_id`, `candidate`, `run`, `digest`, `name_key`, `state`, `zip`, `phone_key`, `domain_key`, `reading` as the reading's JSON, `reason`, `confidence`, `first_seen`, `last_seen`, `gone`), unique on `scraper` and `source_id`, indexed on `name_key`, `state` and `zip`, and on `candidate`. `0003_estimates.sql`: `estimates` (`candidate`, `source`, `low`, `high` nullable, `confidence`, `facts` as JSON, `filed`, `formula`), unique on `candidate` and `source`. `0004_assessments.sql`: `assessments` (`candidate` primary key, `fleet`, `low`, `high` nullable, `confidence`, `filed`, `minutes` nullable, `exclusions` as JSON, `excluded`, `base`, `rules`, `scored`), indexed on `base`, the stored score. `0005_decisions.sql`: `decisions` (`seq` integer primary key, `kind`, `candidate`, `other`, `keys` as a JSON array, `why`, `user_id`, `user_email`, `at`), indexed on `candidate` and on `other`. `0006_passes.sql`: `passes` (`id` primary key, `trigger`, `status`, `reason`, `started`, `finished`, the nine counts, `user_id`, `user_email`, `request_id`, `delivery`), indexed on `started`, unique on `delivery` where it is not empty. `0007_zip_drive.sql`: `zip_drive` (`zip` primary key, `minutes`). `0008_windows.sql` (R-YFY0-FLH1): `assessments` gains `effective`, `score` and `score_key`, nullable, and the index `assessments_score` on `score_key` descending and `candidate`; `candidate_cargo` (`candidate`, `cargo`, the pair its primary key, without rowid), indexed on `cargo` and `candidate`, filled from every candidate's `cargo` array; `links` gains the index `links_phone` on `phone_key`, a column it already has; `candidates` the index `candidates_window` on `status`, `created` and `id`; `passes` the index `passes_window` on `started` and `id`, and `passes_trigger` on `trigger`, for the redelivery check. Times are RFC 3339 UTC to the second; an empty time is one not set. SQL keywords used as column names (`trigger`, `rows`, `new`, `keys` and the like) are quoted. The first seven files' text is stated by no requirement, since a test proves the records through the store; the eighth's is, because it is the first migration to run on databases a release already filled, so its shape binds the previous release and the next, and its tests write its columns as the previous release would (R-4J1Y-2VBP, R-4K9U-GN2E). The sandbox check, which sets a pass to `running` by hand and seeds assessments with `sqlite3`, writes these columns.
- A link keeps the source's whole reading of its row as JSON beside the key columns matching reads, so a re-score and a merge need no read of scrapes and a rebuild rewrites both at once (decision 6, "matching runs against the links and never calls scrapes").
- Estimates are answered as `sources.Estimate`, the type a source makes them in; the store adds no type of its own for them, since the candidate is the argument of the read.
- One pass at a time is refused by `AddPass` itself, in its write, so a `rebuild` and a delivery racing cannot both record a pass; the delivery is a column of `passes`, not a table of its own, and is forgotten with its pass at the prune, long after the events app's retries end.
- A redelivery is told by the delivery and also by the trigger: a pass already naming the run is enough, so a second `scrape.finished` for one run, under another bus event, is skipped (decision 11).
- A failed pass keeps its counts at 0, as a failed scrapes run does; what it wrote stays in the candidates and links, which the next pass or a rebuild repairs.
- Every id is minted by the store, 8 bytes at a time, at most 8 attempts, as in scrapes; a pass id and a candidate id are never compared, since their prefixes differ.
- **Scores are written at pass time** (orchestrator decision, a departure from decision 8's freshness judged at query time, recorded in `D13-scoring`): `Shortlist` reads the stored `effective`, `score` and `score_key` and reads no clock, and the tools and pages show the stored numbers. Its range filter reads the stored `minutes`, which the re-score copied from `zip_drive`: the decisions document's "ZIP drive-time join stays in SQL" is read as the minutes reaching the assessment through the re-score path, the shortlist query joining no ZIP table (`D13-scoring`). Filtering on `effective > 0` and ordering by `score_key` in SQL needs the numbers stored; decay judged in SQL on every request is deferred unless a shortlist stale by one pass turns out to matter.
- A write given a value no consumer sends answers an error matching `ErrUnreachable` and changes nothing, as in scrapes; `ErrInvalid` is kept for the one write whose arguments come from a person, a ruling.
- **Keyed, never whole** (orchestrator ruling): the pass path reads and writes by key on decision 16's indexes, and no index is added for it (the indexes `0008_windows.sql` adds serve the three windows and the phone filter): the gone-marking's statement runs on the scraper prefix of the links' unique index and its display re-derivation on the links' candidate index, `RescoreAll` on the candidates' index on status, the match on the links' name key, state and ZIP joined to the candidates by id. Only the time bound of `D06-passes` and the read that answers while a write is open (R-SATC-3077) are required; the statements are the build's.
- **Ruling points 1 and 2 carry no requirement of their own** (orchestrator ruling): reads by key, work confined to a batch's rows and their candidates, and a bounded gone-marking cannot be observed by use, since a test never reads tables or counts statements; the cost requirements of `D06-passes` (R-UTW4-OJCI, R-UV41-2B37, R-UWBX-G2TW) are their proof, and the read during a write (R-SATC-3077) is ruling point 4's.
- **An unchanged row still re-derives its candidate's display once per batch**: a link's last seen orders the display (`D12-resolution`, the display link), so the touch an unchanged row makes can change which link shows, and R-GAAK-IQEA requires the display current after every `Attach`; the cost stays one re-derivation per candidate per batch, from that candidate's own links. This goes beyond the ruling's "one lookup and a touch of last seen", deliberately.
- **A read never waits for a write**: appkit's `db.Read` answers from the last commit while `db.Write` holds the writer, which a probe against appkit's released `db` showed (a read returned while a test held a write transaction open), and the store adds no lock of its own across a transaction. The store this replaces held one store-wide lock across every transaction, so a read waited behind a write that was itself waiting for the writer; a test holding a `Write` open while an `Attach` waits tells the two apart. A lock the store took only inside its own write transaction, after appkit's writer is won, would escape that test, and this limitation is accepted: use cannot observe when an `Attach` is inside its own transaction, and a lock held there blocks reads only for as long as the batch's own write transaction, which the time bound of `D06-passes` keeps short. Likewise the test cannot confirm that its waiting `Attach`, `Decide` and `Rescore` have begun waiting before it reads, since the design declares no hook that would tell it: a store lock held across a whole write call is caught only when a waiting call has taken it before the reads end, which the test makes likely, not certain, by starting the writes first and yielding between reads; this limitation is accepted too.
- `ListCandidates`' `phone` filter is matched on the links' phone keys, any link, gone or not, with the filter normalized by `sources.PhoneKey`: a phone is identity evidence, and a gone link still counts for identity (decision 6).
- **Windows by position, not offset** (appkit's D25): each list read takes the position of the last entry of the window before and a count `n`, as prompts' `Runs` does; a position is the sort key of the entry, the created text (`Created` as RFC 3339 UTC, which is how it is stored) and id for a candidate, the started text and id for a pass, the score key and candidate id for a shortlist entry, and an empty id asks for the first window. The tools and pages pass `n` one more than the window `paging.Window` read. An `n` below 1 is refused `ErrUnreachable`, as every value no consumer sends is in candidates' store, where prompts answers an empty window.
- **The order each window takes, and the plan that serves it**: candidates `status = 'active'`, `(created, id) < (?, ?)`, `ORDER BY created DESC, id DESC`, on `candidates_window`; passes `(started, id) < (?, ?)`, `ORDER BY started DESC, id DESC`, on `passes_window`; the shortlist driven from `assessments` and joined to `candidates` by id with a `CROSS JOIN` (`FROM assessments AS a CROSS JOIN candidates AS c ON c.id = a.candidate`), `ORDER BY score_key DESC, candidate ASC`, on `assessments_score`, whose own order is exactly that; the `CROSS JOIN` fixes the join order, since with merged candidates among the rows and no statistics SQLite 3.53.4 and 3.46.1 both drive a plain join from `candidates_window` or `candidates_created` on `status` and sort in a `USE TEMP B-TREE FOR ORDER BY`; the position written `score_key <= ? AND (score_key < ? OR candidate > ?)`, since the plain form `score_key < ? OR (score_key = ? AND candidate > ?)` scans the index from its top rather than seeking. `EXPLAIN QUERY PLAN` on SQLite 3.53.4, the version appkit's driver `modernc.org/sqlite` v1.59.0 embeds, over a database built from the eight migrations and seeded with 10,000 candidates, one in twenty of them merged, each with an assessment and two links, and 2,000 passes, both before and after `ANALYZE`: the candidates window, a `SEARCH c` on `candidates_window` in both cases, `(status=?)` for the first window and `(status=? AND (created,id)<(?,?))` after a position, with every filter, the phone filter probing each candidate's links in an `EXISTS` through `links_phone` (`phone_key=?`) or, on other statistics, through `links_candidate` (`candidate=?`), neither of which sorts; the passes window `SEARCH passes USING INDEX passes_window ((started,id)<(?,?))`, the first window `SCAN passes USING INDEX passes_window` (covering when the query selects only the indexed columns); the shortlist, with and without class and cargo, `SEARCH a USING INDEX assessments_score (score_key<?)` after a position and `SCAN a USING INDEX assessments_score` for the first window, then `SEARCH c USING INDEX sqlite_autoindex_candidates_1 (id=?)` and the cargo probe `SEARCH k EXISTS` on `candidate_cargo`'s primary key or `candidate_cargo_cargo`; and no `USE TEMP B-TREE FOR ORDER BY` in any. The evidence database must hold merged candidates, as the sandbox check's seed must (`D11-on-a-space`), since a store of active candidates alone hides the join-order hazard. The indexes carry `id` because a table whose primary key is text keeps its rows by rowid, so `candidates_created` and `passes_started`, ordered by rowid among equal times, cannot serve the id tie-break; those two are left in place, since `0008` only adds, and a later contract migration may drop them. **Each window is two fixed statements** (orchestrator decision D28): the first window and the window after a position are separate statements, exported from `internal/store` as `ShortlistFirst` and `ShortlistAfter`, `CandidatesFirst` and `CandidatesAfter`, and `StartedFirst` and `StartedAfter` for the passes (named for their order, since gate 5's `gosec` G101 flags a string constant whose name holds `pass` as a hardcoded credential), each with every value bound (as scrapes' rows window and prompts' `Runs` are), and each window method runs the first of its pair for an empty id and the second otherwise. The build of design `73bc4b9` folded both into one statement whose position clause read `(?='' OR score_key<? OR (score_key=? AND candidate>?))`, and its candidates and passes counterparts likewise: SQLite cannot take a disjunction guarded by a bound value as an index bound, so the sandbox check over 10,000 candidates and 2,000 passes found `SCAN a USING INDEX assessments_score` for a shortlist page after a position, `SCAN passes USING COVERING INDEX passes_window` for passes, and `SEARCH candidates USING INDEX candidates_window (status=?)` with the position outside the seek, every deep page walking its index from the start. The positioned forms are the shortlist's `WHERE <filters> AND score_key <= ? AND (score_key < ? OR candidate > ?) ORDER BY score_key DESC, candidate ASC LIMIT ?`, the leading `score_key <= ?` being the seek bound on `assessments_score(score_key DESC, candidate)` (a row value cannot carry the index's mixed directions, so the two-term form stays); the candidates' `WHERE status = 'active' AND <filters> AND (created, id) < (?, ?) ORDER BY created DESC, id DESC LIMIT ?`; and the passes' `WHERE (started, id) < (?, ?) ORDER BY started DESC, id DESC LIMIT ?`. The filters may stay guarded by their bound values (`?='' OR ...`), since none of them is an index bound; the filter-guarded cargo probe and phone probe plan as a correlated subquery on `candidate_cargo`'s primary key and on `links_phone`. A first window has no position to seek to, so the shortlist's and the passes' are a `SCAN` of their index in its own order, stopped by the `LIMIT`, and the candidates' a `SEARCH` on `status = ?`. Observed with the `sqlite3` CLI 3.46.1 over a database built from the eight migrations and seeded with 10,000 candidates (500 merged), an assessment each, 20,000 links and 2,000 passes, before and after `ANALYZE`, over the same schema empty, and through appkit's `db` (`Read` on a handle `db.Open` returned, SQLite 3.53.4) over the same seed, with these statements, every filter in place: `ShortlistAfter` `SEARCH a USING INDEX assessments_score (score_key<?)`, then `SEARCH c USING INDEX sqlite_autoindex_candidates_1 (id=?)` and the cargo probe `SEARCH k USING PRIMARY KEY (candidate=? AND cargo=?)`; `ShortlistFirst` the same with `SCAN a USING INDEX assessments_score` first; `CandidatesAfter` `SEARCH candidates USING INDEX candidates_window (status=? AND (created,id)<(?,?))` and the phone probe `SEARCH l USING INDEX links_phone (phone_key=?)`; `CandidatesFirst` the same with `(status=?)`; `StartedAfter` `SEARCH passes USING INDEX passes_window ((started,id)<(?,?))`; `StartedFirst` `SCAN passes USING INDEX passes_window`; no `USE TEMP B-TREE` in any. appkit's driver refuses a statement given fewer arguments than its parameters, so the requirements declare each statement's parameters in order. The plans are required of the six statements (R-4JNJ-VR0A, R-4NB9-128D, R-4PR1-SLPR), and each statement's rows are required to be its method's window (R-4H7R-47IW). That a window method runs its statement rather than another giving the same rows cannot be observed by use, since no test reads source or traces statements; this limitation is accepted, and the sandbox check's deep-page timings and plans cover it on the real binary.
- **The name filter compares Go's lowering, not SQL's.** `names_lower` is written as Go's `strings.ToLower` of the names joined by line feeds, and SQLite's `lower()` folds only ASCII, so the filter is lowered with `strings.ToLower` before it reaches SQL and found with `instr(names_lower, ?) > 0`, a plain substring test: no `LIKE`, so `%` and `_` need no escape, and no `LIKE` pattern-length limit (50,000 bytes by default) can fail a long filter. The brief's `names_lower LIKE '%' || lower(?) || '%'` with an escape would differ from the Go semantics on non-ASCII letters; this does not. The one difference from the Go semantics the store had is the line feed that joins the names: a filter holding a line feed matches no candidate, where it matched a name holding the same line feed before; no source writes one into a name.
- **What still reads whole tables.** The three windows and every read a page or a tool makes read by key or by window: `GetCandidate`, `Links`, `Estimates`, `GetAssessment`, `Rulings`, `GetPass` and `ZipMinutes` read one candidate's or one pass's rows by index. `RunningPasses` is no page's or tool's read: the start calls it once, and with no index on `status` it scans `passes`, whose size is the configured retention plus the passes recorded since the last sweep. What still reads a table whole is on the pass and ruling paths, out of this change's scope: `RescoreAll`, which covers every active candidate by definition, `RefreshShortlist`, which rewrites every assessment and re-derives `candidate_cargo` in bounded statements, and `Decide`, `PrunePasses` and `ReplaceZipDrive`, as they stand. The engine's redelivery check (`D06-passes`, R-YRFA-2BM8) does not list the passes: `FindDelivered` asks for one pass carrying the delivery's event id or naming its run, on `passes_delivery` and on `passes_trigger`, which `0008` adds. `passes_delivery` is partial (`WHERE delivery <> ''`, `0006`), so the delivery arm states `delivery <> ''` for SQLite to use it; and since two passes can match at once (one by delivery, another by run), the first in pass order is chosen with `ORDER BY started DESC, id DESC LIMIT 1`. Listing them would read a table whose size grows with the configured retention, which `CANDIDATES_KEEP_PASSES` accepts up to any count, plus every pass recorded since the last hourly sweep. With the guard, `EXPLAIN QUERY PLAN` on SQLite 3.46.1 shows the two arms as `SEARCH passes USING INDEX passes_delivery (delivery=?)` and `SEARCH passes USING INDEX passes_trigger (trigger=?)`, as a `MULTI-INDEX OR` when written as one `OR` and as two searches when written as a `UNION ALL`; either form works. The ordering sorts in a temporary B-tree over the matched rows only, at most one by delivery, which is unique, and the passes naming the run, which `AddPass` keeps to one. That a list or page read holds no more than its window cannot be observed by use, since a test never counts statements or reads tables (the tests of R-4H7R-47IW and the plan requirements run only the statements the store exports, never SQL of their own); it carries no requirement of its own, and the sandbox check measures it: memory over 100 page reads against 10,000 seeded candidates, page timings, and the plans of the three windows, which the requirements on the six window statements also prove; the `FindDelivered` and `RunningPasses` plans above are this document's evidence and not part of that check.
- **`candidate_cargo` follows `cargo`**: every write of a candidate's `cargo` replaces that candidate's `candidate_cargo` rows in the same transaction. Candidates are never deleted, and a merged candidate keeps its cargo and its rows; the shortlist answers active candidates only. `RefreshShortlist` also re-derives the whole table from every candidate's `cargo`, so a database the previous release wrote after `0008` had run, which never maintains the table, is repaired at the next start or pass end; that the shortlist's cargo filter follows `Cargo` is the observable (R-4GM5-BBUB, R-4J1Y-2VBP).
- **The previous release on `0008`'s schema.** `0008` adds only nullable columns, a table, and indexes, so the previous release runs on it: its store names every column it inserts and reads (`INSERT ... ON CONFLICT DO UPDATE SET` over its own columns), never touches `candidate_cargo`, and appkit's `db` opens a database recording a migration it was not given with a warning and applies nothing. A row its re-score inserts has `effective`, `score` and `score_key` NULL, and a row it updates keeps the three as this release last wrote them; this release reads a NULL as 0, so such a row is off the shortlist (its effective confidence is not above 0) and shows zero numbers until the next `RefreshShortlist`, which the start runs before ready, so a roll forward over a rollback serves no stale or NULL row once ready (`D03-serve`, R-4QDC-DHRV).

## Consumer tasks

The engine (`D06-passes`), `c` the caller, records a rebuild with `p, err := st.AddPass(ctx, store.Pass{Trigger: store.TriggerRebuild, UserID: c.UserID, UserEmail: c.Email, RequestID: c.RequestID})`, `store.ErrBusy` answering `busy`; a delivery with `st.AddPass(ctx, store.Pass{Trigger: run, UserID: user, RequestID: c.RequestID, Delivery: d.Event.ID})`, `store.ErrDelivered` answering `Skip` and `store.ErrBusy` `Fail`. The work hands each batch to `n, touched, err := st.Attach(ctx, run, rebuild, batch)`, then calls `st.MarkGone(ctx, scraper, run)` and `st.Rescore(ctx, ids)` (or `st.RescoreAll(ctx)` for a rebuild), adds the `store.Counts` they answer, calls `st.RefreshShortlist(ctx)`, and ends with `st.FinishPass(ctx, p.ID, total)`, or, its work failed or interrupted, or a delivery's pass recorded with no work (R-JU7T-NHB1), calls `st.RefreshShortlist(rctx)`, `rctx` the uncancelled context it records the ending with, and ends with `st.FailPass(ctx, p.ID, store.ReasonScrapes)` or its other reason. A delivery asks `_, err := st.FindDelivered(ctx, d.Event.ID, run)` before it reads scrapes, a nil error answering `Skip` and `store.ErrNotFound` going on. The start calls `st.ReplaceZipDrive(ctx, candidates.ZipDrive())`, then `st.RefreshShortlist(ctx)`, then `st.RunningPasses(ctx)`; the sweep `st.PrunePasses(ctx, s.KeepPasses)`.

A test of a window's plan, `d` the handle its store was built over, runs `d.Read(ctx, func(tx *sql.Tx) error { rows, err := tx.QueryContext(ctx, "EXPLAIN QUERY PLAN "+store.ShortlistAfter, int64(90), int64(1000000), "carrier", "general", int64(5), "x", 26); ... })` and reads each row's `id`, `parent`, `notused` and `detail`; and a test of a statement's rows runs `tx.QueryContext(ctx, store.StartedAfter, started, id, n)` the same way and compares the first column of each row with the `ID`s `st.ListPasses(ctx, started, id, n)` returns.

The tools and pages (`D10-tools`, `D08-pages`), `n` from `paging.Window`, call `rs, err := st.Shortlist(ctx, store.ShortlistFilter{MaxMinutes: scoring.DefaultMaxMinutes, MinRevenue: scoring.DefaultMinRevenue}, 0, "", n+1)` for a first window and `st.Shortlist(ctx, f, key, id, n+1)` after `paging.Token{Tool: "shortlist"}.Decode(page, &key, &id)`, the `n`th entry's `r.Assessment.ScoreKey` and `r.Candidate.ID` giving `next` when `n+1` came back and `r.Assessment.Effective` and `r.Assessment.Score` its numbers; `cs, err := st.ListCandidates(ctx, store.CandidateFilter{Name: "trucking"}, created, id, n+1)`, the `n`th candidate's `c.Created.UTC().Format(time.RFC3339)` and `c.ID` giving `next`; `ps, err := st.ListPasses(ctx, started, id, n+1)`, the `n`th pass's `p.Started.UTC().Format(time.RFC3339)` and `p.ID` giving `next`; the landing `st.Shortlist(ctx, defaults, 0, "", paging.DefaultLimit+1)` and `st.ListPasses(ctx, "", "", paging.DefaultLimit+1)`; and `st.GetCandidate`, `st.Links`, `st.Estimates`, `st.GetAssessment`, `st.Rulings` and `st.GetPass`; `decide` calls `r, cs, err := st.Decide(ctx, store.Ruling{Kind: store.KindMerge, Candidate: a, Other: b, Why: why, UserID: c.UserID, UserEmail: c.Email})`, `store.ErrNotFound` answering `not_found` and `store.ErrInvalid` `invalid`. Any error matching `store.ErrUnreachable` is answered with `store.Unreachable`. A test opens its own database with `db.Open` and the root package's `Migrations()`, builds `store.New(d, store.Config{Now: clock, Rand: rnd})`, replaces the ZIP table with `candidates.ZipDrive()`, attaches observations it builds from `sources.Reading` values, records, finishes and fails passes, pages each list window by window, flips `d.SetFailing(true)`, and reopens the path to prove what persists. A test of `0008` reads `fs.ReadFile(candidates.Migrations(), "0008_windows.sql")`; a test of the previous release's rows opens a database with a file system holding only the first seven files, writes rows with `d.Write` as that release would, opens it again with `candidates.Migrations()`, and calls `st.RefreshShortlist(ctx)`. A test of serving holds `d.Write(ctx, fn)` open, its `fn` waiting on a channel the test holds, starts `st.Attach(ctx, run, false, batch)`, `st.Decide(ctx, r)` and `st.Rescore(ctx, ids)` each in a goroutine of its own, and calls `st.GetCandidate`, `st.Links` and `st.Shortlist`, each called a fixed number of times, yielding between calls, and each answering before the test releases `fn`; were a read to wait for the write, the test would never release it and would fail at the package's timeout, so the test waits on no clock.
