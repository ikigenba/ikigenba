# D04-store

The records: `internal/store`, which owns candidates' eight tables in its SQLite database, `state/candidates.db`, and every read and write of them (decision 16): `candidates`, one row per candidate business, never deleted (decision 4); `links`, one row per scrapes row attached to a candidate, addressed by its source key (decision 6); `estimates`, one per source per candidate; `assessments`, one per candidate (decision 8); `decisions`, the owner's rulings (decision 10); `passes`, one row per pass until the prune removes it (decision 11); `zip_drive`, the ZIP drive-time table, replaced whole at every start (decision 9); and `candidate_cargo`, one row per cargo tag of each candidate, kept beside the candidate's cargo so the shortlist's cargo filter is a lookup. This document declares the store's whole public surface: its records, the words they are spelled with, every method with its signature, the errors every consumer tells apart and the one line every consumer answers when the database cannot be reached. It states what the pass records, the ZIP table, the reads and their windows, the schema's eighth and ninth migrations, the prune and `db status` do. What a row does to the candidates and links when it is attached, what a gone run does, and what each ruling does (`Attach`, `MarkGone`, `Decide`) are `D12-resolution`'s; what a judge writes and which candidates the shortlist holds in which order (`Judge`, `JudgeAll`, the **shortlist**) are `D13-scoring`'s; which pass calls which write is `D06-passes`'. Opening, migrating, transactions and the failure seam are appkit's `db`; `D01-layout-and-run-seam` resolves the path and declares the root package's `Migrations()`. It is scrapes' store in shape, with a pass in place of a run and the candidates, their evidence and the rulings beside it.

Decisions cited by number are the decisions document that delivered candidates; "judgments decision N" is decision N of the later one, *two judgments and the PPP reader*, which splits each candidate's one score into two judgments and splits storing rows from judging them.

## One database, one writer

candidates is the only writer of its database, and the database is the only record of its candidates, links, estimates, assessments, rulings, passes and drive times; nothing else is kept on disk (decision 1). `store.New` builds a store over a handle and opens or creates nothing. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds; a test proves the records that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`) answers every call with `ErrUnreachable` and changes nothing. `Config.Now` is the clock every stamp is read from, and the moment a judge measures freshness at; `Config.Rand` is the source pass ids and candidate ids are drawn from. `Run` hands in `Process.Now` and `Process.Rand`, and the store has no default for either.

## By key

A pass costs in proportion to its rows, and the pages and the tools answer while it runs (orchestrator ruling, after a pass over the real FMCSA run of 16,706 rows never finished: every batch loaded, copied and compared the whole database under one lock). The store reaches every record the pass path needs by key through SQL, on decision 16's indexes: a link by its source key (the links' unique scraper and source id), the active candidates one of whose links holds a match key by the links' name key, state and ZIP, the oldest first, a candidate's links by the links' candidate, a candidate by its id, its estimates, assessment and rulings by its id, a ZIP's minutes by the ZIP. No write on the pass path reads a whole table, but `JudgeAll`, which a judge pass and a rebuild run and which covers every active candidate by definition, and so enumerates the active candidates once. An `Attach` touches its batch's rows and the candidates they attach to: an unchanged row costs the lookup of its link and the write of its run, last seen and gone; a candidate's display is re-derived from its own links once per batch for each candidate one of whose links the batch wrote, since a link's last seen and gone order the display (`D12-resolution`). `MarkGone` is one bounded statement per `MarkGone` call, over that call's scraper's links last seen in a run other than that call's run, after which it re-derives by key the display of each candidate whose link it marked, since gone orders the display, bounded by those candidates. `Judge` reads and writes each candidate it is given by its id, reading the candidate's record, its own links and rulings, and the ZIP table's minutes for its display ZIP, and writing its estimates and assessment. An ingest judges nothing, so its cost is its rows alone (judgments decision 23). A ruling works the same way, touching only the candidates it names, each by key (its record, its own links, its rulings and the ZIP table's minutes for its display ZIP), so its cost is bounded by those candidates' links: a `not_same` judges none and re-derives nothing; an `exclude` or `include` judges `r.Candidate`; a merge or a split re-derives the display of, and judges, the candidates it touches (`r.Candidate` and `r.Other`, or `r.Candidate` and the split's new candidate). It reads no table whole and refreshes no other candidate (`D12-resolution`).

Every write is one write transaction of appkit's `db`, and the store holds no lock of its own across one: the only lock it keeps guards `Config.Rand`. A read goes through `db.Read`, which answers from what was last committed while a write transaction is open, since appkit's handle reads beside its one writer; so a page or a tool never waits for a batch, a judge or a ruling. Calls racing still behave as one after another (`D12-resolution`, R-4YPM-MZ41), because every write goes through appkit's one writer. Which statements the store issues is not contract; that a read answers while a write is open is, and so is the time a pass over thousands of rows takes (`D06-passes`).

## The records

A **candidate** (`store.Candidate`) is one business: its id, `cand_` and 16 lowercase hexadecimal digits; its status, `active` or `merged`, with the id it was merged into; its display fields (name, every name, street, city, state, ZIP, county as `MN-115`, phone, email, people); its tags (class and cargo); and when it was created and last updated (decision 4). Which link the display fields come from and when they change is `D12-resolution`'s.

A **link** (`store.Link`) is one row's attachment to one candidate: the candidate, the source key (scraper and source id), the run the row was last seen in and its digest, the source's reading of the row as last seen (`sources.Reading`: the keys, the envelope's common fields, the tags, the filing date, the fleet test, the estimate, the operating evidence, the date the row shows the business existing since, the category and the government name match), how it attached (`source_key`, `match_key` or `decision`) with its confidence, when it was first and last seen, and whether it is gone (decision 6). A source key is unique among links: a row attaches to one candidate at a time.

An **estimate** is one source's `sources.Estimate` for one candidate, at most one per source per candidate. An **assessment** (`store.Assessment`) is a candidate's two judgments as the last judge wrote them (judgments decision 1): its **operating confidence**, how sure we are that it is a business operating today, with the **operating evidence** behind it, and its **revenue estimate**, a low, a high and a confidence. Beside them it keeps the facts the cohort filters will read: the date the business is known since, the government name pattern its name matched, the newest filing among its links not gone, its categories each with its source, the fleet test, the drive minutes from its display ZIP (nil when the table lacks it), whether the owner's standing ruling excludes it, the rules version and when it was calculated. Its **operating key** is the operating confidence scaled by a million and rounded to an integer, -1 when it has none: the shortlist's order and its windows' position (`D13-scoring`). A judgment the evidence does not support is empty, never 0 (judgments decision 2). What a judge computes is `D13-scoring`'s; judgments are written only by a judge: a judge pass, a rebuild, or a ruling re-judging the candidates it touches and no other (`JudgeAll`, `Judge`, `Decide`). An ingest stores links and writes no judgment. A read shows what was last written and computes nothing, so a store read between two judges shows each assessment as the last judge wrote it; nothing decays between judges (judgments decision 6).

A **ruling** (`store.Ruling`) is one of the owner's decisions: its kind (`merge`, `split`, `not_same`, `exclude`, `include`), the candidate it names, the other candidate (the other side of a merge or a `not_same`, the new candidate of a split), the source keys a split moved, why, who (user id and email) and when (decision 10). Rulings are never changed or removed.

A **pass** (`store.Pass`) is one ingest, one judge or one rebuild. Its id is `pass_` and 16 lowercase hexadecimal digits. It keeps its **kind**, what it does: `ingest` stores one run's rows as links and marks the vanished ones gone, `judge` judges every active candidate, and `rebuild` ingests every source's current run and then judges; its **origin**, what started it: `run`, a `scrape.finished` delivery, `cron`, a delivery of the daily trigger's event, or `rebuild`, the `rebuild` tool; its **trigger**, the run id an ingest's delivery named, the trigger's slug `judge_candidates` for a judge, or `rebuild` (judgments decision 25); its **status**, one of `running`, `done` and `failed`, and when failed one of three **reasons**, `scrapes`, `interrupted` and `store` (which failure is which is `D06-passes`'); **started** and **finished**, each UTC to the second; the nine counts, each 0 until the pass is done; its starter's user id and email; the request id it was started under; and, for a delivery, the bus event's id, the **delivery**, an internal column no tool or page shows: it is how a redelivered event is told from a new one (`D06-passes`).

Every id the store mints, a pass's or a candidate's, is its prefix and 8 bytes read from `Config.Rand`, written as 16 lowercase hexadecimal digits, drawn again when it is the id of a record of its kind the store holds.

## Passes

A pass has three writes. `AddPass` records it `running`, stamping started and minting the id. It is refused `ErrDelivered` when its delivery is one an existing pass carries, or when its origin is `run` and its trigger is the run id an existing pass of origin `run` names, whatever that pass's status; and otherwise `ErrBusy` while any pass is `running`, so one pass runs at a time (decision 11). A judge's trigger is the same slug every day, so the trigger refuses only run ids, and a redelivered trigger event is told by its delivery alone. `FinishPass` ends a `running` pass `done` with the nine counts its work gathered; `FailPass` ends a `running` pass `failed` with a reason and leaves everything the pass wrote in place, since every write is idempotent and the next pass or a rebuild repairs it (decision 11). Of two calls racing on the same pass one succeeds and the other is told it is no longer running (`ErrEnded`). Nothing moves a pass back.

The counts a pass finishes with are the sums of the `store.Counts` its writes answered: `Attach` answers `Rows`, `New`, `Changed`, `Unchanged`, `Created` and `Linked` for a batch; `MarkGone` answers `Gone`; `Judge` and `JudgeAll` answer `Judged` and `Unranged`. So an ingest finishes with `Judged` and `Unranged` 0 and a judge with only those two. What each counts is the owning document's.

`GetPass` answers any pass, whoever started it. `ListPasses` is one window of the passes in pass order, newest first: those after a position, the started text and id of the last pass of the window before, at most `n`; `RunningPasses` every pass still `running`, which the start finishes `failed` with `interrupted` (`D06-passes`). `PrunePasses` removes, in one write, every `done` pass beyond the newest keep count of `done` passes and every `failed` pass beyond the newest keep count of `failed` passes; a `running` pass is neither counted nor removed (decision 16). A pruned pass is gone from every read, its delivery and trigger with it. Candidates, links, estimates, assessments and rulings are never pruned; the prune touches none of them. A judge replaces a candidate's estimates and assessment (`D13-scoring`); a merge moves the merged candidate's links to the survivor, and the merged candidate otherwise keeps what it had at the merge: its display fields, tags, estimates and last assessment (`D12-resolution`).

## The ZIP table

`ReplaceZipDrive` replaces the whole table with the map it is given in one write; the start hands it the root package's `ZipDrive()`, so the table is always the release's (decision 9). `ZipMinutes` answers one ZIP's minutes. A judge reads the table for each candidate's display ZIP (`D13-scoring`).

## Reads

`GetCandidate` answers any candidate, active or merged: a merged candidate's record carries its status and the id it was merged into. `Links`, `Estimates`, `GetAssessment` and `Rulings` answer what the store holds for one candidate; each tells an unknown candidate (`ErrNotFound`) from a known one with nothing to show, except `GetAssessment`, which answers `ErrNotFound` for a candidate not yet judged too. Links come not gone first, then newest filing first, so the freshest evidence leads; rulings newest first. `ListCandidates` is one window of the active candidates newest first, those after a position, the created text and id of the last candidate of the window before, at most `n`, optionally only those one of whose names contains a text, case-insensitively, those at a ZIP, or those one of whose links has a phone key (decision 14). `Shortlist` is one window of the shortlist under a filter, those after a position, the operating key and candidate id of the last entry of the window before, at most `n`, each entry with its candidate and its assessment as stored; which candidates, in which order, with which numbers, is `D13-scoring`'s. A filter field left nil or empty is a filter not passed, so the zero `ShortlistFilter` is no filter at all. `ShortlistOffset` counts the entries of the shortlist under a filter that do not follow a position, the position's own entry included, which is the number of entries the windows before the one after that position hold; the landing ranks a later window's rows from it (`D08-pages`). Beside `Shortlist` and `ListPasses` sit their reversed windows, which the landing's backward step and its last window read (`D08-pages`): `ShortlistReversed` answers at most `n` of the entries of the shortlist under a filter that precede a position, nearest first, that is in the reverse of the shortlist's order, and `ListPassesReversed` likewise for the passes in pass order; an empty id there means the end of the order, so the reversed window from no position is the lowest-ranked entries, or the oldest passes, last first. The position need not be any entry's. The tools never call them. Each window is filtered, ordered and cut by the database on an index (appkit's D25, the suite's Storage convention): a read holds at most the window it was asked for, and the tools and pages ask for one more than they show to learn whether more follow. The store knows nothing of tokens; the tools and pages encode and decode them with `appkit/paging` from the position fields an entry carries (`D10-tools`, `D08-pages`). All lists are never nil.

## Errors

`ErrNotFound`, `ErrBusy`, `ErrDelivered`, `ErrEnded` and `ErrInvalid` are answers about the records; `ErrInvalid` is `Decide`'s alone, a ruling that is malformed or one the records forbid (`D12-resolution`). Every other error satisfies `errors.Is(err, ErrUnreachable)`, and every consumer answers it with `Unreachable` (a tool's `unavailable`, a page's unavailable answer, a delivery's `Fail`, a pass failed `store`), never quoting the cause. A done context, a failing handle, a random source that fails and a write given a value no consumer sends all end there, the last changing nothing.

## `db status`

`candidates db status` writes what appkit's `db.Status` writes for `state/candidates.db` and the root package's `Migrations()`, and creates nothing.

## Recorded decisions

- **A store fails only through its handle's `SetFailing`**, the one way candidates' test discipline provokes a database failure (candidates/AGENTS.md); what a store answers once its handle is closed is not contract, since no test may close the store to make it fail.

- The schema is nine migrations: seven, one per table in decision 16's order, named as the scaffold's `AGENTS.md` names them, an eighth that only expands them, and a ninth that recreates `assessments` for the two judgments and gives passes a kind and an origin. `0001_candidates.sql`: `candidates` (`id` primary key, `status`, `merged_into`, `name`, `names` as a JSON array, `names_lower`, `street`, `city`, `state`, `zip`, `county`, `phone`, `email`, `people` as a JSON array, `class`, `cargo` as a JSON array, `created`, `updated`), indexed on `status` and `created`. `0002_links.sql`: `links` (`scraper`, `source_id`, `candidate`, `run`, `digest`, `name_key`, `state`, `zip`, `phone_key`, `domain_key`, `reading` as the reading's JSON, `reason`, `confidence`, `first_seen`, `last_seen`, `gone`), unique on `scraper` and `source_id`, indexed on `name_key`, `state` and `zip`, and on `candidate`. `0003_estimates.sql`: `estimates` (`candidate`, `source`, `low`, `high` nullable, `confidence`, `facts` as JSON, `filed`, `formula`), unique on `candidate` and `source`. `0004_assessments.sql`: `assessments` (`candidate` primary key, `fleet`, `low`, `high` nullable, `confidence`, `filed`, `minutes` nullable, `exclusions` as JSON, `excluded`, `base`, `rules`, `scored`), indexed on `base`, the stored score. `0005_decisions.sql`: `decisions` (`seq` integer primary key, `kind`, `candidate`, `other`, `keys` as a JSON array, `why`, `user_id`, `user_email`, `at`), indexed on `candidate` and on `other`. `0006_passes.sql`: `passes` (`id` primary key, `trigger`, `status`, `reason`, `started`, `finished`, the nine counts, `user_id`, `user_email`, `request_id`, `delivery`), indexed on `started`, unique on `delivery` where it is not empty. `0007_zip_drive.sql`: `zip_drive` (`zip` primary key, `minutes`). `0008_windows.sql` (R-YFY0-FLH1): `assessments` gains `effective`, `score` and `score_key`, nullable, and the index `assessments_score` on `score_key` descending and `candidate`; `candidate_cargo` (`candidate`, `cargo`, the pair its primary key, without rowid), indexed on `cargo` and `candidate`, filled from every candidate's `cargo` array; `links` gains the index `links_phone` on `phone_key`, a column it already has; `candidates` the index `candidates_window` on `status`, `created` and `id`; `passes` the index `passes_window` on `started` and `id`, and `passes_trigger` on `trigger`, for the redelivery check. `0009_judgments.sql` (R-35WR-U8HP): `assessments` recreated with every column it had, `confidence` and `base` now nullable and `low`, `filed` and `exclusions` given defaults, since this release stops writing them, beside the new `operating`, `operating_key` (not null, default -1), `evidence` as JSON, `revenue_low`, `revenue_high`, `revenue_confidence`, `known_since`, `government_match`, `newest_filing` and `categories` as JSON, all nullable but the key; the old rows dropped with the old table; `assessments_base` and `assessments_score` recreated on the new table, and `assessments_operating` added on `operating_key` descending and `candidate`; `passes` gains `kind` and `origin`, defaulting to `ingest` and `run`, and every pass whose trigger is `rebuild` is set to `rebuild` and `rebuild`. This release writes `fleet`, `minutes`, `excluded`, `rules`, `scored` (which holds `Calculated`) and every new column, and none of the old score columns; the passes' `rescored` column holds `Judged`. Both keep their names so the previous release still finds them. `passes_trigger` stays non-unique: the uniqueness of a run id among ingest passes is `AddPass`'s. Times are RFC 3339 UTC to the second; an empty time is one not set. SQL keywords used as column names (`trigger`, `rows`, `new`, `keys` and the like) are quoted. The first seven files' text is stated by no requirement, since a test proves the records through the store; the eighth's and the ninth's are, because they run on databases a release already filled, so their shape binds the previous release and the next, and the tests of the ninth write rows as the previous release would (R-5YW6-HWFH, R-38CK-LRZ3). The sandbox check, which sets a pass to `running` by hand and seeds assessments with `sqlite3`, writes these columns.
- **`0009` departs from expand then contract** (orchestrator decision 2; the root `AGENTS.md` asks that the release before the current one run on the current one's schema). It keeps every column the previous release names, so that release's inserts and updates still succeed: its store names every column it writes, `operating_key` takes its default -1, and appkit's `db` opens a database recording a migration it was not given with a warning and applies nothing. But `confidence` and `base` become nullable and this release leaves them NULL, as it leaves every old score column; the previous release reads both as numbers, so its read of an assessment this release wrote fails, and a pass it records takes kind `ingest` and origin `run` whatever it is. A rollback is therefore not supported short of a rebuild on the previous release's own terms. Giving `confidence` and `base` `DEFAULT 0` instead would let the previous release read every row, as zero numbers off its shortlist; the orchestrator chose NULL, since nothing unknown is stored as 0 (judgments decision 2), and the departure stands. Old assessments are discarded, not copied: the rules change this release makes needs a rebuild, which rewrites every one (judgments decisions 27 and 28), and the dropped rows hold nothing it cannot remake. Rolling forward over a rollback works: an assessment row the previous release inserted reads as an assessment holding no judgment, its key -1, until the next judge (R-38CK-LRZ3). The next release contracts, dropping the old score columns and `assessments_base` and `assessments_score`. `shape/` has no entry on migrations, so this departs from no `shape/` convention; it is recorded here against the root rule.
- A link keeps the source's whole reading of its row as JSON beside the key columns matching reads, so a judge and a merge need no read of scrapes and a rebuild rewrites both at once (decision 6, "matching runs against the links and never calls scrapes"). A link an earlier release stored holds a reading without the fields this release added; it reads with them empty, and a rebuild rewrites it.
- Estimates are answered as `sources.Estimate`, the type a source makes them in; the store adds no type of its own for them, since the candidate is the argument of the read.
- **Kind and origin are two fields** (orchestrator decision 5): a kind says what a pass does and an origin what started it, so a page can show both and a rebuild, one pass that ingests and judges, has kind and origin both `rebuild`. The pass kinds are spelled `KindIngest`, `KindJudge` and `KindRebuild` beside the ruling kinds, since a name holding `Pass` trips gate 5's `gosec` G101.
- One pass at a time is refused by `AddPass` itself, in its write, so a `rebuild` and a delivery racing cannot both record a pass; the delivery is a column of `passes`, not a table of its own, and is forgotten with its pass at the prune, long after the events app's retries end.
- A redelivery of `scrape.finished` is told by the delivery and also by the trigger: an ingest pass already naming the run is enough, so a second `scrape.finished` for one run, under another bus event, is skipped (decision 11). A judge's trigger is the same slug every day, so a judge pass is told by its delivery alone and the same trigger may stand on many passes (orchestrator decision 5).
- A failed pass keeps its counts at 0, as a failed scrapes run does; what it wrote stays in the candidates and links, which the next pass or a rebuild repairs.
- Every id is minted by the store, 8 bytes at a time, at most 8 attempts, as in scrapes; a pass id and a candidate id are never compared, since their prefixes differ.
- **Judgments are written by a judge** (judgments decisions 6 and 23 to 25): `Shortlist` reads the stored `operating_key`, `revenue_low` and `minutes` and reads no clock, and the tools and pages show the stored numbers, at most a day old since the daily judge rewrites them. Nothing rewrites a judgment in SQL: the refresh that re-applied the freshness math to every stored score at every pass end and at the start is gone with its test, so the formulas live once, in Go (`D13-scoring`). The range filter reads the stored `minutes`, which the judge copied from `zip_drive`, the shortlist query joining no ZIP table.
- **The order is an integer key.** Operating confidence is a float, and appkit's `paging` token carries only `int64` and string values, so the store keeps `operating_key`, the confidence times 1,000,000 rounded to an integer, and -1 for none, so that an empty confidence sorts last in descending order (`D13-scoring` defines it). The operating confidence is stored and answered rounded to six decimal places and the key is derived from that rounded value, so the key is exact and two confidences share a key only when they are equal, ties falling to id order (orchestrator ruling, after the sandbox showed one 0.2 piece answering 0.19999999999999996; `D13-scoring`). The column is not null with default -1, so a row the previous release inserts sorts last and no keyset comparison meets a NULL.
- **A filter not passed is nil** (orchestrator decision 3, judgments decision 18): `ShortlistFilter`'s `MaxMinutes` and `MinRevenue` are pointers, the zero filter is no filter, and a candidate whose minutes or revenue low is unknown is left out only when that filter is passed. The statements take a nil as NULL and guard each numeric filter as `?1 IS NULL OR a.minutes<=?1`, `?2 IS NULL OR a.revenue_low>=?2`; the minimum revenue reads the revenue low.
- A write given a value no consumer sends answers an error matching `ErrUnreachable` and changes nothing, as in scrapes; `ErrInvalid` is kept for the one write whose arguments come from a person, a ruling.
- **Keyed, never whole** (orchestrator ruling): the pass path reads and writes by key on decision 16's indexes, and no index is added for it (the indexes `0008_windows.sql` and `0009_judgments.sql` add serve the three windows and the phone filter): the gone-marking's statement runs on the scraper prefix of the links' unique index and its display re-derivation on the links' candidate index, `JudgeAll` on the candidates' index on status, the match on the links' name key, state and ZIP joined to the candidates by id, and a ruling on the candidates' id, the links' candidate index and the rulings by candidate, for the candidates it touches alone. Only the time bound of `D06-passes` and the read that answers while a write is open (R-34OV-GGR0) are required; the statements are the build's.
- **Ruling points 1 and 2 carry no requirement of their own** (orchestrator ruling): reads by key, work confined to a batch's rows and their candidates, and a bounded gone-marking cannot be observed by use, since a test never reads tables or counts statements; the cost requirements of `D06-passes` (R-00FD-PO9J, R-01NA-3G08, R-02V6-H7QX) are their proof, and the read during a write (R-34OV-GGR0) is ruling point 4's.
- **An unchanged row still re-derives its candidate's display once per batch**: a link's last seen orders the display (`D12-resolution`, the display link), so the touch an unchanged row makes can change which link shows, and `D12-resolution` requires the display of every candidate an `Attach` returns current after it; the cost stays one re-derivation per candidate per batch, from that candidate's own links. This goes beyond the ruling's "one lookup and a touch of last seen", deliberately.
- **A read never waits for a write**: appkit's `db.Read` answers from the last commit while `db.Write` holds the writer, which a probe against appkit's released `db` showed (a read returned while a test held a write transaction open), and the store adds no lock of its own across a transaction. The store this replaces held one store-wide lock across every transaction, so a read waited behind a write that was itself waiting for the writer; a test holding a `Write` open while an `Attach` waits tells the two apart. A lock the store took only inside its own write transaction, after appkit's writer is won, would escape that test, and this limitation is accepted: use cannot observe when an `Attach` is inside its own transaction, and a lock held there blocks reads only for as long as the batch's own write transaction, which the time bound of `D06-passes` keeps short. Likewise the test cannot confirm that its waiting `Attach`, `Decide` and `Judge` have begun waiting before it reads, since the design declares no hook that would tell it: a store lock held across a whole write call is caught only when a waiting call has taken it before the reads end, which the test makes likely, not certain, by starting the writes first and yielding between reads; this limitation is accepted too.
- `ListCandidates`' `phone` filter is matched on the links' phone keys, any link, gone or not, with the filter normalized by `sources.PhoneKey`: a phone is identity evidence, and a gone link still counts for identity (decision 6).
- **Windows by position, not offset** (appkit's D25): each list read takes the position of the last entry of the window before and a count `n`, as prompts' `Runs` does; a position is the sort key of the entry, the created text (`Created` as RFC 3339 UTC, which is how it is stored) and id for a candidate, the started text and id for a pass, the operating key and candidate id for a shortlist entry, and an empty id asks for the first window. The tools and pages pass `n` one more than the window `paging.Window` read. An `n` below 1 is refused `ErrUnreachable`, as every value no consumer sends is in candidates' store, where prompts answers an empty window.
- **The order each window takes, and the plan that serves it**: candidates `status = 'active'`, `(created, id) < (?, ?)`, `ORDER BY created DESC, id DESC`, on `candidates_window`; passes `(started, id) < (?, ?)`, `ORDER BY started DESC, id DESC`, on `passes_window`; the shortlist driven from `assessments` and joined to `candidates` by id with a `CROSS JOIN` (`FROM assessments AS a CROSS JOIN candidates AS c ON c.id = a.candidate`), `ORDER BY operating_key DESC, candidate ASC`, on `assessments_operating`, whose own order is exactly that. The `CROSS JOIN` fixes the join order: when the order was `score_key` on `assessments_score`, with merged candidates among the rows and no statistics, SQLite 3.53.4 and 3.46.1 both drove a plain join from `candidates_window` or `candidates_created` on `status` and sorted in a `USE TEMP B-TREE FOR ORDER BY`. The position is written `operating_key <= ? AND (operating_key < ? - **The name filter compares Go's lowering, not SQL's.** `names_lower` is written as Go's `strings.ToLower` of the names joined by line feeds, and SQLite's `lower()` folds only ASCII, so the filter is lowered with `strings.ToLower` before it reaches SQL and found with `instr(names_lower, ?) > 0`, a plain substring test: no `LIKE`, so `%` and `_` need no escape, and no `LIKE` pattern-length limit (50,000 bytes by default) can fail a long filter. The brief's `names_lower LIKE '%' || lower(?) || '%'` with an escape would differ from the Go semantics on non-ASCII letters; this does not. - **What still reads whole tables.** The three windows and every read a page or a tool makes read by key or by window: `GetCandidate`, `Links`, `Estimates`, `GetAssessment`, `Rulings`, `GetPass` and `ZipMinutes` read one candidate's or one pass's rows by index. `RunningPasses` is no page's or tool's read: the start calls it once, and with no index on `status` it scans `passes`, whose size is the configured retention plus the passes recorded since the last sweep. - **`candidate_cargo` follows `cargo`**: every write of a candidate's `cargo` replaces that candidate's `candidate_cargo` rows in the same transaction. Candidates are never deleted, and a merged candidate keeps its cargo and its rows; the shortlist answers active candidates only. `JudgeAll` also re-derives the whole table from every candidate's `cargo` in its write, a defensive repair: the previous release maintains the table too, but a row any other writer leaves out of step (a hand edit, a sandbox seed) is put right at the next judge or rebuild; that the shortlist's cargo filter follows `Cargo` once a `JudgeAll` has returned is the observable (R-2L6H-C4VW, R-5YW6-HWFH).
