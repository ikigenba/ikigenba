# D04-store

The records: `internal/store`, which owns candidates' ten tables in its SQLite database, `state/candidates.db`, and every read and write of them (decision 16): `candidates`, one row per candidate business, never deleted (decision 4); `links`, one row per scrapes row attached to a candidate, addressed by its source key (decision 6); `estimates`, one per source per candidate; `assessments`, one per candidate (decision 8); `decisions`, the owner's rulings (decision 10); `passes`, one row per pass until the prune removes it (decision 11); `zip_drive`, the ZIP drive-time table, replaced whole at every start (decision 9); `candidate_cargo`, one row per cargo tag of each candidate, kept beside the candidate's cargo for the previous release, which reads it, though nothing in this one does (log 30); `cohorts`, one row per cohort until it is deleted (cohorts decision 23); and `rejects`, one row per reject or unreject record, never deleted (cohorts decisions 11 and 23). This document declares the store's whole public surface: its records, the words they are spelled with, every method with its signature, the errors every consumer tells apart and the one line every consumer answers when the database cannot be reached. It states what the pass records, the ZIP table, the reads and their windows, the cohort and reject writes and reads, the schema's eighth, ninth and tenth migrations, the prune and `db status` do. What a row does to the candidates and links when it is attached, what a gone run does, and what each ruling does (`Attach`, `MarkGone`, `Decide`) are `D12-resolution`'s; what a judge writes, the fleet verdict and its counts included (`Judge`, `JudgeAll`), is `D13-scoring`'s; what a cohort is, which validation set each `ValidCohort` function accepts, and which candidates a cohort's members and its matching count are, in which order, with which standing rejects, are `D14-cohorts`'; which pass calls which write is `D06-passes`'. Opening, migrating, transactions and the failure seam are appkit's `db`; `D01-layout-and-run-seam` resolves the path and declares the root package's `Migrations()`. It is scrapes' store in shape, with a pass in place of a run and the candidates, their evidence, the rulings and the cohorts beside it.

Decisions cited by number are the decisions document that delivered candidates; "judgments decision N" is decision N of the later one, *two judgments and the PPP reader*, which splits each candidate's one score into two judgments and splits storing rows from judging them; "cohorts decision N" is decision N of the latest, *cohorts*, which replaces the shortlist with the owner's cohorts, and "log N" is entry N of its decisions log.

## One database, one writer

candidates is the only writer of its database, and the database is the only record of its candidates, links, estimates, assessments, rulings, passes, cohorts, reject records and drive times; nothing else is kept on disk (decision 1). `store.New` builds a store over a handle and opens or creates nothing. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds; a test proves the records that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`) answers every call with `ErrUnreachable` and changes nothing. `Config.Now` is the clock every stamp is read from, the moment a judge measures freshness at, and the clock a cohort read measures filing age by (log 3); `Config.Rand` is the source pass ids, candidate ids and cohort ids are drawn from. `Run` hands in `Process.Now` and `Process.Rand`, and the store has no default for either.

## By key

A pass costs in proportion to its rows, and the pages and the tools answer while it runs (orchestrator ruling, after a pass over the real FMCSA run of 16,706 rows never finished: every batch loaded, copied and compared the whole database under one lock). The store reaches every record the pass path needs by key through SQL, on decision 16's indexes: a link by its source key (the links' unique scraper and source id), the active candidates one of whose links holds a match key by the links' name key, state and ZIP, the oldest first, a candidate's links by the links' candidate, a candidate by its id, its estimates, assessment and rulings by its id, a ZIP's minutes by the ZIP. No write on the pass path reads a whole table, but `JudgeAll`, which a judge pass and a rebuild run and which covers every active candidate by definition, and so enumerates the active candidates once. An `Attach` touches its batch's rows and the candidates they attach to: an unchanged row costs the lookup of its link and the write of its run, last seen and gone; a candidate's display is re-derived from its own links once per batch for each candidate one of whose links the batch wrote, since a link's last seen and gone order the display (`D12-resolution`). `MarkGone` is one bounded statement per `MarkGone` call, over that call's scraper's links last seen in a run other than that call's run, after which it re-derives by key the display of each candidate whose link it marked, since gone orders the display, bounded by those candidates. `Judge` reads and writes each candidate it is given by its id, reading the candidate's record, its own links and rulings, and the ZIP table's minutes for its display ZIP, and writing its estimates and assessment. An ingest judges nothing, so its cost is its rows alone (judgments decision 23). A ruling works the same way, touching only the candidates it names, each by key (its record, its own links, its rulings and the ZIP table's minutes for its display ZIP), so its cost is bounded by those candidates' links: a `not_same` judges none and re-derives nothing; an `exclude` or `include` judges `r.Candidate`; a merge or a split re-derives the display of, and judges, the candidates it touches (`r.Candidate` and `r.Other`, or `r.Candidate` and the split's new candidate). It reads no table whole and refreshes no other candidate (`D12-resolution`). A cohort write touches its one cohort row, and a reject or unreject its one pair's records, its cohort and its candidate, each by key. The upkeep the start and the sweep run touches only its own table (log 36, after candidates was killed at its start on the `us` space under `memory_max = 256M`, the two upkeep writes loading, copying and comparing every candidate, link, estimate, assessment and ruling of a database holding 43,000 candidates and 54,000 links): `ReplaceZipDrive` reads and writes `zip_drive` alone, and `PrunePasses` reads and deletes in `passes` alone, so the memory either takes does not grow with the candidates, links, estimates, assessments or rulings the store holds. No call of the store loads every record.

Every write is one write transaction of appkit's `db`, and the store holds no lock of its own across one: the only lock it keeps guards `Config.Rand`. A read goes through `db.Read`, which answers from what was last committed while a write transaction is open, since appkit's handle reads beside its one writer; so a page or a tool never waits for a batch, a judge, a ruling or a cohort write. Calls racing still behave as one after another (`D12-resolution`, R-4YPM-MZ41), because every write goes through appkit's one writer. Which statements the store issues is not contract; that a read answers while a write is open is, and so is the time a pass over thousands of rows takes (`D06-passes`).

## The records

A **candidate** (`store.Candidate`) is one business: its id, `cand_` and 16 lowercase hexadecimal digits; its status, `active` or `merged`, with the id it was merged into; its display fields (name, every name, street, city, state, ZIP, county as `MN-115`, phone, email, people); its tags (class and cargo); and when it was created and last updated (decision 4). Which link the display fields come from and when they change is `D12-resolution`'s.

A **link** (`store.Link`) is one row's attachment to one candidate: the candidate, the source key (scraper and source id), the run the row was last seen in and its digest, the source's reading of the row as last seen (`sources.Reading`: the keys, the envelope's common fields, the tags, the filing date, the fleet test and the row's fleet verdict and counts, the estimate, the operating evidence, the date the row shows the business existing since, the category and the government name match), how it attached (`source_key`, `match_key` or `decision`) with its confidence, when it was first and last seen, and whether it is gone (decision 6). A source key is unique among links: a row attaches to one candidate at a time.

An **estimate** is one source's `sources.Estimate` for one candidate, at most one per source per candidate. An **assessment** (`store.Assessment`) is a candidate's two judgments as the last judge wrote them (judgments decision 1): its **operating confidence**, how sure we are that it is a business operating today, with the **operating evidence** behind it, and its **revenue estimate**, a low, a high and a confidence. Beside them it keeps the facts the cohort filters read (`D14-cohorts`): the date the business is known since, the government name pattern its name matched, the newest filing among its links not gone, its categories each with its source, the **fleet verdict**, `pass`, `fail` or `unknown`, with the power units and drivers of the FMCSA link it was read from (cohorts decision 13, log 20), the drive minutes from its display ZIP (nil when the table lacks it), whether the owner's standing ruling excludes it, the rules version and when it was calculated. The verdict replaces the boolean fleet test in the Go type, the tools and the pages under one name, `fleet_verdict` (log 10); the store still writes the `fleet` column, true exactly when the verdict is `pass`, for the previous release (cohorts decision 14). Its **operating key** is the operating confidence scaled by a million and rounded to an integer, -1 when it has none: what a cohort's order compares operating confidence by (`D14-cohorts`, `D13-scoring`). A judgment the evidence does not support is empty, never 0 (judgments decision 2). What a judge computes is `D13-scoring`'s; judgments are written only by a judge: a judge pass, a rebuild, or a ruling re-judging the candidates it touches and no other (`JudgeAll`, `Judge`, `Decide`). An ingest stores links and writes no judgment. A read shows what was last written and computes nothing, so a store read between two judges shows each assessment as the last judge wrote it; nothing decays between judges (judgments decision 6).

A **ruling** (`store.Ruling`) is one of the owner's decisions: its kind (`merge`, `split`, `not_same`, `exclude`, `include`), the candidate it names, the other candidate (the other side of a merge or a `not_same`, the new candidate of a split), the source keys a split moved, why, who (user id and email) and when (decision 10). Rulings are never changed or removed. The `exclude` and `include` tools and `decide` all record theirs through `Decide`, unchanged (cohorts decision 12).

A **cohort** (`store.Cohort`) is one saved search: its id, `coh_` and 16 lowercase hexadecimal digits; its name, free text, not unique; its size; its filters (`store.CohortFilters`); its order (`[]store.CohortOrder`); who created it (user id and email) and when; and who last changed it and when, which creation sets to the creator and the creation time (cohorts decision 1, log 24). Its members are never stored: `ReadCohort` works them out at every read (cohorts decisions 3 and 25). The store keeps the filters and the order in their **normal form**, the categories de-duplicated and in byte order and an empty order as the default order, so an edit that changes nothing compares equal and writes nothing (log 8, log 16). An edit (`store.CohortEdit`) names the cohort and any of its name, size, filters and order, nil for each part it leaves alone; a passed filter set or order replaces the stored one whole, so `&CohortFilters{}` clears every filter and `&[]CohortOrder{}` sets the default order (cohorts decision 6, log 8). A delete removes the row; its reject records stay.

A **reject record** (`store.Reject`) is one reject or unreject: its kind (`reject` or `unreject`), the cohort and the candidate it names, why, who and when (cohorts decision 10). Records are never changed or removed, not at an unreject and not when their cohort is deleted (cohorts decision 11). Which record stands for a cohort and a candidate is `D14-cohorts`' **standing reject**. `CohortName` is filled on every read from the cohort the record names while that cohort exists, so it is empty once the cohort is deleted.

A **pass** (`store.Pass`) is one ingest, one judge or one rebuild. Its id is `pass_` and 16 lowercase hexadecimal digits. It keeps its **kind**, what it does: `ingest` stores one run's rows as links and marks the vanished ones gone, `judge` judges every active candidate, and `rebuild` ingests every source's current run and then judges; its **origin**, what started it: `run`, a `scrape.finished` delivery, `cron`, a delivery of the daily trigger's event, or `rebuild`, the `rebuild` tool; its **trigger**, the run id an ingest's delivery named, the trigger's slug `judge_candidates` for a judge, or `rebuild` (judgments decision 25); its **status**, one of `running`, `done` and `failed`, and when failed one of three **reasons**, `scrapes`, `interrupted` and `store` (which failure is which is `D06-passes`'); **started** and **finished**, each UTC to the second; the nine counts, each 0 until the pass is done; its starter's user id and email; the request id it was started under; and, for a delivery, the bus event's id, the **delivery**, an internal column no tool or page shows: it is how a redelivered event is told from a new one (`D06-passes`).

Every id the store mints, a pass's, a candidate's or a cohort's, is its prefix and 8 bytes read from `Config.Rand`, written as 16 lowercase hexadecimal digits, drawn again when it is the id of a record of its kind the store holds; a cohort id is drawn again also when a reject record names it, so a deleted cohort's id is never reused while its records stand (cohorts decision 1).

## Passes

A pass has three writes. `AddPass` records it `running`, stamping started and minting the id. It is refused `ErrDelivered` when its delivery is one an existing pass carries, or when its origin is `run` and its trigger is the run id an existing pass of origin `run` names, whatever that pass's status; and otherwise `ErrBusy` while any pass is `running`, so one pass runs at a time (decision 11). A judge's trigger is the same slug every day, so the trigger refuses only run ids, and a redelivered trigger event is told by its delivery alone. `FinishPass` ends a `running` pass `done` with the nine counts its work gathered; `FailPass` ends a `running` pass `failed` with a reason and leaves everything the pass wrote in place, since every write is idempotent and the next pass or a rebuild repairs it (decision 11). Of two calls racing on the same pass one succeeds and the other is told it is no longer running (`ErrEnded`). Nothing moves a pass back.

The counts a pass finishes with are the sums of the `store.Counts` its writes answered: `Attach` answers `Rows`, `New`, `Changed`, `Unchanged`, `Created` and `Linked` for a batch; `MarkGone` answers `Gone`; `Judge` and `JudgeAll` answer `Judged` and `Unranged`. So an ingest finishes with `Judged` and `Unranged` 0 and a judge with only those two. What each counts is the owning document's.

`GetPass` answers any pass, whoever started it. `ListPasses` is one window of the passes in pass order, newest first: those after a position, the started text and id of the last pass of the window before, at most `n`; `RunningPasses` every pass still `running`, which the start finishes `failed` with `interrupted` (`D06-passes`). `PrunePasses` removes, in one write, every `done` pass beyond the newest keep count of `done` passes and every `failed` pass beyond the newest keep count of `failed` passes; a `running` pass is neither counted nor removed (decision 16). A pruned pass is gone from every read, its delivery and trigger with it. Candidates, links, estimates, assessments, rulings, cohorts and reject records are never pruned; the prune touches none of them. A judge replaces a candidate's estimates and assessment (`D13-scoring`); a merge moves the merged candidate's links to the survivor, and the merged candidate otherwise keeps what it had at the merge: its display fields, tags, estimates, last assessment and reject records (`D12-resolution`).

## The ZIP table

`ReplaceZipDrive` replaces the whole table with the map it is given in one write; the start hands it the root package's `ZipDrive()`, so the table is always the release's (decision 9). `ZipMinutes` answers one ZIP's minutes. A judge reads the table for each candidate's display ZIP (`D13-scoring`).

## Cohorts

`CreateCohort` mints the id, stamps created and changed with the caller and the clock, and keeps the normal form of what it was given. `EditCohort` replaces each part the edit passes, and when the cohort that results is the one stored it writes nothing and keeps changed and its user as they were, so an empty edit or a repeated one is the same as none (log 8). `DeleteCohort` removes the cohort and answers it as it was; deleting it again is `ErrNotFound` (cohorts decision 7). `GetCohort` answers a definition without its members. Each write refuses a part a `ValidCohort` function refuses with `ErrInvalid` before it looks for the cohort, and an empty user id `ErrUnreachable`, as no consumer sends one (log 7). Creating twice makes two cohorts, as cohorts decision 18 accepts.

`ReadCohort` answers the definition, its **matching** count, its **members** in their order, each the candidate and its assessment as stored, and its standing rejects, newest first, each with the cohort's name, all as `D14-cohorts` defines them, at the clock `Config.Now()` gives once for the read (log 3). Membership is one query over the assessments joined to the candidates, cut by the size, beside one count (cohorts decision 25); the store holds no more than the members.

`ListCohorts` and `ListCohortsReversed` are the cohort windows the `cohorts` tool and the landing read, in **cohort order**, name then id, each in byte order (log 18), a window after a position or before it, as the passes' are.

`Reject` records a reject or an unreject. A reject of a pair that has no standing reject, or an unreject of one that has, records one record and answers it; a reject of a pair already rejected writes nothing and answers the record that stands; an unreject of a pair with no standing reject writes nothing and answers a record of kind `unreject` naming the cohort, the candidate and the cohort's name, with no why, user or time (log 27), so every reject and unreject is safe to repeat (cohorts decisions 10 and 18). It refuses a blank why `ErrInvalid`, a cohort the store does not hold, a deleted one included, `ErrNotFound`, then a candidate it does not hold `ErrNotFound`, then a merged candidate `ErrInvalid` (log 6). `Rejects` answers every record naming a candidate, active or merged, newest first (cohorts decision 11). A cohort's standing rejects are listed whatever the candidate's status (`D14-cohorts`), so a reject of a candidate that is later merged keeps standing on its cohort's read and cannot be cleared, since `Reject` refuses a merged candidate `ErrInvalid` either way; a merged candidate is no member of any cohort, so the row only shows.

## Reads

`GetCandidate` answers any candidate, active or merged: a merged candidate's record carries its status and the id it was merged into. `Links`, `Estimates`, `GetAssessment`, `Rulings` and `Rejects` answer what the store holds for one candidate; each tells an unknown candidate (`ErrNotFound`) from a known one with nothing to show, except `GetAssessment`, which answers `ErrNotFound` for a candidate not yet judged too. Links come not gone first, then newest filing first, so the freshest evidence leads; rulings and reject records newest first. `ListCandidates` is one window of the active candidates newest first, those after a position, the created text and id of the last candidate of the window before, at most `n`, optionally only those one of whose names contains a text, case-insensitively, those at a ZIP, or those one of whose links has a phone key (decision 14). Beside `ListPasses` and `ListCohorts` sit their reversed windows, which the landing's backward step and its last window read (`D08-pages`): `ListPassesReversed` answers at most `n` of the passes that precede a position in pass order, nearest first, and `ListCohortsReversed` likewise in cohort order; an empty id there means the end of the order, so the reversed window from no position is the oldest passes, or the cohorts last in order, last first. The position need not be any entry's. The tools never call them. Each window is ordered and cut by the database on an index (appkit's D25, the suite's Storage convention): a read holds at most the window it was asked for, and the tools and pages ask for one more than they show to learn whether more follow. The store knows nothing of tokens; the tools and pages encode and decode them with `appkit/paging` from the position fields an entry carries (`D10-tools`, `D08-pages`). All lists are never nil.

## Errors

`ErrNotFound`, `ErrBusy`, `ErrDelivered`, `ErrEnded` and `ErrInvalid` are answers about the records; `ErrInvalid` is the answer of the writes whose arguments come from a person: `Decide`'s, a ruling that is malformed or one the records forbid (`D12-resolution`), `CreateCohort`'s and `EditCohort`'s, a part a validator refuses, and `Reject`'s, a blank why or a merged candidate. Every other error satisfies `errors.Is(err, ErrUnreachable)`, and every consumer answers it with `Unreachable` (a tool's `unavailable`, a page's unavailable answer, a delivery's `Fail`, a pass failed `store`), never quoting the cause. A done context, a failing handle, a random source that fails and a write given a value no consumer sends all end there, the last changing nothing. No error variable is added for cohorts.

## `db status`

`candidates db status` writes what appkit's `db.Status` writes for `state/candidates.db` and the root package's `Migrations()`, and creates nothing.

- **`0010` is the contract `0009` promised, and an expand for the verdict** (cohorts decisions 14, 16 and 24). The previous release names none of the dropped columns in what it writes or reads (log 9), so it runs on the migrated database: its assessment upsert leaves `fleet_verdict` at its default, so a row it inserts reads `unknown` with no counts until the next judge (R-D7SX-NYM2), and a row it updates keeps the verdict this release wrote beside the `fleet` it wrote, which the next judge after a roll forward rewrites; it never reads `cohorts` or `rejects`. `fleet_verdict` is not null with a default rather than the nullable column the decisions document names (log 9): the store reads no NULL into a string, and the default is what an unwritten verdict means; it is never derived from `fleet`. The release before the previous one names `confidence` and `base` and does not run on `0010`, which the root rule does not ask. The next release drops `fleet` and may drop `low`, `high` and `candidate_cargo`. `0009` has run on `us` and is frozen; R-35WR-U8HP stands.
- **`0009` departs from expand then contract** (orchestrator decision 2; the root `AGENTS.md` asks that the release before the current one run on the current one's schema). It kept every column the release before it named, but made `confidence` and `base` nullable and left them NULL, so that release could not read an assessment `0009`'s release wrote; a rollback across `0009` was not supported short of a rebuild on that release's own terms, and the orchestrator chose NULL over `DEFAULT 0`, since nothing unknown is stored as 0 (judgments decision 2). Old assessments were discarded, not copied, since the rules change needed a rebuild. `shape/` has no entry on migrations, so this departs from no `shape/` convention; it is recorded here against the root rule. A database a release before `0009` filled still migrates through all ten files (R-D6L1-A6VD).
- A link keeps the source's whole reading of its row as JSON beside the key columns matching reads, so a judge and a merge need no read of scrapes and a rebuild rewrites both at once (decision 6, "matching runs against the links and never calls scrapes"). A link an earlier release stored holds a reading without the fields this release added, the fleet verdict and counts among them; it reads with them empty, and a rebuild rewrites it.
- Estimates are answered as `sources.Estimate`, the type a source makes them in; the store adds no type of its own for them, since the candidate is the argument of the read.
- **Kind and origin are two fields** (orchestrator decision 5): a kind says what a pass does and an origin what started it, so a page can show both and a rebuild, one pass that ingests and judges, has kind and origin both `rebuild`. The pass kinds are spelled `KindIngest`, `KindJudge` and `KindRebuild` beside the ruling kinds, since a name holding `Pass` trips gate 5's `gosec` G101; the reject kinds `KindReject` and `KindUnreject` sit beside them too.
- One pass at a time is refused by `AddPass` itself, in its write, so a `rebuild` and a delivery racing cannot both record a pass; the delivery is a column of `passes`, not a table of its own, and is forgotten with its pass at the prune, long after the events app's retries end.
- A redelivery of `scrape.finished` is told by the delivery and also by the trigger: an ingest pass already naming the run is enough, so a second `scrape.finished` for one run, under another bus event, is skipped (decision 11). A judge's trigger is the same slug every day, so a judge pass is told by its delivery alone and the same trigger may stand on many passes (orchestrator decision 5).
- A failed pass keeps its counts at 0, as a failed scrapes run does; what it wrote stays in the candidates and links, which the next pass or a rebuild repairs.
- Every id is minted by the store, 8 bytes at a time, at most 8 attempts, as in scrapes; a pass id, a candidate id and a cohort id are never compared, since their prefixes differ.
- **Judgments are written by a judge** (judgments decisions 6 and 23 to 25): `ReadCohort` reads the stored judgments and facts, `operating_key`, `revenue_low`, `minutes`, `fleet_verdict` and the rest, and reads the clock only for the filing age, so the tools and pages show the stored numbers, at most a day old since the daily judge rewrites them. Nothing rewrites a judgment in SQL: the formulas live once, in Go (`D13-scoring`). The drive-time filter reads the stored `minutes`, which the judge copied from `zip_drive`, so a cohort read joins no ZIP table.
- **The operating order is an integer key.** Operating confidence is a float, so the store keeps `operating_key`, the confidence times 1,000,000 rounded to an integer, and -1 for none (`D13-scoring` defines it). The operating confidence is stored and answered rounded to six decimal places and the key is derived from that rounded value, so the key is exact and two confidences share a key only when they are equal (orchestrator ruling, after the sandbox showed one 0.2 piece answering 0.19999999999999996; `D13-scoring`). The column is not null with default -1, so a row the previous release inserts reads as no confidence; a cohort's order puts an unknown last by the confidence being nil, not by the key (`D14-cohorts`), and the key stays the comparison among known ones.
- **A cohort keeps the normal form, and an edit compares it** (log 8, log 16): the filters and the order are stored as the JSON of the store's own types, `omitempty` on every filter member, so the zero filter set is `{}`, a `government` of false is kept and a nil one dropped, and the answer encodes the same type, so the stored text is the answered one. An empty categories list reads back as none, which `D14-cohorts` treats as the filter not carried. An edit builds the cohort that would result, in normal form, and writes only when its name, size, filters or order differ from the stored ones, so a repeated edit restamps nothing and `changed` says when the definition last changed. Create stamps changed as created, so every column is not null (log 24).
- **A deleted cohort is removed, not flagged** (cohorts decision 7): no column of log 16 is a deleted flag, the landing lists only cohorts that exist, and the candidate page shows a record's cohort as deleted by its missing name. Its reject records stay and keep its id, which minting never reuses.
- **One `Reject` method takes the kind**, as `Decide` takes a ruling's kind, since a reject and an unreject name the same three things and differ in what they record. `Decide` is unchanged and still takes `KindExclude` and `KindInclude`; that `decide` refuses them is the tool's (`D10-tools`).
- **The cohort store reads `Config.Now` itself** (log 3): a cohort read's filing-age date comes from the store's own clock, read once per `ReadCohort`, computed in Go and bound, never SQL's `now`, so the tool and the page answer on the day they are called and a test drives the date through the clock it hands in. A cohort read is one statement for the members, `LIMIT` the size, and one for the count (cohorts decision 25); which statements, and that the store holds no more than the members, cannot be observed by use, carry no requirement of their own, and are the build's.
- A write given a value no consumer sends answers an error matching `ErrUnreachable` and changes nothing, as in scrapes; `ErrInvalid` is kept for the writes whose arguments come from a person: a ruling, a cohort and a reject (log 7). The `ValidCohort` functions are exported so the tools refuse `invalid` before the store is read and the store refuses `ErrInvalid` by the same rule, which cannot disagree.
- **Keyed, never whole** (orchestrator ruling): the pass path reads and writes by key on decision 16's indexes, and no index is added for it (the indexes `0008_windows.sql`, `0009_judgments.sql` and `0010_cohorts.sql` add serve the windows, the phone filter and the reject lookups): the gone-marking's statement runs on the scraper prefix of the links' unique index and its display re-derivation on the links' candidate index, `JudgeAll` on the candidates' index on status, the match on the links' name key, state and ZIP joined to the candidates by id, and a ruling on the candidates' id, the links' candidate index and the rulings by candidate, for the candidates it touches alone. Only the time bound of `D06-passes` and the read that answers while a write is open (R-DA8Q-FI3G) are required; the statements are the build's.
- **Ruling points 1 and 2 carry no requirement of their own** (orchestrator ruling): reads by key, work confined to a batch's rows and their candidates, and a bounded gone-marking cannot be observed by use, since a test never reads tables or counts statements; the cost requirements of `D06-passes` (R-00FD-PO9J, R-01NA-3G08, R-02V6-H7QX) are their proof, and the read during a write (R-DA8Q-FI3G) is ruling point 4's.
- **Upkeep touches only its own table, and its memory is the bound** (log 36): `ReplaceZipDrive` and `PrunePasses` had gone through a write that read every record of every table into memory, copied it and compared the copy afterwards, so the start took 450 to 700 MB over the `us` space's 43,000 candidates and 54,000 links and was killed under `memory_max = 256M` (`D02-cli`). They were that path's only callers, so the path is gone with them; every write is now bounded by what it touches. Which statements they run is the build's; what use can observe is the memory a call allocates, which a test reads with `runtime.ReadMemStats` around the call. R-Y4NM-OD2H and R-Y5VJ-24T6 bind it over the store `D06-passes`' cost chain leaves behind, 5,000 active candidates judged and 10,000 links, generated as the time bounds' runs are, so no production data is needed: measured over that store, each call allocated about 174 MiB through the whole-database path, 0.7 MiB for the same call over an empty store, and reading the 5,000 candidates alone allocated 15.5 MiB, so the bound of 4 MiB fails a call that reads the candidates whole, and so any that reads the links, twice as many, and leaves the keyed calls room. The cost store holds no ruling, cohort or reject, so a call that read one of those tables whole would pass; this limitation is accepted, since those tables grow only by the owner's hand. `TotalAlloc` counts every goroutine of the test process and only grows, so a collection does not disturb it; the test that reads it does not call `t.Parallel`, waits for the pass's ending event in its capture before it measures, and makes no other call while it measures.
- **An unchanged row still re-derives its candidate's display once per batch**: a link's last seen orders the display (`D12-resolution`, the display link), so the touch an unchanged row makes can change which link shows, and `D12-resolution` requires the display of every candidate an `Attach` returns current after it; the cost stays one re-derivation per candidate per batch, from that candidate's own links. This goes beyond the ruling's "one lookup and a touch of last seen", deliberately.
- **A read never waits for a write**: appkit's `db.Read` answers from the last commit while `db.Write` holds the writer, which a probe against appkit's released `db` showed (a read returned while a test held a write transaction open), and the store adds no lock of its own across a transaction. The store this replaces held one store-wide lock across every transaction, so a read waited behind a write that was itself waiting for the writer; a test holding a `Write` open while an `Attach` waits tells the two apart. A lock the store took only inside its own write transaction, after appkit's writer is won, would escape that test, and this limitation is accepted: use cannot observe when an `Attach` is inside its own transaction, and a lock held there blocks reads only for as long as the batch's own write transaction, which the time bound of `D06-passes` keeps short. Likewise the test cannot confirm that its waiting `Attach`, `Decide` and `Judge` have begun waiting before it reads, since the design declares no hook that would tell it: a store lock held across a whole write call is caught only when a waiting call has taken it before the reads end, which the test makes likely, not certain, by starting the writes first and yielding between reads; this limitation is accepted too.
- `ListCandidates`' `phone` filter is matched on the links' phone keys, any link, gone or not, with the filter normalized by `sources.PhoneKey`: a phone is identity evidence, and a gone link still counts for identity (decision 6).
- **Windows by position, not offset** (appkit's D25): each list read takes the position of the last entry of the window before and a count `n`, as prompts' `Runs` does; a position is the sort key of the entry, the created text (`Created` as RFC 3339 UTC, which is how it is stored) and id for a candidate, the started text and id for a pass, the name and id for a cohort, and an empty id asks for the first window. The tools and pages pass `n` one more than the window `paging.Window` read. An `n` below 1 is refused `ErrUnreachable`, as every value no consumer sends is in candidates' store, where prompts answers an empty window. The landing no longer ranks a window, so no offset count is kept.
- **The order each window takes, and the plan that serves it**: candidates `status = 'active'`, `(created, id) < (?, ?)`, `ORDER BY created DESC, id DESC`, on `candidates_window`; passes `(started, id) < (?, ?)`, `ORDER BY started DESC, id DESC`, on `passes_window`; cohorts `(name, id) > (?, ?)`, `ORDER BY name, id`, on `cohorts_window`, `shape/`'s Storage row value, catalogs by name (log 18). The indexes carry `id` because a table whose primary key is text keeps its rows by rowid, so `candidates_created` and `passes_started`, ordered by rowid among equal times, cannot serve the id tie-break; those two are left in place, and a later contract migration may drop them. **Each window is two fixed statements** (orchestrator decision D28): the first window and the window after a position are separate statements, exported from `internal/store` as `CandidatesFirst` and `CandidatesAfter`, `StartedFirst` and `StartedAfter` for the passes (named for their order, since gate 5's `gosec` G101 flags a string constant whose name holds `pass` as a hardcoded credential), and `CohortsFirst` and `CohortsAfter`, each with every value bound (as scrapes' rows window and prompts' `Runs` are), and each window method runs the first of its pair for an empty id and the second otherwise: SQLite cannot take a disjunction guarded by a bound value as an index bound, so a folded statement walked its index from the start on every deep page (the sandbox check over 10,000 candidates and 2,000 passes). The filters may stay guarded by their bound values (`?='' OR ...`), since none of them is an index bound; the phone probe plans as a correlated subquery on `links_phone`. A first window has no position to seek to, so the passes' and the cohorts' are a `SCAN` of their index in its own order, stopped by the `LIMIT`, and the candidates' a `SEARCH` on `status = ?`. Observed through appkit's driver (`Read` on a handle `db.Open` returned, SQLite 3.53.4) and with the `sqlite3` CLI 3.46.1, over the nine migrations for the candidates and passes, as recorded for `0009` (`CandidatesAfter` `SEARCH candidates USING INDEX candidates_window (status=? AND (created,id)<(?,?))`, `CandidatesFirst` the same with `(status=?)`, `StartedAfter` `SEARCH passes USING COVERING INDEX passes_window ((started,id)<(?,?))` for a statement selecting the id alone, `StartedFirst` `SCAN passes USING INDEX passes_window`), and over the ten for the cohorts (`CohortsAfter` `SEARCH cohorts USING INDEX cohorts_window ((name,id)>(?,?))`, `COVERING INDEX` for a statement selecting the id and name alone, `CohortsFirst` `SCAN cohorts USING INDEX cohorts_window`, before and after `ANALYZE`); no `USE TEMP B-TREE` in any. appkit's driver refuses a statement given fewer arguments than its parameters, so the requirements declare each statement's parameters in order. The plans are required of the six window statements (R-CVLX-U974, R-CWTU-80XT, R-TGA0-W4TG), and each statement's rows are required to be its method's window (R-CUE1-GHGF). That a window method runs its statement rather than another giving the same rows cannot be observed by use, since no test reads source or traces statements; this limitation is accepted, and the sandbox check's deep-page timings and plans cover it on the real binary.
- **The reversed windows mirror the forward ones** (decided 2026-10-13, for the landing's Prev and Last, `D08-pages`) rather than taking a direction flag: each is two fixed statements, as each forward window is, with every value bound, and each reversed method runs the first of its pair for an empty id and the second otherwise. `ListPassesReversed` runs `StartedLast`, `ORDER BY started ASC, id ASC LIMIT ?`, and `StartedPreceding`, `WHERE (started, id) > (?, ?) ORDER BY started ASC, id ASC LIMIT ?`; `ListCohortsReversed` runs `CohortsLast`, `ORDER BY name DESC, id DESC LIMIT ?`, and `CohortsPreceding`, `WHERE (name, id) < (?, ?) ORDER BY name DESC, id DESC LIMIT ?`. They are named for the end they start from and the side of the position they read, mirroring `First` and `After`. Both read the forward windows' indexes in the other direction. Observed as above: `StartedPreceding` `SEARCH passes USING COVERING INDEX passes_window ((started,id)>(?,?))` for a statement selecting the id alone, `StartedLast` `SCAN passes USING INDEX passes_window`, `CohortsPreceding` `SEARCH cohorts USING INDEX cohorts_window ((name,id)<(?,?))`, `CohortsLast` `SCAN cohorts USING INDEX cohorts_window`; no `USE TEMP B-TREE` in any. They answer in the reverse of list order, the order a keyset read from a position backwards takes; the landing page reverses the window it draws. An `n` below 1 is refused `ErrUnreachable`, as the forward windows refuse it. The plans are required of the four (R-D458-INDZ, R-THHX-9WK5) and their rows to be their methods' windows (R-D1PF-R3WL); that a method runs its statement rather than another giving the same rows is accepted unobserved, as for the forward windows.
- **The name filter compares Go's lowering, not SQL's.** `names_lower` is written as Go's `strings.ToLower` of the names joined by line feeds, and SQLite's `lower()` folds only ASCII, so the filter is lowered with `strings.ToLower` before it reaches SQL and found with `instr(names_lower, ?) > 0`, a plain substring test: no `LIKE`, so `%` and `_` need no escape, and no `LIKE` pattern-length limit (50,000 bytes by default) can fail a long filter. The brief's `names_lower LIKE '%' || lower(?) || '%'` with an escape would differ from the Go semantics on non-ASCII letters; this does not. The one difference from the Go semantics the store had is the line feed that joins the names: a filter holding a line feed matches no candidate, where it matched a name holding the same line feed before; no source writes one into a name.
- **What still reads whole tables.** The windows and every read a page or a tool makes read by key or by window: `GetCandidate`, `Links`, `Estimates`, `GetAssessment`, `Rulings`, `Rejects`, `GetCohort`, `GetPass` and `ZipMinutes` read one candidate's, one cohort's or one pass's rows by index. `ReadCohort` reads the assessments of the active candidates its filters do not rule out, ordered by its order and cut by its size, and counts them, which `D14-cohorts`' definition asks of it; its standing rejects come from `rejects_cohort`. `RunningPasses` is no page's or tool's read: the start calls it once, and with no index on `status` it scans `passes`, whose size is the configured retention plus the passes recorded since the last sweep. What still reads a table whole is the judge path and upkeep: `JudgeAll`, which covers every active candidate by definition, and `PrunePasses` and `ReplaceZipDrive`, each its own table alone (log 36). `Decide` reads and writes by key the candidates it touches alone (orchestrator ruling, after the sandbox found one ruling taking eight minutes over 43,058 candidates and 53,787 links, past the MCP gateway's 50 seconds; `D12-resolution`'s requirements bind it). The engine's redelivery check (`D06-passes`, R-YRFA-2BM8) does not list the passes: `FindDelivered` asks for one pass carrying the delivery's event id or naming its run, on `passes_delivery` and on `passes_trigger`, which `0008` adds; for a judge delivery the engine passes no run, so only the delivery arm can match. `passes_delivery` is partial (`WHERE delivery <> ''`, `0006`), so the delivery arm states `delivery <> ''` for SQLite to use it; and since two passes can match at once (one by delivery, another by run), the first in pass order is chosen with `ORDER BY started DESC, id DESC LIMIT 1`. With the guard, `EXPLAIN QUERY PLAN` on SQLite 3.46.1 shows the two arms as `SEARCH passes USING INDEX passes_delivery (delivery=?)` and `SEARCH passes USING INDEX passes_trigger (trigger=?)`. That a list or page read holds no more than its window cannot be observed by use, since a test never counts statements or reads tables (the tests of R-CUE1-GHGF and the plan requirements run only the statements the store exports, never SQL of their own); it carries no requirement of its own, and the sandbox check measures it.
- **`candidate_cargo` is still written, and observed by nothing** (log 30): every write of a candidate's `cargo` replaces that candidate's `candidate_cargo` rows in the same transaction, so the previous release's shortlist cargo filter reads it right after a rollback; `JudgeAll` no longer re-derives the table, the repair having served only the shortlist (`D13-scoring`). Cargo is not a cohort filter (cohorts decision 4), so no read of this release reads the table, and the requirements only the shortlist could observe are gone with it; the upkeep is carried by this prose alone, since a test may not read tables. Dropping the table is a finding for the next contract.
- **The `fleet` column is still written, and observed by nothing in this release** (cohorts decision 14): the store writes it true exactly when the assessment's fleet verdict is `pass`, for the previous release, which reads it. The Go type carries the verdict alone, so no read of this release answers the column and no test may read it; like `candidate_cargo`, the write is carried by this prose and checked in the sandbox, and the next release drops the column.

## Consumer tasks

The engine (`D06-passes`), `c` the caller, records a rebuild with `p, err := st.AddPass(ctx, store.Pass{Kind: store.KindRebuild, Origin: store.OriginRebuild, Trigger: store.TriggerRebuild, UserID: c.UserID, UserEmail: c.Email, RequestID: c.RequestID})`, `store.ErrBusy` answering `busy`; an ingest delivery with `st.AddPass(ctx, store.Pass{Kind: store.KindIngest, Origin: store.OriginRun, Trigger: run, UserID: user, RequestID: c.RequestID, Delivery: d.Event.ID})` and a judge delivery with `st.AddPass(ctx, store.Pass{Kind: store.KindJudge, Origin: store.OriginCron, Trigger: store.TriggerJudge, UserID: user, RequestID: c.RequestID, Delivery: d.Event.ID})`, `store.ErrDelivered` answering `Skip` and `store.ErrBusy` `Fail`. An ingest hands each batch to `n, touched, err := st.Attach(ctx, run, rebuild, batch)`, then calls `st.MarkGone(ctx, scraper, run)`, adds the `store.Counts` they answer and ends with `st.FinishPass(ctx, p.ID, total)`; a judge calls `n, err := st.JudgeAll(ctx)` and ends with `st.FinishPass(ctx, p.ID, n)`; a rebuild does an ingest's writes for each scraper's current run, then `st.JudgeAll(ctx)`, and finishes with the sum. A pass whose work failed or was interrupted ends with `st.FailPass(ctx, p.ID, store.ReasonScrapes)` or its other reason. An ingest delivery asks `_, err := st.FindDelivered(ctx, d.Event.ID, run)` before it reads scrapes and a judge delivery `st.FindDelivered(ctx, d.Event.ID, "")`, a nil error answering `Skip` and `store.ErrNotFound` going on. The start calls `st.ReplaceZipDrive(ctx, candidates.ZipDrive())`, then `st.RunningPasses(ctx)`; the sweep `st.PrunePasses(ctx, s.KeepPasses)`. `decide`, `exclude` and `include` re-judge through `st.Decide` (`D12-resolution`, `D13-scoring`).

The cohort tools (`D10-tools`), `c` the caller, check `store.ValidCohortName`, `store.ValidCohortSize`, `store.ValidCohortFilters` and `store.ValidCohortOrder` on what was passed and `store.ValidCohortID` on the id before the store, then `create_cohort` calls `k, err := st.CreateCohort(ctx, store.Cohort{Name: a.Name, Size: size, Filters: f, Order: o, CreatedUserID: c.UserID, CreatedUserEmail: c.Email})`, `size` being `store.CohortSizeDefault` when none was passed and `f` and `o` built from the arguments with `store.OrderRevenueLow`, `store.DirectionAsc` and the like as their words; `edit_cohort` `k, err := st.EditCohort(ctx, store.CohortEdit{ID: a.Cohort, Name: a.Name, Size: sz, Filters: fp, Order: op, UserID: c.UserID, UserEmail: c.Email})`, each pointer nil when its argument was absent, `fp` `&store.CohortFilters{}` for a passed `{}` and `op` `&[]store.CohortOrder{}` for a passed `[]`; `delete_cohort` `k, err := st.DeleteCohort(ctx, a.Cohort)`; `cohort` `r, err := st.ReadCohort(ctx, a.Cohort)`, answering `r.Cohort`, `r.Matching`, each `m` of `r.Members` from `m.Candidate` and `m.Assessment` (`m.Assessment.FleetVerdict`, `m.Assessment.Excluded` among them) and `r.Rejects`; `cohorts` `ks, err := st.ListCohorts(ctx, name, id, n+1)` after `paging.Token{Tool: "cohorts"}.Decode(page, &name, &id)`, the `n`th cohort's `k.Name` and `k.ID` giving `next`; `reject` and `unreject` `x, err := st.Reject(ctx, store.Reject{Kind: store.KindReject, Cohort: a.Cohort, Candidate: a.Candidate, Why: a.Why, UserID: c.UserID, UserEmail: c.Email})`, with `store.KindUnreject` for `unreject`, answering `x`, whose `Why`, `UserID`, `UserEmail` and `At` are empty for an unreject of a pair with no standing reject; and `candidate` adds `xs, err := st.Rejects(ctx, id)`. `store.ErrNotFound` answers `not_found`, `store.ErrInvalid` `invalid`, and any error matching `store.ErrUnreachable` `unavailable`.

The pages (`D08-pages`) call `r, err := st.ReadCohort(ctx, id)` for `/cohorts/<id>`, `store.ErrNotFound` answering the not-found page, and the landing `st.ListCohorts(ctx, name, id, paging.DefaultLimit+1)` and `st.ListPasses(ctx, started, id, paging.DefaultLimit+1)`, each position decoded from its query parameter or empty; for a before-token `ks, err := st.ListCohortsReversed(ctx, name, id, paging.DefaultLimit+1)` and `ps, err := st.ListPassesReversed(ctx, started, id, paging.DefaultLimit+1)`, for `last` the same with `"", ""`, each window the first `paging.DefaultLimit` reversed and underflowing when no more came back; the candidate page `st.GetCandidate`, `st.Links`, `st.Estimates`, `st.GetAssessment`, `st.Rulings` and `st.Rejects`, a record whose `CohortName` is empty naming a deleted cohort. The tools also call `cs, err := st.ListCandidates(ctx, store.CandidateFilter{Name: "trucking"}, created, id, n+1)`, the `n`th candidate's `c.Created.UTC().Format(time.RFC3339)` and `c.ID` giving `next`, and `ps, err := st.ListPasses(ctx, started, id, n+1)`, the `n`th pass's `p.Started.UTC().Format(time.RFC3339)` and `p.ID` giving `next`; `decide` calls `r, cs, err := st.Decide(ctx, store.Ruling{Kind: store.KindMerge, Candidate: a, Other: b, Why: why, UserID: c.UserID, UserEmail: c.Email})` and `exclude` the same with `store.KindExclude` and no `Other`. Any error matching `store.ErrUnreachable` is answered with `store.Unreachable`.

A test opens its own database with `db.Open` and the root package's `Migrations()`, builds `store.New(d, store.Config{Now: clock, Rand: rnd})`, replaces the ZIP table with `candidates.ZipDrive()`, attaches observations it builds from `sources.Reading` values, judges with `st.Judge(ctx, ids)` and `st.JudgeAll(ctx)`, records, finishes and fails passes, creates, edits, reads, rejects in and deletes cohorts, moves the clock to move a cohort's filing-age date, pages each list window by window, flips `d.SetFailing(true)`, and reopens the path to prove what persists. A test of a window's plan, `d` the handle its store was built over, runs `d.Read(ctx, func(tx *sql.Tx) error { rows, err := tx.QueryContext(ctx, "EXPLAIN QUERY PLAN "+store.CohortsAfter, "x", "y", 26); ... })` and reads each row's `id`, `parent`, `notused` and `detail`; a test of a statement's rows runs `tx.QueryContext(ctx, store.CohortsPreceding, name, id, n)` the same way and compares the first column of each row with the `ID`s `st.ListCohortsReversed(ctx, name, id, n)` returns, and likewise for the other statements. A test of `0010` reads `fs.ReadFile(candidates.Migrations(), "0010_cohorts.sql")`; a test of the previous release's rows opens a database with a file system holding only the first nine files, writes rows with `d.Write` as that release would, opens it again with `candidates.Migrations()` and asks `st.GetAssessment`; a test of a roll forward writes an assessment row with `d.Write` naming only the previous release's columns and asks `st.GetAssessment`. A test of serving holds `d.Write(ctx, fn)` open, its `fn` waiting on a channel the test holds, starts `st.Attach(ctx, run, false, batch)`, `st.Decide(ctx, r)` and `st.Judge(ctx, ids)` each in a goroutine of its own, and calls `st.GetCandidate`, `st.Links` and `st.ReadCohort`, each called a fixed number of times, yielding between calls, and each answering before the test releases `fn`; were a read to wait for the write, the test would never release it and would fail at the package's timeout, so the test waits on no clock.
