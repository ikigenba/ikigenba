## What ships

The release holds four members of candidates' directory: `bin/candidates`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `filter`, human-authored (decision 1). No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The two files under `etc/` are what the root package's `Etc` embeds (`D01-layout-and-run-seam`): `etc/manifest.toml` holds the bytes of `cli.Manifest`, which `D02-cli` states byte for byte with the command that prints it, and `etc/nginx.conf` the bytes of `cli.NginxConf`, which this document states. `share/zip_drive.csv` ships inside the binary, embedded by the root package (`D01-layout-and-run-seam`), not beside it.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox and home read it, so its text is contract, stated byte for byte as `cli.Manifest` in `D02-cli`, which also compares its description with `pages.Description` and its `[env]` with `settings.Defaults()`. What a space takes from it: it names the app `candidates`; its description, the same as `pages.Description`; that it is not the default app; that it is an MCP service (`mcp = true`), so the gateway offers the eighteen tools (`D10-tools`); that it does not serve guests (`guests = false`), so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); two secrets, `CANDIDATES_ROUTE_ORIGIN` and `GOOGLE_MAPS_API_KEY`, in that order, the base the drive is measured from and the key the routing service is asked with (drive route decisions 2 and 13), its other outside traffic, the website check's, `add_page`'s and the website search's confirmation fetches of public sites, needing no credential; an `[env]` table whose one line is `CANDIDATES_KEEP_PASSES = "20"` (decision 17), so the value the host writes into candidates' environment is the one candidates applies when the setting is unset; the `[database]` table that has the host keep and replicate `state/candidates.db`; a `[resources]` table whose only line is `memory_max = "256M"`, room enough since a run's rows are streamed and handled a batch at a time (decision 1); and, last, a `[home]` table whose only line is `group = "application"`, so home lists candidates under Application. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app, and `settings.Read` defaults it to 5 (`D01-layout-and-run-seam`). The change to two judgments and the PPP reader changes nothing in the manifest; the cohorts change alters only its description, which no longer speaks of a ranking against the fit test (`D02-cli`, with `pages.Description` in `D01-layout-and-run-seam`). The website check changes nothing in it (website log P2, revised): the stand-in fetcher is chosen by `IKIGENBA_SANDBOX`, which the sandbox sets for every app and `us` never sets, so no `[env]` line is needed, and none could be sandbox-only, since the sandbox renders an app's environment from the same `[env]` table `us` reads; and `memory_max` still holds, since an enrich pass holds no more than the fetches in flight and one batch of candidates (`D15-website-check`). The enrichers change nothing in it either: the derived kinds read only candidates' own database, a batch of candidates at a time, and need no setting, secret or outside address (`D16-enrichers`, `D06-passes`). The site text changes nothing in it either: prompts is a sibling the services file names, and the manifest lists no sibling; a `site_text` pass holds no more than the runs in flight, at most `passes.RunsInFlight`, and an `add_page` one body read to `website.BodyCap`, so `memory_max` still holds; and no setting is added, `site_text`'s pacing being `passes`' constants and its only time limit prompts' own (`D06-passes`). The categories change nothing in it either: the new words are constants in `sources` and JSON in the readings, the results, the facts rows and the judgments, and no setting, secret or column is added. The brief changes nothing in it either: it shares `site_text`'s prompts client and pacing, a `brief` pass holding no more than the runs in flight, each input bounded by `enrichers.BriefInputBytes` (`D16-enrichers`), so `memory_max` still holds, and its two columns are the database's, which the `[database]` table already keeps. The category evidence changes nothing in it either: it adds no setting, secret or column, `classified_by` and `classified` being derived when they are read. The website search changes nothing in it either: it shares the other prompts kinds' client and pacing and the website check's fetcher, a `website_search` pass holding no more than the runs in flight, each confirmation one fetch read to `website.BodyCap` (`D15-website-check`), so `memory_max` still holds; it adds no setting or secret, the search's web access being prompts' (website search decision 4); and its two columns are the database's, which the `[database]` table already keeps. The exact drive time changes the manifest's `secrets` line alone (`D02-cli`). The key is a secret as prompts' Brave key is. The origin is no secret, but it rides the same road, as the suite's other per-space values do (Google's client id, the CRM organisation in opsctl's own example): opsctl writes an app's environment only from the space's parameter store, the manifest's `[env]` and its fixed lines, so a value in `[env]` changes only with a release, and the owner moves the base without one (drive route decision 2); a name the manifest lists among its secrets may not also be an `[env]` key, so `settings.DefaultRouteOrigin`, `Sandstone, MN`, stays out of `[env]` and applies only where the variable is unset or empty (`D01-layout-and-run-seam`). Both are read once at the start. `memory_max` still holds: a `drive_route` pass holds no more than `passes.RoutesInFlight` requests in flight, each answer a few numbers and an address, and the result rows are the database's. The revenue bands change nothing in it either: the bands and the keyword table are constants in the judge (revenue bands decision 9), the headcounts JSON in the readings, the results, the facts rows and the estimates, and no setting or secret is added; its five columns are the database's, which the `[database]` table already keeps, and a judge holds no more than before, a batch of candidates at a time. The Form 5500 source changes nothing in it either: the source is a reader in the binary over a sibling's runs, which the services file's `scrapes` entry already reaches, and no setting or secret is added; its column, table and indexes are the database's, which the `[database]` table already keeps, and an ingest holds no more than before, a run's rows streamed and handled a batch at a time.

## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. Nothing else is held back; candidates has no sibling read path, so the public name serves the pages, a kept page's text page among them, and `/mcp`, behind auth.

## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a full ingest read; `prompts`, whose socket a pass of kind `enrich_target` walking a prompts kind, `site_text`, `website_search` or `brief`, calls as the caller of the `enrich`, through appkit's `prompts` client, which the start builds from the entry (`D03-serve`, `D06-passes`); `events` and `telemetry`, appkit's sinks'; `auth`, for the banner's addresses (decision 17); and `campaigns`, whose URL alone builds the candidate page's link to each campaign's page, its socket never dialled (`D01-layout-and-run-seam`, `D08-pages`); it calls no other sibling, campaigns included. Outside the host it reaches only the public websites the website check, `add_page` and the website search's confirmation fetch, through the real fetcher, which follows no proxy and refuses loopback, private, link-local and unspecified addresses (`D15-website-check`); the agent of a `site-text` run crawls a company's site from prompts, not from candidates, and names the pages worth keeping back through the gateway's `add_page`, which candidates then fetches itself; the agent of a `website-search` run searches the web from prompts, with the `web` tool group prompts runs it with, never from candidates, and names one URL in its answer, which candidates fetches once under `D15-website-check`'s rules before it records it (website search decisions 4 and 5); the agent of a `brief` run is given the pages in its input and calls nothing. It reaches one service outside the suite: a pass of kind `enrich_target` walking `drive_route` asks Google's geocoding and routing services through the routes client, over the process's outbound HTTP client (`D17-drive-route`, `D01-layout-and-run-seam`), at most `passes.RoutesInFlight` requests at once, each carrying the key and the address strings and coordinates `D17-drive-route` gives, and no identity of the suite's; no other pass, the corpus enrich and an `enrich` with no kind among them, sends a request to the routing service (`D06-passes`). A missing file or entry never refuses the start (`D03-serve`); with no `prompts` entry, `site_text`, `website_search` and `brief` are `unavailable` and every other kind runs as before (site text decision 21), and with no fetcher `website_search` is `unavailable` too, as `website_check` is (`D16-enrichers`); with `GOOGLE_MAPS_API_KEY` unset or empty the start still serves, and an `enrich` of `drive_route` with a target is `invalid` with `passes.NoRouteKey`'s text while every other kind runs as before (drive route decision 13, `D06-passes`), a state a sandbox never reaches, since `sandbox up` refuses a listed secret that is unset or empty, and a space reaches only when an empty key was pushed, since opsctl's activation refuses a listed secret only when it is absent from the space's object. The host must run events, which delivers `scrape.finished`, `cron.judge_candidates.fired` and campaigns' three events to candidates and takes its pass events; scrapes, which it reads; prompts, which runs each `site-text`, `website-search` and `brief` run and in which the owner keeps the prompts of those names, a `website-search` run reaching the web through prompts' `web` tool group, since candidates knows no prompt's model, instructions or tools (site text decision 7); and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`). So with campaigns, which emits `campaign.member.added`, `campaign.member.rejected` and `campaign.piece.delivered` as its `add_member`, `add_prospect_list`, `reject`, `deliver` and `deliver_channel` change a campaign: candidates accepts each by its exact name and never calls campaigns. A host without campaigns leaves every candidate's campaigns empty, and a services file with no `campaigns` entry has the candidate page draw each campaign's id unlinked; neither refuses anything (`D03-serve`, `D08-pages`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored opinions as the last judge wrote them, while the facts still move at each enrich that writes a result (`D16-enrichers`); nothing decays either, and `judge`, or a full `ingest`, judges on demand (funnel rename decision 10). candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `judge`, a full `ingest` and rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]`, `IKIGENBA_SANDBOX`, which it sets for every app, and the two secrets the manifest lists, each read from the variable of the same name in the environment `sandbox up` runs with; puts every request through auth's `/check`; and includes `etc/nginx.conf` in candidates' server. `sandbox up` starts nothing while a secret some manifest lists is unset or empty: it names every missing one with the variable it is read from and stops. ## Trust

candidates believes the identity it is sent, as every sibling does: `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx or the gateway set them on a request to its socket. It checks them against nothing and asks auth nothing; an `ingest` or an `enrich` is recorded as started by the user the request names, a ruling as made by that user, and an open of a prospect list, by `prospect_list` or by its page, as made by that user, and an `ingest`'s reads of scrapes forward that identity, as every sibling call forwards its caller. It takes a delivery at `POST /events` from any process that can reach its socket, with no identity at all, as appkit's delivery handler admits it (`D03-serve`, `D07-events`). A delivered `scrape.finished` starts an ingest pass that no person started, and scrapes' read path requires an identity, so that pass reads scrapes as the **service identity**: `X-User-Id` `candidates`, no email, the delivery's request id, with the bus event as cause (decision 12, `D06-passes`). scrapes trusts any process at its socket, so the read is answered, and scrapes' trail records `candidates` as its user: the first service-to-service call in the suite made as no person. A delivered `cron.judge_candidates.fired` starts a judge pass that no person started either; it reads nothing and calls no sibling, so it names no identity to anyone. A pass of kind `enrich_target` walking a prompts kind forwards its caller on every request to prompts, so prompts runs the caller's own `site-text`, `website-search` or `brief` prompt as the caller (site text decision 7, `D03-serve`, `D06-passes`); a `site-text` run's agent calls `add_page` through the gateway like any agent, and the page records the identity that request names (`D10-tools`), while a `website-search` run's searches the web from prompts and calls nothing of the suite, and a `brief` run's is given the company's pages and facts in its input and calls nothing. A pass another pass starts, the enrich an ingest starts or the judge an enrich starts, has no user either, carrying the starting pass's request id and cause (`D06-passes`); an enrich, and a website search's confirmation, fetch public sites and send them no identity, and a `drive_route` pass sends Google the key and the address strings and coordinates `D17-drive-route` gives for each due candidate, and no identity of the suite's. A delivered campaign event is taken the same way, with no identity, and records a use on the candidate it names, or the one that candidate was merged into, as campaigns told it; it starts no pass and calls nothing (`D06-passes`). A process that can reach candidates' socket can therefore name any user, start a full ingest or an enrich, and so a run of that user's prompt at prompts, keep a page or make a ruling as that user, start a judge, spend the routing key on a `drive_route` pass, record a campaign use on any candidate, record an open of any prospect list as that user, so moving the point the next open's changes are worked out from, and read every candidate; every service on the host is trusted, and the gateway and nginx are the only doors from outside, nginx refusing the bus's two paths there.
