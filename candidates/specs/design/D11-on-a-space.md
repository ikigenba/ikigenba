# D11-on-a-space

What candidates contributes when it runs on a space and in a sandbox: what ships, the manifest and the nginx fragment, which entries of the services file it uses, the cron trigger the owner creates for the daily judge, the trust it places in the identity it is sent and the identity it sends scrapes and prompts (decisions 12 and 21, site text decisions 7 and 21), which of the contract's guarantees the delivery's sandbox check and the `us` smoke test stand on, and how the enrichers (`D16-enrichers`), six kinds with `website_search` fourth and `brief` last, reach a space: the derived kinds read only candidates' own database; the website check (`D15-website-check`), `add_page` (`D10-tools`) and the website search's confirmation fetch through a stand-in in a sandbox and through the real fetcher on `us`; and the prompts kinds `site_text`, `website_search` and `brief` run the caller's prompt named for the kind, `site-text`, `website-search` or `brief`, at prompts, through a stand-in prompts in a sandbox and the real one on `us`, a `website_search` run searching the web from prompts and naming one URL back, which candidates fetches once to confirm before it records it, and a `brief` run reading the pages `site_text` kept and calling no tool, so it fetches nothing and keeps no page. A confirmed site the search found becomes the facts row's website, with the source `search`, as soon as its result is written, wherever the website check found none (`D04-store`, website search decision 7), so `site_text` is due for it at the owner's next ask with no other step (website search decision 8); the release adds one migration, `0015_website_search.sql`, on which the previous release, release-50, runs unchanged (website search decision 14). A good brief that gives a category decides the facts row's categories alone, each with the source `brief`, as soon as its result is written, and one that gives none leaves the link facts' standing (`D04-store`, category evidence decisions 1 and 2), so a space needs no judge to show a new brief's decision. A change to how a source reads a row reaches a space's stored readings only through a `rebuild`, which rereads every row and writes `link_facts` again: so the category list's growth reached them, a government name match becoming a category from `name`, and so does this change's FMCSA reading, which gives `trucking and logistics` only to a carrier whose class is `for_hire` or `mixed` (`D05-sources`, `D16-enrichers`, `D06-passes`); the same `rebuild` projects every facts row again, whether or not its link facts changed, which is how a facts row written under the earlier projection comes to follow this one (`D06-passes`, `D04-store`). It follows scrapes' on-a-space design. The guarantee such documents end with, that no business name, address, phone, email, person or ruling text reaches the trail, the bus, a refusal or standard error, is `D09-trail`'s here, as it is scrapes' trail document's there.

Decisions cited by number are the decisions document that delivered candidates. "Website log X" is entry X of the decisions log of the website-check change, "site text decision N" entry N of the decisions document of the site-text change, "brief decision N" entry N of the decisions document of the brief change, "P N" entry N of the decisions log of the brief change's delivery, "category evidence decision N" entry N of the decisions document of the category-evidence change, "website search decision N" outcome N of the decisions document of the website-search change, and "S N" entry DN of the decisions log of the website-search change's delivery.

## What ships

The release holds four members of candidates' directory: `bin/candidates`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `filter`, human-authored (decision 1). No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The two files under `etc/` are what the root package's `Etc` embeds (`D01-layout-and-run-seam`): `etc/manifest.toml` holds the bytes of `cli.Manifest`, which `D02-cli` states byte for byte with the command that prints it, and `etc/nginx.conf` the bytes of `cli.NginxConf`, which this document states. `share/zip_drive.csv` ships inside the binary, embedded by the root package (`D01-layout-and-run-seam`), not beside it.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox and home read it, so its text is contract, stated byte for byte as `cli.Manifest` in `D02-cli`, which also compares its description with `pages.Description` and its `[env]` with `settings.Defaults()`. What a space takes from it: it names the app `candidates`; its description, the same as `pages.Description`; that it is not the default app; that it is an MCP service (`mcp = true`), so the gateway offers the seventeen tools (`D10-tools`); that it does not serve guests (`guests = false`), so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); no secrets, since candidates holds none of its own and calls no service outside the suite, its outside traffic, the website check's and `add_page`'s fetches of public sites, needing no credential; an `[env]` table whose one line is `CANDIDATES_KEEP_PASSES = "20"` (decision 17), so the value the host writes into candidates' environment is the one candidates applies when the setting is unset; the `[database]` table that has the host keep and replicate `state/candidates.db`; a `[resources]` table whose only line is `memory_max = "256M"`, room enough since a run's rows are streamed and handled a batch at a time (decision 1); and, last, a `[home]` table whose only line is `group = "application"`, so home lists candidates under Application. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app, and `settings.Read` defaults it to 5 (`D01-layout-and-run-seam`). The change to two judgments and the PPP reader changes nothing in the manifest; the cohorts change alters only its description, which no longer speaks of a ranking against the fit test (`D02-cli`, with `pages.Description` in `D01-layout-and-run-seam`). The website check changes nothing in it (website log P2, revised): the stand-in fetcher is chosen by `IKIGENBA_SANDBOX`, which the sandbox sets for every app and `us` never sets, so no `[env]` line is needed, and none could be sandbox-only, since the sandbox renders an app's environment from the same `[env]` table `us` reads; and `memory_max` still holds, since an enrich pass holds no more than the fetches in flight and one batch of candidates (`D15-website-check`). The enrichers change nothing in it either: the derived kinds read only candidates' own database, a batch of candidates at a time, and need no setting, secret or outside address (`D16-enrichers`, `D06-passes`). The site text changes nothing in it either: prompts is a sibling the services file names, and the manifest lists no sibling; a `site_text` pass holds no more than the runs in flight, at most `passes.RunsInFlight`, and an `add_page` one body read to `website.BodyCap`, so `memory_max` still holds; and no setting is added, `site_text`'s pacing being `passes`' constants and its only time limit prompts' own (`D06-passes`). The categories change nothing in it either: the new words are constants in `sources` and JSON in the readings, the results, the facts rows and the assessments, and no setting, secret or column is added. The brief changes nothing in it either: it shares `site_text`'s prompts client and pacing, a `brief` pass holding no more than the runs in flight, each input bounded by `enrichers.BriefInputBytes` (`D16-enrichers`), so `memory_max` still holds, and its two columns are the database's, which the `[database]` table already keeps. The category evidence changes nothing in it either: it adds no setting, secret or column, `classified_by` and `classified` being derived when they are read. The website search changes nothing in it either: it shares the other prompts kinds' client and pacing and the website check's fetcher, a `website_search` pass holding no more than the runs in flight, each confirmation one fetch read to `website.BodyCap` (`D15-website-check`), so `memory_max` still holds; it adds no setting or secret, the search's web access being prompts' (website search decision 4); and its two columns are the database's, which the `[database]` table already keeps.

## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. Nothing else is held back; candidates has no sibling read path, so the public name serves the pages, a kept page's text page among them, and `/mcp`, behind auth.

## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a rebuild read; `prompts`, whose socket a pass of kind `enrich_cohort` walking a prompts kind, `site_text`, `website_search` or `brief`, calls as the caller of the `enrich`, through appkit's `prompts` client, which the start builds from the entry (`D03-serve`, `D06-passes`); `events` and `telemetry`, appkit's sinks'; and `auth`, for the banner's addresses (decision 17); it calls no other sibling. Outside the host it reaches only the public websites the website check, `add_page` and the website search's confirmation fetch, through the real fetcher, which follows no proxy and refuses loopback, private, link-local and unspecified addresses (`D15-website-check`); the agent of a `site-text` run crawls a company's site from prompts, not from candidates, and names the pages worth keeping back through the gateway's `add_page`, which candidates then fetches itself; the agent of a `website-search` run searches the web from prompts, with the `web` tool group prompts runs it with, never from candidates, and names one URL in its answer, which candidates fetches once under `D15-website-check`'s rules before it records it (website search decisions 4 and 5); the agent of a `brief` run is given the pages in its input and calls nothing. A missing file or entry never refuses the start (`D03-serve`); with no `prompts` entry, `site_text`, `website_search` and `brief` are `unavailable` and every other kind runs as before (site text decision 21), and with no fetcher `website_search` is `unavailable` too, as `website_check` is (`D16-enrichers`). The host must run events, which delivers `scrape.finished` and `cron.judge_candidates.fired` to candidates and takes its pass events; scrapes, which it reads; prompts, which runs each `site-text`, `website-search` and `brief` run and in which the owner keeps the prompts of those names, a `website-search` run reaching the web through prompts' `web` tool group, since candidates knows no prompt's model, instructions or tools (site text decision 7); and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored opinions as the last judge wrote them, while the facts still move at each enrich that writes a result (`D16-enrichers`); nothing decays either, and `rebuild` judges on demand. candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `rebuild` and on rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]` and `IKIGENBA_SANDBOX`, which it sets for every app, puts every request through auth's `/check`, and includes `etc/nginx.conf` in candidates' server. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools. The sandbox runs a real scrapes and a real prompts too, which the check never reaches: for every exercise that ingests, rebuilds or calls prompts, the services file's `scrapes` and `prompts` entries name stand-ins instead.

**The stand-in fetcher.** With `IKIGENBA_SANDBOX` present, whatever its value, candidates fetches websites through the in-process loopback stub `D15-website-check` declares, and through nothing else (website log P2, revised): the website check's fetches, `add_page`'s and the website search's confirmations alike. The stub listens on two loopback ports, one plain and one TLS, and its client dials one of them whatever host a request names, so no fetch in a sandbox leaves the machine: not the verification list's and not one an ingest starts on its own. It answers by domain: a host under `.test`, a name reserved never to resolve in public DNS (RFC 2606, RFC 6761), whose first label (after one leading `www.`) is one of the stub's keywords, or a keyword followed by `-` and anything, gets that keyword's behaviour (`secure`, `plain`, `prefixed`, `upgrade`, `away`, `missing`, `empty`, `binary`, `refused`, `slow`, `big` and `loop`), and every other host is refused at once, so the real runs' domains each come out `none` without a byte sent and gain no evidence. The keywords, their answers and the results they give are `D15-website-check`'s stub table; a check that names domains names them by keyword, `secure-found.test` being a `secure` domain, and expects the answers that table gives. A `secure` host answers a page on every path, titled with the host, and a `missing` host a 404 on every path. The stub is unchanged by this change; the only fetches of the check are the website check's of the stand-in rows' own domains, which an ingest's follow-on enrich makes, the website search's confirmations of the URLs the stand-in prompts names, and `add_page`'s of the pages the stand-in's `site-text` run names. No confirmation in the check reaches the web (website search decision 5, S 8): the site the stand-in finds is on a `secure` host and the one that does not load on a `missing` host, each answered by the stub.

**The stand-in scrapes.** The change asks for companies with no website on record beside one the website check gave a site and one whose own domain the check found serving none, and the runs of `fmcsa` scrapes holds from earlier checks cannot be made to hold a row with a chosen email; and the migration's backfill must be shown over facts rows the previous release's own website check wrote. So the rows reach candidates from a stand-in, as the categories and category evidence changes' checks did: a program the delivery writes and runs from a temporary directory outside the tree, never committed, that serves on a Unix socket in a short temporary directory one `done` run of `fmcsa` at `/scrapers/fmcsa/current`, `/runs/<r>/record` and `/runs/<r>/rows`, `<r>` its run's id, the paths a fake run (R-76JM-ZE8M) serves, in the shapes appkit's `scrapes` client reads, with the rows below, and answers 404 for any other scraper's current run, as R-IBIN-ZJ0W's fake does, so V11's `rebuild` reads `fmcsa` alone.

**The stand-in prompts.** Nothing in the check may reach a real prompts (V12): the real one cannot be made to answer a chosen standard output or end a run `failed` on demand, a real `website-search` run reaches the web through Brave and spends money on a model, and the change asks that no sandbox run reach the web (website search decision 5). So every exercise that runs prompts goes to a stand-in, as the brief's and the category evidence's checks did (S 8): a program the delivery writes and runs from a temporary directory outside the tree, never committed, that serves MCP at `POST /mcp` on a Unix socket in a short temporary directory, with the tools `show`, `run` and `result` answering as prompts' published tools answer them, in the shapes appkit's `prompts` client reads (D27 of appkit). It records every call it receives, with its arguments and its `X-User-Id`, `X-User-Email` and `X-Request-Id` headers. The delivery sets its behaviour before each exercise: `show` answers the prompt it is asked for, `website-search` or `site-text`, the prompt `D16-enrichers` names for the kind, or refuses as prompts refuses a prompt the caller does not hold; `run` answers a new run id; a run of `website-search` calls nothing and has its `result` answer the ending picked for the company its input's `candidate` names, either `exited`, with exit code 0 unless an item says otherwise, the standard output (`stdout`) the stand-in is told to give and a `cost_nanos` picked, or `failed`, with no exit code and a `cost_nanos` picked; a run of `site-text` has its `result` answer `running` for a hold the delivery picks, during which the stand-in calls `add_page` through the gateway with the stored token for the URLs picked for that company, and then `exited` with exit code 0 and a `cost_nanos` picked. ## Trust

candidates believes the identity it is sent, as every sibling does: `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx or the gateway set them on a request to its socket. It checks them against nothing and asks auth nothing; a `rebuild` or an `enrich` is recorded as started by the user the request names, and a ruling as made by that user, and a `rebuild`'s reads of scrapes forward that identity, as every sibling call forwards its caller. It takes a delivery at `POST /events` from any process that can reach its socket, with no identity at all, as appkit's delivery handler admits it (`D03-serve`, `D07-events`). A delivered `cron.judge_candidates.fired` starts a judge pass that no person started either; it reads nothing and calls no sibling, so it names no identity to anyone. A pass of kind `enrich_cohort` walking a prompts kind forwards its caller on every request to prompts, so prompts runs the caller's own `site-text`, `website-search` or `brief` prompt as the caller (site text decision 7, `D03-serve`, `D06-passes`); a `site-text` run's agent calls `add_page` through the gateway like any agent, and the page records the identity that request names (`D10-tools`), while a `website-search` run's searches the web from prompts and calls nothing of the suite, and a `brief` run's is given the company's pages and facts in its input and calls nothing. A process that can reach candidates' socket can therefore name any user, start a rebuild or an enrich, and so a run of that user's prompt at prompts, keep a page or make a ruling as that user, start a judge, and read every candidate; every service on the host is trusted, and the gateway and nginx are the only doors from outside, nginx refusing the bus's two paths there.
