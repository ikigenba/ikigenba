# D11-on-a-space

What candidates contributes when it runs on a space and in a sandbox: what ships, the manifest and the nginx fragment, which entries of the services file it uses, the cron trigger the owner creates for the daily judge, the trust it places in the identity it is sent and the identity it sends scrapes (decisions 12 and 21), and which of the contract's guarantees the delivery's sandbox check (decision 20) and the `us` smoke test stand on. It follows scrapes' on-a-space design. The guarantee such documents end with, that no business name, address, phone, email, person or ruling text reaches the trail, the bus, a refusal or standard error, is `D09-trail`'s here, as it is scrapes' trail document's there.

## What ships

The release holds four members of candidates' directory: `bin/candidates`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `filter`, human-authored (decision 1). No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The two files under `etc/` are what the root package's `Etc` embeds (`D01-layout-and-run-seam`): `etc/manifest.toml` holds the bytes of `cli.Manifest`, which `D02-cli` states byte for byte with the command that prints it, and `etc/nginx.conf` the bytes of `cli.NginxConf`, which this document states. `share/zip_drive.csv` ships inside the binary, embedded by the root package (`D01-layout-and-run-seam`), not beside it.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox and home read it, so its text is contract, stated byte for byte as `cli.Manifest` in `D02-cli`, which also compares its description with `pages.Description` and its `[env]` with `settings.Defaults()`. What a space takes from it: it names the app `candidates`; its description, the same as `pages.Description`; that it is not the default app; that it is an MCP service (`mcp = true`), so the gateway offers the fifteen tools (`D10-tools`); that it does not serve guests (`guests = false`), so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); no secrets, since candidates holds none of its own and calls nothing outside the suite; an `[env]` table whose one line is `CANDIDATES_KEEP_PASSES = "20"` (decision 17), so the value the host writes into candidates' environment is the one candidates applies when the setting is unset; the `[database]` table that has the host keep and replicate `state/candidates.db`; a `[resources]` table whose only line is `memory_max = "256M"`, room enough since a run's rows are streamed and handled a batch at a time (decision 1); and, last, a `[home]` table whose only line is `group = "application"`, so home lists candidates under Application. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app, and `settings.Read` defaults it to 5 (`D01-layout-and-run-seam`). The change to two judgments and the PPP reader changes nothing in the manifest; the cohorts change alters only its description, which no longer speaks of a ranking against the fit test (`D02-cli`, with `pages.Description` in `D01-layout-and-run-seam`).

## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. Nothing else is held back; candidates has no sibling read path, so the public name serves the pages and `/mcp`, behind auth.

## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a rebuild read, `events` and `telemetry`, appkit's sinks', and `auth`, for the banner's addresses (decision 17); it calls no other sibling and nothing outside the host. A missing file or entry never refuses the start (`D03-serve`). The host must run events, which delivers `scrape.finished` and `cron.judge_candidates.fired` to candidates and takes its pass events; scrapes, which it reads; and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored judgments as the last judge wrote them; nothing else decays them, and `rebuild` judges on demand. candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `rebuild` and on rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]`, puts every request through auth's `/check`, and includes `etc/nginx.conf` in candidates' server. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools, and the gateway's `call` of cron's tools for the trigger.

**The chain.** No scraper is run against an outside source: the sandbox uses the runs of `fmcsa` and `ppp` scrapes already holds from earlier checks, as the change's Sequence says. With candidates stopped and its database emptied, then started: a `scrape.finished` naming the held `fmcsa` run, `done`, is delivered by hand to candidates' socket at `POST /events` and answered `ok`; within a minute `passes` shows an ingest pass with that run as trigger, `done`, `new` equal to the run's `rows`, `created` close to it and `judged` 0, and a cohort created with no filters answers no members and `matching` 0. A `scrape.finished` naming the held `ppp` run is delivered likewise, and its ingest pass likewise. The trigger `judge_candidates` is created with cron's `create` on a schedule a minute away; events' `subscribers` is observed to list candidates `ok` for `cron.judge_candidates.fired`; the fire is observed to start a judge pass that ends `done` with `judged` equal to the live candidates, and the cohort, read again, then answers its first 30 members ranked by `operating_confidence` and a `matching` equal to the active candidates the owner has not excluded; the trigger stays in place for the verification list, whose judges it fires. A `rebuild`, which reads the same held runs as scrapes' current ones, then ends `done` as one pass of kind `rebuild`, and the cohort is deleted.

**The verification list** (the change's Verification section, numbered V1 to V19 here in the order it lists them), run in the sandbox over rows the tests build. V18 is read first, at `sandbox up`: before it, `sqlite3` records the columns of `assessments` and of `passes` in the database the previous release's check left, and after it, over the same file migrated. For the rest candidates is stopped and a test helper builds a fresh database with the root package's `Migrations()`, builds the rows the items name as `scrapes.Row` values (FMCSA rows active with three power units and with one, inactive, and one the plausibility rule rejects; PPP rows alone, one in `other`; one whose rows give no category; revenue estimates at, inside and outside 5,000,000 to 10,000,000 and none; a name matching a government pattern; a carrier class `for_hire` and none; a newest filing 730 days and 731 days before the check's UTC date and none; an operating confidence tied with another's, and a revenue low tied with another's), reads each through the release's own sources (`fmcsa.New().Read`, `ppp.New().Read`), hands them to a store over that database with `Attach`, records an owner exclusion of one of the built candidates with the store's `Decide` (kind `exclude`) so that V1 and V8 have an excluded candidate to leave out and to show, and the file is copied into candidates' `state/`; candidates is started and the trigger is updated with cron's `update` to a schedule a minute away, as scrapes' check does, so its fire judges them (or, where cron cannot be waited on, `cron.judge_candidates.fired` is delivered by hand to candidates' socket at `POST /events`). Each item is then exercised through the gateway's tools and, for V19, the pages with the stored token. The database holds the helper's rows alone (see Recorded decisions). The reads V1 to V10 and V16 run before the writes V11 to V15, which reject and exclude helper-built candidates; V17 changes nothing; V19 runs last, over the rejects and records the writes left. A filing-age item read within a minute of midnight UTC is read again after it, since the cohort measures the filing's age at the UTC date of the read (`D14-cohorts`). After V19 the trigger is updated to `0 7 * * *`, and at cleanup deleted.

(`D13-scoring`, `D05-sources`)

(`D08-pages`)

**The failure case** edits the services file's `scrapes` entry to name a socket nothing listens on and restarts candidates, since the passes' client is built at the start (`D03-serve`); restores it and restarts again afterwards. With scrapes unreachable a `rebuild` and an ingest delivery each leave a pass `failed` `scrapes`, the delivery being answered `ok`, so the bus retries nothing and candidates is `ok` among events' subscribers afterwards (`D06-passes`); a judge fire, delivered by hand to the socket, ends `done`, since a judge reads nothing from scrapes.

**The scale check** follows, on candidates' database alone: candidates is stopped, 10,000 candidates with judgments and links, about one in twenty merged, 2,000 passes of the three kinds, half `done` and half `failed`, and 300 cohorts, a few with rejects, are built through a test helper with `Attach`, `JudgeAll`, `CreateCohort` and `Reject` and the file copied in (or inserted with `sqlite3`, the judgments with their `operating_key`); the helper runs `JudgeAll` with a clock a year before the check, so the stored judgments are a year old. `CANDIDATES_KEEP_PASSES` is raised to 1000 in candidates' environment so the start's prune (`D06-passes`) keeps every seeded pass and deep `passes` pages can be measured, and candidates is started; the start judges nothing (`D03-serve`), so a cohort shows the year-old numbers. The three list tools and the landing are timed for a first, a deep and a filtered page, `cohort` and the cohort page for a cohort with no filters and for cohorts carrying each filter and a non-default order, resident memory is read before and after 100 reads, and `sqlite3` gives `EXPLAIN QUERY PLAN` for each window's statement and for the cohort read with its bound values. A judge fire then rewrites every judgment, and a cohort's numbers are compared before and after it: they move only at the judge, the seeded filings' `fmcsa_active` weights now measured at the day of the check. Cleanup deletes the trigger, empties candidates' database, leaves scrapes' runs in place for the next check, and restores `CANDIDATES_KEEP_PASSES`.

These steps are the delivery's: no permitted test reaches the real scrapes, cron, events, the gateway, FMCSA or the SBA, so no requirement states the counts of the held runs or the trigger; the requirements below and those of `D06-passes` state the chain's behaviour through the binary's seam, over a fake scrapes, and every item of the verification list is proved by the requirements of the documents it names.

## On `us`

The delivery carries this change to `us` itself, after the sandbox check, in this order (the change's Sequence and Finish line):

1. Build: the build run closes the gap and the gates pass.
2. Sandbox: `sandbox up` and the check above.
3. Land: the branch onto `main` with `git fetch . <branch>:main`.
4. Tag: a release tag on `main`.
5. Push: `main` and the tag to origin.
6. Deploy: `devctl deploy us <tag>`.
7. Rebuild on `us`: a `rebuild`, which rereads the current FMCSA and PPP runs and writes every judgment and estimate under the release's rules, as a change of rules version needs, and gives every link stored by an earlier release its fleet verdict and counts, which the release before wrote none of.
8. Smoke: the test below.

The trigger `judge_candidates` the owner created on `us` stays as it is. The smoke test goes through the gateway's tools and the pages at `https://candidates.us.ikigenba.dev`:

- the rebuild of step 7 ends `done`; `candidate` for `cand_57ae04308642fbc0` (Stan Koch & Sons Trucking) answers the rules version the release declares and `fleet_verdict` `pass`; `candidate` for `cand_36116db1b28ab49c` (Northland Irrigation, PPP-only) answers `fleet_verdict` `unknown`.
- `create_cohort` named `Trucking and construction, $5M to $10M, 2 hours`, with revenue 5,000,000 to 10,000,000, `max_minutes` 120, the categories `trucking and logistics` and `construction`, and size 30; `cohort` answers 30 members and a `matching` above 30.
- `reject` one member with a reason; `cohort` shows a replacement among the members and the reject among its rejects; `unreject` it.
- `exclude` one member with a reason; it leaves the cohort; `include` it; it returns.
- `cohorts` lists the cohort; the landing and the cohort page show it.

The smoke test may create and delete whatever cohorts it needs. It leaves the named cohort above in place as the owner's first cohort to groom and deletes any other it made; the reject, un-reject, exclude and include records it wrote stay, as every such record does, with the candidate it touched back where it started. The change is finished when the release is deployed on `us`, the smoke test has passed and the named cohort is in place; nothing is left for the owner to do.

## Trust

candidates believes the identity it is sent, as every sibling does: `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx or the gateway set them on a request to its socket. It checks them against nothing and asks auth nothing; a `rebuild` is recorded as started by the user the request names, and a ruling as made by that user, and a `rebuild`'s reads of scrapes forward that identity, as every sibling call forwards its caller. It takes a delivery at `POST /events` from any process that can reach its socket, with no identity at all, as appkit's delivery handler admits it (`D03-serve`, `D07-events`). A delivered `scrape.finished` starts an ingest pass that no person started, and scrapes' read path requires an identity, so that pass reads scrapes as the **service identity**: `X-User-Id` `candidates`, no email, the delivery's request id, with the bus event as cause (decision 12, `D06-passes`). scrapes trusts any process at its socket, so the read is answered, and scrapes' trail records `candidates` as its user: the first service-to-service call in the suite made as no person. A delivered `cron.judge_candidates.fired` starts a judge pass that no person started either; it reads nothing and calls no sibling, so it names no identity to anyone. A process that can reach candidates' socket can therefore name any user, start a rebuild or make a ruling as that user, start a judge, and read every candidate; every service on the host is trusted, and the gateway and nginx are the only doors from outside, nginx refusing the bus's two paths there.

## Recorded decisions

- **Trust is stated as the design's own decision** (decision 21), as scrapes' on-a-space design records its own: the suite's identity model is that auth answers nginx's subrequest and the gateway forwards the caller, and a service that re-checked would ask auth on every call for nothing nginx has not already decided; the evidence candidates holds is copied from public records and belongs to the funnel, not a user (decision 14), so a forged identity reads nothing it could not read signed in; what it can do, a rebuild, a judge or a ruling, is bounded (one pass at a time; a judge recomputes from what is stored and loses nothing; rulings are never overwritten and are recorded with the identity that made them).
- **The service identity is a marked decision** (decision 12): a pass a delivery started has no person behind it, and inventing one (the run's starter from `scrape.finished`) would record a person as having read what they did not ask for; `candidates` names the reader truthfully. It is stated here, at the binary's seam, and in `D06-passes`, at the engine's.
- **The judge trigger is the owner's, created through cron's published tools**, as the scrape triggers are: candidates accepts `cron.judge_candidates.fired` and never calls cron, so its schedule is visible, pausable and changeable where every other schedule in the suite is, and candidates keeps the services file use it had: R-WBVO-DL78 shows the tools, the pages, a rebuild and an ingest delivery call no `cron` entry, and that the judge path calls no sibling is `D06-passes`' judge run-seam requirement and `D09-trail`'s. A space without the trigger still judges on `rebuild` and on rulings. The schedule `0 7 * * *` follows the scrapes' 06:00 triggers so a day's ingests are judged the same morning; its hour is the owner's to change.
- **The chain through the binary for the judge is `D06-passes`'**, beside its seam requirement for the ingest (R-ZQSD-5O4D): a `POST /events` delivering `cron.judge_candidates.fired` answered `ok`, a pass of kind `judge` with trigger `judge_candidates` then `done`, and no request to scrapes. This document adds no requirement of its own for it, and its eight requirements are unchanged by the change to two judgments: an ingest pass's counts, the rebuild's recorded identity, the ruling's identity, the scrapes failure and the sibling entries a served process leaves alone all hold as they were. The cohorts change re-mints only the last, as R-WBVO-DL78, since the tools it calls are now fifteen and the pages it asks gain a cohort path, and it has every call and page reach the store rather than stop at a refusal before it: the other fourteen tools run in a fixed order after a `rebuild` is `done`, with arguments `D10-tools` accepts (a non-blank `why`, a `decide` kind of `merge` or `not_same` over two distinct active candidates, since a split the test could make of a one-link candidate would name every link and be refused); `pass` and the pass path name the rebuild's pass; `candidate` and `decide` name candidates the `candidates` call answered, whoever created them, so the delivery may come at any point; `exclude`, `include`, `reject`, `unreject` and the candidate path name a candidate still active after the `decide`, `include` the one `exclude` named and `unreject` the pair `reject` named; every cohort tool but `create_cohort`, and the cohort path, name the one cohort `create_cohort` made; `edit_cohort` renames it, so the edit writes; and `delete_cohort` comes after the cohort path is asked; the cohorts, rejects and the `exclude` and `include` tools read and write candidates' own database and call no sibling.
- **The verification list runs in the sandbox over rows the tests build**, as the change asks: the real runs cannot be made to hold a row with a given status, date or amount, so the helper builds the rows, reads them through the release's sources and attaches them, and the sandbox's own trigger fire judges them; the real runs check the chain, the counts and the scale. The cohort items run over a database holding the helper's rows alone, not a copy of the chain's: a cohort answers at most 100 members, so over the real runs a helper-built candidate could pass a filter and still fall past the size cut, and V1's whole set could not be counted.
- **The manifest is `D02-cli`'s and the fragment this document's**, as `D02-cli` divides them; this document states no manifest requirement of its own.
- **The services file gives scrapes' socket**, with events', telemetry's and auth's (decision 17); a requirement here proves no other entry is called, which is also the evidence that candidates asks auth nothing and cron nothing on those paths; a judge pass's calling nothing is `D06-passes`' and `D09-trail`'s.
- **The sandbox check restarts candidates around the failure case**: the passes' scrapes client is built from the entry the services file names at the start (`D03-serve`), so an entry edited while candidates runs is not seen until the next start.
- No release is named in the manifest or in any requirement, and no requirement or check spells the rules version: each reads the one the release declares (`sources.Rules`); the release number and the deploy are the delivery's. The change's "rules version 4" is the value `D13-scoring` gives `sources.Rules`, so the smoke test's "the rules version the release declares" is that 4 without this document going stale at the next.
- **The delivery deploys and smokes this change itself** (the change's Sequence and Finish line, and its decisions log): the judgments change left landing, deploying, the rebuild and the smoke to the owner; this one ends with the release on `us`, the rebuild done, the smoke passed and the first cohort in place, so the steps are listed here in order, without the release number, which the log records. The rebuild is in the list because the three-valued verdict and its counts come from the reading of a link (`D05-sources`): a link stored by the release before carries none until a rebuild rereads it, and every judgment and estimate must carry the new rules version.
- **The smoke test leaves one cohort**, the owner's first to groom, and deletes any other it made; its reject and exclusion records stay, since such records are never deleted (`D14-cohorts`), with the standing state they touched restored by the un-reject and the include.

An operator installs the release; opsctl reads `etc/manifest.toml`, writes `CANDIDATES_KEEP_PASSES` and `DRAIN_SECONDS` into `/etc/opt/ikigenba/candidates/env`, drops `etc/nginx.conf` into candidates' server, adds candidates' entry to the services file and starts the unit. A test reads `nginx.conf` from the root package's `Etc()` with `fs.ReadFile` and compares it with `cli.NginxConf`. A test builds a `cli.Process` with a temporary `Dir`, a services file whose entry `scrapes` names a Unix socket on which a fake scrapes serves a `done` run of `fmcsa` and its rows, answers 404 for any other scraper's current run, and records every request, whose entries `auth`, `artifacts`, `connections`, `cron` and `gdrive` name sockets on which fakes record every request, captures as sinks, and its own `Now`, `After` and `Rand`; it posts a delivery of `scrape.finished` to `/events`, calls `rebuild` and, once its pass is `done`, each of the other fourteen tools through `mcp.Client` with identity headers of its choosing, in the order R-WBVO-DL78 gives (the candidate tools on candidates `candidates` answered, `decide` a `merge` or `not_same` of two distinct ones, those after `decide` on one still active, `include` and `unreject` on what `exclude` and `reject` named, `pass` on the rebuild's pass, the cohort tools on the cohort `create_cohort` made, `edit_cohort` renaming it), asks the pages, the cohort's, an active candidate's and the pass's paths among them, before `delete_cohort`, waits for the passes to end, cancels, and checks the pass records, the requests the fake scrapes received with their identity headers, and that the other fakes received nothing.
