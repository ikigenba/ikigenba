# D11-on-a-space

What candidates contributes when it runs on a space and in a sandbox: what ships, the manifest and the nginx fragment, which entries of the services file it uses, the cron trigger the owner creates for the daily judge, the trust it places in the identity it is sent and the identity it sends scrapes (decisions 12 and 21), and which of the contract's guarantees the delivery's sandbox check (decision 20) and the `us` smoke test stand on. It follows scrapes' on-a-space design. The guarantee such documents end with, that no business name, address, phone, email, person or ruling text reaches the trail, the bus, a refusal or standard error, is `D09-trail`'s here, as it is scrapes' trail document's there.

## What ships

The release holds four members of candidates' directory: `bin/candidates`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `filter`, human-authored (decision 1). No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The two files under `etc/` are what the root package's `Etc` embeds (`D01-layout-and-run-seam`): `etc/manifest.toml` holds the bytes of `cli.Manifest`, which `D02-cli` states byte for byte with the command that prints it, and `etc/nginx.conf` the bytes of `cli.NginxConf`, which this document states. `share/zip_drive.csv` ships inside the binary, embedded by the root package (`D01-layout-and-run-seam`), not beside it.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox and home read it, so its text is contract, stated byte for byte as `cli.Manifest` in `D02-cli`, which also compares its description with `pages.Description` and its `[env]` with `settings.Defaults()`. What a space takes from it: it names the app `candidates`; its description, decision 1's text, the same as `pages.Description`; that it is not the default app; that it is an MCP service (`mcp = true`), so the gateway offers the seven tools; that it does not serve guests (`guests = false`), so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); no secrets, since candidates holds none of its own and calls nothing outside the suite; an `[env]` table whose one line is `CANDIDATES_KEEP_PASSES = "20"` (decision 17), so the value the host writes into candidates' environment is the one candidates applies when the setting is unset; the `[database]` table that has the host keep and replicate `state/candidates.db`; a `[resources]` table whose only line is `memory_max = "256M"`, room enough since a run's rows are streamed and handled a batch at a time (decision 1); and, last, a `[home]` table whose only line is `group = "application"`, so home lists candidates under Application. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app, and `settings.Read` defaults it to 5 (`D01-layout-and-run-seam`). The change to two judgments and the PPP reader changes nothing in the manifest.

## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. Nothing else is held back; candidates has no sibling read path, so the public name serves the pages and `/mcp`, behind auth.

## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a rebuild read, `events` and `telemetry`, appkit's sinks', and `auth`, for the banner's addresses (decision 17); it calls no other sibling and nothing outside the host. A missing file or entry never refuses the start (`D03-serve`). The host must run events, which delivers `scrape.finished` and `cron.judge_candidates.fired` to candidates and takes its pass events; scrapes, which it reads; and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored judgments as the last judge wrote them; nothing else decays them, and `rebuild` judges on demand. candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `rebuild` and on rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]`, puts every request through auth's `/check`, and includes `etc/nginx.conf` in candidates' server. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools, and the gateway's `call` of cron's tools for the trigger.

**The chain.** In the sandbox where scrapes' database was emptied after its own check: `scrape` of `fmcsa` lands a run of about 16,700 rows; within a minute `passes` shows an ingest pass with that run as trigger, `done`, `new` equal to the run's `rows`, `created` close to it and `judged` 0, and `shortlist` still answers an empty list. `scrape` of `ppp` lands a run of about 37,081 rows and its ingest pass likewise. The trigger `judge_candidates` is created with cron's `create` on a schedule a minute away; events' `subscribers` is observed to list candidates `ok` for `cron.judge_candidates.fired`; the fire is observed to start a judge pass that ends `done` with `judged` equal to the live candidates, and the shortlist then holds them, ranked by `operating_confidence`; the trigger stays in place for the verification list, whose judges it fires. A `rebuild` then ends `done` as one pass of kind `rebuild`.

**The verification list** (the change's Verification section, numbered V1 to V11 as the change's vocabulary numbers it), run in the sandbox over rows the tests build: candidates is stopped, a test helper builds the rows each item names as `scrapes.Row` values, reads each through the release's own sources (`fmcsa.New().Read`, `ppp.New().Read`), hands them to a store over a copy of candidates' database with `Attach`, and the file is copied back; candidates is started and the trigger is updated with cron's `update` to a schedule a minute away, as scrapes' check does, so its fire judges them (or, where cron cannot be waited on, `cron.judge_candidates.fired` is delivered by hand to candidates' socket at `POST /events`); each item is then read through `candidate`, `shortlist` and `decide` over the gateway. The items run in order, V1 to V8 read before anything V9 to V11 do: an ingest of a run marks gone every link of its scraper that the run does not hold (`D12-resolution`), so V9's real `scrape` of `fmcsa` and V11's `rebuild` mark the helper-built links gone, and V1 to V8 must have been read by then. V10's fire is caused the same way, by a schedule a minute away or a delivery by hand. After V11 the trigger is updated to `0 7 * * *`, and at cleanup deleted. The helper sets each row's dates relative to the day the check runs, so each item's freshness is the one it names on that day.

**The failure case** edits the services file's `scrapes` entry to name a socket nothing listens on and restarts candidates, since the passes' client is built at the start (`D03-serve`); restores it and restarts again afterwards. With scrapes unreachable a `rebuild` and an ingest delivery each leave a pass `failed` `scrapes`, the delivery being answered `ok`, so the bus retries nothing and candidates is `ok` among events' subscribers afterwards (`D06-passes`); a judge fire, delivered by hand to the socket, ends `done`, since a judge reads nothing from scrapes.

**The scale check** follows, on candidates' database alone: candidates is stopped, 10,000 candidates with judgments and links, about one in twenty merged, and 2,000 passes of the three kinds, half `done` and half `failed`, are built through a test helper with `Attach` and `JudgeAll` and the file copied in (or inserted with `sqlite3`, the judgments with their `operating_key`); the helper runs `JudgeAll` with a clock a year before the check, so the stored judgments are a year old. `CANDIDATES_KEEP_PASSES` is raised to 1000 in candidates' environment so the start's prune (`D06-passes`) keeps every seeded pass and deep `passes` pages can be measured, and candidates is started; the start judges nothing (`D03-serve`), so the landing shows the year-old numbers. The three tools and the landing are timed for a first, a deep and a filtered page, resident memory is read before and after 100 page reads, and `sqlite3` gives `EXPLAIN QUERY PLAN` for each window's statement with its bound values. A judge fire then rewrites every judgment, and the landing's numbers are compared before and after it: they move only at the judge, the seeded filings' `fmcsa_active` weights now measured at the day of the check. Cleanup deletes the trigger, empties both databases and restores `CANDIDATES_KEEP_PASSES`.

These steps are the delivery's: no permitted test reaches the real scrapes, cron, events, the gateway, FMCSA or the SBA, so no requirement states the counts of the real runs or the trigger; the requirements below and those of `D06-passes` state the chain's behaviour through the binary's seam, over a fake scrapes.

## Trust

candidates believes the identity it is sent, as every sibling does: `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx or the gateway set them on a request to its socket. It checks them against nothing and asks auth nothing; a `rebuild` is recorded as started by the user the request names, and a ruling as made by that user, and a `rebuild`'s reads of scrapes forward that identity, as every sibling call forwards its caller. It takes a delivery at `POST /events` from any process that can reach its socket, with no identity at all, as appkit's delivery handler admits it (`D03-serve`, `D07-events`). A delivered `scrape.finished` starts an ingest pass that no person started, and scrapes' read path requires an identity, so that pass reads scrapes as the **service identity**: `X-User-Id` `candidates`, no email, the delivery's request id, with the bus event as cause (decision 12, `D06-passes`). scrapes trusts any process at its socket, so the read is answered, and scrapes' trail records `candidates` as its user: the first service-to-service call in the suite made as no person. A delivered `cron.judge_candidates.fired` starts a judge pass that no person started either; it reads nothing and calls no sibling, so it names no identity to anyone. A process that can reach candidates' socket can therefore name any user, start a rebuild or make a ruling as that user, start a judge, and read every candidate; every service on the host is trusted, and the gateway and nginx are the only doors from outside, nginx refusing the bus's two paths there.

## Recorded decisions

- **Trust is stated as the design's own decision** (decision 21), as scrapes' on-a-space design records its own: the suite's identity model is that auth answers nginx's subrequest and the gateway forwards the caller, and a service that re-checked would ask auth on every call for nothing nginx has not already decided; the evidence candidates holds is copied from public records and belongs to the funnel, not a user (decision 14), so a forged identity reads nothing it could not read signed in; what it can do, a rebuild, a judge or a ruling, is bounded (one pass at a time; a judge recomputes from what is stored and loses nothing; rulings are never overwritten and are recorded with the identity that made them).
- **The service identity is a marked decision** (decision 12): a pass a delivery started has no person behind it, and inventing one (the run's starter from `scrape.finished`) would record a person as having read what they did not ask for; `candidates` names the reader truthfully. It is stated here, at the binary's seam, and in `D06-passes`, at the engine's.
- **The judge trigger is the owner's, created through cron's published tools**, as the scrape triggers are: candidates accepts `cron.judge_candidates.fired` and never calls cron, so its schedule is visible, pausable and changeable where every other schedule in the suite is, and candidates keeps the services file use it had: R-7F2X-NSFH shows the tools, the pages, a rebuild and an ingest delivery call no `cron` entry, and that the judge path calls no sibling is `D06-passes`' judge run-seam requirement and `D09-trail`'s. A space without the trigger still judges on `rebuild` and on rulings. The schedule `0 7 * * *` follows the scrapes' 06:00 triggers so a day's ingests are judged the same morning; its hour is the owner's to change.
- **The chain through the binary for the judge is `D06-passes`'**, beside its seam requirement for the ingest (R-ZQSD-5O4D): a `POST /events` delivering `cron.judge_candidates.fired` answered `ok`, a pass of kind `judge` with trigger `judge_candidates` then `done`, and no request to scrapes. This document adds no requirement of its own for it, and its eight requirements are unchanged by the change to two judgments: an ingest pass's counts, the rebuild's recorded identity, the ruling's identity, the scrapes failure and the sibling entries a served process leaves alone all hold as they were.
- **The verification list runs in the sandbox over rows the tests build**, as the change asks: the real runs cannot be made to hold a row with a given status, date or amount, so the helper builds the rows, reads them through the release's sources and attaches them, and the sandbox's own trigger fire judges them; the real runs check the chain, the counts and the scale.
- **The manifest is `D02-cli`'s and the fragment this document's**, as `D02-cli` divides them; this document states no manifest requirement of its own.
- **The services file gives scrapes' socket**, with events', telemetry's and auth's (decision 17); a requirement here proves no other entry is called, which is also the evidence that candidates asks auth nothing and cron nothing on those paths; a judge pass's calling nothing is `D06-passes`' and `D09-trail`'s.
- **The sandbox check restarts candidates around the failure case**: the passes' scrapes client is built from the entry the services file names at the start (`D03-serve`), so an entry edited while candidates runs is not seen until the next start.
- No release is named in the manifest or in any requirement, and no requirement or check spells the rules version: each reads the one the release declares (`sources.Rules`); the release number and the deploy are the delivery's.

## Consumer tasks

An operator installs the release; opsctl reads `etc/manifest.toml`, writes `CANDIDATES_KEEP_PASSES` and `DRAIN_SECONDS` into `/etc/opt/ikigenba/candidates/env`, drops `etc/nginx.conf` into candidates' server, adds candidates' entry to the services file and starts the unit. The owner creates the trigger `judge_candidates` with cron's `create` through the gateway. A test reads `nginx.conf` from the root package's `Etc()` with `fs.ReadFile` and compares it with `cli.NginxConf`. A test builds a `cli.Process` with a temporary `Dir`, a services file whose entry `scrapes` names a Unix socket on which a fake scrapes serves a `done` run of `fmcsa` and its rows, answers 404 for any other scraper's current run, and records every request, whose entries `auth`, `artifacts`, `connections`, `cron` and `gdrive` name sockets on which fakes record every request, captures as sinks, and its own `Now`, `After` and `Rand`; it posts a delivery of `scrape.finished` to `/events`, calls the tools through `mcp.Client` with identity headers of its choosing, asks the pages, waits for the passes to end, cancels, and checks the pass records, the requests the fake scrapes received with their identity headers, and that the other fakes received nothing.

- R-743U-7UR8: The `internal/cli` package MUST export `const NginxConf = "location = /events { return 404; }\nlocation = /declarations { return 404; }\n"`.
- R-75BQ-LMHX: The contents of `nginx.conf` in the file system the root package's `Etc` returns (`D01-layout-and-run-seam`) MUST be exactly the bytes of `cli.NginxConf`.
- R-76JM-ZE8M: candidates' design defines a **fake run** of `n` rows as a fake scrapes serving, on the Unix socket a services file's entry `scrapes` names, a run whose record has the `id` `<r>`, the `scraper` `fmcsa`, the `status` `done` and `rows` `n`, at `/runs/<r>/record`, at `/scrapers/fmcsa/current`, and, at `/runs/<r>/rows`, `n` rows of the scraper `fmcsa` and the run `<r>` whose `source_id`s are distinct; every requirement of candidates' design naming a fake run MUST denote such a fake.
