## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a full ingest read; `prompts`, whose socket a pass of kind `enrich_target` walking a prompts kind, `site_text`, `website_search` or `brief`, calls as the caller of the `enrich`, through appkit's `prompts` client, which the start builds from the entry (`D03-serve`, `D06-passes`); `events` and `telemetry`, appkit's sinks'; `auth`, for the banner's addresses (decision 17); and `campaigns`, whose URL alone builds the candidate page's link to each campaign's page, its socket never dialled (`D01-layout-and-run-seam`, `D08-pages`); it calls no other sibling, campaigns included. Outside the host it reaches only the public websites the website check, `add_page` and the website search's confirmation fetch, through the real fetcher, which follows no proxy and refuses loopback, private, link-local and unspecified addresses (`D15-website-check`); the agent of a `site-text` run crawls a company's site from prompts, not from candidates, and names the pages worth keeping back through the gateway's `add_page`, which candidates then fetches itself; the agent of a `website-search` run searches the web from prompts, with the `web` tool group prompts runs it with, never from candidates, and names one URL in its answer, which candidates fetches once under `D15-website-check`'s rules before it records it (website search decisions 4 and 5); the agent of a `brief` run is given the pages in its input and calls nothing. It reaches one service outside the suite: a pass of kind `enrich_target` walking `drive_route` asks Google's geocoding and routing services through the routes client, over the process's outbound HTTP client (`D17-drive-route`, `D01-layout-and-run-seam`), at most `passes.RoutesInFlight` requests at once, each carrying the key and the address strings and coordinates `D17-drive-route` gives, and no identity of the suite's; no other pass, the corpus enrich and an `enrich` with no kind among them, sends a request to the routing service (`D06-passes`). A missing file or entry never refuses the start (`D03-serve`); with no `prompts` entry, `site_text`, `website_search` and `brief` are `unavailable` and every other kind runs as before (site text decision 21), and with no fetcher `website_search` is `unavailable` too, as `website_check` is (`D16-enrichers`); with `GOOGLE_MAPS_API_KEY` unset or empty the start still serves, and an `enrich` of `drive_route` with a target is `invalid` with `passes.NoRouteKey`'s text while every other kind runs as before (drive route decision 13, `D06-passes`), a state a sandbox never reaches, since `sandbox up` refuses a listed secret that is unset or empty, and a space reaches only when an empty key was pushed, since opsctl's activation refuses a listed secret only when it is absent from the space's object. The host must run events, which delivers `scrape.finished`, `cron.judge_candidates.fired` and campaigns' three events to candidates and takes its pass events; scrapes, which it reads; prompts, which runs each `site-text`, `website-search` and `brief` run and in which the owner keeps the prompts of those names, a `website-search` run reaching the web through prompts' `web` tool group, since candidates knows no prompt's model, instructions or tools (site text decision 7); and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`). So with campaigns, which emits `campaign.member.added`, `campaign.member.rejected` and `campaign.piece.delivered` as its `add_member`, `add_prospect_list`, `reject`, `deliver` and `deliver_channel` change a campaign: candidates accepts each by its exact name and never calls campaigns. A host without campaigns leaves every candidate's campaigns empty, and a services file with no `campaigns` entry has the candidate page draw each campaign's id unlinked; neither refuses anything (`D03-serve`, `D08-pages`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored opinions as the last judge wrote them, while the facts still move at each enrich that writes a result (`D16-enrichers`); nothing decays either, and `judge`, or a full `ingest`, judges on demand (funnel rename decision 10). candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `judge`, a full `ingest` and rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]`, `IKIGENBA_SANDBOX`, which it sets for every app, and the two secrets the manifest lists, each read from the variable of the same name in the environment `sandbox up` runs with; puts every request through auth's `/check`; and includes `etc/nginx.conf` in candidates' server. `sandbox up` starts nothing while a secret some manifest lists is unset or empty: it names every missing one with the variable it is read from and stops. So since the exact drive time a developer exports both before `sandbox up`: `GOOGLE_MAPS_API_KEY`, which the owner's keyring gives every new shell (drive route prerequisites), and `CANDIDATES_ROUTE_ORIGIN` as `Sandstone, MN`, the default and the ZIP table's own origin, so a sandbox's routes are measured from where its ZIP estimates are. A changed value reaches candidates at the next `sandbox up`, which reads the secrets again. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools. The sandbox stands up every app whose directory in the worktree holds `etc/manifest.toml`, so it runs a real scrapes, a real prompts and a real campaigns as well: the check ingests the real scrapes' runs, the services file's `scrapes` entry naming a stand-in only for the fixture items, no exercise calls prompts, and no exercise makes a campaign.

**The stand-in fetcher.** With `IKIGENBA_SANDBOX` present, whatever its value, candidates fetches websites through the in-process loopback stub `D15-website-check` declares, and through nothing else (website log P2, revised): the website check's fetches, `add_page`'s and the website search's confirmations alike. The stub listens on two loopback ports, one plain and one TLS, and its client dials one of them whatever host a request names, so no fetch in a sandbox leaves the machine: not the verification list's and not one an ingest starts on its own. It answers by domain: a host under `.test`, a name reserved never to resolve in public DNS (RFC 2606, RFC 6761), whose first label (after one leading `www.`) is one of the stub's keywords, or a keyword followed by `-` and anything, gets that keyword's behaviour (`secure`, `plain`, `prefixed`, `upgrade`, `away`, `missing`, `empty`, `binary`, `refused`, `slow`, `big` and `loop`), and every other host is refused at once, so the real runs' domains each come out `none` without a byte sent and gain no evidence, the check's `none` leaving each company's website `unknown` (website states outcome 2). The keywords, their answers and the results they give are `D15-website-check`'s stub table. The stub is unchanged by this change: the real FMCSA rows carry emails, so the follow-on enrich of each ingest checks their domains through it, each coming out `none` at once and its website `unknown`; the fixture's rows carry none; and no exercise adds a page or runs a search.

**No stand-in routing service, and no route.** The stub is the website fetcher's alone: with `IKIGENBA_SANDBOX` present the routes client is still the real one, over the process's outbound HTTP client (`D01-layout-and-run-seam`), so a `drive_route` pass in a sandbox reaches Google and is charged for. This change adds no kind and routes nothing, so no exercise runs `enrich` of `drive_route` and nothing in the check reaches Google, which V14 shows.

**The real runs.** The companies the check reads, Hjort Excavating, KTM Paving, Design Ready Controls, Rosenbauer Minnesota, Molin Concrete, a school district and a row with nonsense figures, are real ones the OSHA ITA document names from the real rows, and the full ingest over every real run is the change at its real size, so the check reads the sandbox's scrapes as it stands: it must hold a `done` current run of each of `fmcsa`, `ppp`, `form5500` and `osha_ita`, the last a real OSHA ITA run of every file the scraper's setting names, the one scrapes' own check landed or, when scrapes holds none, one the delivery lands with scrapes' `scrape` tool through the gateway before the baseline, as it does for any other scraper without one. No scrape is started from then until cleanup, so every full ingest reads the same rows and no `scrape.finished` reaches candidates meanwhile but those the check delivers by hand.

**The stand-in scrapes.** The fixture items need rows built to the EINs, names, years, figures, states and ZIPs each item names, the only candidates in the database so that a pass's counts are known, and no email; the real runs hold none chosen. **No stand-in prompts.** The change adds no prompts kind and no exercise runs one, so nothing in the check calls prompts and its entry is left as the sandbox wrote it; V14 shows nothing reached it.

**The swap**: the sandbox's services file's `scrapes` entry is edited to name the stand-in's socket and candidates is restarted, since the client is built from the entry at the start (`D03-serve`); afterwards the entry is restored and candidates restarted again. The file is shared and the gateway reads it on every request, so during the swap the gateway's `scrapes` is the stand-in too, and no tool of the real scrapes is called through the gateway then. `sandbox up` rewrites the file from the manifests, so every `sandbox up` of the check undoes the swap, which is then made again. scrapes' own runs are left as they are.
