# D11-on-a-space

What candidates contributes when it runs on a space and in a sandbox: what ships, the manifest and the nginx fragment, which entries of the services file it uses, the cron trigger the owner creates for the daily judge, the trust it places in the identity it is sent and the identity it sends scrapes (decisions 12 and 21), which of the contract's guarantees the delivery's sandbox check (decision 20) and the `us` smoke test stand on, and how the enrichers (`D16-enrichers`) reach a space: the derived kinds read only candidates' own database, and the website check (`D15-website-check`), the one fetched kind, fetches through a stand-in in a sandbox and through the real fetcher on `us`. It follows scrapes' on-a-space design. The guarantee such documents end with, that no business name, address, phone, email, person or ruling text reaches the trail, the bus, a refusal or standard error, is `D09-trail`'s here, as it is scrapes' trail document's there.

## What ships

The release holds four members of candidates' directory: `bin/candidates`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `filter`, human-authored (decision 1). No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The two files under `etc/` are what the root package's `Etc` embeds (`D01-layout-and-run-seam`): `etc/manifest.toml` holds the bytes of `cli.Manifest`, which `D02-cli` states byte for byte with the command that prints it, and `etc/nginx.conf` the bytes of `cli.NginxConf`, which this document states. `share/zip_drive.csv` ships inside the binary, embedded by the root package (`D01-layout-and-run-seam`), not beside it.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox and home read it, so its text is contract, stated byte for byte as `cli.Manifest` in `D02-cli`, which also compares its description with `pages.Description` and its `[env]` with `settings.Defaults()`. What a space takes from it: it names the app `candidates`; its description, the same as `pages.Description`; that it is not the default app; that it is an MCP service (`mcp = true`), so the gateway offers the sixteen tools (`D10-tools`); that it does not serve guests (`guests = false`), so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); no secrets, since candidates holds none of its own and calls no service outside the suite, its one outside traffic, the website check's fetches of public sites, needing no credential; an `[env]` table whose one line is `CANDIDATES_KEEP_PASSES = "20"` (decision 17), so the value the host writes into candidates' environment is the one candidates applies when the setting is unset; the `[database]` table that has the host keep and replicate `state/candidates.db`; a `[resources]` table whose only line is `memory_max = "256M"`, room enough since a run's rows are streamed and handled a batch at a time (decision 1); and, last, a `[home]` table whose only line is `group = "application"`, so home lists candidates under Application. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app, and `settings.Read` defaults it to 5 (`D01-layout-and-run-seam`). The change to two judgments and the PPP reader changes nothing in the manifest; the cohorts change alters only its description, which no longer speaks of a ranking against the fit test (`D02-cli`, with `pages.Description` in `D01-layout-and-run-seam`). The website check changes nothing in it (decisions log P2, revised): the stand-in fetcher is chosen by `IKIGENBA_SANDBOX`, which the sandbox sets for every app and `us` never sets, so no `[env]` line is needed, and none could be sandbox-only, since the sandbox renders an app's environment from the same `[env]` table `us` reads; and `memory_max` still holds, since an enrich pass holds no more than the fetches in flight and one batch of candidates (`D15-website-check`). The enrichers change nothing in it either: the derived kinds read only candidates' own database, a batch of candidates at a time, and need no setting, secret or outside address (`D16-enrichers`, `D06-passes`).

## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. Nothing else is held back; candidates has no sibling read path, so the public name serves the pages and `/mcp`, behind auth.

## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a rebuild read, `events` and `telemetry`, appkit's sinks', and `auth`, for the banner's addresses (decision 17); it calls no other sibling. Outside the host it reaches only the public websites the website check fetches, through the real fetcher, which follows no proxy and refuses loopback, private, link-local and unspecified addresses (`D15-website-check`). A missing file or entry never refuses the start (`D03-serve`). The host must run events, which delivers `scrape.finished` and `cron.judge_candidates.fired` to candidates and takes its pass events; scrapes, which it reads; and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored opinions as the last judge wrote them, while the facts still move at each enrich that writes a result (`D16-enrichers`); nothing decays either, and `rebuild` judges on demand. candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `rebuild` and on rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]` and `IKIGENBA_SANDBOX`, which it sets for every app, puts every request through auth's `/check`, and includes `etc/nginx.conf` in candidates' server. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools, and the gateway's `call` of cron's tools for the trigger.

**The stand-in fetcher.** With `IKIGENBA_SANDBOX` present, whatever its value, candidates checks websites through the in-process loopback stub `D15-website-check` declares, and through nothing else (decisions log P2, revised). The stub listens on two loopback ports, one plain and one TLS, and its client dials one of them whatever host a request names, so no fetch in a sandbox leaves the machine: not the verification list's and not one an ingest starts on its own. It answers by domain: a host under `.test`, a name reserved never to resolve in public DNS (RFC 2606, RFC 6761), whose first label (after one leading `www.`) is one of the stub's keywords, or a keyword followed by `-` and anything, gets that keyword's behaviour (`secure`, `plain`, `prefixed`, `upgrade`, `away`, `missing`, `empty`, `binary`, `refused`, `slow`, `big` and `loop`), and every other host is refused at once, so the real runs' domains each come out `none` without a byte sent and gain no evidence, and the checks of earlier changes keep their confidences. The keywords, their answers and the results they give are `D15-website-check`'s stub table; the list below names domains by keyword, `secure-a.test` being a `secure` domain, and expects the results that table gives. A `slow` domain answers nothing until each attempt's ten-second timeout, so a pass that holds one runs for at least four times that, which the list uses to hold an enrich pass running.

**The baseline.** The comparisons the change asks for (V7 to V10) need what the previous release wrote over the same candidates, so they are taken first, and they need this worktree's sandbox still running the previous release, as its check left it: the release in candidates' footer is read before anything else, and if it is not the previous release the delivery stops and asks, since only this sandbox holds the held runs and the file the upgrade restarts over, and no `sandbox up` of this release may come before the baseline. No scraper is run against an outside source: the sandbox uses the runs of `fmcsa` and `ppp` scrapes already holds from earlier checks, as the change's Sequence says. With candidates stopped and its database emptied, then started: a `scrape.finished` naming the held `fmcsa` run, `done`, is delivered by hand to candidates' socket at `POST /events`, and, once its ingest is `done`, one naming the held `ppp` run; the enrich the first ingest starts checks the real own-domain candidates through the stub, each `none`, at the steady pace, and once the `ppp` ingest is `done` candidates is restarted, which fails that enrich `interrupted`, so some own-domain candidates hold a `none` result and the rest none at all. A `cron.judge_candidates.fired` delivered by hand then starts a judge that ends `done`. Cohorts are created: one with no filters, one for each filter, once with its unknown switch and once without, and one with an order other than the default, each of size 100; each one's `cohort` answer is saved, and so are the `candidate` answers of a sample: a candidate with a PPP link, a government-matched one when the runs hold one, and one with a `none` result. With `sqlite3`, the tables and the columns of `assessments`, `enrichments` and `passes` are saved, and so are every `assessments` row and every `enrichments` row. Nothing runs between that judge and the upgrade, so the saved judgments are the last the previous release wrote, at the day of the check.

**The upgrade.** `sandbox up` then builds this release from the worktree and restarts candidates over the same file, which the start migrates through `0012_facts.sql` and whose facts rows it fills from the stored website results before ready; V1 is read at once with `sqlite3` against what the baseline saved. Nothing fetches until the comparisons are done: the enrich calls here each name a derived kind, so the candidates the baseline's enrich never reached stay unchecked and every website fact stays as the previous release's judge wrote it. `enrich` with kind `link_facts` answers a pass `running`, which ends `done` with `derived` equal to the active candidates holding a link, counted with `sqlite3`, and every other count 0, and starts a judge, which ends `done`; `enrich` with kind `drive_minutes` then ends `done` with `derived` equal to the active candidates with a non-empty ZIP, and its judge `done` too. V7 to V10 are then read against the baseline, V11's `rebuild` follows, and the baseline's cohorts are read once more after it and deleted.

**The chain.** With candidates stopped and its database emptied, then started: a `scrape.finished` naming the held `fmcsa` run, `done`, is delivered by hand to candidates' socket at `POST /events` and answered `ok`; within a minute `passes` shows an ingest pass with that run as trigger, `done`, `new` equal to the run's `rows`, `created` close to it and `judged` 0, and beside it an `enrich` pass of origin `pass` whose trigger is that ingest pass's id, `running`. Its derived kinds end in moments, so while its website check still runs `candidate` already answers, for the candidates the ingest created, their `link_facts` and `drive_minutes` results and the facts from them, and most own-domain ones no website result yet (V5 over the real runs); a cohort created with no filters answers no members and `matching` 0 while no judge has run, since a member needs an assessment. A `scrape.finished` naming the held `ppp` run is delivered likewise; while the enrich still runs, the ppp ingest pass runs beside it, ends `done`, and starts no second enrich, so the candidates it created hold no derived result until the next enrich or rebuild. The enrich works through the run's own-domain candidates at the steady pace, about two domains a second, every result `none` from the stub's refusal; the chain does not wait for it to end. ## Trust

candidates believes the identity it is sent, as every sibling does: `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx or the gateway set them on a request to its socket. It checks them against nothing and asks auth nothing; a `rebuild` or an `enrich` is recorded as started by the user the request names, and a ruling as made by that user, and a `rebuild`'s reads of scrapes forward that identity, as every sibling call forwards its caller. It takes a delivery at `POST /events` from any process that can reach its socket, with no identity at all, as appkit's delivery handler admits it (`D03-serve`, `D07-events`). A delivered `scrape.finished` starts an ingest pass that no person started, and scrapes' read path requires an identity, so that pass reads scrapes as the **service identity**: `X-User-Id` `candidates`, no email, the delivery's request id, with the bus event as cause (decision 12, `D06-passes`). scrapes trusts any process at its socket, so the read is answered, and scrapes' trail records `candidates` as its user: the first service-to-service call in the suite made as no person. A delivered `cron.judge_candidates.fired` starts a judge pass that no person started either; it reads nothing and calls no sibling, so it names no identity to anyone. A pass another pass starts, the enrich an ingest starts or the judge an enrich starts, has no user either, carrying the starting pass's request id and cause (`D06-passes`); an enrich fetches public sites and sends them no identity. A process that can reach candidates' socket can therefore name any user, start a rebuild or an enrich or make a ruling as that user, start a judge, and read every candidate; every service on the host is trusted, and the gateway and nginx are the only doors from outside, nginx refusing the bus's two paths there.

- **Step 5 changes a candidate between two starts and holds a pass `running` by hand**: no held run can be made to change one helper candidate's email and ZIP, so the helper attaches a second reading over the stopped service's file, as a second ingest would; and over the helper's database a judge or ingest ends in moments, so no pass of the sandbox's own can be relied on to still run when an enrich ends, so a `done` pass set `running` with `sqlite3`, as the restart check already does, is seen by the store as running (`D04-store`'s busy rule) until a restart fails it `interrupted`.
