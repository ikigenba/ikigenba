# D11-on-a-space

What candidates contributes when it runs on a space and in a sandbox: what ships, the manifest and the nginx fragment, which entries of the services file it uses, the cron trigger the owner creates for the daily judge, the trust it places in the identity it is sent and the identity it sends scrapes and prompts (decisions 12 and 21, site text decisions 7 and 21), which of the contract's guarantees the delivery's sandbox check and the `us` smoke test stand on, and how the enrichers (`D16-enrichers`), seven kinds with `website_search` fourth, `brief` sixth and `drive_route` last, reach a space: the derived kinds read only candidates' own database; the website check (`D15-website-check`), `add_page` (`D10-tools`) and the website search's confirmation fetch through a stand-in in a sandbox and through the real fetcher on `us`; and the prompts kinds `site_text`, `website_search` and `brief` run the caller's prompt named for the kind, `site-text`, `website-search` or `brief`, at prompts, through a stand-in prompts in a sandbox and the real one on `us`, a `website_search` run searching the web from prompts and naming one URL back, which candidates fetches once to confirm before it records it, and a `brief` run reading the pages `site_text` kept and calling no tool, so it fetches nothing and keeps no page; and the routing kind `drive_route` asks Google, through the routes client (`D17-drive-route`) over the process's outbound HTTP client, in a sandbox and on `us` alike, for the drive by car from the base the setting `CANDIDATES_ROUTE_ORIGIN` names to a candidate's street address, only within a pass of kind `enrich_target` and only with the key `GOOGLE_MAPS_API_KEY`, the two values the manifest lists as its secrets (drive route decisions 1, 2, 4 and 13). A confirmed site the search found becomes the facts row's website, with the source `search`, as soon as its result is written, wherever the website check found none (`D04-store`, website search decision 7), so `site_text` is due for it at the owner's next ask with no other step (website search decision 8); the release adds one migration, `0015_website_search.sql`, on which the previous release, release-50, runs unchanged (website search decision 14). A good brief that gives a category decides the facts row's categories alone, each with the source `brief`, as soon as its result is written, and one that gives none leaves the link facts' standing (`D04-store`, category evidence decisions 1 and 2), so a space needs no judge to show a new brief's decision. A change to how a source reads a row reaches a space's stored readings only through an `ingest`, which rereads every row and writes `link_facts` again: so the category list's growth reached them, a government name match becoming a category from `name`, and so does this change's FMCSA reading, which gives `trucking and logistics` only to a carrier whose class is `for_hire` or `mixed` (`D05-sources`, `D16-enrichers`, `D06-passes`); the same `ingest` projects every facts row again, whether or not its link facts changed, which is how a facts row written under the earlier projection comes to follow this one (`D06-passes`, `D04-store`). Campaign history reaches a space only over the bus: campaigns emits `campaign.member.added`, `campaign.member.rejected` and `campaign.piece.delivered` as its tools change a campaign, events delivers each to candidates' socket, and candidates records the use on the candidate the event names, or the active candidate that one was merged into, starting no pass and never calling campaigns (campaigns decisions 16 and 17, campaigns log D1, `D06-passes`, `D07-events`); the services file's `campaigns` entry only builds the candidate page's link to a campaign's page, and the prospect list filter `min_campaign_age_days` reads the uses as they stand at the read (campaigns decision 18, `D14-prospect-lists`); the funnel rename adds one migration, `0017_prospect_lists.sql`, which copies the saved searches, their rejects, the campaign uses' list and the judgments into tables and columns named for the stage names and rewrites the pass words, leaving every table and column the previous release reads in place, so release-52 runs on it both ways (funnel rename decision 17, `D04-store`); candidates also answers, unlisted, the one old tool name release-52 campaigns calls, and redirects the old list path (`D10-tools`, `D08-pages`). The exact drive time adds one migration, `0018_drive_route.sql`, an expand that gives the facts table the minutes' source, the route's miles and resolved address and the route kind's time, and marks every row that holds minutes as decided by the ZIP, on which the previous release, release-53, runs both ways (drive route decision 15, `D04-store`); a route result whose inputs match the candidate's current address and the origin, and that routed, then decides the facts row's minutes, with the source `route`, as soon as it is written, and the prospect lists' drive time filter and `drive_minutes` order read those minutes unchanged in meaning (drive route decisions 7 and 8, `D14-prospect-lists`); and a changed origin takes effect at the start that reads it, which projects again the facts row of every candidate holding a route result (`D04-store`). The prospect basis and changes add one migration, `0019_opens.sql`, an expand that adds one table, `opens`, empty at the upgrade, and changes no table or column the previous release, release-57, reads, so release-57 runs on it both ways, never naming the table, at the costs `D04-store`'s Known limits give a rollback (`D04-store`); every open of a prospect list, by `prospect_list` without `peek` or by its page, records one row there, against which the next open's changes are worked out, and a member's basis is read from the results the candidate holds at each read and stored nowhere, so it reaches a space's stored results with no ingest, enrich or judge (basis decisions 1, 7, 8 and 11, `D14-prospect-lists`, `D04-store`, `D10-tools`, `D08-pages`). It follows scrapes' on-a-space design. The guarantee such documents end with, that no business name, address, phone, email, person or ruling text reaches the trail, the bus, a refusal or standard error, is `D09-trail`'s here, as it is scrapes' trail document's there.

Decisions cited by number are the decisions document that delivered candidates. "Website log X" is entry X of the decisions log of the website-check change, "site text decision N" entry N of the decisions document of the site-text change, "brief decision N" entry N of the decisions document of the brief change, "P N" entry N of the decisions log of the brief change's delivery, "category evidence decision N" entry N of the decisions document of the category-evidence change, "website search decision N" outcome N of the decisions document of the website-search change, "S N" entry DN of the decisions log of the website-search change's delivery, "campaigns decision N" decision N of the decisions document that delivered campaigns and the campaign history with it, and "campaigns log DN" entry DN of that delivery's decisions log. "Funnel rename decision N" is decision N of the decisions document of the funnel rename, which gives what candidates stores, answers and shows the funnel's stage names, and "funnel rename log DN" entry DN of its delivery's decisions log. "Drive route decision N" is outcome N of the decisions document of the exact drive time change, which adds the kind `drive_route`, and "drive route log DN" entry DN of its delivery's decisions log. "Basis decision N" is outcome N of the decisions document of the prospect basis and changes, which gives every prospect list member a basis and every open the changes since the previous one.

## What ships

The release holds four members of candidates' directory: `bin/candidates`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `filter`, human-authored (decision 1). No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The two files under `etc/` are what the root package's `Etc` embeds (`D01-layout-and-run-seam`): `etc/manifest.toml` holds the bytes of `cli.Manifest`, which `D02-cli` states byte for byte with the command that prints it, and `etc/nginx.conf` the bytes of `cli.NginxConf`, which this document states. `share/zip_drive.csv` ships inside the binary, embedded by the root package (`D01-layout-and-run-seam`), not beside it.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox and home read it, so its text is contract, stated byte for byte as `cli.Manifest` in `D02-cli`, which also compares its description with `pages.Description` and its `[env]` with `settings.Defaults()`. What a space takes from it: it names the app `candidates`; its description, the same as `pages.Description`; that it is not the default app; that it is an MCP service (`mcp = true`), so the gateway offers the eighteen tools (`D10-tools`); that it does not serve guests (`guests = false`), so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); two secrets, `CANDIDATES_ROUTE_ORIGIN` and `GOOGLE_MAPS_API_KEY`, in that order, the base the drive is measured from and the key the routing service is asked with (drive route decisions 2 and 13), its other outside traffic, the website check's, `add_page`'s and the website search's confirmation fetches of public sites, needing no credential; an `[env]` table whose one line is `CANDIDATES_KEEP_PASSES = "20"` (decision 17), so the value the host writes into candidates' environment is the one candidates applies when the setting is unset; the `[database]` table that has the host keep and replicate `state/candidates.db`; a `[resources]` table whose only line is `memory_max = "256M"`, room enough since a run's rows are streamed and handled a batch at a time (decision 1); and, last, a `[home]` table whose only line is `group = "application"`, so home lists candidates under Application. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app, and `settings.Read` defaults it to 5 (`D01-layout-and-run-seam`). The change to two judgments and the PPP reader changes nothing in the manifest; the cohorts change alters only its description, which no longer speaks of a ranking against the fit test (`D02-cli`, with `pages.Description` in `D01-layout-and-run-seam`). The website check changes nothing in it (website log P2, revised): the stand-in fetcher is chosen by `IKIGENBA_SANDBOX`, which the sandbox sets for every app and `us` never sets, so no `[env]` line is needed, and none could be sandbox-only, since the sandbox renders an app's environment from the same `[env]` table `us` reads; and `memory_max` still holds, since an enrich pass holds no more than the fetches in flight and one batch of candidates (`D15-website-check`). The enrichers change nothing in it either: the derived kinds read only candidates' own database, a batch of candidates at a time, and need no setting, secret or outside address (`D16-enrichers`, `D06-passes`). The site text changes nothing in it either: prompts is a sibling the services file names, and the manifest lists no sibling; a `site_text` pass holds no more than the runs in flight, at most `passes.RunsInFlight`, and an `add_page` one body read to `website.BodyCap`, so `memory_max` still holds; and no setting is added, `site_text`'s pacing being `passes`' constants and its only time limit prompts' own (`D06-passes`). The categories change nothing in it either: the new words are constants in `sources` and JSON in the readings, the results, the facts rows and the judgments, and no setting, secret or column is added. The brief changes nothing in it either: it shares `site_text`'s prompts client and pacing, a `brief` pass holding no more than the runs in flight, each input bounded by `enrichers.BriefInputBytes` (`D16-enrichers`), so `memory_max` still holds, and its two columns are the database's, which the `[database]` table already keeps. The category evidence changes nothing in it either: it adds no setting, secret or column, `classified_by` and `classified` being derived when they are read. The website search changes nothing in it either: it shares the other prompts kinds' client and pacing and the website check's fetcher, a `website_search` pass holding no more than the runs in flight, each confirmation one fetch read to `website.BodyCap` (`D15-website-check`), so `memory_max` still holds; it adds no setting or secret, the search's web access being prompts' (website search decision 4); and its two columns are the database's, which the `[database]` table already keeps. The exact drive time changes the manifest's `secrets` line alone (`D02-cli`). The key is a secret as prompts' Brave key is. The origin is no secret, but it rides the same road, as the suite's other per-space values do (Google's client id, the CRM organisation in opsctl's own example): opsctl writes an app's environment only from the space's parameter store, the manifest's `[env]` and its fixed lines, so a value in `[env]` changes only with a release, and the owner moves the base without one (drive route decision 2); a name the manifest lists among its secrets may not also be an `[env]` key, so `settings.DefaultRouteOrigin`, `Sandstone, MN`, stays out of `[env]` and applies only where the variable is unset or empty (`D01-layout-and-run-seam`). Both are read once at the start. `memory_max` still holds: a `drive_route` pass holds no more than `passes.RoutesInFlight` requests in flight, each answer a few numbers and an address, and the result rows are the database's.

## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. Nothing else is held back; candidates has no sibling read path, so the public name serves the pages, a kept page's text page among them, and `/mcp`, behind auth.

## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a full ingest read; `prompts`, whose socket a pass of kind `enrich_target` walking a prompts kind, `site_text`, `website_search` or `brief`, calls as the caller of the `enrich`, through appkit's `prompts` client, which the start builds from the entry (`D03-serve`, `D06-passes`); `events` and `telemetry`, appkit's sinks'; `auth`, for the banner's addresses (decision 17); and `campaigns`, whose URL alone builds the candidate page's link to each campaign's page, its socket never dialled (`D01-layout-and-run-seam`, `D08-pages`); it calls no other sibling, campaigns included. Outside the host it reaches only the public websites the website check, `add_page` and the website search's confirmation fetch, through the real fetcher, which follows no proxy and refuses loopback, private, link-local and unspecified addresses (`D15-website-check`); the agent of a `site-text` run crawls a company's site from prompts, not from candidates, and names the pages worth keeping back through the gateway's `add_page`, which candidates then fetches itself; the agent of a `website-search` run searches the web from prompts, with the `web` tool group prompts runs it with, never from candidates, and names one URL in its answer, which candidates fetches once under `D15-website-check`'s rules before it records it (website search decisions 4 and 5); the agent of a `brief` run is given the pages in its input and calls nothing. It reaches one service outside the suite: a pass of kind `enrich_target` walking `drive_route` asks Google's geocoding and routing services through the routes client, over the process's outbound HTTP client (`D17-drive-route`, `D01-layout-and-run-seam`), at most `passes.RoutesInFlight` requests at once, each carrying the key and the address strings and coordinates `D17-drive-route` gives, and no identity of the suite's; no other pass, the corpus enrich and an `enrich` with no kind among them, sends a request to the routing service (`D06-passes`). A missing file or entry never refuses the start (`D03-serve`); with no `prompts` entry, `site_text`, `website_search` and `brief` are `unavailable` and every other kind runs as before (site text decision 21), and with no fetcher `website_search` is `unavailable` too, as `website_check` is (`D16-enrichers`); with `GOOGLE_MAPS_API_KEY` unset or empty the start still serves, and an `enrich` of `drive_route` with a target is `invalid` with `passes.NoRouteKey`'s text while every other kind runs as before (drive route decision 13, `D06-passes`), a state a sandbox never reaches, since `sandbox up` refuses a listed secret that is unset or empty, and a space reaches only when an empty key was pushed, since opsctl's activation refuses a listed secret only when it is absent from the space's object. The host must run events, which delivers `scrape.finished`, `cron.judge_candidates.fired` and campaigns' three events to candidates and takes its pass events; scrapes, which it reads; prompts, which runs each `site-text`, `website-search` and `brief` run and in which the owner keeps the prompts of those names, a `website-search` run reaching the web through prompts' `web` tool group, since candidates knows no prompt's model, instructions or tools (site text decision 7); and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`). So with campaigns, which emits `campaign.member.added`, `campaign.member.rejected` and `campaign.piece.delivered` as its `add_member`, `add_prospect_list`, `reject`, `deliver` and `deliver_channel` change a campaign: candidates accepts each by its exact name and never calls campaigns. A host without campaigns leaves every candidate's campaigns empty, and a services file with no `campaigns` entry has the candidate page draw each campaign's id unlinked; neither refuses anything (`D03-serve`, `D08-pages`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored opinions as the last judge wrote them, while the facts still move at each enrich that writes a result (`D16-enrichers`); nothing decays either, and `judge`, or a full `ingest`, judges on demand (funnel rename decision 10). candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `judge`, a full `ingest` and rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]`, `IKIGENBA_SANDBOX`, which it sets for every app, and the two secrets the manifest lists, each read from the variable of the same name in the environment `sandbox up` runs with; puts every request through auth's `/check`; and includes `etc/nginx.conf` in candidates' server. `sandbox up` starts nothing while a secret some manifest lists is unset or empty: it names every missing one with the variable it is read from and stops. So since the exact drive time a developer exports both before `sandbox up`: `GOOGLE_MAPS_API_KEY`, which the owner's keyring gives every new shell (drive route prerequisites), and `CANDIDATES_ROUTE_ORIGIN` as `Sandstone, MN`, the default and the ZIP table's own origin, so a sandbox's routes are measured from where its ZIP estimates are. A changed value reaches candidates at the next `sandbox up`, which reads the secrets again. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools. The sandbox stands up every app whose directory in the worktree holds `etc/manifest.toml`, so it runs a real scrapes, a real prompts and a real campaigns as well, which the check never reaches: the services file's `scrapes` entry names a stand-in for every exercise that ingests, no exercise calls prompts, and no exercise makes a campaign.

**The stand-in fetcher.** With `IKIGENBA_SANDBOX` present, whatever its value, candidates fetches websites through the in-process loopback stub `D15-website-check` declares, and through nothing else (website log P2, revised): the website check's fetches, `add_page`'s and the website search's confirmations alike. The stub listens on two loopback ports, one plain and one TLS, and its client dials one of them whatever host a request names, so no fetch in a sandbox leaves the machine: not the verification list's and not one an ingest starts on its own. It answers by domain: a host under `.test`, a name reserved never to resolve in public DNS (RFC 2606, RFC 6761), whose first label (after one leading `www.`) is one of the stub's keywords, or a keyword followed by `-` and anything, gets that keyword's behaviour (`secure`, `plain`, `prefixed`, `upgrade`, `away`, `missing`, `empty`, `binary`, `refused`, `slow`, `big` and `loop`), and every other host is refused at once, so the real runs' domains each come out `none` without a byte sent and gain no evidence. The keywords, their answers and the results they give are `D15-website-check`'s stub table. The stub is unchanged by this change, and the check fetches nothing through it: the stand-in's rows carry no email, so no candidate has a domain of its own and the ingest's follow-on enrich checks none, and no exercise adds a page or runs a search.

**No stand-in routing service, and no route.** The stub is the website fetcher's alone: with `IKIGENBA_SANDBOX` present the routes client is still the real one, over the process's outbound HTTP client (`D01-layout-and-run-seam`), so a `drive_route` pass in a sandbox reaches Google and is charged for. This change adds no kind and reads only the results a candidate already holds, so the check needs a route result, not a route: the results that give its carriers their bases are written by a test helper through the store over the stopped service's database, as the scale check seeds its candidates (`D04-store`), and no exercise runs `enrich` of `drive_route`, so nothing in the check reaches Google, which V9 shows.

**The stand-in scrapes.** The check needs a few companies, the only candidates in the database so that a prospect list's members are known without grooming, and no email, so the website check fetches nothing for them; the runs of `fmcsa` scrapes holds are thousands of real companies, none of them chosen; and the migration must be shown over the previous release's own database. So the rows reach candidates from a stand-in, as the earlier changes' checks did: a program the delivery writes and runs from a temporary directory outside the tree, never committed, that serves on a Unix socket in a short temporary directory one `done` run of `fmcsa` at `/scrapers/fmcsa/current`, `/runs/<r>/record` and `/runs/<r>/rows`, `<r>` its run's id, the paths a fake run (R-76JM-ZE8M) serves, in the shapes appkit's `scrapes` client reads, with the rows below, and answers 404 for any other scraper's current run, as R-YKXK-J639's fake does.

**No stand-in prompts.** The change adds no prompts kind and no exercise runs a prompts kind, the one brief the check needs being seeded as the route result is, so nothing in the check calls prompts and its entry is left as the sandbox wrote it; V9 shows nothing reached it.

**The swap**: the sandbox's services file's `scrapes` entry is edited to name the stand-in's socket and candidates is restarted, since the client is built from the entry at the start (`D03-serve`); afterwards the entry is restored and candidates restarted again. The file is shared and the gateway reads it on every request, so during the swap the gateway's `scrapes` is the stand-in too, and no tool of the real scrapes is called through the gateway then. `sandbox up` rewrites the file from the manifests, so every `sandbox up` of the check undoes the swap, which is then made again. scrapes' own runs are left as they are.

With candidates stopped and its database emptied, then started, the swap is made; a `scrape.finished` naming the stand-in's `fmcsa` run, `done`, is delivered by hand to candidates' socket at `POST /events`, and its ingest and the enrich that follows it end `done`; a `cron.judge_candidates.fired` delivered by hand then judges every candidate.
