# D11-on-a-space

What candidates contributes when it runs on a space and in a sandbox: what ships, the manifest and the nginx fragment, which entries of the services file it uses, the cron trigger the owner creates for the daily judge, the trust it places in the identity it is sent and the identity it sends scrapes and prompts (decisions 12 and 21 of the parent, decisions 7 and 21 of the site text), which of the contract's guarantees the delivery's sandbox check and the `us` smoke test stand on, and how the enrichers (`D16-enrichers`) reach a space: the derived kinds read only candidates' own database; the website check (`D15-website-check`) and `add_page` (`D10-tools`) fetch through a stand-in in a sandbox and through the real fetcher on `us`; and `site_text` runs the caller's `site-text` prompt at prompts, through a stand-in prompts in a sandbox and the real one on `us`. It follows scrapes' on-a-space design. The guarantee such documents end with, that no business name, address, phone, email, person or ruling text reaches the trail, the bus, a refusal or standard error, is `D09-trail`'s here, as it is scrapes' trail document's there.

## What ships

The release holds four members of candidates' directory: `bin/candidates`, `etc/manifest.toml`, `etc/nginx.conf` and `share/icon.svg`, the last Tabler's `filter`, human-authored (decision 1). No test reads the checkout, so the release and the icon are outside what a requirement can state; a developer checks them with `tar`. The two files under `etc/` are what the root package's `Etc` embeds (`D01-layout-and-run-seam`): `etc/manifest.toml` holds the bytes of `cli.Manifest`, which `D02-cli` states byte for byte with the command that prints it, and `etc/nginx.conf` the bytes of `cli.NginxConf`, which this document states. `share/zip_drive.csv` ships inside the binary, embedded by the root package (`D01-layout-and-run-seam`), not beside it.

## The manifest

The manifest is a program-parsed file: opsctl, the sandbox and home read it, so its text is contract, stated byte for byte as `cli.Manifest` in `D02-cli`, which also compares its description with `pages.Description` and its `[env]` with `settings.Defaults()`. What a space takes from it: it names the app `candidates`; its description, the same as `pages.Description`; that it is not the default app; that it is an MCP service (`mcp = true`), so the gateway offers the seventeen tools (`D10-tools`); that it does not serve guests (`guests = false`), so the host's nginx puts every request through auth's `/check`, to the pages and to `/mcp` alike, and a page asked without a credential is sent to sign in (the 302 the checks expect is nginx's and auth's); no secrets, since candidates holds none of its own and calls no service outside the suite, its outside traffic, the website check's and `add_page`'s fetches of public sites, needing no credential; an `[env]` table whose one line is `CANDIDATES_KEEP_PASSES = "20"` (decision 17), so the value the host writes into candidates' environment is the one candidates applies when the setting is unset; the `[database]` table that has the host keep and replicate `state/candidates.db`; a `[resources]` table whose only line is `memory_max = "256M"`, room enough since a run's rows are streamed and handled a batch at a time (decision 1); and, last, a `[home]` table whose only line is `group = "application"`, so home lists candidates under Application. `DRAIN_SECONDS` is not in `[env]`: it is the space's, as for every app, and `settings.Read` defaults it to 5 (`D01-layout-and-run-seam`). The change to two judgments and the PPP reader changes nothing in the manifest; the cohorts change alters only its description, which no longer speaks of a ranking against the fit test (`D02-cli`, with `pages.Description` in `D01-layout-and-run-seam`). The website check changes nothing in it (decisions log P2, revised): the stand-in fetcher is chosen by `IKIGENBA_SANDBOX`, which the sandbox sets for every app and `us` never sets, so no `[env]` line is needed, and none could be sandbox-only, since the sandbox renders an app's environment from the same `[env]` table `us` reads; and `memory_max` still holds, since an enrich pass holds no more than the fetches in flight and one batch of candidates (`D15-website-check`). The enrichers change nothing in it either: the derived kinds read only candidates' own database, a batch of candidates at a time, and need no setting, secret or outside address (`D16-enrichers`, `D06-passes`). The site text changes nothing in it either: prompts is a sibling the services file names, and the manifest lists no sibling; a `site_text` pass holds no more than the runs in flight, at most `passes.RunsInFlight`, and an `add_page` one body read to `website.BodyCap`, so `memory_max` still holds; and no setting is added, `site_text`'s pacing being `passes`' constants and its only time limit prompts' own (`D06-passes`).

## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. Nothing else is held back; candidates has no sibling read path, so the public name serves the pages, a kept page's text page among them, and `/mcp`, behind auth.

## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes and a rebuild read; `prompts`, whose socket a pass of kind `enrich_cohort` walking `site_text` calls as the caller of the `enrich`, through appkit's `prompts` client, which the start builds from the entry (`D03-serve`, `D06-passes`); `events` and `telemetry`, appkit's sinks'; and `auth`, for the banner's addresses (decision 17); it calls no other sibling. Outside the host it reaches only the public websites the website check and `add_page` fetch, through the real fetcher, which follows no proxy and refuses loopback, private, link-local and unspecified addresses (`D15-website-check`); the agent of a `site-text` run crawls a company's site from prompts, not from candidates, and names the pages worth keeping back through the gateway's `add_page`, which candidates then fetches itself. A missing file or entry never refuses the start (`D03-serve`); with no `prompts` entry, `site_text` is `unavailable` and every other kind runs as before (decision 21). The host must run events, which delivers `scrape.finished` and `cron.judge_candidates.fired` to candidates and takes its pass events; scrapes, which it reads; prompts, which runs each `site-text` run and in which the owner keeps the prompt of that name, since candidates knows no prompt's model, instructions or tools (decision 7); and cron, which emits `cron.judge_candidates.fired` each time the trigger `judge_candidates` fires. candidates never calls cron: it only accepts the event cron emits, by its exact name, as scrapes accepts its own triggers' fires (`D07-events`).

### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored opinions as the last judge wrote them, while the facts still move at each enrich that writes a result (`D16-enrichers`); nothing decays either, and `rebuild` judges on demand. candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `rebuild` and on rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]` and `IKIGENBA_SANDBOX`, which it sets for every app, puts every request through auth's `/check`, and includes `etc/nginx.conf` in candidates' server. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools. The sandbox runs a real prompts too, which the check never reaches: for every exercise that calls prompts, the services file's `prompts` entry names a stand-in instead.

**The stand-in fetcher.** With `IKIGENBA_SANDBOX` present, whatever its value, candidates fetches websites through the in-process loopback stub `D15-website-check` declares, and through nothing else (decisions log P2, revised): the website check's fetches and `add_page`'s alike. The stub listens on two loopback ports, one plain and one TLS, and its client dials one of them whatever host a request names, so no fetch in a sandbox leaves the machine: not the verification list's and not one an ingest starts on its own. It answers by domain: a host under `.test`, a name reserved never to resolve in public DNS (RFC 2606, RFC 6761), whose first label (after one leading `www.`) is one of the stub's keywords, or a keyword followed by `-` and anything, gets that keyword's behaviour (`secure`, `plain`, `prefixed`, `upgrade`, `away`, `missing`, `empty`, `binary`, `refused`, `slow`, `big` and `loop`), and every other host is refused at once, so the real runs' domains each come out `none` without a byte sent and gain no evidence. The keywords, their answers and the results they give are `D15-website-check`'s stub table; the list below names domains by keyword, `secure-a1.test` being a `secure` domain, and expects the answers that table gives. A `secure` host answers a page on every path, titled with the host. The stub is unchanged by this change (decision 22): a site on `secure-co.test` takes pages at `secure-co.test`, at `www.secure-co.test` and at any subdomain whose first label is itself a keyword, so `secure.secure-co.test` is a page of that site and `missing.secure-co.test`, `empty.secure-co.test` and `binary.secure-co.test` are its 404, its empty 200 and its non-HTML 200, the three failures V2 asks for, each on the company's own site.

## Trust

candidates believes the identity it is sent, as every sibling does: `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx or the gateway set them on a request to its socket. It checks them against nothing and asks auth nothing; a `rebuild` or an `enrich` is recorded as started by the user the request names, and a ruling as made by that user, and a `rebuild`'s reads of scrapes forward that identity, as every sibling call forwards its caller. It takes a delivery at `POST /events` from any process that can reach its socket, with no identity at all, as appkit's delivery handler admits it (`D03-serve`, `D07-events`). A delivered `scrape.finished` starts an ingest pass that no person started, and scrapes' read path requires an identity, so that pass reads scrapes as the **service identity**: `X-User-Id` `candidates`, no email, the delivery's request id, with the bus event as cause (decision 12, `D06-passes`). scrapes trusts any process at its socket, so the read is answered, and scrapes' trail records `candidates` as its user: the first service-to-service call in the suite made as no person. A delivered `cron.judge_candidates.fired` starts a judge pass that no person started either; it reads nothing and calls no sibling, so it names no identity to anyone. A pass of kind `enrich_cohort` walking `site_text` forwards its caller on every request to prompts, so prompts runs the caller's own `site-text` prompt as the caller (decision 7, `D03-serve`, `D06-passes`); the run's agent calls `add_page` through the gateway like any agent, and the page records the identity that request names (`D10-tools`). A pass another pass starts, the enrich an ingest starts or the judge an enrich starts, has no user either, carrying the starting pass's request id and cause (`D06-passes`); an enrich fetches public sites and sends them no identity. A process that can reach candidates' socket can therefore name any user, start a rebuild or an enrich, and so a run of that user's prompt at prompts, keep a page or make a ruling as that user, start a judge, and read every candidate; every service on the host is trusted, and the gateway and nginx are the only doors from outside, nginx refusing the bus's two paths there.

## Recorded decisions

- **Trust is stated as the design's own decision** (decision 21), as scrapes' on-a-space design records its own: the suite's identity model is that auth answers nginx's subrequest and the gateway forwards the caller, and a service that re-checked would ask auth on every call for nothing nginx has not already decided; the evidence candidates holds is copied from public records and belongs to the funnel, not a user (decision 14), and a kept page is a page of a company's public site, so a forged identity reads nothing it could not read signed in; what it can do, a rebuild, an enrich, a judge, an `add_page` or a ruling, is bounded (one pass of a kind over one scope at a time; an enrich only adds results and rewrites the facts rows from them, the derived kinds from what candidates holds, the website check at its pace and once per domain, and `site_text` only with a target, at most `passes.RunsInFlight` runs at once of the named user's own prompt; `add_page` keeps only pages of the company's own site, at most `store.PageCap` URLs, and deletes nothing; a judge recomputes from what is stored and loses nothing; rulings are never overwritten and are recorded with the identity that made them).
- **The service identity is a marked decision** (decision 12): a pass a delivery started has no person behind it, and inventing one (the run's starter from `scrape.finished`) would record a person as having read what they did not ask for; `candidates` names the reader truthfully. It is stated here, at the binary's seam, and in `D06-passes`, at the engine's.
- **The judge trigger is the owner's, created through cron's published tools**, as the scrape triggers are: candidates accepts `cron.judge_candidates.fired` and never calls cron, so its schedule is visible, pausable and changeable where every other schedule in the suite is, and candidates keeps the services file use it had: R-IBIN-ZJ0W shows the tools, the pages, a rebuild and an ingest delivery call no `cron` entry, and that the judge path calls no sibling is `D06-passes`' judge run-seam requirement and `D09-trail`'s.
