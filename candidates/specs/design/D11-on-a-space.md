## The nginx fragment

The fragment, `NginxConf`, answers the event bus's two paths, `/events` and `/declarations`, 404 at the public name, as every consumer's does: a delivery reaches candidates only over its socket. ## On a space

candidates on a space is the same binary on the same terms as under a test: a socket passed as descriptor 3 (`/run/ikigenba/candidates.sock`), `/var/opt/ikigenba/candidates` as its working directory, its settings from `/etc/opt/ikigenba/candidates/env`, and `IKIGENBA_SERVICES` naming the host's services file. Of that file it uses `scrapes`, whose socket the ingest passes, a full ingest and the parks passes read, and the start once, asking for the current `mn_parcels` run (`D03-serve`, `D06-passes`); `prompts`, whose socket a pass of kind `enrich_target` walking a prompts kind, `site_text`, `website_search` or `brief`, calls as the caller of the `enrich`, through appkit's `prompts` client, which the start builds from the entry (`D03-serve`, `D06-passes`); `events` and `telemetry`, appkit's sinks'; `auth`, for the banner's addresses (decision 17); and `campaigns`, whose URL alone builds the candidate page's link to each campaign's page, its socket never dialled (`D01-layout-and-run-seam`, `D08-pages`); it calls no other sibling, campaigns included. Outside the host it reaches only the public websites the website check, `add_page` and the website search's confirmation fetch, through the real fetcher, which follows no proxy and refuses loopback, private, link-local and unspecified addresses (`D15-website-check`); the agent of a `site-text` run crawls a company's site from prompts, not from candidates, and names the pages worth keeping back through the gateway's `add_page`, which candidates then fetches itself; the agent of a `website-search` run searches the web from prompts, with the `web` tool group prompts runs it with, never from candidates, and names one URL in its answer, which candidates fetches once under `D15-website-check`'s rules before it records it (website search decisions 4 and 5); the agent of a `brief` run is given the pages in its input and calls nothing. It reaches one service outside the suite, Google: a pass of kind `enrich_target` walking `drive_route` asks Google's geocoding and routing services through the routes client, over the process's outbound HTTP client (`D17-drive-route`, `D01-layout-and-run-seam`), at most `passes.RoutesInFlight` requests at once, each carrying the key and the address strings and coordinates `D17-drive-route` gives, and no identity of the suite's; no other pass, the corpus enrich and an `enrich` with no kind among them, sends a request to the routing service (`D06-passes`). ### The daily trigger

The judge runs once a day because a cron trigger fires it, and the trigger is the owner's, not candidates': after the release is deployed, the owner creates it on `us` with cron's published `create` tool through the gateway, the slug `judge_candidates` and a daily schedule, `0 7 * * *`, an hour after the scrapes' 06:00 triggers, as the scrape triggers were created. Every fire is emitted on the bus as `cron.judge_candidates.fired`, which candidates declares among the events it accepts, so events delivers each fire to candidates' socket at `POST /events`, and each starts one judge pass (`D06-passes`). A missed or paused fire leaves the stored opinions as the last judge wrote them, while the facts still move at each enrich that writes a result (`D16-enrichers`); nothing decays either, and `judge`, or a full `ingest`, judges on demand (funnel rename decision 10). candidates neither creates, checks nor repairs the trigger: a space without it simply judges only on `judge`, a full `ingest` and rulings.

## In a sandbox

The sandbox builds candidates from the worktree, gives it `CANDIDATES_KEEP_PASSES` from the manifest's `[env]`, `IKIGENBA_SANDBOX`, which it sets for every app, and the two secrets the manifest lists, each read from the variable of the same name in the environment `sandbox up` runs with; puts every request through auth's `/check`; and includes `etc/nginx.conf` in candidates' server. `sandbox up` starts nothing while a secret some manifest lists is unset or empty: it names every missing one with the variable it is read from and stops. So since the exact drive time a developer exports both before `sandbox up`: `GOOGLE_MAPS_API_KEY`, which the owner's keyring gives every new shell (drive route prerequisites), and `CANDIDATES_ROUTE_ORIGIN` as `Sandstone, MN`, the default and the ZIP table's own origin, so a sandbox's routes are measured from where its ZIP estimates are. A changed value reaches candidates at the next `sandbox up`, which reads the secrets again. Its state is `<data>/apps/candidates/state/`. An agent is curl on the developer's machine with the stored token, at `http://candidates.<sandbox>.localhost:<port>/` for the pages and the gateway for the tools. The sandbox stands up every app whose directory in the worktree holds `etc/manifest.toml`, so it runs a real scrapes, a real prompts and a real campaigns as well: the check ingests the real scrapes' runs, the services file's `scrapes` entry naming a stand-in only for the fixture items, no exercise calls prompts, and no exercise makes a campaign.

**The stand-in fetcher.** With `IKIGENBA_SANDBOX` present, whatever its value, candidates fetches websites through the in-process loopback stub `D15-website-check` declares, and through nothing else (website log P2, revised): the website check's fetches, `add_page`'s and the website search's confirmations alike. The stub listens on two loopback ports, one plain and one TLS, and its client dials one of them whatever host a request names, so no fetch in a sandbox leaves the machine: not the verification list's and not one an ingest starts on its own. It answers by domain: a host under `.test`, a name reserved never to resolve in public DNS (RFC 2606, RFC 6761), whose first label (after one leading `www.`) is one of the stub's keywords, or a keyword followed by `-` and anything, gets that keyword's behaviour (`secure`, `plain`, `prefixed`, `upgrade`, `away`, `missing`, `empty`, `binary`, `refused`, `slow`, `big` and `loop`), and every other host is refused at once, so the real runs' domains each come out `none` without a byte sent and gain no evidence, the check's `none` leaving each company's website `unknown` (website states outcome 2). The keywords, their answers and the results they give are `D15-website-check`'s stub table. The stub is unchanged by this change: the real FMCSA rows carry emails, so the follow-on enrich of each ingest checks their domains through it, each coming out `none` at once and its website `unknown`; the fixture's rows carry none; and no exercise adds a page or runs a search.

**No stand-in routing service, and no route.** The website fetcher's stub and the walk's Places fake are the sandbox's only stand-ins (`D19-walk`): with `IKIGENBA_SANDBOX` present the routes client is still the real one, over the process's outbound HTTP client (`D01-layout-and-run-seam`), so a `drive_route` pass in a sandbox reaches Google and is charged for. This change adds no kind and routes nothing, so no exercise runs `enrich` of `drive_route` and nothing in the check reaches Google, which V14 shows.

**The real runs.** The companies the check reads, Hjort Excavating, KTM Paving, Design Ready Controls, Rosenbauer Minnesota, Molin Concrete, a school district and a row with nonsense figures, are real ones the OSHA ITA document names from the real rows, and the full ingest over every real run is the change at its real size, so the check reads the sandbox's scrapes as it stands: it must hold a `done` current run of each of `fmcsa`, `ppp`, `form5500` and `osha_ita`, the last a real OSHA ITA run of every file the scraper's setting names, the one scrapes' own check landed or, when scrapes holds none, one the delivery lands with scrapes' `scrape` tool through the gateway before the baseline, as it does for any other scraper without one. No scrape is started from then until cleanup, so every full ingest reads the same rows and no `scrape.finished` reaches candidates meanwhile but those the check delivers by hand.

**The stand-in scrapes.** The fixture items need rows built to the EINs, names, years, figures, states and ZIPs each item names, the only candidates in the database so that a pass's counts are known, and no email; the real runs hold none chosen. So those rows reach candidates from a stand-in, as the earlier changes' checks did: a program the delivery writes and runs from a temporary directory outside the tree, never committed, that serves on a Unix socket in a short temporary directory one `done` run of `osha_ita` at `/scrapers/osha_ita/current`, `/runs/<r>/record` and `/runs/<r>/rows`, `<r>` its run's id, the paths a fake run (R-76JM-ZE8M) serves for `fmcsa`, in the shapes appkit's `scrapes` client reads, with the rows below, and answers 404 for any other scraper's current run, as R-LFE5-HICE's fake does for every scraper but `fmcsa` and `mn_parcels`.
