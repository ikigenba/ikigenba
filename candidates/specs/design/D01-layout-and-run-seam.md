# D01-layout-and-run-seam

candidates is stages two and three of the funnel, resolve and qualify: one Go binary that turns the rows scrapes collects into candidate businesses, one per real business with every row that describes it attached as evidence, and judges each twice, how sure it is that the business is operating today and how big it is, so the owner can read them through **cohorts**, saved searches whose members are worked out each time one is read (`D14-cohorts`). A **source** is Go code in the service that knows how a row of one scraper becomes match keys, tags, a size estimate, a filing date, operating evidence, a known-since date, a category and a government name match; the registry is fixed and holds two sources, `fmcsa` and `ppp` (`D05-sources`). A **pass** is one ingest, judge, rebuild, enrich or targeted enrich, recorded at once and worked in the background (`D06-passes`): an **ingest** is started by a `scrape.finished` delivered on the bus and reads that run's record and rows from scrapes over its socket through appkit's `scrapes` client; a **judge** is started by the daily `cron.judge_candidates.fired` delivered on the bus and reads nothing from scrapes; a **rebuild**, started by the `rebuild` tool, ingests every source's current run, then recomputes every derived kind for every candidate, and then judges; an **enrich**, started by an ingest that ends `done` or by the `enrich` tool without a target, runs the **enrichers**, the fixed registry of kinds (`D16-enrichers`), on the candidates that are **due** for each, those whose **inputs** for the kind, one string it names from what the candidate holds, are not empty and either it holds no result of that kind yet or they differ from the inputs of its newest result of that kind (empty inputs are never due): first the **derived** kinds, which read only what the service holds, `drive_minutes` from the display ZIP and `link_facts` from the links, then the **fetched** kind, the **website check**, which fetches the home page of the domain of each one's display email (`D15-website-check`); a **targeted enrich**, an `enrich_cohort` pass, started by the `enrich` tool with a cohort or a candidate, runs one kind over that target's candidates, the due ones or, with `force`, every one, and is the only pass that runs **site text**, the fetched kind `site_text`, for which candidates asks the `prompts` service to run the caller's `site-text` prompt once per company, an agent run that keeps the pages describing the business through the `add_page` tool; each result is recorded as an **enrichment** on the candidate, and an enrich of either kind that recorded a derived or website result starts a judge unless a judge is running (`D06-passes`). A pass is refused `busy` only while another of the same kind over the same scope is running (`D04-store`). A **candidate** gathers **links**, one per row attached to it (`D12-resolution`); each source gives a candidate an **estimate**; each candidate has **facts**, the projection of its newest enrichment of each kind, written whenever an enrichment is, and keeps **pages**, the copies of pages of its website that `add_page` fetched, the newest copy of each URL being the one read (`D04-store`); and each candidate has one **assessment**, its two judgments, operating confidence and revenue, written only by a judge, which reads the facts and derives none (`D13-scoring`); the owner's **rulings** override matching (`D12-resolution`); and the owner's **rejects** take a candidate out of one cohort (`D14-cohorts`). All of it lives in the app's own SQLite database, `state/candidates.db` (`D04-store`). Each pass's start and end is an event on the bus and in the trail (`D07-events`, `D09-trail`). Seventeen MCP tools are offered at `/mcp` (`D10-tools`); a landing page, a page per cohort, per candidate, per kept page's text and per pass, a tools page, an about screen and the not-found page are served to a signed-in user (`D08-pages`).

This design is the structural ground the others stand on: where the code lives and what each package is for, every name that crosses a package boundary with its shape, the seam through which the process is run so that every part can be tested without a real process, the settings, the path, the addresses, where the identity and the display string come from, and the binary's wiring. The command line is `D02-cli`'s; the store's whole surface is `D04-store`'s; the serve path, the services file and the route table are `D03-serve`'s. It follows scrapes' layout and run seam, with the sources in place of the scrapers, the pass engine in place of the run engine, and appkit's `scrapes` and `prompts` clients in place of scrapes' HTTP client for its siblings; the HTTP client candidates does take, `Process.HTTP`, is the website check's and `add_page`'s alone.

The module is `github.com/ikigenba/ikigenba/candidates`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/candidates`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/candidates` is wiring only.

## The dependencies

candidates depends on two modules besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required at a published release with no `replace` directive, and `golang.org/x/net`, whose `html` package the website check parses a page's title with and `add_page` strips a page to its text with (`D15-website-check`, decisions log P5). Its `db` package brings the pure-Go SQLite driver, which keeps the release build cgo-free. candidates uses appkit's `db`, `version`, `services`, `page`, `identity`, `mcp`, `telemetry`, `events`, `scrapes` and `prompts`, and restates none of their contracts. It uses neither `artifacts` nor `connections`. It calls two siblings, each only through appkit's client for it, built from the services file's entry of its name: scrapes through the `scrapes` client from the `scrapes` entry, and prompts through the `prompts` client, the installed interface appkit's design D27 describes, from the `prompts` entry, always as the caller of the `enrich` that started the targeted pass, so a prompt and its runs are that caller's; the event bus and the telemetry socket are reached through appkit's sinks. With no `prompts` entry there is no client and `site_text` is `unavailable`, as `website_check` is without a checker (`D06-passes`). Outside the suite it calls nothing but the websites the website check and `add_page` fetch, over outbound HTTP through `Process.HTTP`; with `IKIGENBA_SANDBOX` present it fetches only from an in-process stub on loopback (`D15-website-check`). Which release of appkit or `golang.org/x/net` is data that `AGENTS.md` and `go.mod` hold; the appkit release candidates requires is one that exports `prompts`, so appkit is released with it before candidates is built against it.

## Where the environment is read

`main` makes the one read of the environment that is not `Run`'s own: it calls appkit's `version.Read` exactly once, first, and holds the result, the **identity**, whose `String()` is the **display string**. It hands the identity to `page.New`, whose banner carries its `Release` and `Commit` to every page's footer and to the about screen, and the display string to the `mcp.ServerConfig` its `Process.MCP` builds and to `Run` as `Process.Version`. Nothing below `main` calls `version.Read`. `Run` reads every variable through `Process.LookupEnv`: `DRAIN_SECONDS` and `CANDIDATES_KEEP_PASSES` once at start, through `settings.Read`; `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness; `IKIGENBA_SERVICES` once, when it starts to serve; and `IKIGENBA_SANDBOX`, whose presence chooses the website check's fetcher (`D15-website-check`). appkit's constructors also read `IKIGENBA_SERVICES` from the process environment; that read is appkit's.

## Packages

The root package, named `candidates`, holds what the module embeds: `Assets` (the eight templates `about.html`, `candidate.html`, `cohort.html`, `landing.html`, `notfound.html`, `page.html`, `pass.html` and `tools.html`), `Etc` (`manifest.toml` and `nginx.conf`), `Migrations` (the seven files that create seven of the thirteen tables `D04-store` describes, one each, in decision 16's order, `0008_windows.sql`, which only expands: it adds the stored scores, creates the eighth table, `candidate_cargo`, and adds the list windows' indexes, `0009_judgments.sql`, which gives the assessments their two judgments and the facts beside them and the passes their kind and origin and is frozen, and `0010_cohorts.sql`, which creates the ninth and tenth tables, `cohorts` and `rejects`, gives the assessments their fleet verdict and counts, and drops the stored scores and the columns only the shortlist read, and `0011_enrichments.sql`, which creates the eleventh table, `enrichments`, gives the assessments their website and the passes the enrich counts, and drops the assessments' columns `fleet`, `low` and `high`, `0012_facts.sql`, which only expands: it gives the enrichments their inputs, backfilled from the source for every website check, and an index on them, creates the twelfth table, `facts`, and gives the passes their derived count, and `0013_site_text.sql`, which only expands: it creates the thirteenth table, `pages`, with its index, gives the passes their target, the kind a targeted pass walks and the counts of its prompts runs, and gives the facts `site_text_at`, `D04-store`'s) and `ZipDrive`, the ZIP drive-time table read from the embedded `share/zip_drive.csv`, as a map from a five-digit ZIP to whole minutes from the origin. The start loads `ZipDrive()` into the store whole (`D03-serve`); a test that needs drive minutes reads them from `ZipDrive()`.

The internal packages hold the concerns, one each. Each package's shapes that another package uses are declared here (the store's in `D04-store`); the behavior of each name is the document named:

- `internal/cli`: the run seam (this document), the command, the manifest and the usage text (`D02-cli`), the serve path (`D03-serve`), `cli.SweepInterval` (this document; the sweep itself is `D06-passes`'), and `cli.NginxConf` (`D11-on-a-space`).
- `internal/settings`: the two settings (this document).
- `internal/server`: a listener's life (`D03-serve`).
- `internal/web`: the route table, `web.Config` and `web.Handler` (`D03-serve`).
- `internal/store`: every record and every read and write of them: candidates, links, estimates, assessments, rulings, cohorts, rejects, enrichments, facts, pages, passes and the ZIP table (`D04-store` declares the whole surface and owns the pass records, the reads, the enrichment, facts and page writes, the cohort and reject writes, the ZIP table and the prune; `D12-resolution` owns `Attach`, `MarkGone` and `Decide`, a merge's move of pages included; `D13-scoring` owns `Judge` and `JudgeAll`; `D14-cohorts` defines what a cohort is, the terms its reads answer by).
- `internal/sources`: what every source shares: a source's reading of a row (`sources.Reading`, `sources.Estimate`, `sources.Evidence`, `sources.Person`) and a category with the source that gave it (`sources.Category`), the `Source` interface and the fixed registry, the class tags, the fleet verdicts, the category names, the evidence kinds and the government name match (`D05-sources`); the website check's kind and the website states (this document, used by `D16-enrichers`, `D15-website-check`, `D04-store` and `D13-scoring`); the normalized keys and the source key (`D12-resolution`); the rules version (`D13-scoring`).
- `internal/fmcsa`: the FMCSA source (`D05-sources`).
- `internal/ppp`: the PPP loan source (`D05-sources`).
- `internal/scoring`: the judgment rules as functions of values: the combined estimate, the freshness weight, a piece of evidence's weight at a moment, the operating confidence and the integer it is ordered by (`D13-scoring`).
- `internal/passes`: the engine, `passes.Engine` built by `passes.New(passes.Config)`: starting a pass by `rebuild`, by `enrich` over the corpus (`Engine.Enrich`) or over a target (`Engine.EnrichCohort`), by a delivery of either event it accepts and by another pass, the work in the background, a targeted pass's prompts runs and its waits on `passes.Config.After`, the identity of its reads and runs, the start's settling (`Engine.Recover`), the drain (`Engine.Drain`), the pass record's JSON and every refusal word (`D06-passes`).
- `internal/enrichers`: the enrichers: the kinds and their source words, a candidate's subject, the `Enricher`, `Deriver`, `Fetcher` and `Prompter` interfaces, the four kinds with their inputs, results and found shapes, a prompted kind's prompt name and run input, the link fingerprint, and the fixed registry with its validation of a found value (`D16-enrichers`, which declares the whole package).
- `internal/website`: the website check: a domain's attempts and their result, the pace and the concurrency of a pass's checks, the fetch of one page with its text and the host guard `add_page` uses, the real fetcher and the in-process loopback stub the sandbox fetches from (`D15-website-check`, which declares the whole package).
- `internal/trail`: the pass events, the two events accepted, and their declarations (`D07-events`); the trail as a whole and its secrecy (`D09-trail`).
- `internal/urls`: the auth address, the addresses of scrapes' pages and the page path (this document).
- `internal/tools`: the seventeen tools, their catalog and their refusal sentences (`D10-tools`).
- `internal/pages`: the templates' data and the page routes (`D08-pages`); `pages.ServiceName` and `pages.Description` (this document).

`internal/scoring` is warranted: the judgment rules are pure functions of estimates, evidence, a filing date and the clock that the store's judge applies, and a test proves them by calling them; in `internal/sources` they would join a second concern to the sources', and in `internal/store` they could not be proved without a database. `internal/ppp` is a package the scaffold's test-file list does not yet name; it sits beside `internal/fmcsa` because each source keeps its own facts, formulas and parsing, as scrapes keeps one package per scraper, and the delivery adds it to that list. `internal/website` is warranted: the website check is outbound HTTP, a pace and a stub server, a concern no other package has, and it is proved by calling it over an injected client; in `internal/passes` it would join a network client to the engine, and the store never fetches. `internal/enrichers` is warranted: an enricher is a kind's inputs, its result and the check of a found value, pure functions of a candidate's subject that a test proves by calling them, and the store, the engine, the tools and the pages all need the kinds; in `internal/store` the derived kinds could not be proved without a database, in `internal/passes` the store could not reach them without importing the engine, and in `internal/sources` they would join a second concern to the sources'. The store builds the registry with neither a checker nor a prompts client, `enrichers.New(enrichers.Config{})`, whose website and site-text kinds can do nothing, so the store still fetches nothing and calls no sibling. No matching package is added: the attach rule reads and writes links in one transaction per batch, so it is a store write (`store.Attach`, `D12-resolution`), and the normalization it compares is the sources' (`sources.NameKey` and its siblings), since a source produces a row's keys. No package is added for the pages or for site text either: a page is a store record, `add_page` is a tool over the store and the website check's one-page fetch, `site_text` is an enricher, the client is appkit's, and a targeted pass's runs are the engine's work.

The registry lives in `internal/sources` with no default list: `fmcsa` and `ppp` import `sources` for the reading's types, so a registry that named either source there would make them import each other. `Run` builds the fixed registry, `sources.New(fmcsa.New(), ppp.New())`, whose order, `fmcsa` then `ppp`, is the order a rebuild ingests in (`D05-sources`). The enrichers' registry has a fixed list instead, built by `enrichers.New(cfg)` from the parts that vary at run time, an `enrichers.Config` holding the website checker and the prompts client: no import cycle forces an injected list, since `internal/enrichers` imports `internal/sources`, `internal/fmcsa` (for `fmcsa.Name`), `internal/website` and appkit's `prompts`, and nothing under it imports `internal/store` or `internal/passes`; `internal/store` imports `internal/enrichers`, and runs the derived kinds itself, so that a merge or split recomputes them in the same write as its ruling and its judging (`D12-resolution`). Its order, `drive_minutes`, `link_facts`, `website_check`, `site_text`, puts the derived kinds before the fetched ones, and is no longer the kinds' name order (`D16-enrichers`). Which package imports which is guidance, not contract.

Template data types, tool argument and result types, copy constants and the constants a package uses only itself are declared by the document that owns the package's behavior, not here.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, and returns the exit code. It is scrapes' seam with `HTTP` kept for one use: scrapes and prompts are reached over the sockets the services file names, so a `Run`-level test serves a fake scrapes on a Unix socket its services file's `scrapes` entry names and a fake prompts on one its `prompts` entry names, and the only addresses candidates reaches of its own choosing are on a candidate's website, the home page the website check fetches and a page `add_page` is asked to keep, fetched through `HTTP`. A nil `HTTP` is no website check at all, so a `Run`-level test that sets neither `HTTP` nor `IKIGENBA_SANDBOX` fetches nothing, and one that sets `IKIGENBA_SANDBOX` in its lookup checks against the stub on loopback (`D15-website-check`). `Now` is the clock every time candidates stamps or compares is read from: a pass's started and finished, a link's first and last seen, a candidate's created and updated, a ruling's time, an assessment's calculated time, the moment a judge measures a filing's freshness at, the prune's ordering, every event's time. `Sleep` is the pause the writer and the emitter wait with between delivery attempts. `After` is the sweeper's timer (`D06-passes`); the website check's, for each attempt's timeout and the pace between checks, and `add_page`'s fetch's, for its one attempt's timeout (`D15-website-check`); and the engine's, for a targeted site-text pass's result poll and its wait when prompts' queue is full, which `Run` hands the engine as `passes.Config.After` (`D06-passes`). `Rand` is the source of every value candidates mints: request ids, pass ids, candidate ids and bus event ids. `Inherit`, `Now` and `Rand` are the caller's to give whenever `Args` is empty: `Run` has no default for any of them, and the choice of the process's own descriptor 3, `time.Now` and `crypto/rand.Reader` is made once, at the process boundary, by `cmd/candidates`. The event bus, telemetry, scrapes and prompts sockets reach `Run` through the services file `IKIGENBA_SERVICES` names (`D03-serve`). There are no live tests. The one test that execs the binary starts exactly one pass and no other: an `enrich` of the kind `website_check` over the empty store it started on, which proves the binary hands `Run` a fetcher, reads nothing from scrapes, and, with no candidate due, fetches nothing.

## Settings

candidates reads two values at start, in this order: `DRAIN_SECONDS`, the space's, and `CANDIDATES_KEEP_PASSES`, the one its manifest's `[env]` declares (decision 17). An unset or empty one is its default: 5 seconds and 20 passes. Both are spelled as opsctl writes an integer: one or more ASCII digits, no sign, no leading zero, so `0` is refused. Digits beyond what an `int64` holds read as the largest `int64`. `settings.Read` refuses the first value in that order that is not acceptable with a `*settings.Error` naming it, quoting its value and saying what was wanted, and `Run` writes its text after `candidates: ` as a usage error before it looks for its socket. The origin, the rules' numbers and evidence weights, the free-provider list, the government patterns, the NAICS prefixes, the page sizes, the batch size, the hourly sweep and the website check's tuning numbers are constants of the documents that use them.

## Paths

Relative to `Process.Dir` (the process's working directory when empty) the database is `state/candidates.db`, opened with `db.Open`, the root package's `Migrations()` and `Process.Now`; `state/` is created when absent. candidates writes nothing outside `Dir` and nothing under it but the database: a run's rows are streamed and handled a batch at a time (decision 1), and the store reaches each record a batch needs by key, so a pass costs in proportion to its rows (`D04-store`, `D06-passes`).

## The addresses

`internal/urls` holds the addresses candidates builds that are not its own paths, and one that is. The **auth address** is the `URL` of the services file's entry `auth`, trailing `/` removed, or, with no such entry, built from the request's scheme and host with a leading `candidates.` removed (`urls.Auth`), which the pages' banner links to (`D08-pages`). The **scrapes address** is the `URL` of the services file's entry `scrapes`, every trailing `/` removed (`urls.Base`, `urls.Scrapes`), and empty when the file has no such entry: a relative address would name a page of candidates' own. On it are built a row's page at scrapes, `<scrapes address>/runs/<run>/rows/<source id>` (`urls.RowPage`, decision 15), which a candidate's links point to, and a run's page, `<scrapes address>/runs/<run>` (`urls.RunPage`), which an ingest pass, started by a `scrape.finished` delivery, points to; each is empty when the address, the run or the source id is empty. The source id is path-escaped, so an id holding `/` stays one segment. The page paths `/cohorts/<id>`, `/candidates/<id>` and `/passes/<id>` are spelled by the templates, which build them from the data they receive. The **page path**, where a kept page's text is served, `/candidates/<candidate>/pages/<number>` (`D08-pages`), is built by `urls.PagePath` instead, since two packages give it: the tools answer it as a page's `path` (`D10-tools`) and the candidate page links each page to it (`D08-pages`).

## Recorded decisions

- The layout is scrapes' with `internal/sources` in place of `internal/source` and one package per source, `internal/fmcsa` and `internal/ppp`, as scrapes has one per scraper, `internal/passes` in place of `internal/runs`, and `internal/scoring` added; scrapes' `internal/scrapers` registry package has no counterpart because the registry is `sources.Registry` and `Run` lists its two sources. The PPP source is a package beside the FMCSA one, the smallest change to this layout; the packages added since, `internal/website` and `internal/enrichers`, are each warranted under Packages. Pages and site text add no package (Packages).
- The domain records (`store.Candidate`, `store.Link`, `store.Assessment`, `store.Ruling`, `store.Cohort`, `store.Reject`, `store.Page`, `store.Pass`) are the store's, as scrapes' `store.Run` is; a source's per-row reading and per-source estimate are the sources' (`sources.Reading`, `sources.Estimate`), since a source makes them and the store keeps them as given. A link keeps its row's whole reading, evidence, dates and category included, so neither the `link_facts` enricher nor a judge needs a read of scrapes.
- Matching, merging and splitting are store writes (`store.Attach`, `store.MarkGone`, `store.Decide`), each one transaction, so a ruling and the links it moves, or a batch and the candidates it creates, cannot be seen half done. `decide`, `exclude` and `include` reach the store directly, as the cohort and reject tools do; the engine is not in their path, since neither a ruling nor a cohort reads scrapes or waits for a pass.
- The root package exports the ZIP table as a typed map, `ZipDrive() map[string]int64`, rather than the CSV file: every consumer wants minutes by ZIP, and a test reads the embedded table through it without opening the checkout.
- No `Process` field names scrapes' address: the services file names its socket, as it names the bus's and telemetry's.
- `Process.Inherit`, `Process.Now` and `Process.Rand` are required whenever `Args` is empty, as in scrapes; no requirement states the precondition, because no permitted test can observe a default.
- A `scrape.finished` delivery reads the run's record from scrapes before it records a pass (orchestrator ruling; the behavior is `D06-passes`'): a run not found or not `done` is `Skip` with no pass recorded; any other failed read records the pass and fails it `scrapes`, answering `OK`; `Fail` is kept for a pass already running, the drain and the database failing. `Deliver` holds the delivery's context and calls `store.AddPass` and `store.FailPass` after that read, so no signature changes. A `cron.judge_candidates.fired` delivery reads nothing from scrapes; `Deliver` tells the two by the event's name, so the engine gains no entry point.
- A pass started by a delivery reads scrapes as the service identity (decision 12, binding); that identity is the engine's (`D06-passes`), and no `Process` field carries it.
- candidates accepts the judge's trigger by its exact name, `trail.AcceptedJudge`, `cron.judge_candidates.fired` (cron emits `cron.<slug>.fired`), with no pattern, as scrapes accepts its triggers; the slug `judge_candidates` is the one the owner creates on a space.
- `sources.Rules`, the rules version, is declared without its value: no requirement states a version, a test reads the value the source declares, and `D13-scoring`'s prose says which it is.
- The category names and evidence kinds are stored and answered as given, so they are contract constants with their values (`sources.Category*`, `sources.Evidence*`); an evidence item's description is copy, a constant `D05-sources` declares without its value.
- A reading carries one category word and its evidence items each name their source; `sources.Category` pairs a category with the source that gave it, for the assessment (`D04-store`). `Evidence.Source` is any source's name, not only a scraper's, and `scoring.Operating` takes any evidence list, so evidence from an enrichment joins a candidate's without a new shape: the website check's evidence, `sources.EvidenceWebsiteLive`, names `sources.WebsiteCheck` as its source (`D13-scoring`).
- Cohorts add no package: a cohort's constants, validators, types and reads are the store's (`D04-store`) and what a cohort is `D14-cohorts`', because the tools and the store both need the validators and both already import `store`.
- The fleet verdict is a reading's before it is a fact (cohorts decisions log 11): the `link_facts` enricher reads the stored link reading, not the row (`D16-enrichers`), so `sources.Reading` carries `FleetVerdict`, with the row's `PowerUnits` and `Drivers`, right after `Fleet`, which is still written so the release before reads new readings. The verdict words are stored and answered as given, so they are contract constants with their values (`sources.FleetPass`, `sources.FleetFail`, `sources.FleetUnknown`), beside the class tags; a link an earlier release stored reads with an empty verdict, which its readers take as unknown (`D05-sources`, `D16-enrichers`).
- `passes.Record` gains the pass's `Kind` and `Origin`, and its count of candidates judged is `Judged`, where `Rescored` was; its JSON is `D06-passes`'.
- The website check's vocabulary is `internal/sources`', beside the class tags and fleet verdicts: the kind `sources.WebsiteCheck`, which is also the source its evidence names, and the states `sources.WebsiteHTTPS`, `WebsiteHTTP`, `WebsiteNone` and `WebsiteUnknown`, stored and answered as given, so contract constants with their values. `internal/store`, `internal/scoring` and `internal/enrichers` all need them and import `sources`; the website check's kind keeps its name there rather than moving to `internal/enrichers` beside the derived kinds' (`enrichers.KindDriveMinutes`, `enrichers.KindLinkFacts`), since the names the code uses stay as they are. The pass vocabulary (`store.KindEnrich` and the origins) stays the store's, beside the other kinds (`D04-store`). `sources.Rules` is still declared without its value, and `D13-scoring`'s prose says which it is; moving the facts from the judge to the enrichers leaves it as it was, since the values written do not change.
- `passes.Config` keeps `Website`, the checker the engine's website check fetches with, and gains `Prompts`, appkit's `prompts` client, after `Scrapes`, beside the other sibling's client; the engine builds its registry from the two, `enrichers.New(enrichers.Config{Website: cfg.Website, Prompts: cfg.Prompts})`, rather than taking a registry: the derived kinds need neither, so a field for a registry would carry nothing the engine cannot build, and the engine needs the client itself for `Show`, `Run` and `Result`. A nil `Website` means only that the website kind is not ready: `Enrich` asked for `website_check` is refused `unavailable`, while an enrich of every kind, the ingest's follow-on included, runs the derived kinds and skips the website check (`D06-passes`). A nil `Prompts`, a services file with no `prompts` entry, means only that `site_text` is not ready, so a targeted enrich of it is refused `unavailable` (decision 21); an untargeted enrich never walks it.
- **`passes.Config` gains `After`, last,** the timer the engine's own waits end on, the result poll and the queue-full wait of a targeted site-text pass, nil meaning `time.After`; `Run` sets it to `Process.After`, the timer the sweeper and the website check already wait on. Decision 8 measures the poll on `Process.After`, and a test that holds the channels drives every wait of a pass without real time passing; a test tells the engine's two waits from the sweeper's and the checker's by their durations, `passes.PollInterval` and `passes.QueueWait` (`D06-passes`).
- **A targeted enrich is a method of its own, `Engine.EnrichCohort`,** taking the kind, the target and `force`, beside `Engine.Enrich`, whose signature stays: a target makes a different pass kind with its own refusals and work (`D06-passes`), and the many requirements citing `Enrich` still hold for the corpus enrich.
