# D01-layout-and-run-seam

candidates is stages two to four of the funnel, ingest, enrich and judge: one Go binary that ingests the rows scrapes takes from public records into candidate businesses, one per real business with every row that describes it attached as evidence, and judges each twice, how sure it is that the business is operating today and how big it is, so the owner can read them through **prospect lists**, saved searches whose members are worked out each time one is read (`D14-prospect-lists`). A **source** is Go code in the service that knows how a row of one scraper becomes match keys, tags, a headcount, a size estimate, a filing date, operating evidence, a known-since date, a category and a government name match; the registry is fixed and holds four sources, `fmcsa`, `ppp`, `form5500` and `osha_ita` (`D05-sources`), and the scraper `mn_parcels`, whose rows parks are derived from, is not one. A **pass** is one ingest, judge, enrich, targeted enrich or parks pass, recorded at once and worked in the background (`D06-passes`): an **ingest** is started by a `scrape.finished` delivered on the bus and reads that run's record and rows from scrapes over its socket through appkit's `scrapes` client; a **judge** is started by the daily `cron.judge_candidates.fired` delivered on the bus, or by the `judge` tool, and reads nothing from scrapes; an ingest started by the `ingest` tool ingests one named scraper's current run as a delivered ingest does, or, named none, is a **full ingest**, which ingests every source's current run, then recomputes every derived kind for every candidate, and then judges; an **enrich**, started by an ingest that ends `done` or by the `enrich` tool without a target, runs the **enrichers**, the fixed registry of kinds (`D16-enrichers`), on the candidates that are **due** for each, those whose **inputs** for the kind, one string it names from what the candidate holds, are not empty and either it holds no result of that kind yet or they differ from the inputs of its newest result of that kind (empty inputs are never due): first the **derived** kinds, which read only what the service holds, `drive_minutes` from the display ZIP and `link_facts` from the links, then the **fetched** kind, the **website check**, which fetches the home page of the domain of each one's display email (`D15-website-check`); a **targeted enrich**, an `enrich_target` pass, started by the `enrich` tool with a prospect list or a candidate, runs one kind over that target's candidates, the due ones or, with `force`, every one, and is the only pass that runs the **prompts kinds**, the fetched kinds for which candidates asks the `prompts` service to run the caller's prompt named for the kind once per company: the **website search**, `website_search`, whose `website-search` prompt is an agent run that searches the web for the website of a company with none on record, or with one on record whose site text kept no page (empty sites outcome 1), a site it names being recorded only once candidates has fetched it under the website check's rules, **site text**, `site_text`, whose `site-text` prompt is an agent run that keeps the pages describing the business through the `add_page` tool, and the **brief**, `brief`, whose `brief` prompt reads those pages and writes a short summary of the business with the categories it picks; it is also the only pass that runs the **drive route**, `drive_route`, the fetched kind for which candidates asks Google's routing service, through `internal/routes`, for the drive by car from the **origin**, an address the service reads at start, to the candidate's street address, and keeps the minutes and miles (`D16-enrichers`, `D17-drive-route`); each result is recorded as an **enrichment** on the candidate, and an enrich of either kind that recorded a derived result or a website check result starts a judge unless a judge is running, while a targeted enrich of a prompts kind starts none (`D06-passes`); a **parks** pass reads the Minnesota parcel rows scrapes holds for `mn_parcels` and derives from them the industrial **parks**, places the owner can name for a later walk and never candidates (`D18-parks`), and is started by a `scrape.finished` of `mn_parcels` delivered on the bus, by the `edit_park_rules` tool, or at start, when scrapes' current `mn_parcels` run is not the one the parks were last derived from (`D06-passes`). A pass is refused `busy` only while another of the same kind over the same scope is running (`D04-store`), so a parks pass runs beside every other kind and is refused `busy` only beside another parks pass. A **candidate** gathers **links**, one per row attached to it (`D12-ingest`); each source may give a candidate an **estimate**, and the judge forms one more from the candidate's headcount and a band of revenue per employee (`D13-judging`); each candidate has **facts**, the projection of its enrichments of each kind, written whenever an enrichment is, and keeps **pages**, the copies of pages of its website that `add_page` fetched, the newest copy of each URL being the one read (`D04-store`); and each candidate has its **judgments**, operating confidence and revenue, written only by a judge, which reads the facts and derives none (`D13-judging`); the owner's **rulings** override matching (`D12-ingest`); and the owner's **rejects** take a candidate out of one prospect list (`D14-prospect-lists`). Each candidate keeps its **campaign uses**, one per campaign it was put in, recorded from the three events campaigns emits on the bus when a member is added, rejected or has a piece delivered, a use naming a merged candidate landing on the survivor (campaigns decision 17, campaigns log D1, `D04-store`, `D06-passes`); a prospect list may leave out the candidates used in a campaign within so many days (campaigns decision 18, `D14-prospect-lists`). All of it lives in the app's own SQLite database, `state/candidates.db` (`D04-store`). Each pass's start and end is an event on the bus and in the trail (`D07-events`, `D09-trail`). Twenty-two MCP tools are offered at `/mcp` (`D10-tools`), and, unlisted, the one tool a sibling of the previous release still calls by its old name; a landing page, a page per prospect list, per candidate, per kept page's text and per pass, the parks page and a page per park, a tools page, an about screen and the not-found page are served to a signed-in user (`D08-pages`).

This design is the structural ground the others stand on: where the code lives and what each package is for, every name that crosses a package boundary with its shape, the seam through which the process is run so that every part can be tested without a real process, the settings, the path, the addresses, where the identity and the display string come from, and the binary's wiring. The command line is `D02-cli`'s; the store's whole surface is `D04-store`'s; the serve path, the services file and the route table are `D03-serve`'s. It follows scrapes' layout and run seam, with the sources in place of the scrapers, the pass engine in place of the run engine, and appkit's `scrapes` and `prompts` clients in place of scrapes' HTTP client for its siblings; the HTTP client candidates does take, `Process.HTTP`, is the website check's, `add_page`'s and the website search's, which confirms the site its agent names through it (website search decision 5, S 1), the routes client's, which asks Google's routing service for a drive route through it (`D17-drive-route`), and the Places client's, which asks Google's Places API for a walk's searches through it outside the sandbox (`D19-walk`), alone.

The module is `github.com/ikigenba/ikigenba/candidates`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/candidates`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/candidates` is wiring only.

Decisions cited by number are the decisions document that delivered candidates; "cohorts log N" is entry N of the decisions log of the cohorts change. "Website log X" is entry X of the decisions log of the website-check change, "site text decision N" entry N of the decisions document of the site-text change, "brief decision N" entry N of the decisions document of the brief change, "website search decision N" entry N of the decisions document of the website-search change, and "S N" entry DN of the decisions log of the website-search change. "Campaigns decision N" is entry N of the decisions document that delivered campaigns, and "campaigns log DN" entry DN of its decisions log. "Funnel rename decision N" is decision N of the decisions document of the funnel rename, which gives what candidates stores, answers and shows the funnel's stage names, and "funnel rename log DN" entry DN of its delivery's decisions log. "Revenue bands decision N" is entry N of the decisions document of the revenue-bands change, which makes a candidate's revenue estimate its headcount times a band of revenue per employee, under rules version 6. "Form5500 decision N" is candidates decision N of the decisions document of the Form 5500 change, which adds the `form5500` source and matches a row by its EIN and by every name it carries, under rules version 7. "OSHA ITA outcome N" is outcome N of the reader's section of the intent document of the OSHA ITA change, which adds the `osha_ita` source, reading each establishment's OSHA Form 300A summary as a headcount of employees with the hours worked beside it, under rules version 8, and "OSHA ITA P N" is entry PN of that change's delivery decisions log. "Headcount trend decision N" is outcome N of the decisions document of the headcount-trend change, which gives a candidate a series of headcount figures, one per kind per year, and a trend read within one kind from it, under rules version 9. "Parks decision N" is entry N of the decisions of the parks change, which derives industrial parks from the county parcel records scrapes holds (`D18-parks`). "Empty sites outcome N" is outcome N of the decisions document of the empty-sites change, which also runs the website search for a company whose site on record kept no page to site text and records what the search found against that site, and "empty sites decision N" is decision N of that change's delivery.

## The dependencies

candidates depends on two modules besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required at a published release with no `replace` directive, and `golang.org/x/net`, whose `html` package the website check parses a page's title with and `add_page` strips a page to its text with (`D15-website-check`, website log P5). Its `db` package brings the pure-Go SQLite driver, which keeps the release build cgo-free. candidates uses appkit's `db`, `version`, `services`, `page`, `identity`, `mcp`, `telemetry`, `events`, `scrapes` and `prompts`, and restates none of their contracts. It uses neither `artifacts` nor `connections`. It calls two siblings, each only through appkit's client for it, built from the services file's entry of its name: scrapes through the `scrapes` client from the `scrapes` entry, within a pass and also once at start, for its current `mn_parcels` run (`D03-serve`, `D06-passes`), and prompts through the `prompts` client, the installed interface appkit's design D27 describes, from the `prompts` entry, always as the caller of the `enrich` that started the targeted pass, so a prompt and its runs are that caller's; the event bus and the telemetry socket are reached through appkit's sinks. It names a third sibling, campaigns, only to link to it: the services file's entry `campaigns` gives the address a campaign's page is built on (`urls.Campaigns`), and candidates never calls campaigns; what campaigns tells it arrives as events on the bus (campaigns decisions 16 and 17). With no `prompts` entry there is no client and `website_search`, `site_text` and `brief` are `unavailable`, as `website_check` and `website_search` are without a checker (`D06-passes`, S 1). Outside the suite it calls nothing but the websites the website check and `add_page` fetch, the URL the website search confirms (website search decision 5), and Google's geocoding and routing services, which the routes client asks for a drive route only when a targeted enrich of `drive_route` runs (`D17-drive-route`), and Google's Places API, which the Places client asks only when a walk runs (`D19-walk`), all over outbound HTTP through `Process.HTTP`; with `IKIGENBA_SANDBOX` present the website check, `add_page` and the website search fetch only from an in-process stub on loopback (`D15-website-check`) and a walk searches only the in-process Places fake (`D19-walk`), while the routes client stays the real one, since a drive route is asked for only by hand and no stub stands in for it. Which release of appkit or `golang.org/x/net` is data that `AGENTS.md` and `go.mod` hold; the appkit release candidates requires is one that exports `prompts`, so appkit is released with it before candidates is built against it.

## Where the environment is read

`main` makes the one read of the environment that is not `Run`'s own: it calls appkit's `version.Read` exactly once, first, and holds the result, the **identity**, whose `String()` is the **display string**. It hands the identity to `page.New`, whose banner carries its `Release` and `Commit` to every page's footer and to the about screen, and the display string to the `mcp.ServerConfig` its `Process.MCP` builds and to `Run` as `Process.Version`. Nothing below `main` calls `version.Read`. `Run` reads every variable through `Process.LookupEnv`: `DRAIN_SECONDS`, `CANDIDATES_KEEP_PASSES`, `CANDIDATES_ROUTE_ORIGIN` and `GOOGLE_MAPS_API_KEY` once at start, through `settings.Read`; `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness; `IKIGENBA_SERVICES` once, when it starts to serve; and `IKIGENBA_SANDBOX`, whose presence chooses the website check's fetcher (`D15-website-check`). appkit's constructors also read `IKIGENBA_SERVICES` from the process environment; that read is appkit's.

`internal/judging` is warranted, and is named for the stage it serves (funnel rename decision 11; a test proves the owner by importing it from that path): the judgment rules are pure functions of estimates, evidence, a filing date, the clock, and a candidate's headcounts, brief labels and categories that the store's judge applies, and a test proves them by calling them; in `internal/sources` they would join a second concern to the sources', and in `internal/store` they could not be proved without a database. `internal/parks` is warranted for the same reasons (parks decisions 2 to 4): the parks rules are pure functions of a parcel row, the rules, the candidates' address keys and the parks already held, which the parks pass applies, and a test proves them by calling them; in `internal/store` or `internal/passes` they could not be proved without a database or a fake scrapes, and in `internal/sources` they would join a concern that is not a source's, since a parcel row makes no candidate. `internal/ppp` is a package the scaffold's test-file list does not yet name; it sits beside `internal/fmcsa` because each source keeps its own facts, formulas and parsing, as scrapes keeps one package per scraper, and the delivery adds it to that list. `internal/form5500` sits beside them for the same reason (form5500 decision 12), its plan-word table its own and unexported; the test-file list in candidates' `AGENTS.md` does not yet name it, and the delivery adds it there. `internal/oshaita` sits beside them for the same reason (OSHA ITA outcome 9), named for the `osha_ita` scraper as scrapes' package for it is, without the underscore a Go package name does not take; its figure, submission-time and EIN rules are its own and unexported, and the delivery adds it to that test-file list. The NAICS table is `internal/sources`' (`sources.NAICSCategory`, `D05-sources`), no longer `internal/ppp`'s, since `ppp`, `form5500` and `oshaita` each read a NAICS code (form5500 decision 19, OSHA ITA outcome 14) and a source that imported another source's package would join two sources' concerns. `internal/website` is warranted: the website check is outbound HTTP, a pace and a stub server, a concern no other package has, and it is proved by calling it over an injected client; in `internal/passes` it would join a network client to the engine, and the store never fetches. `internal/enrichers` is warranted: an enricher is a kind's inputs, its result and the check of a found value, pure functions of a candidate's subject that a test proves by calling them, and the store, the engine, the tools and the pages all need the kinds; in `internal/store` the derived kinds could not be proved without a database, in `internal/passes` the store could not reach them without importing the engine, and in `internal/sources` they would join a second concern to the sources'. `internal/routes` is warranted: asking Google for a drive is outbound HTTP to a vendor, with its own request shapes, key, counts and price, a concern neither the website check, which fetches candidates' own sites under its host guard, nor the engine has, and it is proved by calling it over an injected client; in `internal/website` it would join a vendor client to the fetcher of public pages, and in `internal/enrichers` it would join a network client to pure functions. The store builds the registry with neither a checker, a prompts client nor a routes client, `enrichers.New(enrichers.Config{})`, whose website, prompts and route kinds can do nothing, so the store still fetches nothing and calls no sibling. No matching package is added: the attach rule reads and writes links in one transaction per batch, so it is a store write (`store.Attach`, `D12-ingest`), and the normalization it compares is the sources' (`sources.NameKey` and its siblings), since a source produces a row's keys. No package is added for the pages, for the website search, for site text or for the brief either: a page is a store record, `add_page` is a tool over the store and the website check's one-page fetch, `website_search`, `site_text` and `brief` are enrichers, the client is appkit's, and a targeted pass's runs are the engine's work.

The registry lives in `internal/sources` with no default list: `fmcsa`, `ppp`, `form5500` and `oshaita` import `sources` for the reading's types, so a registry that named any source there would make them import each other. `Run` builds the fixed registry, `sources.New(fmcsa.New(), ppp.New(), form5500.New(), oshaita.New())`, whose order, `fmcsa`, then `ppp`, then `form5500`, then `osha_ita`, is the order a full ingest ingests in (`D05-sources`). The enrichers' registry has a fixed list instead, built by `enrichers.New(cfg)` from the parts that vary at run time, an `enrichers.Config` holding the website checker, the prompts client and the routes client: no import cycle forces an injected list, since `internal/enrichers` imports `internal/sources`, `internal/fmcsa` (for `fmcsa.Name`), `internal/website`, `internal/routes` and appkit's `prompts`, and nothing under it imports `internal/store` or `internal/passes`; `internal/store` imports `internal/enrichers`, and runs the derived kinds itself, so that a merge or split recomputes them in the same write as its ruling and its judging (`D12-ingest`). Its order, `drive_minutes`, `link_facts`, `website_check`, `website_search`, `site_text`, `brief`, `drive_route`, puts the derived kinds before the fetched ones and the website search before site text, since a site the search finds makes site text due as pages make the brief due, and `drive_route` last, since nothing it records makes another kind due; it is no longer the kinds' name order (`D16-enrichers`). `internal/parks` imports only appkit's `scrapes` and the standard library, and `internal/store`, `internal/passes`, `internal/tools`, `internal/pages` and `internal/places` (`D19-walk`, for `parks.Distance` and `parks.EarthRadius`) import it, so nothing under it reaches the database, the engine or a sibling. Which package imports which is guidance, not contract.

Template data types, tool argument and result types, copy constants and the constants a package uses only itself are declared by the document that owns the package's behavior, not here.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, and returns the exit code. It is scrapes' seam with `HTTP` kept for one use: scrapes and prompts are reached over the sockets the services file names, so a `Run`-level test serves a fake scrapes on a Unix socket its services file's `scrapes` entry names and a fake prompts on one its `prompts` entry names, and the only addresses candidates reaches of its own choosing are on a candidate's website, the home page the website check fetches, a page `add_page` is asked to keep and the URL a website search's agent names, which the search confirms (website search decision 5), fetched through `HTTP`; and the routes client asks Google's services through the same `HTTP`, so a `Run`-level test that drives a drive route hands in a client over a transport of its own and never reaches Google. The walk's Places client asks Google's Places API through the same `HTTP`, or, under `IKIGENBA_SANDBOX`, through the in-process fake `places.Fake`, so a `Run`-level test that drives a walk hands in a client over a transport of its own or names `IKIGENBA_SANDBOX` (`D19-walk`). A nil `HTTP` is no website check at all, so a `Run`-level test that sets neither `HTTP` nor `IKIGENBA_SANDBOX` fetches nothing, and one that sets `IKIGENBA_SANDBOX` in its lookup checks against the stub on loopback (`D15-website-check`). `Now` is the clock every time candidates stamps or compares is read from: a pass's started and finished, a link's first and last seen, a candidate's created and updated, a ruling's time, judgments's calculated time, the moment a judge measures a filing's freshness at, the prune's ordering, every event's time. `Sleep` is the pause the writer and the emitter wait with between delivery attempts, and the store waits with before it tries a busy write again (`D04-store`, decisions log P15). `After` is the sweeper's timer (`D06-passes`); the website check's, for each attempt's timeout and the pace between checks, and `add_page`'s fetch's and the website search's confirmation's, for their one attempt's timeout, `website.Timeout` (`D15-website-check`, `D16-enrichers`); the routes client's, for each request's timeout, `routes.Timeout`, which `Run` hands it as `routes.Client.After` (`D17-drive-route`); the Places client's request timeout, `places.Timeout`; and the engine's, for a targeted pass of a prompts kind's result poll and its wait when prompts' queue is full, which `Run` hands the engine as `passes.Config.After` (`D06-passes`). `Rand` is the source of every value candidates mints: request ids, the start read's among them (`D03-serve`, R-73LI-FCRL), pass ids, candidate ids, park ids and bus event ids. `Inherit`, `Now` and `Rand` are the caller's to give whenever `Args` is empty: `Run` has no default for any of them, and the choice of the process's own descriptor 3, `time.Now` and `crypto/rand.Reader` is made once, at the process boundary, by `cmd/candidates`. The event bus, telemetry, scrapes and prompts sockets reach `Run` through the services file `IKIGENBA_SERVICES` names (`D03-serve`). There are no live tests. The one test that execs the binary starts exactly one pass and no other: an `enrich` of the kind `website_check` over the empty store it started on, which proves the binary hands `Run` a fetcher, reads nothing from scrapes, and, with no candidate due, fetches nothing.

## Settings

candidates reads four values at start, in this order: `DRAIN_SECONDS`, the space's, `CANDIDATES_KEEP_PASSES`, the one its manifest's `[env]` declares (decision 17), and then `CANDIDATES_ROUTE_ORIGIN` and `GOOGLE_MAPS_API_KEY`, the two its manifest lists as secrets (`D02-cli`). The two integers are spelled as opsctl writes an integer: one or more ASCII digits, no sign, no leading zero, so `0` is refused; an unset or empty one is its default, 5 seconds and 20 passes, and digits beyond what an `int64` holds read as the largest `int64`. `settings.Read` refuses the first integer in that order that is not acceptable with a `*settings.Error` naming it, quoting its value and saying what was wanted, and `Run` writes its text after `candidates: ` as a usage error before it looks for its socket.

The two strings are never refused. `CANDIDATES_ROUTE_ORIGIN` is the **origin**, the address a drive route is measured from, as one string the routing service places; unset or empty it is `settings.DefaultRouteOrigin`, the centre of Sandstone, MN, the origin the ZIP table measures from, so the two kinds start from the same place. `Run` hands it to the store as `store.Config.Origin`, which puts it on every candidate's subject (`D04-store`, `D16-enrichers`), so a changed origin makes every candidate with a street due for `drive_route` again and takes effect at the restart that reads it. `GOOGLE_MAPS_API_KEY` is the key the routes client and the walk's Places client ask Google with; unset or empty, `Run` builds neither, `passes.Config.Routes` and `passes.Config.Places` are nil, and only a targeted enrich of `drive_route` and a walk are affected: they are refused `invalid` with `passes.NoRouteKey` and `passes.NoPlacesKey` (`D06-passes`, `D19-walk`), while the service starts and every other kind runs as before. With a key, `Run` builds `&routes.Client{HTTP: p.HTTP, Key: s.MapsAPIKey, After: p.After}` whether or not `IKIGENBA_SANDBOX` is present; with a key but a nil `HTTP`, which only a test gives, the client is built with no transport, is not ready, and the same enrich is refused `unavailable`. The key's value is never written to the trail, a pass record, a result or a diagnostic (`D17-drive-route`). The rules' numbers and evidence weights, the free-provider list, the government patterns, the NAICS prefixes, the page sizes, the batch size, the hourly sweep, the website check's tuning numbers and the routes client's timeout are constants of the documents that use them.

## Paths

Relative to `Process.Dir` (the process's working directory when empty) the database is `state/candidates.db`, opened with `db.Open`, the root package's `Migrations()` and `Process.Now`; `state/` is created when absent. candidates writes nothing outside `Dir` and nothing under it but the database: a run's rows are streamed and handled a batch at a time (decision 1), and the store reaches each record a batch needs by key, so a pass costs in proportion to its rows (`D04-store`, `D06-passes`).

## The addresses

`internal/urls` holds the addresses candidates builds that are not its own paths, and one that is. The **auth address** is the `URL` of the services file's entry `auth`, trailing `/` removed, or, with no such entry, built from the request's scheme and host with a leading `candidates.` removed (`urls.Auth`), which the pages' banner links to (`D08-pages`). The **scrapes address** is the `URL` of the services file's entry `scrapes`, every trailing `/` removed (`urls.Base`, `urls.Scrapes`), and empty when the file has no such entry: a relative address would name a page of candidates' own. On it are built a row's page at scrapes, `<scrapes address>/runs/<run>/rows/<source id>` (`urls.RowPage`, decision 15), which a candidate's links point to, and a run's page, `<scrapes address>/runs/<run>` (`urls.RunPage`), which an ingest or parks pass started by a `scrape.finished` delivery points to, as do the parks page's summary and a park's page for the run its parks were derived from (`D08-pages`); each is empty when the address, the run or the source id is empty. The source id is path-escaped, so an id holding `/` stays one segment. The **campaigns address** is built the same way from the services file's entry `campaigns` (`urls.Campaigns`), and empty when there is no such entry or the file cannot be read; on it is built a campaign's page at campaigns, `<campaigns address>/campaigns/<campaign>` (`urls.CampaignPage`), which each campaign use on the candidate page links to (`D08-pages`, campaigns decision 17), empty when the address or the campaign is empty, the campaign id path-escaped as the source id is. The entry is used for nothing else: candidates never calls campaigns (`D03-serve`). The page paths `/prospect-lists/<id>`, `/candidates/<id>`, `/passes/<id>` and `/parks/<id>` are spelled by the templates, which build them from the data they receive. The **page path**, where a kept page's text is served, `/candidates/<candidate>/pages/<number>` (`D08-pages`), is built by `urls.PagePath` instead, since two packages give it: the tools answer it as a page's `path` (`D10-tools`) and the candidate page links each page to it (`D08-pages`).

## Recorded decisions

- The layout is scrapes' with `internal/sources` in place of `internal/source` and one package per source, `internal/fmcsa`, `internal/ppp`, `internal/form5500` and `internal/oshaita`, as scrapes has one per scraper, `internal/passes` in place of `internal/runs`, and `internal/judging` added; scrapes' `internal/scrapers` registry package has no counterpart because the registry is `sources.Registry` and `Run` lists its four sources. The PPP, Form 5500 and OSHA ITA sources are each a package beside the FMCSA one, the smallest change to this layout; the packages added since, `internal/website`, `internal/enrichers` and `internal/parks`, are each warranted under Packages. Pages and site text add no package (Packages).
- The domain records (`store.Candidate`, `store.Link`, `store.Judgments`, `store.Ruling`, `store.ProspectList`, `store.Reject`, `store.Page`, `store.CampaignUse`, `store.Pass`) are the store's, as scrapes' `store.Run` is; a source's per-row reading and per-source estimate are the sources' (`sources.Reading`, `sources.Estimate`), since a source makes them and the store keeps them as given. A link keeps its row's whole reading, evidence, dates and category included, so neither the `link_facts` enricher nor a judge needs a read of scrapes.
- Matching, merging and splitting are store writes (`store.Attach`, `store.MarkGone`, `store.Decide`), each one transaction, so a ruling and the links it moves, or a batch and the candidates it creates, cannot be seen half done; a batch the database answers busy is paused and tried again whole by the store (`D04-store`). A judge of every candidate is not one transaction: the engine walks `JudgeAll` a page at a time, so it may be seen part done (`D13-judging`). `decide`, `exclude` and `include` reach the store directly, as the prospect list and reject tools do; the engine is not in their path, since neither a ruling nor a prospect list reads scrapes or waits for a pass.
- The root package exports the ZIP table as a typed map, `ZipDrive() map[string]int64`, rather than the CSV file: every consumer wants minutes by ZIP, and a test reads the embedded table through it without opening the checkout.
- No `Process` field names scrapes' address: the services file names its socket, as it names the bus's and telemetry's.
- `Process.Inherit`, `Process.Now` and `Process.Rand` are required whenever `Args` is empty, as in scrapes; no requirement states the precondition, because no permitted test can observe a default.
- A `scrape.finished` delivery reads the run's record from scrapes before it records a pass (orchestrator ruling; the behavior is `D06-passes`'): a run not found or not `done` is `Skip` with no pass recorded; any other failed read records the pass and fails it `scrapes`, answering `OK`; `Fail` is kept for a pass already running, the drain and the database failing. `Deliver` holds the delivery's context and calls `store.AddPass` and `store.FailPass` after that read, so no signature changes. A `cron.judge_candidates.fired` delivery reads nothing from scrapes; `Deliver` tells the two by the event's name, so the engine gains no entry point.
- A pass started by a delivery reads scrapes as the service identity (decision 12, binding); that identity is the engine's (`D06-passes`), and no `Process` field carries it.
- candidates accepts the judge's trigger by its exact name, `trail.AcceptedJudge`, `cron.judge_candidates.fired` (cron emits `cron.<slug>.fired`), with no pattern, as scrapes accepts its triggers; the slug `judge_candidates` is the one the owner creates on a space.
- `sources.Rules`, the rules version, is declared without its value: no requirement states a version, a test reads the value the source declares, and `D13-judging`'s prose says which it is. The revenue-bands change moves it to 6 (revenue bands decision 15) and changes no declaration of it. The Form 5500 change moves it to 7 (form5500 decision 21), since every source's reading gains keys and a source joins, and changes no declaration of it either. The OSHA ITA change moves it to 8 (OSHA ITA P2), since a source joins with evidence and headcounts the judge weighs and a full ingest re-reads every row under one version, and changes no declaration of it either. The headcount-trend change moves it to 9 (headcount trend decision 14), since the judge writes a series and a trend it did not before while no reading or derived fact changes, so a judge over everything carries it without a full ingest, and changes no declaration of it either.
- The category names and evidence kinds are stored and answered as given, so they are contract constants with their values (`sources.Category*`, `sources.Evidence*`); an evidence item's description is copy, a constant `D05-sources` declares without its value.
- A reading carries one category word and its evidence items each name their source; `sources.Category` pairs a category with the source that gave it, for the facts (`D04-store`). `Evidence.Source` is any source's name, not only a scraper's, and `judging.Operating` takes any evidence list, so evidence from an enrichment joins a candidate's without a new shape: the website check's evidence, `sources.EvidenceWebsiteLive`, names `sources.WebsiteCheck` as its source (`D13-judging`).
- Prospect lists add no package: a prospect list's constants, validators, types and reads are the store's (`D04-store`) and what a prospect list is `D14-prospect-lists`', because the tools and the store both need the validators and both already import `store`.
- The fleet verdict is a reading's before it is a fact (cohorts log 11): the `link_facts` enricher reads the stored link reading, not the row (`D16-enrichers`), so `sources.Reading` carries `FleetVerdict`, with the row's `PowerUnits` and `Drivers`, right after `Fleet`, which is still written so the release before reads new readings. The verdict words are stored and answered as given, so they are contract constants with their values (`sources.FleetPass`, `sources.FleetFail`, `sources.FleetUnknown`), beside the class tags; a link an earlier release stored reads with an empty verdict, which its readers take as unknown (`D05-sources`, `D16-enrichers`).
- **A reading carries its headcount** (revenue bands decision 1): `sources.Reading` gains `Headcount`, a `*sources.Headcount`, right after `PowerUnits` and `Drivers`, nil when the row gives none. `sources.Headcount` names the scraper whose row gave it and its kind, beside the count and the date it is as of, so `link_facts` copies it into the facts row and the judge ranks it without the link (`D16-enrichers`, `D13-judging`); the store's facts and the judge's `Staff` hold it as declared here rather than a copy of their own. The kind words are stored and answered as given, so they are contract constants with their values (`sources.HeadcountEmployees` and its siblings), declared beside the fleet verdicts in a requirement of their own as those are; all five are declared though only `jobs` and `drivers` are given now, so the later sources slot in without a rules change (revenue bands decision 6). A link an earlier release stored reads with a nil `Headcount` (`D05-sources`).
- **A reading carries its name keys and its EIN key** (form5500 decisions 14 and 15): `sources.Reading` gains `NameKeys`, a `[]string`, right after `NameKey`, and `EINKey`, a string, right after `NameKeys`, so the keys stay together before `PhoneKey` and `DomainKey`. `NameKey` stays, so a link an earlier release stored, whose reading has no `NameKeys`, still holds its one name key (`D12-ingest`). `sources.NameKeys` and `sources.EINKey` are declared beside `sources.NameKey` and `sources.PhoneKey`, their behavior `D12-ingest`'s; `sources.NAICSCategory` is declared beside them, its behavior `D05-sources`'. The evidence kind `sources.EvidenceForm5500Filing` joins the other evidence kinds in their requirement, so that requirement and the one listing the categories by its id are re-minted; its copy constant, `sources.DescribeForm5500Filing`, is declared with the other descriptions in `D05-sources`.
- **A reading carries the figures it shows** (OSHA ITA outcomes 11 and 16, OSHA ITA P6): `sources.Reading` gains `Establishment`, a string, and `Year`, `Employees` and `Hours`, each an `*int64`, at its end after `GovernmentMatch`, and `sources.Headcount` gains `Hours`, an `*int64`, at its end after `AsOf`. They are the first fields of a reading that one source alone fills and no matching or judging rule reads: the card and the `candidate` tool show each OSHA link's establishment name, filing year, annual average employees and hours worked (`D08-pages`, `D10-tools`), and they show them from the link's stored reading, as `link_facts` and the judge read everything else from it, so neither reads scrapes. The four hold the row's values as read and are kept when the hours fall outside the band and the reading's `Headcount` is nil (OSHA ITA P6.2), so a figure a typo made shows beside the headcount it withheld; they are empty or nil for every other source. `Headcount.Hours` carries a headcount's hours worked beside its count wherever the count goes (OSHA ITA outcome 11): into the facts row's headcounts, one entry per link with its own hours (`D16-enrichers`, `D04-store`), and into the judge's sum of one business's sites (OSHA ITA P6.3, `D13-judging`); it is nil for every source but `osha_ita`, and nil on an OSHA headcount whose row gives no hours. Both are added last so the fields before keep their order, and since a stored reading's members are named by its fields the new members are additive: a reading an earlier release stored reads with them empty or nil, and the release before reads a new reading, ignoring them (`D04-store`). The evidence kind `sources.EvidenceOSHAITASummary` joins the other evidence kinds in their requirement, so that requirement and the one listing the categories by its id are re-minted; its copy constant, `sources.DescribeOSHAITASummary`, is declared with the other descriptions in `D05-sources`.
- **A reading tells its trade names and a mailing address** (the facts-from-the-candidate change): `sources.Reading` gains `TradeNames`, a `[]string`, `Mailing`, a `bool`, and `MailingAddress`, a `*sources.Address`, at its end after `Hours`, so the orders can put a trade name over a legal name and a business location over a mailing address, and a mailing address a row gives beside its location is kept and shown (`D05-sources`, which declares `sources.Address` and says how each source fills them). `Name` stays the row's own name and `Street`, `City`, `State` and `Zip` its one address, so no existing member changes its meaning; the three are added last, and a reading an earlier release stored reads with them empty, false and nil, and the release before reads a new reading, ignoring them (`D04-store`).
- **The OSHA ITA source pads its own EIN** (OSHA ITA outcome 10): an `ein` of exactly eight digits is read as nine with a leading zero, since the source drops the zero in some years, so KTM Paving's years share one EIN key; the padding is `internal/oshaita`'s, and `sources.EINKey`, whose behavior is `D12-ingest`'s, is unchanged, so every other source still reads anything but nine digits as no key (`D05-sources`).
- **The band and the `headcount` estimate are `internal/judging`'s** (revenue bands decisions 6 to 11): `judging.PickHeadcount`, `judging.ChooseBand` and `judging.HeadcountEstimate` are pure functions of a candidate's headcounts, brief labels and categories, which the store's judge applies to the facts row and a test proves by calling, and `judging.Staff`, `judging.Band` and `judging.Choice` are what they answer. The estimate's source word, `judging.HeadcountSource`, the band names and the chosen-by words are stored in an estimate's source and facts and answered as given, so they are contract constants with their values, declared together in a requirement apart from the types and functions as the sources' constants are; the band numbers and the keyword table are `D13-judging`'s. No package is added: in `internal/sources` the band would join a judgment about the candidate to the reading of one row (revenue bands, Rejected), and in `internal/store` it could not be proved without a database. `HeadcountEstimate` answers a `sources.Estimate`, so the judge writes it into the estimates table beside the sources' and the card and the tools show it as any estimate (revenue bands decision 16).
- **The series and the trend are `internal/judging`'s** (headcount trend decisions 1 to 9): `judging.HeadcountSeries` and `judging.HeadcountTrend` are pure functions of a candidate's headcounts and of the series formed from them, which the store's judge applies to the facts row and a test proves by calling, and `judging.Series`, `judging.Figure` and `judging.Trend` are what they answer; the store keeps a `judging.Series` as declared here rather than a copy of its own. The trend words are stored, filtered on and answered as given, so they are contract constants with their values; the thresholds, three years back, a window of four years, two years at the least, a fifth and five people, are the owner's table (headcount trend decision 8), so they are declared as constants with their values too, untyped so that a rule reads them in exact integer arithmetic, together in a requirement apart from the types and functions as the band constants are; how the series is formed and the trend read is `D13-judging`'s. No package is added: the series and the trend are judgments about a candidate from the headcounts `judging.PickHeadcount` already ranks, and in `internal/store` they could not be proved without a database.
- `passes.Record` gains the pass's `Kind` and `Origin`, and its count of candidates judged is `Judged`, where an earlier name for the same count was; with the funnel rename it gains `Scraper`, the one scraper a hand ingest names; its JSON is `D06-passes`'.
- The website check's vocabulary is `internal/sources`', beside the class tags and fleet verdicts: the kind `sources.WebsiteCheck`, which is also the source its evidence names, and the states `sources.WebsiteHTTPS`, `WebsiteHTTP`, `WebsiteNone` and `WebsiteUnknown`, stored and answered as given, so contract constants with their values. `internal/store`, `internal/judging` and `internal/enrichers` all need them and import `sources`; the website check's kind keeps its name there rather than moving to `internal/enrichers` beside the derived kinds' (`enrichers.KindDriveMinutes`, `enrichers.KindLinkFacts`), since the names the code uses stay as they are. The pass vocabulary (`store.KindEnrich` and the origins) stays the store's, beside the other kinds (`D04-store`). `sources.Rules` is still declared without its value, and `D13-judging`'s prose says which it is; moving the facts from the judge to the enrichers leaves it as it was, since the values written do not change.
- `passes.Config` keeps `Website`, the checker the engine's website check fetches with, and gains `Prompts`, appkit's `prompts` client, after `Scrapes`, beside the other sibling's client; the engine builds its registry from the two, `enrichers.New(enrichers.Config{Website: cfg.Website, Prompts: cfg.Prompts})`, rather than taking a registry: the derived kinds need neither, so a field for a registry would carry nothing the engine cannot build, and the engine needs the client itself for `Show`, `Run` and `Result`. A nil `Website` means only that the kinds that fetch through it are not ready: `Enrich` asked for `website_check` is refused `unavailable`, and so is a targeted enrich of `website_search`, whose named site is confirmed through the checker, while an enrich of every kind, the ingest's follow-on included, runs the derived kinds and skips the website check (`D06-passes`). A nil `Prompts`, a services file with no `prompts` entry, means only that the prompts kinds, `website_search`, `site_text` and `brief`, are not ready, so a targeted enrich of any of them is refused `unavailable` (site text decision 21); an untargeted enrich never walks them.
- **`passes.Config` gains `After`, last,** the timer the engine's own waits end on, the result poll and the queue-full wait of a targeted pass of a prompts kind, nil meaning `time.After`; `Run` sets it to `Process.After`, the timer the sweeper and the website check already wait on. Decision 8 measures the poll on `Process.After`, and a test that holds the channels drives every wait of a pass without real time passing; a test tells the engine's two waits from the sweeper's and the checker's by their durations, `passes.PollInterval` and `passes.QueueWait` (`D06-passes`).
- **`passes.Config` gains `Stderr`, last,** the engine's own diagnostic stream, nil meaning its diagnostics are discarded; `Run` sets it to `Process.Stderr`, as it hands `p.Stderr` to `db.Config.Stderr`, so no `Process` field is added. A pass that failed `store` on `us` left no trace of the error that ended it (decisions log P13), so the engine writes that error there (`D06-passes`). That `Run` sets it is described, not required: no permitted test can fail the store under `Run`, since a test fails only a handle it hands in itself (candidates' `AGENTS.md`).
- **`passes.Config` gains `Routes`, after `Website`,** the routes client the engine's drive routes are asked through, and the engine builds its registry with it, `enrichers.New(enrichers.Config{Website: cfg.Website, Prompts: cfg.Prompts, Routes: cfg.Routes})`, as it does with the checker and the prompts client. `Run` builds it from the settings and the run seam, so no `Process` field is added: the client reuses `Process.HTTP`, the one outbound client, and `Process.After`, the one timer. A nil `Routes` means no key: a targeted enrich of `drive_route` is refused `invalid` with `passes.NoRouteKey`, a corpus enrich walks it and writes nothing, and nothing else changes (`D06-passes`). A test observes what `Run` built by use: it drives a targeted enrich of `drive_route` over a transport of its own and compares the requests it receives with those a `routes.Client` it builds itself sends for the same origin and destination, which `D17-drive-route` makes deterministic, so the key and the origin are proved without this design stating how either travels.
- **No stub stands in for the routing service** (departure from the website check's rule that nothing a sandbox runs reaches outside): under `IKIGENBA_SANDBOX` `Run` still builds the real routes client over `Process.HTTP`. A drive route runs only when the owner asks for one by name over a target, never over the corpus or after an ingest, and the finish line's one sandbox check is made from a shell holding the key, so the stub would only stand between that check and what it is meant to prove. No test reaches Google: every test hands `Process.HTTP` a transport of its own. The walk's Places client is the exception: under `IKIGENBA_SANDBOX` it searches the in-process fake `places.Fake`, and no request to `places.NearbyURL` leaves the process (`D19-walk`, walk decision 3).
- **The origin rides the store's config, not the enrichers'** (`D04-store`, `D16-enrichers`): the drive route's inputs include the origin, and the store computes inputs and the facts row's drive decision from a candidate's subject, so the store must know the origin to tell whether a route still matches; `store.Config.Origin` puts it on every subject, and the registry stays one the store can build with an empty config.
