# D08-pages

What candidates draws as HTML: `internal/pages`, the six templates `landing`, `candidate`, `pass`, `tools`, `about` and `notfound` and the data each is executed with, and the handler that answers `/`, `/candidates/<id>`, `/passes/<id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it (decision 15). It is scrapes' pages with the shortlist and the passes on the landing page, a page per candidate and a page per pass below it.

## The pages

The landing page shows the shortlist with no filter, every active candidate the owner has not excluded that a judge has judged, ranked by operating confidence with those that have none last (`D13-scoring`): one window of it, `paging.DefaultLimit` ranked (appkit's D25), each linked to its candidate's page; then one window of the passes, `paging.DefaultLimit` newest first in the store's pass order, each linked to its page. Both lists grow, so each navigates (`shape/`, Listing; `design/`, the listing entry and its two-list form). Two lists share the page, so each has its own query parameter, `shortlist_page` and `passes_page`, each the first value of its name in the query, and nothing else is read from the query; the detail routes read none. A list's **page value** asks for one of four windows, and **decodable** names all four. The empty value asks for the **first window**. The token the list's tool issues as `next`, an **after-token** (`shortlist` and `passes`, `D10-tools`), asks for the window after the entry it names, exactly what that tool answers for the same `page` with no `limit` (and, for `shortlist`, no filter), read through the store's positioned windows (`Shortlist`, `ListPasses`, `D04-store`). The way back is a token the page issues itself, since neither tool has a backward step: a **before-token** is `paging.Token{Tool: "shortlist-before"}` or `paging.Token{Tool: "passes-before"}` over the same two key fields, the operating key and candidate id or the started text and id, carried in the same parameter, the checksum appkit's token carries keeping it apart from the after-token; it asks for the `paging.DefaultLimit` entries that precede the one it names in the list's order, drawn in that order, whether or not an entry still has that key. The literal word `last`, which decodes as no token, asks for the **last window**, the lowest-ranked `paging.DefaultLimit` entries of the shortlist or the oldest `paging.DefaultLimit` passes, drawn in the list's order. The page reads a before-token's window and the last window from the store's reversed windows, `ShortlistReversed` and `ListPassesReversed` (`D04-store`), from the token's position or, for `last`, from the end of the list, asking for one entry more than the window and drawing the first `paging.DefaultLimit` of them reversed, so it learns whether the window **underflows**: when at most `paging.DefaultLimit` entries precede a before-token's position, or the list holds at most `paging.DefaultLimit` entries in all for `last`, the window asked for is that list's first window, and the page answers a 303 whose `Location` is `/` with the other list's parameter kept as the request carried it, so each list's first window keeps one address and paging one list never resets the other; when both lists underflow, both parameters are dropped. Neither parameter changes the other list's window. The template receives, for each list, its page value as the request carried it (`ShortlistPage`, `PassesPage`: empty on the first window, `last` on the last), the before-token of the window's first entry (`ShortlistPrev`, `PassesPrev`: empty on the first window and on an empty after-window), and the after-token of its last entry when more follow (`ShortlistNext`, `PassesNext`: on an after-window exactly the tool's `next`, on a before-window always set, on the last window empty); what it draws from them, the two navs with First, Prev, Next and Last included, is the asset's. A value either parameter cannot decode, one list's token in the other's parameter, a token another tool issued, or a word such as `bogus` or `LAST`, is the not-found page, never a first window. A shortlist row's rank is its place in the whole ranked shortlist, not in its window, on every window: a window's first row is ranked one more than the number of entries before it, which the store counts (`ShortlistOffset`), through the token's position for an after-window and through the window's first entry, less that entry, for a before-window or the last window. No filter applies, so the landing names no cutoff: drive minutes, the fleet test and the government match are shown beside each row and remove no one. The number of rows shown follows `paging.DefaultLimit`, and the template states no count of its own. No row of either list shows a phone or an email.

`/candidates/<id>` is one candidate: its display fields and tags, its assessment, the two judgments and the facts beside them as the last judge, rebuild or ruling wrote them, with the operating evidence behind it, each estimate with the facts it used, each link with its last seen and gone, linked to its row's page at scrapes, and the rulings that name it. A merged candidate's page shows its id, status, the candidate it was merged into (linked), its created and updated times and its rulings, and no display field, tag, assessment, estimate or link: the store keeps its display fields as they were at the merge, and the page data blanks them, so the page says only what it merged into (the template's comment). An active candidate not yet judged shows the template's not-judged state: an ingest stores its rows and judges nothing.

`/passes/<id>` is one pass's record in full; when it failed, the reason's sentence, which the template chooses from `Reason`; when a scrapes run's delivery started it, its trigger linked to the run's page at scrapes. A pass still `running` shows its record as it stands; the page does not stream.

An unknown candidate id, an unknown or pruned pass id, and a path whose id is not a well-formed candidate or pass id are answered alike, the not-found page with 404, byte for byte the not-found page of any other path.

The tools page lists the seven tools in the catalog's order (`D10-tools`), each with its one-line description. The about screen shows the service's name, the banner's `Release` and `Commit` and `pages.Description`. Any other path is the not-found page, 404, whatever the method.

The landing page is the root of the banner's trail; a candidate page is one level below it, named by the candidate's id at `/candidates/<id>`; a pass page one, named by the pass's id at `/passes/<id>`; and the tools page and the about screen one, `pages.ToolsLevel` and `pages.AboutLevel`. The banner's user is the caller's email, with auth's profile and sign-out addresses built on `urls.Auth` (`D01-layout-and-run-seam`).

## Who started a pass

A pass says what started it by its `Origin` (`D04-store`): a `rebuild` call's pass, origin `rebuild`, shows its caller's email, or user id when the caller has no email; an ingest a scrapes run's delivery started, origin `run`, shows its trigger, the run id, linked to the run's page at scrapes, and the template names scrapes as its starter; a judge the daily cron trigger's fire started, origin `cron`, shows its trigger, the slug `judge_candidates`, unlinked. The data carries `Kind` and `Origin` as stored, `StartedBy` (a rebuild's caller's email, or its user id when the email is empty; empty for any other origin) and `RunPage` (set only for origin `run`); the template keys the starter on `Origin`, and the words are the template's. The landing's pass rows carry `Kind`, `Trigger` and `Judged`, and no origin.

## Numbers as shown

The templates receive numbers already formatted, as their comments name them: dollars as `$` and the whole number of dollars with a comma between each group of three digits; operating and revenue confidences, evidence weights, an estimate's confidence and a link's confidence with two decimals, though the tools answer the judgments at full precision (`D10-tools`); drive minutes, on the landing and the candidate page alike, as decimal text, empty when absent; filing dates, the known-since date and the newest filing as `YYYY-MM-DD` in both the `datetime` and the text; other times RFC 3339 to the second for a `time` element's `datetime`, and a `...Text` field in the page's layout, `pages.MinuteLayout` for the landing's passes, a link's first and last seen and a ruling's time, `pages.SecondLayout` for a candidate's created and updated, an assessment's calculated time and the pass page. An empty judgment gives empty strings, never `0.00` or `$0`, so the template can show that there is no evidence or no estimate. Counts, ranks and the rules version are integers. A time not yet set gives both strings empty. The landing shows a candidate's distinct category words, each once in ascending order; the candidate page shows each category with the source that gave it, in the order stored.

## Pages show what is stored

Pages make no call to scrapes and change no record: a pass's page shows the status the store holds, and the two judgments and the facts beside them are the stored assessment's, as the last judge, rebuild or ruling wrote them (`D13-scoring`). Nothing decays between judges, and freshness is measured when a judge runs, so no page reads a clock and `pages.Config` carries none. Candidates and passes belong to no one (decision 14), so every signed-in user sees the same pages.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so nginx sends a request with no credential to sign in before it reaches candidates, and `D03-serve` mounts this handler inside `identity.Require`. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. On `/` the two page values are decided next, both before the store is read: an undecodable one is the not-found page, the same with the store unavailable. The landing with decodable values, the candidate and the pass pages answer 503 with a read refusal (`D03-serve`) when the store cannot be read, the landing drawing no window and making no redirect; the about, tools and not-found pages are served without reading it.

## Recorded decisions

- Candidate pages at `/candidates/<id>` and pass pages at `/passes/<id>` (decision 15). A path whose id fails `store.ValidCandidateID` or `store.ValidPassID` is not looked up.
- `ServiceName` and `Description` are `D01-layout-and-run-seam`'s; the layouts are contract constants with values here, as in scrapes. `ShortlistShown` goes: the landing shows `paging.DefaultLimit` of each list, the window the matching tool answers for the same `page` and no `limit`, so the page and the tool agree on every window.
- One data type per thing a template draws, each field list the template comment's in its order. Every value a template receives is a string, a bool, an `int64`, a slice or a pointer to a struct; the template comments' `int` fields are `int64`, as the store holds counts.
- **The landing applies no filter** (intent 18): it reads the shortlist of `store.ShortlistFilter{}`, the zero filter, so every active candidate the owner has not excluded that a judge has judged is on it, and drive time, the fleet test and the government match are shown beside each row and decide nothing. The `shortlist` tool takes the filters; the page takes none, so the landing data loses `MaxMinutes` and `MinRevenue` and the template names no cutoff. The number of rows shown is `paging.DefaultLimit`, which the template does not state.
- **Every judgment is the store's** (`store.Assessment`, `D13-scoring`): the landing and the candidate page show what the last judge, rebuild or ruling wrote, so a page and the tools agree, and a judgment moves once per judge rather than per request. Freshness is measured when a judge runs, not when a page is drawn, so the pages show no freshness of their own and need no clock.
- **The landing's forward tokens are the tools'**: an after-token in `shortlist_page`, and `ShortlistNext`, are `paging.Token{Tool: "shortlist"}` over a shortlist entry's operating key (`Assessment.OperatingKey`) and candidate id, and an after-token in `passes_page`, and `PassesNext`, `paging.Token{Tool: "passes"}` over a pass's started text and id (`D04-store`), so a window on the page and the tool's answer for the same `page` are one window, read through the same store window, and a token on the page can be handed to an agent. They are strings, empty on the first window and when nothing follows, so the template tests them as it tests any other field.
- **The page steps back and jumps to the end** (`design/`'s listing entry, with Prev and Last, decided 2026-10-13): each parameter also carries a before-token the page issues under its tool's name with `-before` appended, or `last`, and the landing data gains `ShortlistPrev` and `PassesPrev`. `shortlist` and `passes` decode only their own tokens, so they refuse a before-token and `last` with `paging.BadPage` as any page they did not issue (`D10-tools`), and the agreement with the tools holds for the empty value and after-tokens only. `last` is no token: appkit's `paging` (v0.26.0) encodes a token as unpadded URL-safe base64 of a payload and a four-byte checksum and refuses a decoded value shorter than four bytes, and `last` decodes to three; the definitions test it only after both tokens regardless.
- **An underflow answers 303**, rather than drawing the first window under another address, so each list's first window has one URL and its page value is always empty. The redirect drops the underflowing list's parameter and keeps the other's as the request carried it, which is URL-safe since only a decodable value gets this far and appkit's tokens are URL-safe base64; when both underflow at once both are dropped, so one redirect lands on the first windows. candidates had no redirect before; the 303 is the listing entry's.
- **The last window is the lowest-ranked `paging.DefaultLimit` entries, and the oldest `paging.DefaultLimit` passes**, aligned to the end of the list, not the final window of the Next walk: the two are equal only when the entries number a multiple of `paging.DefaultLimit`. Prev from the last window steps back in windows aligned to the end until one underflows.
- **Rank continues on a reversed window too**: a before-window's or the last window's offset is one `ShortlistOffset` over the window's first entry's operating key and candidate id, less one, since the count includes the entry it is given; it is one query, as an after-window's is, and the window's own read cannot give it, since that read holds only the window and the one entry beyond it. A judge between the two reads can skew one page's ranks, which is accepted as for an after-window.
- **One parameter per list** (`design/`'s two-list form): `shortlist_page` and `passes_page`, never `page`, and the page data carries each list's own token so the asset's navs carry the other list's along. An undecodable value in either is the existing not-found answer, decided after identity, path and method and before any store read, so a URL carrying a token the page never issued names no page and the answer is the same with the store unavailable.
- **Rank continues across windows** (decided 2026-10-13): a row's `Rank` is its place in the whole shortlist with no filter, so a person reading a later window sees where it stands. The alternatives were a rank counted from 1 within each window, which would show two rows ranked 1 for different places, and no rank on later windows, which would leave a deep window unplaced. A later window's offset is one `COUNT(*)` over the shortlist window's own filters with its position inverted (`ShortlistOffset`, statement `ShortlistBefore`, `D04-store`), a `SEARCH` on `assessments_operating`; the first window's offset is 0 and costs no query. The count is of the entries that do not follow the position, the position's own entry included, since a token names the last entry of the window before; a strict `candidate < ?` would leave that entry out and rank every later window one too low. The count is read apart from the window, so a judge between the two reads can skew one page's ranks; the reads are each consistent, and the next request agrees, which is accepted.
- A merged candidate's page data blanks its display fields and tags, and carries no assessment, estimate or link, as the template's comment and the mock show; the store keeps them (decision 10, coordinator decision C3). Its rulings are shown, since they record the merge.
- Money is shown in whole dollars: the revenue range and an estimate's low and high are stored as whole dollars, so nothing is rounded on the way to the page.
- **Confidences and weights show two decimals** (orchestrator decision 8): the tools answer them at full precision for agents; a person reads two decimals. An empty operating confidence or revenue estimate is an empty string, never 0 (intent 2), and the template says which.
- **The starter is keyed on `Origin`**, not on `Trigger`: a run id and a cron slug are both triggers as stored, so only the origin tells a scrapes run's ingest from a cron fire's judge. `RunPage` is built only for origin `run`, and `StartedBy` only for origin `rebuild`, since a delivery's caller is the service identity, not a person.
- **The landing's categories are words only**, each once, in ascending order: the row is narrow and its question is which kinds of business the candidate is; the candidate page shows each category with the source that gave it.
- **The landing lists one window of the passes**, not every kept pass: D25 asks every list an agent or a person can add to to be paged, and a retention setting raised far enough would make the whole list unbounded; the old loop over `ListPasses` until it answered short goes. The rest are reached through `passes_page` or the `passes` tool.
- An unknown, pruned or malformed id is one not-found answer, byte for byte the not-found page of any other path; a database outage is a plain-text 503 read refusal, as in scrapes.

## Consumer tasks

`web.Handler` (`D03-serve`) builds `s, err := pages.Load()` and mounts `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store})` inside `identity.Require` for the page paths. `D01-layout-and-run-seam`'s about requirement executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}` and `b.Trail` set to `[]page.Level{pages.AboutLevel}`. The handler reads `sp := r.URL.Query().Get("shortlist_page")` and `pp := r.URL.Query().Get("passes_page")`, tries a non-empty `sp` with `paging.Token{Tool: "shortlist"}.Decode(sp, &key, &id)` (`key` an `int64`), then `paging.Token{Tool: "shortlist-before"}.Decode(sp, &key, &id)`, then `sp == "last"`, and a non-empty `pp` likewise with `passes`, `passes-before` and `last` into `&started, &pid`, answering the not-found page if either fits none, then builds the landing, `d` being `store.ShortlistFilter{}`, no filter: for an empty value or an after-token `rs, err := st.Shortlist(ctx, d, key, id, paging.DefaultLimit+1)` and `off, err := st.ShortlistOffset(ctx, d, key, id)` when `id` is not empty (0 otherwise); for a before-token `rs, err := st.ShortlistReversed(ctx, d, key, id, paging.DefaultLimit+1)` and for `last` `st.ShortlistReversed(ctx, d, 0, "", paging.DefaultLimit+1)`, the window the first `paging.DefaultLimit` reversed, underflowing when no more came back, and `off` one less than `st.ShortlistOffset(ctx, d, e.Assessment.OperatingKey, e.Candidate.ID)`, `e` the window's first entry; each row ranked `off + i + 1`; and `ps, err := st.ListPasses(ctx, started, pid, paging.DefaultLimit+1)` or `st.ListPassesReversed(ctx, started, pid, paging.DefaultLimit+1)` (`"", ""` for `last`) the same way; when either underflows it answers `http.Redirect(w, r, loc, http.StatusSeeOther)` with `loc` `/` or `/?passes_page=` followed by `pp` (or `/?shortlist_page=` and `sp`), and otherwise sets `ShortlistPage` to `sp` and `PassesPage` to `pp`, `ShortlistPrev` to `paging.Token{Tool: "shortlist-before"}.Encode(e.Assessment.OperatingKey, e.Candidate.ID)` of the first entry shown and `PassesPrev` to `paging.Token{Tool: "passes-before"}.Encode(p.Started.UTC().Format(time.RFC3339), p.ID)` of the first pass shown, unless the value is empty or nothing is shown, and `ShortlistNext` to `paging.Token{Tool: "shortlist"}.Encode(r.Assessment.OperatingKey, r.Candidate.ID)` or `PassesNext` to `paging.Token{Tool: "passes"}.Encode(p.Started.UTC().Format(time.RFC3339), p.ID)` of the last entry shown when an after-read came back long or the value is a before-token; a candidate page with `st.GetCandidate`, `st.GetAssessment`, `st.Estimates`, `st.Links` and `st.Rulings`, a link's address with `urls.RowPage(urls.Scrapes(cfg.ServicesPath), l.Run, l.SourceID)`, and the assessment view from `a`'s judgments and facts as stored, no clock read; a pass page with `st.GetPass`, `urls.RunPage(urls.Scrapes(cfg.ServicesPath), p.Trigger)` when `p.Origin` is `store.OriginRun`, and `StartedBy` when it is `store.OriginRebuild`. A test builds a store over its own database with a clock it sets, replaces the ZIP table with `candidates.ZipDrive()`, attaches observations it builds, judges them with `JudgeAll` or `Judge`, records rulings with `Decide`, records passes of each kind and origin and finishes or fails them, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a fixed banner and a services file whose `scrapes` entry names a URL it chose, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template writes for a `LandingData`, a `CandidateData`, a `PassData`, a `ToolsData` built from `tools.Catalog()`, an `AboutData` or a `NotFoundData` it builds by the definitions below; it asks a pruned pass and a malformed id and gets the not-found page, and turns the store's failing switch on to see the 503. A test of the landing's windows registers the tools over the same store, hands each `next` back as that list's parameter, and compares each window and its `ShortlistNext` or `PassesNext` with what `shortlist` or `passes` answers for the same `page`; pages one list while the other's token is set and sees the other's window unchanged; checks that the first row of a later shortlist window is ranked one more than the number of entries before it, a shared operating key straddling the boundary; walks each list's Next to the end and its Prev back, finding the same windows reversed, with the same ranks for the shortlist, and at the end the 303 to `/` carrying the other list's value; asks `last` of each list and finds the last `paging.DefaultLimit` entries the Next walk reached, ranked as there; pages one list by an after-token, a before-token or `last` while the other's value is set and sees the other's window, prev and next unchanged; and asks `/` with an undecodable value in either parameter, the other list's token, a before-token of the other list and `LAST` included, and gets the not-found page with the store failing or not.
