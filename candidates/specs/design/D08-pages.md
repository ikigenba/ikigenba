# D08-pages

What candidates draws as HTML: `internal/pages`, the six templates `landing`, `candidate`, `pass`, `tools`, `about` and `notfound` and the data each is executed with, and the handler that answers `/`, `/candidates/<id>`, `/passes/<id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it (decision 15). It is scrapes' pages with the shortlist and the passes on the landing page, a page per candidate and a page per pass below it.

## The pages

The landing page shows the shortlist under the default filters, the shortlist query's own defaults (`scoring.DefaultMaxMinutes` and `scoring.DefaultMinRevenue`): one window of it, `paging.DefaultLimit` ranked (appkit's D25), each linked to its candidate's page; then one window of the passes, `paging.DefaultLimit` newest first in the store's pass order, each linked to its page. Both lists grow, so each navigates (`shape/`, Listing; `design/`, the listing entry and its two-list form). Two lists share the page, so each has its own query parameter: `shortlist_page` takes the token the tool `shortlist` issues and `passes_page` the token `passes` issues (`D10-tools`), each the first value of its name in the query, and nothing else is read from the query; the detail routes read none. Each list shows the window its parameter names, exactly what its tool answers for the same `page` with no `limit` (and, for `shortlist`, the default filters), through the store's positioned windows (`Shortlist`, `ListPasses`, `D04-store`); the first window when the parameter is absent or empty; and neither parameter changes the other list's window. The template receives each list's own token, `ShortlistPage` or `PassesPage` (empty on the first window), and the token its tool answers as `next` for that window, `ShortlistNext` or `PassesNext` (empty when none remain); what it draws from them, the two navs included, is the asset's. A value either parameter cannot decode, a token issued for the other list included, is the not-found page, never a first window. A shortlist row's rank is its place in the whole ranked shortlist, not in its window: a later window's first row is ranked one more than the number of entries before the window's position, which the store counts (`ShortlistOffset`). The two cutoffs are template data, so the sentence that names them follows the query; the origin and every other constant of the rules version are copy in the template; the number of rows shown follows `paging.DefaultLimit`, and the template states no count of its own. No row of either list shows a phone or an email.

`/candidates/<id>` is one candidate: its display fields and tags, its assessment with the effective numbers as the store last wrote them, each estimate with the facts it used, each link with its last seen and gone, linked to its row's page at scrapes, and the rulings that name it. A merged candidate's page shows its id, status, the candidate it was merged into (linked), its created and updated times and its rulings, and no display field, tag, assessment, estimate or link: the store keeps its display fields as they were at the merge, and the page data blanks them, so the page says only what it merged into (the template's comment). An active candidate not yet scored shows the template's not-scored state.

`/passes/<id>` is one pass's record in full; when it failed, the reason's sentence, which the template chooses from `Reason`; when a delivery started it, its trigger linked to the run's page at scrapes. A pass still `running` shows its record as it stands; the page does not stream.

An unknown candidate id, an unknown or pruned pass id, and a path whose id is not a well-formed candidate or pass id are answered alike, the not-found page with 404, byte for byte the not-found page of any other path.

The tools page lists the seven tools in the catalog's order (`D10-tools`), each with its one-line description. The about screen shows the service's name, the banner's `Release` and `Commit` and `pages.Description`. Any other path is the not-found page, 404, whatever the method.

The landing page is the root of the banner's trail; a candidate page is one level below it, named by the candidate's id at `/candidates/<id>`; a pass page one, named by the pass's id at `/passes/<id>`; and the tools page and the about screen one, `pages.ToolsLevel` and `pages.AboutLevel`. The banner's user is the caller's email, with auth's profile and sign-out addresses built on `urls.Auth` (`D01-layout-and-run-seam`).

## Who started a pass

A pass a `rebuild` call started shows its caller's email, or user id when the caller has no email; one a delivery started shows its trigger, the run id, linked to the run's page at scrapes, and the template names scrapes as its starter. The data carries `StartedBy` (a rebuild's caller's email, or its user id when the email is empty; empty for a delivery) and `RunPage` (empty for a rebuild); the template keys the starter on `Trigger`, and the words are the template's. An assessment's exclusions are handed as stored, whether or not it is excluded; the template lists them only when it is.

## Numbers as shown

The templates receive numbers already formatted, as their comments name them: dollars as `$` and the whole number of dollars with a comma between each group of three digits (a score or a base, which are not whole, rounded to the nearest dollar first); confidences, freshness and link confidences with two decimals; drive minutes on the candidate page as decimal text, empty when absent; filing dates as `YYYY-MM-DD` in both the `datetime` and the text; other times RFC 3339 to the second for a `time` element's `datetime`, and a `...Text` field in the page's layout, `pages.MinuteLayout` for the landing's passes, a link's first and last seen and a ruling's time, `pages.SecondLayout` for a candidate's created and updated, an assessment's scored and the pass page. Counts, ranks, the landing's minutes and cutoff and the rules version are integers. A time not yet set gives both strings empty.

## Pages show what is stored

Pages make no call to scrapes and change no record: a pass's page shows the status the store holds, and the effective confidence, freshness and score are the stored assessment's, as the last re-score or `RefreshShortlist` wrote them (`D13-scoring`), the freshness being the freshness as scored `D10-tools` defines. No page reads a clock, so `pages.Config` carries none. Candidates and passes belong to no one (decision 14), so every signed-in user sees the same pages.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so nginx sends a request with no credential to sign in before it reaches candidates, and `D03-serve` mounts this handler inside `identity.Require`. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. On `/` the two page tokens are decided next, both before the store is read: an undecodable one is the not-found page, the same with the store unavailable. The landing with decodable tokens, the candidate and the pass pages answer 503 with a read refusal (`D03-serve`) when the store cannot be read; the about, tools and not-found pages are served without reading it.

## Recorded decisions

- Candidate pages at `/candidates/<id>` and pass pages at `/passes/<id>` (decision 15). A path whose id fails `store.ValidCandidateID` or `store.ValidPassID` is not looked up.
- `ServiceName` and `Description` are `D01-layout-and-run-seam`'s; the layouts are contract constants with values here, as in scrapes. `ShortlistShown` goes: the landing shows `paging.DefaultLimit` of each list, the window the matching tool answers for the same `page` and no `limit`, so the page and the tool agree on every window.
- One data type per thing a template draws, each field list the template comment's in its order. Every value a template receives is a string, a bool, an `int64`, a slice or a pointer to a struct; the template comments' `int` fields are `int64`, as the store holds counts.
- The shortlist's two cutoffs are template data (`MaxMinutes`, `MinRevenue`) taken from `scoring`'s defaults, so the landing's sentence cannot drift from the query; the origin's name and the freshness window are copy in the template, constants of the rules version; the number of rows shown is `paging.DefaultLimit`, which the template does not state.
- **Every number is the store's** (`store.Assessment.Effective` and `Score`, `D13-scoring`): the landing and the candidate page show what the last re-score or `RefreshShortlist` wrote, so a page and the tools agree, and a score moves once per pass rather than per request (decision 8 departed from; `D03-serve`). The freshness shown is derived from the stored numbers as `D10-tools` derives it, so it never contradicts the effective confidence beside it.
- **The landing's tokens are the tools'**: `shortlist_page` and `ShortlistNext` are `paging.Token{Tool: "shortlist"}` over a shortlist entry's score key and candidate id, and `passes_page` and `PassesNext` `paging.Token{Tool: "passes"}` over a pass's started text and id (`D04-store`), so a window on the page and the tool's answer for the same `page` are one window, read through the same store window, and a token on the page can be handed to an agent. They are strings, empty on the first window and when nothing follows, so the template tests them as it tests any other field.
- **One parameter per list** (`design/`'s two-list form): `shortlist_page` and `passes_page`, never `page`, and the page data carries each list's own token so the asset's navs carry the other list's along. An undecodable value in either is the existing not-found answer, decided after identity, path and method and before any store read, so a URL carrying a token the page never issued names no page and the answer is the same with the store unavailable.
- **Rank continues across windows** (decided 2026-10-13): a row's `Rank` is its place in the whole shortlist under the default filters, so a person reading a later window sees where it stands. The alternatives were a rank counted from 1 within each window, which would show two rows ranked 1 for different places, and no rank on later windows, which would leave a deep window unplaced. A later window's offset is one `COUNT(*)` over the shortlist window's own filters with its position inverted (`ShortlistOffset`, statement `ShortlistBefore`, `D04-store`), a `SEARCH` on `assessments_score`; the first window's offset is 0 and costs no query. The count is of the entries that do not follow the position, the position's own entry included, since a token names the last entry of the window before; a strict `candidate < ?` would leave that entry out and rank every later window one too low. The count is read apart from the window, so a re-score between the two reads can skew one page's ranks; a pass's refresh is one write and the reads are each consistent, and the next request agrees, which is accepted.
- A merged candidate's page data blanks its display fields and tags, and carries no assessment, estimate or link, as the template's comment and the mock show; the store keeps them (decision 10, coordinator decision C3). Its rulings are shown, since they record the merge.
- Money is shown in whole dollars: a score is a product of a dollar figure and a confidence, so its cents are noise; it is rounded half away from zero (`math.Round`).
- **The landing lists one window of the passes**, not every kept pass: D25 asks every list an agent or a person can add to to be paged, and a retention setting raised far enough would make the whole list unbounded; the old loop over `ListPasses` until it answered short goes. The rest are reached through `passes_page` or the `passes` tool.
- An unknown, pruned or malformed id is one not-found answer, byte for byte the not-found page of any other path; a database outage is a plain-text 503 read refusal, as in scrapes.

## Consumer tasks

`web.Handler` (`D03-serve`) builds `s, err := pages.Load()` and mounts `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store})` inside `identity.Require` for the page paths. `D01-layout-and-run-seam`'s about requirement executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}` and `b.Trail` set to `[]page.Level{pages.AboutLevel}`. The handler reads `sp := r.URL.Query().Get("shortlist_page")` and `pp := r.URL.Query().Get("passes_page")`, decodes a non-empty `sp` with `paging.Token{Tool: "shortlist"}.Decode(sp, &key, &id)` (`key` an `int64`) and a non-empty `pp` with `paging.Token{Tool: "passes"}.Decode(pp, &started, &pid)`, answering the not-found page if either fails, then builds the landing with `rs, err := st.Shortlist(ctx, d, key, id, paging.DefaultLimit+1)`, `d` being `store.ShortlistFilter{MaxMinutes: scoring.DefaultMaxMinutes, MinRevenue: scoring.DefaultMinRevenue}`, `off, err := st.ShortlistOffset(ctx, d, key, id)` when `id` is not empty (0 otherwise), each row ranked `off + i + 1`, and `ps, err := st.ListPasses(ctx, started, pid, paging.DefaultLimit+1)`, sets `ShortlistPage` to `sp` and `PassesPage` to `pp`, and, when one came back long, sets `ShortlistNext` to `paging.Token{Tool: "shortlist"}.Encode(r.Assessment.ScoreKey, r.Candidate.ID)` or `PassesNext` to `paging.Token{Tool: "passes"}.Encode(p.Started.UTC().Format(time.RFC3339), p.ID)` of the last entry shown; a candidate page with `st.GetCandidate`, `st.GetAssessment`, `st.Estimates`, `st.Links` and `st.Rulings`, a link's address with `urls.RowPage(urls.Scrapes(cfg.ServicesPath), l.Run, l.SourceID)`, the point with `scoring.Point` and the effective numbers from `a.Effective`, `a.Score` and the freshness as scored of `a` (`D10-tools`, R-5QRJ-WSYK); a pass page with `st.GetPass` and `urls.RunPage(urls.Scrapes(cfg.ServicesPath), p.Trigger)`. A test builds a store over its own database with a clock it sets, replaces the ZIP table with `candidates.ZipDrive()`, attaches observations it builds, re-scores them, records rulings with `Decide`, records passes and finishes or fails them, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a fixed banner and a services file whose `scrapes` entry names a URL it chose, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template writes for a `LandingData`, a `CandidateData`, a `PassData`, a `ToolsData` built from `tools.Catalog()`, an `AboutData` or a `NotFoundData` it builds by the definitions below; it asks a pruned pass and a malformed id and gets the not-found page, and turns the store's failing switch on to see the 503. A test of the landing's windows registers the tools over the same store, hands each `next` back as that list's parameter, and compares each window and its `ShortlistNext` or `PassesNext` with what `shortlist` or `passes` answers for the same `page`; pages one list while the other's token is set and sees the other's window unchanged; checks that the first row of a later shortlist window is ranked one more than the number of entries before it, a shared score key straddling the boundary; and asks `/` with an undecodable token in either parameter, the other list's token included, and gets the not-found page with the store failing or not.
