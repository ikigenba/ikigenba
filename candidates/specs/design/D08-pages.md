# D08-pages

What candidates draws as HTML: `internal/pages`, the seven templates `landing`, `cohort`, `candidate`, `pass`, `tools`, `about` and `notfound` and the data each is executed with, and the handler that answers `/`, `/cohorts/<id>`, `/candidates/<id>`, `/passes/<id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it (decision 15). It is scrapes' pages with the cohorts and the passes on the landing page, and a page per cohort, per candidate and per pass below it. The pages say nothing of their own about what a cohort holds: who is a member, what `matching` counts and which reject stands are `D14-cohorts`' terms, the store's read answers them (`D04-store`), and the pages format what it answers.

## The pages

The landing page shows one window of the cohorts, `paging.DefaultLimit` of them (appkit's D25) in the store's cohort order, by name and then by cohort id, each in byte order, each linked to its cohort's page; then one window of the passes, `paging.DefaultLimit` newest first in the store's pass order, each linked to its page. A deleted cohort is on no window. Both lists grow, so each navigates (`shape/`, Listing; `design/`, the listing entry and its two-list form). Two lists share the page, so each has its own query parameter, `cohorts_page` and `passes_page`, each the first value of its name in the query, and nothing else is read from the query; the detail routes read none. A list's **page value** asks for one of four windows, and **decodable** names all four. The empty value asks for the **first window**. The token the list's tool issues as `next`, an **after-token** (`cohorts` and `passes`, `D10-tools`), asks for the window after the entry it names, exactly what that tool answers for the same `page` with no `limit`, read through the store's positioned windows (`ListCohorts`, `ListPasses`, `D04-store`). The way back is a token the page issues itself, since neither tool has a backward step: a **before-token** is `paging.Token{Tool: "cohorts-before"}` or `paging.Token{Tool: "passes-before"}` over the same two key fields, the name and cohort id or the started text and pass id, carried in the same parameter, the checksum appkit's token carries keeping it apart from the after-token; it asks for the `paging.DefaultLimit` entries that precede the one it names in the list's order, drawn in that order, whether or not an entry still has that key. The literal word `last`, which decodes as no token, asks for the **last window**, the last `paging.DefaultLimit` cohorts by name or the oldest `paging.DefaultLimit` passes, drawn in the list's order. The page reads a before-token's window and the last window from the store's reversed windows, `ListCohortsReversed` and `ListPassesReversed` (`D04-store`), from the token's position or, for `last`, from the end of the list, asking for one entry more than the window and drawing the first `paging.DefaultLimit` of them reversed, so it learns whether the window **underflows**: when at most `paging.DefaultLimit` entries precede a before-token's position, or the list holds at most `paging.DefaultLimit` entries in all for `last`, the window asked for is that list's first window, and the page answers a 303 whose `Location` is `/` with the other list's parameter kept as the request carried it, so each list's first window keeps one address and paging one list never resets the other; when both lists underflow, both parameters are dropped. Neither parameter changes the other list's window. The template receives, for each list, its page value as the request carried it (`CohortsPage`, `PassesPage`: empty on the first window, `last` on the last), the before-token of the window's first entry (`CohortsPrev`, `PassesPrev`: empty on the first window and on an empty after-window), and the after-token of its last entry when more follow (`CohortsNext`, `PassesNext`: on an after-window exactly the tool's `next`, on a before-window always set, on the last window empty); what it draws from them, the two navs with First, Prev, Next and Last included, is the asset's. A value either parameter cannot decode, one list's token in the other's parameter, a token another tool issued, or a word such as `bogus` or `LAST`, is the not-found page, never a first window. A cohort row carries the cohort's id, name and size, who created it and when it last changed; the landing shows no member of any cohort, so it reads no clock and no assessment. The number of rows shown follows `paging.DefaultLimit`, and the template states no count of its own. No row of either list shows a phone or an email.

`/cohorts/<id>` is one cohort as one `ReadCohort` of the store answers it (`D04-store`): its definition (name, size, each filter it carries with its unknown switch, its order, who created and last changed it and when), its `matching`, its members in rank order, ranked from 1, and its standing rejects, newest first, each with the candidate, who, when and why (`D14-cohorts`). Each member row has the shape the landing's shortlist rows had, with the fleet verdict in place of the fleet test, the website fact and the address it landed on, and the known-since date and the newest filing beside them, as the candidate's facts row holds them when the cohort is read (`D04-store`, `D16-enrichers`), whether the owner excluded it, and links to its candidate's page. The page is a listing: it carries no form, and a cohort is made, changed and groomed through the tools (`D10-tools`). The members are worked out at each read, so two requests minutes apart can show different members when a judge, an enrichment, a ruling or a reject came between them.

`/candidates/<id>` is one candidate: its display fields and tags, its website as its newest `website_check` result found it (the state, the address it landed on, the page title and when it was checked, or `unknown` when it has no result); its facts as its facts row holds them, the projection of the newest result of each enricher's kind (`D04-store`, `D16-enrichers`): the known-since date, the newest filing, the categories with their sources, the government match, the fleet verdict, the truck and driver counts, the drive minutes and when each kind last wrote the row, or the template's no-facts state when it has no row; its assessment, the two judgments as the last judge, rebuild or ruling wrote them, with the operating evidence behind it; each estimate with the facts it used, each link with its last seen and gone, linked to its row's page at scrapes, the rulings that name it, every enrichment result on it, of every kind, newest first, each with its kind, its source and its time, a `website_check` result with its state, landed address, title, status code, bytes read and error, and a result of a derived kind with what it found, member by member (`D04-store`, `D15-website-check`, `D16-enrichers`), and every reject and unreject record that names it, each with its cohort's id, the cohort's name while the cohort exists, who, when and why. A merged candidate's page shows its id, status, the candidate it was merged into (linked), its created and updated times, its rulings and its reject records, and no display field, tag, website, fact, enrichment result, assessment, estimate or link (a merge moves the results to the survivor, `D04-store`): the store keeps its display fields as they were at the merge, and the page data blanks them, so the page says only what it merged into (the template's comment). An active candidate not yet judged shows the template's not-judged state: an ingest stores its rows and judges nothing. Facts and the assessment are apart, so a candidate an enrich has reached and no judge has shows its facts beside the not-judged state, and one no enrich has reached shows the no-facts state.

`/passes/<id>` is one pass's record in full, an enrich pass's six counts (derived, the results the derived kinds wrote, `D06-passes`; then due, fetched, https, http and none, whose meaning is `D15-website-check`'s) among them, which the template shows only for an enrich; when it failed, the reason's sentence, which the template chooses from `Reason`; when a scrapes run's delivery started it, its trigger linked to the run's page at scrapes; when another pass started it, its trigger, that pass's id, linked to that pass's page by the template. A pass still `running` shows its record as it stands; the page does not stream.

An unknown candidate id, an unknown or pruned pass id, an unknown or deleted cohort id, and a path whose id is not a well-formed candidate, pass or cohort id are answered alike, the not-found page with 404, byte for byte the not-found page of any other path.

The tools page lists the sixteen tools in the catalog's order (`D10-tools`), each with its one-line description. The about screen shows the service's name, the banner's `Release` and `Commit` and `pages.Description`. Any other path is the not-found page, 404, whatever the method.

The landing page is the root of the banner's trail; a cohort page is one level below it, named by the cohort's id at `/cohorts/<id>`; a candidate page one, named by the candidate's id at `/candidates/<id>`; a pass page one, named by the pass's id at `/passes/<id>`; and the tools page and the about screen one, `pages.ToolsLevel` and `pages.AboutLevel`. The banner's user is the caller's email, with auth's profile and sign-out addresses built on `urls.Auth` (`D01-layout-and-run-seam`).

## Who started a pass

A pass says what started it by its `Origin` (`D04-store`): a `rebuild` call's pass, origin `rebuild`, shows its caller's email, or user id when the caller has no email; an ingest a scrapes run's delivery started, origin `run`, shows its trigger, the run id, linked to the run's page at scrapes, and the template names scrapes as its starter; a judge the daily cron trigger's fire started, origin `cron`, shows its trigger, the slug `judge_candidates`, unlinked; an `enrich` call's pass, origin `enrich`, shows its caller as a rebuild's does; and a pass another pass started, origin `pass` (an enrich an ingest started, or a judge an enrich started, `D06-passes`), shows its trigger, the starting pass's id, which the template links to that pass's page. The data carries `Kind` and `Origin` as stored, `StartedBy` (a rebuild's or an enrich call's caller's email, or its user id when the email is empty; empty for any other origin) and `RunPage` (set only for origin `run`); the template keys the starter on `Origin`, and the words are the template's. The landing's pass rows carry `Kind`, `Trigger` and `Judged`, and no origin.

## Numbers as shown

The templates receive numbers already formatted, as their comments name them: dollars as `$` and the whole number of dollars with a comma between each group of three digits, for a revenue range, an estimate's low and high and a cohort's revenue bounds alike; operating and revenue confidences, evidence weights, an estimate's confidence and a link's confidence with two decimals, though the tools answer the stored values, the operating confidence stored rounded to six decimal places (`D10-tools`, `D13-scoring`); drive minutes on the cohort page and the candidate page, a cohort's drive-minutes maximum and filing-age days, and a candidate's truck and driver counts, as decimal text, empty when absent; what a derived kind's result found as one key and value per member, in key order, the value as compact JSON text, as an estimate's facts are; filing dates, the known-since date and the newest filing as `YYYY-MM-DD` in both the `datetime` and the text; other times RFC 3339 to the second for a `time` element's `datetime`, and a `...Text` field in the page's layout, `pages.MinuteLayout` for the landing's cohorts and passes, a link's first and last seen, a ruling's time, a reject's time and an enrichment result's time, `pages.SecondLayout` for a candidate's created and updated, when its website was checked and when each kind wrote its facts, an assessment's calculated time, a cohort's created and changed times on its page and the pass page. An empty judgment gives empty strings, never `0.00` or `$0`, so the template can show that there is no evidence or no estimate. Counts, sizes, ranks, `matching` and the rules version are integers. A time not yet set gives both strings empty. A member row shows a candidate's distinct category words, each once in ascending order; the candidate page shows each category with the source that gave it, in the order stored; a cohort's category filter shows its words as stored. The fleet verdict is shown as stored, `pass`, `fail` or `unknown`, and a website state likewise, `https`, `http`, `none` or `unknown`. An enrichment result's status code is decimal text, empty when no response came, and its bytes read an integer.

## Pages show what is stored

Pages make no call to scrapes and change no record: a pass's page shows the status the store holds, the two judgments are the stored assessment's, as the last judge, rebuild or ruling wrote them (`D13-scoring`), the facts are the facts row's, as the enrichers last wrote it (`D04-store`, `D16-enrichers`), and a cohort's page shows what the store's read of it answers, its members' facts from the facts row and their judgments from the assessment. Nothing decays: a fact changes only when an enricher writes a new result, in an enrich whose inputs changed, a rebuild, or a merge or split, and a judgment when a judge runs. The candidate card's website is read from the newest `website_check` result, which is also what the facts row's website holds, so the card and a cohort's member row agree as soon as a result is recorded, without a judge between. The one date a page depends on is the filing-age date of a cohort read, and that is the store's: `ReadCohort` reads the store's own clock (`D14-cohorts`, `D04-store`), so no page reads a clock of its own and `pages.Config` carries none. Candidates, cohorts, rejects and passes belong to no one (decision 14; cohorts decision 8), so every signed-in user sees the same pages.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so nginx sends a request with no credential to sign in before it reaches candidates, and `D03-serve` mounts this handler inside `identity.Require`. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. On `/` the two page values are decided next, both before the store is read: an undecodable one is the not-found page, the same with the store unavailable. A path that is not a well-formed cohort, candidate or pass path is the not-found page without a store read. The landing with decodable values, the cohort, candidate and pass pages answer 503 with a read refusal (`D03-serve`) when the store cannot be read, the landing drawing no window and making no redirect; the about, tools and not-found pages are served without reading it.

## Recorded decisions

- Candidate pages at `/candidates/<id>` and pass pages at `/passes/<id>` (decision 15). A path whose id fails `store.ValidCandidateID` or `store.ValidPassID` is not looked up.
- **Cohort pages at `/cohorts/<id>`** (cohorts decision 21). A path whose id fails `store.ValidCohortID` is not looked up. The cohort path is defined in a requirement of its own beside the candidate and pass paths, so the existing definition keeps its id and only the requirements that list the page paths change.
- `ServiceName` and `Description` are `D01-layout-and-run-seam`'s; the layouts are contract constants with values here, as in scrapes. The landing shows `paging.DefaultLimit` of each list, the window the matching tool answers for the same `page` and no `limit`, so the page and the tool agree on every window.
- One data type per thing a template draws, each field list the template comment's in its order. Every value a template receives is a string, a bool, an `int64`, a slice or a pointer to a struct; the template comments' `int` fields are `int64`, as the store holds counts.
- **The shortlist leaves the landing** (cohorts decisions 15 and 20), with its parameter `shortlist_page`, its window, its ranks and the offset count behind them; `ShortlistRow` and the shortlist row at an offset go. The ranked view of everything is now a cohort with no filters, on its own page. A URL still carrying `shortlist_page` names nothing the landing reads, so it is answered as the landing with that parameter absent; URLs are not persisted contract, so there is no expand period.
- **The landing lists cohorts by name, then id, in byte order** (cohorts decision 20, log 18), the order `ListCohorts` windows and the `cohorts` tool pages in. A cohort row carries no rank: the list is alphabetical, not ranked.
- **Every judgment is the store's** (`store.Assessment`, `D13-scoring`): the cohort page and the candidate page show the judgments the last judge, rebuild or ruling wrote, so a page and the tools agree, and a judgment moves once per judge rather than per request. Freshness is measured when a judge runs, not when a page is drawn, so the pages show no freshness of their own.
- **The page reads no clock of its own** (cohorts decision 4, log 3): the filing-age filter is measured on the day a cohort is read, and the date is the store's, read from its own `Config.Now` inside `ReadCohort`. `pages.Config` gains nothing, so the cohort page and the `cohort` tool measure the same day under one clock.
- **The landing's forward tokens are the tools'**: an after-token in `cohorts_page`, and `CohortsNext`, are `paging.Token{Tool: "cohorts"}` over a cohort's name and id, and an after-token in `passes_page`, and `PassesNext`, `paging.Token{Tool: "passes"}` over a pass's started text and id (`D04-store`), so a window on the page and the tool's answer for the same `page` are one window, read through the same store window, and a token on the page can be handed to an agent. They are strings, empty on the first window and when nothing follows, so the template tests them as it tests any other field.
- **The page steps back and jumps to the end** (`design/`'s listing entry, with Prev and Last, decided 2026-10-13): each parameter also carries a before-token the page issues under its tool's name with `-before` appended, `cohorts-before` or `passes-before`, or `last`, and the landing data carries `CohortsPrev` and `PassesPrev`. `cohorts` and `passes` decode only their own tokens, so they refuse a before-token and `last` with `paging.BadPage` as any page they did not issue (`D10-tools`), and the agreement with the tools holds for the empty value and after-tokens only. `last` is no token: appkit's `paging` (v0.26.0) encodes a token as unpadded URL-safe base64 of a payload and a four-byte checksum and refuses a decoded value shorter than four bytes, and `last` decodes to three; the definitions test it only after both tokens regardless. Both lists' tokens now carry two strings, so only the checksum over the tool's name keeps one list's token out of the other's parameter, and the definitions say so.
- **An underflow answers 303**, rather than drawing the first window under another address, so each list's first window has one URL and its page value is always empty. The redirect drops the underflowing list's parameter and keeps the other's as the request carried it, which is URL-safe since only a decodable value gets this far and appkit's tokens are URL-safe base64; when both underflow at once both are dropped, so one redirect lands on the first windows. The 303 is the listing entry's.
- **The last window is the last `paging.DefaultLimit` cohorts by name, and the oldest `paging.DefaultLimit` passes**, aligned to the end of the list, not the final window of the Next walk: the two are equal only when the entries number a multiple of `paging.DefaultLimit`. Prev from the last window steps back in windows aligned to the end until one underflows.
- **One parameter per list** (`design/`'s two-list form): `cohorts_page` and `passes_page`, never `page`, and the page data carries each list's own token so the asset's navs carry the other list's along. An undecodable value in either is the existing not-found answer, decided after identity, path and method and before any store read, so a URL carrying a token the page never issued names no page and the answer is the same with the store unavailable.
- **The cohort page is one `ReadCohort`** (cohorts decisions 3 and 21): its definition, `matching`, its members and its standing rejects come from one store read, so the page never shows a member count from one moment and members from another. Its members are ranked from 1 in the order the read answers them; the rank is the place in the cohort, which is the whole list, since a cohort is read whole.
- **The cohort page lists its members and its standing rejects whole, unpaged**, a departure from `shape/`'s Listing rule, which pages every list an agent or a person can add to. A cohort is read whole in one answer (cohorts decision 2): its members are at most its size, and its size at most `store.CohortSizeMax`, so the members are bounded; its standing rejects are made by hand, one candidate at a time, and the `cohort` tool answers them whole too (cohorts decision 17), so the page and the tool show the same list. The candidate page lists its reject records whole, as it lists its rulings.
- **The cohort page shows the standing rejects; the candidate page shows every record** (cohorts decision 11): a cohort's page answers which candidates are kept out of it now, and a candidate's page keeps the history, rejects and unrejects alike, including those on a deleted cohort, whose record keeps the cohort's id and shows no name.
- **The filters are pre-formatted display fields** (log 25): `FiltersView` holds one field per part of the filter set and every label stays in the template. `Government` is the string `"true"`, `"false"` or empty, since a pointer to false reads as set in a template; the revenue bounds are dollars and the drive-minutes maximum and the filing-age days decimal text, each empty when the cohort does not carry it, so the template can say the filter is absent.
- **The fleet verdict replaces the boolean** (cohorts decision 14, log 10): a member row and the facts view carry `FleetVerdict` as stored, and the facts view carries the truck and driver counts the facts row holds (log 20) as decimal text, each empty when unknown. The template shows an unknown verdict or count muted, which is copy.
- A merged candidate's page data blanks its display fields and tags, and carries no assessment, estimate or link, as the template's comment and the mock show; the store keeps them (decision 10, coordinator decision C3). Its rulings are shown, since they record the merge, and its reject records, since they are history on the candidate.
- **The candidate card and the cohort row both read the newest result** (enrichers decision 7, replacing website-check decisions log A2): the candidate page shows what the website check last found, as soon as it is recorded, from `Enrichments`' first `website_check` result, decoded from its `Found`, `unknown` when there is none; a cohort's member row shows the `website` and `website_url` facts the cohort read answers from the facts row (`D04-store`), which the same result wrote, so a row agrees with the card, with the filter that admitted it and with the `cohort` tool, and no longer waits for a judge. The facts view does not repeat the website, since the card already shows it. A `none` result's address is not shown even if one were stored, as the template's comment asks.
- **Facts leave the assessment view for a facts view of their own** (enrichers decisions 5 and 7): the template shows the facts row in its own card, nil when the candidate has no row, beside the assessment, nil when it is not judged; the two are read apart (`GetFacts`, `GetAssessment`), so either can be shown without the other. The facts view's field list is the template comment's, and `Written` says when each kind last wrote the row, in kind name order, to the second, as the candidate's own times are.
- **One enrichment row for every kind**: `Source` replaces `Domain`, since a derived kind's source is a word (`links`, `zip_drive`) and the website check's the domain. A `website_check` row carries the decoded `website.Result`'s six fields and an empty `Found`; a derived kind's row carries its found object as key and value rows, the form an estimate's facts take, and empty website fields, as the comment asks. The row never interprets a derived kind's members, so a kind that gains a member needs no page change.
- **Enrichment results follow the rulings and precede the rejects** in `CandidateData`, the order the template draws its sections in and its comment now lists them in. An enrichment result's time is shown to the minute, as a ruling's and a reject's are, and when the card's website was checked to the second, as the candidate's own times are, as the comment asks.
- **The pass view carries the enrich counts and caller**: an enrich pass's six counts are among the pass view's fifteen, and an `enrich` call's caller is its `StartedBy`, as a rebuild's is. The landing's pass rows gain nothing: an enrich pass's row shows its kind, trigger and status, and its counts are on its page. `Derived` joins the pass view through its definition, re-minted to name fifteen counts, since a definition naming fourteen would no longer describe the view; the landing's and the pass page's requirements and their walks, which cite it, are re-minted with it. The template shows `Derived` only for an enrich, so no requirement asks it of another kind's page.
- **The filter set and the member row are supplemented, not re-minted**: their definitions are cited by the cohort page's requirement, so new requirements add the website filter and switch to the filters view and the website facts to the member row, each in addition to the base definition.
- Money is shown in whole dollars: the revenue range, an estimate's low and high and a cohort's revenue bounds are stored as whole dollars, so nothing is rounded on the way to the page.
- **Confidences and weights show two decimals** (orchestrator decision 8): the tools answer agents the stored values, the operating confidence stored rounded to six decimal places (`D13-scoring`); a person reads two decimals. An empty operating confidence or revenue estimate is an empty string, never 0 (intent 2), and the template says which.
- **The starter is keyed on `Origin`**, not on `Trigger`: a run id and a cron slug are both triggers as stored, so only the origin tells a scrapes run's ingest from a cron fire's judge. `RunPage` is built only for origin `run`, and `StartedBy` only for origins `rebuild` and `enrich`, since a delivery's caller is the service identity, not a person, and a pass another pass started has no caller (`D06-passes`); its trigger, the starting pass's id, says what started it.
- **A member row's categories are words only**, each once, in ascending order: the row is narrow and its question is which kinds of business the candidate is; the candidate page shows each category with the source that gave it.
- **The landing lists one window of the passes**, not every kept pass: D25 asks every list an agent or a person can add to to be paged, and a retention setting raised far enough would make the whole list unbounded. The rest are reached through `passes_page` or the `passes` tool.
- An unknown, pruned, deleted or malformed id is one not-found answer, byte for byte the not-found page of any other path; a database outage is a plain-text 503 read refusal, as in scrapes.
- **Asset issue, not a data gap**: the opening comment of `notfound.html` names `/candidates/<id>` and `/passes/<id>` among the paths it answers and not `/cohorts/<id>`. The page drawn for an unknown cohort is the same `NotFoundData`, so no requirement changes; the comment is stale and the asset is the delivery's to correct, not this design's.

## Consumer tasks

`web.Handler` (`D03-serve`) builds `s, err := pages.Load()` and mounts `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store})` inside `identity.Require` for the page paths. `D01-layout-and-run-seam`'s about requirement executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}` and `b.Trail` set to `[]page.Level{pages.AboutLevel}`.

The landing: the handler reads `cp := r.URL.Query().Get("cohorts_page")` and `pp := r.URL.Query().Get("passes_page")`, tries a non-empty `cp` with `paging.Token{Tool: "cohorts"}.Decode(cp, &name, &cid)`, then `paging.Token{Tool: "cohorts-before"}.Decode(cp, &name, &cid)`, then `cp == "last"`, and a non-empty `pp` likewise with `passes`, `passes-before` and `last` into `&started, &pid`, answering the not-found page if either fits none; then for an empty value or an after-token `cs, err := st.ListCohorts(ctx, name, cid, paging.DefaultLimit+1)`, for a before-token `st.ListCohortsReversed(ctx, name, cid, paging.DefaultLimit+1)` and for `last` `st.ListCohortsReversed(ctx, "", "", paging.DefaultLimit+1)`, the window the first `paging.DefaultLimit` reversed, underflowing when no more came back; and `ps, err := st.ListPasses(ctx, started, pid, paging.DefaultLimit+1)` or `st.ListPassesReversed(ctx, started, pid, paging.DefaultLimit+1)` (`"", ""` for `last`) the same way. When either underflows it answers `http.Redirect(w, r, loc, http.StatusSeeOther)` with `loc` `/` or `/?passes_page=` followed by `pp` (or `/?cohorts_page=` and `cp`); otherwise it builds each `pages.CohortRow{ID: c.ID, Name: c.Name, Size: c.Size, CreatedBy: c.CreatedUserEmail, CreatedUser: c.CreatedUserID, Changed: …, ChangedText: …}` and each `pages.PassRow`, sets `CohortsPage` to `cp` and `PassesPage` to `pp`, `CohortsPrev` to `paging.Token{Tool: "cohorts-before"}.Encode(c.Name, c.ID)` of the first cohort shown and `PassesPrev` to `paging.Token{Tool: "passes-before"}.Encode(p.Started.UTC().Format(time.RFC3339), p.ID)` of the first pass shown, unless the value is empty or nothing is shown, and `CohortsNext` to `paging.Token{Tool: "cohorts"}.Encode(c.Name, c.ID)` or `PassesNext` to `paging.Token{Tool: "passes"}.Encode(p.Started.UTC().Format(time.RFC3339), p.ID)` of the last entry shown when an after-read came back long or the value is a before-token, and executes `landing` with the `pages.LandingData`.
