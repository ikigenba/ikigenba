# D09-trail

The trail as a whole: the closed set of event names candidates records, the request pair the telemetry middleware records for every request, deliveries from the bus as appkit records them, `sibling.called` for every read of scrapes, the start's one read among them, and every request to prompts, the two pass events as the assembled run shows them, `owner_record.written` for every owner record written, the clock and the random source every event is stamped and named from, and decision 18's secrecy, stated once for the whole app. It is scrapes' trail document with the pass events in place of the run events and appkit's `sibling.called` in place of `source.called`.

Who tells each event is another document's. The request pair is appkit's `telemetry.Middleware`'s, which `D03-serve` mounts on every request; `tool.called` is appkit's MCP server's; `service.started` and `service.stopping` are `D03-serve`'s; `event.lost` is appkit's emitter's, since the emitter is built with the writer; `sibling.called` is appkit's `scrapes` client's and appkit's `prompts` client's, each of which records one for every request it sends, as every sibling client of appkit does. `pass.started` and `pass.finished`, their attributes, their identity and their cause are `D07-events`'; when each is told is `D06-passes`'. This document states what the assembled run shows of them. `owner_record.written` is told by the tool that wrote the record, `add_business` or `set_facts` (`D10-tools`), through the writer the handler is built with (`D03-serve`); its name, its attributes and when the assembled run shows it are this document's.

Decisions cited by number are the decisions document that delivered candidates; "cohorts decision N" is entry N of the decisions document of the cohorts change, and "cohorts log N" entry N of its decisions log. "Site text decision N" is entry N of the decisions document of the site-text change, and "brief decision N" entry N of the decisions document of the brief change. "Website search decision N" is outcome N of the decisions document of the website-search change, and "S N" entry DN of its decisions log. "Campaigns decision N" is entry N of the decisions document of the campaigns change, and "campaigns log DN" entry DN of its delivery log. "Empty sites outcome N" is outcome N of the decisions document of the empty-sites change, which also runs the website search for a company whose site on record kept no page to site text, and "empty sites decision N" decision N of that change's delivery. "Owner records outcome N" is outcome N of the decisions document of the owner-records change, in which the owner, through an agent, adds a business or sets or clears facts on a candidate as an owner record.

## The request pair and deliveries

Every request, whatever its path and whether or not it carries an identity, is recorded by the telemetry middleware as one `request.started` (method, path) and one `request.finished` (status, duration, bytes), under its request id and its caller's user (`D03-serve`). A delivery from the bus is a request like any other, `POST /events` with the events app's `X-Request-Id` and no user: appkit's delivery handler records nothing of its own, so a delivery is recorded as that request pair, its record read as a `sibling.called`, and the pass it starts tells its events, and its reads their `sibling.called`, under the same request id (decision 18). A judge fire, a delivery of `cron.judge_candidates.fired`, is a delivery like any other: its request pair and, under its request id, the pass events of the pass it starts, if any (a skipped or busy judge delivery starts no pass and leaves only the request pair), and no `sibling.called`, since a judge pass reads nothing from scrapes and calls no sibling (`D06-passes`). A parks delivery, of `scrape.finished` for the scraper `parks.Scraper` (`D18-parks`), is a delivery like any other: its request pair, its record read as a `sibling.called`, and, under its request id, the events of the `parks` pass it starts, if any, and that pass's reads as their `sibling.called` (`D06-passes`). The start is no request: once the settling and the prune are done and the facts fill has ended (`D06-passes`), `Run` has the engine read scrapes once for the current run of `parks.Scraper`, the **start read**, made as `candidates` under the **start request id** `Run` draws for it (`D03-serve`, R-73LI-FCRL); that read's `sibling.called`, the events of the `parks` pass of origin `start` it may start and that pass's reads all carry it, so the start's whole trail is found under one request id as a delivery's is. A campaign delivery, of `campaign.member.added`, `campaign.member.rejected`, `campaign.piece.delivered` or `campaign.member.opened`, is recorded by its request pair alone, whatever it answers: it starts no pass, calls no sibling and tells no event of its own, its one write to the store being seen only in the uses the `candidate` tool and page show (`D06-passes`, `D07-events`, R-0FWV-JLS0).

## sibling.called

One `sibling.called` per request to scrapes (decision 18): `target` `scrapes`, `method` `GET`, `path` the read's path (`/scrapers/<name>/current`, `/runs/<id>/record` or `/runs/<id>/rows`), the status answered (0 when none came), and `duration_us`, as appkit's client records it. Its request id and user are those of the identity the read is made as (`D06-passes`): a full ingest's reads name its caller and the tool call's request id; a delivery's reads name `candidates`, the service identity, and the delivery's request id (decision 12); a `parks` pass started by `edit_park_rules` reads as its caller under the call's request id, as a full ingest does; and the start read and the reads of the `parks` pass it starts name `candidates` and the start request id; so the trail shows which reads no person made. Paths carry run ids and scraper names only; no row, query or body travels in it.

One `sibling.called` per request to prompts (site text decision 21), recorded by appkit's `prompts` client, the installed interface D27 of appkit describes: it sends every call, `show`, `run` or `result`, as one `tools/call` POST to `/mcp` on the socket the services file's `prompts` entry names, so the event has `target` `prompts`, the entry's name, `method` `POST`, `path` `/mcp`, the status answered and `duration_us`. candidates records nothing of its own for a prompts request. Every one is made as the caller of the `enrich` that needs it, forwarded on the request (site text decision 7, `D06-passes`): the `show` the call makes before it starts a pass, and the `run` and `result` calls of the pass, which runs on after the call is answered, all name that caller's user and the tool call's request id. The path names no prompt, run or input; what candidates sends prompts, a company's id, name, city and state, and, for `site_text` and `brief`, its website, for `brief` also its facts, the categories and its people's names and roles among them, and the titles and text of the pages kept on it, and, for `website_search`, no website and no page but its street, ZIP and phone, its email's domain and what the website check found there, its people's names and roles and its categories (website search decision 3, `D16-enrichers`), travels in the request body, which no event carries; so does what prompts answers, a brief's or a website search's standard output among it. The fetch that confirms the site a website search names is the website checker's, as the check's own fetches are, and records no event (website search decision 5). A delivery's pass and an ingest's follow-on never call prompts, since a kindless enrich leaves out every kind that runs prompts (`D06-passes`). candidates calls no other sibling, so no `sibling.called` names a target but `scrapes` and `prompts`. A walk's requests to Google Places, like the routing service's, are no sibling's: no `sibling.called` is recorded for them, and the places they answer reach no event, log or refusal (`D19-walk`, R-1WS0-70BI).

## owner_record.written

One `owner_record.written` for every owner record written (owner records outcome 9): an `add_business` or `set_facts` call (`D10-tools`) that the store answers with a record (`store.AddOwnerRecord`, `D04-store`) leads to exactly one, under the call's request id and its caller's user, carrying `record`, the record's `own_` id, `candidate`, the `cand_` id it names, `founded`, whether the write created that candidate, `set`, the fact words the record sets, and `cleared`, the fact words it clears, each list in the order `sources.SettableFacts()` gives (`D05-sources`) joined by commas. It carries no note, no value and no email: the record's `UserEmail` stays in the store, and its user id is the event's `User`, as for every event of the call. A call that wrote no record, refused or with the store failing, leads to none; a call that wrote one leads to one even if its answer then fails, since the record is in the store. It is a trail event only: no bus event is emitted for it (`D07-events`, R-ZY3R-GAKJ), since no service accepts one and nothing on the suite waits on an owner write.

## The clock and the random source

Every event's time is read from `Process.Now`, and every request id `Run` mints, the start request id among them, every pass id, every park id and every bus event id are drawn from `Process.Rand` (`D01-layout-and-run-seam`). Both are seams `cmd/candidates` fills with `time.Now` and `crypto/rand.Reader`; a test fills them with a fixed clock and a constant reader and finds the stamps and ids those give.

## Secrecy

Events, the trail, refusals, standard error and the logs carry ids, names of scrapers and tools, words and counts only (decision 18). No business name, address, phone, email, person, ruling or reject reason, prospect list name, kept page's title or text, brief's summary, reasons or labels, website search's named or rejected sites, reasons, or confirming page's URL or title, campaign reject's reason, parcel's owner or taxpayer name or site address, park's town or name, label given to `edit_park_rules`, or owner record's note or any value it sets reaches the trail, the bus, standard output or standard error, on success or failure; candidates writes no log of its own, and a serving run writes standard error only as `D03-serve` says. Rows and what candidates makes of them reach the callers' tool answers and the signed-in pages, which is what they are for, and nowhere else. A refusal's sentence, a delivery's failure message and an error page are fixed copy constants and templates, but for three refusals that carry a detail (`D10-tools`): `enrich`'s missing prompt names the prompt and quotes prompts' refusal, `add_page`'s failed fetch quotes the failure, which may hold the URL the caller gave, and `add_page`'s cap names the cap. None of them holds a value a row, scrapes' answer or the store supplied, so no row's contents, no `name` or `phone` filter, no `q` given to `search`, no prospect list's name and no ruling's or reject's why can reach them. The owner tools' refusals carry no detail (`D10-tools`), so no note or value given to `add_business` or `set_facts` can reach one. The parks tools' refusals carry no detail (`D10-tools`), so no label given to `edit_park_rules` and nothing a parcel row holds can reach one. The paging refusals are appkit's sentences, `paging.BadPage` and `paging.Window`'s, which hold the bounds and the offending `limit` and never the `page` (`D10-tools`).

Paging adds nothing to the trail: reading a page of `prospect_lists`, `candidates`, `passes` or `parks` is a tool call recorded by appkit's `tool.called`, which carries no arguments, so neither a `page` a caller sent nor a `next` candidates answered reaches an event, the bus, a stream or a log line. A `candidates` or `passes` token holds only a number or a time and an id, and a `parks` token, and the parks page's before-token, only a sort word, a decimal and a park id, each of which the parks page takes in its `page` parameter (`D08-pages`), but a `prospect_lists` token holds a prospect list's name, which a person wrote, and the landing's prospect list window takes the same token in its `prospect_lists_page` parameter (`D08-pages`); the request pair records the path and never the query, so the token stays out of the trail there too. A token is the caller's handle on a position and the rule is kept whole, so the run that proves secrecy also searches its captures for every token, and pages the landing with one.

## Recorded decisions

- The closed set is scrapes' with `source.called` replaced by `sibling.called` and the two run names by the two pass names: candidates calls no source of its own, and scrapes and prompts are siblings reached through appkit's clients.
- **prompts adds a target, not a name** (site text decision 21): its requests are recorded by appkit's `prompts` client as `sibling.called`, with the entry's name `prompts` as target, `POST` and `/mcp`, so the closed set is unchanged, and candidates records no event of its own around a run, since appkit's client already records each request and the pass events carry the runs' counts (`D07-events`).
- **A delivery's reads are recorded as `candidates`** (decision 12): the user of their `sibling.called` is the service identity, while the pass events keep the delivery's starter, which has no user (`D07-events`). The two share the delivery's request id, so a delivery's whole trail is found under it.
- A delivery is recorded by the request pair alone, as appkit's delivery handler records it: the handler takes no writer and records nothing; its outcome is the answer's status and body, which the middleware's `request.finished` carries as the status.
- Markers are compared without regard to letter case and phone markers as digits, because candidates' normalized keys upper-case names, lower-case email domains and keep a phone's last ten digits (`D12-ingest`); a leak of a key is a leak of the value.
- A `name` or `phone` filter given to `candidates`, a `q` given to `search` and a ruling's why are treated as record text: each may be a business's name, number or a person's words, so each is a marker in the secrecy conditions and never reaches the trail, a refusal or a delivery's answer.
- **Every person-written text is a marker** (cohorts log 31): a prospect list's `name`, given to `create_prospect_list` and `edit_prospect_list`, and the `why` given to `reject`, `unreject`, `exclude` and `include`, as to `decide`, are words the owner wrote and may name a business or a person, so the secrecy conditions give a marker in each, both on the run and on the failing handler. The cohorts change adds no event (cohorts decision 26): a prospect list tool call is appkit's `tool.called`, which carries no arguments, so the closed set and the request pair are unchanged. Filter values, order entries and argument names hold no marker: they are enumerated words and numbers, and appkit's schema refusal names an unknown argument and echoes a number out of range before the handler runs (`D10-tools`), so a marker there would test appkit, not candidates.
