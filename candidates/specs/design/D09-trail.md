# D09-trail

The trail as a whole: the closed set of event names candidates records, the request pair the telemetry middleware records for every request, deliveries from the bus as appkit records them, `sibling.called` for every read of scrapes, the two pass events as the assembled run shows them, the clock and the random source every event is stamped and named from, and decision 18's secrecy, stated once for the whole app. It is scrapes' trail document with the pass events in place of the run events and appkit's `sibling.called` in place of `source.called`.

Who tells each event is another document's. The request pair is appkit's `telemetry.Middleware`'s, which `D03-serve` mounts on every request; `tool.called` is appkit's MCP server's; `service.started` and `service.stopping` are `D03-serve`'s; `event.lost` is appkit's emitter's, since the emitter is built with the writer; `sibling.called` is appkit's `scrapes` client's, which records one for every request it sends, as every sibling client of appkit does. `pass.started` and `pass.finished`, their attributes, their identity and their cause are `D07-events`'; when each is told is `D06-passes`'. This document states what the assembled run shows of them.

## The request pair and deliveries

Every request, whatever its path and whether or not it carries an identity, is recorded by the telemetry middleware as one `request.started` (method, path) and one `request.finished` (status, duration, bytes), under its request id and its caller's user (`D03-serve`). A delivery from the bus is a request like any other, `POST /events` with the events app's `X-Request-Id` and no user: appkit's delivery handler records nothing of its own, so a delivery is recorded as that request pair, its record read as a `sibling.called`, and the pass it starts tells its events, and its reads their `sibling.called`, under the same request id (decision 18).

## sibling.called

One `sibling.called` per request to scrapes (decision 18): `target` `scrapes`, `method` `GET`, `path` the read's path (`/scrapers/<name>/current`, `/runs/<id>/record` or `/runs/<id>/rows`), the status answered (0 when none came), and `duration_us`, as appkit's client records it. Its request id and user are those of the identity the read is made as (`D06-passes`): a rebuild's reads name its caller and the tool call's request id; a delivery's reads name `candidates`, the service identity, and the delivery's request id (decision 12), so the trail shows which reads no person made. Paths carry run ids and scraper names only; no row, query or body travels in it. candidates calls no other sibling, so no `sibling.called` names another target.

## The clock and the random source

Every event's time is read from `Process.Now`, and every request id `Run` mints, every pass id and every bus event id are drawn from `Process.Rand` (`D01-layout-and-run-seam`). Both are seams `cmd/candidates` fills with `time.Now` and `crypto/rand.Reader`; a test fills them with a fixed clock and a constant reader and finds the stamps and ids those give.

## Secrecy

Events, the trail, refusals, standard error and the logs carry ids, names of scrapers and tools, words and counts only (decision 18). No business name, address, phone, email, person or ruling text reaches the trail, the bus, standard output or standard error, on success or failure; candidates writes no log of its own, and a serving run writes standard error only as `D03-serve` says. Rows and what candidates makes of them reach the callers' tool answers and the signed-in pages, which is what they are for, and nowhere else. A refusal's sentence, a delivery's failure message and an error page are fixed copy constants and templates: they hold no value a call, a row, scrapes' answer or the store supplied, so no row's contents, no `name` or `phone` filter and no ruling's why can reach them.

The rule is proved at the run seam, by use, as scrapes proves its own: a fake scrapes answers rows whose names, street, city, people, phone and email are random **markers**; some of its answers are failures whose bodies echo every marker; the test's `candidates` calls filter by a marker and its `decide` calls give a marker as why; every tool, page and delivery is exercised, with passes ending `done`, `failed` with `scrapes`, `failed` with `store` and `failed` with `interrupted`, and every tool and delivery tried again with the database broken; and every capture of the run is searched, letters compared without regard to case, since candidates upper-cases names into keys and lower-cases domains: both sinks, in every field and as JSON, both streams, every refused tool result and every answer to `/events`.

## Recorded decisions

- The closed set is scrapes' with `source.called` replaced by `sibling.called` and the two run names by the two pass names: candidates calls no source of its own, and scrapes is a sibling read through appkit's client.
- **A delivery's reads are recorded as `candidates`** (decision 12): the user of their `sibling.called` is the service identity, while the pass events keep the delivery's starter, which has no user (`D07-events`). The two share the delivery's request id, so a delivery's whole trail is found under it.
- A delivery is recorded by the request pair alone, as appkit's delivery handler records it: the handler takes no writer and records nothing; its outcome is the answer's status and body, which the middleware's `request.finished` carries as the status.
- Markers are compared without regard to letter case and phone markers as digits, because candidates' normalized keys upper-case names, lower-case email domains and keep a phone's last ten digits (`D12-resolution`); a leak of a key is a leak of the value.
- A `name` or `phone` filter given to `candidates` and a ruling's why are treated as record text: each may be a business's name, number or a person's words, so each is a marker in the secrecy conditions and never reaches the trail, a refusal or a delivery's answer.
- Secrecy is required of the whole run, because the leak it guards against is a wiring one only the assembled process shows. What the tools and the pages answer is `D10-tools`' and `D08-pages`'.

## Consumer tasks

A test drives `cli.Run` with a `*telemetry.Capture` as `Sink`, an `*events.Capture` as `EventSink`, buffers as `Stdout` and `Stderr`, a `Now` returning one fixed time, a `Rand` yielding `0x5a`, and a services file whose `scrapes` entry names a Unix socket on which a fake scrapes answers and records every request; waits for `READY=1`; makes a `rebuild` call with `mcp.Client` and a `POST /events` delivery of `scrape.finished` with its own `X-Request-Id`; sends a page request with no `X-Request-Id`; lets the passes end; cancels; and compares each captured event's `Name` with the closed set, its `Time` with the fixed time, the request pair's `RequestID` with the minted id, the bus events' ids, and the `sibling.called` events with the fake's recorded requests. A test of secrecy builds the fake's rows with markers, makes every call and request R-SIQ9-63BL names, and searches every capture for every marker.
