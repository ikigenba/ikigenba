# D09-trail

The trail as a whole: the closed set of event names candidates records, the request pair the telemetry middleware records for every request, deliveries from the bus as appkit records them, `sibling.called` for every read of scrapes and every request to prompts, the two pass events as the assembled run shows them, the clock and the random source every event is stamped and named from, and decision 18's secrecy, stated once for the whole app. It is scrapes' trail document with the pass events in place of the run events and appkit's `sibling.called` in place of `source.called`.

Who tells each event is another document's. The request pair is appkit's `telemetry.Middleware`'s, which `D03-serve` mounts on every request; `tool.called` is appkit's MCP server's; `service.started` and `service.stopping` are `D03-serve`'s; `event.lost` is appkit's emitter's, since the emitter is built with the writer; `sibling.called` is appkit's `scrapes` client's and appkit's `prompts` client's, each of which records one for every request it sends, as every sibling client of appkit does. `pass.started` and `pass.finished`, their attributes, their identity and their cause are `D07-events`'; when each is told is `D06-passes`'. This document states what the assembled run shows of them.

## The request pair and deliveries

Every request, whatever its path and whether or not it carries an identity, is recorded by the telemetry middleware as one `request.started` (method, path) and one `request.finished` (status, duration, bytes), under its request id and its caller's user (`D03-serve`). A delivery from the bus is a request like any other, `POST /events` with the events app's `X-Request-Id` and no user: appkit's delivery handler records nothing of its own, so a delivery is recorded as that request pair, its record read as a `sibling.called`, and the pass it starts tells its events, and its reads their `sibling.called`, under the same request id (decision 18). A judge fire, a delivery of `cron.judge_candidates.fired`, is a delivery like any other: its request pair and, under its request id, the pass events of the pass it starts, if any (a skipped or busy judge delivery starts no pass and leaves only the request pair), and no `sibling.called`, since a judge pass reads nothing from scrapes and calls no sibling (`D06-passes`).

## sibling.called

One `sibling.called` per request to scrapes (decision 18): `target` `scrapes`, `method` `GET`, `path` the read's path (`/scrapers/<name>/current`, `/runs/<id>/record` or `/runs/<id>/rows`), the status answered (0 when none came), and `duration_us`, as appkit's client records it. Its request id and user are those of the identity the read is made as (`D06-passes`): a rebuild's reads name its caller and the tool call's request id; a delivery's reads name `candidates`, the service identity, and the delivery's request id (decision 12), so the trail shows which reads no person made. Paths carry run ids and scraper names only; no row, query or body travels in it.

One `sibling.called` per request to prompts (site text decision 21), recorded by appkit's `prompts` client, the installed interface D27 of appkit describes: it sends every call, `show`, `run` or `result`, as one `tools/call` POST to `/mcp` on the socket the services file's `prompts` entry names, so the event has `target` `prompts`, the entry's name, `method` `POST`, `path` `/mcp`, the status answered and `duration_us`. candidates records nothing of its own for a prompts request. Every one is made as the caller of the `enrich` that needs it, forwarded on the request (site text decision 7, `D06-passes`): the `show` the call makes before it starts a pass, and the `run` and `result` calls of the pass, which runs on after the call is answered, all name that caller's user and the tool call's request id. The path names no prompt, run or input; what candidates sends prompts, a company's id, name, city, state and website, travels in the request body, which no event carries. A delivery's pass and an ingest's follow-on never call prompts, since a kindless enrich leaves out every kind that runs prompts (`D06-passes`). candidates calls no other sibling, so no `sibling.called` names a target but `scrapes` and `prompts`.

## The clock and the random source

Every event's time is read from `Process.Now`, and every request id `Run` mints, every pass id and every bus event id are drawn from `Process.Rand` (`D01-layout-and-run-seam`). Both are seams `cmd/candidates` fills with `time.Now` and `crypto/rand.Reader`; a test fills them with a fixed clock and a constant reader and finds the stamps and ids those give.

## Secrecy

Events, the trail, refusals, standard error and the logs carry ids, names of scrapers and tools, words and counts only (decision 18). No business name, address, phone, email, person, ruling or reject reason, cohort name, or kept page's title or text reaches the trail, the bus, standard output or standard error, on success or failure; candidates writes no log of its own, and a serving run writes standard error only as `D03-serve` says. Rows and what candidates makes of them reach the callers' tool answers and the signed-in pages, which is what they are for, and nowhere else. A refusal's sentence, a delivery's failure message and an error page are fixed copy constants and templates, but for three refusals that carry a detail (`D10-tools`): `enrich`'s missing prompt names the prompt and quotes prompts' refusal, `add_page`'s failed fetch quotes the failure, which may hold the URL the caller gave, and `add_page`'s cap names the cap. None of them holds a value a row, scrapes' answer or the store supplied, so no row's contents, no `name` or `phone` filter, no cohort's name and no ruling's or reject's why can reach them. The paging refusals are appkit's sentences, `paging.BadPage` and `paging.Window`'s, which hold the bounds and the offending `limit` and never the `page` (`D10-tools`).

Paging adds nothing to the trail: reading a page of `cohorts`, `candidates` or `passes` is a tool call recorded by appkit's `tool.called`, which carries no arguments, so neither a `page` a caller sent nor a `next` candidates answered reaches an event, the bus, a stream or a log line. A `candidates` or `passes` token holds only a number or a time and an id, but a `cohorts` token holds a cohort's name, which a person wrote, and the landing's cohort window takes the same token in its `cohorts_page` parameter (`D08-pages`); the request pair records the path and never the query, so the token stays out of the trail there too. A token is the caller's handle on a position and the rule is kept whole, so the run that proves secrecy also searches its captures for every token, and pages the landing with one.

The rule is proved at the run seam, by use, as scrapes proves its own: a fake scrapes answers rows whose names, street, city, people, phone and email are random **markers**; some of its answers are failures whose bodies echo every marker; a fake prompts answers `show`, `run` and `result` with no marker, refuses some, ends some runs failed, and fails some requests with bodies that echo every marker; the website check and `add_page` fetch through a transport the test holds, whose pages hold markers in their titles and text, so a company's website, found from its email's domain, holds that domain's marker; the test's `candidates` calls filter by a marker, its `create_cohort` and `edit_cohort` calls name cohorts with markers, and its `decide`, `exclude`, `include`, `reject` and `unreject` calls give a marker as why; every tool, page and delivery is exercised, `add_page` with pages kept and fetches failed and `enrich` with `site_text` over a cohort of members holding markers, with passes ending `done`, `failed` with `scrapes`, `failed` with `prompts` and `failed` with `interrupted`; and every capture of the run is searched, letters compared without regard to case, since candidates upper-cases names into keys and lower-cases domains: both sinks, in every field and as JSON, both streams, every refused tool result and every answer to `/events`. The database failing is proved where the test hands the store in, as candidates' test discipline requires: a handler built over the test's own store, with the same fakes, the same transport and the same markers, has its handle failed with `SetFailing(true)` while a pass reads rows holding markers, and is then called on every tool, page and delivery; both captures, every refused tool result and every answer to `/events` are searched the same way. The handler writes neither stream, so the streams are searched at the run seam alone.

## Recorded decisions

- The closed set is scrapes' with `source.called` replaced by `sibling.called` and the two run names by the two pass names: candidates calls no source of its own, and scrapes and prompts are siblings reached through appkit's clients.
- **prompts adds a target, not a name** (site text decision 21): its requests are recorded by appkit's `prompts` client as `sibling.called`, with the entry's name `prompts` as target, `POST` and `/mcp`, so the closed set is unchanged, and candidates records no event of its own around a run, since appkit's client already records each request and the pass events carry the runs' counts (`D07-events`).
- **A delivery's reads are recorded as `candidates`** (decision 12): the user of their `sibling.called` is the service identity, while the pass events keep the delivery's starter, which has no user (`D07-events`). The two share the delivery's request id, so a delivery's whole trail is found under it.
- A delivery is recorded by the request pair alone, as appkit's delivery handler records it: the handler takes no writer and records nothing; its outcome is the answer's status and body, which the middleware's `request.finished` carries as the status.
- Markers are compared without regard to letter case and phone markers as digits, because candidates' normalized keys upper-case names, lower-case email domains and keep a phone's last ten digits (`D12-resolution`); a leak of a key is a leak of the value.
- A `name` or `phone` filter given to `candidates` and a ruling's why are treated as record text: each may be a business's name, number or a person's words, so each is a marker in the secrecy conditions and never reaches the trail, a refusal or a delivery's answer.
- **Every person-written text is a marker** (cohorts decisions log 31): a cohort's `name`, given to `create_cohort` and `edit_cohort`, and the `why` given to `reject`, `unreject`, `exclude` and `include`, as to `decide`, are words the owner wrote and may name a business or a person, so the secrecy conditions give a marker in each, both on the run and on the failing handler. The cohorts change adds no event (cohorts decision 26): a cohort tool call is appkit's `tool.called`, which carries no arguments, so the closed set and the request pair are unchanged. Filter values, order entries and argument names hold no marker: they are enumerated words and numbers, and appkit's schema refusal names an unknown argument and echoes a number out of range before the handler runs (`D10-tools`), so a marker there would test appkit, not candidates.
- **A kept page is record text**: its title and text are what a company says about itself, so the transport's pages hold markers in both, and the trail, the bus and the streams must hold neither. They reach the `add_page` and `candidate` answers and the candidate and text pages, which is what they are for.
- **Departure: refusals that carry variable text** (`D10-tools`' rule that a refusal is a word and a fixed sentence, and decision 18 of the parent, which keeps refusals to ids, names and words). Three refusals carry a detail: `enrich`'s missing prompt names the prompt and quotes prompts' refusal (site text decision 7), `add_page`'s failed fetch quotes the failure (decision 2), and `add_page`'s cap names the cap (decision 3). The prompt's name is the kind's and the cap a constant, so neither can hold a marker. prompts' refusal is prompts' sentence about a prompt candidates named, so the secrecy conditions make no prompts answer a marker source: the fake's refusals and successes hold none. A failed fetch's text may hold the URL the caller gave, which is on the company's website and so holds its domain's marker; the caller sent it and gets it back, and it reaches no event, so the refusal requirements (R-0JFG-JVIV, R-0KNC-XN9K) let a refused `add_page` result hold the markers its own `url` holds and no other, while the trail and stream requirements make no exception. A leak of the company's email domain into that one refusal cannot be told from the URL there, which is accepted: it is the host the caller named.
- **prompts' failure bodies echo markers**, as scrapes' do: candidates sends prompts a company's name, city and website, so a failing prompts may answer with them, and nothing of a failed request's body may reach a refusal, the trail or a stream. Only the answers candidates may relay, its refusals and the run's members, hold no marker.
- **A `cohorts` token holds a cohort's name**, so R-0LV9-BF09 pages `cohorts` and requests the landing with a `cohorts` token: the token is searched for whole, and the landing's query is shown never to reach the trail.
- **A failing database is proved at the handler, not the run** (candidates/AGENTS.md): a store failure is provoked only with `SetFailing(true)` on a handle the test hands in, and `cli.Run` builds its store over its own, so secrecy on the database's failure paths is the handler's (R-0EJV-0SK3), and the run's conditions (R-0DBY-N0TE) end no pass `failed` with `store`. The streams have no failure-path counterpart, since only the run writes them.
- **Tokens are searched like markers**: the conditions page every paged tool with tokens it answered and with a `page` that is a marker, and R-0LV9-BF09 searches every capture for both; the trail itself is unchanged by paging, as appkit's D25 states of every paged tool.
- Secrecy is required of the whole run, because the leak it guards against is a wiring one only the assembled process shows. What the tools and the pages answer is `D10-tools`' and `D08-pages`'.
