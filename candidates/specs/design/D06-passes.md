# D06-passes

The engine: `internal/passes`, the one place a pass is started, worked, finished, settled at start and abandoned at the stop, and the place a `scrape.finished` delivered on the bus becomes a pass. A `rebuild` call (`D10-tools`) or a delivery starts a pass; the engine records it `running` (`D04-store`), tells `pass.started` (`D07-events`), answers at once, and works it in the background: it reads the run's rows from scrapes over the socket through appkit's `scrapes` client, hands them to the store a batch at a time to be resolved (`store.Attach`, `D12-resolution`), marks gone the links the run no longer holds (`store.MarkGone`, `D12-resolution`), re-scores the candidates it touched (`store.Rescore` or `store.RescoreAll`, `D13-scoring`), and finishes the pass `done` with its nine counts or `failed` with its reason, telling `pass.finished`. One pass runs at a time (decision 11). It also declares the pass record's JSON, which the tools answer, every refusal word the tools answer, and the identity every read of scrapes is made as (decisions 12 and 21). It is scrapes' run engine with a pass in place of a run, scrapes' sibling read path in place of a source, and one pass at a time in place of one run per scraper.

`D01-layout-and-run-seam` declares the run seam, the settings, `cli.SweepInterval` and the names that cross packages (`passes.Config`, `Engine`, `New`, `Rebuild`, `Deliver`, `Handlers`, `Recover`, `Drain`, `Refusal`, `Record`, `RecordOf`); `D04-store` the pass records, their words, one pass at a time in `AddPass`, the redelivery refusal and the prune; `D12-resolution` what `Attach` and `MarkGone` do to candidates and links; `D13-scoring` what `Rescore` and `RescoreAll` write; `D05-sources` the registry and how a source reads a row; `D07-events` the two pass events, their identity and cause, and `/declarations`; `D09-trail` `sibling.called` and secrecy; `D10-tools` the tools and the sentences a refusal word is shown with; `D03-serve` builds the engine, mounts the delivery and calls `Recover` and `Drain` in its start and stop.

## Starting a pass by `rebuild`

`Rebuild` takes the caller. Once the drain has begun it is refused `stopping`; with no scrapes client (the services file names no `scrapes` entry) `unavailable`, since a pass could read nothing; while a pass is `running`, whoever started it, `busy` (the store refuses the record, so a `rebuild` and a delivery racing cannot both win); and the database failing is an error matching `store.ErrUnreachable`, which the tool answers `unavailable`. Otherwise the pass is recorded with trigger `rebuild` and the caller as its starter, `pass.started` is told, the work begins in a goroutine, and `Rebuild` answers the record, `running`, without waiting: the MCP gateway gives a call fifty seconds and a pass over 17,000 rows may take longer.

## Starting a pass by a delivery

candidates accepts exactly one event name, `scrape.finished` (`trail.Accepted`, `D07-events`), which appkit's delivery handler hands to `Deliver` with the bus event's id and depth already on the context as its cause, and the caller appkit's telemetry middleware built from the request: the events app's request id, or one minted for it, and no user. The bus event carries scrapes' attributes `scraper`, `run`, `status`, `reason` and the counts; the engine reads `scraper`, `run` and `status` and the event's id.

A delivery is skipped (`Skip`, nothing to retry) when it is not for candidates: an event of another name, one with no id, one whose `status` is not `done`, one whose `scraper` the registry does not hold (decision 3), or one with no `run`. It is skipped too when a pass the store holds already carries its event id as its delivery or already names its run as its trigger, whatever became of that pass: redelivery is safe, and a second `scrape.finished` for one run under another event id is the same run (decision 11). That check reads only candidates' own records, so a redelivery is skipped even while scrapes cannot be reached.

Otherwise the delivery reads the run's record from scrapes before it answers (orchestrator ruling): a run scrapes does not know (404, unknown or pruned) or a record whose status is not `done` is skipped. Any other failure of the read, scrapes unavailable, a dead socket, another status, an answer that is not a record, or no scrapes client at all, is a pass that failed: the pass is recorded, failed `scrapes` with its counts 0, `pass.started` and `pass.finished` told, and `OK` answered, so the bus does not retry and the failure is on the record where a person sees it; a later delivery of the same run is skipped as a redelivery, and a rebuild repairs. A record that is read and `done` is recorded as a pass, with the run's id as its trigger and the bus event's id as its delivery, `pass.started` told and `OK` answered, all before the rows are read. While another pass runs the store refuses the record and the delivery answers `Fail`: a pass takes seconds and the bus retries for minutes, so a run landing during a pass is resolved after it, not lost (decision 11). Stopping and the database failing answer `Fail` as well; `Fail` is kept for those three.

A pass a delivery started is started as the delivery: its request id is the delivery's, and its user is whatever user the delivery's request named, which is none; the starter shown is scrapes and the run (decision 11), which the trigger says, as scrapes' run started by a cron fire shows `cron` and its slug.

## Identity on the read

scrapes' read path requires an identity, and appkit's `scrapes` client forwards the caller on the call's context. A pass a `rebuild` started reads scrapes as its caller: the request carries the caller's user id, email and request id, as every sibling call forwards the caller. A delivery carries no person, so every read a delivery makes, its record read and its pass's rows, is made as the **service identity** (decision 12): `X-User-Id` `candidates`, no `X-User-Email`, and the delivery's request id, with the delivered bus event as the cause of the pass's events. scrapes trusts any process at its socket, so the read is answered and its trail names `candidates` as the user (decision 21). It is the suite's first service-to-service call made as no person, and recorded as such below.

## The work

A pass's work runs in a goroutine and is cancelled by the drain and by nothing else: the call or delivery that started it may end while it runs. For a delivery, the run is the one the record named; for a rebuild, each registered scraper's current run, read with `Current` in the registry's order, a scraper with no current run (scrapes answers 404) contributing no rows and marking nothing gone. For each run the work streams the rows (`Rows`) and has the source the registry holds for the run's scraper read each one (`D05-sources`), handing the store a batch of `passes.BatchSize` observations at a time, as they arrive, so a run of any size passes through with one batch held (decision 1). Once a run's stream has ended, and the number of rows it handed equals the record's `rows`, the links of that scraper the run no longer holds are marked gone. Then the candidates touched are re-scored, each once: every distinct candidate the batches and the marking touched for a delivery, every active candidate for a rebuild, which treats every row as changed so normalized forms, keys, estimates and assessments are recomputed while candidates, their ids and the rulings stay (decision 11). Rulings are applied throughout, by the store (`D12-resolution`).

The pass then finishes `done` with its nine counts: `rows` the rows streamed, and the rest the sums of what the store's writes answered (`new`, `changed`, `unchanged`, `created`, `linked` from the batches, `gone` from the marking, `rescored` and `unranged` from the re-score). What each counts is the owning document's.

## Cost

A pass costs in proportion to its rows (orchestrator ruling). A pass over the real FMCSA run of 16,706 rows never finished: 1,970 rows took 82 seconds and a re-scrape with every row unchanged four minutes, the pages timing out meanwhile, because every batch reloaded and compared the whole database and every row re-derived every candidate. Now each batch is one write transaction touching its own rows and the candidates they attach to, by key (`D04-store`); an unchanged row costs a lookup, a touch of its last seen, and its share of its candidate's display re-derived once per batch; the gone-marking is one statement per run; and each candidate the pass touched is re-scored once, after the stream, from the candidate's record, its own links and rulings, and the ZIP table's minutes for its display ZIP. A pass's work holds no lock of the engine's while it calls the store, and a read of the store answers while a batch is being written (`D04-store`), so the pages and the tools answer throughout.

What is required is the time: a delivery of a **generated run** of 10,000 rows into an empty store, a second delivery of a run alike to it with every row unchanged, and a rebuild over that run each finish `done` within 120 seconds, under the race detector the gate runs, with the counts the attach rule gives. The work the pass asks of scrapes is counted too: one rows read per run (R-JVFQ-191Q).

A pass ends `failed` with one reason (decision 11):

- `interrupted`: the drain cancelled the work before it ended, whatever else then failed;
- `store`: a write the work handed the store failed;
- `scrapes`: any other failure: a read of scrapes that failed or answered something that is not a record or a row, a current run not `done`, or a stream whose row count disagrees with its record's `rows`, a stream cut short at a line boundary being told this way (appkit's `scrapes` client leaves that check to its caller).

A failed pass keeps its record and its counts at 0, and leaves in place every batch it had already handed the store; the next pass or a rebuild repairs them, since every write is idempotent. A stream that failed marks nothing gone, so a short read never takes evidence away. `pass.finished` is told once the ending is recorded; an ending the store cannot record tells no event and leaves the pass `running` for the next start to settle, as scrapes leaves a run.

## Starting and stopping

`Recover` runs at start, before ready (`D03-serve`): every pass still `running` was cut off by a dead process and is failed `interrupted`, its `pass.finished` told as its starter with no cause. `Drain` is the stop: from its call `Rebuild` refuses `stopping` and `Deliver` answers `Fail`, and a call already under way that has not recorded its pass records none; every running work is cancelled at once, its read of scrapes ended, and its pass failed `interrupted` (decision 11). `Drain` returns once every pass the engine started has ended, or when its context ends, which `D03-serve` sets to the drain deadline, `DRAIN_SECONDS` after the signal.

## The sweep

Once before ready, after `Recover`, and then each time a wait of `cli.SweepInterval` on `Process.After` ends, the passes past keeping are pruned with `store.PrunePasses` and `CANDIDATES_KEEP_PASSES`: the newest that many `done` passes are kept and, separately, the newest that many `failed` passes, so a page still shows what went wrong; a `running` pass is never pruned (decision 16). A pruned pass is gone from the tools and the pages; candidates, links, estimates, assessments and rulings are never pruned. A prune that fails is silent and tried again at the next interval.

## The pass record

The record the tools answer is `passes.Record`, made from a stored pass by `passes.RecordOf`: `id`, `trigger`, `status`, `reason` when failed, `started`, `finished` once ended, the nine counts, and the starter: `user` and `email` for a `rebuild`, nothing for a delivery, whose trigger names the run. The delivery and the request id are not part of it.

## Refusals and failures

A refusal is a `*passes.Refusal`, a word. All of candidates' refusal words are declared in `internal/passes` (`D01-layout-and-run-seam`), so the tools tell every refusal apart with one `errors.As` (`D10-tools`): `not_found`, `invalid`, `busy`, `stopping` and `unavailable` (decision 14). The engine answers `busy`, `stopping` and `unavailable`; `not_found` and `invalid` are the tools' (`D10-tools`), and the database failing reaches them as an error matching `store.ErrUnreachable`, which they answer `unavailable`. A delivery's `Fail` carries a fixed message, a copy constant naming no value: `passes.Stopping` while stopping, `passes.Busy` while a pass runs, `store.Unreachable` when the database fails.

## Recorded decisions

- **The service identity on a delivery's reads** (decision 12, binding): `X-User-Id` `candidates`, the service's own name, no email, the delivery's request id. It is the suite's first service-to-service call made as no person. The pass's own starter stays the delivery's caller, as scrapes' delivery-started run keeps the delivery's caller, so the pass's events carry the delivery's request id and no user (`D07-events`) while its reads' `sibling.called` carry `candidates` (`D09-trail`).
- **The record is read before the delivery is answered** (orchestrator ruling, superseding coordinator decision C1): an unknown run or one not `done` is skipped; any other read failure records a pass failed `scrapes` and answers `OK`, so a scrapes outage shows as a failed pass rather than as retries and a paused subscriber, and `Fail` stays reserved for busy, stopping and the database. A delivery with no scrapes client is treated as an unavailable read. The redelivery check comes first and reads only the store, so a retry of a run already passed is skipped without asking scrapes.
- **One pass at a time, refused by the store** (`D04-store`): a rebuild during a pass is `busy`, a delivery `Fail`. scrapes' delivery skips when busy; candidates fails, because a lost `scrape.finished` is a lost month of evidence (decisions document, Rejected).
- **A scraper with no current run contributes nothing to a rebuild** rather than failing it: the registry may hold a scraper whose first run has not landed, and the rebuild still re-scores every candidate. A current run that is not `done` fails `scrapes`, since scrapes answers only `done` runs as current.
- **The line count is the stream's check** (decision 2): appkit's client cannot tell a stream cut at a line boundary from a whole one; the pass compares the rows handed with the record's `rows` and fails `scrapes` on a mismatch, before marking anything gone.
- **The batch size, 500, is a constant of the rules version** (decision 17), declared as `passes.BatchSize`; a failed pass keeps every full batch it handed over. Whether a partial last batch of a failed stream is kept is left open: the next pass repairs either way.
- **Precedence of endings**: a work the drain cancelled is `interrupted` whatever then failed; a refused write is `store`; anything else is `scrapes`. The drain cancels at once, as scrapes' does: the pass cannot be resumed, and the next delivery or a rebuild repairs it.
- **An ending the store cannot record leaves the pass `running`**, as scrapes leaves a run, for the next start's `Recover` to fail `interrupted`; until then every new pass is refused as busy. Retrying the ending is not designed: the database failing is a broken host.
- **No queue**: one pass at a time is the whole concurrency rule, and the bus's retries are the queue.
- **The sweep's requirements are stated here, at the run seam**, as scrapes states its own; the prune is the store's (`D04-store`).
- **A failed prune is described, not required, at the run seam.** A store failure is provoked only with `SetFailing(true)` on a handle the test hands in (candidates/AGENTS.md), and `cli.Run` builds its store over its own handle, so no permitted test can fail a prune under `Run`. What is required is the store's half, that a failing `PrunePasses` answers `ErrUnreachable` and removes nothing (`D04-store`, R-OD8H-2EDG), and the sweep's, that the next interval prunes again (R-ZLWR-ML5L); that the start goes on to ready and the failure is silent is this overview's.
- **The bound is 120 seconds for 10,000 rows** (orchestrator ruling): a probe of a keyed pass, SQL by key on decision 16's indexes over appkit's `db`, took 14 to 23 seconds per pass of 5,000 rows under `go test -race` and about one second without it on the developer's machine. At that rate 10,000 rows take about 30 to 45 seconds under the race detector, leaving the build's fuller work and a loaded machine room inside 120 seconds, and 16,706 real rows well under a minute without it: about 3.4 seconds at the probe's rate of about one second per 5,000 rows, and at most about 13 seconds even at the rate the bound allows, 120 seconds per 10,000 rows under the race detector divided by the probe's race factor of about 15, times 1.67, inside decision 20's minute. The store this replaces took 82 seconds for 1,970 rows, four minutes for a re-scrape with every row unchanged, and had not finished the real 16,706 rows after 14 minutes, each without the race detector. 10,000 rows rather than 5,000 makes a cost growing with the square of the rows four times as visible. A re-scrape with every row unchanged and a rebuild are held to the same bound, since the first was the slowest case seen and the second is the repair every failure points to.
- **Re-scoring once per touched candidate per pass** is R-YZYK-QPT3, whose writes end with one `Rescore` of the distinct ids the batches and the marking answered, with R-Z16H-4HJS, which requires the records those writes leave.
- **A delivery is worked whatever run is current**: a delivery of an older run after a newer one marks gone what the older run lacks; the next delivery or a rebuild repairs it.

## Consumer tasks

`D03-serve` builds `eng := passes.New(passes.Config{Store: st, Sources: reg, Scrapes: sc, Telemetry: w, Events: em})`, `sc` nil when the services file has no `scrapes` entry; mounts `events.DeliveryHandler(eng.Handlers())` and `events.DeclarationsHandler(em, eng.Handlers())`; calls `eng.Recover(bg)` and `st.PrunePasses(bg, s.KeepPasses)` before ready, prunes again on each `p.After(cli.SweepInterval)`, and calls `eng.Drain(drainCtx)` at the signal. The `rebuild` tool (`D10-tools`), `c` the call's caller: `p, err := eng.Rebuild(ctx, c)`, answering `passes.RecordOf(p)`; a refusal told with `var rf *passes.Refusal; errors.As(err, &rf)`, reading `rf.Word`, and any other error, which matches `store.ErrUnreachable`, answered `unavailable`. The `pass` and `passes` tools answer `passes.RecordOf(p)` of what `st.GetPass` and `st.ListPasses` return.

A test opens its own database, builds a store over it, a writer over a `*telemetry.Capture` and an emitter over an `*events.Capture` with `trail.Emits()`, serves a fake scrapes on a Unix socket in a short temporary directory that answers `/runs/<id>/record`, `/runs/<id>/rows` and `/scrapers/<name>/current` with the record and rows the test chooses, holds the rows answer open after the lines it chooses until released, and records every request with its headers; builds `sc := scrapes.NewClient(scrapes.ClientConfig{Service: services.Entry{Name: "scrapes", Socket: sock}, Telemetry: w})` and `eng := passes.New(passes.Config{Store: st, Sources: sources.New(fmcsa.New()), Scrapes: sc, Telemetry: w, Events: em})`; calls `eng.Rebuild(ctx, identity.Caller{UserID: u, Email: m, RequestID: q})`; calls `eng.Deliver(events.NewContext(identity.NewContext(ctx, identity.Caller{RequestID: q}), events.Cause{ID: e, Depth: 0}), events.Delivery{Event: events.Event{ID: e, Name: trail.Accepted, Attrs: events.Attrs{"scraper": "fmcsa", "run": r, "status": "done"}}, Attempt: 1})` and compares the outcome with `events.OK()`, `events.Skip()`, `events.Fail(passes.Busy)`, `events.Fail(passes.Stopping)` or `events.Fail(store.Unreachable)` by `==`; polls `st.GetPass` until the pass is `done` or `failed`; reads the links with `st.ListCandidates` and `st.Links`; calls `Drain` with a context it cancels; and compares the store, the fake's requests and the captured events. A test of cost serves a generated run from the fake, its rows built in the test from a counter, delivers it, delivers an alike run under another run id and event id, answers that run as current and calls `Rebuild`, and polls `st.GetPass` for each pass with a deadline of 120 seconds from the call that fails the test, as candidates/AGENTS.md lets a test wait for a pass it started, each row's `Run` the run's id, comparing its counts. A run-seam test seeds a `Dir` with a pass left `running` and with done and failed passes, drives `cli.Run` with a services file whose `scrapes` entry names the fake, an `After` whose channels it holds, `CANDIDATES_KEEP_PASSES` and `DRAIN_SECONDS` set through its `LookupEnv`, and reopens the database after `Run` returns.
