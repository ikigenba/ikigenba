# D06-passes

The engine: `internal/passes`, the one place a pass is started, worked, finished, settled at start and abandoned at the stop, and the place an event delivered on the bus becomes a pass. A pass is one of four kinds (`D04-store` records its kind and its origin). An **ingest** pass, started by a `scrape.finished` delivered on the bus, reads the run's rows from scrapes over the socket through appkit's `scrapes` client, hands them to the store a batch at a time to be ingested (`store.Attach`, `D12-ingest`) and marks gone the links the run no longer holds (`store.MarkGone`, `D12-ingest`); it judges nothing. A **judge** pass, started by a `cron.judge_candidates.fired` delivered on the bus or by a `judge` call (`D10-tools`), judges every active candidate from scratch (`store.JudgeAll`, `D13-judging`) and reads nothing from scrapes. An `ingest` call (`D10-tools`) starts an ingest pass by hand: named a scraper, it ingests that scraper's current run as a delivered ingest does, and an enrich follows it when it ends `done`; named none, it is a **full ingest**, which ingests every registered scraper's current run, then records a fresh result of every derived kind for every active candidate (`store.Derive` forced, `D04-store`, `D16-enrichers`), and then judges every active candidate, as one pass; it fetches nothing. An **enrich** pass, started by an `enrich` call with no target (`D10-tools`) or by an ingest pass that ended `done`, walks the enrichers' registry (`D16-enrichers`) over the whole corpus: the one kind the call named, or every kind in registry order but those run through prompts and `drive_route`, the derived kinds (`drive_minutes`, `link_facts`) first and then the fetched one (`website_check`, `D15-website-check`) when its checker is ready; for each kind it records a result for every candidate due for it, due meaning that the candidate's inputs for the kind are not empty and differ from those of its newest result of the kind, or it has none. An **enrich_target** pass, started by an `enrich` call with a target, one prospect list or one candidate, walks the one kind the call named over the target's candidates alone: those due for it or, with `force`, every one whose inputs are not empty. For the prompts kinds `website_search`, `site_text` and `brief` (`D16-enrichers`) that is one run of the caller's prompt named for the kind (`website-search`, `site-text`, `brief`) per candidate in the prompts app, through appkit's `prompts` client, at most `RunsInFlight` at once; the agent in a `website_search` run searches the web for the site of a company with none on record and names it, candidates confirming that site with one fetch through the website checker as the result is recorded; the agent in a `site_text` run keeps pages on the company through `add_page` (`D10-tools`); the agent in a `brief` run reads the pages kept, which its input carries, and keeps none; and when the run ends the pass records a result saying how it ended and what it cost. For `drive_route` (`D16-enrichers`) that is one routing of the candidate's address per selected target, from the origin the space sets, through the routing client `Config.Routes` (`D17-drive-route`), at most `RoutesInFlight` at once, each recorded as a result with the minutes and miles or why there are none; it runs only over a target, never over the corpus. Neither enrich kind reads anything from scrapes, and each writes nothing but results and the facts rows beside them; outside the suite each fetches only through the website checker, and a `drive_route` pass makes its **requests to the routing service** through the routing client alone, which are not fetches. An enrich of either kind that wrote at least one derived or website result starts a judge, unless a judge is already running, so the new facts reach the opinions without waiting for the morning; a pass of a prompts kind or of `drive_route` writes neither and starts none. Whatever starts it, the engine records the pass `running` (`D04-store`), tells `pass.started` (`D07-events`), answers at once, works it in the background, and finishes it `done` with its nineteen counts or `failed` with its reason, telling `pass.finished`. One rule says what runs together: a pass is refused `busy` only while another pass of the same kind over the same scope is running, the scope being a delivered ingest's run, a hand ingest's scraper or, for a full ingest, the corpus, an `enrich_target`'s target, and the corpus for a judge and an enrich (`D04-store`); every other combination runs together. Nothing refreshes a stored judgment: a pass's end writes nothing but its own record. The engine also declares the pass record's JSON, which the tools answer, every refusal word the tools answer, the identity every read of scrapes is made as (decisions 12 and 21), and that every request to prompts is made as the caller of the `enrich`. It is also where campaigns' three events become campaign uses: a delivery of `campaign.member.added`, `campaign.member.rejected` or `campaign.piece.delivered` records, by one write to the store, that a business was added to, rejected in or sent a piece by a campaign, and starts no pass (campaigns decisions 16 and 17). It is scrapes' run engine with a pass in place of a run, scrapes' sibling read path in place of a source, and one pass per kind and scope in place of one run per scraper.

`D01-layout-and-run-seam` declares the run seam, the settings, `cli.SweepInterval` and the names that cross packages (`passes.Config`, `Engine`, `New`, `Ingest`, `Enrich`, `EnrichTarget`, `Deliver`, `Handlers`, `Recover`, `Drain`, `Refusal`, `Record`, `RecordOf`); `D16-enrichers` the registry, its kinds, which are derived, which fetched and which run through prompts (an `enrichers.Prompter`), each kind's inputs and result, and a prompts kind's prompt name, run input and result, the website search's confirmation of the site its agent names included; `D15-website-check` what the website kind checks and records, its batches and what its five counts mean, and the one fetch `Get` makes, which the website search's confirmation is; `D04-store` the due rule, `Derive`, `DueAmong` and `DeriveAmong`, the facts row, a candidate's subject and its pages, and the pass records, their kinds, origins, targets and words, the busy rule in `AddPass`, the redelivery refusal and the prune; `D14-prospect-lists` a prospect list's members; `D12-ingest` what `Attach` and `MarkGone` do to candidates and links; `D13-judging` what `Judge` and `JudgeAll` write, the judgments of a candidate at a time; `D05-sources` the registry and how a source reads a row; `D07-events` the two pass events, their identity and cause, the five names candidates accepts, and `/declarations`; `D09-trail` `sibling.called` and secrecy; `D04-store` also the campaign uses, their three writes, the merge pointer each follows and what a repeat changes, and `D14-prospect-lists` the filter that reads them; `D10-tools` the tools, `add_page` among them, and the sentences a refusal word is shown with; `D03-serve` builds the engine, mounts the delivery and calls `Recover` and `Drain` in its start and stop. The prompts client is appkit's `prompts` package (D27 of appkit), installed as an interface: `Show` reads a prompt by name, `Run` starts a run with an input object, `Result` reads a run, a refusal is a `*prompts.Refusal` carrying prompts' text, and the client waits for nothing. The routing client is `internal/routes`' `Client` (`D17-drive-route`), which `D01-layout-and-run-seam` builds over `Process.HTTP` only when the space holds the Maps key, leaving `Config.Routes` nil otherwise; `D16-enrichers` declares `drive_route` an `enrichers.Router`, its `Route` answering a result and an `enrichers.Tally` of the requests made, and `D04-store` the origin the subject carries and how the facts row prefers a matching route over the ZIP estimate.

Decisions cited by number are the decisions document that delivered candidates. "Judgments decision N" is entry N of the decisions document of the two-judgments change, "Enrichers decision N" is entry N of the decisions document of the enrichers change, "website log X" entry X of the decisions log of the website-check change, "site text decision N" entry N of the decisions document of the site-text change, "brief decision N" entry N of the decisions document of the brief change, "website search decision N" outcome N of the decisions document of the website-search change, and "S N" entry DN of the decisions log of the website-search change. "Website states outcome N" is outcome N of the decisions document of the website-states change, which made `none` mean that a search found nothing. "Campaigns decision N" is entry N of the decisions document of the campaigns change, and "campaigns log DN" entry DN of its delivery log. "Funnel rename decision N" is decision N of the decisions document of the funnel rename, which gives what candidates stores, answers and shows the funnel's stage names, and "funnel rename log DN" entry DN of its delivery's decisions log. "Drive route decision N" is outcome N of the decisions document of the exact drive time change.

## Starting a pass by `ingest` or `judge`

`Ingest` takes the caller and a scraper, empty for every scraper. Once the drain has begun it is refused `stopping`; a scraper the registry does not hold is `invalid`; with no scrapes client (the services file names no `scrapes` entry) `unavailable`, since a pass could read nothing; while another hand ingest of the same scraper, or, for an empty scraper, another full ingest, is `running`, whoever started it, `busy` (the store refuses the record, so two `ingest` calls racing cannot both win), a delivered ingest, a judge or an enrich of either kind being no bar; and the database failing is an error matching `store.ErrUnreachable`, which the tool answers `unavailable`. Otherwise the pass is recorded with kind `ingest`, origin `ingest`, trigger `ingest`, its scraper and the caller as its starter, `pass.started` is told, the work begins in a goroutine, and `Ingest` answers the record, `running`, without waiting: the MCP gateway gives a call fifty seconds and a pass over 17,000 rows may take longer. The work reads each scraper's current run with `Current`, as the caller; a scraper with no current run gives no rows. A scraper ingest then works its run as a delivered ingest does, marking gone and judging nothing, and an enrich follows it when it ends `done`, as one follows an automatic ingest (funnel rename decision 9); a full ingest goes on to force every derived kind and judge, and starts nothing. `Judge` takes the caller. Once the drain has begun it is refused `stopping`; while any judge is `running`, `busy`; it needs no scrapes client. Otherwise it records a pass with kind `judge`, origin `judge`, trigger `judge` and the caller as its starter, and works it as the daily judge's pass (funnel rename decision 10); a judge starts nothing.

## Starting a pass by `enrich`

`Enrich` takes the caller and the kind the `enrich` tool was given with no target, empty for every kind (`D10-tools`). Once the drain has begun it is refused `stopping`; with a kind the registry does not hold, or a kind run through prompts (`website_search`, `site_text` or `brief`, site text decision 6, brief decision 10 and website search decision 1: a pass over every candidate would be thousands of paid runs by accident), or `drive_route`, run through the routing service (drive route decision 1: forty thousand paid requests for companies that will never be prospects), `invalid`, though the tool refuses both before it calls; with a fetched kind named whose fetcher is not ready (`website_check` while `Config.Website` is nil, which `D15-website-check` says when) `unavailable`; and while another corpus enrich is `running`, whoever started it, `busy`. An empty kind is never `unavailable`: with no checker it walks the derived kinds and fetches nothing, and it never runs a kind through prompts or the routing service. Any other pass running is no bar, an `enrich_target` included: an enrich reads the candidates' display emails and ZIPs, their links and the ZIP table, and writes only results and facts rows (site text decisions 15 and 16; see the recorded decision on the busy rule). The database failing is an error matching `store.ErrUnreachable`. Otherwise the pass is recorded with kind `enrich`, origin `enrich`, trigger `enrich` and the caller as its starter, `pass.started` is told, the work begins in a goroutine and `Enrich` answers the record, `running`: some 7,000 domains at the website check's pace take about an hour. The kind asked for is not stored on a corpus enrich; its `enrich_kind` is empty.

## Starting a pass by a targeted `enrich`

`EnrichTarget` takes the caller, the kind, the target, a `pl_` or `cand_` id, and `force`, as the `enrich` tool was given them with a `prospect_list` or a `candidate` (`D10-tools`, site text decision 12). It is refused, the first that holds: `stopping` once the drain has begun; `invalid` with no kind or one the registry does not hold, since one targeted pass walks exactly one kind; `not_found` for a target that is neither id, a prospect list the store does not hold or has deleted, or a candidate it does not hold; `invalid` for a merged candidate, as a reject of one is; `unavailable` for a fetched kind whose checker is not ready or a prompts kind that is not ready: one with no prompts client (the services file names no `prompts` entry, site text decision 21), and `website_search` also with no checker, since it confirms the site its agent names through the checker (S 1); for `drive_route`, `invalid` with the text `passes.NoRouteKey` when there is no routing client, the space holding no Maps key (drive route decision 13), and `unavailable` when there is one its `Ready` refuses; for a prompts kind, the prompt's check below; `busy` while another `enrich_target` over the same target is running, whatever its kind; and the database failing is an error matching `store.ErrUnreachable`. A prospect list and a candidate it holds are different targets, and a corpus enrich, a full ingest, an ingest or a judge running is no bar.

For a prompts kind, before it records anything, the call asks prompts for the caller's prompt by the kind's prompt name (`site-text` for `site_text`, site text decision 7; `brief` for `brief`, brief decision 1; `website-search` for `website_search`, website search decision 1). A refusal, which is how prompts answers a prompt the caller does not have, refuses the call `invalid` with a text of its own: `passes.NoPrompt`, the prompt's name and, when prompts said why, prompts' own text, so the caller reads which prompt is missing. Any other failure of that request refuses it `unavailable`. The model, the instructions and the tools are the prompt's; candidates reads none of them.

Otherwise the pass is recorded with kind `enrich_target`, origin `enrich`, trigger `enrich`, the target, the kind as its `enrich_kind` and the caller as its starter, `pass.started` is told, the work begins in a goroutine and `EnrichTarget` answers the record, `running`. The **targets** are fixed at the call: the prospect list's current members in their order, as `ReadProspectList` answers them (`D14-prospect-lists`: the first `size` matching candidates, standing rejects and excluded candidates already left out), or the one candidate.

## Passes started by a pass

Two endings start a pass, its **follow-on**, with origin `pass` and the starting pass's id as its trigger (website log A1):

- an ingest recorded `done` starts an enrich of every kind but those run through prompts and `drive_route`, whether or not there is a checker, so a run's new and changed candidates get their derived facts and, with a checker, their websites; while a corpus enrich is already running the store refuses the record and nothing is started or recorded, not even a failed pass, since the running enrich re-reads the due set batch by batch (website log P8); nothing else refuses it;
- an enrich or an `enrich_target` recorded `done` with at least one derived or website result written (its `derived`, `https`, `http` and `none` summing to one or more) starts a judge, so the new facts reach the opinions at once; while a judge is running the store refuses it, nothing is recorded, and the next day's judge picks the results up. A pass of a prompts kind, `website_search`, `site_text` or `brief`, writes none of those four counts, so it starts no judge (site text decision 10, brief decision 9): neither site text nor a brief feeds a judgment, and a website search follows the same rule, the site it found moving the facts row's website but no opinion, since the judge's website evidence reads the website check alone (website search decision 12, `D13-judging`).

Nothing else starts a follow-on: not a judge, a full ingest, a failed pass, an enrich of either kind that wrote no derived or website result, or anything once the drain has begun. A follow-on is started as no person: no user, the starter's request id, and on its events the starter's event cause, so the trail of a delivered `scrape.finished` runs through the ingest, the enrich and the judge. Its `pass.started` follows its starter's `pass.finished`.

## Starting a pass by a delivery

candidates accepts exactly five event names (`D07-events`): `scrape.finished` (`trail.Accepted`), which starts an ingest pass; `cron.judge_candidates.fired` (`trail.AcceptedJudge`), the daily fire of the cron trigger `judge_candidates`, which starts a judge pass; and campaigns' three, `campaign.member.added` (`trail.AcceptedAdded`), `campaign.member.rejected` (`trail.AcceptedRejected`) and `campaign.piece.delivered` (`trail.AcceptedDelivered`), which start no pass and record a campaign use (campaigns decision 16, campaigns log D15 and D25). They are exact names, as scrapes accepts its triggers' `cron.scrape_<scraper>.fired`: the events app delivers only on `*` or an exact name. appkit's delivery handler hands the first two to `Deliver` and the other three to `DeliverCampaign`, with the bus event's id and depth already on the context as its cause, and the caller appkit's telemetry middleware built from the request: the events app's request id, or one minted for it, and no user. `Deliver` tells its two apart by the event's name, and `DeliverCampaign` its three; a pass is started by a delivery only through `Deliver`.

### An ingest delivery

The bus event carries scrapes' attributes `scraper`, `run`, `status`, `reason` and the counts; the engine reads `scraper`, `run` and `status` and the event's id.

A delivery is skipped (`Skip`, nothing to retry) when it is neither a delivery for candidates nor a judge delivery: an event of another name, one with no id, a `scrape.finished` whose `status` is not `done`, one whose `scraper` the registry does not hold (decision 3), or one with no `run`. It is skipped too when a pass the store holds already carries its event id as its delivery or already names its run as its trigger, whatever became of that pass: redelivery is safe, and a second `scrape.finished` for one run under another event id is the same run (decision 11). That check reads only candidates' own records, so a redelivery is skipped even while scrapes cannot be reached.

Otherwise the delivery reads the run's record from scrapes before it answers (orchestrator ruling): a run scrapes does not know (404, unknown or pruned) or a record whose status is not `done` is skipped. Any other failure of the read, scrapes unavailable, a dead socket, another status, an answer that is not a record, or no scrapes client at all, is a pass that failed: the pass is recorded, failed `scrapes` with its counts 0, `pass.started` and `pass.finished` told, and `OK` answered, so the bus does not retry and the failure is on the record where a person sees it; a later delivery of the same run is skipped as a redelivery, and a full ingest repairs. A record that is read and `done` is recorded as an ingest pass of origin `run`, with the run's id as its trigger and the bus event's id as its delivery, `pass.started` told and `OK` answered, all before the rows are read. The store never refuses an ingest `busy`: the only pass that could block it, an ingest of the same run, is found first and refused as a redelivery, whatever its status, so an ingest runs beside a judge, a full ingest, an enrich of either kind and another run's ingest (site text decisions 15 and 17). Stopping and the database failing answer `Fail`; `Fail` is kept for those two, and the store's `busy`, which an ingest never gets, would be answered `Fail` with `passes.Busy` as a judge delivery's is (see the recorded decision on the second delivery).

### A judge delivery

A `cron.judge_candidates.fired` with an event id is a judge delivery, whatever its attributes. It reads nothing from scrapes, so it needs no scrapes client. It is skipped when a pass the store holds already carries its event id as its delivery: the redelivery check asks the store with the event id and no run, since a cron slug fires many times and only the event id names one fire. Otherwise the pass is recorded with kind `judge`, origin `cron`, trigger `judge_candidates` (`store.TriggerJudge`) and the bus event's id as its delivery, `pass.started` told and `OK` answered once it is recorded, the judging left to the background. The store lets one trigger stand on many judge passes; only a run id is unique as a trigger (`D04-store`). A judge fired while an ingest or a full ingest runs now runs beside it (site text decision 17). Only while another judge runs does the delivery answer `Fail` with `passes.Busy`, and the bus retries: a judge takes seconds, so the fire is not lost. Stopping and the database failing answer `Fail`.

A pass a delivery started is started as the delivery: its request id is the delivery's, and its user is whatever user the delivery's request named, which is none; the starter shown is what the trigger says, scrapes and the run for an ingest pass (decision 11) and the cron slug for a judge pass, as scrapes' run started by a cron fire shows `cron` and its slug.

### A campaign delivery

campaigns emits an event each time a business is added to a campaign, rejected in one or sent a piece (campaigns decision 16), told as the tool call's caller. candidates keeps from them, per business, which campaigns it has been in, when it was added, whether and why it was rejected there, and when a piece was last delivered (campaigns decision 17), so the `candidate` tool and page show it (`D10-tools`, `D08-pages`) and a prospect list can leave out a business used lately (campaigns decision 18, `D14-prospect-lists`). Every payload value is a string and every key is always present (campaigns log D15 and D25): `campaign.member.added` carries `campaign`, `candidate` and `prospect_list`, the prospect list empty when the business was added one at a time; `campaign.member.rejected` carries `campaign`, `candidate` and `reason`; `campaign.piece.delivered` carries `campaign`, `candidate`, `piece`, `channel` and `how`, of which candidates reads only `campaign` and `candidate`. The time recorded is the bus event's own `Time`, when campaigns told it, not when the bus delivered it.

`DeliverCampaign` makes one write to the store per delivery, chosen by the event's name: an added is `AddCampaignUse` with the payload's candidate, campaign and prospect list, a rejected `RejectCampaignUse` with its candidate, campaign and reason, a delivered `DeliverCampaignUse` with its candidate and campaign, each at the event's `Time` (`D04-store`). The store follows the merge pointer from the candidate named to the candidate at the end of the chain and records there, so a use told of a candidate since merged lands on its survivor (campaigns log D1). The outcome is `OK` when the store answered nil, whether or not the write changed anything; `Skip` when the payload's `campaign` or `candidate` is empty or missing, when the event's `Time` is the zero `time.Time`, which the store refuses as `ErrUnreachable` (`D04-store`), or when the payload names a candidate the store does not hold (`ErrNotFound`), since a retry would find the same; and `Fail`, so the bus retries, once the drain has begun (`passes.Stopping`) and on any other error the store answers, `store.Unreachable` when the database fails. An event of another name handed to it directly is skipped; `Handlers` hands it only its three.

A campaign delivery records no pass and tells no event: it is one write that ends before the answer, with nothing left to do in the background, campaigns records its own trail of the add, the reject or the delivery, and appkit's request pair records the delivery itself (`D09-trail`). It reads nothing from scrapes or prompts and calls no sibling, so it needs no scrapes client and no service identity, and the caller the delivery's request named, which is none, is not used. It is not deduplicated by event id: the store's writes make it safe to repeat. A repeat changes nothing, an add keeping the earliest time and its prospect list, a reject the first, a delivery the latest, so a redelivery, a retry after a lost answer and a delivered or rejected told before its added all leave the uses as one delivery of each, in order, would. A campaign's reject marks the business rejected in that campaign alone; a prospect list's rejects are candidates' own, and the delivery leaves them, and the candidate's status, as they were (campaigns log D4, campaigns decision 5).

## Identity on the read

scrapes' read path requires an identity, and appkit's `scrapes` client forwards the caller on the call's context. A pass an `ingest` started reads scrapes as its caller: the request carries the caller's user id, email and request id, as every sibling call forwards the caller. A delivery carries no person, so every read an ingest delivery makes, its record read and its pass's rows, is made as the **service identity** (decision 12): `X-User-Id` `candidates`, no `X-User-Email`, and the delivery's request id, with the delivered bus event as the cause of the pass's events. scrapes trusts any process at its socket, so the read is answered and its trail names `candidates` as the user (decision 21). It is the suite's first service-to-service call made as no person, and recorded as such below. A judge delivery makes no read at all.

prompts is reached only by an `enrich_target` of a prompts kind, and always as the caller of the `enrich`: the check of the prompt at the call and every show, run and result request of the work carry the caller's user id, email and request id, as every sibling call forwards the caller, so the prompt run is the caller's own and prompts refuses one they do not have (site text decision 7). appkit's client records each request as `sibling.called` with the target `prompts` (`D09-trail`); the engine records nothing of its own for it.

## The work

A pass's work runs in a goroutine and is cancelled by the drain and by nothing else: the call or delivery that started it may end while it runs. Its runs are, for an ingest pass, the run the record named; for a full ingest, each registered scraper's current run (`fmcsa`, `ppp`, `form5500`, then `osha_ita`), read with `Current` in the registry's order, a scraper with no current run (scrapes answers 404) contributing no rows and marking nothing gone; and for a judge pass, none. For each run the work streams the rows (`Rows`) and has the source the registry holds for the run's scraper read each one (`D05-sources`), handing the store a batch of `passes.BatchSize` observations at a time, as they arrive, so a run of any size passes through with one batch held (decision 1). Once a run's stream has ended, and the number of rows it handed equals the record's `rows`, the links of that scraper the run no longer holds are marked gone. A full ingest treats every row as changed, so normalized forms, keys and readings are recomputed while candidates, their ids and the rulings stay (decision 11). Rulings are applied throughout, by the store (`D12-ingest`).

An ingest pass stops there: it writes links and the candidates' display, and no estimate or judgments; a candidate it creates has none until a judge, and a candidate whose rows it changed keeps the judgment the last judge wrote. A full ingest, after its runs, walks each derived kind in registry order with `store.Derive` forced, a window of `passes.BatchSize` candidates by id at a time, so every active candidate gets a fresh result of each derived kind whose inputs are not empty, due or not, and its facts row with it; it fetches nothing. Every active candidate holds a link, so the forced walk of `link_facts` records a result for each and rewrites each one's facts row to the projection `D04-store` defines, whether or not its link facts changed: after a deploy that changes the projection or a source's reading, a full ingest brings every facts row to the new rules before its judge reads them (category evidence decisions 1 and 12). A judge pass and, after that, a full ingest call `JudgeAll` once: every active candidate's estimates and judgments are rewritten from every link not gone, from every source, and from its facts row, measured at one time the store's clock reads, the judge's date (`D13-judging`). So a filing's `fmcsa_active` weight is the one it had on the day of the last judge, and between judges nothing decays. A judge started by an enrich is a judge pass like the cron's.

An enrich pass walks its kinds in registry order: the one kind the call named, or every kind but one run through prompts and a fetched one whose fetcher is not ready. Every derived kind is walked before the first fetch, so the derived facts are in place while the hour of fetching runs. A derived kind is walked with `store.Derive` not forced, a window of `passes.BatchSize` candidates by id at a time, each call recording a result for each candidate in its window that is due and writing its facts row in the same write; the count `derived` sums what the calls recorded. The fetched kind is the website check's (`D15-website-check`): it selects the due candidates in keyset batches of `passes.BatchSize` by candidate id, one batch held at a time, hands each batch's domains not yet checked in the pass to the fetcher, and never selects one candidate twice within a pass, so a domain whose fetch failed is not retried until the next pass. An enrich has no runs, makes no request to scrapes, and writes only results and facts rows, never a candidate, link, estimate or judgments. Fetching nothing is not a failure: a domain that answers nothing is a `none` result, recorded and counted, which decides no website and leaves a company no search has answered `unknown` (`D04-store`, website states outcome 2). An enrich over a corpus whose inputs have not changed since the last records nothing, its counts all 0, and starts no judge.

An `enrich_target` walks its one kind over its targets, which it selects once, when it begins: each target that is active, whose inputs for the kind are not empty and that, without `force`, is due for it (site text decision 13). The rule is the same for every kind. A derived kind is recorded for the selected targets in one `store.DeriveAmong` call, a fresh result for each when forced, as a full ingest records one, and its count is `derived`. The website kind selects with `store.DueAmong` and checks each selected domain once, at the checker's pace, with the counts `D15-website-check` gives an enrich pass. So `website_check` over a prospect list without `force` checks only the members whose domain changed, likely none, and the record says so with `due` 0; with `force` it checks every member once and each domain once.

A prompts kind, `website_search`, `site_text` or `brief`, starts one prompts run per selected target, with the input the kind gives for the candidate's subject (`D16-enrichers`): for `website_search` what tells the company from a namesake, its name, town, street, ZIP and phone, the domain of its email and what the check found there, its people and its categories (website search decision 3); for `site_text` its `candidate`, `name`, `city`, `state` and `website`; for `brief` `Brief.Input`, those beside its facts and its pages (brief decision 4); keeping at most `RunsInFlight` runs going and starting the next as soon as one ends. A run is started once prompts accepts it. When prompts refuses a start, which is how it answers a full queue, the work waits `QueueWait` on `Config.After`, asks for the prompt again, so a prompt deleted meanwhile ends the work rather than looping, and tries again, at most `StartTries` starts per target. It learns that a run ended only by asking prompts for its result, each time a wait of `PollInterval` on `Config.After` ends, and by no other means; a run that is queued or running is asked again at the next interval, for as long as it takes: prompts' own bound on a run, `PROMPT_SECONDS`, is the only time limit (site text decision 8). When a run has ended, however it ended (`exited` with any exit code, `failed`, `killed`, `timed_out` or any status prompts adds), the pass records the kind's result for the target, unless the kind's `Valid` rejects it, which is a failure of prompts: the run's id, its ending and the cost prompts reports, for `site_text` the number of distinct URLs the company then holds, for `brief` the summary, categories and labels the run's standard output gives, for `website_search` the agent's answer and the confirmation of the URL it names, and the result's cost in dollars (`D16-enrichers`). The confirmation is made while the result is recorded: when a `website_search` run exited cleanly and its answer names a URL, the kind's `Found` fetches it once through the checker, as `add_page` does (`D15-website-check`), the fetch waiting `website.Timeout` on the checker's `After` and ended by the drain, and the result holds what the fetch found; a run that did not exit cleanly is not confirmed, and an empty URL or a site that did not load is an answer, not a failure (website search decisions 5 and 6). A failed run is a result (site text decision 9, brief decision 6, website search decision 6): the company is not due again, the failure shows on the candidate page, the pages the agent added stay, and the owner redoes it with `force`. The pages themselves are added by the agent through `add_page` while the run goes on, never by the pass; a `site_text` pass counts the copies the company gained during each run, and a `brief` or `website_search` pass, whose runs keep none, counts none (brief decision 10, website search decision 1). A `website_search` result moves the facts row the store rewrites beside it (`D04-store`): a confirmed site becomes the company's website, decided by the search, which makes it due for site text (website search decisions 7 and 8); a search that is not failed and named no URL, or named one that did not load, makes the website `none`, with the agent's why, unless the newest check found a site or a confirmed search exists; and a failed search leaves the website as it was (website states outcomes 1 and 3).

`drive_route` selects its targets with `store.DueAmong` as the website kind does: a member with no street, or a space with no origin, has empty inputs and is never selected, so the ZIP estimate stands for it; without `force` a member whose newest route result has its current address and origin is not due, so a repeat over the same prospect list makes no request; with `force` every member with a street is routed again (drive route decision 3). For each selected target the work reads its subject, asks the kind's `Route` for the drive, and records the one result it answers with the inputs selected, keeping at most `RoutesInFlight` targets routing at once and starting the next as soon as one is recorded; a **request to the routing service** is a request the routing client hands its own `*http.Client`, a different thing from a fetch, which the website checker makes, though in production both ride `Process.HTTP`. Each routing waits `routes.Timeout` per request on the client's `After` and is ended by the drain. Every answer is a result, nothing routable and a failed request included (drive route decisions 1 and 5): a failed result leaves the company not due, shows failed on the candidate page and is redone with `force`, and the pass goes on and ends `done`. A routing the drain cut records nothing, so its company is due again. No other pass makes a request to the routing service: not an enrich of every kind, not the ingest's follow-on, not a full ingest, not a judge, not an `enrich_target` of another kind.

The pass then finishes `done` with its nineteen counts: `rows` the rows streamed, and the rest the sums of what the store's writes answered (`new`, `changed`, `unchanged`, `created`, `linked` from the batches, `gone` from the marking, `judged` and `unranged` from `JudgeAll`, 0 for an ingest pass, `derived` from the `Derive` calls of an enrich or a full ingest and the `DeriveAmong` call of an `enrich_target`, 0 for every other kind), for an enrich that walked the website kind and an `enrich_target` of it `due`, `fetched`, `https`, `http` and `none` as `D15-website-check` pins them, for an `enrich_target` of a prompts kind `due` the targets selected, `runs` the runs started, `runs_failed` those whose result the kind's `Failed` says failed (for `site_text` an ending other than `exited` with exit code 0; for `brief` that, or an empty summary or a standard output that does not decode, brief decision 6; for `website_search` that, or a standard output that does not decode as the answer, website search decision 6), `pages` for `site_text` the page copies the targets gained during their runs and for `brief` and `website_search` 0, and `cost` the runs' cost in nano-dollars; for an `enrich_target` of `drive_route` `due` the targets selected, `runs` the requests to the routing service made, `runs_failed` those that failed and `cost` what the requests the service answered cost in nano-dollars, each summed from the `enrichers.Tally` its routings answered, and `pages` 0; and 0 for every other pass. What each counts is the owning document's.

## Cost

A pass costs in proportion to its rows (orchestrator ruling). A pass over the real FMCSA run of 16,706 rows never finished: 1,970 rows took 82 seconds and a re-scrape with every row unchanged four minutes, the pages timing out meanwhile, because every batch reloaded and compared the whole database and every row re-derived every candidate. Now each batch is one write transaction touching its own rows and the candidates they attach to, by key (`D04-store`); an unchanged row costs a lookup, a touch of its last seen, and its share of its candidate's display re-derived once per batch; and the gone-marking is one bounded statement per `MarkGone` call, over that call's scraper's links last seen in a run other than that call's run, after which the display of each candidate it touched is re-derived by key from that candidate's own links. An ingest pass judges nothing, so its cost is its rows alone. A judge covers every active candidate by definition, from each candidate's record, its own links and rulings, and its facts row: a full judge of the 16,580 candidates on `us` took 18 seconds. A pass's work holds no lock of the engine's while it calls the store, and a read of the store answers while a batch is being written (`D04-store`), so the pages and the tools answer throughout.

What is required is the time: a delivery of a **generated run** of 10,000 rows into an empty store, a second delivery of a run alike to it with every row unchanged, and a full ingest over that run, which judges its 5,000 candidates, each finish `done` within 120 seconds, under the race detector the gate runs, with the counts the attach rule gives. The work the pass asks of scrapes is counted too: one rows read per run (R-ONN0-GDTS). Each of the three passes is timed with every pass the engine started before it ended, the ingests' follow-on enrich and judge included, so that each pass is measured alone; the full ingest's 120 seconds hold its derived step, two results for each of the 5,000 candidates, as well as its judge.

A pass ends `failed` with one reason (decision 11):

- `interrupted`: the drain cancelled the work before it ended, whatever else then failed;
- `store`: a write the work handed the store failed, `JudgeAll` and `Derive` included; for an enrich of either kind, any call of the store failed, a read of the due set included;
- `prompts`: for an `enrich_target`, any failure of prompts in the work (a `drive_route` pass has none: every answer of the routing service, a failed request included, is a result): the prompt asked for again before a retried start refused or not answered, a start that fails other than by a refusal, the `StartTries`-th start of one target refused, a run's ending that the kind's `Valid` rejects (an empty status or a negative cost), or a result request that fails or is refused (an unknown run reads the same as an unreadable one, and a run whose ending cannot be read cannot be recorded);
- `scrapes`: any other failure, which neither enrich kind, reading nothing from scrapes, ever has: a read of scrapes that failed or answered something that is not a record or a row, a current run not `done`, or a stream whose row count disagrees with its record's `rows`, a stream cut short at a line boundary being told this way (appkit's `scrapes` client leaves that check to its caller).

A failed pass keeps its record and its counts at 0 and leaves in place every batch it had already handed the store; the next pass or a full ingest repairs them, since every write is idempotent. A stream that failed marks nothing gone, so a short read never takes evidence away. A judge that fails leaves the judgments as `JudgeAll` left them (`D13-judging`); its delivery was already answered, so the next day's fire, or a full ingest, judges again. An `enrich_target` that fails keeps every result it recorded and abandons its runs in flight: the client offers no cancel, prompts ends them under `PROMPT_SECONDS`, and the pages their agents add still land; the targets it did not finish are due again at the next pass. `pass.finished` is told once the ending is recorded; an ending the store cannot record tells no event and leaves the pass `running` for the next start to settle, as scrapes leaves a run.

## Starting and stopping

`Recover` runs at start, before ready (`D03-serve`): every pass still `running` was cut off by a dead process and is failed `interrupted`, its `pass.finished` told as its starter with no cause. A running enrich of either kind is settled so too, as every kind is; the next enrich finds what is still due. `Drain` is the stop: from its call `Ingest`, `Enrich` and `EnrichTarget` refuse `stopping`, `Deliver` and `DeliverCampaign` answer `Fail` and no pass starts a follow-on, and a call already under way that has not recorded its pass records none; every running work is cancelled at once, its read of scrapes, its fetches, a website search's confirmation included, its requests to prompts, its requests to the routing service and its waits ended, and its pass failed `interrupted` (decision 11), a `drive_route` pass recording nothing for the routings it cut. A drained `enrich_target`'s runs are abandoned as a failed one's are, and a run whose confirmation the drain cut records nothing, so its company is due again. `Drain` returns once every pass the engine started has ended, or when its context ends, which `D03-serve` sets to the drain deadline, `DRAIN_SECONDS` after the signal.

## The sweep

Once before ready, after `Recover`, and then each time a wait of `cli.SweepInterval` on `Process.After` ends, the passes past keeping are pruned with `store.PrunePasses` and `CANDIDATES_KEEP_PASSES`: the newest that many `done` passes are kept and, separately, the newest that many `failed` passes, so a page still shows what went wrong; a `running` pass is never pruned (decision 16). A pruned pass is gone from the tools and the pages; candidates, links, estimates, judgments and rulings are never pruned. A prune that fails is silent and tried again at the next interval. The website check waits on the same `Process.After`, with its own durations (`D15-website-check`), during a pass, during an `add_page` call's one fetch and during a website search's confirmation, which waits `website.Timeout` while an `enrich_target` runs; the routing client waits `routes.Timeout` on the same `Process.After` for each request of a `drive_route` pass (`D17-drive-route`), a duration equal to `website.Timeout`, so a test tells those two waits apart by the pass it runs, not by the duration; the engine's own waits, the result poll's `PollInterval` and the queue-full `QueueWait`, end on `Config.After`, which `cli.Run` sets to the same `Process.After` and which, nil, is `time.After`; only a wait of `cli.SweepInterval` prunes.

## The pass record

The record the tools answer is `passes.Record`, made from a stored pass by `passes.RecordOf`: `id`, `kind`, `origin`, `trigger`, `target` and `enrich_kind` when not empty, which is for an `enrich_target` alone, `status`, `reason` when failed, `started`, `finished` once ended, the nineteen counts, the fifteen with `judged` where `judged` stood, `derived` after `unranged` and the five website counts after it, then `runs`, `runs_failed`, `pages` and `cost`, always present as every count is, and the starter: `user` and `email` for a pass of origin `ingest` or `enrich`, an `enrich_target` included, nothing for a delivery, whose trigger names the run or the cron slug, or for a follow-on, whose trigger names its starter. The delivery and the request id are not part of it. The record is a tool's and a page's answer, not a persisted event payload, so it renames `judged` to `judged` at once; the pass events keep `judged` beside `judged` for one release (`D07-events`). The members it adds are added keys only (site text decision 14).

## Refusals and failures

A refusal is a `*passes.Refusal`, a word and, rarely, a text. All of candidates' refusal words are declared in `internal/passes` (`D01-layout-and-run-seam`), so the tools tell every refusal apart with one `errors.As` (`D10-tools`): `not_found`, `invalid`, `busy`, `stopping` and `unavailable` (decision 14). The engine answers `busy`, `stopping` and `unavailable`, `invalid` for a kind given to `Enrich` that the registry does not hold or that runs through prompts, and every refusal of `EnrichTarget`, `not_found` and `invalid` included, since only the store can say whether a target exists or is merged; `not_found` and `invalid` are otherwise the tools' (`D10-tools`), and the database failing reaches them as an error matching `store.ErrUnreachable`, which they answer `unavailable`. A refusal's `Text` is empty but for the missing prompt and the missing Maps key (`passes.NoRouteKey`), whose text the tools answer in place of the word's fixed sentence. A delivery's `Fail` carries a fixed message, a copy constant naming no value: `passes.Stopping` while stopping, `passes.Busy` while a pass of its own kind and scope runs, which for a judge delivery is another judge, `store.Unreachable` when the database fails. A campaign delivery fails with the same `passes.Stopping` and `store.Unreachable` and never `passes.Busy`, since it records no pass.

## Recorded decisions

- **Ingesting and judging are separate passes** (decisions document, Ingest and judge): an ingest pass stores rows and judges nothing; a judge pass judges every active candidate and reads nothing; a full ingest ingests every current run, records every derived kind afresh and then judges, as one pass of kind `ingest`, so its record says what started it and a judge never runs between its ingests. Nothing else computes a judgment but an owner's ruling, which judges what it touches in the same call (`D13-judging`).
- **The judge runs daily, not on change and not on read** (judgments decision 26). The candidates whose `fmcsa_active` weight is moving are those whose filing nobody updated, so their rows never change: 2,431 of the 16,706 active MN and WI carriers are in the two-to-five-year band and 2,663 change weight within 30 days, so judging only the candidates a pass touched would never revisit them. Judging on read would make the first read after a quiet stretch wait for a full judge and put a staleness check on every read path, to save 18 seconds of CPU a day. A daily cron trigger is the pattern the suite already has, and it keeps a stored judgment within a day of true.
- **No pass refreshes** (judgments decision 25): the SQL statement that rewrote every stored ranking number at each pass's end, on failure and at start, and its agreement test with Go, are gone, so the judgment formulas live once, in Go (`D13-judging`). A pass's ending writes only its record, whatever the ending, and `Recover` writes nothing but the endings it settles.
- **A judge delivery is skipped only by its event id**: a cron slug fires many times, so the trigger `judge_candidates` stands on many passes, and the redelivery check asks the store with the event id and no run. A judge delivery needs no scrapes client and reads nothing, so it is recorded even when the services file names no `scrapes` entry.
- **A judge fire during another judge fails `busy`** (as before, rather than skipping): the bus retries for minutes and a judge takes seconds, so the fire runs after the judge and the day's judgment is not lost; a fire whose retries are spent is caught by the next day's. A fire during an ingest or a full ingest is no longer refused (site text decision 17): it runs beside it, reading what the ingest has attached so far, and the next judge corrects the rest.
- **A judge delivery is answered once its pass is recorded**, the judging left to the background as an ingest pass's rows are. That the answer comes before the judge ends is stated here, not required: unlike an ingest, whose first read a fake scrapes can hold, a judge has no seam a permitted test can hold open, and `JudgeAll` over a test's store ends in milliseconds.
- **The service identity on a delivery's reads** (decision 12, binding): `X-User-Id` `candidates`, the service's own name, no email, the delivery's request id. It is the suite's first service-to-service call made as no person. The pass's own starter stays the delivery's caller, as scrapes' delivery-started run keeps the delivery's caller, so the pass's events carry the delivery's request id and no user (`D07-events`) while its reads' `sibling.called` carry `candidates` (`D09-trail`).
- **The record is read before the delivery is answered** (orchestrator ruling, superseding coordinator decision C1): an unknown run or one not `done` is skipped; any other read failure records a pass failed `scrapes` and answers `OK`, so a scrapes outage shows as a failed pass rather than as retries and a paused subscriber, and `Fail` stays reserved for busy, stopping and the database. A delivery with no scrapes client is treated as an unavailable read. The redelivery check comes first and reads only the store, so a retry of a run already passed is skipped without asking scrapes.
- **One busy rule, in the store** (site text decisions 15 and 16, replacing the slots): a pass is refused `busy` only while a pass of the same kind over the same scope is running, the scope being an ingest's run, an `enrich_target`'s target, and the corpus for a judge, a full ingest and an enrich; `AddPass` keeps it (`D04-store`), so two calls racing cannot both win. The slots managed contention SQLite already handles: it serializes writes, so the rule protects no data, only paid or heavy work started twice, two website checks over the corpus, two `site_text` passes over one prospect list, two full ingests. Every other combination runs together: two ingests of different runs, a judge beside an ingest, a full ingest beside an `enrich_target`, a corpus enrich beside an `enrich_target`.
- **The busy scope ignores the kind walked** (site text decision 15 as written): two `enrich_target` passes over one target are `busy` whatever their `enrich_kind`, so a `website_check` and a `site_text` over one prospect list wait for each other though they would not pay twice. A rule that let them run together would need a scope the decisions document does not name; the cost is a second call after the first ends.
- **A candidate target and a prospect list holding it are different scopes**, accepted: an `enrich_target` over one candidate and one over a prospect list holding it may both start the candidate's run of a prompts kind, the one paid twice. Comparing the members of every running target would make the busy rule read prospect lists, and the owner names a candidate alone to redo it, not beside a prospect list pass.
- **The second delivery of the same scrape run** (site text decision 17's "a delivery whose own kind and scope is already running") is the existing redelivery skip: the store holds every pass that names a run as its trigger, whatever its status, so a second `scrape.finished` of a run already running is skipped (`Skip`) by `FindDelivered` and `ErrDelivered` before `AddPass` could answer `busy`, as the sandbox check expects ("skipped as today"); `AddPass` itself answers `ErrDelivered` before `ErrBusy` for a pass naming the run, so even two deliveries racing never see `busy`. `Fail` with `passes.Busy` is then answered only to a judge delivery while a judge runs. That an ingest delivery would answer `ErrBusy` with `Fail` and `passes.Busy` is described, not required: no store a permitted test can build gives an ingest `ErrBusy`, so no test could tell that mapping from another.
- **A scraper with no current run contributes nothing to a full ingest** rather than failing it: the registry may hold a scraper whose first run has not landed, and the full ingest still judges every candidate. A current run that is not `done` fails `scrapes`, since scrapes answers only `done` runs as current.
- **The line count is the stream's check** (decision 2): appkit's client cannot tell a stream cut at a line boundary from a whole one; the pass compares the rows handed with the record's `rows` and fails `scrapes` on a mismatch, before marking anything gone.
- **The batch size, 500, is a constant of the rules version** (decision 17), declared as `passes.BatchSize`; a failed pass keeps every full batch it handed over. Whether a partial last batch of a failed stream is kept is left open: the next pass repairs either way.
- **Precedence of endings**: a work the drain cancelled is `interrupted` whatever then failed; a refused write, or for an enrich of either kind any failed call of the store, is `store`; for an `enrich_target`, any other failure is `prompts`; anything else is `scrapes`. The drain cancels at once, as scrapes' does: the pass cannot be resumed, and the next delivery, enrich or a full ingest repairs it.
- **An ending the store cannot record leaves the pass `running`**, as scrapes leaves a run, for the next start's `Recover` to fail `interrupted`; until then every new pass it blocks is refused as busy, but an ingest of the same run, which is skipped as a redelivery. Retrying the ending is not designed: the database failing is a broken host.
- **No queue**: the busy rule is the whole concurrency rule, and the bus's retries are the queue for a judge fire during a judge. An ingest that ends while a corpus enrich runs starts nothing and records nothing (website log P8): the running enrich re-reads the due set per batch and window, and the next ingest or an `enrich` call covers what it did not select. An `enrich` or `enrich_target` refused `busy` is the caller's to call again.
- **Origins `enrich` and `pass`** (website log A1): `enrich` mirrors `ingest`, the tool naming itself; `pass` with the starter's id as trigger says which pass led to which.
- **A follow-on carries no person**: no one asked for it, so it has no user; it keeps its starter's request id and event cause, the honest provenance and the one a delivery's pass already has.
- **"At least one new result" is at least one derived or website result written** (enrichers decision 10, site text decision 10): every such result an enrich of either kind writes is a new row (`D04-store`), and its `derived`, `https`, `http` and `none` sum to them, so the rule reads off the pass's own counts. A pass that wrote none starts no judge: nothing a judge reads changed. A pass of a prompts kind writes none, so it starts no judge without the engine testing its kind. A good brief's categories, when it gives any, become the facts row's categories (`D04-store`, category evidence decision 1), yet no judge follows (brief decision 9): the readers answer judgments's facts from the facts row at the read (`D13-judging`), so a prospect list's filter sees them at once, and the stored copy is refreshed by the next daily judge. A website search follows the same rule (website search decision 12): a confirmed site becomes the facts row's website, decided by the search (`D04-store`), so the `website` filter admits it at the read, and a search that found nothing makes the row's website `none` when the newest check found no site and no confirmed search exists, which the filter reads at once too (website states outcome 3), yet the judge counts no searched site as operating evidence and no `none` against a company (`D13-judging`), so there is nothing for a judge to do. The change that makes a prompts kind's result move an opinion adds that kind's count to the sum.
- **An enrich's judge is refused only by a running judge** (site text decision 17): the daily judge picks the results up, so nothing is lost. A judge running beside an ingest or a full ingest is accepted (site text decision 16), and an enrich recorded after this one ended and before its judge is recorded does not stop the judge; an enrich writes only results and facts rows, and the judge's guarantees already exclude any `AddEnrichments`, `Derive` or `DeriveAmong` made during it; the next judge reads the later facts.
- **An enrich of either kind fails `store` on any store failure**, a read included, where the other kinds fail `store` only on a refused write: a corpus enrich has no other failing sibling, a failed fetch being a `none` result, so `scrapes` would mislead; an `enrich_target` of a prompts kind has one, and fails `prompts` for it.
- **`Enrich` and `EnrichTarget` refuse what the tool refuses** (site text decisions 6 and 12): a kind the registry does not hold, and for `Enrich` a prompts kind, for `EnrichTarget` an empty kind, so the engine's contract does not lean on its caller. There is no age: a candidate is due by its inputs alone (enrichers decision 3), and `older_than_days` fails the tool's schema like any unknown argument, so it never reaches the engine.
- **A targeted enrich names its kind** (orchestrator ruling): an `enrich_target` walks exactly one kind, its `enrich_kind`, so its record and its counts say what it did; a kindless target would run every kind, a prompts kind included, over a prospect list, which no decision asks for.
- **A kindless corpus enrich, and the ingest's follow-on, leave out every prompts kind** (orchestrator ruling, from site text decisions 6 and 12): site text decision 12 leaves an untargeted enrich as release-44 left it, and a corpus walk of `website_search`, `site_text` or `brief` would be the paid runs site text decision 6 forbids (brief decision 10; website search decision 1, which requires a target, and its rejection of a search over the whole corpus). Only a targeted enrich runs a prompts kind.
- **A merged candidate as a target is `invalid`**, as a reject of one is (`D14-prospect-lists`): it has no facts and no due results, so a pass over it would do nothing and say nothing.
- **The targets are fixed at the call**: the prospect list's members as `ReadProspectList` answers them while the call runs, so the pass's `due` and `runs` describe the prospect list the caller saw; a member that joins later waits for the next call, and one that leaves is still worked.
- **`unavailable` only for a named kind that is not ready**: with no checker an enrich of every kind still walks the derived kinds, so a space without a checker still gets its link and drive facts, and the ingest's follow-on enrich runs whatever `Config.Website` is (enrichers decision 9); an `EnrichTarget` of a prompts kind with no prompts client is `unavailable` (site text decision 21), as one of `website_check` without a checker is, and so is one of `website_search` without a checker (S 1): the kind's `Ready` asks for both, and the existing rule refuses a `Prompter` that is not ready before any request to prompts.
- **Derived kinds before fetched ones** (enrichers decision 8): derived results take seconds and fetches an hour, so the derived facts land first, and a follow-on judge after the pass reads both. The registry's order puts them first; the engine does not reorder it.
- **The kind asked for is stored only on a targeted pass** (site text decision 14): an `enrich_target` records its `target` and `enrich_kind`, which its page and record show; a corpus enrich stores neither, its counts saying what was done, as the old age override was not stored.
- **The busy rule protects no data** (site text decision 16, generalizing enrichers decision 11): a pass reading a candidate another pass is writing records what it read. An enrich beside an ingest may derive a candidate's link facts while the ingest is between two batches touching it; its result records the inputs it read, so the ingest's own follow-on enrich finds the inputs changed and derives again. A judge beside an ingest judges what was attached so far, and the next judge corrects it; a full ingest beside an ingest redoes one run's rows. This is accepted, not prevented: preventing it would need passes to wait for each other, which the rule exists to avoid.
- **A full ingest derives forced, never fetches** (enrichers decision 9): a full ingest is the repair every failure points to and the way a new ZIP table or a new derivation reaches every candidate, so it records a fresh derived result for every candidate whatever its inputs; a fetch is an hour of outside requests, which a repair should not start.
- **A full ingest re-projects every facts row through its forced walks** (category evidence decisions 1 and 12; orchestrator ruling): the full ingest, after its forced derived walks and before its `JudgeAll`, leaves every active candidate's facts row equal to its projection, whether or not its link facts changed, so a projection rule that changes in a release, such as a good brief's categories standing alone, or a check's `none` reading `unknown` (website states outcome 2), reaches the candidates whose records did not move, and the judge's copy of the categories, which a prospect list's filter reads, is taken from the re-projected rows. No store call is added: the inputs of `link_facts` are empty only for a candidate with no link at all, and no active candidate has none (a split refuses to take every link, `D12-ingest`), so the forced walk of `link_facts` records a result for every active candidate and each `Derive` call rewrites the facts row of each candidate it records (`D04-store`). No migration and no start-up pass do it: until the owner runs `ingest` after a deploy, a row no write has touched since keeps what the previous release projected, and an enrich or an `enrich_target` rewrites only the rows of the candidates it records a result for. The previous release, run on this schema after a rollback, writes its own projection again for each candidate it re-projects, which is accepted (category evidence decision 11).
