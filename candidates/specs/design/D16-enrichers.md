# D16-enrichers

The enrichers: the kinds of enrichment candidates keeps, each a kind word with a rule naming a candidate's inputs and a rule computing a result from them, held in one fixed registry the enrich pass walks without knowing any kind in particular (enrichers decisions document, decisions 1 and 2). The site text decisions document adds a fourth kind, `site_text`, the first whose result is a run of a prompt kept in the prompts service (its decisions 5 to 9). This document owns the package `internal/enrichers` whole: the kind words and source words, the **subject** an enricher reads of a candidate, the result and the found shapes, the `Enricher`, `Deriver`, `Fetcher` and `Prompter` interfaces, the four enrichers `drive_minutes`, `link_facts`, `website_check` and `site_text`, what each names as its inputs and, for the two derived kinds, what each computes, for `site_text` the prompt it names, the input object of a run and the result recording one, which found values each accepts, and the registry with what it is built from. The records, the due read, the derived walk, the facts row and the reads of results are `D04-store`'s (`store.Enrichment`, `DueEnrichments`, `Derive`, `AddEnrichments`, `GetFacts`, `FillFacts`); the enrich pass, the rebuild, their counts and follow-ons are `D06-passes`'; what the website check fetches, how, and what its `Ready` and `Fetch` do are `D15-website-check`'s; the targeted enrich pass that runs `site_text`, asking the prompts service for the prompt, starting runs, waiting on them and counting the pages they add, is `D06-passes`'; the pages themselves are `D04-store`'s; merge and split re-running the derived kinds are `D12-resolution`'s; what a judge makes of the facts is `D13-scoring`'s; the `enrich` tool is `D10-tools`'.

## Fetched and derived

An enricher is one kind. A kind is **fetched** when it reaches outside the service and may cost money, and **derived** when it reads only what the service holds (decision 1). The distinction is the enricher's `Fetched`. A derived kind is a `Deriver`, whose `Derive` computes a result from the subject alone, so the store can run it inside its own writes. A fetched kind is one of two things. A `Fetcher`, the website check, computes many inputs at a pace of its own through `Fetch`, one result per distinct inputs. A `Prompter`, `site_text`, is one run of a prompt per candidate: it names the prompt, builds the run's input object from the subject and turns the run's outcome into a result, and the pass does the running (`D06-passes`). Both have a `Ready` saying whether they have anything to fetch with. A rebuild treats every derived kind as due for every candidate and never a fetched one (`D06-passes`); a merge or split re-runs the derived kinds for what it touched (`D12-resolution`). Every enricher is exactly one of the three.

Four kinds are registered in this release, in this order, which is the order the enrich pass walks them: `drive_minutes` and `link_facts`, derived, then `website_check` and `site_text`, fetched (decision 8 of the enrichers document: derived kinds first, since they finish in seconds and the fetched kinds can take hours; site text decision 5: `site_text` after `website_check`). It is no longer kind name order, since `site_text` sorts before `website_check` (recorded decision below). `enrichers.Kinds()` lists them. An enrich with no target never walks a `Prompter` kind, and `site_text` runs only over a cohort or one candidate (site text decision 6; `D06-passes`).

## Inputs and due

Every kind names a candidate's **inputs** as one string: the display ZIP for `drive_minutes`, the link fingerprint for `link_facts`, the checked domain (`website.Domain` of the display email, `D15-website-check`) for `website_check`, and the website URL the facts row holds for `site_text`. Every result records the inputs it was computed from (`store.Enrichment.Inputs`, `D04-store`). A candidate is due for a kind when it has no result of that kind, or its newest result's inputs differ from the inputs named now; there are no refresh ages (decision 3). Empty inputs mean not due and no result: no ZIP, no own domain, no link at all, no website.

The inputs are computed from the candidate's **subject**, the one value an enricher reads: the candidate's id, display name, city, state, email and ZIP, the website URL its facts row holds (the URL the newest website check landed on, `D04-store`), the ZIP table's minutes for that ZIP, and every link with its scraper, source id, whether it is gone and the source's reading of it, in the order `store.Links` answers (`D12-resolution`: not gone first, then newest filing date, then newest last seen). The subject is built by the store, which holds all of it; the enrichers never read the store, so they are pure functions a test drives with subjects it builds.

## drive_minutes

The inputs are the display ZIP, and the result is the minutes the ZIP table holds for it (decision 2), as `{"minutes":84}`, with source word `zip_drive` and cost 0. When the table lacks the ZIP, or holds a negative value for it, the minutes are unknown and the result is still written, as `{}`: a candidate whose ZIP moves from a known one to an unknown one must lose its stale minutes, and a result keeps it from being due on every pass forever (recorded decision below).

## link_facts

The result is the facts a judge derived from links before this release (decision 2), computed now once, when the links change, over the links not gone: **known since**, the earliest date any shows the business existing; the **newest filing**; the **government match**, the first pattern a link's name matched, in link order; the **categories**, each a link's category with the scraper that gave it, and beside them one from the government match with the source word `name`: `education` when the match is `SCHOOL DISTRICT` or `UNIVERSITY`, `government` for every other pattern (categories document, decision 3); and the **fleet verdict** with the **power units** and **drivers**, from the first FMCSA link, which in link order is the freshest. A date whose UTC year is outside 0 to 9999, a category from a link with no scraper and a verdict outside the three are absent or unknown, never copied (recorded decision below). The rules are `D13-scoring`'s of before, moved here unchanged but for the category from the government match, and so are their examples but for two, whose categories now hold that category; the categories are sorted by name, then source, and kept once each, which puts `government` from `name` before `trucking and logistics` from `fmcsa`, and keeps `government` from `name` beside `government` from `ppp` since the source differs; the result's source word is `links` and the cost 0. Link facts are one kind, not five, because they share one input and are always recomputed together.

## The fleet verdict

The fleet verdict is `pass`, `fail` or `unknown` (`sources.FleetPass`, `sources.FleetFail`, `sources.FleetUnknown`). Each FMCSA row already says which, on its reading (`D05-sources`). `link_facts` copies the verdict of the candidate's first FMCSA link not gone, `unknown` when it is not one of the three, and that link's power units and drivers beside it; with no such link the verdict is unknown and both counts are absent. Only FMCSA counts trucks, so a candidate known only from PPP is unknown, never fail, whatever its readings say; a link stored by an earlier release decodes with an empty verdict and gives `unknown`, never a guess from its old fleet boolean. A negative count on that link's reading is absent, as if the reading lacked it. Power units and drivers come from the same link as the verdict, so they never disagree.

## The link fingerprint

The inputs of `link_facts` are a fingerprint of every link of the candidate, gone ones included: the SHA-256, in lowercase hexadecimal, of one line per link holding its source key, whether it is gone and its reading as JSON, the lines sorted. Sorting makes the order of the links irrelevant; including the gone flag makes a link going gone change the inputs, so the facts drop it. The inputs are empty only when the candidate has no link at all.

## website_check

The website check is `D15-website-check`'s; here it is one enricher among four. Its inputs are the checked domain, its source word is that domain too, and its found value is the JSON of a `website.Result`. `Ready` is whether it holds a checker, so an enrich pass with no checker still runs the derived kinds; `Fetch` checks each domain once through the checker's `CheckAll` (`D15-website-check`).

## site_text

`site_text` records that the owner's prompt was run for a company (site text decision 5). Its inputs are the website URL the subject carries, exactly as the facts row holds it, so a company is due when it has no result yet or a new website check landed on another URL, and a company with no website is never due. Its source word is `prompts`. Its prompt is named after the kind, `_` made `-`, by `PromptName`: `site-text` (decision 7); the prompt itself, its model, instructions and tools, are the prompts service's, and candidates knows none of them. A run's input object holds the candidate's id, name, city, state and website URL, each always present (decision 8). `Ready` is whether it holds a prompts client, so a registry built without one still holds the kind, and an `enrich` of it is refused `unavailable` (decision 21; `D06-passes`, `D10-tools`).

Its found value records the run: the prompts run id, the status it ended with and its exit code when it has one, the number of distinct page URLs the company held when the run ended, and the cost in nano-dollars as prompts reports it; the result's cost is the same in dollars. `Found` copies these from the run's outcome (appkit's `prompts.Outcome`, D27 of appkit) and the count the pass gives it. The pages themselves are read off the company, never off the result. A run that ended `failed`, `killed` or `timed_out`, or exited with any code but 0, is still a result (decision 9), and `Failed` is the one rule for which those are: the pass counts its failed runs by it and the candidate page marks a failed result by it.

## What a result holds

A result is the source word, the found value, JSON shaped by its kind, and the cost; the store adds the candidate, the kind, the inputs and the time (decision 4). `AddEnrichments` asks the registry whether a found value is valid for its kind instead of checking that the kind is `website_check` (`D04-store`). Every found value a `Derive` returns is valid for its kind, for every subject: `Derive` normalizes what it reads rather than copying a value its kind's `Valid` refuses. A negative minutes or count is absent; a time whose UTC year falls outside 0 to 9999, which `time.Parse` with `2006-01-02` cannot read back, is absent like a zero one; a category from a link whose scraper is empty is left out; and a fleet verdict other than `pass`, `fail` and `unknown` is `unknown`.

Release-43 decodes every row of a candidate's enrichments into its own `store.Enrichment`, whose fields are `Candidate`, `Kind`, `State`, `URL`, `Title`, `StatusCode`, `Size`, `Error`, `Source`, `Cost` and `At`, matching member names without regard to case. So the website found value keeps the Go member names release-43 reads, and the derived found values use snake_case members none of which equals one of those names, so a rolled-back release-43 decodes a derived row into an empty website result and never fails on it.

## Known limits

- **A tie reordered by last seen alone is not seen.** `store.Links` breaks filing-date ties by last seen, and the fingerprint leaves last seen out, so two FMCSA links filed the same day that swap places only because one was seen again do not make `link_facts` due, and the fleet verdict may stay the other link's until something else changes. A rebuild recomputes every derived kind and puts it right.

## Recorded decisions

- **The registry is fixed and built by `New` from a `Config`** (sheet 0.1), in the order `drive_minutes`, `link_facts`, `website_check`, `site_text`. Unlike `sources`, nothing forces an injected list: no import cycle, and the only runtime parts are the checker and the prompts client, which the `Config` carries. `New` took the checker alone before; a struct now, because the later kinds the site text document names (the brief, website search, exact drive time) each bring a client of their own, and a struct stops the signature changing with each.
- **Registry order is no longer kind name order.** `site_text` sorts before `website_check`, but decision 5 puts it after, and the fetched kinds come last because they are slow. Nothing depended on the two orders being equal: the facts row's written times are sorted by kind themselves (`D04-store`).
- **A fetched kind that is not a `Fetcher`.** The enrichers document made every fetched kind a `Fetcher`, and the site text document asked for one whose `Fetch` runs prompts. `Fetch` is handed inputs strings and answers one result per distinct inputs; a prompts run needs the candidate's id, name, city and state as well, and runs once per candidate, not once per website. So `site_text` is a `Prompter`: it names the prompt, builds the input and records the outcome, and the pass makes the calls to prompts through the client the `Config` holds, the same one the registry's `SiteText` holds. A `Fetch` that took subjects instead would have changed the website check, which the document leaves unchanged (decision 22).
- **`Found` copies the outcome rather than normalizing it.** Unlike `Derive`, `Found` reads prompts' answer, not the store: a run id or status that is empty, or a negative cost, is prompts misbehaving, and its result is not valid for the kind, so the store refuses to record it rather than record a guess. What the pass does then is `D06-passes`'.
- **`Failed` is the found value's own rule**, not the pass's or the page's, so the count of failed runs and the mark on the candidate page cannot disagree. A status prompts may add later counts as failed unless it is an exit with code 0.
- **`site_text`'s found members are snake_case and avoid release-43's field names**, like the derived kinds', and it refuses unknown members, since nothing old writes them.
- **Derived work runs inside the store** (sheet 0.3): the store calls `Derive` within its own writes, so a merge or split re-runs the derived kinds atomically with the ruling and the judge that follows. `internal/store` imports `enrichers`; `enrichers` imports `sources`, `fmcsa` and `website` and never `store` or `passes`.
- **The website found value is `website.Result`'s JSON** (sheet 0.6), with Go's member names, because release-43 decodes it by those names. Rows release-43 wrote hold more members (`Candidate`, `Kind`, `Source`, `Cost`, `At`) and are still valid; a reader decodes them into `website.Result` and ignores the rest, so the website kind does not refuse unknown members.
- **Derived found members are snake_case and avoid release-43's field names** (sheet 0.7), so release-43 never fails on a derived row. The derived kinds refuse unknown members, since nothing old writes them.
- **`drive_minutes` writes `{}` for a ZIP the table lacks** (sheet 0.8), rather than writing nothing: otherwise a ZIP moving to an unknown one would keep stale minutes, and the candidate would be due on every pass forever.
- **The fingerprint hashes every link, gone ones included** (sheet 0.9; settled decision 2: each link's id, state and reading values, sorted), so a link going gone changes it; the inputs are empty only with no link at all.
- **A candidate whose inputs become empty keeps its last result's facts** (sheet 0.10), departing from decision 3's "the facts projection shows unknown": the facts row is the projection of the newest result of each kind and must be rebuildable from the enrichments alone (decision 5), and a candidate that has none newer keeps its newest. This is `D13-scoring`'s precedent for the website check: a candidate that stops being checked keeps its last result as the newest.
- **Derive is total; it normalizes rather than refuses.** A `Subject` is a plain value any caller can build, so `Derive` cannot assume what the store's readings guarantee (a scraper on every link, a verdict from `fmcsa.Read`, a date a scrape could hold). Rather than narrow the contract to an input domain, each value its kind's `Valid` would refuse is read as absent or unknown, the way an empty verdict already was: every found value it returns is then valid for any subject, and the store never fails on a derived write. For the store's own subjects nothing changes.
- **The rules moved, not changed** (decision 6): `link_facts` gives, field for field, what the judge wrote before for the same links, but for the category the government match adds (categories document, decision 3), and the rules version stays 5.
- **The government match's category comes from the one match `link_facts` keeps**, the first in link order, not from every link's match: the fact and the category then never disagree, and two links matching `COUNTY` and `CITY OF` give `government` from `name` once. The fact stays, and so does the `government` cohort filter. The fingerprint is unchanged: the match is already on each link's reading, which it hashes.

## Consumer tasks

The store builds a candidate's subject as `s := enrichers.Subject{ID: c.ID, Name: c.Name, City: c.City, State: c.State, Email: c.Email, Zip: c.Zip, Website: f.WebsiteURL, Minutes: m, Links: ls}`, `f` from `GetFacts` (empty on `store.ErrNotFound`), `m` from `ZipMinutes` and `ls` from `Links`, each `enrichers.Link{Scraper: l.Scraper, SourceID: l.SourceID, Gone: l.Gone, Reading: l.Reading}`; it keeps `reg := enrichers.New(enrichers.Config{})` and validates with `reg.Valid(e.Kind, e.Found)`; for a derived kind `k` it takes `en, ok := reg.Get(k)` and `d, ok := en.(enrichers.Deriver)`, `in := d.Inputs(s)`, skipping an empty `in`, and `r := d.Derive(s)` gives the `Source`, `Found` and `Cost` it records beside `in`.

The engine builds `reg := enrichers.New(enrichers.Config{Website: cfg.Website, Prompts: cfg.Prompts})` and walks `reg.All()`: a value whose `Fetched()` is false is run through `st.Derive`; one that is a `enrichers.Fetcher` is skipped when `Ready()` is false and otherwise handed each batch's unchecked inputs through `Fetch(ctx, inputs, func(in string, r enrichers.Result) { … })`; one that is a `enrichers.Prompter` is skipped by an untargeted pass. A targeted pass over `site_text` takes `p, _ := en.(enrichers.Prompter)`, refuses it when `!p.Ready()`, calls `cfg.Prompts.Show(ctx, p.Prompt())`, and for each due subject `s` calls `cfg.Prompts.Run(ctx, p.Prompt(), p.Input(s))`, polls `Result` until the status is neither `enrichers.RunQueued` nor `enrichers.RunRunning`, and records `r := p.Found(out, n)` with `n` the distinct URLs the candidate holds, inputs `p.Inputs(s)`; it counts a failed run when `json.Unmarshal(r.Found, &f)` into an `enrichers.SiteTextFound` gives `f.Failed()`. The `enrich` tool refuses a `kind` not in `enrichers.Kinds()`.

A test of a derived kind builds a subject, calls `enrichers.LinkFacts{}.Inputs(s)` and `res := enrichers.LinkFacts{}.Derive(s)`, checks `res.Source == enrichers.SourceLinks`, decodes `var lf enrichers.LinkFound; json.Unmarshal(res.Found, &lf)` and compares it field by field; a test of the registry calls `` enrichers.New(enrichers.Config{}).Valid(enrichers.KindDriveMinutes, json.RawMessage(`{"minutes":84}`)) ``. A test of `site_text` builds a subject, compares `enrichers.SiteText{}.Input(s)` with the bytes it expects, builds a `prompts.Outcome` of its own and decodes `enrichers.SiteText{}.Found(out, 3).Found` into an `enrichers.SiteTextFound`, and checks `Ready` with a client from `prompts.NewClient` over a `telemetry.Capture` writer, which does no I/O.
