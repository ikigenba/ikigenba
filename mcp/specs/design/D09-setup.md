# D09-setup

The two setup files mcp serves to anyone, signed in or not: `/setup.txt`, plain-text instructions an agent reads and follows to connect its own client to the gateway, and `/setup.sh`, a Bash script the user runs in their own terminal to store a token for this space. The connect page's `Automatic Install` section points at the first (`D04-connect`); the first has the agent ask the user to run the second, then configure its client from what the second stored. Both carry this space's values, computed once by the gateway for each request and filled in, so neither the agent nor the script derives any of them. `D01-layout-and-run-seam` declares the names this design behaves through — `gateway.Handler`, `gateway.Config` with its services path, and the root package's `Assets` — and the listed entries (R-VPSY-X98Z). `D04-connect` defines the request's scheme, endpoint, gateway origin, space and auth profile URL, which this design reuses unchanged, so the setup files and the connect page always name the same addresses. `D03-serve` puts these paths under appkit's `identity.Optional`, so a guest reaches them with an empty caller, and owns the trail: every request here records its `request.started` and `request.finished` and nothing else, under an empty user for a guest. `D04-connect` states, for every path outside the MCP endpoint, that no answer sets a cookie or contacts a backend.

## Routes

The **setup paths** are exactly `/setup.txt` and `/setup.sh`, as `net/http` decodes the request's `URL.Path`. Each takes `GET` and `HEAD` and refuses every other method with a 405 naming `GET, HEAD` and an empty body, as the connect page does. A path beneath either, either with a trailing `/`, and `/setup` are not setup paths: they are the gateway's 404 (`D04-connect`). The answer is the same whoever asks: a guest and a signed-in user get the same bytes, since nothing in the data depends on the caller, and mcp reads the services file afresh for each request, as for the page.

## Per-space names

Tokens are per space: each space has its own auth, so a user connected to several spaces holds several tokens, and nothing about one may collide with another's. The gateway's host is always `mcp.<space>`, so the space is the request's space as `D04-connect` defines it: the `Host` with a trailing port dropped, then one leading `mcp.` label. From it the gateway names two things. The **variable**, the environment variable that holds the space's token on the user's machine, is `IKIGENBA_TOKEN_` and the space with every character that is not an ASCII letter or digit turned into `_`, in upper case. The **server**, the name of the space's entry in a client's MCP configuration, is `ikigenba-` and the space with every such character turned into `-`, in lower case. For `Host: mcp.sbx.ikigenba.dev` they are `IKIGENBA_TOKEN_SBX_IKIGENBA_DEV` and `ikigenba-sbx-ikigenba-dev`; for `Host: mcp.wip-mcp.localhost:7403`, `IKIGENBA_TOKEN_WIP_MCP_LOCALHOST` and `ikigenba-wip-mcp-localhost`. The space's directory on the user's machine is `${XDG_CONFIG_HOME:-~/.config}/ikigenba/<space>/`; the instructions write it out with the space filled in, and the script expands it in the user's own shell. The gateway computes these in tested Go code and hands them to both templates, so the script carries them as values rather than working them out.

## The templates

The setup files are human-authored assets, `assets/setup.txt` and `assets/setup.sh`, embedded by the root package beside `connect.html` (`D01-layout-and-run-seam`); the build run never writes them. They are not HTML, so they are Go `text/template` files, parsed into a set of their own, the **setup template set**: the standard library's `text/template` `ParseFS` over `Assets()` with the two file names as patterns, with no function added. This departs from the `html/template` precedent every page follows, `connect.html` included: `html/template` would escape for an HTML context and corrupt a shell script or plain text, and neither file draws appkit's banner or footer, so neither needs `page.Templates()`. As `connect.html` defines `connect`, `setup.txt` defines the template `instructions` and `setup.sh` the template `installer`, each file opening with a comment that names the template's data and the text tests read; a define keeps that comment out of the output, so the script's first line is its `#!`.

Both templates take the same data, the **setup data**, named by each file's top comment:

- `Space`, the request's space.
- `Origin`, the request's gateway origin, `<scheme>://<Host>`, from which the instructions' command fetches `<Origin>/setup.sh`.
- `Endpoint`, the request's endpoint, `<Origin>/mcp`, which the script checks the token against and writes into `config` as `mcp`.
- `TokenURL`, the request's auth profile URL, auth's profile page, where a user creates a token: from the services file's `auth` entry, or from the `Host`, exactly as the connect page's profile link. The script writes it into `config` as `auth`.
- `Variable`, the request's variable.
- `Server`, the request's server.

`text/template` escapes nothing, so the values arrive in the files exactly as the request and the services file give them, and the script's quoting cannot protect against a value that itself holds a quote. The guard is the host: nginx routes a request to mcp only for the server names opsctl configures, and the `auth` URL is opsctl's, so on a space neither carries shell syntax; a `Host` a developer types by hand reaches only that developer's own script.

The body of each `GET` is exactly the output of its template for the request's setup data, which a test renders itself and compares byte for byte, and both are served as `text/plain; charset=utf-8`, the script included, so a browser shows it rather than downloading it. Beyond the byte-for-byte rule, the tests read the text the stories fix, with any `Host` and services file the test chooses, so a template that wrote a fixed value, or left one for the script to derive, fails: the instructions carry the endpoint, the token page, the command `curl -fsSL <Origin>/setup.sh | bash` on a line of its own, the variable, the server and the space's directory, which names the space; the script begins `#!/usr/bin/env bash` and carries the space, the endpoint, the token page, the variable and the server each as a single-quoted shell word, which is how it holds them as values. A test cannot tell a value printed from one recomputed by the template's own text, so the delimited forms are what keep the space from passing as a mere substring of the endpoint.

## What the assets must do

Everything below is the assets' contract, which the human who writes them follows. `S12` is normative for it by reference, in full: every outcome the instructions state, the script's every terminal line and diagnostic with its detail, the `config` file's five lines and their order, the files' modes, and the postconditions. The summary below orients and does not replace it; it is checked by hand, by fetching the files from the sandbox, running the script under a temporary `HOME` and `XDG_CONFIG_HOME` in a terminal, and having a real client follow the instructions, never by mcp's tests, which may start no process but the binary (`AGENTS.md`). So it carries no requirement id, and the build run neither writes nor tests it. A gap found in that check is fixed in the asset, not in code.

`setup.txt` is written for the agent, not the user, and states outcomes to make true rather than steps (`S12`, `An agent reads the setup instructions`). It names the space. It tells the agent that it must run on the user's own machine and otherwise say so and stop; that the script runs on Linux only, and on any other OS the agent says so and stops, giving no command; and that a client with its own way to add a remote MCP server with a secret typed outside the chat, as grokbot has, uses that way instead. Then: ask the user to create a token at the token page and run `curl -fsSL <Origin>/setup.sh | bash` in a terminal, and wait; the script saves `config` and `token` in the space's directory, written out in full; the agent reads `config` and uses its values, deriving none, and never reads, prints or copies `token`. Then the four outcomes: the variable holds the token in the environment the client gets when restarted the way it runs now, moved by no command that prints it; the client has an MCP server named the server at the endpoint, sending `Authorization: Bearer <token>` by referring to the variable, never holding the token unless the client can read neither a variable nor a file and the user agrees; nothing else in the user's configuration changes, and another ikigenba entry or token variable is left alone and mentioned; and, for a client with both a user and a project scope, the user has chosen which. Then tell the user what was configured, the server, its file and scope, the variable and where it is set, and exactly what to restart, without asking how they launch the client, and wait. After the restart, the `services` tool and one read-only `call` must both succeed, since some clients connect without a token; on failure, find out why and fix it. Last comes a reference of facts, not steps, about Codex, Claude Code, the Grok CLI, and where a Linux terminal and a Linux desktop session take their environment from.

`setup.sh` is a Bash program for Linux (`S12`, the stories from `A user stores a token for the space` on), run as `curl -fsSL <Origin>/setup.sh | bash`, taking no options and asking only for the token. Its diagnostics begin `ikigenba-setup: `, with any detail after one empty line, and go to stderr; every other line, its prompt and the token's asterisks go to the terminal, `/dev/tty`, and nothing goes to stdout. It stops with exit 1 before anything else on an OS that is not Linux, without `curl`, or with no `/dev/tty` to open. It shows the space, the endpoint and the directory it saves to, tells the user to create a token at the token page, and reads the token from `/dev/tty` one character at a time, echoing `*`, with backspace and Ctrl-U, restoring the terminal on Ctrl-C; it trims white space from both ends and stops on an empty token. It checks the token before writing anything — a `POST` to the endpoint of a JSON-RPC `tools/list` with the MCP transport's `Content-Type` and `Accept`, the `Authorization` header passed to `curl` on its standard input so the token is never in a process's arguments, and a 30-second limit: a 2xx goes on, 401 or 403 is `the gateway refused the token`, and anything else, no answer included, is `cannot reach <endpoint> (HTTP <status>)`; each stop changes nothing. With a good token it creates the space's directory with mode `0700` when absent and replaces `token` (mode `0600`, the token and a newline) and `config` (mode `0644`, the lines `space`, `mcp`, `auth`, `variable` and `server`, in that order) each whole, never half-written, stopping with `cannot create <dir>` or `cannot write <dir>/<file>` when it cannot. It always asks, and a good token replaces the stored one. It changes no environment, shell profile or client configuration, and exits 0 once the token is stored.
