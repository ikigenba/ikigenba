# D09-setup

The two setup files mcp serves to anyone, signed in or not: `/setup.txt`, plain-text instructions an agent reads and follows to have the user connect its client to the gateway, and `/setup.sh`, the installer the user runs in their own terminal. The connect page points at the first (`D04-connect`); the first tells the agent to have the user run the second. Both carry this deployment's addresses, filled in for each request, so neither names a host of its own. `D01-layout-and-run-seam` declares the names this design behaves through — `gateway.Handler`, `gateway.Config` with its services path, and the root package's `Assets` — and the listed entries (R-VPSY-X98Z). `D04-connect` defines the request's scheme, endpoint, gateway origin and auth profile URL, which this design reuses unchanged, so the setup files and the connect page always name the same addresses. `D03-serve` puts these paths under appkit's `identity.Optional`, so a guest reaches them with an empty caller, and owns the trail: every request here records its `request.started` and `request.finished` and nothing else, under an empty user for a guest. `D04-connect` states, for every path outside the MCP endpoint, that no answer sets a cookie or contacts a backend.

## Routes

The **setup paths** are exactly `/setup.txt` and `/setup.sh`, as `net/http` decodes the request's `URL.Path`. Each takes `GET` and `HEAD` and refuses every other method with a 405 naming `GET, HEAD` and an empty body, as the connect page does. A path beneath either, either with a trailing `/`, and `/setup` are not setup paths: they are the gateway's 404 (`D04-connect`). The answer is the same whoever asks: a guest and a signed-in user get the same bytes, since nothing in the data depends on the caller, and mcp reads the services file afresh for each request, as for the page.

## The templates

The setup files are human-authored assets, `assets/setup.txt` and `assets/setup.sh`, embedded by the root package beside `connect.html` (`D01-layout-and-run-seam`); the build run never writes them. They are not HTML, so they are Go `text/template` files, parsed into a set of their own, the **setup template set**: the standard library's `text/template` `ParseFS` over `Assets()` with the two file names as patterns, with no function added. This departs from the `html/template` precedent every page follows, `connect.html` included: `html/template` would escape for an HTML context and corrupt a shell script or plain text, and neither file draws appkit's banner or footer, so neither needs `page.Templates()`. As `connect.html` defines `connect`, `setup.txt` defines the template `instructions` and `setup.sh` the template `installer`, each file opening with a comment that names the template's data and the text tests read; a define keeps that comment out of the output, so the installer's first line is its `#!`.

Both templates take the same data, the **setup data**, named by each file's top comment:

- `Origin`, the request's gateway origin, `<scheme>://<Host>`, from which the agent's command fetches `<Origin>/setup.sh`.
- `Endpoint`, the request's endpoint, `<Origin>/mcp`, the URL the installer writes into the client's configuration and checks the token against.
- `TokenURL`, the request's auth profile URL, auth's profile page, where a user creates a token: from the services file's `auth` entry, or from the `Host` with its port and one leading `mcp.` label dropped, exactly as the connect page's profile link.

`text/template` escapes nothing, so the values arrive in the files exactly as the request and the services file give them, and the installer's quoting cannot protect against a value that itself holds a quote. The guard is the host: nginx routes a request to mcp only for the server names opsctl configures, and the `auth` URL is opsctl's, so on a space neither carries shell syntax; a `Host` a developer types by hand reaches only that developer's own script.

The body of each `GET` is exactly the output of its template for the request's setup data, which a test renders itself and compares byte for byte, and both are served as `text/plain; charset=utf-8`, the script included, so a browser shows it rather than downloading it. Beyond the byte-for-byte rule, the tests read the text the stories fix, with any `Host` and services file the test chooses, so a template that wrote a fixed address instead of its data fails: the instructions carry the endpoint, the token page, the installer's command and the five client names; the installer begins `#!/usr/bin/env bash` and carries the endpoint and the token page.

## What the assets must do

Everything below is the assets' contract, which the human who writes them follows. `S12` is normative for it by reference, in full: the configuration paths per client and scope (`${CODEX_HOME:-~/.codex}/config.toml` and `.codex/config.toml`; `~/.claude.json` and `.mcp.json`, under `mcpServers`; `${GROK_HOME:-~/.grok}/config.toml` and `.grok/config.toml`), the three entry shapes, the clients' display names, every output line and diagnostic with its detail, and the postconditions, the user's trust files left untouched among them. The summary below orients and does not replace it; it is checked by running the installer on the developer's machine against the sandbox, never by mcp's tests, which may start no process but the binary (`AGENTS.md`). So it carries no requirement id, and the build run neither writes nor tests it. A gap found in that check is fixed in the asset, not in code.

`setup.txt` is written for the agent, not the user (`S12`, `An agent reads the setup instructions`). It tells the agent to set up only the client the user is talking to it through, and to stop, saying where it runs, when it runs on a machine other than the user's; to work out the client and the OS from its own instructions, confirming the OS with a command where it can, and to ask the user only what it cannot tell, and which scope, `user` or `project`, when the user has not said; that the installer runs on Linux only, so on any other OS it says so and stops; the five client names `codex-cli`, `codex-desktop`, `claude-cli`, `claude-desktop` and `grok-cli`; to give the user the three-step message of `S12` — create a token at the token page, run `curl -fsSL <Origin>/setup.sh | bash -s -- --client <client> --scope <scope>` and paste the token at its prompt, restart the client and say so — with the client's name and the flags filled in; never to ask for the token in the chat; once the user says the client is back, to check the connection with the gateway's `services` tool and one read-only `call`, since a client with no token may still list tools, the `call` running a read tool of a service `services` lists as available, and when either fails, saying the connection did not work, quoting the gateway's error and pointing the user back to the installer; and, for an agent with its own way to add a remote MCP server and take a secret outside the chat, as grokbot has, to add the endpoint that way instead of the installer.

`setup.sh` is a Bash program for Linux (`S12`, the stories from `A user sets up Codex desktop for their account` on). Its diagnostics begin `ikigenba-setup: `, with any detail after one empty line; prompts and the token's asterisks go to `/dev/tty`, other lines to stdout, diagnostics to stderr. It takes `--client` and `--scope` and nothing else, refusing a missing or unknown one, or an unknown option, before anything else, with exit 2. On an OS that is not Linux it stops with exit 1 before the summary; with no `/dev/tty` to open it stops with exit 1. It prints the summary (client, OS, scope with the configuration file it will change, endpoint) and asks `Continue? [y/N]`, taking only `y` or `yes` in either case; it then reads the token from `/dev/tty` one character at a time, echoing `*` and honouring backspace, stops on an empty token, and checks the token with the gateway before writing anything — a `POST` to `<Endpoint>` carrying `Authorization: Bearer <token>`, `Content-Type: application/json`, the `Accept` the MCP transport asks for and a JSON-RPC request the gateway answers for any signed-in caller, such as `tools/list`, since a bare `GET` is the transport's 405 whatever the token: a 2xx goes on, 401 or 403 is `the gateway refused the token`, anything else, no answer included, is `cannot reach <Endpoint>`; each stop exits 1 and changes nothing. It then writes `~/.config/environment.d/ikigenba.conf`, mode `0600`, holding the one line `IKIGENBA_TOKEN=<token>`, sets the variable in the systemd user manager for the current session, and writes the client's `ikigenba` entry for the chosen scope — the project scope being the current working directory — with the client's own `codex`, `claude` or `grok` `mcp add` when that command is on the `PATH`, and otherwise by editing the file itself, replacing only the `ikigenba` entry and creating the file and its directory when absent. The entry references `IKIGENBA_TOKEN` and never holds the token. A run always asks for a token and replaces the stored one. It writes nothing at all when it stops: should a write fail after an earlier one succeeded, a client's `mcp add` say, it restores what it changed and exits 1 with a diagnostic naming the step. It ends with the restart lines `S12` shows, and the trust line for a project scope of the Codex or Grok clients, and exits 0. The token should never appear in a process's arguments, where another user's `ps` could read it: the check passes the header to `curl` on its standard input, and the session variable is set with `systemctl --user import-environment` from the script's own environment rather than on a command line.
