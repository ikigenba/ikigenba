# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail it records from its start to its stop, and the rules the gateway's handler keeps on every route — the identity gate, the request's id, and the request's two events. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run`, the exit codes, `server.Serve`, `server.DrainError`, and `gateway.Config` and `gateway.Handler`; appkit's `telemetry` package (its designs D11 to D14) owns the events, the writer, the middleware and the sibling client this design wires. `D02-cli` decides that an empty `Args` means serve and that nothing else touches the environment. This design says how `Run` reads the drain deadline and the services path, takes the socket the host passes in, tells systemd it is ready, serves and stops, and how `Serve` treats the listener it is handed, in the shapes the serve stories show: a clean start, a stop that drains, a stop whose drain runs out, a stop forced by the socket failing, and the three ways a start is refused. What the handler answers on each route is `D04-connect`, `D05-assets`, `D06-mcp-endpoint`, `D07-describe-and-backend-hop` and `D08-call-and-mutate`.

## The terms every app serves on

mcp serves on the platform's common terms, the same as every app. It serves only on a listening socket it inherits and never opens one of its own. On a host, opsctl publishes `ikigenba-mcp.socket`, holding the Unix stream socket `/run/ikigenba/mcp.sock`, beside `ikigenba-mcp.service`, a `Type=notify` service that runs the binary with no arguments as the `ikigenba` user; nginx proxies to that socket. A deploy restarts the service alone, so the socket, and the connections queued on it, outlive every restart.

mcp takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment once it has taken the socket. Once it is ready it sends the datagram `READY=1` to the Unix datagram socket named by `NOTIFY_SOCKET`, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace. On `SIGTERM` or `SIGINT` it stops accepting, lets the requests it already accepted finish for at most `DRAIN_SECONDS`, then cuts off whatever is left, says how many it cut off, and exits 1. It closes its own copy of the socket and never removes the socket's path. `DRAIN_SECONDS` is a positive whole number of seconds, 5 when unset or empty, with no upper limit of mcp's own; opsctl owns its value and the unit's stop timeout.

The environment also carries `IKIGENBA_SERVICES`, the path of the host's services file. `Run` looks it up through `LookupEnv` when it starts to serve and hands the value to the gateway's handler as `Config.ServicesPath`; the handler reads the file afresh for every request (`D01-layout-and-run-seam`'s listed entries). Nothing about the variable or the file can stop a start: unset, empty, or naming a file that is missing, unreadable or malformed, mcp starts, serves and says nothing about it, and its connection reaches no MCP service. The file is read only while a request is being answered, so it can neither delay nor fail a start.

The suite is a closed system: an app trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them. mcp is the one app whose purpose is to call its siblings: while serving a request to `/mcp` it calls a backend directly at the socket that backend's entry names and forwards those three headers (`D07-describe-and-backend-hop`). Every request has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it as it arrives, and that id is the one every event about the request carries and the one every backend request made for it forwards.

mcp's standard error holds only trouble: a condition it cannot continue from, and an event it could not deliver to the telemetry service. A request it answers with a 5xx, the missing-identity 500 included, is a handled failure, recorded by that request's `request.finished` with its status; a backend that fails is told to the model and recorded by a `sibling.called`. So the handler has no stream at all, and `Run` writes only its start-up refusals, its accept failure, its drain cut-off, and the lines its telemetry writer writes for undelivered events.

## Taking the socket

With `Args` empty, `Run` reads `DRAIN_SECONDS` first, so a bad value is found at start, and when both the drain and the socket are wrong the drain is the one reported. The value is spelled the way opsctl writes an integer: one or more ASCII digits, no sign, no leading zero, no unit, no whitespace. A value too large for a `time.Duration` is the longest drain a `time.Duration` holds rather than an error or a wrap. A value that is not acceptable is a usage error, quoted back verbatim.

A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one. Anything else is no socket passed in, and a count above one is a unit mcp will not guess about. Both are usage errors with the detail line saying how to run mcp. None of the refused starts takes the descriptor, unsets a variable, serves anything or tells systemd anything.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv` and takes descriptor 3 as its listener: through `Process.Inherit` when a test supplies one, otherwise with `net.FileListener` over the real descriptor. The Go `net` documentation of `UnixListener.SetUnlinkOnClose` states that a listener made by `FileListener` does not remove the socket file when closed, and `FileListener` documents that closing the listener does not affect the file it was made from, so the path systemd created stays and systemd's copy keeps queueing connections for the next mcp. If the descriptor cannot be made into a listener, that is trouble on the host: `mcp: ` and the error, exit 1.

With the listener in hand `Run` tells systemd it is ready and serves the gateway's handler on it until `ctx` is done. The socket has been listening since systemd made it, so ready is true before the first `Accept`, and a failure to send it is reported without anything having been served: `mcp: ` and the error, exit 1.

## Serving and stopping

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted, drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it returns nil as soon as they have. If some are still being handled when `drain` runs out, it closes their connections without the rest of their responses and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. A request waiting on a backend is a request being handled like any other: it is let finish within the drain, and cut off and counted after it. `Run` reports a cut-off as `mcp: stopped with <n> requests unfinished` (`1 request` when `<n>` is 1) and exits 1.

An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other error ends serving as an accept failure, after which `Run` drains the requests in progress and cuts off the rest, the deadline counted from the failure, exactly as the requirements state. The check is made by finding, with `errors.As`, a value with a method `Temporary() bool` in the error, through an interface the build declares locally: calling `Temporary` on `net.Error` itself is deprecated, and the lint gate's staticcheck rejects it (SA1019).

The drain is stated at two seams. At `Serve` a test hands in the duration. At `Run` it exists only as `DRAIN_SECONDS`, so the requirement is what a client sees: a request still being handled when `ctx` is done is given the drain deadline and cut off less than a second after it. A test holds a request open — a `POST /mcp` whose declared `Content-Length` exceeds the bytes it sends, or a `call` to an in-process backend that blocks on a channel — with `DRAIN_SECONDS=1`, unset and empty.

`Serve` is silent in its own right: Go's `net/http` documents at `Server.ErrorLog` that, when that field is nil, server errors go through the `log` package's standard logger to the real standard error, so `Serve` gives the server an `ErrorLog` that goes nowhere. A healthy run whose trail is delivered is silent from start to finish; nothing reaches `Stdout` while serving. Once `Run` has returned it writes nothing more: an undelivered-event line for an event recorded after the drain deadline, a cut-off request's `request.finished` say, appears before the stop line or not at all. `Run` makes sure no two writes to `Stderr` are ever in progress at once, its own lines and the writer's alike, because requests are concurrent and a test's `Stderr` is a `bytes.Buffer` the race detector watches. No read, write or idle timeouts are contract; the build sets `ReadHeaderTimeout` because the lint gate's gosec `G112` demands it, and must not set a write timeout that could cut a response short inside the drain or the backend budget.

## The trail from start to stop

When it serves, `Run` builds one telemetry writer with appkit's `telemetry.New`, naming the service `mcp` (`gateway.ServiceName`) and the version `Version`, delivering to `Process.Sink`, or to appkit's socket sink when that is nil, through a sink of its own placed in front of it (below), and writing the lines for undelivered events to `Process.Stderr` through the same guard as its own lines. It makes the MCP server by calling `Process.MCP` with that writer, once, and hands the same writer to the handler as `Config.Telemetry`, so every event of the process goes through one queue and one sink. A refused start records nothing: no writer delivers, and the sink is never called.

Once it has told systemd it is ready, `Run` calls `Writer.Ready`, so `service.started`, carrying `Version`, is the first event of the trail, before any request's. When `ctx` is done it drains the server first, so every request that finishes records its `request.finished`, and then, inside the same drain window — a context whose deadline is the drain deadline — calls `Writer.Shutdown` with the reason, which records `service.stopping` as the last event and delivers what is queued. The reason is the text of `context.Cause(ctx)`, which in the binary is the signal's name, `SIGTERM` or `SIGINT`. When the requests use the whole window, nothing is left for delivery: every event still queued, `service.stopping` included, is written to `Stderr` before the stop line, which is always `Run`'s last. An accept failure is trouble mcp cannot continue from, and `Run` stops as a signal stops it, the drain deadline counted from the failure: it accepts nothing more, lets the requests in progress finish within the deadline and cuts off the rest, records `service.stopping` with the reason `failed` after the finished requests' `request.finished`, gives the trail what is left of the same deadline, writes what is still undelivered to `Stderr`, and then writes `mcp: ` and the error `Accept` returned, last, and exits 1. Past either deadline the sink is handed nothing: no call to `Process.Sink`'s `Deliver` begins then, so a cut-off request's `request.finished`, and `service.stopping` when the requests use the whole window, are never in the trail, whatever the sink does with a context that is done.

appkit's writer cannot keep that promise alone. Its deliveries are given a done context only once the context passed to `Shutdown` is done (appkit's D12), and `Run` calls `Shutdown` only after the server has drained, which, when requests use the whole window, is a moment after the deadline; and after `Shutdown` returns the writer may still begin one call it had already set out to make, with a done context (D12 again), which a sink that ignores its context, a `*telemetry.Capture` say, would store. So the sink `Run` hands `telemetry.New` is `Run`'s own, standing in front of `Process.Sink` (or of the sink `telemetry.NewSocketSink` returns). It learns the deadline the moment `ctx` is done or the accept failure happens; a `Deliver` it receives at or after the deadline returns an error at once without calling the sink behind it, and one it receives before the deadline is passed on with a context that is done by the deadline too. The writer counts such an event as undelivered, so its line is written as for any other (R-G20L-5D38), and since the context `Run` gives `Shutdown` ends at the same deadline, `Shutdown` returns at once and the writer's one late call, if it makes one, reaches only `Run`'s sink.

Sending the trail never holds up readiness or a request: appkit's writer queues and returns, so a sink that blocks or fails changes neither when `READY=1` is sent nor any answer. A test proves the trail at this seam with a `*telemetry.Capture` as `Process.Sink`, read once `Run` has returned; the undelivered lines with a sink that rejects every event; and the drain bound with a sink that blocks until the test releases it.

## The handler's rules on every route

`gateway.Handler` wraps its whole surface — `/`, `/_appkit/`, `/mcp`, `/mcp/<scope>`, and every path it does not serve — in appkit's `identity.Require`, and that in appkit's `telemetry.Middleware` with `Config.Telemetry`. So a request without `X-User-Id` is answered by appkit's identity middleware before the path, the method or the scope is looked at: a malformed scope without identity gets the 500, not the 404. What the middleware answers is appkit's contract; the requirement below states only that the handler's answer is that middleware's, which a test proves by comparing against a handler it builds with `identity.Require` itself.

Every request the handler answers, whatever its path and whether or not it carries an identity, records `request.started` as it arrives and `request.finished` once its answer is complete, with every other event of the request — a backend request's `sibling.called`, a tool call's `tool.called` — between them, all under the request's id and its `X-User-Id`. The handler records no event of its own beyond these: what each records, and when, is appkit's contract, and the requirements below state what a test of the gateway observes of it.
