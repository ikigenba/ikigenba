# D07-describe-and-backend-hop

`describe` is the tool a model calls to learn what a service can do before it runs anything there, and the backend hop is the one path by which `describe`, `call` and `mutate` reach a service. This design owns both: what `describe` answers, and everything the three tools share on the way to a backend — which name is a service the connection can use, where the request goes and whom it carries, how fresh the backend's tool list is, how long the gateway waits, what happens when the client gives up, how each failure is told to the model, and the `sibling.called` event the gateway records for every request it makes to a backend. `D08-call-and-mutate` adds what only `call` and `mutate` do: the kind check, the backend's `tools/call`, and the relay of its result. The four tools' names, descriptions, schemas and annotations are `D06-mcp-endpoint`'s; the terms connection, reached services, MCP services, entry, available, unavailable, reason, listed entries and budget are `D01-layout-and-run-seam`'s, the request id is `D03-serve`'s, and a test that exercises one of them carries that term's id too.

## A gateway call

A gateway call is a `tools/call` of `describe`, `call` or `mutate` whose arguments appkit's server has accepted. Arguments it refuses are answered in appkit's wording before the gateway looks at anything, and such a refusal reaches no backend. An accepted call names a service and, always for `call` and `mutate` and optionally for `describe`, a tool. Its checks run in a fixed order, and the first that refuses ends the call: a service the connection does not reach is unknown; a reached service that is unavailable is refused with its reason; then the backend is asked for its `tools/list`, and whatever goes wrong with that ends the call; then a tool the backend does not list is refused. Each refusal is an `isError` result with exactly one text block telling the model its next move. The first two are made before any backend is asked, so they contact nothing and record no `sibling.called`.

## The hop

The gateway goes straight to the Unix socket the service's entry names in the services file as it stands for that request, never through the space's nginx and never by the entry's URL. It posts to `/mcp`, speaking revision `2026-07-28`, and carries the caller it serves: the first `X-User-Id` value it received, the first `X-User-Email` value it received only when present and not empty, and the request's id (`D03-serve`) as `X-Request-Id` — the first value it received, or, for a request that came without one or with an empty one, the id appkit's request middleware made up for it, so the backend's trail carries the same id as the gateway's; a duplicated header goes on as its first value, and an empty `X-User-Email` is dropped. Every backend request goes through appkit's sibling client, `telemetry.SiblingClient` with the handler's writer, the service's name and `telemetry.SocketTransport` over the entry's socket, handed to appkit's `mcp` client as its `HTTPClient`: the sibling client forwards the caller from the request's context and records the hop, and changes neither the request nor the answer, so the budget, the cancellation and every outcome below are what they were without it. The gateway follows no redirect. appkit's sibling client, left as it is, follows redirects as `http.Client` does (its D14), which would send a second `tools/call` for one call; so the gateway sets `CheckRedirect` on the `*http.Client` it gets to one that returns `http.ErrUseLastResponse`, and a 3xx answer comes back as the answer to the one request that drew it. Each backend request is thus exactly one HTTP request per page, and each records one `sibling.called` carrying the backend's status, a 307 recording 307. It names itself to the backend as `mcp` at its own version, in the `clientInfo` every request's `_meta` carries. A backend's `tools/list` may come in pages; the gateway follows them all, and the whole exchange counts as one backend request with one outcome, though each page is an HTTP request of its own and records its own `sibling.called`.

The gateway keeps no copy of a backend's tools. Every gateway call asks the backend afresh, so a backend redeployed with a tool gained, lost or re-annotated shows the change on the very next call, with no restart and nothing to expire. The requirement is stated as that outcome; how the build arranges it is its own.

## Time and the client going away

One budget (`D01-layout-and-run-seam`: `DefaultBudget`, or `Config.Budget` when a test injects a short one) covers every backend request a gateway call makes, counted from the moment the gateway's handler receives the call, so the `tools/list` of a `call` eats into the time its `tools/call` has. When the budget runs out the gateway abandons the backend request in flight, closing its connection, and answers at once. It never abandons one sooner. The refusal names the budget in seconds, written as Go's shortest decimal form, so the binary says `50` and a test with a 200-millisecond budget reads `0.2`.

A client that stops waiting closes its connection. The gateway notices through the request's context, abandons the backend request in flight at once, closing that connection too, and makes no further backend request for the call. The tool still answers, with an `isError` result no one reads, so its `tool.called` records the outcome `error` and the request's `request.finished` the status 200 the answer carried; what the result says is not contract, since no client ever sees it.

A test proves the budget with a backend that blocks on a channel and a budget of a few hundred milliseconds, and cancellation by cancelling the context of its own client's call while the backend blocks, watching the backend's request context end. Proving that the budget is shared by both backend requests of one call needs the backend's `tools/list` answer held for part of the budget, released on a timer, while its `tools/call` is held until the gateway gives up; the test fails if the answer has not come within a deadline shortly after the budget.

## How each backend request ends

Every backend request ends in exactly one outcome, the first that applies: `cancelled` when the client went away first; `timed out` when the budget ran out first; `unreachable` when nothing accepted a connection at the socket's path; `bad response (status <n>)` when the backend answered with a 3xx status, whatever the answer's body, since the gateway never follows a redirect and appkit's client would report a JSON-RPC error in such a body as an `RPCError` (a build can read the status by wrapping the sibling client's transport from outside, which leaves its recording as it is); `rpc error <code>: <message>` when the backend answered with a JSON-RPC error; `bad response (status <n>)` when it answered with something appkit's client reports as an HTTP-level failure; `bad response` for any other failure once connected, a connection broken before any status included; `tool error` for a `tools/call` answered with an `isError` result; and `ok` otherwise. The classes lean on what appkit's `mcp.Client` reports for the backend's answer (its `RPCError` and `HTTPError` types) and on its documented wrapping of dial failures and context ends, without restating those rules.

A `tools/list` that does not end `ok` ends the call: unreachable and bad answers invite a retry later, a timeout says how long the gateway waited, and a JSON-RPC error passes the backend's message on unaltered after naming the service. The unreachable and JSON-RPC-error texts are shared with the `tools/call` of `D08-call-and-mutate`; the timeout and bad-answer texts for a `tools/call` are `D08-call-and-mutate`'s, because a tool that may have run must not be retried blindly.

A tool's kind is `read` only when its backend says so, with `readOnlyHint` `true`; a tool with no annotations at all, or any other hints, is `write`. That is exactly what appkit's `ToolInfo.Effect` reports as `Read`, so a build may use either reading.

## What describe answers

With a service alone, `describe` answers the backend's tools in the backend's order, each with its name, its summary (the description up to its first LF) and its kind. With a tool too, it answers that tool's full description, its kind, its input schema and, only when the backend gives one, its output schema, both equal as JSON values to what the backend listed. Both answers carry the object twice, as `structuredContent` and as one text block holding it compactly encoded, the convention `S05` fixes for every result of the gateway's own making. `describe` never runs a tool.

Whether `describe` is registered with an output schema is `D06-mcp-endpoint`'s to state; nothing here depends on it.

## The trail of a backend request

For every HTTP request it sends to a backend — a `tools/list` page or a `tools/call` — the gateway records one `sibling.called` through the handler's writer, under the request id and user of the request carrying the call, once the backend's status and headers arrive or, when none arrive, once the request fails. appkit's sibling client records it (its D14); what the gateway fixes is what it says: `target` is the service's name, `method` is `POST`, `path` is `/mcp`, and `status` is the one appkit's sibling client records (its D14): the backend's status when a whole response head came back, and 0 when the exchange failed instead — nothing accepted the connection, the budget ran out or the client went away first, or the connection broke before the response head was complete, even after a status line or an interim 1xx answer had arrived. A JSON-RPC error carried by a 500 records 500, and a 502 records 502. Its `duration_us` runs from sending the request until the status arrived or the request failed, by the writer's clock, so a test whose clock moves only while its backend holds a request reads exactly that movement. The event names no tool and carries nothing of the answer: which tool ran, and how it ended, is in the backend's own trail under the same request id, beside the gateway's `tool.called` (`D06-mcp-endpoint`), which follows the call's backend requests. A refusal made before any backend is asked records no `sibling.called`, and nothing the gateway does with a backend writes to any stream.
