# D10-about

The about screen at `/about`: mcp's name, the release and commit it runs and its one-line description, for a signed-in user. Every app of the suite has one, and appkit's banner offers it in every page's menu, beside the landing row; mcp has no MCP tools of its own (its manifest says `mcp = false`), so the kit leaves the banner's `Tools` false and the menu holds the landing row and About only. `D01-layout-and-run-seam` declares `gateway.Handler`, `gateway.Config` with its banner source, `gateway.ServiceName`, the root package's `Assets`, which holds `about.html` beside `connect.html` (R-ZSAC-3MTK), and `cli.Manifest`, whose description line is this design's `gateway.Description` (R-ZZLQ-E99Q). `D04-connect` defines the terms this design answers with: the gateway's template set, the banner user and the sign-in URL. `D03-serve` puts `/about` under appkit's `identity.Optional`, like every path outside the MCP endpoint, and owns the request's two trail events; `D04-connect` states for every path outside the MCP endpoint that nothing there contacts a backend or sets a cookie. Tests of this design carry those documents' ids where they exercise those rules.

## The page and its data

The screen is the human-authored template `about` in `assets/about.html`, part of the gateway's template set. Its data is `gateway.AboutData`: the banner, which carries the service's name as `Service` and the run's `Release` and `Commit`, the identity `main` handed the kit (`D01-layout-and-run-seam`), and which the template hands to appkit's `banner` and `footer`, the footer emitting that `Release` and `Commit`; and `Description`, which is always `gateway.Description`. That constant is the one place mcp's description is written: `cli.Manifest` carries it on its `description` line, so the line the host publishes in its services file and the line the about screen shows cannot drift, and the screen says the same with or without a services file. Its words are copy; no requirement states them.

The banner comes from the handler's banner source, called with the request's banner user, exactly as the connect page's does. The about screen sits one level below the landing page, so before drawing it the handler sets the banner's `Trail` to the **about trail**: one level, named `about`, the path segment, at `/about`. It replaces whatever trail the source returned; in the binary that is always empty (appkit's D02). With that trail appkit's banner marks About as the current row of the page menu. A test proves the level by executing `about` with the data this design states, the about trail included, and comparing the body byte for byte, with a banner closure that returns a trail of its own so that a handler which kept or extended it fails; it never looks for a word or a hook. The connect page leaves the trail empty (`D04-connect`), and mcp draws no other page: its 404, its 405s and its sign-in redirects carry no banner.

## Who sees it

The screen names its caller in the banner, so, like the connect page, it is for signed-in users, as the template's opening comment says. mcp serves guests (`guests = true`), so a guest reaches `/about` through `identity.Optional` with an empty caller; a guest's `GET` or `HEAD` is sent to auth's sign-in with `302` and the request's sign-in URL, its `return` naming `/about`, exactly as a guest at `/` is (`D04-connect`), and no banner is drawn. This follows mcp's own connect page and the other app whose manifest serves guests, which sends a guest at its about screen to sign in the same way.

## Methods

`/about` takes `GET` and `HEAD`. Any other method is refused 405 with `Allow: GET, HEAD` and an empty body, a guest's included: the method is looked at before the caller. `HEAD` is answered with the status and headers of the `GET` and no body. Only exactly `/about` is the screen: `/about/` and every path beneath it are the gateway's 404 (`D04-connect`).

## Consumer tasks

`gateway.Handler` routes exactly `/about`, under `identity.Optional`, to the about screen. For a signed-in `GET /about` it calls `b := cfg.Banner(u)` with the request's banner user `u`, sets `b.Trail = []page.Level{{Name: "about", URL: "/about"}}`, and executes `about` of the gateway's template set with `gateway.AboutData{Banner: b, Description: gateway.Description}`. `cli.Manifest`'s description line is `gateway.Description`.

A test builds the handler as `D04-connect`'s tests do, with a `Banner` closure that records its argument and returns a fixed `page.Banner` whose `Trail` is non-empty, requests `GET /about` with `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` set as nginx would, builds its own copy of the gateway's template set from `page.Templates()` and `mcp.Assets()`, executes `about` with `gateway.AboutData{Banner: want, Description: gateway.Description}`, `want` being the fixed banner with its `Trail` replaced by the about trail, and compares the bodies byte for byte. It requests `/about` without `X-User-Id` for the redirect, with `POST` for the 405, and with `HEAD` beside `GET` for the HEAD rule. It executes `about` with the zero `gateway.AboutData`. It compares `cli.Manifest` with `gateway.Description` for the description line.

## REQUIREMENTS

- R-ZYDU-0HJ1: The `internal/gateway` package MUST export `const Description string`, a copy constant whose words are not contract, whose value is not empty and holds no `"`, no `\` and no control character.
- R-00TM-S10F: The `internal/gateway` package MUST export `type AboutData struct { Banner page.Banner; Description string }`, with exactly these fields in this order, where `page` is the package `github.com/ikigenba/ikigenba/appkit/page`.
- R-021J-5SR4: mcp's design defines the **about trail** as a `[]page.Level` of length one whose one element has the `Name` `about` and the `URL` `/about`, and the **about data** for a `page.Banner` `b` as the `gateway.AboutData` whose `Banner` is `b` with its `Trail` replaced by the about trail and every other field unchanged, and whose `Description` is the value of `gateway.Description`; and every requirement of mcp's design that names the about trail or about data MUST denote such a value.
- R-09CX-GF7A: Executing, into a `bytes.Buffer`, the template `about` of the gateway's template set with any `gateway.AboutData`, the zero value included, MUST return a nil error.
- R-039F-JKHT: A handler `gateway.Handler(cfg)` returns MUST answer every `GET` request whose first `X-User-Id` value is non-empty and whose URL path is `/about`, whatever its other headers, query and body, with status 200, exactly one `Content-Type` header, whose value is exactly `text/html; charset=utf-8`, and a body that is exactly the text that executing the template `about` of the gateway's template set writes with the about data for the `page.Banner` returned by a call of `cfg.Banner` that was made while that request was being answered and whose argument was the banner user of that request, whatever `Trail` that `page.Banner` carries.
- R-05P8-B3Z7: For two requests to `/about` whose first `X-User-Id` value is non-empty, that differ only in that one's method is `HEAD` and the other's is `GET`, answered by one handler `gateway.Handler(cfg)` returned, whose `cfg.Banner` returns equal values for equal arguments, while the file at `cfg.ServicesPath` holds the same content or is absent for both, that handler MUST answer the `HEAD` request with the same status and the same value for every header it sets as it answers the `GET` request, and with an empty body.
- R-06X4-OVPW: A handler `gateway.Handler(cfg)` returns MUST answer every request whose URL path is `/about` and whose method is neither `GET` nor `HEAD`, whatever its identity headers, other headers and body, a request whose `X-User-Id` header is absent or whose first `X-User-Id` value is empty included, with status 405, exactly one `Allow` header, whose value is exactly `GET, HEAD`, and an empty body.
- R-0851-2NGL: A handler `gateway.Handler(cfg)` returns MUST answer every `GET` or `HEAD` request whose URL path is `/about` and whose `X-User-Id` header is absent or whose first `X-User-Id` value is empty, whatever its `X-User-Email`, query, other headers and body, with status 302, exactly one `Location` header, whose value is exactly the request's sign-in URL, and an empty body, without calling `cfg.Banner`; so that, with `Host: mcp.sbx.ikigenba.dev` and while the listed entries hold an entry named `auth` whose `URL` is `https://auth.sbx.ikigenba.dev`, a guest's `GET /about` with `X-Forwarded-Proto: https` gets `Location: https://auth.sbx.ikigenba.dev/?return=https%3A%2F%2Fmcp.sbx.ikigenba.dev%2Fabout`.
