# D04-connect

What the gateway's handler answers at every path but the MCP endpoint, the setup files and the shared files: the connect page at `/` for a signed-in user, the sign-in redirect for a guest there, the refusal of any other method there, and the plain-text 404 for every path mcp does not serve. `D01-layout-and-run-seam` declares the names this design behaves through — `gateway.Handler`, `gateway.Config` with its banner source and services path, `gateway.ServiceName`, and the root package's `Assets` — and defines the domain terms it uses: the listed entries (R-VPSY-X98Z) and the MCP services, their entries and whether each is enabled (R-VR0V-B0ZO). `D03-serve` owns the rules the handler keeps on every route, this one included: which identity middleware guards each path — every path this design answers is under appkit's `identity.Optional`, so a guest, whose `X-User-Id` is absent or empty whatever `X-User-Email` it carries, reaches it with an empty caller and is never answered 500 — and the trail (R-O1E7-TCYD), under which every request this design answers records its `request.started` and `request.finished` and nothing else, and writes nothing to any stream. `D05-assets` defines the appkit paths and owns their answers, and `D09-setup` defines the setup paths and owns theirs. `D06-mcp-endpoint` owns `/mcp` and every path beneath it, and cites this design's 404 for a malformed scope. Tests of this design carry D01's definitional ids where they exercise those terms.

## Routes

The handler routes on the request's `URL.Path` as `net/http` decodes it, exactly, and never redirects but to send a guest at `/` to sign in. `/` takes `GET` and `HEAD` and refuses every other method with a 405 naming `GET, HEAD` and an empty body, a guest's included: the method is looked at before the caller. An appkit path is `D05-assets`'s; `/setup.txt` and `/setup.sh` are `D09-setup`'s; `/mcp` and everything beginning `/mcp/` are `D06-mcp-endpoint`'s. Every other path is **the gateway's 404**, whatever the method and whoever asks, a guest never being sent to sign in for it: one line of plain text, `not found`, with no banner and no footer. `/_appkit` without its slash, `/assets/...`, `/logout`, `/setup.txt/` and every path beneath a setup file, a trailing-slash variant and a path holding `.` or `..` segments are all such paths, which is why the handler cannot lean on `http.ServeMux`'s pattern matching as it stands: that would answer the first and the last with a redirect. Nothing outside the MCP endpoint contacts a backend or sets a cookie: the page, the redirect and the setup files read the services file and nothing else, and mcp serves no logout route.

## The connect page

The page is the human-authored template `connect` in `assets/connect.html`, embedded by the root package (`D01-layout-and-run-seam`). The handler builds the **gateway's template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher` and `footer`; the template draws `banner` first in its body and `footer` last, both from the page's banner data. The code adds no template function and writes no markup of its own: the body of a `GET /` is exactly the output of `connect` for the request's **connect data**, which a test can render itself and compare byte for byte.

The connect data has five members, named by the template's top comment:

- `Banner`, the `page.Banner` the handler's banner source returns, called while the request is answered with the **banner user**: the caller's `X-User-Email` exactly as it arrived, auth's profile URL and auth's logout URL. In the binary the banner source is the `Banner` method of appkit's kit, which adds the service's name, mcp's version and the launcher's services, read afresh from the host's services file; what the banner and the launcher draw from it is appkit's contract, and whether the binary carries the launcher is `D01-layout-and-run-seam`'s exec test. A handler test uses a closure of its own.
- `Endpoint`, the **endpoint**: the request's scheme, `://`, its `Host` exactly as it arrived, port included, and `/mcp`. The **scheme** is `X-Forwarded-Proto` when that header is exactly `http` or exactly `https`, and `https` for anything else, an absent or empty header included.
- `Services`, one element per MCP service of the request's listed entries, in their order: its name, its entry's `Description`, its scoped endpoint (the endpoint, `/`, the name), whether it is available, and the reason it is not. The page lists the MCP services alone, so the reason is always `disabled`; `not installed` is a reason only a scoped MCP connection can produce (`D01-layout-and-run-seam`, R-VUOK-GC7R). These are the services the `services` tool lists on the unscoped endpoint (`D06-mcp-endpoint`). The gateway's own entry is never among them, whatever it says, and a missing or unreadable services file leaves the list empty, which the template shows as the line `No MCP services are installed.` in place of the table.
- `SetupURL`, the **setup URL**: the **gateway origin** — the request's scheme, `://` and its `Host` exactly as it arrived, the endpoint without its `/mcp` — followed by `/setup.txt`. The template's `Connect your agent to ikigenba` section, between the token line and `Services`, tells the user to ask their agent to read it, as code a user can copy: the section's heading is an `h2` reading `Connect your agent to ikigenba`, after the profile link and before the services, and the address is `code#setup-url`; what the agent finds there is `D09-setup`'s.
- `GitScope`, the **git scope**: the request's scheme, `://*.`, and the **git space**, which is the request's `Host` exactly as it arrived with a single leading `mcp.` label dropped and its port kept. The template's `Git` section writes it into the one command it offers, `git config --global credential.<git scope>.helper '...'`, which installs a credential helper that hands git the token from `IKIGENBA_TOKEN` for every host of the user's space and no other. Git matches a `credential.<url>` key whose host begins `*.` against any single leading label (gitcredentials(7), "Credential contexts", and observed with `git credential fill`), and the port must be kept because git's URL matching compares it. The section's text does not depend on the services file.

Auth's two URLs come from the services file's entry named `auth` when it has one with a URL: that URL followed by `/` for the profile, and by `/logout` for sign-out. Otherwise mcp reads the space from the request's `Host`: a trailing `:` and port digits are dropped, then a single leading `mcp.` label; auth is `auth.` and that space, under the request's scheme. There is no fixed fallback address. An entry named `auth` whose URL is empty is not usable, so it falls back the same way.

`HEAD /` is answered with the status and headers of the `GET` and no body.

## A guest at the connect page

The page names its caller in the banner and lists the space's MCP services, so it is for signed-in users. A guest's `GET /` or `HEAD /` is sent to auth's sign-in with `302` and a `Location` that is the **sign-in URL**: the auth profile URL, derived exactly as for the page's profile link (services file first, then the `Host`, port dropped), then `?return=` and the URL the guest asked for — the request's scheme, `://`, its `Host` as it arrived and its path and query — escaped with the standard library's `url.QueryEscape`. The redirect's body is empty, since the code writes no markup of its own, and drawing it calls no banner source, so no page is drawn. This departs from sites, whose sign-in redirect never reads the services file and keeps the port: mcp's stories derive the address as the profile link is derived, and auth's sign-in is its profile URL with `return` (mcp's `S03`).

## Reading the page

The tests have no HTML parser — appkit is mcp's one module dependency and carries none — so this design fixes the hooks the template's top comment names and the visible text the stories quote, and defines how each is read with the standard library: start and end tags, attributes read left to right as a browser reads them, an element's content, and normalisation (tags removed, character references unescaped, whitespace collapsed). Rules about the page's own markup are read over its **written markup**, the body with appkit's banner and footer taken out, because those are appkit's output. The git command's quotes and `&&` come back unchanged through normalisation, which unescapes character references, so the hook's text is the command exactly as a user pastes it. The hook requirements are stated for a **plain page request**, whose host, service names and auth URL carry nothing that escaping would change and whose descriptions carry no whitespace that collapsing would change (a description may hold markup characters or character references, which escaping and then reading back restore exactly); the byte-for-byte requirement covers every other request, so `html/template`'s contextual autoescaping is what keeps a caller's or the services file's bytes from becoming markup. A hook the template lacks is an issue for a human, never a change to the asset.
