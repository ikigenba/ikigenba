# D04-connect

What the gateway's handler answers at every path but the MCP endpoint, the protected-resource metadata and the shared files: the connect page at `/` for a signed-in user, the sign-in redirect for a guest there, the refusal of any other method there, and the plain-text 404 for every path mcp does not serve. `D01-layout-and-run-seam` declares the names this design behaves through — `gateway.Handler`, `gateway.Config` with its banner source and services path, `gateway.ServiceName`, and the root package's `Assets` — and defines the domain term it uses, the listed entries (R-VPSY-X98Z). `D03-serve` owns the rules the handler keeps on every route, this one included: which identity middleware guards each path — every path this design answers is under appkit's `identity.Optional`, so a guest, whose `X-User-Id` is absent or empty whatever `X-User-Email` it carries, reaches it with an empty caller and is never answered 500 — and the trail (R-O1E7-TCYD), under which every request this design answers records its `request.started` and `request.finished` and nothing else, and writes nothing to any stream. `D05-assets` defines the appkit paths and owns their answers, and `D09-resource-metadata` defines the metadata paths and owns theirs, using this design's request terms: the scheme, the endpoint, the space and the listed entries' `auth`. `D06-mcp-endpoint` owns `/mcp` and every path beneath it, and cites this design's 404 for a malformed scope. Tests of this design carry D01's definitional ids where they exercise those terms.

## Routes

The handler routes on the request's `URL.Path` as `net/http` decodes it, exactly, and never redirects but to send a guest at `/` to sign in. `/` takes `GET` and `HEAD` and refuses every other method with a 405 naming `GET, HEAD` and an empty body, a guest's included: the method is looked at before the caller. An appkit path is `D05-assets`'s; a metadata path, `/.well-known/oauth-protected-resource` and every path beneath it, is `D09-resource-metadata`'s; `/mcp` and everything beginning `/mcp/` are `D06-mcp-endpoint`'s. Every other path is **the gateway's 404**, whatever the method and whoever asks, a guest never being sent to sign in for it: a plain-text body that is the copy constant `NotFound`, with no page around it. `/_appkit` without its slash, `/assets/...`, `/logout`, `/setup.txt` and `/setup.sh`, which the gateway no longer serves, `/.well-known/` and `/.well-known/oauth-authorization-server`, which is auth's to publish, `/.well-known/oauth-protected-resourcex`, which is not beneath the metadata path, a trailing-slash variant and a path holding `.` or `..` segments are all such paths, which is why the handler cannot lean on `http.ServeMux`'s pattern matching as it stands: that would answer the first and the last with a redirect. Nothing outside the MCP endpoint contacts a backend or sets a cookie: the page, the redirect and the metadata read the services file and nothing else, and mcp serves no logout route.

## The connect page

The page is the human-authored template `connect` in `assets/connect.html`, embedded by the root package (`D01-layout-and-run-seam`). The handler builds the **gateway's template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`. The code adds no template function and writes no markup of its own: the body of a `GET /` is exactly the output of `connect` for the request's **connect data**, which a test can render itself and compare byte for byte.

The connect data has three members:

- `Banner`, the `page.Banner` the handler's banner source returns, called while the request is answered with the **banner user**: the caller's `X-User-Email` exactly as it arrived, auth's profile URL and auth's logout URL. In the binary the banner source is the `Banner` method of appkit's kit, made with `page.New(gateway.ServiceName, v)`, `v` being the display string `main` reads (`D01-layout-and-run-seam`), which adds the service's name, the display string `--version` prints and the launcher's services, read afresh from the host's services file; what the banner and the launcher draw from it is appkit's contract (its D02 and D03), and whether the binary carries the launcher is `D01-layout-and-run-seam`'s exec test. A handler test uses a closure of its own.
- `Endpoint`, the **endpoint**: the request's scheme, `://`, its `Host` exactly as it arrived, port included, and `/mcp`. The **scheme** is `X-Forwarded-Proto` when that header is exactly `http` or exactly `https`, and `https` for anything else, an absent or empty header included.
- `Server`, the **server name**: the request's **space** — its `Host` with a trailing `:` and port digits dropped, then a single leading `mcp.` label — with every character that is not an ASCII letter or digit turned into `-`, in lower case, with no prefix, so `mcp.sbx.ikigenba.dev` gives `sbx-ikigenba-dev` and a sandbox's `mcp.wip-mcp.localhost:7403` gives `wip-mcp-localhost`. It is the name both commands give the gateway in the client. The services file plays no part in it.

Everything the page shows and how it is marked up are the template's: its words, its headings, its copy blocks, its head and the hooks the stylesheet and appkit's feedback script use. The template composes the commands that add the gateway to Claude Code and to Codex from `Server` and `Endpoint` and shows the endpoint for any other client, which learns the rest from the protected-resource metadata (`D09-resource-metadata`). The design fixes only which template is executed and with which data; the page's markup is the same whatever else the services file lists, since the file is read only for auth's URLs and, through the banner source, the launcher. No test runs the page's scripts (`AGENTS.md`); that pressing a copy button puts the command or the endpoint on the clipboard is checked by hand in a browser against the sandbox, and carries no id.

The head is the `connect` template's too: a page opts in to appkit's stylesheet, favicon and feedback script by linking them under `/_appkit/` (`D05-assets`), and invokes appkit's `preload` template for the font, whose URL carries a hash of its bytes that mcp never writes.

Auth's two URLs come from the services file's entry named `auth` when it has one with a URL: that URL followed by `/` for the profile, and by `/logout` for sign-out. Otherwise mcp reads the space from the request's `Host`: a trailing `:` and port digits are dropped, then a single leading `mcp.` label; auth is `auth.` and that space, under the request's scheme. There is no fixed fallback address. An entry named `auth` whose URL is empty is not usable, so it falls back the same way.

`HEAD /` is answered with the status and headers of the `GET` and no body.

## A guest at the connect page

The page names its caller in the banner, so it is for signed-in users. A guest's `GET /` or `HEAD /` is sent to auth's sign-in with `302` and a `Location` that is the **sign-in URL**: the auth profile URL, derived exactly as for the banner's profile link (services file first, then the `Host`, port dropped), then `?return=` and the URL the guest asked for — the request's scheme, `://`, its `Host` as it arrived and its path and query — escaped with the standard library's `url.QueryEscape`. The redirect's body is empty, since the code writes no markup of its own, and drawing it calls no banner source, so no page is drawn. Only `/` sends a guest to sign in: the protected-resource metadata, the shared files, the 405s and the 404 answer a guest as they answer a user. This departs from sites, whose sign-in redirect never reads the services file and keeps the port: mcp derives the address as the profile link is derived, and auth's sign-in is its profile URL with `return`.
