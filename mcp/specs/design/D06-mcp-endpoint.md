# D06-mcp-endpoint

The gateway's MCP endpoint: appkit's MCP server mounted at `/mcp` and at every `/mcp/<scope>` whose scope is well-formed, the four tools it offers there, the server's name and version, the instructions it gives each connection, and the whole behaviour of the first tool, `services`. `D01-layout-and-run-seam` declares the names this design behaves through — `gateway.Handler`, `gateway.Config`, `gateway.NewServer`, `gateway.ServiceName` — and defines the terms it speaks in: the listed entries, the MCP services, a well-formed scope, a request's connection and its reached services, and whether a reached service is available, with its reason and description. A test of this document that exercises one of those terms carries that term's id from `D01-layout-and-run-seam` as well as the id of the requirement it proves here. `D03-serve` defines a request's request id and owns the trail every request records; this document adds the `tool.called` event each of the four tools records.

## Everything around the tools is appkit's

appkit's `mcp` package is the transport and the protocol: the methods the endpoint answers, both protocol families and their envelopes, the `405` with `Allow: POST` for every method that is not POST, the `Origin`, `Content-Type` and size checks, `notifications/initialized` and its `202`, the absence of sessions, the unknown-tool protocol error with its code and message, schema derivation from Go types, strict argument decoding and its error text, and the success result built from a typed tool's output (appkit's designs D07-mcp-server, D08-mcp-tools and D09-mcp-schema). This document restates none of it and mcp's tests never re-prove it. What the gateway adds is stated as an observable outcome at its own seam: the handler answers a request on a connection exactly as appkit's server, wrapped in the same identity gate, answers it, except for the answers that carry the gateway's own content — the instructions of `initialize` and `server/discover`, and the result of a call of one of its four tools. So a `GET /mcp/dummy,notes`, a `DELETE /mcp`, a call of an unknown tool such as `list_widgets`, and a legacy `tools/list` are appkit's answers at every connection alike, which a test proves by sending the same request to the handler and to `identity.Require(cfg.MCP)` — the same server, served outside any gateway handler, which must then answer without panicking — and comparing the two answers. The comparison covers `initialize`, `server/discover` and calls of the four tools too, all but the instructions and a tool's own result, which are the gateway's and are stated below.

The identity gate comes first on every path (`D03-serve`): a request without `X-User-Id` gets the gate's 500 and never reaches the routing below, the malformed-scope 404 included. The handler has no stream to write to, and the trail every request records is `D03-serve`'s too.

## Paths beneath /mcp

The connection is decided by the decoded URL path (`D01-layout-and-run-seam`): `/mcp` is unscoped, `/mcp/<well-formed scope>` is scoped, and every other path beginning `/mcp/` names no services the gateway could reach and does not exist. It gets the gateway's 404, the plain-text answer `D04-connect` defines for every path the gateway does not serve, whatever its method and body, and never a JSON-RPC response. Go's `http.ServeMux` would answer some of those paths with a `301` to a cleaned path (`/mcp//dummy`, `/mcp/./dummy`, `/mcp/a/../dummy`); the gateway never redirects them. A well-formed name the file does not hold is not malformed: `/mcp/Dummy` is scoped and reaches `Dummy`, which is not installed because names match exactly.

## The four tools

The server `gateway.NewServer` makes offers exactly four tools, in this order, whatever the connection and whatever the services file holds: `services`, `describe`, `call`, `mutate`. Each Tool object is stated here whole, member for member and in member order, as the mcp story shows it. appkit's derivation rules produce every one of these schemas — a probe against appkit's published release confirmed each byte — from these shapes: `services` is a typed tool whose input is a struct with no properties and whose output is an object holding a `services` array of objects whose `reason` is a pointer, so it is absent for an available service; `describe` is a raw tool, so it carries no output schema, taking a required `service` string and an optional `tool` string pointer, which also accepts JSON `null` as no tool; `call` and `mutate` are raw tools taking a required `service` and `tool` and an optional `args` of type `json.RawMessage`, whose schema is `{"type":"object"}` with the description appended, and so carry no output schema. Effects give the annotations: `services`, `describe` and `call` are `mcp.Read`, `mutate` is `mcp.Destructive`.

Decisions recorded for what the story leaves open. The `services` output schema marks `services`, `name`, `description` and `available` required, because a non-pointer member is always written (appkit D09-mcp-schema, Writing Out) and a client may rely on it, and leaves `reason` optional; every property of it carries a description written for the model. `describe` carries no output schema, as the story's listing shows: its result has two shapes, and its results are `D07-describe-and-backend-hop`'s.

The exact member order is observable through a raw `tools/list` on an earlier revision, which appkit's client cannot send and which the story `A client speaking an earlier revision lists the tools` makes anyway; appkit gives both revisions the same Tool objects. The tools on the current revision are seen through `mcp.Client.ListTools` on `/mcp`, on a scope that reaches an available service, and on a scope that reaches nothing installed.

## Name, version and instructions

The server reports the name `mcp` (`gateway.ServiceName`) and the version `NewServer` was given, which in the binary is `cli.Version`. It records each tool call through the telemetry writer `NewServer` was given, which in the binary is the run's one writer; served without the identity gate it answers appkit's missing-caller 500 and records nothing, as appkit's server does.

The instructions are the gateway's, made for each request from its reached services: two lines joined by LF and no LF after the second. The first names the reached services in name order joined by `, `, unavailable ones included, or says there are none; the second tells the model how to go on. They are therefore never empty, so `initialize` and `server/discover` always carry them. appkit's client speaks neither method, so a test reads them over raw HTTP.

## The tool call in the trail

Every call of one of the four tools that appkit's server answers with a result, an `isError` result included, records one `tool.called` through the handler's writer, under the request's id and user, once the tool has done its work and before the answer goes out — so after every `sibling.called` its backend requests recorded (`D07-describe-and-backend-hop`) and before the request's `request.finished`. appkit's server records it (its D08); what the gateway fixes is what the attributes say for its own tools. `tool` is the gateway tool's name, never a backend tool's. `kind` follows the effect each tool is registered with: `read` for `services`, `describe` and `call`, `destructive` for `mutate`, as the annotations above tell the client. `outcome` is `invalid_arguments` when appkit refused the gateway's own arguments, `ok` for a result that is not an error, and `error` for every other `isError` result: a refusal of the gateway's own, or a backend's result relayed with `isError` `true`, a backend's refusal of the `args` it was passed included. A request answered with a JSON-RPC error, a call of an unknown tool say, reached no tool and records no `tool.called`. The backend records its own `tool.called` for the tool it ran, in its own trail under the same request id, so a trace shows both the forward and the execution.

## The services tool

`services` takes no arguments; arguments absent and `{}` are the same call, and any member at all is appkit's unknown-field offence. Its answer lists the request's reached services, in their order, each with its name, its description, whether it is available and, only when it is not, the reason — all read from the services file as it stands for that request, so a rewrite shows in the next call (`D01-layout-and-run-seam`'s listed entries). The gateway's own entry is never listed on the unscoped connection, whatever its `mcp` says, and on a scope that names it, it is `not installed`. `services` contacts no backend: availability is what the file says, not whether a socket answers. In fact no answer this document governs contacts a backend; only `describe`, `call` and `mutate` do (`D07-describe-and-backend-hop`, `D08-call-and-mutate`). A test proves it by listening on a Unix socket at the path each listed entry names, recording every connection it accepts, and, after the gateway's answer has been received and the server serving the handler has been closed, accepting once more with a deadline already past, which finds a connection made late as well as one made during the request.
