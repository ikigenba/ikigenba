# D01-layout-and-run-seam

mcp is the suite's MCP gateway: one Go binary that offers MCP clients four tools over the suite's MCP services at `/mcp` and `/mcp/<scope>`, and a connect page at `/` that tells a person how to point a client at it. This design is the structural ground the other designs stand on: where the code lives, which package exports which name, how the version, the manifest and the usage text are declared, the seam through which the process is run so that the command, the server and the gateway can be tested without a real process, the seam through which the backend budget is injected so that no test waits fifty seconds, and the domain terms every later design uses — the services a connection reaches and whether each is available.

The module is `github.com/ikigenba/ikigenba/mcp`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/mcp` because `devctl build` finds an app as a `package main` in `cmd/<app>`, like every other binary in the repository. `cmd/mcp` is wiring only.

## The one dependency

mcp depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, the platform's shared library, fetched through the ordinary module proxy with no `replace` directive. Which release is data (`go.mod` and `AGENTS.md` name it); no requirement names a version. appkit is a sibling, reached only through its published packages and their documented contracts, and mcp uses four of them: `page` for the banner, launcher and footer and the shared files under `/_appkit/`; `services` for reading the host's services file; `identity` for the caller nginx authenticated, required on every request and forwarded on every backend call; and `mcp` for the server mounted at `/mcp` and the client that calls the backends. appkit owns the banner's markup, the stylesheet, fonts, licences and launcher script, the MCP transport and protocol, schema derivation, argument decoding and its error text, and the reading of the services file; mcp authors none of them and restates none of their contracts.

## The reads of the environment

Two appkit constructors read `IKIGENBA_SERVICES` (`services.Variable`) from the real process environment, once, during the call, and keep the path: `page.New`, whose kit's `Banner` method reads the file afresh for the launcher, and appkit's `mcp.NewServer`, which `gateway.NewServer` calls. Neither offers a form that takes the path from a caller. Reading the real environment is what the run seam keeps out of everything below `main`, so `main` calls both, once each, at start, and nothing else in the binary does. A test that calls `gateway.NewServer` first sets the variable with `testing.T.Setenv`, to the empty string or to a file of its own, as `AGENTS.md` asks; the value cannot change a result, because the gateway supplies its own instructions and never uses the path appkit's server captured.

The gateway's own catalogue read does not need appkit's captured path: `cli.Run` looks `IKIGENBA_SERVICES` up through the seam's `LookupEnv`, once, when it starts to serve, and hands the value to the gateway's handler as `Config.ServicesPath`. So every read of the variable happens at start, which is what the serve story says, and none can fail a start: an unset or empty variable, or a file that is missing, unreadable or malformed, simply lists no services.

`main` builds the banner source as the `Banner` method of `page.New(gateway.ServiceName, cli.Version)` and the server as `gateway.NewServer(cli.Version, os.Stderr)`, and passes both to `cli.Run` in `Process`. `gateway.ServiceName` is the one declaration of the name and `cli.Version` the one declaration of the version, so the footer, the MCP `serverInfo`, the identity diagnostics and the backend-call lines all name the same release. That `main` hands them on correctly is wiring, proved only by the one exec'ing test that `AGENTS.md` admits: it builds the binary, runs `--version`, `bogus` and a bare start with no socket, and then serves on a socket it passes as descriptor 3, with an environment it composes, and makes these requests over that socket with the identity headers set: a `GET /` with `IKIGENBA_SERVICES` unset, whose footer names the name and version; a `GET /` with a services file that lists a service with an icon, which carries the launcher; an appkit `mcp.Client` call of the `services` tool, whose `serverInfo` names the gateway and whose list reflects the file the environment names; and a `call` through the gateway to a backend the test serves in process on a Unix socket, which relays the backend's answer and leaves the two backend-call lines on the binary's standard error. It then stops the child with `SIGTERM`, and in a second run with `SIGINT`.

## Packages

The module's root package, `mcp`, holds the embedded template. The gateway's markup is the human-authored `html/template` file `assets/connect.html`, which the build run reads and never writes. Go's `embed` reaches only files at or below the embedding package's directory, so the root package is the one that can embed it. It exports one name, `Assets`, a file system holding exactly that file. Because the root package and appkit's `mcp` package share a name, a file that imports both aliases one of them; only `internal/gateway` and tests import the root package.

Three internal packages hold the concerns. `internal/cli` owns the program as a command: the version, the manifest text, the usage text, the exit codes, the run seam, the argument handling `D02-cli` specifies, and the serve path `D03-serve` specifies — reading the drain deadline and the services path, taking the socket the host passes in, building the gateway's handler, and telling systemd it is ready. `internal/server` owns the listener's life and nothing else, exactly as in the platform's reference app: handed a context, a listener, a handler and a drain deadline, it serves and drains. `internal/gateway` owns the gateway's whole HTTP surface: the one handler, wrapped in `identity.Require`; the connect page (`D04-connect`); the mount of appkit's shared files (`D05-assets`); the mount of the MCP server at `/mcp` and under well-formed scopes, the four tools and the instructions (`D06-mcp-endpoint`); and the hop to the backends (`D07-describe-and-backend-hop`, `D08-call-and-mutate`). The four tools live with the handler because each answer depends on the request's connection — the scope its path names — and on the services file as it stands for that request, which the handler establishes; splitting them into a package of their own would export a context protocol that no consumer outside the gateway needs. Which package imports which is not observable, so this paragraph is guidance.

## The run seam

The run seam is `cli.Run`. It takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package or from the two environment-reading constructors: the arguments without the program name, an environment lookup, a way to remove a variable from the environment, the process's own id, the two output streams, a way to turn an inherited descriptor into a listener, the banner source, and the MCP server. Its return value is the exit code. `main` fills `Process` from the real process, leaves `Inherit` nil so that `Run` takes the real descriptor 3, and cancels the context on `SIGTERM` or `SIGINT`; a test fills it with buffers, a map, a pid of its choosing, a listener it bound itself, a banner closure and a server it made with `gateway.NewServer`, and cancels the context itself. The environment half of socket activation — `LISTEN_PID`, `LISTEN_FDS`, `NOTIFY_SOCKET`, `DRAIN_SECONDS` and `IKIGENBA_SERVICES` — arrives through `LookupEnv`, and readiness is the `READY=1` datagram a test receives on a socket it named in `NOTIFY_SOCKET`, as `D03-serve` states. Nothing below `main` reads `os.Args`, the real environment, the real pid or the real streams, changes the real environment, calls `page.New` or `gateway.NewServer`, or installs a signal handler.

## The gateway's seam

`gateway.Handler` takes a `gateway.Config`: the banner source, the server `gateway.NewServer` made, the path of the services file, the backend budget and the stream the gateway's diagnostics go to. `gateway.NewServer` makes the server: appkit's server named `mcp`, at the version given, with appkit's own diagnostics going to the stream given, the gateway's instructions and its four tools registered. One server may back several handlers, before or after any of them has served, so a test may build as many handlers as it likes over one server. The design states what a handler does only for a `Config` whose `Banner` is not nil and whose `MCP` came from `NewServer`.

The **budget** is how long one gateway call may wait on its backends, counted from the moment the call arrives and shared by every backend request the call makes. In the binary it is `DefaultBudget`, fifty seconds, which keeps every answer inside nginx's sixty. `Config.Budget` is the injection seam: zero, which is what `cli.Run` passes, means the default, and a test that proves a timeout sets a few hundred milliseconds and a backend that blocks on a channel. What the budget does is `D07-describe-and-backend-hop`'s.

## Domain terms

Every later design speaks of the same few things, defined once here. The **listed entries** are what appkit's `services.Read` finds in the services file as it stands when a request is answered — nothing at all when it cannot read one. The **MCP services** are the names whose entry is marked `mcp`, other than the gateway's own name, in bytewise order; an entry's `enabled` makes the service enabled or disabled. A request's **connection** is decided by its path: `/mcp` is unscoped, and `/mcp/<scope>` with a **well-formed scope** — comma-separated names of 1 to 63 ASCII letters, digits and hyphens, beginning and ending with a letter or digit, no name twice — is scoped to those names. The **reached services** of a request are the MCP services on the unscoped connection and the scope's names on a scoped one, in bytewise order either way. A reached service is **available** when it is an enabled MCP service; otherwise it is unavailable, for the **reason** `disabled` or `not installed`.

## Declarations and the checkout

The version is a `var` in `internal/cli`; its value is data, and a requirement fixes only its name, that it is a `var`, and its shape. The manifest is a constant in the same package holding exactly the five lines the bootstrap story shows, with a trailing newline: mcp's name; its description; that it is not the host's default app; that it is not one of the suite's MCP services, so the gateway's own tools are never in its catalogue; and no secrets. It declares no port. The usage text is a constant there too, whose value `D02-cli` fixes. `etc/manifest.toml` is written by the build run holding exactly the `Manifest` constant; no test reads the checkout, so that copy, like `share/icon.svg` and the release tarball (human-authored and `devctl`'s respectively), is outside what a requirement can state. Everything mcp serves is inside the binary — its template, embedded by the root package, and appkit's embedded files alike.
