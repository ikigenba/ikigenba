# D01-layout-and-run-seam

mcp is the suite's MCP gateway: one Go binary that offers MCP clients four tools over the suite's MCP services at `/mcp` and `/mcp/<scope>`, a connect page at `/` that tells a person how to point a client at it, and the protected-resource metadata at `/.well-known/oauth-protected-resource`, from which an MCP client learns where to sign its user in. This design is the structural ground the other designs stand on: where the code lives, which package exports which name, where the version it shows comes from, how the manifest and the usage text are declared, the seam through which the process is run so that the command, the server and the gateway can be tested without a real process, the seam through which a test catches the trail the gateway records, the seam through which the backend budget is injected so that no test waits fifty seconds, and the domain terms every later design uses — the services a connection reaches and whether each is available.

The module is `github.com/ikigenba/ikigenba/mcp`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/mcp` because `devctl build` finds an app as a `package main` in `cmd/<app>`, like every other binary in the repository. `cmd/mcp` is wiring only.

## The one dependency

mcp depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, the platform's shared library, required at a published release through the ordinary module proxy and checksum database, like any other module, with no `replace` directive. Which release is data (`go.mod` and `AGENTS.md` name it); no requirement names a version. appkit is a sibling, reached only through its published packages and their documented contracts, and mcp uses six of them: `page` for the banner, launcher and footer and the shared files under `/_appkit/`; `services` for reading the host's services file; `identity` for the caller nginx authenticated: `Require` on `/mcp` and every path beneath it, `Optional` on every other path, because the manifest declares `guests = true` and nginx lets a visitor with no credential through to those, and the caller forwarded on every backend call; `mcp` for the server mounted at `/mcp` and the client that calls the backends; `telemetry` for the trail: the writer that queues the gateway's events and delivers them to the telemetry service, the request middleware that records every request, and the sibling client every backend request goes through; and `version` for the code identity the host gives every app: `version.Display()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment at the time of the call and returns the **display string** built from them, the empty string when neither is set (its D21). mcp carries no version of its own: nothing in its source or its build names one. appkit owns the banner's markup, the stylesheet, fonts, licences, launcher script, feedback script and favicon, the MCP transport and protocol, schema derivation, argument decoding and its error text, the reading of the services file, the shape of an event and the framework events every app records, and how an event is delivered, retried and written out when it cannot be; mcp authors none of them and restates none of their contracts. The gateway records no event of its own beyond appkit's framework events: everything it does is a request, a call to a sibling, or a tool call.

## The reads of the environment

`version.Display` reads `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` from the real process environment, and `main` calls it exactly once, first, and holds the result: that value is the version mcp shows everywhere it shows one, and the one it hands `page.New`, `gateway.NewServer` and `Run`. So one start reads the two variables once, as the serve story says, and `--version`, which is a run of its own, reads them once too. Nothing below `main` calls `version.Display`; `Run` receives the string as `Process.Version`, so an in-process test hands it any string it likes, the empty string included, and sets no variable. This is the one shape every app copies: one call in `main`, its result passed down, the app's name being the only thing that differs.

Two appkit constructors read `IKIGENBA_SERVICES` (`services.Variable`) from the real process environment, once, during the call, and keep the path: `page.New`, whose kit's `Banner` method reads the file afresh for the launcher, and appkit's `mcp.NewServer`, which `gateway.NewServer` calls. Neither offers a form that takes the path from a caller. Reading the real environment is what the run seam keeps out of everything below `main`, so only code `main` supplies calls them: `main` calls `page.New` once at start, and puts in `Process.MCP` a function that calls `gateway.NewServer`, which `Run` calls once when it starts to serve. A test that calls `gateway.NewServer` first sets the variable with `testing.T.Setenv`, to the empty string or to a file of its own, as `AGENTS.md` asks; the value cannot change a result, because the gateway supplies its own instructions and never uses the path appkit's server captured.

appkit's socket sink is the third reader: it finds the telemetry service by reading the variable, and the file it names, afresh on every delivery, so a telemetry service installed or moved while mcp runs gets the next event. It is the sink only when `Process.Sink` is nil, which only `main` leaves it; a test passes a sink of its own (a `*telemetry.Capture`, or one that fails or blocks), and a test that leaves it nil sets the variable with `testing.T.Setenv` to a services file naming a stand-in it serves.

The gateway's own catalogue read does not need appkit's captured path: `cli.Run` looks `IKIGENBA_SERVICES` up through the seam's `LookupEnv`, once, when it starts to serve, and hands the value to the gateway's handler as `Config.ServicesPath`. None of these reads can fail a start: an unset or empty variable, or a file that is missing, unreadable or malformed, simply lists no services, and names no telemetry service, so every event is written to standard error as undelivered.

`main`, with `v` the display string it read, builds the banner source as the `Banner` method of `page.New(gateway.ServiceName, v)`, and the server maker as a function that returns `gateway.NewServer(v, w)` for the writer `w` it is given, leaves `Sink` nil so that events go to the telemetry service, and passes them to `cli.Run` in `Process`, with `v` itself as `Process.Version`. It cancels `Run`'s context on `SIGTERM` or `SIGINT` with a cause whose text is the signal's name, `SIGTERM` or `SIGINT`, which `Run` records as the reason of `service.stopping`. `gateway.ServiceName` is the one declaration of the name and the display string `main` reads the one value of the version, the one `--version` prints, so the footer, the MCP `serverInfo`, the `clientInfo` the gateway names itself with to a backend, the service named in every event and the version `service.started` carries all name the same code. That `main` hands them on correctly is wiring, proved only by the one exec'ing test that `AGENTS.md` admits: it builds the binary, runs `--version` with neither `IKIGENBA_COMMIT` nor `IKIGENBA_RELEASE` in the child's environment and expects one empty line, runs `bogus` and a bare start with no socket, and then serves on a socket it passes as descriptor 3, with an environment it composes, `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` both non-empty in it, and computes the display string it expects by calling `version.Display` itself after setting the same two values with `testing.T.Setenv`, so the expectation rests on appkit's promise and no test spells a version. It makes these requests over that socket with the identity headers set: a `GET /` with `IKIGENBA_SERVICES` unset, whose footer names the name and that display string; a `GET /` with a services file that lists a service with an icon, which carries the launcher; an appkit `mcp.Client` call of the `services` tool, whose `serverInfo` names the gateway and that display string and whose list reflects the file the environment names; a `describe` of a service whose socket the test serves with a handler that records each request's body, every one of which carries the gateway's `clientInfo` with that display string; and a `call` through the gateway to a backend the test serves in process on a Unix socket, which relays the backend's answer, with a services file whose `telemetry` entry names a Unix socket on which the test serves appkit's `telemetry.IngestHandler` over a `*telemetry.Capture`, so the test reads the trail the binary delivered: `service.started` with that display string first, the call's events, and `service.stopping` with the signal's name last. It then stops the child with `SIGTERM`, and in a second run with `SIGINT`.

## Packages

The module's root package, `mcp`, holds the embedded templates. They are human-authored files in `assets/`, which the build run reads and never writes: the connect page's `html/template` file `connect.html` (`D04-connect`), the only one. Go's `embed` reaches only files at or below the embedding package's directory, so the root package is the one that can embed them. It exports one name, `Assets`, a file system holding exactly that file. Because the root package and appkit's `mcp` package share a name, a file that imports both aliases one of them; only `internal/gateway` and tests import the root package.

Three internal packages hold the concerns. `internal/cli` owns the program as a command: the manifest text, the usage text, the exit codes, the run seam, the argument handling `D02-cli` specifies, and the serve path `D03-serve` specifies — reading the drain deadline and the services path, taking the socket the host passes in, building the telemetry writer and the gateway's handler, telling systemd it is ready, and recording the start and the stop in the trail. `internal/server` owns the listener's life and nothing else, exactly as in the platform's reference app: handed a context, a listener, a handler and a drain deadline, it serves and drains. `internal/gateway` owns the gateway's whole HTTP surface: the one handler, whose MCP routes are wrapped in `identity.Require` and every other route in `identity.Optional`, the whole in `telemetry.Middleware`; the connect page and the guest's sign-in redirect (`D04-connect`); the protected-resource metadata (`D09-resource-metadata`); the mount of appkit's shared files (`D05-assets`); the mount of the MCP server at `/mcp` and under well-formed scopes, the four tools and the instructions (`D06-mcp-endpoint`); and the hop to the backends through appkit's sibling client (`D07-describe-and-backend-hop`, `D08-call-and-mutate`). The four tools live with the handler because each answer depends on the request's connection — the scope its path names — and on the services file as it stands for that request, which the handler establishes; splitting them into a package of their own would export a context protocol that no consumer outside the gateway needs. Which package imports which is not observable, so this paragraph is guidance.

## The run seam

The run seam is `cli.Run`. It takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package or from the environment-reading constructors: the arguments without the program name, an environment lookup, a way to remove a variable from the environment, the process's own id, the two output streams, the display string `--version` prints and the trail names, a way to turn an inherited descriptor into a listener, the banner source, a function that makes the MCP server from the telemetry writer, and the sink the writer delivers events to. Its return value is the exit code. When it serves, `Run` builds the one telemetry writer, naming the service `mcp` and the version `Process.Version`, delivering to `Sink` (appkit's socket sink when it is nil) and writing undeliverable events to `Stderr`; it calls `MCP` with that writer once, and hands the same writer to the gateway's handler. `main` fills `Process` from the real process, leaves `Inherit` nil so that `Run` takes the real descriptor 3, leaves `Sink` nil, and cancels the context on `SIGTERM` or `SIGINT` with the signal's name as its cause; a test fills it with buffers, a map, a pid of its choosing, a display string of its choosing, a listener it bound itself, a banner closure, a function that calls `gateway.NewServer` with the writer it is given, and a `*telemetry.Capture` or another sink of its own, and cancels the context itself, with `context.WithCancelCause` when it checks the reason. The environment half of socket activation — `LISTEN_PID`, `LISTEN_FDS`, `NOTIFY_SOCKET`, `DRAIN_SECONDS` and `IKIGENBA_SERVICES` — arrives through `LookupEnv`, and readiness is the `READY=1` datagram a test receives on a socket it named in `NOTIFY_SOCKET`, as `D03-serve` states. Nothing below `main` reads `os.Args`, the real environment, the real pid or the real streams, changes the real environment, calls `version.Display` or `page.New`, or installs a signal handler; `gateway.NewServer` is called only through `Process.MCP`, and the real environment is read only by appkit's socket sink when `Process.Sink` is nil.

## The gateway's seam

`gateway.Handler` takes a `gateway.Config`: the banner source, the server `gateway.NewServer` made, the path of the services file, the backend budget and the telemetry writer the handler records its events through. The handler has no stream of its own: everything it has to say is an event, and an event that cannot be delivered is written out by the writer. `gateway.NewServer` makes the server: appkit's server named `mcp`, at the version given, recording each tool call through the writer given, the gateway's instructions and its four tools registered. One server may back several handlers, before or after any of them has served, so a test may build as many handlers as it likes over one server. The design states what a handler does only for a `Config` whose `Banner` is not nil, whose `Telemetry` is not nil, and whose `MCP` came from `NewServer` with that same writer. A test builds the writer itself with appkit's `telemetry.New`, naming the service `mcp`, over a `*telemetry.Capture`, calls `Flush` before it reads `Capture.Events`, and shuts the writer down before it ends.

The **budget** is how long one gateway call may wait on its backends, counted from the moment the call arrives and shared by every backend request the call makes. In the binary it is `DefaultBudget`, fifty seconds, which keeps every answer inside nginx's sixty. `Config.Budget` is the injection seam: zero, which is what `cli.Run` passes, means the default, and a test that proves a timeout sets a few hundred milliseconds and a backend that blocks on a channel. What the budget does is `D07-describe-and-backend-hop`'s.

## Consumer tasks

The binary's start, in outline: `main` calls `version.Display()` once for `v` and hands `cli.Run` a `Process` whose `Version` is `v`, whose `Banner` is the `Banner` method of the kit `page.New(gateway.ServiceName, v)` returns, whose `MCP` returns `gateway.NewServer(v, w)` for the writer `w` it is given, and whose `Sink` is nil, under a context it cancels with the signal's name as the cause. `Run` builds the writer with `telemetry.New` from a `telemetry.Config` naming `gateway.ServiceName`, `Process.Version`, a sink of `Run`'s own standing in front of `Process.Sink` (or of the sink `telemetry.NewSocketSink` returns when it is nil), which hands it nothing past the drain deadline as `D03-serve` states, and a guarded `Process.Stderr`; calls `Process.MCP` with it; builds the handler with `gateway.Handler` from a `gateway.Config` carrying the banner source, that server, the services path, a zero budget and the writer; tells systemd it is ready and calls `Writer.Ready`; serves until the context ends; and then, inside the drain window, calls `Writer.Shutdown` with the context's cause as the reason.

The handler, in outline: `telemetry.Middleware(cfg.Telemetry, routes)`, where `routes` sends `/mcp` and every path beneath it to `identity.Require` over the MCP routes and every other path to `identity.Optional` over the connect page, the protected-resource metadata, the shared files and the 404; each backend is reached by an `mcp.Client` whose `ClientConfig.HTTPClient` is `telemetry.SiblingClient(cfg.Telemetry, <service name>, telemetry.SocketTransport(<entry's socket>))` with its `CheckRedirect` set to return `http.ErrUseLastResponse`, so it follows no redirect (`D07-describe-and-backend-hop`), on a context bounded by the budget.

A test of the run seam passes a `*telemetry.Capture` as `Process.Sink` and a buffer as `Stderr`, serves, cancels with `context.WithCancelCause`, and once `Run` has returned reads `Capture.Events`: `service.started` first, the requests' events, `service.stopping` last. A test of the handler builds its own writer over a `*telemetry.Capture`, the server with `gateway.NewServer` over that writer, and the handler with `gateway.Handler`, drives it, calls `Writer.Flush`, and asserts on the events by name, attributes, request id and user; it passes a sink that fails to see the undelivered lines, and one that blocks to see that answers never wait on the trail.

## Domain terms

Every later design speaks of the same few things, defined once here. The **listed entries** are what appkit's `services.Read` finds in the services file as it stands when a request is answered — nothing at all when it cannot read one. The **MCP services** are the names whose entry is marked `mcp`, other than the gateway's own name, in bytewise order; an entry's `enabled` makes the service enabled or disabled. A request's **connection** is decided by its path: `/mcp` is unscoped, and `/mcp/<scope>` with a **well-formed scope** — comma-separated names of 1 to 63 ASCII letters, digits and hyphens, beginning and ending with a letter or digit, no name twice — is scoped to those names. The **reached services** of a request are the MCP services on the unscoped connection and the scope's names on a scoped one, in bytewise order either way. A reached service is **available** when it is an enabled MCP service; otherwise it is unavailable, for the **reason** `disabled` or `not installed`.

## Declarations and the checkout

`internal/cli` declares no version: the version `--version` prints is the display string `main` reads and hands `Run` as `Process.Version`, and its value is data the host supplies at run time. The manifest is a constant in `internal/cli` holding exactly the nine lines the bootstrap story shows, with a trailing newline: mcp's name; its description; that it is not the host's default app; that it is not one of the suite's MCP services, so the gateway's own tools are never in its catalogue; that it serves guests, so nginx lets a visitor with no credential reach every path outside `/mcp`; and no secrets; then, after an empty line, a `[resources]` table capping its memory at 128M. It declares no port. The usage text is a constant there too, whose value `D02-cli` fixes. `etc/manifest.toml` is written by the build run holding exactly the `Manifest` constant; no test reads the checkout, so that copy, like `share/icon.svg` and the release tarball (human-authored and `devctl`'s respectively), is outside what a requirement can state. Everything mcp serves is inside the binary — its templates, embedded by the root package, and appkit's embedded files alike.

- R-VPSY-X98Z: mcp's design defines the **listed entries** of a handler `Handler(cfg)` returned, for a request, as the `services.List` that appkit's `services.Read(cfg.ServicesPath)` returns at the time that request is answered when the error it returns is nil, and as an empty list when that error is not nil; every requirement of mcp's design that names the listed entries MUST denote that list, so that a services file rewritten between two requests is seen by the second as rewritten.
- R-VR0V-B0ZO: mcp's design defines the **MCP services** of a list `l` of `services.Entry` values as the strings `n` such that some entry of `l` has the `Name` `n`, `n` is not `ServiceName`, and the entry `l.Find(n)` returns has `MCP` true, each string once, in ascending bytewise order; it calls the entry `l.Find(n)` returns the **entry** of the MCP service `n`, and the MCP service **enabled** when that entry's `Enabled` is true and **disabled** otherwise; and the MCP services of a handler for a request are the MCP services of its listed entries for that request.
- R-VS8R-OSQD: mcp's design defines a **well-formed scope** as a string that, split at every `,`, yields one or more **scope names** of which each is 1 to 63 bytes long, consists only of ASCII letters, ASCII digits and `-`, and begins and ends with an ASCII letter or ASCII digit, and no two are equal byte for byte; so the empty string, and every string with an empty element, are not well-formed.
- R-VTGO-2KH2: mcp's design defines the **connection** of a request to a handler `Handler` returned by the request's URL path as `net/http` decodes it into `URL.Path`: the path `/mcp` is the **unscoped** connection, and a path that is `/mcp/` followed by a well-formed scope `s` is the connection **scoped** to the scope names of `s`; and it defines the **reached services** of such a request as, on the unscoped connection, the MCP services of the handler for that request, and on a scoped connection, the scope names of `s` in ascending bytewise order.
- R-VUOK-GC7R: mcp's design defines, for a reached service `n` of a request, that `n` is **available** when it is an enabled MCP service of the handler for that request, and that otherwise it is **unavailable** with the **reason** `disabled` when it is a disabled MCP service and with the reason `not installed` when it is not an MCP service of the handler for that request; and it defines the **description** of `n` as the `Description` of its entry when `n` is an MCP service and as the empty string otherwise.
