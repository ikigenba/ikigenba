# D09-resource-metadata

The gateway's protected-resource metadata: the one JSON document an MCP client reads to learn which authorization server issues the tokens `/mcp` accepts. A client refused at `/mcp` is pointed at `/.well-known/oauth-protected-resource` by the gate's challenge, or probes that path, or probes the path-specific form for the endpoint it was given, `/.well-known/oauth-protected-resource/mcp` or beneath a scope; so the handler answers the same document at `/.well-known/oauth-protected-resource` and at every path beneath it, and reads nothing of the path after it. A path is beneath it when it continues with `/`; `/.well-known/oauth-protected-resourcex`, `/.well-known/` and `/.well-known/oauth-authorization-server`, which auth publishes, are the gateway's 404 (`D04-connect`). The document is auth's and mcp's shared contract with the clients, and its fields are the delivery's settled set: what MCP clients read, and nothing that advertises what the suite refuses.

`D01-layout-and-run-seam` declares `gateway.Handler` and its `Config` and defines the listed entries (R-VPSY-X98Z). `D04-connect` defines the request terms this design uses — the scheme, the endpoint and the space — and states for every path outside the MCP endpoint that no answer sets a cookie or contacts a backend. `D03-serve` puts every metadata path under appkit's `identity.Optional`, so a client with no token reaches it as a guest, and owns the trail: each request records its `request.started` and `request.finished` (R-O1E7-TCYD) and nothing else.

## The document

The document is a JSON object with exactly three members, in no fixed order and with no fixed spacing. `resource` is the request's endpoint, `<scheme>://<Host>/mcp`, built as the connect page builds it, whichever path beneath the document was asked for, since every scoped endpoint lies beneath it. `authorization_servers` is an array holding one string, the **authorization server**. `bearer_methods_supported` is `["header"]`. It names no scopes, since the suite has none.

The authorization server must equal auth's `issuer` exactly, or the client's issuer check fails; auth's issuer is its origin with no trailing slash. So the handler reduces the `url` of the services file's `auth` entry to its origin: the scheme, `://` and the host with its port, as the standard library's `url.Parse` reads them, with no path, query, fragment or trailing slash. When the file has no `auth` entry, its `url` is empty, or it does not parse as an absolute URL with a host, auth is read from the request as the connect page reads it for its links: the request's scheme, `://auth.` and the request's space. In a sandbox the services file names auth at `http://auth.<sandbox>.localhost:<port>`, auth's own public origin, so the fallback is for a host whose file lacks the entry. This is a different reduction from the banner's links, which take the entry's `url` as written and append to it (`D04-connect`).

A `HEAD` is answered as the `GET` with no body, and every other method with a 405 naming `GET, HEAD`, a signed-in user's included. Nothing in the answer depends on who asks: a guest and a user get the same bytes, and no guest is sent to sign in.

- R-RTW5-3SJ9: mcp's design defines a **metadata path** as a request's URL path, as `net/http` decodes it into `URL.Path`, that is exactly `/.well-known/oauth-protected-resource` or begins with `/.well-known/oauth-protected-resource/`; and every requirement of mcp's design that names a metadata path MUST denote such a path.
