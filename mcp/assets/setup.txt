{{/* The setup instructions at GET /setup.txt. Data: .Space, .Origin, .Endpoint, .TokenURL, .Variable, .Server. */}}{{define "instructions"}}Connect an agent to ikigenba
============================

You are an agent helping your user connect you to the ikigenba MCP gateway for the space {{.Space}}. Your job is to make the four outcomes below true for the client you are running in, then prove they are true. How you get there is up to you; use what you know about your own client and the user's machine, and ask the user only what you cannot find out.

First: you must be running on the user's own machine. If you run somewhere else (a hosted sandbox, a cloud container), tell the user you cannot configure their machine from there and stop. The script in step 1 runs on Linux only: on any other operating system, say so and stop, and give no command. If your client has its own way to add a remote MCP server with a secret typed outside the chat, use that instead and skip the rest.

Step 1: the user stores a token
-------------------------------

Ask the user to run this in a terminal on their machine:

    curl -fsSL {{.Origin}}/setup.sh | bash

It asks for a token (they create one at {{.TokenURL}}), checks it with the gateway, and saves two files in ${XDG_CONFIG_HOME:-~/.config}/ikigenba/{{.Space}}/:

    config   space, mcp, auth, variable and server, as key=value lines. Read it.
    token    the token. Never read, print, echo, copy into the chat or into a command line you show.

Wait for the user to say it is done, then read config. Use its values; do not derive them yourself. For this space they are: mcp {{.Endpoint}}, variable {{.Variable}}, server {{.Server}}.

Step 2: make these true
-----------------------

1. The environment variable named by `variable` holds the contents of `token` in the environment you, this client, get when restarted the way you are running now: a terminal session for a CLI, the desktop session for a desktop app. Any command that moves the token must not print it.
2. Your client has an MCP server named by `server`, URL `mcp`, that sends `Authorization: Bearer <token>` by referencing the variable. The client's config never holds the token itself, unless the client has no way to read a variable or file and the user agrees.
3. Nothing else in the user's configuration is lost or changed: edit only the entry named by `server`, and leave other servers, other spaces' entries and other variables alone. If another ikigenba entry or token variable already exists, leave it and tell the user.
4. If your client supports both user scope (all projects) and project scope (this project only), ask the user which they want. Otherwise use the scope it has.

Then tell the user what you configured: the MCP server name (`server`) and the file and scope it is in, the variable name and where it is set. They may have other ikigenba spaces installed and need the name to tell them apart. Then tell the user exactly what to restart (and whether a new terminal or a fresh login is needed for the variable), and wait for them.

Step 3: prove it
----------------

After the restart, call the gateway's `services` tool, then one read-only `call` on a service it lists. Both must succeed. A connection alone proves nothing: some clients connect without a token when the variable is missing. If either fails, find out why (is the variable set in your process? is it the right one? does the config reference it?) and fix it.

Reference
---------

These are facts about clients, not steps. Check your client's own docs or `--help` when unsure.

Codex (CLI, desktop app and IDE extension share one file)
  User config ${CODEX_HOME:-~/.codex}/config.toml; project .codex/config.toml, loaded only for trusted projects.
  `codex mcp add <server> --url <mcp> --bearer-token-env-var <variable>` writes:
      [mcp_servers.<server>]
      url = "<mcp>"
      bearer_token_env_var = "<variable>"
  Connects without a token if the variable is unset. Desktop app: Restart in its MCP settings.

Claude Code (CLI and the Code tab of Claude desktop share files)
  User and local scope in ~/.claude.json; project scope .mcp.json at the project root. ${VAR} expands in url and headers.
  `claude mcp add --transport http --scope user <server> <mcp> --header 'Authorization: Bearer ${<variable>}'`
  `claude mcp add` fails if the name exists; remove it first. An unset variable sends the literal text.
  On Linux the desktop app's environment is undocumented; check what it actually sees.

Grok CLI
  User ${GROK_HOME:-~/.grok}/config.toml; project .grok/config.toml (needs folder trust).
  `grok mcp add -s user <server> <mcp> -H 'Authorization: Bearer ${<variable>}'`
  Also supports bearer_token_file = "<path to token>", which reads the file per request and needs no variable.
  ${VAR} expands at load time, so a new value needs a new process.

Linux environments
  A terminal-started client inherits the shell's environment (~/.bashrc, ~/.profile, ...). A shell profile can read the file at startup, e.g. export <variable>="$(cat <token path>)".
  A desktop-launched client gets the systemd user session's environment: ~/.config/environment.d/*.conf (KEY=value, read at login, cannot run commands) and `systemctl --user set-environment` for the current session.
  A shell profile that sets the same variable overrides the session value in terminals.
