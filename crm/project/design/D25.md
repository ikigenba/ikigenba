# Decision 25 — Tracking tokens: the `contact_tokens` table, the `mint` verb, and `search` token lookup

**Context.** The operator runs outreach campaigns and wants to know when a
prospect engages with a handed-out link. A tracking token is a short opaque code
tied to one contact; it is handed out (in a URL, a QR code), and when it comes
back — a link hit arriving elsewhere in the suite — something must be able to
turn that code back into the contact it belongs to. crm owns contacts, so crm
owns the token → contact relationship: it mints tokens and resolves them. crm
does **not** host the links, receive the hits, or send notifications — those are
other services. crm's whole job here is mint and resolve.

**Decision.**

A new owned child table, one new verb, and one new `search` lookup.

1. **`contact_tokens` — tokens belong to a contact.** A forward, timestamped
   migration (`bin/create-migration crm <name>`) adds:

   ```sql
   CREATE TABLE contact_tokens (
       id          TEXT PRIMARY KEY,             -- ULID
       contact_id  TEXT NOT NULL REFERENCES contacts(id) ON DELETE CASCADE,
       token       TEXT NOT NULL,
       campaign    TEXT NULL,
       created_at  TEXT NOT NULL,
       deleted_at  TEXT NULL
   );
   CREATE UNIQUE INDEX uq_contact_tokens_token_live
       ON contact_tokens(token) WHERE deleted_at IS NULL;   -- global uniqueness among live tokens
   CREATE INDEX idx_contact_tokens_contact_live
       ON contact_tokens(contact_id) WHERE deleted_at IS NULL;
   ```

   Many tokens may belong to one contact (one per campaign / outreach attempt);
   a token is **globally unique** among live rows, so it resolves to exactly one
   contact. Soft-delete follows the entity convention (`deleted_at`); a deleted
   token frees its value and stops resolving.

2. **`mint` — a new domain verb.** Input `{ contact_id (required), campaign
   (optional) }`. It resolves the contact (must be live), generates a token,
   inserts one live `contact_tokens` row, and returns
   `{ token, contact_id, campaign }` with `structuredContent` + a declared
   `outputSchema` like every domain verb (D19). The token is **6 characters from
   the lowercase Crockford base32 alphabet** — the digits `0-9` and letters
   `a-z` excluding the confusable `i`, `l`, `o`, `u` (32 symbols) — drawn
   randomly; on the rare clash with the live-unique index the mint retries with a
   fresh value (bounded), so a returned token is always unique. `mint` never
   overwrites or reuses; each call adds a row.

3. **`search` resolves a token to its contact.** `search` gains a `token`
   filter under `type:"contact"`:
   `search { type:"contact", filters:{ token:"oak7k" } }` returns the single
   live contact that owns a **live** token equal to that value, or no results if
   the token is unknown or soft-deleted. This is the reverse lookup a link-hit
   consumer uses; it reuses the existing `search` verb rather than adding a
   surface (the operator's choice).

4. **No events.** `mint` publishes nothing on the event plane: the link host and
   the hit consumer live in other services and react to *their* events, not to a
   mint. crm's outbox producer is unchanged.

**Error surface.**

- `mint` with a `contact_id` that names no live contact returns crm's typed
  not-found error (D19) and creates **no** token row.
- `mint` with a missing/empty `contact_id` returns the typed validation error.
- A token-collision that survives the bounded retry budget returns crm's typed
  internal error (astronomically unlikely at 32⁶ live values; it is an
  unexpected runtime condition, surfaced, never a silent duplicate and never a
  panic).
- `search` with an unknown or soft-deleted `token` is **not** an error — it
  returns an empty result set, like any other non-matching search.

**Rejected.**

- **A caller-supplied token on `save`.** Pushes uniqueness and generation onto
  the agent and invites collisions and malformed values; crm owns the identity,
  so crm mints. Rejected.
- **A dedicated `get`-by-token verb.** A second read surface for what `search`
  already models as a filtered contact lookup. Rejected in favor of the `token`
  filter.
- **Per-contact uniqueness instead of global.** Would make a bare token
  ambiguous (which contact?) and defeat the reverse lookup. Rejected; tokens are
  globally unique among live rows.
- **A longer/opaquer token or a UUID.** The token is handed to humans (printed,
  read aloud, encoded in a QR); 6 Crockford-base32 chars are short, unambiguous,
  and ample (≈1 billion values). Rejected.
- **Emitting a `token.minted` event.** Nothing in the suite consumes a mint;
  the tracked hit is the interesting event, and it originates outside crm.
  Rejected as speculative surface.

**Verification** (real substrates: real SQLite for the table/uniqueness/lookup;
the assembled MCP server the composition root wires for the verb-reachability
claim).

- R-9QOE-LQTI — `mint` for a live contact returns a token that is exactly 6
  characters, each from the lowercase Crockford base32 alphabet (`0-9a-z` minus
  `i`,`l`,`o`,`u`), and a matching live `contact_tokens` row exists for that
  contact carrying the token and the supplied `campaign`.
- R-9RWA-ZIK7 — global uniqueness: a batch of many `mint` calls returns pairwise
  **distinct** tokens, and a direct insert of a second live row with an
  already-live token is **rejected** by `uq_contact_tokens_token_live`.
- R-9T47-DAAW — `search { type:"contact", filters:{ token:T } }` returns exactly
  the contact that owns live token `T`; after that token is soft-deleted, and for
  an unknown token, the same search returns **no** contact.
- R-9UC3-R21L — minting twice for one contact with two different `campaign`
  labels yields two distinct live tokens, **both** resolving to that one contact,
  each row carrying its own campaign label.
- R-9VK0-4TSA — `mint` with a `contact_id` naming no live contact returns the
  typed not-found error and creates **no** `contact_tokens` row (row count
  unchanged).
- R-9XZS-WD9O — wiring: a `mint` call driven through the **assembled MCP server**
  (the composition root, real SQLite) creates the live token row and returns the
  token in `structuredContent`; a follow-up `search` token lookup over the same
  assembled server resolves it back to the contact — proving both the new verb
  and the new filter are connected end to end, not just unit-reachable.
