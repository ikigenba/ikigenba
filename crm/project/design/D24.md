# Decision 24 — Sales-funnel vocabularies: contact lifecycle and deal stage, via row-preserving rebuild migrations

**Context.** With the domain now governed here (product scope note), the first
domain Decision fixes the two closed vocabularies that describe where a contact
and a deal sit in the operator's sales funnel. The legacy vocabularies came from
a marketing-funnel model (`subscriber/lead/opportunity/customer` on contacts,
`lead/qualified/proposal/negotiation/won/lost` on deals) that does not fit the
operator's cold-outreach business. This Decision replaces both with the
operator's own words and preserves every existing row through the change.

**Decision.**

Two closed vocabularies change; nothing else about the entities does.

1. **Contact lifecycle becomes `prospect | customer`, default `prospect`.** A
   contact is either a **prospect** (someone the operator is pursuing) or a
   **customer** (closed, paying). The `contacts.lifecycle` `CHECK` set is exactly
   these two values and the column default is `prospect`. `subscriber`, `lead`,
   and `opportunity` are removed from the vocabulary.

2. **Deal stage becomes `contacted | interested | proposal | won | lost`,
   default `contacted`.** A deal is one sale moving through the operator's steps.
   The `deals.stage` `CHECK` set is exactly these five values and the column
   default is `contacted`. `lead`, `qualified`, and `negotiation` are removed.

3. **The derived deal `status` is unchanged in shape.** `status` remains
   never-stored, derived from stage by `dealStatus`: `won → "won"`,
   `lost → "lost"`, every other stage `→ "open"`. The `search` status filter
   keeps mapping `open` onto `stage NOT IN ('won','lost')`. `save` still rejects a
   client-supplied `status`.

4. **A forward, timestamped migration rebuilds `contacts` and `deals` in place,
   preserving every row and every child.** SQLite cannot alter a `CHECK`
   constraint, so each table is redefined by the safe rebuild sequence (new table
   with the new `CHECK` and default, copy all live and soft-deleted rows across,
   drop the old, rename), with foreign-key integrity preserved so no
   `contact_emails` / `contact_phones` / `contact_tags` / `deal_contacts` child
   row is lost. The migration is created with `bin/create-migration crm <name>`
   (UTC-timestamped, forward-only, immutable — never hand-numbered), applied once
   by the appkit runner. It **remaps** each existing value:

   | table.column        | legacy value                       | new value     |
   |---------------------|------------------------------------|---------------|
   | `contacts.lifecycle`| `customer`                         | `customer`    |
   | `contacts.lifecycle`| `subscriber`, `lead`, `opportunity`| `prospect`    |
   | `deals.stage`       | `lead`                             | `contacted`   |
   | `deals.stage`       | `qualified`                        | `interested`  |
   | `deals.stage`       | `proposal`                         | `proposal`    |
   | `deals.stage`       | `negotiation`                      | `proposal`    |
   | `deals.stage`       | `won`                              | `won`         |
   | `deals.stage`       | `lost`                             | `lost`        |

   Every existing row survives with a value legal under the new `CHECK`; the row
   count and every child row are unchanged.

5. **Validation and the guide follow the new vocabularies.** The domain
   validation that backs `save` accepts only the new sets and rejects anything
   else with crm's existing closed-vocabulary error code (D19); the `guide`
   field catalog names the new lifecycle and stage values and their defaults.
   These are the only surfaces that state the vocabulary, and they move together
   with the schema.

**Error surface.** `save` with a `lifecycle` or `stage` outside the new set
returns the closed-vocabulary domain error (D19's typed code), not a silent
coercion; the caller sees which field and which value were rejected. The
migration is transactional: it applies wholly or leaves the database untouched —
a partial rebuild is never observable. No new error types are introduced.

**Rejected.**

- **Keeping a three-stage contact funnel (`prospect | engaged | customer`).** The
  "engaged" middle overlaps a deal's own existence; the operator settled on the
  person being simply prospect-or-customer, with the active pursuit carried by a
  deal. Rejected in favor of the two-value set.
- **Renaming `lead` in place rather than replacing the set.** Would leave the
  other stale values (`subscriber`, `opportunity`) legal and the vocabulary
  half-migrated. Rejected; the set is replaced whole.
- **`ALTER TABLE` to widen the `CHECK`.** SQLite has no such operation for a
  `CHECK` constraint; the table must be rebuilt. Not a choice, a constraint of
  the engine.
- **Dropping the `CHECK` and enforcing the vocabulary only in code.** Loses the
  database-level guarantee for a greenfield-cheap constraint and invites drift
  between the code list and the stored data. Rejected; the `CHECK` stays the
  source of truth, mirrored by the validation and the guide.
- **A destructive migration that rebuilds `state/` or drops rows that don't map.**
  Every legacy value has a defined new value; the migration is row-preserving by
  construction. Data loss is unacceptable (suite rule), and unnecessary here.

**Verification** (real substrates: the real appkit migration runner over real
SQLite, and `save`/`search` exercised against a real database).

- R-9LST-2NUQ — after the migration, `contacts.lifecycle` accepts `prospect` and
  `customer` and **rejects** any other value (`lead`, `opportunity`, `subscriber`)
  with the closed-vocabulary error; a `save` that omits `lifecycle` stores
  `prospect`.
- R-9N0P-GFLF — after the migration, `deals.stage` accepts exactly `contacted`,
  `interested`, `proposal`, `won`, `lost` and **rejects** any other value
  (`lead`, `qualified`, `negotiation`) with the closed-vocabulary error; a `save`
  that omits `stage` stores `contacted`.
- R-9O8L-U7C4 — `dealStatus` derives `status` `"won"` from stage `won`, `"lost"`
  from stage `lost`, and `"open"` from each of `contacted`, `interested`,
  `proposal`; and `search {type:deal, filters:{status:"open"}}` returns deals
  whose stage is not `won`/`lost` and excludes those that are.
- R-9PGI-7Z2T — the migration applied to a database seeded with the full legacy
  spread (a contact at each of `subscriber`/`lead`/`opportunity`/`customer` with
  child emails/phones/tags, and a deal at each of
  `lead`/`qualified`/`proposal`/`negotiation`/`won`/`lost` with participants)
  preserves the exact row count of `contacts`, `deals`, and every child table,
  and remaps every value per the table above (`subscriber`/`lead`/`opportunity`→
  `prospect`, `customer`→`customer`; `lead`→`contacted`, `qualified`→
  `interested`, `negotiation`→`proposal`, and `proposal`/`won`/`lost` unchanged).
