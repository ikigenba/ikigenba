# Decision 20 — Correlation-id adoption: the nginx fragment forwards the chain id, and event appends carry it

**Decision.** crm joins the suite's correlation chain as a **pure adopter**: it
writes no correlation code and stores no telemetry. Two things change.

**(1) The nginx fragment (`crm/etc/nginx.conf`) forwards the chain id.** The
dashboard's introspection endpoint mints an `X-Correlation-Id` for every gated
route and returns it on the auth subrequest response. Each of crm's three
**gated** proxying locations — the session-gated `= /srv/crm/` landing page, the
session-gated `/srv/crm/static/` assets, and the bearer-gated `/srv/crm/` prefix
— captures it and forwards it, exactly as it already does for owner identity:

```nginx
auth_request_set $crm_correlation $upstream_http_x_correlation_id;
proxy_set_header X-Correlation-Id $crm_correlation;
```

The `proxy_set_header` is the load-bearing half: nginx does not forward an
inbound client header as a proxy header unless explicitly set, and the last
`proxy_set_header` for a name wins, so this **replaces** any client-supplied
`X-Correlation-Id` — the same identity-hygiene argument the fragment's existing
comment makes for `X-Owner-Email`. A client cannot graft itself onto another
chain.

crm's one **ungated** proxying location, the PRM bootstrap
`= /srv/crm/.well-known/oauth-protected-resource`, has no auth subrequest and
therefore no minted id to capture. It sets the header **empty** so the chassis
mints a fresh id for that request:

```nginx
proxy_set_header X-Correlation-Id "";
```

The two non-proxying locations — `= /srv/crm/feed` (a bare `return 404`) and
`@crm_authn_500` — forward nothing upstream and are untouched. The invariant the
fragment must hold, stated so a later edit cannot quietly break it: **every
location that proxies to the crm loopback upstream sets `X-Correlation-Id`**,
to the captured value when gated and to the empty string when not.

**(2) Event appends carry the chain id.** `correlation_id` becomes a first-class
outbox column and wire-envelope field populated by eventplane from the calling
context, which changes `Outbox.Append` to take a context:

```go
func (o *Outbox) Append(ctx context.Context, tx *sql.Tx, ev Event) error
```

crm's single emit site — the contact-event loop inside `Service.Save`
(`internal/crm/service.go`) — already holds the request context and passes it
through. This is a compile-caught change: crm does not build against the new
eventplane until the call is updated. Nothing else about crm's four first-wave
contact events changes — kinds, subjects (`/<contact id>`), payload structs, and
the reflection `Registry` (D18) are all untouched, and **no crm payload carries
a correlation field**: the id rides the envelope, superseding the old
payload-field convention.

**Everything else arrives free.** MCP `request` records (`mcp:<tool>`), plain
HTTP request records, param capture under the suite's byte budgets, and
`lifecycle` start/stop records are emitted by the rebuilt appkit chassis with no
crm-side code. crm re-proves none of that; it is appkit's coverage. crm
constructs no `http.Client`, so the Router-provided instrumented client is not a
crm concern, and crm originates no self-driven work (no timer, no run spawn, no
event consumption), so it never mints a **root** id — every chain it takes part
in was rooted at the edge and arrives on the header.

**Rejected.**
- **Reading the client's `X-Correlation-Id` when the auth subrequest returns
  none** — would let a public caller choose its own chain id on the PRM path.
  Stripping to empty and letting the chassis mint is the only safe default.
- **Carrying the correlation id in the contact-event payloads** — duplicates the
  envelope field, forces a payload-shape change on every consumer, and is
  exactly the convention the suite is retiring.
- **A crm-side correlation package or recorder** — every behavior here belongs
  to appkit or eventplane; a crm copy would drift and would re-prove chassis
  coverage.
- **Leaving the ungated PRM location without an `X-Correlation-Id` line** — it
  would "work" (the chassis mints when the header is absent) but leaves the
  injection hole open, and leaves the fragment without a uniform, greppable
  invariant.

**Verification.**
- R-X9B0-30E7 — Reading the shipped `crm/etc/nginx.conf` from disk: each of the
  three gated locations (`= /srv/crm/`, `/srv/crm/static/`, `/srv/crm/`) carries
  both `auth_request_set $crm_correlation $upstream_http_x_correlation_id;` and
  `proxy_set_header X-Correlation-Id $crm_correlation;` — a location carrying
  the capture but not the `proxy_set_header` (the client-overwrite half) fails.
- R-XAIW-GS4W — In the same fragment, the ungated PRM location
  `= /srv/crm/.well-known/oauth-protected-resource` carries
  `proxy_set_header X-Correlation-Id "";` — the empty literal specifically, not
  a captured variable and not an absent line.
- R-XCYP-8BMA — In the same fragment the number of
  `proxy_set_header X-Correlation-Id` lines equals the number of
  `proxy_pass http://127.0.0.1` lines (4 and 4): adding a location that proxies
  to the loopback upstream without setting the header fails this count.
- R-XE6L-M3CZ — Against a real temp SQLite with the migrations applied, a
  `Service.Save` of a contact driven with a context carrying correlation id
  `X` writes outbox rows whose `correlation_id` column is exactly `X` for every
  event the save emits; the same save driven with a bare context writes rows
  whose `correlation_id` is empty rather than a value crm invented.
