# D18-space-move

`space move` puts a space on a new instance launched from the current launch
template and carries everything the old host held across to it: every app's
data, the host's own configuration store, its users, groups, keys, homes,
`/srv`, its certificate, and its sshd host keys. The space keeps its names,
its role, and its secrets; only its instance and its Elastic IP change. It
lives in `internal/spacemove` and follows the session `space create` (D07)
follows: usage errors first, then the checkout, then the release, chosen
exactly as create chooses it, then the root file, then the `<space>` operand
through the one parser (D04), then one cloud session whose first call is STS
(D03).

Before it prints or changes anything it checks what create checks of the
platform, the hosted zone, the launch template, and the permissions boundary
named after the root, and finds the space's one active instance through
`cloud.LookupSpace`, which refuses a label with none and a label with two. The
instance must be `running` or `stopped`; any state between is refused as
`space status` refuses a host it cannot reach. Whether the space holds the
apex, and the old instance's active Elastic IP, are read here too, so a move
knows before it starts what it will tag and whether the root must follow it.
Then the `account` and `domain` lines, and the release is built with
`build.Suite` (D08) before anything changes, so a move that cannot build
leaves the space where it was.

The old host goes first. A stopped one is started, as `space start` starts
it, because only a running host can take its final backup. `sudo systemd-run
--quiet --wait --pipe --collect opsctl retire` runs on it on every move,
through the opsctl the host already has, as destroy runs it (D06).
That opsctl may be a release older than the one being
moved to, whose host backup lacks what the new release's `host restore`
reads, such as the host's accounts; so the `backup` step then has the
release's own opsctl take one more host backup on the old host, and that
backup, the newest in the bucket, is the one the new host is restored from.
The old host may not be arm64, which is all a release is built for, so the
step reads its architecture with `uname -m` and compiles the release's
opsctl for it (D08's `Tool`) into the move's temporary directory, copies it
to a fresh temporary file on the host, runs `host backup` with it as root,
and removes the file again. The binary is the same one code path on an
arm64 host, and it never lands in `dist/` or a release.
Then the old instance is stopped, and it and its Elastic IP are tagged
`Retired` in one request (D03's `TagRetired`) with the time the clock gave.
Neither is removed: they stay, stopped and retired, as the way back, until
`space destroy` removes them.

The new instance is launched with the space's existing role and instance
profile, given a new Elastic IP, and waited for as create waits for it. The
release is copied and unpacked as create does it (D16's `Put`), and from then
on every opsctl command on the new host is the release's own, by absolute
path. It sets only the five keys derived from the root, the zone and the
space (D10's `Configure` with no email and no periods); `host restore` over
the newest host backup then brings back the old store, `acme.email`, the
backup periods and `host.apex` among it, and the five keys are set again so
devctl's values win. Unlike create, nothing deletes `host.apex`: a space that
held the apex still holds it. A move whose bucket holds no host backup stops
there, since the `backup` step has just written the newest one and a host
without it has neither an address for the CA nor the old host's data; a
bucket holding only an accounts archive, a host tarball's sibling, holds no
host backup. Only then are the space's two
records pointed at the new address, so the new host answers at the space's
names with the old host's identity; then `init`, each app's data put back as
create puts it back, and the release activated. A space that held the apex
has the root's record pointed at the new address last (D14's `PutRecord`).

The host key changes part-way. The new host is launched with a key of its
own and presents the old host's key from its host restore on, so devctl
never records the launch key where the developer's ssh would later trust it.
Every connection to the new address goes through a `host.Host` whose
`KnownHosts` names a file in a temporary directory of the move's own: one
file up to and including the host restore, and a second, fresh one after it,
in which ssh records the restored key. The old host, whose key the
developer's own known hosts already hold, is reached without one. The
directory is removed when the move returns, however it ends. A failure stops
the move where it is and undoes nothing, as create's and destroy's do.
