# D07-space-create

`space create` makes one complete space at one label under the root and
deploys a release to it. It follows the session every space-taking command
follows: usage errors first, then the checkout, then the release, then the
root file, then the `<space>` operand through the one parser (D04), then one
cloud session whose first call is STS (D03). The release is what
`--release` names, in any form `deploy` takes (D16's `Resolve`), or without
it the newest `r<N>` tag in the local repository (D04's `NewestRelease`);
with neither there is nothing to deploy and create refuses before any cloud
call. Before it prints or changes anything it establishes that the platform
is there and the name is free: the hosted zone, the launch template, and the
permissions boundary named after the root exist, no `NS` record delegates the
space's name away, no instance is tagged for the space, and no role or
instance profile of the space's name was left behind.

Then it builds the release with `build.Suite` (D08), before anything is
created in the account, so a create that cannot build leaves nothing behind.
It pushes the secrets of the apps the release holds, read from the
developer's keyring as `secrets push` does; makes the role; launches the
instance; gives it an Elastic IP; writes its two `A` records; and waits for
the host's first boot. A new host has no opsctl until the release reaches it,
so the release is copied and unpacked there as `deploy` does (D16's `Put`),
and everything create then asks of the host is asked of that release's own
opsctl by its absolute path: it sets the ten host keys, restores the space's
own host backup when the bucket holds one, runs `init`, puts each app's data
back when a host backup was found, and last activates the release, with the
tag as its label. Each of devctl's lines is one step; activate's lines are
opsctl's, copied as they are written; the last line is the space domain and
the address. Failures leave completed work for destroy to clean up.

A freshly created instance profile is not visible to EC2 the instant IAM
returns it, so the `role` step does not finish until the profile is provably
usable: after attaching the role it waits, through `space.WaitLaunchReady`,
for a dry-run launch to be accepted, and only then writes `role: ok`. The
`instance` step's real launch therefore never races the profile's
propagation.

The role and its instance profile are named exactly the space domain
(`space.RoleName`). IAM documents a `RoleName` of at most 64 characters, and a
63-byte label under the root would exceed it, so create refuses such a name
before it connects. The role's one inline policy, `space.PolicyName`, is the
document `space.PolicyDocument` (D06) builds from the root, the zone id, and
the space; what it grants is D06's contract, and create only writes it with
`apex` false, so the fresh role reads the space's parameters, works under the
space's label in the bucket named after the root, and writes `TXT` records at
the space's own two names in the zone and nothing else in Route 53. That is
what proving ownership for its certificate takes. Create writes the
space's `A` records itself, with the developer's identity, so the host never
needs an `A`-record write, and it never enumerates zones, since opsctl
carries the zone id in `dns.zones`. `apex set` and `apex clear` (D14)
regenerate the same document with `apex` true or false, which adds or removes
the one name outside the space's subtree, `_acme-challenge.<root>`, that only
the holder of the apex may prove.

The `restore` step runs on every create. It lists `<label>/host/` in the
bucket; when nothing is there the line says so, the space is new, and no
app's data is looked for. When a backup is there, `host restore` puts the old
host's certificate and store back, the ten keys are set again so what create
was told wins over the backup's copy, and `host.apex` is deleted so a rebuilt
host never holds the apex until `apex set` says so. The restore's documented
selection is the newest backup, so the key the line reports is the newest
object devctl listed; nothing opsctl prints is parsed. After `init`, a create
that found a host backup puts each app's data back before any app runs: for
each app in the release, in name order, whose prefix `<label>/<app>/` holds
anything, the release's opsctl runs `restore <app>`, one `restore` line each,
and an app with nothing there gets a line that says so. Activate starts every
app, and an app that finds no database makes and seeds one, so restoring
first is what lets each app start over its own data.
