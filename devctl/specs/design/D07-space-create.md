# D07-space-create

`space create` makes one complete space at one label under the root and
deploys a release to it. It follows the session every space-taking command
follows: usage errors first, then the checkout, then the release, then the
root file, then the `<space>` operand through the one parser (D04), then one
cloud session whose first call is STS (D03). The release is what
`--release` names, in any form `deploy` takes (D16's `Resolve`), or without
it the newest `release-<N>` tag in the local repository (D04's `NewestRelease`);
with neither there is nothing to deploy and create refuses before any cloud
call. `--apex <app>` and `--no-apex` say what create does with the store's
`host.apex` after the restore; together they are a usage error. Before it
prints or changes anything it establishes that the platform is there and the
name is free: the hosted zone, the launch template, and the permissions
boundary named after the root exist, no `NS` record delegates the space's
name away, no space is at the label, and no role or instance profile of the
space's name was left behind. A space is at the label while an instance that
is not terminated or an Elastic IP carries it, so the lookup is D03's
`LookupSpace`: a label a failed replace left with only its address is
refused for that address, which is the space's for its whole life until
`space destroy` releases it, and a label carrying two instances or two
addresses is refused as every lookup refuses it.

Then it builds the release with `build.Suite` (D08), before anything is
created in the account, so a create that cannot build leaves nothing behind.
An app `--apex` names must be one the release holds, which is known once the
release is built, so that check comes right after the `build` line. It pushes
the secrets of the apps the release holds, read from the developer's keyring
as `secrets push` does; makes the role; launches the instance; gives it its
Elastic IP; writes its two `A` records; and waits until the developer's own
resolver answers the space domain with that address (`resolve`, D06's
`WaitResolves`). Every connection to the host is by name,
`ec2-user@<space domain>`, so no ssh runs before the name resolves, and a
name that does not resolve in time ends the create as a DNS failure with no
ssh at all.

A new host has no opsctl until the release reaches it, so the release is
copied and unpacked there as `deploy` does (D16's `Put`), and everything
create then asks of the host is asked of that release's own opsctl by its
absolute path: it sets the ten host keys, restores the space's own host
backup when the bucket holds one, runs `init`, puts each app's data back when
a host backup was found, and activates the release, with the tag as its
label. That stretch, from the `host` step through activate, is exported as
two functions, `SetUpHost` (`host`, `copy`, `unpack`, `opsctl`, `restore`)
and `FinishHost` (`init`, each app's `restore`, activate), driven by one
`Launch` value, so `space replace` (D18) runs exactly create's path by
calling the two in turn. Create's own steps sit outside them: between the two
it runs `known_hosts`, the `apex` step, and the apex `role` step, and after
`FinishHost` the `record` and `previous` steps and its last line. Replace
calls neither the in-between steps nor the closing ones, sets
`RequireHostBackup` so that a bucket with no host backup ends it at the
`restore` step, and writes its own last line. `Resolve`, the `resolve` step,
is exported beside them so the two commands' `resolve` lines cannot differ.
Each of devctl's lines is one step; activate's lines are opsctl's, copied as
they are written; the last line is the space domain and the address.
Failures leave completed work for destroy to clean up.

A freshly created instance profile is not visible to EC2 the instant IAM
returns it, so the `role` step does not finish until the profile is provably
usable: after attaching the role it waits, through `space.WaitLaunchReady`,
for a dry-run launch to be accepted, and only then writes `role: ok`. The
`instance` step's real launch therefore never races the profile's
propagation.

The role and its instance profile are named exactly the space domain
(`space.RoleName`). IAM documents a `RoleName` of at most 64 characters, and a
63-byte label under the root would exceed it, so create refuses such a name
before it connects. The role's one inline policy, `space.PolicyName`, is the
document `space.PolicyDocument` (D06) builds from the root, the zone id, and
the space; what it grants is D06's contract, and the `role` step writes it
with `apex` false, so the fresh role reads the space's parameters, works
under the space's label in the bucket named after the root, and writes `TXT`
records at the space's own two names in the zone and nothing else in Route 53.
Create writes the space's `A` records itself, with the developer's identity,
so the host never needs an `A`-record write, and it never enumerates zones,
since opsctl carries the zone id in `dns.zones`.

The `restore` step runs on every create. It lists `<label>/host/` in the
bucket; when nothing is there the line says so, the space is new, and no
app's data is looked for. When a backup is there, `host restore` puts the old
host's certificate, store and sshd host keys back, and the ten keys are set
again so what create was told wins over the backup's copy. The restored
store keeps whatever `host.apex` the backup held. The restore's documented
selection is the newest backup, so the key the line reports is the newest
host backup devctl listed, by the time its name carries; nothing opsctl
prints is parsed. After `init`, a create that found a host backup puts each
app's data back before any app runs: for each app in the release, in name
order, whose prefix `<label>/<app>/` holds anything, the release's opsctl
runs `restore <app>`, one `restore` line each, and an app with nothing there
gets a line that says so. Activate starts every app, and an app that finds no
database makes and seeds one, so restoring first is what lets each app start
over its own data.

What the two listings hold at once is bounded. D03's `ListObjects` hands
its caller one page at a time, at most `cloud.ObjectPageSize` objects, and
fetches the next only when the caller asks for it. `SetUpHost` reads every
page of `<label>/host/`, because the newest host backup can be on any page,
and holds only the page in hand and the newest host backup seen so far, one
`cloud.Object`. `FinishHost` needs to know only whether `<label>/<app>/`
holds anything, so for each app it asks for one page and stops there,
holding that page and one flag, and drops both before the next app's.

The host key changes part-way. The new host is launched with a key of its
own, and when a host backup is found it presents the old host's key from its
host restore on; had the developer's known hosts recorded the launch key
under the name, the next connection would be refused as a changed host key.
Once every check has passed and before it prints anything, create makes a
temporary directory of its own, and every connection up to and including the
host restore goes through a `host.Host` whose `KnownHosts` is the file
`known_hosts.launch` in it, keyed by the name. From the host restore on, or
from the `restore` line when there was no backup, the host has no
`KnownHosts`, so the developer's own known hosts serve. The directory is
removed when create returns, however it ends. The `known_hosts` step then
squares the developer's file with the host: a host that found no backup
keeps its launch key, which an entry an earlier host at the same name left
would contradict, so create runs `ssh-keygen -R <space domain>` against the
developer's default known hosts file (ssh-keygen(1), `-R hostname`), before
any connection through that file, and reports the name removed. ssh-keygen
fails on a file that does not exist, so create first stats
`$HOME/.ssh/known_hosts` through `Deps.Stat`, the only look devctl takes
into the developer's home and made through the seam; a file that does not
exist holds nothing to remove, so ssh-keygen is not run and the line is the
one a file without an entry for the name gets, and any other stat error
fails the step as a failing ssh-keygen does. A host that restored a backup
presents the keys the backup holds, so nothing is removed
and the line says `kept`. ssh-keygen's output is bounded by the entries for
one name and is discarded; a non-zero exit is a failure whose detail quotes
its stderr.

The store states the apex and create makes the account match it. Whether the
store holds the apex is decided once, after the `known_hosts` step: with
`--apex <app>` it does, the `apex` step having set `host.apex` to the app
(D10 R-DYY1-CBDS); with `--no-apex` it does not, the `apex` step having
deleted it; with neither, a fresh store has no `host.apex`, and a restored
store is asked with one `config get host.apex` by the release's opsctl (D10 R-DYY1-CBDS), whose
documented exit 1 means the key is unset; that question writes no line. When
the store holds the apex, create does what `apex set` does with `apex set`'s
own pieces (D14) and in its order, restating none of them: `CheckHolder`
finds the holder and refuses as `set`'s preflight refuses, then `GrantApex`
writes the second `role` line before `init`, so the certificate `init` keeps
or obtains may carry the root, and after activate `PointRoot` writes the
root's `A` record to the space's address and `ClearPrevious` clears the space
that held it before, or reports none. When the store does not hold the apex,
create does nothing about it.
