# D18-space-replace

`space replace` puts a space on a new instance launched from the current launch template, at the address the space has for its whole life, and carries everything the old host held across to it: every app's data, the host's own configuration store, its users, groups, keys, homes, `/srv`, its certificate, and its sshd host keys. The space keeps its names, its Elastic IP, its records, its role, its secrets, and whatever it holds of the apex; only its instance changes, except that a space with no Elastic IP is first given one and its records pointed at it, as below. It lives in `internal/spacereplace`, which D06 dispatches to, and follows the session `space create` (D07) follows: usage errors first, then the checkout, then the release, chosen exactly as create chooses it, then the root file, then the `<space>` operand through the one parser (D04), then one cloud session whose first call is STS (D03).

Before it prints or changes anything it checks what create checks of the platform, the hosted zone, the launch template, and the permissions boundary named after the root, and finds the space through `cloud.LookupSpace`, which refuses a label with nothing, a label with two instances, and a label with two Elastic IPs. A label with only its Elastic IP is a space, left so by a replace that could not launch, and replace acts on it. A label with an instance and no Elastic IP is a space created before every space had one, and replace acts on it too. A host that must take its final backup has to be running or stopped; any state between is refused. Then the `account` and `domain` lines, and the release is built with `build.Suite` (D08) before anything changes, so a replace that cannot build leaves the space where it was.

Replace is strictly serial and the label never carries two instances. The old host goes first. A stopped one is started, as `space start` starts it, because only a running host can take its final backup. The `retire` step runs `opsctl retire` on it through the opsctl the host already has, as destroy runs it (D06), reaching it by name through the developer's own known hosts; the host backup it writes is the newest in the bucket and the one the new host is restored from, readable by the release being deployed by the expand-then-contract rule. `--no-backup` skips `retire` and makes no connection to the old host, so a stopped one is not started; the new host is then restored from the newest backups already kept. A label with no instance has nothing to retire, and nothing to terminate either, so its `instance` line names only the new instance, in the form create's has. For a space that has its Elastic IP, the `address` step after `retire` disassociates it from the old instance, the `instance` step terminates the old instance, waits until it is terminated, and only then launches the new one with the space's existing role and instance profile, and the second `address` step associates the same Elastic IP with the new instance. No address is allocated or released and no record is written: the space's two `A` records, and the root's record when the space holds the apex, already point at the address.

A space with no Elastic IP is the one exception, by the owner's decision, to the rule that only `space create` allocates a space's address and writes its records: its first replace gives it both, once, for a space created before every space had an Elastic IP, and from then on it has its address for life like any other. Right after `build`, or after `start` for a stopped space, and before `retire`, replace allocates an Elastic IP, tagged as create tags it, and associates it with the old instance, writing create's `address` line; writes the space's two `A` records to point at it with D06's `PutRecords` and waits for `INSYNC`, writing create's `records` line; and waits with create's `Resolve` until the developer's resolver answers the name with it, since the records pointed at the instance's own public address until then. Only after that `resolve` line does anything reach the old host by name: the ssh wait `start` otherwise makes on a stopped host, then `retire`. There is no disassociation: terminating the old instance ends the association, and the second `address` step associates the same Elastic IP with the new instance, as for any replace.

The `resolve` step after the second `address` step is create's own (D07's `Resolve`) and passes at once, because the name resolves to the address already; it is what makes the first connection to every new host follow the name. From the `host` step through activate replace runs exactly create's path, by calling D07's `SetUpHost` and `FinishHost` with one `Launch`: the release is copied and unpacked, the release's own opsctl sets the five keys derived from the root, the zone, and the space, with no email and no periods, the `restore` step restores the newest host backup, which a replace requires, then `init`, each app's data, and activate. Replace has no `known_hosts`, `apex`, `role`, `record`, or `previous` step and touches nothing about the apex: the restored store keeps the apex key its backup held, the restored certificate carries what it carried, and the role is the one it was.

The host key changes part-way. The new host is launched with a key of its own and presents the old host's key from its host restore on. Once every check has passed and before it prints anything, replace makes a temporary directory of its own, and every connection to the new host up to and including the host restore goes through a `host.Host` whose `KnownHosts` is the file `known_hosts.launch` in it, keyed by the name; from the host restore on, the developer's own known hosts serve, which already hold the old host's key for the name. Replace never runs `ssh-keygen`. The directory is removed when replace returns, however it ends. A failure stops the replace where it is and undoes nothing; the way on is to replace again, with `--no-backup` when the space's one instance is a half-built host.

Replace holds fixed-size data only: the one `Space` the lookup answers, the one `Address` an allocation returns, the release's manifests, which the release bounds, and a handful of names and ids. The release file reaches the host through D16's `Put`, the backups move on the host and never through devctl, activate's output is copied as it is written (D16), and the listings are D07's, one prefix at a time.
