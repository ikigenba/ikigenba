# D20-events-delivery

The broker delivers each event it has recorded to every service that accepts it, one HTTP request per delivery, over that service's unix socket. Both ends of that hop live in package `events`, as both ends of the emit hop do (D19): the delivery handler a consuming service mounts, and `Send`, which the broker calls. A service also publishes what it emits and what it accepts, so the broker knows where to deliver and an agent can read the bus's shape without reading code; that is the declarations handler.

## Handlers and outcomes

A consuming service registers a `Handler` per event name in a `Handlers` map, or one under `*` for every event. A name's own handler wins over `*`, so a service can treat one event specially and pass everything else to a general handler. Keys are fixed at start-up: the delivery and declarations handlers panic on a key that is neither a valid event name (R-GD26-8ONE) nor `*`, and on a nil handler, so a registration mistake surfaces when the service starts rather than as a missed delivery. Both take a copy of the map, so changing it later changes nothing.

A handler receives a `Delivery`: the delivered event and the attempt number, 1 for the first delivery and one more for each retry, so a handler that is not idempotent can tell a retry from a first sight. It answers with an `Outcome`, built by one of three constructors: `events.OK()` (handled), `events.Skip()` (not for this service, or nothing to do), or `events.Fail(msg)` (failed, with a message for the broker's log). The outcome's kind and message are read back with `Kind` and `Message`; the kind is one of the strings `events.OutcomeOK`, `events.OutcomeSkip`, and `events.OutcomeError`, which are also its spelling on the wire. `Outcome` keeps its fields unexported so that an ok or skip outcome can never carry a message, and it is comparable, so a test checks a handler with `got == events.OK()`. The zero `Outcome` is an error with an empty message: a handler that forgot to choose an outcome is retried, not silently counted as handled.

## The delivery request and its answer

A delivery is `POST` to `events.EventsPath` (D19) with `Content-Type: application/json` and, as the body, the delivered event's JSON form (R-GMTD-AUKY) with one more member, `attempt`, last. The delivery handler checks, in order, the method (405), the content type (415), the size (413), and the body (400), as telemetry's ingest handler does (D13), and then finds the handler for the event's name; with none, it answers 404 and calls nothing. A 404 means "not for me", so the broker counts it as a skip rather than a failure.

The size limit is `events.MaxDeliveryBytes`, twice `MaxEventBytes`, and it counts the whole body, `attempt` included. The broker re-encodes an event it accepted at up to `MaxEventBytes` and adds `seq`, `received` and `attempt`; a limit equal to the ingest limit would refuse such an event at every consumer for ever.

The handler runs with a context derived from the request's context, so the request id and caller the telemetry middleware (D14) put there, and the request's cancellation, reach it. Before calling the handler, the delivery handler adds the delivered event's id and depth as the cause (R-GAMD-H560), so an event the handler emits with that context names the delivered event as its cause and has its depth plus one (D18). The delivery carries no user identity; the delivery handler is mounted inside `telemetry.Middleware` and outside `identity.Require`.

The answer is the outcome: 200 with `{"outcome":"ok"}` or `{"outcome":"skip"}`, 500 with `{"outcome":"error","error":"<message>"}`, each with `Content-Type: application/json`. Every other status has an empty body. The error message is cut to its first `MaxEventBytes / 8` bytes (8192), backing off to the start of a character so a valid message stays valid text: `encoding/json` spells a byte as at most six, so the whole body stays under `MaxEventBytes`, the cap `Send` puts on an outcome body, and every answer the delivery handler writes is one `Send` reads as an outcome. A message is for the broker's log, and 8 KiB is plenty for one. A handler that panics is answered as a failure, with the fixed message `events.PanicMessage`, and the service goes on serving: as with an MCP tool (D08), a panic is a bug whose reproduction starts from the request id, and its value is free text that does not travel.

## Sending a delivery

`events.Send` is the broker's half. It takes the client to send with, normally `telemetry.SiblingClient` over `telemetry.SocketTransport` of the consumer's socket (D14), the consumer's service name, which becomes the host of the URL `http://<target>/events`, and the delivery. A delivery that could never be accepted (an event that is not a valid delivered event, an attempt below 1, a body past `MaxDeliveryBytes`) is refused with an error wrapping `ErrRejected` (D18) and no request.

The `Result` says what came back. When the consumer answered with an outcome (200 or 500 with a well-formed outcome body) or with 404, `Send` returns a nil error and the outcome, 404 as `events.Skip()`; `Result.Status` tells a 404 skip from one the handler chose. Anything else is an error: the transport failed, the body was not a well-formed outcome, or the status was another one. The broker then retries by its own policy, and `Result.Status` (0 when no response came) lets it treat, say, a 415 as permanent.

A 429 or 503 may carry `Retry-After` (RFC 6585 §4; RFC 9110 §15.6.4), whose value is either a number of seconds or an HTTP-date (RFC 9110 §10.2.3). `Send` honours only the seconds form, as `Result.RetryAfter`; a date, or anything else, gives 0, meaning the broker's own backoff. Converting a date would need a clock `Send` does not have, and the consumers are this suite's own services, which send seconds.

## The declarations

`events.DeclarationsHandler` answers `GET` on `events.DeclarationsPath` (D19) with what the service emits, read from its emitter's `Emits` (D18), and what it accepts, the keys of its handlers. Emissions are sorted by event name with their attributes in the order declared; accepted names are sorted, so `*` (which sorts before every event name) comes first when present, and the named handlers beside it still appear, since a name's own handler is not the wildcard's. A service that emits nothing or accepts nothing passes nil for that argument, and the list is `[]`, never `null`. Every other method is answered 405 with `Allow: GET`; `HEAD` is not served, as a declarations reader always wants the body.

## Consumer tasks

A producer (repos-like) builds its emitter (D18) with `Config.Emits` set to `[]events.Emission{{Event: "repo.pushed", Attrs: []string{"repo", "ref", "old", "new"}}}`, mounts `events.DeclarationsHandler(em, nil)` at `events.DeclarationsPath`, and emits `repo.pushed` after a push. A `GET` answers `{"emits":[{"event":"repo.pushed","attrs":["repo","ref","old","new"]}],"accepts":[]}`.

A consumer (scripts-like) builds `h := events.Handlers{"*": func(ctx context.Context, d events.Delivery) events.Outcome { ...; return events.OK() }}`, mounts `events.DeliveryHandler(h)` at `events.EventsPath` and `events.DeclarationsHandler(em, h)` at `events.DeclarationsPath`, both outside `identity.Require` and inside `telemetry.Middleware`. A handler that emits a follow-up with its `ctx` links it to the delivered event; one that cannot act returns `events.Fail("script not found")`.

The broker, having recorded an event as a valid delivered event (D17, D19), finds each accepting consumer's services-file entry, builds `client := telemetry.SiblingClient(w, entry.Name, telemetry.SocketTransport(entry.Socket))`, and calls `res, err := events.Send(ctx, client, entry.Name, events.Delivery{Event: e, Attempt: n})`. With a nil `err` it records `res.Outcome.Kind()` and `res.Outcome.Message()`; with `errors.Is(err, events.ErrRejected)` it gives up; otherwise it retries after `res.RetryAfter` when that is positive and after its own backoff when not.

A service's test calls its handlers directly with `events.Delivery{Event: e, Attempt: 1}` and a context built by `events.NewContext`, comparing the result with `events.OK()`; or serves `events.DeliveryHandler(h)` with `httptest`, posts a delivery body, and reads the outcome back with `events.Send` over the test server's client, with no clock needed.
