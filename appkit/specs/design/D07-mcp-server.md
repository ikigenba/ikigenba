# D07-mcp-server

A service offers its tools to MCP clients through one `mcp.Server`. The service builds it with `mcp.NewServer`, naming itself and its release version and handing it the service's telemetry writer (D12), registers its tools on it (D08), and mounts it on the same mux as its pages, the whole mux wrapped in `identity.Require` (D06): `mux.Handle("/mcp", srv)`. The server is an `http.Handler` that speaks the Model Context Protocol over the Streamable HTTP transport. It ignores the URL path, so the consumer chooses where to mount it; the gateway mounts it at `/mcp` and under `/mcp/`.

This document is the server's transport and protocol: which HTTP requests it accepts, how it parses them, which protocol revision serves each one, the methods it answers, and the HTTP status of every answer. What a tool is, how its arguments are decoded, how its result is built, and when registration panics belong to D08; how a tool's schemas are derived belongs to D09; the client belongs to D10. Wire facts below cite the primary sources collected for this design: S26 is the 2026-07-28 specification, S1125 the 2025-11-25 one, S0618 the 2025-06-18 one, TS26 / TS1125 / TS0618 their `schema.ts`, and JR the JSON-RPC 2.0 specification.

## Two protocol families, one server

MCP changed shape in 2026-07-28: there is no `initialize` handshake any more, every request carries its protocol version and client capabilities in `params._meta`, the server answers `server/discover`, and `ping` is gone (S26 changelog, S26 basic/versioning). Clients in the field still speak 2025-11-25 and 2025-06-18, which open with `initialize`. The server speaks both families, chosen per request, and a tool handler never learns which one served it. The spec itself sanctions this: "A request carrying modern per-request `_meta` is served statelessly according to this revision. An `initialize` request selects legacy semantics" (S26 basic/versioning).

The rule for each POST, in order:

- A request whose `params._meta` carries `io.modelcontextprotocol/protocolVersion` is served on the 2026 path. The only modern version served is `2026-07-28`; any other value is answered `400` with `UnsupportedProtocolVersion` (`-32022`) and `data: {supported, requested}` (S26 basic/transports/streamable-http#protocol-version-header, TS26).
- Otherwise a request whose method is `initialize` is legacy.
- Otherwise the `MCP-Protocol-Version` header decides. `2026-07-28` without the `_meta` fields is a malformed modern request: `400` with `-32602` (S26 basic#meta). `2025-11-25` and `2025-06-18` are legacy. Any other value is answered `400` with `-32022`: the legacy text requires `400` for an unsupported header value but names no code (S1125 basic/transports#protocol-version-header), so the server uses the modern code for one consistent answer — a choice.
- When the header is absent the request is legacy. The legacy text says a server without the header "SHOULD assume protocol version `2025-03-26`"; this server does not implement 2025-03-26, so it serves such a request with the shapes it serves 2025-06-18 rather than rejecting it — best-effort service, recorded here as a choice.

The two legacy revisions get the same answers, apart from the version `initialize` echoes. Everything the server emits on the legacy path — `Implementation` with `name` and `version`, `ServerCapabilities.tools`, the `Tool` members D08 emits, `CallToolResult` — has the same shape in TS0618 and TS1125, so there is nothing to vary.

On the 2026 path the transport also carries the request's identity in headers, and the server checks them against the body as S26 requires (basic/transports/streamable-http#server-validation): `MCP-Protocol-Version` must equal the `_meta` version, `Mcp-Method` must equal `method`, and for `tools/call` `Mcp-Name` must equal `params.name`, after decoding the `=?base64?…?=` sentinel (#value-encoding). A missing or different value is `400` with `HeaderMismatch` (`-32020`). The server decodes the sentinel as standard Base64 with padding (RFC 4648 section 4), which is what the spec's own examples use: `PT9iYXNlNjQ/bGl0ZXJhbD89` contains `/`, which only the standard alphabet has, and `SGVsbG8sIOS4lueVjA==` is padded (S26 #value-encoding). D10's client produces the same encoding. A header value the spec calls invalid is also `400` with `-32020` (S26 #server-validation: "a header value contains invalid characters"). The server reads that as any byte outside printable ASCII, a sentinel that is not valid Base64, or one that decodes to bytes that are not UTF-8. `io.modelcontextprotocol/clientCapabilities` is required (S26 basic#meta); its absence is `400` with `-32602`. `io.modelcontextprotocol/clientInfo` is optional and ignored.

## No sessions, no streams

The server keeps no state between requests. It never issues `Mcp-Session-Id` (optional in S0618/S1125, removed in S26) and ignores one a client sends; it ignores `Last-Event-ID`. A legacy client may send any request without having sent `initialize` first, and is answered the same as after one: the server cannot tell and does not try. `GET`, `DELETE`, and every other non-POST method are `405 Method Not Allowed` with `Allow: POST` — the answer each revision permits for a server that offers no stream and no session termination (S1125 #listening-for-messages-from-the-server, S1125 session DELETE, S26 #earlier-streamable-http-revisions). Every POST carrying a request is answered with exactly one `application/json` body; the server never answers `text/event-stream`, which every revision permits (S26 and S1125 streamable-http: "either"). It does not check `Accept`: no revision names a status for a wrong one.

A POST carrying a notification is `202 Accepted` with no body, on either path, whatever its method (S26, S1125, S0618 streamable-http). The only notification a client sends this server in practice is legacy `notifications/initialized`; S26 defines none over HTTP and leaves notification header requirements undefined, so the server checks no header on a notification. A legacy client may also POST a JSON-RPC response (S1125: "a single JSON-RPC request, notification, or response"); the server has sent no request, so it accepts and ignores it with `202`. S26 forbids client-sent responses, so one that arrives with a header other than a legacy version is `400`.

## Before parsing

The server rejects a request at the transport, in this order, before it reads the body as JSON:

1. A method other than POST: `405`.
2. An `Origin` header that does not name the request's own host: `403`. Every revision requires the server to validate `Origin`; S1125 and S26 name `403` (#security). The rule: a present `Origin` matches exactly when it is `<scheme>://<host>` with the part after `://` equal to the request's `Host`, compared without regard to letter case. `null`, or anything else, mismatches. A request with no `Origin` passes, as non-browser clients send none. This is the second line of defence after the session cookie's `SameSite=Lax`.
3. A `Content-Type` whose media type is not `application/json` (parameters such as `charset` allowed): `415`. No revision names a status for this; `415` is HTTP's own answer.
4. A body longer than 1 MiB (1048576 bytes): `413`, decided before any parsing.

Each of `403`, `413`, and `415` carries a JSON-RPC error response with no `id`, which S1125 and S26 permit for the `403` ("MAY comprise a JSON-RPC error response that has no `id`"); the server answers all three alike with code `-32600` and a fixed message. The `405` has an empty body.

## Parsing

The body must be one JSON value (`-32700` Parse error otherwise) that is a single JSON-RPC message object (`-32600` Invalid Request otherwise): MCP removed batching in 2025-06-18 (S0618 changelog), and S26 requires "a single JSON-RPC request or notification". A request's `id` is a string or an integer and never `null` (all three revisions, basic); the server echoes it exactly as received. MCP's `params` is always an object (TS26 `RequestParams`, TS1125, TS0618). Both errors are `400`. When the `id` cannot be read the error response omits `id`, the MCP schema form (TS1125/TS26 `id?: RequestId`) rather than JSON-RPC's `null` (JR section 5); MCP does not reconcile the two, and the omission is a choice.

## Methods

On the 2026 path the server answers `server/discover`, `tools/list`, and `tools/call`; anything else, `ping` and `initialize` included, is `-32601` with HTTP `404`, as S26 requires (#protocol-version-header). On the legacy path it answers `initialize`, `ping`, `tools/list`, and `tools/call`; anything else, `server/discover` included, is `-32601`. The server offers tools only: no resources, prompts, logging, or completions.

`initialize` (legacy) negotiates the version: a requested `2025-11-25` or `2025-06-18` is echoed, and anything else is answered `2025-11-25`, the latest legacy version the server supports (S1125 basic/lifecycle#version-negotiation). The result carries the version, the capabilities, `serverInfo`, and the instructions when there are any (TS1125/TS0618 `InitializeResult`).

`server/discover` (2026) carries the supported versions, the capabilities, and the instructions (TS26 `DiscoverResult`). It is a `CacheableResult`, so it needs `ttlMs` and `cacheScope`; the server sends `0` and `"private"`, because the instructions may be computed per caller (below) and the tools may change with a restart.

`ping` (legacy) answers an empty result (S1125 basic/utilities/ping).

`tools/list` returns every registered tool, in registration order, in one page; S26 asks for a deterministic order (server/tools#capabilities). The server never issues a cursor, so a request carrying one presented a cursor the server did not issue: `-32602`, as pagination prescribes for an invalid cursor (server/utilities/pagination, all revisions). On the 2026 path the result also carries `ttlMs: 0` and `cacheScope: "private"` (TS26 `ListToolsResult`).

`tools/call` finds the tool by `params.name`. An unknown tool is a protocol error, `-32602`, in every revision (S0618, S1125, S26 server/tools#error-handling, whose example message is `Unknown tool: invalid_tool_name`). Everything after that — argument decoding, the handler, the result — is the tool's call as D08 defines it, and is the same on both paths.

Every result on the 2026 path carries `resultType: "complete"` (S26 basic, TS26 `Result`) and `_meta["io.modelcontextprotocol/serverInfo"]` with the server's name and version (S26 basic#meta: "SHOULD include"). This includes a `tools/call` result a tool's handler returned whole (a `RawTool`, D08). The server sets only that key and keeps every other `_meta` key. Legacy results carry neither key, nor `ttlMs` or `cacheScope`. A relayed result that arrives carrying the serverInfo key has just that key removed from its `_meta`, and an emptied `_meta` is dropped. This document states the envelope once; every other member of a tool's result is what D08's call produced, unchanged on both paths.

## HTTP status

A successful request is `200`. On the 2026 path a JSON-RPC error is `404` for `-32601` (S26 requires it), `500` for `-32603`, and `400` for every other code; S26 fixes `400` for its own version, header, and `_meta` errors and states no status for the rest, so `400` for `-32602` and `500` for `-32603` are choices that follow HTTP's meaning. On the legacy path a JSON-RPC error from a method is `200`, the conventional answer since no legacy revision names one; only the transport rejections, parse and envelope errors, and the version rejections above are `4xx`.

## Instructions

The server's instructions tell a model what the service is for. By default they are the service's own description, from its entry in the host's services file — the manifest is the description's single source, so no service writes one in Go. `NewServer` reads the variable `services.Variable` names once, and every `initialize` and `server/discover` reads the file anew through `services.Read` (D05) and takes the `Description` of the entry `List.Find` returns for the server's name. When the variable was unset, the file cannot be read, no entry has that name, or its description is empty, the instructions are omitted.

A consumer whose instructions depend on the request supplies `ServerConfig.Instructions` instead. The gateway does: its instructions name the services in the requested scope. The function is called with the request's context on every `initialize` and `server/discover`, so it can read the caller and anything else the context carries, and an empty result omits the instructions.

## The caller

A tool handler receives the caller explicitly (D08). The server takes it from the request's context with `identity.FromContext` (D06). A request whose context carries no caller, or a caller with no user id, reached the server without `identity.Require` in front of it: a mounting mistake, not a client's. (The telemetry middleware, D14, puts a caller into every request's context, the user id empty when nginx sent none, so only `Require` guarantees a user id.) The server answers it `500` with a fixed plain-text body, whatever the request, before any other check. It writes nothing to standard error: the 500 is recorded by the middleware's `request.finished` event.

## Telemetry

The server records each tool call as a `tool.called` event (D08) through the writer in `ServerConfig.Telemetry`. The writer is required, so no service can serve tools whose calls leave no trail: `NewServer` panics without one. `ServerConfig` has no `Stderr` any more. Under the two-channel rule (D11) the server's former diagnostics — the missing-caller line and a tool's panic or unencodable output — are handled failures the server continues from, so they are trail events, and the server has nothing left that belongs on standard error. A writer kept only to be ignored would be a field with no behaviour.

## Errors as constants

The JSON-RPC and MCP error codes the server emits are exported, so a consumer (the gateway, a service's tests, D10's `RPCError`) compares against names rather than numbers. `ProtocolVersion` names the version the client speaks (D10).
