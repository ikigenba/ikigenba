# D28-candidates-client

Package `candidates` is the client a service on the host uses to read the businesses the candidates app resolved: the members of a cohort, and one business by its id. The candidates app offers its work only as MCP tools, through the server appkit's `mcp` package provides (D07, D08), at the path `/mcp` on the unix socket its services-file entry names. This package calls two of them and nothing else: `cohort` reads a cohort's members, and `candidate` reads one business. Grooming cohorts, ruling on merges and exclusions, and starting passes stay with candidates and the agents and owner that use it. The client holds no state of its own: every call is one request.

A `Client` is built from a `ClientConfig` naming the candidates app's entry in the services file (D05) and the service's telemetry writer (D12). `NewClient` panics without the writer, as `telemetry.SiblingClient`, `scrapes.NewClient` (D24) and `prompts.NewClient` (D27) do; given one, it does no I/O and cannot fail. It reaches the app through appkit's `mcp.Client` (D10) at the endpoint `http://<Service.Name>/mcp`, over `telemetry.SiblingClient` with `telemetry.SocketTransport` on the entry's `Socket` (D14), so every call is one `tools/call` POST recorded as `sibling.called` with the path `/mcp`. A client is safe for concurrent use.

## The request

`Members` calls `cohort` with the arguments `{"cohort":<cohort>}`, and `Candidate` calls `candidate` with `{"candidate":<candidate>}`. candidates' `cohort` is not paged: it answers the whole cohort, which holds at most 100 members, in one answer, so `Members` sends one request and has no paging loop. The client checks nothing about a cohort or candidate id: which exist is candidates' to say.

The caller is taken from the call's context with `identity.FromContext` and passed to `mcp.Client.CallTool` as its explicit caller argument, which `mcp.Client` requires; the sibling client forwards the same caller from the same context, so the two agree. When the context holds no caller, the zero `Caller` is passed, and `identity.Forward` with a zero `Caller` removes the three identity headers (D06), so the request carries none of them. candidates' `/mcp` requires a caller, and refuses a request without `X-User-Id` with an HTTP 500, which the client returns as an `*HTTPError`; so a consumer calls from a context holding the caller it acts for.

## The answer

A typed tool's success result carries its output object as `structuredContent`, with the same JSON repeated in a text block for older clients (D08, R-LHOP-I51T). The client decodes `structuredContent` alone and ignores `content` on a success.

Both tools answer businesses as one candidate object: `id`, `status`, `merged_into` when the record was merged, `name`, `names` (every name the business was seen under), `street`, `city`, `state`, `zip`, `county`, `phone`, `email`, and `people`, each with a `name` and a `role`; `class`, `cargo`, `created` and `updated` are candidates' and unused here. A value candidates does not know is `""` or `[]`. The client returns it as a `Business`, with each `Person` in order. A merged id answers the merged record itself, its `status` `merged` and `merged_into` the survivor's id; the client does not follow it, since every call is one request, and exposes `Status` and `MergedInto` so the consumer decides.

`cohort` answers the cohort, its `matching` and `classified` counts, its `members` and its `rejects`. Each member holds its business as `candidate`, beside other member fields, and `excluded`. The members come in the cohort's order and already leave out standing rejects; an excluded business is left out unless the cohort's own filter shows exclusions, in which case it appears with `excluded` true. `Members` returns every member as answered, in order, each as a `Member` with its `Business` and `Excluded`; it filters nothing. `candidate` answers the business as `candidate` beside its assessment, estimates and links; `Candidate` reads `candidate` alone.

Members the client does not name are ignored, so candidates may add one without breaking it. A success whose `structuredContent` is not the declared shape is an error of its own, neither a sentinel, a `*Refusal` nor an `*HTTPError`: the app answered and the answer is wrong. The same holds for an answer that breaks the MCP protocol as D10 states it, and for a result `mcp.Result` cannot decode.

## Refusals

candidates answers every refusal as an `isError` result whose text is a word, a colon, a space and a sentence: the word is a code a program reads, the sentence copy. The words are `not_found`, `invalid`, `busy`, `stopping` and `unavailable`. The client reads the refusal's text, the `text` of each `text` item of the result's `content`, in order, joined by a newline, and maps the three words a reader acts on to sentinels:

- `ErrNotFound`: on `Members` the cohort is unknown, deleted or malformed; on `Candidate` the candidate is unknown, pruned or malformed. A consumer refuses its own call.
- `ErrUnavailable`: candidates' store cannot be read now.
- `ErrStopping`: candidates is shutting down.

A consumer may retry the last two on its own clock. Any other refusal, `invalid`, `busy`, or a text with no word the client knows, is a `*Refusal` carrying the text in `Text`, its `Error` `candidates: ` followed by `Text`. A well-formed call sends its id as a string, so `invalid` does not arise from the client's own arguments.

## Other failures

A JSON-RPC error (an unknown tool, params candidates' server rejects; D07) is the protocol refusing the exchange, not the tool answering. The client returns an error of its own, beginning `candidates: `, that wraps the `*mcp.RPCError` so `errors.As` reaches its code and message. An answer that is not JSON-RPC at all, or any status other than 200 that is not a JSON-RPC error, is, while the caller's context has not ended, an `*HTTPError` holding the status and the first 4096 bytes of the body, mapped from the `*mcp.HTTPError` D10 returns, with the same shape and text as `scrapes.HTTPError` and `prompts.HTTPError`. A failure to reach the app at all, a missing socket or the caller's context ending, is returned wrapped so `errors.Is` and `errors.As` see the transport's own error. When the context is done by the time a call that has not decoded a success, a refusal or a JSON-RPC error returns, the error satisfies `errors.Is(err, ctx.Err())` and is neither an `*HTTPError` nor a `*Refusal`, as in D27.

Decisions recorded: transport is `mcp.Client`, as in prompts, because candidates has no sibling read path, only MCP tools. There are three sentinels and one `*Refusal`, unlike prompts, because candidates' refusal word is a parsable code, not copy: the sentinels are the three words a reader can get and a consumer acts on, and `*Refusal` carries the rest, `invalid`, `busy` and any text without a known word, which a consumer treats as its own failure. There is no paging loop because `cohort` is read whole. The client filters no member, excluded ones included, and follows no merge pointer, so what candidates answered is what the consumer sees and each call stays one request. As in D27, the caller has one source, the context; the client sets no `X-Event-Cause` or `X-Event-Depth` header; it follows no redirect, a 3xx being an `*HTTPError` unless the context has ended first; and a response body is closed before the call returns, whatever its status.

## Consumer tasks

campaigns is the canonical use. It reads the services file with `services.Read` at the path `services.Variable` names, finds the `candidates` entry with `List.Find`, and builds `candidates.NewClient(candidates.ClientConfig{Service: entry, Telemetry: writer})`, calling from the request context that holds its caller. To add a cohort's businesses it calls `ms, err := client.Members(ctx, cohortID)`, skips each `m` whose `m.Excluded` is true, and for every other member records `m.Business.ID` and, to decide which channel pieces to make, checks `m.Business.Email` and the address fields `m.Business.Street`, `m.Business.City`, `m.Business.State` and `m.Business.Zip`. To add one business by id and produce its merge list it calls `b, err := client.Candidate(ctx, id)` and reads `b.Name`, `b.Names`, `b.Street`, `b.City`, `b.State`, `b.Zip`, `b.Phone`, `b.Email`, and each `b.People[i].Name` and `b.People[i].Role`; when `b.Status` is `merged` it may call `Candidate` again with `b.MergedInto`. On an error, `errors.Is(err, candidates.ErrNotFound)` refuses its own call; `errors.Is(err, candidates.ErrUnavailable)` or `errors.Is(err, candidates.ErrStopping)` it retries later or reports; a `*candidates.Refusal` (its `Text` for the log), a `*candidates.HTTPError`, an `*mcp.RPCError` and anything else, a malformed answer or a transport failure, are its own internal failure.

A test serves an `mcp.Server` (D07, D08) or a hand-written handler on a loopback HTTP server bound to a unix socket in its temporary directory, names that socket as the `Socket` of a `services.Entry`, builds a writer over the capturing sink (D12), and checks the request the server receives (method, path, query, host, identity headers, the JSON-RPC method, tool name and arguments) and what each call returns for each answer the server gives: a success, a malformed success, an `isError` result for each refusal word and for text without one, a JSON-RPC error, a non-JSON-RPC status, a 3xx, a closed socket, and a 200 `application/json`, a 200 `text/event-stream`, a 200 `text/plain`, a 500 and a 3xx whose headers and part of whose body the server writes and flushes before waiting on a channel while the test cancels the context. To prove the body is closed, its server answers an event stream that goes on after the response event and waits for its write to fail.
