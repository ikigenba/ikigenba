# D17-events-record

Services in the suite tell each other what happened through an internal event bus. A producer emits an event when something changes (a repository was pushed), the bus's broker, a separate app named `events`, records it in one ordered log, and delivers it to every service that accepts it (a script runner that reacts to pushes). Package `events` is the client half of that bus in appkit: the record every hop shares (this document), the emitter that queues and sends a service's events (D18), the wire between a service and the broker (D19), and the deliveries a service receives and the declarations it publishes (D20). The broker's own storage, ordering, and fan-out are the broker's design, not appkit's.

The bus is not the telemetry trail. Telemetry (D11 to D14) records what a service did, for an agent to read later; an event on the bus is a fact other services act on. The two share their vocabulary on purpose, so an agent who knows one already reads the other: event names, attribute keys, attribute values, and the time layout are telemetry's.

## The record

An event is an envelope: a producer-assigned id, the time, the service that emitted it, the event's name, the request id and user of the request that caused it, the attributes, the id of the event that caused it, and its depth in that chain. The broker adds two more when it records an event: its sequence number, the event's place in the broker's log counting from 1, and the time the broker received it. `events.Event` is that envelope in Go and `events.Attrs` its attributes.

The id is `evt_` followed by sixteen lowercase hexadecimal digits, minted by the emitter from its random source (D18), so a producer knows an event's id before the broker has seen it and a retry of the same event carries the same id. `evt_` is registered in D11's entity-id table with the entity type `event`, so a telemetry event that names a bus event (D18's `event.lost`) does so under the key `event`.

The cause and the depth make a chain traceable and bounded. An event emitted with no cause has an empty `Cause` and depth 0. An event emitted while handling a delivery names the delivered event's id as its cause and has the delivered event's depth plus one; the emitter takes both from the context (below), so a handler that emits with the context it was given links its events without doing anything.

## Emitted and delivered

The same record travels in two forms. On the way in, from producer to broker, it has no sequence number and no received time: the broker assigns those. On the way out, from broker to consumer, it has both. This document names the two as predicates, a valid emitted event and a valid delivered event, which D18 to D20 cite: the emitter sends only valid emitted events, the broker's ingest accepts only those, and a consumer's delivery endpoint accepts only valid delivered events. Everything else about validity is shared: a well-formed id, a non-empty service, a valid name, valid attributes, a time a four-digit year can carry, and a cause and depth that agree with each other.

## The JSON form

`Event.MarshalJSON` is the exact body the emitter posts to the broker (D19), the body the broker posts to a consumer (D20), and the text the emitter writes to its standard-error writer for an event it gives up on (D18). As in telemetry, it is defined in terms of the standard library's `encoding/json`, so map keys are sorted and strings and numbers are spelled the same way every time; times use telemetry's layout, UTC with exactly six fractional digits and `Z`. The members `seq` and `received` appear exactly when the event is a valid delivered event, so the form says which leg it is on. An event that is neither valid emitted nor valid delivered has no JSON form: `MarshalJSON` fails.

`Event.UnmarshalJSON` is the inverse and is as strict as telemetry's ingest (D13): it accepts exactly the text of a valid emitted or a valid delivered event, every member present once and no other member, and leaves the event untouched on any failure. An attribute number decodes the way telemetry's ingest decodes one, so an event `MarshalJSON` wrote, read back, writes the same bytes whenever its strings are valid text. A consumer's delivery body carries one more member than the event (D20); D20 defines that body in terms of the texts named here.

## The cause context

`events.NewContext` puts a `Cause` (an event id and that event's depth) into a context, and `events.FromContext` reads it back. D20's delivery handler does this for every delivery before calling the service's handler, and D18's emitter reads it on every `Emit`. The key is the package's own, distinct from `identity`'s, so a context may carry a caller and a cause at once and neither hides the other.

## Across a process boundary

A reaction often reaches its effect through another service: a script run for a `repo.pushed` delivery pushes to a repository, and it is `repos`, not the script runner, that emits the next `repo.pushed`. For that event to name its cause, and for the broker's depth limit to stop a loop that runs through several services, the cause has to travel with the call. It travels in two request headers: `X-Event-Cause`, the cause's event id, and `X-Event-Depth`, its depth in decimal, named by `events.CauseHeader` and `events.DepthHeader`.

`events.Forward` is the calling side, the way `identity.Forward` (D06) is for the caller: given the context of the work being done, it copies that context's cause onto an outgoing request, replacing whatever the two headers held, and leaves the request alone when the context carries no cause. `events.Middleware` is the receiving side: when a request carries a well-formed id and a non-negative decimal depth, it puts that cause on the request's context before calling the handler, so the service's emitter (D18) stamps its events with `Cause` that id and `Depth` one more, exactly as for an event emitted while handling a delivery. Only the first value of each header counts. A request without the pair, or with a malformed one, passes through with its context as it was: the middleware never refuses a request, since a missing cause only means the event starts a new chain, and it changes nothing about the request but its context, headers included.

D20's delivery handler does not consult these headers: it takes the cause from the delivered event itself. A service mounts `events.Middleware` inside `telemetry.Middleware` and outside `identity.Require` (or `identity.Optional`), around its whole handler tree.

## What the package promises

Package `events` keeps D01's promises: it never writes to the process's standard output or standard error, or through the standard library's default logger, except through a writer its consumer supplied, and it behaves the same whatever the working directory is. D01's requirements name the older packages; the requirements below restate both rules for `events`.

## Consumer tasks

A consumer's handler reacts to a delivery and emits a follow-up. D20's delivery handler has put the delivered event's id and depth in the request context with `events.NewContext`; the handler emits through the emitter (D18) with that same context, and the follow-up's `Cause` is the delivered event's `ID` and its `Depth` one more. The handler can read the cause itself with `events.FromContext`, and `identity.FromContext` on the same context is unaffected.

A service accepts causes from its callers. It wraps its handler tree as `telemetry.Middleware(tw, events.Middleware(identity.Require(mux)))`, where `tw` is its telemetry writer. A script runner handling a `repo.pushed` delivery calls `events.Forward(ctx, req)` with the delivery's context on each request it makes to `repos` on the script's behalf, so the push that request performs reaches `repos`' handler with the cause on its context, and `repos` emits its next `repo.pushed` with `Cause` the delivered event's id and `Depth` one more; a chain that loops back through the script runner grows deeper on every pass until the broker's depth limit stops it.

The broker ingests an event. Its emit handler (D19) has decoded the body with `json.Unmarshal` into an `events.Event`, which succeeds for a valid emitted or a valid delivered event text, and rejected the delivered form; the broker sets `Seq` and `Received` from its log and posts the result of `MarshalJSON`, now a valid delivered event, to each consumer (D20).

A service's test checks what it emitted. It builds its emitter over a capturing sink with a fixed `Now` and a `Rand` of known bytes (D18), emits with a context built by `events.NewContext(ctx, events.Cause{ID: "evt_00000000000000aa", Depth: 2})`, flushes, and asserts that the captured `Event` has the `ID` the known bytes give, `Cause` `evt_00000000000000aa`, and `Depth` 3; it marshals the event and decodes it back to check the JSON round trip.
