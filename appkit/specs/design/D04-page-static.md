# D04-page-static

Every app serves the same shared files — the stylesheet, the launcher script, the button feedback script, the favicon, the fonts, and their licences — from the same path prefix, `/_appkit/`, so a page's links and the banner's script tag are identical in every app. `page.StaticPrefix` names the prefix and `page.Static` returns the handler the app mounts at it with `mux.Handle(page.StaticPrefix, page.Static())`. The handler sees the full request path, prefix included. The prefix keeps its name: it is a URL every page already links, and naming the library rather than the package keeps it stable however the library's packages are arranged.

The handler serves exactly nine files, each the bytes of the embedded asset of that name, embedded from `page/assets/`, unaltered except the stylesheet:

- `theme.css`, as `text/css; charset=utf-8`, with its font references rewritten to the hashed names (below);
- `launcher.js` and `feedback.js`, as `text/javascript; charset=utf-8`;
- `InterVariable.woff2`, `InterVariable-Italic.woff2`, and `JetBrainsMono.woff2`, as `font/woff2`, each only under its hashed name (below);
- `OFL.txt` and `TABLER-LICENSE.txt`, as `text/plain; charset=utf-8`;
- `favicon.svg`, as `image/svg+xml`.

Nothing else is served. `banner.html` is embedded but is a template, not a file for the browser, so it is 404 like every other path, and so is the prefix itself: there is no directory listing. The path is matched exactly as the request carries it, after URL decoding; a query string does not matter. GET and HEAD are allowed on the nine files; any other method on one of them is 405 with `Allow: GET, HEAD`. An unknown path is 404 whatever the method, since there is no resource there to have methods.

Because the assets are embedded, `page.Templates` and `page.Static` never look for them on disk, and an app behaves the same whichever directory it is started from.

## Fonts: hashed names, a long cache, and a preload

A font is the one asset a page cannot render well without, and checking back for it on every page load is what lets a page paint once in a fallback face and again in Inter. So each font is served under a *hashed name*: its file name's stem, a dot, the first 16 lowercase hex digits of the SHA-256 of its bytes, and `.woff2`, such as `InterVariable.693b77d4f32ee9b8.woff2`. The name changes whenever the bytes do, so a browser may keep a font for a year without asking again (`Cache-Control: public, max-age=31536000, immutable`), and an app upgrade that changes a font changes its URL instead. The plain names, such as `/_appkit/InterVariable.woff2`, are not served, and neither is a hashed name whose hash is wrong: each font has one URL.

The stylesheet stays a copy of `design/` and names the fonts by their plain names, relative to itself, as `url("InterVariable.woff2")`. appkit serves it with each such reference rewritten to the font's hashed name, `url("InterVariable.693b77d4f32ee9b8.woff2")`, and nothing else changed; its `ETag` follows the bytes it serves, so it changes when a font does. The stylesheet itself, the scripts, the favicon and the licences keep the plain names and the revalidation below.

Every page preloads upright Inter, the face nearly all its text is set in, so the font is on its way before the stylesheet asks for it. appkit owns that URL: `page.PreloadURL` returns it, and the `preload` template (D03) renders the link from it, so no app writes a font name or a hash. A page whose templates appkit parses invokes `{{template "preload"}}` in its head; one that renders its head another way emits the same link with `page.PreloadURL`'s value as its `href`. The italic and the monospace faces are not preloaded: most pages use them little or not at all.

## Revalidation

Browsers may keep the other files but must check back before using them, so an app upgrade that changes an asset is seen on the next page load while an unchanged asset costs only an empty reply. Every 200 response for one of the nine files, to GET or HEAD, carries a strong `ETag`, and every one but a font's carries `Cache-Control: no-cache`. The ETag is the SHA-256 digest of the bytes served, in lowercase hex, quoted: it follows the bytes alone, so the same content yields the same tag on every request and in every build, and it stays 66 characters whatever the file's size. The bound matters because a proxy in front of an app caps the size of a response's headers, so a tag that grew with the file would turn a large asset into a proxy error.

The caching promise covers a *plain* request: a GET or HEAD for one of the nine files carrying none of `Range`, `If-Match`, `If-Unmodified-Since`, or `If-Range`. A plain request whose `If-None-Match` matches the tag is answered 304 with the same `ETag`, `Cache-Control`, and an empty body, even if it also carries `If-Modified-Since`: as RFC 9110 requires, `If-None-Match` takes precedence, so a browser that sends both still gets its empty reply. A plain request whose non-empty `If-None-Match` does not match gets the normal 200, again whatever its `If-Modified-Since`; so does one with no `If-Modified-Since` whose `If-None-Match` is absent or does not match. `If-None-Match` matches when it is exactly `*`, or when it is a well-formed comma-separated list of entity-tags, empty elements ignored, at least one of which equals the tag under RFC 9110's weak comparison; a well-formed list with no such tag does not match.

Not fixed by this design, so the implementation may send or honour them or not and no consumer may rely on either: which status, and what body, answers a request carrying `Range`, `If-Match`, `If-Unmodified-Since`, or `If-Range`, or a plain request carrying `If-Modified-Since` whose `If-None-Match` is absent or empty — though any 200 or 304 such a request does receive for one of the nine files still carries the `ETag`, `Cache-Control`, and (on a 200) `Content-Type` the requirements state; `Last-Modified`, `Accept-Ranges`, and other headers the requirements do not name; the `Content-Type` and other headers of a 304; how a malformed `If-None-Match`, one mixing `*` with entity-tags, or one split across several header lines is treated; and any header or body on the 404 and 405 responses beyond what the requirements state.

## Browser behaviour (the script and icon assets, not testable here)

`feedback.js` is human-written and static, a copy of the repository's `design/ikigenba/feedback.js`. Pages opt in by linking `<script src="/_appkit/feedback.js" defer>` in their own head, as they link the stylesheet; the banner does not load it (D03). Its intended behaviour: every enabled `button` or `.button` (neither `disabled` nor `aria-disabled="true"`) scales to .96 while held and gets the class `pulse` on click; a `button` that is a child of a `.secret` element copies the text of its sibling `code` element; success shows a `Copied to clipboard` toast for about 2.2 seconds and leaves the button unchanged; failure selects the code text and shows an error toast for about 4.5 seconds, `Couldn't copy. The text is selected; press Ctrl+C.` (`⌘C` on a Mac); the toasts share one `aria-live="polite"` region at the bottom right; under reduced motion a toast fades without sliding.

None of that is a requirement, for the reason D03 gives for `launcher.js`: no gate runs a browser. The build's part is limited to serving the script's bytes unaltered.

`favicon.svg` is likewise a human-drawn copy, of the repository's `design/ikigenba/favicon.svg`: the suite's one favicon. Pages link it in their own head with `<link rel="icon" type="image/svg+xml" href="/_appkit/favicon.svg">`; the banner does not (D03). Its switch to a light stroke under `prefers-color-scheme: dark` lives inside the SVG and is a browser's to honour, so it is no requirement either; the build serves the bytes unaltered.

What the preload, the long cache and `font-display` do in a browser — fetching upright Inter early, reusing a font without asking, and showing the fallback face only for a moment — is likewise a browser's to honour and no requirement. The build's part is the URLs, headers, and markup the requirements state.

## Notes for the asset author

These are decisions about `page/assets/theme.css`, recorded here so the human copying it has them in one place; the build run neither writes nor tests them. Every `@font-face` rule uses `font-display: fallback`, as `design/README.md` decides. Each rule names its font file by its plain name, relative to the stylesheet and in double quotes, exactly `url("InterVariable.woff2")`, `url("InterVariable-Italic.woff2")`, or `url("JetBrainsMono.woff2")`: that is the form the served stylesheet's rewrite replaces, and the copy never names a hash. The header names the `design/` commit the copy came from, which is now the commit that changed the Google Fonts import to `display=fallback`.
