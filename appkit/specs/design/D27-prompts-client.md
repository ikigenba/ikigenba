# D27-prompts-client

Package `prompts` is the client a service on the host uses to run a prompt kept in the prompts app's catalog and read the run's outcome. The prompts app offers its work only as MCP tools, through the server appkit's `mcp` package provides (D07, D08), at the path `/mcp` on the unix socket its services-file entry names. This package calls three of them and nothing else: `show` reads one prompt by name, `run` starts a run of a prompt with an input object, and `result` reads a run. Editing the catalog, subscriptions, files and transcripts stay with prompts and the agents that call it. The client holds no state of its own: every call is one request, and it does not wait for a run to end.

A `Client` is built from a `ClientConfig` naming the prompts app's entry in the services file (D05) and the service's telemetry writer (D12). `NewClient` panics without the writer, as `telemetry.SiblingClient` and `scrapes.NewClient` (D24) do; given one, it does no I/O and cannot fail. It reaches the app through appkit's `mcp.Client` (D10) at the endpoint `http://<Service.Name>/mcp`, over `telemetry.SiblingClient` with `telemetry.SocketTransport` on the entry's `Socket` (D14), so every call is one `tools/call` POST recorded as `sibling.called` with the path `/mcp`. A client is safe for concurrent use.

## The request

`Show` calls `show` with the arguments `{"name":<name>}`, `Result` calls `result` with `{"run":<run>}`, and `Run` calls `run` with `{"name":<name>}` when its input is nil and `{"name":<name>,"input":<input>}` otherwise. prompts' `run` takes its input as an object, so a non-nil input that is not exactly one JSON object is refused by the client itself with an error, before anything is sent: no request, no `sibling.called`. The client checks nothing else about a name, a run id or an input's members: which exist and what an input must hold is prompts' to say.

The caller is taken from the call's context with `identity.FromContext` and passed to `mcp.Client.CallTool` as its explicit caller argument, which `mcp.Client` requires; the sibling client forwards the same caller from the same context, so the two agree. When the context holds no caller, the zero `Caller` is passed, and `identity.Forward` with a zero `Caller` removes the three identity headers (D06), so the request carries none of them, as a scrapes call without a caller does.

## The answer

A typed tool's success result carries its output object as `structuredContent`, with the same JSON repeated in a text block for older clients (D08, R-LHOP-I51T). The client decodes `structuredContent` alone and ignores `content` on a success: the structured member is the one D08 guarantees as JSON, and the text is a copy of it.

`show` answers the prompt: `id`, `name`, `model`, `prompt`, `system`, and `tools`, an array of tool names; `schema`, `created`, `subscriptions` and `last_run` are prompts' and unused here. `Show` returns it as a `Prompt`. `run` answers `id` and `status`, and `reason` when it has one; `Run` returns them as a `Start`. `result` answers a run's record: `id`, `prompt` (the prompt's name), `model`, `status`, `reason`, `exit_code`, `started` and `finished` (RFC 3339), `stdout`, and its usage, `input_tokens`, `cached_tokens`, `output_tokens`, `reasoning_tokens` and `cost_nanos`; while a run is queued or running its usage, `exit_code` and `finished` are absent. `Result` returns it as an `Outcome`, its times parsed into `time.Time` in UTC, `ExitCode` nil when `exit_code` is absent, `Finished` the zero time when `finished` is absent, and any other absent member empty or zero. The statuses are prompts' (queued, running, exited, killed, timed_out, failed today); the client checks no status value.

Members the client does not name are ignored, so prompts may add one without breaking it. A success whose `structuredContent` is not the declared shape is an error of its own, neither a `*Refusal` nor an `*HTTPError`: the app answered and the answer is wrong. The same holds for an answer that breaks the MCP protocol as D10 states it (another request's id, an unknown `resultType`, a stream with no response), and for a result `mcp.Result` cannot decode, one that repeats a top-level member such as `isError`: `mcp.Client` returns an error for it, so it is neither a success nor a refusal.

## Refusals

Every refusal prompts gives, whatever the tool, is an `isError` result whose content is copy text and nothing a program can read: a prompt that does not exist, a run that does not exist, a server that is stopping, runs that are unavailable, a full queue, a catalog that cannot be reached. So the client returns one `*Refusal` for any `isError` result, carrying the result's text in `Text`, and never reads meaning from the text. There are no sentinels such as scrapes' `ErrNotFound`: prompts gives no code to map to one, and matching copy would break on the first reworded message.

prompts also answers an `isError` result for arguments its server refuses (R-L31W-WW5H). The client always sends `name` and `run` as strings and `input` only as a JSON object, so a well-formed call does not draw that refusal; but since it is indistinguishable from the others, a consumer that retries `Run` refusals SHOULD bound its retries or end with its own deadline.

A caller decides what a refusal means from which call got it:

- A refusal on `Show` means the named prompt cannot be used. A consumer refuses its own call and quotes `Text` to its caller.
- A refusal on `Run` after a `Show` that succeeded means not now: the queue is full, prompts is draining, runs are unavailable or the catalog is unreachable. A consumer waits on its own clock and retries, calling `Show` again first, so a prompt deleted meanwhile ends its work with a `Show` refusal rather than looping on `Run`.
- A refusal on `Result` means the run is unknown or cannot be read now.

`Text` is the `text` of each `text` item of the result's `content`, in order, joined by a newline, and empty when there is none. `Refusal.Error` is `prompts: ` followed by `Text`.

## Other failures

A JSON-RPC error (an unknown tool, params prompts' server rejects; D07) is the protocol refusing the exchange, not the tool answering, so it is neither a refusal to wait out nor an HTTP failure. The client returns an error of its own, beginning `prompts: `, that wraps the `*mcp.RPCError` so `errors.As` reaches its code and message; the mcp type already carries both, and a second type would only copy it. An answer that is not JSON-RPC at all, a proxy's plain-text 502, say, or any status other than 200 that is not a JSON-RPC error, is, while the caller's context has not ended, an `*HTTPError` holding the status and the first 4096 bytes of the body, mapped from the `*mcp.HTTPError` D10 returns, with the same shape and text as `scrapes.HTTPError`, so a consumer needs one package's types. A failure to reach the app at all, a missing socket or the caller's context ending, is returned wrapped so `errors.Is` and `errors.As` see the transport's own error. The context can also end after an answer has begun, whatever its status or media type, while its body or stream is still being read; `mcp.Client` then fails reading the body and returns a plain error with no status, and D10 does not promise its shape, so the client itself checks: when the context is done by the time a call that has not decoded a success, a refusal or a JSON-RPC error returns, the error satisfies `errors.Is(err, ctx.Err())` and is neither an `*HTTPError` nor a `*Refusal`.

Decisions recorded: transport is `mcp.Client` rather than scrapes' plain HTTP, because prompts has no sibling read path, only MCP tools. The caller has one source, the context, as in scrapes; it is handed to `mcp.Client` explicitly only because that client's signature takes one. There are no sentinels and one `*Refusal`, unlike scrapes, because prompts' refusals are copy with no code (see Refusals). The client sets no `X-Event-Cause` or `X-Event-Depth` header. It follows no redirect: a 3xx answer is an `*HTTPError` (unless the context has ended first) and only one request is sent, as in scrapes, although `telemetry.SiblingClient` alone would follow one. A response body is closed before the call returns, whatever its status; a body that is not a 200 event stream is read whole first, as `mcp.Client` does, because a JSON-RPC error's `data` may run to its last byte. Whether the request carries `clientInfo` (D10) is not part of this contract. There is no polling loop: scrapes has none, and how often to poll a run and when to give up is the consumer's to decide; candidates measures its interval on its own clock. Times are `time.Time` and counts `int64`, so a caller compares instants and sums costs without parsing; `ExitCode` is a pointer because 0 is a real exit code and a running run has none.

## Consumer tasks

candidates' site_text pass is the canonical use. It reads the services file with `services.Read` at the path `services.Variable` names, finds the `prompts` entry with `List.Find`, and builds `prompts.NewClient(prompts.ClientConfig{Service: entry, Telemetry: writer})`. It starts with `p, err := client.Show(ctx, "site-text")`; on an error for which `errors.As(err, &ref)` finds a `*prompts.Refusal`, it refuses the pass as invalid, quoting `ref.Text`, and otherwise may record `p.ID`, `p.Model` and `p.Tools`. For each company it builds the input object with the members `candidate`, `name`, `city`, `state` and `website` as a `json.RawMessage` and calls `st, err := client.Run(ctx, "site-text", input)`. On a `*prompts.Refusal` it waits on its own clock, calls `Show` again (a refusal there ends the pass) and retries `Run`. With `st.ID` in hand (and `st.Status`, `st.Reason` for its log) it polls `out, err := client.Result(ctx, st.ID)` on its own interval until `out.Status` is neither `queued` nor `running`, then reads `out.Status`, `out.ExitCode`, `out.Reason`, `out.Stdout`, `out.CostNanos` and `out.InputTokens`, `out.CachedTokens`, `out.OutputTokens` and `out.ReasoningTokens`, with `out.Started` and `out.Finished` for its timing. Any error that is not a `*prompts.Refusal` it reports: `errors.As(err, &he)` with `he` a `*prompts.HTTPError` gives the status, `errors.As` with an `*mcp.RPCError` the protocol error, and anything else is a malformed answer or a transport failure, the pass's own internal failure.

A test serves an `mcp.Server` (D07, D08) or a hand-written handler on a loopback HTTP server bound to a unix socket in its temporary directory, names that socket as the `Socket` of a `services.Entry`, builds a writer over the capturing sink (D12), and checks the request the server receives (method, path, query, host, identity headers, the JSON-RPC method, tool name and arguments) and what each call returns for each answer the server gives: a success, an `isError` result, a JSON-RPC error, a non-JSON-RPC status, a 3xx, a closed socket, and a 200 `application/json`, a 200 `text/event-stream`, a 200 `text/plain`, a 500 and a 3xx whose headers and part of whose body the server writes and flushes before waiting on a channel while the test cancels the context. To prove the body is closed, its server answers an event stream that goes on after the response event and waits for its write to fail.
