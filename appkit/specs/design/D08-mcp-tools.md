# D08-mcp-tools

A service offers tools by registering them on its `mcp.Server` (D07) before it serves the first request. Registration is two generic functions, because Go methods cannot be generic: `mcp.AddTool` registers a typed `Tool[In, Out]`, whose handler takes a decoded `In` and returns an `Out`; `mcp.AddRawTool` registers a `RawTool[In]`, whose handler returns a wire `Result` built by hand or received from another server. The typed form is what every ordinary service uses. The raw form exists for passthrough: the gateway's call and mutate tools relay a backend's result verbatim.

Every tool names its `Effect`. The effect is required and is the only source of the tool's annotations, so a client's confirmation policy never depends on what a handler happens to do. The three effects map onto the annotation hints every revision defines in its `ToolAnnotations` (TS0618, TS1125, TS26): `readOnlyHint` defaults to false and `destructiveHint` and `openWorldHint` default to true, so the server always states all three explicitly rather than leaning on defaults. `idempotentHint` and `title` are never emitted. Every tool of this suite works on the suite's own data, so `openWorldHint` is always false.

## Registration is checked, loudly

Registration happens at start-up, in code the service author controls, so every mistake panics there instead of surfacing as a strange answer to a model later. The panic value is a string that names the tool and the reason, and a panicking registration registers nothing. Names follow the suite's snake_case, verb-first convention: lower-case ASCII words joined by single underscores, at most 64 bytes, which sits inside the character set and length the 2025-11-25 and 2026-07-28 tool-name guidance recommends (S1125 and S26, server/tools#tool-names). The description is hand-written for a model and sent unaltered; its first line is the summary the gateway shows in its catalogue, so it must be one short sentence. Registration closes when the server is first asked to serve: a tool added after `ServeHTTP` has run would appear to some clients and not others, which the 2026 revision forbids for the tool set of one authorization (S26, server/tools#capabilities).

Decision recorded: "after the first request" is fixed as "after `ServeHTTP` has been called at least once", which is decidable without timing.

## The tool object in tools/list

Each registered tool's entry in a `tools/list` result is a Tool object (TS0618, TS1125, TS26 `interface Tool`) with `name`, `description`, `inputSchema`, `outputSchema` for a typed tool only, and `annotations`. The schemas are derived from `In` and `Out` by the rules of D09. Every revision the server speaks accepts these objects: `outputSchema` is always an object schema because `Out` is always a struct, which satisfies the 2025-06-18 and 2025-11-25 `type: "object"` constraint as well as 2026's looser one.

## Calling a tool

`tools/call` arguments are decoded strictly into `In` before the handler runs. Since 2025-11-25 an input validation failure is a tool execution error reported with `isError: true`, not a protocol error (S1125 and S26, server/tools#error-handling; changelog "Clarify that input validation errors should be returned as Tool Execution Errors"). The server applies that rule on every revision it speaks, including 2025-06-18, so a model always sees the same correctable text. The text names every offending field at once, so a model fixes all of them in one retry. The acceptance rules are D09's; the text format is fixed here.

A typed tool's success result carries `structuredContent` and, as every revision asks for backwards compatibility, the same JSON serialized in a text block (server/tools#structured-content, all three revisions). A handler error is the tool's own failure, written for the model, and becomes an `isError` result with that text (`CallToolResult.isError`: "Any errors that originate from the tool SHOULD be reported inside the result object"). A panic is recovered: the model gets a fixed, generic text, and the trail records the call with the outcome `panicked` under the request's id, so the operator finds it by request. An `Out` that cannot honour its own output schema (a non-finite float, an enum value outside its list) is answered the same way, because every revision says "Servers MUST provide structured results that conform to this schema", and recorded with the outcome `unencodable_output`. Neither writes to standard error: the server continues from both, so under the two-channel rule (D11) they are trail events. The panic value itself is free text the trail does not carry (D11's metadata-only rule); a panic is a bug, and its reproduction starts from the request id.

## Recording the call

Every `tools/call` that reaches a registered tool — every call this document defines, answered with a `result` — emits one `tool.called` event (D11's catalogue) through the server's writer before the answer goes out, so in a trace it falls between the middleware's `request.started` and `request.finished` (D14). A call answered with a JSON-RPC error never reached a tool and emits none; the request's own `request.finished` records it. The gateway's relaying tool and the backend's tool each emit one, so a trace shows both the forward and the execution.

The attributes come from the vocabulary the package already has. `kind` is the tool's `Effect`, spelled `read`, `additive`, or `destructive`. `outcome` names which of this document's answers the call got: `ok` for a result that is not an error; `error` for the tool's own failure, a handler error or a relayed `isError` result; `invalid_arguments` when decoding failed and the handler never ran; `panicked`; and `unencodable_output`. The four failures all answer `isError: true`; the outcome tells them apart without carrying the text. `duration_us` spans the handler, from its call to its return or panic, measured with the writer's clock (`Writer.Now`, D12) so a test with an injected clock records an exact value; it is 0 when the handler never ran.

## Result

`Result` is the wire `CallToolResult` as an opaque value. It keeps every member it was built with or decoded from, in order, so the gateway can relay a backend's result without understanding or losing any of it. The one exception is `resultType`, which belongs to the 2026 envelope rather than to the tool's answer (S26/basic: "The `result` MUST include a `resultType` field"): decoding strips it, and the server adds it back on the 2026 path. The server also owns the `io.modelcontextprotocol/serverInfo` key of `_meta` (S26/basic#meta); D07's per-revision envelope rule says how it treats that key on each path, and every other member is left alone. `IsError` reads the `isError` member, which "if not set, ... is assumed to be false" (TS `CallToolResult.isError`).

Unknown-tool and malformed-params errors in `tools/call` are protocol errors and belong to D07.

## REQUIREMENTS

- R-K4WQ-7BE1: Package `mcp` MUST export `type Effect int` and the constants `Read Effect = 1`, `Additive Effect = 2`, and `Destructive Effect = 3`.
- R-K64M-L34Q: Package `mcp` MUST export `type Enumerator interface { Enum() []string }`.
- R-K7CI-YUVF: Package `mcp` MUST export `type Tool[In, Out any] struct { Name, Description string; Effect Effect; Handler func(ctx context.Context, c identity.Caller, in In) (Out, error) }`, with exactly these fields in this order, where `identity` is package `github.com/ikigenba/ikigenba/appkit/identity`.
- R-K8KF-CMM4: Package `mcp` MUST export `type RawTool[In any] struct { Name, Description string; Effect Effect; Handler func(ctx context.Context, c identity.Caller, in In) (Result, error) }`, with exactly these fields in this order.
- R-KB08-463I: Package `mcp` MUST export `func AddTool[In, Out any](s *Server, t Tool[In, Out])`.
- R-KC84-HXU7: Package `mcp` MUST export `func AddRawTool[In any](s *Server, t RawTool[In])`.
- R-KDG0-VPKW: Package `mcp` MUST export `type Result` as a struct type with no exported fields, with the methods `func (r Result) IsError() bool`, `func (r Result) MarshalJSON() ([]byte, error)`, and `func (r *Result) UnmarshalJSON(data []byte) error`.
- R-KENX-9HBL: Package `mcp` MUST export `func ErrorResult(text string) Result`.
- R-KFVT-N92A: Package `mcp` MUST export `func TextResult(text string) Result`.
- R-KH3Q-10SZ: Package `mcp` MUST export `const PanicText = "The tool failed with an internal error."`.
- R-KIBM-ESJO: Every panic `AddTool` or `AddRawTool` raises MUST have a `string` panic value that begins with `mcp: tool `, followed by the tool's `Name` quoted as `strconv.Quote` quotes it, followed by `: ` and a non-empty reason; and a call that panics MUST leave the Server's set of registered tools unchanged.
- R-KJJI-SKAD: `AddTool` and `AddRawTool` MUST panic when the tool's `Name` does not match the regular expression `^[a-z][a-z0-9]*(_[a-z0-9]+)*$` or is longer than 64 bytes.
- R-KKRF-6C12: `AddTool` and `AddRawTool` MUST panic when the tool's `Name` equals the `Name` of a tool already registered on the same Server by either function.
- R-KLZB-K3RR: `AddTool` and `AddRawTool` MUST panic when the tool's `Handler` is nil.
- R-KN77-XVIG: `AddTool` and `AddRawTool` MUST panic when the tool's `Effect` is not `Read`, `Additive`, or `Destructive`.
- R-KOF4-BN95: `AddTool` and `AddRawTool` MUST panic when the tool's `Description` is not valid UTF-8, or when its summary line — the text before its first LF, or the whole `Description` when it has no LF — is empty, begins or ends with a character `unicode.IsSpace` reports as space, is longer than 120 runes, does not end with `.`, or contains the two-character sequence `. `.
- R-KPN0-PEZU: `AddTool` and `AddRawTool` MUST panic when `ServeHTTP` has already been called on the Server at least once.
- R-KQUX-36QJ: A call to `AddTool` or `AddRawTool` that runs concurrently with `ServeHTTP` calls on the same Server MUST NOT cause a data race, whichever of the two the Server observes first.
- R-BTJA-WZ53: The Tool object a `tools/list` result carries for a registered tool MUST have exactly the members `name`, `description`, `inputSchema`, `outputSchema`, and `annotations`, in that order, except that `outputSchema` MUST be absent for a tool registered with `AddRawTool`.
- R-BUR7-AQVS: The `name` and `description` members of a registered tool's Tool object MUST be the tool's `Name` and `Description`, unaltered.
- R-BVZ3-OIMH: The `inputSchema` member of a registered tool's Tool object MUST be the schema D09 derives for the tool's `In` type.
- R-BYEW-G23V: The `outputSchema` member of a tool registered with `AddTool` MUST be the schema D09 derives for the tool's `Out` type.
- R-BZMS-TTUK: The `annotations` member of a registered tool's Tool object MUST be an object with exactly the members `readOnlyHint`, `destructiveHint`, and `openWorldHint`, in that order, whose values are `true`, `false`, `false` for `Read`; `false`, `false`, `false` for `Additive`; and `false`, `true`, `false` for `Destructive`.
- R-L0M4-5CO3: A `tools/call` request for a registered tool whose params have no `arguments` member MUST be handled exactly as one whose `arguments` is `{}`.
- R-L1U0-J4ES: A `tools/call` request for a registered tool whose `arguments` member is present and is not a JSON object MUST be answered with a result equal to `ErrorResult` of the argument error text (whose single offence has the path `arguments` and the reason for a type mismatch against `object`), and the tool's `Handler` MUST NOT be called.
- R-L31W-WW5H: A `tools/call` request for a registered tool whose `arguments` object holds any offence D09 defines MUST be answered with a result equal to `ErrorResult` of the argument error text naming every offence the arguments hold, and the tool's `Handler` MUST NOT be called.
- R-BG4E-PHZG: The argument error text MUST be the line `invalid arguments:` followed, for each offence, by an LF and the line `<path>: <reason>`, with no trailing LF.
- R-BHCB-39Q5: The `<path>` of an offence MUST be built from the path from the arguments object to the offending value, where a member whose name matches `^[A-Za-z_][A-Za-z0-9_]*$` contributes its name (preceded by `.` unless it is the first segment), any other member contributes `[` followed by its name encoded as a JSON string and then `]`, and an array element contributes `[<index>]` with its zero-based decimal index; an offence of the arguments value itself MUST have the path `arguments`.
- R-BIK7-H1GU: The offences of an object MUST be listed in this order: for each property of its schema in property order, the offences of that member (or its missing-required-member offence); then the unknown-member offences in the order those members appear in the arguments; the offences of an array MUST be listed element by element in index order.
- R-BJS3-UT7J: The reason of an unknown-member offence MUST be `unknown field`, of a missing-required-member offence `missing required field`, and of a duplicate-member offence `duplicate field`.
- R-L95E-TQUY: The reason of a type-mismatch offence MUST be `expected <want>, got <got>`, where `<want>` is the schema's `type` value and `<got>` is `null`, `boolean`, `number`, `string`, `array`, or `object` according to the JSON value received.
- R-LADB-7ILN: The reason of a non-integral-number offence MUST be `expected integer, got <number>`, where `<number>` is the number exactly as it appears in the arguments.
- R-LCT3-Z231: The reason of an integer-range offence MUST be `must be between <min> and <max>, got <number>`, where `<min>` and `<max>` are the decimal bounds of the field's Go integer kind and `<number>` is the number exactly as it appears in the arguments.
- R-LE10-CTTQ: The reason of a float-range offence MUST be `out of range for a 64-bit float, got <number>`, where `<number>` is the number exactly as it appears in the arguments.
- R-LF8W-QLKF: The reason of an enum offence MUST be `must be one of <values>, got <value>`, where `<values>` is each value `Enum` returned, encoded as a JSON string, in `Enum` order, joined by `, `, and `<value>` is the received string encoded as a JSON string.
- R-1VNJ-S2WS: The `ctx` a tool's `Handler` receives MUST be the context of the HTTP request that carried the `tools/call`, or one derived from it, so that context's values, deadline, and cancellation remain visible through it and a client disconnect that cancels the request's context cancels `ctx`; the `c` it receives is D07's.
- R-LHOP-I51T: When a `Tool` handler returns a nil error, the call's result MUST have exactly the members `content` and `structuredContent` (besides any member D07 adds for the protocol revision), where `content` is an array of one object `{"type":"text","text":<text>}`, `<text>` is the compact JSON encoding of the handler's `Out` value as D09 encodes it, and `structuredContent` is a JSON value equal to that encoding.
- R-LIWL-VWSI: When a `Tool` or `RawTool` handler returns a non-nil error `err`, the call's result MUST be equal to `ErrorResult(err.Error())`, and whatever else the handler returned MUST be discarded.
- R-LK4I-9OJ7: When a `Tool` or `RawTool` handler panics, the Server MUST recover, MUST answer the call with a result equal to `ErrorResult(PanicText)`, and MUST go on serving later requests.
- R-2UIX-CNYK: When a `Tool` handler returns a nil error and an `Out` value D09 cannot encode, the Server MUST answer the call with a result equal to `ErrorResult(PanicText)`.
- R-H0J4-YSFR: When a `RawTool` handler returns a nil error and a `Result` `r`, the call's result MUST hold exactly the members of the object `r.MarshalJSON` produces, each unchanged, except as D07's per-revision envelope rule changes them.
- R-LRFW-KAZD: `ErrorResult(text).MarshalJSON()` MUST return a JSON object with exactly the members `content`, equal to `[{"type":"text","text":<text>}]` with `<text>` the JSON string of `text`, and `isError`, equal to `true`, in that order.
- R-LSNS-Y2Q2: `TextResult(text).MarshalJSON()` MUST return a JSON object with exactly the one member `content`, equal to `[{"type":"text","text":<text>}]` with `<text>` the JSON string of `text`.
- R-LV3L-PM7G: The zero value of `Result` MUST marshal to `{"content":[]}`, and its `IsError` MUST return false.
- R-LWBI-3DY5: `Result.UnmarshalJSON` MUST return a non-nil error and leave the receiver unchanged when its input is not a single JSON object, including JSON `null`, or when the object holds two members with the same name.
- R-LXJE-H5OU: After `Result.UnmarshalJSON` succeeds on a JSON object, `MarshalJSON` MUST return an object with every member of the decoded object except `resultType`, in the decoded order, each member's value being the decoded value's bytes with insignificant whitespace removed.
- R-LYRA-UXFJ: `Result.IsError` MUST return true exactly when the Result holds a member `isError` whose value is JSON `true`.
- R-LZZ7-8P68: `Result.IsError` and `Result.MarshalJSON` MUST be safe to call concurrently on the same `Result`, and a copy of a `Result` MUST marshal to the same bytes as the original.
- R-M173-MGWX: The Server MUST NOT serialize tool handlers: the handlers of two `tools/call` requests in flight at the same time MUST run concurrently, so a handler that waits for another call's handler to start is not blocked by it.
- R-2WYQ-47FY: For each `tools/call` request that `Server.ServeHTTP` answers with a JSON-RPC `result`, the Server MUST emit exactly one event named `tool.called` through `ServerConfig.Telemetry` before `ServeHTTP` returns, and for every other request, a `tools/call` answered with a JSON-RPC error included, it MUST emit no `tool.called` event.
- R-2Y6M-HZ6N: The envelope request id and user of a `tool.called` event MUST be the `RequestID` and `UserID` of the `Caller` that `identity.FromContext` returns for the context of the HTTP request that carried the `tools/call`.
- R-2ZEI-VQXC: The attributes of a `tool.called` event MUST be exactly `tool`, `kind`, `outcome`, and `duration_us`, where `tool` is the called tool's `Name`.
- R-30MF-9IO1: The `kind` attribute of a `tool.called` event MUST be the string `read`, `additive`, or `destructive` when the called tool's `Effect` is `Read`, `Additive`, or `Destructive` respectively.
- R-31UB-NAEQ: The `outcome` attribute of a `tool.called` event MUST be the string `invalid_arguments` when the call is answered as R-L1U0-J4ES or R-L31W-WW5H states; `panicked` when the handler panicked; `unencodable_output` when the call is answered as R-2UIX-CNYK states; `error` when the handler returned a non-nil error, or a `RawTool` handler returned a nil error and a `Result` whose `IsError` is true; and `ok` when a `Tool` handler returned a nil error and an `Out` value D09 encodes, or a `RawTool` handler returned a nil error and a `Result` whose `IsError` is false.
- R-JPSY-MGRS: The `duration_us` attribute of a `tool.called` event MUST be 0 when the tool's handler is not called, and otherwise `int64(t1.Sub(t0) / time.Microsecond)`, or 0 when that is negative, where `t0` is what one `Writer.Now` call on `ServerConfig.Telemetry` returns before the handler is called and `t1` is what one such call returns after the handler returns or panics.
