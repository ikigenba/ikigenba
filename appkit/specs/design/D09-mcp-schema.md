# D09-mcp-schema

A tool's author writes Go types; the model sees JSON Schema. This document is the one rule that turns the `In` and `Out` types of a registration (D08) into the `inputSchema` and `outputSchema` a `tools/list` result carries, decides which `arguments` a `tools/call` accepts for `In`, and fixes how an `Out` value is written back. The same rule serves both directions, so what the schema promises and what the server accepts or returns never drift apart. There is no exported derivation function: a consumer meets these rules only through `tools/list` and `tools/call`, and that is how they are tested.

## Why a small subset

Schemas without a `$schema` member are read as JSON Schema 2020-12 by the 2025-11-25 and 2026-07-28 revisions ("When a schema does not include a `$schema` field, it defaults to JSON Schema 2020-12", S1125/basic#json-schema-usage and S26/basic), and 2025-06-18 states no dialect, so the server emits no `$schema` and uses only keywords that read the same everywhere: `type` (a string, or for `Nullable` an array of two), `properties`, `required`, `additionalProperties`, `items`, `enum`, `minimum`, and `description`. Every revision requires `type: "object"` at the root of `inputSchema`, and 2025-06-18 and 2025-11-25 require it of `outputSchema` too (TS0618, TS1125, TS26 `interface Tool`), so both `In` and `Out` must be structs. Objects are closed with `additionalProperties: false`, the form 2025-11-25 and 2026 recommend for a tool without parameters (S1125 and S26, server/tools#tool); a struct with no properties emits exactly that recommended form.

A Go type the subset cannot describe exactly — a map, an interface, a type with its own JSON or text marshalling, an embedded field whose promotion rules are subtle — panics at registration rather than producing a schema that lies. The one exception is `json.RawMessage` as a struct field: it stands for "any JSON object", schema `{"type":"object"}`, carried byte-for-byte in both directions. The gateway needs it to pass a backend's arguments and schemas through untouched. It is never the whole `In` or `Out`, and never a slice element or pointer target. Pointers mark optional values; an `mcp:"required"` struct tag marks a member that must be present. The marker is its own tag key rather than an option of the `json` tag because the `json` tag's options belong to `encoding/json`, and static checkers (staticcheck SA5008) rightly report an option it does not define; a `json` tag here carries a name and nothing else. In `Out`, a required pointer could be nil and break the promise "Servers MUST provide structured results that conform to this schema" (server/tools#output-schema, all revisions), so it panics too.

Property names are restricted to ASCII identifiers. That keeps every name valid for the stricter clients models run behind and keeps the argument error paths of D08 unambiguous.

Two properties of one struct with the same `json` name are not checked at registration. `go vet`'s `structtag` analyzer reports every such struct statically (it flags a repeated `json` name among a struct's fields, a superset of the duplicates these rules could produce), and it runs in this module's lint gate and in every consumer's, so the type never lints clean; a check no lint-clean code can reach would be untestable.

## Acceptance follows the schema

Decoding `arguments` is validation against the derived schema plus the limits of the Go type the schema stands for. Every violation is an offence, and every offence is reported, not just the first (D08 fixes the text). An integer is any JSON number with a zero fractional part, in any notation, because that is what `"type": "integer"` means in JSON Schema 2020-12 (Validation, section 6.1.1); a compliant client may send `3.0` and is not refused. A Go integer kind narrower than the JSON number is a range limit the schema does not state for signed kinds, and is reported with the bounds so a model can correct it.

One leniency is deliberate and recorded: a pointer field accepts JSON `null` as nil although its schema is the element's schema, as agreed in the interface brief. A client that validates against the schema never sends it; one that does is not punished for it.

## Absent or null

A pointer cannot tell a member that was left out from one sent as `null`: both arrive as nil, and for an optional member that is the right reading. Some updates need the difference, because `null` there is an instruction: an update tool that keeps a field when its member is absent clears it when the member is `null`. `Nullable[T]` is that field type. It is a plain struct, `Present`, `Null` and `Value`, so a handler reads it without methods, and its zero value is the absent member. An absent member leaves `Present` false; `null` sets `Present` and `Null`; any other value sets `Present` and holds the value in `Value` exactly as a field of type `T` would. The value is validated as `T` is, so every offence path is unchanged.

Because the `null` is meaningful here, the schema promises it, unlike a pointer's tolerated `null`: the `type` member becomes the pair of `T`'s type and `"null"`, and an `enum` gains `null` as its last value, since JSON Schema 2020-12 lets `type` be an array of unique type names ("The value of this keyword MUST be either a string or an array", Validation section 6.1.1) and an `enum` element be any JSON value, `null` included (section 6.1.2). Every JSON Schema draft the revisions could mean reads both the same way. So `Nullable[json.RawMessage]`, the shape an object that can be cleared takes, has the schema `{"type":["object","null"]}`, and a type mismatch against it reads `expected object or null`.

`Nullable` belongs to `In` only. An `Out` value already says "none" by leaving a member out, and a written `null` would need its own rule, so `Nullable` in `Out` panics at registration; so does a `Nullable` anywhere but as a struct field's type, and one wrapping a pointer or another `Nullable`, which would add a fourth state with no meaning. A `Nullable` field may be marked required: the member must then be sent, and `null` is a sent value.

## Writing Out

An `Out` value is written as the object its schema describes: members in field order, non-pointer members always present, nil pointers omitted, nil slices written as empty arrays so `type: "array"` holds. A value the schema cannot carry — a non-finite float, or an enum-typed string outside its list — makes the value unencodable, which D08 turns into a generic error result and a `tool.called` event with the outcome `unencodable_output`; nothing is written to standard error.

## REQUIREMENTS

- R-U2UU-HRWG: `AddTool` MUST panic, as D08 states for registration panics, when `In` or `Out` is not a struct type, and `AddRawTool` MUST panic when `In` is not a struct type.
- R-6MRV-S1RK: The schema of a struct type MUST be a JSON object with, in this order, `type` equal to `"object"`; `properties`, an object holding one member per property of the struct, present only when the struct has at least one property; `required`, an array of the names of the properties whose field's `mcp` struct tag is exactly `required` (such a property is marked required), in property order, present only when that array is non-empty; and `additionalProperties` equal to `false`.
- R-TRVR-1U87: The properties of a struct MUST be its exported, non-embedded fields other than those whose `json` tag is exactly `-`, in field declaration order, each named by the name part (the text before the first comma) of its `json` tag; unexported fields MUST contribute nothing.
- R-6NZS-5TI9: `AddTool` and `AddRawTool` MUST panic when a property's field has no `json` tag or an empty name part, or when a property name does not match `^[A-Za-z_][A-Za-z0-9_]*$`.
- R-6P7O-JL8Y: `AddTool` and `AddRawTool` MUST panic when a field's `json` tag contains a comma, when a field carries an `mcp` struct tag whose value is not exactly `required`, and when a field that is not a property carries an `mcp` struct tag.
- R-TT3N-FLYW: When a property's field carries a non-empty `description` struct tag, the property's schema MUST end with a member `description` whose value is the tag's value unaltered; otherwise the property's schema MUST have no `description` member.
- R-TVJG-75GA: The schema of a type of kind `string` that does not implement `Enumerator` MUST be `{"type":"string"}`, of kind `bool` `{"type":"boolean"}`, of kind `int`, `int8`, `int16`, `int32`, or `int64` `{"type":"integer"}`, of kind `uint`, `uint8`, `uint16`, `uint32`, or `uint64` `{"type":"integer","minimum":0}`, and of kind `float64` `{"type":"number"}`.
- R-TWRC-KX6Z: The schema of a type `T` of kind `string` where `T` or `*T` implements `Enumerator` MUST be `{"type":"string","enum":[...]}`, whose `enum` holds the values `Enum` returns on the zero value of `T` at registration, in that order.
- R-U42Q-VJN5: `AddTool` and `AddRawTool` MUST panic when, for a type `T` of kind `string` where `T` or `*T` implements `Enumerator`, `Enum` returns no values or the same value twice, and when `T` or `*T` implements `Enumerator` for a non-pointer type `T` whose kind is not `string`.
- R-TPFY-AAQT: The schema of a slice type other than `json.RawMessage` MUST be `{"type":"array","items":<element schema>}`, where `<element schema>` is the schema of the element type, and `AddTool` and `AddRawTool` MUST panic for any other slice whose element kind is `uint8`.
- R-PI8U-UZFZ: A `Nullable` type is an instantiation of `Nullable`, never a type defined from one; no requirement of D07 to D10 that applies to struct types applies to a `Nullable` type itself, so its fields `Present`, `Null` and `Value` are never properties and its schema and decoding are only those that requirements naming `Nullable` state, while its `T` is subject to every requirement that applies to the type of a struct field. The schema of any other struct-typed field MUST be the schema of that struct type, and any other struct type nested in `In` or `Out` MUST follow the same rules as the top-level struct.
- R-TZ75-CGOD: The schema of a field of type `*T` MUST be the schema of `T`, and `AddTool` and `AddRawTool` MUST panic for a pointer type anywhere other than as the type of a struct field, and for a pointer to a pointer.
- R-TQNU-O2HI: The schema of a struct field of type `json.RawMessage` MUST be `{"type":"object"}` (with no `additionalProperties` member), and `AddTool` and `AddRawTool` MUST panic when `json.RawMessage` appears anywhere other than as the type of a struct field, including as a slice element type and as the type a pointer points to.
- R-BPVL-RNX0: A JSON object received for a `json.RawMessage` field MUST be accepted whatever its members, and any other JSON value, `null` included, MUST be a type-mismatch offence against `object`.
- R-6QFK-XCZN: `AddTool` MUST panic when a field of type `*T` anywhere in `Out` is marked required.
- R-MJHL-D11C: `AddTool` and `AddRawTool` MUST panic when `In` or `Out` contains a type of kind `map`, `interface`, `array`, `float32`, `complex64`, `complex128`, `chan`, `func`, `uintptr`, or `unsafe.Pointer`.
- R-GT7Q-O5ZL: `AddTool` and `AddRawTool` MUST panic when `In` or `Out` contains a type `T` other than `json.RawMessage` where `T` or `*T` implements `json.Marshaler`, `json.Unmarshaler`, `encoding.TextMarshaler`, or `encoding.TextUnmarshaler`.
- R-U5AN-9BDU: `AddTool` and `AddRawTool` MUST panic when a struct in `In` or `Out` has an embedded (anonymous) field, whatever its tag.
- R-U6IJ-N34J: `AddTool` and `AddRawTool` MUST panic when `In` or `Out` contains a struct type that contains itself, directly or through other types.
- R-U0F1-Q8F2: A derived schema MUST contain no members other than those these requirements state, and in particular no `$schema` member.
- R-U1MY-405R: Every schema member these requirements list in a given order MUST appear in that order, with `description` always last.
- R-PFT2-3FYL: A JSON value whose JSON type matches neither its schema's `type` nor, when that `type` is an array, any of its elements — `null` for anything other than a field of pointer type or of a `Nullable` type, any number for `integer` or `number` being a match — MUST be a type-mismatch offence.
- R-BL00-8KY8: A member of an arguments object that names no property of its schema MUST be an unknown-member offence, once per occurrence.
- R-BM7W-MCOX: A property marked required whose member is absent from an arguments object MUST be a missing-required-member offence.
- R-BNFT-04FM: A property whose member appears more than once in an arguments object MUST be a single duplicate-member offence, and none of that member's values MUST be validated further.
- R-MVOL-6QGA: A JSON number received for an `integer` schema MUST be accepted exactly when its value has a zero fractional part, whatever its notation (so `3`, `3.0`, and `3e0` are the integer 3); otherwise it MUST be a non-integral-number offence.
- R-MWWH-KI6Z: An integral JSON number outside the range of the field's Go integer kind MUST be an integer-range offence.
- R-MY4D-Y9XO: A JSON number received for a `float64` whose magnitude exceeds the largest finite `float64` MUST be a float-range offence; any other JSON number MUST be accepted as the nearest `float64`.
- R-N0K6-PTF2: A JSON string received for an `Enumerator` type that is not one of the values in its schema's `enum` MUST be an enum offence.
- R-BR3I-5FNP: JSON `null` received for a field of type `*T` MUST be accepted, whether or not the field is required, and decoded as a nil pointer.
- R-BONP-DW6B: Every offence in an arguments value MUST be found, including offences in every element of an array and in every member of nested objects, except within a duplicated member's values.
- R-VBQP-WXUR: When the arguments hold no offence, the handler's `In` MUST hold, for every property whose field is not of a `Nullable` type and whose member is present, the member's value — strings unaltered, integers and numbers as received, arrays as slices of the same length and order, objects for a struct-typed field decoded by the same rule, objects for a `json.RawMessage` field as its bytes unaltered — and for every absent property the field's zero value, a nil pointer for an absent or `null` pointer field and a nil `json.RawMessage` for an absent `json.RawMessage` field.
- R-6RNH-B4QC: The JSON encoding of an `Out` value MUST be an object with, in property order, one member per property of its struct type, where a non-pointer field other than a `json.RawMessage` is always present, a nil pointer field is absent, a non-nil pointer field is encoded as the value it points to, a nil slice other than a `json.RawMessage` is encoded as `[]`, a non-nil `json.RawMessage` is written as its bytes unaltered, a nil `json.RawMessage` in a field not marked required is absent, and nested structs are encoded by the same rule.
- R-U7QG-0UV8: In the JSON encoding of an `Out` value, a string MUST be encoded with each invalid UTF-8 byte replaced by U+FFFD, a `bool` as `true` or `false`, an integer kind as a JSON integer of the same value, and a `float64` as a JSON number that parses back to the same `float64`.
- R-6SVD-OWH1: An `Out` value MUST be unencodable when it contains a `float64` that is NaN or infinite, a value of an `Enumerator` type that is not one of the values in its schema's `enum`, a nil `json.RawMessage` in a field marked required, or a non-nil `json.RawMessage` that is not exactly one JSON object.
- R-P61V-1A11: Package `mcp` MUST export `type Nullable[T any] struct { Present, Null bool; Value T }`, with exactly these fields in this order and no exported methods.
- R-P79R-F1RQ: The schema of a field of type `Nullable[T]` MUST be the schema of `T` with its `type` member's value replaced by an array of two strings, the `type` value of `T`'s schema followed by `"null"`, and, when `T`'s schema has an `enum` member, with JSON `null` appended as the last element of that `enum` array; every other member of `T`'s schema MUST be kept, unaltered and in its order; so the schema of a field of type `Nullable[json.RawMessage]` without a `description` tag is `{"type":["object","null"]}`.
- R-P8HN-STIF: `AddTool` and `AddRawTool` MUST panic when a `Nullable[T]` type is `In` itself, the element type of a slice, or the type a pointer points to, and when `In` contains a `Nullable[T]` type whose `T` is a pointer type or a `Nullable` type.
- R-P9PK-6L94: `AddTool` MUST panic when `Out` contains a `Nullable[T]` type anywhere.
- R-PAXG-KCZT: JSON `null` received for a field of type `Nullable[T]` MUST be accepted, whether or not the field is marked required, and the handler's `In` MUST hold for that field a `Nullable[T]` whose `Present` and `Null` are true and whose `Value` is the zero value of `T`.
- R-PC5C-Y4QI: A JSON value other than `null` received for a field of type `Nullable[T]` MUST yield exactly the offences, at the same paths, that the same value received for a field of type `T` would yield, except that a type-mismatch reason is as R-PH0Y-H7PA states for the field's own schema; and when the arguments hold no offence the handler's `In` MUST hold for that field a `Nullable[T]` whose `Present` is true, whose `Null` is false, and whose `Value` equals what a field of type `T` would hold for the same member under R-VBQP-WXUR.
- R-PEL5-PO7W: When the member of a field of type `Nullable[T]` is absent from an arguments object that holds no offence, the handler's `In` MUST hold for that field the zero `Nullable[T]`, whose `Present` and `Null` are false and whose `Value` is the zero value of `T`.
