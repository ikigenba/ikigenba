# Decision 19 — `appkit/httpclient`: the shared instrumented outbound client

**Problem.** Eight services make outbound HTTP calls (gmail, dropbox, github,
notify, sites, repos, wiki, and the dashboard's IdP calls), each with its own
`http.Client`. Those calls are the one class of suite activity a request
recorder cannot see, and they are where a chain leaves the box — so they are
both the biggest forensic blind spot and the place where propagating a
correlation id to a **third party** would leak internal identifiers to
Google, Dropbox, and GitHub.

**Decision.** A new package `appkit/httpclient` provides one instrumented
client, built as a `http.RoundTripper` so a service swaps its client and
changes nothing else about how it makes requests.

```go
package httpclient // appkit/httpclient

type Options struct {
    Recorder *telemetry.Recorder // nil ⇒ no recording, still a working client
    Timeout  time.Duration       // default 30s
    Base     http.RoundTripper   // default http.DefaultTransport
}

// New returns an *http.Client whose transport records every round trip and
// propagates the correlation id to loopback suite peers only.
func New(opts Options) *http.Client

// NewTransport is the same instrumentation as a bare RoundTripper, for callers
// that build their own *http.Client (custom redirect or cookie policy, or a
// per-client timeout like a long-poll's).
func NewTransport(opts Options) http.RoundTripper
```

`Options.Base` is what keeps a service's existing offline unit tests working:
a test injects its stub `http.RoundTripper` there and the instrumentation
composes over it. Most services never call `New` directly — D20's
`rt.HTTPClient(timeout)` wires the recorder for them in one line; `New` and
`NewTransport` are for the callers that need a custom transport, redirect
policy, or client shape.

Per round trip the transport:

1. **Propagates conditionally.** It sets `correlation.Header` to
   `correlation.FromContext(req.Context())` **only when the request URL's host is a
   loopback IP literal** — `127.0.0.0/8` or `::1`. Anything else (a public
   host, and deliberately also the *name* `localhost`) gets no header. A name
   can resolve anywhere; only an IP literal is provably on-box.
2. **Records** a `telemetry.Record`: `kind` `outbound`, `op`
   `<METHOD> <host><path>` (host including port, path without query),
   `correlation_id` from the context, `outcome.status` = the numeric response
   status as a decimal string, `outcome.duration_ms`, `outcome.bytes` /
   `outcome.sha256` = size and digest of the **response body**, and `detail`
   `{"request_bytes": N, "request_sha256": "<hex>"}` for the request body.
   Both digests are computed **streaming**, by wrapping the request and
   response body readers, so no body is ever buffered or retained.
3. **Records failures too.** A transport error (refused connection, timeout,
   DNS failure) records `outcome.status` `error` with `outcome.error` carrying
   the error **class** — `timeout`, `connection_refused`, `dns`, or
   `source_unavailable` as the residue — never the raw error text (which can
   embed a URL with credentials). The error is returned to the caller
   unchanged.
4. **Never carries `params`.** The op names the endpoint; query strings on
   third-party calls routinely carry tokens and are deliberately not captured.

The response record is emitted when the response body is closed (or on error),
so `outcome.bytes` reflects what the caller actually read to completion. A
caller that abandons a body still gets a record at `Close`.

**Judgment calls recorded.** (a) Loopback is decided by IP literal, not by
name resolution: `localhost` is not propagated to. (b) The request-side size
and digest live in `detail` because the contract's `outcome` describes the
response; `detail` is the record's slot for small kind-specific extras.
(c) Query strings are excluded from outbound records entirely. (d) Error
classes are a small closed set rather than the raw error string.

**Rejected.**
- **A wrapper struct with its own `Get`/`Post` methods** — every call site
  would have to be rewritten rather than re-pointed, and any code taking an
  `*http.Client` (SDKs, oauth2) could not use it.
- **Propagating the id to every host** — leaks a suite-internal chain
  identifier into third-party logs for no benefit to us.
- **Resolving the host to decide loopback** — a DNS lookup per request, on the
  hot path, to answer a question an IP literal already answers, and a
  rebindable name could flip the answer between check and dial.
- **Recording before the round trip returns** — the size and status of the
  response are the whole point of the record.
- **Buffering bodies to digest them** — an upload or a large fetch would be
  duplicated in memory.

**Verification** (against **real** HTTP: `httptest.NewServer` for the success
paths, a genuinely closed port for the failure path — a stub transport cannot
falsify "the header actually went on the wire" or "a refused connection still
records").
- R-22VU-7KW7 — a `POST` through the client to a live `httptest` server records
  `kind` `outbound`, `op` `POST <host:port><path>`, `outcome.status` equal to
  the status the server returned, a non-negative `duration_ms`, `outcome.bytes`
  and `outcome.sha256` equal to the length and SHA-256 of the real response
  body, and `detail.request_bytes` / `detail.request_sha256` matching the real
  request body.
- R-25BM-Z4DL — a request to a live server addressed as `127.0.0.1:<port>`
  arrives at that server carrying `X-Correlation-Id` equal to the id on the
  caller's context — observed **by the server**, not by inspecting the request
  struct.
- R-26JJ-CW4A — the same live server addressed as `localhost:<port>` (a real,
  successful round trip) receives **no** `X-Correlation-Id` header at all — the
  discriminating property against a build that propagates by any-loopback or
  unconditionally.
- R-27RF-QNUZ — a request to a closed port returns the transport error to the
  caller **and** still emits an `outbound` record whose `outcome.error` is
  `connection_refused` and whose `op` names the attempted method and host —
  and the record's JSON does not contain the raw Go error text.
- R-28ZC-4FLO — a client built with a nil `Recorder` completes a real request
  against a live server normally (correct status and body) and emits no
  records — instrumentation is never load-bearing for the request itself.
