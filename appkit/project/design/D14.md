# Decision 14 — Correlation context: read-or-mint at the chassis edge, Crockford ULIDs

**Problem.** Every suite service already tags each inbound HTTP request with a
**fresh** id (`logging.RequestIDMiddleware` mints one per hop). That is exactly
wrong for forensics: a chain that crosses four services produces four unrelated
ids, so nothing ties the hops together. The suite telemetry capability needs
**one id per causal chain, propagated verbatim on every hop**
(`project/design/D14.md` at the repo root), and the chassis is the only place every service's
inbound traffic passes through. Two further defects block that: appkit's
`logging.NewULID` encodes with **RFC 4648** base32 (alphabet `A–Z2–7`), not the
**Crockford** base32 the suite standard specifies, so appkit-minted ids are not
suite ULIDs at all; and appkit owns the context key for its request id, which
would force `eventplane` (which must never import appkit) to duplicate it.

**Decision.** The correlation id becomes a first-class chassis concept sourced
from the shared leaf package **`eventplane/correlation`** (owned by the
eventplane workspace — see `project/research/research.md`; appkit consumes it
and designs none of its internals):

```go
// eventplane/correlation — consumed, not designed here.
const Header = "X-Correlation-Id"          // the wire header
func New() string                          // mints a 26-char Crockford ULID
func Valid(s string) bool                  // 26 chars, Crockford alphabet only
func WithContext(ctx context.Context, id string) context.Context // ignores an invalid id
func FromContext(ctx context.Context) string                     // "" when absent
func Ensure(ctx context.Context) (context.Context, string)       // read-or-mint
```

appkit's changes:

- **`logging.RequestIDMiddleware` becomes read-or-mint** and is renamed
  `logging.CorrelationMiddleware(logger, next)` (the old name is deleted, not
  aliased — every mount of it is inside appkit). Per request:
  1. read the `correlation.Header` value; if `correlation.Valid` accepts it,
     attach it with `correlation.WithContext` and **use it verbatim** —
     loopback callers are inside the trust boundary, so an inbound id is
     trusted and never re-minted;
  2. otherwise (absent, or malformed) take `correlation.Ensure(ctx)`, which
     mints a fresh root. A malformed inbound value is never propagated —
     `WithContext` would ignore it anyway, and `Ensure` is the primitive that
     names this intent;
  3. the id lives on the context under `correlation`'s own key — the single
     home shared with eventplane;
  4. echo it on the response as `X-Correlation-Id`, and keep the existing
     `X-Request-ID` response header carrying **the same value** so nothing
     already reading it breaks;
  5. emit the existing `request.begin` / `request.end` debug records with the
     id under the `correlation_id` attribute.
- **`logging.RequestID(ctx)`** is retained as a thin read of
  `correlation.FromContext(ctx)` — one id in flight, never two. `logging.WithRequestID`
  is deleted; callers use `correlation.WithContext`.
- **`logging.NewULID` is fixed to Crockford base32** — alphabet
  `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (no `I`, `L`, `O`, `U`), same 48-bit
  millisecond + 80-bit random construction, still 26 characters. This is the
  minter the rest of appkit (record ids) uses; it now agrees with
  `correlation.New()` and with `project/design/D14.md` at the repo root.

**Judgment calls recorded.** (a) `X-Request-ID` is kept as a mirror rather than
deleted — it costs one header set and removes a migration from every consumer of
the old header. (b) A malformed inbound id is replaced rather than passed
through: an id the suite cannot parse is worse than a fresh one, and the trust
argument covers well-formed peers, not corrupt input. (c) The mint-vs-trust
decision lives in the chassis middleware, not in nginx-shaped conditionals —
nginx's strip-and-mint rules (suite-level) decide what reaches us; the chassis
just honors what arrives.

**Rejected.**
- **An appkit-owned correlation package** — eventplane must not import appkit,
  and the id must live on the same context key both libraries read; a leaf
  package below both is the only shape that works.
- **Keeping a per-hop request id beside the correlation id** — two ids on every
  record and log line, with the per-hop one carrying no information the record
  id does not already carry.
- **Trusting the inbound header unconditionally** — a public caller can never
  reach a service without crossing nginx (which overwrites or clears the
  header), but validating costs one alphabet scan and makes the invariant
  "every id in a record is a well-formed suite ULID" true by construction.
- **Leaving `NewULID` on RFC 4648 and minting correlation ids separately** —
  two ULID shapes in one binary, and appkit-minted record ids would be
  unsortable against suite ids in the telemetry store.

**Verification** (via `httptest` through the real middleware and the real
`server.New` mux — the substrate that can falsify header handling).
- R-14QN-I04R — a request carrying a **valid** `X-Correlation-Id` reaches the
  inner handler with `correlation.FromContext(ctx)` equal to that exact value, and the
  response echoes the same value — a build that mints fresh per hop fails this.
- R-15YJ-VRVG — a request with **no** `X-Correlation-Id` reaches the inner
  handler with a non-empty ctx id that is 26 characters and passes
  `correlation.Valid`, and the response echoes it.
- R-176G-9JM5 — a request carrying a **malformed** `X-Correlation-Id` (wrong
  length, and separately a 26-char value containing `I`/`L`/`O`/`U`) reaches the
  inner handler with a **different**, valid, freshly minted id — the malformed
  value never appears in the ctx or on the response.
- R-18EC-NBCU — over 500 `logging.NewULID()` mints, every character is in the
  Crockford alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, none of `I`,`L`,`O`,`U`
  ever appears, digits `0`/`1` do appear (impossible under RFC 4648's `A–Z2–7`),
  and every value is 26 characters — a build still on RFC 4648 fails this.
- R-19M9-133J — the response of a request through `server.New`'s real chain
  carries `X-Correlation-Id` and `X-Request-ID` with the **same** value, equal
  to the id the inner handler observed on its context.
