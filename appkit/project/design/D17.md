# Decision 17 — Inbound instrumentation: MCP tool calls and plain HTTP requests

**Problem.** Recording has to be automatic. If instrumenting were a per-service
obligation, coverage would be exactly as uniform as the twelve hand-copied MCP
transports were before the chassis absorbed them — which is to say, not.
Everything inbound crosses two chassis seams already: `mcp.Handler.dispatchTool`
for MCP traffic and the `server.New` middleware chain for everything else.
Instrumenting those two seams instruments the whole suite by recompile — and
the uniformity argument applies to the **wiring** as much as to the call sites:
a recorder a fragment must remember to pass is a per-service obligation in
disguise, and the type system will not flag the omission because a nil recorder
no-ops by design.

**Decision.** The chassis delivers the recorder to both seams **by
construction**: the `server.New` middleware chain installs the process recorder
on **every** request's context (excluded paths and the MCP mount included —
exclusion suppresses the HTTP record, never the context), and the MCP handler
reads it from there. No fragment passes a recorder anywhere.

**(a) The context seam — `telemetry` package.**

```go
package telemetry // appkit/telemetry

// WithRecorder returns ctx carrying r for downstream instrumentation sites.
func WithRecorder(ctx context.Context, r *Recorder) context.Context

// RecorderFromContext returns the recorder installed by the serve chain, or
// nil when absent (a bare test context) — and a nil *Recorder no-ops, so an
// unwired unit test behaves exactly as today.
func RecorderFromContext(ctx context.Context) *Recorder
```

`server.New`'s chain installs it once, above the mux, before any skip logic:
`securityHeaders(logging.CorrelationMiddleware(logger, recorderContext(rec, recordMiddleware(rec, mux))))`.
Installation is unconditional — a request whose HTTP record is suppressed
(`RecordExclude`, `POST /mcp`) still carries the recorder, because the richer
MCP-layer record depends on it.

**(b) MCP tool calls — `mcp` package.** `mcp.Options` carries **no recorder
field**: `dispatchTool` obtains the recorder via
`telemetry.RecorderFromContext(ctx)` per call. A handler mounted under the
chassis serve path is therefore recorded with zero wiring in the fragment that
built it; a handler driven outside the serve path (a bare unit test) finds nil
and no-ops.

```go
type Tool struct {
    // …existing fields…
    // SensitiveParams names arguments whose values must NEVER be captured in
    // telemetry, regardless of size. They are elided in place (D16 step 2).
    SensitiveParams []string
}
```

`dispatchTool` wraps every call — standard tools included — with a record:

- `kind` = `request`, `op` = `mcp:<tool-name>`;
- `actor` = `{owner_email, client_id}` from the `server.Identity` already
  threaded to the handler, fields omitted when empty;
- `correlation_id` = `correlation.FromContext(ctx)`;
- `params` = `telemetry.EncodeParams(args, tool.SensitiveParams)`;
- `outcome.duration_ms` = the wall time of the handler call;
  `outcome.status` = `ok` or `error`; `outcome.bytes`/`sha256` =
  `telemetry.Digest` over the **marshaled result**;
- `outcome.error` = the **class**: the `mcp.ErrorCode` when the tool returned a
  coded `ErrorResult`, or `internal` when the handler returned a Go error.
  A raw error message is never copied into a record.
- An unknown tool name records with `op` = `mcp:<name>` and error class
  `validation`, so probing shows up in the trail.

**(c) Plain HTTP — `server` package.** `Options` keeps
`Recorder *telemetry.Recorder` (the process recorder `runServe` passes — this
is the chassis's own construction seam, not a fragment obligation) and
`RecordExclude []string`. Per request:

- `kind` = `request`, `op` = `<METHOD> <path>` (the post-strip path the service
  actually sees);
- `actor` resolved from two sources, in order. The record middleware sits
  **above** the mux, so it cannot see the identity a downstream gate installs
  on its derived context; instead it plants a capture slot on the request
  context and `withIdentity` fills it. (1) The **captured identity** when an
  inner gate ran — the validated source, and the only one for routes whose
  identity is not header-borne (the dashboard apex's session-authenticated
  routes). (2) Otherwise the raw `X-Owner-Email` / `X-Client-Id` **request
  headers** — authoritative under D13's trust boundary (loopback bind, nginx
  the only ingress) — so a request that dies before any gate runs still
  records its caller; the canonical case is the mux-synthesized `405` when a
  `GET /mcp` mismatches the `POST /mcp` method pattern and no appkit handler
  ever executes. When both sources are empty (direct loopback callers,
  ungated routes) the fields are simply omitted;
- `params` = `telemetry.EncodeParams` over the **URL query** rendered as an
  object. **Request bodies are never read** — reading one would consume the
  handler's reader and could capture arbitrary content;
- `outcome.status` = the numeric HTTP status as a decimal string;
  `outcome.duration_ms`; `outcome.bytes`/`sha256` computed by extending the
  existing `statusRecorder` with a running byte count and a streaming
  `sha256.Hash` — the body is digested as it is written and **never buffered**;
- the record is emitted after the handler returns (so an SSE stream records
  once, at stream end).

`/health` is recorded like everything else: uniformity beats noise-trimming,
because "the service answered health checks the whole time" is itself a
forensic fact.

**(d) The exclusion mechanism.** `Spec.TelemetryExclude []string` carries exact
request paths that produce **no** request record; `runServe` passes it to
`server.Options.RecordExclude`. Its purpose is the telemetry service's own
`/ingest` route — recording ingest is an infinite regress. Additionally the
chassis **always** excludes the MCP mount path (`POST /mcp`) from the HTTP
recorder, because `dispatchTool` already emits the richer per-tool record;
without that, every tool call would produce two records.

**Judgment calls recorded.** (a) Exclusion is an exact-path list on `Spec`,
not a per-route wrapper: the recorder sits in the middleware chain above the
mux, so it cannot see per-route registration, and an exact-match list is
trivially checkable. (b) `POST /mcp` is suppressed at the HTTP layer rather
than the MCP layer being demoted, keeping the richer record. (c) Query strings
are captured as params but bodies never are. (d) Error classes come from the
closed `mcp.ErrorCode` vocabulary rather than free text. (e) The recorder
reaches the MCP layer via the request context installed by the serve chain —
one chassis-owned write point — never via a per-fragment option; context
installation is unconditional even where the HTTP record is suppressed.
(f) The HTTP recorder falls back to the raw identity headers rather than
recording anonymous: telemetry is forensics, not authorization, and the record
should carry the best information the request bore no matter how shallow in
the stack it died — but the captured (gate-validated) identity always wins
when present, because for session-authenticated routes the headers are absent
or wrong.

**Rejected.**
- **Per-service instrumentation calls** — the drift the chassis exists to end.
- **An optional `mcp.Options.Recorder` field** — a per-fragment wiring
  obligation the compiler cannot enforce: nil is a valid value, the no-op is
  silent, and the omission surfaces only as forensic records that never
  existed. The Problem paragraph's uniformity argument applies to wiring, so
  the wiring must be chassis-owned.
- **Recording at the `Router` registration seam** — misses routes registered
  by the chassis itself and offers no single place to read the response size.
- **Buffering response bodies to digest them** — turns every large content
  response into a second full copy in memory.
- **Skipping `/health`** — cheap to record, and its absence is the kind of gap
  that makes a forensic timeline ambiguous.
- **Capturing request bodies** — cannot be done without consuming or
  duplicating the reader, and is exactly the bulk content the capability
  refuses to store.

**Verification** (through the real `ServeHTTP` JSON-RPC seam and the real
`server.New` mux via `httptest`, with a real recorder draining to a live
in-process sink or an inspectable in-memory ring; MCP-layer tests deliver the
recorder the way production does — `telemetry.WithRecorder` on the request
context — never through a constructor field).
- R-1PGY-03QK — one `tools/call` produces **exactly one** record with
  `kind` `request`, `op` `mcp:<tool>`, `service` set, `actor.owner_email` /
  `actor.client_id` equal to the request's identity headers, and
  `correlation_id` equal to the id on the request context.
- R-1QOU-DVH9 — that record's `outcome` carries a non-negative `duration_ms`,
  `status` `ok`, and `bytes`/`sha256` equal to the length and SHA-256 of the
  marshaled tool result; and the record's full JSON contains **none** of a
  distinctive marker string the tool put in its response body — response
  content is never stored.
- R-1RWQ-RN7Y — a tool returning a coded `ErrorResult` records `status`
  `error` with `outcome.error` equal to that `ErrorCode`; a tool handler
  returning a Go error records `status` `error` with `outcome.error` `internal`
  and **not** the error's message text; both records are still emitted.
- R-1T4N-5EYN — a tool call whose arguments include a param declared in
  `Tool.SensitiveParams` records that param as an `$elided` marker while an
  undeclared sibling argument is captured literally, and an argument exceeding
  1024 bytes is elided per D16.
- R-1UCJ-J6PC — through the real `server.New` chain: `GET /health` produces a
  record with `kind` `request`, `op` `GET /health`, `outcome.status` `"200"`,
  and `bytes`/`sha256` matching the real response body; and a `POST /mcp` tool
  call produces **exactly one** record in total (the `mcp:<tool>` one), never a
  second `POST /mcp` record.
- R-1VKF-WYG1 — a path listed in `Options.RecordExclude` produces **zero**
  records while a sibling path served by the same server produces one — a
  build that ignores the exclusion list fails this.
- R-RI9E-W0G2 — an MCP handler built with **no recorder anywhere in its
  construction**, mounted at `POST /mcp` under the real `server.New` chain
  (whose `Options.Recorder` is the process recorder), yields a tool call whose
  `mcp:<tool>` record arrives at a live sink carrying the request's identity
  and correlation id — the by-construction wiring claim; a build that still
  requires a per-fragment recorder field fails this.
- R-RKP7-NJXG — `mcp.Options` exposes no recorder-typed field (asserted via
  reflection over the struct's fields, so a reintroduced per-fragment wiring
  seam fails); and `dispatchTool` driven with a bare context carrying no
  recorder completes the call normally and emits nothing — the safe-degradation
  half of the context seam.
- R-K59U-9DWS — through the real `server.New` chain with an MCP handler
  mounted, a `GET /mcp` carrying `X-Owner-Email` / `X-Client-Id` headers is
  answered `405` (the mux-synthesized method mismatch — no identity gate ever
  runs) and produces a request record with `op` `GET /mcp`, `outcome.status`
  `"405"`, and `actor.owner_email` / `actor.client_id` equal to those headers —
  a build that records this request as anonymous fails.
- R-K6HQ-N5NH — a route whose handler establishes identity through the
  identity seam with values **different** from the request's identity headers
  records the established identity, not the headers — the captured
  (gate-validated) source wins over the raw-header fallback.
