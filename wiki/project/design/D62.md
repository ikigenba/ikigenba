# Decision 62 — Origin attribution on every inference call

**Decision.** Every call wiki makes to prompts carries an **origin** naming the causing identity, from prompts' grammar (research §12). Origin answers *who caused this*; the causal-chain correlation is a separate concern owned by D64 (the chain id wiki receives and forwards) and D65 (where a background job's chain id comes from) — this Decision owns origin alone.

**Origin** (`user:<email>` | `trigger:<source>` | `service:wiki`):

- **Ask path** (MCP `ask` tool or the web `?q=` surface): `user:<email>` from the request identity the chassis already provides (MCP `Identity` / the session-gated web request's owner). Applies to `wiki.embed-query`, `wiki.ask-subject`, `wiki.ask-synthesis`.
- **Job-driven pipeline** (`wiki.extract`, `wiki.compile`, `wiki.embed-page`, merge's LLM work): `user:<job.owner_email>` — the job's write-once `owner_email` snapshot (D3 conversion) records who enqueued the ingest; carried from the job row into every call the worker makes for it. The origin token keeps the suite grammar's `user:<email>` shape, sourced from the display snapshot; the durable `owner_id` is the row's key but is not the origin token's form. When `owner_email` is empty (rows created with no forwarded email, internally-generated work): `service:wiki`.
- **Event-triggered work** (none exists today — wiki neither produces nor consumes event-plane events; e.g. a future dropbox ingest-folder consumer): `trigger:<source>` per the grammar — stated here so the case lands correctly when built.

**Threading.** Origin travels as one half of the D5 `Attribution` value, passed explicitly down the call chain (worker → extract/compile/embed-page; ask handler → retrieve/ask sites); D64 owns the other half. No context-smuggling **for origin**: the old `WithJobID` context key retired with the recorder (D63), and origin is a visible parameter because stages now *must* supply it. The correlation half legitimately arrives on the context, because the chassis puts it there for every inbound request (D64).

**Rejected.**
- **`service:wiki` for everything** — simplest, but discards causing-identity attribution prompts' `usage` can group by, which the owner explicitly wants tied back to the initial user action.
- **Context-key threading for origin (the old `WithJobID` pattern)** — invisible parameters invite a stage to silently drop attribution; an explicit `Attribution` argument makes the compiler enforce it.
- **A second wiki-side attribution store** — origin lives on prompts' rows; wiki holds it only in flight.

**Verification.**
- R-16VU-W6UV — An ask driven with identity `alice@example.com` posts **all** its `/complete` and `/embed` calls with `origin` `user:alice@example.com` (captured via the httptest prompts through the real ask path).
- R-183R-9YLK — A worker-processed job whose row carries `owner_email` `bob@example.com` posts its extract, compile, and embed-page calls with `origin` `user:bob@example.com`; the same job with an empty `owner_email` posts `origin` `service:wiki`.
