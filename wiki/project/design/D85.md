# Decision 85 — Orphan-free page embeddings: guarded writes, subject-joined hydration, sweep reaping

**Decision.** No `page_embeddings` row may outlive its subject — durably, unattended, on every path. The operator's standing constraint is that every inconsistency between the database and a derivative is **self-healing**; a durable orphan row is the one way today's embedding lifecycle can violate it permanently. The known minting path: the catch-up sweep (D35) selects its candidates, a `scope_delete` (D74) commits between selection and store, and the sweep then re-inserts an embedding row for a subject that no longer exists. Worse, startup hydration (`LoadVectorCacheEntries`) resolves each embedding's scope with a bare subject lookup that **errors** on a missing subject — one stray orphan row prevents the service from booting. Three cooperating pieces — the guard prevents, the load tolerates, the reap converges:

**1. Guarded write.** `EmbeddingStore.Upsert` lands only if the subject row exists **at write time**, enforced inside the write statement itself:

```sql
INSERT INTO page_embeddings (subject_id, model, dims, vec, content_hash, updated_at)
SELECT ?, ?, ?, ?, ?, ?  WHERE EXISTS (SELECT 1 FROM subjects WHERE id = ?)
ON CONFLICT(subject_id) DO UPDATE SET ...
```

Because all writes serialize on the single writer (D17), a `scope_delete` and a sweep store cannot interleave: whichever commits second sees the other's outcome. A store for a vanished subject is a silent no-op (zero rows), never an error — the sweep's work item simply evaporated, which is the expected outcome of the race, not a failure. `Upsert` returns its underlying database error otherwise, as today.

**2. Subject-joined hydration.** Startup hydration reads embeddings **joined against `subjects`** (one query returning subject id, scope, and vector; the page title still comes from `pages` as today). An orphan row — from any cause, foreseen or not — is simply not selected: it cannot fail boot and cannot enter the cache. The current per-embedding `SELECT scope FROM subjects` (which returns `sql.ErrNoRows` on an orphan and aborts startup) is deleted. Hydration still fails loudly on real database errors — tolerance is for the *orphan*, not for a broken store.

**3. Sweep reaping.** Each catch-up cycle (D35's worker) first deletes any orphan rows:

```sql
DELETE FROM page_embeddings
WHERE subject_id NOT IN (SELECT id FROM subjects)
```

This is the convergence guarantee: even an orphan minted by a cause this design has not foreseen is removed within one sweep cycle, unattended, and the next hydration is clean. The reap runs on the write handle (serialized, D17), is O(orphans) against an indexed key, and needs no scheduling of its own — it rides the existing sweep cadence.

**Error surface.** The guarded `Upsert` and the reap return database errors only (no new named errors); a zero-row guarded insert is success. Hydration returns database errors as today; a missing subject is no longer one of them. Nothing here panics.

**Rejected.**
- **A `subjects(id)` foreign key with `ON DELETE CASCADE`.** Already rejected by D38 for the merge path — SQLite requires a full table-rebuild migration to add a FK, and the guard+reap pair achieves the same durable invariant with code only. The scope-delete transaction already deletes the scope's embedding rows explicitly (D74); this Decision closes the *re-insertion* race the cascade cannot see.
- **Relying on the guard alone (no reap, no join).** The guard closes the known race, but "no unforeseen orphan can ever exist" is not a claim this design can make — and without the join, a single such row bricks boot: the opposite of self-healing. Tolerate at read, converge in the background.
- **Reap at startup instead of per sweep cycle.** Heals only on restart; the constraint is unattended convergence. The sweep already wakes on the right cadence.
- **Erroring (or logging loudly) when the guarded write finds its subject gone.** The vanished subject is the *expected* outcome of a sanctioned race with `scope_delete`, not a defect; an error here would train operators to ignore errors (and fail the sweep run for nothing).

**Verification.**
- R-R7IF-IID7 — The guarded `Upsert` is a no-op for a deleted subject and a real write for a live one: after deleting a subject's scope, storing an embedding for that subject leaves **zero** `page_embeddings` rows for it, while the same store against a live subject persists the row — real temp SQLite.
- R-R8QB-WA3W — Hydration tolerates an orphan: with an artificially seeded orphan `page_embeddings` row (no matching subject), `LoadVectorCacheEntries` succeeds, returns every live entry with its correct scope, and omits the orphan — where before the fix it returned an error and the service could not hydrate.
- R-R9Y8-A1UL — The sweep reaps: after a catch-up cycle runs against a store holding both live and orphan embedding rows, the orphan rows are gone and every live row is untouched — and a subsequent hydration is clean.
- R-RB64-NTLA — The race end-to-end: candidates selected, the scope deleted (rows cascaded), the sweep then stores — no orphan row exists afterward and the next hydration succeeds; the sweep run itself completes without error. Exercised through the real worker path against real temp SQLite.
