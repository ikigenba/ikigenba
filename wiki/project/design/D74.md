# Decision 74 — Scopes: named content partitions, the registry, and the hard wall

**Decision.** All wiki content is partitioned into named **scopes**. A scope is a registry row, not a database: one SQLite, with a `scope` dimension on the content tables. The partition is a **hard wall**: every content read and write names exactly one scope and sees only that scope — subjects, claims, pages, aliases, merges, jobs, keyword search, vector search, `ask`, link projection, and the home suggested-pages list never cross it. The same subject name may exist independently in any number of scopes, each with its own claims and page. There are **no per-scope ACLs**: any authenticated caller may use any scope; a scope is a namespace, not a permission boundary (visibility — who can *read a scope's web pages anonymously* — is the one exception, D76/D77).

Scopes are **explicit**: a scope must exist in the registry before use. The product's reserved scope **`default`** is seeded by migration, cannot be deleted, and is otherwise ordinary (its visibility can change like any other's). Naming an unknown scope is a **typed error** (`ErrScopeNotFound`) — never a lazy create, never a silent empty result — because a typo'd scope name is the mis-filing risk the mandatory parameter exists to prevent.

## The registry and the scoped schema

One new timestamped migration (`bin/create-migration wiki <name>`; committed migrations untouched) creates the registry and rebuilds the content tables with the scope dimension:

```sql
-- scopes — the explicit registry; a scope exists iff a row exists.
CREATE TABLE scopes (
  name       TEXT PRIMARY KEY,               -- the scope name; validated slug (see below)
  visibility TEXT NOT NULL DEFAULT 'private',-- 'private'|'public' (D76: web-tier gating only)
  created_at INTEGER NOT NULL,
  CHECK (visibility IN ('private','public'))
);
INSERT INTO scopes (name, visibility, created_at) VALUES ('default','private', <migration time>);
```

`subjects`, `jobs`, and `aliases` each gain a `scope TEXT NOT NULL` column (relationship to `scopes.name` is a comment, no FK — suite style). `claims` and `pages` need **no** column: both key on `subjects.id`, and a subject lives in exactly one scope, so their scope is derived. Subject identity becomes **`UNIQUE(scope, norm_name)`** — one normalized name per scope, the D3 name-only rule applied per partition. The alias key becomes per-scope the same way (`UNIQUE(scope, alias_norm)` in D25's terms): a folded name routes to its survivor only inside its own scope. `jobs.scope` is stamped at enqueue (ingest and merge both) and is how job listings partition.

Because prod holds only droppable demo data (operator-confirmed) and a stored row cannot be assigned a meaningful scope after the fact any more than an email could be mapped to an owner id (the D3 conversion precedent), the migration **rebuilds the content tables in their effective current shape plus `scope` and drops all rows** — deterministic on any database, fresh start, no backfill. The D3 rebuild pattern is reused verbatim.

## Scope names

A scope name is a validated slug: **`[a-z0-9-]`, 1–64 chars, no leading or trailing hyphen** (regexp `^[a-z0-9]([a-z0-9-]{0,62}[a-z0-9])?$`, plus the 1-char case). Validation happens at creation (`ValidateScopeName(name) error` in `internal/wiki`, called by `ScopeStore.Create` and the D75 verb); names are **not** normalized — an invalid name is rejected, never coerced, so the name a caller types is byte-identical everywhere it later appears (tool params, URLs, the cookie, the selector). `Normalize` (D3) is for subject names only and is not involved.

## The seam

```go
// internal/wiki — the scope registry store (write handle for mutations, read pool for lookups, D17).
type Scope struct { Name, Visibility string; CreatedAt int64 }

type ScopeStore struct{ /* db handles */ }
func (s *ScopeStore) Create(ctx context.Context, name string) (Scope, error)        // validates; ErrScopeExists on dup (incl. "default")
func (s *ScopeStore) Get(ctx context.Context, name string) (Scope, error)           // ErrScopeNotFound
func (s *ScopeStore) List(ctx context.Context) ([]Scope, error)                     // name-ordered
func (s *ScopeStore) SetVisibility(ctx context.Context, name, visibility string) error
func (s *ScopeStore) Delete(ctx context.Context, name string) error                 // ErrScopeIsDefault for "default"; removes the scope AND all its content

var ErrScopeNotFound = errors.New("wiki: scope not found")
var ErrScopeExists   = errors.New("wiki: scope already exists")
var ErrScopeIsDefault = errors.New("wiki: the default scope cannot be deleted")
```

Every existing content seam gains the scope as a **leading parameter** (after `ctx`): `Service.Ingest`, `ask.Asker.Ask`, `SubjectStore.List`/`GetByPath`, `ClaimStore.ListBySubject` (via its subject), `ListJobs`/`CountJobs`, `Merge`, `ListMerges`, `Mentions`/`MentionsIn`/`LinkifyMentions`/`PageWithLinks` (key loading restricted to the scope), the D81 `Recent` home list, the D31 keyword lane, and the D32 in-memory vector lane (its index is per-scope, or filtered by scope at query time — implementation's choice, behavior pinned below). Each such method resolves the scope against the registry first and returns `ErrScopeNotFound` for an unknown one. Id-addressed operations (`JobStatus`, `Abort`, `Rerun`) take **no** scope — a job id names one job in one scope already; the pipeline worker reads the job row's stored `scope` and integrates into it.

`scope_delete` removes the registry row and **every** row of that scope's content (subjects, their claims and pages, its aliases, its jobs) in one transaction on the write handle. Deleting content is the verb's purpose — a typo'd scope must be removable — and the no-ACL model means anyone authenticated could have written that content anyway.

**Rejected.**
- **`partition` as the name** — connotes physical storage layout; this is a logical namespace. `scope` reads naturally on every surface.
- **Lazy scope creation on first use** — a typo silently mints a partition and mis-files content into it, exactly the failure the mandatory parameter exists to stop. Explicit creation makes the typo a loud error and gives the web selector an authoritative list.
- **One SQLite database per scope** — real physical isolation, but multiplies migration runs, handles, and backup surface, and makes `scopes`/`scope_delete` filesystem operations. A column on one database gives the same observable wall at a fraction of the moving parts.
- **Scope columns on `claims`/`pages` too** — denormalized copies that can drift from the subject's scope; both tables reach their scope through `subjects.id` in one indexed hop.
- **Normalizing scope names instead of validating** — coercion means the name the caller typed and the name stored diverge (`Team X` → `team-x`), reintroducing ambiguity; validation keeps one byte-exact name everywhere.
- **Per-scope ACLs** — a much larger identity feature; the box is single-team by construction and the operator explicitly chose namespaces-not-permissions.
- **Preserving existing rows by assigning them all to `default`** — mechanically possible, but the operator chose a fresh start (prod holds demo data only), and the D3 rebuild precedent keeps the migration deterministic and simple.
