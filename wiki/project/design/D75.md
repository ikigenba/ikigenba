# Decision 75 — Scope on the MCP surface: the mandatory parameter + the four management verbs

**Decision.** The MCP surface adopts the D74 scope model. Every verb that addresses or lists content by name carries a **required `scope` parameter**; verbs addressed by an opaque `job_id` and the meta verbs carry none; and four new management verbs — **`scopes`**, **`scope_create`**, **`scope_delete`**, **`scope_set_visibility`** — administer the registry. The surface grows from fifteen tools to **nineteen** (16 wiki domain tools + `guide` + chassis `health`/`reflection`).

## Who carries `scope`

| verbs | `scope` | why |
|---|---|---|
| `ingest`, `ask`, `subjects`, `claims`, `page`, `merge`, `merges`, `jobs`, `jobs_count` | **required** | they address or list content; omission risks mis-filing (the operator's explicit call: omission is an error, never a default) |
| `status`, `abort`, `rerun` | none | a `job_id` names one job in one scope already; a redundant scope adds a right-id-wrong-scope failure mode and prevents nothing |
| `guide`, `health`, `reflection` | none | they describe the service, not content |

Each scoped verb resolves the scope first; `ErrScopeNotFound` renders as a **typed clean tool error** (D61 error-code `scope_not_found`) whose message points at the `scopes` tool — never a silent empty page, and never a lazy create. The `scope` property's schema description states that scopes are explicit and lists are per-scope; it is a plain `string` (no enum — the set is dynamic).

## The management verbs

| tool | input | → result |
|---|---|---|
| `scopes` | `{}` | `{scopes:[{name, visibility, created_at}]}` — name-ordered, `default` always present |
| `scope_create` | `{name (req)}` | `{name, visibility:"private"}` |
| `scope_delete` | `{name (req)}` | `{name, deleted:true}` |
| `scope_set_visibility` | `{name (req), visibility (req, enum ["private","public"])}` | `{name, visibility}` |

- `scope_create` validates via `ValidateScopeName` (invalid name → clean error stating the slug rule) and returns a typed `scope_exists` error on a duplicate — including `"default"`. A created scope starts **private** and is usable immediately.
- `scope_delete` refuses `"default"` (typed error), returns not-found for an unknown name, and otherwise deletes the scope **and all its content** (D74) — the description says so plainly (irreversible, like `merge`).
- `scope_set_visibility` publishes the closed two-value set in its `inputSchema` `enum`; an unknown value is a clean error naming the set. Visibility governs only the human web tiers (D76/D77) — MCP itself stays bearer-gated for every scope, public or private.
- All four are `WithScopeService`-wired Options in the established pattern; schemas follow the D10 rules (no `additionalProperties`, `required` omitted when empty — `scopes` is the new no-required verb).

**Supersessions (edited in place).** D10 R-MUQ4-K1JS now pins the **eighteen-verb** domain membership (the fourteen prior verbs plus the four management verbs); D57 R-YF06-03HO now pins the **nineteen-tool** `tools/list`. The D57 guide document and `Instructions` are extended with the scope model (the vocabulary, the always-required parameter, worked examples); D57's two-places-only guide-pointer rule is unchanged.

**Rejected.**
- **`scope` on the id-addressed verbs too, for uniformity** — pure redundancy plus a new mismatch failure mode; uniformity buys nothing because an id-addressed verb cannot mis-file content.
- **A default scope when the parameter is omitted** — the operator reversed this explicitly: the cost of content landing in the wrong scope outweighs the convenience; omission is an error.
- **An enum of scope names in the `scope` schema** — the set is dynamic; a stale enum would refuse valid scopes. The typed error + `scopes` verb is the discovery path.
- **A combined `scope <action>` mega-verb** — same reasoning as D16's rejected `job <action>`: one verb, one job.
- **Folding scope management into the dashboard** — scopes are wiki content structure, not suite identity; the wiki owns its own registry.

**Verification.** Through the assembled `appkit/mcp` handler over real wired services (real temp SQLite, mock provider), the D10/D16 strategy:
- R-H8HN-EXJE — Each of the nine content verbs (`ingest`, `ask`, `subjects`, `claims`, `page`, `merge`, `merges`, `jobs`, `jobs_count`) declares `scope` as a **required** property in its `inputSchema`, and calling any of them without `scope` returns a clean tool error, not a result from an assumed scope. `status`/`abort`/`rerun`/`guide` declare no `scope` property.
- R-H9PJ-SPA3 — Calling a content verb with a `scope` that has no registry row returns a typed `scope_not_found` tool error whose message names the `scopes` tool; no scope row is created and no content is written.
- R-HAXG-6H0S — `scopes` returns every registry row as `{name, visibility, created_at}`, name-ordered, with `default` present on a fresh database.
- R-HC5C-K8RH — `scope_create {name:"team-x"}` returns `{name:"team-x", visibility:"private"}`, the new scope appears in `scopes`, and an immediate `ingest {scope:"team-x", …}` is accepted.
- R-HDD8-Y0I6 — `scope_create` with an invalid name (uppercase, space, leading hyphen, empty, >64 chars) returns a clean error stating the slug rule; `scope_create {name:"default"}` (or any existing name) returns a typed `scope_exists` error.
- R-HEL5-BS8V — `scope_delete {name:"default"}` is refused with a clean typed error and deletes nothing; `scope_delete` of a populated scope returns `{deleted:true}`, after which that scope is absent from `scopes`, its former content is gone, and another scope's content is untouched; an unknown name returns a clean not-found.
- R-HFT1-PJZK — `scope_set_visibility {name, visibility:"public"}` flips the scope to public (visible in `scopes`), flipping back to `"private"` works, the `visibility` property carries the two-value `enum`, and an out-of-set value returns a clean error naming `{private, public}`.
- R-HH0Y-3BQ9 — `jobs`/`jobs_count` partition by the required `scope`: jobs enqueued in `s1` appear in (and are counted by) `s1` queries only; the same filter in `s2` returns none of them.
- R-HI8U-H3GY — `merges` lists only the named scope's merge audit rows: a merge performed in `s1` appears in `merges {scope:"s1"}` and not in `merges {scope:"s2"}`.
- R-HJGQ-UV7N — The embedded guide document and the `initialize` `instructions` both mention scopes (the guide states the required-`scope` rule, names the four management verbs, and shows a scoped worked example; `instructions` contains "scope"), and no tool description other than `guide`'s own points at the guide (D57 rule preserved).
