# Decision 97 — The match stage (`internal/match`): judging what a correction covers, in the pipeline and in merge

**Decision.** Whether a correction covers a claim is a narrow inference judgment, made **once per new pair** and stored as D96 suppression edges — never re-litigated at compile time. A new package **`internal/match`** owns the fifth production chat call site, **`match`**: one call per subject presents the subject's corrections and claims as numbered lists and returns, per correction, the claims it refutes and the older corrections it contradicts. The ingest pipeline (D4) gains a **`match` phase** between extract and compile for the subjects that need it; merge (D26) gains a **cross-pair match** over the pairs a merge creates. Compile's input becomes the **effective claim set** (D96 `Effective`) — the compile model never sees a suppressed claim.

## The package

```go
package match

// Judgment is one correction's coverage, by list index.
type Judgment struct {
    Correction  int   // index into the rendered corrections list
    Refutes     []int // indices into the rendered claims list
    Contradicts []int // indices of OLDER corrections this one overrules
}
type Result struct { Judgments []Judgment }

func DefaultCallSite() llm.CallSite // Stage "match", Provider "openrouter", Model "gpt-5.6-luna", Effort "medium", MaxTokens 16384, MaxParseRetries 2; System = DefaultPromptInstructions
```

- **Prompt housing** follows D6/D7 exactly: `internal/match/prompt.txt`, `//go:embed` → `DefaultPromptInstructions`, sent as the site's **System** (D82-composed when the scope carries instructions); the **user message is only the rendered input** — the subject identity, a numbered **Corrections** list, and a numbered **Claims** list, each entry the row's text plus a `new`/`existing` marker, **no ids of any kind**. Render and parse are split halves (the D4 idiom) so the pipeline can hand the request to the queue and validate the delivered result.
- **Prompt content:** task framing (corrections are rulings; claims are observations); a correction **refutes** a claim only when the claim asserts the very fact the correction rules false — related is not refuted; it **contradicts** an older correction only when the two rulings cannot both hold; **when unsure, output no edge** — a wrongly suppressed true claim is worse than a surviving disagreement, which the compile prose still shows as conflicting accounts (D7). Output schema `{judgments:[…]}` + a worked example.
- **Semantic `validate`** (the D5 hook): every index in range; `Judgments` may be empty (no coverage is a valid answer). A violation is a semantic failure → corrective item per D5's recipe; attempts exhausted → job `failed`, nothing written.
- **The mechanical new-pair filter** — applied after parse, before staging: keep only edges where **at least one side is new** (old-pair judgments are discarded — settled edges never churn); drop any correction→correction edge that is same-job or not strictly backward in assertion order (D96 invariants). What survives is by construction insertable; `ErrInvalidSuppression` at the store is therefore a programming error, not a data path.
- **Configuration:** the site joins D19's closed set with knobs `MATCH_MODEL / MATCH_REASONING / MATCH_TEMPERATURE / MATCH_MAX_TOKENS` and `Config.CallSites.Match`; the composition root constructs the matcher from `DefaultCallSite`, never a bare `llm.CallSite{…}`. Attribution rides D62 (`origin` from the job's owner snapshot; accounting name `wiki.match`) and the job's chain id (D64/D65) — cited, not restated.

## The pipeline's match phase (extends D4)

The job `phase` vocabulary becomes `'' | 'extract' | 'match' | 'compile'` (still internal — the five product statuses are untouched, D95).

- **Extract apply** stages the plan as today, with each subject's statements now split into claims and corrections (D6). A subject **needs matching** iff it has new corrections, or it has new claims and standing corrections already in the store. When **no** subject needs matching, the flow is byte-compatible with today: ensure the compile fan-out, `phase='compile'`. Otherwise: stage the match fan-out plan, ensure one item per needing subject — key `<jobID>/match/<norm-name>/a1`, envelope `{job_id, stage:"match", subject:<norm-name>, units:M}` — ensure the compile items for the subjects that need **no** matching, and set `phase='match'`.
- **Match apply** (the inbox drain, D94): parse/validate; apply the new-pair filter; **stage the unit's surviving edge set** (a `job_staging` row, `stage='match'`, `unit=<norm-name>`). Staged edge endpoints reference existing rows by id and **this job's new statements by `(norm_name, ordinal in the staged plan)`** — new rows have no ids until the integrate commit mints them (D4). Then ensure **that subject's** compile item, rendered from the subject's **post-replacement effective set** — `(persisted rows − this job's old rows) + this job's staged new rows`, filtered through D96 `Effective` with persisted + staged edges (the D14 step-2 semantics, now effective-set-aware). The staged-compile-row guard (D4 R-OQJZ) governs replays unchanged; a replayed match delivery re-stages the identical edge set and mints no new paid items for already-staged compile units. When the last match unit is staged, set `phase='compile'` (bookkeeping only).
- **The integrate commit** (D4/D14, extended in place): in the one transaction — delete this job's prior rows **with the D96 edge cascade**, insert the new claims **and corrections** (kinds explicit), resolve staged edge ordinals to the freshly-minted ids and insert the edges, upsert each affected subject's page compiled from its effective set — **deleting the page when the effective set is empty** (the subject row stays, the D14 `has_page:false` shape; a fully-suppressed subject honestly has no page) — and finish the job under the status guard. Nothing partial lands.
- **Boot/abort/stray behavior is inherited**, not restated: a job with `phase='match'` is left alone by the boot sweep (its state lives in the queue and staging, D4), an aborted job's late match deliveries hit the stray rule, and no match item may stop the drain (D94).

## Merge (extends D26)

Phase B additionally loads both subjects' corrections and edges. The pairs a merge creates — loser corrections × winner rows and winner corrections × loser rows — have never been judged, so when both sides of either product are non-empty, Phase B runs **one live match call** (`llm.JSON` under `ConsumerAsk`, same site, stage `match`) over the combined lists and keeps, via the mechanical filter, **only cross-subject pairs** (within-subject pairs are settled edges). It then compiles the winner from the combined **effective** set. Phase C inserts the surviving cross edges in the merge transaction; existing edges need nothing — they key claim ids, which `RepointSubject` does not change. Recency stays global: the D96 `(created_at, id)` order, indifferent to which side of the merge a row came from.

**Rejected.**
- **Compile-time judgment (hand corrections to the compile prompt: "omit what these rule false")** — re-litigates every falsehood on every recompile forever; one inattentive generation puts the false fact back on the page. Mechanical filtering from stored edges is the point of the feature.
- **Ask-style retrieval for matching** — matching needs no search: extract already binds every statement to its subject, so the candidate set is one subject's bounded row list, fetched by id.
- **A barrier compile fan-out (ensure all compile items only after every match unit)** — a subject's compile depends only on its own match unit; per-subject pipelining is the D4 idiom and wastes no wall-clock on the units that finish early.
- **Persisting judged-pair bookkeeping (a `matched_pairs` table)** — the new-pair rule derives from row novelty within the job being applied; a second ledger would have to be kept consistent with rows that D14 replacement deletes.
- **Suppressing at extract time (extract emits "this correction covers claims 3 and 7 of this document")** — extract sees only the new document, never the subject's standing rows, so it cannot judge the pairs that matter most (new correction × old claims, new claim × standing correction).
- **Skipping merge cross-matching** — silently weakens standing corrections at every merge: a falsehood suppressed on one side reappears on the merged page through the other side's unjudged rows.

**Verification.**
- R-7FBT-OXWC — `match.DefaultCallSite()` carries `Stage "match"`, `Provider "openrouter"`, `Model "gpt-5.6-luna"`, `Effort "medium"`, `MaxTokens >= 16384`, `MaxParseRetries 2`, no temperature and no thinking field; the composition root builds the matcher from it (no bare `llm.CallSite{Stage:"match",…}`), and the D19 resolver applies `MATCH_*` knobs onto it.
- R-7GJQ-2PN1 — The captured match completion item for a scope without instructions carries `system` equal to the embedded `internal/match/prompt.txt` contents and a user message containing **only** the subject identity plus the numbered corrections and claims lists with their `new`/`existing` markers — no ULID and no internal id anywhere in the user turn.
- R-7HRM-GHDQ — For a job in a scope whose instructions are set, the captured match item's `system` is the base match prompt composed per D82 (base + wrapper + block); with empty instructions it is the base prompt byte-exact. *(worker integration: real temp SQLite + httptest prompts)*
- R-7IZI-U94F — A match result carrying an out-of-range index ensures a corrective item (`/a2`, D5 recipe) and acks the bad delivery with the job still in phase; attempts exhausted ends the job `failed` with the semantic error and **zero** rows, edges, or pages written.
- R-7K7F-80V4 — The mechanical filter: from a scripted result naming (a) an old-claim×old-correction pair, (b) a same-job correction→correction pair, and (c) a forward-in-time correction→correction pair alongside valid new-pair edges, **only** the valid new-pair edges are staged — the staged set for the unit contains none of (a)/(b)/(c).
- R-7LFB-LSLT — Extract apply for a job whose statements include corrections sets `phase='match'` and ensures exactly one match item per **needing** subject (key `<jobID>/match/<norm-name>/a1`, envelope naming job, stage, subject, units), while a job with no new corrections and no standing corrections in its subjects ensures **no** match item and proceeds straight to the compile fan-out with `phase='compile'` (today's flow, unchanged).
- R-7MN7-ZKCI — Applying a done match item stages the unit's filtered edge set and ensures **that subject's** compile item; replaying the same delivery leaves the staged edge set identical and, when the subject's compile row is already staged, ensures nothing new (no unbounded paid items).
- R-7NV4-DC37 — The compile request rendered after a match apply contains the subject's **effective** claims only: a claim suppressed by a staged or standing live edge does not appear anywhere in the compile user message, while unsuppressed claims (including the correction's own carried truth, extracted as a claim) all do.
- R-7QAX-4VKL — The integrate commit is one transaction that lands rows, edges, and pages together: new claims and corrections inserted with explicit kinds, staged edge ordinals resolved to the minted ids, the affected pages built from effective sets — and a subject whose effective set is **empty** has its page **deleted** with its subject row retained; a failure injected mid-commit leaves none of it (no rows, no edges, no page change, job non-terminal).
- R-7RIT-INBA — **Reassertion dies.** With a standing correction on a subject, a later ingest whose document reasserts the refuted fact ends with that new claim suppressed (edge from the standing correction) and the recompiled page free of the falsehood — the correction beats a claim ingested *after* it.
- R-7SQP-WF1Z — **Recency between corrections, end to end.** Correction A suppresses matching claims; a later ingest carrying correction B that contradicts A yields B→A staged and committed, A no longer live, A's formerly-suppressed claims effective again, and the recompiled page carrying the revived facts; B's own carried truth (if extracted as a claim) also appears.
- R-7TYM-A6SO — **Re-run re-matches.** Re-running a job whose claims were suppressed by another job's standing correction replaces the rows (fresh ids), cascades the old edges, matches the fresh claims against the standing correction, and ends with the resurrected claims suppressed again — the page after the re-run still excludes the refuted fact.
- R-7V6I-NYJD — **Merge cross-match.** Merging loser L (holding a standing correction) into winner W (holding a matching claim) mints the cross edge in the merge transaction, leaves both sides' pre-existing edges intact across the claim repoint, and compiles W's page from the merged effective set — the refuted fact absent; a merge where neither cross product has both sides non-empty makes **no** match call.
