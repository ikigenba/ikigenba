# Decision 79 — Truthful submit controls: Ask/Search labels + script-driven pending feedback

**Problem.** The question form's button reads the same on both tiers, so it never says whether submitting will run inference (`ask`, private tier — D44) or a keyword lookup (search, public tier — D78). And after clicking, nothing changes until the response page arrives: on a multi-second `ask` the user has no signal the wiki is working. The old "no-JS" posture that blocked a pending indicator was never an operator requirement (agent-introduced; retired — see D43/D76/D39, trued in place).

**Decision.** Two coupled behaviors on the question form (the `q` form on the scope home and result pages — D43/D44/D78):

1. **The button names what submitting does.** On the **private** tier the submit button's text is **`Ask`** and the input's `aria-label` is `Ask this wiki`; on the **public** tier the button's text is **`Search`** and the input's `aria-label` is `Search this wiki`. (This also settles the drift between D43's sketch, which said Ask, and the shipped template, which said Search everywhere.) The scope selector's `Go` button is unchanged (D76).

2. **Submitting shows the page is working.** The question form carries `data-busy` and its button carries `data-busy-label` — `Asking…` (private) / `Searching…` (public). A small inline `<script>` in the layout template (`share/www/layout.tmpl` — embedded like the rest of the surface, no new asset route) wires every `data-busy` form: on `submit` it disables the submit button, replaces its text with its `data-busy-label`, and adds class `busy` to `<body>`; layout CSS under `.busy` dims `main` and shows a spinner overlay. The form still submits as the plain GET navigation (D43) — the script never calls `preventDefault`, never fetches, and holds no state; the browser's navigation replaces the page when the response arrives, which is what clears the busy state. **Progressive enhancement:** with scripts disabled the form works exactly as before (no feedback, full function); nothing on the surface *requires* JS. The scope selector form carries no `data-busy` and gets no busy behavior — its redirect is effectively instant.

**Rejected.**
- **XHR/fetch-in-place submission** — forfeits bookmarkable `?q=` URLs and the back button (D43's standing call) for nothing the busy indicator needs.
- **CSS-only feedback** (`:active`/`:focus` styling) — cannot persist through the navigation wait; the pending state lasts seconds and must survive until the response document arrives, which only script-set state does.
- **A server-rendered interstitial "working…" page** — the wait *is* the request; the server cannot respond before the work completes without restructuring ask into an async job, wildly out of proportion for a progress indicator.
- **Busy feedback on the scope selector** — the redirect is instant; a spinner there is noise. Excluded by construction (no `data-busy`).
- **One shared neutral label ("Go"/"Submit") on the question form** — the whole point is telling the user whether they are about to spend an inference call or a DB lookup; a neutral label is the status quo being fixed.

**Verification.** httptest against the D42 handler (stub seams, both tiers); behavior is browser-side, so the checkable proof is the markup contract the script and CSS key on.

- R-VBAY-V6II — **Private tier says Ask.** The private-tier scope home (`GET /private/{scope}/`, and the ask result page with `?q=`) renders the question form's submit button with text `Ask` and `data-busy-label="Asking…"`, and the `q` input's `aria-label` is `Ask this wiki` — a private-tier page whose question button reads `Search` (the shipped drift) fails.
- R-VCIV-8Y97 — **Public tier says Search.** The public-tier scope home (`GET /public/{scope}/`, and its `?q=` results page) renders the question form's submit button with text `Search` and `data-busy-label="Searching…"`, and the `q` input's `aria-label` is `Search this wiki`.
- R-VDQR-MPZW — **The busy wiring ships on every question-form page, and only there.** On both tiers, every page bearing the question form carries: `data-busy` on that form, the inline busy script (the layout's `submit`-handler script element) and the `.busy` spinner/dim CSS hooks in the document — while the scope-selector form on the same page carries **no** `data-busy` attribute; a page shipping the labels without the script/CSS hooks, or wiring the selector, fails.
