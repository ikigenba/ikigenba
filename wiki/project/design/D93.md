# Decision 93 — Serialized ingest admission: the durable per-scope lease

**Decision.** At most **one ingest job per scope** may hold the pipeline between admission and its terminal write. The guarantee is a durable row, not a goroutine's position in a loop.

Serialization is required because a job's read-modify-write **span** crosses an LLM round trip: the plan is computed at extract-apply time from the scope's current subjects and claims, and integrated minutes later. Two documents whose spans overlap in one scope compute their plans against the same "before" snapshot, and the second to integrate silently overwrites the first's contribution to any page they share. No transaction can cover that span — D4's doctrine forbids holding one across inference — so the exclusion has to be durable and outside the transaction.

**The lease.**

```sql
CREATE TABLE ingest_lease (
  scope       TEXT PRIMARY KEY,
  job_id      TEXT NOT NULL,
  acquired_at TEXT NOT NULL,
  expires_at  TEXT NOT NULL
);
```

`scope` is the primary key, so the exclusion is a database invariant rather than a convention.

**Acquire in the admission transaction.** `ClaimPending` selects the oldest `pending` job **whose scope holds no lease** and, in the same transaction, writes `status='working'` and inserts the lease row. Admission and exclusion commit together or not at all:

```go
func (s *JobStore) ClaimPending(ctx context.Context, now time.Time, ttl time.Duration) (Job, bool, error)
func (s *JobStore) ReleaseLease(ctx context.Context, tx *sql.Tx, jobID string) error
```

**Release in the transaction that ends the job's hold.** Every path out releases: the integrate commit (`done`), `FailWaiting` and `FinishWorking` (`failed`), `Abort` (`aborted`), the reaper (D95), and the boot sweep's `working → pending` requeue. The requeue matters most: it is not a terminal status, so a lease left behind by it would block its scope until expiry with no job to explain why.

**Per scope, not global.** The state a job mutates is scope-local by construction — `subjects` and `aliases` are unique per `(scope, norm_name)`, and pages hang off subject ids. A global lease would buy nothing extra and would let one scope's slow document stall every other scope's ingest, which is precisely the cross-scope blast radius worth avoiding.

**Merge jobs take the same lease.** A merge rewrites the subject graph its scope's staged plans name. Holding the same lease also retires the in-memory `mergeMu`: an in-process mutex never protected an invariant that has to survive a restart.

**Release wakes the claim loop.** Admission is now refusable, and the doorbell is a one-slot non-blocking channel — a job that fails to admit consumes the signal, so the next pending job in a freed scope could otherwise wait for an unrelated ingest. Every release notifies, and the loop keeps its periodic tick as a floor.

**`Wait` is renamed.** `JobStore.Wait` never waited; it flipped a status and returned, which is how the serialization invariant was lost without anyone editing the loop. It becomes `MarkPhase`, and `Service.Wait` becomes `WaitForWork`.

**Rejected.**
- **Relying on the worker loop's shape** — the previous serialization was an accident of a blocking call, held nothing durable, and vanished the moment the call stopped blocking. An invariant no artifact records is not an invariant.
- **An in-process mutex** — dies with the process, and does not exclude the MCP request goroutines that also write jobs.
- **A single global lease** — simpler by one column, but couples every scope's throughput to the slowest document in any one of them.
- **Optimistic concurrency (version the page, retry the loser)** — the honest alternative, and the one to revisit if intra-scope ingest throughput ever matters. It requires page integration that merges rather than overwrites; until that exists, retrying the loser re-spends a full compile fan-out to resolve a conflict the lease prevents for free.
- **A lease with no expiry** — a crash between admission and the terminal write would strand a scope permanently; expiry plus the reaper's unconditional reclaim makes a leaked lease self-healing.

**Verification.**
- R-OXVD-UPJD — With one job admitted in a scope, claiming again returns no job while that scope's lease is held, and the lease row names the admitted job; the admitted job's status and its lease row are written by the same transaction (an injected failure after the status write leaves neither).
- R-P2QZ-DSI5 — A pending job in a **different** scope is admitted while the first scope's lease is held: per-scope exclusion, not global.
- R-OZ3A-8HA2 — Each terminal transition — `done` via the integrate commit, `failed`, `aborted` — deletes the job's lease row in the same transaction that writes the status, and the next pending job in that scope is admitted immediately afterward.
- R-P1J3-00RG — The boot sweep's `working → pending` requeue deletes the requeued job's lease; a crash simulated between admission and handoff therefore leaves no lease row behind and the scope admits again.
- R-P3YV-RK8U — A claim attempt refused for a held lease does not strand the queue: after the lease is released, the next pending job in that scope is admitted without any further ingest arriving (release notifies the loop).
