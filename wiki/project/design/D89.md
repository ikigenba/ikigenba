# Decision 89 — An honest ask failure on the web: a styled error page and a logged cause

**Decision.** When a web ask genuinely fails — the asker seam returns an error the pipeline could not absorb (D86 absorbs the sanctioned transients; what remains is a real failure: the LLM seam, the database) — the handler stops collapsing it into `http.Error(w, "ask wiki", 500)` and instead does two things:

**1. Renders a real error page in the site shell.** The response is the wiki's normal page chrome (header bar with brand mark, scope selector, and the question box **retaining the just-asked question**, ready to edit and resubmit; footer with service and version) around a plain outcome-altitude message — the question could not be answered right now, try again — with no internal error text, stack, or mechanism leaked into the page. The HTTP status stays **500** (it *is* a server failure; monitoring and telemetry keep seeing the truth). A new `error` template state joins the existing home/answer/subject states in `share/www`, styled by the suite's shared tokens like every other page — no new styling system. Both tiers (public and private) render it identically.

**2. Logs the underlying error.** The handler logs one structured line at error level through the service's existing logger — the wrapped underlying error plus the scope and the question — so the next diagnosis starts from the service log, not from telemetry archaeology. (The 2026-08-11 incident cost a multi-hour forensic reconstruction because the only artifact was a bare nine-byte "ask wiki" body; the actual error, `wiki: subject not found`, was discarded unlogged.)

The same treatment applies to the ask handler's other internal-failure exits (mention listing, linkify, render): one failure posture for the ask page, not a per-exit lottery. The not-implemented guard (no asker wired) keeps its distinct status but renders through the same error state.

**Error surface.** The handler's contract: asker/seam errors → the styled 500 error page + one error-level log line; a template render failure of the error page itself falls back to `http.Error` (the terminal fallback — never a render loop). Nothing here panics.

**Rejected.**
- **Rendering failures as a 200 with an error message.** Lies to every mechanical observer — uptime checks, telemetry outcome fields, caches. The page is for the human; the status is for the machines; they need not agree on tone, only on truth.
- **Showing the underlying error text on the page.** Internal error strings leak schema and seam names to anonymous visitors on public scopes; the log is the diagnostic channel, the page is not.
- **Leaving the bare `http.Error` and only adding the log line.** Fixes the operator's pain but not the user's: the product promises a styled, on-brand surface, and a naked one-line 500 body on a public scope is neither.

**Verification.**
- R-RM58-3R9J — A failing asker yields the styled error page: with the asker seam erroring, `GET /{$}?q=…` (both tiers) returns HTTP 500 whose body is the full site shell — header with the question retained in the box, footer, suite tokens — containing the plain failure message and **none** of the underlying error text; where before the fix the body was the bare text `ask wiki`.
- R-RND4-HJ08 — The cause is logged: the same failing ask emits exactly one error-level log record through the service logger carrying the underlying error, the scope, and the question — captured at the logger seam in the test.
