# Decision 65 — Inherit the chain across the async boundary; mint a root only for genuinely self-started work

**Decision.** wiki's background work splits cleanly in two, and the split decides where a correlation id comes from.

**Inherited — work an inbound request caused.** An MCP `ingest` call enqueues a job and returns; the worker processes it later, after the request is gone. That is still the request's causal chain, so the chain id must survive the async boundary — it is **stored on the job row**, and the worker resumes it. Re-minting here would sever the trail exactly where it matters most ("what did that ingest do?").

*The column.* A new forward-only migration (authored with `bin/create-migration wiki <name>`, never hand-numbered, never editing a committed file) adds one additive column to `jobs`:

```sql
ALTER TABLE jobs ADD COLUMN correlation_id TEXT NOT NULL DEFAULT '';
```

No table rebuild, no change to any existing column, and every pre-existing job row migrates forward with an empty `correlation_id`. `wiki.Job` gains the matching `CorrelationID string` field.

*Capture at enqueue.* `Service.Ingest` reads the chain id from its context — the chassis middleware guarantees one on every inbound request — and writes it onto the job row in the same insert that records `owner_id`/`owner_email`. Capture is write-once, like those: a job's chain id is the chain that caused it, and a re-run (D14) does not re-root it.

*Resume at processing.* When the stored id is non-empty it is the chain id for every stage of that job — extract, compile, embed-page, and the merge work item's LLM calls — threaded on the job's derived context so D64's outbound client forwards it and `Attribution.GroupID` carries it.

**Self-started — work no request is waiting on.** These mint a **root**: one root id per *cycle* of self-originated work, never per page, per claim, or per call, so everything one cycle caused shares one chain. wiki has exactly two such cases:

- **The catch-up embedding sweep** (D35) — an independent `Spec.Workers` loop that drains the "needs embedding" set and makes `wiki.embed-page` calls with no inbound request and no job behind them. **One root per drain cycle**: every embed in that cycle carries the same id, and the next cycle mints a fresh one. Minting per page would shatter one maintenance pass into hundreds of one-hop chains and make "what did that sweep cost" unanswerable.
- **A job row with an empty `correlation_id`** — a row written before this column existed, or work wiki generated internally. The job is the unit of self-originated work, so it gets **one root for the whole job**, covering every stage.

The boot `RequeueWorking` sweep mints nothing: it touches only the local database, makes no outbound call and publishes no event, so there is no hop to correlate.

Minting is never hand-rolled. appkit owns a **single root-start helper** — mint the id, install it in the context, emit the `root` record — and wiki calls it at exactly the two sites above, consuming it as an external fact. The `root` record's shape and the recorder behind it are appkit's coverage; wiki does not re-prove them. What wiki proves is its own rule: which id a unit of work runs under, that it is never `job.ID`, and that a cycle is one chain.

**Rejected.**
- **Reuse `job.ID` as the correlation id** (the old durable-root-reuse rule) — needs no column, but permanently severs the pipeline from the request that enqueued it: the id in prompts' `calls` rows and in telemetry resolves to nothing upstream. This is precisely the change the new standard makes.
- **Treat every pipeline run as a root, ignoring the enqueuing request** — loses the same trail for every job, not just legacy ones, and makes "what did this user's ingest do" unanswerable.
- **Mint per embed call in the sweep** — technically "self-originated work mints", but shatters one cycle into hundreds of single-hop chains; the rule is one root per cycle for exactly this reason.
- **Give the sweep no correlation id at all** (its behavior before this Decision — "maintenance, so no group id") — leaves a whole class of outbound calls and their cost uncorrelatable, and leaves a gap in the forensic record indistinguishable from a bug.
- **Keep the chain id only in memory, handing it from `Ingest` to the worker** — the worker claims jobs off the queue, possibly after a restart; anything not on the row is lost.
- **Backfilling the column for existing rows** — there is nothing truthful to backfill; an empty value correctly says "chain unknown", and the root rule handles it.
- **A nullable column** — an empty string is the same statement with no three-valued logic at the read sites.

**Verification.**
- R-XGME-DMUD — Against a real temp SQLite with the migrations applied, `Service.Ingest` called under a context carrying chain id `X` writes a job row whose `correlation_id` reads back as exactly `X`; called under a bare context it writes an empty `correlation_id` rather than the job's own id or an invented value.
- R-XJ27-56BR — The worker's per-job attribution derivation returns `GroupID` equal to the row's stored `correlation_id` when it is non-empty (and never `job.ID`, proven with a row whose stored id differs from its id); when the stored value is empty it returns one freshly minted 26-character Crockford base32 ULID for the whole job — neither empty nor `job.ID`, identical across that job's stages, and different for a second empty-correlation job.
- R-KIH2-R4UC — One drain cycle of the catch-up embedding sweep over several stale pages issues every one of its `wiki.embed-page` calls under a single correlation id — one distinct id across the whole cycle, not one per page — and a second drain cycle uses a different id; captured at the httptest prompts, so a per-page mint and a reused-forever id both fail.
- R-XKA3-IY2G — A database migrated to the previous version, seeded with job rows, and then migrated forward retains every seeded row with its original column values and reports `correlation_id` as the empty string — asserted against the real `modernc.org/sqlite` engine through the appkit runner.
