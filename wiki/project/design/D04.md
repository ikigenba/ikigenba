# Decision 4 — The ingest pipeline: handoff and apply over the completion queue

**Decision.** Ingest is fire-and-return at the front door, and the pipeline behind it is **split in two**: a stage that needs inference *hands the work off* to prompts' durable completion queue (D5/research §12) and ends — no goroutine waits on a model — and a separate **inbox applier** collects finished work and applies it. A job therefore rests in exactly two kinds of durable state at all times: its row in wiki's `jobs` table, and its outstanding work items in prompts' queue. Neither process restarting loses anything; nothing is ever "in flight" only in memory.

**Front door — unchanged.** `wiki.Service.Ingest(ctx, …) (jobID, err)`: one `jobs` INSERT (`status='pending'`), nudge, return. No LLM work on the request path. `JobStatus` reads the row.

**Job lifecycle gains `waiting`.** `pending → working → waiting → done | failed | aborted`. `working` marks only the brief in-process moments (claiming, applying); `waiting` means "handed off — the job's next event is a queue delivery." The closed set stays a product constant honored in Go (no CHECK constraint; no migration for the status itself).

**The two halves:**

*Handoff (producer).* The worker claims the oldest `pending` job (`working`), renders the extract request from `source_text` (D6's render half), and **ensures** one queue item — key `<jobID>/extract/a1`, context envelope `{job_id, stage:"extract"}` — then sets the job `waiting` and moves on. Ensure's idempotency makes the claim-crash-reclaim path safe: re-ensuring after a boot sweep dedupes against the item already queued.

*Apply (consumer).* A second worker loop — the **inbox tick** — runs every few seconds: `Inbox()` → for each terminal item, apply it, then `Ack`. Applying dispatches on the item's context envelope:

- **`stage:"extract"` done** → decode/validate claims (D6's parse half; semantic failure → ensure a corrective item per D5's recipe, ack the bad one, job stays `waiting`; attempts exhausted → job `failed`). On success, in one tx: store the extract output on the job's staging state and record the compile fan-out plan; then ensure the compile items — key `<jobID>/compile/<norm-name>/a1`, envelope `{job_id, stage:"compile", subject:<norm-name>, units:N}` — each carrying the D7-rendered prompt over the subject's post-replacement claim set (computed per D14's read rules); ack the extract item **last**. Ack-after-consequences is the invariant: a crash anywhere before the ack redelivers the extract item, and re-applying is idempotent (the staging write is an upsert; re-ensuring the compile items dedupes).
- **`stage:"compile"` done** → decode/validate the page (D7's parse half; semantic retries as above). Persist the unit's result into the job's staging state; ack. When the staged compile results reach the fan-out's `units` count, run **D14's atomic integrate commit** over the staged outputs — delete the job's prior claims, insert the new ones, upsert/delete the affected pages, `status='done'` guarded by `WHERE status='waiting'` — then clear the staging rows. Embedding writes (D30/D34/D35) follow as today.
- **any `failed` item** → job `failed` with the queue's error (guarded terminal write), staging cleared, ack.
- **stray item** — its `job_id` is unknown, terminal, or not `waiting`, or its stage doesn't match the job's staging state, or its envelope kind is not a pipeline stage (e.g. an ask item orphaned by a crashed `Do` poll) → **ack and discard**, writing nothing. The queue must drain even when wiki has moved on.

**Staging state** — one new table (created with `bin/create-migration wiki create-job-staging`), the durable scratch between handoff and integrate:

```sql
CREATE TABLE job_staging (
  job_id   TEXT NOT NULL,
  stage    TEXT NOT NULL,             -- 'extract' | 'compile'
  unit     TEXT NOT NULL DEFAULT '',  -- compile: the subject norm-name; extract: ''
  payload  TEXT NOT NULL,             -- extract output / compiled page JSON
  units    INTEGER NOT NULL DEFAULT 0,-- compile fan-out size, stamped on every row
  PRIMARY KEY (job_id, stage, unit)
);
```

Upsert-keyed so every apply is idempotent; rows die in the integrate commit (or with the job's terminal write). The integrate commit reads **only** staged payloads + the job row — it makes no LLM call and holds no tx before it begins (the D4 doctrine survives: no tx across inference, which is now trivially true because no inference happens inside wiki at all).

**Worker shape.** Still `Spec.Workers`, now two loops: the claim loop (pending jobs → handoff, doorbell + poll fallback, unchanged) and the inbox tick (fixed short interval, ~2 s; drains the whole inbox each tick; no doorbell — the queue is remote). Both single-flight; concurrency 1, no knob. **Boot sweep:** `working → pending` (unchanged — `working` still means "an in-process step died mid-stride"); `waiting` jobs are deliberately **not** swept: their state lives in the queue and staging, and the inbox tick resumes them without re-spending.

**Anti-poisoning invariant — unchanged and structural.** Extract renders only from `job.source_text`; compile renders only from claim sets; no page body is ever an input. The render halves' signatures still make it unexpressible.

**Rejected.**
- **The blocking pipeline (the prior form of this decision)** — extract and compile held a goroutine through every model call; any completion slower than the chassis's 15 s write deadline killed the whole job (production jobs 008/009), and a wiki restart vaporized all in-flight work. The split makes both impossible by construction.
- **Persisting queue item ids and resuming polls** — retained handoff knowledge wiki doesn't need: keys are derivable from durable job state, Ensure dedupes, and the inbox delivers regardless of who's listening. Nothing to resume means nothing to recover.
- **Waking the applier via the event plane** — the outbox retains by horizon, not by consumption (prompts D29's rejection); and a wake-up-only event still ends in the same inbox drain. The tick is the correctness mechanism; push is at most a future latency tweak.
- **Sweeping `waiting` jobs to `pending` on boot** — would re-run stages whose work sits finished in the queue, double-spending on every restart; `waiting` is exactly the state whose truth is external.
- **A per-stage in-memory fan-in (channels/WaitGroups)** — reintroduces state that dies with the process; the staging table's count-against-`units` is the same fan-in, durable.

**Verification.**
- R-M8RN-87WV — `Ingest` returns a job id produced by a single INSERT, with no LLM/queue call on the request path (fire-and-return).
- R-K73J-J3W3 — Claiming a `pending` job ensures exactly one extract item (key `<jobID>/extract/a1`, envelope naming the job and stage, request rendered from `source_text`) and leaves the job `waiting`; re-claiming after a simulated crash re-ensures the **same** key (captured requests show identical keys — no duplicate work).
- R-K8BF-WVMS — Applying a done extract item stages the output, ensures one compile item per affected subject (keys `<jobID>/compile/<norm-name>/a1`, envelopes carrying the fan-out count), and acks the extract item only after both; replaying the same delivery (unacked redelivery) leaves staging and the ensured set identical.
- R-K9JC-ANDH — Applying a done compile item stages that unit's page; the **last** unit's apply (staged count = `units`) runs the atomic integrate commit: the job's prior claims replaced, affected pages upserted, job `done`, staging cleared — and redelivering any already-applied compile item after that acks-and-discards without altering the committed state.
- R-KAR8-OF46 — A semantically bad extract or compile result ensures a corrective item (`/a2`, corrective replay per D5) and acks the bad one with the job still `waiting`; attempts exhausted ends the job `failed` with the semantic error and zero subjects/claims/pages written.
- R-KBZ5-26UV — A `failed` queue item (provider failure, runtime bound, model `error` status) ends the job `failed` carrying the queue's error, clears its staging, and acks the item; nothing partial lands.
- R-KEEX-TQC9 — A stray terminal item — unknown job, terminal job, stage mismatched to staging, or a non-pipeline envelope — is acked and discarded: the inbox drains, no job or staging row changes.
- R-KFMU-7I2Y — The inbox tick drains **every** terminal item present in a tick (a scripted inbox of mixed items empties in one tick), and boot leaves `waiting` jobs untouched while sweeping `working` → `pending` (the sweep discriminates on exactly these two states).
- R-MB7F-ZRE9 — When integration errors mid-commit, the job ends `failed` with a non-empty `error` and **zero** subjects/claims/pages are written (atomic commit).
- R-MCFC-DJ4Y — A second job naming an existing subject (same `Normalize(name)`) appends its claims and bumps that subject's page `version`, creating no duplicate subject.
- R-MG31-IUD1 — Compile requests are rendered from claim sets and never receive page-body input (the anti-poisoning invariant, asserted at the handoff render seam).
