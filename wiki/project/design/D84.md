# Decision 84 — Scope-labeled vector cache: the scope-carrying update seam + scope-wide eviction on scope delete

**Decision.** The in-memory vector cache (D32) is a per-scope structure in fact, not just in query filtering — and the two paths that mutate it at runtime must both preserve that fact. Today only startup hydration labels entries with their subject's scope; the runtime update hook drops the scope on the floor and the cache silently coerces the missing label to `default`, and `scope_delete` (D74) never touches the cache at all. Live evidence (2026-08-11, `int`): a `scope_delete`/`scope_create`/re-ingest cycle left every ask in the recreated scope failing — the cache still served the deleted generation's subject ids — and the re-ingested pages, upserted under the coerced `default` label, were invisible to their own scope's meaning lane while leaking their ids into `default`-scope asks. Two changes close this:

**1. The update seam carries the scope.** The cache-update hook and every layer feeding it gain the subject's scope as a leading value:

```go
// internal/wiki — the composition-root hook signature (was func(subjectID, title string, vec []float32)).
func WithVectorCacheUpdater(update func(scope, subjectID, title string, vec []float32)) ServiceOption
```

`embedAndStore` (D35) supplies it: the ingest/merge after-commit path already holds the job's scope; the catch-up sweep's candidate query joins `subjects` to select each page's scope alongside its body (one indexed hop — `claims`/`pages` reach their scope through `subjects.id`, D74). The composition root passes the scope through to `VectorCache.Upsert` verbatim.

**2. An unlabeled entry is a programming error, not a default.** `VectorCache.Upsert` (and `Replace`) **panic** on an entry with an empty scope. The current coercion (`"" → "default"`) is deleted — it is precisely what converted a missing argument into silent cross-scope corruption. After change 1 an empty scope can only mean a new wiring bug, and the panic surfaces it at the earliest detectable point (construction of the cache state, not a later cross-scope answer). Query-side behavior is unchanged: `nearest` filters entries by exact scope match (D74 R-H79R-15SP).

**3. `scope_delete` evicts the scope's live entries — commit-then-evict.** `VectorCache` gains a scope-wide removal:

```go
// internal/retrieve
func (c *VectorCache) RemoveScope(scope string)   // deletes every entry labeled scope; no-op when none

// internal/wiki — a ScopeStore hook parallel to the existing AskInvalidate (D83)
type ScopeStore struct {
    AskInvalidate    func(scope string)  // existing (D83)
    VectorInvalidate func(scope string)  // new; the composition root wires VectorCache.RemoveScope
}
```

`ScopeStore.Delete` drives `VectorInvalidate` **immediately after its transaction commits**, exactly where it already drives `AskInvalidate`. Ordering is deliberate: the database is the source of truth, so it changes first; if the delete transaction fails or rolls back, the hook never fires and the cache still agrees with the database. The residual window — an ask that drew hits between the commit and the eviction — is transient and tolerated by the reader (D86); a crash between the two self-heals because startup hydration rebuilds from a database whose rows died inside the transaction. Deleting a scope's durable rows remains what it is today (one transaction, D74); this Decision adds only the in-process half.

**Error surface.** `RemoveScope` and the hooks return nothing and never fail (pure in-memory mutation); a nil hook is skipped (the store works unhooked, as `AskInvalidate` does today). `Upsert`/`Replace` panic on an empty scope — a broken invariant, never an expected runtime failure. No new returned errors.

**Rejected.**
- **Evict-before-delete ordering.** If the database delete then fails, the cache has dropped entries for subjects that still exist — the scope's pages silently vanish from meaning search until restart, and nothing heals it (the catch-up sweep only re-embeds when the *stored* vector is missing or stale, and it is neither). Not self-healing; excluded by the operator's constraint.
- **Keeping the lenient `default` coercion.** Re-arms exactly the observed failure: a future caller that forgets the scope silently corrupts two scopes at once instead of failing its first test.
- **Rebuilding the whole cache from storage on scope delete (`LoadAll`→`Replace`).** Correct but O(corpus) work and a read-storm on every delete; `RemoveScope` is a single filtered pass over memory with the same observable result.
- **A per-subject eviction loop over the deleted scope's subjects.** Requires the subject list *before* the delete and N hook calls, racing the cascade it follows; one scope-wide removal keyed by the label the entries already carry is atomic with respect to the cache lock and needs no pre-delete snapshot.

**Verification.**
- R-R1EX-LNNQ — After a runtime (re-)embed of a page in scope `s1`, the live cache entry carries scope `s1` verbatim: a meaning-lane query in `s1` returns the subject, and a query in `default` does **not** — the runtime-upserted entry is neither hidden from its own scope nor leaked into `default` (the observed live failure, inverted). Exercised through the service built the way `buildSpec` constructs it (real temp SQLite + mock embedder), not a hand-wired cache.
- R-R2MT-ZFEF — `VectorCache.Upsert` and `Replace` panic on an entry whose scope is empty, and the `"" → "default"` coercion is gone: no code path stores an entry under a scope the caller did not name.
- R-R3UQ-D754 — `ScopeStore.Delete(s1)` evicts every `s1` entry from the live cache with **no restart**: immediately after the delete returns, a meaning-lane query in `s1` returns nothing, while another scope's entries still return — where before the fix the deleted generation's ids kept surfacing until reboot.
- R-R52M-QYVT — Commit-then-evict: when the delete transaction cannot commit (forced failure), `VectorInvalidate` never fires and the cache still serves the scope's entries — cache and database stay consistent on the failure path; and with a successful delete the hook fires after the rows are durably gone.
- R-R6AJ-4QMI — Wiring guard: the composition root wires the scope-carrying updater and the `VectorInvalidate` hook end to end — an ingest's after-commit embed labels its entry with the job's scope, and a `scope_delete` through the composed service empties that scope's meaning lane; a build that drops either wire fails these tests (parallels D38 R-WS3C-J4QB).
