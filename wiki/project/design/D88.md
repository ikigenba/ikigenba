# Decision 88 — A job whose row is gone integrates nothing: the dead-job discard

**Decision.** A job whose row no longer exists at integration time **discards its own result, cleanly**. `scope_delete`'s cascade already deletes the scope's job rows (D74); a job claimed before the delete and still extracting through it is a **zombie**: its LLM work completes, but its generation is dead. Both integration transactions (ingest `integrate`, merge `mergeSubjects`) already re-read the job row in-transaction for the D14 abort check (`SELECT status FROM jobs WHERE id = ?`, discarding unless `working`); this Decision extends that same guard to the **missing row**: `sql.ErrNoRows` from that read means the job's generation was deleted — the transaction discards as a **clean no-op** (`return nil`), exactly like the not-`working` case, writing nothing and reporting nothing. Today the missing row propagates as a raw `sql.ErrNoRows` error — the content is (accidentally) discarded, but the worker records a failure for an expected outcome.

The single writer (D17) makes the guard airtight: the delete's cascade and the integration transaction serialize, so the integration either commits before the delete (and the cascade then removes everything it wrote) or reads the deleted state and discards. This holds **even when the scope is immediately recreated under the same name** — the recreated scope is a new generation; the zombie's job row is still gone, so its content can never materialize in the namesake. The after-commit embed step never runs on a discarded integration (it is unreachable when the transaction did not commit its pages), so no vector work leaks either.

**Zombies run to completion; nothing cancels, nothing reruns.** Deliberately: cancellation machinery (a scope-delete hook into the in-process cancel registry) buys only the zombie's remaining inference spend — cents for a typical document — at the cost of new wiring and timing races, and the operator chose the simpler shape (grill Q5). Rerun is excluded by construction: the re-run verb (D14) operates on a job row, and the dead generation's rows no longer exist; a recreated scope gets its content only from fresh ingests.

**Error surface.** The missing-row case returns `nil` (a sanctioned discard, not a failure — consistent with D86's posture that expected races carry no error signal); all other errors from the guard read propagate unchanged. No new named errors, no panics.

**Rejected.**
- **Cancelling in-flight jobs at scope delete.** Correctness-neutral (the guard alone is airtight) and economically marginal; adds a `ScopeStore`→service cancel-registry wire and enumeration-under-race tests for spend measured in cents. Guard-only was the operator's explicit choice.
- **Re-running old-generation jobs into the recreated scope.** Resurrects data the delete promised was gone — the exact violation of "as if it never existed". A namesake scope starts empty.
- **Leaving the missing-row case as a propagated error.** The discard already happens, but as a recorded failure of an expected outcome — noise that trains operators to ignore failures. The not-`working` discard already returns `nil`; the missing row is the same situation one step further.

**Verification.**
- R-RJPF-C7S5 — Ingest zombie discard: a claimed job whose row is deleted mid-flight (scope delete, then the same scope name recreated) completes its integration as a clean no-op — `integrate` returns `nil`, no subject, claim, or page from the dead generation exists in the recreated scope, and no job row is resurrected. Real temp SQLite through the worker path.
- R-RKXB-PZIU — Merge zombie discard: the same guard on the merge path — a merge job whose row is gone at transaction time returns `nil` and writes nothing (no alias, no subject deletion, no page rewrite), where before the fix it surfaced `sql.ErrNoRows`.
