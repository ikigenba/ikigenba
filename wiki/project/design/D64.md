# Decision 64 — Prompts calls ride the chassis's instrumented client, and the chain id replaces every wiki-minted correlation id

**Decision.** wiki's calls to prompts are its only outbound HTTP. They move onto **appkit's shared instrumented HTTP client**, and the correlation value they carry becomes the **chain id wiki received** rather than one wiki invented.

**The client.** `internal/llm`'s `Client` stops constructing its own transport (`&http.Client{}`) and is handed the **chassis-provided instrumented outbound client obtained from the Router**, injected at the composition root like every other external effect (Conventions: *Time / IO*). Illustratively:

```go
// internal/llm
func New(baseURL string, hc *http.Client) *Client
```

`cmd/wiki/main.go` obtains that client from the `Router` inside `Spec.Handlers` — the Router hands back the instrumented client already wired to the recorder, so wiki names no recorder, no transport, and no telemetry type. It asks for **no client-level timeout**: calls carry their own context deadlines, and prompts' admission gate can legitimately block a call before it executes (research §12), so a client-level deadline would abort legitimate work.

Two things follow, neither of them wiki's code: every completion-queue and `/embed` call is recorded as an `outbound` telemetry record (method, host+path, elapsed, status, response size and SHA-256 — never the body), and the client attaches `X-Correlation-Id` because prompts is a **loopback suite peer** (`registry.BaseURL("prompts")`, `127.0.0.1:3002`). The never-propagate-to-third-parties half of that rule never binds here: wiki calls no third party.

**The chain id, not a wiki-minted one.** appkit's middleware trusts or mints an `X-Correlation-Id` for every inbound request and exposes it on the context, so every ask — MCP `ask` or the web `?q=` surface — already has a chain id in `ctx` before any handler runs. `Attribution.GroupID` is therefore **read from the context**, never minted:

- **Ask path**: `ask.Asker.Ask` stops calling `ids.New()` and takes the chain id from `ctx`. One question's whole fan-out — `wiki.embed-query`, every `wiki.ask-subject`, `wiki.ask-synthesis` — carries that one value, which is also the value on the outbound header, so prompts' `calls` filter and telemetry's `chain` tool agree on one id. `internal/ids` keeps `New()` for the entity ids it exists for; the ask path simply stops using it as a correlation minter.
- **Worker path**: `jobAttribution` sources `GroupID` from the job's correlation id as D65 defines it — the row's stored chain id when it has one, the job's own id when it does not. When a chain id is stored, `GroupID` is **not** `job.ID`: the enqueuing request's chain outranks wiki's key for the job.
- **Self-started work**: the catch-up embedding sweep runs under a root minted by appkit's root-start helper, one per drain cycle (D65). A job whose row stores no chain id is itself the durable root and reuses `job.ID`, per root `project/design/D14.md`. `GroupID` reads whichever value the context carries, so no call site distinguishes an inherited chain from a rooted one.

**`group_id` stays; it is prompts' field, not a correlation convention.** The suite is retiring the *payload-field* convention for correlation (the event-plane envelope now carries the id), but `group_id` is a first-class field of prompts' completion-queue and `/embed` API: prompts persists it on each `calls` row and its `calls`/`usage` MCP tools filter on it (research §12). Removing it would delete a real inspection capability and require a prompts-side change wiki does not own. So wiki keeps sending `group_id` and keeps its **value identical to the header** — one id per chain, appearing in both places, minted by neither of them. There remains exactly one correlation id per causal chain; wiki never mints a second.

**Rejected.**
- **Keep the per-ask mint** — produces a second id for a chain that already has one, so telemetry's `chain` view and prompts' `calls` view of the same question disagree. This is exactly the "re-minting mid-chain severs the trail" failure.
- **Keep `group_id = job.ID` unconditionally** — same defect one level down: for a job an inbound request enqueued, the chain that caused it is lost at the async boundary and the id in prompts' rows resolves to nothing in telemetry. (Reuse is correct only where the job *is* the outermost cause and no chain was stored; that case is the root contract's durable-root reuse, not this defect.)
- **Drop `group_id` and rely on the header alone** — cleaner on the wire, but throws away prompts' per-chain call/cost filtering unless prompts first learns to capture the header onto its rows. Cross-workspace coupling wiki cannot land on its own, for no gain: the two fields carry the same value.
- **A wiki-local instrumented client** — duplicates the chassis recorder, and would drift from the loopback-only propagation rule.
- **Reaching past the Router to appkit's recorder or transport types directly** — the Router accessor is the service-facing seam; naming what sits behind it couples wiki to appkit internals it has no reason to know.
- **Keeping `&http.Client{}` and setting the header by hand** — the header is the easy half; the `outbound` record, the digesting, and the loopback-only rule are the parts that must not be reimplemented per service.

**Verification.**
- R-XLHZ-WPT5 — Driven through the real `internal/llm` client against the httptest prompts (a `127.0.0.1` loopback peer), every completion-queue and `/embed` request issued under a context carrying chain id `X` arrives with header `X-Correlation-Id: X`; the same calls issued under a bare context arrive with that header absent or empty — never a value wiki generated.
- R-XMPW-AHJU — A source-scan test over wiki's tree asserts zero `http.Client{` constructions in non-test `.go` files (`*_test.go` excluded), so no package can quietly bypass the instrumented client.
- R-XNXS-O9AJ — One ask driven under chain id `X` posts every call of its fan-out — `wiki.embed-query`, each `wiki.ask-subject`, and `wiki.ask-synthesis` — with `group_id` exactly `X`; a second ask driven under chain id `Y` posts `Y`. Neither ask emits a `group_id` absent from its context, so a re-introduced per-ask mint fails.
- R-XP5P-2118 — A worker-processed job whose row stores correlation id `X` while its own `job.ID` is a different ULID posts `group_id` `X` — not `job.ID` — on its extract, compile, and embed-page calls, captured at the httptest prompts.
