# Decision 87 — The exact-name pin inside the scope wall: scoped resolution, subject-id hits

**Decision.** The hybrid retriever's exact-name pin (D33) is brought inside the D74 scope wall, fixing two implementation drifts the 2026-08-11 diagnosis exposed:

**1. Pin candidates resolve in the asked scope.** The pin path resolves each candidate name through the resolver **with the ask's scope**: `ResolveByName(ctx, scope, candidate)`. Today the call drops the scope argument and the resolver's one-argument form defaults to `default` — every ask, in every scope, pins by looking names up in `default`. That is a hole in the hard wall ("every content read names exactly one scope", D74): a `default`-scope subject can be pinned into another scope's ask, and a scope's own exact-name subjects can never pin at all. The hybrid search seam already carries the scope (D74 gave every lane a leading scope parameter); the pin path now uses it. `SearchAnalyzed` threads the scope into `pinnedHit`; no seam signature changes.

**2. A pinned hit carries the subject id.** The pin builds its `Hit` with `PageID` = the **subject id**, like every other lane (keyword returns `pages.subject_id`; the meaning lane returns the cache entry's subject id). Today it prefers the page's *own* row id (`page.ID`, falling back to the subject id only when empty) — an id the downstream subject lookup can never resolve, so every ask that successfully pinned failed outright with `wiki: subject not found` (a second, independent source of the observed live failure). The page row id appears in no other hit and serves no consumer; it is simply the wrong field.

**Why this belongs to this goal.** With D86's drop-and-continue in place, both drifts stop erroring and instead **silently discard every pinned hit forever** — the pin feature becomes dead code with no symptom. Fixing the pin is therefore a precondition of shipping D86 without burying a feature: after this Decision, a pinned hit resolves and survives to the answer, so the drop path never sees it.

**Error surface unchanged.** The pin path keeps its existing posture: a candidate that resolves to nothing is skipped silently (not-found is the common case — most sub-queries are not exact names); real resolver/store errors propagate and fail the search.

**Rejected.**
- **Leaving the pin as-is and letting D86 absorb the failures.** Turns a broken feature into an invisible one — the discriminating regression this goal exists to prevent. The pin either works inside the wall or is dead code; the operator chose to fix it (grill Q7).
- **Deleting the pin feature instead.** D33's rationale stands: an exact-name question should surface its named subject first, above fusion noise. The feature lost to drift, not to a design flaw.
- **Resolving pin candidates across all scopes as a "helpful" fallback.** Reintroduces exactly the cross-scope leak D74 forbids; the wall admits no fallback reads.

**Verification.**
- R-RG1Q-6WK2 — A pin candidate naming a subject that exists in the **asked** scope pins it: the ask's retrieval returns that subject first (the D33 pin position), proven in a non-`default` scope — where before the fix the lookup consulted `default` and the scope's own subject never pinned.
- R-RH9M-KOAR — The wall holds: a candidate naming a subject that exists **only in another scope** (including `default`) does not pin — the other scope's subject appears nowhere in the asked scope's results; same-named subjects in two scopes pin only their own scope's ask.
- R-RIHI-YG1G — A pinned hit survives to the answer: its `PageID` is the subject id, `ask`'s page-gathering resolves it in the asked scope, and the pinned subject's page is gathered and citable — the end-to-end ask with a pinning question completes with the pinned subject cited, where before the fix it errored (or, under D86 alone, silently dropped the pin).
