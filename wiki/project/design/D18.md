# Decision 18 — Output-token budget & honest truncation handling

**Decision.** Every call site carries an explicit, generous output budget, the seam **detects truncation** and surfaces a **distinct reason**, and truncation is **terminal for the call** so no retry re-truncates. (History: with no budget, generations ran at a provider-adapter default of 4096; a large extract overran it, the reply stopped mid-JSON, and the job died as `unexpected end of JSON input` after burning every re-prompt identically.) Extends the D5 seam and the D6/D7 call-site defaults; the atomic no-partial-write failure path is D4 (R-MB7F).

## (a) `MaxTokens` on the call site, faithfully applied

The ceiling lives on the D5 `Config` (`max_tokens`), carried verbatim in the queue item's payload, so the configured ceiling reaches prompts (and through it the provider) instead of any silent adapter default. A production JSON call site **never leaves `MaxTokens` at 0**; the default call sites below set it explicitly.

## (b) Truncation detected at the seam

A terminal `done` item carries the item's aggregate usage; detection lives in the D5 seam wherever a result is consumed — `JSON` on the live path, the D4 applier on the pipeline path. When the reported **output-token usage meets or exceeds the site's `MaxTokens`** (and `MaxTokens > 0`), the result is a **truncation**, not a normal reply: the consumer surfaces the distinct sentinel `llm.ErrTruncated` (wrapping stage/usage) instead of the truncated result. (The attempts are on prompts' record; wiki records nothing, D63.) When the item carries **no** usage, detection cannot fire and the result falls through to the normal decode path unchanged.

## (c) Truncation is terminal — no futile re-prompt

Truncation is **non-retriable**: no corrective item is ensured, because a re-prompt under the same ceiling truncates identically. (A normal semantic failure still retries via a corrective item, D5 R-K27Y-00XB.) On the pipeline path the error ends the job `failed` with this reason and writes **zero** subjects/claims/pages (D4 R-MB7F).

## (d) The budgets

Each stage owns its ceiling in its `DefaultCallSite` (D6 extract, D7 compile; the ask sites per D19), generously above realistic output and tunable via manifest knobs:

- **extract** — sized well above the largest realistic per-document extraction, e.g. **16384**. Contract is "generously above realistic extract output," not the exact integer.
- **compile** — sized above the 12,000-char page cap (~3–4 K tokens) plus structural overhead, e.g. **16384**.
- **ask** — both ask call sites cap `MaxTokens` at **16384**, uniform with the other stages.

These are headroom, not a guarantee any document fits: a pathologically large source can still exceed the budget, and when it does it fails **honestly** (b/c). Chunking oversized sources remains a deferred follow-on.

**Rejected.**
- **Just raising the budget without detecting truncation.** A bigger ceiling pushes the failure out but never removes it. Detection + a clear reason is the durable fix.
- **Inferring truncation from the parse error text** (`unexpected end of JSON input`). Brittle — couples wiki to the encoding/json wording and confuses a malformed-but-complete reply with a truncated one. Usage-at-ceiling is precise and provider-grounded.
- **Retrying a truncation with a larger budget automatically.** Doubles cost and latency and still has a ceiling; failing fast with a clear reason is simpler. (Deferred with chunking.)

**Verification.**
- R-MSKH-GPX5 — The ensured item's payload carries the call site's `MaxTokens` verbatim as `max_tokens` (captured via the httptest prompts queue), instead of omitting it for a downstream default.
- R-MTSD-UHNU — When a collected `done` item reports output usage at/above the call site's `MaxTokens` with a truncated result, the consumer returns a distinct truncation error (not a generic JSON-parse error).
- R-MV0A-89EJ — A truncation is terminal for the call: `JSON` returns immediately without re-prompting, even with `MaxParseRetries > 0` (exactly one HTTP call is made), distinguishing it from a retriable unmarshal/validate failure.
- R-MW86-M158 — `extract.DefaultCallSite` and `compile.DefaultCallSite` each carry `MaxTokens >= 16384` (a test that passes at 4096 does not cover this), and the extractor/compiler the composition root builds are constructed from them, so the production stages run at that budget.
