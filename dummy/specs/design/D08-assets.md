# D08-assets

dummy's pages take the platform's visual style from files dummy does not author: the stylesheet every page links, the fonts that stylesheet loads, one of which every page preloads, the button-feedback script every page links, the favicon every page links as its icon, and the licences of the fonts and of the Tabler icons the style draws. They are the platform's shared web files, the same for every app, and they come from appkit's `page` package (`github.com/ikigenba/ikigenba/appkit/page`), which embeds them and serves them through the handler `page.Static()` returns, under the prefix `page.StaticPrefix`, `/_appkit/`. This design is how dummy mounts that handler and what a caller observes of it through dummy.

dummy holds no copy of any of these files. Its own `assets/` directory holds only its page templates (`D04-panel`, `D06-table`, `D07-form`), including those of the about and tools pages, which are never served as files; dummy has no `/assets/` route and no extension-to-`Content-Type` table of its own, and a path under `/assets/` is an ordinary path that does not exist, answered by `D04-panel`'s catch-all like any other.

## Mounting inside the identity gate

The shared files are routes like any other, served by `panel.Handler` (`D04-panel`), which mounts the handler `page.Static()` returns at `page.StaticPrefix` on the mux it wraps in `identity.Require`, and passes it every request whose path begins with `/_appkit/`, unchanged: that handler compares the request's whole `URL.Path` against `/_appkit/<name>` itself, so no prefix is stripped. The identity gate runs first, as on every route, so a request with no `X-User-Id` gets `D04-panel`'s plain 500, recorded by its `request.finished` with nothing written to stderr, and is never answered by appkit at all. `D04-panel`'s rule that a `HEAD` is answered with the status and headers of the matching `GET` does not reach here: appkit promises a `HEAD` of a served name only the `GET`'s status, its `Content-Type`, `ETag` and `Cache-Control`, and an empty body, and leaves every other header of either answer open, so that is all dummy states. Because every such path is none of `/`, `/widgets`, `/widgets/table` and `/mcp`, `D04-panel`'s store-neutrality requirement for such paths already guarantees that no request for a shared file changes the widgets.

Delegation is one requirement: through dummy, a request with identity under `/_appkit/` gets exactly what appkit's handler gives it. The requirements after it state what dummy relies on of that answer, as dummy's own observable behaviour, so that dummy's tests fail if a different appkit release stopped giving it. They agree with appkit's published contract for `page.Static` (its D04), which fixes the same files, types, validators and refusals.

## What is served

Five paths name a file by a fixed name: `/_appkit/` followed by `theme.css`, `feedback.js`, `favicon.svg`, `OFL.txt` or `TABLER-LICENSE.txt`, compared byte for byte. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit are not served. dummy never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads (`D04-panel`), and the paths the served stylesheet names, each a `url("…")` of a name ending in `.woff2` beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet dummy serves. The path compared is the request's `URL.Path`, which `net/http` stores decoded. A plain `GET` of one — one carrying none of `If-None-Match`, `If-Modified-Since`, `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range` — answers 200 with the file and a fixed `Content-Type` per file; the body is the same bytes on every request to one binary, and no requirement says what the bytes are. Every other path under `/_appkit/` — the prefix itself, another name such as `banner.html`, a served name with a further `/` or segment, a served name in other letter case, a font path with its hash taken out — answers 404, whatever the method; a method other than `GET` and `HEAD` on a served name answers 405 with `Allow: GET, HEAD`. The bodies and other headers of the 404 and the 405, an `ETag` included, are appkit's and are not fixed here: they are not HTML documents with the banner, and nothing under `/_appkit/` is.

## Revalidation

Every 200 and 304 for a served name carries one strong `ETag`. A font path's answer carries one `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again; every other served name's carries one `Cache-Control: no-cache`, so a browser keeps its copy but asks each time. The tag's value is opaque here; what is fixed is that it is a well-formed strong entity tag (RFC 9110 section 8.8.3) and that one binary gives one file the same tag every time. That different content yields a different tag is appkit's property and not dummy's: dummy embeds no content of its own under `/_appkit/`, and every such request is handed to `page.Static()`, so one dummy binary only ever serves one content for each file. Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, the plain requests appkit's contract covers. Such a request whose single `If-None-Match` line is `*`, or a comma-separated list of tags one of which, with any `W/` removed, is the file's tag, gets 304 with an empty body and the same tag, whatever `If-Modified-Since` says; a well-formed list holding at least one tag, none of them current, gets the 200 as if the field were absent, also whatever `If-Modified-Since` says. Several `If-None-Match` lines, a malformed list, a list holding no tag at all, `Range`, `Last-Modified`, `If-Match`, `If-Unmodified-Since`, `If-Range`, and `If-Modified-Since` without `If-None-Match` are not fixed here.

## REQUIREMENTS

- R-RC34-YCCP: dummy's design defines an **appkit path** as a request path — the value of the request's `URL.Path` field, which `net/http` stores decoded — that begins with `/_appkit/`, the value of `page.StaticPrefix`; a **font path** as the string `page.PreloadURL()` returns, and as `/_appkit/` followed by any string `f` that ends in `.woff2`, contains none of the characters `/`, `\`, `:`, `"`, `?`, `#` and `%`, and occurs, immediately preceded by `url("` and immediately followed by `")`, in the body of the 200 answer `Handler` gives to a `GET` request carrying a non-empty `X-User-Id` header and none of the headers `If-None-Match`, `If-Modified-Since`, `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, whose path is `/_appkit/theme.css`; and a **shared file path** as an appkit path that is a font path or is exactly `/_appkit/` followed by one of `theme.css`, `feedback.js`, `favicon.svg`, `OFL.txt`, and `TABLER-LICENSE.txt`, compared byte for byte and so case-sensitively; and every requirement in dummy's design that names an appkit path, a font path or a shared file path MUST denote such a path.
- R-19LL-IENZ: `Handler` MUST answer every request carrying a non-empty `X-User-Id` header whose path is an appkit path, whatever its method and other headers, exactly as the `http.Handler` that `page.Static()` returns answers the same request: with the same status, the same set of header fields with the same values, and the same body.
- R-RDB1-C43E: `Handler` MUST answer a `GET` request carrying a non-empty `X-User-Id` header and none of the headers `If-None-Match`, `If-Modified-Since`, `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, whose path is a shared file path, with status 200, a non-empty body, and exactly one `Content-Type` header, whose value is exactly `text/css; charset=utf-8` for `/_appkit/theme.css`, exactly `text/javascript; charset=utf-8` for `/_appkit/feedback.js`, exactly `image/svg+xml` for `/_appkit/favicon.svg`, exactly `font/woff2` for each font path, and exactly `text/plain; charset=utf-8` for each of `/_appkit/OFL.txt` and `/_appkit/TABLER-LICENSE.txt`.
- R-REIX-PVU3: `Handler` MUST answer a `HEAD` request carrying a non-empty `X-User-Id` header and none of the headers `If-None-Match`, `If-Modified-Since`, `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, whose path is a shared file path, with status 200, an empty body, exactly one `Content-Type` header, whose value is the one R-RDB1-C43E states for that path, and the `ETag` value that a `GET` of that path carrying none of those headers is answered with.
- R-Y960-B9D1: A response `Handler` sends with status 200 or 304 to a request carrying a non-empty `X-User-Id` header whose path is a shared file path MUST carry exactly one `ETag` header, whose value is a strong entity tag — a `"`, then zero or more characters each of which is the byte 0x21 or in the byte ranges 0x23–0x7E and 0x80–0xFF, then a `"`, with nothing before or after — and, when that path is not a font path, exactly one `Cache-Control` header, whose value is exactly `no-cache`.
- R-YADW-P13Q: A response `Handler` sends with status 200 or 304 to a request carrying a non-empty `X-User-Id` header whose path is a font path MUST carry exactly one `Cache-Control` header, whose value is exactly `public, max-age=31536000, immutable`.
- R-M9E7-IAKV: Any two `GET` requests carrying a non-empty `X-User-Id` header and none of the headers `If-None-Match`, `If-Modified-Since`, `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, whose path is the same shared file path, answered by `Handler` in one binary, whether by one handler or by two, MUST be answered with byte-identical bodies and the same `ETag` value.
- R-YBLT-2SUF: `Handler` MUST answer a `GET` or `HEAD` request carrying a non-empty `X-User-Id` header and none of the headers `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, whose path is a shared file path, and which carries exactly one `If-None-Match` header line whose value either is exactly `*` or is a list of one or more elements separated by commas — each element being empty or, once leading and trailing spaces and tabs are removed, an entity tag of the form R-Y960-B9D1 describes, optionally preceded by `W/` — at least one of whose entity tags, with any `W/` removed, is byte-identical to the `ETag` value a `GET` of that path carrying no `If-None-Match` header is answered with, with status 304, an empty body, and that same `ETag` value, whatever `If-Modified-Since` header the request carries.
- R-YCTP-GKL4: `Handler` MUST answer a `GET` request carrying a non-empty `X-User-Id` header and none of the headers `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`, whose path is a shared file path, and which carries exactly one `If-None-Match` header line whose value is not `*` and is a list of the form R-YBLT-2SUF describes holding at least one entity tag, none of whose entity tags, with any `W/` removed, is byte-identical to the `ETag` value a `GET` of that path carrying no `If-None-Match` header is answered with, with status 200, that `ETag` value, and the body that `GET` is answered with, whatever `If-Modified-Since` header the request carries.
- R-MD1W-NLSY: `Handler` MUST answer a request carrying a non-empty `X-User-Id` header whose path is a shared file path and whose method is neither `GET` nor `HEAD`, whatever `If-None-Match` header it carries, with status 405 and the header `Allow: GET, HEAD`.
- R-ME9T-1DJN: `Handler` MUST answer a request carrying a non-empty `X-User-Id` header whose path is an appkit path and not a shared file path — `/_appkit/` itself, a shared file path followed by further characters, and a shared file path's name in other letter case included — whatever its method and whatever `If-None-Match` header it carries, with status 404.
- R-YE1L-UCBT: For every font path that ends in `.`, then one or more hexadecimal digits, then `.woff2`, `Handler` MUST answer a request carrying a non-empty `X-User-Id` header, whatever its method, whose path is that font path with that `.` and those hexadecimal digits removed, with status 404.
