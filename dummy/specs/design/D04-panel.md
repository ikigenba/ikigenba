# D04-panel

What a visitor gets from a running dummy. dummy's whole HTTP surface lives in one package, `internal/panel`: the one `http.Handler` the process serves, the identity gate every request passes through, routing, the MCP endpoint's mount, the template set every page is rendered from and the data each page template receives, the page frame the platform's banner and footer are drawn in, the head every page carries, the two failure shapes, the panel page itself, the about page and the tools page, and the trail each page hands the banner. What a serving `cli.Run` answers on its socket is this handler's behavior over one widget store, built over the database `Run` opened, and the banner source, MCP server and telemetry writer in `cli.Process` (`D01-layout-and-run-seam`, `D03-serve`). This design says nothing about the socket, nginx, TLS or the host's name, because none of those reach the handler.

dummy builds on four packages of appkit (`github.com/ikigenba/ikigenba/appkit`, at the release `AGENTS.md` names): `page` for the banner and footer templates and the shared files under `/_appkit/`; `identity` for the gate; `mcp` for the MCP server; and `telemetry` for the trail every request leaves. The banner is the platform's, the same for every app: appkit ships it as the template named `banner` in the set `page.Templates()` returns, together with the footer that ends each page, the template named `footer`, drawn from the same data. dummy decides what goes into it — the caller's email and the two auth URLs it derives from the request — and where it goes on the page; appkit decides how it is drawn. The banner data comes from the **banner source**, the function `Handler` is built over: in the running binary the `Banner` method of the kit `main` made with `page.New(ServiceName, id)`, `id` being the identity `main` reads (`D01-layout-and-run-seam`), which adds the service's name, the identity's release and commit, and dummy's icon, the home app's URL and whether dummy offers MCP tools, read afresh from the host's services file on every call; in a test, a closure returning whatever the case needs.

Five sibling designs finish the surface. `D05-widgets` owns the domain — the widget, the store over dummy's database, the line `widget.Unreachable` every consumer answers when the store cannot reach the widgets, and the rules a submission is judged by. `D06-table` owns the `table` template's data and the whole of the `GET`/`HEAD /widgets/table` route. `D07-form` owns the `form` template's data and the whole of `POST /widgets`. `D08-assets` owns the platform's shared files dummy serves through appkit and every answer a request under `/_appkit/` gets: it defines an **appkit path**, and this document uses that term to leave those paths out of its catch-all. `D09-mcp` owns dummy's MCP tools: their names, schemas, descriptions and effects. This document states nothing route-specific about `/widgets/table` beyond that it exists, so that routing stays total, and nothing about what `/mcp` answers beyond that it is the MCP server's answer.

Every exported name of `internal/panel` but one is declared here, `MethodNotAllowedBody` and `UnsupportedMediaTypeMessage` included, even though the behavior that names each is stated by `D06-table` or `D07-form`; the exception is `FormView`, the `form` template's data, which `D07-form` declares. So are `Description`, dummy's one-line description, which the about page shows and the manifest publishes (`D02-cli`), and `AboutData`, `ToolsData` and `Tool`, the data of the `about` and `tools` templates. `ServiceName` is declared here too: `main` hands it to `page.New`, `mcp.NewServer` and `telemetry.New` (`D01-layout-and-run-seam`), so the name the page template is handed, the name appkit's banner shows, the name the MCP server reports, and the service every event of dummy's trail names are one declaration.

## What this revision retires

An earlier iteration of this design had dummy check identity itself and declared `MissingIdentityBody` for its answer; appkit's `identity.Require` now does that, for every app the same way, and its `identity.MissingBody` is the body. The earlier `Handler` took no MCP server and imported appkit's root package, which no longer exports anything. The earlier `internal/panel` built markup in Go and its templates lived under `internal/panel/templates`; markup now lives only in dummy's human-authored `assets/` (`AGENTS.md`), embedded by the module's root package (`D01-layout-and-run-seam`). The previous `Handler` took a `stderr` writer and wrote a line for every missing-identity 500; under the suite's two-channel rule a handled failure is a trail event, so that line, the `stderr` parameter and the requirements that fixed it are gone, and `Handler` takes the telemetry writer instead (below). `html/template`'s contextual autoescaping is the only escaping there is, and dummy's template set carries no function of its own. An earlier revision also fixed the pages' words, markup and hooks and defined how a test reads them; those are copy, kept in the templates alone, and every requirement that named them is retired: a page is designed as the template it executes and the data it is handed.

The earlier handler was built over an in-memory widget set seeded with three fixture widgets at process start, and its requirements read that set through a `Store.All()` that could not fail. The store now keeps the widgets in dummy's database (`D05-widgets`), so every read and write can fail, and the requirements read the store through the term the widgets of a store (below) rather than through a call shape; a later change to `All`'s signature re-mints that one definition instead of every requirement that compares the widgets before and after a request.

## Identity comes first

An nginx gate in front of dummy authenticates every request and sets `X-User-Id` and `X-User-Email` on what it passes upstream, and a sibling app that calls dummy — the MCP gateway included — forwards the ones it received (`D03-serve` states the terms). Only nginx and the suite's own apps can reach dummy's socket. So a request arriving without `X-User-Id` says the gate or a sibling is misconfigured — dummy's fault to report, not the caller's to fix, hence a 500 and not a 400 or a 401. `X-User-Id` alone gates the request: a present-but-empty value counts as missing. `X-User-Email` is not a precondition at all; dummy hands the banner source whatever arrived, which may be nothing.

`Handler` wraps its whole mux — the pages, the fragment, the form, the shared files under `/_appkit/` and `/mcp` — in `identity.Require(mux)`, and wraps that in `telemetry.Middleware(w, …)` with its telemetry writer, so the middleware sees every request, the ones `Require` refuses included. What `Require` answers is appkit's contract (its D06), and dummy restates the parts it relies on as dummy's own observable behavior, so dummy's tests fail if a different appkit release stopped giving it: status 500 and `Content-Type: text/plain; charset=utf-8`; appkit promises nothing more of its headers, so dummy states nothing more. The body is the one exception: dummy states it as the value of appkit's `identity.MissingBody` (empty for `HEAD`) rather than restating its bytes, so a test compares the body against appkit's constant. The 500 writes nothing to standard error: it is recorded, like every other answer, by its `request.finished` event.

The gate runs before dummy looks at the path or the method, so a request without identity is never a 303, a 404, a 405 or a 415, on any route, and never reaches the MCP server, the banner source, or appkit's static handler. There is no unauthenticated case anywhere, so there is no sign-in page and no signed-out banner.

## The trail every request leaves

Every request `Handler` answers is recorded through its telemetry writer, whatever the route and whatever the answer, the missing-identity 500 and the shared files under `/_appkit/` included. appkit's `telemetry.Middleware` does the recording (its D14); dummy restates what it relies on as its own observable behavior, for the same reason it restates the gate's answer. A request records `request.started`, with its method and its path but never its query, before anything else recorded for it, and `request.finished`, with the status appkit's middleware records for it, how long that took, and how many bytes of the request's body were read and of the answer's body were written, after everything else. That status is the one appkit's D14 defines, not always the status on the wire: they differ, for instance, for a request whose handling panics before anything is written, recorded as 500. Between them fall dummy's own events for the request — `widget.created` (`D07-form`, `D09-mcp`) — and the `tool.called` appkit's MCP server records for a tool call. Every one of them carries the request's `X-Request-Id`, or, when the request has none or an empty one, an id the middleware mints from the writer's random source in nginx's shape, so a test that supplies the writer's `Rand` knows the id in advance; and the caller's `X-User-Id`, empty when there is none. No event carries the caller's email, a query, or a widget's name, count or status: each event's attributes are exactly the ones named for it. Conversely, a widget's id is the trail's name for it and the MCP tools' to show; no page and no table fragment shows it, whatever the templates are handed. Every event dummy records is well formed, so while telemetry takes every event the writer has nothing to write to standard error, and a healthy dummy is silent.

A test observes all of this by building the writer itself, over appkit's capturing sink (`&telemetry.Capture{}`) with a buffer as its `Stderr`, building the MCP server over the same writer, handing both to `Handler`, driving requests, calling `Writer.Flush`, and reading `Capture.Events` in order.

## The space, the scheme, the profile URL and the logout URL

The banner offers sign-out as a one-button `POST` to auth's `/logout` on the same space, and a way to the caller's profile at auth's `/`. dummy decides both addresses and hands them to the banner; appkit draws them. What auth does at either address is auth's behavior and is not restated here; dummy serves no logout route — `/logout` is an unknown path like any other — and sets no cookie on any answer.

dummy derives the space per request, from the request's own `Host`: strip a trailing port if there is one, then strip a single leading `dummy.` label; what remains is the space. The logout URL is the scheme, `://auth.`, the space, and `/logout`; the profile URL is the same with `/` in place of `/logout`. When `Host` carries no `dummy.` label to strip — as on a developer's laptop — both name auth's local origin instead, `http://localhost:3001/logout` and `http://localhost:3001/` — auth's published local origin, not anything read from auth's tree.

The scheme reading is deliberately strict. It is `X-Forwarded-Proto` only when that header is exactly `http` or exactly `https`; anything else — `HTTPS`, a `https, http` list, a stray space, an empty value, an absent header — yields `https`. The header is attacker-influenced unless the gate rewrites it, so its bytes must never reach a rendered URL unvalidated, and a request whose `Host` carries a space is by construction a deployed one, where `https` is the truth. `LogoutURL` and `ProfileURL` are exported so each derivation is testable directly, as a table of host and forwarded-proto against the resulting URL.

## The template set and the data each template receives

dummy's markup is six Go `html/template` files in `assets/` — `page.html`, `table.html`, `form.html`, `script.html`, `about.html` and `tools.html` — written and approved by a human (`AGENTS.md`), embedded by the module's root package and handed out as `dummy.Assets()` (`D01-layout-and-run-seam`). `Handler` makes **dummy's template set** once: it takes a fresh set from `page.Templates()`, which already defines appkit's `banner`, `footer` and `preload`, and parses every file of `dummy.Assets()` into it. The files define the templates `page`, `table`, `form`, `script`, `about` and `tools`. No function is added to the set, so the templates use `html/template`'s predefined functions and nothing else, and every value a template writes goes through its contextual autoescaping. The code never writes markup of its own: every HTML body `Handler` sends is the output of executing one of these templates.

The `page` template draws every HTML document dummy sends, in one of two states, chosen by its data. Its data, **page data**, has six fields:

- `Banner`, the `page.Banner` the banner source returned for this request; the template draws appkit's banner and footer from it.
- `Panel`, true for the panel page and false for a failure page.
- `Message`, the failure message on a failure page (`NotFoundMessage`, `MethodNotAllowedMessage` or `UnsupportedMediaTypeMessage`), empty on the panel page.
- `Count`, the number of widgets the page's table shows.
- `Table`, the `table` template's data (`D06-table`), which the template passes to `{{template "table" .Table}}`.
- `Form`, the `form` template's data (`D07-form`), which the template passes to `{{template "form" .Form}}`.

The `script` template receives no data; the panel state of `page` invokes it.

The `about` template receives an `AboutData`: the banner, and `Description`. The `tools` template receives a `ToolsData`: the banner, and `Tools`, one `Tool` per MCP tool, each a name and a description. Executing either with any value of its type, the zero value included, succeeds, so markup that cannot take its data fails a test rather than a page.

The requirements state the data `Handler` passes to each template and that the body is exactly the template's output for it, so a test renders the expected body itself from dummy's template set and compares, or checks that a value it supplied appears in the body. What a template writes for its data — its words, its markup, its classes, ids and attributes — is the asset's, and no requirement and no test names it. A template that cannot show a state this design names is an issue for a human, never a change the build makes to the asset.

## The banner, the footer and the two failure shapes

Everything in this section is said about **an HTML document dummy sends**: every non-empty `text/html; charset=utf-8` body `Handler` sends except the ones answering `/widgets/table` (whose fragment `D06-table` designs), `/mcp` (whose answers are the MCP server's), or an appkit path.

Every HTML document dummy sends but the about and tools pages is the `page` template's output for page data whose `Banner` is what the banner source returned while that request was answered, and the template draws appkit's banner and footer from it; the about and tools pages are their own templates' output, drawn from that same value with its trail set (below). `Handler` calls the banner source once per page, with the **banner user** for the request — the email `X-User-Email` carried and the two URLs `ProfileURL` and `LogoutURL` derive from its `Host` and `X-Forwarded-Proto` — afresh for every page, so when the kit's services file changes the next page shows it; and never for an answer that draws no banner — the missing-identity 500, the fragment, `/mcp`, the shared files — so those never cause a read of the services file.

What appkit draws is appkit's, and dummy depends only on what appkit promises of it: that `page.Templates()` defines `banner` and `footer` and renders them, invoked from a template dummy parses into the set, as appkit's D03 describes for the `page.Banner` they are handed, and that the kit's `Banner` fills that value as appkit's D02 describes. dummy restates none of what appkit draws. dummy's part, which its tests prove, is the data: every page is executed with the `page.Banner` the banner source returned for the banner user of that request. Which icon the kit puts in the banner — that of dummy's own entry in the services file, none when it has none — and the release and commit it fills from the identity are the kit's behavior (appkit's D02), proved by the wiring and not by dummy's handler tests.

dummy's tests cannot build the kit inside a handler test without setting the environment, so they draw the banner through an **echoing banner source**: a function returning the banner user's three values with `ServiceName`, and no icon, release or commit, since the handler draws whatever its source returns and those are the kit's to fill; they compare each page against the text appkit's templates write for that value. The one exec'ing test compares the running binary's page against a kit it makes itself over the same services file (`D01-layout-and-run-seam`).

A failure dummy can name to an identified caller is itself a page with the banner, with a way back to the panel; only the missing-identity fault, where there is no identity to draw with, is bare text. So there are two failure shapes, defined here as shapes; which one a route uses is stated by whoever owns the route. The **plain failure shape** is a fixed `text/plain` body, a copy constant. The **banner failure shape** is the `page` template's failure state, executed with failure page data for a message constant. `D06-table`'s route is plain always, because the panel's script splices that response into a live document.

A **panel page** is a document shape a requirement assigns — the 200 on `GET /widgets` here, the 422 body in `D07-form` — never one a body has merely by looking like one; were it decided by appearance, the 404 page would qualify and be required to carry a table and a form. It is the `page` template's panel state, executed with **panel page data**.

## The about page, the tools page and the trail

Every app in the suite has an about page and, when it offers MCP tools, a tools page, both reached from the banner's page menu, which appkit draws. dummy answers `GET` and `HEAD /about` with the `about` template, executed with an `AboutData` holding the page's banner and `Description`, the same constant the manifest's description line carries (`D02-cli`), so the two cannot drift. It answers `GET` and `HEAD /tools` with the `tools` template, executed with a `ToolsData` holding the page's banner and one `Tool` per entry of `Tools()` of the MCP server `Handler` was built over, in that order: the server `tools.Register` filled and that serves `/mcp`, so the page lists exactly the names and descriptions, in registration order, that `tools/list` gives, and a tool added to `D09-mcp` appears on the page with no change here. Any other method on either path is a 405 naming `GET, HEAD`, in the banner failure shape, like dummy's other pages. A `HEAD` is answered as the `GET` is, with an empty body. Neither page needs a widget, so each is answered the same while the store is unreachable, and neither changes the store. `Description` holds no quote, backslash or control character, so the manifest can carry it verbatim as a TOML basic string.

The banner draws the page's place below the app's landing page as a trail of levels (appkit's `page.Banner.Trail`, each a `page.Level` with a name and a URL); the kit's `Banner` always returns an empty trail (appkit's D02), and the app sets the levels per page after the call. dummy's levels:

- `/about`: exactly one level, name `about`, URL `/about`.
- `/tools`: exactly one level, name `tools`, URL `/tools`.
- `/widgets`, the landing page (`/` redirects there): no level.
- Every notice page — the 404, the 405s and the 415 — and the 422 redraw of the panel: no level.

The table fragment draws no banner and so has no trail. dummy states the empty trails by stating that those pages are drawn from exactly the banner the source returned, which, from the kit, carries none; only the about and tools pages replace the source's trail with their one level. A test proves each page by executing the named template with the banner its echoing source returns, the trail set as above, and comparing, or by checking that the level's name and URL it expects appear in the body.

## The head and what a page loads

Everything before a page's body — its title, the platform stylesheet, the font preload, the favicon, appkit's feedback script and the viewport — is the `page` template's; the font preload is appkit's `preload` template, invoked from it, because the font's URL carries a hash of its bytes that dummy never writes. Design fixes none of it: the head is part of the template's output that a test compares whole. The table fragment is spliced into a page that already has a head, and the plain-text 500 has none.

A page makes no request to any third party. The part of that a page's own markup decides is the asset author's obligation, held in the template, not a requirement: stating it would mean reading markup.

## A caller's bytes never become markup

Three kinds of caller-supplied value reach a page: the email from `X-User-Email`; the profile and logout URLs, which derive from `Host` and `X-Forwarded-Proto`; and, on a 422, the name, the count and the status exactly as they were submitted. No value a caller sends may contribute a tag. `html/template`'s contextual autoescaping is how both dummy's templates and appkit's get there, and since every body dummy sends is a template's output and the set carries no function of its own, it holds without a requirement of dummy's that would have to read markup.

## The panel page

The panel page is the `page` template's panel state, executed with panel page data: the widgets the table draws (`D06-table`), their count, and the form's data (`D07-form`). Because `Count` is the length of the same slice the table draws, the count the page shows and the rows its table shows never disagree. It is drawn when the page is rendered and sits outside the table, so a poll never changes it; it catches up on the next load. Because it is stated over every panel page, the 422 redraw carries it too.

The panel keeps itself fresh with the `script` template's inline script, which re-fetches the table fragment every 5 seconds and swaps it into the page. What it does cannot be decided without a JavaScript engine, which the gates do not have, so design fixes only that the panel state is the `page` template's output, which invokes the script.

## Routing

Identity first, then path, then method. Path matching is exact on the URL's path component and nothing else; `/widgets/`, `/widgets/table/`, `/about/`, `/tools/` and `/mcp/` are unknown paths and take the 404, and dummy never answers a trailing-slash variant with a redirect, which Go's `http.ServeMux` would otherwise supply.

The table is total. `/` answers `GET` and `HEAD` with a 303 to `/widgets` and every other method with a 405 naming `GET, HEAD`. `/widgets` answers `GET` and `HEAD` with the panel page, `POST` as `D07-form` defines, and every other method with a 405 naming `GET, HEAD, POST`. `/about` and `/tools` answer `GET` and `HEAD` with the about and tools pages and every other method with a 405 naming `GET, HEAD`. `/widgets/table` is answered as `D06-table` defines. An appkit path is answered by appkit as `D08-assets` says. `/mcp`, exactly that path, is answered by the MCP server, whatever the method — its 405 for a `GET`, with `Allow: POST`, is appkit's and never one of dummy's pages. Every other path is a 404 with the banner, whatever the method — `/mcp/` and everything beneath it, `/assets/` and everything beneath it included.

A `HEAD` with identity is answered exactly as the corresponding `GET` would be — same status, same headers, empty body — on every route dummy answers itself. `/mcp`'s answers are the MCP server's, and an appkit path's are appkit's, whose `HEAD` promises are narrower and are stated in `D08-assets`; the missing-identity 500 is the gate's, whose `HEAD` is promised only its status, its `Content-Type` and an empty body. Reading never mutates: the requirements below state it for every read route.

## The MCP endpoint

`Handler` is built over an MCP server `main` made with `mcp.NewServer` (`D01-layout-and-run-seam`), one no tool was registered on and that has not served. Before it returns, `Handler` registers dummy's tools on it by calling `tools.Register(srv, s, w)` (`D09-mcp`), so the tools act on the same store the panel shows, and mounts it at exactly `/mcp`, inside the identity gate. The tools page reads the same server's `Tools()`, so the page and `tools/list` name the same tools. A request with identity to `/mcp` gets exactly what the server gives it, with the caller the gate put in the request's context; a request without identity gets the gate's 500 and never reaches the server. What the server answers — the protocol, its versions, its statuses, the instructions — is appkit's (its D07) and the tools are `D09-mcp`'s.

## The widgets of a store, and when they cannot be reached

The handler reads and writes the widgets only through the store it was built over. Requirements throughout dummy's design need to say what that store holds before and after a request, so this document defines it once: the **widgets of** a store at a moment are the slice its `All` returns then, when it returns no error. A store is **reachable** while its calls succeed and **unreachable** while every call of `All`, `Check` and `Create` fails, which is exactly what appkit's `SetFailing(true)` on the database handle under it provokes (`D05-widgets`); a test opens a database in its own temporary directory with appkit's `db.Open` and `dummy.Migrations()`, builds the store over it, seeds what the case needs, and flips that switch.

While the store is unreachable, a route that shows or stores widgets has nothing true to say, and drawing an empty panel would tell the user the widgets were gone. So such a route answers the **unreachable answer**: a 503 in plain text whose body is the line `widget.Unreachable` and a newline, with no banner, no footer and no `ETag`, quoting nothing of the database's own error. That shape needs no template: it is a fixed line like the missing-identity 500. The panel (`GET`/`HEAD /widgets`) answers it here; the fragment answers it in `D06-table`, conditional requests included; the form answers it in `D07-form` for every form-encoded submission, acceptable or not, since a rejection would redraw the table. Every route that needs no widget is answered exactly as it is while the store is reachable: the missing-identity 500, the root's redirect, the 404, the 405s, the 415 and the shared files. The MCP tools refuse with the same line as an `isError` result (`D09-mcp`). The status the trail records for the 503 is appkit's middleware's, like every other.

An empty database is not a failure: a store with no widgets is reachable, and the panel is drawn with an empty slice of widgets, which the requirements below and `D06-table`'s already cover for every widget count.

## What the handler does not depend on

The handler's responses do not depend on the process's working directory or on any file outside the binary other than the database its store is built over — dummy's templates are embedded, and appkit embeds its own and the shared files. The other files a response does depend on are the host's services file, which the banner source and the MCP server read, never the handler itself. So the rule is stated for a banner source that reads no file, an MCP server made with no services file, and a store over a database in a temporary directory of the test's own, and tested by driving two handlers with the working directory set to an empty temporary directory and to the checkout.
