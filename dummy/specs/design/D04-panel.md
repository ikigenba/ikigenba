# D04-panel

What a visitor gets from a running dummy. dummy's whole HTTP surface lives in one package, `internal/panel`: the one `http.Handler` the process serves, the identity gate every request passes through, routing, the MCP endpoint's mount, the template set every page is rendered from and the data each page template receives, the page frame the platform's banner and footer are drawn in, the head every page carries, the two failure shapes, and the panel page itself. What a serving `cli.Run` answers on its socket is this handler's behavior over one widget set and the banner source, MCP server and telemetry writer in `cli.Process` (`D01-layout-and-run-seam`, `D03-serve`). This design says nothing about the socket, nginx, TLS or the host's name, because none of those reach the handler.

dummy builds on four packages of appkit (`github.com/ikigenba/ikigenba/appkit`, at the release `AGENTS.md` names): `page` for the banner, launcher and footer templates and the shared files under `/_appkit/`; `identity` for the gate; `mcp` for the MCP server; and `telemetry` for the trail every request leaves. The banner is the platform's, the same for every app: appkit ships it as the template named `banner` in the set `page.Templates()` returns, together with the service launcher it opens and the footer that ends each page, the template named `footer`, drawn from the same data. dummy decides what goes into it — the caller's email and the two auth URLs it derives from the request — and where it goes on the page; appkit decides how it is drawn. The banner data comes from the **banner source**, the function `Handler` is built over: in the running binary the `Banner` method of the kit `main` made with `page.New(ServiceName, cli.Version)`, which adds the service's name, dummy's release version exactly as `--version` prints it, and the launcher's services, read afresh from the host's services file on every call; in a test, a closure returning whatever the case needs.

Five sibling designs finish the surface. `D05-widgets` owns the domain — the widget, the store, and the rules a submission is judged by. `D06-table` owns the `table` template's data and hooks and the whole of the `GET`/`HEAD /widgets/table` route. `D07-form` owns the `form` template's data and hooks, the card it sits in, and the whole of `POST /widgets`. `D08-assets` owns the platform's shared files dummy serves through appkit and every answer a request under `/_appkit/` gets: it defines an **appkit path**, and this document uses that term to leave those paths out of its catch-all and out of the rules it states over what dummy writes. `D09-mcp` owns dummy's MCP tools: their names, schemas, texts and effects. This document states nothing route-specific about `/widgets/table` beyond that it exists, so that routing stays total, and nothing about what `/mcp` answers beyond that it is the MCP server's answer.

Every exported name of `internal/panel` but one is declared here, `MethodNotAllowedBody` and `UnsupportedMediaTypeMessage` included, even though the behavior that names each is stated by `D06-table` or `D07-form`; the exception is `FormView`, the `form` template's data, which `D07-form` declares beside the hooks it carries. `ServiceName` is declared here too: `main` hands it to `page.New`, `mcp.NewServer` and `telemetry.New` (`D01-layout-and-run-seam`), so the name the page's title carries, the name appkit's banner marks and its footer shows, the name the MCP server reports, and the service every event of dummy's trail names are one declaration.

## What this revision retires

An earlier iteration of this design had dummy check identity itself and declared `MissingIdentityBody` for its answer; appkit's `identity.Require` now does that, for every app the same way, and its `identity.MissingBody` is the body. The earlier `Handler` took no MCP server and imported appkit's root package, which no longer exports anything. The earlier `internal/panel` built markup in Go — the `PlusIcon` constant, the pre-rendered banner and footer handed to the page — and its templates lived under `internal/panel/templates`; markup now lives only in dummy's human-authored `assets/` (`AGENTS.md`), embedded by the module's root package (`D01-layout-and-run-seam`), and the plus icon is the `form` template's (`D07-form`). The previous `Handler` took a `stderr` writer and handed it, with `ServiceName`, to `identity.Require`, which wrote the line `dummy: request <id>: X-User-Id is missing` for every missing-identity 500; under the suite's two-channel rule a handled failure is a trail event, so that line, the `stderr` parameter and the requirements that fixed it are gone, and `Handler` takes the telemetry writer instead (below). The earlier design also had dummy's templates escape `=` by hand, through template functions of its own, because its attribute-reading rule could be fooled by a caller's `x" value="y`; that rule now reads attributes the way a browser does (below), so `html/template`'s contextual autoescaping is the only escaping there is, and dummy's template set carries no function of its own.

## Identity comes first

An nginx gate in front of dummy authenticates every request and sets `X-User-Id` and `X-User-Email` on what it passes upstream, and a sibling app that calls dummy — the MCP gateway included — forwards the ones it received (`D03-serve` states the terms). Only nginx and the suite's own apps can reach dummy's socket. So a request arriving without `X-User-Id` says the gate or a sibling is misconfigured — dummy's fault to report, not the caller's to fix, hence a 500 and not a 400 or a 401. `X-User-Id` alone gates the request: a present-but-empty value counts as missing. `X-User-Email` is not a precondition at all; dummy hands the banner source whatever arrived, which may be nothing.

`Handler` wraps its whole mux — the pages, the fragment, the form, the shared files under `/_appkit/` and `/mcp` — in `identity.Require(mux)`, and wraps that in `telemetry.Middleware(w, …)` with its telemetry writer, so the middleware sees every request, the ones `Require` refuses included. What `Require` answers is appkit's contract (its D06), and dummy restates the parts a story fixes as dummy's own observable behavior, so dummy's tests fail if a different appkit release stopped giving it: status 500 and `Content-Type: text/plain; charset=utf-8`; appkit promises nothing more of its headers, so dummy states nothing more. The body is the one exception: dummy states it as the value of appkit's `identity.MissingBody` (empty for `HEAD`), the text the stories show as `identity header missing` and a newline, rather than restating those bytes, so a test compares the body against appkit's constant. The 500 writes nothing to standard error: it is recorded, like every other answer, by its `request.finished` event.

The gate runs before dummy looks at the path or the method, so a request without identity is never a 303, a 404, a 405 or a 415, on any route, and never reaches the MCP server, the banner source, or appkit's static handler. There is no unauthenticated case anywhere, so there is no sign-in page and no signed-out banner.

## The trail every request leaves

Every request `Handler` answers is recorded through its telemetry writer, whatever the route and whatever the answer, the missing-identity 500 and the shared files under `/_appkit/` included. appkit's `telemetry.Middleware` does the recording (its D14); dummy restates what the stories fix as its own observable behavior, for the same reason it restates the gate's answer. A request records `request.started`, with its method and its path but never its query, before anything else recorded for it, and `request.finished`, with the status appkit's middleware records for it and how long that took, after everything else. That status is the one appkit's D14 defines, not always the status on the wire: they differ, for instance, for a request whose handling panics before anything is written, recorded as 500. Between them fall dummy's own events for the request — `widget.created` (`D07-form`, `D09-mcp`) — and the `tool.called` appkit's MCP server records for a tool call. Every one of them carries the request's `X-Request-Id`, or, when the request has none or an empty one, an id the middleware mints from the writer's random source in nginx's shape, so a test that supplies the writer's `Rand` knows the id in advance; and the caller's `X-User-Id`, empty when there is none. No event carries the caller's email, a query, or a widget's name, count or status: each event's attributes are exactly the ones named for it. Conversely, a widget's id is the trail's name for it and the MCP tools' to show; no page and no table fragment shows it, whatever the templates are handed. Every event dummy records is well formed, so while telemetry takes every event the writer has nothing to write to standard error, and a healthy dummy is silent.

A test observes all of this by building the writer itself, over appkit's capturing sink (`&telemetry.Capture{}`) with a buffer as its `Stderr`, building the MCP server over the same writer, handing both to `Handler`, driving requests, calling `Writer.Flush`, and reading `Capture.Events` in order.

## The space, the scheme, the profile link and the sign-out form

The banner offers sign-out as a form, not a link: a one-button `POST` to auth's `/logout` on the same space; its profile link leads to the caller's profile at auth's `/`. dummy decides both addresses and hands them to the banner; appkit draws them. What auth does at either address is auth's behavior, stated in auth's own stories and not restated here; dummy serves no logout route — `/logout` is an unknown path like any other — and sets no cookie on any answer.

dummy derives the space per request, from the request's own `Host`: strip a trailing port if there is one, then strip a single leading `dummy.` label; what remains is the space. The form's `action` is the scheme, `://auth.`, the space, and `/logout`; the profile link's `href` is the same with `/` in place of `/logout`. When `Host` carries no `dummy.` label to strip — as on a developer's laptop — both name auth's local origin instead, `http://localhost:3001/logout` and `http://localhost:3001/`, facts taken from auth's stories, not from auth's tree.

The scheme reading is deliberately strict. It is `X-Forwarded-Proto` only when that header is exactly `http` or exactly `https`; anything else — `HTTPS`, a `https, http` list, a stray space, an empty value, an absent header — yields `https`. The header is attacker-influenced unless the gate rewrites it, so its bytes must never reach a rendered `action` unvalidated, and a request whose `Host` carries a space is by construction a deployed one, where `https` is the truth. `LogoutURL` and `ProfileURL` are exported so each derivation is testable directly, as a table of host and forwarded-proto against the resulting URL.

## The template set and the data each template receives

dummy's markup is four Go `html/template` files in `assets/` — `page.html`, `table.html`, `form.html` and `script.html` — written and approved by a human (`AGENTS.md`), embedded by the module's root package and handed out as `dummy.Assets()` (`D01-layout-and-run-seam`). `Handler` makes **dummy's template set** once: it takes a fresh set from `page.Templates()`, which already defines appkit's `banner`, `launcher` and `footer`, and parses every file of `dummy.Assets()` into it. The files define the templates `page`, `table`, `form` and `script`. No function is added to the set, so the templates use `html/template`'s predefined functions and nothing else, and every value a template writes goes through its contextual autoescaping. The code never writes markup of its own: every HTML body `Handler` sends is the output of executing one of these templates.

The `page` template draws every HTML document dummy sends, in one of two states, chosen by its data. Its data, **page data**, has six fields:

- `Banner`, the `page.Banner` the banner source returned for this request; the template draws `{{template "banner" .Banner}}` as the first thing in the body and `{{template "footer" .Banner}}` as the last.
- `Panel`, true for the panel page and false for a failure page.
- `Message`, the failure message on a failure page (`NotFoundMessage`, `MethodNotAllowedMessage` or `UnsupportedMediaTypeMessage`), empty on the panel page.
- `Count`, the number of widgets the page's table shows, from which the template writes the panel subtitle.
- `Table`, the `table` template's data (`D06-table`), which the template passes to `{{template "table" .Table}}`.
- `Form`, the `form` template's data (`D07-form`), which the template passes to `{{template "form" .Form}}`.

The `script` template receives no data; the panel state of `page` invokes it after its `main` element.

What the `page` template emits in each state is stated below as hooks over the documents `Handler` sends: the head, the frame, the heading, the subtitle, the panel wrapper and the inline script in the panel state; the message and the link back in the failure state. The requirements state the data `Handler` passes and that the body is exactly the template's output for it, so a test can render the expected body itself from dummy's template set and compare; and they state the hooks, so a test can tell whether the asset carries them. Tests assert hooks and visible text, never layout. A hook a requirement names that the asset lacks is an issue for a human, never a change the build makes to the asset.

## Reading a document

dummy's tests have no HTML parser — appkit is dummy's one module dependency and carries none — so the design fixes visible text and hooks and defines how each is read, as procedures the Go standard library can run. They are stated once, here, for every document in this design: `D06-table` and `D07-form` refer to them by name and restate no step. A **start tag** for an element is a `<`, the element's name, a delimiter that is neither an ASCII letter nor an ASCII digit, and everything through the next `>`; an **end tag** is the same with a `/` after the `<`. The **script-stripped form** removes every `script` and `style` element whole; **normalisation** strips, removes the remaining tags, unescapes character references and collapses whitespace; the **visible text** is the normalisation of what lies between `<body>` and `</body>`. Script-stripping runs first, because script source is not markup: a `<` inside it would otherwise swallow real text and a `#widgets-table` in it would be counted as a hook.

A start tag's **attributes** are read the way a browser reads them, from left to right after the tag name: whitespace, a name, and optionally `=` and a double-quoted value, until the tag's grammar stops. An **occurrence** of a named attribute is such an attribute with a value, and its **read value** is that value with character references unescaped and nothing else changed; a **bare occurrence** is one without a value. Reading attributes in sequence, rather than scanning for a name followed by `=`, is what makes `html/template`'s escaping sufficient: it writes a caller's `"` as `&#34;` and leaves `=` and whitespace alone, so the echo of `x" value="zzz` sits whole inside one quoted value, where a sequential reading never mistakes it for a second attribute. Every tag dummy writes is **well formed** — every attribute preceded by whitespace and written bare or with a double-quoted value holding no `"`, `<` or `>` — which is what the escaping produces for a caller's value and what makes the first `>` the browser's end of the tag.

These rules are over what dummy writes, never over what appkit writes: every answer to an appkit path is appkit's, and inside a page the appkit banner and the appkit footer are appkit's output, each launcher entry's icon the services file's SVG inserted verbatim. So each rule over a page's markup is read over its **written markup**, the page with its appkit banner and appkit footer taken out.

## The banner, the footer and the two failure shapes

Everything in this section is said about **an HTML document dummy sends**: every non-empty `text/html; charset=utf-8` body `Handler` sends except the ones answering `/widgets/table` (whose fragment `D06-table` forbids a doctype, an `html` element and a `body`), `/mcp` (whose answers are the MCP server's), or an appkit path.

Every HTML document dummy sends is **drawn with the banner**: right after the body's start tag it holds the **appkit banner** for the request — exactly what appkit's `banner` template writes for the banner data the banner source returned while that request was answered — and **drawn with the footer**: its last thing before the body's end tag is the **appkit footer**, what appkit's `footer` template writes for the same data. `Handler` calls the banner source once per page, with the **banner user** for the request — the email `X-User-Email` carried and the two URLs `ProfileURL` and `LogoutURL` derive from its `Host` and `X-Forwarded-Proto` — afresh for every page, so when the kit's services file changes the next page shows it; and never for an answer that draws no banner — the missing-identity 500, the fragment, `/mcp`, the shared files — so those never cause a read of the services file.

What appkit draws is appkit's, and dummy depends only on what appkit promises of it: that `page.Templates()` defines `banner` and `footer` and renders them, invoked from a template dummy parses into the set, as appkit's D03 describes for the `page.Banner` they are handed, and that the kit's `Banner` fills that value as appkit's D02 describes. Those promises are where the story's banner comes from — the mark naming the service, the profile link labelled `Profile`, titled with the email and leading to the profile URL, the sign-out form POSTing to the logout URL around a button reading `Sign out`, and, when the `Banner` lists services, the launcher button, the list of services and the launcher's script — and dummy restates none of them, nor anything appkit does not promise about how its markup is written: where its elements sit, what else they carry, or how their attributes are quoted. dummy's part, which its tests prove, is the data and the place: every page is drawn with exactly the text appkit's two templates write for the `page.Banner` the banner source returned for the banner user of that request, at the top and the bottom of the body. Which services the kit lists — only entries with an icon, in the file's order, dummy's own marked current — is the kit's behavior (appkit's D02), proved by the wiring and not by dummy's handler tests.

dummy's tests cannot build the kit inside a handler test without setting the environment, so they draw the banner through an **echoing banner source**: a function returning the banner user's three values with `ServiceName` and a list of services the test chose, and they compare each page against the text appkit's templates write for that value. The one exec'ing test compares the running binary's page against a kit it makes itself over the same services file (`D01-layout-and-run-seam`).

The written markup's body holds exactly one thing, one `main` element, and everything that is the page's own is inside it; what lies between its start and end tags is the **page content**.

A failure dummy can name to an identified caller is itself a page with the banner, with a way back to the panel; only the missing-identity fault, where there is no identity to draw with, is bare text. So there are two failure shapes, defined here as shapes; which one a route uses is stated by whoever owns the route. The **plain failure shape** is a fixed `text/plain` body. The **banner failure shape** is the `page` template's failure state for a message constant: a page whose content says the message and links to `/widgets`. `D06-table`'s route is plain always, because the panel's script splices that response into a live document.

A **panel page** is a document shape a requirement assigns — the 200 on `GET /widgets` here, the 422 body in `D07-form` — never one a body has merely by looking like one; were it decided by appearance, the 404 page would qualify and be required to carry a table and a form. It is the `page` template's panel state, executed with **panel page data**.

## The head every page carries

Every HTML document dummy sends carries the same three things before its body: a `title` reading `ServiceName`, one stylesheet link to `/_appkit/theme.css`, the platform stylesheet appkit serves through dummy (`D08-assets`), and the phone-width viewport, `width=device-width, initial-scale=1`. The head is the `page` template's, not appkit's. The table fragment is spliced into a page that already has them, and the plain-text 500 has none: a request without identity is sent no stylesheet.

A page makes no request to any third party, and the part of that a page's own markup decides is closed here. The attributes a plain HTML element loads a resource from — `href` and `xlink:href` on anything but an `a`, `src`, `poster`, `data`, `background`, `manifest`, and every candidate of a `srcset` or `imagesrcset` — name a path on dummy's own host: `/` alone or `/` followed by anything but a second slash or a backslash, read after tabs and newlines are dropped, as a browser's URL parser reads them. Further routes are closed outright, because dummy's markup needs none of them: no `style` attribute, no `ping`, no event-handler attribute, no `srcdoc`, no `http-equiv`, no `math`, a `script` with no `src`, and an `svg` only as an icon outline hidden from assistive technology whose shapes name no resource. Each rule is read over the raw written markup, so nothing a fake `<script` could cut away hides from it. The launcher's script, which does carry a `src`, sits in the appkit banner. The inside of a script element is the author's obligation: the gates have no JavaScript engine.

## A caller's bytes never become markup

Three kinds of caller-supplied value reach a page: the email from `X-User-Email`; the profile link's `href` and the sign-out form's `action`, which derive from `Host` and `X-Forwarded-Proto`; and, on a 422, the name, the count and the status exactly as they were submitted. What is contract is the invariant, not the mechanism: no value a caller sends may contribute a tag, so a document's tag structure does not depend on anything a caller sends. `html/template`'s autoescaping is how both dummy's templates and appkit's get there. Inside the banner and the footer that is appkit's promise (its D03 escapes every string field it emits), so dummy's requirement is stated over its written markup, where it is dummy's own. It is decidable with the standard library: submit a value full of markup and an innocuous value that fails validation the same way, with the widget set held fixed, and compare the two pages' written markup by tag-name sequence and count of `>`.

## The panel page

The panel page's content is, in order, the `h1` reading `Widgets`, the **subtitle hook** — the element whose `id` is `panel-subtitle` — and the **panel wrapper**, a `div` of class `panel` holding the widgets table (`D06-table`) and then the form card (`D07-form`). The stylesheet lays the wrapper's two children side by side on a wide screen and stacks them on a narrow one; which happens at 960 pixels is a fact about a layout engine the gates do not have, so the contract is the hooks the stylesheet reads and the document order, table first. The subtitle counts the widgets and says how often the table refreshes — `3 widgets · refreshes every 5 seconds`, `1 widget · …` for exactly one — and the count is the number of rows the page's own table shows, so the two never disagree on a page. It is drawn when the page is rendered and sits outside the table, so a poll never changes it; it catches up on the next load. Because it is stated over every panel page, the 422 redraw carries it too.

The panel keeps itself fresh with the `script` template's inline script, which re-fetches the table fragment every 5 seconds and swaps it into the page. It sits outside the table — inside, the first swap would delete it — and carries no `src`. Its requirement is deliberately weaker than its behavior: "re-fetches and swaps" cannot be decided without a JavaScript engine, so what is fixed is what a standard-library test can see — exactly one script element in dummy's written markup, no `src`, and a source carrying the literals `/widgets/table`, `widgets-table` and `5000`.

## Routing

Identity first, then path, then method. Path matching is exact on the URL's path component and nothing else; `/widgets/`, `/widgets/table/` and `/mcp/` are unknown paths and take the 404, and dummy never answers a trailing-slash variant with a redirect, which Go's `http.ServeMux` would otherwise supply.

The table is total. `/` answers `GET` and `HEAD` with a 303 to `/widgets` and every other method with a 405 naming `GET, HEAD`. `/widgets` answers `GET` and `HEAD` with the panel page, `POST` as `D07-form` defines, and every other method with a 405 naming `GET, HEAD, POST`. `/widgets/table` is answered as `D06-table` defines. An appkit path is answered by appkit as `D08-assets` says. `/mcp`, exactly that path, is answered by the MCP server, whatever the method — its 405 for a `GET`, with `Allow: POST`, is appkit's and never one of dummy's pages. Every other path is a 404 with the banner, whatever the method — `/mcp/` and everything beneath it, `/assets/` and everything beneath it included.

A `HEAD` with identity is answered exactly as the corresponding `GET` would be — same status, same headers, empty body — on every route dummy answers itself. `/mcp`'s answers are the MCP server's, and an appkit path's are appkit's, whose `HEAD` promises are narrower and are stated in `D08-assets`; the missing-identity 500 is the gate's, whose `HEAD` is promised only its status, its `Content-Type` and an empty body. Reading never mutates: every read route's postcondition in the stories asserts it.

## The MCP endpoint

`Handler` is built over an MCP server `main` made with `mcp.NewServer` (`D01-layout-and-run-seam`), one no tool was registered on and that has not served. Before it returns, `Handler` registers dummy's tools on it by calling `tools.Register(srv, s, w)` (`D09-mcp`), so the tools act on the same store the panel shows, and mounts it at exactly `/mcp`, inside the identity gate. A request with identity to `/mcp` gets exactly what the server gives it, with the caller the gate put in the request's context; a request without identity gets the gate's 500 and never reaches the server. What the server answers — the protocol, its versions, its statuses, the instructions — is appkit's (its D07) and the tools are `D09-mcp`'s.

## What the handler does not depend on

The handler's responses do not depend on the process's working directory or on any file outside the binary — dummy's templates are embedded, and appkit embeds its own and the shared files. The files a response does depend on are the host's services file, which the banner source and the MCP server read, never the handler itself. So the rule is stated for a banner source that reads no file and an MCP server made with no services file, and tested by driving two handlers with the working directory set to an empty temporary directory and to the checkout.
