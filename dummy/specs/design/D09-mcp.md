# D09-mcp

dummy's two MCP tools: `list_widgets`, which lists the widgets a page at a time, and `create_widget`, which creates one under the same rules as the form. This document is the whole of `internal/tools`, a package that exports one function, `Register`, and the observable contract of the two tools it registers: what a client sees of them in `tools/list`, what a `tools/call` of each answers and does to the widgets, and what each records in dummy's telemetry trail. The tools page (`D04-panel`) lists the same tools, with their names and descriptions, from the server they are registered on.

Everything around the tools is appkit's or another document's, and this one restates none of it. appkit's `mcp` package (its designs D07–D10) is the transport and the protocol: the methods `/mcp` answers, both protocol families and their envelopes, the 405 for a method other than POST, the `Origin`, `Content-Type` and size checks, the unknown-tool protocol error (appkit D07-mcp-server, Methods), the schema derivation from Go types (appkit D09), the strict argument decoding and its error text (appkit D08-mcp-tools, Calling a tool), and the success result built from a handler's output (appkit D08-mcp-tools, Calling a tool). dummy's tests never re-prove any of that. The server itself is built in `main`, with the name `dummy` (`panel.ServiceName`), the version the display string `main` reads (`D01-layout-and-run-seam`), dummy's telemetry writer, and no `Instructions` function, so the instructions a client is given are dummy's description read afresh from the services file by appkit's default (appkit D07-mcp-server, Instructions); that wiring is `D01-layout-and-run-seam`'s. Mounting the server at `/mcp`, wrapping it with the rest of the panel in `identity.Require` and the telemetry middleware, and calling `Register` on it with the panel's own store and telemetry writer are `D04-panel`'s, which is why a request to `/mcp` without `X-User-Id` gets the same 500 every route gives. The widgets, their rules and their messages are `D05-widgets`'s.

Each tool is registered with `mcp.AddTool`, so its schemas are derived from Go types `internal/tools` keeps unexported, and those types are not contract; the schemas they produce are, and they are stated here whole. Both tools work on the store `Register` was given and on nothing else, which is the store the panel shows, so the panel and the tools are two ways into one set of widgets: what one creates the other shows at once.

`list_widgets` is read-only, and it pages, as the suite's listing rule asks (`shape/`, Listing), on the contract of appkit's `paging` package (appkit's D25), which this document cites and never restates. dummy is the precedent app `shape/` names for that rule, so the shape here is the one the next app copies, and dummy requires an appkit release that provides `paging`. The tool's input struct declares two optional members, `Page *string` named `page` and `Limit *int` named `limit`: pointers, because appkit's schema derivation forbids `json` tag options and a pointer is how a member is made optional (appkit D09). Each carries a `description` tag repeating `paging.PageDescription` or `paging.LimitDescription` word for word, since a struct tag is a literal, and a test compares the description `tools/list` shows with the constant; any other argument is still appkit's unknown-field offence. Its answer is an object rather than a bare array, because an output schema must be an object: `widgets`, then `next`, `Next *string` with a tag repeating `paging.NextDescription`, written exactly when at least one widget follows the page and left out otherwise.

The order is the store's, oldest first (`D05-widgets`), and the token is `paging.Token{Tool: "list_widgets"}` over exactly one `int64`, the `Seq` of the last widget the page answered, so the following page is the widgets whose `Seq` is greater. The tool reads one window from the store: it asks `List` for one more widget than the page size, answers the page, and sets `next` only when the extra widget came back, so neither `next` on a last page that happens to be full nor a widget repeated or skipped at a page's edge is possible. Serving each call from one `List` window of at most the page size plus one row, so that dummy never holds more than one page plus one row, is the storage convention of `shape/` (Storage), which dummy follows; no test can observe how many rows a call held, so it carries no requirement, and the requirements state only what the answer holds. A null `limit` is an absent one, and a null `page` is an absent one, the first page. An absent, null or empty `page` asks for the first page, and `next` handed back as `page` unchanged asks for the following one; the widgets and the `next` `list_widgets` answers for a `page` and no `limit` are exactly the window and the next token the panel page shows for that same `page` as its query parameter, the first page when it has none (`D04-panel`). The widget object is unchanged: a widget's `Seq` is the store's position and the token's content, never a member of the answer, so a model sees only the opaque token.

A call is refused, before the store is read, in two cases. A `limit` outside 1 to `paging.MaxLimit` is refused with the text of the error `paging.Window` returns for it. A `page` that is not empty and that the token's `Decode` refuses — one another tool issued, a mistyped one, one made by hand — is refused with `paging.BadPage`. When both offend, the `limit` is the one reported, because the page size is read first. A refusal is shaped as every tool error dummy returns: an `isError` result whose one text block is the sentence and nothing else, with no `structuredContent`. Because the store is not read, the answer is the same while the store is unreachable: the refusal, not `widget.Unreachable`, which would tell a model to try again when its arguments can never succeed. A `limit` too large for a Go `int` never reaches the tool; appkit refuses it as an integer-range offence (appkit D09).

`create_widget` takes three required arguments. The name is a string, passed to the store untrimmed; trimming is the store's (`D05-widgets`), as it is for the form. The count is a Go `int`, whose schema is a plain `integer` with no minimum, so a negative count passes decoding and is refused by dummy's rule, alongside any name offence, with the form's own message; and since dummy is built for 64-bit Linux, a count outside 64-bit range is appkit's range offence with 64-bit bounds. The status is `widget.Status`, whose `Enum` method makes its schema an `enum` of the three words, so a status outside them is refused by appkit's decoder before dummy's rules run and dummy's rules never see a bad status. The handler hands the three values to `widget.Store.Create` as a `widget.Draft`, so acceptance and creation are one step against every other creation, through the form or the tool.

There are therefore two layers of refusal, and a call sees only one of them. If decoding finds any offence, appkit answers with its own argument error text and the handler never runs, so nothing is created and dummy's rules are not consulted. Otherwise the store decides, and every rule offence is reported at once in the same shape appkit uses: the line `invalid arguments:` and one `<field>: <message>` line per offending field, name before count, with the message the form shows beside that field.

The store keeps the widgets in dummy's database, and it can fail. While it cannot reach the widgets (`D04-panel` defines the store being unreachable), neither tool has anything true to say: `list_widgets`, for arguments it does not refuse, does not answer an empty list, which would tell the model the widgets were gone, and `create_widget`, for arguments that pass appkit's decoding, stores nothing. Each refuses with an `isError` result whose one text block is exactly the constant `widget.Unreachable` (`D05-widgets`), with no newline and no `structuredContent`, quoting nothing of the database's own error, so a model can tell it from a refusal of its arguments. appkit records the call's `tool.called` with the outcome `error`, as it does for any tool's own failure, and dummy records no `widget.created`. A test provokes it as the panel's do: a store over a database in its own temporary directory, opened with appkit's `db.Open` and `dummy.Migrations()`, with `SetFailing(true)` on that handle.

Each tool call is recorded in dummy's trail. appkit's server records `tool.called` for every call that reaches a tool (appkit D08-mcp-tools), with the tool's name, its kind, the outcome and the handler's duration, so dummy states nothing about that event. What dummy adds is its one domain event: a `create_widget` call that creates a widget records `widget.created` through the writer `Register` was given, with one attribute, `widget`, the new widget's id, and nothing else — never the name, count or status. It is recorded while the handler runs, so it falls before the call's `tool.called`, and it carries the request's id and the caller's user id because it is emitted with the request's context. A refused call, and every `list_widgets` call, record nothing of dummy's own. A paged call is a tool call like any other: `tool.called` carries no arguments, so a page token appears in no event and no log line, and paging adds nothing to the trail. `Register` takes the writer rather than reaching for the server's because appkit's server exposes none; the two are the same writer in every use (`D01-layout-and-run-seam`, `D04-panel`).

A widget's id is shown in both tools' results, first among its members, so that a model that knows a widget by its name can find it in the trail; no tool takes one. The input schema of `create_widget` therefore stays the three-property widget schema, while both output schemas describe the four-property **widget output schema**, whose `id` property carries a description of its own.

Decisions recorded here: every member of both output schemas but `next` is marked required, since a non-pointer field is always written (appkit D09-mcp-schema, Writing Out) and a client may rely on it, while `next` is a pointer, left out when no widget follows; the output `widgets` property carries a description of its own; the output widget's properties carry the same descriptions as the input properties of the same names. Every description, a tool's included, is copy: the requirements say each exists and is not empty, and the words live in the source alone.
