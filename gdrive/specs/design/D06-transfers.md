# D06-transfers

The engine: `internal/transfers`, the one place a transfer is validated, recorded, queued, started, streamed, finished, settled at start, abandoned at the stop and pruned; and `internal/urls`, the three addresses the engine and the pages build from the services file and the request. A `pull` or a `push` (`D09-tools`) hands the engine the caller and the arguments; the engine asks connections for the caller's Google token, checks everything it can check before anything is written, records the transfer `running` or `queued` (`D04-store`), answers it at once, and moves the bytes in the background as the caller: Drive to artifacts for a pull, artifacts to Drive for a push. It is scripts' run core in shape (a record made at once and observed later, a bounded queue shared by every user, a start that settles what a dead process left, a drain, a prune) with connections' refusal-with-URL in front of it and appkit's two sibling clients and gdrive's Drive client (`D05-drive`) under it.

`D01-layout-and-run-seam` declares the run seam, the settings and the default Drive client; `D04-store` the record, its words and its transitions; `D05-drive` the Drive client, the file object, the kinds, the export table and its errors; `D08-trail` the two events and the trail's secrecy; `D09-tools` the tools and the words a refusal is shown with; `D03-serve` builds the engine and calls its `Recover`, `Prune` and `Drain`.

## The addresses

`internal/urls` holds three addresses, declared here because the engine is the first to need one. The **connect page** is where a person connects their Google account: the `URL` of the services file's entry `connections`, every trailing `/` removed (`urls.Base`), followed by `/google/connect` (`urls.Connect`), and so relative, `/google/connect`, when the file has no such entry, as connections' own `connect` tool answers it. An artifact's **page** on artifacts is the `URL` of the entry `artifacts`, trailing `/` removed, followed by `/` and the artifact's id (`urls.ArtifactPage`), and empty when either is empty: only a pull's `Put` answers an id (`D04-store`), and with no entry there is no artifacts host to point at, since a relative `/<id>` would name a page of gdrive's own. The **auth address**, whose `/` and `/logout` are the banner's profile and sign-out links, is the `URL` of the entry `auth`, trailing `/` removed, or, when the file has no such entry, the scheme the request came with (`X-Forwarded-Proto`, `https` unless it says `http`), `://auth.`, and the request's host with its port and a leading `gdrive.` removed (`urls.Auth`), as connections builds its own. The pages (`D07-pages`) build the artifact page and the auth address; the engine is built with the connect page.

## Asking for the token

Every tool but `transfers` and `transfer` begins by asking connections, over its socket and as the caller, for the caller's Google token (`Token`): connections answers the access token, or refuses. `not_connected` becomes the engine's refusal `not_connected` carrying the connect page; `reconnect` becomes `reconnect` carrying the address connections named; `unknown_provider`, which cannot happen, and `provider` become `provider` (decision 7); and connections answering `unavailable` or an answer the client does not expect or cannot read, or not answering at all, becomes `unavailable` (orchestrator P3); so does a missing `connections` entry, for which the engine holds no client and sends nothing. The read tools then call Drive with the token; `Pull` and `Push` go on checking.

## Refusals

A refusal is a `*transfers.Refusal`: a word, one of the thirteen `Refusal*` constants, and, for `not_connected` and `reconnect`, the URL the person opens. The engine never words a refusal; `D09-tools` turns a word into the text an agent reads. A call refused records nothing, emits nothing and touches no artifact. The words are decision 5's and the orchestrator's (ORCH D11, P1, P3): `not_connected`, `reconnect`, `not_a_file`, `not_exportable`, `format`, `expires`, `too_large`, `not_found`, `provider`, `path`, `unavailable`, `stopping` and `queue_full`. gdrive's own database failing as the transfer is recorded is not a refusal: the call answers an error matching `store.ErrUnreachable`, which `D09-tools` shows with the word `unavailable` (orchestrator P2); `Token`, `Pull` and `Push` answer no other kind of error.

## Pull

`Pull` checks, in order, and refuses at the first that fails:

1. the token, as above;
2. `expires`, when given: it must parse as RFC 3339 and, truncated to the second, be later than the engine's clock truncated to the second, as artifacts' `import` judges it (ORCH D10/D13); otherwise `expires`;
3. the path: artifacts' `Head` of `path`, as the caller; a path artifacts refuses (`ErrBadPath`) is `path` (orchestrator P1: gdrive restates no path rule of its own), any other failure but not found is `unavailable`, and an artifact already there, or none, passes;
4. the file: Drive's `Show` of `file`; not found (a trashed file included) is `not_found`, and Drive refusing (403) or failing is `provider` (root R6);
5. a shortcut is followed one hop: `Show` of its target, judged as the file was; the transfer then names the target;
6. the kind: a folder, a shortcut whose target is a folder or another shortcut, or a shortcut Drive answers with no target, is `not_a_file`; `other` is `not_exportable`;
7. the format: a `format` given for a file with bytes, or one `drive.Formats` does not list for a Google-native kind, is `format`; with none given a Google-native file is exported to `drive.DefaultFormat` of its kind;
8. the size: a file whose size Drive reports above `TRANSFER_MAX_BYTES` is `too_large` (a Google-native file has no size and is not checked);
9. the drain: once `Drain` has been called, `stopping`;
10. the queue: with `TRANSFER_MAX_QUEUED` transfers already waiting, `queue_full`.

There is no up-front `forbidden`: artifacts' reads are open to every signed-in user and its `HEAD` carries no owner, so gdrive cannot learn who owns `path` before it writes (orchestrator decision D2/D12). A `Put` artifacts refuses with 403 fails the transfer with reason `forbidden` instead.

The transfer recorded names the file (the target's id, name and kind for a followed shortcut), the path, the content type the bytes move as (the file's MIME type, or the export format), and the export format for a Google-native file.

## Push

`Push` checks, in order: the token; artifacts' `Head` of `path`, as the caller: a path artifacts refuses is `path`, an artifact that does not exist is `not_found`, any other failure is `unavailable` (orchestrator P1, P3), and one whose size is above `TRANSFER_MAX_BYTES` is `too_large`; then, with `file` given, Drive's `Show` of it: not found is `not_found`, refused or failed is `provider`, and a kind other than `file` is `not_a_file`; or, with no `file` and a `folder` given, `Show` of the folder, judged the same way, a kind other than `folder` being `not_a_file` (a shared drive's id shows as a folder); with neither, the file goes to My Drive's root and nothing is shown. With `file` given, `folder` is ignored and never named to Drive. Then the drain and the queue, as for a pull. A push never searches Drive for a name (decision 5).

The transfer recorded has kind `file`, the path, the artifact's content type as `Head` answered it, no format, and a name: for a push that creates, `name`, or the path's last segment when `name` is empty or absent; for a push that replaces, `name`, or, with none, the name Drive's `Show` of `file` answered. A given `name` renames the file a push replaces, and an absent one keeps Drive's current name (orchestrator P4); when the upload lands, the record takes the name Drive answers. A push that creates learns the Drive id only when its upload lands, so its record's `file` is empty until it is done.

## The queue

`TRANSFER_MAX_ACTIVE` transfers run at once, across every user; a transfer **holds a slot** from the moment it is recorded or started `running` until its `transfer.finished` is emitted. A transfer recorded while every slot is held, or while another is waiting, is recorded `queued` and waits in one queue, first in, first out, shared by every user. When a slot is released, the transfer queued longest is started (`store.Start`), then its `transfer.started` is emitted, after the `transfer.finished` of the transfer whose slot was released. The queue-full check counts the waiting transfers once, at the call. The queue lives in the engine's memory; the store keeps only each transfer's status (`D04-store`).

## The work

A transfer's work runs in the background, as the caller: under a context carrying the `identity.Caller` rebuilt from the record's user id, email and request id (`identity.NewContext`), and the event cause the call's context carried, so every request it sends to connections and artifacts carries the caller's identity headers and every event it records and emits names the caller, long after the call has been answered. It is cancelled by the drain, and by nothing else: a transfer outlives the request that asked for it.

The work asks connections for a fresh token first, since a transfer may wait in the queue longer than the token the call used lives. A pull then opens Drive's stream, `alt=media` for a file with bytes or `export` to the format for a Google-native file, and hands it to one artifacts `Put` of the path with the content type and the expiry; the bytes are never held. A push opens artifacts' `Get` of the path and hands the body to Drive's `Upload` (`D05-drive`) with the artifact's size and content type, creating the file under `folder` with the name, or updating `file` in place, renamed to `name` when one was given. Bytes moved are counted as the destination reads them, and the record's `bytes` follows the count at every whole multiple of `ProgressStep`, so a page or `transfer` shows a long transfer moving; the final count is written when it ends.

A transfer ends exactly once: `done`, carrying the artifact's `url`, the Drive file's `link`, the artifact's id for a pull, and for a push the Drive id of a file it created and the name Drive answered; or `failed`, with a reason (root R10):

- the token for the work: `reconnect` when connections answers `reconnect` or `not_connected` (the person disconnected after the call, the closest of decision 8's reasons), `provider` for any other refusal or failure;
- Drive, while reading or writing: not found is `not_found`; the export cap is `too_large`, whether Drive refuses the export or breaks its stream past `drive.ExportCap`, and even when artifacts' `Put` reports that broken read as its own failure; a refusal of a write (an upload's 403) is `forbidden`; a refusal of a read and any other failure, a stream that breaks mid-body included, is `provider`;
- artifacts: a `Put` refused with 403 is `forbidden`, with 413 `too_large`; a push's `Get` of an artifact gone is `not_found`; any other `Put`, `Get` or body failure, artifacts unreachable or an answer the client cannot read, is `artifacts`;
- the drain, and the start after a dead process: `interrupted`.

## Starting, stopping and pruning

`Recover` runs at start, before ready (`D03-serve`): every transfer still `queued` or `running` was cut off by a process that died; each is finished `failed` with `interrupted`, its bytes as they were, and its `transfer.finished` emitted as its caller.

`Drain` is the stop. From its call `Pull` and `Push` refuse with `stopping`; every queued transfer is finished `failed` with `interrupted` at once, its `transfer.finished` emitted and no `transfer.started` ever; no released slot starts anything. Running transfers go on while `Drain`'s context lives, so a small one finishes; when that context ends, at the drain deadline `D03-serve` gives it (`DRAIN_SECONDS`), the work of every running transfer is cancelled, its exchange with connections, Drive or artifacts ended, and it is finished `failed` with `interrupted` and the bytes it had moved. An artifacts `Put` cut off leaves nothing, by artifacts' guarantee, and a resumable upload cut off before its last piece creates or changes nothing at Drive (decision 9, decision 11). `Drain` returns once no transfer of the engine is queued or running.

`Prune` removes every transfer past keeping at the engine's clock, as `store.Prune` decides with `TRANSFER_KEEP_DAYS` and `TRANSFER_KEEP_COUNT` (decision 12); it records no event, and the artifact or Drive file a pruned transfer made is untouched. `D03-serve` calls it once before ready and on every sweep.

## Recorded decisions

- **No up-front `forbidden` on pull** (orchestrator D2/D12, overriding decision 5's "forbidden, learned by Head" and the Verification bullet that expects it): artifacts' `HEAD` names no owner and every signed-in user may read every artifact, so the only owner check is artifacts' own on the `Put`, and a pull to another user's path is recorded and then fails with `forbidden`. The decisions document's Verification step "refused `forbidden` before any record" no longer holds.
- **Refusals carry a word, not a sentence.** The engine answers `*Refusal` with one of thirteen words and, for the two connection refusals, the URL; the sentences are `D09-tools`' copy constants (ORCH D11). The URL travels in the refusal's text, not a separate member, departing from decision 7's "refuses with `not_connected` and `url`" by the orchestrator's decision.
- **The token lookup is the engine's**, exported as `Token`, so the read tools and the two transfer tools refuse a missing or broken connection with one mapping, and a `pull` or `push` fetches the call's token once, in the engine. A missing `connections` entry leaves `Config.Connections` nil (root R1, looked up with `List.Find` and never built over a zero entry), refused `unavailable` with no request, like connections' own `unavailable`, an unexpected status and an unreadable answer (orchestrator P3); connections' `provider` stays `provider`. A missing `artifacts` entry leaves `Config.Artifacts` nil, and a `pull` or `push` is refused `unavailable` where its `Head` would be sent. The clients are fixed at start, so no entry goes missing between a call and its work.
- **Check order.** The token first (decision 5 lists it first, and it is what every tool needs); then what needs no call (`expires`); then artifacts' `Head` of the path, so a pull to a path artifacts would refuse asks Drive nothing; then Drive; then the size; then the drain and the queue, last, in scripts' order (the drain after the lookup, the queue counted once just before recording). A draining process therefore still asks connections and Drive before refusing `stopping`; the drain is short and nothing is written.
- **A Drive 403 seen before recording is `provider`** (root R6), since only a write can be refused for permission and nothing is written before the record; seen while writing, it is `forbidden`. Rate-limit 403s are not told apart in this pass (root R8).
- **Shortcuts.** One hop: a shortcut to a shortcut is `not_a_file`, as a shortcut to a folder is, rather than a chain followed; so is a shortcut Drive answers without `shortcutDetails`, since there is nothing to follow. The record names the target, so its kind is the target's (root R4) and `shortcut` never reaches a record; a push's kind is `file`.
- **The size is checked only where it is known**: a file's reported size at the call, and the artifact's `Head` size for a push. An export has no size until Drive renders it; Drive's own cap (`too_large`) and artifacts' cap (413, `too_large`) bound it. The engine does not count a stream against `TRANSFER_MAX_BYTES` mid-flight.
- **A fresh token for the work.** The call's token is used for the call's checks; the work asks again, because a queued transfer may start minutes later, and a `reconnect` or `not_connected` then fails it `reconnect` (decision 7; root R10 for `not_connected`).
- **The started time is the record's** (root R3): `started` is when the call recorded the transfer, and `transfer.started` is emitted when the work begins, at once for a transfer recorded `running` and later for one that waited.
- **Drain lets running transfers run until the deadline**, then cancels them, as scripts' drain lets runs run and kills them at its deadline; decision 11's "abandoned the same way inside `DRAIN_SECONDS`" is read as within the drain window. Queued transfers are abandoned at once with `interrupted` (scripts' `queue_abandoned`; gdrive has one word for both, decision 11).
- **Progress is written at whole multiples of `ProgressStep`, 1 MiB**, so a 1 GiB transfer writes its record about a thousand times, not once per read; the count is the bytes the destination has read from the source.
- **The event cause travels in memory.** The work's events carry the cause and depth of the call that recorded the transfer, so a script that pulls on `transfer.finished` cannot loop without the bus seeing the depth grow; the store does not keep the cause, so a transfer settled at start carries none.
- **An ending the store cannot record emits no event** and releases the slot: the record stays `running` or `queued` until the next start settles it `interrupted`. A `store.Start` that fails as a queued transfer leaves the queue is treated alike, as scripts treats a failed `StartRun`: no event, the record left `queued` for the next start, and the slot handed to the next transfer, so the drain never waits on it. A `store.SetBytes` that fails is ignored: progress is a view, and `Finish` writes the final count.
- **Streams, not buffers.** A pull's `Put` receives Drive's bytes as they arrive and a push's pieces go out as artifacts' body yields them, so no transfer holds more than one piece in memory; every stream the work opens is closed when the work ends, so an early failure never leaves a sibling or Drive writing to nobody. A failure before the bytes move (the work's token, Drive refusing the read, artifacts refusing the `Get`) sends no `Put` and no upload, so a failed pull never overwrites the artifact and such a failed push changes nothing at Drive.
- **The queue's bound holds under concurrency**: the count and the recording are one step, so racing calls never queue more than `TRANSFER_MAX_QUEUED`.
- **`Prune` touches the database alone**: it sends nothing to Drive, artifacts or connections, and the artifact or Drive file a pruned transfer made is untouched.
- **Deferred** (decisions document): a short wait inside `pull` and `push` so a small transfer answers `done` in one call; `cancel` of a running transfer; retries against Google; resuming an interrupted transfer; conversion to a Google-native format on push; pulling a folder as an archive; pulling an `other` kind. None is in this design: a transfer is answered at once, runs once, and ends `interrupted` when cut off.
- **Rejected** (decisions document): a synchronous transfer, with or without a raised gateway budget, since the suite models minutes-long work as a record; transfers held in memory, since `transfers` and the pages would be empty after every redeploy (`D04-store` keeps them); replacing a Drive file by a name match on push, since the agent names `file` when it means replace; refusing Google-native files, which are most of a workgroup's Drive.
- **The queue-full refusal is a word without a count**, departing from scripts' `QueueFull` format, which names `RUN_MAX_QUEUED`: an agent can do nothing with the operator's number, and the engine's refusal carries no text of its own.
- **Push names** (orchestrator P4). A push without `file` names the new file `name`, or the path's last segment (decision 5). A push with `file` renames the replaced file to `name` when one is given and keeps Drive's current name when none is; the record shows the name from the call (`name`, or the name `Show` answered) until the upload lands and then the name Drive answers, so `D04-store`'s `Ending` carries a `Name`.
- **The path is judged by artifacts** (orchestrator P1): `pull` and `push` alike send artifacts' `Head` of `path` as a check, and a `Head` answering `artifacts.ErrBadPath`, whether the client could not send the path or artifacts answered 400, is the refusal `path`. For a pull it comes right after `expires`, before any Drive call; for a push it is the same `Head` that learns the artifact's size.
- **Artifacts or connections unreachable at the call is `unavailable`** (orchestrator P3): a push's `Head` failing other than not found or a bad path, and connections failing other than with a word of its own. A pull's `Head` failing other than not found or a bad path is `unavailable` too: P3 names push's `Head`, the only one when it was asked, and a pull's is the same check of the same sibling, so it is answered alike rather than recorded to fail later as `artifacts`.
- **The database failing is the tools' `unavailable`** (orchestrator P2), not an engine refusal: the engine answers the store's error, as `D04-store` has every consumer do, and `D09-tools` gives it the word.
- **Work-time failures keep the store's seven reasons.** `unavailable` is a refusal word, not a reason: a token the work cannot fetch because connections is unreachable fails the transfer `provider` (root R10), as any other connections failure but `reconnect` does.

## Consumer tasks

`D03-serve` builds `eng := transfers.New(transfers.Config{Store: st, Drive: dc, Artifacts: ac, Connections: cc, Telemetry: w, Events: em, ConnectURL: urls.Connect(urls.Base(connectionsEntry.URL)), MaxBytes: s.TransferMaxBytes, MaxActive: s.TransferMaxActive, MaxQueued: s.TransferMaxQueued, KeepDays: s.TransferKeepDays, KeepCount: s.TransferKeepCount, Now: p.Now})`, calls `eng.Recover(bg)` and `eng.Prune(bg)` before ready, `eng.Prune(bg)` on every sweep, and `eng.Drain(drainCtx)` at the signal. The tools (`D09-tools`), `c` the call's caller: `tok, err := eng.Token(ctx, c)` before `drives`, `list`, `search` and `show`; `t, err := eng.Pull(ctx, c, transfers.PullRequest{File: f, Path: p, Format: format, Expires: expires})` and `eng.Push(ctx, c, transfers.PushRequest{Path: p, Folder: folder, Name: name, File: file})`, telling a refusal with `errors.As(err, &r)` for `var r *transfers.Refusal` and reading `r.Word` and `r.URL`, and any other error, which matches `store.ErrUnreachable`, as the database failing. The pages build `urls.ArtifactPage(urls.Base(artifactsEntry.URL), t.ArtifactID)` and `urls.Auth(r, servicesPath)`. A test builds a store over its own database, an `artifacts.Client` and a `connections.Client` over `services.Entry` values naming Unix sockets on which loopback fakes listen, a `drive.Client` whose `BaseURL` is an `httptest.Server` faking Drive, a writer and an emitter over captures, and an engine with small limits and a fixed clock; it calls `Pull` and `Push` with an `identity.Caller`, holds a fake's answer open to keep a transfer running, polls `store.Get`, calls `Drain` with a context it cancels, and compares the store, the fakes' requests and the captured events.
