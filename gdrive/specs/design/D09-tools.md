# D09-tools

The eight MCP tools agents reach Google Drive by through the MCP gateway: `internal/tools`. No tool accepts or answers a file's bytes, a token or a credential; that is the point of the connector (decision 5). An agent finds a file with `drives`, `list`, `search` and `show`, asks for a transfer with `pull` (Drive to artifact) or `push` (artifact to Drive), each of which records the transfer and answers it at once (`D06-transfers`), and reads the outcome with `transfer`, or every transfer of its own with `transfers`. The bytes move on the host; the artifact's `url` in a done transfer is where a shell fetches the result.

## The tools

- `drives` takes nothing and answers the shared drives the caller's account can see, each `id` and `name` (`D05-drive`'s drive object), under `drives`, listed whole.
- `list` takes optional `folder` (a folder's id, or a shared drive's id for its root; absent or empty is My Drive's root), optional `page` and optional `limit`, and answers one page of the folder's children as file objects, folders first then by name, at most `limit` of them, under `files`, with `next` when Drive says more remain.
- `search` takes `query`, words matched against name and content as Drive's own search matches them, optional `folder` to search within one folder, optional `drive` to search one shared drive, optional `page` and optional `limit`; it answers matching file objects under `files` and `next`. With neither `folder` nor `drive` it searches My Drive and every shared drive. Quotes and backslashes in `query` are escaped, never interpreted (`D05-drive`).
- `show` takes `file` and answers its file object, a shortcut's carrying `target`.
- `pull` takes `file`, `path`, optional `format` and optional `expires`, and answers the transfer it recorded.
- `push` takes `path`, optional `folder`, optional `name` and optional `file`, and answers the transfer it recorded.
- `transfers` takes optional `page` and optional `limit` and answers one page of the caller's transfers, newest first, under `transfers`, with `next` when more remain.
- `transfer` takes `transfer`, an id, and answers that transfer.

The file object is `D05-drive`'s `drive.File`, encoded as it is: `id`, `name`, `kind`, `mime_type`, `bytes` (absent for a Google-native file), `modified`, `folder` (absent at a root), `drive` (absent in My Drive), `link`, and `target` for a shortcut.

## Paging

Three tools list, and each list is handled as the suite's listing rule asks (`shape/`, Listing), on the contract of appkit's `paging` package (`appkit/paging`, appkit's D25), which this document cites and never restates; `dummy`'s `list_widgets` is the precedent. `limit` is `Limit *int` and `page` is `Page *string` on each tool's own argument type, each carrying a `description` tag that repeats `paging.LimitDescription` or `paging.PageDescription` word for word, and `limit` is read through `paging.Window`: absent or null is `paging.DefaultLimit`, and a value outside 1 to `paging.MaxLimit` is refused with the text of `Window`'s error.

- `list` and `search` are **provider-paged**, as `shape/` allows a provider-backed list to be: `page` and `next` are Drive's own page token, passed through opaque (ORCH D14), and an agent hands `next` back as `page`. The page size `Window` reads is sent as Drive's `pageSize` (`D05-drive`); Drive's cap is 1000, above `paging.MaxLimit`, so nothing is clamped further. `next` is present exactly when Drive answers a `nextPageToken`. Drive may answer fewer files than asked and still a token (`D05-drive`), so a short page with `next` is not the end. A bad `limit` is refused before any Drive request; the token is Drive's, so gdrive never judges `page`: a `page` Drive rejects is the Drive refusal it is today, `provider` (Drive answers 400, `D05-drive`), and `paging.BadPage` is not used by these two tools. Both are raw tools with no output schema (below), so `next`'s description has nowhere to appear; `FileList.Next` is a `*string`, absent when nil.
- `transfers` is paged from the store. Its order is the store's, newest first: descending `started`, then descending `id`, within the caller (`D04-store`). The token is `paging.Token{Tool: "transfers"}` over two string fields, the last answered transfer's `started` as the store keeps it, RFC 3339 in UTC to the second, and its `id`; the next page is the caller's transfers after that key, read by one `ListAfter` window of one more than the page size (`D04-store`). `next`, a `*string` whose tag repeats `paging.NextDescription`, is present exactly when at least one transfer follows the page. A `page` that `Decode` refuses (the landing page's own before-token and `last` among them, `D07-pages`), or whose fields are not a canonical RFC 3339 UTC second and a transfer id, is refused with `paging.BadPage`. Both refusals come before the store is read, so they are the same while the store is unreachable: a refusal of arguments that can never succeed, not `unavailable`.
- `drives` is not paged: Google's shared drives are bounded by the account, as configuration bounds a list, so it is listed whole, as `shape/` asks of such a list.

A token does not bind `folder`, `drive` or `query`; keeping them the same is the caller's part (appkit's D25). The trail is unchanged: a page is a tool call like any other, and no token appears in any event or log line.

## The transfer record

A transfer is answered as one JSON object, declared here once and shared by `pull`, `push`, `transfers` and `transfer` (decision 8): `id`, `direction`, `status`, `reason` (only when failed), `file`, `name`, `kind`, `path`, `content_type`, `format` (only when exported), `bytes` (moved so far, final when done), `started`, `finished` (only once ended), and, when done, `url` (the artifact's `/files/<path>` address, for both directions) and `link` (the Drive file's address, for both). Times are RFC 3339, UTC, to the second. The artifact's id, the caller and the request id stay in the record and out of the answer: the pages use the first (`D07-pages`), and the caller already knows the rest.

## For its caller alone

Every tool works for its caller, the `identity.Caller` appkit hands the handler (decision 5). The six Drive tools ask connections for the caller's own token (`D06-transfers`), so they see exactly the Drive the caller's account sees. `transfers` lists the caller's transfers only, and `transfer` treats an unknown id, a pruned one and another user's alike, refused `not_found` (root R5). `push` may name any artifact the caller can read, since artifacts' reads are open to every signed-in user (root R7).

## Refusals

A refusal is an MCP error result whose text is a word, a colon and a space, and a sentence: `<word>: <sentence>` (ORCH D11), except the two paging refusals, whose text is the shared sentence alone (Paging, above). The word is the engine's (`D06-transfers`), one of `not_connected`, `reconnect`, `not_a_file`, `not_exportable`, `format`, `expires`, `too_large`, `not_found`, `provider`, `path`, `unavailable`, `stopping` and `queue_full`, so an agent can switch on it, and every refusal but those two carries one; the sentence is one copy constant per word, `tools.Refuse*`, written for a model. For `not_connected` and `reconnect` the text ends with a space and the URL the person opens: the connect page for `not_connected`, connections' address for `reconnect`. The Drive tools refuse a Drive answer themselves: not found is `not_found`, and a refusal or failure is `provider` (root R6, R8). gdrive's own database failing is `unavailable` (orchestrator P2), for `pull` and `push`, whose engine answers the store's error, and for `transfers` and `transfer`, which read the store; connections or artifacts unreachable at the call is `unavailable` too, the engine's word (P3). Malformed arguments, a missing required one or one of the wrong type, are appkit's schema refusal, as in every app (root R11).

## Descriptions

Every tool's description is its own first line, an empty line, and `tools.TransferGuide`, one constant line shared by all eight: no tool carries bytes or a credential; `pull` and `push` record a transfer that moves them on the host, `transfer` shows its outcome, and the artifact's `url` is where a shell fetches the result (decision 5, ORCH D15). `tools.Catalog()` answers each tool's name and its first line, which the tools page shows (`D07-pages`, root R9).

## Recorded decisions

- **Provider-paged `list` and `search`** (`shape/`, Listing): Drive's token passes through `page` and `next` and `limit` maps onto `pageSize`, rather than a token of gdrive's own over a position, which gdrive could not resume from without re-reading Drive from the start.
- **The paging refusals carry no word**, departing from gdrive's `<word>: <sentence>` rule: the text is exactly `paging.BadPage` or the `Error()` of `paging.Window`'s error, as appkit's D25 and every paged tool in the suite answer them, so an agent that has paged one list recognises the refusal in this one.
- **`list` and `search` judge `limit` after the token and before Drive**: the token is asked first, as for every Drive tool (R-KPVQ-5UGU, R-KM81-0J8R hold unchanged), and a bad `limit` is then refused with no Drive request.
- **`transfers` checks the token's fields**: a token `Decode` accepts but whose `started` is not the canonical RFC 3339 UTC second or whose `id` `store.ValidID` refuses can only be made by hand, and is refused `paging.BadPage` rather than read.
- **Raw registration for the Drive tools.** `drives`, `list`, `search` and `show` answer `D05-drive`'s types as `encoding/json` encodes them, through appkit's `mcp.AddRawTool`, as artifacts' `import` is registered: appkit's typed `mcp.AddTool` refuses a field whose type implements `json.Marshaler` (a `time.Time`) and any tag holding a comma (`omitempty`), and the file object needs both. They therefore carry no output schema. `pull`, `push`, `transfers` and `transfer` answer `tools.Record`, whose fields appkit's encoder handles, through `mcp.AddTool`.
- **Effects.** The six that change nothing are `mcp.Read`. `pull` and `push` are `mcp.Destructive`: decision 5 calls them write-kind, and each can replace bytes in place, an existing artifact at `path` for a pull and an existing Drive file named by `file` for a push, which is what the destructive hint warns of; scripts' `run`, which only adds a record, is `mcp.Additive`.
- **Refusal text** is `<word>: <sentence>`, the sentence a named copy constant (ORCH D11), the URL appended after a space for the two connection refusals. This departs from decision 7's "refuses with `not_connected` and `url`" as a separate member, and from connections' and artifacts' refusals, whose whole text is copy: an agent needs a word it can match and a link it can hand on, and an MCP error result carries text only.
- **The queue-full sentence names no number**, departing from scripts' `QueueFull`, which names `RUN_MAX_QUEUED` (`D06-transfers`).
- **`Catalog` answers first lines** (root R9), departing from connections' and artifacts' `Catalog`, which answer whole descriptions beside a `FirstLine` helper: the tools page is the catalog's only reader and shows the first line, and `ListTools` proves the whole description.
- **An empty optional argument is an absent one**: `folder`, `drive`, `page`, `format`, `name` and `file` given as the empty string mean what their absence means, since none has an empty value of its own. `expires` is the exception, as artifacts' `import` takes it: given empty, it is refused `expires`.
- **An empty `query` searches everything** in the scope, as Drive's `trashed = false` alone does (`D05-drive`); a required string may be empty under appkit's schema, and refusing it would only make the agent use `list`, which walks one folder (root R11).
- **An empty id is not found.** `show` and `pull` with `file` given as the empty string are refused `not_found` with no Drive request, since no file has the empty id (`D05-drive`'s client answers it unasked; a `pull` still asks for the token and judges `expires` and `path` first, in the engine's order). `push`'s `file` and `folder` are optional, so given empty they are absent, as above.
- **One token per call.** The four read tools take the token through the engine's `Token`; `pull` and `push` hand the call to the engine, which fetches it once as its first check, so no transfer call asks connections twice.
- **`DriveList` and `FileList` encode an empty list as `[]`**, never `null`, through their own `MarshalJSON`, whatever slice Drive's reduction handed them.
- **One `not_found` for every id that is not the caller's** (root R5): an unknown id, a pruned one and another user's are refused alike, as the pages answer them alike with the not-found page (`D07-pages`), so no tool tells a caller that someone else's transfer exists.
- **`transfer` judges the id before the store**: a string `store.ValidID` refuses names no transfer and is refused `not_found` without a read, as scripts' `result` judges a run id.
- **`unavailable` for the database** (orchestrator P2): every gdrive refusal but the two paging refusals carries a word, so the database failing is the word `unavailable` and `tools.RefuseUnavailable`, the same word the engine uses for a sibling unreachable at the call (P3), since an agent can do the same with either: try again later. The engine itself answers the store's error, not a refusal (`D06-transfers`).
- **Deferred** (decisions document): a path form on `search`, resolved segment by segment. **Rejected**: naming the pair `import` and `export` (`import` is artifacts' plan the agent executes) or `download` and `upload` (read from the provider's side, and colliding with artifacts' upload); paths for Drive files, which Drive has no API for and whose names repeat, so `search` shows the matches instead.
- **The tools hold no token code of their own**: `Token` is the engine's (`D06-transfers`), so the read tools and the two transfer tools refuse a missing or broken connection alike, and `tools.Config` carries no connections client and no services path.

## Consumer tasks

`D03-serve`'s handler registers the tools on the server it mounts at `/mcp` with `tools.Register(srv, tools.Config{Transfers: eng, Drive: dc, Store: st})`. The tools page reads `tools.Catalog()` (`D07-pages`). A model, through the gateway, calls `list` with `{"folder":"0FoL…","limit":100}` and gets up to a hundred files and, while Drive has more, `next`, which it hands back with `{"folder":"0FoL…","limit":100,"page":<next>}` until `next` is absent; `{"limit":0}` is refused with the text of `paging.Window`'s error and reaches no Drive. It calls `transfers` with `{}` and gets the newest `paging.DefaultLimit` transfers and `next` when more remain, then `{"page":<next>}` for the following ones; a `page` it made up is refused with `paging.BadPage`, the same while the database is down. It calls `search` with `{"query":"Q3 report"}` and gets `{"files":[{"id":"1AbC…","name":"Q3 report","kind":"document",…}],"next":"…"}`; then `pull` with `{"file":"1AbC…","path":"finance/q3.docx"}` and gets `{"id":"xfr_…","direction":"pull","status":"running",…}`; then `transfer` with `{"transfer":"xfr_…"}` until `status` is `done` and `url` is there; or is refused `not_connected: <sentence> https://connections.<space>/google/connect` and hands the link to the person. A test builds a store, an engine and a Drive client over fakes (`D06-transfers`), an `mcp.Server` with a capturing writer, registers the tools, serves the server inside `identity.Require`, calls `mcp.Client.CallTool` with the argument types encoded as JSON, decodes a success result's structured content into `drive.File`, `tools.FileList`, `tools.DriveList`, `tools.Record` or `tools.TransferList`, builds a `transfers` token with `paging.Token{Tool: "transfers"}.Encode`, compares a paging refusal's text with `paging.BadPage` or the `Error()` of `paging.Window`'s error, and compares any other refusal's text with the word, `": "`, the `tools.Refuse*` constant and, for the two connection refusals, `" "` and the URL.
