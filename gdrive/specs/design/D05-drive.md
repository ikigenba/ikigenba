# D05-drive

The Drive client: `internal/drive`, the one place in gdrive that speaks Google Drive's REST v3 API and the one place that reads Drive JSON. It is written over the standard library alone, and it makes exactly the calls the decisions document's decision 3 names: `files.list`, `files.get` as metadata and as `alt=media`, `files.export`, `drives.list`, and the resumable upload session, created for a new file or opened as an update of an existing one. Every answer Google gives is reduced at the edge to the connector's own types, the file object, the drive object and a page of files, so the engine (`D06-transfers`), the tools (`D09-tools`) and the pages never see a Drive field name.

## The client

A `Client` is built once per process from a `Config`: the `*http.Client` every request is sent through (`cli.Process.HTTP`, `D01-layout-and-run-seam`, which owns the default client and its timeouts), the base URL, empty meaning Google's `https://www.googleapis.com`, and the telemetry writer `drive.called` is recorded through. A nil `HTTP` means `http.DefaultClient`, a gloss no offline test observes. The process leaves the base URL empty, and its tests answer Drive through `HTTP`'s transport; this package's own tests may point the base URL at a loopback fake instead. Both the metadata paths (`/drive/v3/...`) and the upload paths (`/upload/drive/v3/...`) hang off the one base URL, as they do at Google.

A `Client` serves every user: the caller's access token is an argument of every call, a string the caller has just obtained from `appkit/connections`' `Token`. Each call but `Upload` is one short exchange, or a few (`Drives` follows pages; `List`, `Search`, `Show` and `Upload` first ask for the caller's My Drive root id), so a token taken just before the call is good for all of it; a stream from `Media` or `Export` is authorized when it starts and is not cut off by the token's expiry. The upload is the one long exchange, but only the requests before the pieces carry the token: the session URI Drive answers is itself the credential for the pieces, which are sent without `Authorization` (observed), so a token that expires mid-upload does not cut it short.

Every request the client sends to Drive with the token carries `supportsAllDrives=true`, and every `files.list` also carries `includeItemsFromAllDrives=true`; without them a shared drive's file is not found at all (observed: `files.get` of a file in "Shared" without the parameter answered 404). Every call that answers files names the fields it wants: unasked, Drive answers only a file's `kind`, `id`, `name` and `mimeType` (observed), with no size, parents, time, link or trashed flag.

## The file object

A `File` is decision 4's object: `id`, `name`, `kind`, `mime_type`, `bytes` (absent for a Google-native file, which has no bytes), `modified`, `folder` (the parent's id, absent at a root), `drive` (the shared drive's id, absent in My Drive) and `link` (Drive's `webViewLink`). A shortcut's object also carries `target`, the target's id and kind, which `Show` fills from Drive's `shortcutDetails`: its `targetId` and the kind of its `targetMimeType` (observed). A shortcut in a list or search page carries no `target`; decision 4 asks it of `show` alone. A Google-native file has no bytes, though Drive now answers a `size` for one (observed: an empty Doc answered `1`, then `1024`); the reduction drops it, so `bytes` is present only for kind `file`. The JSON encoding of a `File` is the object the tools answer, so the tools encode it as it is.

"At a root" means the file has no parent, or its parent is the shared drive it lives in (a shared drive's root folder has the drive's own id, observed), or its parent is the caller's My Drive root, whose id Drive answers for `files.get` of the alias `root` (observed, `files-get-root`: the one JPEG in My Drive has as its parent the id `files.get` of `root` answers, and that folder itself has no parent). So every call whose answer holds files, `List`, `Search`, `Show` and `Upload`, first sends one `GET` of `/drive/v3/files/root` asking only for `id`, and a missing id is `ErrProvider`; the same id is the parent of a new file pushed with no folder. A shortcut Drive answers without a usable `shortcutDetails` carries no `target`, and the engine refuses it `not_a_file` (`D06-transfers`).

`kind` is one of `file`, `folder`, `shortcut`, `document`, `spreadsheet`, `presentation`, `drawing` and `other`, read from the MIME type: Google's native types all begin `application/vnd.google-apps.`, a native type this design does not name is `other`, and anything else has bytes and is a `file`. The four exportable kinds have an export table and a default each; a `pull` that names no `format` exports to the default, and one that names a format must name one the table lists for the kind (`D06-transfers`).

## Listing and searching

`List` answers one page of a folder's children, folders first and then by name: the client asks Drive to sort with `orderBy=folder,name`, which Drive applies across pages, so the order is Drive's and the client keeps it (observed: a subfolder whose name sorts last came before every file). An absent folder means My Drive's root, asked for with the alias `root`; a shared drive's id names that drive's root. `Search` answers one page of the files whose name or content matches the words, by Drive's `fullText contains`, in Drive's relevance order: Drive refuses any `orderBy` on a `fullText` query (observed: 403). Optional `Folder` keeps the search inside one folder and optional `Drive` inside one shared drive; absent both, it searches My Drive and every shared drive (`corpora=allDrives`). Both ask for `trashed = false`, which omits a trashed file (observed), and `Show` asks for the `trashed` flag and answers a trashed file as not found (observed: `files.get` of a trashed file answers 200 with `trashed: true`, and `alt=media` of one still answers its bytes), so a trashed file is never listed, searched or shown.

The words and every id the client writes into Drive's query language are quoted: put between single quotes with each backslash and each single quote escaped by a backslash, so nothing an agent types is interpreted (observed: an escaped quote is accepted, an unescaped one answers 400).

A page is at most as many files as the caller asks for, `List`'s `size` or the query's `Size`, sent as Drive's `pageSize`, and `Next`, Drive's `nextPageToken`, empty on the last page. Drive documents `pageSize` as the most files it answers, "The service may return fewer than this value", with a maximum of 1000 to which larger values are coerced; and `nextPageToken` as the token for the next page, "absent if the end of the files list has been reached", which `pageToken` takes back (Google's Drive v3 reference for `files.list`, read 2026-10-13). The tools ask for at most `paging.MaxLimit` (appkit's D25), below that cap, so the client sends the size it is given and clamps nothing. The client keeps no page size of its own. The tools pass `Next` out as `next` and back in as `page` untouched; it is opaque to gdrive (orchestrator decision D14). These two lists are provider-paged, as `shape/` (Listing) allows a provider-backed list to be: the token is Drive's, not an `appkit/paging` token (`D09-tools`).

## Streams

`Media` and `Export` answer Drive's body as an `io.ReadCloser` as soon as the headers arrive, never reading it first; the caller streams it into one artifacts `Put` and closes it. The bytes are the body exactly. Cancelling the call's context ends the stream, which is how the drain abandons a pull. An export's answer carried `Content-Length` (observed, for a small Doc exported as `.docx`), but the client relies on neither a length nor chunking.

## The upload

`Upload` takes the target (a new file's name and parent folder, or the id of a file to replace and an optional new name), the content type and length, and the body, and answers the file Drive made or changed. It is decision 9's protocol, proven against Drive in a throwaway folder. After the root-id request, one request opens a resumable session: a `POST` of `/upload/drive/v3/files` with the name and parent for a new file (the folder given, or the My Drive root id the call asked for, the form the probe used to make its folder), or a `PATCH` of `/upload/drive/v3/files/<id>` for an update, with the token, `uploadType=resumable`, the `fields` the final answer should carry, and the content type and length in `X-Upload-Content-Type` and `X-Upload-Content-Length`. Drive answers 200 with an empty body and the session URI in `Location`. The body then goes in `PushChunk` pieces, each a `PUT` to that URI with its `Content-Range` and no `Authorization`; Drive answers `308` with `Range: bytes=0-<last byte held>` until the last piece, whose answer is 200 and the file resource with the fields the session asked for. A zero-byte body is one empty `PUT` with `Content-Range: bytes */0`, answered with a file of size 0.

On an update, a given name renames the file and an absent one leaves Drive's name as it is (orchestrator P4; observed both ways); the parent is kept, and the content type becomes the one declared. Drive makes or changes nothing until the last piece lands: a session opened and given one piece, then abandoned, left no file (observed). So when the body fails, `Upload` stops sending, and a failed push changes nothing at Drive.

Since the session URI is the credential for the pieces, it is treated like the token: it never appears in an error text or an event.

## The trail

Every request the client sends is recorded as one `drive.called` event through the writer, the same shape as appkit's `sibling.called`: `endpoint`, the call's name; `status`, the answer's status or 0 when none came; and `duration_us`, the exchange up to the response headers on the writer's clock. Nothing else travels: no token, no file id, no name, no query and no byte of a body. The event's request id and user are the caller's in the context, as the writer reads them.

## Errors

Every failure is one of four kinds the engine and the tools tell apart with `errors.Is`. `ErrNotFound`: Drive answered 404, or `Show` found the file trashed; the tools refuse with `not_found` and a transfer fails with reason `not_found`. `ErrForbidden`: Drive answered 403; the engine decides what that means for a read and for a write (`D06-transfers`). `ErrTooLarge`: an export passed Drive's cap, which the client recognizes in two forms: a 403 whose error reason is `exportSizeLimitExceeded`, and an export stream that breaks after `ExportCap` bytes; a transfer fails with reason `too_large`. `ErrProvider`: anything else Google did, any other status, no answer, or an answer the client cannot read; the tools refuse with `provider` and a transfer fails with reason `provider`. When no answer came because the call's context was done, the error also matches the context's error, so the engine can tell a drain from a Google failure. An error reading the body handed to `Upload` is the reader's error, never `ErrProvider`, so the engine can tell artifacts' failure from Google's.

## Recorded decisions

- **Live read-only probes, 2026-10-11**, with a token refreshed from the seeded grant, saved with the token redacted under `/tmp/scratch.vUpLRj/probes/`: `drives.list` answers `{"drives":[{"id","name"}]}` with one drive "Shared" and accepts `supportsAllDrives=true`; `files.list` answers `files` (present and empty when nothing matches) and `nextPageToken` only when more remain, and a page token passed back answers the next page; `size` is a decimal string, `modifiedTime` RFC 3339 with milliseconds and `Z`, `webViewLink` a URL, `driveId` absent in My Drive and present in a shared drive, `parents` one id; `files.get` of `root` answers My Drive's root folder with no `parents`; `files.get` of a shared drive's id answers a folder with that `driveId` and no `parents`; a bogus id answers 404 with `{"error":{"code","message","errors":[{"reason":"notFound",...}]}}` on `files.get`, `alt=media` and `export`; `'<bogus>' in parents` answers 404, a file's id there answers an empty list; `corpora=drive` with a bogus `driveId` answers 404; a bogus page token answers 400; a bogus access token answers 401 with reason `authError`; `alt=media` answers 200 with the file's `Content-Type` and `Content-Length` and its exact bytes; `export` of a non-native file answers 403 reason `fileNotExportable`; `orderBy` with `fullText` answers 403 reason `forbidden`; `orderBy=folder,name` with `'root' in parents` and with a shared drive's id is accepted; `fullText contains` matched words of file names in both drives; `corpora=allDrives` reaches My Drive and the shared drive, `corpora=drive` with `driveId` only the shared drive.
- **The export table is the documented one** (orchestrator decision), fetched from Google's export-formats guide on 2026-10-11. `about.get` with `fields=exportFormats`, read live the same day, names each of the four native MIME types this design maps and lists every documented format for it, plus two the guide does not list (`text/x-markdown` for documents, `application/x-vnd.oasis.opendocument.spreadsheet` for spreadsheets); those two are left out, as aliases the documentation does not promise.
- **Live write probes, 2026-10-11** (orchestrator P5), inside one folder `ikigenba-design-probe-20261011T224429Z` made in My Drive and permanently deleted with its contents afterwards (`files.get` of it and of each child then answered 404); evidence with the token and session ids redacted in `/tmp/scratch.vUpLRj/probes/write-probes.md`. Proven: the session create and update requests and their 200 answer with `Location`; pieces `PUT` without `Authorization` accepted; `308` with `range: bytes=0-262143` after a first 256 KiB piece; the last piece answered 200 with exactly the members the session's `fields` named (`driveId` absent in My Drive); the zero-byte form; an abandoned session leaving no file; rename on update by metadata `name`, and `{}` keeping the name; a folder made in My Drive's root with `parents` holding the root's id; a shortcut's `shortcutDetails` `{targetId, targetMimeType}` and no `size`; a new empty Doc answering a `size`; export of a Doc to `.docx` answering 200 with `Content-Length`, and to `image/png` answering 400 reason `badRequest` (not in the table, never sent); `orderBy=folder,name` putting a subfolder first; a trashed file answering `trashed: true` on `files.get`, and omitted by `trashed = false`; Drive's default answer without `fields` holding only `kind`, `id`, `name` and `mimeType`.
- **The token is a string per call, not a source**, and the session URI is the credential for the upload's pieces. Only the root-id request and the session-opening request carry the token, and both are sent right after the work fetched a fresh token; the pieces, sent without `Authorization` as Drive accepts them, run as long as the body takes. A token source would buy nothing, so `Upload` keeps its string token and its signature. The URI is kept out of every error and event as the token is.
- **The export cap is recognized but unproven.** Google documents that an export past 10 MB is refused with a 403 whose reason is `exportSizeLimitExceeded`; the probe did not manufacture a Doc that large (orchestrator P5 carve-out), so this form rests on the documentation alone, a departure from proving every vendor fact live, until a real case appears. Because it is unproven whether Drive refuses with the headers or breaks a stream it began, the client takes both: the documented 403 is `ErrTooLarge`, and so is a read of an export stream that fails, other than by the context, after `ExportCap` (10,000,000 bytes, the smaller reading of "10 MB") bytes, since a stream should never get that far. Any other 403 to an export is `ErrForbidden`.
- **A native file's `size` is dropped.** Decision 4 says `bytes` is absent for a Google-native file; Drive answers a quota size for one, which is not the size of anything a pull moves, so the reduction keeps `size` for kind `file` only.
- **Fields are named on every file call.** `Show` asks for the trashed flag and `shortcutDetails`; `List` and `Search` ask for `nextPageToken` and the file fields the reduction reads; the upload's session asks for the fields of the file it answers.
- **An upload's answers are classified by status, as reads are.** Opening the session: 404 (the file to replace or the parent gone) is `ErrNotFound`, 403 `ErrForbidden`, any other failure `ErrProvider`. A piece: 403 (Drive refusing the write, its storage quota for one) is `ErrForbidden`; 404 means the session is gone, not the file, so it is `ErrProvider` like every other status but 200, 201 and the expected `308`. A `308` whose `Range` does not hold every byte sent so far is `ErrProvider`: the client sends each piece once and never resumes.
- **`drive.called` is emitted by this package** through the writer in `Config`, as `telemetry.SiblingClient` emits `sibling.called`, rather than by `internal/trail`: the client is the only thing that sees each request, its status and its timing. The endpoint names are this design's: `files.list`, `files.get` (metadata, including the lookup of `root`), `files.get.media`, `files.export`, `drives.list`, `files.create` and `files.update` (opening a session) and `upload.chunk` (each piece).
- **Only status classifies an answer**, except an export's 403, whose error reason tells the size cap apart. Two observed 403s are not about permission (`fileNotExportable`, and `forbidden` for a sort on a full-text query), and the client never sends either: `Export` is called only for the four exportable kinds, and `Search` never sorts. 401 is `ErrProvider`: connections hands out a token it believes good, so a 401 is Google's failure as far as gdrive can tell, and the next call's token request reports a dead grant as `reconnect`.
- **List order is Drive's.** Sorting a page in the client would break the order across pages, so `List` asks Drive for `orderBy=folder,name` and keeps what it answers. `name` is Drive's lexical sort, not `name_natural`.
- **`Search` with empty words** asks for every untrashed file in its scope; the tools decide whether to allow it.
- **An empty id is not found, unasked.** `Show`, `Media` and `Export` given an empty id answer `ErrNotFound` and send nothing, since `files/` with no id is `files.list`, not a file; the tools rely on it for `show` and `pull` (`D09-tools`).
- **The root id is asked for, never assumed.** A new file pushed with no folder names My Drive's root by the id `files.get` of `root` answers, as the write probe made its folder, rather than by the alias `root` in `parents`, which no probe tried. The same request lets the reduction tell a My Drive root parent apart, at one short request per call (root R8).
- **`Show` of the alias `root` sends two requests to `/drive/v3/files/root`** (the user's ruling on the show-root issue): the lookup asking for `id` alone, then the metadata request for the supplied id, whose path is the same, with `Show`'s full `fields`. The lookup is told apart by its `fields`, so the rules about it (R-R6PH-DMIO, R-R7XD-RE9D, R-R95A-5602) speak of the request to that path whose `fields` is `id`, and the supplied-id path and `fields` rules stay uniform. `Media` of `root` likewise reaches that path with `alt=media` and no lookup. `List`, `Search` and `Upload` never collide: their other requests go to `/drive/v3/files` or under `/upload/`, and a folder or parent `root` travels in `q` or the body, not the path.
- **What is proven, what is tolerated, what is unproven.** Every fact this document states about Drive's behaviour was observed live in the read-only and write probes above. Three things the client meets were not observed and are not asserted as facts; the client tolerates each whatever Drive does: it follows a `nextPageToken` on `drives.list` when one is answered and stops when none is (the probe account holds one shared drive, so none was seen); it takes 200 or 201 to the last piece as success (every probe answered 200); and a shared-drive folder given to `Upload` is only a parent id sent with `supportsAllDrives=true`, as every request carries it (only My Drive was written). The one unproven fact the design relies on is the export size cap, sanctioned by the orchestrator (below).
- **A body longer than its declared length is not checked.** `Upload` reads at most `u.Bytes`; the push hands it artifacts' `Get` body with the `Bytes` that same answer's `Content-Length` gave, which the HTTP client already holds the body to.
- **Rejected** (decisions document): Google's Go client library, the largest dependency in the suite for six calls when a fake server is needed either way; and proving shared drives and export against the fake alone, which is why every Drive fact stated here was observed live, the export cap excepted; the three tolerances above are client behaviour, not Drive facts.
- **No retry, no redirect policy of its own**: the client sends each request once, as decision 8 says, and leaves redirects to `HTTP`.
- **`PushChunk` lives here**, beside the upload it sizes, rather than in `internal/transfers`; 8 MiB is a multiple of 256 KiB, the granularity Google's resumable protocol asks of every piece but the last.

## Consumer tasks

The engine builds `drive.NewClient(drive.Config{HTTP: p.HTTP, Telemetry: w})` once. A tool gets `tok, err := cc.Token(ctx, "google")` from `appkit/connections` and calls `dc.List(ctx, tok.AccessToken, folder, page, n)`, `dc.Search(ctx, tok.AccessToken, drive.Query{Text: q, Folder: f, Drive: d, Page: page, Size: n})`, `n` being what `paging.Window` read from the call's `limit`, `dc.Show(ctx, tok.AccessToken, id)` or `dc.Drives(ctx, tok.AccessToken)`, answering the files and `Next`. A pull's validation calls `Show`, follows a shortcut's `Target` with a second `Show`, checks `Kind`, `drive.DefaultFormat` and `drive.Formats`, and the background work calls `Media` or `Export` and hands the stream to `artifacts.Client.Put`. A push calls `dc.Upload(ctx, tok.AccessToken, drive.Upload{Name: name, Folder: folder, ContentType: m.ContentType, Bytes: m.Bytes}, body)` to create, or `drive.Upload{File: id, Name: name, ...}` to replace, `Name` empty keeping Drive's name, and records the `File` it answers, its `Name` included. Each maps `errors.Is(err, drive.ErrNotFound)`, `ErrForbidden`, `ErrTooLarge` and `ErrProvider` to its refusal word or failure reason. A test builds a `telemetry.Writer` over a capturing sink with a fixed clock, a fake Drive on `httptest.Server`, a `Client` with `BaseURL` set to it, and checks each request's method, path, query and headers, each answer's reduction, each error kind, and one `drive.called` per request.
