# D07-pages

What gdrive draws as HTML: `internal/pages`, the five templates `landing`, `transfer`, `tools`, `about` and `notfound` and the data each receives, and the handler that answers `/`, `/<id>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it. It follows artifacts' pages for the record-per-page form and connections' for the tools and about pages; scripts' run page is the precedent for a record that is private to its caller and shown as it stands when loaded.

## The pages

The landing page shows the caller's own transfers, newest first, in the order the store lists them (`D04-store`: descending started, then descending id): each row's id linking to its page, its direction and status, its reason when failed, the Drive file's name linked to Drive's `webViewLink` when the record holds one, the artifact's path linked to the artifact's page on artifacts, the bytes moved, and when it started and finished, each in RFC 3339 and to the minute. Another user's transfer is never shown. With no transfer the template shows its empty state. The list is data agents add, so the page pages, as the suite's listing rule asks (`shape/`, Listing; appkit's D25, `appkit/paging`), and it navigates: `GET /` takes one optional query parameter, `page`, the very token the `transfers` tool issues as `next` (`paging.Token{Tool: "transfers"}` over a transfer's started and id, `D09-tools`), and nothing else is read from the query. A request's **page value** is its first `page` value, empty when it carries none. An empty page value asks for the **first window**: the first `paging.DefaultLimit` of the caller's transfers in that order, the same first page `transfers` answers with `{}`. A page value the token decodes asks for the window after it: the next `paging.DefaultLimit` of the caller's transfers after the key the token holds, exactly the transfers `transfers` answers when passed that `page` and no `limit`. `Page` is the page value, so the template knows whether it draws the first window; `Next` is the token `transfers` answers as `next` for that window, over the last row's started and id, and empty when none remain. The window is always `paging.DefaultLimit` transfers at most; `limit` is the tool's alone. What the template draws from `Page` and `Next`, the navigation, its links and when it appears, is the asset's. The page reads a window with one `ListAfter` call of `paging.DefaultLimit` plus one transfers from the key the page value holds, or from the start when it is empty (`D04-store`), so it learns whether more follow without holding more than a window and one row.

`/<id>` is one transfer's page: the record in full, the Drive file's id and kind, the content type and export format, both times to the second, the artifact's `url` and the Drive `link` when done, and, when it failed, the reason, whose sentence the template chooses from `Reason` (orchestrator decision D7). The page does not stream: a transfer still queued or running is shown as it stands when the page is loaded. An unknown id, a pruned one and another user's are answered alike, the not-found page with status 404 (root decision R5), so a page never tells a caller that someone else's transfer exists.

The tools page lists the eight tools in the catalog's order (`D09-tools`), each with the first line of its description, which is what the catalog answers (root decision R9). The about screen shows the service's name, the banner's `Release` and `Commit` as its version, and `Description`. Any other path is the not-found page, status 404, whatever the method, drawn with the footer only.

The landing page sits at the root of the banner's trail, so its trail is empty; the transfer page is one level below it, named by the transfer's id at `/<id>`; the tools page and the about screen are one level below it, `pages.ToolsLevel` and `pages.AboutLevel`. The banner's user is the caller's email, with auth's profile and sign-out addresses, built on `urls.Auth` (`D06-transfers`), as connections' are.

## The data

Every value a template receives is a string or, for bytes, an `int64`; no data type carries an access token or a credential, a byte of a file, an owner or anything of another user's, so no page can show one. Times are the stored UTC times formatted twice: `Started` and `Finished` in RFC 3339 to the second, for a `time` element's `datetime`, and `StartedText` and `FinishedText` in the page's own layout, `pages.MinuteLayout` on the landing page and `pages.SecondLayout` on the transfer page, as the templates' comments name them (root decision R12). A transfer not yet finished has both `Finished` strings empty. `Link` and `URL` are the record's, empty unless the transfer is done (`D04-store`). `ArtifactPage` is the artifact's page on artifacts, built with `urls.ArtifactPage` from the artifacts entry's `URL` in the services file and the artifact id the record holds (`D06-transfers` owns the rule); it is empty when the record holds no id, which is every push and every pull not done (orchestrator decision D6), and the landing template then links the path to `URL`, or shows it plain.

## Guests and methods

The manifest says `guests = false` (`D02-cli`), so the host's nginx sends a request with no credential to sign in before it reaches gdrive, and `D03-serve` mounts this handler inside appkit's `identity.Require`; there is no guest branch and no sign-in address, as in artifacts. A request to `/`, `/tools`, `/about` or a transfer path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD`, decided before the store is read. A page value the handler cannot decode, one edited by hand, one another tool issued, a word such as `bogus`, names no window, so `GET` and `HEAD /` answer it with gdrive's not-found answer, status 404, never quietly with the first window; the tool's refusal sentence, `paging.BadPage`, stays the agents' interface. A page value is decodable exactly when `transfers` would accept it as `page`: the token decodes and holds a canonical RFC 3339 UTC second and a valid transfer id. The handler decides in order: the identity gate, the path, the method, then the page value, so `POST /?page=bogus` is still the 405; and the page value is decoded before the store is read, so the 404 is the same while the database is unreachable. The landing page for a decodable page value and a transfer page answer 503 with `store.Unreachable` as plain text when the store cannot be read; the about, tools and not-found pages are served without reading it.

## Recorded decisions

- `ServiceName`, `Description` and the two layouts are contract constants with values stated. `Description` is the manifest's text (decision 1), which the host parses (`D02-cli`); the layouts are data formats the templates name (root decision R12), not words a person reads, so connections' and artifacts' practice holds rather than scripts' unstated layout constants.
- The landing row and the transfer view are two types, `TransferRow` and `TransferView`, because their `StartedText` and `FinishedText` differ in layout and the view carries four more fields; each field list is the template comment's, in its order.
- `ArtifactPage` is `urls.ArtifactPage(urls.Base(u), id)` (`D06-transfers`), `u` being the `artifacts` entry's `URL` as the services file holds it when the page is asked; this document restates no address rule. It is empty when the services file has no `artifacts` entry or its `URL` is empty: a relative page address on gdrive's own host would name nothing (unlike the connect page's relative fallback, decision 7). The templates' fallback to `URL` then applies on the landing page.
- The auth address is `urls.Auth` (`D06-transfers`), declared once beside the other two addresses gdrive builds, as connections keeps its own in its `internal/urls`.
- An unknown, pruned or another user's id is one not-found answer, byte for byte the not-found page of any other path (root decision R5); a string that is not a valid transfer id is not looked up at all.
- An undecodable page value is answered with the not-found answer of any other path, byte for byte, as an unknown transfer is (root decision R5), rather than a sentence of its own: a URL carrying a token the page never issued names no page. "Undecodable" is the set the `transfers` tool refuses with `paging.BadPage`, so every page value the page accepts has a tool answer to compare against.
- A database outage is a plain-text 503 with `store.Unreachable` and a newline, the unavailable answer `D04-store` names for a page, as artifacts and connections answer it.
- The tools page's description is the catalog's first line (root decision R9); this package does not cut a description itself, so it needs no `FirstLine` of its own.
- The about page carries a prose section on how gdrive works; the design names only the template `about` and its data.
- Every template can show every state the decisions name: the seven reasons each have a sentence in `transfer.html`, the four statuses and both directions are drawn, and the absent `Link`, `URL`, `ArtifactPage`, `Format`, `Reason` and `Finished` each have a branch. Nothing is reported against the templates.

## Consumer tasks

`web.Handler` (`D03-serve`) builds a set with `s, err := pages.Load()` and mounts `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: s, ServicesPath: cfg.ServicesPath, Store: cfg.Store})` inside `identity.Require` for every path that is not `/mcp`, `/events`, `/declarations` or under `/_appkit/`. The about requirement of `D01-layout-and-run-seam` executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}` where `b.Trail` is `[]page.Level{pages.AboutLevel}`; `D02-cli` compares the manifest with `pages.Description`; `main` names the service `pages.ServiceName`. A test builds a store over its own database with a clock it sets, adds transfers for two users and finishes some `done` with an artifact id and a link and some `failed` with each reason, writes a services file naming an `artifacts` entry, builds its own set with `pages.Load()`, serves `identity.Require(pages.Handler(cfg))` with a `Banner` func returning a fixed banner, sends raw requests with `X-User-Id` and `X-User-Email`, and compares each body with what executing the named template of its own set writes for a `LandingData` of `TransferRow`s, a `Page` and a `Next` (with `paging.DefaultLimit` plus one transfers of one user, the first `paging.DefaultLimit` rows, an empty `Page` and a `Next` it builds with `paging.Token{Tool: "transfers"}.Encode`, the same as the `next` a `transfers` call with `{}` answers; then, requesting `/?page=<that Next>`, the oldest transfer's row alone, that token as `Page` and an empty `Next`, the same as `transfers` answers with `{"page":<that Next>}`), a `TransferData` of a `TransferView`, a `ToolsData` of `ToolRow`s built from `tools.Catalog()`, an `AboutData` or a `NotFoundData`; it asks the other user's id and a pruned id and gets the not-found page; it requests `/?page=bogus` and `/?page=` followed by a token `paging.Token{Tool: "list"}` encodes, with the store reachable and failing, and gets the not-found page each time; it turns the store's failing switch on to see the 503.
