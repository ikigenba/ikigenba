# D08-trail

The trail: `internal/trail`, the two transfer events gdrive emits on the suite's event bus and records in its own trail, their declaration to the events app, the identity they carry; the closed set of event names gdrive records; and decision 15's secrecy, stated once for the whole app: no byte of a file ever leaves the process except to Drive and artifacts, the two places the bytes are for, and no access token except to Drive, the one place it is for; gdrive never sends it to artifacts or back to connections (proved at their fakes' sockets). It is connections' and artifacts' trail with gdrive's events: fixed names, one function for both, and the transfer's caller, not the moment's, on every event, as scripts' run events carry the run's caller.

`drive.called`, the record of every request to Drive, is `D05-drive`'s: the Drive client is the only thing that sees each request, its status and its timing, and records it itself. `sibling.called` is appkit's clients'; the request pair and `tool.called` are appkit's middleware and MCP server's; `service.started` and `service.stopping` are `D03-serve`'s. When the engine emits each transfer event is `D06-transfers`'.

## The two transfer events

A transfer's life is told by `transfer.started`, when its work begins, at once for a transfer recorded `running` and later for one that waited in the queue, and `transfer.finished`, when it ends, however it ends: `done`, failed for any reason, abandoned in the queue at the stop, cut off at the drain deadline, or settled `interrupted` by the next start. A transfer that never ran has a `transfer.finished` and no `transfer.started`. `transfer.started` carries four attributes, in this order in its declaration: `transfer`, the transfer's id; `direction`; `file`, the Drive file's id (empty for a push that creates, until it is done); and `path`, the artifact's path. `transfer.finished` carries the same four and then `status`, `reason` (empty when `done`) and `bytes`, the count moved, an integer. Nothing else travels: no name, no link, no URL, no email, no content type, no token and no byte of a file. A consumer that wants the outcome in full asks `transfer` as the user, and one that wants the bytes fetches the artifact's `url` with its own credential.

Every transfer event goes two ways at once, under the same name, attributes, request id and user: recorded in the trail through the run's writer, and emitted on the bus through the run's emitter (decision 10). It is told as the transfer's caller, the user id, email and request id the record keeps (`D04-store`), whatever context the moment that tells it has: a transfer started from the queue, ended by the drain or settled at the next start is still told as the user whose `pull` or `push` recorded it, under that call's request id, so a transfer's trail is whole under one request id. The bus event carries the event cause of the context it is told under, its id and its depth plus one, as connections' and artifacts' events do; the engine tells a transfer's events under the cause the recording call carried (`D06-transfers`), so a script that pulls on `transfer.finished` deepens the chain.

An event is told after the change it reports is committed, never before, and never for a change that did not happen: a refused `pull` or `push` tells none. A crash between the commit and the emit loses the event while the record stands, the window every sibling accepts (decision 10).

## The declarations

`trail.Emits()` declares the two names, literal, each with its attribute keys in order. The run's emitter is built with them, and `/declarations` publishes them (`D03-serve`).

## Secrecy

No body byte, in whole or in part, and no access token reaches telemetry, the bus, a page, a tool answer, standard output, standard error or a log, on success or on failure (decision 15). gdrive writes no log of its own: its only text streams are standard output, which a serving run never writes, and standard error, which a serving run writes only when its drain runs out (`D03-serve`): the drain's last line, and appkit's `undelivered event` and `lost event` lines, each an event's JSON, which carries no secret because no event does. The rule is proved at the run seam, by use: fakes of connections, Drive and artifacts serve a 40-character random token and long random file bodies, of ASCII letters and digits so that no encoding hides a match, every other value the fakes answer kept free of both so that no match is a coincidence, answer some calls with failures whose bodies echo both, and every capture of the run, the telemetry sink's events, the bus sink's events, both streams, every tool result and every page body, is searched for the token and for every 16-byte piece of every body. An attribute that names what happened, the ids and the counts, is not a secret; a Drive file's name is the user's own and is shown on the pages and in tool answers by design (decision 14), but is never put in an event.

## Recorded decisions

- Fixed names and one `Record`, as artifacts and connections: the two names are decision 10's, the bus's `transfer.*` pattern picks both, and `Record` knows which attributes each name carries.
- **The record's caller, not the context's.** `Record` tells the event as `trail.Caller` of the transfer, whatever caller its context carries, where connections and artifacts tell an event as the caller on the context. A transfer's events are told from the background, the queue, the drain and the next start, where no request is around, and decision 8 says the work runs as the caller under the originating request id; putting the rule in `Record` makes it hold wherever an event is told, as scripts' `runs.Caller` does for its run events. The cause still comes from the context, since the record does not keep it.
- `file` is present on `transfer.started` even when empty (a push that creates): the bus holds an event to its declaration's keys, so every key is always there; `reason` is present and empty on a `done` `transfer.finished` for the same reason, as decision 10 says.
- `bytes` is an integer attribute, the record's `int64`, as artifacts' `bytes`.
- `event.lost`, which appkit's emitter records through the writer for a bus event it could not deliver, is in the closed set of names, since `D03-serve` builds the emitter with the writer.
- Secrecy is required of the whole run rather than of each package, because the leak it guards against is a wiring one (an error text quoted onto a stream, a body echoed into an attribute) that only the assembled process can show; `D05-drive` separately requires that its errors and `drive.called` never hold the token, and appkit's clients' `HTTPError` keeps a sibling's answer body, which gdrive therefore never quotes.

## Consumer tasks

The engine (`D06-transfers`), once the store holds a transfer `running`, calls `trail.Record(ctx, w, em, trail.Started, t)`, and once it holds its ending, `trail.Record(ctx, w, em, trail.Finished, t)` with the transfer `store.Finish` answered, `ctx` carrying the recording call's event cause or none. `Run` builds its emitter with `events.Config{Emits: trail.Emits(), Telemetry: w, ...}`. A test builds a writer over a `*telemetry.Capture` and an emitter over an `*events.Capture` with `trail.Emits()`, calls `trail.Record` with a `store.Transfer` and a context it built with `identity.NewContext` for another caller and `events.NewContext` for a cause, and compares the captured events' `Name`, `Attrs`, `RequestID`, `User`, `Cause` and `Depth`. A test of secrecy drives `cli.Run` with the three fakes and the captures, makes every tool call and page request with a caller, lets the transfers end, cancels, and searches every capture.
