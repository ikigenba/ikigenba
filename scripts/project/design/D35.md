# Decision 35 — Script definitions are git-backed trees: `main.py` is the entrypoint, `scripts/<name_key>` is the repo

> **Suite adoption (operator-sequenced).** This Decision is scripts' slice of
> the **version plane**, `root project/design/D24.md`. It assumes repos holds
> one bare repository per artifact keyed `<kind>/<name>`, that `main` is live,
> and that the owning service enforces name uniqueness within its kind and
> calls repos' rename when its key changes. scripts owns none of that contract
> and restates none of it; what follows is only scripts' side.

**Problem.** A script is a single `TEXT` column: `scripts.body` holds one
Python file, `update` overwrites it, and there is no history, no second file,
and nothing a laptop can check out. Every real automation outgrows one file —
a shared helper module, a fixture, a template — and every mistake is
unrecoverable because the previous body is gone the instant it is replaced.
The version plane makes history ambient, so a script becomes what it always
wanted to be: **a directory of files under version control**.

**Decision.** A script's **definition is a git tree** held by repos, and the
`scripts` row keeps metadata only.

1. **The tree, and its entrypoint by convention.** A script's repository holds
   whatever files its author wants; the runner executes **`main.py`** from the
   tree root. Supporting modules and data files ride along and are importable
   and readable because the process cwd is the tree (D38). There is no manifest,
   no declared file list, and no build step — the convention *is* the contract,
   and a tree with no `main.py` at its root fails its run with a plain
   interpreter error, exactly as a missing file does today.

2. **The repository key is `scripts/<name_key>`.** `name_key` is a slug derived
   from the script's name by a boring, total rule
   (`internal/script/namekey.go`):

   ```go
   // slugify lowercases, maps every rune outside [a-z0-9] to '-', collapses
   // runs of '-', trims leading/trailing '-', and truncates to 48 bytes
   // (re-trimming after the cut). An empty result becomes "script-" + the
   // lowercased script id, so the rule is total for any user text.
   func slugify(name, scriptID string) string
   ```

   **Uniqueness is service-wide, not per owner.** The plane's namespace for
   this kind is `scripts/<name>` (`root project/design/D24.md`), so two owners
   cannot both hold `scripts/nightly`. `deriveNameKey(ctx, excludeID, name)`
   slugifies, then appends `-2`, `-3`, … until the key is free, and the DB
   enforces the invariant with a real UNIQUE index — the derivation is a
   convenience, the index is the guarantee. `RepoKey(nameKey) = "scripts/" +
   nameKey` is the only place the `scripts/` prefix is written.

3. **One new timestamped migration**, minted with
   `bin/create-migration scripts version_plane` (never a hand-picked number),
   **purely additive** — no table is rebuilt and no row is dropped, because
   `scripts` now holds production data (`root project/design/D05.md`):

   ```sql
   ALTER TABLE scripts ADD COLUMN name_key       TEXT;  -- NULL until seeded (D40)
   ALTER TABLE scripts ADD COLUMN repo_seeded_at TEXT;  -- stamp: repo exists + body committed
   ALTER TABLE runs    ADD COLUMN repo_sha       TEXT NOT NULL DEFAULT '';
   CREATE UNIQUE INDEX idx_scripts_name_key ON scripts(name_key) WHERE name_key IS NOT NULL;
   ```

   Every committed migration — `002_scripts.sql`,
   `20260609135007_add_source_path.sql`, `20260720020257_owner_id_keying.sql`
   and the rest — is untouched. `body` **stays** in this migration: it is the
   seeding sweep's input (D40) and is retired only by a later migration, after
   every row's content is in the plane.

4. **`body` is superseded as the definition.** From this Decision on, the tip of
   the repository's `main` branch **is** the script; the `body` column is
   legacy storage on its way out (D40) and is never read to execute a run
   (D38). `Script.Body` survives as a *derived, on-demand* field — `get` reads
   `main.py` at `main` through the version plane (D37) — so the MCP surface's
   shape is unchanged for a caller that only ever authored one file.

5. **`config` stays a row column.** `config_json` (`interpreter`,
   `timeout_secs`) is **runner** configuration, not authored content: it is
   scripts' operational knob on the run, it is materialized into the run dir by
   the runner (D21), and putting it in the tree would let a git push change the
   service's execution policy. It stays on the row and out of the repository.

**Rejected.**
- **Keeping `body` as the definition and mirroring it into git.** Two writable
  copies of the same content with no merge story: a laptop push and an
  `update` would silently fight, and the loser's work would vanish. One
  writable copy — `main` — is the whole point of the plane.
- **A declared entrypoint field (`entrypoint` on the row or a manifest file).**
  A knob whose only sane value is `main.py`, plus a new failure mode
  (entrypoint names a file the tree does not have) and a second place for the
  truth to live. Convention costs nothing and is already how the runner behaves.
- **Per-owner repository keys (`scripts/<owner_id>/<name>`).** The plane's
  keyspace for this kind is the service's own key (`root
  project/design/D24.md`); nesting an owner id inside it invents a second
  namespace the plane does not model, and makes every key unreadable in
  listings and clone URLs. Service-wide uniqueness with numeric suffixing gets
  the same guarantee with none of that.
- **Using the script id as the key (`scripts/01J…`).** Correct and useless: the
  point of a checkout-able repository is that a human recognizes it on their
  laptop. The id remains the durable handle inside scripts; the key is the
  human-facing name.
- **Rebuilding the `scripts` table to add the columns.** The owner-id
  conversion (D28) could drop rows because the migration window sanctioned it;
  that window is closed and scripts' `state/` is live customer data. Additive
  columns plus a seeding sweep preserve every row.
- **Putting `config.json` in the tree.** See §5 — it would make a push able to
  change the interpreter and the TTL, converting a content channel into a
  control channel.

**Verification** (real substrates: migration claims apply scripts' full
embedded migration set (`db.FS`) through the appkit runner to a fresh real
SQLite database and read back `PRAGMA table_info`/`index_list`; the uniqueness
claim is falsified by the real SQLite UNIQUE index, not by a Go pre-check;
derivation claims run the real `slugify`/`deriveNameKey` over a real store).

- R-20IL-OWGP — applying the full embedded migration set to a fresh real SQLite
  database yields a `scripts` table carrying **both** `name_key` and
  `repo_seeded_at` columns **and still carrying `body` and `source_path`**, a
  `runs` table carrying `repo_sha`, and a **UNIQUE** index over `scripts(name_key)`
  — while `002_scripts.sql`, `20260609135007_add_source_path.sql` and
  `20260720020257_owner_id_keying.sql` remain byte-identical to their committed
  (frozen) bodies. A migration that rebuilds `scripts` fails it.
- R-21QI-2O7E — a pre-existing `scripts` row (inserted before the new migration
  runs, with a non-empty `body`) **survives** the migration with its `body`,
  `owner_id`, `source_path` and `id` unchanged and `name_key`/`repo_seeded_at`
  NULL — the additive migration preserves production rows. A drop-and-recreate
  fails it.
- R-22YE-GFY3 — `slugify` discriminates: `"Nightly Export!"` → `nightly-export`;
  `"  a//b  "` → `a-b`; `"Ünïcödé ✨"` → a key matching `^[a-z0-9]+(-[a-z0-9]+)*$`
  containing no non-ASCII byte; a 200-character name yields a key of **at most
  48 bytes** with no leading or trailing `-`; and a name of only punctuation
  (`"!!!"`) yields exactly `script-` + the lowercased script id (never the empty
  string). `RepoKey` of any of them is `"scripts/" + key`.
- R-246A-U7OS — service-wide uniqueness holds against the real index: creating a
  second script named `Nightly Export` — **under a different `owner_id`** —
  yields `name_key` exactly `nightly-export-2` (a third yields
  `nightly-export-3`), and a direct SQL insert of a duplicate `name_key`
  is rejected by the SQLite UNIQUE constraint. A per-owner-scoped index fails it.
