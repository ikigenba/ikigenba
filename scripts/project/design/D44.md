# Decision 44 — `webhooks` becomes a trigger source: scripts reacts to inbound webhooks

**Problem.** The webhooks service turns an authenticated inbound
`POST /in/<name>` into a `webhooks:received/<hook>` fact on the event plane — it
is the suite's public ingress, the one place an outside HTTP call becomes a
suite event. Nothing in the suite can *act* on that fact yet: a script is the
natural place to translate an inbound hit into work (resolve it against another
service, notify, record it), but scripts does not consume webhooks, so an
inbound webhook is received and goes nowhere.

**Decision.** `webhooks` joins the consumed sources, by the ordinary D17
mechanism and with no new machinery.

1. **The family table gains one entry** (`internal/script/trigger.go`):

   ```go
   var knownFamilies = map[string][]string{
       "cron":     {"tick"},
       "crm":      {"contact.created", "contact.updated", "contact.tagged", "contact.untagged"},
       "ledger":   {"recorded"},
       "dropbox":  {"create", "modify", "delete"},
       "prompts":  {"run.succeeded", "run.failed"},
       "repos":    {"push"},
       "webhooks": {"received"},
       // still deliberately no "scripts" entry: self-chaining remains out (D11, D17).
   }
   ```

   Everything else in D17 is unchanged: the source segment stays literal, the
   known set is now **seven**, and unknown-source rejection names all seven. A
   received event's subject is webhooks' `/<hook name>`, so canonical filters
   read `webhooks:received/mg-dev-track` or `webhooks:received/**` — ordinary
   globs over the shared matcher, needing no scripts-side parsing of the subject.

2. **A seventh consumer entry.** `cmd/scripts/main.go` adds
   `scriptsConsumerEntry("webhooks")` to `Spec.Consumers`; the subscription
   filter stays the honest catch-all `"**"` and `consume.Handler` is untouched —
   the fan-out is per-source and already generic. The upstream feed URL default
   is chassis/registry-resolved like the other six (D10, D11); `webhooks` already
   holds a registry row, so no new address plumbing is needed.

3. **The workflow shape this enables is authored, not built.** A tracking script
   sets `webhooks:received/mg-dev-track`, reads `suite.event()` for the delivered
   body, resolves it against another service, and notifies with
   `suite.mcp("notify", "send", …)`. scripts adds no webhook concepts of its own —
   no signature model, no hook registry — those live in webhooks; a script reacts
   to the fact and nothing more. `describe` already teaches the trigger pattern
   (D26); the source list it derives from `knownFamilies` now includes webhooks.

**Rejected.**
- **Subscribing only to a fixed hook name.** A hardcoded `mg-dev-track` filter
  would bind scripts to one hook; the canonical filter already lets each script
  name the hook it wants (`webhooks:received/<hook>`), so the general source is
  strictly more useful and no more code.
- **A dedicated webhook-trigger field beside the canonical filter.** A second
  trigger vocabulary for one source; D17's whole point is one string, one
  matcher.
- **Verifying the webhook signature inside scripts.** The secret and its
  verification live in webhooks (its D3/D4); by the time a `received` fact exists
  the trigger was already authenticated at the ingress. A scripts-side check
  would be a second, drifting copy of someone else's trust boundary.
- **Adding `scripts` as a self-chaining source while in here.** Unchanged
  rejection from D11/D17: a new upstream is its own behavior change.

**Verification** (real substrates: validation claims run the real
`eventplane/routing` matcher and the real `outbox.Registry.CouldMatch` over the
revised family table; the wiring claim reads the assembled `scriptsSpec()` and a
real SQLite trigger store).

- R-IM5H-6CKN — `webhooks` validates as an ordinary source:
  `webhooks:received/mg-dev-track` and `webhooks:received/**` are **accepted**,
  `webhooks:nosuchkind/**` is **rejected** with `ErrValidation`, and an unknown
  source (`github:push/**`) is rejected with an error naming all **seven** known
  sources — `webhooks` included and `scripts` still absent.
- R-INDD-K4BC — `scriptsSpec()` declares **seven** consumer entries whose sources
  are exactly `cron`, `crm`, `ledger`, `dropbox`, `prompts`, `repos`, `webhooks`,
  each with a single subscription whose `Filter` is exactly `"**"`; and
  `ScriptsForEvent(ctx, "webhooks", "webhooks:received/mg-dev-track")` over real
  SQLite returns the script holding `webhooks:received/**` and **not** one
  holding a different source's filter.
