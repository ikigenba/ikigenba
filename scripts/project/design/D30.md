# Decision 30 — The chain crosses the sandbox boundary: `SUITE_CORRELATION_ID` and `X-Correlation-Id` on every `suite.*` call

> **⛔ EXTERNAL ORDERING.** Depends on **D29** (the run carries a chain id) and,
> for the header name, on `eventplane/correlation`'s `Header` constant. The
> `suite` module is stdlib-only Python and hard-codes the header string, exactly
> as it hard-codes `X-Owner-Id` / `X-Client-Id` today.

**Problem.** A script run reaches the rest of the suite through the injected
`suite` module (D21–D24): `suite.mcp` calls another service's `/mcp`,
`suite.fetch` pulls content over the content plane, and `suite.files` works the
account file share. Each of those lands on a **real suite service**, whose
chassis records it — but as an *uncorrelated* request, because nothing tells the
callee which chain it belongs to. The result would be the exact failure the
capability exists to prevent: the run is on one chain, and the seven writes it
made to `files` and the two tools it called on `crm` are each a headless chain of
one, with no path back to the run, the script, or the owner action that started
it. The suite's exclusion for sandboxes is explicitly about the **inside** of a
run, not about the calls a run makes back into the suite: those are the
boundary, and the boundary is recorded.

**Decision.** The run's chain id is injected into the sandbox as one more
runtime fact, and the `suite` module sends it on every request it makes.

1. **The runner injects it.** `Runner.Spawn` already receives the whole
   `script.Run`, so the env block beside `SUITE_RUN_ID` gains one entry:

   ```go
   // internal/runner/runner.go — the per-run env block.
   "SUITE_CORRELATION_ID="+run.CorrelationID,
   ```

   It is always non-empty in production (D29 guarantees every run row carries an
   id), and an empty value is tolerated by the module below rather than
   crashing a run.

2. **`suite` sends it on every suite call.** The header
   `X-Correlation-Id: <SUITE_CORRELATION_ID>` joins the header block of
   `suite.mcp`, of `suite.fetch`'s content-plane request, and of
   `suite.files`' `_headers()` — the three places the module already sets
   `X-Client-Id`. When the env var is absent or empty the header is **omitted
   entirely** rather than sent empty, so the callee's read-or-mint middleware
   mints instead of adopting a blank id.

   Every one of those requests is confined to a loopback suite origin by
   construction (D22's service table, D23's port confinement, D24's
   `SUITE_FILES_BASE_URL`), so this Decision cannot leak a chain id to a third
   party: the module has no code path that sends a request anywhere else.

3. **The callee does the recording.** scripts records nothing here. The target
   service's chassis sees an inbound `X-Correlation-Id` from a loopback peer —
   inside the trust boundary, therefore trusted — and records the call as its
   own kind `request` on the run's chain, with the actor scripts already
   asserts (`X-Owner-Id` and `X-Client-Id: scripts:<script_id>`). A single
   `chain` query therefore returns the owner's action, the run's spawn, and
   every suite call the script made, in order, across services.

4. **A script's own traffic stays out.** Anything the script does with the
   standard library directly — `urllib` to a third-party API, a subprocess, a
   local file — carries no chain id, produces no record, and is deliberately
   invisible to telemetry. The run's stdout/stderr and its run dir are the
   record of the inside; D32 states that boundary in full and proves it.

**Rejected.**
- **Passing the chain id to the script as a `suite.correlation_id()` accessor
  the author must attach.** It would work exactly as often as script authors
  remembered, which is the wrong failure mode for a forensic guarantee. The
  module owns its own headers today and should own this one.
- **Sending the header empty when the env var is missing.** An empty header is
  a *present* header; a middleware that trusts inbound values would then have to
  special-case blank, and the read-or-mint rule would be spelled twice. Omission
  is unambiguous.
- **Deriving the header from `SUITE_RUN_ID` instead of injecting the chain
  id.** They coincide only for a run that roots its own chain (D29); for a run
  continuing an inbound chain — a triggered run, or a manual run from an MCP
  call — it would silently start a second chain at every suite call.
- **Propagating the id to non-suite destinations too.** The suite rule is
  explicit: correlation ids go to loopback peers only, never to third parties.
  A chain id leaked in an outbound header to an external API is an
  infrastructure detail handed to a stranger.
- **Recording the boundary calls from inside scripts (an `outbound` record per
  `suite.*` call).** scripts cannot see them — they are made by a `python3`
  child process over its own socket, not by scripts' Go code. The callee's
  `request` record is the true, unavoidable observation of the same hop, and a
  scripts-side guess would double-count it.

**Verification** (real substrates: Go tests in `internal/runner` materialize the
embedded `suite.py` exactly as the runner does and exec the **real `python3`**
on probe scripts, with test-controlled `SUITE_*` env pointing at real
`net/http/httptest` loopback servers that record the method, path and headers
they receive — the substrate design's *Testing strategy* already establishes. A
stub could not falsify these: the assertion is on what a real server actually
received).

- R-4UZN-MWCU — a probe run whose env carries `SUITE_CORRELATION_ID=X` and
  which calls `suite.mcp(...)` causes the recording server to receive a request
  whose `X-Correlation-Id` header is exactly `X` (alongside the unchanged
  `X-Owner-Id` and `X-Client-Id: scripts:<script_id>`); with
  `SUITE_CORRELATION_ID` unset the same call arrives carrying **no**
  `X-Correlation-Id` header at all (not an empty one).
- R-4W7K-0O3J — the same propagation holds for the other two suite surfaces: a
  probe calling `suite.fetch(content_url, dest)` and a probe calling a
  `suite.files` verb each cause their recording server to receive
  `X-Correlation-Id: X`, so no suite surface is a hole in the chain. (A build
  that wired only `suite.mcp` fails this.)
