# Decision 40 — Seeding existing scripts into the plane, then retiring the `body` column

> **Production data.** `scripts/state/` holds live customer data
> (`root project/design/D05.md`): no row may be dropped and no body may be lost.
> This Decision is the whole reason D35's migration was additive.

**Problem.** Every script that exists today lives only in `scripts.body`. The
plane cannot be the definition until each of those bodies is a commit on its
own repository, and the column cannot go until that has actually happened —
on the live box, not merely in principle. A migration cannot do it: creating a
repository and committing to it is a loopback call, not SQL.

**Decision.** A **boot-time seeding sweep**, then — in a *later release* — a
guarded migration that drops the column.

1. **The sweep.** `Service.SeedRepos(ctx)` runs from `registerRoutes` after the
   crash-recovery sweep and before the service serves. For each row with
   `repo_seeded_at IS NULL`, in id order:
   - derive and persist `name_key` if it is NULL (D35's rule and its real
     UNIQUE index arbitrate collisions among legacy names);
   - `Plane.Create(repoKey, "scripts:"+id)` — an `ErrConflict` (the repository
     already exists, e.g. a sweep that died after creating) is **not** an
     error: it means the precondition already holds, and the sweep proceeds;
   - `Plane.Commit(repoKey, {"main.py": row.Body}, "seed from scripts", …)`;
   - stamp `repo_seeded_at`.

   It is **idempotent** (a stamped row is never visited again — a second boot
   makes zero plane calls) and **non-fatal**: any row that fails is logged with
   its id and left unstamped, the sweep continues with the next row, and boot
   proceeds. An unreachable repos must not keep the service down; the row is
   retried on the next boot.

2. **A commit is not a substitute for the column.** Until §3 ships, `body`
   remains written by `create`/`update`/`import` (D37) and remains the sweep's
   input. This is a deliberate, bounded double-write: the column is *never
   read* to execute (D38) or to answer `get` (D37), so it cannot drift into
   anything observable — it is a dated backup with a scheduled deletion.

3. **The retiring migration, guarded.** A second timestamped migration
   (`bin/create-migration scripts retire_body`) drops the column, but refuses
   to run on a database where any row is still unseeded:

   ```sql
   -- Abort the migration (and the boot) if any script has not reached the
   -- plane: dropping body then would destroy the only copy of its content.
   CREATE TABLE _seed_guard (ok INTEGER NOT NULL CHECK (ok = 1));
   INSERT INTO _seed_guard(ok)
     SELECT CASE WHEN EXISTS (SELECT 1 FROM scripts WHERE repo_seeded_at IS NULL)
                 THEN 0 ELSE 1 END;
   DROP TABLE _seed_guard;

   ALTER TABLE scripts DROP COLUMN body;
   ```

   The failing `CHECK` surfaces as a migration error, which the appkit runner
   reports and which stops the deploy — loudly, before data is lost. The same
   phase deletes the sweep (its input is gone), stops `create`/`update`/`import`
   writing the column, and makes `name_key` effectively mandatory on new rows.

4. **Release ordering is a deploy constraint, not just a phase order.** §1 must
   be *running in production* — and every row stamped — before §3 is deployed.
   The plan therefore places them in separate phases, and the guard in §3 makes
   a premature deploy fail safely rather than quietly.

**Rejected.**
- **Seeding inside the migration.** SQL cannot make a loopback call; a Go
  migration hook would put HTTP, retries, and peer availability inside the
  migration runner, where a failure means the service will not boot.
- **A one-shot `opsctl`/CLI seeding command.** A step someone must remember to
  run, on a box where forgetting costs the `body` column its only reader. The
  sweep runs every boot and is free once stamped.
- **Dropping `body` in the same migration that adds the columns.** The bodies
  would be gone before anything had committed them — the exact data loss this
  Decision exists to prevent.
- **Making the sweep fatal on failure.** A repos outage would become a scripts
  outage at boot, for a background migration task.
- **Trusting phase ordering instead of the SQL guard.** Phases order *building*,
  not *deploying*; the guard is the only thing that holds on a real box.

**Verification** (real substrates: sweep claims drive the real `SeedRepos` over
a real temp-file SQLite database seeded with pre-conversion rows and a recording
fake `VersionPlane` that can be made to fail; migration claims apply scripts'
full embedded migration set through the appkit runner to a fresh real SQLite
database and read back `PRAGMA table_info` plus row contents).

- R-2W7Z-MXQR — the sweep seeds and stamps: over a database holding two rows
  with non-empty bodies and NULL `repo_seeded_at`, `SeedRepos` issues one
  `Create` and one `Commit` per row whose `main.py` content is **byte-identical**
  to that row's stored `body`, and afterwards both rows carry a non-NULL
  `name_key` and `repo_seeded_at`, with **no row deleted or altered otherwise**.
  A second `SeedRepos` on the same database issues **zero** plane calls.
- R-2XFW-0PHG — the sweep is idempotent under partial failure and non-fatal: a
  plane whose `Create` returns `ErrConflict` for a row still commits and stamps
  that row (an existing repository is a satisfied precondition), a plane whose
  `Commit` fails for one row leaves **that** row unstamped while the other row is
  stamped and `SeedRepos` returns without error (boot proceeds), and a
  subsequent sweep with a healthy plane stamps the previously failed row.
- R-2YNS-EH85 — the retiring migration is guarded: applied to a database where
  every `scripts` row is stamped, it succeeds and `PRAGMA table_info(scripts)`
  shows **no `body` column** while every row survives with its `id`, `owner_id`,
  `name_key` and `repo_seeded_at` intact; applied to a database holding one
  **unstamped** row, the migration **fails** (the guard aborts; the error
  surfaces from the runner) and the `body` column and its content are still
  there. Every previously committed migration remains byte-identical to its
  frozen body.
