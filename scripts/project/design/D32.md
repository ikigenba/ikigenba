# Decision 32 — Rebuild to adopt: chain continuation across the consumer fan-out, the ctx-bearing `Append`, the origin at spawn, and the recorded boundary of a run

> **⛔ EXTERNAL ORDERING (operator-sequenced, not built by any scripts phase).**
> This Decision consumes **both** chassis revisions and cannot build before they
> land:
> - **eventplane** — `eventplane/correlation` (D6), the `correlation_id` outbox
>   column + wire envelope field and the ctx-bearing
>   `Append(ctx, tx, ev)` (D7), the chain the consumer engine installs on the
>   handler's context (D8), and the `eventplane/observe` hook (D9).
> - **appkit** — the correlation middleware, the telemetry recorder and its
>   root-start helpers, MCP-dispatch and plain-HTTP request instrumentation,
>   lifecycle records, and the publish/consume observation hooks it injects.

**Decision.** Most of scripts' telemetry arrives **free, by rebuilding against
the new chassis**: inbound MCP tool calls (`request`, `mcp:<tool>`), the landing
page and static assets (`request`), the `start`/`stop` `lifecycle` pair, and the
`publish`/`consume` hops on the event plane — none of which scripts writes a
line for. Four things do **not** arrive free.

### 1. The chain survives the consumer's detached fan-out

eventplane hands the handler a context already carrying the delivered event's
chain (propagated when the envelope carried one, a fresh root per delivery when
it did not — D8), and appkit's consumer wrapper names that origin with a `root`
record when the envelope was uncorrelated. scripts' handler then does the one
thing that would throw it away: it fans out to **detached goroutines** on
`context.Background()` so a fired run outlives the engine's delivery. The
detached context is therefore re-seeded from the handler's:

```go
// internal/consume/consume.go — inside the fan-out loop.
corr := correlation.FromContext(ctx)          // the delivered event's chain
go func(scriptID string) {
    fireCtx := correlation.WithContext(context.Background(), corr)
    if err := fire(fireCtx, scriptID, source, ev.Kind, ev.Subject, ev.ID, ev.Payload); err != nil { … }
}(scriptID)
```

**The value to carry is the context's, never `ev.CorrelationID`.** The delivered
`consumer.Event` also gains a `CorrelationID` field, but it reports the **wire**
fact verbatim and is `""` in exactly the case the engine minted a root for this
delivery — so a fan-out that re-seeded from the event field would silently
orphan precisely the runs that root a chain, while compiling and looking
correct. `correlation.FromContext(ctx)` is always non-empty and always valid.

`FireFunc`'s signature is unchanged — the chain rides the context that path
already carries — so the `Spec.Consumers` wiring (D11), the five upstream
Handlers, the fire-and-forget contract, and the `ErrSkip` poison rule are all
untouched. `newRun` then applies D29's one rule, and because the engine always
installs an id, an event-fired run always **continues** a chain rather than
rooting one. The fan-out is per script: five scripts matching one event all run
on the **one** chain the event carried, which is the correct causal reading —
one upstream fact caused five runs.

### 2. The producer emits on the run's chain

`Append` becomes ctx-populated and the outbox grows a `correlation_id` column,
so scripts' single emission path is compile-caught:
`FinishRun` → `completionEvent` → `outbox.Append(ctx, tx, Event{Kind, Subject,
Payload})`, still on the **same transaction** as the run's terminal-state write
(at-most-once per run, cancelled-emits-nothing — D18, unchanged).

The context that reaches `FinishRun` is the runner's, deliberately detached from
whatever started the run, so it carries no chain. `FinishRunInput` therefore
gains one field, `CorrelationID`, filled by the runner from the `script.Run` it
already holds, and `FinishRun` wraps its own context with it before appending:

```go
// internal/script/store.go — inside FinishRun, before Append.
actx := correlation.WithContext(ctx, in.CorrelationID)
… s.Outbox.Append(actx, tx, ev) …
```

So `scripts:succeeded/<name>` carries the chain of the run that produced it, and
a downstream consumer — notify, another script, a prompt — continues that chain
instead of starting a new one. A script fired by a webhook delivery and a script
fired by that script's success are then one reconstructible chain, end to end.

**Schema.** eventplane's revised `outbox.SchemaSQL` is re-applied by each
producer through its own runner: scripts appends **one new timestamped
migration** minted with `bin/create-migration scripts outbox_correlation` that
drops and recreates the outbox table per the revised constant verbatim (a
`DROP TABLE`/`DROP INDEX` preamble + the constant's DDL) — outbox rows are
disposable retention data inside the migration window. The frozen
`004_outbox.sql` and the D18 `outbox_routing` migration are **not** touched; the
DDL drift guard (`internal/db/migrations_outbox_test.go`) re-points at the
**newest** outbox migration. This mirrors exactly the handling D18 established.

### 3. Naming the origin at spawn

When a run has no inbound chain at all (D29's fallback — the run's own ULID
becomes the chain id), the origin is established through **appkit's root-start
helper**, consumed as an external fact: one call adopts the durable root id,
returns a context carrying it, and emits the `root` record with op
`run:<run-id>`. scripts mints no chain ids, builds no records, and never talks
to the recorder directly. When the run inherits a chain — which is **both live
paths today**, the MCP request context and the consumer's re-seeded context —
the helper is not called: the chain already has an origin, and a second root
would falsify which one started it.

The seam is a narrow injected function, so the domain imports no chassis
telemetry type and tests observe the decision directly:

```go
// internal/script — injected by the composition root, which binds it to the
// chassis root-start helper (adopt-or-mint + ctx + `root` record). nil returns
// ctx unchanged, so telemetry-disabled builds and every existing test are
// unaffected.
type RootStarter func(ctx context.Context, rootID, op string) context.Context
```

*This is scripts' one requirement on the helper's contract: it must accept a
**caller-supplied durable root id** and mint only when the caller has none. A
helper that always minted would put two ULIDs on one origin and contradict
`project/design/D14.md` at the repo root's published durable-root rule. prompts states the
identical requirement for its runs; a mismatch here is a cross-workspace finding
to surface, not to work around in this workspace.* What is proven here is
scripts' half — *whether and with what* the helper is called — never the
helper's own behavior, which is appkit's coverage. Rooting is best-effort by the
chassis contract: a failed or disabled recorder never fails a spawn.

### 4. The recorded boundary of a run — what is deliberately NOT recorded

A run's **boundary** is recorded: the spawn (the inbound `request` that caused
it, or the `root` above), every call the script makes back into the suite
through the `suite` module (recorded by the **callee**, on the run's chain —
D30), the outcome event (`publish`), and the run's own terminal row. The run's
**inside** is not: the Python code's own logic, its files, its subprocesses, and
its network calls to anything outside the suite produce **no** telemetry
records.

That is not an omission, it is the boundary the suite drew: a script is the
owner's own code running with the service's full local authority, and recording
its internals would mean recording arbitrary third-party traffic in a store
designed for skeletons. scripts already keeps the inside — the run row's status,
exit code and error, the captured `stdout`/`stderr`, and the whole persisted run
dir, addressable afterwards by `run_fs_list`/`run_fs_read` and `content_url`
(D25) — and the run's `correlation_id` (D29) is the pivot from a chain to that
record. Telemetry points at the run; the run holds the inside.

**Rejected.**
- **Extending `FireFunc` with a correlation-id parameter.** Every entry in the
  `Spec.Consumers` table and the fan-out contract would move to carry a value the
  context already carries end to end; the re-seed is two lines at the one place
  the context is deliberately broken.
- **Letting a fired run mint a fresh chain and ignore the event's id.** It
  severs the trail at exactly the interesting hop — the thing that caused the run
  is one feed away — and defeats the whole capability for triggered work, which
  is most of what scripts does.
- **Threading the chain id into `Append` as an explicit argument.** The
  eventplane contract populates it from context; passing it twice invites the two
  to disagree.
- **Reading the run's chain id back from SQL inside `FinishRun` instead of
  carrying it on `FinishRunInput`.** An extra query on the terminal write's hot
  path to recover a value the runner already holds in memory, and it would make
  the atomic terminal write depend on a prior read.
- **Emitting a `root` record for every run, inherited or not.** Two origins on
  one chain; a forensic reader could not tell which actually started it.
- **Recording the script's own third-party network calls as `outbound`.**
  scripts cannot see them — they are made by a `python3` child over its own
  socket, not by scripts' Go code — and the suite's stated exclusion puts them
  out of scope deliberately.
- **Recording `publish`/`consume` hops from scripts' own code.** eventplane
  exposes the observation hook and appkit injects the recorder; a service-side
  hand-rolled record would duplicate every hop.

**Verification** (real substrates: the consume claims drive the real
`consume.Handler` over the real `script.Service` + `Store` on a temp-file SQLite
database built by the full embedded migration set; the outbox claim reads a real
SQLite outbox row back by SQL after a real `FinishRun`; the origin claim
observes the injected `RootStarter`; the boundary claim runs the real `python3`
probe harness. None of these can pass against a stub — each reads a value out of
a real substrate or counts real observations).

- R-4XFG-EFU8 — an event delivered to `consume.Handler` on a handler context
  carrying correlation id `X` fires a run whose stored `correlation_id`, read
  back by SQL, is exactly `X` — proving the id survives the detached fan-out
  goroutine; a build that fires on a bare `context.Background()` stores the run
  id instead and fails. When the same event matches **three** scripts, all three
  run rows carry `X`. And for a delivery whose envelope carried **no** chain —
  where the engine minted the root onto the handler context, so
  `ev.CorrelationID == ""` while the context's id is valid — the fired run stores
  that **context** id, not an empty string and not the run id: an implementation
  that re-seeded from `ev.CorrelationID` fails here and nowhere else.
- R-4YNC-S7KX — after `FinishRun` lands a succeeded run whose row carries
  correlation id `X`, the real SQLite outbox holds exactly one row for that run
  whose `correlation_id` column is exactly `X` (not empty, not the run id),
  appended on the same transaction as the terminal-state write; a cancelled run
  still emits no row at all.
- R-4ZV9-5ZBM — the injected `RootStarter` observes **exactly one** call for a
  run spawned on a context carrying no chain, with `rootID` equal to that run's
  own id and `op` exactly `run:<run-id>`; for a run spawned on a context already
  carrying chain `X` it observes **zero** calls, and the run still stores `X`.
- R-5135-JR2B — the boundary holds: a run whose probe script performs a real
  HTTP call to a **non-suite** `httptest` server and writes a file into its run
  dir produces **no** telemetry observation naming that call (the run's total
  observed origin calls remain the single spawn), while the run's captured
  `stdout` and its persisted run dir **do** contain the evidence of both — the
  run record holds the inside, telemetry holds only the boundary.
