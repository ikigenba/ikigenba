# Decision 37 — The write path: every authoring verb is a commit; `get` reads `main`

**Problem.** With the repository as the definition (D35) and a client to reach
it (D36), the authoring verbs must change what they *mean*: `create` must bring
a repository into existence, `update` must produce a commit, a renamed script
must carry its repository along, `delete` must archive rather than erase, and
`get` must answer with what is actually live. Done wrong this is where the two
copies drift.

**Decision.** `internal/script/service.go` grows a version-plane leg on each
write verb; the row keeps metadata only.

1. **`create`** — derive `name_key` (D35), insert the row (with `name_key`,
   `repo_seeded_at` NULL, and `body` still written so the row is
   self-describing until D40 retires the column), then `Plane.Create(repoKey,
   "scripts:"+id)` and `Plane.Commit(repoKey, {"main.py": body}, "create <name>",
   "scripts:"+id)`, then stamp `repo_seeded_at`. **Insert first** so the real
   UNIQUE index (D35) arbitrates the key before a repository is made under it.
   If the plane fails, the just-inserted row is **deleted** and the verb returns
   the mapped error (typically `source_unavailable`): a caller never gets a
   script id for a script that does not exist in the plane.

2. **`update`** — two independent legs, both in the one call:
   - **content**: a supplied `body` becomes
     `Plane.Commit(repoKey, {"main.py": body}, "update <name>", "scripts:"+id)`;
     an omitted `body` commits **nothing** (no empty commits).
   - **name**: a supplied `name` whose derived key differs from the stored
     `name_key` calls `Plane.Rename(oldKey, newKey, …)` and writes the new
     `name_key` on the row; a name whose slug is unchanged (`"Nightly Export"` →
     `"nightly export"`) issues **no** rename call.

   Neither owner column is ever rewritten (D28 §3, unchanged).

3. **`import`** — unchanged in every respect the owner sees (fetch the Dropbox
   mirror bytes over loopback, UTF-8 + size validation, upsert on
   `(owner_id, source_path)`) and additionally commits the fetched bytes as
   `main.py`. An import that upserts an **existing** row commits onto that row's
   existing repository; an import that inserts a new row creates the repository
   first, exactly as `create` does.

4. **`delete`** — the tombstone semantics are unchanged (the row and its
   triggers go; run history and on-disk run artifacts survive) and the verb
   additionally calls `Plane.Delete(repoKey, …)`, which under
   `root project/design/D24.md` **archives** the bare repository rather than
   destroying history. A plane failure here does **not** block the delete: the
   row is removed and the failure is logged — an unreachable custodian must not
   pin a script the owner asked to be rid of, and an unarchived repository is
   recoverable by an operator while a half-deleted row is not.

5. **`get` reads the plane; `list` does not.** `Get` populates `Script.Body`
   from `Plane.ReadFile(repoKey, "main", "main.py")` — the tip of `main` is what
   would run, so it is what the owner is shown. `List` leaves `Body` **empty**
   and performs **zero** plane calls: listing N scripts must not fan out into N
   loopback reads, and no caller needs N bodies at once. `run_*` verbs are
   untouched.

6. **No materialized copy — a recorded deviation from
   `root project/design/D24.md`.** That contract has each owning service keep a
   materialized copy of `main` under its own `state/`, refreshed on
   `repos:push`, because the service *serves or executes* from it. scripts does
   neither: every run executes from a **fresh clone pinned to a sha** (D38), so
   the contract's actual requirement — never serve or execute out of repos'
   tree — is satisfied without a copy. A copy would exist solely to answer
   `get`'s body field, and would buy a cache, a refresh consumer, and a staleness
   bug in exchange for one loopback read per `get`. scripts therefore keeps no
   materialized copy and reads on demand.

**Rejected.**
- **Writing the row and the commit in "one transaction."** There is no shared
  transaction across a SQLite write and a loopback HTTP call, and pretending
  otherwise hides the failure mode. The compensating delete in §1 is the honest
  version: exactly one observable outcome (script exists in both, or in
  neither).
- **Blocking `delete` on the plane.** See §4 — it converts a peer outage into an
  undeletable script.
- **Keeping `body` authoritative and committing asynchronously.** An async
  mirror is the drifting second copy D35 rejected, with a queue added.
- **Populating `Body` in `list`.** N loopback reads per list call, on the
  hottest verb, for a field nobody reads N of.
- **Refusing `update` when the tree has files other than `main.py`.** A tree is
  the point; committing `main.py` beside a helper module the author pushed is
  exactly the intended behavior, and a guard here would make the MCP surface and
  the git door disagree about what a script may contain.
- **A separate `rename` tool.** The name lives on `update`; a second verb would
  give the same fact two doors.

**Verification** (real substrates: every claim drives the assembled
`appkit/mcp` handler — the D13/D19/D28 harness — over a real `script.Service` on
a temp-file SQLite DB, with a **recording fake `VersionPlane`** that captures
every call in order and can be made to fail; the DB assertions are real SQL
reads).

- R-2BHP-4U4Y — `create` produces exactly one `Create` and one `Commit`, in that
  order, on key `scripts/<derived name_key>`, whose files map is exactly
  `{"main.py": <the submitted body>}` and whose attribution is
  `scripts:<new script id>`; the stored row carries that `name_key` and a
  non-empty `repo_seeded_at`.
- R-2CPL-ILVN — when the plane fails `create` (returning
  `ErrSourceUnavailable`), the tool returns the `source_unavailable` structured
  error **and the `scripts` table holds zero rows** — the compensating delete
  ran, so no orphan row survives. An implementation that leaves the row fails it.
- R-2DXH-WDMC — `update` with a new `body` issues exactly one `Commit` carrying
  that body and **no** `Rename`; `update` with only a `name` whose slug changes
  issues exactly one `Rename` from the old key to the new key (and updates the
  row's `name_key`) and **no** `Commit`; `update` with a name whose slug is
  unchanged (`"Nightly Export"` → `"nightly export"`) issues **neither**.
- R-2F5E-A5D1 — `import` of a new `source_path` issues `Create` then `Commit`
  with the fetched mirror bytes as `main.py`; re-importing the **same**
  `source_path` for the same `owner_id` issues **no second `Create`** and one
  `Commit` onto the same key, and still upserts the one row (no duplicate).
- R-2GDA-NX3Q — `delete` issues exactly one `Delete` on the script's key and
  removes the row; and when the plane's `Delete` fails, the tool still
  **succeeds** and the row is still gone (the outage does not pin the script).
- R-2HL7-1OUF — `get` returns a `body` equal to what the plane serves for
  (`main`, `main.py`) — not the stored `body` column: with the fake serving
  content that differs from the column, the result carries the plane's content.
- R-2IT3-FGL4 — `list` over three scripts performs **zero** plane calls and
  returns entries whose `Body` is empty, while every other `Script` field
  (id, name, owner, timestamps) is present.
