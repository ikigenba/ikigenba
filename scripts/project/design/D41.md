# Decision 41 — Outbox schema convergence: the `outbox_correlation` rebuild migration, the restored frozen body, and the migration-immutability guard

**Problem.** D32 requires the outbox table to carry a `correlation_id` column
and ordered it realized as **one new timestamped migration**. What the tree
carries instead is an in-place edit of the already-committed
`20260712192242_outbox_routing.sql` — exactly the violation the suite's
migration rule forbids. The appkit runner keys on version and silently skips an
edited body, so the two lineages have diverged: a **fresh** database (every
test database) has the column, while a database that applied the *original*
body before the edit — the deployed one — does not. On that lineage every
`outbox.Append` and every feed fetch fails with
`no such column: correlation_id`; because `FinishRun` appends the completion
event on the same transaction as the terminal write (D18/D32), the failed
append rolls back the terminal write too, so **every run is left `running`
forever and scripts publishes nothing**. This Decision converges the lineages
and adopts the suite's mechanical guard so the violation class cannot recur.

**Decision.**

1. **The frozen body is restored.** `20260712192242_outbox_routing.sql` is
   restored to its original committed body, byte-identical — sha256
   `9348de0c347feaa2f9ce74c90d53c9fcf17eed56fd66538e528c8f729b46eb38`
   (recoverable as `git show 1e26ba16^:` that path). The restore changes
   nothing on any database (both lineages have that version recorded as
   applied); it makes the version→body mapping truthful again.

2. **One new rebuild migration converges both lineages.** A new timestamped
   migration, minted with `bin/create-migration scripts outbox_correlation`,
   whose entire body is a drop-and-recreate to the library constant:

   ```sql
   DROP INDEX IF EXISTS idx_outbox_created_at;
   DROP TABLE IF EXISTS outbox;
   ```

   followed by `eventplane`'s `outbox.SchemaSQL` verbatim. Drop-and-recreate
   is correct here because outbox rows are disposable retention data (the D32
   rationale, unchanged): the migration window is a deploy restart, retention
   would trim the rows anyway, and consumers survive an epoch change by
   design. The same body lands identically on the deployed lineage (drops the
   column-less table) and on a fresh lineage (drops the already-revised
   table), so after this migration every database has one byte-identical
   outbox schema.

3. **The DDL drift guard resolves its target by name order.** Per the suite
   contract (`root project/design/D25.md` §4), the guard in
   `internal/db/migrations_outbox_test.go` no longer names a migration file:
   it selects the **lexically-greatest** migration filename containing
   `outbox` and asserts that file contains `outbox.SchemaSQL` verbatim
   (R-84Q9-6QMD's existing assertion, re-pointed). A future revision of the
   constant can then only be satisfied by adding a newer migration, never by
   editing history. The guard's frozen-legacy assertion on `004_outbox.sql`
   is unchanged.

4. **scripts adopts the migration-immutability contract.** Per
   `root project/design/D25.md`, the tree commits
   `internal/db/migrations.sha256` — one `<sha256-hex>  <filename>` line per
   embedded migration, sorted by filename — and a guard test that recomputes
   and compares with total set equality. The manifest line for
   `20260712192242_outbox_routing.sql` carries the restored original's hash
   above, so the manifest also pins the restoration. Adoption id:
   R-NFQ1-NA7N (`root project/design/D25.md`, [proof: per-service]).

Nothing else moves: `FinishRun`'s atomic terminal-write-plus-append (D18, D32),
the correlation plumbing (D29, D32), and the boot-time crash sweep are all
already correct — the sweep will mark the wedged `running` rows failed on the
first post-deploy restart with no new mechanism.

**Rejected.**

- **`ALTER TABLE outbox ADD COLUMN` (eventplane's `AddCorrelationIDSQL`).**
  Correct on the deployed lineage but fails on any database built from the
  edited migration, where the column already exists — SQLite has no
  `ADD COLUMN IF NOT EXISTS`. The rebuild body is lineage-independent.
- **Leaving the edited `20260712192242` body in place.** Functionally inert
  once the rebuild migration exists, but it leaves the committed history lying
  about what deployed databases ran, and the immutability manifest would then
  enshrine the violation's bytes as "frozen truth".
- **A one-off operator `ALTER` on the live box instead of a migration.** Fixes
  one database by hand, leaves the tree unable to reproduce it, and the next
  install diverges again. Schema state must be derivable from the migration
  set alone.
- **Reconciling the wedged runs with a new migration or admin tool.** The
  existing crash sweep already marks orphaned `running` rows failed at boot;
  new mechanism would duplicate it.

**Verification** (real substrates: both claims run the appkit migration runner
against real temp-file SQLite databases; the lineage claim constructs the
deployed history for real, not as a fixture description).

- R-NGXY-11YC — lineage convergence: a real SQLite database prepared by
  applying the **original** `20260712192242_outbox_routing.sql` body (the
  restored bytes, i.e. an outbox with **no** `correlation_id` column) with
  that version recorded as applied, then migrated with scripts' full current
  embedded set, ends with an `outbox` table whose columns match
  `outbox.SchemaSQL` (including `correlation_id`), and a subsequent
  `outbox.Append` on it succeeds. A migration set that only edits history
  (leaving the runner to skip the version) fails this — the deployed lineage
  stays broken.
- R-NJDQ-SLFQ — the restoration is byte-exact: the embedded
  `20260712192242_outbox_routing.sql` hashes to sha256
  `9348de0c347feaa2f9ce74c90d53c9fcf17eed56fd66538e528c8f729b46eb38` — the
  original committed body — so the edited variant (or any future edit) fails
  by hash, independent of the manifest file's own correctness.
