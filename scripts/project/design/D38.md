# Decision 38 — A run is a real clone pinned to a sha, with a run token in its environment

> **Suite adoption (operator-sequenced).** The run-token contract — short-lived,
> scoped to one repository, fetch plus push to **non-`main`** refs, presented as
> the HTTP Basic password at repos' git door — and the "no ambient merge" rule
> are `root project/design/D24.md`'s. scripts restates neither; it mints a token
> through the client seam (D36) and hands it to the run.

**Problem.** Today the runner reads the script's `body` **at exec time**
(`store.ScriptForRun` inside the goroutine) and writes it to `main.py`. An
`update` between spawn and exec silently changes what runs, so a run is not
reproducible and its own record does not say what it executed. With the
definition in git that hazard has a real fix: **pin a commit at spawn, and
execute a checkout of exactly that commit.**

**Decision.**

1. **The sha is resolved at spawn, on the caller's thread.** Before the run row
   is inserted, `Service.newRun` calls `Plane.Head(repoKey, "main")` and records
   the result on the row (`runs.repo_sha`, D35). It is exposed on the run wire
   shape as `repo_sha` (`Run.RepoSha string \`json:"repo_sha"\``), so
   `run_get`/`run_list` say precisely which commit ran. **A failed resolution
   creates no run**: the manual `run` verb returns the mapped error (typically
   `source_unavailable`) and `RunForEvent` returns it to the consumer, which
   logs and advances (its existing fire-and-forget posture, D17 §5). A run row
   that could never be honestly reproduced is worse than no run row.

2. **Materialization is a real `git clone`.** `internal/runner` replaces
   "mkdir + write `main.py`" with, in order (`internal/runner/git.go`, all with
   `GIT_TERMINAL_PROMPT=0` and the run's context so a TTL kills them):

   ```
   token, cloneURL := plane.RunToken(repoKey)          # short-lived, one repo
   git -c credential.helper=<helper> clone --quiet <cloneURL> <runDir>
   git -C <runDir> checkout --quiet --detach <sha>     # the pinned commit
   git -C <runDir> config credential.helper <helper>   # persisted for the run's own pushes
   git -C <runDir> config user.name  <script name>
   git -C <runDir> config user.email <owner email>
   ```

   where `<helper>` is the shell snippet
   `!f(){ echo username=run; echo "password=$SUITE_GIT_TOKEN"; };f` — it reads
   the token from the **environment**, so the token is never written into
   `.git/config` or any other file in the run dir. The pinned sha is always
   reachable: it was `main`'s head moments earlier and force-pushes to `main`
   are rejected by the plane. Any git step failing fails the run with that
   step's stderr as the run error, before the interpreter starts.

3. **Injected files sit beside the tree, and stay out of its status.** After the
   checkout the runner writes `suite.py` (0600) and `config.json` (0600) into
   the run dir exactly as before (D21 §2), and appends
   `suite.py`, `config.json`, `stdout.log`, `stderr.log` to
   `.git/info/exclude` — a **local** ignore, not a tracked `.gitignore`, so a
   workflow that runs `git add -A` commits its own work and none of ours, and
   the tree the author sees is the tree they pushed. `cmd.Dir` is the run dir,
   so `python3 main.py` runs at the tree root, `import suite` resolves, and
   sibling modules import normally.

4. **Git facts travel in the environment**, beside D21's `SUITE_*` set:

   - `SUITE_REPO_KEY` — the repository key (`scripts/<name_key>`);
   - `SUITE_REPO_SHA` — the pinned commit, identical to `runs.repo_sha`;
   - `SUITE_GIT_TOKEN` — the minted run token, so the run's own `git fetch`
     and `git push` (of non-`main` refs) work with no ceremony.

   A script therefore *is* a CI/workflow engine when its author wants one: it
   clones nothing extra, tests the checkout it is standing in, pushes a branch,
   and posts a status with `suite.mcp("repos", "status_set", …)`.

5. **Merging is authored, never ambient.** The runner performs no merge, no
   `push` of its own, and no cleanup push at the end of a run. A run's work
   reaches `main` only because its author wrote `suite.mcp("repos", "merge", …)`
   — the plane's rule, and here it is simply the absence of code.

6. **Run trees stay disposable.** They are already wiped and recreated at boot
   (`recreateRunsDir`) and that is unchanged — a run tree is now exactly
   reproducible from `(repo_key, repo_sha)`, which is the point of recording
   them.

**Rejected.**
- **Exporting the tree over HTTP instead of cloning** (an archive endpoint, or
  N `ReadFile` calls). It would give the run files without a repository: no
  `git log`, no branch to push, no way for a workflow to be a workflow. The
  plane's own answer is "runs perform real `git clone`/`push`".
- **Embedding the token in the clone URL** (`https://x:<token>@…`). git writes
  the remote URL into `.git/config`, so the token would land on disk inside a
  directory the owner can read through `run_fs_read` and `/run-content`. The
  env-reading credential helper keeps it out of every file.
- **Resolving the sha inside the runner goroutine.** That is the exact hazard
  being fixed, moved three lines down: the gap between spawn and exec would
  still be unpinned, and the failure would surface as a mysteriously failed run
  instead of a typed error on the verb the caller made.
- **`git fetch <sha>` into a bare-initialized dir instead of `clone` +
  `checkout --detach`.** Fetching an arbitrary sha needs the server to allow
  any-SHA1-in-want; clone-then-checkout works against a stock server and gives
  the run real refs to branch from.
- **A tracked `.gitignore` for the injected files.** It would be a commit
  scripts made into the author's tree, visible on their laptop forever, to
  describe a runtime detail. `.git/info/exclude` is local by design.
- **Deleting `.git` after checkout to keep run trees small.** It would take the
  push channel away to save bytes on a tree that is deleted at next boot.
- **An end-of-run merge or auto-push.** `root project/design/D24.md` places that
  intent in the author's text; the platform must not relocate it.

**Verification** (real substrates: the run-lifecycle claims exec **real
`git`** against a **real bare repository on disk** reached by a `file://` remote
(the local git transport — real objects, real refs, real sha resolution), with
the run executed by the real runner under real `python3` (the D21 probe harness);
the token/clone-URL pair is supplied by a fake `VersionPlane` pointing at that
bare repo. `git` on `PATH` is a declared environmental precondition (D34) — its
absence fails these tests, never skips them.)

- R-2K0Z-T8BT — a spawned run records the pin: the `runs` row's `repo_sha`
  equals the plane's reported head at spawn, and `run_get`/`run_list` through
  the assembled MCP handler expose it as `repo_sha`. A run row with an empty
  `repo_sha` fails it.
- R-2L8W-702I — the run dir is a **real git working tree at exactly the pinned
  commit**: `git -C <runDir> rev-parse HEAD` equals `repo_sha`, `git -C <runDir>
  symbolic-ref -q HEAD` fails (detached), and both a root `main.py` **and a
  supporting module committed beside it** are present with byte-identical
  committed content — and the running script successfully `import`s that module
  (proving the tree, not just the file, is what executes).
- R-2MGS-KRT7 — the pin beats a later commit: after the sha is resolved and
  **before** the clone happens, a new commit lands on the remote's `main`
  replacing `main.py`; the run nevertheless executes the **pinned** content
  (the probe's `stdout.log` carries the old file's marker, never the new one).
  An implementation reading the body at exec time, or cloning `main`'s tip
  without the detached checkout, fails it.
- R-2NOO-YJJW — injection and cleanliness: the run dir carries `suite.py`
  byte-identical to the embedded source and a `config.json` holding the row's
  config; the probe observes `os.getcwd()` equal to the run dir and imports
  `suite` successfully; and after the run, `git -C <runDir> status --porcelain`
  lists **none** of `suite.py`, `config.json`, `stdout.log`, `stderr.log`.
- R-2OWL-CBAL — git facts reach the child and the token reaches no file: a probe
  printing `SUITE_REPO_KEY`, `SUITE_REPO_SHA`, and `SUITE_GIT_TOKEN` emits
  exactly `scripts/<name_key>`, the pinned sha, and the minted token; a
  recursive scan of every file under the run dir (`.git/` included) finds the
  token value in **none** of them; and `git -C <runDir> config
  credential.helper` returns a helper whose text names `SUITE_GIT_TOKEN`.
- R-2RCE-3URZ — a run can push, and nothing merges by itself: a probe whose body
  is `git push origin HEAD:refs/heads/wip` succeeds, the **real** bare remote
  afterwards has `refs/heads/wip` at the pinned sha, and the remote's `main` is
  **still** at the commit it was at before the run — the runner performed no
  merge and no push of its own.
- R-2SKA-HMIO — a plane that fails `Head` yields **no run**: the manual `run`
  tool returns the `source_unavailable` structured error and the `runs` table
  holds zero rows for that script, and `RunForEvent` returns the error to its
  caller having inserted nothing. An implementation that records a failed run
  row fails it.
