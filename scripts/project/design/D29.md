# Decision 29 — `runs.correlation_id`: mint-or-inherit at spawn, stored on the run, exposed on the run surface

> **⛔ EXTERNAL ORDERING (operator-sequenced, not built by any scripts phase).**
> This Decision consumes the stdlib-only leaf package
> **`eventplane/correlation`** — `Header` (`X-Correlation-Id`), `New()` (a bare
> 26-character Crockford-base32 ULID), `Valid`, `WithContext`, `FromContext`,
> `Ensure` — specified in `eventplane/project/design/` (its D6) and realized by
> eventplane's telemetry phases, together with **appkit**'s read-or-mint
> request middleware that puts the inbound chain id on every served request's
> context. scripts consumes those accessors as a fixed external contract and
> never re-implements them: `internal/ids` keeps minting **run** ids and does
> not mint chain ids. Both must be **BUILT before this Decision's phase runs**.

**Problem.** A run is where a chain goes quiet. The owner (or an upstream
event) causes a run, the run does work across several services over minutes,
and today nothing on the run row says which causal chain it belongs to. A
forensic reader holding a chain id cannot find the run; a reader holding a run
cannot find the chain. Everything else scripts needs for telemetry arrives free
from the chassis — this is the one fact only scripts can record, because only
scripts knows a run exists.

**Decision.** The chain id becomes a first-class, indexed **column on the run
row**, assigned once at spawn by one rule that every start path shares.

**One rule at spawn.** `Service.newRun` is the single constructor for both start
paths (`Run`, the manual MCP verb, and `RunForEvent`, the consumer path), so
the rule lives there and takes the context both callers already have:

```go
// internal/script/service.go — newRun gains a ctx parameter.
func (s *Service) newRun(ctx context.Context, scriptID, source, kind, subject, eventID string) Run {
    runID := ids.NewULID()
    corrID := correlation.FromContext(ctx)
    if corrID == "" {
        corrID = runID // durable-root reuse: the run IS the root (project/design/D14.md at the repo root)
    }
    …
}
```

- **Manual run** — the chassis middleware has already placed the inbound MCP
  request's chain id on the request context (nginx-supplied at the edge, per
  D31, or a loopback peer's), so the run **continues** the caller's chain. The
  user's `run` tool call and everything the run then does read back as one
  chain, which is the whole point.
- **Event-fired run** — the consumer re-attaches the delivered envelope's chain
  id onto the detached fire context (D32), and this same line reads it.
- **No inbound chain** — nothing is minted: the run's own ULID **is** the
  correlation id. A run that roots a chain and the chain share one identifier,
  so "resolve a chain id to the run" is a primary-key lookup and there is no
  second ULID to keep in sync. The `root` telemetry record for exactly this
  case is D32's.

This mirrors prompts' rule verbatim (its D39) — deliberately, because the two
run-spawning services must not disagree about what a run's chain id means.

**Storage — one new timestamped migration**, minted with
`bin/create-migration scripts correlation_id` (never a hand-picked number),
purely additive so no table is rebuilt, nothing is lost, and no frozen
migration is touched:

```sql
ALTER TABLE runs ADD COLUMN correlation_id TEXT NOT NULL DEFAULT '';
CREATE INDEX idx_runs_correlation ON runs (correlation_id);
```

`''` on a pre-migration row means "started before chains existed" and is never
confusable with a real id, which is always 26 characters. `InsertRun` writes the
column; every `SELECT` in `Store` that builds a `Run` reads it, and `scanRun`
gains the field.

**Model and MCP surface.** `script.Run` gains
`CorrelationID string \`json:"correlation_id,omitempty"\``, so `run`,
`run_get`, and `run_list` report it, and `run_list` accepts an optional
`correlation_id` argument filtering to exactly the runs on that chain (its
structured output schema, D19, gains the field; its input schema gains the
argument). That argument is the forensic pivot from scripts' side: telemetry
answers "which chain", scripts answers "which run of which script, with what
outcome", and the run dir holds what the run actually produced.

**Rejected.**
- **Deriving the chain id from the run id (no column).** Correct only for a run
  that roots its own chain; a run continuing an inbound chain — the manual-MCP
  and event-fired cases, i.e. the interesting ones — would have nowhere to
  record it.
- **Minting a fresh chain id for a root run.** Two ULIDs naming one origin, both
  stored, both needing to agree, for no gain — and it contradicts the
  durable-root-reuse rule `project/design/D14.md` at the repo root already publishes.
- **Rebuilding the `runs` table to place the column.** `ALTER TABLE … ADD
  COLUMN` with a `NOT NULL DEFAULT ''` is additive, instant, and loses nothing;
  a rebuild would drop run history for no benefit and touch a frozen migration's
  territory.
- **Keeping the id out of the MCP surface (store-only).** A stored-but-hidden
  column forces a forensic reader to open the SQLite file to cross from a chain
  to a run, which is exactly the "ask the box, not the disk" property the
  capability exists to provide. prompts exposes it; a divergence here would make
  the same question answerable in one service and not the other.
- **Reusing `trigger_event_id` as the chain handle.** It names the one event
  that fired this run, not the chain — a chain spans many events across many
  services, and a manual run has no triggering event at all.

**Verification** (real substrates throughout: migration and storage claims apply
scripts' **full embedded migration set** through the appkit runner to a fresh
real SQLite database and read rows back by SQL; MCP claims drive the assembled
`appkit/mcp` handler. A mocked store could not falsify any of these).

- R-4OW5-Q1ND — applying scripts' full embedded migration set to a fresh real
  SQLite database yields a `runs` table carrying a `correlation_id` column with
  index `idx_runs_correlation` present, while every frozen committed migration
  (`002_scripts.sql`, `004_outbox.sql`, and the committed timestamped set)
  remains byte-identical to its committed body.
- R-4Q42-3TE2 — a run started through `Service.Run` on a context carrying **no**
  correlation id persists `correlation_id` **exactly equal to that run's own
  id**, read back by SQL — not empty, and not a second distinct 26-character
  ULID (an implementation that mints a fresh chain id fails this).
- R-4RBY-HL4R — a run started on a context carrying correlation id `X` (a valid
  26-character Crockford id, different from any run id) persists
  `correlation_id == X`, and that value is **not** the run's id — the inbound
  chain is continued, never replaced.
- R-4SJU-VCVG — through the assembled MCP handler: `run_get` returns the run's
  `correlation_id`, and `run_list` given `correlation_id: X` returns exactly the
  runs stored with `X` and omits a run on a different chain and a run whose id
  is empty; the advertised input schema carries the `correlation_id` argument
  and the output schema carries the field.
