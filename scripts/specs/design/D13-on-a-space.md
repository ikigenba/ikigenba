# D13-on-a-space

What scripts itself contributes when it runs on a space and in a sandbox, and what it does not. The package story (`S23-package.md`), the Python stories (`S22-python.md`), the space stories (`S24-on-a-space.md`) and the sandbox stories (`S25-in-a-sandbox.md`) prove the whole path from a checkout to a browser, curl and an agent, and almost every step on that path belongs to someone else: devctl builds and ships the file, opsctl installs it, writes the environment, publishes the socket, bounds the unit, keeps and replicates the database and generates nginx, the space's first boot installs `git` and `python3.12`, auth decides every credential and whether a request reaches scripts at all, the host's nginx terminates TLS, sends a guest to sign in and challenges `/mcp`, the mcp gateway relays tool calls, repos holds the repositories, and the sandbox stands the same arrangement up on a developer's machine. scripts' own share is what the earlier designs already state — the layout, the run seam, the paths and the Python declaration (`D01-layout-and-run-seam`), the command and the manifest (`D02-cli`), the serve path and its start checks (`D03-serve`), the catalog (`D04-store`), git and the repositories (`D05-git-and-source`), the process (`D06-runner`), the run core and a script's environment (`D07-runs`), the pages (`D08-pages`), the run files (`D09-run-files`), the trail (`D10-trail`), the tools (`D11-tools`) and the settings and limits (`D12-limits`) — plus one guarantee the space and sandbox stories lean on that no single earlier document owns: the credential a caller presents never lands in anything scripts records or keeps, nor in the environment of a script it runs. This design states that guarantee, records where scripts departs from sites' shape, maps every outcome of those stories to the design that covers it, and says plainly what can be checked only on a running space or sandbox.

This design declares no name. Everything it states is behaviour of names `D01-layout-and-run-seam` declares: `cli.Process` and `cli.Run`, and the `Sink`, `Stderr`, `Dir`, `Database`, `LookupEnv` and `Environ` fields of `cli.Process`. It mentions `runner.PythonVersion` and `runner.Interpreter` (`D01-layout-and-run-seam`, R-8VHE-9O35) and the variable `IKIGENBA_OUT_DIR` (`D07-runs`, R-XBLK-US05) without restating them.

## What ships

The package story lists three members of the release file: `bin/scripts`, `etc/manifest.toml` and `share/icon.svg`. One of those is scripts' contract and is already designed: the manifest's exact text, its `[env]` defaults, its `[database]` table naming `state/scripts.db`, its `[resources]` table (`cpu_weight` 50, `memory_max` `1G`, `io_weight` 50), and the absence of `guests`, `port` and `DRAIN_SECONDS`, are `D02-cli`'s (`cli.Manifest`, R-TAN4-QOQ0); the root package's `Etc` proves that `etc/` holds exactly `manifest.toml` and nothing else (`D01-layout-and-run-seam`, R-S0RY-EOPY, R-J8DY-WCVQ), with exactly the bytes of `cli.Manifest` (`D02-cli`, R-S1ZU-SGGN), and since `Etc` is an `embed.FS` those bytes are the committed file's. That is also how "nothing under `etc/` but the manifest" and "scripts ships no `etc/nginx.conf`" are proved: an `etc/nginx.conf` would give `Etc`'s `etc` directory a second entry. That `scripts --version` prints the version and `scripts manifest` prints the manifest byte for byte is `D02-cli`'s (R-TJ6F-F2WV, R-TKEB-SUNK). That the binary is static `linux/amd64` and cgo-free is `AGENTS.md`'s release build gate, not a requirement. That no `assets/` directory or font ships beside the binary follows from the templates being embedded in the root package (`D01-layout-and-run-seam`, R-J4Q9-R1NN, R-J5Y6-4TEC) and appkit's shared files being served from appkit's `page` package (`D08-pages`). That neither the database nor any run folder is in the file, and that scripts creates `state/scripts.db` and `state/runs/` on its first start, is `D01-layout-and-run-seam`'s (R-JN0R-HLS2, R-JPGK-959G, R-8U9H-VWCG) and `D03-serve`'s. Neither `git` nor `python3.12` is in the file; both are the host's.

The rest of the file is not scripts' to state. The tarball, its member list, its name carrying the version and no member's path carrying it are `devctl build`'s; `share/icon.svg` is human-authored (`AGENTS.md`), and that its presence lists scripts in the launcher is opsctl's services file. No test reads the checkout, so the tarball and the icon are outside what a requirement can state; a developer checks them with the package story's own `tar` commands.

## python3.12 on a host and on a developer's machine

scripts has no Python of its own. The version is one declaration, `runner.PythonVersion`, whose value is the decided `3.12`; the command's name is `runner.Interpreter`, derived from it (`D01-layout-and-run-seam`, R-8VHE-9O35). scripts looks for an executable of that name on the `PATH` `LookupEnv` gives it at start and refuses to start without one with `scripts: python3.12 not found on PATH`, before it opens its database (`D03-serve`); every run is started with that same `PATH` (`D07-runs`, R-XBLK-US05), so every script runs under the interpreter the start found. Which patch level it is, and how it got there, is not scripts'.

On a host, `python3.12` comes from the space's first boot, which is infra's behaviour, not scripts': the decisions document states that infra's first-boot line installs `python3.12` from the distribution and names the version independently, and opsctl's published stories state that the host's programs, `git` among them, are installed by the space's first boot, not by opsctl (opsctl's `S4-init.md`). So the version is named in two places: a change of version edits `runner.PythonVersion` and that line. First boot runs only when an instance is launched, so a space whose instance was launched before that line named `python3.12` lacks it. On such a space the first install of scripts leaves the service failed with scripts' refusal quoted from the journal, and the fix is a one-off install by an operator on the host (`dnf install -y python3.12`, as root) followed by a restart of scripts, through `opsctl restart scripts` on the host or `devctl space restart <space> scripts` from the developer's machine. opsctl does not install `python3.12` or `git`: its `init` only finds the host's programs on the `PATH` (opsctl's `S4-init.md`), and nothing in this design or any other relies on opsctl provisioning either. A space launched after that line, a destroyed and re-created one included, has it from first boot.

On a developer's machine `python3.12` must be on the `PATH` for scripts' tests (`AGENTS.md`, gate 4) and for a sandbox, which starts scripts with the `PATH` the developer's systemd user manager gives its services. The developer installs it with `uv python install 3.12`, which places `python3.12` in uv's executable directory, `~/.local/bin`; that directory being on the developer's `PATH` and on the user manager's is the developer's own set-up, named in the stories as a precondition.

## On a space

scripts on a space is the same binary serving on the same terms as under a test: a socket passed as descriptor 3, `/opt/scripts` as its working directory, its settings from `/opt/scripts/etc/env`, `IKIGENBA_SERVICES` naming the host's services file `/var/lib/ikigenba/services.json`, and the host's `git` and `python3.12` on its `PATH`. Who supplies each of those is opsctl's and first boot's (the unit, the socket `/run/ikigenba/scripts.sock`, `etc/env` from the manifest's `[env]` and the space's `DRAIN_SECONDS`, the `[resources]` bounds over the unit and so over every `git` and every script it starts, the services file with its `url` `https://scripts.<space>` and `mcp` true, and the replication of the database `[database]` declares); what scripts does with them is the earlier designs'. With `/opt/scripts` as `Dir`, the catalog is `/opt/scripts/state/scripts.db`, the run folders are under `/opt/scripts/state/runs/`, and `REPOS_DIR` at its default resolves to `/opt/scripts/../repos/state/repos`, which is where repos keeps its bare repositories (`D01-layout-and-run-seam`, R-JRWD-0OQU). Every script scripts runs is handed that services file's path as `IKIGENBA_SERVICES` and the service's `PATH` verbatim (`D07-runs`, R-XBLK-US05), so it reaches its siblings as the gateway does. The run folders live under `state/` and stay on the host across releases; they are not replicated, because only the declared database is, and a catalog restored from the replica comes back with every run's files gone, which scripts shows as such (`D03-serve`, `D07-runs`).

Because the manifest declares no `guests`, the space's nginx puts every request for scripts to auth's `/check`. A request with no credential never reaches scripts: a page is redirected to sign in and `/mcp` is challenged with `401`, by nginx. A request whose credential auth refuses is answered by auth and never reaches scripts either. Every request nginx passes carries `X-User-Id` and `X-User-Email`, which appkit's `identity.Require` turns into the caller (`D03-serve`), `X-Forwarded-Proto: https`, which makes the addresses scripts builds `https` ones (`D08-pages`), and an `X-Request-Id`, which scripts records as each event's request id and hands to a run it starts (`D03-serve`, `D10-trail`, `D07-runs`), so auth's check event and scripts' events of one request share it. A deploy restarts scripts, which is a stop: a run still in flight at the drain deadline is killed, its process group whole, and recorded `killed` by the stopping scripts (`D03-serve`, R-BH2J-3S0P).

## The credential

On a space every request scripts receives has been admitted by auth, and nginx passes the client's `Authorization` header on to scripts untouched: an agent's or curl's `Bearer` token, or git's `Basic` credential, which can reach scripts because the host's nginx challenges git's paths with `Basic` in every wired server block, scripts' included (opsctl's `S5-nginx.md`; sandbox's `S4-routing.md`). scripts never needs the header — the caller is appkit identity's `identity.Caller`, from the identity headers nginx sets — and the stories promise that the token's secret is in no record any of them leaves: not in the trail, not in nginx's logs, and not in any run's folder. The trail is scripts' to keep clean, and so is everything scripts keeps on disk and everything it hands a script; nginx's logs are opsctl's.

A request carries a **credential header** when its `Authorization` header is `Bearer <p>`, or `Basic ` and the standard base64 of `<u>:<p>`, the test choosing `<u>` and `<p>` long, with an uppercase letter in every 8-character stretch of each and of their base64 value so that no id, sha, request id or number scripts mints or a fixture holds can match them, and occurring nowhere else in what it sends or stores. Its **secret strings** are every run of 8 or more consecutive characters of `<p>`, of `<u>` and of the base64 value, so a truncated or partial leak counts as a leak (R-VZA3-2BOY). A secret scripts wrote in another encoding — re-encoded in base64, URL-escaped, changed in case, split by other bytes — is outside what these tests can detect, as with sites: the guarantees are about the credential's own characters.

The guarantees are proved over one sequence of requests (R-BB9G-J9E5), made once with every request carrying a `Bearer` credential and once more, over scripts of other names, with every request carrying a `Basic` one, so a leak of either form is caught. The sequence reaches every kind of route scripts serves and every tool: `tools/list` and all nine tools, a refused tool call, the catalog, about and appkit paths, a script page and a run page with their slash-less forms, a script name and a run id that name nothing, each of a run's files, its `out/` folder and a directory under it as well as a file, a run that fails to start, a run cancelled while it runs, and a script deleted with a run in flight. Its runs come from one `main.py` that copies its whole environment, the bytes of `/proc/self/environ`, to its standard output and to two files under its out folder, and, when its input asks, then waits until it is killed. One path is not in the sequence: the catalog refusal, the unavailable page a page or tool gives when the catalog cannot be read, because a test of `Run` has no way yet to make the catalog `Run` opened fail after it opened it; it writes nothing to `Stderr` of its own (`D03-serve`, R-CK3B-CFQX, R-SBR1-UME7), and adding it waits on the form `D08-pages` gives that state. Four guarantees follow. First, nothing scripts records — no event's name, envelope or attribute — holds a secret string (R-BB9G-J9E5). Each event's exact keys are already fixed by the documents that own them (`D03-serve` for the request pair and the service events, `D10-trail` for every `script.*` and `run.*` event, appkit's MCP tools design for `tool.called`), and none of them reads the header, so this is the end-to-end statement of what those already imply, proved through `Run` with a capturing sink. Second, nothing `Run` writes to `Stderr` holds one, including the journal's copy of an event telemetry could not take, which is the only line `D03-serve` lets `Run` write while it serves (R-SBR1-UME7, R-CK3B-CFQX; this design R-BCHC-X14U). Third, the environment of a script holds none (R-BDP9-ASVJ): it is exactly the twelve variables `D07-runs` composes, and of the request only the caller's user id and the request id reach it, never a header's value. Fourth, nothing scripts leaves on disk holds one: after such a sequence, no file under its working directory — the catalog and its SQLite sidecar files, and every run folder's `input.json`, `stdout`, `stderr`, `tree/` and `out/` — contains a secret string (R-BEX5-OKM8). Beside them, one guarantee the stories state that no earlier document owns: scripts sets no cookie, so no response to a page, run file or appkit path of the sequence carries `Set-Cookie` (R-BG52-2CCX); MCP answers are left to appkit's client, whose results a test asserts on, not their headers. A run's `input.json` is the `input` argument byte for byte, which the test chose; the guarantee is that scripts adds nothing of the header to it.

## In a sandbox

In a sandbox scripts is the same binary in the same arrangement. The sandbox takes as an app every immediate subdirectory of the checkout holding `etc/manifest.toml`, so scripts joins a sandbox as soon as the build run has written its manifest, with no change to sandbox: it builds `cmd/scripts` from the worktree, runs it under its own units with a working directory of its own (`<data>/apps/scripts`), gives it the environment of a host — `DRAIN_SECONDS`, `IKIGENBA_SERVICES` and the manifest's seven settings — plus variables a host never sets, checks but does not apply `[resources]`, puts its own nginx in front, and routes every request through auth's `/check` since the manifest declares no `guests` (sandbox's `S3-apps.md` and `S4-routing.md`). All of that is the sandbox's. scripts' contributions are the ones it makes on a space:

- It serves under the sandbox like any app, at `http://scripts.wip.localhost:7400`. Its catalog and run folders are under its working directory (`D01-layout-and-run-seam`, R-JN0R-HLS2, R-JPGK-959G), so they survive `down` and `up` because the sandbox keeps that directory until `wipe`.
- `REPOS_DIR` at its default resolves against that working directory to `<data>/apps/scripts/../repos/state/repos`, which is repos' own directory in the sandbox, so scripts reads exactly the repositories repos holds with no setting changed (`D01-layout-and-run-seam`, R-JRWD-0OQU). scripts does not need repos running to start: it looks at no repository at start, and a repository directory that appears later is found without a restart (R-JUC5-S888). repos is needed only for the stories that push a repository and run it.
- It finds `git` and `python3.12` on the `PATH` it is given, which in a sandbox is the developer's user manager's; that the developer's own `python3.12` is there is the precondition `S22` names; sandbox's `AGENTS.md` does not name it yet, which is step 2 of the decisions document's Sequence, still pending; and without it the sandbox reports scripts' service failed with scripts' own refusal in its journal (`D03-serve`). Every script is handed that `PATH` and the sandbox's services file (`D07-runs`, R-XBLK-US05).
- Its addresses are built from the sandbox's services file and the requests arrive with `X-Forwarded-Proto: http`, so its profile and sign-out addresses are `http://auth.wip.localhost:7400/` ones (`D08-pages`).
- It reads nothing from its environment beyond what a host gives it, so the variables only the sandbox sets change nothing it does: the keys `Run` looks up are the closed list `D01-layout-and-run-seam` states (R-JWRY-JRPM).
- The same credential guarantees hold; `sandbox logs scripts` showing no line is `D03-serve`'s quiet standard error.

## Departures from sites

- scripts serves no guest. sites' manifest says `guests = true` and sites decides itself who must sign in; scripts' manifest declares no `guests`, so nginx and auth turn every guest away before scripts, and scripts' share of the guest stories is only that it records nothing for a request it never receives. scripts has no visitor cookie and no apex host, so neither appears here.
- The credential guarantee reaches further: beside the trail, standard error and the catalog, it covers every file of every run folder and the environment of every script scripts starts, because scripts keeps a run's input, output and files and hands a process an environment, which sites never does.
- What scripts keeps besides the catalog is under `state/`, not `cache/`: run folders are kept across releases, never rebuilt and not replicated, where sites' trees are disposable. Pruning after every run's end is `D07-runs`' departure, recorded there.
- The host needs a second program, `python3.12`, and a space launched before first boot named it needs a one-off install by an operator, which sites never needed.

This design records no departure from a story of its own.

## What only a space can show

These outcomes are space-level checks: no test of scripts can make them, and they are verified by running the stories on a space or in a sandbox. They are recorded here, not required.

- The release file holds exactly `bin/scripts`, `etc/manifest.toml` and `share/icon.svg`, `bin/scripts` is a static `linux/amd64` executable (`AGENTS.md`'s release build gate proves the build, devctl's release build makes the file), the icon is an SVG, the version is in the file's name and nowhere in a member's path, and `space status` reports the version the binary prints (devctl).
- `python3.12` is installed by the space's first boot, a space launched before that lacks it until an operator installs it, the install of scripts on such a space leaves its units written, its socket listening, nginx routing and the services file listing it while the service is failed, and `opsctl install` and `devctl deploy` report that failure with scripts' line quoted; the operator's `dnf install` and `opsctl restart scripts` (or `devctl space restart`) bring it up (infra's first boot, opsctl, devctl; scripts' part is its refusal and first start, `D03-serve`).
- `uv python install 3.12` puts `python3.12` in `~/.local/bin`, and the developer's user manager gives the sandbox's services that `PATH`; without it `sandbox up` exits 1 and reports scripts' service failed (uv, the developer's set-up, the sandbox; scripts' part is its refusal, `D03-serve`).
- The unit runs as `ikigenba` under `[resources]`, so `memory_max` bounds scripts and every script together, with no limit per run and no cap on how many run at once, and a script the kernel kills for memory is recorded `exited` with code 137 while scripts itself keeps serving and answers every tool as before, which holds only when the kernel picks the script's process and not scripts' (opsctl's unit, the kernel; scripts' part `D06-runner`, R-JA3X-ZAPK, and `D07-runs`); `etc/env` holds the seven settings beside `DRAIN_SECONDS` and `IKIGENBA_SERVICES`; the database is kept and replicated across releases while the run folders are kept and not replicated; a catalog lost on the host comes back only from the replica (opsctl).
- A guest is redirected to sign in, a refused credential is answered `403`, and a `POST /mcp` with no credential is answered `401` with `www-authenticate: Bearer realm="ikigenba"` and nginx's one-line body, in each case nothing reaching scripts' socket and scripts recording no event (nginx and auth, opsctl's `S5-nginx.md`, auth's `S4-check.md`; in a sandbox, the sandbox's nginx).
- auth's own records of each request (`check.allowed`, `check.refused`) and their sharing a request id with scripts' events (auth, nginx).
- The host's nginx log holds no token: its format is opsctl's, and scripts neither writes it nor affects it.
- The answers arrive over HTTP/2 and TLS on a space and over HTTP/1.1 in a sandbox (nginx).
- The gateway offers scripts' nine tools, runs `create` and `run` through `mutate` and `result` through `call`, forwards the caller and the request id, and relays scripts' results under its own `serverInfo` (mcp's `S08-call.md`, `S09-mutate.md` and `S11-on-a-space.md`).
- In a sandbox, repos makes the repository an agent pushes to, at `<data>/apps/repos/state/repos/<rep>.git`, and records `repo.created` and `repo.pushed` (repos, the sandbox).
- The launcher a browser opens lists scripts with its icon, an enabled button visibly reacts as it is pressed, and the page's style and button-feedback script are fetched from scripts' own host and from no other origin (appkit's scripts; no test runs them).
- The `PATH` the sandbox gives scripts holds the developer's own `git` and `python3.12` (the sandbox, the developer).
