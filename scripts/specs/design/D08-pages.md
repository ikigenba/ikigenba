# D08-pages

What scripts draws as HTML and the addresses it draws with: the packages `internal/urls` and `internal/pages`; the seven human-authored templates `landing`, `script`, `run`, `about`, `tools`, `notfound` and `unavailable` and the three partials `run-status`, `run-duration` and `file-size` that `run.html` defines, the data each receives and the layouts its times are formatted with; the levels of the banner trail each page sets; the handler that answers `/`, `/about`, `/tools` and every script path that is not one of a run's files — the catalog, a script's page, a run's page, the about screen and the tools page, the redirects that add a missing trailing `/`, the not-found page, the unavailable page when the catalog cannot be read, and the refusal of any other method; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the names this design behaves through outside its two packages: the root package's `Assets`, and the run seam whose `Banner` the binary sets to the `Banner` method of `page.New(pages.ServiceName, id)`, `id` being the identity `main` reads (`D01-layout-and-run-seam`), whose release and commit are empty when the host sets none. `D04-store` declares `store.Store`, its `List`, `ListBefore`, `Find`, `Runs`, `RunsBefore`, `RunCount` and `FindRun`, run order and a run's started text, the records `store.Script`, `store.Subscription` and `store.Run`, their status, reason and trigger words and `store.Unreachable`; `D05-git-and-source` declares `source.Source` and its `Name` and `RepoDir`; `D07-runs` declares `runs.Core` and its `Folder`, `Gone` and `Sizes`, and the names of a run folder's entries; `D09-run-files` declares the run file paths and the handler that answers them; `D03-serve` declares `web.Handler` and `web.Config`, defines a script path, and owns the route table, `identity.Require` around every route, the request's id and its two events, and that nothing reaches standard error while telemetry takes every event. appkit's `paging` declares `DefaultLimit` and the tokens the catalog and the script page share with `list` and `runs`, taking one as `page` and handing on the next (appkit's D25). The eleven tools' names and descriptions, and what `list` and `runs` answer for a token, are `D11-tools`'; the tools page reads them from the `mcp.Server` on which `D11-tools`' `Register` put them, which `D03-serve` hands this design as `pages.Config.MCP`.

## Addresses

`internal/urls` builds the two addresses scripts writes into a page that are not its own: auth's profile page and auth's sign-out action, which the banner carries. Each reads the services file afresh through appkit's `services.Read` on every call, so a rewrite shows on the next page, and treats a file it cannot read — no path, no file, not a services file — as listing nothing, writing nothing about it. They are the `url` of the file's entry named `auth` followed by `/` and by `/logout`; with no such entry, or an empty `url`, the space is read from the request's `Host`, a trailing port dropped and then one leading `scripts.` label, and the scheme is the request's `X-Forwarded-Proto` when that is exactly `http` or exactly `https`, and `https` for anything else.

Every other address a page carries is a path of scripts' own, relative to the host the browser used: `/`, `/about`, `/tools`, `/<name>/`, `/<name>/runs/<run id>/` and the run's files beneath it. scripts never sends a visitor to sign in: nginx does that before a request reaches scripts, and a request that arrives with no `X-User-Id` is appkit's `identity.Require` 500 on every route (`D03-serve`), so `urls` has no sign-in address.

## The template set and its data

The seven pages are the files of `assets/`, embedded by the root package and returned by `Assets()`; `run.html` also defines three partials, `run-status`, `run-duration` and `file-size`, which `landing`, `script` and `run` call. `pages.Load` builds **scripts' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `footer` and `preload`; the code adds no template function and writes no markup of its own. `Set.Write` is the one way any handler sends a page: it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set first, and sets nothing else. A `HEAD` gets the status and headers and no body.

Each template's data is a named struct whose fields are exactly what its page shows. The data carries values, never words: a run's status, exit code and failure reason as the store records them, a duration as whole minutes and seconds, a size as a scaled number and a unit, and the limits a failure names as numbers. Every word a page shows, the status word and its kind, the notice, a failure's title and sentence, the units, is chosen by the template from those values. Times are the one thing the code formats, with three layouts of `pages`, because a template cannot format a time without a function the set does not have:

- `LandingData`: the banner, one `ScriptRow` per script of one window of the caller's scripts, by name, `paging.DefaultLimit` of them at most, the window the request's `page` names; `Page`, the request's `page`, empty on the first window; `Prev`, the before-token of the window's first script, empty on the first window and on an empty window after a token; and `Next`, the token `list` takes as `page` for the scripts after them, empty when none remain and on the last window; a row carries the script's name, its page's path, its `Repo` (the id and the name read now, empty when it cannot be read), its ref and its last run as a `RunRow`, nil when it never ran.
- `ScriptData`: the banner, a `ScriptCard` (id, name, `Repo`, ref, created, how many runs the script holds in all and the retention rule), one `RunRow` per run of one window of its runs, newest first, `paging.DefaultLimit` of them at most, the window the request's `page` names: id, page path, the store's status and exit code, short commit, start and a `Duration`, nil when the run has none; the event patterns the script is subscribed to, each exactly as subscribed, sorted by pattern, with no time, since the page shows none; `Page`, the request's `page`, empty on the first window; `Prev`, the before-token of the window's first run, empty on the first window and on an empty window after a token; and `Next`, the token `runs` takes as `page`, with the script's name as `name`, for the runs after them, empty when none remain and on the last window.
- `RunData`: the banner, a `ScriptLink` (name and path), a `RunCard` (everything the run's summary shows: its status and exit code, whether it has not ended yet, its times, its `Duration`, its stream sizes as `Size`s, its `Failure`, the run's trigger and, for a run an event started, that event's id among it), a `FileText` for each of `input.json`, `stdout` and `stderr` that exists, and one `FileRow` per regular file under `out/`, each with its `Size`.
- `AboutData`: the banner and `pages.Description`, the manifest's one-line description.
- `ToolsData`: the banner and one `Tool` per MCP tool, its name and its description, in the order the server holds them, read from the server's `Tools` as the page is drawn.
- `NoticeData`: only a banner, from which the not-found and unavailable pages draw appkit's footer, which carries the release and then the commit of the identity `main` reads (`D01-layout-and-run-seam`) and no service name.

The three partials take a part of that data: `run-status` a `RunRow` or a `RunCard`, of which it reads the status and exit code, `run-duration` a `Duration` and `file-size` a `Size`. They are named so a test can execute one alone, and are proved by use: each page that calls one is compared whole.

No data type has a field for a script's owner or anything of another user's, so no page can show them; a run's reason is carried only in its `Failure`. What the banner holds — the mark, scripts' own icon from the services file's entry named `scripts`, the link to the suite's home from the entry named `home` while it is enabled, the link to the tools page when scripts' entry offers tools, the profile link and the sign-out form, and the trail — is appkit's output (its page banner and page templates designs); there is no service launcher, and nothing replaces it. This design states only which data a page is drawn with, and one binary-level requirement (R-IU2H-3517) proves that the binary's banner source is appkit's kit made for `pages.ServiceName`, reading the services file afresh.

The `unavailable` page is what a page path answers when the catalog cannot be read: status 503, drawn with the banner the banner source gives for the empty `page.User`, as the not-found page is, so it carries nothing of the error and is the same bytes for every caller. A run's files are not pages: `D09-run-files` answers them with the plain-text catalog refusal this design defines, and the tools answer with `store.Unreachable` (`D11-tools`).

## The banner trail

appkit's banner draws where a page sits in scripts as a trail of levels below the landing page, each a `page.Level`, a name and a URL. A page sets its levels on the banner's `Trail` after its banner source returns, replacing whatever the source returned; in the binary the source is appkit's kit, which also fills the banner's home link and whether the service has tools. The landing page has no level. The about screen has one, `about` at `/about`, and the tools page one, `tools` at `/tools`, each named by its path segment. A script's page has one, the script's name at `/<name>/`; a run's page two, the script's name at `/<name>/` and then the run id at `/<name>/runs/<run id>/`. The not-found and unavailable pages draw no banner, only its footer, so they keep the banner for the empty user with no level set; a run's files are bytes, not pages, and carry none (`D09-run-files`). No page draws levels of its own under `main`: the trail is the banner's. A test proves the levels by executing the page's template with the data this design states, the trail included, against a banner source that returns a fixed banner whose `Trail` is not empty, and comparing the bodies byte for byte, so the script's name and the run id it supplied appear in the body as the trail's levels.

## The pages handler

`pages.Handler` answers `/`, `/about`, `/tools`, and every **script path** — every path but `/`, `/about`, `/tools`, `/mcp`, `/events`, `/declarations` and those beginning `/_appkit/`, as `D03-serve` defines it (R-RKBX-PTUG) — that is not a **run file path** (`D09-run-files`). `D03-serve` routes those paths to it inside `identity.Require`, so it never sees a request without a caller, and a test wraps it the same way. It reads the path as **pieces**: the escaped path less its leading `/`, split at every `/`, each piece percent-decoded. A piece is compared byte for byte, never tidied: `.`, `..`, an empty piece and a piece that was percent-encoded are names like any other and match nothing that is not spelled so.

Each request is answered in this order. The method first: anything but `GET` and `HEAD` is refused 405 with `Allow: GET, HEAD` and an empty body, before the catalog is read, so the answer is the same for a script, another user's script and no script. Then:

- `/about` draws the about screen, reading no catalog and running no git, so it is served with the catalog unreachable. Its version fact is the banner's `Release` and `Commit`, the identity `main` reads (`D01-layout-and-run-seam`), and stays on the screen whatever they hold, both empty included, when the host sets no identity.
- `/tools` draws the tools page: the tools registered on `cfg.MCP`, read with its `Tools` as the page is drawn, each with its name and description, in the order the server holds them. It reads no catalog and runs no git, so it too is served with the catalog unreachable.
- `/` takes the first `page` of its query, and nothing else from it: absent or empty, the first window; a token `paging.Token{Tool: "list"}` decodes, the window after the name it carries; a token `paging.Token{Tool: "list-before"}` decodes, the `paging.DefaultLimit` scripts before the name it carries, whether or not a script still has it, drawn in ascending order; exactly `last`, the last `paging.DefaultLimit` scripts, drawn the same way; anything else the not-found page, decided before the catalog is read, so the answer is the same with the catalog unreachable and never the first window. It then reads that window of the caller's scripts with `store.List`, once, asking for one more than `paging.DefaultLimit` after the decoded name to learn whether more follow, reads no run folder, and draws the catalog: exactly what `list` answers the same caller for the same `page` and no `limit`. A before-token or `last` is read with `store.ListBefore`, once, asking for one more than `paging.DefaultLimit` nearest the bound; when that extra script does not come back, the window would reach the first script, and the page answers 303 to `/`, the first window's one address, rather than draw a second copy of it.
- A script path looks its first piece up among the caller's own scripts with `store.Find`. A name that is none of theirs — no script, another user's, a different letter case, `about`, `tools`, `mcp`, `events`, `declarations` — is the not-found page, whatever follows it, so `/events/` and `/declarations/repo.pushed` are answered with it and never reach the events app's handlers. Under one of theirs: the path that is the name alone is redirected 301 to `/<name>/`, the query kept whole, a bad `page` included; `/<name>/` draws the script page, from the window of the script's runs its `page` names, read with `store.Runs` asking for one more than `paging.DefaultLimit` after the started text and id a token `paging.Token{Tool: "runs"}` decodes into, exactly what `runs` answers for the same name and `page` and no `limit`, and the count of all its runs, read with `store.RunCount`; a token `paging.Token{Tool: "runs-before"}`, over a started text and an id, names the `paging.DefaultLimit` runs before that position in run order, the newer ones, and `last` the oldest `paging.DefaultLimit`, each read with `store.RunsBefore` asking for one more and drawn newest first, and a window that would reach the newest run is answered 303 to `/<name>/`; `/<name>/runs/<run id>` and `/<name>/runs/<run id>/` look the run up with `store.FindRun`, and a run of this script is redirected or drawn the same way, while any other run id is the not-found page; every other path under the script, `/<name>/runs/` included, is the not-found page.
- A `/<name>/` whose `page` is not empty, a `runs` or `runs-before` token or `last` is the not-found page whatever the name: it is decided without the catalog, so a missing script, another user's and the caller's own are answered alike, and so is a catalog that is unreachable or a context already done. The script lookup and the token decide the same 404 whichever is consulted first.
- Any catalog read that answers neither a record nor `store.ErrNotFound` is answered with the unavailable page, status 503, for every request but a `/` or `/<name>/` whose `page` does not decode.

The contract states that answer for a failing store and for a request whose context is already done as it arrives: turning on `SetFailing` for the store's handle and cancelling a request's context are the ways the test rules allow to fail the catalog, and each fails the first read, `List` or `Find`. So no permitted test can fail `Runs`, `RunCount` or `FindRun` alone, and a failure of either alone, answered the same way, is unstated as contract until the test rules decide whether a seam may fail one read. Likewise, that `/about`, `/tools` and a 405 read no catalog and that the catalog page reads it once and reads no run folder are contract only through their answers: a read that changes no answer is not observable by a permitted test.

The not-found page is the `notfound` template with status 404, drawn with the banner the banner source gives for the empty `page.User`, so the answer to a path naming another user's script or run is byte for byte the answer to one naming nothing. A `HEAD` is answered with the status and headers its `GET` has and no body, redirects and refusals included. No answer sets a cookie. A page reads the catalog and, for the run page, the run's folder through `runs.Core`; it runs git only to read a repository's name with `source.Name`, and only where a page shows it: each listed script's on the catalog, the script's on its page, and on a run page only for a run that failed to start, whose `Failure` carries the repository. Drawing a page writes nothing anywhere: nothing is created under the runs directory, not even a folder for a script that has never run.

## How the data is formatted

The data carries values and the templates choose the words. A run's `Status` and `ExitCode` are the record's, the exit code 0 unless the run exited (`D04-store`); `run-status` turns them into the status word and its kind. A time in a table is formatted with `pages.MinuteLayout`, the script's created time with `pages.CardLayout` and a run page's times with `pages.SecondLayout`, each in UTC and each carried as well in its RFC 3339 form; the layouts are copy constants of `pages`, declared by name and never by value. A duration is the record's finished less its started, in whole seconds, carried as whole minutes and the seconds left over, and is nil while the run is queued or running and when it failed to start; `run-duration` writes it, leaving out the minutes when there are none. A size is the byte count scaled by the code: bytes under 1000, otherwise thousands or millions truncated to one decimal, carried as that number as a string and the unit `byte`, `kilobyte` or `megabyte`; `file-size` writes the unit's word. A commit in a table is its first seven digits; on the run page it is whole; both are empty when the ref never resolved. So changing how a page reads touches one template and no requirement.

A repository is carried as its id and the name `source.Name` reads from its directory as the page is drawn, the name empty when there is none to read — one treatment for a directory that is gone, a config without the name and a git that cannot read it (`D05-git-and-source`).

The run data carries what the run page needs for each state of a run. A run that has not ended, queued or running, has `Running` true, and the template words its notice from `Status`; it carries what its files hold so far and its stream sizes measured from them (`runs.Core.Sizes`); a queued run has no finish and no duration, and since its script has not started its folder holds no stream file. A run abandoned in the queue (`store.ReasonQueueAbandoned`) is a run that failed to start, with the commit it had resolved. A run that failed to start carries a `Failure`: its reason as recorded, the script's repository (its id and the name read now), the ref, and the two limits a reason may name, `TreeMaxBytes` and `OperationSeconds`; the template chooses the failure's title and sentence from the reason and names what it needs from the rest. A run whose output was cut carries one `Truncated`, whichever stream was cut, and its sizes are the bytes kept. A run whose folder is gone (`runs.Core.Gone`) has `FilesGone` true and no file data. Otherwise `Input`, `Stdout` and `Stderr` are present only for a file that exists, each with the file whole and its address (`D09-run-files`), and `Files` lists every regular file under `out/`, at any depth, hidden ones included and symbolic links left out, by path, each with its size and address. The card's `Trigger` and `Event` say who started the run: an event, by its id, or the `run` tool.

A script's data carries the event patterns the script is subscribed to, each exactly as subscribed, sorted by pattern, and no subscription's time.

## How a page is proved

A test proves a page by executing the named template of its own copy of scripts' template set with the data this design states and comparing the body byte for byte, or by checking that a value it supplied appears in the body. No requirement names a heading, a label, a sentence, a class, an id or an attribute, and none defines how markup is read: the words and hooks are the templates', documented in each template's opening comment. `html/template`'s contextual autoescaping is what keeps a caller's, a repository's or a script's bytes from becoming markup, and the byte-for-byte requirements cover every input. A template that cannot show a state this design names is an issue for a human, never a change to the asset.

## The head

Each template carries its own head, which loads appkit's stylesheet, favicon and button-feedback script from `/_appkit/` and invokes appkit's `preload` template for the font, whose URL carries a hash of its bytes that scripts never writes. What the head holds is the template's, so no requirement states it; the shared files it loads are served as the next section states. A run's files are the run's own (`D09-run-files`); none of this reaches them.

## The shared files

The stylesheet, its three fonts, one of which every page preloads, the button-feedback script, the favicon and the two licences are the platform's shared files: appkit's `page` package embeds them and `page.Static()` serves them under `page.StaticPrefix`, `/_appkit/`. scripts holds no copy and reads nothing from disk for them; `D03-serve` hands every request whose path begins with `page.StaticPrefix` to that handler unchanged, inside `identity.Require` like every route. The requirements here state appkit's answer as scripts' own behaviour at `web.Handler`, so scripts' tests fail if a different appkit release stopped giving it. Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`.

Five shared files have fixed names: `theme.css`, `feedback.js`, `favicon.svg`, `OFL.txt` and `TABLER-LICENSE.txt`; `/_appkit/launcher.js`, which an earlier appkit release served, is not found like any other name appkit does not serve. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit are not served, and a font path with its hash taken out answers 404 like any other name appkit does not serve. scripts never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads, and the paths the served stylesheet names, each a `url("…")` of a name ending in `.woff2` beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet scripts serves. Every 200 and 304 for a shared file carries one strong `ETag`; a font path's carries one `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again, and every other shared file's one `Cache-Control: no-cache`, so a browser keeps its copy but asks each time.

## Decisions

- The catalog unreachable on a page path is the `unavailable` page with status 503, drawn with the banner for the empty `page.User`, as the not-found page is: a person reaching a page gets a page. Every other answer to it keeps `store.Unreachable`: a run's files, whose bytes are the run's, with the plain-text catalog refusal, and the tools with their refusal.
- There is no guest branch and no `urls.SignIn`: unlike sites, every route is behind `identity.Require`, nginx sends a visitor with no credential to sign in, and a request without `X-User-Id` is a 500.
- The scheme is exactly `http` or exactly `https`, case-sensitively (`HTTPS` is `https` because it is neither); sites lowercases first.
- The handler reads the caller from `identity.FromContext`, so its behaviour is stated for `identity.Require(pages.Handler(cfg))`.
- `ScriptData.Subscriptions` is a slice of patterns, not of `store.Subscription`: the page shows no subscription's time, so the data carries none, and the order is the catalog's, by pattern.
- The data carries no word: no status word, kind, notice, failure title or text, and no unit word. The template chooses each from `Status`, `ExitCode`, `Failure.Reason` and `Size.Unit`, so a change to how a page reads is a change to one template.
- `RunCard.Event` is the run's `Event`, empty for a manual run; the template chooses the card's first line from it, so the data needs no flag of its own.
- One `RunRow` type serves both a script's runs and the catalog's last run, whose template reads only its status, exit code and start.
- The code still does the arithmetic a template cannot: a duration split into minutes and seconds, a size scaled to its unit, a commit shortened, and times formatted with the three layouts, which stay copy constants of `pages`. A `Duration` is a pointer so that a run with none carries nil rather than a zero that reads as a duration.
- A `Failure` carries the script's repository for every reason, so the run page of any failed run reads the repository's name; the template names it only where its sentence needs it.
- The three partials are templates of the set, named with the data each takes, so a test can execute `run-status` alone with a row or a card.
- The run page carries one `Truncated`, the record's, not one per stream: the record has one flag.
- Sizes are truncated, not rounded, to one decimal, so a size under a million never reads as a thousand thousands.
- A piece is percent-decoded before it is compared, so a link the page writes for a file whose name needs escaping leads back to it; nothing is tidied, so a decoded `.` or `..` is still a piece that names nothing.
- The not-found page is drawn with the banner for the empty `page.User`, so it is the same bytes for every caller.
- The tools page lists the tools of the very `mcp.Server` `D03-serve` mounts at `/mcp`, read through appkit's `Tools`, rather than a list of its own, so the page and `tools/list` cannot drift; `pages.Config` carries that server as `MCP`.
- Each page replaces the banner's `Trail` whatever its source returned, the landing page with a trail of no level, so no page's levels rest on what the source leaves there.
- The not-found and unavailable pages keep the banner for the empty `page.User` with no level: their templates draw only its footer.
- The catalog and the script page navigate, as the suite's Listing convention asks: each takes the `page` token of the matching tool, `list` for the catalog and `runs` for a script's runs, and draws exactly the window that tool answers for the same caller, name and `page` with no `limit`, `paging.DefaultLimit` entries at most, through the same store windows. The data carries the token the request carried as `Page`, the next one as `Next` and the one before as `Prev`; the template writes the links, `last` included, which the data does not carry. Prev and Last read the same windows reversed (`store.ListBefore`, `store.RunsBefore`), and their tokens are the pages' own (`list-before`, `runs-before`): the tools take neither, nor `last`.
- A Prev or Last window that would reach the first entry is not drawn: it is redirected 303 to the page's own path, so the first window has one address and the backward walk ends on it. A before-token over an entry since deleted still names a position, so the window before where it sorted is drawn. The token binds no filter, so a `runs` token from another script's page is drawn from the same position, as `runs` answers it.
- A `page` that does not decode is the not-found page, never the first window: a wrong token is a wrong address. It is decided before the catalog is read, so it holds with the catalog unreachable, and the unavailable rules are stated for a decodable `page` only. Only the first `page` of the query is read; the script's name in the links the page writes is safe in a path as it stands, since `store.ValidName` admits only `a`–`z`, `0`–`9` and `-`.
- `RunsKept` is how many runs the script holds in all, one count the store makes (`store.RunCount`), not the length of the page the script page draws: the card says how many runs are kept under the retention rule, which a page of 25 cannot tell.

## Consumer tasks

`web.Handler` calls `pages.Load()` once, when it is built, and builds `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: path, Store: cfg.Store, Source: cfg.Source, Runs: cfg.Runs, MCP: cfg.MCP, KeepDays: s.RunKeepDays, KeepCount: s.RunKeepCount, TreeMaxBytes: s.TreeMaxBytes, OperationSeconds: s.OperationSeconds})`, the four numbers being the settings `D12-limits` read at start; it serves `/`, `/about`, `/tools` and every script path that is not a run file path with it, and every path beginning with `page.StaticPrefix` with `page.Static()`, each inside `identity.Require`.
