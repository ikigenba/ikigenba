# D08-pages

What scripts draws as HTML and the addresses it draws with: the packages `internal/urls` and `internal/pages`; the six human-authored templates `landing`, `script`, `run`, `about`, `notfound` and `unavailable`, the data each page receives and the hooks each state emits; the handler that answers `/`, `/about` and every script path that is not one of a run's files — the catalog, a script's page, a run's page and the about screen, the redirects that add a missing trailing `/`, the not-found page, the plain-text answer when the catalog cannot be read, and the refusal of any other method; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the names this design behaves through outside its two packages: the root package's `Assets`, and the run seam whose `Banner` the binary sets to the `Banner` method of `page.New(pages.ServiceName, v)`, `v` being the display string `main` reads (`D01-layout-and-run-seam`), which is empty when the host sets no identity. `D04-store` declares `store.Store`, its `List`, `Find`, `Runs` and `FindRun`, the records `store.Script`, `store.Subscription` and `store.Run`, their status, reason and trigger words and `store.Unreachable`; `D05-git-and-source` declares `source.Source` and its `Name` and `RepoDir`; `D07-runs` declares `runs.Core` and its `Folder`, `Gone` and `Sizes`, and the names of a run folder's entries; `D09-run-files` declares the run file paths and the handler that answers them; `D03-serve` declares `web.Handler` and `web.Config`, defines a script path, and owns the route table, `identity.Require` around every route, the request's id and its two events, and that nothing reaches standard error while telemetry takes every event. The eleven tools' names and descriptions, whose first lines the catalog carries, are `D11-tools`'.

## Addresses

`internal/urls` builds the two addresses scripts writes into a page that are not its own: auth's profile page and auth's sign-out action, which the banner carries. Each reads the services file afresh through appkit's `services.Read` on every call, so a rewrite shows on the next page, and treats a file it cannot read — no path, no file, not a services file — as listing nothing, writing nothing about it. They are the `url` of the file's entry named `auth` followed by `/` and by `/logout`; with no such entry, or an empty `url`, the space is read from the request's `Host`, a trailing port dropped and then one leading `scripts.` label, and the scheme is the request's `X-Forwarded-Proto` when that is exactly `http` or exactly `https`, and `https` for anything else, as `S03` fixes it.

Every other address a page carries is a path of scripts' own, relative to the host the browser used: `/`, `/about`, `/<name>/`, `/<name>/runs/<run id>/` and the run's files beneath it. scripts never sends a visitor to sign in: nginx does that before a request reaches scripts (`S03`), and a request that arrives with no `X-User-Id` is appkit's `identity.Require` 500 on every route (`D03-serve`), so `urls` has no sign-in address.

## The template set and its data

The six templates are the files of `assets/`, embedded by the root package and returned by `Assets()`. `pages.Load` builds **scripts' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; the code adds no template function and writes no markup of its own. `Set.Write` is the one way any handler sends a page: it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set first, and sets nothing else. A `HEAD` gets the status and headers and no body.

Each template's data is a named struct whose fields are exactly what its page shows, every value already formatted as the page shows it, so a template does no arithmetic and no formatting:

- `LandingData`: the banner and one `ScriptRow` per script of the caller's, by name; a row carries the script's name, its page's path, its `Repo` (the id and the name read now, empty when it cannot be read), its ref and its last run as a `RunRow`, nil when it never ran.
- `ScriptData`: the banner, a `ScriptCard` (id, name, `Repo`, ref, created, how many runs are kept and the retention rule), one `RunRow` per run, newest first: id, page path, status word and kind, short commit, start, duration and exit code, and the event patterns the script is subscribed to, each exactly as subscribed, sorted by pattern, with no time, since the page shows none (`S12`).
- `RunData`: the banner, a `ScriptLink` (name and path), a `RunCard` (everything the headline, the alerts and the run card show, the first word of the running notice (`.Notice`, shown in `strong#notice`), the run's trigger and, for a run an event started, that event's id among it), a `FileText` for each of `input.json`, `stdout` and `stderr` that exists, and one `FileRow` per regular file under `out/`.
- `AboutData`: the banner and `pages.Description`, the manifest's one-line description.
- `NoticeData`: only a banner, from which the not-found page draws appkit's footer, `scripts` followed by one space and the display string `main` reads (`D01-layout-and-run-seam`); it draws no banner.

No data type has a field for a script's owner, a run's reason word, or anything of another user's, so no page can show them. The banner and what it holds, in order — the mark showing the favicon, the product name `Ikigenba` and the service, scripts' own icon before its name when the `page.Banner` carries one and its name alone otherwise; the launcher button after the mark; the profile link titled with the email; the sign-out form around an icon button with no text of its own, labelled and titled `Sign out` — the launcher's entries in the file's order, a switched-off service titled `<name> is unavailable`, scripts' own entry marked current, and the icon in the mark, which the kit's `Banner` takes from the entry it marks current and leaves empty when it marks none, are appkit's output (its page banner and page templates designs); this design states which data a page is drawn with, and one binary-level requirement proves that the binary's banner source is appkit's kit reading the services file. Over a services file that lists scripts with an icon, that kit marks scripts' entry current and so shows scripts' icon in the mark; the exec test's services file gives every entry, `scripts` included, an icon (R-XW4F-83YL), so its banner carries that icon in the mark as well as in the launcher, and the strings that requirement keeps out of every icon keep its counts true with the icon in both places.

The `unavailable` template is in the set, because `D01-layout-and-run-seam` embeds six templates, but no answer of scripts draws it: every story answers a catalog that cannot be read with the plain text `D04-store` fixes, never with a page (see Decisions).

## The pages handler

`pages.Handler` answers `/`, `/about`, and every **script path** — every path but `/`, `/about`, `/mcp`, `/events`, `/declarations` and those beginning `/_appkit/`, as `D03-serve` defines it (R-6T5B-KO7F) — that is not a **run file path** (`D09-run-files`). `D03-serve` routes those paths to it inside `identity.Require`, so it never sees a request without a caller, and a test wraps it the same way. It reads the path as **pieces**: the escaped path less its leading `/`, split at every `/`, each piece percent-decoded. A piece is compared byte for byte, never tidied: `.`, `..`, an empty piece and a piece that was percent-encoded are names like any other and match nothing that is not spelled so.

Each request is answered in the order the stories fix. The method first: anything but `GET` and `HEAD` is refused 405 with `Allow: GET, HEAD` and an empty body, before the catalog is read, so the answer is the same for a script, another user's script and no script. Then:

- `/about` draws the about screen, reading no catalog and running no git, so it is served with the catalog unreachable. Its `Version` fact is the banner's `Version`, the display string, and stays on the screen whatever that holds, the empty string included, when the host sets no identity.
- `/` reads the caller's scripts with `store.List`, once, reads no run folder, and draws the catalog.
- A script path looks its first piece up among the caller's own scripts with `store.Find`. A name that is none of theirs — no script, another user's, a different letter case, `about`, `mcp`, `events`, `declarations` — is the not-found page, whatever follows it, so `/events/` and `/declarations/repo.pushed` are answered with it and never reach the events app's handlers (`S12`). Under one of theirs: the path that is the name alone is redirected 301 to `/<name>/`, the query kept; `/<name>/` draws the script page; `/<name>/runs/<run id>` and `/<name>/runs/<run id>/` look the run up with `store.FindRun`, and a run of this script is redirected or drawn the same way, while any other run id is the not-found page; every other path under the script, `/<name>/runs/` included, is the not-found page.
- Any catalog read that answers neither a record nor `store.ErrNotFound` is answered `503` with the plain text `store.Unreachable` and a newline, as every consumer answers it (`D04-store`), with no banner and no footer.

The contract states that answer for a failing store and for a request whose context is already done as it arrives: turning on `SetFailing` for the store's handle and cancelling a request's context are the ways the test rules allow to fail the catalog, and each fails the first read, `List` or `Find`. So no permitted test can fail `Runs` or `FindRun` alone, and a failure of either alone, answered the same way, is unstated as contract until the test rules decide whether a seam may fail one read. Likewise, that `/about` and a 405 read no catalog and that the catalog page reads it once and reads no run folder are contract only through their answers: a read that changes no answer is not observable by a permitted test.

The not-found page is the `notfound` template with status 404, drawn with the banner the banner source gives for the empty `page.User`, so the answer to a path naming another user's script or run is byte for byte the answer to one naming nothing. A `HEAD` is answered with the status and headers its `GET` has and no body, redirects and refusals included. No answer sets a cookie. A page reads the catalog and, for the run page, the run's folder through `runs.Core`; it runs git only to read a repository's name with `source.Name`, and only where a page shows it: each listed script's on the catalog, the script's on its page, and on a run page only for a failure sentence that names the repository. Drawing a page writes nothing anywhere: nothing is created under the runs directory, not even a folder for a script that has never run.

## What each page shows

A status reads as a word with a kind: `queued` and `running`, `info`; `exited <n>`, `ok` when `<n>` is 0 and `warn` otherwise; `timed out` and `killed`, `warn`; `failed`, `err`. A time in a table reads in UTC to the minute, `2026-10-05 09:31`; the script's created time reads `2026-09-18 16:40 UTC`; a run page's times read to the second, `2026-10-05 09:14:02 UTC`; each sits in a `time` whose `datetime` is RFC 3339 in UTC. A duration is the record's finished less its started, `12s` under a minute and `3m 41s` from a minute on, and is empty while the run is queued or running and when it failed to start. A size is `<n> B` under 1000 bytes and otherwise thousands, truncated to one decimal, `kB` and then `MB` from a million: `1.2 kB`, `12.0 kB`, `1.0 MB`. A commit in a table is its first seven digits; on the run page it is whole; both are empty when the ref never resolved. An exit code shows only for `exited`.

A repository is shown by the name `source.Name` reads from its directory as the page is drawn, with its id beside it, or, when there is no name to read, by its id, muted and titled `the repository is gone` — one treatment for a directory that is gone, a config without the name and a git that cannot read it (`D05-git-and-source`).

The run page shows the run in one of its states. A run still `running` carries `div#running`, saying the page does not stream, and `a#reload` back to itself; it shows what its files hold so far, its Output line measured from them (`runs.Core.Sizes`). A run still `queued` has not ended either, so its card's `Running` is true and its page carries the same `div#running` and `a#reload`, the notice's first word, `strong#notice`, being the card's `Notice`: `Queued` while the run is queued, as S13's `A user opens a queued run` quotes it, and `Running` once it has started; its headline reads `queued` and its start, with no duration, its card has no `Finished` and no `Duration`, and since its script has not started its folder holds no stream file, so it shows no Standard output or Standard error section, `No files.`, and an Output line of `0 B` for each stream. A run abandoned in the queue (`store.ReasonQueueAbandoned`) is a run that failed to start, shown as one, with the commit it had resolved. A run that failed to start carries `div#failure` with a title and a plain-text sentence for its reason, the sentence naming the ref, the repository (by its name, read now, or its id), or the setting whose limit it met; its headline holds the time alone, and its card shows `Finished` and no `Duration`. A run whose output was cut carries one `output truncated` badge beside its status, whichever stream was cut, and its sizes are the bytes kept. A run whose folder is gone (`runs.Core.Gone`) carries `div#files-gone` and none of the four sections of files. Otherwise the Input, Standard output and Standard error sections are present only for a file that exists, each showing the file whole in a `pre`, or `No input.` or `No output.` for an empty one, with a Download link to the file's address (`D09-run-files`); and Files lists every regular file under `out/`, at any depth, hidden ones included and symbolic links left out, by path, each with its size and a Download link. The card's first line, `p#started-by`, says who started the run: `Started by the event <id>.`, the event's id in a code element, for a run an event started (`S27`), and `Started by the run tool.` for one the `run` tool started; the card's `Trigger` reads `event` or `manual`.

A script page lists, in `section#subscriptions`, the event patterns the script is subscribed to, each exactly as subscribed, sorted by pattern, each in its own `li[data-event]`, or says the script is subscribed to none; it shows no subscription's time.

## Reading the page

The tests have no HTML parser, since none is an approved dependency, so this design fixes the hooks the stories and the templates' opening comments name and the visible text the stories quote, and defines how each is read with the standard library: start and end tags, attributes read left to right, with or without a value, an element's content, and normalisation (tags removed, character references unescaped, whitespace collapsed). Rules about a page's own markup are read over its **written markup**, the body with appkit's banner and footer taken out. The hook requirements are stated for a **plain page request**, whose inputs carry nothing that would make appkit's banner ambiguous; the byte-for-byte requirements cover every other input, so `html/template`'s contextual autoescaping is what keeps a caller's, a repository's or a script's bytes from becoming markup. A hook a template lacks is an issue for a human, never a change to the asset. The icon appkit's mark shows is the `page.Banner`'s `Icon`, the services file's SVG inserted verbatim as the launcher's icons are; a banner the kit returns carries as its `Icon` one of its `Services`' icons, or nothing when it lists none, so the conditions a requirement puts on the launcher's icons, or its banner's holding no `page.Service`, hold of the mark's icon too, and a test's banner source keeps to the same rule. The mark's favicon is an `img` inside the appkit banner, so it is not the page's icon link, which the written markup carries.

## The head every page carries

Every page scripts draws — the catalog, the about screen, a script's page, a run's page and the not-found page — carries the same six things before its body: a `title`, one stylesheet link to `/_appkit/theme.css`, one font preload link, which has the browser fetch upright Inter, the face nearly all the page's text is set in, before the stylesheet asks for it, one icon link to `/_appkit/favicon.svg` of type `image/svg+xml`, the suite's one favicon, one deferred script loading `/_appkit/feedback.js`, appkit's button-feedback script, and the phone-width viewport, `width=device-width, initial-scale=1`. The head is the template's, not appkit's: a page opts in to the feedback script by linking it, as it links the stylesheet, and the appkit banner does not load it, so the not-found page, which draws no banner, links it all the same; the favicon link is the template's for the same reason. The preload link is the one head element appkit draws: the font's URL carries a hash of its bytes that scripts never writes, so each page template — `landing`, `script`, `run`, `about`, `notfound` and `unavailable` — invokes `{{template "preload"}}` in its head, beside its stylesheet link, and appkit's `preload` template renders the link, with `rel` `preload`, `as` `font`, `type` `font/woff2`, a bare `crossorigin`, and `page.PreloadURL()` as its `href`. What the preload does in a browser is a browser's, so what is fixed is that link's attributes. The `unavailable` template carries the same head, though no answer draws it. What the script does in a browser — press feedback on buttons — is appkit's and needs a JavaScript engine the gates do not have, so what is fixed is the hook a standard-library test can see: the `script` start tag in the head, its `src` and its `defer`, which a page writes bare and which a start tag bears whether written bare or with a value. A page carries no script of its own: the only `script` start tags its own markup holds are the feedback script's, whose `src` names a path on scripts' own host, and the launcher's script sits in the appkit banner. A run's files are the run's own (`D09-run-files`); none of this reaches them.

## The shared files

The stylesheet, its three fonts, one of which every page preloads, the launcher's script, the button-feedback script, the favicon and the two licences are the platform's shared files: appkit's `page` package embeds them and `page.Static()` serves them under `page.StaticPrefix`, `/_appkit/`. scripts holds no copy and reads nothing from disk for them; `D03-serve` hands every request whose path begins with `page.StaticPrefix` to that handler unchanged, inside `identity.Require` like every route. The requirements here restate what `S04` fixes about the answer as scripts' own behaviour at `web.Handler`, so scripts' tests fail if a different appkit release stopped giving it. Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`.

Six shared files have fixed names: `theme.css`, `launcher.js`, `feedback.js`, `favicon.svg`, `OFL.txt` and `TABLER-LICENSE.txt`. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit are not served, and a font path with its hash taken out answers 404 like any other name appkit does not serve. scripts never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads, and the paths the served stylesheet names, each a `url("…")` of a name ending in `.woff2` beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet scripts serves. Every 200 and 304 for a shared file carries one strong `ETag`; a font path's carries one `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again, and every other shared file's one `Cache-Control: no-cache`, so a browser keeps its copy but asks each time.

## Decisions

- The catalog unreachable is plain text, not the `unavailable` template: `S03`, `S12`, `S13` and `S14` all fix `503` with the one line `cannot reach the catalog; try again later`, no banner and no footer, and `D04-store` fixes the same for every consumer. The `unavailable` template therefore has no answer; whether to delete it (with `D01-layout-and-run-seam`'s six-file `Assets` and `AGENTS.md`'s asset list) is a question for a human.
- There is no guest branch and no `urls.SignIn`: unlike sites, every route is behind `identity.Require`, nginx sends a visitor with no credential to sign in, and a request without `X-User-Id` is a 500 (`S03`).
- The scheme is exactly `http` or exactly `https`, case-sensitively, as `S03` words it (`HTTPS` is `https` because it is neither); sites lowercases first.
- The handler reads the caller from `identity.FromContext`, so its behaviour is stated for `identity.Require(pages.Handler(cfg))`.
- `ScriptData.Subscriptions` is a slice of patterns, not of `store.Subscription`: the page shows no subscription's time, so the data carries none, and the order is the catalog's, by pattern.
- `RunCard.Notice` carries the first word of `div#running`, `Queued` or `Running`, in `strong#notice`, so the template prints a value rather than choosing between status words; it is empty when `Running` is false.
- `RunCard.Event` is the run's `Event`, empty for a manual run; the template chooses the card's first line from it, so the data needs no flag of its own.
- One `RunRow` type serves both a script's runs and the catalog's last run, whose template reads only its status, kind and start.
- The data carries every value formatted, so the rules for words, kinds, times, durations, sizes and short commits are stated once, here, and the templates only place them.
- The run page carries one `Truncated`, the record's, not one per stream: the record has one flag and `S13` shows one badge.
- Sizes are truncated, not rounded, to one decimal, so a value never reads `1000.0 kB`; every example the stories give reads the same either way.
- A piece is percent-decoded before it is compared, so a link the page writes for a file whose name needs escaping leads back to it; nothing is tidied, so a decoded `.` or `..` is still a piece that names nothing.
- The not-found page is drawn with the banner for the empty `page.User`, so it is the same bytes for every caller.
- The HTML reading vocabulary is defined here once and may be used by any scripts document that reads a page.

## Consumer tasks

`web.Handler` calls `pages.Load()` once, when it is built, and builds `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: path, Store: cfg.Store, Source: cfg.Source, Runs: cfg.Runs, KeepDays: s.RunKeepDays, KeepCount: s.RunKeepCount, TreeMaxBytes: s.TreeMaxBytes, OperationSeconds: s.OperationSeconds})`, the four numbers being the settings `D12-limits` read at start; it serves `/`, `/about` and every script path that is not a run file path with it, and every path beginning with `page.StaticPrefix` with `page.Static()`, each inside `identity.Require`. It builds `web.Files(web.FilesConfig{Banner: cfg.Banner, Pages: set, Store: cfg.Store, Runs: cfg.Runs})` with the same set and serves every run file path with it (`D09-run-files`). `cli.Manifest`'s description and the MCP server's name use `pages.Description` and `pages.ServiceName`.

A page request: `GET /nightly-report/runs/run_d4a7e2c9f1b8630a/` reaches `pages.Handler` with the caller on its context; the method is `GET`; the pieces are `nightly-report`, `runs`, `run_d4a7e2c9f1b8630a` and the empty string; `cfg.Store.Find(ctx, u.UserID, "nightly-report")` gives the script, `cfg.Store.FindRun(ctx, u.UserID, "run_d4a7e2c9f1b8630a")` the run, whose `Script` is the script's `ID`; the run is `failed` with `commit_missing`, so `cfg.Source.Name(ctx, sc.Repo)` reads the repository's name for the sentence; `cfg.Runs.Gone(r)` is false, so `cfg.Runs.Folder(r)` is read for `input.json`, `stdout`, `stderr` and `out/`; `cfg.Banner` is called with the banner user; and `cfg.Pages.Write(w, r, 200, "run", pages.RunData{...})` sends the page. Where a script page was drawn with `pages.ScriptData{Banner: b, Script: card, Runs: rows}` and a run's card with `pages.RunCard{..., Trigger: r.Trigger, User: r.User, ...}`, they are now drawn with `pages.ScriptData{Banner: b, Script: card, Runs: rows, Subscriptions: names}`, `names` holding `sub.Event` for each `sub` of `sc.Subscriptions`, and `pages.RunCard{..., Trigger: r.Trigger, Event: r.Event, User: r.User, ...}`.

A test of the handler builds a `store.Store` with `store.New` over a handle `db.Open` returned for a file in its temporary directory with `scripts.Migrations()`, creates scripts, subscribes them with `Subscribe`, and adds runs with `AddRun` and `FinishRun`, event runs among them, makes bare repository fixtures with the names it chooses, makes run folders under a temporary `Runs` the `runs.Core` it builds names (or removes one), writes a services file in its temporary directory, builds `identity.Require(pages.Handler(pages.Config{...}))` with a `Banner` closure that counts its calls and returns a fixed `page.Banner`, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of scripts' template set from `page.Templates()` and `scripts.Assets()`, executes `landing`, `script` or `run` with the data it expects, built from its own store calls and the formatting rules below, and compares bodies byte for byte; it reads hooks with the reading vocabulary below. It calls `SetFailing(true)` on that handle, or serves a request whose context it cancelled first, to make the catalog unreachable, and reads the trace `GIT_TRACE` names in its git environment to see which git ran. A test of `urls` calls each function with a request and a services file of its own. A test of the shared files builds `web.Handler` as `D03-serve` states and requests `/_appkit/...` with `X-User-Id` set. The one exec test of the binary in `cmd/scripts` rewrites the services file between two `GET /` requests.
