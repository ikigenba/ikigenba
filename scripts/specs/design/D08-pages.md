# D08-pages

What scripts draws as HTML and the addresses it draws with: the packages `internal/urls` and `internal/pages`; the six human-authored templates `landing`, `script`, `run`, `about`, `notfound` and `unavailable` and the three partials `run-status`, `run-duration` and `file-size` that `run.html` defines, the data each receives and the layouts its times are formatted with; the handler that answers `/`, `/about` and every script path that is not one of a run's files — the catalog, a script's page, a run's page and the about screen, the redirects that add a missing trailing `/`, the not-found page, the unavailable page when the catalog cannot be read, and the refusal of any other method; and the shared files under `/_appkit/` every page loads. `D01-layout-and-run-seam` declares the names this design behaves through outside its two packages: the root package's `Assets`, and the run seam whose `Banner` the binary sets to the `Banner` method of `page.New(pages.ServiceName, v)`, `v` being the display string `main` reads (`D01-layout-and-run-seam`), which is empty when the host sets no identity. `D04-store` declares `store.Store`, its `List`, `Find`, `Runs` and `FindRun`, the records `store.Script`, `store.Subscription` and `store.Run`, their status, reason and trigger words and `store.Unreachable`; `D05-git-and-source` declares `source.Source` and its `Name` and `RepoDir`; `D07-runs` declares `runs.Core` and its `Folder`, `Gone` and `Sizes`, and the names of a run folder's entries; `D09-run-files` declares the run file paths and the handler that answers them; `D03-serve` declares `web.Handler` and `web.Config`, defines a script path, and owns the route table, `identity.Require` around every route, the request's id and its two events, and that nothing reaches standard error while telemetry takes every event. The eleven tools' names and descriptions are `D11-tools`'.

## Addresses

`internal/urls` builds the two addresses scripts writes into a page that are not its own: auth's profile page and auth's sign-out action, which the banner carries. Each reads the services file afresh through appkit's `services.Read` on every call, so a rewrite shows on the next page, and treats a file it cannot read — no path, no file, not a services file — as listing nothing, writing nothing about it. They are the `url` of the file's entry named `auth` followed by `/` and by `/logout`; with no such entry, or an empty `url`, the space is read from the request's `Host`, a trailing port dropped and then one leading `scripts.` label, and the scheme is the request's `X-Forwarded-Proto` when that is exactly `http` or exactly `https`, and `https` for anything else.

Every other address a page carries is a path of scripts' own, relative to the host the browser used: `/`, `/about`, `/<name>/`, `/<name>/runs/<run id>/` and the run's files beneath it. scripts never sends a visitor to sign in: nginx does that before a request reaches scripts, and a request that arrives with no `X-User-Id` is appkit's `identity.Require` 500 on every route (`D03-serve`), so `urls` has no sign-in address.

## The template set and its data

The six pages are the files of `assets/`, embedded by the root package and returned by `Assets()`; `run.html` also defines three partials, `run-status`, `run-duration` and `file-size`, which `landing`, `script` and `run` call. `pages.Load` builds **scripts' template set** by parsing every file of `Assets()` into a fresh set from appkit's `page.Templates()`, which already defines appkit's `banner`, `launcher`, `footer` and `preload`; the code adds no template function and writes no markup of its own. `Set.Write` is the one way any handler sends a page: it executes one named template with its data, writes exactly one `Content-Type: text/html; charset=utf-8` and the status, keeps whatever headers its caller set first, and sets nothing else. A `HEAD` gets the status and headers and no body.

Each template's data is a named struct whose fields are exactly what its page shows. The data carries values, never words: a run's status, exit code and failure reason as the store records them, a duration as whole minutes and seconds, a size as a scaled number and a unit, and the limits a failure names as numbers. Every word a page shows, the status word and its kind, the notice, a failure's title and sentence, the units, is chosen by the template from those values. Times are the one thing the code formats, with three layouts of `pages`, because a template cannot format a time without a function the set does not have:

- `LandingData`: the banner and one `ScriptRow` per script of the caller's, by name; a row carries the script's name, its page's path, its `Repo` (the id and the name read now, empty when it cannot be read), its ref and its last run as a `RunRow`, nil when it never ran.
- `ScriptData`: the banner, a `ScriptCard` (id, name, `Repo`, ref, created, how many runs are kept and the retention rule), one `RunRow` per run, newest first: id, page path, the store's status and exit code, short commit, start and a `Duration`, nil when the run has none, and the event patterns the script is subscribed to, each exactly as subscribed, sorted by pattern, with no time, since the page shows none.
- `RunData`: the banner, a `ScriptLink` (name and path), a `RunCard` (everything the run's summary shows: its status and exit code, whether it has not ended yet, its times, its `Duration`, its stream sizes as `Size`s, its `Failure`, the run's trigger and, for a run an event started, that event's id among it), a `FileText` for each of `input.json`, `stdout` and `stderr` that exists, and one `FileRow` per regular file under `out/`, each with its `Size`.
- `AboutData`: the banner and `pages.Description`, the manifest's one-line description.
- `NoticeData`: only a banner, from which the not-found and unavailable pages draw appkit's footer with the service name and the display string `main` reads (`D01-layout-and-run-seam`).

The three partials take a part of that data: `run-status` a `RunRow` or a `RunCard`, of which it reads the status and exit code, `run-duration` a `Duration` and `file-size` a `Size`. They are named so a test can execute one alone, and are proved by use: each page that calls one is compared whole.

No data type has a field for a script's owner or anything of another user's, so no page can show them; a run's reason is carried only in its `Failure`. What the banner holds — the mark, the launcher and its entries in the services file's order, the profile link and the sign-out form — is appkit's output (its page banner and page templates designs); this design states only which data a page is drawn with, and one binary-level requirement (R-OWYV-ML7F) proves that the binary's banner source is appkit's kit reading the services file afresh.

The `unavailable` page is what a page path answers when the catalog cannot be read: status 503, drawn with the banner the banner source gives for the empty `page.User`, as the not-found page is, so it carries nothing of the error and is the same bytes for every caller. A run's files are not pages: `D09-run-files` answers them with the plain-text catalog refusal this design defines, and the tools answer with `store.Unreachable` (`D11-tools`).

## The pages handler

`pages.Handler` answers `/`, `/about`, and every **script path** — every path but `/`, `/about`, `/mcp`, `/events`, `/declarations` and those beginning `/_appkit/`, as `D03-serve` defines it (R-6T5B-KO7F) — that is not a **run file path** (`D09-run-files`). `D03-serve` routes those paths to it inside `identity.Require`, so it never sees a request without a caller, and a test wraps it the same way. It reads the path as **pieces**: the escaped path less its leading `/`, split at every `/`, each piece percent-decoded. A piece is compared byte for byte, never tidied: `.`, `..`, an empty piece and a piece that was percent-encoded are names like any other and match nothing that is not spelled so.

Each request is answered in this order. The method first: anything but `GET` and `HEAD` is refused 405 with `Allow: GET, HEAD` and an empty body, before the catalog is read, so the answer is the same for a script, another user's script and no script. Then:

- `/about` draws the about screen, reading no catalog and running no git, so it is served with the catalog unreachable. Its `Version` fact is the banner's `Version`, the display string, and stays on the screen whatever that holds, the empty string included, when the host sets no identity.
- `/` reads the caller's scripts with `store.List`, once, reads no run folder, and draws the catalog.
- A script path looks its first piece up among the caller's own scripts with `store.Find`. A name that is none of theirs — no script, another user's, a different letter case, `about`, `mcp`, `events`, `declarations` — is the not-found page, whatever follows it, so `/events/` and `/declarations/repo.pushed` are answered with it and never reach the events app's handlers. Under one of theirs: the path that is the name alone is redirected 301 to `/<name>/`, the query kept; `/<name>/` draws the script page; `/<name>/runs/<run id>` and `/<name>/runs/<run id>/` look the run up with `store.FindRun`, and a run of this script is redirected or drawn the same way, while any other run id is the not-found page; every other path under the script, `/<name>/runs/` included, is the not-found page.
- Any catalog read that answers neither a record nor `store.ErrNotFound` is answered with the unavailable page, status 503.

The contract states that answer for a failing store and for a request whose context is already done as it arrives: turning on `SetFailing` for the store's handle and cancelling a request's context are the ways the test rules allow to fail the catalog, and each fails the first read, `List` or `Find`. So no permitted test can fail `Runs` or `FindRun` alone, and a failure of either alone, answered the same way, is unstated as contract until the test rules decide whether a seam may fail one read. Likewise, that `/about` and a 405 read no catalog and that the catalog page reads it once and reads no run folder are contract only through their answers: a read that changes no answer is not observable by a permitted test.

The not-found page is the `notfound` template with status 404, drawn with the banner the banner source gives for the empty `page.User`, so the answer to a path naming another user's script or run is byte for byte the answer to one naming nothing. A `HEAD` is answered with the status and headers its `GET` has and no body, redirects and refusals included. No answer sets a cookie. A page reads the catalog and, for the run page, the run's folder through `runs.Core`; it runs git only to read a repository's name with `source.Name`, and only where a page shows it: each listed script's on the catalog, the script's on its page, and on a run page only for a run that failed to start, whose `Failure` carries the repository. Drawing a page writes nothing anywhere: nothing is created under the runs directory, not even a folder for a script that has never run.

## How the data is formatted

The data carries values and the templates choose the words. A run's `Status` and `ExitCode` are the record's, the exit code 0 unless the run exited (`D04-store`); `run-status` turns them into the status word and its kind. A time in a table is formatted with `pages.MinuteLayout`, the script's created time with `pages.CardLayout` and a run page's times with `pages.SecondLayout`, each in UTC and each carried as well in its RFC 3339 form; the layouts are copy constants of `pages`, declared by name and never by value. A duration is the record's finished less its started, in whole seconds, carried as whole minutes and the seconds left over, and is nil while the run is queued or running and when it failed to start; `run-duration` writes it, leaving out the minutes when there are none. A size is the byte count scaled by the code: bytes under 1000, otherwise thousands or millions truncated to one decimal, carried as that number as a string and the unit `byte`, `kilobyte` or `megabyte`; `file-size` writes the unit's word. A commit in a table is its first seven digits; on the run page it is whole; both are empty when the ref never resolved. So changing how a page reads touches one template and no requirement.

A repository is carried as its id and the name `source.Name` reads from its directory as the page is drawn, the name empty when there is none to read — one treatment for a directory that is gone, a config without the name and a git that cannot read it (`D05-git-and-source`).

The run data carries what the run page needs for each state of a run. A run that has not ended, queued or running, has `Running` true, and the template words its notice from `Status`; it carries what its files hold so far and its stream sizes measured from them (`runs.Core.Sizes`); a queued run has no finish and no duration, and since its script has not started its folder holds no stream file. A run abandoned in the queue (`store.ReasonQueueAbandoned`) is a run that failed to start, with the commit it had resolved. A run that failed to start carries a `Failure`: its reason as recorded, the script's repository (its id and the name read now), the ref, and the two limits a reason may name, `TreeMaxBytes` and `OperationSeconds`; the template chooses the failure's title and sentence from the reason and names what it needs from the rest. A run whose output was cut carries one `Truncated`, whichever stream was cut, and its sizes are the bytes kept. A run whose folder is gone (`runs.Core.Gone`) has `FilesGone` true and no file data. Otherwise `Input`, `Stdout` and `Stderr` are present only for a file that exists, each with the file whole and its address (`D09-run-files`), and `Files` lists every regular file under `out/`, at any depth, hidden ones included and symbolic links left out, by path, each with its size and address. The card's `Trigger` and `Event` say who started the run: an event, by its id, or the `run` tool.

A script's data carries the event patterns the script is subscribed to, each exactly as subscribed, sorted by pattern, and no subscription's time.

## How a page is proved

A test proves a page by executing the named template of its own copy of scripts' template set with the data this design states and comparing the body byte for byte, or by checking that a value it supplied appears in the body. No requirement names a heading, a label, a sentence, a class, an id or an attribute, and none defines how markup is read: the words and hooks are the templates', documented in each template's opening comment. `html/template`'s contextual autoescaping is what keeps a caller's, a repository's or a script's bytes from becoming markup, and the byte-for-byte requirements cover every input. A template that cannot show a state this design names is an issue for a human, never a change to the asset.

## The head

Each template carries its own head, which loads appkit's stylesheet, favicon and button-feedback script from `/_appkit/` and invokes appkit's `preload` template for the font, whose URL carries a hash of its bytes that scripts never writes. What the head holds is the template's, so no requirement states it; the shared files it loads are served as the next section states. A run's files are the run's own (`D09-run-files`); none of this reaches them.

## The shared files

The stylesheet, its three fonts, one of which every page preloads, the launcher's script, the button-feedback script, the favicon and the two licences are the platform's shared files: appkit's `page` package embeds them and `page.Static()` serves them under `page.StaticPrefix`, `/_appkit/`. scripts holds no copy and reads nothing from disk for them; `D03-serve` hands every request whose path begins with `page.StaticPrefix` to that handler unchanged, inside `identity.Require` like every route. The requirements here state appkit's answer as scripts' own behaviour at `web.Handler`, so scripts' tests fail if a different appkit release stopped giving it. Revalidation is fixed only for a request carrying none of `Range`, `If-Match`, `If-Unmodified-Since` and `If-Range`.

Six shared files have fixed names: `theme.css`, `launcher.js`, `feedback.js`, `favicon.svg`, `OFL.txt` and `TABLER-LICENSE.txt`. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit are not served, and a font path with its hash taken out answers 404 like any other name appkit does not serve. scripts never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads, and the paths the served stylesheet names, each a `url("…")` of a name ending in `.woff2` beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet scripts serves. Every 200 and 304 for a shared file carries one strong `ETag`; a font path's carries one `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again, and every other shared file's one `Cache-Control: no-cache`, so a browser keeps its copy but asks each time.

## Decisions

- The catalog unreachable on a page path is the `unavailable` page with status 503, drawn with the banner for the empty `page.User`, as the not-found page is: a person reaching a page gets a page. Every other answer to it keeps `store.Unreachable`: a run's files, whose bytes are the run's, with the plain-text catalog refusal, and the tools with their refusal.
- There is no guest branch and no `urls.SignIn`: unlike sites, every route is behind `identity.Require`, nginx sends a visitor with no credential to sign in, and a request without `X-User-Id` is a 500.
- The scheme is exactly `http` or exactly `https`, case-sensitively (`HTTPS` is `https` because it is neither); sites lowercases first.
- The handler reads the caller from `identity.FromContext`, so its behaviour is stated for `identity.Require(pages.Handler(cfg))`.
- `ScriptData.Subscriptions` is a slice of patterns, not of `store.Subscription`: the page shows no subscription's time, so the data carries none, and the order is the catalog's, by pattern.
- The data carries no word: no status word, kind, notice, failure title or text, and no unit word. The template chooses each from `Status`, `ExitCode`, `Failure.Reason` and `Size.Unit`, so a change to how a page reads is a change to one template.
- `RunCard.Event` is the run's `Event`, empty for a manual run; the template chooses the card's first line from it, so the data needs no flag of its own.
- One `RunRow` type serves both a script's runs and the catalog's last run, whose template reads only its status, exit code and start.
- The code still does the arithmetic a template cannot: a duration split into minutes and seconds, a size scaled to its unit, a commit shortened, and times formatted with the three layouts, which stay copy constants of `pages`. A `Duration` is a pointer so that a run with none carries nil rather than a zero that reads as a duration.
- A `Failure` carries the script's repository for every reason, so the run page of any failed run reads the repository's name; the template names it only where its sentence needs it.
- The three partials are templates of the set, named with the data each takes, so a test can execute `run-status` alone with a row or a card.
- The run page carries one `Truncated`, the record's, not one per stream: the record has one flag.
- Sizes are truncated, not rounded, to one decimal, so a size under a million never reads as a thousand thousands.
- A piece is percent-decoded before it is compared, so a link the page writes for a file whose name needs escaping leads back to it; nothing is tidied, so a decoded `.` or `..` is still a piece that names nothing.
- The not-found page is drawn with the banner for the empty `page.User`, so it is the same bytes for every caller.

## Consumer tasks

`web.Handler` calls `pages.Load()` once, when it is built, and builds `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: path, Store: cfg.Store, Source: cfg.Source, Runs: cfg.Runs, KeepDays: s.RunKeepDays, KeepCount: s.RunKeepCount, TreeMaxBytes: s.TreeMaxBytes, OperationSeconds: s.OperationSeconds})`, the four numbers being the settings `D12-limits` read at start; it serves `/`, `/about` and every script path that is not a run file path with it, and every path beginning with `page.StaticPrefix` with `page.Static()`, each inside `identity.Require`. It builds `web.Files(web.FilesConfig{Banner: cfg.Banner, Pages: set, Store: cfg.Store, Runs: cfg.Runs})` with the same set and serves every run file path with it (`D09-run-files`). `cli.Manifest`'s description and the MCP server's name use `pages.Description` and `pages.ServiceName`.

A page request: `GET /nightly-report/runs/run_d4a7e2c9f1b8630a/` reaches `pages.Handler` with the caller on its context; the method is `GET`; the pieces are `nightly-report`, `runs`, `run_d4a7e2c9f1b8630a` and the empty string; `cfg.Store.Find(ctx, u.UserID, "nightly-report")` gives the script, `cfg.Store.FindRun(ctx, u.UserID, "run_d4a7e2c9f1b8630a")` the run, whose `Script` is the script's `ID`; the run is `failed` with `commit_missing`, so `cfg.Source.Name(ctx, sc.Repo)` reads the repository's name for its `Failure`; `cfg.Runs.Gone(r)` is false, so `cfg.Runs.Folder(r)` is read for `input.json`, `stdout`, `stderr` and `out/`; `cfg.Banner` is called with the banner user; and `cfg.Pages.Write(w, r, 200, "run", pages.RunData{...})` sends the page. Where a script page was drawn with `pages.ScriptData{Banner: b, Script: card, Runs: rows}` and a run's card with `pages.RunCard{..., Trigger: r.Trigger, User: r.User, ...}`, they are now drawn with `pages.ScriptData{Banner: b, Script: card, Runs: rows, Subscriptions: names}`, `names` holding `sub.Event` for each `sub` of `sc.Subscriptions`, and `pages.RunCard{..., Trigger: r.Trigger, Event: r.Event, User: r.User, ...}`.

A test of the handler builds a `store.Store` with `store.New` over a handle `db.Open` returned for a file in its temporary directory with `scripts.Migrations()`, creates scripts, subscribes them with `Subscribe`, and adds runs with `AddRun` and `FinishRun`, event runs among them, makes bare repository fixtures with the names it chooses, makes run folders under a temporary `Runs` the `runs.Core` it builds names (or removes one), writes a services file in its temporary directory, builds `identity.Require(pages.Handler(pages.Config{...}))` with a `Banner` closure that counts its calls and returns a fixed `page.Banner`, and serves requests made with `httptest.NewRequest`, setting `Host`, `X-Forwarded-Proto`, `X-User-Id` and `X-User-Email` as nginx would. It builds its own copy of scripts' template set from `page.Templates()` and `scripts.Assets()`, executes `landing`, `script` or `run` with the data it expects, built from its own store calls, the rules above and `pages`' three layouts, and compares bodies byte for byte; it may execute a partial, `run-status` with a row it built, and find that text in a body. It calls `SetFailing(true)` on that handle, or serves a request whose context it cancelled first, to make the catalog unreachable, and compares the answer with `unavailable` executed with the `NoticeData` for the empty user's banner, and reads the trace `GIT_TRACE` names in its git environment to see which git ran. A test of `urls` calls each function with a request and a services file of its own. A test of the shared files builds `web.Handler` as `D03-serve` states and requests `/_appkit/...` with `X-User-Id` set. The one exec test of the binary in `cmd/scripts` rewrites the services file between two `GET /` requests.
