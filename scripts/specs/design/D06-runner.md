# D06-runner

How scripts starts a script's process and ends it. This document is `internal/runner`, the seam between the run core and the operating system: `Start` launches `python3.12 main.py` in a directory the caller names, with exactly the environment the caller gives, in a process group of its own and, when the caller names one, in a control group of its own bounded by the memory and process limits the caller gives, and returns a `*Process` whose `Wait` answers how `main.py` ended and whose `Kill` ends the whole group and says whether it ended `main.py` before `main.py` ended on its own. It declares every exported name of `internal/runner` but the Python version, which `D01-layout-and-run-seam` declares here (`PythonVersion`, `Interpreter`), and states what each does. `D07-runs` composes the environment, makes the run's folder, bounds the output through the writers it hands in, enforces `SCRIPT_SECONDS`, decides what status an ending is recorded with, and maps a failed `Start` to `start_failed`; `D03-serve` looks for the interpreter on `PATH` at start with `Find` and turns its absence into the start refusal `scripts: python3.12 not found on PATH`.

## The contract and the wrapper

The contract is the command, `python3.12 main.py`, the working directory, the environment, the two output streams, the process group, and what an ending reads as. How the process is wrapped is the runner's own: the first implementation is a plain `exec` of the interpreter, and bubblewrap is the planned second, which binds the run folder at a fixed path, binds `tree/` read-only and cuts the network while keeping the services' sockets reachable. Nothing above this package knows which is in use, so every requirement here is one both satisfy: a script finds its paths only through the variables it is given, signal deaths read as 128 plus the signal, and the group is killed whole. The run core never names the interpreter's path, never sets a process attribute, and never sends a signal itself.

## Starting

`Start` looks for `Interpreter` on the `PATH` the caller's environment carries, each time it is called, the way `Find` looks: so a `python3.12` removed from the host after scripts started makes the next `Start` fail, which the run core records as `start_failed`. It runs it with the one argument `main.py` and does not look for `main.py` itself: a tree with no `main.py` is a process that the interpreter ends with exit status 2, not a failed start. The process runs as scripts' own user and group, whatever the script holds. Its working directory is `Spec.Dir` as the process sees it (the bubblewrap runner may bind it elsewhere), its environment is exactly `Spec.Env`, nothing added, its standard input is empty, so a read sees end of file at once, and it holds no open descriptor but its three standard streams, whatever the calling process has open: scripts' own listening socket and database are never a script's. It is the leader of a new process group, so it and everything it starts that stays in that group can be ended with one signal. `Start` returns as soon as the process is running; it never waits for it. A context ended before `Start` starts nothing; once `Start` has returned, the context is no longer consulted, because a run outlives the request that started it and is ended only by `Kill`.

## The control group

When `Spec.Cgroup` names a directory, the run gets a control group of its own there, the run core naming it `<runs group>/<run id>` (`D07-runs`). `Start` makes the directory (never a missing parent; a directory already there is used as it is), writes the group's limits into it, `memory.max` `Spec.MemoryMax`, `memory.oom.group` `1`, `pids.max` `Spec.PidsMax` and `memory.swap.max` `0`, then opens the directory and asks `statfs(2)` what file system holds it. On a cgroup2 file system (`CGROUP2_SUPER_MAGIC`), the real tree, the process is created directly in the group: `syscall.ForkExec` with `SysProcAttr{Setpgid: true, UseCgroupFD: true, CgroupFD: <the directory's descriptor>}`, which is `clone3(2)` with `CLONE_INTO_CGROUP`, and nothing is written to `cgroup.procs`. So on a real tree no memory and no process of a run is ever charged to scripts' own `main/` group: the interpreter, and every process `main.py` starts, whatever process group or session it moves to, is born in the run's group under its limits. On any other file system, a stand-in only a test provides, `Start` starts the process as above and then writes its pid to `cgroup.procs`, and a write that fails kills it. A limit write that fails, a directory that cannot be made or opened, or a process that cannot be created in the group, starts nothing or kills what it started, and `Start` returns an error, which the run core records as `start_failed`; a directory `Start` made is removed again. When `main.py` has ended, `Wait` writes `1` to `cgroup.kill`, which kills every process still in the group, the ones that left the process group included, and removes the directory; a directory that cannot be removed does not change what `Wait` answers. An empty `Cgroup` gives the process no group of its own and makes `MemoryMax` and `PidsMax` meaningless; the run core never passes one when runs are available, but a test of the runner, or of the core, may.

Every operation on the group is a plain file operation under `Spec.Cgroup` — make a directory, write a file, remove the directory — but the placement, which on the real tree is the `clone3` above, so a test hands the runner a temporary directory standing in for the tree and reads back the files, the stand-in's `cgroup.procs` showing where the process was put; a real control group is never available to a gate, and the cgroup2 path is proved by the sandbox and space exercise (`D13-on-a-space`), not by a gate. The writes carry no newline. On a real cgroup file system the interface files already exist when the directory is made, a write to one is the kernel's to accept or refuse, and the directory is removed with `rmdir` once no process is left in it (`SIGKILL` being asynchronous, the runner waits for the group to empty, as it waits for the process group); on a stand-in the files are made by the writes and removed with the directory. The file system type decides only the placement; every other step is the same on both.

## Output

What the process and its group write to standard output and standard error is copied to `Spec.Stdout` and `Spec.Stderr` as it arrives, in order, every byte written before `main.py` exited delivered before `Wait` returns. A writer that fails does not stop the process or block it: the rest of that stream is read and dropped. Bounding what is kept is the writer's business (`D07-runs`). A nil writer discards its stream.

## Ending

A run is `main.py`'s: `Wait` returns when `main.py`'s own process has ended, whatever it started. When it ends, the runner kills whatever is left in its process group before it collects `main.py`'s status, and `Wait` returns only once every process of the group is gone, collected or a zombie, since `SIGKILL` takes effect asynchronously; while the group's id is still `main.py`'s and cannot be reused by another run's group; so nothing a script starts and leaves in its group outlives the run, writes to its output after it, or holds `Wait` open. A process that left the group (with `setsid`, say) is out of reach of the plain runner; it cannot hold `Wait` open either, since the runner stops reading the streams once the group is gone, and what it writes afterwards is dropped. Bubblewrap's own process namespace closes that gap.

`Wait` answers one number, the run's exit code under the status rule: the status `main.py` exited with, or 128 plus the signal's number when `main.py` died of a signal, so 143 for a `SIGTERM` it sent itself and 137 for a `SIGKILL`, the kernel's out-of-memory kill included: with `memory.oom.group` set, a group that needs more than `memory.max` is killed whole by `SIGKILL`, so the run reads `exited` 137, never `killed`. `Kill` sends `SIGKILL` to the whole process group, `main.py` and every process in its group, and answers true when it reached `main.py` before `main.py` had exited; `Wait` then answers 137. It answers false when `main.py` had already ended on its own, which is how the run core refuses a `cancel` that lost the race to the run's own exit (`D07-runs`). Which ending the run core records, `exited`, `killed` or `timed_out`, is decided by who called `Kill` and why, which the run core knows and the runner does not. `Kill` and `Wait` may be called from any goroutine, any number of times; `Kill` after `Wait` has returned does nothing and answers false.

## Proofs

Linux facts the requirements rest on, from the manual pages and observed with the host's `python3.12` started from Go: setpgid(2), a process made with a process group id of 0 becomes the leader of a new group whose id is its pid (observed: `os.getpgrp() == os.getpid()`, different from the parent's group); kill(2), a negative pid sends the signal to every process of that group; wait(2) and waitid(2), a child killed by a signal reports `WIFSIGNALED` and the signal, and `WNOWAIT` leaves the child waitable, so its pid, and with it the group id, is not reused until it is collected (observed: `kill(-pid, SIGKILL)` after `waitid(..., WEXITED|WNOWAIT)` killed a child `main.py` left running, which was gone afterwards); execve(2), a descriptor without close-on-exec stays open across exec (observed: a descriptor the parent opened without `O_CLOEXEC` was open in the script, so the runner must close it); and that a child left holding the output pipe keeps a plain `exec.Cmd.Wait` from returning (observed), which is why the group is killed before the status is collected and the streams are not waited on past it; and that `SIGKILL` is asynchronous (observed: in 200 trials of 200, a process just sent `SIGKILL` through `killpg` still showed state `R` in `/proc/<pid>/stat` immediately afterwards), which is why `Wait` waits until every process of the group is gone rather than returning when the signal is sent. execve(2) and credentials(7): a process keeps its parent's user and group ids across fork and exec unless the file executed is set-user-ID or set-group-ID, which an interpreter on `PATH` is not, so the plain runner sets no credential and the script runs as scripts does (observed: `os.getuid()`, `os.geteuid()`, `os.getgid()` and `os.getegid()` printed by `python3.12` equal the starting process's ids). Control groups, from the kernel's `Documentation/admin-guide/cgroup-v2.rst`: a group is a directory of the cgroup file system, made with `mkdir` and removed with `rmdir` once it has no live process and no child group; writing a pid to `cgroup.procs` migrates that process into the group, and a process's children are born in its group; `memory.max` is the hard memory limit, past which the group's processes are killed by the out-of-memory killer, and with `memory.oom.group` `1` the whole group is killed together; `memory.swap.max` `0` gives the group no swap; `pids.max` bounds the processes in the group, a `fork` or `clone` past it failing with `EAGAIN`; and writing `1` to `cgroup.kill` sends `SIGKILL` to every process in the group and its descendants. `clone3(2)`: with `CLONE_INTO_CGROUP` the child is created in the cgroup whose directory descriptor `cgroup` names, rather than in its parent's, so it is never in another group; Go's `syscall.SysProcAttr` documents `UseCgroupFD` and `CgroupFD` as that flag and descriptor on Linux. `statfs(2)` reports `CGROUP2_SUPER_MAGIC` (`0x63677270`) as the type of a cgroup2 file system. Python's own: `python3.12` exits 2 when it cannot open the script file (observed: `can't open file ... [Errno 2]`, exit 2); `sys.executable` is the interpreter's own path (the `sys` module's documentation), so a fixture starts a child interpreter without naming the command; `/proc/self/environ` holds exactly the environment the process was started with, while Python's `os.environ` gains `LC_CTYPE=C.UTF-8` when started with no locale variable at all (PEP 538's coercion), which `LANG=C.UTF-8` in the run's environment avoids.

## Decisions

- The command is fixed in the runner, not passed in `Spec`: the contract is `python3.12 main.py`, and a caller that cannot name another command cannot drift from it.
- `Start` looks the interpreter up on `Spec.Env`'s `PATH` rather than once at start, so a removed interpreter is a `start_failed` run rather than a failure nobody records.
- `Wait` returns one `int`; whether a signal was the runner's own is told by `Kill`'s answer, and a writer's failure is the writer's to remember.
- `Kill` answers a `bool` because only the runner can tell, without a race, whether the kill reached `main.py` before it exited; the run core uses it to refuse a `cancel` of a run that had already ended.
- The group is killed before `main.py`'s status is collected, so `Kill` never signals a group id another run may have taken.
- On the real tree the process is created inside its group (`CLONE_INTO_CGROUP`) rather than moved there after it starts, because a process moved after it starts has already been charged to the group it started in, and could fork there before the move (observed in the sandbox: a 400 MB write exited 0 with 203 MB charged to `main/`, and a script's 100 forks succeeded past `pids.max`). The stand-in path keeps the move, because a plain file write is what a test can prove; only tests take it.
- `Wait` writes `cgroup.kill` even when the process group was already killed, because a process that left the group with `setsid` is out of the process group's reach but not the control group's.
- `Find` is exported for `D03-serve`'s start check, so the start and every run look for the interpreter the same way.

## Consumer tasks

At start (`D03-serve`): `_, err := runner.Find(path)` with the `PATH` value; `errors.Is(err, runner.ErrNotFound)` is the start refusal.

Starting a run (`D07-runs`): `p, err := runner.Start(ctx, runner.Spec{Dir: <run folder>/tree, Env: env, Stdout: out, Stderr: errw, Cgroup: filepath.Join(cfg.Cgroup, id), MemoryMax: cfg.RunMemoryMaxBytes, PidsMax: cfg.RunPidsMax})`, `env` being the fourteen variables `D07-runs` composes, for a run the `run` tool asked for and for one a delivered event started alike (`D14-delivery`), `out` and `errw` its bounded writers over the run's `stdout` and `stderr` files; a non-nil `err` is a failed run with `store.ReasonStartFailed`; otherwise the run is recorded `running` and a goroutine calls `code := p.Wait()` and records the ending. `cancel`, the drain deadline, a script's deletion and `SCRIPT_SECONDS` call `p.Kill()` and record `killed` or `timed_out` when it returns true; a `cancel` whose `Kill` returns false is refused as a run that has already ended.

A test finds the interpreter with `exec.LookPath(runner.Interpreter)`, writes a `main.py` into a temporary directory, and calls `runner.Start` with an `Env` holding a `PATH` of that interpreter's directory, `HOME` in its temporary directory and `LANG=C.UTF-8`, and writers it reads; the script tells the test what it saw by printing it (its argument list, working directory, `/proc/self/environ`, `/proc/self/fd`, process group, what it read from standard input) or writing its child's pid; the test waits for `Wait` with a deadline that fails the test, and checks that a pid is gone through `/proc/<pid>/stat`. For the control group it names a `Cgroup` under its temporary directory, absent or made beforehand with whatever it wants there (a directory at `cgroup.procs`, a named pipe at `cgroup.kill`), reads the files `Start` wrote while `main.py` waits for a file the test creates, and sees the directory gone once `Wait` has returned.
