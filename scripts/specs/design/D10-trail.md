# D10-trail

The trail: the contract of every `script.*` and `run.*` event scripts records — the closed set of event names, each domain event's attributes with their keys, types and values, which outcome records which event and in which request, the identity each event carries, and what no attribute ever carries — together with the three functions of `internal/runs` through which a run's events are formed. `D01-layout-and-run-seam` declares the names this design behaves through for a whole run (`cli.Process`, `cli.Run`, its `Sink`, `Now` and `Dir`) and the entity ids (`store.ValidScriptID`, `store.ValidRunID`); `D04-store` declares the run record (`store.Run`) and the status, reason and trigger words; `D03-serve` records the framework events (`service.started`, `service.stopping`, and the request pair through appkit's `telemetry.Middleware`) and wires identity; `D07-runs` decides when a run starts, ends, is cancelled, killed with its script, killed at the drain deadline or marked at the next start, and what its record then holds; `D11-tools` declares the eleven tools, their results and refusals, and each tool's `tool.called`; `D14-delivery` decides which runs a delivered event makes and under whose identity. This document says, for those outcomes, which domain events they record with which values and under whose identity; it restates none of them.

## What is someone else's

The envelope of an event (`Time`, `Service`, `RequestID`, `User`), its JSON form, delivery, retries and the `undelivered event` line are appkit's telemetry contract and writer: its published writer hands the sink one event at a time in the order they were emitted, never holding up `Emit`; gives each event up to `telemetry.Attempts` attempts with pauses of `telemetry.RetryBackoff` and twice that between them; does not retry an event the sink rejects with an error wrapping `telemetry.ErrRejected`, which its socket sink returns for telemetry's `4xx`, that sink reading the services file afresh for every delivery, so telemetry installed or restarted later is found without a restart; and writes an event it could not deliver as the `undelivered event` line. Its retries, a few times over a fraction of a second with a `4xx` unretried, are appkit's, and scripts states none of it again; scripts records every event through its one `*telemetry.Writer` with `Emit`, whose envelope request id and user are those of the `identity.Caller` on the context it is given. The registered entity prefixes `scr_` (entity type `script`) and `run_` (entity type `run`), both owned by scripts, are in appkit's telemetry contract; this design holds the requirements that scripts' values fit them, under the keys `script` and `run`.

## The events

scripts records exactly ten events: `service.started`, `service.stopping`, `request.started`, `request.finished`, `tool.called`, and the five domain events below. scripts calls no sibling itself, so it records no `sibling.called`; a call a running script makes to a sibling is recorded by that sibling, under the run's request id and user.

| Event | Attributes | Recorded when |
|---|---|---|
| `script.created` | `script` (`string`) | a `create` that succeeds |
| `script.updated` | `script` (`string`) | an `update` that succeeds and changes the ref; a same-ref `update` records none, and so do `subscribe` and `unsubscribe` |
| `script.deleted` | `script` (`string`) | a `delete` that succeeds, after the `run.finished` of every run of the script it killed |
| `run.started` | `run`, `script`, `sha`, `trigger` (`string`, `manual` or `event`) | a run's process has started: at once, in its `run` call's request or its delivery's, before the call's `tool.called`; or later, for a run that was queued, when it leaves the queue, with no request around it |
| `run.finished` | `duration_us` (`int64`); `exit_code` (`int64`, only when `exited`); `reason` (`string`, only when `failed`); `run`, `status` (`string`); `truncated` (`bool`) | a run reaches a final status, however it ends; a run that could not start, and a queued run that ended without starting (cancelled, deleted with its script, or `failed` with `queue_abandoned` at the stop or the next start), records only this |

Attributes name what happened and the ids of what it touched, never data: no name, repository, ref, input, output, file, email, query, argument, refusal text, event name, event id or event attribute reaches a domain event. `run.finished` has no `script` and no `sha`: the run's id leads to both through its `run.started` or `result`.

## Identity

A request's `script.*` events carry its own request id and caller, as every handler's events do. A run's events are the exception: a run is caused by the `run` call that asked for it and keeps that call's user and request id, recorded on the run (`D04-store`), for as long as it lives. So both its `run.started` and its `run.finished` carry them, whenever its process starts, at once or later when it leaves the queue with no request around it, and whichever request or moment ends it: the script ending on its own, `SCRIPT_SECONDS`, a `cancel` made under another request id, a `delete` of its script, the drain deadline, a stop that abandons it in the queue, or the next start finding it still recorded `running` or `queued`. The run core emits a run's events under a context carrying `runs.Caller` of its record, never the context of the request or moment that ends it, so a run's trail is whole under one request id, and the request that ended it is tied to it only by the run's id and by where the event falls in that request's window. A run a delivered event made (`D14-delivery`) was asked for by no `run` call: its record keeps the delivery's request id, the one `telemetry.Middleware` read or minted for the events app's request, not the event's own `request_id`, and its script's owner as its user, whoever caused the event; so its `run.started`, or its lone `run.finished` when it could not start, falls in the delivery's window when the delivery started it at once, and its `run.started` comes later, under the same two, when the delivery queued it, and its `run.finished` carries the same two whenever and however it ends, at the drain deadline included. A delivery records no `tool.called`, since no tool was called, and a delivery that makes no run records no `run.*` event. The event's id is the run's link back to it, in `result` and on the run's page, never in the trail.

## Where the events are formed

The run core, `internal/runs`, is the only place a run starts or ends, the place the event bus calls, and so the one emitter of `run.*` events: it exports `StartedAttrs`, `FinishedAttrs` and `Caller`, which form a run's attributes and its identity from its record, so the tools, pages and tests never form a run event themselves. The `script.*` events are emitted by the tools (`D11-tools`), the only callers that change the catalog's scripts, each with the call's own context and the one attribute `script`. No `trail` package exists: a package holding three pure functions over `store.Run` would be a concern without a caller of its own, and `runs` already imports the store and is the only caller.

## Decisions

- `duration_us` is passed to `FinishedAttrs` as a measured `time.Duration`, not derived from the record's `Started` and `Finished`, because the catalog keeps times to the second while the trail measures in microseconds; it runs from the reading of `Now` the `run` call takes, a failed start's included, to the reading taken when the run core sees the end. A run killed at the drain deadline has its `run.finished` emitted before the writer's shutdown, but the drain has spent the deadline, and from the deadline on `Run` hands its sink nothing (`D03-serve`, R-HZS1-B4XT): that `run.finished` never reaches telemetry and is an `undelivered event` line before `service.stopping`'s, which reaches telemetry no more than it does. So the rules below that a run's `run.finished` precedes `service.stopping` in the trail are stated for a `Run` whose drain ended before its deadline; a trail cut at the deadline is `D03-serve`'s. A run the next start marks `killed` has no reading of its start but its record's, so its duration runs from its recorded `Started` to the moment it is marked.
- A `run` call whose run was recorded, and so emitted `run.started`, can still get no answer: one cut off at the drain deadline just after its recording, or one whose client left then. No test can fix which side of the deadline, or of the client's leaving, the recording falls on (`D03-serve` admits the same race), so the rule that every `run.started` names an answered call is stated only for a `Run` that cut off nothing and whose clients waited, and the rule that a call given no answer records no `run.*` event only for a call whose git was still running when it was cut off. A call cut off by its client's leaving is this design's; one cut off at the drain deadline is `D03-serve`'s (R-I3FQ-GG5W), whose events, recorded after the deadline, reach only standard error. The client's leaving is seen as a cut-off while scripts still serves, so its test needs no drain to end it: a call whose cancellation were ignored would hold its git, and so the drain, to the deadline, and the stop would then count it unfinished and lose `service.stopping` from the trail.
- A request that is not a tool call records its request pair and nothing else; `tool.called`'s attributes are appkit's, and the trail states them end to end only to prove scripts hands them to the sink unaltered.
- `truncated` is present on every `run.finished`, a failed start's included, holding the record's flag.
- A queued run's `run.started` lies in no request's window: it is tied to its `run` call, or its delivery, by the request id it carries, so the rules that a run's events belong to a call are stated by identity, and by window only for what a call itself records before its `tool.called`. A queued run abandoned at the stop is recorded at the signal, without waiting for any running run (`D07-runs` R-YIQQ-03KZ, `D03-serve` R-HMD5-3NS6), so its `run.finished` precedes `service.stopping` and the `run.finished` of every run that ends within the drain; a test proves the order by holding each running run until the abandoned run's `run.finished` is seen.
- A refused tool call, a tool that only reads, `subscribe` and `unsubscribe`, a page, a run file and `/_appkit/` record no domain event; neither does pruning, nor the removal of an ended run with its script.
- A domain event is told to belong to a request by its request id for `script.*`, and by the request id of the `run` call or the delivery that made the run for `run.*`; position in another request's window is what ties a `cancel` or a `delete` to the `run.finished` it caused.

## Consumer tasks

The run core (`D07-runs`), once a run's process has started, at once or when it leaves the queue, its record `r` in hand: `w.Emit(identity.NewContext(ctx, runs.Caller(r)), "run.started", runs.StartedAttrs(r))`; when the run reaches a final status, its ended record `r` and measured duration `d` in hand, whether it was recorded `failed` (`queue_abandoned` included, at the stop or at start), ended on its own, timed out, was cancelled or taken from the queue, was killed or taken from the queue with its script, killed at the drain deadline, or marked at start: `w.Emit(identity.NewContext(base, runs.Caller(r)), "run.finished", runs.FinishedAttrs(r, d))`, `base` being any context, a cancel's request context or `context.Background()` alike.

The tools (`D11-tools`), `u` the call's caller: `create` on success calls `w.Emit(ctx, "script.created", telemetry.Attrs{"script": sc.ID})`; `update` calls `w.Emit(ctx, "script.updated", telemetry.Attrs{"script": sc.ID})` only when `store.SetRef` answered `changed`; `delete` hands the script to the run core's deletion, which kills its running runs and emits their `run.finished`, and once that returns calls `w.Emit(ctx, "script.deleted", telemetry.Attrs{"script": sc.ID})`; `cancel` hands the run to the run core, which emits its `run.finished`; `run`, `subscribe` and `unsubscribe` emit nothing themselves.

A unit test calls `runs.FinishedAttrs(store.Run{ID: id, Status: store.StatusExited, ExitCode: 137}, 1500*time.Microsecond)` and compares with `telemetry.Attrs{"duration_us": int64(1500), "exit_code": int64(137), "run": id, "status": "exited", "truncated": false}`, and `runs.Caller(r)` with `identity.Caller{UserID: r.User, RequestID: r.RequestID}`. A trail test runs `cli.Run` with a `*telemetry.Capture` as `Sink`, a constant `Now` and a temporary `Dir` of its own, makes tool calls with `mcp.Client` over the inherited listener as callers with distinct request ids, posts deliveries to `/events` with an `X-Request-Id` of its own and no `X-User-Id`, stops the run, reads `Capture.Events()`, and opens the catalog under that `Dir` with `db.Open` and `scripts.Migrations()`, and a store over it, to compare each `run.finished` with `runs.FinishedAttrs` of the record.
