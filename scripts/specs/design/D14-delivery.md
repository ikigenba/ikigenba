# D14-delivery

What scripts does when the events app delivers an event to it: `Deliver`, the one method of the run core (`internal/runs`) that the event bus calls. For every script subscribed to the delivered event's name it makes one run of that script, as the script's owner, from the script's own ref, with the event as its input, unless the script already has a run from that event; and it answers the events app whether the delivery is done, irrelevant, or to be delivered again. This document declares `Deliver` and states what it does. `D04-store` declares the subscriptions, `Subscribers`, `Delivered`, the trigger word `event` and the run's `Event`; `D07-runs` declares the run core, `runs.Request` with its `Cause`, and everything a run does once `Run` makes it; `D10-trail` states the run's events as the trail shows them; `D03-serve` mounts `Deliver` behind appkit's `events.DeliveryHandler` and `events.DeclarationsHandler` at `events.EventsPath` and `events.DeclarationsPath`, inside `telemetry.Middleware` and outside `identity.Require`; `D11-tools` declares `subscribe` and `unsubscribe`, which make and remove the subscriptions.

## What is someone else's

How a delivery reaches scripts is appkit's events contract: `events.DeliveryHandler` refuses a request that is not a valid delivery (a method other than `POST`, a body that is not one delivered event and its attempt, a body too large), picks the handler registered for the event's name or the `*` handler, calls it with the request's context and the `events.Delivery`, and writes the answer: `events.OK()` and `events.Skip()` as status 200, `events.Fail(msg)` as status 500 carrying `msg`, which the events app retries. scripts registers one `*` handler, `Deliver`, so it accepts every event name, and declares that it emits none (`events.DeclarationsHandler` with a nil emitter answers `{"emits":[],"accepts":["*"]}`). The delivery carries no identity: its request id is the one `telemetry.Middleware` read from `X-Request-Id` or minted, which `Deliver` reads with `identity.FromContext`. What the events app retries, and when, is its own; scripts only makes redelivery safe.

## Matching and making

`Deliver` looks at the event's `event` (its name) and `id` only. Its **subscribers** are the scripts `Subscribers` names for the name, byte for byte, of every owner; neither the event's `attrs`, nor its `service`, nor its `user` narrows them, so a script that cares which repository a push moved reads its input and decides. For each subscriber it calls the core's own `Run`, with a context the delivery's end does not reach, and a request whose `Ref` is empty (the script's ref as the delivery read it), whose `Input` is the event's canonical JSON (`d.Event.MarshalJSON()`: the eleven members `id`, `time`, `service`, `event`, `request_id`, `user`, `attrs`, `cause`, `depth`, `seq` and `received`, without the delivery's `attempt`; this canonical form is what the stories' "byte for byte as the events app sent it" means), whose `Caller` is the script's owner and the delivery's request id, and whose `Cause` is the event's id and depth. So the run is a run like any other — same folder, same git, same process and limits, same endings and pruning — with trigger `event`, its `Event` the event's id, its environment carrying `IKIGENBA_EVENT_ID` and `IKIGENBA_EVENT_DEPTH`, and its events under the delivery's request id and the owner. The runs of one delivery are made side by side: none waits for another's git.

One script gets at most one run from one event. `Run` asks `Delivered` first, so a redelivered event makes nothing for a script that has its run, whether that run is running, ended or pruned, and runs no git; a delivery arriving while an earlier attempt of the same event is still making a script's run (the events app retries after its own attempt timeout) is refused for that script at once, before any git, with `runs.ErrStarting`, and answered `events.Fail("a run for this event is starting; try again later")`, so the events app tries again and finds the run made; one core never starts two processes for one event and script. A script deleted while its run was being made has nothing to make.

## Answers

- `events.Fail("scripts is stopping; try again later")` once `Drain` has been called, before anything is read or made, and when a subscriber's run was refused by the drain or cut off at its deadline: a run started now would only be killed, and the events app delivers the event again to a scripts serving again.
- `events.Fail(store.Unreachable)` when the catalog cannot be read to find the subscribers, or when a subscriber gets no run for any other reason (a catalog that will not take the record, a folder that cannot be made): treating the event as one nobody is subscribed to would lose the run for good.
- `events.Fail("a run for this event is starting; try again later")` when an earlier attempt of the same event is still making a subscriber's run.
- `events.Fail("event has no id")` for an event without an id, which appkit's handler never passes on; nothing is made.
- `events.Skip()` when no script is subscribed to the name: there is nothing to retry. A call during part of which the catalog fails may answer either this or `events.Fail(store.Unreachable)`, depending on whether its read of the subscribers met the failure; the requirements fix the answer only for a catalog failing throughout the call or not at all.
- `events.OK()` when every subscriber has its run from this event, made now or by an earlier delivery (a call that made every run itself answers so even if the catalog fails just after), a run that could not start and was recorded `failed` included: its failure is the run's, and delivering again would fail the same way.

A delivery that is refused keeps every run it did make; the redelivery makes the rest and nothing twice. `Deliver` returns only once every run it makes is recorded or abandoned, so an accepted delivery's runs are in the catalog, and in `runs` and `result`, by the time the events app has its answer, and the record of each, written with its delivered-event memory in one write, survives a restart.

## Decisions

- `Deliver` is a method of `*runs.Core`, not a package of its own: the core already holds the store, the drain and `Run`, and a method value is an `events.Handler`, so `D03-serve` registers `events.Handlers{"*": core.Deliver}` and needs no new configuration.
- Runs are recorded before the answer, as `run` records them before answering: the store records a run only once its process has started or it failed, so the process of each run starts before the answer and the script runs on after it. A run made after an `OK` could be lost by a stop in between, and one acknowledged but not yet recorded would be missing from `runs` when the stories look for it.
- The delivery's own context does not cut a run off: the events app gives up on an attempt after its own attempt timeout, and a run cut off with it would be cut off again on every retry. The run goes on and is recorded, and the retry finds it.
- The drain refuses every delivery, a delivery no script is subscribed to included, so a stopping scripts answers the events app one way.
- Matching ignores everything but the name, so the subscribers of one name are one read of the catalog.

## Consumer tasks

Serving (`D03-serve`), `core` being the run core: `h := events.Handlers{"*": core.Deliver}`; `events.DeliveryHandler(h)` at `events.EventsPath` and `events.DeclarationsHandler(nil, h)` at `events.DeclarationsPath`, both inside `telemetry.Middleware(w, ...)` and outside `identity.Require`, by exact path.

`Deliver` itself, `rid` the request id `identity.FromContext(ctx)` gives: after `Drain`, `events.Fail("scripts is stopping; try again later")`; with an empty `d.Event.ID`, `events.Fail("event has no id")`; `subs, err := st.Subscribers(ctx, d.Event.Name)`, an error being `events.Fail(store.Unreachable)` and none `events.Skip()`; `b, _ := d.Event.MarshalJSON()`; for each `sc` of `subs`, side by side, `_, err := c.Run(context.WithoutCancel(ctx), sc, runs.Request{Input: b, Caller: identity.Caller{UserID: sc.Owner, RequestID: rid}, Cause: events.Cause{ID: d.Event.ID, Depth: d.Event.Depth}})`, a nil error, `store.ErrDelivered` and `store.ErrNotFound` meaning the script has, or needs, no run, `runs.ErrDraining` and `limits.ErrHalted` the stopping answer, `runs.ErrStarting` the starting answer, and anything else the unreachable one; then `events.OK()` when every one is settled.

A test builds a store over its own catalog, a source over bare repository fixtures, a writer over a `*telemetry.Capture` and a core, as `D07-runs`' tests do; subscribes scripts with `st.Subscribe`; and calls `core.Deliver(identity.NewContext(ctx, identity.Caller{RequestID: rid}), events.Delivery{Event: ev, Attempt: 1})` with an `events.Event` it builds, comparing the outcome with `events.OK()`, `events.Skip()` or `events.Fail(...)` by `==`, then reads `st.Runs`, the run's folder, what its `main.py` printed, and the capture. It drives the same through `httptest` and `telemetry.Middleware(w, events.DeliveryHandler(events.Handlers{"*": core.Deliver}))` with a body `json.Marshal` makes of the event and its attempt, to see the request id flow. It holds a run's git from its `limits.Clock`'s `After` to race deliveries or to fail the catalog with `SetFailing(true)` mid-delivery, and calls `core.Drain` to see the stopping answer.
