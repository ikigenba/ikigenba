# D01-layout-and-run-seam

scripts is the suite's script runner: one Go binary, behind the host's nginx at `scripts.<space>`, that keeps a catalog of each user's scripts, each naming one of that user's repositories in repos and a ref, runs a script's `main.py` with the host's `python3.12` from the commit its ref resolves to, unpacked with the host's own `git archive` into a folder of the run's own, and keeps every run's input, output, files and outcome. It offers eleven MCP tools at `/mcp` (`list`, `show`, `create`, `update`, `delete`, `subscribe`, `unsubscribe`, `run`, `runs`, `result`, `cancel`), runs a script each time the suite's events app delivers an event the script is subscribed to, keeps its catalog of scripts, their subscriptions and their runs in its own SQLite database, `state/scripts.db`, keeps each run's folder under `state/runs/`, and serves a catalog page at `/`, a page per script and per run, the run's files, and an about screen at `/about`, all to a signed-in user only, beside the two exact paths `/events` and `/declarations` on which the events app, a sibling on the socket, delivers events and learns which scripts accepts. This design is the structural ground the other designs stand on: where the code lives, which package owns which concern, the seam through which the process is run so that the command, the server, the pages, the store, the runs, the limits and the tools can be tested without a real process, the entity ids, the one declaration of the Python version, the paths, the migrations that give the catalog its schema, the version, the files under `etc/`, and the one binary's wiring. Every other package's names are declared by the document that owns that package, listed below.

The module is `github.com/ikigenba/ikigenba/scripts`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/scripts`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/scripts` is wiring only.

## The dependencies

scripts depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required by a released version with no `replace` directive. The SQLite driver, the pure-Go one that keeps the release build cgo-free, arrives through appkit's `db` package; scripts never imports it. Which release is data that `AGENTS.md` and `go.mod` hold; no requirement names one. It runs two programs, the host's `git` and the host's `python3.12`, which `AGENTS.md` declares in the toolchain; it links no git library and embeds no interpreter.

appkit is a sibling reached only through its published packages, and scripts uses seven of them: `db` (below), `services` (the services file), `page` (the banner, launcher, footer and font preload, the template set the six templates are parsed into, and the shared static files), `identity` (`Require` on every route but the events app's two, since every page and `/mcp` is for a signed-in user), `mcp` (the server mounted at `/mcp` and the client the tests drive it with), `telemetry` (the event, the request middleware, the writer, the socket sink and the capturing sink tests use), and `events` (the delivery and declarations handlers mounted at `events.EventsPath` and `events.DeclarationsPath`, the delivered event, its outcomes and its cause; `D03-serve`, `D14-delivery`). appkit's designs own their contracts; scripts restates none.

`github.com/ikigenba/ikigenba/appkit/db` is the suite's one way to keep a SQLite database. `db.Open` opens or creates the database at an ordinary file path, creating its missing directories, applies the migrations it is given that the database has not had, stamping each with the clock it is given, and refuses a database it cannot open or one that records a migration it was not given (`db.ErrUnknownVersion`, whose text names that version); `DB.Read` runs a read-only transaction and `DB.Write` a transaction on the one writer, so writes are serialized by the handle; `DB.Close` closes the handle; `DB.SetFailing` makes a handle fail every transaction until it is turned off, which is how scripts' tests make the catalog fail; and `db.Status` writes, changing nothing, which migrations a database has had and which it has not. The journal mode, the busy timeout, the reader pool and the writability probe are appkit's too. All of that is appkit's contract (its D15 and D16): scripts restates none of it, and its tests re-prove none of it.

repos is reached only through the on-disk layout it publishes for siblings, one bare repository per repository at `<REPOS_DIR>/<rep id>.git` whose own config holds the `ikigenba.*` keys, read with the host's `git` as git's manual documents it (`D05-git-and-source`). scripts never calls repos over HTTP and never writes under `REPOS_DIR`.

## Identity

Identity is established at nginx and arrives on every request in `X-User-Id`, `X-User-Email` and `X-Request-Id`, which appkit's `identity.Require` turns into an `identity.Caller` (`UserID`, `Email`, `RequestID`) on the request's context, and appkit's request middleware makes the request id of every event the request records. A script's owner is the `UserID` of the call that created it (`D04-store`); a run's user and request id are the `UserID` and `RequestID` of the `run` call that caused it, recorded on the run (`D04-store`) and handed to the script in `IKIGENBA_USER_ID` and `IKIGENBA_REQUEST_ID` (`D07-runs`), so that the script's own calls to siblings carry them on. A run the events app's delivery of an event makes acts instead as its script's owner and carries the request id of that delivery, which arrives with no user of its own (`D14-delivery`). A test is a signed-in user by setting those headers, as `AGENTS.md` describes. Which routes exist and which of them require identity, every one but the events app's two, is `D03-serve`'s.

## Where the environment is read

`Run` reads every variable through `Process.LookupEnv`: `DRAIN_SECONDS` and the thirteen settings once at start, through `D12-limits`' settings reader; `LISTEN_PID`, `LISTEN_FDS` and `NOTIFY_SOCKET` for the socket and readiness (`D03-serve`); `PATH`, where `git` and `python3.12` are looked for at start (`D03-serve`) and which every script is given verbatim (`D07-runs`); and `IKIGENBA_SERVICES`, once, when it starts to serve, whose value it hands on as the services path that the handler, the pages and the tools read afresh whenever they need the file, and which every script is given verbatim (`D07-runs`). `Process.Environ` is the whole environment every `git` scripts runs is started with, so a test composes the git environment `AGENTS.md` asks for and hands it to `Run` without touching the real environment. A script's own environment is not `Environ`: it is exactly the fourteen variables `D07-runs` composes, its `PATH` taken from `LookupEnv`, so a test that chooses the `PATH` and the working directory chooses everything a script sees of the host.

Three readers of `IKIGENBA_SERVICES` sit outside the seam, all appkit's: `page.New` and `mcp.NewServer` read the real environment when they are called, and the socket sink reads it on every delivery. So `main` calls `page.New` once and puts in `Process.MCP` a function that calls `mcp.NewServer` with `Instructions` nil; and the socket sink is what a nil `Process.Sink` means, used only by the binary, while a test of `Run` names its own sink, a `*telemetry.Capture`.

## Packages

The module's root package, `scripts`, holds what the module embeds, because Go's `embed` reaches only files at or below the embedding package's directory. It exports `Assets`, a file system holding exactly the six templates from `assets/`, which `internal/pages` parses into the set `page.Templates()` returns (`D08-pages`), and `Etc`, an `embed.FS` holding exactly `etc/manifest.toml` and `etc/nginx.conf`, through which a test proves that the committed files are the manifest and the nginx fragment `D02-cli` declares: the `embed` package documents that an `embed.FS` declared without a `//go:embed` directive is an empty file system, so the bytes a test reads from `Etc` are the committed files' as the build embedded them, never a copy made from a constant. It also exports `Migrations`, a file system holding exactly the migrations from `migrations/`.

The catalog's schema is a sequence of migration files, each named with a four-digit version, that the binary carries and appkit's `db` applies in order. This scripts carries two. `0001_catalog.sql` is the schema scripts has always created, its one table `catalog` (`D04-store` declares it), written so that it creates the table only if it does not exist and seeds nothing, so a catalog an earlier scripts kept before it recorded migrations is adopted as it is. `0002_subscriptions.sql` adds the subscriptions and the memory of which event each script has had a run from (`D04-store` declares both), and applies after `0001` on a fresh catalog and on every catalog an earlier scripts kept. `Migrations()` is what `Run` hands `db.Open` and `db.Status`, and what a test hands `db.Open` to make a catalog of scripts' shape in its own temporary directory; it is the same on every call and depends on no file beside the binary. A later migration is a new file with the next version; none is ever edited once released.

Thirteen internal packages hold the concerns, one each. Ten follow sites' names and roles; three are scripts' own (`runner`, `runs`, `source`).

- `internal/cli` owns the program as a command: the version and the run seam (this document), the exit codes, the usage text, the manifest and the nginx fragment (`D02-cli`), and the serve path (`D03-serve`).
- `internal/server` owns a listener's life: serving a handler and draining for a deadline (`D03-serve`).
- `internal/settings` owns the values scripts reads from its environment at start, their defaults, their spelling and the refusal of one that is not acceptable (`D12-limits`).
- `internal/limits` owns the settings as applied: the per-git-run deadline and halting (`D12-limits`); a script's `SCRIPT_SECONDS` and draining are the run core's (`D07-runs`).
- `internal/git` owns finding and running the host's `git` (`D05-git-and-source`).
- `internal/source` owns reading a repository: its owner, its name, resolving a ref and unpacking a commit (`D05-git-and-source`).
- `internal/store` owns the catalog: script, subscription and run records, statuses, failure reasons, the name rule and the event-name rule (`D04-store`) and the entity ids (this document).
- `internal/runner` owns starting one process in its own process group and ending it (`D06-runner`), and the Python version declaration (this document).
- `internal/runs` owns the run core: the run folder, starting, bounding, ending, recording, recovering and pruning runs (`D07-runs`), and the runs a delivered event makes (`D14-delivery`).
- `internal/urls` owns the addresses built from a request and the services file (`D08-pages`).
- `internal/pages` owns the template set, the six templates' data, the catalog, script, run and about pages, `ServiceName` and `Description` (`D08-pages`).
- `internal/tools` owns the eleven MCP tools (`D11-tools`).
- `internal/web` owns the one handler: the route table, the middlewares and the mounting, the events app's two paths included (`D03-serve`), and the run files beneath a run's page as `D09-run-files` places them.

The events scripts records are `D10-trail`'s; it names the package each is recorded from.

`internal/server` and `internal/git` are copies of sites' packages of the same names, as sites copied them; with scripts each exists in more than two apps, which makes both candidates for appkit. Promoting them is a separate change, and until it lands each copy is a debt this design records rather than designs away.

Dependencies point one way: `cmd/scripts` imports `internal/cli`, `internal/pages` and appkit; `internal/cli` imports the root package, `server`, `settings`, `limits`, `git`, `store`, `source`, `runner`, `runs`, `web` and `pages`; `web` imports `pages`, `tools`, `store`, `source`, `runs`, `limits` and `urls`; `tools` imports `store`, `source`, `runs` and `limits`; `runs` imports `store`, `source`, `git`, `runner` and `limits`; `pages` imports the root package, `store`, `source`, `runs` and `urls`; `source` imports `git`, `limits` and `store`; `limits` imports `settings`; the root package, `server`, `settings`, `git`, `store`, `runner` and `urls` import nothing of scripts'. Which package imports which is not observable, so this paragraph is guidance.

## The run seam

The run seam is `cli.Run`, which takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, and returns the exit code. It is sites' seam with two fields more, `ScriptAfter` and `Cgroup`. There is no field naming another database, because appkit's `db` takes only an ordinary file path, so the catalog is always `state/scripts.db` under `Dir` and a test that needs its own catalog gives `Run` a temporary `Dir`. `Environ` is the environment every git process starts with. `After` is the timer one git run's `OPERATION_SECONDS` ends on, and `ScriptAfter` the timer one script's `SCRIPT_SECONDS` ends on, two fields so that a test fires either deadline on its own without the other; the drain deadline and the writer's delivery attempts run on real time, because the drain is the one wait `AGENTS.md` lets a test keep to a few real seconds. What each deadline does when it fires is `D12-limits`' and `D07-runs`'. `Now` is the clock every time scripts stamps is read from (a script's `created`, a run's `started` and `finished`, every event's time, the moment a prune measures age from, and the time each migration it applies is recorded at). `Rand` is the source of every id scripts mints: request ids (through the writer), script ids and run ids; `Run` never reads it from two goroutines at once, so a test may hand in a `bytes.Reader`. `Dir` is the working directory the state paths and a relative `REPOS_DIR` resolve against. `Sink` is where the writer delivers: a `*telemetry.Capture` in a test, appkit's socket sink in the binary. `Cgroup` is the directory of the process's own control group, which a host delegates to scripts' service and which `Run` arranges (`D03-serve`): it moves its own process into a child group `main/`, makes a child group `runs/` that bounds every run together, and gives each run a group of its own beneath `runs/` (`D06-runner`, `D07-runs`). Every operation on it is a plain file operation, making a directory, writing a file, removing a directory, as the kernel's control group v2 documentation (`Documentation/admin-guide/cgroup-v2.rst`) describes its interface files, so a test hands `Run` a temporary directory standing in for the tree and reads what was written there. `Inherit`, `Unsetenv`, `Pid`, `Stdout`, `Stderr`, `Sleep`, `Banner` and `MCP` are as in sites.

## Entity ids

A script's id is `scr_` and a run's id is `run_`, each followed by 16 lowercase hexadecimal digits, the prefixes appkit's telemetry contract registers for the entity types `script` and `run`. Both are minted from 8 bytes of the random source, written in the order read. `internal/store` exports the prefixes, a validity check for each form, and the two functions that mint them: the store mints a script's id inside `Create` (`D04-store`), while the run core mints a run's id before anything of the run exists, because the run's folder is named by it before the run is recorded (`D07-runs`). Ids never change. A drawn script id that collides with one already catalogued is drawn again by the store, a bounded number of times (`D04-store`); a run id that collides with one already catalogued is refused by `AddRun` as a catalog error (`D04-store`), which with 64 random bits the run core does not plan for.

## Python

Python is pinned to one minor version, declared once in the source: `runner.PythonVersion`, `3.12`. Everything else derives from it: `runner.Interpreter`, the command's name `python3.12`, which every run executes as `python3.12 main.py` (`D06-runner`, `D07-runs`); the start's prerequisite, an executable of that name on `PATH`, and its refusal `scripts: python3.12 not found on PATH` (`D03-serve`); and the tests, which find the interpreter with `exec.LookPath(runner.Interpreter)` and fail, never skip, when it is missing, never naming the command or the version in a literal of their own. The patch level is the host's. Infra's first-boot line names the same version independently, so a version change edits both places.

## Paths

Relative to `Process.Dir` (the process's own working directory when empty, which is how `main` leaves it; `/opt/scripts` on a host, `<data>/apps/scripts/` in a sandbox): the catalog is the SQLite database `state/scripts.db`, opened with `db.Open`, `scripts.Migrations()` and `Process.Now`, `state/` created when absent; the runs live under `state/runs/`, one folder `state/runs/<script id>/<run id>/` per run, whose contents are `D07-runs`'. The folders are the product, not a cache: they live under `state/`, never `cache/`, and nothing rebuilds them. `REPOS_DIR` is resolved once, at start: a relative value is joined to `Dir`, so the default is `/opt/repos/state/repos` on a host and repos' own directory in a sandbox; an absolute value is used as it is. A repository `<rep id>` is then the directory `<REPOS_DIR>/<rep id>.git`, looked for afresh whenever a tool, a page or a run needs it. scripts writes nothing outside `Dir` but under `Cgroup`; what a script itself writes to `/tmp` is the script's.

## The version

`cli.Version` is a variable in the source, never injected at build time, holding `v` and a Semantic Versioning version. It is the one version string scripts shows: `scripts --version` (`D02-cli`), the footer of every page and the about screen's version (through `page.New(pages.ServiceName, cli.Version)`), the MCP `serverInfo` (through `mcp.ServerConfig.Version`), and `service.started`'s `version` (through the writer's `telemetry.Config.Version`). Its value is data that the deploy sets.

## Decisions

- `Process` is sites' seam plus `ScriptAfter` and `Cgroup`; one timer for both deadlines would leave a test unable to fire one without the other when both settings share a value, as their defaults do.
- `Cgroup` is a field, not something `Run` finds for itself, so that a test hands it a temporary directory and never touches the real control group tree. `main` resolves it from `/proc/self/cgroup`: the line that begins `0::` names the process's control group v2 path, which joined to `/sys/fs/cgroup` is the directory (`Documentation/admin-guide/cgroup-v2.rst`, and `cgroups(7)` for the file's format); with no such line, or no file, `Cgroup` is empty. That resolution is wiring, stated in prose and not as a requirement: the one exec'ing test cannot tell it from a `main` that leaves `Cgroup` empty, since a binary started under a test shares its control group with the test's own process, so either way its start meets a group it may not arrange and runs are unavailable (`D03-serve`). A space or a sandbox shows it (`D13-on-a-space`).
- The id functions live in `internal/store`, beside the records the ids name, rather than in a package of their own; the run core calls `store.NewRunID` with the seam's `Rand`.
- The Python version lives in `internal/runner`, the package whose contract is the command; `internal/cli` imports it for the start's lookup.
- Proving the declaration by running the interpreter, not by comparing the constant with a literal, is how a test checks the version without naming it.
- That a running scripts writes nothing outside `Dir` but under `Cgroup` is proved over the test's own temporary tree, with fixture scripts that write only into their out folder.
- That `cli.Version` is never injected at build time stays prose, not a requirement: the version is data no test names, so no permitted test can tell a value the source holds from a placeholder a linker flag (`-ldflags -X`) would replace at release, and a requirement that the variable resist `-X` would force a contrived initializer (cmd/link documents that `-X` takes effect only on a variable uninitialized or initialized to a constant string). The deploy's own check, that the binary reports the tag being released (`AGENTS.md`, Deploy), is what catches a binary built otherwise.
- `Etc` returns an `embed.FS` rather than an `fs.FS` so that its type alone proves the bytes come from a `//go:embed` of the committed `etc/manifest.toml` and `etc/nginx.conf`; a file system built in code from `cli.Manifest` and `cli.NginxConf` would satisfy an `fs.FS` signature and prove nothing about the committed files.
- `Migrations` returns an `fs.FS` holding its files at its root, as `db.Config.Migrations` takes them; unlike `Etc` it needs no proof of where its bytes came from, since what they make is proved by the schema and adoption tests (`D04-store`).
- Paths, the services path and the version are proved at `Run` and at the binary, since `main` is not usable: the binary requirements below are what the one exec'ing test of `cmd/scripts` proves.

## Consumer tasks

The binary's start: `main` hands `cli.Run` a `cli.Process` whose `Args`, `LookupEnv`, `Environ`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Banner` is the `Banner` method of `page.New(pages.ServiceName, cli.Version)`, whose `MCP` returns `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: cli.Version, Telemetry: w})`, whose `After` and `ScriptAfter` are `time.After`, whose `Cgroup` is the directory it resolves from `/proc/self/cgroup` (Decisions), and whose `Inherit`, `Now`, `Sleep`, `Rand`, `Dir` and `Sink` are left zero; it cancels the context on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name, and exits with what `Run` returns. `Run` reads the settings (`D12-limits`), and otherwise follows the serve path `D03-serve` states: the socket, `git` and `runner.Interpreter` on `PATH`, `db.Open` and `store.New`, the runs directory, the control group under `Cgroup`, the writer, recovery (each run still recorded `running` marked `killed` and each still recorded `queued` finished `failed`, each one's `run.finished` recorded through that writer) and then pruning (`D07-runs`), `web.Handler`, which mounts the run core's `Deliver` at `/events` (`D14-delivery`), then readiness, `READY=1` with `service.started` after every recovered run's `run.finished`, and the drain.

The run core mints a run: `id, err := store.NewRunID(rand)`, the folder `state/runs/<script.ID>/<id>/`, then the record (`D04-store`, `D07-runs`). A test of ids calls `store.NewScriptID(bytes.NewReader(known))` and `store.ValidRunID(s)`. A test that needs the interpreter calls `exec.LookPath(runner.Interpreter)` and fails when it errors, and compares what a script printed of `sys.version_info` with `runner.PythonVersion`.

A test of the run seam builds a `cli.Process` with a temporary `Dir`, a `Cgroup` elsewhere in its temporary tree whose `cgroup.procs` holds the decimal `Pid` it chose (or none, to see runs unavailable), a `LookupEnv` and an `Environ` over one map holding its git environment, a `PATH` holding git's and the interpreter's directories and its settings, an `Inherit` returning a listener it bound, a `NOTIFY_SOCKET` it holds, a `Now`, an `After`, a `ScriptAfter` and a `Rand` it controls, a `*telemetry.Capture` as `Sink`, a `Banner` from `page.New` and an `MCP` that calls `mcp.NewServer` (having set `IKIGENBA_SERVICES` with `t.Setenv`), calls `cli.Run` with a context from `context.WithCancelCause`, waits for `READY=1`, drives the listener with `mcp.Client` and raw HTTP, cancels, and inspects `Dir`, the capture and the streams. A test of the root package calls `scripts.Assets()`, `scripts.Etc()` and `scripts.Migrations()` and lists and reads them with `fs.ReadDir` and `fs.ReadFile`, reading the manifest at `etc/manifest.toml` and the fragment at `etc/nginx.conf`. Before this revision `fs.ReadDir(scripts.Etc(), "etc")` listed `manifest.toml` alone and `fs.ReadDir(scripts.Migrations(), ".")` `0001_catalog.sql` alone; now the first lists `manifest.toml` and `nginx.conf`, and the second `0001_catalog.sql` and `0002_subscriptions.sql`, and `fs.ReadFile(scripts.Etc(), "etc/nginx.conf")` is compared with `cli.NginxConf` (`D02-cli`). The one test that execs the binary builds `cmd/scripts` and runs it in a temporary working directory.
