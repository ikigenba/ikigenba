# D12-limits

scripts runs the host's `git` and the host's `python3.12` for anyone who runs a script, and for every event a script is subscribed to, so it bounds that work, and it reads the numbers it bounds it with, and the place repos keeps its repositories, from its environment once, at start. This document is two packages. `internal/settings` is the fourteen values scripts reads at start through `Process.LookupEnv`: `DRAIN_SECONDS`, the space's, and the thirteen the manifest's `[env]` declares (`D02-cli`), `REPOS_DIR`, `TREE_MAX_BYTES`, `OUTPUT_MAX_BYTES`, `OPERATION_SECONDS`, `SCRIPT_SECONDS`, `RUN_MEMORY_MAX_BYTES`, `RUNS_MEMORY_MAX_BYTES`, `RUNS_CPU_PERCENT`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE`, `RUN_MAX_QUEUED`, `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT`; their spelling, defaults, the order they are checked in and the refusal of one that is not acceptable. `internal/limits` is the `Limits` value that carries those settings for one run of the process, the per-git-run deadline measured on an injected clock, the halt that ends every git run still going at the drain deadline, and the three sentinels the other packages report those limits with. It also states how a serving `cli.Run` applies the settings it read. It declares every exported name of both packages and states what each does.

What the other documents own: `cli.Process`, `cli.Run`, `Process.After` and `Process.ScriptAfter`, and where `REPOS_DIR` resolves, are `D01-layout-and-run-seam`'s; the manifest's `[env]` defaults are `D02-cli`'s; the start order, the settings refusal's diagnostic and exit code, the drain and its deadline of `DRAIN_SECONDS` real seconds, and when `Run` calls `Halt`, are `D03-serve`'s; measuring a tree against `TREE_MAX_BYTES`, timing each git run with `Operation`, and the `reason` values `too_large` and `timed_out` are `D05-git-and-source`'s; `SCRIPT_SECONDS`, `OUTPUT_MAX_BYTES`, `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT` as the run core applies them, the run refusal while draining (`runs.ErrDraining`), the queue `RUN_MAX_ACTIVE` and `RUN_MAX_QUEUED` bound and its refusals, and the killing of scripts at the drain deadline are `D07-runs`'; writing `RUN_MEMORY_MAX_BYTES` and `RUN_PIDS_MAX` into each run's own control group is `D06-runner`'s; writing `RUNS_MEMORY_MAX_BYTES` and `RUNS_CPU_PERCENT` into the group every run shares, and handing the run settings to the run core, are `D03-serve`'s; and the words a page shows for a failed run and for the runs a script keeps are `D08-pages`'.

## The settings

scripts reads fourteen values at start, in this order: `DRAIN_SECONDS`, `TREE_MAX_BYTES`, `OUTPUT_MAX_BYTES`, `OPERATION_SECONDS`, `SCRIPT_SECONDS`, `RUN_MEMORY_MAX_BYTES`, `RUNS_MEMORY_MAX_BYTES`, `RUNS_CPU_PERCENT`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE`, `RUN_MAX_QUEUED`, `RUN_KEEP_DAYS`, `RUN_KEEP_COUNT`, and `REPOS_DIR`, which is never refused so its place in the order changes nothing. The thirteen numbers are spelled as opsctl writes an integer: one or more ASCII digits, no sign, no leading zero, no unit, no white space. An unset or empty one is its default: 5 seconds, 268435456 bytes, 1048576 bytes, 600 seconds, 600 seconds, 268435456 bytes, 536870912 bytes, 100 percent, 64 processes, 2 runs, 10 runs, 15 days and 10 runs. scripts sets no upper limit: digits beyond what an `int64` holds read as the largest `int64`; a `RUNS_CPU_PERCENT` over 100 lets the runs together use more than one CPU. `0` is refused for every one of them; for `RUN_KEEP_COUNT` that means every script keeps at least its newest run whatever its age, for `RUN_KEEP_DAYS` that a run is kept at least one day, which the catalog's `PastKeeping` (`D04-store`) relies on, for `RUN_MAX_ACTIVE` that some run can always start, and for `RUN_MAX_QUEUED` that there is always room for one run to wait (`S02`, `S08`). `REPOS_DIR` is any string; unset or empty it is `../repos/state/repos`, and it is never refused and never checked at start, since repos may be installed after scripts.

`settings.Read` takes the lookup `Run` hands it (`Process.LookupEnv`) and returns a `settings.Settings`, or, for the first number in that order that is not acceptable, a `*settings.Error` naming it, quoting its value verbatim and giving its unit: `seconds`, `bytes`, `percentage`, `processes`, `days` or `runs`. Its text is what `Run` writes after `scripts: ` (`D03-serve`): `TREE_MAX_BYTES is 'abc', not a positive whole number of bytes`, and, for the one setting that is a share rather than a count, `RUNS_CPU_PERCENT is 'abc', not a positive whole percentage`, as the stories spell it (`S02`). `settings.Defaults` is the value `Read` returns when every variable is unset. Every field is a plain value: the numbers as `int64`, the unit in the field's name, and `ReposDir` unresolved, exactly as the environment gave it, which `Run` resolves against `Dir` once (`D01-layout-and-run-seam`).

## The limits

`limits.New` takes the `settings.Settings` that `Run` read and a `Clock`, and the `Limits` it returns holds those settings unchanged for the life of the process: `Settings` answers them, and every consumer reads its numbers there or from the plain values `Run` hands on from the same read (`D07-runs`' `Config`). Nothing in the catalog or under `state/runs/` remembers a limit, so a process never applies another process's value: a tree refused under one `TREE_MAX_BYTES` runs under a higher one after a restart, and the refused run stays as it was recorded.

`OPERATION_SECONDS` is the longest one git run may take: reading a repository's owner or name, resolving a ref, or unpacking a commit, each timed on its own, whether a `run` call or a delivered event started the run (`S17`, `D14-delivery`). `D05-git-and-source` calls `Operation` once for each git it attempts to start, just before starting it, runs git under the context `Operation` returns, and when that context ends because the deadline passed, kills git and reports `ErrTimedOut`. `TREE_MAX_BYTES` is the most a run's tree may hold; `D05-git-and-source` measures it and reports `ErrTooLarge`. `SCRIPT_SECONDS` is not measured here: the run core times each script on `Process.ScriptAfter`, a timer of its own, so that a test fires either deadline without the other (`D01-layout-and-run-seam`, `D07-runs`). `Limits` therefore times git runs only, and its `Clock` is `Process.After`.

Every limit here bounds a run an event started exactly as it bounds one the `run` tool started: such a run is made by the same run core call, with the same `Limits` and the same `ScriptAfter` (`D14-delivery`, R-2N1J-5PBX), and it is kept and pruned with the others by the same two keeping settings.

No setting bounds a run's `out/` folder: a script writes there as much as the disk takes, neither `TREE_MAX_BYTES` nor `OUTPUT_MAX_BYTES` counts it, and pruning answers the growth (`S17`, `S19`; `D07-runs` states it).

Six settings bound what runs take of the host, and none of them is applied by `internal/limits`: the kernel applies four, through the control groups scripts arranges, and the run core the other two. `RUNS_MEMORY_MAX_BYTES` and `RUNS_CPU_PERCENT` are written once, at start, into the group `runs/` that every run shares (`D03-serve`); `RUN_MEMORY_MAX_BYTES` and `RUN_PIDS_MAX` into each run's own group as it starts (`D06-runner`), through the run core's `Config` (`D07-runs`). A run the kernel kills for memory ends `exited` with exit code 137, as any death by a signal scripts did not send (`D06-runner`); a script refused a process by `pids.max` sees its own attempt fail and runs on. `RUN_MAX_ACTIVE` and `RUN_MAX_QUEUED` are how many runs run at once and how many more may wait, which the run core counts (`D07-runs`). Above them all the manifest's `[resources]` `memory_max` bounds the service unit as a whole (`D02-cli`). Like every other setting, each is the value the serving process read at its start.

## Operations, the deadline and the halt

`Operation(ctx)` returns the context one git run runs under and the function that releases it. That context ends at the first of four things: `ctx` ends (the `run` call's caller went away; a delivery's runs are made under a context its end does not reach, so a run an event starts is never cut off that way, `D14-delivery`), the deadline passes (the channel `After` returned for `OPERATION_SECONDS` delivers), the limits are halted, or the caller releases it. `context.Cause` of the ended context tells which: `ctx`'s own cause, `ErrTimedOut`, `ErrHalted`, or `context.Canceled`. Whichever is seen first decides the cause, and nothing later changes it; when `ctx` ended first, `ctx`'s cause wins even if the deadline has also passed; and a `ctx` done before `Operation` returns, already done at the call or done during it, gives a context already done when it returns, so a source that checks it starts no git.

A stop has one moment here. At the signal the run core refuses new runs (`runs.ErrDraining`, `D07-runs`) and new deliveries (`D14-delivery`); draining ends no git and refuses no `Operation`, so the limits have no draining state of their own. At the drain deadline `Run` calls `Halt` (`D03-serve`), concurrently with the run core's `Drain`: every operation context still open ends at once with `ErrHalted`, so its git is killed, and every `Operation` after that returns a context already ended without asking the clock, so no git starts afterwards. No git scripts started outlives the process. `Halt` kills no script: the run core kills the process groups of the runs still running (`D07-runs`).

## Sync points

Tests drive the deadline without sleeping, through the `Clock` they hand `limits.New` (and, for a whole process, through `cli.Process.After`), so one moment is contract. `Operation` calls `After` exactly once, with `OPERATION_SECONDS` as a `time.Duration`, before it returns, and so before the git it bounds can start; nothing else in the package calls `After`. `Clock` carries `After` alone, since no limit here is measured on a reading of the time. A nil `After` means `time.After`; that meaning is the declaration's gloss and is accepted as untestable, since proving it needs the real clock, so tests hand a non-nil `After`. A test therefore learns that a git run is about to start when its fake `After` is asked for `OPERATION_SECONDS`, and may use that call as a hook (to turn on `SetFailing` for the store's handle, say, as `D04-store` describes); it fires the channel when it chooses, and a channel on which a value is ready at any time after that call counts as the deadline passing, so a test may return a channel with a value already ready and know the git run fails as one that took too long. `Halt` ends every open operation context before it returns, so a test that calls it can then wait for git to be gone.

A number of seconds turned into a `time.Duration` saturates at the longest duration, so every setting `settings.Read` accepts is usable.

## Decisions

- Both packages are one document because a setting and its application share one vocabulary; `internal/settings` stays a package of its own so that `D03-serve` reads and refuses the settings before it builds anything, and so that `internal/limits` is the only package that imports it besides `internal/cli`.
- `internal/limits` owns three sentinels: `ErrTooLarge` and `ErrTimedOut` because they name these two limits, `ErrHalted` because halting lives here; `D05-git-and-source` returns them, `D07-runs` reads `ErrHalted` and `D05-git-and-source`'s `Reason` reads the other two with `errors.Is`. None matches a context error, so a consumer that compares an error with `context.Cause(ctx)` never mistakes a deadline for its caller leaving.
- No `Drain`, `Draining` or `ErrDraining` here, departing from sites: scripts' only refusals while draining are a new run's and a new delivery's, which the run core owns because the event bus calls it too, and no git scripts runs is refused while draining.
- No `Clock` method on `Limits`, departing from sites: no consumer reads the clock back, and the sync point is stated on the `Clock` `New` was given.
- The deadline is a context cause, not a timer the consumer selects on, so `D05-git-and-source` bounds a git run by handing git the context and learns why it ended from `context.Cause`.
- `RUN_KEEP_DAYS` `0` is refused like `RUN_KEEP_COUNT` `0`: the stories refuse it (`S02`), and the catalog's `PastKeeping` is defined for one day or more only.
- `RUNS_CPU_PERCENT`'s unit is `percentage`, and `Error` words it `not a positive whole percentage` rather than `not a positive whole number of percentage`, because that is the story's line (`S02`); every other unit reads `not a positive whole number of <unit>`.
- The six run settings are `Settings` fields like the rest, read and refused by `Read` in the stories' order, so a setting that cannot be read is refused before scripts touches any control group (`S02`). `Limits` carries them unread: no package applies them through it.
- The sentinels' `Error` texts are not contract; every text a user sees that quotes a limit is `D08-pages`'. The catalog records no limit with a run (`D04-store`), so a page can quote only the value the serving process read at its start, never the one a run was refused under.

## Consumer tasks

The start (`D03-serve`): `s, err := settings.Read(p.LookupEnv)`; when `err != nil`, `Run` writes `"scripts: " + err.Error() + "\n"` to `Stderr` and refuses before it looks for its socket (the exit code is `D03-serve`'s), so a test of the refusal uses `errors.As(err, &se)` with `var se *settings.Error` and reads `se.Name`, `se.Value` and `se.Unit`. Otherwise `l := limits.New(s, limits.Clock{After: p.After})`; `src := source.New(source.Config{Repos: <s.ReposDir resolved against Dir>, Git: g, Limits: l})` (`D05-git-and-source`); `core := runs.New(runs.Config{…, ScriptSeconds: s.ScriptSeconds, OutputMaxBytes: s.OutputMaxBytes, KeepDays: s.RunKeepDays, KeepCount: s.RunKeepCount, RunMemoryMaxBytes: s.RunMemoryMaxBytes, RunPidsMax: s.RunPidsMax, MaxActive: s.RunMaxActive, MaxQueued: s.RunMaxQueued, ScriptAfter: p.ScriptAfter, …})` (`D07-runs`), its `Cgroup` the `runs/` group the start prepared with `s.RunsMemoryMaxBytes` and `s.RunsCPUPercent` (`D03-serve`); the numbers a page quotes reach the pages as plain values through `D03-serve`'s wiring, which `D03-serve` and `D08-pages` own; the drain deadline is `time.Duration(s.DrainSeconds) * time.Second` of real time, saturating (`D03-serve`). At the drain deadline: `l.Halt()`, concurrently with `core.Drain(drainCtx)`.

The source (`D05-git-and-source`): for each git run, `op, cancel := l.Operation(ctx)`, `defer cancel()`, then runs git under `op`; once git has exited it checks `context.Cause(op)` and returns `limits.ErrTimedOut` when `errors.Is(context.Cause(op), limits.ErrTimedOut)`, `limits.ErrHalted` when it matches that, and `ctx`'s cause otherwise. While unpacking it adds each file's size and, once the sum exceeds `l.Settings().TreeMaxBytes`, ends the unpack and returns `limits.ErrTooLarge`.

The run core (`D07-runs`): `sha, err := src.Resolve(ctx, sc.Repo, ref)`, then `src.Archive`; an error from either for which `errors.Is(err, limits.ErrHalted)` holds (a git halted at the drain deadline) or `errors.Is(err, context.Cause(ctx))` holds (the `run` call's own context ended) is a cut-off call that records no run (`D07-runs` R-FKYP-VVQK, `D05-git-and-source`); any other error is a failed run with `source.Reason(err)`, which maps `limits.ErrTooLarge` to `too_large` and `limits.ErrTimedOut` to `timed_out`.

A test of the settings calls `settings.Read` with a lookup over a map and compares the result with `settings.Defaults()` or the expected `settings.Settings` with `==`, or uses `errors.As` to get the `*settings.Error` and compares its `Name`, `Value`, `Unit` and `Error()`. A test of the limits builds `limits.New(settings.Defaults(), limits.Clock{After: after})` whose `after` records each requested duration and returns a channel the test holds; it calls `op, cancel := l.Operation(context.Background())`, reads that `after` was asked once for 600 seconds, fires the channel, waits on `op.Done()` with a deadline that fails the test, and asserts `errors.Is(context.Cause(op), limits.ErrTimedOut)`; it opens a second operation, calls `l.Halt()`, asserts the second is done with `ErrHalted` as soon as `Halt` returns, and that a third `Operation` is done at once without a call of `after`. A test of a whole process hands `cli.Run` a `Process` whose `LookupEnv` answers `TREE_MAX_BYTES` `1024`, `OUTPUT_MAX_BYTES` `1024`, `OPERATION_SECONDS` `60` and `SCRIPT_SECONDS` `30`, and whose `After` and `ScriptAfter` record their durations and return channels the test holds; it runs fixture scripts over appkit's `mcp.Client` and reads the runs, the pages and the catalog, then starts a second `Run` over the same `Dir` with other values.
