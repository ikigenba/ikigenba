# D07-runs

The run core: `internal/runs`, the one place a run is made, started, bounded, ended, recorded, recovered and pruned, and the piece the event bus calls. A `*runs.Core` takes a script and a request, makes the run's folder, resolves and unpacks the commit through `internal/source`, starts `python3.12 main.py` through `internal/runner` in a control group of its own, or queues the run when every slot is taken, and answers at once, without waiting for the script or a slot; from then on it enforces `SCRIPT_SECONDS`, keeps the head of each output stream, records how the run ended, and prunes. It also ends runs on request (`cancel`), with their script (`delete`), at the drain deadline, and settles at start the runs a dead scripts left `running`. This document declares every exported name of `internal/runs` but the three `D10-trail` declares (`StartedAttrs`, `FinishedAttrs`, `Caller`) and `Deliver`, which `D14-delivery` declares, and states what each does.

`D01-layout-and-run-seam` declares `cli.Process`, whose `Now`, `ScriptAfter`, `Rand` and `Dir` reach the core through `cli.Run`, places the runs under `state/runs/`, and declares the run id (`store.NewRunID`) and the Python version; `D04-store` declares the run record, its status, reason and trigger words, and the two transitions `AddRun` and `FinishRun`; `D05-git-and-source` declares `source.Source` (`Resolve`, `Archive`, `Reason`) and `git.Error`; `D06-runner` declares `runner.Start`, `Spec` and `Process` (`Wait`, `Kill`); `D10-trail` declares the run's events and the three functions that form them; `D12-limits` reads and refuses the settings, so this document receives `SCRIPT_SECONDS`, `OUTPUT_MAX_BYTES`, `RUN_KEEP_DAYS`, `RUN_KEEP_COUNT`, `RUN_MEMORY_MAX_BYTES`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE` and `RUN_MAX_QUEUED` as plain values, and declares `limits.ErrHalted`, which ends a git run at the drain deadline. `D03-serve` builds the core, handing it the `runs/` control group its start prepared, or the reason it could not, and calls `Recover`, `Prune` and `Drain`, and mounts `Deliver` as the event bus's handler; `D11-tools` calls `Run`, `Cancel` and `Delete`; `D14-delivery`'s `Deliver` calls `Run` once for each script a delivered event concerns; `D08-pages`, `D09-run-files` and `D11-tools` locate a run's files and learn that they are gone through `Folder`, `Gone` and `Sizes`.

## The run folder

Every run gets a folder of its own, `<Runs>/<script id>/<run id>/`, `Runs` being `state/runs` under the process's directory in a running scripts. The folder is the product, not a cache: nothing rebuilds it. A run that started holds five entries: `input.json`, the request's input byte for byte, the `input` argument or, for an event run, the event (`D14-delivery`), or `{}` without one; `tree/`, the commit's files as `git archive` emits them, with every write permission removed from `tree/` and from every directory and file under it before the script starts, symbolic links left alone since their own bits mean nothing and following one would reach outside the folder; `out/`, empty at start, where the script writes; and `stdout` and `stderr`, the head of each stream. The run's metadata is in the catalog; the folder holds no file of the core's own beyond those five.

A run that could not start holds what was produced before its failure and no stream it never opened: always `input.json`; `tree/` when the unpack got as far as making it, partial or whole, read-only all the same; `out/` only when the process could not be launched, everything before it having succeeded; and `stderr` only when git failed with words of its own, which are written there, unprefixed, bounded as a script's standard error is. So a run whose ref did not resolve holds `input.json` alone, as the run page shows it.

Write permission is restored under `tree/` by the code that removes a folder, pruning, deletion and the clean-up of a call cut off, and by nothing else, so no other package knows about the bits. The bit is a guard against an accidental write, not a boundary: a process with the service's own user and group can restore it, and bubblewrap's read-only bind, the planned second runner, is the boundary.

`Folder`, `Gone` and `Sizes` are how the pages, the run files and the tools find a run's files without knowing the layout: `Folder` is the directory, the five entry names are exported constants, `Gone` says the folder is no longer there (a fact about the run, shown as such, never an error), and `Sizes` is the bytes kept of each stream, the record's for an ended run and the files' for a running one, whose record holds zero until it ends.

## Starting a run

`Run` refuses at once, in this order: with `ErrDraining` once `Drain` has been called; with `ErrNoCgroup`, its text `runs.NoRuns` filled with the reason, while `Config.Unavailable` holds a reason; for a run an event asks for, as below; and with `ErrQueueFull` while `MaxQueued` runs are queued. The queue's count is taken once, then, so a run whose tree is unpacking while the queue fills is still queued, and the queue may briefly hold more than `MaxQueued`. Otherwise it reads `Now` once, the run's `started` and the start of its duration, draws the run's id, makes the folder and writes `input.json`, resolves the ref (`req.Ref`, or the script's own when it is empty) and unpacks the commit into `tree/`, removes write permission there, and makes `out/`. If fewer than `MaxActive` runs hold a slot and none is queued, it makes the two stream files and starts the process; when the process cannot be launched, it removes the two stream files again, since the run never opened a stream. Only then does it record the run, `running`, emit `run.started`, and answer. Otherwise it records the run `queued`, emits nothing, and answers; its folder holds `input.json`, `tree/` and `out/` and no stream file until its process starts. A resolve or unpack that fails, and a process that cannot be launched, make a run all the same: it is recorded `failed` with `source.Reason` of the error or `start_failed`, its prune runs, its one `run.finished` is emitted, and `Run` answers it, with a nil error, so the caller answers `failed` and the reason. Two failures make no run at all, because nothing true can be recorded: a folder or `input.json` that cannot be made, and a catalog that will not take the record (`AddRun` answering a catalog error, `running` or `failed` alike). Either way `Run` returns an error that matches none of the package sentinels, the process it may have started is killed and the folder removed, and the caller answers `store.Unreachable`, so a `run` that cannot reach the catalog changes nothing.

A call is cut off, rather than failed, when the limits halt its git, or when its context ends or the drain deadline passes before it has recorded its run: it records nothing, removes the folder it had begun, starts nothing and emits nothing, and `Run` returns an error matching `limits.ErrHalted` when its git was halted or the drain deadline passed, and the context's cause when its context ended. The same holds when its script was deleted while it ran its git: `AddRun` answers `store.ErrNotFound`, and the process it may already have started is killed and its folder removed. Whenever `Run` returns an error, nothing of the call remains. Once the run is recorded, the caller's context no longer matters: a run outlives the request that asked for it.

The process is `runner.Start`'s command, the interpreter `runner.Interpreter` names running `main.py`, in `tree/`, in a process group of its own, with exactly the fourteen variables the decisions fix: `PATH`, scripts' own verbatim; `HOME` and `IKIGENBA_RUN_DIR`, the folder; `LANG`, `C.UTF-8`; `IKIGENBA_RUN_ID`; `IKIGENBA_SCRIPT`, the script's id; `IKIGENBA_SHA`; `IKIGENBA_OUT_DIR` and `IKIGENBA_INPUT`, the paths of `out/` and `input.json`; `IKIGENBA_USER_ID` and `IKIGENBA_REQUEST_ID`, the run's user and request id; `IKIGENBA_EVENT_ID` and `IKIGENBA_EVENT_DEPTH`, the id and depth of the event the run was made for, empty and `0` for a run no event made, which a script sends on as `X-Event-Cause` and `X-Event-Depth` when it calls a sibling (scripts forwards nothing itself); and `IKIGENBA_SERVICES`, scripts' services path verbatim, empty when scripts has none. The paths are absolute and name the run's real places; nothing promises their shape, so the bubblewrap runner may bind the folder elsewhere.

Runs are concurrent, across scripts and within one, up to `MaxActive` at once: within that nothing serializes them. A run **holds a slot** from the moment its process starts until its `run.finished` is emitted. A run beyond them waits in one queue, shared by every script and every user and by the runs events make, first in, first out. When a slot is released, after the ending's `run.finished`, the run queued longest starts: its stream files are made, its process started, its record moved to `running` with `Store.StartRun`, and its `run.started` emitted under its own caller, with no request around it. Its `started` stays the time it was asked for, so its duration counts the wait, while `SCRIPT_SECONDS` counts from its process's start. A queued run whose process cannot be launched ends `failed` with `start_failed` and the next takes the slot. `Cancel` takes a queued run out of the queue and records it `killed`; `Delete` does so for its script's queued runs before it kills their running ones, so none starts in the slot a kill frees. A queued run's ending is pruned after and reported with a `run.finished` and never a `run.started`. The queue lives in the core's memory; the catalog keeps only each run's status.

Every process the core starts runs in a control group of its own, `<Config.Cgroup>/<run id>`, bounded by `RunMemoryMaxBytes` and `RunPidsMax` (`D06-runner`). An empty `Cgroup` with an empty `Unavailable` gives a run no control group, which only a test does; `cli.Run` passes the `runs/` group when its control group step succeeded and a reason otherwise. Each has its own folder, and making, running or ending one run touches no other run's folder; only a prune removes another run's.

A request with a `Cause` makes an **event run**: its trigger is `event` and its record keeps the event's id. One script gets at most one run from one event: `Run` asks `Store.Delivered` before it makes anything, so an event already delivered to the script starts no git, and a call made while another call for the same script and event is still in progress is refused at once with `ErrStarting`, before any git, so one core never starts two processes for one event; `AddRun`'s `store.ErrDelivered` remains the guard for a race the core cannot see. The deterministic proof of that refusal holds the first call in its git, through the `limits.Clock` `After` seam; the parts of the first call's span outside its git (before its first git, between its resolve git and its archive git, and from the end of the archive through the process start to its run being recorded) have no seam to hold them and hold by the same requirement, which speaks of the whole span from the call's beginning to its return. A `Delivered` that cannot be answered is a catalog error before anything is made, never read as false. Which scripts an event concerns, and the request each run is made with, are `D14-delivery`'s.

## Bounds and endings

`SCRIPT_SECONDS` is counted from the moment the process started, on the timer `ScriptAfter` returns, one per started process. `OUTPUT_MAX_BYTES` bounds each stream on its own: the first `OUTPUT_MAX_BYTES` bytes of a stream are kept in its file, the rest is read and dropped, the script is neither killed nor held up, and the run is `truncated` when either stream was cut; `stdout_bytes` and `stderr_bytes` count what was kept. Nothing bounds `out/`: `OUTPUT_MAX_BYTES` is the streams' and `TREE_MAX_BYTES` the tree's, and a script writes to `out/` as much as the disk takes, pruning answering the growth.

A running run ends exactly once, and its status says who ended it: `exited`, with `runner.Process.Wait`'s code, when `main.py` ended on its own; `timed_out` when the timer fired first; `killed` when `Cancel`, `Delete` or the drain deadline killed it first. `Kill` answering false means `main.py` had already ended, so the ending is the run's own: a `cancel` racing the run's exit is refused with `store.ErrEnded` and the run keeps its exit. The stream files are final when the ending is recorded: what `main.py`'s leftovers wrote between its exit and the group's kill may be kept, but nothing is written after. The ending is recorded with `FinishRun` once the process group is dead, `finished` and the end of the duration being one reading of `Now` taken then; the prune that every ending triggers runs next; and the run's `run.finished` is emitted last, so a test that sees the event sees the prune done.

## Stopping, recovering and pruning

`Drain` is the stop: from its call `Run` refuses new runs, while the calls already accepted and the runs already running go on. At the call every queued run is finished `failed` with `queue_abandoned`, at once, its `run.finished` emitted, and no slot released from then on starts anything; a call in progress whose tree is unpacked while every slot is taken is recorded `failed` with `queue_abandoned` the same way, and answered so. It returns as soon as no run is running and no `Run` call is in progress. When its context ends first, at the drain deadline, it kills every run still running and records each `killed`, emits each `run.finished`, and makes every `Run` call still in progress a cut-off call; it returns once those calls have returned and no process it started is alive, killing and recording any run recorded after the deadline. A call still in its git returns only when its git ends, so `D03-serve` must call `Halt` on its `*limits.Limits` at the drain deadline concurrently with `Drain`, not after `Drain` returns. So every killed run's `run.finished` is emitted before the writer's shutdown, which `D03-serve` calls after `Drain` returns.

`Recover` runs at start, before readiness: every run still recorded `running` belonged to a scripts that died, so each is recorded `killed`, finished now, with the sizes its stream files hold, and its `run.finished` emitted through the writer, its duration running from its recorded `started`; every run still recorded `queued` is recorded `failed` with `queue_abandoned` the same way, and never started. `Prune` follows it, and runs again after every ending: it removes, over the whole catalog, every run `store.PastKeeping` names for `Now` and the two keeping settings, the folder first and then the record, so a failure between them leaves a record whose files are gone, never a folder no record names. It never touches a running or queued run and records no event. There is no timer: a run past keeping stays until the next `Prune` or the prune of the next ending, however long that is. This departs from sites, which prunes after a publish: scripts has no publish, and a run's end is the moment the catalog grows.

## Decisions

- Settings arrive as plain `int64` values in `Config`; `D12-limits` parses, defaults and refuses them. `ScriptSeconds` seconds past `math.MaxInt64` nanoseconds is `time.Duration(math.MaxInt64)`, as sites caps `OPERATION_SECONDS`.
- The drain refusal is the core's (`ErrDraining`), because the core is what the event bus calls and must refuse on its own; `D11-tools` answers it with `runs.Stopping` after looking the script up.
- A call whose context ends before its process starts is cut off like one halted at the drain deadline, not a `git_failed` run: either way the caller gets no answer, so a record would be a run nobody asked to see.
- A failed run's `stderr` holds git's words only when the error carries a `*git.Error` whose `Stderr` is not empty; it is bounded by `OUTPUT_MAX_BYTES` and sets `truncated` when cut, which `D04-store` permits on a failed record. A failed run never has `stdout`, and `start_failed` leaves no stream files, since the run never opened a stream.
- Write permission is removed from a partial tree too, so every `tree/` a folder holds behaves alike.
- `Recover` records `truncated` false: whether a dead scripts cut a stream is not known after the fact, so a run marked `killed` at start is exempt from the trail's rule that a cut stream reports `truncated` true (`D10-trail` is amended to say so).
- A recorded `finished` is never before `started`: when `Now` has stepped back, `finished` is the run's `started`, so `FinishRun` never refuses an ending and `Recover` cannot fail on one.
- `Cancel` of a run recorded `running` that has no process of this core records it `killed` all the same, so `Cancel` never leaves a record no one can end.
- The prune of an ending runs before that ending's `run.finished`, so the event marks a settled catalog.
- `Delete` removes folders before the records, as pruning does, and returns only after every killed run's `run.finished`, so `script.deleted`, which `D11-tools` emits after it returns, follows them.
- An event run is made by `Run` itself, with `Request.Cause`, not by a second path, so every rule of making, bounding, ending, recording and pruning a run holds for it unchanged; `Cause` is appkit's `events.Cause`, the id and depth a handler's context carries, which is exactly what the script is given and forwards.
- A queued run is recorded before it waits, so `run` answers it and `runs`, `result` and `cancel` see it; the queue is the core's own, since one core is the only one that starts processes.
- A queued run starts after the released slot's `run.finished`, so the trail shows the slot change in order.
- The queue-full refusal counts once, at the call, before anything is made; a run already unpacking when the queue fills still queues.
- `ErrNoCgroup` wraps the reason `Config.Unavailable` holds, so the tools answer its text as it is and the delivery can quote it.
- The core reads `Config.Rand` from one goroutine at a time; sharing one `Rand` with the store and the writer is `cli.Run`'s to serialize (`D01-layout-and-run-seam`).

## Consumer tasks

At start (`D03-serve`): `core := runs.New(runs.Config{Store: st, Source: src, Writer: w, Runs: filepath.Join(dir, "state", "runs"), Path: path, Services: servicesPath, Cgroup: runsGroup, Unavailable: reason, ScriptSeconds: s.ScriptSeconds, OutputMaxBytes: s.OutputMaxBytes, KeepDays: s.RunKeepDays, KeepCount: s.RunKeepCount, RunMemoryMaxBytes: s.RunMemoryMaxBytes, RunPidsMax: s.RunPidsMax, MaxActive: s.RunMaxActive, MaxQueued: s.RunMaxQueued, Now: p.Now, ScriptAfter: p.ScriptAfter, Rand: rand})`; then `core.Recover(bg)`, `core.Prune(bg)`, `bg` being a context the stop signal does not end (`context.WithoutCancel(ctx)`, say), since a done context makes every catalog call fail (`D04-store`) and both must run to completion (`D03-serve`); then readiness. At the signal: `core.Drain(drainCtx)` beside the server's drain, `l.Halt()` on its `*limits.Limits` `l` as soon as `drainCtx` ends, concurrently with `Drain`, and the writer's `Shutdown` after `Drain` returns.

The tools (`D11-tools`), `u` the call's caller: `run` is `s.Find` then `r, err := core.Run(ctx, sc, runs.Request{Ref: ref, Input: raw, Caller: u})`: `errors.Is(err, runs.ErrDraining)` is the stopping refusal, `runs.ErrNoCgroup` the unavailable refusal, answered with `err.Error()`, `runs.ErrQueueFull` the queue-full refusal, answered with `err.Error()`, `runs.QueueFull` filled with `MaxQueued`, `store.ErrNotFound` the missing-script refusal, an error matching `limits.ErrHalted` or the request context's cause is a cut-off call, answered with nothing at all, and any other error, a catalog error or a folder that cannot be made, `store.Unreachable`; otherwise `r.Status` is `running`, `queued` or `failed`, with `r.SHA` and `r.Reason`. `cancel` is `s.FindRun` then `core.Cancel(ctx, id)`, `store.ErrEnded` being the ended refusal. `delete` is `s.Find` then `core.Delete(ctx, sc.ID)`, then `script.deleted`. `result` is `s.FindRun`, then `core.Gone(r)` for `files_gone`, `core.Sizes(r)` for the byte counts, and the files under `core.Folder(r)`: `runs.StdoutFile`, `runs.StderrFile` (absent read as `""`) and the regular files under `runs.OutDir`.

The delivery (`D14-delivery`): for each subscriber `sc`, `core.Run(context.WithoutCancel(ctx), sc, runs.Request{Input: b, Caller: identity.Caller{UserID: sc.Owner, RequestID: rid}, Cause: events.Cause{ID: d.Event.ID, Depth: d.Event.Depth}})`, `b` the event's canonical JSON; `errors.Is(err, store.ErrDelivered)` means the script already has its run.

The pages and run files (`D08-pages`, `D09-run-files`): `core.Folder(r)` joined with `runs.InputFile`, `runs.StdoutFile`, `runs.StderrFile` or `runs.OutDir`; `core.Gone(r)` for whether the run's files are shown as gone; `core.Sizes(r)` for the byte counts the run's card shows.

A test builds a store, a source over a bare repository fixture, a writer over a `*telemetry.Capture`, and a core over a temporary `Runs`, with a `Now` it switches, a `ScriptAfter` whose channel it fires, and a `PATH` holding the real `python3.12`; it runs fixture scripts that report what they see by printing it or by writing into the directory `IKIGENBA_OUT_DIR` names, and that wait for a file the test creates in their run folder, which is how a test holds a slot: with `MaxActive` 1 a run so waiting makes the next `Run` queue, deterministically; it hands `Cgroup` a directory of its own and reads each run's control group files there; it reads the folder, the catalog and the capture.
