# D11-tools

scripts' MCP endpoint is its catalog and its runs offered to models: eleven tools, `list`, `show`, `create`, `update`, `delete`, `subscribe`, `unsubscribe`, `run`, `runs`, `result` and `cancel`, registered on the one `mcp.Server` the handler mounts at `/mcp`. This document is `internal/tools`: what `Register` puts on a server, in that order; what a client sees of each tool in `tools/list` (its name, the description written for a model, its input schema, its output schema and its annotations); the argument and result types the package exports; which script a `name` argument and which run a `run` argument name; the rules each tool holds its arguments to, the order it checks them in and the exact words of every refusal; what a success answers and what it changes; the one answer every tool gives when the catalog cannot be reached; the drain refusal; and the `kind` and `outcome` of the `tool.called` each call records.

`D01-layout-and-run-seam` declares the run seam, `pages.ServiceName`, the display string `main` reads, the entity ids (`store.ValidScriptID`, `store.ValidRunID`) and the wiring of the server `main` builds; `D04-store` declares the catalog (`store.Store` and its methods, `Subscribe` and `Unsubscribe` among them, `store.Script`, `store.Subscription`, `store.Run`, `store.Draft`, `store.ValidName`, `store.ValidEvent`, the status, reason and trigger words, `store.Unreachable`, the sentinels `store.ErrNotFound`, `store.ErrNameTaken`, `store.ErrEnded` and `store.ErrNotSubscribed`, and what a catalog error is, R-R9U5-5IF5); `D05-git-and-source` declares `source.Source` (`Owner`), `source.ValidRepo`, `source.ValidRef` and how a repository's owner is read; `D07-runs` declares `runs.Core` (`Run`, `Cancel`, `Delete`, `Drain`, `Folder`, `Gone`, `Sizes`), `runs.Request`, `runs.ErrDraining`, `runs.ErrNoCgroup`, `runs.ErrQueueFull`, `runs.Config` (its `Cgroup` and `MaxQueued`) and the run folder's entry names, and states how a run is made, queued, started, ended, killed or taken from the queue with its script, and refused while draining, while runs are unavailable and while the queue is full; `D04-store` declares `store.StatusQueued` and `store.ReasonQueueAbandoned` among the status and reason words; `D10-trail` declares every `script.*` and `run.*` event, their attributes, which outcome records each and in which order, and that `subscribe` and `unsubscribe` record none; `D12-limits` declares `limits.New`, `limits.Clock`, `limits.Limits` (`Halt`) and `limits.ErrHalted`; `D03-serve` declares `web.Config` and `web.Handler`, which build the tools set, mount the server at `/mcp`, and cut off requests at the drain deadline. This document restates none of them.

## What is someone else's

- appkit's `mcp` server is the transport and the protocol: `/mcp` takes only POST, one JSON-RPC message per POST, one `application/json` answer, no session and no stream; the 2026-07-28 envelope and the earlier revisions; the 405 for every other method; the malformed-transport checks; `server/discover` and `initialize` with their `instructions`, read afresh from the services file's entry named after the server and absent when there is none; for a client of an earlier revision, `initialize` echoing a requested `2025-11-25` or `2025-06-18`, no `Mcp-Session-Id` on any answer, and `202` with no body for `notifications/initialized`; and the protocol error `Unknown tool: <name>` for a tool scripts does not have.
- appkit's `AddTool` and schema rule are the Tool object's members and their order, the annotations each `Effect` gives, the derivation of every schema from the Go types declared below, the strict reading of `arguments` with its `invalid arguments:` text, a `tools/call` with no `arguments` read as one with `{}` (restated by R-O92S-SQ5B as scripts' own answer, so that scripts' tests fail should another appkit release stop giving it), the success result a typed handler's output becomes, the `isError` result a handler's error becomes, and the `tool.called` event for every call that reaches a tool, recorded after whatever the handler recorded, with `duration_us` 0 when the arguments were refused and otherwise measured on the writer's clock. A `json.RawMessage` field is appkit's one carrier of an arbitrary JSON object, schema `{"type":"object"}`, received as its bytes unaltered; that is how `run`'s `input` reaches `input.json` byte for byte.
- `main` builds the server with `pages.ServiceName`, the display string it read with `version.Display`, the writer `Run` builds and `Instructions` nil (`D01-layout-and-run-seam`). Routing exactly `/mcp` to it, `identity.Require` around it with its 500 for a request without `X-User-Id`, `telemetry.Middleware` with `request.started` and `request.finished`, calling `Register` once when the handler is built, and cutting a request off at the drain deadline are `D03-serve`'s. The tools need nothing from the request's context but the caller appkit hands each handler: no tool answers a URL, so nothing is put in the context for them.
- Which `script.*` and `run.*` events a call records, with which attributes, under which identity and in which order, is `D10-trail`'s: the tools emit `script.created`, `script.updated` (only when the ref changed) and `script.deleted` (only after `runs.Core.Delete` has returned) through the writer with the call's own context, and the run core emits every `run.*` event.

Story by story: S05's protocol stories (`initialize`, earlier revisions, `server/discover`, the browser's 405, the missing identity) are appkit's server given `D01-layout-and-run-seam`'s wiring and `D03-serve`'s mounting; its tool list, refusal forms, catalog answer and `tool.called` are this document's. S06 to S11 and S26 are this document's, and so are the members S27 adds to what `runs`, `result` and `cancel` answer of a run an event started. S16's events are `D10-trail`'s; what a delivered event makes is `D14-delivery`'s. S17, S18 and S19 reach this document where a tool answers: the start answer of a run `too_large`, the drain refusal, the start answer `failed` with `queue_abandoned` of a run whose tree was unpacked during the drain while every slot was taken (`D07-runs`), and `no run '<id>'` for a pruned run. S02 and S08 reach it with the unavailable refusal, and S08 with the queue and the queue-full refusal.

## What a client is told

All eleven tools are registered with `mcp.AddTool`, in S05's order, `subscribe` and `unsubscribe` after `delete`, so every schema is derived from the argument and result types this package exports, and the schemas are stated here whole, property descriptions included, since a model reads them. Each description is S05's word for word: a one-line summary, the line the landing page shows beside the tool's name, then a paragraph on how to call the tool. `list`, `show`, `runs` and `result` change nothing and are `mcp.Read`; `create`, `update`, `subscribe` and `run` add a script, a ref, a subscription or a run, which a later call can change back or which is a record, `mcp.Additive`; `delete` removes a script and every run for good, `unsubscribe` removes a subscription, so events that would have run the script no longer do, and `cancel` kills a running script, `mcp.Destructive`. That is what the gateway's `describe` reports as each tool's kind and what `tool.called`'s `kind` says.

appkit derives a schema's `required` list from the `mcp:"required"` struct tag and a property's `description` from the `description` tag, so each argument and result type below states its fields' tags whole. Every output schema marks required each member that is always present, a non-pointer field tagged `mcp:"required"`, which appkit always writes; a member S05 says is "not always present" is a pointer field, untagged, left out when nil, never sent as `null`. No output property carries a description. An argument S05 requires is tagged `mcp:"required"`, and every argument carries S05's description. `input` is a `json.RawMessage`, so any JSON object is accepted and any other value, `null` included, is refused as the arguments are read (`input: expected object, got string`).

## Which script, which run

Every tool works for its caller alone, the `identity.Caller` appkit hands the handler. A `name` argument names the caller's script of that name, as `Store.Find` answers it for the caller's user id. Another user's script, a name no script has, a script's id, and a string `store.ValidName` refuses all name nothing, and are refused alike with `no script named '<name>'`, quoting the value as sent; a string `ValidName` refuses is refused without asking the catalog, since no script can have it. A `run` argument names a run of one of the caller's scripts, as `Store.FindRun` answers it; another user's run, an id no run has (a pruned run's, a deleted script's), a script's id or name, and any string `store.ValidRunID` refuses name nothing, and are refused alike with `no run '<id>'`, the last without asking the catalog. The caller so learns nothing of other users' scripts and runs, though their names stay taken for `create`.

## Rules, order and refusals

A handler is reached only with arguments appkit read cleanly. From there each tool checks its rules in a fixed order, and the first that fails is the whole answer, one line in scripts' words, the value quoted exactly as sent:

- `create`: the name rule (`invalid name '<name>'`); the name not taken by any script of any owner (`a script named '<name>' already exists`); the repository, `rep_` and 16 lowercase hexadecimal digits, whose directory exists and whose `ikigenba.owner` is the caller (`no repository '<repo>'`); the ref, when sent, a string git accepts as a ref name (`invalid ref '<ref>'`).
- `show`, `delete` and `runs`: the script.
- `subscribe`: the script; then the event name, two lowercase words joined by one `.` as `store.ValidEvent` reads it (`invalid event '<event>'`). A pair already subscribed is not a refusal: it succeeds and changes nothing.
- `unsubscribe`: the script; then the event name, as `subscribe`; then the pair (`'<name>' is not subscribed to '<event>'`).
- `update`: the script; the ref (`invalid ref '<ref>'`).
- `run`: the script; then the drain (`scripts is stopping; try again later`); then runs being unavailable (`runs are unavailable: <reason>`, the reason scripts gave on stderr as it started, S02); then the queue (`the run queue is full (<n> queued); try again later`, `<n>` being `RUN_MAX_QUEUED`), counted before anything is made. The ref is not checked: a ref git cannot accept names no commit, and its run fails `commit_missing` (`D05-git-and-source`).
- `result`: the run.
- `cancel`: the run; then that it is still queued or running (`run '<id>' has already ended`).

A field counts as sent when its member is present and not `null`; values are compared exactly as sent, never trimmed or folded. `create`'s owner read is the only git a tool runs: an owner read that fails any other way (git cannot be started, git exits otherwise non-zero, the read outlasts `OPERATION_SECONDS`) leaves the repository unproven to be the caller's, and is refused like a missing one. `run`'s resolve and unpack are the run core's, and a run that could not start is not a refusal but a run, answered `failed` with its reason as a success.

**The catalog.** Every tool answers from the catalog, so a tool that cannot read or write it has nothing true to say. It refuses with exactly `cannot reach the catalog; try again later` (`store.Unreachable`), quoting nothing of the underlying error, whenever a store method its answer is made from, directly or through the run core, fails with a catalog error (`D04-store`). A rule decidable without the catalog still answers first: the name rule, the ref rule and the run-id rule. The event rule is not one of them, though `store.ValidEvent` needs no catalog: S05 and S26 check it only once the script has been found, so with the catalog out of reach a `subscribe` or `unsubscribe` naming a valid script name gets the catalog line whatever its event. A test produces a catalog error by turning on `SetFailing` for the store's handle after `Register` has the store: before the call, or, for `create` and `run`, from a hook the call runs between its reads and its write, the `limits.Clock.After` the source's limits call before each git run (`D05-git-and-source`, `D12-limits`). `update`, `delete`, `subscribe`, `unsubscribe`, `runs` and `cancel` run no git and so have no hook between their reads and their writes, so no requirement states their answer to a catalog that fails partway through a call; the requirement covers them only for a catalog failing before the call. `tools/list` reads nothing of the catalog and runs no git. The same line answers a failure of `runs.Core.Run` that is not about the catalog, such as a run folder or `input.json` that cannot be made, since S05 allows a tool no other words for it. `D07-runs` says what `Run` returns in each case: when the folder or `input.json` cannot be made, a non-nil error matching no store sentinel, no `limits` error and no context error, leaving no record and no folder (R-FPUB-EYPC); and when recording the run fails, a non-nil error matching the catalog error `AddRun` returned and neither `runs.ErrDraining` nor `limits.ErrHalted`, leaving no process, no folder and no event (R-0I8W-4NXM). Either is answered `store.Unreachable`.

**The drain.** Once the run core is draining (`D07-runs`), `run` refuses every call for a script of the caller's with `scripts is stopping; try again later`, after looking the script up, so the drain refusal never tells a caller that a script it does not own exists. Every other tool answers during the drain as it always does.

**Runs unavailable and the queue full.** Both come from `runs.Core.Run`, after the drain: `runs.ErrNoCgroup` when scripts started with no control group to run scripts in, every call refused with the reason it gave on stderr as it started, and `runs.ErrQueueFull` when `RUN_MAX_QUEUED` runs are already queued, whoever's. The tools word neither from anything of their own: the unavailable refusal is the error's own text, since only the run core holds the reason, and the queue-full refusal is the error's own text too, which names the `MaxQueued` the core was built with. Either is a refusal like the drain's: no run, no folder, no git, no `run.*` event, `tool.called` with `outcome` `error`.

**A call cut off.** A `run` whose git the limits halted, or whose request's context ended before its run was recorded, and a `create` whose owner read was so halted or ended, answer nothing and record nothing: the request is cut off (`D03-serve`), its caller gets no result, and the trail holds no `tool.called` for it (S18). appkit's server records `tool.called` once a handler returns or panics and records none for a `tools/call` answered with no result, so such a handler never returns: it ends its goroutine without returning, as `runtime.Goexit` does.

A refused call has changed nothing: no script made, changed or removed, no run and no run folder, no git beyond `create`'s owner read, no script started and no running script killed; and it records no `script.*` or `run.*` event.

## What a success answers and changes

`show`, `create`, `update`, `subscribe` and `unsubscribe` answer the **script object** (`tools.Script`): `id`, `name`, `repo`, `ref`, `created`, `subscriptions`, `last_run`; `subscriptions` always present, each subscription `{"event":...,"created":...}` (`tools.Subscription`) in the catalog's order, by event name, `[]` when none; `last_run` absent for a script never run and otherwise the newest run's `id`, `status`, `exit_code` (only when `exited`) and `started`. `list` answers `{"scripts":[...]}` (`tools.ScriptList`), one listing entry per script of the caller's, by name: the script object without `created`, and with `subscriptions` the number of the script's subscriptions rather than the list. `delete` answers `{"deleted":true,"id":"<script id>"}` (`tools.Deleted`). `run` answers the **start answer** (`tools.Started`): `id`, `status`, `sha` (absent when the ref never resolved) and `reason` (only when `failed`). `runs` answers `{"runs":[...]}` (`tools.RunList`), newest first, each a **run entry** (`tools.RunEntry`): `id`, `sha`, `ref`, `trigger`, `event` (only for a run an event started), `status`, `exit_code`, `started`, `finished` (absent while `queued` or `running`), `truncated`, `reason`; `cancel` answers the run entry of the run it ended. `result` answers the **run result** (`tools.RunResult`): the run object, `id`, `script`, `sha`, `ref`, `user`, `request_id`, `trigger`, `event` (likewise), `status`, `exit_code`, `started`, `finished`, `stdout_bytes`, `stderr_bytes`, `truncated`, `reason`, then `stdout`, `stderr` and `files`, or `files_gone` `true` when the run's folder is gone. Every time is RFC 3339 UTC to the second.

`create` adds one script, owned by the caller, `ref` `main` unless sent; it reads only the repository's owner, its one git being that owner read, resolves and unpacks nothing and makes no run folder. `update` sets the ref, never the name, the repository, a subscription or a run, and runs no git; sending the ref the script has succeeds and changes nothing; a run an event starts later resolves the new ref (`D14-delivery`). `subscribe` and `unsubscribe` add and remove one subscription through `store.Subscribe` and `store.Unsubscribe` and nothing else: they read no repository, run no git, start, touch and kill no run, and record no `script.*` or `run.*` event (`D10-trail`); a repeated `subscribe` answers the script as the first did, the subscription keeping the time it was made. `delete` hands the script to the run core, which kills its running runs, records their ends, removes its folders and its record, its subscriptions and its memory of delivered events going with the record (`D04-store`), and returns; only then does the tool record `script.deleted`. `run` hands the script, the ref when sent, the input's bytes and the caller to the run core, which answers at once without waiting for the script: `running` when a slot was free and the process started, `queued` when `RUN_MAX_ACTIVE` runs were running, the run then starting on its own when a slot frees. A queued run is answered by `runs` and `result` as not yet finished, with no `finished` and no `exit_code`, and, its script not having started, `result` answers its streams `""`, their sizes 0 and its files `[]`. `runs` and `result` read the catalog, and `result` the run's folder too: the kept stream files, as they are at the call, and every regular file under `out/`, at any depth, as its path there and its size, sorted by path, no symbolic link followed. `cancel` hands the run to the run core, which kills its group, or takes a queued run from the queue so it never starts, records it `killed` and its `run.finished`, and answers the ended record; `delete` likewise takes its script's queued runs from the queue before the script goes.

`stdout_bytes` and `stderr_bytes` are what the record kept for an ended or queued run and what the stream files hold for a running one (`runs.Core.Sizes`). `stdout` and `stderr` are the files' bytes as a JSON string; appkit writes each byte that is not part of valid UTF-8 as U+FFFD, the one change a JSON string forces, so a stream cut mid-character at `OUTPUT_MAX_BYTES` reads with one U+FFFD for each byte of the cut character it kept, more than one when it kept more than one. A stream file that is absent, a symbolic link, not a regular file or unreadable reads as `""`, and a directory under `out/` that cannot be read lists nothing, so whatever a script does to its own folder, `result` answers.

## Decisions

- Output schemas mark required every member that is always present (house style, as sites); the stories leave it open.
- A `name` that `store.ValidName` refuses and a `run` that `store.ValidRunID` refuses are answered without reading the catalog, so the answer holds when the catalog cannot be reached.
- With the catalog unreachable, a rule decidable without it answers before the catalog refusal, even when a catalog check comes earlier in the order (`update`'s script before its ref).
- Every failure of `create`'s owner read other than a missing directory, an unset owner, or another owner (git cannot start, git fails, the read times out) is answered `no repository '<repo>'`: S05's refusals are a closed list of one-line texts, and ownership that cannot be read is not established. sites answers these with multi-line git texts; scripts' stories allow none.
- A `ref` sent to `run` as the empty string runs the script's own ref, as `runs.Request` reads an empty `Ref`; no run can be recorded with an empty ref (`D04-store`).
- A cut-off call never returns, as in sites; this depends on appkit's mcp server running a tool's handler on the goroutine of its `ServeHTTP` and recording `tool.called` after the handler returns and not from a deferred function, which appkit's design does not yet promise.
- A `delete` or `cancel` whose catalog write fails after the run core killed a run answers `store.Unreachable` with that run killed; the run stays recorded `running` until the next start marks it `killed` (`D07-runs`). No declared hook sits between the kill and the write, so no requirement states it.
- The result types are exported so a test decodes `structuredContent` into them member for member; the argument types are exported so a test encodes arguments with them.
- `subscribe` and `unsubscribe` take the same two arguments but each has its own argument type, because S05 gives `event` a different description in each schema.
- The listing entry's `subscriptions` is a count, not the list: `list` shows at a glance which scripts an event may start, and `show` names them (S07).
- An invalid event name is answered after the script is found, as S26 orders the checks, so it is not a catalog-free rule even though `store.ValidEvent` reads no catalog; a name the event rule refuses never reaches the store, which would refuse it too (`D04-store`).
- A repeated `subscribe` is a success, not a refusal, and keeps the subscription's `created`: a model retrying a call that already happened gets the first answer (S26). A missing pair on `unsubscribe` is a refusal, so a mistyped event name is noticed (S26).
- No package beyond `store`, `source`, `runs` and appkit is needed: no tool answers a URL, so `internal/tools` does not import `internal/urls`.

## Consumer tasks

The handler (`D03-serve`), when it is built, registers the tools once on the server `Process.MCP` made for the writer `w`: `tools.Register(srv, tools.Config{Store: st, Source: src, Runs: core, Telemetry: w})`, where `core` is the `*runs.Core` built over the same `st`, `src` and `w`; and it mounts `srv` at exactly `/mcp` inside `identity.Require` inside `telemetry.Middleware` over `w`. It puts nothing in the request's context for the tools.

A model, through the gateway's `call`, lists the eleven tools, reads its scripts with `list` and `{}`, one with `show` and `{"name":"nightly-report"}`, the runs of one with `runs` and `{"name":"nightly-report"}`, and one run with `result` and `{"run":"run_3f9a1c2e8b7d4a60"}`, calling `result` again while `status` is `queued` or `running`. Through `mutate` it makes a script with `create` and `{"name":"crm-weekly","repo":"rep_41d8f0a6b2c97e13"}` (or with `"ref":"v1"`), points it elsewhere with `update` and `{"name":"crm-weekly","ref":"next"}`, starts a run with `run` and `{"name":"crm-weekly","input":{"since":"2026-10-04"}}` (or `"ref":"v1"` for this run only), getting `{"id":"run_…","status":"running","sha":"…"}`, `{"id":"run_…","status":"queued","sha":"…"}` when every slot is taken, or `{"id":"run_…","status":"failed","reason":"commit_missing"}`, ends one early with `cancel` and `{"run":"run_…"}`, and removes a script with `delete` and `{"name":"crm-weekly"}`. Through `mutate` it also makes a script run on every push with `subscribe` and `{"name":"nightly-report","event":"repo.pushed"}`, getting the script object with `"subscriptions":[{"event":"repo.pushed","created":"2026-10-05T09:32:00Z"}]`, and stops that with `unsubscribe` and the same arguments; a run a push started then shows in `runs` and `result` with `"trigger":"event","event":"evt_…"`. Before this revision `show` answered `{"id":…,"name":…,"repo":…,"ref":…,"created":…,"last_run":…}` and a `list` entry `{"id":…,"name":…,"repo":…,"ref":…,"last_run":…}`; now the first carries `"subscriptions":[…]` and the second `"subscriptions":<n>`, each just before `last_run`. A refusal's text tells it what to fix (`invalid name 'CRM Weekly'`, `invalid ref '..bad'`), that the thing is not there (`no script named 'cleanup'`, `no run 'run_…'`, `no repository 'rep_…'`, `'sync-crm' is not subscribed to 'crm.contact_added'`), that an event name is malformed (`invalid event 'Repo.Pushed'`), that it is too late (`run '<id>' has already ended`), or to try again later (`cannot reach the catalog; try again later`, `scripts is stopping; try again later`, `the run queue is full (10 queued); try again later`), or that no run can be made at all (`runs are unavailable: <reason>`).

A tools test sets `IKIGENBA_SERVICES` with `t.Setenv` to the empty string; finds git with `exec.LookPath("git")` and the interpreter with `exec.LookPath(runner.Interpreter)`, failing when either is missing; composes its isolated git environment and builds `git.Find(path, environ)`; makes bare repository fixtures under a temporary repositories directory with `ikigenba.owner` set and commits of small standard-library `main.py` files with fixed dates; opens `db.Open(ctx, db.Config{Path: ..., Migrations: scripts.Migrations(), Now: ...})` over a temporary file and builds `store.New(d, store.Config{Now: ..., Rand: ...})` over it with a clock it controls and a seeded random source; builds `limits.New(settings.Defaults(), limits.Clock{After: ...})` with an `After` whose channels it fires, from settings with a small `TreeMaxBytes` where it needs one; builds `source.New(source.Config{Repos: ..., Git: g, Limits: l})`; builds a writer with `telemetry.New(telemetry.Config{Service: pages.ServiceName, Sink: capture, Now: ...})` over a `*telemetry.Capture`; builds `runs.New(runs.Config{Store: st, Source: src, Writer: w, Runs: ..., Path: <PATH holding git's directory and that of the file exec.LookPath(runner.Interpreter) returns>, ...})`; builds `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Version: v, Telemetry: w})`, `v` a string of its own,; calls `tools.Register(srv, tools.Config{Store: st, Source: src, Runs: core, Telemetry: w})`; and serves `srv` on loopback inside `identity.Require` inside `telemetry.Middleware` over `w`. It drives it with `mcp.NewClient(mcp.ClientConfig{Endpoint: ...})`: `ListTools(ctx, caller)` for the eleven `mcp.ToolInfo`, whose `Name`, `Description`, `InputSchema`, `OutputSchema` and `Effect()` it asserts; `CallTool(ctx, caller, "create", args)` with `args` the `json.Marshal` of a `tools.CreateArgs`, or literal bytes for arguments the types cannot hold, a `run` without `input` among them (`{"name":"crm-weekly"}`), since a `tools.RunArgs` with a nil `Input` encodes `"input":null`, which appkit refuses, and appkit's tags allow no `omitempty`; it reads each `mcp.Result` through `MarshalJSON`, subscribes and unsubscribes with `json.Marshal` of a `tools.SubscribeArgs` or `tools.UnsubscribeArgs`, makes event runs to read back with `runs.Core.Deliver` as `D14-delivery`'s tests do, decodes `structuredContent` into `tools.Script`, `tools.ScriptList`, `tools.Deleted`, `tools.Started`, `tools.RunList`, `tools.RunEntry` or `tools.RunResult`, and compares the members, in order, and the one text block. It sends `run` with an `input` whose white space it chose by raw HTTP to `/mcp`, since the client may re-encode arguments. It holds a script running with a `main.py` that waits for a file the test creates in the directory `IKIGENBA_RUN_DIR` names; holds a git at its start with a `GIT_TRACE` FIFO in the git environment; makes the catalog unreachable with `SetFailing(true)` on the store's handle, before the call or from the limits' `Clock.After` once the call's reads are done; makes the run core fail otherwise by clearing every write permission bit of the runs directory before a script's first run; drains with `core.Drain` in a goroutine of its own while a run is held; cuts a call off by calling `ServeHTTP` in a goroutine of its own and cancelling the request's context, or by calling `Halt` on the limits, and notes in a deferred function whether the call returned. It reads the catalog back with `Store.Find`, `Store.Runs` and `Store.RunByID`, the run folders by walking `runs.Config.Runs`, and the trail with `Writer.Flush` and `Capture.Events`.
