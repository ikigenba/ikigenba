# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the trail scripts records of itself from its start to its stop, and the rules its one handler keeps on every request — which route a path falls to, the identity gate around every route but the events app's two, the request's id and its two events, and how a listener is served and drained. It covers, with what stopping, pruning, verification and the Python interpreter add to a start and a stop, and what event delivery adds to the routes: a clean start, a first start, a start with no services file or no telemetry, a start that prepares the control group it runs every script in or, without one, serves with runs unavailable, a start that settles runs a dead scripts left `running` or `queued` and prunes what is past keeping, a start over a catalog a newer scripts upgraded, which warns and serves, a stop that drains requests and runs and abandons the queue, a stop whose drain runs out on a request or on a run, a restart, and every way a start is refused.

`D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, the display string `main` reads, `cli.Run`, `runner.Interpreter`, and where the catalog, the runs directory and `REPOS_DIR` resolve under `Process.Dir`. `D02-cli` declares the exit codes `cli.ExitSuccess`, `cli.ExitServerFailed` and `cli.ExitUsage`, and decides that an empty `Args` means serve. `D12-limits` declares `settings.Read`, `settings.Settings` and `settings.Error`, and `limits.New`, `limits.Clock` and `(*limits.Limits).Halt`. `D01-layout-and-run-seam` also declares the root package's `Migrations`, and names appkit's `db` package, whose `db.Open` with its `db.Config` fields `Service` and `Stderr`, `DB.Close` and `DB.SetFailing` this design uses as appkit's D15 and D16 state them; `D04-store` declares `store.New`, `store.Config` and `store.Unreachable`. `D05-git-and-source` declares `git.Find`, `source.New` and `source.Config`; `D06-runner` declares `runner.Find`; `D07-runs` declares `runs.New`, `runs.Config`, `(*runs.Core).Recover`, `Prune` and `Drain`, `runs.ErrDraining`, and the `runs.Config` fields `Cgroup`, `Unavailable`, `RunMemoryMaxBytes`, `RunPidsMax`, `MaxActive` and `MaxQueued`; `D06-runner` declares what each run's own control group holds; `D04-store` declares the status `queued` and the reason `queue_abandoned`. `D08-pages` declares `pages.ServiceName`, `pages.Load`, `pages.Config` and `pages.Handler`; `D09-run-files` declares what a run file path is, `web.FilesConfig` and `web.Files`; `D11-tools` declares `tools.Config` and `tools.Register`, and the drain refusal; `D14-delivery` declares `(*runs.Core).Deliver` and what a delivery answers and makes; `D02-cli` declares the nginx fragment that closes `/events` and `/declarations` at the public name. appkit's `telemetry` package owns the events, the writer and the request middleware this design wires; its `identity` package the gate, `Require`; its `page` package the shared files under `/_appkit/`; its `mcp` package the endpoint; its `events` package `EventsPath`, `DeclarationsPath`, `Handlers`, `DeliveryHandler` and `DeclarationsHandler`, the wire of a delivery and of the declarations. This document declares `server.Serve`, `server.DrainError`, `web.Config` and `web.Handler`, and says in what order `Run` checks its start and which refusal touches what, how it takes the socket, opens the catalog and the runs directory, settles and prunes the runs, builds the writer, the limits, the run core and the handler, tells systemd it is ready, serves and stops.

`internal/server` is a copy of sites' package of the same name, as sites copied it; with scripts it exists in a third app, which makes it a candidate for appkit. Promoting it is a separate change, and until it lands the copy is a debt this design records rather than designs away. Its requirements below are sites', restated for scripts' module path.

## The terms scripts serves on

scripts serves on the platform's common terms, the same as every app. It serves only on a listening socket it inherits and never opens one of its own; on a host that is `/run/ikigenba/scripts.sock`, held by `ikigenba-scripts.socket` beside the `Type=notify` `ikigenba-scripts.service`. A deploy restarts the service alone, so the socket and the connections queued on it outlive every restart; scripts' part is to finish what it accepted and leave the socket where systemd put it, so that a connection made while no scripts runs waits in the socket's queue and the next scripts answers it (R-BODX-EEGV, R-LSIN-QYFI).

scripts takes the socket the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. It removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` from its environment as it takes the socket, before it reads `Process.Environ` or starts any process, so that no git and no script it starts inherits them. The same environment may carry `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE`, the code the host is running; scripts reads them once, at start, through appkit's `version.Display` in `main` (`D01-layout-and-run-seam`), and shows the display string it returns as its version in its `service.started`, its pages' footer and about screen, and its MCP `serverInfo`. Neither is ever a reason not to start: with neither set the string is empty and scripts serves all the same. `Run` never looks either up, and neither is among the variables a script is given (`D07-runs`). Once it is ready it sends the datagram `READY=1` to the Unix datagram socket `NOTIFY_SOCKET` names, as `sd_notify(3)` documents, a name beginning with `@` being in the abstract namespace.

The suite is a closed system: scripts trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway calling it at its socket to have forwarded them. The manifest declares no `guests` (`D02-cli`), so every route but two, `/_appkit/` and `/mcp` included, is behind appkit's `identity.Require`: a request with no `X-User-Id` is answered 500 with `identity.MissingBody` before its path's handler or its method is looked at. The two are the exact paths `/events` and `/declarations` (`events.EventsPath` and `events.DeclarationsPath`), on which the suite's events app, a sibling on the socket, delivers events and asks which scripts accepts: a delivery carries no user, so neither path is behind the gate, and a request to either is answered by appkit's events handlers whatever identity headers it carries. They are closed to browsers by nginx, not by scripts: scripts' nginx fragment answers both 404 at scripts' public name (`D02-cli`), so only a sibling on the socket reaches them. Every request has an id: the one nginx set, or, for a request that came without one, the one appkit's request middleware makes up for it from the writer's random source, which is `Process.Rand`. `Process.Rand` is also where the catalog draws script ids and the run core draws run ids, so `Run` hands the writer, the store and the run core one reader that never lets two reads of `Process.Rand` overlap.

scripts' standard error holds only trouble: a start it refuses, a start that cannot prepare its control group and so can run no script, a socket it cannot take, a readiness it cannot report, a socket that stops accepting, a stop that cut requests off, the lines appkit's writer writes for an event it could not deliver, and appkit's one warning over a catalog a newer scripts upgraded, written as the catalog opens, which scripts serves all the same (below). A request answered with any status, a tool refused, a run that failed to start, exited non-zero, timed out, was cancelled or was killed at the drain deadline are handled, recorded in the trail, a run or a tool's result, and earn no line. So the handler has no stream at all, and while telemetry takes every event, its control group is ready and its catalog is not ahead of it, a running scripts writes nothing to either stream. What git or a script writes to its own streams is `D07-runs`' and never reaches scripts' standard error.

## Checking the start

With `Args` empty, `Run` checks, in this order: its fourteen settings, through `settings.Read` over `LookupEnv` (`D12-limits` fixes the spelling, the defaults, the order and the text of the refusal); then whether a socket was passed in; then whether git is on the `PATH`; then whether `runner.Interpreter`, `python3.12`, is; then it opens the catalog; then it makes the runs directory. Then it prepares its control group, which is never a refusal (below). Each refusal is the first one that applies, so a bad setting is reported whether or not a socket was passed in or git or the interpreter is installed, a missing socket whether or not either is, and a missing git whether or not the interpreter is.

A bad setting is the caller's mistake: `scripts: `, the `Error` text of the `*settings.Error`, a newline, exit 2. A socket is passed in only when `LISTEN_PID` is exactly the decimal spelling of `Process.Pid` and `LISTEN_FDS` is a count of at least one; anything else is no socket passed in, and a count above one is a unit scripts will not guess about. Both are usage errors, exit 2, with the detail line saying how to run scripts. None of these refusals touches `Process.Cgroup`, takes the descriptor, unsets a variable, looks for git or the interpreter, creates or opens anything under `Process.Dir`, serves, tells systemd anything, or records an event.

With exactly one socket passed in, `Run` removes the three `LISTEN_*` variables through `Unsetenv`, before anything else it does, so that the environment `Process.Environ` gives every git no longer holds them, and takes descriptor 3 as its listener: through `Process.Inherit` when a test supplies one, otherwise with `net.FileListener` over the real descriptor, which, as Go's `net` documentation of `FileListener` and `UnixListener.SetUnlinkOnClose` states, leaves the socket's path in place when the listener is closed. A descriptor that cannot be made into a listener is trouble on the host: `scripts: ` and the error, exit 1.

Then git and the interpreter, each a dependency the host provides, so each refusal exits 1. `Run` looks `PATH` up once, after it has taken its listener, and hands that value (empty when unset) to `git.Find` with `Process.Environ`, and then to `runner.Find`. When `git.Find` finds none it is `scripts: git not found on PATH`; when `runner.Find` finds none it is `scripts: ` followed by the value of `runner.Interpreter` and ` not found on PATH`, which reads `scripts: python3.12 not found on PATH`, the name derived from the one version declaration (`D01-layout-and-run-seam`) and never written as a literal in a requirement of this design. Both come before the catalog is opened, so a host without either keeps its state exactly as it was: an absent `state/` is still absent. Finding either runs nothing (`D05-git-and-source`, `D06-runner`).

## The catalog, the runs directory and readiness

With both found, `Run` opens the catalog with appkit's `db.Open` at `state/scripts.db` under `Process.Dir`, with the migrations `scripts.Migrations()`, the clock `Process.Now`, the service `pages.ServiceName` and, as the writer for appkit's warning, the guarded `Process.Stderr`, and builds the store over that handle with `store.New`, `Process.Now` and the guarded `Process.Rand`. On a first start `db.Open` creates `state/` and the database and applies every migration, so the catalog names no script and no run; on a later start it applies only the migrations the catalog has not had, so a catalog an earlier scripts kept is brought up to date and keeps every script and run (`D04-store`); on its way it may create and remove a probe file of its own in `state/`, which is appkit's and never outlives the call. scripts never rebuilds a catalog from anywhere. Every failure of `db.Open` is `scripts: cannot open database state/scripts.db: ` and the error's text, each newline in it replaced by a space, whether the directory could not be made or the file is not a database it can open; the path is always this relative spelling, whatever `Process.Dir` is. A catalog a newer scripts has upgraded, as after a deploy rolled back, records a migration this scripts does not carry. It is not refused: data never rolls back, so older code runs on newer data. appkit's `db.Open` applies nothing to it and writes one warning line, beginning with the service name it was given and naming the lowest version this scripts does not carry, to the writer it was given, so to `Process.Stderr`; under systemd that line reaches the journal. It is written once, as the catalog opens, before `READY=1`; it is the whole warning, and the trail records nothing about it. Then the start goes on exactly as over any catalog: the runs directory, the control group, `Recover` and `Prune` settling what a previous process left, readiness, `service.started`, and serving the scripts and runs the catalog holds. scripts states nothing about the line's wording: a test compares what `Run` wrote with what its own `db.Open` call, given the same service name and a buffer, writes over the same catalog, and that the line begins `scripts: ` is what shows `Run` handed appkit scripts' name. A start that is refused or stopped after the catalog opened, for the runs directory, a failed `Recover` or `Prune`, a signal or a readiness it cannot report, has written the warning already, and keeps it.

Then `Run` makes the runs directory, `state/runs` under `Process.Dir`, with any missing parent, when it is absent; its failure is `scripts: cannot create directory state/runs: ` and the text of the error `os.MkdirAll` gives for that path. Either refusal is exit 1, before anything is served, before systemd is told anything and before any event is recorded; the catalog refusal leaves no `state/runs` behind, and the runs-directory refusal leaves the catalog `db.Open` created or brought up to date, with no run marked and none pruned.

Then `Run` builds the run's writer with appkit's `telemetry.New`, whose `Service` is `pages.ServiceName`, whose `Version` is `Process.Version`, and whose sink, standard error, clock, pause and random source are `Process.Sink` (or appkit's socket sink when it is nil), wrapped so that it is handed nothing once the drain deadline has passed, the guarded `Process.Stderr`, `Process.Now`, `Process.Sleep` and the guarded `Process.Rand`; builds the limits, `limits.New` over the settings it read and `limits.Clock{After: Process.After}`; builds the source, `source.New` over the resolved `REPOS_DIR`, the git it found and those limits; and builds the run core, `runs.New` over the store, the source, the writer, the runs directory, the `PATH` value it looked up, the `IKIGENBA_SERVICES` value (read once, here), the eight run settings that are the core's, the control group and reason the cgroup step left (below), `Process.Now`, `Process.ScriptAfter` and the guarded `Process.Rand`. Building any of these touches nothing.

Then it settles what a previous process left, which is the whole of the start's work on the runs: `Recover` marks every run still recorded `running` as `killed`, finishes every run still recorded `queued` as `failed` with reason `queue_abandoned`, since a run asked for before a crash is never run behind its caller's back after it, and records each one's `run.finished`; `Prune` then removes every run past keeping, record and folder. Both run to completion once begun, whatever `ctx` does meanwhile, so a signal that arrives during them leaves a settled catalog. Beyond them the start does not look in `REPOS_DIR`, at any repository, or at any run folder but those `Recover` measures and `Prune` removes, runs no git and no script, and unpacks, removes and rewrites no tree. A test sees "runs no git" by putting `GIT_TRACE2_EVENT`, naming a file in its temporary directory, into `Process.Environ`: git writes its trace2 events there whenever it runs (git's `api-trace2` documentation), so the file is still absent once `READY=1` has arrived.

When `Recover` or `Prune` returns an error, the catalog failed under them: scripts cannot serve a catalog it cannot write, and serving over runs it could not settle would show runs as `running` that nothing will ever end. So the start is refused, as a catalog that will not open is: `scripts: ` and `store.Unreachable`, exit 1, before readiness and before `service.started`. The line quotes no underlying error, as every consumer of a catalog error answers it (`D04-store`). A test makes `Recover` fail by making its own database fail once `Run` has opened it (Consumer tasks); a failure of `Prune` alone cannot be isolated that way, since anything that makes the catalog fail before `Prune` makes `Recover`, which runs first, fail too, so the refusal for `Prune` is proved only as part of the same requirement.

A signal that arrives before `Run` has begun to report ready is a stop, not a failure: exit 0 (`D02-cli` keeps 1 for a server that failed), with no `READY=1`, no connection accepted, and neither `service.started` nor `service.stopping`. The refusals before the catalog still come first, whatever the context holds. Events already recorded by then — the `run.finished` of the runs `Recover` marked — are not lost: `Run` waits, at most the drain deadline, until the writer has delivered them or written them to standard error, and only then returns. The same holds for a start refused because `Recover` or `Prune` failed.

Then `Run` calls `Process.MCP` once with the writer and builds the handler with `web.Handler` over `Process.Banner`, that server, the `IKIGENBA_SERVICES` value, the store, the source, the run core, the limits and the writer. Nothing about `IKIGENBA_SERVICES` or the file it names can stop a start: unset, empty, or naming a file that is missing, unreadable or malformed, scripts starts, serves and says nothing about it; its pages lose the launcher, its endpoint the instructions, its scripts the services they would find, and its events, with no `telemetry` entry to find, go to standard error, all as the owning designs state.

The socket has been listening since systemd made it, so ready is true before the first `Accept`, and sending it first means a failure to send is reported before anything was served: one line beginning `scripts: ` that names the notification socket's address, exit 1. Once `READY=1` is sent, and before any connection is accepted, `Run` calls `Writer.Ready`, so `service.started`, carrying `Process.Version`, is the first event of a run after the `run.finished` of every run `Recover` marked.

## The control group

On a host the service unit delegates its control group to scripts (the manifest's `delegate`, `D02-cli`), and `main` hands its directory to `Run` as `Process.Cgroup` (`D01-layout-and-run-seam`). Once the runs directory is made, and before the runs are settled, `Run` takes the **cgroup step**: it checks that the group is scripts' alone, its `cgroup.procs` naming `Process.Pid` and nothing else; moves its own process into a child group `main/`, by writing its pid to `main/cgroup.procs`; enables the `cpu`, `memory` and `pids` controllers for the group's children, by writing `+cpu +memory +pids` to `cgroup.subtree_control`; makes the child group `runs/`, writes `RUNS_MEMORY_MAX_BYTES` to its `memory.max` and `RUNS_CPU_PERCENT` percent of one CPU to its `cpu.max`, as a quota of `RUNS_CPU_PERCENT` × 1000 microseconds in a period of 100000, so that every run together is held to both; and enables `memory` and `pids` under `runs/`, by writing `+memory +pids` to `runs/cgroup.subtree_control`. Each run's own group is then made under `runs/` by the runner (`D06-runner`). The kernel's control group v2 documentation (`Documentation/admin-guide/cgroup-v2.rst`) proves the file semantics relied on: a process is moved by writing its pid to the target group's `cgroup.procs`; `cgroup.subtree_control` takes several space-separated `+controller` tokens in one write; `memory.max` takes a number of bytes; `cpu.max` takes `$MAX $PERIOD` in microseconds, `max` meaning no limit; and a group with controllers enabled for its children may hold no process of its own ("no internal process" rule), which is why scripts moves itself into `main/` before it enables them, an order a temporary directory standing in for the tree cannot show and a space does (`D13-on-a-space`). A `RUNS_CPU_PERCENT` whose quota the kernel refuses makes the write fail like any other.

The check that the group is scripts' alone is what keeps a scripts started at a developer's terminal, or by the one test that execs the binary, from arranging a group that holds other processes: there the group holds the shell or the test as well, so the step fails before it writes anything. When `Process.Cgroup` is empty, or the check or any creation or write fails, scripts does not refuse to start and has no other way to run a script: it writes one line, `scripts: runs are unavailable: ` and the reason, to standard error before it reports ready, hands the run core an empty `Cgroup` and that reason as `Unavailable`, and serves as on any start, every `run` refused with `runs.NoRuns` filled with the same reason. The reason for an empty `Process.Cgroup` is exactly `no control group was found`; for anything else it says what failed. A step that failed part way is not undone, and nothing more is written under `Process.Cgroup` by that process. A start refused earlier, for its settings, its socket, git, the interpreter, the catalog or the runs directory, touches no control group.

## The trail of a run

Every event of the process goes through the run's writer: the request middleware's, the tools', the run core's and the run's own. appkit's writer queues and returns, so neither readiness nor any answer nor any run waits on telemetry; an event it cannot deliver goes to standard error as `scripts: undelivered event: ` and the event's JSON (appkit's writer design), in the order recorded, and scripts keeps serving. Apart from `service.started`, `service.stopping` and the `run.*` events, every event is recorded while the handler answers a request and carries that request's id; a run's events carry the run's own user and request id, whenever they are recorded (`D10-trail`). That a telemetry installed or restarted after scripts started is found without a restart, and that an event already written out is not sent again, is appkit's socket sink, which `main` gets by leaving `Process.Sink` nil (`D01-layout-and-run-seam`).

This design assumes a clock that reads times in the UTC years 0 through 9999, the years an RFC 3339 time can spell; appkit's writer cannot encode an event stamped outside them, and what scripts records under such a clock is not contract.

## Stopping

When `ctx` is done — in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the context's cause — `Run` at once calls the run core's `Drain`, which at once finishes every queued run `failed` with reason `queue_abandoned`, starting none of them and recording each one's `run.finished`, so a `run` call whose run core call begins from then on is refused with `runs.ErrDraining`, which `D11-tools` answers with its drain refusal, `runs.Stopping`, after looking the script up, and a delivery whose `Deliver` begins from then on is answered `events.Fail(runs.Stopping)` with no run made (`D14-delivery`), so the events app delivers it again to the next scripts; every other tool and page answers as ever. Requests in progress carry on, a `create` reading its repository and a `run` resolving and unpacking among them, and so do the runs already running: scripts signals none of them. It drains the server through `Serve`. Once every request has finished and `Drain` has returned — every run having ended — `Run` calls `Writer.Shutdown` with the reason, the text of `context.Cause(ctx)`, inside the same drain window, which records `service.stopping` as the last event and delivers what is queued, and returns 0 without waiting out the rest of the window.

The **drain deadline** is `DRAIN_SECONDS`, as `settings.Read` returns it, in seconds, the longest `time.Duration` when that many seconds is longer, and it runs on real time: `Process.After` is never used for it (`D01-layout-and-run-seam`), so a drain test runs with `DRAIN_SECONDS=1` and waits about a second. At the deadline `Run` calls `Limits.Halt` at once, while `Drain` is still running and not after it returns: `Drain` returns only once every `Run` call in progress has returned, and a call still in its git returns only when its git ends, which `Halt` makes happen (`D07-runs`, `D12-limits`). `Drain` kills every run still running, its process group whole, records each `killed` and records each `run.finished`; a `run` call cut off records no run and leaves no folder (`D07-runs`). Only after `Drain` has returned does `Run` call `Shutdown`, so every killed run's `run.finished` precedes `service.stopping`; the window being spent, both go to standard error as `undelivered event` lines and never to the sink: from the drain deadline on, `Run` hands its sink nothing (R-HZS1-B4XT), so telemetry receives neither. What the sink would do with an event handed to it late is beside the point, since none is. A run killed at the deadline is the stop working as designed, not a request: it is never counted and never makes the stop exit non-zero.

A request still in progress at the deadline is cut off: `Serve` cuts the remaining requests off only after its `stop` has returned, ends their contexts and closes their connections without the rest of their answers, and `Run` says `scripts: stopped with <n> requests unfinished` (`1 request` for one), exit 1, as its last line, less than a second after the deadline, with every git and every script it started gone. A cut-off request's `request.finished`, recorded after the deadline, is written out or not at all, never delivered; so telemetry's trail shows the cut-off request by its `request.started` alone. A request cut off while it waits on a git run records nothing else from the deadline on: no `tool.called`, no `script.*` and no `run.*` event. A test holds a request open without sleeping in one of two ways: it posts to `/mcp` with a body it never finishes, which keeps the handler reading; or, to hold a git run past the deadline, it puts `GIT_TRACE` naming a FIFO in its temporary directory into `Process.Environ` and never opens the FIFO for reading. git(1) documents that `GIT_TRACE` set to an absolute path makes git write its trace to that file. Opening a FIFO for writing blocks until a reader opens it (fifo(7)), so every git `Run` starts blocks at its first trace line until the drain deadline kills it. A test makes its scripts before it adds `GIT_TRACE` to what `Process.Environ` returns, so `create`'s owner read is not held. A run is held past the deadline by a `main.py` that waits for a file the test never creates. A test sees "every git it started gone" by putting a variable with a value unique to the test in `Process.Environ`, which every git `Run` starts receives, and, once `Run` has returned, scanning `/proc/*/environ` on Linux, without starting a process, finding no process whose environment holds that variable; it sees "every script gone" the same way through the run's own `IKIGENBA_RUN_ID`, unique to the run, which every process of the run inherits.

## Serving and stopping the listener

`Serve` owns `ln` from the call. It serves plain HTTP/1.1 with `h` and blocks. When `ctx` is done, `Serve` closes the listener so nothing new is accepted — new connections wait in the socket's queue for the next scripts — drops connections that carry no request, and lets every request already being handled finish and receive its whole response, for at most `drain`. If they all finish, it calls `stop` and returns nil as soon as `stop` has. If some are still being handled when `drain` runs out, it calls `stop`, then ends those requests' contexts, closes their connections without the rest of their responses, and returns a `*DrainError` counting them, without waiting for the handlers themselves to return. The count is of calls to `h.ServeHTTP` that had begun and had neither returned nor ended their goroutine without returning. `stop` is called once, when the drain is over, with a context that ends at the deadline; `Run`'s `stop` waits for the run core's `Drain` and then shuts the writer down. An `Accept` error that reports itself temporary is retried, as `net/http`'s `Server.Serve` retries it; any other ends serving, and that is trouble: `scripts: ` and the error as `Run`'s last line, exit 1. `Serve` gives its server an `ErrorLog` that goes nowhere, since Go's `net/http` documents that a nil one writes to the real standard error. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` because gosec `G112` demands it.

## The handler's routes

`web.Handler` is appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping a router that sorts every request by its path alone, whatever its host: the two **events paths**, exactly `/events` and exactly `/declarations`, go straight to appkit's events handlers, and every other path goes through `identity.Require` to the routes below. Every request records its two events, whatever route answers it, a delivery included, whose `request.started` and `request.finished` carry its request id and an empty user; and every request to any other path without an `X-User-Id` is answered by the gate before any route sees it.

Routing is on the request's `URL.Path` as `net/http` decodes it, compared exactly, by hand — no `http.ServeMux`, which would clean `..` with a redirect — and the router itself never redirects:

- exactly `/events`: `events.DeliveryHandler(h)`, `h` being `events.Handlers{"*": Config.Runs.Deliver}`, built once, when the handler is built: one handler for every event name, so every delivery reaches `Deliver` (`D14-delivery`), which reads the delivery's request id from the context `telemetry.Middleware` filled. appkit's handler refuses what is not a delivery (a method other than `POST`, a body that is not one) and writes `Deliver`'s outcome.
- exactly `/declarations`: `events.DeclarationsHandler(nil, h)`, over the same `h`, which answers `{"emits":[],"accepts":["*"]}`: scripts emits nothing on the bus and accepts every name.
- exactly `/mcp`: `Config.MCP`, with the eleven tools registered on it by `tools.Register` once, when the handler is built.
- exactly `/` and `/about`: `pages.Handler` (`D08-pages`, which owns their pages and their 405).
- an **appkit path**, beginning `/_appkit/`: appkit's `page.Static()`, unchanged.
- every other path is a **script path**, whose first segment is a script's name: a **run file path**, as `D09-run-files` defines it, is answered by `web.Files`, which `D09-run-files` declares in `internal/web`; every other script path — `/<name>/`, `/<name>`, `/<name>/runs/<run id>/`, `/nope`, `/about/`, `/mcp/tools`, `/events/`, `/declarations/repo.pushed`, `/_appkit` — is answered by `pages.Handler`, which owns the script page, the run page, their redirects, the not-found page, and the catalog refusal on them (`D08-pages`).

`web.Handler` loads the template set once with `pages.Load` and hands it to the pages handler with `Config.Banner`, `Config.ServicesPath`, `Config.Store`, `Config.Source`, `Config.Runs` and the four numbers the pages quote from `Config.Limits.Settings()` (`D08-pages`), and to the run files' handler, `web.Files`, with `Config.Banner`, `Config.Store` and `Config.Runs` (`D09-run-files`). It registers the tools with `Config.Store`, `Config.Source`, `Config.Runs` and `Config.Telemetry`, and builds the two events handlers over `Config.Runs`; `web.Config` gains no field for them, since `Deliver` is a method of the run core it already has. scripts calls no sibling while serving a request: no route connects to a socket the services file names, the telemetry entry's deliveries excepted. A script it runs reaches siblings on its own, and that is not a request scripts serves.

The middleware records `request_bytes` as the bytes of the request body the handler read and `response_bytes` as the bytes of body it wrote (appkit's HTTP middleware design), both after any chunked coding is removed and with no header counted.

## Decisions

- The settings refusal at `Run` (its line, its exit 2, touching nothing) is this design's alone, because it is the first step of the start's order; `D12-limits` keeps the `settings.Error` text. The rule that no socket, `PATH`, `NOTIFY_SOCKET` or `IKIGENBA_SERVICES` lookup comes before the settings is also this design's; `D01-layout-and-run-seam` keeps the whitelist of keys `Run` may look up.
- The interpreter's refusal is built from `runner.Interpreter`, so the design, the code and the tests never spell the version but in its one declaration.
- `Run` makes `state/runs` itself, after the catalog and before `Recover`, so its refusal has its own line and comes before any run is marked; `Recover` also makes it when absent (`D07-runs`), which then changes nothing.
- A failed `Recover` or `Prune` refuses the start with `scripts: ` and `store.Unreachable`, exit 1, as sites refuses a catalog that will not open: the catalog failing after it opened is the same trouble, and starting over unsettled runs would leave records `running` that nothing ends. The line quotes no underlying error, as `D04-store` asks of every consumer of a catalog error once the catalog has opened.
- `Recover` and `Prune` run to completion once begun even when `ctx` ends during them, and a stop that arrives then is honoured right after, before readiness. Interrupting them would leave a half-settled catalog for the next start to settle again for no gain, since both are short catalog and folder work.
- The events recorded before readiness, the recovered runs' `run.finished`, are flushed (delivered or written out, within the drain deadline) before a start that stops or is refused returns, with no `service.started` or `service.stopping`, so every run keeps its one `run.finished` (`D10-trail`) and a start that never served shows no start or stop.
- The drain state is the run core's (`runs.ErrDraining`, `D07-runs`): the limits have no draining state, so a `create` or an `update` during the drain proceeds, and only `run` is refused. `Run` calls `Drain` at the signal so the refusal begins then, and `Halt` at the deadline concurrently with `Drain`, because `Drain` waits for the `run` calls whose git only `Halt` ends.
- From the drain deadline on, `Run` begins no `Deliver` on its sink, whatever appkit's writer would still try: telemetry is to receive none of the events recorded once the window is spent (a killed run's `run.finished`, `service.stopping`, a cut-off request's `request.finished`), and appkit's writer can hand the sink an event recorded after the deadline before `Shutdown` is called. Since `Process.Sink` is the writer's sink, `Run` keeps that promise by what it hands the writer as its sink; each such event then reaches standard error as an `undelivered event` line, in the order recorded, through the writer's `Shutdown`.
- Killed runs never make the stop exit non-zero; only requests cut off do, through `*server.DrainError`; nor do queued runs abandoned at the signal, which are finished at once rather than at the deadline, since a script started during a drain would only be killed at its end.
- The cgroup step is never a refusal: without it scripts serves every page and every tool but `run`. Its first check, that `cgroup.procs` names scripts' process alone, is this design's addition to the steps; it is what makes "a group nothing delegated to it" detectable without guessing, and it keeps the exec'ing test, whose binary shares the test's control group, from writing into the developer's real control group tree.
- The reason travels to the run core as `runs.Config.Unavailable`, so the refusal quotes exactly the reason the start printed; only the empty-`Cgroup` reason is fixed text, since the others quote the operating system's error.
- A cgroup step that fails part way leaves what it wrote: undoing it could fail the same way, and systemd removes the service's group when the service stops.
- The stop line is always `Run`'s last write, which places it after every `undelivered event` line, `service.stopping`'s included.
- A request cut off while it waits on git records nothing from the drain deadline on, as in sites: `Serve` ends the context of a cut-off request after `stop` has returned, `Run` has called `Limits.Halt`, and the run core has made the `run` call a cut-off call, so such a handler meets an error matching its ended context or `limits.ErrHalted`, a cut-off call's error matching `limits.ErrHalted` when the drain deadline cut it off (`D07-runs`); the tool's handler then answers nothing and records nothing (`D11-tools`). A `request.finished` recorded for it after the deadline is written out or dropped. What remains a race is only a request whose last write returned just before the deadline and whose events are recorded just after it; no test can fix which side of the deadline those fall on, so no requirement speaks of them, and no requirement states the status a cut-off request's `request.finished` carries.
- There is no apex host and no guest: every request goes to the same routes whatever its `Host`, and every route but the two events paths is behind `identity.Require`, `/_appkit/` included.
- The events paths are outside `identity.Require` and inside `telemetry.Middleware`: a delivery has no user to require, and the middleware is what gives `Deliver` the delivery's request id and records the request's pair. They are matched exactly, as `/mcp` is, so a path beneath either is a script path, answered with the not-found page, and is still behind the gate.
- Which methods and bodies the events paths accept, and the status and body of each outcome, are appkit's events contract; scripts' requirements state the routing by equivalence with the handlers appkit returns, and give the answers a test sees only as examples of it.
- Deliveries need no drain logic of their own here: `Run` calls `Drain` at the signal, and `Deliver` refuses from then on (`D14-delivery`); a delivery whose runs are being made when the signal arrives is a request in progress like any other, and the runs it made are waited for and killed at the deadline like every run.
- The handler has no random source of its own: scripts mints no visitor ids, and the request ids are the middleware's, drawn from the writer's.
- appkit's warning over a catalog ahead of the binary goes straight to `Process.Stderr` as `db.Open` writes it, rather than being held back until the start is sure to serve: holding it would cost a buffer for no reader's gain, and an operator whose rolled-back start then fails for its runs directory or a broken catalog is better told both. So every requirement that bounds what a start writes to standard error once the catalog has opened admits that line (R-H2UQ-ZBX2, R-H42N-D3NR, R-H5AJ-QVEG, R-H6IG-4N55).
- `internal/server` is copied from sites unchanged in behaviour; the debt is recorded in prose, and promoting it to appkit is a separate change.
