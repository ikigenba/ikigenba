# D04-store

The catalog: `internal/store`, which owns scripts' one SQLite database, `state/scripts.db`, and everything it records — every script's id, name, owner, repository, ref and created time, every subscription of a script to an event pattern, every run's id, script, sha, ref, user, request id, trigger, event, status, exit code, times, output sizes, truncation and failure reason, and the memory of which event each script has had a run from — together with the rules a script's name and an event pattern obey, the words a run's status, failure reason and trigger are spelled with, and the one line every consumer answers when the catalog cannot be reached. `D01-layout-and-run-seam` declares `cli.Process`, whose `Dir`, `Now` and `Rand` reach the catalog through `cli.Run`, resolves the path the catalog lives at, declares the root package's `Migrations`, the schema's migrations, and declares the entity ids this package exports (`ScriptPrefix`, `RunPrefix`, `NewScriptID`, `NewRunID`, `ValidScriptID`, `ValidRunID`); `D03-serve` opens the catalog with appkit's `db.Open` at start, builds the store over that handle, writes the diagnostic for a catalog that will not open, and closes the handle after the drain. Opening, migrating, the journal mode, transactions and the failure seam are appkit's `db` (its D15 and D16), which this document restates none of. This document declares every other exported name of `internal/store` and states what each does. What a tool checks before it calls the store and what it answers is `D11-tools`'; what the pages show of a record is `D08-pages`'; when a run is recorded, ended, recovered and pruned, and its folder, are `D07-runs`'; which subscriptions a delivered event starts runs for is `D14-delivery`'s; the repositories under `REPOS_DIR` are `D05-git-and-source`'s. The store holds no file but the database, runs no git and starts no process. This revision is the third and last of three stages that move the catalog's scripts and runs out of one stored value into tables of their own (Moving the catalog into tables): every read is answered from the tables, every write goes to them alone, and the table `catalog` is left as it is.

## One catalog, one writer

scripts is the catalog's only writer, and no sibling reads it. Metadata is in the catalog and bytes are on disk: a run's output, input, tree and files are under its folder (`D07-runs`), and the catalog keeps only what lists and pages are drawn from, so a list or a page is a few queries of the catalog, each filtered, ordered and windowed by the database. A run's record survives its folder going missing. What is contract is what a reader and a restart see: what a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds, field for field; and what the tables `scripts` and `runs` hold, which mirror what a store holds and are where it reads it from. The table `catalog`, which once held the whole catalog in one stored value, is neither read nor written by a store and keeps whatever rows it held. A test proves the content by closing the handle and opening another, proves the mirror by reading those two tables through `DB.Read`, and proves that `catalog` is left alone by reading its rows through `DB.Read` before and after.

The schema is contract too, because a migration is applied to a catalog that already exists and the migrations must agree with what earlier releases left on disk. It is three migrations, and this revision adds none. `0001_catalog.sql` is the schema scripts has always created: a table `catalog` with the columns `id`, an integer primary key that only the value 1 may take, and `value`, a blob, not null, which held the whole catalog's scripts and runs in one row, as `encoding/gob` wrote one value of them, until the tables took them: the **stored value**, which this stage neither reads nor writes. Written with `CREATE TABLE IF NOT EXISTS` and seeding nothing, it creates the table on a fresh catalog and changes nothing on a catalog an earlier scripts kept, which `db.Open` then records as having had `0001`. `0002_subscriptions.sql` adds two tables: `subscriptions`, one row per subscription, with the columns `script` and `event`, text, together the primary key, so a script never holds one pattern twice, and `created`, an integer; and `event_runs`, one row per script and event id a run was made for, with the columns `script` and `event`, text, together the primary key. `event_runs` is the delivered-event memory: a row is written in the same write as the event run it records, is kept when that run is pruned, and goes only with its script, so the same event delivered again starts no second run of a script even after its run is gone. `0002` applies after `0001` on a fresh catalog and on one that has had `0001` alone, and changes nothing in `catalog`. `0003_tables.sql` adds the tables `scripts` and `runs`, the first stage below, and applies after `0002` on a fresh catalog and on one that has had `0001` and `0002`. Their tests are of the shape every service has: open a fresh catalog with `scripts.Migrations()` and inspect `sqlite_master` and `PRAGMA table_info`; and, for a catalog an earlier scripts kept, one with a row in `catalog` and no `schema_migrations`, one that has had `0001` alone and one that has had `0001` and `0002`, open it with `scripts.Migrations()` and see every table present, `scripts` and `runs` empty, and the row of `catalog` as it was. The rows of `scripts` and `runs` are contract, each column the encoding of a field (R-B6OW-3ELR), because a store reads them; the stored value is not, since nothing this release supports reads it; beyond that and what the tests above need, how the records are laid out is not contract: no sibling reads the database, and the host's replication copies it whole. A later change to the schema is a new migration file, never an edit of one already released.

The store does not open anything. `store.New` builds a store over a handle `db.Open` returned, with the clock and random source it stamps and draws from; every read is a `DB.Read` and every write a `DB.Write` on that handle, so the handle's one writer serializes the writes and the store keeps no lock of its own. A write that must check and change together — a create's name check and insert, a run's script check and insert, an event run's insert with its delivered-event row, a subscription's check and insert or removal, an ending's check that the run is still running, a script's removal with its runs — does both inside one `DB.Write`, which is what keeps the catalog's invariants under concurrent calls.

A catalog that fails is a **failing** store: from a `SetFailing(true)` on its handle until a `SetFailing(false)`, and once its handle is closed, every method answers a catalog error and changes nothing. That is the one failure seam: a test that needs a call's reads to succeed and its write to fail turns it on from an injected function the call calls between them — a test's `runs.Config.Now`, or the `After` of the test's `limits.Clock`, called before each git run, as `D11-tools` does before a `run`'s git — and never takes a permission away, which under WAL does not reliably fail a write. `cli.Run` holds its handle itself, so a test of `Run` that needs the catalog to fail after `Run` opened it does so from outside, as `D03-serve`'s consumer tasks describe.

## Moving the catalog into tables

The catalog's scripts and runs lived in one stored value, a gob value in the one row of the table `catalog`, that every call decoded whole and every write encoded whole, so a list cost the whole catalog and could not be filtered, ordered and windowed by the database as the suite's Storage convention asks. They moved into tables of their own over three releases, expand then contract as the root `AGENTS.md` asks of a schema and of a data rewrite, because the release before must run on each release's database, so that a mix of the two, during a rolling restart or after a rollback, works in both directions. The first two stages were the releases before this one; this revision designs the third and last, which leaves the table `catalog` in place for a later delivery to drop.

**Stage 1: the tables were written and never read.** `0003_tables.sql` creates, without `IF NOT EXISTS`, since it runs only on a catalog `0002` made, two tables. `scripts` holds one row per script: `id`, the primary key; `name`, unique, so the database holds the space-wide namespace too; `owner`, `repo`, `ref` and `created`; every column text and not null (R-BBKH-MHKJ). `runs` holds one row per run: `id`, the primary key; `script`, `sha`, `ref`, `user`, `request_id`, `trigger`, `event` and `status`, text and not null; `exit_code`, an integer, not null; `started`, text, not null; `finished`, text, null while the run is queued or running; `stdout_bytes`, `stderr_bytes` and `truncated`, integers, not null; and `reason`, text, not null (R-BCSE-09B8). The indexes `scripts_owner_name` on `scripts(owner, name)` and `runs_script_started_id` on `runs(script, started, id)` serve this stage's windows (R-BE0A-E11X). The migration seeds nothing and touches no other table: an SQL migration cannot decode a gob value, so filling the tables from the stored value is the binary's work. Each column is its field: an empty string as the empty string, never null; a time as the text `time.RFC3339` gives for it in UTC, which for the whole-second UTC times the store keeps (R-9371-GYU4) is the fixed-width form `2006-01-02T15:04:05Z`, so that text order is time order for every year written in four digits; the exit code as the integer the record holds, 0 for every status but `exited`; `truncated` as 1 or 0; and a zero `finished` as null. The tables **mirror** a store's content when they hold exactly one row for each script and each run it answers, and no other row, each column so (R-B6OW-3ELR).

The release before the first stage did not know the tables, and ran on the first stage's database: whatever it created, recorded, ended or deleted during a mixed window was missing from, or wrong in, the tables. So the first stage rebuilt them from the stored value at every start, with a method `SyncTables` that inserted the rows the value had, changed those that differed and deleted those it lacked, before `Recover` or anything else touched the catalog; its reads stayed on the stored value, and the tables were proved only by reading them.

**Stage 2 (release-26), the release before: reads moved to the tables, and this revision keeps every read as it made it.** Every read is a query, or a few, over `scripts`, `runs`, `subscriptions` and `event_runs` that the database filters, orders and windows, and the stored value is no longer decoded to answer one. `Find` is the row of `scripts` with that owner and name, `Taken` a look for the name on its unique index, and `List` the window `WHERE owner = ? AND name > ? ORDER BY name LIMIT ?` over `scripts_owner_name`, whose limit a tool sets one past its page, as appkit's D25 sets out, to learn whether a next page exists. `Runs` is the window `WHERE script = ? AND (started, id) < (?, ?) ORDER BY started DESC, id DESC LIMIT ?` over `runs_script_started_id`, newest first, the keyset being the pair of the run's started text and its id, which is why a time is fixed-width text; `RunCount` counts the script's rows of `runs` over the same index, so a script's page states how many runs it keeps without reading them. A script's `Last` is a correlated subquery over `runs(script, started, id)` taking the first of its runs in run order, and its subscriptions are its rows of `subscriptions`. `FindRun` and `RunByID` read one row of `runs` by its primary key, `FindRun` joined to its script for the owner. `PastKeeping` ranks each script's runs in run order with a window function over `runs_script_started_id` and keeps those ranked at `keepCount` or more that are old enough and ended. `Running` and `Queued` scan `runs` by status: there is no index on `status`, and none is added. `Subscribers` and `Delivered` read their own tables as before. The landing page and a script's page show the first page of each list, with the rest at `p#next` (`D08-pages`, `D11-tools`).

Stage 2 still wrote the stored value beside the rows, in the same `DB.Write`, each write rewriting it from the content the tables held, so that the first stage, run again after a rollback, read it and found every record, and its own start's `SyncTables` rebuilt the tables from it. `SyncTables` went in stage 2, method and call: its only supported predecessor, the first stage, wrote the stored value and the rows alike, so nothing remained for a start to repair.

**Stage 3, this revision: the stored value is neither read nor written.** Every write goes to the rows alone, in one `DB.Write`: `Create` inserts the script's row, `SetRef` updates its `ref`, `AddRun` inserts the run's row, `StartRun` and `FinishRun` update it, `DeleteRun` deletes it, and `Delete` deletes the script's row and every row of `runs` whose `script` is its id; `Subscribe`, `Unsubscribe` and the reads change neither table. A call that answers an error changes neither, a failing store's included (R-X16O-9NPO). So from a fresh catalog, whose empty tables mirror its empty content, the mirror holds after every call (R-EE5D-1U9Q). No call reads, writes or deletes a row of `catalog`: whatever the table held when this release first opened the catalog, the last value a stage-2 write left or no row at all, it holds after every call of a store (R-AC4G-1TTA), and what is written there other than by a store changes no answer (R-WZYR-VVYZ). What this stage removes is the store's side of the stored value: the gob encoding and the private type that carried the stored value go, and scripts reads and writes no gob.

The table `catalog` stays in the schema: this revision adds no migration and no DDL, and the migration set is the three stage 1 carried. The only predecessor this release supports is stage 2 (release-26), and it runs on this release's database: it reads only the tables, which this stage keeps writing, so a stage-2 binary rolled back onto this database starts and serves every record from the tables, its start recording nothing it does not carry; its writes rewrite the stored value from the tables, which is harmless, since this release, started again after it, reads none of it. Stage 1 is not a supported predecessor: it reads only the stored value, which this stage leaves as stage 2 last wrote it. A catalog no stage-1 start opened, one an earlier scripts kept with no recorded migration, with `0001` alone, or with `0001` and `0002`, stays unserved as in stage 2: `db.Open` applies the migrations it lacks and it gains the tables, empty, and its `catalog` row is kept as it was and never read (R-ADCC-FLJZ, R-AEK8-TDAO, R-AFS5-751D).

Dropping `catalog` is the contract step that follows, and it is not this seam: a release that drops the table must follow one in which nothing writes the stored value, because its predecessor, rolled back onto its database, must still run there. Stage 2, this release's predecessor, writes it, so a drop now would break the rollback to stage 2; once this release, which writes nothing there, is the predecessor, a later delivery drops it with a new migration.

## Scripts

A script's **id** is `scr_` and 16 lowercase hexadecimal digits (`D01-layout-and-run-seam`), drawn from the random source when the script is created and never changed. Its **name** is 1 to 64 bytes, each a lowercase ASCII letter, a digit or `-`, the first not `-`, and none of `about`, `tools`, `mcp`, `events` and `declarations`, since `/about`, `/tools`, `/mcp`, `/events` and `/declarations` are scripts' own paths (a script named `tools` is not expected on any space, and nothing migrates); it is taken as given, never trimmed or folded, and never changes, since there is no rename. Names are one namespace for the whole space, because the name is the URL segment: a name is **taken** when any script, of any owner, has it. Its **owner** is the user id of the caller that created it. Its **repository** is a repository id as repos names its directory, kept verbatim, so a script keeps working across a rename in repos; the store never looks at it. Its **ref** is what a run without a ref of its own resolves, `main` unless the creator gave another, and the one field `SetRef` changes. **Created** is the time of the create in UTC to the second, the precision the tools answer it in.

Every read that returns a script returns it with its **last run**: the first of its runs in run order (Reads), or none for a script that has never run. The catalog page, `list`, `show`, `create` and `update` all show it, so it is part of the record a reader gets rather than a second query.

Every read that returns a script returns it with its **subscriptions** too, so `show`, `create`, `update`, `subscribe` and `unsubscribe` answer them and `list` counts them without a second query.

## Subscriptions

A **subscription** is a pair, one script and one event pattern, kept as the exact string given, with **created**, the time of the `Subscribe` that made it, in UTC to the second. An **event pattern** is two or more words joined by single `.`s, each word either a lowercase letter followed by lowercase letters and digits, single `_` allowed between them, or exactly `*`; a pattern with no `*` is an event name. `ValidEvent` is the rule, exported because the tools check it, after finding the script, before they call the store, and the store refuses a pattern it fails as it refuses an invalid script name. It is the pattern rule of appkit's `events` package, which exports `Match` but no validator of its own, so the store states it as a regular expression. A pattern **matches** an event name of as many words, word for word, each `*` standing for exactly one word: `cron.*.fired` matches `cron.hourly.fired` and not `cron.fired` or `cron.a.b.fired`, and `repo.pushed` matches only itself. That is appkit's `events.Match`, which the store may use. `Subscribers` answers by matching; everything else compares patterns as strings: `Subscribe` is idempotent for the exact string, so subscribing a script to a pattern it already holds changes nothing and keeps the time it was made, and a retried call answers what the first did, while another string, even one matching the same names, is another subscription. `Unsubscribe` removes only the subscription whose pattern is the string given, never one that matches it or that it matches, and a pair the store does not hold is refused with `ErrNotSubscribed`, so a caller that mistyped learns nothing was removed. A script's subscriptions are listed in ascending byte order of the pattern. `SetRef` keeps them, and `Delete` removes them with the script. Subscriptions say nothing about runs: making one runs nothing, and removing one touches no run.

## Runs

A run's **id** is `run_` and 16 lowercase hexadecimal digits, minted by the run core with `NewRunID` before the run is recorded, because its folder is named by it (`D07-runs`). Its **script** is its script's id, the one reference from a run to its script. Its **sha** is the 40-hexadecimal-digit commit the run resolved, empty only for a run that failed before its ref resolved. Its **ref** is the ref it was resolved from. Its **user** and **request id** are those it acts as and was caused by. Its **trigger** is `manual` for a run the `run` tool asked for and `event` for one a delivered event started (`D14-delivery`), and its **event** is, for an event run, the id of the event it was made for, and empty otherwise. Its **started** and **finished** times are the run core's, kept in UTC to the second; started is the moment the run was asked for, whether its process started then or later, and finished is zero while the run is queued or running. **Stdout bytes** and **stderr bytes** are how many bytes of each stream the run kept, recorded when the run is recorded failed or ends; while a run is queued or running the record holds zero and its files, if any, are the measure (`D07-runs`). **Truncated** says either stream was cut at `OUTPUT_MAX_BYTES`. Its **status** is one of six words, and its **exit code** and **reason** apply only to one of them each:

- `queued` while the run waits for a slot to run in, its tree unpacked and no process of it started (`D07-runs`);
- `running` while the process lives;
- `exited` when the process ended on its own, with its exit code, from 0 to 255, 128 plus the signal's number for a signal scripts did not send;
- `killed` when scripts killed it, or took it out of the queue before it started: on `cancel`, on its script's `delete`, at the drain deadline, or at the next start for a run still recorded `running`;
- `timed_out` when scripts killed it at `SCRIPT_SECONDS`;
- `failed` when the script never started, with one of seven reasons: `repository_missing`, `commit_missing`, `too_large`, `git_failed`, `timed_out` (git outlasted `OPERATION_SECONDS`), `start_failed` and `queue_abandoned` (the run was still waiting for a slot when scripts stopped, or when the next start found it recorded `queued`).

The status and reason words are exported constants of this package, beside the record whose field they fill, because the store refuses a record that does not use them and every consumer — the run core that writes them, the tools, pages and trail that show them — already imports the store; a reason's sentence on the run page is `D08-pages`'.

A run has three transitions in the catalog. `AddRun` records it once: `running`, after its process has started; `queued`, when every slot is taken and it must wait; or `failed`, when it could not start; `D07-runs` decides which and when, and a run cut off before any is never recorded. `StartRun` moves a `queued` run to `running` once its process has started, keeping its `started`. `FinishRun` ends a run exactly once: a `running` run as `exited`, `killed` or `timed_out`, and a `queued` run as `killed` (cancelled or deleted before it started) or `failed` with `start_failed` or `queue_abandoned`, with no output, since it never ran. Of two calls racing to end the same run, one succeeds and the other is told the run has already ended (`ErrEnded`), which is how `cancel` racing a run's own exit is refused; `StartRun` of a run no longer queued is told the same. Nothing moves a run back to `queued` or `running`, and nothing makes a running run `failed`.

## Reads

`Find` is a caller's own script by name, so another owner's script is indistinguishable from none; `List` is a window of one owner's scripts, in ascending byte order of name, those after a name the caller gives and at most as many as it asks for; `Taken` is the space-wide name check. `FindRun` is a run of one of a caller's own scripts, so another owner's run is indistinguishable from none; `RunByID` is any run, for the run core. `Subscribers` is every script, of every owner, holding a subscription that matches one event name, each once, for the delivery (`D14-delivery`); `Delivered` says whether a script has had a run from one event id. `Runs` is a window of one script's runs in **run order**, newest first: in descending order of started, and among runs started in the same second in descending byte order of id; it answers those after a position the caller gives as a run's **started text**, its started time as `time.RFC3339` writes it in UTC, the fixed-width text the `started` column holds, and its id, and at most as many as the caller asks for. `RunCount` is how many runs one script has, whatever their status. `Running` is every run still recorded `running`, of every owner, which a start marks `killed`, and `Queued` every run still recorded `queued`, which a start marks `failed` with `queue_abandoned` (`D07-runs`). `PastKeeping` is every run past keeping at a moment, over the whole catalog: a run that is neither `running` nor `queued`, that started more than `RUN_KEEP_DAYS` days of 24 hours before that moment, and that is not among its script's first `RUN_KEEP_COUNT` runs in run order; every run counts toward that rank, a running or queued one included. The store reads neither setting; `D07-runs` hands in the values `D12-limits` read. A window asked for fewer than one is empty, and the store checks no page or limit of its own: what a tool refuses before it reads is `D11-tools`'. All lists are never nil.

## Writes

`Create` mints a script's id and stamps its created time. `SetRef` changes a script's ref and says whether it changed, so a same-ref `update` records no event (`D10-trail`). `Delete` removes a script and every run record of it, whatever their status, in one step; the run core kills its running runs and removes its folders before that call (`D07-runs`). `Subscribe` and `Unsubscribe` add and remove a subscription and answer the script as it is after the call. `AddRun`, `StartRun` and `FinishRun` are the three transitions above; `AddRun` of an event run also records its script and event id, in the same write, and refuses a second run of one script for one event id with `ErrDelivered`, which is what makes a redelivered event start nothing. `DeleteRun` removes one run record, which is what pruning removes once the run core has removed the folder (`D07-runs`); it leaves the delivered-event memory, so `Delivered` still answers true for a pruned event run. At every moment every run the store holds names a script the store holds, so a run recorded while its script is being deleted is either refused or removed with it.

## Errors

`ErrNotFound`, `ErrNameTaken`, `ErrEnded`, `ErrNotSubscribed` and `ErrDelivered` are answers about the catalog's content. Every other error from a method is answered as the catalog being unreachable: every consumer answers it with `Unreachable`, or, for a page, with the unavailable page (`D08-pages`), never quoting the underlying error. A failing store, a random source that fails and a context already done all end there. So does a write given a value no consumer sends — a name `ValidName` refuses, an event pattern `ValidEvent` refuses, an empty owner, repository or ref, a run that breaks the record's rules — which changes nothing. When one call meets several of these conditions, one fixed precedence decides its answer: a done context, then a failing store, then an invalid argument, then a missing record, then a taken name, an ended run, a missing subscription or an event already delivered.

## Decisions

- Ids are 8 bytes of `Rand`; a drawn script id already catalogued is drawn again, up to eight candidates in all, after which `Create` gives up with a catalog error, so a `Rand` that repeats itself cannot hold a call for ever. A run id already catalogued is a catalog error from `AddRun`; with 64 random bits the run core does not plan for it.
- Run times are given by the run core, not stamped by the store, because started is the moment of the `run` call and finished the moment the run core saw the end; the store keeps them to the second.
- Run order breaks a tie of started by descending id, so a script's whole list of runs is the exact reverse of ascending (started, id); ties go by id, and the direction is this design's choice.
- Pruning is split: the store answers which runs are past keeping and deletes a record; the run core removes the folder first, so a failure between the two leaves a record whose files are gone, a state the pages and tools already show, never a folder no record names.
- A queued run is a record before its process exists, because `run` answers it at once and `runs` and `result` show it; `StartRun` is its own transition, not a second `AddRun`, so its `started` stays the moment it was asked for. The queue's order is the run core's, held in memory; the store keeps only the status, and `Queued` exists for the start that finishes what a dead scripts left waiting.
- `Delete` removes running runs' records too: the store does not wait for a process, and `D07-runs` ends every running run before calling it.
- The store has no `Open` and no `Close`: the handle is appkit's, opened and closed by `cli.Run`, and a store over it lives as long as it does.
- The baseline migration is the table every earlier scripts made, `CREATE TABLE IF NOT EXISTS`, so an earlier catalog opens with nothing changed. The stored value in its one row is no longer contract: nothing this release supports reads it, and a store leaves the row as it found it (R-AC4G-1TTA), so a test writes whatever bytes it likes there.
- The delivered-event memory is a table of its own, not the run record: runs lived in the gob blob when it was made, which has no unique index, and a run is pruned while the memory must outlive it; recording both in one write keeps the pair and the run together, so no memory exists without the run it names until pruning removes the run.
- Subscriptions are rows of `subscriptions`, kept out of the blob when it held the catalog so the pair's uniqueness is the table's primary key; the store reads them with the script.
- The tables `subscriptions` and `event_runs` and their columns are a recorded decision, stated as requirements because a migration, once released, binds every later one. A test proves their shape only, through `DB.Read` of `sqlite_master` and `PRAGMA table_info`, and never reads their rows beyond R-BGG3-5KJB's emptiness on a fresh catalog: that subscriptions and the delivered-event memory live there is proved, as far as tests reach, by behaviour — `Subscriptions` and `Delivered` answering the same across a closed and reopened handle, `Delivered` surviving `DeleteRun` and ending with `Delete`, and a catalog that has had `0001` alone gaining both tables empty. The rows of `scripts` and `runs` are another matter: a store reads them, so a test reads them, through `DB.Read`, and compares them with what the store answers (R-B6OW-3ELR); and the rows of `catalog` a test reads only to see them unchanged (R-AC4G-1TTA).
- The tables' columns are the record's fields one for one, so a read takes a record from one row with no decoding: `Script`'s `Subscriptions` and `Last` have no column, the first being rows of `subscriptions` and the second derived from `runs`. Every column is its field's name in lower case with `_` between words, `user` and `trigger` included, SQLite accepting both as column names.
- Nullability follows the Go types: every string field and every number is never absent, so its column is not null and an empty string is stored as the empty string; `ExitCode` is an `int` that is 0 for every status but `exited` (R-9371-GYU4), so `exit_code` is not null and holds that 0 rather than null; `Finished` alone has a value meaning none, the zero `time.Time`, so `finished` alone is nullable and null is that zero. `truncated` is 1 or 0, SQLite having no boolean.
- Times in `scripts` and `runs` are text, `time.RFC3339` in UTC, the fixed-width `2006-01-02T15:04:05Z` for the whole-second UTC times the store keeps: text in that form sorts as time does, which the keyset of `Runs` on `(started, id)` needs, and reads in `sqlite3` as it does in the tools. `subscriptions.created` stays the integer `0002` released, Unix seconds, since a released migration is never edited and nothing reads it in order.
- No foreign key ties `runs.script` to `scripts.id`: the store already keeps every run's script held (R-M41F-EUWR) and removes a script's runs with it.
- `0003` creates its tables without `IF NOT EXISTS`, as `0002` did, since it runs only on a catalog `0002` made, and it copies nothing: a migration is SQL and the stored value is gob, which only the binary decodes.
- `SyncTables` went in the second stage rather than this one: its rebuild repaired what a release that ignored the tables wrote, and the second stage followed only the first, which writes them; keeping it would have rebuilt the rows from a stored value this stage stops writing. A catalog no first-stage start opened is left unserved rather than adopted, because adopting it would need that rebuild or a decoding of the stored value, and this stage keeps neither.
- The stored value stops being written in this stage, not with the reads in the second, so that each release's predecessor runs on its database: the first stage reads only the stored value, which the second kept recording, and the second reads only the rows, which this stage keeps writing. The table `catalog` is not dropped here, because the second stage, this release's predecessor, writes it.
- `List` and `Runs` take the window's bound and size and answer at most `n`, and a caller asks for one past its page to learn whether there is a next one, as appkit's D25 sets out; `RunCount` is its own method so a page can say how many runs a script keeps while showing only its first page. A window of fewer than one is empty rather than an error: the tools refuse a bad limit before they read (`D11-tools`), and the store has no limit of its own to enforce.
- `Running` and `Queued` scan `runs` with no index on `status`: they run once per start, and an index every write maintains would cost more than the scan it saves.
- What `0003` does, and that the previous release starts over a catalog that records it, rest on appkit's published `db` at the release `AGENTS.md` pins: its documentation says only that `Open` applies migrations before admitting readers, so the behaviour over a catalog ahead of the binary was observed by a probe against that published module: a database `Open` made with migrations `0001` and `0002`, opened again with `0001` alone and a `Stderr` buffer, opened with a nil error, wrote the one line `probe: unknown migration version 0002: database is ahead of this binary` to it, and then took a write; `db.Status` listed `0002` as unknown. `D01-layout-and-run-seam` and `D03-serve` already state this as appkit's contract.
- `0002` runs only on a catalog `0001` made, fresh or adopted, so it creates its two tables without `IF NOT EXISTS` and touches nothing else.
- Matching is done when an event is delivered, over the patterns as stored: a pattern is kept as given, so `show` and `unsubscribe` see exactly what `subscribe` took, and no schema change is needed, the table's primary key still holding one pattern once per script.
- `Delivered` answers false, not `ErrNotFound`, for a script id the store does not hold: the run core asks it before anything else and a missing script is found by `AddRun`.
- Times are kept to the second in UTC, so every record the store returns has the shape R-9371-GYU4 states and the text a row holds for a time reads back as exactly that time.

## Consumer tasks

`cli.Run` opens the catalog with `d, err := db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "scripts.db"), Migrations: scripts.Migrations(), Now: p.Now})`; on any error while `ctx` is not done it writes `D03-serve`'s diagnostic with the error's text as the reason; otherwise it builds `st := store.New(d, store.Config{Now: p.Now, Rand: rand})`, hands it to the run core and the handler, and calls `d.Close()` after the drain. After making `state/runs` and the cgroup step, the run core's `Recover` is the first call on `st` (`D03-serve`). No consumer reads the tables or the table `catalog`: they call the store's methods.

The tools (`D11-tools`), `u` being the `identity.Caller` of the call: `list` is `s.List(ctx, u.UserID, after, n+1)`, `after` empty for the first page and the name the page token carries otherwise, `n` the limit, each `Script`'s `Last` giving `last_run`, where before this revision it was `s.List(ctx, u.UserID)` whole; `show` is `s.Find(ctx, u.UserID, name)`; `create` checks `store.ValidName(name)`, then `s.Taken(ctx, name)`, then the repository and ref, and calls `s.Create(ctx, store.Draft{Owner: u.UserID, Name: name, Repo: repo, Ref: ref})`, `store.ErrNameTaken` still answering the taken refusal when a racing create won; `update` is `s.Find` then `s.SetRef(ctx, sc.ID, ref)`, its `changed` deciding the event; `subscribe` is `s.Find`, then `store.ValidEvent(event)`, then `s.Subscribe(ctx, sc.ID, event)`; `unsubscribe` is `s.Find`, then `store.ValidEvent(event)`, then `s.Unsubscribe(ctx, sc.ID, event)`, `store.ErrNotSubscribed` answering `tools.NotSubscribed`; every answered `Script`'s `Subscriptions` giving `subscriptions`, each `Event` and `Created`, and its `len` `list`'s count; `delete` is `s.Find` then the run core's deletion, which ends with `s.Delete(ctx, sc.ID)`; `runs` is `s.Find` then `s.Runs(ctx, sc.ID, started, id, n+1)`, `started` and `id` empty for the first page and the position the page token carries otherwise, where before this revision it was `s.Runs(ctx, sc.ID)` whole; the tools refuse a bad `limit` or `page` before they call the store (`D11-tools`); `result` and `cancel` are `s.FindRun(ctx, u.UserID, id)`, `cancel` then handing the run to the run core, whose `s.FinishRun` answering `store.ErrEnded` is the refusal `tools.Ended`. `store.ErrNotFound` is `tools.MissingScript` or `tools.MissingRun`; an error matching no sentinel is `store.Unreachable`. A `Run`'s `Status` compared with `store.StatusExited` decides whether `exit_code` is present, with `store.StatusFailed` whether `reason` is, and its `Trigger` compared with `store.TriggerEvent` whether `event`, its `Event`, is.

The run core (`D07-runs`): `id, _ := store.NewRunID(rand)`; after the process has started, `s.AddRun(ctx, store.Run{ID: id, Script: sc.ID, SHA: sha, Ref: ref, User: u.UserID, RequestID: u.RequestID, Trigger: store.TriggerManual, Status: store.StatusRunning, Started: started})`, or for an event run `Trigger: store.TriggerEvent, Event: req.Cause.ID` (`D14-delivery`), whose `store.ErrDelivered` means the script already has its run from that event, after a `s.Delivered(ctx, sc.ID, req.Cause.ID)` asked first; or, when every slot is taken, the same with `Status: store.StatusQueued`, and once its process has started `s.StartRun(ctx, id)`; or for a run that could not start the same with `Status: store.StatusFailed`, `Reason` its reason and `Finished` set, `SHA` empty when the ref did not resolve (`SHA: ""`, `Reason: store.ReasonCommitMissing`, say) and the resolved sha otherwise (`Reason: store.ReasonTooLarge`, say); when the process ends, `s.FinishRun(ctx, id, store.Ending{Status: store.StatusExited, ExitCode: code, Finished: now, StdoutBytes: n, StderrBytes: m, Truncated: cut})`; for a queued run cancelled, `s.FinishRun(ctx, id, store.Ending{Status: store.StatusKilled, Finished: now})`, and abandoned, `store.Ending{Status: store.StatusFailed, Reason: store.ReasonQueueAbandoned, Finished: now}`; at start, `s.Running(ctx)` and a `FinishRun` with `store.StatusKilled` for each, and `s.Queued(ctx)` and a `FinishRun` with `store.StatusFailed` and `store.ReasonQueueAbandoned` for each; after every end, `s.PastKeeping(ctx, now, days, count)`, each run's folder removed, then `s.DeleteRun(ctx, r.ID)`; to delete a script, `s.Running(ctx)` and `s.Queued(ctx)` to find which of its runs are running or queued, where before this revision it read `s.Runs(ctx, sc.ID)` whole, the kills and `FinishRun`s, then the folder `state/runs/<script id>/` removed, then `s.Delete(ctx, sc.ID)`.

The pages (`D08-pages`, `D09-run-files`): the catalog is `s.List(ctx, u.UserID, after, paging.DefaultLimit+1)`, the window its `page` names, `after` as for `list`; a script page is `s.Find`, `s.Runs(ctx, sc.ID, started, id, paging.DefaultLimit+1)`, the window of runs its `page` names, `started` and `id` as for `runs`, and `s.RunCount(ctx, sc.ID)`, the runs kept, where before this revision they were `s.List(ctx, u.UserID)` and `s.Runs(ctx, sc.ID)` whole, `len` of the second being the runs kept, `paging` being appkit's package (its D25); a run page and its files are `s.Find` then `s.FindRun`, the run's `Script` compared with the script's `ID`. For an error matching no sentinel, a page answers the unavailable page with status `503`, and a run's file answers `store.Unreachable` and a newline, as plain text with status `503`.

A test opens a handle with `d, err := db.Open(ctx, db.Config{Path: filepath.Join(t.TempDir(), "state", "scripts.db"), Migrations: scripts.Migrations(), Now: clock})` and builds a store with `store.New(d, store.Config{Now: clock, Rand: bytes.NewReader(known)})`; creates, finds, lists and deletes scripts; adds, finishes, lists, counts and deletes runs; walks `List` and `Runs` a window at a time, passing as the next window's bound the last name, or the last run's started text, `r.Started.UTC().Format(time.RFC3339)`, and id; subscribes and unsubscribes scripts, patterns among them, and lists an event name's subscribers; adds event runs and asks `Delivered` before and after `DeleteRun` and `Delete`; asks which are past keeping at a moment it chooses; closes the handle and opens another on the same path to see the same records; and calls `d.SetFailing(true)`, before a call or from a hook the call runs after its reads, to see a catalog error, and `d.SetFailing(false)` to see the same store answer again. A schema test opens a fresh catalog with `scripts.Migrations()` and, inside a `d.Read`, queries `sqlite_master` and `PRAGMA table_info`. An adoption test opens a handle on a file with an empty migrations file system, creates the table `catalog` by R-ADCC-FLJZ's statement and writes its one row through `d.Write`, bytes it chose, drops `schema_migrations`, closes the handle, opens the file again with `scripts.Migrations()`, reads the tables and the row of `catalog` inside a `d.Read`, and sees a store over the handle answer no script and no run. A test of a catalog of `0001` alone opens a handle with a `fstest.MapFS` holding only `0001_catalog.sql`, its bytes read with `fs.ReadFile(scripts.Migrations(), "0001_catalog.sql")`, writes the `catalog` row through `d.Write`, closes it, and opens the file again with `scripts.Migrations()`; a test of a catalog of `0001` and `0002` does the same with a `fstest.MapFS` holding both. A test of the mirror reads, inside a `d.Read`, every column of `scripts` with its `typeof`, `SELECT id, typeof(id), name, typeof(name), …, created, typeof(created) FROM scripts`, and every column of `runs` with its `typeof`, `SELECT id, typeof(id), script, typeof(script), …, reason, typeof(reason) FROM runs`, sixteen pairs, and compares the rows with the content, every owner's `List` and every script's `Runs` asked with an empty bound and an `n` past the store's size, each time formatted with `t.UTC().Format(time.RFC3339)`: after each kind of write, after a write refused and one made while failing, and across a closed and reopened handle. A test that a store leaves `catalog` alone writes its one row through `d.Write`, bytes it chose, and reads `SELECT id, value FROM catalog` inside a `d.Read` at the same moments, seeing that row unchanged, and on a fresh catalog with no row written sees none after them.
