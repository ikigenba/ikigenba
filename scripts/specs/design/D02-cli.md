# D02-cli

scripts as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, what `db status` reports of the catalog, and the two constants whose text is fixed here, the usage text and the manifest, with the one file under `etc/` that copies the manifest. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run`, `cli.Version` and the root package's `Etc` and `Migrations`; `D12-limits` declares `settings.Defaults` and the `Settings` it returns; `D08-pages` declares `pages.Description`. When `Args` is empty scripts serves, and everything from there is `D03-serve`'s.

The arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Version` and a newline, `manifest` writes `Manifest`, and `--help` writes `Usage`. The one two-word command, `db status`, reports the catalog's migrations (below). Any other `Args` is a usage error. The argument scripts complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`; and otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `scripts: `, and after exactly one empty line comes the hint to run `scripts --help`, unprefixed because scripts is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. The constant for 1 keeps its name, `ExitServerFailed`, though it now also covers a `db status` that fails. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a setting that is not a positive whole number) exits 2, while trouble on the host once scripts is past its checks (no `git` or `python3.12` on the `PATH`, a catalog it cannot open, a `state/runs` it cannot create, a drain that runs out) exits 1, and so does a `db status` whose catalog cannot be read or is newer than the binary. `Run` returns no other value.

## db status

`db status` is an operator's look at the catalog: which of the migrations the binary carries `state/scripts.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status` (its D16), which scripts calls with the path `state/scripts.db` resolved against `Process.Dir` (so relative to the working directory in the binary) and the migrations `scripts.Migrations()` returns, writing straight to `Stdout`; it reads no clock, so the `Config` carries no `Now`. scripts adds nothing to the lines and states nothing about their format; its requirements say only that the bytes on `Stdout` are the ones `db.Status` writes for that path and those migrations, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database, never with a format it spells out. `db.Status` only looks: it applies nothing and creates nothing, so before scripts' first start `db status` reports every migration pending and leaves the directory as it was, and a catalog an earlier scripts kept, which records no migration, reads the same way. When it returns an error, scripts says so on one line, `scripts: ` and the error's text with each newline replaced by a space, and exits 1. Whatever `db.Status` had already written to `Stdout` stays there: findings are product, and the repository's command-line conventions send a report to stdout whole, bad news included. That is the one case in which a failure leaves anything on `Stdout`: a catalog that records a migration this scripts does not carry is reported line by line, the unknown version among them, and then refused, while a catalog that cannot be read yields no lines at all. `db status` reads no environment, takes no socket, runs neither `git` nor `python3.12`, and looks at nothing under `state/runs/`.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket, no git, no interpreter and no repository, and only `db status` reads the catalog, so `scripts --version` succeeds with nothing passed in and `scripts bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, either timer, the random source, the sink, the banner source or the server maker, and only `db status` reads anything under the working directory, creating nothing there. A command runs no git and no script, so it reads no repository, and records no event: the trail is what scripts records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns, `db status` and `db bogus` included. Every failure but that one `db status` case leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text is exactly the bootstrap story's: scripts' name; its description, which is `pages.Description`, the line the about screen shows, the host publishes in its services file, and the MCP endpoint gives its clients as instructions; that it is not the host's default app; that it is one of the suite's MCP services; no secrets; the seven settings of `[env]` with the defaults `settings.Defaults` holds, `REPOS_DIR`, `TREE_MAX_BYTES`, `OUTPUT_MAX_BYTES`, `OPERATION_SECONDS`, `SCRIPT_SECONDS`, `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT`, in the order the stories list them; the `[database]` table that tells the host to keep and replicate `state/scripts.db`; and the `[resources]` table opsctl writes into the service unit, `cpu_weight` 50, `memory_max` `1G` and `io_weight` 50, which bounds scripts, every git it runs and every script it runs together. It declares no `guests`, since every page and `/mcp` is for a signed-in user and the host's nginx sends a visitor with no credential to sign in; no port, since scripts serves on the socket the host passes it; no `DRAIN_SECONDS`, which is opsctl's to set; and no `cache/`, since a run's folder is the product and lives under `state/runs/`.

## The file under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ. The build run writes it from the constant and keeps the two in step. The file is proved by use: the root package embeds the committed `etc/manifest.toml` and exports it as `Etc`, an `embed.FS` (`D01-layout-and-run-seam`), which only a `//go:embed` directive can fill (the `embed` package's documentation), so a test compares the embedded `etc/manifest.toml` with `cli.Manifest` without ever opening the checkout, and a build whose `etc/` lacks the file fails to compile while one holding a stale copy fails that test. That test lives in the external test package `scripts_test` beside the root package, since it imports both the root package and `internal/cli`, and `internal/cli` reaches the root package through `internal/pages`, so a test inside package `scripts` would form an import cycle.

scripts ships no nginx fragment, so this design declares no nginx constant and `Etc` holds the manifest alone. What the release file holds beside `etc/` (`bin/scripts` and the human-drawn `share/icon.svg`), that nothing else is in it, and that the version appears only in the file's name and the binary are `devctl build`'s output, which no test this design permits can see; they are `D13-on-a-space`'s to record.

## Departures from sites

The words differ where scripts differs: the program name, the help text's description of what scripts serves, the description, seven settings in `[env]` rather than three, and no `guests` line. The list of things a command leaves untouched gains `ScriptAfter`, the second timer `D01-layout-and-run-seam` adds to the seam, and the interpreter beside git among the processes a command never starts.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `scripts --version`, `scripts manifest` or `scripts --help` and reads stdout; an operator types `scripts db status` in `/opt/scripts` before or after a deploy and reads which migrations the catalog has had; `devctl build` runs `scripts manifest` and compares its output with the release's `etc/manifest.toml`, refusing the app when they differ; opsctl reads the manifest's `[env]`, `[database]` and `[resources]` from the installed `etc/manifest.toml`; the help text tells a caller what `ExitSuccess`, `ExitServerFailed` and `ExitUsage` mean.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s) and `Dir` (an empty temporary directory) set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `cli.Version + "\n"`, `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Environ`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `After`, `ScriptAfter`, `Banner` and `MCP` to functions that record a call, `Rand` to a reader and `Sink` to a `*telemetry.Capture` that record any use, `Stderr` to a writer that counts its `Write` calls, and asserts none was used. A test of `db status` makes a catalog under its `Dir` with `db.Open` and `scripts.Migrations()` (or with a fixed `Now` and an extra recorded version written through `DB.Write`, or a file that is not a database), closes it, runs `cli.Run` with `Args` `["db", "status"]`, and compares `Stdout` with what its own `db.Status` call wrote into a buffer for the same path and migrations before `Run` was called, and with what it writes after, and `Stderr` with `"scripts: "` and that call's error text. A test compares `cli.Manifest` with `pages.Description` and with the fields of `settings.Defaults()`. A test in package `scripts_test` reads `etc/manifest.toml` from `scripts.Etc()` with `fs.ReadFile` and compares it with `cli.Manifest`.
