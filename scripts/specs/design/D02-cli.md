# D02-cli

scripts as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, what `db status` reports of the catalog, and the three constants whose text is fixed here, the usage text, the manifest and the nginx fragment, with the two files under `etc/` that copy the manifest and the fragment. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process` with its `Version`, `cli.Run` and the root package's `Etc` and `Migrations`; `D12-limits` declares `settings.Defaults` and the `Settings` it returns; `D08-pages` declares `pages.Description`. When `Args` is empty scripts serves, and everything from there is `D03-serve`'s.

The arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity, `manifest` writes `Manifest`, and `--help` writes `Usage`. The one two-word command, `db status`, reports the catalog's migrations (below), which in this scripts are `0001` and `0002`, one line each. Any other `Args` is a usage error. The argument scripts complains about is the first one it does not take: the first element when that is not a recognised word, or when it is `db` standing alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`; and otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `scripts: `, and after exactly one empty line comes the hint to run `scripts --help`, unprefixed because scripts is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. The constant for 1 keeps its name, `ExitServerFailed`, though it now also covers a `db status` that fails. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a setting that is not a positive whole number) exits 2, while trouble on the host once scripts is past its checks (no `git` or `python3.12` on the `PATH`, a catalog it cannot open, a `state/runs` it cannot create, a drain that runs out) exits 1, and so does a `db status` whose catalog cannot be read. `Run` returns no other value.

## db status

`db status` is an operator's look at the catalog: which of the migrations the binary carries `state/scripts.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status` (its D16), which scripts calls with the path `state/scripts.db` resolved against `Process.Dir` (so relative to the working directory in the binary) and the migrations `scripts.Migrations()` returns, writing straight to `Stdout`; it reads no clock, so the `Config` carries no `Now`. scripts adds nothing to the lines and states nothing about their format; its requirements say only that the bytes on `Stdout` are the ones `db.Status` writes for that path and those migrations, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database, never with a format it spells out. `db.Status` only looks: it applies nothing and creates nothing, so before scripts' first start `db status` reports every migration pending and leaves the directory as it was, and a catalog an earlier scripts kept, which records no migration, reads the same way. When it returns an error, scripts says so on one line, `scripts: ` and the error's text with each newline replaced by a space, and exits 1. Whatever `db.Status` had already written to `Stdout` stays there: findings are product, and the repository's command-line conventions send a report to stdout whole, bad news included. That is the one case in which a failure may leave anything on `Stdout`. A catalog that records a migration this scripts does not carry, one a newer scripts upgraded, is not a failure: older code runs on newer data (`D03-serve`), appkit's `db.Status` lists every line, the unknown version among them, and returns nil, so `db status` writes nothing to `Stderr` and exits 0. A catalog that cannot be read yields no lines at all and exits 1. `db status` reads no environment, takes no socket, runs neither `git` nor `python3.12`, and looks at nothing under `state/runs/`.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket, no git, no interpreter and no repository, and only `db status` reads the catalog, so `scripts --version` succeeds with nothing passed in and `scripts bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the control group under `Process.Cgroup`, the inherited descriptor, systemd's notification socket, the clock, either timer, the random source, the sink, the banner source or the server maker, and only `db status` reads anything under the working directory, creating nothing there. A command runs no git and no script, so it reads no repository, and records no event: the trail is what scripts records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns, `db status` and `db bogus` included. Every failure but that one `db status` case leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text: scripts' name; its description, which is `pages.Description`, the line the about screen shows, the host publishes in its services file, and the MCP endpoint gives its clients as instructions; that it is not the host's default app; that it is one of the suite's MCP services; no secrets; the thirteen settings of `[env]` with the defaults `settings.Defaults` holds, `REPOS_DIR`, `TREE_MAX_BYTES`, `OUTPUT_MAX_BYTES`, `OPERATION_SECONDS`, `SCRIPT_SECONDS`, `RUN_MEMORY_MAX_BYTES`, `RUNS_MEMORY_MAX_BYTES`, `RUNS_CPU_PERCENT`, `RUN_PIDS_MAX`, `RUN_MAX_ACTIVE`, `RUN_MAX_QUEUED`, `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT`, in that order; the `[database]` table that tells the host to keep and replicate `state/scripts.db`; and the `[resources]` table opsctl writes into the service unit (opsctl's published interface): `slice` `apps`, so scripts runs among the suite's other apps; `memory_max` `896M`, one ceiling over scripts, every git it runs and every script it runs together; `go_memory_limit` `128M`, the soft limit scripts' own Go runtime collects garbage against; and `delegate` `true`, so the host hands scripts' service its part of the control group tree, which `cli.Run` arranges and runs every script in (`D03-serve`). It declares no CPU or IO weight, so scripts has its slice's default share. It declares no `guests`, since every page and `/mcp` is for a signed-in user and the host's nginx sends a visitor with no credential to sign in; no port, since scripts serves on the socket the host passes it; no `DRAIN_SECONDS`, which is opsctl's to set; and no `cache/`, since a run's folder is the product and lives under `state/runs/`.

## The nginx fragment

`/events` and `/declarations` are for scripts' siblings on its socket: the events app delivers events there and asks which scripts accepts (`D03-serve`, `D14-delivery`). The host's nginx proxies everything at scripts' public name to that same socket, so the fragment closes the two paths to the outside: the host and the sandbox include an app's `etc/nginx.conf` inside the server block of its public name, and the fragment's two exact-match locations, `location = /events` and `location = /declarations`, each answering `return 404`, therefore answer both paths 404 at the public name for every method, while the same paths on the socket stay open. nginx's documentation proves the two facts relied on: an exact-match `location` (`=`) is chosen, and ends the search for a location, when it matches, whatever order the server's locations are declared in (`ngx_http_core_module`, the `location` directive), and `return` is allowed in a `location` and ends processing with the code it names (`ngx_http_rewrite_module`). The fragment matches only those two exact paths, so `/events/` and `/declarations/<x>` reach scripts and are script paths, answered with the not-found page (`D03-serve`, `D08-pages`); and it redeclares none of the host's own locations. telemetry's fragment, its one `location = /ingest`, is the shape.

The fragment is a fact about the binary like the manifest, so it is the constant `NginxConf`; nothing prints it. The `manifest` command is unchanged: it prints `Manifest` alone, which is all `devctl build` compares, and a command printing the fragment would be a usage-text change nothing asks for. The constant's value is contract, proved by use as the manifest's is.

## The files under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ; the committed `etc/nginx.conf` holds exactly the text of `NginxConf`. The build run writes both from the constants and keeps them in step. The files are proved by use: the root package embeds the committed `etc/manifest.toml` and `etc/nginx.conf` and exports them as `Etc`, an `embed.FS` (`D01-layout-and-run-seam`), which only a `//go:embed` directive can fill (the `embed` package's documentation), so a test compares each embedded file with its constant without ever opening the checkout, and a build whose `etc/` lacks either file fails to compile while one holding a stale copy fails that test. That test lives in the external test package `scripts_test` beside the root package, since it imports both the root package and `internal/cli`, and `internal/cli` reaches the root package through `internal/pages`, so a test inside package `scripts` would form an import cycle.

What scripts' directory in the suite release holds beside `etc/` (`bin/scripts` and the human-drawn `share/icon.svg`), that nothing else is in it, and that the commit appears only in the release's name and top-level directory, and in no member of scripts' directory and no such member's path, are `devctl build`'s output, which no test this design permits can see; they are `D13-on-a-space`'s to record. That a host or a sandbox includes `etc/nginx.conf` in scripts' server, and what nginx then answers, is opsctl's, the sandbox's and nginx's, also recorded there.

## Departures from sites

The words differ where scripts differs: the program name, the help text's description of what scripts serves, the description, thirteen settings in `[env]` rather than three, a `[resources]` table that delegates the control group, and no `guests` line. Unlike sites, scripts ships an nginx fragment, in telemetry's shape. The list of things a command leaves untouched gains `ScriptAfter`, the second timer `D01-layout-and-run-seam` adds to the seam, and the interpreter beside git among the processes a command never starts.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `scripts --version`, `scripts manifest` or `scripts --help` and reads stdout; an operator types `scripts db status` in `/var/opt/ikigenba/scripts` before or after a deploy and reads which migrations the catalog has had; `devctl build` runs `scripts manifest` and compares its output with the release's `etc/manifest.toml`, refusing the app when they differ; opsctl reads the manifest's `[env]`, `[database]` and `[resources]` from the release's `etc/manifest.toml`, and opsctl and the sandbox include the release's or checked-out `etc/nginx.conf` in scripts' server block, where before this revision there was none to include; the help text tells a caller what `ExitSuccess`, `ExitServerFailed` and `ExitUsage` mean.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s) and `Dir` (an empty temporary directory) set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `p.Version + "\n"` (a `Version` it chose, and the empty string, which gives exactly `"\n"`), `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Environ`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `After`, `ScriptAfter`, `Banner` and `MCP` to functions that record a call, `Rand` to a reader and `Sink` to a `*telemetry.Capture` that record any use, `Stderr` to a writer that counts its `Write` calls, and asserts none was used; it also sets `Cgroup` to a temporary directory holding only a `cgroup.procs` naming `Pid`, and finds it unchanged. A test of `db status` makes a catalog under its `Dir` with `db.Open` and `scripts.Migrations()` (or with a fixed `Now` and an extra recorded version written through `DB.Write`, or a file that is not a database), closes it, runs `cli.Run` with `Args` `["db", "status"]`, and compares `Stdout` with what its own `db.Status` call wrote into a buffer for the same path and migrations before `Run` was called, and with what it writes after, and `Stderr` with `"scripts: "` and that call's error text when it returned one, or with nothing, the catalog with an extra recorded version included, when it returned nil. A test compares `cli.Manifest` with `pages.Description` and with the fields of `settings.Defaults()`. A test in package `scripts_test` reads `etc/manifest.toml` and `etc/nginx.conf` from `scripts.Etc()` with `fs.ReadFile` and compares them with `cli.Manifest` and `cli.NginxConf`; a test compares `cli.NginxConf` with the two lines R-6PHM-FCZC spells.
