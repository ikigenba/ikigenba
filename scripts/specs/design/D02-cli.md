# D02-cli

scripts as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, the exit codes it returns, and the two constants whose text is fixed here, the usage text and the manifest, with the one file under `etc/` that copies the manifest. `D01-layout-and-run-seam` declares the names this design behaves through: `cli.Process`, `cli.Run`, `cli.Version` and the root package's `Etc`; `D12-limits` declares `settings.Defaults` and the `Settings` it returns; `D08-pages` declares `pages.Description`. When `Args` is empty scripts serves, and everything from there is `D03-serve`'s.

`Run` takes at most one argument and the argument decides everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching anything else: `--version` writes `Version` and a newline, `manifest` writes `Manifest`, and `--help` writes `Usage`. Any other `Args` is a usage error. The argument scripts complains about is the first one it does not take: the first element when that is not a recognised word, otherwise the second, which is surplus whatever it says. An argument that starts with `-` is an unknown option, any other an unknown command. The diagnostic follows the repository's command-line conventions: its first line begins `scripts: `, and after exactly one empty line comes the hint to run `scripts --help`, unprefixed because scripts is speaking for itself. The usage text is never written to `Stderr`.

## Exit codes

The help text names the exit codes: 0 for success, 1 for a server that failed, 2 for a usage error. `D03-serve` leans on that split: a start the caller got wrong (no socket, several sockets, a setting that is not a positive whole number) exits 2, while trouble on the host once scripts is past its checks (no `git` or `python3.12` on the `PATH`, a catalog it cannot open, a `state/runs` it cannot create, a drain that runs out) exits 1. `Run` returns no other value.

## Commands touch nothing

Arguments are checked before anything else. A command needs no socket, no git, no interpreter, no catalog and no repository, so `scripts --version` succeeds with nothing passed in and `scripts bogus` fails whatever the environment holds. Unless `Args` is empty, `Run` touches none of the environment, the inherited descriptor, systemd's notification socket, the clock, either timer, the random source, the sink, the banner source, the server maker, the database source or the working directory. A command runs no git and no script, so it reads no repository, and records no event: the trail is what scripts records while it serves. That a command creates nothing is observable: with `Dir` naming an empty directory, it is still empty when `Run` returns. Every failure leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole when journald interleaves another writer.

## The manifest

The manifest is a fact about the binary, so the binary carries it as the constant `Manifest` and prints it for `manifest`. Its text is exactly the bootstrap story's: scripts' name; its description, which is `pages.Description`, the line the about screen shows, the host publishes in its services file, and the MCP endpoint gives its clients as instructions; that it is not the host's default app; that it is one of the suite's MCP services; no secrets; the seven settings of `[env]` with the defaults `settings.Defaults` holds, `REPOS_DIR`, `TREE_MAX_BYTES`, `OUTPUT_MAX_BYTES`, `OPERATION_SECONDS`, `SCRIPT_SECONDS`, `RUN_KEEP_DAYS` and `RUN_KEEP_COUNT`, in the order the stories list them; the `[database]` table that tells the host to keep and replicate `state/scripts.db`; and the `[resources]` table opsctl writes into the service unit, `cpu_weight` 50, `memory_max` `1G` and `io_weight` 50, which bounds scripts, every git it runs and every script it runs together. It declares no `guests`, since every page and `/mcp` is for a signed-in user and the host's nginx sends a visitor with no credential to sign in; no port, since scripts serves on the socket the host passes it; no `DRAIN_SECONDS`, which is opsctl's to set; and no `cache/`, since a run's folder is the product and lives under `state/runs/`.

## The file under etc/

The committed `etc/manifest.toml` holds exactly the text of `Manifest`, and `devctl build` refuses an app where they differ. The build run writes it from the constant and keeps the two in step. The file is proved by use: the root package embeds the committed `etc/manifest.toml` and exports it as `Etc`, an `embed.FS` (`D01-layout-and-run-seam`), which only a `//go:embed` directive can fill (the `embed` package's documentation), so a test compares the embedded `etc/manifest.toml` with `cli.Manifest` without ever opening the checkout, and a build whose `etc/` lacks the file fails to compile while one holding a stale copy fails that test. That test lives in the external test package `scripts_test` beside the root package, since it imports both the root package and `internal/cli`, and `internal/cli` reaches the root package through `internal/pages`, so a test inside package `scripts` would form an import cycle.

scripts ships no nginx fragment, so this design declares no nginx constant and `Etc` holds the manifest alone. What the release file holds beside `etc/` (`bin/scripts` and the human-drawn `share/icon.svg`), that nothing else is in it, and that the version appears only in the file's name and the binary are `devctl build`'s output, which no test this design permits can see; they are `D13-on-a-space`'s to record.

## Departures from sites

The words differ where scripts differs: the program name, the help text's description of what scripts serves, the description, seven settings in `[env]` rather than three, and no `guests` line. The list of things a command leaves untouched gains `ScriptAfter`, the second timer `D01-layout-and-run-seam` adds to the seam, and the interpreter beside git among the processes a command never starts.

## Consumer tasks

`main` hands `cli.Run` the process's arguments after the program name, with the other `Process` fields `D01-layout-and-run-seam` names, and exits with what it returns. A developer types `scripts --version`, `scripts manifest` or `scripts --help` and reads stdout; `devctl build` runs `scripts manifest` and compares its output with the release's `etc/manifest.toml`, refusing the app when they differ; opsctl reads the manifest's `[env]`, `[database]` and `[resources]` from the installed `etc/manifest.toml`; the help text tells a caller what `ExitSuccess`, `ExitServerFailed` and `ExitUsage` mean.

A test builds a `cli.Process` with only `Args`, `Stdout`, `Stderr` (two `bytes.Buffer`s) and `Dir` (an empty temporary directory) set, calls `cli.Run(ctx, p)`, and compares the returned value with `cli.ExitSuccess` or `cli.ExitUsage`, `Stdout` with `cli.Version + "\n"`, `cli.Manifest` or `cli.Usage`, and `Stderr` with the exact diagnostic; it then lists `Dir` and finds it empty. To prove nothing else is touched it sets `LookupEnv`, `Environ`, `Unsetenv`, `Inherit`, `Now`, `Sleep`, `After`, `ScriptAfter`, `Banner` and `MCP` to functions that record a call, `Rand` to a reader and `Sink` to a `*telemetry.Capture` that record any use, `Stderr` to a writer that counts its `Write` calls, and `Database` to a path under `Dir`, and asserts none was used. A test compares `cli.Manifest` with `pages.Description` and with the fields of `settings.Defaults()`. A test in package `scripts_test` reads `etc/manifest.toml` from `scripts.Etc()` with `fs.ReadFile` and compares it with `cli.Manifest`.
