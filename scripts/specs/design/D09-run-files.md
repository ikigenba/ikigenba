# D09-run-files

The files beneath a run's page: what scripts answers at `/<name>/runs/<run id>/input.json`, `/<name>/runs/<run id>/stdout`, `/<name>/runs/<run id>/stderr` and `/<name>/runs/<run id>/out/<path>`, the addresses the run page's Download links lead to (`D08-pages`). This document declares `web.FilesConfig` and `web.Files`, the handler `D03-serve` routes every run file path to, defines which paths those are, and states what each is answered with. `D03-serve` owns the rest of `internal/web`: `web.Handler`, `web.Config`, the route table, `identity.Require` around every route, the request's id and its two events, and that nothing reaches standard error while telemetry takes every event. `D04-store` declares `store.Store`, `Find`, `FindRun`, `store.ErrNotFound` and `store.Unreachable`; `D07-runs` declares `runs.Core`, its `Folder` and `Gone`, and `runs.InputFile`, `runs.StdoutFile`, `runs.StderrFile` and `runs.OutDir`; `D08-pages` declares the template set, `pages.Set`, the pieces of a request, the user id, the not-found answer and the catalog refusal this handler answers with.

## Which paths are a run's files

A run gives exactly four kinds of file: its input, its two streams, and what its script wrote under `out/`. A **run file path** is one whose pieces (`D08-pages`) are a name, `runs`, a run id and at least one piece more, other than the run page's own `/<name>/runs/<run id>/`. `D03-serve` hands every such path to `web.Files`, whatever lies after the run id, so that a path naming nothing beneath a run is answered here too, and every other script path to `pages.Handler`. The two never disagree about a path that names nothing: both answer the not-found page.

## How a path is answered

In the order `S14` fixes, after `identity.Require`: a method other than `GET` or `HEAD` is refused 405 with `Allow: GET, HEAD` and an empty body, before the catalog is read. Then the first piece is looked up among the caller's own scripts with `store.Find`, and the third among the caller's runs with `store.FindRun`, the run counting only when its `Script` is that script's id; a name or a run that is not the caller's, or not that script's, is the not-found page, so the answer never says another user's run exists. A catalog read that answers neither a record nor `store.ErrNotFound` is the catalog refusal, `503` and the one line `store.Unreachable`.

Then the file. The pieces after the run id name a file only in four forms: exactly `input.json`, `stdout` or `stderr`; or `out` followed by one or more pieces, each a name: never empty, never `.` or `..`, holding no `/` and no NUL, whether it arrived plainly or percent-encoded. Nothing is tidied, so `out/charts/../report.csv` and `out/./report.csv` name nothing even though tidying would land on a file. The file is read from the run's folder, `runs.Core.Folder`, as it is at that moment and from nowhere else, and only when it is a regular file reached without following a symbolic link at any step: `out/` and every directory below it must be directories, not links to one, and the file itself must be a regular file, not a link to one. A directory, a link, a file the run never wrote, `tree/` and everything in it, and any file of a run whose folder is gone (`runs.Core.Gone`) name nothing and are the not-found page, never redirected.

A file that is served is sent whole, its bytes exactly, with `Content-Length` its size and `X-Content-Type-Options: nosniff`. `input.json`, `stdout` and `stderr` are `text/plain; charset=utf-8` with no `Content-Disposition`, so a browser shows them; a file under `out/` is `application/octet-stream` with `Content-Disposition: attachment` and its base name, whatever its extension, so a browser saves it and never renders a script's output as a page of scripts. A name beginning with `.` is served like any other: `out/` is its owner's own output, not a site published to the world. A `HEAD` gets the status and headers and no body. A run still running is served as its files stand when they are read; a later request gets more. No caching header is fixed.

Answering reads the catalog and the run's folder only: no repository, no git, no process, nothing written, not even a folder for a script that has never run, no cookie.

With the catalog unreachable every run file path is the catalog refusal, whatever follows the run id, because the file is judged only after both lookups. The contract states it for a failing store and for a request whose context is already done as it arrives, where `Find` is the read that fails, since turning on `SetFailing` for the store's handle and cancelling a request's context are the ways the test rules allow to fail the catalog; a failure of `FindRun` alone is answered the same way, the catalog refusal and never the not-found page, but that is unstated as contract until the test rules decide whether a seam may fail one read. A not-found answer carries only the not-found page's own header, never one a served file would carry.

The checks that no step of a path is a symbolic link hold for a folder that stands still while the request is answered. That a link under `out/` is never followed even to look at what it names, by a `Stat` say, is intended but not contract: following a link only to look at it and then answering the not-found page gives the same answer, and no test the rules allow can tell the two apart. A path component replaced concurrently with the request, a directory swapped for a link between the check and the read say, is outside the contract: no test the rules allow can provoke that interleaving deterministically.

## Decisions

- The handler lives in `internal/web`, as `D01-layout-and-run-seam` places it, beside the route table that sends it the paths, rather than in `internal/pages`: it serves bytes, not pages, and draws no template but the not-found page, which it takes from the same `*pages.Set`.
- A run file path is decided by the pieces alone, before the catalog is read, so `D03-serve` can route without a lookup, and the two handlers each do their own method check and lookups in the stories' order.
- `Content-Disposition` quotes the base name as an HTTP quoted string when every byte of it is printable ASCII, a `\` or `"` escaped with a `\`; a name with any other byte is sent as `attachment` alone, leaving the browser to name the file from the URL, since no story fixes that case and the header must not carry raw bytes.
- The serving requirements are stated for a request that carries none of `Range`, `If-Match`, `If-None-Match`, `If-Modified-Since`, `If-Unmodified-Since` and `If-Range`, since the stories fix no answer to them.
- The four forms are matched byte for byte after decoding, so `Stdout` and `stdout/` name nothing.

## Consumer tasks

`web.Handler` builds `web.Files(web.FilesConfig{Banner: cfg.Banner, Pages: set, Store: cfg.Store, Runs: cfg.Runs})` once, with the set `pages.Load` returned, and serves every run file path with it inside `identity.Require` (`D03-serve`).

A download: `GET /nightly-report/runs/run_3f9a1c2e8b7d4a60/out/charts/sales.svg` reaches `web.Files` with the caller on its context; the method is `GET`; the pieces are `nightly-report`, `runs`, `run_3f9a1c2e8b7d4a60`, `out`, `charts` and `sales.svg`; `cfg.Store.Find(ctx, u.UserID, "nightly-report")` gives the script and `cfg.Store.FindRun(ctx, u.UserID, "run_3f9a1c2e8b7d4a60")` the run, whose `Script` is the script's `ID`; `cfg.Runs.Gone(r)` is false; `out` and `out/charts` under `cfg.Runs.Folder(r)` are directories and `sales.svg` a regular file; the answer is 200 with `Content-Type: application/octet-stream`, `Content-Length: 12034`, `Content-Disposition: attachment; filename="sales.svg"`, `X-Content-Type-Options: nosniff` and the file's bytes. A missing file is `cfg.Pages.Write(w, r, http.StatusNotFound, "notfound", pages.NoticeData{Banner: cfg.Banner(page.User{})})`.

A test builds a `store.Store` with `store.New` over a handle `db.Open` returned for a file in its temporary directory with `scripts.Migrations()`, creates scripts and adds runs, builds a `runs.Core` over a temporary `Runs` and writes each run's folder itself — `input.json`, `stdout`, `stderr`, files and directories under `out/`, symbolic links to files and directories inside and outside the folder, a file under `tree/`, a removed folder — builds `identity.Require(web.Files(web.FilesConfig{...}))` with a `Banner` closure and a set from `pages.Load()`, and serves requests made with `httptest.NewRequest` with the identity headers set; it compares status, headers and body bytes, snapshots the folder before and after, calls `SetFailing(true)` on that handle, or serves a request whose context it cancelled first, to make the catalog unreachable, and reads the trace `GIT_TRACE` names to see that no git ran. A target outside the folder is a file in the test's own temporary directory, never `/etc/passwd`.
