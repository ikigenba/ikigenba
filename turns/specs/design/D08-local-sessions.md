# D08-local-sessions

This document covers two packages. `internal/dispatch` reads the dispatch tool's job directories and gives a dispatched Codex CLI or Grok CLI session its Claude Code parent. `internal/local` reads every session on this machine: it runs the three readers (D05-D07) over the roots `paths.Paths` names (D03) with the cutoff it is given, links them, and answers one result. `local.Read` is the one entry point `turns push` (D10) and `turns status` (D12) use to read sessions, so both commands read sessions the same way: push with the cutoff of its last successful push (D10), status with the zero cutoff, reading everything (D12). The commands' own documents state what each does with the result.

The dispatch skill hands a task to `codex exec` or `grok -p` in the background. Each job gets a directory `<Jobs>/<job>/` (the job name carries a date, a time, the tool and a task name; turns does not interpret it), and once the child starts, the file `session-id` in that directory holds the child's session id: on this machine a 36-character uuid followed by a newline. Some jobs have no `session-id` file, because the child never started or the job predates the file; such a job is not a job for turns. `dispatch.Jobs` lists the jobs it can read, each as its directory path and the id with surrounding white space removed. The directory path is the jobs directory joined with the job's name, so it is absolute when the caller passes an absolute directory, as `local.Read` always does (`paths.Paths.Jobs` is absolute). Nothing about a job is ever written.

A dispatched child carries no link to the session that dispatched it: a top-level `codex exec` rollout names no parent thread and a headless Grok session no parent session. The link comes from the other side. The dispatching Claude session reads the job's files, so its tool results name the job directory's path. `local.Read` gives `claude.Read` the directory of every job, and `claude.Read` answers a `Mention` for each Claude session whose tool results name one of them, carrying the path exactly as it was given, the Claude session, and the earliest moment that session named it (D05). `dispatch.Link` then takes each Codex or Grok session that has no parent, finds the jobs whose session id is that session's id, and gives the session as its parent the Claude session of the earliest mention of any of those jobs' directories. When two mentions share the earliest moment, the one whose session id sorts first wins, so the result never depends on input order. A session that already has a parent, such as a Codex subagent thread, keeps it: the tool's own record wins over a path match. Claude sessions are never changed, since a Claude session is never a dispatch child. A job no Claude session names, or whose id matches no session read, links nothing; a parent found by a later run reaches the space because push re-sends each session's latest held turn and the space sets a parent while it holds none.

`local.Read` takes a cutoff, `since`, under D04's rule. The jobs are not subject to it: every call lists every job and reads every `session-id` afresh, whatever its modification time, because a job's file is tiny and a job made long ago can be named by a Claude session changed today. `since` goes to `claude.Read` as it is, so only the Claude files changed since the cutoff are read and only their mentions are returned. The Codex and Grok readers get `since` and, as `ids`, the session ids of the jobs whose directories those mentions name; each reader reads a session whose id is in `ids` changed or not (D06, D07). So a Claude session that is read makes its jobs' sessions read too, and `Link` sends the parent with them; this is how a parent found after the child was pushed reaches the space. The link applies only to what was read: a job's session read because it changed, while its dispatching Claude session did not, has no mention to link it and is returned with no parent, and the space keeps the parent it already holds. Among several Claude sessions naming one job, the earliest is chosen among those read in that call. A job no read Claude session names puts nothing in `ids`, so an unchanged child of an unchanged parent is not read at all.

The match is on the session id alone, not the tool: the job's name carries the tool, but turns does not parse it, and a uuid shared by a Codex and a Grok session is not a case that arises; both would be linked. `Link` returns a new slice and leaves its arguments as they were, so a caller may keep the readers' results unchanged beside the linked one.

`local.Found` is the gathered result: the sessions of all three tools, Claude's first, then Codex's, then Grok's, each tool's in its reader's order (by id), and the skip count per tool, with an entry for every tool even when it is zero so a caller can print a line per tool without checking for absence. A home where none of the tools was ever installed reads as no session and nothing skipped, and nothing is created.
