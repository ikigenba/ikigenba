# Decision 15 — Adopt the suite brand icon contract: the shipped icon set and its link markup

**Decision.** github adopts the suite's **brand icon contract** —
`root project/design/D29.md` — which owns the shipped file set, the filenames,
the static location, the three `<link>` elements, and the pinned content types.
This Decision is the **citation, and citation is adoption**: github owns none of
that contract's content and restates none of it normatively. What is local — and
all this Decision adds — is **where the files land in this tree, which documents
carry the markup, and where the proof lives**.

The contract carries three `[proof: per-service]` ids, which github therefore proves
in its own tree:

- `R-RYDN-YNR5` — every HTML document the service serves carries all three link
  elements.
- `R-RZLK-CFHU` — each of the three asset paths answers `200` through the composition
  root with the pinned content type.
- `R-8MFA-HUNC` — the bare `GET /favicon.ico` answers `200` at the service's root
  path through the composition root, with the same bytes as the static path.

**Where the files land.** The three shipped files are committed into github's own
disk-served static root, beside the `tokens.css` and `.woff2` fonts already there
(D6):

    github/share/www/static/favicon.ico
    github/share/www/static/favicon-32.png
    github/share/www/static/apple-touch-icon.png

They are copied from `design/brand/`, the suite's shared reference directory, by
the same hand-copy that already put `tokens.css` and the fonts in this tree. They
ship on disk, installed as `share/<version>/www/static`, and are **not** compiled
into the binary — github serves its static subtree from `share/www` through
appkit's WWW loader (D6), not from a `go:embed` tree.

**Which documents carry the markup.** github serves one document,
`share/www/landing.html`, with a single `<head>`, already carrying
`static/tokens.css` and the font preloads.

**The `href` form** is the relative `static/…` form the page's stylesheet link
already uses. The contract fixes the target — the service's own static mount — and
not the string, so this form conforms.

**Content type and the static mount come from the chassis.** github declares
`Spec.WWW = true` (D6), so `appkit/web` serves the `share/www/static/` subtree and
**pins the content types itself**: its package `init()` registers `.ico` →
`image/x-icon` (and `.woff2` → `font/woff2`), so github does not pin any type in
its own code. The composition root is `internal/githubapp/spec.go`, which hand-
wires only `GET /{$}`; the `GET /static/` mount is provided automatically by the
chassis WWW mount (`appkit project/design/D07.md`).

**The root-path route.** The `/static/` mount does not answer the bare
`/favicon.ico` — they are different paths — so the chassis WWW mount registers
`GET /favicon.ico` beside `GET /static/` when `Spec.WWW` is set: appkit's favicon
alias re-dispatches the request to `/static/favicon.ico` on a shallow copy of the
request and delegates to the same site static handler, so the root path returns
the same bytes and the same pinned content type as the static path by
construction. It is registered ungated, like the static mount: the clients the
root path exists for hold no session and parse no markup.

github receives this route from the chassis rather than registering it itself —
declaring `Spec.WWW` is the whole opt-in. In production nginx strips the
`/srv/github/` prefix, so `/srv/github/favicon.ico` arrives as `/favicon.ico` and
this route answers it; on the bare loopback port under `bin/start` a browser
issues it directly.

**Where the proof lives.** All three adopted ids are proven in
**`cmd/github/main_test.go`**, the composition root's test file — the only place a
request can reach the icon routes the way production does, because the chassis WWW
mount (`GET /static/`, `GET /favicon.ico`) exists only on the appkit-assembled
router, not on github's bare Spec. This matches every other disk-served service
(`crm`, `notify`, `ledger`, `dropbox`), which prove these ids in their own
`cmd/<svc>/main_test.go`. The markup assertion reads the committed documents
through the same rendering path a user's request takes; the asset assertion issues
`GET` for each of the three paths against the assembled router at its mounted path
and checks status, non-empty body, and exact content type. Neither test constructs
a handler directly: a directly-driven handler proves the bytes exist, never that
the assembled service serves them.

**Rejected.**

- **Restate the file set and the markup locally so this design reads
  self-contained.** A local restatement is drift by construction: it goes stale
  the moment `root project/design/D29.md` changes, and the suite's rule is cite,
  never restate. Rejected.
- **Re-mint local ids for the two behaviors instead of citing `R-RYDN-YNR5` /
  `R-RZLK-CFHU`.** Both are `[proof: per-service]`: each is the suite's handle for one
  behavior, proven once per adopting tree. Parallel local ids would give one
  behavior two handles and break the id-to-behavior invariant. Rejected.
- **Assert the markup by string-matching the committed HTML file on disk instead
  of through the render path.** It is the cheaper test and it is a proxy: it
  proves a file contains a substring, not that the served response does. For a
  template-rendered head the two can differ. Rejected.
- **Prove the assets by calling the site static handler directly.** Same proxy
  pattern: it cannot fail when the route is missing from the composition root,
  which is the failure actually worth catching. Rejected.
- **Keep pinning `.ico` in github's own code (a `staticContentType` switch).**
  With the static subtree served through `appkit/web`, the chassis already pins
  `.ico` in its package `init()`; a second pin in github would give the content
  type two homes for a subtree github no longer serves itself. Rejected — the pin
  lives where the bytes are served, in the chassis.

**Verification.**

All three ids below are **adopted**, not minted here: each belongs to
`root project/design/D29.md`, which states the behavior. These lines say only
what substrate proves it inside `github/`.

**Assembling the router requires the app-auth environment.** `Spec()` mints an
installation token while it registers routes, so github's composition root cannot
be built at all without `IKIGENBA_APP_ID`, `IKIGENBA_GITHUB_ORG`, and
`IKIGENBA_APP_PRIVATE_KEY`. All three tests below therefore set those from a
**per-test generated RSA key** before assembling — the same fixture the package's
existing composition-root tests use — and point the WWW loader at the committed
`share/www` tree. This keeps the substrate hermetic and adds **no** environmental
precondition: no credential is read from the machine, and nothing reaches the
network. A test that reaches the assembled router without this setup fails during
route registration, before it can assert anything.

- `R-RYDN-YNR5` — adopted from `root project/design/D29.md`. Substrate: hermetic — a Go
  test in `cmd/github/main_test.go` that renders every document github serves
  through the real rendering path (the loaded `share/www` site) and asserts each
  response's `<head>` carries all three link elements: `rel="icon"` with
  `sizes="any"` at `favicon.ico`, `rel="icon"` with `type="image/png"` at
  `favicon-32.png`, and `rel="apple-touch-icon"` at `apple-touch-icon.png`. The
  document set is **enumerated from the committed `share/www` tree**, not
  hard-coded, so a page added later without the links fails.
- `R-RZLK-CFHU` — adopted from `root project/design/D29.md`. Substrate: hermetic — a Go
  test in `cmd/github/main_test.go` that builds github's real appkit-assembled
  router over the committed `share/www` tree and issues `GET` for `favicon.ico`,
  `favicon-32.png`, and `apple-touch-icon.png` beneath the mounted static prefix,
  asserting `200`, a non-empty body, and `Content-Type` exactly `image/x-icon` for
  the ICO and exactly `image/png` for both PNGs.
- `R-8MFA-HUNC` — adopted from `root project/design/D29.md`. Substrate: hermetic — a Go
  test in `cmd/github/main_test.go` that builds github's real appkit-assembled
  router and issues `GET /favicon.ico` at the **root path**, asserting `200` (not a
  `3xx`, so a redirect to the static path fails), `Content-Type` exactly
  `image/x-icon`, and a body byte-identical to the same router's
  `GET /static/favicon.ico` response.
