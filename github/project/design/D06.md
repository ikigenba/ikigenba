# Decision 6 — The landing page and nginx fragment

## Decision

`github` serves the suite's uniform landing page and ships its path-routed nginx
fragment, with **no** consent flow and **no** OAuth routes (the GitHub App is
pre-installed; there is no per-user consent).

**github serves its landing page and static assets from disk — the `share/www`
shape the rest of the page-serving suite uses** (`crm`, `notify`, `ledger`,
`gmail`, and the others), not from an embedded `internal/web` package. This
Decision moves github onto that shape for consistency; umbrella
`root project/design/D29.md` sanctions **both** the disk-served and the embedded
form, so this is a uniformity choice, not a contract repair.

**`share/www/landing.html` is a byte-exact clone of the canonical suite
landing** — the single `share/www/landing.html` structure every disk-served
service ships. **`crm` is the reference of record** (`crm`, `gmail`, `ledger`,
`notify`, and the rest share this file identically modulo three text fields).
github's `landing.html` reproduces crm's markup and `<style>` block **verbatim**;
only three fields carry github's own copy:

- the `<title>` suffix — `{{.Service}} · github`;
- the eyebrow — **`GitHub connector`**;
- the one-line description — **`Github connects the suite to GitHub through one
  shared GitHub App and exposes repository, pull request, and issue actions as MCP
  tools.`** — it deliberately omits the producers' "…publishes typed events to the
  event plane" clause, because github owns no event-plane producer.

Everything else is identical to crm's: the centred `<main>` column, the top-left
`Home` link (`<a class="home" href="/">Home</a>`) as the first element inside
`<main>`, the `<section aria-labelledby="page-title">` wrapping the eyebrow, the
`<h1 id="page-title">{{.Service}}</h1>`, and the description, the
`<dl aria-label="Service details">` Service·Version·API grid whose **API** cell is
`<code>POST /mcp</code>` (Version cell `class="version"`), the `<style>` block, and
the `static/` tree (the Carbon `tokens.css` and the woff2 fonts). The page renders
indistinguishably from `/srv/crm/`. The dynamic `service` and `version` values are
injected through appkit/web's `html/template` render, so they are HTML-escaped.

**The assets live on disk under `github/share/www/`**, installed as
`share/<version>/www` with `share/current` selecting the active version — the same
layout `crm`/`notify` ship. `share/www/landing.html` is the template;
`share/www/static/` holds `tokens.css`, the four woff2 fonts, and the three brand
icons (D15). The `internal/web` package — `embed.go`, `web.go`, its `landing.html`,
its `static/` tree, and its `*_test.go` files — is **deleted**; nothing embeds
these assets into the binary any more.

Wiring in `Handlers` (D1), in `internal/githubapp/spec.go`: github declares
`Spec.WWW = true`, so appkit loads the `share/www` site at startup, exposes it
through `Router.WWW()`, and **auto-mounts `GET /static/`** (`site.Static()`) **and
`GET /favicon.ico`** (the favicon alias re-dispatching to `/static/favicon.ico`).
github hand-wires only the landing route:

```go
rt.Handle("GET /{$}", landingHandler(rt.WWW(), rt.Service(), rt.Version()))
rt.Handle("POST /mcp", rt.RequireIdentity(
    mcp.NewHandler(client, rt.Version(), rt.Service(), health, rt.Logger())))
```

where `landingHandler` renders `share/www/landing.html` through `rt.WWW().Render`
with a `struct{ Service, Version string }`. github no longer registers
`GET /static/`, a `web.StaticHandler`, or a favicon route itself — those come from
the chassis WWW mount. Content types for the static subtree (including `.ico` →
`image/x-icon`) are pinned by `appkit/web`, not by github.

**Fidelity is proven the canonical way — by cloning crm's own disk-served landing
test set** (`cmd/crm/main_test.go`), not by github-bespoke guards. github's
landing/static proofs live in `cmd/github/main_test.go`, the composition root's
test file, and drive github's **real assembled router** (built through appkit with
the loaded `share/www` site) rather than a directly-constructed handler: they
render the landing through the WWW site, issue `GET /static/…` against the
assembled router, and assert github's own literals (the service name in the
render, the eyebrow `GitHub connector`, the `<h1 …>github</h1>`, and the
description). Assembling the router needs the app-auth environment (`Spec()` mints
an installation token while registering routes), so these tests set
`IKIGENBA_APP_ID`, `IKIGENBA_GITHUB_ORG`, and `IKIGENBA_APP_PRIVATE_KEY` from a
per-test generated RSA key — hermetic, no network, no real credential. github is a
**non-producer** with no `/feed`, so the no-shadow route test omits the `/feed`
stub. The tests live entirely within `github/`'s own tree; nothing here tests
against a sibling service.

**`etc/nginx.conf`** is the path-routed location fragment (not a vhost), mirroring
`gmail/etc/nginx.conf` with literal `MOUNT=/srv/github/` and port `3203`:

- `= /srv/github/.well-known/oauth-protected-resource` → open PRM bootstrap (no
  auth_request).
- `= /srv/github/` → bare mount root, gated by `auth_request /_session-authn`
  (dashboard browser session), proxied to `/` — the landing page.
- `/srv/github/static/` → session-gated static assets.
- `/srv/github/` (prefix) → every other path gated by `auth_request /_authn` (the
  bearer gate) with the identity-header hygiene and the 429-faithful `error_page`
  block, proxied to loopback `:3203` — this covers `/mcp`.
- `= /srv/github/pr` → `return 404`: the loopback-private twin (D5) must never be
  reachable through the public front door (defence in depth; the handler
  self-guard is primary).

github has **no `/feed`**, so — unlike the producer services — the fragment
carries no `/srv/github/feed` block; nothing under the mount serves a feed.

**Identity-header forwarding: all four owner headers, everywhere identity flows
today.** The dashboard's introspection hooks (`/_authn` for the bearer tier,
`/_session-authn` for the session tier) each emit four owner headers on every
allow — `X-Owner-Id` and `X-Owner-Email` (never empty), and the percent-encoded
`X-Owner-Name` and `X-Owner-Picture` (either MAY be empty) — plus `X-Client-Id`
on the bearer tier. Every location in this fragment that forwards identity today
captures **all four** owner headers with `auth_request_set` and re-emits them
with a single `proxy_set_header` per name (the identity-hygiene property: one
`proxy_set_header` per header name replaces any client-smuggled inbound value).
Variable names stay unique per service because all fragments are included into
one apex server block; github follows its existing `$github_owner` /
`$github_session_owner` convention:

- The **bearer-gated mount prefix** `location /srv/github/` (`/_authn`) captures
  `$github_owner` ← `$upstream_http_x_owner_email`, `$github_owner_id` ←
  `$upstream_http_x_owner_id`, `$github_owner_name` ←
  `$upstream_http_x_owner_name`, `$github_owner_picture` ←
  `$upstream_http_x_owner_picture`, and `$github_client` ←
  `$upstream_http_x_client_id`; it forwards `X-Owner-Id $github_owner_id`,
  `X-Owner-Email $github_owner`, `X-Owner-Name $github_owner_name`,
  `X-Owner-Picture $github_owner_picture`, and `X-Client-Id $github_client`.
- The **session-gated bare mount root** `location = /srv/github/`
  (`/_session-authn`) captures `$github_session_owner` ←
  `$upstream_http_x_owner_email`, `$github_session_owner_id` ←
  `$upstream_http_x_owner_id`, `$github_session_owner_name` ←
  `$upstream_http_x_owner_name`, `$github_session_owner_picture` ←
  `$upstream_http_x_owner_picture`; it forwards `X-Owner-Id
  $github_session_owner_id`, `X-Owner-Email $github_session_owner`, `X-Owner-Name
  $github_session_owner_name`, `X-Owner-Picture $github_session_owner_picture`
  (today it forwards only email).

The session-gated `location /srv/github/static/`, the open PRM bootstrap, and
the `= /srv/github/pr` denial forward **no** identity today and are unchanged.
Downstream consumption of `X-Owner-Id` by the github binary is out of scope for
this pass; this Decision governs fragment forwarding only.

**`etc/manifest.env`** declares `APP=github`, `MOUNT=/srv/github/`, `PORT=3203`,
`MCP=true`, `DEFAULT=false`, and **no** `FEED=` line and no outbox retention keys
(non-producer, D1). `etc/deploy.env` mirrors the other connectors' workstation
routing.

## Rejected

- **Keep serving from the embedded `internal/web` package.** It works, and
  `root project/design/D29.md` sanctions it, so this is not a correctness fix. But
  it leaves `github` and `artifacts` as the only two trees off the disk-served
  `share/www` shape, and that divergence has a standing cost: every reader carries
  a second mental model of how a page is served, and every landing/static test
  needs a bespoke substrate (an offline `LandingHandler`/`StaticHandler` call)
  instead of the suite's shared "assemble the real router, render through the WWW
  site" pattern. Joining the majority shape is the whole point of this pass.
  Rejected.
- **A github-bespoke fidelity harness** — a byte-for-byte **golden fixture**, a
  **structural-contract** marker check, a **token-integrity** subset check, and a
  hostile-input **HTML-escaping** test. No sibling service carries any of them, and
  they did not prevent the very drift they were meant to catch: earlier phases
  shipped a github-only landing variant (blue eyebrow, viewport-pinned Home link,
  renamed detail classes) with every one of those guards green, because a golden
  regenerated from a drifted template pins the drift rather than catching it. The
  suite verifies its landing by the shared crm-style test set over a **byte-exact
  canonical clone** rendered through the assembled router; github now does the
  same, and the golden fixture is gone.
- **A consent binary (`cmd/consent`) and OAuth callback routes.** gmail needs them
  for per-user Google OAuth; the GitHub App is installed once at the org, so there
  is no consent step and no callback — omitted entirely.
- **A `/feed` block in the fragment.** github publishes no events and mounts no
  feed; a block would guard a route that does not exist.
- **A shared landing handler.** The suite convention is each app owns its landing
  page, template, and static assets under its own tree; github ships its own copy
  of `tokens.css` and the fonts under `share/www/static/`.

## Verification

- `R-WI06-793Q` — `GET /` on github's **real assembled router** (built through
  appkit with the loaded `share/www` site) returns `200 text/html; charset=utf-8`;
  for a distinct service/version pair rendered through `rt.WWW().Render`, the
  service name appears exactly three times (title, `<h1>` heading, and the Service
  detail cell) and the running version exactly once.
- `R-WJ82-L0UF` — the composition root declares `Spec.WWW = true` and serves the
  landing and the `/static/` subtree from the on-disk `share/www` tree through
  appkit's WWW loader (`Router.WWW()`), with **no** `internal/web` embed package in
  the module. Asserted by building the assembled router over the real `share/www`
  tree and confirming both that the landing renders and that a `share/www` static
  asset is served through the chassis mount; a router assembled with `WWW=false` or
  against a missing `share/www` root fails.
- `R-WKFY-YSL4` — the rendered landing HTML links **only app-local** static
  assets: it contains `href="static/tokens.css"` (mount-relative) and none of the
  forbidden forms — an origin-absolute `href="/static/tokens.css"`, a
  cross-service `dashboard` / `/srv/dashboard` reference, or any `http://` /
  `https://` asset URL. Asserted on the body rendered through `rt.WWW().Render`.
- `R-WLNV-CKBT` — the rendered document head preloads the two self-served woff2
  fonts (`space-grotesk.woff2`, `ibm-plex-sans.woff2`) as
  `<link rel="preload" as="font" type="font/woff2" crossorigin href="static/fonts/…">`,
  and the `tokens.css` served by the assembled router references each of those
  files via a matching self-served `url('fonts/…')`.
- `R-WMVR-QC2I` — the rendered landing shows the canonical suite layout: the
  eyebrow `GitHub connector`, the exact one-line description above, the
  `<section aria-labelledby="page-title">`-wrapped `<h1 id="page-title">github</h1>`,
  and a `<dl aria-label="Service details">` Service / Version / API grid whose

  page and uses the canonical anchored styling: a `.home` rule set
  `position: absolute; top: var(--space-8);` within a `position: relative` `main`,
  with `.home:hover, .home:focus-visible { color: var(--color-text); }`. Asserted
