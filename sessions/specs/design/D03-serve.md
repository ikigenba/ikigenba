# D03-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, the terms sessions serves on, the listener's life, the one step the start takes over the store before it serves, and the route table its one handler keeps with the identity each route takes. It is accounts' serve path less the host: no host is chosen, built or reached, so no route runs a host command, and the one thing the start does over the store is the store's startup refresh, `FinishRefresh` (`D04-store`), which finishes any summary refresh left incomplete before sessions serves. The identity gate keeps the suite's shape (appkit's `identity.Optional` before the pages and the shared files, `identity.Require` at `/mcp`), while the manifest's `guests = false` has nginx gate every path as well. This document declares `internal/server` and `internal/web`. Outcomes cited as outcome N are those of /home/mgreenly/Documents/ikigenba-sessions.md, and decisions cited as DN are those of /home/mgreenly/Documents/ikigenba-sessions-decisions.md.

`D01-layout-and-run-seam` declares the run seam (`cli.Process`, `cli.Run`), the settings (`settings.Settings`, `settings.Read`, `settings.Defaults`, `Drain()`), the database path, `pages.ServiceName`, the identity and display string of a run, and the root package's `Migrations()`; `D02-cli` the exit codes (`ExitSuccess`, `ExitUsage`, `ExitServerFailed`); `D04-store` the store (`store.New`, `store.Config`, the error `store.ErrUnreachable` it fails with and the line `store.Unreachable` sessions answers when its database cannot be read or written), the stored summaries, their refresh, the startup refresh `FinishRefresh` and how a test leaves a refresh incomplete; `D06-pages` the pages (`pages.Load`, `pages.Handler`, `pages.Config`), the sign-in redirect a guest gets and the addresses it is built on; `D07-tools` the tools (`tools.Register`, `tools.Config`) and their answers; `D08-trail` the trail, `service.started`, `service.stopping`, the refresh's event `refresh.finished` among it and its recorder `trail.Refresh` with `trail.Result`; `D09-on-a-space` the manifest's `guests = false`, the nginx fragment and the environment. appkit's `db`, `telemetry`, `identity`, `page`, `mcp` and `services` packages own their contracts; this document wires them and restates none of them.

## The services file

`IKIGENBA_SERVICES` names the services file. sessions uses two of its entries: `auth`, read afresh per request by the pages for the banner's links and a guest's sign-in address (`D06-pages`), and `telemetry`, appkit's sink's, which reads the file afresh on each delivery. sessions builds no sibling client (it calls none), so `Run` reads nothing from the file at the start: it hands the path on. With `IKIGENBA_SERVICES` unset, naming no file, or naming one `services.Read` refuses, the start is not refused and sessions serves as with a file holding no entry; the pages then build their addresses on the request's scheme and host (`D06-pages`). A changed `auth` entry reaches the next page request.

## The terms sessions serves on

sessions serves only on a listening socket it inherits, taken as `sd_listen_fds(3)` documents, and reports readiness with `READY=1` to `NOTIFY_SOCKET` as `sd_notify(3)` documents. It trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them, and trusts the MCP gateway to have forwarded them (`D09-on-a-space`); the `turns` command reaches `/mcp` through the gateway (D4) like any agent. Every request has an id: the one nginx or the caller set, or one appkit's telemetry middleware draws from `Process.Rand`.

The manifest declares `guests = false`, so nginx admits no request without a credential, to the pages and to `/mcp` alike. A request with no `X-User-Id`, or an empty one, is a **guest**, whatever `X-User-Email` it carries; on a host none reaches sessions, and the handler still answers one as below.

## The route table

Every request goes through appkit's `telemetry.Middleware` over `Config.Telemetry`, which records the request pair (`D08-trail`) and puts the request's caller on its context. Then, by `URL.Path` alone, compared by hand, so nothing is cleaned and nothing redirected:

- exactly `/mcp`: `identity.Require`, then the MCP server `Config.MCP`, on which the tools of `D07-tools` are registered with `tools.Register` once, when the handler is built. A guest is answered `identity.Require`'s 500 with `identity.MissingBody`, which on a host never happens because nginx demands a credential first.
- a path beginning `/_appkit/`: `identity.Optional`, then `page.Static()`; nothing there is private.
- every other path: `identity.Optional`, then the page handler, `pages.Handler` over `pages.Config` (`D06-pages`), which sends a guest a 302 to the sign-in address and draws the page for a signed-in user. So `/`, `/about`, `/tools`, and `/nope`, `/mcp/`, `/events` and `/_appkit` all reach it.

There is no guest route and there are no bus paths: sessions emits no bus event and accepts none, so `/events` and `/declarations` are paths like any other. Only `/mcp` changes anything: a page reads the store and changes nothing (outcome 9). No answer on any route carries `Set-Cookie`.

The handler is built from a `web.Config` carrying what its routes need: the banner source, the MCP server, the services file's path, the store, the writer and the settings. `web.Handler` builds the page handler and the tool registration from it, both over the same store; which fields each of `pages.Config` and `tools.Config` takes is that document's.

## The start

With `Args` empty, `Run` checks the settings (`D01-layout-and-run-seam`), then whether exactly one socket was passed in, with the diagnostics below. It removes the three `LISTEN_*` variables, takes descriptor 3, and opens the database with `db.Open` at `state/sessions.db` with `sessions.Migrations()` and `Process.Now`; a failure is `sessions: cannot open database state/sessions.db: ` and the reason, exit 1. It builds the store with `store.New`, the run's writer, and records `service.started`, so that it is the first event of every run.

Then it runs the store's startup refresh, `FinishRefresh` (`D04-store`), and records its outcome with `trail.Refresh`, the roots `FinishRefresh` answered and `trail.Result` of its error (`D08-trail`), whether it succeeded or failed. The stored summaries are refreshed inside each write, and after a rule, price or away-limit change every root is recomputed in pages of bounded size, each page its own transaction, before the changing tool answers (`D04-store`); a process that dies between two pages leaves a refresh incomplete. The startup refresh finishes it, so that no request is answered over summaries a dead process left half-recomputed: once `READY=1` is sent, `list_sessions`, `total_sessions` and the landing page reflect every change that was answered, and every change that was written but whose refresh the crash cut short. A startup refresh that fails, the database having failed under it so that `FinishRefresh` answers an error matching `store.ErrUnreachable`, refuses the start with the line `sessions: ` followed by `store.Unreachable`, `ExitServerFailed` (`D02-cli`), before `READY=1` and before any connection is accepted, as scrapes refuses a settling that fails; the trail then holds `service.started` and one `refresh.finished` whose `result` is `trail.ResultFailed`, and nothing a request recorded. That answer is described, not required (see Recorded decisions). A refresh with nothing left incomplete changes nothing and answers 0; that every start records `refresh.finished`, and where among the run's events, is `D08-trail`'s.

Then it builds the handler, calling `Process.MCP` once with the writer, sends `READY=1`, and serves. Nothing else is read from the store at the start, and sessions works nothing in the background.

## Stopping

When `ctx` is done (in the binary, on `SIGTERM` or `SIGINT`, the signal's name being the cause) `Run` drains the server for `DRAIN_SECONDS` (`settings.Settings.Drain()`), shuts the writer down with the cause's text as `service.stopping`'s reason, and closes the database. From shortly after the drain deadline on, `Run` hands the sink nothing: an event not handed to it by then is never handed to it, and reaches standard error, if at all, only as appkit's `undelivered event` line, and only before the drain line; after the drain line `Run` writes nothing more to standard error, not even after it returns. A drain that runs out on requests is `sessions: stopped with <n> request(s) unfinished`, exit 1. Serving that fails before `ctx` is done, as when the listener's `Accept` fails, is `sessions: ` and the error, exit 1. A request still in progress when the drain runs out has its context done. A push cut off there is one write transaction (`D04-store`), so it either answered or changed nothing; a rule, price or away-limit change cut off between two refresh pages is left incomplete for the next start's refresh.

## The binary

The one exec'ing test proves the wiring of `cmd/sessions`. `D01-layout-and-run-seam` states what the binary does at the start (it creates `state/sessions.db` in its working directory, keeps what it records across runs, carries the display string in `serverInfo` and `service.started`, carries the release and commit to the about screen) and that `SIGTERM` stops it cleanly; this document adds the bare start with no socket and the stop on `SIGINT`.

## Recorded decisions

- **`internal/server` is the suite's, unchanged**: one function and one error type, declared here because `D01-layout-and-run-seam` assigns the listener's life to this document.
- **Pages use `identity.Optional` and a 302 to sign in, and the manifest says `guests = false` so nginx gates too**, as accounts. `identity.Require` sits at `/mcp` alone, so a guest that reaches a page anyway is sent to sign in by the page handler (`D06-pages`) rather than answered a 500.
- **No guest route and no bus paths.** sessions has no record a visitor without a credential may reach (P6: the page is behind auth like every other app's), and it neither emits nor accepts a bus event, so no path sits outside identity and `/events` and `/declarations` are the page handler's like any other path.
- **`/_appkit/` goes through `identity.Optional`**: the shared files are not private, and the wrapper changes no answer.
- **`web.Config` is accounts' less `Host`**: sessions reaches no host, so the tools and the pages share one store and nothing else; that they read one store is `D01-layout-and-run-seam`'s requirement, not restated here.
- **`web.Config` carries the settings whole**, though the handler reads none of them; a setting a handler needs later is added to `settings` without reshaping `web.Config`.
- **`web.Config` carries no clock and no random source**: the present moment that places the current week is the store's, through `store.Config` (`D04-store`), the writer holds its own, and sessions mints no id of its own.
- **`Run` reads nothing from the services file at the start**: it builds no sibling client, so the file is read only by the pages, per request, and by appkit's sink, per delivery. A missing or unreadable file never stops the start.
- **The `/mcp` server's identity is `main`'s**: `Run` mounts the server `Process.MCP` returns and builds none itself; `main` names it `pages.ServiceName` with the display string (`D01-layout-and-run-seam`). This document requires only that `Run` calls `MCP` once with the run's writer and mounts what it returns.
- **The drain line is the last line on `Stderr`, though a cut-off request may still record an event**, as accounts: `Run` hands the writer a `Stderr` of its own that passes lines to `Process.Stderr` until `Run` closes it and drops them after, and closes it on every return once the writer is shut down, before the drain line when there is one. A serving failure before `ctx` is done is the third way out, and `server.Serve` answers it with an error that is not a `*server.DrainError`.
- **The startup refresh runs before `READY=1`** (departure from accounts, whose start reads nothing from the store before ready; the sheet's ruling that serve finishes an incomplete refresh before it listens). Serving first would answer reads over summaries a crash left half-recomputed, which breaks the contract that an answered change is reflected. A failure refuses the start, in scrapes' settling class: the database opened but cannot be written, so serving would answer every read with the store's unreachable line anyway, and exit 1 lets systemd restart it. The risk is candidates' (its facts fill outran systemd's 90-second start timeout before ready): an incomplete refresh recomputes every root, which grows with the sessions held. It is bounded per page and normally empty, since only a crash mid-recompute leaves one, so it stays before ready; if the space grows past what one start can recompute in the timeout, the refresh moves after `READY=1` with the reads answering over the old summaries until it ends, a change recorded then with a new id.
- **The startup refresh is `D04-store`'s `FinishRefresh`, and its event `D08-trail`'s**: its signature, what marks a refresh incomplete (R-C3UW-DYAT), how a test leaves one so, and when it fails are `D04-store`'s; `refresh.finished`, its attributes, and that every start records it after `service.started` and before any request's events (R-VGUN-Z27V) are `D08-trail`'s. This document requires only what a run answers once ready.
- **The start's answer to a failing startup refresh is described, not required**, as accounts records for a failing database after `db.Open`: `cli.Run` opens its own handle, and sessions/AGENTS.md provokes a database failure only with `SetFailing(true)` on, or by closing, a handle the test hands in, so no permitted test can fail the startup refresh under `Run`. `D04-store` offers no fixture a test reaches through `Dir` alone that makes `FinishRefresh` fail: its one refresh fixture (R-C3UW-DYAT, the empty pair set through `DB.Write`) leaves a refresh incomplete that `FinishRefresh` then completes, and `FinishRefresh` fails only as every method does (R-2KXQ-MCYG), on a done context or a failing or closed handle. The behaviour stays as described above: `trail.Refresh` with `trail.Result` of the error, the line `sessions: ` and `store.Unreachable`, `ExitServerFailed`, never ready, no connection accepted. If `D04-store` later declares such a fixture (a database a test's own `db.Open` made and changed through `DB.Write` so the refresh cannot complete), the refusal becomes a requirement here with a new id.
- **The drain's in-progress request is any request**: sessions has no host command a test can hold open, so a test holds a request in progress by sending its headers and not finishing its body; what the drain then does is accounts'.
- **The binary's bare start and `SIGINT` are stated here**, beside the `Run`-level requirements they exercise; the binary's other serve expectations are `D01-layout-and-run-seam`'s.

## Consumer tasks

`Run`, serving, calls `s, err := settings.Read(p.LookupEnv)`, checks the socket, unsets the three `LISTEN_*` variables and takes `ln, _ := p.Inherit(3)`; opens `d, err := db.Open(ctx, db.Config{Path: filepath.Join(p.Dir, "state", "sessions.db"), Migrations: sessions.Migrations(), Now: p.Now, Service: pages.ServiceName, Stderr: p.Stderr})`; builds `st := store.New(d, store.Config{...})` (`D04-store`) and `w := telemetry.New(...)`, the writer's `Stderr` being a gate over `p.Stderr` that passes lines until it is closed and drops them after; reads the path `IKIGENBA_SERVICES` names; calls `w.Ready()`, recording `service.started`; calls `n, err := st.FinishRefresh(ctx)` (`D04-store`) and `trail.Refresh(ctx, w, n, trail.Result(err))` (`D08-trail`), on success and on failure alike, answering a failure by writing `sessions: ` and `store.Unreachable` as one line, shutting the writer down and closing `d`, `ExitServerFailed`; builds `hd := web.Handler(web.Config{Banner: p.Banner, MCP: p.MCP(w), ServicesPath: path, Store: st, Telemetry: w, Settings: s})`; sends `READY=1`; and calls `server.Serve(ctx, ln, hd, s.Drain(), stop)`, `stop` calling `w.Shutdown(c, context.Cause(ctx).Error())`; closes the gate once `server.Serve` has returned, however it returned; answers a `*server.DrainError`, after closing the gate, by writing `sessions: ` and its text, `ExitServerFailed`; closes `d`.

`web.Handler(cfg)` calls `tools.Register(cfg.MCP, tools.Config{Store: cfg.Store, Telemetry: cfg.Telemetry})` once, loads `set, err := pages.Load()`, builds `pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, MCP: cfg.MCP})`, mounts `identity.Require(cfg.MCP)` at `/mcp`, `identity.Optional(page.Static())` under `/_appkit/` and `identity.Optional` over the page handler everywhere else, and returns `telemetry.Middleware(cfg.Telemetry, mux)`.

A test of the handler builds `web.Handler` over a store on its own database, a writer over a capture, a server from `mcp.NewServer` and `settings.Defaults()`, serves it with `httptest`, and sends raw requests with the identity headers set or left out, and `/mcp` calls through `mcp.Client`. A test of the start drives `cli.Run` with a listener, a `NOTIFY_SOCKET` it binds, a `Now`, a `Sleep` and a `Rand` it controls, a services file whose `auth` entry names a URL of its own, and, for the startup refresh, a `Dir` whose database its own store wrote and then left with a refresh incomplete through `DB.Write`, as `D04-store` R-C3UW-DYAT states; waits for `READY=1`; drives `/mcp` with `mcp.Client` and the pages with raw HTTP; rewrites the services file; cancels; and inspects the capture, the streams and the exit code. The exec'ing test runs the binary bare with no socket, and serving, stops it with `SIGINT`.
