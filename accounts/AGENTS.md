# accounts

An app of the Ikigenba platform: the business's SSH hosts, the accounts (customer businesses) placed on them and the users of each account, served at `accounts.<host>`. The module builds two binaries. `accounts` serves on the listening socket it is passed as descriptor 3 (`/run/ikigenba/accounts.sock` on a space), behind the host's nginx: it keeps its record in its own SQLite database, `state/accounts.db`, which is the source of truth; runs EC2 instances, Elastic IPs, EBS volumes and Route 53 records through the AWS SDK for Go v2 when the space's settings name the hosts, on an in-memory cloud with simulated hosts in a sandbox, and on none otherwise; offers its MCP tools at `/mcp` as the only API for the space's callers; offers the box tools to the users of its hosts, whose daemons forward them to `/accountsd/v1/box`; serves read-only pages to a signed-in user and the enrollment page at `/join?token=<token>` to anyone holding an invite link; and serves the daemon binary and the daemon protocol at `/accountsd` and below `/accountsd/`. `accountsd` runs as root on every host, pulls the host's desired state from accounts, makes the host match it and reports back; run under the name `accountsd-session` the same binary is the PAM session helper, and run under the name `accountsd-mcp` it is the box's stdio MCP server, which relays a host user's tool calls to the daemon's Unix socket. accounts calls no sibling and runs no program; outside the suite it reaches only AWS. The module path is `github.com/ikigenba/ikigenba/accounts`. The contract is the documents in `specs/design/`; this file restates none of it. accounts is an app, so it has no stories: its intent is the decisions document that delivered it, or what was agreed in conversation, together with its templates under `assets/`, and the design is the record.

This sub-project is spec-driven: `specs/design/` defines the contract, and the build run writes the Go source (both `cmd/accounts` and `cmd/accountsd` and everything under `internal/`), the tests, `go.mod`'s requirements and `go.sum`, the migrations under `migrations/` (`0001_accounts.sql`, kept byte for byte, `0002_hosts.sql`, `0003_bans.sql`, `0004_invites.sql`, `0005_host_records.sql` and `0006_kept_volumes.sql`), which the root package embeds, and everything under `etc/` (`etc/manifest.toml` and the nginx fragment `etc/nginx.conf`, whose bytes design states). The build run owns `go.mod` and `go.sum` and changes them as design and the Toolchain below say. It never writes `assets/`, `seed/`, `share/`, this `AGENTS.md`, the `Makefile` or `.golangci.yml`. `state/` is where a running accounts keeps `accounts.db` and, in a sandbox, `sandbox-cloud.json` and the simulated hosts' box sockets under `box/`, and where a person at a sandbox may drop `sandbox-bans`, which the simulated hosts read and remove; it is created at run time and never committed. See the `spec` and `build-spec` skills. Everything below is what the build run computes the gap and runs the gates against; it is written outside the run and read-only to it.

## Assets

`assets/` holds accounts' markup: Go `html/template` files, each opening with a comment naming the data it receives: `landing.html`, `host.html`, `tools.html`, `about.html`, `notfound.html` and `join.html`. Every page but one is shown only to a signed-in user, and a guest is sent to sign in; the exception is the enrollment page at `/join?token=<token>` (`join.html`), which answers a guest and a signed-in person alike, since the invite link is the credential. They are written by the user or the delivering agent, following the repository's `design/`, and are inputs to the spec: the build run reads them and never writes them. The code parses them into the set appkit's `page.Templates` returns and executes them by template name; it never writes markup of its own, not even a fragment or an error page. Go's `embed` reaches only files at or below the embedding package's directory, so the module's root package (the directory holding `go.mod`) embeds `assets/`, and design names what it exports.

Every word a person or an agent reads, and every class, id and attribute, lives in exactly one place, a template under `assets/` or a named copy constant in the source; a test and a requirement never spell one. Design names each template and the data it receives, never its text, hooks, markup or styles. A test proves a page by executing the named template with the data the design says and comparing, or by checking that a value the test supplied appears in the body; it never looks for a word or a tag. A change to copy or markup is an edit to the asset alone. A needed template that is missing or wrong, or a template that cannot show a state the design names, is an issue: the run files it in `specs/issues/` and never edits the asset to close it.

accounts holds no copy of the stylesheet, fonts, or licences; appkit's `page` package embeds and serves them. `share/icon.svg` is accounts' icon, shown in the banner's trail and on home: Tabler's `users` outline, without its class, width, height, or invisible bounding path, as `design/README.md` asks of a service icon. The build run never writes it. `devctl build` packs it beside `bin/` and `etc/`.

## Test files

The sub-project's tests are all `*_test.go` files in the module: the root package, `cmd/accounts`, `cmd/accountsd` and everything under `internal/` (`internal/valid`, `internal/settings`, `internal/cloud`, `internal/cloud/awssdk`, `internal/cloud/awshost`, `internal/cloud/memory`, `internal/protocol`, `internal/trail`, `internal/hostauth`, `internal/machine`, `internal/linux`, `internal/store`, `internal/ops`, `internal/daemonapi`, `internal/daemon`, `internal/sim`, `internal/tools`, `internal/box`, `internal/boxmcp`, `internal/pages`, `internal/join`, `internal/server`, `internal/web` and `internal/cli`). This is the file set the canonical gap greps for requirement ids:

```
grep -rhoE 'R-[A-Z0-9]{4}-[A-Z0-9]{4}' --include='*_test.go' . | sort -u
```

`specs/`, `assets/` and `share/` hold no `*_test.go`, so the design documents never enter the test side of the grep.

**No id-shaped literal in a fixture.** The grep cannot tell a requirement tag from any other string of that shape: such a literal anywhere in a `*_test.go` file counts as a covered id. accounts echoes back what callers, the cloud and the daemons give it — host, account and user names, uids, public keys and their comments, invite ids, tokens and links, instance, volume, allocation and change ids, ARNs, presigned URLs and their signatures, digests, report facts, user ids and emails, request ids, the services file's URLs — so a test that sends an id-shaped value lands one in the test file. No fixture carries one: not a header value, a query parameter, a tool argument, a fake cloud's answer, a fake resource id, a name, a key or its comment, a URL, a services file entry, a report, a JSON-RPC body, an event's payload, or an expected body.

## Test discipline

These rules govern the unit tests: everything `go test ./...` runs.

- Offline: no network beyond loopback and Unix sockets, no real credentials, no real AWS, and no real `sudo`, `opsctl`, account, group, mount, unit or file of the machine.
- Deterministic: time, randomness, and environment are injected; no test sleeps to wait for something. Clocks, timers and pauses are injected: a test hands in a `Now`, an `After`, a `Sleep` and a `Rand` it controls.
- No fixed ports: a test binds `127.0.0.1:0` or a Unix socket in a temporary directory.
- Isolated: a test touches only its own temporary directory, never the developer's home, config, `~/.aws`, or real state.

**Nothing leaves the test process but loopback.** No test reaches anything outside loopback, its own Unix sockets, its own temporary directory and the fakes and stubs it made. accounts has no HTTP client of its own toward siblings and calls none, and a test proves the absence by use, as design names: the `Process` shape, the variables `Run` looks up, and a services file naming every sibling on a listener that records each connection, none of which is reached.

**AWS is a fake, the memory cloud, or an in-memory transport.** No test reaches AWS, IMDS or a real credential, and no test calls `awssdk.Open` or `awshost.Open`, which load the SDK's default chain; their only callers are `cmd/accounts` and `cmd/accountsd`, and the finish line proves them. A test reaches the cloud one of the ways design names: a recording fake `cloud.Cloud` (or `Presigner`, `Metadata`) of its own that answers what it chooses; the memory cloud, `memory.New` over a path in the test's own temporary directory with a clock the test advances past each transition instead of waiting; or, for the adapters themselves, `awssdk.OpenWithLoader` and `awshost.OpenWithLoader` over a configuration with fake static credentials whose HTTP client is an in-memory transport answering EC2, Route 53, STS and IMDS with the test's own fixtures, never the default chain, the environment, IMDS or the network. Identity verification is proved over the memory cloud's STS (`c.Presigner(id)`, `c.CallerOf`) or a fake STS of the test's own. A `Run`-level test that sets the five hosts variables always hands its own fake as `Process.Cloud`; one in sandbox mode gets the memory cloud from its own `Dir`. The `Run`-level tests of the box path (design `D03-serve`, `D08-trail`) run in AWS mode, because a box request must be signed for a host the run holds: the fake's `CallerOf` accepts each identity header the test makes for that host's instance, each header dated at the run's `Now` and carrying a signature of its own, since the verifier refuses a replayed one.

**The host is a temporary root.** No test touches the real host's `/etc`, `/usr/local`, `/proc`, `/sys`, `/home`, `/srv`, `/data` or any device, and none runs as root. A test of `internal/linux` builds `linux.New(linux.Env{Root: t.TempDir(), Execute: rec.Execute, Now: clock, Fetch: fake.Fetch, Stderr: &errs})`: it writes the fixtures it needs (`etc/passwd`, `etc/group`, `etc/shadow`, `etc/os-release`, files under `proc/`, unit and configuration files) under that root, hands an `Execute` that records each command and answers what the test chooses and a `Fetch` that answers from memory, and proves a change by the files under the root, the commands recorded and the URLs fetched; the links `Apply` makes for the session helper and the box MCP server and the Claude Code files it writes land under that root too. `linux.Get` itself is tested against an `httptest` server on loopback. `linux.Session` is tested the same way, with a `getenv` the test gives it. No test hands `linux.Real()` to `linux.New` or `linux.Session`. The daemon's tests and the simulated hosts use `machine.NewMemory` with a `Sleep` and a `Now` the test controls.

**The run seam carries the process.** accounts binds nothing itself; it serves on the listener it is passed. Arguments, environment lookup and removal, the pid, the inherited listener, the output streams, the clock, the timer source, the pause between delivery attempts, the random source, the executable lookup, the cloud opener and the working directory come in through the run seam design declares (`cli.Run` with `cli.Process`), and tests inject them. A `Run`-level test sets the version string to one of its own and `Dir` to a temporary directory of its own, so the database and the memory cloud's file land there and never in the checkout, and sets `Executable` to a path in its own temporary tree. A test never reads or changes the real environment, clock, or randomness, and never leaves the inherited-listener step unset, since that would take the test process's real descriptor 3. The one exception is the working directory: a test that proves what an empty `Dir`, or the root package's `Assets`, `Etc`, `Migrations` or `Seed` does whatever the working directory is may `t.Chdir` into a temporary directory of its own, and such a test does not call `t.Parallel`. A test learns that the server is ready the way systemd does: it binds a Unix datagram socket in a short temporary directory (`os.MkdirTemp("", ...)`, since a Unix socket path is limited to 108 bytes and `t.TempDir()` can exceed it), names it in `NOTIFY_SOCKET`, and waits for `READY=1` with a deadline that fails the test. A test waits on the clock in two places only, because there the deadline is the behavior: a drain test, which keeps that wait to a few seconds, and a test of the stdio server's answer timeout, which hands `boxmcp.Serve` a `Config.Timeout` of a few milliseconds (design `D20-box-mcp`). The gates run offline as an ordinary user, with no systemd.

**The daemon's seam carries its process.** `daemon.Run` takes its HTTP client, presigner, metadata, machine, clock, pause and stderr in `daemon.Config`, and for the box socket its listener `Box`, the uid source `PeerUID` and the timer source `After`; a test serves a fake accounts on loopback with `httptest`, hands fakes for the rest and a `Sleep` that advances the clock, and asserts what the fake server received and what the machine holds. A test of the box socket listens on a Unix socket in a short temporary directory (`os.MkdirTemp("", ...)`) or hands a listener over `net.Pipe`, sets `PeerUID` to a function answering a uid it chose and `After` to one handing out channels it fires, and never waits out `daemon.BoxTimeout`. `daemon.Main` takes its arguments, environment lookup, stderr, executable lookup, trust roots and box socket path in `daemon.Process`, and the opener and machine as arguments; a test hands its own, with `Executable` naming a file in its temporary directory and `Socket`, when it serves the box socket, a path in its own short temporary directory, where the uid `daemon.KernelUID` reads is the test process's own. A `Main` test that reaches `Run` ends it by cancelling its context, never by waiting out a backoff.

**The state is an isolated directory.** Each test gives accounts a working directory inside a test-owned temporary directory, so the database and the memory cloud's file are the test's own. A test that needs a store opens its own database with appkit's `db.Open` at a path in its own temporary directory, with the root package's `Migrations()` and a clock it controls, closes the handle when it ends, and builds the store over that handle with `store.New`. Tests may create filesystem fixtures inside that temporary tree (a regular file named `state`, a file at `state/accounts.db` that is not a database, a database a test's own `db.Open` made and then changed through `DB.Write`, a memory cloud's file a test's own `memory.New` made, a file standing for the daemon binary and a symbolic link to it, the hosts' temporary roots and the stubs); nothing touches `/var/opt/ikigenba/accounts`, the checkout's `state/` or a shared file. A database failure is provoked with `SetFailing(true)` on the handle the store the test handed the server or handler was built over, or by closing that handle, as design names, never by corrupting the file or removing permissions. Tests prove accounts' use of the database, its schema, its store and its wiring, never SQLite's own guarantees (atomicity, durability, locking) and never appkit's `db` contract (opening, migrations, transactions, `db status`), which appkit's own tests prove; they prove what a store holds by reopening its path, never by reading tables.

**Time is driven, not waited out.** Every time accounts stamps, every step the engine defers, every transition of the memory cloud, every long poll and every simulated host's cycle is driven through the injected `Now` and `After`: a test advances the clock it handed in and fires the timers it handed out, never waits real seconds. A long poll is ended by the test's `After` or by `daemonapi`'s `Stop`, never by waiting out `protocol.LongPoll`. The engine is driven one pass at a time with `Pass` and `Scan`. The writer's pause between delivery attempts and the daemon's pauses, its wait for the one-header-a-second gate included, are the injected `Sleep`; a box connection's `daemon.BoxTimeout` is the daemon's injected `After`; the enrollment page's rate limiter refills by the clock it is built over (`join.NewLimiter`). A test that sleeps to age a record is a bug. A test waits for something it started to finish (an event reaching a capture, a fake server receiving a request) with a deadline that fails the test.

**Events come from the test's own sink.** Where a test observes the events accounts records, it hands accounts' writer appkit's `telemetry.Capture`, or a services file whose `telemetry` entry names a Unix socket the test holds, as design names. Every test builds its own database; no test depends on state another test made or on the order the tests run in.

**Environment variables, set by the test.** appkit's constructors read `IKIGENBA_SERVICES` (`services.Variable`) from the process environment; it is the one environment read accounts cannot route through the run seam, and in the binary only `main` makes it. A test that reaches such a read, directly or through an accounts constructor, first sets that variable with `testing.T.Setenv` to a services file it wrote or to the empty string, so the developer's environment never decides a result. It is the only variable an in-process test sets for accounts' own code; every variable `Run` reads (`DRAIN_SECONDS`, `IKIGENBA_SANDBOX`, `AWS_REGION`, the four `IKIGENBA_HOSTS_*` keys, the socket and readiness variables and `IKIGENBA_SERVICES`) reaches it through the `LookupEnv` the test gives it, `ACCOUNTS_URL` reaches `daemon.Main` through `daemon.Process.LookupEnv`, `ACCOUNTSD_SOCKET` (`boxmcp.EnvSocket`) reaches `boxmcp.Run` through the `getenv` the test gives it, and `PAM_TYPE` and `PAM_USER` reach `linux.Session` through the `getenv` the test gives it. The tests of `linux.Exec` may set `PATH` with `testing.T.Setenv`, to a directory of their own or to the empty string, to prove that `Exec` neither searches nor passes on the caller's `PATH`; a stub they put there must never run. The exec'ing test of `cmd/accounts` also sets `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` with `testing.T.Setenv`, so it may call appkit's `version.Read()` and the identity's `String()` under the same two values it composes into the child's environment; the commit it sets is longer than seven characters, so a `main` that skipped shortening would fail. Any test that sets a variable with `testing.T.Setenv` does not call `t.Parallel`.

**Process-wide state is not shared.** A test that changes process-wide state, such as the standard `log` package's output, restores it when it ends and does not call `t.Parallel`, so no other test's line lands in its buffer.

**Identity comes from headers the test sets.** appkit's `identity.Require` wraps `/mcp`, and `identity.Optional` the pages and `/_appkit/`; the daemon routes and `/join?token=<token>` take no person's identity. A test sets the identity headers to be a signed-in user, or omits `X-User-Id` to be a guest: at `/mcp` it exercises the missing-identity answer, on a page the redirect to sign in, and at `/accountsd`, below `/accountsd/` and at `/join?token=<token>` the same answer as with the headers. A box call's caller is not a header: `daemonapi` resolves the verified host and uid to a host user and serves the call as `box.ActorPrefix` followed by that user's name, whatever `X-User-Id` the request carries. It sets `Host` and `X-Forwarded-Proto` the way nginx does. Where it matters it acts as two users, and it proves that each change's event in the trail names its caller, by the capture, and that what it created is recorded with its caller's user id, by the record. A daemon's identity is the presigned header design names, made by the memory cloud's presigner or a fake of the test's own. What appkit's middleware and writer do is appkit's contract; accounts' tests prove only that its handlers are wired to them, by use.

**MCP through appkit's client.** A test drives `/mcp` the way a client would: it serves the handler it built on loopback or a Unix socket and calls it with appkit's `mcp.Client`, passing the caller whose identity headers the client forwards. The box servers are driven the same way: a test registers `box.RegisterUser` or `box.RegisterAdmin` on a server from `mcp.NewServer`, serves it inside `identity.Require`, and calls it with `mcp.Client` on behalf of `identity.Caller{UserID: box.ActorPrefix + name}`. Raw HTTP to `/mcp` is for what the client cannot send (a missing identity header, `server/discover`), never a substitute for the client. Assertions are on the `mcp.Result` and `mcp.ToolInfo` the client returns. accounts' tests never re-prove appkit's transport.

**Pages and the daemon routes are raw HTTP.** A test drives `/`, `/hosts/<name>`, `/tools`, `/about`, `/join?token=<token>`, `/accountsd`, the paths below `/accountsd/`, `protocol.BoxPath` among them with JSON-RPC bodies the test writes, and any other path as a browser or a daemon would: raw HTTP requests on the handler it built, served with `httptest` or on a Unix socket, with the headers the route takes, and never follows a redirect.

**The addresses are the test's own.** The banner's profile and sign-out addresses and a guest's sign-in address are built on the services file's entry `auth`, and the accounts URL and binding on its entry `accounts`, as design names, or, with none, as design says. A test chooses them: it writes a services file into its own temporary directory whose entries name URLs, or none, and hands its path in the config or names it in `IKIGENBA_SERVICES` through the `LookupEnv` it gives `Run`.

**No test runs the page's scripts.** Every page carries appkit's feedback script. The gates have no browser and no JavaScript engine, and adding one is an external dependency no one has approved, so a test asserts what a response body carries and never what a script would do with it.

**No test reads the checkout.** A test opens no file of this directory — no `.go` file, not `go.mod` or `go.sum`, nothing under `etc/`, `share/`, `assets/`, `migrations/` or `seed/` — and never parses or inspects source. It proves what the design declares by using it, the embedded files through the root package's `Assets`, `Etc`, `Migrations` and `Seed`. Handing `cmd/accounts` or `cmd/accountsd` to `go build` is not the test reading it.

**Which tests start a process.** No test starts a process except the three named here; tests under `internal/` never start `accounts` or `accountsd`. A stub accounts' own code runs is not a process the test starts. Any other test that builds, execs, waits on, or signals a process is a bug.

1. **The tests of `linux.Exec`**, in `internal/linux`, prove `Exec` itself (design `D15-machine`) by running, through `Exec`, `/bin/sh` scripts they wrote into their own temporary directory (which may write to stdout and stderr, read stdin and exit with a status the test chose) and a path that names no file. Nothing else in `internal/linux` reaches `Exec`.
2. **One exec'ing test of `cmd/accounts`.** The wiring in `cmd/accounts` can be proved no other way. It builds the binary into a temporary directory and runs it with `--version`, with `manifest`, with `bogus`, and bare with no socket passed in. For the serve case it stands in for systemd: it makes a Unix socket in a short temporary directory, passes it as `exec.Cmd.ExtraFiles[0]` (descriptor 3 in the child), and starts the child through `/bin/sh -c 'LISTEN_PID=$$ LISTEN_FDS=1 exec "$0"' <binary>`, because `LISTEN_PID` must be the child's own pid and `exec` keeps the shell's. The child runs in a test-owned temporary working directory, where it creates `state/`. Its environment is one the test composes, never the developer's: it never holds `AWS_REGION` or an `IKIGENBA_HOSTS_*` key, so the binary never reaches AWS, and it holds `IKIGENBA_SANDBOX` wherever design's binary requirements serve in sandbox mode, non-empty `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE`, and a `PATH` naming only a directory of the test's own. The test computes the release and commit it expects with `version.Read()` and the display string with its `String()` after setting the same two values with `t.Setenv`, so no test spells a version. Separately it runs `--version` with neither variable in the child's environment and expects exactly one empty line. The test waits for `READY=1`, makes the requests and tool calls design names for the binary over the socket, starts a later process over the same working directory where design asks what survives a restart, then stops the child with `SIGTERM`, and in a second run with `SIGINT`, asserting what design states. To prove that accounts runs no program (R-ETO0-MM7J), the `PATH` it composes names only a directory holding `/bin/sh` stubs named `sudo` and `opsctl` that record each run in the test's temporary directory and must never run; the test asserts their records are empty after the binary has exited. The binary's `--version` output, the MCP `serverInfo` and `service.started` all carry that display string, and the pages' footer the release and commit.
3. **One exec'ing test of `cmd/accountsd`.** It builds the binary into a temporary directory and runs it, in an environment it composes that holds no `ACCOUNTS_URL`, `PAM_TYPE`, `PAM_USER` or AWS variable, in the four cases design names (`D14-accountsd`, R-BGR6-LSZ9, R-KKV0-8QID), each of which ends before anything reaches IMDS, AWS, systemd, a socket or the machine's files: under its own name with an argument; under its own name with `ACCOUNTS_URL` absent; through a symbolic link named `accountsd-session` (`linux.SessionName`), made in the test's temporary directory, with neither PAM variable set, which must exit 0 having run nothing; and through a symbolic link named `accountsd-mcp` (`linux.MCPName`), made there too, with `ACCOUNTSD_SOCKET` naming a path in its temporary directory where nothing listens and one JSON-RPC `ping` line on stdin, whose stdout must be exactly what `boxmcp.Run` writes in process for the same input and which must exit 0. Everything else `daemon.Main`, `linux.Session` and `boxmcp.Run` do is proved in process with injected seams.

## Live tests

There are none. No test reaches outside the suite, AWS included, or runs as root: a fake, the memory cloud or an in-memory transport stands in for AWS, and a temporary root with a recording `Execute` and a `Fetch` answering from memory for the host. The sandbox runs accounts on the memory cloud with simulated hosts running the real `daemon.Run` loop, so the sandbox walk drives every page, tool and daemon route end to end without AWS. The real chain, AWS, IMDS, STS, real hosts, SSH, Claude Code's package repository and the space's nginx, is proved on a space, at the delivery's finish line.

## Gates

Run from this directory (`accounts/`), in order; every command must exit 0. No skipped tests, no disabled linters laundering a failure. A per-finding suppression comment (`//nolint` and the like) is a skip: the run never adds one; a finding it cannot fix, or believes is wrong, is filed as an issue.

1. `test -z "$(gofmt -l .)"` — fails if any file is unformatted (fix with `make fmt`)
2. `go build ./...`
3. `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o /dev/null ./cmd/accounts` — accounts' release build, static and cgo-free, the way `devctl build` builds it, which is why the SQLite driver must be pure Go
4. `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o /dev/null ./cmd/accountsd` — the daemon's release build for the hosts, static and cgo-free, the way `devctl build` builds an app's extra command; a daemon that cannot build for the hosts cannot ship, and one that cannot start there cannot be rolled back by accounts
5. `go test -race ./...`
6. `GOLANGCI_LINT_CACHE="$(git rev-parse --absolute-git-dir)/golangci-lint" golangci-lint run --allow-parallel-runners` — the cache lives in this worktree's git directory, so worktrees never share it, and `--allow-parallel-runners` lets gates for several sub-projects lint at once; `make lint` runs this form

Gate 6 also flags an undocumented `package main` (`revive`), an `http.Server` without `ReadHeaderTimeout` (`gosec` G112) and a subprocess launched with a variable program (`gosec` G204); all are fixed in code, never suppressed.

## Build

`make` builds `bin/accounts` and `bin/accountsd` from the checkout for the developer's machine (`make build`), `bin/accountsd` beside `bin/accounts`, where accounts looks for the daemon binary it serves. `make install` installs both into the Go bin directory, side by side for the same reason. `make fmt` rewrites unformatted files, and `make test` and `make lint` run the test and lint gates. The gates do not go through `make`: they call the Go tool directly, and the two tests that need a binary build their own into a temporary directory.

## Deploy

accounts ships in the suite release: `devctl build <sha|tag>` builds it with every other app, its part of the release holding `bin/accounts`, `bin/accountsd` (static, linux/arm64, as every app's extra command), `etc/` and `share/icon.svg`, and `devctl deploy <space> <sha|tag>` deploys that release; on a space accounts serves `/opt/ikigenba/current/accounts/bin/accountsd`. The preconditions of the hosts feature (infra applied, `devctl hosts set` on the operating space, opsctl writing `AWS_REGION` and the four `IKIGENBA_HOSTS_*` keys and accepting extra files in `bin/`) are design's (`D09-on-a-space`); every other space runs the same binary unconfigured. accounts is served at `accounts.<host>`, reaches IMDS and AWS's regional endpoints for EC2, Route 53 and STS from the space's instance role, and holds no secret of its own. The host's backup archives `state/` whole, so `accounts.db` is taken with it.
