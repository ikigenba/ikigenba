# D11-protocol

The daemon protocol: the wire between accounts and `accountsd`, the daemon on every host. A host's daemon pulls one document, the host's desired state, applies it, and posts back one report. This document owns package `internal/protocol`. It holds the paths, the two JSON documents and their member types, the size limits, the box path's query member and methods, the long-poll duration, the daemon's version form, the decoders both sides use, and the rule by which the protocol changes from one release to the next (outcome 23 of ikigenba-ssh-hosts.md). It also owns the report's schema (outcome 24's schema half). `protocol` imports no other package of accounts. It sits at the bottom of the import order, so both `internal/daemonapi` (`D13-daemon-endpoints`), which serves the protocol, and `internal/daemon` (`D14-accountsd`), which speaks it, import it without either importing the other. That is why `LongPoll` is declared here and not in either of them.

## The four paths

`BinaryPath` (`/accountsd`) serves the daemon's own binary, unauthenticated. `StatePath` (`/accountsd/v1/state`) answers the host's desired state, by long poll, with the query members `QueryAfter` and `QueryDigest`. `ReportPath` (`/accountsd/v1/report`) takes the report. `BoxPath` (`/accountsd/v1/box`) takes the box tools' requests that a host's daemon forwards for its SSH users. What each answers, and when, is `D13-daemon-endpoints`'. How a request proves which host it comes from is `D12-host-identity`'s. The path constants are declared here so that the server and the client spell them from one place.

## The box path

A user on a host reaches the box tools (`D19-box-tools`) through the host's daemon, which forwards each request to accounts under the host identity it already proves (`D14-accountsd` sends, `D13-daemon-endpoints` serves). The daemon posts to `BoxPath` with one query member, `QueryUID`, holding the caller's uid in decimal, and a `ContentJSON` body that is exactly one JSON-RPC 2.0 request whose `method` is `MethodToolsList` or `MethodToolsCall`, at most `MaxBoxRequest` bytes: the line the host's stdio client read, relayed byte for byte. accounts resolves the verified host and the uid to the user; it never reads a name or an account from the host. A 200 answer is one JSON-RPC response object of at most `MaxBoxAnswer` bytes, which the daemon relays byte for byte. Which statuses the daemon tells apart, and how it words each, is `D14-accountsd`'s. The method names are declared here because both sides spell them: accounts accepts only these two, and the host side forwards only these two.

The box path adds no member to `DesiredState` or `Report`. The daemon's local check before a forward needs each user's `uid`, `state` and `account` and each account's `state`, which the state already carries.

## Desired state

`DesiredState` is the whole document for one host. It holds the protocol number, the host's name, the host's version, the digest of the daemon binary accounts serves, the data volume's EBS id, the root and data sizes, the accounts placed on the host and their users, the host's SSH allowlist (addresses and CIDR prefixes its jail never bans, loopback left out because the jail always writes it), and its pending unbans (addresses to lift from the jail once). accounts builds it from its record (`D04-store`'s `Desired`, which also states the order: accounts by slug, users by name, keys sorted, allowlist and unbans sorted); `D13-daemon-endpoints` fills `Daemon`. Allowlist entries and unban addresses are in `D17-names-keys-sizes`' canonical forms; `D15-machine` refuses a state holding any other, or more than `MaxAllowlist` allowlist entries or `MaxUnbans` unbans. An account is `active` or `removed`. A pending account is sent as `active`, because the host must make its group before the account can turn active, and a failed one stays `active` until it is removed. A user is `active`, `locked` or `deleted`. The document is bounded by `D17-names-keys-sizes`' caps: at most 50 accounts and 200 users, each user with at most 10 keys of at most 512 bytes, and at most 50 allowlist entries and 50 unbans, each at most 43 bytes, a few KB together. That comes to about 1.1 MB, under `MaxStateBytes` (2 MiB).

## Report

`Report` is what the daemon posts each cycle. It carries the version the daemon tried (`Attempted`), the version it applied (`Applied`, 0 for none), the error of the attempt (empty on success), what the instance is, its load, memory and disks, its sessions, pending security updates and whether a reboot is wanted, its failed units, the use of each account slice, the last sign-in of each user who has signed in, the jail's current bans (`Ban`: the address, when it was banned and when the ban expires) with the total number of bans the jail holds, and the allowlist the jail is written with, loopback left out. `D15-machine`'s `Inspect` collects the facts and `D14-accountsd` fills in the versions, the error and its own digest. `D04-store`'s `RecordReport` keeps the latest report. `D06-pages` shows it and `D07-tools`' `host` returns it. Five lists can grow with the host: the failed units, the slices, the sign-ins, the bans and the allowlist. `Bounded` sorts each one and caps it, and it caps the error text, so a report is canonical and small on both sides. Bans are kept newest first, so the cap keeps the newest `MaxBans`; `BanTotal` still counts every ban, and `Bounded` never lets it fall below the number of bans the report listed before the cut. `DecodeReport` applies `Bounded`, so accounts never keeps more than the caps, whatever a daemon sends.

## Decoding

`DecodeState` (the daemon's) and `DecodeReport` (accounts') read one document from a body. Neither reads past its limit plus one byte. Each refuses three things: a body over its limit (`ErrTooLarge`), anything that is not exactly one JSON object of the right shape (`ErrMalformed`), and a `protocol` member other than `Version` (`ErrVersion`). Unknown members are ignored, absent members and members whose value is `null` read as their zero values, and member names match as `encoding/json` matches them (without regard to case, the last duplicate deciding). That is the standard decoder's behaviour, accepted rather than replaced by a stricter one. The state decoder also refuses a document with no host or a version below 1. It never judges an enumerated value such as an account's or a user's state. A daemon that cannot decode a document changes nothing, and that includes not updating itself. A decoder that refused a new state word would therefore strand every old daemon. What a daemon does with a word it does not know is `D15-machine`'s concern.

## The daemon's version

The daemon's version is the digest of its binary: `sha256:` followed by 64 lowercase hex digits. devctl builds a release with no `-ldflags`, so the binary cannot know which release it belongs to. A digest also tells a rollback apart from an upgrade. `Digest` computes it by streaming the bytes through one buffer of at most `DigestBuffer` bytes. accounts digests the binary it serves (`D13-daemon-endpoints`), and the daemon digests its own executable (`D14-accountsd`). An empty `Daemon` member means "do not update".

## Changing the protocol: expand, then contract

Hosts and accounts upgrade at different times. The protocol therefore changes the way every interface between releases does in this repository (root `AGENTS.md`): expand, then contract.

- Both sides ignore unknown members and read an absent member as its zero value. The decoders here guarantee this for every member.
- A member is added by its producer in one release and relied on by its consumer in the next. It is removed in the reverse order: the consumer stops relying on it in one release and the producer stops sending it in the next. A new value of an enumerated member is a new member for this rule. Accounts sends a new user or account state only in a release after the one whose daemon knows it.
- `protocol` stays `Version` (1) for every change that can be made this way. A change that cannot be made this way adds `/accountsd/v2/…` beside v1 for at least one release. v1 is removed only in a later release, after every daemon has updated itself. Daemons update within one cycle of an accounts deploy, because the digest a waiting poll compares changes and the poll answers at once.
- The self-update channel is frozen forever: `BinaryPath`, `StatePath`, and the `protocol`, `host`, `version` and `daemon` members of v1 state. A daemon of any age can always fetch v1 state, find a new digest and fetch the new binary. `DecodeState` accepts a document made of only those four members, so contracting every other member can never strand a daemon.

This rule is process, not code. Its testable half is in the requirements: the decoders' tolerance, the frozen names, and the minimal document. The other half binds the authors of later releases.

The SSH bans change (`allowlist` and `unban` in state; `bans`, `ban_total` and `allowlist` in the report) is the one recorded departure: it lands in a single release. Recorded decisions says why that is safe.

The box path is an expansion, a new path under v1 with no change to the state or the report, so `protocol` stays `Version`. An old accounts answers 404 on `BoxPath`, which a new daemon treats as "cannot reach accounts" (`D14-accountsd`). An old daemon never calls it.

## Bounded work

Each decoder reads at most its limit plus one byte, and holds the decoded document, which the caps bound. `Digest` holds one buffer of at most `DigestBuffer` (32 KiB) and the hash state, whatever the binary's size. `Bounded` keeps at most `MaxFailedUnits`, `MaxSlices`, `MaxSignIns`, `MaxBans` and `MaxAllowlist` entries and `MaxErrorBytes` of error text; it holds the receiver and one sorted copy of each list, both within `MaxReportBytes` once decoded. Each of these is a requirement below. How the daemon gathers the bans without holding the jail's whole list is `D15-machine`'s (one line and at most `MaxBans` bans at once). `MaxBoxRequest` and `MaxBoxAnswer` bound what each side of the box path holds for one forward; `D13-daemon-endpoints` reads a request body through a limit of `MaxBoxRequest`, and `D14-accountsd` reads an answer through a limit of `MaxBoxAnswer`.

## Recorded decisions

- **Long poll of 45 seconds.** `LongPoll` sits under nginx's default `proxy_read_timeout` of 60 seconds (nginx's `ngx_http_proxy_module` documentation), which opsctl's generated server block leaves unset, with a 15-second margin for the apply that follows. It is declared here because both `D13-daemon-endpoints` (how long a poll waits) and `D14-accountsd` (its client timeout, `LongPoll + 15s`) depend on it, and neither may import the other.
- **Limits.** `MaxStateBytes = 2 MiB` is about twice the bounded document's worst case. `MaxReportBytes = 256 KiB` comfortably holds 200 sign-ins, 50 slices, 100 failed units and a 4 KiB error. `MaxBinaryBytes = 64 MiB` is several times a static Go binary built with the AWS SDK's STS and IMDS clients. `MaxErrorBytes = 4096` keeps a whole command diagnostic while bounding the page. `MaxFailedUnits = 100`. `MaxSlices = 50` and `MaxSignIns = 200` equal `D17-names-keys-sizes`' `MaxAccountsPerHost` and `MaxUsersPerHost`. They are restated here as wire bounds because `protocol` may import nothing; if those caps change, these change with them. `MaxAllowlist = 50` and `MaxUnbans = 50` restate `D17-names-keys-sizes`' `MaxAllowlistPerHost` and `MaxUnbansPerHost` the same way. `MaxBans = 200` is the decisions document's cap on the bans a report lists; the jail may hold more, which `BanTotal` counts. The new members grow the state by at most 50 entries of each list, a few KB, and the report by at most 200 bans of about 100 bytes each and 50 entries, about 25 KB; both stay under the existing `MaxStateBytes` and `MaxReportBytes` (the report's worst case was well under half its limit), so no limit changes.
- **Box limits.** `MaxBoxRequest = 64 KiB` holds any box tool request many times over (the largest argument is a key line of at most 512 bytes) and sits below the 1 MiB body appkit's MCP server reads. `MaxBoxAnswer = 1 MiB` is above the largest answer a box tool can give, about 309 KB (a 200-user `users` list with the longest recorded creators, plus a 64 KiB string id); `D19-box-tools` and `D13-daemon-endpoints` show why every answer stays under it, so the box lists are not paged.
- **The SSH bans change lands in one release** (outcome 17 of ikigenba-ssh-bans.md), a departure from expand-then-contract above, which would have the producer add the members in one release and the consumer rely on them in the next. It is safe in every old and new mix. An old accounts ignores the report's new members, as the decoders guarantee. A new daemon handed an old accounts' state, during a rollback, reads the absent `allowlist` and `unban` as empty: for one cycle it writes the jail with loopback only and lifts nothing, then sees the old digest and rolls itself back. An old daemon never applies a new state before updating, because the new release's digest answers its poll at once and it updates first; the exception is an update that fails, when the old daemon applies the state without the members it does not know and reports the version applied, so `D04-store` drops the pending unban without its having been lifted. That is accepted: the agent sees the ban still in the report and calls `unban_ip` again. Splitting the change over two releases would buy nothing the agent cannot already recover.
- **Ban times are `time.Time` in UTC to the second**, like `Booted` and `At`. The daemon converts fail2ban's local-time output (`D15-machine`).
- **Typed decoders and `Bounded` in `protocol`.** They are additions inside this package. They give one definition of "a valid v1 document" for both sides, and of the caps accounts trusts. The sibling precedent is appkit's `paging` package, where one package owns both ends of a token.
- **Times as `time.Time`.** `Booted` and a sign-in's `At` are `time.Time`, so both sides use the standard JSON form (RFC 3339). A producer writes UTC to the second. An absent member decodes as the zero time, which the pages show as empty.
- **Version is a digest, not the display string** (a departure `D14-accountsd` records). Sibling apps report their version with appkit's `version` display string. accounts' daemon cannot: devctl's build stamps nothing into a binary, and a host must also tell a rollback from an upgrade. The digest does both.
- **Unknown enumerated values pass through.** If the decoder refused them, it would block the self-update that teaches a daemon the new value.

## Consumer usage

The consumer tasks that touch this surface, written against exactly these names:

- Daemon first boot (task 2): `D14-accountsd` digests its own executable with `protocol.Digest(f)` and requests `BinaryPath` and `StatePath + "?" + QueryAfter + "=0&" + QueryDigest + "=" + digest`. It reads the answer with `protocol.DecodeState(body)`, gets a `DesiredState` back, and changes nothing on `ErrTooLarge`, `ErrMalformed` or `ErrVersion`.
- Daemon applies and reports (task 3): the daemon fills `Report{Protocol: protocol.Version, Attempted: s.Version, Applied: …, Error: …, DaemonVersion: digest, …}` from `Machine.Inspect` (`D15-machine`), calls `r.Bounded()`, and posts it as `ContentJSON` to `ReportPath`. accounts decodes it with `protocol.DecodeReport(body)` (`D13-daemon-endpoints`), maps `ErrTooLarge` to 413 and the other two errors to 400, and records it (`D04-store`'s `RecordReport`).
- Users and accounts (tasks 4–6): `D04-store`'s `Desired` builds `DesiredState{Protocol: Version, Host, Version, DataVolume, RootGB, DataGB, Accounts: []Account{{Slug, GID, State: AccountActive}}, Users: []User{{Name, Account, UID, State: UserLocked, Keys}}}`. `D13-daemon-endpoints` sets `Daemon` to its digest and encodes the document with `encoding/json`.
- Self-update (task 13): the waiting poll answers when `QueryDigest` differs from accounts' digest. The daemon downloads `BinaryPath` up to `MaxBinaryBytes` and checks it against `DesiredState.Daemon`. Its next report's `DaemonVersion` equals `Daemon`.
- The report page (task 3): `D06-pages` builds its view from `Report`'s members (`Root`, `Data` as `Disk`; `Slices` as `[]Slice`; `Bans` as `[]Ban`, `BanTotal`, `Allowlist`), and `D07-tools`' `host` returns them.
- SSH bans: `D04-store`'s `Desired` also fills `Allowlist: []string{"192.0.2.0/24"}` and `Unban: []string{"198.51.100.7"}`, each `[]string{}` when empty. `D15-machine` checks the state against `MaxAllowlist` and `MaxUnbans`, lifts each `Unban` address and every banned address an `Allowlist` entry covers, at most `MaxBans` per cycle, and its `Inspect` fills `Report{…, Bans: []Ban{{Address: "192.0.2.77", Banned: …, Expires: …}}, BanTotal: n, Allowlist: […]}`, keeping at most `MaxBans` bans while counting all.
- A box forward: `D14-accountsd` posts the request line, at most `MaxBoxRequest` bytes, as `ContentJSON` to `BoxPath + "?" + QueryUID + "=" + strconv.FormatInt(uid, 10)` with its identity header, for a request line whose `method` is `MethodToolsList` or `MethodToolsCall`, and reads at most `MaxBoxAnswer` bytes of the answer. `D13-daemon-endpoints` serves `BoxPath`, refuses any other method and reads at most `MaxBoxRequest` bytes of the body.
