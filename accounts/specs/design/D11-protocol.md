# D11-protocol

The daemon protocol: the wire between accounts and `accountsd`, the daemon on every host. A host's daemon pulls one document, the host's desired state, applies it, and posts back one report. This document owns package `internal/protocol`. It holds the paths, the two JSON documents and their member types, the size limits, the box path's query member and methods, the long-poll duration, the daemon's version form, the decoders both sides use, and the rule by which the protocol changes from one release to the next (outcome 23 of ikigenba-ssh-hosts.md). It also owns the report's schema (outcome 24's schema half), and the wire half of host backups (ikigenba-host-backups.md): the prefixes under which a host's backups are kept, the state's backup member and the report's backup facts. `protocol` imports no other package of accounts. It sits at the bottom of the import order, so both `internal/daemonapi` (`D13-daemon-endpoints`), which serves the protocol, and `internal/daemon` (`D14-accountsd`), which speaks it, import it without either importing the other. That is why `LongPoll` is declared here and not in either of them.

## The four paths

`BinaryPath` (`/accountsd`) serves the daemon's own binary, unauthenticated. `StatePath` (`/accountsd/v1/state`) answers the host's desired state, by long poll, with the query members `QueryAfter` and `QueryDigest`. `ReportPath` (`/accountsd/v1/report`) takes the report. `BoxPath` (`/accountsd/v1/box`) takes the box tools' requests that a host's daemon forwards for its SSH users. What each answers, and when, is `D13-daemon-endpoints`'. How a request proves which host it comes from is `D12-host-identity`'s. The path constants are declared here so that the server and the client spell them from one place.

## The box path

A user on a host reaches the box tools (`D19-box-tools`) through the host's daemon, which forwards each request to accounts under the host identity it already proves (`D14-accountsd` sends, `D13-daemon-endpoints` serves). The daemon posts to `BoxPath` with one query member, `QueryUID`, holding the caller's uid in decimal, and a `ContentJSON` body that is exactly one JSON-RPC 2.0 request whose `method` is `MethodToolsList` or `MethodToolsCall`, at most `MaxBoxRequest` bytes: the line the host's stdio client read, relayed byte for byte. accounts resolves the verified host and the uid to the user; it never reads a name or an account from the host. A 200 answer is one JSON-RPC response object of at most `MaxBoxAnswer` bytes, which the daemon relays byte for byte. Which statuses the daemon tells apart, and how it words each, is `D14-accountsd`'s. The method names are declared here because both sides spell them: accounts accepts only these two, and the host side forwards only these two.

The box path adds no member to `DesiredState` or `Report`. The daemon's local check before a forward needs each user's `uid`, `state` and `account` and each account's `state`, which the state already carries.

## Desired state

`DesiredState` is the whole document for one host. It holds the protocol number, the host's name, the host's version, the digest of the daemon binary accounts serves, the data volume's EBS id, the root and data sizes, the accounts placed on the host and their users, the host's SSH allowlist (addresses and CIDR prefixes its jail never bans, loopback left out because the jail always writes it), its pending unbans (addresses to lift from the jail once), and the hosts domain (`Domain`), under which the host's name is `<host>.<domain>`; an empty `Domain` tells the daemon to leave the host's hostname alone; and the team template's URL and ref (`TemplateURL`, `TemplateRef`), which a host clones when it creates an account's folder or a user's home (see The team template). accounts builds it from its record (`D04-store`'s `Desired`, which also states the order: accounts by slug, users by name, keys sorted, allowlist and unbans sorted); `D13-daemon-endpoints` fills `Daemon`, and `Domain` from its configuration, since the store knows no settings. What the daemon does with `Domain` is `D15-machine`'s. Allowlist entries and unban addresses are in `D17-names-keys-sizes`' canonical forms; `D15-machine` refuses a state holding any other, or more than `MaxAllowlist` allowlist entries or `MaxUnbans` unbans. An account is `active` or `removed`. A pending account is sent as `active`, because the host must make its group before the account can turn active, and a failed one stays `active` until it is removed. A user is `active`, `locked` or `deleted`. The document is bounded by `D17-names-keys-sizes`' caps: at most 50 accounts and 200 users, each user with at most 10 keys of at most 512 bytes, and at most 50 allowlist entries and 50 unbans, each at most 43 bytes, a few KB together, and one domain name, which `MaxStateBytes` bounds like every member. With the backup member's credential sets, the worst answer comes to about 2.06 MB, about 40 KB under `MaxStateBytes` (2 MiB); `D13-daemon-endpoints` counts it, encodes the answer without HTML escaping so that a key comment's worst character costs two bytes, and states the bound as a requirement.

## Report

`Report` is what the daemon posts each cycle. It carries the version the daemon tried (`Attempted`), the version it applied (`Applied`, 0 for none), the error of the attempt (empty on success), what the instance is, its load, memory and disks, its sessions, pending security updates and whether a reboot is wanted, its failed units, the use of each account slice, the last sign-in of each user who has signed in, the jail's current bans (`Ban`: the address, when it was banned and when the ban expires) with the total number of bans the jail holds, the allowlist the jail is written with, loopback left out, the host's static hostname as the daemon read it (`Hostname`, empty when the host has none), and, at its end, the template commit each account's folder was seeded from (`Seeds`) and each user's home file came from (`Homes`), for the creations this daemon made (see The team template). `D15-machine`'s `Inspect` collects the facts and `D14-accountsd` fills in the versions, the error and its own digest. `D04-store`'s `RecordReport` keeps the latest report. `D06-pages` shows it and `D07-tools`' `host` returns it. Five lists can grow with the host: the failed units, the slices, the sign-ins, the bans and the allowlist, and the backup members add three more (see Backups). `Bounded` sorts each one and caps it, and it caps the error text and the OS name, so a report is canonical and small on both sides. Bans are kept newest first, so the cap keeps the newest `MaxBans`; `BanTotal` still counts every ban, and `Bounded` never lets it fall below the number of bans the report listed before the cut. `DecodeReport` applies `Bounded`, so accounts never keeps more than the caps, whatever a daemon sends.

## Backups

Host backups keep each account's files, databases and each host's SSH host key in one S3 bucket. The protocol carries what the daemon needs to back up and restore, and what it found.

**Prefixes.** `AccountPrefix(slug)` (`accounts/<slug>/`) holds everything of one account, `FilesPrefix(slug)` (`accounts/<slug>/files`) is its restic repository and `DataPrefix(slug)` (`accounts/<slug>/data`) the root of its Litestream replicas. `HostPrefix(host, seq)` (`hosts/<host>/<seq>/`) is the host key's repository, keyed by the host's `Seq` as well as its name, so a later host that reuses a name never restores or deletes an earlier host's key. They are declared here because both sides spell them: accounts' session policies (`D21-backup-access`), its state (`D04-store`), its deletes (`D10-operations`) and its name check (`D07-tools`), and the daemon (`D15-machine`). The daemon takes the host prefix from the state as given and never builds it.

**State.** `DesiredState` gains `Backup` (`backup`), a pointer: nil means "no backups", which is what an old accounts sends by omitting it. `Backup` holds the bucket and region, the backup `Settings` (a copy of the store's), the host's `Credentials` and one `AccountCredentials` per account, all filled by `D13-daemon-endpoints` at answer time from `D21-backup-access`; and the host prefix, the running close's id (`Close`, empty when none), a whole-host restore (`Restore`, a `HostRestore`: the replace operation's id and each account with its gid and the database paths last reported) and the pending partial restores (`Restores`, each a `RestoreRequest` of kind `RestoreDatabase` or `RestoreFiles`, `User` empty for the account folder), all filled by `D04-store`'s `Desired`. Credentials are short-lived session credentials; accounts never stores them and the daemon keeps them only in memory and root-only files (`D15-machine`).

**Report.** `Report` gains three members at its end: `Backups`, one `AccountBackup` per account; `HostBackup`, the host key repository's facts; and `Restores`, one `RestoreResult` per partial restore the state asked for. An `AccountBackup` holds the last snapshot, the snapshots the repository holds as Unix seconds newest first, the last integrity check, the last files, prune or check error, the databases (each a `Database`: path below the account folder, earliest restorable time, newest write the replica holds, last time the replica held every write, error), counts and times computed over all the account's databases so they stay true when the list is cut, and two `Step`s: the account's final backup of a close and its restore in a replace from backup. A `Step` carries the operation id, a state (`StepPending`, `StepDone`, `StepFailed`), a time and a code (`CodeNotEmpty`, `CodeFailed` or empty), never free text, so `D10-operations` decides from `CodeNotEmpty` without reading words; the text is in the account's or host's `Error`. `D15-machine`'s `Inspect` fills these, `D04-store`'s `RecordReport` folds them, `D06-pages` and `D07-tools` show them. A backup problem never touches the report's `error`.

**Caps.** `Bounded` caps the new lists too: `MaxBackupAccounts` accounts, `MaxSnapshots` snapshot times each, `MaxDatabases` database entries in the whole report, `MaxRestores` results. Each cap on a backup string is on its encoded length, the length of `encoding/json`'s output for it with its quotation marks, since that writes `<`, `>`, `&` and control bytes as six bytes each: an error is cut to `MaxBackupError`, a database whose path exceeds `MaxDatabasePath` is dropped (still counted in `DatabaseTotal`), and a result whose copy path exceeds `MaxCopyPath` loses its copy and is made `StepFailed`. `D17-names-keys-sizes`' `MaxDatabasePath` and `MaxRestorePath` are measured the same way, so every path a tool accepts survives `Bounded`.

## The team template

A host clones the team template's repository when it creates an account's folder or a user's home, and seeds them from it (`D15-machine`). The service never fetches the template or ships its files; it only tells the host where the template is and records what the host used.

**State.** `DesiredState` gains `TemplateURL` (`template_url`) and `TemplateRef` (`template_ref`) at its end, the store's team-template setting at the time of the answer (`D04-store`'s `Desired`), changed only through `set_team_template` (`D07-tools`). A changed setting raises no host's version, since it changes nothing on a host until a later creation, and every creation raises the version, so the state that carries a creation carries the setting current when it was answered. An empty member means the default: `DefaultTemplateURL`, `https://github.com/ikigenba/team-template`, and `DefaultTemplateRef`, `main`. That is what a daemon of this release does when the release before's accounts, during a rollback, sends a state without them, so a creation still clones the default template; the defaults are declared here because both the store, which answers them while no setting is stored, and the daemon need them, and `protocol` is the one package both import.

**Report.** `Report` gains `Seeds` (`seeds`), one `Seed` per account whose folder this daemon seeded, with the account's gid and the commit (`Commit`, `git rev-parse HEAD` in the clone, 40 lowercase hex digits, or 64 for a SHA-256 repository), and `Homes` (`homes`), one `Home` per user whose home file this daemon wrote, with the user's uid and the commit. They are keyed by gid and uid because accounts never reuses either, so a slug or name placed again is never credited with an earlier one's commit. The daemon keeps them in memory and reports them in every report while the state still names the account or user, because only the store knows whether it already holds them; `D04-store`'s `RecordReport` records the first commit reported for each and never changes it. `Bounded` drops an entry whose id is not positive or whose commit is not of either form, keeps one entry per id, sorts by id and caps them at `MaxSeeds` (50, `MaxAccountsPerHost`) and `MaxHomes` (200, `MaxUsersPerHost`).

## Decoding

`DecodeState` (the daemon's) and `DecodeReport` (accounts') read one document from a body. Neither reads past its limit plus one byte. Each refuses three things: a body over its limit (`ErrTooLarge`), anything that is not exactly one JSON object of the right shape (`ErrMalformed`), and a `protocol` member other than `Version` (`ErrVersion`). Unknown members are ignored, absent members and members whose value is `null` read as their zero values, and member names match as `encoding/json` matches them (without regard to case, the last duplicate deciding). That is the standard decoder's behaviour, accepted rather than replaced by a stricter one. The state decoder also refuses a document with no host or a version below 1. It never judges an enumerated value such as an account's or a user's state. A daemon that cannot decode a document changes nothing, and that includes not updating itself. A decoder that refused a new state word would therefore strand every old daemon. What a daemon does with a word it does not know is `D15-machine`'s concern.

## The daemon's version

The daemon's version is the digest of its binary: `sha256:` followed by 64 lowercase hex digits. devctl builds a release with no `-ldflags`, so the binary cannot know which release it belongs to. A digest also tells a rollback apart from an upgrade. `Digest` computes it by streaming the bytes through one buffer of at most `DigestBuffer` bytes. accounts digests the binary it serves (`D13-daemon-endpoints`), and the daemon digests its own executable (`D14-accountsd`). An empty `Daemon` member means "do not update".

## Changing the protocol: expand, then contract

Hosts and accounts upgrade at different times. The protocol therefore changes the way every interface between releases does in this repository (root `AGENTS.md`): expand, then contract.

- Both sides ignore unknown members and read an absent member as its zero value. The decoders here guarantee this for every member.
- A member is added by its producer in one release and relied on by its consumer in the next. It is removed in the reverse order: the consumer stops relying on it in one release and the producer stops sending it in the next. A new value of an enumerated member is a new member for this rule. Accounts sends a new user or account state only in a release after the one whose daemon knows it.
- `protocol` stays `Version` (1) for every change that can be made this way. A change that cannot be made this way adds `/accountsd/v2/…` beside v1 for at least one release. v1 is removed only in a later release, after every daemon has updated itself. Daemons update within one cycle of an accounts deploy, because the digest a waiting poll compares changes and the poll answers at once.
- The self-update channel is frozen forever: `BinaryPath`, `StatePath`, and the `protocol`, `host`, `version` and `daemon` members of v1 state. A daemon of any age can always fetch v1 state, find a new digest and fetch the new binary. `DecodeState` accepts a document made of only those four members, so contracting every other member can never strand a daemon.

This rule is process, not code. Its testable half is in the requirements: the decoders' tolerance, the frozen names, and the minimal document. The other half binds the authors of later releases.

Four changes are recorded departures, each landing in a single release; Recorded decisions says why each is safe:

- The SSH bans change: `allowlist` and `unban` in state; `bans`, `ban_total` and `allowlist` in the report.
- The host names change: `domain` in state; `hostname` in the report.
- The host backups change: `backup` in state; `backups`, `host_backup` and `restores` in the report.
- The team template change: `template_url` and `template_ref` in state; `seeds` and `homes` in the report; and `MaxReportBytes` raised to 320 KiB.

Both directions of the backups change are observable here. A previous release's state, with no `backup`, decodes with `Backup` nil, and a previous release's report, with none of the three new members, decodes with them empty (both requirements below). A new document read by the previous release's decoders loses only the new members, because those decoders ignore unknown members (R-U6VF-GCXW, unchanged since then), and every member the previous release declared keeps its name, type, order and meaning.

The weekly-retention change is an expansion, not a departure: `Settings` gains `weekly`, which the previous release's daemon ignores and which a daemon of this release reads as 0 from the previous release's accounts, passing then no weekly keep (`D15-machine`). `monthly` stays, sent as 0 by this release, only because the previous release's daemon passes it to restic and this release's daemon reads it from the previous release's accounts; removing it is later work, in the order above.

The box path is an expansion, a new path under v1 with no change to the state or the report, so `protocol` stays `Version`. An old accounts answers 404 on `BoxPath`, which a new daemon treats as "cannot reach accounts" (`D14-accountsd`). An old daemon never calls it.

## Bounded work

Each decoder reads at most its limit plus one byte, and holds the decoded document, which the caps bound. `Digest` holds one buffer of at most `DigestBuffer` (32 KiB) and the hash state, whatever the binary's size. `Bounded` keeps at most `MaxFailedUnits`, `MaxSlices`, `MaxSignIns`, `MaxBans` and `MaxAllowlist` entries and `MaxErrorBytes` of error text, and `OS` within 256 bytes encoded, and of the backup members at most `MaxBackupAccounts` accounts with `MaxSnapshots` snapshot times each, `MaxDatabases` database entries in all and `MaxRestores` results, every backup string within its encoded cap; the result marshals within the budget below (a requirement measured on a worst-case report). It holds the receiver and one sorted copy of each list, both within `MaxReportBytes` once decoded. `Hostname` is kept as it is, uncut: it is one string, which `DecodeReport`'s limit bounds whatever a daemon sends, and a real host's is at most 64 bytes. Each of these is a requirement below. How the daemon gathers the bans without holding the jail's whole list is `D15-machine`'s (one line and at most `MaxBans` bans at once). `Bounded` keeps at most `MaxSeeds` seeds and `MaxHomes` homes, each one id and one commit of at most 64 bytes. `MaxBoxRequest` and `MaxBoxAnswer` bound what each side of the box path holds for one forward; `D13-daemon-endpoints` reads a request body through a limit of `MaxBoxRequest`, and `D14-accountsd` reads an answer through a limit of `MaxBoxAnswer`.

## Recorded decisions

- **Long poll of 45 seconds.** `LongPoll` sits under nginx's default `proxy_read_timeout` of 60 seconds (nginx's `ngx_http_proxy_module` documentation), which opsctl's generated server block leaves unset, with a 15-second margin for the apply that follows. It is declared here because both `D13-daemon-endpoints` (how long a poll waits) and `D14-accountsd` (its client timeout, `LongPoll + 15s`) depend on it, and neither may import the other.
- **Limits.** `MaxStateBytes = 2 MiB` was about twice the bounded document's worst case when it was chosen; `D13-daemon-endpoints`' recount, with every key comment at its worst encoding and the backup member, leaves about 40 KB under it. `MaxReportBytes`, 256 KiB when chosen and 320 KiB since the team template change (below), comfortably holds 200 sign-ins, 50 slices, 100 failed units and a 4 KiB error. `MaxBinaryBytes = 64 MiB` is several times a static Go binary built with the AWS SDK's STS and IMDS clients. `MaxErrorBytes = 4096` keeps a whole command diagnostic while bounding the page. `MaxFailedUnits = 100`. `MaxSlices = 50` and `MaxSignIns = 200` equal `D17-names-keys-sizes`' `MaxAccountsPerHost` and `MaxUsersPerHost`. They are restated here as wire bounds because `protocol` may import nothing; if those caps change, these change with them. `MaxAllowlist = 50` and `MaxUnbans = 50` restate `D17-names-keys-sizes`' `MaxAllowlistPerHost` and `MaxUnbansPerHost` the same way. `MaxBans = 200` is the decisions document's cap on the bans a report lists; the jail may hold more, which `BanTotal` counts. The new members grow the state by at most 50 entries of each list, a few KB, and the report by at most 200 bans of about 100 bytes each and 50 entries, about 25 KB; both stay under the existing `MaxStateBytes` and `MaxReportBytes`, so no limit changes. The host backups change recounts the report's worst case, every string at its worst escaping, at 125,679 bytes for these members and 225,641 bytes with the backup members, 36,503 bytes under the 256 KiB `MaxReportBytes` then was (see the budget decision below). The host names change adds one `domain` string to the state and one `hostname` string to the report, which hostname(5) limits to 64 characters on a real host (the kernel's limit); neither changes a limit.
- **Box limits.** `MaxBoxRequest = 64 KiB` holds any box tool request many times over (the largest argument is a key line of at most 512 bytes) and sits below the 1 MiB body appkit's MCP server reads. `MaxBoxAnswer = 1 MiB` is above the largest answer a box tool can give, about 309 KB (a 200-user `users` list with the longest recorded creators, plus a 64 KiB string id); `D19-box-tools` and `D13-daemon-endpoints` show why every answer stays under it, so the box lists are not paged.
- **The SSH bans change lands in one release** (outcome 17 of ikigenba-ssh-bans.md), a departure from expand-then-contract above, which would have the producer add the members in one release and the consumer rely on them in the next. It is safe in every old and new mix. An old accounts ignores the report's new members, as the decoders guarantee. A new daemon handed an old accounts' state, during a rollback, reads the absent `allowlist` and `unban` as empty: for one cycle it writes the jail with loopback only and lifts nothing, then sees the old digest and rolls itself back. An old daemon never applies a new state before updating, because the new release's digest answers its poll at once and it updates first; the exception is an update that fails, when the old daemon applies the state without the members it does not know and reports the version applied, so `D04-store` drops the pending unban without its having been lifted. That is accepted: the agent sees the ban still in the report and calls `unban_ip` again. Splitting the change over two releases would buy nothing the agent cannot already recover.
- **The host names change lands in one release** (decision P2 of ikigenba-host-names-decisions.md), a departure from expand-then-contract above, as the SSH bans change was. The daemon ships inside accounts and updates itself to the digest accounts names, so it cannot lag a release for long. Both decoders ignore unknown members, so an old daemon ignores `domain` and an old accounts ignores `hostname`. A daemon given no domain leaves the hostname alone, so a new daemon handed an old accounts' state, which has no `domain`, renames nothing, and an old and new mix works in both directions. A rollback therefore never renames a host: the hostname a new release set stays until a later release sets it again. Splitting the change over two releases would buy nothing.
- **The host backups change lands in one release** (backups plan, section 4.3), a departure from expand-then-contract above, as the SSH bans and host names changes were: the daemon of the release that sends `backup` is the one that reads it, and accounts relies on `backups`, `host_backup` and `restores` in the release that adds them. Absence means "no backups", so every mix works but one, a cost `D09-on-a-space` records as accepted: a replace from backup caught by a rollback after its old instance is retired and before admission is sent its accounts and users by the release before, whose daemon formats the new volume and seeds new folders before the host's data is restored; after the roll-forward the per-account emptiness check refuses to restore over them, the replace fails, and the operator replaces from backup again onto a fresh volume. An old daemon ignores `backup` and reports none, so its accounts read `none`, a close never completes (an open cancels it) and restores stay pending until it updates, which it does within a cycle. A new daemon handed an old accounts' state, during a rollback, finds `Backup` nil, stops its Litestream units and reports `machine.NoCredentials` (`D15-machine`) until it rolls itself back, also within a cycle. An old accounts' `DecodeReport` drops the three new members and its stored body loses them. The lock of a close travels as `locked` users, a value every daemon knows, so an old daemon applies it without `backup`. Splitting the change over two releases would buy nothing.
- **Report budget recounted, worst-escaped; `MaxDatabases` stays 50.** `store.RecordReport` stores the re-marshalled report and refuses one over `MaxReportBytes` (`D04-store`), so `Bounded`'s output must already fit, whatever the daemon writes within its types and the documented limits of its sources. The count takes every string at its worst escaping (`encoding/json` writes `<`, `>`, `&` and control bytes as six bytes, `\` and `"` as two), every integer at 19 digits (no member is negative), every float at 25 characters (`-0.0000012345678901234567`) and every time as a producer writes it, UTC to the second (22 bytes with quotes). Existing members: the error, 4,096 bytes at six each, 24,578; 100 failed units, each a unit name of up to 255 characters (systemd.unit(5): "The total length of the unit name including the suffix must not exceed 255 characters"), whose allowed characters include `\`, two bytes each, 50,801; 200 bans of about 125 bytes (a 45-byte address and two times), 25,001; 200 sign-ins of 72 bytes, 14,401; 50 slices of 122 bytes, 6,101; 50 allowlist entries, 2,301; the scalars, with `os` cut by `Bounded` to 256 bytes of encoded length (`PRETTY_NAME`, which os-release(5) does not bound; the fixture's control bytes give 254), `kernel` and `hostname` at 64 bytes (uname(2) and hostname(5)) at six bytes a byte, four AWS ids and the digest at 80 bytes, numbers, disks and member names, about 2,500; together 125,679 bytes, against the plan's estimate of 110 KB. New members: an account entry without databases is 1,172 bytes (slug 34, 32 snapshot times as 12-digit integers, the widest a time `encoding/json` can write gives, 416, four times, the 256-byte error, two counts, two steps of about 95, names), times 50 is 58,600; a database entry is 627 bytes (path 256, error 256, three times, names), times 50 is 31,350; the host member 507; a restore result 959 (copy 640, error 256, id, state), times 10 is 9,601; together about 100 KB. The total is 225,641 bytes, 36,503 bytes under `MaxReportBytes` (262,144), above the 32 KiB margin the plan asks for, so `MaxDatabases` stays 50 and no other cap moves. The recount was made by marshalling that report with the standard library (go1.26) in a scratch program; R-VBTK-6GRT states the same report, with the team template's seeds and homes added later (below), and the bound `MaxReportBytes - 32 KiB`, so a cap or member that later grows the worst case fails a test. The margin above that bound was thin (3,735 bytes); the team template change recounted it and raised `MaxReportBytes` (below).
- **State budget.** The `backup` member adds 51 credential sets, at most `MaxDatabases` restore paths and `MaxRestores` requests. AWS publishes no maximum for a session token (STS API reference, `AssumeRole` and the `Credentials` type), so `D13-daemon-endpoints` caps each set's three strings at its `MaxCredentialBytes` (2,048 bytes encoded) and answers a larger set as zero; a real set, measured against the backup role, encodes them in about 1,166 bytes (key id 20, secret 40, token about 1,100 characters), about 1.2 KB with its member names, well under the cap, though `D13-daemon-endpoints` counts that size as unproven until `D09-on-a-space`'s finish-line check observes it. With that cap the worst answer is about 2.06 MB, about 40 KB under `MaxStateBytes`, which does not change; the count and the requirement are `D13-daemon-endpoints`'.
- **`Bounded` cuts `OS` to 256 bytes of encoded length** (group B pick). `D15-machine` reads `PRETTY_NAME` through its capture limit and nothing else bounded it, so a hostile or broken `/etc/os-release` could push a re-marshalled report past `MaxReportBytes`, which `D04-store` would refuse; the cut makes the budget's assumption true on both sides and closes a gap the previous release already had. The cut is the backup errors' rule, at the same 256 bytes, written as a number rather than a new constant because no other document needs it. `kernel` and `hostname` stay uncut: the kernel and hostname(5) bound them at 64 bytes.
- **Encoded length, quotes included.** A backup string's cap is on the length of `encoding/json`'s `Marshal` of it, its two quotation marks included, so the budget is a sum of the bytes on the wire. `D17-names-keys-sizes`' `MaxDatabasePath` and `MaxRestorePath` must be measured the same way for every accepted path to survive `Bounded`.
- **Snapshot times as Unix seconds.** `Snapshots` is `[]int64`, never escaped and 12 digits at most for any time `encoding/json` can write, where 32 `time.Time` strings would cost twice as much.
- **Prefix functions here.** The bucket layout is spelt by both sides and by four documents on accounts' side; `protocol` is the one package both import. `HostPrefix` carries the host's `Seq` (backups pick 20); the daemon uses the state's `host_prefix` as given.
- **`MaxBackupAccounts = 50`** restates `D17-names-keys-sizes`' `MaxAccountsPerHost`, as `MaxSlices` does, because `protocol` imports nothing; `MaxRestores = 10` is the cap `D17-names-keys-sizes`' `MaxRestoresPerHost` restates.
- **Ban times are `time.Time` in UTC to the second**, like `Booted` and `At`. The daemon converts fail2ban's local-time output (`D15-machine`).
- **Typed decoders and `Bounded` in `protocol`.** They are additions inside this package. They give one definition of "a valid v1 document" for both sides, and of the caps accounts trusts. The sibling precedent is appkit's `paging` package, where one package owns both ends of a token.
- **Times as `time.Time`.** `Booted` and a sign-in's `At` are `time.Time`, so both sides use the standard JSON form (RFC 3339). A producer writes UTC to the second. An absent member decodes as the zero time, which the pages show as empty.
- **Version is a digest, not the display string** (a departure `D14-accountsd` records). Sibling apps report their version with appkit's `version` display string. accounts' daemon cannot: devctl's build stamps nothing into a binary, and a host must also tell a rollback from an upgrade. The digest does both.
- **Unknown enumerated values pass through.** If the decoder refused them, it would block the self-update that teaches a daemon the new value.

- **The team template change lands in one release** (team-template delivery), a departure from expand-then-contract above, as the bans, host names and backups changes were. Both decoders ignore unknown members. An old daemon ignores `template_url` and `template_ref`: the release-106 daemon, in the minutes before it updates itself under the new accounts, seeds a new folder or home from the template copy it embeds (`v2`), and reports no commit, so that account or user shows none; accepted, since the daemon updates within one cycle of the deploy. A new daemon handed an old accounts' state, during a rollback, finds both empty and clones `DefaultTemplateURL` at `DefaultTemplateRef`, so creation still works, then rolls itself back within a cycle; the old accounts drops `seeds` and `homes`, so a creation in that cycle records no commit. Nothing the previous release reads is removed: every member it declared keeps its name, type, order and meaning.
- **`MaxReportBytes` raised from 256 KiB to 320 KiB** (team-template delivery). The new lists add, at their worst (50 seeds and 200 homes, each id at 19 digits and each commit at 64 hex digits), 26,020 bytes, measured by marshalling them with the standard library; the report's worst case becomes 251,661 bytes, past the 229,376 bytes that 256 KiB less the plan's 32 KiB margin allows. At 320 KiB (327,680 bytes) the margin is 76,019 bytes, and R-VBTK-6GRT's bound, `MaxReportBytes - 32 KiB`, is met with 43,251 to spare. Cutting the lists shorter was rejected: a fact cut from one report has no later report to ride in when the lists stay full. The raise is a provider's expansion shipped with its use: the release-106 accounts, during a rollback, refuses with 413 only a report beyond 256 KiB, which only a host near every cap at once can send, and the new daemon rolls back within a cycle.

## Consumer usage

The consumer tasks that touch this surface, written against exactly these names:

- Daemon first boot (task 2): `D14-accountsd` digests its own executable with `protocol.Digest(f)` and requests `BinaryPath` and `StatePath + "?" + QueryAfter + "=0&" + QueryDigest + "=" + digest`. It reads the answer with `protocol.DecodeState(body)`, gets a `DesiredState` back, and changes nothing on `ErrTooLarge`, `ErrMalformed` or `ErrVersion`.
- Daemon applies and reports (task 3): the daemon fills `Report{Protocol: protocol.Version, Attempted: s.Version, Applied: …, Error: …, DaemonVersion: digest, …}` from `Machine.Inspect` (`D15-machine`), calls `r.Bounded()`, and posts it as `ContentJSON` to `ReportPath`. accounts decodes it with `protocol.DecodeReport(body)` (`D13-daemon-endpoints`), maps `ErrTooLarge` to 413 and the other two errors to 400, and records it (`D04-store`'s `RecordReport`).
- Users and accounts (tasks 4–6): `D04-store`'s `Desired` builds `DesiredState{Protocol: Version, Host, Version, DataVolume, RootGB, DataGB, Accounts: []Account{{Slug, GID, State: AccountActive}}, Users: []User{{Name, Account, UID, State: UserLocked, Keys}}}`. `D13-daemon-endpoints` sets `Daemon` to its digest and encodes the document with `encoding/json`.
- Self-update (task 13): the waiting poll answers when `QueryDigest` differs from accounts' digest. The daemon downloads `BinaryPath` up to `MaxBinaryBytes` and checks it against `DesiredState.Daemon`. Its next report's `DaemonVersion` equals `Daemon`.
- The report page (task 3): `D06-pages` builds its view from `Report`'s members (`Root`, `Data` as `Disk`; `Slices` as `[]Slice`; `Bans` as `[]Ban`, `BanTotal`, `Allowlist`), and `D07-tools`' `host` returns them.
- SSH bans: `D04-store`'s `Desired` also fills `Allowlist: []string{"192.0.2.0/24"}` and `Unban: []string{"198.51.100.7"}`, each `[]string{}` when empty. `D15-machine` checks the state against `MaxAllowlist` and `MaxUnbans`, lifts each `Unban` address and every banned address an `Allowlist` entry covers, at most `MaxBans` per cycle, and its `Inspect` fills `Report{…, Bans: []Ban{{Address: "192.0.2.77", Banned: …, Expires: …}}, BanTotal: n, Allowlist: […]}`, keeping at most `MaxBans` bans while counting all.
- Host names: `D13-daemon-endpoints` sets `DesiredState.Domain` to its configured hosts domain (`"hosts.example.com"`), empty when unconfigured, as it sets `Daemon`; `D04-store`'s `Desired` leaves it empty. `D15-machine`'s `Apply` makes the static hostname `s.Host + "." + s.Domain` when `Domain` is non-empty and leaves it alone otherwise, and its `Inspect` fills `Report{…, Hostname: "host01.hosts.example.com"}`. `D06-pages` shows `Hostname` in the report view, and `D07-tools`' `host` returns it as the report's `hostname`.
- A box forward: `D14-accountsd` posts the request line, at most `MaxBoxRequest` bytes, as `ContentJSON` to `BoxPath + "?" + QueryUID + "=" + strconv.FormatInt(uid, 10)` with its identity header, for a request line whose `method` is `MethodToolsList` or `MethodToolsCall`, and reads at most `MaxBoxAnswer` bytes of the answer. `D13-daemon-endpoints` serves `BoxPath`, refuses any other method and reads at most `MaxBoxRequest` bytes of the body.
- Backups in the state: `D04-store`'s `Desired` sets `s.Backup = &protocol.Backup{HostPrefix: protocol.HostPrefix("host01", 7), Close: closeID, Restore: &protocol.HostRestore{ID: opID, Accounts: []protocol.RestoreAccount{{Slug: "acme", GID: 20000, Databases: []string{"data/app.db"}}}}, Restores: []protocol.RestoreRequest{{ID: opID, Account: "acme", Kind: protocol.RestoreDatabase, Path: "data/app.db", AsOf: t}}}`; `D13-daemon-endpoints` fills `Bucket`, `Region`, `Settings: protocol.Settings{EveryMinutes: 60, Hourly: 24, Daily: 7, Weekly: 5, WindowDays: 35, FilesStaleMinutes: 120, DatabaseStaleMinutes: 10, CheckDays: 7}`, `Host` and `Accounts: []protocol.AccountCredentials{{Account: "acme", Credentials: protocol.Credentials{AccessKeyID, SecretAccessKey, SessionToken, Expires}}}` from `D21-backup-access`, whose session policies name `protocol.AccountPrefix("acme")` and `s.Backup.HostPrefix`. `D15-machine` reads `protocol.FilesPrefix("acme")` for the restic repository and `protocol.DataPrefix("acme")` for the replicas, and treats `s.Backup == nil` as no backups.
- Backups in the report: `D15-machine`'s `Inspect` fills `Report{…, Backups: []protocol.AccountBackup{{Account: "acme", Snapshot: t, Snapshots: []int64{t.Unix()}, Databases: []protocol.Database{{Path: "data/app.db", Oldest: t0, Written: t, Synced: t}}, DatabaseTotal: 1, Final: protocol.Step{ID: closeID, State: protocol.StepDone, At: t}}}, HostBackup: protocol.HostBackup{Snapshot: t}, Restores: []protocol.RestoreResult{{ID: opID, State: protocol.StepDone, Copy: "data/app.restored-20261118T120000Z.db"}}}`; the daemon calls `r.Bounded()`, which keeps at most `MaxBackupAccounts`, `MaxSnapshots`, `MaxDatabases` and `MaxRestores` entries and cuts each error to `MaxBackupError`. `D04-store`'s `RecordReport` folds them; `D10-operations` fails a replace with its not-empty reason when a step's `Code` is `protocol.CodeNotEmpty`; `D07-tools`' `restore_points` answers `Snapshots` as times and `D06-pages` shows the databases.
- The team template: `D04-store`'s `Desired` fills `TemplateURL: "https://github.com/ikigenba/team-template"` and `TemplateRef: "main"` from the stored setting; `D15-machine` clones `protocol.DefaultTemplateURL` at `protocol.DefaultTemplateRef` when they are empty, and its `Inspect` fills `Report{…, Seeds: []protocol.Seed{{GID: 20000, Commit: c}}, Homes: []protocol.Home{{UID: 20001, Commit: c}}}`; the daemon calls `r.Bounded()`, which keeps at most `protocol.MaxSeeds` and `protocol.MaxHomes`, and `D04-store`'s `RecordReport` gives the account of gid 20000 and the user of uid 20001 the commit `c` once.
- Deletes and checks: `D10-operations` lists and deletes `protocol.HostPrefix(name, seq)` of a host deleted with its data and `protocol.AccountPrefix(slug)` for `delete_account_backups`; `D07-tools`' `create_account` asks whether `protocol.AccountPrefix(slug)` holds keys.
