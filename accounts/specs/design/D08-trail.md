# D08-trail

The trail as a whole: the closed set of event names accounts records, the ones it declares itself with their attributes, the functions that record them, the request pair the telemetry middleware records for every request, and secrecy, stated once for the whole app. Outcome 15 of /home/mgreenly/Documents/ikigenba-ssh-hosts.md asks that every change, every host state change and every host going silent, coming back in sync or failing to apply be recorded in telemetry; this document names those events. Outcome 27 of /home/mgreenly/Documents/ikigenba-self-service-accounts.md asks that minting, revoking and using an invite each be recorded, that an enrollment name the invite it used, and that the trail never carry a token, a key or any part of either; this document adds the four events that do so and the secrecy rule for the token. Outcomes 11 and 15 of /home/mgreenly/Documents/ikigenba-host-numbers-and-delete.md ask that the trail say whether a delete kept the host's data and record the delete of a kept volume like any other change; this document adds `data` to the operation events and the event `volume.changed`. /home/mgreenly/Documents/ikigenba-host-backups.md adds closing, opening and replacing a host and restoring an account's files or databases; each is an operation, and it is recorded by the events that already exist, so the closed set does not change. What it adds here is secrecy: the credentials accounts issues to hosts, the paths a restore names or writes, and the error text a host reports about its backups never reach the trail. accounts calls no sibling and joins no bus this release, so it records no `sibling.called` and no `event.lost`, emits nothing on the bus, and its manifest declares no `[events]` (`D09-on-a-space`).

Who records each name is another document's; this one declares the names, their attributes and the functions that hand them to the writer. The request pair is appkit's `telemetry.Middleware`'s, which `D03-serve` mounts on every request, `/accountsd` and `/accountsd/` included; `tool.called` is appkit's MCP server's; `service.started` and `service.stopping` are the run's (`D01-layout-and-run-seam`). `change.finished`, `operation.started`, `host.changed` for a transition a tool makes, and `account.changed` for one a tool makes are told by the tools (`D07-tools`); `operation.finished` by the operations engine (`D10-operations`), except an operation a tool cancels in its own transaction, whose `operation.finished` with status `cancelled` the tool tells (`D07-tools`), since the engine never sees it end: a `place` that `remove_account` cancels, a `close` that `open_host` cancels, and each restore that `remove_account` or `replace_host` cancels, one event per restore its store call answered, in the order it answered them; `host.changed` and `account.changed` for every transition the engine makes by the engine, which also tells `host.silent` from its silence sweep and `resource.unexplained` from its stray scan; `host.synced` and `host.apply_failed` by the daemon endpoints from the report intake (`D13-daemon-endpoints`); `invite.created`, `invite.revoked` and `admin.changed` by the tools `create_invite`, `revoke_invite` and `set_admin` (`D07-tools`, which also sets their order beside `change.finished`); `invite.used` by the enrollment page's handler (`D18-enrollment`); `volume.changed` from `kept` to `deleting` by the tool `delete_kept_volume` (`D07-tools`, which also sets its order beside `change.finished`), and every later change of a kept volume's state, to `deleted` or back to `kept`, by the engine's pass (`D10-operations`). A kept volume's row appearing, when a delete finishes or the scan adopts a deleted host's volume, is not a state change and tells nothing. A host's user changes things too, from the host, through the box tools (`D19-box-tools`), which the host's daemon forwards to accounts at `/accountsd/v1/box` (`D13-daemon-endpoints`); a box call tells `change.finished`, `invite.created`, `invite.revoked` and `admin.changed` through the same functions, under the same rules and in the same order as the central tool of the same name (`D07-tools`), so a box change is recorded as a central one is, and a box read tells nothing but appkit's `tool.called`. The box path adds no event name and no attribute.

## The events

Every attribute is always present, empty when it does not apply; every value is a string unless noted. Keys are listed in the order each function takes them.

- `change.finished` — one per accepted call of a changing tool, whatever its ending: `tool`, `host`, `account`, `user`, `ip` (the address or allowlist entry `unban_ip`, `allow_ip` or `disallow_ip` was given, in canonical form, empty for every other tool and when the call's `ip` is refused), `result` (`ok`, `refused` or `failed`).
- `operation.started` — an operation recorded: `operation` (its id), `kind`, `host`, `account` (empty for a host kind), `data` (for a delete, its choice, `keep` or `delete`, `D04-store`'s `Host.OnDelete`; empty for every other kind).
- `operation.finished` — an operation that ended: `operation`, `kind`, `host`, `account`, `status` (`done`, `failed` or `cancelled`), `reason` (empty when done or cancelled; the `cloud.Error` text or a reason constant of `D10-operations` when failed, never text a host reported: a close, a replace or a restore the host's backups failed ends with one of `D10-operations`' backup reasons, and the host's own words stay in the record), `data` (as in `operation.started`).
- `host.changed` — every stored change of a host's state: `host`, `from` (empty for a host just created), `to`, `operation` (the operation that made it).
- `account.changed` — every stored change of an account's state, and its removal: `account`, `host`, `from` (empty for an account just created), `to` (`removed`, `AccountRemoved`, when its row is deleted).
- `host.silent` — a running host whose daemon has not reported for `store.SilentAfter`: `host`, `applied` (int64, the version it last applied).
- `host.synced` — a report applying the current version after the host was silent or failing to apply: `host`, `applied` (int64).
- `host.apply_failed` — a report carrying an apply error when the host was not already marked so: `host`, `attempted` (int64, the version the daemon tried).
- `resource.unexplained` — a tagged AWS resource no host record explains, told once when first seen: `resource` (its id), `kind` (`instance`, `volume` or `address`), `host` (its `Host` tag, empty when it has none).
- `invite.created` — a `create_invite` that made an invite: `invite` (its id, never its token), `account`, `host` (the account's host), `admin` (bool, whether the invite makes an admin).
- `invite.revoked` — a `revoke_invite` that deleted an invite: `invite`, `account`, `host`.
- `invite.used` — an enrollment that created a user: `invite` (the id of the invite it used), `account`, `host`, `user` (the login created), `admin` (bool, the invite's flag, which the user now holds).
- `volume.changed` — every stored change of a kept volume's state: `volume` (its EBS volume id), `host` (the host's name as it was when deleted), `from` and `to` (among `kept`, `deleting` and `deleted`), `reason` (empty unless a refused delete returned the volume to `kept`; then the `cloud.Error` text).
- `admin.changed` — a `set_admin` that changed a user's flag: `account`, `host`, `user`, `admin` (bool, the flag as it now is). A `set_admin` that finds the flag already as asked records none.

The time is the event's own `Time`, from the writer's clock; the caller is the event's `User` and its request id the event's `RequestID`, both from the `identity.Caller` on the context the function is handed. A tool call's events carry that call's caller. The engine tells an operation's events, and the state changes it makes, under the caller stored with the operation (its user id and request id), as gdrive tells background work; the silence sweep, the report intake and the stray scan tell theirs with no caller, so their `User` and `RequestID` are empty. An enrollment has no signed-in caller behind it: the person enrolling is a guest of the link, and `/join` takes no identity (`D03-serve`), so `invite.used` is told under a caller holding only the request's id, with an empty `User`, even when the person who opens the link happens to be signed in to the space; its actor is the attribute `invite`, which names the invite and so, through `invite.created`, whoever made it. A box call's caller is the one `D13-daemon-endpoints` puts on the context for a `BoxPath` request: its `UserID` is `box.ActorPrefix` (`ssh:`, `D19-box-tools`) followed by the name of the host user the request's uid resolved to, its email empty and its request id the request's; so every event of a box call, `tool.called` included, has the host user who acted as its `User`, and the `X-User-Id` a box request carries is never its `User`. A host user's name is unique across every host and account (`D17-names-keys-sizes`), so it implies both, and auth's user ids hold no `:`, so `ssh:<name>` never reads as a space user. An invite made from the box records `ssh:<name>` as its `invite.created`'s `User` and as its `CreatedBy` (`D04-store`), so an enrollment through it leads, by the invite id, to the host user who made it. The request pair of a box request is the middleware's like any other, its `User` the `X-User-Id` header, which the daemon does not send. No attribute repeats the user or the request id.

## Secrecy

The trail carries names, ids, states, versions, tool names, results, reasons, methods, request paths, statuses, times, admin flags, delete choices, kept volumes' ids, and the addresses and allowlist entries a tool was given. A volume id and a host's name are not secrets: they are the record's own names, answered by `kept_volumes` to any caller, and grant nothing. No event carries a caller's email, a key or any part of one, a key's comment, an invite's token or any part of one, AWS's message text (`cloud.Error`'s text is service, operation, subject and code only, `D05-cloud`), a report's body or its error text, anything read from a report (a ban's address, the host's allowlist as the daemon read it, a ban count included), or a desired state. The functions take no argument that could carry one: `host.apply_failed` takes the attempted version, not the error, and `change.finished`'s `ip` is the tool's own argument, canonical, never an address the daemon reported. The rule is proved at the run seam, by use, under secrecy conditions: every email and every key a test sends holds a random marker, and every capture of the run is searched for every marker. The three address tools are part of those conditions, so their `change.finished` is searched under callers whose emails hold markers; an address cannot itself hold a marker (it has no letter from `G` to `Z`), so that only a tool's own address reaches the trail is proved by `D07-tools`' requirement on the `ip` each tool passes to `Change`, and by no other function here taking an address, not by the markers.

An invite's token is a secret of the same kind as a key: whoever holds the link can enroll. No event carries a token or any part of one. No function here takes a token: the invite events take the invite's id, which `D04-store` draws separately and which grants nothing. The one place the token could reach the trail is the request that opens or submits the link; the token is in the link's query, and appkit's middleware records only `URL.Path` as `request.started`'s `path`, so the trail records `/join`: that a link was opened, not which (`D03-serve`). The secrecy run also mints, lists and revokes invites, opens a link and enrolls through it, and sets and clears an admin flag; a token is drawn from `Rand` in `D04-store`'s fixed alphabet, so the test shapes it only through the `Rand` it picks and cannot make it hold a marker; the rule for it is that no event holds any 8 consecutive characters of it.

A box call holds a key in its request body and answers an invite's link in its answer; neither reaches the trail. The box path adds no function: its events go through the functions above, which take no key and no token, and appkit's middleware records a box request's path, never its body or its query (the uid). The box path's secrecy is proved by a run of its own, in AWS mode with the test's own fake cloud, because a box request must be signed for a host the run holds and the sandbox's memory cloud keeps its signing key to itself (`D16-sandbox`): a host user who is an admin adds and removes a marker key, mints, lists and revokes an invite, sets and clears another user's admin flag and locks that user, and every event of that run is searched for the markers and for runs of the box-made token. The run-level box events are proved the same way.

A kept volume's id and its host's name are the record's own names, as a host's are; `volume.changed`'s `reason` is a `cloud.Error` text, which holds no AWS message. The secrecy run also deletes a second host keeping its data and then deletes the kept volume, so the delete's `data` and the volume's events are searched like every other.

Host backups add three secrets and change no function. The credentials accounts issues to a host (`D21-backup-access`, answered in the state's `backup` member by `D13-daemon-endpoints`) are a key of the same kind as an SSH key: whoever holds them can read and write an account's backups for an hour. The paths a restore names (`restore_database`'s and `restore_files`' `path`), the copy a host reports writing, and a database's path are a customer's file names; they are tool arguments and report facts, told to the caller who asked and shown on the host's page, never told to the trail. And the text a host reports about a failed backup, a failed final or a failed restore is read from a report like any other report text: it is kept with the step or the restore it belongs to (`D04-store`) and never becomes an operation's `reason`, which for these failures is one of `D10-operations`' reason constants. No function here takes a credential, a path or a host's text: `change.finished` names the tool, the host, the account and the user, `operation.started` and `operation.finished` the operation, its kind, host and account, and the delete choice stays the only `data`. The rule is proved by a run of its own in AWS mode, as the box path's is, because only a fake cloud of the test's own can answer `AssumeRole` with credentials holding markers and only a test acting as the host's daemon can report backup text and restore copies holding them: the test is answered the state carrying the fake's credentials, reports backups, finals and restores whose every string it chose holds a marker, asks for both kinds of restore with paths holding markers, closes the host and fails the close, then replaces it from backup and fails the whole-host restore, and every event of the run is searched. The sandbox's secrecy run also calls the backup tools other than the two restores (which the AWS run covers), so their events are searched under callers whose emails hold markers.

## Recorded decisions

- **The delete choice is an attribute of the operation events, `data`** (the host numbers and delete delivery): a query for deletes that removed data filters `operation.started` on `kind` `delete` and `data` `delete`, with no new event name. The key is general, empty for every kind but a delete, so a later operation with a choice of its own can use it; `change.finished` keeps its shape, since its keys are the call's names, not its arguments. `operation.finished` carries it too, so the end of a delete says what it did without a join to its start. Adding `data` to the two operation events and adding `volume.changed` is the expand step of expand then contract: every existing attribute and name stays, and nothing is removed.
- **`volume.changed` is one event for every kept volume state change, told by whoever made it** (as `host.changed`): the tool for `kept` to `deleting`, the engine for `deleting` to `deleted` and for a refused delete's `deleting` to `kept`, with the refusal's `cloud.Error` text as `reason`. A volume's adoption or its row's creation when a delete finishes is not a change of state and tells nothing; the delete's own `operation.finished` already says the host is gone. The engine tells under the caller stored with the kept volume's delete, as it does for an operation.

- **`change.finished` keeps its name and its three results; the `group` attribute is replaced by `host` and `account`** (departure from accounts' previous trail, which had `tool`, `group`, `user`, `result`): groups are gone, and a change now names the host and the account it touched. A query for one tool's changes still filters on `tool`. Expand-then-contract does not apply to the trail: an event recorded is history, not an interface a later release reads.
- **`change.finished` gains `ip`** (the SSH bans delivery, /home/mgreenly/Documents/ikigenba-ssh-bans.md, following the change above that replaced `group` by `host` and `account`): `unban_ip`, `allow_ip` and `disallow_ip` act on an address or an allowlist entry, not on an account or a user, so the trail needs a key for it to say what was unbanned or allowed. One key for all three, always present and empty for every other tool, keeps `change.finished` one shape, as every attribute is always present. It holds the canonical form the tool computed (`valid.Address` or `valid.AllowEntry`), so a query for one address matches however the caller spelled it, and is empty when the tool refused the argument as malformed, so a caller's arbitrary text never reaches the trail. An unnamed `unban_ip` has an empty `host`: one event for the call, not one per host. An address is not a secret: it is the caller's own argument, as a host or account name is. Anything read from a report stays out.
- **One name per kind of fact, not per tool** (`<thing>.<past>`, the suite's form, `operation.started|finished` after gdrive's `transfer.started|finished`): an operation's start and end are separate events because its end can be minutes later and under the engine, not the tool.
- **Trail only, no bus** (as sites' and ledger's trail-only names): outcome 15 says recorded in telemetry; no sibling consumes these, and joining the bus is a decision for a later release.
- **`host.changed` and `account.changed` for every stored state change, told by whoever made it**: the tools for the transitions their writes make (a host created `provisioning`, `running` to `stopping`, `failed` back to its operation's state on retry, an account created `pending`, an account to `removing`), the engine for the rest. One rule, every change told once, by the code that committed it.
- **Health events are edge-triggered**: `host.silent`, `host.synced` and `host.apply_failed` are told when the host's stored alarm changes (`D04-store`), never once per report or per sweep, so a host silent for a day records one `host.silent`.
- **`resource.unexplained` is told once per resource**, when the stray table first notes it (`D04-store`, `D10-operations`); it is never deleted or tagged, only reported.
- **`Result` takes the refusal errors as arguments** (departure from the previous `Result(err) string`): the trail imports nothing of accounts' own, so it cannot name `store.ErrTaken` or `valid.ErrName` itself; the tools pass the errors they treat as refusals, and the classification stays one function.
- **The value constants live here**: `AccountRemoved` for `account.changed`'s `to` and the three resource kinds, so the engine and the tests spell them once. Operation statuses and kinds are the store's words (`D04-store`), passed through.
- **Delivery is appkit's writer's**: each function emits one event through `w` and returns. The writer's queue holds 1024 events and drops one it cannot queue with an `undelivered event` line, so an event reaches the sink when the writer admits it; the trail adds no backpressure and no storage of its own, and tests keep fewer than 1024 events waiting.
- **The caller is the event's `User`, not an attribute**, as before: appkit's writer stamps every event from the context.
- The functions take plain values, not records, so the trail's contract does not move when a record gains a field; the run-level requirements and `D07-tools`, `D10-operations` and `D13-daemon-endpoints` prove the right values are passed.
- **The run-level promises are bounded to a clean run**, as before: every answered request leaves its pair, and every accepted change its `change.finished`, when the sink delivers without delay, serving does not fail before the stop signal, and no request is cut off at the drain deadline (`D03-serve`).
- Markers are compared without regard to letter case, and so are a token's runs.
- **Invites and the admin flag get events of their own, not new `change.finished` keys** (the self-service accounts delivery, /home/mgreenly/Documents/ikigenba-self-service-accounts.md, step 1): `change.finished` keeps one shape for every changing tool, and the three new tools still tell it like any other; the facts it cannot hold, which invite was made or revoked and what flag a user now has, go in `invite.created`, `invite.revoked` and `admin.changed`, each told only for a call that did it, so a query for invites or admins needs no tool names. `invite.used` has no tool behind it at all.
- **`set_admin` records `admin.changed` only when the flag changed**: a call that finds the flag already as asked answers `ok` and tells `change.finished` like any accepted call, but no fact changed, so the trail does not claim one.
- **The enrollment's actor is the invite**: the person enrolling has no identity on the space, so `invite.used` has an empty `User` and names the invite, even when the browser that opens the link is signed in; the caller who made the invite is on that invite's `invite.created`. A signed-in person's identity is not taken from a guest route.
- **A refused enrollment is not recorded**: anyone holding or guessing a link can submit as often as the rate limit allows, so recording refusals would let a guest flood the trail; only the request pair records that a submission came. Every successful enrollment records one `invite.used`.
- **The token never reaches the trail; it rides in the link's query**: the token is the whole of what an enrollment needs, so a trail reader must not be able to enroll. `request.started` records the path `/join` and no query, so how often links are opened stays visible and which link does not, in accounts' trail and in auth's `check.allowed` alike. The space's nginx access log still holds the full request line; that is `D18-enrollment`'s recorded risk, outside accounts.
- **A box change names the host user who made it as the event's `User`, not in a new attribute** (the self-service accounts delivery, step 2, the box path; outcome 27): `User` already carries who acted, every function already stamps it from the context, and `box.ActorPrefix` keeps a host user apart from a space user (auth's ids hold no `:`), so a box change and a central one have one shape and a query for one tool's changes, or one actor's, needs nothing new. A `box_user` attribute was rejected: it would be empty on every other event and repeat what `User` says. The box path adds no name to the closed set (R-1P7E-LHJI).
- **Box refusals are `refused`**: the box tools pass `Result` their twin's refusal errors plus the store's `ErrNotActive`, `ErrNotAdmin`, `ErrSelf` and `ErrLastKey` (`D19-box-tools`), each of which matches `store.ErrConflict`; so a call answered `LastKey`, `NotSelf`, `OnlyAdmin`, or `NoUser` for an actor who stopped being active mid-call, records `refused`, as every refusal but an unreachable store does. `Result` itself is unchanged.
- **The box path's `X-User-Id` is ignored, its request pair is not**: the middleware records every request's pair under the `X-User-Id` it carries, a box request's included; the events the box server and the box tools tell during it carry the resolved host user instead, because the host, not a person, signed the request, and the host user is who acted.
- **The box path holds nothing new in the trail**: each function still emits one event through `w` and returns, through the writer's queue of 1024; the trail keeps no storage and adds no bound of its own.
- **Host backups add no event** (the host backups delivery, /home/mgreenly/Documents/ikigenba-host-backups.md): a close, an open, a replace and a restore are operations, so `operation.started`, `operation.finished` and `host.changed` already record them, with the store's new kinds and states passed through as every kind and state is; the restoring account is the operations' `account`, empty for the three host kinds. A replace's mode is not told: `data` stays the delete choice alone, and the mode is answered by `host` while the replace runs. Backup health is computed when read and nothing is told when an account goes stale or fails (active alerts are deferred), so a stale account does not flood the trail once per report. A deletion of a removed account's backups is a row the engine works, not an operation; the tool's `change.finished` records the request, and its progress is answered by `backup_status`. The closed set (R-1P7E-LHJI) is unchanged.
- **Credentials, restore paths and a host's backup text never reach the trail** (the same delivery; backups outcomes 5 and 7): the credentials are a secret like a key, the paths are a customer's file names, and a host's error text is report text, which the trail has never carried. The trail needs none of them: an operation's id leads to the restore, its path and its copy through `restore_points`, `host` and the host's page, and the failed step's text is kept on the step. This is why a failed final or restore ends with a reason constant and not the host's words.
- **The backups secrecy run is in AWS mode, with the test as the host's daemon** (as the box path's run): the sandbox's memory cloud issues credentials and its simulated hosts report text of their own making, neither of which a test can make hold a marker, so only a fake `AssumeRole` and reports the test writes can put markers where a leak would show.

## Consumer usage

A tool, after its store write commits (`D07-tools`): `trail.HostChanged(ctx, w, "host01", "", store.HostProvisioning, op.ID)`, `trail.OperationStarted(ctx, w, op.ID, store.OpCreate, "host01", "", "")`, or for a delete `trail.OperationStarted(ctx, w, op.ID, store.OpDelete, "host01", "", h.OnDelete)`, then `trail.Change(ctx, w, tools.ToolCreateHost, "host01", "", "", "", trail.ResultOK)`; an address tool, `trail.Change(ctx, w, tools.ToolAllowIP, "host01", "", "", "192.0.2.0/24", trail.ResultOK)`, or for an `unban_ip` naming no host `trail.Change(ctx, w, tools.ToolUnbanIP, "", "", "", "192.0.2.77", trail.ResultOK)`; a refusal by the store, `trail.Change(ctx, w, tools.ToolCreateAccount, "host01", "acme", "", "", trail.Result(err, store.ErrTaken, store.ErrConflict, store.ErrNotFound))` (every store guard error matches `ErrConflict` or, for `ErrNotInAccount` and `ErrKeyNotHeld`, `ErrNotFound`, so all classify as refused).

The engine (`D10-operations`), under `identity.NewContext(ctx, op.Caller)` (`D04-store`'s `Operation.Caller`): `trail.HostChanged(ctx, w, h, store.HostProvisioning, store.HostRunning, op.ID)`, `trail.OperationFinished(ctx, w, op.ID, op.Kind, h, "", store.OpDone, "", data)` (`data` the host's `OnDelete` for a delete, empty otherwise), `trail.AccountChanged(ctx, w, "acme", h, store.AccountRemoving, trail.AccountRemoved)`; with no caller, `trail.HostSilent(ctx, w, h, applied)` and `trail.Unexplained(ctx, w, "i-…", trail.ResourceInstance, "host03")`.

A kept volume: `delete_kept_volume` tells `trail.VolumeChanged(ctx, w, v.Volume, v.Host, store.VolumeKept, store.VolumeDeleting, "")` before its `trail.Change(ctx, w, tools.ToolDeleteKeptVolume, v.Host, "", "", "", trail.ResultOK)`; the engine, under `identity.NewContext(ctx, v.Caller)`, `trail.VolumeChanged(ctx, w, v.Volume, v.Host, store.VolumeDeleting, store.VolumeDeleted, "")`, or for a refused delete `trail.VolumeChanged(ctx, w, v.Volume, v.Host, store.VolumeDeleting, store.VolumeKept, cerr.Error())`.

The report intake (`D13-daemon-endpoints`): `trail.HostSynced(ctx, w, h, applied)` or `trail.HostApplyFailed(ctx, w, h, attempted)` from `store.RecordReport`'s transition.

The invite and admin tools (`D07-tools`), on success: `trail.InviteCreated(ctx, w, inv.ID, "acme", "host01", inv.Admin)`, `trail.InviteRevoked(ctx, w, inv.ID, "acme", "host01")`, and, when `store.SetAdmin` reports the flag changed, `trail.AdminChanged(ctx, w, "acme", "host01", "daffy", true)`; each beside its `trail.Change(ctx, w, tools.ToolCreateInvite, "host01", "acme", "", "", trail.ResultOK)` (the account's host, empty only on a `NoLink` refusal) in the order `D07-tools` sets.
