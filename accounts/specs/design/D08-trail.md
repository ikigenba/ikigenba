# D08-trail

The trail as a whole: the one event that tells every change accounts asks of the host, its result, the closed set of event names accounts records, the request pair the telemetry middleware records for every request, and secrecy, stated once for the whole app. accounts calls no sibling and has no bus, so it records no `sibling.called` and no `event.lost`.

Who records each name is another document's, but for the one declared here. The request pair is appkit's `telemetry.Middleware`'s, which `D03-serve` mounts on every request; `tool.called` is appkit's MCP server's; `service.started` and `service.stopping` are the run's, through its writer (`D01-layout-and-run-seam` states what `service.started` carries, the display string among it). `change.finished`, its constant, the three result constants and the two functions `trail.Change` and `trail.Result` are declared here, in package `trail`. Which tool calls change something, and so call `Change`, is `D07-tools`'; what the host does is `D05-host`'s; what the record keeps is `D04-store`'s. This document states what `Change` records and what the assembled run shows.

## One event per change

Each call of one of the ten changing tools (`create_group`, `remove_group`, `add_user`, `add_key`, `remove_key`, `add_member`, `remove_member`, `lock_user`, `unlock_user`, `delete_user`) is told in the trail by exactly one `change.finished`, whether the host made the change, refused it or failed, with four attributes, every key always present and every value a string:

- `tool`: the name of the tool called.
- `group`: the group the call named, empty when the tool takes no group (`add_key`, `remove_key`, `lock_user`, `unlock_user`, `delete_user`).
- `user`: the user the call named, empty when the tool takes no user (`create_group`, `remove_group`).
- `result`: `ok`, `refused` or `failed`.

`ok` is a change the host made and the record kept; `refused` is one the host refused for its input or its state (`D05-host`'s `*RefusedError`); `failed` is everything else: the host failed, the command could not run, or the host made the change and the record write then failed (that case is `D07-tools`' to state: a failing or closed store handle provokes it, and so does an empty `group` to `create_group` or `remove_group`, or an empty `user` to `add_user` or `delete_user`, which the record refuses). `trail.Result` maps a host error to the first two and the third, so the tools classify a host outcome one way; the tools pass `ResultFailed` themselves when the record write fails, and when `remove_key`'s follow-up read of the host fails after the host removed the key (`D07-tools`).

The time is the event's own `Time`, read from `Process.Now` (`D01-layout-and-run-seam`), and the caller is the event's `User`, with the call's request id as its `RequestID`, minted from `Process.Rand` when the request carried none (`D01-layout-and-run-seam` R-PE8F-6SDX); no attribute repeats either. The event is recorded under the tool call's context, before that call's `tool.called`. A read (`groups`, `group`, `users`), a page and any request that is not a tool call record none.

`Change` takes the call's context, the writer and plain values, records one event under the request id and user of the `identity.Caller` on that context, queues and returns, returns nothing, and is safe to call from many goroutines at once.

## The request pair

Every request, whatever its path and whether or not it carries an identity, is recorded by the telemetry middleware as one `request.started` (method, path) and one `request.finished` (status, duration, bytes), under its request id and its caller's user. A guest's request to a page is answered with a redirect to sign in (`D06-pages`) and records the pair with no user; a request to `/mcp` with no identity is refused by appkit's `identity.Require` and records the pair likewise.

## Secrecy

accounts holds no secret, and its events carry names, tool names, results, methods, paths, statuses and times. No event carries a caller's email, a key, any part of one, or anything the host command wrote. The rule is proved at the run seam, by use: every email the test sends, every key's comment and its base64 field, and every diagnostic and failure output the stub writes, hold a random **marker**; the stub's `user list` document hands those keys back, as the host would, so a key that reached an event through a read of the host would show; and every capture of the run is searched for every marker.

## Recorded decisions

- **The run-level promises are bounded to a clean run.** That every answered request leaves its pair, and every answered change its `change.finished`, holds when the sink delivers without delay, serving does not fail before the stop signal, and no request is cut off at the drain deadline, the conditions under which `D03-serve` promises that every event recorded reaches the sink. A request cut off at the drain deadline may record its events after the writer is shut down, and those never reach the sink; a serving failure before the stop signal ends the run as `D03-serve` states, and nothing here promises `service.stopping`, or any event, on that exit.
- **One name, `change.finished`, with the tool as an attribute** (departure from ledger's one name per mutation kind). A change here is an attempt with three endings, and every ending is recorded; a past-tense name per kind (`group.created`) would read as done on a refusal. The suite's `<thing>.finished` events (a transfer's, a run's, a scrape's) carry how they ended as an attribute; this follows them, and names the tool as the decisions document asks, so a query for one tool's changes filters on `tool`.
- **`result` is an attribute, not part of the name**, for the same reason, and its three values are constants the tools pass, never spelled twice.
- **No key in the payload, and no fingerprint.** The decisions name tool, caller, group or user, and result. A public key is not a secret, but its comment is free text a person chose and may hold an email; a fingerprint would make accounts parse keys, which it leaves to the host (it validates nothing itself and relays the host's refusal). Which key a user holds is answered by the `users` tool from the host. A fingerprint can be added later as a new attribute if an audit needs it.
- **No diagnostic in the payload.** The refusal text is relayed to the caller in the tool's answer (`D07-tools`); the trail records that it was refused, not why, so nothing the host command wrote reaches telemetry.
- **The caller is the event's `User`, not an attribute**: appkit's writer stamps every event with the caller's user from the context; a second copy as an attribute would invite two answers.
- **`trail.Result` is declared here** so the classification of a host outcome into a result is one function both the tools and this document's tests use; the record-write failure, which no host error shows, is the tools' to pass as `ResultFailed`.
- `Change` takes plain values, not a host or store record, so the trail's contract does not move when either gains a field; it records whatever it is given, so the run-level requirements, not `Change`, prove the tools pass the right values.
- The time and request-id stamping of every event is `D01-layout-and-run-seam`'s (its writer's clock and random source); this document proves only that a change's event takes the request id of its call.
- Markers are compared without regard to letter case.

## Consumer tasks

The tools (`D07-tools`) call, with the tool call's context, once the call's outcome is known: `trail.Change(ctx, cfg.Telemetry, "create_group", slug, "", trail.Result(err))` after `GroupAdd` answered `err`, replacing the result with `trail.ResultFailed` when the host answered nil and the record write failed; `trail.Change(ctx, w, "add_user", group, name, result)` for `add_user`; and alike for the other eight, with the empty string for the argument the tool does not take. A unit test builds a writer with `telemetry.New(telemetry.Config{Service: "accounts", Sink: capture, Now: now, Rand: rnd})` over a `*telemetry.Capture`, calls `Change` under `identity.NewContext(ctx, identity.Caller{UserID: u, Email: e, RequestID: q})`, flushes the writer, and compares the captured event's `Name` with `trail.EventChangeFinished`, and its `Attrs`, `RequestID` and `User`. A test of `Result` hands it nil, a `*host.RefusedError`, a wrapped one, a `*host.FailedError` and a plain error. A run-level test drives `cli.Run` with a `*telemetry.Capture` as `Sink`, `ACCOUNTS_HOST_COMMAND` naming a stub that answers success, a refusal or a failure on demand, a fixed `Now` and a `Rand` that never repeats an id; waits for `READY=1`; calls every tool with `mcp.Client`, each call with an `X-Request-Id` of its own; requests the pages as a guest and as a user; cancels; and compares each captured event's `Name` with the closed set, and the `change.finished` events under each call's request id with that call and its `tool.called`. A test of secrecy runs the conditions R-AIGD-MOM0 names and searches the capture for every marker.
