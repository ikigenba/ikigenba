## What Apply does

`Apply` makes the host match one `protocol.DesiredState` (D11). It never replays: every part reads what the host holds, acts only when that differs, and writes every file whole to a temporary file in the same directory and renames it over the destination, so a kill at any point leaves either the old file or the new one and the next cycle finishes the work (outcome 22). A part whose check or reload fails puts the file it wrote back, so a failed configuration is never left installed and the next cycle tries again. The parts run in this order:

1. Packages. `nftables`, `fail2ban-server`, `dnf-automatic` and `git`, queried with `rpm -q` and installed together with one `dnf install -y` for whichever are missing (opsctl D19, plus `nftables`, which the next part needs before fail2ban would have brought it, and `git`, which the accounts part's `git init` and `git config` run and the AL2023 image lacks: `rpm -q git` on the first host answered not installed). Then `cronie` and `at`, queried the same way and removed together with one `dnf remove -y` for whichever are installed, because customers get no scheduler (below).
2. IMDS closed to customers. It fails closed: sshd's drop-in (part 12) `Requires=` and orders `After=` the unit that loads the rule, so a host whose rule cannot load at boot starts no sshd and admits no one; operators still reach it through SSM, whose sessions start as root. An nftables table `inet ikigenba_imds` drops every packet to the instance metadata service whose sending socket belongs to any uid but 0, so a person signed in to a host can never read the instance role's credentials and presign as the host (D12's Trust). The rules live in `/etc/nftables/ikigenba-imds.nft`, which starts with the declare-then-delete pair so loading it again replaces the table in one transaction; a oneshot unit `ikigenba-imds.service` loads it at boot before sshd, and every cycle checks the table is loaded (`nft list table`, exit 1 when absent) and loads the file when it is not. `accountsd` runs as root, as do the SSM agent and dnf, so none of them loses the metadata service.
3. The journal made persistent (opsctl D19, unchanged), because sign-ins are read from it.
4. Unattended security updates: the release lock lifted, dnf-automatic set to apply security updates, its timer on (opsctl D19, unchanged).
5. fail2ban's sshd jail, enabled and started. opsctl D19's jail with two changes (bans outcome 1): `mode = normal` where D19 has `aggressive`, and no `bantime.increment` or `bantime.maxtime`, so a ban lasts ten minutes flat; and an `ignoreip` line holding loopback (`127.0.0.1/8 ::1`) followed by the state's allowlist in the state's order (bans outcome 11). jail.conf(5) documents `ignoreip` as a space-separated list of addresses and CIDR masks. A changed jail is reloaded, as before.
6. Bans (bans outcomes 7 and 12). Every address of the state's `unban` is lifted with `fail2ban-client set sshd unbanip`, which is safe to repeat: on an address that is not banned it prints `0` and exits 0 (proved on `host01`). Then, only when the state has an allowlist and this cycle did not just start fail2ban, the jail's bans are read with `fail2ban-client get sshd banip --with-time`, streamed line by line, and the ban of every listed address an allowlist entry covers (`valid.Covers`, D17) is lifted too, because `ignoreip` keeps an address from being banned but does not lift a ban already in place. At most `protocol.MaxBans` such lifts run per cycle; the rest wait for the next. With an empty `unban` and an empty allowlist the part runs nothing. The part holds one line and at most `protocol.MaxBans` addresses at once.
7. The shell group `shell`, the keys directory and an empty skeleton directory for new homes.
8. The hostname (host names outcomes 1 to 6, below).
9. The root filesystem grown to its disk when the disk grew (outcome 16).
10. The data volume. The desired state names it by EBS id; the device is the NVMe disk whose serial is that id without its hyphen (AWS, "Identify the EBS device", `lsblk` SERIAL). A device with no signature at all gets an XFS filesystem labelled `ikigenbadata`, without a hyphen because an XFS label is at most 12 characters (mkfs.xfs(8) `-L`; `mkfs.xfs` refuses a longer one, as `ikigenba-data` was refused on the first host); a device with any signature is never formatted, and `mkfs.xfs` itself refuses one without `-f` (mkfs.xfs(8)), which is never passed. `data.mount` mounts it at `/data` by UUID, and two bind mounts put `/data/home` at `/home` and `/data/srv` at `/srv`. The filesystem is grown online when its disk grew. A state that names no data volume, or one whose device is not attached yet, is not an error while it names no account and no user: a host just created runs its first cycles before the volume is attached (D10's `attach` follows `launch`), and there is nothing yet to put on it. Once the state names an account or a user, a missing volume stops `Apply` with `machine.ErrNoDataVolume` before anything is created on the root volume, whose `/home` the bind mount would later hide.
11. The SSH host key on the data volume: `/data/ssh/ssh_host_ed25519_key` and its `.pub`, copied once from the instance's own pair when absent, so every instance that ever mounts the volume presents the same key (outcome 17).
12. sshd: a unit drop-in that makes sshd require the mounts holding `/data/ssh` (systemd.unit(5), `RequiresMountsFor=`), so at boot it starts only once the key is there, and the configuration drop-in, opsctl D19's bytes with `AllowGroups shell` alone (no `ec2-user`: there is no admin SSH login, outcome 19) and the host key on the data volume. It is checked with `sshd -t` before sshd reloads, and put back when the check or the reload fails.
13. Slices (outcome 18): the pool `acct.slice`, one slice per account below it, one per person below that, the session helper's link and, beside it, the box MCP server's link `/usr/local/libexec/accountsd-mcp` (box outcome 16, below). Then the accounts the state marks `active`, each new folder seeded (below), the users, the accounts it marks `removed`, and the isolation checks.
14. Claude Code (box outcome 16, sheet decision 9), last, and the one part whose failure never fails `Apply` (below).

What `Apply` does to accounts and users follows opsctl's D20 and D21, which ran the same commands for the same purpose on `us`, with three differences. Every uid and gid comes from the state (accounts allocates them, D04), so a replacement instance recreates the same owners on the kept data volume. A user's private group is made with `groupadd --gid` before `useradd --gid`, where opsctl used `useradd --user-group`, whose group id is not guaranteed to equal the uid. A user's account is fixed (outcome 9), so there is no join or leave. A user present on the host and in the group `shell` but absent from the state is locked and never deleted; only a user the state marks `deleted` is removed (outcome 22). An account absent from the state is not touched at all: its group, service account and folder stay, so a row accounts deleted only after the host applied its removal (D10) never strands anything. Locking expires the Linux account (`usermod --expiredate 1`, which sshd honours through PAM's account check under `UsePAM yes`, opsctl D19) and stops the person's slice, which ends every process of their sessions. Deleting reassigns the person's files under `/srv` to the folder's service account, then removes the account and its home; the folder and everyone else's files stay (outcome 13).

Accounts and users are read from `/etc/passwd`, `/etc/group` and `/etc/shadow` under `Root` (opsctl D20's rule: no process for a read), line by line, keeping only the entries the state names and the members of `shell`.

## Account slices and sessions

Each account's slice is a child of `acct.slice` and each person's a child of their account's, by systemd's naming rule (systemd.slice(5): a `-` in a slice name is a step down the tree, so `acct-acme-bugs.slice` sits in `acct-acme.slice` in `acct.slice`), with `-` inside a name escaped as `\x2d` the way `systemd-escape` does. For the names `valid` accepts (D17: lowercase letters, digits, `_` and `-`), `-` is the only byte `systemd-escape` changes (`systemd-escape 'a_b-c'` prints `a_b\x2dc`). The values are M1's (ikigenba-accounts-decisions.md), mapped onto three levels where opsctl's B5 had two: the pool's `CPUWeight=50` stays on the pool, so sshd, `accountsd` and journald at the default 100 win under contention; M1's pool memory ceiling (`MemoryHigh=1.5G`, `MemoryMax=2G`, `TasksMax=512`) becomes each account's ceiling, with an equal `CPUWeight=100` among accounts (CPUWeight divides a parent's share among siblings, systemd.resource-control(5)); M1's per-person cap is each person's slice.

The outcome is placement: every process of a person's SSH session runs in their slice. systemd puts login sessions under `user-<uid>.slice` through `pam_systemd`, and documents no way to choose another slice for them. The mechanism this design expects, and which is **unproven** (coordinator decision on Q2), is a PAM session hook for members of `shell`: sshd's stack skips `pam_systemd` for them (`pam_succeed_if user ingroup shell`) and runs, through `pam_exec`, a root helper that starts a transient scope in the person's slice holding the session's process (`StartTransientUnit` with `PIDs`, org.freedesktop.systemd1(5)), so the shell sshd forks after it inherits the scope. Whether OpenSSH's PAM session runs where moving that process captures the shell, and what skipping logind costs (no `XDG_RUNTIME_DIR`, no lingering, neither of which a customer session needs), is proved only on a real host. So the requirements state the slice files, the placement, and the mechanism's seam. The helper is `accountsd` itself: `Apply` links `/usr/local/libexec/accountsd-session` to `/usr/local/bin/accountsd`, and the binary run under that name calls `linux.Session` instead of the daemon (D14), so the helper is one Go function, tested over a temporary root with a recording `Execute`, and a self-update updates it with the daemon. `Session` reads only `PAM_TYPE` and `PAM_USER` (pam_exec(8) exports the PAM items so), runs no shell, acts only on a session opening for a `shell` member with a person slice, and moves only its parent, the process opening the session, into a transient scope in that slice with one `busctl` call, then waits until `/proc/<parent>/cgroup` names that scope before it returns, failing the session when it does not within `SessionWait`. `Apply` adds the `pam_exec` lines for `shell` members to `/etc/pam.d/sshd` with the control `required`, so a session the helper cannot place is refused, never left outside the slice; their exact words are the build's; the seam tests prove the files, the link and `Session`'s command under a temporary root; and the finish line proves the placement with `/proc/<pid>/cgroup` of a signed-in session. If it fails there, the fallback (opsctl B5's `user.slice` pool) misses outcome 18's "slice of its own" and goes to the owner.

## The account folder's seed

A new account's folder starts with the team template (seed outcomes 1 to 12). The files are the root package's `Seed()` (D01), the template's `seed/` folder embedded in `accountsd`, so a host fetches nothing and creating an account never needs GitHub (decision P1). The seed happens once, when `Apply` itself makes the folder, and it is the folder's first commit.

**"This apply made it" is made atomic by building the folder aside.** When nothing is at `/srv/<s>`, the folder is built at `/srv/.<s>.seed`, a name no slug can take (D17: a slug never begins with `.`): created `0700`, given to the service account, set `02770` with its default ACL, `git init`ed as the service account, and given the marker `.git/ikigenba-seed` (`SeedMarker`) holding `pending <gid>`, written by the service account with `tee`, all before one `rename` puts it at `/srv/<s>`. rename(2) is atomic within one filesystem, and `/srv` is one bind mount of `/data/srv`. So `/srv/<s>` either does not exist or exists holding a marker, and whatever is left at the building path by an interrupted `Apply` is removed by the next one before it builds again. A folder that already exists with no marker, such as `mg`'s (which holds only `.git`) or one a removed account left behind, is never seeded and nothing is written in it beyond what the folder rule already did before this change (decision P4).

**The marker's states.** `pending <gid>\n`: the folder was made by `Apply` for the account with that gid, and its seed is not finished. `done\n`: finished. Anything else, absence included, means never seed. The gid in the pending state keeps a folder that a removed account left half-seeded from being finished for a new account of the same slug, whose gid differs and which could not write the old `.git`. The marker is the service account's, written by `tee` like the seed, and lives in `.git`, so the working tree never shows it, and root never writes it or any seed file, so nothing a member might plant there is ever followed with root's rights by the seed; a team that deletes it, or the whole history, only makes the folder one that is never seeded.

**The seed itself**, each step checked before it acts (decision P3). With the marker pending, `git rev-parse --verify --quiet HEAD` as the service account says whether the first commit has landed: git-rev-parse(1) documents that with `--quiet` an invalid name makes it "exit with non-zero status silently", and git 2.47.3 exited 1 in a fresh repository and 0 after a commit (observed 2026-11-26). Not landed: every directory and file of the seed is made by the service account itself, `mkdir -p` for a directory and `tee` for a file, the file's bytes on its standard input (tee(1): "copy standard input to each FILE", truncating it unless `-a` is given), and the seed's paths are added and committed as the service account, the name and email given with `-c` on that one command (git(1): `-c` "Pass a configuration parameter to the command") and never written to the folder's configuration (decision P5). Landed, or once the commit exits 0: the marker becomes `done`. A team that deleted `setup.md` therefore never sees it again: the folder's marker is `done`, or absent (seed outcomes 2 and 3).

**What each interruption leaves**, and what the next `Apply` does:

| Stopped | Left | Next `Apply` |
|---|---|---|
| while building aside | nothing at `/srv/<s>`; a partial `/srv/.<s>.seed` | removes it and builds again |
| after the rename | the folder with `.git` and the marker pending | writes the seed, adds, commits, marks done |
| while writing files | some seed files, one perhaps cut short | makes every directory and file again, adds, commits, marks done |
| after `git add` | a staged index | writes the same bytes again, adds again (adding an unchanged staged path changes nothing), commits, marks done |
| after the commit | one commit, marker pending | finds `HEAD`, writes nothing, marks done |
| after `done` | the seeded folder | nothing, ever |

A failing step stops `Apply` like any failed command or filesystem failure (R-S739-S0BW): the error is a `*CommandError` labelled `runuser` for the commands run as the service account, or one naming the host path, reported as the report's `error` like its neighbours; the version is not reported applied, and accounts does not make the account `active` until a later `Apply` finishes (decision P6, seed outcome 11). Every later part waits for that cycle, as it does behind any other failed part, so a new account's people get no login before its seed is finished, and the seed writes into a folder that only root and the service account can reach.

**Owners and modes** (seed outcome 6). A member's file in an account folder gets the folder's group by its setgid bit, and its mode from the default ACL `g::rwx,o::-`, which acl(5) applies instead of the umask: `0660` for a file created with `0666`, as `tee` creates one (observed with GNU coreutils), and `02770` with the same default ACL for a directory made with `0777`, as `mkdir` makes one (mkdir(1): "a=rwx - umask"; acl(5): a new directory takes the parent's default ACL as its default ACL; mkdir(2): "If the parent directory has the set-group-ID bit set, then so will the newly created directory"). The seed is made the way a member makes files, by the service account in the folder, so it gets exactly that, with the service account as owner since no member exists yet. The seed has root write nothing beneath the folder, not even the marker (removing a leftover building path is root's one change there, and only to what `Apply` itself made): no `chown`, no mode set, and no symbolic link a member might plant is ever followed with root's rights.

**The commit's name** is the service account, and its email `<s>@<N>`, `<N>` the name the hostname part gives the host, `<host>.<domain>`, or the state's `host` when the state carries no domain. No remote is added and the template's history does not come along, since the files come from the binary and not from a clone (seed outcome 7). The commit message is copy, `machine.SeedMessage`, declared in `machine` so the memory machine can record it too (`linux` imports `machine`, never the reverse).

**Memory.** Each file reaches `tee` as its standard input, streamed from the embedded seed as `tee` reads it, and `git add` names at most `ChownBatch` paths per command; the marker is read through a reader of at most `MaxCapture` bytes; removing a building path walks what `git init` made there, a fixed set of a few dozen entries. The whole seed is about 1.3 KB at `v1`, so nothing it holds grows with anything but the binary.

**Rollout.** Neither the protocol nor the state changes, so an old and a new release mix in both directions (D11's rule). A host made before this release gets the seed through the self-update it already does (D14): accounts' new digest answers the waiting poll at once, and the daemon updates before it applies (seed outcome 9). An old daemon that applies a new release's state, as one whose update failed would, makes a new folder the old way, unmarked, which the new daemon then never seeds. A new daemon rolled back leaves at most a `/srv/.<s>.seed`, which the old daemon ignores and the new one removes when it returns, and a pending marker, which the old daemon ignores and the new one finishes. The account `mg`, created before this release, keeps its folder as it is (seed outcome 10).

## The box MCP server and Claude Code

Box outcome 16 puts a local MCP server on every host, and sheet decision 1 makes it `accountsd` once more: `Apply` links `MCPHelper`, `/usr/local/libexec/accountsd-mcp`, to `DaemonPath` exactly as it links `SessionHelper`, and the binary run under `MCPName` serves MCP over stdio (D14 dispatches, D20 is the server). The link is laid down in the slices part beside the session helper's, kept every cycle, owned by root by the isolation rule, and updated by a self-update with the daemon.

Claude Code is the client configured first (box outcome 16). The Claude Code part runs last, after isolation, so nothing that protects the host waits on a download of about 350 MB, and it never fails `Apply`: users, keys, locks and bans have all applied by the time it starts, and a repository outage or a key problem must not keep a state's version unapplied, since accounts finishes removals only once a host has applied them (D10). Each cycle it does, in order:

1. **Configuration files**, by the exact-bytes rule every part follows (sheet decision 9): `/etc/claude-code/managed-settings.json`, which accountsd owns whole and rewrites when it differs, and the plugin marketplace under `/usr/local/share/accountsd/claude`, whose plugin's `.mcp.json` names `MCPHelper` as its command. Files `0644`, directories `0755`, root's. Nothing is written in a home, in the skeleton directory (R-C67D-ES5W stands) or for any one user: Claude Code reads its managed settings for every user of the machine.
2. **Pacing.** Like every part after the data volume's, this one is skipped while a new host has no volume and no user (R-C8N6-6BNA), and it does not run in a cycle an earlier part stopped. A part that failed is not tried again by the same process for `ClaudeRetry` (an hour), so a repository outage costs one attempt an hour, never a dnf run every cycle. The pacing is kept in memory: a restarted daemon tries once at once, which a restart's rarity bounds (self-updates, or `RestartSec=5` after a crash, where the dnf run itself takes longer than the restart delay).
3. **The signing key.** rpm keeps an imported key as a header named `gpg-pubkey-<keyid>`, queried like a package (rpmkeys(8), rpm 4.16: "An imported public key is carried in a header, and key ring management is performed exactly like package management", with the example `rpm -qi gpg-pubkey-db42a60e`; the version is the last eight hex digits of the key id in lowercase, as dnf's own import line `Importing GPG key 0xD832C631` for fingerprint `… D832 C631` shows in AL2023's "Repository metadata signing" page). So `rpm -q gpg-pubkey-1a7ecace` says whether the pinned key is in. Only when it is not, the part fetches `ClaudeKeyURL` (the repository file's `gpgkey`) through `Env.Fetch`, streams it to `ClaudeKeyFile` through one buffer and refuses past `MaxKeyBytes`, reads it with `gpg --homedir GnupgHome --batch --show-keys --with-colons` and imports it with `rpmkeys --import` only when the listing holds exactly one primary key whose fingerprint is `ClaudeKeyFingerprint`. The GnuPG manual documents `--show-keys` as taking "OpenPGP keys as input and print[ing] information about them in the same way the command --list-keys does for locally stored key", "combined with the option --with-colons" for automated processing; GnuPG's `doc/DETAILS` gives the colon records `pub` (primary key), `sub` and `fpr` ("fingerprint is in field 10"). `--show-keys` imports nothing, but gpg still creates a keybox and trust database in its home (observed with gpg 2.4.7, 2026-11-24), so it gets a home of its own, `GnupgHome`, mode `0700`, never root's `~/.gnupg`. Requiring exactly one `pub` record refuses a file that carries the pinned key beside a second primary key, which `rpmkeys --import` would otherwise import too. The temporary key file is removed whatever happens.
4. **The repository file and the package.** Only once the key is in rpm's keyring does the part write `/etc/yum.repos.d/claude-code.repo` with sheet decision 9's bytes, so a host whose key check fails has no Claude Code repository at all. Then `rpm -q claude-code`: when missing, `dnf install -y`; when installed, `dnf upgrade -y` at most once per `ClaudeUpgradeInterval` (a day; dnf-automatic is security-only, sheet decision 9). Every dnf command of the part carries `--setopt=claude-code.gpgkey=`. With `-y`, dnf answers yes to its key-import prompt and imports whatever the repository's `gpgkey` serves (dnf(8) `-y`: "Automatically answer yes for all questions"; AL2023's "Repository metadata signing" page shows that prompt and tells unattended runs to pass `-y` so "the key import succeeds"), while dnf.conf(5)'s `gpgkey` is used only to import keys when a package "can not be verified using the already imported keys". Clearing it for the command (dnf(8) `--setopt`: "To override configuration options for repositories, use repoid.option", and "specifying an empty value … will clear the option") means dnf can only verify against the key the part checked, and a package signed by any other key fails the command instead of importing an unchecked key. dnf 4.14.0's source shows it: `dnf/base.py` `_sig_check_pkg` sets `hasgpgkey = not not repo.gpgkey`, and a package whose public key is not installed is result 2, "Fatal GPG verification error, give up", when `hasgpgkey` is false, rather than result 1, "installation of the right GPG key might help"; and where it does return 1 (a key present but not trusted), `_get_key_for_package` takes its candidate keys from `keyurls = [] if key_installed else repo.gpgkey`, an empty list, so nothing is imported there either.
5. **Once a day across restarts.** `ClaudeStamp`, a root-owned file beside the skeleton directory under `/var/lib/accountsd` on the root volume, holds the time of the last upgrade attempt (or successful install) as RFC 3339 UTC. An upgrade is due when the stamp is absent, unreadable, a day old, or in the future, so a clock set back produces one early upgrade and then the day counts again; a reboot keeps the stamp; a replacement instance starts without one and installs anyway. A failed upgrade still stamps, so upgrades are attempted at most once a day whatever happens.

**Reporting a failure.** The report protocol does not change (sheet decision 5's preference) and the report's `error` carries only `Apply`'s error, which this part must never set. So a failure is said where the daemon's other diagnostics go: one stderr line, `accountsd: ` followed by the copy constant `DiagClaudeCode` and the failure's text, which journald keeps with the unit (D14's line form, R-6VMC-LRG8). The words `DiagClaudeCode` is to hold are "cannot install or update Claude Code", and those of `ErrClaudeKey`, the failure of a key whose fingerprint is not the pinned one, "the Claude Code signing key is not the pinned key"; the copy lives in those two declarations only (sheet decision 7). The owner decided failures go to the journal only, with no report member (recorded below).

**The network seam.** The key is the only thing `linux` fetches, and it fetches through `Env.Fetch`, as it runs programs through `Env.Execute`; `Real()` hands `Get`, a plain GET under the context `Apply` gives it, with a deadline of `FetchTimeout`. `Real()` also hands `os.Stderr` as `Env.Stderr`. The constructor is unchanged, so `cmd/accountsd` still builds the host with `linux.New(linux.Real())` and `linux.Session(ctx, linux.Real(), …)`, and D14's argv[0] dispatch needs no new wiring for the host beyond its `linux.MCPName` case. A test hands a `Fetch` that answers from memory and a `Stderr` buffer; a test of `Get` serves it on loopback with `httptest`.

**Memory.** The key is streamed through one fixed buffer, and at most `MaxKeyBytes` reach the disk; the signing key was 1,688 bytes when fetched on 2026-11-24 (one RSA 4096 primary key, fingerprint `31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`), so 64 KiB leaves room for added subkeys and signatures while bounding the file. gpg's listing and dnf's output are read from `Result`, which `Exec` caps at `MaxCapture` each (R-SCRB-B1BJ).

**On AL2023.** The AL2023 AMI carries `dnf` 4.14.0, `rpm` 4.16.1.3 and `gnupg2-minimal` 2.3.7 ("Comparing packages installed on Amazon Linux 2023 Images"), so dnf here is dnf 4 and the commands above are dnf 4's (dnf.readthedocs.io), `rpmkeys` comes with `rpm`, and `--show-keys` is in GnuPG 2.3. That `gnupg2-minimal` installs `/usr/bin/gpg` is not stated on that page; it is a finish-line check (`rpm -ql gnupg2-minimal`), as are the `gpg-pubkey-1a7ecace` name after the first import and the empty `--setopt` refusing an unchecked import. AL2023 sets `skip_if_unavailable=True` (same "Repository metadata signing" page), so an outage of the Claude Code repository does not fail the other dnf commands of `Apply`, `Inspect` or dnf-automatic; an upgrade during an outage finds nothing, exits 0 and waits a day.

## The hostname

A host calls itself `<host>.<hosts domain>` in full (host names outcome 1). The state carries the domain in `domain` (D11), which accounts fills from its configured hosts domain (D13); an empty `domain` means the host is not told one, and the part then creates, changes, removes and executes nothing, so a state from accounts without the setting, like an older daemon that ignores the member, leaves the hostname alone (host names outcome 6).

With a domain, the part first checks the name, the state's `host`, a dot and the domain, by hostnamectl(1)'s rule for a static hostname: one DNS label of lowercase letters, digits and hyphens, or several separated by single dots, at most 64 characters. A name that fails stops `Apply` with `machine.ErrInvalidState`, having done nothing in the part. Then it keeps the cloud-init drop-in `/etc/cloud/cloud.cfg.d/99-ikigenba.cfg` holding exactly `preserve_hostname: true` and one LF, by the exact-bytes rule every host file follows, and reads the static hostname from `/etc/hostname` under `Root` (hostname(5): the file holds a single newline-terminated hostname), trimmed of surrounding blanks and line ends; only when that differs from the name does it run `hostnamectl set-hostname <name>`. hostnamectl(1) documents that the verb, given no `--static`, `--transient` or `--pretty`, sets the static, transient and pretty hostnames alike, and systemd-hostnamed.service(8) that the static hostname is stored in `/etc/hostname`; systemd 252's source (`src/hostname/hostnamectl.c`, `set_hostname`) clears the pretty hostname rather than setting it when the name given is already a valid hostname, so `/etc/machine-info` loses any pretty name and gains none. So the next cycle reads the name back from `/etc/hostname` and runs nothing: the part never replays. The drop-in is written first, so a host renamed is never one whose name a lost cloud-init state could undo.

The part runs right after the shell group and before root growth and the data volume, so it is not held back by the rule that skips every part after the data volume's on a new host with no volume and no user (R-C8N6-6BNA): a new host has its name in its first cycle, before its first report in sync (host names outcome 3, log A5). Existing hosts get it through the daemon's normal self-update and next cycle (host names outcome 4).

**Failure.** The part follows the rule every part but Claude Code follows (R-S739-S0BW). A drop-in that cannot be written is a filesystem failure naming its path, and no `hostnamectl` runs. A `hostnamectl` that cannot run or exits non-zero stops `Apply` with a `*CommandError` labelled `hostnamectl`; the drop-in stays, since it changes nothing until cloud-init next runs and then only keeps whatever name `/etc/hostname` holds; and the version is not reported applied, so the next cycle tries again. Every later part waits for that cycle, as it does behind any other failed part; a bad domain therefore holds back users and keys but never locks, which run second.

**Memory.** The part holds the name and at most `MaxCapture` bytes of `/etc/hostname`; `Inspect`'s read holds the same.

## Inspect

`Inspect` reports what the machine knows; the daemon adds identity, versions, the error and its own digest (D14). Each fact comes from one documented source: the OS name from `/etc/os-release`'s `PRETTY_NAME`, the kernel from `/proc/sys/kernel/osrelease`, the boot time from `/proc/uptime`, load from `/proc/loadavg`, CPU from two readings of `/proc/stat`, memory and swap from `/proc/meminfo`, volume use from `statfs`, sessions from the scopes under `acct.slice` in the cgroup tree, each account slice's CPU and memory from its `cpu.stat` and `memory.current` (cgroup v2), failed units from `systemctl list-units`, pending security updates from `dnf updateinfo` and whether a reboot is needed from `dnf needs-restarting -r`. Sign-ins come from sshd's journal, read forward from the last cursor, so each cycle reads only what is new. The two dnf queries refresh repository metadata and take seconds, so they run at most once per `UpdatesInterval` and the last answer is reported between. The hostname is the static hostname, `/etc/hostname`'s content trimmed of surrounding blanks and line ends, read through a reader of at most `MaxCapture` bytes, and empty when the file is absent (host names outcome 14: accounts compares it with the name it asked for). A fact that cannot be read is reported as its zero value; `Inspect` fails only when its context is done.

The bans (bans outcome 4) come from `fail2ban-client get sshd banip --with-time`, which on `host01` (fail2ban 1.1.0, AL2023) printed one line per ban: the address, one space, one TAB, the start, ` + `, the ban's seconds, ` = `, the end, each time `%Y-%m-%d %H:%M:%S` in the host's local zone with no zone printed, sorted by end, the end sometimes one second past start plus seconds; with no bans it printed one empty line and exited 0. The output is streamed through a fixed buffer line by line: every non-empty line counts in `ban_total`, a line that parses becomes a ban, and only the `protocol.MaxBans` with the latest start are kept, so `Inspect` holds one line and at most `protocol.MaxBans` bans whatever the jail holds. The times are read in the zone of the clock `Env.Now` returns, which on a host is `time.Now`'s local zone, the one fail2ban prints in, and reported in UTC. When the command cannot run or fails, no bans and a total of 0 are reported, like any fact that cannot be read. The allowlist the host applied (bans outcome 13) is read back from the jail's `ignoreip` line, loopback left out because the jail always holds it.

## Self-update target

`InstallDaemon` streams the body accounts served into `/usr/local/bin/.accountsd.new`, hashing as it writes and never holding more than one buffer, checks the ELF magic, the size cap `protocol.MaxBinaryBytes` and the digest, syncs, and renames it over `/usr/local/bin/accountsd`, the path infra's user data installs and the unit runs (log D7). Any failure removes the temporary file and leaves the running binary in place. Replacing the file a process runs from is safe on Linux: the running process keeps its open inode, and systemd starts the new file when the daemon exits (D14).

## Backups

Every account on a host is backed up to S3 (backups outcomes 10 to 18): its folder and its users' homes by restic, as hourly snapshots in one repository per account, and every SQLite database under its `data/` folder by Litestream, streamed continuously. `accountsd` runs both, with credentials accounts hands it in the state's `backup` member (D11, D13, D21), and reports what it found in the report's `backups` and `host_backup` members. Two methods of `Machine` do the work, each one pass at a time, on two workers of the daemon with ticks of their own, started after the first `Apply` of a run returns and handed the state of the latest `Apply` that has returned (D14): `Stream`, every 30 seconds, finds the databases, keeps one Litestream unit per account running with current credentials and checks that each replica holds every write; `Backup`, every minute, installs restic, takes the snapshots, prunes, checks, backs up the host key, and carries out a close's finals and the restores (those are described in the sections that follow). Neither waits for the other, so renewing Litestream's credentials never waits behind a long restic run, and neither changes what `Apply` returns: a backup problem is a fact of the report, never its `error` (R-R7Q6-ONTR's policy, extended).

**When there is nothing to do.** A state with no `backup` member (an accounts of the previous release, or no hosts settings), an unusable bucket or region, or no schedule, gives every account and the host the copy constant `machine.NoCredentials` as its error, stops every Litestream unit and runs nothing else. An account whose credentials accounts could not issue this time (D21 leaves them zero and retries on the next answer) gets the same error, and nothing is run for it; its Litestream unit keeps the credentials it has, which last about 44 minutes from when accounts issued them. The values are checked before they land in a file: a credential holds only base64 bytes, a region only lowercase letters, digits and `-`, a bucket only what an S3 bucket name may hold, so nothing accounts sends can add a line to a unit's environment file.

**Pinned installs** (backups outcome 4). restic and Litestream are installed by the passes, at pinned versions, from their GitHub releases: restic `0.20.0` (`ResticVersion`), asset `restic_0.20.0_linux_arm64.bz2`, digest `sha256:1188daded239bccb5952a01d2ad33e77a0d3dc34f9d9fc1e7fdda618d44938ef` (`ResticDigest`); Litestream `0.5.17` (`LitestreamVersion`, the version the suite's spaces run, `infra/templates/space-first-boot.sh`), asset `litestream-0.5.17-linux-arm64.tar.gz`, digest `sha256:f8ca4a050095c1efbda2c4365172e61bf9d955ea0d9ac42f448b52e51819baa5` (`LitestreamDigest`). The four constants are declared without their values (the `SeedVersion` precedent, R-027W-U4P5): no test can tell one release from another without spelling it, so the values live here and in the source. Each install fetches the asset once through `Env.Fetch` under `InstallTimeout`, streams it to a temporary file on disk through one buffer, hashing as it writes and refusing past `MaxInstallBytes`, checks the digest before anything is unpacked, then unpacks from that file through one buffer into a temporary file beside the destination, checks the ELF magic and renames it over `ResticPath` or `LitestreamPath`; a stamp file under `BackupDir` holding the digest says the pinned release is in place, so a pass fetches nothing while the binary and the stamp agree, and a changed pin installs once. A failed install is not tried again by the same process for `InstallRetry` (an hour, the `ClaudeRetry` precedent), and its text becomes every account's error (restic) or every database's (Litestream), so health shows `error` at once rather than going stale two hours later. The install itself is the exported `InstallRestic` and `InstallLitestream`, which take the version and digest as arguments, so a test serves a fixture archive it built and the digest of that fixture, never the real assets: a gzip-compressed tar through the standard library's writers, and for restic a small bzip2 stream the test carries as bytes, since the standard library decompresses bzip2 but cannot compress it. `Backup` and `Stream` call them with the pinned constants, which a test proves by the URL fetched and the digest refused. `Get`, the real `Fetch`, now follows the redirects GitHub's release downloads answer with, at most `MaxRedirects`, never from `https` to anything else.

Probes made for the pins (2026-11-26, credential-free, into fresh temporary directories, nothing executed): the restic asset's SHA-256 is the digest above and matches the release's `SHA256SUMS`; it is one bzip2 stream (`bzip2 -t`), 11,274,882 bytes, decompressing to one 35,979,424-byte static ELF for ARM aarch64. The Litestream tarball's SHA-256 is the digest above and matches the release's `checksums.txt`; it is 12,336,596 bytes, and `tar tzvf` lists `LICENSE`, `README.md`, `etc/litestream.service`, `etc/litestream.yml` and one regular file `litestream` at the archive's top level, 36,241,592 bytes, a static ELF for ARM aarch64. Both binaries and both archives are under `MaxInstallBytes` (64 MiB) with room for later releases.

**Databases** (backups outcomes 15 and 18, backups log 5). A database is any regular file under an account's `data/` folder whose first sixteen bytes are SQLite's header string, `SQLite format 3` and a NUL ("Database File Format", sqlite.org, section 1.3, offset 0); it is in WAL mode when the file format write and read versions, the bytes at offsets 18 and 19, are both 2 (same section: "1 for legacy; 2 for WAL"). The walk never follows a symbolic link and reads at most twenty bytes of each file, opened for reading; the daemon never writes a customer's file. A database not in WAL mode is reported with `machine.NotWAL`, never handed to Litestream (whose `DB.init` runs `PRAGMA journal_mode = wal` on what it is given, `db.go` at v0.5.17, so handing it one would change the customer's file) and left in the restic snapshot, hourly, as a plain file. A file whose path `valid.DatabasePath` refuses, or that is not valid UTF-8, is passed over and left to restic too: it could not be named exactly in Litestream's configuration or the report. A database restored beside the live one (`restore_database`) is itself a SQLite file under `data/` and is streamed like any other. The walk is bounded: directories are read `ReadBatch` entries at a time, it descends at most `MaxDepth` levels below `data/` and reads at most `MaxVisit` entries per account and pass, holding at most `MaxDepth` + 1 open directories and `MaxDatabasesPerAccount` paths; past the depth or visit bound it keeps the set the previous walk found and reports `machine.DataTooLarge`, and past `MaxDatabasesPerAccount` databases it streams that many, counts the rest as errors and reports `machine.TooManyDatabases`.

**Litestream** (backups outcomes 16 and 17). Each account with a database in WAL mode gets a configuration `BackupDir/<a>.yml` naming exactly its streamed databases, each replicated to `<DataPrefix(a)>/<path below data/>` in the bucket, and a template unit instance `accountsd-litestream@<a>.service` (`LitestreamUnit`) running `litestream replicate` over it. The configuration keys are Litestream v0.5.17's, read from its source at the tag (`cmd/litestream/main.go`): `dbs` with `path`, `meta-path` and `replica`; the replica's `type`, `bucket`, `path` and `region`; the global `snapshot` with `interval` and `retention`; and `shutdown-sync-timeout`. `snapshot.retention` is the settings' `WindowDays` in hours (five weeks by default), `snapshot.interval` 24 hours, so history reaches back the whole window (litestream.io, How it works: retention prunes all levels together, and a restore starts from the last snapshot before its time). `meta-path` keeps Litestream's local state under `BackupDir/meta/<a>/`, out of the account folder. The replica is named by `bucket` and `path` rather than an `s3://` URL, so no path needs URL escaping, and every value is written as its JSON encoding, which yaml.v2 (Litestream's YAML package) reads back as the same string. Every `litestream` command passes `-no-expand-env`, because Litestream otherwise expands `$` in the whole configuration (`ReadConfigFile`, `os.Expand`) and a database name may hold one. Credentials reach Litestream only through the unit's `EnvironmentFile=` (systemd.exec(5); lines beginning `#` are comments there), mode `0600` in a root-only directory (backups outcome 7): a configuration that names no keys builds its S3 client with the AWS SDK's default chain (`s3/replica_client.go`, `Init`, at v0.5.17), which reads `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` from the environment (AWS SDK for Go v2, "Specify credentials": environment variables). A replica URL on the command line would not do: Litestream's URL path copies the key and secret into a static provider with an empty session token (`NewReplicaClientFromURL`), which session credentials cannot sign with, so every command names the configuration and the database's path instead. `%i` in the unit is the instance name as given (systemd.unit(5), Specifiers), the account's slug, `-` included. The unit is not enabled: the next `Stream` pass after a boot finds it inactive and starts it.

Litestream reads its credentials once, when it starts. So `Stream` restarts an account's unit, writing the environment file just before, when its configuration changed, when it is not active, or when the credentials it runs on expire within `RestartBefore` (20 minutes) and accounts has sent newer ones; the file records the expiry of the credentials it holds, and the Litestream install stamp the unit was started with, in comment lines. With `ReissueAfter` 15 minutes on accounts' side (D21) the daemon always holds credentials with about 44 minutes left, so a unit restarts about every 40 minutes, and each restart costs a final sync of up to `ShutdownSyncTimeout` (Litestream's `DB.Close` retries its last sync for `shutdown-sync-timeout`, `db.go`), well inside the unit's `TimeoutStopSec=60`. An account no longer active, or with no database left, has its unit stopped and its files removed.

**The sync check.** `litestream status -json` reports the local position, the highest transaction id in the local level-0 directory (`status.go`, `DB.MaxLTX`), and `litestream ltx -json` lists a replica's files of one level with `level`, `min_txid`, `max_txid`, `size` and `timestamp` (`ltx.go`; litestream.io, ltx reference). A database is synced when its status is `ok` and some replica level-0 file's `max_txid` is at least the local `local_txid`; `Synced` is then the time taken just before `status`, so it says the replica held every write the database had at that moment. `Written` is the newest level-0 file's `timestamp` (the time S3 last modified it) and `Oldest` the oldest level-9 file's, the earliest snapshot a restore can start from. Only levels 0 and 9 are listed: Litestream never deletes the newest level-0 file, remotely or locally (`EnforceL0RetentionByTime` keeps the last one), so level 0 always holds the newest position while level 9 holds about one snapshot a day; listing levels 1 to 3, which keep thirty-second to hourly files for the whole five weeks, would cost a hundred list requests per database each pass. A check that fails leaves the database's facts as they were; when one of its commands does not answer, that is a failure of the pass for the account, its error until a later `Stream` meets none (Pass failures, below).

**restic** (backups outcomes 9 to 14, 21). Per account, when its snapshot is due (none yet, or `EveryMinutes` since the last, which after an attempt that made no snapshot is every pass), `Backup` runs restic against `s3:s3.<region>.amazonaws.com/<bucket>/<FilesPrefix(a)>`, the path-style form restic documents for Amazon S3 with a path inside the bucket ("Preparing a new repository", Amazon S3, v0.20.0), with `--insecure-no-password` on every command (same page, "Repositories with empty password": the option "must always be specified when operating on repositories with an empty password"; restic(1) lists it as a global option) and the credentials, region (`AWS_DEFAULT_REGION`) and cache (`RESTIC_CACHE_DIR`) in the command's environment, never its arguments (the same page tells container users to avoid passing secrets as command arguments, "where they can be exposed in process listings"; restic's environment table in "Scripting" lists all four). `cat config` says whether the repository exists (exit 10 when it does not, "Scripting", since 0.17.0), and `init` makes it. The snapshot is `backup --json --host <a>` over the account folder, the home of each of its users and a manifest of its streamed databases, `BackupDir/manifest/<a>`, which records each database's path with its owner, group and mode, because the databases themselves are excluded and a whole-host restore needs both. Excluded: each streamed database with its `-wal`, `-shm` and `-journal` files, and in each home `.cache`, `.npm`, `.local/share/claude` and `.local/state/claude` (backups outcome 12, the plan's pick), and nothing else: the account folder is taken whole but for its streamed databases (backups outcome 11, git-ignored files included), so no cache-marker rule applies, since `--exclude-caches` would act on every path and drop, say, a `target/` directory holding a `CACHEDIR.TAG` inside the folder. Exclude patterns use Go's `filepath.Match` syntax, anchored by a leading `/` ("Backing up", Excluding files), so the bytes `\`, `*`, `?` and `[` of a database's name are escaped with `\` (`filepath.Match`: "'\\' c matches character c", on systems other than Windows); they are passed as `--exclude` arguments rather than an `--exclude-file`, whose contents restic expands with `os.ExpandEnv`. The summary line, "the last output line in a successful backup", carries `snapshot_id` and `backup_end` ("Scripting", JSON output); exit 3, "could not read some source data", still makes a snapshot of what could be read ("Backing up", Exit status codes), so it counts as a snapshot with an error recorded. Then `forget --host <a> --group-by host --keep-hourly 24 --keep-daily 7 --keep-monthly 1 --prune` (the settings' values; "Removing backup snapshots"), grouped by host only so the changing set of homes stays one series per account (the plan's pick: the snapshot's host is the account's slug), and `snapshots --host <a> --json`, a JSON array whose elements carry `time` ("Scripting"), for the newest `protocol.MaxSnapshots` times. Every `CheckDays` days, `check --read-data-subset=10%` (restic-check(1); the plan's pick: a tenth of the data each week, where a full read is slow and a structure-only check finds less). A command that exits 11, "Failed to lock repository", is followed by one `unlock`, which removes only stale locks (restic-unlock(1)), and the account is tried again on the next pass. Any other failure is the account's error: the `*CommandError` text and the last line restic wrote to stderr, then the pass goes on with the next account.

**The host key** (backups outcome 14). The host's own repository, `<HostPrefix>` in the bucket with the host's credentials, gets a snapshot of `/data/ssh` with the host's name as its restic host, when its last snapshot is `EveryMinutes` old or the key files' bytes changed since; it is pruned by the same policy.

**What a pass holds.** restic and Litestream write their output to `Command.Stdout`, and the pass reads it as it comes: a line of `backup --json` longer than `MaxJournalLine` is skipped, and of the JSON arrays `snapshots`, `status` and `ltx` print, a string longer than that is passed over unheld, so a pass holds at most `MaxJournalLine` bytes of any output beyond its fixed buffers, whatever the number of snapshots or replica files (Litestream's `ltx` builds its whole listing in its own process; that memory is Litestream's, bounded by the files of one level). An install holds one copy buffer and keeps the archive on disk. The walk's bounds are above. What the passes found is kept in small files under `BackupDir/status/`, each written whole by rename, so a restarted daemon reports what it knew and decides its first passes from it; `Inspect` reads at most `protocol.MaxBackupAccounts` + `protocol.MaxRestores` + 1 of them, each within `MaxCapture`. A final: one account's database sync times and one restic run at a time. A restore: one work directory per target on disk, never the restored data in memory; a `snapshots` listing read as a stream keeping one entry; a manifest read line by line keeping at most `MaxDatabasesPerAccount` paths; command output line by line (part A's rule). The memory machine: one disk per data volume a sandbox named, each holding at most what the sandbox's backups file added; at most `protocol.MaxSnapshots` snapshot times per account; one result per request of the state.

**Pass failures** (backup facts repair). A pass that fails for an account, a Litestream unit that will not start or restart above all, is that account's error in the next report, so `backup_status` shows `error` within a cycle instead of `stale` after `DatabaseStaleMinutes`. Each of `Stream` and `Backup` keeps one **pass error** per account: the first failure the call met for it that is not already its restic error, a command for its unit or its configuration (the `*CommandError` text and the command's last stderr line, as for restic, cut to `protocol.MaxBackupError`), its walk, or its own files below `BackupDir` and `ResticCache`; a later call of the same method that reaches the account and meets none empties it. A command that answers with output the pass cannot read is not a failure and is not reported, as before. Two slots, one per method, because the passes run at once and a `Backup` that succeeds must not hide a unit `Stream` cannot start. `Inspect` reports them after the restic error, which wins while both remain, so an unkept walk reads `machine.WalkUnrecorded` (its only report) whatever pass error a `Stream` that could not write `BackupDir` left. Only an account the pass backs up, active with usable credentials and past the settings check, gets a pass error: stopping and clearing the unit of an account it does not back up stays diagnostic, and a pass that returns at that check returns nil. A pass error the pass cannot keep, because `BackupDir` cannot be written, is reported by that process alone; a restarted one reports the last pass error that was kept, none when none was. Every line taken from a credentialed command's output has the three credential values replaced by `machine.Redacted` first, in the bytes already kept, and the restic error is cut to `protocol.MaxBackupError` as the pass error is. The pass still returns its error and the daemon still writes its one diagnostic line (D14).

**Facts end with the account** (backup facts repair). The passes keep facts per slug, and a slug comes back: removed, its backups deleted and placed again, it once read the earlier account's snapshot time, `healthy`, over an empty prefix, and its first snapshot was not due for up to an hour. Two rules close that. Every `Stream` and `Backup` pass drops whatever it holds and keeps for a slug its state does not list `active`, a `removed` slug and an absent one alike, its manifest included; the accounts of a whole-host restore are kept, since such a state names no accounts and the restore's steps must survive. And every fact belongs to the account's `gid`, which accounts allocates anew for each placement (`D04-store`): a fact recorded under another gid is none, so a slug placed again starts with no facts and its first snapshot due at once, whatever the host remembers, even when no pass saw the state between (a remove, a delete and a create can all land inside one long `Backup` pass) and even when a pass of the old state writes its facts after the drop. Close and open, a restart and a self-update leave the account listed with its gid; a whole-host restore names its accounts with their gids in the restore while the state names none; and the states that withhold accounts during a replace reach only the new instance, whose `BackupDir` starts empty on its new root volume. So each of them keeps every fact it kept before. A Litestream unit still running for the earlier account of a slug, which a pass never saw leave, is restarted with its local state cleared when the gid changes.

**Secrecy.** The key, secret and session token appear only in the units' environment files and in the environment of the restic and Litestream commands, never in an argument, a diagnostic line, an error text, the report or any other file. `/proc/<pid>/environ` is readable only by the process's owner, root (proc(5)), where `/proc/<pid>/cmdline` is readable by every user.

**Rollout.** The state and report members are additive (D11). A new daemon talking to the previous accounts gets no `backup` member, so it stops its units and reports `NoCredentials`, and it rolls back within a cycle anyway when accounts' digest says so (D14). An old daemon talking to a new accounts reports no `backups` member, which accounts reads as `none` (D04). Litestream keeps no state in the account folder; on a database it streams it creates its `_litestream_seq` and `_litestream_lock` tables and takes over checkpointing, holding a read transaction and running its own checkpoints (`db.go` at v0.5.17). That is inherent in the tool the owner chose for databases (backups outcome 16) and is recorded, not designed around. For the close finals and restores of the sections below:

- An old daemon ignores `backup` (R-U6VF-GCXW): it locks users the overlay sends `locked`, never writes the lock record or the marker, and takes no final, so a close under it never completes (an open cancels it, D10).
- A replace from backup caught by a rollback after `Retire`: the old daemon formats the new volume, writes no marker and seeds new folders; rolled forward, the new daemon finds no marker (the host step fails `not_empty`), or a marker left in place but an account's targets not empty (that account fails `not_empty`). Nothing is restored over them.
- A new daemon under an old accounts gets no `backup` member: the lock record, marker, finals and restores never start, and a marker left from an earlier restore stays until a state with a `backup` member and no restore reaches a `Backup` pass.
- The lock record, restore steps and results under `BackupDir` are read only by the daemon that wrote them; a rolled-back daemon ignores them and the new one finds them when it returns.
- Facts kept by the release before this one record no gid. This release takes such facts as the account's under the gid its first state gives it and keeps them with that gid from its next write, so a self-update keeps every fact and decides its first passes from them as before. The format of these files is not contract, so no test can make one; it is a finish-line observation, the self-update of a host that already holds facts. A slug removed and placed again while a daemon of the release before ran is the one case this cannot catch: that daemon kept the earlier account's facts under no gid, and they are taken as the new account's until its next snapshot. A rolled-back daemon reads a file this release wrote as before, its JSON decoding passing over the members it does not know, and drops no fact: it reports the pass errors as nothing, and a slug that comes back under it shows the defect this release repairs.
- The pass errors change nothing on the wire: they reach accounts as the `error` member of the account's `backups` entry, which every accounts since backups reads as `error` health (D04), so an accounts of the release before shows them too.

**Unproven, checked at the finish line.** Three things documentation does not settle. That restic converges when one run outlives its credentials: restic 0.20.0's documents do not say an interrupted backup's uploaded data is reused by the next run (the only mention found is the 0.9.x changelog, Bugfix #1589, of intermediate index files uploaded during a run; prune is documented resumable, Enhancement #3806), so an account whose first backup takes longer than about 44 minutes may never finish; the finish line checks that `mg` reaches healthy, and the delivery stops and reports if it does not. That restic (`init`, `backup`, `forget --prune`, `check`, `snapshots`, `unlock`) and Litestream (`replicate`, `status`, `ltx`) work under the session policy whose `s3:ListBucket` grant is conditioned on `s3:prefix` (D21): AWS documents the condition key for `ListObjectsV2`'s `prefix` parameter, but whether every list request either tool makes carries a prefix inside the account's own is not documented by either tool; minio-go's region lookup is `GetBucketLocation`, which the policy grants. And that a running unit restarted with renewed credentials picks them up and goes on streaming from where it stopped. Each is probed with a real issued credential at the finish line, as D09 lists.

## Close finals

A close (D04, D10) locks every user through the state (`Desired` sends them `locked`) and asks, in `backup.close`, for one last copy of everything before the host is called closed. The daemon side is two records and one rule.

`Apply`'s locks part, once its commands have all run without failure for a state whose `backup.close` is `C` at version `V`, leaves `BackupDir/status/locked` holding `C`, `V` and the time it first wrote that pair. That is the moment the lock is applied: every user of the state is expired and their slices stopped (R-KXYD-8O0O, R-AXUQ-0YCB), so nothing a member runs can write after it. The record is kept in the locks part, not at the end of `Apply`, because the lock is what it proves and a later part's failure (a repository outage, say) does not undo it.

The `Backup` pass, seeing `close` `C` and a lock record naming `C` with lock time `L`, takes each active account's final: it waits until every database the last `Stream` pass streamed for the account shows `Synced` later than `L`, which is a `Stream` pass that began after the lock finding the replica holding the local position (that is "Litestream has sent everything"), and then takes the account's restic snapshot whatever its schedule. The wait never blocks a pass: each `Backup` pass (one a minute, D14) checks again, and once `FinalSyncTimeout` (two minutes) has passed since `L` without it, the account's final fails with `machine.ErrNotSynced` (or `NoCredentials` when the account had no credentials). When every account's final is done or failed, the pass snapshots the host repository the same way. Each final is reported as a `protocol.Step` with the close's id: `pending` until it finishes, then `done` or `failed` with `CodeFailed`, the failure's text in the account's `error` (the host's in `host_backup`'s). An account placed while the close runs is active in a later state and gets its final at a later pass.

A retry (`retry_host`, D10) keeps the close's id and adds 1 to the host's version. The new version reaches `Apply`, whose locks part rewrites the lock record with the new version and a new lock time, and a final recorded failed is taken again only then, its timeout counted from the new lock time. A done final is never taken again while the close is asked. The finals are kept under `BackupDir`, so a restarted daemon reports them and does not repeat a done one.

**Memory.** A final holds what the pass already holds (Backups, above): one account's sync times and one restic run at a time, and the lock record of at most `MaxCapture` bytes.

## Whole-host restore

A replace from backup (D10) gives a host a new instance and a new, empty data volume, and once the old instance is terminated `Desired` names no account and no user and carries `backup.restore`: the replace's id and each account with its gid and the database paths accounts last saw. The daemon formats the volume, proves it did, restores the host key, then each account, and reports each step.

**Apply while a restore is pending.** `Apply` runs every part up to and including the data volume, then slices, and nothing after: no host key copy, no sshd, no accounts or users (the state names none anyway), no isolation, no Claude Code. Slices are kept for the same reason R-C8N6-6BNA keeps them on a host waiting for its volume: they touch only the root volume and name no account here. The host key part in particular never runs while the restore is pending, so the instance's own key never lands on the volume before the restored one.

**The marker.** In the data volume part, when the state carries a restore with id `I` and `blkid` found no signature, so that this very call ran `mkfs.xfs`, `Apply` writes `RestoreMarker` (`/data/.accountsd-restore`, mode `0600`, root's) holding exactly `restore <I>` and a LF, after the mounts. Nothing else ever writes it. So the marker proves the volume was empty and was formatted for this restore. A crash between `mkfs.xfs` and the marker leaves a volume with a signature and no marker; the restore then reports `not_empty` and the operator replaces again onto a fresh volume, which is the safe direction.

**When the pass acts.** The `Backup` pass does nothing for a restore until an `Apply` of the same process returned nil for a state carrying that restore and found the data device. The workers start only after the first `Apply` of a run returns, and each pass is handed the state of the latest `Apply` that has returned, not merely the latest fetched (D14); but the first states a new instance receives can name the old volume id (the host row learns the new volume only at `new_volume`'s advance, D10), which this instance does not have, and `Apply` then skips everything after the data volume and returns nil (R-C8N6-6BNA). Without this gate the pass would find no marker on a volume not yet attached and fail the replace. The gate is kept in memory: a restarted daemon applies again within a cycle. Once the gate is passed, the pass reads the marker; when it does not hold this restore's id, the host step fails with `protocol.CodeNotEmpty` and nothing is restored. An `Apply` that fails after `mkfs.xfs` and before the marker is written (a mount that fails, say) leaves a volume with a signature and no marker: the next `Apply` does not format it again, and once one returns nil having found the device, the pass finds no marker and fails the host step with `CodeNotEmpty`. The operator then replaces from backup again onto a fresh volume; the half-made one is kept as a replaced volume (D10). Trying to recognise a freshly formatted volume by its contents instead would reopen the question the marker settles. The gate depends on D10's replace giving the new instance the new volume in its state soon after launch (the host row's `DataVolume` recorded at `new_volume`'s advance and attached before `restore`): until a state names a volume this instance has attached, the pass waits.

**Validation.** The pass refuses a restore whose accounts fail `valid.Slug`, whose gids are below 1000, whose database paths fail `valid.DatabasePath`, or which lists more than `protocol.MaxBackupAccounts` accounts or a slug twice: the host step fails with `CodeFailed` and `machine.ErrInvalidState`'s text. `Apply` refuses a whole state whose `close` or restore `id` is not 1 to 64 bytes of lowercase letters, digits and `_` (an operation id is `op_` and 16 hex digits, D04), since `Apply` writes both into root-owned files.

**The host key.** With the host repository's credentials (`backup.host`), the pass lists the host repository's snapshots and restores the newest one's `/data/ssh` into `/data/ssh` (`restic restore <id>:/data/ssh --target /data/ssh`). The directory is root's and mode `0700` (R-CCAV-BMVD), so no team member can reach it. A host whose repository holds no snapshot (one replaced in its first hour) gets no key from it; after admission `Apply` copies the new instance's key as it does for any new volume, and SSH clients see a new host key. That is recorded below.

**Each account.** After the host step is done, for each account of the restore: the newest snapshot of its repository (`snapshots --host <a> --json`, read as a stream keeping one entry); its targets, `/srv/<a>` and each `/home/<u>` among that snapshot's paths; and the emptiness check. A target that exists and is not an empty directory makes the account's step fail with `CodeNotEmpty`, and nothing is written for that account, so outcome 32 holds even when a rollback let an old daemon seed folders on the volume while the marker stayed. Otherwise the folder is restored into a work directory `/srv/.accountsd-restore-<a>` and each home into `/home/.accountsd-restore-<u>`, both root's with mode `0700`, with `restic restore <id>:/srv --target <W> --include /<a> --overwrite if-changed` (and `:/home`, `/<u>` for a home): restic restores the folder at `<W>/<a>` with its owner, group, mode and ACLs. The manifest the snapshot holds (`BackupDir/manifest/<a>`, Backups above) is read with `restic dump`, line by line, each line giving a streamed database's owner, group, mode and path below the account folder. Each database in the union of the manifest's paths and the paths accounts last saw is restored with `litestream restore -config <W>/litestream.yml -no-expand-env -if-replica-exists -o <W>/.database /srv/<a>/<p>` to its latest write, given the owner, group and mode its manifest line records (the account's service user and group and mode `0660` for a path only accounts listed, which was never in a manifest), and moved to `<W>/<a>/<p>`; one with no replica is skipped (`-if-replica-exists`), and one restic already restored (a database that was never streamed) is left as restic restored it. Then `<W>/<a>` is renamed to `/srv/<a>` and each `<W_u>/<u>` to `/home/<u>` (an empty directory there removed first), and the step is `done`. An account whose repository holds no snapshot is genuinely new: nothing is restored and its step is done, and `Apply` seeds its folder after admission as any new folder (R-288Q-42K0).

The work directories sit directly under `/srv` and `/home`, which are root's (R-CCAV-BMVD makes `/data/srv` and `/data/home` mode `0755`), so their names cannot be taken by a team member, and a rename from them to `/srv/<a>` or `/home/<u>` stays within one mount (rename(2): `EXDEV` across mount points even of one filesystem, and `/srv` and `/home` are separate bind mounts).

**Re-runs.** A run that fails, most often because the hour's credentials ran out (D21 issues credentials with about 44 minutes left), is run again at the next pass, up to `RestoreAttempts` (3) failed runs per step, and then the step fails with `CodeFailed` and the last failure's text, so the replace fails visibly instead of waiting forever. The plan asked whether a re-run resumes. restic does: the work directories are kept across runs, and restic 0.20.0's restore documentation says that restoring into a directory that already holds files "will verify the existing file content and only restore mismatching parts to minimize downloads", `--overwrite if-changed` "speeds up the file content check by assuming that files with matching size and modification time (mtime) are already up to date" (`doc/050_restore.rst`, "Restoring in-place"). So a second run downloads only what the first did not finish, and three runs cover about three credential lifetimes of transfer. Litestream does not resume: v0.5.17's `Replica.Restore` writes `<output>.tmp` and removes it on any failure (`replica.go`, `defer os.Remove(tmpOutputPath)`), so each database starts over; a database whose restore outlasts one credential lifetime fails its account after `RestoreAttempts` runs. How long a large database's Litestream restore takes, and whether a large folder's restic restore fits in three lifetimes, are **unproven** and are finish-line observations, recorded as risk. The failed-run count is kept under `BackupDir`.

**After admission.** When the state no longer carries a restore, the pass removes the marker. `Apply` then runs every part: the host key part finds both key files restored and copies nothing (R-YU0J-J9RB), groups and users are created with `useradd --create-home` over the restored homes, and the folders exist with their seed marker `done` (or none), so R-288Q-42K0 never seeds them. `useradd --create-home` over an existing home exits 0, copies nothing from the skeleton and changes neither the home's owner nor its mode: shadow-utils 4.9 (the release AL2023 ships, `4.9-12.amzn2023.0.4` in the AL2023.9 package list) documents `-m` as "Create the user's home directory if it does not exist" (useradd(8)), and its `src/useradd.c` creates, chowns and chmods the home only when `access(home, F_OK)` fails, copies the skeleton only when it created the home, and otherwise prints "the home directory … already exists. Not copying any file from skel directory into it." and goes on to return `E_SUCCESS`. Amazon's patches to that package are not read; the restored-home case is a finish-line check.

**When the restore is dropped without admission.** accounts also stops carrying the restore when the replace that asked for it is superseded, its host deleted, or its operation finished without admission (`D04-store`), while the host stays withheld, so the state names no accounts or users. The pass then removes the marker (R-ZKUB-Y82L) and `Apply` runs every part with nothing to place: it creates no group, user or folder, and may write the new instance's host key onto the volume (R-YU0J-J9RB). That is safe: a withheld host refuses a replace that keeps the volume, so the ways on are a delete or another replace from backup, onto a fresh volume, with this one kept as replaced (D10).

**Restic facts this relies on** (restic 0.20.0, `doc/050_restore.rst`): `restore <snapshot>:<subfolder> --target <dir> --include /<p>` restores `<subfolder>/<p>` to `<dir>/<p>` ("This will restore the file `/home/user/work/foo` to `/tmp/restore/foo`"); `dump <snapshot> <file>` writes the file to standard output ("Printing files to stdout"); the repository's paths are absolute (the passes back up absolute paths, `doc/040_backup.rst`, "Absolute and relative paths"), so `/srv` and `/home` are subfolders of every snapshot. That restic restores a directory's metadata when a child of it is restored, and none for the target directory itself, is from restic 0.20.0's `internal/restorer/restorer.go` (`leaveDir` runs `restoreNodeMetadataTo` when the node is selected or a child was restored, and returns early for the target's nil node), not its documentation.

**Memory.** A restore holds one snapshot entry beside the one it reads, at most `MaxDatabasesPerAccount` manifest paths plus the account's listed paths, one line of command output, and no restored data: restic and Litestream write to disk, and the daemon only renames. The work directories are on the data volume, never in memory.

## Partial restores

An agent asks for one database as it was at a time (`restore_database`) or for files as they were in one snapshot (`restore_files`, D07). Each request reaches the host in `backup.restores` with its operation's id, and the `Backup` pass runs it once, writes the copy beside the original with a name that says when it is from, and keeps the result until the request leaves the state. Nothing that exists is changed or removed.

**Names** (backups log: restore naming). A database `data/<dir>/<name>.<ext>` is copied to `data/<dir>/<name>.restored-<T>.<ext>` (a base with no `.` after its first byte gets `<name>.restored-<T>`), `<T>` the requested time in UTC as `20060102T150405Z`. Files are copied to `restored/<T>/<path>` in the account folder, or in `/home/<user>` for a home, `<T>` the snapshot's time. When the name is taken, `-2`, `-3`, … is appended to `<T>` until one is free; for files the name that must be free is the timestamp directory `restored/<T><n>`, never the path inside it.

**A database.** `litestream restore -config <W>/litestream.yml -no-expand-env -timestamp <T> -o <W>/database /srv/<a>/<p>`. Litestream v0.5.17's `-timestamp` is exclusive: `CalcRestorePlan` (`replica.go`) skips every snapshot and every LTX file whose `CreatedAt` is not before the timestamp (`!info.CreatedAt.Before(timestamp)`), as its reference page says ("a file created at exactly the requested instant is skipped"). The tools take `as_of` to the second, so the daemon passes `as_of` plus one second: the copy holds everything Litestream stamped up to the end of the second the agent named. The copy is given the live database's owner, group and mode (read without following a link; the account's service user and group and `0660` when the live one is gone) while it is still in the work directory, then moved into place.

**Files.** The snapshot whose time, to the second, is the requested one is found by listing the account's snapshots as a stream; then `restic restore <id>:/srv/<a> --target <W>/r --include /<p>` (`:/home/<u>` for a home; no `--include` for the whole folder) restores owners, modes and ACLs, and the directories leading to `<p>`'s metadata too (restorer source, above). restic's `--include` takes patterns in `filepath.Match`'s syntax (`doc/040_backup.rst`: "Patterns use the syntax of the Go function filepath.Match"), so the daemon puts a `\` before every `\`, `*`, `?` and `[` of the path, which `filepath.Match` reads as the character itself; a path from `valid.RestorePath` always begins the pattern with `/`, never `!`. The directory `<W>/r`, which becomes `restored/<T>`, gets the account's service user and group and mode `02770` (in a home: the user, mode `0700`); when the folder has no `restored` yet, one is made in the work directory with the same owner and mode and moved in whole. Since the whole of `<W>/r` becomes the timestamp directory, vacancy is judged there: with `restored/<T>` free, `docs/a.txt` lands at `restored/<T>/docs/a.txt`, with it taken at `restored/<T>-2/docs/a.txt`, and the copy reported is the path written. Judging the reported leaf instead would pick a name that never changes with the suffix (`a.txt`) and could pick an occupied timestamp directory, which the no-replace move cannot enter.

**Credentials and config.** Each command carries the account's credentials and the region in `Command.Env` (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION`). Litestream is given a config file, never a replica URL: v0.5.17's URL path copies `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` into a static provider with an empty session token (`s3/replica_client.go`, `NewReplicaClientFromURL`), which session credentials cannot use, while the config path leaves the keys empty when the config names none (`cmd/litestream/main.go`, `NewS3ReplicaClientFromConfig`) and the client then loads the AWS SDK's default chain (`config.LoadDefaultConfig`), whose environment provider reads all three variables, session token included (AWS SDK for Go v2, "Specifying Credentials": `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`). `litestream restore -config` looks the database up by its path in the config (`Config.DBConfig`) and opens neither it nor its directory: with `-o` it writes `<output>.tmp` and renames it (`replica.go`), so the live path given is only a key. These are read from source; the real run under session credentials is the finish line's (D09).

**Where the config lives.** Each `litestream restore` gets its own config, `litestream.yml` in the directory holding its `-o` output, which is the restore's own work directory: `/srv/.accountsd-restore-<a>/litestream.yml` beside `.database` in a whole-host restore, and beside `database` in a partial one. It cannot collide. The stream configurations are `BackupDir/<a>.yml`, and the stale and invalid-config sweeps (R-Y6RR-TK2S, R-MOTD-5EBA) and the stream units read only `BackupDir`'s top level, never `/srv`. Inside the work directory the other entries are the restored folder `<a>`, which `valid.Slug` keeps free of `.` (D17, R-JJ57-TB53), `.database` with its `-wal`, `-shm` and `-journal` and Litestream's `.tmp`, or `database` and its `.tmp`; homes have work directories of their own and run no Litestream. Each restore's work directory is its own, so no two restores share a config.
**Results.** A request whose fields fail `valid` (a bad id, kind, slug or path, or a user not of the account) gets a failed result with `machine.ErrInvalidState`'s text and runs nothing. A request for an account the state no longer marks active, or with no credentials yet, waits. Every other request runs once; a failure is final (the agent asks again, D10). The result `{id, done, copy, ""}` or `{id, failed, "", error}` is kept under `BackupDir` until the state stops carrying the request.

## Writing as root where a team can write

An account folder and a home are writable by the team (`02770`) or the user (`0700`), and anything in them can be a symbolic link a member planted. Every place a restore puts something there is reached from `/srv` or `/home` one component at a time, each opened from the one above with `openat(O_NOFOLLOW|O_DIRECTORY)`, so a link or a non-directory anywhere on the way is refused, never followed with root's rights. What is put there is first made complete in a work directory directly under `/srv` or `/home`, root's with mode `0700` under a name that did not exist (`.accountsd-restore-` and more), owners and modes set while it is there (`chown --no-dereference` on paths whose every component is root's or inside that directory, which no member can reach), and only then renamed into place with `renameat2(RENAME_NOREPLACE)` under a name nothing holds. restic and Litestream are only ever given paths inside a work directory (and, to Litestream, a live database's path as the key it looks up in its config, which it does not open). A partial restore's work directory is removed on any failure (without following links), leaving nothing at the destination; a whole-host restore keeps its work directories for the next run. So a member who plants a link in their folder or home can make a restore fail, never make root write outside it. The same rule reaches inside a whole-host restore's work directory, whose contents come from a snapshot that may hold a planted link.

`RENAME_NOREPLACE` comes from rename(2) (Linux 3.15, XFS supported). The Go standard library's `syscall` package exports no `renameat2`; `golang.org/x/sys/unix` (already in accounts' module graph, `go.mod` lists `golang.org/x/sys v0.47.0` as indirect) exports `Renameat2` and `RENAME_NOREPLACE`. `internal/linux` may import `golang.org/x/sys/unix` directly: the module is already in accounts' module graph, so importing it is not a new external dependency and needs no approval (recorded below); the release stays `go.mod`'s, and no requirement names it.

## The memory machine

`Memory` holds the accounts, users, keys and folders the states it applied put on it, the digest it was last given, and fixed facts for its report. Each `Apply` first waits `ApplyDelay` through its injected `Sleep`, so the sandbox shows `pending` before `applied` (D16). It follows the same rules as the real host for what is created, locked, kept and removed, so a daemon test over it proves the daemon's side of outcome 22, and `SetFailure` makes it fail on demand.

It also holds the allowlist of the last state it applied and a set of bans, so the sandbox can show a ban listed, lifted and allowlisted (bans outcomes 4 to 13). Nothing there signs in, so `Ban` makes one by hand: the sandbox calls it when a line names the host in its bans file (D16-sandbox). A ban lasts `MemoryBanTime`, ten minutes as on a real host, and an expired ban is simply not held. Like the real jail, `Ban` refuses an address its allowlist covers and holds at most `protocol.MaxBans`; a successful `Apply` lifts every address of the state's `unban` and every ban the new allowlist covers, with no per-cycle cap since nothing is executed. `Ban` and `State` are called from the sandbox's watcher while the simulated daemon runs `Apply` and `Inspect`, so the machine is safe for that concurrent use, and neither waits out an `Apply`'s delay.

It also holds a hostname, empty when made. A successful `Apply` of a state with a non-empty `domain` sets it to the state's `host`, a dot and the domain; one with an empty `domain` leaves it; a failed `Apply` changes nothing, as for everything else it holds. It applies no hostnamectl rule and writes no drop-in: there is no machine to rename and no cloud-init to keep it (the intent's What was observed: the sandbox can show what a host is asked to call itself, never a real hostname). `State()`'s `Snapshot` carries it as `Hostname`, appended after `Bans`, and `Inspect` reports it as the report's `hostname`, so a simulated host reports the name it was asked to take (D16).

It also simulates the seed (decision P9). A successful `Apply` that makes an account's folder, the first time a state marks that slug `active`, records a seed for it: the paths of the regular files of `accounts.Seed()` and one commit, with the author, email and message a real host would give it, in `State()`'s `Seeds`, appended after `Hostname`; the sandbox lists them in its seeds file (D16). A folder it already holds, a removed account's included, is never seeded again, as on a real host. It writes no file and runs no git; it holds one list of the seed's paths per seeded account.

The memory machine holds nothing of Claude Code and the box MCP link: it records no files, fetches nothing and runs no package manager, and its `Snapshot` gains nothing for them. How a person at a sandbox runs the stdio client is D16's, and does not go through the memory machine.

It also simulates backups (plan 3.12). Machines share **disks** as instances share volumes: `NewDisks` makes a set the sandbox builds once (D16) and hands every machine with `MemoryConfig.Disks`; a machine's disk is the one keyed to the `data_volume` of the last state it applied, made empty the first time a volume is named. Folders and seeds now belong to the disk, so a replace that keeps its volume finds the old instance's folders (and its seeds, which the sandbox keeps listing), and one from backup starts on an empty disk. `AddDatabase` gives an account a database on the current disk, in WAL mode or not, and `FailBackups` makes an account's backups fail until healed; the sandbox calls them from its backups file (D16). `Put` is the memory cloud's (D16): every key a pass writes goes through it with the credentials the state carries, so a credential mistake shows as a backup error.

`Stream` streams each WAL database of an active account with credentials: it puts `accounts/<a>/data/…` until one put succeeds, then has `Oldest` that pass's time and `Synced` and `Written` every pass's while the account is not failing; a database not in WAL mode reports `NotWAL`. `Backup` takes a snapshot at the first pass, every `EveryMinutes` after, and at the next pass after one that failed or was withheld, a healed account included (a put of `accounts/<a>/files/config`), a check every `CheckDays`, and the host's snapshot (a put under the host prefix). Close finals, whole-host restores and partial restores complete at the first pass `ApplyDelay` after the pass that first saw them, so the sandbox shows `pending` first. A whole-host restore proceeds only on a disk this machine made for that restore's id; on a disk it made otherwise the host step fails `not_empty`, and on a disk another machine made (the old volume a new instance's first states still name) it waits, as a real host waits for its volume. Restored accounts join the disk's folders, so they are never seeded, and are listed in `State().Restored`. Partial restores name their copies as a real host does. `Inspect` reports all of it, and `State()` carries the same `Backups` and `Restores`.

**Where the memory machine differs from a real host.** It counts an account's or the host's credentials as present when their `AccessKeyID` is non-empty, where a real host also checks the bytes of all three values (R-Y7ZO-7BTH) and the backup member's bucket and region (R-Y6RR-TK2S): the memory cloud's `Put` is what refuses a bad credential there. It treats a close as locked once an `Apply` that returned nil applied a state naming it, where a real host records the lock in the locks part of `Apply`, with its version and time, even when a later part fails, and times a final out after `FinalSyncTimeout` from that lock; the memory machine finishes every final at the first pass `ApplyDelay` after it saw the lock, with no sync to wait for. It walks no folder, runs no restic or Litestream, writes no file and keeps nothing across a restart of the sandbox's process beyond what `sandbox-cloud.json` holds. Like a real host, it drops an account's facts once a state no longer lists it `active` and counts as none the facts it recorded under another gid, so a slug placed again in the sandbox snapshots at its first pass; it has no unit to fail, so a pass error shows there only through `FailBackups`. Its backup facts are the machine's, not the disk's, so after a replace from backup the new instance's machine starts with no snapshot history, no `Snapshot`, `Snapshots` or `Checked` until its own first pass, and no snapshot taken before the replace can be restored, where a real host keeps the history in its restic repository in S3 and lists it at its first snapshot (R-YTXV-375Z). It takes a snapshot at the next pass whenever an account's error is not empty, a final that failed included, where a real host retries by its schedule, which repeats only an attempt that made no snapshot, and a failed final by the final's own rules. A replace from backup gives every database it names back in WAL mode (R-Z3RQ-LFOV), so one that was not in WAL mode comes back a healthy streamed database, where a real host's restic restore brings it back as the file it was, still reported `NotWAL`.

## Recorded decisions

- **The helper is `accountsd` under another name** (argv[0] dispatch), not a third binary or a script: a script would need a shell, a third `cmd/` would be another build input and another download, and a link to `DaemonPath` can never drift from the daemon a self-update installs.
- **Outcome 18's "nothing readable that should not be"** is stated as owners and modes `Apply` checks every cycle: everything it installs is root's and not writable by others, the private host key not readable by them, homes `0700`, account folders `02770`, and no placed user in any group but `shell`, its account and its own private group, so none is in `wheel`, the group AL2023's sudoers admits; `Apply` writes nothing to sudoers. Key files stay world-readable (`0644`, as opsctl D21): they hold public keys, and sshd reads them as root anyway.
- **The state is checked before anything runs.** accounts validates every name, key and id (D17, D04), but `linux` puts them in command arguments, unit file names and authorized_keys files as root, so it checks them again with `valid` and refuses a whole state that fails: a key line with a line break could otherwise add an authorized_keys line with options, and an id below 1000 could reach a system account. Combined with refusing any existing group or account whose id differs from the state's (`ErrIdentity`), no system group or account can ever be handed to a customer. A refused state changes nothing, locks included; it can only come from a defect in accounts, never from a tool.
- **Locks run first.** Every other part can fail on its own (a repository outage, a missing data volume); locking is the one change that must never wait, so it runs right after the check and before them, and a user absent from the state loses their running sessions too, its slice found by file name. A user the state creates locked is created expired (`useradd --expiredate 1`), so there is no moment when it can sign in.
- **No `nofail` on `data.mount`.** An earlier draft had it; with `WantedBy=local-fs.target` (not `RequiredBy=`) a missing device already leaves boot going on, and `nofail` is an fstab option (systemd.mount(5)) that the unit does not need.
- **A host before its volume runs the AMI's sshd.** While the state names no data volume or it is not attached, the sshd part is skipped (its `HostKey` lives on the volume), so for the first minute of a new host sshd is the image's. No user exists then, so nothing can sign in but what the image allows; infra's hosts launch template sets no key pair, so not even `ec2-user` has one, and the IMDS rule is already loaded.
- **Programs by a fixed search path.** pam_exec starts the session helper with an empty environment (no `PATH`), so a bare `busctl` failed and every SSH session was refused on the first host. Every program `Apply`, `Inspect` and `Session` run goes through `Exec`, which looks names up in the AL2023 system directories itself and hands the child that same `PATH`, rather than trusting whatever environment started the process; the requirements keep naming programs bare.
- **Placement is waited for, and logind is skipped through `password-auth`.** The finish line on `host01` found about 3 of 28 sign-ins in logind's `session-<n>.scope` instead of the person slice. Two causes. The image's `/etc/pam.d/sshd` pulls `pam_systemd` in through `session include password-auth`, so the skip written only into `sshd` never applied and every session first got a logind scope; and `StartTransientUnit` returns when its job is queued, not done, so sshd could fork the shell before PID 1 moved the parent, and the shell stayed where it was. So `Apply` writes the skip before every `pam_systemd` line of `password-auth` as well (a `%config(noreplace)` file of the `pam` package on AL2023, so an update keeps it, and `Apply` restores it each cycle; it is included only by `sshd` and `remote`, and only `shell` members are skipped), and `Session` reads `/proc/<parent>/cgroup` until it names the new scope, refusing the session after `SessionWait`. busctl on AL2023's systemd 252 cannot wait for a job itself, and the cgroup is the outcome, so it is both the wait and the proof. Skipping logind costs a member no `XDG_RUNTIME_DIR`, no user manager (`systemctl --user`) and no lingering; a customer's shell, scp, sftp and a remote coding agent over SSH need none of them, and nothing of the design relies on them.
- **Locking stops the user's systemd slice too.** Before the skip reached `password-auth`, `pam_systemd` ran for every SSH session, so a person also had `user-<uid>.slice` holding their user manager and, while a session ended or when placement failed, that session's processes; a host may still hold one from then, and anything that reaches logind for the person later would make one. Stopping it with the person slice (`systemctl stop` waits for the stop job) leaves no process of the account behind, so `userdel` no longer finds one and exits 8, as it did once on the first host when a user was deleted right after a refused sign-in. Should one still survive, `userdel` fails, the cycle reports the error and the next one retries.
- **No cron or at for customers.** Processes started outside an SSH session would land in `user-<uid>.slice` (pam_systemd), outside the account's ceiling, and would survive a lock. The image is not trusted to lack them: the finish line found `at` installed on the first host (`at-3.1.23`, `atd.service` enabled and active, an empty `/etc/at.deny`, so every user could queue jobs) and `cronie` absent, so the packages part removes either when installed. No installed package requires `at` (`rpm -q --whatrequires at`).

- **Ported, not shared.** The hardening is a port of opsctl D19's bytes and commands (outcome 19); D19's parts that serve a space's apps (the `ikigenba` account, the sudo rule for accounts, the state directories) and the pool on `user.slice` are not ported: a host runs no app, and the pool is replaced by account slices. opsctl D21's linger and `turns` timer steps are not ported (no `turns` on a host), and `loginctl terminate-user` is replaced by stopping the person's slice. Sibling version: opsctl `internal/hardening.Apply`, D20, D21.
- **`AllowGroups shell` alone** (outcome 19), where D19 allows `ec2-user shell`. Operators reach a host through SSM Session Manager.
- **Packages before the IMDS rule.** An earlier draft put the IMDS rule first; it needs the `nft` program, which a new AL2023 instance gets only with the `nftables` package (opsctl D19: dnf installs it with `fail2ban-server`). Packages run first and install `nftables` too; the rule still lands before any user exists, since users come last. The nft file's bytes were loaded, reloaded and listed with nftables 1.1.3 in a user and network namespace (`unshare -rn nft -f`): both loads succeeded and left one table, and `nft list table` of an absent table exited 1. The drop itself, IMDS unreachable as a customer and reachable as root, is a finish-line check.
- **IMDS for `ssm-user`.** An operator's SSM shell runs as `ssm-user`, which loses the metadata service like any non-root uid; `sudo` gives it back. Accepted.
- **Mount by UUID**, read from `blkid -p --output export`, rather than by label: a second volume carrying the same label, such as an orphaned one attached by hand, could otherwise be mounted in its place. The filesystem type is read from the same output, so a volume formatted by anything else is still mounted and grown by its own type.
- **Bind mounts over `/home` and `/srv`.** Whatever the AMI put in the root volume's `/home` (`ec2-user`'s home) is hidden once `/home` is bound; nobody signs in as `ec2-user` (outcome 19).
- **Growth is checked per process.** `Apply` grows a filesystem the first time it runs in a process and whenever the disk's size differs from the size it last saw; growing a filesystem that already fills its disk changes nothing (xfs_growfs(8) `-d`: "grown to the largest size possible"; resize2fs(8)). The root filesystem's type is read, not assumed: that AL2023's root is XFS is unproven, so `xfs` grows with `xfs_growfs` and `ext4` with `resize2fs`, which grows a mounted ext4 online (resize2fs(8)); any other type is left as it is.
- **Updates every hour** (`UpdatesInterval`): a cycle runs every `LongPoll` at most, and dnf's metadata queries are too slow to run every cycle; an hour-old count is current enough for a page.
- **Sign-ins by cursor.** opsctl D21 asked the journal for one user's last sign-in per read; a host has up to 200 users and a cycle every 45 s, so the daemon reads forward from the last cursor and keeps the latest time per user of the state. A restarted daemon has no cursor and reads the journal from the start once, streamed.
- **No data volume, nothing to put on it** is not an error (part 10 above), so a new host's first reports are not failures and no `host.apply_failed` is told for a host still being created.
- **The jail's settings and allowlist** (bans outcomes 1, 2 and 11). `mode = normal` replaces opsctl D19's `aggressive` and the escalation lines go: under `normal` an unknown user counts once per connection and a known user's wrong key does not count (observed on `host01`, fail2ban 1.1.0, 2026-11-18), and a ban lasts ten minutes flat. `enabled`, `backend` and `banaction` stay D19's. The allowlist goes into `ignoreip` beside loopback, which is always written; jail.conf(5) documents the list as space separated addresses and CIDR masks. The state check refuses any entry `valid` would not have stored, since the entries land in a root-owned file and the addresses in command arguments.
- **Bans right after the jail.** The lift must run whatever else fails or is skipped, and a missing data volume skips every later part but slices (R-C8N6-6BNA), so it could not sit at the end; right after the jail it also runs after any reload that put a new `ignoreip` in place. It comes after locks, which must never wait.
- **A `fail2ban-client` failure stops `Apply`** like any failed command (R-S739-S0BW): the cycle reports the error and the version is not reported applied, so accounts keeps the unban pending and the next cycle tries again, as a failed reload does. In `Inspect` the bans are a fact like any other, zero when they cannot be read.
- **No coverage read in the cycle that starts fail2ban.** An allowlist can be set on a provisioning host, and right after `systemctl enable --now fail2ban.service` the server's socket may not exist yet, so a read then would fail `Apply` and tell `host.apply_failed` during creation. The coverage lift is per cycle and tied to no version, so skipping it once costs nothing: the next cycle lifts. The `unban` list's commands still run in that cycle; a failure there keeps the version unapplied and is retried, which is right.
- **The coverage lift is capped per cycle** at `protocol.MaxBans` addresses, so a part holds a bounded list whatever the jail holds; any beyond it are lifted on the next cycle, at most `protocol.LongPoll` later.
- **Times in the host's zone.** fail2ban prints its times in the host's local zone without naming it. The daemon reads them in the location of the time `Env.Now` returns, which on a host is `time.Now` in the same local zone (the hosts run in UTC), so a test controls the zone through its clock and the report is UTC whatever the host's zone.
- **The ban source and its proofs** (bans "To prove on a real host"). On `host01` (fail2ban 1.1.0, AL2023, 2026-11-18): `fail2ban-client get sshd banip --with-time` prints the form `Inspect` parses and exits 0 with one empty line when nothing is banned; `fail2ban-client set sshd unbanip <address>` of an address not banned prints `0` and exits 0, so an unban is safe to repeat; reload is `systemctl reload fail2ban.service`. A line that does not parse still counts in the total, so a format change shows as a total above the listed bans rather than as fewer bans.
- **The memory machine's bans come from a call, not a log.** A memory machine has no sshd; `Ban` stands in for fail2ban so the sandbox walk can list, lift and allowlist one without a real host.
- **The box MCP server is `accountsd` under a third name** (sheet decision 1), linked like the session helper and for the same reasons: no third binary, and the link can never drift from the daemon a self-update installs.
- **Claude Code last, and never fatal.** Every other part stops `Apply` on a failure so the version stays unapplied and the next cycle retries; Claude Code cannot, because a vendor repository outage or a rotated key would then hold back removals, which accounts finishes only once a host applied them (D10), and every later state's `applied`. It runs after isolation so a 350 MB install delays nothing that protects the host, and a failure ends only its own part.
- **Reported on stderr, not in the report.** The report's `error` means "this version did not apply", and `applied` follows it (D14 R-6QQR-2OHG); a Claude Code failure is neither. A new report member would be additive but is a protocol change step 2 prefers to avoid, so the failure is a journal line. The owner settled it: journal only, no report member.
- **Our key check, then dnf.** dnf with `-y` imports whatever key `gpgkey` serves when a package does not verify; so the part imports the key itself, only after checking its fingerprint, writes the repository file only once the key is in, and clears `gpgkey` on its own dnf commands. A key rotation by the vendor then shows as a failed upgrade until the pinned fingerprint is changed here, which is the intended gate. dnf commands outside the part (the packages part, dnf-automatic) install nothing from the Claude Code repository, so they never reach its key. Should the repository ever publish security advisories, dnf-automatic's `-y` upgrade could import its `gpgkey` unchecked; the owner accepted that risk, and dnf-automatic gets no `exclude`.
- **Key presence by rpm's short id.** `gpg-pubkey-1a7ecace` names the pinned key by the last 32 bits of its id. A different key with the same short id could only be in rpm's keyring if root imported it, and root already owns the host; checking presence this way keeps the fetch off every cycle.
- **Pacing in two clocks.** A failed part waits `ClaudeRetry` in memory, so a broken repository costs one attempt an hour; a successful or failed upgrade waits `ClaudeUpgradeInterval` on disk, so upgrades are at most daily across restarts and reboots. An install is never held for a day: a host without Claude Code tries hourly until it has it.
- **`MaxKeyBytes = 64 << 10`.** The key served on 2026-11-24 is 1,688 bytes; an armored key grows by about that much per added subkey or signature, so 64 KiB is far above any key the vendor would serve and still a fixed bound on disk.
- **Claude Code files as exact bytes** (owner). The managed settings, marketplace, plugin and `.mcp.json` files are stated as exact bytes in requirements, like every other host file `Apply` writes. That includes the words of the plugin's description: the owner accepted them inside a requirement, following this sub-project's practice for host files.
- **gpg and rpm facts checked at the finish line** (owner). Three things are not proven from documentation and are checked on a real host at the finish line: that `gnupg2-minimal` provides `/usr/bin/gpg`, that the first import names the key `gpg-pubkey-1a7ecace`, and that dnf with the cleared `gpgkey` refuses rather than imports.
- **The hostname by `hostnamectl`, kept by cloud-init's `preserve_hostname`** (log A4). Proofs: hostnamectl(1) (systemd 252, freedesktop.org, and 257 locally): the verb sets "the pretty, the static, and the transient hostname alike" unless a selector is given, and a static hostname is "either a single DNS label … or a sequence of such labels separated by single dots that forms a valid DNS FQDN", "at most 64 characters". The man page since 249 names the verb `hostname`; systemd's NEWS for 249 says the `set-*` verbs "have been replaced by a single "xyz" verb … The old names continue to be supported for compatibility", and 252's `hostnamectl.c` still lists `set-hostname` (marked obsolete) beside `hostname`. The contract names `hostnamectl set-hostname`, which works on AL2023's systemd 252 and on every systemd before 249 too. systemd-hostnamed.service(8) (252): "The static hostname is stored in /etc/hostname"; hostname(5): "The file should contain a single newline-terminated hostname string", so the trimmed content is the name. The intent's What was observed: on the hosts' image a full dotted name set as the static hostname worked cleanly and survived a reboot and a stop and start, but not a reboot after cloud-init's saved state was removed, unless cloud-init was told to preserve the hostname. cloud-init's module reference: Set Hostname "If `preserve_hostname` is set, then the hostname will not be altered" (once per instance) and Update Hostname "Do not update system hostname when `true`" (every boot).
- **The drop-in's name is `99-ikigenba.cfg`.** cloud-init reads only files ending `.cfg` in `cloud.cfg.d`; its README there says "They are read in lexical order. Later files overwrite values in earlier files", and `util.read_conf_d` (cloud-init 22.2 and current) sorts the names with Python's `sorted`, byte order. A name beginning `99-` sorts after every file the image or a package names with a lower two-digit prefix, so no such file can set `preserve_hostname` back. `ikigenba` follows the sshd drop-in's `10-ikigenba.conf`, whose prefix plays the same ordering role there. What could still outrank it is user data (cloud-init's "Configuration priority": runtime configuration outranks `/etc/cloud/cloud.cfg.d/*.cfg`); infra's hosts user data is a bash script (`templates/hosts-first-boot.sh`), not cloud-config, so it sets no key. A file named `99_…` or with a later letter would still sort after it; none is known on AL2023, and the finish line's reboot and stop-start checks the name holds.
- **The name is checked in the part, not with the state.** The state check refuses a whole state before locks (above), which is right for what a defect in accounts can put in a state; but the domain is a setting, and a bad one would then hold back every lock on every host. Checked inside the hostname part by hostnamectl's own rule, a bad domain stops the part and what follows it, never the locks, and the name never reaches `hostnamectl` as anything but one valid argument (a leading hyphen is refused, so it is never an option).
- **Trimmed content, not hostname(5)'s comment rule.** `/etc/hostname` may hold `#` comment lines (hostname(5)); systemd-hostnamed writes none. A file with one reads as differing, and `hostnamectl` rewrites it with the name alone, so the host converges; `Inspect` may report the comment until then.
- **The memory machine checks no name.** It renames nothing real, so it takes any name the state gives; the sandbox's domain is a configured one, which the real host checks.
- **The seed is built aside and renamed into place** (decisions P3, P4). Writing the marker the moment the folder is made would still leave a window, between `mkdir` and the marker, in which a crash leaves a folder that looks pre-existing and is never seeded (seed outcome 5). Building at `/srv/.<s>.seed` and renaming closes it, at the cost of one more path, which only `Apply` ever creates and which it removes whenever it finds one for an `active` account.
- **The marker is inside `.git`**, so the working tree stays clean and the team never sees it; the files and history the team owns are never consulted to decide whether to seed (seed outcome 3).
- **The seed is made by the service account, not written by root.** Writing the files as root and handing them over would have every root write in a folder the team owns follow whatever a member might plant there, and would put them under the isolation rule (R-KWQG-UW9Z), which gives every file `Apply` writes to root (the marker included, which a member could then swap for a link under a root `chmod`); `mkdir` and `tee` run through `runuser` make them exactly as a member's are made and reach nothing the service account cannot. It costs one command per entry, five at `v1`.
- **Accepted risks** (confirmed by the orchestrator): the four below.
- **An old daemon makes an unmarked folder.** A host whose self-update failed runs the old daemon, which creates a new account's folder the old way, with no marker; that account can go `active` with an empty folder the new daemon never seeds. Accepted: a failed self-update is already a fault the operator sees.
- **Durability is git's and the filesystem's.** `Apply` syncs nothing of the seed; a power loss could in principle keep a `done` marker and lose the commit, leaving the seed's files uncommitted. Accepted: the window is the moment of creation, and the files are still there for the team.
- **A building path for an account later removed stays.** `Apply` removes `/srv/.<s>.seed` only for an `active` account, and touches nothing of an account it is told is `removed` beyond R-CX15-TQH6; such a path holds an empty repository and is accepted.
- **No rewrite once committed.** An interrupted seed rewrites the seed's files only while no commit exists; once `HEAD` exists the marker is completed and nothing is written, so a change made after the commit is never undone. One window is accepted: a new release rolled back between the rename and the commit, its old daemon then creating the account's users, and the release restored, finishes a seed in a folder people could already reach.
- **Seed paths added by name with `--force`**, never `git add --all`, so the first commit holds exactly the seed, whatever else might be in the folder and whatever the seed's own `.gitignore` says.
- **The email's host name is the one the hostname part gives** (decision P5's `<host name>`), since that is what the host calls itself; on a state with no domain, the bare host name.
- **Departure.** Account slices with a PAM hook replace opsctl B5's pool on `user.slice`; IMDS is closed to non-root uids, which nothing on a space does. Both are recorded above with their proof status.
- **Two passes, not one** (the plan's pick 22). `Stream` (discovery, Litestream units, sync checks) and `Backup` (installs, restic, host key, finals, restores) are separate `Machine` methods run on separate workers (D14), so Litestream's credential restarts and sync checks never wait behind a restic run that may take most of an hour. `Backup` takes no snapshot of an account until a `Stream` call of the same `*Host` has finished a walk of that account and kept it where `Backup` can read it (R-NVHU-JD9L), so no snapshot includes a database it should exclude. A `*Host` is safe for the two passes, `Apply` and `Inspect` at once.
- **Installs are exported functions taking their pins.** `InstallRestic` and `InstallLitestream` take the version and digest as arguments, and the passes call them with the pinned constants. A digest pinned to the real asset could otherwise never be matched by a fixture, so the success path of an install (unpack, ELF check, rename, stamp) would be untestable. The names are D15's own.
- **The pins are declared without values** (the `SeedVersion` precedent, R-027W-U4P5), a departure from the design format's rule that a contract constant states its value: the format forbids a requirement to state a version. The values are in the prose above; the requirement states their form.
- **Install failures are errors at once.** A failed restic install becomes every account's error and a failed Litestream install every database's, so `backup_status` shows `error` within a minute instead of `stale` after two hours, and a host that never manages to install shows its accounts in error rather than `none`. One attempt an hour (`InstallRetry`).
- **Litestream by configuration file, never by URL.** Litestream's URL path drops the session token (source at v0.5.17), so every command names `-config` and the database's path; `-no-expand-env` on every command keeps a `$` in a database's name literal; the replica is given by `bucket` and `path` so nothing is URL-escaped. The replica's location is the plan's, `<bucket>/<DataPrefix(a)>/<path below data/>`.
- **Restart on expiry, not on every reissue.** The environment file holds the credentials the unit runs on, with their expiry in a comment, and is rewritten only when the unit restarts: on a changed configuration, an inactive unit, or credentials within `RestartBefore` of expiry when newer ones have arrived. Restarting on every reissue (every 15 minutes) would cost a final sync each time for nothing.
- **The unit is not enabled.** The passes start it; after a reboot the first `Stream` pass finds it inactive and starts it, with credentials the daemon has just been given, where an enabled unit would start at boot on credentials that may have expired.
- **The sync check lists levels 0 and 9 only.** The newest level-0 file always survives Litestream's retention, so it carries the replica's position; levels 1 to 3 keep files for the whole window and would cost about a hundred list requests per database per pass. A failed check changes no fact: staleness flags the database, and a transient error does not show as `error`.
- **A name Litestream cannot be given exactly is left to restic.** A database whose path `valid.DatabasePath` refuses or that is not valid UTF-8 is neither streamed nor reported; restic backs it up hourly with the folder. Reporting it would need a path the report cannot carry.
- **The manifest records owner, group and mode** with each database's path, where the plan wrote "one streamed database path per line": the databases are excluded from the snapshot, so nothing else in it records who owned them, and a whole-host restore gives each restored database its original owner, group and mode.
- **Exclusions as escaped arguments.** Database names are escaped for `filepath.Match` and passed as `--exclude` arguments; an `--exclude-file` would expand `$` in them. A database's path is visible in the host's process list while restic runs, as account names already are; the credentials never are.
- **The host's restic cache is `ResticCache/.host`**, where the plan wrote `ResticCache/<a>` for accounts only: a slug never begins with `.` (D17), so the host's cache can never be an account's.
- **Home exclusions** (the plan's pick 8, backups outcome 12): `.cache`, `.npm`, `.local/share/claude` and `.local/state/claude` in each home, as named patterns. The plan's "any directory holding `CACHEDIR.TAG`" is dropped: restic's `--exclude-caches` applies to every path backed up, so it would also drop cache-marked directories inside the account folder (a build's `target/`, say), which backups outcome 11 says the snapshot holds whole. Inside the folder the only exclusions are the streamed databases and their `-wal`, `-shm` and `-journal` files.
- **The weekly check reads a tenth of the data** (pick 10); **a snapshot's restic host is the account's slug, retention grouped by host** (pick 12).
- **One-hour credentials** (pick 17). restic and Litestream run on credentials that expire within the hour. A restic run longer than about 44 minutes fails and runs again on the next pass; whether it then converges is unproven (above) and observed at the finish line.
- **An error is the `*CommandError` and restic's last stderr line.** The label and exit status alone would tell an operator nothing; restic's last line names the cause (an access denial, a missing repository) and carries no credential. The report caps it at `protocol.MaxBackupError` (D11).
- **Exit 3 is a snapshot with an error.** restic made a snapshot of everything it could read, so `Snapshot` moves and the account shows `error` until a later backup reads everything.
- **Litestream changes a streamed database** (its own tables, its own checkpoints): a consequence of the owner's choice of tool, recorded rather than designed around. It never touches a database not in WAL mode.
- **The lock is recorded in the locks part** (plan 3.5 says "when an `Apply` that returns nil"). The locks part is where users are expired and their slices stopped (R-KXYD-8O0O, R-AXUQ-0YCB), and a later part's failure does not undo that; recording it there proves exactly what the final waits for, and a failing package repository cannot hold a close back.
- **Finals never block a pass.** The wait for Litestream is a condition each `Backup` pass checks, with `FinalSyncTimeout` measured from the lock time, rather than a sleep inside one pass; a test drives it with the clock, and a restic run for another account is never held behind it.
- **A failed final re-runs on a new version only.** `retry_host` adds 1 to the version (D10), so the lock record's version is the retry signal; re-running every minute would snapshot every minute while Litestream cannot sync.
- **The pass waits for its volume before reading the marker.** A new instance's first states can name the old volume (D10 records the new one later), and `Apply` then skips everything after the data volume; reading the marker before an `Apply` found the device would fail every replace from backup. The memory machine mirrors it by waiting on a disk another machine made.
- **Slices run while a restore is pending**, where plan 3.6 lists "no slices": R-C8N6-6BNA already runs slices on a host waiting for its volume, and slices touch only the root volume; keeping one rule avoids re-minting R-C8N6-6BNA. The host key part, the one that matters, never runs.
- **R-0RPX-5CWH is kept** (plan 9 lists it for re-mint): its `blkid`/`mkfs.xfs` text stays true; the marker is a separate requirement after the mounts, since `/data` must be mounted to write it.
- **Whole-host restores resume; partial restores and Litestream start over.** restic documents that a restore into a partly restored directory downloads only what differs, so the work directories are kept across runs under fixed names (safe because only root can create entries in `/srv` and `/home`); Litestream removes its partial output on failure, so a database starts over. `RestoreAttempts` still bounds a step that never finishes (plan pick 17's risk).
- **Work directories directly under `/srv` and `/home`**, not beside the destination inside the folder (plan 3.13 says "beside it"): a path handed to restic or Litestream then has no component a member can swap for a link between the daemon's check and the tool's open; the rename stays within one mount.
- **A restored database gets the owner, group and mode its manifest line records** (plan 3.6: "the owner, group and mode recorded in the snapshot for the manifest's path"). The database files are excluded from restic, so the manifest, which is in the snapshot, records them beside each path (R-MTOY-OHA2). A path only accounts listed, never in a manifest, gets the account's service user and group and `0660`, what a member's file gets in the folder under its default ACL (R-5WTB-RRWI).
- **An `Apply` that fails between `mkfs.xfs` and the marker fails the replace** (`CodeNotEmpty` once a later `Apply` returns nil having found the device). The marker can only be written once `/data` is mounted, so the window cannot be closed; failing toward a fresh replace never restores over data. Passes act on the state of the latest `Apply` that returned, and the workers start after the first one (D14), so the gate and the lock record are always read against a state `Apply` has acted on.
- **R-KWQG-UW9Z is kept.** Its subject is `Apply` ("`Apply` MUST leave … every file the requirements of this document have it write"), so the files `Backup` writes, restored copies included, are not handed to root by it; re-minting it to spell `Apply` twice would re-mint R-KXYD-8O0O, R-KR34-ANBD, R-QYMO-5NWI and R-KVIK-H4JA, which cite it, and every requirement citing those, for no change of meaning.
- **No host key snapshot is not a failure.** A host replaced before its first host-key snapshot restores no key and gets a new one at admission; failing the replace would leave a host with no way back.
- **An account with no snapshot is new.** Its step is done with nothing restored, and `Apply` seeds it after admission (plan 3.6).
- **Two error texts.** `machine.ErrNotSynced` (a final whose databases did not sync within `FinalSyncTimeout`) and `machine.ErrNoSnapshot` (a files restore whose snapshot is gone) are declared beside the other copy of `machine`; every other restore failure carries its command's `*CommandError` text, `NoCredentials` or `ErrInvalidState`'s text.
- **restic include patterns are escaped.** `valid.RestorePath` accepts `*`, `?`, `[` and `\`; unescaped, `--include` would restore more than asked, or fail on a lone `[`.
- **Memory folders and seeds belong to the disk** (so the memory machine's requirements on `Folders` and `Seeds` are replaced, not kept). R-ZKBA-QWDO stays: a removed account's slug stays among its disk's folders, which its text still says.
- **A snapshot waits for its account's walk.** `Backup` runs no snapshot command for an account until a `Stream` call of the same `*Host` has finished a walk of that account; a `Stream` that returned at the gate (a state with no `backup` member) or before walking a newly placed account does not count, so a first snapshot never takes a live database the walk would have excluded with an empty manifest. A walk that ended with `DataTooLarge` counts: the account is then backed up with the exclusions it has rather than not at all, those of its last walk that ended without that error and was kept, unless a walk of it since could not be kept (below). Restores need no walk.
- **A snapshot fails safe when its walk was not kept** (the user's pick, after the third build run found a failed status write could leave `Backup` without the exclusions). The walk only counts once `Stream` has kept its result under `BackupDir` and `Backup` can read it back, and a walk that could not be kept stops the earlier ones counting, so a snapshot's exclusions are always those of the account's last walk: a streamed database and its `-wal`, `-shm` and `-journal` files are never in a snapshot. When the walk was not kept or cannot be read, `Backup` takes nothing for that account in the pass and records `machine.WalkUnrecorded` as its error, and the next pass tries again, after the next `Stream` has kept a walk. A close final waits the same way, until `FinalSyncTimeout` after the lock, and then fails, so a host whose walks can never be kept does not hold its close open forever. Backing up without the exclusions was the alternative, rejected because a live database copied mid-write is not a backup.
- **A walk that was not kept withholds restic until a complete walk is kept** (the user's pick, after the fourth build run found that the depth-limit fallback could take its facts from a walk that was never kept). A walk that could not be kept may have found a database the kept walks never saw, so after one `Backup` takes no snapshot of the account, a close's final included, until a later walk that did not stop at `DataTooLarge` is kept and reads back; a walk that stops at the depth limit in between is kept but authorizes nothing. So no snapshot is taken with exclusions older than a walk this `*Host` knows found more, and a streamed database's files are never in a snapshot. The stopped walk's own databases, counts and facts are those of the account's last walk that ended without that error and was kept, as `Stream` reads them back from `BackupDir`, and none when there is none; an unkept walk supplies nothing to any later one. Nothing that survives a restart can record an unkept walk, since `BackupDir` was not writable when it happened, so a `*Host` made after a restart decides from what is kept (R-N3G5-QN7M): it still needs a walk of its own kept before any snapshot, and only an unkept walk of the earlier process followed by a restart and a walk that stops at the depth limit can then snapshot with the kept walk's exclusions. Withholding on every new `*Host` until a complete walk is kept was not chosen, because an account that always stops at the depth limit would then never be backed up again after the daemon's next self-update.
- **A snapshot attempt that made no snapshot is tried again at the next pass** (the user's pick, after the sandbox kept an account in `error` for most of an hour after its fault was healed). On a real host the schedule already does it: an attempt is made only when the snapshot is due, and one that records no `Snapshot`, because a command failed before `backup` recorded one, a lock, `machine.WalkUnrecorded` or unusable credentials, leaves the last `Snapshot` as old as it was, so the snapshot is still due at the next `Backup` pass (R-MSH2-APJD's example). The sandbox's lag was the memory machine's, which after a heal waited for its schedule; it now takes a snapshot at the next pass whenever the account's error is not empty (R-8RX7-64FH). A `backup` that answered 3 made a snapshot of what it could read: it counts for the schedule, so the next attempt is at the next scheduled snapshot, and the account keeps its error until a pass runs its commands without failure, normally that next snapshot, so it stays flagged; so does a `forget` or `snapshots` that failed after a snapshot was recorded. A fault that persists therefore costs at most one attempt of the account's restic commands per `Backup` pass, and a pass begins at most once a `BackupTick` and never beside another (D14). No backoff is added, following the machine's precedent for a failing restic run: a lock, an expired credential and a restore step are each run again at the next pass, and a check that failed is due at every pass already; `InstallRetry`'s and `ClaudeRetry`'s hour pace only an install, a download from outside, and would bring back the hour's wait this pick removes; the daemon's doubling backoff stops at `MaxBackoff`, a minute, which the `BackupTick` already gives. A close's final keeps its own rules (R-N5VY-I6P0).
- **Redirects may stay on `http`.** The plan says each redirect goes to an `https` URL. `Get` follows a redirect to `http` only from an `http` URL and never from `https` to anything else, because the tests serve `Get` on loopback over plain `httptest`, which no client of `Get`'s trusts over TLS, and a rule refusing every `http` redirect could not be shown to follow one. Every URL `Get` is handed in production (`ClaudeKeyURL`, the release assets) is `https`, so in production only `https` is ever followed.
- **The output bound is measured.** A pass's hold on command output is proved by heap in use, sampled halfway through a 256 MiB output, so an implementation that buffers the whole output and then splits it fails the test.
- **Litestream's restore output is cleared before each run.** Litestream v0.5.17 refuses an `-o` path that exists and is not empty, or whose `-wal`, `-shm` or `-journal` exists (`prepareOutputPath`, `cmd/litestream/restore.go`), and a whole-host restore keeps its work directory across runs, so each `litestream restore` there is preceded by removing those four paths. Every `litestream restore` also passes `-no-expand-env`, since a database path may hold `$` (`valid.DatabasePath` accepts it).
- **A re-run of a whole-host restore resumes, never rechecks.** The emptiness check runs on a step's first run only, its passing recorded under `BackupDir`, and every target moved into place is recorded as moved; a later run neither checks, restores nor moves a moved target. Otherwise a run that moved the folder and then failed on a home would find its own folder at `/srv/<a>` and fail the replace `not_empty`.
- **Root's ownership of work directories is set, not assumed**, by `chown --no-dereference root:root` when `Lstat` shows another owner (the R-KWQG-UW9Z and R-OD2V-MRI2 precedent), so a test running as an ordinary user sees the command rather than an unprovable owner.
- **Paths inside a snapshot are host paths resolved under `Root`**, the paths the backups named, so a test's snapshot holds `<root>/srv/acme` and a host's `/srv/acme`.
- **The safe-write mechanism is prose.** The requirement on writes beneath a team's folder states what a test sees (a link on the way fails the restore, nothing is created beneath its target or outside `Root`, nothing already at a destination is replaced); the `openat` walk with `O_NOFOLLOW|O_DIRECTORY` and `renameat2(RENAME_NOREPLACE)` that achieve it are described under Writing as root, above.
- **`golang.org/x/sys/unix` may be imported by `internal/linux`** for `renameat2(RENAME_NOREPLACE)`, which the standard library does not export. The module is already in accounts' module graph (`go.mod` requires it indirectly), so this adds no external dependency; the build run uses the release `go.mod` already holds, and no requirement names a version.
- **No `--exclude-caches`** (a departure from the plan's pick 8): see Home exclusions above.
- **A pass failure is the account's error** (backup facts repair, the user's decision). Before it, a pass error was a diagnostic only and a Litestream unit that would not start showed as `stale` after ten minutes. The user decided that a pass that fails for an account, a unit that will not start or restart included, is its error on the next report and clears at the next pass that succeeds. A failed sync check is such a failure, so it now shows `error` for one pass where the earlier design left it to staleness so as not to flap; the decision covers it, and the facts the check measures are still left as they were.
- **Facts are dropped with the account and bound to its gid** (backup facts repair, the user's decision for the drop). Dropping alone would miss a slug that comes back before a pass sees it gone and a pass of the old state that writes after the drop; the gid, which accounts never reuses, catches both, so the decision's "whatever the host remembers" holds on the host. Keying the files by gid instead of slug was not needed: the drop keeps one set per slug, and the bound `Inspect` reads under (R-N3G5-QN7M) stays per account.
- **A changed Litestream pin restarts the units.** A running unit keeps the old binary's inode, so each unit's environment file records, in a comment line, the Litestream install stamp it was started with, and `Stream` restarts a unit whose line differs from the stamp now in `BackupDir`. The restart is keyed on that recorded stamp, not on whether this pass's install replaced the binary, because a test cannot make an install with the pinned digest succeed, while it can write a stamp and an environment file that disagree.
- **Installs are synced before the rename**, as the daemon's own self-update is (R-D5KG-I4O1), so a power loss right after the rename leaves either the old binary or the whole new one.
- **The memory machine's simplifications** (credential presence by a non-empty key id; a close locked by any successful `Apply` of it, its finals done one `ApplyDelay` later) are recorded above; they keep the sandbox walk deterministic without a real lock or sync to wait for.
