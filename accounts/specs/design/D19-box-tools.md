# D19-box-tools

The box tools: the MCP tools a person reaches from a shell on one of the business's hosts, through Claude Code on that host, to keep their own SSH keys and, as an admin of their account, their account's users and invites (outcomes 16 to 27 of /home/mgreenly/Documents/ikigenba-self-service-accounts.md, 27 as it applies to the box; outcomes cited as outcome N are that document's). This document owns package `internal/box`: its actor prefix, its `Config`, the two registration functions that put the box tools on an appkit `mcp.Server`, the argument and result types the box adds, and the box's copy constants. The central tools (`D07-tools`) are unchanged and keep full control: an operator at `/mcp` can still do everything a box call refuses.

What this document cites from the others: `D07-tools` for the central tools a box call mirrors, their names (`tools.ToolAddKey` and the rest), argument copy (`tools.ArgKey`, `ArgAdmin`, `ArgInvite`), result types, refusal constants and answers; `D04-store` for the store and its guarded twins (`UserNamed`, `AddKeyAs`, `RemoveKeyAs`, `AdminCheck`, `UsersAs`, `LockAs`, `UnlockAs`, `DeleteAs`, `SetAdminAs`, `CreateInviteAs`, `InvitesAs`, `RevokeInviteAs`), which check the actor's own state in the same transaction as the read or write; `D08-trail` for the events; `D17-names-keys-sizes` for `valid.ParseKey` and the caps; `D13-daemon-endpoints` for the path that serves these servers and the tier choice; `D03-serve` for the wiring. appkit's `mcp`, `identity` and `telemetry` packages own their contracts.

## The chain

`claude` on the host starts `accountsd-mcp` (the stdio server, `internal/boxmcp`, `D20-box-mcp`), which relays each `tools/list` and `tools/call` line over a unix socket to `accountsd` (`internal/daemon`, `D14-accountsd`); `accountsd` forwards it as `POST /accountsd/v1/box?uid=N` with the host's identity header to accounts' `daemonapi` (`D13-daemon-endpoints`), which hands it to a box `mcp.Server` (`internal/box`, this document), whose tools read and write the store (`D04-store`) and tell the trail (`D08-trail`).

The host's daemon learns the caller's uid from the kernel and forwards the JSON-RPC request under the host's own identity. accounts resolves the verified host and uid to an active user of an account placed on that host (`D04-store`'s `ActiveUserByUID`, `D13-daemon-endpoints`) and serves the request with one of two box servers, under the caller `identity.Caller{UserID: box.ActorPrefix + <the user's name>}`. Names are unique across the whole space (`D17-names-keys-sizes`), so the name alone fixes the account and the host. This document starts at that caller: it never sees a uid, a host or a header, and it never reads a name or an account from anything the host says.

## The two tiers

`RegisterUser` puts the three tools every user has on a server: `keys`, `add_key`, `remove_key`. `RegisterAdmin` puts all eleven on another: those three, then `users`, `lock_user`, `unlock_user`, `delete_user`, `set_admin`, `create_invite`, `list_invites`, `revoke_invite`, the central catalog's order. `D13-daemon-endpoints` answers `tools/list` from the user server for a user who is not an admin and from the admin server for an admin, and serves every `tools/call` from the admin server. So a user who is not an admin is never offered an admin tool, and is refused one regardless (outcome 26): every admin tool checks, in the same store transaction as its read or write, that the actor is still an active admin of its account. A demotion that races a call is refused too.

No tool takes an `account`: the account is always the actor's. Names follow the central tools, so an agent that knows one catalog knows the other. Every name but `keys` is the central constant (`tools.ToolAddKey`, `ToolRemoveKey`, `ToolUsers`, `ToolLockUser`, `ToolUnlockUser`, `ToolDeleteUser`, `ToolSetAdmin`, `ToolCreateInvite`, `ToolListInvites`, `ToolRevokeInvite`); `keys` is new (`box.ToolKeys`), since the central catalog reads a user's keys through `users`.

| Tool | Tier | Effect | Takes | Answers |
|---|---|---|---|---|
| `keys` | user | read | nothing | `box.KeyList`: the actor's name and key lines |
| `add_key` | user | additive | `key` | `tools.UserChange` |
| `remove_key` | user | destructive | `key` | `tools.KeyRemoved` |
| `users` | admin | read | nothing | `box.UserList`: every user of the account |
| `lock_user` | admin | additive | `user` | `tools.UserChange` |
| `unlock_user` | admin | additive | `user` | `tools.UserChange` |
| `delete_user` | admin | destructive | `user` | `tools.UserChange` |
| `set_admin` | admin | additive | `user`, `admin` | `tools.UserChange` |
| `create_invite` | admin | additive | nothing | `tools.InviteMade`, always `admin` false |
| `list_invites` | admin | read | nothing | `tools.InviteList` |
| `revoke_invite` | admin | destructive | `invite` | `tools.Invite` |

## The actor

The caller's `UserID` is `ssh:` (`box.ActorPrefix`) followed by the SSH user's name. The part after the prefix is the **actor**. The actor's user is the user the store holds under that name, and A, the account, is that user's account. A caller with no prefix, or nothing after it, has no actor: a user tool answers it `tools.NoUser` and an admin tool `OnlyAdmin`, before anything is read. Auth's user ids carry no prefix and no `:` (`D17-names-keys-sizes`), so a space caller can never be mistaken for a box actor, and the store caps every caller id it records at `valid.MaxUserIDBytes`, which `ssh:` and a 32-byte name fit.

An actor is **active** when its user is `active` and A is not being removed; it is an **active admin** when its user is also an admin. A pending or failed account counts, as it does for the daemon's resolution (`D04-store`).

## The central twin

Each box tool but `keys` and `users` mirrors one central call, its **central twin**: the same tool, made by the same caller, with `account` A and, for the key tools, `user` the actor. The box does not share the central handlers. It calls the store's guarded twins (`D04-store`, whose R-RLI6-NN3V names each `*As` method's central twin method, as this document names each box call's central twin call), each of which checks the actor's guard in its own transaction and then does exactly what the central store method does. Its answer, its refusals and its change to the record are its twin's, except for the differences listed here, and a test proves this by making the box call and its twin on two stores built the same way.

The differences:

- **Every box key write checks the actor is active** (the self guard). A locked actor, one whose account is being removed, or one that names no user is refused `tools.NoUser`, where the twin would add or remove the key on a locked user. The daemon already refuses such a person before forwarding (`D14-accountsd`), so this answer is reached only by a race a few milliseconds wide; the next request gets the daemon's own refusal.
- **`remove_key` keeps the last key**: removing the one key the actor holds is refused `LastKey`, after `KeyNotHeld`. Central `remove_key` still removes it (outcome 22).
- **Every admin tool checks the admin guard first**, before any argument, link or target refusal: a non-admin always gets `OnlyAdmin` and learns nothing about targets (outcome 26). This departs from the central order (shape, then record): for the admin tools an empty `user` and a malformed `invite` are answered after the guard, so while the store fails they get `store.Unreachable` where the central `revoke_invite` would answer `NoInvite`.
- **A target outside A is an unknown user**: `lock_user`, `unlock_user`, `delete_user` and `set_admin` of a user of another account, of no user, or of an empty name answer `tools.NoUser`, never `NotInAccount` (outcome 23), and `revoke_invite` of another account's invite answers `tools.NoInvite`, as an unknown one does.
- **An admin cannot act on itself**: `lock_user` and `delete_user` of the actor, and `set_admin` of the actor with `admin` false, are refused `NotSelf` (outcome 3). `unlock_user` of the actor and `set_admin` of it with `admin` true are already so, and answer as such.
- **`create_invite` makes only ordinary invites**: it has no `admin` member, so no box call mints an admin (outcomes 9 and 10). Without a link base it writes nothing and answers `OnlyAdmin` to a non-admin and `NoLink` to an admin.
- **No `NotConfigured`**: a box call reaches accounts only from a verified host's active user, which an unconfigured space cannot have, so the box has no `Configured` and no cloud. A lock or delete raises the host's version through the store, as the central tool does, and the host's long poll wakes through the store's watch; no box tool calls `Wake`.

`keys` answers the actor's own name and key lines, whatever the actor's state: it is a read of one's own record, and the daemon already turns away a person who is not active. `users` answers every user of A, in name order, as `box.User`: the central user answer without `account`, which is always the caller's, and without `keys`, which an admin cannot act on from the box and which would make the list too large to send whole.

## Checks and refusals

A refusal is an MCP error result whose one text block holds exactly one copy constant: a box refusal constant (`LastKey`, `NotSelf`, `OnlyAdmin`), a central refusal constant (`tools.InvalidKey`, `KeyNotHeld`, `TooManyKeys`, `NoUser`, `UserRemoving`, `UserNotLocked`, `TooManyInvites`, `NoInvite`, `NoLink`, `AccountRemoving`), or `store.Unreachable`.

- **`keys`**: no actor (`NoUser`); the store fails (`store.Unreachable`); the actor names no user (`NoUser`).
- **`add_key`, `remove_key`**: `InvalidKey` from `valid.ParseKey`, with nothing read, even while the store fails; no actor (`NoUser`); the store fails; the actor is not active (`NoUser`); then the twin's checks, with `remove_key`'s `LastKey` after `KeyNotHeld`.
- **The eight admin tools**: no actor (`OnlyAdmin`); the store fails; the actor is not an active admin (`OnlyAdmin`); then the target (`NoUser`, `NoInvite`), then `NotSelf`, then the twin's checks. `create_invite` asks `Config.AccountsURL` first, as its twin does; with no link base it answers by the guard alone and writes nothing.

## Copy

The words live in Go constants in `internal/box`, declared here by name only. The build puts these words in them (the settled contract for the box path, decision 7):

- `DescribeKeys`: "List your own SSH user's public keys."
- `DescribeAddKey`: "Add a public key to your own SSH user."
- `DescribeRemoveKey`: "Remove a public key from your own SSH user; your last key stays."
- `DescribeUsers`: "List the users of your account."
- `DescribeCreateInvite`: "Make an invite link that adds one ordinary user to your account."
- `DescribeListInvites`: "List your account's unused invites."
- `DescribeRevokeInvite`: "Revoke an unused invite of your account."
- `DescribeLockUser`: "Lock a user of your account and end their sessions."
- `DescribeUnlockUser`: "Restore access to a locked user of your account."
- `DescribeDeleteUser`: "Delete a locked user of your account and their home."
- `DescribeSetAdmin`: "Make a user of your account an admin or an ordinary user."
- `ArgUser`: "SSH user name in your account."
- `LastKey`: "you cannot remove your last key from the host"
- `NotSelf`: "you cannot lock, delete or demote yourself"
- `OnlyAdmin`: "only an admin of your account can do that"

Each description passes appkit's summary rule (one line, ending in `.`, no `. ` inside, at most 120 runes), so registration does not panic; the requirement that registration succeeds and lists each description is what catches a description that breaks the rule. `key`, `invite` and `admin` reuse `tools.ArgKey`, `tools.ArgInvite` and `tools.ArgAdmin`, which mean the same here. The box has its own `ArgUser` because its `user` is always in the caller's account. Because the tool list reaches the host through accounts, the words live only here, never on the host.

## Events

A box change is recorded as a central one is (outcome 27): one `change.finished` per accepted changing call, and before it `invite.created`, `invite.revoked` or `admin.changed` when the call made, revoked or changed them, through the same `D08-trail` functions. The event's `User` is the caller's `UserID`, `ssh:<name>`, so the trail says which host user acted; the email is empty. In `change.finished`, `tool` is the central name, `account` A and `host` A's host (both empty when the call has no actor, its actor names no user, or the store cannot be read), `user` the actor for the key tools, the call's `user` for the four user-changing admin tools and empty for the invite tools, and `ip` empty. `LastKey`, `NotSelf`, `OnlyAdmin` and every `NoUser` are `refused`; `store.Unreachable` is `failed`. An invite made from the box records `CreatedBy` `ssh:<name>`, so the later `invite.used` (`D18-enrollment`) points back to the inviting host user through the invite id. The reads (`keys`, `users`, `list_invites`) tell nothing but appkit's `tool.called`. No event carries a token, a key, or part of either: the trail functions take none.

## Answer sizes

Every answer goes back through `D13-daemon-endpoints`, which relays it unbuffered and bounds it by `protocol.MaxBoxAnswer` (1 MiB) by construction. The worst cases, as appkit writes the whole result (the envelope, the text copy and `structuredContent`, every string at its worst JSON escape), are:

- `users`: at most `valid.MaxUsersPerHost` (200) users, with 32-byte names and a `created_by` at the store's 64-byte cap of all `<`: 243,333 bytes; about 91 KB with real auth ids.
- `keys`: at most `valid.MaxKeysPerUser` (10) lines of at most `valid.MaxKeyBytes` (512) bytes, every comment byte `<`: 57,949 bytes.
- `list_invites`: at most `store.MaxInvites` (20) invites: 24,177 bytes.
- `tools/list` of the admin tier: eleven tools, a few KB.

A string JSON-RPC id echoes up to `protocol.MaxBoxRequest` (64 KiB) more, so the largest answer is about 309 KB. No list is paged: each is bounded by a constant cap and listed whole.

## Bounded work

- `keys` holds one user and at most `valid.MaxKeysPerUser` keys.
- `users` holds at most `valid.MaxUsersPerHost` users of one account (with their keys, as `UsersOf` reads them: at most 200 × 10 × 512 bytes, about 1 MB), and the answer appkit builds from them.
- `list_invites` holds at most `store.MaxInvites` invites.
- Every other tool holds the actor, one target user or one invite, the account's host name and one count (`D04-store`).
- appkit holds the encoded result, its text copy and the response at once: at most about three times the worst answer above, under 1 MB.
- No box tool starts background work, keeps state between calls, reaches a cloud or wakes the engine.

## Recorded decisions

- **Two servers, not a filtered list.** The tier split is two `mcp.Server`s, one per tier, so `tools/list` is what appkit answers for each and the copy lives in one place. `tools/call` always goes to the admin server, and every admin tool refuses a non-admin itself, so the tier choice is never the only check.
- **Guarded store twins, not shared handler bodies** (supersedes `D07-tools`' "Room for step 2"). Central handlers take an `account` and answer `NotInAccount`; the box has no account argument and must answer a foreign target as unknown, and its actor checks must hold in the same transaction as the write. The store's `*As` methods put the guard and the write in one transaction and then run exactly the central store method, so each guard lives in one copy. Behaviour is tied to the central tools by the twin requirement, not by shared code.
- **Admin guard first** (departure from `D07-tools`' shape-then-record order): a non-admin gets one answer for every admin tool, whatever its arguments, and learns nothing about targets or links.
- **A self key write by an actor no longer active answers `tools.NoUser`** (owner's decision): the closest existing refusal. The daemon's "not an active user" words belong to `internal/daemon`, which `internal/box` cannot import. An admin tool's actor in the same race answers `OnlyAdmin`.
- **A caller with no actor is refused before anything is read**: a box server is only ever handed a caller D13 built, so a caller with no actor is a wiring fault, and answering it without the store keeps it from costing a read.
- **The actor is a name, not a uid.** The box server sees only `Caller.UserID`; names are unique across the space, and the uid was already resolved to the name by D13.
- **`users` drops `keys` and `account`** (owner's decision: box `users` shows no keys). With keys, the worst case is about 13 MB and would need paging the box does not offer; an admin cannot act on another user's keys from the box. The account is always the caller's.
- **No paging** (departure from `shape/` Listing): `users`, `keys` and `list_invites` are each bounded by a constant cap and answered whole, as the central `list_invites` is.
- **`keys` is a new tool.** The central catalog reads keys through `users`, which the box keeps for admins and strips of keys; a user who is not an admin needs a read of their own keys.
- **`keys` answers whatever the actor's state**: it reads only the actor's own record, and the daemon and D13 already turn away a person who is not active.
- **An admin may lock, delete or demote another admin of its account** (owner's decision): the box forbids only acting on oneself (outcome 3), and otherwise runs the central rules.
- **Invites outlive their maker's admin rights** (owner's decision, as centrally): an invite made from the box stays usable after its maker is demoted, locked or deleted. The invite is the approval, any admin of the account can revoke it, and `CreatedBy` keeps naming the host user who made it.
- **The tools page does not list the box tools** (owner's decision): `tools.html` (`D06-pages`) lists the gateway's catalog, `/mcp`'s server, and the box servers are reached only from a host.
- **The guard's same transaction is not proved at this seam** (owner's decision, with `D04-store`'s R-CHYK-RE03 as precedent): that each box write judges its actor in the transaction that writes is `D04-store`'s requirement on the `*As` methods. At the box seam a race between a demotion and a call cannot be told from the two run one after the other, so this document states the guard on calls made in sequence.

## Consumer usage

`cli.Run` (`D03-serve`) builds both servers from `Process.MCP`, since only `main` may read the environment `mcp.NewServer` reads, and hands them to the daemon endpoints: `bu, ba := p.MCP(w), p.MCP(w)`; `bc := box.Config{Store: st, Telemetry: w, AccountsURL: func() (string, error) { return s.AccountsURL(path) }}`; `box.RegisterUser(bu, bc)`; `box.RegisterAdmin(ba, bc)`; then `daemonapi.New(ctx, daemonapi.Config{…, BoxUser: bu, BoxAdmin: ba})`.

`daemonapi` (`D13-daemon-endpoints`) serves a resolved request with `ba.ServeHTTP` (or `bu.ServeHTTP` for a non-admin's `tools/list`) under `identity.Caller{UserID: box.ActorPrefix + u.Name, RequestID: q}`.

Through Claude Code on `host01`, as the SSH user `daffy`, an admin of `acme`:

1. `tools/list` → eleven tools, each description a `box.Describe*` constant.
2. `keys{}` → `box.KeyList{User: "daffy", Keys: []string{"ssh-ed25519 AAAA… daffy@laptop"}}`.
3. `add_key{key: "ssh-ed25519 BBBB… daffy@desk"}` → `tools.UserChange{User: "daffy", Account: "acme", Admin: true, State: "active", Pending: true}`; `remove_key{key: "ssh-ed25519 AAAA…"}` → `tools.KeyRemoved{…, KeysLeft: 1}`; `remove_key` of the last one → refused `box.LastKey`.
4. `users{}` → `box.UserList{Users: []box.User{{User: "bugs", Admin: false, State: "active", …, CreatedBy: "ssh:daffy"}, {User: "daffy", Admin: true, …}}}`.
5. `create_invite{}` → `tools.InviteMade{Invite: "iv_…", Account: "acme", Admin: false, CreatedBy: "ssh:daffy", Link: "https://accounts.metaspot.org/join/inv_…"}`; `list_invites{}` → `tools.InviteList{Invites: []tools.Invite{{Invite: "iv_…", …}}}`; `revoke_invite{invite: "iv_…"}` → `tools.Invite{…}`.
6. `set_admin{user: "bugs", admin: true}` → `tools.UserChange{User: "bugs", Account: "acme", Admin: true, …}`; `set_admin{user: "daffy", admin: false}` → refused `box.NotSelf`.
7. `lock_user{user: "bugs"}` → `tools.UserChange{User: "bugs", State: "locked", Pending: true}`; `delete_user{user: "bugs"}` → `State: "removing"`; `lock_user{user: "daffy"}` → refused `box.NotSelf`; `lock_user{user: "elmer"}`, `elmer` being a user of `beta` → refused `tools.NoUser`.

As `bugs`, an ordinary user: `tools/list` → `keys`, `add_key`, `remove_key`; `users{}`, sent anyway → refused `box.OnlyAdmin`.

A test sets `IKIGENBA_SERVICES` with `t.Setenv`, builds a store on its own database with a clock and a random source it controls and a writer over a `telemetry.Capture`, makes hosts, accounts and users with the store's own methods, calls `mcp.NewServer` and `box.RegisterUser` or `box.RegisterAdmin`, serves the server inside `identity.Require` with `httptest`, and calls it through `mcp.Client` as `identity.Caller{UserID: box.ActorPrefix + "daffy"}`. It compares each box call with its central twin: the same records built on a second store, `tools.Register` on a second server, the same caller. It flips `SetFailing(true)` for `store.Unreachable` and reads events from the capture after `Flush`.
