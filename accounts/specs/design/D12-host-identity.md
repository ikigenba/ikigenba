# D12-host-identity

How a host proves to accounts which EC2 instance it is (outcome 21 of ikigenba-ssh-hosts.md, the identity half). This document owns package `internal/hostauth`. The daemon side presigns an AWS STS `GetCallerIdentity` request with the host's instance-role credentials and sends it as a header. accounts parses the header, checks it hard before making any outbound call, executes the presigned request against STS itself, and accepts the caller only when STS answers with the hosts' role in accounts' own AWS account, in a session named for an instance. `Verify` returns that instance id. `D13-daemon-endpoints` maps it to exactly one live host with `D04-store`'s `HostByInstance`, and answers 403 when no host matches.

## The header

`Header(ctx, presigner, binding)` is the daemon's half. It asks the presigner (`D05-cloud`'s `cloud.Presigner`, implemented by `cloud/awshost` on a host and by `D16-sandbox`'s memory cloud in the sandbox) for a presigned `GetCallerIdentity` URL. The URL expires after `PresignExpires` and is signed over the header `BindingHeader` carrying the binding. `Header` returns the URL encoded with `base64.RawURLEncoding`, and the daemon sends that as `HeaderName` on every request. A daemon makes a fresh header per request, since accounts accepts each one once. The binding is the host part, port included and lowercased, of the daemon's `ACCOUNTS_URL` (`D14-accountsd`). It comes from the instance's `AccountsURL` tag, which carries accounts' own base URL (`D01-layout-and-run-seam`), so it equals accounts' configured binding.

## Verification, in order

`Verify(ctx, header)` refuses at the first failure. Each check runs before any outbound call:

1. **Shape** (`ErrMalformed`): the header must be present and at most `MaxHeaderBytes`, decode as raw URL-safe base64, and parse as a URL. The scheme must be `https`. The URL must have no user info, port or fragment. Its host must be exactly `sts.<Region>.amazonaws.com`, so accounts never fetches a URL a caller chose, and its path must be `/`. The query must hold exactly one `Action=GetCallerIdentity`, `Version=2011-06-15` and `X-Amz-Algorithm=AWS4-HMAC-SHA256`, a `X-Amz-SignedHeaders` whose `;`-separated list includes `host` and `x-ikigenba-accounts`, an `X-Amz-Expires` from 1 to `MaxExpires`, an `X-Amz-Date` in SigV4's basic form, and a non-empty `X-Amz-Signature`.
2. **Freshness** (`ErrStale`): `X-Amz-Date` must lie between `Freshness` before now and `MaxSkew` after it. accounts judges freshness itself and does not trust STS to expire the URL.
3. **Replay** (`ErrReplayed`): a signature STS has already accepted is refused, whatever else the URL holds. A request carrying a signature whose STS call is in progress waits for it: if STS accepted, the waiter is `ErrReplayed`; otherwise it carries on as if it had not waited. At most one request per signature ever succeeds, concurrent copies included, and a burst of copies of a good header costs one STS call. The signature must be 64 lowercase hex digits, so a case variant is never a second key.
4. **Binding** (`ErrUnavailable`): `Binding()` is read from configuration (`D01-layout-and-run-seam`), never from the request. An error or an empty value means accounts cannot say who it is.
5. **Admission** (`ErrBusy`): a token bucket of `VerifyRate` per second, with burst `VerifyBurst`, shared by every caller, and at most `VerifyBurst` STS calls in flight. Unverified traffic is bounded before it reaches STS.
6. **STS** (`ErrRejected` / `ErrUnavailable`): `STS.CallerOf(url, binding)` executes the GET with the binding header set by accounts. A header presigned for any other binding therefore fails STS's signature check. A transient failure is `ErrUnavailable`, any other failure `ErrRejected`. Once STS answers a caller, the signature is remembered.
7. **Caller** (`ErrRejected` / `ErrUnavailable`): the caller's account must equal accounts' own account (`STS.Account()`, fetched once and cached after its first success; a failure is `ErrUnavailable`). Its `Arn` must be exactly `arn:aws:sts::<account>:assumed-role/<Role>/<session>`, its `session` must match `^i-[0-9a-f]{8,17}$`, and its `UserID` must be `<role id>:<session>`. The session is the instance id `Verify` returns.

## Errors and what they mean to the daemon

`ErrMalformed`, `ErrStale`, `ErrReplayed` and `ErrRejected` are refusals; `D13-daemon-endpoints` answers each one 401. `ErrUnavailable` and `ErrBusy` mean accounts cannot judge right now, and are answered 503. A daemon backs off and retries with a fresh header after either kind (`D14-accountsd`), and keeps its host's last applied state meanwhile (outcome 22).

## External facts relied on

- The presigned URL's shape (GET; `https://sts.<region>.amazonaws.com/` with `Action`, `Version`, `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Security-Token`, `X-Amz-SignedHeaders`, `X-Amz-Signature`). A custom signed header appears in `X-Amz-SignedHeaders` in lower case, and the SDK sets no `X-Amz-Expires` unless a wrapping presigner does. All of this was observed by a probe with the real SDK (facts.md §2). `D05-cloud`'s presigner sets both the header and the expiry.
- `GetCallerIdentity` needs no permission, and its result carries `Account`, `Arn` and `UserId` (AWS STS API reference, GetCallerIdentity). An assumed-role session's ARN is `arn:aws:sts::<account>:assumed-role/<role-name>/<role-session-name>` (IAM User Guide, IAM identifiers, IAM ARNs; checked 2026-11-17). Its `UserId` is `<role id>:<role-session-name>` (GetCallerIdentity, example 2). For a role assigned to an EC2 instance, `aws:userid` is `<role-id>:<ec2-instance-id>` (IAM User Guide, policy variables, principal table; facts.md §2). So the session of an instance's credentials is its instance id.
- Executing a presigned `GetCallerIdentity` server-side, binding it with a signed header the verifier sets itself, keeping an allowlist of STS hosts, refusing redirects and timing out at 10 seconds are the published practice of aws-iam-authenticator and Vault's AWS auth method (facts.md §3).
- Not relied on: that STS enforces `X-Amz-Expires` (second-hand, UNPROVEN). accounts does its own freshness check instead. Nor is any STS skew window relied on (UNPROVEN). `MaxSkew` is accounts' own bound.

## Trust

- **Who can produce a valid header.** Only a holder of credentials for the hosts' role. The role trusts only `ec2.amazonaws.com` (infra), so the session name, which `Verify` trusts as the instance id, is set by EC2. Nobody chooses it with `AssumeRole`. Customer users cannot reach the role's credentials: `D15-machine` blocks IMDS for every uid except root, and `accountsd` runs as root. Anyone who can still presign holds root on that host, which already controls it.
- **What a captured header buys.** One use, within `Freshness`, carried only over TLS: the replay set remembers every signature STS accepted until its date is older than `Freshness`, and freshness refuses it after that. A header presigned for another accounts deployment fails at STS, because accounts signs the binding it was configured with.
- **What a forged report could do even then.** It could only misreport its own host. `D04-store`'s `RecordReport` never raises `applied` above the host's current version, takes sign-ins and slices only for that host's own users and accounts, never accepts a future time, and `MaxReportBytes` caps every body.
- **Junk traffic.** The token bucket is global, so unauthenticated junk above `VerifyRate` per second makes honest daemons get `ErrBusy` and back off. This is accepted: a host that cannot reach accounts keeps its last applied state and sign-ins keep working (outcome 22). The bucket's purpose is that accounts never makes unbounded outbound STS calls. Junk that fails the shape, freshness or replay checks costs no token and no outbound call.
- **No per-poll cache.** Every request costs one STS call, about two per minute per host. `GetCallerIdentity` needs no permission, and a session scheme's extra risk is not worth that saving.

## Bounded work

A header is at most `MaxHeaderBytes` (8 KiB). STS's answer is read through `D05-cloud`'s `cloud.MaxCallerBytes` (64 KiB) limit, and the call gives up after `cloud.CallerTimeout`, which `STSTimeout` names. At most `VerifyBurst` STS calls are in flight, each holding one URL. At most `VerifyBurst + VerifyRate · t` STS calls start in any span of `t` seconds. The replay set holds only signatures STS accepted, each forgotten once its date is more than `Freshness` old, so at most `Freshness + MaxSkew` after acceptance (its date may be up to `MaxSkew` ahead). It therefore holds at most `VerifyBurst + VerifyRate × 360 = 7240` entries in steady use, under `ReplayCapacity` (10 000), which is a hard ceiling: a verifier at the ceiling answers `ErrBusy` rather than forget a signature early. Only accepted signatures count toward the ceiling; signatures whose STS call is still in progress are bounded separately, at most `VerifyBurst`, by the in-flight cap, so the two bounds add to at most `ReplayCapacity + VerifyBurst` held signatures (a pick: counting in-flight ones too would let a burst of slow STS calls refuse admission the set itself does not need). The rate, in-flight, forgetting and ceiling rules are requirements; a test proves forgetting by verifying 20 000 headers on an advancing clock without `ErrBusy`, which a verifier that never forgot would fail at the ceiling.

## Recorded decisions

- **Header encoding**: unpadded URL-safe base64 of the URL, as aws-iam-authenticator encodes its token (facts.md §3). It survives every proxy as a header value.
- **Constants**: `BindingHeader` and `STSTimeout` are `D05-cloud`'s `cloud.BindingHeader` and `cloud.CallerTimeout` by name, because `cloud/awssdk`, which sends the header and times the call, cannot import `hostauth`. `PresignExpires = 60s`, as aws-iam-authenticator's client sets it. `MaxExpires = 300`: a daemon that asks for more is refused. `Freshness = 5 minutes`, the window the replay set must cover, shorter than the 15 minutes Vault and aws-iam-authenticator accept. `MaxSkew = 1 minute`, the clock skew allowed in the other direction. `MaxHeaderBytes = 8 KiB`, half of aws-iam-authenticator's 16 KiB (a presigned URL with a session token is about 1.5 KiB). `VerifyRate = 20/s` with burst 40: six times the steady load of a hundred hosts at two calls a minute each, and room for every host to reconnect at once after an accounts restart within a few seconds. `STSTimeout = 10s`, aws-iam-authenticator's.
- **One header per second per daemon.** A SigV4 presigned URL is a function of the credentials, the second of `X-Amz-Date`, the expiry and the signed headers, so two headers a daemon makes within one second are identical and the second is `ErrReplayed`. `D14-accountsd` therefore never makes two headers within one second of its clock, and `D16-sandbox`'s fake signer mirrors the rule. A presigned URL need not carry `X-Amz-Security-Token`: `Verify` never requires it (the sandbox's fake carries none); STS judges the credentials.
- **Single flight and replay both keyed by the signature.** A signature names one canonical request, so a reordered or re-encoded copy of an accepted request is the same request to STS, and keying by the URL would let two such copies succeed at once. A waiter whose leader failed carries on rather than inheriting the failure, so a junk URL that reuses an honest signature cannot steer the honest request's outcome; it only delays it by one STS call.
- **Partition `aws` only.** The ARN check and the STS host name the commercial partition. Infra runs there, and a GovCloud or China host fails `ErrRejected` / `ErrMalformed` rather than being half-supported.
- **`UserID` checked too.** The ARN alone would do. Requiring `UserID`'s session to match costs nothing and catches an answer that is not an assumed-role session.
- **Precedent.** No sibling verifies a presigned request: devctl's only STS use is `GetCallerIdentity` for its own account (precedent §9). The design follows aws-iam-authenticator and Vault's AWS auth instead, and departs from both on two points, each recorded above: a one-use replay set (both accept reuse within 15 minutes) and a binding taken from configuration (Vault takes it from configuration too; aws-iam-authenticator from the cluster id).

## Consumer usage

- Daemon first boot (task 2): `D14-accountsd` calls `hostauth.Header(ctx, presigner, binding)` and sets the result as `hostauth.HeaderName` on `GET` `StatePath`. A non-nil error means the presign failed. The daemon backs off and changes nothing.
- accounts' start (`D03-serve`): `hostauth.NewVerifier(hostauth.VerifierConfig{Region: hosts.Region, Role: hosts.InstanceProfile, Binding: <D01's binding func>, STS: cloud, Now: p.Now})` builds one `*Verifier`, which it hands to `daemonapi.Config.Verifier`. In the sandbox the memory cloud is the `STS`, with `Region` `sandbox`, so the allowlisted host is `sts.sandbox.amazonaws.com`.
- Every state or report request (tasks 2, 3, 5): `D13-daemon-endpoints` calls `v.Verify(ctx, r.Header.Get(hostauth.HeaderName))`. It answers 401 on `ErrMalformed`, `ErrStale`, `ErrReplayed` or `ErrRejected` and 503 on `ErrUnavailable` or `ErrBusy`. On success it passes the instance id to `store.HostByInstance`.
