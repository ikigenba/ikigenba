# D03-serve

The serve path covers what happens between `cli.Run` being called with no arguments and the process being gone:

- the terms accounts serves on
- the listener's life
- the route table its one handler keeps, with the identity each route takes
- the start and the stop of the background work: the operations engine and, in the sandbox, the simulated hosts

It is the suite's app serve path with three changes:

- It adds two routes that take no identity: the daemon's (`/accountsd` and everything below `/accountsd/`) and the enrollment page's (exactly `/join`, the token in its query).
- It adds the engine and the simulated hosts beside the server.
- It builds two more MCP servers, which hold the box tools a host's users reach through their host's daemon at `/accountsd/v1/box`.
- It drops what accounts has no use for: no sibling client and no bus paths.

This document declares `internal/server` and `internal/web`. Outcomes cited as outcome N are those of /home/mgreenly/Documents/ikigenba-ssh-hosts.md; self-service outcome N is outcome N of /home/mgreenly/Documents/ikigenba-self-service-accounts.md.

## The services file

`IKIGENBA_SERVICES` names the services file. accounts uses three of its entries:

- `auth`: the pages read it afresh per request (`D06-pages`).
- `telemetry`: appkit's sink reads it afresh per delivery.
- `accounts`: read afresh for the accounts URL each time a launch step needs it or `create_invite` makes a link, and for the binding at each verification (`D01-layout-and-run-seam`).

`Run` also reads the binding once at the start, for the simulated hosts. A services-file change after the start therefore leaves the simulated daemons on the old binding while the verifier reads the new one; accepted, because only the sandbox runs simulated hosts and its `accounts` entry does not change while it runs (a restart picks up a new one).

The start is not refused when `IKIGENBA_SERVICES` is unset, names no file, or names a file `services.Read` refuses. accounts then serves as with a file holding no entry.

## The terms accounts serves on

accounts serves only on a listening socket it inherits, taken as `sd_listen_fds(3)` documents. It reports readiness with `READY=1` to `NOTIFY_SOCKET`, as `sd_notify(3)` documents.

It trusts `X-User-Id`, `X-User-Email` and `X-Request-Id` as nginx sets them. The manifest declares `guests = true` (`D09-on-a-space`). nginx therefore lets a request with no credential through to every path but `/mcp`, so that a daemon reaches `/accountsd` and `/accountsd/…` (outcome 21), and a person holding an invite link reaches `/join?token=<token>` (self-service outcome 11).

A request with no `X-User-Id`, or an empty one, is a **guest**:

- The pages send a guest to sign in.
- `/mcp` refuses one.
- The daemon routes take no user at all: a daemon proves who it is by its presigned identity header (`D12-host-identity`), which `D13-daemon-endpoints` checks.
- The enrollment page takes no user either: its authority is the invite's token in the path, and it answers a guest and a signed-in person alike (`D18-enrollment`).

## The route table

Every request goes through appkit's `telemetry.Middleware` over `Config.Telemetry`, which records the request pair (`D08-trail`). The middleware records the request's `URL.Path` and never its query, and an enrollment link carries the invite's token in its query, so the request pair of a link records the path `/join` alone with no special handling (`D08-trail`). Then the handler routes by `URL.Path` alone, compared by hand, so nothing is cleaned and nothing is redirected:

- **Exactly `/mcp`**: `identity.Require`, then the MCP server `Config.MCP`. The tools of `D07-tools` are registered on it with `tools.Register` once, when the handler is built.
- **A path beginning `/_appkit/`**: `identity.Optional`, then `page.Static()`.
- **Exactly `/accountsd`, or a path beginning `/accountsd/`**: no identity wrapper, then `Config.Daemon` (`D13-daemon-endpoints`).
- **Exactly `/join` (`join.Path`)**: no identity wrapper, then the enrollment handler `join.Handler` (`D18-enrollment`), built once when the handler is built over the same template set as the pages, `Config.Store`, `Config.Configured`, the hosts domain `Config.Hosts.Domain`, one `join.NewLimiter` over the writer's clock, and `Config.Telemetry`.
- **Every other path**: `identity.Optional`, then `pages.Handler` (`D06-pages`). That includes `/accountsdx`, `/mcp/`, `/events`, `/hosts/<name>`, `/`, `/tools`, `/join/`, everything below it and `/joinx`.

Only `/mcp` changes the record on behalf of a person who is signed in. `/accountsd/v1/report` records the host's report, on behalf of a verified daemon. `/accountsd/v1/box` runs a box tool on behalf of an active user of an account placed on a verified daemon's host (`D13-daemon-endpoints`, `D19-box-tools`), so a box tool that changes something changes the record. A `POST` to `/join?token=<token>` uses up one invite and creates one user, on behalf of whoever holds the invite's link (`D18-enrollment`). No other request changes the record. None but `/mcp` wakes the engine, and none but `/mcp` and the daemon routes reaches the cloud: the daemon routes reach only its STS, to verify a daemon (`D12-host-identity`) and, for a state answer, to issue the host's backup credentials (`D21-backup-access`, `D13-daemon-endpoints`). Nothing else does: a user enrolled reaches its host as desired state through the store's watch (`D04-store`, `D13-daemon-endpoints`), as one `add_user` adds does, with no operation. No answer on any route carries `Set-Cookie`.

## The start

With `Args` empty, `Run` goes through these steps in order:

1. It checks the settings, then that exactly one socket was passed in, with the diagnostics below.
2. It removes the three `LISTEN_*` variables and takes descriptor 3.
3. It opens the database (`D01-layout-and-run-seam`), and builds the store over `Process.Now` and `Process.Rand`, then the writer.
4. It records `service.started`.
5. It chooses the cloud by `Settings.Cloud()`:
   - `Process.Cloud(ctx, region)` in AWS mode.
   - `memory.New` over `state/sandbox-cloud.json` in sandbox mode.
   - None otherwise.

   A cloud that fails to open is not fatal. accounts writes one line, `accounts: ` followed by `cli.NoCloud` and the reason, and serves as in mode none.
6. It builds three MCP servers with `Process.MCP`: first the one it will serve at `/mcp`, then the two box servers, one for each tier. It registers the box tools on the box servers (`D19-box-tools`), and builds the daemon endpoints with `daemonapi.New` over the daemon binary it resolved, the two box servers and the hosts domain in use, `Settings.HostsInUse().Domain` (`D01-layout-and-run-seam`): the domain the hosts settings name in AWS mode, `settings.SandboxHosts`' in sandbox mode, and empty in mode none. The state answer hands that domain to every host, which takes `<host>.<domain>` as its hostname (`D13-daemon-endpoints`, `D15-machine`). The daemon endpoints also take those hosts settings whole, `Settings.HostsInUse()`, from which the state answer names the backup bucket and region, and one credential issuer, `access.New` over the opened cloud's STS, the same hosts settings and `Process.Now` (`D21-backup-access`), which the state answer uses to hand each host its backup credentials (`D13-daemon-endpoints`). In mode none, and when the cloud failed to open, there is no issuer and `Access` is nil. `daemonapi.New` streams the binary once to compute its digest.
7. It builds the engine with `ops.New`, and the handler.
8. It sends `READY=1`.
9. It starts the engine's `Run`, and in sandbox mode the simulated hosts' `sim.Run`, each in a goroutine. The simulated hosts take `state/sandbox-bans` under `Dir` as their bans file (`D16-sandbox`): a line `<host> <address>` a person writes there bans that address on that host's memory machine. They take `state/box` under `Dir` as their box dir (`D16-sandbox`): there the sim serves one Unix socket per user its hosts hold, through which a person drives the box path as that user, and lists them in `sockets.txt`. They take `state/sandbox-seeds` under `Dir` as their seeds file (`D16-sandbox`), where the sim lists each account folder a simulated host seeded. They take `state/sandbox-backups` under `Dir` as their backups file (`D16-sandbox`): a line a person writes there adds a database to an account on a simulated host, or makes that account's backups fail or heal. `Run` creates none of these, so `state/` holds only what `D01-layout-and-run-seam` says until a person writes a bans or backups file, a host holds a user or a host seeds an account.
10. It serves.

The engine resumes every unsettled operation at once, so an operation interrupted by a restart continues without a tool call (outcome 11). The tools wake the engine through `tools.Config.Wake`, so a new operation's first step does not wait for the engine's timer.

## Stopping

When `ctx` is done, `Run` stops in this order:

1. It calls `daemonapi.Server.Stop()`. Every long poll in progress then answers at once, so a waiting daemon never holds the drain up.
2. It drains the server for `DRAIN_SECONDS`.
3. It waits for the engine and the simulated hosts. Both return on `ctx`.
4. It shuts the writer down with the cause's text as `service.stopping`'s reason.
5. It closes the database.

The engine never blocks the drain. An AWS call in flight is cancelled with `ctx`. Its step was recorded before the call, so it resumes at the next start (outcome 11).

From shortly after the drain deadline on, `Run` hands the sink nothing. A drain that runs out on requests is `accounts: stopped with <n> request(s) unfinished`, exit 1.

## The binary

The one exec'ing test of `cmd/accounts` proves the wiring. `D01-layout-and-run-seam` states what the binary does at the start. This document adds the bare start with no socket and the stop on `SIGINT`.

## Recorded decisions

- **`internal/server` is the suite's, unchanged.**
- **The daemon routes sit outside identity**, so that a daemon with no credential reaches `D13-daemon-endpoints`.
  - Precedent: webhooks' `/in/<slug>` behind `guests = true`.
  - The departure from outcome 21's wording ("a path nginx passes without auth's subrequest") is recorded in `D09-on-a-space`. It takes nginx's `/check/open` subrequest instead.
  - The prefix match `/accountsd/` and the exact `/accountsd` are compared by hand, as `/mcp` is, so `/accountsdx` stays a page path and reaches the not-found page.
- **The enrollment route sits outside identity too** (self-service outcome 11), so a person with no credential on the space reaches `D18-enrollment`, and one who happens to be signed in gets the same answer.
  - Precedent: the daemon routes above, and webhooks' `/in/<slug>`; no manifest or fragment change is needed, since `guests = true` already passes `location /` through `/check/open` (`D09-on-a-space`).
  - Only the exact path `/join` is the route, compared by hand: `/join/`, every path below it and `/joinx` are page paths, so a guest there is sent to sign in and a signed-in person sees the not-found page, as for any unknown path. A link with no usable `token` parameter is the join handler's, which answers it as an unusable link.
  - The route is decided before the page handler, so `D06-pages`' guest redirect (R-SFH9-7KWL) needs no exception.
- **The token is in the query, out of the request pair.** appkit's middleware records `path` as `URL.Path` and drops the query, so the token reaches no event (self-service outcome 27) and the request pair needs no rewriting. The earlier path form, `/join/<token>`, was hidden from the middleware by rewriting the path, but nginx's sign-in subrequest still sent the full path to auth, which records it on `check.allowed`; auth cuts everything from `?` on, so a token in the query reaches neither trail (`D18-enrollment`).
- **The join handler is built once per `web.Handler`**, so its limiter is one table across all requests, and its clock is the writer's `Now`, as the pages' is. Its memory bounds are `D18-enrollment`'s (at most `join.MaxAddresses` limiter entries, a body of at most `join.MaxBodyBytes`).
- **The tools' accounts URL comes from the settings**, `cfg.Settings.AccountsURL(cfg.ServicesPath)` read afresh at each call, the same source the engine tags instances with (`D01-layout-and-run-seam`), so an invite's link names the accounts URL the services file names when the invite is made. `web.Config` gains no field: it already carries `Settings` and `ServicesPath`.
- **`web.Config` gains `Cloud`, `Hosts`, `Configured`, `Wake` and `Daemon`, and loses `Host`.**
  - The tools need the cloud for the DNS check, the hosts settings in use, whether the run is configured, and the engine's wake.
  - The pages need whether the run is configured and the hosts domain.
  - The route table needs the daemon endpoints.
- **The pages' clock is the writer's `Now`.** `web.Config` carries no clock of its own, as before. `pages.Config.Now` is `cfg.Telemetry.Now`, which is `Process.Now`.
- **A cloud that fails to open is not fatal**.
  - accounts serves as mode none and says why on standard error.
  - It writes one line, so an operator sees it in the journal, and the tools say "not configured" rather than failing.
  - `cli.NoCloud` is a copy constant, a pick.
  - The sandbox's unreadable memory-cloud file takes the same path.
- **A failing `daemonapi.New` has no stated answer.** `D13-daemon-endpoints` makes a missing binary a 404 rather than a failure, and no permitted test can make reading an existing file fail. This follows the old store-failure decision.
- **Stop order: daemon endpoints, drain, background, writer, database.**
  - Long polls would otherwise run out the drain. Precedent: no sibling long-polls. gmail's and gdrive's workers stop on `ctx` before the writer shuts down.
  - Stopping the background before the writer keeps `service.stopping` the last event, as R-UVI5-53XK requires.
- **The engine resumes on start, where gdrive and gmail fail interrupted work at `Recover`.** Outcome 11 requires resume. The resume is the engine's (`D10-operations`). This document requires only that the engine runs from the start of every configured run.
- **The simulated hosts' diagnostics never reach `Process.Stderr`.** R-H30N-ZNGY allows nothing on standard error beyond the lines it lists, in every mode. `D16-sandbox` gives each simulated daemon a `Stderr` that discards (R-D60E-MFUA).
- **The bans file sits beside the memory cloud's file**, at `state/sandbox-bans` in accounts' data directory (on a developer's machine `~/.local/state/ikigenba/sandbox/<name>/apps/accounts/state/sandbox-bans`), so `sandbox wipe` removes it with the rest and a person finds it where the sandbox's other state is. `Run` only names it; the sim reads and removes it, and nothing creates it but the person.
- **Three MCP servers, all from `Process.MCP`.** `/mcp` gets the first; the box path's user tier and admin tier (`D19-box-tools`) get the second and third, handed to the daemon endpoints as `daemonapi.Config`'s `BoxUser` and `BoxAdmin` (`D13-daemon-endpoints`). `Run` cannot call appkit's `mcp.NewServer` itself, because `NewServer` reads `IKIGENBA_SERVICES` from the process environment and only `main` reads the environment (`D01-layout-and-run-seam`); `Process.MCP` is already the seam that call goes through, so no new seam is needed. Each box server is built with the serving writer, so each box call's `tool.called` comes from appkit with `User` `ssh:<name>` and the request's id, inside the request pair `telemetry.Middleware` records for `/accountsd/v1/box`; the pair records `URL.Path`, so the `uid` query is not in the trail. `web.Config` gains nothing: `Daemon` already carries the box servers to the route table.
- **The box tools reach the same accounts URL as the central ones**, `Settings.AccountsURL(path)` read afresh at each call, so a box invite's link and a central one name the same address.
- **The box dir sits beside the bans file**, at `state/box` in accounts' data directory, as `D16-sandbox` recommends, so `sandbox wipe` removes it and a person finds the sockets with the sandbox's other state. `Run` only names it; the sim creates it when a host first holds a user and removes it when empty. A long data directory can push a socket path past the 108-byte limit, which the sim reports in its listing (`D16-sandbox`).
- **The daemon endpoints take `Process.After`** as `daemonapi.Config.After` (`D13-daemon-endpoints`, R-KU9L-II31), so a long poll's 45 s wait is driven by the test's timer source, as the engine's and the simulated hosts' waits are.
- **The daemon endpoints' domain is the hosts domain in use** (`Settings.HostsInUse().Domain`), the same value the tools, pages and enrollment page are given, so a host's hostname, its record and the name the pages show cannot disagree. In sandbox mode the settings' own `Hosts.Domain` is empty and `settings.SandboxHosts` applies, which is why the source is `HostsInUse()` and not `Settings.Hosts`. Unconfigured, whether in mode none or because the cloud failed to open, the endpoints answer every path 404 (R-YDH0-PCK8), so no host ever reads the domain; `Run` passes `HostsInUse().Domain` regardless, which is empty in mode none. No requirement states the unconfigured value, since no test can observe it.
- **The daemon endpoints take one credential issuer, built over the opened cloud's STS** (`D21-backup-access`). In AWS mode that is the cloud `Process.Cloud` returned, so the issuer assumes the backup role with accounts' own credentials, the space role's; in sandbox mode it is the memory cloud, whose `AssumeRole` checks the role and the session policy and whose S3 accepts only what its credentials allow (`D16-sandbox`), so the sandbox walks the same credential path a space does. The issuer's hosts settings are `Settings.HostsInUse()`, the same value the daemon endpoints, the tools, the pages and the engine get, so the role the issuer assumes, the bucket the state answer names and the bucket the memory cloud holds cannot disagree; its clock is `Process.Now`, so a test drives reissue by the clock it hands in. It is built once per run, so its cache of issued credentials lives as long as the run and is never stored.
- **The daemon endpoints' `Hosts` is required only where a test can see it.** In AWS mode the state answer's `backup.bucket` and `backup.region` come from it (`D13-daemon-endpoints`), and R-PLAM-5U68 checks them. In sandbox mode `Run` passes `HostsInUse()` too, `settings.SandboxHosts`, but no permitted test sees it: the simulated machine stores nothing by bucket or region (the memory cloud's `Put` takes credentials and a key, `D16-sandbox`), and a sandbox test cannot sign a state request for a simulated host. The sandbox's credential path is still proved end to end through the issuer, whose role and policy the memory cloud checks against its own hosts settings. The engine's and the tools' hosts settings are another matter: they name the bucket the engine deletes an account's backups from and the tools' `create_account` checks (`D10-operations`, `D07-tools`), and the memory cloud holds only `settings.SandboxHosts`' bucket, so a zero value there is seen in sandbox mode too; R-3W54-93QJ states both modes.
- **The engine and the tools take the hosts settings in use in both modes** (`Settings.HostsInUse()`), as the daemon endpoints and the issuer do: the engine names the backups bucket with `Hosts.BackupBucket()` for a removed account's backups delete and a delete's `delete_backups`, and the tools with it for `create_account`'s backups check, so in sandbox mode the zero `Settings.Hosts` would name a bucket the memory cloud does not hold.
- **No issuer without a cloud.** In mode none, and when the cloud failed to open, `Access` is nil: the daemon endpoints then answer every path 404 (R-YDH0-PCK8), so no state answer is made and nothing could observe the issuer. No requirement states that value, as none states the unconfigured `Domain`.
- **`daemonapi.Config` keeps `Domain` and gains `Hosts`** (host-backups plan 2.10). `Hosts.Domain` equals `Domain` here, since both are `Settings.HostsInUse()`'s; keeping `Domain` leaves R-AX78-VHKU and its story untouched.
- **The backups file sits beside the bans file**, at `state/sandbox-backups` in accounts' data directory, for the same reasons: `sandbox wipe` removes it, and a person finds it with the sandbox's other state. `Run` only names it; the sim reads and removes it, and nothing creates it but the person.
- **Tests these requirements need**, each permitted by `accounts/AGENTS.md`, Test discipline:
  - sandbox mode over a temp `Dir`, with an `After` the test controls
  - AWS mode with a recording or blocking fake `cloud.Cloud` handed as `Process.Cloud`
  - AWS mode with a fake `cloud.Cloud` whose `CallerOf` accepts the test's identity headers for a host's instance, each with its own signature, for the box path's wiring (R-Z3DU-2772)
  - long-poll tests that never wait out `protocol.LongPoll`, because the stop answers them at once
  - AWS mode with a fake `cloud.Cloud` whose `Identity` and `AssumeRole` answer what the test chooses and record each `cloud.RoleRequest`, for the issuer's wiring (R-PLAM-5U68)

## Consumer usage

`Run`, serving:

1. It reads `s, err := settings.Read(p.LookupEnv)`, checks the socket, unsets the three `LISTEN_*` variables and takes `ln, _ := p.Inherit(3)`.
2. It opens `d` with `db.Open` at `state/accounts.db`, builds `st := store.New(d, store.Config{Now: p.Now, Rand: rnd})` and `w := telemetry.New(...)`, and records `service.started`.
3. It opens the cloud `c` by mode. On failure it writes `"accounts: " + cli.NoCloud + ": " + reason` and sets `configured = false`.
4. It builds `v := hostauth.NewVerifier(hostauth.VerifierConfig{Region: hosts.Region, Role: hosts.InstanceProfile, Binding: binding, STS: c, Now: p.Now})`.
5. In AWS and sandbox mode with the cloud open, it builds `acc := access.New(access.Config{STS: c, Hosts: hosts, Now: p.Now})`, `hosts` being `s.HostsInUse()`; otherwise `acc` is nil.
6. It builds the MCP servers in this order, `m := p.MCP(w)` for `/mcp`, then the box servers `bu, ba := p.MCP(w), p.MCP(w)`, registers `bc := box.Config{Store: st, Telemetry: w, AccountsURL: func() (string, error) { return s.AccountsURL(path) }}` with `box.RegisterUser(bu, bc)` and `box.RegisterAdmin(ba, bc)`, then builds `ds, _ := daemonapi.New(ctx, daemonapi.Config{Store: st, Verifier: v, Binary: bin, Telemetry: w, Now: p.Now, Configured: configured, After: p.After, BoxUser: bu, BoxAdmin: ba, Domain: hosts.Domain, Access: acc, Hosts: hosts})`. Before this revision the `daemonapi.Config` ended at `Domain: hosts.Domain` and no issuer was built.
7. It builds `eng := ops.New(ops.Config{Store: st, Cloud: c, Hosts: hosts, AccountsURL: accountsURL, Telemetry: w, Now: p.Now, After: p.After})`.
8. It builds `h := web.Handler(web.Config{Banner: p.Banner, MCP: m, ServicesPath: path, Store: st, Cloud: c, Hosts: hosts, Configured: configured, Wake: eng.Wake, Daemon: ds, Telemetry: w, Settings: s})`.
9. It sends `READY=1` and starts `go eng.Run(ctx)`.
10. In sandbox mode only, it builds `sm := sim.New(sim.Config{Cloud: mc, Handler: h, Binding: b, Digest: ds.Digest, Now: p.Now, Sleep: p.Sleep, After: p.After, BanFile: filepath.Join(p.Dir, "state", "sandbox-bans"), BoxDir: filepath.Join(p.Dir, "state", "box"), SeedFile: filepath.Join(p.Dir, "state", "sandbox-seeds"), BackupFile: filepath.Join(p.Dir, "state", "sandbox-backups")})` and starts `go sm.Run(ctx)`. Before this revision the `sim.Config` ended at `SeedFile`.
11. It calls `server.Serve(ctx, ln, h, s.Drain(), stop)`, where `stop` calls `ds.Stop()` first, then waits for the engine and the sim, then calls `w.Shutdown`.
12. It closes `d`.

`web.Handler(cfg)`:

1. It calls `tools.Register(cfg.MCP, tools.Config{Store: cfg.Store, Cloud: cfg.Cloud, Hosts: cfg.Hosts, Configured: cfg.Configured, Wake: cfg.Wake, Telemetry: cfg.Telemetry, AccountsURL: func() (string, error) { return cfg.Settings.AccountsURL(cfg.ServicesPath) }})` once.
2. It builds `pages.Handler` over `pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, MCP: cfg.MCP, Configured: cfg.Configured, Domain: cfg.Hosts.Domain, Now: cfg.Telemetry.Now}`.
3. It builds `jh := join.Handler(join.Config{Pages: set, Store: cfg.Store, Configured: cfg.Configured, Domain: cfg.Hosts.Domain, Limiter: join.NewLimiter(cfg.Telemetry.Now), Telemetry: cfg.Telemetry})`.
4. It routes by hand on `URL.Path`, with no `http.ServeMux`, which would redirect `/join` and clean paths: `identity.Require(cfg.MCP)` for exactly `/mcp`, `identity.Optional(page.Static())` for a path beginning `/_appkit/`, `cfg.Daemon` for exactly `/accountsd` or a path beginning `/accountsd/`, `jh` for exactly `join.Path`, and `identity.Optional(pages)` for every other path.
5. It returns `telemetry.Middleware(cfg.Telemetry, router)`.

A test of the handler:

2. It adds `daemonapi.New` over a temp binary, a writer over a capture, and a server from `mcp.NewServer`.
