# D18-enrollment

The enrollment page: how a person holding an invite link becomes a user of an account without signing in to the space (outcomes 5, 6, 8, 11 to 15 and 27 of /home/mgreenly/Documents/ikigenba-self-service-accounts.md; outcomes cited as outcome N are that document's). This document owns package `internal/join`: its `Config`, its `Handler`, which `D03-serve` mounts at exactly `/join` (`join.Path`), and its `Limiter`, which rate limits submissions per address.

The link is `<accounts URL>/join?token=<token>`, the token being the one `D04-store`'s `CreateInvite` answers once and `D07-tools`' `create_invite` hands back in its `Link`. Opening the link (`GET`) shows a form naming the invite's account; submitting it (`POST` to the same address) creates the user. The page is drawn by the template `join` with `pages.JoinData`, both declared in `D06-pages` with the outcome constants `pages.JoinForm`, `JoinUnusable`, `JoinName`, `JoinKey`, `JoinLimited`, `JoinFull` and `JoinDone`; this document says which outcome each request is answered with, under which status and headers, and with which data. It is the one page that answers a guest and the one page that changes the record; every other page is read-only and sends a guest to sign in (`D06-pages`).

What this document cites from the others: `D04-store` for `store.ValidToken`, `InviteByToken`, `NameHeld`, `Enroll`, `Account`, the errors and `store.Unreachable`; `D06-pages` for `pages.Set`, `Set.Write`, `JoinData`, the outcome constants and the plain refusal (R-AY74-302P); `D08-trail` for `trail.InviteUsed` and the `invite.used` event; `D17-names-keys-sizes` for `valid.Name`, `valid.ParseKey` and `valid.Address`; `D03-serve` for the route, the hiding of the path from the request pair, and the config `web.Handler` builds. appkit's `telemetry` and `identity` packages own their contracts.

## The link and its token

The handler takes the token from the query parameter `token` (`join.TokenParam`) of a request to exactly `/join` (`join.Path`), as `URL.Query()` decodes it: the parameter must appear exactly once and hold a string `store.ValidToken` accepts. Anything else (no `token`, an empty one, two of them, a token of the wrong length or alphabet) is answered as an unusable link without the store being read, and so is every link while the space operates no hosts (`Configured` false). Other query parameters are ignored, so a link a chat app has decorated with tracking parameters still works.

A well-formed token is looked up with `InviteByToken`, which answers only a usable invite: unexpired, unused, unrevoked, and of an account that still exists with the same gid and is not being removed. Unknown, used, expired, revoked, a removed or removing account, malformed, and unconfigured are one answer: the same status, the same headers and the same body (outcome 13). The token never enters `JoinData`: the template's form has no action, so it posts back to the address it was opened at.

## The order of checks

1. **Method.** Anything but `GET`, `HEAD` or `POST` is 405 with `Allow: GET, HEAD, POST` and an empty body; nothing is read.
2. **Rate limit, `POST` only.** The request's key is `valid.Address` of its first `X-Real-IP` value, the address nginx sets from the peer; a missing or malformed value gives the key `""`, which all such requests share. One `Allow` call on `Config.Limiter` with that key; a refusal is 429 with `Retry-After` and the outcome `JoinLimited`, decided before the link is looked at.
3. **Link shape and configuration.** A malformed token, or `Configured` false, is the unusable answer.
4. **`GET` and `HEAD`.** `InviteByToken`; not found is the unusable answer; otherwise 200 with the form (`JoinForm`) and the invite's account, its DNS name (`<slug>.<Domain>`) and its admin flag.
5. **`POST`.** The body is read through `http.MaxBytesReader` at `MaxBodyBytes`; more is 413 with an empty body. The form fields `user` and `key` are the first values of each in the URL-encoded body; another content type, or a body that does not decode, gives both empty. Then `InviteByToken` (unusable); then `valid.Name` of the user as submitted, and, when that accepts it, `NameHeld` of it, one answer `JoinName` for malformed, reserved and taken (outcome 13); then `valid.ParseKey` of the key with its leading and trailing spaces, tabs, carriage returns and line feeds removed (`JoinKey`); then `Enroll` with the canonical key (`store.Key{Type: k.Type, Body: k.Body, Line: k.Line()}`, as `add_user` stores it): `ErrNotFound` is unusable (the invite was used or revoked meanwhile), `ErrTaken` is `JoinName` (the name was taken meanwhile), `ErrAccountFull` is `JoinFull`. Success is `JoinDone`, and `trail.InviteUsed` is told.

Any other store error, at any step, is the plain refusal with `store.Unreachable`, 503, as the pages answer a store that cannot be read (`D06-pages`).

## Answers

| Status | Outcome | Data |
|---|---|---|
| 200 | `JoinForm` (GET, HEAD) | `Account`, `DNSName`, `Admin` from the invite |
| 200 | `JoinDone` | `Account`, `DNSName`, `Admin`, `User` the created login; `Key` empty |
| 404 | `JoinUnusable` | nothing else |
| 422 | `JoinName`, `JoinKey` | the invite's three, `User` and `Key` as submitted, untrimmed |
| 409 | `JoinFull` | the same as 422 |
| 429 | `JoinLimited` (with `Retry-After`) | nothing else |
| 405 | none (with `Allow`) | empty body |
| 413 | none | empty body |
| 503 | none | the plain refusal, `store.Unreachable` |

Every answer, whatever its status, carries `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and `X-Robots-Tag: noindex, nofollow`, and none carries `Set-Cookie`. `no-store` keeps the page, which holds an account's name and, on a refusal, the key a person typed, out of every cache and the back-forward history. `no-referrer` matters because the token is in the page's own address: without it, the browser would send that address as `Referer` with every fetch the page makes for its assets (`/_appkit/theme.css`, the fonts, `feedback.js`) and with any link a person follows from it, so the token would reach whatever those requests reach, access logs and telemetry included. `DENY` stops another site framing the form, and `noindex, nofollow` keeps a link that was pasted somewhere public out of search engines.

`HEAD` is answered as `GET` is, without a body, and never takes from the limiter. The answer is the same whatever identity headers the request carries: a signed-in person opening a link is treated as a guest, the created user's `CreatedBy` is the invite's creator (`D04-store`), and `invite.used` names the invite, never the person (`D08-trail`).

## The limiter

`Limiter` is a token bucket per key. A key it has not seen starts full, at `Burst`; it refills continuously at one token per `Every`, up to `Burst`; each `Allow` that answers true takes one. A refused `Allow` answers how long until the key has a whole token again, and takes nothing. So an address may submit 10 times at once and then once every 6 seconds; `Retry-After` is that wait in whole seconds, rounded up.

It holds at most `MaxAddresses` keys. `Allow` on a key it does not hold, while it holds `MaxAddresses`, first forgets the key least recently passed to `Allow`; a forgotten key starts full again when it returns. One limiter lives for the life of the process, built by `web.Handler` over the run's clock (`D03-serve`); a restart forgets every bucket.

## The trail

Only a successful enrollment is recorded: `trail.InviteUsed` with the invite's id, its account, that account's host, the created login and its admin flag, under a context whose caller has an empty `UserID` and `Email` and the request's id as `RequestID`, even when the request carried a signed-in person's headers (`D08-trail`). The host is read with `Account` after `Enroll`; should that read fail, the user is still created and the page still answers `JoinDone`, and the event carries an empty host. A refused enrollment records nothing. The request pair is recorded by appkit's middleware, whose `path` is `/join` without the query, so it never holds the token (`D03-serve`, `D08-trail`).

## Bounded work

- The limiter holds at most `MaxAddresses` (4096) buckets, each a key of at most one canonical address, a token count and a time.
- A `POST` body is read through `MaxBytesReader` at `MaxBodyBytes` (4096 bytes), so a request holds at most that many bytes of body, and the two fields within it.
- A request reads at most one invite (`InviteByToken`), one namespace lookup (`NameHeld`), one account (`Account`) and writes one user (`Enroll`); `D04-store` bounds each.

## Recorded decisions

- **The route is `/join?token=<token>`, the exact path `/join` compared by hand ahead of the page catch-all**, as `/accountsd` is (`D03-serve`), so `/join/`, everything below it and `/joinx` are page paths, answered as any unknown path is (a guest sent to sign in, a signed-in person the not-found page), and nothing is cleaned or redirected. It sits outside identity because the person enrolling has no account on the space. The form has no action, so it posts back to the address it was opened at, query included, and the template never holds the token.
- **The token is in the query, not the path.** The path form, `/join/<token>`, was rejected after the sandbox found it leaking: nginx's sign-in subrequest sends every request's URI to auth as `X-Original-URI`, and auth records it as `path` on its `check.allowed` event, so every opened link put its token in the space's telemetry, whatever accounts did with its own request pair. auth already cuts everything from `?` on before recording, the platform's existing way of keeping secrets out of that event, and appkit's middleware records `URL.Path` without the query, so a token in the query reaches neither trail and accounts needs no path rewriting of its own. Links minted in the path form stop working with this release (their route is gone); an invite made before it is revoked and made again.
- **A package of its own, not a page of `internal/pages`.** The page handler sends a guest to sign in before it looks at anything and never writes; this handler answers a guest and writes. Keeping them apart keeps `D06-pages`' guarantees whole. A separate service was rejected in the decisions document.
- **Why this page answers a guest though every other page sends one to sign in.** The invite is the credential: the person it is for has no space account and cannot sign in, which is the point of outcome 5. The link is single use, lasts 72 hours and is revocable (`D04-store`), and the page reveals only the invite's account and admin flag to whoever holds the token. A signed-in person gets exactly the guest's answer, so the page never depends on who opens it.
- **Statuses.** 404 for an unusable link: to the person it is a link that leads nowhere, and one status for every cause keeps them indistinguishable. 422 for a refused name or key: the request was well formed and its content was refused, and the form is drawn again holding what was typed. 409 for a full host: a conflict with the account's state that may clear, the invite still usable. 429 with `Retry-After` for the limit (RFC 6585 §4). 405 with `Allow` and 413 empty, as the daemon routes answer them (`D13-daemon-endpoints`). 503 plain text for an unreachable store, as the pages. 200, not a redirect, for a successful submission: a redirect after the `POST` would need an address that shows the result, which would hold the token or a session; a reload of the done page resubmits, and that submission is answered unusable, which says nothing the person does not already know.
- **Only `POST` is limited**, and every `POST` that passes the method check takes a token, even for an unusable link or an unconfigured space, before the link is looked at, so a stream of guesses costs the same as a stream of submissions. A `GET` changes nothing and a 256-bit token cannot be guessed, so a link preview or a reload is never limited. 10 at once and one per 6 seconds after (outcome 14 left the limit to the delivery) lets a person retry a mistyped key several times while turning a flood into a trickle.
- **The key is `X-Real-IP` canonicalized by `valid.Address`**, the address nginx sets from the peer on every space and in the sandbox; `X-Forwarded-For` is ignored, since a client writes it. A request without a usable `X-Real-IP` reaches accounts only around nginx, and all such requests share one bucket. Each IPv6 address is its own key, so a client holding a whole prefix can rotate: accepted, since the limit curbs floods and each invite still makes one user.
- **Memory is bounded by eviction, not by a sweep.** At most `MaxAddresses` buckets, the least recently used forgotten first. A forgotten address starts full: an attacker who cycles through more than 4096 addresses already has more than 4096 tokens a minute, so eviction gives away nothing the address count does not.
- **The fields come from the body alone.** A `user` or `key` in the query is ignored, so a link cannot carry a prefilled submission. A body that is not URL-encoded is read as both fields empty, which the name check refuses (`JoinName`): no new answer for a case only a hand-made request reaches.
- **The namespace is checked before the key, unlike `add_user`** (`D07-tools`, R-F9EO-NBLZ, which judges the key before it looks for the account and the name). The page asks `valid.Name` and then `NameHeld` before `valid.ParseKey`, deliberately, so one name answer covers malformed, reserved and taken before the key is judged, and a person fixes the name first. `NameHeld` is asked only for a well-formed name. The page asks it before `Enroll` so a taken name and a full host are told apart without a write; `Enroll` checks again in its transaction, so a race still gets the right answer.
- **The submitted key is trimmed of leading and trailing spaces, tabs, carriage returns and line feeds before `valid.ParseKey`.** A key pasted from a terminal or a `.pub` file commonly ends with a line break, and a browser's textarea sends it as `%0D%0A`; refusing that would refuse most first attempts. `valid.ParseKey` itself trims only spaces and tabs (`D17-names-keys-sizes`), and stays as it is: the trimming is the page's, since only a pasted form field carries the line break. The user name is not trimmed.
- **The submitted user is echoed untrimmed**, and the key as typed, untrimmed, so a refusal keeps what the person wrote; the user is checked untrimmed too, so ` daffy` is refused, not silently corrected. The done page shows the created login.
- **The nginx access log is an accepted risk.** The space's nginx (opsctl's, outside accounts) logs each request's full URI, query and token included. accounts cannot change that, and does not ask for it: the token is single use, expires after 72 hours and can be revoked, and the access log is readable only by an operator who could mint invites anyway.
- **Refused enrollments are not recorded in the trail**, only `invite.used`: a guest could otherwise write events at the limiter's rate for free. A refusal changes nothing, so the trail misses no change. The request pair still records each request, its path `/join` without the token.
- **No `Cloud` and no `Wake`.** `Config` has neither, so the page cannot reach AWS or the engine. A user is desired state, not an operation: `Enroll` bumps the host's version in its transaction and the host's long poll picks it up (`D13-daemon-endpoints`), as for `add_user`.
- **Two concurrent submissions on one link make one user**, because `Enroll` uses the invite in the same transaction that creates the user (`D04-store`); the other is answered unusable, or `JoinName` when it named the same user.

## Consumer usage

`web.Handler` (`D03-serve`) builds the handler once, beside the pages, over the same set and store:

`h := join.Handler(join.Config{Pages: set, Store: cfg.Store, Configured: cfg.Configured, Domain: cfg.Hosts.Domain, Limiter: join.NewLimiter(cfg.Telemetry.Now), Telemetry: cfg.Telemetry})`, mounted with no identity wrapper at exactly `join.Path`.

A guest's `GET`: an agent's `create_invite{account: acme}` answered the link `https://accounts.us.ikigenba.dev/join?token=inv_…`. The person opens it, signed out. `InviteByToken` answers the invite, and the page is `set.Write(w, r, 200, "join", pages.JoinData{Outcome: pages.JoinForm, Account: "acme", DNSName: "acme.metaspot.org", Admin: true})` with the four security headers. A mail app's link preview gets the same answer and uses nothing.

Refused `POST`s: `user=root&key=ssh-ed25519 …` draws `pages.JoinData{Outcome: pages.JoinName, Account: "acme", DNSName: "acme.metaspot.org", Admin: true, User: "root", Key: "ssh-ed25519 …"}` with 422, as `user=Bugs` and a `user` already held anywhere in the namespace do. `user=bugs&key=ssh-rsa …` draws `JoinKey` with 422. On a host with `valid.MaxUsersPerHost` users, `Enroll` answers `store.ErrAccountFull` and the page draws `JoinFull` with 409. In each case no record changes, nothing is told to the trail, and the link still opens the form.

The successful `POST`: `user=bugs&key=ssh-ed25519 AAAA… bugs@laptop`. `Enroll(ctx, token, "bugs", store.Key{Type: "ssh-ed25519", Body: "AAAA…", Line: "ssh-ed25519 AAAA… bugs@laptop"})` answers the invite and the user `bugs` of `acme`, `Admin` true, `Pending` true, `CreatedBy` the inviter's user id. The page draws `pages.JoinData{Outcome: pages.JoinDone, Account: "acme", DNSName: "acme.metaspot.org", Admin: true, User: "bugs"}` with 200, and `trail.InviteUsed(ctx, w, "iv_…", "acme", "host03", "bugs", true)` is told under a caller holding only the request id. Once host03 applies the version, `ssh bugs@acme.metaspot.org` works.

Reuse: the same link, opened again or submitted again, is answered 404 with `pages.JoinData{Outcome: pages.JoinUnusable}`, exactly as a revoked, expired or mistyped one.

Rate limiting: an eleventh `POST` from `X-Real-IP: 203.0.113.9` within a moment of the first ten is answered 429 with `Retry-After: 6` and `pages.JoinData{Outcome: pages.JoinLimited}`, without the link being looked up; a `GET` from the same address is still answered. A test builds its own limiter with `join.NewLimiter(clock)` over a clock it advances, calls `l.Allow("203.0.113.9")` itself to drain a bucket, and hands the same limiter in `join.Config` to see the handler share it.

A test serves `join.Handler(cfg)` over a store on its own database with a clock and a `Rand` it controls, `pages.Load()`'s set and a writer over `telemetry.Capture`; mints invites with `CreateInvite`, revokes them with `RevokeInvite`, ages them past `store.InviteLife` by its clock, removes their accounts; sends raw requests with and without identity headers and `X-Real-IP`; and compares each body with what `Set.Write` writes for the data below, and the capture with the event below. It turns `SetFailing(true)` on to see the 503.
