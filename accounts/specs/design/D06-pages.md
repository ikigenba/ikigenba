# D06-pages

What accounts draws as HTML: `internal/pages`, the four templates `landing`, `tools`, `about` and `notfound` of the root package's `Assets()` and the data each is executed with, `pages.Description`, the time layout the pages format with, the auth and sign-in addresses the pages build, and the page handler that answers `/`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it: the landing page, which says what the service is and lists the space's groups with their members and its users with their state and last sign-in (outcome 1), the tools page, the about screen and the not-found page. The pages are read-only: they carry no form, no per-record page, change nothing on the host and nothing in the record, and reach no sibling; every change goes through a tool (`D07-tools`). A guest is sent to sign in. Outcomes cited as outcome N are those of /home/mgreenly/Documents/ikigenba-accounts.md.

`D01-layout-and-run-seam` declares `pages.ServiceName` and records that accounts has no address package, so the two addresses the pages build live here; `D03-serve` routes `/`, `/tools`, `/about` and every path that is not `/mcp` or under `/_appkit/` to this handler inside `identity.Optional`, and defines a request's caller and a guest; `D05-host` declares `host.Host`, the three lists it reads, `host.Group`, `host.User` and `host.HostFailed`; `D04-store` declares `store.Store`, its `Groups` lookup and `store.Unreachable`; `D07-tools` registers the tools the tools page lists, in its catalog order, declares `tools.Register` and `tools.FirstLine`, answers the `groups` and `users` windows the landing's two lists share, and records the departure from shape's Storage entry that the landing inherits; `D09-on-a-space` carries `pages.Description` in the manifest. appkit's `page`, `identity`, `mcp`, `paging` and `services` packages own their contracts.

## The pages

The landing page, `/`, is the root of the banner's trail. It shows one window of the groups and one window of the users, as the host lists them (`group list` and `user list`, `D05-host`), each sorted by name in byte order. A group row carries its slug, how many members the host counts for it, the login names of the users the user list puts in it, sorted, and when accounts created it; the created time comes from the record (`D04-store`): a group on the host that accounts did not create shows no created time, and a group in the record that the host no longer lists is not shown. A user row carries the login, the state, the user's groups, how many keys the user has and the last sign-in, both time strings empty when the user never signed in; it carries no created time, since the template has none. Times are UTC, RFC 3339 to the second for a `time` element and `pages.MinuteLayout` for the text, as the template comment names them. Every signed-in user sees the same groups and users: they are the space's, not a user's.

The tools page lists every tool registered on the MCP server, in registration order, which is `D07-tools`' catalog order, each with the first line of its description as `tools.FirstLine` takes it; the about screen shows the service's name, the banner's `Release` and `Commit`, and `pages.Description`, the manifest's description. Each is one level below the root, `pages.ToolsLevel` and `pages.AboutLevel`. Every other path is the not-found page, 404, whatever the method. A query is ignored on every page but the landing's two parameters.

The banner's user is the caller's email with auth's profile and sign-out addresses built on `pages.Auth`. The **auth address** is the `URL` of the services file's entry `auth`, every trailing `/` removed, or, with no such entry, built from the request's scheme and host with any port and a leading `accounts.` removed. The **sign-in address** is the auth address, then `/?return=`, then the request's own address query-escaped (`pages.SignIn`).

## The landing's two lists

The landing has two lists, so it uses the two-list form of `design/`'s listing entry: each list has its own parameter, `groups_page` and `users_page`, each the first value of its name in the query, and its own `Page`, `Prev` and `Next` fields; each nav carries the other list's value, so paging one list never resets the other. Each window holds `paging.DefaultLimit` entries, 25. A list's page value is one of four. The empty value asks for the first window. An **after-token** is the token the list's tool answers as `next`, `paging.Token{Tool: "groups"}` or `paging.Token{Tool: "users"}` over the slug or login name of a window's last entry, and asks for the entries after that name in byte order, exactly the window the tool answers for the same `page` and no `limit`. A **before-token** is a token the page issues itself under the tool's name with `-before` appended, over the name of a window's first entry, and asks for the 25 entries before that name, drawn in order. The literal word `last` asks for the last 25 entries. A before-token or `last` with 25 or fewer entries before it **underflows**: the window asked for is the first window, and the page answers a 303 to `/` keeping only the other list's value, so each list's first window has one address. A value the page cannot decode, a token issued for the other list or by another tool included, is the not-found page, decided before the host is read.

The lists are the host's: both are read whole, each with one `opsctl` call, and windowed in memory, and the record is asked only for the created times of the groups window's slugs. That departs from shape's Storage entry; `D07-tools` records the departure and why, and the page inherits it with the tools' windows.

## Guests, methods and failures

The handler decides in this order. A guest is answered 302 to `pages.SignIn` with an empty body, whatever its path and method, before anything else is read. A signed-in request to a path that is not one of the three page paths is the not-found page, whatever its method. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD` and an empty body. On `/`, an undecodable page value in either parameter is the not-found page. None of these reads the host or the store. Then the landing reads both host lists: when either cannot be read, the answer is 503 in plain text with the line `host.HostFailed`, whatever the host said, a refusal's diagnostic included; with both read, an underflow is answered 303 without reading the record; otherwise the record is read for the groups window's created times, and a store that cannot be read is 503 in plain text with the line `store.Unreachable`. The tools page, the about screen and the not-found page read neither and are served the same while either fails. `HEAD` is answered as `GET` without a body. No answer sets a cookie.

## Recorded decisions

- **One data type per thing a template draws**, each field list exactly the template comment's, in its order (the root `AGENTS.md`'s Web assets rule): `LandingData` with `GroupRow` and `UserRow`, `ToolsData` with `ToolRow`, `AboutData` and `NotFoundData`.
- **A group's members come from the user list and its count from the group list** (the root's ruling): the landing reads `user list` once and puts in each group the users whose groups include its slug, rather than calling `group members` once per row, so one page view runs two host commands whatever the window holds. `MemberCount` is the host's count as `group list` gives it; the host keeps the two in agreement, and the page shows each as the host said it.
- **A group's created time is the record's, by slug**; a group the host lists that the record does not hold has `Created` and `CreatedText` empty, and a group the record holds that the host does not list is never shown, since the page draws only the host's entries (the brief's settled record). Users carry no created time on the page: the template has none.
- **Counts are Go `int`** and **names are relayed as the host gives them**: `MemberCount` is `host.Group.Members`, `KeyCount` the length of `host.User.Keys`, and `State` the host's word, one of `host.StateActive` and `host.StateLocked`.
- **Times in two forms**: `time.RFC3339` in UTC for the `time` element and `pages.MinuteLayout` for the text, the forms the template comment names; `pages.MinuteLayout` is a contract constant with its value, as the suite's other apps declare it. The page needs no second layout: it shows no stamp to the second as text.
- **The landing's forward tokens are the tools'**: an after-token in `groups_page`, and `GroupsNext`, are `paging.Token{Tool: "groups"}.Encode` of a slug, and in `users_page`, and `UsersNext`, `paging.Token{Tool: "users"}.Encode` of a login name, the tokens `D07-tools`' `groups` and `users` answer as `next`; so a window on the page and the tool's answer for the same `page` are one window, and a token on the page can be handed to an agent. `groups` and `users` refuse a before-token and `last`, so the agreement holds for the empty value and after-tokens only.
- **Prev, Last and the 303 follow `design/`'s listing entry and its two-list form**: before-tokens under `groups-before` and `users-before`, `last` naming the last 25 entries aligned to the end of the list (equal to the Next walk's final window only when the entries number a multiple of 25), and an underflow answered 303 to `/` keeping the other list's value, query-escaped, both dropped when both underflow.
- **An undecodable value is the not-found page** (`design/`'s listing entry), decided before the host is read, so it is the same while the host or the store fails; the not-found template's comment says accounts has no page values, which the landing's two parameters contradict: an asset nit to report, not a contract.
- **A host that cannot list is a plain-text 503 with `host.HostFailed`**: the landing template has no unavailable state, the page is not the tool's caller, so it relays no diagnostic of the host's, a refusal's included, and says the host failed, as the tools' failure says it (`D05-host`). The host is read before the record, so a host failure answers `host.HostFailed` whatever the store's state.
- **A database outage is a plain-text 503 with `store.Unreachable`**, as the suite's apps answer where the answer is not a page; a landing that would draw a page reads the record even when its groups window is empty, so the outage is answered the same whatever the host lists. An underflow's 303 needs only the host's lists, so it is answered while the store fails.
- **The guest's redirect follows `D03-serve`** (pages inside `identity.Optional`, with `guests = false` in the manifest so nginx gates too). A guest is sent to sign in before the method or the query is looked at, and the 302 has an empty body: it is not a page, so it draws no template.
- **`pages.Auth` and `pages.SignIn` are declared here**, with the host prefix `accounts.`: the pages are their only consumer and accounts has no address package (`D01-layout-and-run-seam`). The sign-in address is built on the auth address, so the banner's links and a guest's sign-in link name the same auth address in every case.
- **The tools page reads the MCP server's registered tools**, `mcp.Server.Tools()`, at each request: `D03-serve` hands `pages.Config` the server on which `tools.Register` registers `D07-tools`' tools in catalog order, so the page and `tools/list` cannot disagree, and each row's description is `tools.FirstLine` of the registered description.
- **`pages.Description` is a copy constant declared without a value**: the decisions document does not fix the manifest's description, so its words are copy, in one place, and `D09-on-a-space` ties the manifest's description line to the constant by name.
- **`pages.Config` carries the host and the store and no clock**: the page formats the times the host and the record hold and stamps nothing.

## Consumer tasks

`web.Handler` (`D03-serve`) calls `set, err := pages.Load()` once and serves every page path with `identity.Optional(pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, Host: cfg.Host, MCP: cfg.MCP}))`, `tools.Register` having filled the server.

The landing reads `gs, err := cfg.Host.GroupList(ctx)` and `us, err := cfg.Host.UserList(ctx)`, windows each by its page value, reads `rec, err := cfg.Store.Groups(ctx, slugs)` for the groups window's slugs, and executes `landing` through `set.Write(w, r, http.StatusOK, "landing", pages.LandingData{Banner: b, Groups: []pages.GroupRow{{Slug: g.Slug, MemberCount: g.Members, Members: members, Created: c.UTC().Format(time.RFC3339), CreatedText: c.UTC().Format(pages.MinuteLayout)}, …}, GroupsPage: p, GroupsPrev: …, GroupsNext: …, Users: []pages.UserRow{{Login: u.Name, State: u.State, Groups: u.Groups, KeyCount: len(u.Keys), LastSignIn: …, LastSignInText: …}, …}, UsersPage: q, UsersPrev: …, UsersNext: …})`, `b` being `cfg.Banner(page.User{Email: …, ProfileURL: pages.Auth(r, cfg.ServicesPath) + "/", LogoutURL: pages.Auth(r, cfg.ServicesPath) + "/logout"})` with a nil `Trail`. The tools page maps `cfg.MCP.Tools()` to `[]pages.ToolRow{{Name: t.Name, Description: tools.FirstLine(t.Description)}, …}` with `b.Trail` set to `[]page.Level{pages.ToolsLevel}`; the about screen executes `about` with `pages.AboutData{Banner: b, Description: pages.Description}`, `b.Trail` set to `[]page.Level{pages.AboutLevel}`; the not-found page executes `notfound` with `pages.NotFoundData{Banner: b}`.

A test opens a store over its own database with a clock it sets, records groups with `AddGroup`, builds a host with `host.NewMemory()` and fills it, or a `host.Host` of its own that answers lists it chooses, fails on demand and records every call, writes a services file with a URL for `auth`, or none, and entries for at least one sibling naming a Unix socket on which a fake records each connection, builds its own set with `pages.Load()`, a server `mcp.NewServer(mcp.ServerConfig{Name: pages.ServiceName, Telemetry: w})` (after `t.Setenv` of `IKIGENBA_SERVICES`) on which it registers tools, serves `identity.Optional(pages.Handler(cfg))` with a fixed banner, sends raw requests with and without `X-User-Id`, and compares each body with what `set.Write` writes for the data the definitions below build. It lists more than 25 groups or users to get a non-empty next token, hands it back as that list's parameter, compares the window with what `groups` or `users` answers for the same `page`, walks Next to the end and Prev back to the 303, asks `last`, pages one list while the other's value is set, asks an undecodable value, and turns the host's failure and the store's `SetFailing(true)` on to see each 503.
