# D06-pages

What accounts draws as HTML: `internal/pages`, the six templates `landing`, `host`, `tools`, `about`, `notfound` and `join` of the root package's `Assets()` and the data each is executed with, `pages.Description`, the two time layouts, the auth and sign-in addresses the pages build, and the page handler that answers `/`, `/hosts/<name>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it. The landing page says what the service is and lists the hosts, the data volumes kept from deleted hosts, the accounts placed on them and the users of each account, four lists with their own paging; the host page shows one host's record and its latest report in full (outcomes 10, 14 and 24 of /home/mgreenly/Documents/ikigenba-ssh-hosts.md; outcomes cited as outcome N are that document's), its bans and allowlist included (outcomes 5 and 13 of /home/mgreenly/Documents/ikigenba-ssh-bans.md). The landing also shows which users are admins of their account and how many unused invites each account holds (outcomes 1 and 7 of /home/mgreenly/Documents/ikigenba-self-service-accounts.md, cited below as self-service outcome N). Both pages show each host's DNS name, and the host page the hostname the host last reported (outcomes 13 and 14 of /home/mgreenly/Documents/ikigenba-host-names.md, cited below as host-names outcome N). Both pages show what the delete asked of a host does with its data volume, and the landing lists the volumes kept from deleted hosts, and from hosts replaced from backup (outcomes 11 and 14 of /home/mgreenly/Documents/ikigenba-host-numbers-and-delete.md, cited below as delete outcome N). Both pages show backups (/home/mgreenly/Documents/ikigenba-host-backups.md, cited below as backups outcome N, with its log /home/mgreenly/Documents/ikigenba-host-backups-decisions.md): each account's backup health and last snapshot on the landing, each host's closed time and how many of its accounts are flagged (backups outcomes 20 and 22, 24), and on the host page each account's backups, databases, final backup and restore, the host's replacement and the restores agents asked for (backups outcomes 24, 28 to 31, 37 and 38); the about screen shows the backup settings every host gets (backups outcome 19). The pages this handler serves are read-only: they carry no form, change nothing in the record, make no AWS call and reach no daemon or sibling; every change goes through a tool (`D07-tools`). A guest is sent to sign in.

The enrollment page at `/join?token=<token>` (self-service outcomes 11 to 15) is the one page that has a form, changes the record and answers a guest, and it is not this handler's: `D03-serve` routes exactly `/join` to `internal/join` (`D18-enrollment`) ahead of the page handler, so such a request never reaches the page handler. This document declares only what that page is drawn with: the template `join`, its data `JoinData`, and the outcome constants it switches on; `D18-enrollment` decides the outcome and writes the page through the same `Set`.

Each template's data is exactly what its opening comment in `assets/` names, field for field and in its order: `landing.html` (`LandingData` with `HostRow`, `KeptVolumeRow`, `AccountRow`, `UserRow`), `host.html` (`HostData` with `HostView`, `ReportView`, `VolumeView`, `SliceRow`, `BanRow`, `BackupRow`, `DatabaseRow`, `RestoreRow`), `tools.html` (`ToolsData`, `ToolRow`), `about.html` (`AboutData`), `notfound.html` (`NotFoundData`) and `join.html` (`JoinData`).

`D01-layout-and-run-seam` declares `pages.ServiceName`, the root package's `Assets()` and what configured means; `D03-serve` routes every path that is not `/mcp`, under `/_appkit/`, `/accountsd`, under `/accountsd/` or exactly `/join` to this handler inside `identity.Optional`, defines a guest, and builds `pages.Config` (`Configured` from `Settings.Cloud()`, `Domain` the hosts domain, `SandboxHosts.Domain` in sandbox mode); `D04-store` holds every host, kept volume, account, user, invite and report the pages show, with each host's delete choice (`Host.OnDelete`), each user's admin flag and each account's count of unexpired invites, answers no deleted host by name or in its host lists, computes health with `store.Health`, and declares `store.Unreachable`; it also holds each host's closed time and replace mode (`Host.Closed`, `Host.Replace`), each kept volume's cause, the backup settings (`BackupSettings`, `store.DefaultBackupSettings()` while it holds none), each account's backup facts (`AccountBackup`, answered by `BackupOf` and `BackupsOn`) and the restores asked on a host (`Restore`, answered by `RestoresOn`), and declares the backup health functions `store.BackupHealth`, `store.FilesStale` and `store.DatabaseHealth`; `D11-protocol` declares the backup members of a report the host page reads (`protocol.AccountBackup`, `protocol.Database`) and the step and restore kind values; `D07-tools` registers the tools the tools page lists, in catalog order, declares `tools.FirstLine` and the four list tools whose tokens the landing shares, `kept_volumes` among them with the members of its key; `D17-names-keys-sizes` declares the defaults the about screen shows; `D09-on-a-space` carries `pages.Description` in the manifest; `D18-enrollment` executes `join` with a `JoinData` for every answer of the enrollment page but its 405, 413 and 503. appkit's `page`, `identity`, `mcp`, `paging` and `services` packages own their contracts.

## The landing page

On a space that operates no hosts (`Configured` false) the landing shows only the notice: `LandingData` with `Configured` false and nothing else filled; nothing is read and the page values are ignored.

Otherwise it shows one window of each of four lists, each read from the store alone (no AWS call, no daemon, no report body decoded):

- **Hosts** in creation order (their sequence number, `D04-store`), deleted hosts never shown. A host takes the lowest number no live host holds, so a name a deleted host had is taken again and names are not in creation order: a later `host02` is listed after `host05` when it was created after it. A row carries the name, its DNS name (`<name>.<hosts domain>`, empty when no hosts domain is configured), the state as stored, a reason (that of a failed state, or else why the host's own DNS record could not be made, as the engine's scan notes it, `D10-ops`), what the delete asked of it does with its data volume (`keep` or `delete`, empty when no delete is its current operation, as the store answers `Host.OnDelete`), the health `store.Health` computes from the host's columns and the page's clock, the type, both volume sizes, the Elastic IP, how many accounts are placed on it, when its latest report was received, when its last close finished (empty while it is open: closed is a recorded time, not a state, and stays through stop, start and resize) and how many of its accounts are flagged, their backup health `stale` or `error`.
- **Kept volumes**, the data volumes of deleted hosts and of hosts replaced from backup that accounts' record explains, in state `kept` or `deleting` (`D04-store`), the most recently kept first (by when it was kept, latest first, then by volume id, greatest first): the volume id, the name of the host it came from (a deleted host, whose name a later live host may have too, or a replaced host, which is still live), why it was kept, the size and when it was kept: when its host was deleted, or when a replace kept it. A replace from backup keeps the host's old data volume the same way, with the cause `replaced` and the replace's time as its deleted time; every other kept volume, those the previous release kept included, has the cause `deleted`. A volume being deleted stays listed, drawn like a kept one, until its delete finishes; one whose delete was refused is kept again. Nothing in AWS that the record does not explain is listed.
- **Accounts** by slug: the slug, its host, its DNS name (`<slug>.<hosts domain>`), its state, the reason of a failed state, how many users it has, how many unused invites it holds (its invites neither used, revoked nor expired, as the store counts them; never an invite's id, token or link), its backup health and the time of its last file snapshot, and when it was created.
- **Users** by account slug then login name, so each account's users read together: the login, the account, whether the user is an admin of that account, the state, whether a change is pending on the host (the user's version is above the version its host last applied), how many keys and the last sign-in.

Times are UTC, RFC 3339 to the second for a `time` element and `pages.MinuteLayout` for the text, as the template comment names them.

Paging is `design/`'s two-list form carried to four, as the template asks: each list has its own parameter (`hosts_page`, `accounts_page`, `users_page`, `volumes_page`) and its own `Page`, `Prev` and `Next`; each nav carries the other three lists' values, in that order. A list's page value is empty (the first window), an **after-token** (the token its tool answers as `next`: `paging.Token{Tool: "hosts"}` over a host's sequence number, `{Tool: "accounts"}` over a slug, `{Tool: "users"}` over an account slug and a login name, `{Tool: "kept_volumes"}` over the time a volume was kept (when its host was deleted, or when a replace kept it) and a volume id, encoded as `D07-tools` encodes them), a **before-token** issued by the page under the tool's name with `-before` appended over a window's first key, or `last`. A before-token or `last` with 25 or fewer entries before it **underflows**: the page answers 303 to `/` keeping the other lists' values that are set and do not underflow, so each list's first window has one address. A value the page cannot decode, a token of another list included, is the not-found page, decided before the store is read.

## The host page

`/hosts/<name>` shows one live host: its record (`HostView`, the landing row's fields, its delete choice among them, then its instance id, data volume id, created time and the allowlist accounts' record holds for it) and its latest report (`ReportView`), nil when none has been received. The report view carries the static hostname the host reported having, read from the stored report's body (`D04-store` keeps no other copy), so a reader compares it with the host's DNS name to see whether the name is applied (host-names outcome 14); a report from a daemon that sends no hostname shows it empty. Received, booted, created, banned and expiry times are shown to the second in `pages.SecondLayout`; the report's applied version beside the host's current version (`Wanted`) shows whether the host is behind.

The report view carries the host's current fail2ban bans as the report lists them (newest first, at most `protocol.MaxBans`, as `D11-protocol`'s `Bounded` leaves them), the report's ban total, which exceeds the listed bans when the report cut the list or when a line of the host's listing could not be listed (`D15-machine`), so the total can be positive with no ban listed, and the allowlist the host applied. The record's allowlist (`HostView.Allowlist`) and the applied one (`ReportView.Allowlist`) are shown side by side, so a reader sees whether the host has caught up with an `allow_ip` or `disallow_ip`; neither holds loopback, which the jail always adds (`D15-machine`). A report from a daemon that sends no bans or allowlist shows both empty and a total of 0. The page stays read-only: lifting a ban or editing the allowlist is a tool's (`D07-tools`). The banner's trail is the one level `pages.HostLevel(name)`. A name no live host has, a deleted host's, any other path under `/hosts/`, `/hosts` itself, and any host page on a space that operates no hosts are the not-found page. Once a host finishes its delete it has no page; its kept volume, if any, is on the landing. When a later host takes a deleted host's name, `/hosts/<name>` is the later host's alone: the store vacates the earlier host's row when the name is taken (`D04-store`), so the report and allowlist the page reads by name are the live host's own, never the earlier one's.

## Backups on the pages

Backup health is computed when a page is drawn, never stored: from each account's backup facts as the store folds them from its host's reports (`AccountBackup`), the backup settings the store holds (or its defaults) and the page's clock, by `store.BackupHealth`, `store.FilesStale` and `store.DatabaseHealth` (`D04-store`). The settings are read once per request. An account whose host's daemon has never reported backups, as from a daemon older than them, has zero facts and reads `none`. A stopped host's accounts go stale once the threshold passes, since nothing backs them up.

The landing's host row adds when the host's last close finished and how many of the accounts placed on it are flagged (health `stale` or `error`); its account row adds the account's health and its last file snapshot. The host page's view adds the replace mode while a replace is the host's current operation (running or failed), and the page adds three lists: one backup row per account placed on the host, in slug order, with its health, whether its files are behind, its last snapshot and check, its error, its final backup in the host's latest close and its restore in a current replace from backup, and its databases as the latest report lists them; how many databases are listed over all accounts; and the newest `pages.MaxRestoreRows` restores asked on the host with the host's total. Each account shows at most `pages.MaxDatabaseRows` databases, by path, with the total the report gives, so the page says when a list was cut. Database health and last write come from the stored report's body, the one report the page already decodes; the account-level facts come from the store's backup rows, so they stay true when the report cut an account's databases.

A host's state while it is closed is `running`; `closing`, `opening`, `replacing` and `restoring` are states of their own, drawn as any state is.

## The enrollment page's data

`JoinData` is what the template `join` draws, field for field and in the order of its opening comment: the outcome, the invite's account, that account's DNS name, whether the invite makes an admin, and the user name and key the person submitted. It carries no `page.Banner`: the page has no banner and no footer, since both are for a signed-in user, as auth's sign-in card has none.

`Outcome` is one of seven constants, and their values are what the template compares it with: `JoinForm` (the empty string) the form, `JoinUnusable` an invite link that cannot be used (unknown, used, expired, revoked or malformed alike), `JoinName` a refused user name (malformed, reserved or taken alike), `JoinKey` a refused key, `JoinFull` an account whose host cannot take another user now, `JoinLimited` a submission refused by the rate limit, and `JoinDone` a user created. Which fields each outcome fills, and from what, is `D18-enrollment`'s; the template comment says the same: `Account` and `DNSName` empty for `JoinUnusable` and `JoinLimited`, `User` and `Key` as submitted for `JoinName`, `JoinKey` and `JoinFull`, `User` the created login and `Key` empty for `JoinDone`.

## Tools, about and not found

The tools page lists every tool registered on the MCP server, in registration order, each with the first line of its description; the about screen shows the service's name, the banner's `Release` and `Commit`, `pages.Description`, and the defaults a host gets when its creation names none (`valid.DefaultType`, `valid.DefaultRootGB`, `valid.DefaultDataGB`), and the backup settings every host gets as the store answers them (its schedule, the snapshots kept, the database window and the two staleness thresholds; the weekly check's interval is not shown), on a space that operates no hosts as well. Every other path is the not-found page, 404, whatever the method.

## Guests, methods and failures

The path `/join` never reaches this handler (`D03-serve`), so the enrollment page changes nothing here: the handler still sends every guest that reaches it to sign in, `/join/`, every path below it and `/joinx` included, which are page-handler paths and, signed in, the not-found page.

The handler decides in this order. A guest is answered 302 to `pages.SignIn` with an empty body, whatever its path and method, before anything else is read. A signed-in request to a path that is not a page path is the not-found page, whatever its method. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD` and an empty body. On `/` with `Configured` true, an undecodable page value is the not-found page; on `/hosts/<name>` with `Configured` false, the not-found page. None of these reads the store. Then the landing, the host page or the about screen reads the store: a store that cannot be read is 503 in plain text with the line `store.Unreachable`; an underflow is answered 303; an unknown or deleted host is the not-found page. The about screen reads only the backup settings, and reads them whether or not the space operates hosts. The tools page and the not-found page never read the store and are served the same while it fails. `HEAD` is answered as `GET` without a body. No answer sets a cookie.

## Recorded decisions

- **One data type per thing a template draws**, each field list exactly the template comment's, in its order (root `AGENTS.md`, Web assets).
- **A per-record page, `/hosts/<name>`, and a four-list landing** (departure from `design/README.md`'s two-list form, as log D4 settled and entry A1 of the host-numbers decisions log (/home/mgreenly/Documents/ikigenba-host-numbers-and-delete-decisions.md) extended): a host's latest report is too much for a row, and hosts, kept volumes, accounts and users are four different things. The nav carries the other three values in the order `hosts_page`, `accounts_page`, `users_page`, `volumes_page`, as the template's comment asks, though the kept volumes section is drawn second; the 303's query follows the same order.
- **Hosts are ordered by creation sequence, not by name**: a host takes the lowest number no live host holds (`D04-store`), so after a delete a new host's name can be lower than an older host's, and creation order keeps each new host at the end of the list. The landing template's comment says so.
- **Kept volumes are a list of the landing, not a page of their own** (entry A1 of the host-numbers decisions log): a kept volume is one row of five values (volume id, host, cause, size and when it was kept, that time in two forms). Its key is the pair of the time it was kept (when its host was deleted, or when a replace kept it) and its volume id, ordered latest first, so the most recently kept volume leads and a volume id breaks a tie; the token's members are whatever `D07-tools`' `kept_volumes` encodes, since the page's forward tokens are the tool's. A row's host is the name of the host the volume came from, not a link: for a deleted host, the name it had when deleted, which has no page and which a later live host may carry as another host; for a volume a replace kept, the replaced host, which is still live under that name. A volume whose delete is in flight is listed as kept volumes are, since the row carries no state (`KeptVolumeRow` has none, as the template names it); it leaves the list once deleted.
- **A deleted host's name, taken again, shows only the live host.** Every host read the page makes, by name for the host page and by list for the landing, answers live hosts only (`D04-store`), and the vacate moves a deleted host's report, allowlist and operations off the name before a new host takes it, so neither page can show a deleted host or mix one into a live host's page.
- **The landing's forward tokens are the tools'**: an after-token on the page and the `next` its tool answers for the same `page` and no `limit` are one window, so a token on the page can be handed to an agent.
- **Health is computed, never stored**, by `store.Health` from host columns and `Config.Now` (`D04-store`): the landing decodes no report body, so a page of 25 hosts costs one keyset read.
- **`Pending` is the user's version above the host's applied version**, and **`Wanted` is the host's version**, beside the report's `Applied`: what the user and the host page show agree with what the tools answer.
- **Times in three forms**: `time.RFC3339` UTC for `time` elements, `pages.MinuteLayout` for the landing's texts and `pages.SecondLayout` for the host page's created, received, booted, banned and expiry texts, as the templates name them.
- **Bans and allowlists are shown as the record and the report hold them**: the page neither re-sorts nor re-cuts them, since the store answers the allowlist sorted (`D04-store`) and the report it keeps is already `Bounded` (`D11-protocol`); bans seen in reports are shown, never recorded as events.
- **A database outage is a plain-text 503 with `store.Unreachable`**, as before: the templates have no unavailable state.
- **An unconfigured space shows the notice and reads nothing**, whatever the page values: there is nothing to page, and the store is not consulted for hosts that cannot exist. `/hosts/<name>` there is the not-found page, as the template comment states.
- **Prev, Last and the 303 follow `design/`'s listing entry** with before-tokens under `hosts-before`, `accounts-before`, `users-before` and `kept_volumes-before`, `last` aligned to the end of the list, and an underflow keeping the other values.
- **The guest's redirect follows `D03-serve`**: pages sit inside `identity.Optional`; with `guests = true` in the manifest (`D09-on-a-space`) nginx lets a guest through to the page, which sends it to sign in before the method or the query is looked at.
- **`pages.Config` carries a clock**, `Now`, for health only; it carries no cloud and no engine, so the pages cannot change anything.
- **`HostLevel(name)` is a function**, not a variable: the level names the host.
- **The enrollment page's data is declared here; its handler is `D18-enrollment`'s.** `internal/pages` owns every template's data type and `Load`, so the six templates are loaded and checked in one place and the join handler writes through the same `*Set`. The page handler itself does not serve `join`: its routes stay read-only and signed-in, and the one guest page with a form lives in a package of its own.
- **The outcome constants carry values, and the values are contract.** The template switches on `.Outcome` by comparing it with strings, so the strings are read by a program, the template, not by a person: they are contract like a token's tool name, not copy. A rename of a value is an edit to both the constant and the asset. `JoinForm` is the empty string so a zero `JoinData` is the plain form.
- **`JoinData` carries no banner**, as the template asks: the banner's profile, sign-out and page menu lead nowhere a guest may go.
- **Admins and invites are shown, never changed, on the landing.** `UserRow.Admin` and `AccountRow.InviteCount` are read with the rows; promoting, demoting, making, listing and revoking invites are tools (`D07-tools`). The landing shows a count, never an invite: an invite's id is `list_invites`', and its token and link are answered once, by `create_invite`, and shown nowhere else.
- **The guest's redirect is unchanged** (R-SFH9-7KWL keeps its id): the enrollment route is decided before the page handler, so no requirement of the page handler gains an exception.
- **A host's DNS name is computed, never stored**, as `<name>.<cfg.Domain>`, the same `Config.Domain` the account rows use, and empty when that is empty, so a space that names no hosts domain shows none rather than a name ending in a dot. On a configured space `D03-serve` always gives a non-empty domain, so the empty case is for tests and the template's own empty state.
- **The reported hostname is read from the stored report**, `Report.Body.Hostname` (`D04-store`, `D11-protocol`), never from a column of its own, as the contract settled: the host page already decodes that one report body, and the landing, which decodes none, does not show the hostname.
- **One `Reason` for two causes**: a host's shown `Reason` is its failure reason, or when that is empty the reason its own record could not be made (`Host.RecordReason`, noted by the engine's scan, `D10-ops`). A failed operation's reason wins because it is what an agent must act on first; a record conflict on a running host is shown beside a healthy state, since it never fails or stops the host. The templates draw `.Reason` whenever it is set.
- **The delete's choice is shown as the store answers it**: `HostRow.OnDelete` and `HostView.OnDelete` are `Host.OnDelete` (`D04-store`), `keep` or `delete` while a delete is the host's current operation and empty otherwise, so a host failed by its delete keeps showing the choice its retry would carry. After the delete finishes the host has no row and no page: a kept volume shows on the kept volumes list, and a delete that took the data leaves nothing on a page (delete outcome 11, as entry A1 of the host-numbers decisions log reads it).
- **Memory**: each list reads one window plus one row through the store's keyset listings (`D04-store`; the kept volumes list through `ListKeptVolumes`, `ListKeptVolumesBefore` and `LastKeptVolumes`), each host row's DNS name, reason and delete choice computed from its own row (the record reason and the choice coming with the host as the store reads it, `D04-store`), each kept volume row from its own row, each account row's invite count and each user row's admin flag coming with its row (a count bounded by `store.MaxInvites`, no invite row read), and the host page one host with its at most `valid.MaxAllowlistPerHost` allowlist entries, its accounts' count and one report row (bounded by `protocol.MaxReportBytes`, the reported hostname included; its view holds at most `protocol.MaxBans` ban rows and `protocol.MaxAllowlist` entries). No test can see this at the page seam without a counting store, so it is a bound the page does not prove itself: the store's listing methods return at most the limit they are given (`D04-store` R-JA1O-3JB7), and the page asks for one window plus one row. Backups add, per request, one read of the backup settings; on the landing one account's backup facts per account row and, per host row, the backup facts of the accounts placed on it (at most 25 rows times `valid.MaxAccountsPerHost`), each folded to a count before the next host is read; and on the host page the backup facts of the host's accounts (at most `valid.MaxAccountsPerHost`), the one report body it already decodes (whose database entries `protocol.MaxDatabases` bounds in a bounded report) and at most `pages.MaxRestoreRows` restores with the host's total. The page's own cuts, `MaxRestoreRows` restores and `MaxDatabaseRows` databases per account, are requirements, since a test sees them; the rest is guidance like the above.
- **Backup health is computed at read time, never stored** (backups log): `store.BackupHealth`, `store.FilesStale` and `store.DatabaseHealth` over the store's facts, the settings and `Config.Now`, as `store.Health` is for hosts, so the landing, the host page and `backup_status` agree for the same moment. A host's flag is the count of its accounts that are `stale` or `error`, so `none` (never reported) does not flag a host whose daemon predates backups. Database staleness is measured by when the replica last held every write (`Synced`, backups log): an idle database stays healthy.
- **The about screen reads the settings and fails like the landing** (backups log): the settings are the store's, so a store that cannot be read is the plain refusal with `store.Unreachable`, as for the landing and the host page, rather than a page showing defaults the hosts may not have. It reads them whatever `Configured` is, since the settings and the copy describing them do not depend on the space operating hosts. The weekly check interval (`CheckDays`) is not in `AboutData`: the template words it.
- **The host row's new fields go at its end** (`Closed`, `ClosedText`, `BackupFlagged`, after `ReportedText`), in the order both `landing.html`'s and `host.html`'s comments name the host's fields, so `HostView`'s first sixteen fields are the host row's and the existing fields keep their positions; like every other data type, `HostRow` follows its template comment's order without exception.
- **New row fields are further definitions, not re-mints of the row definitions** (precedent R-31QS-98MR, R-CZHZ-O7RU, R-D0PW-1ZIJ, R-D1XS-FR98): the host and account row definitions stay true as written, and re-minting them would re-mint every paging requirement that cites them without changing what any of them says. The kept volumes list and kept volume row definitions were re-minted, because a replace keeps a volume whose host is still live, so their key and time are when the volume was kept rather than when its host was deleted; the landing data and the paging requirements that cite them were re-minted with them. The struct declarations, the host view (whose field count changed) and the host page (whose data grew) are re-minted.
- **Databases come from the latest report's body; account facts from the store's backup rows.** The host page already decodes that one body, and the store keeps no database rows (`D04-store`). An account's `DatabaseTotal` is the report's (raised to the listed count if lower), so the page shows how many it cut; a report without backups, from an earlier daemon, lists none and a total of 0. `FinalAt` is shown only when the final is `done`, as the template asks; a failed final's text is the row's `Error`.
- **Restores are the newest `MaxRestoreRows` with the host's total**, through `store.RestoresOn`, so the list is bounded and says when it was cut; they are the live host's own, matched by its sequence number, not by name (`D04-store`).
- **Closing, opening, replacing and restoring are drawn as states**; closed is not a state but a time beside it, which survives stop, start and resize. The replace mode is shown while a replace is the current operation, running or failed, as the store answers `Host.Replace`.

## Consumer usage

`web.Handler` (`D03-serve`) calls `set, err := pages.Load()` once and serves every page path with `identity.Optional(pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, MCP: cfg.MCP, Configured: cfg.Configured, Domain: cfg.Hosts.Domain, Now: now}))`.
