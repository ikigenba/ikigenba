# D06-pages

What accounts draws as HTML: `internal/pages`, the five templates `landing`, `host`, `tools`, `about` and `notfound` of the root package's `Assets()` and the data each is executed with, `pages.Description`, the two time layouts, the auth and sign-in addresses the pages build, and the page handler that answers `/`, `/hosts/<name>`, `/tools`, `/about` and every other path the route table (`D03-serve`) hands it. The landing page says what the service is and lists the hosts, the accounts placed on them and the users of each account, three lists with their own paging; the host page shows one host's record and its latest report in full (outcomes 10, 14 and 24 of /home/mgreenly/Documents/ikigenba-ssh-hosts.md; outcomes cited as outcome N are that document's). The pages are read-only: they carry no form, change nothing in the record, make no AWS call and reach no daemon or sibling; every change goes through a tool (`D07-tools`). A guest is sent to sign in.

Each template's data is exactly what its opening comment in `assets/` names, field for field and in its order: `landing.html` (`LandingData` with `HostRow`, `AccountRow`, `UserRow`), `host.html` (`HostData` with `HostView`, `ReportView`, `VolumeView`, `SliceRow`), `tools.html` (`ToolsData`, `ToolRow`), `about.html` (`AboutData`) and `notfound.html` (`NotFoundData`).

`D01-layout-and-run-seam` declares `pages.ServiceName`, the root package's `Assets()` and what configured means; `D03-serve` routes every path that is not `/mcp`, under `/_appkit/`, `/accountsd` or under `/accountsd/` to this handler inside `identity.Optional`, defines a guest, and builds `pages.Config` (`Configured` from `Settings.Cloud()`, `Domain` the hosts domain, `SandboxHosts.Domain` in sandbox mode); `D04-store` holds every host, account, user and report the pages show, computes health with `store.Health`, and declares `store.Unreachable`; `D07-tools` registers the tools the tools page lists, in catalog order, declares `tools.FirstLine` and the three list tools whose tokens the landing shares; `D17-names-keys-sizes` declares the defaults the about screen shows; `D09-on-a-space` carries `pages.Description` in the manifest. appkit's `page`, `identity`, `mcp`, `paging` and `services` packages own their contracts.

## The landing page

On a space that operates no hosts (`Configured` false) the landing shows only the notice: `LandingData` with `Configured` false and nothing else filled; nothing is read and the page values are ignored.

Otherwise it shows one window of each of three lists, each read from the store alone (no AWS call, no daemon, no report body decoded):

- **Hosts** in creation order (their sequence number, which is name order up to `host99` and keeps creation order beyond, where byte order would put `host100` before `host20`), deleted hosts never shown. A row carries the name, the state as stored, the reason of a failed state, the health `store.Health` computes from the host's columns and the page's clock, the type, both volume sizes, the Elastic IP, how many accounts are placed on it, and when its latest report was received.
- **Accounts** by slug: the slug, its host, its DNS name (`<slug>.<hosts domain>`), its state, the reason of a failed state, how many users it has and when it was created.
- **Users** by account slug then login name, so each account's users read together: the login, the account, the state, whether a change is pending on the host (the user's version is above the version its host last applied), how many keys and the last sign-in.

Times are UTC, RFC 3339 to the second for a `time` element and `pages.MinuteLayout` for the text, as the template comment names them.

Paging is `design/`'s two-list form carried to three, as the template asks: each list has its own parameter (`hosts_page`, `accounts_page`, `users_page`) and its own `Page`, `Prev` and `Next`; each nav carries the other two lists' values. A list's page value is empty (the first window), an **after-token** (the token its tool answers as `next`: `paging.Token{Tool: "hosts"}` over a host's sequence number, `{Tool: "accounts"}` over a slug, `{Tool: "users"}` over an account slug and a login name), a **before-token** issued by the page under the tool's name with `-before` appended over a window's first key, or `last`. A before-token or `last` with 25 or fewer entries before it **underflows**: the page answers 303 to `/` keeping the other lists' values that are set and do not underflow, so each list's first window has one address. A value the page cannot decode, a token of another list included, is the not-found page, decided before the store is read.

## The host page

`/hosts/<name>` shows one live host: its record (`HostView`, the landing row's fields then its instance id, data volume id and created time) and its latest report (`ReportView`), nil when none has been received. Received, booted and created times are shown to the second in `pages.SecondLayout`; the report's applied version beside the host's current version (`Wanted`) shows whether the host is behind. The banner's trail is the one level `pages.HostLevel(name)`. A name no live host has, a deleted host's, any other path under `/hosts/`, `/hosts` itself, and any host page on a space that operates no hosts are the not-found page.

## Tools, about and not found

The tools page lists every tool registered on the MCP server, in registration order, each with the first line of its description; the about screen shows the service's name, the banner's `Release` and `Commit`, `pages.Description`, and the defaults a host gets when its creation names none (`valid.DefaultType`, `valid.DefaultRootGB`, `valid.DefaultDataGB`). Every other path is the not-found page, 404, whatever the method.

## Guests, methods and failures

The handler decides in this order. A guest is answered 302 to `pages.SignIn` with an empty body, whatever its path and method, before anything else is read. A signed-in request to a path that is not a page path is the not-found page, whatever its method. A request to a page path whose method is not `GET` or `HEAD` is 405 with `Allow: GET, HEAD` and an empty body. On `/` with `Configured` true, an undecodable page value is the not-found page; on `/hosts/<name>` with `Configured` false, the not-found page. None of these reads the store. Then the landing or the host page reads the store: a store that cannot be read is 503 in plain text with the line `store.Unreachable`; an underflow is answered 303; an unknown or deleted host is the not-found page. The tools page, the about screen and the not-found page never read the store and are served the same while it fails. `HEAD` is answered as `GET` without a body. No answer sets a cookie.

## Recorded decisions

- **One data type per thing a template draws**, each field list exactly the template comment's, in its order (root `AGENTS.md`, Web assets).
- **A per-record page, `/hosts/<name>`, and a three-list landing** (departure from `design/README.md`'s two-list form, as log D4 settled): a host's latest report is too much for a row, and hosts, accounts and users are three different things. The nav carries the other two values in the order `hosts_page`, `accounts_page`, `users_page`, as the template's comment asks.
- **Hosts are ordered by creation sequence, not by name**: identical to name order up to `host99`, and right after it. The landing template's comment says "sorted by name"; an asset nit, reported, not a contract.
- **The landing's forward tokens are the tools'**: an after-token on the page and the `next` its tool answers for the same `page` and no `limit` are one window, so a token on the page can be handed to an agent.
- **Health is computed, never stored**, by `store.Health` from host columns and `Config.Now` (`D04-store`): the landing decodes no report body, so a page of 25 hosts costs one keyset read.
- **`Pending` is the user's version above the host's applied version**, and **`Wanted` is the host's version**, beside the report's `Applied`: what the user and the host page show agree with what the tools answer.
- **Times in three forms**: `time.RFC3339` UTC for `time` elements, `pages.MinuteLayout` for the landing's texts and `pages.SecondLayout` for the host page's created, received and booted texts, as the templates name them.
- **A database outage is a plain-text 503 with `store.Unreachable`**, as before: the templates have no unavailable state.
- **An unconfigured space shows the notice and reads nothing**, whatever the page values: there is nothing to page, and the store is not consulted for hosts that cannot exist. `/hosts/<name>` there is the not-found page, as the template comment states.
- **Prev, Last and the 303 follow `design/`'s listing entry** with before-tokens under `hosts-before`, `accounts-before` and `users-before`, `last` aligned to the end of the list, and an underflow keeping the other values.
- **The guest's redirect follows `D03-serve`**: pages sit inside `identity.Optional`; with `guests = true` in the manifest (`D09-on-a-space`) nginx lets a guest through to the page, which sends it to sign in before the method or the query is looked at.
- **`pages.Config` carries a clock**, `Now`, for health only; it carries no cloud and no engine, so the pages cannot change anything.
- **`HostLevel(name)` is a function**, not a variable: the level names the host.
- **Memory**: each list reads one window plus one row through the store's keyset listings (`D04-store`), and the host page one host, its accounts' count and one report row (bounded by `protocol.MaxReportBytes`). No test can see this at the page seam without a counting store, so it is a bound the page does not prove itself: the store's listing methods return at most the limit they are given (`D04-store` R-JA1O-3JB7), and the page asks for one window plus one row.

## Consumer usage

`web.Handler` (`D03-serve`) calls `set, err := pages.Load()` once and serves every page path with `identity.Optional(pages.Handler(pages.Config{Banner: cfg.Banner, Pages: set, ServicesPath: cfg.ServicesPath, Store: cfg.Store, MCP: cfg.MCP, Configured: cfg.Configured, Domain: cfg.Hosts.Domain, Now: now}))`.

Agent creates a host: after `create_host`, `GET /` shows `pages.HostRow{Name: "host01", State: "provisioning", Health: "none", Type: "t4g.medium", RootGB: 20, DataGB: 50, …}`; `GET /hosts/host01` draws `host` with `pages.HostData{Banner: b, Host: pages.HostView{Name: "host01", …, InstanceID: "", DataVolume: "", Created: …, CreatedText: …}, Report: nil}`, `b.Trail` being `[]page.Level{pages.HostLevel("host01")}`. Task 3: once the daemon reported, `Report: &pages.ReportView{Received: …, Applied: 3, Wanted: 3, …, Root: pages.VolumeView{…}, Slices: []pages.SliceRow{{Account: "acme", …}}}`. Task 5: `pages.UserRow{Login: "daffy", Account: "acme", State: "active", Pending: true, KeyCount: 1}` until applied. Task 12: a silent host's row and page show `Health: "silent"`. Task 14: `GET /` draws `pages.LandingData{Banner: b, Configured: false}` and `GET /hosts/host01` is the not-found page.

A test opens a store over its own database with a clock it sets, creates hosts, accounts, users and reports with the store's own methods (`D04-store`), builds its set with `pages.Load()`, serves `identity.Optional(pages.Handler(cfg))` with a fixed banner and a `Now` it controls, sends raw requests with and without `X-User-Id`, and compares each body with what `set.Write` writes for the data the definitions below build. It creates more than 25 of each to page, hands `next` tokens back, compares a window with what the matching tool answers, walks Next to the end and Prev back to the 303, asks `last`, pages one list while the others' values are set, asks undecodable values, and turns `SetFailing(true)` on to see the 503.
