# D16-sandbox

Outcomes cited as outcome N are those of /home/mgreenly/Documents/ikigenba-ssh-hosts.md; log entries are those of /home/mgreenly/Documents/ikigenba-ssh-hosts-decisions.md.

A sandbox has no AWS account and no host, yet the sandbox walk must show everything a person sees on a space: a host created and going from `provisioning` to `running` and in sync, an account going from `pending` to `active`, users going from pending to applied, lock, unlock and delete, stop, start and resize, an operation resuming after accounts restarts in the middle of it, `/accountsd` downloading (outcome 4), an SSH ban listed, lifted by `unban_ip` and lifted by an allowlist entry (outcomes of /home/mgreenly/Documents/ikigenba-ssh-bans.md), and a person enrolling through an invite link, an admin flag set, a link reused and revoked (outcomes 1 to 15 of /home/mgreenly/Documents/ikigenba-self-service-accounts.md). Invites and enrollment need nothing of this document: they live in the store, the tools and the enrollment page (`D04-store`, `D07-tools`, `D18-enrollment`), which run in the sandbox exactly as on a space, and a user enrolled reaches its simulated host as desired state like one `add_user` adds. This document owns the two pieces that make that so: `internal/cloud/memory`, an in-memory `cloud.Cloud` (D05) that keeps its state in a file in accounts' data directory, and `internal/sim`, which runs one real daemon loop (D14) over a memory machine (D15) for every running instance of that cloud, talking to accounts' own handler in process.

How accounts picks them is D01's and D03's: with `IKIGENBA_SANDBOX` present and none of the five hosts variables set, `Settings.Cloud()` is `settings.ModeSandbox` (D01), accounts builds `memory.New` over `state/sandbox-cloud.json` in its working directory with `settings.SandboxHosts`, hands the result to the engine, the tools and the verifier as their `cloud.Cloud`, and starts `sim.Run` beside the engine, giving it `state/sandbox-bans` in the same directory as its bans file (D03). Nothing here names a space: the sandbox is chosen by the variable the sandbox sub-project sets for every app (sandbox D05), as accounts' in-memory host was before it.

## The memory cloud

The memory cloud answers like AWS where accounts can tell the difference, so the engine (D10) runs exactly the code it runs on a space.

**It persists.** Its whole state, every instance, volume, address, record, change, modification, client token and id counter, is one JSON file, loaded by `memory.New` and rewritten whole, to a temporary file in the same directory renamed over it, after every call that changed something. A missing file is an empty cloud; a file that cannot be read or decoded fails `New`, and accounts then serves unconfigured with its stderr line (D03). So when accounts restarts in the middle of an operation, the next `memory.New` finds what the interrupted attempt made, and the engine's lookups by tag and client tokens (D10) find it there exactly as they would in AWS. `sandbox wipe` removes the file with the app's directory.

**It takes observable time.** Every transition is computed from the time it began, which the file keeps, and the injected `Now`, so it survives a restart and a test drives it with a clock instead of waiting. An instance is `pending` for `BootDelay` (20 s), `stopping` for `StopDelay` (10 s), `shutting-down` for `TerminateDelay` (10 s); a volume is `creating` for `VolumeDelay` (5 s) and an attachment `attaching` for as long; a modification is `modifying` for `ModifyDelay` (10 s) and `optimizing` for as long again; a Route 53 change is `PENDING` for `ChangeDelay` (5 s). A host create therefore shows `provisioning` for about 40 seconds, long enough to restart accounts in the middle of it by hand, and a resize with a type change about a minute.

**It holds AWS's rules that the engine relies on.** Client tokens on `RunInstance` and `CreateVolume`: the same token with the same parameters answers the same resource, with different ones `IdempotentParameterMismatch`. Stopping a stopped instance and terminating a terminated one succeed. A volume only grows, one modification at a time, at most four in 24 hours. A Route 53 `CREATE` of a name that holds a record, or a `DELETE` that does not match the record exactly, is refused. Instance type changes need a stopped instance. Releasing an associated address is refused.

**It holds the infra contract.** The real account denies what the tag contract and the operator policy do not allow (step 2 of the log); the memory cloud refuses the same calls with the code D05's adapter gives before sending (`cloud.CodeTagContract`, class `ClassRefused`), and a launch from another template or profile with `UnauthorizedOperation`, the code EC2 gives for a denied action, so a mistake in the engine shows in the sandbox and in tests rather than first on a space: a launch from another template or profile, an instance type outside `t4g`, `m7g`, `c7g` and `r7g`, a launch without `Kind=host`, a volume without `Kind=host-data`, an address without `Kind=host`, any `Space` tag, and any later tag of `Kind`, `Space` or `Domain`. Route 53 changes below the hosts domain only, and of type A only, which `cloud.RecordChange` cannot express otherwise.

**It signs like STS, without secrets that matter.** `Presigner(instanceID)` gives the simulated daemon of that instance a presigner whose URLs have exactly the shape D12's verifier checks: the host `sts.<region>.amazonaws.com` for the sandbox region, so `sts.sandbox.amazonaws.com`, the action, version, algorithm, signed headers `host;x-ikigenba-accounts`, the expiry and the date, and a signature that is an HMAC over the instance, the date, the expiry and the binding under a key the cloud drew once. `CallerOf`, which the verifier calls, accepts exactly those URLs, unexpired, sent with the same binding, for an instance that is not terminated, and answers the ARN `arn:aws:sts::000000000000:assumed-role/<instance profile>/<instance id>` that a host's role would give. Like SigV4, the same instance, second, expiry and binding give the same URL, so the verifier's replay set behaves in the sandbox as on a space. Addresses come from `192.0.2.0/24` (TEST-NET-1, RFC 5737), so nothing in the sandbox points at a real machine.

## The simulated hosts

`sim.Run` looks at the memory cloud every `WatchInterval` (2 s). For every instance tagged `Kind=host` that is `running` and has no loop it starts `daemon.Run` (D14) with a memory machine (D15) that takes `ApplyDelay` (3 s) per apply, the cloud's presigner and metadata for that instance, the digest accounts serves, so no simulated daemon ever updates itself, a stderr that discards, so nothing a simulated daemon says reaches accounts' own stderr (D03), and an HTTP client whose transport hands each request to accounts' own handler in process with the binding as its host. A loop whose instance is no longer running is cancelled, and is started afresh when it runs again. So the real protocol runs end to end in the sandbox: identity through the verifier and the memory cloud's `CallerOf`, the long poll, `store.Watch`, the apply, the report and its health. A user added shows pending until the waiting poll wakes and the machine has slept its `ApplyDelay`, then applied. A machine's state lives only in memory: after accounts restarts, the new loop's machine starts empty and its first cycle applies the whole desired state, which is what a real daemon does after a reboot.

## The bans file

A memory machine has no sshd and no fail2ban, so nothing on it ever fails to sign in; a ban is put there by hand. A person at the sandbox writes lines to `state/sandbox-bans` in accounts' data directory; on this machine that is `~/.local/state/ikigenba/sandbox/<name>/apps/accounts/state/sandbox-bans`, `<name>` from `sandbox ls`. Each line is a host name and an address separated by spaces or TABs:

```
echo 'host01 192.0.2.77' >> ~/.local/state/ikigenba/sandbox/<name>/apps/accounts/state/sandbox-bans
```

At its next look, within `WatchInterval` (2 s), `sim.Run` reads the file, removes it, and for each line calls `Ban` (D15) on the memory machine of the running loop of the instance tagged `Host=<host>`. The machine then holds a ban of that address for `machine.MemoryBanTime` (10 minutes), unless an entry of the allowlist it last applied covers the address, in which case it bans nothing. The ban shows in the host's next report, on the host page and in the `host` tool's `report`: the daemon reports after each cycle, and a cycle ends when the long poll answers, at once after any change to that host's desired state and otherwise after at most `protocol.LongPoll` (45 s), then `ApplyDelay` (3 s). So a ban appears within about 50 seconds of writing the line, sooner when anything about the host changes.

A line that is not exactly two fields, whose address `valid.Address` (D17) refuses, or that names a host with no running loop (stopped, provisioning, unknown) is ignored, and the file is removed all the same: the line is consumed, not retried. Writing the line with one `echo`, or writing another file and `mv`ing it into place, keeps a look from reading half a line. The file is read through a cap of `MaxBanFileBytes` (64 KiB), one line at a time; bytes past the cap and a line the cap cuts are dropped. accounts never creates the file, so an untouched sandbox's `state/` holds only the database and `sandbox-cloud.json` (D01).

## The walk, observable by observable

| Observable | How the sandbox shows it |
| --- | --- |
| Create a host | `create_host` → `provisioning` while the address, launch (20 s boot), volume (5 s), attach (5 s) and association run → `running`; health `none` until the simulated daemon's first report, then `sync`. |
| Create an account | `create_account` → `pending` while the A record's change is `PENDING` (5 s) and until the host applies the version that added it → `active`. |
| Add users | `add_user` → `pending: true` → applied after one poll wake and `ApplyDelay`. |
| Lock, unlock, delete | the state changes, the machine applies it; `delete_user` shows `removing` until the report applies it, then the row is gone. |
| Stop, start | `stopping` (10 s) → `stopped`, its loop cancelled and health keeping the last report's word; `starting` (20 s boot) → `running`, a new loop, back to `sync`. |
| Resize | `resizing` through the modification (10 s + 10 s) and, for a type change, a stop and start. |
| Restart accounts mid-operation | `systemctl --user restart sandbox-<name>-accounts` during `provisioning` or `resizing`: the file keeps what was made, the engine resumes the recorded step, lookups by tag find the resources, nothing is duplicated. |
| A ban listed | write `host01 192.0.2.77` as a line to the bans file; within 2 s the file is gone, and the host's next report (at once after any change to `host01`, otherwise within `protocol.LongPoll` plus `ApplyDelay`) lists `192.0.2.77` with its banned and expires times and a total of 1; it expires after 10 minutes. |
| Lifted by `unban_ip` | `unban_ip` `192.0.2.77`, naming `host01` or no host → the host's applied version trails its version → applied after one poll wake and `ApplyDelay`, and the report no longer lists the ban. |
| Lifted by an allowlist entry | with `192.0.2.77` banned again, `allow_ip` `host01` `192.0.2.0/24` → applied: the ban is gone from the report and the report's allowlist shows the entry; a later line `host01 192.0.2.78` bans nothing. |
| Allowlist entry removed | `disallow_ip` `host01` `192.0.2.0/24` → applied: the report's allowlist no longer shows it, and a later line `host01 192.0.2.78` is then listed. |
| Invite and enroll | `create_invite` `acme` → a `link` under the sandbox's accounts URL (the services file's `accounts` entry, `http://accounts.<sandbox>.localhost:<port>`); `curl` of it with no bearer token, no credential at all, shows the form; a form `POST` of a free name and a fresh key → the user created, then pending → applied after one poll wake and `ApplyDelay`, like `add_user`; the link then answers the unusable page. |
| Reuse and revoke | a name already held, submitted through a second invite, gets the one name answer and the invite stays usable; `revoke_invite` of it → its link answers the same unusable page as a used one. |
| Admin | an invite made with `admin` true enrolls an admin; `set_admin` clears and sets the flag, which the landing's users list shows at once and no host ever receives. |
| Rate limit | every `POST` from the developer's machine comes from one address (nginx's `X-Real-IP`), so a burst of them ends in 429, and one more is allowed every 6 s. |
| Download the daemon | `curl <accounts>/accountsd` returns `<data>/bin/accountsd`, which the sandbox builds beside `bin/accounts` (D09, log D11). |

Silence is not part of the walk: a running simulated host always reports. It is proved by unit tests with an injected clock (D04, D10).

## Recorded decisions

- **A persisted in-memory cloud**. devctl and opsctl test their cloud seams with per-test recording stubs and run nothing in memory; accounts' own sandbox ran an in-memory host, empty at each start. A cloud empty at each start would make the restart observable meaningless, so this one keeps a file in accounts' data directory, under `state/` beside the database (D01).
- **Written whole.** The file is rewritten whole after each change, which a production store would not do; it is sandbox-only and small by construction (a handful of instances, volumes, addresses and records, each a few hundred bytes), so the bound is the sandbox's own scale, recorded here as its memory bound.
- **Transitions from timestamps, not timers**, so they survive a restart and need no goroutine.
- **The real daemon loop, a memory machine.** The sim runs `daemon.Run` itself rather than a stand-in, so the sandbox exercises the protocol, identity and versioning the hosts will run; only the machine and the cloud are fakes.
- **Contract denials mirror the adapter.** Whatever D05's `awssdk` refuses before sending is `cloud.CodeTagContract` here too, so tests over the memory cloud see the same error as over the adapter; a wrong template or profile, which only IAM would deny, is `UnauthorizedOperation`. Both are `ClassRefused` (D05), so the engine fails the operation as it would on a space.
- **Bans come from a file the person writes, which is new.** No earlier sim mechanism injected host facts: a memory machine's facts are constants (D15), and `SetFailure` is a test's seam, not reachable in a running sandbox. The nearest in spirit is the memory cloud's file under `state/`: sandbox-only state in accounts' data directory that `sandbox wipe` removes. A tool or route that bans would put a sandbox-only surface into accounts' API and its tests; a file needs neither and is written with `echo`. The file is consumed (read, then removed) so each line is one ban event: a line left in place would ban the address again at every look, after `unban_ip` or expiry. accounts never creates it, so D01's account of what `state/` holds (R-Y9CP-KR8R) stays true.
- **The bans file is read with fixed memory**: through a cap of `MaxBanFileBytes`, one line at a time, so a look holds at most that many bytes of it at once whatever was written; each `Ban` adds at most one ban to a machine that holds at most `protocol.MaxBans` (D15).
- **Self-update is not simulated**: the sim hands each daemon accounts' served digest. Self-update is proved by D14's tests.

## Consumer usage

accounts in sandbox mode (D03): `c, err := memory.New(memory.Config{Path: filepath.Join(dir, "state", "sandbox-cloud.json"), Now: p.Now, Rand: p.Rand, Hosts: settings.SandboxHosts})`; the engine, the tools and the verifier take `c` as their `cloud.Cloud`; `s := sim.New(sim.Config{Cloud: c, Handler: handler, Binding: binding, Digest: daemonServer.Digest, Now: p.Now, Sleep: sleep, After: p.After, BanFile: filepath.Join(dir, "state", "sandbox-bans")})` and `go s.Run(ctx)`. A test of the bans file writes `host01 192.0.2.77\n` to a path in its temporary directory named as `BanFile`, fires the look's `After`, and reads the machine's `State().Bans` or, over accounts' handler, the host's report. A test of the engine opens `memory.New` over a path in its temporary directory with a clock it advances past `memory.BootDelay` instead of waiting; a resume test closes it, opens a second `memory.New` over the same path, and checks the engine finds the first one's instance by its `Operation` tag. A test of the verifier presigns with `c.Presigner(id)` and verifies through `c`'s `CallerOf`.
