# D16-sandbox

Outcomes cited as outcome N are those of /home/mgreenly/Documents/ikigenba-ssh-hosts.md; log entries are those of /home/mgreenly/Documents/ikigenba-ssh-hosts-decisions.md.

A sandbox has no AWS account and no host, yet the sandbox walk must show everything a person sees on a space: a host created and going from `provisioning` to `running` and in sync, an account going from `pending` to `active`, users going from pending to applied, lock, unlock and delete, stop, start and resize, an operation resuming after accounts restarts in the middle of it, `/accountsd` downloading (outcome 4), an SSH ban listed, lifted by `unban_ip` and lifted by an allowlist entry (outcomes of /home/mgreenly/Documents/ikigenba-ssh-bans.md), a person enrolling through an invite link, an admin flag set, a link reused and revoked (outcomes 1 to 15 of /home/mgreenly/Documents/ikigenba-self-service-accounts.md), and a person on a host managing their keys and, as an admin, their account's users through the host's own MCP server (that document's outcomes 16 to 27, cited below as box outcome N), and a host with a DNS name of its own that it calls itself by (the outcomes of /home/mgreenly/Documents/ikigenba-host-names.md, cited below as the names outcomes), and a new host taking the lowest free number, a delete that takes the data volume with it, and a kept data volume listed and deleted (the outcomes of /home/mgreenly/Documents/ikigenba-host-numbers-and-delete.md, cited below as numbers outcome N). Invites and enrollment need nothing of this document: they live in the store, the tools and the enrollment page (`D04-store`, `D07-tools`, `D18-enrollment`), which run in the sandbox exactly as on a space, and a user enrolled reaches its simulated host as desired state like one `add_user` adds. This document owns the two pieces that make that so: `internal/cloud/memory`, an in-memory `cloud.Cloud` (D05) that keeps its state in a file in accounts' data directory, and `internal/sim`, which runs one real daemon loop (D14) over a memory machine (D15) for every running instance of that cloud, talking to accounts' own handler in process, and serves each simulated host's box socket (D14) as one Unix socket per simulated user, so the sandbox's own `accountsd`, run as `accountsd-mcp` (D20), drives the box path end to end.

How accounts picks them is D01's and D03's: with `IKIGENBA_SANDBOX` present and none of the five hosts variables set, `Settings.Cloud()` is `settings.ModeSandbox` (D01), accounts builds `memory.New` over `state/sandbox-cloud.json` in its working directory with `settings.SandboxHosts`, hands the result to the engine, the tools and the verifier as their `cloud.Cloud`, and starts `sim.Run` beside the engine, giving it `state/sandbox-bans` in the same directory as its bans file (D03). Nothing here names a space: the sandbox is chosen by the variable the sandbox sub-project sets for every app (sandbox D05), as accounts' in-memory host was before it.

## The memory cloud

The memory cloud answers like AWS where accounts can tell the difference, so the engine (D10) runs exactly the code it runs on a space.

**It persists.** Its whole state, every instance, volume, address, record, change, modification, client token and id counter, is one JSON file, loaded by `memory.New` and rewritten whole, to a temporary file in the same directory renamed over it, after every call that changed something. A missing file is an empty cloud; a file that cannot be read or decoded fails `New`, and accounts then serves unconfigured with its stderr line (D03). So when accounts restarts in the middle of an operation, the next `memory.New` finds what the interrupted attempt made, and the engine's lookups by tag and client tokens (D10) find it there exactly as they would in AWS. `sandbox wipe` removes the file with the app's directory.

**It takes observable time.** Every transition is computed from the time it began, which the file keeps, and the injected `Now`, so it survives a restart and a test drives it with a clock instead of waiting. An instance is `pending` for `BootDelay` (20 s), `stopping` for `StopDelay` (10 s), `shutting-down` for `TerminateDelay` (10 s); a volume is `creating` for `VolumeDelay` (5 s), an attachment `attaching` for as long, and a deleted volume `deleting` for as long again before it is gone; a modification is `modifying` for `ModifyDelay` (10 s) and `optimizing` for as long again; a Route 53 change is `PENDING` for `ChangeDelay` (5 s). A host create, which now waits for its own record's change before it launches (D10), therefore shows `provisioning` for about 45 seconds, long enough to restart accounts in the middle of it by hand, and a resize with a type change about a minute.

**It holds AWS's rules that the engine relies on.** Client tokens on `RunInstance` and `CreateVolume`: the same token with the same parameters answers the same resource, with different ones `IdempotentParameterMismatch`. Stopping a stopped instance and terminating a terminated one succeed. A volume only grows, one modification at a time, at most four in 24 hours. A Route 53 `CREATE` of a name that holds a record, or a `DELETE` that does not match the record exactly, is refused. Instance type changes need a stopped instance. Releasing an associated address is refused. Deleting a volume follows AWS's `DeleteVolume` (D05 cites the proof): a volume it does not hold, one deleted earlier included, is `InvalidVolume.NotFound`, which the engine counts as done; an attached one is refused with `VolumeInUse`; an `available` one goes `deleting` and is then gone from every describe and find, as a volume AWS deleted is. A volume still `creating` answers `IncorrectState`, transient, so a delete that reaches it tries again once it is available; AWS's code for that case is unproven (D05), and the engine copes with either class. A second `DeleteVolume` of a volume already `deleting` succeeds and changes nothing, so a step repeated after a restart is harmless.

**It holds the infra contract.** The real account denies what the tag contract and the operator policy do not allow (step 2 of the log); the memory cloud refuses the same calls with the code D05's adapter gives before sending (`cloud.CodeTagContract`, class `ClassRefused`), and a launch from another template or profile with `UnauthorizedOperation`, the code EC2 gives for a denied action, so a mistake in the engine shows in the sandbox and in tests rather than first on a space: a launch from another template or profile, an instance type outside `t4g`, `m7g`, `c7g` and `r7g`, a launch without `Kind=host`, a volume without `Kind=host-data`, an address without `Kind=host`, any `Space` tag, and any later tag of `Kind`, `Space` or `Domain`. The operator policy allows `ec2:DeleteVolume` only on a volume tagged `Kind=host-data` (D05; infra commit e69e0506), so the memory cloud refuses a delete of any other volume, a root volume among them, with `UnauthorizedOperation`, as AWS would. Route 53 changes below the hosts domain only, and of type A only, which `cloud.RecordChange` cannot express otherwise. That rule already admits both kinds of record accounts writes, an account's at `<account>.<domain>` and a host's own at `<host>.<domain>` (D05, D10), and tells them apart no more than Route 53 does, so the host names need no change to the memory cloud: in the sandbox, whose hosts domain is `settings.SandboxHosts.Domain`, `hosts.test` (D01), a create of `host01` leaves an A record at `host01.hosts.test` valued with the host's address.

**It signs like STS, without secrets that matter.** `Presigner(instanceID)` gives the simulated daemon of that instance a presigner whose URLs have exactly the shape D12's verifier checks: the host `sts.<region>.amazonaws.com` for the sandbox region, so `sts.sandbox.amazonaws.com`, the action, version, algorithm, signed headers `host;x-ikigenba-accounts`, the expiry and the date, and a signature that is an HMAC over the instance, the date, the expiry and the binding under a key the cloud drew once. `CallerOf`, which the verifier calls, accepts exactly those URLs, unexpired, sent with the same binding, for an instance that is not terminated, and answers the ARN `arn:aws:sts::000000000000:assumed-role/<instance profile>/<instance id>` that a host's role would give. Like SigV4, the same instance, second, expiry and binding give the same URL, so the verifier's replay set behaves in the sandbox as on a space. Addresses come from `192.0.2.0/24` (TEST-NET-1, RFC 5737), so nothing in the sandbox points at a real machine.

## The simulated hosts

`sim.Run` looks at the memory cloud every `WatchInterval` (2 s). For every instance tagged `Kind=host` that is `running` and has no loop it starts `daemon.Run` (D14) with a memory machine (D15) that takes `ApplyDelay` (3 s) per apply, the cloud's presigner and metadata for that instance, the digest accounts serves, so no simulated daemon ever updates itself, a stderr that discards, so nothing a simulated daemon says reaches accounts' own stderr (D03), and an HTTP client whose transport hands each request to accounts' own handler in process with the binding as its host. A loop whose instance is no longer running is cancelled, and is started afresh when it runs again. So the real protocol runs end to end in the sandbox: identity through the verifier and the memory cloud's `CallerOf`, the long poll, `store.Watch`, the apply, the report and its health. A user added shows pending until the waiting poll wakes and the machine has slept its `ApplyDelay`, then applied. A machine's state lives only in memory: after accounts restarts, the new loop's machine starts empty and its first cycle applies the whole desired state, which is what a real daemon does after a reboot.

**The host's name.** The sim gives a memory machine no domain of its own: the domain reaches it as a real host's does, in the desired state the daemon fetches, whose `Domain` accounts sets from the hosts domain it serves with (D13, D03), `hosts.test` in sandbox mode. The memory machine, asked to take `<host>.<domain>`, holds that name and reports it as the report's `hostname` (D15). So a simulated host's first report in sync already names it `host01.hosts.test`, the `host` tool shows that `hostname` in its `report` beside its own `dns_name`, and the host page shows both. After accounts restarts, the new loop's machine starts with no name and takes it again at its first apply, as it does the rest of the desired state.

## The bans file

A memory machine has no sshd and no fail2ban, so nothing on it ever fails to sign in; a ban is put there by hand. A person at the sandbox writes lines to `state/sandbox-bans` in accounts' data directory; on this machine that is `~/.local/state/ikigenba/sandbox/<name>/apps/accounts/state/sandbox-bans`, `<name>` from `sandbox ls`. Each line is a host name and an address separated by spaces or TABs:

```
echo 'host01 192.0.2.77' >> ~/.local/state/ikigenba/sandbox/<name>/apps/accounts/state/sandbox-bans
```

At its next look, within `WatchInterval` (2 s), `sim.Run` reads the file, removes it, and for each line calls `Ban` (D15) on the memory machine of the running loop of the instance tagged `Host=<host>`. The machine then holds a ban of that address for `machine.MemoryBanTime` (10 minutes), unless an entry of the allowlist it last applied covers the address, in which case it bans nothing. The ban shows in the host's next report, on the host page and in the `host` tool's `report`: the daemon reports after each cycle, and a cycle ends when the long poll answers, at once after any change to that host's desired state and otherwise after at most `protocol.LongPoll` (45 s), then `ApplyDelay` (3 s). So a ban appears within about 50 seconds of writing the line, sooner when anything about the host changes.

A line that is not exactly two fields, whose address `valid.Address` (D17) refuses, or that names a host with no running loop (stopped, provisioning, unknown) is ignored, and the file is removed all the same: the line is consumed, not retried. Writing the line with one `echo`, or writing another file and `mv`ing it into place, keeps a look from reading half a line. The file is read through a cap of `MaxBanFileBytes` (64 KiB), one line at a time; bytes past the cap and a line the cap cuts are dropped. accounts never creates the file, so an untouched sandbox's `state/` holds only the database and `sandbox-cloud.json` (D01).

## The box sockets

On a host, a person signed in over SSH starts `claude`, which starts `accountsd-mcp`, which connects to `/run/accountsd.sock`; the daemon learns the person's uid from the kernel (D14). In the sandbox there is no SSH and every process is the developer's, so the kernel would name the developer's uid, which no simulated user has. The sim therefore chooses the uid, and does it by where the client connects: it serves one Unix socket per simulated user, named by the user, and every connection on a user's socket is that user's. The production listener has no such choice: `daemon.Main` always serves `boxmcp.SocketPath` with `KernelUID` (D14, R-KIF7-H70Z); the sim never calls `Main` and hands `daemon.Run` its own `Box` and `PeerUID`.

**Which sockets.** A *box user* of a look is a user that the memory machine of an instance with a running loop holds and has not locked (`State().Users` with `Locked` false, D15): a person who could be signed in on that host. Its *socket path* is `<box dir>/<user name>`, the box dir being `Config.BoxDir` made absolute. User names are unique across every host (D17), so the name alone is the key, and a user name is never `sockets.txt` or a name beginning with `.` (D17's `^[a-z_][a-z0-9_-]*$`), so the sim's own files cannot collide with a socket. At each look, after the loops and the bans file, the sim listens at the socket path of every new box user and closes the socket of every user who is no longer one: deleted or locked once the host has applied it (a lock ends sessions, box outcome 24), or on a host whose loop was cancelled because the instance stopped. So a user's socket appears within `WatchInterval` of the host applying the user and disappears within `WatchInterval` of the host applying a lock or a delete. A user of a pending account is served too; the daemon and accounts judge them as they would on a host. The uid each socket stands for is the `UID` the machine holds for that user, which is the uid of the desired state the daemon fetched (D11), so the daemon's local judgement (D14, R-PT7L-W7VD) and accounts' resolution of host and uid to a user (D13) see that user.

**One listener per host.** All the sockets of one host are merged into the one `net.Listener` that host's loop is given as `Config.Box`; its `Accept` returns the next connection on any of them, and the loop's `PeerUID` answers the uid of the socket the connection came in on. The sim accepts on a socket only when the loop is ready to take the connection, so it holds at most one accepted connection per socket that the daemon has not yet taken; everything else waits in the kernel's backlog. When a socket closes (the user locked or deleted, the instance stopped) or the loop closes its `Box`, a connection the sim accepted and the daemon never took is closed unanswered, so the client's stdio server answers that the daemon is not answering, and nothing of that socket keeps running. Two box users with one name in one look (a name freed and reused while the old host has not yet applied the removal) get no socket until only one remains; both are listed `failed`. The daemon's own bound (D14: `MaxBoxConns` open connections, the next refused at once) is therefore the bound per simulated host, as on a real one; the sim adds one listener and at most one waiting connection per socket, and there is one socket per box user, at most `valid.MaxUsersPerHost` (D17) per host.

**Where they are.** D03 names the box dir `state/box` in accounts' data directory, beside the bans file, so `sandbox wipe` removes it and a person finds it with the sandbox's other state: on this machine `~/.local/state/ikigenba/sandbox/<name>/apps/accounts/state/box/<user>`. The sim makes the directory, mode 0700 (only the developer's processes can reach a simulated user's socket), when it first has a user to list, and removes it again, when empty, once it has none and when `Run` returns; so a sandbox whose hosts hold no user has no such directory, and D01's account of `state/` after `create_host` (R-Y9CP-KR8R) stays true. A socket left by an accounts process that crashed is a socket file nothing listens on: at each look the sim removes every socket in the box dir it is not listening on, before it listens, because `bind` fails with `EADDRINUSE` when "the filesystem socket object already exists" (unix(7)). It touches nothing else there. On a clean stop Go's listener removes its own file (`UnixListener.SetUnlinkOnClose`, as D14 cites).

**The listing.** A person learns the paths from `sockets.txt` in the box dir, rewritten at each look: one line per box user, sorted by name, holding the name, the host, the uid, a status and the socket path, separated by TABs. The status is `served`, `too-long` or `failed`. It is written to a dot-file and renamed into place, so a reader never sees half of it.

**The 108-byte limit.** A pathname socket's `sun_path` is a 108-byte array that holds the path and its terminating null byte (unix(7), Address format), so a socket path is at most `MaxSocketPath` (107) bytes. The box dir on a developer's machine is about 75 bytes for a short sandbox name and a user name is up to 32 bytes (D17), so a long sandbox name or home directory can push a path over. Such a user is not served, nothing is created at their path, and the listing says `too-long` beside the path, so the failure is visible exactly where the person looks for the socket. A listen that fails for any other reason (something not a socket at the path, say) is listed `failed` and tried again at the next look. Nothing is written to stderr: accounts' standard error carries only the lines D03 lists (R-H30N-ZNGY), and the simulated daemons' diagnostics are discarded.

## Recorded decisions

- **A persisted in-memory cloud**. devctl and opsctl test their cloud seams with per-test recording stubs and run nothing in memory; accounts' own sandbox ran an in-memory host, empty at each start. A cloud empty at each start would make the restart observable meaningless, so this one keeps a file in accounts' data directory, under `state/` beside the database (D01).
- **Written whole.** The file is rewritten whole after each change, which a production store would not do; it is sandbox-only and small by construction (a handful of instances, volumes, addresses and records, each a few hundred bytes), so the bound is the sandbox's own scale, recorded here as its memory bound.
- **Transitions from timestamps, not timers**, so they survive a restart and need no goroutine.
- **The real daemon loop, a memory machine.** The sim runs `daemon.Run` itself rather than a stand-in, so the sandbox exercises the protocol, identity and versioning the hosts will run; only the machine and the cloud are fakes.
- **Contract denials mirror the adapter.** Whatever D05's `awssdk` refuses before sending is `cloud.CodeTagContract` here too, so tests over the memory cloud see the same error as over the adapter; a wrong template or profile, which only IAM would deny, is `UnauthorizedOperation`. Both are `ClassRefused` (D05), so the engine fails the operation as it would on a space.
- **Bans come from a file the person writes, which is new.** No earlier sim mechanism injected host facts: a memory machine's facts are constants (D15), and `SetFailure` is a test's seam, not reachable in a running sandbox. The nearest in spirit is the memory cloud's file under `state/`: sandbox-only state in accounts' data directory that `sandbox wipe` removes. A tool or route that bans would put a sandbox-only surface into accounts' API and its tests; a file needs neither and is written with `echo`. The file is consumed (read, then removed) so each line is one ban event: a line left in place would ban the address again at every look, after `unban_ip` or expiry. accounts never creates it, so D01's account of what `state/` holds (R-Y9CP-KR8R) stays true.
- **The bans file is read with fixed memory**: through a cap of `MaxBanFileBytes`, one line at a time, so a look holds at most that many bytes of it at once whatever was written; each `Ban` adds at most one ban to a machine that holds at most `protocol.MaxBans` (D15).
- **The memory cloud deletes volumes** (numbers outcomes 8, 10 and 15), as D05's seam now does. A deleted volume is `deleting` for `VolumeDelay`, the volume transition the cloud already uses, so no constant is added and the engine's wait for a deleted volume is observable in a test and in the walk; then it is gone, answering `InvalidVolume.NotFound` like any id the cloud does not hold, `TagResource` included, though there as for any id a tag with a forbidden key is refused first, as the adapter refuses before sending, so a repeated delete and a kept volume removed by hand both look as they would in AWS. The `UnauthorizedOperation` refusal of a volume not tagged `Kind=host-data` mirrors the operator policy's condition, as the launch refusals mirror its template and profile conditions. The change is persisted like every other (R-GV9R-543N), so a delete interrupted by a restart finds the volume `deleting` or gone. A deleted volume holds at most what it held before, so the sandbox scale the whole-file rewrite is bounded by is unchanged. A full teardown with `keep_data` false is proved end to end by R-L5PS-7HX9, a `Run`-level sandbox test in the manner of R-VN5D-PUG1.
- **Self-update is not simulated**: the sim hands each daemon accounts' served digest. Self-update is proved by D14's tests.
- **The host names change neither the memory cloud nor the sim** (names outcomes). The memory cloud's record rule (R-H05C-O72F) already allows any A record below the hosts domain, and a host's own record is one; its file grows by one small record per host, within the sandbox scale the whole-file rewrite is bounded by. The sim adds no domain setting: `sim.Config` and the memory machine's `MemoryConfig` are unchanged, because the domain travels in the desired state (`DesiredState.Domain`, D11) the daemon fetches from accounts, so the simulated host takes its name by the same path a real one does, and a sandbox whose accounts gave no domain would leave the name alone exactly as a host would. Nothing is added that holds memory; what is new is proved end to end by R-VN5D-PUG1, a `Run`-level sandbox test in the manner of the bans file's (D03).
- **The sim chooses the uid by socket, one socket per user** (sheet decision 11). A single socket with a per-connection choice would need the client to say who it is, which is the forgery the kernel's uid exists to prevent, and would put a sandbox-only input on the wire D20 shares with production. A socket per user keeps the wire and the stdio server exactly production's; only `ACCOUNTSD_SOCKET`, which D20 already has, picks the user. The production `Main` has no way to choose a uid (D14).
- **Named by user, not by host and user.** Names are unique across hosts (D17), and a shorter path leaves more room under the 108-byte limit. A root socket (uid 0) per host was considered and left out: the daemon's refusal of root is proved by D14's tests, and a socket per host would need a host level in the path.
- **Box users come from the machine, not from accounts' store.** The sockets follow what the simulated host has applied, as a real host's sign-ins follow its `/etc/passwd`: a user appears after the apply, and a lock or delete ends the user's socket once applied, which is what ending their sessions looks like here. Locked users get no socket because a locked user cannot sign in.
- **A listing file, not stderr, for paths and failures.** accounts' standard error is closed to the sim (D03, R-H30N-ZNGY), and the person needs the path anyway; the file is where they look, so a path over the limit is reported there. The `sandbox` command is another sub-project and is not changed by this design; a `sandbox` subcommand that prints the box dir is a follow-up for it.
- **Box dir created lazily and removed when empty**, so `state/` keeps D01's shape until a host holds a user, and a `sandbox wipe` or a stop leaves nothing behind.
- **Bounded.** Per look the sim holds the set of box users (one entry per user each running host holds, at most `valid.MaxUsersPerHost` per host), one listener per box user, at most one accepted connection per socket not yet taken by the daemon, and the listing it writes line by line; the daemon's `MaxBoxConns` bounds the connections each simulated host serves, as on a host (R-2H5X-FS6I); what one look holds is R-P4EZ-66LH.
- **No process-starting test.** The sim's sockets are proved in process: a test names a short temporary directory (`os.MkdirTemp("", ...)`, since `t.TempDir()` can exceed the 108-byte limit) as `BoxDir`, dials a user's socket and writes a line, or runs `boxmcp.Run` against it with a `getenv` naming it. That the sandbox's `accountsd` binary is the stdio server under the name `accountsd-mcp` is D14's exec'ing test (R-KKV0-8QID).

## Consumer usage

Accounts in sandbox mode, as D03 passes it: `c, err := memory.New(memory.Config{Path: filepath.Join(dir, "state", "sandbox-cloud.json"), Now: p.Now, Rand: p.Rand, Hosts: settings.SandboxHosts})`; the engine, the tools and the verifier take `c` as their `cloud.Cloud`; `s := sim.New(sim.Config{Cloud: c, Handler: handler, Binding: binding, Digest: daemonServer.Digest, Now: p.Now, Sleep: sleep, After: p.After, BanFile: filepath.Join(dir, "state", "sandbox-bans"), BoxDir: filepath.Join(dir, "state", "box")})` and `go s.Run(ctx)`. Each loop the sim starts is `daemon.Run(ctx, daemon.Config{..., Box: hostListener, PeerUID: hostListener's uid of a connection, After: cfg.After})`, `hostListener` merging the sockets `<BoxDir>/<user>` of that host's box users.

A person in the sandbox:

```
box=~/.local/state/ikigenba/sandbox/<name>/apps/accounts/state/box
cat "$box/sockets.txt"                 # alice  host01  2001  served  /home/.../state/box/alice
ln -s ~/.local/state/ikigenba/sandbox/<name>/bin/accountsd /tmp/b/accountsd-mcp
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25"}}' \
              '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' |
  ACCOUNTSD_SOCKET="$box/alice" /tmp/b/accountsd-mcp
```
