# D10-operations

The operations engine: `internal/ops`, which carries every long AWS-side change to its end. A tool records an operation through the store and answers at once (`D07-tools`); the engine, running beside the server for as long as accounts serves (`D03-serve`), advances each running operation one step at a time against the cloud (`D05-cloud`), recording each step before the call that makes it and what the call learned after it (`D04-store`). An interrupted operation resumes where it stopped, against what AWS already holds, whenever accounts starts again (outcome 11 of ikigenba-ssh-hosts.md). Beside the operations the engine runs two sweeps: the silence sweep, which tells `host.silent` for a running host that stopped reporting (outcome 24), and the stray scan, which reports once each resource tagged as a host's that no record explains (outcome 11). This document declares the engine's surface, its constants and step names, the state machine of each operation kind, the rules every step follows, and the events it tells (`D08-trail`).

## The loop

`Run` makes a pass at once, treating every running operation as due whatever its next try says, and runs the stray scan; then it waits, for `Wake`, for the earliest deferred step to come due (never sooner than `PollInterval`), or for `ReconcileInterval`, whichever comes first, and passes again, until its context is done. A pass reads running operations that are due, in pages of `store.BatchSize`, and moves each by at most one step; then it runs the silence sweep; then, when `ScanInterval` has passed since the last scan, the stray scan. `Pass` and `Scan` are exported so a test drives the engine one pass at a time with an injected clock and never waits.

## Every step

Every step is recorded before its AWS call: the store holds the operation at that step and generation before the request is sent, so a crash between the call and recording its result re-runs the step, and every step begins with a lookup that makes a repeat harmless. The client token of `RunInstances` and `CreateVolume` is `<operation id>-<step>-<generation>`: a repeat of the same step and generation sends the same token, and AWS answers the same resource. Every resource is tagged in the call that creates it with its kind, its host and its operation (`Kind`, `Host`, `Operation`), the instance also with accounts' URL (`AccountsURL`), the data volume `Kind=host-data`; later only `Orphaned=true` on a deleted host's data volume. Lookups go by the operation's tag and the kind, never by host name alone: a database reset must never adopt an old host's resources, which then show as strays. When a lookup finds more than one live resource of a kind under the operation's tag (only a lost `AllocateAddress` retry can make two), the one with the lowest id is adopted and the others are left to the stray scan and to `delete`.

An error's class decides: a transient error defers the step with a backoff doubling from `PollInterval` up to `MaxBackoff`; a refused error or a token mismatch fails the operation with the error's text as its reason; not found means what each step says. A step not done within `StepTimeout` of its start fails with `ReasonTimedOut`, except the waits on the host (`wait_address`, `wait_applied`), a volume wait while AWS reports the modification still `modifying`, and a grow step while it is deferred. An unexpected not found fails the operation with `ReasonMissing`; an operation another writer ended (a cancelled `place`, an `unplace` a delete closed) is dropped without an event. A wait that is not yet satisfied defers by `PollInterval`. Cancelling `Run`'s context cancels any call in flight; the operation keeps its recorded step and resumes at the next start.

## The machines

**`create`** (host `provisioning` → `running`): `address` (adopt the operation's address or allocate one) → `launch` (needs accounts' URL, else fails with `ReasonNoAccountsURL`; adopt the operation's live instance or launch one with the step's token) → `wait_running` (pending waits; running records the zone and root volume; shutting down or terminated starts a new generation back at `launch`, failing with `ReasonTerminated` beyond `MaxGenerations`) → `volume` (adopt the operation's data volume or create one in the instance's zone) → `wait_volume` → `attach` (at `DataDevice`) → `wait_attached` → `associate` → done.

**`stop`** (`stopping` → `stopped`): `stop` → `wait_stopped`. **`start`** (`starting` → `running`): `start` → `wait_running` (terminated fails with `ReasonTerminated`) → `associate`, which keeps the Elastic IP on the host (outcome 17).

**`resize`** (`resizing` → the state it started from): `grow_root` → `wait_root` when the root grows, then `grow_data` → `wait_data` when the data volume grows, then the type change: from `running`, `stop` → `wait_stopped` → `set_type` → `start` → `wait_running` → `associate`; from `stopped`, `set_type` alone. A grow step reads the volume and its latest modification first and skips the call when the volume already has the target size or a modification to it exists, defers while another modification is still in progress (EC2 allows one at a time), and otherwise notes the grow and then modifies. A wait step records the new size, which bumps the host's version so the daemon grows the filesystem online (`D15-machine`), once AWS reports `optimizing` or `completed`, where the new size takes effect. The four-grows-per-24-hours rule is checked by the store when the tool starts the resize; a `VolumeModificationRateExceeded` that still occurs is deferred by `MaxBackoff`, never a failure.

**`delete`** (`deleting` → `deleted`): `unrecord` (delete the A record of every `removing` account on the host that still points at its address) → `wait_unrecord` (every change in sync, and at least `RecordSettle` since it began) → `terminate` → `wait_terminated` → `release` → `orphan` (tag every data volume `Orphaned=true`; never delete it, log D8) → done. Each of `terminate`, `release` and `orphan` acts on the ids the host row holds and on every resource of its kind tagged with any of the host's operations, found page by page, so a host whose create failed half-way still leaves nothing behind. No address is released while a record of the host's accounts may still point at it. Finishing the delete finishes every `removing` account on the host with it (`D04-store`).

**`place`** (account `pending` → `active`): `wait_address` (the host has an Elastic IP) → `record` (a record at the account's name holding exactly the host's address is adopted and `wait_record` skipped; no record creates one; anything else, or a refused create, fails with `ReasonRecordConflict` and the account stays `pending`) → `wait_record` → `wait_applied` (the host applied the version that added the account) → done. A failed `place` is retried by `remove_account` and `create_account` again; there is no account retry tool.

**`unplace`** (`removing` → row gone): `unrecord` → `wait_unrecord` → `wait_applied` → done. `wait_applied` is skipped when the host never applied nor tried the version that added the account; otherwise it waits, with no timeout, until the host applied the removal. What bounds it is the host: a running host applies within a cycle, and the `delete` of a stopped, failed or silent host ends it.

## Sweeps

The silence sweep runs each pass: `store.MarkSilent` in pages, one `host.silent` for each host it marks. The stray scan lists, page by page, instances tagged `Kind=host`, volumes tagged `Kind=host` and `Kind=host-data`, and addresses tagged `Kind=host`; each whose id the store does not explain and whose `Operation` tag names no running operation is noted, and the first time it is noted `resource.unexplained` is told. Nothing is ever deleted or tagged by the scan. The scan also prunes expired volume grows with `store.PruneGrows`, in pages; that is retention only and changes nothing a caller sees.

## Events

The engine never tells `operation.started` (the tools do). It tells `operation.finished` when an operation finishes or fails, with the failure's reason; `host.changed` for every host state change it makes (to the end state on finish, to `failed` on failure); `account.changed` when a `place` makes its account active and when an `unplace` or a `delete` removes an account (`to` is `trail.AccountRemoved`). All of these are told under the operation's stored caller. `host.silent` and `resource.unexplained` carry no caller.

## Memory

A pass holds at most one page of `store.BatchSize` operations and, per operation, its host, its account and one cloud answer; the silence sweep holds one page of hosts. The scan folds each cloud page into the store before it returns from the page's callback, so it never holds a listing; `delete` walks the host's operations page by page in the same way. Nothing the engine holds grows with the number of hosts, accounts, operations or resources.

## Recorded decisions
- **Sizes cross the seam checked**: the store keeps sizes as `int`, the cloud seam takes `int32`; the engine refuses a size outside 1..`math.MaxInt32` with `ReasonBadSize` rather than convert blindly. `D17-names-keys-sizes`' bounds keep every real size far inside.
- **Grows are noted before `ModifyVolume`**, on the step's first attempt only, while the modification itself is sent at every attempt; a crash between noting and sending, or a transient failure later retried after a restart at attempt 0, can count one grow twice, accepted as the safe side: a crash between noting and sending counts a grow that never happened, which only makes the four-per-24-hours limit stricter; a grow sent and never counted could let a fifth through, which EBS would refuse for up to a day.
- **Grow steps never time out while deferred** (rate limit, or another modification still in progress): the plan makes a rate-exceeded modification transient, never a host failure, and EBS can hold a volume in `optimizing` for hours.
- **An unexpected not found fails with `ReasonMissing`**: a resource gone from under a step (an address released by hand, an instance gone) is not success; each step that expects not found says so.
- **The store ending an operation under the engine is not an error**: `RemoveAccount` cancels a running `place`, and finishing a `delete` closes the host's `unplace` operations; the engine drops such an operation for the pass and tells nothing for it, since the writer that ended it told its events.
- **`wait_unrecord` waits at least `RecordSettle`** (one minute, Route 53's documented propagation bound, facts.md §2) after it starts: a crash between a record's DELETE and recording its change id leaves no change to wait on, and the address must not be released while the record may still resolve.
- **A create failed with `ReasonTerminated` is deleted, not retried**: `retry_host` keeps the generation, so the retried launch gets the same terminated instance back and fails again; `delete_host` cleans it up. Resetting a generation budget on retry was rejected as a second counter for a rare case.
- **`delete` looks up only resources tagged by the host's `create` operations**, the only kind that creates any, so a delete's AWS calls do not grow with how often the host was stopped, started or resized.

- **Exported `Pass` and `Scan`**, so tests drive one pass under an injected clock. Siblings' workers are unexported loops behind `Run`; here the steps are the contract and a test must reach each one.
- **Departure: resume, not fail.** gdrive, gmail and scripts finish interrupted work `failed` or `interrupted` at start; outcome 11 requires resume, so the engine continues every running operation from its recorded step. A timer reconcile has no sibling precedent (gmail reconciles lazily, when a tool touches a draft).
- **Departure: client tokens plus lookup by operation tag**, where devctl looks up by tag only.
- **Timers**: `PollInterval` 5 s, `ReconcileInterval` 1 min, `ScanInterval` 1 h, `StepTimeout` 30 min (a launch settles in minutes; a large `ModifyVolume` reaches `optimizing`, where the size takes effect, in seconds), `MaxBackoff` 5 min, `MaxGenerations` 3, `RecordTTL` 300 s (plan §6).
- **A step's time runs across restarts**: a step started before a long outage can time out at resume; `retry_host` resumes it with a fresh start.
- **Waits that depend on the host have no timeout**: `wait_address` and `wait_applied` end when the host acts or the account is removed, never by the clock.
- **`ReasonVolumeFailed`** is added beside the plan's six reasons, for a data volume AWS reports in state `error`.
- **A refused Route 53 create fails `place` with `ReasonRecordConflict`**, the plan's choice: the usual cause is a record that appeared at the name between the tool's check and the create. The account stays `pending`; the template shows no reason for it (plan §10 assets issue).
- **Not found on a change id counts as in sync**: Route 53 keeps change ids for a limited time, and a change accounts recorded and cannot find was accepted earlier.
- **Steps not named in the plan's sketch keep its names**; the first step of each kind is chosen by the engine from an operation's empty step (`D04-store`).

## Consumer usage

Wiring (`D03-serve`): `e := ops.New(ops.Config{Store: st, Cloud: cl, Hosts: s.Hosts, AccountsURL: func() (string, error) { return s.AccountsURL(servicesPath) }, Telemetry: w, Now: p.Now, After: p.After})`; `go e.Run(ctx)`; the tools are handed `e.Wake` (`D07-tools`). Agent creates a host: `create_host` records the operation and calls `Wake`; the next pass runs `ops.StepAddress`, `ops.StepLaunch` with the token `op.ID + "-" + ops.StepLaunch + "-1"`, `ops.StepWaitRunning`, `ops.StepVolume`, `ops.StepWaitVolume`, `ops.StepAttach` at `ops.DataDevice`, `ops.StepWaitAttached` and `ops.StepAssociate`, deferring by `ops.PollInterval` while AWS settles, and tells `host.changed` provisioning→running and `operation.finished` done. Agent places an account: `ops.StepWaitAddress`, `ops.StepRecord` (an A record with TTL `ops.RecordTTL`), `ops.StepWaitRecord`, `ops.StepWaitApplied`, then `account.changed` pending→active. Stop and start: `ops.StepStop`, `ops.StepWaitStopped`; `ops.StepStart`, `ops.StepWaitRunning`, `ops.StepAssociate`. Resize to `t4g.large` with 60 GB data from running: `ops.StepGrowData`, `ops.StepWaitData`, `ops.StepStop`, `ops.StepWaitStopped`, `ops.StepSetType`, `ops.StepStart`, `ops.StepWaitRunning`, `ops.StepAssociate`. Restart accounts mid-operation: the new `Run`'s first pass finds the operation at its recorded step and generation, looks up by its `Operation` tag, resends the same client token, and creates nothing twice; the scan finds no stray. Failure: a refused `RunInstances` fails the operation with the `cloud.Error` text and tells `host.changed` provisioning→failed; `retry_host` makes it running again at the same step; a launch whose instance vanished fails with `ops.ReasonTerminated` after `ops.MaxGenerations`. Delete: `ops.StepUnrecord`, `ops.StepWaitUnrecord`, `ops.StepTerminate`, `ops.StepWaitTerminated`, `ops.StepRelease`, `ops.StepOrphan`. Silence: each pass `store.MarkSilent`, `trail.HostSilent` per host. A test: `e := ops.New(cfg)` over a temporary store, `memory.New` or a recording fake `cloud.Cloud`, a moved clock and a `telemetry.Capture`; `e.Pass(ctx)` repeatedly; `e.Scan(ctx)`.
