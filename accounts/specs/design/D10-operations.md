# D10-operations

The operations engine: `internal/ops`, which carries every long AWS-side change to its end. A tool records an operation through the store and answers at once (`D07-tools`); the engine, running beside the server for as long as accounts serves (`D03-serve`), advances each running operation one step at a time against the cloud (`D05-cloud`), recording each step before the call that makes it and what the call learned after it (`D04-store`). An interrupted operation resumes where it stopped, against what AWS already holds, whenever accounts starts again (outcome 11 of ikigenba-ssh-hosts.md). Beside the operations the engine works the deletes of kept volumes, the data volumes of deleted hosts that a caller asked to delete (outcome 15 of ikigenba-host-numbers-and-delete.md), and runs two sweeps: the silence sweep, which tells `host.silent` for a running host that stopped reporting (outcome 24), and the stray scan, which reports once each resource tagged as a host's that no record explains (outcome 11), gives every live host with an Elastic IP its own A record at `<host>.<hosts domain>` (outcomes 8 and 9 of ikigenba-host-names.md), removes the record a host deleted while the release before this one ran left behind at its name, and lists as kept the data volume of every deleted host the kept-volume record does not hold yet. Host backups (ikigenba-host-backups.md) add four operation kinds that end on what a host reports, `close`, `open`, `replace` and `restore`, a last step for a delete told not to keep its data that removes the host's key backup from the backups bucket, and beside the kept-volume deletes the deletes of a removed account's backups. This document declares the engine's surface, its constants and step names, the state machine of each operation kind, the rules every step follows, and the events it tells (`D08-trail`).

## The loop

`Run` makes a pass at once, treating every running operation as due whatever its next try says, and runs the stray scan; then it waits, for `Wake`, for the earliest deferred step or kept-volume delete to come due (`store.NextTry` counts both; never sooner than `PollInterval`), or for `ReconcileInterval`, whichever comes first, and passes again, until its context is done. A pass reads running operations that are due, in pages of `store.BatchSize`, and moves each by at most one step; then it works the kept volumes whose delete is due, in pages of the same size; then the deletes of removed accounts' backups that are due, in pages of the same size; then it runs the silence sweep; then, when `ScanInterval` has passed since the last scan, the stray scan. `Pass` and `Scan` are exported so a test drives the engine one pass at a time with an injected clock and never waits.

## Every step

Every step is recorded before its AWS call: the store holds the operation at that step and generation before the request is sent, so a crash between the call and recording its result re-runs the step, and every step begins with a lookup that makes a repeat harmless. The client token of `RunInstances` and `CreateVolume` is `<operation id>-<step>-<generation>`: a repeat of the same step and generation sends the same token, and AWS answers the same resource. Every resource is tagged in the call that creates it with its kind, its host and its operation (`Kind`, `Host`, `Operation`), the instance also with accounts' URL (`AccountsURL`), the data volume `Kind=host-data`; later only `Orphaned=true` on a kept data volume. Lookups go by the operation's tag and the kind, never by host name alone: a database reset must never adopt an old host's resources, which then show as strays, and since a host's number is reused once its delete has finished (outcomes 1 to 3 of ikigenba-host-numbers-and-delete.md), a resource tagged `Host=host01` may be an earlier `host01`'s, kept or stray, which the live `host01` must never adopt, delete or explain away. When a lookup finds more than one live resource of a kind under the operation's tag (only a lost `AllocateAddress` retry can make two), the one with the lowest id is adopted and the others are left to the stray scan and to `delete`.

An error's class decides: a transient error defers the step with a backoff doubling from `PollInterval` up to `MaxBackoff`; a refused error or a token mismatch fails the operation with the error's text as its reason; not found means what each step says. A step not done within `StepTimeout` of its start fails with `ReasonTimedOut`, except the waits on the host (`wait_address`, `wait_applied`, and for host backups `wait_final`, `restore`, `wait_admitted` and `wait_restored`), a volume wait while AWS reports the modification still `modifying`, and a grow step while it is deferred. An unexpected not found fails the operation with `ReasonMissing`; an operation another writer ended (a cancelled `place`, an `unplace` a delete closed) is dropped without an event. A wait that is not yet satisfied defers by `PollInterval`. Cancelling `Run`'s context cancels any call in flight; the operation keeps its recorded step and resumes at the next start.

## The machines

**`create`** (host `provisioning` → `running`): `address` (adopt the operation's address or allocate one) → `host_record` (the host's own name, `<host>.<hosts domain>`: a record there holding exactly the host's address is adopted and `wait_host_record` skipped; no record creates one; anything else, or a refused create, fails with `ReasonRecordConflict` and leaves that record as it was, so a taken name is never overwritten) → `wait_host_record` → `launch` (needs accounts' URL, else fails with `ReasonNoAccountsURL`; adopt the operation's live instance or launch one with the step's token) → `wait_running` (pending waits; running records the zone and root volume; shutting down or terminated starts a new generation back at `launch`, failing with `ReasonTerminated` beyond `MaxGenerations`) → `volume` (adopt the operation's data volume or create one in the instance's zone) → `wait_volume` → `attach` (at `DataDevice`) → `wait_attached` → `associate` → done.

**`stop`** (`stopping` → `stopped`): `stop` → `wait_stopped`. **`start`** (`starting` → `running`): `start` → `wait_running` (terminated fails with `ReasonTerminated`) → `associate`, which keeps the Elastic IP on the host (outcome 17).

**`resize`** (`resizing` → the state it started from): `grow_root` → `wait_root` when the root grows, then `grow_data` → `wait_data` when the data volume grows, then the type change: from `running`, `stop` → `wait_stopped` → `set_type` → `start` → `wait_running` → `associate`; from `stopped`, `set_type` alone. A grow step reads the volume and its latest modification first and skips the call when the volume already has the target size or a modification to it exists, defers while another modification is still in progress (EC2 allows one at a time), and otherwise notes the grow and then modifies. A wait step records the new size, which bumps the host's version so the daemon grows the filesystem online (`D15-machine`), once AWS reports `optimizing` or `completed`, where the new size takes effect. The four-grows-per-24-hours rule is checked by the store when the tool starts the resize; a `VolumeModificationRateExceeded` that still occurs is deferred by `MaxBackoff`, never a failure.

**`delete`** (`deleting` → `deleted`): `unrecord` (delete the A record of every `removing` account on the host, and the host's own record, each only while it still points at the host's address and nothing else) → `wait_unrecord` (every change in sync, and at least `RecordSettle` since it began) → `terminate` → `wait_terminated` → `release` → then by the host's `OnDelete`, the choice the delete was started with (`D04-store`): for `keep`, `orphan` (tag every data volume `Orphaned=true`, never delete it) → done, exactly as before; for `delete`, `delete_data` (delete every data volume, a volume already gone or going counting as done, tagging nothing) → `wait_data_deleted` (until no data volume of the host is left in any state but `deleted`) → `delete_backups` (the host's key backup, below) → done. Each of `terminate`, `release`, `orphan`, `delete_data` and `wait_data_deleted` acts on the ids the host row holds and on every resource of its kind tagged with any of the host's `create` operations, found page by page, so a host whose create failed half-way still leaves nothing behind, and a host whose create never made a data volume has nothing to delete. No address is released while a record of the host or its accounts may still point at it, and no volume is deleted while an instance of the host may still hold it. Finishing the delete finishes every `removing` account on the host with it, and records the host's data volume, when it had one, in the kept-volume record, `kept` after `orphan` and `deleted` after `delete_backups` (`D04-store`). The host's own record is removed inside `unrecord` and waited for inside `wait_unrecord`; `delete_data` and `wait_data_deleted` are step names `release-100` does not know, and `delete_backups` one the release before host backups does not know (Recorded decisions). A data volume a replace kept (below) is a kept volume, not one of the host's resources: it is tagged with the host's `create` operation, but no delete tags, deletes or waits on it, and it stays until its owner deletes it with `delete_kept_volume` (backups outcome 35).

**Kept-volume deletes** (kept volume `deleting` → `deleted`, or back to `kept` with a reason): not an operation, since a deleted host has no current operation and the delete has one step. `delete_kept_volume` marks the volume `deleting` under its caller, due at once, and wakes the engine (`D07-tools`, `D04-store`); each pass then reads it and either finds it gone (state `deleted`), finds AWS still deleting it (defer by `PollInterval`), or sends `DeleteVolume` and defers by `PollInterval`. A transient error defers by the same backoff an operation's step uses; a refused one (an attached volume answers `VolumeInUse`) returns the volume to `kept` with the error's text as its reason, so the caller sees why and may try again. It has no timeout: AWS's own deleting is the only wait, and nothing else waits on it. Every change of state is told as `volume.changed` under the caller that asked. Only a volume the kept-volume record holds as `deleting` is ever worked; the record only holds data volumes of hosts accounts deleted, so nothing in AWS the record does not explain is ever deleted (outcome 16).

**`place`** (account `pending` → `active`, or `failed` with the reason): `wait_address` (the host has an Elastic IP) → `record` (a record at the account's name holding exactly the host's address is adopted and `wait_record` skipped; no record creates one; anything else, or a refused create, fails with `ReasonRecordConflict`) → `wait_record` → `wait_applied` (the host applied the version that added the account) → done. A failed `place` leaves its account `failed` with the reason; `remove_account` clears it and `create_account` places it again; there is no account retry tool (`D04-store`).

**`unplace`** (`removing` → row gone): `unrecord` → `wait_unrecord` → `wait_applied` → done, touching its one account's record and never the host's. `wait_applied` is skipped when the host never applied nor tried the version that added the account; otherwise it waits, with no timeout, until the host applied the removal. What bounds it is the host: a running host applies within a cycle, and the `delete` of a stopped, failed or silent host ends it.

## Host backups

The four kinds host backups add are recorded by the tools (`D07-tools`) in a table the release before host backups never reads (`D04-store`), and end on facts the host's report carries: `RecordReport` writes the host's per-account results, and the engine's waits read them. None of the waits on the host but `wait_opened` has a timeout; what bounds each of the others is the host, as for `wait_applied`.

A close's and a replace's **step set** is the host itself (its key backup, the `store.BackupStep` with an empty `Account`) and every account on the host that `Desired` sends as active (pending, active or failed; an account being removed gets no final and no restore). A member is done or failed by its row in `store.BackupSteps`, and pending otherwise, a member with no row included: an account placed during a close holds the close until its own final is reported. Rows of accounts no longer on the host do not count.

**`close`** (host `closing` → `running`, closed): `wait_final` finishes once every member of the step set is done, and fails with `ReasonFinalFailed` once one is failed. The host's text stays on the step's row; the operation's reason is the constant (`D08-trail`'s secrecy). While the close runs or is failed, `Desired` locks every user (`D04-store`), so a failed close, like a finished one, keeps the host's users locked until `open_host` records an open, across a replace too (`D04-store`): no step of a replace, its `admit` included, unlocks anyone.

**`open`** (`opening` → `running`): `wait_opened` finishes once the host's `Applied` reaches its `Version`, as the pass reads it; the daemon then has the state that no longer locks its users, which `Desired` sends from the `OpenHost` call itself (`D04-store`). Unlike the other waits on the host it times out: an open of a host whose daemon no longer reports (a dead host, its close failed because it died) fails with `ReasonTimedOut` after `StepTimeout`, the host `failed`, and `replace_host` is then accepted and `delete_host` no longer refused as busy. The users stay unlocked in `Desired` after that failure, since the open superseded the close, so a later replace brings the host back unlocked, as the operator asked.

**`replace`** (`replacing` → `running`, keeping the host's record, name, address, accounts and users; backups outcome 28): `retire` (terminate the old instance the replacement row holds, unless it is gone or going) → `wait_retired` (until that instance is `terminated` or not found, and only then `store.Retire`, from which `Desired` withholds accounts and users and, from backup, carries the `restore` member; so the old machine never receives either) → `relaunch` (as create's `launch`, with the target's type and root size, recording the new instance on the host at once, so a delete after a failed replace terminates it through the row) → `wait_relaunched` (records the zone, root volume, type and root size). Keeping the volume: → `reattach` (the host's data volume, the old one, once AWS reports it `available`) → `wait_reattached` → `reassociate` → `admit` → `wait_admitted` → done. From backup: → `new_volume` (a volume of the target's size in the new instance's zone, recorded as the host's data volume at once, which keeps the old one as a kept volume of cause `replaced`, `D04-store`) → `wait_new_volume` → `reattach` → `wait_reattached` → `tag_old` (`Orphaned=true` on the old volume, as `orphan` tags) → `reassociate`, which makes the host `restoring` → `restore` (until every member of the step set is done; `ReasonNotEmpty` when the host found its target not as the format left it, `ReasonRestoreFailed` for any other failure) → `admit` (`store.Admit`, after which `Desired` sends accounts and users again, still locked when the host was closed) → `wait_admitted` (the host applied that state) → done. The EC2 steps time out as create's do; `restore` and `wait_admitted` do not for their age, since a large restore takes hours and the host page shows `restoring` and each account's restore meanwhile, but each pass at them checks that the new instance still runs and the host still reports, and fails the replace otherwise. A replace never deletes or detaches a volume and never touches an address but to associate it: the old data volume is kept, not deleted (backups outcome 35). The new instance must be in the zone of the volume it reattaches; the launch template decides the zone, as it did for the host's create, and an `AttachVolume` AWS refuses fails the replace with its text, so the operator replaces from backup instead.

**`restore`** (no host state; the restoring account is the operation's `account`): `wait_restored` finishes when the host reports the copy made and fails with `ReasonRestoreFailed` when it reports a failure, whose text stays in the restore's record. A restore is not retried; the agent asks again.

**A deleted host's key backup.** A delete told not to keep its data ends, after `wait_data_deleted`, with `delete_backups`: one page of the keys under `protocol.HostPrefix` of the host's name and `Seq` per pass, deleted with one `DeleteKeys`, until a pass lists no keys at all, a missing bucket counting as nothing to delete; a short page proves nothing, since S3 may answer fewer keys than it was asked for while more remain. The `Seq` in the prefix means a later host of the same name never removes an earlier one's key backup. Nothing under `accounts/` is touched (backups outcome 46); a delete that keeps its data keeps the host prefix. Every key deleted becomes a hidden version, kept 35 days by the bucket's rule (`D05-cloud`'s `DeleteKeys` sends no version id).

**Deletes of a removed account's backups** (a row `delete_account_backups` makes `deleting`, `D04-store`): not an operation, for the reason a kept-volume delete is not one; a removed account has no host and its slug may be reused. Each pass, after the kept volumes, reads the due rows in pages and for each sends one `ListKeys` page under `protocol.AccountPrefix` of the slug and one `DeleteKeys` of it: a pass that deleted any keys leaves the row due at once for the next pass, one that lists none finishes it, a missing bucket finishes it, a transient error backs off as a kept-volume delete does, and a refused one makes the row failed with the error's text, which calling the tool again retries. It tells nothing: the tool's `change.finished` records the request and `backup_status` answers the progress.

## Sweeps

The silence sweep runs each pass: `store.MarkSilent` in pages, one `host.silent` for each host it marks. The stray scan lists, page by page, instances tagged `Kind=host`, volumes tagged `Kind=host` and `Kind=host-data`, and addresses tagged `Kind=host`; each whose id the store does not explain and whose `Operation` tag names no running operation is noted, and the first time it is noted `resource.unexplained` is told. A data volume a replace kept is held by no host row, but `store.Explains` explains every kept volume and each replacement's old instance and old volume (`D04-store`), so the scan never tells it. The stray listing never deletes or tags anything; a resource in its sense, and in R-0DM7-JP72's, is an instance, a volume or an address, never a Route 53 record, which the record and leftover checks below handle. The scan also prunes expired volume grows with `store.PruneGrows`, in pages; that is retention only and changes nothing a caller sees.

The scan also heals host names. Page by page it checks every host that is `running`, `stopping`, `stopped`, `starting` or `resizing` and has an Elastic IP: exactly one A record at `<host>.<hosts domain>` holding that address is right, and clears the host's record reason if one was noted; no record at the name creates one, noting its change id; anything else, or a refused create, notes `ReasonRecordConflict` as the host's record reason and leaves the record as it was. A conflict is a note, never a failure: the host's state, its reason and its operations stay as they were and no event is told, and the pages and tools show the record reason where the host has no reason of its own (`D06-pages`, `D07-tools`). This is how hosts made before host names get their record, and how a record removed by hand comes back, within one `ScanInterval`. Stop, start and resize keep the Elastic IP, so they add no record step. Any other cloud error, or a store error, ends the record check for that scan, never the stray listing, and the scan returns the error; the next scan checks every host again from the first. A host deleted since its page was read is skipped.

After the record check the scan clears leftovers. A host deleted while the release before this one ran kept its own record, since that release's `unrecord` removes only accounts' records; nothing else would ever remove it. So page by page the scan reads every deleted host it has not yet settled (`store.DeletedHosts`), and for each whose Elastic IP is known finds the records at its name and deletes the A record there only when it holds exactly that address and nothing else; any other record at the name is left as it was. Then it settles the host (`store.SettleDeleted`), so no later scan asks Route 53 about it again: each deleted host costs one Route 53 read once, whichever release deleted it. A host this release deleted has already lost its record in `unrecord` and is settled after one read that finds nothing. Like the record check, the leftover check changes no state and tells nothing; any cloud or store error ends it for that scan, leaves that host unsettled for the next scan, and `Scan` returns the error. When more than one part of a scan ends by an error, the record check, the leftover check and the adoption below among them, `Scan` returns one error matching each of them, joined, never only the first.

The scan also adopts kept volumes. A host deleted by the release before this one, or by any release before kept volumes, kept its data volume and wrote no kept-volume row; so does a host `release-100` deletes after a rollback, whatever its delete was told. Each scan calls `store.AdoptKept` with `store.BatchSize` until it answers fewer: each call, one transaction, makes a `kept` row for up to that many deleted hosts whose row names a data volume and that have no kept-volume row, from what the host row already holds. It sends no cloud request and tells nothing; a volume removed from AWS by hand is still listed, and deleting it then counts as done. A store error ends the adoption for that scan, the other parts still run, and `Scan` returns an error matching it; the next scan starts again.

## Events

The engine never tells `operation.started` (the tools do). It tells `operation.finished` when an operation finishes or fails, with the failure's reason and, for a delete, `data`, the host's `OnDelete` (`keep` or `delete`), so the trail says whether the data was kept (outcome 11 of ikigenba-host-numbers-and-delete.md); `host.changed` for every host state change it makes (to the end state on finish, to `failed` on failure); `account.changed` when a `place` makes its account active or failed and when an `unplace` or a `delete` removes an account (`to` is `trail.AccountRemoved`). All of these are told under the operation's stored caller. `volume.changed` is told for each kept-volume delete the engine ends, `deleting` → `deleted`, or `deleting` → `kept` with the refusal's text, under the caller the kept volume stores; the tool tells `kept` → `deleting`. `host.silent` and `resource.unexplained` carry no caller, and the adoption tells nothing. Host backups add no event (`D08-trail`): a close, an open, a replace and a restore end with `operation.finished` as every kind does, a restore's naming its account, and a replace's move to `restoring` is a host state change the engine makes, told as `host.changed`. The deletes of removed accounts' backups tell nothing.

## Memory

A pass holds at most one page of `store.BatchSize` operations and, per operation, its host, its account and one cloud answer; the silence sweep holds one page of hosts, and so does each of the scan's record check and leftover check, with one Route 53 answer for the host it is checking. The scan folds each cloud page into the store before it returns from the page's callback, so it never holds a listing; `delete` walks the host's operations page by page in the same way. `delete_data` and `wait_data_deleted` do the same, holding the host, one page of its operations and one cloud page or answer. The kept-volume work holds one page of `store.BatchSize` kept volumes and, for the one it is working, one cloud answer; the adoption holds only the count `store.AdoptKept` answers, each call's work bounded by its limit inside the store. Nothing the engine holds grows with the number of hosts, accounts, operations, kept volumes or resources. The leftover check's bound, at most one page of `store.BatchSize` deleted hosts and one Route 53 answer at once, keeping no host of an earlier page, is design guidance, not a requirement: no test can see what `Scan` holds by use, so R-ABJK-WACE states only what a test can see, that the check reads its hosts a page at a time and reaches every one. The kept-volume work's and the adoption's bounds are guidance in the same way: R-9DJQ-0TTM states only what a test can see of the kept-volume work, that it reads due kept volumes in pages of `store.BatchSize` after the last volume of the page before and reaches every one, and R-9M30-P80H only that every adoptable host is adopted however many there are. Host backups keep the same shape: `wait_final` and `restore` hold one answer of `store.BackupSteps` (at most `valid.MaxAccountsPerHost` + 1 rows, bounded by the store) and one of `store.AccountsOn` (at most `valid.MaxAccountsPerHost`); `wait_restored` one restore; `delete_backups` and each removed account's delete one page of at most `cloud.MaxKeysPerPage` keys and one `DeleteKeys` of it, never a listing, since the step reads one page per pass (R-3539-TPS4, R-36B6-7HIT state what a test sees: one `ListKeys` whose callback refuses a second page, and `DeleteKeys` of exactly that page); the backup-delete work one page of `store.BatchSize` rows (R-DT7Q-M9S7). Nothing grows with the number of keys in the bucket.

## Recorded decisions
- **Sizes cross the seam checked**: the store keeps sizes as `int`, the cloud seam takes `int32`; the engine refuses a size outside 1..`math.MaxInt32` with `ReasonBadSize` rather than convert blindly. `D17-names-keys-sizes`' bounds keep every real size far inside.
- **Grows are noted before `ModifyVolume`**, on the step's first attempt only, while the modification itself is sent at every attempt; a crash between noting and sending, or a transient failure later retried after a restart at attempt 0, can count one grow twice, accepted as the safe side: a crash between noting and sending counts a grow that never happened, which only makes the four-per-24-hours limit stricter; a grow sent and never counted could let a fifth through, which EBS would refuse for up to a day.
- **Grow steps never time out while deferred** (rate limit, or another modification still in progress): a rate-exceeded modification is transient (R-RJIJ-058Q), never a host failure, and EBS can hold a volume in `optimizing` for hours.
- **An unexpected not found fails with `ReasonMissing`**: a resource gone from under a step (an address released by hand, an instance gone) is not success; each step that expects not found says so.
- **The store ending an operation under the engine is not an error**: `RemoveAccount` cancels a running `place`, and finishing a `delete` closes the host's `unplace` operations; the engine drops such an operation for the pass and tells nothing for it, since the writer that ended it told its events.
- **`wait_unrecord` waits at least `RecordSettle`** (one minute, Route 53's documented propagation bound) after it starts: a crash between a record's DELETE and recording its change id leaves no change to wait on, and the address must not be released while the record may still resolve.
- **A create failed with `ReasonTerminated` is deleted, not retried**: `retry_host` keeps the generation, so the retried launch gets the same terminated instance back and fails again; `delete_host` cleans it up. Resetting a generation budget on retry was rejected as a second counter for a rare case.
- **`delete` looks up only resources tagged by the host's `create` operations**, the only kind that creates any, so a delete's AWS calls do not grow with how often the host was stopped, started or resized.

- **Exported `Pass` and `Scan`**, so tests drive one pass under an injected clock. Siblings' workers are unexported loops behind `Run`; here the steps are the contract and a test must reach each one.
- **Departure: resume, not fail.** gdrive, gmail and scripts finish interrupted work `failed` or `interrupted` at start; outcome 11 requires resume, so the engine continues every running operation from its recorded step. A timer reconcile has no sibling precedent (gmail reconciles lazily, when a tool touches a draft).
- **Departure: client tokens plus lookup by operation tag**, where devctl looks up by tag only.
- **Timers**: `PollInterval` 5 s, `ReconcileInterval` 1 min, `ScanInterval` 1 h, `StepTimeout` 30 min (a launch settles in minutes; a large `ModifyVolume` reaches `optimizing`, where the size takes effect, in seconds), `MaxBackoff` 5 min, `MaxGenerations` 3, `RecordTTL` 300 s.
- **A step's time runs across restarts**: a step started before a long outage can time out at resume; `retry_host` resumes it with a fresh start.
- **Waits that depend on the host have no timeout**: `wait_address` and `wait_applied` end when the host acts or the account is removed, never by the clock.
- **`ReasonVolumeFailed`** is added beside the other reasons, for a data volume AWS reports in state `error`.
- **A refused Route 53 create fails `place` with `ReasonRecordConflict`**: the usual cause is a record that appeared at the name between the tool's check and the create. The account is then `failed` with that reason, which the landing shows (log D13, Q2).
- **Not found on a change id counts as in sync**: Route 53 keeps change ids for a limited time, and a change accounts recorded and cannot find was accepted earlier.
- **The first step of each kind is chosen by the engine from an operation's empty step (`D04-store`).
- **A create records the host's name before it launches** (`address` → `host_record` → `wait_host_record` → `launch`): the name exists before the instance first boots and its daemon first applies the hostname, so a new host's first in-sync report already carries a name that resolves (outcome 3 of ikigenba-host-names.md), and a taken name fails the create before an instance or volume is paid for (outcome 10).
- **A host's record steps have step names of their own, `host_record` and `wait_host_record`, not `record` and `wait_record`** (rollback safety; expand then contract). An operation's step is persisted, and the release before this one must run on what this one persists. That release runs `record` and `wait_record` as an account's steps; a create resumed there would act on an account that does not exist and could finish without launching an instance. A step name it does not know it answers with an error and no cloud call: the pass ends at that operation, and the create stays at its step until the step's `StepTimeout` fails it with `ReasonTimedOut`, having launched nothing; after rolling forward, `retry_host` resumes it at the same step. The cost, accepted for a rollback in the minute or so a create spends at these steps, is that while such a create is due that release's passes stop at it, delaying the operations after it, the silence sweep and the scan by at most `StepTimeout`, and by that again for each `retry_host` made while it still runs. `record` and `wait_record` stay an account's steps alone (R-9PC1-U6OX). Rejected: an intermediate release that teaches the old engine the new steps first, which costs a release for a rollback window of minutes, and reusing step names that release already handles, all of which act wrongly on a host.
- **A delete keeps its step names** (`unrecord`, `wait_unrecord`): the release before this one runs them for a delete correctly, only without the host's own record, which it leaves at the name. Its `wait_unrecord` still waits `RecordSettle` before an address is released, as after a lost change id. The `host_records` row a delete writes is a table that release never reads.
- **The scan removes a deleted host's leftover record** (rollback safety): a host deleted while the release before this one ran keeps its own record, pointing at an address it released. The scan deletes it only while it holds exactly the address the host had, the rule every record removal follows, and settles each deleted host once, so the check costs one Route 53 read per deleted host ever, not one per scan. Every deleted host is checked once, hosts deleted before host names and by this release included, since the store cannot tell which release deleted a host; marking this release's deletes settled at `Finish` was rejected as a change to `Finish` for one saved read per host. An error in the record check does not stop the leftover check, as it does not stop the stray listing: the leftover check ends at its own first error, as the record check does.
- **Host names heal in the scan, not in every pass**: one Route 53 read per live host per `ScanInterval` rather than one per host every pass (log A2). An hour's delay for a host made before host names, or a record deleted by hand, is acceptable; a new host gets its record from its create.
- **A conflict found by the heal is noted, not failed**: the host runs whatever its name resolves to, so failing or stopping it would take service away for a DNS problem. Only a create fails on a taken name (outcome 10), because there nothing runs yet. The note is the host's `RecordReason`, separate from `Reason`, so a heal never overwrites why an operation failed.
- **A cloud error in the heal ends the record check, not the scan**: the record check sends no further Route 53 request in that scan, the stray listing is still done in full, `Scan` returns the error, `Run` passes on, and the next scan, `ScanInterval` later, starts again from the first host. Stopping rather than skipping the host: under throttling, going on would send more requests to an API that is already refusing them, and a failure that persists at one host shows as `Scan`'s error every interval. A host's record reason is never set from a throttled or failed read; only a record seen at the name, or a refused create, is a conflict.
- **Store errors in the heal**: a host deleted since its page was read (`NoteHostRecord` answering not found) is skipped and the check goes on, since there is nothing left to note; any other store error ends the record check as a cloud error does.
- **A delete removes the host's own record only while it holds exactly the host's address**, the rule account records follow, so a record someone else put at the name survives the delete, and `wait_unrecord` waits for that change with the accounts' before the address is released.
- **The data-removing steps have names of their own, `delete_data` and `wait_data_deleted`** (rollback safety; expand then contract; log P3), in B1's grammar for `host_record`. The release before this one (`release-100`) knows every other delete step, and its `release` goes to `orphan`. So a delete told not to keep the data, caught by a rollback at `unrecord`, `wait_unrecord`, `terminate`, `wait_terminated` or `release`, is carried on by that release to `orphan` and done: the data is kept and tagged, the safe side, and since that release writes no kept-volume row, the first scan after rolling forward adopts the volume and it is listed as kept, for the owner to delete with `delete_kept_volume`. One caught at `delete_data` or `wait_data_deleted` is at a step name that release does not know: it answers with an error and no cloud call, its pass stops at that operation (delaying the operations behind it, the silence sweep and the scan, each by at most `StepTimeout`, and by that again for each `retry_host` made while it still runs), and after `StepTimeout` it fails the delete with `ReasonTimedOut`. A `DeleteVolume` already sent goes on in AWS regardless. After rolling forward, `retry_host` resumes the delete at its step, where a volume already gone counts as done, or `delete_host` starts a new delete with its own choice; one started by `release-100` has no choice row and so keeps the data. The cost, accepted, is the same as B1's: a delete waits for roll-forward, and the passes of the release before this one are delayed while it is due. Rejected: reusing `orphan` with a different meaning, which that release would run as a keep and finish while recording nothing, and an intermediate release, for a window of the minutes a delete spends at these steps.
- **`orphan` honours a choice to delete the data** (rollback safety): a delete told not to keep the data that `release-100` moved from `release` to `orphan`, and that is still at `orphan` when the roll-forward reaches it, moves to `delete_data` instead of tagging and finishing, so a delete finished by this release always did what its choice says and `Finish` records the kept-volume row's state truthfully. Symmetrically `delete_data` and `wait_data_deleted` of a delete whose choice is to keep the data move to `orphan` sending nothing; no step this release writes leads there, so this guards only a step written by hand or by a release to come. The timeout check comes first, as at every other step: a delete at these steps older than `StepTimeout` fails with `ReasonTimedOut` and `retry_host` resumes it at the same step, where the next pass redirects it, as a step's time runs across restarts and as for a create stuck at `host_record`.
- **No kept-volume state reaches the release before this one**: the choice and the kept-volume rows live only in the new table of `0006_kept_volumes.sql`, which `release-100` never reads. A kept-volume delete in flight at a rollback stays `deleting` and is worked again after rolling forward, where a volume AWS finished deleting meanwhile counts as gone. A host row gains no column, so `release-100` reads and writes host rows as before.
- **A reused host number** (outcomes 1 to 3 of ikigenba-host-numbers-and-delete.md): when `CreateHost` gives a new host the name of a deleted one, the store first vacates the deleted row, re-keying it with its operations and settling its record (`D04-store`). So `OperationsOf(name)` answers only the live host's operations, and a delete of the live host, in either release, walks only its own `create` operations' tags and its own row's ids, never the earlier host's kept or stray volume (R-8VIM-KBOF); records are bound to the live host's own address by R-IZ7Z-00CB, so if AWS hands the new host the address the earlier one released, its own record at that address is its own to remove. The vacate leaves a settled `host_records` row under the vacated key even when the earlier host had none (`D04-store`), so `store.DeletedHosts` never answers a vacated row, in either release, and neither release's leftover check sends a Route 53 request for a name a live host now holds. A deleted host from before host names whose leftover record was never removed would, once vacated, keep it; the next create of that name then fails at `host_record` with `ReasonRecordConflict`, never overwriting it, the safe side. In practice every such host was settled by the first scan of `release-100`.
- **No lookup by host name alone adopts, deletes or explains away an earlier same-named host's resource** (outcome 3 of ikigenba-host-numbers-and-delete.md). Checked part by part. The stray scan asks `store.Explains` by resource id, and a vacated row keeps every id, so an earlier host's resource is explained by its own row, never the live host's; a stray's `Host` tag is only reported. The record heal and a create's `host_record` look up the name but adopt only a record holding exactly the live host's own address, and note or fail on anything else, changing nothing. The leftover check never covers a vacated row. A create's `address`, `launch` and `volume` find by the operation's tag, and an operation id is never reused. A delete's `unrecord` removes only a record holding exactly the host's own address; its `terminate`, `release`, `orphan`, `delete_data` and `wait_data_deleted` act on the row's ids and on resources tagged with the host's own `create` operations, never on the `Host` tag. A kept-volume delete acts on the one volume id its row holds. No lookup in this design filters by the `Host` tag.
- **The kept-volume delete is a row of its own, not an operation**: an operation has a host whose current operation it is, and a deleted host has none and may have had its name reused; a kept volume is keyed by its volume id alone. It reuses the operation's discipline (state recorded before the call, describe before delete, not found as done, the same backoff) and has no `StepTimeout`, since nothing waits on it and AWS's deleting ends by itself.
- **The adoption runs in the scan**, in transactions of `store.BatchSize` hosts: `Run`'s first pass scans at once, so hosts deleted by earlier releases (host06 and host07 on `us`) are listed as soon as this release starts, and a host deleted by a rolled-back release within one `ScanInterval` of rolling forward. Once a host has its row the adoption never considers it again, so the steady cost is one store query per scan.
- **`wait_data_deleted` only waits**: a volume AWS reports in a state other than `deleting` or `deleted` after `delete_data` is not deleted again by the wait; the step fails at `StepTimeout` with `ReasonTimedOut`, and a new `delete_host` with `keep_data` false runs `delete_data` again (`retry_host` would resume the same wait). AWS documents that a successful `DeleteVolume` moves an available volume to `deleting`, so this case is only AWS losing an accepted delete.
- **The new kinds wait in a table the previous release never reads** (host backups pick 1; rollback safety; expand then contract). The release before host backups answers a kind it does not know with an empty first step and a step error, stopping its passes at that operation until `StepTimeout` fails it and, through its `Fail`, the host (a restore included). A close, open, replace or restore therefore lives in `D04-store`'s `backup_operations`: across a rollback it pauses at its recorded step and resumes after rolling forward, and since the new waits last hours, a shared table would have failed hosts. Each new step still has a name of its own (R-CQ6Y-DM1Z), so dispatch by step stays unambiguous across kinds. Recorded costs (pick 16): while rolled back, that release's `host` tool refuses with `store.Unreachable` a host whose current operation is a new kind, its `retry_host` refuses such a failed host, and its `resize_host` and `delete_host` could act on such a host, which it believes idle.
- **`delete_backups` stays in `operations`, under its own name** (the R-968B-Q7DG precedent): a delete is a kind every release knows. A delete caught at `delete_backups` by a rollback stalls that release's passes for at most `StepTimeout`, then fails with `ReasonTimedOut`; `retry_host` after rolling forward resumes it at the step, where keys already deleted are simply not listed again. A delete told to keep its data that is found at `delete_backups` (only a step written by hand or by a release to come) moves to `orphan` sending nothing, as `delete_data` does (R-P2DG-ME5W).
- **The host key prefix carries the host's `Seq`** (pick 20): `delete_backups` removes `hosts/<host>/<seq>/` of the host being deleted, so a later host given the same name (outcomes 1 to 3 of ikigenba-host-numbers-and-delete.md) never removes, and is never restored from, an earlier host's key backup.
- **Withholding starts only at `Retire`, after the old instance is terminated or absent** (pick 19): before it, the old instance may still run and poll, and a withholding state would lock its users out early, while a `restore` member reaching its daemon would fail the replace on a volume that is not empty. `wait_retired` therefore calls `store.Retire` only on `terminated` or not found, never on `shutting-down`, and nothing is launched, created, attached or associated before it (R-CZY5-FRZJ). The data volume survives the termination, as every delete that keeps its data already relies on: AWS documents `DeleteOnTermination` false by default for a volume attached after launch (EC2 User Guide, "Preserve data when an instance is terminated"), and only the root volume, launched with delete-on-termination (R-XADN-4G62), goes with the instance; no requirement here states the AWS fact.
- **A replace records its new instance at `relaunch`** (pick 21), and its new data volume at `new_volume`, each as soon as AWS answers it, as create records its own; so a delete after a replace failed at a later step terminates and deletes them through the host row, and R-8VIM-KBOF's walk of the `create` operations' tags needs no change. Recording the new volume at once is also when the store keeps the old one as a kept volume of cause `replaced`; a new `replace_host` on a failed replace from backup likewise keeps the half-made volume, so nothing is lost or unexplained. Rejected: recording the volume after `wait_new_volume`, which leaves a volume no row explains if that wait fails.
- **A replace reattaches only an `available` volume**: after `wait_retired` the old volume may still show its attachment to the terminated instance for a moment; `reattach` waits rather than sending an `AttachVolume` AWS would refuse, and a volume attached to some other live instance waits until `StepTimeout` fails the replace, never detaching anything.
- **The waits on the host compare with the host's current `Version`**: `wait_opened` and `wait_admitted` finish once `Applied` reaches the `Version` the pass reads, which is at least the version the open or the admission set, since versions only grow. No operation stores the version its change made, and a stricter wait only finishes when the host has caught up with everything, which a running host does within a cycle.
- **The host becomes `restoring` as the replace enters `restore`, in `reassociate`'s own advance** (a departure in timing from the plan, which has the `restore` step set it): the move to the step and the state change are then one store write, so no pass can see the replace at `restore` with its host still `replacing`, and a crash between them cannot leave the two apart. The `restore` step still sets `restoring` itself whenever it finds the host in another state, which is the plan's rule and is what a `retry_host` (which makes the host `replacing`) relies on (R-HHEN-C5N4); the observable result is the plan's.
- **`wait_opened` times out, unlike the other waits on the host** (the root's decision): an open that waits forever on a dead host would stay a running host-kind operation and hold off `replace_host` and `delete_host`, so a dead host's recovery would be blocked; with `StepTimeout` it is only delayed, the open failing with `ReasonTimedOut` and the host `failed`, which `replace_host` accepts and `delete_host` no longer refuses as busy. Refusing `open_host` on a silent host was rejected: it cannot cover a daemon that dies after the open starts. The users stay unlocked in `Desired` after the failure, since `OpenHost` itself superseded the close (`D04-store`); a later replace brings the host back unlocked, as the operator asked, and `retry_host` waits for the host again.
- **A replace watches its host while it waits on it** (the root's decision): `restore` and `wait_admitted` have no age limit, and the host is busy while they run, so a new instance that died there would hold the host forever, `replace_host` and `delete_host` refusing it as busy and `retry_host` needing a failed host. Each pass at those steps therefore reads the new instance, as the EC2 steps do, and fails the replace with `ReasonTerminated` when it is not running, `ReasonMissing` when it is gone, and `ReasonTimedOut` when the host has not reported for `StepTimeout`, counted from the later of the step's start and the last report (R-21ST-G3KK), so a long restore on a live host is never cut short. Existing reasons say each case; no new constant. The host's last report is `store.Host`'s `Reported`, already readable. Recovery of a dead host is delayed, never blocked, as for `wait_opened`.
- **`ReasonNotEmpty` wins over `ReasonRestoreFailed`** when several members of a restore failed: a target not left empty means the restore must start over on a fresh volume (`replace_host` from backup again), the more specific instruction; the other members' texts stay on their rows.
- **`retry_host` of a failed restore fails again at once** while its step rows stay failed: the store resets failed rows only for a close (`D04-store`), since a restore that found its target not empty, or gave up after its attempts, cannot succeed on the same volume. The way on is a new `replace_host` from backup, which starts afresh with a new volume.
- **Key deletes read one page per pass**, for `delete_backups` and for a removed account's backups alike: a pass stays short whatever a prefix holds, and the engine holds one page of keys. A pass that deleted keys leaves the work due at the pass's time, so the next pass, at most `PollInterval` later, takes the next page; a deleted key is no longer current, so it is not listed again. Only a pass whose listing hands no keys ends the work: S3 may answer a page of fewer than `cloud.MaxKeysPerPage` keys while more remain (`D05-cloud` hands each non-empty response as it comes), so a short page is not the end. The cost is one more listing per prefix. A missing bucket (`ClassNotFound`) counts as nothing to delete in both, as a missing volume does for a kept-volume delete.
- **A removed account's backup delete is a row the engine works, not an operation** (pick 11), on the kept-volume precedent: it has no host, nothing waits on it, and it reuses the operation's backoff. It has no timeout and tells no event.
- **A kept volume is neither one of the host's resources nor a stray**: a replace from backup keeps the old data volume, which is still tagged with the host's `create` operation; the host's resources leave out every volume `store.KeptVolume` answers (R-DJGJ-K3UN), so a later delete neither deletes nor waits on it; `store.Explains` explains it as a kept volume (`D04-store`), so the stray scan (R-0DM7-JP72, unchanged) does not tell it. The host's resources still need the exclusion: a delete finds data volumes by its `create` operations' tags, not by `Explains`. During a rollback the release before host backups, whose `Explains` covers host rows only, explains it by no row and tells `resource.unexplained` for it once (accepted: the event is advisory and told once per database).

Agent places an account: `ops.StepWaitAddress`, `ops.StepRecord` (an A record with TTL `ops.RecordTTL`), `ops.StepWaitRecord`, `ops.StepWaitApplied`, then `account.changed` pending→active.
