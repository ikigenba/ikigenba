# D04-store

The record: `internal/store`, which owns accounts' tables in its SQLite database, `state/accounts.db`, and every read and write of them. The record is now the source of truth for the whole service (outcome 8 of ikigenba-ssh-hosts.md): hosts with their allowlists, pending unbans and the state of their own DNS records, accounts with their invites, users with their keys and admin flags, the operations that change AWS with the choice each delete made about the host's data, the data volumes kept from deleted hosts, the latest report of each host, the namespace, the counters that allocate sequence numbers, gids and uids, and the strays and volume grows the engine notes. Nothing else holds a host's desired state; the daemon on each host makes the host match what this store answers (`D11-protocol`, `D14-accountsd`). This document declares the store's whole public surface: its types, every method with its signature, what each does, the errors every consumer tells apart, the one line every consumer answers when the database cannot be reached, and the migration. Which tool calls which method is the tools' (`D07-tools`); the pages read the same lists (`D06-pages`); the operations engine drives the operations (`D10-operations`); the daemon endpoints serve `Desired` and take `RecordReport` (`D13-daemon-endpoints`); the trail is `D08-trail`'s. Opening, migrating, transactions and the failure seam are appkit's `db`; `D01-layout-and-run-seam` resolves the path, declares the root package's `Migrations()` and builds the store. For step 2 of ikigenba-self-service-accounts.md, the box path, the store also answers which user a host's uid is (`ActiveUserByUID`, for `D13-daemon-endpoints`) and holds a guarded twin of every change a host's user may make from the box, which the box tools (`D19-box-tools`) call; it adds no table. For host backups (ikigenba-host-backups.md and its decisions log), the store also records closing, opening and replacing a host and partial restores as operations of new kinds, each account's backup facts as its host reports them, the backup settings, and the deletes of a removed account's backups, in the tables `0007_host_backups.sql` creates; and `Desired` gains the lock overlay of a close, the withholding of a replace and the `backup` member's store-filled fields.

## One database, one writer

accounts is the only writer of its database. `store.New` builds a store over a handle and opens or creates nothing. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds; a test proves the record that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`), or closed, answers every call with an error matching `ErrUnreachable` and changes nothing. `Config.Now` is the clock every time the store stamps on its own is read from (created times, an operation's start, a step's start when the engine does not pass one); `Config.Rand` is where operation ids are drawn. `Run` hands in `Process.Now` and `Process.Rand`; the store has no default for either. Every write a method makes is one transaction: a call either changes everything its requirement says or nothing.

## Hosts

A host row is created by `CreateHost` in state `provisioning` with its `create` operation. Its name is `host` and the lowest number from 1 up, at least two digits, that no host in any state but `deleted` has as its name: with `host01` and `host03` live the next is `host02`, with none live it is `host01`, and `host100` follows `host99` (outcomes 1 to 5 of ikigenba-host-numbers-and-delete.md). A host holds its number from its create until its delete finishes, so a host provisioning, failed, stopped or still deleting holds it; a deleted host does not, and neither does a data volume kept from it. Names are therefore reused. `Seq` is a separate creation sequence, drawn from a counter exactly as before, one more per create, deleted hosts included, never reused; it orders every list (creation order) and is no longer the name's number. A live host's number is never above its own `Seq`, since fewer than `Seq` hosts were created before it, and the counter is above every `Seq`, so the release before this one, which names a host `host` and its counter value, can never give out a name a live host holds.

The row is kept after deletion in state `deleted`: no read or list answers it, but its resource ids still explain what AWS holds (`Explains`). When `CreateHost` picks a name a deleted row holds, it **vacates** that row first, in the same transaction. `hosts.name` is the table's key and the operations, report, record state, allowlist and unbans refer to it, so the row is re-keyed to a key that is not a valid host name and is unique (the build's choice; guidance `<name>#<seq>`, as `host01#1`); its operations move with it (moved, never deleted, so `Operation` still answers each), a settled `host_records` row is recorded under the new key whether or not the host had one (its own moving with it), and its report, allowlist and pending unbans are removed, since a deleted host's are never read. The settled row matters to the release before this one: its `DeletedHosts` answers a deleted row with no settled `host_records` row, and would otherwise ask Route 53 about `host01#1.<domain>`. Guidance on the order within the one transaction: delete the report first (`reports.host` is an immediate foreign key; a deleted host has no accounts, since its delete's `Finish` removed them), then re-key `hosts.name`, then move the operations (a deferred foreign key) and the `host_records` row; `hosts.seq` is unique, which rules out inserting a copy and then deleting the original. It keeps state `deleted`, its `Seq` and every resource id, so `Explains` still explains its resources, and `DeletedHosts` never answers it again. So the new host starts with no report, an empty allowlist, no unbans, no record change or reason, and `OperationsOf` of its name answers only its own operations; a later delete of it walks only those, and never touches a resource of the earlier host. Before re-keying, when the row has a data volume and no kept-volume row, the vacate adopts it (Kept volumes, below), so the kept volume keeps the name the host had. The re-keyed key is never answered as a host: only `Explains` and adoption read a vacated row (though `Operation` of one of its moved operations answers that key as its `Host`), and the vacate has already recorded any data volume it had.

The host's columns hold everything the landing and the silence sweep need, so neither ever decodes a report body: the state and failure reason, type and sizes, the resource ids AWS gave, the desired-state `Version` and the `Applied` version the host last reported, the `Attempted` version and whether the latest report carried an error, when it last reported and when it last entered `running`, and the `Alarm`, the last abnormal health an event told. `Health` computes the health word from those columns alone.

A host also holds an **allowlist** and its **pending unbans** (outcomes 6 to 12 of ikigenba-ssh-bans.md), both parts of its desired state. The allowlist is the addresses and CIDRs the host's fail2ban jail ignores: `Allow` adds an entry and `Disallow` removes one, each on a host in any state but `deleting` and `deleted`, so an edit made while a host is stopped applies when it runs; at most `valid.MaxAllowlistPerHost` entries. Every `Host` the store answers carries its allowlist, sorted. A pending unban is an address whose ban the daemon lifts on its next apply: `Unban` records one on a named running host, and `UnbanRunning` records one on every running host at once, all or nothing; at most `valid.MaxUnbansPerHost` per host. An unban is a pending change, not an operation: it carries the version that recorded it and lives until a report applies that version. The store takes each address or entry already in the canonical form `D17-names-keys-sizes`'s `valid.Address` or `valid.AllowEntry` gives; the tools canonicalize before they call, so a non-canonical one is an argument no consumer sends.

A host also has a name in DNS, `<host>.<hosts domain>`, an A record holding its Elastic IP (outcomes 8 to 10 of ikigenba-host-names.md). The record is not desired state: the daemon never sees it, and `Desired` leaves `D11-protocol`'s `Domain` empty, since the store knows no settings (`D13-daemon-endpoints` fills it). The store keeps two facts about it, on the host beside its other columns: `Change`, the Route 53 change id of the host's own record, as `Account.Change` is the account's, and `RecordReason`, why the record could not be made outside an operation, empty when nothing is wrong. An operation records its change with `RecordHostChange`, the twin of `RecordChange`: it needs the running operation `opID` to be on that host. The engine's scan, which heals the records of hosts made before this release and of records lost later (`D10-operations`), acts outside any operation, so it writes with `NoteHostRecord`, which sets the change when it has one and always sets the reason, an empty reason clearing it. Neither bumps the `Version`, wakes the long poll or touches a host's `State`, `Reason` or `Operation`: a conflict found by the scan is a note on a running host, never a failure. A deleted host keeps the `EIP` it last had, since nothing clears it, and the scan uses it once to remove a record the host left at its name (a host deleted while the release before this one ran keeps its record, `D10-operations`): `DeletedHosts` is the one read that answers deleted hosts, those not yet **settled**, and `SettleDeleted` marks one settled once the scan has checked its name, so it is answered no more. The hostname the host last reported is not a column: it is the `hostname` member of the stored latest report, read as `Report.Body.Hostname`, which `RecordReport` already keeps whole.

A host changes state only through the store's operation methods: `CreateHost`, `StartHostOp` and `DeleteHost` move it into the transitional state of the operation they record, `Finish` moves it to the state the operation's kind ends in, `Fail` moves it to `failed` with a reason, and `RetryHost` moves a failed host back into the transitional state of its failed operation. The guards for each tool live here, in the same transaction as the write, so two racing tools never both pass: one host-kind operation at a time, only `retry_host` and `delete_host` act on a failed host, stop needs `running`, start needs `stopped`, resize needs something to grow or change and grows only, and delete needs every account on the host to be already `removing`, whatever the delete's choice about the data (the delete guard, stated here once, in `DeleteHost`'s requirement, and cited by `D07-tools` and `D10-operations`).

## Deleting a host

`DeleteHost` is the one way to start a delete. It refuses what `StartHostOp` refused for a delete, in the same order, records the `delete` operation as `StartHostOp` did, and also stores the caller's `keepData` against that operation, in a table of its own keyed by the operation's id (outcomes 7 to 13). No row means keep, which is what every delete an earlier release recorded means. `StartHostOp` no longer takes `OpDelete`: no consumer sends it, so it is an argument no consumer sends and answers `ErrUnreachable`. The store answers the choice as `Host.OnDelete`: `OnDeleteKeep` or `OnDeleteDelete` while the host's current operation (`Host.Operation`) is a delete, the host `deleting` or `failed` by that delete and awaiting retry, and empty otherwise. `RetryHost` resumes the same operation, so the choice survives a failure and a retry; a later `DeleteHost` of the failed host starts a new delete with its own choice. A failed host can be deleted either way, one whose create never recorded a data volume included. The engine reads `OnDelete` after its `release` step to choose between keeping the volume and deleting it (`D10-operations`). Since host backups, a delete that deletes the data also needs the host closed, so its final backups were taken, or `lost` true, which says no final backup is possible; otherwise it is refused with `ErrNotClosed` after the delete guard. `lost` is a guard argument only and is not stored.

## Kept volumes

A **kept volume** is the data volume of a deleted host that accounts' record explains (outcomes 14 to 16). The store keeps one row per volume id: the volume id, the host's name as it was when deleted, the size (the host's `DataGB`), when the host was deleted (the finish time of its delete operation), the state (`kept`, `deleting` or `deleted`), the reason the last kept-volume delete was refused (empty otherwise), and for a delete in flight its attempts, next try and caller, kept whole as appkit's `identity.Caller` as an operation's is. Rows come from three places, none of them a cloud call:

- `Finish` of a delete, in its own transaction, records the host's row when it had a data volume: `kept` for a delete that kept the data and `deleted` for one that deleted it.
- `AdoptKept`, which the engine's scan calls until it answers fewer than its limit (`D10-operations`), records as `kept` every deleted host with a data volume and no row yet, up to its limit in one transaction. This is how hosts deleted by the release before this one and earlier (`host06` and `host07` on `us` among them), and hosts a rolled-back release deletes, come to be listed: their rows already hold the name, `data_volume`, `data_gb` and the delete operation with its finish time.
- `CreateHost`'s vacate adopts a deleted row's data volume the same way before it re-keys the row.

A row is never removed; state `deleted` keeps adoption from recording it again. The list, `ListKeptVolumes`, `ListKeptVolumesBefore` and `LastKeptVolumes`, the hosts' three windows in the list's order, answers the `kept` and `deleting` rows, most recently deleted host first (`Deleted` descending, then `Volume` descending); the first page passes the zero `time.Time` and an empty volume. It comes only from this record: a volume in AWS the record does not explain is never listed or deleted, and stays a stray (`NoteStray`). The list may name a volume removed from AWS by hand; deleting it then counts as done (`D10-operations`).

`DeleteKeptVolume` makes a `kept` volume `deleting`, due at the call's stamp, with the caller stored and the reason cleared; one already `deleting` is refused with `ErrVolumeDeleting`, and any other id, unknown, a live host's volume, one already deleted or a stray, with `ErrNotFound`. The engine's pass pages `DueVolumeDeletes`, puts one off with `DeferVolumeDelete` and ends it with `FinishVolumeDelete` (gone: `deleted`) or `FailVolumeDelete` (refused: back to `kept` with the reason). `NextTry` counts the due time of every `deleting` volume beside the operations', so the engine wakes for them, and a delete in flight survives a restart as an operation does: it is a row with its next try.

## Closing, opening and replacing a host

Host backups add four operation kinds, `close`, `open`, `replace` and `restore`, whose rows live in `backup_operations`, a table the release before this one never reads (Recorded decisions). Every operation method answers and acts on both tables alike: ids are unique across both, `Runnable` and `OperationsOf` order by id across both, and `RecordStep`, `Advance`, `Defer`, `Fail` and `Finish` take either. A host is **busy** while any running operation of a host kind, the three new host kinds included, is on it; a running `restore` never makes it busy.

**Close.** `CloseHost` records a running `close`, makes the host `closing`, bumps its `Version` and records one pending **step row** per account on the host not being removed and one for the host itself. While the host's latest close runs or has failed, and after it finished, until an `OpenHost`, the host is **locked over**, whatever other operations (a retry, a replace) follow: `Desired` sends every active user `locked`, which every daemon knows how to apply, and `backup.close` carries the close's id while it runs, asking the daemon for final backups. Stored user states never change, so lists and pages show the user's own state. `RecordReport` writes each final the daemon reports into its step row; the engine (`D10-operations`) finishes the close once every row is done, which makes the host `running` with its **closed time** set, or fails it when one failed, which leaves users locked. `RetryHost` of a failed close makes its failed rows pending again and bumps the `Version`. Closed is a time, not a state: a closed host may be stopped, started, resized, replaced and deleted, and keeps its closed time through all of them. A close of a host already closed answers success with no operation.

**Open.** `OpenHost` accepts a host whose close runs or failed, cancelling a running one, or a closed running host; it clears the closed time, records an `open`, makes the host `opening` and bumps the `Version`, so `Desired` sends users as they are stored; the engine finishes it once the host applied that version.

**Replace.** `ReplaceHost` records a `replace` with its target (the host's type and sizes where the call leaves them out) and a **replacement**: the mode (`volume` or `backup`), the old instance and data volume, and two flags. It cancels the host's pending restores, and for `backup` records a pending step row per account not being removed and the host, and copies, as the **restore paths**, each account's database paths from the host's latest report. Nothing a daemon sees changes until the engine has seen the old instance terminated and calls `Retire`: from then the host is **withheld**, and `Desired` sends no account and no user, so no instance that might be the old one is ever sent either. Withholding outlives its replace: it holds while the replace the host's latest `Retire` retired has not been admitted, through that replace's failure, a store-level `Finish` of it before `Admit`, a later replace not yet retired, and a delete; it ends only when that replace, or a later one once retired, is admitted. It belongs to the host's `Seq`, so a deleted host's name reused by a new host inherits nothing. While withheld, and while the host's current operation is still that retired replace from `backup`, running or failed, the host carries its **restore overlay**: `backup.restore` naming every account on the host not being removed with its gid and restore paths. A superseding replace, a delete or a `Finish` drops the overlay while accounts and users stay withheld, and the next replace from backup carries a new overlay from its own `Retire`. Every change to what the host is told bumps the `Version` once: `Retire` and `Admit` bump as before, and `ReplaceHost`, `DeleteHost` and a replace's `Finish` bump when they drop the overlay (`Finish` at most once in all, whatever volume or size it records too); `Fail` and `RetryHost` change neither and bump nothing. A replace keeping the volume is refused with `ErrWithheld` on a withheld host, since only a restore from backup can bring its accounts back; a replace from backup and a delete are accepted under their usual refusals, so a withheld host is never stranded. The engine's `Advance` records the new instance and volume on the host as it goes; recording a new data volume records the old one as a kept volume of cause `replaced`, so nothing is lost or unexplained, and `Explains` answers true for every kept volume and for the old instance and volume of every replacement. `Update.HostState` lets the engine's restore step make the host `restoring`. `Admit` ends the withholding with one `Version` bump; `Finish` makes the host `running`, admitted or not. `Host.Replace` shows the mode while the replace runs or has failed. A replace keeps the closed time, so a closed host replaced stays closed.

## Restores

`RequestRestore` records a partial restore, of one database at a time or of files from one snapshot, as a running `restore` operation of the account and a **restore** row in state pending, and bumps the host's `Version`; `Desired` carries every pending restore of the host in `backup.restores`. The store checks the request against the host's latest stored report (the database is listed and restorable at that time; the snapshot exists), the account is active, the host running and below `valid.MaxRestoresPerHost` **unfinished restores**: restores of the host still pending or whose operation is still running, so one whose result a report has already written but the engine has not yet settled counts, and so does one still pending whose operation a `Finish` has already settled; a request is thus refused before either the running restores or the pending ones of a host could outgrow the cap. `RecordReport` writes the result the daemon reports, done with the copy's path or failed with its text, which leaves the list; the engine then finishes or fails the operation, and the host is never touched. `RemoveAccount` and `ReplaceHost` cancel running restore operations and pending restores, and since every restore whose operation is running is unfinished, each answers at most `valid.MaxRestoresPerHost` cancelled ids; a delete's `Finish` finds none to cancel, since every account of the host was removed first, so it needs no rule of its own. `RestoresOn` pages a host's restores, newest first.

## Backup facts, settings and deletes

`RecordReport` folds each `backups` entry of an account on the host into that account's **backup facts**; health is computed from them at read time by `BackupHealth`, `FilesStale` and `DatabaseHealth` with the reader's clock and the settings, and never stored. `BackupOf`, `BackupsOn` and `ListBackups` answer them with the account's step states in its host's latest close and current replace from backup, a step row counting as an account's only when its operation began, or the row's own time (`At`) is, at or after the account's creation, so a slug placed again never shows the final or restore of the account it replaced. An account placed during a close has only its row's time, the daemon's: a host clock behind the service's by more than the seconds between placement and that account's first final would hide its own final from the pages and tools, never from the engine; with the hosts' synchronized clocks this is accepted. The engine's step set (`BackupSteps`, `D10-operations`) is unchanged: hiding a row there could hold a close forever. Step rows record no gid and the frozen `0007_host_backups.sql` cannot add one, so the row's own time decides, with no new migration. When an account row is deleted, its facts move to the slug's **removed backups**, which `ListBackups` answers in state `removed` until its backups are deleted. `DeleteAccountBackups` records a **backups delete**, a row the engine works like a kept-volume delete (`DueBackupDeletes`, `DeferBackupDelete`, `FinishBackupDelete`, `FailBackupDelete`) and `BackupsDeleteOf` reads, a failed one with its reason, and `PlaceAccount` refuses a slug whose backups are being deleted. `BackupSettings` answers the one settings row, or `DefaultBackupSettings()` while there is none; nothing writes it.

Every record of these belongs to the host's `Seq`, not only its name: the release before this one, during a rollback, may create a host of a reused name without moving any of these rows, and the new host never inherits them.

## Operations

An operation is a recorded state machine (`D10-operations` owns the steps): its kind, its current step and generation, its status, the target of a resize, the state a resize returns to, the error a failure recorded, how many deferred attempts the current step has had, when it started, when the current step started, when it may next run, when it finished, and the caller who started it, kept whole as appkit's `identity.Caller` so the engine tells events as that caller. A new operation's step is empty: the engine begins at its kind's first step. `RecordStep` records the step about to run before the AWS call it makes; `Advance` records what the call learned and clears the attempts; `Defer` puts the step off and `NextTry` tells the engine when the earliest deferred step is due; `Finish` and `Fail` end the operation. The step's start time survives a repeated `RecordStep` of the same step and generation, so a step that keeps being retried still times out.

Operation ids are `op_` and 16 lowercase hex digits drawn from `Config.Rand`, redrawn on a collision as gdrive draws its `xfr_` ids.

## The team template

The team template's setting is one row, like the backup settings: the URL a host clones and the ref it checks out (`D15-machine`). `TemplateSettings` answers the stored row, or `DefaultTemplateSettings()`, `protocol.DefaultTemplateURL` at `protocol.DefaultTemplateRef`, while there is none; `SetTemplateSettings` is the one writer, called by `set_team_template` (`D07-tools`), and replaces either member, leaving the one it is not given. It raises no host's version: the setting changes nothing on a host until a later creation, and only later creations use it, so nothing existing is ever re-seeded. `Desired` carries the setting in every state it builds, read in the same transaction as the rest of the state.

Each account and each user records the template commit it was created from (`Account.Template`, `User.Template`): the commit the host reported having seeded the account's folder from, or written the user's home file from, empty until a report names it and for every account and user created before this release. `RecordReport` sets it from the report's `seeds` and `homes` (`D11-protocol`), matched by gid and uid, which accounts never reuses, and only while it is empty, so the first commit reported is kept, a later report naming another changes nothing, and a host can only ever credit its own accounts and users.

## Accounts, users and the namespace

An account is placed on one host forever. `PlaceAccount` records it `pending` with its `place` operation; `Finish` of that operation makes it `active`, and `Fail` of it makes it `failed` with the reason, as a failed host operation does to its host; `RemoveAccount` makes a `pending`, `active` or `failed` account `removing` with an `unplace` operation, cancelling a `place` still running; `Finish` of the `unplace` deletes the row. A user belongs to one account, fixed at add. Account slugs and user names share one namespace across every host: a name is taken while its row exists and freed only when the row is gone. Gids and uids come from one counter starting at `FirstID` and are never reused.

Every change that alters what `Desired` answers for a host bumps that host's `Version` by one in the same transaction and stores the new version on what changed (the account's `Version` or `RemovedVersion`, the user's `Version`, an unban's version); a change that is already in effect (a key already held, a user already locked, an allowlist entry already held or not held, an address already pending) changes nothing and bumps nothing. A user is `Pending` while its version is above its host's applied version. Purging rows the host already applied (a user deleted and applied, an account removed and applied, an unban applied) bumps nothing.

## Admins and invites

Step 1 of ikigenba-self-service-accounts.md gives an account admins and lets a person join it by an invite link (outcomes 1 to 15). Both live only here; neither reaches a host, so `Desired` and the protocol do not change.

A user's **admin flag** is a fact about the user beside its state. `AddUser` records it false; `SetAdmin` sets or clears it on a user in any state but `UserRemoving`, answering whether it changed, and bumps no version, so the user's `Pending` and its host's `Version` stay as they were and the long poll is not woken. Every `User` the store answers carries it in `Admin`.

An **invite** belongs to one account and carries the admin flag the user it makes will get, its created and expiry times (`InviteLife`, 72 hours, after its creation) and, as `CreatedBy`, the `UserID` of the caller who made it. `CreateInvite` records one on an account that is not `removing` and answers it with its **token**, a secret drawn from `Config.Rand` in the same form as webhooks' secrets: `inv_` and 32 bytes in unpadded Crockford base32. The token is answered once; the store keeps only its SHA-256 and compares in constant time, and nothing it answers afterwards carries the token or a part of it. The invite's id, `iv_` and 16 hex digits, names it everywhere else: in `list_invites`, `revoke_invite` and the trail. An invite is **live** while it has not been used, revoked or deleted with its account and its expiry has not come; an account holds at most `MaxInvites` (20) live invites and `CreateInvite` refuses one more with `ErrTooManyInvites`. `Invites` lists an account's live invites, at most 20; every `Account` carries their number in `Invites`. `RevokeInvite` deletes a live invite. `InviteByToken` answers the invite a token names when it is usable, live on an account that is not `removing`, and `ErrNotFound` for anything else, unknown, used, revoked, expired or malformed alike, so the enrollment page (`D18-enrollment`) answers them all the same. `NameHeld` tells the page whether a name is taken without adding anything.

`Enroll` is the one write a guest reaches. In one transaction it checks the invite is usable, the name free and the host not full, then deletes the invite and creates the user exactly as `AddUser` would, with the invite's admin flag and the invite's `CreatedBy` as its own. So an invite makes at most one user: of two submissions racing on one token one succeeds and the other finds no invite. A refused submission (a taken name, a full host) leaves the invite usable, and opening the link (`InviteByToken`) consumes nothing (outcome 6).

There is no sweep. A used or revoked invite is deleted at once; `RemoveAccount` deletes every invite of the account, and a `Finish` of `unplace` or `delete` deletes any left for a slug whose row it deletes; an expired invite stays until the next `CreateInvite` of its account deletes it before counting. So an account never holds more than `MaxInvites` invite rows. Each invite also records its account's gid, and only an invite whose gid is the current account's counts or is usable, so a row left behind for a slug that was removed and placed again (by the previous release, which knows nothing of invites) never applies to the new account; `CreateInvite` deletes such rows with the expired ones.

## Acting from a host

Step 2 of ikigenba-self-service-accounts.md (outcomes 16 to 27) lets an SSH user manage their own keys, and an admin their account, from a host, through the box tools (`D19-box-tools`) that `D13-daemon-endpoints` serves at `protocol.BoxPath`. The store adds no table, column or migration for it: every method below reads and writes the tables `0002_hosts.sql` and `0004_invites.sql` already create, so `Desired` and the release before this one are untouched.

**Who is calling.** `ActiveUserByUID(ctx, host, uid)` turns the uid a host's daemon forwards into a user: the user holding that uid whose name is **active** (its state `active`, its account anything but `removing`) and whose account is on that host. Anything else, uid 0, a negative uid, a gid, a locked or deleted user, a user of another host, is `ErrNotFound`, which `D13-daemon-endpoints` answers 403. Pending and failed accounts count, as `Desired` sends them `active` and the host holds their group and users; a removing account never holds a user, since `RemoveAccount` refuses one that does. From then on the box knows the caller only as a name, `box.ActorPrefix` and the user's name in `Caller.UserID`, so the guarded methods below take the **actor** by name, and `UserNamed` answers a name's user whatever its state.

**Guarded twins.** Each change a box tool makes has a `*As` method that checks the actor's own standing in the same transaction as its write, then does exactly what its **central twin**, the method the central tools call, does for the actor's account:

- `AddKeyAs` and `RemoveKeyAs`, for every user on their own SSH user: the actor must be active, else `ErrNotActive`. `RemoveKeyAs` then refuses `ErrLastKey` when the key is the actor's only one, after `ErrKeyNotHeld`; central `RemoveKey` still removes a last key.
- `UsersAs`, `LockAs`, `UnlockAs`, `DeleteAs`, `SetAdminAs`, `CreateInviteAs`, `InvitesAs` and `RevokeInviteAs`, for admins: the actor must be an **active admin**, else `ErrNotAdmin`, before any other refusal, so a non-admin learns nothing about targets. `AdminCheck` answers the same guard alone, without writing, for the one box answer that writes nothing (a `create_invite` with no link base).
- A target user or invite outside the actor's account answers `ErrNotFound`, exactly as an unknown one, never `ErrNotInAccount`; an empty name or a malformed invite id answers the same, after the guard.
- `LockAs` and `DeleteAs` of the actor, and `SetAdminAs` demoting the actor, answer `ErrSelf` (outcome 3); a self-promotion is already in effect and answers unchanged. Delete still needs a locked user, as centrally.
- `CreateInviteAs` always makes an ordinary user's invite: it is `CreateInvite` with `admin` false.

A twin's successful call counts as its central twin's call wherever a requirement defines or counts by calls (an invite `CreateInviteAs` made is live and usable like any other). Because every guard sits in the write's transaction, a lock, delete or demotion that races a box call always wins. The central methods are unchanged: they take no actor and the central tools keep full control (outcome 4).

**Recorded callers are capped.** Every method that records a caller's `UserID` (`CreateHost`, `StartHostOp`, `DeleteHost`, `RetryHost`, `DeleteKeptVolume`, `PlaceAccount`, `RemoveAccount`, `AddUser`, `CreateInvite` and `CreateInviteAs`) refuses one longer than `valid.MaxUserIDBytes` (64 bytes, `D17-names-keys-sizes`) with `ErrUnreachable`: an argument no consumer sends, since auth's ids are 26 characters and a box actor's is `ssh:` and at most 32 bytes. The cap bounds what a box `users` or `list_invites` answer can carry in `created_by`, which keeps every box answer under `protocol.MaxBoxAnswer`. `Enroll` records the invite's `CreatedBy`, already capped; an operation's `Email` and `RequestID` reach no box answer and are not capped.

## Desired state and reports

`Desired` builds `D11-protocol`'s `protocol.DesiredState` for a host from its rows, its `allowlist` and `unban` included, each sorted; `D13-daemon-endpoints` fills in the daemon digest. `RecordReport` keeps the latest report of a host and folds it into the host's columns. A report can only ever misreport its own host: its applied version is clamped to the host's own version and never goes backwards, sign-ins and slices count only for the host's own users and accounts, and sign-in times never lie in the future (the trust argument of `D12-host-identity`). A report that applies a removal deletes the removed users and frees their names, and one that applies an unban's version deletes that unban, so an unban recorded at version 5 stays in `Desired` until a report applies 5. The report itself, its bans and the allowlist the host applied included, is kept as `D11-protocol`'s `DecodeReport` bounded it. `RecordReport` answers a `Transition` from which `D13-daemon-endpoints` tells `host.synced` and `host.apply_failed`; `MarkSilent` marks running hosts that stopped reporting, and `D10-operations` tells `host.silent` for each.

## Strays, grows and watching

`NoteStray` records a resource the stray scan could not explain, answering true only the first time so the event is told once; `Explains` says whether any host row, deleted ones included, holds a resource id. `NoteGrow` records each volume modification accounts started, and `StartHostOp` refuses a resize that would grow a volume already grown `MaxGrows` times within `GrowWindow` (EBS allows four modifications per volume in a rolling 24 hours); expired rows are pruned by the next `NoteGrow` of the same volume and by `PruneGrows`, which the engine's scan pass calls in pages. `Watch` lets the daemon endpoints' long poll wait for a host's version to change; it is in-process only.

## Errors

`ErrUnreachable` covers every failure of the database and every argument no consumer sends, an address or allowlist entry not in canonical form included; consumers answer it with `Unreachable`, never quoting the cause. `ErrNotFound` says the named entity does not exist (or the host is deleted, for reads). `ErrTaken` says a name is held in the namespace. `ErrConflict` says a state guard failed; each guard has its own error that matches `ErrConflict` under `errors.Is`, so `D07-tools` picks the refusal it words without re-reading state, and `D08-trail`'s `Result` classifies them all as refused; the bans add `ErrTooManyUnbans` and `ErrAllowlistFull` for the two caps, and reuse `ErrNotRunning` and `ErrHostGone`; the invites add `ErrTooManyInvites` for their cap, and `Enroll` reuses `ErrTaken` and `ErrAccountFull` as `AddUser` answers them. Two not-found cases are told apart the same way: a user that exists but in another account (`ErrNotInAccount`) and a key the user does not hold (`ErrKeyNotHeld`), both matching `ErrNotFound`. `SettleDeleted` answers `ErrNotFound` for a host that does not exist and `ErrConflict` for one that is not deleted. `RecordHostChange` answers `ErrNotFound` and `ErrConflict` as `RecordChange` does, but checks its operation (not found, then not running) before its host, as its requirement lists, and `NoteHostRecord` answers `ErrNotFound` for a host that does not exist or is deleted. The guarded twins add `ErrNotActive` (the actor is not active), `ErrNotAdmin` (the actor is not an active admin), `ErrSelf` (an admin locking, deleting or demoting themselves) and `ErrLastKey` (the actor's only key), each matching `ErrConflict`, and answer a target outside the actor's account `ErrNotFound`, never `ErrNotInAccount`. `DeleteHost` answers `ErrNotFound`, `ErrHostGone`, `ErrBusy` and `ErrHasAccounts` as `StartHostOp` answered them for a delete, and `StartHostOp` answers `ErrUnreachable` for `OpDelete`. The kept volumes add `ErrVolumeDeleting`, matching `ErrConflict`, for a delete of a volume already being deleted; `KeptVolume` and `DeleteKeptVolume` answer `ErrNotFound` for every volume the list would not show; and `DeferVolumeDelete`, `FinishVolumeDelete` and `FailVolumeDelete` answer `ErrNotFound` for a volume with no row and `ErrConflict` for one not `deleting`, as the operation methods answer for an operation not running. A caller `UserID` longer than `valid.MaxUserIDBytes` is an argument no consumer sends. Host backups add `ErrNotClosed` (a delete of the data from a host never closed, an open of a host not closed), `ErrNoDataVolume`, `ErrNoAddress` (a replace that has no volume to keep or no address to move), `ErrWithheld` (a replace keeping the volume of a withheld host), `ErrAccountNotActive`, `ErrNotRestorable` and `ErrTooManyRestores` (restores), `ErrAccountExists` (a delete of a live account's backups) and `ErrBackupsDeleting` (a placement of a slug whose backups are being deleted), each matching `ErrConflict`, and `ErrNoDatabase`, `ErrNoSnapshot` and `ErrNoUser` (a files restore naming a user that does not exist), matching `ErrNotFound`; they reuse `ErrBusy`, `ErrHostFailed`, `ErrNotRunning`, `ErrHostGone` and `ErrNotInAccount`. Precedence: a done context and a failing or closed handle first, then an argument no consumer sends, then not found, then the method's guards in the order its requirement lists; the guarded twins put their actor guard (`ErrNotActive`, `ErrNotAdmin`) right after the arguments no consumer sends, before not found.

## Memory

Every list takes a `limit` and answers at most that many rows, read by a keyset query over an index; a page asks for one row more than it shows (`D06-pages`, `D07-tools`), so the store accepts up to `paging.MaxLimit + 1`. Passes over operations, silent hosts and grows are in pages of the caller's limit (`BatchSize` for the engine). `AccountsOn`, `UsersOf` and `Desired` answer every row of one host or account, bounded by the caps the store itself enforces (`valid.MaxAccountsPerHost`, `valid.MaxUsersPerHost`, `valid.MaxKeysPerUser`); `Desired` adds at most `valid.MaxAllowlistPerHost` allowlist entries and `valid.MaxUnbansPerHost` unban addresses, and every `Host` carries at most `valid.MaxAllowlistPerHost` entries. `Unban`, `Allow` and `Disallow` each hold one host with its at most 50 entries and 50 unbans; `UnbanRunning` reads the running hosts one at a time in its one transaction, holding one host and its unbans at once and a count, never a list of hosts, whatever the number of hosts the store holds. This bound is design guidance, not a requirement: no test can see it by use. A report is one body of at most `protocol.MaxReportBytes`. `Watch` holds one channel per waiter. `Invites` answers at most `MaxInvites` invites, which the cap bounds and a requirement states; `InviteByToken`, `RevokeInvite` and `Enroll` each hold one invite (and `Enroll` one user with its one key); `CreateInvite` holds a count, never a list; `SetAdmin` and `NameHeld` hold one user or one name. Since nothing sweeps, the invite rows of an account are bounded by the same cap: at most `MaxInvites`, expired ones included. The box path's methods hold no list beyond their twins': `UserNamed`, `ActiveUserByUID` and `AdminCheck` each hold one user; `AddKeyAs` and `RemoveKeyAs` hold the actor with its at most `valid.MaxKeysPerUser` keys; `LockAs`, `UnlockAs`, `DeleteAs` and `SetAdminAs` hold the actor and one target; `CreateInviteAs` holds the actor, one invite and a count, and `RevokeInviteAs` the actor and one invite; `UsersAs` answers what `UsersOf` answers, at most `valid.MaxUsersPerHost` users with their keys, and `InvitesAs` what `Invites` answers, at most `MaxInvites`, both entry caps stated by requirements. Every answer's size is bounded too: no caller `UserID` the store records exceeds `valid.MaxUserIDBytes`. `DeletedHosts` answers at most its `limit` hosts, as every list does (R-7F0I-RMRD), and `SettleDeleted` holds one host; `RecordHostChange` holds one operation and one host, and `NoteHostRecord` one host; each writes one `host_records` row, which it replaces, so a host keeps at most one row, one change id and one reason, however often the scan notes it. These bounds are design guidance, not requirements: no test can see them by use, since none reads tables or what a method holds. Only the engine calls them (`D10-operations`), with a Route 53 change id the cloud answered and a reason that is one of its reason constants, so each stored value's size is bounded by what the engine passes and the store sets no cap of its own. Every `Host` carries those two strings; the hostname a host reported stays inside its one stored report.

Host numbers and kept volumes add no list held whole. `CreateHost` holds one candidate name at a time and probes at most one more name than there are live hosts; its vacate is set-based statements bounded by the one earlier host's own rows (its operations, its one report, its at most `valid.MaxAllowlistPerHost` entries and `valid.MaxUnbansPerHost` unbans, its one `host_records` row, its one kept volume), passing none of them through the process. `DeleteHost` holds one host, one operation and one choice, as `StartHostOp` holds them; `OnDelete` is one more value read with each host. `Finish` of a delete writes one kept-volume row more. `KeptVolume`, `DeleteKeptVolume`, `DeferVolumeDelete`, `FinishVolumeDelete` and `FailVolumeDelete` each hold one kept volume; the three list windows and `DueVolumeDeletes` answer at most their `limit`, as every list does (R-7JW4-APQ5), so the engine holds one page of `BatchSize` kept volumes and one cloud answer; `AdoptKept` is one set-based insert of at most `limit` rows that holds only its count, whatever the number of deleted hosts; `NextTry` reads two times and answers one. A refused delete's reason is the error text the engine passes, bounded by what the cloud answered, and the store sets no cap of its own, as for a failed operation's `Error`. These bounds are design guidance, not requirements, for the reason above.

Host backups add no list held whole either. `RestoresOn`, `ListBackups` and `DueBackupDeletes` answer at most their `limit` (R-75JE-BGKN), by keyset over an index (`restores_host_asked`, the slugs, `backups_deletes_due`). `BackupsOn` answers at most `valid.MaxAccountsPerHost` entries and `BackupSteps` at most that plus one, both stated by requirements; `Desired` adds at most `valid.MaxRestoresPerHost` restore requests, and `RemoveAccount` and `ReplaceHost` answer at most that many cancelled restore ids (R-PV9G-ZJQN), since `RequestRestore` caps a host's unfinished restores, which take in every pending restore and every restore whose operation is running; and, while it carries the restore overlay, one restore account per account on the host with at most `protocol.MaxDatabases` restore paths in all, which `ReplaceHost` copies from one stored report and caps. Whether a host is withheld, and which replace its overlay names, is one bounded lookup, never a read of the host's replaces, which grow with its history: the one replacement of the host's `Seq` retired last, found by an index (or a pointer the host row keeps, the build's choice), and whether it was admitted; `ReplaceHost`, `DeleteHost`, `Finish` and `Desired` each read that one row. `RecordReport` still holds one report body of at most `protocol.MaxReportBytes`, and writes at most one facts row per account on the host, one step row per account and the host, and one result per pending restore of the host, each folded as it is read. `ReplaceHost` and `RequestRestore` each read one stored report body; `CloseHost`, `ReplaceHost` and `RetryHost` write at most `valid.MaxAccountsPerHost` + 1 step rows by set-based statements; every other new method holds one row. The settings are one row. These are guidance where no test can see them, as above. The team template adds one settings row, one string per account and per user, and to `RecordReport` one write per seed and home of the report, at most `protocol.MaxSeeds` and `protocol.MaxHomes`, each folded as it is read.

## Recorded decisions

- **The record is the source of truth** (outcome 8). Previous design: the record held only what accounts created, and the host (opsctl) held keys, memberships, states and sign-ins. That host is gone; there is nothing else to agree with.
- **Guards in the store, one error per guard.** `ErrConflict` stands for every failed guard; each guard also has its own error matching it, so the tool words the right refusal from one transactional answer instead of a racy read before the write. Sibling: gdrive's store answers `ErrEnded` for its one guard.
- **A deleted host is not found to reads and gone to writes.** `Host`, `HostByInstance` and the lists answer `ErrNotFound` for it; `StartHostOp`, `DeleteHost`, `RetryHost`, `PlaceAccount`, `Unban`, `Allow` and `Disallow` answer `ErrHostGone`, which `D07-tools` words as `HostGone`. `Allow` and `Disallow` also answer it for a `deleting` host, as `PlaceAccount` does.
- **An unban is a pending change, not an operation** (outcome 7). It is one repeatable command on the host, so it is a row with a version, like a user change, and the host's applied version retires it; it has no id, step or failed state. It needs a running host (outcome 8): a ten-minute ban does not outlive a stop, so a named host that is not running is refused with `ErrNotRunning` and `UnbanRunning` skips it. The allowlist, by contrast, is lasting desired state, accepted on any host not being deleted.
- **Idempotent edits follow `AddKey`.** An address already pending, an entry already held, or an entry not held is answered unchanged with a nil error and no bump; the already-in-effect check comes before the cap, so a full host still answers an address it already holds.
- **The unnamed unban is all or nothing.** `UnbanRunning` is one transaction over every running host: when any running host that does not already hold the address is at `valid.MaxUnbansPerHost`, it refuses with `ErrTooManyUnbans` and records nothing, so an agent never has to work out which hosts took it. It answers a count of the running hosts, which `D07-tools` answers, not a list, so the answer stays bounded whatever the number of hosts.
- **Departure from shape/ Bounded work: `UnbanRunning`'s one transaction spans every running host.** The rule asks that no transaction span the set. All or nothing needs one transaction; its memory stays bounded (one host and its unbans at a time, and a count), and the set is the business's hosts, each an EC2 instance it pays for, tens and not thousands. Paging the hosts would let a refusal leave earlier hosts changed.
- **The store takes canonical forms only.** An address or entry is canonicalized by `valid` in `D07-tools` before the call; one the store would canonicalize differently is an argument no consumer sends (`ErrUnreachable`), so equal strings are the same entry and the store never rewrites what the tool echoes.
- **Overlapping allowlist entries are both kept.** `192.0.2.7` beside `192.0.2.0/24` is a second entry: equality is by canonical string, and merging would surprise a `disallow_ip` of either.
- **The engine owns step names; the store records them.** A new operation's step is empty, the engine's cue to begin; the store never interprets a step name.
- **Finish and Fail know the kind's end state.** The store, not the engine, moves a host to `running`, `stopped`, the resize's resume state or `deleted`, and an account to `active` or gone, so the state machine's end states hold whatever engine calls them.
- **The step's start time survives a repeated `RecordStep`** of the same step and generation, so `StepTimeout` counts from the step's first attempt.
- **Alarms persist until in sync.** `silent` and `error` stay until a report applies the current version, so `host.synced` is told once per episode and a host that goes silent again while still marked silent is not told twice.
- **Purges bump nothing.** Deleting a user or account row whose removal the host already applied, or an unban whose version it applied, changes nothing the host must do, so it does not wake the long poll for an empty cycle.
- **The Route 53 change id lives on the account** (`Change`), since a host delete records one change per removing account.
- **An unplace records what it superseded** (`Operation.Supersedes`), so the tool that cancelled a running `place` tells its `operation.finished` with status `cancelled` from the answer alone.
- **A failed account is removed, not retried.** A `failed` account (its `place` failed) and a `removing` account whose `unplace` failed are both taken on by `remove_account`: `RemoveAccount` starts an `unplace`, which deletes the account's record only when it points at the host and waits for the host to drop the group; with one running it answers `ErrAccountRemoving`. The agent then creates the account again. This is outcome 10's retry for an account. A retry tool was rejected: it would add a tool, a store method and its errors, and repeating a `place` from its recorded step does not cure its usual failure, a record at the name that is not the host's (`ReasonRecordConflict`). Until it is removed a `failed` account keeps its group on the host (`Desired` sends it `active`) and takes users as a `pending` one does.
- **`RetryHost` keeps the generation**: a create failed with `ReasonTerminated` cannot be retried into a fresh launch; it is deleted instead (`D10-operations`).
- **The last key may be removed centrally, not from the box.** A user with no key cannot sign in, which is the central caller's choice; `remove_key` answers the keys left (`D07-tools`). From the box, `RemoveKeyAs` refuses the actor's last key with `ErrLastKey` (outcome 21), so a user cannot lock themselves out of the host they are on.
- **`CreatedBy` is the creating caller's `UserID`**, kept as given, for a host, account, user or invite: an auth user id for what a central tool created, `box.ActorPrefix` and the SSH user's name (`ssh:bugs`) for an invite a box call created (`D19-box-tools`), and for an enrolled user its invite's. auth's ids carry no `:`, so the two never collide. An operation keeps the whole caller because its events are told as that caller (gdrive's transfers keep user id, email and request id the same way).
- **Recorded callers are capped at `valid.MaxUserIDBytes`.** The box answers lists that carry `created_by`, and the answer must stay under `protocol.MaxBoxAnswer` without paging; capping what the store records (64 bytes, above auth's 26 and the box's 36) bounds them by construction. A longer caller is an argument no consumer sends (`ErrUnreachable`), reachable only by a forged identity header; each recording method's own requirement states the cap.
- **Guarded twins, not an actor on the central methods** (replaces step 1's "the store is actor-free"). Step 2's rules for a host's user (no self-lock, self-delete or self-demotion, no removing one's own last key, admin tools for admins only, the account always the actor's) must hold atomically with the write, so each is checked inside a new `*As` method's transaction, which then does exactly what its central twin does. The central methods and their requirements do not change and keep full control (self-service outcome 4); sharing at the store keeps one copy of every guard, where sharing tool bodies would add contract to `D07-tools` and still need these methods.
- **Every box write checks the actor's own standing.** Key writes check that the actor is active, admin writes and reads that the actor is an active admin, in the same transaction, so a lock, deletion or demotion that commits first always wins over a box call already in flight.
- **A foreign target is unknown.** A user or invite of another account answers `ErrNotFound`, exactly as one that does not exist, so an admin learns nothing outside their account; an empty name or malformed invite id answers the same after the guard, so the guard is always the first refusal a non-admin sees.
- **Resolution counts pending, active and failed accounts, not removing ones.** `Desired` sends the first three `active`, so the host holds their group and users and the daemon's own check on the state it fetched agrees; a removing account holds no user anyway.
- **The actor is a name, not a uid.** Names are unique system-wide (`D17-names-keys-sizes`), and the box server sees only `Caller.UserID`; `D13-daemon-endpoints` resolves the uid once with `ActiveUserByUID` and passes the name on.
- **An admin may lock, delete or demote another admin** (outcomes 2 and 23). The `*As` guards forbid only acting on oneself (`ErrSelf`, outcome 3); any other active admin of the account is an ordinary target.
- **Invites survive their maker.** An invite stays live when the admin who made it is later demoted or locked, as it does centrally: the invite is the approval, and any admin of the account may revoke it. Nothing deletes or hides an invite on its maker's change.
- **The same-transaction guards are not provable by a deterministic test.** That `AddKeyAs`, `RemoveKeyAs`, the admin guard, the target and self rules, `CreateInviteAs` and `RevokeInviteAs` judge the actor in the write's own transaction would need a race the test cannot schedule; so it is guidance for the build, not a requirement: each of those methods judges the actor's standing, the target and the self rules in the same transaction as the read or write it makes, and their requirements state only the refusals and the unchanged store a deterministic test proves. The weakness is accepted, as the central guards' concurrency is.
- **The removing clause of "active" stays.** No permitted test can reach a user of a removing account, since `RemoveAccount` refuses an account that has users; the clause is kept so the definition does not lean on that other guard.
- **Ids** `op_` + 16 hex from `Config.Rand`, redrawn up to 8 times, as gdrive's `xfr_`.
- **Departure: operations survive a restart.** gdrive, gmail and scripts finish interrupted work `failed` or `interrupted` at start; outcome 11 requires resume, so the store keeps every running operation as it was and the engine continues it (`D10-operations`).
- **Departure: strays are a table**, so each unexplained resource is told once across restarts; devctl reports duplicates on every listing instead.
- **Departure: the old tables stay unused**, not dropped (outcome 27, expand). accounts' previous design kept `groups` and `users` as its whole record.
- **Desired state does not change** (self-service outcome 19). The admin flag and the invites live only in the store; `Desired` answers what it answered before (its requirement then stood unchanged), the protocol keeps its version, and `SetAdmin`, `CreateInvite` and `RevokeInvite` bump no version. Only `Enroll`, which creates a user, bumps one, as `AddUser` does.
- **The previous release runs on this schema.** `0004_invites.sql` only adds two tables and changes no existing one (expand then contract). The admin flag is a table of uids rather than a column on the users, so a user the previous release adds is simply not an admin, and a row its purge leaves names a uid never reused. It knows nothing of invites, so its `RemoveAccount` leaves them in place. While that account is `removing`, this release may still count and list those invites (but never accept their tokens, since the account is removing) until a `Finish` of its `unplace` or `delete` deletes them; no test can reach this, and it is accepted. Once the row is gone, the gid each invite records keeps such a row from applying to a later account at the same slug, and the next `CreateInvite` of that slug deletes it; for a slug never placed again the rows stay, at most `MaxInvites` per slug, unusable and invisible.
- **Rollback protection the build keeps, not a requirement.** Each invite records its account's gid, and only an invite whose gid is the current account's counts, is listed or is usable; `CreateInvite` deletes an account's invites of another gid with its expired ones, and a `Finish` of an `unplace` or `delete` deletes any invite left for a slug whose row it deletes. Within this release `RemoveAccount` already deletes every invite, so no test can reach either: only the previous release, which knows nothing of invites, leaves such rows. They are stated here because a clause no permitted test can reach is not a requirement.
- **The token is kept as a hash.** Only the SHA-256 of a token is stored, and a lookup compares in constant time, so a copy of the database does not hand out usable links; webhooks' bearer secrets are the precedent. Neither is provable by use, since no test reads tables or times comparisons; what is provable is that nothing the store answers carries the token after `CreateInvite`.
- **An invite is consumed by success only** (outcome 6). `InviteByToken` reads; `Enroll` deletes the invite in the transaction that creates the user, so a refused submission leaves it usable and two racing submissions make one user.
- **One not-found for every unusable link** (outcome 13). Unknown, used, revoked, expired, malformed, for a removing account: `InviteByToken` and `Enroll` answer `ErrNotFound` for all, and `RevokeInvite` likewise, so no caller can tell them apart.
- **No sweep for invites.** Used and revoked invites are deleted at once and expired ones by the account's next `CreateInvite` or its removal, so the rows stay within `MaxInvites` per account without a background pass. An expired invite of an account that never makes another lingers until the account is removed, unusable and invisible.
- **Expiry is judged at each use, by that use's own clock.** An invite is live while it is held and its `Expires` is after the call's stamp; the cleanup inside `CreateInvite` deletes only the account's invites expired at that call's own stamp. Nothing more is promised about a clock that moves backward: an invite a cleanup deleted stays deleted, whatever a later stamp says.
- **A used, revoked or expired token never works again because a fresh token is fresh randomness.** `Enroll` and `RevokeInvite` delete the invite, and a token is 32 random bytes from `Config.Rand`, so no rule forbids minting a token again: with real randomness a repeat does not happen, and a test's constant source that repeats one is outside the guarantee.
- **Secrecy is about what accounts minted or stored.** No answer and no event carries a token, its hash or a stored key beyond the one answer that hands the token out (`CreateInvite`'s and `CreateInviteAs`'s second result, and the link built from it). A value the requester supplied, echoed in the same answer, is not a disclosure, and a value that merely coincides with part of a token is not one either; the tests prove the rule with markers and random sources chosen independently of every other value. The trail never carries a token or a key, or part of either, whether accounts minted it or the requester supplied it.
- **An enrolled user's `CreatedBy` is its invite's `CreatedBy`**: the invite is the approval (outcome 8), and whoever made it, a person's auth user id or a box admin's `ssh:` name, is who brought the user in.
- **Departure from shape/ paging: `Invites` takes no limit.** It answers every live invite of one account, bounded by `MaxInvites`, as `UsersOf` is bounded by its cap.
- **The hostname a host last reported is its stored report's `hostname`, not a column** (root decision; departs from the wording of decision A1 of ikigenba-host-names-decisions.md, which names it among the new store state). `RecordReport` already keeps the latest report whole, and `D11-protocol`'s `Report` now carries `Hostname`, so `Report(ctx, host)` answers it as `Body.Hostname`; a copy in a column would be state nothing reads, since neither the landing nor the silence sweep needs it (the pages and tools read it from the report, `D06-pages`, `D07-tools`). A1's choice of a new table stands for the state that is new.
- **The host's record state is a new table, `host_records`, not new columns on `hosts`** (decision A1). Every migration after `0001`, up to `0007`, only creates (R-29RC-8KEO, R-CQHV-FS6Y), so the release before this one runs on the schema and a rollback loses nothing: expand then contract, as `0003_bans.sql` and `0004_invites.sql` did. An `ALTER TABLE hosts` would also run on the previous release, but the CREATE-only rule keeps every migration provable by one shape of requirement.
- **The host's own record's change id lives on the host** (`Host.Change`), beside the accounts' (`Account.Change`): a create records one change for the host's record, and a delete one for the host's record besides one per removing account.
- **Two writers, two methods.** `RecordHostChange` is for an operation's steps and refuses a change from an operation that is not running or not on that host, as `RecordChange` does, so an engine holding a stale operation cannot write; `NoteHostRecord` is for the scan, which runs outside any operation and must also set and clear the reason. Folding them into one would either let the scan pass an empty operation id, an argument no consumer otherwise sends, or let an operation's step set a reason no operation shows.
- **A record conflict found outside an operation is a note, not a failure** (decision A2). `NoteHostRecord` changes no `State`, `Reason`, `Operation` or `Version`, so a running host keeps running and its desired state is untouched; `D06-pages` and `D07-tools` show `RecordReason` where `Reason` is empty.
- **`NoteHostRecord` on a deleted host is not found**, as reads treat a deleted host; the scan checks only live hosts, so it never asks.
- **No delete of record state.** A host row is never deleted, only marked `deleted`. Its name may be reused (host numbers, below), so its `host_records` row moves with it when a create vacates the name, and it can never apply to another host; no read but `DeletedHosts` answers it, and that only until it is settled or vacated. The record itself is deleted by the delete's `StepUnrecord` (`D10-operations`), or, for a host the release before this one deleted, by the scan's leftover check.
- **A deleted host's former address is its kept `EIP`, and its settled flag lives in `host_records`** (rollback safety). The release before this one deletes a host without its own record, which then points at a released address until something removes it. The store already knows the address: `Advance` and `Finish` never clear a field, so a deleted host keeps the `EIP` it had, in both releases. What it lacks is a way to stop checking: without a mark the scan would ask Route 53 about every deleted host every hour forever. The mark is a column of `host_records`, a table only `0005_host_records.sql` creates and which, when this was decided, had run on no space, so every migration after `0001` stays CREATE-only and no `ALTER` of an existing table is needed. `DeletedHosts` is a departure from "a deleted host is not found to reads", for the scan alone; no page or tool calls it.
- **Host numbers are the lowest free, and `Seq` stays a creation sequence** (decision 1 of ikigenba-host-numbers-and-delete-decisions.md; replaces "named from a sequence that never goes back, a name is never reused", ikigenba-ssh-hosts.md's "in order, never reused"). The owner wants the name to say what is there. A host holds its number until its delete finishes, so a failed or still deleting host, whose resources may still exist, never shares a name with a new one. `Seq` keeps ordering the lists, as the landing says, and keeps the counter the release before this one names hosts from. The existing database on `us`, which has given out numbers 1 to 4 and more, needs no reset: with no live host the next is `host01` (outcome 4).
- **A reused name vacates the deleted row; the row is re-keyed, not deleted** (decision 2). `hosts.name` is the key every host table refers to, and no migration may alter a table, so a deleted row cannot gain a surrogate key; re-keying it in the create's transaction frees the name and keeps the row, its `Seq` and its resource ids, so `Explains` still explains them and a later delete of the new host, which walks `OperationsOf` its name, never reaches the earlier host's resources. The deleted host's report, allowlist and unbans are removed rather than moved: nothing reads a deleted host's. Its `host_records` row moves and is marked settled, because the scan would otherwise check DNS at the re-keyed key, which is no name. The cost is the case of a host deleted by a release older than the host names delivery, whose leftover record the scan has not yet settled when a create reuses its name: the scan no longer checks it, so the new host's create finds its name held by another record and fails with `ReasonRecordConflict`, never overwriting it (host names outcome 10), and the leftover is removed by hand. The scan's leftover check has run on every space since the host names delivery, so none is expected; it is accepted.
- **`DeleteHost` is its own method, and `StartHostOp` no longer starts a delete** (decision 3). The choice belongs to a delete alone, and a `keepData` on `StartHostOp` would be an argument every other kind ignores. `StartHostOp` answers `OpDelete` with `ErrUnreachable`, as an argument no consumer sends, rather than keeping a second way to start a delete that records no choice.
- **The choice is a row of its own, keyed by the delete operation** (decision 3; rollback). No column is added to `hosts` or `operations`; an absent row reads as keep, which is right for every delete an earlier release recorded, so nothing is rewritten. `OnDelete` is answered from the host's current operation, so a retry keeps it and a new delete of a failed host replaces it.
- **Kept volumes are a table of their own, never removed** (decision 6). The list must come from the record alone (outcome 16), so the store records each kept volume when it can explain it: at a delete's `Finish`, by adoption of hosts deleted before this release, and at a vacate, before the row loses its name. State `deleted` is kept rather than deleting the row, so adoption, which looks for a deleted host's data volume with no row, never lists a volume again. Adoption needs no data rewrite: a host deleted by any earlier release already holds `state` `deleted`, its `data_volume` and `data_gb` (`Finish` never clears a field) and `operation` naming its finished delete, whose `finished` is the deleted time; `AdoptKept` reads only those.
- **The kept list's first page is the zero time** (decision 6). The list is ordered most recent first, so no real `Deleted` can serve as the start cursor the way `Seq` 0 does for the hosts; a zero `afterDeleted` means the start. No kept volume has a zero `Deleted`, since every delete operation's `Finished` is its finish's stamp.
- **A kept-volume delete is a row, not an operation** (decision 7). It has no host to put into a transitional state, no steps and no generation, and it must not be held up by, or hold up, the host's own operations; it needs only a due time, attempts and a caller, which its row carries. It has no timeout and no failed state: a refusal returns it to `kept` with the reason, and the agent may try again.
- **Rollback: a host mid delete with the data deleted** (decision 5). The choice lives only in `delete_choices`, which the release before this one (`release-100`) never reads. At any step up to and including `release`, `release-100` carries the delete on as its own and its `release` goes to `orphan`, so the data is kept, the safe side; its `Finish` writes no kept-volume row, and after roll-forward `AdoptKept` records the volume as `kept`. At `delete_data` or `wait_data_deleted`, step names `release-100` does not know, it answers an error and makes no cloud call, its pass stops at that operation (delaying those behind it, the silence sweep and the scan, as decision B1 of ikigenba-host-names-decisions.md accepted), and after `StepTimeout` it fails the delete with `ReasonTimedOut`; after roll-forward the host answers `OnDelete` `delete` again, `retry_host` resumes it at its step, or `delete_host` starts a new delete with a new choice. A kept-volume delete in flight lives only in `kept_volumes`, so `release-100` neither sees nor advances it, and it resumes after roll-forward.
- **Rollback: a host row** (decision 5). No column is added to any existing table, so `release-100` reads and writes every host row as it did; a host it creates or deletes simply has no row in the new tables, which reads as keep and, once deleted, is adopted.
- **Rollback: a reused host number** (decision 5). `release-100` serves a live host with a reused name as any other. Its own creates take the counter's next value, above every number ever given, so they never collide with a live name or a re-keyed key, which is no valid host name. Its delete of such a host walks only that host's operations, since the vacate moved the earlier host's, and `release-100`'s `DeletedHosts` never answers the vacated row, since the vacate recorded a settled `host_records` row under its new key whether or not one existed before. Its `Explains` still finds the vacated row's resources.
- **The new operation kinds live in `backup_operations`** (host backups pick 1). The previous release's engine answers a kind it does not know with a step error, stalls its pass on it and, after `StepTimeout`, fails it and its host, which a restore or a close lasting hours would hit. A table it never reads lets a close, open, replace or restore pause across a rollback and resume after. Rejected: one table with the delete step precedent's cost (R-968B-Q7DG), because these waits last hours. Accepted costs during a rollback (pick 16): its `host` tool refuses a host whose current operation is a new kind, its `retry_host` refuses such a failed host, and its `resize_host` and `delete_host` could act on such a host, since it sees no running operation; a closed host reopens, since its `Desired` sends users as stored, and is locked again after roll-forward.
- **Host-scoped rows carry the host's `seq`; no new table has a foreign key** (pick 23). The previous release's vacate re-keys `hosts` and moves `operations` and `host_records` only, so a key from a new table to `hosts` would break it, and a host it creates under a reused name would otherwise inherit an earlier host's closed time, restores or operations. This release's own vacate moves them with the earlier host's `operations` (plan 2.14), so `OperationsOf` of the reused name answers only the new host's operations; `Seq` matching is the guard for the rows the previous release's vacate leaves, and an operation of a new kind answers as its `Host` the name the host row of its `Seq` now holds, so `OperationsOf` agrees in both cases.
- **Account facts carry the account's gid** (precedent: invites). The previous release removes an account without moving its facts; the gid, never reused, keeps a later account of the slug from inheriting them.
- **Settings are one row, defaulted by a function** (pick 3). `DefaultBackupSettings()` is a function, so no package can change the defaults (precedent `ReservedLabels()`), and the store answers it while `backup_settings` holds no row; no tool writes the table (decisions log 6). The `scope` column leaves room for per-host settings, which are deferred.
- **Weekly in place of monthly; the monthly keep stays only for the previous release** (owner). restic's `--keep-monthly 1` keeps only the newest snapshot of the current month, which is the newest snapshot anyway, so file history reached back only seven days; `--keep-weekly 5` keeps the most recent snapshot of each of the last five weeks that have snapshots ("Removing backup snapshots", v0.20.0). The defaults become hourly 24, daily 7, weekly 5 and monthly 0. `0008_weekly_retention.sql` moves every stored row, not only one still at the old defaults: no tool, route or page writes the table, so a row is one an operator wrote by hand, and the owner wants every space on the new retention. `Monthly` and the `monthly` column are kept only because the previous release's service and daemon read them; removing them is a later release's contract half, and this release is the expand half only.
- **Close is a lock overlay, closed is a time** (pick 4). Locking is a value every daemon knows, so even a daemon of an earlier release ends sessions; the stored user states never change, so nothing needs undoing at open. A failed close keeps users locked; an open may cancel a running close. Only an open unlocks: the overlay follows the host's latest close by `Seq`, not its current operation, so a retry or a replace of the host, finished or failed, never unlocks users a close locked; a finished replace keeps the closed time. `OpenHost` accepts any host locked over that is running or whose current operation is the close; its users are unlocked in `Desired` from the open on, and the open's finish then waits for the daemon to apply that version (`D10-operations`' `wait_opened`), so a host whose daemon is unreachable unlocks in the record at once but its open finishes only when the daemon applies, or as `D10-operations` fails it. An open that then fails (its wait timed out) leaves users unlocked, since the `OpenHost` call already superseded the close (R-GT8P-VIM1), and the host, failed by an open and not a delete, is accepted by `ReplaceHost` (R-PNY2-OXAH). Rejected: refusing `replace_host` after a failed close, which would leave a host with a dead machine and a failed close no way on. A closed host that was then stopped is refused `ErrNotRunning` by `OpenHost` until started, since the open waits for the host to apply its version and a stopped host never does.
- **Withholding and the restore member start at `Retire`** (picks 5 and 19). Absence from the state removes nothing on a host, but it would lock users out of the old machine before the replace began, and a restore member reaching the old instance's daemon would make it report its volume not empty; both wait until the engine has seen the old instance gone. `Admit` and `Retire` are each a no-op the second time, so an engine repeating a step after a restart bumps no version twice.
- **Withholding outlives its replace; the overlay does not** (replacement-overlay issue, option A). Once a `Retire` has run, the host's data is on no instance the host is told about, and sending its accounts and users again before a restore was admitted would give them a host whose data was never restored. So withholding lasts until the replace retired last is admitted, through its failure, a store-level `Finish`, a superseding replace and a delete, and a reused name, being a new `Seq`, inherits none. The restore overlay names one replace, so it lasts only while the host's current operation is that replace, running or failed; dropping it is a change to what the host is told and bumps the `Version`, so two documents at one version never differ in it. A replace keeping the volume of a withheld host is refused (`ErrWithheld`), since the volume it would keep was never admitted; a replace from backup and a delete stay open, so the host is never stranded. This replaces the build's interim guards, which refused a superseding replace, a delete and an early `Finish` of a retired, unadmitted replace from backup.
- **Restore paths are copied at `ReplaceHost`** (pick 6, the store's half). The daemon restores the union of these and the snapshot's manifest; the copy is taken before the old machine stops reporting.
- **A replace takes defaults, cancels restores, keeps the closed time and needs an address** (pick 25). The store fills a target the tool leaves out from the host in the same transaction, so no read races the write; pending partial restores are cancelled since the machine that would carry them out goes away; a host with no Elastic IP has nothing to move, so it is retried or deleted instead.
- **A stale report cannot undo a reset step.** `RetryHost` of a close stamps the rows it makes pending again, and a reported failure changes such a row only when it is not older than that stamp, so a report still carrying the failure from before the retry does not fail the close again. A reported done always settles a pending row: the row's stamp is accounts' clock and the step's time the host's, and comparing them for a done would hang a close or a replace forever behind a host clock a few seconds slow. A step row once done or failed is never changed by a report.
- **Only a close's failed steps are reset by a retry** (plan 3.5). The consequence is recorded: retrying a replace that failed at its restore step finds the failed rows still failed and fails again, so a new `replace_host` from backup, which starts afresh on a new volume, is the only way on; it is accepted although the host is withheld, and one keeping the volume is refused with `ErrWithheld`.
- **A backups delete is a row, and placement waits for it** (pick 11). As a kept-volume delete, it has no host or steps. `PlaceAccount` refuses a slug whose delete is in flight with `ErrBackupsDeleting`, since the engine's next page would otherwise delete a new account's first backups; `DeleteAccountBackups` refuses a live slug with `ErrAccountExists` in the same way, so the two never overlap.
- **The host prefix is the store's** (pick 20). `Desired` answers `protocol.HostPrefix` of the host's name and `Seq`, so a later host of a reused name never restores or deletes an earlier host's key backup, and neither the daemon nor `D13-daemon-endpoints` builds it.
- **Explains covers what a replace leaves.** A replaced instance and a data volume a replace kept are no longer held by the host row, so `Explains` also answers kept volumes and replacements' old ids, and the stray scan never reports them.
- **Two `Desired` changes bump nothing.** A close that stops running empties `backup.close` and a restore with a result leaves `backup.restores` without a version bump: the daemon learns of either on its next full answer, within `protocol.LongPoll`, and nothing it must do waits on them.
- **Departures from plan 2.14's table list, each local to the store.** `removed_backups` also holds the account's facts (snapshot, checked, error, databases, database errors, synced, written, reported), because `ListBackups` answers a removed account with the facts it had and the `account_backups` row is gone or about to be replaced by a later account of the slug. `restores.user` is `user_name`, so no column shares a word with a table or a common SQL keyword. Four indexes are added: `replacements_old_instance` and `replacements_old_volume`, since `Explains` looks a resource up by those columns as it does the hosts' ids; `removed_backups_host`, since `ListBackups` with a host keys removed rows by host and slug; and `restores_pending`, a partial index over pending rows by host and id, since `Desired` lists a host's pending restores on every answer and a host's restore rows accumulate.
- **Stopped hosts' accounts go stale; silence stays for running hosts** (pick 13). A stopped host is not backed up, so `BackupHealth` shows it after the threshold with no exception; `Health` and `MarkSilent` are unchanged.
- **A partial restore needs a running host; a closed one is fine** (pick 14). The daemon must be running to carry the request out, so `RequestRestore` refuses `ErrNotRunning` otherwise; closing changes no state, so a closed running host accepts restores.
- **Database staleness is measured by `Synced`** (pick 18): a database is stale when its newest write has not been streamed for longer than the threshold, which `Synced` measures, so an idle database stays healthy whatever its `Written`.
- **A replace from the volume takes no data size.** `ReplaceHost` with `ReplaceVolume` and a non-zero `target.DataGB` is an argument no consumer sends (`ErrUnreachable`): the tool refuses any `data_gb` with `KeepsVolumeSize` first, since the old volume is reattached as it is, and a size recorded for it would be a size the host does not have.
- **A failed backups delete's reason is readable** (root decision). `BackupsDeleteOf` answers the row in either state with its attempts, next try and reason, as `KeptVolume` answers a kept volume, and every `AccountBackup` carries the row's state in `Delete` and a failed one's reason in `DeleteReason` (root decision, agreed with `D07-tools`), so `backup_status` shows why a removed account's backups were not deleted from the one page it reads, with no read per row; `BackupsDeleteOf` stays for the engine's tests. Only a removed slug's entry carries them: an account placed again after its earlier backups' delete failed (`PlaceAccount` refuses only a delete in flight) answers them empty, since the failure concerns the earlier account's backups and `DeleteAccountBackups` refuses a live slug, so showing it on the new account would last forever; the failed row stays, and `BackupsDeleteOf` still answers it.
- **`RemoveAccount` answers the restores it cancelled** (root decision, for `D07-tools`). Its third result is the ids of the restore operations it set to cancelled, ascending, nil when none and on every refusal, so the tool tells one `operation.finished` per cancelled restore from the one transaction's answer (`ReplaceHost` answers the restores it cancels the same way), with no read before or after the write that a racing call could change; the same way an unplace's `Supersedes` names the `place` it cancelled. A list rather than one more field of `Operation`, since an account may have up to `valid.MaxRestoresPerHost` restores running; the list is bounded at its source, because `RequestRestore` counts unfinished restores, pending rows and running operations alike, so a restore reported done but not yet settled by the engine still holds its place under the cap, as does a pending row whose operation was finished, and no sequence of requests, reports and finishes grows the list or `Desired`'s pending restores past it.
- **A missing user of a files restore has its own error** (root decision). `ErrNoUser` lets the tool answer `NoUser` apart from `NoAccount`, both otherwise not found; a user of another account stays `ErrNotInAccount`.
- **Rollback cost: a replace-kept volume is a stray to the previous release.** Its `Explains` checks host rows only, so while rolled back its stray scan reports each volume a replace kept once (strays are told once); accepted, since the volume is listed and explained again after roll-forward.
- **A removing account gets no final backup and no restore** (root decision, with `D10-operations`). Close and replace record no step row for an account in `AccountRemoving`, `BackupSteps` answers none for one, a report's step for one changes nothing, and `backup.restore` names none, so it gets no restore credentials and no wait ever depends on it.
- **A database never synced is not restorable.** Its `oldest` is zero, so no time is restorable yet; the request is refused `ErrNotRestorable` rather than sent to a host that has nothing to restore.

- **The team template setting is stored, as the backup settings are, and has a writer** (team-template delivery; the owner's ruling). The backup settings have none (pick 3); this setting is changed through `set_team_template`, so the store has `SetTemplateSettings`, which takes each member as a pointer so that a call changing one member cannot undo a concurrent change of the other. It refuses what `valid` refuses with `ErrUnreachable`, an argument no consumer sends, since the tool checks first.
- **The template commit is set once, by gid and uid.** The daemon reports a commit in every report while the state names the account or user (`D11-protocol`); keeping the first one makes the record independent of report order and of a daemon that restarted, and matching by id, never by name, means a slug or name placed again starts empty.

## Consumer usage

Agent creates a host (`D07-tools`): `h, op, err := st.CreateHost(ctx, store.HostSpec{Type: "t4g.medium", RootGB: 20, DataGB: 50}, c)` answers `h.Name` `host01` in `store.HostProvisioning` and `op.Kind` `store.OpCreate`; the engine (`D10-operations`) pages `st.Runnable(ctx, now, after, store.BatchSize)`, calls `st.RecordStep(ctx, op.ID, step, op.Generation, now)` before each AWS call, `st.Advance(ctx, op.ID, store.Update{Step: next, AllocationID: id, EIP: ip})` after it, `st.Defer(ctx, op.ID, next, attempts)` on a transient error, and `st.Finish(ctx, op.ID, store.Update{AssociationID: assoc})`, after which `st.Host(ctx, "host01")` answers `store.HostRunning`. Daemon first boot (`D13-daemon-endpoints`): `h, err := st.HostByInstance(ctx, instanceID)`, then `ds, err := st.Desired(ctx, h.Name)`, waiting with `ch, release := st.Watch(h.Name)` when nothing changed. Report: `tr, err := st.RecordReport(ctx, h.Name, r, now)`, telling `host.synced` when `tr.Synced` and `host.apply_failed` when `tr.ApplyFailed`. Agent places an account: `a, op, err := st.PlaceAccount(ctx, "acme", "host01", c)` answers `store.AccountPending`; the engine records the Route 53 change with `st.RecordChange(ctx, op.ID, "acme", changeID)` and finishes `place`, after which `a.State` is `store.AccountActive`. Users: `u, err := st.AddUser(ctx, "acme", "bugs", store.Key{Type: t, Body: b, Line: l}, c)` answers `u.Pending` true until a report's applied version reaches `u.Version`; `st.Lock`, `st.Unlock`, `st.Delete(ctx, "acme", "daffy")` (refused with `store.ErrNotLocked` unless locked), after which a report applying it removes the row and `st.AddUser(ctx, "acme", "daffy", k, c)` succeeds again. Stop, start and resize: `st.StartHostOp(ctx, "host01", store.OpStop, store.Target{}, c)`, `store.OpStart`, and `st.StartHostOp(ctx, "host01", store.OpResize, store.Target{Type: "t4g.large", DataGB: 60}, c)`, which the engine reads back as `op.Target` and `op.ResumeState`, noting each modification with `st.NoteGrow(ctx, volume, now)`.
