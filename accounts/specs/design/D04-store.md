# D04-store

The record: `internal/store`, which owns accounts' tables in its SQLite database, `state/accounts.db`, and every read and write of them. The record is now the source of truth for the whole service (outcome 8 of ikigenba-ssh-hosts.md): hosts with their allowlists, pending unbans and the state of their own DNS records, accounts with their invites, users with their keys and admin flags, the operations that change AWS, the latest report of each host, the namespace, the counters that allocate names and numbers, and the strays and volume grows the engine notes. Nothing else holds a host's desired state; the daemon on each host makes the host match what this store answers (`D11-protocol`, `D14-accountsd`). This document declares the store's whole public surface: its types, every method with its signature, what each does, the errors every consumer tells apart, the one line every consumer answers when the database cannot be reached, and the migration. Which tool calls which method is the tools' (`D07-tools`); the pages read the same lists (`D06-pages`); the operations engine drives the operations (`D10-operations`); the daemon endpoints serve `Desired` and take `RecordReport` (`D13-daemon-endpoints`); the trail is `D08-trail`'s. Opening, migrating, transactions and the failure seam are appkit's `db`; `D01-layout-and-run-seam` resolves the path, declares the root package's `Migrations()` and builds the store. For step 2 of ikigenba-self-service-accounts.md, the box path, the store also answers which user a host's uid is (`ActiveUserByUID`, for `D13-daemon-endpoints`) and holds a guarded twin of every change a host's user may make from the box, which the box tools (`D19-box-tools`) call; it adds no table.

## One database, one writer

accounts is the only writer of its database. `store.New` builds a store over a handle and opens or creates nothing. What a store holds when its handle is closed is what a store over the next `db.Open` of the same path holds; a test proves the record that way, never by reading tables. A store whose handle is failing (`SetFailing(true)`), or closed, answers every call with an error matching `ErrUnreachable` and changes nothing. `Config.Now` is the clock every time the store stamps on its own is read from (created times, an operation's start, a step's start when the engine does not pass one); `Config.Rand` is where operation ids are drawn. `Run` hands in `Process.Now` and `Process.Rand`; the store has no default for either. Every write a method makes is one transaction: a call either changes everything its requirement says or nothing.

## Hosts

A host row is created by `CreateHost` in state `provisioning` with its `create` operation, named `host01`, `host02`, … from a sequence that never goes back, deleted hosts included, so `host100` follows `host99` and a name is never reused. The row is kept after deletion in state `deleted`: no read or list answers it, but its resource ids still explain what AWS holds (`Explains`) and its sequence number stays taken. The host's columns hold everything the landing and the silence sweep need, so neither ever decodes a report body: the state and failure reason, type and sizes, the resource ids AWS gave, the desired-state `Version` and the `Applied` version the host last reported, the `Attempted` version and whether the latest report carried an error, when it last reported and when it last entered `running`, and the `Alarm`, the last abnormal health an event told. `Health` computes the health word from those columns alone.

A host also holds an **allowlist** and its **pending unbans** (outcomes 6 to 12 of ikigenba-ssh-bans.md), both parts of its desired state. The allowlist is the addresses and CIDRs the host's fail2ban jail ignores: `Allow` adds an entry and `Disallow` removes one, each on a host in any state but `deleting` and `deleted`, so an edit made while a host is stopped applies when it runs; at most `valid.MaxAllowlistPerHost` entries. Every `Host` the store answers carries its allowlist, sorted. A pending unban is an address whose ban the daemon lifts on its next apply: `Unban` records one on a named running host, and `UnbanRunning` records one on every running host at once, all or nothing; at most `valid.MaxUnbansPerHost` per host. An unban is a pending change, not an operation: it carries the version that recorded it and lives until a report applies that version. The store takes each address or entry already in the canonical form `D17-names-keys-sizes`'s `valid.Address` or `valid.AllowEntry` gives; the tools canonicalize before they call, so a non-canonical one is an argument no consumer sends.

A host also has a name in DNS, `<host>.<hosts domain>`, an A record holding its Elastic IP (outcomes 8 to 10 of ikigenba-host-names.md). The record is not desired state: the daemon never sees it, and `Desired` leaves `D11-protocol`'s `Domain` empty, since the store knows no settings (`D13-daemon-endpoints` fills it). The store keeps two facts about it, on the host beside its other columns: `Change`, the Route 53 change id of the host's own record, as `Account.Change` is the account's, and `RecordReason`, why the record could not be made outside an operation, empty when nothing is wrong. An operation records its change with `RecordHostChange`, the twin of `RecordChange`: it needs the running operation `opID` to be on that host. The engine's scan, which heals the records of hosts made before this release and of records lost later (`D10-operations`), acts outside any operation, so it writes with `NoteHostRecord`, which sets the change when it has one and always sets the reason, an empty reason clearing it. Neither bumps the `Version`, wakes the long poll or touches a host's `State`, `Reason` or `Operation`: a conflict found by the scan is a note on a running host, never a failure. The hostname the host last reported is not a column: it is the `hostname` member of the stored latest report, read as `Report.Body.Hostname`, which `RecordReport` already keeps whole.

A host changes state only through the store's operation methods: `CreateHost` and `StartHostOp` move it into the transitional state of the operation they record, `Finish` moves it to the state the operation's kind ends in, `Fail` moves it to `failed` with a reason, and `RetryHost` moves a failed host back into the transitional state of its failed operation. The guards for each tool live here, in the same transaction as the write, so two racing tools never both pass: one host-kind operation at a time, only `retry_host` and `delete_host` act on a failed host, stop needs `running`, start needs `stopped`, resize needs something to grow or change and grows only, and delete needs every account on the host to be already `removing` (the delete guard, stated here once and cited by `D07-tools` and `D10-operations`).

## Operations

An operation is a recorded state machine (`D10-operations` owns the steps): its kind, its current step and generation, its status, the target of a resize, the state a resize returns to, the error a failure recorded, how many deferred attempts the current step has had, when it started, when the current step started, when it may next run, when it finished, and the caller who started it, kept whole as appkit's `identity.Caller` so the engine tells events as that caller. A new operation's step is empty: the engine begins at its kind's first step. `RecordStep` records the step about to run before the AWS call it makes; `Advance` records what the call learned and clears the attempts; `Defer` puts the step off and `NextTry` tells the engine when the earliest deferred step is due; `Finish` and `Fail` end the operation. The step's start time survives a repeated `RecordStep` of the same step and generation, so a step that keeps being retried still times out.

Operation ids are `op_` and 16 lowercase hex digits drawn from `Config.Rand`, redrawn on a collision as gdrive draws its `xfr_` ids.

## Accounts, users and the namespace

An account is placed on one host forever. `PlaceAccount` records it `pending` with its `place` operation; `Finish` of that operation makes it `active`, and `Fail` of it makes it `failed` with the reason, as a failed host operation does to its host; `RemoveAccount` makes a `pending`, `active` or `failed` account `removing` with an `unplace` operation, cancelling a `place` still running; `Finish` of the `unplace` deletes the row. A user belongs to one account, fixed at add. Account slugs and user names share one namespace across every host: a name is taken while its row exists and freed only when the row is gone. Gids and uids come from one counter starting at `FirstID` and are never reused.

Every change that alters what `Desired` answers for a host bumps that host's `Version` by one in the same transaction and stores the new version on what changed (the account's `Version` or `RemovedVersion`, the user's `Version`, an unban's version); a change that is already in effect (a key already held, a user already locked, an allowlist entry already held or not held, an address already pending) changes nothing and bumps nothing. A user is `Pending` while its version is above its host's applied version. Purging rows the host already applied (a user deleted and applied, an account removed and applied, an unban applied) bumps nothing.

## Admins and invites

Step 1 of ikigenba-self-service-accounts.md gives an account admins and lets a person join it by an invite link (outcomes 1 to 15). Both live only here; neither reaches a host, so `Desired` and the protocol do not change.

A user's **admin flag** is a fact about the user beside its state. `AddUser` records it false; `SetAdmin` sets or clears it on a user in any state but `UserRemoving`, answering whether it changed, and bumps no version, so the user's `Pending` and its host's `Version` stay as they were and the long poll is not woken. Every `User` the store answers carries it in `Admin`.

An **invite** belongs to one account and carries the admin flag the user it makes will get, its created and expiry times (`InviteLife`, 72 hours, after its creation) and, as `CreatedBy`, the `UserID` of the caller who made it. `CreateInvite` records one on an account that is not `removing` and answers it with its **token**, a secret drawn from `Config.Rand` in the same form as webhooks' secrets: `inv_` and 32 bytes in unpadded Crockford base32. The token is answered once; the store keeps only its SHA-256 and compares in constant time, and nothing it answers afterwards carries the token or a part of it. The invite's id, `iv_` and 16 hex digits, names it everywhere else: in `list_invites`, `revoke_invite` and the trail. An invite is **live** while it has not been used, revoked or deleted with its account and its expiry has not come; an account holds at most `MaxInvites` (20) live invites and `CreateInvite` refuses one more with `ErrTooManyInvites`. `Invites` lists an account's live invites, at most 20; every `Account` carries their number in `Invites`. `RevokeInvite` deletes a live invite. `InviteByToken` answers the invite a token names when it is usable, live on an account that is not `removing`, and `ErrNotFound` for anything else, unknown, used, revoked, expired or malformed alike, so the enrollment page (`D18-enrollment`) answers them all the same. `NameHeld` tells the page whether a name is taken without adding anything.

`Enroll` is the one write a guest reaches. In one transaction it checks the invite is usable, the name free and the host not full, then deletes the invite and creates the user exactly as `AddUser` would, with the invite's admin flag and the invite's `CreatedBy` as its own. So an invite makes at most one user: of two submissions racing on one token one succeeds and the other finds no invite. A refused submission (a taken name, a full host) leaves the invite usable, and opening the link (`InviteByToken`) consumes nothing (outcome 6).

There is no sweep. A used or revoked invite is deleted at once; `RemoveAccount` deletes every invite of the account, and a `Finish` of `unplace` or `delete` deletes any left for a slug whose row it deletes; an expired invite stays until the next `CreateInvite` of its account deletes it before counting. So an account never holds more than `MaxInvites` invite rows. Each invite also records its account's gid, and only an invite whose gid is the current account's counts or is usable, so a row left behind for a slug that was removed and placed again (by the previous release, which knows nothing of invites) never applies to the new account; `CreateInvite` deletes such rows with the expired ones.

## Acting from a host

Step 2 of ikigenba-self-service-accounts.md (outcomes 16 to 27) lets an SSH user manage their own keys, and an admin their account, from a host, through the box tools (`D19-box-tools`) that `D13-daemon-endpoints` serves at `protocol.BoxPath`. The store adds no table, column or migration for it: every method below reads and writes the tables `0002_hosts.sql` and `0004_invites.sql` already create, so `Desired` and the release before this one are untouched.

**Who is calling.** `ActiveUserByUID(ctx, host, uid)` turns the uid a host's daemon forwards into a user: the user holding that uid whose name is **active** (its state `active`, its account anything but `removing`) and whose account is on that host. Anything else, uid 0, a negative uid, a gid, a locked or deleted user, a user of another host, is `ErrNotFound`, which `D13-daemon-endpoints` answers 403. Pending and failed accounts count, as `Desired` sends them `active` and the host holds their group and users; a removing account never holds a user, since `RemoveAccount` refuses one that does. From then on the box knows the caller only as a name, `box.ActorPrefix` and the user's name in `Caller.UserID`, so the guarded methods below take the **actor** by name, and `UserNamed` answers a name's user whatever its state.

**Guarded twins.** Each change a box tool makes has a `*As` method that checks the actor's own standing in the same transaction as its write, then does exactly what its **central twin**, the method the central tools call, does for the actor's account:

- `AddKeyAs` and `RemoveKeyAs`, for every user on their own SSH user: the actor must be active, else `ErrNotActive`. `RemoveKeyAs` then refuses `ErrLastKey` when the key is the actor's only one, after `ErrKeyNotHeld`; central `RemoveKey` still removes a last key.
- `UsersAs`, `LockAs`, `UnlockAs`, `DeleteAs`, `SetAdminAs`, `CreateInviteAs`, `InvitesAs` and `RevokeInviteAs`, for admins: the actor must be an **active admin**, else `ErrNotAdmin`, before any other refusal, so a non-admin learns nothing about targets. `AdminCheck` answers the same guard alone, without writing, for the one box answer that writes nothing (a `create_invite` with no link base).
- A target user or invite outside the actor's account answers `ErrNotFound`, exactly as an unknown one, never `ErrNotInAccount`; an empty name or a malformed invite id answers the same, after the guard.
- `LockAs` and `DeleteAs` of the actor, and `SetAdminAs` demoting the actor, answer `ErrSelf` (outcome 3); a self-promotion is already in effect and answers unchanged. Delete still needs a locked user, as centrally.
- `CreateInviteAs` always makes an ordinary user's invite: it is `CreateInvite` with `admin` false.

A twin's successful call counts as its central twin's call wherever a requirement defines or counts by calls (an invite `CreateInviteAs` made is live and usable like any other). Because every guard sits in the write's transaction, a lock, delete or demotion that races a box call always wins. The central methods are unchanged: they take no actor and the central tools keep full control (outcome 4).

**Recorded callers are capped.** Every method that records a caller's `UserID` (`CreateHost`, `StartHostOp`, `RetryHost`, `PlaceAccount`, `RemoveAccount`, `AddUser`, `CreateInvite` and `CreateInviteAs`) refuses one longer than `valid.MaxUserIDBytes` (64 bytes, `D17-names-keys-sizes`) with `ErrUnreachable`: an argument no consumer sends, since auth's ids are 26 characters and a box actor's is `ssh:` and at most 32 bytes. The cap bounds what a box `users` or `list_invites` answer can carry in `created_by`, which keeps every box answer under `protocol.MaxBoxAnswer`. `Enroll` records the invite's `CreatedBy`, already capped; an operation's `Email` and `RequestID` reach no box answer and are not capped.

## Desired state and reports

`Desired` builds `D11-protocol`'s `protocol.DesiredState` for a host from its rows, its `allowlist` and `unban` included, each sorted; `D13-daemon-endpoints` fills in the daemon digest. `RecordReport` keeps the latest report of a host and folds it into the host's columns. A report can only ever misreport its own host: its applied version is clamped to the host's own version and never goes backwards, sign-ins and slices count only for the host's own users and accounts, and sign-in times never lie in the future (the trust argument of `D12-host-identity`). A report that applies a removal deletes the removed users and frees their names, and one that applies an unban's version deletes that unban, so an unban recorded at version 5 stays in `Desired` until a report applies 5. The report itself, its bans and the allowlist the host applied included, is kept as `D11-protocol`'s `DecodeReport` bounded it. `RecordReport` answers a `Transition` from which `D13-daemon-endpoints` tells `host.synced` and `host.apply_failed`; `MarkSilent` marks running hosts that stopped reporting, and `D10-operations` tells `host.silent` for each.

## Strays, grows and watching

`NoteStray` records a resource the stray scan could not explain, answering true only the first time so the event is told once; `Explains` says whether any host row, deleted ones included, holds a resource id. `NoteGrow` records each volume modification accounts started, and `StartHostOp` refuses a resize that would grow a volume already grown `MaxGrows` times within `GrowWindow` (EBS allows four modifications per volume in a rolling 24 hours); expired rows are pruned by the next `NoteGrow` of the same volume and by `PruneGrows`, which the engine's scan pass calls in pages. `Watch` lets the daemon endpoints' long poll wait for a host's version to change; it is in-process only.

## Errors

`ErrUnreachable` covers every failure of the database and every argument no consumer sends, an address or allowlist entry not in canonical form included; consumers answer it with `Unreachable`, never quoting the cause. `ErrNotFound` says the named entity does not exist (or the host is deleted, for reads). `ErrTaken` says a name is held in the namespace. `ErrConflict` says a state guard failed; each guard has its own error that matches `ErrConflict` under `errors.Is`, so `D07-tools` picks the refusal it words without re-reading state, and `D08-trail`'s `Result` classifies them all as refused; the bans add `ErrTooManyUnbans` and `ErrAllowlistFull` for the two caps, and reuse `ErrNotRunning` and `ErrHostGone`; the invites add `ErrTooManyInvites` for their cap, and `Enroll` reuses `ErrTaken` and `ErrAccountFull` as `AddUser` answers them. Two not-found cases are told apart the same way: a user that exists but in another account (`ErrNotInAccount`) and a key the user does not hold (`ErrKeyNotHeld`), both matching `ErrNotFound`. `RecordHostChange` answers `ErrNotFound` and `ErrConflict` as `RecordChange` does, but checks its operation (not found, then not running) before its host, as its requirement lists, and `NoteHostRecord` answers `ErrNotFound` for a host that does not exist or is deleted. The guarded twins add `ErrNotActive` (the actor is not active), `ErrNotAdmin` (the actor is not an active admin), `ErrSelf` (an admin locking, deleting or demoting themselves) and `ErrLastKey` (the actor's only key), each matching `ErrConflict`, and answer a target outside the actor's account `ErrNotFound`, never `ErrNotInAccount`. A caller `UserID` longer than `valid.MaxUserIDBytes` is an argument no consumer sends. Precedence: a done context and a failing or closed handle first, then an argument no consumer sends, then not found, then the method's guards in the order its requirement lists; the guarded twins put their actor guard (`ErrNotActive`, `ErrNotAdmin`) right after the arguments no consumer sends, before not found.

## The migration

The schema is `0001_accounts.sql`, unchanged, plus `0002_hosts.sql`, which only adds tables and indexes: `hosts`, `operations`, `accounts`, `ssh_users`, `ssh_keys`, `reports`, `names`, `counters`, `strays` and `volume_grows`, with these indexes (a partial unique index on a live host's instance id, operations by status and next try, accounts by host and slug, users by account and name). The old `groups` and `users` tables are left in place and never read or written: this release is the expand half of outcome 27, and the release before it runs on this schema, since appkit's `db` opens a database whose applied migrations it does not know with a warning only. The next release drops them. `0003_bans.sql` follows, again only adding tables and indexes, two tables for the hosts' allowlist entries and pending unbans, and naming no table `0001` or `0002` creates: a host recorded before it has an empty allowlist and no pending unbans, and the release before this one runs on it, since nothing that release writes touches the new tables. `0004_invites.sql` follows the same rule, only adding tables and indexes and naming no table `0001` to `0003` creates: `user_admins`, one row per admin's uid, so a user is an admin exactly when a row holds its uid, and `invites`, keyed by id, with a unique token hash and the account's slug and gid, the admin flag, the created and expiry times and the creator, indexed by account and created time. No existing table changes shape, so the release before this one runs on it unchanged: it never reads or writes the new tables, a user it adds has no admin row and so is not an admin, and a uid it purges leaves an admin row that applies to no one, since uids are never reused. The column lists are the build run's, inside the requirements below. Step 2 (the box path) adds no migration and changes no table: the uid, state, account, admin row and invite columns it reads are already there. `0005_host_records.sql` follows the same rule, only adding tables and indexes and naming no table `0001` to `0004` creates: `host_records`, at most one row per host, keyed by the host's name, holding the host's record change id and its record reason. A host without a row has an empty `Change` and `RecordReason`, so a host recorded before it, or one the release before this one creates, reads as having neither until the engine records a change or the scan notes one. No existing table changes shape, so the release before this one runs on it unchanged: it never reads or writes `host_records`, and a host it deletes keeps a row no read answers, since a deleted host is answered by no read and its name is never reused.

## Memory

Every list takes a `limit` and answers at most that many rows, read by a keyset query over an index; a page asks for one row more than it shows (`D06-pages`, `D07-tools`), so the store accepts up to `paging.MaxLimit + 1`. Passes over operations, silent hosts and grows are in pages of the caller's limit (`BatchSize` for the engine). `AccountsOn`, `UsersOf` and `Desired` answer every row of one host or account, bounded by the caps the store itself enforces (`valid.MaxAccountsPerHost`, `valid.MaxUsersPerHost`, `valid.MaxKeysPerUser`); `Desired` adds at most `valid.MaxAllowlistPerHost` allowlist entries and `valid.MaxUnbansPerHost` unban addresses, and every `Host` carries at most `valid.MaxAllowlistPerHost` entries. `Unban`, `Allow` and `Disallow` each hold one host with its at most 50 entries and 50 unbans; `UnbanRunning` reads the running hosts one at a time in its one transaction, holding one host and its unbans at once and a count, never a list of hosts, whatever the number of hosts the store holds. This bound is design guidance, not a requirement: no test can see it by use. A report is one body of at most `protocol.MaxReportBytes`. `Watch` holds one channel per waiter. `Invites` answers at most `MaxInvites` invites, which the cap bounds and a requirement states; `InviteByToken`, `RevokeInvite` and `Enroll` each hold one invite (and `Enroll` one user with its one key); `CreateInvite` holds a count, never a list; `SetAdmin` and `NameHeld` hold one user or one name. Since nothing sweeps, the invite rows of an account are bounded by the same cap: at most `MaxInvites`, expired ones included. The box path's methods hold no list beyond their twins': `UserNamed`, `ActiveUserByUID` and `AdminCheck` each hold one user; `AddKeyAs` and `RemoveKeyAs` hold the actor with its at most `valid.MaxKeysPerUser` keys; `LockAs`, `UnlockAs`, `DeleteAs` and `SetAdminAs` hold the actor and one target; `CreateInviteAs` holds the actor, one invite and a count, and `RevokeInviteAs` the actor and one invite; `UsersAs` answers what `UsersOf` answers, at most `valid.MaxUsersPerHost` users with their keys, and `InvitesAs` what `Invites` answers, at most `MaxInvites`, both entry caps stated by requirements. Every answer's size is bounded too: no caller `UserID` the store records exceeds `valid.MaxUserIDBytes`. `RecordHostChange` holds one operation and one host, and `NoteHostRecord` one host; each writes one `host_records` row, which it replaces, so a host keeps at most one row, one change id and one reason, however often the scan notes it. These bounds are design guidance, not requirements: no test can see them by use, since none reads tables or what a method holds. Only the engine calls them (`D10-operations`), with a Route 53 change id the cloud answered and a reason that is one of its reason constants, so each stored value's size is bounded by what the engine passes and the store sets no cap of its own. Every `Host` carries those two strings; the hostname a host reported stays inside its one stored report.

## Recorded decisions

- **The record is the source of truth** (outcome 8). Previous design: the record held only what accounts created, and the host (opsctl) held keys, memberships, states and sign-ins. That host is gone; there is nothing else to agree with.
- **Guards in the store, one error per guard.** `ErrConflict` stands for every failed guard; each guard also has its own error matching it, so the tool words the right refusal from one transactional answer instead of a racy read before the write. Sibling: gdrive's store answers `ErrEnded` for its one guard.
- **A deleted host is not found to reads and gone to writes.** `Host`, `HostByInstance` and the lists answer `ErrNotFound` for it; `StartHostOp`, `RetryHost`, `PlaceAccount`, `Unban`, `Allow` and `Disallow` answer `ErrHostGone`, which `D07-tools` words as `HostGone`. `Allow` and `Disallow` also answer it for a `deleting` host, as `PlaceAccount` does.
- **An unban is a pending change, not an operation** (outcome 7). It is one repeatable command on the host, so it is a row with a version, like a user change, and the host's applied version retires it; it has no id, step or failed state. It needs a running host (outcome 8): a ten-minute ban does not outlive a stop, so a named host that is not running is refused with `ErrNotRunning` and `UnbanRunning` skips it. The allowlist, by contrast, is lasting desired state, accepted on any host not being deleted.
- **Idempotent edits follow `AddKey`.** An address already pending, an entry already held, or an entry not held is answered unchanged with a nil error and no bump; the already-in-effect check comes before the cap, so a full host still answers an address it already holds.
- **The unnamed unban is all or nothing.** `UnbanRunning` is one transaction over every running host: when any running host that does not already hold the address is at `valid.MaxUnbansPerHost`, it refuses with `ErrTooManyUnbans` and records nothing, so an agent never has to work out which hosts took it. It answers a count of the running hosts, which `D07-tools` answers, not a list, so the answer stays bounded whatever the number of hosts.
- **Departure from shape/ Bounded work: `UnbanRunning`'s one transaction spans every running host.** The rule asks that no transaction span the set. All or nothing needs one transaction; its memory stays bounded (one host and its unbans at a time, and a count), and the set is the business's hosts, each an EC2 instance it pays for, tens and not thousands. Paging the hosts would let a refusal leave earlier hosts changed.
- **The store takes canonical forms only.** An address or entry is canonicalized by `valid` in `D07-tools` before the call; one the store would canonicalize differently is an argument no consumer sends (`ErrUnreachable`), so equal strings are the same entry and the store never rewrites what the tool echoes.
- **Overlapping allowlist entries are both kept.** `192.0.2.7` beside `192.0.2.0/24` is a second entry: equality is by canonical string, and merging would surprise a `disallow_ip` of either.
- **The engine owns step names; the store records them.** A new operation's step is empty, the engine's cue to begin; the store never interprets a step name.
- **Finish and Fail know the kind's end state.** The store, not the engine, moves a host to `running`, `stopped`, the resize's resume state or `deleted`, and an account to `active` or gone, so the state machine's end states hold whatever engine calls them.
- **The step's start time survives a repeated `RecordStep`** of the same step and generation, so `StepTimeout` counts from the step's first attempt.
- **Alarms persist until in sync.** `silent` and `error` stay until a report applies the current version, so `host.synced` is told once per episode and a host that goes silent again while still marked silent is not told twice.
- **Purges bump nothing.** Deleting a user or account row whose removal the host already applied, or an unban whose version it applied, changes nothing the host must do, so it does not wake the long poll for an empty cycle.
- **The Route 53 change id lives on the account** (`Change`), since a host delete records one change per removing account.
- **An unplace records what it superseded** (`Operation.Supersedes`), so the tool that cancelled a running `place` tells its `operation.finished` with status `cancelled` from the answer alone.
- **A failed account is removed, not retried.** A `failed` account (its `place` failed) and a `removing` account whose `unplace` failed are both taken on by `remove_account`: `RemoveAccount` starts an `unplace`, which deletes the account's record only when it points at the host and waits for the host to drop the group; with one running it answers `ErrAccountRemoving`. The agent then creates the account again. This is outcome 10's retry for an account. A retry tool was rejected: it would add a tool, a store method and its errors, and repeating a `place` from its recorded step does not cure its usual failure, a record at the name that is not the host's (`ReasonRecordConflict`). Until it is removed a `failed` account keeps its group on the host (`Desired` sends it `active`) and takes users as a `pending` one does.
- **`RetryHost` keeps the generation**: a create failed with `ReasonTerminated` cannot be retried into a fresh launch; it is deleted instead (`D10-operations`).
- **The last key may be removed centrally, not from the box.** A user with no key cannot sign in, which is the central caller's choice; `remove_key` answers the keys left (`D07-tools`). From the box, `RemoveKeyAs` refuses the actor's last key with `ErrLastKey` (outcome 21), so a user cannot lock themselves out of the host they are on.
- **`CreatedBy` is the creating caller's `UserID`**, kept as given, for a host, account, user or invite: an auth user id for what a central tool created, `box.ActorPrefix` and the SSH user's name (`ssh:bugs`) for an invite a box call created (`D19-box-tools`), and for an enrolled user its invite's. auth's ids carry no `:`, so the two never collide. An operation keeps the whole caller because its events are told as that caller (gdrive's transfers keep user id, email and request id the same way).
- **Recorded callers are capped at `valid.MaxUserIDBytes`.** The box answers lists that carry `created_by`, and the answer must stay under `protocol.MaxBoxAnswer` without paging; capping what the store records (64 bytes, above auth's 26 and the box's 36) bounds them by construction. A longer caller is an argument no consumer sends (`ErrUnreachable`), reachable only by a forged identity header; each recording method's own requirement states the cap.
- **Guarded twins, not an actor on the central methods** (replaces step 1's "the store is actor-free"). Step 2's rules for a host's user (no self-lock, self-delete or self-demotion, no removing one's own last key, admin tools for admins only, the account always the actor's) must hold atomically with the write, so each is checked inside a new `*As` method's transaction, which then does exactly what its central twin does. The central methods and their requirements do not change and keep full control (self-service outcome 4); sharing at the store keeps one copy of every guard, where sharing tool bodies would add contract to `D07-tools` and still need these methods.
- **Every box write checks the actor's own standing.** Key writes check that the actor is active, admin writes and reads that the actor is an active admin, in the same transaction, so a lock, deletion or demotion that commits first always wins over a box call already in flight.
- **A foreign target is unknown.** A user or invite of another account answers `ErrNotFound`, exactly as one that does not exist, so an admin learns nothing outside their account; an empty name or malformed invite id answers the same after the guard, so the guard is always the first refusal a non-admin sees.
- **Resolution counts pending, active and failed accounts, not removing ones.** `Desired` sends the first three `active`, so the host holds their group and users and the daemon's own check on the state it fetched agrees; a removing account holds no user anyway.
- **The actor is a name, not a uid.** Names are unique system-wide (`D17-names-keys-sizes`), and the box server sees only `Caller.UserID`; `D13-daemon-endpoints` resolves the uid once with `ActiveUserByUID` and passes the name on.
- **An admin may lock, delete or demote another admin** (outcomes 2 and 23). The `*As` guards forbid only acting on oneself (`ErrSelf`, outcome 3); any other active admin of the account is an ordinary target.
- **Invites survive their maker.** An invite stays live when the admin who made it is later demoted or locked, as it does centrally: the invite is the approval, and any admin of the account may revoke it. Nothing deletes or hides an invite on its maker's change.
- **The same-transaction guards are not provable by a deterministic test.** That `AddKeyAs`, `RemoveKeyAs`, the admin guard, the target and self rules, `CreateInviteAs` and `RevokeInviteAs` judge the actor in the write's own transaction would need a race the test cannot schedule; so it is guidance for the build, not a requirement: each of those methods judges the actor's standing, the target and the self rules in the same transaction as the read or write it makes, and their requirements state only the refusals and the unchanged store a deterministic test proves. The weakness is accepted, as the central guards' concurrency is.
- **The removing clause of "active" stays.** No permitted test can reach a user of a removing account, since `RemoveAccount` refuses an account that has users; the clause is kept so the definition does not lean on that other guard.
- **Ids** `op_` + 16 hex from `Config.Rand`, redrawn up to 8 times, as gdrive's `xfr_`.
- **Departure: operations survive a restart.** gdrive, gmail and scripts finish interrupted work `failed` or `interrupted` at start; outcome 11 requires resume, so the store keeps every running operation as it was and the engine continues it (`D10-operations`).
- **Departure: strays are a table**, so each unexplained resource is told once across restarts; devctl reports duplicates on every listing instead.
- **Departure: the old tables stay unused**, not dropped (outcome 27, expand). accounts' previous design kept `groups` and `users` as its whole record.
- **Desired state does not change** (self-service outcome 19). The admin flag and the invites live only in the store; `Desired` answers what it answered before (R-263N-396L stands unchanged), the protocol keeps its version, and `SetAdmin`, `CreateInvite` and `RevokeInvite` bump no version. Only `Enroll`, which creates a user, bumps one, as `AddUser` does.
- **The previous release runs on this schema.** `0004_invites.sql` only adds two tables and changes no existing one (expand then contract). The admin flag is a table of uids rather than a column on the users, so a user the previous release adds is simply not an admin, and a row its purge leaves names a uid never reused. It knows nothing of invites, so its `RemoveAccount` leaves them in place. While that account is `removing`, this release may still count and list those invites (but never accept their tokens, since the account is removing) until a `Finish` of its `unplace` or `delete` deletes them; no test can reach this, and it is accepted. Once the row is gone, the gid each invite records keeps such a row from applying to a later account at the same slug, and the next `CreateInvite` of that slug deletes it; for a slug never placed again the rows stay, at most `MaxInvites` per slug, unusable and invisible.
- **Rollback protection the build keeps, not a requirement.** Each invite records its account's gid, and only an invite whose gid is the current account's counts, is listed or is usable; `CreateInvite` deletes an account's invites of another gid with its expired ones, and a `Finish` of an `unplace` or `delete` deletes any invite left for a slug whose row it deletes. Within this release `RemoveAccount` already deletes every invite, so no test can reach either: only the previous release, which knows nothing of invites, leaves such rows. They are stated here because a clause no permitted test can reach is not a requirement.
- **The token is kept as a hash.** Only the SHA-256 of a token is stored, and a lookup compares in constant time, so a copy of the database does not hand out usable links; webhooks' bearer secrets are the precedent. Neither is provable by use, since no test reads tables or times comparisons; what is provable is that nothing the store answers carries the token after `CreateInvite`.
- **An invite is consumed by success only** (outcome 6). `InviteByToken` reads; `Enroll` deletes the invite in the transaction that creates the user, so a refused submission leaves it usable and two racing submissions make one user.
- **One not-found for every unusable link** (outcome 13). Unknown, used, revoked, expired, malformed, for a removing account: `InviteByToken` and `Enroll` answer `ErrNotFound` for all, and `RevokeInvite` likewise, so no caller can tell them apart.
- **No sweep for invites.** Used and revoked invites are deleted at once and expired ones by the account's next `CreateInvite` or its removal, so the rows stay within `MaxInvites` per account without a background pass. An expired invite of an account that never makes another lingers until the account is removed, unusable and invisible.
- **Expiry is judged at each use, by that use's own clock.** An invite is live while it is held and its `Expires` is after the call's stamp; the cleanup inside `CreateInvite` deletes only the account's invites expired at that call's own stamp. Nothing more is promised about a clock that moves backward: an invite a cleanup deleted stays deleted, whatever a later stamp says.
- **A used, revoked or expired token never works again because a fresh token is fresh randomness.** `Enroll` and `RevokeInvite` delete the invite, and a token is 32 random bytes from `Config.Rand`, so no rule forbids minting a token again: with real randomness a repeat does not happen, and a test's constant source that repeats one is outside the guarantee.
- **Secrecy is about what accounts minted or stored.** No answer and no event carries a token, its hash or a stored key beyond the one answer that hands the token out (`CreateInvite`'s and `CreateInviteAs`'s second result, and the link built from it). A value the requester supplied, echoed in the same answer, is not a disclosure, and a value that merely coincides with part of a token is not one either; the tests prove the rule with markers and random sources chosen independently of every other value. The trail never carries a token or a key, or part of either, whether accounts minted it or the requester supplied it.
- **An enrolled user's `CreatedBy` is its invite's `CreatedBy`**: the invite is the approval (outcome 8), and whoever made it, a person's auth user id or a box admin's `ssh:` name, is who brought the user in.
- **Departure from shape/ paging: `Invites` takes no limit.** It answers every live invite of one account, bounded by `MaxInvites`, as `UsersOf` is bounded by its cap.
- **The hostname a host last reported is its stored report's `hostname`, not a column** (root decision; departs from the wording of decision A1 of ikigenba-host-names-decisions.md, which names it among the new store state). `RecordReport` already keeps the latest report whole, and `D11-protocol`'s `Report` now carries `Hostname`, so `Report(ctx, host)` answers it as `Body.Hostname`; a copy in a column would be state nothing reads, since neither the landing nor the silence sweep needs it (the pages and tools read it from the report, `D06-pages`, `D07-tools`). A1's choice of a new table stands for the state that is new.
- **The host's record state is a new table, `host_records`, not new columns on `hosts`** (decision A1). Every migration after `0001` only creates (R-29RC-8KEO, R-CQHV-FS6Y), so the release before this one runs on the schema and a rollback loses nothing: expand then contract, as `0003_bans.sql` and `0004_invites.sql` did. An `ALTER TABLE hosts` would also run on the previous release, but the CREATE-only rule keeps every migration provable by one shape of requirement.
- **The host's own record's change id lives on the host** (`Host.Change`), beside the accounts' (`Account.Change`): a create records one change for the host's record, and a delete one for the host's record besides one per removing account.
- **Two writers, two methods.** `RecordHostChange` is for an operation's steps and refuses a change from an operation that is not running or not on that host, as `RecordChange` does, so an engine holding a stale operation cannot write; `NoteHostRecord` is for the scan, which runs outside any operation and must also set and clear the reason. Folding them into one would either let the scan pass an empty operation id, an argument no consumer otherwise sends, or let an operation's step set a reason no operation shows.
- **A record conflict found outside an operation is a note, not a failure** (decision A2). `NoteHostRecord` changes no `State`, `Reason`, `Operation` or `Version`, so a running host keeps running and its desired state is untouched; `D06-pages` and `D07-tools` show `RecordReason` where `Reason` is empty.
- **`NoteHostRecord` on a deleted host is not found**, as reads treat a deleted host; the scan checks only live hosts, so it never asks.
- **No delete of record state.** A host row is never deleted, only marked `deleted`, and its name is never reused, so its `host_records` row can never apply to another host and no read answers it; the build may leave it. The record itself is deleted by the delete's `StepUnrecord` (`D10-operations`).

## Consumer usage

Agent creates a host (`D07-tools`): `h, op, err := st.CreateHost(ctx, store.HostSpec{Type: "t4g.medium", RootGB: 20, DataGB: 50}, c)` answers `h.Name` `host01` in `store.HostProvisioning` and `op.Kind` `store.OpCreate`; the engine (`D10-operations`) pages `st.Runnable(ctx, now, after, store.BatchSize)`, calls `st.RecordStep(ctx, op.ID, step, op.Generation, now)` before each AWS call, `st.Advance(ctx, op.ID, store.Update{Step: next, AllocationID: id, EIP: ip})` after it, `st.Defer(ctx, op.ID, next, attempts)` on a transient error, and `st.Finish(ctx, op.ID, store.Update{AssociationID: assoc})`, after which `st.Host(ctx, "host01")` answers `store.HostRunning`. Daemon first boot (`D13-daemon-endpoints`): `h, err := st.HostByInstance(ctx, instanceID)`, then `ds, err := st.Desired(ctx, h.Name)`, waiting with `ch, release := st.Watch(h.Name)` when nothing changed. Report: `tr, err := st.RecordReport(ctx, h.Name, r, now)`, telling `host.synced` when `tr.Synced` and `host.apply_failed` when `tr.ApplyFailed`. Agent places an account: `a, op, err := st.PlaceAccount(ctx, "acme", "host01", c)` answers `store.AccountPending`; the engine records the Route 53 change with `st.RecordChange(ctx, op.ID, "acme", changeID)` and finishes `place`, after which `a.State` is `store.AccountActive`. Users: `u, err := st.AddUser(ctx, "acme", "bugs", store.Key{Type: t, Body: b, Line: l}, c)` answers `u.Pending` true until a report's applied version reaches `u.Version`; `st.Lock`, `st.Unlock`, `st.Delete(ctx, "acme", "daffy")` (refused with `store.ErrNotLocked` unless locked), after which a report applying it removes the row and `st.AddUser(ctx, "acme", "daffy", k, c)` succeeds again. Stop, start and resize: `st.StartHostOp(ctx, "host01", store.OpStop, store.Target{}, c)`, `store.OpStart`, and `st.StartHostOp(ctx, "host01", store.OpResize, store.Target{Type: "t4g.large", DataGB: 60}, c)`, which the engine reads back as `op.Target` and `op.ResumeState`, noting each modification with `st.NoteGrow(ctx, volume, now)`. Restart: the next `Run` pages `st.Runnable` from the start and every running operation is there at its recorded step and generation. Failure and retry: `st.Fail(ctx, op.ID, reason)` leaves the host `store.HostFailed` with `h.Reason`; `st.RetryHost(ctx, "host01", c)` resumes it. Delete: `st.StartHostOp(ctx, "host01", store.OpDelete, store.Target{}, c)` answers `store.ErrHasAccounts` until `st.RemoveAccount(ctx, "acme", c)` made the account `store.AccountRemoving`; the engine walks `st.OperationsOf(ctx, "host01", after, store.BatchSize)` and its `Finish` leaves the host hidden and the account gone. Silence: `hs, err := st.MarkSilent(ctx, now, after, store.BatchSize)`, one `host.silent` per answered host. Pages: `st.ListHosts(ctx, after, 26)`, `st.ListAccounts`, `st.ListUsers(ctx, "", afterAccount, afterName, 26)`, each row's health from `store.Health(h, now)`. Bans (`D07-tools`, after `valid.Address` or `valid.AllowEntry` canonicalized the argument): `h, err := st.Unban(ctx, "host01", "192.0.2.7")` answers `h.Version` one higher, `store.ErrNotRunning` for a stopped host and `store.ErrTooManyUnbans` at the cap; `n, err := st.UnbanRunning(ctx, "192.0.2.7")` answers how many running hosts now hold it; `st.Desired(ctx, "host01")` lists it in `unban` until `st.RecordReport` applies that version. `h, err := st.Allow(ctx, "host01", "198.51.100.0/24")` answers `h.Allowlist` holding the entry, `store.ErrAllowlistFull` at the cap and `store.ErrHostGone` for a host being deleted; `st.Disallow(ctx, "host01", "198.51.100.0/24")` removes it. Admins and invites (`D07-tools`, `D18-enrollment`): `u, changed, err := st.SetAdmin(ctx, "acme", "bugs", true)` answers `u.Admin` true and `changed` true, with `u.Version` and `u.Pending` as they were; `inv, token, err := st.CreateInvite(ctx, "acme", true, c)` answers `inv.ID` satisfying `store.ValidInviteID`, `inv.Expires` `store.InviteLife` after `inv.Created`, and `token` satisfying `store.ValidToken`, which the tool puts in the link and nowhere else; a twenty-first answers `store.ErrTooManyInvites`. `invs, err := st.Invites(ctx, "acme")` lists at most `store.MaxInvites`; `st.Account(ctx, "acme")` answers their number in `Invites`; `st.RevokeInvite(ctx, inv.ID)` answers the invite and then `store.ErrNotFound`. The page: `inv, err := st.InviteByToken(ctx, token)` on a GET (`store.ErrNotFound` for anything unusable); on a POST, `held, err := st.NameHeld(ctx, "daffy")` and then `inv, u, err := st.Enroll(ctx, token, "daffy", store.Key{Type: t, Body: b, Line: l})`, which answers `u.Admin` equal to `inv.Admin`, `u.CreatedBy` equal to `inv.CreatedBy` and `u.Pending` true, or `store.ErrNotFound`, `store.ErrTaken` or `store.ErrAccountFull`; after success the same token answers `store.ErrNotFound`.

The box path (`D13-daemon-endpoints`, `D19-box-tools`): the daemon endpoint resolves the forwarded uid with `u, err := st.ActiveUserByUID(ctx, h.Name, uid)`, answering 403 on `store.ErrNotFound`, and hands the box server the caller `ssh:` + `u.Name`; the box tool takes the actor `bugs` back off that caller. User tools: `u, err := st.AddKeyAs(ctx, "bugs", k)` answers what `st.AddKey(ctx, "acme", "bugs", k)` would, or `store.ErrNotActive` once `bugs` is locked; `u, left, err := st.RemoveKeyAs(ctx, "bugs", k)` answers `store.ErrLastKey` for `bugs`'s only key; `keys` reads `st.UserNamed(ctx, "bugs")`. Admin tools, with `bugs` an active admin of `acme`: `us, err := st.UsersAs(ctx, "bugs")` and `invs, err := st.InvitesAs(ctx, "bugs")` answer `acme`'s users and live invites; `st.LockAs(ctx, "bugs", "daffy")`, `st.UnlockAs`, `st.DeleteAs(ctx, "bugs", "daffy")` (`store.ErrNotLocked` unless locked) and `u, changed, err := st.SetAdminAs(ctx, "bugs", "daffy", true)` act on `daffy` of `acme`, answer `store.ErrNotFound` for a user of any other account, and `store.ErrSelf` for `st.LockAs(ctx, "bugs", "bugs")`, `st.DeleteAs(ctx, "bugs", "bugs")` and `st.SetAdminAs(ctx, "bugs", "bugs", false)`; `inv, token, err := st.CreateInviteAs(ctx, "bugs", identity.Caller{UserID: "ssh:bugs"})` answers an invite of `acme` with `Admin` false and `CreatedBy` `ssh:bugs`; `st.RevokeInviteAs(ctx, "bugs", inv.ID)` revokes it, and answers `store.ErrNotFound` for another account's invite. When the link base is missing the tool writes nothing and asks `err := st.AdminCheck(ctx, "bugs")` to choose between its two refusals. Every admin method answers `store.ErrNotAdmin` first when `bugs` is not an active admin.

Host names (`D10-operations`, `D06-pages`, `D07-tools`): a create's record step makes the A record and calls `st.RecordHostChange(ctx, op.ID, "host01", changeID)`, then waits until `h.Change` is in sync; once the operation has finished the same call answers `store.ErrConflict`, and one naming another host `store.ErrNotFound`. A delete's unrecord step does the same for the host's own record. The scan, outside any operation, pages `st.ListHosts(ctx, after, store.BatchSize)` and for a live host with an `EIP` calls `st.NoteHostRecord(ctx, h.Name, changeID, "")` after creating a missing record, `st.NoteHostRecord(ctx, h.Name, "", reason)` when the name is held by another record, and `st.NoteHostRecord(ctx, h.Name, "", "")` to clear a reason once the record is right; none of these changes `h.State`, `h.Reason` or `h.Version`. Pages and tools read `h.Change` and `h.RecordReason` from `st.Host` and the lists, showing `h.Reason`, or `h.RecordReason` when that is empty, and the reported hostname from `rep, err := st.Report(ctx, "host01")` as `rep.Body.Hostname`. `st.Desired(ctx, "host01")` answers an empty `Domain`; `D13-daemon-endpoints` sets it.

A test opens its own database with `db.Open` and the root package's `Migrations()` in a temporary directory, builds `store.New(d, store.Config{Now: clock, Rand: rnd})` with a clock it moves and a random source it controls, drives the methods, flips `d.SetFailing(true)` or closes `d`, and reopens the path to prove what persists. A test of the migration reads `fs.ReadFile(accounts.Migrations(), "0002_hosts.sql")`, `"0003_bans.sql"`, `"0004_invites.sql"` and `"0005_host_records.sql"`; a test of the old tables' neglect drops them through `DB.Write` on its own database.
