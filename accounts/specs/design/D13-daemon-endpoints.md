# D13-daemon-endpoints

The accounts side of the daemon protocol. This document owns package `internal/daemonapi`, the handler `D03-serve` mounts at `/accountsd` and at every path beginning `/accountsd/`. It answers three paths, all declared in `D11-protocol`:

- `BinaryPath` streams the daemon binary that sits beside accounts' own executable. No identity is needed (outcome 21; outcome 23's download half).
- `StatePath` answers a host's desired state by long poll (outcome 21, outcome 22's pull).
- `ReportPath` takes the host's report (outcome 24's intake). From the change each report makes, it tells `host.synced` and `host.apply_failed` (outcome 15's health edges).

Requests here carry no user. The paths ride nginx's `location /` under the manifest's `guests = true` (`D09-on-a-space`; the coordinator's decision Q1), and `D03-serve` wraps no identity middleware around them. A request proves which host it comes from with `D12-host-identity`'s header and nothing else.

## The binary

`New` opens the file at `Config.Binary` once and digests it with `D11-protocol`'s `Digest`. `D01-layout-and-run-seam` resolves that path with `filepath.EvalSymlinks` at start. `New` keeps the file open for the life of the process and serves every download from that open file, each download reading from offset 0 independently of the others, so concurrent downloads never share a position. The bytes served are therefore always the bytes digested, even after a deploy switches `/opt/ikigenba/current`, or opsctl prunes the release accounts started from, while this process still runs. A missing, unreadable or non-regular file is not a start failure. The digest is then empty and `BinaryPath` answers 404, which is also what an unconfigured accounts answers. A daemon sees an empty `daemon` member and does not update. The download is `200 application/octet-stream` with `Content-Length`, streamed through one buffer of `CopyBuffer` bytes. It is never a redirect: the instance's user data fetches it with a plain `curl`, and a daemon's client follows no redirects (`D14-accountsd`).

## The state long poll

`GET StatePath?after=<version>&digest=<daemon digest>`. A malformed `after` is refused before identity is checked, so a junk query costs no STS call. Next comes identity (`D12-host-identity`'s `Verify`), then the host (`D04-store`'s `HostByInstance`, which matches only a non-deleted host). If the host's version differs from `after`, or accounts has a digest and it differs from `digest`, the current document is answered at once. Otherwise the request waits. It waits on `D04-store`'s `Watch` for the host, which it subscribes to before it reads the version, so no change is lost between the read and the wait. The wait ends at `LongPoll` (timed by `Config.After`), at `Stop`, or when the client goes away. Every wait that ends while the client is still there answers 200 with the current document, the same version included. The document is `D04-store`'s `Desired` with `Daemon` set to `Digest()`, encoded straight to the response. A host's version changes whenever its accounts, users, keys, data volume or sizes change (`D04-store`). The digest changes only when a new accounts process starts. When it does, the old process's `Stop` has already answered every waiter, and later polls to the stopping process that would wait get 503, so daemons back off instead of looping while it drains; the next poll to the new process compares against the new digest. That is how a deploy reaches every daemon within one cycle (outcome 23).

At most `MaxWaiters` requests wait at once. A request that would be the next waiter is answered 503 at once. A request answered at once never counts as a waiter.

## The report

`POST ReportPath`. After identity and the host, the body is read through `http.MaxBytesReader` at `MaxReportBytes` and decoded once with `D11-protocol`'s `DecodeReport`, which caps the lists and the error text. Too large is 413. Malformed or another protocol version is 400. The decoded report goes to `D04-store`'s `RecordReport` with `Config.Now()` as its received time, and the answer is 204. `RecordReport` keeps it as the host's latest, moves `applied` (never above the host's version, never backwards), and returns the health before and after and the alarm change (`D04-store`). From that change (`store.Transition`, whose `Synced` and `ApplyFailed` flags `D04-store` sets from the host's alarm), this package tells:

- `host.synced` (`trail.HostSynced`, `D08-trail`): told when a report with no error leaves the host's applied version equal to its current version, and the host's alarm before the report was `silent` or `error`.
- `host.apply_failed` (`trail.HostApplyFailed`): told when a report carries an error, unless the host's alarm before the report was already `error`.

Neither event carries a user. `host.silent` is the engine's (`D10-operations`), never this package's.

## Answers

| Status | When | Body |
|---|---|---|
| 200 | binary; state | bytes; JSON |
| 204 | report recorded | none |
| 400 | malformed `after`; undecodable report or wrong protocol | `BadRequest` |
| 401 | `ErrMalformed`, `ErrStale`, `ErrReplayed`, `ErrRejected` | `Refused` |
| 403 | the instance maps to no live host | `UnknownHost` |
| 404 | unconfigured; no binary; any other path under `/accountsd/` | `NotFound` |
| 405 | wrong method (with `Allow`) | `NotAllowed` |
| 413 | report over `MaxReportBytes` | `TooLarge` |
| 503 | `ErrUnavailable`, `ErrBusy`, too many waiters | `Busy` |
| 503 | the store cannot be read or written | `store.Unreachable` |

Error bodies are one line of plain text. Each is a copy constant, declared below without its words.

## Bounded work

- The download holds one `CopyBuffer` (32 KiB) buffer, whatever the binary's size. The start-time digest holds one `DigestBuffer` (`D11-protocol`).
- A waiter holds one watch subscription and nothing else until it answers. At most `MaxWaiters` wait at once.
- An answer is one `DesiredState`, which `D17-names-keys-sizes`' caps bound (`D11-protocol`), encoded straight to the response.
- A report body is read through `MaxBytesReader` at `MaxReportBytes`, decoded once, and written as one row.

## Recorded decisions

- **One open descriptor for the binary.** accounts could reopen the path on each request. It does not: the resolved path names a release directory, which a later deploy may prune. An open file keeps the digested bytes servable for as long as this process advertises their digest. Sibling precedent: artifacts and sites stream blobs from files they open per request; their files are immutable and never pruned under them, and this one may be.
- **`After` added to `Config`.** It is an injected timer for the long poll (nil means `time.After`). This field lets a test end a wait at `LongPoll` without waiting 45 seconds (`accounts/AGENTS.md`, Test discipline). `D03-serve` passes `Process.After`.
- **An empty digest never makes the poll answer at once.** If it did, an accounts process with no binary beside it would answer every poll immediately and spin every daemon.
- **Query checked before identity, body after it.** A malformed `after` costs no STS call. A report body is read only from a verified host, so junk reports cost a token, not a 256 KiB read.
- **`WWW-Authenticate` on 401.** HTTP requires a challenge with 401 (RFC 9110 §15.5.2). The value is the scheme name `Accountsd-Identity`. No client parses it.
- **Statuses.** 403 for a verified instance that maps to no host. That happens to a host deleted while its daemon ran, or to a database reset. It is distinct from 401, so an operator reading the trail's request pair can tell a stranger from a forgotten host. 503 for every "cannot judge now" answer, which a daemon retries with backoff (`D14-accountsd`).
- **No `Content-Type` check on the report.** The decoder is the judge. A daemon sends `ContentJSON` (`D11-protocol`).

## Consumer usage

- Daemon first boot (task 2): user data runs `curl -fsS <AccountsURL>/accountsd`, and `ServeHTTP` streams the file `New` opened. The daemon then sends `GET /accountsd/v1/state?after=0&digest=sha256:…` with `hostauth.HeaderName`. `Verify` returns the instance id, `HostByInstance` finds the host, and since version 1 ≠ 0 the request is answered 200 at once with `Desired` plus `Daemon: s.Digest()`.
- Adding a user (task 5): the daemon waits with `after=<v>`. `D07-tools`' `add_user` commits a version bump, `D04-store`'s `Watch` channel closes, and the waiter answers the new document.
- Daemon applies and reports (task 3): `POST /accountsd/v1/report` with the report. `DecodeReport`, then `RecordReport(ctx, host.Name, r, cfg.Now())`, then 204. A silent host's report that applies the current version tells `trail.HostSynced` (task 12).
- Self-update (task 13): a new accounts process starts with a new `Digest()`. The old process's `Stop()` has answered every waiter. The daemon's next poll carries the old digest, so it is answered at once and the daemon downloads `/accountsd`.
- accounts' start and stop (`D03-serve`): `daemonapi.New(ctx, daemonapi.Config{Store, Verifier, Binary: <D01's resolved path>, Telemetry, Now: p.Now, Configured, After: p.After})`. Then `web.Config.Daemon = s`. On shutdown, `s.Stop()` runs before the drain.
- Unconfigured (task 14): `Configured` is false, so every path answers 404 `NotFound`.
