# D13-daemon-endpoints

The accounts side of the daemon protocol. This document owns package `internal/daemonapi`, the handler `D03-serve` mounts at `/accountsd` and at every path beginning `/accountsd/`. It answers four paths, all declared in `D11-protocol`:

- `BinaryPath` streams the daemon binary that sits beside accounts' own executable. No identity is needed (outcome 21; outcome 23's download half).
- `StatePath` answers a host's desired state by long poll (outcome 21, outcome 22's pull), with the backup overlay: where the host's backups go, the backup settings, and short-lived credentials for the host and each of its accounts (host backups).
- `ReportPath` takes the host's report (outcome 24's intake). From the change each report makes, it tells `host.synced` and `host.apply_failed` (outcome 15's health edges).
- `BoxPath` takes the box tools' requests a host's daemon forwards for its SSH users (outcomes 16 to 27, the box path), resolves the host and the uid to one user of an account placed on that host, and hands the request to the box server of the user's tier (`D19-box-tools`) as that user.

Requests here carry no person's identity. The paths ride nginx's `location /` under the manifest's `guests = true` (`D09-on-a-space`; the coordinator's decision Q1), and `D03-serve` wraps no identity middleware around them. A request proves which host it comes from with `D12-host-identity`'s header and nothing else.

## The binary

`New` opens the file at `Config.Binary` once and digests it with `D11-protocol`'s `Digest`. `D01-layout-and-run-seam` resolves that path with `filepath.EvalSymlinks` at start. `New` keeps the file open for the life of the process and serves every download from that open file, each download reading from offset 0 independently of the others, so concurrent downloads never share a position. The bytes served are therefore always the bytes digested, even after a deploy switches `/opt/ikigenba/current`, or opsctl prunes the release accounts started from, while this process still runs. A missing, unreadable or non-regular file is not a start failure. The digest is then empty and `BinaryPath` answers 404, which is also what an unconfigured accounts answers. A daemon sees an empty `daemon` member and does not update. The download is `200 application/octet-stream` with `Content-Length`, streamed through one buffer of `CopyBuffer` bytes. It is never a redirect: the instance's user data fetches it with a plain `curl`, and a daemon's client follows no redirects (`D14-accountsd`).

## The state long poll

`GET StatePath?after=<version>&digest=<daemon digest>`. A malformed `after` is refused before identity is checked, so a junk query costs no STS call. Next comes identity (`D12-host-identity`'s `Verify`), then the host (`D04-store`'s `HostByInstance`, which matches only a non-deleted host). If the host's version differs from `after`, or accounts has a digest and it differs from `digest`, the current document is answered at once. Otherwise the request waits. It waits on `D04-store`'s `Watch` for the host, which it subscribes to before it reads the version, so no change is lost between the read and the wait. The wait ends at `LongPoll` (timed by `Config.After`), at `Stop`, or when the client goes away. Every wait that ends while the client is still there answers 200 with the current document, the same version included. The document, the **state answer**, is `D04-store`'s `Desired` with `Daemon` set to `Digest()`, `Domain` set to `Config.Domain` and `Backup` completed by the backup overlay below, encoded straight to the response by a `json.Encoder` that does not escape `<`, `>` and `&`. `Config.Domain` is the hosts domain in use, `HostsInUse().Domain`, which `D03-serve` hands in from the settings (the configured hosts' domain in AWS mode, the sandbox hosts' in sandbox mode, empty in mode none), and it tells the daemon the name its host takes, `<host>.<domain>` (`D15-machine`); an empty one tells it to leave the hostname alone (`D11-protocol`). `Desired` leaves `Domain` empty, since the store knows no settings, so the answer carries `Config.Domain` whatever the store returns. A host's version changes whenever its accounts, users, keys, data volume or sizes change (`D04-store`). The digest and the domain change only when a new accounts process starts. When one starts, the old process's `Stop` has already answered every waiter, and later polls to the stopping process that would wait get 503, so daemons back off instead of looping while it drains; the next poll to the new process compares against the new digest. That is how a deploy reaches every daemon within one cycle (outcome 23). A new domain bumps no version, and it arrives only with a new accounts process: when that process's digest differs from the one a daemon holds, the daemon's next poll is answered at once with the new domain; when the binary, and so the digest, is unchanged, the daemon learns it when its wait ends at `LongPoll`, within one cycle.

At most `MaxWaiters` requests wait at once. A request that would be the next waiter is answered 503 at once. A request answered at once never counts as a waiter.

## The backup overlay

Every state answer carries a `backup` member (`D11-protocol`'s `Backup`), never null. `Desired` fills the store's part of it: `host_prefix` (`protocol.HostPrefix` of the host's name and `Seq`), `close`, `restore` and `restores` (`D04-store`). daemonapi fills the rest on every answer, whether it is given at once or at the end of a wait:

- `bucket` is `Config.Hosts.BackupBucket()` and `region` is `Config.Hosts.Region` (`D01-layout-and-run-seam`). `D03-serve` hands in `Settings.HostsInUse()`, so in sandbox mode the bucket is `hosts-test-hosts-backups` and the region `sandbox`.
- `settings` is `D04-store`'s `BackupSettings`, read on every answer and copied member for member: the store's row, or `store.DefaultBackupSettings()` while it holds none. A settings change therefore bumps no version; a daemon learns it at its next answer, within one `LongPoll`. A store that cannot answer the settings fails the answer as a failing `Desired` does, 503 `store.Unreachable`, and no credential is asked for.
- `host` and `accounts` are credentials, issued by `Config.Access` (`D21-backup-access`) with one `Issue` per answer, for the host's name, the answer's `host_prefix` and the **issue set**: the slugs of the answer's `accounts` entries in state `active`, and every slug of `restore.accounts`, so a host restoring from backup gets credentials for accounts its state does not yet hold. An account in state `removed` gets none; its last credentials expire within the hour. `accounts` holds one entry per slug of the issue set, ascending by slug.
- An entry `Issue` could not issue, because its `AssumeRole` failed, did not answer within `access.IssueBudget`, or the partition and account could not be learnt, is the zero `Credentials` (or the older set `Access` still holds, while it has not expired, as `D21-backup-access` states), and the answer is still 200. Each entry carries exactly what `Issue` answered for it: `Issue` returns an error whenever any set is zero, and that error zeroes nothing else and fails nothing (root decision). The daemon reports such an account as having no credentials (`D15-machine`) and the next answer retries. So a state answer is delayed by at most `access.IssueBudget` (8 s, `D21-backup-access`) beyond what it already waited: an answer at the end of a wait arrives by `LongPoll` + 8 s, 53 s, inside the daemon's `RequestTimeout` (`LongPoll` + 15 s, `D14-accountsd`). Most answers take no STS call at all, since `Access` reuses a set for 15 minutes (`access.ReissueAfter`).
- A set whose `AccessKeyID`, `SecretAccessKey` and `SessionToken`, each encoded as the answer writes it (quotes and escapes counted: a `"`, `\` or control character takes two bytes or more, a U+2028 or U+2029 six), together take more than `MaxCredentialBytes` (2,048 bytes) is answered zero too. The cap is on the encoded length, as `D11-protocol`'s caps on report strings are, because a raw cap would let a set of `"` characters double. AWS publishes no maximum for a session token (the STS API reference's `Credentials` type, https://docs.aws.amazon.com/STS/latest/APIReference/API_Credentials.html, bounds only `AccessKeyId`, 16 to 128 characters), so the cap is what keeps the answer under `MaxStateBytes` by construction. The plan's estimate of a set is about 1.3 KB. The user measured real sets twice against the role `ikigenba.dev-hosts-backup` with a 727-byte session policy, longer than the longest policy `access.Policy` answers (675 characters, `D21-backup-access`), so the measurement covers it conservatively: an access key id of 20 characters, a secret of 40 and a session token of 1,100 (base64, nothing JSON escapes), packed policy size 26%; such a set encodes to roughly 1.2 KB, its three strings 1,166 bytes, well under the cap. Still, that a real issued set for the longest policy encodes within `daemonapi.MaxCredentialBytes` is unproven here and is checked at the finish line (`D09-on-a-space`), where a set over the cap would show as every account lacking credentials.
- With `Config.Access` nil (mode none, where `Configured` is false and no state is ever answered, or a test), `host` is zero and `accounts` is the empty array; `bucket`, `region` and `settings` are still filled.

Every other member of the answer is what `Desired` returned, so the overlay never changes a host's version: a reissued credential wakes no waiter, and a daemon receives renewed sets at least once per `LongPoll`. The secret and the token go into the 200 answer and nowhere else: never into an event, a log line, an error body or the store.

## The report

`POST ReportPath`. After identity and the host, the body is read through `http.MaxBytesReader` at `MaxReportBytes` and decoded once with `D11-protocol`'s `DecodeReport`, which caps the lists and the error text. Too large is 413. Malformed or another protocol version is 400. The decoded report goes to `D04-store`'s `RecordReport` with `Config.Now()` as its received time, and the answer is 204. `RecordReport` keeps it as the host's latest, moves `applied` (never above the host's version, never backwards), and returns the health before and after and the alarm change (`D04-store`). From that change (`store.Transition`, whose `Synced` and `ApplyFailed` flags `D04-store` sets from the host's alarm), this package tells:

- `host.synced` (`trail.HostSynced`, `D08-trail`): told when a report with no error leaves the host's applied version equal to its current version, and the host's alarm before the report was `silent` or `error`.
- `host.apply_failed` (`trail.HostApplyFailed`): told when a report carries an error, unless the host's alarm before the report was already `error`.

Neither event carries a user. `host.silent` is the engine's (`D10-operations`), never this package's.

## The box path

`POST BoxPath?uid=<decimal uid>` (`D11-protocol`'s `BoxPath` and `QueryUID`). `D14-accountsd` sends it for each `tools/list` or `tools/call` line a user's stdio client relays; its body is that line, a JSON-RPC 2.0 request of at most `MaxBoxRequest` bytes. `daemonapi.Config` carries the two box servers as `BoxUser` and `BoxAdmin`, each an `http.Handler`: `D03-serve` hands it two appkit `mcp.Server`s, on which `D19-box-tools`' `box.RegisterUser` and `box.RegisterAdmin` registered the user tier (`keys`, `add_key`, `remove_key`) and the admin tier (all eleven). A test can hand recording handlers instead, which is why the fields are handlers and not servers.

A box request is judged in this order, each step answering before the next is reached:

1. With `BoxUser` or `BoxAdmin` nil, `BoxPath` is like any unknown path: 404 `NotFound`. A release or a test without the box answers as an old accounts does.
2. A method other than `POST` is 405 `NotAllowed` with `Allow: POST`.
3. The `uid` member must appear once and be a decimal integer from 0 to 4294967295, the range of a 32-bit `uid_t`, which is all a peer credential can hold. Anything else is 400 `BadRequest`. As with `after`, junk costs no STS verification, which would spend the global admission bucket.
4. Identity, as for state and report (`D12-host-identity`'s `Verify`): 401 `Refused` or 503 `Busy`.
5. The host, by `HostByInstance`: 403 `UnknownHost` or 503 `store.Unreachable`.
6. The user, by `D04-store`'s `ActiveUserByUID` for the host's name and the uid: the active user with that uid in an account placed on that host that is not being removed. None is 403 `NotUser`; a store failure is 503 `store.Unreachable`. accounts never reads a name or an account from the host, so a host can reach only the users of accounts placed on it.
7. At most `MaxBoxServing` (32) box requests are served at once, each counted from here until its answer is written. One more is answered 503 `Busy` at once, its body unread. The waiter cap does not cover this (it counts long-poll waiters only), and the admission bucket limits how fast requests arrive, not how many are held. 32 covers about one forward a second per host (`D14-accountsd`'s signing gate) over tens of hosts, each lasting milliseconds.
8. The body, through `http.MaxBytesReader` at `MaxBoxRequest`, read once: over the limit is 413 `TooLarge`. It must be exactly one JSON object with `"jsonrpc":"2.0"`, an `id` that is a string or an integer, and a `method` that is `MethodToolsList` or `MethodToolsCall`; anything else (a batch, a notification, a null id, `initialize` or any other method) is 400 `BadRequest`. The stdio client answers `initialize`, `ping` and notifications itself (`D20-box-mcp`), so only those two methods ever need to travel.
9. The tier: `tools/list` goes to `BoxAdmin` for an admin and to `BoxUser` otherwise, so a non-admin is never offered the admin tools. `tools/call` always goes to `BoxAdmin`, the server holding every box tool, whose admin tools check, atomically with their write, that the actor is still an active admin (`D19-box-tools`); so a non-admin is refused them with `D19-box-tools`' own copy, and a demotion racing a call is refused too.
10. The handler serves a clone of the request with no `Origin` header (so appkit's 403 for a foreign `Origin` can never reach a daemon, which would read it as `UnknownHost` or `NotUser`), its body the bytes read, whose context carries the box caller: `identity.Caller{UserID: box.ActorPrefix + <the user's name>, Email: "", RequestID: <the request id>}`. The request id is the one appkit's `telemetry.Middleware` put on the context (`D03-serve`, R-QP6K-92D8), read with `identity.FromContext`, so the request pair, `tool.called` and the trail's events share it. `X-User-Id` and `X-User-Email` are never read here.

The handler's answer goes straight to the response, with no buffer. A box server answers 200 `ContentJSON` with one JSON-RPC response on one line, a tool's refusal included (an MCP error result), and so does an unknown tool (a JSON-RPC error, appkit's legacy mode). Its other answers (415 for a body that is not JSON by its `Content-Type`, 400 for mismatched MCP headers) are relayed as they are, and a daemon shows any status but 200 and 403 as "cannot reach accounts" (`D14-accountsd`). Every answer stays under `MaxBoxAnswer` by construction: the store caps every recorded caller at `valid.MaxUserIDBytes` (`D04-store`, `D17-names-keys-sizes`) and every box list is capped (`D19-box-tools`), so the largest answer, a 200-user `users` list with the longest, worst-escaped creators and a string id that fills the request, is about 309 KB. No over-bound answer can be produced, so none is designed.

Nothing else about the daemon protocol changes. Replay and STS stay as `D12-host-identity` states: one `Verify` per forward, and an `ErrBusy` or `ErrUnavailable` 503 is, to the daemon, "cannot reach accounts". The box servers, not this package, tell the box events and make the box writes (`D19-box-tools`, `D08-trail`).

## Answers

| Status | When | Body |
|---|---|---|
| 200 | binary; state; a box request, as the box server answers | bytes; JSON |
| 204 | report recorded | none |
| 400 | malformed `after`; undecodable report or wrong protocol; malformed `uid`; a box body that is not one allowed JSON-RPC request | `BadRequest` |
| 401 | `ErrMalformed`, `ErrStale`, `ErrReplayed`, `ErrRejected` | `Refused` |
| 403 | the instance maps to no live host | `UnknownHost` |
| 403 | the uid is no active user of an account placed on the host | `NotUser` |
| 404 | unconfigured; no binary; no box servers; any other path under `/accountsd/` | `NotFound` |
| 405 | wrong method (with `Allow`) | `NotAllowed` |
| 413 | report over `MaxReportBytes`; box body over `MaxBoxRequest` | `TooLarge` |
| 503 | `ErrUnavailable`, `ErrBusy`, too many waiters, `MaxBoxServing` box requests already served | `Busy` |
| 503 | the store cannot be read or written, the backup settings included | `store.Unreachable` |
| any | a box request the box server answered | the box server's own |

Error bodies daemonapi words itself are one line of plain text. Each is a copy constant, declared below without its words; the build chooses them, as for the others. The box server's answers, refusals included, are its own and are relayed unchanged.

## Bounded work

- The download holds one `CopyBuffer` (32 KiB) buffer, whatever the binary's size. The start-time digest holds one `DigestBuffer` (`D11-protocol`).
- A waiter holds one watch subscription and nothing else until it answers. At most `MaxWaiters` wait at once.
- An answer is one `DesiredState`, which `D17-names-keys-sizes`' caps bound (`D11-protocol`), with its overlay, encoded straight to the response; it is at most `protocol.MaxStateBytes` encoded, a requirement proved with the worst fixtures. Its `Domain` is the one string `Config.Domain` holds, fixed when the process starts and grown by no record. The worst case: 2,000 keys of 512 bytes whose comments are all `"` (two bytes each encoded, since the encoder leaves `<`, `>` and `&` unescaped; with them escaped, six bytes each would put the keys alone near 5.3 MB; a comment of U+2028, three bytes raw and six encoded, is no worse than `"`) come to about 1.89 MB (12 + 68 + 1 + 431 × 2 + 3 = 946 bytes a key); 200 users' names, accounts, uids, states and key brackets about 25.6 KB; 50 accounts about 3.3 KB; 100 allowlist and unban entries about 4.6 KB; domain, settings, bucket, region and `host_prefix` under 1 KB; `close`, one operation id, under 100 bytes; `restores`, `valid.MaxRestoresPerHost` (10) requests of about 720 bytes each (a path of at most `valid.MaxRestorePath` 512 bytes encoded, slug and user of 34, kind, id, `as_of` and member names), about 7.2 KB. Pending restores and a running close coexist with every user (a close cancels no restore, `D04-store`), so the fixture holds all of them. A whole-host `restore` comes only while accounts and users are withheld (`D04-store`), and at most 50 slugs and `protocol.MaxDatabases` paths of 256 bytes, about 16 KB, it is far smaller than the users it replaces, so it is not in the fixture. 51 credential sets, each at most `MaxCredentialBytes` encoded for its three strings plus about 170 bytes of member names, slug and `expires`, about 113 KB. About 2.05 MB in all, about 47 KB under `MaxStateBytes` (2 MiB, 2,097,152 bytes).
- An answer's credentials come from one `Issue` call, which holds at most one host's sets and at most `access.IssueParallel` STS answers at a time (`D21-backup-access`).
- A report body is read through `MaxBytesReader` at `MaxReportBytes`, decoded once, and written as one row.
- A box request holds one body of at most `MaxBoxRequest` (64 KiB), one host, one user, and the answer as appkit builds it, which daemonapi relays without a buffer. appkit holds the encoded output, its text copy and the response at once: at most about 3 × 309 KB at the hard worst case, under 100 KB with auth's real user ids. About 1 MB per request at worst; at most `MaxBoxServing` (32) served at once, so about 32 MB, within the manifest's 256M `memory_max` (`D09-on-a-space`). A request beyond that count is refused before its body is read, and an unverified one or one that resolves to no user costs no body read.

## Recorded decisions

- **One open descriptor for the binary.** accounts could reopen the path on each request. It does not: the resolved path names a release directory, which a later deploy may prune. An open file keeps the digested bytes servable for as long as this process advertises their digest. Sibling precedent: artifacts and sites stream blobs from files they open per request; their files are immutable and never pruned under them, and this one may be.
- **`After` added to `Config`.** It is an injected timer for the long poll (nil means `time.After`). This field lets a test end a wait at `LongPoll` without waiting 45 seconds (`accounts/AGENTS.md`, Test discipline). `D03-serve` passes `Process.After`.
- **An empty digest never makes the poll answer at once.** If it did, an accounts process with no binary beside it would answer every poll immediately and spin every daemon.
- **Query checked before identity, body after it.** A malformed `after` costs no STS call. A report body is read only from a verified host, so junk reports cost a token, not a 256 KiB read.
- **`WWW-Authenticate` on 401.** HTTP requires a challenge with 401 (RFC 9110 §15.5.2). The value is the scheme name `Accountsd-Identity`. No client parses it.
- **Statuses.** 403 for a verified instance that maps to no host. That happens to a host deleted while its daemon ran, or to a database reset. It is distinct from 401, so an operator reading the trail's request pair can tell a stranger from a forgotten host. 503 for every "cannot judge now" answer, which a daemon retries with backoff (`D14-accountsd`).
- **No `Content-Type` check on the report.** The decoder is the judge. A daemon sends `ContentJSON` (`D11-protocol`).
- **Box servers as `http.Handler`.** daemonapi needs only `ServeHTTP` from them, and a test can hand a recording handler to prove the tier chosen, the caller given and the bytes relayed. `D03-serve` hands real servers.
- **The uid query before identity, the body after the user.** A malformed uid costs no STS verification; a body is read only for a verified host's real user, and only within `MaxBoxServing`.
- **403 for no such user.** The daemon treats it as it treats `UnknownHost`: the "not an active user" refusal (`D14-accountsd`). `NotUser` is its own constant so an operator reading the request pair can tell a forgotten host from a stranger's uid.
- **The caller comes from the store, never the request.** The box caller's `UserID` is `box.ActorPrefix` and the resolved user's name; names are unique system-wide (`D17-names-keys-sizes`), so the name implies account and host. `ssh:` can never collide with auth's user ids. A request's `X-User-Id` is ignored here, as everywhere under `/accountsd/`.
- **No over-bound answer.** An earlier sketch answered 500 when a box answer would exceed `MaxBoxAnswer`. The store's caller cap and the list caps keep every answer under it, so no test could ever reach that branch; the bound is a requirement proved with the worst fixtures instead.
- **An escaped alias of an envelope member is refused.** The tier is chosen by the `method` written literally, and the body is handed on byte for byte to appkit's MCP server, which decodes escaped member names and keeps the last; `"method":"tools/call","metho\u0064":"tools/list"` would otherwise be routed as a call and served as a list, handing a non-admin the admin list. A member that decodes to `jsonrpc`, `id` or `method` without being written so is therefore a `BadRequest`, as the daemon (`D14-accountsd`) and the stdio server (`D20-box-mcp`) refuse it too, so all three sides judge one request alike. Literal names are untouched: an unambiguous request's bytes still pass unchanged.
- **The domain comes from the config, not the store.** The hosts domain is a setting, and the store knows no settings, so `Desired` leaves `Domain` empty and daemonapi sets it on every state answer, as it sets `Daemon`. Changing the domain therefore bumps no host's version; a daemon learns a new one at its next answer, within one `LongPoll`. `D03-serve` passes the hosts domain in use, `HostsInUse().Domain`, empty in mode none, and an empty domain leaves every hostname alone.
- **`Access` and `Hosts` added to `Config`; `Domain` kept.** `Hosts` gives the bucket (`BackupBucket()`) and the region (`Region`, the field the hosts settings already hold; no new name was needed). `Domain` could have been replaced by `Hosts.Domain`; it is kept (plan pick), so the field list only grows and `D04-store`'s R-YBAC-4CV8 and `D03-serve`'s wiring of `Domain` stand. `D03-serve` hands both from `Settings.HostsInUse()`, so they cannot disagree.
- **Credentials at answer time, never failing the answer.** The answer is the daemon's only channel and its credentials expire within the hour, so they are issued when the answer is written, not stored with the state (plan pick 2: one set per account plus one for the host, reissued after 15 minutes, `D21-backup-access`). A failed or late entry is zero rather than a failed answer, so one account's STS trouble never keeps a host from its users and keys; the daemon reports that account as having no credentials and the next answer retries.
- **A failing settings read is 503 `store.Unreachable`.** It is what this package already answers when `Desired` or a version read fails (R-OKLA-OIOR), and a daemon retries 503 with backoff. Answering defaults instead would hand the daemon a schedule the operator did not set. The settings are read before any credential is asked for, so a failing store costs no STS call.
- **Answers ended by `Stop` still carry credentials.** Sending zero would stop every account's streaming until the next process answers. `Access` reuses a set for 15 minutes, so after the first answers nearly every `Issue` is answered from its cache; a stop that meets an uncached host can hold that answer up to `access.IssueBudget` into the drain.
- **The state answer is encoded without HTML escaping.** `encoding/json`'s default writes `<`, `>` and `&` as six bytes each; key comments may be made of them, and the worst case would then be about 5.3 MB, over `MaxStateBytes`, already before the overlay. Unescaped, the worst character (`"` or a tab) costs two bytes and the bound holds. The bytes decode to the same document; the daemon decodes any JSON (`D11-protocol`).
- **`MaxCredentialBytes`.** AWS publishes no bound on a session token, so the answer's bound needs one of its own. 2,048 bytes for a set's three strings, measured encoded so that no escaping can grow it, is above the plan's estimate of a real set and leaves the worst answer, pending restores and a running close included, about 47 KB under `MaxStateBytes`. A set over it is answered zero, as an unissued one is. Kept at 2,048 after a measurement (root decision): real sets against `ikigenba.dev-hosts-backup` with a 727-byte policy encode their three strings in 1,166 bytes, about 880 bytes of margin, so `MaxStateBytes` stays as it is and `D09-on-a-space`'s finish-line check stays. The measured session policy was 727 bytes, longer than the longest policy `access.Policy` answers (675 characters), so the measurement covers it conservatively. Rejected: raising `MaxStateBytes`, which old daemons enforce at 2 MiB, and restricting key comments.
- **Expand then contract.** The `backup` member is a protocol addition read only by the daemon of the release that sends it, a departure `D11-protocol` records, as it records `domain`'s. An old daemon (a failed self-update) ignores the member (R-U6VF-GCXW) and backs nothing up, every other member being unchanged by the overlay; a new daemon under an old accounts (a rollback) sees no `backup` member, stops its backup units and reports no credentials until it rolls back with accounts, within one cycle (the digest). Accounts and users that `Desired` sends `locked` or withholds (`D04-store`) are members an old daemon already applies.
- **Expand then contract (box path).** `BoxPath` is a new path only: no schema, state or report change. An old accounts answers it 404, which a new daemon shows as "cannot reach accounts"; an old daemon never calls it. The state answer's `domain` member is a protocol addition that lands in the same release as the daemon that reads it, a departure `D11-protocol` records: an old daemon ignores the unknown member, and an old accounts sends none, which a new daemon reads as empty and so leaves the hostname alone.

## Consumer usage

- Daemon first boot (task 2): user data runs `curl -fsS <AccountsURL>/accountsd`, and `ServeHTTP` streams the file `New` opened. The daemon then sends `GET /accountsd/v1/state?after=0&digest=sha256:…` with `hostauth.HeaderName`. `Verify` returns the instance id, `HostByInstance` finds the host, and since version 1 ≠ 0 the request is answered 200 at once with `Desired` plus `Daemon: s.Digest()`, `Domain: cfg.Domain` and the backup overlay. On a space whose hosts domain is `hosts.example.com`, the answer's `domain` is `hosts.example.com` and the daemon names host `host01` `host01.hosts.example.com` (`D15-machine`); on an unconfigured accounts the member is empty and the daemon leaves the hostname alone.

- Adding a user (task 5): the daemon waits with `after=<v>`. `D07-tools`' `add_user` commits a version bump, `D04-store`'s `Watch` channel closes, and the waiter answers the new document.
- Daemon applies and reports (task 3): `POST /accountsd/v1/report` with the report. `DecodeReport`, then `RecordReport(ctx, host.Name, r, cfg.Now())`, then 204. A silent host's report that applies the current version tells `trail.HostSynced` (task 12).
- Self-update (task 13): a new accounts process starts with a new `Digest()`. The old process's `Stop()` has answered every waiter. The daemon's next poll carries the old digest, so it is answered at once and the daemon downloads `/accountsd`.
- accounts' start and stop (`D03-serve`): `bu, ba := p.MCP(w), p.MCP(w)` and `bc := box.Config{Store: st, Telemetry: w, AccountsURL: func() (string, error) { return s.AccountsURL(path) }}` (`st` the run's store, `w` its writer, `s.AccountsURL(path)` the invite link base as `tools.Config.AccountsURL` has it), then `box.RegisterUser(bu, bc)` and `box.RegisterAdmin(ba, bc)` (`D19-box-tools`), then `daemonapi.New(ctx, daemonapi.Config{Store, Verifier, Binary: <D01's resolved path>, Telemetry, Now: p.Now, Configured, After: p.After, BoxUser: bu, BoxAdmin: ba, Domain: hosts.Domain, Access: <access.New over the opened cloud's STS in AWS and sandbox modes, nil in mode none>, Hosts: hosts})`, `hosts` being `s.HostsInUse()` (until this revision, the same without `Access` and `Hosts`). Then `web.Config.Daemon = s`. On shutdown, `s.Stop()` runs before the drain.
- A user's tool call from a host (outcomes 16 to 26): `claude` writes a `tools/call` line for `add_key` to `accountsd-mcp`, which relays it over the host's socket (`D20-box-mcp`); `accountsd` posts it to `/accountsd/v1/box?uid=1001` with its identity header (`D14-accountsd`). `Verify`, `HostByInstance`, then `ActiveUserByUID(ctx, host.Name, 1001)` returns `daffy`; the body is read and checked; `tools/call` goes to `cfg.BoxAdmin` with the caller `{UserID: "ssh:daffy", RequestID: <the request id>}`; the box server's 200 JSON answer is the response, and the daemon relays it.
- The same user's `tools/list`: an ordinary user's goes to `cfg.BoxUser` and lists `keys`, `add_key` and `remove_key`; an admin's goes to `cfg.BoxAdmin` and lists all eleven.
- A uid that is root, or no active user of an account placed on that host: 403 `NotUser`, which the daemon shows as "not an active user". A burst beyond `MaxBoxServing`: 503 `Busy`, which it shows as "cannot reach accounts".
- Unconfigured (task 14): `Configured` is false, so every path answers 404 `NotFound`.
