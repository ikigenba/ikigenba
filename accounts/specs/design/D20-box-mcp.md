# D20-box-mcp

Outcomes cited as outcome N are those of /home/mgreenly/Documents/ikigenba-self-service-accounts.md.

`accountsd-mcp` is the local MCP server every host carries (outcome 16). It is not a binary of its own: it is `accountsd` run through the link `linux.MCPHelper` (`/usr/local/libexec/accountsd-mcp`), which D15's `Apply` keeps beside `accountsd-session`, and D14's argv[0] dispatch hands it to `boxmcp.Run(ctx, os.Stdin, os.Stdout, os.Getenv)`. Claude Code starts it as a child process through the plugin's `.mcp.json` (D15) and speaks MCP to it over stdio. It holds no authority and stores no secret (outcome 17): it answers the protocol's housekeeping itself and relays every tool request, as the bytes it read, over the unix socket `accountsd` serves (D14), which reads the caller's uid from the kernel and forwards the request to accounts (D11, D13). The tool list, the tool descriptions, the schemas and every tool result come from accounts (D19), so nothing here knows a tool. This document owns package `internal/boxmcp`: the stdio server, the socket's wire (`Answer`, `WriteAnswer`, the socket path and the variable that overrides it) and its one copy constant of substance, `NotAnswering`. The daemon's side of the socket (listening, peer credentials, refusals, the forward) is D14's.

## The stdio server

The MCP stdio transport is newline-delimited JSON-RPC 2.0: "Messages are delimited by newlines, and MUST NOT contain embedded newlines", and "The server MUST NOT write anything to its stdout that is not a valid MCP message" (modelcontextprotocol.io, specification 2025-11-25, Basic, Transports, stdio). So `Run` reads `in` one LF-terminated line at a time and writes to `out` nothing but JSON-RPC responses, one line each, ending in LF. It has no stderr and writes no diagnostic.

A line is at most `protocol.MaxBoxRequest` bytes (64 KiB, D11), the largest request the daemon forwards; a box tool's arguments are a user name, a key of at most 512 bytes or an invite id, so a real request is a few hundred bytes. A longer line is answered with a JSON-RPC Invalid Request error whose id is null and is then skipped through its LF without being held: the reader keeps at most the bound and throws the rest away, and resynchronizes at the next LF. The id is null because finding it would mean holding the line; JSON-RPC 2.0 says an id that cannot be detected is answered as null (jsonrpc.org/specification, 5 Response object). An empty or whitespace-only line is no message and is skipped silently.

Each message is judged as JSON-RPC 2.0 judges it (jsonrpc.org/specification, 4 Request object, 5.1 Error object, 7 Examples): not JSON is a Parse error (-32700) with a null id; JSON that is not an object (a batch array included) is an Invalid Request (-32600) with a null id; an object that is not a valid request is an Invalid Request with its id when the id is a string or an integer, and null otherwise, a null id included, since MCP says "Unlike base JSON-RPC, the ID MUST NOT be null" (specification 2025-11-25, Basic, Messages, Requests); an unknown method is Method not found (-32601). Member names match exactly and an id is a string or an integer written with neither fraction nor exponent (MCP's "string or integer ID", same page), for every method: these are the requests accounts accepts on the box path (D13, R-8NGO-3ATJ), so whatever the server forwards accounts takes, and anything else is answered here as an Invalid Request. Go's `encoding/json` matches member names without regard to case, so the build cannot lean on it for this. A member whose name is written with escapes but decodes to `jsonrpc`, `id` or `method` (`"metho\u0064"`, say) is refused as an Invalid Request rather than ignored, on all three sides alike (here, the daemon's D14 and accounts' D13): appkit's MCP server decodes escaped names and keeps the last, so such an alias could make accounts read a method other than the one the route chose the tier by. Batches are refused, not answered element by element: MCP removed JSON-RPC batching in revision 2025-06-18 (specification 2025-06-18, Key Changes, major change 1), and both revisions this server speaks come after it. A notification (a request with no `id`) is never answered, whatever its method: `notifications/initialized` and `notifications/cancelled` are accepted and do nothing. A JSON-RPC response from the client (an object with `result` or `error` and no `method`) answers a request this server never sends and is ignored.

`initialize` follows the lifecycle's version negotiation: "If the server supports the requested protocol version, it MUST respond with the same version. Otherwise, the server MUST respond with another protocol version it supports. This SHOULD be the latest version supported by the server." (specification 2025-11-25, Basic, Lifecycle, Version Negotiation). The server supports the versions `ProtocolVersions` returns, latest first, and answers the requested one when it is among them and the first otherwise. Its result carries `protocolVersion`, the capabilities `{"tools":{}}` (it offers tools and sends no `list_changed` notification, so `listChanged` is absent) and `serverInfo` with `name` `ServerName` and a non-empty `version`. `ping` is answered with an empty result (specification 2025-11-25, Basic, Utilities, Ping). The server keeps no session: every message is judged alone, so a `tools/list` before `initialize` is served too (the lifecycle only says a client SHOULD NOT send one).

`tools/list` and `tools/call` are forwarded. Everything else is answered locally, and only these two ever reach the socket.

## The socket's wire

One connection per forwarded request (the root contract, section B). `Run` dials the socket, writes the line it read from `in`, byte for byte and without its LF, then one LF, and reads one answer line: an `Answer`, a JSON object with exactly one of `message` (accounts' JSON-RPC response, relayed) and `refusal` (one of the daemon's copy constants), then LF. A daemon at its connection bound (D14's `MaxBoxConns`) writes a refusal at once without reading the request and closes, so a failed or short write of the request is not itself a failure: `Run` still reads the answer line and relays a refusal that arrives. A `message` goes to `out` as it came, then LF. A `refusal` becomes, for `tools/call`, the tool error result `{"content":[{"type":"text","text":<refusal>}],"isError":true}` with the request's id, so the model reads the refusal as the tool's outcome; for `tools/list`, which has no error result, a JSON-RPC error with the request's id, code `CodeRefused` (-32000, the first of JSON-RPC 2.0's "implementation-defined server-errors", -32000 to -32099) and the refusal as message. When the socket cannot be dialled, closes before an LF, sends an answer line that is not a well-formed `Answer`, sends one longer than `MaxAnswerLine`, or has not answered within `AnswerTimeout` of the dial, the request is answered the same way with `NotAnswering`.

`WriteAnswer` writes the answer line, so both sides spell the envelope from one place: the daemon writes every answer line with it (D14, R-ZD3Z-LKAQ) and relays only bodies it accepts (R-ZBW3-7SK1), and the tests' fake daemons use it too. It writes the message's bytes verbatim, so the relay is byte for byte end to end; `encoding/json`'s `Marshal` would compact a `json.RawMessage` and escape `<`, `>` and `&`, which changes the bytes and can grow them sixfold. It refuses an answer `Run` would not accept: neither or both members set, a message that is not one JSON object or holds an LF, a message over `protocol.MaxBoxAnswer`, or a line over `MaxAnswerLine`. So `MaxAnswerLine`, `protocol.MaxBoxAnswer` plus 1 KiB for the envelope and a refusal, bounds every answer a correct daemon writes, and `Run` reads at most `MaxAnswerLine + 1` bytes of one.

`Answer` decodes tolerantly (unknown members ignored), because a long-lived `accountsd-mcp` process under a running Claude session can be older than the daemon after a self-update; the envelope changes by expand then contract like every interface between releases.

## Bounded work

`Run` handles one message at a time: it reads no further line while a forward is in flight, and it has at most one connection open. At once it holds one line of at most `protocol.MaxBoxRequest` bytes (with its read buffer), one answer line of at most `MaxAnswerLine` bytes, and the one response it is writing, which is the answer's message or a small envelope around a refusal. An over-long line and an over-long answer are discarded or abandoned as they stream, never accumulated. `WriteAnswer` holds the one line it writes. Requirements R-7AHR-9OH2, R-7FDC-SRFU, R-POO9-DTY4 and R-PR42-5DFI state these bounds.

## Recorded decisions

- **The handshake-era protocol, not 2026-07-28.** The owner's decision names `initialize`, which is how the 2025-11-25 and earlier revisions open a session. The current revision, 2026-07-28, has no handshake: each request carries its version in `_meta` and servers must implement `server/discover` (specification 2026-07-28, Versioning). A dual-era client probes a stdio server with `server/discover` and falls back to `initialize` on "any other error" than a recognized modern one, "commonly -32601" (2026-07-28, Transports, stdio, Backward Compatibility), which is what this server answers. A modern-only client fails against it. The owner's decision: keep `initialize` only, with no `server/discover`; that Claude Code completes `initialize` against this server is verified on the host at the finish line.
- **Versions 2025-11-25 and 2025-06-18.** Both are handshake-era and batch-free. Tool results relayed from accounts carry `outputSchema` and structured content, added in 2025-06-18 (Key Changes, major change 2); 2025-03-26 also allowed batches. A client asking for an older version is answered 2025-11-25 and, per the lifecycle, disconnects if it cannot speak it. These are protocol identifiers on the wire, like `protocol.Version`, not release versions.
- **`serverInfo.version` is not fixed.** The binary cannot know its release (devctl stamps nothing, D11), no client parses the field, and the build may put any non-empty string there; the daemon's digest is not available to `Run` without reading the executable, which this process has no reason to do.
- **Sequential.** One request at a time is the simplest bounded design, and a person's agent rarely has two tool calls in flight to one server; the daemon accepts about one forward per second per host anyway (the root contract, decision 4). A `notifications/cancelled` for the request in flight is therefore read only after its answer, when there is nothing left to cancel; the spec's "MUST NOT send any further messages for it" (2026-07-28 stdio, Cancellation) holds because the answer was already sent.
- **`Serve` beside `Run`.** `Run` has the signature the binary calls and waits `AnswerTimeout` (30 s), longer than the daemon's `daemon.BoxTimeout` (15 s, D14) so an answer in time is never cut off. No test may wait 30 s on the clock (`accounts/AGENTS.md`, Test discipline), so `Serve` takes the socket path and the timeout in `Config`, and `Run` is `Serve` with the socket from `getenv` and `AnswerTimeout`. This is a timeout seam, not a second dial seam: production still dials only `getenv(EnvSocket)` or `SocketPath`. `Run` passes exactly `AnswerTimeout` as `Config.Timeout`; that is guidance for the build, not a requirement, since telling it from a shorter or longer wait means waiting on the clock for up to 30 s, which no permitted test does. The requirements prove `Run`'s socket choice and environment lookup, and the timeout behaviour through `Serve` with a timeout the test passes; `Run`'s value is left to review and the finish line.
- **`ACCOUNTSD_SOCKET` in production is harmless.** A user who points their own client at another socket gains nothing: the daemon reads the uid from the kernel (D14), and any other listener is one the user could talk to anyway.
- **Over-long lines answer with a null id**, so a client waiting on that id times out on its own side; holding up to 64 KiB to recover the id was rejected as complexity for a line no real client sends.
- **Copy.** `NotAnswering` holds "the host's accounts daemon is not answering" (the root contract, decision 7). The JSON-RPC error messages are copy constants too, holding JSON-RPC 2.0's own names: `MsgParseError` "Parse error", `MsgInvalidRequest` "Invalid Request", `MsgMethodNotFound` "Method not found", and `MsgTooLarge` "request too large".
- **Unix socket paths in tests.** A pathname socket's `sun_path` holds at most 108 bytes including the terminating NUL (unix(7), Address format), and `t.TempDir()` can be longer, so a test makes its socket under `os.MkdirTemp("", ...)`, as `accounts/AGENTS.md` already directs for the readiness socket.
- **No process-starting test.** Every requirement is proved in process: `Run` and `Serve` over `io.Pipe` or byte buffers, against a real unix socket the test serves in a short temporary directory, named through `getenv` or `Config.Socket`. That `accountsd` dispatches to `Run` under the name `accountsd-mcp` is D14's requirement.

## Consumer usage

Current: none; the package is new.

Proposed:

- `cmd/accountsd` (D14), under the name `linux.MCPName`: `err := boxmcp.Run(ctx, os.Stdin, os.Stdout, os.Getenv)`, exiting 0 when `err` is nil.
- The daemon's socket server (D14), per accepted connection: it reads one line of at most `protocol.MaxBoxRequest` bytes (or, over `MaxBoxConns`, reads nothing), decides, and writes one line with `boxmcp.WriteAnswer(conn, boxmcp.Answer{Message: body})` for a 200 whose body `WriteAnswer` accepts or `boxmcp.WriteAnswer(conn, boxmcp.Answer{Refusal: daemon.CannotReach})` (or another of its refusals), then closes. D14 and D15 spell the socket's path as `boxmcp.SocketPath`.
- The sandbox (D16): it serves the simulated host's socket at a path of its own and runs the sandbox's `accountsd` through a link named `accountsd-mcp` with `ACCOUNTSD_SOCKET` (`boxmcp.EnvSocket`) naming that path.
- A test: `dir, _ := os.MkdirTemp("", "box")`, a `net.Listen("unix", dir+"/s")` the test answers with `boxmcp.WriteAnswer`, and `boxmcp.Serve(ctx, inR, outW, boxmcp.Config{Socket: dir + "/s", Timeout: time.Second})` over `io.Pipe`s; it writes `{"jsonrpc":"2.0","id":1,"method":"tools/list"}` and LF, asserts the listener received exactly those bytes and LF, and decodes the line `out` carries. A timeout test hands a listener that never answers and a `Timeout` of a few milliseconds and expects a `CodeRefused` error with `boxmcp.NotAnswering`.

### The answer line

- R-781Y-I4ZO: `encoding/json`'s `Marshal` of an `Answer` MUST omit `message` when `Message` is empty and `refusal` when `Refusal` is empty, so that `Answer{Refusal: "x"}` marshals to exactly `{"refusal":"x"}`; and `Unmarshal` into an `Answer` MUST ignore members it does not declare, so that `{"refusal":"x","later":1}` decodes with `Refusal` `x` and `Message` empty.
- R-799U-VWQD: When `a.Message` is set and `a.Refusal` is empty, `WriteAnswer` MUST write exactly the bytes `{"message":`, then `a.Message` unchanged, then `}` and one LF; when `a.Refusal` is set and `a.Message` is empty, it MUST write exactly `{"refusal":`, then `a.Refusal` as a JSON string with no HTML escaping (as `encoding/json`'s `Encoder` writes it after `SetEscapeHTML(false)`), then `}` and one LF; in both cases it MUST return nil when `w` accepted every byte. So `Answer{Message: json.RawMessage(`{"jsonrpc":"2.0","id":1,"result":{"a":"<b>"}}`)}` is written as `{"message":{"jsonrpc":"2.0","id":1,"result":{"a":"<b>"}}}` and LF.
- R-7AHR-9OH2: `WriteAnswer` MUST return `ErrAnswer` (tested by `errors.Is`) and write nothing to `w` when both or neither of `a.Message` and `a.Refusal` are set (a `Message` that is empty or exactly `null` counting as not set), when `a.Message` is not exactly one JSON object with no surrounding whitespace, when `a.Message` contains an LF or CR byte, when `a.Message` is longer than `protocol.MaxBoxAnswer` bytes, or when the line it would write, LF excluded, is longer than `MaxAnswerLine` bytes; when `w` fails it MUST return that error (tested by `errors.Is`). It MUST hold no more than the one line it writes.

### Run and Serve

- R-42UO-JH5T: `Run(ctx, in, out, getenv)` MUST answer each line it reads from `in` as `Serve(ctx, in, out, Config{Socket: s, Timeout: t})` does for some positive `t`, where `s` is `getenv(EnvSocket)` when that is non-empty and `SocketPath` otherwise, and MUST call `getenv` with no name but `EnvSocket`; so that with a `getenv` answering a unix socket the test serves for `EnvSocket`, a `tools/list` line given to `Run` reaches that socket, and a recording `getenv` records no other name.
- R-7CXK-17YG: `Serve` MUST return a non-nil error without reading `in` or writing `out` when `cfg.Socket` is empty or `cfg.Timeout` is not positive.
- R-7E5G-EZP5: `Serve` MUST read `in` as a sequence of lines, each ended by LF, the last one also by end of file; a line is the bytes before its LF. A line of at most `protocol.MaxBoxRequest` bytes is one message, judged by R-7FDC-SRFU through R-7RKC-MGUS. A line that is empty or holds only JSON whitespace (space, tab, CR) MUST be skipped with nothing written.
- R-7FDC-SRFU: For a line longer than `protocol.MaxBoxRequest` bytes, `Serve` MUST write one JSON-RPC error response with `id` null, `code` `CodeInvalidRequest` and `message` `MsgTooLarge`, MUST discard the line's bytes through its LF without accumulating them, and MUST then go on with the next line; so that a stream holding a line of 256 MiB without an LF until its end, then a `ping` request line, is answered with that error and then the `ping`'s answer, and the test process's `runtime.MemStats.TotalAlloc` grows by less than 16 MiB over the call.
- R-7GL9-6J6J: For a message that is not valid JSON, `Serve` MUST write one JSON-RPC error response with `id` null, `code` `CodeParseError` and `message` `MsgParseError`; for valid JSON that is not an object, a JSON array of any length included, it MUST write exactly one JSON-RPC error response with `id` null, `code` `CodeInvalidRequest` and `message` `MsgInvalidRequest`; and it MUST dial nothing for either.
- R-7HT5-KAX8: For a JSON object that has no `method` member and has a `result` or an `error` member, `Serve` MUST write nothing and dial nothing.
- R-PUFI-9ZM2: Wherever this document's requirements name a member of a message read from `in` (`jsonrpc`, `id`, `method`, `params`, `result`, `error`), the name MUST match exactly, byte for byte and with case significant; a member named otherwise is an unknown member, except that a member whose name is not written byte for byte as `jsonrpc`, `id` or `method` but, its JSON escapes decoded, is one of them makes the object one `Serve` MUST answer as an Invalid Request below. A valid id is a JSON string or a JSON number written with neither a fraction nor an exponent, the same rule for every method, local or forwarded. For any JSON object not covered by R-7HT5-KAX8, `Serve` MUST write one JSON-RPC error response with `code` `CodeInvalidRequest` and `message` `MsgInvalidRequest`, and dial nothing, when the object holds such a member, when its `jsonrpc` member is not the string `2.0`, its `method` member is absent or not a string, or its `id` member is present and not a valid id; the response's `id` MUST be the object's `id` member, its bytes unchanged, when that is a valid id, and null otherwise. - R-7K8Y-BUEM: A valid request object with no `id` member (a notification), whatever its method, `notifications/initialized` and `notifications/cancelled` included, MUST NOT be answered and MUST NOT cause a dial.
- R-ISYS-K21D: A valid request with an `id` and the method `MethodInitialize` MUST be answered, without a dial, with a JSON-RPC result response carrying the request's `id`, its bytes unchanged, whose `result` is an object with exactly the members `protocolVersion`, `capabilities` and `serverInfo`: `protocolVersion` the request's `params.protocolVersion` when that is a string equal to an element of `ProtocolVersions()`, and `ProtocolVersions()[0]` in every other case (absent or non-object `params` included); `capabilities` exactly the object `{"tools":{}}`; and `serverInfo` an object whose `name` is `ServerName` and whose `version` is a non-empty string. It MUST be answered the same way however many times it comes and whatever came before it. So a request whose `params.protocolVersion` is `ProtocolVersions()[1]` (an older supported version) is answered with `ProtocolVersions()[1]`, not the latest, and one whose `params.protocolVersion` is `1900-01-01` is answered with `ProtocolVersions()[0]`.
