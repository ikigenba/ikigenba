# D07-tools

The thirty-six MCP tools agents run SSH hosting with, through the MCP gateway: `internal/tools`. They are the only API for the space's callers; a host's users reach the box tools at `/accountsd/v1/box` (`D19-box-tools`). An agent lists hosts with `hosts` and reads one with `host`; creates, stops, starts, resizes, retries and deletes hosts with `create_host`, `stop_host`, `start_host`, `resize_host`, `retry_host` and `delete_host`, keeping a deleted host's data volume or deleting it with the host; lists and deletes the data volumes kept from deleted hosts with `kept_volumes` and `delete_kept_volume` (/home/mgreenly/Documents/ikigenba-host-numbers-and-delete.md, cited as delete outcome N); lists and reads accounts with `accounts` and `account` and places and removes them with `create_account` and `remove_account`; lists users with `users`, adds one with `add_user`, keeps their keys with `add_key` and `remove_key`, and locks, unlocks and deletes them with `lock_user`, `unlock_user` and `delete_user` (outcome 9 of /home/mgreenly/Documents/ikigenba-ssh-hosts.md; outcomes cited as outcome N are that document's); sets or clears a user's admin flag with `set_admin`, and makes, lists and revokes the invite links a person joins an account by with `create_invite`, `list_invites` and `revoke_invite` (/home/mgreenly/Documents/ikigenba-self-service-accounts.md, cited as self-service outcome N); lifts a fail2ban ban with `unban_ip` and keeps a host's allowlist with `allow_ip` and `disallow_ip` (/home/mgreenly/Documents/ikigenba-ssh-bans.md, cited as bans outcome N); and keeps the hosts' backups (/home/mgreenly/Documents/ikigenba-host-backups.md, cited as backups outcome N, with its log, cited as backups log): closes a host and confirms it is fully backed up with `close_host` and lets people back in with `open_host`, puts a host on a new machine keeping its data volume or restored from backup with `replace_host`, reads each account's backup health with `backup_status` and what can be restored with `restore_points`, restores a database or files as of an earlier time beside the originals with `restore_database` and `restore_files`, and deletes a removed account's backups with `delete_account_backups`. Every signed-in caller reads and changes everything, admins included (self-service outcome 4); the caller is used only to record who created a host, an account, a user or an invite, by its user id (an invite a box call creates records the box actor, `ssh:` and the host user's name, `D19-box-tools`), and as the trail's user. The person who uses an invite is not a tool caller: the enrollment page (`D18-enrollment`) creates their user.

A tool never waits for AWS or a host. A changing tool checks its arguments (`D17-names-keys-sizes`), checks the record, writes its change in one store transaction (`D04-store`), wakes the operations engine when it started an operation (`D10-operations`), tells its events (`D08-trail`) and answers at once with what it recorded. What happens next is the engine's and the host daemon's: a host's state moves on, an account turns active, a user's change, an unban or an allowlist edit stops being pending, and the reads show it. The admin flag and invites are accounts' alone: they never reach a host, so `set_admin`, `create_invite` and `revoke_invite` raise no desired-state version and leave nothing pending. The two calls a tool makes outside the record are `create_account`'s: its DNS check (outcome 2), which before it reserves `<slug>.<hosts domain>` asks Route 53 whether anything is already there, and its backups check (backups outcome 45), which then asks S3 whether the backups bucket holds anything under the account's prefix; `create_invite` also asks `Config.AccountsURL` for the link's base, which reads the services file. Reads touch only the record.

Where the tools are mounted, and how the run builds `tools.Config`, is `D03-serve`'s; the tools page, which lists `mcp.Server.Tools()` in the order `Register` registers them, each description cut with `tools.FirstLine`, is `D06-pages'`; the landing page's four lists share the tokens of `hosts`, `kept_volumes`, `accounts` and `users`.

## The tools

In catalog order, each with the effect appkit's `mcp` registers it with:

- `hosts` (read) takes `page` and `limit`; answers live hosts in creation order, each with its name, its DNS name `<host>.<hosts domain>`, state, reason (its failure reason, or when it has none why its own DNS record could not be made), health, type, volume sizes, Elastic IP, account count, last report time, when its last close finished (`closed`, empty while open) and the mode of a replace it is in (`replace`, `volume` or `backup`, empty otherwise), then `next`.
- `host` (read) takes `host`; answers that host with its instance id, data volume, desired and applied versions, created time and creator, its accounts' slugs, its allowlist as the record holds it, the operation its state names, and its latest report, whose `bans`, `ban_total` and `allowlist` are what the host last saw and applied (`D11-protocol`), so the two allowlists can be compared (bans outcome 13), and whose `hostname` is the static hostname the host last reported, so it can be compared with `dns_name` (host names outcome 14, /home/mgreenly/Documents/ikigenba-host-names.md, cited as host names outcome N).
- `create_host` (additive) takes optional `type`, `root_gb` and `data_gb` (defaults `t4g.medium`, 20, 50); records a new host `provisioning` and its `create` operation.
- `stop_host`, `start_host` (additive) take `host`; a running host stops, a stopped one starts.
- `resize_host` (additive) takes `host` and at least one of `type`, `root_gb`, `data_gb`; volumes only grow; a type change on a running host stops and starts it, and the answer says so (`restarts`, outcome 16).
- `retry_host` (additive) takes `host`; a failed host's operation resumes from its recorded step.
- `delete_host` (destructive) takes `host` and optional `keep_data` (true when absent) and `lost` (false when absent); refused while the host holds an account that is not being removed, whatever the choice; with `keep_data` true or absent the data volume is kept, tagged orphaned, exactly as before; with `keep_data` false the delete also deletes the host's data volume and the host's own key backup, which cannot be undone (`D10-operations`), and is refused `HostNotClosed` unless the host's close has finished or `lost` says the host is already dead (backups outcomes 26 and 46). The answer, `hosts` and `host` carry the choice as `on_delete` (`keep` or `delete`) while the host's operation is that delete, empty otherwise (delete outcomes 7, 11 to 13).
- `kept_volumes` (read) takes `page` and `limit`; answers the data volumes kept from deleted hosts, the most recently deleted host's first, each with its volume id, the host's name as it was, why it was kept (`cause`: `deleted` for a deleted host's, `replaced` for the old data volume of a replace from backup), its size, when the host was deleted, its state (`kept`, or `deleting` while its delete runs) and the reason its last delete was refused, then `next` (delete outcomes 14 and 16). Only volumes accounts' own record explains are listed; a stray is never listed.
- `delete_kept_volume` (destructive) takes `volume`, a volume id `kept_volumes` answered; a `kept` volume turns `deleting` and the engine deletes it in AWS, which cannot be undone; answers the volume as it now is (delete outcome 15).
- `accounts` (read) takes `page` and `limit`; answers accounts by slug, each with its host, DNS name, state, failure reason, user count, unexpired invite count, created time and creator, then `next`.
- `account` (read) takes `account`; answers it with its users' names and its operation.
- `create_account` (additive) takes `account` and `host`; places a new account on that host, `pending` until its DNS record is in sync and the host has applied it.
- `remove_account` (destructive) takes `account`; refused while it has users; a `failed` account, or one whose removal failed, is removed this way too; its DNS record goes and the host drops its group and service account, keeping `/srv/<slug>`.
- `users` (read) takes optional `account`, `page` and `limit`; answers users by account then name, each with its admin flag, its state, whether a change is pending on the host, its keys, last sign-in, created time and creator, then `next`.
- `add_user` (additive) takes `account`, `user` and `key`; every user starts with one key in one account.
- `add_key` (additive), `remove_key` (destructive) take `account`, `user` and `key`; `remove_key` says how many keys are left.
- `lock_user`, `unlock_user` (additive) take `account` and `user`; locking ends access and keeps everything.
- `delete_user` (destructive) takes `account` and `user`; only a locked user; the user turns `removing` and its row goes once the host applied the removal.
- `set_admin` (additive) takes `account`, `user` and `admin`; sets or clears the user's admin flag (self-service outcomes 1, 2 and 4); the flag never reaches the host, so the user's `pending` is left as it was; answers the user's change, as `lock_user` does.
- `create_invite` (additive) takes `account` and optional `admin` (false when absent); records an invite that lasts `store.InviteLife`, 72 hours, and answers it with its link, `<accounts URL>/join?token=<token>`, the one time the token is ever answered (self-service outcomes 5, 7, 9 and 10); an account holds at most `store.MaxInvites`, 20, unexpired invites.
- `list_invites` (read) takes `account`; answers its unexpired invites, oldest first, each with its id, admin flag, created and expiry times and creator, never its link; at most 20, so no `next`.
- `revoke_invite` (destructive) takes `invite`, an invite id; an unexpired, unused invite is deleted and answered as it was; its link then shows the page's one unusable answer (self-service outcomes 7 and 13).
- `unban_ip` (additive) takes `ip` and optional `host`; one address, never a CIDR; with a host, that running host, and with none, every running host; the address is a pending unban until the host applies it; answers the address in canonical form, the host named or empty, and how many hosts now hold it pending.
- `allow_ip` (additive), `disallow_ip` (destructive) take `host` and `ip`; an address or a CIDR no wider than /24 (IPv4) or /48 (IPv6); edit the host's allowlist on any live host not being deleted, applied when it runs; answer the entry in canonical form, the host's allowlist after the call and whether a change is pending. Allowing an entry also lifts the bans it covers, on the host's next cycle (`D15-machine`).
- `close_host` (additive) takes `host`; a running host turns `closing`: its users are locked and their sessions end, Litestream finishes sending, restic takes a final snapshot of each account and of the host key, and once every account's final backup is done the host is `running` again with `closed` set (backups outcomes 24 and 27); a host already closed, running or stopped, answers its state and no operation.
- `open_host` (additive) takes `host`; a closed running host, or one closing or whose close failed, turns `opening` (a closed host that was then stopped is started first), a running close is cancelled, `closed` is cleared, and the host is `running` once it has unlocked its users (backups outcome 25).
- `replace_host` (destructive) takes `host`, `from` (`volume` or `backup`) and optional `type`, `root_gb` and `data_gb` (the host's own when absent); the host keeps its record, name, address, accounts and users; its old instance is terminated, a new one launched, and the old data volume attached (`volume`) or a new empty one restored from backup (`backup`, the old one kept as a kept volume with `cause` `replaced`); nobody signs in until the restore is complete (backups outcomes 28 to 35). `data_gb` is refused with `from` `volume`, since the kept volume keeps its size.
- `backup_status` (read) takes optional `host`, `page` and `limit`; answers every account by slug, removed accounts whose backups remain included, each with its host, state, health (`healthy`, `stale`, `error` or `none`), last snapshot, last check, error, database counts, oldest sync, newest write, its final backup in the host's latest close and when that final finished (`final_at`), its restore in a replace from backup, when its facts were reported, and, for a removed account, the state of its backups delete (`delete`) and why it failed (`delete_reason`), then `next` (backups outcomes 20 to 23).
- `restore_points` (read) takes `account`; answers the snapshots its host last reported for it, newest first, and each database with its health and restorable range (backups outcome 41).
- `restore_database` (additive) takes `account`, `path` (a database below the account folder's `data/`) and `as_of`; `restore_files` (additive) takes `account`, `snapshot` and optional `user` and `path` (the whole folder or home when absent); each records a pending restore the host writes beside the original, never over it, and answers it (backups outcomes 37 to 40).
- `delete_account_backups` (destructive) takes `account`, the slug of a removed account; refused while an account of that slug exists; the engine deletes everything under the account's prefix, which cannot be undone, and until then `backup_status` shows it `removed` (backups outcomes 43 to 45).

## Checks and refusals

Each changing tool checks in one order and refuses at the first failing check, before anything is written: configured, then argument shape (`D17-names-keys-sizes`: `valid.Slug`, `valid.Name`, `valid.ParseKey`, `valid.Type`, `valid.RootGB`, `valid.DataGB`, `valid.Address`, `valid.AllowEntry`, `valid.RestorePath`, `valid.DatabasePath`, and an RFC 3339 time for `as_of` and `snapshot`), then the record's state, then, for `create_account` alone, the DNS check and then the backups check. A refusal is an MCP error result with one text block holding exactly one copy constant: the refusal constants below, `store.Unreachable` when the record cannot be read or written, or one of appkit's paging texts. A changing call whose change is already so (a key the user holds, a user already locked or active, a user already removing, an address already pending on the host, an allowlist entry already held or not held) answers as a success and changes nothing.

The three address tools check in this order. `unban_ip`: `InvalidAddress`; then, with a host named, `NoHost`, `HostNotRunning`, already pending (ok), `TooManyUnbans`; with none, `TooManyUnbans` when any running host that lacks the address is at the cap, all or nothing. `allow_ip` and `disallow_ip`: `InvalidAddress` or `PrefixTooWide`, `NoHost`, `HostGone` (a host being deleted); then `allow_ip` already held (ok), `AllowlistFull`; `disallow_ip` not held (ok). Each tool canonicalizes its `ip` before it reaches the store, so the store, the desired state, the answer and the trail hold the same string.

The four admin and invite tools check in this order. `set_admin`: the user check (`NoAccount`, `NoUser`, `NotInAccount`, `UserRemoving`); then the flag already as asked (ok). `create_invite`: `NoLink` when there is no link base (`Config.AccountsURL` nil or failing), before the record is read and even while the store fails; then `NoAccount`, `AccountRemoving`, `TooManyInvites`. `revoke_invite`: `NoInvite` for an id `store.ValidInviteID` refuses, before the record is read; then `NoInvite` for an invite that is unknown, used, revoked or expired, one answer for all. `list_invites`: `NoAccount`; a removing account answers `[]`, since removal deleted its invites.

The two kept-volume tools check in this order. `kept_volumes`: the paging refusals, before the record is read. `delete_kept_volume`: `NoKeptVolume` for an id that is not a kept volume in state `kept` or `deleting` (unknown, a live host's data volume, a stray, one already deleted: one answer for all); then `VolumeDeleting` for one whose delete is already running. A volume whose last delete was refused is back in `kept` with its reason, and `delete_kept_volume` of it again is the retry.

The backup tools check in this order. `close_host`: `NoHost`, `HostBusy` (any of the transitional states, `closing`, `opening`, `replacing` and `restoring` included), `HostFailed`, then a host already closed answers (ok), then `HostNotRunning`. `open_host`: `NoHost`, `HostBusy` (a transitional state other than `closing`), `HostNotClosed` unless its users are locked by a close that no open has ended (`D04-store`'s locked over), then `HostNotRunning` for such a host that is not running and whose operation is not a close (a closed host that was then stopped is started first). `replace_host`: `BadReplace`, `TypeNotAllowed`, `SizeOutOfRange`, `KeepsVolumeSize`, all before the record; then `NoHost`, `HostBusy`, `HostFailed` (a host whose failed operation is a delete), `NoDataVolume` (for `volume`), `NoAddress` (a host whose create failed before it had an Elastic IP). `restore_database`: `InvalidPath`, `BadTime`, then `NoAccount`, `AccountNotActive`, `HostNotRunning`, `NoDatabase`, `NotRestorable`, `TooManyRestores`. `restore_files`: `InvalidPath`, `BadTime`, then `NoAccount`, `NoUser` and `NotInAccount` when a user is named, `AccountNotActive`, `HostNotRunning`, `NoSnapshot`, `TooManyRestores`. `TooManyRestores` counts the host's unfinished restores (`D04-store`), those still pending or whose operation is still running, so a restore a report has finished still counts until the engine settles its operation, and the restores `remove_account` cancels are bounded by that cap. Both restore tools take their time to the whole second, UTC. `backup_status`: the paging refusals, then `NoHost` for a named host that is not live. `restore_points`: `NoAccount`. `delete_account_backups`: `InvalidName` or `ReservedName`, `AccountExists`, then a delete already running answers (ok). `delete_host` adds `HostNotClosed` after `HostHasAccounts`; `create_account` adds `NameHasBackups` (or `CloudFailed`) after the DNS check. Every stop, start, resize and delete refuses `HostBusy` on a host `closing`, `opening`, `replacing` or `restoring`, and works on a closed host, which stays closed.

On a space whose configuration names no hosts (`Configured` false, `D01-layout-and-run-seam`), every tool, the reads included, is refused with `NotConfigured` and reads nothing.

## Events

An accepted changing call tells exactly one `change.finished` (`D08-trail`) with its tool, host, account, user, address and result. The address (`ip`) is the canonical form of what `unban_ip`, `allow_ip` or `disallow_ip` was given, empty when the call's `ip` was refused and for every other tool; an `unban_ip` naming no host tells one event with an empty host (bans outcome 16). The result is `ok` for a success, already-in-state included; `failed` for `CloudFailed` and `store.Unreachable`; `refused` for every other refusal. Before it, a call that started an operation tells, in order: for `remove_account` over a running `place`, that place's `operation.finished` with status `cancelled`; the `host.changed` or `account.changed` of the state its write made; and the new operation's `operation.started` (for `retry_host`, again, with the same id). A delete's `operation.started` carries the choice as `data` (`store.OnDeleteKeep` or `store.OnDeleteDelete`), every other operation's an empty `data`. The engine tells the rest of the operation's life. The three address tools start no operation and tell nothing but their `change.finished`; a ban the host reports is not an event (bans outcome 5), and nothing read from a report, a ban's address included, reaches the trail.

`delete_kept_volume` starts no operation but wakes the engine, as an operation tool does, since the engine does the delete. An answered call tells `volume.changed` (`trail.VolumeChanged`, from `kept` to `deleting`) and then its `change.finished`, whose `host` is the volume's host (empty when the id names no kept volume) and whose `account`, `user` and `ip` are empty; a refused call tells `change.finished` alone. The engine tells the volume's later changes. `kept_volumes` is a read and tells nothing of its own.

The admin and invite tools start no operation either (self-service outcome 27). An answered `create_invite` tells `invite.created` (`trail.InviteCreated`), an answered `revoke_invite` `invite.revoked` (`trail.InviteRevoked`), and a `set_admin` that changed the flag `admin.changed` (`trail.AdminChanged`), each before its `change.finished`; a refused call, and a `set_admin` already as asked, tell none of them. `set_admin`'s `change.finished` names the account's host, account and user; `create_invite`'s the account's host and account; `revoke_invite`'s the revoked invite's account and host, both empty when it revoked nothing. A `NoLink` refusal is `refused`, as every refusal but `CloudFailed` and `store.Unreachable` is. `invite.used` is the enrollment page's (`D18-enrollment`), never a tool's. The token reaches no event: the invite's id names it.

The backup tools tell nothing new. `close_host`, `open_host` and `replace_host` tell as every host operation tool does: `host.changed` to `closing`, `opening` or `replacing`, `operation.started` with kind `close`, `open` or `replace` and an empty `data`, then `change.finished`; an `open_host` that cancelled a running close tells that close's `operation.finished` with status `cancelled` first, as `remove_account` does for a `place`. `restore_database` and `restore_files` tell `operation.started` with kind `restore`, the account and its host, then `change.finished`; a restore changes no host's or account's state, so it tells no `host.changed` or `account.changed`, and its path and time are never told (`D08-trail`). `delete_account_backups` starts no operation and tells its `change.finished` alone, with the account and an empty host, then wakes the engine. A `close_host` of a closed host and a `delete_account_backups` already running tell `change.finished` alone and wake nothing. `replace_host` cancels the host's pending partial restores in its transaction and tells each one's `operation.finished` with status `cancelled`, with the restore's account, before its `host.changed`: exactly the ids `ReplaceHost` answers as its third result (`D04-store`), in their ascending order, as `remove_account` does. A `remove_account` that cancels the account's running restores tells each one's `operation.finished` with status `cancelled`, as it does a cancelled `place`, before its `account.changed`: exactly the ids `RemoveAccount` answers as its third result (`D04-store`), in their ascending order. A `delete_host` tells its choice as `data`, never `lost`.

## Recorded decisions

- **Tool names** (pick): accounts' existing `<verb>_<noun>` form, a plural noun for a list and a singular for one read. The six group and membership tools (`groups`, `group`, `create_group`, `remove_group`, `add_member`, `remove_member`) are deleted: a user is in exactly one account, fixed at `add_user`.
- **Every tool refuses `NotConfigured` when the space operates no hosts**, the reads included: the record is empty there and an answer would mislead an agent into thinking hosts could exist; one word for the whole catalog.
- **Check order** (configured, shape, record, DNS last): a refusal the record can make never costs an AWS call, and a malformed argument never costs a database read.
- **Tools tell `host.changed` and `account.changed` for the transitions their own writes commit**, the engine for the rest (`D08-trail`), so each change is told once by the code that committed it.
- **`remove_account` tells the cancelled `place`'s `operation.finished`**: the store cancels it in the same transaction that starts the `unplace` (`D04-store`), the engine never sees it end, and the tool is the only code that knows.
- **`operation` in `host` and `account` is the one the state names**: a host in `provisioning`, `stopping`, `starting`, `resizing`, `deleting`, `closing`, `opening`, `replacing` or `restoring` has exactly one running host operation, and a `failed` host the failed one; an account's running `place` or `unplace`, or the failed `place` of a `failed` account, or the failed `unplace` of a `removing` one. A settled host or account answers no operation.
- **`report` is the stored `protocol.Report` as JSON, typed `json.RawMessage`** (`D11-protocol`), and `reported` is when it was received: appkit v0.32.0's output-schema builder refuses `time.Time` and arrays, both of which `protocol.Report` holds (`Booted`, sign-in times, `Load`), so a typed field would make `Register` panic; the raw value relays what the daemon said without restating its schema here.
- **Keys are stored canonical**: the store is handed `valid.Key.Line()`, never the argument as written, so the tools' answers, the desired state and the host's `authorized_keys` agree byte for byte.
- **Health is computed with the writer's clock** (`telemetry.Writer.Now`, the run's `Now`): `tools.Config` carries no clock of its own, and the trail and the health agree on the time.
- **`users` lists every user when `account` is absent** (departure from the per-owner listing other apps use): the landing's users list shares its token, and agents ask "who is on this host" across accounts.
- **Naming a user with an account it is not in answers `NotInAccount`**, not `NoUser`: names are global and listed, so saying so hides nothing, and it tells the agent its account argument is wrong.
- **`delete_user` of a user already `removing` answers ok**, as every already-in-state change does; `lock_user`, `unlock_user`, `add_key` and `remove_key` of a `removing` user refuse `UserRemoving`, since the change could never be applied.
- **`AccountFull` refuses a user whose account's host already holds `valid.MaxUsersPerHost` users**, `HostFull` an account on a host holding `valid.MaxAccountsPerHost`: each names what the agent tried to add to.
- **`GrowLimit` is the store's refusal** (`store.ErrGrowLimit` from `StartHostOp`, counted against the store's own clock, `D04-store`): EC2 allows four modifications of a volume in 24 hours (facts), and refusing early beats an operation stuck in back-off; the tool keeps no second count and no second clock.
- **A host change answers `{host, state, operation}`**, not the full host: the state is the transitional one the write set, and the operation id is what an agent follows with `host`.
- **Argument descriptions are seventeen copy constants**, one per member name, since each member means the same in every tool: `ArgHost`, `ArgAccount`, `ArgUser`, `ArgKey`, `ArgType`, `ArgRootGB`, `ArgDataGB`, `ArgIP`, `ArgAdmin`, `ArgInvite`, `ArgKeepData`, `ArgVolume`, `ArgFrom`, `ArgLost`, `ArgPath`, `ArgAsOf` and `ArgSnapshot`. Each constant is the copy's one home, and the struct tag of every field carrying that member repeats it verbatim: a recorded departure from `spec`'s Copy rule, extending to these constants the one exception it makes for appkit's paging members, because appkit v0.32.1 reads a member's description only from the field's tag and offers no other route, and no asset can carry it (`assets/tools.html` receives only each tool's name and the first line of its description). The schema requirements (R-YJIB-9CDJ, R-YKQ7-N448, R-YLY4-0VUX, R-YN60-ENLM, R-ZDGD-9JHM, R-CTL6-NUKD, R-CUT3-1MB2, R-CW0Z-FE1R, R-GS2Q-QFV3, R-0YDM-6J88, R-HMK8-APEG, R-HNS4-OH55, R-HP01-28VU and R-HQ7X-G0MJ) bind each tag to its constant through `ListTools`, so a build may and must mirror the constant in the tag. The box tools reuse `ArgKey`, `ArgInvite` and `ArgAdmin` but declare their own `box.ArgUser` (`D19-box-tools`), since a box `user` is always a user of the caller's own account.
- **Lists are keyset windows** (`shape/` Listing and Storage): `hosts` over the host's creation sequence (name order up to `host99`, creation order beyond, where byte order would put `host100` before `host20`), `accounts` over the slug, `users` over account then name. Each call holds one window and one row (`D04-store`'s listing reads), and `host`/`account` hold one entity and its children, bounded by `valid`'s caps.
- **The DNS check is bounded** by `DNSCheckTimeout`, five seconds: a slow Route 53 answers `CloudFailed`, and the agent retries.
- **Store guard errors map one to one** (`D04-store`): a race the tool's own read did not see is refused by the store, and the tool words it: `store.ErrTaken` `NameTaken`; `store.ErrBusy` `HostBusy`; `store.ErrHostFailed` `HostFailed`; `store.ErrNotFailed` `HostNotFailed`; `store.ErrNotRunning` `HostNotRunning`; `store.ErrNotStopped` `HostNotStopped`; `store.ErrHasAccounts` `HostHasAccounts`; `store.ErrHostFull` `HostFull`; `store.ErrHostGone` `HostGone`; `store.ErrNothingToChange` `NothingToChange`; `store.ErrShrinks` `SizeShrinks`; `store.ErrGrowLimit` `GrowLimit`; `store.ErrHasUsers` `AccountHasUsers`; `store.ErrAccountRemoving` `AccountRemoving`; `store.ErrAccountFull` `AccountFull`; `store.ErrTooManyKeys` `TooManyKeys`; `store.ErrNotLocked` `UserNotLocked`; `store.ErrUserRemoving` `UserRemoving`; `store.ErrNotInAccount` `NotInAccount`; `store.ErrKeyNotHeld` `KeyNotHeld`; `store.ErrTooManyUnbans` `TooManyUnbans`; `store.ErrAllowlistFull` `AllowlistFull`; any other `store.ErrNotFound` `NoHost`, `NoAccount` or `NoUser` by what the call named. No central tool's behaviour changes for the box, and the central tools keep full control. The one change here is the caller's length: the store records a caller's `UserID` only when it is at most `valid.MaxUserIDBytes` bytes (`D04-store`, `D17-names-keys-sizes`), which holds auth's user ids and the box actor alike, so the tool requirements denote only a call whose caller's `UserID` is that long or shorter (R-ESC3-AJ89); a longer one comes only from a forged header.
- **Host DNS names** (host names outcomes 13 and 14, decisions A6): `tools.Host` and `tools.HostRead` gain `DNSName`, JSON `dns_name`, right after `Host`, the member name and place the account answers already use (`account`, `host`, `dns_name`). In the binary, `Configured` implies a non-empty `Domain` (`D01-layout-and-run-seam`); at this package's seam `Configured` and `Hosts` are independent (R-ESC3-AJ89), and, as for the account answer, no empty case is stated. Additions only: no member is removed or renamed, and `HostChange` and `HostResize` are unchanged, since they answer the transitional state, not the host.
- **A host's `reason` is its failure reason, or when that is empty its record reason** (`D04-store`'s `Host.RecordReason`, set and cleared by the engine's scan, `D10-operations`): one member, as the page shows one (`D06-pages`), so an agent sees why a live host's own record could not be made without a new member, and a failed host's failure, which is what it must act on first, is never hidden by a record conflict. A conflict never fails or stops a host, so a running host with a non-empty `reason` means exactly that.

Whether the name is applied is the agent's comparison of `report.hostname` with `dns_name`.

- **A closed host is not refused `close_host`** (pick, backups log): a host whose close has finished, running or stopped, answers its state and no operation and changes nothing, as every already-in-state change does; the check comes before `HostNotRunning`, so a stopped closed host is answered, not refused.
- **`open_host` may cancel a running close** (pick, backups log): an operator who closed a host by mistake opens it at once; the close is cancelled in the open's transaction and the tool tells its `operation.finished`, since the engine never sees it end.
- **`replace_host` checks the argument shape first, then `NoHost`, `HostBusy`, `HostFailed`, `NoDataVolume`, `NoAddress`**: the record's refusals come from the store's `ReplaceHost` (`D04-store`), so the tool follows its order; a failed delete is refused first because its way on (`retry_host` or a new `delete_host`) is what the agent must hear before anything about volumes or addresses. `from` is a required string the tool checks (`BadReplace`) rather than an enumeration in the schema, as every other word argument is. `data_gb` with `from` `volume` is refused `KeepsVolumeSize`, since the kept volume keeps its size and a silent ignore would mislead.

It is keyed by slug with its own token, `paging.Token{Tool: "backup_status"}`, and lists removed accounts whose backups remain with state `removed`, since those are the backups `delete_account_backups` acts on.
- **Health is computed, never stored** (backups outcome 22): `store.BackupHealth` and `store.DatabaseHealth` with the store's backup settings and the writer's clock, as host health is.
- **`restore_points` caps what it answers** (local pick): the newest `protocol.MaxSnapshots` snapshots and the first `protocol.MaxDatabases` databases by path, the caps the daemon's report already keeps (`D11-protocol`), so the answer stays bounded even for a stored report that exceeds them; `database_total` still counts every database.

A removed account's name is held by its backups, not by the record, so the check asks S3, the one source of truth; in the sandbox it reads the memory cloud.

- **Store guard errors of the backup methods map one to one** (`D04-store`): `store.ErrNotClosed` `HostNotClosed`; `store.ErrNoDataVolume` `NoDataVolume`; `store.ErrNoAddress` `NoAddress`; `store.ErrAccountNotActive` `AccountNotActive`; `store.ErrNoDatabase` `NoDatabase`; `store.ErrNoSnapshot` `NoSnapshot`; `store.ErrNoUser` `NoUser` (from `RequestRestore` for a named user it does not hold, matched before `ErrNotFound`, which it matches, so it is never read as `NoAccount`); `store.ErrNotRestorable` `NotRestorable`; `store.ErrTooManyRestores` `TooManyRestores`; `store.ErrAccountExists` `AccountExists`; `store.ErrBackupsDeleting` `BackupsDeleting`; each matched before `ErrConflict` and `ErrNotFound`, which they match. `ErrBusy`, `ErrHostFailed` and `ErrNotRunning` from the new methods map as before (`OpenHost`'s `ErrNotRunning` to `HostNotRunning`), and `PlaceAccount`'s `ErrBackupsDeleting` to `BackupsDeleting`. `NameHasBackups` is the tool's own cloud check and maps no store error.
- **Expand then contract at this seam**: every change here is an addition. `closed`, `replace` and `cause` are new members, `lost` a new optional member whose absence is today's delete, and the eight tools are new names; no member is removed or renamed and no existing answer changes shape, so an agent that knows only the previous release's tools reads this release's answers. A kept volume the previous release recorded answers `cause` `deleted` (`D04-store`). The new kinds' operations live where the previous release never reads (`D04-store`, `D10-operations`), so during a rollback its tools may refuse a host in a new state; that cost is the store's and recorded there.
- **A removed account's backups delete is shown in `delete` and `delete_reason`** (root pick): `error` on a removed account's entry already carries the account's last backup error, kept with its removed backups (`D04-store`), so putting a failed delete's reason there would hide that error and leave an agent unable to tell the two apart; two members at the end, `delete` (the backups delete's state, `deleting` or `failed`, empty when none) and `delete_reason` (its reason when failed), say it without ambiguity and also show a delete still running. `tools.AccountBackups` is this document's alone (the host page has its own `pages.BackupRow`, and the box tools do not use it), so the addition touches no other document. - **Bounded work**: `close_host`, `open_host` and `replace_host` hold one host; the restore tools one account, its host and one stored report; `restore_points` one stored report; `backup_status` one window and one row, as `accounts` does (`D04-store`'s `ListBackups`); `delete_account_backups` one row. ## Consumer usage

`web.Handler` (`D03-serve`) calls `tools.Register(srv, tools.Config{Store: st, Cloud: c, Hosts: hosts, Configured: configured, Wake: engine.Wake, Telemetry: w, AccountsURL: func() (string, error) { return cfg.Settings.AccountsURL(cfg.ServicesPath) }})` once.

Consumer tasks, against the declared names:

1. `create_host{}` → `tools.HostChange{Host: "host01", State: "provisioning", Operation: "op_…"}`; `hosts{}` → `tools.HostList{Hosts: []tools.Host{{Host: "host01", DNSName: "host01.metaspot.org", State: "provisioning", Health: "none", Type: "t4g.medium", RootGB: 20, DataGB: 50, …}}}`; later `host{host: "host01"}` → `tools.HostRead{Host: "host01", DNSName: "host01.metaspot.org", …, State: "running", Report: json.RawMessage(`{"protocol":1,…,"hostname":"host01.metaspot.org"}`)}` (decoded with `json.Unmarshal` into a `protocol.Report`, whose `Hostname` equal to `DNSName` says the name is applied).
2. A taken host name found by the engine's scan (`D10-operations`): `hosts` and `host` answer the running `host01` with `State: "running"`, `DNSName: "host01.metaspot.org"` and `Reason` the record conflict; once the scan finds the record right, `Reason: ""`. A failed host answers its failure reason whatever its record reason.
