# D07-tools

The twenty-six MCP tools agents run SSH hosting with, through the MCP gateway: `internal/tools`. They are the only API for the space's callers; a host's users reach the box tools at `/accountsd/v1/box` (`D19-box-tools`). An agent lists hosts with `hosts` and reads one with `host`; creates, stops, starts, resizes, retries and deletes hosts with `create_host`, `stop_host`, `start_host`, `resize_host`, `retry_host` and `delete_host`; lists and reads accounts with `accounts` and `account` and places and removes them with `create_account` and `remove_account`; lists users with `users`, adds one with `add_user`, keeps their keys with `add_key` and `remove_key`, and locks, unlocks and deletes them with `lock_user`, `unlock_user` and `delete_user` (outcome 9 of /home/mgreenly/Documents/ikigenba-ssh-hosts.md; outcomes cited as outcome N are that document's); sets or clears a user's admin flag with `set_admin`, and makes, lists and revokes the invite links a person joins an account by with `create_invite`, `list_invites` and `revoke_invite` (/home/mgreenly/Documents/ikigenba-self-service-accounts.md, cited as self-service outcome N); and lifts a fail2ban ban with `unban_ip` and keeps a host's allowlist with `allow_ip` and `disallow_ip` (/home/mgreenly/Documents/ikigenba-ssh-bans.md, cited as bans outcome N). Every signed-in caller reads and changes everything, admins included (self-service outcome 4); the caller is used only to record who created a host, an account, a user or an invite, by its user id (an invite a box call creates records the box actor, `ssh:` and the host user's name, `D19-box-tools`), and as the trail's user. The person who uses an invite is not a tool caller: the enrollment page (`D18-enrollment`) creates their user.

A tool never waits for AWS or a host. A changing tool checks its arguments (`D17-names-keys-sizes`), checks the record, writes its change in one store transaction (`D04-store`), wakes the operations engine when it started an operation (`D10-operations`), tells its events (`D08-trail`) and answers at once with what it recorded. What happens next is the engine's and the host daemon's: a host's state moves on, an account turns active, a user's change, an unban or an allowlist edit stops being pending, and the reads show it. The admin flag and invites are accounts' alone: they never reach a host, so `set_admin`, `create_invite` and `revoke_invite` raise no desired-state version and leave nothing pending. The one call a tool makes outside the record is `create_account`'s DNS check (outcome 2): before it reserves `<slug>.<hosts domain>` it asks Route 53 whether anything is already there; `create_invite` also asks `Config.AccountsURL` for the link's base, which reads the services file. Reads touch only the record.

Where the tools are mounted, and how the run builds `tools.Config`, is `D03-serve`'s; the tools page, which lists `mcp.Server.Tools()` in the order `Register` registers them, each description cut with `tools.FirstLine`, is `D06-pages'`; the landing page's three lists share the tokens of `hosts`, `accounts` and `users`.

## The tools

In catalog order, each with the effect appkit's `mcp` registers it with:

- `hosts` (read) takes `page` and `limit`; answers live hosts in creation order, each with its name, state, failure reason, health, type, volume sizes, Elastic IP, account count and last report time, then `next`.
- `host` (read) takes `host`; answers that host with its instance id, data volume, desired and applied versions, created time and creator, its accounts' slugs, its allowlist as the record holds it, the operation its state names, and its latest report, whose `bans`, `ban_total` and `allowlist` are what the host last saw and applied (`D11-protocol`), so the two allowlists can be compared (bans outcome 13).
- `create_host` (additive) takes optional `type`, `root_gb` and `data_gb` (defaults `t4g.medium`, 20, 50); records a new host `provisioning` and its `create` operation.
- `stop_host`, `start_host` (additive) take `host`; a running host stops, a stopped one starts.
- `resize_host` (additive) takes `host` and at least one of `type`, `root_gb`, `data_gb`; volumes only grow; a type change on a running host stops and starts it, and the answer says so (`restarts`, outcome 16).
- `retry_host` (additive) takes `host`; a failed host's operation resumes from its recorded step.
- `delete_host` (destructive) takes `host`; refused while the host holds an account that is not being removed; the data volume is kept, tagged orphaned (`D10-operations`).
- `accounts` (read) takes `page` and `limit`; answers accounts by slug, each with its host, DNS name, state, failure reason, user count, unexpired invite count, created time and creator, then `next`.
- `account` (read) takes `account`; answers it with its users' names and its operation.
- `create_account` (additive) takes `account` and `host`; places a new account on that host, `pending` until its DNS record is in sync and the host has applied it.
- `remove_account` (destructive) takes `account`; refused while it has users; a `failed` account, or one whose removal failed, is removed this way too; its DNS record goes and the host drops its group and service account, keeping `/srv/<slug>`.
- `users` (read) takes optional `account`, `page` and `limit`; answers users by account then name, each with its admin flag, its state, whether a change is pending on the host, its keys, last sign-in, created time and creator, then `next`.
- `add_user` (additive) takes `account`, `user` and `key`; every user starts with one key in one account.
- `add_key` (additive), `remove_key` (destructive) take `account`, `user` and `key`; `remove_key` says how many keys are left.
- `lock_user`, `unlock_user` (additive) take `account` and `user`; locking ends access and keeps everything.
- `delete_user` (destructive) takes `account` and `user`; only a locked user; the user turns `removing` and its row goes once the host applied the removal.
- `set_admin` (additive) takes `account`, `user` and `admin`; sets or clears the user's admin flag (self-service outcomes 1, 2 and 4); the flag never reaches the host, so the user's `pending` is left as it was; answers the user's change, as `lock_user` does.
- `create_invite` (additive) takes `account` and optional `admin` (false when absent); records an invite that lasts `store.InviteLife`, 72 hours, and answers it with its link, `<accounts URL>/join?token=<token>`, the one time the token is ever answered (self-service outcomes 5, 7, 9 and 10); an account holds at most `store.MaxInvites`, 20, unexpired invites.
- `list_invites` (read) takes `account`; answers its unexpired invites, oldest first, each with its id, admin flag, created and expiry times and creator, never its link; at most 20, so no `next`.
- `revoke_invite` (destructive) takes `invite`, an invite id; an unexpired, unused invite is deleted and answered as it was; its link then shows the page's one unusable answer (self-service outcomes 7 and 13).
- `unban_ip` (additive) takes `ip` and optional `host`; one address, never a CIDR; with a host, that running host, and with none, every running host; the address is a pending unban until the host applies it; answers the address in canonical form, the host named or empty, and how many hosts now hold it pending.
- `allow_ip` (additive), `disallow_ip` (destructive) take `host` and `ip`; an address or a CIDR no wider than /24 (IPv4) or /48 (IPv6); edit the host's allowlist on any live host not being deleted, applied when it runs; answer the entry in canonical form, the host's allowlist after the call and whether a change is pending. Allowing an entry also lifts the bans it covers, on the host's next cycle (`D15-machine`).

## Checks and refusals

Each changing tool checks in one order and refuses at the first failing check, before anything is written: configured, then argument shape (`D17-names-keys-sizes`: `valid.Slug`, `valid.Name`, `valid.ParseKey`, `valid.Type`, `valid.RootGB`, `valid.DataGB`, `valid.Address`, `valid.AllowEntry`), then the record's state, then, for `create_account` alone, the DNS check. A refusal is an MCP error result with one text block holding exactly one copy constant: the refusal constants below, `store.Unreachable` when the record cannot be read or written, or one of appkit's paging texts. A changing call whose change is already so (a key the user holds, a user already locked or active, a user already removing, an address already pending on the host, an allowlist entry already held or not held) answers as a success and changes nothing.

The three address tools check in this order. `unban_ip`: `InvalidAddress`; then, with a host named, `NoHost`, `HostNotRunning`, already pending (ok), `TooManyUnbans`; with none, `TooManyUnbans` when any running host that lacks the address is at the cap, all or nothing. `allow_ip` and `disallow_ip`: `InvalidAddress` or `PrefixTooWide`, `NoHost`, `HostGone` (a host being deleted); then `allow_ip` already held (ok), `AllowlistFull`; `disallow_ip` not held (ok). Each tool canonicalizes its `ip` before it reaches the store, so the store, the desired state, the answer and the trail hold the same string.

The four admin and invite tools check in this order. `set_admin`: the user check (`NoAccount`, `NoUser`, `NotInAccount`, `UserRemoving`); then the flag already as asked (ok). `create_invite`: `NoLink` when there is no link base (`Config.AccountsURL` nil or failing), before the record is read and even while the store fails; then `NoAccount`, `AccountRemoving`, `TooManyInvites`. `revoke_invite`: `NoInvite` for an id `store.ValidInviteID` refuses, before the record is read; then `NoInvite` for an invite that is unknown, used, revoked or expired, one answer for all. `list_invites`: `NoAccount`; a removing account answers `[]`, since removal deleted its invites.

On a space whose configuration names no hosts (`Configured` false, `D01-layout-and-run-seam`), every tool, the reads included, is refused with `NotConfigured` and reads nothing.

## Events

An accepted changing call tells exactly one `change.finished` (`D08-trail`) with its tool, host, account, user, address and result. The address (`ip`) is the canonical form of what `unban_ip`, `allow_ip` or `disallow_ip` was given, empty when the call's `ip` was refused and for every other tool; an `unban_ip` naming no host tells one event with an empty host (bans outcome 16). The result is `ok` for a success, already-in-state included; `failed` for `CloudFailed` and `store.Unreachable`; `refused` for every other refusal. Before it, a call that started an operation tells, in order: for `remove_account` over a running `place`, that place's `operation.finished` with status `cancelled`; the `host.changed` or `account.changed` of the state its write made; and the new operation's `operation.started` (for `retry_host`, again, with the same id). The engine tells the rest of the operation's life. The three address tools start no operation and tell nothing but their `change.finished`; a ban the host reports is not an event (bans outcome 5), and nothing read from a report, a ban's address included, reaches the trail.

The admin and invite tools start no operation either (self-service outcome 27). An answered `create_invite` tells `invite.created` (`trail.InviteCreated`), an answered `revoke_invite` `invite.revoked` (`trail.InviteRevoked`), and a `set_admin` that changed the flag `admin.changed` (`trail.AdminChanged`), each before its `change.finished`; a refused call, and a `set_admin` already as asked, tell none of them. `set_admin`'s `change.finished` names the account's host, account and user; `create_invite`'s the account's host and account; `revoke_invite`'s the revoked invite's account and host, both empty when it revoked nothing. A `NoLink` refusal is `refused`, as every refusal but `CloudFailed` and `store.Unreachable` is. `invite.used` is the enrollment page's (`D18-enrollment`), never a tool's. The token reaches no event: the invite's id names it.

## Recorded decisions

- **Tool names** (pick): accounts' existing `<verb>_<noun>` form, a plural noun for a list and a singular for one read. The six group and membership tools (`groups`, `group`, `create_group`, `remove_group`, `add_member`, `remove_member`) are deleted: a user is in exactly one account, fixed at `add_user`.
- **Every tool refuses `NotConfigured` when the space operates no hosts**, the reads included: the record is empty there and an answer would mislead an agent into thinking hosts could exist; one word for the whole catalog.
- **Check order** (configured, shape, record, DNS last): a refusal the record can make never costs an AWS call, and a malformed argument never costs a database read.
- **Tools tell `host.changed` and `account.changed` for the transitions their own writes commit**, the engine for the rest (`D08-trail`), so each change is told once by the code that committed it.
- **`remove_account` tells the cancelled `place`'s `operation.finished`**: the store cancels it in the same transaction that starts the `unplace` (`D04-store`), the engine never sees it end, and the tool is the only code that knows.
- **`operation` in `host` and `account` is the one the state names**: a host in `provisioning`, `stopping`, `starting`, `resizing` or `deleting` has exactly one running host operation, and a `failed` host the failed one; an account's running `place` or `unplace`, or the failed `place` of a `failed` account, or the failed `unplace` of a `removing` one. A settled host or account answers no operation.
- **`report` is the stored `protocol.Report` as JSON, typed `json.RawMessage`** (`D11-protocol`), and `reported` is when it was received: appkit v0.32.0's output-schema builder refuses `time.Time` and arrays, both of which `protocol.Report` holds (`Booted`, sign-in times, `Load`), so a typed field would make `Register` panic; the raw value relays what the daemon said without restating its schema here.
- **Keys are stored canonical**: the store is handed `valid.Key.Line()`, never the argument as written, so the tools' answers, the desired state and the host's `authorized_keys` agree byte for byte.
- **Health is computed with the writer's clock** (`telemetry.Writer.Now`, the run's `Now`): `tools.Config` carries no clock of its own, and the trail and the health agree on the time.
- **`users` lists every user when `account` is absent** (departure from the per-owner listing other apps use): the landing's users list shares its token, and agents ask "who is on this host" across accounts.
- **Naming a user with an account it is not in answers `NotInAccount`**, not `NoUser`: names are global and listed, so saying so hides nothing, and it tells the agent its account argument is wrong.
- **`delete_user` of a user already `removing` answers ok**, as every already-in-state change does; `lock_user`, `unlock_user`, `add_key` and `remove_key` of a `removing` user refuse `UserRemoving`, since the change could never be applied.
- **`AccountFull` refuses a user whose account's host already holds `valid.MaxUsersPerHost` users**, `HostFull` an account on a host holding `valid.MaxAccountsPerHost`: each names what the agent tried to add to.
- **`GrowLimit` is the store's refusal** (`store.ErrGrowLimit` from `StartHostOp`, counted against the store's own clock, `D04-store`): EC2 allows four modifications of a volume in 24 hours (facts), and refusing early beats an operation stuck in back-off; the tool keeps no second count and no second clock.
- **A host change answers `{host, state, operation}`**, not the full host: the state is the transitional one the write set, and the operation id is what an agent follows with `host`.
- **Argument descriptions are eight copy constants**, one per member name, since each member means the same in every tool; the struct tag repeats the constant because appkit reads only the tag, and a requirement binds the two. The box tools reuse `ArgKey`, `ArgInvite` and `ArgAdmin` but declare their own `box.ArgUser` (`D19-box-tools`), since a box `user` is always a user of the caller's own account.
- **Lists are keyset windows** (`shape/` Listing and Storage): `hosts` over the host's creation sequence (name order up to `host99`, creation order beyond, where byte order would put `host100` before `host20`), `accounts` over the slug, `users` over account then name. Each call holds one window and one row (`D04-store`'s listing reads), and `host`/`account` hold one entity and its children, bounded by `valid`'s caps.
- **The DNS check is bounded** by `DNSCheckTimeout`, five seconds: a slow Route 53 answers `CloudFailed`, and the agent retries.
- **Store guard errors map one to one** (`D04-store`): a race the tool's own read did not see is refused by the store, and the tool words it: `store.ErrTaken` `NameTaken`; `store.ErrBusy` `HostBusy`; `store.ErrHostFailed` `HostFailed`; `store.ErrNotFailed` `HostNotFailed`; `store.ErrNotRunning` `HostNotRunning`; `store.ErrNotStopped` `HostNotStopped`; `store.ErrHasAccounts` `HostHasAccounts`; `store.ErrHostFull` `HostFull`; `store.ErrHostGone` `HostGone`; `store.ErrNothingToChange` `NothingToChange`; `store.ErrShrinks` `SizeShrinks`; `store.ErrGrowLimit` `GrowLimit`; `store.ErrHasUsers` `AccountHasUsers`; `store.ErrAccountRemoving` `AccountRemoving`; `store.ErrAccountFull` `AccountFull`; `store.ErrTooManyKeys` `TooManyKeys`; `store.ErrNotLocked` `UserNotLocked`; `store.ErrUserRemoving` `UserRemoving`; `store.ErrNotInAccount` `NotInAccount`; `store.ErrKeyNotHeld` `KeyNotHeld`; `store.ErrTooManyUnbans` `TooManyUnbans`; `store.ErrAllowlistFull` `AllowlistFull`; any other `store.ErrNotFound` `NoHost`, `NoAccount` or `NoUser` by what the call named. The cancelled `place` is the new `unplace`'s `Supersedes`.
- **`remove_account` is an account's only retry** (`D04-store`): of a `failed` account it starts the `unplace` that clears what the failed `place` left, and of an account whose `unplace` failed it starts a new one; a failed account is then created again.
- Old decisions deleted with the host command: no `Failed` or `KeysUnread` constant, no host diagnostic relayed.
- **Address tool names** (bans outcomes 6 and 10, picks): `unban_ip`, `allow_ip`, `disallow_ip`, each `<verb>_<noun>`; one member `ip` with one copy constant `ArgIP` for an address and an allowlist entry alike, since both are what the agent typed as an IP.
- **An unban is a pending change, not an operation** (bans outcome 7): the tool records it and bumps the host's version, as `lock_user` does, and answers at once; it wakes no engine, calls no cloud and has no id to follow; the agent watches `host`'s `version`, `applied` and report. Unbanning an address that is not banned succeeds (bans outcome 9): the tool never reads a report.
- **A named host that is not running refuses `unban_ip` with `HostNotRunning`; with none named, non-running hosts are skipped** (bans outcome 8): a ten-minute ban does not outlive a stop.
- **The unnamed `unban_ip` is all or nothing and answers a count** (`D04-store`'s `UnbanRunning`): one host at the cap refuses the call and changes nothing, so the agent never has to learn which hosts took it; `Unbanned.Hosts` is a number, not a list of host names, so the answer is bounded whatever the number of hosts. With no running host it answers `hosts` 0, not a refusal: the call has nothing to lift.
- **An absent, null or empty `host` names no host** in `unban_ip`, as `users` reads its `account`: an agent clearing the member and an agent omitting it mean the same.
- **Allowlist edits accept any live host not being deleted**, stopped and failed included (bans outcome 11): the list is lasting desired state that applies when the host runs. A `deleting` host refuses `HostGone`, as `create_account` does, since the edit could never apply.
- **The already-in-state check comes before the cap**, as in `add_key`: an address already pending or an entry already held answers ok even on a host at its cap, because the call asks for nothing new.
- **`InvalidAddress` and `PrefixTooWide` are two refusals**: a malformed entry and one wider than the caps (`valid.MinPrefixIPv4`, `valid.MinPrefixIPv6`) need different fixes. A CIDR given to `unban_ip` is `InvalidAddress`, since `valid.Address` refuses it (bans outcome 6).
- **`AllowlistChange` answers the whole allowlist**: it is at most `valid.MaxAllowlistPerHost` entries, so the agent sees the effect of its edit without a second call; `Pending` is the host's, as `UserChange.Pending` is.
- **The record's allowlist is a typed `HostRead.Allowlist`**; the host's own bans and applied allowlist stay inside the raw `report`, since a ban holds `time.Time`, which appkit v0.32.0's output-schema builder refuses.
- **Bounded work**: `unban_ip` with a host and `allow_ip`/`disallow_ip` hold one host, its at most 50 pending unbans and 50 entries; the unnamed `unban_ip` holds one host at a time and a count (`D04-store`).
- **Admin and invite tool names** (self-service, coordinator picks): `set_admin`, `create_invite`, `list_invites`, `revoke_invite`, each `<verb>_<noun>`. `set_admin` takes `(account, user, admin)` as `lock_user` takes `(account, user)`: one tool sets and clears, so the agent names the state it wants and a repeat answers ok, as every already-in-state change does. `list_invites` is a plural list, not `invites`, because it is scoped to one account and an agent reads it as an action on that account. Two new copy constants, `ArgAdmin` and `ArgInvite`, each meaning the same wherever it appears.
- **Catalog order** follows the tools page's copy (`assets/tools.html`): the user tools, then the admin flag, then the invites (make, list, revoke), then the address tools. The tools page and the about page need no new data: the tools page lists `srv.Tools()` whatever they are.
- **The central tools keep full control** (self-service outcome 4): no existing tool reads the admin flag, so an admin is locked, deleted, demoted and stripped of its last key centrally as any user is, and an account may be left with no admin. The rules that stop an admin acting on itself (self-service outcomes 3 and 22) are the box's (`D19-box-tools`), never the space's.
- **The link is answered once.** `create_invite` answers `InviteMade` with `link`; the store keeps only the token's hash (`D04-store`), so no later read could answer it, and `list_invites`, `revoke_invite` and the trail name the invite by its `iv_` id. An agent that loses the link revokes the invite and makes another.
- **The link's base is `Config.AccountsURL`**, the run's `Settings.AccountsURL` bound to its services file (`D03-serve`, `D01-layout-and-run-seam`), read on each call so a rewritten services file takes effect, as the daemon binary's URL does. Without one, `create_invite` refuses `NoLink` before reading the record: an invite whose link cannot be told would be an invite no one can use. A base longer than `MaxLinkBase` (512 bytes) is refused the same way, as no link: the base is a scheme, a host of at most 253 bytes (RFC 1035's longest name), a port and perhaps a short path, so 512 leaves room for any real one, and with the 56-character token the link stays a few hundred bytes, so every `InviteMade`, central or from the box (whose `create_invite` answers as its central twin, `D19-box-tools`), stays far under `protocol.MaxBoxAnswer` by construction and no link is ever cut after its invite was made. The bound is checked at the call, not at start, because the base is read afresh from the services file on every call and there is no start-time refusal of it to follow; the services file is the operator's, so an over-long entry is a misconfiguration the refusal names. `NoLink` is `refused` in the trail, as every refusal constant but `CloudFailed` is.
- **`set_admin` refuses a removing user with `UserRemoving`**, a narrowing of self-service outcome 4's "any user": the user is on its way out, its row goes once the host applies the removal, and a flag set now would be lost with it; this matches `lock_user`, `unlock_user`, `add_key` and `remove_key`.
- **`revoke_invite` takes only the id**: ids are global and the invite names its account, so asking for the account too would add a way to be wrong. Unknown, used, revoked, expired and malformed are one refusal, `NoInvite`, as the page's one unusable answer is (self-service outcome 13): the agent's fix is the same in each case.
- **`create_invite`'s `admin` is optional and false when absent**, so an agent that does not think about admins makes an ordinary invite (self-service outcome 9); only a central call makes an admin invite (self-service outcome 10), since the box's `create_invite` (`D19-box-tools`) offers no `admin` member.
- **`list_invites` is unpaged** (departure from `shape/` Listing): it answers every unexpired invite of the account in one `InviteList` with no `page`, `limit` or `next`, because the store never holds more than `store.MaxInvites`, 20, of them (`D04-store`), fewer than one default page; a list bounded by a constant is listed whole as `shape/` lists one bounded by configuration whole. Raising `MaxInvites` past `paging.DefaultLimit` would bring paging back.
- **No new tool touches a host or the engine**: the flag and invites are not desired state (`D11-protocol` is unchanged), so they raise no version, start no operation and call no `Wake`; the enrolled user is the one change that reaches the host, through `D04-store`'s `Enroll`.
- **Store guard errors of the new methods map** (`D04-store`): `store.ErrTooManyInvites` `TooManyInvites`; `store.ErrAccountRemoving` `AccountRemoving`; `store.ErrUserRemoving` `UserRemoving`; `ErrNotFound` from `CreateInvite` `NoAccount`, from `SetAdmin` `NoUser` or `NotInAccount` (`store.ErrNotInAccount`), and from `RevokeInvite` `NoInvite`.
- **The box tools are `D19-box-tools`'s** (the box path, self-service outcomes 16 to 27): a host's user reaches `keys`, `add_key` and `remove_key` and, as an admin of their account, `users`, the user tools, `set_admin` and the invite tools at `/accountsd/v1/box`, through `internal/box`. That package shares no handler body with this one: it calls `internal/store` directly, the central store methods for the reads and the guarded twins (`D04-store`'s `*As` methods) for every write, which check the actor's own state and the actor rules in the write's transaction, so one copy of every guard lives in the store. It reuses this package's result types, `Tool*`, `Arg*` and refusal constants and `InviteArgs`, and each box call answers and records as its central twin, the call of this document's tool for the actor's account, except for the differences `D19-box-tools` lists. The sketch this bullet held before (these handler bodies run under a context actor, the rules checked before them) is superseded: the box has no `account` argument, answers a foreign target as `NoUser` rather than `NotInAccount`, and its rules must hold atomically with the write. No central tool's behaviour changes for the box, and the central tools keep full control. The one change here is the caller's length: the store records a caller's `UserID` only when it is at most `valid.MaxUserIDBytes` bytes (`D04-store`, `D17-names-keys-sizes`), which holds auth's user ids and the box actor alike, so the tool requirements denote only a call whose caller's `UserID` is that long or shorter (R-ESC3-AJ89); a longer one comes only from a forged header.
- **Bounded work**: `set_admin` holds one user; `create_invite` one account, one count and one invite; `revoke_invite` one invite and its account's host name; `list_invites` at most `store.MaxInvites` invites (`D04-store`).

## Consumer usage

`web.Handler` (`D03-serve`) calls `tools.Register(srv, tools.Config{Store: st, Cloud: c, Hosts: hosts, Configured: configured, Wake: engine.Wake, Telemetry: w, AccountsURL: func() (string, error) { return cfg.Settings.AccountsURL(cfg.ServicesPath) }})` once.

Consumer tasks, against the declared names:

1. `create_host{}` → `tools.HostChange{Host: "host01", State: "provisioning", Operation: "op_…"}`; `hosts{}` → `tools.HostList{Hosts: []tools.Host{{Host: "host01", State: "provisioning", Health: "none", Type: "t4g.medium", RootGB: 20, DataGB: 50, …}}}`; later `host{host: "host01"}` → `tools.HostRead{…, State: "running", Report: json.RawMessage(`{"protocol":1,…}`)}` (decoded with `json.Unmarshal` into a `protocol.Report`).
4. `create_account{account: "acme", host: "host01"}` → `tools.Account{Account: "acme", Host: "host01", DNSName: "acme.metaspot.org", State: "pending", …}`; `account{account: "acme"}` shows `Operation` while the place runs.
