# D07-tools

The thirteen MCP tools agents keep the host's groups and users with, through the MCP gateway: `internal/tools`. They are accounts' only API. An agent lists the groups with `groups` and reads one with its members with `group`, and keeps them with `create_group` and `remove_group`; lists the users with `users`, adds one with `add_user`, keeps their keys with `add_key` and `remove_key` and their memberships with `add_member` and `remove_member`, and ends, restores and removes their access with `lock_user`, `unlock_user` and `delete_user`. Every signed-in caller reads and changes everything; the caller a tool is handed is used only to record who created a group or user, by user id, and as the trail's user. What the host does with each command, which names, keys and states it accepts and what it refuses, is `D05-host`'s and, beyond it, opsctl's: the folder a group owns, its modes, and how a locked user is kept from signing in are the host's, and a tool only asks for them. What the record keeps is `D04-store`'s; the trail event and its functions are `D08-trail`'s; where the tools are mounted and how the run builds their configuration is `D03-serve`'s; the tools page, which lists `mcp.Server.Tools()` in the catalog order `Register` registers them in, each description cut with `tools.FirstLine`, is `D06-pages`'.

## The tools

In catalog order, each with the effect appkit's `mcp` registers it with:

- `groups` (read) takes `page` and `limit` and answers the groups the host lists, each with its slug, member count and, when accounts created it, when and by whom, then `next`.
- `group` (read) takes `group` and answers that group with its members as the host lists them, and when and by whom accounts created it.
- `create_group` (additive) takes `group` and asks the host to create it (a Linux group, a service account and its shared folder, all the host's to make); once the host has, the record keeps who created it and when.
- `remove_group` (destructive) takes `group` and asks the host to remove it. The host refuses while it has members, and leaves its folder in place; no tool deletes a folder.
- `users` (read) takes `page` and `limit` and answers the users the host lists, each with its name, every group it belongs to, every key byte for byte, its state, its last sign-in and, when accounts created it, when and by whom, then `next`: enough to recreate every user on another host.
- `add_user` (additive) takes `user`, `group` and `key`, all required, so every user starts with one key and one group.
- `add_key` (additive) takes `user` and `key`.
- `remove_key` (destructive) takes `user` and `key`, and answers whether the user has any key left: a user with none cannot sign in.
- `add_member` (additive) takes `user` and `group`.
- `remove_member` (destructive) takes `user` and `group`.
- `lock_user` (additive) takes `user`; the host ends their access and keeps their home, keys and memberships, so the listing changes in state alone.
- `unlock_user` (additive) takes `user` and restores it.
- `delete_user` (destructive) takes `user`; the host removes the account and its home, and refuses a user who is not locked.

accounts checks no name and no key: every value reaches the host as the caller gave it, and the host's refusal is relayed. The only checks of its own are the paging members.

## How a change runs

Each of the ten changing tools asks the host for its one change at once, during the call, through the matching `host.Host` method. The outcome is the host's:

- The host made it (a nil error, an already-in-state command included, which `create_group` and `add_user` never are: the host refuses a name it holds as taken, and that refusal records nothing): `create_group`, `remove_group`, `add_user` and `delete_user` then write the record (`AddGroup`, `RemoveGroup`, `AddUser`, `DeleteUser`); the call answers which group or user it changed.
- The host refused it (`*host.RefusedError`): the call is refused with the diagnostic, carried unaltered, and nothing is recorded.
- The host failed, or the command could not run, or anything else went wrong: the call is refused with `tools.Failed`, and nothing is recorded.
- The host made it but the record write failed: the call is refused with `store.Unreachable`; the host's change stands, and the record catches up only when a later call writes it (a group or user the host lists and the record lacks is shown with no created time).

`remove_key` then reads the host's users to learn whether the user has a key left. If that read fails or is refused, the call is refused with `tools.KeysUnread` and the removal stands.

Each changing call records exactly one `change.finished` through `trail.Change`, with its tool name, group, user and result, before it answers: `trail.Result` of the host's error, but `trail.ResultFailed` when the host made the change and the record write, or `remove_key`'s follow-up read, then failed. Reads record nothing.

## Paging

`groups` and `users` page as the suite's listing convention asks, on the contract of appkit's `paging` package. Each input declares `page` and `limit` as pointer fields carrying `paging.PageDescription` and `paging.LimitDescription`; each answer is its list then `next`, carrying `paging.NextDescription`, present exactly when at least one entry follows. The token is `paging.Token{Tool: <tool name>}` over the slug or name of the last entry the page answered; the next page is every entry the host lists whose key is greater in byte order. A `limit` outside 1 to `paging.MaxLimit` is refused with the text of `paging.Window`'s error, then a `page` the tool's token does not decode with `paging.BadPage`, before the host is asked anything and before the record is read. The landing page (`D06-pages`) windows the same lists with the same tokens.

`group`'s members are answered whole: a group's membership is bounded by the people of one business.

## Answers

Times are RFC 3339 in UTC to the second, the empty string where there is none: a group or user the record does not hold has an empty `created` and `created_by`, and a user who never signed in an empty `last_sign_in`. Who created something is a user id, never an email. Every member is present, a list `[]` when empty, but `next` absent when nothing follows. A host entry the record lacks is shown; a record entry the host does not list is not.

## Refusals

A refusal is an MCP error result with one text block: the host's diagnostic as `D05-host` carries it, `tools.Failed`, `tools.KeysUnread`, `store.Unreachable`, or one of appkit's two paging texts.

## Recorded decisions

- Departure from shape's Storage: **the host, not the database, is the store `groups` and `users` are read from.** One `opsctl` call answers the whole list, which a host's accounts bound (the people and businesses of one host), and the tool windows it in memory, keyset by slug or name over the host's sorted list. The record is read only for the window's created times. `D06-pages` cites this departure for its two lists.
- **`tools.Config` carries `Store`, `Host` and `Telemetry`** and no clock: the record stamps its own times (`D04-store`), and the trail's time is the writer's.
- **Changes answer what they changed, not the record after** (no `changed` member): the host answers an already-in-state command as it answers a change, so accounts cannot tell the two apart, and a read after a change could fail after the change was made. `remove_key` is the one exception, because it must say whether a key is left.
- **`remove_key` learns what is left from the host's users read after the removal**, not from comparing keys itself: which keys match is the host's rule, and accounts parses no key. A user the host no longer lists has no key left.
- **A refusal is its text alone**, with no word before it: the host's diagnostic already says why, and an agent tells a failure from a refusal by the distinct constants `Failed`, `KeysUnread` and `store.Unreachable`, which only failures carry.
- **`lock_user` is additive**: it keeps everything and `unlock_user` restores it; the destructive four remove something (a group, a key, a membership, an account and its home).
- **Argument descriptions are three copy constants**, `ArgGroup`, `ArgUser` and `ArgKey`, one per member name, since each means the same thing in every tool; the struct tag repeats the constant because appkit reads only the tag, and a requirement binds the two.
- **Entities use the host's words, changes the arguments'**: a listed group's key is `slug` and a user's `name`, as the host lists them; a change answers the `group` and `user` it was called with.
- Excluded from this document: the folder's ownership, modes and repository, and how a locked user is kept from signing in, are opsctl's; the tools only ask (`D05-host`). Which tools the one exec'ing test calls is `D01-layout-and-run-seam`'s.

## Consumer tasks

`web.Handler` (`D03-serve`) calls `tools.Register(srv, tools.Config{Store: st, Host: h, Telemetry: w})` once; the tools page lists `srv.Tools()`, each description cut with `tools.FirstLine`, and the landing page builds its list tokens with `paging.Token{Tool: tools.ToolGroups}` and `tools.ToolUsers`.

A test opens its own database with `db.Open` and `Migrations()`, builds `store.New` over it with its own clock, a writer with `telemetry.New` over a `*telemetry.Capture`, and either `host.NewMemory()` or a fake `host.Host` that records each call and answers nil, a `*host.RefusedError`, a `*host.FailedError` or a plain error on demand; registers the tools on `mcp.NewServer`, serves it inside `identity.Require` with `httptest`, and calls `mcp.Client.CallTool` with `tools.AddUserArgs{...}` and the rest as JSON. It decodes `structuredContent` into `tools.GroupList`, `tools.UserList`, `tools.KeyRemoved` and the rest, walks `next`, compares refusal text with a diagnostic it chose, `tools.Failed`, `tools.KeysUnread`, `store.Unreachable`, `paging.BadPage` and `paging.Window`'s error, flips `SetFailing(true)` on the handle for record failures, and after `Flush` reads `change.finished` events from the capture.
