# D09-tools

events' five MCP tools: `internal/tools`, whose one function, `Register`, puts `catalog`, `search`, `subscribers`, `skip` and `resume` on the `mcp.Server` that `cli.Run` mounts at `/mcp`. This document says what a client is told about each tool in `tools/list`, how each tool reads its arguments, the order it checks them in, which refusal each gets, what each answers from the log (`D04-store`), and the one record a tool makes itself, the `event.skipped` of an agent's `skip`.

## What is someone else's

- appkit's `mcp` server is the transport and the protocol: POST only, one JSON-RPC message per request, one `application/json` answer, no session; the `2026-07-28` envelope (`resultType`, `_meta`, `ttlMs`, `cacheScope`) and the earlier revisions with `initialize`; the 405 for other methods; the malformed-transport checks; and `tool.called`, which appkit's server records for every call that reaches a tool, with its `kind` taken from the tool's effect. `D06-serve` builds the server and mounts it: its name and version (`R-9ZXZ-FU3S`), its instructions (`R-CK5X-DTG8`), the identity gate's 500 (`R-9Q17-90VQ`) and the 405 (`R-D2GF-4DKN`). `D10-trail` owns the trail as a whole: `request.*`, `tool.called` and the order of a request's records.
- appkit's `AddTool` derives each schema from the Go types the build chooses and reads `arguments` strictly against the input schema, refusing with its `invalid arguments:` text and recording `tool.called` with `outcome` `invalid_arguments` and `duration_us` 0. It lists each tool as an object with the members `name`, `description`, `inputSchema`, `outputSchema` and `annotations`, in that order, and lists the offences of `invalid arguments:` one per line, the schema's fields first in schema order, then each unknown field in the order it was sent. It turns a handler's error into an `isError` result whose one text block is the error's text, and a handler's value into `structuredContent` plus one text block holding the same bytes. Probed from the installed module: a field tag may hold only a name (no `omitempty`), so a member that is sometimes absent is a pointer left nil; `json.RawMessage` is allowed only as a struct field (schema `{"type":"object"}`, bytes passed through), so a search record is a struct with `attrs` as a raw object; a `null` argument counts as absent only for a pointer field, and is otherwise an offence (`service: expected string, got null`); an integer argument accepts `3.0` as 3 and refuses `3.5` and anything outside `int64` in its own words.
- `D04-store` answers everything a tool shows: the catalog, one window of the search, the subscribers, and what `Skip` and `Resume` change. `D07-delivery` delivers to a subscriber that `skip` or `resume` made `ok` again.

## What a client is told

The tools are registered in the order the requirements give, each with a description, which is copy the build writes, as is each property's own `description`. Input schemas are the requirements', property for property and in their order. `catalog`, `search` and `subscribers` are `mcp.Read`; `skip` is `mcp.Destructive`, since the skipped event is never delivered to that subscriber again; `resume` is `mcp.Additive`. appkit turns those into the annotations the requirements state and into `tool.called`'s `kind`. No output schema is fixed beyond `search`'s `records` and `next` members and the description of `next`, but every tool has one, as appkit derives it.

`tools/list` reads nothing of the log, so it answers the same when the database cannot be read.

## Arguments, order and refusals

A handler is reached only with arguments appkit read cleanly. `catalog`'s `service` and `event` are strings, absent meaning `""`, which is no filter. `search`'s arguments map onto `store.Filter`: a time is accepted exactly when `time.Parse(time.RFC3339, v)` accepts it, so a date alone, a bare word, a local time without offset and the empty string are refused, naming the argument and quoting the value; `services` and `events` keep the events any of their names matches, an empty array none; `user`, `request_id` and `cause` are exact, `""` included; `attrs` is decoded keeping each number exact — an integer as `int64`, or `uint64` above it, anything else as `float64` — so `1` matches the record's `1`, `1.0` and `1e3` match `1` and `1000` as appkit writes them, and an integer above 2^53 matches only itself; a value that is not a string, boolean or finite number matches nothing. `limit` and `page` are the paging members, described below. When several things are wrong, `search` answers the first in the order `since`, `until`, `limit`, `page`, then the log: the input schema's order, the order appkit lists its own offences in, and the page before the log because a token is checked without reading the database.

`skip` and `resume` take `service`, required, matched as sent. `D04-store` refuses a service with no subscriber first, then one that is not `paused`, `gone` included (`R-E072-ZVSD`); the tools quote the name back exactly as sent, even the empty string.

Every other failure of the store is the one `Unreachable` refusal, quoting nothing of the error. A refused call changes nothing and records nothing of its own.

## Paging `search`

`search` lists the retained log, which every emit adds to, so it pages as the suite's listing rule asks (`shape/`, Listing), on the contract of appkit's `paging` package (appkit's D25), which this document cites and never restates. `dummy` is the precedent app `shape/` names for that rule, and `search` takes its shape from dummy's `list_widgets`; events therefore requires an appkit release that exports `paging` (`AGENTS.md` names which). The input keeps every filter it had, then `limit`, `*int`, and `page`, `*string`, in that order, each with a `description` tag repeating `paging.LimitDescription` or `paging.PageDescription` word for word; the answer keeps `records`, then `next`, `*string` with a tag repeating `paging.NextDescription`, written exactly when at least one record follows the page. A test compares each description `tools/list` shows with its constant. The members named `cursor`, in the input and in the answer, are gone, and so are events' own `BadCursor` and `BadLimit`.

The page size is what `paging.Window` reads from `limit`: `paging.DefaultLimit` when absent or `null`, so the default moves from the 50 events had to the suite's 25, and the largest is `paging.MaxLimit`. A `limit` outside the range is refused with the text of the error `Window` returns. The token is `paging.Token{Tool: "search"}` over one `int64`, the `seq` of the last record the page answered; the next page is the matching records whose `seq` is smaller, newest first as before. An absent, `null` or empty `page` is the first page; a `page` that `Decode` refuses, one another tool issued or one made by hand, is refused with `paging.BadPage`. Both refusals come before the store is read, so they are the same while the log is unreachable: a refusal of arguments that can never succeed, not `Unreachable`, which would invite a retry. A token does not bind its filters: a `page` handed back with other filters continues from the same position in the new filter's order, and one naming a position the sweep has since passed is no error, as the search cursor was before. The tool asks the store for one more record than the page size and sets `next` only when the extra one came back, so a full last page carries no `next` and no record is repeated or skipped at a page's edge; the store windows the query in SQL (`D04-store`), so events holds one page plus one row.

The `cursor` of a subscriber, in the `subscribers` answer, the `skip` and `resume` answers, the `subscribers` table and the landing page, is a different thing, the subscriber's place in the log, and keeps its name and meaning; nothing here touches it.

Paging adds nothing to the trail: `tool.called` carries no arguments, so a token appears in no event and no log line. No page lists records, so no asset changes. events has no live test, and its `make live` target needs no change.

## What a success answers

Times are the **wire time**, RFC 3339 UTC with six fraction digits, the form a record's `received` has. `catalog` answers `{"events":[...]}` in the store's order, each entry `event`, `emits`, `accepts`, `count` and, only when `count` is above 0, `last_seen`, in that order. `search` answers `{"records":[...]}`, each record the event's eleven members as the store keeps them, and `next` only when a record follows the page. `subscribers` answers `{"subscribers":[...]}`, each a **subscriber entry**: `service`, `status`, `cursor`, `lag`, `since` and, only while `paused`, `reason` with `event`, `name`, `seq` and `error`, in that order. `skip` and `resume` answer the subscriber entry of the subscriber after the change. `skip` records `event.skipped` with the stuck event's id and the subscriber's service, under the caller's request id and user, before it answers, so it comes before appkit's `tool.called` in the trail. `resume` records nothing of its own.

Every user sees the same bus: nothing a tool answers depends on who called.

## Decisions

- Empty `since` or `until` is refused as a bad time: only an empty `page` is the same as leaving it out, and `since` and `until` are RFC 3339 or absent.
- Refusal order `since`, `until`, `limit`, `page`, then the log, as above. `limit` stays before `page` in the input schema, where `cursor` stood after it, so the schema's order and the refusal order still agree and the page size is read first, as appkit's D25 has it.
- The default page size is the suite's `paging.DefaultLimit`, not the 50 `search` had; the cap stays 500, now `paging.MaxLimit`.
- `search` orders by `seq` descending, newest first.
- `since` in a subscriber entry uses the same six-digit form as `last_seen` and the records' `received`.
- A refusal quotes the value exactly as sent. A refusal is one line unless the value it quotes holds a line break, which it carries as sent.
- The argument and result types stay unexported: the wire is the contract, and the tests drive the tools with literal JSON through `mcp.Client`.

## Consumer tasks

`cli.Run` builds the MCP server and calls `tools.Register(srv, tools.Config{Store: st, Telemetry: w})` once, with the run's store and writer. A tools test sets `IKIGENBA_SERVICES` with `t.Setenv` to the empty string, opens its own log with `db.Open` and `events.Migrations()`, builds `store.New` over it with a clock it controls, declares services and stores events, builds a writer over a `telemetry.Capture`, builds `mcp.NewServer`, registers the tools, serves the server on loopback inside `telemetry.Middleware` and `identity.Require`, and drives it with `mcp.Client`: `ListTools` for the five `mcp.ToolInfo`, and `CallTool` with literal JSON arguments, reading each `mcp.Result` through `MarshalJSON`. It provokes the log's failure with `SetFailing(true)` on its handle, and reads the trail with `Writer.Flush` and `Capture.Events`; in production the server and the tools share one writer, so appkit's `request.*` and `tool.called` go through `cfg.Telemetry` too; a test that must tell the tools' own records from appkit's hands `tools.Config` a writer of its own, separate from the server's. No test needs raw HTTP to `/mcp`.

An agent reading every `repo.pushed` event from repos, today and as proposed:

- Today: `search` with `{"services":["repos"],"events":["repo.pushed"]}` answers up to 50 records and, when more follow, `cursor`; the agent calls again with the same filters and `"cursor":<that value>`, and stops when an answer has no `cursor`.
- Proposed: `search` with `{"services":["repos"],"events":["repo.pushed"]}` answers up to `paging.DefaultLimit` records and, when more follow, `next`; the agent calls again with the same filters and `"page":<that value>`, `"limit"` too if it wants other than the default, and stops when an answer has no `next`. A `page` from another tool, or made by hand, is refused with `paging.BadPage`; a `limit` of 0 with the text `paging.Window` gives.
