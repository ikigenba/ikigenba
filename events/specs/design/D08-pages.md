# D08-pages

What events draws as HTML: the package `internal/pages`, which answers the landing page at `/`, the about screen at `/about`, the not-found page for every path that names nothing, and the unavailable page when the landing page cannot read the log. `D06-serve` owns the routes: it calls `Landing` and `About` only for a `GET` or `HEAD` of exactly `/` and `/about` (R-CXKT-LALV), answers every other method on them 405 itself (R-D00M-CU39), calls `NotFound` for every other path that is not `/mcp`, `/emit` or under `/_appkit/` (R-D18I-QLTY), and puts the identity gate and the request records around all of it. `D01-layout-and-run-seam` declares the root package's `Assets`, which holds the four templates (R-ZM76-17RB), and `cli.Process.Version`, the display string `main` reads, which `cli.Run` hands to `pages.New` as `Config.Version` (R-9YQ3-22D3). `D04-store` declares `store.Store`, its `Subscribers` and the `store.Subscriber` and `store.Reason` it answers with (R-CNF3-P24L, R-DKCE-0V5C). `D02-cli` holds the agreement between the manifest's description and `pages.Description` (R-0GON-LHAO); this design only declares the constant. The five tools whose first description lines the landing page lists are `D09-tools`'. The request records every page answer adds are `D10-trail`'s. That nothing reaches standard error for a page answer, a missing or broken services file included, is `D06-serve`'s R-A2DS-7DL6 (after the start `cli.Run` writes only appkit's warning over a database a newer events upgraded, undelivered-event lines and its exit diagnostics) and R-AZ4W-FGNR (nothing to the `log` package's standard logger); `pages` holds no stream, so it adds none. A visitor with no credential being sent to auth's sign-in is nginx's and auth's on a host and never reaches events; `D11-on-a-space` records it.

## Templates and data

The four templates are the files of `assets/`, each opening with a comment that names its data and its hooks. **events' template set** is what parsing all four into a fresh set from appkit's `page.Templates()` gives, so `banner`, `launcher`, `footer` and `preload` are appkit's and `landing`, `about`, `notfound` and `unavailable` are events'. Every page answer is one template of that set executed with its data, `Content-Type: text/html; charset=utf-8` and nothing else added; a `HEAD` gets the same status and header and no body, so the request's `response_bytes` is 0.

- `landing` takes a `LandingData`: the page banner and one `SubscriberRow` per subscriber, in the order `Subscribers` gives them (by service name). A row's words are text: the status word, the theme kind it shows as (`ok` is `ok`, `paused` is `warn`, `gone` is `info`), the reason as `at <name> <seq>: <error>` for a paused subscriber and empty otherwise, and the cursor and lag in decimal; `Since` stays a `time.Time` because the template formats it twice.
- `about` takes an `AboutData`: the page banner and `Description`.
- `notfound` and `unavailable` take a `NoticeData` whose banner carries only the service name and the version, since those pages draw appkit's footer (`events <display>`, or `events` alone when the display string is empty) and no banner.

Every page's head preloads upright Inter, the face nearly all its text is set in, so a browser fetches it before the stylesheet asks for it. The font's URL carries a hash of its bytes that events never writes, so each of the four templates invokes `{{template "preload"}}` in its head, beside its stylesheet link, and appkit's `preload` template renders the one link, with `rel` `preload`, `as` `font`, `type` `font/woff2`, a bare `crossorigin` and `page.PreloadURL()` as its `href`. What the preload does in a browser is a browser's, so what is fixed is that link's attributes.

## The banner

events never calls `page.New`, which would read `IKIGENBA_SERVICES` from the process environment; `pages` builds the `page.Banner` itself, from the services path it was handed, reading the file afresh through appkit's `services.Read` on every call, so a rewrite of the file shows on the next page. The banner carries `events`, the version (`Config.Version`, possibly empty), the caller's `X-User-Email` exactly as it arrived, auth's profile and sign-out addresses, and the launcher's entries: every listed entry that carries an icon, in the file's order, `events`' own marked current. A file that cannot be read is no services: no launcher and nothing written about it.

Auth's addresses come from the file's `auth` entry when it has a non-empty `url`; otherwise from the request's `Host`, a trailing port dropped and then one leading `events.` label, under the scheme `X-Forwarded-Proto` names when it is exactly `http` or `https`, `https` otherwise. The about screen's three facts are the running events' own; only its banner reads the services file.

## Reading a page

The tests have no HTML parser, so the hook requirements name elements by tag, `id`, `class` and attributes as the templates' comments do, and read an element's text by a rule stated below. The byte-for-byte requirements pin the data; the hook requirements pin what the stories show a user, so a template that cannot show a state is an issue, never a change to the asset. The footer appkit draws is `events`, one space and the version; when the host set no identity the version is empty, and the footer's text, its trailing space removed by that rule, is `events` alone, so the footer requirements state both cases.

What a browser does with a page is outside this design: the launcher's list opening on its button and filtering as the user types (`S03`), and the buttons' feedback, are the behaviour of appkit's `launcher.js` and `feedback.js` (`S04`) acting on appkit's `launcher` template. events serves those files and draws the hooks they act on; its tests have no browser and do not exercise the scripts.
