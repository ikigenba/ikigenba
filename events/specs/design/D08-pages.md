# D08-pages

What events draws as HTML: the package `internal/pages`, which answers the landing page at `/`, the about screen at `/about`, the not-found page for every path that names nothing, and the unavailable page when the landing page cannot read the log. `D06-serve` owns the routes: it calls `Landing` and `About` only for a `GET` or `HEAD` of exactly `/` and `/about` (R-CXKT-LALV), answers every other method on them 405 itself (R-D00M-CU39), calls `NotFound` for every other path that is not `/mcp`, `/emit` or under `/_appkit/` (R-D18I-QLTY), and puts the identity gate and the request records around all of it. `D01-layout-and-run-seam` declares the root package's `Assets`, which holds the four templates (R-ZM76-17RB), and `cli.Process.Banner`, the banner source `main` makes with appkit's `page.New` from the display string it reads, which `cli.Run` hands to `pages.New` as `Config.Banner` (R-SPXR-BL15). `D04-store` declares `store.Store`, its `Subscribers` and the `store.Subscriber` and `store.Reason` it answers with (R-CNF3-P24L, R-DKCE-0V5C). `D02-cli` holds the agreement between the manifest's description and `pages.Description` (R-0GON-LHAO); this design only declares the constant. The five tools the landing page names are `D09-tools`'. The request records every page answer adds are `D10-trail`'s. That nothing reaches standard error for a page answer, a missing or broken services file included, is `D06-serve`'s R-A2DS-7DL6 (after the start `cli.Run` writes only appkit's warning over a database a newer events upgraded, undelivered-event lines and its exit diagnostics) and R-AZ4W-FGNR (nothing to the `log` package's standard logger); `pages` holds no stream, so it adds none. A visitor with no credential being sent to auth's sign-in is nginx's and auth's on a host and never reaches events; `D11-on-a-space` records it.

## Templates and data

The four templates are the files of `assets/`, each opening with a comment that names the data it receives. **events' template set** is what parsing all four into a fresh set from appkit's `page.Templates()` gives, so `banner`, `launcher`, `footer` and `preload` are appkit's and `landing`, `about`, `notfound` and `unavailable` are events'. Every page answer is one template of that set executed with its data, `Content-Type: text/html; charset=utf-8` and nothing else added; a `HEAD` gets the same status and header and no body, so the request's `response_bytes` is 0.

- `landing` takes a `LandingData`: the page banner and one `SubscriberRow` per subscriber, in the order `Subscribers` gives them (by service name). A row carries its values as strings: the status, the theme kind it is shown as (`KindOK`, `KindWarn` or `KindInfo`), the reason of a paused subscriber, made with `ReasonFormat`, and empty otherwise, and the cursor and lag in decimal; `Since` stays a `time.Time` because the template formats it.
- `about` takes an `AboutData`: the page banner and `Description`.
- `notfound` and `unavailable` take a `NoticeData` whose banner is the banner source's answer for no user, since those pages draw appkit's footer, which shows the banner's service and version, and no banner.

Every page's head preloads the face nearly all its text is set in, so a browser fetches it before the stylesheet asks for it. The font's URL carries a hash of its bytes that events never writes, so the templates use appkit's `preload` template, which renders it from `page.PreloadURL()`. What a page's head carries is the templates' and appkit's, not this design's.

## The banner

events gets every banner from appkit's `Kit.Banner`, as every app does: `main` makes the kit with `page.New(events.ServiceName, v)`, `v` being the display string, and the run seam carries its `Banner` method through `cli.Process.Banner` to `pages.Config.Banner` (`D01-layout-and-run-seam`). The pages call it while each request is answered, with the caller's `X-User-Email` exactly as it arrived and auth's profile and sign-out addresses for the landing page and the about screen, and with no user for the notice pages. What comes back is appkit's (its D02): `events`, the version, the user's three values, the launcher's entries read afresh from the services file the kit's path names, in the file's order with `events`' own marked current, and events' own icon, which appkit's mark shows. A rewrite of the file shows on the next page; a file that cannot be read is no services, so no launcher, no icon in the mark and nothing written about it. The banner and its sign-out button are appkit's `banner` template; events passes the data and draws none of it. A pages test sets `services.Variable` with `testing.T.Setenv` to a services file it wrote and calls `pages.New(pages.Config{Banner: page.New(events.ServiceName, "r1 (abc1234)").Banner, ServicesPath: path, Store: st})`, or passes as `Banner` a function of its own that records the `page.User` it is given and returns a `page.Banner` it chose.

Auth's addresses come from the file's `auth` entry when it has a non-empty `url`; otherwise from the request's `Host`, a trailing port dropped and then one leading `events.` label, under the scheme `X-Forwarded-Proto` names when it is exactly `http` or `https`, `https` otherwise. The pages read `Config.ServicesPath` only for these addresses; the launcher and the icon come from the kit.

## Proving a page

A test proves a page by executing the named template of events' template set with the data the requirements state and comparing the answer's body with what that writes, or by checking that a value it supplied appears in the body; it never looks for a word, a tag, a class or an id. A template that cannot show a state this design names is an issue, never a change to the asset.

What a browser does with a page is outside this design: the launcher's list opening on its button and filtering as the user types, and the buttons' feedback, are the behaviour of appkit's `launcher.js` and `feedback.js` acting on appkit's `launcher` template. events serves those files and its templates carry what they act on; its tests have no browser and do not exercise the scripts.
