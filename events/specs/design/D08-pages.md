# D08-pages

What events draws as HTML: the package `internal/pages`, which answers the landing page at `/`, the tools page at `/tools`, the about screen at `/about`, the not-found page for every path that names nothing, and the unavailable page when the landing page cannot read the log. `D06-serve` owns the routes: it calls `Landing`, `About` and `Tools` only for a `GET` or `HEAD` of exactly `/`, `/about` and `/tools` (R-CXKT-LALV, R-DCJR-1M7B), answers every other method on them 405 itself (R-DEZJ-T5OP), calls `NotFound` for every other path that is not `/mcp`, `/emit` or under `/_appkit/` (R-DG7G-6XFE), and puts the identity gate and the request records around all of it. `D01-layout-and-run-seam` declares the root package's `Assets`, which holds the five templates (R-D7O5-IJ8J), and `cli.Process.Banner`, the banner source `main` makes with appkit's `page.New` from the identity it reads, which `cli.Run` hands to `pages.New` as `Config.Banner`, together with the tools page's list as `Config.Tools` (R-B2WL-CQEE). `D04-store` declares `store.Store`, its `Subscribers` and the `store.Subscriber` and `store.Reason` it answers with (R-CNF3-P24L, R-DKCE-0V5C). `D02-cli` holds the agreement between the manifest's description and `pages.Description` (R-0GON-LHAO); this design only declares the constant. The landing page names no tool; the tools page lists the five tools `D09-tools` declares, each by its name and description, as the MCP server `cli.Run` built offers them (R-B2WL-CQEE). The request records every page answer adds are `D10-trail`'s. That nothing reaches standard error for a page answer, a missing or broken services file included, is `D06-serve`'s R-A2DS-7DL6 (after the start `cli.Run` writes only appkit's warning over a database a newer events upgraded, undelivered-event lines and its exit diagnostics) and R-AZ4W-FGNR (nothing to the `log` package's standard logger); `pages` holds no stream, so it adds none. A visitor with no credential being sent to auth's sign-in is nginx's and auth's on a host and never reaches events; `D11-on-a-space` records it.

## Templates and data

The five templates are the files of `assets/`, each opening with a comment that names the data it receives. **events' template set** is what parsing all five into a fresh set from appkit's `page.Templates()` gives, so `banner`, `footer` and `preload` are appkit's and `landing`, `tools`, `about`, `notfound` and `unavailable` are events'. Every page answer is one template of that set executed with its data, `Content-Type: text/html; charset=utf-8` and nothing else added; a `HEAD` gets the same status and header and no body, so the request's `response_bytes` is 0.

- `landing` takes a `LandingData`: the page banner and one `SubscriberRow` per subscriber, in the order `Subscribers` gives them (by service name). A row carries the service, the status as the store's value and the cursor and lag in decimal as strings; `Since` stays a `time.Time` because the template formats it; and a paused subscriber's stuck event, when there is one, as a `Reason` holding the event's name, `seq` and error text, nil otherwise. How a status is shown and how the stuck event is put into words are the template's.
- `tools` takes a `ToolsData`: the page banner and one `Tool` per tool, a name and a description, in the order of `Config.Tools`. The page holds no list of its own: `cli.Run` builds the MCP server, lets `tools.Register` fill it, and hands `pages.New` one `Tool` per entry appkit's `Server.Tools` returns, in registration order, so the page lists exactly what `tools/list` names and cannot drift from it (R-B2WL-CQEE). The list is fixed for the run, so the page reads neither the store nor the services file for it.
- `about` takes an `AboutData`: the page banner and `Description`. The banner's `Service` is the name the screen shows and its `Release` and `Commit` the code it runs, shown apart.
- `notfound` and `unavailable` take a `NoticeData` whose banner is the banner source's answer for no user, since those pages draw appkit's footer, which shows the banner's release and commit, and no banner.

Every page's head preloads the face nearly all its text is set in, so a browser fetches it before the stylesheet asks for it. The font's URL carries a hash of its bytes that events never writes, so the templates use appkit's `preload` template, which renders it from `page.PreloadURL()`. What a page's head carries is the templates' and appkit's, not this design's.

## The banner

events gets every banner from appkit's `Kit.Banner`, as every app does: `main` makes the kit with `page.New(events.ServiceName, id)`, `id` being the `version.Identity` it read, and the run seam carries its `Banner` method through `cli.Process.Banner` to `pages.Config.Banner` (`D01-layout-and-run-seam`). The pages call it while each request is answered, with the caller's `X-User-Email` exactly as it arrived and auth's profile and sign-out addresses for the landing page, the tools page and the about screen, and with no user for the notice pages. What comes back is appkit's (its D02): `events`, the identity's release and commit, the user's three values, and, read afresh from the services file the kit's path names, events' own icon from the entry named `events`, which appkit's mark shows, the home link from the `home` entry, and whether events offers tools. A rewrite of the file shows on the next page; a file that cannot be read gives no icon, no home link and no tools, and nothing written about it. The banner and its sign-out button are appkit's `banner` template, and the release and commit at the foot of every page are appkit's `footer`; events passes the data and draws none of it. A pages test sets `services.Variable` with `testing.T.Setenv` to a services file it wrote and calls `pages.New(pages.Config{Banner: page.New(events.ServiceName, version.Identity{Release: "r1", Commit: "abc1234"}).Banner, ServicesPath: path, Store: st, Tools: []pages.Tool{{Name: "one", Description: "first"}}})`, or passes as `Banner` a function of its own that records the `page.User` it is given and returns a `page.Banner` it chose.

Auth's addresses come from the file's `auth` entry when it has a non-empty `url`; otherwise from the request's `Host`, a trailing port dropped and then one leading `events.` label, under the scheme `X-Forwarded-Proto` names when it is exactly `http` or `https`, `https` otherwise. The pages read `Config.ServicesPath` only for these addresses; the icon, the home link and the tools flag come from the kit.

## The trail

appkit's banner draws the page's place below events' landing page as a trail of levels after the root, each a `page.Level`; `Kit.Banner` always returns an empty `Trail`, and the app sets the levels on the banner it got before it renders (appkit's D02). events has one level of hierarchy: the landing page is the root and its trail is empty; the about screen's trail is exactly one level, named `about` and linking to `/about`; the tools page's is exactly one level, named `tools` and linking to `/tools`. The name is the path segment, as the suite's banner decisions fix it. No page of events lies below these. The notice pages, not found and unavailable, draw appkit's footer and no banner, and their banner is the notice banner exactly as the source returned it, whose trail the kit leaves empty; the 405 events answers on a page path draws no page at all (`D06-serve`). The pages replace whatever `Trail` the source returned, so a test proves a level by handing `Config.Banner` a function of its own that returns a banner whose `Trail` it chose, and comparing the body with the named template executed with the levels this design states. A wrong URL on the current level shows only through appkit's page menu, whose current row is the tools row only when the banner's `Tools` is true and the trail is exactly the one level linking to `/tools`; so a test proving the tools page's trail hands a banner whose `Tools` is true; the about screen's needs no such flag.

## Proving a page

A test proves a page by executing the named template of events' template set with the data the requirements state and comparing the answer's body with what that writes, or by checking that a value it supplied appears in the body; it never looks for a word, a tag, a class or an id. A template that cannot show a state this design names is an issue, never a change to the asset.

What a browser does with a page is outside this design: the buttons' feedback is the behaviour of appkit's `feedback.js`. events serves that file and its templates carry what it acts on; its tests have no browser and do not exercise the script.
