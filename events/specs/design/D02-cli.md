# D02-cli

events as a command: what `cli.Run` does with the arguments `D01-layout-and-run-seam` hands it through `Process`, and the constants the binary carries about itself. This design covers the four commands (`--version`, `manifest`, `--help`, `db status`), the usage error, the exit codes, the usage text, the manifest, the nginx fragment, and the two files under `etc/` that copy the last two. When `Args` is empty, events serves, and everything from there is `D03-settings` (the settings and their refusal) and `D06-serve` (the socket, the log, readiness, the drain and their failures).

`Run` takes at most three arguments and the arguments decide everything. An empty `Args` means serve. The three recognised single arguments each write one product to `Stdout` and return `ExitSuccess` without touching the environment: `--version` writes `Process.Version`, the display string `main` read (`D01-layout-and-run-seam`), and a newline, which is one empty line when the host set no identity, `manifest` writes `Manifest`, and `--help` writes `Usage`. The one two-word command is `db status`. Any other `Args` is a usage error, and the argument events complains about is the first one it does not take: the first element when that is not a recognised word; `db` itself when it stands alone, since `db` is not a command by itself; the word after `db` when that is not `status`; the word after `db status`, which takes nothing; and otherwise the second element, which is surplus after `--version`, `manifest` or `--help`. An argument that starts with `-` is an unknown option; any other is an unknown command. Both diagnostics follow the repository's command-line conventions: the first line begins `events: `, and after exactly one empty line comes the hint to run `events --help`, unprefixed because events is speaking for itself. The usage text is never written to `Stderr`.

`db status` is an operator's look at the log: which of the migrations the binary carries `state/events.db` has had applied, and when, which it has not, and any it records that the binary does not carry. What it prints, line by line, is appkit's `db.Status`, called with the path `state/events.db` resolved against `Process.Dir` and the migrations `events.Migrations()` returns, writing straight to `Stdout`. events adds nothing to the lines and states nothing about their format, so a test compares `Run`'s output with what its own `db.Status` call writes for the same database. `db.Status` only looks: it applies nothing, and creates nothing when no database exists (probed against the installed appkit: an absent database reports `0001 pending` and leaves no `state/` behind). When it returns an error, events says so on one line, `events: ` and the error's text, and exits 1. Whatever `db.Status` had already written to `Stdout` stays there, since findings are product; a database that cannot be read yields no lines at all (`invalid SQLite database header`, probed). A database that records a migration this events does not carry, one a newer events upgraded, is not a failure: older code runs on newer data (`D06-serve`), appkit's `db.Status` lists every line, the unknown versions among them as `unknown`, and returns nil (probed against the installed appkit: a database recording `0001` to `0003` under migrations holding only `0001` gives three lines and a nil error), so `db status` writes nothing to `Stderr` and exits 0. `db status` reads no environment, takes no socket and reads no clock.

The help text names the exit codes: 0 for success, 1 for a failure, 2 for a usage error. The constants are `ExitSuccess`, `ExitFailure` and `ExitUsage`. `D03-settings` and `D06-serve` lean on that split: a start the caller got wrong (a setting that is not a positive whole number, no socket, several sockets) exits 2, while trouble on the host once events is past its checks (a log it cannot open, a drain that runs out) exits 1, as does a `db status` whose database cannot be read.

Arguments are checked before anything else. A command never needs a socket and only `db status` reads a database, so `events --version` succeeds with nothing passed in and `events bogus` fails whatever the environment holds; `Run` touches none of the environment, the inherited descriptor, the notification socket, the clock, the timers, the random source or the sink unless `Args` is empty. A command records nothing in the trail: the trail is what events records while it serves. Only `db status` reads anything under `Dir`, and it creates nothing there when no database exists; every other command and every usage error leaves `Dir` as it found it.

Every failure but the one `db status` case leaves `Stdout` empty, and every diagnostic is one write to `Stderr`, so a two-line diagnostic lands whole even when journald interleaves another writer.

## The manifest and the fragment

The manifest is a fact about the binary, so the binary carries it as `Manifest`, holding exactly the text the bootstrap story shows: events' name; its description, the same string the about screen shows as `pages.Description` (`D08-pages`) and the host publishes in its services file; that it is not the host's default app; that it is one of the suite's MCP services; no secrets; its six settings with their defaults, which are `settings.Defaults()`'s values (`D03-settings`), so the defaults the host writes into the app's environment file, `/etc/opt/ikigenba/events/env`, are the ones events applies when a setting is unset; and its SQLite database. It declares no `guests`, no `port`, no `[resources]` table and no `DRAIN_SECONDS`, which is the space's.

The nginx fragment is `NginxConf`, the one directive the public `/emit` needs: the host's nginx includes an app's `etc/nginx.conf` in the server block for its public name, and an exact-match location (nginx's `ngx_http_core_module` `location` directive: an exact match ends the search) answering `return 404` (`ngx_http_rewrite_module`) answers `/emit` through nginx with 404 for every method before any other location, while the same path on the socket still takes every sibling's events. What that does on a host is `D11-on-a-space`'s. Nothing prints the fragment: the bootstrap story fixes the commands, and a command that printed it would be a story change.

The committed `etc/manifest.toml` and `etc/nginx.conf` are copies the build run writes from the constants, and the root package embeds them (`D01-layout-and-run-seam`), so a test proves each copy equals its constant by reading `events.Etc()`, never the checkout. `devctl build` refuses an app whose `manifest` disagrees with the committed `etc/manifest.toml`; the release file's members and their listing (`S16`) are devctl's and `D11-on-a-space`'s.

## Consumer tasks

`events --version`: `cli.Run(ctx, cli.Process{Args: []string{"--version"}, Stdout: &out, Stderr: &errw, Dir: t.TempDir()})` with `Version: "r1 (abc1234)"` returns `cli.ExitSuccess` with `out` holding `"r1 (abc1234)\n"`, and with `Version` left empty, `"\n"`. `events manifest` and `events --help` are the same with `cli.Manifest` and `cli.Usage`. `events db status` over a log the test made with `db.Open` under `Dir` writes what `db.Status(ctx, db.Config{Path: filepath.Join(dir, "state", "events.db"), Migrations: events.Migrations()}, &want)` writes. `events bogus` returns `cli.ExitUsage` with `events: unknown command 'bogus'\n\nsee 'events --help' for usage\n` on `Stderr`. A test of the copies reads `fs.ReadFile(events.Etc(), "etc/manifest.toml")` and compares it with `cli.Manifest`, and `etc/nginx.conf` with `cli.NginxConf`; a test of the manifest's agreement finds the `description` line and the `[env]` lines in `cli.Manifest` and compares them with `pages.Description` and `settings.Defaults()`.
