# D06-serve

The serve path: what happens between `cli.Run` being called with no arguments and the process being gone, how `server.Run` starts, serves and stops, and the rules `web.Handler` keeps on every route — the identity gate, the exact paths, `/emit` mounted outside both the identity gate and the request records, `/mcp`, the shared files under `/_appkit/`, and the answer for a method a page does not take or a path that names nothing. `D01-layout-and-run-seam` declares `cli.Process` with its `Version`, the display string of the identity `main` reads, `cli.Run`, the exit codes and how `main` builds the real process; `D03-settings` declares `settings.Read` and the order and wording of the seven settings' refusals; `D04-store` declares the store, its `Sweep`, its `Declarations`, and the `events.Sink` it is; `D05-declarations` declares `declarations.Declarations` with its `Refresh` and `Ask` and `declarations.AskTimeout`. This design declares the `server` and `web` packages and says how `Run` takes the socket, opens the log, wires every part over it, and hands them to `server.Run`. What a page shows is `D08-pages`; what the tools answer is `D09-tools`; how the delivery loop delivers, retries, pauses, and gives up an attempt at the drain deadline is `D07-delivery`; the trail as a whole, the records of each request and each tool call among it, is `D10-trail`.

## The terms events serves on

events serves only on a listening socket it inherits, the way `sd_listen_fds(3)` documents: `LISTEN_PID` is its own process id, `LISTEN_FDS` counts the sockets passed, and the first is file descriptor 3. Anything else — `LISTEN_FDS` unset, empty, `0` or not a number, `LISTEN_PID` unset or naming another process — is no socket passed in; a count above one is a unit events will not guess about. Both are usage errors, each with the detail line saying how to run events, and both come only after `settings.Read` (`D03-settings`) has accepted the environment, so a bad setting is reported whether or not a socket was passed. A refused start takes no descriptor, unsets nothing, opens no database, sends no datagram, and records nothing. With exactly one socket, `Run` removes `LISTEN_PID`, `LISTEN_FDS` and `LISTEN_FDNAMES` through `Unsetenv` and takes descriptor 3 through `Process.Inherit`, or with `net.FileListener` over the real descriptor when `Inherit` is nil. The Go `net` documentation states that a listener `FileListener` makes does not unlink the socket file when closed, and closing is all events ever does to it, so the path systemd made stays and systemd's own copy keeps queueing connections for the next events.

The environment also carries `IKIGENBA_SERVICES`. `Run` looks it up once, before it serves, and hands the path on: to `declarations` (which services to ask), to `delivery` (where each subscriber's socket is), to `pages` (auth's addresses on the banner, whose other fields come from `Process.Banner`), and to the MCP server's instructions. Each reads the file afresh when it needs it. Nothing about the variable or the file can stop a start. The same environment may carry `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE`, the code the host is running; only `main` reads them, through appkit's `version.Read`; it hands the identity to `page.New`, whose banner carries the release and the commit the pages' footer and about screen show, and `Run` takes the identity's display string as `Process.Version` (`D01-layout-and-run-seam`) and shows it as events' version in its `service.started` and its MCP `serverInfo`. Neither is ever a reason not to start: with neither set the string is empty and events serves all the same.

## The log

With the listener in hand, `Run` opens the **database path**, `state/events.db` resolved against `Process.Dir`, through appkit's `db.Open` with `events.Migrations()`, `Process.Now`, the service `events.ServiceName` and `Process.Stderr` as the writer for appkit's warning; appkit creates the directories and the file, applies the migrations the database has not had, and refuses one it cannot open. How it does each is appkit's contract; events' tests prove the wiring, by comparing `db.Status` of the database a start made with that of one the test made itself. When `db.Open` fails the start is refused with one line, `events: cannot open database state/events.db: <reason>`, the relative path whatever `Dir` is, any newline in the reason turned into a space, exit 1, before anything is served, before systemd hears anything, and before anything is recorded.

A database a newer events has upgraded, as after a deploy rolled back, records a migration this events does not carry. It is not refused: data never rolls back, so older code runs on newer data. appkit's `db.Open` applies nothing to it and writes one warning line, beginning with the service name it was given and naming the lowest version this events does not carry, to the writer it was given, `Process.Stderr`, in one write (probed against the installed appkit: `events: unknown migration version 0002: database is ahead of this binary`, one `Write`); under systemd that line reaches the journal. It is written before `READY=1`, it is the whole warning, and the trail records nothing about it. Then the start goes on exactly as over any database: the sweep, the declarations refresh, `READY=1`, `service.started`, and serving the log the database holds. events states nothing about the line's wording: a test compares what `Run` wrote with what its own `db.Open` call, given the same service name and a buffer, writes over the same database, and that the line begins `events: ` is what shows `Run` handed appkit events' name. The test makes such a database with its own `db.Open` and `DB.Write`, as `AGENTS.md` allows, recording a version above every one `events.Migrations()` holds.

Over the handle `Run` builds, in one place, everything that serves: the run's telemetry writer (service `events`, version `Process.Version`, sink `Process.Sink`, stderr `Process.Stderr`, and the process's clock, sleep and random source); the store, with `EVENTS_DEPTH_MAX` and the declarations' `Ask` for an undeclared name; the declarations, over the services path and `Process.AskAfter`; the MCP server, named `events`, with version `Process.Version` and instructions read from the services file's `events` entry on every request that asks, and the five tools registered on it; the pages, given the tools that server then offers, each as a `pages.Tool` holding the `Name` and `Description` appkit's `Server.Tools` returns for it, in registration order, so the tools page lists exactly what `tools/list` names; the handler; and the delivery loop over the services path, the settings and `Process.TimeoutAfter` and `Process.BackoffAfter`. Then it calls `server.Run` with the listener, the handler, the store, the declarations, the loop, the writer, `NOTIFY_SOCKET`, the retention window, the refresh interval, the drain, `Process.Now`, `Process.SweepAfter` and `Process.RefreshAfter`.

## server.Run: start

`server.Run` makes the start. It sweeps the log once, removing what `store.Store.Sweep` removes for the moment `Now()` less the retention window, so an events that was stopped for a while never serves a stale log; a sweep that fails is routine, not trouble, and the start goes on. It refreshes the declarations once and waits for that refresh to end, every ask answered or past its deadline, so the services' answers are held before the first emit is taken and the `sibling.called` records of the asks come before `service.started`. Then it sends `READY=1` to the notify socket, as `sd_notify(3)` documents (a name beginning with `@` is in the abstract namespace), then records `service.started` through `Writer.Ready`, then starts the delivery loop and accepts connections. Ready is true before the first `Accept` because systemd's socket has queued every connection since it was made; a datagram that cannot be sent is trouble, so `Run` returns an error and nothing is served. Delivery starts only after `service.started`, so every `sibling.called` of a start is a declaration ask. What `systemctl start` and `systemctl restart` report — exiting 0 once events is ready, or reporting a failure when events exits before it is — is systemd's handling of a `Type=notify` unit, as `systemd.service(5)` documents; events' part is sending `READY=1` only once it can serve, and exiting non-zero when it cannot, which the requirements below state.

While it serves, two timers run. Each hourly sweep waits on `SweepAfter(time.Hour)`, sweeps at the clock's moment when it fires, and arms the next; the sweeps follow the start by whole hours rather than the wall clock's. The refreshes keep a fixed period from one start to the next instead: the first wait on `RefreshAfter(Refresh)` is armed as the start refresh begins, and each time a wait fires the next is armed at once, before the refresh that tick begins has ended, so a service that never answers delays no later ask. A tick that fires while an earlier refresh is still running begins none; it is skipped, and the next tick comes a full period later. A test fires either timer by sending on the channel it handed back, and sees the next wait armed while a sibling it holds keeps the refresh running.

## server.Run: stop

When the context is done `Run` closes its listener — new connections wait in the socket's queue for the next events — drops idle connections, arms no timer and starts no sweep or refresh. The delivery loop's `Run` returns, starting no attempt after it; `Run` then calls the loop's `Drain` with a context that ends at the **drain deadline**, `Drain` after the context was done, in real time, while the requests already accepted, a sibling's post to `/emit` among them, finish within the same deadline. When both are done before the deadline, `Run` calls `Writer.Shutdown` with the reason, the text of `context.Cause(ctx)` (`SIGTERM` or `SIGINT` in the binary), on a context that ends at the deadline: `service.stopping` is recorded last, after every finished request's `request.finished` and every outcome the loop recorded in its drain, and `Run` returns nil once it is delivered, without waiting out the deadline. A delivery still unanswered at the deadline is the loop's to abandon (`D07-delivery`); it is not a request, so `Run` still returns nil, and the writer, out of time, writes `service.stopping` to stderr as an `undelivered event` line. appkit's writer, handed a context already done, cancels its own sending before the event can be taken, so a `service.stopping` written that way never reaches telemetry as well (the installed `telemetry.Writer.Shutdown`). A request still running at the deadline is cut off: `Run` calls `Shutdown` first, so the `service.stopping` line is written before any connection is closed, then closes those connections without the rest of their answers and returns a `*server.DrainError` counting them; `cli.Run` writes `events: stopped with <n> requests unfinished` (`1 request` for one) as its last line and exits 1.

`server.Run` requires of the `Delivery` it is handed what `delivery.Loop` (`D07-delivery`) promises: `Run` returns once its context is done, and `Drain` returns once every attempt in flight has ended or its context is done. Of the store and declarations it needs only their declared methods. `server.Run` writes nothing of its own to any stream: `net/http`'s server logs through `log`'s standard logger when `Server.ErrorLog` is nil (the `net/http` documentation of `Server.ErrorLog`), so it gets one that discards. No read, write or idle timeout is contract; the build sets `ReadHeaderTimeout` for gosec `G112` and no write timeout that could cut a response short inside the drain.

## The handler's routes

`web.Handler` splits its surface at the door, on the request's `URL.Path` compared exactly, never redirecting. A request whose path is exactly `/emit` goes to appkit's `events.EmitHandler` over `Config.Sink` and nowhere else: no identity is looked for, since a sibling, not a caller, posts there, and the handler records nothing for it, so an emit adds no `request.started` or `request.finished`; what it answers (405 with `Allow: POST`, 415, 413, 400, 204, 422 for a sink error wrapping `events.ErrRejected`, 500 otherwise, every body empty) is appkit's, proved by the installed module.

Every other request goes through appkit's `telemetry.Middleware` over `Config.Telemetry`, wrapping `identity.Require`, wrapping the routes: so a request without `X-User-Id` is answered 500 with appkit's `identity.MissingBody` before its path or method is looked at, and every such request records its two events (`D10-trail`). With identity: `/`, `/tools` and `/about` take `GET` and `HEAD`, answered by `Pages.Landing`, `Pages.Tools` and `Pages.About`, and every other method is 405 `Allow: GET, HEAD` with an empty body; `/mcp` exactly goes to the MCP server, which answers a method other than `POST` 405 `Allow: POST` with an empty body and answers whatever `Host` names; a path beginning `/_appkit/` goes to appkit's `page.Static()`, which compares the whole path against the shared files it serves and answers anything else with a bare 404, never events' not-found page; and every other path, `/mcp/`, `/emit/`, `/about/`, `/tools/`, `/assets/...` and `/_appkit` among them, is answered by `Pages.NotFound` whatever the method. The page methods are called only for those requests, and always with the caller in the request's context. The shared-file answers events relies on are stated below as events' own behaviour, so events' tests fail if a release of appkit stopped giving them; they agree with what the installed `page.Static` answers. That a file's `ETag` follows from its content alone is `page.Static`'s doing: it is the SHA-256 of the file's bytes, in hex, between double quotes, so two binaries carrying the same file give the same tag and a changed file a new one; events states only the shape of the tag and its sameness within one binary. `page.Static` sets the file's `Content-Type` before it compares `If-None-Match`, so a file sent again to a browser whose copy is out of date carries the same type as a plain `GET` of it.

Five shared files are served under fixed names: `theme.css`, `feedback.js`, `favicon.svg`, `OFL.txt` and `TABLER-LICENSE.txt`. The fonts are served only under **font paths**, names appkit derives from a hash of each font's bytes, so that a browser may keep a font for a year and an appkit release that changes one changes its URL; the plain names a font file carries in appkit are not served, and answer the bare 404. events never writes a font's name or hash: the font paths are the path `page.PreloadURL()` returns, which every page preloads (`D08-pages`), and the paths the served stylesheet names, each a `url("…")` of a name ending in `.woff2` beside the stylesheet under `/_appkit/`. A test learns them the same way, from `page.PreloadURL()` and from the stylesheet events serves. A font path's 200 and 304 carry `Cache-Control: public, max-age=31536000, immutable`, so a browser keeps the font without asking again; every other shared file's carry `Cache-Control: no-cache`, so a browser keeps its copy but asks each time.

- R-DENE-Y2ZL: A handler `web.Handler(cfg)` returns MUST answer a request carrying a non-empty `X-User-Id` whose path is an appkit path and not a shared file path — `/_appkit/`, `/_appkit/banner.html`, `/_appkit/nope.css`, `/_appkit/theme.css/`, `/_appkit/theme.css/x` and `/_appkit/THEME.CSS` included — whatever its method, with status 404 and without calling `cfg.Pages.NotFound`.
- R-HZLG-QTUF: For every font path that ends in `.`, then one or more hexadecimal digits, then `.woff2`, a handler `web.Handler(cfg)` returns MUST answer a request carrying a non-empty `X-User-Id`, whatever its method, whose path is that font path with that `.` and those hexadecimal digits removed, with status 404 and without calling `cfg.Pages.NotFound`.
- R-DFVB-BUQA: A handler `web.Handler(cfg)` returns MUST NOT treat `X-User-Email` as a precondition: a request carrying a non-empty `X-User-Id` and no `X-User-Email` header MUST NOT be answered with status 500 on that account.
- R-DH37-PMGZ: A handler `web.Handler(cfg)` returns MUST NOT add a `Set-Cookie` header to any response it gives itself or through `page.Static()`, `events.EmitHandler` or `cfg.MCP`.
