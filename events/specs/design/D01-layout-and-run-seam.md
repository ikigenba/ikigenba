# D01-layout-and-run-seam

events is the suite's internal event bus: one Go binary, behind the host's nginx at `events.<space>`, that takes the events every service emits to its socket at `/emit`, checks each against what its producer declared, keeps them in a retained log in its own SQLite database, and delivers each, in order, to every service that accepts it. It offers five MCP tools at `/mcp` (`catalog`, `search`, `subscribers`, `skip`, `resume`) and serves a landing page of its subscribers at `/`, a page listing those tools at `/tools` and an about screen at `/about`, all to a signed-in user only. This design is the structural ground the other designs stand on: where the code lives, which package owns which concern, the root package's embedded files, where the version events shows comes from, the seam through which the process is run so that the command, the server, the store, the declarations, the delivery loop, the pages and the tools can be tested without a real process, and what `main` hands that seam.

The module is `github.com/ikigenba/ikigenba/events`, rooted at the sub-project directory, with `go.mod` beside `specs/`. Its `main` package sits at `cmd/events`, because `devctl build` finds an app as a `package main` in `cmd/<app>` under the directory that holds `etc/manifest.toml`. `cmd/events` is wiring only.

## The dependency

events depends on one module besides the standard library: `github.com/ikigenba/ikigenba/appkit`, required at a published release with no `replace` directive. Which release is data: `AGENTS.md` and `go.mod` name it, and no requirement names a version. The SQLite driver arrives through appkit's `db` package; events never imports it.

appkit is a sibling, reached only through its published packages. events uses eight of them. `db` gives the log's handle (`db.Open`, `DB.Read`, `DB.Write`, `DB.Close`, `DB.SetFailing`) and `db.Status`, the read-only report of which migrations a database has had. `events` gives the suite's event contract: `events.Event`, `events.Sink`, `events.EmitHandler` mounted at `/emit`, `events.ErrRejected`, the declarations path and shape, `events.Send` for a delivery, and `events.ServiceName`, `"events"`, the one name events goes by: the service the writer names, the banner's service, the MCP server's name and the services-file entry events never asks or delivers to. `telemetry` gives the trail's machinery: the writer, the request middleware, `telemetry.SiblingClient` and `telemetry.SocketTransport` for every call events makes to a sibling's socket, `telemetry.Capture` for tests, and `telemetry.NewSocketSink`, which finds the telemetry service afresh in the services file for every event. `page` gives the banner, the footer, the font preload, the template set and the shared files under `/_appkit/`. `identity` gives `identity.Require`. `mcp` gives the server mounted at `/mcp` and the client the tests drive it with. `services` gives `services.Read` and `List.Find`, through which every reader of the services file finds its entries, and `services.Variable`. `version` gives the code identity the host hands every app: `version.Read()` reads `IKIGENBA_COMMIT` (`version.CommitVariable`) and `IKIGENBA_RELEASE` (`version.ReleaseVariable`) from the process environment when it is called and returns them as a `version.Identity`, the release and the short commit, each empty when its variable is unset; `Identity.String()` is the **display string** built from them, the empty string when neither is set, and `version.Display()` returns the same string for the environment at its call. appkit owns the contracts of all of these; events restates none of them.

## Where the environment is read

`main` calls `version.Read` exactly once, before it calls `Run`, hands the `Identity` it returned to `page.New`, and passes its `String()` as `Process.Version`: the identity is what the pages' footer and about screen show, the release and the commit apart, and the display string is the version events shows everywhere else. So a start reads the two variables once, and `--version`, a run of its own, reads them once too. Nothing below `main` calls `version.Read` or `version.Display`, and `Run` never asks `LookupEnv` for either variable (R-ZX69-H5FK), so an in-process test hands `Run` any string it likes, the empty string included, and sets neither variable.

Nothing else below `main` reads the real environment, with one exception events cannot route: appkit's `mcp.NewServer` reads `IKIGENBA_SERVICES` (`services.Variable`) from the process environment when it is called, and uses the value only when `ServerConfig.Instructions` is nil. events always supplies `Instructions`, built from the services path `Run` looked up through the seam, so the value `mcp.NewServer` reads decides nothing; a test that reaches that call still sets the variable with `testing.T.Setenv`, as `AGENTS.md` asks. appkit's `page.New` reads the variable too, once, when it is called, and offers no form that takes the path from a caller, so `main` calls it, once, before `Run`, as `page.New(events.ServiceName, id)` with `id` the identity it read, and hands the kit's `Banner` method to `Run` as `Process.Banner`; the pages get every banner from it (`D08-pages`). A test of `Run` hands a banner source of its own, a kit it made after setting the variable with `testing.T.Setenv` or a function of its own. The trail's sink is on the seam: `main` passes `telemetry.NewSocketSink()`, which reads the real environment on every delivery, as only `main` may; a test passes a `*telemetry.Capture` or a sink of its own.

## Packages

The module's root package, `events`, holds what only it can embed, since Go's `embed` reaches only files at or below the embedding package's directory. It exports `Assets`, the five human-authored templates in `assets/` (`landing.html`, `tools.html`, `about.html`, `notfound.html`, `unavailable.html`), which `D08-pages` parses and executes; `Migrations`, the log's schema as numbered migrations, of which this events carries one, `0001_log.sql` (`D04-store` declares what it creates); and `Etc`, the two committed files under `etc/`, `manifest.toml` and `nginx.conf`, whose contents `D02-cli` fixes. Each is the same on every call and depends on no file beside the binary. A later migration is a new file with the next four-digit version; none is edited once released.

Nine internal packages hold the concerns, one each:

- `internal/cli` owns the program as a command: the run seam (this document), the exit codes, the usage text, the manifest, the nginx fragment and the commands (`D02-cli`), and the serve path, which builds every package below and hands each what it needs (`D06-serve`).
- `internal/settings` owns the seven values events reads from its environment at start, their defaults, their spelling and the refusal of one that is not acceptable (`D03-settings`).
- `internal/store` owns the log: the schema, the `events.Sink` that takes an emitted event, the held declarations, the subscribers and their cursors, the catalog, the search, and the sweep (`D04-store`).
- `internal/declarations` owns asking each enabled service what it emits and accepts, and keeping the answers through the store (`D05-declarations`).
- `internal/web` owns the one handler: routing by exact path, `/emit` mounted outside identity and the request middleware, `/mcp`, `/_appkit/`, and the answers for a method a route does not take and a path that does not exist (`D06-serve`).
- `internal/server` owns the serving life: the start's sweep and refresh, readiness, the hourly sweep and periodic refresh, starting and draining delivery, the drain and the stop (`D06-serve`).
- `internal/delivery` owns the delivery loop (`D07-delivery`).
- `internal/pages` owns the pages' data and rendering (`D08-pages`).
- `internal/tools` owns the five MCP tools (`D09-tools`).

Dependencies point one way: `cmd/events` imports `internal/cli` and appkit's `telemetry` and `version`; `internal/cli` imports the root package and every internal package; `server` imports `store` and `declarations` and reaches delivery through its own `server.Delivery` interface; `web` imports no internal package and reaches the pages through its own `web.Pages` interface; `delivery`, `declarations` and `tools` import `store`; `pages` imports the root package and `store`; `delivery` imports `settings`; `store`, `settings` and the root package import nothing of events'. Which package imports which is not observable, so this paragraph is guidance, not a requirement.

## The run seam

The run seam is `cli.Run`. It takes a context and a `cli.Process` carrying everything the program would otherwise take from the `os` package, and returns the exit code. `main` fills `Process` from the real process and cancels the context on a signal, with the signal's name, `SIGTERM` or `SIGINT`, as the cause; a test fills it with buffers, a map, a pid and a display string of its choosing, a listener it bound itself, a clock, timers and a pause it controls, a reader of known bytes, a temporary directory of its own as `Dir`, and a `*telemetry.Capture` as `Sink`.

Socket activation hands the process its listening socket as descriptor 3, and `Inherit` is the one step below the seam that touches a real descriptor: `main` leaves it nil, so `Run` takes descriptor 3; a test returns a listener it bound. The environment half of the protocol (`LISTEN_PID`, `LISTEN_FDS`, `NOTIFY_SOCKET`) arrives through `LookupEnv` with the settings and `IKIGENBA_SERVICES`, and removing the `LISTEN_*` variables goes through `Unsetenv`. What `Run` does with them is `D06-serve`'s.

Time is injected because events stamps and schedules by it. `Now` is the one clock: an event's `received`, a subscriber's `since`, the moment a sweep subtracts the retention window from, every event of the trail, and the time each migration is recorded as applied at. Each wait events schedules has a timer of its own, a `func(d time.Duration) <-chan time.Time`, so a test fires one without the others: `SweepAfter` between one sweep and the next (`D06-serve`), `RefreshAfter` between one refresh of the declarations and the next (`D06-serve`, `D05-declarations`), `AskAfter` for one declarations ask's deadline (`D05-declarations`), `TimeoutAfter` for one delivery attempt's deadline and `BackoffAfter` for the wait before a delivery's next attempt (`D07-delivery`). `Sleep` is the pause the telemetry writer waits between its attempts to hand an event to its sink. The drain deadline is measured in real time, never through these, because the drain is the one wait `AGENTS.md` lets a test keep to a few real seconds. `Rand` is the source the request ids are drawn from. Each nil field means the real thing: `time.Now`, `time.After`, a context-aware pause, `crypto/rand.Reader`.

`Dir` is the directory `Run` resolves `state/events.db` against. `main` leaves it empty, so the log is `state/events.db` relative to the working directory, `/var/opt/ikigenba/events` on a host; a test sets a temporary directory, so two `Run`s given the same `Dir` share one log and two given different ones do not. There is no field naming another database: appkit's `db` takes only a file path.

`Sink` is where every event of the trail goes. It is required: `Run`'s behaviour with a nil `Sink` is not contract, so `main` passes `telemetry.NewSocketSink()` and every test passes its own.

## The version

events carries no version of its own: nothing in its source or its build names one. `Process.Version` is the one version string events shows, the display string of the identity `main` read: `events --version` (`D02-cli`), the MCP `serverInfo` and the run's writer, whose `service.started` carries it as `version` (`D06-serve`). The footer and the about screen show the identity's release and commit apart, from the banner of the kit `main` makes with `page.New` from that identity and hands `Run` as `Process.Banner` (`D08-pages`). Its value is data the host supplies at run time; no test spells one.

## Decisions

- The seam is named `cli.Process`, as in both precedents. Five timer fields rather than one, so a test fires the sweep, the refresh, an ask's deadline, a delivery's deadline or a backoff without firing the others.
- `Sink` is on the seam and required, rather than defaulting to the socket sink below `main`: that default would read the real environment on every delivery, which `AGENTS.md` lets only `main` do.
- A `Banner` field and no `MCP` field: `page.New` reads the services path from the real environment and its kit's `Banner` is the suite's one way to build a banner, so `main` calls it and the seam carries the method, as in the telemetry and sites precedents; the one environment read `mcp.NewServer` makes decides nothing because `Instructions` is always supplied, so `Run` builds the server itself.
- `Etc` returns an `embed.FS`, so its type alone proves the bytes come from a `//go:embed` of the committed files; `Assets` and `Migrations` return an `fs.FS` holding their files at the root, as `page.Templates` and `db.Config.Migrations` take them.
- The version is a `Process` field rather than something `Run` reads, as in the dummy precedent: `main` is the one place that reads the identity, and `Run` uses the field for `--version`, the MCP server and the writer, so in-process tests prove every use of it with a string of their own. Unlike dummy, events builds its MCP server inside `Run`, so no binary-level requirement about `serverInfo` is needed: `Run`-level tests prove it shows `Process.Version`, and the binary-level ones prove `main` hands it the display string. The pages' banner and footer come from the kit `main` makes, so one binary-level requirement (R-5MS9-KEY1) proves `main` built it with `events.ServiceName`, the run's identity and the services file the child was started with: on a start whose services file also holds an `events` entry with an icon and `mcp` true, the about screen must be exactly what the pages write with a kit the test made the same way, so a kit with the wrong name, the display string as its release, or no services path shows.
- What `main` hands the seam is proved only at the binary, by the one exec'ing test `AGENTS.md` admits: it runs `--version` with non-empty `IKIGENBA_COMMIT` and `IKIGENBA_RELEASE` in the child's environment and again with neither, `manifest`, `bogus`, a bare start with no socket, and a start on a socket it passes as descriptor 3, whose trail goes to a `telemetry` entry the test holds, stopped by `SIGTERM` and in a second run by `SIGINT`. It computes the display string and the identity it expects by calling `version.Display` and `version.Read` after setting the same two values with `testing.T.Setenv`, so the expectation rests on appkit's promise and no test spells a version; with neither variable set it expects one empty line.

## Consumer tasks

The binary's start: `main` calls `cli.Run` with a `cli.Process` whose `Args`, `LookupEnv`, `Unsetenv`, `Pid`, `Stdout` and `Stderr` are the real process's, whose `Version` is `id.String()`, `id` being what `version.Read()` returned, whose `Banner` is the `Banner` method of `page.New(events.ServiceName, id)`, whose `Sink` is `telemetry.NewSocketSink()`, and whose `Dir`, `Inherit`, `Now`, `Sleep`, `Rand` and timers are left zero, under a context it cancels on `SIGTERM` or `SIGINT` with a cause whose `Error` is the signal's name; it exits with what `Run` returns.

A test of the run seam builds a `cli.Process` with a `Version` of its own, such as `id.String()` for `id := version.Identity{Release: "r1", Commit: "abc1234"}`, or `""`, a temporary `Dir`, a `LookupEnv` and an `Unsetenv` over one map, an `Inherit` returning a listener it bound on a Unix socket in a short temporary directory, `NOTIFY_SOCKET` naming a datagram socket it holds, a fixed `Now`, timers returning channels it owns, a `Rand` of known bytes, a `*telemetry.Capture` as `Sink`, and as `Banner` the `Banner` method of `page.New(events.ServiceName, id)` called after it sets `services.Variable` with `t.Setenv`; calls `cli.Run` with a context from `context.WithCancelCause`; waits for `READY=1`; drives the listener with `mcp.Client` and raw HTTP; cancels with `errors.New("SIGTERM")`; and inspects `Dir`, the capture and the streams. A test of the root package lists and reads `events.Assets()`, `events.Migrations()` and `events.Etc()` with `fs.ReadDir` and `fs.ReadFile`, from a working directory of its own made with `t.Chdir`.

## The documents

`D02-cli` is the command, the exit codes, the usage text, the manifest, the nginx fragment and the two files under `etc/`. `D03-settings` is `internal/settings` and the refusal of a start whose settings are not acceptable. `D04-store` is the log. `D05-declarations` is asking the services. `D06-serve` is the serve path, `internal/server` and `internal/web`. `D07-delivery` is the delivery loop. `D08-pages` is the pages. `D09-tools` is the five tools. `D10-trail` is the trail as a whole. `D11-on-a-space` is what events is on a host and in a sandbox.
